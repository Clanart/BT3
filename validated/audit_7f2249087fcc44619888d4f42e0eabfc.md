Based on the investigation, I found a concrete analog: the `checkRun.htmlUrl` from the CI Checks API is passed directly to `dispatcher.openInBrowser` (which is a thin wrapper over `shell.openExternal`) without any protocol allow-listing, unlike the markdown link path which does enforce `/^https?:/` before forwarding a URL.

### Title
Attacker-controlled CI check-run `htmlUrl` forwarded unvalidated to `shell.openExternal` - ([File: app/src/ui/check-runs/ci-check-run-popover.tsx])

### Summary
`CICheckRunPopover.onViewCheckDetails` and `onViewJobStep` take the `htmlUrl`/step URL fields straight from the GitHub Checks API response and pass them to `dispatcher.openInBrowser(url)`, which resolves to `shell.openExternal(path)` in the main process. Neither the renderer call site nor the main-process IPC handler restricts the accepted protocol.

### Finding Description
`onViewCheckDetails` builds `url` from `checkRun.htmlUrl` (an attacker-influenceable field: any GitHub App/Action/CI integration the PR author or a malicious fork controls can set an arbitrary `details_url`/`html_url` for a check run) and calls `this.props.dispatcher.openInBrowser(url)` with no scheme check: [1](#0-0) 
This differs from the markdown-link path, `SandboxedMarkdown.setupLinkInterceptor`, which explicitly restricts forwarded URLs to `https?:` before invoking `onMarkdownLinkClicked`: [2](#0-1) 
`dispatcher.openInBrowser` / `_openInBrowser` is a direct pass-through to `shell.openExternal`: [3](#0-2) 
And the main-process IPC handler for `open-external` performs no protocol filtering at all — it only logs when the string happens to start with `http(s)://`, then unconditionally calls Electron's `shell.openExternal`: [4](#0-3) 
So a check run's `htmlUrl` (or `getCheckRunStepURL` result) that is not an `https://` URL — e.g. a `file://` path, a Windows UNC path, or another OS-registered custom protocol — reaches `shell.openExternal` unfiltered.

### Impact Explanation
Depending on OS/Electron shell handling, forwarding an attacker-supplied non-http(s) string to `shell.openExternal` can result in launching arbitrary local files/executables or handing off to another installed protocol handler, which is the same class of primitive as the report's "unprotected forwarder" (attacker-supplied data is passed through unchecked into a sensitive sink). This is not the sandboxed-markdown path (which is protected), but a second, less-guarded invocation path reachable from data returned by third-party CI integrations tied to a repository/PR the user has opened in Desktop.

### Likelihood Explanation
Requires the victim to open a pull request with checks from a CI integration/app the attacker controls (e.g., a PR from a fork, or a CI provider the attacker configured) and click "View check details" or a job step link — a normal, expected user interaction, not a special "unnatural" step. `checkRun.htmlUrl` and `getCheckRunStepURL` originate from the Checks API JSON, which for third-party apps is attacker-influenceable.

### Recommendation
Apply the same allow-list used by `SandboxedMarkdown` (`/^https?:/`) at the point `onViewCheckDetails`/`onViewJobStep` build/forward the URL, and/or enforce protocol validation centrally in the `open-external` IPC handler in `app/src/main-process/main.ts` instead of only logging for `http(s)`.

### Proof of Concept
1. Configure (or compromise) a GitHub App/CI integration on a repository/fork whose check runs report a `details_url` such as `file:///Users/victim/malicious.app` (or an OS-registered custom scheme pointing at a vulnerable local handler).
2. Victim opens the PR in GitHub Desktop, opens the Checks popover, and clicks "View check details" for that check run.
3. `onViewCheckDetails` passes the crafted `htmlUrl` unchanged to `dispatcher.openInBrowser` → `shell.openExternal`, with no protocol filtering anywhere in the chain, unlike the markdown-link path which would have rejected it.

Note: I could not fully verify runtime behavior of Electron's `shell.openExternal` on this specific version/OS combination for non-http(s) inputs (e.g., whether it silently no-ops for unregistered schemes) — this would need to be confirmed by a Devin session with access to build/run the app, since the index only contains source, not a live environment.

  private onViewCheckDetails = (checkRun: IRefCheck): void => {
    if (checkRun.htmlUrl === null && this.props.repository.htmlURL === null) {
      // A check run may not have a url depending on how it is setup.
      // However, the repository should have one; Thus, we shouldn't hit this
      return
    }

    // Some checks do not provide htmlURLS like ones for the legacy status
    // object as they do not have a view in the checks screen. In that case we
    // will just open the PR and they can navigate from there... a little
    // dissatisfying tho more of an edgecase anyways.
    const url =
      checkRun.htmlUrl ??
      `${this.props.repository.htmlURL}/pull/${this.props.prNumber}`

    this.props.dispatcher.openInBrowser(url)
    this.props.dispatcher.incrementMetric('viewsCheckOnline')
  }
