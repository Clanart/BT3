## Title
`rewards()` in the distribution precompile silently accepts and strands `msg.value` - (File: `precompiles/distribution/distribution.go`)

### Summary
The distribution precompile's `rewards` view method is the only query-type method in the precompile that does not call `pcommon.ValidateNonPayable(value)` before executing. Every other view/query method (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) routes through `p.validateInput(value, args, N)`, which internally calls `ValidateNonPayable` and reverts the whole EVM call (and its native value transfer) if `value != 0` [1](#0-0) . `rewards` skips this check entirely and doesn't even take `value` as a parameter [2](#0-1) [3](#0-2) .

### Finding Description
When a caller invokes the distribution precompile (address `0x0000000000000000000000000000000000001007`) with a low-level call attaching non-zero `value` and calldata selecting `rewards(address)`, the EVM's normal value-transfer semantics move the attached `usei`/`wei` balance from the caller to the precompile's associated account as part of the `CALL` opcode, before `Run`/`Execute` is invoked. Because `rewards` never checks `ValidateNonPayable(value)` and returns success (`nil` error) as long as the query itself succeeds, the call does **not** revert, so the value transfer is never rolled back. Unlike the transactional/payable methods (`deposit`-style flows in gov/other precompiles) which call `pcommon.HandlePaymentUsei` to immediately forward the transferred coin to its intended destination or refund the payer [4](#0-3) , `rewards` has no such payment-handling logic at all — it simply ignores the value that was already moved into the precompile's account [3](#0-2) .

Distribution is also notably absent from the `payablePrecompiles` allow-list used elsewhere in the EVM keeper to suppress spurious transfer events for precompiles that are intentionally designed to receive funds (`bank`, `staking`, `gov`, `wasmd`) [5](#0-4) , confirming that distribution was never intended to hold a balance, yet this one method allows it to happen unnoticed.

### Impact Explanation
Any `usei`/`wei` sent alongside a `rewards()` call becomes permanently stuck in the distribution precompile's account. There is no withdrawal, sweep, or refund mechanism for this precompile, and no other method exposes a way to move funds back out of `0x...1007`. This is a direct, irreversible loss of user funds triggered by a normal user transaction (or accidental wallet misuse sending value with a view call), matching the "payable function but no way to withdraw" bug class from the reference report — permanent freezing/loss of funds.

### Likelihood Explanation
Reachable by any unprivileged EVM caller performing a single low-level `call{value: X}(abi.encodeWithSelector(rewards.selector, delegator))` against the precompile address. No special privileges, precompile allow-listing, or contract deployment tricks are needed — only the ABI signature and value. The Solidity interface for this precompile does not mark `rewards` as `payable`, so a normal high-level Solidity call would be rejected by the compiler, but a raw/assembly `call` (or another contract's `.call{value}`) bypasses that and reaches the vulnerable code path directly, which is a realistic attack surface given how common low-level calls are in DeFi routers/adapters.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check to `rewards` (and pass `value` into it, mirroring the other view methods), so that any non-zero value attached to the call causes the whole EVM call to revert, rolling back the value transfer along with it — consistent with how every other view method in this precompile already behaves.

### Proof of Concept
1. Associate an EVM address with a Sei address.
2. Craft calldata for `rewards(address delegator)` using the precompile ABI.
3. Send a raw contract call (e.g., via a helper contract or `eth_call`/`eth_sendTransaction` with low-level `call`) to `0x0000000000000000000000000000000000001007` with `value = 1000000000000000000` wei (1 SEI) attached and the `rewards` calldata.
4. Observe the call succeeds (status 1) and returns the rewards data, while the sender's `usei` balance decreases by the sent amount.
5. Query the precompile account's bank balance — the sent `usei` now sits there with no method available anywhere in `precompiles/distribution/distribution.go` to withdraw or reclaim it.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
