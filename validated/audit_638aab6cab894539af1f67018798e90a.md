### Title
`SignableTransaction::new` omits the OP_RETURN data output from fee/vbyte estimation, so the constructed transaction pays a lower effective fee rate than requested and may fall below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
When `data` is specified, `SignableTransaction::new` appends an OP_RETURN output to `tx_outs`, but the fee estimation helper `calculate_weight_vbytes` builds its dummy transaction only from `payments` (and optionally `change`). The OP_RETURN output's weight is never accounted for, so `needed_fee` / `fee_with_change` underpay relative to the real transaction size. When a change output exists, the change amount absorbs the difference, meaning the transaction's actual sat/vbyte rate is strictly lower than `fee_per_vbyte` and can drop below `DEFAULT_MIN_RELAY_TX_FEE`, producing a signed transaction that nodes will not relay.

### Finding Description
The constructor pushes the OP_RETURN output at `send.rs:194-202`, then estimates weight at `send.rs:204` via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`. Inside `calculate_weight_vbytes` (`send.rs:62-99`), the mock transaction's outputs are built exclusively from `payments`, plus an optional `change` output — there is no parameter or path that accounts for the OP_RETURN output. The same omission applies to the with-change estimation at `send.rs:225-227`.

Consequences in the code itself:

- The minimum-fee check at `send.rs:211` (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) validates against the underestimated `vbytes`, so a transaction can pass this check while its real feerate is below the relay minimum.
- The change computation at `send.rs:228-230` uses `fee_with_change`, which is also computed without the OP_RETURN weight. `fee()` (`send.rs:138-141`) confirms the actual fee equals `fee_with_change`, i.e., `input_sat - payment_sat - change` — the underestimated value. The extra ~11-91 bytes (script + data push) of real transaction weight are unfunded.

With the maximum allowed data (80 bytes, checked at `send.rs:171`), the omitted output adds roughly 90 bytes (~23 vbytes) of weight the fee never pays for. On a small transaction this is a ~10-15% effective feerate reduction.

### Impact Explanation
An unprivileged party who can cause `data` to be attached to a vault spend (the Serai data field carried in Bitcoin transactions, e.g., `Output.data` / `extract_serai_data` flow in `processor/src/networks/bitcoin.rs:730`) produces a `SignableTransaction` whose real feerate is below the requested `fee_per_vbyte`. If the requested rate is near the relay minimum, the resulting fully-signed transaction is non-standard for relay: Bitcoin Core nodes will reject it from their mempools, so the threshold-signed transaction cannot propagate. The vault must discard the signatures and reconstruct/re-sign the transaction, stalling withdrawals. This maps the audit's "accounted amount vs. actual transferred amount" mismatch onto Bitcoin's fee/change math: the accounted fee (`needed_fee`) is less than what the real serialized transaction requires for the target rate.

### Likelihood Explanation
Any call path that supplies both `data: Some(..)` and a `change` script hits the underestimation deterministically — no attacker sophistication is needed beyond causing a data-bearing spend. Whether the transaction is actually rejected depends on the requested `fee_per_vbyte` being close enough to the minimum that the ~10-15% shortfall crosses it, so the bug is conditional in impact but unconditional in fee underpayment.

### Recommendation
Include the OP_RETURN output (and any other unconditional outputs) in `calculate_weight_vbytes`, e.g., pass the final `tx_outs` list — or a `data_len` parameter — into the estimation so the dummy transaction matches the real output set. Both the no-change estimate at `send.rs:204` and the with-change estimate at `send.rs:225-227` must account for the data output.

### Proof of Concept
```rust
// Conceptual: construct a SignableTransaction with data + change near min feerate
let data = Some(vec![0u8; 80]);
let tx = SignableTransaction::new(
  vec![output],          // one input worth e.g. 10_000 sats
  &[(payment_script, 5_000)],
  Some(change_script),
  data,
  MIN_FEE_PER_VBYTE,     // e.g. 1 sat/vbyte
).unwrap();

// tx.transaction() contains payments + OP_RETURN + change,
// but needed_fee was computed on a tx without the OP_RETURN output.
let real_vsize = signed_vsize(&tx);        // > vbytes used internally by ~23 vbytes
assert!(tx.fee() as f64 / real_vsize as f64 < 1.0); // below requested 1 sat/vbyte
```
Concretely: `calculate_weight_vbytes` at `send.rs:85-94` iterates only `payments`, and the call sites at `send.rs:204` and `send.rs:226` never mention `data`, while the OP_RETURN output is pushed to `tx_outs` at `send.rs:195-201`. The discrepancy is directly observable by comparing `tx.transaction().vsize()` against the `vbytes` the fee was derived from.
