### Title
Aggregate Schnorr nonces are not bound to the claimed component challenges, allowing forged aggregate signatures - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregate::verify` derives its aggregation weights only from the supplied challenges, not from the aggregate nonce vector `Rs` or the public keys. Because `Rs` is fully attacker-controlled through `SchnorrAggregate::read`, an unprivileged party can algebraically construct nonce points and a scalar `s` that satisfy the verifier’s multi-exponentiation equation without knowing any private key or possessing valid component signatures. [1](#0-0) 

### Finding Description
The verifier checks:

```text
sum_i z_i * R_i + sum_i z_i * c_i * A_i - s * G = 0
```

where `z_i` is generated by `weight(&mut digest)`. The digest is initialized with the caller-provided domain separator and only receives the sequence of challenges. [2](#0-1) 

The aggregate nonces are decoded directly from attacker-controlled bytes via `SchnorrAggregate::read`. [3](#0-2)  Neither the read path nor `verify` proves that each `R_i` was produced by a signer or that the supplied challenge `c_i` actually binds that exact `R_i`.

For arbitrary `x_i`, an attacker can set:

```text
R_i = x_i * G - c_i * A_i
s   = sum_i z_i * x_i
```

The verifier expression then cancels to zero:

```text
sum_i z_i * (x_iG - c_iA_i)
  + sum_i z_i * c_iA_i
  - sum_i z_i * x_iG
= 0
```

This exploits the fact that the aggregate proof combines nonce terms and key terms while leaving the attacker free to choose `R_i` after learning `A_i`, `c_i`, and the deterministic `z_i`.

### Impact Explanation
A valid-looking `SchnorrAggregate` can be forged for an arbitrary list of public keys and externally supplied challenges. In an authentication or authorization flow using aggregate Schnorr verification as the accepted credential, this lets an attacker hijack the flow by substituting an attacker-constructed aggregate rather than relaying signatures genuinely produced by the key holders.

This is a signature forgery, not merely signature malleability: the attacker does not need a valid component signature, any private key, or any nonce scalar.

### Likelihood Explanation
The attack is deterministic and purely algebraic. The attacker only needs public keys, the corresponding challenge values supplied to `verify`, and control of the aggregate bytes. Since `SchnorrAggregate::read` accepts an arbitrary length and arbitrary canonical points, the attacker can construct the forged aggregate locally and submit it to the verifier. [3](#0-2) 

### Recommendation
Bind every component nonce and public key to the challenge used by `verify`, and ensure verification recomputes those challenges from the exact `R_i`, `A_i`, and message rather than accepting unbound challenge scalars. If callers must supply challenges, the API should make the binding structurally unavoidable—for example, accept `(key, message)` pairs and derive `c_i = H(R_i, A_i, message_i)` internally from the decoded aggregate nonces.

The aggregation-weight transcript should also commit to the complete ordered `Rs` and key list before deriving weights, so replacement of either list changes every `z_i`.

### Proof of Concept
Conceptual construction over the crate’s own equation:

```rust
// Public inputs:
// - A_i: public key
// - c_i: challenge supplied to SchnorrAggregate::verify
// - G: C::generator()

let mut rs = Vec::new();
let mut xs = Vec::new();

for (key, challenge) in keys_and_challenges {
    let x = C::random_nonzero_F(&mut rng);
    xs.push(x);

    // Choose R_i so the nonce and public-key terms cancel.
    rs.push((C::generator() * x) - (*key * *challenge));
}

// Reproduce the deterministic weight derivation used by verify().
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
for (_, challenge) in keys_and_challenges {
    digest.append_message(b"challenge", challenge.to_repr());
}

let mut s = C::F::ZERO;
for x in xs {
    let z = weight::<_, C::F>(&mut digest);
    s += z * x;
}

// Forged aggregate accepted by:
// SchnorrAggregate { Rs: rs, s }.verify(dst, keys_and_challenges)
```

For each index, `R_i + c_iA_i = x_iG`; therefore the weighted sum equals `sum_i z_i x_iG`, which is exactly `sG`. [4](#0-3)
