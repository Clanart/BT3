Found it: `getBranchCheckoutArgs` in `app/src/lib/git/checkout.ts` builds the `git checkout` argument list with the branch name placed *before* the `--` end-of-options separator, which defeats the purpose of the separator and allows a branch name that itself is a git option string to be interpreted as a flag rather than a literal ref, when that name reaches `git` unfiltered.

### Title
Argument injection via branch name in `checkout` due to misplaced `--` separator - (File: app/src/lib/git/checkout.ts)

### Summary
`checkoutBranch` in [1](#0-0)  builds its `git checkout` argument array by calling `getBranchCheckoutArgs`, which places `branch.name` first and only appends `--` at the end: [2](#0-1) . The `--` end-of-options marker only protects arguments that come *after* it; putting the branch name before it means a branch value that starts with `-` is still parsed by `git checkout` as an option rather than a literal ref name.

### Finding Description
The Desktop "Open in Desktop" deep-link flow (`x-github-client://openRepo/...?branch=...`) accepts an attacker-controlled `branch` query parameter and passes it through to `checkoutLocalBranch` → `checkoutBranch` → `getBranchCheckoutArgs`, as seen in `openBranchNameFromUrl` in `dispatcher.ts`: [3](#0-2) . Before reaching the git layer, the branch value only passes through `testForInvalidChars`, which does **not** reject a leading `-`: [4](#0-3)  and [5](#0-4) . (Note that `sanitizedRefName`, which *does* strip a leading `-`, is a separate function used elsewhere for user-typed branch creation, not for this deep-link path — see the tests confirming the stripping behavior exists only in that other function: [6](#0-5) .) Because `getBranchCheckoutArgs` places the branch name *before* `--` instead of after it, git's own protection against option-like refnames is bypassed for this argument.

This mirrors the report's underlying pattern of "attacker-influenced input crosses a trust boundary without effective downstream containment" — here the containment mechanism (`--`) exists in the code but is misordered, so it doesn't actually enforce the boundary it appears to enforce.

### Impact Explanation
If a git checkout option string can be smuggled as the "branch" value (e.g., something equivalent to `--conflict=merge`, `-b`, or other checkout flags/values), an attacker who can get a victim to click a crafted `x-github-client://openRepo/<url>?branch=<payload>` link could alter the behavior of the checkout operation on the victim's machine beyond a normal branch switch, potentially corrupting the working tree state or triggering unintended git behavior tied to whichever flag is smuggled — falling into the "silent corruption of what the user commits/pushes or executes locally" impact category for an unprivileged, link-triggered vector.

### Likelihood Explanation
The link click is a normal, low-friction social-engineering-free vector already supported natively by the app's registered URL protocol handler (`handleAppURL` in `main.ts` and `openBranchNameFromUrl` in `dispatcher.ts`). Exploitability depends on which specific git checkout flags can be abused via a bare value (this requires further practical verification of which flags accept a value directly appended without `=`, since `git checkout` mostly expects `--flag=value` or a preceding `-b`/`-B`); this reduces confidence versus a definitive proof, and I was not able to fully verify a concrete damaging flag combination within the scope of this review.

### Recommendation
Move the `--` separator to precede the branch name argument (and any other externally influenced ref-like argument) in `getBranchCheckoutArgs`, matching the pattern already used correctly in `checkoutPaths` and `checkoutConflictedFile` in the same file: [7](#0-6) . Additionally, validate/reject branch names beginning with `-` in `parseAppURL`'s handling of the `branch` query parameter, consistent with the stricter sanitization already applied elsewhere (`sanitizedRefName`).

### Proof of Concept
Unverified/not fully reproduced — I confirmed the code-level ordering issue (`branch.name` before `--`) via static review of `getBranchCheckoutArgs` and traced the untrusted input path from `parseAppURL` → `dispatcher.openBranchNameFromUrl` → `checkoutBranch`, but did not execute an end-to-end proof against a real `git checkout` invocation to confirm which specific option value would produce a damaging effect. This should be validated by a Devin session with terminal access, constructing a deep link such as `x-github-client://openRepo/https://github.com/<owner>/<repo>?branch=<candidate-flag-value>` and observing the actual `git checkout` argv and its effect on a test repository.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
