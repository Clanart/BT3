Audit Report

## Title
Unauthenticated `DuplicateShred.from` field lets a single attacker identity bypass the per-node buffer cap in `DuplicateShredHandler`, causing unbounded memory growth - (File: `gossip/src/duplicate_shred_handler.rs`)

## Summary
`DuplicateShredHandler::handle_shred_data` keys its reassembly buffer by `(chunk.slot, chunk.from)`, where `chunk.from` is a `Pubkey` field embedded in the attacker-supplied `DuplicateShred` payload rather than the cryptographically verified signer of the enclosing `CrdsValue`. `Sanitize::sanitize` on `DuplicateShred` only checks wallclock bounds, chunk-index bounds, and a structural no-op `self.from.sanitize()` — it never confirms `from` matches the actual gossip message signer. This lets a single valid gossip identity mint unlimited distinct `(slot, fake_pubkey)` buffer entries, defeating the intended per-identity cap `MAX_NUM_ENTRIES_PER_PUBKEY = 128` and inflating memory usage until the lazy `maybe_prune_buffer` threshold (`BUFFER_CAPACITY * 2` = 131,072 entries) is reached.

## Finding Description
`DuplicateShred` carries a `from: Pubkey` field that is intended to identify the sending node [1](#0-0) . Its `Sanitize` implementation only validates the wallclock and chunk-index bounds, and calls `self.from.sanitize()`, which is a purely structural check that does not compare `from` against the actual signer of the gossip `CrdsValue` [2](#0-1) .

On the honest send path, `from_shred` always sets `from: self_pubkey`, the sender's own key passed in by the caller [3](#0-2) . This is only a courtesy convention of the sending helper; nothing in the wire format or `Sanitize` enforces that a `DuplicateShred` payload's `from` matches the signer of the `CrdsValue` that carries it. The receive path, `DuplicateShredListener::recv_loop`, simply pulls `DuplicateShred` values out of the CRDS table via `cluster_info.get_duplicate_shreds` and forwards them to the handler with no re-derivation from the CRDS signer [4](#0-3) .

`DuplicateShredHandler::handle_shred_data` then inserts each chunk into `self.buffer` keyed by `(chunk.slot, chunk.from)` — the unverified, attacker-controlled field [5](#0-4) . The only defenses are `MAX_NUM_ENTRIES_PER_PUBKEY = 128` and `BUFFER_CAPACITY = 512 * 128`, enforced lazily only once `self.buffer.len()` reaches `BUFFER_CAPACITY * 2` (131,072) [6](#0-5) [7](#0-6) . Because the per-pubkey key is fabricated per-message at zero cost by whoever crafts the raw `DuplicateShred` chunk, the per-identity cap is trivially defeated: one real gossip identity can generate arbitrarily many distinct `(slot, fake_pubkey)` keys, each occupying up to `MAX_NUM_CHUNKS = 3` slots of `DuplicateShred` payload data, before the global lazy-prune threshold is even reached.

I was unable to fully confirm within this session whether the CRDS ingestion layer performs any additional cross-check that a `CrdsData::DuplicateShred`'s embedded `from` field matches the CRDS value's own signer pubkey before insertion into the table (this would live in `crds.rs`/`crds_gossip.rs`/`crds_value.rs`, whose relevant verify/signature logic I located but did not fully trace end-to-end). Based on the code paths I did trace — `Sanitize::sanitize`, `from_shred`, `DuplicateShredListener::recv_loop`, and `DuplicateShredHandler::handle_shred_data` — no such cross-check exists in the duplicate-shred-specific logic itself; the `from` field is used as-is for buffer keying.

## Impact Explanation
This matches the "non-RPC remote exhaustion" category: any unprivileged gossip participant with one valid, low-cost gossip identity can drive `DuplicateShredHandler::buffer` toward `BUFFER_CAPACITY * 2` (131,072) entries using forged `from` values, each entry holding up to 3 chunks of attacker-sized payload, consuming memory proportional to `entries * MAX_NUM_CHUNKS * max_chunk_size` on the victim validator's gossip-processing path [8](#0-7) . The corrupted resource-bound value is the per-pubkey entry-count invariant enforced by `MAX_NUM_ENTRIES_PER_PUBKEY`, which is meant to bound the buffer contribution of any single logical identity but is keyed on unverified data [9](#0-8) .

## Likelihood Explanation
High reachability with a caveat on full confirmation. `Sanitize` explicitly performs only a structural check on `from` and never compares it to the CRDS value's real signer [2](#0-1) . The only requirement is one valid gossip keypair, which is a standard requirement for any gossip participant and does not constitute "privileged" access. However, since I could not fully trace whether an outer CRDS/signature-verification layer independently constrains this (e.g., possibly rejecting or capping messages by actual signer at a different point in the pipeline before reaching `DuplicateShredListener`), this should be verified further — if such a layer exists and is strict, it could reduce practical severity, though it would not change the fact that `handle_shred_data`'s cap itself is bypassable via forged `from`.

## Recommendation
- Bind the buffer/accounting key in `DuplicateShredHandler::handle_shred_data` to the actual signer pubkey of the enclosing `CrdsValue`, not to the payload-embedded `from` field.
- Alternatively, add an explicit equality check between `chunk.from` and the CRDS value's own pubkey at ingestion (in `DuplicateShredListener::recv_loop` or upstream in CRDS processing), rejecting mismatches before they reach `handle_shred_data`.
- Consider making the buffer bound strict and non-lazy, and enforce `MAX_NUM_ENTRIES_PER_PUBKEY` on every insert rather than deferring to `maybe_prune_buffer`'s `BUFFER_CAPACITY * 2` threshold.

## Proof of Concept
1. Attacker uses one real, valid gossip keypair to sign ordinary Push/PullResponse gossip messages.
2. Each message's `CrdsData::DuplicateShred` payload sets a distinct random `from` pubkey (not the attacker's real signing key), `num_chunks = 3`, `chunk_index = 0..2`, and a maximal `chunk` payload, with a unique `slot`/index per message.
3. These are delivered through `DuplicateShredListener::recv_loop` → `DuplicateShredHandler::handle` → `handle_shred_data`, which inserts each into `buffer` keyed by `(chunk.slot, chunk.from)` [10](#0-9) .
4. Because `chunk.from` differs on every message, each "pubkey" only ever accumulates 1 entry, so `MAX_NUM_ENTRIES_PER_PUBKEY` (128) never triggers per-key, while `self.buffer.len()` grows unbounded until `maybe_prune_buffer`'s `BUFFER_CAPACITY * 2` (131,072) check fires [8](#0-7) .
5. A Rust unit test extending the existing `test_reject_abuses`/`test_handle_mixed_entries` tests in `gossip/src/duplicate_shred_handler.rs` [11](#0-10)  could directly call `handle_shred_data` (or `handle`) in a loop with distinct forged `from` values and assert `self.buffer.len()` grows past `MAX_NUM_ENTRIES_PER_PUBKEY * N` without per-key eviction, confirming the cap bypass.

pub(crate) fn from_shred<T: AsRef<[u8]>, F>(
    shred: Shred,
    self_pubkey: Pubkey, // Pubkey of my node broadcasting crds value.
    other_payload: T,
    leader_schedule: Option<F>,
    wallclock: u64,
    max_size: usize, // Maximum serialized size of each DuplicateShred.
    shred_version: u16,
) -> Result<impl Iterator<Item = DuplicateShred>, Error>
where
    F: FnOnce(Slot) -> Option<Pubkey>,
    shred::Payload: From<T>,
{
    if shred.payload().as_ref() == other_payload.as_ref() {
        return Err(Error::InvalidDuplicateShreds);
    }
    let other_shred = Shred::new_from_serialized_shred(other_payload)?;
    check_shreds(leader_schedule, &shred, &other_shred, shred_version)?;
    let slot = shred.slot();
    let proof = DuplicateSlotProof {
        shred1: shred.into_payload(),
        shred2: other_shred.into_payload(),
    };
    let data = wincode::serialize(&proof)?;
    let chunk_size = if DUPLICATE_SHRED_HEADER_SIZE < max_size {
        max_size - DUPLICATE_SHRED_HEADER_SIZE
    } else {
        return Err(Error::InvalidSizeLimit);
    };
    let chunks: Vec<_> = data.chunks(chunk_size).map(Vec::from).collect();
    let num_chunks = u8::try_from(chunks.len())?;
    let chunks = chunks
        .into_iter()
        .enumerate()
        .map(move |(i, chunk)| DuplicateShred {
            from: self_pubkey,
            wallclock,
            slot,
            num_chunks,
            chunk_index: i as u8,
            chunk,
            _unused: 0,
            _unused_shred_type: ShredType::Code.into(),
        });
    Ok(chunks)
}

    fn recv_loop(
        exit: Arc<AtomicBool>,
        cluster_info: &ClusterInfo,
        mut handler: impl DuplicateShredHandlerTrait + 'static,
    ) {
        let mut cursor = Cursor::default();
        while !exit.load(Ordering::Relaxed) {
            let entries: Vec<DuplicateShred> = cluster_info.get_duplicate_shreds(&mut cursor);
            for x in entries {
                handler.handle(x);
            }
            sleep(Duration::from_millis(GOSSIP_SLEEP_MILLIS));
        }
    }

    fn handle_shred_data(&mut self, chunk: DuplicateShred) -> Result<(), Error> {
        if !self.should_consume_slot(chunk.slot) {
            return Ok(());
        }
        let slot = chunk.slot;
        let num_chunks = chunk.num_chunks();
        let chunk_index = chunk.chunk_index();
        if usize::from(num_chunks) > MAX_NUM_CHUNKS || chunk_index >= num_chunks {
            return Err(Error::InvalidChunkIndex {
                chunk_index,
                num_chunks,
            });
        }
        let entry = self.buffer.entry((chunk.slot, chunk.from)).or_default();
        *entry
            .get_mut(usize::from(chunk_index))
            .ok_or(Error::InvalidChunkIndex {
                chunk_index,
                num_chunks,
            })? = Some(chunk);

    fn maybe_prune_buffer(&mut self) {
        // The buffer is allowed to grow to twice the intended capacity, at
        // which point the extraneous entries are removed in linear time,
        // resulting an amortized O(1) performance.
        if self.buffer.len() < BUFFER_CAPACITY.saturating_mul(2) {
            return;
        }
        self.consumed.retain(|&slot, _| slot > self.last_root);
        // Filter out obsolete slots and limit number of entries per pubkey.
        {
            let mut counts = HashMap::<Pubkey, usize>::new();
            self.buffer.retain(|(slot, pubkey), _| {
                *slot > self.last_root
                    && should_consume_slot(*slot, &self.blockstore, &mut self.consumed)
                    && {
                        let count = counts.entry(*pubkey).or_default();
                        *count = count.saturating_add(1);
                        *count <= MAX_NUM_ENTRIES_PER_PUBKEY
                    }
            });
