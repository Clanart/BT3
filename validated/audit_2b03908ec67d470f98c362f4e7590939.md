### Title
Webhook Shop-Domain Header Is Not Covered by HMAC Verification, Enabling Cross-Shop Data Injection - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` only validates the HMAC over the raw request body, and never checks that the `X-Shopify-Shop-Domain` header actually corresponds to that body. The gem exposes `shop_domain` (a raw, unauthenticated header read) as the officially documented way for custom webhook controllers to determine which shop a webhook belongs to. Because the shared secret used to compute the HMAC is the app's static API secret (identical for every shop the app is installed on, not per-shop), any merchant who has the app installed can capture one of their own legitimately-signed webhook deliveries and replay it with only the `X-Shopify-Shop-Domain` header changed to a victim shop's domain — the HMAC over the body remains valid, and `shop_domain` returns the attacker-controlled value. This mirrors the reported bug class of "missing validation that a supplied identifier is valid/consistent for the given data", here applied to shop-tenant attribution instead of token/market validation.

### Finding Description
- `hmac_valid?` in `PayloadVerification` computes/verifies the HMAC strictly over `request.raw_post`: [1](#0-0) 
- `WebhookVerification#verify_request` gates the action purely on that body HMAC and exposes `shop_domain` sourced directly from the `X-Shopify-Shop-Domain` request header, which is never included in the HMAC computation: [2](#0-1) 
- The gem's own documentation instructs developers building custom webhook controllers to trust this unauthenticated `shop_domain` helper as the tenant key for background job dispatch: [3](#0-2) 

Since the API secret used for HMAC computation is shared across all shops that install the app (it is the app's client secret, not a per-shop secret), any authenticated merchant of the app can obtain a validly-signed webhook body for their own shop and then modify only the `X-Shopify-Shop-Domain` header before replaying it to the app's webhook endpoint. The HMAC check in `hmac_valid?` still passes because it only covers `request.raw_post`, and the resulting `shop_domain` value used downstream (per the documented pattern) will be whatever the attacker set it to.

### Impact Explanation
An attacker-controlled shop can inject its own webhook data (e.g., customer, order, or product payloads) as if it belonged to an arbitrary victim shop, as long as they can guess/target the victim's `myshopify.com` domain. Depending on how the consuming app's background job uses `shop_domain` (as documented, to scope `perform_later(shop_domain: ..., webhook: ...)`), this can lead to cross-tenant data corruption, spoofed records attributed to another merchant, or triggering shop-scoped side effects (e.g., inventory/order updates) against a shop the attacker does not control — a cross-shop access/data-integrity violation reachable by any existing app-installer, i.e., an unrelated-merchant HTTP request relative to the victim shop.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that follow the documented custom-webhook pattern: the attacker only needs to be a legitimate (even trial) installer of the target app on their own shop, trigger any webhook topic that is HMAC-verified the same way, and replay it with a modified header — no secret material needs to be leaked, since the design flaw is that the header sits outside the signed payload.

### Recommendation
- Do not treat the `X-Shopify-Shop-Domain` header as trusted tenant context. Cross-validate it against the shop identifier embedded in the signed webhook body (or, where using `ShopifyAPI::Webhooks::Request`, use the parsed/verified shop from that library rather than the raw header) before using it for any tenant-scoped storage or job dispatch.
- Update `shop_domain` in `WebhookVerification` (and the corresponding documentation example) to derive/validate the shop from the verified webhook payload rather than an unsigned header, or explicitly document that `shop_domain` is untrusted and must not be used for authorization/tenant routing without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook topic handled by a custom controller using the documented pattern (`include ShopifyApp::WebhookVerification` + `shop_domain` for job dispatch).
2. Attacker captures the resulting POST request, including its valid `X-Shopify-Hmac-Sha256` header and raw body.
3. Attacker replays the exact same body/HMAC to the app's webhook endpoint but changes only the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
4. `PayloadVerification#hmac_valid?` recomputes the HMAC over the (unchanged) raw body using the app's static secret and returns `true`; `verify_request` allows the request through.
5. The custom controller calls `shop_domain`, which returns `"victim-shop.myshopify.com"`, and dispatches `SomeJob.perform_later(shop_domain: "victim-shop.myshopify.com", webhook: attacker_controlled_body)`, injecting attacker data under the victim shop's identity.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
