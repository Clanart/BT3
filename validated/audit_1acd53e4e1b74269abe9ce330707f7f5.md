### Title
PedPoP blame proof leaks a victim's ECDH share-decryption key because the per-message proof-of-possession is never verified before the blame is emitted — (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The GitLab CVE is an information-disclosure issue: an unprivileged user learns metadata about private entities via a legitimate public API. The Serai analog lives in PedPoP's blame flow. `EncryptedMessage` carries a Schnorr proof-of-possession (`pop`) precisely so that an attacker who reuses someone else's per-message encryption key cannot trick a victim into publishing a blame proof whose ECDH key would decrypt the victim's *other* message (crypto/dkg/pedpop/src/encryption.rs:84-91; spec/cryptography/Distributed Key Generation.md:28-35). However, `KeyMachine::calculate_share` only *queues* the PoP into a `BatchVerifier` inside `Encryption::decrypt`, and returns early — emitting the blame proof — whenever the decrypted bytes are not a canonical scalar, i.e., before `batch.verify_with_vartime_blame()` is ever called. The PoP is therefore never checked before the ECDH key is published, fully re-enabling the key-co-option disclosure the PoP was designed to prevent.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs:476-499`, `calculate_share` loops over the sender-supplied `EncryptedMessage<C, SecretShare<C::F>>` values:

- `Encryption::decrypt` (encryption.rs:469-501) calls `msg.pop.batch_verify(...)` — which merely *queues* the PoP statement — then computes `key = ecdh(&self.enc_key, msg.key)` and unconditionally returns an `EncryptionKeyProof { key, dleq }` attesting that `key` is the shared ECDH point between the recipient's registered encryption key and `msg.key`.
- Back in `calculate_share`, `C::F::from_repr(share_bytes.0)` is evaluated and, on failure, `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` is returned via `?` — before the loop finishes and before `batch.verify_with_vartime_blame()` at line 493 runs. The queued PoP statement for that message is never verified.
- The processor then serializes this blame into `ProcessorMessage::InvalidShare { ..., blame: Some(blame.serialize()) }` (processor/src/key_gen.rs:419-425), broadcasting `proof.key` — the ECDH shared point — to all validators. `CoordinatorMessage::VerifyBlame`/`AdditionalBlameMachine` does eventually verify the PoP inside `decrypt_with_proof` (encryption.rs:374-379) and correctly blames the sender, but by then `proof.key` is already public.

Because the PoP is unverified at publication time, a malicious participant Eve can set `msg.key` to `X`, the per-message public key Alice used in her encrypted share to Bob (observable on the share-distribution channel, exactly the scenario described in the code comments), attach any PoP, and fill the ciphertext with non-canonical scalar bytes. Bob's `decrypt` computes `bX` — the identical ChaCha20 input used to encrypt Alice's real share — and packages it into a blame proof that Bob broadcasts.

### Impact Explanation
`cipher(context, proof.key)` decrypts Alice's `EncryptedMessage` to Bob (encryption.rs:101-133, 392). Alice's secret share `f_Alice(Bob)` — private share-evaluation data that only Bob was meant to see — is disclosed to every observer of the blame message. This is the "key share recovery"/private-data disclosure class: one leaked evaluation per victim, and if Eve performs the co-option against `t` distinct recipients of Alice's shares (one per DKG instance or per victim), Alice's degree-`(t-1)` polynomial, and hence her secret contribution to the group key, is fully recoverable, collapsing the DKG's confidentiality guarantee to that of the remaining honest contributions.

### Likelihood Explanation
The attack requires only that Eve (a DKG participant) can observe Alice's encrypted share to Bob — an assumption the code itself makes ("Eve could observe Alice encrypt to Bob with key X", encryption.rs:84-85) — and send one malformed share message, a public input via `CoordinatorMessage::Shares` → `EncryptedMessage::read` → `calculate_share`. No collusion, timing, or privileged position is needed. The only mitigation — PoP verification — is skipped on precisely the code path (non-canonical plaintext) the attacker controls, since she chooses the ciphertext and the resulting plaintext is garbage after a wrong key anyway. Note the attack is not free: `VerifyBlame` will ultimately blame Eve for the invalid PoP, so it costs Eve a slashing/fault mark — but the disclosure is irreversible and this is a documented-and-partially-mitigated bug where the mitigation is incomplete on an early-return path.

### Recommendation
Verify the PoP synchronously before any early return that carries a blame proof: in `calculate_share`, either call `msg.pop.verify` directly before decrypting/`from_repr`, or restructure so that `batch.verify_with_vartime_blame()` (or at least the `BatchId::Decryption` statements) is checked before `PedPoPError::InvalidShare { blame: Some(..) }` can be returned. Concretely, in `Encryption::decrypt`, verify the PoP non-batched and return an error type that carries no `EncryptionKeyProof` when it fails, so no ECDH key material can escape for a message whose key-ownership was never proven.

### Proof of Concept
Setup follows the existing test harness (`crypto/dkg/pedpop/src/tests.rs:30-80`):

1. Alice (`i=1`), Bob (`i=2`), Eve (`i=3`) run `KeyGenMachine::generate_coefficients` and `generate_secret_shares` for a `t=2, n=3` PedPoP instance. Eve observes `alice_to_bob: EncryptedMessage<Ristretto, SecretShare>` and extracts `alice_to_bob.key` (the per-message public key `X`) and ciphertext.
2. Eve constructs `evil: EncryptedMessage<Ristretto, SecretShare>` with `evil.key = X`, any `evil.pop` (e.g. `invalidate_msg`-style signature over garbage, or a malformed signature — it will not be checked), and `evil.msg` set to non-canonical bytes (all-`0xFF`, guaranteed non-`Repr` per the existing `invalidate_share_serialization` test, tests.rs:219-239).
3. Bob runs `KeyMachine::calculate_share(rng, {1: alice_share_to_bob, 3: evil})`. Inside `Encryption::decrypt`, `key = ecdh(bob_enc_key, X) = bX` is computed and wrapped in an `EncryptionKeyProof`; `from_repr` fails; `calculate_share` returns `Err(PedPoPError::InvalidShare { participant: 3, blame: Some(proof) })` without calling `batch.verify_with_vartime_blame()` — so Eve's invalid/missing PoP over `X` is never checked.
4. Bob (via processor/src/key_gen.rs:419-425) publishes `ProcessorMessage::InvalidShare { accuser: 2, faulty: 3, blame: Some(proof.serialize()) }`. Any observer reads `EncryptionKeyProof::read` → `proof.key = bX`, runs `cipher::<Ristretto>(context, &proof.key).apply_keystream(alice_to_bob.msg)`, and recovers Alice's secret share `f_Alice(2)` in cleartext — share data that was only ever encrypted for Bob.

The `invalid_ecdh_blame` test (tests.rs:208-244) already exercises the adjacent machinery; the distinguishing step here is that the blame proof is emitted on the `from_repr` early-return path *before* batch PoP verification, which no existing check covers.
