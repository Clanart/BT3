## Analysis

The reported Sablier bug class — an unprivileged party being able to force a withdrawal/token push onto another user's (or contract's) address without their consent, potentially breaking accounting or permanently locking funds in a receiving DeFi contract — has a direct analog in `MasterMagpie.multiclaimFor`.

### Title
Unrestricted `multiclaimFor` allows any unprivileged wallet to force-push MGP and bonus reward tokens onto an arbitrary account, risking permanent loss/misaccounting of yield - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie.multiclaimFor` can be called by **any address**, with only a `whenNotPaused` guard, to force-claim and push both MGP and bonus reward tokens directly into the balance of an arbitrary `_account` at any time, with the receiver hard-coded to be the same `_account`. [1](#0-0) 

### Finding Description
`multiclaimFor` calls the internal `_multiClaim(_stakingTokens, _account, _account, _rewardTokens)`, where both the "user" whose rewards are claimed and the "receiver" of the transferred tokens are the caller-supplied `_account`, with no `msg.sender == _account` check, and no allow-list/authorization modifier (compare with `multiclaimOnBehalf`, which is properly gated by `_onlyCompounder`). [2](#0-1) 

`_multiClaim` computes pending MGP and bonus rewards for `_account` and unconditionally transfers them to `_receiver` (`_account`) via `_sendMGP`/`_sendMGPForVlMGPPool` and `_claimBaseRewarder`, which in turn calls each pool's `getReward`/`getRewards`, ending in a raw `safeTransfer(_receiver, ...)`. [3](#0-2) [4](#0-3) 

This mirrors exactly the pattern flagged in the Sablier report: a third party — with no relationship to the target account beyond knowing its address — can force an unsolicited inbound token transfer into that account at a time of the third party's choosing. If `_account` is a smart contract integrated with the Magpie ecosystem (e.g., a pool helper, vault, aggregator, or any DeFi contract that holds a staking position on behalf of its own users and expects to control when/if it receives reward tokens), an attacker can force premature or repeated reward pushes into that contract's balance:
- If the receiving contract does socialized accounting per-share (e.g., a vault that distributes any token balance increase pro-rata to depositors), forced pushes can dilute/misdistribute rewards meant for the specific staker.
- If the receiving contract has no sweep/rescue mechanism for unexpected token inflows, the pushed tokens become permanently stuck, exactly as described in the reported bug class ("the tokens would be locked in the contract or they would be distributed evenly over all participants of the contract").

### Impact Explanation
Anyone can force MGP and any number of bonus reward tokens to land in a DeFi contract's balance without that contract's consent or awareness, at attacker-chosen timing. Depending on the receiving contract's design, this can cause a permanent freeze of yield (funds stuck with no withdrawal path) or a theft/misdistribution of unclaimed yield away from its intended beneficiary — both are impacts explicitly in scope.

### Likelihood Explanation
The function is `external`, requires no special role, and is only gated by the global pause flag — trivially callable by any wallet against any `_account` address at any time, so likelihood of exploitation (intentional or accidental, exactly as Sablier's report notes) is high, contingent only on some integrator holding staking positions inside a contract that cannot gracefully absorb unsolicited reward inflows.

### Recommendation
Restrict `multiclaimFor` so tokens can only be sent to `msg.sender` (self-claim) unless the caller is the account itself or an explicitly authorized operator (mirroring the existing `_onlyCompounder` gate on `multiclaimOnBehalf`), or require the target `_account` to pre-approve/whitelist which addresses may trigger claims on its behalf, similar to the "accept" pattern Sablier ultimately recommended raising awareness of.

### Proof of Concept
1. Contract `V` (any pool helper, vault, or aggregator) stakes a Magpie LP position in `MasterMagpie` on behalf of its own depositors, and has no logic to handle unsolicited MGP/bonus-token inflows.
2. An unrelated wallet `A` calls `MasterMagpie.multiclaimFor(_stakingTokens, _rewardTokens, address(V))` at any time.
3. `_multiClaim` computes `V`'s pending MGP/bonus rewards and force-transfers them into `V`'s balance via `_sendMGP`/`getReward`.
4. `V` has no code path to redistribute or rescue this unexpected inflow correctly, so the yield is either permanently stuck in `V` or gets smeared across all of `V`'s depositors regardless of who actually earned it in `MasterMagpie`. [5](#0-4)

    function _multiClaim(address[] calldata _stakingTokens, address _user, address _receiver, address[][] memory _rewardTokens) internal nonReentrant {
        uint256 length = _stakingTokens.length;
        if (length != _rewardTokens.length) revert LengthMismatch();

        uint256 vlMGPPoolAmount;
        uint256 mWOmPoolAmount;
        uint256 defaultPoolAmount;

        for (uint256 i = 0; i < length; ++i) {
            address _stakingToken = _stakingTokens[i];
            UserInfo storage user = userInfo[_stakingToken][_user];
            
            updatePool(_stakingToken);
            uint256 claimableMgp = _calNewMGP(_stakingToken, _user) + unClaimedMgp[_stakingToken][_user];

            if (_stakingToken == address(vlmgp)) {
                vlMGPPoolAmount += claimableMgp;
            } else if (MPGRewardPool[_stakingToken]) {
                mWOmPoolAmount += claimableMgp;
            } else {
                defaultPoolAmount += claimableMgp;
            }

            unClaimedMgp[_stakingToken][_user] = 0;
            user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
            _claimBaseRewarder(_stakingToken, _user, _receiver, _rewardTokens[i]);
        }
