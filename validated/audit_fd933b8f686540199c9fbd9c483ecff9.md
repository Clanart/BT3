### Title
Empty `SchnorrAggregate` verifies as a valid signature, granting "signed" status with zero signers - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` returns `true` for an aggregate signature containing zero individual signatures and `s = 0`, whenever the caller's `keys_and_challenges` list is empty. This is the in-scope analog of "missing credential grants access": the absent signer set is treated as a successfully authenticated authorization rather than rejected. An unprivileged party can forge a cryptographically "valid" aggregate signature over any message for which the verifier's expected signer set is (or can be made) empty.

### Finding Description
`SchnorrAggregate::read` accepts a `u32` count of `R` values followed by a single scalar `s` [1](#0-0) . A 5-byte payload `00 00 00 00 || 0x00..00` deserializes to `SchnorrAggregate { Rs: [], s: 0 }` with no rejection of the empty case.

`verify` then only checks `self.Rs.len() == keys_and_challenges.len()` and evaluates `multiexp_vartime` over the constructed pairs [2](#0-1) . For the empty case:

- the length check `0 == 0` passes,
- no `z`-weighted `(R_i, c_i·A_i)` pairs are produced,
- the sole remaining pair is `(-s, G) = (0, G)`, so the multiexp equals the identity,
- `verify` returns `true`.

Nothing in `read`, `verify`, or `SchnorrAggregator::complete` requires at least one constituent signature. The `batch_statements`/`verify` path for a single `SchnorrSignature` is not affected (a lone identity `R` still requires `c·A - sG = -R` to hold), but the aggregate form collapses to a vacuous check when the statement list is empty. The production consumer `Validators::verify_aggregate` in `coordinator/tributary/src/tendermint/mod.rs` checks only `signers.len() == aggregate.Rs().len()` before calling `aggregate.verify`, inheriting the same acceptance condition [3](#0-2) .

### Impact Explanation
Any verifier that derives its `keys_and_challenges` from attacker-influenced data — e.g., a claimed signer list, a filtered/eligible-validator subset, or a per-input commitment set — will accept `(Rs=[], s=0)` as a valid aggregate signature whenever that derived set is empty. Concretely, this produces a forged signature acceptance: the verifier concludes "the designated parties signed this message" when no party signed anything. In a threshold/validator context (as in `Validators::verify_aggregate`), an attacker-supplied aggregate over an empty claimed-signer list passes the cryptographic check; whether the surrounding consensus weight check stops it is outside this crate and not guaranteed by the verifier itself.

### Likelihood Explanation
Exploitation requires a call path where the expected-signer set fed to `verify` can be empty while the aggregate's acceptance carries security weight. `SchnorrAggregate::read` is a public untrusted-bytes entry point and `verify` performs no minimum-signer check, so any such caller is exposed. The primary mitigating factor is that honest callers typically verify against a fixed, non-empty validator/key set, which prevents the empty-list condition; hence Medium rather than higher.

### Recommendation
Reject empty aggregates at both boundaries:

1. In `SchnorrAggregate::read` / `verify`, return an error / `false` when `self.Rs.is_empty()` (and symmetrically when `keys_and_challenges.is_empty()`).
2. Optionally, have `SchnorrAggregator::complete` return `None` when no signatures were aggregated, so a valid empty aggregate can never be produced.

### Proof of Concept
```rust
// crypto/schnorr (Ed25519 ciphersuite)
use dalek_ff_group::Ed25519;
use schnorr::aggregate::SchnorrAggregate;

// Crafted bytes: len = 0, s = 0
let mut bytes = vec![0u8; 4 + 32];
let agg = SchnorrAggregate::<Ed25519>::read::<&[u8]>(&mut bytes.as_slice()).unwrap();

// Verifies as valid for an empty signer set, for ANY dst/message context
assert!(agg.verify(b"any dst", &[]));
```
The assertion succeeds because `verify` computes `multiexp_vartime(&[(-0, G)]) == identity`.
