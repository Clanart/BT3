### Title
Gasless swap deadline check uses stale last-block timestamp instead of the pending/execution block time, allowing execution of expired swaps - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The Kaia gasless module validates a `swapForGas` transaction's `deadline` parameter against `g.Chain.CurrentBlock().Time()` — i.e., the timestamp of the last **already-mined** block — rather than the timestamp of the block in which the transaction will actually be executed. This mirrors the OTLM `_claimEpochRewards` bug class: an expiration/deadline check compared against an imprecise or manipulable time reference, allowing the check to pass even though the transaction is effectively stale by the time it lands on-chain.

### Finding Description
In `checkBalanceForSwap`, the code enforces `tx.deadline >= currentTimestamp` as: [1](#0-0) 

```go
// tx.deadline >= currentTimestamp
deadline := swapArgs.Deadline
if deadline.Cmp(g.Chain.CurrentBlock().Time()) < 0 {
    return fmt.Errorf("insufficient deadline: deadline=%s, want=%s", deadline.String(), g.Chain.CurrentBlock().Time().String())
}
```

`g.Chain.CurrentBlock().Time()` is the timestamp of the last block already appended to the chain, not the timestamp that will be assigned to the block that ultimately includes and executes this transaction. This check is invoked from `GetCheckBalance()` [2](#0-1)  which is wired into the tx pool's balance-check hook (`blockchain/tx_pool.go`), i.e. it is performed once at admission time (and potentially re-checked periodically), using a reference timestamp that necessarily lags the eventual block-inclusion timestamp by at least one block interval, and can lag further if the transaction sits in the pending pool.

Because a swap can be admitted to the pool and remain pending across multiple blocks (bundled with a preceding approve tx per nonce ordering, `IsReady`/`knownTxs` logic), the deadline that a user set to protect against stale-price execution can silently expire between admission-time validation and actual execution-time. Unlike a typical DEX router which enforces `require(deadline >= block.timestamp)` at execution time inside the contract itself, here the only "deadline" gate visible in-repo is this pool-level pre-check tied to a strictly older timestamp; there is no evidence in the available bindings that `GaslessSwapRouter.swapForGas` re-validates the deadline against the real `block.timestamp` at execution (the Solidity source for `GaslessSwapRouter` is not present in this repo — only its generated Go bindings — so this cannot be fully confirmed from the indexed code, which is a limitation of the available index).

### Impact Explanation
If the on-chain contract's own deadline enforcement is weak, absent, or also based on a similarly stale value, a swap whose price-protection deadline has genuinely elapsed could still execute, using outdated `minAmountOut`/`amountRepay` bounds relative to current pool state. This can allow adversarial actors (e.g., the searcher/bundler ordering transactions, or an attacker manipulating pool state while the swap is pending) to extract value at the user's expense — a concrete instance of "unauthorized value movement" via stale-deadline execution, analogous to the OTLM reward-theft-via-stale-expiration bug class. Given this runs in the public tx-pool admission path reachable by any unprivileged transaction sender, and directly gates fund-moving swap execution, the severity aligns with Medium/High.

### Likelihood Explanation
The condition is trivially reachable: any user or attacker can submit an approve+swap gasless bundle with a deadline set to be valid at admission time but stale by execution time, simply by exploiting normal network latency or by having the transaction sit pending due to nonce ordering / pool congestion (`QueueTimeout`/`PendingTimeout` are 10 seconds, meaning bundles are expected to persist in the pool for meaningful periods) [3](#0-2) . No special privilege or validator collusion is required — a single submitted transaction bundle is enough to reach this code path.

### Recommendation
Re-validate the swap deadline at the actual point of state application (ideally the destination contract should enforce `require(deadline >= block.timestamp)` at execution time using the timestamp of the block actually being processed), and/or have the tx-pool level check use the timestamp of the block being built (pending block time) rather than `CurrentBlock().Time()`, and re-run `checkBalanceForSwap` immediately before promotion/inclusion, not only at initial admission, to close the gap between admission-time and execution-time timestamps.

### Proof of Concept
1. Attacker (or normal user under network delay) crafts an `approveTx` + `swapTx` gasless bundle with `deadline = CurrentBlock().Time() + 1` so it passes the pool-admission check in `checkBalanceForSwap` at `kaiax/gasless/impl/tx_pool.go:175-179`.
2. Due to pool congestion, nonce ordering (`IsReady`), or the `PendingTimeout`/`QueueTimeout` windows (10 seconds) [3](#0-2) , the bundle remains pending across several blocks before being included.
3. By the time the bundle is actually executed, the real `block.timestamp` may exceed the originally intended deadline window, yet the transaction was already admitted and, absent a robust execution-time deadline check in the router contract, is settled — enabling settlement using stale price-protection parameters (`minAmountOut`, `amountRepay`) set against the user's/protocol's expectations at submission time, not execution time.

```go
func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}
```
