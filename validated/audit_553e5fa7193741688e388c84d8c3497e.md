## Finding

The external Balancer report warns that any custom ERC-20 the protocol accepts might not be compliant — specifically, it may **return `false` on failure instead of reverting**, and code that only checks "the low-level call didn't revert" will silently treat a failed transfer as a success. Hyperbridge has a direct, exploitable local analog to this exact pattern in the Tron deployment of the Intent Gateway.

### Title
Non-compliant ERC-20 `transfer` return value is unchecked in `withdraw()`/`SweepDust`, letting escrow be finalized without delivering funds - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` (Tron) imports and uses `SafeERC20` for token pulls (`safeTransferFrom` in `placeOrder`), but the two functions that push tokens *out* of escrow — `withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow` and from `onGetResponse`) and the `SweepDust` handler inside `onAccept` — bypass `SafeERC20` entirely and instead do a raw low-level call, checking only that the call itself did not revert: [1](#0-0) [2](#0-1) 

For an ERC-20 that returns `false` (a boolean payload) instead of reverting on a failed transfer — a non-compliant-but-still-callable token, exactly the class of token the cited Balancer report warns about — `token.call(...)` returns `success = true` even though no tokens moved. The code never decodes/checks the returned boolean.

### Finding Description
`withdraw()` is the terminal settlement path for both `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund), and is also reached from `onGetResponse` for source-side cancellations: [3](#0-2) 

It (1) unconditionally marks the order settled — `_filled[body.commitment] = beneficiary;` — (2) decrements the internal escrow accounting `_orders[body.commitment][token] -= amount;`, and only *after* that does the raw `.call()` transfer, whose success is judged solely by the outer call not reverting. If the input `token` is a contract that returns `false` on transfer failure (e.g. insufficient real balance due to any prior accounting drift, a paused/blacklisted state, or a token deliberately crafted this way by the order creator, who freely picks `order.inputs[i].token` when placing an order with no allow-list observed in `placeOrder`), the function:
- reports `success = true` and skips the `TransferFailed()` revert,
- permanently finalizes `_filled[commitment] = beneficiary` (blocking any retry or alternate recovery path),
- deletes/decrements the escrow slot as if funds were paid out,
- while the beneficiary never actually receives the tokens.

The exact same unchecked-low-level-call pattern is repeated in the `SweepDust` branch of `onAccept`.

Contrast this with the canonical (non-Tron) `IntentsBase._withdraw`, which correctly uses `IERC20(token).safeTransfer(beneficiary, amount);`, and with `SafeERC20`'s own guarantee that it reverts unless the token either has no return value or returns `true`. The Tron contract deliberately re-implements the transfer without that protection in exactly the two paths that release custody of escrowed funds.

### Impact Explanation
This breaks the "assets move exactly once and only to the rightful beneficiary" invariant required for intent settlement/reward paths: the contract's internal bookkeeping (`_orders`, `_filled`) is advanced to a finalized state that no longer matches on-chain reality, while the beneficiary receives nothing. The escrowed tokens become permanently unrecoverable — the order is marked filled/refunded so it can never be retried by `onAccept`, `onGetResponse`, or a subsequent cancellation, and the escrow slot has already been zeroed. This is a direct loss-of-funds bug in production bridge/settlement logic, not a peer/relayer/prover trust assumption — it is triggered purely by the properties of the ERC-20 the order creator selected as an input token.

### Likelihood Explanation
Order input tokens appear to be chosen freely by the order creator in `placeOrder` (no on-chain allow-list was found gating `order.inputs[i].token`), so any user can construct an order denominated in a token contract they deploy that returns `false` (rather than reverting) under conditions they control (e.g., simulate insufficient balance, a pause flag, or an unconditional `false`). Once such an order reaches `withdraw()` — whether via a legitimate relayer delivering `RedeemEscrow`/`RefundEscrow`, or via the source-chain `onGetResponse` cancellation flow — the mis-accounting triggers deterministically, with no privileged actor, governance action, or compromised relayer required.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept` with `SafeERC20.safeTransfer`, consistent with the rest of the contract (which already imports and uses `SafeERC20` for inbound transfers). This decodes and enforces the ERC-20 boolean return value (or the absence of one) instead of only checking that the call did not revert.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer()` returns `false` (no revert) whenever `msg.sender == <IntentGatewayV2 address>` and some attacker-controlled condition holds (or simply always returns `false` while still allowing `transferFrom`/`balanceOf` to behave normally so `placeOrder`'s `safeTransferFrom` succeeds and escrow is funded).
2. Attacker calls `placeOrder` with `order.inputs[0].token = EvilToken`, funding escrow normally via `safeTransferFrom` (which succeeds, `EvilToken.transferFrom` returns `true`).
3. A relayer later delivers a `RedeemEscrow` or `RefundEscrow` message, invoking `onAccept` → `withdraw(body, ...)`.
4. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes `EvilToken.transfer`, which returns `false` but does not revert, so `success == true`.
5. `withdraw` proceeds: `_orders[commitment][token] -= amount` and `_filled[commitment] = beneficiary` are set, `EscrowReleased`/`EscrowRefunded` is emitted — yet `beneficiary`'s `EvilToken` balance never increased.
6. The escrowed `EvilToken` amount is now stuck in `IntentGatewayV2` forever: the order is marked filled/refunded, so no other code path can be used to move it out, resulting in a permanent loss of the escrowed funds.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
