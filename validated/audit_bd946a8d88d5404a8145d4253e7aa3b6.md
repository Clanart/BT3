### Title
Unrestricted `Name`/`Symbol` fields in `MsgSetDenomMetadata` enable token identity spoofing ([File: sei-cosmos/x/bank/types/metadata.go])

### Summary
Any account that creates a tokenfactory denom becomes its admin and can call `MsgSetDenomMetadata` to set the denom's `Name` and `Symbol` display fields to *any* string, including characters that are visually indistinguishable from those of well-known assets (e.g. Cyrillic/Greek homoglyphs of `USDC`, `SEI`, `ATOM`), or even the exact same string as a legitimate token. `Metadata.Validate()` only checks that `Name`/`Symbol` are non-blank — it performs no uniqueness check against existing metadata and no character-set restriction, unlike the `Base`/`Display` fields which are constrained by `sdk.ValidateDenom`.

### Finding Description
`Metadata.Validate()` in `sei-cosmos/x/bank/types/metadata.go` only enforces: [1](#0-0) 
It never restricts the character set or checks collision with other denoms' `Name`/`Symbol`. Only `Base` and `Display` (the actual denom strings) are passed through `sdk.ValidateDenom`, which restricts to a fixed ASCII regex: [2](#0-1) 

Any unprivileged account can create a tokenfactory denom permissionlessly via `CreateDenom`, becoming its admin: [3](#0-2) 

That same admin can then call `MsgSetDenomMetadata`, which is validated only via `msg.Metadata.Validate()` and an admin check, with no restriction on `Name`/`Symbol` content or uniqueness: [4](#0-3) [5](#0-4) 

Because the underlying denom (`Base`) is namespaced by creator address (`factory/{creator}/{subdenom}`), an attacker can never collide with the *denom* itself, but the `Name` and `Symbol` fields — the human-readable identity shown by wallets, explorers, the bank precompile's `name()`/`symbol()` methods, and CosmWasm/EVM tooling — carry no such namespacing or uniqueness guarantee: [6](#0-5) 

This is directly analogous to the IDN homograph spoofing in CVE-2019-13663: the underlying technical identifier (URL/domain in Chrome, or `Base` denom in sei-chain) is correctly distinguished, but the human-facing display identity (rendered domain / `Name`/`Symbol` metadata) can be spoofed to impersonate a trusted entity.

### Impact Explanation
A malicious actor can create a tokenfactory denom and set its metadata `Name`/`Symbol` to match (exactly or via homoglyphs) a legitimate, high-value asset such as `USDC` or `SEI`. Any wallet, DEX front-end, block explorer, or EVM contract that displays or trusts `Name`/`Symbol` from `GetDenomMetaData` (including via the bank precompile's `name`/`symbol` calls) will show the spoofed identity as if it were the genuine asset. This can be leveraged for phishing-style fund-loss attacks — e.g., listing a fake "USDC" token on a DEX interface or wallet that a user is tricked into swapping into or transferring funds against, believing it is the canonical stablecoin.

### Likelihood Explanation
Trivial to exploit: `CreateDenom` and `SetDenomMetadata` are both public, permissionless, unprivileged transactions requiring no special access. Any single unprivileged sender can create a spoofed-name token in one transaction.

### Recommendation
Harden `Metadata.Validate()` (or add an additional check in `x/tokenfactory/keeper/msg_server.go`'s `SetDenomMetadata`) to:
- Restrict `Name`/`Symbol` to a defined safe character set (reject non-printable/confusable Unicode ranges, or normalize/reject mixed-script strings, similar to Chrome's IDN homograph mitigations).
- Optionally reject `Name`/`Symbol` values that collide with metadata of pre-existing/well-known denoms unless the module itself is the admin.

### Proof of Concept
1. Attacker calls `MsgCreateDenom{sender: attacker, subdenom: "spoof"}` → denom `factory/{attacker}/spoof` created, attacker is admin. [3](#0-2) 
2. Attacker calls `MsgSetDenomMetadata` with `Metadata{Base: "factory/{attacker}/spoof", Display: "factory/{attacker}/spoof", Name: "USD Coin", Symbol: "USDC"}` (or Unicode homoglyph variants of `USDC`). [4](#0-3) 
3. `Metadata.Validate()` passes since `Name`/`Symbol` are non-blank and `Base`/`Display` are valid tokenfactory denoms. [1](#0-0) 
4. Any client (wallet, explorer, precompile `name()`/`symbol()` caller) querying this denom's metadata now displays "USD Coin"/"USDC" for an attacker-controlled asset, enabling spoofing-based fund-loss attacks against unsuspecting users.

func (server msgServer) SetDenomMetadata(goCtx context.Context, msg *types.MsgSetDenomMetadata) (*types.MsgSetDenomMetadataResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Defense in depth validation of metadata
	err := msg.Metadata.Validate()
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Metadata.Base)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	server.bankKeeper.SetDenomMetaData(ctx, msg.Metadata)

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgSetDenomMetadata,
			sdk.NewAttribute(types.AttributeDenom, msg.Metadata.Base),
			sdk.NewAttribute(types.AttributeDenomMetadata, msg.Metadata.String()),
		),
	})

	return &types.MsgSetDenomMetadataResponse{}, nil
}
