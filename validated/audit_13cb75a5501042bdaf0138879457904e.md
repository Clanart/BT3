## Analysis

I reviewed the exact code at `modules/consensus/bsc/verifier/src/lib.rs` and confirmed the threshold arithmetic in question.### Title
BSC light-client supermajority check uses `<` with floored integer division, accepting a sub-2/3 signer set - (File: `modules/consensus/bsc/verifier/src/lib.rs`)

### Summary
`verify_bsc_header` computes the BEP-126 quorum threshold as `(2 * current_validators.len()) / 3` using integer (floor) division and rejects only when `participant_count < threshold`. This means `participant_count == threshold` is accepted. For any validator count where `2n` is not evenly divisible by `3` (e.g. `n = 22, 23`), `floor(2n/3)` is strictly less than the true `2n/3` fraction, so the check lets in a signer set that is below the actual two-thirds supermajority. [1](#0-0) 

### Finding Description
The comment at line 81-82 states the intent is to mirror BSC's own parlia consensus threshold, linking to `parlia.go`. Upstream BSC's `verifyVoteAttestation` rejects when `signed <= len(validators)*2/3` (i.e., requires **strictly more** than `2n/3`, using `<=` as the rejection boundary). This codebase instead rejects only when `participant_count < (2*n)/3` (using `<` as the rejection boundary), which is a strictly weaker check.

- Upstream BSC: accept requires `signed > floor(2n/3)`, i.e., `signed >= floor(2n/3) + 1`.
- Hyperbridge verifier: accept requires `signed >= floor(2n/3)`.

For `n = 22`: `floor(2*22/3) = floor(44/3) = 14`. True 2/3 supermajority is `14.67`, so a genuine `>2/3` quorum requires at least `15` signers. The verifier's check `participant_count < 14` only rejects `<14`, so `participant_count = 14` (14/22 ≈ 63.6%, below both the true 2/3 fraction and BSC's own on-chain quorum requirement) passes the check and proceeds to signature aggregation/verification. If 14 validators (real or colluding) actually sign the attestation, the aggregate BLS signature check at line 124-133 will also succeed, and the header will be treated as finalized, producing a trusted `state_commitment` for a chain state that BEP-126's honest-majority (`>2/3`) assumption does not actually guarantee. [2](#0-1) 

The existing unit tests in the file only cover `n = 21` (divisible by 3), where `floor(2*21/3) = 14` happens to equal the exact fractional threshold, masking the off-by-one/rounding gap that is visible with non-multiple-of-3 validator counts: [3](#0-2) 

Even for `n = 21`, the boundary itself is one vote weaker than upstream BSC (`>=14` accepted here vs. `>=15` required upstream), but this is only clearly demonstrable as breaking the *fractional* 2/3 guarantee for non-multiple-of-3 counts such as 22 or 23, which is realistic since BSC's validator set size has grown over time and is not guaranteed to remain a multiple of 3.

### Impact Explanation
This directly violates the "Consensus proofs, state proofs, challenge periods, and state commitments must never let false remote state become trusted" pivot. A signer set that does not meet the true BEP-126 honest-majority threshold can produce a `VerificationResult` that Hyperbridge's BSC light client treats as a finalized `state_commitment`, which downstream ISMP consumers use for cross-chain proof verification, request/response routing, and settlement. This can enable false proof acceptance, i.e., trusting BSC state finalized by a sub-quorum, which weakens all state proofs relayed for BSC across the bridge.

### Likelihood Explanation
Exploiting this requires collusion or compromise of a set of BSC validators equal to the flawed threshold (e.g., 14 of 22) rather than the true safe supermajority (15 of 22) — a materially lower bar than intended by the protocol design, and the gap widens further as the validator set grows and moves away from multiples of three. This is not reliant on relayer or peer misbehavior; it is a logic error in the on-chain-equivalent verification arithmetic itself, present in the `verify_bsc_header` function used to validate consensus updates.

### Recommendation
Change the threshold comparison to match upstream BSC parlia semantics exactly: reject when `participant_count * 3 <= current_validators.len() * 2` (avoiding floor-division truncation by cross-multiplying), or equivalently require `participant_count > (2 * current_validators.len()) / 3` using ceiling-based comparison, so that the accepted set always exceeds the true 2/3 fraction regardless of `n mod 3`.

```rust
fn accepts_sub_quorum_for_22_validators() {
    let validators = dummy_validators(22);
    // floor(2*22/3) = 14; true 2/3 supermajority requires >= 15 (14.67 rounded up).
    let mask: u64 = (1u64 << 14) - 1; // 14 in-range bits set
    let header = header_with_vote_set(mask, B256::repeat_byte(1), B256::repeat_byte(2));
    let err = verify_bsc_header::<TestHost, Testnet>(&validators, update_with(header), 1000)
        .expect_err("downstream signature check must fail");
    let msg = format!("{err}");
    // Demonstrates the quorum check itself does NOT reject 14/22, despite 14/22 < 2/3.
    assert!(!msg.contains("Not enough participants"));
}
```
This mirrors the existing `accepts_fully_populated_in_range_bits` / `rejects_too_few_in_range_participants` tests and shows the `NotEnoughParticipants` guard does not fire for `14` participants out of `22`, confirming the threshold check accepts a sub-2/3 signer set. [4](#0-3)
