### Title
`Scanner::scan_block` reports coinbase outputs as spendable `ReceivedOutput`s despite the 100-block maturity rule - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
Analogous to consuming a Chainlink feed without checking its freshness/validity window, `Scanner::scan_block` consumes every transaction in a block — including `txdata[0]`, the coinbase — without checking the Bitcoin-imposed freshness/validity constraint on it (the 100-block maturity rule). The returned `ReceivedOutput` carries no maturity flag, height, or coinbase indicator, so the output is presented as a normal spendable output even though it cannot legally be spent until 100 confirmations have elapsed.

### Finding Description
`Scanner::scan_block` iterates over `block.txdata` unconditionally and passes every transaction — including the coinbase — into `scan_transaction`:

```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
}
``` [1](#0-0) 

`scan_transaction` only matches `output.script_pubkey` against the scanner's registered scripts; it never inspects `tx.is_coinbase()`, the coinbase's input, or the block height the output was created at:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
    res.push(ReceivedOutput {
      offset: *offset,
      output: output.clone(),
      outpoint: OutPoint::new(tx.compute_txid(), vout),
    });
}
``` [2](#0-1) 

`ReceivedOutput` is documented as "a spendable output" yet stores only `offset`, `output`, and `outpoint` — there is no field recording whether the output came from a coinbase or at what height, so freshness/maturity information is permanently discarded at scan time:

```rust
/// A spendable output.
pub struct ReceivedOutput {
  offset: Scalar,
  output: TxOut,
  outpoint: OutPoint,
}
``` [3](#0-2) 

The only guard is a doc comment on `scan_block` stating "a post-processing pass is needed" — the API itself returns the immature output indistinguishably. The analogous missing check to the report's `require(block.timestamp - updatedAt < HEARTBEAT)` is the absence of any `tx.is_coinbase() → skip` / height gate inside the scanning path.

### Impact Explanation
Any consumer calling the natural API (`scan_block`) receives an output labeled as spendable that Bitcoin consensus will refuse to let it spend for 100 blocks. If such an output is fed into `SignableTransaction`/the multisig spend flow, the produced transaction is consensus-invalid — the vault would sign and broadcast a transaction that cannot confirm (or, worse, treat the coinbase as immediately-available liquidity for accounting purposes). This is the "funds reported received that are not spendable" impact class.

### Likelihood Explanation
Reachable by an unprivileged party: any miner can create a coinbase paying to a scanned P2TR scriptPubKey — coinbase output scripts are entirely miner-chosen, no threshold cooperation required. On regtest/testing this is trivial (`generatetoaddress` to the vault script does exactly this, as the existing test `send_and_get_output` demonstrates at `networks/bitcoin/tests/wallet.rs:40-77`). The severity is bounded by the fact that mainnet miners are a limited set and the primary processor consumer (`processor/src/networks/bitcoin.rs:691`) already skips `txdata[1 ..]` — but that skip is an out-of-scope caller-side workaround, and the in-scope `scan_block` API itself remains incorrect. Medium.

### Recommendation
Inside `scan_block`, skip `block.txdata[0]` (or check `tx.is_coinbase()`), mirroring the heartbeat/freshness `require` from the source report. Alternatively, add a `coinbase: bool` (or creation height) field to `ReceivedOutput` so downstream spend logic can reject immature inputs, and make `SignableTransaction`/spend construction refuse coinbase outpoints younger than 100 confirmations.

### Proof of Concept
On regtest:

```rust
// networks/bitcoin/tests/wallet.rs pattern (send_and_get_output, lines 40-77)
// 1) Mine 1 block whose coinbase pays directly to the vault's p2tr script:
rpc.rpc_call::<Vec<String>>(

  json!([1, Address::from_script(&p2tr_script_buf(key).unwrap(), Network::Regtest)]),

// 2) Do NOT mine the 100 maturity blocks.
let block = rpc.get_block(&rpc.get_block_hash(block_number).await.unwrap()).await.unwrap();

// 3) scan_block reports the coinbase output as a spendable ReceivedOutput
let outputs = scanner.scan_block(&block);
assert_eq!(outputs[0].outpoint(), &OutPoint::new(block.txdata[0].compute_txid(), 0));
// ^ test line 65-70 already asserts exactly this behavior.

// 4) Feeding outputs[0] into SignableTransaction and broadcasting produces a tx that
//    consensus rejects (BIP-113/rule: coinbase spend before 100 confirmations).
```

The existing test itself proves the issue: `send_and_get_output` must mine 100 blocks after the fact (`generatetoaddress` 100, line 55-61) precisely because the scanned output is immature, yet `scan_block` returns it as spendable with no maturity metadata.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
