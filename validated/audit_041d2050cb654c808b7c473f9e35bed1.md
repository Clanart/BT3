### Title
`SignableTransaction::new` silently discards change when the change-output check fails, diverting the entire remainder to miner fees - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The reported bug class is a fallible operation whose failure is discarded, so the caller proceeds believing the requested outcome occurred. The same shape exists in `SignableTransaction::new`: when a `change` script is supplied, the code conditionally creates the change output inside a `checked_sub`/`>= DUST` guard. If the leftover amount is zero-underflow or below `DUST`, the change output is silently omitted, yet the transaction is still constructed and returned `Ok`. The entire remainder (`input_sat - payment_sat`) is then paid as a fee, which can far exceed the caller's requested `needed_fee`. [1](#0-0) 

### Finding Description
In `SignableTransaction::new`, after computing `needed_fee` from the no-change vbytes and verifying `input_sat >= payment_sat + needed_fee` (lines 204–221), the change path is handled as:

```rust
if let Some(change) = change {
  let (weight_with_change, vbytes_with_change) =
    Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
  let fee_with_change = fee_per_vbyte * vbytes_with_change;
  if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
    if value >= DUST {
      tx_outs.push(TxOut { value: Amount::from_sat(value), script_pubkey: change });
      weight = weight_with_change;
      needed_fee = fee_with_change;
    }
  }
}
```

There are two silent failure modes:

1. **`checked_sub` underflow**: if `input_sat < payment_sat + fee_with_change` (possible because `fee_with_change > needed_fee` once the change output's weight is included), no change is added. The transaction still pays `input_sat - payment_sat` as fee. Notably, a caller-specified `fee_per_vbyte` that overflows `u64` in `fee_per_vbyte * vbytes` (release builds wrap) can also distort this arithmetic.

2. **Sub-dust remainder**: if `input_sat - payment_sat - fee_with_change` is in `1..=DUST-1` sats, the leftover is burned as fee instead of returned. The caller's observable `fee()` (lines 138–141) then reports a fee larger than `needed_fee()`, with no error signaling that the change was dropped.

The function returns `Ok` in both cases, so the downstream `SignableTransaction`/`multisig`/`preprocess`/`sign`/`complete` pipeline produces and signs a transaction whose economics differ from what the caller requested — the exact "success reported on a degraded/failed sub-operation" shape of the report.

### Impact Explanation
The change output is where residual funds return to the controlled wallet. When it is silently dropped, those funds go to miners as an inflated fee. Unlike the AshPostgres analog (cross-tenant access), the consequence here is unrecoverable loss of funds rather than unauthorized access: `fee()` may be arbitrarily larger than `needed_fee()` up to `input_sat - payment_sat` in the underflow case. Because `TransactionSignMachine::sign` commits to `Prevouts::All` and the final `tx`, the signed transaction faithfully reflects the (incorrect) output set — every validator's share is valid, so the loss completes successfully with no verification failure to trigger blame.

### Likelihood Explanation
Reachability requires influence over `inputs`, `payments`, `change`, or `fee_per_vbyte`. In Serai's architecture, `SignableTransaction::new` runs on processor/coordinator plans; a withdrawal payment's amount and script are attacker-chosen. An attacker can size a payment so the change remainder lands below `DUST` (546 sats), guaranteed to burn the remainder to fees. That is bounded griefing (~545 sats + the delta between `needed_fee` and `fee_with_change` per attempt). The more severe `checked_sub` underflow requires `payment_sat + fee_with_change > input_sat` while `payment_sat + needed_fee <= input_sat`, i.e., the caller must set `input_sat` within ~`fee_with_change - needed_fee` of the minimum — feasible for exact-UTXO-change workflows but requires a near-exact input selection. Severity: Medium — reliable small-amount fund burning, larger amounts only in narrow input-selection scenarios.

### Recommendation
Make the change decision explicit and lossless:

- If `change` is `Some` and the remainder after `fee_with_change` is positive-but-dusty or `checked_sub` fails, either return `Err(TransactionError)` (e.g., a new `InsufficientChange`/`NoChangePossible` variant) or re-derive the change amount as `input_sat - payment_sat - needed_fee` using the no-change fee so the transaction still meets its requested fee rate.
- At minimum, cap the resulting fee at `needed_fee`/`fee_with_change` and error if `fee() > needed_fee` at construction.
- Use `checked_mul`/`saturating_mul` for `fee_per_vbyte * vbytes` and reject on overflow.

### Proof of Concept
Sketch (API-level, against `SignableTransaction::new`):

```rust
// Attacker-controlled payment: amount chosen so remainder is just under DUST.
// input_sat = 100_000, payment_sat = 100_000 - fee_with_change - (DUST - 1)
// => remainder = DUST - 1 = 545 sats, silently burned as extra fee.
let payments = &[(attacker_script, payment_sat)];
let stx = SignableTransaction::new(
    vec![received_output],   // input_sat = 100_000
    payments,
    Some(change_script),     // caller expects change back
    None,
    fee_per_vbyte,
).unwrap();

// Change output was never pushed to tx_outs:
assert_eq!(stx.transaction().output.len(), payments.len());
// Fee exceeds the requested budget; remainder is lost to miners:
assert!(stx.fee() > stx.needed_fee());
```

Note: I verified this path directly in `send.rs`. I did not exhaustively audit every other in-scope crate (e.g., `crypto/dkg/pedpop/src/encryption.rs` and `crypto/frost/src/algorithm.rs` had `ok()`-related matches I could not fully inspect within the iteration budget), so additional discarded-result analogs may exist; this finding stands on the confirmed code above.
