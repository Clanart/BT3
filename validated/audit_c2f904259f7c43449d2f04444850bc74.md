The bug class maps onto Serai's Bitcoin wallet: an unprivileged sender can push outputs to a victim's watched address, and the wallet reports them as received without any economic-spendability check. Let me confirm the input-side handling.### Title
Attacker can force a watched wallet to accept economically unspendable outputs, imposing mandatory fee costs on the receiver - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The ParaSpace report describes an attacker who unilaterally transfers collateral to a victim, where the protocol then auto-enables that collateral for the receiver, permanently increasing the receiver's costs on every subsequent operation. The analog in Serai's Bitcoin wallet: `Scanner::scan_transaction` records any on-chain output paying to a watched script as a `ReceivedOutput` — regardless of value — and `SignableTransaction::new` applies its dust check only to outgoing payments, never to inputs. An unprivileged attacker can therefore send outputs worth less than the marginal fee required to spend them to a victim's P2TR address. The wallet reports these as received spendable balance even though spending them is a net loss, and the receiver has no way to refuse or "disable" them.

### Finding Description
`Scanner::scan_transaction` iterates every `TxOut` and pushes a `ReceivedOutput` whenever `output.script_pubkey` matches a registered script, with no minimum-value filter: [1](#0-0) 

A `ReceivedOutput` is unconditionally treated as a spendable input. In `SignableTransaction::new`, the only value checks are `DustPayment` on outgoing payments and `NotEnoughFunds` on the aggregate input sum — there is no per-input check that `input.value` exceeds the marginal fee the input adds (~57 vbytes for a Taproot input per the in-file analysis): [2](#0-1) [3](#0-2) 

The `DUST = 546` constant is used only to bound *payments*, not to bound which inputs are economically rational to include, even though the fee contribution of an input is computed against `vbytes`: [4](#0-3) 

Because the sighash commits to all prevouts (`Prevouts::All`), every input listed is signed and its fee is paid: [5](#0-4) 

Like the ParaSpace auto-enabled collateral, the attacker decides the receiver's cost structure: the receiver cannot reject an on-chain transfer, and each pushed output either (a) is spent at a loss — a 546-sat output costs ~285+ sats of fee at just 5 sat/vB and proportionally more at higher rates, so outputs below `57 * fee_rate` are strictly negative-value — or (b) remains in the wallet's tracked UTXO set forever, inflating every future scan/spend pass. This is the same "sender forces receiver into a recurring/higher-cost state they cannot opt out of" shape, realized as fee burn and unspendable reported balance rather than gas.

### Impact Explanation
An unprivileged attacker sending Bitcoin transactions to a victim's watched address can:
- Cause `ReceivedOutput`s to be reported as received spendable funds that cannot actually be spent without a net loss ("funds reported received that are not spendable").
- Force the victim to either subsidize the attacker-funded dust with real fee expenditure on consolidation, or permanently carry a bloated UTXO set — an unavoidable cost imposed by a third party, mirroring the original finding's forced gas overhead / near-DoS.

### Likelihood Explanation
Sending a small P2TR output to an arbitrary known address is trivially reachable by any Bitcoin user; the victim's script pubkeys are public once used. The cost to the attacker is the dust value itself (as low as the relay dust limit), while the damage is recurring. It requires the wallet/integrator to actually include the poisoned outputs as inputs to realize direct loss, so impact is bounded — consistent with Medium severity, matching the M-08 classification of the original.

### Recommendation
Apply a minimum-value filter when classifying scanned outputs: in `Scanner::scan_transaction` (or immediately after scanning in the caller), drop outputs whose `value` is below the marginal cost to spend them (e.g., `57 * fee_rate` or a fixed conservative floor), rather than reporting every script match as a spendable `ReceivedOutput`. Additionally or alternatively, `SignableTransaction::new` should reject or warn on inputs whose value is below the fee contribution they add, so poisoned dust can never be signed into a transaction at a loss.

### Proof of Concept
1. Victim creates `Scanner::new(key)`; the base script `p2tr_script_buf(key)` is registered automatically (`mod.rs:162-165`).
2. Attacker broadcasts a transaction with an output paying `value = 546` sats (or any value `< 57 * prevailing_fee_rate`) to that script.
3. `scanner.scan_transaction(&tx)` returns a `ReceivedOutput` reporting `value() == 546` as received, spendable balance (`mod.rs:199-214`).
4. The wallet includes it among `inputs` to `SignableTransaction::new`; the only checks are on payments and the aggregate sum (`send.rs:165-221`), so the input is accepted. At 10 sat/vB the input costs ~570 sats of fee — the signature (`Prevouts::All` at `send.rs:375`) burns more of the victim's other funds than the output contributes. Repeating with N outputs scales the forced loss/bloat linearly, and nothing in the wallet lets the receiver opt out.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
