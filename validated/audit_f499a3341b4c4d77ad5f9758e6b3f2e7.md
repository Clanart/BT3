### Title
Explicit disabling of Git's clone hook-injection protection during recursive clone - ([File: app/src/lib/git/clone.ts])

### Summary
GitHub Desktop's `clone()` helper unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` on every clone, including the default `--recursive` clone of a user-supplied URL [1](#0-0) . This is the same broken-invariant pattern as the fyDAI report: a safety check that is supposed to gate a sensitive operation (there: `redeem` during flash mint; here: Git's internal guard against writing/executing hook-like files supplied by an untrusted, attacker-controlled repository during a recursive clone/submodule operation) is deliberately bypassed for the whole operation, letting attacker-supplied content reach code paths the guard exists to block.

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is a Git-internal environment variable that upstream Git uses to guard `git clone --recursive`/submodule operations against maliciously crafted repositories that try to smuggle files into `.git/hooks` (or otherwise abuse case-insensitive/symlink filesystem tricks in nested submodule clones) so that a hook executes automatically right after clone. Git toggles this variable itself around recursive submodule cloning to detect and refuse such repositories.

In `clone()`, Desktop builds the execution environment for every clone with:
```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
```
and then always invokes `git clone --recursive ... -- url path` [1](#0-0) [2](#0-1) . Because `url` and therefore the entire content of the cloned repository (including any submodules it declares) come directly from the user (via `_clone`/`CloneRepository` popup, or via a deep link/CLI action such as `dispatchCLIAction({kind: 'clone-url', url})` and `openOrCloneRepository` reachable from `x-github-client://` deep links) [3](#0-2) [4](#0-3) , the attacker fully controls the repository content that Git is about to clone recursively, while Desktop has explicitly told Git to treat this operation as "protection not active," which is exactly the state the upstream check is meant to prevent from being forced by the caller of a recursive clone.

This mirrors the report's core flaw: an operation that is supposed to be atomic and invariant-preserving (`isMature` gating `redeem`) is instead placed in a state, by design, where the invariant is not enforced (`GIT_CLONE_PROTECTION_ACTIVE=false`), and the attacker supplies the payload that exploits the resulting gap (a malicious repo/submodule layout instead of a flash-mint callback).

### Impact Explanation
If exploitable end-to-end, this allows an attacker who merely gets a user to clone or open (via deep link) a crafted repository URL to have Git write and subsequently execute a hook file on the victim's machine during the recursive clone — i.e., unprivileged, remote code execution triggered by ordinary use of the "Clone repository" feature or an `x-github-client://openRepo/...` link, with no further user action beyond the normal clone/open flow. That squarely matches the requested impact category (attacker controls a cloned/fetched repository → code execution outside the repo).

### Likelihood Explanation
Likelihood depends on details I could not fully verify from the code alone within this session:
- The exact semantics of `GIT_CLONE_PROTECTION_ACTIVE` (i.e., whether `'false'` truly disables the protection Git added for this class of clone-time hook-injection issue, or whether it is a no-op/only relevant for nested-clone bookkeeping) needs confirmation against the specific `dugite`/Git version vendored by this app.
- Whether the vendored Git version is new enough to have this protection at all, and whether other layers (e.g., sandboxing, `protocol.file.allow`, filesystem case-sensitivity on the victim's OS) block the exploit path.

Given the explicit, unconditional, always-on setting of this flag to `'false'` for every clone regardless of trust level of the URL, and the fact that clone URLs are attacker-reachable via the UI and via deep links, this is a plausible and directly reachable analog rather than a theoretical one, but I do not have full certainty it is exploitable without validating against the exact Git version behavior.

### Recommendation
- **Short term:** Remove the hard-coded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (and any other call site that sets it) unless there is a specific, well-documented compatibility reason; if such a reason exists, scope it narrowly and document why it is safe, or gate it behind a check that the source is trusted.
- **Long term:** Audit all environment variables Desktop forces on Git subprocesses (as in `envForRemoteOperation`/`clone.ts`) to ensure Desktop never overrides Git's own security defaults when performing operations against attacker-supplied, unauthenticated URLs.

### Proof of Concept
Not fully constructable from static code review alone in this session — validating a working PoC requires:
1. Confirming the vendored `dugite`/Git version's exact behavior for `GIT_CLONE_PROTECTION_ACTIVE=false` (what specific hook-injection check it disables).
2. Crafting a repository (e.g., with a submodule path/name and `.git` layout known to trigger the corresponding upstream advisory) and cloning it via Desktop's "Clone repository" dialog or a `x-github-client://openRepo/<url>` deep link, then observing whether a hook script from the malicious repo executes post-clone.

Given the tool-call budget was exhausted before this verification step, I flag this as the strongest candidate analog found in the codebase, but recommend a Devin session with terminal access to confirm exploitability against the specific Git/dugite version before treating this as a confirmed vulnerability.

  private async openOrCloneRepository(url: string): Promise<Repository | null> {
    const state = this.appStore.getState()
    const repositories = state.repositories
    const existingRepository = repositories.find(r =>
      this.doesRepositoryMatchUrl(r, url)
    )

    if (existingRepository) {
      return await this.selectRepository(existingRepository)
    }

    return this.appStore._startOpenInDesktop(() => {
      this.changeCloneRepositoriesTab(CloneRepositoryTab.Generic)
      this.showPopup({
        type: PopupType.CloneRepository,
        initialURL: url,
      })
    })
  }
