### Title
`rewards()` in the Distribution Precompile Omits the Non-Payable Check, Permanently Stranding Sent Native Funds - ([File: precompiles/distribution/distribution.go])

### Summary
The `rewards` view method of the Cosmos Distribution precompile (address `0x0000000000000000000000000000000000001007`) is dispatched without ever validating that `msg.value` is zero, unlike every other query method in the same dispatcher. A caller that sends a value-bearing `CALL` to `rewards(address)` will have the EVM state-transition logic debit `msg.value` from their EVM balance and credit it to the precompile's account, but the `rewards` executor never refunds or otherwise routes that value back to the caller, so the funds become permanently unrecoverable.

### Finding Description
The `Execute` dispatcher for the distribution precompile explicitly enforces `pcommon.ValidateNonPayable(value)` for `WithdrawValidatorCommissionMethod` before dispatch, and every other query method (`ParamsMethod`, `ValidatorOutstandingRewardsMethod`, `ValidatorCommissionMethod`, `ValidatorSlashesMethod`, `DelegationRewardsMethod`, `DelegatorValidatorsMethod`, `DelegatorWithdrawAddressMethod`, `CommunityPoolMethod`) is dispatched with `value` passed through to its handler, which internally validates it is non-payable (e.g. `delegationRewards` calls `p.validateInput(value, args, 2)`).

`RewardsMethod`, however, is dispatched as: [1](#0-0) 

and its handler `rewards(ctx, method, args)` does not even take a `value` parameter, so it is never inspected or rejected: [2](#0-1) 

This is confirmed by the repository's own integration test comment, which documents the quirk directly: [3](#0-2) 

This same missing check exists consistently across the current implementation and essentially every legacy version (`v65`, `v66`, `v67`, `v614`, `v620`, `v630`, `v640`), confirming it is a long-standing bug rather than a recent regression: [4](#0-3) 

The pattern used elsewhere in the precompile suite (`gov.deposit`, `staking.delegate`, `bank.sendNative`) shows the correct handling: when a precompile method is meant to accept native value, it must call `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei`, which explicitly refunds the payer and re-collects the amount as a `sdk.Coin`/`sdk.Int` to be spent by the underlying Cosmos message: [5](#0-4) [6](#0-5) 
Because `rewards()` never performs this dance and never rejects nonzero `value` via `ValidateNonPayable`, the wei the EVM already transferred into the precompile's balance as part of the `CALL` semantics is never routed anywhere — it neither triggers a Cosmos-side accounting event nor is refunded to the caller.

### Impact Explanation
This matches the report's bug class ("function should be non-payable but isn't validated, causing value to be mishandled") but with a stronger impact: instead of merely being unable to pay when payment is desired, here calling with value causes an unrecoverable loss/permanent freezing of the sender's native tokens, satisfying the "permanent freezing" criterion. Any unprivileged EVM account can trigger this in a single transaction by calling `rewards(address)` on the distribution precompile with a nonzero `value`; the funds cannot be withdrawn by any user-facing mechanism afterward.

### Likelihood Explanation
Trivially reachable: any EVM account can call the public precompile method `rewards(address)` at `0x...1007` with nonzero `value` in one transaction. No special permissions, delegation, or preconditions are required (the only optional dependency is having an associated Sei address for the argument decoding, which is unrelated to the value bug). The likelihood is High since the only barrier is a user or wallet integration mistakenly attaching value to what should be a `view` call — an easy mistake for tooling/bots that generically attach value or use pre-built payable interfaces.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to the `RewardsMethod` case in `Execute` (mirroring the check already applied to `WithdrawValidatorCommissionMethod`), and update the `rewards` handler signature to accept and reject nonzero `value`, consistent with the other query handlers (`validatorOutstandingRewards`, `validatorCommission`, etc.). Apply the same fix across all still-supported legacy versions of the distribution precompile that expose the same `rewards` dispatch path.

### Proof of Concept
1. Associate an EVM account with a Sei address and ensure it has a nonzero EVM/usei balance.
2. Construct and send an EVM transaction that performs a `CALL` (not `staticcall`) to `0x0000000000000000000000000000000000001007` with:
   - `data` = ABI-encoded `rewards(address)` for any delegator address (even the caller's own address),
   - `value` = any nonzero wei amount.
3. Observe the transaction succeeds (status = 1) and returns the rewards data as if it were a pure view call, exactly as demonstrated in the existing dispatch-semantics test: [7](#0-6) 
4. Check the caller's post-tx balance: it decreases by exactly `value` (plus gas), while no corresponding usei/wei credit occurs anywhere reachable by the caller (no `HandlePaymentUsei`/`HandlePaymentUseiWei` call exists in the `rewards` code path) — the funds are stuck at the precompile's account with no code path to reclaim them.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}

func HandlePaymentUseiWei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Int, sdk.Int, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	// refund payer because the following precompile logic will debit the payments from payer's account
	// this creates a new event manager to avoid surfacing these as cosmos events
	if err := bankKeeper.SendCoinsAndWei(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, usei, wei); err != nil {
		return sdk.Int{}, sdk.Int{}, err
	}
	if hooks != nil {
		newCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))
		if hooks.OnEnter != nil {
			hooks.OnEnter(depth+1, byte(vm.CALL), evmKeeper.GetEVMAddressOrDefault(newCtx, precompileAddr), evmKeeper.GetEVMAddressOrDefault(newCtx, payer), []byte{}, GetRemainingGas(newCtx, evmKeeper), value)
		}
		if hooks.OnExit != nil {
			hooks.OnExit(depth+1, []byte{}, 0, nil, false)
		}
	}
	return usei, wei, nil
}
