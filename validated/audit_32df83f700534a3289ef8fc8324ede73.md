### Title
OP_RETURN data output excluded from weight/fee calculation causes under-priced transactions that fall below the minimum relay feerate - ([File: networks/bitcoin/src/wallet/send.rs](File: networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` accepts a caller-supplied `data` payload which is appended as an `OP_RETURN` output, but the weight/vsize used for both the required-fee computation and the minimum-relay-fee check is calculated from `payments` only — the data output is never included. The resulting transaction therefore pays strictly less than the caller-requested `fee_per_vbyte`, and can pass the internal `TooLowFee` check while its real feerate is below Bitcoin's `DEFAULT_MIN_RELAY_TX_FEE`, making the signed transaction unrelayable.

### Finding Description
In `SignableTransaction::new`, the transaction skeleton is built with `payments`, then the `OP_RETURN` output is pushed onto `tx_outs`, and only afterwards is the fee weight computed:

```rust
// send.rs:193-204
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` reconstructs a `Transaction` whose `output` list contains only `payments` (and optionally `change`). The `data` output — up to 80 bytes of pushdata plus the 8-byte value field and script overhead, roughly ~95 weight-units/vbytes — is absent from the estimation. The same omission occurs in the change path at `send.rs:225-226`, which again passes `payments` (not `tx_outs`).

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` under-charges by up to `fee_per_vbyte * ~95` sats, so the transaction's realized feerate is lower than the caller specified.
2. The minimum-fee guard `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` uses the same under-counted `vbytes`. With `fee_per_vbyte = 1`, the check passes (equality), yet the real transaction is ~95 vbytes larger, so its actual feerate is < 1 sat/vbyte — below the 1000 sat/kvB relay floor — and standard nodes will reject it.
3. Because the actual paid fee is `sum(inputs) - sum(outputs)` and `tx_outs` (including the OP_RETURN) is what gets committed, the change amount is computed as `input_sat - payment_sat - fee_with_change` where `fee_with_change` is also under-estimated — i.e., change is over-credited and the fee shrinks further, worsening the effective feerate.

### Impact Explanation
Any caller that attaches `data` (public input to `SignableTransaction::new`) receives a transaction that silently pays a lower feerate than requested. At low fee rates — exactly what this fee estimator encourages — the transaction fails Bitcoin's minimum relay policy and cannot be broadcast/confirmed; the multisig has signed a transaction that miners will not accept, so the planned payment stalls until a new transaction is constructed. `fee()`/`needed_fee()` misreport the economics of the signed transaction.

### Likelihood Explanation
The bug is deterministic: it triggers on every `SignableTransaction::new` call with `data = Some(_)`. Triggering a policy rejection additionally requires a low `fee_per_vbyte` (≈1 sat/vb) or a sufficiently large `data` payload relative to transaction size, both of which are caller-controlled and realistic for OP_RETURN-carrying consolidation transactions.

### Recommendation
Compute weight/vsize over the outputs that will actually be serialized. Either pass `data` into `calculate_weight_vbytes` (adding a representative OP_RETURN output of the final size) or compute the weight from `tx_outs` directly after all outputs — payments, OP_RETURN, and change — have been appended. Re-derive `needed_fee` and the `TooLowFee` bound from that complete size, and size the change output against the corrected `fee_with_change`.

### Proof of Concept
```rust
// Construct a transaction whose only output is an 80-byte OP_RETURN,
// paying fee_per_vbyte = 1 sat/vbyte.
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
    vec![received_output],                       // one P2TR input
    &[],                                         // no payments
    Some(change_script),                         // or None; applies either way
    Some(data.clone()),                          // 80-byte OP_RETURN
    1,                                           // 1 sat/vbyte
).unwrap();

// vbytes was estimated WITHOUT the OP_RETURN output.
// needed_fee = 1 * vbytes_no_data, which passes the TooLowFee check since
// needed_fee == vbytes_no_data == (1000 * vbytes_no_data) / 1000.
//
// The real serialized transaction includes the ~95-vbyte OP_RETURN output,
// so its actual feerate is  vbytes_no_data / (vbytes_no_data + ~95) < 1 sat/vb,
// below DEFAULT_MIN_RELAY_TX_FEE (1000 sat/kvB) -> rejected by relay policy.
assert_eq!(tx.needed_fee(), /* vbytes without the data output */);
// tx.fee() == needed_fee, confirming the fee paid is the underestimated value.
```

The contrast with `test_data` (`networks/bitcoin/tests/wallet.rs:290-325`) is telling: the test verifies the OP_RETURN output exists but never checks that the paid fee covers the data output's size, so the omission goes uncaught.
