### Title
Denial of service via unbounded-length string in `Offer.from_bech32` bech32 decoding — ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.from_bech32()` calls `bech32_decode(offer_bech32, max_length=len(offer_bech32))`, which overrides the library's normal 90-character cap with the length of the attacker-supplied string itself, so there is effectively no upper bound on how large an "offer" string a wallet, CLI, or RPC caller will attempt to decode. [1](#0-0) 

### Finding Description
`bech32_decode` normally rejects any string longer than `max_length` (default 90, matching legitimate bech32-encoded addresses): [2](#0-1) 

`Offer.from_bech32` explicitly defeats that protection by passing `max_length=len(offer_bech32)`, meaning any string, no matter how large, is accepted for full decoding (per-character `ord()` validation, `rfind`, charset membership scan, and full bech32 checksum computation over the entire payload): [1](#0-0) 

This function is reachable from numerous unauthenticated/low-trust entry points that accept attacker-controlled offer strings:
- `TakeOffer.parsed_offer` (wallet RPC `take_offer`), decoded lazily via `Offer.from_bech32(self.offer)`. [3](#0-2) 
- `GetOfferSummary`/`CheckOfferValidity` RPC handlers call `Offer.from_bech32` directly on the request string. [4](#0-3) 
- The CLI `take_offer` command parses an offer file/string of arbitrary size the same way. [5](#0-4) 

After bech32 decoding, the payload passes through `convertbits` and then `try_offer_decompression` → `decompress_object_with_puzzles`, which does apply a `max_length=6*1024*1024` cap on the zlib decompression output. [6](#0-5) 

However, that downstream cap only bounds the *decompressed* size — it does nothing to bound the cost of the initial bech32/base32 decoding pass itself, which is linear-but-unbounded in the length of the attacker-supplied string (character validation, `rfind`, charset membership check via `all(...)`, and `bech32_polymod` checksum, each iterating over every character). An attacker (any wallet counterparty, or any caller of the RPC endpoints above) can therefore submit an arbitrarily large string (megabytes to gigabytes) as an "offer," forcing the receiving wallet/full node to allocate and iterate over the entire string in Python before any size or validity check meaningfully rejects it. This is directly analogous to the Mattermost issue: a client-supplied string field (there: emoji; here: an "offer" bech32 blob) that is not length-validated before expensive processing, allowing repeated submission of very large strings to exhaust CPU/memory on the receiving node.

### Impact Explanation
Any Data Layer/offer counterparty, or a caller with access to a wallet's RPC (`take_offer`, `get_offer_summary`, `check_offer_validity`, `get_all_offers` file round-trip), can submit an oversized "offer" string. Because the intentional length cap was removed by design (`max_length=len(offer_bech32)`), repeated submissions of very large strings can consume disproportionate CPU/memory in the wallet process handling untrusted offer input, potentially degrading or halting the wallet's transaction-processing capability (a resource-exhaustion DoS against wallet spend/offer processing), matching the CWE-400/CVSS profile of the reference advisory (availability impact, no confidentiality/integrity impact).

### Likelihood Explanation
High likelihood of triggerability: no special privileges are required, the vulnerable code path is reachable by any external counterparty offering a trade or any RPC caller supplying an offer string, and the fix (removing the intentional `max_length` override) is trivial to identify from the code, making the bug easy to discover and exploit.

### Recommendation
Restore a sane upper bound on `bech32_decode` length in `Offer.from_bech32` (e.g., use the library default or a fixed generous-but-bounded maximum tied to the maximum plausible compressed-offer size, not `len(offer_bech32)` itself), and validate/reject oversized offer strings before performing any bech32 character/checksum scanning.

### Proof of Concept
1. Construct a very large string (e.g. tens of MB) consisting only of valid bech32 charset characters plus an `hrp` + `1` separator, so it passes the initial character-set filter in `bech32_decode`.
2. Submit it as the `offer` field to the wallet RPC `take_offer`, `get_offer_summary`, or `check_offer_validity` endpoint, or pass it as a CLI argument to `chia wallet take_offer`.
3. Observe that `Offer.from_bech32` → `bech32_decode(offer_bech32, max_length=len(offer_bech32))` processes the entire string (character validation + checksum computation) with no early length rejection, consuming CPU/memory proportional to the attacker-chosen string size; repeated submissions amplify resource consumption on the target wallet process. def bech32_decode(bech: str, max_length: int = 90) -> tuple[str | None, list[int] | None]:
```python
    """Validate a Bech32 string, and determine HRP and data."""
    bech = bech.strip()
    if (any(ord(x) < 33 or ord(x) > 126 for x in bech)) or (bech.lower() != bech and bech.upper() != bech):
        return (None, None)
    bech = bech.lower()
    pos = bech.rfind("1")
    if pos < 1 or pos + 7 > len(bech) or len(bech) > max_length:
        return (None, None)
    if not all(x in CHARSET for x in bech[pos + 1 :]):
        return (None, None)
    hrp = bech[:pos]
    data = [CHARSET.find(x) for x in bech[pos + 1 :]]
    if not bech32_verify_checksum(hrp, data):
        return (None, None)
    return hrp, data[:-6]
```

```python
def decompress_with_zdict(blob: bytes, zdict: bytes) -> bytes:
    do = zlib.decompressobj(zdict=zdict)
    return do.decompress(blob, max_length=6 * 1024 * 1024)  # Limit output size


def decompress_object_with_puzzles(compressed_object_blob: bytes) -> bytes:
    version = int.from_bytes(compressed_object_blob[0:2], "big")
    if version > len(ZDICT):
        raise CompressionVersionError(version)
    zdict = zdict_for_version(version)
    object_bytes = decompress_with_zdict(compressed_object_blob[2:], zdict)
    return object_bytes
```
