### Title
Attacker-controlled submodule path escapes repository root in `buildSubmoduleDiff()` without the containment check used elsewhere - (File: `app/src/lib/git/diff.ts`)

### Summary
GitHub Desktop enforces a path-containment guard (`isAbsolute()` + `resolveWithin()`) whenever it turns an *untrusted* path into a filesystem action reachable from outside the repo — specifically the `filepath` query parameter of the `x-github-client://openRepo/...` deep link. [1](#0-0)  That guard exists precisely so a crafted deep link can't make Desktop touch anything outside the cloned repository.

However, the same class of untrusted, attacker-supplied path — the **submodule path**, which comes straight from a cloned/fetched repository's `.gitmodules`/tree content — is turned into a filesystem path in `buildSubmoduleDiff()` with a plain `Path.join()` and **no** equivalent containment check: [2](#0-1)  This mirrors the Lens bug pattern exactly: a validation exists on the "normal" entry point (`FollowLib::follow()` blocking self-follow) but a different, less-guarded entry point that reaches the same sensitive effect (`FollowNFT::tryMigrate()`) has no such check.

### Finding Description
`buildSubmoduleDiff()` computes `fullPath = Path.join(repository.path, path)` where `path` is `file.path`, i.e. the submodule's path as recorded in the repository the user cloned/fetched — fully attacker-controlled content in a malicious repository. Unlike `dispatcher.openRepositoryFromUrl()`, which validates a similarly untrusted, externally-supplied path via `isAbsolute(filepath)` rejection and `resolveWithin(repository.path, filepath)` before any filesystem action, `buildSubmoduleDiff()` performs no traversal check at all. This `fullPath` becomes `ISubmoduleDiff.fullPath` and is surfaced to the UI's "Open this submodule on GitHub Desktop" action in `SubmoduleDiff`, which forwards it verbatim via `onOpenSubmoduleClick` to the `onOpenSubmodule` callback: [3](#0-2) 

If a submodule's recorded path contains traversal segments (e.g. `../../../../.ssh` in `.gitmodules`), `Path.join(repository.path, path)` will resolve outside the repository root, and this un-sanitized value flows into the "open as repository" action without ever passing through the `resolveWithin`-style containment check that the deep-link `filepath` action deliberately applies.

### Impact Explanation
This corrupts the invariant that "submodule paths displayed/acted upon by Desktop must stay within the cloned repository." Depending on what the downstream `onOpenSubmodule` handler does with the resulting path (adding it as a tracked/opened repository, running git operations in it, or revealing it in the file manager), the attacker-supplied traversal path can cause Desktop to operate on, expose, or add an arbitrary directory on the victim's filesystem outside the repository they intended to clone — matching the report's "file read outside the repo" / "silent corruption of app state" impact class. This is directly analogous to `FollowNFT::tryMigrate()` skipping a check that exists on the primary code path (`FollowLib::follow()`), letting an invariant be bypassed through a secondary, less-scrutinized entry point.

### Likelihood Explanation
The attacker only needs the victim to clone/fetch a malicious repository containing a crafted submodule path and then view the diff for that submodule in Desktop's Changes/History view — no unusual user action, no admin rights, no local access, and no prior compromise required. This satisfies the "attacker controls a cloned/fetched repository" criterion directly.

### Recommendation
Apply the same containment check used in `dispatcher.openRepositoryFromUrl()` to submodule paths before constructing `fullPath` in `buildSubmoduleDiff()`: reject the diff item's `fullPath`/refuse the "Open Repository" action when `await resolveWithin(repository.path, path)` returns `null`, instead of trusting `Path.join()` output directly.

### Proof of Concept
1. Attacker creates a repository with a `.gitmodules` entry whose `path` is a traversal string, e.g. `path = ../../../../../../Users/victim/.ssh`.
2. Victim clones this repository in GitHub Desktop.
3. Desktop computes the submodule diff via `buildSubmoduleDiff()`, producing `fullPath = Path.join(repository.path, '../../../../../../Users/victim/.ssh')`, which resolves outside the repo (no `resolveWithin` check is applied, unlike the analogous `filepath` deep-link handling in `dispatcher.ts`). [2](#0-1) 
4. Victim clicks "Open this submodule on GitHub Desktop" in the Submodule diff view, which passes this unvalidated `fullPath` to the `onOpenSubmodule` handler. [3](#0-2) 

Note: I was not able to trace the exact final consumer wired to `onOpenSubmodule` (the prop is passed down from a parent diff component) within the available search budget, so the precise terminal effect (e.g., whether it opens the path as a new repository, calls `shell.showItemInFolder`, or something else) is unconfirmed — I recommend a Devin session with full repo access to trace `onOpenSubmodule`'s wiring and confirm the exact sink before treating severity as final.
