### Title
Stale index-based partial-diff selection can silently commit unintended lines after concurrent file mutation - (File: app/src/lib/stores/app-store.ts)

### Summary
GitHub Desktop tracks a user's partial "stage these lines" selection using raw line indices (`DiffSelection.divergingLines`), not line content or hunk anchors. When a tracked file is modified on disk between the time a partial selection is made and the time the commit is created, Desktop revalidates the selection only against the *set* of selectable indices in the newly-loaded diff — not against whether those indices still correspond to the same content.

### Finding Description
`updateChangedFiles` preserves `existingFile.selection` across a status refresh purely keyed by file `id` (path + kind), regardless of content changes: [3](#0-2) 

`updateChangesWorkingDirectoryDiff` then "reconciles" the previous selection with a freshly-fetched diff by computing the new `selectableLines` set and calling `withSelectableLines`, explicitly acknowledging in its own comment that it does not verify content, only that the index is still "includeable": [1](#0-0) 

`DiffSelection.withSelectableLines` simply filters `divergingLines` by index membership in the new `selectableLines` set — it never compares the actual line text: [2](#0-1) 

This is structurally identical to the reported smart-contract flaw: a value (validator balance / diff selection) is carried forward across a state transition (deactivate-then-reactivate / async diff refresh race) without being recomputed against the true current state, because the guard only checks *existence*/*index membership*, not *identity of content*.

### Impact Explanation
If a file's diff hunks shift (lines inserted/removed above the previously selected lines) after a partial selection was made but before commit — e.g., a build tool, formatter, git hook, `.gitattributes` filter, or an external process modifies the file, or the diff is momentarily reloaded while a background operation touches the working tree — the same numeric line indices can now point to entirely different content. Desktop will silently commit whatever content now occupies those indices, meaning the user's authored commit can contain lines they never reviewed or intended to stage. This is a silent corruption of what the user commits, one of the explicitly valid impact categories.

### Likelihood Explanation
This requires no attacker privilege beyond normal repository interaction: any process that mutates a tracked file in the working directory while Desktop has a partial selection pending (a common workflow — partial staging is a core Desktop feature) can trigger the stale-index reuse. The `updateChangesWorkingDirectoryDiff` code path runs on every diff refresh, and the comment at line 3480-3485 explicitly documents that the implementers were aware line-identity is not preserved ("we'll settle on just updating the selectable lines… for now"), indicating this is a known, unaddressed gap rather than a hypothetical.

### Recommendation
When reconciling a partial `DiffSelection` against a newly loaded diff, validate selection identity by line content (or a stable anchor such as unified-diff hunk + line text hash) rather than raw index membership. If the content at a previously-selected index no longer matches, drop that line from the selection (fail closed) instead of silently carrying the index forward, analogous to zeroing out a stale value at the point where it would otherwise be reused.

### Proof of Concept
1. Modify a tracked file to add several new lines, producing a multi-hunk diff.
2. In Desktop's Changes view, use partial line selection to stage only specific lines in a later hunk (e.g., line index 40).
3. Before committing, have another process (editor auto-format, a git hook, or a script) insert/remove lines earlier in the same file, shifting all subsequent line numbers, and trigger a diff refresh (e.g., switch away from and back to the file, or wait for background refresh).
4. Observe that `updateChangesWorkingDirectoryDiff` recomputes `selectableLines` and calls `withSelectableLines`, which keeps index 40 selected only because it is still within the "selectable" set — even though the content at index 40 is now different from what the user originally selected.
5. Commit: the resulting commit contains the new content at that index, not the line the user reviewed and intended to stage — a silent, unreviewed content change captured in the user's commit.

    const divergingLines = this.divergingLines

      divergingLines,
      selectableLines
    )
  }
