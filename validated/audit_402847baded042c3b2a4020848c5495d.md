### Title
Symlinked `.gitignore` in a cloned repo causes arbitrary local file read (and write) outside the repo tree - (File: `app/src/lib/git/gitignore.ts`)

### Summary
Git checkouts can materialize tracked symlinks as real filesystem symlinks (mode `120000`). If an attacker-controlled repository commits `.gitignore` as a symlink pointing to an absolute path outside the repository (e.g. `~/.ssh/id_rsa`, a config file, etc.), `readGitIgnoreAtRoot` will transparently follow that symlink and display the target file's contents in the "Repository Settings > Ignored Files" UI, and `saveGitIgnore`/`appendIgnoreRule` will write through the same symlink and overwrite the target file.

### Finding Description
`readGitIgnoreAtRoot` builds `ignorePath` via `Path.join(repository.path, '.gitignore')` and calls `FS.readFile(ignorePath, 'utf8', ...)` [1](#0-0) . Node's `fs.readFile` dereferences symlinks by default. Nothing in this function (or its caller in `RepositorySettings.componentWillMount`) checks whether `.gitignore` is a symlink or restricts the resolved target to stay inside `repository.path` [2](#0-1) .

The same absence of protection exists on the write side: `saveGitIgnore` calls `writeFile(ignorePath, fileContents)` from `fs/promises`, which also follows symlinks, meaning a save will overwrite whatever file the symlink points to [3](#0-2) . `appendIgnoreRule`, used by the common "Ignore file"/"Ignore folder" context-menu actions in the Changes list, reads then re-saves through the same unguarded path [4](#0-3) [5](#0-4) .

This is notable because the codebase already has a purpose-built defense for exactly this class of bug — `resolveWithin` in `app/src/lib/path.ts`, which explicitly detects and rejects symlink-based escapes from a root directory (its own test suite verifies this: "fails for paths that use a symlink to traverse outside of the root") [6](#0-5) , and it is used elsewhere (`dispatcher.ts`, `app-store.ts`, `copilot-conflict-context.ts`) but not in `gitignore.ts`.

### Impact Explanation
- **Read impact:** Opening Repository Settings > Ignored Files after cloning such a repo silently discloses the contents of an arbitrary local file (readable by the desktop process) inside the app UI — a file read outside the repository tree, matching the "file read outside the repo" impact category.
- **Write impact (more severe):** If the user edits and saves the Ignored Files tab, or uses the very common "Ignore file"/"Ignore folder" context-menu action on any change, `saveGitIgnore`'s `writeFile` follows the symlink and overwrites the target file's contents with gitignore text — an arbitrary file write outside the repository, which can corrupt or destroy sensitive local files (e.g. SSH keys, shell profiles) the attacker chose as the symlink target.

### Likelihood Explanation
The attacker only needs to commit a symlinked `.gitignore` in a repository the victim clones — no admin rights, malware, or unusual steps required. Reading the leaked content requires the victim to open Repository Settings > Ignored Files (a normal workflow), and the write path is triggered by an extremely common action: right-clicking a changed file and choosing "Ignore file", which many users do routinely without suspecting anything unusual, since the target path/filename is invisible to them.

### Recommendation
Before reading or writing `.gitignore`, verify with `fs.lstat`/`fs.promises.lstat` that the path is a regular file (not a symlink), or use the repo's existing `resolveWithin(repository.path, '.gitignore')` helper together with `fs.open(..., 'r'/'w', { flag: 'wx' or O_NOFOLLOW })` semantics to refuse to read/write through symlinks that escape the repository root. Reject/skip `.gitignore` entries that are symlinks rather than regular files, both on read and on write in `readGitIgnoreAtRoot` and `saveGitIgnore`.

### Proof of Concept
1. Attacker creates a repo where `.gitignore` is committed as a symlink to `/home/victim/.ssh/id_rsa` (or another sensitive path), e.g.:
   ```
   ln -s /home/victim/.ssh/id_rsa .gitignore
   git add .gitignore && git commit -m "add gitignore"
   ```
2. Victim clones the repo in GitHub Desktop (default `core.symlinks=true` materializes the symlink on checkout on macOS/Linux).
3. Victim opens Repository Settings > Ignored Files — the textarea renders the contents of `id_rsa` instead of a normal gitignore file, because `readGitIgnoreAtRoot` followed the symlink [7](#0-6) .
4. If the victim edits and clicks Save (or uses "Ignore file" from the Changes context menu), `saveGitIgnore`'s `writeFile` overwrites `id_rsa` with the new gitignore content, destroying the private key [8](#0-7) .
