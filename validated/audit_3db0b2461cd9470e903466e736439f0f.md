### Title
Checks-effects-interactions violation in `IntentGatewayV2.withdraw()` decrements escrow after external token transfer - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of the Intent Gateway settlement path performs the outbound token transfer to the order beneficiary *before* debiting the internal `_orders[commitment][token]` escrow accounting, reproducing exactly the checks-effects-interactions violation pattern described in the source report (state mutated after, not before, an external call).

### Finding Description
In `withdraw()`, for every token in the withdrawal request the contract does: [1](#0-0) 
i.e. it sends native ETH via `beneficiary.call{value: amount}("")` (or an ERC20 `transfer` call) to an address fully controlled by the withdrawal beneficiary, and only afterward executes `_orders[body.commitment][token] -= amount;`. This is the same class of bug flagged in the report ("`distributeToOwner()` sends the contract's balance ... before clearing the internal accounting").

By contrast, the primary (non-Tron) EVM implementation of the same logic in `IntentsBase.sol` performs the decrement first and the transfer second: [2](#0-1) 
confirming that the correct ordering was implemented elsewhere in the codebase but the Tron variant diverged and reintroduced the unsafe pattern.

`withdraw()` is reachable from two `onlyHost`-gated entry points, `onAccept` (RedeemEscrow/RefundEscrow) and `onGetResponse`: [3](#0-2) [4](#0-3) 

For the primary EVM host, direct re-entry into `onAccept`/`dispatchIncoming` for the *same* commitment is blocked because the request receipt is written before the external call: [5](#0-4) 
This is the guard that keeps the vulnerable CEI ordering in `withdraw()` from being trivially exploitable through a replayed `onAccept`. I was not able to locate or confirm an equivalent host/handler implementation for the Tron chain within the indexed contents (the Tron host/handler contracts were not returned by search), so I cannot confirm whether Tron's host applies the same receipt-before-call ordering, nor whether Tron's `TRC20`/native-transfer semantics allow a reentrant callback during `.call{value:}` the same way EVM does.

### Impact Explanation
If the Tron host's request/response dispatch does **not** set the replay-protection receipt before invoking `onAccept`/`onGetResponse` (unverified — Tron host/handler source was not found in the index), a malicious beneficiary contract could reenter during the native-token `.call{value: amount}("")` in `withdraw()` and drain escrowed funds for the same commitment multiple times, or interleave with `cancelOrder`/other order-state-dependent functions before `_orders[...]` and `_filled[...]` are fully settled. At minimum, this is a structural CEI violation in the fund-release path of the Intent Gateway's cross-chain settlement, which is exactly the class of bug the source report flags as a general attack-surface risk warranting defense-in-depth even against "trusted" call targets — here the call target (`beneficiary`) is an **attacker-chosen, untrusted address** (the order's own beneficiary/solver), which is a stronger threat model than the report's "trusted contract" caveat.

### Likelihood Explanation
Medium-to-uncertain: the vulnerable ordering is real and directly present in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`, and the beneficiary/solver address is attacker-controllable by construction (any account can be named beneficiary/solver of an order it fills). However, full exploitability depends on the Tron host's message-dispatch ordering (receipt-before-call), which could not be located and verified in this pass — this is the key missing piece needed to escalate from "unsafe pattern" to "provable double-spend."

### Recommendation
Move `_orders[body.commitment][token] -= amount;` (and the `TRANSACTION_FEES` decrement) to occur **before** the corresponding external transfer call in `withdraw()`, mirroring the already-correct ordering in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. Additionally, verify (and if necessary add) a `nonReentrant` guard on `withdraw()`/`onAccept`/`onGetResponse` in the Tron contract, and confirm that the Tron host writes request/response receipts before invoking `onAccept`, matching `EvmHost.sol`'s pattern.

### Proof of Concept
Conceptual (partially unverified due to missing Tron host source):
1. Attacker places or fills a cross-chain order naming their own malicious contract as `beneficiary`/`order.user`.
2. On settlement, Hyperbridge delivers a `RedeemEscrow`/`RefundEscrow` message; the Tron host invokes `onAccept` → `withdraw()`.
3. `withdraw()` sends native ETH to the malicious beneficiary via `beneficiary.call{value: amount}("")` *before* decrementing `_orders[commitment][token]`.
4. If the Tron host does not set the request receipt before this call (unverified), the beneficiary's fallback reenters the host to redeliver/reprocess the same message, causing `withdraw()` to run again against the still-undecremented `_orders[commitment][token]`, transferring the same escrowed amount twice.
