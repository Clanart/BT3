### Title
Missing-index panic in `GeneratorPromotion::complete` lets an unprivileged peer crash honest participants - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` validates only the *count* and the *upper bound* of the `proofs` map keys, then indexes the map with `proofs.get(&i).unwrap()` for every participant `i` in `1 ..= n` other than itself. An attacker who controls or relays promotion proofs can submit a well-formed map whose keys all satisfy `<= n` and whose length is exactly `n - 1`, yet which contains the victim's own `Participant` index (or omits any required index). The `.unwrap()` then panics, aborting the victim's key-promotion session — the Serai analog of CVE-2023-5171's "potentially exploitable crash" (A:H, Medium).

### Finding Description
The validation in `complete` is:

```rust
if proofs.len() != (usize::from(params.n()) - 1) { ... }
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() { ... }
}
```

followed by an unconditional lookup:

```rust
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();   // panic if i absent
``` [1](#0-0) 

Nothing rejects a `proofs` entry keyed by `params.i()` itself, and nothing verifies the map's key set equals `all_participant_indexes() \ {i}`. For `n = 3` and victim `i = 2`, a map `{2: P, 3: P}` passes both checks (len = 2 = n-1, all keys <= 3) but lacks index `1`, so `proofs.get(&Participant(1)).unwrap()` panics.

### Impact Explanation
A single malicious participant (or a coordinator/mixer supplying the aggregated `HashMap`) can deterministically panic every other participant's promotion. If promotion runs in a service context (node key rotation, generator migration), this is a remote, input-triggered crash — exactly the availability impact class of the source CVE (write of NUL bytes → crash here is an unwrap panic → abort). The panic occurs *before* any proof verification, so it costs the attacker nothing — the fake proofs are never even checked.

### Likelihood Explanation
Any unprivileged party able to supply or influence the `proofs` map to `complete` triggers it with trivially constructed input (duplicate one's own index, or swap in the victim's index for a missing one). No timing, race, or probabilistic element is required; it is 100% reliable.

### Recommendation
Validate the key set rather than relying on the count: iterate `1 ..= params.n()` and, for each `i != params.i()`, use `proofs.get(&i).ok_or(PromotionError::MissingProof(i))?` instead of `.unwrap()`; additionally reject any map containing `params.i()`. Alternatively reuse `dkg::validate_map`-style set-equality checking as done in `pedpop::KeyMachine::calculate_share`.

### Proof of Concept
```rust
// n = 3, victim is participant 2
let (promotion, _proof) =
  GeneratorPromotion::<C, C2>::promote(&mut rng, victim_keys.clone());

let mut proofs = HashMap::new();
// Attacker supplies n - 1 = 2 entries, all with keys <= n, but keyed by
// the victim's own index and participant 3 — participant 1 is missing.
proofs.insert(Participant::new(2).unwrap(), attacker_proof_a); // wrong key!
proofs.insert(Participant::new(3).unwrap(), attacker_proof_b);

// Passes len check (2 == n-1) and the i <= n check,
// then panics at proofs.get(&Participant(1)).unwrap()
let _ = promotion.complete(&proofs); // thread panic
```
