### Title
`SignableTransaction::new` omits the OP_RETURN output from weight/fee and size-limit accounting, undercharging the fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the reported bug (an amount expressed in raw gas units was added to a gas *cost* without conversion, so the real cost was undercharged), `SignableTransaction::new` computes `vbytes`/`weight` from `payments` only, but the transaction actually built also includes the OP_RETURN `data` output. The extra output's weight is never converted into fee, so the resulting transaction pays a lower effective fee rate than `fee_per_vbyte`, and can silently exceed `MAX_STANDARD_TX_WEIGHT`.

### Finding Description
`SignableTransaction::new` pushes the OP_RETURN output onto `tx_outs` at lines 194-202, then calculates the weight/vbytes used for fee estimation via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) and `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (line 226). Both calls pass `payments`, which does not include the `data` output. [1](#0-0) 

Consequently:
- `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change` (line 227) under-count the OP_RETURN output's vbytes. When a change output is produced, the change amount is `input_sat - payment_sat - fee_with_change` (line 228), so the actual fee paid (`sum(inputs) - sum(outputs)`, line 139) equals the underestimated `needed_fee` — the transaction's real fee rate is strictly below the requested `fee_per_vbyte`.
- The `NotEnoughFunds` check (line 215) is performed against the under-estimated fee, and the standardness check `weight > MAX_STANDARD_TX_WEIGHT` (line 241) uses a `weight` that never includes the OP_RETURN bytes, so a transaction that is actually non-standard can be constructed, signed, and broadcast.

This mirrors the report's root cause: a cost accounting formula that omits a term which must be included (there, `refundPostOpCost * gasPrice`; here, the `data` output's contribution to vbytes/weight), producing a fee lower than intended. [2](#0-1) 

### Impact Explanation
An unprivileged user requesting a Bitcoin withdrawal/burn supplies the `data` bytes that become the OP_RETURN output. With `data` present and a change output produced, the resulting threshold-signed transaction pays less than the configured fee rate — potentially falling below relay/mining expectations and stalling the payout — and is never checked for the true weight, so it can exceed `MAX_STANDARD_TX_WEIGHT` and be rejected by the network while Serai considers the funds sent.

### Likelihood Explanation
Any public input path that produces an OP_RETURN `data` output on a Bitcoin send triggers the miscalculation; it requires no malicious validator, no collusion, and no leaked keys — only that `data.is_some()` in `SignableTransaction::new`.

### Recommendation
Include the full output set in the weight calculation: pass `tx_outs` (or `payments` plus the OP_RETURN output) into `calculate_weight_vbytes` both for the no-change and with-change calls, so `needed_fee`, `fee_with_change`, the `NotEnoughFunds` check, and the `MAX_STANDARD_TX_WEIGHT` check all account for the data output.

### Proof of Concept
Conceptual: call `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)` with `input_sat` chosen so change exists. The constructed `tx.output` contains `payments.len() + 2` outputs (payments + OP_RETURN + change), while `needed_fee` was computed for only `payments.len() + 1` outputs. `tx.weight()` on the signed result exceeds the `weight` used at line 241, and `fee() / actual_vbytes < fee_per_vbyte`.
