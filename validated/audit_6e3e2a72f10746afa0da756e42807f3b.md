### Title
Transaction fee computed from stale vsize that excludes the OP_RETURN data output - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

`SignableTransaction::new` builds `tx_outs` including an optional OP_RETURN `data` output, but computes `weight`/`vbytes`/`needed_fee` by calling `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which reconstructs a transaction from `payments` only. The `data` output's weight is never accounted for, so the fee committed to (`needed_fee`) is stale with respect to the transaction that is actually signed and broadcast. This mirrors the reported bug class: an update (here, the fee/change commitment the signature signs over) uses a previously stored value rather than the value describing the current state. ### Finding Description

In `SignableTransaction::new`:

1. The data output is pushed onto `tx_outs` before the size calculation (lines 194-202).
2. `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` (line 204) passes `payments`, not `tx_outs`. Inside `calculate_weight_vbytes`, the mock transaction's `output` list is built solely from `payments` plus an optional change output (lines 85-99). The OP_RETURN output is absent from the weight measurement.
3. `needed_fee = fee_per_vbyte * vbytes` (line 206) and the minimum-relay-fee check (line 211) both use this stale `vbytes`.
4. The same stale measurement feeds the change path: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (line 226) also omits the data output, so `fee_with_change` and the change amount `input_sat - (payment_sat + fee_with_change)` are computed as if the data output did not exist.

The resulting `SignableTransaction.tx` (which is what the FROST `TransactionMachine` sighashes via `taproot_key_spend_signature_hash` over `Prevouts::All`, lines 373-390) does contain the data output. So the signature commits to a transaction whose real vsize is larger than the `vbytes` used for fee policy: the effective fee rate is `needed_fee / actual_vbytes < fee_per_vbyte`. [3](#0-2) [4](#0-3) 

### Impact Explanation

- The transaction pays strictly less fee per vbyte than the caller requested. Up to ~80 bytes of OP_RETURN data plus output overhead (~10 bytes, so up to roughly 90+ vbytes, ~30-45% overhead on a typical 1-in/2-out Taproot transaction) go unfunded.
- The `TooLowFee` guard uses the stale `vbytes`, so a caller specifying `fee_per_vbyte` at or near the relay minimum produces a transaction whose real fee rate is below `DEFAULT_MIN_RELAY_TX_FEE` — it will be rejected by Bitcoin nodes' mempool. Funds committed to payments/change are then unspendable until an entirely new transaction is constructed and re-signed by the threshold set; there is no RBF/fee-bump path in this code.
- Because `change = input_sat - payment_sat - fee_with_change` was computed against the underestimated fee, the accounting still balances, so nothing downstream detects the shortfall — the defect only manifests as broadcast failure or underpriced transactions, which is exactly the "corrupted accounting invisible to later consumers" shape of the source bug.

### Likelihood Explanation

The `data` parameter is attacker-influenced: it carries the Serai `OutInstruction` payload embedded in withdrawal transactions, and an unprivileged user can supply up to the 80-byte limit (`TooMuchData` check, line 171). Any caller using a fee rate within ~`data_len/tx_vsize` of the relay minimum produces a non-propagating transaction. Even at moderate fee rates, every data-bearing transaction silently pays a lower effective rate than intended, degrading confirmation reliability for a fixed class of outputs.

### Recommendation

Include the data output in the size calculation, e.g. by passing the full output list to `calculate_weight_vbytes` instead of `payments`:

```rust
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs_as_scripts, None);
```

or move the OP_RETURN push into `payments`-equivalent form before measurement so `vbytes`, `needed_fee`, the `TooLowFee` check, and the `fee_with_change`/change-amount branch all reflect the transaction actually signed. Alternatively, recompute `vbytes` from `tx_outs` after construction (`self.tx.vsize()`) and use that everywhere.

### Proof of Concept

```rust
// Construct inputs with enough funds
let inputs = vec![received_output];                 // e.g. 10_000 sats
let payments = &[(p2tr_script_buf(key).unwrap(), 5_000)];
let data = Some(vec![0xaa; 80]);                    // max-size OP_RETURN payload
let fee_per_vbyte = 1;                              // ~relay minimum

let stx = SignableTransaction::new(inputs, payments, None, data, fee_per_vbyte).unwrap();

// needed_fee was charged on vbytes WITHOUT the ~90-byte OP_RETURN output
let actual_vbytes = stx.transaction().vsize() as u64;
assert!(stx.needed_fee() < actual_vbytes);          // effective rate < 1 sat/vB
// stx.fee() == needed_fee, so the signed tx is below min relay fee and is rejected
```

The assertion holds because `needed_fee == fee_per_vbyte * vbytes_no_data` while `transaction()` includes the OP_RETURN output, so `needed_fee / actual_vbytes < fee_per_vbyte`.

Caveat I could not fully resolve within scope: the exact call sites supplying `data` (the processor-side scheduler/plan construction that turns `OutInstruction`s into `SignableTransaction`s) sit outside the listed in-scope files, so attacker control of the `data` field is inferred from the `InInstruction`/`OutInstruction` design rather than verified line-by-line.
