## Analysis

The Node.js report's broken invariant is: *"once a path has been through the canonicalizing/sanitizing step, everything downstream can trust it as safe."* The exploit shows that this trust boundary can be violated between sanitization and consumption.

GitHub Desktop has the exact same architectural pattern. It defines a hardened, symlink-aware path-containment helper, `resolveWithin()`, which normalizes, rejects null bytes, and — critically — calls `realpath()` on both the root and the candidate to make sure a symlink cannot walk the resolved path outside the repository root: [1](#0-0) 

This helper is correctly used in a few places, e.g. `openRepositoryFromUrl` in the dispatcher and the Copilot conflict-context builder: [2](#0-1) [3](#0-2) 

However, several other sinks that turn a **repository-relative path taken from git status/diff output** (i.e., attacker-controlled content of a cloned/fetched repository) into a filesystem action bypass `resolveWithin` entirely and use plain `Path.join`, with no symlink or root-containment check:

- `revealInFileManager()` — shows the resolved path in Finder/Explorer: [4](#0-3) 
- `onOpenInExternalEditor` in the main app view: [5](#0-4) 
- The commit file context menu, which wires up "Reveal in Finder", "Open in External Editor" and "Open with Default Program": [6](#0-5) 
- `openFile()`, which is what "Open with Default Program" ultimately calls, handing the joined path straight to `shell.openExternal('file://' + fullPath)`: [7](#0-6) 
- The "safe extension" gate used to decide whether "Open with Default Program" is even offered only inspects the *string suffix* of `file.path`, not the resolved target: [8](#0-7) 
- The submodule diff full path is likewise built with a raw `Path.join(repository.path, path)` from `.gitmodules`/submodule status output, with no containment check: [9](#0-8) 

### Title
Symlink-based path traversal in file-reveal / open-in-editor / open-with-default-program actions bypasses Desktop's own `resolveWithin` containment check - (File: `app/src/lib/app-shell.ts`, `app/src/ui/history/selected-commits.tsx`, `app/src/ui/lib/open-file.ts`)

### Finding Description
Desktop's own hardened path helper, `resolveWithin()`, exists specifically to stop a repository-relative path from escaping the repository root via a symlink, using `realpath()` to canonicalize both the root and the candidate before comparing prefixes: [10](#0-9) 

This is precisely the class of protection that the Node.js `path.resolve()`/`Buffer.from()` invariant was trying to provide. But — mirroring the report's finding that the invariant doesn't hold everywhere it's assumed to — Desktop only applies `resolveWithin` in some call sites (`dispatcher.ts`'s deep-link handler, the Copilot conflict-context builder) and *not* in the much more commonly exercised commit/changes context-menu actions that reveal, open, or launch a file straight from git status/diff `file.path` values, via plain `Path.join(repository.path, path)`: [4](#0-3) [6](#0-5) 

Because `file.path` is derived from the on-disk state of a repository that the attacker fully controls (a committed symlink whose target points outside the repo, e.g. `..%2f..%2f..%2f.ssh` or an absolute path via a followed symlinked directory), `Path.join` will happily produce an absolute path pointing anywhere on the victim's disk, without the `realpath()`-based root-containment check that `resolveWithin` performs. The corrupted value here is the `fullPath`/`fullyQualifiedFilePath` computed in these handlers — it is trusted to be "inside the repo" purely because it began life as a relative status path, exactly the same class of unfounded trust that let the Node.js exploit's `Buffer.from()` result stand in for a "safely resolved" path.

### Impact Explanation
- `revealInFileManager` / `showItemInFolder` reveals arbitrary files/directories outside the cloned repo in the OS file browser, an information-disclosure/path-traversal primitive over the local filesystem.
- `onOpenInExternalEditor` and the "Open in External Editor" context-menu action open an arbitrary out-of-repo file in the user's configured code editor — potential arbitrary file read outside repo bounds, and depending on editor behavior (e.g. workspace auto-load, extensions autoruns), a further code-execution vector.
- `openFile()` → `shell.openExternal('file://'+fullPath)` used by "Open with Default Program" hands the resolved (symlink-followed) path to the OS shell association handler. The `isSafeFileExtension` gate only inspects the string suffix of the *symlink name* recorded in git, not the type of the file the symlink actually resolves to; an attacker can commit a symlink named `notes.txt` pointing at an executable/script elsewhere on the victim's machine (or a locally reachable network path), so that clicking "Open with Default Program" launches/executes content outside the repo. This satisfies the "code execution ... outside the repo" impact bucket from an attacker-controlled cloned repository.
- The submodule diff's `fullPath` (built without containment checking) is surfaced to `onOpenSubmodule`, which Desktop treats as a directory to open as a new repository — a crafted `.gitmodules`/submodule symlink combination could similarly redirect this outside the intended tree.

### Likelihood Explanation
The user only needs to open a maliciously crafted repository (clone/fetch a repo, or check out a branch/PR containing the payload) and interact with the standard "Changes"/"History" file context menu — actions that are core, everyday Desktop functionality, not obscure code paths. No admin rights, local pre-existing malware, or unnatural steps are required beyond normal repository browsing that GitHub Desktop is designed to facilitate. Symlink commits are ordinary, common git objects (mode `120000`), so no exotic git trickery is needed to plant the payload.

### Recommendation
Route every consumer of a repository-relative `file.path` that is turned into a filesystem or shell action (`revealInFileManager`, `onOpenInExternalEditor`, `openFile`/"Open with Default Program", `buildSubmoduleDiff`'s `fullPath`, and the equivalent code in `pull-request-files-changed.tsx` / `filter-changes-list.tsx`) through `resolveWithin(repository.path, file.path)` instead of raw `Path.join`, rejecting (and refusing to act on) any path that resolves to `null`. Additionally, `isSafeFileExtension` should validate the extension of the fully resolved/`realpath`'d target, not just the tracked path string, before permitting "Open with Default Program".

### Proof of Concept
1. Attacker creates a repository containing a symlink `evil.txt` → `/Users/victim/.ssh/id_rsa` (or, on the traversal side, a symlinked directory `link` → `/`, with an "untracked" nested entry appearing as `link/Users/victim/.ssh/id_rsa`), and pushes/publishes it, or serves it via a malicious remote/fetch URL.
2. Victim clones or fetches the repository in GitHub Desktop and views the file (e.g. History or Changes list shows `evil.txt`).
3. Victim right-clicks the entry and selects "Reveal in Finder"/"Show in Explorer", "Open in External Editor", or "Open with Default Program".
4. `revealInFileManager`/`onOpenInExternalEditor`/`openFile` build `fullPath = Path.join(repository.path, file.path)` with no `realpath`/root-containment validation, and the OS follows the symlink, revealing/opening/launching the target file (e.g. `~/.ssh/id_rsa`) outside the repository, whereas `resolveWithin(repository.path, file.path)` — already used elsewhere in the same codebase — would have returned `null` and blocked the action, per the existing symlink-escape test: [11](#0-10)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

```typescript
export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
