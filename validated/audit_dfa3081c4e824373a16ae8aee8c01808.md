### Title
EndBlock skips sweeping the ephemeral per-tx coinbase balance for ante-failed EVM transactions, permanently freezing already-charged gas fees - ([File: x/evm/keeper/abci.go])

### Summary
The TON report describes `on_bounce()` treating any failed downstream message as a governing-action failure and refunding the whole balance to the wrong party, because the protocol lacks a correct fund-disposition path for failed proposals. The same class of bug — "funds already collected are mishandled once the corresponding action fails" — exists in `x/evm/keeper/abci.go`'s `EndBlock`, where gas fees already deducted from an EVM sender and credited to a per-transaction ephemeral "coinbase" account are never swept to the real fee collector once that transaction is recorded as failed with a non-empty `Error`.

### Finding Description
`EVMFeeCheckDecorator.AnteHandle` in `x/evm/ante/fee.go` runs `BuyGas()`, which subtracts the fee from the sender and credits it to the per-transaction coinbase address (`state.GetCoinbaseAddress(idx)`), then calls `stateDB.Finalize()` (which commits balance mutations to the real `BankKeeper`) and records the resulting surplus with `AddAnteSurplus`. [1](#0-0) 

This fee-check decorator runs before the sig/nonce-verification decorator in the EVM ante chain, so a transaction can successfully pay the fee (moving real bank balance to the ephemeral coinbase[idx] account) and then still fail later in the ante chain (e.g., nonce mismatch in `EVMSigVerifyDecorator`) or panic in the msg server. [2](#0-1) 

When a tx never reaches `AppendToEvmTxDeferredInfo` (because the ante chain failed or the msg server panicked), `GetAllEVMTxDeferredInfo` synthesizes a `DeferredInfo` with `Error: txRes.Log` instead of the normal record containing bloom/hash/surplus. [3](#0-2) 

In `EndBlock`, any deferred info with a non-empty `Error` is handled purely as a receipt-writing/bookkeeping branch and always `continue`s past the code that sweeps the tx's dedicated coinbase account balance into the real coinbase/fee collector address: [4](#0-3) 

Specifically:
```go
for _, deferredInfo := range evmTxDeferredInfoList {
    txHash := common.BytesToHash(deferredInfo.TxHash)
    if deferredInfo.Error != "" && txHash.Cmp(ethtypes.EmptyTxsHash) != 0 {
        if !k.GetNonceBumped(ctx, deferredInfo.TxIndex) {
            continue
        }
        _ = k.SetTransientReceipt(ctx, txHash, &types.Receipt{...})
        continue
    }
    idx := int(deferredInfo.TxIndex)
    coinbaseAddress := state.GetCoinbaseAddress(idx)
    ...
    if err := k.BankKeeper().SendCoinsAndWei(ctx, coinbaseAddress, coinbase, balance, weiBalance); err != nil { ... }
    surplus = surplus.Add(deferredInfo.Surplus)
}
```
Both `continue` paths in the error branch skip the `SendCoinsAndWei(coinbaseAddress, coinbase, ...)` sweep entirely. If a transaction paid its fee in `EVMFeeCheckDecorator` (real bank-keeper credit to `coinbaseAddress`) but then failed for any reason recorded as `Error != ""` (ante failure after fee-check, or msg-server panic), that fee's balance sits in the per-tx-index synthetic `coinbaseAddress` and is never moved out. This mirrors the TON bug pattern: a downstream failure ("bounce") after funds were already locked/charged leaves those funds mishandled instead of following the expected fee-collector distribution path.

### Impact Explanation
This is not merely value stuck for one block — the per-tx coinbase address is keyed only by `idx` (the transaction's index within the block), i.e. `state.GetCoinbaseAddress(idx)`. The same index is reused across blocks. If a stuck balance from a prior block's failed transaction at index `idx` is left there, and a *different* transaction later lands at the same index `idx` in a subsequent block, `EndBlock`'s sweep for that later (successful) transaction will pick up and forward the *combined* balance (its own fee plus the previously stuck fee) to the coinbase/fee collector. This is a fund-misallocation outcome: fees paid by one sender in a failed transaction end up commingled with, and ultimately swept alongside, a different (unrelated) transaction's fee — a direct analog to the report's "voter fees redirected to the wrong party" scenario, except here funds move to an unrelated future transaction's sweep rather than to the proposal initiator. In the interim (before any tx reuses that index), the fee is effectively frozen/unaccounted, since it's real bank-keeper balance that increases total tracked account balances outside of the fee collector's accounting.

### Likelihood Explanation
Reachable directly by a public RPC client / transaction sender: any submitter can craft an EVM transaction whose signature/nonce check fails deterministically after fee validation succeeds (e.g., submit with the correct fee/base-fee parameters but an already-stale/incorrect nonce that still passes preliminary checks yet fails `EVMSigVerifyDecorator`), or trigger a msg-server panic path. No validator or governance privilege is needed — an ordinary user transaction is sufficient to place the chain into this state.

### Recommendation
In `x/evm/keeper/abci.go`'s `EndBlock`, the error branch for deferred info should still sweep the per-tx `coinbaseAddress` balance (if any was actually credited by the ante fee-check) to the real coinbase/fee collector before `continue`-ing, regardless of whether the transaction ultimately succeeded, failed at the VM level, or failed later in the ante chain / panicked. Alternatively, track explicitly (e.g. via a flag alongside `AddAnteSurplus`) whether `BuyGas`/`Finalize` already committed a fee credit to `coinbaseAddress` for a given tx index, and unconditionally sweep that balance in `EndBlock` independent of the `Error` classification, so charged fees are never left in — or leaked from — the reused per-index ephemeral coinbase account.

### Proof of Concept
1. Submit an EVM transaction whose `GasFeeCap`/base-fee parameters satisfy `EVMFeeCheckDecorator` (so `BuyGas()` succeeds, debiting the sender and crediting `state.GetCoinbaseAddress(idx)` via the real `BankKeeper`, and `AddAnteSurplus` records the surplus) [5](#0-4) .
2. Ensure the same transaction fails in a later ante decorator (`EVMSigVerifyDecorator`, e.g. nonce mismatch) or causes a panic reaching the msg-server's recover handler, so no `AppendToEvmTxDeferredInfo` entry is written for that tx index.
3. At `EndBlock`, `GetAllEVMTxDeferredInfo` synthesizes a `DeferredInfo{Error: txRes.Log}` for that tx index [6](#0-5) , causing the sweep of `state.GetCoinbaseAddress(idx)`'s balance to be skipped [7](#0-6) .
4. Query the bank balance of `state.GetCoinbaseAddress(idx)` after the block commits — the previously charged fee remains present in that account, not the fee collector.
5. Submit a subsequent transaction that legitimately lands at the same block-relative index `idx` in a later block; observe that `EndBlock`'s sweep for that transaction forwards the combined (stale + current) balance to the fee collector, demonstrating fund misallocation across unrelated transactions.
