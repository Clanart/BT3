### Title
CPU-exhaustion Denial-of-Service via unbounded multisig signature recovery before signature-count validation - ([File: blockchain/types/accountkey/account_key_weighted_multi_sig.go])

### Summary
The Django CVE (`UserAttributeSimilarityValidator`) is a DoS caused by performing expensive comparison work on an attacker-controlled-size input *before* any cheap short-circuit check rejects the oversized input. Kaia has an analogous pattern in multisig transaction validation: every signature attached to a transaction is cryptographically recovered (`crypto.Ecrecover`) *before* the account-key logic checks whether the number of signatures is even plausible for the target account, allowing an unprivileged sender to force expensive ECDSA recovery work on all validating nodes for a transaction that is destined to be rejected anyway.

### Finding Description
When a transaction other than a legacy/Ethereum-typed one is validated, `Transaction.ValidateSender` first recovers **all** public keys from **all** attached signatures via `SenderPubkey` → `TxSignatures.RecoverPubkey`, which calls `crypto.Ecrecover` once per signature: [1](#0-0) [2](#0-1) 

Only *after* this full recovery pass does the account-key validation get a chance to reject the transaction because the signature count exceeds the number of registered keys: [3](#0-2) 

The rejection check `len(recoveredKeys) > len(a.Keys)` is a cheap length comparison, but it is only reached after the expensive `Ecrecover` loop has already run for every signature the attacker chose to attach — there is no early bound on the number of signatures relative to `MaxNumKeysForMultiSig` (10) or the account's actual key count before recovery begins. The only limit on signature count is the generic transaction byte-size cap (`MaxTxDataSize = 128KB`): [4](#0-3) 

Because each RLP-encoded `TxSignature` (V, R, S) is only tens of bytes, the 128KB limit still permits attaching on the order of a thousand-plus signatures to a single transaction. Every one of those signatures triggers a full secp256k1 recovery operation, and afterward the `AccountKeyWeightedMultiSig.Validate` function additionally does two more O(n) passes (map construction and lookup) over the recovered keys: [5](#0-4) 

before finally returning `false` because `numSigs > numKeys`. The expensive work (signature recovery, RLP re-encoding of each key, map building) is thus proportional to the attacker-chosen number of signatures, not to the small, fixed number of keys actually registered on the account — mirroring the Django advisory's core flaw of unbounded comparison cost driven by attacker-controlled input size.

This path is reachable by any unprivileged party who can submit a transaction: `TxPool.AddRemote`/public RPC `eth_sendRawTransaction`, since `ValidateSender` (and therefore the expensive recovery) is invoked during tx-pool admission via `tx.Validate`/`ValidateSender` before the transaction is confirmed valid or discarded.

### Impact Explanation
An attacker can craft transactions bound to any address (the target account key type doesn't even need to be `AccountKeyWeightedMultiSig`; any account key validated through `ValidateSender` triggers `SenderPubkey` recovery for however many signatures are attached) that carry hundreds to over a thousand signatures. Submitting many such transactions to the tx pool or via public RPC forces every receiving/validating node to perform proportionally large amounts of ECDSA recovery and hashing/map work per rejected transaction, well beyond the resources spent processing a normal, valid transaction. Sustained submission of such transactions can degrade transaction-pool processing throughput and consume CPU on all full nodes/RPC endpoints that admit the transaction for validation — a denial-of-service against block producers' and RPC nodes' capacity to process legitimate traffic (CWE-400), consistent severity class with the Django advisory (`AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`).

### Likelihood Explanation
High likelihood of reachability: any external, unauthenticated party can submit an RLP-encoded transaction with an arbitrarily large `TxSignatures` list (up to the byte-size cap) via public RPC `eth_sendRawTransaction` or p2p tx gossip. No special privileges, staking, governance access, or malicious-peer status are required — only crafting a transaction with many (invalid or duplicated) signature triples, which requires no valid private keys.

### Recommendation
Add an early, cheap bound on the number of signatures relative to `accountkey.MaxNumKeysForMultiSig` (or the actual number of keys on the target account, when cheaply retrievable) in `TxPool.validateTx`/`Transaction.ValidateSender` *before* invoking `SenderPubkey`/`RecoverPubkey`, so that transactions with an implausible number of signatures are rejected without performing any ECDSA recovery. Additionally consider charging intrinsic gas or applying a strict pool-admission cap on `len(tx.RawSignatureValues())` independent of the byte-size limit.

### Proof of Concept
1. Construct a transaction of a Kaia-typed transaction (e.g., `TxTypeValueTransfer` or `TxTypeAccountUpdate`) whose `From` address has a normal `AccountKeyPublic` or small `AccountKeyWeightedMultiSig` (few keys).
2. Populate its `TxSignatures` field with as many (V, R, S) triples as fit under `MaxTxDataSize` (128KB) — using either random/invalid values or duplicated valid signatures (~1000+ signatures fit easily).
3. Submit the transaction via `eth_sendRawTransaction` or directly to `TxPool.AddRemote`.
4. Observe that `Transaction.ValidateSender` → `SenderPubkey` → `TxSignatures.RecoverPubkey` executes `crypto.Ecrecover` once per attached signature (~1000+ recoveries) before `AccountKeyWeightedMultiSig.Validate`/equivalent check finally rejects the transaction for `len(recoveredKeys) > len(a.Keys)` or invalid signatures — measurable CPU time spent is proportional to the attacker-chosen signature count, not the account's real key count.
5. Repeating this submission at volume demonstrates disproportionate CPU consumption on the validating node relative to the trivial cost of producing the spam transactions.

func (t TxSignatures) RecoverPubkey(txhash common.Hash, homestead bool, vfunc func(*big.Int) *big.Int) ([]*ecdsa.PublicKey, error) {
	var err error

	pubkeys := make([]*ecdsa.PublicKey, len(t))
	for i, s := range t {
		pubkeys[i], err = s.RecoverPubkey(txhash, homestead, vfunc)
		if err != nil {
			return nil, err
		}
	}

	return pubkeys, nil
}
