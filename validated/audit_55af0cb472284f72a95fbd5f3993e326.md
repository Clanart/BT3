### Title
Sandwiching a GaslessSwapRouter swap forces revert after the proposer has already lent gas KAIA, causing unrecoverable value loss to the proposer - (File: kaiax/gasless/impl/tx_pool.go, kaiax/gasless/impl/builder.go, kaiax/gasless/impl/getter.go)

### Summary
The `kaiax/gasless` module (KIP-247) lets an unprivileged, balance-less sender submit a `GaslessSwapTx` that swaps ERC20 for KAIA/WKAIA through a `GaslessSwapRouter` (an AMM-style constant-product router, exercised in tests with a Uniswap V2 pool). Unlike the audited "Well," the router does charge a small commission, but the *timing model* around it reproduces the M-04 pattern: the tx-pool admission check re-derives `minAmountOut`/`amountIn` validity from the *current* chain state [1](#0-0) , while the actual value-critical step — the block proposer unconditionally transferring `lendAmount` KAIA to the user via a `LendTx` before the swap executes — happens in a separate, non-atomic transaction ahead of the swap in the block [2](#0-1) . Any state change to the underlying AMM pool between admission-time validation and inclusion-time execution (i.e., a sandwich) can push the swap output below `minAmountOut`, causing `swapForGas` to revert on-chain, while the `LendTx` funds have already left the proposer's control.

### Finding Description
The gasless flow is:
1. `checkBalanceForSwap` validates `AmountIn >= gsr.GetAmountIn(minAmountOut)` using the router's *current* on-chain reserves at the moment the transaction is being promoted/added to the pool [3](#0-2) .
2. At block-building time, `ExtractTxBundles` builds a bundle `[LendTxGenerator, ApproveTx?, SwapTx]` [4](#0-3) .
3. `GetLendTxGenerator` creates and signs a **real, unconditional value-transfer transaction** from the proposer's node key to the user for `lendAmount = ApproveTx.Fee() + SwapTx.Fee()` [2](#0-1) . This LendTx is a standalone tx placed *before* the ApproveTx/SwapTx in the block; it succeeds and transfers KAIA to the user irrespective of what happens afterward.
4. The `SwapTx` then calls `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` on the router, which internally performs the constant-product swap and is expected to repay `amountRepay` (covering `R1` = LendTx's own gas + `R2`/`R3` = Approve/Swap tx fees) back to the proposer, keeping only the surplus for the user [5](#0-4) .

Because the AMM price used for step 1's admission check is evaluated at add-to-pool time and the actual swap executes later at block-inclusion time, an attacker who observes the pending `GaslessSwapTx` (visible in mempool, since gasless params like `token`, `amountIn`, `minAmountOut` are ABI-decodable, per `decodeSwapTx`) can, exactly as in the M-04 PoC, submit a bundle of two swaps against the same constant-product pool: one to push the price against the victim before the victim's swap executes and one to reverse it afterward. If the resulting execution-time reserves make the realized output fall below `minAmountOut`, `swapForGas` reverts on-chain (the router's Uniswap-V2-style `getAmountOut`/slippage check fails, same "insufficient output amount" class of check demonstrated in `tests/gasless_test.go` lines 247-253) [6](#0-5) .

When the `SwapTx` reverts:
- The token repay logic inside `swapForGas` never executes, so the proposer's `amountRepay` (its principal + fees advanced via `LendTx`) is never returned.
- The `LendTx` itself already succeeded and irreversibly transferred `lendAmount` KAIA out of the proposer's control before the swap ran.
- Standard EVM gas-fee accounting (base fee burn / rewardbase distribution in `state_transition.go`) reimburses only the gas consumed by the reverted `SwapTx`, not the `LendTx` principal, so the proposer is left short the lent amount minus whatever gas the failing swap burned back to it.

This differs from the disputed Well report only in that Basin's Well had no proposer-side unconditional pre-funding; here the proposer (or fee-delegation-like lender) is the one who loses actual value, which raises severity above "DOS/UX griefing" to "unauthorized value extraction/loss."

### Impact Explanation
An attacker with no special privileges — merely observing the public mempool/RPC and submitting ordinary swap transactions against the same pool the `GaslessSwapRouter` uses — can force the proposer to bear a real KAIA loss equal to (approximately) `lendAmount` per griefed `GaslessSwapTx`, repeatable against any/every gasless swap the attacker chooses to target. Because gasless transactions are, by design, aimed at users without KAIA balances (a broad, permissionless surface), and the attack cost is only the attacker's own swap gas fees (potentially net-recovered via the reverse leg of the sandwich, per the constant-product argument in the original report), this is economically repeatable and scales with gasless-swap volume.

### Likelihood Explanation
Likelihood is Medium-High: it requires only (a) visibility of a pending `GaslessSwapTx` (public mempool/RPC), (b) the ability to submit ordinary swap transactions to the same underlying pool ahead of/around it in the same block, which any unprivileged sender can do, and (c) enough liquidity asymmetry/slippage tolerance in the victim's `minAmountOut` to be pushable — a condition inherent to any AMM-based swap with attacker-controlled ordering. No special node access, validator collusion, or leaked keys are required.

### Recommendation
- Re-validate `minAmountOut`/expected output against the router's state at the actual point of inclusion (i.e., immediately before executing `SwapTx` within the bundle), and drop/re-queue the bundle rather than let the `LendTx` execute unconditionally, or make the `LendTx` conditional/atomic with the swap outcome (e.g., use a single atomic multicall so the KAIA transfer and swap-repay happen atomically, reverting together).
- Consider having the router itself lend the gas amount contingent on successful repayment within the same transaction, rather than a separate proposer-funded `LendTx` preceding the swap.
- Add commission/fee or minimum swap-size floors sufficient to make repeated sandwich-induced reverts economically unprofitable for attackers, and/or require private/protected submission paths for gasless swaps to reduce sandwich visibility.

### Proof of Concept
1. User (balance-less) submits a `GaslessApproveTx` + `GaslessSwapTx` pair with `MinAmountOut = M`, `AmountRepay = R` against `GaslessSwapRouter`, admitted per `checkBalanceForSwap` using current pool reserves [7](#0-6) .
2. Attacker observes the pending pair (mempool) and, in the same target block, submits: (a) a swap on the router's underlying pool in the same direction as the victim to move reserves so that the victim's realized output at execution time < `M`; (b) a reverse swap after the victim's slot to restore reserves and reclaim most of the temporary slippage, per the constant-product argument in the original report.
3. Block is built: bundle `[LendTxGenerator, ApproveTx, SwapTx]` is assembled per `ExtractTxBundles` [4](#0-3) ; `LendTx` executes and unconditionally transfers `lendAmount` KAIA to the user [2](#0-1) .
4. `SwapTx` executes `swapForGas`, whose internal slippage/output check fails because realized output < `M` (as demonstrated by the equivalent revert path in `tests/gasless_test.go` lines 245-253) [6](#0-5) , so `amountRepay` is never sent back to the proposer.
5. Net result: proposer is out `lendAmount` (minus gas actually burned by the reverted `SwapTx`), while the attacker's sandwich largely restores its own capital via the constant-product reversal — reproducing the M-04 attack pattern but with the proposer, not merely the victim user, suffering direct financial loss.

**Uncertainty / unverified aspects:** I was not able to fully trace, within the available index, the exact call site/timing where `GetCheckBalance`/`checkBalanceForSwap` is invoked relative to `promoteExecutables`/block building (i.e., whether it is re-run immediately before every block or only at initial admission), nor the exact bytecode-level revert condition inside `GaslessSwapRouter.swapForGas` (only its Go bindings were indexed, not the Solidity source). These would need direct inspection of the full `GaslessSwapRouter` contract source and the tx-pool promotion/worker integration path to fully confirm the precise reentry window and whether any additional re-check occurs immediately before block inclusion.

// MakeLendTx creates a transaction with following properties:
// L1. LendTx.type = 0x7802 (TxTypeEthereumDynamicFee)
// L2. LendTx.from = proposer
// L3. LendTx.to = SwapTx.from
// L4. LendTx.value = LendAmount(approveTxOrNil, swapTx)
func (g *GaslessModule) GetLendTxGenerator(approveTxOrNil, swapTx *types.Transaction) *builder.TxOrGen {
	var src []byte
	if approveTxOrNil != nil {
		src = append(src, approveTxOrNil.Hash().Bytes()...)
	}
	src = append(src, swapTx.Hash().Bytes()...)
	bundleHash := crypto.Keccak256Hash(src)

	gen := func(nonce uint64) (*types.Transaction, error) {
		var (
			chainId = g.InitOpts.ChainConfig.ChainID
			signer  = types.LatestSignerForChainID(chainId)
			key     = g.InitOpts.NodeKey
		)

		to, err := types.Sender(signer, swapTx)
		if err != nil {
			return nil, err
		}

		tx, err := types.NewTransactionWithMap(types.TxTypeEthereumDynamicFee, map[types.TxValueKeyType]interface{}{
			types.TxValueKeyNonce:      nonce,
			types.TxValueKeyTo:         &to,
			types.TxValueKeyAmount:     lendAmount(approveTxOrNil, swapTx),
			types.TxValueKeyData:       common.Hex2Bytes("0x"),
			types.TxValueKeyGasLimit:   params.TxGas,
			types.TxValueKeyGasFeeCap:  swapTx.GasFeeCap(),
			types.TxValueKeyGasTipCap:  swapTx.GasTipCap(),
			types.TxValueKeyAccessList: types.AccessList{},
			types.TxValueKeyChainID:    chainId,
		})
		if err != nil {
			return nil, err
		}

		err = tx.Sign(signer, key)
		return tx, err
	}

	return builder.NewTxOrGenFromGen(gen, bundleHash)
}

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}

func (g *GaslessModule) ExtractTxBundles(txs []*types.Transaction, prevBundles []*builder.Bundle) []*builder.Bundle {
	// there are only at most two gasless transactions in pending for a sender
	bundles := []*builder.Bundle{}
	approveTxs := map[common.Address]*types.Transaction{}
	targetTxHash := common.Hash{}
	for _, tx := range txs {
		addr, err := types.Sender(g.signer, tx)
		if err != nil {
			continue
		}
		if g.IsApproveTx(tx) {
			approveTxs[addr] = tx
		} else if g.IsSwapTx(tx) && g.IsExecutable(approveTxs[addr], tx) {
			bundleTxs := builder.NewTxOrGenList(g.GetLendTxGenerator(approveTxs[addr], tx))
			if approveTxs[addr] != nil {
				bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(approveTxs[addr]))
			}
			bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(tx))

			b := builder.NewBundle(
				bundleTxs,
				targetTxHash,
				false,
			)

			targetTxHash = tx.Hash()

			isConflict := false
			for _, prev := range append(prevBundles, bundles...) {
				if prev.IsConflict(b) {
					isConflict = true
					break
				}
			}
			if isConflict {
				// Gasless transactions will just fail even if they aren't bundled.
				continue
			}
			bundles = append(bundles, b)
		} else {
			targetTxHash = tx.Hash()
		}
	}
	return bundles
}
