### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external report's bug class is "user-supplied input used without proper validation before being consumed by a security-relevant operation." In Serai's Bitcoin scanner, `Scanner::scan_block` iterates `block.txdata` including `block.txdata[0]` (the coinbase transaction) and feeds every output paying to a registered script into `scan_transaction`, which emits a `ReceivedOutput` carrying a valid `offset` and `outpoint` — indistinguishable from a mature, spendable output. Bitcoin consensus renders coinbase outputs unspendable for 100 blocks, so the returned `ReceivedOutput` describes funds that are not actually spendable.

### Finding Description
`scan_block` (crypto/bitcoin wallet) calls `self.scan_transaction(tx)` for every transaction in the block, with no coinbase/maturity check:

```rust
// networks/bitcoin/src/wallet/mod.rs:221-227
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

`scan_transaction` (lines 199–214) only matches `output.script_pubkey` against `self.scripts` and, on a match, constructs `ReceivedOutput { offset, output, outpoint: OutPoint::new(tx.compute_txid(), vout) }`. `ReceivedOutput` exposes `offset()`, `output()`, `outpoint()`, and `value()` — the exact bundle passed to the spend/signing path (`send.rs`). There is no field or check indicating coinbase immaturity, and nothing prevents a downstream caller from selecting it as an input to a transaction.

An unprivileged party who can get a coinbase paying the multisig's script into a block (a miner, or via mining pools that accept arbitrary coinbase payout scripts) causes the scanner to report received funds whose outpoint cannot be spent. The code comment acknowledges maturity but delegates the filter to callers; `scan_block` itself performs no validation of the input's spendability before producing a `ReceivedOutput`.

### Impact Explanation
"Funds reported received that are not spendable" — an accepted impact class. A `ReceivedOutput` from an immature coinbase will be treated as a usable UTXO: any spend transaction built with it as an input is consensus-invalid and will be rejected by the network, or the accounting records a deposit that cannot be moved. Severity: Medium — the funds are not stolen and eventually mature, but the reported output is unusable and can poison UTXO selection/signing attempts and deposit accounting.

### Likelihood Explanation
Low-to-moderate. Receiving coinbase outputs requires a miner (or pool payout) to direct reward outputs at the multisig's script — not common for a threshold-wallet address, but fully within an unprivileged party's ability if they mine a block or control a pool payout, and costs them nothing beyond the normal reward mechanics. Once such an output exists, `scan_block` reports it unconditionally.

### Recommendation
In `Scanner::scan_block`, skip or flag `block.txdata[0]` (the coinbase): either scan `block.txdata[1 ..]` by default and expose a separate `scan_coinbase` API that returns outputs marked immature (e.g., carrying a maturity height field on `ReceivedOutput`), or require the caller to pass the block height and filter outputs until maturity. At minimum, add a `is_coinbase`/maturity marker to `ReceivedOutput` so the spend path can reject immature outpoints rather than relying on callers to remember the post-processing pass.

Root cause: `scan_block` at `networks/bitcoin/src/wallet/mod.rs:221-227` performs no validation distinguishing coinbase outputs from spendable ones before handing input data to `scan_transaction` (lines 199–214), which trusts `script_pubkey` matching alone to declare an output received and spendable.

Caveat: the in-code comment documents that coinbase outputs are returned and suggests post-processing; this is reported nonetheless because the API emits security-relevant `ReceivedOutput`s with no marker distinguishing immature funds, matching the "funds reported received that are not spendable" acceptance criterion. I was unable to fully verify the downstream spend path (`send.rs`, `processor/src/networks/bitcoin.rs`) within the available iterations, so whether production callers already filter immature outputs is unconfirmed.
