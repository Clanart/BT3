### Title
Explicit disabling of Git's clone-time hook protection during `git clone --recursive` re-enables symlinked-submodule-hook code execution - ([File: app/src/lib/git/clone.ts])

### Summary
GitHub Desktop's `clone()` helper invokes `git clone --recursive` while explicitly setting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the child process environment. `GIT_CLONE_PROTECTION_ACTIVE` is the flag Git itself sets internally to mark that it is inside a clone/recursive-submodule-update operation so that its built-in safety checks (added after the family of submodule-hook RCEs, e.g. the case-insensitive/symlinked `.git` hook attacks) refuse to run hooks or trust ambiguous submodule paths during that specific operation. By forcing this variable to `'false'` from the outside, Desktop tells Git it is *not* in a protected clone context even though it explicitly is, which removes the safety check for the exact code path (`--recursive` clone from a URL the user does not control the contents of) that the variable exists to protect. [1](#0-0) 

### Finding Description
The broken invariant mirrors the NFT report: a security guard is keyed on process/operation identity (the NFT ID / the "are we inside a protected clone" flag) but the calling code strips that identity marker, so the protection that should be tied to a specific operation is bypassed for every invocation. Here, `clone()` builds the `git clone --recursive` command and merges in `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally: [2](#0-1) 
This clone is driven by an attacker-controlled `url` argument that reaches `clone()` from multiple untrusted external entry points, including the `openrepo://` deep link handler (`open-repository-from-url`) and CLI clone argument: [3](#0-2) [4](#0-3) 
Because the clone always passes `--recursive`, any submodules declared in the attacker's `.gitmodules` are cloned and checked out as part of the same operation that this protection is meant to cover. The existing guard rails in the codebase (`isClonePathSensitive`, `sanitizeCloneName`, the "unsafe repository"/`safe.directory` warning shown for local directories owned by another user) all address different classes of problems — destination path traversal and post-hoc ownership warnings on the *top-level* repo — none of them re-enable or replace the specific in-flight protection that `GIT_CLONE_PROTECTION_ACTIVE` provides during the recursive submodule clone/checkout itself. [5](#0-4) [6](#0-5) 

I was not able to find, within the indexed portion of this repository, any comment, test, or changelog entry explaining *why* `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` here (e.g. to avoid a known false-positive or to preserve some legitimate workflow), so the intent behind this override is not fully verifiable from local code alone — this is a limitation of what I could confirm from the index and would need confirmation from git blame/PR history in a full checkout.

### Impact Explanation
If Git's clone-protection mechanism would otherwise reject or neutralize a malicious submodule/hook combination embedded in an attacker-supplied repository (the classic vector: a submodule path/URL crafted to collide with the parent's `.git` directory on case-insensitive or otherwise permissive filesystems, or a hook file placed in a location Git's protection would normally refuse to trust during clone), disabling the flag removes that last line of defense for every clone Desktop performs — including ones reached via an `x-github-client://openrepo/...` link that a user simply clicks. That is a "attacker controls a cloned/fetched repository" scenario resulting in potential code execution during the clone, which is explicitly in scope per the Valid Impact criteria.

### Likelihood Explanation
Every "Open in Desktop" deep link and CLI `clone` invocation goes through `clone()` with `--recursive` and this overridden env var, so the vulnerable path is hit on the default, most common flow (not an edge case), and requires only that the victim open a link to (or otherwise initiate cloning) an attacker-controlled/malicious repository containing crafted submodules — no local access, no admin rights, and no social-engineering beyond a normal "clone this repo" action that the app is designed to perform.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Let Git manage this internal state itself during `clone --recursive`, and if there is a legitimate reason for overriding it (e.g., to allow trusted internal recursive fetches), gate the override behind the same trust decision the app already asks the user to make for "unsafe" repositories (the `addSafeDirectory`/"Trust Repository" flow), rather than unconditionally disabling it for all clone operations including ones sourced from untrusted deep links and CLI arguments.

### Proof of Concept
1. Publish a malicious Git repository whose `.gitmodules` defines a submodule whose name/path is designed to collide with or escape into the parent working tree's `.git` directory on a case-insensitive filesystem (the class of issue Git's clone protection was introduced to stop).
2. Host a link such as `x-github-client://openrepo/https://attacker.example/evil-repo.git`.
3. Victim clicks the link; Desktop's `parseAppURL` resolves it to an `open-repository-from-url` action and calls `openOrCloneRepository` → `_clone` → `clone()`.
4. `clone()` runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` injected into the environment, disabling Git's own safety check for this exact recursive-submodule clone operation.
5. If the crafted submodule payload would otherwise have been rejected/mitigated by Git's clone protection, it instead proceeds, potentially leading to hook execution or file writes outside the intended submodule directory during the clone.

Note: I could not execute Git locally to confirm the precise CVE-class payload still triggers on the currently bundled Git version; this PoC describes the reachable code path and the specific protection that is disabled, which is verifiable directly from `app/src/lib/git/clone.ts`.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

    '-c',
    `init.defaultBranch=${defaultBranch}`,
