## Title
Missing concurrent-operation guard in `_fetchRefspec()` allows a fork/PR-triggered fetch to race a user push and corrupt the ref/index state — (File: `app/src/lib/stores/app-store.ts`)

### Summary
The external report describes a "broken invariant" class of bug: a Git-transaction function that intentionally omits the app's own reentrancy/concurrency guard for functional reasons, leaving a documented gap that the maintainers accepted as a calculated risk. GitHub Desktop has a direct structural analog: `AppStore._fetchRefspec()` explicitly opts out of the `withPushPullFetch()` concurrency lock that every other network Git operation (`_pull`, `_fetch`, `_push`) uses, and the code comment says so outright.

### Finding Description
GitHub Desktop serializes all push/pull/fetch operations per-repository through `withPushPullFetch()`, which sets `isPushPullFetchInProgress` and returns early if another network operation is already running: [1](#0-0) 

`_pull` and `_fetch`/`_fetchRemote` both funnel through this guard: [2](#0-1) 

`_fetchRefspec`, however, is explicitly documented as bypassing it: [3](#0-2) 

This method is invoked when the user views a Pull Request whose head is a fork (`refspec` and remote URL are attacker/PR-author controlled data coming from the GitHub API and the fork's remote), and it runs a real `git fetch` against the repository's working copy: [4](#0-3) 

Because this fetch does not set `isPushPullFetchInProgress`, it can run **concurrently** with a user-initiated `_pull`/`_push`/`_fetch` (which also invoke `git fetch`/`git push` against the same working directory and refs) without the mutual-exclusion the rest of the app relies on to prevent overlapping Git processes. Unlike the smart-contract report, there is no secondary invariant (like `currentContextAddress_ != address(0)`) protecting this specific case — the code comment itself acknowledges "This might require some rework in the future to chain these actions," meaning the maintainers are aware the safety property is not actually enforced, only assumed to be low-risk.

### Impact Explanation
Concurrent `git fetch`/`git push`/`git pull` processes operating on the same repository's `.git` directory can race on shared mutable state: the packed-refs file, loose ref files, the object store, and (for pull, which also merges) the index and working tree. Two Git processes writing refs or the index simultaneously can produce corrupted refs, lost updates (a fetch silently overwriting a ref the user's concurrent push just moved), or an index/lock-file collision that leaves the repository in an inconsistent state requiring manual recovery. Because the attacker only needs to control (or author) a fork PR that the victim views in Desktop while performing a push/pull, this satisfies "silent corruption of what the user commits/fetches" without requiring local access, malware, or unnatural user steps — simply having a PR open from an attacker-controlled fork while the user does ordinary sync actions.

### Likelihood Explanation
Likelihood is moderate-to-low in practice: it requires precise timing (the refspec fetch and a manual push/pull racing within the same short window), and Git itself has some internal locking (e.g., `.git/index.lock`) that will cause one of the two operations to fail loudly rather than corrupt silently in many cases. However, ref updates in particular (`packed-refs`, loose refs) are not always protected by the same lock scope as the index, so a genuinely silent, non-fatal race (e.g., a fetched remote-tracking ref clobbering a ref the concurrent operation just wrote) is plausible. This is explicitly the same risk category the maintainers accepted in the original report — a "not impossible, but currently unmitigated" reentrancy/race window they chose not to close for functional reasons.

### Recommendation
- Route `_fetchRefspec` through the same `withPushPullFetch` (or an equivalent per-repository async mutex) as the other network Git operations, queuing it rather than skipping the guard, since PR-preview fetches are not truly latency-critical enough to justify bypassing the lock.
- If immediate response is required for the PR view, use a separate lock scope that still mutually excludes it from concurrent `git fetch`/`git push`/`git pull` on the same repository (e.g., a lightweight fetch-refspec queue chained after any in-flight push/pull/fetch completes), rather than no lock at all.
- Add a regression test that asserts `_fetchRefspec` cannot start while `isPushPullFetchInProgress` is true (mirroring how `_pull`/`_fetch` are already tested to be gated).

### Proof of Concept
1. Attacker opens a PR from a fork against a repository the victim has open in GitHub Desktop.
2. Victim opens/views that PR in Desktop's PR list — Desktop calls `_fetchRefspec(repository, refspec)` for the fork's ref, which runs `git fetch <fork-remote> <refspec>` without acquiring `isPushPullFetchInProgress`.
3. Concurrently (or within the same UI session, e.g. the victim clicks "Push" or "Pull" right after opening the PR list), Desktop independently calls `_pull`/`_push`, which does check/set `isPushPullFetchInProgress` but has no knowledge of the already-running unlocked `_fetchRefspec` fetch.
4. Both `git` subprocesses operate on the same `repository.path` concurrently; depending on OS/filesystem timing, ref writes or the index can be corrupted or a ref update from one operation can be silently lost, without any error surfaced to the user beyond a possibly generic failure — the victim's next commit/push may reference stale or inconsistent state.

Note: I was unable to fully verify at what UI trigger points and how frequently `_fetchRefspec` is actually invoked relative to user pull/push actions (e.g., exact call sites in the PR list/branch UI), as the index does not surface every caller. A background Devin session with full repo access could confirm the precise UI trigger frequency and attempt to reproduce the race under load to validate real-world exploitability.

    repository: Repository,

    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return

      isPushPullFetchInProgress: true,
    }))

      await fn()
    } finally {

        isPushPullFetchInProgress: false,
