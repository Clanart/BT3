### Title
`SignableTransaction::new` computes `needed_fee` over a transaction that omits the `OP_RETURN` data output, underpaying the intended fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Cooler report — where a stored `loan.amount` that silently included interest was later used as the base for a new collateral requirement — `SignableTransaction::new` builds `tx_outs` containing an extra `OP_RETURN` output for `data`, but then computes the transaction weight/vbytes (and therefore `needed_fee`, the `NotEnoughFunds` check, the change amount, and the minimum-relay-fee check) over a transaction built solely from `payments`, omitting the data output entirely.

### Finding Description
`tx_outs` gets the `OP_RETURN` output pushed at send.rs:194-202, yet both weight calculations at send.rs:204 and send.rs:225-226 call `Self::calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which only serializes `payments` (plus optionally change) — never the data output. `calculate_weight_vbytes` (send.rs:62-99) constructs the measurement `Transaction` purely from the `payments` slice it is given. The result:

- `needed_fee = fee_per_vbyte * vbytes` (send.rs:206, 227, 232) is understated by `fee_per_vbyte * ~vsize(OP_RETURN output)` (up to ~90 vbytes for the permitted 80-byte payload).
- The minimum-relay-fee check at send.rs:211 compares against understated `vbytes`, so a transaction whose true size requires a higher minimum fee can pass.
- The change computation at send.rs:228 (`input_sat - payment_sat - fee_with_change`) uses the understated fee, so the actual fee paid (`fee()`, send.rs:138-141 = inputs − outputs) equals `fee_with_change`, i.e. less than `fee_per_vbyte` × actual vbytes.

Callers that supply `data` (the public `new` API takes `data: Option<Vec<u8>>` up to 80 bytes) produce a transaction paying a lower effective fee rate than requested — the mirror of the Cooler bug: the amount base used for a downstream requirement does not match the real composition of the transaction.

### Impact Explanation
The produced transaction pays an effective fee rate below the caller-specified `fee_per_vbyte`, and can fall below Bitcoin's default minimum relay fee for its true size (the check at send.rs:211 uses the same understated vbytes). Such a transaction will be rejected or never relayed/confirmed, stalling the spend of the inputs it commits to — functionally burning usability of those UTXOs until a replacement is constructed. `needed_fee()` (send.rs:133-135) also returns the understated value to any caller budgeting or amortizing fees.

### Likelihood Explanation
Deterministic whenever `data` is `Some`: the OP_RETURN output (11-byte header + up to 80 bytes of pushes ≈ up to ~90 vbytes) is always omitted from the measured transaction. The size of the fee shortfall scales with `fee_per_vbyte`; at high fee rates the gap is proportional and the min-relay check can be definitively bypassed since it is evaluated against the same wrong vbytes.

### Recommendation
Include the OP_RETURN output (and any other outputs actually appended to `tx_outs`) in the transaction used by `calculate_weight_vbytes` — e.g. pass the final `tx_outs` (or a `payments` slice that includes a `(op_return_script, 0)` entry) into both weight computations so `needed_fee`, `NotEnoughFunds`, the change value, and the min-relay check all reflect the real transaction size.
