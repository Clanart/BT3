### Title
Unbounded per-proposal deposit iteration in gov `EndBlocker` allows deposit-spam DoS of block processing - (File: sei-cosmos/x/gov/keeper/deposit.go)

### Summary
`x/gov`'s `EndBlocker` bounds vote-tallying work per block via `MaxVotesProcessedPerBlock`/`TallyIncremental` [3](#0-2) , but once a proposal's tally completes, `EndBlocker` unconditionally calls `keeper.DeleteDeposits` or `keeper.RefundDeposits` for that proposal with no work budget [2](#0-1) . Both functions call `IterateDeposits`, which walks every deposit record stored under the proposal's key prefix in a single, unbroken loop, performing a bank transfer/burn per record [4](#0-3) [5](#0-4) [6](#0-5) .

### Finding Description
`MsgDeposit` allows any account to deposit to any open proposal, and `AddDeposit` only merges deposits into a single store entry per unique depositor address on that proposal [7](#0-6) . There is no cap on the number of distinct depositor addresses that may deposit to a single proposal, nor any minimum deposit amount enforced per individual `MsgDeposit` call (only the cumulative `TotalDeposit` is checked against `MinDeposit` to activate voting) [8](#0-7) . An attacker who controls many funded accounts (a sybil set, which is cheap to bootstrap since Sei has low tx fees) can issue a large number of dust `MsgDeposit` transactions from distinct addresses against one proposal, creating an unbounded number of deposit records under that `proposalID`'s key prefix.

When that proposal's voting period ends (whether the proposal passes, is rejected, or is converted from expedited to regular), `EndBlocker` calls `DeleteDeposits` (on burn) or `RefundDeposits` (otherwise) exactly once, with **no** incremental/budgeted work limit, unlike the tally step which was deliberately protected by `MaxVotesProcessedPerBlock` and `TallyIncremental` for this exact class of unbounded-work concern [1](#0-0) . Both `DeleteDeposits` and `RefundDeposits` perform a full store iteration plus a bank operation (`BurnCoins` or `SendCoinsFromModuleToAccount`) and a store delete for every single deposit record [6](#0-5) [9](#0-8) . If the attacker inflates the deposit count sufficiently (e.g., tens/hundreds of thousands of entries), this single-block iteration can consume enough wall-clock time to push block production past acceptable latency, since `EndBlocker` executes as part of consensus block finalization outside of any per-transaction gas metering that would otherwise bound it.

The `legacyEndBlocker` path (used when `IncrementalTallyEnabled` is false) has the identical unbounded `DeleteDeposits`/`RefundDeposits` calls with no protection at all [10](#0-9) .

### Impact Explanation
An attacker-inflated deposit set on a single proposal causes the block containing that proposal's `EndBlocker` completion to take substantially longer to process (unbounded iteration + per-entry bank transfers/burns and store writes), which can delay block production beyond acceptable thresholds or, in the extreme, cause validators to fall behind/halt while processing that block — directly matching the "block delay beyond 2.5 seconds" / "validator halt" impact classes. Because deposits are refunded to real accounts (or burned) once, this is a decentralized, permissionless attack vector requiring only ordinary `MsgDeposit` transactions from many funded accounts; it does not require any privileged, validator, or network-level position.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker to fund and control a large number of distinct accounts to bypass the per-depositor merge in `AddDeposit`, and to pay gas for many individual deposit transactions before a target proposal's voting period ends. However, this cost is bounded and predictable (proportional to desired deposit-record count), and the attack can be timed against any proposal (including one the attacker itself submits with a long voting period) to maximize the number of accumulated deposit records before the unbounded refund/burn pass executes.

### Recommendation
Apply the same incremental/budgeted-work pattern already used for vote tallying (`MaxVotesProcessedPerBlock`, `TallyIncremental`) to deposit refund/burn processing: track partially-processed deposit iteration state per proposal and spread `RefundDeposits`/`DeleteDeposits` work across multiple blocks, or cap/rate-limit the number of distinct depositor records a single proposal may accumulate.

### Proof of Concept
1. Attacker submits (or waits for) a governance proposal with a sufficiently long voting period.
2. Using N distinct funded accounts, attacker submits N `MsgDeposit` transactions with dust amounts to that proposal, each from a unique depositor address, creating N deposit store entries via `AddDeposit`/`SetDeposit` [7](#0-6) .
3. When the proposal's voting period ends, `EndBlocker` invokes `TallyIncremental` (bounded) but then unconditionally calls `RefundDeposits` (or `DeleteDeposits`) once, iterating all N entries with a bank operation each [2](#0-1) .
4. For sufficiently large N, this single-block operation's execution time exceeds normal block-time budgets, delaying or stalling block finalization for that height.

// IterateDeposits iterates over the all the proposals deposits and performs a callback function
func (keeper Keeper) IterateDeposits(ctx sdk.Context, proposalID uint64, cb func(deposit types.Deposit) (stop bool)) {
	store := ctx.KVStore(keeper.storeKey)
	iterator := sdk.KVStorePrefixIterator(store, types.DepositsKey(proposalID))

	defer func() { _ = iterator.Close() }()

	for ; iterator.Valid(); iterator.Next() {
		var deposit types.Deposit

		keeper.cdc.MustUnmarshal(iterator.Value(), &deposit)

		if cb(deposit) {
			break
		}
	}
}

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
}
