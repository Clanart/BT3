### Title
`ReceivedOutput::read` accepts arbitrary (offset, TxOut) pairs that `SignableTransaction::multisig` can never spend, permanently locking the associated funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The reported bug class is a deposit path that accepts a value satisfying the funding interface but which the payout path can never process (an ERC721 fed to an ERC20-only flow). The analog in Serai's Bitcoin wallet is `ReceivedOutput`: its deserializer accepts any consensus-valid `TxOut` (any `script_pubkey`, including non-P2TR scripts like OP_RETURN) paired with any canonical `Scalar` offset, while the spending path (`SignableTransaction::multisig`) only succeeds when `output.script_pubkey == p2tr_script_buf(group_key + offset * G)` *and* that key is even-Y. A crafted serialized `ReceivedOutput` therefore represents funds "received" that can never be included in a valid spend, permanently bricking that input and any transaction plan containing it.

### Finding Description
`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) performs only three checks:
- `Secp256k1::read_F` for the offset (canonical scalar, no parity constraint),
- `TxOut::consensus_decode` (any `script_pubkey` accepted),
- `OutPoint::consensus_decode`.

It never enforces the invariant that legitimately-produced `ReceivedOutput`s always satisfy — namely `output.script_pubkey == p2tr_script_buf(scanner.key + GENERATOR * offset)` with the tweaked key having even Y. That invariant is only ever established inside `Scanner::scan_transaction`/`register_offset` (`wallet/mod.rs:180-214`), which populate `offset` from the `scripts` map keyed by exact `ScriptBuf`.

The spending side is strict: `SignableTransaction::multisig` (`networks/bitcoin/src/wallet/send.rs:273-285`) computes `p2tr_script_buf(offset.group_key())` and returns `None` if it doesn't equal `prevouts[i].script_pubkey`, or if the offset-adjusted group key is odd (in which case `p2tr_script_buf` returns `None` and the `?` short-circuits). Additionally, `sign` (`send.rs:383-390`) commits to `Prevouts::All`, so one poisoned input prevents signature generation for the whole transaction.

So a `ReceivedOutput` deserializing to, e.g., a P2PKH `script_pubkey`, or a P2TR script not matching `key + offset*G`, or an offset that makes `key + offset*G` odd, is accepted by `read` but can never be spent: `multisig` returns `None` and the transaction machine is never constructed — the exact "deposits accepted, payouts permanently broken" shape of the reference finding, except expressed via an asymmetric read/spend typecheck instead of ERC20-vs-ERC721.

### Impact Explanation
Any consumer that materializes a `ReceivedOutput` from bytes an unprivileged party can influence (e.g., an integrator that accepts user-supplied or coordinator-supplied serialized outputs — `ReceivedOutput::read` is an explicitly listed untrusted-byte sink) obtains an object indistinguishable from a spendable UTXO. `SignableTransaction::new` happily includes it (`send.rs:150-256` validates only amounts/dust/fees, never script ownership). The failure only surfaces in `multisig`, which returns `None`, and if the poisoned input is mixed with honest inputs, the entire plan is blocked — mirroring the report's "all payouts from the bounty will no longer work." Combined with any flow that refuses to drop/re-pick inputs, all funds committed alongside it are stuck.

### Likelihood Explanation
The defect is a missing invariant check on a deserialization boundary; it is deterministic once attacker-influenced `ReceivedOutput` bytes are consumed. Its realized severity depends on whether an integrator feeds untrusted bytes to `ReceivedOutput::read` — within Serai itself the type is produced by `Scanner` and stored in the local DB, so exploitation requires a deployment where serialized outputs cross a trust boundary. That keeps it out of Critical/High, but the code-level asymmetry is unconditional.

### Recommendation
Either validate at `read` time or make the type unconstructible-invalid:
- Change `ReceivedOutput::read` to take the scanner/`ProjectivePoint` key (or make `ReceivedOutput::new` the only constructor) and verify `p2tr_script_buf(key + GENERATOR * offset) == Some(output.script_pubkey.clone())`, rejecting otherwise — the equivalent of the report's "split the whitelist into an NFT whitelist and an ERC20 whitelist": separate acceptance domains so only spendable outputs deserialize.
- Alternatively, store the key inside `ReceivedOutput` at scan time so `read` can self-validate.

### Proof of Concept
```rust
use bitcoin::{
  transaction::Transaction, OutPoint, TxOut, Amount, ScriptBuf,
};
use frost::curve::Secp256k1;
use ciphersuite::Ciphersuite;
use k256::Scalar;
use serai_bitcoin::wallet::ReceivedOutput;

// Craft serialized bytes for a ReceivedOutput that read() accepts:
//   offset = 1 (a perfectly canonical scalar)
//   TxOut  = valid consensus TxOut paying to an OP_RETURN script
//            (never a registered p2tr script)
let mut bytes = vec![];
bytes.extend(Scalar::ONE.to_bytes()); // Secp256k1::read_F accepts

let fake_out = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new_op_return(&[]), // non-P2TR, unspendable by the key
};
bytes.extend(bitcoin::consensus::serialize(&fake_out));
bytes.extend(bitcoin::consensus::serialize(&OutPoint::null()));

let received = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// `received` is now a "spendable output" per the type system, yet for ANY
// multisig keys, SignableTransaction::multisig hits:
//   send.rs:277  p2tr_script_buf(offset.group_key())? != prevouts[i].script_pubkey
// and returns None — the funds described can never be spent, and any
// SignableTransaction containing this input among honest inputs is bricked.
```

An equivalent variant uses a P2TR `script_pubkey` not equal to `p2tr_script_buf(key + offset*G)` for the victim key, or an `offset` making `key + offset*G` odd — same `read` acceptance, same `multisig` rejection.
