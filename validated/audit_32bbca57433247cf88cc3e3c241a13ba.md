### Title
Unbounded recursive `AccountKey` RLP decoding causes stack-exhaustion DoS on `AccountUpdate`-type transactions - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`TxInternalDataAccountUpdate` (and its fee-delegated variants) carry an `accountkey.AccountKey` field that is decoded from raw bytes via a self-recursive `DecodeRLP` implementation. A crafted transaction whose `Key` bytes encode deeply nested `AccountKeyRoleBased` values will cause `AccountKeyRoleBased.DecodeRLP` to call `rlp.DecodeBytes` on itself once per nesting level, growing the Go call stack without any depth limit until the process crashes. The "no nested composite key" rule that is supposed to forbid this pattern is enforced only *after* decoding completes (in `tx.Validate()` / `CheckInstallable`), so it cannot prevent the stack exhaustion, which happens purely inside RLP decoding.

### Finding Description
`TxInternalDataAccountUpdate.DecodeRLP` decodes the serializable form and calls `fromSerializable`, which decodes the `Key` bytes into an `accountkey.AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type tag and then decodes the concrete key using `s.Decode(serializer.key)`: [2](#0-1) 

When `keyType == AccountKeyTypeRoleBased`, the target is `*AccountKeyRoleBased`, whose custom `DecodeRLP` reads a list of byte strings and, for **each element**, invokes a brand-new `rlp.DecodeBytes` call into a fresh `AccountKeySerializer`: [3](#0-2) 

Because each nested element is itself free to be another RLP-encoded `AccountKeySerializer` with `keyType = AccountKeyTypeRoleBased`, this produces genuine unbounded recursion: `DecodeRLP → rlp.DecodeBytes → Stream.Decode → decodeDecoder → DecodeRLP → rlp.DecodeBytes → ...`. There is no depth counter or recursion limit anywhere in this chain, unlike, e.g., Go's own `reflect`-based struct decoders which are bound by static Go types.

The only defense against nested `AccountKeyRoleBased` keys is the "no composite key" check, `IsCompositeType()`/`ErrNestedCompositeType`, but that check runs strictly *after* decoding has already completed, inside `AccountKeyRoleBased.CheckInstallable`/`CheckUpdatable`, which are only reached from `tx.Validate()`: [4](#0-3) 

Existing regression tests (`TestAccountUpdateRoleBasedKeyNested`) confirm that a *single* level of nesting is caught by `ErrNestedCompositeType`, but only at the tx-pool/`Validate()` stage — i.e., after `rlp.DecodeBytes`/`DecodeRLP` for the whole transaction has already succeeded: [5](#0-4) 

This is analogous to CVE-2019-12212, where `StreamCalcIFDSize` in FreeImage's JXR parser recursively called itself based on attacker-controlled nested structures with no depth bound, exhausting the stack. Here the recursive, self-feeding decode function is `AccountKeyRoleBased.DecodeRLP`, and the attacker-controlled "nesting" comes from the `Key` field of an `AccountUpdate`-family transaction.

### Impact Explanation
Any component that RLP-decodes a raw `TxTypeAccountUpdate` / `TxTypeFeeDelegatedAccountUpdate*` transaction — including `TxPool.AddRemote` reached from public RPC (`eth_sendRawTransaction`/`klay_sendRawTransaction`), p2p transaction gossip, and block/transaction validation during block processing — will attempt this recursive decode. A sufficiently deep nesting depth (bounded only by the size of the transaction payload, which can be made large) will exhaust the goroutine stack and crash the Go process (`fatal error: stack overflow`, which is not a recoverable `panic`). Because this triggers uniformly on every honest node that decodes the same transaction bytes (mempool relay, RPC submission, or block inclusion), it is a broadly reachable network-wide denial-of-service vector originating from a single unprivileged, unauthenticated submitted transaction — matching the required "unauthorized value movement/DoS reachable from a single submitted transaction" bar via node crash and consequent network disruption.

### Likelihood Explanation
High. Constructing the malicious payload requires no special privileges: any account can craft raw RLP bytes for an `AccountUpdate`-type transaction body with a nested `AccountKeyRoleBased` `Key` field of arbitrary depth and submit it via a public RPC endpoint or the p2p network. No valid signature verification, balance, or nonce check occurs before RLP decoding takes place — decoding happens as part of parsing the transaction itself, prior to and independent of the subsequent semantic `Validate()` checks.

### Recommendation
Add an explicit recursion/nesting depth limit to `AccountKeySerializer.DecodeRLP` and `AccountKeyRoleBased.DecodeRLP` (e.g., pass a depth counter through decoding and reject with an error once a small fixed bound, such as 1, is exceeded — enough to cover the single level of role-based nesting that is otherwise valid). This should be enforced during decoding itself, not only in the later `CheckInstallable`/`CheckUpdatable` validation, so that the byte size of the input directly limits achievable recursion depth to a small constant regardless of the encoded structure.

### Proof of Concept
1. Build a byte string `L0` that RLP-encodes an `AccountKeySerializer` with `keyType = AccountKeyTypeRoleBased` and a single-element key list `[L0]` (i.e., the key list element is itself another fully-encoded `AccountKeySerializer` of RoleBased type).
2. Repeat this nesting programmatically N times (e.g., tens of thousands of levels), each level wrapping the previous serialized bytes as the sole list element, analogous to the `nestedAccKey` construction shown in `tests/account_keytype_test.go` lines 1737-1739 but iterated instead of a single level.
3. Place the resulting deeply-nested byte blob into the `Key` field of a `TxInternalDataAccountUpdate`, matching the wire format built by `toSerializable`/`fromSerializable` (`blockchain/types/tx_internal_data_account_update.go:129-157`).
4. Sign the transaction normally and submit the raw RLP transaction bytes to a node's public RPC endpoint (`eth_sendRawTransaction`) or broadcast over the transaction gossip protocol.
5. When the receiving node calls `rlp.DecodeBytes`/`tx.DecodeRLP` on the payload, `AccountKeyRoleBased.DecodeRLP` recurses once per nesting level; at sufficient depth the goroutine stack is exhausted, crashing the node process before any `ErrNestedCompositeType` validation is ever reached.

```go
func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
```

```go
func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
```
