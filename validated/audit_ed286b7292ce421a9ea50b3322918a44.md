Based on my investigation, I found a strong analog to the Derby "shared reward pool with unaccounted-for double-claim" bug class in Agave's SIMD‑0123 block‑revenue-sharing reward path.

### Title
`pending_delegator_rewards` is never debited when block rewards are distributed to stakers, causing an unbacked/inflationary staking-reward claim on the shared vote-account reward pool - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
SIMD‑0123 lets a validator pre-fund a per-epoch reward pool on its vote account (`pending_delegator_rewards`) via `deposit_delegator_rewards`, which transfers lamports from a source account into the vote account and increments `pending_delegator_rewards`. [1](#0-0)  Every epoch, `calculate_block_reward` computes each stake delegation's proportional share of that same `pending_delegator_rewards` pool and credits it directly to the stake account. [2](#0-1)  The credited lamports are added to the stake account balance in `build_updated_stake_reward` [3](#0-2) , and the sysvar accounting explicitly treats these lamports as "already existing" so bank capitalization is *not* incremented when they are minted into the epoch-rewards sysvar or distributed out of it. [4](#0-3) [5](#0-4)  However, I could not find any code path that debits the vote account's own lamport balance or decrements `vote_state.pending_delegator_rewards` after that pool has been used to compute block rewards — `add_pending_delegator_rewards` is the only mutator I found, and it only increases the field. [6](#0-5) 

### Finding Description
This is the same broken invariant as the Derby report: a single accounted pool (`pending_delegator_rewards`) is treated as the basis for computing rewards that are paid out from a *separate* place (fresh stake-account lamports / the epoch-rewards sysvar) rather than being reduced from the pool that was supposed to back them. In the Derby case, two independent claimants (game players and vault stakers) both draw against `getTotalUnderlyingVault` without either side reducing the other's claim, so the sum of claims exceeds the pool. In Agave's analog, the "claim" (`calculate_block_reward`, using `pending_delegator_rewards` as the numerator) is recomputed from the *same, never-decremented* field every epoch that `block_revenue_sharing` remains active and the delegation continues to exist, while the actual lamports paid out are minted directly onto stake accounts without ever subtracting from the vote account balance or the `pending_delegator_rewards` counter.

Concretely:
- `calculate_block_reward` reads `vote_state.pending_delegator_rewards()` fresh from the vote account state on every call and uses it, unmodified, as the pool size for that stake delegation's share. [7](#0-6) 
- The resulting `block_reward` is added straight to the stake account's lamports in `build_updated_stake_reward`. [3](#0-2) 
- `distribute_epoch_rewards_in_partition` only increments capitalization by `stake_reward_lamports_minted` (the inflation share), never by `block_reward_lamports_distributed`, on the stated assumption that block-reward lamports "already existed" somewhere. [8](#0-7) 
- The epoch-rewards sysvar creation/update functions move lamports in and out of the sysvar account for `block_rewards` "without updating capitalization, since block reward lamports already existed" — but that pre-existence is only true for the *first* time a given deposit is spent; nothing marks the deposit as spent. [9](#0-8) [10](#0-9) 

Since `pending_delegator_rewards` is never reduced by the amount actually distributed, the same deposited pool is available to be "claimed" again in every subsequent epoch that the delegation remains active, effectively multiplying a single validator deposit into unlimited staking rewards not backed by capitalization — the direct analog of Bob and Alice both being able to withdraw against the same unreduced pool balance in the Derby report.

### Impact Explanation
If confirmed, this breaks the core Agave invariant that total lamports in all accounts equals `capitalization`, and lets stakers receive rewards repeatedly from a validator's single `DepositDelegatorRewards` deposit, i.e., false/duplicated reward issuance (fund creation) at consensus level, since this logic runs identically on every validator during epoch-boundary reward calculation and distribution. This would fall under "false execution/rooting/acceptance" and fund-theft/mint categories, since honest validators could unknowingly generate un-backed lamports every epoch a delegation stays active against a vote account with any positive `pending_delegator_rewards` balance.

### Likelihood Explanation
This code path executes automatically for every epoch boundary in which `block_revenue_sharing` (SIMD‑0123) and `custom_commission_collector`/`commission_rate_in_basis_points` are active and a vote account has `pending_delegator_rewards > 0`; no attacker action beyond a normal `DepositDelegatorRewards` call is required. The likelihood is high if my reading of the missing decrement is correct, but I want to flag material uncertainty: I was not able to fully search the entire repository (index size limits and iteration constraints), so a decrement site (e.g., inside `redeem_delegation_rewards`, `distribute_reward_commissions`, or a vote-program instruction I did not surface) may exist elsewhere and simply wasn't returned by my searches. I found `add_pending_delegator_rewards` as the sole exposed mutator in `vote_state/handler.rs` and no corresponding "subtract" method, and no call site debiting vote-account lamports for block rewards, but this should be verified by directly reading the full `partitioned_epoch_rewards` module and `vote_state` module in a real checkout before treating this as a confirmed, exploitable bug.

### Recommendation
- Confirm (via full source access, not the indexed snapshot) whether `pending_delegator_rewards` and the vote account's lamport balance are debited anywhere at distribution time (e.g., search for `checked_sub_lamports` calls scoped to vote accounts during `distribute_partitioned_epoch_rewards`, and for any additional mutator on `pending_delegator_rewards` beyond `add_pending_delegator_rewards`).
- If no such debit exists, `store_stake_accounts_in_partition`/`build_updated_stake_reward` must, for each `block_reward` credited to a stake account, atomically debit the same amount from the originating vote account's lamports and decrement `pending_delegator_rewards` by the aggregate amount distributed for that vote account in the epoch, so the pool cannot be re-used across epochs beyond its actual deposited/remaining balance.
- Add an invariant assertion (as already done for inflation rewards via `total_stake_rewards_lamports` bound checks) verifying that per-vote-account cumulative `block_reward` distributed across an epoch never exceeds that vote account's `pending_delegator_rewards` at the start of the epoch, and that capitalization changes reconcile with actual debits from vote accounts rather than being assumed pre-existing.

### Proof of Concept
Conceptual sequence (pending full-source confirmation):
1. Validator V deposits `D` lamports into its vote account via `DepositDelegatorRewards`, setting `pending_delegator_rewards = D`. [11](#0-10) 
2. At epoch N boundary, `calculate_block_reward` computes each delegator's proportional share of `D` and credits it to their stake accounts via `build_updated_stake_reward`, while `pending_delegator_rewards` on V's vote account remains `D` (no decrement observed). [2](#0-1) [3](#0-2) 
3. At epoch N+1 boundary, with no new deposit from V, `pending_delegator_rewards` is still read as `D`, so the same delegators again receive a full share of `D`, repeating indefinitely as long as `block_revenue_sharing` is active and stake remains delegated — each round adding lamports to stake accounts without a corresponding capitalization increase or vote-account debit. [8](#0-7) 

Because I could not fully verify the absence of a decrement across the entire codebase, I recommend the user start a Devin session with full repository access to trace every write site touching `pending_delegator_rewards` and vote-account lamports during the reward-distribution path before treating this as a confirmed critical finding.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)

    pub(crate) fn pending_delegator_rewards(&self) -> u64 {
        match &self.target_state {
            TargetVoteState::V4(v4) => v4.pending_delegator_rewards,
        }
    }

    pub(crate) fn add_pending_delegator_rewards(
        &mut self,
        amount: u64,
    ) -> Result<(), InstructionError> {
        match &mut self.target_state {
            TargetVoteState::V4(v4) => {
                v4.pending_delegator_rewards = v4
                    .pending_delegator_rewards
                    .checked_add(amount)
                    .ok_or(InstructionError::ArithmeticOverflow)?;
                Ok(())
            }
        }
    }
