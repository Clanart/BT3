### Title
Renderer runs with `nodeIntegration: true` / `contextIsolation: false`, a superfluous privilege grant beyond what the app's own IPC design requires - ([File: app/src/main-process/app-window.ts])

### Summary
The External Report's bug class is a capability declared/granted (`snap_getEntropy`) that is not needed by the code and therefore needlessly expands the attack surface if the sandboxed component is ever compromised. The equivalent invariant in GitHub Desktop is the main application window's Electron `webPreferences`, which grant the renderer full Node.js access (`nodeIntegration: true`) and disable process isolation (`contextIsolation: false`), even though Desktop already implements a dedicated, typed IPC bridge (`app/src/lib/ipc-renderer.ts`, `app/src/ui/main-process-proxy.ts`) for every legitimate main-process interaction the renderer needs. [1](#0-0) [2](#0-1) 

### Finding Description
`AppWindow`'s `BrowserWindow` (the main UI surface that renders GitHub-controlled content such as commit messages, branch/PR titles, notifications, and pull-request bodies/comments) is created with:

```
webPreferences: {
  disableBlinkFeatures: 'Auxclick',
  nodeIntegration: true,
  spellcheck: true,
  contextIsolation: false,
}
``` [1](#0-0) 

The same superfluous configuration is duplicated in `CrashWindow`: [2](#0-1) 

This is a superfluous privilege in the exact sense of the External Report: Desktop already built a strongly-typed IPC contract (`invoke`/`send`/`on` in `app/src/lib/ipc-renderer.ts`, wrapped by `invokeProxy`/`sendProxy` in `app/src/ui/main-process-proxy.ts`) specifically so the renderer never needs direct Node access to talk to the main process. [3](#0-2) [4](#0-3) 

Because that IPC layer already exists and is used pervasively, `nodeIntegration`/disabled `contextIsolation` is not required for any documented feature — it is an unused/unnecessary capability left enabled on the renderer, mirroring the "declared but unused" nature of `snap_getEntropy` in the original report. The Desktop team is clearly aware that content flowing from the GitHub API (PR/comment bodies) is attacker-influenced: they render it through `SandboxedMarkdown`, using `marked` + `DOMPurify` and an isolated `<iframe sandbox="allow-same-origin">` (no `allow-scripts`) specifically to prevent script execution from untrusted markdown. [5](#0-4) [6](#0-5) 

However, that containment is a property of the *iframe*, not of the *outer window*. The outer window that hosts `SandboxedMarkdown` and every other UI surface (diff viewer, file/branch names, notification toasts, repository/menu labels, etc.) still runs with Node integration enabled. Any script-execution primitive that reaches the outer renderer context — a DOMPurify/marked bypass, a future unsanitized surface, or any other XSS-class defect introduced by attacker-controlled Git/GitHub data — inherits full `require('child_process')`/`fs`/`electron` access instead of being confined to a sandboxed, isolated context.

### Impact Explanation
If any renderer-reachable XSS primitive is ever triggered by attacker-controlled data (a hostile repository's commit metadata, PR title/body, comment, notification content, or other API-sourced string rendered outside the hardened `SandboxedMarkdown` iframe), the superfluous `nodeIntegration: true` + `contextIsolation: false` configuration converts what would otherwise be a contained script-injection bug into full Node.js code execution in the user's session — file read/write outside any repo boundary, spawning of processes, and access to any credentials/tokens reachable from the Node process. This satisfies the "renderer-sandbox or IPC escape" impact category: the renderer is not actually sandboxed from the OS-level Node runtime, unlike a properly isolated Electron app where `contextIsolation: true` + a minimal `contextBridge` preload would confine any renderer compromise to the browser sandbox.

### Likelihood Explanation
Likelihood depends on a script-execution primitive existing somewhere in the renderer outside the `SandboxedMarkdown` iframe (which is itself hardened). This finding does not itself demonstrate such a primitive currently exists in the outer renderer — the search performed found no `dangerouslySetInnerHTML` usage in the codebase, and PR/comment bodies are consistently routed through `SandboxedMarkdown`. The likelihood is therefore best characterized as "elevated blast radius given a not-yet-identified renderer XSS," similar to how the original report's `snap_getEntropy` permission has no proven exploit path today but represents unnecessary exposure that should be removed under least-privilege principles. This is a defense-in-depth/least-privilege gap rather than a confirmed exploit chain.

### Recommendation
- Set `contextIsolation: true` and `nodeIntegration: false` on both `AppWindow` and `CrashWindow`'s `webPreferences`.
- Move any renderer functionality that currently relies on direct Node access to a `preload` script using `contextBridge.exposeInMainWorld`, exposing only the specific, already-typed IPC channels defined in `RequestChannels`/`RequestResponseChannels` (`app/src/lib/ipc-shared.ts`) that the renderer legitimately needs.
- Verify no renderer code path directly imports Node built-ins (`fs`, `path`, `child_process`, etc.) outside of the preload/main process after the change, since `app/src/ui/lib/sandboxed-markdown.tsx` currently calls `readFile` directly from the renderer bundle, which would need to be proxied through IPC once `nodeIntegration` is disabled. [7](#0-6) 

### Proof of Concept
Not directly exploitable from local inspection alone — the concrete PoC path would require a runtime demonstration that: (1) a DOMPurify/marked sanitizer bypass or another unsanitized renderer surface allows script execution in the main window context (outside the `SandboxedMarkdown` iframe), and (2) that script then calls `require('child_process').exec(...)` or similar to prove Node-level code execution is directly reachable due to `nodeIntegration: true`/`contextIsolation: false`. Confirming the existence of such a sanitizer bypass would require dynamic testing beyond what the static index search here can verify; the finding as documented is a systemic least-privilege violation (superfluous capability grant) analogous to the External Report's unused-permission bug class, not a fully chained RCE demonstrated in this analysis.

/**
 * Creates a strongly typed proxy method for sending a duplex IPC message to the
 * main process. The parameter types and return type are infered from the
 * RequestResponseChannels type which defines the valid duplex channel names.
 *
 * @param numArgs The number of arguments that the channel expects. We specify
 *                this so that we don't accidentally send more things over the
 *                IPC boundary than we intended to which can lead to runtime
 *                errors.
 *
 *                This is necessary because TypeScript allows passing more
 *                arguments than defined to functions which in turn means that
 *                functions without arguments are type compatible with all
 *                functions that share the same return type.
 */
export function invokeProxy<T extends keyof RequestResponseChannels>(
  channel: T,
  numArgs: ParameterCount<RequestResponseChannels[T]>
) {
  return (...args: Parameters<RequestResponseChannels[T]>) => {
    // This as any cast here may seem unsafe but it isn't since we're guaranteed
    // that numArgs will match the parameter count of the IPC declaration.
    args = args.length !== numArgs ? (args.slice(0, numArgs) as any) : args
    return ipcRenderer.invoke(channel, ...args)
  }
}
