### Title
Missing `cfg!(test)` guard on `internal_create_assert_commitment_txs` allows any mTLS peer to obtain operator-signed assert-commitment transactions with all-zero Winternitz data, enabling trivial disprove and operator collateral seizure — (`core/src/rpc/operator.rs`)

### Summary
The `internal_create_assert_commitment_txs` gRPC endpoint is reachable in production. It unconditionally constructs and returns operator-signed BitVM MiniAssert transactions with all-zero Winternitz commitment data. Any mTLS-authenticated caller can invoke it, receive the signed transactions, broadcast them on-chain, and trigger a successful disprove that seizes the operator's collateral UTXO.

### Finding Description
`internal_create_assert_commitment_txs` (lines 261–296 of `core/src/rpc/operator.rs`) accepts a caller-supplied `TransactionRequest` and calls `operator.create_assert_commitment_txs` with hardcoded zero assertion data:

```rust
ClementineBitVMPublicKeys::get_assert_commit_data(
    (
        [[0u8; 32]; NUM_PUBS],
        [[0u8; 32]; NUM_U256],
        [[0u8; 16]; NUM_HASH],
    ),
    &[0u8; 20],
)
```

The operator's signer signs the resulting MiniAssert transactions. These are returned as serialized, broadcast-ready Bitcoin transactions. Unlike `internal_finalized_payout` — which gates itself with `if !cfg!(test) { return Err(Status::permission_denied(...)) }` — this endpoint has no such guard and is fully active in production builds.

### Impact Explanation
The BitVM assert-commitment protocol requires the operator to commit to the real Groth16 proof outputs via Winternitz signatures in the MiniAssert transactions. All-zero commitments are trivially disprovable. If the returned transactions are broadcast, any on-chain challenger executes the disprove path and claims the operator's collateral UTXO — a direct, permanent loss of operator collateral.

### Likelihood Explanation
Medium. The attacker must hold a valid mTLS certificate for the operator's gRPC interface. In Clementine's multi-party deployment, verifiers, watchtowers, and aggregators all hold such certificates for legitimate inter-service calls. A malicious or compromised peer in any of those roles can exploit this endpoint without needing the operator's signing key.

### Recommendation
Add the same production guard used by `internal_finalized_payout`:

```rust
if !cfg!(test) {
    return Err(Status::permission_denied(
        "This method is only available in tests",
    ));
}
```

Alternatively, remove the endpoint entirely from production builds, or replace the hardcoded zero data with a parameter that callers must supply and that is validated against the operator's stored proof state.

### Proof of Concept
1. Obtain a valid mTLS client certificate for the operator's gRPC server (any bridge participant credential suffices).
2. Call `internal_create_assert_commitment_txs` with a `TransactionRequest` containing a `deposit_outpoint` and `kickoff_id` that exist in the operator's database.
3. Deserialize the returned `SignedTxsWithType` and extract the `MiniAssert` transactions.
4. Inspect the Winternitz witness data in each transaction — all commitment bytes are `0x00`.
5. Broadcast the transactions on-chain.
6. Execute the disprove script path; the all-zero commitments fail verification, and the operator's collateral UTXO is seized by the challenger.
