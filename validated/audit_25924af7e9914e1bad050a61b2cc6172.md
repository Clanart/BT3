The root cause is confirmed in `lib/shopify_app/controller_concerns/webhook_verification.rb` and `lib/shopify_app/controller_concerns/payload_verification.rb`: the HMAC is computed only over `request.raw_post`, and the shop identity (`X-Shopify-Shop-Domain` header, analogous to `chain.id` in the original report) is read out-of-band and never included in the signed/verified data.

### Title
Webhook HMAC signature excludes shop-domain identity, enabling cross-shop replay of signed webhook payloads - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates a webhook purely by checking that `HTTP_X_SHOPIFY_HMAC_SHA256` matches `HMAC(secret, request.raw_post)`. The `X-Shopify-Shop-Domain` header, which is what downstream code (jobs, `Shop.find_by(shopify_domain: shop_domain)`) trusts to identify *which* tenant the webhook belongs to, is never part of the signed material.

### Finding Description
`hmac_valid?` in `lib/shopify_app/controller_concerns/payload_verification.rb` computes/compares the HMAC solely over the raw POST body: [1](#0-0) 

`WebhookVerification#verify_request` uses this same check, and separately exposes an unauthenticated `shop_domain` helper that just reads the header: [2](#0-1) 

Since the app's client secret is shared across every shop that installs the app, this is a multi-tenant analog of the Harpie bug: the signature scope ("chain.id" there, "shop domain" here) is not bound into the signed data. Any entity that can obtain one valid `(body, HMAC)` pair — trivially possible since an attacker can install the app on their own shop and trigger their own real webhooks (e.g. `orders/create`, `customers/data_request`) — can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a victim shop. The HMAC check still passes because the header is not covered by the signature. Generated job templates and the built-in privacy-webhook jobs take the attacker-controlled `shop_domain` value at face value: [3](#0-2) [4](#0-3) 

The controller itself does no cross-check between the verified payload and the shop header either: [5](#0-4) 

### Impact Explanation
An attacker can forge the tenant attribution of an otherwise-legitimately-signed webhook, causing app-side jobs to run "as" a victim shop (`Shop.find_by(shopify_domain: shop_domain)` → `shop.with_shopify_session`) using attacker-supplied body content but the victim's real access token/session context. Depending on the app's webhook handlers, this can drive unauthorized state changes, spurious mandatory-privacy actions (`shop/redact`, `customers/data_request`), or data confusion attributed to the wrong shop — a cross-tenant integrity/authorization violation stemming from the same missing-scope-binding root cause as the reported Vault bug.

### Likelihood Explanation
Reachable by any anonymous HTTP request to the app's public webhook endpoint (`/webhooks/:type`), which has no other authentication. The only precondition is obtaining one valid signed webhook body, which any attacker can trivially get by installing the app on a shop they control and triggering topics they subscribed to.

### Recommendation
Bind the shop domain (and ideally the webhook ID) into the material verified for authenticity — e.g., derive the trusted shop from Shopify's own signed webhook metadata processed by `ShopifyAPI::Webhooks::Registry.process`/`WebhookHandler.handle` (which the underlying `shopify_api` gem is expected to validate) rather than trusting a bare, unauthenticated `shop_domain` helper independently in app code, and ensure custom controllers built on `ShopifyApp::WebhookVerification` never rely on the `shop_domain` header value without confirming it matches the shop the HMAC/registry validation actually attests to.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. `customers/data_request`, with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
2. Attacker POSTs the identical `B` and HMAC header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `WebhookVerification#verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb:15-21`) passes because HMAC only covers `B`.
4. The queued job (e.g. `lib/generators/shopify_app/add_privacy_jobs/templates/customers_data_request_job.rb.tt`) looks up `Shop.find_by(shopify_domain: "victim.myshopify.com")`, finds the real victim record, and executes `shop.with_shopify_session` using attacker-forged webhook content attributed to the victim.
