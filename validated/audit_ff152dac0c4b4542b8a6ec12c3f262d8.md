### Title
Missing recipient binding in DKG encrypted-share PoP lets an attacker redirect an honest dealer's message to a different recipient and get the dealer blamed/slashed - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`pop_challenge` (crypto/dkg/pedpop/src/encryption.rs:302-324) binds the per-message encryption key, the ciphertext, the context, and the **sender** — but never the intended recipient or the recipient's registered encryption key. `EncryptedMessage` therefore authenticates "Alice sent these bytes" without authenticating "Alice sent these bytes *to Bob*". An untrusted party that observes Alice's encrypted share to Bob can replay the identical bytes as Alice's share to Carol. Carol's `Encryption::decrypt` accepts it (the PoP verifies, the ECDH/key-derivation path is symmetric), obtains a valid `EncryptionKeyProof`, and both Carol's `calculate_share` and any third-party `AdditionalBlameMachine::blame` will conclude **Alice (the sender) is faulty** — even though Alice behaved honestly and never sent anything to Carol.

This is the trust-boundary-violation analog: a credential-bearing artifact minted inside one security boundary (Alice→Bob ECDH) is silently accepted under a different principal's boundary (Carol's decryption key), converting a message the attacker merely relays into a weapon against the honest sender.

### Finding Description
In `encrypt` (crypto/dkg/pedpop/src/encryption.rs:135-168), the sender picks a fresh ephemeral scalar `key`, encrypts under `ecdh(key, recipient_enc_pub_key)`, and signs a Schnorr PoP over `pop_challenge(context, pub_nonce, pub_key, from, ciphertext)`. The transcript at lines 309-319 appends `context`, `nonce`, `key`, `sender`, `message` — `to`/`recipient_enc_key` is absent.

On the receive side, `Encryption::decrypt` (encryption.rs:469-501) batch-verifies the same PoP, computes `key = ecdh(self.enc_key, msg.key)` using *the receiver's own* long-term decryption key, and returns a valid `EncryptionKeyProof` (a DLEq over `[G, msg.key]` vs `[enc_pub_key_recipient, shared_key]`). `Decryption::decrypt_with_proof` (encryption.rs:366-397) verifies that DLEq against `self.enc_keys[&decryptor]` — which resolves to *whoever the verifier believes the recipient was*. Both checks pass for a redirected message because neither the PoP nor the DLEq statement commits the intended recipient to the ciphertext.

Consequences in `KeyMachine::calculate_share` (crypto/dkg/pedpop/src/lib.rs:463-499): the misdirected ciphertext decrypts (with probability ~1) to a non-canonical scalar → `PedPoPError::InvalidShare { participant: alice, blame: Some(..) }`, or to a scalar that fails `share_verification_statements`. Either way the honest dealer Alice is reported faulty. A third party holding `AdditionalBlameMachine` (or `VerifyBlame` on the processor side) confirms blame against Alice via `blame_internal` (lib.rs:575-609), since the share simply doesn't verify against Alice's commitments at Carol's index.

### Impact Explanation
Blame in this DKG is fatal: an identified-faulty participant is slashed/excluded. An attacker who can observe and relay authenticated DKG traffic (e.g., the coordinator/channel that routes `EncryptedMessage`s between participants, which is exactly the untrusted-bytes reachability class for `EncryptedMessage::read`/`calculate_share`/`blame`) can cause an honest participant to be condemned as faulty with valid, universally-verifiable blame proofs. This is an integrity/availability violation of the key-generation protocol achievable with zero secret knowledge — mirroring the advisory's "steal another identity's authority by mounting its token" pattern: Alice's validly-signed artifact is mounted under a trust context (Carol's key) where it was never meant to be interpreted.

### Likelihood Explanation
Requires the attacker to sit on or influence the delivery path between DKG participants (a relay/coordinator role, or simply copying a broadcasted/authenticated message into another participant's share map). No collusion, no threshold compromise, and no key leakage is needed — only public ciphertext bytes and the ability to attribute them to a different recipient. Medium severity: concrete false-blame/slashing impact, but gated on delivery-path influence and on the DKG actually treating blame as punitive.

### Recommendation
Bind the recipient into the PoP. In `pop_challenge`, append the recipient's registered encryption public key (or participant index): `transcript.append_message(b"recipient", enc_pub_key.to_bytes())`, and pass it through both `encrypt` (already has `to: C::G`) and all verify sites (`Encryption::decrypt`, `Decryption::decrypt_with_proof`, `blame_internal`). This makes a redirected message fail PoP verification immediately, attributing fault to the relayer rather than the honest sender. Alternatively, include the recipient inside `context`.

### Proof of Concept
1. Participants Alice (1), Bob (2), Carol (3) run PedPoP with params t=2, n=3 over `Ristretto`. Alice's `SecretShareMachine::generate_secret_shares` emits `m_ab = EncryptedMessage` for Bob under `ecdh(k, enc_pub_bob)`, PoP-signed with `pop_challenge(ctx, R, K=kG, sender=1, ct)`.
2. Attacker observes `m_ab` on the authenticated channel and delivers it to Carol inside her `shares` map under key `Participant(1)` — i.e., as Alice's share for Carol — while dropping/withholding Alice's real `m_ac`.
3. Carol calls `KeyMachine::calculate_share(rng, shares)`. In `Encryption::decrypt`, `msg.pop.verify(K, pop_challenge(ctx, R, K, 1, ct))` succeeds — the PoP contains nothing tying it to Bob. Carol derives `key = enc_key_carol * K` (a valid ECDH; note it differs from Alice's `enc_key_bob * K`, so `ct` decrypts to garbage) and produces a *valid* `EncryptionKeyProof` since the DLEq proves `log_{enc_pub_carol}(proof.key) == log_G(K)` — mathematically true.
4. The garbage plaintext either fails `C::F::from_repr` (encryption.rs:480) or fails `share_verification_statements` (lib.rs:490) → `PedPoPError::InvalidShare { participant: 1 }`.
5. Any verifier runs `AdditionalBlameMachine::new(ctx, 3, commitment_msgs)` → `blame(sender=1, recipient=3, m_ab, Some(proof))`. `blame_internal` calls `decrypt_with_proof`, which verifies the PoP (still valid) and the DLEq against `enc_keys[3]` (valid — Carol's key), decrypts to the non-share bytes, and returns `sender` — Alice is definitively blamed and slashed for a message she never addressed to Carol. Bob, who received the genuine share, completes normally, so there is no consistency check that saves Alice.
