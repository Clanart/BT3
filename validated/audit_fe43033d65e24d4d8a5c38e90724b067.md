### Title
Unbounded `ThresholdKeys::read` deserialization enables quadratic CPU denial of service - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts an attacker-controlled participant count `n` up to `u16::MAX` and then calls `ThresholdKeys::new`, which computes the group key by evaluating a Lagrange interpolation factor for each of the first `t` participants. [1](#0-0)  Each interpolation-factor evaluation iterates over the same `t`-participant set, making group-key reconstruction `O(t²)` scalar work when `t == n`. [2](#0-1) [3](#0-2) 

### Finding Description
The deserialization format trusts two 16-bit fields, `t` and `n`, before reading one scalar and `n` group elements. [4](#0-3)  `ThresholdParams::new` only requires `t <= n`, so an input can legally declare `t = n = 65535`. [5](#0-4)  `ThresholdKeys::new` then constructs `included = [1, ..., t]` and calls `interpolation_factor` once for every participant in that list. [3](#0-2)  For Lagrange interpolation, every call loops over all `t` included participants, multiplies both numerator and denominator, and performs an inversion. [6](#0-5) 

### Impact Explanation
A serialized `ThresholdKeys` object of only a few megabytes can therefore trigger approximately `t²` field multiplications during deserialization. [7](#0-6) [8](#0-7)  With the maximum accepted values, this is roughly 4.29 billion inner-loop iterations, before accounting for the outer-loop inversion and point multiplication performed for each participant. [3](#0-2)  An unprivileged party that can submit these bytes to `ThresholdKeys::read` can monopolize the calling worker for a disproportionate amount of CPU time, analogous to blocking a shared service task. [9](#0-8) 

### Likelihood Explanation
The malicious input requires no secret material or malformed encodings: every participant index and every serialized point can be canonical and valid. [10](#0-9)  The only requirement is that the surrounding application deserializes attacker-supplied `ThresholdKeys`; the vulnerable behavior is entirely determined by the public `t` and `n` fields. [1](#0-0)  Repeating the request can amplify the denial of service across otherwise valid inputs. [3](#0-2) 

### Recommendation
Apply an application/protocol-level maximum threshold before deserialization, or extend the trusted serialization format with a precomputed group key rather than recomputing it from `t` Lagrange coefficients. [3](#0-2) [11](#0-10)  If arbitrary `n` must remain supported, bound deserialization work with an explicit byte/operation budget and fail before entering the quadratic interpolation path. [2](#0-1) 

### Proof of Concept
Construct a `ThresholdKeys` serialization whose curve ID matches the target ciphersuite, followed by little-endian `t = 65535`, `n = 65535`, `i = 1`, interpolation tag `1` for Lagrange, any canonical scalar as `secret_share`, and `65535` canonical generator encodings as verification shares. [10](#0-9)  Calling `ThresholdKeys::read` accepts those parameters because `1 <= i <= n` and `t == n`. [5](#0-4) [12](#0-11)  Construction then evaluates Lagrange factors for participants `1..=65535`, and each evaluation loops over all `65535` indexes, producing billions of field operations from a bounded input. [2](#0-1) [3](#0-2)

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
