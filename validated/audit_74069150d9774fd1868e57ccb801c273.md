Confirmed: the gate key comes from `request.from` (the arbitrary bytes an app on the source chain uses as its module id), and `AppKey::truncate_from` silently drops anything past 32 bytes rather than rejecting it — this is the aliasing-by-truncation analog of the "range-checked limbs but the whole value can still overflow/alias" bug class in the original report.

### Title
`AppKey::truncate_from` silently aliases distinct apps to the same bandwidth bucket, letting a purchaser drain another app's paid subscription - (File: `modules/pallets/bandwidth/src/lib.rs`, `modules/pallets/bandwidth/src/types.rs`)

### Summary
`pallet-bandwidth` keys every subscription bucket by `(chain, AppKey)` where `AppKey = BoundedVec<u8, ConstU32<32>>` [1](#0-0) . Both the credit path (`on_accept`) and the debit path (`try_consume`) build this key via `AppKey::truncate_from(...)`, which **silently truncates** any input longer than 32 bytes instead of rejecting it [2](#0-1) [3](#0-2) . Just as the OpenVM report's byte-wise range check on each limb didn't stop the *reconstructed* 32-bit value from wrapping BabyBear's modulus and aliasing a different memory address, per-byte validity of the `app` field here doesn't stop two distinct identifiers that share the same first-32-byte prefix from aliasing to the identical on-chain `AppKey`.

### Finding Description
- On the credit side, `BandwidthManager.purchase(bytes calldata app, ...)` on EVM accepts `app` as an arbitrary-length `bytes` value [4](#0-3) ; there is no length restriction to 20 or 32 bytes anywhere in the contract or in the pallet's `PurchaseMessage` decode [5](#0-4) .
- On the debit side, the consuming key is `request.from` — attacker-controlled bytes on the *dispatching* module of an arbitrary POST/GET, again with no length bound before being passed into the gate [6](#0-5) .
- Both paths funnel into `AppKey::truncate_from(app.to_vec())`, which per the `BoundedVec` semantics simply drops any bytes past index 32 rather than failing [7](#0-6)  and [8](#0-7) .
- This means any two `app` byte-strings that agree on their first 32 bytes but differ afterward collapse to the exact same `AppKey`, and therefore the exact same `Allowance::<T>` storage row.

### Impact Explanation
An attacker who controls a module dispatching through a bandwidth-gated source chain can construct a `from`/`app` value whose first 32 bytes match a legitimate, well-funded app's 20-byte address (left/right padded however the victim happens to encode it) but with extra trailing bytes. Any purchase made under this crafted identifier credits, and any dispatch made under it drains, the identical `Allowance` bucket as the real victim app. This lets the attacker:
- Spend (drain) bandwidth that a paying customer purchased for their own app, causing that app's legitimate messages to be rejected (`GateError::Insufficient`/`NoAllowance`) even though they paid — an unauthorized-transaction / loss-of-paid-resource condition tied directly to the "reward/bandwidth balances must move exactly once and only to the rightful beneficiary" pivot.
- Alternatively spoof a purchase credit onto a target bucket that the attacker doesn't legitimately own, corrupting the accounting the gate relies on for admission control.

### Likelihood Explanation
This does not require a malicious relayer, prover, or admin — any account able to call `BandwidthManager.purchase()` (permissionless) or able to dispatch a POST/GET request as an app module on a bandwidth-gated source chain can pick the `app`/`from` bytes themselves. Constructing a >32-byte identifier with an arbitrary 32-byte prefix collision is trivial (the attacker chooses both halves; nothing needs to be guessed) as long as the target's real key is a known, public 20-byte EVM address, which it always is.

### Recommendation
Reject `app`/`from` byte strings longer than the expected fixed width (e.g. exactly 20 bytes for EVM app identifiers, or whatever canonical width the protocol commits to) at both the `PurchaseMessage::try_from` decode step and in the runtime's bandwidth-gate call site, instead of silently truncating via `BoundedVec::truncate_from`. Use a fallible `try_from`/`BoundedVec::try_from` that errors on oversize input so distinct identifiers can never collapse into the same `AppKey`.

### Proof of Concept
1. Victim deploys app `V` at EVM address `0xAAAA…AAAA` (20 bytes) and buys bandwidth via `BandwidthManager.purchase(app = 0xAAAA…AAAA, tier, months, chain)`. The pallet credits `Allowance[(chain, AppKey(0xAAAA…AAAA))]` with fresh bytes [9](#0-8) .
2. Attacker (unprivileged) dispatches an ordinary ISMP POST from the same source chain with `request.from = 0xAAAA…AAAA‖<12 extra bytes>` (33 bytes total, sharing the victim's 32-byte prefix once padded/aligned).
3. `ProxyModule::on_accept` calls `try_consume(source, &request.from, bytes)`, which builds `AppKey::truncate_from(request.from.to_vec())` — the trailing bytes are dropped, producing the exact same `AppKey` as the victim's [3](#0-2) .
4. The gate drains `V`'s paid `remaining_bytes` for the attacker's unrelated message, and repeating this exhausts `V`'s subscription (`GateError::Insufficient`/`NoAllowance` starts firing for `V`'s legitimate future messages) even though `V` paid and never authorized this consumption.

impl TryFrom<&[u8]> for PurchaseMessage {
	type Error = anyhow::Error;

	fn try_from(body: &[u8]) -> Result<Self, Self::Error> {
		let abi = BandwidthPurchaseMsg::abi_decode(body)
			.map_err(|err| anyhow::anyhow!(format!("invalid bandwidth purchase ABI: {err:?}")))?;

		let tier: u32 = abi.tier.try_into().map_err(|_| anyhow::anyhow!("tier exceeds u32"))?;
		let months: u32 =
			abi.months.try_into().map_err(|_| anyhow::anyhow!("months exceeds u32"))?;
		if months == 0 {
			return Err(anyhow::anyhow!("months must be >= 1"));
		}
		let chain_str = str::from_utf8(&abi.chain)
			.map_err(|err| anyhow::anyhow!(format!("chain is not utf-8: {err}")))?;
		let chain = StateMachine::from_str(chain_str)
			.map_err(|err| anyhow::anyhow!(format!("invalid chain {chain_str:?}: {err}")))?;

		Ok(PurchaseMessage { app: abi.app.into(), tier, months, chain })
	}
