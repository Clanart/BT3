### Title
Bitcoin signing API authenticates the claimed prevout script but not the claimed source outpoint - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction` treats attacker-controlled `ReceivedOutput` records as authentic Bitcoin UTXOs. `ReceivedOutput::read` accepts an arbitrary `(offset, TxOut, OutPoint)` tuple, while `SignableTransaction::multisig` only checks that the supplied `TxOut.script_pubkey` corresponds to the threshold key after applying the supplied offset. It does not verify that the supplied `OutPoint` exists or that the claimed `TxOut` is the source output referenced by that outpoint.

### Finding Description
`ReceivedOutput::read` deserializes the offset, `TxOut`, and `OutPoint` independently and returns them as an allegedly spendable output. `SignableTransaction::new` then stores the deserialized `TxOut` in `prevouts` and places the independently supplied `outpoint` into the transaction input. During `multisig`, authorization is based only on:

```rust
p2tr_script_buf(offset.group_key())? == self.prevouts[i].script_pubkey
```

That check proves the claimed `TxOut` pays to a key controlled by the signing group, but it does not prove that this `TxOut` is the source output named by `previous_output`. An attacker can therefore pair the group's valid script with an arbitrary or nonexistent outpoint and arbitrary value, then have the resulting attacker-controlled sighash signed.

### Impact Explanation
This is analogous to validating a destination while failing to authorize the source object. The signing destination constraints—payments, fee, dust, and transaction weight—are enforced, but the source output's existence and association with its outpoint are not authenticated. An attacker who can cause untrusted `ReceivedOutput` bytes to be deserialized and passed through `SignableTransaction::new` and `multisig` can obtain threshold signatures for sighashes describing sources the signer never established ownership of.

The resulting Bitcoin transaction will generally be invalid on-chain when the alleged prevout is nonexistent or misdescribed, but the API still produces a valid threshold signature over an unintended message. This can undermine downstream code that treats a completed transaction as proof that its inputs were previously authenticated.

### Likelihood Explanation
The vulnerable path is reachable whenever serialized `ReceivedOutput` values are accepted from storage, peers, recovery material, RPC-derived data, or another component that does not independently prove their provenance. The attacker does not need to know the threshold secret share: they only need the public group key to construct a matching Taproot script and can select the offset, value, and outpoint bytes.

Exploitation requires the caller to feed attacker-controlled `ReceivedOutput` records into the signing flow rather than exclusively using outputs returned by `Scanner::scan_transaction`. The API boundary itself does not enforce that invariant.

### Recommendation
Authenticate the source object before signing. In particular:

- Resolve every `OutPoint` against a trusted Bitcoin backend and compare the returned `TxOut` byte-for-byte with `prevouts[i]`.
- Require sufficient confirmations/maturity for the resolved source output.
- Reject `ReceivedOutput::read` results for signing unless their provenance has been authenticated or revalidated.
- Optionally store and verify a cryptographic UTXO proof where available, instead of trusting deserialized `TxOut`/`OutPoint` pairing.
- Document that `ReceivedOutput` is a claim about a source output, not authenticated evidence that the source exists.

### Proof of Concept
The following pseudocode demonstrates the missing source authentication. It constructs a `ReceivedOutput` whose script belongs to the threshold key but whose outpoint is arbitrary:

```rust
use bitcoin::{OutPoint, TxOut, Amount, ScriptBuf};
use k256::Scalar;
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction, p2tr_script_buf};

let group_key = threshold_keys.group_key();

let forged = ReceivedOutput {
    // Cannot construct fields directly outside the crate; equivalent bytes can be
    // supplied through ReceivedOutput::read.
    offset: Scalar::ZERO,
    output: TxOut {
        value: Amount::from_sat(1_000_000),
        script_pubkey: p2tr_script_buf(group_key).unwrap(),
    },
    outpoint: OutPoint::null(), // arbitrary/nonexistent source
};

let signable = SignableTransaction::new(
    vec![forged],
    &[(ScriptBuf::new_op_return(&[]), 546)],
    None,
    None,
    1,
).unwrap();

// This succeeds because only forged.output.script_pubkey is compared with
// p2tr_script_buf(group_key + offset). The arbitrary/nonexistent outpoint and
// forged source value are never authenticated.
let machine = signable.multisig(&threshold_keys).unwrap();
```

After normal preprocessing and signing, `complete` returns a transaction whose input claims `OutPoint::null()` while its sighash commits to the forged `TxOut`. No code path verifies that the outpoint references that `TxOut`.
