I found a strong candidate analog in the Bitcoin scanner. Let me verify the details.### Title
Scanner attaches per-transaction metadata to outputs of unrelated transactions once any earlier transaction in the block matched - (`processor/src/networks/bitcoin.rs:686-740`)

### Summary
`Bitcoin::get_outputs` accumulates Serai-bound outputs in a block-wide `outputs` vector, but the per-transaction guard `if outputs.is_empty() { continue; }` checks that shared vector, not the current transaction's matches. Consequently, any transaction in a block that follows a matching transaction is never skipped: its `input[0]` (spoofed `presumed_origin`) and its OP_RETURN payload (`extract_serai_data`) are stamped onto **all** previously collected outputs, including deposits made by unrelated transactions. This is a direct analog of CVE-2021-41250 — a filter meant to reject/skip a non-matching item is defeated by the presence of an earlier matching item in the same message/block.

### Finding Description
In `get_outputs`, the loop over `block.txdata[1 ..]` scans each transaction for outputs paying the multisig key:

- `processor/src/networks/bitcoin.rs:691-700` — matching outputs are pushed into the shared `outputs` vec.
- `processor/src/networks/bitcoin.rs:702-704` — `if outputs.is_empty() { continue; }` is intended to skip transactions with no Serai output, but it tests the accumulated vec, so after the first matching transaction it is **always false**.
- `processor/src/networks/bitcoin.rs:714-728` — `presumed_origin` is derived from `tx.input[0].previous_output` of the *current* transaction.
- `processor/src/networks/bitcoin.rs:730-736` — `extract_serai_data(tx)` is computed for the current transaction and `clone_from` overwrites `data` (for `OutputType::External`) and `presumed_origin` on **every** output accumulated so far.

So if tx1 contains a deposit to the Serai vault and tx2 (attacker-controlled, no Serai outputs) is in the same block, tx1's `Output` ends up with tx2's `presumed_origin` and tx2's instruction `data`. Each subsequent transaction in the block re-overwrites these fields, so the *last* transaction in the block controls the metadata of *all* deposits in that block.

The `data` field is the InInstruction payload (e.g., the destination Serai address / refund path for minting against a Bitcoin deposit, as exercised in `processor/src/tests/literal/mod.rs`), and `presumed_origin` is used downstream to attribute the deposit's origin.

### Impact Explanation
An unprivileged Bitcoin user who can get a transaction mined in the same block as a victim's deposit (e.g., by watching the mempool and bidding fees, or simply because Bitcoin deposits frequently share blocks) can:

- Attach attacker-chosen `data` to the victim's deposit output. Where a deposit without embedded instruction data would normally carry empty data, the attacker's OP_RETURN payload is grafted on, letting them specify an instruction the depositor never authored (e.g., routing the minted coins to an attacker-controlled Serai address — "funds reported received" with attacker-attributed metadata).
- Spoof `presumed_origin` for every deposit in the block, corrupting attribution/refund routing.

Both are pure-Bitcoin public inputs (`tx.input[0]` and OP_RETURN `data` are fully attacker-chosen) reaching the in-scope `ReceivedOutput`/scanner path, matching the accepted impact classes.

### Likelihood Explanation
Requires only sending an ordinary Bitcoin transaction ordered after a matching deposit within the same block — standard miner ordering / fee bidding suffices. No threshold collusion, no validator compromise. Deterministic whenever a block contains a Serai-bound output followed by the attacker's transaction.

### Recommendation
Track per-transaction results: collect `let mut tx_outputs = scanner.scan_transaction(tx)` results into a local list, `continue` only when *that* list is empty, apply `presumed_origin`/`data` to the local list, then `outputs.extend(tx_outputs)`. This also fixes the correctness bug where later transactions overwrite earlier transactions' legitimately-extracted data.
