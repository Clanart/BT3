### Title
DataLayer mirror URLs enable Server-Side Request Forgery (SSRF) against subscribing peers - ([File: chia/data_layer/download_data.py])

### Summary
Chia's DataLayer mirror mechanism lets any wallet user publish an on-chain "mirror" coin that associates an arbitrary URL with *any* store id (`launcher_id`), including store ids they do not own. Any node subscribed to that store id will fetch data from the published URL via `http_download`, which issues an outbound `aiohttp` request with no validation that the URL does not target internal/private network resources. This mirrors the bug class in the reported fetch-mcp SSRF (CVE-2025-65513/CWE-918): a server-side fetch of an attacker-supplied URL with no private-IP/host filtering.

### Finding Description
`DataLayerWallet.create_new_mirror()` creates a mirror coin with the puzzle hash `create_mirror_puzzle().get_tree_hash()` and memos `[launcher_id, *urls]`, with **no check that `launcher_id` is owned by the caller**: [1](#0-0) 

The RPC endpoint that exposes this to any wallet client performs the same unrestricted call: [2](#0-1) 

The CLI (`add_mirror`) documents this as a generic "publish mirror urls on chain" action, with no ownership requirement enforced beyond a fee: [3](#0-2) 

These mirror coins are parsed on-chain purely from `CREATE_COIN` conditions/memos with no host/scheme filtering: [4](#0-3) 

When any node tracks/subscribes to that `store_id`, `DataLayer.update_subscriptions_from_wallet()` pulls all mirror URLs for the launcher id (again, with no ownership or host filtering) and feeds them into local subscription state: [5](#0-4) 

During the periodic sync loop, `fetch_and_validate()` iterates the stored server URLs and calls `insert_from_delta_file()` → `download_file()` → `http_download()`: [6](#0-5) 

`http_download()` performs the actual outbound request using the attacker-supplied URL directly, with **no validation rejecting private/loopback/link-local/metadata-service addresses**: [7](#0-6) 

Note that Chia does have private-IP detection utilities (`IPAddress.is_private`, `is_localhost`, `is_in_network`) used elsewhere in the codebase for peer trust decisions, but they are **not** applied to mirror/downloader URLs before `http_download` issues the request: [8](#0-7) [9](#0-8) 

This is the same root-cause class as the reported fetch-mcp SSRF: a fetch function takes attacker-controlled input (a URL) and performs a network request without validating that the target host is not a private/internal address, allowing an attacker to make the victim's process issue requests to arbitrary internal endpoints (e.g., localhost admin ports, cloud metadata endpoints, internal RPC services on the victim's LAN).

### Impact Explanation
An unprivileged wallet user can publish a mirror coin naming any store id (including a legitimate/popular public DataLayer store) with a URL pointing at the victim's internal network (e.g. `http://127.0.0.1:<admin-port>/...`, `http://169.254.169.254/...`, internal RPC endpoints). Any node that subscribes to that store — a normal, expected DataLayer client action for consuming public data — will periodically have its DataLayer service (`fetch_and_validate`/`periodically_manage_data`) issue outbound HTTP requests to that internal target, because `http_download()` performs no destination-host validation. This can be used to probe or interact with services bound to localhost/internal network on the victim's machine (SSRF), and because the mirror URL and filename are attacker-influenced, it could also be leveraged to trigger internal side effects on services that respond to unauthenticated GET requests. The DataLayer team's own internal documentation explicitly acknowledges mirror URLs are untrusted ("Do not treat mirror URLs, plugins, or static file names as trusted data sources"), showing the trust boundary is known — the missing piece is that the HTTP fetch itself does not reject private/internal destinations. This qualifies as Medium severity in line with the referenced advisory's CVSS (network-reachable, no privileges, some confidentiality/integrity impact on internal services), reachable purely through a "Data Layer client" subscribing to a public store.

### Likelihood Explanation
Likelihood is realistic: creating a mirror coin only requires a standard wallet transaction with a small fee and is explicitly a supported, unprivileged action (`create_new_mirror`/`dl_new_mirror`/`add_mirror` CLI/RPC) with no restriction tying the target `launcher_id` to the caller's own store. Any client that subscribes to a store for legitimate data-consumption reasons (which is DataLayer's normal usage pattern for public datasets) is automatically exposed, without any additional action, once the malicious mirror is confirmed on-chain and the victim's periodic subscription-management loop (`periodically_manage_data`) runs.

### Recommendation
- Before issuing any outbound request in `http_download()` (and in the plugin/S3 handoff to `downloader.url`), resolve and validate the target host against private/loopback/link-local/multicast ranges (reusing `chia.util.network`/`chia.util.ip_address` helpers already present in the codebase) and reject or explicitly opt-in via configuration.
- Consider restricting `create_new_mirror`/`dl_new_mirror` to require that the caller owns the `launcher_id` singleton, or otherwise flag/segregate untrusted mirrors so nodes can opt out of following mirrors for stores they don't administer.
- Apply the same URL validation to `get_downloader()`'s plugin `handle_download` POST target and to `DataLayerServer` uploader/downloader plugin URLs, since they are also attacker-influenceable via mirror data.

### Proof of Concept
1. Attacker wallet calls `dl_new_mirror`/`add_mirror` RPC with `launcher_id` = the store id of a public DataLayer dataset the attacker does not own, and `urls=["http://127.0.0.1:<internal-service-port>"]` (per `chia/wallet/wallet_rpc_api.py:3255-3274` and `chia/data_layer/data_layer_wallet.py:687-703`, no ownership check blocks this).
2. The mirror coin confirms on-chain; any node that has subscribed to that `store_id` calls `update_subscriptions_from_wallet()` (`chia/data_layer/data_layer.py:979-985`), pulling the attacker's URL into local subscription state.
3. During the periodic sync loop, `fetch_and_validate()` selects the malicious `server_info.url` and calls `insert_from_delta_file()` → `download_file()` → `http_download()` (`chia/data_layer/data_layer.py:642-694`, `chia/data_layer/download_data.py:110-169,298-323`), which performs `session.get("http://127.0.0.1:<port>/" + filename, ...)` from the victim's own process — an SSRF request to an internal endpoint chosen entirely by the attacker.

```python
def create_mirror_puzzle() -> Program:
    return P2_PARENT.curry(Program.to(1))


MIRROR_PUZZLE_HASH = create_mirror_puzzle().get_tree_hash()


def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
```
