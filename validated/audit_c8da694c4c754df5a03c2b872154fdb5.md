### Title
Cross-Language Inconsistency in `debug_redact` Sensitive-Field Masking — Pure-Python `TextFormat` Does Not Redact Annotated Fields (File: `python/google/protobuf/text_format.py`)

### Summary
Protobuf lets a schema owner mark a field `[debug_redact = true]` so that `TextFormat`/`DebugString()` output replaces its value with `[REDACTED]` instead of the real content, intended to prevent sensitive data from leaking into logs, crash dumps, or debug UIs. In the C++ and Java implementations this check is enforced (`TryRedactFieldValue`/`shouldRedact`), but the pure-Python `text_format.py` implementation contains no reference to `debug_redact` at all, so a field explicitly annotated as sensitive is printed in full when serialized through Python's `TextFormat`/`MessageToString`/`str()`/`DebugString()` path.

### Finding Description
The external report's bug class is: a value that the application schema/policy marks as "must be masked from a given audience" is not actually masked because the enforcement check is missing on one code path, while it is enforced elsewhere (view filter metadata was masked for the write-capable role's view but not for the read-only role in Nextcloud Tables).

The same invariant/attacker-value/missing-check pattern transfers to Protobuf's `debug_redact` field option:
- **Trusted invariant**: any field marked `[debug_redact = true]` in the `.proto` schema must be rendered as `[REDACTED]` whenever a message is converted via `TextFormat`/`DebugString`, regardless of language backend.
- **Attacker-controlled value**: an ordinary client populates that field (e.g. an SSN, token, or PII string) through a normal parse API; the field's *contents* are attacker/user-controlled even though the *annotation itself* is trusted schema.
- **Missing check**: `google.protobuf.Descriptors.FieldDescriptor.getRedactionState()` in Java (`java/core/src/main/java/com/google/protobuf/Descriptors.java:2085-2111`) and `TextFormat::GetRedactionState`/`TryRedactFieldValue` in C++ (`src/google/protobuf/text_format.cc:3265-3305`) both consult `FieldOptions.debug_redact` before printing a field value. The equivalent Python module, `python/google/protobuf/text_format.py`, has **zero occurrences** of `redact`/`debug_redact` anywhere in the file — there is no `shouldRedact`/`TryRedactFieldValue` analog gating the printer.
- **Impact**: an application that relies on Protobuf's built-in redaction to scrub sensitive annotated fields before writing `str(message)`/`text_format.MessageToString(message)` to logs, error reports, or debug endpoints will disclose the sensitive value when running on the pure-Python implementation, even though the identical schema and message handled by the C++/Java backend would correctly redact it. This is exactly the "broken sensitive-data masking" pattern from the report: masking is enforced for one consumer/backend but silently bypassed for another. [1](#0-0) [2](#0-1) [3](#0-2) 

I searched `python/google/protobuf/text_format.py` and the broader `python/**` tree for `debug_redact`/`Redact` and found no matches, confirming the Python pure implementation does not implement this gate. I was not able to fully trace, within the remaining tool budget, whether Python's C-extension/upb-backed message (`python_message.py`'s `__str__`/`DebugString`) delegates to a native C++/upb printer that does perform redaction for the default installed backend, versus the pure-Python fallback path (`text_format.py`) which clearly does not. This distinction matters for exploitability and should be verified directly in a checkout before treating this as confirmed exploitable in the default pip package. [4](#0-3) 

### Impact Explanation
If confirmed reachable (i.e., an application on a Python runtime path that resolves to the pure-Python `text_format.py` printer, such as `PYTHON` implementation env var / no compiled extension available), this causes disclosure of data the schema author explicitly intended to keep out of debug/log output — directly analogous to the Nextcloud CVE's "read-only users can see filter metadata that should have been masked." The severity ceiling is bounded because: (1) `debug_redact` is documented upstream as a best-effort debugging aid, not a hard security boundary; (2) it requires the consuming application to actually rely on `TextFormat`/`DebugString` output as a sensitive-data barrier (e.g., logging pipelines) rather than encryption/ACLs; (3) it only affects the pure-Python backend path, not binary/ProtoJSON serialization used for real data transfer.

### Likelihood Explanation
Likelihood is moderate: any application using protobuf-python without the compiled/upb extension (e.g., constrained environments, `PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python`, or certain minimal installs) and printing `DebugString()`/`str(message)` for logging would trigger this by default, with no special crafted input needed beyond normal population of the sensitive field.

### Recommendation
Add the same `debug_redact` check present in the C++/Java printers to `python/google/protobuf/text_format.py`'s field-printing routine (gate value emission on `field.GetOptions().debug_redact`, matching `TextFormat::Printer::TryRedactFieldValue` semantics), and add parity tests analogous to `DebugFormatTest`/`text_format_unittest.cc`'s `ShortFormat`/redaction tests for the Python backend. Audit other language bindings (Ruby, PHP, C#, Objective-C) similarly, since grep found no `debug_redact` references outside descriptor-option plumbing in `csharp/**` and none at all in `ruby/**`.       RedactionState state = redactionState;
      if (state == null) {
        // If the field is directly marked with debug_redact=true, then it is sensitive.
        synchronized (this) {
          state = redactionState;
          if (state == null) {
            FieldOptions options = getOptions();
            state = RedactionState.of(options.getDebugRedact());
            // Check if the FieldOptions contain any enums that are marked as debug_redact=true,
            // either directly or indirectly via a message option.
            for (Map.Entry<Descriptors.FieldDescriptor, Object> entry :
                options.getAllFields().entrySet()) {
              state =
                  RedactionState.combine(

              if (state.redact) {

              }

          }

bool TextFormat::Printer::TryRedactFieldValue(
    const Message& message, const FieldDescriptor* field,
    BaseTextGenerator* generator, bool insert_value_separator) const {
  TextFormat::RedactionState redaction_state =
      DescriptorPool::MemoizeProjection(
          field, [](const FieldDescriptor* field) {
            return TextFormat::GetRedactionState(field);
          });
  if (redaction_state.redact) {
    if (redact_debug_string_) {
      IncrementRedactedFieldCounter();
      if (insert_value_separator) {
        generator->PrintMaybeWithMarker(MarkerToken(), ": ");
      }
      generator->PrintString(kFieldValueReplacement);
      if (insert_value_separator) {
        if (single_line_mode_) {
          generator->PrintLiteral(" ");
        } else {
          generator->PrintLiteral("\n");
        }
      }
      return true;
    }
  }
  return false;
}
