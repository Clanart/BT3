### Title
HMAC verification does not bind the `X-Shopify-Shop-Domain` header, allowing cross-shop webhook forgery/replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates authenticity of a webhook request solely by checking an HMAC over `request.raw_post` (the body), using the app's shared secret. The shop-identifying header `X-Shopify-Shop-Domain`, exposed via `#shop_domain`, is never included in that HMAC computation. Consequently, a valid HMAC only proves "this body was signed with our app secret" — it proves nothing about which shop the request is attributed to. Any actor who possesses one genuine, validly-signed webhook body (e.g., a merchant that installed the app and received real webhooks from their own shop) can replay that exact body with a forged `X-Shopify-Shop-Domain` header pointing at a different, unrelated shop, and the request still passes verification.

### Finding Description
`hmac_valid?` in `lib/shopify_app/controller_concerns/payload_verification.rb` computes the digest strictly from `data` (`request.raw_post`): [1](#0-0) 

`verify_request` in `WebhookVerification` calls this with only the raw body, and `shop_domain` is read straight off request headers, entirely outside the signed material: [2](#0-1) 

The stock `ShopifyApp::WebhooksController#receive` forwards `request.headers.to_h` (including the unauthenticated shop-domain header) straight into `ShopifyAPI::Webhooks::Registry.process`: [3](#0-2) 

Downstream, the gem's own documentation and generator template show that this unauthenticated `shop`/`shop_domain` value is exactly what's used to resolve the tenant and drive stateful side effects (record lookups, session activation, business logic): [4](#0-3) [5](#0-4) 

This is the same bug class as the external report: a verification step ("the transaction/signature succeeds") is decoupled from the actual identity/context the downstream code acts on ("which account/shop the action is executed against"). Just as a delegation's caveats can pass while the real executed action diverges from what was verified, here the HMAC can pass while the shop context the job/webhook processing uses is attacker-controlled and unrelated to the signed payload.

### Impact Explanation
An attacker who legitimately installs the app on their own shop (a routine, unprivileged action) receives real Shopify webhooks with valid HMACs for their own shop's body content. They can replay that identical body against the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value for any other shop that has ever installed the app. Because the header is not part of the signed data, the request is accepted as authentic, and the queued job/business logic will execute using the attacker-chosen shop context — e.g., writing/mutating data keyed to a victim shop, marking stateful counters, or triggering privacy/uninstall-related workflows against a shop the attacker does not control. This is a cross-shop state-corruption / trust-boundary violation reachable by any unrelated merchant, not just an app operator.

### Likelihood Explanation
Any merchant who installs the app can trivially capture at least one valid `(body, hmac)` pair from their own legitimate webhook traffic (e.g., via browser devtools proxy or their own endpoint logs before this reaches the app, or simply by having their own webhook delivered and inspecting the raw request their server received) and replay it with a modified shop-domain header. No secrets, insider access, or dependency bugs are required — only observation of one's own legitimately received webhook and a basic HTTP replay.

### Recommendation
Do not treat the `X-Shopify-Shop-Domain` header (or any other header) as trusted tenant context unless it is cryptographically bound to the verified payload. Either:
1. Include the shop-domain header (and other identifying headers) in the HMAC-covered data used by `hmac_valid?`, or
2. Cross-check the header's shop against a shop-scoped secret/session already on record (i.e., verify the HMAC using a per-shop secret associated with the claimed `shop_domain`, not only the global app secret) so a mismatch between signed body and claimed shop is rejected, or
3. At minimum, resolve the tenant strictly from data embedded in the verified body payload rather than from unauthenticated headers.

### Proof of Concept
1. Install the target app on Shop A (attacker-controlled) and capture a real webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared secret), header `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Replay the exact same POST to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a victim shop that also installed the app).
3. `WebhookVerification#verify_request` calls `hmac_valid?(B)` which succeeds because the body and HMAC still match — the header substitution has no effect on the signature check.
4. `WebhooksController#receive` forwards the headers (including the forged shop domain) to `ShopifyAPI::Webhooks::Registry.process`, which dispatches to the app's job with `shop: "shop-b.myshopify.com"`, causing shop-B-scoped state changes/business logic to run using attacker-supplied body content, despite the request never having been authenticated for shop B.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
