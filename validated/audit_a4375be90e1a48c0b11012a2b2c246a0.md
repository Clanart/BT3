### Title
Unbounded participant count in `ThresholdKeys::read` enables quadratic-CPU denial of service via `Interpolation::Lagrange` - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
CVE-2022-1174 is a DoS where attacker-controlled input forces disproportionate CPU work. The analog in Serai is `ThresholdKeys::read` in `crypto/dkg`: an attacker supplies serialized keys with a large `n`/`t` and `Interpolation::Lagrange`, causing `ThresholdKeys::new` to compute a Lagrange interpolation over participants `1..=t` whose coefficient evaluation is quadratic in `t`. A ~2 MB input forces on the order of billions of field multiplications plus tens of thousands of point decompressions, hanging the verifying/signing host.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` as attacker-controlled `u16`s, so `n` and `t` can each be as large as 65535. It then reads `n` verification-share points, each through `C::read_G` (full point decompression), and calls `ThresholdKeys::new(ThresholdParams::new(t, n, i), interpolation, secret_share, verification_shares)` with no upper bound beyond what `ThresholdParams::new` enforces (t ≤ n, i ≤ n).

When `interpolation` is `Interpolation::Lagrange`, `ThresholdKeys::new` derives the group key by interpolating the verification shares of participants `1..=t` at x=0. The Lagrange coefficients are computed over `t` distinct indexes, which is O(t²) field multiplications (each coefficient is a product of `t` factors), followed by a `t`-element multiexp. With `t = n = 65535`, this is ~4·10⁹ scalar multiplications and ~65k point decompression/scalar-multiplication operations, triggered by roughly `n * 33 bytes` (~2 MB) of input. There is no transaction/size bound inside the crypto crate — the read loops purely off the encoded `n`.

The same read path with `Interpolation::Constant` still forces `n` scalar reads plus an `n`-element multiexp (linear, ~65k point ops) — weaker, but the Lagrange path is the quadratic amplification.

### Impact Explanation
Any component that deserializes `ThresholdKeys` from bytes an unprivileged party can supply (e.g., untrusted bytes fed to `ThresholdKeys::read` per the threat model) burns CPU quadratic in the attacker-chosen threshold. A single small message can pin a core for an extended period, stalling signing/DKG completion for everyone. This is a pure CPU-amplification DoS matching the advisory's bug class (high CPU via crafted input).

### Likelihood Explanation
Exploitation requires reaching `ThresholdKeys::read` with attacker bytes. In Serai's deployment, `ThresholdKeys` are locally generated rather than received over the wire, so the reachable surface is narrower than e.g. `read_preprocess`; where the bytes are integrator-supplied from disk, exposure depends on the integrator. The cost asymmetry is real whenever the function is called on untrusted input, hence Medium rather than High.

### Recommendation
Cap `t`/`n` at deserialization time to a sane protocol maximum (e.g., the 255 participants implicit in the tributary transaction formats, or a configurable bound well below u16::MAX) before allocating or interpolating. Alternatively, reject `Interpolation::Lagrange` for large `t` or require callers to pass a `ThresholdParams` budget into `read`, as `EncryptionKeyMessage::read` already does for PedPoP messages.

### Proof of Concept
Conceptual:
1. Craft a serialized `ThresholdKeys` for a cheap curve (e.g., Ristretto): `C::ID` length+bytes, `t = n = 0xFFFF`, `i = 1`, interpolation byte `1` (Lagrange), a valid scalar share, and `n` valid non-identity point encodings (~2.1 MB total).
2. Feed it to `ThresholdKeys::read`.
3. `ThresholdParams::new(0xFFFF, 0xFFFF, 1)` succeeds; `ThresholdKeys::new` computes Lagrange coefficients over `1..=65535` → ~4·10⁹ field multiplications, pinning the thread.

Supporting code: `crypto/dkg/src/lib.rs` `ThresholdKeys::read` (lines 574–632) — unbounded `u16` `t`/`n`, loop reading `n` points, then `ThresholdKeys::new` performing Lagrange interpolation over `1..=t`.
