### Title
Unbounded ECDSA signature recovery before signature-count validation enables CPU-exhaustion DoS via crafted multi-signature transactions - (File: blockchain/types/tx_signatures.go)

### Summary
The `TxSignatures.RecoverPubkey` function performs a full ECDSA public-key recovery (`crypto.Ecrecover`) for every entry in a transaction's `TxSignatures` list before any bound on the number of signatures is enforced. Since `TxSignatures` is a plain RLP-decoded slice, an attacker can submit a single transaction carrying an arbitrarily large number of `(v, r, s)` signature tuples (limited only by the overall transaction byte-size cap), forcing every validating node to perform hundreds of expensive elliptic-curve recovery operations before the transaction is ultimately rejected for having too many signatures relative to the target account's key set. This mirrors the Dovecot RFC 2231 issue: an attacker-controlled, unbounded-count field is fully processed (expensive parsing/crypto work) prior to any cheap cardinality check, causing disproportionate CPU consumption from a single message/transaction.

### Finding Description
`TxSignatures.RecoverPubkey` iterates over the entire signature slice and calls `s.RecoverPubkey` (which performs `crypto.Ecrecover`) for each element, with no upper bound check on `len(t)`: [1](#0-0) 

This function is reached from `TxPool.validateTx` via `tx.ValidateSender` → `SenderPubkey`: [2](#0-1) [3](#0-2) 

Only *after* all signatures have already been recovered (i.e., after the CPU-expensive work is done) is the number-of-signatures-vs-number-of-registered-keys check performed, inside `AccountKeyWeightedMultiSig.Validate`: [4](#0-3) 

Critically, this check compares the recovered signature count against `len(a.Keys)` — the *target account's own registered key count* (bounded to `MaxNumKeysForMultiSig = 10`): [5](#0-4) 

but this bound applies to the account's key list, not to the attacker-supplied `TxSignatures` slice size itself, which can be crafted independently of the target account's key type (even a simple `AccountKeyPublic` account can be targeted with a large forged/garbage signature list). The only structural limit on the number of signature entries is the overall transaction byte-size cap enforced earlier in `validateTx`: [6](#0-5) 

Because each RLP-encoded `(v, r, s)` tuple is small (tens of bytes), a transaction can be packed with hundreds of forged signature entries. Each remote/pooled transaction gets its `Ecrecover` cost paid by every node that validates it (mempool admission, block validation), independent of whether the signatures are ultimately deemed sufficient.

### Impact Explanation
An unprivileged sender can submit (via public RPC `eth_sendRawTransaction`/`kaia_sendRawTransaction` or p2p tx gossip) a single crafted Kaia-typed transaction containing a large `TxSignatures` array targeting any account (their own or arbitrary addresses). Every node that receives this transaction — during tx-pool admission and again during block execution/validation — performs hundreds of secp256k1 recovery operations before rejecting the transaction. Repeated or batched submission of such transactions (well within the byte-size limit) can consume disproportionate CPU across all full nodes, degrading transaction-pool throughput and block-production/validation latency network-wide. This matches the CVE's bug class: an attacker-controlled cardinality field is fully processed by expensive per-item computation before a cheap sanity/limit check rejects the input.

### Likelihood Explanation
Likelihood is high in terms of reachability — no special privileges, staking, or governance access is required; only the ability to submit a raw transaction is needed, and the transaction does not need to be economically valid (it is rejected only after the expensive recovery loop completes) as long as it passes size/format decoding. The attack is cheap to construct (arbitrary/garbage EC signature bytes are sufficient input to `Ecrecover`, which will simply return either an error or an incorrect pubkey; both are irrelevant to the CPU cost already incurred).

### Recommendation
Enforce an explicit upper bound on `len(TxSignatures)` (e.g., `accountkey.MaxNumKeysForMultiSig`) immediately after RLP-decoding a transaction and before calling `RecoverPubkey`/`SenderPubkey`, both in `TxPool.validateTx` and in block-level transaction validation, so that no elliptic-curve recovery work is performed for transactions that could never validate against any legally-installable account key. Additionally, consider validating signature count against the actual target account's key type/length before invoking `RecoverPubkey`, rather than after.

### Proof of Concept
Conceptual PoC (structural, not executed):
1. Construct a Kaia-typed transaction (e.g., `TxTypeValueTransfer`) targeting any funded or unfunded account.
2. Populate its `TxSignatures` field with several hundred `(v, r, s)` tuples of arbitrary/garbage bytes (valid RLP-encodable big.Int values), keeping total encoded size under `MaxTxDataSize`.
3. Submit via `eth_sendRawTransaction`/p2p.
4. Node calls `TxPool.validateTx` → `tx.ValidateSender` → `SenderPubkey` → `TxSignatures.RecoverPubkey`, which performs `crypto.Ecrecover` once per signature entry (hundreds of times) before the eventual `ErrInvalidAccountKey`/`kerrors.ErrMaxKeysExceed*` rejection is returned.
5. Repeating this with many such transactions (from different or gapped nonces to bypass per-account limits, or via p2p gossip broadcast before admission) multiplies the CPU cost across all validating nodes.

Note: The exact numeric value of `MaxTxDataSize` (which bounds the maximum achievable signature count per transaction) was referenced in `blockchain/tx_pool.go` but its declaration was not located within the scope of this review; confirming the precise achievable signature count per transaction would require locating that constant.

func (t TxSignatures) RecoverPubkey(txhash common.Hash, homestead bool, vfunc func(*big.Int) *big.Int) ([]*ecdsa.PublicKey, error) {
	var err error

	pubkeys := make([]*ecdsa.PublicKey, len(t))
	for i, s := range t {
		pubkeys[i], err = s.RecoverPubkey(txhash, homestead, vfunc)
		if err != nil {
			return nil, err
		}
	}

	return pubkeys, nil
}

func (tx *Transaction) ValidateSender(signer Signer, p AccountKeyPicker, currentBlockNumber uint64) (uint64, error) {
	if tx.IsEthereumTransaction() {
		addr, err := Sender(signer, tx)
		// Legacy transaction cannot be executed unless the account has a legacy key.
		if p.GetKey(addr).Type().IsLegacyAccountKey() == false {
			return 0, kerrors.ErrLegacyTransactionMustBeWithLegacyKey
		}
		tx.mu.Lock()
		if tx.validatedSender == (common.Address{}) {
			tx.validatedSender = addr
			tx.validatedFeePayer = addr
		}
		tx.mu.Unlock()
		return 0, err
	}

	pubkey, err := SenderPubkey(signer, tx)
	if err != nil {
		return 0, err
	}
	txfrom, ok := tx.data.(TxInternalDataFrom)
	if !ok {
		return 0, errNotTxInternalDataFrom
	}
	from := txfrom.GetFrom()
	accKey := p.GetKey(from)

	gasKey, err := accKey.SigValidationGas(currentBlockNumber, GetRoleTypeForValidation(tx.Type()), len(pubkey))
	if err != nil {
		return 0, err
	}
