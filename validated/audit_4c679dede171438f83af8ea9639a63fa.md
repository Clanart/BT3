### Title
Unprivileged sender can disable gasless swap service for all users by cheaply flooding the global bundle-tx queue - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The reported DutchTrade issue lets an attacker cheaply manufacture a "violation" condition (a high sell price vs. best price, with no minimum trade size) that trips a defensive mechanism and disables normal trading for everyone else, at near-zero cost to the attacker. The closest reachable analog in this codebase is the `kaiax/gasless` module's global bundle-transaction admission counter, which any unprivileged transaction sender can inflate cheaply to trip `ErrBundleTxQueueFull` and deny the gasless-swap feature to legitimate users.

### Finding Description
`GaslessModule.PreAddTx` admits any transaction recognized as a gasless module tx (`IsApproveTx`/`IsSwapTx`) into a single, pool-wide queue counter (`g.knownTxs`), independent of sender: [1](#0-0) 

The limit `MaxBundleTxsInQueue` (default 200) is a global, not per-account, limit: [2](#0-1) 

The only balance-related gate for a `GaslessApproveTx` before admission is that the specified ERC-20 token balance of the sender is non-zero — no real economic value or KAIA balance is required, and the sender-code / KAIA-balance checks for the swap itself do not apply to a bare approve tx: [3](#0-2) 

Sender balance checking (for KAIA) is explicitly documented as omitted for gasless transactions, since the entire point of the feature is that the sender need not hold any KAIA: [4](#0-3) 

Because the module accepts and counts any qualifying approve/swap tx pair from any EOA into the same global `numQueue()` counter regardless of eventual bundling success, an attacker can:
1. Deploy a throwaway ERC-20 token and mint themselves a trivial (e.g. 1 wei) balance.
2. Generate many EOAs (or reuse nonces of a funded EOA is not even required — approve tx needs a sender address, not necessarily funded KAIA since balance check is skipped) and submit `GaslessApproveTx` transactions referencing that token.
3. Each accepted tx increments the shared queue counter; once `numQueue() >= MaxBundleTxsInQueue`, `PreAddTx` returns `ErrBundleTxQueueFull` for every subsequent gasless tx, including legitimate users' real approve/swap transactions.

This mirrors the report's bug class exactly: a cheap, unprivileged action (near-zero cost, no minimum "trade" size enforced on the queue counter) manufactures a defensive-limit "violation" that disables the intended service (gasless swaps / trading) for everyone else.

### Impact Explanation
If exploitable as described, this results in denial of service against the gasless swap feature (KIP-247) for all legitimate users on affected nodes: real `GaslessApproveTx`/`GaslessSwapTx` pairs are rejected at the tx-pool admission layer (`ErrBundleTxQueueFull`), effectively "disabling trading" (gasless swap execution) system-wide, without the attacker needing any KAIA balance and at negligible cost (attacker-minted token, trivial gas for pool admission of the approve tx). This qualifies as Medium severity: an availability/service-disruption bug reachable from a single unprivileged transaction sender, matching the analog's "disable trading via cheap fake violation" bug class.

### Likelihood Explanation
Likelihood is limited by residual uncertainty in the exact admission pipeline: I was not able to fully confirm (due to the tool budget running out) the precise ordering between `PreAddTx`, `GetCheckBalance`, and the standard `TxPool.validateTx`/`AddRemotes` path (e.g., whether other pool-level checks such as nonce sequencing, EOA gas requirements, or rate limiting from `blockchain/spam_throttler.go` would throttle repeated failing/no-value transactions before they reach `PreAddTx`, and whether the queue entries are pruned quickly enough via `QueueTimeout` to make sustained flooding impractical). This should be validated with a live/staged reproduction before treating it as confirmed exploitable.

### Recommendation
- Make `MaxBundleTxsInQueue`/`MaxBundleTxsInPending` per-sender (or per-sender-and-token) rather than a single global counter, so no single actor (or Sybil set of actors) can exhaust the shared budget with worthless transactions.
- Require a minimum economically meaningful token balance/allowance (not just non-zero) before admitting a `GaslessApproveTx` into the bundle queue, to raise the cost of manufacturing queue entries.
- Consider incorporating existing spam-defense primitives (e.g., the `blockchain/spam_throttler.go` mechanism, cf. [5](#0-4) ) specifically for gasless-module traffic, so repeated low-value/failing gasless tx submissions from an address are throttled independently of the shared queue limit.

### Proof of Concept
1. Attacker deploys a minimal ERC-20 `EvilToken` and mints themselves `1` unit.
2. Attacker repeatedly submits `GaslessApproveTx(token=EvilToken, spender=<any GaslessSwapRouter>, amount=1)` from many addresses (no KAIA balance required, since KAIA balance checking is skipped for gasless txs per `kaiax/gasless/README.md`).
3. Each tx passes `checkBalanceForApprove` (balance `1 > 0`) and `IsModuleTx`, so `PreAddTx` adds it to `g.knownTxs` with `TxStatusQueue`.
4. Once `g.knownTxs.numQueue() >= GetMaxBundleTxsInQueue()` (default 200), `PreAddTx` returns `ErrBundleTxQueueFull` for all subsequent gasless approve/swap transactions network-wide (see [6](#0-5) ), blocking legitimate users' gasless swaps until the attacker's flood ages out (`QueueTimeout` = 10s, but can be continuously refreshed by resubmitting).

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

func (g *GaslessModule) checkBalanceForApprove(approveArgs *ApproveArgs) error {
	token := approveArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	if g.GaslessConfig.ShouldCheckSenderCode() {
		if g.getCurrentHasCode(approveArgs.Sender) {
			return errors.New("sender with code is not allowed")
		}
	}

	if g.GaslessConfig.ShouldCheckToken() {
		tokenContract, err := sc_erc20.NewERC20(token, bc)
		if err != nil {
			return err
		}

		// tx.token.balanceOf(sender) > 0
		tokenBalance, err := tokenContract.BalanceOf(nil, approveArgs.Sender)
		if err != nil {
			return err
		}
		if tokenBalance.Sign() <= 0 {
			return fmt.Errorf("insufficient sender token balance: token=%s, have=%s, want=nonzero", token.Hex(), tokenBalance.String())
		}
	}
	return nil
}
