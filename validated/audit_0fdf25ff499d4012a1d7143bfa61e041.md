## Analysis

The original report's core issue is a broken security invariant caused by a subtle, easy-to-miss implementation detail (a stray space / wrong type) that silently defeats a boundary check meant to guarantee data integrity. The closest real analog in GitHub Desktop is the boundary check used to keep the `filepath` parameter of an `x-github-client://openRepo/...` deep link confined to the cloned repository.

### Title
Path-containment check in `resolveWithin` uses unbounded string prefix match, allowing deep-link `filepath` to escape the cloned repository - (File: app/src/lib/path.ts)

### Summary
`resolveWithin` (and its Windows/POSIX variants) is the guard that is supposed to guarantee that a path resolved from an attacker-controlled `filepath` deep-link parameter stays inside the intended repository root. The final containment check is a plain string `startsWith` comparison with no path-separator boundary, so any sibling directory whose name happens to start with the root directory's name is treated as "inside" the root.

### Finding Description
`app/src/lib/parse-app-url.ts` parses `x-github-client://openRepo/...&filepath=...` deep links into an `IOpenRepositoryFromURLAction` with an attacker-controlled `filepath` field [1](#0-0) . `Dispatcher.openRepositoryFromUrl` consumes this action, rejects absolute paths, and then relies on `resolveWithin(repository.path, filepath)` to confine the result to the repository, calling `shell.showItemInFolder(resolved)` on success [2](#0-1) .

The containment logic lives in `_resolveWithin`:
```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
``` [3](#0-2) 

`path.resolve` fully normalizes `..` traversal segments *before* the `realpath`/`startsWith` check runs, so a `filepath` value like `../sibling-repo-notes/secret.txt` resolves syntactically to a path outside the intended root. The final check that is supposed to reject this only tests `realResolved.startsWith(realRoot)` — a raw string prefix comparison with no trailing path separator. If the victim happens to have any other local directory next to the cloned repo whose name begins with the repository's own directory name (e.g. cloning `desktop` while `desktop-notes`, `desktop-old`, or `desktop-fork` also exists in the same parent folder — a common pattern for developers who keep forks/backups next to a project), the sibling's real path will satisfy `startsWith(realRoot)` even though it is not actually nested under the root. The guard is broken exactly the way the original report describes: a small, overlooked formatting detail (missing separator boundary, analogous to the missing/added whitespace and type mismatch in the typehash) silently defeats the intended invariant.

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openRepo/<attacker-repo>?filepath=../<sibling-dir-name>/<file>` link can cause Desktop to reveal/open a file located outside the cloned repository via `shell.showItemInFolder`. Depending on what sibling directories the victim already has on disk (other cloned repos, backup folders, notes folders sharing a name prefix), this can expose file paths/contents outside the repo sandbox that "Open in Desktop" is supposed to be confined to — matching the report's class of "silent corruption/bypass of an intended boundary via a link the user clicks."

### Likelihood Explanation
Exploitation requires: (1) the victim clicking an attacker-supplied deep link (a normal, expected Desktop interaction, not "unnatural" steps), and (2) the existence of a sibling directory whose name is a prefix-extension of the cloned repo's directory name. Condition (2) is plausible in real developer environments (forks, `-old`, `-backup`, `-v2` folders) but not guaranteed, so likelihood is moderate rather than certain — it depends on the victim's local directory layout, which the attacker cannot directly observe or control.

### Recommendation
Fix the containment check in `_resolveWithin` to require a path-separator boundary, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This closes the sibling-directory prefix bypass while preserving the existing symlink/`realpath` protections.

### Proof of Concept
1. Victim has `~/GitHub/desktop` (a Desktop-managed clone) and, separately, `~/GitHub/desktop-notes/secret.txt` on disk.
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/desktop/desktop?filepath=../desktop-notes/secret.txt`.
3. `parseAppURL` accepts it (`isAbsolute` check passes since the value is relative) [4](#0-3) .
4. `openRepositoryFromUrl` calls `resolveWithin('~/GitHub/desktop', '../desktop-notes/secret.txt')`; `path.resolve` yields `~/GitHub/desktop-notes/secret.txt`; `realResolved.startsWith(realRoot)` (`realRoot` = `~/GitHub/desktop`) evaluates to `true` because of the missing separator boundary [5](#0-4) .
5. `shell.showItemInFolder(resolved)` reveals `secret.txt`, a file outside the cloned repository [6](#0-5) .
