### Title
DID Metadata Decoding Crash Causes Persistent Wallet Sync/Startup Denial of Service - (File: chia/wallet/did_wallet/did_wallet_puzzles.py)

### Summary
`did_program_to_metadata()` blindly UTF‑8-decodes attacker-controlled bytes taken from a DID coin's curried metadata parameter, with no validation or exception handling, mirroring the MISP bug class where unvalidated data is persisted/consumed without decode-failure handling.

### Finding Description
When a wallet observes (or is transferred) a DID coin, `DIDWallet.create_new_did_wallet_from_coin_spend` uncurries the coin's inner puzzle to obtain the `metadata` `Program`, then calls: [1](#0-0) 

`did_program_to_metadata` performs no try/except around the UTF‑8 decode of attacker-supplied curried atoms: [2](#0-1) 

Because the DID inner puzzle's `metadata` parameter is a plain curried argument chosen entirely by whoever creates/spends the DID coin (the sender), an attacker can curry a byte string that is not valid UTF‑8 (e.g. `b"\xff"`), causing `str(val, "utf-8")` to raise `UnicodeDecodeError`. This is reachable in two unguarded call sites:
1. First-time DID discovery — `create_new_did_wallet_from_coin_spend` (`did_wallet.py:238`).
2. Subsequent DID recovery/update handling in `WalletStateManager.find_lost_did`, which reconstructs `DIDInfo` on every later spend of the same DID coin: [3](#0-2) 

If the exception is raised while `WalletStateManager` is processing incoming coin states during sync (which happens under a broad sync/state-change pathway with no surrounding try/except at this specific call), it aborts wallet coin-state processing, similar in spirit to the MISP report where `afterFind()` decoding failures broke listing for all subsequent callers. Even if the very first occurrence is caught somewhere upstream, the *malformed metadata itself* is never re-validated once accepted as a "known" DID, so every subsequent resync, `find_lost_did` call, or reprocessing of that coin's spend hits the same unguarded decode and fails identically — a persistent, self-reinforcing failure tied to that DID launcher id in the victim's wallet DB (analogous to the MISP scenario where the malformed template row breaks the listing endpoint on every future read).

### Impact Explanation
Any unprivileged party can construct and push a DID-related spend (e.g., transferring a DID to a target puzzle hash they control the visibility of, or crafting a new DID launch that becomes "interesting" to the victim wallet via a hint) whose inner puzzle carries non-UTF‑8 metadata bytes. Once the victim wallet syncs and encounters that coin, `did_program_to_metadata` throws an uncaught `UnicodeDecodeError`, disrupting DID-related coin-state processing (`determine_coin_type` / `find_lost_did`) for that wallet. Because the offending coin/DID becomes part of the wallet's persistent state, this failure recurs on every future sync, restart, or DID-recovery attempt referencing that coin — a repeatable, spend-triggered denial of service against a specific victim's wallet DID handling, consistent with the "spend-triggered transaction-processing halt" acceptance criteria.

### Likelihood Explanation
Likelihood is straightforward: no special privileges, keys, or peer position are required — only the ability to submit a normal spend bundle creating/transferring a DID coin with attacker-chosen curried metadata bytes to a puzzle hash the victim's wallet will observe. This is comparable in ease-of-exploitation to the MISP CVE's "authenticated user creates a template" — here the analog is "any spend-bundle submitter creates a DID coin."

### Recommendation
Wrap the UTF‑8 decoding in `did_program_to_metadata` (and any downstream `json.dumps`/`json.loads` round-trip of `DIDInfo.metadata`) in exception handling that falls back to a safe default (e.g., empty metadata dict) and logs the error, rather than propagating the exception into wallet sync/state-processing code paths. Apply the same defensive decoding wherever curried, attacker-supplied `Program` data is converted to Python strings/JSON in wallet coin-identification code (DID, NFT metadata, VC, CR-CAT, etc.).

### Proof of Concept
1. Attacker creates a DID coin (or spends an existing DID they control) with an inner puzzle curried with a metadata k/v program whose value atom is `b"\xff"` (invalid UTF‑8), targeting the victim wallet's tracked puzzle hash / hint so the victim's wallet will process this coin.
2. Victim's `WalletNode` receives the coin state and calls `WalletStateManager.determine_coin_type` → DID identification path → `DIDWallet.create_new_did_wallet_from_coin_spend` (or, for an already-tracked DID, `find_lost_did`'s inner-puzzle-change branch).
3. `did_program_to_metadata(metadata)` executes `str(val, "utf-8")` on the attacker-chosen bytes, raising `UnicodeDecodeError`.
4. Because no try/except wraps this call at either call site, the exception propagates out of DID coin-state handling; the failure recurs on every subsequent resync or recovery operation touching this DID/coin, since the malformed value is never sanitized or replaced with a fallback. def did_program_to_metadata(program: Program) -> dict[str, str]:
    """
    Convert a program to a metadata dict
    :param program: Chialisp program contains the metadata
    :return: Metadata dict
    """
    metadata = {}
    for key, val in program.as_python():
        metadata[str(key, "utf-8")] = str(val, "utf-8")
    return metadata
