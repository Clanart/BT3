### Title
CPI signer-derivation (`translate_signers`) performs uncharged `Pubkey::create_program_address` SHA256 hashing, unlike the equivalent `SyscallCreateProgramAddress` path - (File: program-runtime/src/cpi.rs)

### Summary
`cpi_common` charges a single flat `invoke_units` fee per CPI call and then calls `translate_signers`, which internally invokes `Pubkey::create_program_address` once per signer-seed set (up to `MAX_SIGNERS`) with no per-derivation compute charge. This is inconsistent with the direct `sol_create_program_address` syscall, which explicitly charges `create_program_address_units` (1500 CU) for the exact same SHA256-based PDA derivation.

### Finding Description
In `program-runtime/src/cpi.rs`, `cpi_common` charges compute only once at the top of the function: [1](#0-0) 

It then calls `translate_signers`, which iterates over up to `MAX_SIGNERS` signer-seed groups, each with up to `MAX_SEEDS` seeds of up to `MAX_SEED_LEN` bytes, and for each group calls `Pubkey::create_program_address(&seeds_bytes, program_id)` directly with no additional compute charge: [2](#0-1) 

Contrast this with the standalone `SyscallCreateProgramAddress` builtin, which explicitly meters this exact operation before performing it: [3](#0-2) 

`Pubkey::create_program_address` computes a SHA256 hash over the concatenated seeds, the program id, and the PDA marker — the same non-trivial cryptographic work priced at `create_program_address_units` (1500 CU) when invoked as a standalone syscall. When invoked from `translate_signers` during CPI setup, this identical hashing work is performed for every signer in `signers_seeds_len` (bounded by `MAX_SIGNERS`) with zero marginal compute charge — the caller only pays the flat, per-call `invoke_units` fee regardless of how many signer derivations are performed.

### Impact Explanation
An attacker-controlled program can call `invoke_signed`/`invoke_signed_unchecked` with `signers_seeds_len` at `MAX_SIGNERS`, each entry populated with `MAX_SEEDS` seeds of `MAX_SEED_LEN` bytes. This forces up to `MAX_SIGNERS` SHA256-based `create_program_address` derivations per CPI call, all folded into the single flat `invoke_units` charge, whereas performing the equivalent work via direct `sol_create_program_address` syscalls would cost `MAX_SIGNERS * create_program_address_units` (up to 16 × 1500 = 24,000 CU). This is a real compute-cost underpricing: real CPU cost of PDA verification during CPI setup is not reflected in the compute units charged, allowing an attacker to consume disproportionate validator CPU per unit of billed compute (matches the "materially underpriced compute" bounty category referenced in the question).

### Likelihood Explanation
This is trivially and repeatably reachable by any unprivileged attacker: deploy a program that calls `invoke_signed` with the maximum allowed `signers_seeds_len`/`MAX_SEEDS`/`MAX_SEED_LEN` combination on every CPI call, and repeat CPI calls up to `max_instruction_trace_length`/stack depth limits within a single transaction, and across many transactions. No special privileges, precompiles, or validator control are required — only crafted instruction data supplied to one's own deployed program.

### Recommendation
Charge `create_program_address_units` (or an equivalent per-derivation cost) for each signer-seed group processed inside `translate_signers`/`cpi_common`, mirroring the charge already applied in `SyscallCreateProgramAddress`/`SyscallTryFindProgramAddress`, so that CPI-embedded PDA verification cost scales with `signers_seeds_len` instead of being absorbed into the flat `invoke_units` fee.
