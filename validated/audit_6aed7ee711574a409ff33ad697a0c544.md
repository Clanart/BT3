## Analysis

I found a genuine analog of the nodemailer bug class (unbounded, input-driven recursion during header/structure parsing leading to DoS) in the Kaia `AccountKey` RLP decoding path.

`AccountKeyRoleBased.DecodeRLP` decodes a `[][]byte` of member-key blobs and, for each blob, calls `rlp.DecodeBytes(b, &serializer)` where `serializer` is an `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads a `keyType` byte, instantiates the corresponding `AccountKey` via `NewAccountKey`, and then calls `s.Decode(serializer.key)`: [2](#0-1) 

`NewAccountKey` allows `AccountKeyTypeRoleBased` to be instantiated again as a fresh `AccountKeyRoleBased`: [3](#0-2) 

Since `AccountKeyRoleBased` implements `rlp.Decoder`, decoding a member key whose type is again `RoleBased` re-enters `AccountKeyRoleBased.DecodeRLP`, which repeats the same recursive-decode-per-member pattern. **No depth limit is enforced anywhere in this chain.** The only defense against nested `RoleBased` keys is a post-decode semantic check (`ErrNestedCompositeType`), exercised in `tests/account_keytype_test.go` via `txpool.AddRemote(tx)` — i.e., the check happens *after* the transaction (and its account key) has already been fully RLP-decoded. This mirrors exactly the nodemailer flaw: a "nested composite structure is invalid" rule is enforced by application logic *after* the parser has already recursed arbitrarily deep to build the structure, rather than the parser limiting depth up front.

This `AccountKey` field is embedded directly in the RLP encoding of `TxTypeAccountCreation` / `TxTypeAccountUpdate` transactions (see `TxInternalDataAccountCreation.fromSerializable` calling `rlp.DecodeBytes(serialized.KeyData, serializer)`): [4](#0-3) 

Such a transaction is reachable directly by any unauthenticated/unprivileged sender via the public RPC entry points `SendRawTransaction` and `SendRawTransactions`, which just RLP-decode attacker-supplied bytes into a `types.Transaction` and hand it to the pool/backend: [5](#0-4) 

An attacker can therefore construct an account-update/account-creation transaction whose `Key` field is an `AccountKeyRoleBased` containing (recursively) another `AccountKeyRoleBased`, nested to an arbitrary depth (e.g. thousands of levels, each adding only a few bytes to the encoded blob). Submitting this via `eth_sendRawTransaction`/`kaia_sendRawTransaction` forces every node that decodes the transaction (RPC node, tx-pool propagation, and any node validating/executing the block) to recurse through `AccountKeyRoleBased.DecodeRLP → AccountKeySerializer.DecodeRLP → rlp.Stream.Decode → AccountKeyRoleBased.DecodeRLP → ...` until the Go call stack is exhausted, crashing the process — a single-request DoS with no authentication required, exactly matching the impact class of GHSA-rcmh-qjqh-p98v.

I could not fully verify (due to the ask-only/index constraints) whether there is any other RLP-level guard (e.g., a global stream depth counter in `rlp.Stream`) that would stop this before native Go stack exhaustion; from what was retrieved, `rlp/decode.go`'s `Stream` struct tracks only a byte-length limit (`remaining`) and a `stack []uint64` of list sizes, not a recursion-depth cap, and no depth check appears in `accountkey/account_key_role_based.go` or `account_key_serializer.go`.

### Title
Unbounded recursive AccountKeyRoleBased RLP decoding allows single-transaction stack-overflow DoS - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively RLP-decodes each member key via `AccountKeySerializer`, which can itself be another `AccountKeyRoleBased`. No recursion-depth limit exists, so a crafted, deeply nested `AccountKey` field inside an `AccountUpdate`/`AccountCreation` transaction causes unbounded recursive decoding.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` (`blockchain/types/accountkey/account_key_role_based.go:120-138`) decodes the RLP payload into `[][]byte`, then for every element calls `rlp.DecodeBytes(b, &serializer)` with a fresh `AccountKeySerializer`. `AccountKeySerializer.DecodeRLP` (`account_key_serializer.go:61-73`) reads a `keyType`, constructs the concrete key type via `NewAccountKey` (`account_key.go:97-114`, which permits `AccountKeyTypeRoleBased`), and calls `s.Decode(serializer.key)`. Because `AccountKeyRoleBased` implements the `rlp.Decoder` interface, decoding a nested `RoleBased` member key re-enters `AccountKeyRoleBased.DecodeRLP`, repeating the same pattern with no depth tracking. The only protection against nested `RoleBased` keys (`ErrNestedCompositeType`) is applied by the tx pool/state-transition logic *after* decoding completes (see `tests/account_keytype_test.go` `TestAccountUpdateRoleBasedKeyNested`), which is too late to prevent the recursive decode itself from exhausting the stack.

This is structurally identical to the nodemailer `addressparser` flaw: a "flatten/reject nested structure" rule is implemented as a post-hoc check while the underlying parser recurses without a depth guard for every level of attacker-controlled nesting.

### Impact Explanation
Any of the RPC entry points that RLP-decode raw transactions (`SendRawTransaction`, `SendRawTransactions` in `api/api_kaia_transaction.go`) will trigger this recursive decode as soon as the raw bytes are parsed into a `types.Transaction`, before any semantic/pool validation runs. A sufficiently deep nesting drives the decoding goroutine to a stack overflow, which in Go is a fatal, unrecoverable runtime error that crashes the entire node process — not just the goroutine. This is a full node crash triggered by a single unauthenticated RPC call, i.e., high-severity availability impact matching CWE-703/DoS class of the reference advisory.

### Likelihood Explanation
Likelihood is high: constructing the payload requires no special privileges, no valid signature is even needed to reach the vulnerable decode path (decoding occurs before signature validation), and the RLP encoding cost per nesting level is small (a handful of bytes), so deep nesting sufficient to overflow the stack can be built cheaply and submitted as one `sendRawTransaction` call.

### Recommendation
Add an explicit recursion/nesting depth counter (e.g., pass a depth argument through `AccountKeySerializer.DecodeRLP`/`AccountKeyRoleBased.DecodeRLP`, or track depth in `rlp.Stream`) and reject decoding once a small maximum depth (e.g., 1, since nested `RoleBased` keys are never valid) is exceeded — enforcing the "no nested composite type" rule during decode rather than only after decode completes. Alternatively, disallow `AccountKeyTypeRoleBased` as a valid member type inside `AccountKeyRoleBased.DecodeRLP`/`NewAccountKey` context immediately, so recursion depth is capped at 2 unconditionally.

### Proof of Concept
Conceptually: build a nested `AccountKeyRoleBased` structure like
```
RoleBased([ RoleBased([ RoleBased([ ... RoleBased([Legacy]) ... ]) ]) ])
```
nested to depth N (e.g., N = 50,000), RLP-encode it as the `Key` field of a `TxTypeAccountUpdate` (or `TxTypeAccountCreation`) transaction, sign or leave unsigned (decode happens before signature check), and submit via `kaia_sendRawTransaction`/`eth_sendRawTransaction`. The receiving node's decode of `AccountKeyRoleBased`/`AccountKeySerializer` recurses N times, exhausting the goroutine stack and crashing the process — analogous to the `buildDeepGroup(DEPTH)` PoC in the nodemailer advisory.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

	}

// SendRawTransactions will add multiple signed transactions to the transaction pool.
func (s *KaiaTransactionAPI) SendRawTransactions(ctx context.Context, inputs []hexutil.Bytes) ([]common.Hash, error) {
	hash := []common.Hash{}
	errs := []error{}

	if len(inputs) == 0 {
		hash = append(hash, common.Hash{})
		return hash, errors.New("Empty input")
	}

	for i, input := range inputs {
		if len(input) == 0 {
			hash = append(hash, common.Hash{})
			errs = append(errs, fmt.Errorf("Index %d: empty input", i))
			break
		}
		// Allow naked Ethereum tx types
		if 0 < input[0] && input[0] < 0x7f {
			input = append([]byte{byte(types.EthereumTxTypeEnvelope)}, input...)
		}
		tx := new(types.Transaction)
		if err := rlp.DecodeBytes(input, tx); err != nil {
			hash = append(hash, common.Hash{})
			errs = append(errs, fmt.Errorf("Index %d: %w", i, err))
			break
		}
		if err := s.b.SendTx(ctx, tx); err != nil {
			hash = append(hash, common.Hash{})
			errs = append(errs, fmt.Errorf("Index %d: %w", i, err))
			break
		}
		hash = append(hash, tx.Hash())
	}

	return hash, errors.Join(errs...)
}
