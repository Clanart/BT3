Confirmed: `placeOrder` (public, unprivileged, `evm/tron/contracts/apps/IntentGatewayV2.sol:332`) lets any caller set `order.inputs[i].token` to an arbitrary address, which later becomes the token entered into escrow accounting `_orders[commitment][token]` and eventually paid out via `withdraw()`.

### Title
Unchecked ERC20 `transfer` return-data in escrow payout allows false settlement / permanent fund loss - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2` pays out escrowed order funds and sweeps protocol dust using a raw low-level `.call()` to the ERC20 `transfer` selector, and only checks that the *call itself* did not revert (`success`). It never decodes/validates the ERC20 boolean return value. A non-reverting ERC20 token that returns `false` on failure will make `withdraw()` and the `SweepDust` handler believe the transfer succeeded, permanently mark the order as settled/refunded, and decrement escrow accounting — while the beneficiary receives nothing and the tokens remain permanently stuck in the contract with no path to recovery.

### Finding Description
`placeOrder` is a fully public, unprivileged entrypoint that lets any user choose an arbitrary token address for `order.inputs[i].token`: [1](#0-0) 

That token is later escrowed under `_orders[commitment][token]` and, on settlement, released via `withdraw()`: [2](#0-1) 

Note that the contract even declares `using SafeERC20 for IERC20;` at the top of the file: [3](#0-2) 

Yet the actual payout path bypasses `safeTransfer` entirely and instead does a raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`, checking only whether the low-level call reverted, not the ABI-decoded boolean return value. The same unsafe pattern also appears in the `SweepDust` handler inside `onAccept`: [4](#0-3) 

and in the `RedeemEscrow` fee-forwarding branch of `withdraw()`: [5](#0-4) 

Per ERC20 (and EIP-20 explicitly), `transfer`/`transferFrom` MAY return `false` instead of reverting on failure, and callers "MUST handle false … MUST NOT assume that false is never returned." A low-level `.call` to such a token succeeds (no revert) even though the encoded return data is `false`. Because `success` here reflects only "the call did not revert," not "the transfer actually moved value," the code proceeds to:
1. Decrement `_orders[body.commitment][token] -= amount;` (escrow accounting says the funds are gone/paid).
2. Set `_filled[body.commitment] = beneficiary;` (order irreversibly finalized).
3. Emit `EscrowReleased`/`EscrowRefunded` as if the transfer succeeded.

This exactly mirrors the external report's core broken invariant — “the contract's security depends on an unenforced assumption that `transferFrom`/`transfer` reverts on failure” — but the local analog manifests in the escrow-settlement path of a live cross-chain intent-fill/refund flow rather than a delegation-proxy drain. Since the "main" EVM `IntentGatewayV2`/`IntentsBase` versions correctly use `SafeERC20.safeTransfer`/`safeTransferFrom` (see e.g. `evm/src/apps/intentsv2/IntentsBase.sol:404-409` and `evm/src/apps/IntentGatewayV2.sol:290`), this is a real regression specific to the Tron contract, not an inherent protocol design choice.

### Impact Explanation
This breaks the Hyperbridge invariant that "bridged assets, order escrow, refunds… must move exactly once and only to the rightful beneficiary and amount." With a token whose `transfer` returns `false` on failure (a valid, standards-compliant behavior explicitly called out by EIP-20), the intent-gateway will:
- Mark a fill/refund/redeem as final and successful (`_filled` set, escrow zeroed, events emitted) while the beneficiary/solver/user receives nothing.
- Permanently strand the underlying token balance inside the `IntentGatewayV2` contract, since the accounting no longer reflects any escrow entry to reclaim it and `_filled` blocks any retry of the same commitment.

This is a direct fund-loss/fund-lock condition triggered purely by the choice of input token in a normal, unprivileged order flow — no malicious relayer, prover, or admin is required.

### Likelihood Explanation
Likelihood is limited to orders that use such a token as an input asset, and requires either the user or attacker to place an order denominated in a token they control (or that already exists with this behavior). Since `placeOrder`'s `order.inputs[i].token` is entirely attacker-chosen and unrestricted (no allowlist is enforced in this code path), any user/attacker can trivially deploy or select such a token and drive their own or another party's order through this payout code path, matching the "not very likely implementation, but a possible and damaging edge case" reasoning accepted as Medium severity in the source report.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;`), which decodes and enforces the boolean return value (or absence thereof) per EIP-20. Additionally, consider verifying the contract's actual token balance decreased by the expected `amount` before finalizing `_filled` and decrementing escrow, to make the invariant hold even against tokens with unusual transfer semantics.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer(address,uint256)` always executes normally (no revert) but returns `false` without moving any balance.
2. Attacker (or any user) calls `placeOrder` on `evm/tron/contracts/apps/IntentGatewayV2.sol` with `order.inputs[0].token = EvilToken`, `amount = X`, funding escrow through the normal `transferFrom`/`safeTransferFrom` deposit path (deposits use `safeTransferFrom`, so `EvilToken` must return `true` on `transferFrom` but `false` on `transfer` — trivial to implement differently per call).
3. Order is filled/cancelled through the normal cross-chain flow, producing a `RedeemEscrow`/`RefundEscrow` message that reaches `onAccept` → `withdraw()`.
4. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, abi.encode(false))` — `success` is `true` because the call itself didn't revert.
5. `if (!success) revert TransferFailed();` does not trigger; `_orders[commitment][token] -= amount;` executes and `_filled[commitment] = beneficiary;` finalizes the order, emitting `EscrowReleased`/`EscrowRefunded`.
6. The beneficiary never actually receives `EvilToken`; the balance remains locked inside `IntentGatewayV2` forever, with no escrow record left to reclaim it.
