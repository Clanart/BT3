### Title
Permissionless lamport-donation griefing of `CreateAccount` via `to.get_lamports() > 0` equality-style guard - ([File: programs/system/src/system_processor.rs])

### Summary
The external report's bug class is: a mechanism checks a contract's balance against an exact/expected value (`balanceOfSelf() != amount`), and because the balance is a globally-writable value that any unprivileged party can mutate (donate to), an attacker can force that check to fail and DOS the legitimate flow. The same broken-invariant pattern exists in Agave's System Program `create_account` instruction handler, which rejects account creation whenever the target account already holds a nonzero lamport balance, and that balance can be inflated by anyone via an ordinary `Transfer` before the legitimate `CreateAccount` transaction lands.

### Finding Description
In `create_account()` [1](#0-0) , before allocating space/assigning the owner and transferring the creation lamports, the code does:

```rust
if to.get_lamports() > 0 {
    ic_msg!(invoke_context, "Create Account: account {:?} already in use", to_address);
    return Err(SystemError::AccountAlreadyInUse.into());
}
``` [2](#0-1) 

This is a balance-state guard analogous to the BunniHook's `balanceOfSelf() != args.amount` check: it treats the account's current lamport balance as a proxy for "is this account already initialized/in use." However, lamports can be added to *any* pubkey — including a not-yet-created account or PDA — by anyone, without any signature from the account itself, via the ordinary `system_instruction::transfer` handled in the same file's `transfer()`/`transfer_verified()` path [3](#0-2) . The `to` side of a `Transfer` is never required to sign; only the `from` side signs. Nothing in `create_account` distinguishes "lamports arrived because someone donated to grief creation" from "lamports arrived because the account was legitimately initialized."

Thus an unprivileged attacker who can predict or observe the target address of an upcoming `CreateAccount` instruction (e.g., a deterministic PDA/seed-derived address, or simply front-running a visible pending transaction) can send even 1 lamport to that address beforehand. The subsequent legitimate `CreateAccount` instruction will then see `to.get_lamports() > 0` and permanently fail with `SystemError::AccountAlreadyInUse`, exactly mirroring the report's root cause: an equality/threshold check against a balance value that is externally, permissionlessly mutable.

Note `create_account_allow_prefund()` exists specifically as a variant that *skips* this zero-lamports check for flows where prefunding is expected [4](#0-3) , which is itself evidence that the zero-balance requirement in ordinary `create_account` is recognized internally as being incompatible with any prefunding/donation scenario — i.e., there is no recovery path for a griefed address using the standard `CreateAccount` instruction.

### Impact Explanation
This is a low-cost, permissionless griefing/DOS vector against any protocol, program, or wallet flow that relies on `system_instruction::create_account` to initialize a specific, predictable address (most commonly PDAs or seed-derived accounts used by on-chain programs, or simple new-keypair account creation whose address was broadcast/observed ahead of confirmation). The attacker spends a trivial number of lamports (as low as 1) to permanently block legitimate account creation at that address, forcing the victim to abandon the address or take a different, non-standard code path (`create_account_allow_prefund`, if the calling program supports it) — most callers do not. This is a repeatable, cheap, single-attacker denial-of-service against account initialization, not a fund-theft primitive, but it can halt application-level flows built on top of standard `CreateAccount` semantics.

### Likelihood Explanation
Likelihood is high for any deterministic/predictable target address (PDA, seed-derived account, or any address whose value is visible in a not-yet-landed transaction in the mempool/gossip). The attack requires only a standard, permissionless `Transfer` instruction to the target address before the `CreateAccount` transaction executes — no special privileges, no validator/leader control, and no reliance on trusted components. This matches "unprivileged attacker/CPI/transaction" primitives and is broadly applicable across the ecosystem's `create_account` usage.

### Recommendation
Do not gate `create_account` purely on `lamports == 0`. Where the caller's intent is to detect "already initialized" rather than "has any lamports," check the meaningful initialization markers instead (e.g., `data.is_empty()` and `owner == system_program::id()`, as `allocate()` already does at [5](#0-4) ), and/or provide the `create_account_allow_prefund` semantics as the default/only path so that pre-existing (possibly donated) lamports are simply topped up to the required amount instead of causing a hard failure. This mirrors the external report's own recommendation: track the meaningful state delta/invariant (uninitialized owner + empty data) rather than an absolute balance value that unprivileged third parties can manipulate.

### Proof of Concept
1. Program/user derives a PDA or new keypair address `X` intended to be created via `system_instruction::create_account(from, X, lamports, space, owner)`.
2. Attacker observes `X` (from a public PDA derivation, or from the pending transaction in the mempool) and submits `system_instruction::transfer(attacker, X, 1)` before the victim's `CreateAccount` transaction is processed. No signature from `X` is required.
3. Victim's `CreateAccount` transaction executes `create_account()`; the check `to.get_lamports() > 0` at [6](#0-5)  now evaluates true, and the instruction fails with `SystemError::AccountAlreadyInUse`, permanently blocking the standard creation path for address `X` until/unless the caller uses the non-standard `create_account_allow_prefund` path.

#[allow(clippy::too_many_arguments)]
fn create_account(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    to_address: &Address,
    lamports: u64,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ic_msg!(
                invoke_context,
                "Create Account: account {:?} already in use",
                to_address
            );
            return Err(SystemError::AccountAlreadyInUse.into());
        }

        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    transfer(
        from_account_index,
        to_account_index,
        lamports,
        invoke_context,
        instruction_context,
    )
}

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
