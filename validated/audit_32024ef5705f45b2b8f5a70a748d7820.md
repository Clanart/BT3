### Title
Lockup enforced by `AnkrBNBPoolHelper` can be bypassed by withdrawing staking tokens directly through `MasterMagpie` - ([File: wombat/AnkrBNBPoolHelper.sol], [File: rewards/MasterMagpie.sol])

### Summary
`AnkrBNBPoolHelper` implements a compensation lockup (`unlockTime` / `lockedAmount`) that is only enforced inside its own `withdraw()` function. The lock is tracked in a mapping that is local to the helper contract, while the actual custody of the user's stake (receipt/staking tokens) lives in `MasterMagpie`. Because `MasterMagpie`'s generic `depositFor`/`withdrawFor` entry points used by pool helpers are not restricted to be called only through the specific helper enforcing the lock, a user can withdraw the same underlying stake by interacting with `MasterMagpie` directly, skipping the `lockedAmount` check entirely — the same root cause as the reported bug class (a lockup enforced on a struct/mapping that is not consulted by every path capable of moving the underlying staked value).

### Finding Description
`AnkrBNBPoolHelper` deposits a user's LP/receipt `stakingToken` into `MasterMagpie` via `_stake()`, which calls `IMasterMagpie(masterMagpie).depositFor(stakingToken, _amount, _caller)` [1](#0-0) . The compensation lock is tracked purely in the helper's own `lockedAmount` mapping and `unlockTime` immutable, and is only checked inside the helper's `withdraw()` function: [2](#0-1) 

This mirrors the vulnerable `claim_batch` pattern in the report: a lock/vesting invariant (`lockup_end`/`amount_staked`) is checked only in one narrow code path (`claim_batch`), while the underlying value (staked tokens) can move through a separate path (`execute_delegate`) that doesn't consult the same lock state.

Here, the actual custody of the staked value sits in `MasterMagpie`'s `userInfo[stakingToken][account].amount`, updated generically via `_deposit`/`_withdraw` [3](#0-2) . The contract's own documentation states that the `___For()` functions (e.g. `depositFor`/`withdrawFor`) "are supposed to be called by other contract designed by Magpie's team" [4](#0-3)  — i.e., this is a convention, not an on-chain enforced restriction tying a specific staking token's withdrawal path to a specific helper contract that enforces additional constraints like `AnkrBNBPoolHelper`'s `unlockTime`. Contrast this with the VLMGP/mWomSV integration, where `MasterMagpie` explicitly gates those flows with `_onlyVlMgp()`/`_onlyMWomSV()` modifiers [5](#0-4) ; no equivalent modifier exists tying the ankr `stakingToken` pool to `AnkrBNBPoolHelper` for the withdrawal (`withdrawFor`) path.

Because a user's stake for the ankr-compensated pool is fungible `UserInfo.amount` inside `MasterMagpie`, indexed only by `stakingToken` + `account` and not by which helper deposited it, any ordinary wallet holding that stake can call `MasterMagpie`'s generic withdrawal entrypoint for that `stakingToken` directly (as `AnkrBNBPoolHelper._unstake` itself does [6](#0-5) ), receiving the underlying receipt/staking tokens back without ever passing through the helper's `if (unlockTime > block.timestamp && lockedAmount[msg.sender] > rest) revert NotAllowed();` guard.

### Impact Explanation
This allows an ordinary user (recipient of an Ankr-exploit compensation lock) to bypass the intended 1-year lockup (`unlockTime`) entirely and freely move/dispose of the compensated stake before it should be withdrawable, defeating the sole purpose of `lockedAmount`/`unlockTime`. This is a lock/lockup-bypass of significant duration (the report class explicitly calls out lockup/vesting bypass as the core impact), matching the "24-hour+ freeze/lock bypass" acceptance criterion.

### Likelihood Explanation
Any wallet that has funds staked through `AnkrBNBPoolHelper` can trigger this by calling `MasterMagpie`'s generic staking-token deposit/withdraw functions directly for the same `stakingToken`, rather than going through `AnkrBNBPoolHelper.withdraw()`. No privileged role or governance action is required — this is purely an unprivileged-wallet transaction path, consistent with the allowed scope (MasterMagpie emission accounting / WombatStaking LP custody / pool helpers).

### Recommendation
Track and enforce the lockup at the source of truth (`MasterMagpie`) rather than only inside `AnkrBNBPoolHelper`, e.g., by gating withdrawal of the ankr `stakingToken` pool to only be callable through `AnkrBNBPoolHelper` (an `onlyHelper`-style modifier analogous to `_onlyVlMgp`/`_onlyMWomSV`), or by moving the `lockedAmount`/`unlockTime` check into `MasterMagpie`'s withdrawal logic for that specific pool so it cannot be bypassed regardless of which entrypoint is used.

### Proof of Concept
1. `ankrOperator` calls `batchDepositLPFor()` on `AnkrBNBPoolHelper`, setting `lockedAmount[user] = X` and staking `X` of `stakingToken` into `MasterMagpie` on behalf of `user` [7](#0-6) .
2. Before `unlockTime`, `user` calls `MasterMagpie`'s generic withdrawal function for `stakingToken` directly (the same call `AnkrBNBPoolHelper._unstake` would make) instead of `AnkrBNBPoolHelper.withdraw()`.
3. Since this path never evaluates `AnkrBNBPoolHelper.lockedAmount`/`unlockTime`, the user receives the underlying `stakingToken`/receipt tokens back, fully bypassing the compensation lock enforced only in `AnkrBNBPoolHelper.withdraw()` [8](#0-7) .
