### Title
stSTX Ratio Applied to Collateral/Debt Pricing Without Any Freshness Check - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`resolve-ststx` multiplies the freshness-checked STX price by a stSTX/STX ratio fetched from an external contract call, but that ratio carries no timestamp and is never subjected to the staleness/monotonicity check that gates every other oracle input in `price-resolve`.

### Finding Description
All base oracle price resolutions (Pyth, DIA) flow through `price-resolve`, which enforces `oracle-timestamp-fresh` (staleness ≤ `max-staleness`, and monotonic vs. `last-update-time`) before the price is accepted: [1](#0-0) 

However, the stSTX ratio callcode transformation is applied on top of the already-validated STX price via `resolve-ststx`, which simply `unwrap!`s the result of `call-ststx-ratio` — a plain `uint` with no accompanying timestamp: [2](#0-1) 

`call-ststx-ratio` itself is a direct pass-through contract-call to an external ratio oracle with zero freshness/staleness logic: [3](#0-2) 

Because the ratio has no timestamp, it cannot be checked against `max-staleness` or `last-update-time` the way Pyth/DIA prices are — the `oracle-timestamp-fresh` gate in `price-resolve` only validates the base feed's `timestamp`, not the ratio multiplier applied afterward in `resolve-callcode`/`resolve-ststx`: [4](#0-3) 

This is the same root cause pattern as the referenced wstETH finding: a derivative conversion ratio is accepted at face value without recency validation, even though the primary underlying price feed is checked.

### Impact Explanation
If `block-info-nakamoto-ststx-ratio-v2` returns a stale ratio (e.g., due to it not being updated for a period, chain congestion, or the oracle's own update cadence lagging the real stSTX/STX exchange rate), stSTX and zstSTX collateral/debt would be mis-valued relative to the true market ratio. Since stSTX/zstSTX is used directly in collateral valuation (`get-notional-evaluation`) and in liquidation health calculations, an inflated stale ratio could let a position appear healthier than it is (avoiding liquidation it should face) or a deflated stale ratio could trigger premature/incorrect liquidations — both are the frozen/lost-funds and improper-liquidation impact class stemming from a wrong price feeding into the health verdict. This lands in the temporary freezing of funds / theft-via-mispriced-liquidation impact category.

### Likelihood Explanation
Likelihood depends on how frequently `block-info-nakamoto-ststx-ratio-v2` is updated on-chain relative to the real staking ratio drift, which is external to this codebase. Since the ratio changes slowly (staking yield accrual) drift is typically small over short periods, but there is no on-chain mechanism in this repo to detect or reject a ratio that hasn't updated for an extended period, unlike every other price feed which is protected by `max-staleness`.

### Recommendation
Have the ratio-provider contract return (or have `call-ststx-ratio` additionally query) a last-updated timestamp for the ratio, and apply the same `oracle-timestamp-fresh` check (with an appropriate `max-staleness` for this feed) before using the ratio in `resolve-ststx`, consistent with how Pyth/DIA feeds are validated in `price-resolve`.

### Proof of Concept
1. `block-info-nakamoto-ststx-ratio-v2.get-ststx-ratio-v3` stops updating (or is delayed) while the real stSTX/STX exchange rate continues to drift.
2. A user calls `collateral-add`/`borrow` with stSTX or zstSTX collateral; `resolve-ststx` fetches the stale ratio via `call-ststx-ratio` with no freshness check.
3. `resolve-callcode` combines this stale ratio with the freshly-validated STX price, producing a distorted USD valuation for the stSTX/zstSTX position.
4. This distorted valuation is used in `get-notional-evaluation` for health/LTV checks, potentially allowing over-borrowing against an inflated stSTX valuation or triggering unwarranted liquidation against a deflated one — with no on-chain safeguard analogous to `oracle-timestamp-fresh` to reject it. (define-private (price-resolve
```text
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```
