### Title
Hookify rule engine tool matcher fails to alias MultiEdit with Edit/Write, allowing dangerous file edits to bypass block rules - (File: plugins/hookify/core/rule_engine.py)

### Finding Description
`RuleEngine._rule_matches` gates condition evaluation entirely on `_matches_tool`, which performs exact literal string matching against `rule.tool_matcher` split on `|` (e.g. `"Edit|Write"`), with no notion that `MultiEdit` is a functionally equivalent "edit a file's contents" operation. [1](#0-0) . Meanwhile `_extract_field` explicitly implements dedicated logic to extract `file_path`/`new_text`/`content` from `MultiEdit`'s `edits` list, showing the engine's author intended `MultiEdit` to be a first-class equivalent of `Edit`/`Write` for content-inspection purposes [2](#0-1) .

A hookify block rule written to catch dangerous file content (e.g. secrets, destructive patterns) with `tool_matcher: "Edit|Write"` will never reach `_check_condition` when the same content is written via the `MultiEdit` tool, because `_matches_tool` returns `False` before any condition is evaluated [3](#0-2) . Since `pretooluse.py`/`posttooluse.py` treat `Edit`, `Write`, and `MultiEdit` as the same `"file"` event class for rule *loading* [4](#0-3) , a rule author reasonably assumes `tool_matcher: "Edit|Write"` (or config generated/copied from examples covering "file edit tools") covers all file-editing tools, but the engine silently excludes `MultiEdit`. The same content that would be blocked via `Edit` or `Write` sails through unblocked via `MultiEdit`, because tool matching only recognizes one representation ("Edit"/"Write") of the semantically equivalent file-edit operation.

### Impact Explanation
This breaks the stated invariant that "a matching block rule must reliably deny the protected operation." An agent (or automated flow) driven to perform a dangerous file mutation that a hookify rule is meant to block can achieve the identical effect by issuing the operation via `MultiEdit` instead of `Edit`/`Write`, causing the guard to be silently bypassed. This is a logic-level service disruption / guard-bypass: the security control the user configured (and believes is enforced) does not fire, undermining hook-based protection without any error or warning to the user.

### Likelihood Explanation
This requires no special privilege beyond normal Claude Code tool use — any workflow that issues a `MultiEdit` call against a rule scoped with `tool_matcher: "Edit|Write"` (a very natural and likely rule-authoring pattern, since `MultiEdit` is easy to forget when listing "Edit"-family tools) triggers the bypass deterministically and repeatably. It requires only that a project define such a rule (this is normal configuration, not a novel attacker precondition) and that the tool invocation choose `MultiEdit` instead of `Edit`/`Write`.

### Recommendation
Normalize tool matching so functionally equivalent tools are treated as aliases: e.g., have `_matches_tool` (or `_rule_matches`) expand `Edit` in a matcher pattern to also match `MultiEdit`, or require rule authors to use semantic groups (e.g. `matcher: "file"`) resolved centrally rather than raw literal tool-name matching split by `|`. At minimum, document/log this gap, and add validation/lint on rule files warning when `tool_matcher` includes `Edit`/`Write` without `MultiEdit`.

### Proof of Concept
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-secret-write",
    enabled=True,
    event="file",
    tool_matcher="Edit|Write",
    conditions=[Condition(field="content", operator="contains", pattern="SECRET_KEY")],
    action="block",
    message="Blocked: secret content"
)

engine = RuleEngine()

# Case 1: Write tool -> correctly blocked
write_input = {
    "tool_name": "Write",
    "tool_input": {"content": "SECRET_KEY=abc123"}
}
assert engine.evaluate_rules([rule], write_input).get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# Case 2: MultiEdit tool with equivalent content -> should also be blocked but isn't
multiedit_input = {
    "tool_name": "MultiEdit",
    "tool_input": {"edits": [{"new_string": "SECRET_KEY=abc123"}]}
}
result = engine.evaluate_rules([rule], multiedit_input)
assert result == {}  # demonstrates bypass: dangerous content allowed through
```
Expected (secure) behavior: both invocations should be denied. Actual behavior: the `MultiEdit` case returns `{}` (no block), confirming the guard is bypassed via the equivalent tool representation.

    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns
