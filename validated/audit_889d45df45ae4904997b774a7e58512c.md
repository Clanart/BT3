Based on my investigation, I found a concrete structural analog in `EvmHost.sol`, though I want to flag upfront: I was not able to fully trace every downstream consumer of the whitelist/cache fields within my remaining tool budget, so I present this with that caveat.

### Title
`updateHostParams` never prunes removed state machines from the `_latestStateMachineHeight` cache - (File: `evm/src/core/EvmHost.sol`)

### Summary

### Finding Description
The external report's core broken invariant: an authoritative list (`operators`) can be mutated (add/remove) independently of a derived "cache" (`operatorCache`/`_latestStateMachineHeight`-style mapping) that downstream trust-critical logic actually consults, and removal from the list is never propagated to the cache.

`EvmHost` has the exact same asymmetry. `HostParams.stateMachines` is documented as "State machines whose state commitments are accepted" [1](#0-0) . When governance calls `updateHostParams` → `updateHostParamsInternal`, the function only **adds** new entries to `_latestStateMachineHeight` for chains present in the new `params.stateMachines` array; there is no code path that removes or resets the cache entry for a state machine that existed in the old params but is absent from the new one: [2](#0-1) 

This is confirmed by the existing test `testCanAddwhitelistedStateMachines`, which shows that after calling `updateHostParams` with a *new* `stateMachines` list, the previously-set `_latestStateMachineHeight` for a chain not included in that new list is left completely untouched ("should be unchanged") [3](#0-2) . There is no test or code exercising the removal case at all — governance has no way to actually purge a state machine's cached height/trust status via `updateHostParams`; the field is monotonic add-only, exactly like `NestedFactory.addOperator()`/`removeOperator()` not calling `rebuildCache()`.

The only place a state-machine entry can be reset is `deleteStateMachineCommitmentInternal`, which is scoped to fishermen vetoing a single specific height, restricted to the `handler`, and only resets the entry to `1` (not zero) rather than actually removing the state machine from the trusted set [4](#0-3) .

### Impact Explanation
Governance's intended action — removing a state machine from `HostParams.stateMachines` (e.g., because that chain's consensus was compromised, deprecated, or needs to be de-authorized) — does not actually revoke that chain's presence in `_latestStateMachineHeight`, nor does it clear any previously stored `_stateCommitments[id][height]` entries for heights other than the single latest one. Any code path elsewhere that treats a non-zero `_latestStateMachineHeight[id]` (or the mere presence of a stored `_stateCommitments` entry) as "this state machine is currently trusted" will continue to accept proofs/state for a chain the operators believed had been de-whitelisted. This is a false-state-acceptance class problem: the governance-facing list (`stateMachines`) and the actually-enforced trust state (`_latestStateMachineHeight` / stored commitments) diverge exactly as they did in the `NestedFactory` bug, and the divergence is a "removal doesn't sync" case that silently preserves stale trust rather than eliminating it.

### Likelihood Explanation
This requires no attacker capability beyond normal usage of an already-deprecated/removed state machine's previously-valid commitment data — no malicious relayer, prover, or admin action is needed to trigger the divergence; it's a direct, deterministic consequence of calling `updateHostParams` with a shorter `stateMachines` list, which is a legitimate, expected governance operation (e.g., during a deprecation). The bug is 100% reproducible any time governance tries to remove a state machine.

### Recommendation
In `updateHostParamsInternal`, diff the old `_hostParams.stateMachines` against the new `params.stateMachines`: for any state machine present in the old set but absent from the new set, explicitly zero out `_latestStateMachineHeight[id]` and consider clearing/marking associated `_stateCommitments` entries as untrusted, mirroring the Nested Finance fix of removing cache entries at the same time the authoritative list is mutated, rather than only ever adding.

### Proof of Concept
1. Governance calls `updateHostParams` with `stateMachines = [2000, 2001]`; both get `_latestStateMachineHeight` initialized/updated as commitments are stored (as in `testCanAddwhitelistedStateMachines` [5](#0-4) ).
2. Governance later calls `updateHostParams` again with `stateMachines = [2001]` only, intending to de-authorize `2000`.
3. `updateHostParamsInternal`'s loop only iterates the new list and only *adds* missing entries [6](#0-5) ; `_latestStateMachineHeight[2000]` remains at its last value (e.g., `100`), and `_stateCommitments[2000][100]` is untouched.
4. Any subsequent code that treats `_latestStateMachineHeight[2000] != 0` as "chain 2000 is a valid/trusted destination/source" still accepts it, even though governance's current `stateMachines` array no longer lists it.

Note: I could not exhaustively confirm every downstream consumer of `_latestStateMachineHeight` vs. `_hostParams.stateMachines` membership within this session's tool budget — the finding is grounded in the confirmed add-only cache bookkeeping bug, but full exploitation impact depends on which specific verification path (message handling, proxy checks, etc.) relies on the stale cache rather than re-checking `_hostParams.stateMachines` directly.

    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.

            _latestStateMachineHeight[height.stateMachineId] = 1;

    function testCanAddwhitelistedStateMachines() public {
        HostParams memory params = host.hostParams();
        uint256[] memory stateMachines = new uint256[](2);
        stateMachines[0] = 2000;
        stateMachines[1] = 2001;
        params.stateMachines = stateMachines;

        // create a state commitment
        StateMachineHeight memory height = StateMachineHeight({height: 100, stateMachineId: 2000});
        vm.prank(params.handler);
        host.storeStateMachineCommitment(
            height, StateCommitment({timestamp: 200, overlayRoot: bytes32(0), stateRoot: bytes32(0)})
        );

        vm.prank(params.handler);
        assert(host.stateMachineCommitment(height).timestamp == 200);

        assert(host.latestStateMachineHeight(height.stateMachineId) == 100);

        // add the new state machine
        vm.prank(params.hostManager);
        host.updateHostParams(params);
        // should be unchanged
        assert(host.latestStateMachineHeight(height.stateMachineId) == 100);
        // should be set to 1
        assert(host.latestStateMachineHeight(2001) == 1);
    }
