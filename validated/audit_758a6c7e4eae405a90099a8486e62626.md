## Title
Stale reward-rate applied retroactively across the entire unpaid block backlog lets a relayer over-drain the incentives treasury after a `cost_per_block` increase - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::calculate_reward` computes a relayer's reward as `(latest_height - baseline) * current_cost_per_block`, where `baseline` is the last-rewarded watermark and `current_cost_per_block` is whatever value happens to be stored in `StateMachinesCostPerBlock` at the moment the reward is calculated [1](#0-0) . This is the same broken invariant as the reported `WithdrawalManager` bug: a value spanning multiple "cycles"/periods is computed by multiplying the *current* per-unit rate by the *entire* span, instead of accounting for the fact that the rate (cycle duration in the original bug) may have changed partway through that span. Since there is no per-height historical rate ledger, any backlog of un-rewarded blocks that straddles a `update_cost_per_block` change gets paid entirely at whichever rate is active when the batch happens to be delivered.

### Finding Description
`StateMachinesCostPerBlock` stores a single current cost-per-block value per state machine, mutated in place by governance via `update_cost_per_block` [2](#0-1) . The reward calculation reads only this current value and applies it to the full un-rewarded span:

```rust
let blocks = latest_height.saturating_sub(baseline);
let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
let reward = blocks_as_balance.saturating_mul(block_cost);
``` [3](#0-2) 

`process_message` then transfers this `reward` from the treasury to the relayer and advances `LastRewardedHeight` to `latest_height` [4](#0-3) . There is no tracking of *when* `cost_per_block` changed relative to the block-height span being paid — exactly analogous to `WithdrawalManager` computing `initialCycleTime` from `3 * currentConfig.cycleDuration` without accounting for already-queued config changes that alter the duration for cycles within that span.

Consensus message delivery (and thus the `FeeHandler::on_executed` call that triggers `process_message`) is permissionless — any relayer can submit `StateMachineUpdated` events for a chain it relays for. A relayer therefore fully controls *when* it chooses to deliver its backlog of consensus proofs relative to a `cost_per_block` governance update.

### Impact Explanation
If governance raises `cost_per_block` for a state machine (a routine incentive-tuning operation, not an attack), any relayer holding back an un-delivered backlog of consensus updates can wait until after the increase and then submit the entire backlog in one batch. `calculate_reward` will pay the *whole* backlog span (`latest_height - baseline`, which can span the entire period since the last reward, potentially thousands of blocks) at the new, higher rate, rather than only the blocks accrued after the rate change. This directly overpays the relayer from `T::TreasuryAccount`, draining more of the treasury than the parameter update was meant to authorize — a fund-loss impact matching the bounty's "stealing or loss of funds" / "logic attacks" category, reachable by an ordinary unprivileged relayer without needing a malicious peer, prover, or admin.

### Likelihood Explanation
Likelihood is moderate-to-high: `update_cost_per_block` is a normal, expected governance operation (the pallet's whole purpose is fee-rate tuning), and delaying delivery of a batch of consensus messages is trivial and free for any relayer to do — no special privileges, front-running, or compromised infrastructure required. The existing safeguard in `FeeHandler::on_executed` only deduplicates multiple `StateMachineUpdated` events *within the same batch* to the highest height [5](#0-4) ; it does nothing to prevent a stale/mismatched rate being applied to a whole multi-update backlog.

### Recommendation
Do not apply the *current* `cost_per_block` value retroactively over a height span that may straddle a rate change. Either (a) require rewards to be claimed incrementally per rate-epoch (recording the height at which each `cost_per_block` update took effect, and integrating the reward across each sub-span at its effective rate, analogous to the recommended fix of summing per-cycle durations for `[currentCycleId, currentCycleId+1, currentCycleId+2]`), or (b) force settlement/flush of all outstanding rewards at the old rate before allowing a `cost_per_block` update to take effect.

### Proof of Concept
1. Governance sets `StateMachinesCostPerBlock[chain] = 100` via `update_cost_per_block`.
2. A relayer intentionally stops delivering consensus updates for `chain`, letting `latest_height` on the counterparty drift far ahead of `LastRewardedHeight` (e.g., a 10,000-block backlog accrues).
3. Governance later raises the rate: `update_cost_per_block(chain, 1000)`.
4. The relayer now submits the entire pending backlog in one (or several chained) consensus message batch(es).
5. `calculate_reward` computes `reward = (latest_height - baseline) * 1000`, i.e., the full 10,000-block backlog paid at the *new* rate, instead of ~9,999 blocks at rate 100 plus a handful at rate 1000 — exactly mirroring the `WithdrawalManager` example where cycles 100-102 should have been priced at `1 day + 7 days + 7 days` but were priced at `3 * 1 day`. 	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}

		/// Update cost per block for a state machine
		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::update_cost_per_block())]
		pub fn update_cost_per_block(
			origin: OriginFor<T>,
			state_machine_id: StateMachineId,
			cost_per_block: <T as pallet_ismp::Config>::Balance,
		) -> DispatchResult {
			T::IncentivesOrigin::ensure_origin(origin)?;

			StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {
				*maybe_cost = Some(cost_per_block);
			});

			Self::deposit_event(Event::<T>::StateMachineCostPerBlockUpdated {
				state_machine_id,
				cost_per_block,
			});

			Ok(())
		}
