### Title
OP_RETURN data is excluded from fee and weight accounting, producing underpriced or non-standard transactions - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/blackvul/serai--018/blob/main/networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` adds the caller-controlled OP_RETURN output to `tx_outs`, but estimates transaction size using only the payment outputs and optional change output. As a result, the calculated `needed_fee`, minimum-relay-fee check, and maximum-standard-weight check all omit the data output. An unprivileged caller can therefore cause the wallet to build and sign a transaction whose actual fee rate or weight does not satisfy the requested constraints.

### Finding Description
The constructor appends a zero-value OP_RETURN output containing up to 80 bytes of caller-controlled data to the transaction output list. [1](#0-0)  However, the initial virtual-size calculation receives only `tx_ins.len()` and `payments`, not the already-created `tx_outs` or the `data` payload. [2](#0-1)  The resulting `needed_fee` is therefore priced for a transaction that does not contain the OP_RETURN output. [3](#0-2)  The same omission occurs when sizing the transaction with change: `calculate_weight_vbytes` is again passed only `payments` and `Some(&change)`. [4](#0-3)  Finally, the standard-weight check uses the underestimated `weight`, so an OP_RETURN output can push the final signed transaction over `MAX_STANDARD_TX_WEIGHT` without triggering `TooLargeTransaction`. [5](#0-4) 

This is the same class as the external report: a fixed validation/probe operation assumes one parameterization is representative, while a supported target variant changes the actual behavior. Here, the sizing probe omits the optional OP_RETURN output even though that output is included in the transaction eventually signed. [6](#0-5) 

### Impact Explanation
A transaction containing data can be signed with a lower fee than requested by `fee_per_vbyte`. For transactions intended to operate near the network’s minimum relay fee, the signed transaction can fall below the actual minimum fee rate once the omitted OP_RETURN output is included, causing relay failure. [7](#0-6) 

A transaction whose payments are already close to the standard weight limit can also pass `TooLargeTransaction` validation while the completed transaction exceeds the limit after the data output is appended. [8](#0-7)  The wallet then produces a signed transaction that may not propagate, preventing the represented spend from completing without reconstructing it under different parameters.

### Likelihood Explanation
The `data` argument is a public input to `SignableTransaction::new`, and values from 0 through 80 bytes are explicitly accepted. [9](#0-8)  Every positive-size data payload affects the real transaction’s serialized output and witness-independent weight, while none of it is included in the estimate. [10](#0-9)  The issue is deterministic; it only requires a caller to request data while the no-data estimate is near a relay-fee or standard-weight boundary.

### Recommendation
Calculate weight and virtual size from the complete output list, including the OP_RETURN output, before deriving `needed_fee` or enforcing `MAX_STANDARD_TX_WEIGHT`. The change-capable estimate should likewise include the data output rather than reconstructing a separate partial transaction from `payments`. After constructing the final `Transaction`, assert that its actual weight and virtual size match the values used for fee and limit validation.

### Proof of Concept
```rust
let output = wallet_output_with_at_least(DUST + 1_000);
let payment = (destination_script, DUST);
let data = vec![0u8; 80];

// This succeeds and prices the transaction as though it only had `payment`.
let tx = SignableTransaction::new(
    vec![output],
    &[payment],
    None,
    Some(data),
    1, // requested 1 sat/vbyte
).unwrap();

// The final transaction nevertheless contains the OP_RETURN output.
assert_eq!(tx.transaction().output.len(), 2);
assert!(tx.transaction().output[1].script_pubkey.is_op_return());

// tx.fee() / tx.transaction().vsize() is below 1 sat/vbyte because
// needed_fee was computed without the OP_RETURN output.
```

The root cause is visible without a node: `tx_outs` contains the OP_RETURN output, while both calls to `calculate_weight_vbytes` are based on `payments` rather than `tx_outs`. [10](#0-9) [11](#0-10)
