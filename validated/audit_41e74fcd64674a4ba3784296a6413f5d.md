## Analog Found

### Title
Automatic remote URL rewrite trusts unvalidated GitHub API `clone_url` field, allowing silent redirection of push/fetch target - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Audius report's broken invariant is: a value is validated where it is first established (constructor) but not re-validated where it is later mutated (setter), letting an attacker push the mutated value into an unsafe state. The Desktop analog is `updateRemoteUrl()`, which silently rewrites a repository's `origin` remote URL based on the `clone_url` field of a GitHub API repository object, without re-validating that the new URL still points to the same trusted host. It only checks that the *protocol* is unchanged and that the *owner/name path* differs from the current value — it never checks that the hostname of the new URL matches the hostname the repository was originally associated with.

### Finding Description
`updateRemoteUrl` compares the current git remote URL to `apiRepo.clone_url` and, if the protocol is unchanged and the URL "looks different," calls `gitStore.setRemoteURL(...)` to overwrite the remote automatically: [1](#0-0) [2](#0-1) 

The only integrity checks performed are:
- `protocolsMatch` – compares `URL.parse(remoteUrl).protocol` vs `URL.parse(updatedRemoteUrl).protocol` [3](#0-2) 
- `urlMatchesRemote` – compares `hostname`, `owner`, and `name` between the *current GitHub repository record* and the *current remote*, and separately between the two URLs to decide whether they already "match" [4](#0-3) 

Crucially, there is no check that `updatedRemoteUrl`'s hostname equals the *current* remote's hostname before the overwrite is performed. The function's own logic explicitly changes the URL only when `!urlsMatch`, i.e., precisely when hostname/owner/name differ from what's currently configured — meaning a hostname change from `github.com` to an attacker-controlled host will not be rejected as long as the protocol (https/ssh) is the same.

This mirrors the Governance bug exactly: the "trusted" value (the remote's origin) is validated carefully at repository add/clone time (`addRemote`/`clone`, where the user explicitly supplies and reviews the URL), but the "setter" path (`updateRemoteUrl` → `gitStore.setRemoteURL` → `setRemoteURL` in `app/src/lib/git/remote.ts`) performs the actual git-level mutation without re-imposing the same origin/host trust check: [5](#0-4) 

### Impact Explanation
`apiRepo.clone_url` originates from a GitHub API repository object — precisely the class of attacker-controlled input called out as valid in this task (a GitHub API object). This field can be influenced by:
- a malicious/compromised GitHub Enterprise Server instance the user is signed into,
- a repository owner/organization performing a "transfer" or renaming maneuver where the API subsequently reports a different `clone_url` for what Desktop still treats as the "same" GitHubRepository record,
- a network position able to tamper with unauthenticated portions of API responses in edge/proxy configurations.

If Desktop's background refresh cycle calls `updateRemoteUrl` with a manipulated `clone_url` pointing to an attacker-controlled host (with the same protocol, e.g. `https`), the local `origin` remote is silently repointed. Subsequent `git push` from the user goes to the attacker's server (credential/code exfiltration of everything pushed), and subsequent `git fetch`/`pull` retrieves attacker-controlled content merged into the user's working tree — silent corruption of what the user commits, pushes, and pulls, without any dialog, confirmation, or visible remote-URL change indication in the UI beyond the Repository Settings page.

### Likelihood Explanation
`updateRemoteUrl` is designed to run automatically (as part of periodic GitHub repository metadata refresh) rather than in response to a deliberate user action, satisfying the requirement that the attacker not need local/physical access, admin rights, or unnatural user steps — the user only needs an already-added repository whose associated GitHub API data can be influenced by the attacker (e.g., via a GHES admin, a compromised third-party API proxy, or a repository transfer scenario). The guard that exists (`protocolsMatch` + `remoteUrlUnchanged`) prevents unrelated tampering but does nothing to stop a same-protocol, different-host URL from being accepted, which is the exact gap being exploited.

### Recommendation
Before calling `gitStore.setRemoteURL` in `updateRemoteUrl`, additionally validate that the hostname of `updatedRemoteUrl` matches the hostname of the repository's associated `GitHubRepository.endpoint` (or the current remote's hostname). If the hostname differs, require explicit user confirmation (similar to how manual edits are handled in `app/src/ui/repository-settings/remote.tsx`) rather than silently rewriting the remote.

### Proof of Concept
1. Add a repository in Desktop whose `origin` remote is `https://github.com/org/repo.git`, associated via the GitHub API with a `GitHubRepository` record.
2. Cause the API response backing that `GitHubRepository`'s subsequent refresh to report `clone_url: "https://attacker-host.example/org/repo.git"` (e.g., via a compromised GHES instance the account is signed into, or a manipulated API response reachable through the account's configured endpoint).
3. On the next background repository-indicator/API refresh, `updateRemoteUrl` computes `protocolsMatch = true` (both `https`) and `remoteUrlUnchanged = true` (assuming the user hadn't manually edited the remote), and `urlsMatch = false` (different hostname) — satisfying `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, so it calls `gitStore.setRemoteURL('origin', 'https://attacker-host.example/org/repo.git')`.
4. `git remote set-url origin https://attacker-host.example/org/repo.git` executes with no host-trust check.
5. The user's next `git push` sends their commits to `attacker-host.example`.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)
```

```typescript
export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
```
