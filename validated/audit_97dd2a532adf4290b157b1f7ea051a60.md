The report's broken invariant: a function validates identity/authorization against one target (`receiver`), but performs the state-changing action against a different, uncontrolled target (the caller). The Desktop analog is the `x-github-client://openRepo` deep-link → "checkout PR" flow, where Desktop authorizes/matches based on the PR's **base** repository (a repo the user already trusts and has cloned), but then performs the actual git fetch+checkout using the PR's **head** repository — a completely different, attacker-controlled fork.

### Title
Deep-link "Open PR from URL" checks out an attacker-controlled fork/ref into the user's trusted local clone - ([File: app/src/ui/dispatcher/dispatcher.ts])

### Summary
`openPullRequestFromUrl` in [1](#0-0)  resolves an `x-github-client://openRepo/...?pr=N` deep link by fetching PR metadata for an attacker-chosen `url`+`pr` pair, matching it to an *already existing, trusted* local repository via `getRepositoryFromPullRequest`, and then calling `_checkoutPullRequest` with the PR's **head** repo clone URL and ref — fields entirely controlled by whoever opened the pull request, not by the base repository owner.

### Finding Description
The deep-link parser accepts `pr` and constructs an `open-repository-from-url` action from an untrusted URL: [2](#0-1) . `dispatchURLAction` routes this to `openRepositoryFromUrl`, which for a PR link calls `openPullRequestFromUrl(url, pr)`: [3](#0-2) .

`openPullRequestFromUrl` fetches the PR via the API (identity check performed on the base `url`/account) and then locates a matching **existing** Desktop repository using `getRepositoryFromPullRequest`, which matches against either the PR's head clone URL or base clone URL: [4](#0-3) .

Critically, once a matching repository is found (typically matched via the trusted **base** URL that the user already has cloned), the code proceeds to check out code using the **head** repo/ref, which is fully attacker-controlled since any GitHub user can open a pull request against a public repository from their own fork: [5](#0-4) 

This is passed into `_checkoutPullRequest`, which adds a new remote for `headCloneUrl` (attacker's fork) if none exists, fetches it, and checks out `headRefName` (attacker's branch) into the user's already-existing, trusted local repository: [6](#0-5)  and [7](#0-6) .

The authorization/trust check (matching against a repo the user has already cloned and presumably trusts) is performed on one identity (the base repo URL), but the actual git operation (fetch + checkout) is performed against a different, unauthenticated identity (the head repo/ref) — mirroring the `receiver`-vs-`caller` mismatch in the Move contract: the checked party and the acted-upon party diverge.

### Impact Explanation
If a user clicks a maliciously crafted `x-github-client://openRepo/...` link (e.g., embedded in a webpage, chat message, or "Open in Desktop" button impersonation) pointing at a PR number the attacker created against a public repository the victim already has cloned locally, Desktop will silently fetch the attacker's fork as a new remote and check out the attacker's branch into the victim's local working copy — without the victim ever visiting the actual pull request page or reviewing the diff. This can silently replace the working directory contents with attacker-controlled code, which the user may then build, run, or unknowingly commit/push on top of, satisfying the "silent corruption of what the user commits or pushes" impact criterion. It does not require local/physical access, admin rights, or prior malware — only a public repo the victim has cloned and a click on a link.

### Likelihood Explanation
Likelihood is moderate-to-high in principle: crafting the link only requires opening a PR on any public repository (no special permission) and getting the victim to click a link referencing that repo/PR — a repo the victim is very likely to already have cloned if they are an active contributor (which is the realistic target audience for such a link). The existing repository-matching logic (`getRepositoryFromPullRequest`) actively looks for repos the user already has, which is exactly the precondition that makes this dangerous (it operates without prompting to add/clone a new unfamiliar repo).

### Recommendation
Before performing `_checkoutPullRequest` against an *existing, already-open* repository located via the deep link, require explicit user confirmation showing the actual head repository owner/fork URL and branch that will be fetched and checked out — do not silently reuse trust established for the base repository to justify fetching/checking out arbitrary head repository content. Alternatively, only allow automatic checkout when the head repo matches the same trusted account/organization as the base repo, and otherwise fall back to the existing "add remote / confirm fork checkout" UI flow used elsewhere in the app.

### Proof of Concept
1. Attacker forks a public GitHub repository that the victim has already cloned in GitHub Desktop (e.g., `github.com/victim-org/project`).
2. Attacker pushes a branch to their fork and opens a pull request (PR #N) against `victim-org/project`.
3. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/victim-org/project?pr=N`.
4. Victim clicks the link. Desktop's `parseAppURL` parses it as an `open-repository-from-url` action with `pr=N`: [2](#0-1) .
5. `dispatchURLAction` → `openRepositoryFromUrl` → `openPullRequestFromUrl(url, "N")` fetches PR #N, matches it to the victim's already-cloned `project` repo via `getRepositoryFromPullRequest`, and calls `_checkoutPullRequest` with the attacker's fork clone URL and branch: [1](#0-0) .
6. `_findPullRequestBranch`/`_checkoutBranch` add the attacker's fork as a remote, fetch it, and check out the attacker's branch into the victim's existing local `project` clone: [7](#0-6) .
7. The victim's working directory now silently contains attacker-controlled files under a repo they trust, with no diff review or confirmation dialog shown.

**Note:** I was not able to fully trace the `_checkoutBranch` implementation or confirm whether any confirmation dialog is shown at the UI layer immediately prior to checkout (index coverage limits prevented locating that specific code path). A Devin session with full repo access would be needed to confirm whether any last-mile prompt exists that partially mitigates this before the working directory is overwritten.

    pullRequest: IAPIPullRequest

    const repositories = state.repositories
    const headUrl = pullRequest.head.repo?.clone_url

        return repository
      }
    }

    for (const repository of repositories) {
      if (this.doesRepositoryMatchUrl(repository, baseUrl)) {
        return repository
      }
    }

    return null
  }

      log.warn(

      log.warn(

      )
      return null

      return null

      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }
