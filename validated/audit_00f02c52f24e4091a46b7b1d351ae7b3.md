## Finding

The TensorFlow advisory describes a `CHECK`-failure (`CWE-190`, unguarded integer overflow → assertion abort) reachable from a bounded, attacker-controlled tensor-shape argument passed through a public op API. The strongest Protobuf analog is the deliberate-but-still-fatal overflow guard in `RepeatedField` packed-parsing, where `internal::CheckedAdd` is used to compute the new element count and, on overflow, calls `ABSL_LOG(FATAL)` (i.e., aborts the process) instead of returning a parse error.

### Title
Reachable `CHECK`/`LOG(FATAL)` abort via `int32` overflow in packed-field size accumulation - (File: `src/google/protobuf/parse_context.h`, `src/google/protobuf/port.h`, `src/google/protobuf/port.cc`)

### Summary
When parsing a packed repeated scalar field, `EpsCopyInputStream::ReadPackedVarintArrayWithField` and `EpsCopyInputStream::ReadPackedFixed` compute `internal::CheckedAdd(out.size(), count)` to size the pre-allocation for newly parsed elements [1](#0-0) . `CheckedAdd` is defined to abort the process via `HandleAddOverflow` → `ABSL_LOG(FATAL)` whenever the addition would overflow an `int32` [2](#0-1) [3](#0-2) . This is directly analogous to the TensorFlow depthwise op bug: an attacker-controlled arithmetic quantity (repeated element count) overflows a bounded integer type, and instead of the API returning a graceful parse failure, the process is killed by an assertion (`CHECK`/`LOG(FATAL)`)—a denial-of-service via `CHECK`-failure, exactly the bug class in the advisory.

### Finding Description
`RepeatedField::MergeFrom`, `AddForwardIterator`, and the packed-parsing helpers all rely on `internal::CheckedAdd(old_size, additional_count)` to compute the field's new logical size before growing storage [4](#0-3) [5](#0-4) . `CheckedAdd` is explicitly designed to prevent silent wraparound/heap corruption, but its failure mode is not a catchable error—it is `[[noreturn]] HandleAddOverflow`, which logs `ABSL_LOG(FATAL)` and aborts [6](#0-5) . The codebase's own tests confirm this is reachable purely from parsing attacker-supplied wire bytes: `RepeatedFieldIsFullTest.ParsedPackedOverflow` and `RepeatedFieldIsFullTest.RepeatedVarintOverflow` drive the abort by calling `MergeFromString` on a message whose repeated field is already near `INT_MAX` size, expecting `EXPECT_DEATH(..., "Integer overflow in CheckedAdd: ")` [7](#0-6) . A related test in `generated_message_tctable_lite_test.cc` also documents that "the parser doesn't overflow an int32 when computing the array's new length," confirming this is a known, previously-hardened overflow surface in the parser [8](#0-7) .

The "missing check" that transfers from the TF advisory is: computing a size/count via addition of two attacker-influenced values without pre-validating the sum stays within the representable range before performing dependent work — same invariant violation as TF's `filter_sizes`/tensor-element-count overflow. Here the difference from TF is that the overflow is *caught* rather than silently used for allocation, but the catch mechanism itself is a fatal abort rather than a returned parse error, so the impact (DoS) is preserved even though memory corruption is prevented.

### Impact Explanation
Impact is Denial of Service: a client sending a specially crafted, though large, bounded binary Protobuf message through a supported public parse API (`MergeFromString`/`ParseFromString` on a message with a packed repeated field, or repeated occurrences of the same packed field merged into one message) can cause the consuming process to abort via `ABSL_LOG(FATAL)`. This matches the TF advisory's impact tier (Medium, DoS via `CHECK`-failure) rather than memory corruption/RCE, since `CheckedAdd`'s guard specifically prevents the wraparound from being used for allocation.

### Likelihood Explanation
Reaching the overflow boundary requires the target `RepeatedField` to already hold a count of elements close to `INT_MAX` (as shown by the tests gating on `RunLargeMemoryTests()`), meaning the practical trigger requires processing an input on the order of gigabytes (e.g., a packed `bool`/varint field near 2^31 elements, achievable within a single ~2GB message since each `bool` byte contributes one element) [9](#0-8) . This is a bounded, reproducible arithmetic trigger (not a generic memory-exhaustion/flooding scenario), but it does require a very large single payload to reach the `INT_MAX` boundary, which somewhat limits real-world likelihood compared to the TF case (where a small tensor-shape descriptor with a huge value directly overflows without needing gigabytes of actual data).

### Recommendation
Change the packed-field parsing and `RepeatedField`/`RepeatedPtrField` growth paths so that reaching the `int32` size limit returns a normal parse failure (e.g., `nullptr`/`false` from the parser) instead of invoking `HandleAddOverflow`'s `ABSL_LOG(FATAL)`, at least for growth paths reachable directly from untrusted wire-format input (`ReadPackedVarintArrayWithField`, `ReadPackedFixed`, `MergeFrom` called during `MergeFromString`). Reserve the abort-on-overflow behavior for internal/API-misuse contract violations where the caller is trusted code, consistent with `BoundsCheckMode::kAbort` being intended as a defense-in-depth safety net rather than the primary error-handling path for parser input [10](#0-9) .

### Proof of Concept
The existing test `RepeatedFieldIsFullTest.ParsedPackedOverflow` is a working, in-repo reproduction of this: it resizes a message's `packed_bool` field to `INT_MAX - 4`, then calls `MergeFromString` with a small serialized packed-bool payload; the merge computes `CheckedAdd(old_size, count)`, overflows, and the process dies with `"Integer overflow in CheckedAdd: "` rather than the merge simply failing [9](#0-8) . No test execution was performed here; this cites the assertions already present and passing in the codebase's own test suite as the reproduction evidence.

  int sum;
  bool overflow = __builtin_add_overflow(a, b, &sum);
