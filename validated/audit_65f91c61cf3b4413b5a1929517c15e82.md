### Title
Off-by-One in Work Comparison Allows Operator with Equal-Work Fork to Pass Bridge Circuit — (`File: circuits-lib/src/bridge_circuit/mod.rs`)

### Summary

The `bridge_circuit` function uses a strict-less-than (`<`) comparison to validate that the operator's cumulative proof-of-work exceeds the maximum watchtower challenge work. When the two values are equal, the check passes silently, contradicting the protocol's explicit requirement that the operator must have **strictly more** work than any challenging watchtower. This is the direct analog of the governance tie-approval bug: a tie is treated as a win for the operator.

### Finding Description

In `circuits-lib/src/bridge_circuit/mod.rs`, the work comparison is:

```rust
// If total work is less than the max total work of watchtowers, panic
if total_work < max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
``` [1](#0-0) 

`TotalWork` is a `[u8; 16]` newtype with a derived `PartialOrd`, meaning comparison is lexicographic over the 16 bytes. [2](#0-1) 

The protocol documentation and the function's own docstring both state the invariant as a **strict** inequality:

> "Asserts that the Operator's `total_work` from their HCP is **greater than** the `max_total_work` from the Watchtowers." [3](#0-2) 

> "If `max_total_work` given by watchtowers is **greater than** `hcp.chain_state.total_work`." (panic condition) [4](#0-3) 

The code only panics when `total_work < max_total_work`. When `total_work == max_total_work`, the circuit continues and commits a valid journal hash, meaning the operator's proof is accepted.

The `total_work` value fed into this comparison is the **lower 128 bits** of the 256-bit chain-state total work:

```rust
let total_work: TotalWork = input.hcp.chain_state.total_work[16..32]
    .try_into()
    .expect("Cannot fail");
``` [5](#0-4) 

Truncating to 128 bits increases the probability of a collision compared to the full 256-bit value.

### Impact Explanation

The bridge circuit is the ZK proof that gates operator reimbursement. If it produces a valid journal hash, the operator can claim collateral reimbursement for their payout. A watchtower that submits a Work-Only Proof (WOP) with `total_work` exactly equal to the operator's HCP `total_work` (lower 128 bits) causes the circuit to pass even though the watchtower has demonstrated an alternative chain of equal weight. Bitcoin's canonical chain is defined as the chain with the **most** cumulative work; equal work is ambiguous and the operator cannot be considered to have proven canonical-chain inclusion. The operator can therefore be reimbursed for a payout made on a fork, resulting in loss of bridged BTC from the collateral pool.

### Likelihood Explanation

Two independent Bitcoin chains reaching exactly the same 128-bit truncated cumulative work is unlikely in normal operation. However:

1. The truncation from 256 to 128 bits (`total_work[16..32]`) reduces the collision space significantly.
2. A sophisticated attacker controlling mining hardware could deliberately mine a fork to reach an exact work tie at the 128-bit level.
3. The bug is unconditional — any future scenario where the truncated values collide triggers it automatically, with no additional attacker capability required beyond submitting a valid WOP Groth16 proof.

### Recommendation

Change the comparison from strict-less-than to less-than-or-equal, so that a tie is also rejected:

```rust
// Operator must have STRICTLY MORE work than any challenging watchtower
if total_work <= max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
``` [1](#0-0) 

This aligns the code with the documented invariant and with Bitcoin's canonical-chain rule (strictly most work wins).

### Proof of Concept

1. Operator initiates a kickoff on a fork chain F whose lower-128-bit total work equals the canonical chain's lower-128-bit total work: `operator_work_128 == canonical_work_128`.
2. A watchtower submits a valid WOP Groth16 proof for the canonical chain with `total_work = canonical_work_128`.
3. Inside `bridge_circuit`, `total_work_and_watchtower_flags` returns `max_total_work = TotalWork(canonical_work_128)`.
4. The check `total_work < max_total_work` evaluates to `false` (they are equal), so no panic occurs.
5. The circuit proceeds through SPV, LCP, and storage proof verification on the fork chain and commits a valid `journal_hash`.
6. The operator uses this valid ZK proof to claim reimbursement for a payout that was included in the fork, not the canonical chain, draining collateral for a withdrawal that was never finalized on the canonical Bitcoin chain.
