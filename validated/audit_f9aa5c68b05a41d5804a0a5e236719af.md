### Title
Permanent forfeiture of legitimately earned vlMGP rewards after `forceUnLock` drains a user's total lock balance to zero - (File: `VLMGP.sol`, `rewards/vlMGPBaseRewarder.sol`)

### Summary
`vlMGPBaseRewarder` pins a user's earned-but-unclaimed rewards into `userRewards[token][account]` at the time `_updateFor`/`updateRewards` runs, but only assesses the "expired lock" forfeiture at the time of actual payout (`_sendReward`), using the account's *current* `getRewardablePercentWAD`. Because `forceUnLock` (unlike `unlock`) never harvests the rewarder before zeroing the user's cooldown/lock balance, a user who force-unlocks the entirety of their locked/cooling-down MGP causes `getRewardablePercentWAD` to permanently return `0` for that account. Any rewards already accrued while the user was properly locked — but not yet paid out — are then forfeited 100% the next time the user claims, even though they were earned honestly during active locking.

### Finding Description
`VLMGP.getRewardablePercentWAD` computes the fraction of a user's rewards that should be honored based on their currently locked vs. cooling-down MGP: [1](#0-0) 
When `userTotalVlmgp` (i.e. `getUserTotalLocked + getUserAmountInCoolDown`) is `0`, the function returns `0` — meaning "forfeit everything."

`vlMGPBaseRewarder` uses this percentage only at claim time in `_calExpireForfeit`, applied against the currently-pinned `userRewards` balance (which represents rewards accrued over potentially a long history of proper locking): [2](#0-1) [3](#0-2) 

Rewards are pinned into `userRewards` via `_updateFor`/`updateRewards`, evaluated against the balance *at the time of pinning*: [4](#0-3) 

The critical asymmetry is in `VLMGP.sol`'s unlock paths. `unlock()` harvests rewards (via `multiclaimFor`) *before* reducing the user's balance, so the forfeit check at that specific claim still sees the pre-unlock balance: [5](#0-4) 

`forceUnLock()`, however, does **not** call `multiclaimFor` at all before reducing the user's lock via `_unlock(slot.amountInCoolDown)`: [6](#0-5) 

If a user has previously accrued rewards that are already pinned in `userRewards[token][account]` (e.g., via a public, permissionless call to `updateFor`, which anyone can trigger for any account) while properly locked, and then calls `forceUnLock` on their remaining slot(s) — driving `getUserTotalLocked + getUserAmountInCoolDown` to zero — their `getRewardablePercentWAD` becomes permanently `0`. The next time the user (or anyone) triggers a claim through MasterMagpie (`getReward`/`getRewards` on the vlMGP pool's rewarder), `_calExpireForfeit` will forfeit 100% of the pinned `userRewards`, even though those rewards were earned entirely while the user held a full, honest lock. The forfeited amount is redirected into the general reward pool via `_queueNewRewardsWithoutTransfer`, effectively transferring the victim's earned yield to other stakers.

This directly parallels the reported bug class: a user's balance-driving action (burning all tokens / unlocking all MGP) that happens to reach zero causes irreversible loss of rewards/payouts that were legitimately earned during a period when the user was fully entitled to them.

### Impact Explanation
This causes a genuine, permanent loss of a user's own already-earned (but not yet transferred) reward tokens — unclaimed yield theft/freezing, entirely triggerable by the account owner's own unprivileged transactions (`updateFor` + `forceUnLock`, or simply having pending unharvested reward growth followed by `forceUnLock`). No admin or privileged role is required. Because `_sendReward` recomputes forfeiture retroactively based on final state rather than state-at-accrual, correctly-earned value is destroyed for the user and effectively donated to remaining stakers.

### Likelihood Explanation
Likelihood is moderate-to-high: `forceUnLock` is a normal, expected exit path for a locked user (e.g., needing liquidity before cooldown ends), and reward pin accrual naturally happens whenever `queueNewRewards`/`queueMGP` is called by the reward manager while a user has not recently claimed. No coordination with other actors or special preconditions beyond ordinary usage timing is needed.

### Recommendation
Do not defer the expiry/forfeiture calculation to claim time using the user's *current* lock state for rewards that were already pinned/accrued in the past. Options:
- Apply `_calExpireForfeit` (or an equivalent rewardable-percent check) at the moment rewards are pinned into `userRewards` (inside `_updateFor`/`updateRewards`), not at the moment of transfer in `_sendReward`, so forfeiture reflects the lock state during which the reward accrued.
- Alternatively, harvest/settle the rewarder (as `unlock()` already does via `multiclaimFor`) inside `forceUnLock()` *before* reducing the user's locked/cooldown balance, so the forfeit percentage used still reflects the balance the reward was earned against.

### Proof of Concept
1. User locks MGP into `VLMGP` via `lock()`; `masterMagpie` pool tracks `user.amount` and `vlMGPBaseRewarder.balanceOf` reflects the full locked amount.
2. Reward manager periodically calls `queueNewRewards`/`queueMGP` on `vlMGPBaseRewarder`, incrementing `rewardPerTokenStored` while the user remains fully locked (`getRewardablePercentWAD` == 100%).
3. Anyone calls `vlMGPBaseRewarder.updateFor(user)` (public, unrestricted), pinning the fully-rewardable accrued amount into `userRewards[token][user]` via `_updateFor` [4](#0-3) .
4. User calls `startUnlock()` then, once cooldown ends, calls `forceUnLock(slotIndex)` on their entire remaining position without an intervening `multiclaimFor` harvest [6](#0-5) , driving `getUserTotalLocked(user) + getUserAmountInCoolDown(user)` to `0`.
5. User (or MasterMagpie on their behalf) subsequently calls a claim path that invokes `vlMGPBaseRewarder.getReward`/`getRewards`. `_calExpireForfeit` now computes `vlMGP.getRewardablePercentWAD(user) == 0` [1](#0-0) , so `_sendReward` forfeits 100% of the previously pinned `userRewards`, sending `0` to the user and re-queuing the entire amount to other stakers [3](#0-2) .

Note: I was unable to fully trace `_unlock`/`_checkInCoolDown` internals or `MasterMagpie`'s exact `claim`/`multiclaim` entry points within the remaining tool budget; these should be reviewed to confirm the exact call sequence and timing window in a live test, but the forfeiture logic itself (`_calExpireForfeit` using post-unlock `getRewardablePercentWAD` against pre-existing `userRewards`) is directly confirmed in the cited code.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
