### Title
Unbounded accumulation of attacker-supplied signatures in `SchnorrAggregator` enables memory-exhaustion DoS - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The external report (CVE-2021-40797) describes a route middleware that accumulates state per request involving nonexistent controllers, letting an authenticated attacker grow a worker's memory until the API degrades or dies (CWE-772, missing resource release/limit). The analogous shape in Serai's in-scope code is `SchnorrAggregator<C>` in `crypto/schnorr/src/aggregate.rs`: every call to `aggregate()` appends the caller-supplied `SchnorrSignature` to an internal `Vec` and appends to the digest transcript, with no bound on the number of items and no eviction until `complete()` consumes the aggregator. An unprivileged party that can feed signatures into an aggregation session causes memory growth proportional to the number of submissions, matching the "increasing amounts of memory → performance degradation or denial of service" bug class.

### Finding Description
`SchnorrAggregator` is defined at `crypto/schnorr/src/aggregate.rs:152-155` with a `sigs: Vec<SchnorrSignature<C>>` field. `aggregate()` (`aggregate.rs:169-172`) unconditionally pushes each provided signature:

```rust
pub fn aggregate(&mut self, challenge: C::F, sig: SchnorrSignature<C>) {
  self.digest.append_message(b"challenge", challenge.to_repr());
  self.sigs.push(sig);
}
```

There is no cap on `sigs.len()`, no deduplication, and no early rejection of signatures that cannot be part of the final aggregate. `complete()` (`aggregate.rs:175-186`) is the only exit path, and it iterates over all accumulated signatures, so the DoS also carries a CPU component: both the digest weight derivation (`weight()`, `aggregate.rs:22-65`, one multi-word wide reduction per signature) and the final `verify()` (`aggregate.rs:127-146`, which allocates `Vec::with_capacity(2 * n + 1)` and runs one `multiexp_vartime` over all pairs) scale linearly in the number of junk signatures submitted.

This mirrors the Neutron bug's structure: a per-session/per-request collection grows monotonically with attacker-influenced inputs, intermediate entries are never released, and the cost is only paid back (much larger) at finalization. Each signature additionally carries a `C::G` point and `C::F` scalar, so memory grows at a fixed rate per accepted submission.

### Impact Explanation
Memory exhaustion / denial of service against any service that exposes signature aggregation over an unauthenticated or low-privilege channel (e.g., collecting Schnorr signatures/co-signatures from arbitrary submitters into one aggregator). The attacker only needs to keep submitting well-formed `SchnorrSignature` encodings — each accepted `aggregate()` call permanently grows the worker's heap for the lifetime of the session. Because `complete()` and `verify()` are O(n) over the accumulated set, a large `sigs` vector also inflates finalization CPU cost, compounding the degradation. This is a Medium-severity availability issue: no secret leakage or forgery, but concrete resource exhaustion reachable with only public inputs.

### Likelihood Explanation
Reachability requires a deployment that instantiates one long-lived `SchnorrAggregator` and calls `aggregate()` on inputs from parties who are not fully trusted — which is exactly the aggregator's purpose (collecting a set of signatures before batch-verifying once). The attacker needs no valid signatures: `aggregate()` performs no verification, so arbitrary `SchnorrSignature { R, s }` values parsed via `SchnorrSignature::read` and passed in all count toward growth. In deployments where aggregation is scoped to a fixed, known signer set and `complete()` is called after `n` items, the exposure is bounded by `n`; where the set is open-ended or the aggregator is reused across an unbounded stream, the growth is unbounded — the same conditional reachability as the Neutron middleware (it only leaked for requests hitting nonexistent controllers). Moderate likelihood: depends on integrator usage, but the library offers no guardrails and the doc comments do not warn that `aggregate()` must be externally bounded.

### Recommendation
Add an explicit capacity bound: either a `max_sigs: usize` parameter on `SchnorrAggregator::new` enforced in `aggregate()` (returning `Err`/dropping excess), or document and enforce that callers must cap the number of aggregated signatures to the expected signer count before calling. Optionally verify each signature cheaply (or at least deduplicate `R` values) at `aggregate()` time so garbage entries cannot accumulate.

### Proof of Concept
```rust
// Attacker-controlled input loop; sig bytes are parsed via SchnorrSignature::read
// and handed to the aggregator with no per-item verification or bound.
let mut aggregator = SchnorrAggregator::<C>::new(b"dst");
while let Ok(sig) = SchnorrSignature::<C>::read(&mut attacker_stream) {
    // challenge derived from the (key, R, msg) tuple as usual
    aggregator.aggregate(challenge, sig); // sigs.push: memory grows per call
}
// aggregator.sigs now holds every submitted signature;
// complete()/verify() then do O(n) hash-weights and one O(n) multiexp over all of them.
```

Root cause location: `crypto/schnorr/src/aggregate.rs:169-172` (unbounded `self.sigs.push(sig)`), with the amplification at `complete()`/`verify()` (`aggregate.rs:180-185`, `138-145`).
