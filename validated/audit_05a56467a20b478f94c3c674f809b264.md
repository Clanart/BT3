### Title
`ThresholdKeys::read` accepts attacker-controlled `Interpolation::Constant` coefficients and never checks `verification_shares[i] == generator * secret_share`, letting a crafted key blob claim an arbitrary group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` in `crypto/dkg/src/lib.rs` deserializes an untrusted byte stream into secret-key material by reading a single tag byte that selects between `Interpolation::Constant` (which then consumes `n` raw scalar coefficients directly from the stream) and `Interpolation::Lagrange`. Neither `read` nor `ThresholdKeys::new` verifies that the supplied `secret_share` is consistent with `verification_shares[params.i()]`, and `Constant` coefficients are accepted verbatim whenever `t == n`. The resulting `group_key` is computed purely from attacker-supplied `verification_shares` and attacker-supplied interpolation factors. This is the direct analog of CVE-2018-8459's "object handled incorrectly in memory": an attacker-controlled type tag causes bytes to be interpreted as a different object variant (Constant coefficients vs. Lagrange), producing a semantically invalid `ThresholdKeys` object that downstream code treats as authentic.

### Finding Description
- `ThresholdKeys::read` reads `interpolation[0]`; `0` maps to `Interpolation::Constant` populated with `n` caller-controlled scalars via `C::read_F`, `1` maps to `Lagrange` [1](#0-0) .
- The `secret_share` and all `n` `verification_shares` are read from the same stream without any consistency check (`C::generator() * secret_share == verification_shares[i]` is never evaluated) [2](#0-1) .
- `ThresholdKeys::new` only rejects `Constant` when `t != n`; for `t == n` it accepts the coefficients and computes `group_key = Σ_{i=1..=t} verification_shares[i] * interpolation_factor(i)` where `interpolation_factor` for `Constant` returns `c[i-1]` — fully attacker-chosen [3](#0-2) .
- `Interpolation::interpolation_factor` indexes the attacker-supplied coefficient vector directly [4](#0-3) .
- When signing, `ThresholdView::verification_share` returns `verification_shares[i] * scalar * interpolation_factor` derived from these same crafted values, so shares produced by the poisoned key verify correctly against the crafted group key [5](#0-4) .

### Impact Explanation
An attacker who supplies the serialized `ThresholdKeys` blob consumed by `ThresholdKeys::read` (key import, backup restore, recovery flows — this crate explicitly exposes `serialize`/`read` for persisted secret material) can construct keys whose reported `group_key()` (and hence the Bitcoin/Monero/etc. deposit address derived from it) corresponds to a discrete log known to the attacker, not to the honest participants' real shares. By choosing `secret_share s_i`, `verification_shares[i] = s_i * G`, and `Constant` coefficients `c_i`, the attacker's recovered key is `Σ s_i * c_i`. The node signs validly — `complete()`'s integrity check passes since all fields are internally consistent under the crafted interpolation — while the attacker unilaterally controls the "threshold" key. Funds deposited to the derived address are spendable by the attacker alone; alternatively, inconsistent blobs cause the node to emit signature shares valid under a group key no honest quorum agreed to. This yields "funds reported under group control that are not" — a High-severity analog reachable purely through untrusted bytes fed to `ThresholdKeys::read`.

### Likelihood Explanation
Requires the attacker to supply the serialized keys blob to a node performing key deserialization (import/restore/migration paths or any RPC/backup channel feeding `ThresholdKeys::read`). `t == n` is required for `Constant` (MuSig-style configurations, e.g., the validator-set MuSig used in coordinator signing, satisfy `t == n` naturally). The crypto/`ThresholdKeys::read` path performs no proof-of-possession, no self-consistency verification, and no check that `group_key` matches a registered DKG transcript, so the crafted blob is accepted unconditionally. Medium likelihood within the stated threat model (untrusted bytes to `ThresholdKeys::read` are explicitly in scope).

### Recommendation
- In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[params.i()]` and reject otherwise.
- Restrict `Interpolation::Constant` deserialization: since `Constant` encodes MuSig binding factors, validate that the coefficients match a recomputation from the verification shares (e.g., recompute `binding_factor(context, i)` where the context is derivable) or refuse to deserialize `Constant` interpolations entirely, forcing MuSig keys through `musig()` which recomputes binding factors internally [6](#0-5) .
- Consider binding the serialized blob to the DKG context/`group_key` the caller expects, so deserialization cannot silently substitute a distinct key set.

### Proof of Concept
```rust
// t == n configuration (e.g., MuSig-style full participation)
let t = 3u16; let n = 3u16; let i = 1u16;

// Attacker picks scalars whose sum (weighted by c) is a key they control
let s: Vec<_> = (0..n).map(|_| <C as Ciphersuite>::F::random(&mut OsRng)).collect();
let c = vec![C::F::ONE; n as usize]; // Constant coefficients, attacker-chosen
// Attacker's known private key: sum_i s[i] * c[i]
let known_key: C::F = s.iter().sum();

let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(t.to_le_bytes());
blob.extend(n.to_le_bytes());
blob.extend(i.to_le_bytes());
blob.push(0); // Interpolation::Constant tag — the variant-confusion byte
for coeff in &c { blob.extend(coeff.to_repr().as_ref()); }
blob.extend(s[0].to_repr().as_ref()); // our secret_share
for s_l in &s { blob.extend((C::generator() * s_l).to_bytes().as_ref()); } // consistent V_shares

let keys = ThresholdKeys::<C>::read::<&[u8]>(&mut blob.as_ref()).unwrap();
assert_eq!(keys.group_key(), C::generator() * known_key); // attacker-controlled group key
// keys.sign(...) produces shares that verify against this group key,
// yet the attacker knows `known_key` and can sign/spend unilaterally.
```

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
