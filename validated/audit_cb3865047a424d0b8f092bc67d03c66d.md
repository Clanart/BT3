### Title
Unauthenticated `NewDeposit` Spam Fills Verifier Nonce-Session Pool via FIFO Eviction, Permanently Blocking Deposit Finalization — (`core/src/verifier.rs`, `core/src/rpc/aggregator.rs`)

---

### Summary

The aggregator's `NewDeposit` gRPC endpoint requires no mTLS authentication. Each call unconditionally triggers `nonce_gen` on every verifier — creating in-memory `NonceSession` entries in the bounded `AllSessions` pool — **before** any on-chain deposit validation occurs. When the deposit outpoint is fake, `deposit_sign` fails inside `is_deposit_valid` after the session is already stored, and the session is never consumed or cleaned up. An attacker can spam 2 000 fake `NewDeposit` calls to saturate the pool, triggering FIFO eviction of every legitimate session and making all concurrent real deposits fail with "Session not found".

---

### Finding Description

**Step 1 — No authentication on the aggregator.**

`docs/usage.md` line 203 states explicitly:

> "The aggregator does not enforce client certificates but does use TLS for encryption."

The `ClementineAggregator` gRPC service applies no `OnlyAggregatorAndSelf` interceptor. Any party that can reach the aggregator's port can call `NewDeposit` with arbitrary input. [1](#0-0) 

**Step 2 — `get_deposit_keys` on the operator performs no on-chain validation.**

`collect_and_distribute_keys` (called first in `new_deposit`) asks each operator for its deposit keys. The operator's `get_deposit_keys` handler only runs deterministic key-derivation; it never queries the Bitcoin node:

```rust
// core/src/rpc/operator.rs:299-327
async fn get_deposit_keys(&self, request: Request<DepositParams>) -> Result<Response<OperatorKeys>, Status> {
    let deposit_data: DepositData = deposit_params.try_into()?;
    let winternitz_keys = self.operator.generate_assert_winternitz_pubkeys(deposit_data.get_deposit_outpoint())?;
    let hashes = self.operator.generate_challenge_ack_preimages_and_hashes(&deposit_data)?;
    Ok(Response::new(OperatorKeys { ... }))
}
```

A fake txid passes this step without error. [2](#0-1) 

**Step 3 — Nonce sessions are created before on-chain validation.**

After `collect_and_distribute_keys` succeeds, `new_deposit` immediately calls `create_nonce_streams`, which calls `nonce_gen` on every verifier. Each verifier allocates a `NonceSession` and inserts it into `AllSessions`:

```rust
// core/src/rpc/aggregator.rs:1498-1505

    create_nonce_streams(verifiers.clone(), num_required_nonces, ...).await?;
``` [3](#0-2) 

```rust

**Step 4 — On-chain validation happens inside `deposit_sign`, after the session is stored.**

`is_deposit_valid` (which calls `get_tx_of_txid` and checks amount/script/confirmation) is invoked at line 876 of `deposit_sign`. The session is only removed from the pool inside a `tokio::spawn` at line 904 — which is never reached if `is_deposit_valid` returns an error:

```rust
// core/src/verifier.rs:866-904
pub async fn deposit_sign(...) -> Result<...> {
    self.is_deposit_valid(&mut deposit_data).await?;  // ← fails here for fake deposit
    // ...
    let handle = tokio::spawn(async move {
        let mut session = {
            let mut session_map = verifier.nonces.lock().await;
            session_map.remove_session_with_id(session_id)?  // ← never reached
        };
``` [5](#0-4) [6](#0-5) 

The session remains in `AllSessions` indefinitely.

**Step 5 — The pool has a hard cap with FIFO eviction.**

`AllSessions::add_new_session_with_id` enforces `MAX_NUM_SESSIONS = 2000`. When the cap is reached, the **oldest** session is silently evicted:

```rust
// core/src/verifier.rs:142-151
loop {
    if total_needed <= MAX_ALL_SESSIONS_BYTES && self.sessions.len() < MAX_NUM_SESSIONS {
        break;
    }
    total_needed = total_needed
        .checked_sub(self.remove_oldest_session()?)
        ...
}
``` [7](#0-6) [8](#0-7) 

Once the pool is full of attacker-created sessions, any legitimate session created before the attack is evicted. When the real `deposit_sign` later looks up its session ID, it gets "Session not found" and the deposit fails.

---

### Impact Explanation

Every in-flight deposit that had its nonce session evicted cannot complete `deposit_sign` or `deposit_finalize`. The aggregator's `new_deposit` pipeline fails, and the signed move-to-vault transaction is never produced. BTC sent to the deposit address is stranded there until the `user_takes_after` timelock expires (a configurable number of blocks). During a sustained attack, **no new deposits can be finalized**, halting the entire peg-in path of the bridge.

---

### Likelihood Explanation

- The aggregator endpoint is reachable by any TLS client (no mTLS).
- Each fake `NewDeposit` call costs nothing on-chain; the fake txid is never validated until `deposit_sign`.
- The default gRPC rate limit is 1 000 requests per 60 seconds; filling 2 000 slots takes ~2 minutes.
- The attack must be sustained (sessions are eventually consumed by legitimate deposits), but the cost per iteration is zero.

---

### Recommendation

1. **Validate the deposit outpoint on-chain before calling `nonce_gen`.** Move the `is_deposit_valid` check (or at minimum the `get_tx_of_txid` + amount check) into the aggregator's `new_deposit` handler, before `create_nonce_streams` is called.

2. **Clean up orphaned sessions.** If `deposit_sign` fails for any reason, explicitly remove the corresponding session from `AllSessions` rather than leaving it to FIFO eviction.

3. **Authenticate `NewDeposit` callers.** Apply the same `OnlyAggregatorAndSelf`-style mTLS check (or a separate backend-service certificate) to the aggregator's `NewDeposit` endpoint so that only the authorized backend can initiate deposits.

---

### Proof of Concept

```
# Attacker (no certificate required, only TLS)
for i in 1..2001:
    grpc_call(aggregator_addr, "ClementineAggregator/NewDeposit", {
        deposit_outpoint: { txid: random_32_bytes(), vout: 0 },
        deposit_data: BaseDeposit { evm_address: [0;20], recovery_taproot_address: "" }
    })
    # Each call:
    #   1. collect_and_distribute_keys → operators return keys (no on-chain check)
    #   2. create_nonce_streams → verifier stores NonceSession in AllSessions
    #   3. deposit_sign → is_deposit_valid fails (txid not on chain)
    #      → session NOT removed, remains in pool

# After 2000 iterations, AllSessions is full.
# Any legitimate deposit whose session was created before iteration (2000 - pool_size)
# has been FIFO-evicted.
# Legitimate deposit_sign call returns: "Session not found" → deposit fails.
```

The exact corrupted value is the `session_id` returned by `nonce_gen` for a legitimate deposit: it is silently removed from `AllSessions.sessions` by `remove_oldest_session`, so the subsequent `remove_session_with_id(session_id)` call in the spawned `deposit_sign` task returns `Err("Session not found")`, aborting the signing pipeline and leaving the user's BTC stranded in the deposit address.     /// Removes the oldest session from the AllSessions.
    /// Returns the number of bytes removed.
    fn remove_oldest_session(&mut self) -> Result<usize, eyre::Report> {
        match self.session_queue.pop_front() {
            Some(oldest_id) => {
                let removed_session = self.sessions.remove(&oldest_id);
                match removed_session {
                    Some(session) => Ok(Self::session_bytes(&session)?),
                    None => Ok(0),
                }
            }
            None => Err(eyre::eyre!("No session to remove")),
        }
