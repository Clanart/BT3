### Title
Early error return in `calculate_share` leaks the ECDH blame key before the per-message proof-of-possession is verified, exposing another participant's DKG secret share - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
CVE-2022-43757 is a plaintext-exposure-of-secrets bug: sensitive values that should have been sealed were left readable to parties with only ordinary authenticated access. The Serai analog lives in PedPoP's blame system. `EncryptedMessage` includes a Schnorr proof-of-possession (PoP) over the per-message encryption key specifically so that an attacker cannot co-opt someone else's key `X` and trick the recipient into publishing a blame proof that reveals the ECDH shared key `bX` — which would decrypt the victim's real message. That protection is implemented by batch-verifying the PoP inside `Decryption`/`BatchVerifier`. However, in `KeyMachine::calculate_share`, when the decrypted share bytes fail to decode as a canonical scalar, the function returns `PedPoPError::InvalidShare` with `blame: Some(blame)` *before* `batch.verify_with_vartime_blame()` ever runs. The blame proof — `EncryptionKeyProof { key, dleq }` containing the ECDH shared key — is therefore published for a message whose PoP was never verified, re-opening exactly the key co-option attack the PoP was added to prevent, and leaking a victim's secret share in plaintext.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs:474-499`, `calculate_share` loops over `shares`, calling `self.encryption.decrypt(...)`, which only *queues* the PoP signature into the batch verifier (`encryption.rs:479-485`) and immediately returns the decrypted bytes plus an `EncryptionKeyProof` containing the ECDH point `key = ecdh(self.enc_key, msg.key)` (`encryption.rs:487-499`). At `lib.rs:480-482`, if `C::F::from_repr(share_bytes.0)` fails, the function returns early:

```rust
let share = Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
  PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
})?);
```

`batch.verify_with_vartime_blame()` at `lib.rs:493` is never reached, so the PoP for that message — and for all other queued messages — is never checked on this path. The spec itself (`spec/cryptography/Distributed Key Generation.md:28-35`) states this scenario is resolved by the PoP: an adversary claims another participant's encryption key, the recipient issues a blame statement, and the published shared key also decrypts the co-opted participant's message. The code comment at `encryption.rs:84-90` says the same. The early-return path bypasses the mitigation.

Attack: participant Eve observes Alice's `EncryptedMessage` to Bob, which uses per-message public key `X` and ciphertext `c`. Eve sends Bob her own `EncryptedMessage` (sender = Eve) with `key = X`, a garbage PoP (she cannot produce a valid signature for `X`), and a random/mutated ciphertext. Decryption under `ecdh(bob_enc_key, X)` — identical to the Alice↔Bob shared key — yields effectively random bytes, which fail `from_repr` with high probability (~7/8 for a ~252-bit group order). Bob returns `InvalidShare { participant: Eve, blame: Some(proof) }` where `proof.key` is the Alice↔Bob ECDH shared key with a valid DLEq. Bob's `ProcessorMessage::InvalidShare` carries this blame to the coordinator (`processor/src/key_gen.rs:419-425`), and `VerifyBlame`/`AdditionalBlameMachine` confirms Eve's PoP is invalid and blames Eve (`key_gen.rs:504-563`) — but the published `proof.key` already decrypts Alice's original message `c` to Bob, exposing Alice's secret share in plaintext to anyone who observes both messages.

### Impact Explanation
A published `EncryptionKeyProof.key` is the ECDH point feeding `cipher()` (`encryption.rs:392`, `101-133`), so the blame proof functions as a plaintext decryption key escrow. Whoever sees the blame and Alice's original `EncryptedMessage` recovers Alice's share `f_alice(bob)` — a secret that the protocol design explicitly encrypts per-recipient to protect (`spec` line 11-17). Leaking dealer shares weakens the DKG: combined with compromised or collaborating participants, leaked shares reduce the effective secrecy/threshold of the generated group key. The exposure is unconditional once the malformed message is processed — no PoP check stands between the attacker and the revealed key on this code path.

### Likelihood Explanation
Reachable by any DKG participant using only public inputs: they submit a well-formed-map `EncryptedMessage` (the read path `EncryptedMessage::read` accepts the untrusted bytes), reusing an observed victim `key` and choosing ciphertext bytes so decryption fails canonical decoding. No collusion, no broken BFT, no key compromise required — the honest victim's own code produces and publishes the decryption key. The attack is deterministic to mount (retry ciphertext mutation until `from_repr` fails, which is a per-message event the attacker cannot observe but can guarantee probabilistically by construction) and the blame publication path is the protocol's normal error handling.

### Recommendation
Do not attach `blame` on the early-return at `crypto/dkg/pedpop/src/lib.rs:480-482` unless the message's PoP has already been verified. Options:

- Verify the individual message's PoP (`msg.pop.verify(...)`) before returning `Some(blame)` on the decode-failure path, returning `blame: None` when the PoP is invalid (consistent with the `BatchId::Decryption` failure handling at `lib.rs:494-497`).
- Or restructure so the scalar-decode failure is recorded and the batch verification still runs before deciding whether to release the stored `EncryptionKeyProof`.

Additionally, the blame released for a *decode* failure should arguably be `None` — a non-canonical share already identifies the sender as faulty only if the message is authentic, which is exactly what the unverified PoP fails to establish.

### Proof of Concept
1. Run a PedPoP session (e.g., `n = 3, t = 2`, Ristretto). Alice sends Bob `EncryptedMessage { key: X, pop: σ_A, msg: c }` encrypting her share `f_alice(bob)`.
2. Eve (a participant) crafts `EncryptedMessage { key: X, pop: garbage, msg: random_bytes }` and sends it to Bob as her share.
3. Bob's `calculate_share` calls `decrypt`, which queues the (invalid) PoP into the batch and returns `EncryptionKeyProof { key = ecdh(bob_enc, X), dleq }` — a valid proof.
4. `c'` decrypts under `cipher(context, ecdh(bob_enc, X))` to random bytes; `from_repr` returns `None` (probability ~7/8; mutate `msg` until the error path is hit).
5. `calculate_share` returns `PedPoPError::InvalidShare { participant: Eve, blame: Some(proof) }` at `lib.rs:481` — before `batch.verify_with_vartime_blame()` at `lib.rs:493` verifies Eve's PoP.
6. Bob broadcasts `ProcessorMessage::InvalidShare { blame: Some(proof.serialize()) }`. Anyone with the proof computes `cipher(context, proof.key)` and decrypts Alice's `c`, recovering her secret share — the same disclosure the spec at `spec/cryptography/Distributed Key Generation.md:28-35` claims the PoP prevents.
