## Finding

Cosmos EVM analog identified in the precompile balance-tracking layer, where a **shared mutable "previous state" field is overwritten by a nested/recursive call**, producing exactly the same bug shape as the Rubicon report (stale state from an outer operation is silently reused/clobbered by an inner operation, corrupting the resulting balance computation).

### Title
Recursive precompile calls corrupt `BalanceHandler.prevEventsLen`, causing StateDB/bank balance desync - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
`BalanceHandler` records `prevEventsLen` in `BeforeBalanceChange` and later slices `ctx.EventManager().Events()[prevEventsLen:]` in `AfterBalanceChange` to translate bank/precisebank events into `StateDB.AddBalance`/`SubBalance` calls [1](#0-0) . When a precompile call recursively/nestedly invokes another (or the same) stateful precompile — e.g. a contract calling back into a precompile within the same EVM call — `runNativeAction` is re-entered, and depending on how the handler is threaded, the inner call's `BeforeBalanceChange` snapshot can overwrite the state relied upon by the outer call's completed operation before `AfterBalanceChange` runs for it [2](#0-1) . This is analogous to the Rubicon bug: a new operation implicitly consumes/overwrites "leftover" bookkeeping from a prior, still-in-flight operation, corrupting the derived value (there, borrow amount; here, the event-index used to compute balance deltas).

### Finding Description
This exact defect is documented and exercised by an existing integration test in the repository: [3](#0-2) 

The test drives a caller contract that recursively invokes a debug precompile (`callback`) and asserts on the resulting event/precompile-call counts [4](#0-3) , confirming the recursive-precompile-call scenario is reachable through ordinary contract execution (an unprivileged EVM call), not a privileged/administrative path.

The root mechanism:
- `BalanceHandler.BeforeBalanceChange` stores `prevEventsLen = len(ctx.EventManager().Events())` as *mutable instance state* [5](#0-4) .
- `AfterBalanceChange` uses this stored index to slice out only the events produced during "this" call and replays `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events into the EVM `StateDB` [6](#0-5) .
- `runNativeAction` creates the handler via `p.BalanceHandlerFactory.NewBalanceHandler()` and calls `BeforeBalanceChange`/`AfterBalanceChange` around the precompile's `action(ctx)` [2](#0-1) . If `action(ctx)` itself triggers another precompile invocation (nested call, e.g. via a Solidity call that re-enters a precompile, or via internal calls that share a handler/precompile instance rather than a fresh per-call one), the inner invocation's `BeforeBalanceChange` records a *new* `prevEventsLen` positioned after the outer call's own bank events have already been emitted. When control returns to the outer call and its `AfterBalanceChange` eventually executes (or when the outer/inner bookkeeping is otherwise interleaved), the event window used to reconstruct balance deltas is wrong: events belonging to the outer operation can be skipped (balance under-credited/under-debited on StateDB, but already applied at the bank level) or double counted, producing a StateDB balance that diverges from the true `x/bank`/`x/precisebank` balance.

### Impact Explanation
This directly falls under the Critical Cosmos EVM invariant of "unauthorized minting, burning, duplication, or irreversible accounting corruption ... across native balances, EVM balances ... or precompile-mediated assets." The `x/vm` StateDB balance is what all subsequent EVM logic (transfers, gas accounting, contract balance checks) operates on; once it desyncs from the ground-truth bank ledger, an attacker can construct call sequences that under-report a debit (retaining spendable EVM balance while the coin was actually spent from the bank module) or over-credit a balance (duplicating value), leading to double-spend/duplication of value or unauthorized extraction of funds through subsequent transfers based on the corrupted StateDB balance.

### Likelihood Explanation
The bug is reachable by any unprivileged user deploying a contract that makes a call which triggers nested/recursive stateful-precompile invocation (this is exactly what the existing repo test does, via a plain `MsgEthereumTx`/contract call, no special privileges required) [7](#0-6) . Any stateful precompile that uses `BalanceHandlerFactory` (distribution, erc20, gov, ics20, slashing, staking) is a candidate surface [8](#0-7) [9](#0-8) .

### Recommendation
Ensure `BalanceHandler` state (`prevEventsLen`) cannot be shared or clobbered across nested precompile invocations: allocate/scope a new handler per call frame strictly on the Go call stack (never store it on a struct field shared across recursive calls), and/or replace the "record event-manager length" approach with a stack/queue of markers so nested calls push/pop instead of overwrite. Add an invariant check that after `AfterBalanceChange`, the aggregate delta applied to `StateDB` for an address matches the aggregate bank-level delta for that address within the same EVM transaction, and fail the transaction if they diverge.

### Proof of Concept
The repository already contains a working PoC demonstrating the recursive-call scenario end-to-end (deploy caller contract → recursive `callback` into debug precompile → transaction succeeds while balance-handler bookkeeping is exercised across nested calls): [10](#0-9) . Further work is needed to extend this test with explicit bank-vs-stateDB balance assertions after the recursive call to directly capture the desync magnitude (the current test only asserts on event counts, not on the resulting balance values), since the index-range/data available did not let me fully confirm the exact numeric divergence produced.

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances
// from the module account to support fractional balance handling.
//
// As a result, even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation
// can emit an x/bank event in which the module account appears as a spender or receiver.
// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
// Instead, the state changes resulting from the precompile call are applied directly via the MultiStore.
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
