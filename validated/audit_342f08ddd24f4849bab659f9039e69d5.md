### Title
Stale Copilot conflict resolution is applied to a different conflict round on the same file path, silently corrupting merge/rebase commits - ([File: app/src/lib/stores/app-store.ts])

### Summary
`MarketController.emergencyResolveMarket` grabs a time-derived `currentEpoch` value and forwards it to the resolver without checking whether the underlying "round" it describes has already rolled over, so the wrong condition id gets a merkle root. GitHub Desktop's AI-assisted conflict resolution flow has the same broken invariant: it captures a conflict-round's resolutions (`copilotResolutions`, keyed only by file **path**) computed against one specific set of conflicted contents, then re-applies those resolutions to whatever is on disk for that same path later — without verifying that the on-disk content still belongs to the same "round" of conflicts the resolution was computed for. [1](#0-0) [2](#0-1) 

### Finding Description
`_startCopilotConflictResolution` reads the `conflictState` for the *current* step and then kicks off a long-running, network-bound LLM call (`_resolveConflictsWithCopilot` → `copilotStore.resolveConflicts`, which can involve multiple chunked requests and per-chunk timeouts up to 600s): [3](#0-2) [4](#0-3) 

The app deliberately tracks that this can take a long time — it buckets timing over 15s/30s/60s/120s: [5](#0-4) 

When the result comes back, the only staleness guards are: (1) `ownsCurrentRun()` — the resolution's `AbortController` reference still matches the live one — and (2) the wizard step is still `ShowCopilotConflictsLoading` or `ConfirmAbort` returning to it: [6](#0-5) 

Crucially, neither guard checks whether the conflicted file *content* (or the rebase/cherry-pick round it belongs to, e.g. `currentTip`/`originalBranchTip` in `IMultiCommitOperationState`) is the same content the model actually resolved. The resolutions are simply stashed and, on "Continue Merge", applied in `_applyCopilotConflictResolutions` purely by matching `resolution.path` against whatever is currently in the working directory: [7](#0-6) 

The one staleness check that exists only protects against a file the user *manually* resolved externally (no remaining conflict markers) — it does nothing to detect the case where the same path is *still conflicted* but the conflict is now a **different** one (e.g. the interactive rebase moved on to a later commit that also touches the same path, or the user aborted and restarted a merge/rebase with a different target that again conflicts on that path): [8](#0-7) 

In that scenario, `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` overwrites the file with content the model generated for a conflict that logically no longer exists, and that content is then staged and committed via `git add` immediately afterward, with no re-diff or re-validation against the new conflict markers: [9](#0-8) 

This is structurally identical to the Sherlock bug: a value (epoch / conflict-round identity) is computed once, an unbounded-duration operation elapses, and the stale value is then blindly applied to storage/state that has since moved on, guarded only by a shallow check (`isMarketReadyForResolution` always true / step-kind equality) that does not verify round identity.

### Impact Explanation
The impact matches "silent corruption of what the user commits or pushes": the resolved file content that gets staged and committed can correspond to a stale/incorrect conflict resolution rather than the actual current conflict, and the merge/rebase commit is created and can later be pushed without the user noticing, since the flow's own safeguard against clobbering user work (`hasUnresolvedConflicts` check) only detects *externally resolved* files, not *differently conflicted* files sharing a path across rounds. An attacker who controls a fetched/cloned repository can shape a branch history (e.g. multiple sequential commits in a rebase that repeatedly touch the same file, each introducing a different conflict against the victim's branch) to make this stale-round collision a real, reachable occurrence during the victim's normal rebase workflow with Copilot resolution enabled — no local access, admin rights, or social engineering beyond a normal "rebase onto attacker's branch" action is required.

### Likelihood Explanation
Triggering this requires: Copilot conflict resolution enabled, a rebase/cherry-pick over multiple commits that repeatedly conflict on the same path (fully controllable by whoever crafts the source branch/history), and the victim continuing the operation into a new conflict round while a previous round's Copilot resolution is still being applied/considered. The multi-second-to-multi-minute latency budgeted by the code itself (`copilotConflictResolutionOver120sCount`, etc.) provides a realistic window for this "round drift" to occur in ordinary interactive-rebase usage. I could not fully trace every caller that re-enters `ShowCopilotConflictsLoading` with a fresh `AbortController` versus reusing multiCommitOperationState across a "skip"/next-commit transition, so I cannot state with certainty whether the `ownsCurrentRun` guard closes every such race — this is a gap in my verification and would need to be confirmed by tracing all callers of `_startCopilotConflictResolution` and the multi-commit-operation step-machine transitions across rebase "continue"/"skip" actions in a live Desktop session.

### Recommendation
Bind each `IFileResolution` to an explicit identifier of the conflict round it was computed for (e.g. the conflicted blob OIDs/hashes for that path, or `currentTip`/`originalBranchTip` from `IMultiCommitOperationState`) at the time the request context was gathered. When applying resolutions in `_applyCopilotConflictResolutions`, recompute or re-check that identifier against the live on-disk conflict for that path before writing `resolvedContent`; if it doesn't match, treat the file as unresolved/skipped and force the user (or a fresh Copilot pass) to resolve the current conflict rather than silently applying the stale content.

### Proof of Concept
1. Enable Copilot-powered conflict resolution.
2. Craft/clone a malicious upstream branch where two separate commits both modify the same file (`shared.txt`) in ways that conflict with the victim's branch at each step of an interactive rebase.
3. Victim starts rebasing onto the malicious branch; Desktop hits conflicts on commit #1 including `shared.txt` and calls `_startCopilotConflictResolution`, capturing `conflictState` for round #1 at `app-store.ts:6928`.
4. While the (multi-second/minute) LLM call for round #1 is in flight, the round transitions (e.g. the round's UI step remains `ShowCopilotConflictsLoading`/`ConfirmAbort` due to timing, or the app is driven to re-enter the same step for the next commit's conflicts on `shared.txt` before the prior run is cleanly invalidated).
5. The stale resolution for round #1's `shared.txt` content is stored in `copilotResolutions` and, upon "Continue Merge", is written via `writeFile` at `app-store.ts:7258` over round #2's actual (different) conflict markers for the same path, then staged with `git add` at `app-store.ts:7263-7267` and committed — producing a merge/rebase commit whose `shared.txt` content never reflects the real current conflict, without any warning to the user.
