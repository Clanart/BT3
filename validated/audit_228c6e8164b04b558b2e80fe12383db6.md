### Title
OP_RETURN data output is excluded from the fee/weight calculation, so transactions underpay the requested fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` adds a caller-supplied OP_RETURN output to `tx_outs`, but `calculate_weight_vbytes` is invoked only over `payments` and `change` — it never sees the data output. `needed_fee = fee_per_vbyte * vbytes` is therefore computed on a smaller virtual size than the transaction that is actually built, signed, and broadcast.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` at lines 194–202 before any weight estimation happens. Both calls to `calculate_weight_vbytes` (lines 204 and 225–226) reconstruct a template `Transaction` whose `output` vector is built solely from `payments` plus an optional `change` output (lines 85–99). The data output is absent from that template, so `weight`/`vbytes` and hence `needed_fee` are too low.

Consequences of the stale `vbytes`:

1. `needed_fee = fee_per_vbyte * vbytes` (lines 206, 227) is lower than the fee required to achieve `fee_per_vbyte` on the real transaction.
2. The minimum-relay-fee gate at line 211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) validates against the understated `vbytes`, so a transaction can pass the check while its true feerate is below the network minimum.
3. The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses the understated `weight`.
4. When `change` is present, `change value = input_sat - payment_sat - fee_with_change` (line 228): the change output absorbs the sats that should have paid for the OP_RETURN's weight, meaning the actual fee paid equals the undercomputed `needed_fee` — the wallet silently pays a lower feerate than the caller requested.

An 80-byte OP_RETURN output adds roughly ~92 weight units (~23 vbytes) to the real transaction that are never priced. With `fee_per_vbyte` near the relay minimum, or in a fee environment where `median_fee` hovers at ~1 sat/vbyte, the effective feerate falls below `DEFAULT_MIN_RELAY_TX_FEE` and the signed transaction is rejected by relay/mempool policy or remains unconfirmed — the protocol's `Eventuality` (which is just the `txid`, per `processor/src/networks/bitcoin.rs` line 830) then has a completion that can never confirm.

### Impact Explanation
Any caller of `SignableTransaction::new` that supplies `data` causes the produced transaction to underpay relative to the specified `fee_per_vbyte`, with the shortfall proportional to the data length. Because the change calculation uses the same understated fee, the transaction is internally consistent and will be signed without error — the bug surfaces only on the network as an under-priced transaction that may be evicted or never mined, stalling the payment plan whose eventuality is bound to this txid. This is the same class as the reference finding: a fee computed against the wrong divisor/quantity, letting a transaction avoid paying the full intended fee.

### Likelihood Explanation
The `data` parameter is a direct public input to `SignableTransaction::new` (up to 80 bytes accepted at line 171). Triggering requires only passing non-empty `data`. In the in-tree processor (`processor/src/networks/bitcoin.rs` line 450) `None` is passed, so the bug is latent for the current scheduler flow, but any other consumer of the `bitcoin-serai` wallet — or a future plan carrying metadata — hits it deterministically. Since `median_fee` can be as low as 1 sat/vbyte, the effective feerate dropping ~15–20% below target is enough to fall under relay minimums for typical transaction sizes (~150–200 vbytes), making the failure realistic rather than marginal.

### Recommendation
Include the data output in the weight template: either pass the already-built `tx_outs` (or the `data` payload) into `calculate_weight_vbytes`, e.g. extend its signature to accept `data: Option<&Vec<u8>>` and push `TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) }` into the template transaction before calling `tx.weight()`. The same corrected vbytes must feed both the min-fee check and the `fee_with_change`/change-amount computation.

### Proof of Concept
```rust
// One P2TR input worth `input_sat`, one payment, no change
let data = vec![0u8; 80];
let stx = SignableTransaction::new(
  vec![output],              // ReceivedOutput
  &[(payment_script, 1000)],
  None,
  Some(data),                // OP_RETURN output added to tx_outs
  1,                         // fee_per_vbyte
).unwrap();

// needed_fee was computed over a template WITHOUT the OP_RETURN output
let declared_fee = stx.needed_fee();
let real_vsize = stx.transaction().vsize() as u64; // includes OP_RETURN, ~23 vbytes larger

// Effective feerate = declared_fee / real_vsize < 1 sat/vbyte,
// i.e. below DEFAULT_MIN_RELAY_TX_FEE, yet the TooLowFee check at
// line 211 passed because it used the understated vbytes.
assert!(declared_fee < real_vsize * 1);
```
