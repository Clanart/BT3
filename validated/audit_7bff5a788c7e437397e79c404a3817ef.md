### Title
`ThresholdKeys::new` derives the group key from only the first `t` verification shares, never validating shares `t+1..=n` or the secret share against them - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::new` validates the verification-share map only in aggregate — it checks the *count* of entries and that every `Participant` key is `<= n` — then computes `group_key` by interpolating **only the first `t` shares**. The remaining `n - t` verification shares, and the supplied `secret_share`, are never validated against the polynomial. This is the direct analog of the TraitForge bug: a check performed on the "slot" (the share map as a whole) that fails to validate each constituent element.

### Finding Description
In `ThresholdKeys::new`, the only checks on `verification_shares` are cardinality and participant-index bounds [1](#0-0) . The group key is then derived by summing `verification_shares[i] * interpolation_factor(i, [1..=t])` for `i` in `1..=t` only [2](#0-1) . Consequently:

- `verification_shares[t+1 ..= n]` are accepted completely unchecked — they are not required to lie on the same degree-`t-1` polynomial as the first `t` shares.
- `secret_share` is never checked against `verification_shares[params.i]` (`G * secret_share == share_i`).

`ThresholdKeys::read` feeds attacker-controlled bytes directly into `new`: it reads `n` arbitrary points into the map and an arbitrary scalar as `secret_share`, then calls `ThresholdKeys::new` [3](#0-2) . Just as `require(pseudoRandomValue != 999999)` validates the packed slot instead of each of the 13 entropies, `new` validates the share map's shape instead of each share's consistency with the committed polynomial.

Later, `view()` interpolates whatever shares happen to be in `included` [4](#0-3) . Because the trailing shares were never bound to the group key, a `ThresholdKeys` whose shares `> t` are off-polynomial is accepted, and different signing subsets interpolate under mutually inconsistent verification shares.

### Impact Explanation
A deserialized or otherwise externally supplied `ThresholdKeys` with inconsistent verification shares is accepted as valid. The resulting `ThresholdView`s produce signature shares whose verification shares do not correspond to `group_key`, so either (a) signatures produced with honest shares fail to reconstruct a signature valid under `group_key`, or (b) outputs received to a key derived from this set are not spendable by the claimed threshold — funds reported received that are not spendable, an accepted impact class. It also enables an inconsistent view of the participant set to persist silently, since no error is ever raised for the unvalidated shares.

### Likelihood Explanation
Reachable by any party able to feed bytes to `ThresholdKeys::read` (an explicitly in-scope untrusted-input API) or to supply `verification_shares`/`secret_share` to `ThresholdKeys::new`. Exploitation requires the integrator to accept key material over an untrusted channel; within the library itself no consistency proof exists, so the malformed set is deterministically accepted. Medium likelihood.

### Recommendation
In `ThresholdKeys::new`, validate each element rather than the aggregate:

- Verify `C::generator() * secret_share == verification_shares[&params.i]`.
- For `Interpolation::Lagrange`, verify all `n` shares are consistent with a single degree-`t-1` polynomial — e.g., check that for every `l` in `t+1..=n`, `verification_shares[l]` equals the interpolation of shares `1..=t` evaluated at `l` (or equivalently interpolate `group_key` over all `n` shares with a consistency check).
- Reject any `ThresholdKeys` where the per-share validation fails, so that the group key is bound to every constituent share, not just the first `t`.

  pub fn new(
    params: ThresholdParams,
    interpolation: Interpolation<C::F>,
    secret_share: Zeroizing<C::F>,
    verification_shares: HashMap<Participant, C::G>,
  ) -> Result<ThresholdKeys<C>, DkgError> {
    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }
