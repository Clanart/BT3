## Title
Keychain namespace confusion via ambiguous string-concatenation cache key in `KeychainServer.get_keychain_for_request` allows cross-user/service keychain access - (File: `chia/daemon/keychain_server.py`)

### Summary
The daemon's remote keychain RPC (`KeychainServer`) partitions private-key storage by a `(kc_user, kc_service)` pair, but caches the resulting `Keychain` object under a key built by naive string concatenation with no separator or length-prefixing. Two distinct `(user, service)` pairs can produce the same cache key (e.g. `user="A", service="BC"` and `user="AB", service="C"` both collapse to `"ABC"`), causing a request for one identity/service to be silently served the previously-cached `Keychain` instance that actually belongs to a different identity/service pair. This is the same bug class as CVE-2020-2228: an authorization decision keyed on a flattened/ambiguous name representation that fails to differentiate between logically distinct identities.

### Finding Description
`KeychainServer.get_keychain_for_request()` computes: [1](#0-0) 

```
key = (user or "unnamed") + (service or "")
if key in self._alt_keychains:
    keychain = self._alt_keychains[key]
else:
    keychain = Keychain(user=user, service=service)
    self._alt_keychains[key] = keychain
```

`user` and `service` are taken directly from the incoming daemon RPC request dictionary (`kc_user`, `kc_service`) in `handle_command()`: [2](#0-1) 

Because the cache key is a raw concatenation of the two strings with no delimiter, the mapping from `(user, service)` to cache key is not injective: any pair of `(user1, service1)` and `(user2, service2)` where `user1 + service1 == user2 + service2` (but `user1 != user2`) will collide. Once a `Keychain` for one pair has been cached, a subsequent request that supplies a different, colliding `(kc_user, kc_service)` pair will retrieve the *same* cached `Keychain` object rather than a keychain scoped to its own identity/service namespace. All subsequent keychain operations (`add_key`, `get_all_private_keys`, `delete_key_by_fingerprint`, `get_public_keys`, label operations, etc., dispatched via `handle_command`) then act on the wrong underlying keyring partition: [3](#0-2) 

This is directly analogous to the Jenkins GitLab plugin flaw: authorization/identity resolution collapses two distinct namespaces into one flattened string representation, letting one caller's request be serviced under another caller's identity/credentials.

### Impact Explanation
An RPC caller who can reach the daemon's keychain command surface (e.g. any local process/service that connects to the daemon websocket and issues `kc_user`/`kc_service`-bearing requests, as documented as an in-scope reachable actor — "daemon/keychain RPC authorization") can construct a colliding `(kc_user, kc_service)` pair to have its request routed to a keychain namespace it does not own. Depending on which alternate keychain was created first, this can expose another namespace's private/public keys to `get_all_private_keys`/`get_key`, or cause `add_private_key`/`delete_all_keys`/`delete_key_by_fingerprint` to mutate keys belonging to a different logical service, resulting in unauthorized key disclosure or unauthorized key deletion/overwrite — a High-impact confidentiality/integrity issue for wallet/farmer key material.

### Likelihood Explanation
Exploitation requires only the ability to open a keychain RPC session and supply attacker-chosen `kc_user`/`kc_service` values for two requests within the same daemon process lifetime, which is straightforward for any local RPC-capable caller (`KeychainProxy`/`connect_to_keychain` clients set these fields freely per request via `format_request`): [4](#0-3) 

No cryptographic material or privileged access beyond normal local daemon RPC connectivity is needed to trigger the collision, only crafting two strings whose concatenation matches.

### Recommendation
Replace the ambiguous concatenation with a collision-free composite key, e.g. a tuple `(user, service)` used directly as the dict key, or a delimiter-safe encoding such as `f"{len(user)}:{user}:{service}"`, so that distinct `(user, service)` pairs can never map to the same `_alt_keychains` entry.

### Proof of Concept
1. Caller sends a keychain RPC with `kc_user="A"`, `kc_service="BC"`, e.g. `add_private_key`. `get_keychain_for_request` computes `key = "ABC"`, creates and caches `Keychain(user="A", service="BC")` under `_alt_keychains["ABC"]`, and the key material is stored in that namespace.
2. A different caller (or the same caller impersonating a different logical identity) sends `kc_user="AB"`, `kc_service="C"` with `get_all_private_keys`. `get_keychain_for_request` computes `key = "ABC"` again, finds it already cached, and returns the *first* caller's `Keychain(user="A", service="BC")` instance instead of creating an isolated `Keychain(user="AB", service="C")`.
3. The second caller's `get_all_private_keys` response now returns keys belonging to the `user="A", service="BC"` namespace, demonstrating cross-namespace key disclosure caused by the ambiguous cache-key construction.

```python
    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
```

```python
    def format_request(self, command: str, data: dict[str, Any]) -> WsRpcMessage:
        """
        Overrides DaemonProxy.format_request() to add keychain-specific RPC params
        """
        if data is None:
            data = {}

        if self.keychain_user or self.keychain_service:
            data["kc_user"] = self.keychain_user
            data["kc_service"] = self.keychain_service
```
