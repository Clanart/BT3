### Title
`SignableTransaction::new` excludes the attacker-controlled OP_RETURN output from weight/vsize and fee accounting, producing transactions that underpay the intended fee rate and can exceed `MAX_STANDARD_TX_WEIGHT` without error - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Maia `depositGasAnycallConfig` finding — where an externally reachable deposit path reused internal logic that assumed a precondition the path never established — `SignableTransaction::new` in bitcoin-serai accepts caller-supplied `data` that becomes an extra `TxOut`, yet performs all weight, vsize, fee, and standardness accounting on the payment list alone. The data output's bytes are simply never counted.

### Finding Description
`SignableTransaction::new` pushes an OP_RETURN output containing `data` (up to 80 bytes, per the `TooMuchData` check) into `tx_outs` at `networks/bitcoin/src/wallet/send.rs:194-202`. However, `calculate_weight_vbytes` is then invoked with `payments` — not `tx_outs` — so the synthetic transaction it builds (send.rs:85-99) contains only the payment outputs plus optional change. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) is computed without the data output, understating the true virtual size.
- The `weight > MAX_STANDARD_TX_WEIGHT` check at send.rs:241 uses the understated `weight`, so a transaction whose real weight exceeds the standardness limit still returns `Ok`.
- The change amount (send.rs:228-234) is correct in value terms (the OP_RETURN carries zero value), so the discrepancy is silent — nothing detects the undercounted fee.

The `data` parameter is reachable by an unprivileged party: it originates from `OutInstruction` data attached to a burn, so an external user controls whether this output exists and its size. `make_signable_transaction`/`prepare_send` in the processor will build, sign, and eventually broadcast this transaction believing it pays `fee_per_vbyte`, when the effective fee rate is lower (worst case ~80+ bytes of unaccounted output/witness-adjacent weight, plus the output's base weight). If the requested rate was the minimum relay rate (the `TooLowFee` guard at send.rs:211 also validates against the understated vbytes), the transaction can fall below mempool acceptance or relay policy and never confirm, stalling the burn. If the real weight exceeds `MAX_STANDARD_TX_WEIGHT`, standard nodes will reject it outright.

### Impact Explanation
A user-initiated burn with `data` yields a signed transaction that cannot be relayed or confirmed at the intended fee rate (or at all, if it is non-standard). Like the Maia bug — where the erroneous `withdraw` blocked gas deposits — an accounting step applied to the wrong object silently breaks a funds-movement path: the multisig produces an invalid-for-relay transaction, freezing the associated funds until handled out-of-band. Outputs spent attempting it remain locked pending re-planning, and the protocol reports/fees a transaction that was never viable.

### Likelihood Explanation
Triggerable by any external user attaching data to a burn instruction whenever the resulting real fee rate dips below relay minimum or real weight crosses the standardness bound — deterministic for sufficiently large `data` combined with many inputs/outputs (the code explicitly allows up to 520 inputs/outputs). No collusion, key compromise, or validator misbehavior is required; only public transaction fields.

### Recommendation
Compute weight/vbytes over the actual `tx_outs` (or pass `payments` plus the data output) in `calculate_weight_vbytes` — e.g., add a `data: Option<&[u8]>` parameter so the synthetic `Transaction` includes the OP_RETURN output. This fixes `needed_fee`, the change-fee variant, the `TooLowFee` minimum-relay check, and the `MAX_STANDARD_TX_WEIGHT` standardness check simultaneously. Alternatively, include `tx_outs` directly rather than reconstructing outputs from `payments`.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte` equals the minimum relay rate (1 sat/vbyte).
2. `calculate_weight_vbytes` builds a transaction containing only payment/change outputs; the 80-byte OP_RETURN output pushed at send.rs:195-201 contributes zero to `weight`/`vbytes`.
3. `needed_fee` passes the `TooLowFee` check against the understated vbytes, and `fee()` (send.rs:138-141) still equals `needed_fee` in absolute sats — but the real transaction is ~80+ vbytes larger, so its actual fee rate is below the relay minimum and below what the caller requested; additionally, if inputs/outputs push real weight past `MAX_STANDARD_TX_WEIGHT`, the check at send.rs:241 still passes and a non-standard, unrelayable transaction is returned as valid.
