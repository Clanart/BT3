This confirms the mechanism: `DiffSelection` is a pure line-index-based bitset with no content binding (no hash, no line-content anchor) — `isSelected(lineIndex)` at [1](#0-0)  only tracks abstract integer line indices, and `withRangeSelection`/`withLineSelection` operate purely on these indices as well [2](#0-1) . Nothing in this model ties a "selected" index back to the specific line content the user visually reviewed.

The exploitable path is in `applyPatchToIndex`, which re-fetches a **fresh** diff from disk (`getWorkingDirectoryDiff`) at staging time rather than reusing the diff the user actually reviewed and selected lines against, then walks the new diff's hunks and asks the stale `file.selection.isSelected(absoluteIndex)` object whether each index is selected: [3](#0-2) . This selection object was computed by the renderer against the diff shown at click-time (see `formatPatch`'s use of `file.selection.isSelected(absoluteIndex)` over `hunk.lines`) [4](#0-3) , but by the time `createCommit` → `stageFiles` → `applyPatchToIndex` executes, `getWorkingDirectoryDiff` reads the file's *current* on-disk content, not a snapshot pinned to the moment of selection: [5](#0-4) . `stageFiles` explicitly documents that the index has just been reset and its job is to make the index "reflect what the user has selected in the app" — an invariant that assumes the diff hasn't moved since selection: [6](#0-5) .

### Title
Silent commit-content corruption via stale line-index diff selection in `applyPatchToIndex()` - (File: app/src/lib/git/apply.ts)

### Summary
GitHub Desktop's partial/line-level staging re-derives the diff from disk at the moment of `git commit`, but applies the user's line-selection bitset — captured against an earlier version of that diff — using raw positional indices with no content binding. If the working-tree file is modified between the time the user reviews/selects lines in the Changes view and the time `_commitIncludedChanges` actually executes `createCommit`, the positional indices from the stale selection get reinterpreted against the new diff's hunks, silently including or excluding different actual content than what the user saw and approved.

### Finding Description
`DiffSelection` (`app/src/models/diff/diff-selection.ts`) stores only abstract integer "line index" positions with no reference to line content or file hash: `isSelected()` [1](#0-0)  is a pure lookup into a `divergingLines` set of indices. Indices are meaningful only relative to the specific `IDiff` object that was rendered when the user made their selection (`unifiedDiffStart` positions from `raw-diff.ts`).

When the user clicks "Commit", `_commitIncludedChanges` captures `selectedFiles` (each carrying its `DiffSelection`) from the current `repositoryStateCache` and passes them into `createCommit` [7](#0-6) . `createCommit` calls `stageFiles`, which for any partially-selected file calls `applyPatchToIndex` [8](#0-7) . Critically, `applyPatchToIndex` does **not** reuse the diff the UI displayed — it calls `getWorkingDirectoryDiff(repository, file)` again, re-reading the file from the working tree at that instant [5](#0-4) , and then builds the patch via `formatPatch(file, diff)`, which walks the *new* diff's hunks/lines and asks `file.selection.isSelected(absoluteIndex)` per line [4](#0-3) . There is no check comparing the diff used at selection-time to the diff used at staging-time (unlike `updateChangesWorkingDirectoryDiff`, which explicitly re-validates state via `isSameDiff`/`isSameFile` before applying async diff results back to the UI [9](#0-8) ). No equivalent staleness guard exists on the commit-write path.

This is the same broken invariant as the LidoVault report: a decision is made ("settle for X" / "commit these exact lines") based on a state snapshot, but the actual state-changing action is executed against state read fresh at a later, non-atomic point, with nothing to detect or reject the mismatch.

### Impact Explanation
If the file content changes between UI selection and `applyPatchToIndex` execution — e.g., due to an editor auto-save/auto-format, a linter/formatter task, a file watcher, or a malicious script dropped by a freshly cloned/fetched repository (e.g. an npm `postinstall`/husky hook, or a build tool invoked as part of opening the project) that rewrites tracked files shortly after checkout — the positional line-selection is silently reapplied to unrelated content. This can cause the commit to include lines the user never reviewed/approved (or exclude ones they intended to include), corrupting what the user believes they are committing and pushing, without any error or warning being surfaced.

### Likelihood Explanation
The race window is small (renderer round-trip between diff display and commit execution) but real: Desktop's own hook interception list shows commits can take non-trivial time due to `pre-commit`/`prepare-commit-msg` hooks and `pre-auto-gc` [10](#0-9) , and any background process with write access to the working directory (an auto-formatter, a repo-provided script) can win the race deterministically by watching for the staged index state or simply rewriting on a timer. This does not require local/physical access beyond what a normal Desktop user already has — the corrupting write can originate from content the repository itself ships.

### Recommendation
Bind `DiffSelection` to the diff it was computed against (e.g., store a content hash or the exact diff text alongside the selection) and have `stageFiles`/`applyPatchToIndex` re-validate that the currently-read working directory diff matches the diff the selection was made against before applying it. If the diff has changed, refuse to stage/commit and force the UI to refresh the diff and require the user to re-confirm their selection — analogous to the recommended `expectedVaultStarted` parameter check in the original report, but implemented as "expected diff snapshot" verification.

### Proof of Concept
1. Clone/open a repository containing a file `foo.txt` with several lines, and a task (e.g. a VS Code auto-format-on-save extension, or simply a script the repo bootstraps) that will rewrite `foo.txt`'s content shortly after it's touched.
2. In GitHub Desktop, modify `foo.txt`, open the Changes diff, and select only specific lines (e.g. lines 1–3) for a partial commit, leaving the rest deselected.
3. Before clicking "Commit," or in the brief window while the commit is executing, have the concurrent process rewrite/reformat `foo.txt` on disk (changing line count/positions but keeping the file "modified").
4. Click "Commit." `applyPatchToIndex` re-reads the diff via `getWorkingDirectoryDiff` [5](#0-4)  against the new content, then reapplies the old selection's line indices to the new hunks via `formatPatch` [4](#0-3) .
5. Inspect the resulting commit: it contains different line content than what was visually selected in step 2, with no warning shown to the user.
