## Title
Silent, unconfirmed rewrite of a repository's git remote URL based on trusted GitHub API `clone_url` field - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically refreshes the GitHub metadata associated with a local repository and, as part of that refresh, will silently call `git remote set-url` on the user's `origin` remote whenever the API-reported `clone_url` differs from what the local remote currently has, with no user prompt or notification of any kind.

### Finding Description
When Desktop refreshes a repository's associated GitHub metadata (`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts:4874-4914`), it fetches the repository object from the API (`api.fetchRepository(owner, name)`) and, if the local repo already has an associated `gitHubRepository`, unconditionally calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [1](#0-0) 

`updateRemoteUrl` then compares the previously cached `gitHubRepository.cloneURL` against the current default remote, and if the API's `clone_url` differs (but "protocol" still matches), it silently rewrites the remote with `gitStore.setRemoteURL(...)`, which calls `git remote set-url`: [2](#0-1) [3](#0-2) 

This is functionally the same "administrator changes a security-relevant parameter with no warning/time-lock" pattern flagged in the source report: a value that governs where the user's future `git push`/`git fetch` traffic (and, for HTTPS remotes, git credential-helper credentials) goes is changed by a value fully controlled by an external, untrusted party (whoever controls the response to `GET /repos/{owner}/{name}` for the endpoint this repository is associated with — GitHub.com or, more realistically, a GitHub Enterprise Server instance/proxy the user is pointed at) — with **no time delay, no diff shown to the user, and no confirmation dialog**. Compare this to the sibling case in the same codebase, `updateExistingUpstreamRemote`/`UpstreamAlreadyExists`, where an analogous remote-URL change (updating the `upstream` remote to a new parent URL) is explicitly gated behind a warning dialog asking the user to confirm ("Update" vs "Ignore"): [4](#0-3) 

No such gate exists for the `origin`/default remote update path. The only guards in `updateRemoteUrl` are: (1) the new URL's `URL.parse` protocol must equal the old URL's protocol, and (2) the *previous* cached `cloneURL` must still match the current remote (i.e., the user hasn't manually changed it). Neither guard validates the *host* or *owner/repo* of the incoming URL — an API response that swaps `clone_url` from `https://github.com/owner/repo` to `https://github.com/attacker/evil-repo` (same protocol) passes both checks and is applied.

### Impact Explanation
If the API endpoint associated with the repository (particularly a self-hosted/enterprise endpoint reachable via a network path an attacker can influence, e.g. a malicious/compromised proxy or GHES instance) returns a `clone_url` pointing elsewhere, Desktop will silently repoint the user's `origin` remote to that URL. Subsequent user-initiated `git push` operations would then push commits — and, for HTTPS remotes, cause the git credential helper to present the user's stored token/credentials — to the attacker-controlled host, without any visual indication in the UI that the destination changed. This satisfies both "silent corruption of what the user commits or pushes" and potential "credential/token exfiltration" impact categories.

### Likelihood Explanation
This refresh path (`repositoryWithRefreshedGitHubRepository`) runs automatically on background repository refresh, not only on explicit user action, so it does not require unusual user steps — it fires whenever Desktop periodically re-fetches repository metadata for a tracked repository. The precondition is that the attacker can control what `api.fetchRepository(owner, name)` returns for the endpoint bound to that repository, which is realistic for a compromised/rogue GitHub Enterprise Server or an on-path proxy/MITM of API traffic — squarely within the "attacker controls...a git remote/proxy response" or "a GitHub API object" categories called out as valid impact. It does not require local/physical access, admin rights, prior malware, or leaked credentials.

### Recommendation
Never silently rewrite an existing remote URL based on API data alone. At minimum:
- Require explicit user confirmation before changing `origin`'s URL, mirroring the existing `UpstreamAlreadyExists` dialog pattern already used for the `upstream` remote.
- Validate that the new URL's host/owner is consistent with the expected endpoint before considering it a "safe" update, not just that the URL scheme/protocol matches.
- Log/surface the change prominently in the UI so users can detect unexpected remote changes.

### Proof of Concept
1. Attacker controls (or MITMs/compromises) the GitHub Enterprise Server / proxy endpoint that a victim's Desktop-tracked repository is configured against, or otherwise controls the API response for `GET /repos/{owner}/{name}`.
2. Victim has the repository open in Desktop; Desktop performs its periodic background refresh, calling `repositoryWithRefreshedGitHubRepository` → `api.fetchRepository(owner, name)`.
3. Attacker's API response sets `clone_url` to `https://<same-scheme>/attacker/evil-repo` (same URL scheme as the original, so the protocol check passes) while the victim has not locally modified the remote (so the "remote unchanged" check passes).
4. `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:42-44`) calls `gitStore.setRemoteURL` → `git remote set-url origin https://.../attacker/evil-repo` with no prompt shown to the user, as demonstrated by the existing unit test asserting the URL is changed unconditionally when `clone_url` differs: `app/test/unit/stores/updates/update-remote-url-test.ts:68-81`.
5. Victim's next `git push` sends commits (and HTTPS credentials via the credential helper) to the attacker-controlled remote. [5](#0-4)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

/** Changes the URL for the remote that matches the given name  */
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
