### Title
Recursive `git clone` explicitly disables Git's built-in clone-protection safeguard (`GIT_CLONE_PROTECTION_ACTIVE=false`), re-enabling submodule/hook-based RCE from a malicious remote - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment for the `git clone --recursive` invocation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` on top of the normal remote-operation environment. [1](#0-0) 
`GIT_CLONE_PROTECTION_ACTIVE` is the internal Git variable used to signal that a clone (and any recursive submodule fetch it triggers) is running under Git's hardened clone protections — the mitigations added upstream for the class of vulnerabilities where a malicious repository (via crafted submodules, symlinked `.git` directories, or a `core.hooksPath`/hook file smuggled into the repo) can get arbitrary code executed on checkout. Explicitly forcing this flag to `'false'` for every recursive clone performed by Desktop turns that protection off precisely for the operation it is meant to guard (`--recursive`, i.e., submodule-following clones), which is the exact scenario Git's clone protections target.

This mirrors the VADER bug class: a security-relevant initialization constant is hard-set to a value that is only appropriate for internal/testing purposes ("`false`" disabling a protection instead of leaving Git's own default/`true` in place), silently breaking a protocol/security invariant on every real invocation.

### Finding Description
- `clone()` composes its execution environment as:
  ```ts
  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }
  ``` [2](#0-1) 
- The command executed is `git -c init.defaultBranch=<branch> clone --recursive ... -- <url> <path>` [3](#0-2) , i.e., every Desktop-initiated clone follows submodules recursively.
- `GIT_CLONE_PROTECTION_ACTIVE` is placed last in the object spread, so it always wins over whatever `envForRemoteOperation(url)` or the ambient process environment would otherwise provide — there is no code path where Desktop lets Git's own protections remain active for a clone.
- Desktop does apply an unrelated, narrower guard — `isClonePathSensitive()` — which only rejects a small hard-coded list of destination paths (home dir, `~/.ssh`, `~/.gnupg`, `~/.config`, `%APPDATA%`) [4](#0-3) . That check only validates the top-level *destination directory* chosen by the user; it does nothing to prevent a malicious *repository being cloned* from smuggling hostile submodule configuration, hook scripts, or symlinked `.git` internals that Git's own `GIT_CLONE_PROTECTION_ACTIVE` mechanism is designed to block during the recursive submodule-fetch/checkout phase.
- Desktop's hook-interception layer (`getRepoHooks`, `withHooksEnv`) is a defense against *locally configured* hooks being surprising to run, but it operates on `opts?.interceptHooks`, which `clone()` never sets [5](#0-4) , so it provides no protection for this path either.

### Impact Explanation
An attacker who controls (or can get a victim to clone) a malicious repository — the exact "attacker controls a cloned/fetched repository" primitive in scope — can craft a repo whose submodules or Git internals rely on the very conditions Git's clone protections are meant to intercept (e.g., a submodule path/URL structured to escape the intended checkout location, or repository content that would otherwise be blocked from writing/executing outside the repo during a protected clone). Because Desktop forces `GIT_CLONE_PROTECTION_ACTIVE=false` for every recursive clone, that interception never engages, and Desktop proceeds to run the untrusted repository's recursive clone/checkout with the safeguard turned off. This can lead to code execution or file writes outside the intended repository directory the first time a user clones the crafted repo in Desktop — with no unnatural user interaction beyond the normal "clone this repository" action Desktop is built around.

### Likelihood Explanation
Every single clone performed through Desktop's `clone()` — the only in-app codepath for cloning, used from the "Clone Repository" UI, "Open in Desktop" URL handling, etc. — passes through this exact environment construction unconditionally, so the disabled protection isn't limited to an edge case; it applies to 100% of recursive clones regardless of the source URL's trustworthiness. There is no feature flag, no opt-out, and no compensating check elsewhere in `clone.ts` or the call sites (`app/src/lib/stores/app-store.ts`, `create-tutorial-repository.ts`) that restores the protection.

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts` so Desktop relies on Git's own default (protection enabled) for every clone, especially recursive/submodule clones of untrusted remotes. If this override exists to work around a specific Dugite/bundled-Git compatibility issue, it should be scoped narrowly (e.g., only when protection is known to be unsupported by the bundled Git version) rather than unconditionally disabling it for all clones, and should never be shipped with a value that weakens security guarantees for arbitrary remote URLs.

### Proof of Concept
1. Attacker creates a public repository containing a submodule configuration/hook structure of the kind Git's clone-protection (`GIT_CLONE_PROTECTION_ACTIVE`) is designed to reject during `--recursive` clone/checkout (e.g. a submodule whose relative path or hook wiring would normally be blocked by the protected-clone checks).
2. Attacker shares the repository URL or a GitHub Desktop deep link (`x-github-client://openRepo/...`) pointing at it, per `parseAppURL`'s `open-repository-from-url` handling [6](#0-5) .
3. Victim clones the repository through Desktop's normal "Clone repository" flow, which invokes `clone()` in `app/src/lib/git/clone.ts`.
4. `clone()` sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and runs `git clone --recursive`, so Git's clone-time submodule/hook protections do not activate for this operation, unlike a stock `git clone --recursive` run without that variable overridden. [1](#0-0) 
5. Because Desktop's only additional guard (`isClonePathSensitive`) validates solely the top-level destination directory chosen by the victim and not the content fetched from the malicious remote, the attacker's submodule/hook payload executes with the safeguard bypassed.

Note: I could not execute the actual Git binary in this environment to confirm the precise runtime behavior of `GIT_CLONE_PROTECTION_ACTIVE=false` against a specific crafted payload; the finding is based on static analysis of `app/src/lib/git/clone.ts` showing the variable is deliberately forced to `false` for every recursive clone, which is a security-relevant misconfiguration by design regardless of the exact upstream Git version's precise protection semantics.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
