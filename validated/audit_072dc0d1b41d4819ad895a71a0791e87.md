### Title
Stale line-selection indices are re-applied against a freshly re-fetched diff during partial-commit patch generation, silently changing what gets committed - (File: `app/src/lib/git/apply.ts`)

### Summary
The external report describes a value (`releaseRate`) that is recomputed without accounting for state that changed since the user's last interaction (`amountClaimed`/`stepsClaimed`), letting a user claim more than intended. The Desktop analog is `applyPatchToIndex` re-deriving the diff fresh from disk at commit time while reusing a `DiffSelection` object whose `divergingLines` were computed as absolute line indices against a *different, earlier* diff of the same file.

### Finding Description
`stageFiles` in `app/src/lib/git/update-index.ts` calls `applyPatchToIndex` for every file with a partial selection [1](#0-0) . Inside `applyPatchToIndex`, the working-directory diff is **re-fetched from the current on-disk file state** immediately before building the patch: [2](#0-1) 

The `file` object passed in, however, carries a `DiffSelection` whose selected/deselected lines are stored as a `Set<number>` of *absolute diff-line indices* (`divergingLines`), computed earlier against whatever diff was rendered in the UI at the time the user made their selection [3](#0-2) . `formatPatch` then walks the newly-fetched diff's hunks and calls `file.selection.isSelected(absoluteIndex)` purely by numeric index, with no check that the line at that index is the same logical line the user actually selected [4](#0-3) .

The app does have logic elsewhere (`updateChangesWorkingDirectoryDiff` in `app-store.ts`) that reconciles selection state against a newly-loaded diff by recomputing `selectableLines` and dropping selections on lines that no longer exist [5](#0-4) . But that reconciliation only runs when the UI proactively reloads the diff for display (e.g., on file selection change or a background status refresh) — it is **not** re-run inside the actual commit path. `applyPatchToIndex` calls `getWorkingDirectoryDiff` directly and hands the result straight to `formatPatch` with the *original* `file.selection`, bypassing the reconciliation/validation step entirely.

If the on-disk content of a file changes between the moment the UI diff was rendered (and the user made a partial line selection) and the moment `stageFiles`/`applyPatchToIndex` runs (e.g., because a git filter/smudge script, a checkout-triggered hook, or an external process controlled by content from a fetched/cloned repository rewrites the file in that window), the hunk layout and `unifiedDiffStart` offsets shift. The stale absolute indices in `divergingLines` no longer correspond to the same logical lines they did when selected. `isSelected()`/`isRangeSelected()` will happily return true/false for whatever line now occupies that index in the new diff [6](#0-5) , and `formatPatch` will build a patch that stages content the user never reviewed or intended, or fails to include content that will be discarded from the working tree state — a real, currently existing gap between the "reload diff" reconciliation path and the "commit" path.

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits primitive: a repository-side actor able to influence a checked-out working tree between diff render and commit apply (via clean/smudge filters, checkout hooks, or any repository-configured content transform triggered by fetched/cloned content) can cause the user to commit and subsequently push lines they never selected, or omit lines they did select, without any error surfaced (`formatPatch` only throws if the resulting patch is completely empty [7](#0-6) , not if it diverges from intent). This matches the report's category of "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Exploitation requires a narrow timing window between the UI's cached diff/selection and the commit-time re-diff, and a mechanism to mutate the working tree file content in that window (e.g., attacker-controlled git filters/hooks configured by the cloned repository, which Desktop does execute git operations against). This is a real, narrow race rather than a straightforward one-shot exploit, and I was not able to fully trace the exact commit dispatcher entry point (`_commit`/`_commitIncludedChanges`) in the indexed portion of `app-store.ts` to confirm whether any additional freshness check happens between "Commit" click and `stageFiles` being invoked — this is an area where the codebase index may be incomplete. A full confirmation would need to trace `Dispatcher.commitIncludedChanges` → `AppStore._commit*` → `createCommit` → `stageFiles` end-to-end, which requires the full file contents.

### Recommendation
Before consuming `file.selection` in `applyPatchToIndex`/`formatPatch`, re-validate the selection against the freshly-fetched diff the same way `updateChangesWorkingDirectoryDiff` does (recompute `selectableLines` from the new diff and intersect/drop any `divergingLines` that reference lines whose content or hunk position has shifted), or key selections by line content/hash rather than raw absolute index so a changed diff cannot silently remap a selection onto unrelated lines. At minimum, detect diff-shape mismatches (hunk count/offsets differing from what was last displayed) and abort the commit with an explicit "changes updated, please re-review" error rather than silently proceeding.

### Proof of Concept
Conceptual reproduction path (I could not execute this against the indexed code, only trace it structurally):
1. User opens a modified file in Desktop and selects only lines 1–5 for commit (via UI, producing a `DiffSelection` with `divergingLines` = indices for lines 1–5 against diff D1).
2. Before clicking "Commit," a git `clean`/`smudge` filter or checkout hook configured in the repository (attacker-controlled, since it ships with the cloned repo's `.gitattributes`/hooks) rewrites the file on disk, shifting hunk boundaries (diff D2).
3. User clicks Commit. `stageFiles` → `applyPatchToIndex` re-fetches the diff (now D2) via `getWorkingDirectoryDiff` [8](#0-7)  but reuses the stale `DiffSelection` computed against D1.
4. `formatPatch` applies `isSelected(absoluteIndex)` against D2's hunks [9](#0-8) , staging different lines than the user visually reviewed and approved, with no warning to the user.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
