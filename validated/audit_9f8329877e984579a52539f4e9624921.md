### Title
Attacker-controlled participant count in `ThresholdKeys::read` forces multi-megabyte allocation and O(n) deserialization work from a handful of bytes — (`crypto/dkg/src/lib.rs`)

### Summary
`ThresholdKeys::<C>::read` trusts the attacker-supplied `n` field (`u16`, up to 65535) to size a `Vec::with_capacity` for `Interpolation::Constant` coefficients and to drive `n` iterations of `read_F`/`read_G` into a `HashMap`. A ~9-byte prefix is sufficient to trigger a ~2 MB allocation and, with a moderately sized message, tens of thousands of scalar/point deserializations plus interpolation evaluation in `ThresholdKeys::new`. Unprivileged parties can feed these bytes via the reachable `ThresholdKeys::read` / `Commitments::read` / `read_preprocess` paths, making repeated messages a memory- and CPU-exhaustion vector — the direct analog of the SpEL crafted-input DoS class.

### Finding Description
In `crypto/dkg/src/lib.rs:591-630`:

```rust
let (t, n, i) = (read_u16()?, read_u16()?, Participant::new(read_u16()?)...);
...
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));   // n up to 65535, attacker-controlled
  for _ in 0 .. n { res.push(C::read_F(reader)?); }
  res
}),
...
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, C::read_G(reader)?);
}
ThresholdKeys::new(ThresholdParams::new(t, n, i)..., interpolation, secret_share, verification_shares)
```

- `n` is a raw `u16` taken straight from the stream; there is no sanity cap before `Vec::with_capacity(usize::from(n))` (line 608). Each element is a field element (`≥32` bytes), so a declared `n = 65535` reserves ~2 MB before a single byte of the claimed data has been validated to exist.
- The subsequent loops perform up to `n` `read_F` calls and `n` `read_G` calls (lines 609-610, 621-622), and `ThresholdKeys::new` then runs interpolation/group-key derivation over participants `1..=n`, an O(n) multi-scalar workload per message.
- The sibling pattern is defended elsewhere in the codebase precisely because of this bug class — e.g., `networks/ethereum/src/machine.rs:51-60` reads attacker-claimed lengths in 1 KB chunks "to only read data actually present", and `coordinator/src/tributary/transaction.rs:286` enforces `TRANSACTION_SIZE_LIMIT` before allocating. `ThresholdKeys::read` has no equivalent guard. The same attacker-controlled-count pattern exists in `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:78-87`), which loops `u32` times over `read_G` with no count limit (though there it is input-length bound).

### Impact Explanation
A remote unauthenticated party that can deliver bytes to any `ThresholdKeys::read` (or caller that wraps it, e.g., DKG message handling reading `EncryptionKeyMessage`/`Commitments` which similarly scale with `ThresholdParams`) can, per ~9 bytes sent, force a ~2 MB heap reservation and up to ~65k point deserializations and an O(n) interpolation. Repeated messages amplify memory pressure and CPU burn on the victim signer/processor, degrading or crashing the signing process — availability loss for the threshold key holder, directly analogous to the crafted-expression DoS in CVE-2024-38808 where a small crafted input causes disproportionate evaluation cost.

### Likelihood Explanation
Reachability is real: the rules explicitly consider untrusted bytes passed to `ThresholdKeys::read` in scope, and the reader APIs are the boundary used to deserialize keys and DKG material received from other (potentially malicious-by-input) parties. The only mitigating factor is that the bulk of the work (the `n` reads) requires the attacker to actually ship ~`n * repr_len` bytes, so sustained impact requires repeated small-prefix allocations (cheap) plus optional large bodies. The `with_capacity` amplification (~340× bytes-to-allocation) is reachable with a tiny input alone. Medium severity per the CVSS 4.3 profile of the source advisory.

### Recommendation
- Validate `n` (and `t`) against a protocol maximum before allocating: reject `n` above the real threshold bound, or derive the count from already-buffered input length rather than a claimed field.
- Replace `Vec::with_capacity(usize::from(n))` with incremental `push`es (no pre-reservation on claimed length), matching the chunked-read approach used in `Call::read` (`networks/ethereum/src/machine.rs:54-60`).
- Optionally cap the number of `read_F`/`read_G` iterations based on remaining reader length for `&[u8]` readers.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;
// For a curve C (e.g., Ristretto):
let mut bytes = vec![];
// curve ID header
bytes.extend_from_slice(&(C::ID.len() as u32).to_le_bytes());
bytes.extend_from_slice(C::ID.as_bytes());
// t = 1, n = 65535, i = 1
bytes.extend_from_slice(&1u16.to_le_bytes());
bytes.extend_from_slice(&u16::MAX.to_le_bytes());
bytes.extend_from_slice(&1u16.to_le_bytes());
// interpolation = 0 (Constant) -> Vec::with_capacity(65535) executes here
bytes.push(0);
// No further bytes needed: the ~2 MB allocation happens before the first read_F fails.
let _ = ThresholdKeys::<C>::read(&mut Cursor::new(bytes));
```
Each invocation allocates ~2 MB from a ~15-byte input; a loop of such messages forces repeated large reservations (`Vec` growth/zeroing on reuse) and, when the attacker does supply the bodies, ~65k `read_F`/`read_G` deserializations plus O(n) interpolation inside `ThresholdKeys::new` per message.
