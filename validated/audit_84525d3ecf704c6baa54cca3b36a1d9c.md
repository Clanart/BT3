### Title
Untrusted participant index in PedPoP blame evaluation panics via `HashMap` indexing (denial of service) - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2025-61100 (a NULL dereference triggered by malformed input reaching a code path that assumes the looked-up object exists), Serai's PedPoP DKG blame path indexes `HashMap`s with participant indices taken from an accusation, without checking they are within `1..=n`. `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` evaluates `self.commitments[&sender]`; `HashMap`'s `Index` impl panics on a missing key. An unprivileged participant can crash any node evaluating their blame accusation by naming a `sender` or `recipient` outside the actual participant set.

### Finding Description
`EncryptedMessage`/`EncryptionKeyProof` are deserialized from peer bytes via `EncryptedMessage::read` and `EncryptionKeyProof::read`, and the blame API (`AdditionalBlameMachine::new` → `blame` → `blame_internal` → `decrypt_with_proof`) accepts `sender`/`recipient` `Participant` values from the accusation. `Participant::new` only rejects zero; any nonzero `u16` is accepted. `AdditionalBlameMachine::new` registers encryption keys only for `1..=n` (pedpop/src/lib.rs:656-660), and `KeyMachine::calculate_share` populates `commitments` only for actual participants. Neither `blame` nor `blame_internal` bounds-checks `sender`/`recipient` against `n`.

Two panic sites:
- `self.enc_keys[&decryptor]` at encryption.rs:388 — reached when `proof` is `Some` and the message PoP verifies (the attacker can trivially produce a self-signed `EncryptedMessage` whose `pop` verifies under their own key).
- `self.commitments[&sender]` at pedpop/src/lib.rs:599 — reached when decryption-with-proof succeeds, if `sender ∉ 1..=n`.

### Impact Explanation
A malicious or even merely misconfigured accuser can abort the DKG/blame-arbitration process by causing a panic in victim nodes. Because `AdditionalBlameMachine` is explicitly designed to let arbitrary third parties ("capable of evaluating blame regardless of if the caller was a member in the DKG protocol") evaluate accusations over public, attacker-supplied messages and participant indices, this is reachable by an unprivileged party with public inputs — the exact shape of the CVE (malformed input → NULL/missing-object dereference → DoS). A panic during blame resolution also prevents the protocol from identifying the genuinely faulty party, stalling the key generation.

### Likelihood Explanation
Triggering requires only submitting a blame evaluation request (or being relayed one) with a syntactically valid `Participant` value greater than `n` or otherwise unregistered, plus a `Some(proof)` where required. No cryptographic forgery is needed: `Participant::new` accepts every nonzero `u16`, and the message PoP can be honestly generated by the attacker for their own key. The only mitigating factor is that the panic occurs in blame handling rather than the hot path, and depends on the integrator exposing blame evaluation to unvalidated indices.

### Recommendation
Replace `HashMap` indexing with fallible lookups and validate indices before use:
- In `Decryption::decrypt_with_proof` (encryption.rs:388), use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` instead of `self.enc_keys[&decryptor]`.
- In `BlameMachine::blame_internal` (pedpop/src/lib.rs:599), use `self.commitments.get(&sender)` and treat a missing entry as a fault/return value rather than panicking.
- At the `blame`/`AdditionalBlameMachine::blame` API boundary, reject `sender`/`recipient` values not present in the registered commitment/encryption-key sets.

### Proof of Concept
```rust
// Setup: 2-of-2 DKG completed; arbitrator builds an AdditionalBlameMachine
let machine = AdditionalBlameMachine::<Ed25519>::new(context, 2, commitment_msgs).unwrap();

// Attacker submits an accusation with a recipient index that was never in the DKG.
// Participant::new accepts any nonzero u16.
let evil_recipient = Participant::new(7).unwrap(); // > n = 2
let sender = Participant::new(1).unwrap();

// Attacker crafts a valid EncryptedMessage they signed themselves and Some(proof)
// so decrypt_with_proof reaches `self.enc_keys[&decryptor]`.
let msg: EncryptedMessage<Ed25519, SecretShare<Scalar>> = /* attacker-built, valid pop */;
let proof = Some(attacker_proof); // contents irrelevant: map index panics first

// Panics: `self.enc_keys[&decryptor]` -> "key not found" -> process abort
machine.blame(sender, evil_recipient, msg, proof);
```
Same crash via `sender`: pass a valid `recipient` in `1..=n` with a working proof, but `sender = Participant::new(9)`, reaching `self.commitments[&sender]` at pedpop/src/lib.rs:599.

Note: I could not fully trace how the in-tree processor wires accusation fields into `blame`, so the precise framing of who supplies `sender`/`recipient` in production is inferred from the API contract (arguments are per-accusation and explicitly caller-supplied). The panic itself is unconditional once such an index reaches the function.
