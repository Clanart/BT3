### Title
False success acceptance on GET response/timeout delivery to non-contract `from` address enables spurious relayer fee payout and unrecoverable receipt state - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(PostRequest, ...)` explicitly checks that the destination module has code (`extcodesize`) before attempting the `onAccept` callback, and treats a non-contract destination as an early no-op return [3](#0-2) . The analogous delivery paths for GET responses and both timeout variants — `dispatchIncoming(GetResponse, ...)`, `dispatchTimeOut(GetRequestTimeout, ...)`, and `dispatchTimeOut(PostRequestTimeout, ...)` — omit this check entirely and instead perform a raw `.call()` directly to `_bytesToAddress(request.from)` [4](#0-3) . A low-level `.call()` in Solidity to an address with no deployed code always returns `success == true` (it is a no-op value/data transfer), so these three functions unconditionally treat delivery to a non-contract address as a successful application callback, releasing relayer fee refunds and permanently finalizing the request/response receipt even though no `IApp` callback logic ever ran.

### Finding Description
The `from` field of both `PostRequest` and `GetRequest` is populated directly from `_msgSender()` with no contract-code check at dispatch time [1](#0-0) [2](#0-1) . Nothing in `dispatch(DispatchGet)` or `dispatch(DispatchPost)` restricts the caller to be a smart contract implementing `IApp`; any EOA can call these functions directly.

When a relayer later submits the corresponding GET response or a timeout proof, the handler invokes one of:
- `dispatchIncoming(GetResponse memory response, address relayer)` [5](#0-4) 
- `dispatchTimeOut(GetRequestTimeout memory timeout, ...)` [6](#0-5) 
- `dispatchTimeOut(PostRequestTimeout memory timeout, ...)` [7](#0-6) 

Each of these stores/deletes replay-protection state first, then does `_bytesToAddress(request.from).call(abi.encodeWithSelector(...))` and checks only `success`. Because a `.call()` to an address without code trivially succeeds, `success` is always `true` when `from` is an EOA or a self-destructed contract. This is functionally identical to the reported bug class: an unchecked external call to an address that does not implement the expected callback interface is treated as a valid execution rather than being rejected up front, exactly the invariant the `dispatchIncoming(PostRequest,...)` function already defends against with its `extcodesize` guard [3](#0-2) .

The consequence differs by path:
- `dispatchIncoming(GetResponse,...)`: the relayer fee stored in `_requestCommitments[commitment].fee` is transferred to `relayer` even though the destination app was never actually notified [8](#0-7) . The `_responseReceipts` entry is permanently finalized, so the response can never be legitimately retried/redelivered to fix the missed callback.
- `dispatchTimeOut(GetRequestTimeout,...)` / `dispatchTimeOut(PostRequestTimeout,...)`: the fee refund goes to `meta.sender` unconditionally once the trivial "success" is observed, and `_requestCommitments[commitment]` is deleted permanently — the corresponding source-side "notify module of timeout" logic is treated as complete even though it never executed [9](#0-8) [10](#0-9) .

### Impact Explanation
This breaks the "requests/responses/timeouts must resolve exactly once, correctly, to the rightful party" invariant that the codebase itself enforces for the POST-accept path. An unprivileged actor can originate a GET request (or a POST request from an address that later has no code, e.g. by dispatching from an EOA or a contract that self-destructs before delivery) so that its `from` is not a contract. Delivery of the response/timeout then always "succeeds" from the Host's perspective:
- Receipts are finalized despite the module never being notified, silently corrupting the request lifecycle bookkeeping and preventing the natural retry mechanism (`delete` on failure) from ever engaging, since `success` never reports `false` for this class of address.
- Relayer fees are paid out for requests whose destination logic was never executed, which is an economic payout that should not have been released under the documented request-lifecycle guarantees.

### Likelihood Explanation
Likelihood is limited by the fact that `from` is `_msgSender()` at origination time — an ordinary contract-to-contract application flow would populate `from` with a valid `IApp` contract. However, nothing in `dispatch(DispatchPost)`/`dispatch(DispatchGet)` enforces that the caller is a contract implementing `IApp`, so any EOA (or any contract without an `onGetResponse`/`onGetTimeout`/`onPostRequestTimeout` implementation, or one that later self-destructs) can trigger this path with a single ordinary dispatch call plus relayer-driven delivery — no privileged role, malicious relayer, or forged proof is required.

### Recommendation
Add the same `extcodesize`/interface-support check that `dispatchIncoming(PostRequest,...)` already performs to `dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(GetRequestTimeout,...)`, and `dispatchTimeOut(PostRequestTimeout,...)`, before finalizing receipts or releasing fees, so that delivery to a non-contract `from` address is treated as a no-op/retryable failure rather than a false success. Optionally, also enforce at `dispatch(DispatchPost)`/`dispatch(DispatchGet)` time that `_msgSender()` has code, consistent with the report's recommendation to validate the counterparty address both at "construction" (dispatch) time and at execution time.

### Proof of Concept
1. From an EOA (or a throwaway contract with no fallback logic implementing `IApp`), call `EvmHost.dispatch(DispatchGet)` — this sets `request.from = abi.encodePacked(_msgSender())` with a fee attached [11](#0-10) .
2. Let the GET request either receive a response or time out; a relayer submits the corresponding proof through the handler, which calls `EvmHost.dispatchIncoming(GetResponse,...)` or `EvmHost.dispatchTimeOut(GetRequestTimeout,...)`.
3. Inside the Host, `_bytesToAddress(response.request.from).call(...)` targets the EOA; since it has no code, the call returns `success == true` trivially [12](#0-11) .
4. The relayer fee is paid out and the receipt is finalized as if the destination module correctly processed the response, even though no `onGetResponse`/`onGetTimeout` logic ever ran — the request lifecycle is marked complete despite delivering to a non-existent callback target, in contrast to the guarded `dispatchIncoming(PostRequest,...)` path which would have safely no-op'd instead.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
