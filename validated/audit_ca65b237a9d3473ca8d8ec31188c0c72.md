### Title
Manual conflict resolutions (`ours`/`theirs`) survive a merge→rebase (or rebase→merge) transition and get silently applied with inverted git-side semantics - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`RewardsEngine` cleared `unitsAccrued` on exclusion but left the paired `rewardDebt` baseline stale, corrupting subsequent reward math. GitHub Desktop has the same "clear one half of a paired state, forget the other" pattern in `updateConflictState`: it clears/rebuilds `conflictState.kind`/`currentTip`/branch fields when the underlying git operation changes, but the `manualResolutions` map — which is *meaning-dependent on the operation kind* (`ours`/`theirs` invert between merge and rebase, per `app/src/lib/git/diff.ts#L430-434`) — is carried forward untouched.

### Finding Description
`updateConflictState` (`app/src/lib/stores/updates/changes-state.ts#L263-292`) unconditionally reuses the previous `manualResolutions` Map when computing the new conflict state: [1](#0-0) 
regardless of whether `prevConflictState.kind` (`'merge'`, `'rebase'`, `'cherryPick'`) matches `newConflictState.kind`. `getConflictState` then bakes this map straight into the new state object: [2](#0-1) 
When the kinds actually differ (e.g. the working directory transitions from an in-progress merge to an in-progress rebase — reachable simply by the user aborting a merge and starting a rebase, or by any external `git` invocation changing `MERGE_HEAD`/`REBASE_HEAD` state while Desktop is polling status), `updateConflictState`'s own comment admits this is unhandled: "Otherwise we transitioned from a merge conflict to a rebase conflict or vice versa, and we should avoid any side effects here" — yet it still returns `newConflictState` carrying the stale `manualResolutions`: [3](#0-2) 

That stale map is later consumed verbatim by `_finishConflictedMerge`/`createMergeCommit` or `continueRebase`, which call `stageManualConflictResolution` for every `(path, resolution)` pair: [4](#0-3) 
`stageManualConflictResolution` resolves `theirs`/`ours` directly to `status.entry.them`/`status.entry.us` with no awareness of which operation produced the resolution. But `app/src/lib/git/diff.ts` explicitly documents that git swaps the ours/theirs sides between merge and rebase: [5](#0-4) 
So a resolution chosen by the user while looking at a **merge** conflict diff (e.g. "keep theirs" meaning the incoming feature branch content) is silently reapplied, unreviewed, to the same file path once the operation has become a **rebase**, where "theirs" now means the opposite side (the commit being replayed instead of upstream). No re-diffing, re-prompting, or invalidation occurs — `_updateManualConflictResolution` (`app/src/lib/stores/app-store.ts#L8796-8828`) only merges the map, it never clears it on a kind change, and `updateMultiCommitOperationStateAfterManualResolution` only checks that `conflictState !== null`, not that its `kind` still matches what the user resolved against.

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits bug: the content actually staged and committed via `createMergeCommit`/`continueRebase` can differ from the side the user consciously selected in the UI, because the semantic meaning of the recorded choice ("ours"/"theirs") inverted between when it was chosen and when it was applied. The user has no visual indication that their earlier per-file choice is being reused against a different operation. Because this directly determines file content baked into a commit, and that commit is typically pushed afterward, it satisfies "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Medium-low likelihood in practice: it requires the working directory's conflict *kind* to change while a manual resolution is already recorded for the same file path across the transition (e.g., merge conflicts → user aborts and rebases, or a background/CLI git operation switches the in-progress operation type while Desktop is polling status). Desktop's own status polling loop calls `updateConflictState` repeatedly, so the window is not purely theoretical, but it does depend on an unusual sequence rather than a single simple click. No repository content or remote attacker input is directly required to *trigger* it — this is a self-inflicted state-machine bug — which is why it is presented as a state-invariant defect rather than a remote-attacker-controlled exploit; I was not able to fully verify from the indexed code whether the UI additionally blocks starting a new operation while `manualResolutions` is non-empty, which could mitigate real-world reachability.

### Recommendation
When `updateConflictState` detects that `prevConflictState.kind !== newConflictState.kind` (the merge/rebase/cherry-pick "operation kind" changed), reset `manualResolutions` to a fresh empty `Map` instead of carrying the old one forward, mirroring the fix pattern from the original report (clear the paired state whenever the primary state it depends on is invalidated). Add a regression test analogous to the existing `update-conflict-state-test.ts` cases but specifically covering merge→rebase and rebase→merge transitions with a pre-existing `manualResolutions` entry for the same file path, asserting the resolution is dropped.

### Proof of Concept
1. Start a merge that conflicts on `foo.txt`; in Desktop's conflict dialog, resolve `foo.txt` as "theirs" (`_updateManualConflictResolution(repo, 'foo.txt', ManualConflictResolution.theirs)`), which is stored via `app/src/lib/stores/app-store.ts#L8796-8828`.
2. Without finishing the merge, run `git merge --abort && git rebase <other-branch>` outside Desktop (or via terminal integration) such that the working directory now has `REBASE_HEAD` set and a conflict on the same path `foo.txt`.
3. Desktop's status refresh calls `updateConflictState`, which — per `app/src/lib/stores/updates/changes-state.ts#L306-310` — returns a new `'rebase'` conflict state that still carries `manualResolutions = { 'foo.txt': theirs }` from step 1.
4. Continue the rebase; `continueRebase` (`app/src/lib/git/rebase.ts#L443-462`) calls `stageManualConflictResolution(repository, file, ManualConflictResolution.theirs)` for `foo.txt`, which stages `status.entry.them` — now the *rebase*-sense "theirs" (the commit being replayed), the inverse of what the user actually approved during the merge — with no diff shown to the user for this file before the commit is finalized.

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}
