### Title
Malformed conflict marker blocks bypass Copilot review and are silently spliced into the "resolved" file - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The report's broken invariant is: a guard (`derivativeCount`) is checked in one place but the actual operation (`stake`'s loop) is driven by a *different* representation of the same state, so a value that should block the action instead lets it silently proceed and lose funds. GitHub Desktop's Copilot merge-conflict resolution feature has the analogous bug: the hunk-count that gates model-output validation is computed by `extractConflictHunks` (which *drops* malformed conflict blocks entirely), while the actual file rewrite (`reassembleResolvedFile`) re-scans the raw on-disk content with a *different* parser that treats the same malformed block as literal text and copies it through verbatim. An attacker who controls a branch/fork that gets merged and produces a conflict can craft a malformed conflict-marker block whose raw bytes are never shown to the model, never counted, but still get spliced unreviewed into the file the user is told is "resolved" and then commits.

### Finding Description
Two independent parsers exist for the same on-disk conflicted file:

1. `extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` builds the list of hunks that are sent to the model and used to compute the *expected* hunk count. If a `<<<<<<<` block never finds a closing `>>>>>>>` before EOF, the function explicitly discards it — the test at `app/test/unit/copilot-conflict-context-test.ts:346-357` confirms a malformed hunk yields `hunks.length === 0`. [1](#0-0) 

2. `validateResolutionPaths` in `app/src/lib/copilot-conflict-resolution.ts` gates the model's response purely on this count: [2](#0-1) 

3. `reassembleResolvedFile`, however, does not use `extractConflictHunks`'s parsed hunks at all — it re-walks the raw file content on disk with its own regexes. When it hits a malformed conflict marker (no separator or no closing marker), it does **not** skip the block; it pushes the marker line as literal content and advances one line at a time, meaning every subsequent line of the malformed block (up to EOF, since no closing marker exists) is copied through untouched into the "resolved" output: [3](#0-2) 

4. `reassembleResolutions` feeds the *full raw file* (`ctx.rawContent`, which still contains the malformed block's bytes) into this function: [4](#0-3) 

The net effect: content inside a malformed conflict block is (a) never sent to the model, (b) never counted against the hunk-count validation, and (c) never flagged to the user as unresolved — yet it ends up verbatim in the file that the dialog presents as a clean, Copilot-reviewed resolution.

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits bug. Because the merge/rebase/cherry-pick that produces the conflict originates from a remote branch or fork the user pulled in (a repository/content object the attacker controls), an attacker can engineer a file so that:
- one legitimate, well-formed conflict block is present (so the file is flagged as conflicted and routed through the Copilot resolver),
- a second, deliberately malformed block (missing `>>>>>>>`) contains attacker-chosen text (e.g. altered logic, additional trailing script/config lines, or content designed to look like normal code but subtly change behavior).

The user sees a Copilot-generated "resolution" that reports full review/reasoning for the well-formed hunk, has no error, and passes validation — but the attacker's block is spliced in unexamined. If the user accepts, that attacker content is written to the working file and can be committed and pushed, all without the model, the validation layer, or the user ever seeing it as "unresolved."

### Likelihood Explanation
Reaching this requires no local access, no credentials, and no unnatural user action beyond the ordinary Desktop workflow of merging/rebasing a branch that produces a conflict and then using the "Resolve with Copilot" feature — a first-class, expected use case. Crafting a conflict block that lacks a closing marker is trivial for anyone who controls the source branch's content (a malicious PR/fork). The divergence between `extractConflictHunks`'s skip-on-malformed behavior and `reassembleResolvedFile`'s copy-through-on-malformed behavior is a deterministic, structural bug rather than a probabilistic race, so it is reliably triggerable whenever this code path is exercised on an attacker-crafted file.

### Recommendation
Make the two parsers consistent, and treat any malformed marker discovered during reassembly as an error rather than literal content:
- Track the raw text of hunks (including malformed ones) alongside `extractConflictHunks`'s counted hunks so `rawContent` used for reassembly cannot contain byte ranges the model never saw and validation never counted.
- In `reassembleResolvedFile`, when a malformed `<<<<<<<` block is detected, fail the resolution for that file (surface it as an `ICopilotSkippedFile` requiring manual resolution) instead of silently copying the block through.
- Add a post-reassembly invariant check that the final file contains no leftover conflict-marker-shaped lines and that the total non-context content matches what was actually reviewed by the model, throwing `CopilotValidationError` otherwise.

### Proof of Concept
1. Prepare a repo where a merge/rebase produces a conflicted file with two blocks:
```
line before
<<<<<<< HEAD
safe ours content
=======
safe theirs content
>>>>>>> feature
middle
<<<<<<< HEAD
attacker-controlled-secret-or-malicious-line
======= (no closing >>>>>>> before EOF)
```
2. `extractConflictHunks(content)` returns exactly 1 hunk (the well-formed one); the malformed block's bytes are dropped from what's sent to Copilot, per `app/test/unit/copilot-conflict-context-test.ts:346-357` behavior.
3. Copilot receives only 1 hunk, returns 1 resolution → `validateResolutionPaths` passes (`resolution.hunks.length === 1 === expectedCount`).
4. `reassembleResolutions` calls `reassembleResolvedFile(ctx.rawContent, raw.hunks)` on the *original* raw file (still containing the malformed second block).
5. Inside `reassembleResolvedFile`, the first block is spliced correctly; on reaching the second (malformed) `<<<<<<<` line, `hasSeparator`/`closingIndex` lookahead fails, so the code falls into the `if (!hasSeparator || closingIndex === -1)` branch and copies the marker line and every following line (including "attacker-controlled-secret-or-malicious-line" and the literal `=======`) verbatim into `resultLines`.
6. The dialog presents this as a complete, reviewed resolution; if the user accepts, the attacker's unreviewed content is written to disk and can be committed/pushed.
