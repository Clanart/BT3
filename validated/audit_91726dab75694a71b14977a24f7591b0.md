## Analysis

The Velodrome bug's core invariant break: **an unprivileged actor can pay trivial amounts to fill a bounded array up to its cap, causing legitimate future entries to be denied or destructively evicted, at the victim's expense.**

The local analog is `pallet-bandwidth`'s per-`(app_chain, app)` FIFO subscription list, capped at `MAX_SUBSCRIPTIONS = 1024`. Unlike Velodrome's `rewards` array (which just *blocks* new entries), this pallet's list *evicts the oldest live subscription* when full — meaning a full attacker-funded fill doesn't just block future purchases, it actively **destroys bytes another party already paid for**.

### Title
Unprivileged bandwidth-purchase flooding evicts a victim app's paid subscriptions before expiry - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
Anyone holding a small amount of the local fee token can call `BandwidthManager.purchase()` for **any** `(app_chain, app)` pair — the `chain`/`app` fields are attacker-supplied and unauthenticated by identity, only by the pallet accepting the message from a registered manager [1](#0-0) . Each purchase message is credited via `push_subscription`, which appends to a `BoundedVec<Subscription, MaxSubscriptions>` capped at 1024, and evicts the oldest entry once full [2](#0-1) .

### Finding Description
`purchase()` takes an arbitrary `app` (bytes) and `chain` (credit destination), pulls the scaled tier price from `msg.sender`, and dispatches a `BandwidthPurchaseMsg` to `pallet-bandwidth` [3](#0-2) . On the pallet side, `on_accept` only checks that `request.from` matches the registered `BandwidthManager` for that source chain — it does not authenticate or restrict who the *payer* is, nor does it validate that `msg.app`/`msg.chain` belong to the caller [4](#0-3) . `push_subscription` then unconditionally appends: if the list is already at `MAX_SUBSCRIPTIONS`, it calls `list.remove(0)` — evicting the oldest live subscription (which may still have remaining unused bytes and time left) — before pushing the new one [5](#0-4) .

Because tier prices are attacker-chosen only in the sense that the attacker picks `tier`/`months` (cheapest tier, `months=1`), an attacker can cheaply push 1024 minimal purchases targeting a specific victim `(app_chain, app)` pair. This evicts the victim's legitimately purchased, unexpired subscription(s) — the docs themselves acknowledge the eviction destroys "what you paid for" (`SubscriptionEvicted` with `lost_bytes`) [6](#0-5) . This is functionally identical to the Velodrome analog: an unprivileged party spends trivial funds to saturate a bounded array keyed by an entity they don't control, destroying/blocking the legitimate party's slot.

Existing guards do not stop this:
- `set_manager`/tier config are governance-gated, but `purchase()` itself is fully permissionless by design (it's the whole point of the feature) [7](#0-6) .
- There is no per-payer or per-source rate limit, no minimum-tier enforcement to make the attack costly, and no protection that reserves capacity for the "legitimate" payer of an app.
- The eviction path removes the **oldest**, not the smallest/attacker's own entries, so a victim's large, high-value, long-duration subscription can be evicted by 1024 cheap trailing purchases from someone else entirely.

### Impact Explanation
This causes real loss of paid-for value: a victim app that purchased bandwidth (paying real fee-token amounts) can have that unexpired allowance silently destroyed by an attacker who pays comparatively trivial amounts (1024 × cheapest-tier price) directed at the same `(app_chain, app)` key. The `remaining_bytes` and time left on the evicted subscription are gone — this is a direct "loss of funds" (paid-for-but-unusable resource) that also causes a denial of the app's cross-chain messaging via the `BandwidthGate`, since with zero live allowance every non-purchase POST from that app is rejected (`GateError::NoAllowance`) until it purchases again [8](#0-7) .

### Likelihood Explanation
The attack requires only holding the local fee token, calling a fully public `purchase()` entrypoint 1024 times (batchable/scriptable), and choosing an arbitrary `(app_chain, app)` target — no relayer, prover, or admin compromise, and no reliance on front-running. Cost scales with the cheapest configured tier price × 1024, which per the docs' example plans ($50 for 100 KB) could still be a meaningfully large one-time cost, but the attack is economically comparable to (and arguably cheaper/more damaging than) the original Velodrome finding since it destroys existing value rather than merely blocking future additions.

### Recommendation
- Bound eviction to entries the *evicting purchaser itself* funded, or require a minimum remaining-bytes/expiry threshold before an entry is evictable, so a third party cannot destroy another payer's live allowance.
- Consider tracking `payer` per subscription and disallowing cross-payer eviction, or moving to a per-payer sub-list within the `(chain, app)` bucket.
- Alternatively, reject purchases that would evict a subscription with more than a governance-configured minimum of `remaining_bytes` or time-to-expiry remaining, forcing an attacker to wait out real subscriptions rather than force-evict them.
- Add a minimum tier/months threshold or a per-source purchase-rate limit to raise the cost of flooding attacks.

### Proof of Concept
1. Victim purchases `TierFour` for their app `AppX` on `chain = EVM-8453`, crediting a subscription with large `remaining_bytes` and long `expires_at` via `on_accept` → `push_subscription` [9](#0-8) .
2. Attacker, using a different EOA/contract, calls `BandwidthManager.purchase()` 1024 times with `app = AppX`, `chain = EVM-8453`, `tier = TierOne`, `months = 1` (cheapest configured tier) [1](#0-0) .
3. Each purchase dispatches a `BandwidthPurchaseMsg` to the pallet; by the 1025th total entry in `(EVM-8453, AppX)`'s list, `push_subscription` evicts the oldest entry — the victim's `TierFour` subscription — emitting `SubscriptionEvicted { lost_bytes: <victim's unused bytes> }` [10](#0-9) .
4. The victim's paid-for bandwidth is gone before expiry; `AppX`'s subsequent dispatches may now fail the `BandwidthGate` (`GateError::NoAllowance`/`Insufficient`) despite having paid for a large tier.

		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
