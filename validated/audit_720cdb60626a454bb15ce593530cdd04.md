### Title
Unchecked u64 overflow/underflow in payment and fee arithmetic allows bypassing the NotEnoughFunds check and producing a transaction with outputs exceeding inputs - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` sums attacker-influenced payment amounts into `payment_sat` with a plain `u64` `sum`, then checks `input_sat < (payment_sat + needed_fee)` without any overflow protection. If `payment_sat` (or `payment_sat + needed_fee`) exceeds `u64::MAX`, the arithmetic wraps in release builds (or panics in debug builds), the `NotEnoughFunds` check is bypassed, and a `SignableTransaction` is constructed whose outputs exceed its inputs — mirroring the rust-lightning bug where a proportional-fee calculation underflowed and forwarded a payment that should have been rejected. [1](#0-0) [2](#0-1) 

### Finding Description
In `SignableTransaction::new`, the only lower bound enforced on payments is `DUST` (546 sats); there is no upper bound on individual payment amounts or on their sum. [3](#0-2)  Two separate unchecked arithmetic points exist:

1. `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();` wraps on overflow. A payment list whose amounts sum past `u64::MAX` produces a small `payment_sat`. [4](#0-3) 
2. `if input_sat < (payment_sat + needed_fee)` performs an unchecked `u64` addition. Even when `payment_sat` itself doesn't wrap, `payment_sat + needed_fee` can. [5](#0-4) 

If either wraps to below `input_sat`, `TransactionError::NotEnoughFunds` is not raised and a transaction is built with `tx_outs` worth more than `input_sat`. [6](#0-5)  The subsequent `fee()` getter then computes `sum(inputs) - sum(outputs)` with a plain subtraction, which underflows — panicking in debug builds and wrapping to a near-`u64::MAX` "fee" in release. [7](#0-6)  The change-output path is the contrast that proves intent: it correctly uses `input_sat.checked_sub(payment_sat + fee_with_change)`, while the primary funds check uses raw `+`/`<`. [8](#0-7) 

The downstream caller in `processor` treats a returned `Ok` as a fulfillable plan and explicitly `panic!`s on several error paths, so an `Ok(SignableTransaction)` for an unspendable-overflow transaction proceeds to the FROST signing flow. [9](#0-8) 

### Impact Explanation
- Debug/validation builds: panic via `sum`/`add`/`sub` overflow → node crash, denial of service of the signing pipeline.
- Release builds: `NotEnoughFunds` is silently bypassed and the multisig is driven to FROST-sign a transaction that is consensus-invalid (outputs > inputs). The signatures are produced for a transaction that can never confirm, causing the affected inputs/plan to be consumed for a payment that can never settle — the same class of harm as the LDK bug (an amount calculation underflowed and a payment that should have been rejected was carried forward). A call to `fee()` afterwards underflows, misreporting the paid fee as ~`u64::MAX` sats. [10](#0-9) 

### Likelihood Explanation
Payments/`(ScriptBuf, u64)` amounts are transaction data that an unprivileged party can cause to be signed (e.g., withdrawal/payment requests fed into the scheduler), so the amounts are attacker-reachable public inputs to `SignableTransaction::new`. Reaching the wrap requires amounts near `u64::MAX` (≈1.8e19 sats, exceeding the real BTC supply), which limits practical exploitability to the panic/DoS and invalid-transaction-signing outcomes rather than actual theft; however the arithmetic error itself is trivially triggerable with two payments summing past `u64::MAX`, which the code never rejects.

### Recommendation
Compute funds checks with saturating/checked arithmetic:

```rust
let payment_sat = payments.iter().try_fold(0u64, |acc, p| acc.checked_add(p.1))
  .ok_or(TransactionError::NotEnoughFunds { inputs: input_sat, payments: u64::MAX, fee: needed_fee })?;
if input_sat < payment_sat.saturating_add(needed_fee) { ... }
```
and make `fee()` use `checked_sub`/`saturating_sub` (or assert the invariant). Also consider rejecting individual payment `u64` values that exceed Bitcoin's maximum money supply.

### Proof of Concept
```rust
// networks/bitcoin wallet context; `input` is any ReceivedOutput with modest value.
let input_sat = input.value(); // e.g. 100_000
let payments = vec![
  (p2tr_script_buf(key).unwrap(), u64::MAX - 1000), // >= DUST
  (p2tr_script_buf(key).unwrap(), 10_000),          // >= DUST
];
// payment_sat wraps to ~9_453; input_sat < payment_sat + needed_fee is false,
// so NotEnoughFunds is NOT returned despite outputs >> inputs.
let tx = SignableTransaction::new(vec![input], &payments, None, None, FEE).unwrap();
// Underflows: sum(inputs) - sum(outputs) < 0 -> panic (debug) / wrap (release).
let _ = tx.fee();
```
The wrapped result is a `SignableTransaction` the scheduler will route to `attempt_sign`/`algorithm.sign` for FROST signing of a consensus-invalid transaction, or a crash of the processor when `fee()` is evaluated.
