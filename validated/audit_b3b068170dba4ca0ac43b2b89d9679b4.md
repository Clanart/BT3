### Title
Schnorr half-aggregation weights omit public keys and nonces, enabling aggregate-signature forgery - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` derives each aggregation weight only from the caller-supplied Schnorr challenge sequence, not from the corresponding public key or nonce commitment. [1](#0-0)  An attacker who controls the serialized aggregate and knows the public inputs can calculate the weights and construct multiple invalid constituent signatures whose verification errors cancel. [2](#0-1) 

### Finding Description
The weight transcript is initialized from the destination tag, domain-separated as `signatures`, and absorbs only each challenge. [3](#0-2)  Verification then checks:

```text
Σ zᵢ·Rᵢ + Σ zᵢ·cᵢ·Aᵢ − s·G = 0
```

where `zᵢ = weight(transcript)` and `Aᵢ` is the public key for challenge `cᵢ`. [2](#0-1) 

For an individual Schnorr signature, validity requires `Rᵢ = sᵢ·G − cᵢ·Aᵢ`; the implementation’s unaggregated statements use the equivalent `Rᵢ + cᵢAᵢ − sᵢG = 0`. [4](#0-3)  Because the attacker can predict every `zᵢ` before choosing `Rᵢ`, they can select verification-error vectors `dᵢ` satisfying `Σ zᵢ·dᵢ = 0`, then set `Rᵢ = sᵢ·G − cᵢ·Aᵢ + dᵢ`. [5](#0-4) 

`SchnorrAggregate::read` accepts attacker-controlled nonce commitments and scalar `s`, and `verify` accepts the associated public keys and challenges as arguments. [6](#0-5) 

### Impact Explanation
A verifier can accept an aggregate whose component signatures are individually invalid, producing a forged aggregate authorization/proof wherever `SchnorrAggregate::verify` is used to represent successful verification of every supplied key/challenge pair. [7](#0-6) 

For two components, the attacker selects nonzero group element `d`, sets:

```text
d₂ = −(z₁ / z₂)·d
R₁ = s₁·G − c₁·A₁ + d
R₂ = s₂·G − c₂·A₂ + d₂
s  = z₁·s₁ + z₂·s₂
```

Both constituent signatures fail because `d` and `d₂` are nonzero, but the aggregate succeeds because `z₁d + z₂d₂ = 0`. [2](#0-1) 

### Likelihood Explanation
The attacker only needs public verification inputs—the destination tag, ordered challenges, public keys, and control over the submitted aggregate encoding—to calculate the weights and cancellation points. [1](#0-0)  No private key, validator privilege, malformed curve encoding, or protocol collusion is required. [6](#0-5) 

### Recommendation
Bind the complete ordered verification context into each weight, including at least the public key, nonce commitment `Rᵢ`, and challenge `cᵢ` for every component. Alternatively, derive weights unpredictably after all aggregate components are committed, or abandon deterministic weak weights in favor of cryptographically random nonzero weights under the batch-verifier model. [1](#0-0) 

### Proof of Concept
```text
Inputs:
  dst
  public keys A₁, A₂
  challenges c₁, c₂

1. Reproduce the verifier transcript:
     DigestTranscript::<C::H>::new(dst)
     domain_separate("signatures")
     append_message("challenge", c₁)
     append_message("challenge", c₂)

2. Reproduce the deterministic weights z₁ and z₂ using the same
   "aggregation_weight" challenge schedule as weight().

3. Choose arbitrary nonzero group element d and scalars s₁, s₂.

4. Compute:
     d₂ = −(z₁ · z₂⁻¹) · d
     R₁ = s₁·G − c₁·A₁ + d
     R₂ = s₂·G − c₂·A₂ + d₂
     s  = z₁·s₁ + z₂·s₂

5. Serialize SchnorrAggregate { Rs: [R₁, R₂], s } and call:
     aggregate.verify(dst, [(A₁, c₁), (A₂, c₂)])

6. Verification succeeds because:
     z₁R₁ + z₁c₁A₁ + z₂R₂ + z₂c₂A₂ − sG
       = z₁d + z₂d₂
       = 0

   Yet both individual statements fail:
     R₁ + c₁A₁ − s₁G = d  ≠ 0
     R₂ + c₂A₂ − s₂G = d₂ ≠ 0
```
