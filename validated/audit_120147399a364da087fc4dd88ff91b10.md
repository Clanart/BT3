### Title
Consumed FROST preprocess seed is never deleted from `CachedPreprocesses`, enabling deterministic nonce reuse across distinct `set_keys` messages - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
The kernel bug is a lifetime race: `cancel_delayed_work()` releases `xc5000_priv` while the delayed work item may still be running and dereferencing it — the resource is torn down before its consumer is guaranteed finished. The Serai analog is the inverse of the same lifetime error: a cryptographic resource that *must* die when consumed is instead kept alive. `SigningProtocol::preprocess_internal` stores the FROST preprocess seed in the `CachedPreprocesses` DB table and `share`/`complete` re-derive the same nonces from it on every call, with no deletion and no guard against being asked to sign a *different* message under the same context.

### Finding Description
`AlgorithmSignMachine::from_cache` rebuilds the entire FROST state — nonces and commitments — deterministically from the 32-byte seed via `ChaCha20Rng::from_seed(*seed.0)` in `crypto/frost/src/sign.rs:127-141`. The FROST docs are explicit: "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" (`crypto/frost/src/sign.rs:216-219`).

In `coordinator/src/tributary/signing_protocol.rs:123-145`, `preprocess_internal` reads `CachedPreprocesses::get(self.txn, &self.context)` where `context = (b"DkgConfirmer", attempt)`, and only generates a fresh seed if none exists. The entry is **never deleted** — there is no `del`/`remove` call anywhere on `CachedPreprocesses`. The safety comment at `signing_protocol.rs:25-48` argues reuse is safe because the messages are BFT-finalized, but the actual signed message is not purely BFT data: `share_internal` computes `msg = set_keys_message(&self.spec.set(), &removed, key_pair)` (lines 296-301) where `key_pair` comes from `generated_key_pair` in `coordinator/src/tributary/handle.rs:47-60`. That function does `DkgKeyPair::set(txn, spec.genesis(), attempt, key_pair)` — an unconditional overwrite with no check that a different `key_pair` was already recorded for this attempt — then calls `share()`, which signs with the reused nonces.

Since the confirmation share is published on tributary inside `Transaction::DkgConfirmed` (`handle.rs:508-516`), an observer obtains Schnorr signature shares. Two shares produced under the same nonces but over different `msg`/`key_pair` (or different preprocess sets after a `removed` change within the same attempt index) yield the classic FROST/Schnorr nonce-reuse equation: `s1 - s2 = share·(c1·λ - c2·λ')`, recovering the coordinator's MuSig secret share.

### Impact Explanation
The `DkgConfirmer` signs with the validators' root-of-trust keys ("we're using the validator's keys, as needed for their being the root of trust", `signing_protocol.rs:6-8`). Recovering a validator's secret share from two published confirmation shares lets an attacker forge that validator's confirmation share for arbitrary `set_keys` messages — e.g., confirming an attacker-chosen `KeyPair` on Substrate, which is exactly the operation this protocol exists to gate. This is key-share recovery, which is squarely in the accepted-impact set.

### Likelihood Explanation
The trigger is a second signing pass under the same `(b"DkgConfirmer", attempt)` context with different sign-bound data. Concrete paths: (a) `generated_key_pair` is invoked once per reported key pair and overwrites `DkgKeyPair` without an equality/duplicate check, so a processor or re-execution reporting a distinct `key_pair` for the same attempt produces a second share over the same nonces; (b) `complete()` re-runs `share_internal` (`signing_protocol.rs:321-324`), so any divergence between the `key_pair` used at `share()` time and at `complete()` time silently emits a second share. The file itself acknowledges the DB is not trustworthy and that re-execution occurs after rebuilds; the seed surviving in the DB across a partial rebuild where the DKG outcome differs is precisely the "work item still running after free" shape. Because the shares are broadcast on the public tributary, an unprivileged observer only needs the two distinct signed messages to exist — both derivable from processor-reported data. This is reachable and High-severity, though it requires the coordinator to be driven into a second sign for the same attempt, which depends on the DKG/reporting path permitting a conflicting `key_pair`.

### Recommendation
Delete the cached seed at the moment of consumption, mirroring `cancel_delayed_work_sync`: call a `CachedPreprocesses::del` inside `share_internal` immediately after `from_cache` succeeds, so a second `share()` for the same context must regenerate fresh nonces rather than re-deriving identical ones. Additionally, in `generated_key_pair` (`handle.rs:47-60`), assert that `DkgKeyPair::get` for this attempt is either `None` or equal to the reported `key_pair` before overwriting and signing; a conflicting report should slash the reporter rather than produce a second signature share under a spent nonce.

### Proof of Concept
Conceptual reproduction:

1. Validator set finalizes DKG attempt `a`. Processor reports `key_pair_A`; `generated_key_pair` stores it and `share()` signs `set_keys_message(set, removed, key_pair_A)` using seed `S` from `CachedPreprocesses[("DkgConfirmer", a)]`, emitting share `σ1` published in `DkgConfirmed`.
2. A second report (duplicate processor message, rebuild replay, or conflicting `key_pair_B` on the same `KeyToDkgAttempt`/attempt index) invokes `generated_key_pair` again. `DkgKeyPair::set` overwrites with `key_pair_B`; `preprocess_internal` reloads the *same* undeleted seed `S`, `seeded_preprocess` regenerates identical nonces, and `share()` emits `σ2` over `set_keys_message(set, removed, key_pair_B)`.
3. Anyone reading the two `DkgConfirmed` shares solves `σ1 - σ2` over the differing challenges (which hash the distinct `key_pair`s) and recovers the validator's MuSig secret share, enabling forgery of future DKG confirmations for that validator.

Verification point in code: `grep CachedPreprocesses` shows only `get`/`set` in `signing_protocol.rs:123,134,137` — no deletion exists anywhere in the crate.
