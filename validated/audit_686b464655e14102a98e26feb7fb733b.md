### Title
Uncosted CLVM execution of untrusted offer puzzle reveals causes CPU-exhaustion DoS on trade cancellation - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.get_cancellation_coins()` executes every coin-spend puzzle reveal in an offer with `run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)`, and `Offer._get_offered_coins()` similarly evaluates spends against `cost_left = INFINITE_COST`. Unlike mempool/consensus validation, which always meters CLVM execution against a bounded cost (`max_tx_clvm_cost` / `MAX_BLOCK_COST_CLVM`), these wallet-side offer-processing paths remove the cost ceiling entirely. Since offers are untrusted objects exchanged between counterparties (bech32-encoded blobs a taker or maker receives from someone else), a malicious offer containing a puzzle reveal that implements a large/expanding loop (the same bug class as ImageMagick's `ExtractPostscript` large-loop CVE) can make `run_with_cost(..., INFINITE_COST, ...)` run indefinitely, hanging the wallet process that tries to cancel or process the trade.

### Finding Description
`get_cancellation_coins()` iterates the offer's non-addition coin spends and, for each, calls: [1](#0-0) 
```
conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]
```
This is invoked from `TradeManager.cancel_pending_offers()` for every trade being cancelled: [2](#0-1) 

All normal chia paths that execute puzzle CLVM against untrusted/attacker-influenced input — mempool admission, block validation, and even the offer's own `conditions()`/`__post_init__` addition computation — use a *finite*, bounded max_cost (`DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`) and stop early once the budget is exhausted: [3](#0-2) [4](#0-3) 

`get_cancellation_coins()` and `_get_offered_coins()` are outliers that pass `INFINITE_COST` instead, discarding this defense: [5](#0-4) 

The codebase's own test suite documents that crafted CLVM programs using deep recursion/looping constructs (`(a (i N (large_string...) ...))`-style self-referencing loops) are a known, deliberately-mitigated attack against Chia's CLVM execution, precisely the same bug class as the ImageMagick `ExtractPostscript` large loop: [6](#0-5) 
Everywhere else in the codebase this class of attack is countered by hard cost limits enforced during CLVM execution; `get_cancellation_coins()`/`_get_offered_coins()` are the exception, executing the same kind of untrusted puzzle without any budget.

### Impact Explanation
An attacker crafts and shares/sends an offer file whose puzzle reveal for one of the non-addition coins is a self-referential CLVM loop (e.g. repeated `apply`/`if` recursion producing an ever-doubling atom, similar to the test-suite's `large_string`/`iter` patterns) that would normally be aborted by the mempool's cost limit but is never capped here. When the victim (offer counterparty or the maker attempting to cancel a pending trade) calls `cancel_pending_offers()` → `Offer.get_cancellation_coins()`, the wallet process invokes `run_with_cost(..., INFINITE_COST, ...)`, pinning a CPU core indefinitely and blocking the wallet's event loop / RPC responsiveness. This is a spend-triggered (offer-object-triggered) transaction-processing halt reachable by any offer counterparty without needing to break signatures, spend authority, or consensus rules — it only requires convincing/enabling a victim to load or attempt to cancel a malicious offer.

### Likelihood Explanation
Likelihood is limited by the requirement that the victim must actually attempt to *cancel* a trade containing the malicious spend, or otherwise trigger `_get_offered_coins()`/`get_cancellation_coins()` on the offer (both are part of the normal offer-viewing/summary and cancellation workflow in `TradeManager`). Because offers are routinely shared and accepted between mutually-untrusted parties in Chia's UX (dexie, marketplaces, manual offer files), and cancellation is a standard user action a maker performs on their own pending offers, the reachability is realistic, though it depends on wallet UI/RPC flows invoking these specific methods rather than every single offer touchpoint.

### Recommendation
Replace `INFINITE_COST` in `Offer.get_cancellation_coins()` and `Offer._get_offered_coins()` with a bounded cost limit (e.g. `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`, consistent with `__post_init__`/`conditions()`), and handle `Program.EvalError`/cost-exceeded exceptions gracefully by treating the coin as non-cancellable/unparseable rather than letting execution run unbounded.

### Proof of Concept
1. Construct a `CoinSpend` whose `puzzle_reveal` is a CLVM program that recursively applies itself with an exponentially/linearly growing atom for a very large iteration count (structurally analogous to the `large_string`/`iter` patterns already present in the repository's own adversarial mempool tests, e.g. `SINGLE_ARG_INT_LADDER_COND` at `chia/_tests/core/mempool/test_mempool.py:2672`), sized so it would exceed `MAX_BLOCK_COST_CLVM` if metered.
2. Embed this `CoinSpend` as a non-addition removal coin inside an `Offer`/`WalletSpendBundle` (the puzzle need not actually pass mempool validation — it is never submitted on-chain, only parsed locally).
3. Serialize and deliver the offer file to a victim wallet (e.g. as a trade offer to accept, or one the maker already created).
4. Have the victim call `TradeManager.cancel_pending_offers()` (or any code path invoking `Offer.get_cancellation_coins()`/`_get_offered_coins()`) on this offer.
5. Observe `run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)` in `chia/wallet/trading/offer.py:436` (or `chia/wallet/trading/offer.py:247`) execute without a cost bound, consuming CPU indefinitely and hanging the wallet's cancellation/RPC path.
