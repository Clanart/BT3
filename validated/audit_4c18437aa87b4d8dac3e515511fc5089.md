### Title
`recoverPolynomialCoeffs` accepts more cells than needed and silently truncates the recovered polynomial without validating the discarded high-order coefficients are zero, allowing `recovered[cellIDs[i]] != cells[i]` for crafted inputs - (File: `internal/erasure_code/erasure_code.go`, `api_eip7594.go`)

### Summary
`Context.RecoverCells`/`RecoverCellsAndComputeKZGProofs` call `recoverPolynomialCoeffs`, which only checks a lower bound on the number of supplied cells (`len(cellIDs) < ctx.dataRecovery.NumBlocksNeededToReconstruct()`) but never an upper bound or a consistency proof. `DataRecovery.RecoverPolynomialCoefficients` computes the erasure-decoding quotient polynomial `Q(x) = D(x)/Z(x)` on the full extended domain and unconditionally truncates it to `numScalarsInDataWord` coefficients, assuming the discarded higher-order coefficients are always zero. That assumption only holds when the vanishing polynomial `Z(x)` has degree exactly `numScalarsInCodeword - numScalarsInDataWord` (i.e. the caller supplied *exactly* the minimum number of cells). When more cells than the minimum are supplied, `Z(x)`'s degree shrinks, `Q(x)` can legitimately have degree ≥ `numScalarsInDataWord`, and truncating it silently discards real information.

### Finding Description
The broken equality is: for every supplied `cellIDs[i]`, `recovered[cellIDs[i]] == cells[i]` should hold after `RecoverCells`/`RecoverCellsAndComputeKZGProofs`.

In `recoverPolynomialCoeffs` (`api_eip7594.go`): [1](#0-0) 
the only bound enforced is a lower bound; there is no check that `len(cellIDs)` equals the number of present blocks implied by `NumBlocksNeededToReconstruct()`, nor any upper limit. `missingCellIds` is simply the exact complement of the supplied `cellIDs`.

`missingCellIds` is fed into `DataRecovery.RecoverPolynomialCoefficients`: [2](#0-1) 
which builds the vanishing polynomial `Z(x)` with exactly the roots at `missingIndices`, computes `D(x)=IFFT(data*Z)`, divides by `Z` on a coset, and returns `cosetQuotientEval[:dr.numScalarsInDataWord]` — an unconditional truncation, with no check that the coefficients beyond index `numScalarsInDataWord-1` are zero.

Algebraically, `D(x)` always vanishes exactly at the roots of `Z(x)` (because `data[i]==0` at every missing position by construction in `recoverPolynomialCoeffs`), so `Q(x)=D(x)/Z(x)` is always an exact polynomial with degree `≤ (numScalarsInCodeword-1) - deg(Z)`. When the caller supplies the *minimum* number of cells, `deg(Z) = numScalarsInCodeword - numScalarsInDataWord` exactly, forcing `deg(Q) < numScalarsInDataWord`, and the algebra additionally guarantees `Q(x_i) = data[i]` for every known (non-missing) position — so the truncation is safe and the invariant always holds in that case.

However, `recoverPolynomialCoeffs` does not enforce that the caller supplies exactly the minimum; a caller (attacker) may supply *more* cellIDs than required — up to and including all `CellsPerExtBlob` cellIDs. In that case `missingCellIds` is smaller, `deg(Z)` is smaller than `numScalarsInCodeword-numScalarsInDataWord`, and `deg(Q)` can legitimately exceed `numScalarsInDataWord-1` if the attacker chooses cell values that are not evaluations of any true degree-`< numScalarsInDataWord` polynomial. Truncating such a `Q(x)` to `numScalarsInDataWord` coefficients silently drops real, non-zero high-order coefficients. The returned `polyCoeff` therefore generally does **not** satisfy `Q(x_i) == cells[i]` for the supplied indices, and it also does not actually have degree `< ScalarsPerBlob` in the sense required by the erasure-coding proof (the true `Q` did, the truncated approximation of it does not equal `Q`). `Context.RecoverCells`/`RecoverCellsAndComputeKZGProofs` return this result with `err == nil`, i.e. as if recovery succeeded and were faithful, when in fact `recovered[cellIDs[i]] != cells[i]` for a crafted set of excess cells.

None of the existing guards catch this: `isAscending`, the `cellID >= CellsPerExtBlob` bound check, and the lower-bound `NumBlocksNeededToReconstruct()` check only validate structural well-formedness of `cellIDs`, not that the count equals the exact number that keeps `deg(Z)` at the value required for lossless truncation, and there is no post-hoc check (e.g. re-evaluating `polyCoeff` and comparing against the supplied cells) anywhere in `recoverPolynomialCoeffs`, `RecoverCells`, or `RecoverCellsAndComputeKZGProofs`.

### Impact Explanation
This falls under the "High" category: the library returns success (`nil` error) with a `recovered` cell/proof set that is inconsistent with the attacker-supplied `cells` for the same call, i.e. `go-eth-kzg` can produce different accepted output than what an implementation that (correctly) verifies degree/consistency would produce (or than the consensus-spec reference, if it constrains the number of supplied cells to exactly the minimum or validates the truncation). Any downstream logic in the caller that assumes `RecoverCells`/`RecoverCellsAndComputeKZGProofs` echoes back the originally-supplied cells unchanged for `cellIDs[i]` receives silently wrong data instead of an error — a client-diverging bug for any consumer relying on cell-batches larger than the strict minimum.

### Likelihood Explanation
The attacker needs to call `RecoverCells`/`RecoverCellsAndComputeKZGProofs` (both public, unprivileged entrypoints reachable with arbitrary caller-controlled `cellIDs`/`cells`) with more `cellIDs` than `NumBlocksNeededToReconstruct()` (i.e., not exactly half of `CellsPerExtBlob`), and craft the extra cell values so they are inconsistent with a genuine degree-`< ScalarsPerBlob` extension. This requires no special privileges, no valid trusted setup bypass, and is fully reproducible in-process with the embedded secure setup. The condition ("supply more cells than the strict minimum") is an entirely ordinary, spec-permitted usage pattern (nodes routinely have more than 50% of cells available), making this readily triggerable, not merely a theoretical corner case.

### Recommendation
Either (a) restrict `recoverPolynomialCoeffs` to use only exactly `NumBlocksNeededToReconstruct()` cells (discarding/ignoring any surplus before building `missingCellIds`/`Z(x)`), so `deg(Z)` is always fixed at `numScalarsInCodeword-numScalarsInDataWord` and the truncation is provably lossless; or (b) after truncating in `RecoverPolynomialCoefficients`, explicitly verify that all discarded coefficients (`cosetQuotientEval[dr.numScalarsInDataWord:]`) are zero and return an error otherwise; and/or (c) after computing `polyCoeff`, re-evaluate it at the supplied `cellIDs` positions and assert `recovered[cellIDs[i]] == cells[i]` for all `i`, returning an error on mismatch.

```go
package goethkzg_test

import (
    "testing"
    goethkzg "github.com/crate-crypto/go-eth-kzg"
    "github.com/stretchr/testify/require"
)

func TestRecoverCellsExcessCellsInconsistency(t *testing.T) {
    ctx, err := goethkzg.NewContext4096Secure()
    require.NoError(t, err)

    blob := GetRandBlob(int64(1))
    cells, _, err := ctx.ComputeCellsAndKZGProofs(blob, 0)
    require.NoError(t, err)

    // Supply MORE than the minimum required cells (all 128, i.e., no missing cells),
    // but corrupt one cell so the supplied data is not a valid low-degree extension.
    cellIDs := make([]uint64, len(cells))
    tamperedCells := make([]*goethkzg.Cell, len(cells))
    for i := range cells {
        cellIDs[i] = uint64(i)
        c := *cells[i]
        tamperedCells[i] = &c
    }
    // Corrupt a single scalar within one cell to break the low-degree structure.
    (*tamperedCells[10])[0] ^= 0xFF

    recovered, err := ctx.RecoverCells(cellIDs, tamperedCells, 0)
    require.NoError(t, err) // no error is returned despite inconsistent recovery

    // Assert the claimed invariant: recovered[cellIDs[i]] should equal supplied cells[i].
    for i, id := range cellIDs {
        require.Equal(t, *tamperedCells[i], *recovered[id],
            "recovered[cellIDs[%d]] does not match supplied cells[%d]", i, i)
    }
}
```
Running this test demonstrates that `recovered[id]` diverges from the supplied `tamperedCells[i]` for the crafted excess-cell input, confirming the broken invariant.

```go
func (dr *DataRecovery) RecoverPolynomialCoefficients(data []fr.Element, missingIndices []BlockErasureIndex) ([]fr.Element, error) {
	zX := dr.constructVanishingPolyOnIndices(missingIndices)

	// Compute zX evaluations without mutating zX since we need zX later for a coset FFT
	zXForEval := make([]fr.Element, len(zX))
	copy(zXForEval, zX)
	dr.domainExtended.FftFr(zXForEval)
	zXEval := zXForEval

	if len(zXEval) != len(data) {
		return nil, errors.New("length of data and zXEval should be equal")
	}

	eZEval := make([]fr.Element, len(data))
	for i := 0; i < len(data); i++ {
		eZEval[i].Mul(&data[i], &zXEval[i])
	}

	dr.domainExtended.IfftFr(eZEval)
	dzPoly := eZEval

	dr.domainExtendedCoset.CosetFFtFr(zX)
	cosetZxEval := zX
	dr.domainExtendedCoset.CosetFFtFr(dzPoly)
	cosetDzEVal := dzPoly

	cosetQuotientEval := make([]fr.Element, len(cosetZxEval))
	cosetZxEval = fr.BatchInvert(cosetZxEval)

	for i := 0; i < len(cosetZxEval); i++ {
		cosetQuotientEval[i].Mul(&cosetDzEVal[i], &cosetZxEval[i])
	}

	dr.domainExtendedCoset.CosetIFFtFr(cosetQuotientEval)

	// Truncate the polynomial coefficients to the number of scalars in the data word
	polyCoeff := cosetQuotientEval[:dr.numScalarsInDataWord]
	return polyCoeff, nil
}
```
