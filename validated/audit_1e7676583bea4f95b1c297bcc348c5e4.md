### Title
Bitcoin deposits attribute `presumed_origin` to the owner of `tx.input[0]` for every matched output, enabling refunds/credit to be sent to the wrong recipient - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` computes a single `presumed_origin` from `tx.input[0]`'s spent output and then assigns that same origin to **all** outputs in the transaction that scan as belonging to Serai (`External`, `Branch`, `Change`, `Forwarded`). This mirrors the reported bug class — a value transfer's "return address"/refund recipient resolved to the wrong party. A transaction with multiple inputs (CoinJoin, batched exchange withdrawal, or any jointly-funded tx) that pays a Serai address causes funds effectively sourced by a later input to be attributed to whoever owns input 0.

### Finding Description
In `get_outputs`, after `scanner.scan_transaction(tx)` collects matched outputs, the code unconditionally reads `tx.input[0]`, fetches its previous output over RPC, and derives `presumed_origin` from that single input's `script_pubkey`. It then loops over **every** matched output and sets `output.presumed_origin` to that value, and for `External` outputs additionally attaches the tx's Serai data.

```rust
// processor/src/networks/bitcoin.rs:714-736
let spent_output = {
  let input = &tx.input[0];               // only the first input is considered
  ...
  tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
};
Address::new(spent_output.script_pubkey)
...
for output in &mut outputs {
  if output.kind == OutputType::External {
    output.data.clone_from(&data);
  }
  output.presumed_origin.clone_from(&presumed_origin);
}
```

The in-code TODO acknowledges the ambiguity ("This may identify the P2WSH output *embedding the InInstruction* as the origin"), but the deeper flaw is structural: input 0 is attacker-malleable and need not correspond to the actual funder of the Serai-bound output, nor to the same funder as other inputs. The downstream processor consumes `presumed_origin` as the counterparty/refund identity for the deposit (it is propagated through `Output` into the multisig scheduler code in `processor/src/multisigs/mod.rs`), so a misattributed origin directly redirects funds owed back to the depositor — exactly the Autonomint pattern of a refund going to `user` instead of the legitimate recipient.

### Impact Explanation
When a deposit carries data the protocol cannot execute (or whenever the system owes the depositor a return of value), the refund/credit is issued to the address derived from input 0. An unprivileged attacker who contributes input 0 of a shared transaction receives refunds for funds actually contributed by other input owners, or has deposits of others attributed to their identity. This is "funds sent to / credited to the wrong recipient" reachable purely via a public Bitcoin transaction the attacker causes to exist — no validator, node, or key compromise required.

### Likelihood Explanation
Multi-input transactions paying a Serai address are commonplace: CoinJoins, PayJoins, and exchange/custodian batch withdrawals all produce transactions where the UTXO at input index 0 belongs to a different party than the effective payer. An attacker can also deliberately engineer this by making their own UTXO input 0 in any jointly-constructed transaction that includes a payment to a Serai `External`/`Branch`/`Change`/`Forwarded` script. The code path is hit unconditionally for every non-coinbase tx containing a scanned output — no special preconditions beyond the input ordering the attacker chooses.

### Recommendation
Do not collapse the entire transaction to a single `tx.input[0]` origin. At minimum:
- Attribute `presumed_origin` per matched output using all inputs (e.g., majority/aggregate of input sources), or refuse to set an origin when inputs have heterogeneous sources.
- Skip setting `presumed_origin` when `tx.input.len() > 1` with distinct source script_pubkeys, or bind origin to the input(s) that actually funded the Serai output where determinable.
- Treat `presumed_origin` as untrusted metadata and gate refundable/attributable actions on the explicit in-band instruction data rather than input ordering.

### Proof of Concept
1. Victim and attacker construct a joint transaction (PayJoin/CoinJoin-style) spending the attacker's UTXO as `tx.input[0]` and the victim's UTXO as `tx.input[1]`, with an output paying the Serai multisig's `External` script carrying an instruction that cannot be executed (or that later triggers a refund path).
2. The processor calls `get_outputs`; `scanner.scan_transaction` matches the output, and `presumed_origin` is computed solely from `tx.input[0]` → the attacker's address.
3. The deposit is attributed to the attacker; any refund of the victim-funded amount is paid out to the attacker's `presumed_origin` address instead of the victim — funds sent to an incorrect recipient, matching the reported bug class.
