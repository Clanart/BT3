### Title
Schnorr aggregate verifier accepts an empty signature sequence as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` in `crypto/schnorr/src/aggregate.rs` accepts a proof consisting of an empty `Rs` vector and `s = 0` as valid for an empty signer/challenge list. This is the direct analog of the Bouncy Castle CVE-2026-5588 bug class: a verifier that reduces "a list of signatures verified" to a zero-sum multiexponentiation trivially passes when the list is empty. The producing side (`SchnorrAggregator::complete`) correctly refuses to emit an empty aggregate, but the verifying side has no corresponding non-emptiness check.

### Finding Description
`SchnorrAggregate::read` parses a length-prefixed `Rs` vector followed by a scalar `s`; a 4-byte `0x00000000` length plus a zero scalar is a perfectly well-formed "aggregate signature" under this encoding [1](#0-0) .

`verify` then checks only `self.Rs.len() == keys_and_challenges.len()` [2](#0-1) . If both are empty, the loop pushes no `(z, R_i)` / `(z*c_i, key_i)` pairs, and `pairs` contains only `(-self.s, C::generator())` [3](#0-2) . With `s = 0`, that term is `0 * G = identity`, so `multiexp_vartime(&pairs).is_identity()` returns `true`.

Meanwhile `SchnorrAggregator::complete` explicitly returns `None` when nothing was aggregated [4](#0-3) , confirming that an empty aggregate is never a legitimate output of this library — yet `verify` will still bless one.

### Impact Explanation
Any caller that derives `keys_and_challenges` from attacker-influenced data (e.g., a signer set, a list of validators that signed, or claims attached to the aggregate signature itself) can be made to accept a "signature" produced by nobody: an attacker supplies `signers = []`, `Rs = []`, `s = 0` and `verify` returns `true`. This is a forged signature acceptance — a signature sequence validates over an unintended (empty) signer set. The only mitigating factor is that the caller must itself supply an empty key list, which is exactly the scenario the upstream CVE addresses (verifier must reject empty sequences rather than rely on callers).

### Likelihood Explanation
Reachability requires a verification path where the signer/key list is attacker-controlled or can be empty — e.g., an aggregate-verification call over a set computed from the submitted signature bytes or from a filter that yields zero entries. `SchnorrAggregate::read`/`verify` is a public API intended for untrusted bytes, and the deserialize-then-verify shape (untrusted `Rs` length drives the expected key count structure) makes the empty case reachable with public input. Within this repo the primary caller (Tendermint `verify_aggregate`) checks `signers.len() == aggregate.Rs().len()` [5](#0-4) , so an exploit additionally needs a path where an empty signer set is considered quorum-satisfying — hence Medium rather than High.

### Recommendation
In `SchnorrAggregate::verify`, reject empty inputs: `if self.Rs.is_empty() || self.Rs.len() != keys_and_challenges.len() { return false; }`. Optionally also reject empty `Rs` in `SchnorrAggregate::read`, matching the `complete()` invariant that a valid aggregate contains at least one signature.

### Proof of Concept
```rust
// crypto/schnorr context, e.g. with C = dalek_ff_group::Ed25519
let sig = SchnorrAggregate::<Ed25519> {
    Rs: vec![],
    s: <Ed25519 as Ciphersuite>::F::ZERO,
};
// Serialized form: 4-byte length 0, then a zero scalar (32 zero bytes).
assert!(sig.verify(b"some dst", &[])); // returns true — empty signature accepted
```
`pairs` reduces to `[(-0, G)]`, whose multiexp is the identity, so verification succeeds with no signer ever having produced a signature.
