Audit Report

## Title
Block-revenue-share `block_reward` is minted into stake accounts via `checked_add_lamports` without ever debiting the source vote account's lamports or `pending_delegator_rewards` counter - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

## Summary
Under SIMD-0123 block-revenue-sharing, `deposit_delegator_rewards` transfers real lamports into a vote account and increments `VoteStateV4::pending_delegator_rewards`, but no code path in the reward-calculation or distribution pipeline ever decrements that counter or subtracts the corresponding lamports from the vote account. `calculate_block_reward` computes each staker's share purely from the unmodified `pending_delegator_rewards` value, and `build_updated_stake_reward` mints that share directly into the stake account via `checked_add_lamports`, with no offsetting debit anywhere in the distribution path or in `Bank::capitalization` bookkeeping.

## Finding Description
The flow is confirmed as follows:

1. `deposit_delegator_rewards` transfers `deposit` lamports into the vote account and calls `add_pending_delegator_rewards(deposit)`, which only ever adds to the counter [1](#0-0) [2](#0-1) .
2. `calculate_block_reward` reads `vote_state.pending_delegator_rewards()` in full and computes a per-stake share of it, clamped only to `pending_delegator_rewards` per individual call — not against a running total already paid out [3](#0-2) .
3. `build_updated_stake_reward` credits `partitioned_stake_reward.block_reward` straight into the stake account via `account.checked_add_lamports(partitioned_stake_reward.block_reward)`, with no corresponding debit from the vote account [4](#0-3) .
4. `distribute_epoch_rewards_in_partition` only adjusts `capitalization` for `stake_reward_lamports_minted` (inflation) and `block_reward_lamports_burned` (failure case); `block_reward_lamports_distributed` is passed only into `update_epoch_rewards_sysvar`, never into `capitalization`, and never into any debit against the originating vote account [5](#0-4) .
5. Critically, `begin_partitioned_rewards` — the function that initializes the `EpochRewards` sysvar at the start of the reward cycle — calls `create_epoch_rewards_sysvar` with a **hardcoded `0`** for the `block_rewards` parameter, regardless of how much block reward was actually calculated for the epoch: `self.create_epoch_rewards_sysvar(distributed_lamports + distributed_to_incinerator_lamports + burned_lamports, distribution_starting_block_height, num_partitions, point_value, 0 /* block_rewards */)` [6](#0-5) .
6. `create_epoch_rewards_sysvar` funds the `EpochRewards` sysvar account's lamports directly from the `block_rewards` argument via `checked_add_lamports(block_rewards)`, explicitly "without updating capitalization, since block reward lamports already existed" [7](#0-6) . Since this argument is always `0` in the only caller found (`begin_partitioned_rewards`), the sysvar account never actually holds any block-reward-backed lamports.
7. Later, `update_epoch_rewards_sysvar` attempts to debit `block_reward_lamports_distributed + block_reward_lamports_burned` from that same sysvar account via `checked_sub_lamports`, with an `.expect("epoch reward sysvar has enough lamports for distribution")` [8](#0-7) .

No code path was found in `vote_state`, `handler.rs`, or the `partitioned_epoch_rewards` module that decrements `pending_delegator_rewards` on the vote account or performs `checked_sub_lamports` on the vote account to fund `block_reward`. The only other consumer of `pending_delegator_rewards`, `withdraw`, merely enforces it as a minimum-balance floor and never spends it down [9](#0-8) .

This confirms the structural gap described in the claim: `block_reward` lamports are created inside stake accounts with `checked_add_lamports` with no offsetting debit from the vote account and no `pending_delegator_rewards` decrement, and — separately but relatedly — the sysvar-funding path that was apparently intended to back these block rewards is wired to always pass `0`, meaning the sysvar's own lamport accounting for block rewards is also broken (it can never legitimately fund a nonzero `block_reward_lamports_distributed` debit without hitting the `.expect()` panic path, given the only caller supplies `0`).

The `test_epoch_rewards_sysvar` unit test only exercises `create_epoch_rewards_sysvar`/`update_epoch_rewards_sysvar` directly with a manually-supplied nonzero `first_block_rewards`, not through the real `begin_partitioned_rewards` call path, so it does not catch that the real caller always passes `0` [10](#0-9) .

## Impact Explanation
This breaks fund/accounting correctness for `Bank::capitalization` and the total-lamports invariant. Every epoch that distributes a nonzero `block_reward` (i.e., `block_revenue_sharing` active and a validator has deposited delegator rewards), stake accounts receive freshly-added lamports via `checked_add_lamports` that are never subtracted from the vote account's balance and never reflected as an increase to `capitalization`, while `pending_delegator_rewards` also stays un-decremented so the same pool re-qualifies for a new share in the following epoch. Additionally, given the `0` argument bug in `begin_partitioned_rewards`, if `block_reward_lamports_distributed` from `store_stake_accounts_in_partition` is ever nonzero, the subsequent `update_epoch_rewards_sysvar` call's `checked_sub_lamports(debit_block_reward_lamports)` would fail its `.expect()` and panic, which — since this runs deterministically on every validator processing the same epoch-reward-distribution block — would cause a consensus-relevant validator crash/halt across the fleet rather than a silent divergence. This corresponds to the fund-accounting/consensus-halt impact category named in scope, with the corrupted value being `Bank::capitalization` and the `EpochRewards` sysvar's lamport balance.

## Likelihood Explanation
This path executes automatically and deterministically every epoch in which `block_revenue_sharing` is active and any validator has nonzero `pending_delegator_rewards`, with no attacker action, special privilege, or race condition required. It is a systemic code-path bug (not a "malicious validator" scenario) reachable purely through the standard leader-fee deposit and epoch-boundary reward machinery.

## Recommendation
Fix `begin_partitioned_rewards` to pass the actual computed total block reward (sum of all `PartitionedStakeReward::block_reward` values, i.e., `rewards_calculation.stake_rewards.total_block_reward_lamports` or equivalent) into `create_epoch_rewards_sysvar` instead of the hardcoded `0`, so the sysvar's lamport balance is correctly pre-funded to match what `update_epoch_rewards_sysvar` will later debit. Separately, when crediting `block_reward` to stake accounts in `build_updated_stake_reward`/`store_stake_accounts_in_partition`, symmetrically debit the same amount from the originating vote account's lamport balance and decrement `pending_delegator_rewards` by the total distributed for that vote account, mirroring how inflation-reward accounting pairs minted lamports with capitalization increases. Add integration-level testing (not just the isolated sysvar unit test) that exercises `begin_partitioned_rewards` → `distribute_epoch_rewards_in_partition` end-to-end with `block_revenue_sharing` enabled and nonzero `pending_delegator_rewards` to catch this class of accounting mismatch.

## Proof of Concept
1. Enable `block_revenue_sharing`, and call `VoteInstruction::deposit_delegator_rewards` to set a vote account's `pending_delegator_rewards = D > 0` [1](#0-0) .
2. Let the epoch boundary trigger `begin_partitioned_rewards`; observe that `create_epoch_rewards_sysvar` is invoked with `block_rewards = 0` regardless of `D` [6](#0-5) .
3. During `calculate_stake_rewards_and_commissions`, `calculate_block_reward` computes a nonzero `block_reward` share of `D` per delegator [11](#0-10) .
4. During distribution, `store_stake_accounts_in_partition` accumulates `block_reward_lamports_distributed > 0` and calls `distribute_epoch_rewards_in_partition`, which calls `update_epoch_rewards_sysvar(_, block_reward_lamports_distributed)`, triggering `checked_sub_lamports` against a sysvar account that was funded with `0` block rewards, causing the `.expect("epoch reward sysvar has enough lamports for distribution")` to panic (or, if the panic path is avoided/patched elsewhere outside the indexed code, resulting in the accounting-invariant break described in the original claim — stake account lamports increase with no corresponding vote-account debit or capitalization update). A minimal Rust unit test extending `test_distribute_partitioned_epoch_rewards` with `block_revenue_sharing` enabled and a vote account carrying nonzero `pending_delegator_rewards` would reproduce the panic/inconsistency.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
