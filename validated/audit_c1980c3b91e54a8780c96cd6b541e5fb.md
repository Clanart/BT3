### Title
Hookify PreToolUse rules with a mistyped/unregistered `tool_matcher` silently fail open, allowing blocked commands to execute undetected - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
The `hookify` plugin implements a `PreToolUse` security-guard hook that blocks dangerous commands based on user-authored rule files. Neither the rule loader nor the rule engine validates that a rule's `tool_matcher` (or the inferred tool binding from `event`) corresponds to an actual, existing Claude Code tool name. A misspelled or unsupported tool identifier causes the rule to silently never match, and the hook then returns an empty (allow) result with no warning — the same "unregistered entity defaults to the insecure branch" pattern as the Spigot `claimRevenue` bug, where an unregistered `revenueContract` silently defaulted to sending 100% of funds to the treasury instead of reverting.

### Finding Description
`load_rules()` in [1](#0-0)  loads `.claude/hookify.*.local.md` files and constructs `Rule` objects via `Rule.from_dict`, which accepts an arbitrary, unvalidated `tool_matcher` string from frontmatter: [2](#0-1) . There is no check anywhere in the loader that this string is one of the real Claude Code tool names (`Bash`, `Write`, `Edit`, `MultiEdit`, etc.) or a syntactically valid matcher — unlike the plugin's own `validate-hook-schema.sh`, which only validates the `hooks/hooks.json` wrapper (matcher/type/command fields), not hookify's own rule files.

At evaluation time, `RuleEngine._rule_matches` in [3](#0-2)  calls `_matches_tool`, which does an exact, case-sensitive membership check against the actual `tool_name` from the hook input: [4](#0-3) . If the configured `tool_matcher` is misspelled, uses an outdated/renamed tool name, or has a case mismatch, `_matches_tool` returns `False` for every real invocation of that tool, so `_rule_matches` returns `False` unconditionally regardless of how dangerous the actual command is.

Critically, `evaluate_rules()` treats "no rule matched" as the fully-permissive default: [5](#0-4) . This propagates all the way up through `pretooluse.py`, which prints whatever the engine returns and always exits 0 (never blocking on hook errors): [6](#0-5) . There is no diagnostic, warning, or startup validation surfaced to the user indicating their supposed security rule never activates — directly analogous to `SpigotLib.claimRevenue` computing `ownerSplit` as `0` for an unregistered `revenueContract` and silently sending everything to the treasury instead of reverting, per the referenced report.

### Impact Explanation
A user (or an org/security team) who authors a `hookify.*.local.md` rule intending to block a dangerous pattern (e.g., `rm -rf`, credential exfiltration via `curl`, etc.) on a mistyped or unsupported `tool_matcher`/`event` value will believe the guard is active while it is completely inert. Because the failure mode is silent (no warning at load time or at match time), the false sense of security persists indefinitely — an attacker-controlled or accidentally dangerous command that should have been blocked by `PreToolUse` executes normally. This is a genuine unauthorized-action/hook-bypass condition consistent with the "unregistered entity → insecure default" bug class, though its blast radius is limited to whatever a single hookify rule was meant to guard (not a systemic bypass of Claude Code's core permission engine).

### Likelihood Explanation
Likelihood is moderate: hookify rules are hand-authored YAML frontmatter with a hand-typed `tool_matcher`/`event` field and no schema enforcement of valid tool names, so typos or use of deprecated/renamed tool identifiers (tool names have changed across versions per the CHANGELOG, e.g. `TeamCreate`/`TeamDelete` removal) are plausible authoring mistakes. It does not require an active attacker — any legitimate user misconfiguring a rule silently loses protection, and there is no feedback loop (test tooling like `test-hook.sh`/`validate-hook-schema.sh` targets `hooks.json`, not hookify's own rule files) that would catch the mistake before it matters.

### Recommendation
- In `config_loader.py`, validate `tool_matcher` (and the `event`-derived implicit tool binding) against the known set of built-in tool names (and known MCP prefix patterns) when loading a rule; warn loudly (to stderr and/or `systemMessage`) if the matcher can never match any known tool.
- In `rule_engine.py`, add a "fail-safe" mode option so that when a supposedly-blocking rule (`action: "block"`) never matches across a full session (or matches zero real tool names at load time), the hook can optionally warn or block instead of silently allowing.
- Extend `scripts/validate-hook-schema.sh` (or add an analogous validator) to also check hookify's own `hookify.*.local.md` rule files, not just `hooks/hooks.json`.

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md`:
```markdown
---
name: block-dangerous-rm
enabled: true
event: bash
tool_matcher: "Baash"   # typo: should be "Bash"
action: block
conditions:
  - field: command
    operator: regex_match
    pattern: "rm\\s+-rf"
---
Blocked: dangerous rm -rf command.
```
2. Trigger a `Bash` tool call with `command: "rm -rf /important/data"`.
3. `pretooluse.py` invokes `load_rules(event='bash')` → the rule loads successfully (no validation error) → `RuleEngine._rule_matches` calls `_matches_tool("Baash", "Bash")`, which returns `False` (per [7](#0-6) ) → `_rule_matches` returns `False` → `evaluate_rules` returns `{}` (allow) as shown in [8](#0-7) .
4. The dangerous `rm -rf` command executes with no block and no warning, even though the user configured and believed they had an active blocking rule for it.

def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules

    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
