### Title
Cached FROST preprocess reused across distinct messages within one DKG attempt enables secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches the FROST preprocess seed in `CachedPreprocesses` keyed only by `context`. For `DkgConfirmer`, the context is `(b"DkgConfirmer", attempt)` — it does not include the message being signed. Every `share`/`complete` call within the same attempt regenerates the *identical* nonces from the cached seed via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` (`ChaCha20Rng::from_seed(*seed.0)`). If `share()` is invoked for more than one distinct `key_pair` (each produces a different `set_keys_message`), the same nonce is used to sign different messages — classic Schnorr nonce reuse. Anyone observing the two published signature shares (they are broadcast as `Transaction::Sign` / `SignData { label: Label::Share }` data) can solve for the signer's secret share.

This mirrors CVE-2019-11502: the *first* caller's state (the first cached preprocess seed) silently becomes the state used by all subsequent callers, regardless of what they are actually signing.

### Finding Description
- `preprocess_internal` only generates a fresh seed when `CachedPreprocesses::get(self.txn, &self.context).is_none()`; otherwise it reuses the stored seed (coordinator/src/tributary/signing_protocol.rs:123-145).
- `DkgConfirmer::signing_protocol` sets `context = (b"DkgConfirmer", self.attempt)` (lines 274-277). The message — `set_keys_message(&self.spec.set(), &removed, key_pair)` — is *not* part of the context.
- `DkgConfirmer::share` → `share_internal` → `preprocess_internal` is called per `key_pair`; `complete` invokes `share_internal` again (lines 288-327). A single DKG confirmation attempt covering multiple key pairs therefore signs multiple distinct messages with the same FROST nonces.
- In FROST, a signature share is `s_i = d_i + e_i·b_i·ρ_i + c·λ_i·x_i` over nonces `(d_i, e_i)`. Two shares `s`, `s'` over the same commitments but different challenges `c ≠ c'` (different messages) yield `x_i = (s - s') / (λ_i·(c - c'))` — full secret-share recovery.
- The cached seed is additionally encrypted with a static key derived from `b"Cached Preprocess Encryption Key" || context || key`, so the encryption does not mitigate reuse.

### Impact Explanation
Recovery of a validator's MuSig/FROST secret share for the tributary signing set. Combined with threshold-many recovered shares, an attacker reconstructs the substrate validator-set key and can forge `set_keys`/batch signatures. The shares are published on the tributary as `SignData`, so recovery is possible by any observer, not just validators.

### Likelihood Explanation
High wherever a confirmation attempt produces more than one `key_pair` to sign (e.g., multiple network keys confirmed in one DKG attempt, or a retry path calling `share` with an updated `key_pair` under the same `attempt`). The nonce reuse is unconditional once a second distinct message is signed under the same `(b"DkgConfirmer", attempt)` context — no fault or race is required.

### Recommendation
Bind the cached-preprocess context to the message being signed: extend `context` to include a hash of `set_keys_message` (i.e., the `key_pair`), or maintain a per-context "consumed" flag that generates a fresh seed for each distinct message. Alternatively, derive the ChaCha20 seed as `H(cached_seed || msg)` inside `from_cache`/`share_internal` so distinct messages deterministically produce distinct nonces while still surviving restarts.

### Proof of Concept
Within a single `attempt`:
1. `confirmer.share(preprocesses, key_pair_A)` → `preprocess_internal` stores seed `S` under context `(b"DkgConfirmer", attempt)`, produces share `s_A` for `msg_A = set_keys_message(.., key_pair_A)`.
2. `confirmer.share(preprocesses, key_pair_B)` (or `complete` after the message changed) → reloads the same `S`, regenerates identical `(d, e)` and identical commitments `R`, produces share `s_B` for `msg_B ≠ msg_A`.
3. Both shares carry the same `R`; the binding coefficient `ρ` and Lagrange weight `λ_i` are public functions of the preprocesses, and the challenges `c_A = H(R, Y, msg_A)`, `c_B = H(R, Y, msg_B)` differ. The observer computes `x_i = (s_A - s_B) / (λ_i (c_A - c_B))` mod q, recovering the private key share.

### Limitations
I could not fully trace `handle.rs` to confirm exactly how many distinct `key_pair` values are signed per attempt in production flows; the vulnerability holds whenever more than one distinct message reaches `share_internal` under the same attempt context, which the `complete`/`share` call structure permits.
