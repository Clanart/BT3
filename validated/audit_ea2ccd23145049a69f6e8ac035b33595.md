### Title
Unnecessary reimplementation of `IntentGatewayV2` for Tron silently drops SafeERC20's return-value checks in escrow settlement, allowing escrow to be marked paid without the beneficiary receiving funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical `IntentGatewayV2` escrow-settlement logic lives in `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw`, which uses OpenZeppelin's `SafeERC20.safeTransfer` — a call that reverts if the token's `transfer` returns `false` or has no return data handling issue. `evm/tron/contracts/apps/IntentGatewayV2.sol` is a wholesale, independent reimplementation of the entire gateway (escrow accounting, `placeOrder`, `cancelOrder`, `onAccept`, `withdraw`) rather than inheriting the shared `IntentsBase`/`ExtrinsicIntents`/`IntrinsicIntents` modules used by the main EVM contract. This unnecessary duplication has already diverged from the audited base logic: its `withdraw()` and `onAccept` (`SweepDust` branch) use raw `.call(...)` and only check that the call itself did not revert, never inspecting the ABI-decoded boolean return value.

### Finding Description
In `IntentsBase._withdraw` (the shared, audited implementation): [2](#0-1) 
tokens are moved with `IERC20(token).safeTransfer(beneficiary, amount)`, which reverts the whole transaction if the ERC20 `transfer` call fails or returns `false`.

The Tron reimplementation's `withdraw` instead does: [3](#0-2) 
and the `SweepDust` handling in `onAccept` does the same: [4](#0-3) 

Both only check `success` (i.e., that the low-level call did not revert) and never decode/validate the returned boolean. Any TRC20/ERC20 token that follows the legacy pattern of returning `false` on failure instead of reverting (a very common pattern on TRON, where many TRC20 tokens are non-standard) will cause:
- `withdraw()`: `_orders[body.commitment][token] -= amount;` still executes, permanently zeroing/decrementing the escrow accounting and marking `_filled[body.commitment] = beneficiary` (this line runs unconditionally at the top of `withdraw`, before the transfer even happens) — while the actual tokens never leave the contract to reach `beneficiary`.
- `SweepDust`: `DustSwept` is emitted and internal bookkeeping proceeds as if funds moved, even though the transfer silently failed.

This is a direct instance of the reported bug class: unnecessary reimplementation of already-solved functionality (safe token transfer with return-value checking, done correctly elsewhere in the same repo via `SafeERC20`) reintroduces a bug class the base implementation already protects against.

### Impact Explanation
This causes real loss/lock of bridged funds under the Hyperbridge Impact Gate's "stealing or loss of funds" and "false proof/state acceptance" categories: escrow tokens become permanently stuck in the `IntentGatewayV2` (Tron) contract — the internal `_orders` mapping is decremented (or the order is marked `_filled`) so no retry path exists, but the beneficiary never receives the corresponding TRC20 tokens. This is a genuine accounting/settlement divergence between the audited base logic and its unnecessary duplicate, not merely a style issue as in the original report — it results in silent, permanent fund loss for legitimate order beneficiaries whenever a non-strictly-compliant TRC20 token is used as escrow/output.

### Likelihood Explanation
Likelihood is high on Tron specifically: TRC20 is not enforced to be ERC20-strict, and many popular TRC20 tokens historically return `false` rather than reverting on transfer failure (e.g., insufficient balance edge cases, blacklists, paused states). No malicious actor, relayer, or governance action is required — this triggers under ordinary operation whenever the escrowed/output token behaves this way and a transfer legitimately fails (e.g., temporary pause, blacklist, insufficient contract balance due to another bug), silently completing settlement bookkeeping without moving value.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw` and `onAccept` (`SweepDust`) with `SafeERC20.safeTransfer`, matching the canonical `IntentsBase._withdraw` implementation. More broadly, eliminate the unnecessary full reimplementation of `IntentGatewayV2` for Tron and have it inherit from the same `IntentsBase`/`ExtrinsicIntents`/`IntrinsicIntents` composition used by the canonical EVM contract, so escrow-settlement logic is defined once and audited once, preventing this kind of silent divergence.

### Proof of Concept
1. Register/deploy a TRC20 token whose `transfer(address,uint256)` returns `false` on failure instead of reverting (e.g., simulate a paused/blacklisted state for the beneficiary) and use it as an order's output/escrow token.
2. A user places an order via `placeOrder`, escrowing this token: `_orders[commitment][token] = amount`.
3. A `RedeemEscrow`/`RefundEscrow` ISMP message is delivered and `onAccept` calls `withdraw(body, ...)`.
4. Inside `withdraw`, `_filled[body.commitment] = beneficiary` is set unconditionally at line 684, then `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` is invoked; the token internally returns `false` (e.g., beneficiary is blacklisted) without reverting, so `success == true`.
5. `_orders[body.commitment][token] -= amount;` executes, zeroing escrow accounting; `EscrowReleased`/`EscrowRefunded` is emitted.
6. The beneficiary never received the tokens (the token's internal state never credited them), and because `_filled` is already set and escrow already decremented, there is no way to retry or recover — the tokens are permanently locked in the `IntentGatewayV2` contract with no accounting reference to them.
