### Title
Wallet signer-protocol RPC acts as a signing oracle for arbitrary attacker-supplied `CoinSpend`s, enabling AGG_SIG_UNSAFE signature reuse against a victim's own keys — ([File: chia/wallet/wallet_signer.py])

### Summary
`WalletRpcApi.gather_signing_info`/`execute_signing_instructions`/`apply_signatures` (backed by `WalletSigner` in `chia/wallet/wallet_signer.py`) will extract `AGG_SIG_*` pubkey/message pairs from *any* caller-supplied `CoinSpend` — not just spends the wallet itself constructed and pushed — and sign them with the wallet's real keys whenever the pubkey resolves to an owned key via sum/path hints. This mirrors the CVE's "confused deputy" pattern: a local actor asks the wallet to "process" attacker-controlled event/spend data during a normal-looking interaction (CHIP-0029 signer-protocol flow / offer completion), and the wallet dutifully signs it without confirming the spend is one it actually intended to make.

### Finding Description
`WalletSigner.gather_signing_info()` takes a list of `Spend` objects (arbitrary `CoinSpend`s reconstructed from caller input) and, for each one, runs the puzzle/solution to extract CLVM conditions, then calls `pkm_pairs_for_conditions_dict()` to get every `(pubkey, message)` pair from `AGG_SIG_UNSAFE`, `AGG_SIG_ME`, and the other AGG_SIG_* opcodes present in that arbitrary spend: [1](#0-0) 

Crucially, there is no check that the coin in the spend belongs to a coin the wallet actually selected/owns/has confirmed on-chain, nor that the spend came from a transaction the wallet itself built via the action-scope/coin-selection path. The only gate is whether the *pubkey* in the AGG_SIG condition resolves to a key the wallet controls (`sum_hint_for_pubkey`/`path_hint_for_pubkey`): [2](#0-1) 

`execute_signing_instructions()` then blindly signs `target.message` for any fingerprint it can resolve via key/path/sum hints, with no validation of what that message represents: [3](#0-2) 

The message-construction logic in `pkm_pairs_for_conditions_dict()` shows that `AGG_SIG_UNSAFE` messages are taken essentially verbatim (only checked to not end with domain-separation suffixes used by the other opcodes) — they carry no coin id, no amount, no puzzle hash binding: [4](#0-3) 

This is reachable via the `gather_signing_info`, `execute_signing_instructions`, and `apply_signatures`/`submit_transactions` wallet RPC endpoints exposed through `WalletRpcApi`, which are part of the CHIP-0029 signer-protocol surface and used by the offer/`take_offer`/`tx_endpoint` flow: [5](#0-4) [6](#0-5) 

The tests confirm this design intent — the wallet will sign for any coin/message combination as long as the pubkey resolves to an owned key, including for a completely fabricated "not our coin" `CoinSpend` with an arbitrary `AGG_SIG_UNSAFE` message and a pubkey the wallet does not own (that specific case fails only because the pubkey isn't the wallet's key, not because the coin is unrecognized): [7](#0-6) 

### Impact Explanation
Because `AGG_SIG_UNSAFE` signatures carry no binding to a specific coin, transaction, or spend bundle, any signature the wallet is tricked into producing for an attacker-chosen message under the victim's real derived key can be replayed by the attacker into a *different*, unrelated spend bundle that uses `AGG_SIG_UNSAFE` with the same pubkey and message to authorize an unintended coin movement. An attacker who can get the victim to feed an offer file, a "sign this bundle" request, or a crafted `Spend`/`CoinSpend` through the signer-protocol RPC (e.g., via `take_offer`, `gather_signing_info`, or third-party wallet-integration tooling that surfaces these endpoints) can obtain a valid BLS signature over content of their choosing, then use it to satisfy an `AGG_SIG_UNSAFE` condition elsewhere and move coins or unlock spends the user never intended to sign. This matches the "unsigned or unauthorized coin movement" acceptance criterion.

### Likelihood Explanation
The signer-protocol endpoints are explicitly public wallet RPC surface intended for offline/remote signing and CHIP-0029 workflows, and offer completion already routes third-party spend content (via `Offer`) through `gather_signing_info_for_trades`. Any local RPC caller or any flow that hands untrusted spend/offer content to the signer (e.g., a compromised or malicious desktop/CLI integration, a scripted "review and sign" tool, or a wallet UI feature that previews/completes third-party offers) can trigger this without needing to compromise the wallet's private keys. The main friction is that the attacker needs the victim to invoke the signing flow on attacker-supplied spend data, which is analogous to the CVE's requirement of "user interaction" (join/leave/knock) that triggers the victim server's signing path.

### Recommendation
- Bind `AGG_SIG_UNSAFE` messages used by the wallet-side signer to be rejected or specially warned/confirmed when they don't correspond to a spend the wallet itself constructed/tracks (e.g., verify the coin is a known/owned wallet coin or part of an active, wallet-initiated `TransactionRecord`/`Offer` before signing).
- Before calling `execute_signing_instructions()` on caller-supplied `SigningInstructions`, validate that every underlying `Spend`'s coin is either a coin the wallet is currently trying to spend (from `action_scope`) or one already recognized/confirmed by the wallet state manager, not an arbitrary CoinSpend reconstructed purely from RPC input.
- Consider requiring explicit user confirmation (or a distinct, more restricted RPC/CLI mode) for signing raw externally supplied `CoinSpend`s/offers that contain `AGG_SIG_UNSAFE` conditions, given their lack of coin-binding.

### Proof of Concept
1. Attacker crafts a `CoinSpend` for their own (or an ephemeral) coin whose puzzle reveals an `AGG_SIG_UNSAFE` condition `(49 <victim_pubkey> <arbitrary_message>)`, where `<victim_pubkey>` is a pubkey the attacker has learned belongs to the victim's wallet (e.g., from a previous transaction or address).
2. Attacker delivers this spend to the victim disguised as part of a "review/sign this offer" or "gather signing info for this bundle" request, e.g. via `gather_signing_info` / `sign_bundle` / offer-taking flow (`chia/wallet/wallet_signer.py:94-117`, `333-351`).
3. Victim's wallet resolves `<victim_pubkey>` via `sum_hint_for_pubkey`/`path_hint_for_pubkey` (`chia/wallet/wallet_signer.py:55-92`) and signs `<arbitrary_message>` in `execute_signing_instructions()` (`chia/wallet/wallet_signer.py:198-212`), returning a valid `AugSchemeMPL` signature over `<arbitrary_message>` under the victim's real key — with no relationship checked between the "spend" shown to the victim and the actual coin/message signed.
4. Attacker takes this signature and inserts it (via `AGG_SIG_UNSAFE`) into a wholly different, unrelated spend bundle that references the same `<victim_pubkey>`/`<arbitrary_message>` pair to authorize a coin spend the victim never approved, then submits it to the mempool.

    async def gather_signing_info(self, spends: list[Spend]) -> SigningInstructions:
        pks: list[bytes] = []
        signing_targets: list[SigningTarget] = []
        for spend in spends:
            coin_spend = spend.as_coin_spend()
            # Get AGG_SIG conditions
            conditions_dict = conditions_dict_for_solution(
                coin_spend.puzzle_reveal,
                coin_spend.solution,
                self.max_block_cost_clvm,
            )
            # Create signature
            for pk, msg in pkm_pairs_for_conditions_dict(
                conditions_dict, coin_spend.coin, self.agg_sig_me_additional_data
            ):
                pk_bytes = bytes(pk)
                pks.append(pk_bytes)
                fingerprint: bytes = pk.get_fingerprint().to_bytes(4, "big")
                signing_targets.append(SigningTarget(fingerprint, msg, std_hash(pk_bytes + msg)))

        return SigningInstructions(
            await self.key_hints_for_pubkeys(pks),
            signing_targets,
        )

def pkm_pairs_for_conditions_dict(
    conditions_dict: dict[ConditionOpcode, list[ConditionWithArgs]],
    coin: Coin,
    additional_data: bytes,
) -> list[tuple[G1Element, bytes]]:
    ret: list[tuple[G1Element, bytes]] = []

    data = agg_sig_additional_data(additional_data)

    for cwa in conditions_dict.get(ConditionOpcode.AGG_SIG_UNSAFE, []):
        validate_cwa(cwa)
        for disallowed in data.values():
            if cwa.vars[1].endswith(disallowed):
                raise ConsensusError(Err.INVALID_CONDITION)
        ret.append((G1Element.from_bytes(cwa.vars[0]), cwa.vars[1]))
