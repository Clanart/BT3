### Title
Verifier/operator `secret_key` printed in clear text via `{:?}` debug logging - (File: core/src/config/env.rs)

### Summary
`BridgeConfig::from_env()` logs the entire, fully-populated configuration struct with `tracing::debug!("BridgeConfig from env: {:?}", config)`. `BridgeConfig` derives `Debug` and contains `pub secret_key: SecretKey` (the operator's/verifier's actual signing key), stored as a plain `bitcoin::secp256k1::SecretKey` rather than a redacting wrapper.

### Finding Description
`BridgeConfig` is declared with `#[derive(Debug, Clone, Deserialize)]` [1](#0-0) . Every other credential field in the same struct — `bitcoin_rpc_user`, `bitcoin_rpc_password`, `db_user`, `db_password` — is explicitly wrapped in `secrecy::SecretString`, whose `Debug` implementation redacts the value [2](#0-1) . The most sensitive field, `secret_key`, is left as a bare `bitcoin::secp256k1::SecretKey` with no redaction wrapper, so it participates in the struct's derived `Debug` formatting exactly like an unprotected field.

`BridgeConfig::from_env()` then logs the assembled struct at debug level: `tracing::debug!("BridgeConfig from env: {:?}", config);` [3](#0-2) . This is the same bug class as the reported `export.go` issue (encoding then printing raw private-key material), except here it is the entity's actual bridge signing key going through a formatting/logging path, not merely a test utility.

This maps to the report's "unsanitized credential logged in clear text" pattern, but on the party's actual N-of-N/operator signing key rather than an incidental credential.

### Impact Explanation
If this debug-level tracing output is captured (log files, log aggregation, `RUST_LOG=debug`, crash dumps, etc.), a party with log access recovers the verifier's or operator's raw `secret_key`. That key is used directly for MuSig2 partial signing (`Actor`/`nonce_pair`/`partial_sign` in `core/src/musig2.rs` and `core/src/actor.rs`), Winternitz key derivation, and Bitcoin transaction signing. Recovery of this key by anyone other than its owner allows forging that party's signatures/partial signatures — this is a "recoverable verifier secret" class of impact.

### Likelihood Explanation
The exposure only manifests at `debug`-level logging, and it depends on log collection/retention actually persisting or forwarding debug-level tracing output — this is a real but conditional exposure path, not something triggered by a normal unprivileged request. I could not verify from the available index whether `bitcoin::secp256k1::SecretKey`'s own `Debug` implementation additionally redacts its bytes at the crate level (this is third-party code I could not inspect); if the underlying crate's `Debug` impl already redacts the raw bytes, the practical severity of this specific line is reduced to a defense-in-depth gap rather than a guaranteed plaintext leak.

### Recommendation
Wrap `secret_key` in a type whose `Debug`/`Display` implementation redacts secret material (e.g. `secrecy::Secret<SecretKey>`, consistent with how `bitcoin_rpc_password`/`db_password` are already handled), or implement a custom `Debug` for `BridgeConfig` that explicitly masks `secret_key`. Additionally, avoid logging the fully assembled `BridgeConfig` via `{:?}` at all; log only non-sensitive fields.

### Proof of Concept
1. Set `RUST_LOG=debug` (or otherwise enable debug-level tracing) and run any Clementine binary that loads config via `BridgeConfig::from_env()`.
2. Observe the log line `BridgeConfig from env: BridgeConfig { ..., secret_key: <derived from bare SecretKey Debug impl>, ... }` emitted by `core/src/config/env.rs:255`.
3. Compare with the redacted output for `bitcoin_rpc_password`/`db_password` in the same log line, which show `Secret([REDACTED])`-style output because those fields use `secrecy::SecretString` — confirming the asymmetric protection and that `secret_key` is the outlier field lacking redaction.
