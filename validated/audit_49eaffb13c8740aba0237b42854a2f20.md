### Title
Zero-Operator Deposit Bypasses All Signature Verification, Permanently Locking Bridged BTC in Vault — (`core/src/verifier.rs`, `core/src/builder/sighash.rs`)

---

### Summary

`get_num_required_nofn_sigs` multiplies by `get_num_operators()`. When the operator list is empty, the result is zero. Every signature-count guard in `deposit_sign` and `deposit_finalize` compares against this zero, passes vacuously, and the verifier proceeds to sign the move-to-vault transaction — without any operator collateral backing, without any kickoff pre-signatures, and without any withdrawal mechanism. The BTC is moved to the vault and locked there permanently.

---

### Finding Description

**`get_num_required_nofn_sigs` collapses to zero with no operators** [1](#0-0) 

```rust
pub fn get_num_required_nofn_sigs(&self, deposit_data: &DepositData) -> usize {
    deposit_data.get_num_operators()          // ← 0 when no operators
        * self.protocol_paramset().num_round_txs
        * self.protocol_paramset().num_signed_kickoffs
        * self.get_num_required_nofn_sigs_per_kickoff(deposit_data)
}
```

Similarly, `get_num_required_operator_sigs` is non-zero per kickoff, but `num_required_total_op_sigs = num_required_op_sigs * get_num_operators()` = 0. [2](#0-1) 

**`deposit_sign` nonce-count guard passes vacuously**

With `num_required_sigs = 0`, the aggregator requests `num_required_nonces = 0 + 2 = 2` nonces. The verifier stores exactly 2 nonces. The guard at line 919 checks `0 + 2 != 2` → false → no error. The signing `while` loop runs zero iterations. The post-loop guard at line 965 checks `2 != 2` → false → no error. [3](#0-2) 

**`deposit_finalize` NofN and operator signature loops are both skipped**

`create_nofn_sighash_stream` iterates over `deposit_data.get_operators()`, which is empty, so the stream yields nothing immediately. The `while let Some(sighash)` loop exits at once, leaving `nonce_idx = 0`. The guard `nonce_idx != num_required_nofn_sigs` → `0 != 0` → false → passes. [4](#0-3) 

The operator-signature loop iterates over `operators_data.iter()` (empty), so `total_op_sig_count` stays 0. The guard `total_op_sig_count != num_required_total_op_sigs` → `0 != 0` → false → passes. [5](#0-4) 

**Execution continues to move-tx signing**

After both guards pass, the verifier creates the move-to-vault tx handler, pops the two reserved nonces, and produces valid partial signatures for the move tx and emergency-stop tx. These are returned to the aggregator, which aggregates them into a fully signed move tx. [6](#0-5) 

**`is_deposit_valid` has no minimum-operator check**

The validation function checks uniqueness, watchtower limits, and cross-references operators in the deposit against operators in the DB. Both loops iterate over empty collections and return no error. There is no `operators.len() > 0` guard. [7](#0-6) 

**Aggregator `new_deposit` also has no guard**

`fetch_operator_keys()` returns `Ok(vec![])` when no operator clients are configured (the `all_collected` vacuous-truth path in `fetch_pubkeys_from_entities`). `collect_and_distribute_keys` completes immediately because the `while received_keys.len() < num_operators` condition is `0 < 0 = false`. [8](#0-7) [9](#0-8) 

---

### Impact Explanation

The move-to-vault transaction is broadcast and confirmed. The BTC now sits in a Taproot vault address controlled by the N-of-N verifier key. Because no operators were registered:

- No kickoff transactions exist (operators pre-sign them during setup).
- No withdrawal can ever be initiated.
- The BTC is permanently locked in the vault until the security council creates a replacement deposit — which itself requires operators to be present for the replacement deposit to be processable.

This is a **permanent lock of bridged BTC** matching the "permanent lock of bridge-controlled UTXOs" impact gate.

---

### Likelihood Explanation

The trigger condition — zero active operators — can arise in two realistic ways:

1. **Fresh deployment**: The aggregator is started and a user sends BTC to the deposit address before any operator has called `set_operator`. The aggregator's `fetch_operator_keys()` returns an empty list and `new_deposit` proceeds.
2. **All collateral spent**: Every registered operator's collateral UTXO is spent (e.g., all operators were slashed or exited). `is_deposit_valid` iterates over an empty `operators_in_db` and raises no error.

Neither path requires privileged access beyond the ability to call the public `new_deposit` gRPC endpoint.

---

### Recommendation

Add an explicit minimum-operator guard in `is_deposit_valid` (and optionally in `new_deposit`):

```rust
// In is_deposit_valid, after the uniqueness checks:
if deposit_data.get_num_operators() == 0 {
    return Err(BridgeError::InvalidDeposit(
        "Deposit must include at least one operator".to_string()
    ));
}
``` [10](#0-9) 

Additionally, add a symmetric guard in `get_num_required_nofn_sigs` or at the call site in `new_deposit` to reject a zero-operator deposit before the signing pipeline is even started. [1](#0-0) 

---

### Proof of Concept

1. Deploy Clementine with N verifiers but **zero operators** (no `set_operator` calls made, or all operator collateral UTXOs spent).
2. Send `bridge_amount` BTC to the deposit address.
3. Call `aggregator.new_deposit(deposit)`.
4. Observe:
   - `fetch_operator_keys()` returns `[]`.
   - `get_num_required_nofn_sigs` = 0.
   - `deposit_sign` completes with 0 partial signatures produced for protocol transactions.
   - `deposit_finalize` completes with 0 NofN signatures verified and 0 operator signatures verified.
   - A fully signed move-to-vault transaction is returned and broadcast.
   - The BTC is confirmed in the vault.
5. Attempt any withdrawal — no kickoff transaction exists; no operator can initiate one. The BTC is permanently locked.
