## Analysis

The Bridges bug's root cause is: an **unbounded loop whose iteration count is controlled by an attacker who can cheaply add entries to a list**, later consumed in a single unbounded pass that exceeds a resource budget (gas/CPU/time).

The closest real analog in this codebase is in Agave's `getProgramAccounts` RPC path, specifically the **non-indexed fallback scan**, which has no size/byte cap — unlike the secondary-index path, which does.

### The vulnerable path

`get_filtered_program_accounts` in the JSON-RPC layer branches on whether a secondary `ProgramId` index is configured. If it is *not* configured (the common/default validator configuration, since secondary indexes carry significant memory overhead), it falls straight into an unbounded scan: [1](#0-0) 

That calls `Bank::get_filtered_program_accounts`, which delegates to `Accounts::load_by_program_with_filter`: [2](#0-1) [3](#0-2) 

This ultimately calls `AccountsDb::scan_accounts`, which iterates over **every account visible from the bank's ancestors** and invokes `scan_func` for each one, with `ScanConfig::default()` — i.e. no `byte_limit_for_scan`, no abort mechanism: [4](#0-3) 

Contrast this with the *indexed* path (`load_by_index_key_with_filter`), which explicitly tracks accumulated result size and aborts the scan once `byte_limit_for_scan` is exceeded: [5](#0-4) 

The asymmetry is intentional but consequential — the comment in `rpc.rs` states plainly: "this path does not need to provide a mb limit because we only want to support secondary indexes" [6](#0-5) . In other words, unless the operator has paid the memory cost of enabling the `ProgramId` secondary index, there is **no cap at all** on how many accounts get materialized into the in-memory `Vec<(Pubkey, AccountSharedData)>` before being serialized into an RPC response.

### Mapping to the Bridges bug class

| Bridges (`distributeDividends`) | Agave analog |
|---|---|
| Attacker deposits miniscule LP to pool 0 | Attacker cheaply creates many rent-exempt accounts owned by an attacker-chosen program id (system-program create_account is nearly free per account) |
| `usersBridges` list grows unbounded | The set of live accounts owned by that `program_id` grows unbounded |
| `distributeDividends` iterates the whole list in one unbounded `for` loop | `scan_accounts` iterates every matching account in one unbounded loop, with no `ScanConfig` abort/size cap on this code path |
| Loop exceeds block gas limit → DoS for all dividend recipients | Scan materializes unbounded memory / unbounded CPU time in the RPC thread pool → single client's low-rate `getProgramAccounts` call degrades/crashes the node (OOM or long scan blocking a blocking-task thread) |

This satisfies the "single-client low-rate RPC crash/degradation" criterion explicitly listed as valid impact, and the attacker primitive (repeatedly, cheaply creating accounts owned by a program they control, then issuing one RPC call) requires no malicious peer/validator/leaked-key assumption — it is fully achievable by an ordinary unprivileged RPC client plus normal transaction submission.

### Caveat

This is a long-known category of risk with `getProgramAccounts` (that's why the byte-limited indexed path exists at all), and many operators mitigate it operationally (disabling the method, enabling secondary indexes, or fronting RPC with a proxy that limits/deny-lists such calls). Whether this counts as a "fresh" finding versus a known, already-partially-mitigated design tradeoff is a judgment call — the code itself does not enforce any limit on the non-indexed path, so the underlying invariant violation is real and present in the reviewed code, but it is a pre-existing/known risk pattern rather than a newly discovered regression.

    pub(crate) fn scan_accounts<F>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        mut scan_func: F,
        config: &ScanConfig,
    ) -> ScanResult<()>
    where
        F: FnMut(Option<(&Pubkey, AccountSharedData, Slot)>),
    {
        // Register this scan so that slots needed by the scan are not cleaned out from under us.
        let scan_guard = ScanGuard::try_new(&self.scan_tracker, bank_id, || self.max_root())
            .ok_or(ScanError::SlotRemoved {
                slot: ancestors.max_slot(),
                bank_id,
            })?;

        // If the scan's ancestors are all rooted, drop them and scan roots only
        // Scan Guard max root must be used as the scan guard guarantees that
        // the account state as of max root is persisted in the database
        let max_root_ancestors = Ancestors::from(vec![scan_guard.max_root()]);
        let ancestors = if scan_guard.should_use_ancestors(ancestors) {
            ancestors
        } else {
            &max_root_ancestors
        };

        // Step 1: Pre-scan the cache index to find the newest visible cached version of each
        // pubkey. Hold the Arc<CachedAccount> to keep the data alive even if the cache flushes
        // between now and step 3 (Arc clone is just a refcount bump).
        let cached_pubkeys = self.accounts_cache.cached_pubkeys();
        let mut cached_versions =
            HashMap::with_capacity_and_hasher(cached_pubkeys.len(), PubkeyHasherBuilder::default());
        for pubkey in cached_pubkeys {
            if config.is_aborted() {
                break;
            }

            if let Some((cached_account, slot)) =
                self.accounts_cache.load_latest(&pubkey, ancestors)
            {
                cached_versions.insert(pubkey, (cached_account, slot));
            }
        }

        // either the storage or the cache. If both versions are the same, use the cached version
        // to avoid a redundant load from storage.
        // Bound max_root by ancestors.min_slot() so that roots from slots
        // beyond the querying bank's ancestor chain are not visible.
        let mut max_root = scan_guard.max_root();

            max_root = max_root.min(min);
        }

            ancestors,
            max_root,
