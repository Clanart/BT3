### Title
Supermajority Threshold Counts Raw Signature Entries Instead of Distinct Signers in BEEFY Consensus Verification - (File: `modules/consensus/beefy/verifier/src/lib.rs`, `evm/src/consensus/EcdsaBeefy.sol`)

### Summary
The external report's root cause — counting signatures instead of distinct signers when checking a `minRequired` threshold — has a direct structural analog in Hyperbridge's BEEFY consensus client. Both the Rust verifier and the Solidity `EcdsaBeefy` contract compute the supermajority participation count directly from the length of the attacker-supplied signature/vote array, before any check that the underlying signatures come from distinct authorities.

### Finding Description
In `verify_mmr_update_proof`, the participation count used for the 2/3+1 threshold gate is taken straight from the submitted array length: [1](#0-0) 

The loop that follows builds `authority_indices`/`authority_leaves` directly from each `sig.index` in the (attacker-controlled) proof, with no deduplication of `sig.index` or the recovered `eth_address` before or after the threshold check: [2](#0-1) 

`check_participation_threshold` itself is a pure length comparison with no notion of uniqueness: [3](#0-2) 

The Solidity `EcdsaBeefy.sol` mirrors the exact same pattern — `sigLen` is `relayProof.signedCommitment.votes.length`, gated against the threshold, then each vote is ECDSA-recovered into a leaf without any per-index/per-address dedup: [4](#0-3) 

This contrasts sharply with two other consensus verifiers in the same repo that explicitly guard against this exact class of bug: the Tendermint verifier's `ensure_unique_addresses` and the Pharos verifier's `verify_validator_membership`, both of which reject duplicate signer/participant entries via a `BTreeSet`/`BTreeMap` dedup check before counting toward any threshold: [5](#0-4) [6](#0-5) 

The BEEFY verifier (both Rust and Solidity implementations) has no equivalent uniqueness check on `authority_indices`/`vote.authorityIndex` prior to (or as part of) the participation-threshold decision — exactly the pattern the external report flags as the root cause (`validateClosestActiveNodeSignatures` counting repeated signatures as distinct signers).

### Impact Explanation
`handleConsensus` in `HandlerV2.sol` is a public, unauthenticated entrypoint reachable by anyone: [7](#0-6) 

If an attacker who controls even a small number (potentially as few as one) of the BEEFY authority set's ECDSA keys can pad `relayProof.signedCommitment.votes` (or `mmr.signed_commitment.signatures` in the Rust path) with repeated copies of the same valid signature/index, the `sigLen`/`signatures_length` threshold gate can be satisfied without a genuine 2/3+1 supermajority of distinct authorities ever having signed the commitment. This would cause the consensus client to accept a forged/insufficiently-attested MMR root update and downstream parachain state commitments, i.e. false state acceptance — directly enabling forged state machine commitments to be stored via `host.storeStateMachineCommitment`, which subsequently gates request/response/timeout handling and asset movement throughout the protocol.

### Likelihood Explanation
Exploitability is bounded by whether the downstream merkle multi-proof verification (`rs_merkle::MerkleProof::verify` in Rust, `MerkleMultiProof.VerifyProof` in Solidity — both external library dependencies not present in this repo) tolerates duplicate `(index, hash)` entries in its leaf/index arrays well enough to still validate a tree containing genuinely fewer unique authority leaves than `authority_set.len` requires for the stated threshold. I could not fully verify from the code available in this repository whether that external merkle library silently accepts duplicate indices/leaves or rejects them outright, since `rs_merkle` and `solidity-merkle-trees` are external dependencies. This is the key uncertainty in this finding: the counting bug in `check_participation_threshold`/`checkParticipationThreshold` is unambiguous and directly analogous to the reported bug class, but whether it is independently exploitable end-to-end depends on behavior of an out-of-repo merkle proof library that was not indexed here.

### Recommendation
Deduplicate `authority_indices` (and/or the recovered signer addresses) before computing the value passed into `check_participation_threshold`/`checkParticipationThreshold`, mirroring the `ensure_unique_addresses` (Tendermint) / `verify_validator_membership` (Pharos) pattern already used elsewhere in this codebase — reject the proof if `sig.index`/`vote.authorityIndex` (or recovered addresses) contain duplicates, and only count unique signers toward the supermajority requirement.

### Proof of Concept
Full exploitation could not be conclusively demonstrated without access to the external `rs_merkle`/`solidity-merkle-trees` verify implementations to confirm duplicate-index handling. Conceptually:
1. Attacker (holding at least one valid BEEFY authority ECDSA key, or with access to a previously broadcast valid signature over a commitment) constructs a `RelayChainProof`/`MmrProof` whose `votes`/`signatures` array repeats the same `(authorityIndex, signature)` pair enough times to make `sigLen`/`signatures_length >= (2/3)*authoritySet.len + 1`.
2. Calls `handleConsensus(host, proof)` (public, no access control) on `HandlerV2.sol`, or the equivalent Rust `verify_consensus` entrypoint.
3. If the merkle multi-proof step does not independently reject duplicate leaf indices, the forged commitment is accepted despite lacking a genuine supermajority of distinct signers, and a false MMR root / parachain state commitment is stored via `host.storeStateMachineCommitment`.

/// Rejects a validator set that reuses the same address twice. Each address is a
/// hash of its public key, so a duplicate signals a set that was not built honestly.
fn ensure_unique_addresses(
	validators: &[cometbft::validator::Info],
) -> Result<(), VerificationError> {
	let unique = validators.iter().map(|v| v.address).collect::<BTreeSet<_>>();
	if unique.len() != validators.len() {
		return Err(VerificationError::ValidatorSetError(
			"duplicate validator address in set".to_string(),
		));
	}
	Ok(())
}

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
