### Title
EVM-originated native value transfers bypass the Cosmos `BlockedAddr` check enforced by bank sends — ([File: x/evm/state/balance.go])

### Summary
Sei's EVM `StateDB` balance mutations (`AddBalance`/`SubBalance`), which back every native-value transfer inside EVM execution, call the bank keeper's low-level `AddCoins`/`SubUnlockedCoins`/`AddWei`/`SubWei` primitives directly. These primitives perform no `BlockedAddr` check. In contrast, the Cosmos-native path for moving funds (`MsgSend`, the bank precompile's `send`, and the wasm `BankCoinTransferrer`) explicitly checks `BlockedAddr` before calling `SendCoins`. This creates the same "forced/internal accounting bypasses a check that the user-initiated path enforces" asymmetry described in the GMX report, but here it lets an unprivileged EVM transaction credit funds directly into an account that the bank module is supposed to protect from ever receiving external transfers.

### Finding Description
The EVM StateDB balance functions are the sole mechanism by which native-value CALLs move `usei`/`wei` balances during EVM execution: [1](#0-0) [2](#0-1) 

Both `SubBalance` and `AddBalance` resolve the counterparty's Sei address via `getSeiAddress`, which falls back to a direct byte-cast of the EVM address when no association exists: [3](#0-2) 

They then call `BankKeeper().AddCoins` / `SubUnlockedCoins` and `AddWei` / `SubWei` directly — none of which check `BlockedAddr`: [4](#0-3) 

By contrast, the Cosmos-native/precompile transfer path used for ordinary `MsgSend`-style transfers goes through code that explicitly rejects blocked recipients before invoking `SendCoins`: [5](#0-4) 

and the bank module's own documentation states the purpose of this check — protecting module accounts and other reserved addresses from unexpected inbound transfers because doing so can break state-machine invariants: [6](#0-5) 

Since Sei module accounts (bonded pool, distribution, gov, etc.) and other blocklisted addresses are 20-byte `sdk.AccAddress` values, an attacker can compute an EVM address whose raw 20 bytes equal a target blocked module account's address bytes. As long as that specific EVM address has never been explicitly associated with a different Sei address via `SetAddressMapping`, `GetSeiAddressOrDefault` will byte-cast it straight to the blocked module's real account address. A plain EVM `CALL` carrying `value` to that address then runs through `AddBalance`, silently crediting `usei`/`wei` into the module account — something a normal `MsgSend`, the bank precompile `send`, or the wasm bridge would all refuse to do to the same address.

### Impact Explanation
Module accounts and other blocked addresses are relied upon by other Cosmos modules (staking, distribution, gov, mint) to hold *only* what the state machine itself deposits through controlled code paths. Uncontrolled external credits to these accounts break supply/balance invariants those modules assume (e.g., the bonded pool's balance no longer matches the sum of delegations, or the distribution module's fee pool receives unaccounted `usei`). The bank module's own spec calls out that such invariant breaks "could result in a halted network." This is a chain-halt/fund-accounting risk reachable purely from a normal EVM transaction sender.

### Likelihood Explanation
The bug requires only:
1. Knowledge of a target blocked module account's `sdk.AccAddress` bytes (these are deterministic and public, e.g. `authtypes.NewModuleAddress("distribution")`).
2. Sending a plain EVM transaction with `value` to the EVM address whose raw bytes equal those module-account bytes, provided that specific EVM address has not been separately associated with a different Sei account.

No special privileges, precompile access, or contract deployment are needed — a single crafted EVM transfer suffices. The main uncertainty is whether some other check (e.g. `CanAddressReceive`, which exists in `x/evm/keeper/address.go` but whose call sites could not be confirmed in this pass) is invoked somewhere in the value-transfer path to block this specific case; this was not verified due to the investigation being cut short, so likelihood should be treated as tentative until that call path is traced end-to-end.

### Recommendation
Add a `BlockedAddr` (or equivalent `CanAddressReceive`) check inside `AddBalance` in `x/evm/state/balance.go` before crediting a recipient whose resolved Sei address is a bank-blocked address, mirroring the check already performed by `MsgSend`/precompile `send`/`BankCoinTransferrer`. Alternatively, reject EVM value transfers whose destination resolves (via cast or association) to any address in the bank module's `blockedAddrs` set at the EVM state-transition level.

### Proof of Concept
1. Compute `distrModAddr := authtypes.NewModuleAddress(distrtypes.ModuleName)` (a blocked `sdk.AccAddress`).
2. Treat those same 20 bytes as an EVM address: `evmAddr := common.BytesToAddress(distrModAddr)`.
3. Confirm no `SetAddressMapping` exists for `evmAddr` (default state), so `GetSeiAddressOrDefault(ctx, evmAddr)` returns `distrModAddr` directly (per `x/evm/keeper/address.go` lines 58-64).
4. From any funded EOA, submit a standard EVM transaction: `CALL` (a plain value transfer, e.g. `to: evmAddr, value: X`).
5. Observe that `AddBalance` credits `X` usei/wei to `distrModAddr` via `BankKeeper().AddCoins`/`AddWei` with no `BlockedAddr` check (`x/evm/state/balance.go` lines 64-95).
6. Compare with an attempted `MsgSend`/bank-precompile `send` to the bech32 form of `distrModAddr`, which is rejected due to the `BlockedAddr` check enforced by the Cosmos-native send path (`sei-wasmd/x/wasm/keeper/keeper.go` lines 1198-1221 shows the pattern used to reject blocked recipients).

func (s *DBImpl) SubBalance(evmAddr common.Address, amtUint256 *uint256.Int, reason tracing.BalanceChangeReason) uint256.Int {
	s.k.PrepareReplayedAddr(s.ctx, evmAddr)
	amt := amtUint256.ToBig()
	if amt.Sign() == 0 {
		return *ZeroInt
	}
	if amt.Sign() < 0 {
		return s.AddBalance(evmAddr, new(uint256.Int).Neg(amtUint256), reason)
	}

	ctx := s.ctx
	var oldBalance *uint256.Int
	if s.logger != nil && s.logger.OnBalanceChange != nil {
		oldBalance = s.GetBalance(evmAddr)
	}

	// this avoids emitting cosmos events for ephemeral bookkeeping transfers like send_native
	if s.eventsSuppressed {
		ctx = ctx.WithEventManager(sdk.NewEventManager())
	}

	// Hook for mock balances (no-op in production builds)
	s.ensureSufficientBalance(evmAddr, amt)

	usei, wei := SplitUseiWeiAmount(amt)
	addr := s.getSeiAddress(evmAddr)
	err := s.k.BankKeeper().SubUnlockedCoins(ctx, addr, sdk.NewCoins(sdk.NewCoin(s.k.GetBaseDenom(s.ctx), usei)), true)
	if err != nil {
		s.err = err
		return *ZeroInt
	}
	err = s.k.BankKeeper().SubWei(ctx, addr, wei)
	if err != nil {
		s.err = err
		return *ZeroInt
	}

	addr, ok := k.GetSeiAddress(ctx, evmAddress)

	}

// TransferCoins transfers coins from source to destination account when coin send was enabled for them and the recipient
// is not in the blocked address list.
func (c BankCoinTransferrer) TransferCoins(parentCtx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amount sdk.Coins) error {
	em := sdk.NewEventManager()
	ctx := parentCtx.WithEventManager(em)
	if err := c.keeper.IsSendEnabledCoins(ctx, amount...); err != nil {
		return err
	}
	if c.keeper.BlockedAddr(toAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", toAddr.String())
	}

	sdkerr := c.keeper.SendCoins(ctx, fromAddr, toAddr, amount)
	if sdkerr != nil {
		return sdkerr
	}
	for _, e := range em.Events() {
		if e.Type == sdk.EventTypeMessage { // skip messages as we talk to the keeper directly
			continue
		}
		parentCtx.EventManager().EmitEvent(e)
	}
	return nil
}

## Blocklisting Addresses

The `x/bank` module accepts a map of addresses that are considered blocklisted
from directly and explicitly receiving funds through means such as `MsgSend` and
`MsgMultiSend` and direct API calls like `SendCoinsFromModuleToAccount`.

Typically, these addresses are module accounts. If these addresses receive funds
outside the expected rules of the state machine, invariants are likely to be
broken and could result in a halted network.
