## Answer

`openFile` performs **no path canonicalization, `lstat`/symlink check, or extension allow‑list** before handing the path to the shell. It simply builds a `file://` URI from the raw `fullPath` argument and calls `shell.openExternal`: [1](#0-0) 

`shell.openExternal` in the renderer is a typed IPC proxy that forwards straight to the main process (`invokeProxy('open-external', 1)`), with no additional path validation on the renderer side: [2](#0-1) 

Compare this to the sibling helper `showFolderContents` in the same file, which explicitly does `stat()`/`isApplicationBundle()` checks before opening a *directory* to avoid accidentally launching an app bundle on macOS: [3](#0-2) 

No equivalent protective logic (real‑path resolution, `lstat` to detect a symlink, or `.lnk`/executable extension gating) exists for `openFile`/`openExternal`. The doc-comment on the `IAppShell` interface even flags this as caller responsibility rather than something enforced by the code: *"Do not use this method with non‑validated paths."* [4](#0-3) 

### Title
`openFile` opens raw, unvalidated repository paths via `shell.openExternal` with no symlink/`.lnk` resolution guard - (File: `app/src/ui/lib/open-file.ts`)

### Summary
`openFile` takes a `fullPath` derived from repository file listings (e.g., changed/committed files shown in the Changes/History/Pull‑Request‑Files views) and passes it unchanged to `shell.openExternal`. If that path is a symlink (POSIX) or points at a `.lnk`/shortcut-style file (Windows), the OS shell will resolve/execute whatever target the file references, which can live entirely outside the cloned repository.

### Finding Description
Multiple UI surfaces call `openFile` with a path built from repository content: [5](#0-4) [6](#0-5) [7](#0-6) 

`openFile` itself does no `fs.lstat`/`fs.realpath` check to detect that the target is a symlink, nor does it restrict the resolved target to stay within `repository.path`. It only wraps the path in a `file://` URI and asks the OS default-application handler to open it: [8](#0-7) 

Because the file is tracked as ordinary repository content (git symlink mode `120000` on POSIX, or a plain committed `.lnk` binary on Windows), an attacker who controls a repository (or a PR the victim reviews) can commit such an entry. When the victim opens it from Desktop's UI, the OS-level "open with default program" behavior follows the symlink/shortcut target — which is outside the checked-out worktree.

### Impact Explanation
If the linked/shortcut target is an executable or script, invoking "open" causes it to run with the user's privileges — i.e., arbitrary code execution driven purely by attacker-controlled repository content, matching the bounty's "code execution... outside the repo" impact category.

### Likelihood Explanation
Requires the victim to explicitly choose an "open file" action (e.g., double-click / "Open with default program" context menu) on a file from an attacker-supplied repository/PR — a fairly natural interaction when reviewing unfamiliar file changes, but it does depend on the OS actually materializing the symlink (POSIX clones normally do; Windows requires Developer Mode/symlink support or falls back to a plaintext placeholder for `core.symlinks=false`, whereas a `.lnk` is checked out as an ordinary binary file regardless of symlink support and is always executable via shell association).

### Recommendation
Before calling `shell.openExternal`/`openPath`, resolve the real path with `fs.realpath`/`fs.lstat`, verify it stays within the repository's working directory (`repository.path`), and refuse or prompt the user when the target is a symlink pointing outside the repo or resolves to a `.lnk`/executable type. Mirror the caution already applied in `showFolderContents` (application-bundle detection) for `openFile`.

### Proof of Concept
1. Create a repo where a tracked file is a symlink (`ln -s /path/to/evil.sh payload.txt` then `git add -A`), or on Windows commit a `.lnk` file whose target is `cmd.exe /c calc.exe` (or a remote UNC path).
2. Clone the repo in GitHub Desktop.
3. In the Changes/History view, use the file's context action that triggers `openFile` (e.g., "Open File").
4. Observe that `shell.openExternal('file://.../payload.txt')` follows the symlink/shortcut and launches the external target rather than refusing or warning that the entry resolves outside the repository. [9](#0-8)

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```

```typescript
export async function showFolderContents(path: string) {
  const stats = await stat(path).catch(err => {
    log.error(`Unable to retrieve file information for ${path}`, err)
    return null
  })

  if (!stats) {
    return
  }

  if (!stats.isDirectory()) {
    log.error(`Trying to get the folder contents of a non-folder at '${path}'`)
    await _showItemInFolder(path)
    return
  }

  // On Windows and Linux we can count on a directory being just a
  // directory.
  if (!__DARWIN__) {
    UNSAFE_openDirectory(path)
    return
  }

  // On macOS a directory might also be an app bundle and if it is
  // and we attempt to open it we're gonna execute that app which
  // it far from ideal so we'll look up the metadata for the path
  // and attempt to determine whether it's an app bundle or not.
  //
  // If we fail loading the metadata we'll assume it's an app bundle
  // out of an abundance of caution.
  const isBundle = await isApplicationBundle(path).catch(err => {
    log.error(`Failed to load metadata for path '${path}'`, err)
    return true
  })

  if (isBundle) {
    log.info(
      `Preventing direct open of path '${path}' as it appears to be an application bundle`
    )

    await _showItemInFolder(path)
  } else {
    UNSAFE_openDirectory(path)
  }
}
```
