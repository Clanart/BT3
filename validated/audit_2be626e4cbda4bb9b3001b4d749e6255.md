### Title
Multi-asset escrow release/refund in IntentGatewayV2 is all-or-nothing — a single non-transferable token permanently locks every other escrowed asset in the same order - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`_withdraw()` in `IntentsBase.sol` iterates over every token in a `WithdrawalRequest` and transfers them to the beneficiary in a single loop, inside a single atomic call. [1](#0-0) 
This function is the sole exit path for escrowed order funds, invoked both for successful cross-chain fills (`RedeemEscrow`) and for cancellations/refunds (`RefundEscrow`) via `onAccept`, as well as for same-chain fills and cancels. [2](#0-1) 
Because the token transfers happen in one loop with no per-token isolation, if a single token in a multi-token order becomes permanently non-transferable to the beneficiary (e.g. a centrally-blacklistable stablecoin like USDC denylists the beneficiary, or the token is paused/frozen), `_withdraw` reverts on every call — for both the fill-redemption path and the refund/cancellation path — because both use the identical `_withdraw` function and both include the same full `body.tokens` array.

### Finding Description
An `Order` can escrow multiple input tokens (`order.inputs`), and settlement always calls `_withdraw(body, ..., finalize=true)` with the complete token list for that order. [3](#0-2) 
`safeTransfer`/native `.call` failures propagate as a revert of the whole `_withdraw` call, and since Solidity reverts undo all state changes in the same transaction, the `_orders[commitment][token] -= amount` decrements for every *other* token in the loop are rolled back too, along with the `_filled[commitment] = beneficiary` write made at the top of the function. [4](#0-3) 

This exactly mirrors the reported bug class: several independent "legs" (there: separate withdrawal requests across different external protocols; here: separate ERC-20 legs of one order) are required to *all* succeed atomically, and a permanent failure of just one leg — driven by conditions entirely outside the protocol's control (an external token issuer's blacklist, pause, or denylist) — blocks the release of every other leg indefinitely.

For the cross-chain path, `onAccept` in `EvmHost.dispatchIncoming` catches the revert and deletes the request receipt "so it can be retried," but retrying does not help: the underlying cause (the beneficiary being blacklisted, or the token being paused) does not change between retries, so the failure is permanent, not transient. [5](#0-4) 

Critically, the *same* `_withdraw` function backs the refund/cancellation path (`RefundEscrow`, `_cancelFromDest`, `_cancelFromSource`), so the affected order cannot even be cancelled to recover the unaffected tokens — cancellation dispatches the identical `WithdrawalRequest.tokens` array and hits the identical revert. [6](#0-5) 
There is no per-token retry, no ability to redeem/refund only the unaffected tokens, and no admin/permissionless mechanism to split or force-release a subset of a stuck order's escrow.

### Impact Explanation
This is a direct, unauthenticated, non-privileged fund-lock vector: any user or solver constructing/receiving a multi-token order that includes a centrally-controlled token (USDC, USDT, and similar blacklist-capable assets are explicitly common in cross-chain intent flows) is exposed. If the beneficiary address is ever blacklisted on just one of the escrowed/output tokens — which can happen for reasons entirely unrelated to the order (a prior unrelated sanction, a compliance freeze, etc.) — **100% of the escrowed value for that order becomes permanently unrecoverable**, not just the value denominated in the blacklisted token. This matches the "stealing or loss of funds" / logic-attack impact category: legitimate funds (including tokens that have no transfer restriction at all) are permanently locked in the gateway contract due to the all-or-nothing design, with no code path to disentangle them.

### Likelihood Explanation
No malicious relayer, prover, or governance actor is required. The trigger is solely an external token issuer's routine compliance action (blacklist/pause) against the beneficiary address, combined with any multi-token order that includes that token — both are realistic, foreseeable conditions in a protocol designed to be "extendable to new yield/asset types" with common stablecoins as at least one leg of many orders. This is a public-entrypoint path (`fillOrder`, `cancelOrder`, `onAccept`) reachable by any unprivileged party who places or fills an order containing the affected token.

### Recommendation
Make `_withdraw` resilient to a single-token failure: either (a) attempt each token transfer independently and retry/queue failed legs individually (e.g. store a per-token pending-withdrawal balance that can be claimed later once unblocked, similar to a pull-payment pattern), or (b) use try/catch around each token transfer so a revert on one token does not roll back the successful transfers of the others, finalizing the order and only leaving the failed token's specific balance in escrow for later resolution (e.g. via `SweepDust`-style recovery to a fallback address, or a dedicated re-claim function scoped to the single stuck token).

### Proof of Concept
1. User places a cross-chain order with two input tokens: `USDC` and `DAI`.
2. Solver fills the order on the destination chain; the destination gateway dispatches a `RedeemEscrow` message back to source with `body.tokens = [USDC, DAI]` and `beneficiary = solver`.
3. Before the message is delivered, `solver` is added to USDC's blacklist (a routine, protocol-external event).
4. `onAccept` on the source chain calls `_withdraw`; the loop successfully decrements `_orders[commitment][DAI]` and prepares to transfer DAI, but the subsequent `IERC20(USDC).safeTransfer(beneficiary, amount)` call reverts (`USDC blacklisted`), reverting the whole `_withdraw` call and undoing the DAI decrement as well.
5. `dispatchIncoming` deletes the request receipt to allow a retry, but every retry hits the exact same revert because the beneficiary's USDC blacklist status never changes.
6. `_cancelFromSource`/`_cancelFromDest` cannot rescue the DAI either, since cancellation dispatches the same `body.tokens` list through the same `_withdraw` function and fails identically.
7. Both the escrowed USDC and the otherwise-redeemable DAI are permanently locked in the `IntentGatewayV2` contract with no recovery path.
