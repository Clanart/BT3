## Analysis

The UFDao root cause was reliance on a manipulable, unprotected on-chain exchange computation ("incorrect parameter setting") when moving funds through a swap, allowing an attacker to extract value via price manipulation. The closest in-scope analog is in `wombat/SmartWomConvert.sol`'s `_convertFor` swap path, which is triggered automatically from `wombat/WombatStaking.sol` on ordinary user deposit/withdraw activity.

### Title
Zero-slippage AMM swap of protocol WOM fees in `smartConvert`/`_convertFor` enables sandwich-extraction of protocol yield - (File: wombat/SmartWomConvert.sol)

### Summary
`SmartWomConvert._convertFor` swaps WOM for mWom through `IWombatRouter.swapExactTokensForTokens` with `amountOutMin` hard-coded to `0` [1](#0-0) , while the routing decision itself (`convertRatio`) is derived from the same AMM's live spot price via `currentRatio()`, which calls `IWombatRouter.getAmountOut` on the `womMWomPool` [2](#0-1) . This function is invoked automatically and permissionlessly whenever `WombatStaking._sendRewards` routes protocol-collected WOM fees into `smartConvert` [3](#0-2) , which itself fires from `_toMasterWomAndSendReward`, called on ordinary user stake/unstake actions that trigger harvest [4](#0-3) .

### Finding Description
`smartConvert(_amountIn, _mode)` computes `convertRatio` from `currentRatio()`, an unguarded spot-price read of the `womMWomPool` via the Wombat router [2](#0-1) . If the ratio is below `buybackThreshold`, it decides how much of the protocol's WOM fee to route through an AMM swap (`buybackAmount`) versus straight `mWom` minting via `IMWom(mWom).deposit` [5](#0-4) . The actual swap in `_convertFor` executes with `amountOutMin = 0`, giving the router zero slippage protection at the swap-call level [1](#0-0) . The only aggregate safety check is `convertAmount + amountRec < _minRec` where, for the `smartConvert` path, `_minRec` is set equal to the *input* WOM amount, i.e. only a 1:1 par floor, not a price-aware floor [6](#0-5) . Because both the *decision* (which pool state to trust) and the *execution* (unprotected swap) key off the same manipulable spot price, an attacker can pre-manipulate the `womMWomPool` (buy mWom to inflate `currentRatio` above/below `buybackThreshold`, or directly depress price before the swap executes) so that the protocol's WOM fee swap executes at an attacker-favorable rate, extracting value from protocol WOM fees that were destined to become staker/emission yield, and then reverse their manipulation trade for profit within the same block/transaction sequence. This flow is reachable from an ordinary wallet: any user calling deposit/withdraw against a WombatStaking pool triggers `_toMasterWomAndSendReward` → `_sendRewards` → `smartConvert`, with no privileged role required [7](#0-6) .

### Impact Explanation
Value is extracted directly from protocol-custodied WOM reward/fee funds that are intended to become staker-distributed mWom yield, at the expense of legitimate LP stakers who receive less converted yield than they should — this is a theft of unclaimed yield within the WombatStaking/SmartWomConvert reward pipeline, one of the explicitly in-scope impact classes.

### Likelihood Explanation
The trigger path (deposit/withdraw on a WombatStaking pool) is a completely ordinary, unprivileged user action that happens continuously in normal protocol operation, and the attacker only needs capital to move the `womMWomPool` price and the ability to time their own transaction around a harvest-triggering deposit/withdraw (or trigger one themselves), making this practically exploitable by any unprivileged wallet, matching the pattern of the referenced UFDao "incorrect parameter setting" exploit where price/quantity parameters were derived from a manipulable on-chain source without adequate protection.

### Recommendation
Do not use `IWombatRouter.getAmountOut`/spot pool state as the sole basis for both the swap-routing decision and the swap execution. Enforce a real `amountOutMin` on the `swapExactTokensForTokens` call in `_convertFor` derived independently (e.g., using the caller-supplied `_minRec` applied specifically to the swapped portion, not just the aggregate), and consider a TWAP or bounded-deviation check before allowing the automatic `smartConvert` path to route protocol fee funds through the AMM.

### Proof of Concept
1. Attacker observes/awaits a WombatStaking pool operation (any user deposit/withdraw) that will trigger `_toMasterWomAndSendReward` → `_sendRewards`, which calls `smartConvert` on accrued WOM fees [3](#0-2) .
2. Immediately before that transaction, attacker swaps against the `womMWomPool` to shift `currentRatio()` so that `smartConvert`'s branch logic and/or the subsequent zero-slippage swap in `_convertFor` executes unfavorably for the protocol (e.g., pool converts WOM to mWom at a depressed mWom price) [8](#0-7) [1](#0-0) .
3. Attacker reverses their initial pool manipulation trade after the protocol's swap lands, capturing the price differential as profit, funded by the protocol's WOM fee reserves that should have become staker yield.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
