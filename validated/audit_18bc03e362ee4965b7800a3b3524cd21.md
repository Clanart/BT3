### Title
Hard Error Return in `update_finalized_payouts` Loop Permanently Halts Verifier Block Processing — (`File: core/src/verifier.rs`)

### Summary

`update_finalized_payouts` iterates over payout txids for a finalized block and, upon finding any single txid absent from the block cache, immediately returns a hard error. Because the DB state that triggered the lookup is not rolled back, every subsequent attempt to process the same block hits the identical error, permanently stalling the verifier's finalized-block pipeline and blocking all downstream bridge operations (deposit tracking, withdrawal recognition, challenge dispatch).

### Finding Description

`update_finalized_payouts` in `core/src/verifier.rs` queries `get_payout_txs_for_withdrawal_utxos` to obtain all withdrawal UTXOs spent in a given block, then iterates over the results to extract the paying operator's xonly public key from the OP_RETURN output: [1](#0-0) 

When `block_cache.txids.get(&payout_txid)` returns `None` for any entry in the batch, the function executes:

```rust
return Err(eyre::eyre!("Payout tx not found in block cache").into());
``` [2](#0-1) 

This error propagates directly to `handle_finalized_block`, which calls `update_finalized_payouts` unconditionally: [3](#0-2) 

`handle_finalized_block` is the verifier's primary per-block processing entry point. A failure here prevents:
- `update_citrea_deposit_and_withdrawals` results from being committed
- `StateManager::dispatch_lcp_processed` from advancing the LCP height
- All downstream state machine transitions for that block [4](#0-3) 

The DB record that caused the lookup — a row in `bitcoin_syncer_spent_utxos` joining to `withdrawals` — is not deleted or modified by the error path. On every retry of the same block, `get_payout_txs_for_withdrawal_utxos` returns the same inconsistent row: [5](#0-4) 

The result is a permanent, self-reinforcing stall: the block cannot be processed, the pipeline does not advance, and the same error fires on every subsequent attempt.

### Impact Explanation

- **Liveness of the entire bridge is broken.** The verifier cannot advance past the stuck block, so no new deposits are recognized, no new withdrawals are tracked, and no malicious kickoffs are challenged.
- **Operator collateral is at risk.** Without challenge dispatch (`Duty::CheckIfKickoffMalicious`), a malicious operator can execute an unchallenged kickoff and claim reimbursement for a fraudulent withdrawal, draining bridge-controlled BTC.
- **All payout txids in the batch are skipped.** Even if only one entry is inconsistent, the remaining valid payout txids in the same block are never recorded, so `PayoutCheckerTask` never sees them as unhandled and the operator's kickoff/reimbursement flow stalls. [6](#0-5) 

### Likelihood Explanation

The inconsistency between `bitcoin_syncer_spent_utxos` and the block cache can arise from:

1. **Chain reorganization.** If a block is reorganized after its spent-UTXO rows are written but before the canonical flag is updated, the `block_id` passed to `update_finalized_payouts` may reference a non-canonical block whose spending txids are absent from the canonical block cache.
2. **Bitcoin syncer race condition.** The syncer writes spent-UTXO rows and the block cache is built independently; a partial write or ordering issue can produce a mismatch.
3. **DB corruption.** Any corruption of `bitcoin_syncer_spent_utxos` that introduces a wrong `spending_txid` for a given `block_id` triggers the condition.

None of these require privileged access or malicious deployment; they are operational edge cases inherent to a live Bitcoin-syncing system.

### Recommendation

Replace the hard `return Err(...)` with a log-and-continue pattern, identical to the fix applied in the Lombard reference:

```rust
for (idx, payout_txid) in payout_txids {
    let payout_tx_idx = match block_cache.txids.get(&payout_txid) {
        Some(idx) => idx,
        None => {
            tracing::error!(
                "Payout tx {:?} not found in block cache for block {:?}; skipping",
                payout_txid, block_id
            );
            continue;
        }
    };
    // ... rest of loop body
}
```

This allows all other payout txids in the batch to be processed normally while the anomalous entry is surfaced in logs for manual investigation, preserving bridge liveness.

### Proof of Concept

1. Arrange for `bitcoin_syncer_spent_utxos` to contain a row where `spending_txid = T` and `block_id = B`, but the actual block `B` does not contain transaction `T` (achievable via a reorg that is not fully cleaned up, or by directly inserting a test row).
2. Ensure `withdrawals` has a row whose `withdrawal_utxo_txid`/`withdrawal_utxo_vout` matches the UTXO in step 1.
3. Trigger `handle_finalized_block` for block `B`.
4. Observe that `update_finalized_payouts` returns `Err("Payout tx not found in block cache")`.
5. Observe that `handle_finalized_block` propagates the error and the block is never marked as processed.
6. On every subsequent invocation for block `B`, the same error fires — the verifier is permanently stuck. [7](#0-6)

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

        Ok(())
    }

    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;

        dbtx.commit().await?;

        Ok(true)
    }
