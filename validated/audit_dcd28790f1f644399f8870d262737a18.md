## Analog Found: Bandwidth-Subscription Eviction Griefing (analogous to `create_lock_for` DoS)

The reported bug's core primitive: an unprivileged caller can write state **for an arbitrary victim identifier** through a "for"-style entrypoint, at negligible per-call cost, filling a bounded per-victim structure and evicting/blocking the victim's legitimate, already-paid-for state. The Hyperbridge analog is `pallet-bandwidth`'s FIFO subscription list, fed by `BandwidthManager.purchase()`, which lets **anyone** credit **any** `(chain, app)` bucket.

### Title
Unprivileged bandwidth purchases can evict a victim app's paid-for subscriptions from the capped FIFO queue - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`BandwidthManager.purchase()` on the EVM side lets any caller specify an arbitrary target `app` (and `chain`) that receives the credited bandwidth subscription — the `app` parameter is never tied to `msg.sender`. On the pallet side, `Pallet::push_subscription` appends to a `BoundedVec<Subscription, ConstU32<1024>>` keyed by `(app_chain, app)`, and once the list is at the 1024 cap, **every** further push evicts the oldest (FIFO-head) entry, regardless of its remaining value. ### Finding Description
`purchase(bytes app, uint256 tier, uint256 months, bytes chain)` only validates that `app`/`chain` are non-empty and `months > 0`; it does not check that `app` corresponds to the caller in any way. The payload is dispatched as-is to `pallet-bandwidth`, whose `on_accept` credits the `(msg.chain, msg.app)` bucket named directly by the purchaser: [4](#0-3) 

`push_subscription` appends the new `Subscription` and, if the `BoundedVec` for that `(app_chain, app)` key is already at `MAX_SUBSCRIPTIONS` (1024), unconditionally removes index 0 — the oldest entry — before pushing the new one: [5](#0-4) 

Because any account can call `purchase()` targeting any victim `app`, an attacker can:
1. Wait for (or front-run) a victim's legitimate, high-value purchase (e.g. an 8 MB / multi-month `Tier4` subscription) landing in the `(chain, app)` FIFO.
2. Repeatedly call `purchase()` for the cheapest configured tier with `months = 1`, targeting the same `app`/`chain`, until the list fills to 1024 entries and then keeps pushing.
3. Each push beyond the cap evicts the current oldest entry. Since the FIFO is drain-ordered by insertion time (not by remaining value), once the attacker's spam entries advance the queue past the victim's position, the victim's still-unconsumed, dearly-paid subscription is evicted and its `remaining_bytes` are permanently lost — emitted only as an auditable `SubscriptionEvicted` event, with no recovery path.

This mirrors the `create_lock_for()` primitive exactly: an entrypoint parameterized by a victim identifier, no ownership/minimum-value gate, and a bounded per-victim list whose overflow behavior (forced eviction / `MAX_DELEGATES`-style revert) is attacker-triggerable and victim-unrecoverable.

### Impact Explanation
This is a direct loss-of-funds path: the victim app already paid real fee-token value (up to the top "$1000 / 8 MB" tier) for bandwidth that is silently destroyed before use, at a cost the attacker controls by choosing the cheapest tier and smallest `months`. It also causes unauthorized manipulation of protocol accounting state (`Allowance` FIFO) belonging to another party's `(chain, app)` identity, entirely from an unprivileged, unauthenticated (from the pallet's perspective, just "some registered manager relayed it") entrypoint — squarely inside the bounty's "stealing or loss of funds" and "logic attacks" categories, not merely a griefing/DoS nuisance, since real economic value is destroyed rather than just blocked.

### Likelihood Explanation
Medium: the attack is public-entrypoint-only, requires no privileged role, no relayer/prover collusion, and no malformed proof — pure use of `purchase()` as designed. The only friction is the attacker's own gas/fee-token cost to push enough entries to reach and evict the victim's position, which scales with how full the queue already is and the cheapest tier's price (a governance-set value, not protocol-enforced to have any floor beyond "non-zero"). For apps with light existing subscription-list occupancy (the common case, since 1024 entries represents "years of headroom" per the docs) the attack is comparatively cheap relative to the value destroyed when the victim later buys a large, long-duration tier.

### Recommendation
- Bind the credited `app` identity to the payer in some verifiable way (e.g., only allow an address to top itself up, or require a signed authorization from the `app` address to accept third-party sponsorship), removing the "anyone can write to anyone's bucket" primitive — mirroring the report's "restrict access to trusted entities" fix.
- Alternatively/additionally, evict based on remaining value or expiry proximity rather than strict insertion order, or maintain per-payer sub-quotas within the shared bucket so one payer's spam cannot force out another payer's entries.
- Consider a per-`(chain, app)` minimum purchase size/months, and/or per-source-chain rate limiting on `push_subscription` to raise the cost of filling the FIFO purely for eviction purposes.

### Proof of Concept
1. Governance configures `TierIndex::TierOne` with `bytes = X`, `duration_secs = Y`, and a low `tierPrice` on `BandwidthManager`; `TierIndex::TierFour` is a large/expensive tier.
2. Victim (owner of app `V` on chain `C`) calls `purchase(app=V, tier=TierFour, months=6, chain=C)` — a large `Subscription` is appended to `Allowance[C][V]`.
3. Attacker, with no relationship to `V`, repeatedly calls `purchase(app=V, tier=TierOne, months=1, chain=C)` from any account, `(1024 - current_len)` times to fill the list, then more times to begin evicting from the head.
4. Once eviction reaches the position of the victim's `TierFour` subscription, `push_subscription` removes it via `list.remove(0)` and fires `SubscriptionEvicted { app_chain: C, app: V, tier: TierFour, lost_bytes: <victim's unused bytes> }` — the victim's paid-for bandwidth is gone, and any subsequent legitimate ISMP traffic from app `V` under tier-four's allowance is rejected by `BandwidthGate::try_consume` for insufficient allowance. 		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});
