### Title
`ThresholdKeys::read` allocates attacker-controlled `n` scalars before validating parameters, enabling memory amplification DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` in `crypto/dkg/src/lib.rs` deserializes `t`, `n`, and `i` directly from untrusted bytes, then — for the `Constant` interpolation variant — performs `Vec::with_capacity(usize::from(n))` and allocates a `HashMap` worth of verification shares sized by `n`, all before `ThresholdParams::new(t, n, i)` validates the parameters at the end of the function. Since `n` is a raw `u16`, a few bytes of input can force a ~2 MB allocation plus up to 65535 field-element read attempts. This is a direct analog of CVE-2021-31409's class: an unbounded, attacker-controlled resource consumption in a deserialization path reachable with untrusted bytes.

### Finding Description
In `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632):

```rust
let (t, n, i) = (
  read_u16()?,
  read_u16()?,
  Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
);

let mut interpolation = [0];
reader.read_exact(&mut interpolation)?;
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));   // attacker-controlled allocation
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
    res
  }),
  1 => Interpolation::Lagrange,
  ...
```

Key facts:

- `n` comes straight from `u16::from_le_bytes` on the input stream — max 65535.
- With interpolation byte `0`, `Vec::with_capacity(usize::from(n))` allocates `n × size_of::<C::F>()` (~2 MB for a 32-byte scalar) after only ~20 bytes of input have been consumed. The subsequent `read_F` loop fails on the first missing byte, but the allocation has already occurred.
- The `verification_shares` loop then attempts `n` `read_G` decompressions before `ThresholdKeys::new` / `ThresholdParams::new` ever validate that `t <= n` or that `n` is sane — parameter validation happens only at line 626, after all reads and allocations.
- `ThresholdKeys::read` is explicitly listed as a sink for untrusted bytes, and the analogous allocation in `Transaction::read` for `DkgCommitments` shows the codebase itself treats `len * elem` checks before allocation as a required defense (`TRANSACTION_SIZE_LIMIT` check at coordinator/src/tributary/transaction.rs:286), which is absent here.

### Impact Explanation
An unprivileged party who can supply bytes to `ThresholdKeys::read` (e.g., key-material payloads relayed through coordinator/processor message paths, or any integrator deserializing externally supplied `ThresholdKeys`) can force a ~2 MB allocation per invocation with a ~20-byte input — an amplification factor of ~100,000×. Repeated or concurrent calls exhaust memory, killing the process. Additionally, supplying a full ~2–4 MB body drives up to 65535 `read_G`/`read_F` decompressions per call before the parameter check ever runs, burning CPU proportional to attacker-chosen `n`. This causes uncontrolled resource consumption (denial of service) reachable from public inputs, matching the CVE-2021-31409 bug class.

### Likelihood Explanation
The vulnerability requires a caller to feed attacker-influenced bytes into `ThresholdKeys::read`. `ThresholdKeys` are secret key material, so the primary exposure is where serialized keys cross trust boundaries (recovery flows, backup/restore, or any transport of serialized `ThresholdKeys`). Within Serai's own deployment most `ThresholdKeys::read` inputs are local/DB-sourced, which lowers practical reachability to Medium; the code defect itself (pre-validation allocation sized by an untrusted field) is unconditional and trivially triggered once any untrusted input path exists.

### Recommendation
Validate `t`, `n`, and `i` via `ThresholdParams::new(t, n, i)` immediately after reading them — before any allocation or group/scalar deserialization — and reject values that fail. Additionally, cap the `Vec::with_capacity(n)` / `HashMap` sizing by a reasonable maximum participant count, and only preallocate after the parameters are proven valid. The pattern used in `Transaction::read` (compute `count * element_size` and compare against a limit before allocating) should be applied here.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ristretto;
use dkg::ThresholdKeys;

fn main() {
  let mut buf = vec![];
  // Curve ID
  buf.extend(u32::try_from(Ristretto::ID.len()).unwrap().to_le_bytes());
  buf.extend(Ristretto::ID);
  // t = 1, n = 65535, i = 1
  buf.extend(1u16.to_le_bytes());
  buf.extend(65535u16.to_le_bytes());
  buf.extend(1u16.to_le_bytes());
  // interpolation = 0 (Constant) -> Vec::with_capacity(65535) of ~32-byte scalars
  buf.push(0);
  // Truncate here: the ~2 MB allocation has already happened by the time
  // the first read_F fails.

  // Each invocation allocates ~2 MB from ~20 bytes of input.
  // In a loop / concurrent context this exhausts memory.
  for _ in 0 .. 1000 {
    let _ = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice());
  }
}
```
