## Title
Unhandled UTF-8 decode crash when processing attacker-controlled DID metadata during wallet coin-state sync - (File: `chia/wallet/did_wallet/did_wallet_puzzles.py`)

### Summary
`did_program_to_metadata()` in `chia/wallet/did_wallet/did_wallet_puzzles.py` decodes the key/value bytes of a DID's curried metadata program as UTF-8 with no exception handling. This metadata comes directly from the on-chain puzzle reveal of a coin being processed during wallet sync, which is attacker-controlled data (any peer/network participant can create a DID coin with arbitrary non-UTF-8 metadata bytes), analogous to the CVE-2020-26421 pattern where a dissector crashed by feeding it malformed field data it did not validate before use.

### Finding Description
`did_program_to_metadata()`: [1](#0-0) 
```
def did_program_to_metadata(program: Program) -> dict[str, str]:
    metadata = {}
    for key, val in program.as_python():
        metadata[str(key, "utf-8")] = str(val, "utf-8")
    return metadata
```
iterates raw bytes decoded from a CLVM `Program` and calls `str(bytes, "utf-8")` on both keys and values without a `try/except`. `bytes.decode`/`str(bytes, "utf-8")` raises `UnicodeDecodeError` for any byte sequence that is not valid UTF-8 (e.g., a lone continuation byte). Since DID metadata is a curried argument of the DID inner puzzle, it is fully attacker-controlled content embedded in the coin's puzzle reveal — no validation step upstream constrains it to valid UTF-8 text.

This function is reached from `WalletStateManager.determine_coin_type()` when a wallet discovers/syncs a coin state and identifies it as a DID coin: [2](#0-1) 
The uncurried `metadata` field is passed into `DIDCoinData`, which is subsequently used by `DIDWallet.identify(...)` to invoke `did_program_to_metadata` (confirmed by the call graph: `did_wallet.py` calls `did_program_to_metadata` twice, and `wallet_state_manager.py` references it 5 times in this coin-identification/creation path). This is normal wallet sync behavior — a wallet processing DID coin states received from a full-node peer (which itself just relays on-chain data), not privileged/mocked-only code.

### Impact Explanation
A crafted DID coin (any user can create a DID singleton with arbitrary curried metadata bytes) that later gets surfaced to a victim wallet during coin-state sync/receive processing (e.g., DID transfer, "identify" during add_coin flows, or manual NFT/DID search) triggers an unhandled `UnicodeDecodeError` deep inside `WalletStateManager` sync/identification logic. Because this runs inside async wallet-sync callbacks rather than inside a caught top-level RPC handler boundary in all call paths, it can halt wallet-side processing of that coin state / sync batch, denying wallet service for anyone whose wallet observes the malicious DID coin — a spend-triggered processing halt matching the CVE's "denial of service via crafted data" bug class.

### Likelihood Explanation
Likelihood is Medium: creating a DID with attacker-chosen metadata bytes is a normal, unprivileged, one-time on-chain action (the DID puzzle takes user-supplied metadata at creation and update time), and any wallet that syncs/observes that coin (directly owned, watched, or encountered via an offer/transfer) will run it through `determine_coin_type` → `DIDWallet.identify` → `did_program_to_metadata`.

### Recommendation
Wrap the UTF-8 decoding in `did_program_to_metadata()` with error handling (e.g., `errors="replace"` or a `try/except UnicodeDecodeError` that stores raw hex/bytes as a fallback), so malformed metadata degrades gracefully instead of raising, mirroring how CVE-2020-26421 was fixed by adding bounds/validity checks before dissecting untrusted fields.

### Proof of Concept
1. Construct a DID singleton coin whose inner puzzle is curried with a metadata program containing a value list entry such as `(b"u" . b"\xff\xfe")` (invalid UTF-8 byte sequence) instead of a normal URI string.
2. Publish/confirm this DID coin on-chain (a standard, permissionless DID creation/update spend).
3. Have a victim wallet observe this coin (e.g., via `get_coin_state` sync, DID transfer to the victim, or `manual_nft_search`/DID identification flow) so that `WalletStateManager.determine_coin_type()` reaches the DID branch and calls into `DIDWallet.identify`, which calls `did_program_to_metadata(metadata_program)`.
4. `str(val, "utf-8")` raises `UnicodeDecodeError`, propagating out of the sync/identify coroutine uncaught at this layer.

**Note on uncertainty:** I could not fully trace every intermediate frame between `DIDCoinData`/`DIDWallet.identify` and the exact call to `did_program_to_metadata` (the tool output showed matches in `did_wallet.py` but I did not view the full function bodies), nor could I confirm whether an outer exception handler in the wallet sync loop (if any) catches generic `Exception` and simply logs/retries rather than crashing the process. This affects the exact severity of "processing halt" (per-coin skip vs. full sync-loop crash) and should be verified by inspecting `DIDWallet.identify` in `chia/wallet/did_wallet/did_wallet.py` and the caller of `determine_coin_type` for surrounding try/except scope.
