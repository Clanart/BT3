### Title
Tier-gaming via ordered `mode=2`→`mode=1` calls lets an attacker unlock a higher flat-rate multiplier with a fraction of committed capital - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.incentiveDeposit`'s `mode==1` reward path uses `getUserTier`, which reads the account's *current* `mWomSV.getUserTotalLocked` balance with no snapshot/consistency protection, while `mode==2` mutates that same balance via `ILocker(mWomSV).lockFor` before returning. By first calling `incentiveDeposit` with `_mode=2` on a small slice of WOM to cross a tier threshold, then calling `incentiveDeposit` with `_mode=1` on the remaining (larger) slice, an attacker gets the boosted flat-rate multiplier applied to an amount that was never actually locked, extracting more MGP reward from the contract's reward pool than the tiered/progressive design intends.

### Finding Description
`getRewardAmount` has two mutually inconsistent computation branches:
- `_lock == false` (mode 1): `mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR`, a **flat** rate based solely on the account's tier at call time, with no double-counting protection and no tracking of amount already staked via mode 1. [1](#0-0) 
- `_lock == true` (mode 2): a **progressive**, tier-bracket calculation over `accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)`, minus `calDoubledCounted(_account)` to avoid re-rewarding already-locked balance. [2](#0-1) 

`getUserTier` is derived purely from live `mWomSV.getUserTotalLocked(_account)`: [3](#0-2) 

`incentiveDeposit` computes the reward and then performs the deposit/lock: [4](#0-3) 

For `_mode == 2`, `_deposit` calls `ILocker(mWomSV).lockFor(mWomBal, _account)`, which immediately updates `mWomSV`'s internal accounting (via `MasterMagpie.depositMWomSVFor`) so that `getUserTotalLocked` reflects the new lock as soon as the call returns: [5](#0-4) [6](#0-5) 

Because `incentiveDeposit` is `nonReentrant` but not otherwise rate-limited or snapshotted per transaction, an attacker's own contract can issue two sequential top-level calls to `incentiveDeposit` (`nonReentrant` only blocks re-entrant nested calls, not sequential calls in the same or different transactions):
1. Call `incentiveDeposit(_amountA, ..., _mode=2)` with just enough WOM to push `mWomSV.getUserTotalLocked(account)` across the next `rewardTier` threshold. This raises `getUserTier(account)`.
2. Call `incentiveDeposit(_amountB, ..., _mode=1)` with a much larger remaining WOM balance. `getRewardAmount` now reads the *already elevated* tier from step 1 and applies its multiplier as a **flat rate over the full `_amountB`**, even though `_amountB` is only converted (via `smartWomConvert.depositFor`), not locked in `mWomSV` at all.

The mode 1 branch has none of the safeguards mode 2 has (`calDoubledCounted`), and it does not track a per-account "already staked at flat rate" total, so this can be repeated as long as the contract's MGP balance (`mgpleft` cap) allows, letting an attacker extract disproportionate MGP relative to how much WOM they actually lock, draining the reward pool faster/further than the tier design intends.

### Impact Explanation
This allows extraction of MGP tokens from `ArbWomUp3`'s incentive/reward reserve beyond what the tiered incentive schedule intends, effectively theft of the protocol's reserved incentive funds (`mgp` balance held by the contract for distribution via `vlMGP.lockFor`). The loss is capped by the contract's MGP balance but is a real, direct, and repeatable value extraction from protocol-funded rewards, matching the "theft of unclaimed yield / protocol insolvency of reward pool" impact class.

### Likelihood Explanation
- Requires no privileged role — any EOA/contract holding WOM can perform this.
- Requires only two ordinary transactions (or one via a wrapper contract for atomicity/front-run protection) calling the public `incentiveDeposit` function with different `_mode` values.
- Capital needed is only enough WOM to cross one tier threshold for the `mode=2` call plus whatever amount the attacker wants rewarded at the inflated flat rate via `mode=1`.
- Repeatable until the contract's MGP balance is exhausted (`mgpleft` cap in `getRewardAmount`), so bounded by, but still capable of draining, the full reward reserve.

### Recommendation
Make the `mode==1` (`!_lock`) branch of `getRewardAmount` consistent with the `mode==2` branch: compute the reward progressively over `_amountToConvert + mWomSV.getUserTotalLocked(_account)` (or an equivalent accumulation metric that is not manipulable within/across the same transaction sequence), and apply the same `calDoubledCounted`-style subtraction so that flat-rate rewards cannot be earned against an artificially and momentarily inflated tier. Alternatively, snapshot the user's tier/locked balance at the start of a batch or require a cool-down between `mode=2` and `mode=1` calls from the same account so tier boosts from a lock cannot be immediately leveraged by a subsequent non-lock deposit in the same or adjacent transaction.

### Proof of Concept
Foundry test outline:
1. Deploy `ArbWomUp3`, `mWomSV`, `MasterMagpie`, `SmartWomConvert`, `mWom`, `vlMGP` mocks/real contracts wired per `__arbWomUp_init`; fund `ArbWomUp3` with a large MGP balance; configure `rewardTier`/`rewardMultiplier` with a threshold crossing at, e.g., `rewardTier[1] = 1000e18` with a materially higher `rewardMultiplier[1]` than `rewardMultiplier[0]`.
2. Baseline: have `userA` call `incentiveDeposit(2000e18, ratio, false, 2)` alone; record MGP locked to `userA` via `vlMGP` (`rewardA_baseline`).
3. Exploit: have `userB` (via a wrapper contract or two sequential txs) call:
   - `incentiveDeposit(1000e18, ratio, false, 2)` (just crosses `rewardTier[1]`), then
   - `incentiveDeposit(1000e18, ratio, false, 1)` immediately after.
   Record total MGP locked to `userB` across both calls (`rewardB_exploit`).
4. Assert `rewardB_exploit > getRewardAmount(2000e18, userB, true)` computed as if the full 2000e18 had gone through a single consistent `mode=2` progressive calculation, demonstrating the split-and-reorder path yields excess reward for the same total WOM committed.
5. Repeat with reversed order (`mode=1` then `mode=2`) to show it does *not* yield the excess, confirming the asymmetry is due to `getUserTier` reading post-lock state only when `mode=2` executes first.
