## Title
Webhook Shop-Domain Spoofing via Unsigned Header Trusted for Job Dispatch — (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` only HMAC-verifies the raw request **body**, but the shop identity attached to that verified body (`shop_domain`) is read directly from the unsigned `X-Shopify-Shop-Domain` request header. The gem's own documentation instructs apps to dispatch background jobs using this unverified header value together with the verified body, so an attacker who can obtain any genuinely-signed webhook payload (e.g. from their own store where the target app is installed) can re-submit that valid `HMAC`+body pair to the app's webhook endpoint while swapping the shop-domain header to an arbitrary victim shop, causing the app to process/store that payload as if it belonged to the victim shop.

### Finding Description
`WebhookVerification#verify_request` validates authenticity solely by comparing `X-Shopify-Hmac-Sha256` against an HMAC of `request.raw_post`: [1](#0-0) 

The companion `shop_domain` helper simply returns the raw header value with no cryptographic binding to the verified body: [2](#0-1) 

`hmac_valid?` computes the digest only over `data` (the raw body) and the app secret — the shop-domain header is never part of the signed material: [3](#0-2) 

The gem's own documentation explicitly instructs developers to build custom webhook controllers that pass this **unverified** `shop_domain` value straight into job dispatch alongside the **verified** body, treating both as equally trustworthy: [4](#0-3) 

The generated declarative webhook controller template follows the same pattern, using `webhook_request.shop` (sourced from the same unsigned header) for job dispatch after only body-HMAC verification succeeds: [5](#0-4) 

Because the HMAC only proves *"this body was signed by someone possessing the app secret"* (i.e., genuinely sent by Shopify for *some* shop with the app installed) and never proves *"this body belongs to the shop named in this header"*, an attacker who can capture or trigger a genuine webhook delivery for their **own** shop (any store where the target app is installed, including a free/dev store the attacker fully controls) possesses a valid `(body, HMAC)` pair. They can replay this exact pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with any victim shop's domain string. `verify_request` will pass (the body/HMAC pair is genuinely valid), and the resulting job will be queued with `shop_domain` = the attacker-chosen victim domain, alongside attacker-controlled webhook body content.

### Impact Explanation
Any job/controller built on top of this documented pattern that uses `shop_domain` to look up a `Shop`/session record and write, update, or otherwise associate the webhook body's data (e.g., cart, order, customer, or product data) is exposed to cross-shop data injection — an unauthenticated attacker can cause data associated with one shop (or with data they craft) to be written into another shop's records, entirely from an unauthenticated webhook endpoint. This is a confused-deputy / cross-tenant access issue directly analogous to a state-changing operation being accepted without adequately confirming the identity of the target it is being applied to.

### Likelihood Explanation
The webhook endpoint is unauthenticated by design (any signature-valid POST is accepted), and obtaining a legitimately signed body only requires installing the target app on any shop the attacker controls (or subscribing to a webhook), which is trivial for any Shopify Partner. Because this is the officially documented/generated integration pattern, any app author following the docs/generator as-is inherits the flaw without writing any additional insecure code themselves.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or `webhook_request.shop`) as an authoritative shop identity unless it is itself bound to the signed body (e.g., cross-checked against a shop identifier embedded in the payload, or validated against an existing, previously-established session/shop record before any state change). At minimum, `WebhookVerification` should document/enforce that `shop_domain` is untrusted input and require callers to verify it against known installed shops (e.g., via `ShopifyApp::SessionRepository.load_shop_session(shop_domain)` returning a valid installed shop) before using it to key any writes, and the docs/generator templates should be updated to demonstrate this safe pattern instead of directly forwarding the header value into job dispatch.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (or otherwise triggers/observes a legitimate webhook delivery for a shop they control).
2. Shopify delivers a webhook POST to the app's webhook URL with a valid body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` against the app's shared secret), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and re-sends a POST to the same webhook endpoint, keeping `B` and `H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` recomputes the HMAC over `B` only, which matches `H`, so the request passes verification.
5. The controller (per documented pattern) queues `SomeJob.perform_later(shop_domain: "victim-shop.myshopify.com", webhook: <attacker's parsed body>)`, causing attacker-controlled data to be processed/stored under the victim shop's identity.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
