Based on my research, the strongest analog I found to the TimeLock "unrestricted arbitrary execution via crafted input" pattern is GitHub Desktop's re-enabling of the `file://` Git transport for submodule initialization, which Git itself disables by default as a hardening measure (post CVE-2022-39253). I was not able to fully confirm the exact gating logic in one of the two call sites within the tool budget available, so I flag that gap explicitly below rather than asserting full exploitability.

### Title
Submodule initialization re-enables the `file://` transport (`protocol.file.allow=always`), potentially permitting a malicious repo to pull arbitrary local paths into a submodule during checkout/clone/pull - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` accepts an `allowFileProtocol` boolean and, when true, adds `-c protocol.file.allow=always` before running `submodule update --init --recursive`. [1](#0-0) 
This flag is threaded through from `checkout.ts` (4 call sites) as well as `clone.ts`'s `--recursive` clone flow. Git ships with `protocol.file.allow` hardened to a restrictive default specifically to stop attacker-controlled repositories from auto-initializing submodules that point at local filesystem paths (a known supply-chain/exfiltration vector). Explicitly forcing `always` reintroduces that class of risk unless the flag is strictly scoped to cases where the *top-level* remote itself is already `file://` (i.e., the user is intentionally working with a local-only repo).

### Finding Description
The broken invariant here mirrors the TimeLock bug: a component that is supposed to perform one narrowly-scoped, safe action (fetch/checkout a specific remote-hosted repository and its submodules) instead grants the untrusted, attacker-authored `.gitmodules` file the ability to specify an arbitrary transport/target (`file://` pointing to any local path) because a blanket permission override (`protocol.file.allow=always`) is applied at the git-invocation level rather than being scoped per-submodule-URL. Git's own hardening (`protocol.file.allow` defaulting to a restricted mode for automatically-triggered submodule recursion) exists precisely to prevent a hosted/cloned repository from declaring a submodule such as `file:///home/victim/.ssh` or another sensitive local git-tracked directory and having it silently pulled into the working tree during a normal clone/checkout/pull. [2](#0-1) 
Desktop's test helpers independently confirm that `-c protocol.file.allow=always` is required specifically to make `submodule add`/`update` succeed against `file://` submodule URLs, corroborating that this flag is the mechanism that lifts Git's default protection. [3](#0-2) [4](#0-3) 

### Impact Explanation
If `allowFileProtocol` is computed too broadly (e.g., always true for `--recursive` clones/checkouts, or derived from something other than strictly verifying the top-level remote is itself `file://`), a malicious remote-hosted repository (fully attacker-controlled content the victim clones/checks out normally over HTTPS) could declare a submodule URL of `file:///path/to/local/git/repo` pointing at a sensitive local directory that happens to be a Git repository, causing Desktop to silently populate the submodule with that local repository's content during a routine clone/checkout/pull. This falls squarely within the accepted impact class: attacker controls a cloned/fetched repository object (`.gitmodules`) and the result is file read/exfiltration outside the intended repo scope, or corruption of the working tree the user will subsequently browse/commit/push.

### Likelihood Explanation
Likelihood is **uncertain without further verification**. The pattern (blanket `protocol.file.allow=always`) is confirmed to exist in the codebase and is exactly the kind of override Git's upstream hardening was designed to prevent. [5](#0-4) 
However, I was unable to fully inspect `app/src/lib/git/checkout.ts` (where `allowFileProtocol` is passed in 4 places) within the available tool budget to confirm whether the boolean is strictly derived from the *current* remote already being `file://` (which would make this safe/intended, matching the local-testing pattern seen in the test helpers) or whether it can be influenced by attacker-controlled repository content on a normal HTTPS-hosted clone. This is the deciding factor for real-world exploitability and remains unconfirmed.

### Recommendation
1. Audit every call site that passes `allowFileProtocol: true` in `app/src/lib/git/checkout.ts` and `app/src/lib/git/clone.ts`/`submodule.ts` to confirm the flag can only become `true` when the *top-level* operation's own remote URL is `file://` (i.e., the user has explicitly opted into local-repo semantics), never based on submodule URLs read from repository content.
2. Never derive `allowFileProtocol` from data contained within the cloned/fetched repository itself (e.g., `.gitmodules`); only from the trusted, user-supplied top-level remote/CLI action.
3. Consider validating each submodule URL against an allowlist of schemes (https/ssh/git) before recursion, rejecting `file://` submodule entries when the parent operation is not itself a local file-based clone.

### Proof of Concept
1. Attacker publishes a public repository on GitHub containing a `.gitmodules` entry: `url = file:///home/victim/some-locally-tracked-git-repo`.
2. Victim uses GitHub Desktop's normal "Clone repository" flow (HTTPS) to clone the attacker's repo, which internally calls `clone()` with `--recursive` and subsequently `updateSubmodulesAfterOperation`. [6](#0-5) 
3. If `allowFileProtocol` is (incorrectly) `true` for this flow, Git executes `submodule update --init --recursive` with `-c protocol.file.allow=always`, allowing the `file://` submodule URL to resolve and clone the local directory's content into the victim's working tree without any additional prompt, bypassing Git's built-in protection against this exact scenario. [7](#0-6) 

**Caveat:** Confirming exploitability requires reading the exact `allowFileProtocol` computation logic in `app/src/lib/git/checkout.ts`, which I could not retrieve before the tool budget was exhausted. If that logic strictly ties `allowFileProtocol` to the top-level remote already being `file://`, this finding would be a false positive / intended local-development behavior rather than an exploitable path.
