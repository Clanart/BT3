### Title
`ReceivedOutput::read` accepts attacker-controlled offset/output pairs with no binding to the scanning key — funds reported received that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to CVE-2022-49307 — where `slgt_cleanup()` dereferenced `info->netdev` state that was never initialized because `alloc_hdlcdev()` failed — `ReceivedOutput::read` constructs a struct that downstream code treats as "a spendable output owned by the multisig" while the field that makes that true (the `offset`) is never validated against the `script_pubkey`/`outpoint` it was read with. The object is materialized in an inconsistent, "partially initialized" state, and every consumer dereferences the assumed invariant.

### Finding Description
`ReceivedOutput` couples three facts that are only coherent together: a scalar `offset` such that `p2tr_script_buf(key + G*offset) == output.script_pubkey`, and an `outpoint` that actually exists on chain and contains that output. `Scanner::scan_transaction`/`scan_block` are the only producers that establish this invariant — they derive `offset` by a `self.scripts.get(&output.script_pubkey)` lookup, so the binding holds by construction (networks/bitcoin/src/wallet/mod.rs:199-214).

`ReceivedOutput::read`, however, decodes `offset`, `output`, and `outpoint` as three independent fields from an untrusted byte stream and returns them with no consistency check (networks/bitcoin/src/wallet/mod.rs:122-134). The reader cannot recompute `key + G*offset` and compare it to `output.script_pubkey` because it doesn't take the key — so the "is this ours / can we spend it" field is accepted on faith, exactly like `slgt_clean()` assuming `netdev` had been assigned.

Consumers then dereference that assumed invariant: the Bitcoin processor's `Output::key()` blindly computes `read_G(taproot_key_from_script) - G*offset` from the untrusted pair (processor/src/networks/bitcoin.rs:112-122), and signing machinery (`SignableTransaction`/`TransactionSignMachine`, networks/bitcoin/src/wallet/send.rs:321-428) will attempt to spend the outpoint under the group key + offset. An invalid pairing produces an output that scans as a received deposit yet either (a) points at a nonexistent/mismatched UTXO, or (b) resolves to a key offset that doesn't actually control the script — in both cases funds are reported received that are not spendable.

### Impact Explanation
Medium. An attacker who can feed bytes into `ReceivedOutput::read` (deposits relayed/encoded between components, or any deserialization surface consuming network- or peer-supplied output claims) can cause the system to credit a deposit that cannot be spent, or attribute funds to an offset/keypair that does not control them — a phantom-balance condition, matching the "funds reported received that are not spendable" acceptance criterion. It is not a direct key/secret leak, hence not High.

### Likelihood Explanation
Moderate-to-low. It requires a path where a `ReceivedOutput` encoding crosses a trust boundary rather than being produced solely by the local `Scanner` (which is the honest producer). The constructor-side API (`Scanner`) is sound; the risk is confined to the deserialization surface. Integrity checks elsewhere (e.g., `assert_eq!(output.key(), key)` in the processor's scanner, processor/src/networks/bitcoin.rs:563) mitigate the naive case but only where that specific wrapper is used — `read` itself remains unguarded.

### Recommendation
Make `ReceivedOutput` unforgeable-by-construction: either (a) make `read` private to the crate / take the scanning `key` and verify `p2tr_script_buf(key + G*offset) == output.script_pubkey`, returning an error on mismatch; or (b) store only `(offset, outpoint)` and re-derive `output` from chain data at use time. At minimum, have `Output::key()` (and any caller trusting the pair) assert the script consistency rather than assuming it.

### Proof of Concept
```rust
// Attacker crafts bytes: arbitrary offset, arbitrary TxOut, arbitrary outpoint.
let mut buf = vec![];
buf.extend(Scalar::ONE.to_bytes());               // offset that does NOT match the script
buf.extend(serialize(&TxOut {
    value: Amount::from_sat(1_000_000),
    script_pubkey: ScriptBuf::new_p2tr_tweaked(
        TweakedPublicKey::dangerous_assume_tweaked(x_only(&ProjectivePoint::GENERATOR)),
    ),                                            // attacker/other key's script
}));
buf.extend(serialize(&OutPoint::new(some_txid, 0))); // outpoint we don't control

// Accepted without error:
let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// forged.value() == 1_000_000 is "received", but no key + offset ever controls
// that script_pubkey; signing machinery will fail to spend it (or, if it
// existed under a *different* offset of ours, attribute it to the wrong offset).
```

Caveat: the exploit requires a deployment path that deserializes `ReceivedOutput` from untrusted bytes rather than from the local `Scanner`; within `scan_transaction`/`scan_block` alone the invariant holds by construction.
