### Title
Unguarded public `updateEndRemainingAllocation()` allows re-snapshotting the bonus denominator to inflate `claim()` payouts - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is a `public` function with no access control and no "already set" guard, so any address can call it directly (outside of `claim()`) at any time after `periodsEndTime[4]` to overwrite `totalEndRemainingAllocation` with the current, shrinking `totalRemainingAllocation`. Because `getBonusAmount()` divides the accumulated `totalBonus` by `totalEndRemainingAllocation`, an attacker who waits for other users to claim (draining `totalRemainingAllocation`) and then calls `updateEndRemainingAllocation()` right before their own `claim()` can collapse the denominator toward their own allocation and capture a wildly outsized share of `totalBonus`.

### Finding Description
In [1](#0-0) , `claim()` only triggers the snapshot lazily: `if (totalEndRemainingAllocation == 0) { updateEndRemainingAllocation(); }`. This guard exists only inside `claim()`; the snapshot function itself is declared `public` and unconditionally overwrites the stored value whenever `block.timestamp >= periodsEndTime[4]`:

```solidity
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4]) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
```

There is no `onlyOwner`, no reentrancy/one-time-set guard, and no check that `totalEndRemainingAllocation` is already non-zero before overwriting it. Since `totalRemainingAllocation` strictly decreases as each user calls `claim()` (`totalRemainingAllocation -= userAllocation` at [2](#0-1) ), an attacker can wait until most other eligible users have claimed their allocation post-period-4, then call `updateEndRemainingAllocation()` directly to re-snapshot `totalEndRemainingAllocation` down to a value close to their own remaining allocation (or the small set of remaining unclaimed allocations).

Because `getBonusAmount()` computes `bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation` ( [3](#0-2) ), shrinking the denominator while `totalBonus` (built up from all prior early-claimers' forfeitures) stays large inflates the attacker's bonus far beyond their fair proportional share. The only safety check in `claim()` is `if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();`, which merely prevents the current transaction from reverting for lack of funds — it does not prevent the attacker from draining a disproportionate amount at the expense of the remaining legitimate claimants, who will subsequently either receive `InsufficientBalance` reverts or be paid less than their entitled `userAllocation + fair bonus`. This breaks the intended invariant that the sum of legitimately owed claims tracks `aidropToken.balanceOf(address(this))`.

### Impact Explanation
This allows an unprivileged attacker to directly steal funds earmarked for other airdrop participants by manipulating a public, unguarded snapshot function to inflate their own bonus share, at the cost of later/remaining claimants who cannot fully claim their fair allocation plus bonus. This matches Immunefi's "Critical - Direct theft of user funds" classification.

### Likelihood Explanation
The precondition is simply that the airdrop has passed `periodsEndTime[4]` (all periods vested) and that some early claimants forfeited amounts into `totalBonus` (a normal, expected occurrence for any user who claims before full vesting). No special privileges, capital, or flash loans are required — the attacker only needs to observe on-chain state (how many allocations remain unclaimed) and send a single `updateEndRemainingAllocation()` transaction followed by `claim()`, or even bundle both in one attacker-controlled contract call. This is trivially repeatable by any late claimant and requires no cooperation from other actors.

### Recommendation
Restrict `updateEndRemainingAllocation()` so it can only set `totalEndRemainingAllocation` once (e.g., add a `require(totalEndRemainingAllocation == 0)` check inside the function itself, mirroring the guard already used in `claim()`), or make it `internal`/`onlyOwner`-gated so it cannot be invoked as a standalone, repeatable snapshot reset by arbitrary callers.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `Airdrop` with `startTime = now + 1`, and register allocations for users A, B, C, and Attacker (e.g., 1000 each) via `register()`.
2. Fast-forward past `periodsEndTime[0..3]` at varying times and have users A and B call `claim()` early (before `periodsEndTime[4]`) to forfeit portions into `totalBonus` (verify `totalBonus > 0` grows).
3. Fast-forward to `block.timestamp >= periodsEndTime[4]`.
4. Have user C call `claim()` first — this triggers the lazy `updateEndRemainingAllocation()` inside `claim()`, setting `totalEndRemainingAllocation` to the (still large) `totalRemainingAllocation` at that point; record C's actual payout and confirm it matches the fair proportional bonus.
5. Before Attacker's own `claim()`, have Attacker directly call the public `updateEndRemainingAllocation()` again (no access control stops this), re-snapshotting `totalEndRemainingAllocation` down to the now much smaller `totalRemainingAllocation` (close to Attacker's own remaining allocation).
6. Attacker calls `claim()` and assert their `claimableAmount`/received tokens are disproportionately larger than their fair share (`userAllocation + userAllocation/totalOriginalRemaining*totalBonus`), demonstrating the denominator collapse.
7. Assert that a legitimate remaining claimant (or the sum of `allocations` outstanding) can no longer be fully satisfied by `aidropToken.balanceOf(address(this))`, proving the invariant "sum of all allocations reconciles with token balance" is broken and funds have been misappropriated.

```text
    /// @notice This will store the ending remaining amount for the bonus.
    function updateEndRemainingAllocation() public {
        if (block.timestamp >= periodsEndTime[4]) {
            totalEndRemainingAllocation = totalRemainingAllocation;
        }
    }

    /// @notice Claim MGP and forfeit remaining allocation
    function claim() external {
        if (totalEndRemainingAllocation == 0) {
            updateEndRemainingAllocation();
        }
        uint256 claimableAmount = getClaimableAmount(msg.sender);
        
        if(claimableAmount == 0) revert NothingToClaim();
        if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();

        uint256 userAllocation = allocations[msg.sender];
        allocations[msg.sender] = 0;
        totalRemainingAllocation -= userAllocation;
        if (claimableAmount <= userAllocation) {
            uint256 forfeited = userAllocation - claimableAmount;
            totalBonus += forfeited;
        }
        aidropToken.safeTransfer(msg.sender, claimableAmount);
    }
```
