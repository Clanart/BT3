### Title
Type confusion in `UnpackTxData`'s type-guessing fallback lets an EVM tx's protobuf payload be silently reinterpreted as the wrong `ethtx.TxData` variant, bypassing type-specific validation - ([File: x/evm/types/codec.go])

### Summary
`UnpackTxData` decodes the `Any`-wrapped `Data` field of a `MsgEVMTransaction` by first checking `GetCachedValue()`, and — when that is unset — falling back to *blindly trial-unmarshaling* the raw bytes into a hard-coded sequence of concrete `ethtx.TxData` implementations (`LegacyTx` → `AccessListTx` → `DynamicFeeTx` → `BlobTx` → `AssociateTx` → `SetCodeTx`), accepting whichever succeeds first, without ever checking the `Any.TypeUrl` that the sender actually declared.

### Finding Description
`UnpackTxData` is defined identically in `x/evm/types/codec.go:93-134` and `giga/deps/xevm/types/codec.go:63-104`: [1](#0-0) 

The correct/authoritative type resolution for a protobuf `Any` is its `TypeUrl` field, resolved through the interface registry (as done in `MsgEVMTransaction.UnpackInterfaces`, `x/evm/types/message_evm_transaction.go:77-79`). But when `GetCachedValue()` is nil, `UnpackTxData` abandons `TypeUrl`-based resolution entirely and instead does `proto.Unmarshal(any.Value, &ltx)`, `&atx`, `&dtx`, `&btx`, `&astx`, `&stx` in sequence, returning the first one that doesn't error.

This is structurally the same bug class as CVE-2018-6480: `ccnl_fwd_handleInterest` assumed a `union` member was of type `ccnl_pktdetail_ndntlv_s` without validating the actual on-wire discriminator, so a payload that was really a different variant got its bytes reinterpreted as a nonce that was never a nonce. Here, `proto.Unmarshal` is permissive of unknown/missing fields by design (it does not enforce that the bytes were actually produced for the target schema), so a byte sequence intended by the sender to be one `ethtx.TxData` variant (declared via `Any.TypeUrl`) can successfully — and silently — decode into an *earlier* variant in the hard-coded try-order without error, because the wire-compatible byte/varint fields of these related messages (e.g., signature `V/R/S` byte fields, `Data` bytes, numeric fields) overlap in field-number/wire-type shape across `LegacyTx`, `AccessListTx`, `DynamicFeeTx`, `AssociateTx`, etc.

The consequence of this mis-typed decode is security relevant because downstream code branches solely on the concrete Go type of the returned `ethtx.TxData`, not on the sender-declared `TypeUrl`:
- `EvmCheckTxAnte` / `EvmStatelessChecks` in `app/ante/evm_checktx.go:47-51` and `:97-103` do `if atx, ok := txData.(*ethtx.AssociateTx); ok { ... }` to decide whether to take the "association" code path (which skips normal EVM fee/nonce/signature checks) or the standard EVM tx path.
- `MsgEVMTransaction.GetAssociateTx()` / `IsAssociateTx()` (`x/evm/types/message_evm_transaction.go:81-94`) make the same type-based branching decision used throughout ante handling, RPC filtering (`evmrpc/utils.go:239-242`), and fee/gas decorators.

If `UnpackTxData`'s guess-order silently resolves attacker-supplied bytes to a *different* concrete type than the sender's declared `TypeUrl` intended, all of these type-assertion branch points can diverge from the sender's actual intent, exactly mirroring the CVE's "nonce check is insufficient because the memory read isn't actually a nonce" failure mode — a critical security decision (fee charge vs. no fee charge, nonce check vs. no nonce check, association vs. normal tx) is made on a value that isn't the type it's assumed to be.

### Impact Explanation
If exploitable, this could allow an unprivileged EVM transaction sender to have their transaction bytes reinterpreted by the chain as a different `TxData` variant than what they (or the type-URL) declared, causing consensus-critical ante-handler logic (fee/nonce/association checks in `app/ante/evm_checktx.go`, `x/evm/ante/preprocess.go`, `x/evm/ante/basic.go`, `x/evm/ante/sig.go`) to run the wrong validation branch. Depending on which mis-typed branch is taken, this could result in fee/nonce check bypass or association-authority confusion, i.e., unauthorized fund/fee handling or state corruption at the ante-handler level.

### Likelihood Explanation
This requires two things to hold, which I could not fully confirm given tool-call limits:
1. That `GetCachedValue()` is actually nil for transactions arriving through the normal broadcast/mempool/RPC path (rather than always being populated via `UnpackInterfaces`/registry resolution before `UnpackTxData` is called), so the fallback path is reachable by an ordinary tx sender.
2. That the protobuf wire encoding of two `ethtx.TxData` variants (e.g., `AssociateTx`'s `V/R/S` byte fields vs. `LegacyTx`'s numeric/byte fields) can genuinely collide such that bytes crafted for one variant parse without error as an earlier variant in the try-order.

Both are plausible given protobuf's permissive/forwards-compatible wire semantics and the shared byte/numeric field shapes across these structs, but I was unable to fully enumerate the exact field-number layouts of every `ethtx.TxData` variant (`x/evm/types/ethtx/tx.pb.go`) before running out of investigation budget, so likelihood should be treated as moderate/unconfirmed pending closer field-by-field wire analysis.

### Recommendation
Remove the blind sequential trial-unmarshal fallback in `UnpackTxData`. Resolve the concrete `ethtx.TxData` type strictly from the `Any.TypeUrl` (via the interface registry, as `UnpackInterfaces` already does), and treat a nil `GetCachedValue()` with no successful registry resolution as a decode error rather than guessing. This removes the "type confusion by trial" behavior entirely and makes type resolution deterministic and attacker-non-influenceable.

### Proof of Concept
I could not construct a concrete byte sequence proof-of-concept within the available tool budget, because it requires enumerating the exact protobuf field numbers/wire types for each `ethtx.TxData` variant in `x/evm/types/ethtx/tx.pb.go` to demonstrate a genuine cross-type parse collision, and confirming empirically that the fallback path in `UnpackTxData` (rather than registry-based `TypeUrl` resolution) is actually exercised for wire-decoded (not in-process-constructed) `MsgEVMTransaction`s. func UnpackTxData(any *codectypes.Any) (ethtx.TxData, error) {
	if any == nil {
		return nil, errors.New("protobuf Any message cannot be nil")
	}

	txData, ok := any.GetCachedValue().(ethtx.TxData)
	if !ok {
		ltx := ethtx.LegacyTx{}
		if proto.Unmarshal(any.Value, &ltx) == nil {
			// value is a legacy tx
			return &ltx, nil
		}
		atx := ethtx.AccessListTx{}
		if proto.Unmarshal(any.Value, &atx) == nil {
			// value is a accesslist tx
			return &atx, nil
		}
		dtx := ethtx.DynamicFeeTx{}
		if proto.Unmarshal(any.Value, &dtx) == nil {
			// value is a dynamic fee tx
			return &dtx, nil
		}
		btx := ethtx.BlobTx{}
		if proto.Unmarshal(any.Value, &btx) == nil {
			// value is a blob tx
			return &btx, nil
		}
		astx := ethtx.AssociateTx{}
		if proto.Unmarshal(any.Value, &astx) == nil {
			// value is an associate tx
			return &astx, nil
		}
		stx := ethtx.SetCodeTx{}
		if proto.Unmarshal(any.Value, &stx) == nil {
			// value is a set code tx
			return &stx, nil
		}
		return nil, fmt.Errorf("cannot unpack Any into TxData %T", any)
	}
