## Title
Governance withdrawal from `EvmHost` can drain relayer-fee escrow reserved for undelivered requests — ([File: evm/src/core/EvmHost.sol])

## Summary
`EvmHost.withdraw()` transfers `params.amount` of `params.token` straight out of the host's raw ERC-20/native balance to a beneficiary, with no check that the withdrawal leaves enough balance to cover the relayer fees already escrowed for requests that are still in flight (undelivered/untimed-out). This mirrors the reported bug class: a payout that is "not connected" to a specific backing balance is drawn from a shared pool that also holds other users' deposits, so an amount paid to one party can come out of funds another party is still owed.

## Finding Description
When a user dispatches a cross-chain POST/GET request, they attach a relayer fee that Hyperbridge escrows in `EvmHost`'s fee-token balance, tracked per-commitment in `_requestCommitments` (`FeeMetadata`) as documented at [1](#0-0) . That fee is meant to be paid out only once the request is actually delivered (to the relayer) or timed out (refunded to the payer).

Separately, `pallet-ismp-relayer` accumulates relayer fee entitlements *on Hyperbridge* purely from state proofs of past deliveries [2](#0-1) , and then dispatches an ISMP message instructing the destination chain's `HostManager` to disburse `available_amount` of the fee token to the relayer [3](#0-2) . On the EVM side, `HostManager.onAccept` unconditionally forwards this to `IHostManager(_params.host).withdraw(withdrawParams)` when the action is `Withdraw`, gated only by `request.source == hyperbridge()` [4](#0-3) . `EvmHost.withdraw()` then just moves tokens out of its own balance:

```solidity
function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
    if (params.token == address(0)) {
        (bool sent,) = params.beneficiary.call{value: params.amount}("");
        if (!sent) revert WithdrawalFailed();
    } else {
        IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
    }
    emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
}
``` [5](#0-4) 

This function contains no invariant check comparing `IERC20(feeToken).balanceOf(address(this))` against the sum of still-outstanding, escrowed relayer fees for pending requests (`_requestCommitments`). The withdrawal amount is a number computed entirely off-chain/on Hyperbridge from historical delivery proofs — it has no cryptographic or accounting tie to the *current* free balance on the EVM host versus the balance that is contractually owed to users who dispatched requests that haven't been delivered/timed out yet.

This is structurally identical to the reported `unStakeAndBurn` bug: a reward/withdrawal amount computed from one side of the system (accumulated "stake2 burnt" / "accumulated proof-of-delivery fees") is paid out of a single shared token balance that also custodies other users' deposits (staked `stakeToken` / escrowed relayer fees for undelivered requests), with no reservation accounting to prevent the payout from eating into funds that rightfully belong to other users.

## Impact Explanation
If relayer-fee withdrawals (or the analogous governance/host-revenue withdrawal path, which shares the exact same `withdraw()` function and `WithdrawParams`) drain the host's fee-token balance below the sum of fees escrowed for requests still awaiting delivery, then when those pending requests are eventually delivered, the relayer who did the work cannot be paid the promised fee out of the shared balance, and/or a user's timeout-triggered fee refund can fail or short-pay. Since `feeToken` balance is a single pooled account with no per-request segregation enforced at the Solidity layer, later users effectively subsidize earlier withdrawals — funds users deposited as relayer fees can be lost/unavailable, matching the "loss of funds" / "wrong beneficiary or amount" bounty categories.

## Likelihood Explanation
The withdrawal path itself is reachable through the standard, intended relayer fee-accumulation-and-withdrawal flow (`pallet-ismp-relayer::withdraw_fees` → ISMP POST → `HostManager.onAccept` → `EvmHost.withdraw`), which is explicitly designed to let any relayer withdraw "at any time" once fees accumulate [6](#0-5) . No malicious peer, relayer collusion, or governance compromise is required — it is simply a missing balance-sufficiency/reservation check in `EvmHost.withdraw()`, the same class of gap the external report flagged for the staking contract ("validate that the contract has enough balance ... to ensure tokens sent ... are not taken from deposits"). I could not fully verify from the indexed code whether an off-chain operational safeguard (e.g., relayer minimum-withdrawal thresholds, or Hyperbridge-side accounting that caps `available_amount` to a chain's actual escrowed liabilities) exists to bound this in practice; the on-chain contract itself has no such guard.

## Recommendation
Add an on-chain invariant in `EvmHost.withdraw()` (or in `HostManager.onAccept`) requiring that after the transfer, `IERC20(feeToken).balanceOf(address(this))` remains ≥ the total fee amount currently escrowed in `_requestCommitments` for undelivered/non-timed-out requests. Alternatively, track a running "reserved" counter that is incremented when a request is dispatched with a fee and decremented only when the fee is actually paid out (delivery) or refunded (timeout), and gate `withdraw()` so it can never dip into the reserved balance.

## Proof of Concept
Not independently reproducible from the indexed context alone — the existing test `test_host_manager_withdraw` in `evm/tests/rust/src/tests/host_manager.rs` exercises the happy path (mint tokens, then withdraw less than the full balance) and passes because no pending-fee liability is modeled in that test [7](#0-6) . Demonstrating actual fund loss would require: (1) dispatching several fee-bearing requests to accumulate escrowed relayer fees in `_requestCommitments`, (2) triggering a governance/relayer `withdraw()` call for an amount that leaves the host's `feeToken` balance below the sum of those outstanding fees, and (3) showing that a subsequent legitimate relayer delivery or timeout can no longer be paid/refunded in full — this last step could not be confirmed against the indexed dispatch/timeout code because the relevant `dispatch`/`handlePostRequestTimeout` fee-payout logic in `EvmHost.sol` was not fully retrieved before the tool budget was exhausted.

        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

## Withdrawals

If a relayer wishes to withdraw their fees, they can do so at any time. They simply need to sign a transaction to the relayer module showing that they possess the private key of the account in question. Recall that their account on the delivery chain is associated with any fees that they may have accumulated. This account scheme may be different from the Hyperbridge account scheme. To allow for this, the relayer can sign a withdrawal request with the private key of the account in question. The `pallet-ismp-relayer` module will then verify the signature and if it is valid, the module will dispatch a request to the `HostManager` to perform the withdrawal on the destination chain.

#[test]
fn test_host_manager_withdraw() {
	let mut env = TestEnv::new();
	let manager = host_manager_of(&mut env);

	// Mint 1000e18 fee tokens to the host
	let amount_to_mint = U256::from(1000u128) * U256::from(10u128.pow(18));
	env.call(env.fee_token, mintCall { to: env.host, amount: amount_to_mint }.abi_encode());
	assert_eq!(host_balance(&mut env), amount_to_mint);

	// Build a withdraw request (body = [0] + abi.encode(WithdrawParams)).
	// Withdraw the fee token (non-zero `token`) — the zero address would be
	// the native-ETH path which this test isn't exercising.
	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	// HostManager.onAccept is `restrict(_params.host)` — must call AS the host
	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	env.call_as(host_addr, manager, calldata);

	let withdraw_amount = U256::from(500u128) * U256::from(10u128.pow(18));
	assert_eq!(host_balance(&mut env), amount_to_mint - withdraw_amount);
}
