### Title
Empty Schnorr aggregate signatures verify as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` accepts an aggregate containing zero signatures when the aggregate scalar is zero. An attacker can deserialize public bytes encoding an empty `Rs` vector and a zero scalar, then pass an empty `keys_and_challenges` list to `verify`, which returns `true` because the only multi-exponentiation term is `0 * G`. [1](#0-0) [2](#0-1) 

### Finding Description
`SchnorrAggregate::read` parses a `u32` count, reads that many nonce points, and then reads the scalar `s`. It does not reject a count of zero. [1](#0-0) 

`SchnorrAggregate::verify` only checks that `self.Rs.len() == keys_and_challenges.len()`. For two empty lists, this check passes, no per-signer statements are queued, and `pairs` contains only `(-self.s, generator)`. If `s == 0`, `multiexp_vartime(&pairs)` evaluates to the identity and verification returns `true`. [2](#0-1) 

This is the Serai analogue of a verifier succeeding after a selection produces no items: the verifier treats an empty statement set as valid instead of rejecting it.

### Impact Explanation
An unprivileged caller can create an aggregate signature encoding that verifies against zero public keys without knowing any private key. Any downstream protocol that accidentally calls `verify` with an attacker-influenced empty signer set would interpret this as a valid aggregate signature. [2](#0-1) 

The producer API avoids creating this object because `SchnorrAggregator::complete` returns `None` when no signatures were aggregated, but the public deserializer still permits the forged encoding. [3](#0-2) 

### Likelihood Explanation
Exploitation requires a caller to invoke `SchnorrAggregate::verify` with an empty `keys_and_challenges` list. The cryptographic primitive itself is public, and the forged bytes are compact and deterministic: `00 00 00 00` followed by the canonical encoding of scalar zero. [1](#0-0) 

No secret material, malicious validator, protocol peer, malformed curve point, or private state is required.

### Recommendation
Reject empty aggregates in both `SchnorrAggregate::read`/`SchnorrAggregate::verify`, matching the non-empty invariant already enforced by `SchnorrAggregator::complete`. [3](#0-2) 

At minimum, `verify` should return `false` when `keys_and_challenges.is_empty()` before performing the multi-exp check. A regression test should assert that the zero-count/zero-scalar encoding never verifies.

use ciphersuite::Ciphersuite;
use schnorr::aggregate::SchnorrAggregate;

fn forge_empty_aggregate<C: Ciphersuite>() -> Vec<u8> {
  let mut bytes = Vec::new();
  bytes.extend_from_slice(&0u32.to_le_bytes());       // zero Rs
  bytes.extend_from_slice(C::F::ZERO.to_repr().as_ref()); // s = 0
  bytes
}

// After deserializing with SchnorrAggregate::<C>::read, this call returns true:
//
// aggregate.verify(dst, &[])
//
// Verification succeeds because the length check is 0 == 0 and the only
// queued statement is -0 * G, whose result is the identity.
