## Title
Attacker-Controlled `WWW-Authenticate` Header From a Malicious Git Remote Can Trigger GitHub Credential Disclosure to That Remote - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's credential-helper trampoline decides whether an unknown Git remote is a "GitHub" host by inspecting the `wwwauth[]` fields that Git forwards from the server's `WWW-Authenticate` response header, trusting the literal string `realm="GitHub"` as proof of GitHub identity. Because that header originates entirely from the remote server the user is connecting to, a malicious or compromised remote/proxy can spoof it, causing Desktop to treat the attacker's host as a legitimate GitHub Enterprise endpoint and prompt the user to "sign in with GitHub" for that host. The resulting real GitHub token is then attached as the Git credential for the attacker's URL, exactly like the report's flaw: a security-relevant classification checks a client-observable but attacker-influenceable signal, without validating the true origin/context, allowing bypass of the invariant that GitHub credentials only go to genuine GitHub hosts.

### Finding Description
`getEndpointKind()` classifies a remote endpoint using several checks, most of them safe (`isDotCom`, `isGHE`, matching an existing stored account by real origin). But when none of these match, it falls back to a heuristic that trusts data supplied by the untrusted remote: [1](#0-0) 

The comment itself acknowledges the header is attacker-observed input ("When Git attempts to authenticate with a host it captures any WWW-Authenticate headers and forwards them to the credential helper"), yet the code uses the presence of `realm="GitHub"` as sufficient evidence to classify the endpoint as `'enterprise'` — i.e., a GitHub host — without any origin/TLS/host-identity verification independent of what the server itself claims.

That classification then drives `getCredential()`: [2](#0-1) 

If `endpointKind !== 'generic'` (i.e. the spoofed header claimed GitHub) and there's no existing account already bound to that exact endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)` and, on success, merges the resulting real GitHub `login`/`token` into the credential template `cred`: [3](#0-2) 

Crucially, `credWithAccount` only overwrites `username`/`password` in the existing credential map — the `host`/`protocol`/`path` fields of `cred` (which came from the attacker's own git request) are left untouched. Git will then hand this credential (with the user's genuine GitHub OAuth token) back to the attacker's own HTTP endpoint as part of `Authorization: Basic`, because Git's credential protocol associates username/password with whatever host/protocol was in the original `fill` request.

The narrower, unspoofable checks — matching an account by actual URL origin via `findGitHubTrampolineAccount` (same-origin comparison of `getHTMLURL(a.endpoint)`): [4](#0-3) 

— are correctly origin-bound and are not the vulnerable path. The vulnerable path is specifically the `wwwauth[]` fallback in `getEndpointKind`, which lets the remote itself assert "I am GitHub" and receive elevated trust for that assertion, similar to `markBeetleSafe()` trusting only caller-supplied context (ownership) without validating the surrounding invariant (that the asset had not already lost a battle). Here Desktop trusts attacker-supplied header content without validating the surrounding invariant (that the host is actually a GitHub-operated origin).

### Impact Explanation
A malicious Git server or a man-in-the-middle/malicious proxy in front of any HTTPS remote (not previously known to Desktop) can respond to Git's initial unauthenticated request with `WWW-Authenticate: Basic realm="GitHub"`. When the user tries to fetch/pull/push against that remote, Desktop's credential-helper trampoline will:
1. Misclassify the endpoint as `'enterprise'` (a GitHub host).
2. Since there's no existing account bound to that endpoint, prompt the user with a "Sign in to GitHub" dialog scoped to the attacker's URL.
3. Because the user believes they are just authenticating to reach the remote they intentionally added, they may proceed (the real OAuth/PAT flow happens against real github.com, so the token itself is legitimate).
4. The resulting real GitHub token is attached as the credential for the attacker's remote and handed to Git, which sends it (Basic auth) directly to the attacker-controlled host.

This is a credential/token exfiltration primitive: the user's GitHub personal token/OAuth token is disclosed to an attacker-controlled server that the user only intended to add as an arbitrary Git remote (e.g., a "self-hosted mirror" or "corporate git server" link they were told to add, or a git proxy in a MITM position). This matches the "credential/token exfiltration" impact category explicitly listed as valid.

### Likelihood Explanation
The attacker only needs to control the HTTP response headers of a Git remote endpoint the user adds/clones/fetches from — no local access, no prior malware, and no social engineering beyond what's inherent to normal Desktop usage (adding a remote and performing a fetch/push, which is a completely ordinary workflow). The spoofed header is a single, standard HTTP response header (`WWW-Authenticate`) that any server operator or MITM proxy fully controls. This is precisely the "attacker controls... a git remote/proxy response" scenario called out as in-scope. The only user action required is normal use of the credential/sign-in prompt Desktop itself presents, not an "unnatural" step.

### Recommendation
Do not use the self-reported `WWW-Authenticate` realm string as sufficient evidence of GitHub identity. At minimum:
- Require the realm-based heuristic to be corroborated by an independent signal (e.g., only trust it for hosts already configured as Enterprise endpoints, or perform a server-signed check via `isGitHubHost()` regardless of the header, rather than skipping that verification when the header is present).
- Bind any credential handed back to Git strictly to the endpoint the user explicitly registered as an Enterprise/GitHub account, never to an arbitrary unknown remote inferred purely from response headers.
- When prompting "Sign in to GitHub" for a previously-unknown endpoint, clearly disambiguate in the UI that the classification came from an unverified header supplied by the remote itself, or suppress the shortcut entirely and fall back to the generic-credential flow for unknown, unverified hosts.

### Proof of Concept
1. Stand up an HTTP server the victim doesn't know is malicious, e.g. `https://git.attacker.example/repo.git`.
2. Configure the server to respond to Git's unauthenticated request with:
   ```
   HTTP/1.1 401 Unauthorized
   WWW-Authenticate: Basic realm="GitHub"
   ```
3. In GitHub Desktop, have the victim "Add" or "Clone" this repository as a generic remote (a normal, unremarkable workflow) and trigger a fetch/push.
4. Git spawns the credential-helper trampoline, which calls `createCredentialHelperTrampolineHandler` → `getCredential` → `getEndpointKind`, which finds the spoofed `wwwauth[...]=Basic realm="GitHub"` and returns `'enterprise'`. [5](#0-4) 
5. Since no account is bound to `git.attacker.example`, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, and the victim signs in with their real GitHub account (a real OAuth/PAT flow against real GitHub). [6](#0-5) 
6. `credWithAccount` merges the real token into the credential for `git.attacker.example`, and Git sends `Authorization: Basic <base64(login:token)>` to the attacker's server, exfiltrating the token. [3](#0-2)

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
