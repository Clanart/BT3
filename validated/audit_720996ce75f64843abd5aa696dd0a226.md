### Title
Unchecked type assertion on attacker-controlled CosmWasm query response causes a panic in the CW→ERC pointer precompile - (File: `precompiles/pointer/pointer.go`)

### Summary
The `pointer` precompile's `AddCW20`, `AddCW721`, and `AddCW1155` handlers query a CosmWasm contract for `token_info`/`contract_info` metadata and then extract the `name`/`symbol` fields from the decoded JSON with unchecked Go type assertions (`.(string)`). Because the CW contract at the target address is fully attacker-controlled (any user can deploy a CosmWasm contract before registering a pointer to it), a contract that returns a non-string `name` or `symbol` field (e.g. a number, `null`, or object) causes an unrecovered `interface conversion` panic during EVM execution of the precompile. This mirrors the CVE-2018-10196 bug class: a function that processes attacker-supplied/crafted data crashes via an unguarded dereference/assertion instead of failing gracefully.

### Finding Description
`AddCW20` in `precompiles/pointer/pointer.go` does: [1](#0-0) 

```go
res, err := p.wasmdKeeper.QuerySmartSafe(ctx, cwAddress, []byte("{\"token_info\":{}}"))
...
formattedRes := map[string]interface{}{}
if err := json.Unmarshal(res, &formattedRes); err != nil {
    return nil, 0, err
}
name := formattedRes["name"].(string)
symbol := formattedRes["symbol"].(string)
``` [2](#0-1) 

The response `res` comes directly from a smart-contract query (`QuerySmartSafe`) against `cwAddress`, which is a caller-supplied string argument (`args[0].(string)`) — i.e., any address the caller chooses, including a contract the caller just deployed with a hostile `token_info` query handler. There is no `ok`-checked type assertion (`v, ok := formattedRes["name"].(string)`), so a JSON response like `{"name": 123, "symbol": "X"}` causes an immediate Go runtime panic (`interface conversion: interface {} is float64, not string`) instead of returning an error. The same unguarded pattern (`formattedRes["name"].(string)` / `formattedRes["symbol"].(string)`) is repeated across the CW721/CW1155 variants and across many legacy precompile versions still compiled into the binary (`precompiles/pointer/legacy/v552/pointer.go`, `v555`, `v562`, `v580`, `v606`, `v630`, `v66`, etc.), meaning the bug is present in essentially every historical and current precompile version used for replaying/tracing old blocks as well as live execution.

### Impact Explanation
A crafted CW20/CW721/CW1155 contract can force an unrecovered type-assertion panic inside EVM precompile execution the moment any user (attacker or otherwise) calls the pointer-registration method against it. While block-processing paths in this codebase generally wrap per-transaction execution with `recover()` (e.g. in `app.ProcessTxsSynchronousGiga`, converting most panics into an `ErrPanic` ABCI result), the same unguarded call path is reachable through `eth_call`/`eth_estimateGas`/tracing RPC entry points where a caller can invoke a non-read-only method without committing state. If that RPC code path (or any future/alternate execution path that lacks the same defensive `recover()`) executes this handler, the panic is not confined to a single request — an unrecovered panic in a goroutine crashes the entire Go process, taking down a public RPC node. Even where the panic is caught by existing per-tx recovery, this remains an unhandled-error condition on a state-changing precompile that any unprivileged EVM caller can trigger deterministically by controlling the wasm contract queried.

### Likelihood Explanation
High from a proof-of-concept standpoint: the attacker only needs to (1) deploy a CosmWasm contract with a custom `token_info`/`contract_info` query handler returning a JSON field of the wrong type, and (2) call the pointer precompile's `addCW20`/`addCW721`/`addCW1155` method (or invoke it via `eth_call`) pointing at that contract. No special privileges, governance, or validator collusion are required — this is a standard CosmWasm deploy + EVM precompile call available to any unprivileged wallet.

### Recommendation
Replace every unchecked type assertion on `formattedRes["name"]`/`formattedRes["symbol"]` (and any other field extracted from wasm-query JSON) in `precompiles/pointer/pointer.go` and all legacy pointer precompile versions with the two-value form, returning a precompile error (not a panic) when the type does not match:
```go
name, ok := formattedRes["name"].(string)
if !ok {
    return nil, 0, fmt.Errorf("cw20 token_info returned non-string name")
}
```
Apply the same fix to the `symbol` extraction and to the CW721/CW1155 variants, and audit other precompiles that unmarshal untrusted wasm-query JSON with unchecked assertions.

### Proof of Concept
1. Deploy a CosmWasm contract whose `token_info` query handler returns `{"name": 12345, "symbol": "X", ...}` (a numeric `name` instead of a string).
2. From an EVM account, call the pointer precompile's `addCW20` method (or `eth_call` it) with the deployed contract's bech32 address as the `cwAddr` argument.
3. Execution reaches `precompiles/pointer/pointer.go`'s `AddCW20`, unmarshals the query response, and executes `formattedRes["name"].(string)`, which panics with `interface conversion: interface {} is float64, not string` because the asserted type does not match.
