### Title
Unchecked u64 overflow/underflow in `SignableTransaction` fee math from attacker-controlled `TxOut` values - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
CVE-2018-1000524 is an integer overflow in `layer_resize()` where attacker-chosen dimensions produce an out-of-bounds allocation/DoS. The analog in Serai is the unchecked `u64` arithmetic in `SignableTransaction` (`send.rs`): input sums, payment sums, and the `fee()` difference are computed with plain wrapping/panicking operations on values that originate from untrusted bytes via `ReceivedOutput::read`.

### Finding Description
`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) deserializes a `TxOut` with `TxOut::consensus_decode`, which accepts any `u64` as the output value — there is no 21M-supply cap enforced at decode time. Those values then flow into `SignableTransaction::new`:

```rust
// send.rs:175
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
// send.rs:187
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();
// send.rs:206
let mut needed_fee = fee_per_vbyte * vbytes;
// send.rs:215
if input_sat < (payment_sat + needed_fee) { ... }
```

`sum::<u64>()`, `fee_per_vbyte * vbytes`, and `payment_sat + needed_fee` are all unchecked. Two inputs claiming `u64::MAX` satoshis overflow `input_sat`; large `fee_per_vbyte` or `payments` overflow the fee/change expressions. Separately, `fee()` (`send.rs:139-141`) computes `sum(prevouts) - sum(outputs)` with a plain subtraction, so any constructed `SignableTransaction` whose stored outputs exceed stored inputs underflows — either a panic or, after release-mode wrapping upstream, a wildly wrong reported fee. The change-branch path uses `input_sat.checked_sub(payment_sat + fee_with_change)` (`send.rs:228`), which partially guards the subtraction but not the `payment_sat + fee_with_change` addition itself or the earlier `input_sat`/`payment_sat` sums.

### Impact Explanation
- **Denial of service (panic):** In builds with overflow checks, `sum::<u64>()` over two `ReceivedOutput`s carrying large `TxOut.value`s panics inside `SignableTransaction::new`, and `sum(prevouts) - sum(outputs)` panics inside `fee()`, which is called by the processor when computing forwarded-output balances (`processor/src/multisigs/mod.rs:884` calls `tx.0.fee()`).
- **Incorrect funds accounting (wrap):** In release builds the overflow wraps silently. `input_sat` can wrap to a small value causing spurious `NotEnoughFunds` rejection of legitimate spends, or a wrapped `payment_sat + needed_fee` comparison can pass when it shouldn't, producing transactions whose real fee is `input_sat - output_sat` differing from `needed_fee` — i.e., funds reported/spent inconsistently with the declared fee rate. This parallels the CVE: untrusted size/value inputs reach unchecked arithmetic that corrupts computation or aborts the process.

### Likelihood Explanation
`ReceivedOutput` is the currency of the scan→spend pipeline; the scanner's `scan_transaction` produces them, but `ReceivedOutput::read` is a public deserialization API and the wallet/`SignableTransaction` constructor does not re-validate `TxOut.value` against consensus limits. Any path where serialized `ReceivedOutput`s or externally influenced `payments`/`fee_per_vbyte` reach `SignableTransaction::new` (e.g., batch/plan data in the processor) can trigger the panic or miscomputed fee. Requires no privileges — only control over the numeric fields fed into the constructor.

### Recommendation
- Compute `input_sat`, `payment_sat`, and `payment_sat + needed_fee`/`fee_with_change` with `checked_add`/`checked_mul`/`checked_sum`, returning `TransactionError::NotEnoughFunds`/a dedicated `Overflow` variant on failure.
- Make `fee()` use `checked_sub` (returning `Option<u64>` or saturating/reporting an error) instead of panicking.
- Optionally validate `TxOut.value <= MAX_MONEY` in `ReceivedOutput::read`/`SignableTransaction::new` so invalid amounts are rejected at the trust boundary rather than propagating into fee math.

### Proof of Concept
```rust
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction};
use bitcoin_serai::bitcoin::{Amount, TxOut, OutPoint, ScriptBuf};
use bitcoin_serai::bitcoin::hashes::Hash;
use bitcoin_serai::bitcoin::Txid;
use bitcoin_serai::crypto::Secp256k1;
use ciphersuite::Ciphersuite;
use frost::curve::Curve;

fn forged_output(value: u64) -> ReceivedOutput {
    ReceivedOutput::read(&mut {
        let mut buf = vec![];
        // zero offset scalar
        buf.extend(Secp256k1::F::ZERO.to_repr().as_ref());
        // TxOut { value: u64::MAX, script_pubkey: empty }
        buf.extend(consensus_serialize(&TxOut {
            value: Amount::from_sat(value),
            script_pubkey: ScriptBuf::new(),
        }));
        // OutPoint::null-ish
        buf.extend(consensus_serialize(&OutPoint {
            txid: Txid::from_byte_array([0; 32]), vout: 0,
        }));
        buf.as_slice()
    }).unwrap()
}

// Two inputs each claiming u64::MAX satoshis: input_sat overflows at
// send.rs:175 -> panic (checked builds) or wraps (release).
let o1 = forged_output(u64::MAX);
let o2 = forged_output(u64::MAX);
let payments = [(ScriptBuf::new_p2tr_tweaked(tweaked_key), 546)];
let _ = SignableTransaction::new(vec![o1, o2], &payments, None, None, 20);
```

Equivalently, an over-claimed `fee_per_vbyte` (e.g., `u64::MAX`) overflows `fee_per_vbyte * vbytes` at `send.rs:206`, and any `SignableTransaction` deserialized with outputs exceeding inputs triggers the `u64` underflow in `fee()` at `send.rs:139-141`.
