### Title
Stale partial line-selection indices can silently include/exclude the wrong diff lines when a working-directory diff changes underneath a pending commit - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a user has a partial (line-level) selection on a modified file and the working-directory diff is reloaded (e.g. after a background refresh triggered by a fetch, checkout, or filter re-running), Desktop only prunes selection indices that no longer exist in the new diff — it does not verify that surviving indices still refer to the same logical lines. The stale index set is then fed straight into `formatPatch`, which builds the commit patch purely from line **indices**, not line identity.

### Finding Description
In `_selectWorkingDirectoryFiles` → `updateChangesWorkingDirectoryDiff`, after a new diff is fetched, Desktop recomputes the set of `selectableLines` from the new diff and calls `withSelectableLines` on the existing selection: [1](#0-0) 

The comment in the code is explicit about the limitation:
> "The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..."

This means the selection is keyed on **absolute line indices** (`hunk.unifiedDiffStart + index`), not on line content or identity. If the diff shape shifts (hunks grow/shrink, lines are added above a previously-selected line) between the time the user made their partial selection and the time the diff is reloaded, an index that used to point at line X can end up pointing at a completely different line Y in the new diff — and if index Y also happens to still be a valid "selectable" line, it is kept selected with no re-validation.

That stale, index-based selection is later consumed verbatim by the patch builder: [2](#0-1) 

`file.selection.isSelected(absoluteIndex)` decides, line-by-line, whether a hunk line is written into the outgoing patch — there is no secondary check that the line text matches what the user actually saw/selected in the UI.

### Impact Explanation
Because the patch is built purely from position (index), not content, a working-directory change that happens between "user selects lines" and "diff reload → commit" can cause Desktop to stage/commit different code than what the user reviewed and intended to include — a silent corruption of what the user commits. This is explicitly called out as an accepted valid-impact category (“silent corruption of what the user commits or pushes”). The trigger for such a working-directory change can come from repository-controlled mechanics that run without explicit user action — e.g. `clean`/`smudge` filters or line-ending normalization (`.gitattributes`, `core.autocrlf`) defined in a cloned/fetched repository, which Desktop itself detects and reports via `parseLineEndingsWarning`: [3](#0-2) 

A malicious repository that ships filters/attributes causing content to reflow when Desktop re-diffs a file (e.g. after a background auto-refresh) could exploit this window to get unintended lines silently committed under the user's identity.

### Likelihood Explanation
This requires a specific race: the user must leave a partial selection pending while a diff reload happens (background refresh on focus, after fetch/checkout, or after an external editor/filter modifies the file) with a repository-supplied mechanism that shifts diff line positions during that window. This is a real but narrow timing window, not attacker-triggered on demand — likelihood is Low/Medium, but it does not require local access, admin rights, or prior malware; the attacker only needs to control repository content (filters/attributes) that a normal `git clone`/fetch would apply.

### Recommendation
Revalidate partial selections against line content (not just index) when a diff is reloaded — e.g., diff the old and new hunk line text at each previously-selected index, and drop (or re-prompt for) any selection whose underlying line text no longer matches, rather than only pruning indices that fell outside the new `selectableLines` range.

### Proof of Concept
1. Clone a malicious repository containing a `.gitattributes`/clean filter that reformats a tracked file (adds/removes leading blank lines) when Git processes it.
2. In Desktop, modify the file and select only specific lines for partial commit (e.g., lines 10–12).
3. Trigger a background repository refresh (e.g. return focus to the app, or a scheduled fetch) that causes `updateChangesWorkingDirectoryDiff` to reload the diff while the filter output shifts line positions.
4. Observe (via `formatPatch`) that the committed patch, keyed on the unchanged absolute indices, now includes/excludes different content than originally selected by the user, producing a commit whose actual content differs from what was reviewed/intended.

/**
 * `git diff` will write out messages about the line ending changes it knows
 * about to `stderr` - this rule here will catch this and also the to/from
 * changes based on what the user has configured.
 */
const lineEndingsChangeRegex =
  /', (CRLF|CR|LF) will be replaced by (CRLF|CR|LF) the .*/

/**
 * Utility function for inspecting the stderr output for the line endings
 * warning that Git may report.
 *
 * @param error A buffer of binary text from a spawned process
 */
function parseLineEndingsWarning(error: Buffer): LineEndingsChange | undefined {
  if (error.length === 0) {
    return undefined
  }

  const errorText = error.toString('utf-8')
  const match = lineEndingsChangeRegex.exec(errorText)
  if (match) {
    const from = parseLineEndingText(match[1])
    const to = parseLineEndingText(match[2])
    if (from && to) {
      return { from, to }
    }
  }

  return undefined
}
