### Title
Relayer fee for GET responses can be paid out repeatedly because the fee record is never cleared and the response-receipt is overwritten without an existence check - (File: `evm/src/core/EvmHost.sol`)

### Summary
The external report's core defect is: a state value tied to a per-user record is decremented/consumed by a public entrypoint **without first checking that the record has already been deleted/used**, letting the same action be repeated and drain a shared resource. The local analog is in `EvmHost.dispatchIncoming(GetResponse, address relayer)`: the "replay protection" write to `_responseReceipts[commitment]` is unconditional (no check that a receipt doesn't already exist), and the relayer-fee payout that follows reads `_requestCommitments[commitment].fee` — a value that is **never zeroed/deleted** on this success path, unlike every other terminal path in the same contract (`dispatchTimeOut` for both GET and POST explicitly `delete _requestCommitments[commitment]` before proceeding).

### Finding Description
In `evm/src/core/EvmHost.sol`: [1](#0-0) 

```solidity
function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
    // replay protection
    bytes32 commitment = response.request.hash();
    _responseReceipts[commitment] = ResponseReceipt({
        relayer: relayer,
        responseCommitment: response.hash()
    });

    (bool success,) = _bytesToAddress(response.request.from)
        .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

    if (!success) {
        // so that it can be retried
        delete _responseReceipts[commitment];
        return;
    }

    // reward the relayer fee
    uint256 fee = _requestCommitments[commitment].fee;
    if (fee != 0) {
        IERC20(feeToken()).safeTransfer(relayer, fee);
    }
    emit GetRequestHandled({commitment: commitment, relayer: relayer});
}
```

Two things are missing that the sibling timeout handlers deliberately implement:

1. **No pre-existence check on `_responseReceipts[commitment]`.** The mapping is written unconditionally rather than guarded (e.g. `require(_responseReceipts[commitment].relayer == address(0))`). The comment even calls this "replay protection," but a comment overwrite with no guard is not protection.
2. **`_requestCommitments[commitment]` is never deleted** after a successful GET response, so `fee` stays non-zero forever. Compare with the timeout paths in the same file, which both explicitly clear this value before proceeding: [2](#0-1) 

```solidity
function dispatchTimeOut(
    GetRequestTimeout memory timeout,
    FeeMetadata memory meta,
    bytes32 commitment
) external restrict(_hostParams.handler) {
    // replay protection
    delete _requestCommitments[commitment];
    ...
```

The GET-response success path is the odd one out: it pays the fee but leaves the exact same commitment's fee record intact, so any subsequent invocation of `dispatchIncoming(GetResponse, relayer)` for the same request commitment (e.g. via a resubmitted or independently-provable state proof for the same `GetResponse`, which is possible any time a fresh membership/state proof can be produced for already-committed state) pays the relayer fee out again.

### Impact Explanation
This is a fund-loss / double-claim bug in the core `EvmHost` contract that everyone's ISMP messages flow through. If the fee record for a request is never invalidated after being consumed once, the same commitment can be used to re-claim the relayer reward each time the handler is invoked with a valid proof for that response, draining `feeToken()` balance from the host to any relayer (or, since `relayer` is an argument controlled by whoever submits the proof through the handler, potentially to an attacker-controlled address) beyond the amount the original requester paid. This falls squarely under the required impact categories: "stealing or loss of funds" and "replay/double-claim/double-settlement."

### Likelihood Explanation
The severity of this finding depends entirely on whether `HandlerV2` (the only contract authorized via `restrict(_hostParams.handler)` to call `dispatchIncoming`) itself prevents a second call for an already-delivered `GetResponse` commitment. I was unable to fully inspect `evm/src/core/HandlerV2.sol` to confirm or rule out an upstream duplicate-commitment check before this iteration ended, so this is the main open uncertainty. However, even if the handler currently blocks exact duplicate calls, the vulnerability's root cause — `_requestCommitments[commitment].fee` never being cleared on the success path, unlike every other terminal path in the contract — is a genuine and locally provable code defect: it means the safety of "no double payout" rests entirely on an assumption external to `EvmHost.sol` rather than on the host's own state machine, exactly the same class of latent risk as the reported `amountOfUsers` bug (a value that should be checked/cleared before being consumed a second time, isn't).

### Recommendation
- After a successful `onGetResponse` call in `dispatchIncoming(GetResponse, ...)`, delete `_requestCommitments[commitment]` (mirroring the timeout paths) so the fee cannot be read/paid a second time.
- Add an explicit existence check on `_responseReceipts[commitment]` before writing it (e.g. revert if `relayer != address(0)`), so the "replay protection" comment matches actual enforced behavior rather than relying solely on the calling handler's own bookkeeping.

### Proof of Concept
Conceptual (contingent on confirming the handler does not itself block re-delivery of the same response commitment):
1. A GET request with a non-zero fee is dispatched and successfully answered; `dispatchIncoming(GetResponse, relayer1)` runs, pays `fee` to `relayer1`, but leaves `_requestCommitments[commitment].fee` unchanged.
2. Because nothing on the `EvmHost` side clears or checks prior consumption of this fee record, any later authorized call to `dispatchIncoming` for the same `commitment` (e.g., a second valid state/membership proof for the identical committed response, submitted through the handler) will again find `fee != 0` and transfer it — this time to whatever `relayer` address is passed in that second call.
3. Repeating step 2 drains `feeToken()` from the host in multiples of the original single-use fee, with no on-chain state ever indicating the fee had already been claimed.

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;

        if (meta.fee != 0) {
            // refund relayer fee

    }
