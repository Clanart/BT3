### Title
SQL Injection in WalletNftStore.get_nft_list via unsanitized `did_id`/`wallet_id` string interpolation - (File: chia/wallet/wallet_nft_store.py)

### Summary
`WalletNftStore.get_nft_list` constructs its `WHERE` clause with Python f-strings that directly splice `wallet_id` and `did_id.hex()` into the SQL text, rather than passing them as bound parameters.

### Finding Description
All other query builders in `wallet_nft_store.py` (`delete_nft_by_nft_id`, `delete_nft_by_coin_id`, `update_pending_transaction`, `save_nft`, `count`, `is_empty`) bind untrusted values using `?` placeholders and a `params` tuple/list, e.g. [1](#0-0)  and [2](#0-1) . In contrast, `get_nft_list` builds the filter clause by directly interpolating `wallet_id` and `did_id.hex()` into the SQL string: [3](#0-2) 

Only `start_index`/`count` are coerced with `int()`; `did_id` is inserted as a raw quoted string (`f" did_id='{did_id.hex()}'"`) with no sanitization, and `wallet_id` is inserted as a raw numeric literal without any type check. `did_id: bytes32 | None` is normally derived from `bytes32.hex()`, which can only produce hex characters, so under the *documented* type contract this path is not directly exploitable from external hex-encoded input. However, this is exactly the "concatenate untrusted-looking values into SQL text" bug class described in CVE-2024-51211 (`resetuserinfo.php`'s `$username_stn_id` parameter) — the value is trusted to already be "safe" (a hex string / int) without the query itself enforcing that with parameter binding, which is a fragile pattern that breaks if `did_id`/`wallet_id` typing is ever loosened, or if this function is called with attacker-influenced values from another calling context (e.g. a future RPC that passes a raw string instead of a `bytes32`).

### Impact Explanation
If `get_nft_list` is ever invoked with a `did_id`/`wallet_id` value that isn't strictly validated as `bytes32`/`uint32` before reaching this function (e.g., values sourced from RPC-supplied wallet IDs or DID strings without a validating decorator), an attacker could inject arbitrary SQL into the `WHERE` clause of the `users_nfts` table query, enabling data exfiltration (e.g., `UNION SELECT`-based reads of the local wallet database), corruption, or query-logic bypass (returning arbitrary NFT ownership records to an unprivileged caller). This does not directly cause unauthorized coin movement, but it is a genuine query-construction defect in the wallet's local database layer that violates the parameterized-query invariant maintained everywhere else in the store, and could escalate to information disclosure of wallet-held NFT/DID ownership data if the call site's input validation is weakened.

### Likelihood Explanation
Current callers of `get_nft_list` (RPC/wallet layer) pass strongly-typed `bytes32`/`uint32` values, which limits practical exploitability today. This is a defense-in-depth violation rather than a currently demonstrated remote-triggerable injection, so likelihood is lower than the reported CVE, but the pattern deviates from the rest of the codebase's consistent parameter-binding discipline and represents latent risk.

### Recommendation
Refactor `get_nft_list` in `chia/wallet/wallet_nft_store.py` to use `?` placeholders and pass `wallet_id`/`did_id.hex()` as bound parameters (consistent with `count()` and `is_empty()` in the same file), eliminating any string interpolation of caller-supplied values into the SQL text.

### Proof of Concept
Not independently demonstrable as a remotely triggerable exploit from the code paths currently reachable, because all current call sites pass typed `bytes32`/`uint32` values that cannot contain SQL metacharacters. The defect is a code-pattern/root-cause finding: [3](#0-2)  constructs SQL via string interpolation rather than parameter binding, unlike the rest of the file.
