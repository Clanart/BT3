### Title
Malformed FROST preprocess can panic Bitcoin transaction signing via an identity aggregate nonce - ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
Bitcoin's FROST algorithm panics when the aggregate nonce `R` is the point at infinity. A participant can feed an attacker-controlled `Preprocess` into `AlgorithmSignMachine::read_preprocess`, after which `sign` calculates aggregate nonces from those commitments and passes `nonce_sums[0][0]` to `Hram::hram`. If the submitted commitments make that sum identity, `x()` panics on `encoded.x().expect("point at infinity")`, causing a repeatable signing-process denial of service. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`TransactionSignMachine::read_preprocess` delegates each input's preprocess parsing to `AlgorithmSignMachine::read_preprocess`, which reads the attacker-controlled `Commitments` before `sign` uses them to construct `B` and derive `Rs = B.nonces(&nonces)`. [1](#0-0) [2](#0-1) 

The Bitcoin Schnorr HRAm documents that `R` or `A` being infinity will panic, and `hram` passes `R` directly into `x(R)`. [4](#0-3) 

`x()` calls `key.to_encoded_point(true)` and then unconditionally unwraps the x-coordinate, which is absent for the point at infinity. [3](#0-2) 

The vulnerable call is reached through `Algorithm::sign_share`, which indexes `nonce_sums[0][0]` without checking whether the aggregate nonce is identity before calling `H::hram`. [5](#0-4) 

### Impact Explanation
An unprivileged signing participant who can submit preprocess bytes can repeatedly abort transaction signing by triggering a panic rather than an error. [1](#0-0) [3](#0-2) 

This is an availability failure matching the externally reported bug class: attacker-controlled protocol input reaches a crash path inside cryptographic processing, rather than merely producing an invalid-signature result. [2](#0-1) [5](#0-4) 

### Likelihood Explanation
The attacker only needs to influence a participant's serialized preprocess commitments; `read_preprocess` is explicitly the parser for those messages, and `sign` incorporates those commitments into the aggregate nonce used as `R`. [1](#0-0) [6](#0-5) 

The panic is deterministic whenever the resulting aggregate nonce is identity, because the Bitcoin HRAm assumes `x()` is only called for non-infinity points. [3](#0-2) [4](#0-3) 

### Recommendation
Reject identity aggregate nonces before calling `Hram::hram`, and reject identity commitment components or the identity aggregate at the `read_preprocess`/`sign` boundary. [1](#0-0) [2](#0-1) 

For Bitcoin specifically, make `x()` return `io::Result`/`Option` or check `key.is_identity()` before `to_encoded_point`, and surface a `FrostError::InvalidPreprocess` rather than panicking. [3](#0-2) [7](#0-6) 

### Proof of Concept
The reachable sequence is:

```rust
// Attacker-controlled bytes
let preprocess_bytes: &[u8] = /* serialized Preprocess<Secp256k1, ()> */;

let preprocess = machine
  .read_preprocess(&mut preprocess_bytes)
  .expect("parser accepts the malformed commitments");

let mut commitments = HashMap::new();
commitments.insert(attacker_participant, preprocess);

// This derives the aggregate nonce from the attacker's commitments and then calls:
// sign_share -> Hram::hram -> x(R)
let _ = machine.sign(commitments, b"");
```

If those commitments make `nonce_sums[0][0]` the point at infinity, execution reaches `x(R)` and panics at `encoded.x().expect("point at infinity")`. [2](#0-1) [5](#0-4) [3](#0-2)
