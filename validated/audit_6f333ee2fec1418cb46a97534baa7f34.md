### Title
Unauthenticated Withdrawal Triggering via Aggregator When `aggregator_verification_address` Is Unset — (File: `core/src/rpc/operator.rs`)

### Summary
The operator's `Withdraw` RPC unconditionally skips ECDSA verification when `aggregator_verification_address` is not configured (the default). Because the aggregator gRPC server enforces no client-certificate authentication by design, any party that can reach the aggregator's TCP port can call `aggregator.Withdraw()` with a valid Citrea withdrawal, causing the operator to sign and broadcast a payout transaction without its consent and without any verification signature.

### Finding Description

**Step 1 — Aggregator enforces no client-certificate authentication.**

The aggregator server is created with the same `create_grpc_server` helper used for operators and verifiers. When `client_verification = false` (the default when the env-var is absent), the interceptor is set to `Noop` and no TLS client certificate is required. [1](#0-0) 

The documentation explicitly states: *"The aggregator does not enforce client certificates but does use TLS for encryption."* [2](#0-1) 

**Step 2 — `aggregator_verification_address` is optional and defaults to `None`.**

`BridgeConfig` declares the field as `Option<alloy::primitives::Address>`. When the env-var `AGGREGATOR_VERIFICATION_ADDRESS` is absent, the field is `None`. [3](#0-2) [4](#0-3) 

**Step 3 — The operator's `Withdraw` RPC skips ECDSA verification when the field is `None`.**

The handler wraps the entire verification block in `if let Some(address_in_config) = self.operator.config.aggregator_verification_address`. When the field is `None`, the block is never entered and execution falls through directly to `operator.withdraw(...)`. [5](#0-4) 

**Step 4 — `Withdraw` is not an "Internal" method, so the operator's mTLS interceptor allows any caller presenting the aggregator's certificate.**

The interceptor classifies a request as internal only if the gRPC method name starts with `"Internal"`. `Withdraw` does not, so it is reachable by anyone presenting the aggregator's certificate. [6](#0-5) [7](#0-6) 

**Step 5 — The aggregator's `Withdraw` handler forwards the request to operators without adding any verification signature.**

The aggregator parses the `AggregatorWithdrawalInput`, validates operator keys, and forwards the `WithdrawParamsWithSig` as-is to each operator. No ECDSA signature is injected. [8](#0-7) 

**Step 6 — The proto definition confirms `verification_signature` is optional.**

`WithdrawParamsWithSig.verification_signature` is declared `optional string`, so a caller may omit it entirely. [9](#0-8) 

### Impact Explanation

An unprivileged attacker who can reach the aggregator's gRPC port (the public-facing bridge endpoint) can:

1. Enumerate pending Citrea withdrawals from the on-chain bridge contract (public data).
2. Call `aggregator.Withdraw()` with a valid withdrawal's parameters and no `verification_signature`.
3. The aggregator forwards the request to every operator using its own mTLS certificate.
4. Each operator whose `aggregator_verification_address` is `None` processes the withdrawal unconditionally: it signs and broadcasts a payout transaction, spending its own BTC liquidity.

The operator's funds are not permanently stolen (the reimbursement flow eventually returns them), but:
- The operator is forced to sign and broadcast Bitcoin transactions without its consent — a direct authorization bypass in the withdrawal signing flow.
- The operator's entire available liquidity can be drained by replaying all pending Citrea withdrawals in rapid succession, causing a liveness failure.
- If the operator's `operator_withdrawal_fee_sats` is `None` or zero, even unprofitable withdrawals are processed, causing direct financial loss per transaction.

This satisfies the allowed impact: *"Authentication or authorization bypass in gRPC, mTLS, actor roles, or signer flow that grants privileged bridge actions to the wrong party"* and *"unauthorized state transition in withdrawal flow that breaks bridge safety/liveness with material fund impact."*

### Likelihood Explanation

- `aggregator_verification_address` is `Option<>` with no enforcement; operators that omit it (the default) are vulnerable.
- The aggregator's gRPC port is the intended public-facing endpoint for the clementine-backend service; it is reachable without a client certificate.
- No special keys or internal access are required — only knowledge of a valid Citrea withdrawal ID and its on-chain parameters, which are public.

### Recommendation

1. **Make `aggregator_verification_address` mandatory** for production deployments. Remove the `Option<>` wrapper or add a startup check that rejects `None` when `client_verification = true`.
2. **Enforce client-certificate authentication on the aggregator** for the `Withdraw` RPC, or add a separate role-based check so that only known backends can trigger withdrawals.
3. **Add a mainnet guard** analogous to the existing `CLIENT_VERIFICATION=false` check that rejects startup when `aggregator_verification_address` is absent on mainnet. [10](#0-9) 

### Proof of Concept

```
# 1. Read a pending withdrawal from the Citrea bridge contract (public on-chain data):
#    withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount

# 2. Connect to the aggregator's gRPC port — no client certificate required:
grpcurl -insecure <aggregator_host>:<port> \
  clementine.ClementineAggregator/Withdraw \
  -d '{
    "withdrawal": {
      "withdrawal": {
        "withdrawal_id": <id>,
        "input_signature": "<hex>",
        "input_outpoint": { "txid": { "txid": "<hex>" }, "vout": <n> },
        "output_script_pubkey": "<hex>",
        "output_amount": <sats>
      }
      // verification_signature intentionally omitted
    }
  }'

# 3. The aggregator forwards to each operator with its mTLS certificate.
# 4. Each operator whose aggregator_verification_address is None processes the withdrawal:
#    - Signs the payout transaction with its private key
#    - Broadcasts it to the Bitcoin network
#    - Returns RawSignedTx confirming the spend
```

The operator's `deposit_sign` RPC exhibits the same pattern — it is not an "Internal" method and has no additional authentication beyond the mTLS interceptor, so when `client_verification = false` it is reachable by any caller and will sign deposit transactions on demand. [11](#0-10) [12](#0-11)
