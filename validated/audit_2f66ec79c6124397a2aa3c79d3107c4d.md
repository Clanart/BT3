### Title
Unconditional re-enabling of `protocol.file.allow=always` for submodule updates on attacker-controlled `.gitmodules` URLs - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` accepts an `allowFileProtocol` flag that, when `true`, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation [1](#0-0) . This flag is threaded through `checkoutBranch` and `checkoutCommit` in `app/src/lib/git/checkout.ts`, both of which default it to `false` but expose it as a caller-supplied boolean parameter used to run submodule updates after every branch/commit checkout [2](#0-1) .

### Finding Description
This maps to the same trust-boundary defect as the reported `Controller._call` issue: a value that is entirely attacker-controlled (the submodule URL embedded in a cloned repository's `.gitmodules` file) is fed into a privileged execution path without the caller validating that the destination is a "safe" endpoint. Just as `Controller._call` blindly invokes `callFunction` on any `callee` address regardless of whether it actually implements `CalleeInterface`, `updateSubmodulesAfterOperation` blindly re-enables the `file://` transport for `git submodule update` regardless of whether the submodule URL is something the user actually trusts.

`protocol.file.allow=always` (as opposed to Git's default `protocol.file.allow=user`) was specifically the setting Git upstream tightened in response to CVE-2022-39253, where a malicious repository could point a submodule at `file://` (potentially combined with hardlink/`.git` file tricks) to make `git submodule update --recursive` read/exfiltrate files from outside the intended working tree during clone/checkout of an untrusted repository. Passing `allowFileProtocol=true` reintroduces exactly that relaxed transport whenever it is invoked, and the URL that gets consumed under that relaxed policy comes straight from the untrusted repository content (`.gitmodules`), not from the app or the user.

### Impact Explanation
If any code path in Desktop calls `checkoutBranch`/`checkoutCommit` (or the lower-level `updateSubmodulesAfterOperation`) with `allowFileProtocol: true` while operating on a repository that was cloned/fetched from an untrusted source, a malicious submodule URL in `.gitmodules` can leverage the `file://` transport during `git submodule update --init --recursive` to read or copy local files outside the intended repository boundary onto disk, corrupting the working tree or exfiltrating local file contents into the checked-out repo — a "silent corruption of what the user commits" (an attacker-supplied submodule payload becomes part of the local working directory as if it were legitimate content) and potentially a file-read outside the repo.

### Likelihood Explanation
Exploitability depends entirely on whether Desktop actually calls these functions with `allowFileProtocol=true` for repositories originating from untrusted/attacker-controlled clones (e.g., a repo added via "Open in Desktop", a cloned fork, or a fetched branch containing a crafted `.gitmodules`). I was not able to fully trace every call site of `checkoutBranch`/`checkoutCommit` within the available search budget to confirm which flows pass `true` versus the safe default `false`, so this should be verified by inspecting `app-store.ts`/`dispatcher.ts` callers of these functions before treating this as a confirmed exploitable bug rather than a latent unsafe API.

### Recommendation
- Never allow `allowFileProtocol=true` to be derived from, or applied uniformly to, repositories/branches/commits that could contain attacker-supplied `.gitmodules` content unless the specific submodule URLs have been validated as safe (e.g., restricted to `https`/`ssh` only, or confirmed to reference the same trusted remote as the parent repo).
- Prefer leaving Git's default `protocol.file.allow=user` behavior intact for submodule operations triggered on cloned/fetched (as opposed to locally created) repositories.
- Add an explicit allowlist check on submodule URLs (protocol + same-origin) before opting into the relaxed `protocol.file.allow=always` behavior, mirroring the "callee must implement `CalleeInterface`" recommendation from the original report.

### Proof of Concept
1. Craft a malicious repository containing a `.gitmodules` entry with a `file://` URL pointing outside the repository (e.g., referencing a sensitive path via a crafted relative/hardlinked target), following the CVE-2022-39253 pattern.
2. Get a victim to clone or add this repository in GitHub Desktop and check out the branch/commit containing this `.gitmodules`.
3. If the checkout path used passes `allowFileProtocol: true` into `updateSubmodulesAfterOperation` [3](#0-2) , `git -c protocol.file.allow=always submodule update --init --recursive` executes with the relaxed policy, allowing the crafted submodule to read/copy files from outside the intended repository directory into the victim's working tree.

**Uncertainty**: I could not confirm, within the available tool budget, which UI/dispatcher call sites pass `allowFileProtocol=true` versus rely on the safe default of `false`. Confirming this (in `app/src/ui/dispatcher/dispatcher.ts` and `app/src/lib/stores/app-store.ts`) is necessary to determine whether this is a live reachable path or a currently-unused defensive parameter.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
