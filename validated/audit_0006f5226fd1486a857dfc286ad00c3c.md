### Title
Cross-shop session/token confusion via unscoped `shopify_user_id` lookup in `UserSessionStorage.store` - ([File: lib/shopify_app/session/user_session_storage.rb])

### Summary
The reported Beanstalk bug is a class of "overwrite instead of properly accumulating/scoping per-key state" issue. The analogous pattern in this repo is `ShopifyApp::UserSessionStorage.store`, which persists an online (user) session keyed **only** by `shopify_user_id`, unconditionally overwriting the `shopify_domain` and `shopify_token` columns of that single record regardless of which shop the new session belongs to.

### Finding Description
`UserSessionStorage.store` looks up (or creates) a `User` record solely by `shopify_user_id` and then overwrites `shopify_domain` and `shopify_token` with the values from whatever session is being stored, with no scoping/reconciliation against the shop already associated with that record: [1](#0-0) 

The same unscoped pattern exists in the deprecated `UserSessionStorageWithScopes`: [2](#0-1) 

Session retrieval mirrors this: both `SessionRepository#load_session` (for online sessions) and `retrieve_by_shopify_user_id` resolve a session purely by the numeric user id parsed out of the session id string, never by shop: [3](#0-2) [4](#0-3) 

Critically, `ShopifyApp::TokenExchange#activate_shopify_session` trusts the *stored* session's `shop` value as the "authenticated" domain rather than strictly deriving it from the freshly verified ID token, and only rejects a mismatch if the `shop` request parameter happens to be present: [5](#0-4) [6](#0-5) 

Because `reject_mismatched_requested_shopify_domain` short-circuits (`return false if requested_domain.blank?`), any authenticated request that omits the `shop` query parameter (e.g. an XHR/API call using only the `Authorization: Bearer <id_token>` header — a normal, legitimate call pattern for embedded apps) skips the domain-consistency check entirely, and whichever shop/token is currently stored against that `shopify_user_id` record is silently used.

### Impact Explanation
If the same numeric Shopify user id (the JWT `sub` claim used as `shopify_user_id`) becomes associated, at different points in time, with sessions for two different shops (this occurs for any staff account/collaborator that has access to multiple shops the app is installed on, or any user record reused when tokens are refreshed for a different shop context), the single `User` record's `shopify_domain`/`shopify_token` gets overwritten by whichever shop authenticated most recently — exactly like the Solidity bug overwriting a balance instead of tracking it per-key. Once overwritten:
- A subsequent verified request from Shop A (whose ID token is otherwise perfectly valid) can be served using Shop B's stored access token and shop context if the `shop` query parameter is absent, because `authenticated_shopify_domain_from_token` prefers `current_shopify_session.shop` (the possibly-stale/overwritten DB value) over the value embedded in the freshly verified token.
- This is a cross-shop/cross-tenant session and token confusion: API calls, billing checks, and business logic keyed off `current_shopify_domain`/`current_shopify_session` can operate against the wrong shop's access token.

### Likelihood Explanation
This requires that the same Shopify `shopify_user_id` be used to authenticate against more than one shop for the same app installation — a legitimate, no-privilege-escalation-required scenario for shared/collaborator staff accounts, which Shopify explicitly supports (staff can be granted access to multiple stores). No cryptographic forgery or secret leakage is required; only the ordinary token-exchange flow and the omission of the `shop` query parameter (common for background/XHR calls using only the bearer/id token) are needed to trigger the confused-session behavior.

### Recommendation
Scope the user session storage/lookup by `(shopify_user_id, shopify_domain)` rather than `shopify_user_id` alone, so switching shop context for the same numeric user id does not overwrite a different shop's stored token, e.g. change `find_or_initialize_by(shopify_user_id: user.id)` in `UserSessionStorage.store` to include the shop domain in the lookup key, and enforce a uniqueness constraint on the pair. Additionally, `authenticated_shopify_domain_from_token` should always be derived from/validated against the freshly verified ID token's domain claim (`jwt_shopify_domain`) rather than trusting the potentially stale `current_shopify_session.shop` value, and the domain-consistency check should not be skippable simply because the `shop` query parameter is absent.

### Proof of Concept
1. App is installed on Shop A and Shop B; a staff user (numeric id `U`) is a collaborator/staff member with access to both.
2. User authenticates (via token exchange or OAuth) on Shop A: `UserSessionStorage.store` creates a `User` row with `shopify_user_id=U`, `shopify_domain="shop-a.myshopify.com"`, `shopify_token=<token-a>`.
3. The same user authenticates on Shop B: `find_or_initialize_by(shopify_user_id: U)` finds the *same* row and overwrites it to `shopify_domain="shop-b.myshopify.com"`, `shopify_token=<token-b>` — see [7](#0-6) .
4. A subsequent legitimate, still-valid ID-token request for Shop A arrives without a `shop` query parameter (e.g., an XHR call authenticated only via `Authorization: Bearer <id_token_for_shop_a>`).
5. `current_shopify_session_id` resolves to `online_U`; `SessionRepository.load_session` returns the (now Shop-B) record; `authenticated_shopify_domain_from_token` returns `"shop-b.myshopify.com"` (from the stale stored session) instead of Shop A; `reject_mismatched_requested_shopify_domain` returns `false` immediately since `requested_shopify_domain` is blank — see [8](#0-7) .
6. The controller action proceeds using Shop B's access token/context for a request that was intended for/verified against Shop A, resulting in cross-shop token/session confusion.

    def authenticated_shopify_domain_from_token
      current_shopify_session&.shop || jwt_shopify_domain
    end

    def reject_mismatched_requested_shopify_domain
      requested_domain = requested_shopify_domain
      return false if requested_domain.blank?

      authenticated_domain = authenticated_shopify_domain_from_token
      return false if authenticated_domain.blank? || authenticated_domain == requested_domain

      ShopifyApp::Logger.debug("Shop context validation failed")
      head(:unauthorized)
      true
    end
