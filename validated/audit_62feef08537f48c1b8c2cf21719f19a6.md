## Analog Found: Missing Range Validation in ProtoJSON `Timestamp` Parsing

### Title
Missing Calendar-Field Range Validation in `ParseTimestamp` Leads to Silent Data Corruption - (File: `src/google/protobuf/json/internal/parser.cc`)

### Summary
The original Solidity report's failed invariant is that `linearInterpolation` performs interval arithmetic (`endX.sub(startX)`) assuming `startX <= endX` without validating it, so out-of-order attacker-influenced inputs silently produce incorrect results rather than being rejected. The direct Protobuf analog is `ParseTimestamp` in the ProtoJSON parser, which performs calendar arithmetic (a Julian-day epoch computation) on `year`/`mon`/`day`/`hour`/`min`/`sec` fields taken from an attacker-supplied JSON string, but never validates that these components lie within their semantically valid ranges (month 1–12, day 1–31, hour 0–23, minute/second 0–59) before doing the math.

### Finding Description
`ParseTimestamp` extracts each date/time component via `TakeTimeDigitsWithSuffixAndAdvance`, which only enforces digit-count and separator-character structure, not value range: [1](#0-0) 

The extracted `year`/`mon`/`day`/`hour`/`min`/`sec` values are then fed directly into a Julian-day style epoch calculation that implicitly assumes calendar-valid inputs (e.g. `mon` in `[1,12]`, `day` in `[1,31]`): [2](#0-1) 

Only "is non-zero" is checked (`*year == 0`, `*mon == 0`, `*day == 0`); values like `mon=99`, `day=99`, `hour=99`, `min=99`, `sec=99` pass structural validation and are used verbatim in the arithmetic. The resulting `secs` value is written straight into the message with no post-hoc bounds/sanity check: [3](#0-2) 

This is the same failure class as the reported Solidity bug: an arithmetic routine assumes its inputs satisfy an implicit ordering/range invariant, but no explicit check enforces that invariant before the computation runs, so malformed-but-structurally-plausible input yields a "successful" parse with an incorrect result instead of an error.

For comparison, the upb C JSON decoder for the same well-known type at least partially checks the *lower* bound of the final computed value (though it similarly fails to validate the individual calendar components before doing the epoch-day math): [4](#0-3) 

The C++ `ParseTimestamp` path has no equivalent bound check at all, so it is strictly weaker.

### Impact Explanation
Any consuming application that accepts ProtoJSON-encoded `google.protobuf.Timestamp` fields (e.g. via gRPC-JSON transcoding, REST APIs, or any service parsing untrusted JSON payloads into protobuf messages) can have a `Timestamp` field silently populated with an arithmetically-wrong but syntactically "valid" `seconds` value from a malformed date string such as `"2023-99-99T99:99:99Z"`. Because the parse call returns `absl::OkStatus()`, the caller has no signal that the value is garbage. Any downstream logic relying on that timestamp for correctness (expiration checks, ordering, audit logging, access windows) would silently operate on corrupted data — a data-integrity impact analogous to the "unexpected behavior in the contract's logic" impact called out in the original report. This is a logic/integrity issue, not a memory-safety issue.

### Likelihood Explanation
High likelihood of reachability: any ordinary client can submit a `Timestamp` JSON string through the public `JsonStringToMessage`/ProtoJSON parsing API, with a trusted schema (well-known `Timestamp` type) and a small, bounded payload (a date string). No privileged access or hostile schema is required — this is a plain malformed-but-shaped input on a supported public parse path.

### Recommendation
Add explicit range validation for each parsed calendar component before performing the epoch arithmetic in `ParseTimestamp`:
- `mon` in `[1, 12]`
- `day` in `[1, 31]` (ideally per-month/leap-year aware, mirroring `google::protobuf::util::TimeUtil`/`well_known_types.py` validation logic used elsewhere)
- `hour` in `[0, 23]`
- `min`, `sec` in `[0, 59]`

Additionally, add a final bounds check on the computed `secs`/`nanos` against the documented valid `Timestamp` range (`0001-01-01T00:00:00Z` to `9999-12-31T23:59:59.999999999Z`), matching the validation already present in `unparser.cc`'s `WriteTimestamp`: [5](#0-4) 

### Proof of Concept
Given a message with a `google.protobuf.Timestamp` field, parsing the JSON string:
```json
{"optionalTimestamp": "2023-99-99T99:99:99Z"}
```
through the public ProtoJSON parse entry point exercises `ParseTimestamp` (`src/google/protobuf/json/internal/parser.cc:832`). `TakeTimeDigitsWithSuffixAndAdvance` accepts `mon=99`, `day=99`, `hour=99`, `min=99`, `sec=99` because it only checks digit-count/separator structure (lines 781-806), not calendar validity. The subsequent epoch-day computation (lines 874-885) then runs on these out-of-range values and produces an arbitrary `secs` value that is written into the message via `Traits::SetInt64` with `absl::OkStatus()` returned — i.e., a "successful" parse of an invalid timestamp into a semantically incorrect field value.

absl::optional<uint32_t> TakeTimeDigitsWithSuffixAndAdvance(
    absl::string_view& data, int max_digits, absl::string_view end) {
  ABSL_DCHECK_LE(max_digits, 9);

  uint32_t val = 0;
  int limit = max_digits;
  while (!data.empty()) {
    if (limit-- < 0) {
      return absl::nullopt;
    }
    uint32_t digit = data[0] - '0';
    if (digit >= 10) {
      break;
    }

    val *= 10;
    val += digit;
    data = data.substr(1);
  }
  if (!absl::StartsWith(data, end)) {
    return absl::nullopt;
  }

  data = data.substr(end.size());
  return val;
}
