### Title
`ThresholdKeys::read` deserializes a semantically unvalidated key set — attacker-supplied `secret_share`/verification shares are never checked for consistency, enabling signing under an attacker-controlled group key - (File: crypto/dkg/src/lib.rs)

### Summary
The bug class in the external report is "unrestricted parameters in a deserialized object lead to execution of attacker-influenced behavior" (CWE-502/CWE-74). Serai's direct analog is `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`, which reconstructs a threshold signing key entirely from a byte stream: `t`, `n`, `i`, an interpolation method plus attacker-supplied `Constant` coefficients, the `secret_share` scalar, and all `n` verification shares. `ThresholdKeys::new` validates only counts and index bounds; it never verifies that `G * secret_share == verification_shares[i]`, nor that the resulting `group_key` matches any externally expected value. The group key is *derived from* the untrusted verification shares at `crypto/dkg/src/lib.rs:376-378`, so whoever controls the serialized blob controls the key the node will sign for.

### Finding Description
`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) reads:

- `t`, `n`, `i` — validated only by `ThresholdParams::new` (non-zero, `t <= n`, `i <= n`) at `crypto/dkg/src/lib.rs:166-179`.
- An interpolation tag; tag `0` reads `n` arbitrary scalars as `Interpolation::Constant` coefficients (`crypto/dkg/src/lib.rs:607-613`), with the sole check `t == n` in `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:368-371`).
- `secret_share` via `C::read_F` (`crypto/dkg/src/lib.rs:618`) — canonical but otherwise unauthenticated.
- `verification_shares[1..=n]` via `C::read_G` (`crypto/dkg/src/lib.rs:620-623`) — note this uses `Ciphersuite::read_G`, not `Curve::read_G`, so even identity points are accepted.

`ThresholdKeys::new` then computes `group_key = Σ_{i∈1..=t} verification_shares[i] * interpolation_factor(i)` from the attacker-supplied data (`crypto/dkg/src/lib.rs:376-378`). There is no consistency proof, no PoK, no hash binding to a prior commitment. The code itself acknowledges the resulting state at `crypto/frost/src/sign.rs:492-494`: "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys."

Two attacker-useful outcomes:

1. **Attacker-known group key.** If the attacker crafts a blob where `secret_share = s` and all `verification_shares[l] = G * s_l` are consistent with a polynomial/constant coefficients the attacker controls, the victim node's `AlgorithmMachine` will happily `preprocess`/`sign`/`complete` signatures under `group_key` whose discrete log the attacker knows. Any signature the node produces is a valid signature under a key the attacker fully controls — and more importantly the victim believes it is signing "as the multisig" for whatever the deserialized key represents.
2. **Silent share/key mismatch.** If `secret_share` does not match `verification_shares[i]`, the victim produces shares that verify against the attacker's chosen verification share but correspond to a different group key — the view and verification share tables are all attacker-defined, so share-level verification in `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:475-489`) validates shares against the attacker-supplied verification shares, not against any trusted key. Offset handling (`crypto/dkg/src/lib.rs:518-521`) adds `offset * G` to `included[0]`'s verification share, again from deserialized state.

The "unrestricted connection parameters" of the GeoServer report map here to unrestricted `t/n/i/interpolation/secret_share/verification_shares` parameters in the serialized key blob — no field is bound to anything the reader already trusts.

### Impact Explanation
Any integrator path that feeds untrusted bytes into `ThresholdKeys::read` — key import/recovery (`crypto/dkg/recovery` family flows), backup restore, or a processor loading validator-set keys received from a peer — lets an unprivileged party define the secret share, the verification shares, and therefore the group key the node will sign under. Concrete results accepted by the scan rules:

- **Signing under an attacker-known group key**: shares combine into valid Schnorr/FROST signatures whose private key the attacker knows (they chose all the shares). Funds or authorizations gated on that key are entirely the attacker's.
- **Forged-looking shares / consensus breakage**: inconsistent `secret_share` vs `verification_shares[i]` produces shares that fail final signature verification while passing per-share verification against the attacker-chosen shares (the `InternalError` branch at `crypto/frost/src/sign.rs:494`), or trivially pass if the attacker made them consistent — either way the node's view of "the multisig key" is attacker-defined.

This is not a malicious-validator/colluding case: the attacker's input is bytes deserialized locally, identical in shape to the GeoServer JDBC-string injection.

### Likelihood Explanation
`ThresholdKeys::read` is a public API explicitly designed to ingest serialized bytes, and the prompt's scope lists it as an accepted untrusted-byte sink. No authentication or MAC is applied to the blob — `write`/`read` is a plain field concatenation (`crypto/dkg/src/lib.rs:538-561`). The only thing standing between an attacker and full key substitution is the integrator's transport-layer trust, which is exactly the assumption the GeoServer advisory violated. Likelihood is therefore moderate-to-high wherever keys are transported or recovered, but it is contingent on an integrator passing attacker-influenced bytes — so it rates below a remotely-reachable wire parser bug.

### Recommendation
- In `ThresholdKeys::new` (or at least in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise.
- For `Interpolation::Constant`, require the caller to additionally supply/verify a commitment to the coefficients, or reject `Constant` on the `read` path unless `t == n` *and* share consistency holds.
- Reject identity points in verification shares by using an identity-rejecting read (as `Curve::read_G` does at `crypto/frost/src/curve/mod.rs:125-131`).
- Document that `ThresholdKeys::read` must only consume authenticated, self-generated bytes, or add a MAC/commitment field to the format so deserialization cannot silently substitute the group's key material.

### Proof of Concept
```rust
// Conceptual PoC (Ed25519 ciphersuite). Attacker constructs a ThresholdKeys
// blob for a group key they fully control, and a node that read()s it will
// sign under that key.

use ciphersuite::Ciphersuite;
use dkg::{ThresholdKeys, Interpolation};
use rand_core::OsRng;
use zeroize::Zeroizing;
use std::collections::HashMap;

// Attacker picks a secret they know.
let attacker_secret = <Ed25519 as Ciphersuite>::random_nonzero_F(&mut OsRng);

// t = n = 1, i = 1, Constant interpolation with coefficient 1.
let mut blob = vec![];
blob.extend((Ed25519::ID.len() as u32).to_le_bytes());
blob.extend(Ed25519::ID);
blob.extend(1u16.to_le_bytes());          // t
blob.extend(1u16.to_le_bytes());          // n
blob.extend(1u16.to_le_bytes());          // i = participant 1
blob.push(0);                             // Interpolation::Constant
blob.extend(Ed25519::F::ONE.to_repr());   // coefficient = 1
blob.extend(attacker_secret.to_repr());   // secret_share (attacker-known)
blob.extend((Ed25519::generator() * attacker_secret).to_bytes()); // vs[1]

// Victim deserializes — no consistency check is performed.
let keys: ThresholdKeys<Ed25519> = ThresholdKeys::read(&mut blob.as_slice()).unwrap();

// keys.group_key() == G * attacker_secret — a key whose discrete log the
// attacker knows. Any AlgorithmMachine built on `keys` produces valid
// FROST signatures under attacker_secret, and keys.params()/view() trust
// the attacker's t/n/i. The mismatch variant (secret_share replaced with a
// random scalar while keeping the same verification share) is also accepted
// by read() and reaches the InternalError branch at frost/src/sign.rs:494.
```
