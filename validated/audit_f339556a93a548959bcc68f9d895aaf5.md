### Title
Hookify block/deny rules silently fail open for `Write` tool due to missing field-mapping validation - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
The Hookify plugin's `RuleEngine._extract_field` maps a rule's configured `field` name to the actual key inside `tool_input`. For the `Write`/`Edit` tools it hard-codes the alias `new_text`/`new_string` → `tool_input.get('new_string', '')`, but the `Write` tool never populates a `new_string` key (it uses `content`), so a rule written against `field: "new_text"` for a `Write` call always evaluates against an empty string. Combined with `_rule_matches` requiring every condition to match and treating a non-matching condition as "rule doesn't fire," this silently disables the security check with no warning to the user, mirroring the reported bug class of missing input validation producing an unintended, insecure default state.

### Finding Description
`_extract_field` first checks `if field in tool_input` directly, then falls back to tool-specific aliasing: [1](#0-0) 

For a `Write` tool call, `tool_input` only contains `file_path` and `content`; it never contains `new_string`. When a rule's `field` is `"new_text"` or `"new_string"`, the direct lookup `field in tool_input` fails, execution falls into the `tool_name in ['Write', 'Edit']` branch, and returns `tool_input.get('new_string', '')`, i.e. an empty string, instead of `None` or the real file content.

`_check_condition` treats `field_value is None` as "condition can never match" (`return False`), but here the returned value is `''` (not `None`), so the condition operator (`contains`, `regex_match`, `starts_with`, etc.) is evaluated against an empty string rather than the actual content being written: [2](#0-1) 

Because `_rule_matches` requires ALL conditions to match for the rule (and hence the block) to trigger, a rule intended to block dangerous Write content (e.g. secrets, `eval(`, obfuscated payloads) via `field: "new_text"` never fires for `Write` tool calls — it silently becomes a no-op: [3](#0-2) 

The plugin's own developer-facing documentation lists `new_text` as a generic, tool-agnostic field name alongside `command`, `file_path`, etc. — reinforcing that a rule author would reasonably expect `new_text` to work uniformly across `Write`/`Edit`/`MultiEdit`: [4](#0-3) 

No validation exists anywhere in `rule_engine.py` or the config loader to detect that a configured `field`/`tool_matcher` combination resolves to a value that can never be populated for the tool being matched, nor is any warning emitted at rule-load or rule-evaluation time.

### Impact Explanation
Hookify's entire purpose is to let a user define `PreToolUse`/`PostToolUse` guardrails (e.g., block writing secrets, block dangerous file content) that constrain the less-trusted party in the trust boundary — the agent, which can be steered by prompt injection, a malicious skill, or poisoned tool output. Because of this unvalidated field-mapping mismatch, a block rule that the user believes protects all file-write operations (`Write`) silently never fires: `evaluate_rules` returns `{}` (no blocking output) even when the actual written content matches the intended dangerous pattern: [5](#0-4) 

This is a hook-bypass in the unprivileged-user trust boundary: the agent can write attacker-influenced content to disk that a security-guidance-style rule was explicitly configured to deny, with the user given no signal that their rule is not enforcing anything. It is the same root cause pattern as the report — a silently permissive/insecure default arising from an unchecked input path — applied to Claude Code's hook-based command/tool approval mechanism instead of Solidity zero-address checks.

### Likelihood Explanation
The likelihood is moderate: it requires a user to author a Hookify rule scoping the `Write` tool with `field: "new_text"` (a name the plugin's own field documentation presents as valid/generic) rather than `content`. This is a very plausible misconfiguration given the API surface explicitly documents both names as legitimate "field" values without clarifying that `new_text`/`new_string` only resolves for `Edit`, not `Write`. Once such a rule exists, every subsequent `Write` call — including ones with attacker-influenced content from a compromised skill, MCP tool output, or prompt-injected instructions — silently bypasses the intended block, with no error, log entry, or warning surfaced anywhere in the code path.

### Recommendation
- In `_extract_field`, return `None` (not `''`) when a field/tool combination has no valid mapping, so `_check_condition`'s existing `None` handling correctly treats it as "cannot evaluate" rather than silently matching against an empty string.
- At rule-load time (in `config_loader.py`) or on first evaluation, validate that a rule's `field` is a supported field for the `tool_matcher`'s tool(s) and emit a `stderr` warning (or refuse to load the rule) when it is not — analogous to explicitly requiring non-zero-address input rather than silently accepting an unusable default.
- Normalize `Write`/`Edit`/`MultiEdit` field aliasing so `new_text`/`content` resolve to the correct underlying key (`content` for `Write`, `new_string` for `Edit`/`MultiEdit`) instead of only checking one hardcoded key per tool.
- Add unit tests asserting that a `field: "new_text"` rule against a `Write` tool_input containing `content` correctly evaluates the real content, not an empty string.

### Proof of Concept
1. Configure a Hookify block rule in the plugin's rule config:
```yaml
name: block-secret-write
event: PreToolUse
tool_matcher: "Write"
action: block
conditions:
  - field: "new_text"
    operator: "contains"
    pattern: "AWS_SECRET_ACCESS_KEY"
message: "Blocked write containing a secret"
```
2. Have the agent call the `Write` tool with:
```json
{"tool_name": "Write", "tool_input": {"file_path": "/tmp/leak.txt", "content": "AWS_SECRET_ACCESS_KEY=AKIA..."}}
```
3. Trace through `_extract_field`: `"new_text" in tool_input` is `False` (only `file_path`/`content` exist) → falls into the `Write`/`Edit` branch → `field == 'new_text'` → returns `tool_input.get('new_string', '')` → `''`.
4. `_check_condition` evaluates `"AWS_SECRET_ACCESS_KEY" in ''` → `False` → the condition, and therefore the rule, never matches.
5. `evaluate_rules` returns `{}` (no block), and the `Write` proceeds, persisting the secret to disk — despite the user's rule appearing correctly configured according to the plugin's documented field names.
