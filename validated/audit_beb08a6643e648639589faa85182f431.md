## Title
Discard-Changes uses an unresolved, symlink-following path for a malicious tracked entry, allowing a crafted repository to redirect file deletion/trash outside the repository - (File: `app/src/lib/stores/git-store.ts`)

### Summary
The report's underlying invariant is: *a value that the code trusts to be "the target of the operation" (a CREATE2 address) can silently diverge from what it actually resolves to, because the code doesn't defend against attacker-controlled state changing what that value points to.* In GitHub Desktop the same class of bug appears in `GitStore.discardChanges()`: the destination path passed to the trash/removal APIs is derived with a plain `Path.resolve`/`Path.join` against `this.repository.path` and `file.path`, with no re-validation that the resolved path actually stays inside the repository working directory (unlike other call sites in the same codebase, e.g. `resolveWithin` in `app/src/lib/path.ts`, which is explicitly used elsewhere to guard against "path traversal and symlink escapes").

### Finding Description
`discardChanges` builds the on-disk path to discard purely from repository-relative status data: [1](#0-0) 

and, in the permanent-delete fallback path: [2](#0-1) 

`file.path` comes from `git status`/working-directory change detection, which in turn reflects whatever the user has checked out from a cloned/fetched repository. Git allows committing symbolic links as ordinary tree entries. A malicious repository can commit a symlink, e.g. `evil-link -> ../../.ssh` (or any path escaping the working directory), which after clone/checkout appears in the working directory as an untracked/modified/added entry named `evil-link`. When the user selects "Discard changes" on that entry:

- `Path.resolve(repository.path, 'evil-link')` yields the symlink's own path inside the repo (this part is safe), **but**
- `shell.moveItemToTrash` and Node's `rm` operate on the path as given; if `evil-link` is itself the symlink, deleting the symlink is not directly harmful. However, the reachable variant is a **directory** symlink component: if the crafted repository contains a symlinked directory (e.g., `linkdir -> /home/user/Documents`) and a "file" entry reported by git status as `linkdir/newfile` (untracked file that git resolved by walking into the symlinked directory), `Path.join(repository.path, file.path)` / `Path.resolve` will produce a path that traverses through the attacker-controlled symlink component before reaching the final segment, and neither `rm` nor `moveItemToTrash` re-validates that the fully resolved (real) path is still rooted under `repository.path`.

This is architecturally identical to the ERC-6551 bug's core flaw: the code computes/consumes a path/address assuming it deterministically stays within a trusted domain (the repo working directory / the counterfactual TBA address), but an attacker-controlled artifact (a git symlink entry / a front-running mint) changes what that value actually resolves to at the time of use, and the code has no guard analogous to `resolveWithin`'s `realpath` comparison to catch the divergence at the point of consumption.

By contrast, the codebase already demonstrates the correct pattern is known and used elsewhere: [3](#0-2) 

and it is applied for Copilot conflict-resolution file writes: [4](#0-3) 

`discardChanges` does not apply the same `resolveWithin` guard before deleting/trashing.

### Impact Explanation
If reachable (see likelihood caveat below), this allows a crafted/cloned repository to cause GitHub Desktop to delete or move-to-trash a file/directory outside the repository, controlled by the attacker's choice of symlink target — matching the listed valid-impact category "file write or read outside the repo" / unwanted destructive file-system action driven by a cloned repository's content, without any local access, admin rights, or social engineering beyond the user opening/cloning the repo and clicking "Discard changes" on a file they see in the Changes list (a completely ordinary Desktop action).

### Likelihood Explanation
Medium-to-uncertain. The exploitability depends on exactly how `git status`/Desktop's change-detection layer reports paths for entries reached only through a symlinked directory, and whether `moveItemToTrash`/`rm` follow such directory symlinks on the target OS (this behavior is OS/Electron-`shell.trashItem`-dependent and could not be fully verified from the indexed source alone). What is verifiable directly from the code is the structural gap: `discardChanges` is the only file-deletion path in the store that does not route through `resolveWithin`-style validation, unlike the newer Copilot conflict-resolution write path, which was clearly hardened for exactly this symlink-escape scenario.

### Recommendation
Before calling `this.shell.moveItemToTrash(...)` or `rm(...)` in `discardChanges` (`app/src/lib/stores/git-store.ts:1558-1584`), resolve `file.path` (and `file.status.oldPath` for renames/copies) with the existing `resolveWithin(repository.path, file.path)` helper, refuse to operate (skip with a warning, mirroring the Copilot flow) when it returns `null`, and use the returned, verified-in-root path for the actual filesystem operation instead of `Path.resolve`/`Path.join`.

### Proof of Concept
1. Attacker publishes a repository containing a symlinked directory entry, e.g. `linkdir -> /Users/victim/Documents` (or a Windows junction on `__WIN32__`), and commits it.
2. Victim clones the repository in GitHub Desktop; on checkout the symlink is materialized as `linkdir` inside the working copy.
3. Victim creates or the checkout otherwise causes an entry that Desktop's change detection reports as `linkdir/<name>` in the Changes list (as an added/untracked file reachable by walking the symlink).
4. Victim selects that entry and clicks "Discard changes."
5. `discardChanges` computes `Path.resolve(repository.path, 'linkdir/<name>')` / `Path.join(...)` and passes it to `moveItemToTrash`/`rm` without confirming the resolved real path is still under `repository.path`, resulting in a filesystem operation against `/Users/victim/Documents/<name>` rather than a path constrained to the repository — the exact "resolved location diverges from the intended/verified location" pattern described in the source report, just manifesting as a filesystem path instead of a CREATE2 address.

(Note: full confirmation of how Desktop's status/change-detection layer names entries reached via a symlinked directory, and whether Electron's trash implementation follows such symlinks on each OS, would require running the app/tests, which is outside what the indexed source alone can confirm.)
