## #Analysis: ICS20/ERC20 Dest-Callback Isolated-Address Fund Freeze / Ack Double-Refund

### Title
Failed ERC20 conversion after successful ICS20 receive returns an Error Acknowledgement, permanently stranding minted/unescrowed coins in an unspendable isolated address while the source chain independently refunds the sender - ([File: x/erc20/ibc_middleware.go], [File: x/erc20/keeper/ibc_callbacks.go], [File: x/ibc/callbacks/keeper/keeper.go])

### Summary
This is the direct Cosmos EVM analog of the Scroll bug: a bridging transfer "succeeds" on one side (tokens are moved/minted to a receiver) while a subsequent step (an EVM-side conversion/call) fails, and the failure is reported back as if the transfer never happened - triggering a refund on the source chain without reversing the state change that already occurred on the destination chain.

### Finding Description
In `x/erc20/ibc_middleware.go`, `OnRecvPacket` first calls the underlying ICS20 transfer module's `OnRecvPacket` (which mints/unescrows the IBC coin to the receiver and commits this state change directly), and only afterwards calls `k.keeper.OnRecvPacket` to convert the coin to its ERC20 representation: [1](#0-0) 

Inside `x/erc20/keeper/ibc_callbacks.go`, if the receiver is not a module account and the token pair is a "native ERC20", the keeper attempts `ConvertCoinNativeERC20`. If this conversion fails (e.g. `MintingEnabled` check fails, or `SendEnabled=false` on the coin's denom), the function returns a **channeltypes.NewErrorAcknowledgement**: [2](#0-1) 

Because the underlying transfer's `OnRecvPacket` (which already unescrowed/minted the bank coin to the receiver) ran and committed *before* this later failure, turning the overall acknowledgement into an `ErrorAcknowledgement` does not undo that mint/unescrow. An `ErrorAcknowledgement` propagated back to the source chain will cause the source chain to run its own refund path (`OnAcknowledgementPacket`/timeout unescrow logic) and return the original sender's funds there - while the coin that was already credited on the destination chain remains, generally landing in an isolated, non-signable address (`types.GenerateIsolatedAddress`) used for the dest-callback flow, which has no private key and can only be moved onward via the ERC20 approve+call flow gated by `IBCReceivePacketCallback` in `x/ibc/callbacks/keeper/keeper.go`.

Test evidence directly confirms coins can become permanently trapped at the isolated address when the erc20 conversion step fails after the base transfer succeeded: [3](#0-2) 

The comment in the test itself acknowledges the exact failure mode: *"SendEnabled=false will cause the conversion of bank tokens to erc20 tokens to fail, but not send them back to escrow"*. [4](#0-3) 

Separately, `IBCReceivePacketCallback` (used for `dest_callback` memos) enforces that the isolated receiver's ERC20 balance is exactly zero after invoking the destination contract, specifically to prevent funds being "irretrievable" in the isolated address: [5](#0-4) 

However this guard only protects the ERC20-token path invoked explicitly through `dest_callback`; it does nothing for the ordinary ICS20 receive path in `x/erc20/keeper/ibc_callbacks.go`, where a bank-coin credit to a receiver (which can independently be an isolated/unspendable address, e.g. mistakenly or via `dest_callback` combined with a disabled/failing conversion) can be stranded while the acknowledgement is simultaneously downgraded to an error, causing the source chain to independently refund.

### Impact Explanation
This breaks the fundamental ICS20 1:1 escrow/mint invariant: value already credited to a receiver on the destination chain is not reversed, yet the source chain treats the packet as failed and refunds/un-escrows the same value to the sender. The net effect is a permanent, unrecoverable increase in total spendable+stranded value across the two chains for the transferred denom - an irreversible accounting corruption of user value that is unprivileged-user triggerable (a sender only needs to construct a transfer whose destination-side ERC20 conversion is set up to fail, e.g., by targeting a bank-`SendEnabled=false` denom or a `MintingEnabled` failure condition, or through the isolated-address callback flow). This matches the Critical "irreversible accounting corruption of spendable user value across ... IBC escrows" and "permanent freezing ... of user funds" impact categories.

### Likelihood Explanation
The trigger conditions (denom send-enabled toggled off, minting-disabled token pair, or a destination contract that does not fully drain its allowance) are reachable via ordinary, unprivileged IBC transfer messages with attacker-controlled memo/denom selection; no validator or relayer privilege is required, and the test suite itself demonstrates the trapped-balance condition occurring under normal test setup.

### Recommendation
The `OnRecvPacket`/`OnAcknowledgementPacket` erc20 conversion logic must not return an `ErrorAcknowledgement` after the underlying transfer's coin has already been committed to the receiver's account. Either (a) perform the ERC20 conversion and the underlying transfer atomically inside a single branched context that is only committed together, so a conversion failure can safely produce an `ErrorAcknowledgement` without side effects, or (b) never emit an `ErrorAcknowledgement` once the base transfer has committed - instead always leave the bank coin with the receiver (as already done in the `MintingEnabled` failure/no-op branches) so the acknowledgement, and any refund it triggers, correctly reflects the real state on both chains.

### Proof of Concept
1. Register an ERC20 token pair as `IsNativeERC20()` for denom `D`.
2. Sender on chain B sends an ICS20 transfer of `D` to a receiver address on the Cosmos EVM chain (either a normal address for which `MintingEnabled` will fail, or an isolated `dest_callback` address whose downstream conversion path is broken).
3. Toggle `SendEnabled(D) = false` (or otherwise make `ConvertCoinNativeERC20` fail) before the packet is relayed, per `evmd/tests/ibc/ibc_middleware_test.go:731-736`.
4. Relay the packet: `im.Module.OnRecvPacket` unescrows/mints `D` to the receiver (test confirms this at `ibc_middleware_test.go:784` `escrowedBal.IsZero()` and `ibc_middleware_test.go:807-808` `trappedBal == recvAmt`), then `k.keeper.OnRecvPacket` fails conversion and returns `channeltypes.NewErrorAcknowledgement`.
5. On chain B, the error acknowledgement is processed via the transfer module's standard ack-failure handling, refunding the original sender's escrowed/burned coins.
6. Result: sender is refunded on chain B while an equivalent, permanently-stranded balance of `D` sits in the receiver account on the Cosmos EVM chain - total supply-vs-escrow invariant is broken.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
