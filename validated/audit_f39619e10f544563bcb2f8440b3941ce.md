## Title
Duplicate/Repeated Signature Entries Inflate BEEFY Participation Threshold Without Deduplication - (File: `modules/consensus/beefy/verifier/src/lib.rs`)

## Summary
`verify_mmr_update_proof` (called from `verify_consensus`, which is reached via the unprivileged/unsigned BEEFY consensus-update path through `pallet_ismp::handle_unsigned`) computes the supermajority participation threshold purely from the raw length of the attacker-supplied signature array, with no deduplication of authority indices before that count is used, and no deduplication check anywhere in the authority-membership verification step either.

## Finding Description
`verify_mmr_update_proof` takes `signatures_length` directly from `mmr.signed_commitment.signatures.len()` and immediately passes it to `check_participation_threshold`: [1](#0-0) 

`check_participation_threshold` is a pure arithmetic check on the passed-in count, with no notion of authority identity: [2](#0-1) 

The loop that follows builds `authority_leaves`/`authority_indices` directly from `mmr.signed_commitment.signatures` without any uniqueness check on `sig.index`: [3](#0-2) 

Because signature recovery (`secp256k1_recover`) is deterministic, an attacker can take one legitimately-obtained authority signature and duplicate the `SignatureWithAuthorityIndex` entry (same `index`, same `signature`) multiple times inside `mmr.signed_commitment.signatures`. This inflates `signatures_length` used for the threshold check without adding any additional distinct authenticated signer. The subsequent `merkle_proof.verify(...)` call is fed the resulting `authority_indices`/`authority_leaves` vectors, which now contain repeated `(index, leaf)` pairs pointing at the *same* real leaf value in the authority set tree — there is no code in this function (or its call sites in `modules/ismp/clients/beefy/src/consensus.rs`) that rejects duplicate indices before or after the merkle-proof check.

The identical structural pattern exists in the EVM Solidity implementation, `EcdsaBeefy.verifyMmrUpdateProof`, which also derives `sigLen` from `relayProof.signedCommitment.votes.length` and never checks `vote.authorityIndex` uniqueness before calling `checkParticipationThreshold` or `MerkleMultiProof.VerifyProof`: [4](#0-3) 

I was not able to fully confirm from this codebase whether the external `rs_merkle::MerkleProof::verify` (and its Solidity counterpart `MerkleMultiProof.VerifyProof`) actually accept a multi-proof query containing duplicate `(index, leaf)` pairs and still return `true` — this is vendored/external crate logic not present in the indexed repository content, so its exact duplicate-index handling could not be directly inspected. This is the key remaining uncertainty: if the multi-proof libraries internally reject duplicate indices (e.g., by requiring strictly increasing/unique indices during the sort-and-pair reconstruction described in `docs/content/protocol/cryptography/merkle-trees/binary.mdx`), then the merkle-membership check would fail and the duplicated-signature attack would be caught at that stage even though the threshold count itself is still wrong in isolation. Regardless of that external-library behavior, the codebase itself provides **no explicit dedup guard on `sig.index`/`vote.authorityIndex`** at either the Rust or Solidity layer, which is the concrete, verifiable code gap.

## Impact Explanation
If the underlying merkle multi-proof verification does tolerate duplicate `(index, leaf)` entries (which is plausible for many multiproof reconstruction algorithms that key on the leaf's tree position and don't enforce array-level uniqueness), an attacker with access to even a minority of genuine BEEFY authority signatures could pad the signature list with repeats of those same signatures to artificially cross the 2/3+1 supermajority threshold. This would let a forged/insufficiently-signed consensus update be accepted as finalized, propagating an attacker-influenced MMR root and parachain header set into the trusted `ConsensusState`, which downstream unlocks acceptance of forged parachain state commitments (`state_id`, `state_root`, `overlay_root`) used for ISMP request/response/timeout proofs and thus asset movement.

## Likelihood Explanation
Unconfirmed without directly testing/exercising the external `rs_merkle`/`MerkleMultiProof` verification against a duplicate-index multiproof. If that library correctly rejects duplicate indices, this specific path is not exploitable in practice, and the missing dedup check is only a defense-in-depth gap. A definitive determination requires a focused unit test (as suggested by the question's "Fast validation" note) submitting a proof with a repeated authority index/signature and asserting whether `check_participation_threshold`/`merkle_proof.verify` combination is bypassed.

## Recommendation
Regardless of the external library's actual behavior, add an explicit uniqueness check on `sig.index` (Rust) and `vote.authorityIndex` (Solidity) before computing `signatures_length`/`sigLen`, e.g., collect indices into a `BTreeSet`/dedup and use the deduplicated count for both the participation threshold and the merkle multi-proof call. This removes the dependency on external multiproof libraries' undocumented duplicate-handling behavior for a critical security invariant.

## Proof of Concept
A conclusive PoC requires exercising the actual `rs_merkle`/`MerkleMultiProof` verify functions with a duplicated `(index, leaf)` entry to determine whether they accept or reject it — this could not be completed within the scope of this review since those verify implementations are external/vendored and not available in the indexed codebase content. Recommended validation, matching the question's own "Fast validation" guidance: construct a `MmrProof` in `modules/consensus/beefy/verifier/src/test.rs` with a real authority signature duplicated twice in `signed_commitment.signatures` (same `index`, same `signature`) such that raw `len()` clears `check_participation_threshold` while genuinely distinct signers do not, and assert whether `verify_mmr_update_proof` returns `Ok` or `Err(InvalidAuthoritiesProof)`.
