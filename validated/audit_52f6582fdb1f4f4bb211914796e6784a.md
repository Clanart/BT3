### Title
`SignableTransaction::new` omits the OP_RETURN output from its fee/vsize accounting, underpaying the fee so the transaction may be unrelayable — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The bug class of the reference report is an accounting/invariant check that fails to include one category of funds, so the safety check passes while obligations are understated. In `SignableTransaction::new`, the vsize used to compute `needed_fee` is derived from a template transaction that includes only the payment outputs — the OP_RETURN data output (up to 80 bytes of attacker-influenced data plus output overhead) is appended to `tx_outs` afterwards but is never added to the weight template. The resulting transaction therefore pays `fee_per_vbyte * vbytes` where `vbytes` excludes a real, consensus-counted output.

### Finding Description
`calculate_weight_vbytes` builds a template `Transaction` whose `output` vector is populated **only from `payments`** (lines 85–93, plus optional change at lines 95–99). In `new()`:

- The OP_RETURN output is pushed to `tx_outs` at lines 194–202 **before** the weight call, but
- line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — `payments`, not `tx_outs` — so the OP_RETURN output (≈ 11-byte output base + ~83-byte script for a full 80-byte payload, all base/non-witness weight) is missing from `vbytes`.
- `needed_fee = fee_per_vbyte * vbytes` (line 206) is thus undersized by roughly `fee_per_vbyte * ~94` vbytes for max-size data.
- The minimum-fee check at line 211 and the `NotEnoughFunds` check at line 215 are also evaluated against this understated vsize/fee, and the change branch at lines 225–234 inherits the same omission (`fee_with_change` still excludes the OP_RETURN output).
- `fee()` (lines 138–141) and the consensus rule define the real fee as `sum(inputs) − sum(outputs)`; the created transaction commits `needed_fee`, so its *effective* feerate is strictly below the requested `fee_per_vbyte`.

An unprivileged party causes this purely through public input: the `data` field is derived from an arbitrary `InInstruction`/message embedded in a deposit transaction they send (see `get_outputs`/`extract_serai_data` usage in `processor/src/networks/bitcoin.rs:730-734`). When the protocol later builds a `SignableTransaction` carrying that OP_RETURN data at/near the minimum feerate, the effective feerate falls below `DEFAULT_MIN_RELAY_TX_FEE` and the signed transaction is rejected by peer mempool policy.

### Impact Explanation
The protocol produces a fully signed transaction that standard Bitcoin nodes will not relay/confirm because its true feerate is below the requested rate (and potentially below the minimum relay feerate, which the code explicitly tries to enforce at line 211). The accounting check that was supposed to guarantee a payable fee (`NotEnoughFunds`, `TooLowFee`) can be circumvented exactly like `fundsSafu` in the reference: the check passes while a real obligation (the bytes of the OP_RETURN output) is unaccounted. Consequence: a withdrawal/forwarding plan yields a transaction that cannot enter the mempool — funds remain spendable but the plan fails, a denial of service on the affected payment, and the discrepancy is attributable to attacker-supplied data bytes. This is an incorrect transaction-building invariant reachable from public inputs; Medium severity.

### Likelihood Explanation
Requires the constructed transaction to carry an OP_RETURN output and the selected `fee_per_vbyte` to be at or near the minimum such that the ~94-vbyte omission drops the effective rate below relay policy, or for the signed TX to otherwise underbid the intended rate. The trigger input (the data bytes) is fully attacker-controlled via a deposit's embedded instruction, so crafting max-size data is trivial whenever such a transaction is planned.

### Recommendation
Include the OP_RETURN output (and any other outputs actually committed) in the template passed to `calculate_weight_vbytes` — e.g., build the weight template from `tx_outs`/`tx_ins` after all outputs are determined, rather than from `payments` alone — so `needed_fee`, the `TooLowFee` check, the `NotEnoughFunds` check, and the change-amount computation all reflect the transaction's true vsize.

### Proof of Concept
1. Attacker submits a deposit/transfer whose embedded instruction yields `data` of 80 bytes (allowed by the `TooMuchData` check at lines 171–173).
2. The wallet calls `SignableTransaction::new(inputs, payments, change, Some(data_80b), fee_per_vbyte)` with `fee_per_vbyte` at the minimum relay rate.
3. `calculate_weight_vbytes` returns `vbytes` excluding the ~94-byte OP_RETURN output; `needed_fee` passes the line-211 minimum check and the line-215 funds check.
4. `multisig`/`sign`/`complete` produce a transaction whose real size is `vbytes + ~94`, so its effective feerate is `needed_fee / (vbytes + 94) < fee_per_vbyte`, below `DEFAULT_MIN_RELAY_TX_FEE` — the node rejects it (`mempool min fee not met`), and the plan cannot complete despite all accounting checks having passed.
