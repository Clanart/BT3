### Title
Missing non-negative-size validation before `memcpy` in `EpsCopyInputStream::ReadPackedFixed` - (File: `src/google/protobuf/parse_context.h`)

### Summary
FontForge's `readcfftopdict` bug is a classic "size not validated as non-negative before `memcpy`" flaw: a signed length derived from attacker-controlled font data is used directly as a `memcpy` size without checking `size > 0`, letting a negative/garbage size be reinterpreted as an enormous unsigned copy length. The closest structural analog in this protobuf checkout is `EpsCopyInputStream::ReadPackedFixed()` [1](#0-0) , which is fed a signed `int size` obtained from `ReadSize(&ptr)` — a value parsed directly from the wire's varint length prefix of a packed fixed-width field — and performs pointer/size arithmetic and `std::memcpy` calls without first asserting `size >= 0`.

### Finding Description
`ReadPackedFixed<T>` is reached for every packed `fixed32/fixed64/sfixed32/sfixed64/float/double` field via two call sites that decode the length straight from the wire:
- `FixedParser<T>` in `src/google/protobuf/parse_context.cc:697-703`, which does `int size = ReadSize(&ptr); return ctx->ReadPackedFixed(ptr, arena, size, ...);` [2](#0-1) 
- `TcParser::MpPackedFixed` in `src/google/protobuf/generated_message_tctable_lite.cc:2191-2223`, which does `int size = ReadSize(&ptr);` then `ctx->ReadPackedFixed(ptr, arena, size, &field)` [3](#0-2) 

Inside `ReadPackedFixed`, the `size` parameter (a signed `int` taken from the wire's length-delimited varint) is used to compute `num = size / sizeof(T)` and `block_size = num * sizeof(T)`, then:
```
auto dst = out->AddNAlreadyReserved(num);
std::memcpy(dst, ptr, block_size);
``` [4](#0-3) 

There is no explicit check that `size >= 0` before this arithmetic. Because the length is read as a wire varint and narrowed into a signed 32-bit `int` (`ReadSize`), a crafted length prefix with the top bit set decodes to a negative `int`. With a negative `size`:
- The `while (size > nbytes)` guard is skipped (negative `size` is never greater than a non-negative `nbytes`) [5](#0-4) .
- `num = size / sizeof(T)` truncates to a small negative integer (e.g., `-6 / 4 == -1`), so the `if (num == 0)` early-exit does not trigger [6](#0-5) .
- `block_size = num * sizeof(T)` becomes negative and is passed as the third argument to `std::memcpy`, which takes an unsigned `size_t`; a negative `int` widened to `size_t` becomes an enormous unsigned value (~2^64), producing a massive out-of-bounds copy [7](#0-6) .
- `AddNAlreadyReserved(num)` is also called with a negative count, which can corrupt the `RepeatedField`'s internal `current_size_` bookkeeping before the `memcpy` even executes.

This is exactly the invariant FontForge violated: a length value taken from untrusted input is not checked to be `>= 0`/positive before being handed to `memcpy`, and a negative interpretation silently becomes an oversized unsigned copy length.

### Impact Explanation
A successful trigger causes `memcpy` to read (and the destination buffer to be written) with an attacker-influenced, effectively unbounded length, leading to a crash (segmentation fault / heap corruption) when parsing a bounded, crafted binary Protobuf message through the public `ParseFrom*` API — a denial-of-service against any consuming application that parses untrusted Protobuf bytes, matching the CVE's classification (local, DoS via crafted input, no special privileges, CVSS impact confined to availability).

### Likelihood Explanation
Reaching this path only requires a client to send a message with a packed fixed-width repeated field whose length-delimited prefix is crafted to decode as a negative `int` (top bit set in the varint) followed by a payload; this is reachable through the standard binary wire-format parse entry points (`ParseFromString`/`MergeFrom`) that dispatch into `TcParser::MpPackedFixed` / `FixedParser`, so no special schema, plugin, or privileged access is needed — only a bounded, well-formed-looking wire payload.

### Recommendation
Add an explicit `if (size < 0) return nullptr;` (or validate before dividing) at the top of `EpsCopyInputStream::ReadPackedFixed` in `src/google/protobuf/parse_context.h`, mirroring the divisibility/size check already present in the legacy `WireFormatLite::ReadPackedFixedSizePrimitive` path (`if (new_bytes != length) return false;` in `wire_format_lite.h:1116-1160`) [8](#0-7) , so negative/garbage sizes are rejected before any arithmetic or `memcpy` occurs.

### Proof of Concept
I could not run this to completion within the available tool budget/iterations, so this is a **traced-but-unverified** reproduction sketch, not a confirmed executed test:
1. Craft a message containing a packed `fixed32` (or `fixed64`) field whose length-delimited varint prefix encodes a value whose low 32 bits, when narrowed to a signed `int` by `ReadSize`, become negative (e.g., a 5-byte varint encoding `0xFFFFFFFA` = -6 as `int32`), followed by a few bytes of payload — analogous to the existing test pattern in `java/core/src/test/java/com/google/protobuf/ArrayDecodersTest.java` (`packedSizeBytesNoTag(-1)` cases) [9](#0-8) , but targeting the C++ `EpsCopyInputStream::ReadPackedFixed` path instead of the Java `ArrayDecoders` (which is already shown, via its own negative-size tests, to explicitly guard against this — evidence that this class of bug is a recognized concern in this codebase, but the C++ fast-table path shown above lacks the equivalent explicit guard in the reviewed lines).
2. Feed the bytes to `SomeMessageWithPackedFixed32Field::ParseFromArray()`.
3. Expected (if unguarded): crash/ASAN violation inside `std::memcpy` in `ReadPackedFixed` due to the huge unsigned `block_size`; expected (if properly guarded): `ParseFromArray` returns `false`/throws `InvalidProtocolBufferException`-equivalent.

Because I was not able to execute this PoC or inspect `ReadSize`'s exact implementation (varint decode bounds) before running out of tool iterations, treat the negative-size reachability as strongly suggested by the code structure shown, but not empirically confirmed — a background engineer should compile and run this reproduction with ASan to confirm before treating it as a verified finding.
