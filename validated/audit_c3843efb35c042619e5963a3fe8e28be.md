### Title
`Scanner::scan_block` returns coinbase-locked outputs as immediately spendable `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report's bug class is "unvalidated/stale external data consumed without freshness or completeness checks" (Chainlink `latestAnswer` returning incomplete-round data). The analog in Serai's in-scope code is `Scanner::scan_block` in `networks/bitcoin/src/wallet/mod.rs` (lines 221–227), which scans `block.txdata` including `txdata[0]` — the coinbase transaction — and emits `ReceivedOutput`s for it with no maturity indicator or check. Coinbase outputs are unspendable for 100 blocks under Bitcoin consensus, so the scanner reports funds as received which cannot actually be spent.

### Finding Description
`Scanner::scan_transaction` iterates every output of a transaction and produces a `ReceivedOutput { offset, output, outpoint }` whenever `output.script_pubkey` matches a registered script (lines 199–213). `scan_block` (lines 221–227) calls it over `block.txdata` including index 0, the coinbase:

```rust
for tx in &block.txdata {
  res.extend(self.scan_transaction(tx));
}
```

The `ReceivedOutput` type (lines 90–97) carries no maturity flag, block height, or coinbase marker — `offset`, `output`, `outpoint` only. Nothing in the returned data distinguishes an immature coinbase output from a normal spendable output, so a downstream consumer has no library-provided way to detect the condition short of re-fetching the block and re-identifying `txdata[0]` — precisely analogous to an oracle response lacking `answeredInRound`/`timestamp` metadata that would let the consumer detect stale/incomplete data.

The doc comment on `scan_block` (lines 216–220) acknowledges the issue ("This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed"), but the invariant is not enforced: any caller that uses `scan_block` (the natural API for block-wise scanning) receives unspendable outputs indistinguishable from spendable ones. Notably, Serai's own processor had to special-case this hazard by manually slicing `block.txdata[1 ..]` in `processor/src/networks/bitcoin.rs` (`get_outputs`, line 691), confirming the footgun is real rather than theoretical.

Reachability for an unprivileged party: any Bitcoin miner can set the coinbase output's `script_pubkey` to Serai's P2TR vault address (the script is public once known, and offsets can be derived since they are hash-to-scalar or zero). The coinbase is a valid transaction the attacker "sends" per the reachability model. The scanner then reports a `ReceivedOutput` that cannot be spent until maturity.

### Impact Explanation
Funds are reported received that are not spendable — an explicitly accepted impact class. Downstream accounting credits an output that any `SignableTransaction`/spend built on top of will fail consensus validation (`bad-txns-premature-spend-of-coinbase`). If the credited outputs drive a forward/batch signing flow, the threshold protocol can be induced to produce signatures for a transaction that can never confirm at that height, mis-reporting vault balances and potentially stalling the rotation/batch pipeline while the invalid input is included.

### Likelihood Explanation
Medium-low. It requires a miner to direct a coinbase payment at the scanned script (or, in practice, any solo miner / pool operator interacting with the address), and a consumer using `scan_block` rather than the maturity-aware `txdata[1 ..]` slicing. No threshold compromise or privileged access is needed — the coinbase transaction is ordinary public input to the scanner.

### Recommendation
Have `scan_block` skip `block.txdata[0]` (coinbases are always index 0), or carry maturity metadata in `ReceivedOutput` (e.g., a `immature: bool` / `kind` field set when the source tx is a coinbase) so callers can filter without reconstructing block context. Alternatively expose `scan_block` only over non-coinbase transactions and document that coinbase detection (`tx.is_coinbase()`) is enforced internally.

### Proof of Concept
```rust
// A miner crafts a block whose coinbase pays to the vault's p2tr script
let script = p2tr_script_buf(vault_key).unwrap();
let coinbase = Transaction {
  input: vec![TxIn { previous_output: OutPoint::null(), ..Default::default() }],
  output: vec![TxOut { value: Amount::from_sat(50_0000_0000), script_pubkey: script }],
  ..Default::default()
};
let block = Block { header: /* .. */, txdata: vec![coinbase, /* user txs */] };

// scan_block reports the coinbase output as received
let outputs = scanner.scan_block(&block);
assert_eq!(outputs[0].outpoint(), &OutPoint::new(block.txdata[0].compute_txid(), 0));
// outputs[0] is indistinguishable from a spendable output, yet spending it
// within 100 blocks fails consensus validation.
```

The existing test in `networks/bitcoin/tests/wallet.rs` (`send_and_get_output`, lines 54–70) already demonstrates this: it mines 100 blocks explicitly because the scanned coinbase output is immature, then asserts `scanner.scan_block(&block)` returns it.
