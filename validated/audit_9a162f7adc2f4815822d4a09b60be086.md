## Finding [1](#0-0) 

### Title
Arbitrary file read via symlinked conflicted path in `getResolutionDiff` (Copilot conflict resolution "Changes" preview) - (File: app/src/lib/git/diff.ts)

### Summary
`getResolutionDiff()` reads the on-disk content of a conflicted file with a plain `readFile(Path.join(repository.path, filePath), 'utf8')` call, with no symlink or path-containment check. [2](#0-1)  This is the same class of bug as the HackerOne report (symlinks extracted/tracked by an untrusted source are followed on read, escaping the intended root), except here the "archive" is a git repository the attacker controls, and the escape happens when Desktop shows the Copilot conflict-resolution diff/preview.

### Finding Description
Desktop's newer Copilot-assisted merge-conflict feature added a dedicated guard, `resolveWithin()`, specifically to stop symlink/path-traversal escapes when reading conflicted-file contents before sending them to Copilot: [3](#0-2) 
`resolveWithin` uses `fs.realpath` to canonicalize both the root and the resolved path and rejects anything that doesn't stay under the real root, explicitly to defeat symlink escapes: [4](#0-3) 

However, the sibling code path that renders the **preview diff** for the same conflicted files in the "Changes" tab of the Copilot conflicts dialog — `getResolutionDiff()` — was not updated with this guard. It joins `repository.path` with the attacker-controlled `filePath` (taken directly from git's unmerged file list) and reads it with plain `readFile`, which follows symlinks: [1](#0-0) 

This function is invoked from `CopilotConflictsChanges.loadDiffForFile()` for every conflicted file whenever the user opens the "Changes" tab of the conflict-resolution dialog during a merge/rebase/cherry-pick, using `file.path` straight from the working directory status: [5](#0-4) 

The resulting `baseContent` is then written to a temp file, diffed, and the raw content is passed back to the UI as `fileContents`/`oldContents`, and rendered in the diff viewer via `SeamlessDiffSwitcher`: [6](#0-5) 

**Attacker-controlled/corrupted value:** the `filePath` under a repository path can correspond to an on-disk entry that is a symlink pointing outside the repository (e.g. checked out as part of a type-change conflict where one side of the merge is a symlink and the other a regular file — a legitimate git conflict scenario). Because `readFile` in Node follows symlinks and `getResolutionDiff` performs no `lstat`/`realpath` containment check (unlike `resolveWithin`), the "on-disk" content read is actually the contents of whatever the symlink points to, anywhere on the filesystem the Desktop process can read (e.g. `~/.ssh/id_rsa`, `~/.aws/credentials`, `%APPDATA%` files).

### Impact Explanation
An attacker who gets a victim to clone/fetch/merge a crafted branch containing a symlink-vs-file conflict can cause Desktop to read and display the contents of an arbitrary file on the victim's machine (any file readable by the Desktop process) inside the Copilot conflict "Changes" diff preview. This is a local arbitrary file read triggered purely by opening/merging an attacker-supplied repository — no local/physical access or pre-existing malware needed on the victim side, matching the report's "arbitrary file read via unsanitized symlink" bug class.

### Likelihood Explanation
Likelihood is moderate: it requires the repository to trigger a merge/rebase/cherry-pick conflict where the conflicting path resolves to (or is) a symlink, and requires the victim to open the Copilot conflicts dialog's "Changes" tab (which is a normal step in Desktop's advertised Copilot-assisted conflict resolution flow, and Copilot resolution is opt-in/"always use" configurable). The existence of a purpose-built guard (`resolveWithin`) for the *exact same read operation* elsewhere in the same feature, but missing here, indicates this is a real gap rather than a defense-in-depth nicety.

### Recommendation
Route the base-content read in `getResolutionDiff` (and any other direct `Path.join(repository.path, filePath)` + `readFile` on conflicted-file paths, e.g. `getWorkingDirectoryImage`) through the existing `resolveWithin()` helper from `app/src/lib/path.ts`, rejecting or safely handling paths that resolve outside the repository root, consistent with the guard already applied in `buildConflictContext`.

### Proof of Concept
1. Attacker prepares a repo with two branches that conflict on path `notes.txt`: on branch A, `notes.txt` is a regular file; on branch B, `notes.txt` is a symlink to `/Users/victim/.ssh/id_rsa` (or `%USERPROFILE%\.aws\credentials`).
2. Victim clones the repo in GitHub Desktop and merges/rebases branch B into branch A (or vice versa), producing a type-change conflict where the working tree entry for `notes.txt` remains a symlink.
3. Victim opens the Copilot conflict resolution dialog and selects the "Changes" tab to preview the resolution diff.
4. `CopilotConflictsChanges.loadDiffForFile` calls `getResolutionDiff(repository, 'notes.txt', ...)`, which executes `readFile(Path.join(repository.path, 'notes.txt'), 'utf8')` — following the symlink and reading the victim's private key/credentials file — and renders that content in the diff pane.
