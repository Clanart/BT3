### Title
Participant index 0 accepted by FROST signing-set validation, zeroing all honest Lagrange coefficients - (File: crypto/dkg/src/lib.rs, crypto/frost/src/sign.rs)

### Summary
The bug class of the external report — two analogous quantities validated with inconsistent strictness — exists in Serai's FROST code. The valid participant domain throughout the codebase is `1..=n` (`ThresholdParams::all_participant_indexes` yields `1..n`, and `ThresholdKeys::new` builds the group key over participants `1..=t`). Yet `ThresholdParams::new` at `crypto/dkg/src/lib.rs:166-178` only checks `i.0 > n` and never rejects `Participant(0)`, and `AlgorithmSignMachine::sign` at `crypto/frost/src/sign.rs:290-310` enforces only an upper bound (`included[last] > n`) plus duplicate checks — never rejecting index `0`. A preprocess map keyed by `Participant(0)` therefore passes all validation.

### Finding Description
In `crypto/dkg/src/lib.rs:174`, `ThresholdParams::new` validates `i` with only `if i.0 > n { Err(InvalidParticipant) }`, omitting the symmetric lower-bound check (`i.0 == 0`), despite `all_participant_indexes` (`crypto/dkg/src/lib.rs:195-197`) enumerating strictly `1..=n`. In `crypto/frost/src/sign.rs:302`, `sign` checks only `included[included.len() - 1] > n` after sorting — an asymmetric check exactly mirroring the OHM-vs-reserve inconsistency: one bound enforced (upper), the analogous bound (lower) skipped.

When `Participant(0)` is in `included`, `ThresholdView` interpolation (`self.params.keys.view(included)`) computes Lagrange coefficients evaluated at x = 0. The coefficient of participant `0` is `∏ x_j / (x_j - 0) = 1`, while every honest participant's coefficient contains the factor `(0 - x_0)/(x_i - x_0) = 0`, making all honest λ_i = 0. The aggregate signature thus depends solely on the participant-0 share, whose verification share interpolates to the group key itself — unforgeable without the group secret, so `complete` fails and blames index 0, but the session is destroyed and honest signers have already consumed their preprocesses (burned one-time nonces, `crypto/frost/src/sign.rs:83-92`).

### Impact Explanation
An attacker who can register a preprocess under `Participant(0)` deterministically aborts every signing session they join, forces honest participants to discard cached one-time preprocesses, and evades blame in protocols that only penalize indexes `1..=n`. If `ThresholdView`'s scalar offset is applied to `included[0]` (per the documented offset behavior), the offset lands on the phantom index instead of an honest signer, corrupting view semantics. This is a protocol-level liveness break analogous to the report's `getCurrentPrice` revert.

### Likelihood Explanation
Reachable wherever preprocess/share `HashMap<Participant, _>` keys are derived from peer-supplied indexes without an external `>= 1` check — `sign` and `complete` (`crypto/frost/src/sign.rs:447-460`, which iterates `shares` against `view.included()`) trust map keys entirely. Requires a participant able to inject index-0 entries; an integrator that filters inputs would mitigate it, but the library itself documents no such precondition.

### Recommendation
Enforce the full domain `1 <= i <= n` symmetrically: reject `i.0 == 0` in `ThresholdParams::new` (`crypto/dkg/src/lib.rs:174`) and reject `included[0] == Participant(0)` (i.e., check `u16::from(included[0]) == 0`) in `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:302`) and equivalently in `complete` before interpolation.
