### Title
Unsigned, unauthenticated OP_RETURN payer attribution lets an attacker credit their own self-funded withdrawal to an arbitrary operator - ([File: core/src/task/payout_checker.rs])

### Summary
The payout OP_RETURN output that names the "fronting" operator is never covered by the withdrawing user's Schnorr signature and is never checked against who actually supplied the funding inputs of the payout transaction. Because the payout tx's user-signed input/output use `SIGHASH_SINGLE|ANYONECANPAY`, anyone (including the withdrawing user acting alone) can complete, fund, and broadcast the payout transaction while writing an arbitrary operator's x-only pubkey into the OP_RETURN. `PayoutCheckerTask::run_once` then blindly attributes the payout to that operator and drives it through `handle_finalized_payout` toward a kickoff/reimburse cycle for a withdrawal it never funded.

### Finding Description
The broken binding: `withdrawals.payout_payer_operator_xonly_pk == operator whose capital funded the payout tx's inputs`. In reality, `payout_payer_operator_xonly_pk` is set to `operator whose xonly_pk happens to appear in the payout tx's OP_RETURN output`, with no check on who paid.

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout tx with input 0 = the Citrea-committed withdrawal UTXO (signed by the withdrawing user with `taproot::Signature` whose sighash type must be `SinglePlusAnyoneCanPay`, verified at `core/src/operator.rs:630-637`), output 0 = the user's payout, and output 2 = an **unsigned** OP_RETURN carrying `operator_xonly_pk`.
- Because the user signature uses `SIGHASH_SINGLE|ANYONECANPAY`, it commits only to input 0 and output 0. Any party can append additional funding inputs (as `Operator::withdraw` itself does via `fund_raw_transaction` with `add_inputs: true`, `core/src/operator.rs:652-674`) and can freely choose the OP_RETURN bytes — nothing about `operator_xonly_pk` is bound by any signature.
- The withdrawing user is not privileged: an attacker can call Citrea's `withdraw` themselves, register their own dust UTXO (`in_outpoint`) plus a `SinglePlusAnyoneCanPay` signature over their own payout output, complete/fund the transaction entirely with their own coins, and set the OP_RETURN to operator O's `xonly_pk`.
- On the verifier side, `update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) parses this OP_RETURN with no re-derivation of who funded the inputs, and stores `operator_xonly_pk` into `withdrawals.payout_payer_operator_xonly_pk` (`core/src/database/schema.sql:276`).
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) queries `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` (`core/src/database/verifier.rs:282-313`), finds the attacker-forged payout attributed to O, and unconditionally calls `self.operator.handle_finalized_payout(...)` (`core/src/operator.rs:839-916`), which allocates a kickoff connector and signs/queues a kickoff tx for O, then `mark_payout_handled` commits O to the reimbursement cycle.
- The only cross-check that exists, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1914`), merely checks that the OP_RETURN pubkey equals `kickoff_data.operator_xonly_pk` and that the committed payout blockhash matches — it is a self-consistency check on the same unauthenticated field, not a check against actual fund source. The bridge circuit (`bridge-circuit-host/src/structs.rs:482-516`) likewise parses the OP_RETURN pubkey directly with no signature or funding-source verification.

### Impact Explanation
Operator O, who never broadcast or funded any payout transaction for this withdrawal, is driven by its own automation into signing/broadcasting a kickoff transaction and (absent any verifier flag, since the malicious-kickoff check only verifies self-consistency of the same forged OP_RETURN field) eventually receives the Reimburse output — vault BTC paid to O — for capital O never fronted. This matches "Critical: an operator reimbursed for a payout it never funded." The attack is repeatable per withdrawal (the attacker just needs to be the withdrawing party on Citrea, which is within an unprivileged attacker's granted capabilities) and can be aimed at any active operator whose x-only pubkey is public.

### Likelihood Explanation
No privileged role, key compromise, or majority hashrate is required. The attacker only needs to: (1) call Citrea's `withdraw` for a withdrawal they legitimately own, (2) sign the payout output with `SinglePlusAnyoneCanPay` (a capability explicitly granted to the attacker per the threat model), (3) fund/complete/broadcast the payout transaction themselves, and (4) write a targeted operator's known x-only pubkey into the OP_RETURN output instead of their own. All operator x-only pubkeys are public protocol parameters. This requires no cooperation from operator O and no chain-reorg or race condition — it is deterministic and repeatable for every future withdrawal.

### Recommendation
Bind the OP_RETURN operator attribution cryptographically to the entity that actually fronts the payout, e.g. by having the operator co-sign (or otherwise authenticate) the OP_RETURN output as part of the sighash it commits to, or by requiring the operator's funding inputs (as recorded on-chain) to be independently verified as belonging to that operator's known UTXO set before `update_finalized_payouts`/`PayoutCheckerTask` attribute a payout to it. At minimum, `is_kickoff_malicious` and `PayoutCheckerTask` should validate that the operator claiming reimbursement actually supplied the transaction's funding inputs (e.g., by checking that the additional inputs beyond the withdrawal UTXO are spends from that operator's registered wallet/round outputs), not merely that the OP_RETURN is internally consistent.
