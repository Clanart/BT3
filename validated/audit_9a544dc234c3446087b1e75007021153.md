## Title
Order-based (not location-based) hunk matching in `reassembleResolvedFile` lets an attacker-crafted merge input silently delete or corrupt unrelated conflict regions when they are applied and committed - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's "Resolve with Copilot" feature parses a conflicted file into an ordered list of conflict hunks (`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts`), sends them to an AI model, and then reassembles the final file by splicing the model's per-hunk resolutions back into the original on-disk content — matched purely **by array index/order**, not by content, hash, or location identifier. [1](#0-0) 

### Finding Description
`reassembleResolvedFile` walks the raw file line-by-line, and for each well-formed `<<<<<<<`/`=======`/`>>>>>>>` block it splices in `hunkResolutions[hunkIndex]`, incrementing `hunkIndex` for every block found — regardless of whether that resolution actually corresponds to that hunk's content: [2](#0-1) 

Critically, if `hunkIndex` reaches or exceeds `hunkResolutions.length` for a given conflict block (e.g., the model returns fewer hunk resolutions than the number of conflict blocks actually present in the file), the code silently emits **nothing** for that block — the conflict markers are stripped and the block's content vanishes entirely, with no error or warning: [3](#0-2) 

Because matching is purely positional, any mismatch between the number/order of conflict blocks detected by `extractConflictHunks` (used to build the prompt) and the number of hunks the model returns in its JSON response causes every subsequent hunk in the file to be misaligned — hunk 3's model output gets spliced into hunk 2's location, and so on, all without any content-equality check. A repository author (attacker) who crafts a file with borderline/ambiguous conflict-marker sequences — e.g. an extra `<<<<<<<`-looking line inside content, or nested/nearly-malformed markers that `extractConflictHunks`'s malformed-hunk skip logic (`hunkEnd === -1` → skip) treats differently than `reassembleResolvedFile`'s own malformed-block detection — can make the two hunk-parsers disagree on hunk count for the same file, since they are two independently written parsers with only partially overlapping heuristics (`extractConflictHunks` at `app/src/lib/copilot-conflict-context.ts:179-279` vs. the reassembly parser at `app/src/lib/copilot-conflict-resolution.ts:549-599`).

The final file produced from this mismatch is used both as the diff-preview content the user sees (`getResolutionDiff`, `app/src/lib/git/diff.ts:447`) and, on "Continue Merge", is written directly to disk and staged: [4](#0-3) 

### Impact Explanation
This breaks the invariant that "what the user reviews in the Copilot conflict-resolution diff is exactly what gets committed and pushed." Because the diff the user reviews is generated from `resolution.resolvedContent` — which is already the (potentially corrupted) reassembled output — a misalignment causes the wrong resolved text to be silently substituted into unrelated code regions, or an entire conflict region's content to be silently deleted (replaced with nothing) without any conflict markers remaining to flag the loss. This can silently corrupt what a user commits and pushes in a repository controlled/influenced by an untrusted collaborator or upstream branch that is merged in, satisfying the "silent corruption of what the user commits or pushes" impact category. The user has no separate ground truth to detect the mismatch since the diff itself is computed post-corruption.

### Likelihood Explanation
Exploitation requires: (1) a merge/rebase/cherry-pick against attacker-influenced content containing multiple conflict hunks with carefully crafted marker-adjacent lines designed to make `extractConflictHunks`'s heuristics diverge from `reassembleResolvedFile`'s heuristics on hunk count, and (2) the user invoking the optional "Resolve with Copilot" AI feature and clicking "Continue Merge" without manually reviewing every resulting file byte-for-byte. This is a non-trivial but plausible scenario: it needs no local access, admin rights, or leaked credentials — only that the user opens Desktop's AI merge-conflict assistant on a repository/branch that the attacker can influence (a common workflow for external contributions). Likelihood is moderate: it depends on crafting specific marker-adjacent inputs and on the model's hunk-count output actually diverging, which I could not fully verify from static code review alone (the model's actual JSON hunk count vs. detected hunk count divergence would need to be tested against the two parser implementations directly).

### Recommendation
Match hunk resolutions to conflict blocks by content/identity (e.g., include a stable per-hunk index or hash of `oursContent`/`theirsContent` in the prompt and validate it in the response) rather than by pure array order. Additionally, `reassembleResolvedFile` should hard-fail (throw, not silently drop content) when `hunkIndex >= hunkResolutions.length`, and the two hunk-parsing implementations (`extractConflictHunks` and the reassembly walker) should share a single canonical parser so their notions of "how many hunks exist" can never diverge.

### Proof of Concept
Not independently executable from static review alone — the exploit path is contingent on the actual Copilot model's hunk-count output diverging from `extractConflictHunks`'s hunk count for a crafted marker sequence, which requires live testing against the SDK/model integration in `app-store.ts`'s `_resolveConflictsWithCopilot`/`_applyCopilotConflictResolutions` flow. This should be validated via a Devin session or manual testing: construct a conflicted file with 2+ hunks plus a borderline malformed marker sequence, run it through both `extractConflictHunks` and `reassembleResolvedFile` with a controlled/mocked resolution array shorter than the actual hunk count, and confirm content silently disappears from the final written file as shown in the code paths cited above.
