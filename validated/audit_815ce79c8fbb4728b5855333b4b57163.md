## Title
`priority_fee` in new v1 transaction message format is unbounded and independent of `compute_unit_limit`, breaking the price = fee/CU invariant enforced everywhere else - (File: `runtime-transaction/src/transaction_meta.rs`)

### Summary
For legacy/v0 transactions, the prioritization fee is *derived* from `compute_unit_price * compute_unit_limit` and is always clamped so that `compute_unit_limit <= MAX_COMPUTE_UNIT_LIMIT` before the fee is computed via `get_prioritization_fee` [1](#0-0) . For the new `v1` message format, however, `priority_fee` is a raw, user-supplied field on `solana_message::v1::TransactionConfig` that is passed straight through with **no upper bound, no relationship to `compute_unit_limit`, and no relationship to actual work performed**, unlike every other field in the same struct (`heap_size` is range/alignment-checked, `compute_unit_limit` and `loaded_accounts_data_size_limit` are `.min()`-clamped) [2](#0-1) .

### Finding Description
`VersionedTransactionConfiguration::try_into_config` sanitizes the v1 `TransactionConfig` fields:

```rust
Self::V1(transaction_configuration) => {
    if !(MIN_HEAP_FRAME_BYTES..=MAX_HEAP_FRAME_BYTES)
        .contains(&transaction_configuration.updated_heap_bytes)
        || !transaction_configuration.updated_heap_bytes.is_multiple_of(1024)
    {
        return Err(TransactionError::SanitizeFailure);
    }

    Ok(TransactionConfiguration {
        updated_heap_bytes: transaction_configuration.updated_heap_bytes,
        compute_unit_limit: transaction_configuration.compute_unit_limit.min(MAX_COMPUTE_UNIT_LIMIT),
        priority_fee_lamports: transaction_configuration.priority_fee_lamports,   // <-- NOT bounded/derived
        loaded_accounts_data_size_limit: transaction_configuration.loaded_accounts_data_size_limit.min(MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES.get()),
    })
}
``` [2](#0-1) 

`heap_size`, `compute_unit_limit`, and `loaded_accounts_data_size_limit` all have thresholds enforced against attacker-controlled input, matching exactly the bug class described in the report ("setter" values must be validated against a defined threshold). `priority_fee` has no such threshold. This is confirmed by the dedicated test `test_try_into_config_v1_no_clamping`, whose name and assertions explicitly document that the value is passed through unmodified [3](#0-2) .

The value comes directly from the wire format: `solana_message::v1::TransactionConfig::priority_fee: Option<u64>` [4](#0-3) , populated from an unprivileged, unsigned-content field of the transaction that any sender constructs (demonstrated for RPC fee estimation in `test_get_fee_for_message`, where a client sets `v1::TransactionConfig { priority_fee: Some(PRIORITY_FEE), .. }`) [5](#0-4) .

This decoupling breaks the invariant that all other paths of the fee/CU model rely on: `compute_unit_price_in_microlamports()` derives an "effective" per-CU price by dividing `priority_fee_lamports` by `compute_unit_limit` [6](#0-5) , and this derived (or raw) `priority_fee_lamports` feeds directly into:
- Transaction scheduling/prioritization ordering, `calculate_priority_and_cost`, which computes `reward / cost` used to rank transactions for block inclusion [7](#0-6) .
- The forwarding stage's priority computation [8](#0-7) .
- The prioritization fee cache used for `getRecentPrioritizationFees` RPC, which records `compute_unit_price_in_microlamports` per block [9](#0-8) .
- Fee/collector reward accounting via `calculate_fee_details`/`calculate_reward_and_burn_fee_details`.

Because a v1 sender can set `priority_fee` to an arbitrary `u64` (e.g. `u64::MAX`) while keeping `compute_unit_limit` tiny (e.g. `1`), a single transaction can report an artificially enormous per-CU "price" that is completely disconnected from real fee-market economics that every other transaction format enforces (price × limit, price bounded by actual lamports paid for actual compute). In the legacy/v0 path this exact scenario is bounded (`get_prioritization_fee` caps at `u64::MAX` computed from the same price×limit product, and `compute_unit_limit` is separately capped at `MAX_COMPUTE_UNIT_LIMIT`), so the price/limit relationship is always self-consistent. In v1 that self-consistency guarantee is absent because `priority_fee` and `compute_unit_limit` are two independent unclamped/partially-clamped fields rather than one derived from the other.

### Impact Explanation
This is an unprivileged, transaction-only issue (any user can submit a v1 transaction once `enable_tx_v1` is active — the feature-gated check only gates the *format*, not the priority_fee sanitization, per `Bank::verify_transaction` [10](#0-9) ). The lack of bound between `priority_fee` and actual compute/lamports paid allows:
- Distorted prioritization/fee-market signals surfaced via `getRecentPrioritizationFees` and internal scheduler priority ordering, letting an attacker cheaply manufacture transactions that appear extremely high-value for scheduling purposes without paying commensurate real fees relative to resource consumption, undermining fair economic ordering of the fee market (a "false" acceptance-order/prioritization primitive, not simply an economic nuisance).
- Downstream numeric surprises in `compute_unit_price_in_microlamports` (u128 math is used defensively there and saturates, so no direct arithmetic panic was found), but the broken price invariant itself is the corrupted value: `priority_fee_lamports` is asserted throughout the codebase (tests, cost model comments) to represent "price × limit"; for v1 it can be an arbitrary unrelated number.

### Likelihood Explanation
Medium: exploitation requires only constructing a v1 message with a large `priority_fee` and minimal `compute_unit_limit`; no special privileges or trusted components are required. It is gated behind the `enable_tx_v1` feature flag being active on-chain, so exploitability is limited until/unless that feature activates cluster-wide, but the missing validation exists in code today with no accompanying bound.

### Recommendation
Apply an explicit threshold to `priority_fee` in the v1 sanitization path in `VersionedTransactionConfiguration::try_into_config` (`runtime-transaction/src/transaction_meta.rs`), analogous to the other v1 fields: either (a) derive `priority_fee_lamports` from a `compute_unit_price` scalar bounded like the legacy path (using `get_prioritization_fee`), or (b) cap `priority_fee` by the same `get_prioritization_fee(price, compute_unit_limit)`-style relationship so it can never exceed what `compute_unit_limit * u64::MAX_micro_lamport_price` would allow, and reject (return `TransactionError::SanitizeFailure`) values inconsistent with a defined maximum price-per-CU threshold, mirroring the heap/CU-limit/loaded-accounts clamps already present in the same function.

### Proof of Concept
1. Enable/assume `enable_tx_v1` feature is active.
2. Construct a `solana_message::v1::Message` with:
   - `config.compute_unit_limit = Some(1)`
   - `config.priority_fee = Some(u64::MAX)`
   - a trivial instruction set.
3. Submit via RPC/`sendTransaction`. `Bank::verify_transaction` accepts the format (feature active) [10](#0-9) ; `VersionedTransactionConfiguration::try_into_config` passes `priority_fee_lamports` through unclamped [11](#0-10) , as directly exercised by `test_try_into_config_v1_no_clamping`, which asserts `priority_fee_lamports` is returned unmodified regardless of `compute_unit_limit` [3](#0-2) .
4. This transaction now reports/derives a per-CU price orders of magnitude beyond what any legacy/v0 transaction could ever produce (since those are capped via `get_prioritization_fee`'s bound on `compute_unit_price * compute_unit_limit`), skewing `calculate_priority_and_cost` ordering and `getRecentPrioritizationFees` statistics.

fn get_prioritization_fee(compute_unit_price: u64, compute_unit_limit: u64) -> u64 {

        (compute_unit_price as u128).saturating_mul(compute_unit_limit as u128);

        .checked_div(MICRO_LAMPORTS_PER_LAMPORT as u128)

        .unwrap_or(u64::MAX)
}

pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
}

```rust
fn calculate_priority(
    transaction: &RuntimeTransaction<SanitizedTransactionView<&[u8]>>,
    bank: &Bank,
) -> Option<u64> {
    let transaction_configuration = transaction
        .transaction_configuration(&bank.feature_set)
        .ok()?;

    // Manually estimate fee here since currently interface doesn't allow a on SVM type.
    // Doesn't need to be 100% accurate so long as close and consistent.
    let prioritization_fee = transaction_configuration.priority_fee_lamports;
    let signature_details = transaction.signature_details();
    let signature_fee = signature_details
        .total_signatures()
        .saturating_mul(bank.fee_structure().lamports_per_signature);
    let fee_details = FeeDetails::new(signature_fee, prioritization_fee);

    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    let cost = CostModel::estimate_cost(
        transaction,
        transaction.program_instructions_iter(),
        transaction.num_requested_write_locks(),
        &bank.feature_set,
    );

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    Some(
        MULTIPLIER
            .saturating_mul(reward)
            .wrapping_div(cost.sum().saturating_add(1)),
    )
}
