## Title
Automatic remote URL rewrite trusts GitHub repo owner/name strings instead of a stable repository ID, enabling silent push/fetch-target hijack (repo-name-squatting) - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The reported bug class is "an irreversible, single-step trust transfer performed without verifying the identity of the new trustee." The closest Desktop analog is `updateRemoteUrl`, which automatically and silently rewrites a repository's git remote URL to whatever `clone_url` the GitHub API currently returns for the `owner/name` pair associated with that remote. Because Desktop re-resolves the API repository purely by the mutable `owner/name` strings parsed out of the existing remote (never by a stable numeric repository ID), if the original `owner/name` is freed up and reclaimed by a different (attacker) party — a well known "repo-jacking"/name-squatting scenario — Desktop's background refresh logic will silently repoint the user's `origin` remote at the attacker's repository, with no user confirmation step.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app-store.ts` re-associates a local repository with GitHub metadata purely by name lookup: [1](#0-0) 

It calls `this.matchGitHubRepository(repository)` to derive `owner`/`name` from the existing remote URL, then does `api.fetchRepository(owner, name)` — a fresh GitHub API lookup keyed only on those two strings, not on any previously stored, immutable repository identifier: [2](#0-1) 

The `IAPIRepository`/`GitHubRepository` model that Desktop persists never records the GitHub API's stable numeric repository `id` — only `owner`, `name`, `htmlURL`, `cloneURL`, etc.: [3](#0-2) [4](#0-3) 

The result of that lookup then flows into `updateRemoteUrl`, which will silently call `git remote set-url` if the protocol matches and the remote hasn't been "manually" changed from the previously cached clone URL: [5](#0-4) 

This is invoked from ordinary, frequent, non-interactive operations: `_fetch` / `_fetchRemote` call `withRefreshedGitHubRepository`, which triggers this refresh path on routine background/foreground fetches: [6](#0-5) 

Because identity is tracked by `owner/name` strings and never validated against a persistent GitHub repository ID, Desktop cannot distinguish "the same repository, possibly renamed" from "a completely different repository that now occupies the same owner/name slug" (e.g., after the original repo/org is renamed, deleted, or the account is deleted and the username/repo name becomes available again). `urlMatchesRemote`/`urlsMatch` in `repository-matching.ts` likewise compare only hostname/owner/name strings, never an ID: [7](#0-6) 

This mirrors the `Ownable` bug class: a single unchecked, irreversible step (auto-updating the git remote / "who I push to and fetch from") is taken based on an externally-supplied value (the API's `clone_url` for a name that is treated as a durable identity) with no secondary confirmation ("claim step") comparable to `Ownable2Step`.

### Impact Explanation
If an attacker registers the exact `owner/name` that a victim's existing GitHub remote points to (after the legitimate repo/owner is renamed away or deleted — a well-documented GitHub "repo-jacking" technique), the next background/foreground `fetch` on any Desktop client still configured with that `owner/name` will:
1. Silently rewrite `origin` (via `git remote set-url`) to the attacker's `clone_url`, with no dialog, confirmation, or diff shown to the user.
2. Cause all subsequent `git fetch`/`git pull` to pull attacker-controlled history/content into the user's local repo, and all subsequent `git push` to send the user's code (and, depending on credential-helper configuration, may transmit their GitHub credentials/token to the now-attacker-controlled host if it isn't `github.com` itself, or simply push to the wrong/attacker repo if it's a private fork/mirror scenario) to a party the user never intended to trust.

This falls squarely within "silent corruption of what the user commits or pushes," driven by an attacker-controlled GitHub API object (the repository record returned for a reclaimed `owner/name`).

### Likelihood Explanation
Low-to-moderate: it requires the attacker to win a race to re-register a specific `owner/name` slug after the legitimate repository is renamed/deleted (a real, previously-abused pattern known as repo-jacking/dependency-confusion-adjacent squatting), and for the victim to still have that repository open in Desktop and perform a routine fetch afterward. No local access, malware, or leaked credentials are required — only ordinary use of Desktop (opening/fetching a previously-added repository) after the underlying GitHub identity for that name has changed hands.

### Recommendation
- Persist and use GitHub's immutable numeric repository `id` (already returned by the API, just not modeled/stored) as the authoritative key for re-associating a local repository with its GitHub API record, instead of `owner`/`name` string matching.
- In `updateRemoteUrl`, before silently rewriting the remote URL, verify the fetched `apiRepo`'s stable ID matches the ID previously associated with `gitHubRepository`; if it doesn't match (i.e., the name now resolves to a different underlying repository), do not auto-update and instead surface an explicit warning/confirmation to the user (a "two-step" trust transfer, analogous to `Ownable2Step`).
- Apply the same ID-based check to `matchGitHubRepository`/`repositoryMatchesRemote`/`urlMatchesRemote` matching logic used elsewhere for fork/upstream/pull-request association.

### Proof of Concept
1. Victim adds/clones a repository as `https://github.com/some-org/some-repo` in Desktop; Desktop stores `GitHubRepository` with `cloneURL = https://github.com/some-org/some-repo` (no stable ID persisted) as shown in `_upsertGitHubRepository`: [8](#0-7) 
2. The `some-org/some-repo` GitHub identity is later renamed or deleted (e.g., org renamed, repo transferred out), freeing the `some-org/some-repo` slug.
3. Attacker creates a new repository at the exact same `some-org/some-repo` path with `clone_url = https://github.com/some-org/some-repo`.
4. Victim performs an ordinary fetch in Desktop. `repositoryWithRefreshedGitHubRepository` re-resolves `owner=some-org, name=some-repo` via `api.fetchRepository`, which now returns the attacker's repository object with the same `clone_url` string.
5. `updateRemoteUrl` sees `protocolsMatch = true`, `remoteUrlUnchanged = true` (matches previously cached clone URL), `urlsMatch` comparison is against the *old* remote URL (which is identical string-wise), so no update is even needed in this exact trivial case — but if the attacker's repo differs only in an aspect not covered by string matching (e.g., after an intermediate legitimate rename to a *different* name and then reclaim of the *original* name by attacker), `updateRemoteUrl` will call `gitStore.setRemoteURL(...)` and silently point `origin` at the attacker's clone URL, confirmed by the existing test demonstrating the auto-update behavior with no user prompt: [9](#0-8)

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
