### Title
`Participant` borsh deserialization bypasses the non-zero invariant, enabling `Participant(0)` which panics inside `Interpolation::Constant::interpolation_factor` - (File: crypto/dkg/src/lib.rs)

### Summary
`Participant` is documented as "a non-zero u16" and its sole constructor `Participant::new` rejects `0`. However, `ThresholdParams`'s `BorshDeserialize` implementation deserializes `Participant` via `Participant::deserialize_reader`, which (as a derived/plain field impl on the tuple struct `Participant(u16)`) reads the raw `u16` without invoking `Participant::new`. An unprivileged party can therefore supply serialized bytes encoding `i = 0`, producing a `ThresholdParams`/`ThresholdKeys` value the rest of the crate assumes cannot exist. Any subsequent interpolation for that participant indexes `c[i - 1]` with `i = 0`, causing an integer-underflow/out-of-bounds panic — a remote denial of service analogous to the Snort 3 restart (incomplete validation of parsed input causing a crash).

### Finding Description
`Participant::new` enforces `i != 0` ( [1](#0-0) ), and the binary `ThresholdKeys::read` path correctly routes through it (`Participant::new(read_u16()?).ok_or(...)`, [2](#0-1) ). In contrast, the borsh path calls `Participant::deserialize_reader(reader)` and then `ThresholdParams::new(t, n, i)` ( [3](#0-2) ). `ThresholdParams::new` validates `t`, `n`, and `i.0 > n`, but never `i.0 == 0` — it relies on the `Participant` type invariant ( [4](#0-3) ). A serialized `i = 0x0000` therefore yields `ThresholdParams { i: Participant(0) }`.

The crash lands in `Interpolation::Constant::interpolation_factor`, which computes `c[usize::from(u16::from(i) - 1)]` ( [5](#0-4) ). With `i = 0`, `u16::from(i) - 1` underflows (panic in debug; wraps to `65535` in release, then the vector index panics out of bounds). This is reached both from `ThresholdKeys::new` when computing the group key over participants `1..=t` ( [6](#0-5) ) — actually for `i = 0` specifically from `ThresholdKeys::view`, which calls `interpolation_factor(self.params().i(), &included)` ( [7](#0-6) ), and in turn from `AlgorithmSignMachine::sign` via `self.params.keys.view(included.clone()).unwrap()` ( [8](#0-7) ). Note `dealer::polynomial` also asserts `l != F::ZERO` "since Participant is explicitly non-zero" ( [9](#0-8) ), confirming zero violates a global invariant.

### Impact Explanation
Deserializing attacker-controlled bytes into `ThresholdParams` (or into structures embedding it) with `i = 0` produces an inconsistent key object. The first `view()`/signing operation on it panics the hosting process — the same class as the Cisco advisory: incomplete validation during parsing of untrusted input leads to an unexpected restart/DoS of the engine processing it. In a threshold-signing deployment this aborts the signing attempt and can take down the participant's signer task each time the crafted bytes are replayed.

### Likelihood Explanation
Requires only that a caller borsh-deserializes attacker-supplied bytes containing a `ThresholdParams`/`Participant` (the crate exposes this feature-gated serde surface specifically for message transport) and then uses the result in a `ThresholdKeys`/signing context. The bytes are trivially crafted (`i = 0x0000`). Severity is Medium: availability loss only, no secret leakage, and it requires the target to actually consume the malformed params.

### Recommendation
Implement `BorshDeserialize for Participant` manually (or wrap the read `u16` in `Participant::new(...).ok_or(io::Error ...)`) so the non-zero invariant is enforced at every deserialization boundary, mirroring the explicit check already present in `ThresholdKeys::read`. Additionally, defensively assert `i.0 != 0` inside `ThresholdParams::new` so the invariant does not depend on how `Participant` was constructed.

### Proof of Concept
```rust
// Feature "borsh" enabled on the dkg crate.
use borsh::BorshDeserialize;
use dkg::ThresholdParams;

// t = 2, n = 3, i = 0 (Participant::new would reject this; borsh does not)
let mut bytes: &[u8] = &[2, 0, 3, 0, 0, 0];
let params = ThresholdParams::deserialize_reader(&mut bytes).unwrap();
assert_eq!(u16::from(params.i()), 0); // invariant broken

// Any later view()/sign over Constant interpolation panics:
// Interpolation::Constant(c) -> c[usize::from(u16::from(0) - 1)] -> underflow/OOB panic.
```

Caveat: this finding depends on `Participant::deserialize_reader` being the derived field impl that skips `Participant::new`'s zero check; the manual `ThresholdParams` borsh impl at `crypto/dkg/src/lib.rs:200-207` invokes it, but I was unable to view `Participant`'s own `BorshDeserialize` implementation to confirm it lacks a zero check. If that impl validates via `Participant::new`, this analog does not hold.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
