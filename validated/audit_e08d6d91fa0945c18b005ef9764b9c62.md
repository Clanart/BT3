### Title
Unbounded recursive parsing of untrusted on-chain custody memos causes wallet-sync DoS via Python `RecursionError` - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
`PuzzleWithRestrictions.from_memo()` recursively decodes an on-chain `CREATE_COIN` memo into nested `MofN` custody structures with no depth or size limit. When a `MofN` hint indicates "further branching," each member memo is parsed by calling `PuzzleWithRestrictions.from_memo()` again, and a member's puzzle can itself be another `MofN` with its own nested members. An attacker who creates a coin whose puzzle matches the PlotNFT singleton mod (a public, well-known puzzle hash) can freely choose the memo contents attached to a `CREATE_COIN` condition. By nesting `MofN` hints arbitrarily deep, the attacker forces every syncing wallet to recurse without bound, exhausting the Python call stack and crashing/hanging the wallet process — the same bug class as the SurrealDB advisory (CWE-674, uncontrolled recursion while parsing nested type/structure annotations from untrusted input), except here it is a Python-level `RecursionError`/crash rather than server OOM.

### Finding Description
`PuzzleWithRestrictions.from_memo()` is defined at [1](#0-0) . When `further_branching` is true, it decodes a `MofNHint` and recurses once per member:
```
puzzle: MIPSComponent = MofN(
    m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
)
```
There is no check on nesting depth, on the size of `member_memos`, or on total memo size before recursing — unlike the CLVM interpreter itself, this is pure Python recursion bounded only by the interpreter's default recursion limit (typically 1000).

This method is reached from untrusted, attacker-controlled chain data: `PlotNFT.get_next_from_coin_spend()` calls it directly on the memo blob of a `CREATE_COIN` condition emitted by *any* coin spend whose puzzle matches the (public) PlotNFT singleton mod: [2](#0-1) 

`get_next_from_coin_spend()` in turn is invoked automatically during wallet chain sync whenever `determine_coin_type()` recognizes a singleton puzzle matching `PlotNFT.singleton_puzzles.singleton_mod`, via `PlotNFT2Wallet.identify()`: [3](#0-2) 

Because the PlotNFT singleton mod hash is public (any spender can curry it and craft an arbitrary memo/solution to satisfy the "some create-coin with this mod" check), a spender does not need to own a plotnft wallet to trigger this path — they only need to create a spend whose output coin's puzzle matches the recognized singleton mod and carries a maliciously deep `MofN` memo. Every wallet client that observes and syncs this coin state (which happens automatically, unauthenticated, for any peer/coin visible on chain) will attempt to parse the memo and recurse to the attacker-chosen depth.

The `MofN` dataclass itself only bounds `m`/`n` relationships (`m <= n`, `m >= 1`, no duplicate nodes) in `__post_init__` — [4](#0-3)  — but does not limit recursive nesting depth of `members`, and this validation only runs after the (possibly already stack-exhausting) `from_memo` recursion has constructed the object graph bottom-up.

### Impact Explanation
A successful exploit causes a Python `RecursionError` (or, depending on platform recursion-limit/stack-size interaction, an actual C-stack overflow crash) inside the wallet process while it is processing normal, unauthenticated chain-sync data. Because coin-state sync loops call this on every relevant coin spend, a single malicious coin observed by the wallet can reliably crash or hang wallet sync for any user/service running the affected wallet code — a spend-triggered transaction-processing halt matching the class accepted by the validation rules. This does not corrupt consensus or move funds, but it denies wallet availability, which is the direct analog to the SurrealDB "authenticated user crashes the server with one deeply nested query" bug — here it's "any observer of chain data crashes/hangs the wallet with one deeply nested memo."

### Likelihood Explanation
Likelihood is high for any attacker willing to spend a small amount to create a coin with the vulnerable puzzle/memo shape: the PlotNFT singleton mod hash is public, the `CREATE_COIN` memo format is fully attacker-controlled bytes, and wallet sync automatically parses memos for coins matching that mod with no size/depth guard prior to invoking `PuzzleWithRestrictions.from_memo()`. No special privileges, signatures, or targeting of a specific victim wallet are required beyond that the victim's wallet is syncing and observes the coin (which is the normal operating mode of any Chia wallet).

### Recommendation
Add an explicit recursion/nesting-depth (and/or size) limit to `PuzzleWithRestrictions.from_memo()`/`MofNHint.from_program()` before recursing into `member_memos`, rejecting memos that exceed a sane depth (mirroring how CLVM execution itself is cost-bounded). Convert the recursive walk into an iterative one with an explicit depth counter, or enforce a maximum nesting constant and raise a `ValueError` (already the expected error type callers such as `get_next_from_coin_spend` catch) once exceeded, so a malformed/hostile memo fails cleanly instead of exhausting the stack.

### Proof of Concept
1. Construct a `CREATE_COIN` condition whose puzzle hash matches `PlotNFT.singleton_puzzles.singleton_mod` curried appropriately (public mod, no secret needed), and whose memo blob is `Program.to((PuzzleWithRestrictions.spec_namespace, [0, [], 1, MofNHint(m=1, member_memos=[<same nested MofNHint recursively repeated N times>]).to_program()]))`, nesting the `MofNHint`/`PuzzleWithRestrictions` memo shape (as validated to round-trip via `PuzzleWithRestrictions.from_memo`/`.memo()` in [5](#0-4) ) to a depth of several thousand.
2. Spend a coin producing this `CREATE_COIN` output on-chain (any coin, any owner).
3. Any wallet client that syncs and observes this coin state calls `determine_coin_type()` → `PlotNFT2Wallet.identify()` → `PlotNFT.get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo()`, which recurses to the attacker-chosen depth and raises `RecursionError`, crashing or hanging the sync task.

Note: I was not able to fully verify the exact code path/guard rails inside `PlotNFT2Wallet.identify()` (in `chia/wallet/plotnft_wallet/plotnft_wallet.py`) due to index coverage limits — only its existence and the call site in `wallet_state_manager.py` were confirmed. Starting a Devin session would allow inspecting that file in full to confirm there is no depth/size pre-check before `get_next_from_coin_spend()` is invoked.
