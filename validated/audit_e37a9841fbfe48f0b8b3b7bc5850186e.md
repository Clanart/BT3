### Title
PedPoP `calculate_share` emits a blame proof (revealing the recipient's ECDH shared key) for a message whose proof-of-possession was never verified, letting an attacker trick a recipient into publishing the decryption key for another sender's encrypted secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts each received `EncryptedMessage` and immediately produces an `EncryptionKeyProof` (the ECDH shared key plus a DLEq proof) intended for public blame adjudication. The Schnorr proof-of-possession on the per-message key is only *queued* into a `BatchVerifier` and verified later. If the decrypted bytes fail `C::F::from_repr`, the function returns early via `?` with `InvalidShare { blame: Some(..) }` — before `batch.verify_with_vartime_blame()` ever runs. An attacker can therefore submit a share message reusing another sender's public ephemeral key with an invalid PoP, and the victim will emit a blame proof that reveals that sender's ECDH shared key, exposing the victim's encrypted secret share to any third party. This is the same class of bug as CVE-2024-47779: secret key material disclosed to third parties under specially crafted attacker-controlled input.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `calculate_share` iterates over `shares`, calling `self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes)` at `lib.rs:477-478`. Inside `Encryption::decrypt` (`encryption.rs:469-501`), the sender's PoP is only *queued* via `msg.pop.batch_verify(...)`, while the ECDH key `key = ecdh(&self.enc_key, msg.key)` and the `EncryptionKeyProof { key, dleq }` are computed unconditionally and returned.

Back in `calculate_share` (`lib.rs:479-482`):

```rust
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);
```

The `?` propagates the error — with the blame proof attached — before the batch verifier runs at `lib.rs:493` (`batch.verify_with_vartime_blame()`). The `BatchId::Decryption` mechanism that correctly maps a failed PoP to `blame: None` is never reached.

The design comment in `encryption.rs:83-90` states the PoP exists precisely to stop this attack: without it, "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X... they'd reveal bX, revealing Alice's message to Bob." The early `from_repr` return bypasses the PoP check entirely, reintroducing exactly that side effect.

### Impact Explanation
The blame proof is public by design — it is returned to the caller for adjudication via `BlameMachine::blame` / `AdditionalBlameMachine::blame`, where `decrypt_with_proof` lets any observer decrypt the accused ciphertext with the revealed `proof.key` (`encryption.rs:366-397`). Once a victim emits the premature blame proof containing `key = enc_key_victim * msg.key` for an attacker-supplied `msg.key` copied from an honest sender's ciphertext, anyone holding the proof and the original ciphertext recovers the plaintext: the honest sender's secret share for the victim. DKG secret shares are high-value key material; disclosure of a threshold number of shares across such leaks enables recovery of the distributed private key, and each individual share is itself secret material that the protocol's encryption layer was explicitly built to protect.

### Likelihood Explanation
The trigger requires only that a sender deliver an `EncryptedMessage` whose ciphertext decrypts to non-canonical scalar bytes. The attacker fully controls `msg.key` (copying the honest sender's public ephemeral point) and the ciphertext body (random bytes almost always fail `from_repr`); the attached PoP can be garbage because it is never verified on this path. The victim's `calculate_share` then deterministically emits the leaking blame proof. The only preconditions are that the attacker participates in (or feeds untrusted bytes into) the share-collection round and that the victim later surfaces the returned blame — both part of the documented reachability surface for `EncryptedMessage::read` / `calculate_share`.

### Recommendation
Verify each message's PoP (or the whole batch) before attaching an `EncryptionKeyProof` to any error. Concretely, in `calculate_share`, do not return `blame: Some(..)` on the `from_repr` failure path unless the corresponding PoP has been confirmed — e.g., defer the error until after `batch.verify_with_vartime_blame()` succeeds (mapping non-canonical plaintext to `BatchId::Share(l)`-style blame only for PoP-valid messages), or perform a standalone `msg.pop.verify` check before constructing/returning the blame proof. Any error returned before PoP verification must carry `blame: None`.

### Proof of Concept
1. Victim Bob runs `KeyGenMachine::generate_coefficients`, publishes `EncryptionKeyMessage` containing `enc_pub_key_bob` (`lib.rs:187-191`, `encryption.rs:448-450`).
2. Honest Alice sends Bob `Enc_A = { key: A_k, pop: σ_A, msg: enc_share }` where `A_k = k_a·G` and `enc_share` is ChaCha20-encrypted under `cipher(context, A_k·enc_key_bob)` (`encryption.rs:135-168`).
3. Attacker Eve observes `A_k` (it is a public field of the ciphertext) and sends Bob `Enc_E = { key: A_k, pop: <arbitrary invalid sig>, msg: <random bytes> }`.
4. Bob's `calculate_share` calls `decrypt` on `Enc_E`: it queues the (invalid) PoP into the batch verifier, then computes `key = ecdh(enc_key_bob, A_k)` — identical to Alice's shared key — and returns `(garbage_plaintext, EncryptionKeyProof { key, dleq: valid })` (`encryption.rs:479-500`). Bob's `enc_key_bob` makes the DLEq proof valid against `enc_pub_key_bob`.
5. `C::F::from_repr` on the garbage fails; `calculate_share` returns `PedPoPError::InvalidShare { participant: Eve, blame: Some(proof) }` at `lib.rs:480-482`, exiting before `batch.verify_with_vartime_blame()` at `lib.rs:493`.
6. Bob's application publishes the blame proof for adjudication. Any observer now takes `proof.key = A_k·enc_key_bob`, derives `cipher(context, proof.key)`, and decrypts Alice's `enc_share` — recovering Alice's secret share for Bob, a secret intended to be known only to Alice and Bob. The PoP check that `decrypt_with_proof` performs first (`encryption.rs:374-379`) does not help because it runs during adjudication, after the key has already been disclosed.
