### Title
Clawback claim marks the incoming transaction as "sent" before the spend bundle is ever pushed, permanently blocking normal re-claim on failure - (File: chia/wallet/clawback_manager.py)

### Summary
In `ClawbackManager.spend_clawback_coins()`, each clawback coin's `incoming_tx.sent` counter is incremented to mark it `PENDING` *before* the aggregate spend bundle is fully built, fee-tandem'd, signed, and actually pushed to the network. This is the same "effect before interaction" ordering flagged in the source report (subtracting `poolAmount` before the transfer): a local accounting/state field is mutated optimistically ahead of the operation whose success it is supposed to represent.

### Finding Description
`spend_clawback_coins()` loops over the coins to claim/clawback and, per coin, calls: [1](#0-0) 
immediately after building that coin's `CoinSpend` — well before the function later builds the fee tandem transaction, aggregates the final `spend_bundle`, and hands the resulting `TransactionRecord` to the action scope: [2](#0-1) [3](#0-2) 

The guard that is supposed to prevent double-claims reads this same field on the *next* call: [4](#0-3) 

Because `increment_sent()` is invoked inside the per-coin loop rather than after the assembled bundle is confirmed to have actually been pushed (i.e., after `action_scope` exit → `add_pending_transactions()` → mempool submission), any failure that occurs after this point but before a successful broadcast leaves `incoming_tx.sent > 0` permanently, with no compensating rollback:
- If `fee > 0` and `create_tandem_xch_tx()` (invoked inside the `if fee > 0:` block) raises — e.g. insufficient spendable coins for the fee, or coin-selection failure — the exception propagates out of `spend_clawback_coins()` before the `TransactionRecord` is ever appended to `action_scope.side_effects.transactions`, so nothing is ever pushed, yet the coin's `incoming_tx` is already marked `sent`.
- If the caller's RPC (`spend_clawback_coins` in `chia/wallet/wallet_rpc_api.py`, lines 1479-1524) or the enclosing action-scope commit fails after this point (e.g., signing failure, DB write failure, node disconnect during push), the same stuck state results.

Once `incoming_tx.sent > 0`, the early-exit check `if incoming_tx.sent > 0 and not force: continue` (lines 226-230) silently skips that coin on every subsequent non-forced claim/clawback attempt, even though no spend was ever actually broadcast or confirmed. This mirrors the report's root cause exactly: a state field meant to reflect "the transfer happened" is updated *before* the transfer is guaranteed to occur, and there is no unwind path if the downstream operation never completes.

### Impact Explanation
This is a state/accounting inconsistency, not a fund-loss bug by itself — the coin itself is unaffected on-chain and is still spendable via `force=True`. However, it produces a wallet-side "spend-triggered transaction-processing halt": ordinary (non-forced) future calls to `spend_clawback_coins` for that coin will silently no-op (`continue`), making the affected clawback/claim funds appear un-claimable through the normal API/CLI/GUI path after a transient failure, until an operator manually discovers and uses the `force` flag. Given the multi-coin batch nature of this method (`clawback_coins: dict[Coin, ClawbackMetadata]`), a fee-tandem failure partway through can strand an arbitrary number of already-"sent"-marked coins in a single call.

### Likelihood Explanation
Reachable by any wallet user calling `spend_clawback_coins` RPC/CLI (`chia/wallet/wallet_rpc_api.py:1479-1524`) with `fee > 0` while coin selection for the fee is constrained (e.g., all other coins locked in pending transactions, exceeded max coin amount, or a transient DB/network error in `create_tandem_xch_tx`). This does not require any privileged or malicious party — it's a self-inflicted local wallet condition triggerable by normal usage plus an ordinary failure in the fee-spend construction path, making likelihood moderate.

### Recommendation
Move the `increment_sent()` call (or an equivalent "claimed" marker) to after the full spend bundle (including the fee tandem transaction) has been successfully assembled and appended to `action_scope.side_effects.transactions`, ideally gated on the eventual mempool submission result rather than being set unconditionally per-coin during bundle construction. Alternatively, wrap the per-coin loop and the fee-tandem/aggregate steps in a single try/except that rolls back (`increment_sent`-equivalent decrement, or re-fetching original `sent` value) any coins already marked if a later step fails.

### Proof of Concept
1. Have wallet A receive several clawback-eligible coins (`incoming` transactions).
2. Call `spend_clawback_coins` with `coin_ids` covering ≥1 clawback coin and `fee > 0`, at a moment where the wallet's other coins are all excluded/pending (so `create_tandem_xch_tx` inside the `if fee > 0:` block raises, e.g. `ValueError` for "not enough coins").
3. Observe: the loop over `clawback_coins` already executed `await self.transaction_store.increment_sent(incoming_tx.name, "", MempoolInclusionStatus.PENDING, None)` for each coin (`chia/wallet/clawback_manager.py:261`) before the exception is raised further down (`chia/wallet/clawback_manager.py:267-298`), so no `TransactionRecord` is ever appended and nothing is broadcast.
4. Retry `spend_clawback_coins` on the same `coin_ids` without `force=True`: the check at `chia/wallet/clawback_manager.py:226-230` (`incoming_tx.sent > 0 and not force`) causes the coin to be skipped, even though it was never actually spent — reproducing the "state mutated before external operation confirms" bug class from the source report.
