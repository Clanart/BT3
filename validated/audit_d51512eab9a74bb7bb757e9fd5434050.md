## Title
Merge-conflict-marker count relies on `git diff --check`, which under-reports (or fails to report) leftover conflict markers for whitespace-error-suppressing or binary-adjacent content — allowing "Continue"/commit with unresolved conflicts left in tracked files - ([File: app/src/lib/git/diff-check.ts])

### Summary
GitHub Desktop decides whether a conflicted file is "resolved" purely by counting lines matching `leftover conflict marker` in the output of `git diff --check`, and treats a count of `0` as "no conflicts remaining," enabling the user to stage/commit/continue the operation. [1](#0-0) 
This is the same bug class as the report: a boolean/derived "is-it-safe-to-proceed" signal defaults to the *safe* outcome whenever the underlying detector doesn't explicitly flag a problem, instead of using an explicit state machine that distinguishes "verified clean," "verified conflicted," and "unable to verify."

### Finding Description
`conflictMarkerCount` for a text-conflicted file is populated entirely from `getFilesWithConflictMarkers`, which shells out to `git diff --check` and parses only lines matching `leftover conflict marker`: [1](#0-0) 

That count then drives every "is this file resolved" decision in the app:
- `hasUnresolvedConflicts` treats `conflictMarkerCount > 0` as unresolved and anything else (`0`) as resolved for `ConflictsWithMarkers` files: [2](#0-1) 
- `mapStatus` reports the file as `'Resolved'` once `conflictMarkerCount` reaches `0`: [3](#0-2) 
- `isFileResolvedExternally` in the Copilot conflict dialog treats `conflictMarkerCount === 0` as proof the on-disk edit resolved the conflict, and lets that "win" over any previous manual choice: [4](#0-3) 
- `stageManualConflictResolution` special-cases `conflictMarkerCount === 0` to skip further processing and just accept the file as-is: [5](#0-4) 

The invariant Desktop relies on is: *"if `git diff --check` reports 0 leftover conflict markers, the file genuinely contains no `<<<<<<<`/`=======`/`>>>>>>>` markers."* That invariant does not hold for all inputs to `git diff --check`:
- `git diff --check` is fundamentally a *whitespace/newline* check tool; its "leftover conflict marker" detection is a side heuristic, and its output/exit behavior is governed by `core.whitespace`/`.gitattributes` `-whitespace`/`conflict-marker-size` settings. A remote/attacker-controlled repository can ship a `.gitattributes` (or the user's own diff driver config for a path) that disables whitespace error reporting for a path, or set `conflict-marker-size` to a non-default value inconsistent with the actual markers left in the file, causing `git diff --check` to emit no `leftover conflict marker` lines for that path even though literal `<<<<<<<`/`=======`/`>>>>>>>` text remains in the working tree.
- The parsing regex `^(.+):\d+: leftover conflict marker` is also line-based and keys strictly off git's fixed English message text; any git version/locale difference, or `diff --check` limitation on binary-adjacent/very large files, silently yields zero matches rather than raising an explicit "unknown/could not verify" state.
- Crucially, none of the consumers distinguish "verified 0 markers" from "the check could not run / did not apply to this file" — there is no analog of the report's recommended enum with an explicit unresolved/unknown value. A `0` from `getFilesWithConflictMarkers` is structurally indistinguishable from "we never checked this path" (the `Map` simply has no entry, and `conflictCountsByPath.get(path) || 0` collapses both cases to `0`): [6](#0-5) 

This mirrors the report's root cause exactly: a downstream consumer (`hasUnresolvedConflicts`, `mapStatus`, `isFileResolvedExternally`, `stageManualConflictResolution`) treats the *absence of a positive detection* as proof of the *safe* case, instead of modeling "not detected" and "confirmed clean" as distinct states.

### Impact Explanation
If the resolved/unresolved determination is wrong, Desktop will:
- Show the file as `'Resolved'`/`defaultConflictsResolvedMessage` in the merge/rebase/cherry-pick conflict UI even though literal conflict markers remain in the tracked file content,
- Enable "Continue"/"Commit merge" for the multi-commit operation, and
- Allow the user to commit and subsequently push a file that still contains raw `<<<<<<<`/`=======`/`>>>>>>>` conflict markers as tracked source content.

This is a silent corruption of what the user commits/pushes: the user believes (based on Desktop's UI) that the merge/rebase/cherry-pick was cleanly resolved, but the committed blob contains unresolved conflict text. This is the same category of harm called out in the report — the off-chain/UI state ("finalized"/"resolved") diverges from the true on-disk/on-chain state ("not actually resolved").

### Likelihood Explanation
The trigger surface is exactly the "attacker controls a cloned/fetched repository" primitive allowed by the task: an attacker who controls the branch being merged, rebased onto, or cherry-picked from can:
- ship `.gitattributes` settings (`-whitespace` for a path, or path-scoped `core.whitespace`) that suppress `diff --check`'s error reporting for the conflicting file, or
- structure content such that `diff --check`'s marker-size assumption diverges from git's default conflict marker length used to render the conflict, or
- rely on the fact that `diff --check` output parsing is best-effort and any path where git produces zero matching lines (for whatever reason) is treated as "no markers" with no fallback "cannot verify" state.

Because none of this requires local/physical access, admin rights, or pre-existing malware — only that the victim merges/rebases/cherry-picks against a repository/branch the attacker controls — likelihood is realistic for a normal GitHub Desktop workflow (pulling a PR branch, merging a fork, etc.).

### Recommendation
Do not treat "0 markers found by `git diff --check`" as equivalent to "verified clean." Introduce an explicit tri-state result (e.g. `Clean | Conflicted | Unknown`) analogous to the report's enum recommendation:
- If `git diff --check` cannot conclusively parse a file (unexpected exit code, unparseable output, path not covered due to `.gitattributes`/binary heuristics), surface `Unknown` rather than defaulting the count to `0`.
- Independently re-verify "no leftover markers" by scanning the actual file bytes for the marker patterns (`^<{7}`, `^={7}`, `^>{7}` at line start, matching git's `conflict-marker-size`) rather than solely trusting `git diff --check`'s heuristic report, so that `.gitattributes`/whitespace-config manipulation by a remote branch cannot suppress detection.
- Block "Continue"/commit when the state is `Unknown`, the same way `checkDynamicConsensusAttestations()` returning false should have blocked finalization rather than falling through to a default "success" value.

### Proof of Concept
1. Attacker creates a branch/fork with a file `foo` and a `.gitattributes` entry disabling whitespace error checks for that path (e.g. `foo -whitespace`), or leverages a `conflict-marker-size` mismatch, then engineers a merge so that after conflict, `foo` still contains real `<<<<<<<`/`=======`/`>>>>>>>` markers.
2. Victim, using GitHub Desktop, merges/rebases against this branch; conflicts are detected (`MergeHead`/rebase state present), Desktop calls `getConflictDetails` → `getFilesWithConflictMarkers` → `git diff --check`. [7](#0-6) 
3. Because of the crafted `.gitattributes`/marker-size mismatch, `git diff --check` reports no `leftover conflict marker` line for `foo`, so `conflictCountsByPath` has no entry for it and `conflictMarkerCount` resolves to `0`. [8](#0-7) 
4. The conflicts UI renders `foo` as resolved (`mapStatus`/`defaultConflictsResolvedMessage`/`isFileResolvedExternally`), the victim clicks "Continue"/"Commit merge," and Desktop commits `foo` with the literal conflict markers still embedded, which then gets pushed to the remote — corrupting the tracked source with unresolved-conflict text without any warning.

Note: I was not able to execute git itself in this environment to empirically confirm the exact `.gitattributes`/`conflict-marker-size` combination that suppresses `diff --check`'s "leftover conflict marker" line while leaving real markers on disk; this analysis is based on the code's reliance on `git diff --check` heuristics and the documented behavior of that command's whitespace/marker-size configurability. A Devin session with shell access could verify the precise reproduction steps against a live repository.

export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files
}

/**
 * Determine if we have any conflict markers or if its been resolved manually
 */
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}

function parseConflictedState(
  entry: UnmergedEntry,
  path: string,
  conflictDetails: ConflictFilesDetails
): ConflictedFileStatus {
  switch (entry.action) {
    case UnmergedEntrySummary.BothAdded: {
      const isBinary = conflictDetails.binaryFilePaths.includes(path)
      if (!isBinary) {
        return {
          kind: AppFileStatusKind.Conflicted,
          entry,
          conflictMarkerCount:
            conflictDetails.conflictCountsByPath.get(path) || 0,
        }
      } else {
        return {
          kind: AppFileStatusKind.Conflicted,
          entry,
        }
      }
    }
    case UnmergedEntrySummary.BothModified: {
      const isBinary = conflictDetails.binaryFilePaths.includes(path)
      if (!isBinary) {
        return {
          kind: AppFileStatusKind.Conflicted,
          entry,
          conflictMarkerCount:
            conflictDetails.conflictCountsByPath.get(path) || 0,
        }
      } else {
        return {
          kind: AppFileStatusKind.Conflicted,
          entry,
        }
      }
    }
    default:
      return {
        kind: AppFileStatusKind.Conflicted,
        entry,
      }
  }
}

async function getConflictDetails(
  repository: Repository,
  mergeHeadFound: boolean,
  conflictedFilesInIndex: ReadonlyArray<IStatusEntry>,
  rebaseInternalState: RebaseInternalState | null
): Promise<ConflictFilesDetails> {
  try {
    if (mergeHeadFound) {
      return await getMergeConflictDetails(repository, conflictedFilesInIndex)
    }

    if (rebaseInternalState !== null) {
      return await getRebaseConflictDetails(repository, conflictedFilesInIndex)
    }

    // If there's conflicted files in the index but we don't have a merge head
    // or a rebase internal state, then we're likely in a situation where a
    // stash has introduced conflicts

        repository,
        conflictedFilesInIndex
      )
    }

    log.error(

    )
  }
