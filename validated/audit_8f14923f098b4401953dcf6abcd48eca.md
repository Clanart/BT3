## Title
NFT DID-Identity Spoofing at Mint — Eve Coin `owner_did` Trusted Without DID-Owner Authorization - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
The NFT ownership layer binds an NFT to a DID (`current_owner`) as a curried puzzle parameter. Chia's own minting code always curries this field to empty (`b""`) at genesis and only sets a real DID via a signed `-10` condition backed by a `CreatePuzzleAnnouncement`/`AssertPuzzleAnnouncement` pair spent from the actual DID coin (`get_did_approval_info`). However, nothing in the CLVM ownership-layer puzzle or in the wallet's coin-identification logic enforces that this convention was followed. A minter using non-standard tooling can curry an arbitrary DID id directly into the genesis (eve) NFT puzzle, and any syncing wallet will read and trust that value as `owner_did`/`minter_did` without verifying that the claimed DID ever authorized the association.

The legitimate DID→NFT binding mechanism requires the DID wallet to actively spend its own coin and create a `CreatePuzzleAnnouncement`, which the NFT-side `-10` condition then asserts (`get_did_approval_info`): [2](#0-1) 

The uncurry logic that parses any NFT's current on-chain state, however, reads the `current_owner` field directly out of the curried puzzle arguments with no cryptographic or announcement-based verification: [3](#0-2) 

And the wallet's coin-identification path (`NFTWallet.identify`) falls back to this raw curried value whenever the current spend's solution does not carry an explicit `-10` reset condition: [4](#0-3)

`get_new_owner_did()` only returns a value when the spend's solution contains a `-10` condition; if a minter simply curries a DID id at genesis and never emits a `-10` condition on the eve spend, `parsed_did_id` is `None` and the code falls back to `old_did_id = uncurried_nft.owner_did` — the attacker-forged curried value — treating it as the NFT's legitimate DID owner: [5](#0-4) 

Because the CLVM ownership-layer puzzle places no restriction on what value may be curried as `current_owner` for a freshly launched singleton, and the wallet-side parser treats that curried value as authoritative absent an explicit reset condition, a malicious minter can forge an association with any DID (e.g. impersonating a well-known collection or creator's DID) without that DID's owner ever spending a coin, creating an announcement, or otherwise authorizing the link. This is directly analogous to the reported APISIX flaw: an unauthenticated identity value is relayed downstream (into `owner_did`/`minter_did`, RPC responses via `nft_get_nfts`, DID-based NFT wallet auto-assignment, and offer `driver_dict` "also"/"owner" metadata) and treated by consumers as an authenticated claim of higher-trust identity/provenance.

### Impact Explanation
Any wallet, marketplace, or offer counterparty that inspects `owner_did`/`minter_did` (surfaced via `nft_get_nfts`/`get_nft_info` RPCs, or embedded offer `driver_dict` metadata) as a provenance/authenticity signal can be deceived into believing an NFT is genuinely associated with/endorsed by a specific DID identity, when no such authorization ever occurred. This enables forged-provenance fraud: an attacker can mint counterfeit NFTs that masquerade as belonging to a trusted DID (brand/collection/creator), auto-populate them into a victim's DID-labeled NFT wallet (`NFTWallet.identify` associates by matching `did_wallet.did_id == new_did_id` even though the DID coin was never touched), and use that forged provenance to defraud offer counterparties in NFT trades. This maps to the "forged asset identity" impact bucket.

### Likelihood Explanation
Exploitation requires only crafting a custom eve-NFT coin spend (bypassing Chia's official `generate_new_nft`) that curries the ownership layer's `current_owner` to an arbitrary DID id and omits the `-10` reset condition — fully achievable by any unprivileged spend-bundle submitter with no special keys, no cooperation from the impersonated DID owner, and no consensus-layer restriction preventing it (the CLVM ownership-layer mod does not gate the curried owner field at genesis).

### Recommendation
Do not trust a curried `owner_did`/`current_owner` value from an NFT's own puzzle reveal as proof of DID authorization. Wallet and RPC consumers should only report an NFT as "DID-owned" when the mint or transfer chain contains a verifiable, on-chain DID coin spend + matching announcement (the same mechanism already implemented in `WalletStateManager.get_minter_did`, which walks back to the actual DID coin spend rather than trusting the curried field). Apply this same verified-lineage check consistently in `NFTWallet.identify()`/`puzzle_solution_received()` instead of falling back to `uncurried_nft.owner_did` when no `-10` condition is present, and clearly mark `owner_did`/`minter_did` as unverified in any RPC/offer-facing metadata unless backed by a checked DID-coin announcement.

### Proof of Concept
1. Attacker crafts a launcher + eve NFT coin spend using `create_ownership_layer_puzzle`/`construct_ownership_layer` (or raw CLVM) with `current_owner` curried directly to `DID_X` (a real, well-known DID the attacker does not control), and does not include a `-10` condition in the eve spend's solution.
2. Attacker submits the resulting spend bundle to the mempool/full node as a normal, unprivileged transaction; it passes standard mempool/consensus validation since the ownership layer puzzle imposes no restriction on the initial curried owner.
3. Any wallet that syncs this coin (via `NFTWallet.identify()`/`puzzle_solution_received()`) computes `old_did_id = uncurried_nft.owner_did == DID_X` and, finding no `-10` reset condition, sets `new_did_id = DID_X`, associating/reporting the NFT as DID_X-owned via `nft_get_nfts`/`get_nft_info` RPCs and (if the local wallet holds DID_X) auto-adds it to that DID's NFT wallet — with no coin spend or announcement ever having been made by DID_X's actual owner.

    async def get_did_approval_info(
        self,
        nft_ids: list[bytes32],
        action_scope: WalletActionScope,
        did_id: bytes32 | None = None,
    ) -> bytes32:
        """Get DID spend with announcement created we need to transfer NFT with did with current inner hash of DID

        We also store `did_id` and then iterate to find the did wallet as we'd otherwise have to subscribe to
        any changes to DID wallet and storing wallet_id is not guaranteed to be consistent on wallet crash/reset.
        """
        if did_id is None:
            did_id = self.did_id
        did_inner_hash: bytes32
        for _, wallet in self.wallet_state_manager.wallets.items():
            self.log.debug("Checking wallet type %s", wallet.type())
            if wallet.type() == WalletType.DECENTRALIZED_ID:
                self.log.debug("Found a DID wallet, checking did: %r == %r", wallet.get_my_DID(), did_id)
                if bytes32.fromhex(wallet.get_my_DID()) == did_id:
                    self.log.debug("Creating announcement from DID for nft_ids: %s", nft_ids)
                    await wallet.create_message_spend(
                        action_scope, extra_conditions=(CreatePuzzleAnnouncement(id) for id in nft_ids)
                    )
                    did_inner_hash = wallet.did_info.current_inner.get_tree_hash()
                    break
        else:
            raise ValueError(f"Missing DID Wallet for did_id: {did_id}")
        return did_inner_hash

def get_new_owner_did(unft: UncurriedNFT, solution: Program) -> Literal[b""] | bytes32 | None:
    conditions = unft.p2_puzzle.run(unft.get_innermost_solution(solution))
    new_did_id: Literal[b""] | bytes32 | None = None
    for condition in conditions.as_iter():
        if condition.first().as_int() == -10:
            # this is the change owner magic condition
            atom = condition.at("rf").as_atom()
            if atom == b"":
                new_did_id = b""
            else:
                new_did_id = bytes32(atom)
    return new_did_id
