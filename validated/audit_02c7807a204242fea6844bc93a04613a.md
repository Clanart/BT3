## Title
Webhook shop attribution relies on an unsigned header, letting a merchant forge cross-shop webhook actions - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates an incoming webhook purely by HMAC-signing the raw request **body**. The `shop_domain` helper that the gem tells app developers to use for tenant scoping reads a **separate, unsigned** HTTP header (`X-Shopify-Shop-Domain`) that is never included in the HMAC computation. Because the signature and the tenant identifier are decoupled, any merchant who legitimately receives a validly-signed webhook for their own shop can replay that exact body to the app with a different `X-Shopify-Shop-Domain` header and have the app act on/for an unrelated shop.

### Finding Description
`hmac_valid?` in `PayloadVerification` computes the HMAC only over `request.raw_post`: [1](#0-0) 

`WebhookVerification#verify_request` gates the controller solely on that body-HMAC check, and separately exposes `shop_domain`, which is read straight from a request header with no cryptographic binding to the verified body: [2](#0-1) 

The gem's own documentation instructs developers to use this unsigned `shop_domain` value as the tenant key when dispatching background jobs from a custom webhook controller: [3](#0-2) 

The generated declarative-webhook controller template follows the same pattern, taking the shop attribution from the request rather than from anything bound to the signature: [4](#0-3) 

Because `X-Shopify-Shop-Domain` is not part of the signed payload, a merchant who has installed the app receives genuine `(raw_body, HMAC)` pairs for events on their own shop (the HMAC secret is the app's shared client secret, identical for every shop using the app — not shop-specific). That merchant can resend the identical, still-valid `(body, hmac)` pair to the webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `verify_request` still passes because it only checks the body/secret, and every downstream consumer that follows the documented pattern (`shop_domain` helper, or the generator template's `webhook_request.shop`) will attribute the action to the attacker-chosen shop instead of the shop that actually produced the body.

This is directly analogous to the Yieldy `burn()` issue: a trusted/verified mechanism (HMAC "role") is allowed to act against an arbitrary target identity (`shop_domain`) that isn't actually scoped/bound to the authorization check performed.

### Impact Explanation
An app that follows the shopify_app gem's documented pattern for custom webhook controllers (or the generator-produced declarative webhook controllers) can be tricked into running background jobs, updating records, or taking any shop-scoped action against a shop the attacker does not control, using a webhook body the attacker does control (from their own legitimate installation). This is a cross-shop/cross-tenant action performed via an accepted forged request — the signature verification succeeds, but the identity used to route the action was never covered by that signature.

### Likelihood Explanation
Reachable by any merchant that has the target app installed (an "unrelated merchant" from the perspective of any other shop using the same app) — no host-operator or developer-only access is required. All they need is one genuine webhook delivery to capture a valid `(raw_body, hmac)` pair and the ability to send an HTTP POST to the app's webhook endpoint with a modified header, which is trivial. Any app author who implements a custom webhook controller by following the gem's documented `shop_domain` usage, or who uses the `add_declarative_webhook` generator, inherits this weakness.

### Recommendation
Do not derive shop attribution from an unsigned header. Either:
- Include the shop domain (and other identifying fields) in the HMAC-signed material, verifying it as part of `hmac_valid?`, or
- Derive the shop strictly from the verified webhook body payload (fields that are part of the signed JSON), never from `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]` alone, and cross-check that the header value matches the shop encoded in the verified body before use.
- Update `docs/shopify_app/webhooks.md` and the declarative webhook generator template to stop recommending/relying on the unauthenticated `shop_domain` header for tenant scoping.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker.myshopify.com`) and triggers a webhook-eligible event (e.g. `carts/update`).
2. Shopify sends the app a POST with `raw_post = BODY` and header `X-Shopify-Hmac-Sha256 = HMAC(secret, BODY)` plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `BODY` and the valid `HMAC` value (they own the endpoint traffic or can reproduce it themselves by re-triggering events).
4. Attacker sends their own POST to the app's webhook endpoint with the exact same `BODY` and `HMAC` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `WebhookVerification#verify_request` → `hmac_valid?(BODY)` succeeds (body/secret unchanged).
6. The controller (following the documented pattern) calls `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)`, where `shop_domain` returns `"victim.myshopify.com"` — the job now executes attacker-controlled webhook data attributed to the victim shop.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
