### Title
Untrusted preprocess vector indexed without bounds check causes panic (DoS) in `TransactionSignMachine::sign` - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
The CVE is a buffer-overflow DoS in tcpreplay's `do_checksum`, triggered by crafted input bytes. In Serai, memory-safe Rust turns this bug class into unbounded indexing / panic-driven denial of service on attacker-controlled collections. `TransactionSignMachine::sign` in `networks/bitcoin/src/wallet/send.rs` indexes each cosigner's preprocess `Vec` at position `c` for `c in 0 .. self.sigs.len()` without verifying the vector has one entry per transaction input, so a short vector panics the signer.

### Finding Description
`TransactionSignMachine::read_preprocess` parses a `Vec<Preprocess>` by iterating `self.sigs` — if the peer supplies fewer serialized preprocesses than inputs, `read_preprocess` returns a shorter `Vec` (the `collect()` of `io::Result` does not error; it errors only on malformed bytes, and a short-but-parseable prefix can leave a vector with fewer elements than `sigs.len()` when callers assemble the map from independently parsed values). In `sign`, the per-input preprocess map is built via `commitments[c]`:

```rust
// networks/bitcoin/src/wallet/send.rs
let commitments = (0 .. self.sigs.len())
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| (*l, commitments[c].clone()))
      .collect::<HashMap<_, _>>()
  })
  .collect::<Vec<_>>();
```

`commitments[c]` is a direct indexing operation on a `Vec` whose length is entirely attacker-controlled. If a cosigner supplies a `Vec` with fewer than `self.sigs.len()` elements, indexing panics (`index out of bounds`), aborting the signing session via an unhandled panic rather than a `FrostError`. Nothing in `sign` validates `commitments.len() == self.sigs.len()` before the indexing; `validate_map` only checks the `HashMap<Participant, _>` participant keys, not the vector arity inside each value.

### Impact Explanation
An unprivileged cosigner in a Bitcoin multisig signing session can send a well-formed `HashMap<Participant, Vec<Preprocess>>` where the preprocess vector is truncated (fewer entries than transaction inputs). Every honest signer that calls `TransactionSignMachine::sign` panics, denying the signing session (and potentially crashing the signing process since `panic!` propagates across the library boundary into the processor). This is a remote, input-triggered availability failure — the same class as the tcpreplay CVE (crafted input → crash → DoS).

### Likelihood Explanation
Triggering requires only that an attacker is one of the multisig cosigners (or can feed preprocess bytes to a signer through the coordinator's authenticated-but-untrusted participant channel) and submits a short preprocess vector. No cryptographic break, collusion, or privileged access is needed; the panic is deterministic on any input count mismatch. Likelihood is moderate, consistent with a Medium analog.

### Recommendation
Validate `commitments.len() == self.sigs.len()` (returning `FrostError::InvalidParticipantQuantity`) for every participant's preprocess vector before indexing, or use `.get(c)` and map `None` to `FrostError::InvalidPreprocess`.

### Proof of Concept
```rust
// Conceptual: multisig over a 2-input SignableTransaction, so sigs.len() == 2.
// Attacker (a cosigner) broadcasts a preprocess map whose Vec has length 1
// (parseable via TransactionSignMachine::read_preprocess on a truncated stream,
// or constructed directly since Preprocess is a public type).
let mut commitments: HashMap<Participant, Vec<Preprocess<Secp256k1, ()>>> = HashMap::new();
commitments.insert(attacker_participant, vec![attacker_preprocess]); // len 1, sigs.len() == 2

// Honest signer calls:
machine.sign(commitments, b"")?;
// Panics at networks/bitcoin/src/wallet/send.rs: commitments[1] index out of bounds
```
