### Title
Spoofable cross-chain module authentication via `instance()` fallback in `IntentGatewayV2.authenticate()` allows unauthorized escrow release - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` authenticates incoming Hyperbridge messages (used to gate escrow release/refund logic) by comparing the claimed sender module address against `instance(request.source)`. Unlike the canonical implementation in `IntentsBase._instance()` (which reverts on an unregistered chain), the Tron `instance()` function falls back to returning `address(this)` when no gateway is registered for the source chain. Because `request.from` is an attacker-controlled field on the *origin* chain's dispatch, an attacker can spoof `from = address(thisGateway)` from any chain that Hyperbridge tracks but that has no registered `_instances` entry, causing `authenticate()` to pass trivially.

### Finding Description
`authenticate()` and `instance()` are defined at [1](#0-0) :

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

The intent of this check is: "trust an incoming message only if it comes from a *known, registered* peer IntentGateway instance." However, `instance()`'s fallback silently substitutes `address(this)` (the destination gateway's own address) whenever `_instances[keccak256(source)]` is unset. Since `request.from` is fully controlled by whoever dispatches the ISMP POST request on the *source* chain (any Hyperbridge-tracked state machine, not necessarily a registered IntentGateway peer), an attacker can:

1. Dispatch a POST request from any state machine ID that this gateway instance has not registered as a known peer (`_instances[keccak256(sourceId)] == address(0)`).
2. Set `request.from = bytes20(address(destinationGateway))`.
3. `instance(request.source)` returns the fallback `address(this)` == `destinationGateway`, matching `module`, so `authenticate()` passes.

This directly contrasts with the safe equivalent in the shared base used elsewhere, which reverts instead of falling back: [2](#0-1) . The Tron contract's divergent, unsafe re-implementation is the local analog of the missing-permission-check bug class in the report: a security-critical identity check silently defaults to an accepting value instead of rejecting.

`authenticate()` gates the message kinds that release escrowed funds, i.e. `RedeemEscrow`/`RefundEscrow`, which invoke `_withdraw()` to transfer escrowed tokens to an attacker-supplied beneficiary, as defined in the shared escrow-release logic: [3](#0-2) .

### Impact Explanation
An attacker who can dispatch an ISMP request from any Hyperbridge-tracked but unregistered source chain can forge a `RedeemEscrow`/`RefundEscrow` message that passes `authenticate()`, then have the gateway release escrowed order funds to an attacker-chosen beneficiary and token amount. This is a direct fund-theft / unauthorized-execution primitive: no relayer, prover, or admin compromise is required — only the ability to dispatch a message from a chain Hyperbridge already routes proofs for, which any unprivileged user can do by deploying a trivial dispatcher contract there. This matches the bounty's "stealing or loss of funds," "unauthorized transaction or execution," and "false proof/state acceptance via wrong module binding" categories.

### Likelihood Explanation
Likelihood is high for any deployment of this Tron variant that has multiple registered chains but not a fully-populated `_instances` map for every chain Hyperbridge supports (a very likely real-world scenario, since instances are added incrementally via governance `NewDeployment` messages). Any state machine not yet registered as a peer instance becomes an attack vector, and the exploit requires no special privileges — just standard ISMP dispatch capability from an arbitrary origin chain.

### Recommendation
Change `instance()` to revert (or otherwise fail closed) when no gateway is registered for the given state machine, mirroring `IntentsBase._instance()`'s `UnknownInstance` revert, instead of falling back to `address(this)`. `authenticate()` should never treat "unregistered" as equivalent to "trusted local address."

### Proof of Concept
1. Governance registers `IntentGatewayV2` instances on chains A and B only (`_instances[A]`, `_instances[B]` populated); chain C is a chain Hyperbridge tracks (consensus/state proofs supported) but has no registered `IntentGateway` instance.
2. A user places a legitimate order on chain B, escrowing tokens in the destination gateway on chain A, generating commitment `C1`.
3. Attacker deploys a minimal ISMP-dispatching contract on chain C and dispatches a POST request to the chain-A gateway with:
   - `request.source = C` (unregistered)
   - `request.from = bytes20(address(gatewayOnA))` (spoofing the destination gateway's own address)
   - `body = RequestKind.RedeemEscrow || abi.encode(WithdrawalRequest{commitment: C1, beneficiary: attacker, tokens: escrowedTokens})`
4. When the message is relayed and `onAccept` is invoked on chain A, `authenticate()` calls `instance(C)`, which returns `address(this)` (the fallback) since chain C is unregistered; this equals `module` (also `address(this)`, spoofed by the attacker), so the check passes.
5. `_withdraw()` releases the escrowed tokens for commitment `C1` to `attacker` instead of the rightful solver/beneficiary, and marks the order filled — a full theft of escrowed funds with no bypass of any other check.
