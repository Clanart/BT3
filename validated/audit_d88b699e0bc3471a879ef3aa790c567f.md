### Title
Out-of-range `sender`/`recipient` index causes panic in PedPoP blame evaluation - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Analog of CVE-2015-9100 (NULL-deref / crash on crafted input): `BlameMachine::blame` / `AdditionalBlameMachine::blame` dereference `self.commitments[&sender]` with an attacker-chosen `Participant` index. `Participant` permits any nonzero `u16` (`Participant::new`, crypto/dkg/src/lib.rs:29-35), but `commitments` only contains keys `1..=n` (populated in `verify_r1` at crypto/dkg/pedpop/src/lib.rs:313-332 and `AdditionalBlameMachine::new` at lines 656-660). A sender index `> n` hits the HashMap `Index` impl and panics, crashing the blaming party — a Rust equivalent of the crafted-input crash in `fill_buffer_resample`.

### Finding Description
`blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609) takes `sender` and `recipient` directly from caller input. After `decrypt_with_proof` succeeds — which an attacker can satisfy by producing a legitimately signed `EncryptedMessage` (they control `key`/`pop` since `EncryptedMessage::read` accepts arbitrary bytes and the PoP is only bound to `from`, per `pop_challenge` usage in crypto/dkg/pedpop/src/encryption.rs:210-214) — execution reaches:

```rust
if !bool::from(
  multiexp_vartime(&share_verification_statements::<C>(
    recipient,
    &self.commitments[&sender],   // lib.rs:599 — panics if sender ∉ commitments
    Zeroizing::new(share),
  ))
  .is_identity(),
) {
```

Neither `BlameMachine::blame` nor `AdditionalBlameMachine::blame` validates that `sender`/`recipient` ∈ `1..=n` before this lookup. `AdditionalBlameMachine::new` even documents itself as usable "regardless of if the caller was a member in the DKG protocol" (lib.rs:639-648), yet only inserts `Participant::new(i)` for `i in 1..=n`. Note `recipient` is only used as the interpolation scalar argument and a transcript value, so it cannot panic; the panic is specifically via `sender` indexing.

### Impact Explanation
An unprivileged party submitting a blame/accusation with `sender` set to a valid `Participant` index outside the DKG set (e.g., `n + 1`, up to 65535) triggers a panic inside `multiexp_vartime(&share_verification_statements::<C>(recipient, &self.commitments[&sender], ...))`, crashing the evaluating node rather than returning an error. In a Tributary/DKG context where blame transactions are deserialized with attacker-controlled participant fields (cf. `Transaction::InvalidDkgShare` reading arbitrary `Participant` values in coordinator/src/tributary/transaction.rs), this is a remotely reachable denial of service — the same availability-impact class as the LAME NULL dereference.

### Likelihood Explanation
Medium, matching the source advisory: triggering requires the blamed-message signature/proof path to reach line 599, which means supplying a well-formed `EncryptedMessage` — feasible for the sender themselves (they can encrypt and sign a share addressed to a fabricated index) or any party relaying one. The input (`Participant`) is fully attacker-controlled bytes; no collusion or secret knowledge is needed.

### Recommendation
In `blame_internal` (and/or at the entry of `BlameMachine::blame` / `AdditionalBlameMachine::blame`), validate `sender` and `recipient` against the known participant set — e.g., `self.commitments.get(&sender).ok_or(...)`-style handling, or reject `u16::from(sender) > n` — returning `sender` as faulty (or a dedicated error) instead of indexing. A defensive fix is to use `self.commitments.get(&sender)` and treat a missing entry as sender-fault rather than panicking.

### Proof of Concept
