Based on my investigation, I found a structural analog to the CVE-2018-10918 bug class (an unchecked nil/null result from a database/store lookup being dereferenced, causing a crash reachable by an authenticated actor) in Sei's Cosmos-tx ante pipeline.

### Title
Unchecked nil AccountKeeper.GetAccount() result dereferenced in ante-handler signer processing - ([File: app/ante/cosmos_checktx.go])

### Summary
`UpdateSigners` in the Cosmos (non-EVM) CheckTx/DeliverTx ante path fetches each tx signer's account via `accountKeeper.GetAccount(ctx, signer)` — which returns a typed nil when the address has no stored account — and immediately dereferences it (`acc.SetSequence(...)`, `acc.GetPubKey()`) without a nil check, mirroring the identical pattern in the EVM signer-association decorator.

### Finding Description
`sdk.AccountKeeper.GetAccount` explicitly returns `nil` when the key is absent from the store: [1](#0-0) . `UpdateSigners`, called from `CosmosCheckTxAnte`/`CosmosDeliverTxAnte` for every signer of a Cosmos transaction, calls this exact lookup and immediately dereferences the result: [2](#0-1) . The same unguarded pattern — `acc := p.accountKeeper.GetAccount(ctx, signer); if acc.GetPubKey() == nil { ... }` — also exists in the EVM address-association decorator used on the main (non-legacy) ante path: [3](#0-2) .

In the pipeline this decorator sits in (`app/ante.go`), the only account existence guarantee upstream comes from `DeductFeeDecorator`, which only validates the **fee payer's** account, not every signer returned by `tx.GetSigners()`: [4](#0-3) . For any Cosmos message type that requires multiple signers (e.g. multi-signer bank/gov/IBC messages) where a non-fee-payer signer address has never had funds sent to it or an account otherwise created on-chain, `GetAccount` for that address returns `nil` at this point in the pipeline, and the subsequent field access panics with a nil pointer dereference.

### Impact Explanation
A panic thrown mid-ante-handler that is not cleanly recovered as a normal tx-validation error can crash node processing of that transaction/block; if this occurs during `DeliverTx`/`FinalizeBlock` rather than being fully contained by `CheckTx`'s recovery middleware, it risks validator liveness/halt for that block, which the validation rules classify as a "crash of default-configuration node" or "validator halt" impact class.

### Likelihood Explanation
Reachability depends on whether earlier ante decorators (`SetPubKeyDecorator` / `GetSignerAcc`) unconditionally reject any signer whose account does not yet exist, in which case this code path is unreachable in practice. I could not fully verify `GetSignerAcc`'s implementation before running out of investigation budget — I confirmed the call site and the vulnerable pattern in two independent locations, but not the exact upstream gating logic in `sei-cosmos/x/auth/ante/sigverify.go`. This is a material gap: if `GetSignerAcc` (unlike the standard upstream cosmos-sdk behavior) creates/returns a non-persisted in-memory account rather than erroring for a never-seen address, or if any Cosmos message type allows a secondary signer to be a fresh address, this becomes trivially and remotely triggerable by a single crafted transaction.

### Recommendation
Add explicit nil checks after every `accountKeeper.GetAccount(ctx, addr)` call before dereferencing the result — specifically in `UpdateSigners` (`app/ante/cosmos_checktx.go`) and `EVMAddressDecorator.AnteHandle` (`x/evm/ante/preprocess.go`) — returning a normal `sdkerrors.ErrUnknownAddress`-style ante error instead of allowing a panic, consistent with how `chargeFees` already guards the fee-payer lookup at `app/ante/cosmos_checktx.go:354-357`.

### Proof of Concept
Not conclusively demonstrable from static analysis alone: I was unable to confirm within the available tool budget whether any Cosmos message type accepted by this chain (i) requires more than one signer and (ii) allows a signer address that has never previously received funds/appeared on-chain to pass `SetPubKeyDecorator`/`GetSignerAcc` without persisting an account first. If this gate does not hold for at least one signer position, submitting such a multi-signer transaction to `CheckTx`/`DeliverTx` would trigger the nil dereference in `UpdateSigners`. I recommend a Devin session with full code/test access to trace `GetSignerAcc` in `sei-cosmos/x/auth/ante/sigverify.go` and enumerate which registered `Msg` types can produce a multi-signer transaction with an unfunded secondary signer, to confirm or rule out concrete exploitability before treating this as verified.
