### Title
Webhook shop identity is spoofable because HMAC verification never binds `X-Shopify-Shop-Domain` to the signed payload - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` authenticates a webhook request purely by validating an HMAC over the raw request body against the app's shared client secret. The shop identity used to route/process that webhook (`shop_domain`) is read directly from the `X-Shopify-Shop-Domain` request header, which is never included in the HMAC computation. Because the same client secret is shared by every shop that installs the app, any actor who controls a legitimate installed shop can obtain a validly-signed webhook body and resend it with a forged `X-Shopify-Shop-Domain` header naming a different (victim) shop, and the app will accept and process it as if it came from that victim shop.

### Finding Description
`PayloadVerification#hmac_valid?` computes the digest solely over `data` (the raw POST body) and the app's `secret`/`old_secret`: [1](#0-0) 

`WebhookVerification#verify_request` uses only this body-based HMAC check as its `before_action`, and separately exposes `shop_domain` sourced straight from the request header, with no cryptographic relationship to the verified HMAC: [2](#0-1) 

The gem's own generated controllers and jobs use exactly this unauthenticated `shop_domain`/`shop` value to look up and act on shop records, e.g. the app-uninstalled job destroys the shop found by that domain, and shop-redact job runs shop-scoped session logic keyed by it: [3](#0-2) [4](#0-3) 

The recommended custom-controller pattern in the docs reinforces the same unauthenticated binding of `shop_domain` to job dispatch: [5](#0-4) 

Because `secret`/`old_secret` are app-level (not per-shop) values, and the HMAC only covers the body, the identity ("who this webhook is about") is never actually authenticated - it is trusted from a plain header. This is the same root cause as the reported `PledgeManager::pledge` bug: a signature/authorization check succeeds, but the entity the action is performed "on behalf of" (`data.signer` there, `shop_domain` here) is taken from an unverified, attacker-controllable value instead of being cryptographically bound to what was verified.

### Impact Explanation
Any party that can install the app on their own shop (an "unrelated merchant" relative to any specific victim shop) can:
1. Trigger/receive a legitimate webhook for their own shop, which comes with a body and a valid `X-Shopify-Hmac-Sha256` signed using the shared app secret.
2. Replay that exact request to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to an arbitrary victim shop's domain.
3. Since HMAC validation never inspects the header, the request is accepted as authentic, and the app processes it as data/events pertaining to the victim shop.

Depending on which webhook jobs are wired up, this enables cross-shop consequences ranging from disclosure/misprocessing of forged shop-scoped data to destructive actions - e.g., forging an `app/uninstalled` webhook against a victim shop domain causes `AppUninstalledJob` to `shop.destroy` the victim's stored session/shop record (removing their installation state) using only a header the attacker controls, without any interaction from the victim.

### Likelihood Explanation
Likelihood is high for any shopify_app-based app that relies on the documented/generated `shop_domain` handling (which is the default and recommended pattern shown in the gem's own docs and generators). The only prerequisite is that the attacker can install the app on any shop they control (a normal, unprivileged path) in order to obtain one validly-signed webhook body/HMAC pair, and can then send arbitrary HTTP requests to the app's public webhook endpoint with a modified header - no secret leakage, no code execution, and no special privileges relative to the victim shop are required.

### Recommendation
Bind the shop identity into the authenticated verification step instead of trusting the header value independently:
- Prefer deriving/validating `shop_domain` from data that is itself covered by the HMAC (e.g., via `ShopifyAPI::Webhooks::Request`/`Registry.process`, which is designed to validate topic/shop consistently with the payload), or
- If a custom controller must read `X-Shopify-Shop-Domain` directly, verify that the shop named in that header actually has a webhook registered/expected for the given topic and reject mismatches, and/or additionally verify per-shop expectations (e.g., confirm the shop is currently installed and cross-check against Shopify's webhook `X-Shopify-Webhook-Id`/topic metadata) before using it to key destructive or data-returning operations.
- At minimum, document this limitation clearly wherever `shop_domain` is used in generated jobs, and avoid using it directly for irreversible actions (like `shop.destroy`) without an additional authenticated check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, then triggers an `app/uninstalled` webhook for that shop (e.g. by uninstalling the app), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header sent by Shopify.
2. Attacker resends this exact body and HMAC header to the app's `/webhooks/app_uninstalled` (or equivalent) endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which succeeds because the body was not altered and the secret is shared across shops.
4. The controller/job reads `shop_domain` from the (forged) header and calls `Shop.find_by(shopify_domain: "victim-shop.myshopify.com").destroy`, as shown in `app_uninstalled_job.rb.tt`, deleting the victim's stored session/installation despite them never uninstalling the app.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
