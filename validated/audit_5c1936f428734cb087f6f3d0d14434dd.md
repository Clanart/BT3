### Title
Broken forfeiture calculation permanently zeroes out early-exit penalties on mWOMSV rewards - (File: `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` is supposed to compute what portion of a user's accrued reward must be forfeited (and redistributed to remaining stakers) based on the user's `mWomSV` lock/cooldown state, mirroring the "rewardable percent" logic defined for lock slots elsewhere in the protocol (`getRewardablePercentWAD`). Instead, the function contains dead arithmetic that always evaluates the forfeit to zero, regardless of a user's actual lock status.

### Finding Description
`_calExpireForfeit` is defined as: [1](#0-0) 

The function sets `rewardableAmount = _amount` unconditionally, then computes `forfeitAmount = _amount - rewardableAmount`, which is always `0`. The subsequent `if (forfeitAmount < (_amount / 1000))` branch is unreachable in any meaningful sense — it always re-confirms `forfeitAmount = 0`. There is no reference anywhere in this function to the account's actual lock/cooldown percentage, unlike the analogous `getRewardablePercentWAD` proportional-lock computation defined for `mWomSV` lock slots: [2](#0-1) 

This forfeit value is consumed directly during reward payout in `_sendReward`, which is invoked whenever an ordinary staker calls `getReward`/claims from this reward pool: [3](#0-2) 

Because `_calExpireForfeit` always returns `0`, the `toSend = userRewards[...] - forfeitAmount` line always sends the full accrued reward, and the `forfeitAmount > 0` branch that would call `_queueNewRewardsWithoutTransfer` (redistributing the forfeited portion back into `rewardPerTokenStored` for the benefit of remaining stakers) never executes. This is the same class of flaw described in the report: fractional/shares-based penalty math (a stand-in for "shares" of a forfeitable amount) is not computed from the correct proportional state and is instead always treated as if the user holds 100% "rewardable" share, silently discarding the intended forfeiture-and-redistribution mechanism.

### Impact Explanation
The mWOMSV lock/forfeit system exists to penalize users who exit their lock early and to socialize that penalty as extra yield to users who remain locked. With this logic broken, that socialized yield is permanently and unconditionally never generated — remaining long-term lockers are permanently deprived of yield that the protocol design entitles them to, satisfying "theft or permanent freezing of unclaimed yield" for honest stakers. Every early exit that should be penalized instead pays out 100% of accrued rewards, which is a deterministic, unconditional, and permanent loss of the redistributive yield stream for the remainder of the mWOMSV staker pool.

### Likelihood Explanation
This triggers on every single call to `getReward`/`_sendReward` for the mWOMSV reward pool — there is no special precondition, race, or opt-in required. Any unprivileged wallet holding mWOMSV rewards can call the standard claim path, and the forfeiture will unconditionally be zero every time, making this a deterministic, always-active flaw rather than an edge case.

### Recommendation
Implement `_calExpireForfeit` to actually use the account's lock/cooldown proportion (e.g., via `ILocker(mWomSV).getRewardablePercentWAD(_account)`) to compute `rewardableAmount = _amount * rewardablePercent / 1e18`, so that `forfeitAmount = _amount - rewardableAmount` reflects genuine early-exit penalties, and ensure the redistribution path (`_queueNewRewardsWithoutTransfer`) is exercised as originally intended.

### Proof of Concept
1. An account with `_amount` of pending `mWOMSV` rewards (regardless of lock/cooldown state) calls `getReward`/triggers `_sendReward` in `rewards/mWOMSVBaseRewarder.sol`.
2. `_sendReward` calls `_calExpireForfeit(_account, userRewards[_rewardToken][_account])`.
3. Inside `_calExpireForfeit`, `rewardableAmount` is set equal to `_amount` before any comparison against lock state, forcing `forfeitAmount = 0` in all cases.
4. `toSend = userRewards[...] - 0` transfers the full reward to the user; the `forfeitAmount > 0` branch that redistributes forfeited rewards to remaining lockers is never triggered.
5. Repeat for any number of accounts/exits — the forfeiture-and-redistribution yield stream to remaining `mWomSV` lockers never accrues, permanently freezing/losing that yield for them. [1](#0-0) [3](#0-2)

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
