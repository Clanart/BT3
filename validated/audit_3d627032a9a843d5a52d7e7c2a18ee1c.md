### Title
`JsonParser.MergeAny()` throws uncaught `InvalidOperationException` instead of `InvalidProtocolBufferException` on attacker-controlled `@type` values, causing unhandled-exception DoS in ProtoJSON parsing - (File: `csharp/src/Google.Protobuf/JsonParser.cs`)

### Summary
The C# ProtoJSON parser's `Any` handler assumes that a valid-looking, attacker-controlled `@type` value will always resolve in the caller-supplied `TypeRegistry`. When it does not, the code throws `InvalidOperationException` rather than the library's documented parsing-failure exception (`InvalidProtocolBufferException`). This is the same bug class as the reported Solidity issue: a "safe"/parsing function assumes a particular shape of untrusted input and, when that assumption is violated, throws an exception type the caller does not expect/catch, causing the call to blow up instead of failing gracefully.

### Finding Description
`JsonParser.MergeAny()` is the well-known-type handler invoked whenever a `google.protobuf.Any` field is parsed from ProtoJSON: [1](#0-0) 

Inside it, once the `@type` string is read from the JSON, the type name is looked up via `settings.TypeRegistry.Find(typeName)`: [2](#0-1) 

- If `typeName` parses to an empty string (malformed URL), the code correctly throws `InvalidProtocolBufferException("Invalid Any.@type value")` — the intended "safe" failure path for bad input.
- However, if `typeName` is syntactically valid but simply is not present in the registry supplied via `JsonParser.Settings` (a scenario fully controllable by an attacker who can choose the `@type` string in the JSON payload being parsed), the code throws `InvalidOperationException` instead:
```
MessageDescriptor descriptor = settings.TypeRegistry.Find(typeName);
if (descriptor == null)
{
    throw new InvalidOperationException($"Type registry has no descriptor for type name '{typeName}'");
}
```
All other JSON-parsing error paths in this class consistently throw `InvalidProtocolBufferException`, which is the exception type application code is expected to catch when calling `JsonParser.Parse`/`Merge` on untrusted data (analogous to how ERC20 consumers expect `symbol()` to always return a string, never revert). By throwing `InvalidOperationException`, this function violates that invariant: any consuming application that catches `InvalidProtocolBufferException` around its JSON-parsing call (the normal, documented pattern) will not catch this exception, and it will propagate up as an unhandled exception.

The root cause mirrors the external report precisely:
- "assumes the return type... to be a string" ↔ the code assumes any syntactically valid `@type` URL will resolve to a known type in the registry.
- "abi.decode() will revert" ↔ `TypeRegistry.Find()` returning `null` causes a throw of an exception type outside the documented/expected contract.
- Root cause is one specific `if`/`throw` block, exactly like the single line cited in the original report.

### Impact Explanation
An ordinary client submitting bounded ProtoJSON containing an `Any` field with an `@type` value referencing a message type not registered in the application's `TypeRegistry` (e.g., a valid-looking but unregistered/unknown fully-qualified type name) causes `JsonParser` to throw `InvalidOperationException`. If the calling application's exception handling is written per the documented contract — i.e., it catches `InvalidProtocolBufferException` to reject malformed/untrusted JSON gracefully — this exception will not be caught, and will propagate as an unhandled exception. Depending on the hosting framework, this can crash a worker thread/request handler, causing a Denial of Service for that request path, and in single-threaded or fail-fast hosts it can bring down the whole process. This is a Medium-severity availability issue: it requires no privileged access, works with fully bounded/valid-schema input, and reliably triggers a divergence from the parser's documented failure contract on ordinary client input.

### Likelihood Explanation
Likelihood is high for any application that (a) exposes `JsonParser.Parse`/`Merge` to untrusted ProtoJSON containing `Any` fields, and (b) uses a `TypeRegistry` that does not contain every type an attacker might name in `@type` (which is the common case, since registries are typically populated only with types the application expects to receive). The attacker only needs to supply a syntactically valid type URL with a message name absent from the registry — a trivial, one-line JSON payload, no schema tampering, no privileged access, and no resource exhaustion required.

### Recommendation
In `MergeAny()`, when `settings.TypeRegistry.Find(typeName)` returns `null`, throw `InvalidProtocolBufferException` (consistent with the rest of the parsing error paths and with the documented exception contract of `JsonParser`), e.g.:
```csharp
if (descriptor == null)
{
    throw new InvalidProtocolBufferException($"Type registry has no descriptor for type name '{typeName}'");
}
```
This aligns the failure mode with all other malformed-input cases in the same method (missing `@type`, empty type name, non-string `@type` value), so that callers catching `InvalidProtocolBufferException` around JSON parsing reliably catch all classes of malformed/adversarial `Any` payloads.

### Proof of Concept
Given a `JsonParser` constructed with a `TypeRegistry` that does not include, say, `foo.bar.Unregistered`, parsing the following ProtoJSON into a message containing an `Any` field:
```json
{
  "any_field": {
    "@type": "type.googleapis.com/foo.bar.Unregistered",
    "value": {}
  }
}
```
drives execution to: [3](#0-2) 
`Any.GetTypeName("type.googleapis.com/foo.bar.Unregistered")` returns `"foo.bar.Unregistered"` (non-empty, so it passes the empty-type-name guard at line 560-563), then `settings.TypeRegistry.Find("foo.bar.Unregistered")` returns `null`, and the code throws `InvalidOperationException` rather than `InvalidProtocolBufferException`. A caller wrapping `JsonParser.Parse(...)` in `try { ... } catch (InvalidProtocolBufferException) { ... }` (the standard, documented pattern for handling malformed/untrusted JSON) will not catch this exception, resulting in an unhandled exception at the call site.
