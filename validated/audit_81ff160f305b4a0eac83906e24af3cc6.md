### Title
Unvalidated attacker-controlled `offset`/`output` pairing in `ReceivedOutput::read` lets untrusted bytes inject a falsified deposit that Serai reports as received but cannot spend - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report is a prototype-pollution bug: attacker-controlled field values (`influencer_field_name` containing `__proto__`) are merged into a trusted object, corrupting downstream behavior. The Serai analog is injection of attacker-controlled *fields* into a trusted structure via deserialization: `ReceivedOutput::read` accepts a caller-supplied scalar `offset` together with an arbitrary `TxOut`/`OutPoint`, with no check that `offset` actually corresponds to the key embedded in `output.script_pubkey`. The invariant `p2tr_script_buf(group_key + G*offset) == output.script_pubkey` is established only when the `Scanner` constructs the object, and is silently broken for any `ReceivedOutput` reconstituted from untrusted bytes.

### Finding Description
`Scanner::scan_transaction` only produces `ReceivedOutput`s whose `offset` genuinely yields the on-chain `script_pubkey` (`networks/bitcoin/src/wallet/mod.rs:199-214`). But `ReceivedOutput::read` (`mod.rs:122-134`) deserializes `offset = Secp256k1::read_F(r)` and then a consensus-decoded `TxOut` and `OutPoint` independently — nothing re-verifies the offset/script correspondence. `SignableTransaction::new` then consumes `inputs: Vec<ReceivedOutput>`, copying `input.offset` into `self.offsets` and `input.output` into `self.prevouts` (`networks/bitcoin/src/wallet/send.rs:175-185, 252-253`). The consistency check only happens later in `multisig()`, where `p2tr_script_buf(offset.group_key()) != prevouts[i].script_pubkey` returns `None` (`send.rs:275-279`) — meaning any accounting/crediting path that consumes a deserialized `ReceivedOutput` before signing will have already recorded value that is provably unspendable. ### Impact Explanation
An attacker who can supply serialized `ReceivedOutput` bytes (the task's own reachability model includes untrusted bytes fed to `ReceivedOutput::read`) can fabricate a deposit: choose any real on-chain `TxOut`/`OutPoint` paying to an address the attacker controls (or any script not equal to `key + G*offset`), pair it with a scanner-registered `offset`, and serialize. The victim records `value` as received funds attributable to the Serai key — e.g., crediting the depositor in a bridge flow — but the resulting `SignableTransaction` can never be signed (`multisig` returns `None`), so the reported funds are unspendable. This is the "funds reported received that are not spendable" acceptance criterion, and mirrors the report's pattern of untrusted fields polluting a trusted object to produce attacker-beneficial state.

### Likelihood Explanation
Reachability depends on an integrator path deserializing `ReceivedOutput` from attacker-influenced bytes (network messages, stored/replayed scan data, or cross-process transport); `read`/`write`/`serialize` are `pub` and explicitly designed for transport (`mod.rs:120-148`). No secret access, validator status, or collusion is required — only the ability to get the bytes parsed. Within Serai itself the scanner path is safe, so severity is Medium rather than High: the exploit requires the integrator-facing deserialize-then-credit flow rather than the local `scan_transaction` path.

### Recommendation
Either make the offset/script binding self-verifying or make the type impossible to misuse: (1) have `ReceivedOutput::read` take the group key (or return a separate `UncheckedReceivedOutput` type) and verify `p2tr_script_buf(key + G*offset) == output.script_pubkey` before yielding a spendable `ReceivedOutput`; or (2) store only the `script_pubkey`-derived offset index and re-derive `offset` from the `Scanner`'s `scripts` map on load, so the serialized form cannot carry a contradictory offset. At minimum, perform the `multisig()` consistency check in `SignableTransaction::new` so malformed inputs are rejected at construction rather than after funds are recorded.

### Proof of Concept
```rust
// Construct a falsified ReceivedOutput: a real TxOut paying to an
// attacker-controlled script, paired with a legitimate scanner offset.
let attacker_txout = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: p2tr_script_buf(attacker_key).unwrap(), // != key + G*offset
};
let forged = ReceivedOutput {
  offset: scanner_offset,          // e.g. OutputType::External offset (ZERO)
  output: attacker_txout,
  outpoint: real_outpoint,         // attacker-funded UTXO
};
let bytes = forged.serialize();

// Victim side: deserialization succeeds with no consistency check.
let received = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(received.value(), 1_000_000); // recorded as received funds

// The funds can never be spent: the multisig construction rejects the
// offset/script mismatch by returning None.
assert!(SignableTransaction::new(vec![received], &payments, change, None, FEE)
  .unwrap()
  .multisig(&keys)
  .is_none());
```

The fix follows directly from `send.rs:277`: the same `p2tr_script_buf(offset.group_key()) == script_pubkey` check must gate deserialization or input acceptance, not just multisig construction.

Caveat: I was unable to fully trace every caller that feeds network-controlled bytes into `ReceivedOutput::read` (processor-side usage appears limited to scanner-produced values). If no untrusted byte path reaches `read`, this degrades to a latent API-invariant bug rather than a directly exploitable one.

    let offset = Secp256k1::read_F(r)?;
    let output;
