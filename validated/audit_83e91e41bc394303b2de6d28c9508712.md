### Title
Divergent conflict-marker parsers let a crafted file silently misalign Copilot's hunk resolutions when writing merged content — (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The ERC4626 bug is fundamentally about two code paths that are supposed to stay in sync (the tracked share ledger and the raw `totalAssets()` reading) diverging because of an attacker-controlled side channel, with no cross-check before an unguarded rounding-down division silently destroys value. GitHub Desktop's Copilot merge-conflict resolver has a structurally similar pattern: the hunk count used to *validate* the model's per-hunk response is computed by one marker parser, while the hunk boundaries used to *splice the model's output back into the file on disk* are computed by a second, independently-written parser over the same untrusted content, with no reconciliation between the two.

### Finding Description
`buildConflictContext()` reads each conflicted file and calls `extractConflictHunks()` (app/src/lib/copilot-conflict-context.ts) to enumerate conflict hunks for the prompt. [1](#0-0) 

That parser requires the exact sequence ours-marker → (optional base) → separator → theirs-marker; if the closing `>>>>>>>` is never found (`hunkEnd === -1`) the whole partial block is silently dropped rather than counted as a hunk. [2](#0-1) 

The number of hunks this parser finds becomes the "expected" count that `validateResolutionPaths()` checks the model's response against: [3](#0-2) 

Separately, when the resolved content is written back to disk, `reassembleResolvedFile()` walks the *same raw file text* with its own, differently-coded lookahead: for each `<<<<<<<`-like line it scans forward for a separator and, independently, for a closing `>>>>>>>`-like line, using different loop semantics than `extractConflictHunks` (it doesn't require the separator to precede the closing marker in the same way, and it doesn't reject a block just because the closing marker check runs into another block first). [4](#0-3) 

Critically, the marker regexes are permissive: `^<{7}(?:\s|$)`, `^={7}$`, `^>{7}(?:\s|$)` match *any* line that begins with seven or more of those characters — not just canonical `<<<<<<< HEAD` git markers. [5](#0-4) [6](#0-5) 

Because a real git conflict inserts genuine markers into the file, and an attacker (via a cloned/fetched branch or PR they control) can also add *incidental* lines that happen to match these loose patterns elsewhere in the same file (e.g., a documentation separator, ASCII-art banner, or embedded example diff containing a run of `=======`, `<<<<<<<`, or `>>>>>>>`), the two parsers can disagree on where hunk boundaries start/stop or how many well-formed hunks exist. `reassembleResolvedFile()` then splices `hunkResolutions[hunkIndex]` into the wrong marker block purely by positional index, with no re-validation against the count `validateResolutionPaths()` already approved: [7](#0-6) 

Nothing recomputes or compares `extractConflictHunks()`'s count to `reassembleResolvedFile()`'s independently-discovered block count before the file is written and `git add`-ed: [8](#0-7) 

This mirrors the ERC4626 flaw precisely: a value trusted from one computation path (`extractConflictHunks` hunk count / the "expected" ledger) is used to validate an external input (the model's resolutions / the deposit), while a second, attacker-influenced computation path (`reassembleResolvedFile`'s independent marker scan / `totalAssets()`) is what's actually used when the write happens — and no guard checks that the two agree before the operation completes.

### Impact Explanation
If the two parsers disagree, `reassembleResolvedFile()` can insert a resolved hunk into the wrong location, or drop/duplicate marker blocks, without throwing any error. The corrupted file is then `git add`-ed and staged automatically as part of "Continue Merge" flow, meaning the user commits and potentially pushes code they never reviewed as-written — a silent corruption of what the user commits, which matches the stated valid-impact class ("silent corruption of what the user commits or pushes"). Because this happens inside a merge/rebase/cherry-pick conflict resolution that the user explicitly asked Copilot to handle, the corrupted region is exactly the part of the file they trust the tool to have gotten right.

### Likelihood Explanation
Triggering this requires an attacker who can influence the contents of a file that will conflict during a merge/rebase (e.g., contributing to a shared branch or opening a PR merged locally) and who can arrange for that same file to contain incidental long runs of `<`, `=`, or `>` characters that satisfy the loose regexes — a low-effort, content-only primitive requiring no special permissions beyond having code reviewed/merged/fetched into the repository, which fits "attacker controls a cloned/fetched repository." However, I was not able to dynamically execute the two parsers against a hand-crafted proof-of-concept file to confirm they produce different hunk counts/positions in practice — this assessment is based on static reading of the two independent implementations and their differing lookahead logic. This should be verified by unit-testing `extractConflictHunks` and `reassembleResolvedFile` against the same crafted fixture before treating this as confirmed rather than a plausible parser-divergence bug class.

### Recommendation
Use a single shared marker-scanning implementation (or one function producing an authoritative block list) for both `extractConflictHunks()` (prompt-building) and `reassembleResolvedFile()` (splicing), so hunk identification can never diverge. At minimum, have `reassembleResolvedFile()` recompute its discovered hunk count and hard-fail (falling back to manual resolution, never writing) if it doesn't exactly match the count already validated by `validateResolutionPaths()`, analogous to minting a fixed first-share amount rather than trusting an unguarded computed ratio.

### Proof of Concept
1. Create a repository file, e.g. `NOTES.md`, containing a long banner line consisting of exactly seven or more `=` characters used as a Markdown Setext-style underline (satisfies `separatorMarker`), located near where a real conflicting change will land.
2. On two branches, both modify a nearby line in `NOTES.md` so that merging produces a genuine `<<<<<<<`/`=======`/`>>>>>>>` conflict block adjacent to (but not identical to) the pre-existing `=======`-like banner line.
3. Merge the branches in Desktop and invoke "Resolve with Copilot."
4. Inspect (via debugger/logging) whether `extractConflictHunks()`'s hunk count for `NOTES.md` differs from the number of well-formed blocks `reassembleResolvedFile()` independently discovers when splicing the model's response back in — if they differ, the resolved content lands in a marker block other than the one it was generated for, and this corrupted file is silently staged by `_applyCopilotConflictResolutions()`.
Note: step 4 needs to be run/observed in an actual Desktop build to confirm divergence; this PoC describes how to reproduce and verify it, but I could not execute it directly in this read-only investigation.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }
