### Title
Clone always disables Git's built-in clone-protection check (`GIT_CLONE_PROTECTION_ACTIVE=false`), re-opening CVE-2024-32002-class recursive-clone file write outside the repo - ([File: app/src/lib/git/clone.ts])

### Summary
`clone()` unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment passed to `git clone --recursive`, explicitly disabling the safety check that upstream Git added specifically to stop malicious repositories from writing files outside the working tree during a recursive clone with submodules. [1](#0-0) 

### Finding Description
Git 2.45.1 introduced `core.protectHFS`/`core.protectNTFS`-adjacent hardening and the `GIT_CLONE_PROTECTION_ACTIVE` mechanism as the fix for CVE-2024-32002: a crafted repository containing a submodule whose path (via case-folding, `.git` symlink tricks, or nested-directory games) collides with the top-level `.git` directory can cause `git clone --recursive` to check out submodule hooks/files onto the containing repository's `.git` directory, resulting in remote code execution once a hook fires. Git's own default is to keep this protection active; the "protection active" gate is exactly what stops the attack. GitHub Desktop's `clone()` function builds the git-invocation environment by spreading `envForRemoteOperation(url)` and then explicitly overriding with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` before calling `git ... clone --recursive -- url path`. [2](#0-1) 

This is structurally the same bug class as the reported "hardcoded tolerance" issue: a security-relevant guard value is hardcoded to the permissive/unsafe setting instead of being conditional, configurable, or defaulted to the safe value, and the surrounding code path (`--recursive`, attacker-controlled `url`) is exactly the one the upstream protection was designed to cover. None of the other hardening present in this codebase — `isClonePathSensitive()` (destination path checks), `sanitizeCloneName()` (clone-name traversal sanitization) — inspects or restricts the *contents* of the cloned repository or its submodules, so nothing else in the call path substitutes for the disabled Git-level protection. [3](#0-2) [4](#0-3) 

### Impact Explanation
An attacker who controls the content of a repository (and its submodules) that a GitHub Desktop user clones — for example via "Open in Desktop" deep links (`x-github-client://openrepo/...`) which route straight into `clone()`, or a plain public/malicious repo URL entered by the user — can craft a submodule structure designed to escape the working tree and write into the local repo's `.git` directory (hook files, config, etc.) during the recursive clone. Because the app force-disables the very protection meant to block this, the outcome can be arbitrary file write outside the intended clone directory and, depending on what gets written (e.g., a hook), local code execution the next time a git operation triggers that hook. This satisfies the "attacker controls a cloned repository... result is code execution / file write outside the repo" impact criteria.

### Likelihood Explanation
Every clone performed by Desktop goes through this single `clone()` function and always passes `--recursive`, so the disabled protection applies unconditionally to all clones, including those triggered by an unauthenticated deep link (`openRepositoryFromUrl` → `openOrCloneRepository` → `clone`) without any additional confirmation of repository trustworthiness. No configuration flag exists to re-enable the check; the override is unconditional and applies to arbitrary attacker-supplied URLs. [5](#0-4) 

### Recommendation
Remove the hardcoded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override (or make it conditional/configurable) so that Git's built-in clone protection remains active by default, matching upstream Git's safe default rather than forcing it off for every clone.

### Proof of Concept
1. Host a malicious Git repository containing a submodule crafted per the CVE-2024-32002 technique (a submodule path/name that collides with `.git` under case-insensitive or symlink-aware filesystems) with a payload hook (e.g., `post-checkout`).
2. Send the victim an `x-github-client://openrepo/https://evil.example.com/attacker/repo.git` deep link, or have them clone the URL directly through the UI.
3. Desktop calls `clone(url, path, options)`, which sets `GIT_CLONE_PROTECTION_ACTIVE=false` and runs `git clone --recursive -- url path`. [6](#0-5) 
4. With the protection disabled, Git proceeds to check out the crafted submodule content into the colliding `.git` path, planting the hook; a subsequent Desktop-triggered git operation (commit, checkout, etc.) executes it.

Note: I was not able to execute git locally to confirm the exact on-disk collision mechanics of CVE-2024-32002 against this specific build of Git bundled with the app, so the PoC above documents the reachable code path and the disabled guard rather than a verified end-to-end exploit trace.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
