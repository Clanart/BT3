Based on my investigation, the real local analog to the reported bug class is in the Tron deployment of the Intent Gateway, where a fund-moving state transition is finalized without validating that the underlying token transfer actually succeeded — mirroring the loan report's "state marked complete but no assets actually moved, permanently locking the resource."

### Title
Unchecked ERC20/TRC20 return value in `IntentGatewayV2.withdraw()` finalizes escrow release without confirming the transfer succeeded, permanently locking user/solver funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` in the Tron `IntentGatewayV2.sol` marks an order as filled/refunded and decrements escrow accounting based solely on whether the low-level `.call()` to a token's `transfer` function did not revert — it never checks the ABI-encoded boolean return value. A token that returns `false` on failure (rather than reverting) will report `success == true` from `.call()`, causing the contract to treat the withdrawal as complete, zero out escrow, and mark `_filled[commitment]`, even though no tokens were delivered to the beneficiary.

### Finding Description
The internal `withdraw()` function performs the transfer like this: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }
    _orders[body.commitment][token] -= amount;
    ...
```

`success` here only reflects whether the external call reverted, not whether the token's `transfer()` returned `true`. Per the ERC20/TRC20 standard, a compliant token is allowed to return `false` on failure instead of reverting (e.g., insufficient internal balance-tracking edge cases, paused/blacklist logic, non-standard tokens). In that case `token.call(...)` returns `success = true` with `returndata` decoding to `false`, so the `if (!success) revert TransferFailed();` guard never fires. The function proceeds to decrement `_orders[body.commitment][token]` to zero and (via `_filled[body.commitment] = beneficiary` set unconditionally at the top) permanently marks the order as settled — with the escrowed tokens never having left the contract and never reachable again, because `UnknownOrder()` will now trip on any retry (`_orders[...][token] == 0`).

The same unchecked pattern also appears in the fee sweep and dust-sweep paths in the same file: [2](#0-1) [3](#0-2) 

This is a direct regression relative to the audited EVM mainline contract, which uses `SafeERC20.safeTransfer`, correctly reverting on both call failure and a `false` return value: [4](#0-3) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```

### Impact Explanation
This directly reproduces the reported bug class: a settlement/withdrawal path marks the resource (here, escrowed order funds) as finalized without confirming the corresponding value transfer actually completed. The consequence is identical — permanent loss/lock of the escrowed input tokens and/or fee-token balance, with the order becoming unusable (any further cancel/redeem/refund path reverts on `UnknownOrder()` because escrow accounting is already zeroed, and `_filled[commitment]` blocks any legitimate re-processing). This applies to every fund-release path that funnels through `withdraw()`: same-chain cancel, source-chain cancel via GET response, and destination-triggered `RedeemEscrow`/`RefundEscrow` via `onAccept`.

### Likelihood Explanation
No malicious relayer, prover, or governance actor is required — the order's `inputs[i].token` is chosen by the ordinary order creator (any unprivileged user) at `placeOrder` time. Any token used for escrow that can return `false` on a failed `transfer` (rather than reverting) — a legal ERC20/TRC20 implementation choice — triggers this path on ordinary operation (e.g., a transient failure condition in the token's own logic), not only via an attacker-deployed token. This makes it a live production risk rather than a contrived edge case, and it is reachable through the standard, unprivileged `cancelOrder`/fill/redeem flows.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()`, the fee-sweep block, and the dust-sweep loop with a transfer helper that validates the ABI-decoded boolean return value in addition to call success (equivalent to `SafeERC20.safeTransfer`, as already used in the mainline EVM `IntentsBase.sol`). Only decrement `_orders[...]` / set `_filled[...]` after the transfer is confirmed to have succeeded.

### Proof of Concept
1. Deploy (or use) a TRC20 token whose `transfer()` returns `false` on failure instead of reverting (standard-compliant behavior).
2. User places a same-chain order escrowing that token as one of `order.inputs`.
3. Under a condition where the token's `transfer()` would fail (e.g., internal transfer restriction returns `false`), call `cancelOrder(order, options)`.
4. `withdraw()` executes: `token.call(...)` returns `success = true` (no revert) even though the transfer failed; `_orders[commitment][token]` is decremented to `0`; `_filled[commitment]` is set to the user.
5. No tokens were delivered to the beneficiary, but the order is now irreversibly marked filled/refunded — the escrowed funds are permanently stranded in the contract with no code path left to recover them. [5](#0-4)
