### Title
Untrusted deserialization tag selects Constant interpolation, letting attacker-defined coefficients/verification shares fully control `ThresholdKeys::group_key` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes a tag byte that selects between `Interpolation::Lagrange` and `Interpolation::Constant`, then reads `n` attacker-supplied scalar coefficients, an arbitrary `secret_share`, and `n` arbitrary `verification_shares`. Like XStream unmarshaling attacker-named classes, this unmarshals an attacker-specified algebraic object which is then trusted as a threshold key — no consistency check binds `secret_share` to `verification_shares[i]` or to any prior DKG transcript.

### Finding Description
In `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632), after the curve-ID check, a single byte selects the interpolation mode: `0` reads `n` raw scalars as `Interpolation::Constant(c)`; `1` selects `Lagrange`. The coefficients, `secret_share`, and all `verification_shares` come entirely from the input stream. `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) only checks share count, participant indexes `<= n`, and `t == n` for `Constant`. It never verifies `C::generator() * secret_share == verification_shares[i]`. The group key is then computed as `sum(verification_shares[i] * interpolation_factor(i, 1..=t))` (lines 376-378).

For `Constant`, `interpolation_factor` is just `c[i-1]` (line 228) — attacker-chosen. An attacker can therefore submit bytes describing a "threshold key" whose `group_key()` is a point for which the attacker knows the discrete logarithm: pick `verification_shares[j] = G * x_j` for known `x_j`, set all `c[j] = 1`, then `group_key = G * sum(x_j)`. Setting `i` to a participant whose `secret_share` equals `x_i` keeps every share self-consistent: `view()` (lines 463-533) multiplies both `secret_share` and `verification_shares[i]` by the same `c[i]`, so FROST share verification passes and `complete()` produces valid signatures — under a key the attacker controls unilaterally.

### Impact Explanation
Any caller that deserializes `ThresholdKeys` from bytes influenced by an untrusted party (key-package delivery, restoration, migration) will compute `group_key()` / `view().group_key()` as an attacker-known key. Funds or UTXOs attributed to that "group key" are spendable solely by the attacker — the threshold degenerates to a 1-of-1 under adversary control while every share verification and produced signature is internally valid. This is key substitution via crafted unmarshaled state, exactly the XStream shape (input-controlled object graph steering security-critical behavior), and satisfies "funds reported received that are not spendable [by the group]".

### Likelihood Explanation
`ThresholdKeys::read` is a public API for reading untrusted serialized key material; reaching it requires only supplying bytes — an explicitly in-scope reachability path. Exploitation requires `t == n` (satisfied by MuSig-style n-of-n setups using `Interpolation::Constant`, cf. crypto/dkg/musig/src/lib.rs:157) or any t-of-n using Lagrange-tagged bytes reinterpreted. No collusion, no malicious validator assumptions, no curve weaknesses needed — only the unchecked deserialization.

### Recommendation
In `ThresholdKeys::new` (or `read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` so the deserialized secret provably matches the claimed share. Additionally, bind the interpolation tag to the originating protocol: Constant interpolation should only be constructible via `musig()`/equivalent (which derives coefficients from `binding_factor_transcript`), and `read` should reject `Constant` unless coefficients are re-derived from a context transcript rather than taken from the stream. At minimum, recompute the group key against an externally-known expected key before use.

### Proof of Concept
```
// n = t = 2, attacker knows x1, x2; wants group_key = G*(x1+x2)
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(2u16.to_le_bytes());          // t
buf.extend(2u16.to_le_bytes());          // n
buf.extend(1u16.to_le_bytes());          // i = 1
buf.push(0);                             // tag: Interpolation::Constant
buf.extend(F::ONE.to_repr());            // c[0] = 1
buf.extend(F::ONE.to_repr());            // c[1] = 1
buf.extend(x1.to_repr());                // secret_share = x1 (attacker-known)
buf.extend((G * x1).to_bytes());         // verification_shares[1]
buf.extend((G * x2).to_bytes());         // verification_shares[2]
let keys = ThresholdKeys::<C>::read(&mut buf.as_ref()).unwrap();
// keys.group_key() == G*(x1+x2): attacker alone knows the discrete log.
// keys.view(vec![1,2]) produces shares that pass FROST verification,
// and complete() emits valid signatures for the attacker-controlled key.
```
Root cause: `crypto/dkg/src/lib.rs:604-616` (unvalidated tag + coefficients), `crypto/dkg/src/lib.rs:376-378` (group key derived from deserialized shares/coefficients), and absence of a `secret_share`↔`verification_shares[i]` consistency check in `ThresholdKeys::new`.
