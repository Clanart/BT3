## Analysis

The Putty bug reduces to: **a value the user implicitly "agreed to" at decision time (fee) is silently re-read from a mutable source at execution time (withdraw), with no verification that it still matches what was agreed.** The equivalent broken invariant in GitHub Desktop is present in the partial-commit ("stage selected lines") flow: the user's line-selection decision is captured against one diff snapshot, but staging re-fetches a fresh diff and blindly reapplies the old selection indices to it, with no re-validation that the content at those indices is still what the user reviewed.

### Title
Stale line-selection indices reapplied against a freshly re-fetched diff cause silent corruption of committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user partially stages a file (selecting individual lines/hunks in the Changes view), Desktop stores the selection as a set of line *indices* relative to the diff that was on screen at selection time. When the user actually commits, `stageFiles` calls `applyPatchToIndex`, which does **not** reuse that diff — it calls `getWorkingDirectoryDiff` again to fetch a brand-new diff from disk, and then feeds the old (stale) `file.selection` into `formatPatch` against this new diff, purely by numeric line index. If the working-tree file changed between the time the user made their selection and the time they clicked "Commit," the indices no longer point at the same content, so the wrong lines are silently included in the patch that gets staged and committed.

### Finding Description
The code itself acknowledges this hazard, but the mitigation it has is incomplete: [1](#0-0) 

`updateChangesWorkingDirectoryDiff` only recomputes `selectableLines` (and thus invalidates stale selections) for the **single currently-selected/viewed file** in the Changes panel — not for every file that currently carries a partial selection. Any other file with a lingering partial selection is left untouched.

When the user commits, `_commitIncludedChanges` takes whatever selection state is currently sitting in `workingDirectory.files` at face value: [2](#0-1) 

That flows into `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex`: [3](#0-2) 

`applyPatchToIndex` re-fetches the diff **fresh from disk** at staging time (not the diff object the user actually saw), then builds the patch by testing `file.selection.isSelected(absoluteIndex)` against that new diff's hunk/line indices: [4](#0-3) [5](#0-4) 

There is no check that the content at a given index still matches what the user selected — only that the index is numerically within range. If the underlying file content shifted (lines added/removed/reordered) after the user made their selection but before the commit is executed, the indices silently point to different content.

### Impact Explanation
This breaks the core guarantee GitHub Desktop is built on: "you commit exactly what you see and select." A file whose content changes between the time it's reviewed/selected and the time "Commit" is pressed (e.g., a build tool, formatter, code generator, or file-watcher that runs against the cloned/fetched repository and rewrites tracked files in place) can cause Desktop to stage and commit different lines than the user actually approved — potentially reintroducing content the user explicitly deselected, or omitting content the user meant to include, all without any warning that the diff changed. This is a silent corruption of what the user commits, matching the report's core theme of “the agreed terms changed before settlement, and the change was applied without the user's knowledge.”

### Likelihood Explanation
The race window is realistic: partial-commit is a common workflow, and many real repositories run local tooling (linters/formatters/watch builds/codegen) that rewrites tracked files during normal use, entirely independent of anything malicious the user does. No elevated privileges, local access, or prior compromise are required — only a normal editing session with a file that is regenerated/modified between selecting lines and pressing Commit, in an ordinarily untrusted cloned repository whose tooling triggers such regeneration.

### Recommendation
Before staging, re-diff every file with a non-`All`/non-`None` selection (not just the one currently displayed in the UI) and validate that the previously selected line indices still correspond to the same content (e.g., by hashing/line-content comparison, not just index bounds). If the diff has materially changed for any file about to be partially committed, invalidate the stale selection and force the user to re-review before allowing the commit to proceed, mirroring the report's suggested mitigation of "verify the agreed terms are still valid at execution time" rather than blindly reapplying possibly-stale state.

### Proof of Concept
1. Clone a repository containing a file `foo.md` and a local tool (e.g., a formatter/watch task, or simply another process) that appends/removes lines from `foo.md` periodically.
2. In Desktop's Changes view, open `foo.md`, and select only a few specific added lines (e.g., lines 5–8) to include in the next commit, leaving the rest unselected.
3. Before clicking "Commit," let the external process mutate `foo.md` (add/remove lines above the selected region, shifting line numbers).
4. Click "Commit." `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff for `foo.md` from disk (now different) and calls `formatPatch` (`app/src/lib/patch-formatter.ts:157`), which uses the *original* `file.selection.isSelected(absoluteIndex)` against the *new* hunk layout.
5. Inspect the resulting commit: it contains different line content than what was visually selected by the user, with no warning ever shown that the diff had changed since selection.
