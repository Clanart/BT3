### Title
Unbounded `object::root_owner()` traversal enables ownership cycles that permanently brick `code::publish_package` upgrades and lazy module self-init - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`code::publish_package` calls `object::root_owner()` on every (re)publish to an object address, in order to record the deploy owner used by the new lazy module self-initialization gate (`init::assert_may_self_initialize`). Unlike the sibling ownership-traversal function `object::owns()` / `verify_ungated_and_descendant()`, which both bound their upward traversal with `MAXIMUM_OBJECT_NESTING`, `root_owner()` has no cycle guard at all. Because `object::transfer_raw` never verifies that the destination address is not itself a descendant of the object being moved, an object owner can construct a self-referencing ownership cycle. Any subsequent call to `root_owner()` on an address inside that cycle loops until the transaction runs out of gas, permanently bricking `code::publish_package` (and thus all future upgrades) for the affected code object, as well as `init::internal_maybe_initialize` self-init for modules deployed there.

### Finding Description
`code::publish_package` records the transitive root owner of the target object for every module in the package being (re)published: [1](#0-0) 

`object::root_owner()` walks the ownership chain until it hits a non-object address, with **no bound**: [2](#0-1) 

Contrast this with `object::owns()` and `verify_ungated_and_descendant()`, both of which use an explicit `MAXIMUM_OBJECT_NESTING` counter to guarantee termination on the same kind of traversal: [3](#0-2) [4](#0-3) 

The transfer path that changes ownership, `object::transfer_raw`, only verifies that the *caller* legitimately owns the object being moved (by walking from the object up to the claimed owner) — it never checks that the new `to` address is not a descendant of the object being transferred: [5](#0-4) 

This allows an object owner to construct A → B → A style ownership cycles: create object `B` nested under object `A` (so `B.owner == A`), then transfer `A` itself to be owned by `B` (`transfer_raw(owner=U, object=A, to=B)`). `verify_ungated_and_descendant(U, A)` passes trivially because `A.owner == U` already, and `transfer_raw_inner` then sets `A.owner = B`, closing the cycle.

Once such a cycle exists at a code-object address, `root_owner()` never terminates:
- `init::assert_may_self_initialize` calls the equivalent chain-walk (`object::address_to_object<ObjectCore>(addr).root_owner()`) to gate lazy self-init: [6](#0-5) 
- `code::publish_package` calls `root_owner()` unconditionally whenever lazy module init is enabled and the target is an object, on every publish/upgrade of that object's code: [7](#0-6) 

Since Move execution is gas-metered rather than instruction-bounded for this loop, the transaction will run out of gas rather than aborting cleanly, permanently denying both further upgrades to that code object (via `object_code_deployment::upgrade` → `code::publish_package`) and lazy self-initialization for any module hosted there.

### Impact Explanation
This is a publish-path/code-safety impact: a permissionless, unprivileged state transition (object transfer) can permanently and irreversibly disable the upgrade capability (`code::publish_package`) and initialization capability (`init::internal_maybe_initialize`) of an on-chain code object once the `LAZY_MODULE_INITIALIZATION` feature is enabled — an unbounded loop reaching protected state-mutation code (`PackageRegistry` update, `InitializationState` update) that can never complete. This is distinct from generic network DoS: it is a durable, attacker-craftable corruption of a specific object's upgrade/init capability caused by a missing bound in a framework-level ownership-traversal primitive used directly by the code-publishing flow.

### Likelihood Explanation
Medium-to-High for self-inflicted bricking (an account can trivially brick its own code object by nesting and cyclically transferring objects it fully controls), and plausible in composed systems (marketplaces/vaults that programmatically call `transfer`/`transfer_to_object` on user- or protocol-supplied object graphs) where an attacker who can influence the destination of an object transfer for a victim-owned code object could induce the same cycle. The precondition (feature-gated by `LAZY_MODULE_INITIALIZATION`, and requiring `object::is_object(addr)` for the code address) narrows the blast radius but does not eliminate it, since object-based code deployment (`object_code_deployment.move`) is the recommended, permissionless publishing path.

### Recommendation
Bound `object::root_owner()`'s traversal the same way `owns()` and `verify_ungated_and_descendant()` are bounded, using `MAXIMUM_OBJECT_NESTING` and aborting with a clear error (e.g., `EMAXIMUM_NESTING`) instead of looping unboundedly. Additionally, `object::transfer_raw`/`transfer_raw_inner` should reject transfers where `to` is a descendant of `object` (i.e., detect and refuse to create ownership cycles) so that such graphs cannot be constructed in the first place.

### Proof of Concept
1. Enable `LAZY_MODULE_INITIALIZATION` feature.
2. As account `U`, create object `A` (`object::create_object(U)`), then create object `B` nested under `A` (`object::create_object(A)`), so `B.owner == A`.
3. Deploy a code package to object `A` via `object_code_deployment::publish` (this records `A`'s current root owner, `U`, for lazy self-init).
4. As `U`, call `object::transfer_raw(U, A, B)` — passes `verify_ungated_and_descendant(U, A)` trivially since `A.owner == U`, and sets `A.owner = B`, closing the cycle `A → B → A`.
5. Any subsequent call to `code::publish_package` targeting `A` (e.g., via `object_code_deployment::upgrade`), or any call into a module hosted at `A` that invokes `init::internal_maybe_initialize`, triggers `root_owner()`/`assert_may_self_initialize`'s unbounded loop on the `A ↔ B` cycle, exhausting gas and aborting — permanently denying upgrade and self-init capability for object `A`.                     from: object_core.owner,
                    to,

    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    public fun root_owner<T: key>(self: Object<T>): address {
        let obj_owner = self.owner();
        while (is_object(obj_owner)) {
            obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
