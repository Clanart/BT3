## Title
Trampoline credential helper leaks stored GitHub/Enterprise tokens (or phishes generic credentials) to any process spawned while operating on an attacker-controlled repository - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

## Summary
Desktop's git operations are proxied through a local TCP "trampoline" server that answers `GIT_ASKPASS`/`credential.helper` requests on behalf of Git subprocesses. Authorization to talk to this server is based solely on a single, operation-scoped `DESKTOP_TRAMPOLINE_TOKEN` that is broadcast via environment variables to the git process **and everything it spawns** (hooks, clean/smudge filters, Git LFS, etc.) for the whole duration of a clone/fetch/push. The handler that answers "get credential" requests never checks *which remote* the operation is actually authenticating against — it just matches the `host`/`url` supplied in the request. This is structurally the same broken invariant as the `FeeWrapper` bug: a shared, unauthenticated relay whose caller identity cannot be distinguished, so any caller holding the (widely distributed) token can make requests "as" the legitimate git process and receive the same privileged answer.

## Finding Description
When Desktop runs a git command it wraps it with `withTrampolineEnv` in `app/src/lib/trampoline/trampoline-environment.ts:93-147`, which sets `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, and — critically — configures the credential helper via the environment variable `GIT_CONFIG_PARAMETERS` (not a `-c` argument) specifically so that it is inherited by every child process Git spawns, including filter drivers: [1](#0-0) 

The token itself is a single UUID that stays valid for the entire git invocation (`withTrampolineToken`), with no binding to a specific remote URL or subprocess: [2](#0-1) 

The trampoline server's only authorization check is that the token is a member of the valid-token set — it never verifies that the credential request's target host corresponds to the remote the current operation is actually talking to: [3](#0-2) 

The credential-helper handler then resolves whatever `host`/`url` it was given against the user's stored accounts purely by origin match, with no relation to the original operation: [4](#0-3) 

`getEndpointKind`'s fallback for unknown hosts calls `isGitHubHost`, which performs a HEAD request and trusts the caller-controlled response header `x-github-request-id` to decide whether to treat an arbitrary host as an "enterprise" GitHub endpoint: [5](#0-4) 

Because the C trampoline client (`vendor/desktop-trampoline/src/desktop-trampoline.c`) simply forwards whatever `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` it finds in its environment to the socket, and Git LFS/hooks/filters are explicitly designed (per the comment above) to inherit that same environment, an attacker who controls a repository's content can cause Desktop to invoke a subprocess (e.g. a Git LFS smudge filter configured through `.lfsconfig`/`.gitattributes`, or a script referenced by a filter/diff driver already registered on the victim's machine) during clone/fetch/checkout of that repository. That subprocess inherits the live trampoline token and can:

1. Request credentials for `host=github.com` (or the user's GHE host). `getGitHubCredential` matches purely by origin and will hand back the user's real, currently signed-in OAuth token — even though the actual operation in progress has nothing to do with github.com — because there is no check tying the credential request to the remote actually being fetched.
2. Request credentials for an arbitrary attacker-owned host. Since no stored account matches, `getGenericCredential`/`promptForCredential` will pop Desktop's native "sign in"/generic-git-auth dialog targeting that attacker-chosen URL, harvesting whatever the user types, or spoof an "enterprise" flow via the forgeable `x-github-request-id` header.

## Impact Explanation
This lets a fully unprivileged, remote attacker who merely gets a user to clone/fetch/checkout their repository (a normal, expected Desktop action) trigger credential disclosure: either exfiltration of the victim's real GitHub.com/GHE OAuth token to an attacker-influenced request path, or a convincing native OS-level credential prompt bound to an attacker-chosen endpoint. There is no reentrancy-style guard, no per-remote scoping of the token, and no user-visible indication that the credential request did not originate from the actual remote-fetch Git process — exactly the "indistinguishable caller / arbitrary target" pattern described in the source report.

## Likelihood Explanation
Git LFS filters and similar checkout-time hooks execute automatically as part of routine clone/fetch/checkout operations with no additional user interaction beyond opening the malicious repository in Desktop, which is a normal, expected user action (not local/physical access, not requiring existing malware, not social engineering beyond "clone this repo"). The `GIT_CONFIG_PARAMETERS`-based credential wiring is explicitly designed to propagate to filter subprocesses, so the primitive is reachable by design, not by an obscure edge case.

## Recommendation
- Bind each trampoline token to the specific remote/host the enclosing git operation is authenticating against, and reject credential requests whose `host`/`url` doesn't match that expected remote.
- Do not rely on an inherited, long-lived, unscoped token shared with all child processes (filters, hooks, LFS) spawned during a git operation; issue distinct, narrowly-scoped tokens/permissions per subprocess purpose.
- Stop trusting a response header (`x-github-request-id`) from an arbitrary caller-supplied host as proof of GitHub identity in `isGitHubHost`.
- Surface to the user, in any credential prompt triggered via the trampoline, which subprocess/tool and destination host is requesting credentials.

## Proof of Concept
1. Attacker publishes a public repository containing a `.lfsconfig` (or `.gitattributes` referencing an already locally-configured filter/diff driver) whose `lfs.url` points to `https://github.com/<anything>` or to an attacker-controlled server.
2. Victim, signed in to GitHub.com in Desktop, clones/fetches the attacker's repository normally.
3. During checkout, Desktop spawns the git process with `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN`/`GIT_CONFIG_PARAMETERS=credential.helper=desktop` in its environment (`app/src/lib/trampoline/trampoline-environment.ts:126-146`). Git spawns the LFS smudge filter for the configured URL, which inherits this same environment.
4. The LFS process calls `git credential fill` for the attacker-specified host; this reaches `desktop-trampoline` → the trampoline TCP server → `createCredentialHelperTrampolineHandler` (`app/src/lib/trampoline/trampoline-credential-helper.ts:220-259`), which only validates the token (`trampoline-server.ts:162-165`), not the host/remote relationship.
5. If the host is `github.com`, `getGitHubCredential` returns the victim's real stored OAuth token to the LFS process, which forwards it in an HTTP request to the attacker-influenced URL; if the host is unknown, the victim is shown a native credential/sign-in prompt for the attacker's chosen host. [6](#0-5)

const trampolineTokens = new Set<string>()

function requestTrampolineToken() {
  const token = crypto.randomUUID()
  trampolineTokens.add(token)
  return token
}

function revokeTrampolineToken(token: string) {
  trampolineTokens.delete(token)
}

/** Checks if a given trampoline token is valid. */
export function isValidTrampolineToken(token: string) {
  return trampolineTokens.has(token)
}

/**
 * Allows invoking a function with a short-lived trampoline token that will be
 * revoked right after the function finishes.
 *
 * @param fn Function to invoke with the trampoline token.
 */
export async function withTrampolineToken<T>(
  fn: (token: string) => Promise<T>
): Promise<T> {
  const token = requestTrampolineToken()
  let result

  try {
    result = await fn(token)
  } finally {
    revokeTrampolineToken(token)
  }

  return result
}

    }

    const handler = this.commandHandlers.get(command.identifier)

      socket.end()
      return
    }

      log.error('Error processing trampoline command', e)
    )

    if (result !== undefined) {
      socket.end(result)
    } else {

    }
  }

  const endpoint = `${getCredentialUrl(cred)}`
  const account = await findGenericTrampolineAccount(token, endpoint)

    return credWithAccount(cred, account)
