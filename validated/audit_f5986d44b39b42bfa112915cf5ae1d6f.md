### Title
Panic on `HashMap` index of an unregistered participant's encryption key when evaluating a blame proof for oneself - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG `BlameMachine` dereferences `self.enc_keys[&decryptor]` inside `Decryption::decrypt_with_proof`. The `enc_keys` map only ever contains the *other* participants' encryption keys — a participant never registers their own key (registration happens in `verify_r1`, which skips `params.i()` since `commitment_msgs` contains no entry for oneself). Consequently, when a participant evaluates a blame proof in which they are the `recipient`/accuser — the exact case produced when a malicious participant sends them an invalid secret share — the indexing panics, crashing the evaluating process instead of attributing fault.

### Finding Description
`Encryption::register`/`Decryption::register` is only invoked for remote participants during `SecretShareMachine::verify_r1` (crypto/dkg/pedpop/src/lib.rs:313-316): it iterates `all_participant_indexes()` but `commitment_msgs.remove(&l)` returns `None` for the local `params.i()`, so `enc_keys` never gains an entry for our own index. Later, `KeyMachine::calculate_share` returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` with an `EncryptionKeyProof` when a sender's share is bad (lib.rs:479-499), handing the caller a `BlameMachine` whose `Decryption` still lacks our own key. When the caller then invokes `BlameMachine::blame(sender, recipient = self.params.i(), msg, Some(proof))` to adjudicate the accusation, `blame_internal` (lib.rs:582) calls `decrypt_with_proof`, which performs `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388) — an unchecked `HashMap` index that panics with "key not found" for our own `Participant`. The same unchecked pattern exists at `self.commitments[&sender]` (lib.rs:599) for out-of-range sender indices in `AdditionalBlameMachine::blame`.

### Impact Explanation
Analogous to CVE-2019-12312 (an attacker-supplied message sequence reaching a state whose missing entry causes a NULL-deref/restart), a malicious DKG participant can send a victim an invalid secret share; when the victim exercises the blame path to prove the sender's fault, the victim's own PedPoP machine panics instead of returning the faulty `Participant`. This aborts the victim's processor mid-protocol, denying it the ability to publish blame and complete the DKG — a remote-triggerable denial of service of the key-generation ceremony reachable purely from attacker-controlled protocol messages.

### Likelihood Explanation
Any participant can trigger it deterministically: send a well-formed `EncryptedMessage` whose `pop` signature verifies but whose decrypted share is non-canonical or fails verification (e.g., via `calculate_share` returning `InvalidShare` with `Some(blame)`), then let the victim call `blame`/`blame_internal` with themselves as recipient and `proof = Some(...)`. Because the `pop` check at encryption.rs:374 passes (the message is honestly formed), execution reaches the `enc_keys[&decryptor]` index and panics.

### Recommendation
Replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor)` and return `DecryptionError::InvalidProof` (or attribute blame to the accuser) on `None`; likewise use `.get()` for `self.commitments[&sender]` in `blame_internal` and return `sender` when absent.
