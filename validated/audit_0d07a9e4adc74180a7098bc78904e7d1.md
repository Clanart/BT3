### Title
`SignableTransaction` fee and weight accounting omits the OP_RETURN data output, misreporting `needed_fee` and allowing under-priced/oversized transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the SimpleTokenSale `hasSaleEnded` bug — where a status was computed from a value (`endTime`) whose update was deferred past an intervening state change — `SignableTransaction::new` computes the transaction's weight and `needed_fee` against a stale transaction shape. The OP_RETURN `data` output is appended to `tx_outs` at line 194-202, but `calculate_weight_vbytes` is only ever called with `payments` (lines 204, 226) and never accounts for the data output. The computed `weight` and `needed_fee` therefore describe a transaction that no longer matches the one actually built and signed.

### Finding Description
In `SignableTransaction::new`:

1. `tx_outs` is populated with payments, then an OP_RETURN `TxOut` carrying up to 80 bytes of caller-supplied `data` is pushed (lines 194-202).
2. `calculate_weight_vbytes(tx_ins.len(), payments, None)` builds a throwaway `Transaction` containing only `payments` — no `data` output — and derives `weight`/`vbytes` from it (line 204).
3. `needed_fee = fee_per_vbyte * vbytes` and the `DEFAULT_MIN_RELAY_TX_FEE` floor check (line 211) both use this underestimated `vbytes`.
4. If change is added, `weight`/`needed_fee` are recomputed — but again only over `payments` + `change`, still omitting the data output (lines 225-233). This mirrors the original bug's "extension applied only later, and still on the wrong basis": the lazy recompute on the change path never corrects for the data output.
5. The `MAX_STANDARD_TX_WEIGHT` check (line 241) uses the same stale `weight`, so a transaction that actually exceeds the standard weight limit can pass validation.
6. The resulting `SignableTransaction` — with the uncounted OP_RETURN output — is what gets signed via the FROST multisig and broadcast.

The OP_RETURN output adds ~10–90 vbytes (8-byte value + compact size + script with pushdata), so `needed_fee` is under-reported by up to ~90 × `fee_per_vbyte` sats, and the real fee rate achieved is strictly below the requested one.

### Impact Explanation
- `needed_fee()` and `fee()` callers (e.g., `prepare_send`/`amortize` flows in the processor) operate on a fee figure that does not correspond to the transaction's actual size, so the transaction pays less per vbyte than intended.
- A transaction near the minimum-relay-fee boundary can pass the `TooLowFee` check while its *actual* fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`, producing a signed transaction the network will not relay or mine — funds sit in an unbroadcastable/stuck spend.
- The stale `weight` also defeats the `TooLargeTransaction` guard, so a transaction that is actually non-standard (> `MAX_STANDARD_TX_WEIGHT`) can be constructed and signed.

This is a concrete misreporting of an accounting value driven by caller-supplied `data` bytes, reachable through the public `SignableTransaction::new` API.

### Likelihood Explanation
Triggered whenever `SignableTransaction::new` is called with a non-`None` `data` argument. The underpayment is proportional to `data` length (up to the 80-byte cap), so the misreport is deterministic and caller-influenced. It does not leak secrets or enable theft directly; its effect is an incorrect fee/weight commitment and potential relay failure — consistent with Medium severity.

### Recommendation
Pass the final `tx_outs` (or an explicit `data`/`op_return` parameter) into `calculate_weight_vbytes` so the weight and fee are computed over the complete output set — i.e., derive the accounting from the transaction state as it will actually be signed, not from a snapshot taken before the data output was appended. Recompute both `weight` and `needed_fee` after every mutation of `tx_outs`.

### Proof of Concept
```rust
// Conceptual PoC against networks/bitcoin/src/wallet/send.rs
let data = vec![0xAA; 80]; // max permitted payload
let stx = SignableTransaction::new(inputs, &payments, change, Some(data), fee_per_vbyte)?;
// stx.needed_fee() == fee_per_vbyte * vbytes(payments + change)   <-- stale
// actual vsize of stx.tx includes the ~92-byte OP_RETURN output
assert!(stx.needed_fee() < fee_per_vbyte * real_vsize(&stx));
// If fee_per_vbyte * vbytes just cleared DEFAULT_MIN_RELAY_TX_FEE,
// the effective relay fee rate is now below the minimum -> TX won't propagate.
```
