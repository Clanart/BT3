### Title
Send-on-closed-channel panic / bid data race in `BidPool` due to unsynchronized `AddBid` vs `stop()` - ([File: kaiax/auction/impl/bid_pool.go])

### Summary
The Linux `ssi_protocol` bug is a UAF caused by a worker (`ssip_xmit_work`) being able to run/queue concurrently with `ssi_protocol_remove()` freeing the shared object, because the work item was not canceled before cleanup. `kaiax/auction/impl/bid_pool.go` has an analogous unsynchronized start/stop race: `BidPool.stop()` closes `bp.bidMsgCh`/`bp.newBidCh` and clears the bid maps while other goroutines (`AddBid`, invoked directly from the public RPC `SubmitBid`, and `handleBidMsg`) can still be sending on those very channels or accessing the maps concurrently.

### Finding Description
`AddBid` is reachable directly from the public (albeit non-default-exposed) `auction_SubmitBid` RPC and indirectly from `HandleBid` (network bid messages) → `bp.bidMsgCh` → `handleBidMsg()` → `AddBid()`. `AddBid` performs `bp.insertBid(bid)` (locked under `bidMu`) and then unconditionally does: [1](#0-0) 

Concurrently, `AuctionModule.Stop()`/`PostInsertBlock` drive `BidPool.stop()`: [2](#0-1) 

There is no synchronization (no lock, no `WaitGroup`/quiescence barrier) between the `atomic.LoadUint32(&bp.running)` check at the top of `AddBid` and the subsequent `bp.newBidCh <- bid` send. Between the `running` check passing and the channel send executing, `stop()` can run on another goroutine (called from `AuctionModule.Stop()` at node shutdown/module teardown, or from `PostInsertBlock` clearing `running` to 0 on every new block when the auctioneer/entry point changes) and close `bp.newBidCh`. The send in `AddBid` then panics with "send on closed channel." Additionally `bp.stop()`'s `clearBidPool()` replaces the maps guarded by `bidMu` while `insertBid`/`validateBid` in a racing `AddBid` call may be operating on the old map references without any coordination with the close of channels that happens right after — i.e., the check-then-act pattern (`running` check → later channel send) is not atomic, mirroring the missing "cancel work before free" fix required for the kernel CVE.

Because `start()` can also run concurrently and recreate `bp.bidMsgCh`/`bp.newBidCh` right after `stop()` closes the old ones (`PostInsertBlock` toggles `running`/pool lifecycle on every block without waiting for in-flight `AddBid`/`HandleBid` calls to drain), a bid submitted right at a block-boundary auctioneer/entry-point change can hit a closed channel from the *previous* generation, producing a crash reachable by:
- an unprivileged public-RPC caller invoking `auction_SubmitBid` (reaches `AddBid` directly), or
- a network peer relaying a bid message (`HandleBid` → `bidMsgCh` → `handleBidMsg` → `AddBid`).

### Impact Explanation
A panic in `AddBid` on `bp.newBidCh <- bid` crashes the node process (or at minimum the RPC/handler goroutine, depending on panic recovery middleware), causing a denial of service for a CN validator running the auction module. Because `PostInsertBlock` toggles `running` on essentially every block (any time the auctioneer/entry point config changes or Randao/downloader-sync state flips), the closed-channel window recurs regularly, making this a reliably triggerable, transaction/RPC-reachable crash rather than a purely theoretical race.

### Likelihood Explanation
The race window is opened on ordinary chain progression (`PostInsertBlock` is called on every inserted block) combined with any external submission of a bid (`SubmitBid` RPC or a bid gossip message) landing in the narrow window between the `running` check and the channel send/`stop()`'s channel close. No special privileges are required — a bidder/searcher issuing bids near block boundaries can trigger it, and under load (auction traffic near every block) the timing window is hit with non-trivial probability.

### Recommendation
Protect the entire "check running → mutate pool → send on channel" sequence in `AddBid`/`HandleBid` with the same lock (or a dedicated `sync.RWMutex`) used to guard channel lifecycle transitions in `start()`/`stop()`, so that `stop()` cannot close `bidMsgCh`/`newBidCh` while a send is in flight — analogous to how the kernel fix ensures `cancel_work_sync()` runs before `kfree(ssi)` so no send/access can race the free. Concretely: take a shared `RLock` in `AddBid`/`HandleBid` around the running-check-and-send, and have `stop()` take the corresponding `Lock` before flipping `running`, clearing the pool, and closing the channels; or replace the channel-close-based shutdown with a `select` on a `done`/`quit` channel plus recovering the send with a `select { case ch <- bid: case <-quit: }` pattern so no send ever targets an already-closed channel.

### Proof of Concept
1. Run a CN with the auction module enabled and `AuctionConfig.Disable = false`.
2. Concurrently (goroutine A) repeatedly call `PostInsertBlock` transitions that flip `running` 1→0→1 (naturally happens as new blocks arrive, or can be forced by toggling the auctioneer/entry-point registry value each block) which internally invokes `bp.stop()`/`bp.start()` via `AuctionModule.Stop`/`Start` during a module restart, or more directly race `AuctionModule.Stop()` against:
3. Goroutine B: continuously call `auction_SubmitBid` RPC (or send `HandleBid` peer messages) with valid signed bids so that `AddBid` is executing its `running` check and reaches `bp.newBidCh <- bid` at the same moment `stop()` executes `close(bp.newBidCh)`.
4. Observe a `panic: send on closed channel` originating from `kaiax/auction/impl/bid_pool.go:271`, crashing the node — demonstrating the unsynchronized shutdown analogous to the referenced UAF pattern.

func (bp *BidPool) stop() {
	// Stop the bid pool.
	atomic.CompareAndSwapUint32(&bp.running, 1, 0)
	bp.clearBidPool()

	// Only close channels if they haven't been closed before
	if atomic.CompareAndSwapUint32(&bp.stopped, 0, 1) {
		close(bp.bidMsgCh)
		close(bp.newBidCh)
	}
	bp.wg.Wait()
}

func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}
