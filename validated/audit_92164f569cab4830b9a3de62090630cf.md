Based on the code I was able to inspect, the strongest and most concrete analog to the "wrong selector → message misrouted → user loses control of outcome" bug class is a validation gap in the deep-link ("Open in Desktop") URL handler, not a full end-to-end confirmed RCE (I was unable to verify the final git-spawn argument construction before running out of tool calls — see caveat at the end).

### Title
Deep-link `branch` parameter is validated with an incomplete regex, allowing option-like values to reach `git checkout` - ([File: app/src/lib/parse-app-url.ts])

### Summary
`parseAppURL()` accepts an `x-github-client://openRepo/...?branch=<value>` deep link from any external source (a website's "Open in Desktop" button, an email, a git host, etc.) and forwards the `branch` string, largely unsanitized, into the app's branch-checkout pipeline.

### Finding Description
`parseAppURL()` validates the attacker-supplied `branch` value using `testForInvalidChars()`, which only tests against `invalidCharacterRegex` (control chars, `~^:?*[\|"<>`, `@{`, `..`, leading/trailing dot, `.lock`, trailing `/`): [1](#0-0) 

Critically, this regex does **not** reject a leading `-`. The companion function `sanitizedRefName()` (used elsewhere when Desktop generates its own branch names) explicitly strips leading `-`/`+` characters as a separate step: `.replace(/^[-\+]*/g, '')`, but `testForInvalidChars()`, the function actually used to gate the deep-link input, has no equivalent check: [2](#0-1) 

In `parseAppURL()`, the branch value is checked only with `testForInvalidChars`, then passed straight through into the `IOpenRepositoryFromURLAction`: [3](#0-2) 

This action reaches `Dispatcher.dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` → `checkoutLocalBranch`, which ultimately shells out to `git`: [4](#0-3) [5](#0-4) 

So a value like `branch=--upload-pack=...` or any other `git`-recognized option string passes Desktop's own validation (since it contains none of the blacklisted characters) and is handed to the git-invoking code as a literal ref name string, exactly the same class of defect as the report's root cause: the wrong/incomplete guard is used at the trust boundary, so a value that should be rejected or neutralized is instead passed downstream unmodified.

By contrast, note that the `filepath` parameter of the same action *is* correctly hardened with an `isAbsolute()` check plus `resolveWithin()` containment check before use: [6](#0-5) [7](#0-6) 

This asymmetry (strong containment on `filepath`, weak/incomplete blacklist on `branch`) is the "wrong selector" analog: the parser applies the incomplete guard (`testForInvalidChars`) instead of the stricter one (`sanitizedRefName`'s leading-dash stripping) that the codebase itself demonstrates is necessary for exactly this kind of value.

### Impact Explanation
If the downstream git-invocation code (in `app/src/lib/git/checkout.ts` / `app-store.ts`) does not itself insert a `--` argument terminator before the ref name — which I was not able to confirm before running out of investigation budget — a leading-dash branch value from an untrusted deep link could be interpreted by the git CLI as an option rather than a ref, which is a classic argument-injection primitive against a locally spawned process. Depending on which git option is smuggled, this ranges from a confusing failure (branch class of the ERC1155 report: the operation silently does the wrong thing) up to more severe outcomes if an option that accepts a path/command argument is reachable (e.g. options that write to arbitrary paths).

### Likelihood Explanation
The trigger requires only that a victim click an attacker-controlled `x-github-client://openRepo/...` link (or a rendered "Open in Desktop" button pointing to it) — no local access, no credentials, and no unnatural steps, matching the "attacker controls a link the user clicks" impact class. The protocol is registered and handled unconditionally by `handleAppURL` in the main process for any of `possibleProtocols`: [8](#0-7) [9](#0-8) 

### Recommendation
Apply the same leading-dash stripping/rejection used in `sanitizedRefName()` to the validation path used by `parseAppURL()` (i.e., make `testForInvalidChars` also reject/neutralize a leading `-`/`+`), and/or ensure every git-spawning call site that consumes a deep-link-derived ref name inserts a `--` terminator before the ref argument, consistent with how `filepath` is already defensively resolved with `resolveWithin`. Add an integration test asserting that `branch=--<option>` deep links are rejected as `unknown`, mirroring the existing `parse-app-url-test.ts` suite.

### Proof of Concept
1. Register/observe that Desktop handles `x-github-client://` (or `github-mac://` / `github-windows://`) URLs via `handleAppURL`.
2. Host or send a link: `x-github-client://openRepo/https://github.com/some/repo?branch=--upload-pack=touch%20/tmp/pwned;`
3. `parseAppURL` passes this branch value through `testForInvalidChars` successfully (no blacklisted characters present) and returns an `open-repository-from-url` action with `branch: "--upload-pack=touch /tmp/pwned;"`.
4. `Dispatcher.openBranchNameFromUrl` calls `checkoutLocalBranch(repository, branchName)` with this value unmodified.

**Caveat / unverified step:** I was not able to inspect `app/src/lib/git/checkout.ts`'s actual `git` argument array construction (whether it prepends `--` before the ref) before the tool budget ran out, so I cannot confirm the option-injection is exploitable end-to-end versus merely producing a git error. The concrete, verified defect is the inconsistent/incomplete validation in `parse-app-url.ts`/`sanitize-ref-name.ts` described above; a Devin session with full file access should confirm the downstream `git checkout` invocation to determine full exploitability.

// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
