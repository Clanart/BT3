I found a viable analog. Looking at `_fillSameChain` in `evm/src/apps/intentsv2/IntrinsicIntents.sol`, there is exactly the same bug pattern as the referral-fee report: two different formulas compute what should be the same underlying value (the escrow amount owed for a fill), and the mismatch is used to release funds.

### Title
Same-chain partial-fill escrow release uses a proportional-share formula inconsistent with the surplus-adjusted fill amount, allowing under/over-release of escrow - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` computes `fillAmount` for the *first* fill of an output leg using a surplus-adjusted formula (capped at `totalRequired`, with the excess split into `beneficiaryShare`/`protocolShare`), but computes the escrowed input to release for a non-final leg using a *different*, naïve proportional formula `(order.inputs[i].amount * fillAmount) / totalRequired`. These two computations are not reconciled: `fillAmount` is derived after subtracting `protocolShare`/`beneficiaryShare` logic on the *output* side, while the escrow release on the *input* side is a simple ratio against `totalRequired`, not against the amount actually reserved for that solver call. This mirrors the referral-fee bug where the reward calculation and the "amount charged" calculation used different formulas for what should be the same value.

The escrow released for a leg is computed as `order.inputs[i].amount * fillAmount / totalRequired` — a ratio taken against the *original* per-leg output requirement — while `fillAmount` itself was derived from a branch that already applied surplus/dust logic on the output side (capping at `totalRequired` when overpaid). Because multiple output legs (`order.output.assets`) can independently drive `_partialFills[commitment][outputToken]` while all draw from the *same* pooled `_orders[commitment][token]` escrow bucket for a given input token index `i`, and each leg's `fillAmount`/`escrowedAmount` is computed independently per-index without any cross-check against the true remaining escrow balance for that token, a solver filling multiple legs in specific orders (or a single leg across multiple partial-fill transactions with different `solverAmount` values) can cause the proportional escrow computed for one leg's `fillAmount` to diverge from the amount actually reserved for it. The `if (amountFilled == totalRequired)` branch takes the literal live escrow balance (correct), but the `else` branch (still-partial) recomputes from `order.inputs[i].amount` scaled by `fillAmount/totalRequired`, ignoring any escrow already consumed by prior partial fills against that same token from *other* output legs indexed differently, or ignoring rounding drift accumulated over repeated partial fills.

### Impact Explanation
If the proportional formula in the non-final branch releases more escrow than is actually left for that specific `order.inputs[i]` entry (e.g., due to repeated partial fills with rounding, since integer division truncates independently on each call rather than tracking a running remainder), later legitimate withdrawals for the same commitment/token could under-deliver or the contract could attempt to release more than `_orders[commitment][token]` holds, reverting on underflow in `_withdraw`'s `escrowed - amount` check — a griefing/lock condition — or, if the ratios drift the other way, the solver can be shorted on their rightful escrow, i.e. a wrong-amount payout to the solver relative to the fraction of goods delivered. This falls under "logic attacks" / "unauthorized transaction/execution amount" for bridge/escrow custody.

### Likelihood Explanation
Medium — this requires a solver to structure a legitimate sequence of partial fills across the same order commitment, which is a permissionless, unprivileged action (any solver can call `fillOrder` repeatedly with partial `solverAmount`). No malicious peer, relayer, or governance actor is needed.

### Recommendation
Track a per-commitment/per-token running "released" counter and always compute the escrow release as `min(desired proportional share, remaining escrow for that token)`, or reconcile `fillAmount` and `escrowedAmount` from a single source of truth (e.g., derive `fillAmount` from the same base used for `escrowedAmount`, or vice versa) so that the sum of all `escrowedAmount` releases across partial fills can never diverge from `_orders[commitment][token]`'s ledger, mirroring the referral-fix recommendation of deriving the secondary value directly from the primary computed value rather than an independently-derived formula.
