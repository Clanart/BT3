### Title
ProtoJSON parse-error messages embed raw (potentially sensitive) field values with no redaction path - ([File: python/google/protobuf/json_format.py])

### Summary
`json_format.py`'s JSON→message parser builds `ParseError` exception text by directly interpolating the raw JSON field value (or the underlying converter's exception, which itself contains the raw value) into the error string. Unlike `TextFormat`/`DebugString`, which have an explicit `debug_redact` mechanism (`FieldOptions.debug_redact`, `TextFormat::Printer::shouldRedact`, `DebugFormat`) to keep sensitive field contents out of human-readable/log output, no equivalent redaction exists on the ProtoJSON parse-error path. A consuming application that logs `ParseError`/`ValueError` text on a marshaling failure (the exact failure mode described in the external report) will disclose the raw field content, which is the same "logged during a specific marshal-error path" bug class as GHSA-rcw7-pqfp-735x.

### Finding Description
`_ConvertFieldValuePair` in `python/google/protobuf/json_format.py` raises `ParseError` strings that splice the raw JSON value directly into the message text, e.g. `'repeated field {0} must be in [] which is {1} at {2}'.format(name, value, path)` [1](#0-0) , and on scalar conversion failure it re-wraps the underlying `ValueError`/`TypeError` (which itself typically contains the offending raw value) into `'Failed to parse {0} field: {1}.'.format(name, e)` [2](#0-1) .

Protobuf already recognizes this exact "value leaks into an error/debug string" hazard for the TextFormat/DebugString surface: `debug_redact` field options and `TextFormat::Printer::shouldRedact` / `DebugFormat` exist precisely to strip sensitive field contents before they reach logs [3](#0-2) , and generated schemas can mark fields `debug_redact = true` for this purpose [4](#0-3) . That protection, however, is scoped to `Printer`/`DebugString` output only — it is never consulted by the JSON (or TextFormat) *parse-error* code paths, which build their error text straight from the raw input value with no redaction check at all.

This is the direct analog of the external report's invariant failure: in secrets-store-sync-controller, a specific marshaling-error branch bypassed the normal handling of `csi.storage.k8s.io/serviceAccount.tokens` and logged the raw token; here, a specific parse-error branch bypasses protobuf's own field-redaction invariant and logs the raw field value.

### Impact Explanation
If the consuming application parses attacker- or system-supplied ProtoJSON containing a sensitive field (a token, credential, or secret value carried in a message field) and that field fails type conversion (wrong JSON type, out-of-range number, malformed string, etc.), the resulting `ParseError`/`ValueError` text — commonly logged verbatim by calling code (`logger.error(str(e))`, `logging.exception(...)`) — will contain the raw sensitive value. Anyone with read access to those logs (the same "actor with access to controller logs" threat model as the original report) can recover the secret. Impact is confidentiality-only (C:H, I:N, A:N in the same CVSS shape as the original advisory), matching CWE-532.

### Likelihood Explanation
Requires: (1) a schema field carrying secret-like data that also participates in ProtoJSON parsing, (2) a type-mismatch/format error on that specific field during parse, and (3) application code that logs the raised exception text. All three are plausible/common patterns (schema validation + generic exception logging), but none are guaranteed by protobuf itself — the disclosure is conditional on the consuming application's logging behavior, same as the original advisory's caveat ("Tokens are only logged when there is a specific error…"). Likelihood is Low–Medium.

### Recommendation
- Do not interpolate raw field values into `ParseError`/`ValueError` messages in `json_format.py`; report only the field name/path and error type/kind, not the value.
- If the raw value must appear for debuggability, gate it behind the same `debug_redact`-aware machinery already used by `TextFormat.Printer`/`DebugFormat`, so fields marked `debug_redact = true` are also protected on the parse-error path, not only the print path.
- Document that catching and logging `google.protobuf.json_format.ParseError`/`text_format.ParseError` text can leak field contents, matching the guidance protobuf already gives around `DebugString`/`debug_redact`.

### Proof of Concept
Conceptually (not run — flagging this as unverified given tool/time limits):
```python
from google.protobuf import json_format
import my_proto_pb2  # message with `token` field typed int32 for illustration

msg = my_proto_pb2.MyRequest()
bad_json = '{"token": "super-secret-service-account-token-xyz"}'  # token wrongly typed as string for an int32 field
try:
    json_format.Parse(bad_json, msg)
except json_format.ParseError as e:
    log.error(str(e))  # <-- raw secret value "super-secret-service-account-token-xyz" ends up in application log
```
The `ParseError` text produced by `_ConvertFieldValuePair`/`_ConvertAndSetScalar` includes the literal offending value in its message [2](#0-1) , so any application-level `log.error(str(e))` on this exception discloses the raw field content — the same class of disclosure as the external report, just triggered via a ProtoJSON type-conversion failure instead of a Kubernetes controller's provider-parameter marshaling failure.

**Caveat:** I was not able to fully inspect the internals of `parseInt32`/`parseBool`/`_ConvertAndSetScalar` within the tool budget to confirm every helper embeds the raw value verbatim (some paths were only partially retrieved), so the exact wording of every downstream `ValueError` is not 100% confirmed — but the two error-construction sites cited directly and unambiguously interpolate the raw value into the exception text.
