### Title
Aggregator's `InternalSendTx` gRPC method is reachable without authentication when `client_verification` is disabled - (File: core/src/rpc/interceptors.rs / core/src/servers.rs)

### Summary
The `only_aggregator_and_self` interceptor is the only enforcement point that checks `leaf_cert == our_cert` for `Internal*`-prefixed aggregator gRPC methods such as `internal_send_tx`. When the deployment sets `client_verification = false`, `create_grpc_server` swaps this interceptor for `Interceptors::Noop`, which unconditionally forwards every request, so `internal_send_tx` becomes callable by any TCP peer that can reach the aggregator's gRPC port.

### Finding Description
The binding the code intends to enforce is: `caller_leaf_cert == our_cert` for any RPC whose `grpc-method` metadata starts with `"Internal"` [1](#0-0) [2](#0-1) .

This equality is only checked inside `only_aggregator_and_self`, which itself is only invoked when the interceptor variant is `OnlyAggregatorAndSelf` [3](#0-2) . `create_grpc_server` selects the interceptor variant based on `config.client_verification`: if false, it builds the `InterceptedService` with `Interceptors::Noop` instead of `OnlyAggregatorAndSelf`, and correspondingly configures the TLS server without a `client_ca_root`, meaning no client certificate is even requested during the TLS handshake [4](#0-3) . `Noop::call` returns `Ok(req)` unconditionally, performing no identity check at all [5](#0-4) .

Consequently, when `client_verification=false`, any unauthenticated network peer able to reach the aggregator's public gRPC port can send an `InternalSendTx` request, and it will be dispatched straight to `AggregatorServiceImpl::internal_send_tx` without any caller-identity check, since the `is_internal`/`leaf_cert == our_cert` equality is never evaluated under `Noop`.

### Impact Explanation
This matches the defined High-severity category "an unauthenticated state-changing or broadcasting call": under the stated configuration, an attacker without any TLS certificate, key share, or protocol role can invoke an `Internal*`-prefixed aggregator method meant to be restricted to the aggregator calling itself, causing state mutation of the `tx_sender` scheduling table and potential broadcast/fee-bumping of an attacker-chosen transaction through the node's Bitcoin RPC connection. The severity and practical blast radius (e.g., whether this can be leveraged to consume the aggregator's own UTXOs for fee-bumping, or is limited to relaying already-valid, self-funded transactions) depends on the exact behavior of `tx_sender.insert_try_to_send`, which I was not able to fully read within the available tool budget.

### Likelihood Explanation
This requires the specific deployment precondition `client_verification=false`, which is a legitimate configuration option in `BridgeConfig` [6](#0-5) , plus network reachability to the aggregator's gRPC port. Under this configuration the exploit requires no BTC cost beyond constructing a request, and is trivially repeatable since `Noop` never performs any check.

### Recommendation
Do not rely solely on TLS peer-certificate identity for the `Internal*` method authorization boundary when `client_verification` can be disabled. Either always enforce the `is_internal` equality check independent of the `client_verification` setting (e.g., reject `Internal*`-prefixed calls outright, or require loopback/local-only transport) when `Noop` is selected, or disallow disabling client verification on the aggregator's public-facing listener entirely, only allowing `Noop` on a private/loopback-bound socket.

    fn call(&mut self, req: Request<()>) -> Result<Request<()>, Status> {

            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),

        }
