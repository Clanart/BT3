## Title
`EvmHost.dispatch()`/`fundRequest()` swap excess native token is refunded to the Host contract, not the payer — analogous to the zero-slippage `addLiquidity()` bug — ([File: evm/src/core/EvmHost.sol])

## Summary
The external report's core defect is: a function performs an AMM operation with **no slippage tolerance parameter**, so the caller's provided amount must exactly match what the AMM needs, and any mismatch (due to price movement) either reverts the whole call or silently mishandles the excess. `EvmHost.sol`'s native-token fee-payment path has the same structural defect: it calls Uniswap V2's `swapETHForExactTokens` with the entire `msg.value` and no `amountInMax`/slippage guard, and it never captures or forwards the refund the router sends back.

## Finding Description
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all execute the identical pattern when a user pays in native token: [1](#0-0) 

```solidity
if (msg.value > 0) {
    address[] memory path = new address[](2);
    address uniswapV2 = _hostParams.uniswapV2;
    path[0] = IUniswapV2Router02(uniswapV2).WETH();
    path[1] = feeToken();
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
```

`swapETHForExactTokens` is an **exact-output** swap: `post.fee`/`get.fee`/`amount` is the exact output, and the entire `msg.value` sent is treated as the maximum acceptable input (functionally, `amountInMax = msg.value`), with no independent slippage/`amountInMax` field exposed to the caller — the same "expects zero slippage" shape as the reported `createPair()` bug, just inverted (here the ceiling is `msg.value` rather than the floor being `amountDesired`).

Two consequences follow directly from Uniswap V2 Router semantics:

1. **Excess refund is misdirected.** When the actual amount-in needed is less than `msg.value`, the Router refunds the difference via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])`. Because `EvmHost` itself is the caller of the router (`IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)`), `msg.sender` from the Router's perspective is **`EvmHost`**, not the original transaction sender who funded `msg.value`. The refunded ETH lands in `EvmHost`'s own balance and `EvmHost` never forwards it back to the dispatching caller. `dispatch()` and `fundRequest()` contain no post-swap refund logic — this repo's grep of the file shows no such handling adjacent to the swap calls.
2. **DoS under price movement (zero-slippage half of the bug class).** If the exchange rate moves unfavorably before the swap executes (block reordering, MEV, normal price drift), the required input can exceed `msg.value`, and `swapETHForExactTokens` reverts the entire `dispatch`/`fundRequest` call — exactly the `createPair()` failure mode in the source report, but here it blocks message dispatch and fee top-ups rather than pool creation.

The user-facing docs confirm there is no way for the caller to specify slippage tolerance or receive a refund address other than what `EvmHost` computes internally: [2](#0-1) 

## Impact Explanation
This is a genuine funds-loss path, not merely a DoS: any caller (dApp or end user) who sends `msg.value` with even a small safety margin above the exact fee-token conversion needed — which is standard practice, since the exact price at execution time can't be known in advance — has the difference silently swallowed into `EvmHost`'s balance instead of being returned to them. Repeated over many dispatches, this constitutes an unbounded, protocol-wide leakage of user ETH into the Host contract with no accounting or recovery path visible in `dispatch()`/`fundRequest()`. This satisfies the bounty's "loss of funds" criterion because it happens under ordinary, honest usage (any overestimate of `msg.value`), not only via a malicious peer, relayer, or front-runner.

## Likelihood Explanation
High. Overpaying `msg.value` slightly is the normal safety behavior recommended for AMM-based native payments (since `quote()` itself is explicitly documented as sandwich-vulnerable and only for off-chain estimation): [3](#0-2) 

Every such call using native payment triggers the misdirected-refund condition; no privileged actor, relayer collusion, or malicious peer is required.

## Recommendation
- Track `address(this).balance` before and after the `swapETHForExactTokens` call, and refund any leftover native token to `_msgSender()` (the actual payer) rather than letting it sit as the Host's raw ETH balance.
- Alternatively, use `swapExactETHForTokens` semantics with an explicit `amountOutMin`/slippage parameter surfaced to the caller, and forward all unspent value back to the payer.
- Add a view/accounting mechanism (or event) so any ETH inadvertently retained by `EvmHost` from historic dispatches can be identified and recovered by governance, and add regression tests asserting `msg.sender`'s ETH balance change equals exactly the fee-equivalent amount consumed.

## Proof of Concept
1. Attacker or ordinary user calls `EvmHost.dispatch{value: X}(DispatchPost{fee: F, ...})` where `X > amountInNeededForF` (a normal safety margin, e.g., `X = 1.05 * quotedAmount`).
2. `swapETHForExactTokens{value: X}(F, [WETH, feeToken], address(this), deadline)` executes: it uses `amountIn = getAmountsIn(F)[0] < X`, and the Router refunds `X - amountIn` to its immediate caller, which is `EvmHost`.
3. `EvmHost.dispatch()` returns without any logic that forwards this refund to `_msgSender()`; the difference is now stuck in `EvmHost`'s own ETH balance, unaccounted for by any state variable.
4. Repeating this for every native-fee dispatch across all users demonstrates a systematic drain of user-supplied safety margin into the Host contract, with no path to recover it visible in `evm/src/core/EvmHost.sol`.

Note: I was not able to fully confirm from the indexed portion of `EvmHost.sol` whether a separate governance/host-manager-only withdrawal function exists elsewhere in the file that could sweep this stray ETH back out (the grep matched 6 occurrences of `receive()/fallback()/withdraw/balance`-related tokens but the surrounding context for those wasn't retrieved). If such a sweep function exists, the issue is a fund-lock/gray-loss issue funneled to governance's control rather than a fully unrecoverable loss; if it does not, the ETH is permanently stranded. A Devin session with full file access is recommended to confirm this before treating the severity as final.
