## Title
`updateRemoteUrl` silently rewrites a trusted git remote based on GitHub API `clone_url`, enabling remote-hijack via repository rename/name-squatting ("repo-jacking") - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` auto-rewrites the local `origin` remote URL whenever the GitHub API reports a different `clone_url` for the repository the app believes is associated with the working directory. The decision to trust and apply that change relies entirely on a stale, string-based checkpoint (`gitHubRepository.cloneURL`) rather than a stable repository identity (API repository id). This mirrors the Livepeer finding's core defect: a security-relevant decision is made against a cache value that is not properly kept in sync with the ground truth, allowing corrupted/attacker-influenced data to silently propagate into an authoritative state (here, the user's push/fetch destination) without any invalidation or identity check.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` resolves the owner/name pair from the *current* git remote URL via `matchGitHubRepository` (`app/src/lib/repository-matching.ts`), then calls `api.fetchRepository(owner, name)`. GitHub's API transparently follows repository renames/transfers: querying by an old `owner/name` path returns the *current* repository object (with a new `clone_url`) if that name was renamed away and, more importantly, will return whatever repository currently occupies that owner/name path if it was recreated by a different actor after the original was renamed away ("repo-jacking").

That freshly fetched `apiRepo` is passed to `updateRemoteUrl`: [1](#0-0) 

The guard logic is:
- `protocolsMatch` — only checks that the scheme (https/ssh) didn't change.
- `remoteUrlUnchanged` — compares the *current* git remote against `gitHubRepository.cloneURL`, a cached value stored in the local Dexie database the last time the association was upserted.
- `!urlsMatch` — the new API URL differs from what's currently configured.

If all three hold, `gitStore.setRemoteURL(...)` is called, silently overwriting `origin` in `.git/config` — with no user prompt, no diffing of repository identity (`id`/`dbID`), and no confirmation that the "new" clone URL actually still points at the repository the user originally trusted.

The invariant that's supposed to hold — "the cached `gitHubRepository.cloneURL` faithfully represents the same underlying repository we're pointed at" — is exactly the kind of checkpoint the Livepeer report shows can go stale: the cache (`gitHubRepository` record in `RepositoriesStore`) is written by `upsertGitHubRepository`/`setGitHubRepository` based on whatever the API returns for an owner/name lookup, with no verification that the numeric GitHub repository ID is unchanged across refreshes. `GitHubRepository.dbID` is explicitly documented as "no relation to the API ID" ( [2](#0-1) ), meaning nothing in this model or in `updateRemoteUrl` ties the cached record back to a specific immutable upstream repository. A rename/transfer + name-squat sequence causes `apiRepo.clone_url` to silently diverge from the true intended target while every existing guard (`protocolsMatch`, `remoteUrlUnchanged`, `urlsMatch`) is satisfied by construction.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes" and "unauthorized... credential/token exfiltration" categories: once `origin` is rewritten, all subsequent `git push`/`git fetch`/`git pull` operations — whether initiated through Desktop or an external terminal using the same working copy — target the attacker-controlled repository without any visible warning in the UI (there is no dialog, confirmation, or log entry surfaced to the user for this specific auto-rewrite; it happens as a background side effect of `_refreshRepository`/`repositoryWithRefreshedGitHubRepository`). This can result in:
- Source code and commit history (potentially containing secrets) being pushed to an attacker's repository instead of the legitimate one.
- The attacker serving crafted content back on `fetch`/`pull`, since the remote now legitimately points at infrastructure they control.

### Likelihood Explanation
The attacker's primitive here matches the allowed threat model: "a git remote/proxy response" the app trusts and "a GitHub API object" returned for a repository the app is tracking. The attacker does not need local access — they only need to (a) wait for/trigger the target repository to be renamed or transferred (a normal GitHub action, sometimes done routinely by org reorganizations, or the attacker can preemptively squat popular repo names that get abandoned/renamed), and (b) register the vacated `owner/name`. Desktop performs this refresh automatically on `_refreshRepository` (app open, focus, add-repository flow), so no unusual user action is required beyond normal use of the app on an already-added repository.

### Recommendation
- Pin the cached `GitHubRepository` association to the upstream repository's immutable numeric API `id`, and have `updateRemoteUrl` (and `repositoryWithRefreshedGitHubRepository`) refuse to auto-update the remote if the API-returned `id` differs from the previously stored one — surfacing a warning/prompt to the user instead of silently rewriting the remote.
- Require explicit user confirmation before ever mutating `.git/config`'s remote URL based on API data, rather than doing it silently as a side effect of a background refresh.

### Proof of Concept
1. User adds/clones a repository `origin` pointing at `https://github.com/victim/repo.git`; Desktop stores `gitHubRepository.cloneURL = https://github.com/victim/repo.git` (see `updateRemoteUrl` test fixtures illustrating this matching logic: [3](#0-2) ).
2. The `victim` account renames/transfers `repo` away (e.g., renames to `repo-old`), freeing the `victim/repo` path.
3. Attacker (or the same "victim" account maliciously, or a compromised org) creates a new repository at `victim/repo`, distinct in identity but with the same owner/name path.
4. On next app focus/refresh, `_refreshRepository` → `repositoryWithRefreshedGitHubRepository` re-resolves owner/name from the *existing* remote URL, calls `api.fetchRepository('victim','repo')`, which now returns the attacker's repository object with a (potentially) different `clone_url` (e.g. a fork URL or same-looking URL but different backing repo).
5. `updateRemoteUrl` sees `remoteUrlUnchanged === true` (matches old cached `cloneURL`), `protocolsMatch === true`, `urlsMatch === false` if the clone_url string differs even slightly (e.g. case, `.git` suffix normalization edge cases, or a genuinely different clone URL) and calls `gitStore.setRemoteURL(...)`, rewriting `origin` with no user interaction.
6. The user's next `git push` from Desktop or terminal silently goes to the attacker's repository.

Note: I was not able to fully verify from the index alone every runtime nuance (e.g., exact `urlMatchesRemote` normalization rules, whether GitHub's redirect actually changes `clone_url` string in typical rename cases) since some file contents may be truncated by index size limits — a full Devin session with terminal/browser access would be needed to trace `urlMatchesRemote` and reproduce the end-to-end rename/squat scenario against the live GitHub API to confirm exploitability with 100% certainty.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```
