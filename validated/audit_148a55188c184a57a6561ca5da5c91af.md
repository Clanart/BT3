### Title
Automatic remote-URL rewrite from untrusted GitHub API data can silently redirect future pushes/fetches - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` silently overwrites the local `origin` remote's URL with whatever `clone_url` the GitHub API currently returns for the associated repository, gated only by structural URL-matching heuristics rather than any stable repository identity check. [1](#0-0) [2](#0-1) 

### Finding Description
`updateRemoteUrl(gitStore, gitHubRepository, apiRepo)` is invoked with an `IAPIRepository` object fetched from the GitHub API and, when three heuristic conditions hold, calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` which in turn shells out to `git remote set-url` for the repository's default remote, with no user confirmation. [3](#0-2) [4](#0-3) 

The three gating conditions are:
- `urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)` – false when the new `clone_url` differs from the current local remote.
- `protocolsMatch` – only compares `http`/`https` protocol strings.
- `remoteUrlUnchanged = urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)` – compares the *previously cached* API `cloneURL` (itself untrusted, sourced from an earlier API response) against the current remote. [5](#0-4) 

None of these checks validate a stable repository identity (e.g. a numeric repository id). `urlMatchesRemote` only parses hostname/owner/name out of the URL strings via `parseRemote` and does case-insensitive string comparison — it is purely structural, not identity based. [6](#0-5) 

Because the check is driven entirely by attacker-observable/attacker-influenceable API fields (`clone_url`, `html_url`) and not by an immutable repository id, a scenario such as a repository rename followed by a different party claiming the vacated `owner/name` slug ("repo-jacking") — or any other path where the API's `clone_url` for the tracked `gitHubRepository` legitimately changes to point at a different underlying repository while the owner/name structure still parses cleanly — will cause `!urlsMatch` and `remoteUrlUnchanged` to both evaluate as expected, triggering an automatic, silent `git remote set-url` on the user's local clone. All subsequent `fetch`/`pull`/`push` operations, which resolve their target purely from `remote.name`/`remote.url` in the git-store, will now silently operate against the attacker-controlled endpoint. [7](#0-6) 

This matches the bug-class of the seed report: a value that should be validated/pinned against a trusted anchor (there, the *new* amplification parameter; here, a stable repository identity) is instead derived from a value that can drift/be attacker-influenced (there, the stale `amplification` state var; here, the API-supplied `clone_url`), causing an operation (supply calculation / remote rewrite) to silently use the wrong value.

### Impact Explanation
If the user's future `git push` is silently redirected to a URL the attacker controls, the user's local branch history, commit content, and potentially credentials sent as part of the push transport (depending on protocol) go to an endpoint the user never chose or confirmed, satisfying "silent corruption of what the user commits or pushes." The write happens with zero UI, zero prompt, and no diff shown to the user, unlike the manual "Repository Settings → Remote" flow which does show the URL to the user. [8](#0-7) 

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control or influence the `clone_url`/`html_url` fields returned by the GitHub API for a repository the user already has cloned and tracked in Desktop (e.g. via a repository-rename/username-squatting scenario), a condition outside the user's direct control but requiring no local access, malware, or leaked credentials — matching the "attacker controls a GitHub API object" acceptance criterion.

### Recommendation
Do not rewrite the local remote URL based solely on structural URL matching of API-supplied fields. Anchor the comparison to a stable, non-reusable repository identifier (e.g., the repository's numeric `id` from the API) captured at the time the `GitHubRepository` association was first made, and/or require explicit user confirmation before calling `gitStore.setRemoteURL` in `app/src/lib/stores/updates/update-remote-url.ts`.

### Proof of Concept
1. User clones/opens a GitHub-associated repository in Desktop; `gitHubRepository.cloneURL` and the local `origin` remote both point at `https://github.com/owner/repo`.
2. The upstream repository at `owner/repo` is renamed/transferred such that the slug `owner/repo` becomes claimable, and a different (attacker-controlled) repository takes over that exact `owner/repo` path (or any equivalent scenario in which the GitHub API subsequently returns a different `clone_url` for the tracked `gitHubRepository` while still parsing to the same owner/name shape expected by `urlMatchesRemote`).
3. On the next background repository refresh, `updateRemoteUrl` is invoked with the new `apiRepo.clone_url` [1](#0-0) 
4. `protocolsMatch` is true (both https), `remoteUrlUnchanged` is true against the stale cached `cloneURL`, `urlsMatch` is false against the new `clone_url`, so `gitStore.setRemoteURL(...)` silently runs `git remote set-url origin <attacker-clone-url>`.
5. Any subsequent Fetch/Pull/Push in Desktop now silently targets the attacker's repository without any dialog shown to the user.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
