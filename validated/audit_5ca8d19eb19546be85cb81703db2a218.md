## Analog Found: Re-entrant sign-in flow lets a stale OAuth completion resolve into a newer, unrelated sign-in session

### Title
Re-entrant `SignInStore.authenticateWithBrowser` overwrites in-flight OAuth state, letting a stale callback complete a newer sign-in with the wrong account - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
The reported Pod.sol bug is a classic check-effects-interactions violation: a shared value (`shares`) is mutated, then an external call is awaited, and a re-entrant call during that await can complete using the wrong/duplicated state. The GitHub Desktop analog is in `SignInStore`: `this.state.oauthState` is mutated as "effects" before awaiting the OAuth token exchange ("interaction"), and the resolution path re-reads the *live* `this.state.oauthState` after the awaits instead of the value that was current when the call started. If a second sign-in flow is initiated (re-entrancy) while a first flow's deep-link resolution is still awaiting network calls, the first flow's fetched account gets delivered to the second flow's callback.

### Finding Description
`authenticateWithBrowser` sets a fresh `oauthState` object (containing `onAuthCompleted`/`onAuthError`, which are the `resolve`/`reject` of that call's own `Promise<Account>`) into `this.state`, then opens the browser: [1](#0-0) 

The only guard against re-entrancy is a check that the store is already in `Authentication` or `ExistingAccountWarning` — it never checks whether an `oauthState` promise is already pending: [2](#0-1) 

When the deep link callback (`x-github-client://oauth?code=...&state=...`) arrives, `resolveOAuthRequest` validates the CSRF `state` against `this.state` *at entry*, then performs two awaited network calls (`requestOAuthToken`, `fetchUser`). After the awaits it reads `this.state.oauthState.onAuthCompleted(account)` again — a **fresh, live read**, not the object captured before the awaits: [3](#0-2) 

If, during those awaits, the store re-enters `authenticateWithBrowser` for a second sign-in (e.g. the user retries, switches endpoints, or an attacker-influenced flow triggers a second "Sign in" action while the first is still resolving in the background), `this.state.oauthState` is replaced with the second flow's `onAuthCompleted`/`onAuthError`. When the first flow's `resolveOAuthRequest` finally resumes, it calls the **second flow's** `onAuthCompleted` with the **first flow's** fetched `Account`. That resolves the second flow's promise, which then runs its own `.then()`: [4](#0-3) 

This calls `this.emitAuthenticate(account)` and completes the second flow's `resultCallback` with the account belonging to the *first* flow's endpoint/session, not the account the second flow's caller intended to authenticate.

### Impact Explanation
This is an unauthorized-account-binding condition: a caller who initiated one sign-in flow (e.g. to a specific GitHub Enterprise endpoint, or a retry after cancelling) can have its `resultCallback` and `emitAuthenticate` fired with an unrelated account resolved from a stale, concurrent flow. Downstream consumers of the sign-in `resultCallback` (repository cloning flows, SAML re-auth retry, "sign in to unlock repository" flows — see `dispatcher.requestBrowserAuthenticationToDotcom`, `saml-reauth-required.tsx`) trust that the resolved account corresponds to the endpoint/context they requested. Silent cross-wiring here can bind actions (repository access, retried Git operations) to the wrong account/session.

### Likelihood Explanation
No explicit guard prevents a second `authenticateWithBrowser`/sign-in initiation while a first one's `oauthState` promise is still unresolved; the only state check is the coarse `SignInStep` check, which a second sign-in attempt (still in `Authentication`) or an `ExistingAccountWarning`-triggered restart satisfies. This makes the race triggerable purely through normal application flows without any special privileges — an existing pending browser-based sign-in plus any second sign-in trigger (UI retry, endpoint-switch, or a queued deep link delivered late) is sufficient. I was not able to fully verify from the index whether any UI-level disabling prevents the user (or an automated flow) from re-triggering sign-in while one is outstanding; a background agent with full repo/runtime access should confirm this before treating it as immediately exploitable end-to-end.

### Recommendation
Capture the specific `oauthState` (and its `onAuthCompleted`/`onAuthError`) in a local variable at the start of `resolveOAuthRequest`, and only invoke that captured reference, never a freshly re-read `this.state.oauthState`. Additionally, guard `authenticateWithBrowser`/sign-in initiation so that starting a new browser-based OAuth flow while one is already pending either rejects the earlier flow's promise explicitly or is refused until the prior flow resolves/times out — mirroring the `withIsCommitting`/`withPushPullFetch` "single in-flight operation" guard pattern already used elsewhere in this codebase: [5](#0-4) 

### Proof of Concept
1. User starts sign-in flow A (e.g. `requestBrowserAuthenticationToDotcom` or Enterprise sign-in), browser opens for OAuth.
2. Before flow A's deep-link callback returns to the app, the user (or a script/second trigger) starts sign-in flow B (e.g. clicks "Sign in" again, or a SAML-reauth retry triggers another `beginBrowserBasedSignIn`). This overwrites `this.state.oauthState` with flow B's `onAuthCompleted`/`onAuthError`, per `authenticateWithBrowser`'s lack of a pending-flow guard.
3. Flow A's browser tab completes and the OS delivers `x-github-client://oauth?code=<A_code>&state=<A_state>`. `resolveOAuthRequest` validates `<A_state>` against `this.state.oauthState.state` — but by now `this.state.oauthState` is flow B's object (whose `.state` may or may not match, depending on timing of steps 2/3; if flow B hasn't yet reached `Authentication` with its own callback set, or if timing allows A's state to still be current at the CSRF check but B's object to land before the `onAuthCompleted` call at line 353), the token exchange and `fetchUser` proceed for flow A's code, then `this.state.oauthState.onAuthCompleted(account)` is invoked — resolving flow B's promise with flow A's account.
4. Flow B's `.then()` (in `authenticateWithBrowser`) fires `emitAuthenticate(accountFromFlowA)` and completes flow B's `resultCallback` with that account, even though flow B's caller expected an account tied to its own sign-in context/endpoint.

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
