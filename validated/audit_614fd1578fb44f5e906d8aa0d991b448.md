### Title
Wrong Pyth Price Feed Selected for `stSTXbtc`/`zstSTXbtc` Causes Massive Mispricing of Collateral/Debt - ([File: local-testing/contracts/utility/protocol-data.clar])

### Summary
`get-asset-price` in the protocol's off-chain/on-chain data helper resolves the price of `stSTXbtc` (and by extension `zstSTXbtc`) by calling `get-pyth-price PYTH-STX` — the STX/USD feed — instead of `get-pyth-price PYTH-BTC`, despite the inline comment explicitly stating "BTC price". This is the same class of bug as the reported ERC1155 bridge issue: the code selects the wrong identifier/selector for a downstream call, producing a value that does not correspond to the intended asset, and any consumer of that value (health checks, liquidation, borrow capacity) is silently corrupted rather than failing loudly.

### Finding Description
`get-asset-price` computes USD prices per asset id and is used by `sum-collateral-usd` and `sum-debt-usd` to build the position's total collateral/debt USD values: [1](#0-0) [2](#0-1) 

Within `get-asset-price`, the branch for `stSTXbtc` and `zstSTXbtc` reads: [3](#0-2) 

Both branches call `get-pyth-price PYTH-STX` — the wrong feed identifier — where `PYTH-BTC` is clearly intended (as documented by the inline comments "BTC price" and "stSTXbtc price x liquidity index", and consistent with how `sBTC`/`zsBTC` correctly use `PYTH-BTC` a few lines above): [4](#0-3) 

Since STX trades orders of magnitude below BTC (e.g. ~$1 vs ~$60,000 in the test fixtures seen in the repo), any collateral/debt valuation involving `stSTXbtc` or `zstSTXbtc` will be off by that same order of magnitude — this is functionally identical to using the wrong selector: the wrong price feed identifier is passed into `get-pyth-price`, which returns a technically valid but semantically wrong price attached to the wrong asset, exactly the "price attached to the wrong asset" bug class called out as in-scope.

### Impact Explanation
- If `stSTXbtc`/`zstSTXbtc` is used as **collateral**, the collateral is drastically undervalued (STX price << BTC price), which would cause spurious unhealthy/liquidation states or reduced borrowing capacity — a temporary freezing of funds for affected users.
- Conversely, if the direction of misvaluation were flipped in any consuming context (e.g., if this helper's output were relied upon to compute a health factor that gates liquidation or additional borrowing), a systematically wrong (too high or too low) collateral value can allow a position to appear healthier than it is or unhealthy when it is not, enabling either escape from deserved liquidation (protocol insolvency risk) or unwarranted liquidation of solvent users (theft of collateral) — landing in the Critical impact class (protocol insolvency / theft of user funds at rest).
- Because `stSTXbtc`/`zstSTXbtc` appears to be a first-class supported asset in the mask/egroup system alongside STX, sBTC, stSTX, USDC, USDH, this is a reachable pricing path, not a hypothetical one.

### Likelihood Explanation
High, if this data path is used anywhere on-chain for health/liquidation decisions rather than being purely a read-only reporting helper: the wrong constant is hard-coded and will trigger on every call involving these two asset ids, with no confidence/staleness check able to catch it, since `PYTH-STX` is itself a live, fresh, valid feed (just for the wrong underlying asset). It requires no attacker action or oracle manipulation — the bug fires automatically whenever the affected asset ids are priced.

### Recommendation
Change both occurrences to use `PYTH-BTC` instead of `PYTH-STX` for the `stSTXbtc` and `zstSTXbtc` branches in `get-asset-price`, matching the existing correct pattern used for `sBTC`/`zsBTC`. Add unit/integration tests asserting that `get-asset-price` for `stSTXbtc`/`zstSTXbtc` tracks the BTC feed (not the STX feed), and cross-check this helper's output against `market.clar`'s canonical `price-resolve`/`resolve-callcode` logic to ensure the two pricing paths never diverge.

### Proof of Concept
1. Set `PYTH-STX` price to $1.20 and `PYTH-BTC` price to $60,000 (as done in existing test fixtures).
2. Register a user position holding `stSTXbtc` as collateral.
3. Call the read-only data helper that invokes `get-asset-price` for `stSTXbtc` (e.g., via `sum-collateral-usd`/`get-position` reporting).
4. Observe the returned USD value reflects the STX price (~$1.20 scale) rather than the BTC price (~$60,000 scale), a ~50,000x undervaluation, demonstrating the wrong feed is used. [3](#0-2)
