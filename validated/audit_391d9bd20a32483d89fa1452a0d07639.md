### Title
Front-runnable offset registration lets an attacker claim a script's identity, causing misattribution of received funds - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`Scanner` maps `ScriptBuf -> Scalar` offset surjectively and attributes every scanned output purely by `script_pubkey`. Because `register_offset` silently increments an odd-parity offset until the resulting key is even, two distinct requested offsets can map to the same script. Whoever registers first owns the script's identity; a later, legitimate registration returns `None`, and all future funds sent to that script are attributed to the attacker's offset. This is the same bug class as the Gitcoin issue: a public identifier (here, a script/offset) can be bound by an unprivileged party before the legitimate party, making legitimate and illegitimate entries indistinguishable.

### Finding Description
`p2tr_script_buf` returns `None` for odd-Y keys, so `register_offset` loops `offset += ONE` until an even key is found (mod.rs:184-195). If offset `o` yields an odd key, the script registered is actually for `o+1`. Consequently the map `scripts: HashMap<ScriptBuf, Scalar>` (mod.rs:153-156) is surjective in offsets: requesting offset `o` may register the script belonging to `o+1`, and a subsequent `register_offset(o + 1)` (or any offset whose requested key equals `key + (o+1)*G`) hits `self.scripts.contains_key(&script)` and returns `None` (mod.rs:187-189). The code itself documents this: "offsets are surjective, not bijective, and the order offsets are registered in may determine the validity of future offsets" (mod.rs:174-175).

`scan_transaction` then attributes outputs solely via `self.scripts.get(&output.script_pubkey)` (mod.rs:205-211), returning a `ReceivedOutput` stamped with whichever offset won the registration race — with no on-chain or cryptographic binding between the output and the intended semantic owner of that offset.

An attacker who can observe or predict a pending `register_offset(o)` call (offsets in practice are deterministically derived, e.g. `hash_to_F(KEY_DST, "branch"/"change"/"forward")` as used by the processor's `scanner()` in `processor/src/networks/bitcoin.rs:333-344`, and the group key is public) computes the even-adjusted key, registers a colliding offset first, and either (a) permanently blocks the legitimate registration (the call returns `None`, and in the processor usage `.expect("offset collision")` panics, halting the scanner), or (b) causes deposits to that script to be reported under the wrong semantic classification — funds sent to what should be an internal (change/branch/forward) script get reported as the attacker's kind, or vice versa. The attacker can also pre-send dust to the colliding script; `scan_transaction` reports it as a received output of the claimed kind.

### Impact Explanation
- Funds received at a script are attributed to whichever offset was registered first, so deposits can be classified under the wrong offset/kind — e.g., an internal change or forwarded output reported as an external user deposit carrying attacker-controlled `InInstruction` data, or the reverse.
- A legitimate offset registration can be permanently denied (returns `None`; downstream callers may panic as in `scanner()`), which is a liveness/availability failure for the affected address path.
- Because there is no distinguisher between "the offset that was meant to own this script" and "the offset that registered it first," downstream accounting cannot separate legitimate from illegitimate attribution — exactly the impact described in the Gitcoin report.

### Likelihood Explanation
Exploitation requires the attacker to influence or predict the sequence/content of offset registrations. Offsets derived from public, deterministic inputs (group key + fixed hash-to-field labels) are fully predictable once the group key is public, and any integrator that registers offsets derived from user-influenced data (e.g., per-deposit or per-user offsets) is directly exposed to front-running. The collision itself requires only finding a requested offset whose parity adjustment lands on the target script — roughly a 1-in-2 chance per candidate, so trivially computable. The finding is Medium rather than High because it requires the integrator to register attacker-influenced/predictable offsets; with fully unpredictable registration order and inputs the window shrinks, though the surjectivity flaw remains latent.

### Recommendation
Make registration bijective and authenticated:
- Refuse to silently adjust the offset inside `register_offset`; instead return the adjusted offset to the caller and require the caller to confirm, or fail outright when `offset` needs adjustment, so a requested offset can never register a script the caller didn't intend.
- Track requested offsets (not just scripts) so two requests for keys that collide on parity are both rejected deterministically rather than order-dependently.
- Where an offset has a designated semantic purpose, bind the offset value to that purpose (e.g., derive via `hash_to_F` over a domain including the purpose and never accept externally supplied offsets for internal kinds), so an attacker-supplied offset cannot occupy another kind's script.

### Proof of Concept
```rust
// Attacker knows `key` (public group key) and predicts that the integrator
// will register offset o, where key + o*G has odd Y.
let mut scanner = Scanner::new(key).unwrap();

// Attacker first registers o' = o - 1 (or any offset whose even-adjusted
// result equals o). p2tr adjusts: script(key + o'*G) where o'' is the
// first even-parity value >= o'. If o'' == o, the attacker's registration
// claims the script the legitimate registration needed.
let stolen = scanner.register_offset(o_prime).unwrap(); // returns o

// The legitimate registration now fails -- the script is already claimed.
assert!(scanner.register_offset(o).is_none());

// Every future on-chain output paying script(key + o*G) is reported by
// scan_transaction as belonging to the attacker's offset, including dust
// the attacker sends themselves to force a misclassified ReceivedOutput.
let out = scanner.scan_transaction(&tx_paying_script_of_o);
assert_eq!(out[0].offset(), o); // attributed to attacker's registration
```

Note on scope confidence: the concrete reachable path is `Scanner::register_offset`/`scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` combined with deterministic, publicly computable offsets (as in `processor/src/networks/bitcoin.rs:313-346`). Whether a given deployment lets an unprivileged party influence registration order is integrator-dependent; the surjective mapping and order-dependence are unconditionally present in the in-scope code.
