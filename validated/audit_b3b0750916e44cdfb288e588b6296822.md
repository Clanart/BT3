## Analog Found: Fee Refund Ignores the Actual Funder in `fundRequest`

### Title
Timeout refunds send the entire accumulated relayer fee to the original `payer`, not to whoever actually funded it via `fundRequest` - (File: `evm/src/core/EvmHost.sol`)

### Summary
This is a direct structural analog of the Babylon `RefundTx` bug: funds are refunded to a fixed "payer" identity recorded at dispatch time, while the entity that actually supplied a portion of the funds (via a later top-up) is never tracked and is not the timeout-refund recipient.

### Finding Description
When a request is dispatched, `EvmHost.dispatch(DispatchPost)`/`dispatch(DispatchGet)` records `FeeMetadata{sender: post.payer, fee: post.fee}` keyed by commitment [1](#0-0) , and separately for GET requests, `sender: _msgSender()` [2](#0-1) .

`fundRequest` allows **any address**, not just the original payer, to top up the relayer fee for a pending request: [3](#0-2) 

Crucially, `fundRequest` only mutates `metadata.fee += amount` — it never updates or tracks `metadata.sender`, and there is no per-funder ledger. The Foundry test suite explicitly documents that "someone else can fund your request" [4](#0-3) , confirming this is an intentional, unrestricted, permissionless path.

When the request later times out, `dispatchTimeOut(PostRequestTimeout)`/`dispatchTimeOut(GetRequestTimeout)` refund the **entire accumulated fee** (original + all top-ups) to `meta.sender` only: [5](#0-4) [6](#0-5) 

This exactly mirrors the Babylon issue: the transaction fee (here, relayer fee) can be supplied by an entity other than the recorded payer/sender, but on refund the full amount — including the portion contributed by the other entity — goes only to the originally recorded `sender`, not to whoever actually funded that increment.

### Impact Explanation
Any address that calls `fundRequest` to top up someone else's pending request (e.g., to speed up delivery, a common documented use case: "someone else can fund your request") permanently loses that contribution if the request times out, because the refund path in `dispatchTimeOut` has no concept of "who funded which portion" — it refunds 100% of `meta.fee` to the single `meta.sender` address recorded at dispatch. This is a direct loss-of-funds bug for any third-party funder, matching the required impact class ("stealing or loss of funds ... to the rightful beneficiary and amount").

### Likelihood Explanation
This requires no privileged actor, relayer collusion, or malicious peer — it is triggered by the normal, publicly documented flow: dispatch a request, have any third party call `fundRequest` (a fully permissionless, unprivileged public entrypoint) to top up the fee, and have the request time out (which can happen naturally or be induced by simply not relaying it). This is entirely within the reach of an ordinary unprivileged user/funder and is explicitly exercised in the test suite as valid usage.

### Recommendation
Track per-funder contributions (e.g., a `mapping(bytes32 => mapping(address => uint256))` of commitment → funder → amount) and, on timeout, refund each funder their own contributed amount rather than sending the entire `meta.fee` to the single recorded `sender`. Alternatively, disallow `fundRequest` from being called by anyone other than the original `payer`, or require the caller to specify/lock in the refund recipient for their own contribution at funding time.

### Proof of Concept
1. Alice dispatches a POST request with `payer: alice`, `fee: 0` via `EvmHost.dispatch`.
2. Bob calls `fundRequest(commitment, 10e18)`, paying 10e18 fee tokens from his own balance — allowed since `fundRequest` has no payer check [3](#0-2) .
3. `_requestCommitments[commitment]` is now `{sender: alice, fee: 10e18}` — Bob's contribution is untracked as his own.
4. The request never gets relayed and times out. Anyone submits the timeout proof; `dispatchTimeOut(PostRequestTimeout)` executes `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` [7](#0-6) .
5. Alice receives the full 10e18 refund even though she contributed 0; Bob, who paid 10e18, receives nothing.

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function fundRequest(bytes32 commitment, uint256 amount) external payable notFrozen {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                amount, path, address(this), block.timestamp
            );
        } else {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), amount);
        }

        FeeMetadata memory metadata = _requestCommitments[commitment];
        if (metadata.sender == address(0)) revert UnknownRequest();

        metadata.fee += amount;
        _requestCommitments[commitment] = metadata;

        emit RequestFunded({commitment: commitment, newFee: metadata.fee});
    }
