### Title
`SignableTransaction::new` omits the OP_RETURN data output when calculating transaction weight, undercharging the fee — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Union Finance report where `getSupplyRate` omits a factor (`utilizationRate`) from its computation, `SignableTransaction::new` computes the transaction's weight/vbytes — and therefore `needed_fee` and the change amount — using only `payments`, ignoring the OP_RETURN `data` output that is pushed onto `tx_outs` beforehand. The resulting fee factor silently excludes up to ~83 bytes of output weight.

### Finding Description
In `SignableTransaction::new`, the `data` output is appended to `tx_outs` at lines 194-202, but the weight calculation at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, where `calculate_weight_vbytes` builds the template transaction's `output` field exclusively from `payments` (lines 85-93) plus the optional `change` output (lines 95-99). The OP_RETURN output — up to 80 bytes of data plus script overhead — is never included in `weight`/`vbytes`. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) is underpriced by `fee_per_vbyte * vbytes(OP_RETURN output)`.
2. The `TooLowFee` minimum-relay check (line 211) is evaluated against the understated `vbytes`, so it can pass when the real transaction does not meet `DEFAULT_MIN_RELAY_TX_FEE`.
3. When a `change` output exists, `fee_with_change` (line 227) is similarly understated, so the change output is over-credited and the *actual* fee (`sum(inputs) - sum(outputs)`, line 139-141) is fixed at the too-low `fee_with_change`. Unlike the no-change case, the shortfall cannot be absorbed by leftover funds.

An unprivileged caller controls `data` (any `Vec<u8>` up to 80 bytes) via the public `SignableTransaction::new` API, making the underestimate deterministic and proportional to `data.len()`.

### Impact Explanation
The produced `SignableTransaction`, once signed via `TransactionMachine`/`complete`, broadcasts a transaction whose effective sat/vbyte rate is strictly below the caller-specified `fee_per_vbyte`, and potentially below the default minimum relay fee despite `TooLowFee` not triggering. The transaction can be rejected by relay policy or languish unconfirmed, and any dependent protocols consuming `needed_fee()`/`fee()` (e.g., fee amortization of external outputs as described in `spec/processor/UTXO Management.md`) will account an incorrect fee. This is a permanent, deterministic miscalculation — not a probability — affecting every transaction carrying `data` and `change`.

### Likelihood Explanation
Any use of the wallet to create a transaction with both an OP_RETURN payload and a change output hits this. The trigger requires no adversarial position — just supplying `Some(data)` and `Some(change)` to the public constructor. Severity is bounded (a modest fixed satoshi shortfall per transaction), so Medium is appropriate rather than High.

### Recommendation
Include the data output in the weight estimation. Either build the OP_RETURN `TxOut` before calling `calculate_weight_vbytes` and pass the full output list (payments + OP_RETURN), or add the serialized size of the OP_RETURN output (`8 + varint + script len`) to the computed weight/vbytes. Apply the same correction in the `change` branch's `calculate_weight_vbytes` call at line 226.

### Proof of Concept
```rust
// inputs: a single ReceivedOutput with ample value
// payments: [(p2tr, 1000)], data: Some(vec![0u8; 80]), change: Some(p2tr), fee_per_vbyte: F
let tx = SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0; 80]), FEE).unwrap();
// tx.needed_fee() == FEE * vbytes(tx without the OP_RETURN output)
// tx.transaction().output.len() == 3 (payment + OP_RETURN + change)
// Actual vsize of the signed tx > assumed vbytes by ~90 vbytes-worth of weight contribution,
// so tx.fee() / actual_vsize < FEE, and may be < DEFAULT_MIN_RELAY_TX_FEE / 1000.
```
