## Title
Silent skip of unresolved conflicted files in Copilot conflict resolution allows corrupted merge/rebase commit with unmerged content mixed as if resolved - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions()` in `app-store.ts` writes and stages the file resolutions produced by the Copilot conflict-resolution flow before the user finalizes a merge/rebase/cherry-pick. For each `resolution` in `copilotResolutions`, the code can `continue` (skip) a file without ever staging it or otherwise flagging it as still unresolved, most notably when `resolveWithin` rejects the path as outside the repository. [1](#0-0) 

### Finding Description
The function loops over AI-produced `copilotResolutions` and, for each entry, either:
- Applies a manual delete/keep resolution via `_updateManualConflictResolution`, or
- Validates the path with `resolveWithin(repository.path, resolution.path)` and, if valid, writes the resolved content and pushes the path into `pathsToStage`. [2](#0-1) 

When `resolveWithin` returns `null` (a path-traversal or out-of-repo path from a malicious/compromised model response) the code logs a warning and does `continue` — it never records that this file failed to resolve, never adds it back to a "still conflicted" set, and never blocks the caller from treating the merge as ready to finish. [1](#0-0) 

This mirrors the reported bug class exactly: a per-item loop that is supposed to update a tracking value (here: "this file is still conflicted / not yet staged") on every iteration, but silently omits the update on the error branch, leaving the aggregate state (`pathsToStage`, and by extension the assumption that all `copilotResolutions` entries were applied) inconsistent with reality — just like `saleSupplyMinted` failing to track minted tokens in the original report.

Only files that made it into `pathsToStage` are explicitly `git add`-ed: [3](#0-2) 

Nothing downstream re-validates that every path in the original conflict set was either staged or explicitly deferred to manual resolution before the "Continue Merge"/"Continue Rebase" action proceeds — the caller (invoked from the Copilot conflicts result dialog's "Continue Merge" button) assumes the write+stage step accounted for all conflicts.

### Impact Explanation
If a file's conflict resolution path is rejected by `resolveWithin` (e.g. the model — driven by attacker-controlled repository content, since the prompt fed to the model includes file paths, commit messages and PR titles from the fetched repository/PR — returns a manipulated or malformed `path` that resolves outside the repo, or is otherwise skipped), that file is silently dropped from the "resolved" set with only a `log.warn`. The user is shown a "Continue Merge" affordance believing all conflicts are handled, but the corresponding file on disk still contains raw `<<<<<<<`/`=======`/`>>>>>>>` conflict markers and is still marked unmerged in the index for that path. If the subsequent commit/rebase-continue step does not itself hard-fail on remaining unmerged entries, the user can end up committing a file that still contains literal conflict markers, or the git operation could error in a way that leaves the repository in a stuck state — either way, "what the user commits or pushes" is silently corrupted or the operation misleads the user about its true state, without any explicit warning tying back to which specific file was skipped.

### Likelihood Explanation
The attacker primitive is realistic under the stated threat model: the content fed to Copilot's conflict-resolution session — file paths, commit messages, PR titles/descriptions — originates from a repository/PR the user has cloned or is merging, which is exactly the "attacker controls a cloned/fetched repository or GitHub API object" scenario. The LLM output is only lightly validated (`validateResolutionPaths` checks path membership against `expectedFiles`, and `normalizeLLMPath` strips `../`-style prefixes only partially), so an unexpected/traversal-like path reaching `resolveWithin`'s `null` branch is plausible, and that branch's `continue` is the confirmed silent-skip point in the code.

### Recommendation
When `resolveWithin` returns `null` (or any other resolution is skipped for any reason), track it in an explicit "unresolved/failed" collection surfaced back to the UI, and refuse to proceed to "Continue Merge/Rebase" (or force the affected file back into the manual conflict resolution flow) until every original conflicted file is accounted for — either staged, converted into a manual resolution, or explicitly deferred with user acknowledgment. Add an assertion comparing the staged/resolved path set against the original conflicted-file set before allowing the operation to continue, mirroring how `validateResolutionPaths` already guards against missing/duplicate paths at the parsing stage.

### Proof of Concept
1. Trigger a merge/rebase/cherry-pick with conflicts and enable the Copilot conflict-resolution flow.
2. Have the underlying model (or a man-in-the-middle/compromised session) return a resolution whose `path`, after `normalizeLLMPath`, still resolves (via `resolveWithin`) to a location outside `repository.path` — this is plausible if `normalizeLLMPath` only strips a single leading `./` and backslashes without fully canonicalizing traversal sequences like `..\\..\\`.
3. `_applyCopilotConflictResolutions` logs `Copilot resolution skipped: path outside repository: ...` and `continue`s without staging or flagging the file. [1](#0-0) 

4. The user clicks "Continue Merge"; the conflicted file for that path still contains raw conflict markers on disk and unmerged status in the index, but the app's tracking state (`pathsToStage`, and the "all conflicts resolved" assumption) does not reflect this — the resulting commit either fails unpredictably or the file with literal conflict markers is included, corrupting what the user commits.

*Note: I was not able to fully trace the exact caller that invokes "Continue Merge" after `_applyCopilotConflictResolutions` (e.g., whether `continueRebase`/`createMergeCommit` independently re-checks for unmerged paths and blocks), due to running out of tool iterations. This means the ultimate exploitability (whether git itself blocks the commit) is unconfirmed — a Devin session with full repository access should verify the caller in `base-multi-commit-operation.tsx` / `dispatcher.ts` and whether `continueRebase`/`createMergeCommit` validate `trackedFilesAfter`/remaining unmerged paths before committing.*

      // The existing stageManualConflictResolution flow handles the
      // actual git checkout --ours/--theirs and staging at commit time.

        const file = state.changesState.workingDirectory.files.find(
          f => f.path === resolution.path
        )
        if (file === undefined) {
          continue
        }
        const deletedSide = getDeletedSideFromStatus(file)
        if (deletedSide === undefined) {
          continue
        }
        // "keep" → choose the non-deleted side, "delete" → choose the deleted side
        const manualChoice =
          resolution.deleteConflictAction === 'keep'
            ? deletedSide === 'ours'
              ? ManualConflictResolution.theirs
              : ManualConflictResolution.ours
            : deletedSide === 'ours'
            ? ManualConflictResolution.ours
            : ManualConflictResolution.theirs
        this._updateManualConflictResolution(
          repository,
          resolution.path,
          manualChoice
        )
        continue
      }

      const absolutePath = await resolveWithin(repository.path, resolution.path)
      if (absolutePath === null) {
        log.warn(
          `Copilot resolution skipped: path outside repository: ${resolution.path}`
        )
        continue
      }

      // If the user resolved this file externally (e.g. in their editor) while
      // the result dialog was open, git status will report it with no remaining
      // conflict markers. Overwriting it with Copilot's stored content would
      // silently clobber their work, so skip it and let their resolution stand.
      // This mirrors how the manual conflicts dialog determines a file is
      // resolved (`hasUnresolvedConflicts`).
      const onDiskFile = state.changesState.workingDirectory.files.find(
        f => f.path === resolution.path
      )
      if (
        onDiskFile !== undefined &&
        isConflictedFileStatus(onDiskFile.status) &&
        !hasUnresolvedConflicts(onDiskFile.status)
      ) {
        continue
      }

      await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
      pathsToStage.push(resolution.path)
