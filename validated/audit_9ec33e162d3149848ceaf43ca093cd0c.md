Based on my research, the codebase confirms that ERC20/WERC20 precompile addresses are only protected against direct fund loss at the **EVM-call layer** (via a value-sign check in `Execute`), not at the **Cosmos SDK bank-message layer**. `BlockedAddresses()` — the analog of `lz_receive_types`'s "list of required accounts" — is a completeness-critical enumeration built once at app wiring time from static, known-at-genesis address sets, and it structurally cannot include dynamically-registered token-pair precompile addresses.

### Title
Dynamic ERC20/WERC20 precompile addresses are excluded from `BlockedAddresses()`, allowing direct bank `MsgSend` to permanently freeze funds - (File: config/evmd_config.go)

### Summary
`BlockedAddresses()` builds the set of addresses the bank module treats as "cannot receive funds" purely from module account permissions and the **static** precompile lists (`evmtypes.AvailableStaticPrecompiles` and `corevm.PrecompiledAddressesPrague`). It never queries `x/erc20`'s dynamic/native precompile registry, so any address registered later via `EnableDynamicPrecompile`/`EnableNativePrecompile` (i.e., every ERC20 token-pair precompile, including WERC20) is absent from the blocked set at the bank-keeper level.

### Finding Description
`BlockedAddresses()` is computed once, from `maccPerms` and static precompile constants: [1](#0-0) 

This map is passed to the bank keeper as `BlockedAddr()`; it is a static function of chain wiring, not of chain state. Meanwhile, ERC20 token-pair precompiles are registered dynamically at runtime (e.g., from governance `RegisterERC20`, IBC auto-registration in `OnRecvPacket`, or `EnableNativePrecompile`) and stored in `x/erc20` keeper state: [2](#0-1) [3](#0-2) 

The ERC20 precompile explicitly documents that it must never hold real balances of its own denom (or any other denom) because there is no way to recover them, and it defends against this **only for EVM `CALL`-with-value**: [4](#0-3) 

That check only inspects `contract.Value()` on an EVM message call. It does nothing to stop a plain Cosmos SDK `bank.MsgSend` (or `MsgMultiSend`, IBC transfer receive, `x/erc20` `MsgConvertCoin`, etc.) targeting the bech32 representation of that same precompile's address, because `BlockedAddr()` — the sole gate x/bank uses to reject a recipient — was never told about it.

### Impact Explanation
Because the precompile has no private key and no fallback/receive logic to move out arbitrary denoms it did not expect, any coins sent to it via a native `bank.MsgSend` (of any denom, not just the one it represents) become permanently unspendable — there is no code path, ERC20 method, or keeper function that reads or moves an arbitrary balance sitting on a precompile's bech32 address back out. This matches the "Critical permanent freezing/locking of user funds" impact category: an ordinary, unprivileged user (or even an innocent mistake, since these addresses look like normal bech32 addresses and are discoverable via the ERC20 precompile's own address/token-pair metadata) can irreversibly lock funds by sending them there.

### Likelihood Explanation
High. Token-pair precompile addresses are public (queryable via `x/erc20` `TokenPairs`/`TokenPair` queries, and exposed as the ERC20 contract address in wallets/block explorers). Any user with a standard Cosmos SDK bank client can construct a `MsgSend` to that bech32 address; no special privilege, contract interaction, or EVM tooling is required, and the funds do not even need to be of the token pair's own denom.

### Recommendation
Make `BlockedAddr()` consult `x/erc20` keeper state (native + dynamic precompiles) in addition to the static lists, or enforce a `SendRestriction` in the bank module that rejects transfers whose recipient is a registered ERC20/WERC20 precompile address, mirroring the existing protection for `x/precisebank`'s module account (`x/precisebank/keeper/send.go`, which explicitly blocks sends to/from its reserve account).

### Proof of Concept
1. Governance/registration flow (or IBC auto-registration) registers a token pair, giving it precompile address `P` (native or dynamic), tracked only in `x/erc20` store — not in `BlockedAddresses()`.
2. An attacker/naive user submits `MsgSend{From: attacker, To: P, Amount: 100 someDenom}` via the standard bank message server. `BlockedAddr(P)` returns `false` (verified logic path in `config/evmd_config.go:58-82`), so the transfer succeeds.
3. `P`'s balance of `someDenom` now sits on an account with no controlling private key and no code path (ERC20/WERC20 methods only move the token pair's *own* denom via `bank.Send` from the caller, never an arbitrary balance held by `P` itself) capable of ever moving those funds out — permanent loss.

I was not able to directly trace whether an additional `SendRestrictionFn` is registered elsewhere in `evmd/app.go` that might independently block these dynamic addresses (index coverage did not surface such a hook keyed on `x/erc20` precompile state); if such a restriction exists it would mitigate this finding, so it is worth an explicit repo check for `bankKeeper.AppendSendRestriction`/`SetSendRestriction` wiring in `evmd/app.go`.

func BlockedAddresses() map[string]bool {
	blockedAddrs := make(map[string]bool)

	maccPerms := GetMaccPerms()
	accs := make([]string, 0, len(maccPerms))
	for acc := range maccPerms {
		accs = append(accs, acc)
	}
	sort.Strings(accs)

	for _, acc := range accs {
		blockedAddrs[authtypes.NewModuleAddress(acc).String()] = true
	}

	blockedPrecompilesHex := evmtypes.AvailableStaticPrecompiles
	for _, addr := range corevm.PrecompiledAddressesPrague {
		blockedPrecompilesHex = append(blockedPrecompilesHex, addr.Hex())
	}

	for _, precompile := range blockedPrecompilesHex {
		blockedAddrs[cosmosevmutils.Bech32StringFromHexAddress(precompile)] = true
	}

	return blockedAddrs
}

// GetERC20PrecompileInstance returns the precompile instance for the given address.
func (k Keeper) GetERC20PrecompileInstance(
	ctx sdk.Context,
	address common.Address,
) (contract vm.PrecompiledContract, found bool, err error) {
	isNative := k.IsNativePrecompileAvailable(ctx, address)
	isDynamic := k.IsDynamicPrecompileAvailable(ctx, address)

	if available := isNative || isDynamic; !available {
		return nil, false, nil
	}

	precompile, err := k.InstantiateERC20Precompile(ctx, address, isNative)
	if err != nil {
		return nil, false, errorsmod.Wrapf(err, "precompiled contract not initialized: %s", address.String())
	}

	return precompile, true, nil
}
