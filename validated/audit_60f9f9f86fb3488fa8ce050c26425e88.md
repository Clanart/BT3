### Title
Aggregator gRPC server accepts unauthenticated calls to `setup` when `client_verification=false` due to `Interceptors::Noop` performing no identity check - ([File: core/src/servers.rs, core/src/rpc/interceptors.rs])

### Summary
When `config.client_verification` is `false`, `create_grpc_server` builds the `ServerTlsConfig` without `.client_ca_root(...)` (no mTLS client-cert requirement) and wraps the aggregator service in `InterceptedService::new(service, Interceptors::Noop)` instead of `OnlyAggregatorAndSelf`. `Interceptors::Noop::call` unconditionally returns `Ok(req)` with no identity check whatsoever, so any TCP client that completes a plain TLS handshake with the server (no client certificate presented, since none is requested) can invoke any RPC exposed by `ClementineAggregatorServer`, including `setup`.

### Finding Description
The binding that should hold is: `caller-that-successfully-invokes-Aggregator::setup == holder-of-a-recognized-aggregator/self-TLS-client-certificate`. Tracing `create_grpc_server` in `core/src/servers.rs` lines 106-138:

```rust
let tls_config = if config.client_verification {
    ServerTlsConfig::new().identity(server_identity).client_ca_root(client_ca)
} else {
    ServerTlsConfig::new().identity(server_identity)
};
...
if config.client_verification { OnlyAggregatorAndSelf { .. } } else { Noop }
``` [1](#0-0) 

and in `core/src/rpc/interceptors.rs`:
```rust
Interceptors::Noop => Ok(req),
``` [2](#0-1) 

When `client_verification=false`, the server's TLS config never requests a client certificate at all (no `client_ca_root`), and the interceptor applied is `Noop`, which performs zero authorization/identity checks compared to `only_aggregator_and_self`, which validates `req.peer_certs()` against pinned `aggregator_cert`/`our_cert` DER bytes at `core/src/rpc/interceptors.rs` lines 36-77. With `Noop`, the equality above is never evaluated — any bytes reaching the socket and completing a normal (non-mutual) TLS handshake are treated as authorized, so `ClementineAggregator::setup` (and every other aggregator RPC) becomes reachable to an anonymous caller who holds no key share, certificate, or credential.

### Impact Explanation
Confirmed: this is an unauthenticated, state-changing RPC exposure — `setup` is a state-changing call on the aggregator that is reachable without any credential once `client_verification=false`, matching the listed High-severity category "an unauthenticated state-changing or broadcasting call." I was not able to fully trace `AggregatorServer::setup`'s internal effects (i.e., whether it mutates a live, in-memory/DB-persisted `VerifierPublicKeys` set that is later re-read when constructing or verifying transactions for deposits that are already committed) within the available iterations, so I cannot independently confirm the more severe claim that repeated unauthenticated `setup` calls permanently freeze an already-created move-to-vault UTXO's `nofn_xonly_pk`. That extended claim would require reading `AggregatorServer::setup`'s implementation and how/where its output is persisted and subsequently consumed by move-to-vault/payout transaction construction — this was not verified.

### Likelihood Explanation
The only precondition is that the aggregator is deployed with `config.client_verification=false`; no key share, deposit, or prior interaction is required. Any party capable of opening a TCP/TLS connection to the aggregator's advertised host:port can attempt this at zero BTC cost, and repeatedly.

### Recommendation
Do not gate identity-checking purely on `client_verification`; when `client_verification=false`, the aggregator's TCP service should still require and check client certificates for state-changing/administrative RPCs like `setup` (e.g., always use `OnlyAggregatorAndSelf`/an equivalent authorization interceptor for these methods, or enforce `client_ca_root` unconditionally on the aggregator's listener regardless of the `client_verification` flag, reserving `Noop` only for services/methods that are intentionally public and read-only).

### Proof of Concept
Not reproducible as "Critical/permanent-freeze" without further confirmation of `AggregatorServer::setup`'s persisted effects. A `cargo test` proof of the confirmed unauthenticated-access issue would: start `create_aggregator_grpc_server` with `client_verification=false`; connect a plain `tonic::transport::Channel` with no `Identity`/`ClientTlsConfig` set; call `setup(Empty{})`; and assert the call returns `Ok(_)` instead of `Status::unauthenticated(..)`, demonstrating the equality `caller-identity == authorized-identity` is never checked under this configuration.
