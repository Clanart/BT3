### Title
`updateRemoteUrl()` auto-rewrites a repository's git remote based on a GitHub API `clone_url` while only checking protocol match, not host/identity match - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The external report's broken invariant is: a security-relevant comparison checks *some* related properties of an operation but omits the one property that actually determines trust (owner of the token). The Desktop analog is `updateRemoteUrl()`, which silently rewrites the user's git remote URL to whatever `clone_url` a `GitHubRepository`/API object reports, gated only by a **protocol** equality check — never validating that the new URL still points at the same host/identity the remote was originally configured for.

### Finding Description
`updateRemoteUrl()` decides whether to silently overwrite the repository's configured remote URL using three conditions: `protocolsMatch`, `remoteUrlUnchanged`, and `!urlsMatch`. [1](#0-0) 

The only identity-style check performed is `protocolsMatch`, which merely compares `URL.parse(...).protocol` (i.e. `"https:"` vs `"https:"`), and `remoteUrlUnchanged`, which checks that the *previously known* clone URL still matches the locally configured remote (i.e., the user hasn't manually edited it): [2](#0-1) 

If those hold and the URL differs from what's cached (`!urlsMatch`), the function calls `gitStore.setRemoteURL(...)` and rewrites the remote — with no check that `updatedRemoteUrl`'s hostname/owner corresponds to the same trusted host the repository was originally associated with: [3](#0-2) 

This mirrors the KUMA bug exactly: the code enforces one attribute of the relevant "identity" (protocol) while never checking the actual identity-defining attribute (host/owner) before performing a trust-sensitive mutation (rewriting the remote that all subsequent `fetch`/`push`/`pull` operations rely on).

### Impact Explanation
The git remote URL is the value that determines where all subsequent `git push`, `git fetch`, and `git pull` operations for that repository go, and which host `envForRemoteOperation`/`envForProxy` use to resolve proxies and authenticate: [4](#0-3) 

If this value can be silently swapped to an attacker-controlled host that merely shares the same `https:`/`ssh:` protocol scheme, the user's local commits can be silently redirected to a destination the user never approved — this falls squarely under the explicitly allowed impact class "silent corruption of what the user commits or pushes," since neither the UI nor the user is prompted before the rewrite happens.

### Likelihood Explanation
The trigger requires an attacker-influenceable `IAPIRepository`/`GitHubRepository` object whose `clone_url` differs from the locally stored remote but keeps the same protocol scheme — e.g. a repository the victim has already added being renamed/transferred (a scenario the API legitimately reports), or a compromised/rogue GitHub Enterprise host response. It does not require local access, admin rights, or pre-existing malware — only a crafted or attacker-influenced API repository object reaching this code path, which matches the "attacker controls a GitHub API object" scenario in the task's Valid Impact list. Note: I could not fully trace every caller that supplies `apiRepo` into `updateRemoteUrl` to confirm the exact upstream trust boundary (e.g., whether GHE server responses are always integrity-checked before reaching this function), so the precise attacker vantage point for spoofing `clone_url` remains uncertain from the indexed code alone.

### Recommendation
Add a hostname/owner-identity check (not just protocol) before rewriting the remote — e.g., require that `URL.parse(updatedRemoteUrl).hostname === URL.parse(remoteUrl).hostname`, or otherwise verify the new URL still resolves to the same GitHub server/account the repository was registered against, and prompt the user for confirmation on host changes rather than silently applying them.

### Proof of Concept
1. User adds/clones a repository whose GitHub API-reported `clone_url` is `https://github.com/victim-org/repo.git`; Desktop's `GitStore.defaultRemote.url` and `gitHubRepository.cloneURL` match this. [5](#0-4) 
2. A subsequent refresh causes Desktop to call `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)` where `apiRepo.clone_url` now reports `https://attacker-host.example/victim-org/repo.git` (same `https:` protocol, different host) — this can occur through repo rename/transfer flows or a compromised GitHub Enterprise endpoint response.
3. `protocolsMatch` is `true` (`https:` === `https:`), `remoteUrlUnchanged` is `true` (user hadn't manually edited the remote), and `urlsMatch` is `false` — the guard passes. [6](#0-5) 
4. `gitStore.setRemoteURL(...)` silently repoints `origin` to `attacker-host.example` with no user prompt; the next `git push` from Desktop is sent to the attacker's host.

  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
