### Title
Trust decisions written to global `safe.directory` are never revoked, letting an attacker-controlled repository silently regain execution trust after path reuse - (File: app/src/lib/git/config.ts)

### Summary
The invariant broken here mirrors the Wildcat bug: a security gate ("is this directory trusted / is this market registered") is keyed off a persistent allow-list entry that is never cleaned up when the corresponding tracked object is removed. In Wildcat, `WildcatArchController.removeMarket()` didn't clear the registration state consumed by `createEscrow()`. In Desktop, `Repository` removal doesn't clear the `safe.directory` entry consumed by Git's ownership check, so the bypass persists even when Desktop no longer considers the path part of a tracked repository.

### Finding Description
When Desktop detects a directory with "dubious ownership" (owned by a different OS user), `getRepositoryType()` returns `{ kind: 'unsafe', path }` (`app/src/lib/git/rev-parse.ts:57-63`). The UI then offers a "Trust Repository" button that calls `addSafeDirectory(path)` (`app/src/lib/git/config.ts:176-189`), which appends the path to the **global** `safe.directory` git config value via `addGlobalConfigValueIfMissing`. This exception is not scoped to Desktop's in-memory `Repository` record, the repository's identity (e.g. remote URL, initial commit, or git dir), or any revocation hook — it is a bare filesystem path written to `~/.gitconfig`.

`app/src/ui/missing-repository.tsx` and `app/src/ui/add-repository/add-existing-repository.tsx` both warn explicitly: *"Adding untrusted repositories may automatically execute files in the repository."* This acknowledges that trusting a path is a security-relevant decision that enables automatic execution of repository content (hooks, `.gitattributes`-driven filters, etc.).

However, `removeRepository`/`_removeRepository` (referenced in `app-store.ts`) only deletes the repository entry from Desktop's `RepositoriesStore` database — there is no corresponding call to strip the path from `safe.directory`. Once a path has been trusted, it remains trusted at the Git level indefinitely, regardless of whether Desktop still tracks a repository there or whether the directory's contents/ownership have since changed (e.g., a shared machine, a re-imaged path, container reuse, or an attacker who gains write access to that same path after the original repo is removed).

This is the same class of bug as the Wildcat report: the removal operation (`removeMarket()` / repository removal) does not update the state consulted by a downstream security check (`isRegisteredMarket()` / `getRepositoryType()`'s `unsafe` detection combined with `safe.directory`), so the check either wrongly blocks a legitimate actor (Wildcat) or wrongly permits an illegitimate one (Desktop) once the tracked object no longer corresponds to what was originally vetted.

### Impact Explanation
An attacker who can place content at a path previously trusted by the victim (shared/multi-user machines, restored disk images, container/VM reuse, symlink or mount-point reuse, or simply a path recycled after the user removes the original repo and later clones something else there) can have Git treat their attacker-controlled repository as trusted without any new ownership prompt. Given Desktop's own stated threat model ("adding untrusted repositories may automatically execute files in the repository"), this results in automatic execution of attacker-supplied repository content on the victim's machine — a code-execution primitive triggered purely by directory/path reuse, with no re-validation of ownership or content identity.

### Likelihood Explanation
Requires a specific but realistic precondition: the victim must have previously trusted a directory ownership exception at a path that is later reused by different content owned by a different user (typical in shared workstations, CI runners, multi-tenant VMs/containers with recycled home directories, or simply removing/re-cloning at the same path). No admin rights or pre-existing malware are needed on the attacker's side beyond eventually gaining write access to that specific path — a condition Git's own dubious-ownership check exists specifically to defend against, but which Desktop's `safe.directory` write undermines by never revoking the exception.

### Recommendation
Bind trust decisions to repository identity rather than bare path, and revoke them on removal:
- When a `Repository` is removed via `removeRepository`, invoke a new `removeSafeDirectory(path)` (a `git config --global --unset safe.directory <path>` equivalent) to revoke the trust exception.
- Alternatively/additionally, avoid relying solely on `safe.directory` path matching; re-validate ownership (or bind the exception to the repository's `gitDir` real path with an ownership fingerprint) before treating a path as trusted again after Desktop no longer had it tracked.
- At minimum, prompt the user to re-confirm trust if a previously-unsafe path is being re-added as a new repository, rather than silently succeeding due to a stale `safe.directory` entry.

### Proof of Concept
1. On a shared machine, User A clones/creates a repo at `/shared/project`, Desktop detects dubious ownership, and User A clicks "Trust Repository" → `addSafeDirectory('/shared/project')` writes to global `~/.gitconfig`.
2. User A later removes the repository from Desktop (`removeRepository`) — this only deletes the DB row; `safe.directory` in `~/.gitconfig` still contains `/shared/project`.
3. An attacker (a different OS user with write access to `/shared/project`, e.g. another account on the shared machine) replaces the directory contents with a malicious Git repository (with hooks, filters, or other auto-executed content) owned by themselves.
4. User A re-adds `/shared/project` in Desktop via "Add Existing Repository". `getRepositoryType()` runs `git rev-parse --is-bare-repository ...`, which no longer reports "dubious ownership" because the path is still in `safe.directory` — Desktop shows it as a normal, trusted repository with no re-prompt.
5. Any Desktop/Git operation that would execute repository-controlled content (hooks, filters, etc.) now runs against attacker-controlled content without any fresh ownership warning, even though the object User A originally vetted no longer exists. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
