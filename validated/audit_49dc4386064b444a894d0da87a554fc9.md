### Title
Quadratic-time Lagrange interpolation on attacker-controlled signing set size enables CPU DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::view` computes a Lagrange `interpolation_factor` for every included participant, and each factor computation iterates over the entire `included` set, giving O(m²) field multiplications/inversions for a signing set of size m. `SignMachine::sign` calls `view()` on the set of `Participant` keys from an attacker-supplied `HashMap` of preprocesses, so a malicious (or spamming) co-signer can force quadratic work with up to n = 65535 distinct participants — roughly 4×10⁹ field operations — before any preprocess content is validated.

### Finding Description
`interpolation_factor` performs a full pass over `included` per participant:

- `crypto/dkg/src/lib.rs:226-249` — `Interpolation::Lagrange` loops over all of `included` doing field muls plus an inversion.
- `crypto/dkg/src/lib.rs:500-507` — `ThresholdKeys::view` calls `interpolation_factor` once per included participant → O(m²).
- `crypto/frost/src/sign.rs:290-312` — `sign` builds `included` from `preprocesses.keys()` (the participant indexes of deserialized `read_preprocess` messages), only checks `included.len() >= t`, max index ≤ n, and duplicates, then calls `self.params.keys.view(included.clone())` — with no upper bound below n.

This mirrors the `millisecond` ReDoS bug class (CWE-1333/CWE-400): untrusted input length controls super-linear work inside a library routine. In Serai there is no regex, but the Lagrange view construction is the equivalent algorithmic-complexity sink reachable purely from unauthenticated bytes fed to `read_preprocess`/`sign`.

### Impact Explanation
A participant (or anyone able to inject preprocess messages into the coordinator's `sign` call) submits preprocesses keyed under all n participant indexes. Each `sign` invocation then burns O(n²) field operations — for a 16-bit participant space this is billions of multiplications per call — stalling the signing session. Repeated submissions keep the signer CPU-bound, denying threshold-signature service (e.g., blocking bitcoin-serai spends). The same O(m²) cost applies on every retry since `view` runs before share verification can blame anyone.

### Likelihood Explanation
Requires the ability to supply preprocess entries for arbitrary `Participant` indexes in `sign`'s `preprocesses` map — a normal protocol message in the FROST flow (an untrusted-party input per the scope rules). No key material, collusion, or privileged role is needed; indexes 1..=n are all accepted since only `> n` and duplicates are rejected (`sign.rs:302-310`). Work scales quadratically in n, so impact grows with multisig size; for small n it is negligible, which caps severity at Medium.

### Recommendation
Cap the effective signing-set size before interpolation, or compute Lagrange factors in O(m) via prefix/suffix products. At minimum, bound `included.len()` (e.g., reject sets much larger than needed) in `SignMachine::sign` before calling `view`, and/or reorder so preprocess validity is established before the quadratic interpolation pass.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
  }
