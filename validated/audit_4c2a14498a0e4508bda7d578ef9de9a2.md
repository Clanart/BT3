Recursive Clone Explicitly Disables Git's Clone Protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), Reintroducing Malicious-Repo Code-Execution Class - (File: `app/src/lib/git/clone.ts`)

### Summary
When GitHub Desktop clones a repository, it invokes `git clone --recursive` and explicitly sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. This variable is the runtime kill-switch for the upstream Git safety checks (added after the disclosed `.git`/hooks-smuggling clone vulnerabilities affecting case-insensitive/normalizing filesystems and recursive submodule clones) that detect and reject repositories/submodules containing maliciously-crafted paths designed to be interpreted as `.git`, `.git/hooks`, or other sensitive control directories. By forcing this protection off for every clone, Desktop removes a Git-provided guard specifically intended to stop attacker-controlled repository content from smuggling executable hooks during clone.

### Finding Description
`clone()` in `app/src/lib/git/clone.ts` builds the environment for the `git clone --recursive` invocation: [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is Git's toggle for the clone-time protections that validate untrusted content pulled in during `clone --recursive` (including nested submodules), rejecting entries that could be used to place files inside `.git` (e.g., via case-folding, Unicode normalization or NTFS short-name collisions on `.git`, `.git/hooks`, `.gitmodules` tricks) before any hook execution can occur. Desktop unconditionally sets this to `'false'`, which disables that check for *every* clone Desktop performs — including clones of arbitrary, attacker-supplied URLs reached via:
- the `x-github-client://openRepo/...` deep link handled by `parseAppURL` / `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts`, [2](#0-1) [3](#0-2) 
- the `github clone <owner>/<repo>` CLI action, [4](#0-3) 
- and the in-app "Clone repository" dialog, which accepts any URL and, on a PR/branch, will also fetch attacker-controlled refs.

The other clone-time guard added in this codebase, `isClonePathSensitive()`, only validates the *destination directory* on the local disk (blocking clones into `~/.ssh`, `~/.gnupg`, etc.) — it does nothing to validate the *content* being written by `--recursive` submodule clone, which is exactly what `GIT_CLONE_PROTECTION_ACTIVE` is meant to police: [5](#0-4) 

So the destination-path allowlist and the source-content protection are two independent controls, and only one of them is active. There is no other visible mitigation (no submodule URL allowlist, no hooks-path override, no `--no-recurse-submodules` default) that would compensate for disabling the upstream check.

### Impact Explanation
If a cloned/fetched repository (fully attacker-controlled, per the in-scope threat model) contains a submodule or tree entry engineered to be interpreted as a Git control path once written to disk, disabling `GIT_CLONE_PROTECTION_ACTIVE` removes the layer that would normally cause Git to abort the clone instead of writing that entry. Depending on the underlying filesystem behavior this could result in planting a hook or config file that executes on subsequent Git operations Desktop performs against the same working copy (fetch, checkout, merge, LFS filters), i.e., code execution triggered purely by the user cloning/opening a link to a malicious repository — squarely in the "attacker controls a cloned/fetched repository ... result is code execution" category defined as valid impact.

### Likelihood Explanation
The trigger requires nothing beyond what the app already exposes to a remote attacker: publishing a malicious public repository and getting a victim to clone it via the in-app dialog, the `github clone` CLI command, or an `x-github-client://openRepo/...` deep link — all reachable, unprivileged, single-click flows. The vulnerable setting is unconditional (not feature-flagged, not limited to a subset of clones), so every clone Desktop performs runs with the protection disabled.

### Recommendation
Do not disable `GIT_CLONE_PROTECTION_ACTIVE` for attacker-reachable clone flows. Either remove the override entirely and let Git's default protection apply, or, if disabling was done to work around a specific compatibility issue, scope it narrowly and pair it with equivalent explicit validation of clone/submodule content (not just the destination path) before allowing the clone to complete.

### Proof of Concept
Not independently reproduced against the underlying Git protection internals from static analysis alone (the exact filesystem preconditions — e.g., case-insensitive/normalizing volume — could not be verified from the indexed source), but the exploitable configuration is directly visible in code:
1. Attacker publishes a public repository containing a submodule/tree entry crafted to collide with `.git`/`.git/hooks` once materialized on a case-insensitive or normalizing filesystem (the class of input Git's clone-protection mechanism exists to reject).
2. Victim clones the repository through any of Desktop's clone entry points, all of which funnel into `clone()`: [6](#0-5)

Because `GIT_CLONE_PROTECTION_ACTIVE=false` is set, Git performs the clone (including `--recursive` submodule fetch) without the safety check that would otherwise reject the crafted entry, allowing the malicious content to be written where it can later be executed by Git hooks during subsequent, routine Desktop-driven Git operations on that repository.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
