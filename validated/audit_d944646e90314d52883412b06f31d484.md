### Title
IntentGatewayV2's `_paused` circuit-breaker is declared but never enforced on fund-moving entrypoints - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase.sol`, the shared base for the `IntentGatewayV2` intent-settlement contract, declares a public pause flag: [1](#0-0) 

but no `whenNotPaused`-style modifier is defined anywhere in `IntentsBase.sol`, `IntrinsicIntents.sol`, or `IntentGatewayV2.sol`, and none of the escrow-moving entrypoints (`placeOrder`, `fillOrder`, `select`, `cancelOrder`, `onAccept`) check `_paused` before executing. This is the same bug class as the external report: a pause state exists at the protocol/storage level, but the functions that actually move value are never gated by it, so "pausing" the contract gives operators/users a false sense of safety while escrow custody, fills, and redemptions continue unrestricted.

### Finding Description
`_paused` is explicitly commented as `"Appended last to preserve existing storage slots"`, indicating it was added to the storage layout to support a circuit breaker, presumably for use during incident response or upgrades: [2](#0-1) 

However, a full read of `IntentsBase.sol` (598 lines) shows no modifier definition referencing `_paused`, and no usage of it in any guard clause. The value-moving functions that would need protection — `fillOrder` (cross-chain and same-chain), `_fillSameChain`, `_withdraw` (escrow release/refund), `_execute` (calldata execution against escrowed funds), and `_sweepDust` — are all defined without any pause check: [3](#0-2) [4](#0-3) [5](#0-4) 

This exactly mirrors the report's core broken invariant: "a paused-state flag exists in the base/parent contract, but the derived/actual execution path (`distribute` in the original report, `fillOrder`/`_withdraw` here) never consults it," so a paused/halted contract still permits full execution of custody-moving logic — order fills, escrow release to solvers, and dust sweeps.

### Impact Explanation
If `_paused` is ever intended to serve as an emergency stop for the IntentGateway (e.g., during a detected pricing bug, oracle failure, or ongoing exploit), the missing enforcement means escrowed user funds keep flowing to solvers via `fillOrder`/`_withdraw` and dust keeps being swept via `_execute`, regardless of the flag's value. This falls squarely under the bounty's "stealing or loss of funds" and "unauthorized execution" categories: an operator or governance action intended to halt the contract during an incident provides no actual protection, and an attacker exploiting a concurrent bug (e.g., a pricing/oracle manipulation caught mid-incident) can continue draining escrow through `fillOrder` even after the contract is marked paused.

### Likelihood Explanation
This is reachable by any unprivileged caller with no relayer, prover, or admin compromise required — `fillOrder` and `select` are public entrypoints. The only open question is whether any current code path sets `_paused = true` (a setter was not located in the reviewed files); regardless, the storage variable's existence signals an intended-but-unimplemented control, and the absence of any modifier referencing it in the reviewed contracts is a concrete, provable gap in the codebase's access-control surface for the fund-custody logic.

### Recommendation
- Short term: add a `whenNotPaused` modifier that checks `_paused` and apply it to all fund-moving entrypoints in `IntentGatewayV2.sol`/`IntrinsicIntents.sol`: `placeOrder`, `fillOrder`, `_fillSameChain`, `_withdraw`, `_execute`/calldata dispatch, and `_sweepDust`. Ensure `onAccept` (cross-chain settlement delivery) also respects `_paused` for `RedeemEscrow`/`RefundEscrow` processing, or explicitly document why settlement of already-placed orders must remain live during a pause.
- Long term: audit the full apps directory (`BandwidthManager.sol`, `SimplexPaymaster.sol`, etc.) for the same pattern — a declared pause/frozen flag without a consistently-applied guard — since the HFT/WHFT/LzEndpoint apps show the project elsewhere uses OpenZeppelin's `Pausable` correctly, confirming this is an inconsistency specific to `IntentsBase`/`IntentGatewayV2`.

### Proof of Concept
1. Confirm (via a Devin/backend session with full repo access) whether any governance call (e.g., an `UpdateParams`/future `RequestKind` in `IntentsBase.RequestKind`) sets `_paused = true`. Based on the grep here, no such setter was found in `evm/src/apps/**`, meaning the flag is either dead code (setter lives elsewhere, e.g. via direct storage write during an upgrade) or is not yet wired up.
2. Regardless of the setter's location, demonstrate the gap directly: deploy `IntentGatewayV2`, force-set `_paused` to `true` via a storage write (`vm.store` in Foundry) at the slot corresponding to `_paused`, then call `placeOrder` and `fillOrder` with a valid order — both succeed and move escrowed funds, proving the flag has zero effect on the actual custody logic.
3. This demonstrates that any future or existing pause mechanism does not stop fund movement through the IntentGateway, matching the "execution during pause" bug class from the external report.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
