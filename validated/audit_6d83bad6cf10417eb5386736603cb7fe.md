## Title
Unbounded Recursive AccountKey RLP Decoding Causes Stack-Exhaustion DoS - (File: blockchain/types/accountkey/account_key_role_based.go)

## Summary
`AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP` mutually recurse to decode nested `AccountKeyRoleBased` keys with **no depth limit**, mirroring the CVE-2019-20198 bug class (`ezxml_ent_ok()` mishandling recursion → stack consumption on crafted input). An attacker can submit RLP bytes containing thousands of nested `RoleBased` account keys to a public RPC endpoint or as part of an `AccountUpdate` transaction, causing unbounded Go-routine stack growth and a node crash before any semantic "nested composite key" validation ever runs.

## Finding Description
`AccountKeySerializer.DecodeRLP` reads a key type and then calls `s.Decode(serializer.key)`: [1](#0-0) 

When the decoded `keyType` is `AccountKeyTypeRoleBased`, this dispatches to `AccountKeyRoleBased.DecodeRLP`, which decodes a list of byte-strings and, for **each element**, recursively calls `rlp.DecodeBytes(b, &serializer)` — reentering `AccountKeySerializer.DecodeRLP`: [2](#0-1) 

Because each element of a `RoleBased` key can itself be RLP bytes encoding another `RoleBased` key, this recursion depth is entirely attacker-controlled and unbounded by the decoder itself — there is no depth counter or nesting limit enforced during `DecodeRLP`. The only place nested `RoleBased` keys are rejected is a *post-decode* semantic check (`kerrors.ErrNestedCompositeType`), enforced later in `blockchain/state_transition.go`, which is reached only **after** the entire (already-decoded) structure has been built: [3](#0-2) 

This means the stack-exhaustion recursion happens strictly before the nesting-rejection logic can act, so the existing "nested RoleBasedKey is not allowed" safeguard does not protect the decode path.

## Impact Explanation
Two independent reachable paths exist:

1. **Direct public RPC call** — `KaiaAPI.DecodeAccountKey` takes arbitrary caller-supplied bytes and feeds them straight into `rlp.DecodeBytes`, with no transaction construction, signature, or gas payment required: [4](#0-3) 
Any public-RPC caller can trigger unbounded recursion with a single crafted call, crashing the serving goroutine/process (stack overflow panics are typically unrecoverable in Go).

2. **AccountUpdate transaction submission** — `SendRawTransaction`/`SendRawTransactions` decode the full `types.Transaction`, which for `TxTypeAccountUpdate` decodes an `AccountKey` field via the same vulnerable serializer chain: [5](#0-4) [6](#0-5) 
This allows any unprivileged transaction sender to crash a node (or every full node that later re-decodes/re-propagates the same tx) via `eth_sendRawTransaction`/`kaia_sendRawTransaction`, causing a denial-of-service impacting availability.

## Likelihood Explanation
High likelihood: no authentication, no fee payment (RPC decode path), no special account state is required, and the byte pattern needed (a small number of deeply nested short RLP lists) is trivial and cheap to construct — RLP nesting can achieve exponential depth increase with linear input size.

## Recommendation
Enforce a hard nesting-depth limit inside `AccountKeyRoleBased.DecodeRLP` / `AccountKeySerializer.DecodeRLP` (e.g., pass and decrement a depth counter, rejecting decode once depth exceeds 1, since nested `RoleBased` keys are never valid), rather than relying solely on the post-decode `ErrNestedCompositeType` check in `state_transition.go`. Additionally, apply the same guard to `KaiaAPI.DecodeAccountKey` and any other RPC/decode entry point that accepts raw `AccountKeySerializer` bytes from untrusted callers.

## Proof of Concept
1. Construct RLP bytes for an `AccountKeySerializer` whose `keyType = AccountKeyTypeRoleBased`, whose payload is a list containing one element which is itself the RLP encoding of another `AccountKeyTypeRoleBased` serializer, and repeat this nesting N times (e.g., N = 100,000), each level being ~10 bytes, producing a modestly sized (~1MB) payload.
2. Call the public RPC method `kaia_decodeAccountKey` (`KaiaAPI.DecodeAccountKey`) with this hex-encoded payload as `encodedAccKey`.
3. `rlp.DecodeBytes` recurses N times through `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` (nested) with no depth check, exhausting the goroutine stack and crashing the node process.
4. Alternatively, embed the same nested-key payload as the `Key` field of an `AccountUpdate`/`FeeDelegatedAccountUpdate` transaction and submit it via `eth_sendRawTransaction`/`kaia_sendRawTransaction`, triggering the identical unbounded recursion during `Transaction.DecodeRLP` before the tx pool's nested-key rejection logic can run.

```go
func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
```

```go
	}
```
