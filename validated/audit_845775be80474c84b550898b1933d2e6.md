### Title
SSRF via unvalidated mirror URLs and unchecked HTTP redirects in DataLayer file sync - (File: `chia/data_layer/download_data.py`)

### Summary
Chia's DataLayer subsystem fetches `.dat` delta/full-tree files from mirror server URLs using `aiohttp` without ever validating that the destination (or any redirect target) is not an internal/private address. Unlike Gitea's migration endpoint (which at least validates the *initial* URL before allowing a redirect bypass), Chia's DataLayer mirror fetch path performs **no host validation at all**, on the initial URL or on any HTTP redirect `aiohttp` follows automatically. Any user who can publish a DataLayer mirror URL for a store (an on-chain, permissionless action) can point a victim node's outbound HTTP fetch at internal services, using either a direct private-IP URL or a public redirecting URL, since `aiohttp.ClientSession.get()` follows redirects (`allow_redirects=True` by default) with no re-check of the resolved target.

### Finding Description
The vulnerable fetch happens in `http_download()`: [1](#0-0) 

```
async with aiohttp.ClientSession() as session:
    headers = {"accept-encoding": "gzip"}
    async with session.get(
        server_info.url + "/" + filename,
        headers=headers,
        timeout=timeout,
        proxy=proxy_url,
    ) as resp:
        resp.raise_for_status()
        ...
```

`session.get()` here is called with no `allow_redirects=False`, so `aiohttp` transparently follows any `3xx` redirect chain to whatever `Location` the remote server supplies — this is the exact bug class described in the Gitea advisory (redirect target bypasses the SSRF check that was applied to the initial URL). In Chia's case it is actually worse: there is no SSRF check applied to `server_info.url` at all before the request is made, so the same code path is reachable both by directly supplying an internal/link-local address and by using an attacker-controlled redirecting server.

`server_info.url` originates from `ServerInfo` records tied to DataLayer store subscriptions/mirrors, which are populated from on-chain mirror coin data (any wallet owner can create a DataLayer mirror coin advertising an arbitrary URL for a given store id, a standard, unprivileged, spend-bundle-driven action — see `data_layer_wallet.py` mirror creation flow and `dl_wallet_store.py`). This is called during the periodic sync loop: [2](#0-1) 

`fetch_and_validate()` pulls `servers_info` (mirror URLs) for a store and calls `insert_from_delta_file()` → `download_file()` → `http_download()` with that attacker-influenced URL, with no host allow/deny-list check anywhere in the chain: [3](#0-2) 

The context documentation for this module explicitly notes that mirror URLs are an external trust boundary that is supposed to be handled carefully ("Plugin and mirror URLs are external trust inputs"), but the actual code never enforces a host/IP validation step before or after redirect resolution: [4](#0-3) 

Any operator running `chia data subscribe`/mirror-following DataLayer node that syncs a store containing an attacker-supplied mirror URL will have their node make outbound HTTP requests — and follow redirects — to whatever host the attacker specifies, including `127.0.0.1`, RFC1918 ranges, or the cloud metadata address `169.254.169.254`.

### Impact Explanation
This is a Medium/High-impact SSRF: an unprivileged Data Layer participant (anyone who can create a store/mirror coin, a normal wallet spend) can cause any other node subscribing to that store to issue arbitrary outbound HTTP GET requests to internal or link-local addresses reachable from that victim node, including localhost RPC ports or other services on the victim's private network, and via a 302-redirecting external server, bypass any future/naive allow-list applied only to the initial URL. Response bodies are written to disk as delta/tree files; while `insert_into_data_store_from_file()` later validates the content against the wallet-advertised Merkle root (limiting silent data corruption), the SSRF request itself — reaching internal services, triggering side effects, or timing/error-based blind SSRF against unreachable internal endpoints — already succeeds before that validation, and download failures/successes are observable by the attacker via subscription failure/backoff behavior and generation state.

### Likelihood Explanation
Likelihood is meaningful because publishing a DataLayer mirror URL requires only a standard wallet-owned coin spend (no special privilege), and any other node subscribing to or syncing that store id will automatically and periodically attempt these downloads through `periodically_manage_data()` / `update_subscription()` / `fetch_and_validate()` without any manual review of the URL.

### Recommendation
- Add explicit host/IP validation before issuing any HTTP request to a mirror or plugin URL in `http_download()` and `download_file()` (`chia/data_layer/download_data.py`), rejecting loopback, link-local, and RFC1918 destinations unless explicitly allowed by local config.
- Disable automatic redirect following (`allow_redirects=False`) on the `aiohttp.ClientSession.get()` call in `http_download()`, and if redirects must be supported, manually resolve and re-validate each `Location` header against the same blocklist before following it.
- Apply the same validation to `get_plugin_info()` and plugin download/upload POST calls in `chia/data_layer/data_layer.py` and `chia/data_layer/s3_plugin_service.py`, since these also consume externally-supplied `PluginRemote`/mirror URLs.

### Proof of Concept
1. As any wallet user, create a DataLayer store and add a mirror URL pointing to an attacker-controlled HTTP server (standard `create_new_mirror`/mirror-coin wallet spend — no elevated privilege required).
2. Configure the attacker server to respond to delta-file requests with `HTTP 302 Location: http://127.0.0.1:<internal-port>/...` (or directly set the mirror URL to `http://127.0.0.1:<port>/` / `http://169.254.169.254/...` since no validation exists at all).
3. Any other node that subscribes to or syncs the store triggers `DataLayer.fetch_and_validate()` → `insert_from_delta_file()` → `download_file()` → `http_download()` (`chia/data_layer/download_data.py:298-323`), which issues `session.get(server_info.url + "/" + filename, ...)` and transparently follows the redirect to the internal address, reaching a service the attacker could not otherwise contact directly.

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
```
