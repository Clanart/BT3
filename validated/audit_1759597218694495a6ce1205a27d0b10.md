### Title
Front-runnable Reward Sniping in `mWOMSVBaseRewarder` due to Missing JIT-Stake Protection - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder` uses an instantaneous, Synthetix-style `rewardPerTokenStored` update in `_provisionReward`/`queueNewRewards`, and `balanceOf()` reflects a user's `mWomSV` stake immediately after `mWomSV.lockFor()` is called, with no minimum holding period, warm-up, or time-weighted checkpoint. An unprivileged attacker can front-run a `queueNewRewards`/`donateRewards` transaction with a large `lockFor()` deposit, causing the new reward to be distributed pro‑rata over an inflated `totalStaked()` that includes their JIT balance, then call `getReward` (via `MasterMagpie.multiclaim`) to capture a share of that reward without ever having staked during the period it accrued.

### Finding Description
- `mWomSV.lockFor(_amount, _for)` → `_lock` → `MasterMagpie.depositMWomSVFor` → `MasterMagpie._deposit` immediately increments `userInfo[stakingToken][_account].amount` [1](#0-0) , and `mWOMSVBaseRewarder.balanceOf()` reads this value directly with no delay or vesting [2](#0-1) .
- `_deposit` does call `_harvestBaseRewarder` (i.e. `rewarder.updateFor(_account)`) *before* incrementing `user.amount`, which correctly checkpoints `userRewardPerTokenPaid` to the pre-deposit `rewardPerTokenStored` using the OLD balance [3](#0-2) . This prevents the attacker from claiming *already-distributed* historical rewards — that specific vector is blocked.
- However, once the deposit lands, the attacker's inflated balance is immediately counted in `totalStaked()` = `IERC20(mWOMSV).totalSupply()` [4](#0-3) . If a manager's `queueNewRewards`/`_provisionReward` transaction is included afterward (e.g., front-run in the mempool), the new reward is spread as `rewardPerTokenStored += amountReward * 1e18 / totalStaked()` [5](#0-4) , diluting the per-token share paid to genuine long-term lockers and simultaneously entitling the attacker's fresh balance to a full pro-rata cut of that same reward event.
- The attacker can then call `getReward`/`getRewards` through `MasterMagpie.multiclaim` (`onlyMasterMagpie` modifier is satisfied because MasterMagpie is the caller) [6](#0-5)  and receive `_earned()` computed from their now-large `balanceOf()` times the newly added `rewardPerToken` delta [7](#0-6) .
- No penalty stops this: `_calExpireForfeit` is dead code that always returns 0 — `rewardableAmount` is set equal to `_amount` and never reduced, so `forfeitAmount` is always `_amount - _amount == 0` [8](#0-7) . Unlike `vlMGPBaseRewarder`, there is no lock-duration-weighted forfeiture wired into `mWOMSVBaseRewarder`, so no penalty discourages instant-in/instant-out reward harvesting.
- The attacker does not even need to unlock afterward to realize the gain — they can call `getReward` and simply leave the `mWomSV` position in place, so the `startUnlock`/cooldown friction in `mWomSV` is not a real barrier to this specific exploit.

### Impact Explanation
This allows an unprivileged actor to capture a portion of bonus/donated reward tokens intended to accrue to long-term `mWomSV` lockers, simply by timing a large `lockFor` deposit immediately before a `queueNewRewards`/`donateRewards` call and then harvesting. This is a theft of unclaimed yield from other, genuinely long-term stakers, matching the "theft of unclaimed yield" Immunefi impact class. The magnitude scales with the attacker's available mWOM capital relative to `totalStaked()` and the size of the incoming reward.

### Likelihood Explanation
- Requires the attacker to hold/acquire mWOM tokens (no special permission needed) and to observe (via mempool) or predict a `queueNewRewards`/`donateRewards` call by the reward manager.
- `queueNewRewards` is restricted to `managers` (a legitimate, non-malicious, expected periodic operation) — the attacker does not need to collude with or compromise this role, only front-run its public, visible transaction, which is a standard, repeatable MEV-style attack on any EVM chain with a public mempool.
- Capital risk to the attacker is limited to the cost of temporarily locking mWOM (no forced long lockup is required to harvest the reward, since forfeiture logic is a no-op).
- This is fully repeatable for every future reward distribution event.

### Recommendation
- Introduce a minimum staking/holding duration or a reward-eligibility checkpoint (e.g., snapshot balances used for `queueNewRewards` distribution prior to the block in which the reward tx executes, or stream rewards linearly over time rather than instantaneously via `rewardPerTokenStored`) so freshly deposited balances cannot capture rewards for periods they were not staked during.
- Fix `_calExpireForfeit` so that it actually implements a time-weighted forfeiture (as intended, mirroring the pattern that appears functional in `vlMGPBaseRewarder`), penalizing withdrawals/claims from positions that have not met a minimum lock duration, and route forfeited amounts back into `_queueNewRewardsWithoutTransfer` for existing long-term stakers.
- Consider requiring `queueNewRewards` to only account for balances staked at least N blocks/seconds prior to the call (i.e., use a delayed/epoch-based snapshot of `totalStaked()` and per-user balances).

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `mWomSV`, `mWOMSVBaseRewarder`, and a reward token; register the `mWomSV` pool with the rewarder.
2. Have `UserA` (long-term locker) call `mWomSV.lock(1000e18)` and let time pass (irrelevant to reward math since there's no time-weighting).
3. As `Attacker` (0 prior stake), construct the front-run: in the same test, before invoking `rewardManager.queueNewRewards(rewardAmount, rewardToken)`, first call `mWomSV.lockFor(9000e18, attacker)` (attacker owns 90% of `totalStaked()`).
4. Call `queueNewRewards(rewardAmount, rewardToken)` as the manager.
5. Immediately, `Attacker` calls `MasterMagpie.multiclaim([mWomSV])` (routes to `getReward`) and asserts `earned(attacker, rewardToken)` ≈ `rewardAmount * 9000/10000`, despite having staked zero blocks/seconds prior to the reward event.
6. Assert `UserA`'s harvested share is diluted to `rewardAmount * 1000/10000`, i.e., far less than what `UserA` would have received had the attacker not front-run (`rewardAmount * 1000/1000 = rewardAmount`, since attacker had no stake before).
7. Confirm `_calExpireForfeit` returns 0 for the attacker's claim (no penalty applied), proving no existing mechanism mitigates this JIT capture.

        IERC20Metadata(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;

                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**mWOMSVDecimal) / totalStaked();
        }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
