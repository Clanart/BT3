### Title
PedPoP commitments and proof-of-knowledge accept identity points and zero scalars (missing `!= 0` / non-identity validation) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The external report describes consumers failing to reject a zero-valued input (`price == 0`), causing invalid downstream values to be used. The same bug class exists in PedPoP: `Commitments::read` deserializes commitment points via `Ciphersuite::read_G`, which enforces only canonical encoding, and `SchnorrSignature::read` does the same for `R` and `s`. Identity points and zero scalars therefore flow into `verify_r1` and `calculate_share`, where the protocol implicitly requires non-degenerate values. FROST's own `Curve::read_G` explicitly rejects the identity point "for this exact reason", but PedPoP bypasses it by calling the generic `Ciphersuite` reader.

### Finding Description
- `Commitments::read` reads each commitment point with `C::read_G` (`crypto/dkg/pedpop/src/lib.rs:115-124`), which resolves to `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-100`): it checks `from_bytes` success and canonical re-encoding, but never `is_identity()`. Compare with `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`), which adds an explicit `is_identity()` rejection because FROST nonces/commitments must never be identity.
- The accompanying PoK is read with `SchnorrSignature::read` (`crypto/schnorr/src/lib.rs:51-53`), likewise imposing no non-identity/non-zero constraint, and is verified in `verify_r1` via `msg.sig.batch_verify(..., msg.commitments[0], challenge)` (`pedpop/src/lib.rs:323-329`). With `commitments[0] = identity`, the equation `s·G == R + c·A` degenerates to `s·G == R`, which any attacker satisfies trivially (e.g. `s = 1, R = G`), without proving knowledge of any committed secret.
- Downstream, an attacker who transmits their `Commitments` last (a rushing participant) can set any commitment term — including the identity — to cancel other participants' contributions at chosen stripe indices. `calculate_share` computes verification shares as `multiexp_vartime(&exponential::<C>(i, &stripes))` over the summed stripes (`pedpop/src/lib.rs:505-521`). The attacker can force a victim's verification share to the identity while still sending a share that verifies against their own (consistent) commitments, so `share_verification_statements` passes and no blame is assigned.

### Impact Explanation
- PoK degeneracy: the proof-of-knowledge over `commitments[0]` is the mechanism that forces each participant to know their constant coefficient. Accepting `identity` lets a participant register with a degenerate proof (`R = s·G`), and accepting identity at arbitrary positions lets a rushing participant zero out other participants' polynomial terms at a chosen evaluation point.
- Verification-share poisoning: if victim `i`'s verification share becomes the identity while `i`'s actual accumulated secret share is non-zero, every FROST signature share `i` honestly produces will fail `verify_share`. `i` is then framed as a faulty signer and can be excluded, biasing which participants effectively form the threshold key. The protocol's blame logic cannot attribute this, because all PedPoP-level checks passed.
- This is a concrete reachable path: the bytes arrive entirely through `Commitments::read` / `SchnorrSignature::read` / `EncryptedMessage::read`, all listed in-scope untrusted-input APIs.

### Likelihood Explanation
Any DKG participant is an unprivileged network peer supplying these bytes; no collusion, broken BFT, or key compromise is required. The attack needs the attacker to order their commitments message after seeing others' (a standard rushing assumption in DKG threat models) to pick cancelling commitment terms. The degenerate-PoK variant works unconditionally. Medium severity: it enables exclusion/framing of honest participants and degenerate key material rather than direct key recovery.

### Recommendation
- In `Commitments::read` (and in the PedPoP verification path), reject the identity point for every commitment, mirroring `Curve::read_G`'s `is_identity()` check — either use an identity-rejecting reader or explicitly check each decoded point.
- Reject `R = identity` / `s = 0` in `SchnorrSignature::read`, or at minimum before queuing the PoK in `verify_r1`.
- Additionally, reject zero secret shares in `calculate_share` (a share of `0` against an all-identity/evaluates-to-identity commitment set currently passes `share_verification_statements`).

### Proof of Concept
1. Attacker `l` serializes a `Commitments` message for `params.t()` where `commitments[0]` is the canonical encoding of the identity point, and appends `SchnorrSignature { R: C::generator() * s, s }` for arbitrary `s` (e.g. `s = 1`, `R = G`).
2. Victim calls `Commitments::read` → succeeds (identity is canonical). `verify_r1` queues `batch_statements(A = identity)`: `(ONE, R) + (c, identity) + (-s, G) = R - s·G = identity` → batch verification passes; the "PoK" verifies with no committed secret.
3. For the rushing variant: after observing all other participants' commitment vectors, attacker computes, for target `i`, coefficients whose commitments satisfy `eval(C_attacker, i) = -Σ_{j≠attacker} eval(C_j, i)` on the affected stripes (choosing identity wherever convenient). Victim's verification share becomes identity (or another attacker-chosen point); their valid share still passes `calculate_share`, but their later FROST signature shares never verify, causing them to be blamed/excluded while the attacker's messages verified cleanly.
