## Analysis

The external report's core invariant is: **an initializer function that lacks its own on-chain access control, relying instead on "it will always be called atomically," can be front-run by anyone if that atomicity assumption is ever violated.**

Searching Hyperbridge's initializer-style entrypoints, every other one-shot setup function is guarded by an explicit `msg.sender` check baked into the function itself:

- `EvmHost.initialize` checks `_msgSender() != _hostParams.admin` and a `_initialized` flag. [1](#0-0) 
- `HostManager.setIsmpHost` is wrapped in `restrict(_params.admin)`. [2](#0-1) 
- `VWAPOracle.init` checks `msg.sender != _admin`. [3](#0-2) 
- Tron's `IntentGatewayV2.setParams` checks `msg.sender != _admin` even though it is called in a **separate transaction after deployment** in the Tron migration script. [4](#0-3) [5](#0-4) 

The one exception is the main EVM `IntentGatewayV2.initialize()`, which uses OpenZeppelin's `initializer` modifier with **no `msg.sender` check at all**. The contract's own comment states this is intentional: authorization is delegated entirely to the assumption that deployment is atomic. [6](#0-5) 

### Title
Unauthenticated one-shot `initialize()` in `IntentGatewayV2` allows front-running to hijack gateway configuration - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.initialize()` sets the entire `Params` struct (host, dispatcher, `solverSelection`, `surplusShareBps`, `protocolFeeBps`, `priceOracle`) and the cross-chain peer registry, but contains **no caller-authorization check**. It is protected only by OpenZeppelin's `initializer` modifier, which allows exactly one call from *anyone*, and the security guarantee is documented as depending entirely on `initialize` being invoked atomically as part of the CREATE2 proxy-deployment transaction.

### Finding Description
`initialize` is `public` and gated only by the `initializer` modifier — it never checks who the caller is: [7](#0-6) 

The contract's own comment on `_owner` confirms this design choice explicitly: `_owner` "Does not gate `initialize`; atomic CREATE2 deployment already binds the init data to the canonical address." [8](#0-7) 

The codebase's own test suite demonstrates and even names the unsafe pattern this security model depends on avoiding: deploying the `ERC1967Proxy` with **empty** init data and calling `initialize` in a later, separate transaction: [9](#0-8) [10](#0-9) 

The only production script that has been verified deploys atomically (proxy + init data in one CREATE2 constructor call): [11](#0-10) 

However, this atomicity is a **process/operational convention**, not an on-chain invariant enforced by the contract. Nothing in `IntentGatewayV2.sol` prevents a proxy from being deployed with empty init data (exactly as the test helper `_deployGatewayProxy()` does), leaving `initialize()` callable by any address in the window between proxy deployment and the intended initialization transaction — the precise "initializer front-running" primitive from the external report. Whoever wins that race permanently sets `host`, `dispatcher`, `priceOracle`, fee parameters, and peer-chain-to-gateway bindings for the life of the proxy (the `initializer` flag cannot be reset).

### Impact Explanation
If `initialize()` is front-run, the attacker can set:
- `dispatcher` to a malicious contract that the gateway later calls in `placeOrder`'s predispatch flow and trusts for `IntentGatewayV2.host()`-derived dispatch,
- `priceOracle` to an attacker-controlled oracle,
- `protocolFeeBps`/`surplusShareBps` to attacker-favorable values,
- peer-chain gateway bindings (`_addDeployment`) to attacker addresses, which are used by `instance()`/`authenticate()` to decide which cross-chain sources are trusted for `RedeemEscrow`/`RefundEscrow` withdrawals.

Since `instance()` and the peer bindings gate which cross-chain source module is authorized to trigger escrow release, a malicious initial peer set could let an attacker's own "peer gateway" instance authorize withdrawal of escrowed user funds — i.e., unauthorized execution and fund loss, matching the bounty's "stealing or loss of funds" / "unauthorized transaction or execution" categories. In the best case it simply forces a costly re-deployment of the proxy.

### Likelihood Explanation
Exploitability is conditional: it requires a deployment flow where proxy creation and the `initialize` call are two separate transactions (as the repository's own test helper and comments show is a real, exercised code path, distinct from the atomic `DeployIntentGateway.s.sol` script). Any environment, integrator, or future deployment tooling (e.g., a manual proxy deploy, a script bug, or a third-party integrator following the `_deployGatewayProxy` pattern used pervasively in the test suite) that does not preserve strict atomicity is directly exploitable by an unprivileged mempool observer — no relayer, prover, or governance compromise needed.

### Recommendation
Add an explicit authorization check to `initialize()` (e.g., restrict to `_owner`/`msg.sender == _owner`, or use a `msg.sender`-bound predetermined admin) rather than relying solely on deployment atomicity, so the contract itself — not the deployment script — enforces the invariant, consistent with every other one-shot initializer in this codebase (`EvmHost.initialize`, `HostManager.setIsmpHost`, `VWAPOracle.init`, Tron `IntentGatewayV2.setParams`).

### Proof of Concept
1. Deploy `IntentGatewayV2` implementation, then deploy `ERC1967Proxy(implementation, "")` with empty init data (this is a supported, tested code path — see `_deployGatewayProxy()`). [12](#0-11) 
2. Before the legitimate deployer's follow-up transaction lands, an attacker calls `intentGateway.initialize(maliciousParams, maliciousPeerChains)` directly — no `msg.sender` check blocks this.
3. `initializer` modifier marks the contract initialized; the legitimate `initialize` call now reverts, and the attacker's `host`, `dispatcher`, `priceOracle`, fee parameters, and peer bindings are permanent for that proxy.

    /// @dev Production deploy path: the proxy initializes atomically via its init data, so the
    /// `initialize` call arrives through the proxy constructor (not from `_owner`). Must succeed.
    function testAtomicInitialization() public {
        IntentGatewayV2 implementation = new IntentGatewayV2(address(this));
        Params memory intentParams = Params({
            host: address(host),
            dispatcher: address(dispatcher),
            solverSelection: false,
            surplusShareBps: 10000,
            protocolFeeBps: 0,
            priceOracle: address(0)
        });
        bytes[] memory peers = new bytes[](1);
        peers[0] = bytes("SOURCE_CHAIN");

        bytes memory initData = abi.encodeCall(IntentGatewayV2.initialize, (intentParams, peers));
        ERC1967Proxy proxy = new ERC1967Proxy(address(implementation), initData);
        IntentGatewayV2 gateway = IntentGatewayV2(payable(address(proxy)));

        assertEq(gateway.params().host, address(host), "params set via atomic init");
        assertEq(gateway.instance(bytes("SOURCE_CHAIN")), address(gateway), "peer bound to address(this)");
