## Analysis

Tracing `handle_get_requests` in [1](#0-0) , the code separates proof/consumption from persistence:

1. In the response-building loop (lines 133–155), each `GetResponse` is verified via `verify_state_proof`, and `BandwidthGate::try_consume` is called **per response**, immediately mutating `Allowance` storage in `pallet_bandwidth::try_consume` via `Allowance::<T>::mutate(...)` [2](#0-1) .
2. Only *after* the entire loop succeeds for every request does the second loop (lines 188–192) call `host.store_response_receipt` and `dispatch_get_response` (MMR insert + `Responded`/`ResponseCommitments` writes) [3](#0-2) .

So the exact scenario in the question — an earlier `GetResponse` being persisted into the MMR/receipts before a later bandwidth check aborts the extrinsic — does **not** occur, because MMR/receipt persistence is strictly deferred until all `try_consume` calls in the batch succeed. That half of the "broken invariant" claim is false.

However, the reverse half of the same invariant *is* broken: `pallet_state_coprocessor::handle_unsigned`, the dispatchable that calls `handle_get_requests`, is **not** annotated with `#[frame_support::transactional]` [4](#0-3) . Contrast this with `pallet_ismp::handle_unsigned`, whose author explicitly wraps the batch handler in `#[frame_support::transactional]` to guarantee atomic revert-on-error [5](#0-4) . The state-coprocessor pallet's own `pre_dispatch` is deliberately left empty specifically "so we don't modify storage" [6](#0-5) , which is direct evidence the authors know `handle_get_requests` performs real, non-reverted storage side effects.

Without `#[transactional]`, FRAME does not automatically roll back storage mutations that happened before a dispatchable returns `Err`. Therefore, in a batch of N `GetRequest`s where the app's allowance covers only N-1 responses' worth of bytes:
- `try_consume` succeeds and **permanently debits** `Allowance` for responses 1..N-1.
- `try_consume` fails on response N, the whole call returns `Err`, `handle_unsigned` fails, and **no** `GetResponse` is ever stored in the MMR or `response_receipt` (since the final loop never runs).

The attacker (any unprivileged submitter of this unsigned extrinsic) gets nothing persisted, but the app's prepaid bandwidth allowance is burned for responses that were never delivered. This can be repeated to drain an app's entire prepaid subscription balance for zero delivered `GetResponse`s — a "bandwidth balance must move exactly once and only to the rightful beneficiary" violation per the review's own pivot list.

### Title
Non-transactional `handle_get_requests` burns prepaid bandwidth allowance on partial batch failure without delivering any `GetResponse` - (File: modules/pallets/state-coprocessor/src/impls.rs)

### Summary
`pallet_state_coprocessor::handle_unsigned` is not wrapped in `#[frame_support::transactional]`, unlike the analogous `pallet_ismp::handle_unsigned`. `BandwidthGate::try_consume` mutates the app's `Allowance` storage directly and immediately for each `GetRequest` in a batch, while MMR insertion / response-receipt storage is deferred to a separate loop that only runs if every request in the batch is consumed successfully. Any unprivileged submitter can craft a batch that succeeds on the first N-1 bandwidth-consuming iterations and deliberately fails on the Nth (by targeting an app whose remaining allowance covers exactly N-1 responses), causing the extrinsic to abort with `Error::Custom("bandwidth gate: ...")` after the bandwidth for N-1 responses has already been irreversibly deducted, while zero `GetResponse`s are ever persisted.

### Finding Description
`try_consume` is called inside the per-request loop immediately after `verify_state_proof`, debiting `pallet_bandwidth::Allowance` directly via `StorageDoubleMap::mutate` [7](#0-6) . This debit is a normal storage write, not deferred to a commit phase. The response is only pushed to an in-memory `Vec`, and the actual on-chain persistence (`store_response_receipt`, MMR push, `Responded` insert) happens in a second loop after the full first loop completes [3](#0-2) . If `try_consume` fails on any request within the batch, `handle_get_requests` returns `Err` via `?`, and `handle_unsigned` converts it into `Error::<T>::HandlingError`, failing the extrinsic. Because there is no `#[frame_support::transactional]` wrapper on this dispatchable, FRAME does not automatically discard the storage writes already committed earlier in the same call (the `Allowance` mutations for the requests preceding the failing one persist).

### Impact Explanation
An app's prepaid bandwidth subscription (purchased via `pallet_bandwidth`, credited by `BandwidthManager.sol` purchases) can be drained to zero by repeated crafted failing batches without the app ever receiving the corresponding `GetResponse` data it paid for. This is loss of a bridged/paid asset (bandwidth balance) to no beneficiary — pure burn — matching the bounty's "stealing or loss of funds" / bandwidth-balance-integrity criteria.

### Likelihood Explanation
High. The path is reachable via the public unsigned extrinsic `handle_unsigned` (`ensure_none(origin)`) with no authorization required. The attacker only needs knowledge of an app's remaining allowance (readable via `pallet_bandwidth::remaining`) and control over batch composition/ordering, both of which are attacker-controlled inputs to `GetRequestsWithProof`.

### Recommendation
Add `#[frame_support::transactional]` to `pallet_state_coprocessor::handle_unsigned` (mirroring `pallet_ismp::handle_unsigned`) so that any `Err` returned from `handle_get_requests` rolls back all storage mutations made during that call, including partial `BandwidthGate::try_consume` debits, restoring the 1:1 correspondence between bandwidth charged and responses delivered.

### Proof of Concept
1. Credit an app with an allowance covering exactly `N-1` `GetResponse` payload sizes.
2. Submit a `GetRequestsWithProof` batch of `N` valid `GetRequest`s (all pass source/response proof checks) ordered so the first `N-1` responses fit the allowance and the Nth does not.
3. Observe: `try_consume` succeeds for the first `N-1` requests (debiting `Allowance` in storage), fails on the Nth, and `handle_get_requests` returns `Err`, aborting the extrinsic — no `GetResponse` is ever inserted into the MMR or `response_receipt`.
4. Inspect on-chain state post-failure: `pallet_bandwidth::Allowance` for `(source, app)` shows the bytes for `N-1` responses already deducted, while `pallet_ismp::Responded`/`ResponseCommitments`/MMR show nothing new — demonstrating the debit persisted despite the batch failing atomically everywhere else.

			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
