## Finding: CW721 pointer NFTs become permanently untransferable to any unassociated EVM address (auction/marketplace escrow, freshly-deployed contracts, or unfunded wallets)

### Title
CW721ERC721Pointer.transferFrom reverts unconditionally for unassociated recipients, permanently freezing pointer-wrapped NFTs sold through marketplaces/auctions - (File: contracts/src/CW721ERC721Pointer.sol)

### Summary
`CW721ERC721Pointer.transferFrom` (and `approve`, `setApprovalForAll`) always resolves the counterparty EVM address to a Sei bech32 address via `AddrPrecompile.getSeiAddr()` before executing the underlying CW721 `transfer_nft` message. `getSeiAddr` unconditionally reverts with `"EVM address %s is not associated"` if the target EVM address has never been associated with a Sei address. Because a CW721 pointer NFT cannot exist as a "pure" ERC721 (its ownership is proxied through a CosmWasm contract requiring bech32-addressed CW messages), any recipient that has not yet been associated — e.g. a freshly deployed marketplace/auction/escrow contract, or a bidder wallet that has never transacted on Sei — can never receive the NFT. This mirrors the reported Debita bug class: an unconditional address-format/eligibility check baked into `transferFrom` blocks legitimate transfer paths (auction/marketplace settlement), permanently freezing the asset and any value locked behind it.

### Finding Description
`transferFrom` in `CW721ERC721Pointer.sol` builds the CW721 `transfer_nft` payload using the Sei bech32 address of `to`: [1](#0-0) 

`AddrPrecompile.getSeiAddr` delegates to the `addr` precompile's `getSeiAddr` method, which has no fallback for unassociated addresses — it simply errors out: [2](#0-1) 

Unlike native/ERC20 pointer paths (`ERC20toNativePointer`, `sendNative`), which either bootstrap association implicitly or allow sending to unassociated recipients and merely defer full linkage, the CW721 pointer path has no such fallback: it hard-fails at the point of `getSeiAddr(to)`. This exact limitation is called out in the repo's own integration test documentation as a known restriction: [3](#0-2) 

The practical consequence is structurally identical to the reported Debita `TaxTokenReceipt` bug: a legitimate transfer path required for auction/marketplace settlement (paying out an NFT to the winning bidder, or moving an NFT into/out of an escrow/auction contract) can be permanently blocked if the recipient side of that flow has not been "associated." For CosmWasm-native NFT collections wrapped by the CW721-to-ERC721 pointer (used so EVM-side marketplaces/auction contracts can interact with CW721 assets), this means:
- A marketplace/auction contract that is deployed but has not yet sent any EVM transaction from its own address context (contracts don't self-associate) cannot receive the NFT into escrow.
- A winning bidder whose EVM address has never transacted on Sei (no prior association) can never receive the NFT payout from an auction, permanently freezing the NFT and any value/collateral tied to it, exactly like the original report's "lenders experience a big loss of funds" scenario.

### Impact Explanation
This causes permanent freezing of a CW721-wrapped NFT (and any funds/collateral logic built around it in EVM-side DeFi/marketplace/auction protocols using the pointer) whenever the transfer counterparty is unassociated. There is no recovery path once the transfer reverts other than requiring the recipient to separately associate first — which is often infeasible for contract addresses (e.g., an auction contract can't "sign" to associate itself) or externally impossible to force for a third-party bidder. This matches the accepted impact class of permanent freezing of funds/assets reachable via a normal transaction.

### Likelihood Explanation
High likelihood in practice: any EVM-side marketplace, auction, or escrow contract interacting with CW721 pointer NFTs, or any bidder/buyer wallet that hasn't previously transacted on Sei, will trigger this. This is a deterministic, reproducible revert condition rather than an edge case, and is already acknowledged as a current limitation in the codebase's own test documentation.

### Recommendation
For `CW721ERC721Pointer.transferFrom`/`approve`/`setApprovalForAll`, add a fallback when the recipient/spender address is unassociated — either by auto-associating a deterministic Sei address for the EVM address (similar to how EVM->native token transfers handle unlinked recipients) before issuing the CW `transfer_nft`/`approve` message, or by maintaining an internal address mapping so pointer-tracked NFTs can be held on behalf of unassociated EVM addresses without requiring a live bech32 counterpart at transfer time.

### Proof of Concept
1. Deploy a `CW721ERC721Pointer` for an existing CW721 collection.
2. Deploy (or use) an EVM auction/marketplace contract address that has never been associated with a Sei address (fresh contract deployment, no prior `associate` call).
3. Owner calls `pointer.transferFrom(owner, auctionContract, tokenId)` to place the NFT into the auction/escrow.
4. Call reverts inside `_execute`/`getSeiAddr` with `"EVM address %s is not associated"` [4](#0-3) , permanently blocking the NFT from entering the auction/marketplace flow. [1](#0-0) [2](#0-1) [3](#0-2)

    function transferFrom(address from, address to, uint256 tokenId) public override {
        if (to == address(0)) {
            revert ERC721InvalidReceiver(address(0));
        }
        require(from == ownerOf(tokenId), "`from` must be the owner");
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
        string memory req = _curlyBrace(_formatPayload("transfer_nft", _curlyBrace(_join(recipient, tId, ","))));
        _execute(bytes(req));
    }

func (p PrecompileExecutor) getSeiAddr(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}

	seiAddr, found := p.evmKeeper.GetSeiAddress(ctx, args[0].(common.Address))
	if !found {
		metrics.IncrementAssociationError("getSeiAddr", types.NewAssociationMissingErr(args[0].(common.Address).Hex()))
		return nil, 0, fmt.Errorf("EVM address %s is not associated", args[0].(common.Address).Hex())
	}
	ret, err = method.Outputs.Pack(seiAddr.String())
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
