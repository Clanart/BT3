Based on the investigation, I found a strong analog. The bug-class in the ERC20 report is "an interface/format is assumed to be well-behaved and safe, but attacker-controlled input can violate that assumption, and the code does not validate before acting on it, causing unsafe/irrecoverable behavior." In GitHub Desktop's submodule handling, this pattern reappears with `protocol.file.allow=always`, which re-opens a `file://` submodule vector that upstream Git deliberately closed (as CVE-2022-39253) as a hardening default.

### Title
Re-enabling `file://` submodule protocol on attacker-controlled `.gitmodules` URLs allows local file/directory exfiltration into the working tree - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` in [1](#0-0)  conditionally prepends `-c protocol.file.allow=always` to `git submodule update --init --recursive` based on a caller-supplied `allowFileProtocol` boolean. Since Git 2.38 (backported to 2.35.5), Git disables the `file://` transport for submodule operations by default specifically to prevent a cloned/fetched repository from using a crafted `.gitmodules` entry to make the client silently "clone" an arbitrary local path (CVE-2022-39253). Desktop's code deliberately re-enables this protocol for submodule updates that originate from `checkoutBranch`/`checkoutCommit` flows [2](#0-1) [3](#0-2) .

### Finding Description
The submodule URL is untrusted, attacker-controlled data: it comes from `.gitmodules`/`git config` inside a cloned or fetched repository, exactly analogous to the ERC20 report's "address passed as input parameter, assumed to conform to a trusted interface." Nothing in `updateSubmodulesAfterOperation` inspects the submodule URL scheme before deciding whether `protocol.file.allow=always` should apply; it simply trusts the caller's boolean flag to gate a git-level protocol restriction meant to protect against exactly this attacker-controlled value [4](#0-3) . When a checkout/pull operation is invoked with `allowFileProtocol=true`, any `submodule.<path>.url = file:///some/local/path` entry defined by the (attacker-controlled) repository content will be honored: Git will treat that local path as a clone source and copy its full working tree into the submodule directory inside the user's repository — the same "corruption of what the user commits" impact class as the ERC20 report's "stuck funds," here manifesting as unauthorized data flowing into the user's working tree and index. Test fixtures confirm the exact underlying git behavior this flag controls: `protocol.file.allow=always` is required specifically to let `git submodule add ../repo2`-style local paths work [5](#0-4) , i.e., the flag is precisely the guard Git's own CVE fix put in place, and this code path re-opens it based only on a boolean the caller passes, not on any validation of the submodule URL itself.

### Impact Explanation
If `allowFileProtocol` is `true` for a checkout/pull driven by data from an untrusted/attacker-supplied remote (e.g. opening a maliciously crafted repository, or pulling from a remote that changes `.gitmodules` to point a submodule at `file:///Users/victim/.ssh` or another sensitive local directory), Git will copy the contents of that local path into the submodule folder under the user's repository. This can (a) read/exfiltrate local files outside the repo boundary into a location that later gets committed and pushed to a remote the attacker controls, and (b) silently corrupt the working tree the user believes only contains legitimate submodule content — matching the "unpredictable/uncontrolled write outside the intended scope" and "silent corruption of what the user commits" impact classes in the Valid Impact criteria.

### Likelihood Explanation
The exact set of caller boolean values passed into `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` across `app-store.ts` and the dispatcher could not be fully enumerated within the available tool budget — I was unable to confirm from the index whether `allowFileProtocol=true` is reachable from an ordinary "checkout a branch that adds/changes a submodule" flow on a cloned/fetched repository versus being restricted to a more controlled internal path (e.g., only for locally created submodules during tests). This is a material open question: the finding is strong evidence that Desktop's own code deliberately overrides a security fix upstream Git shipped for this exact attacker model, but confirming full exploitability requires tracing every caller of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` with a Desktop session that can read the complete `app-store.ts` and `dispatcher.ts` call graphs.

### Recommendation
Do not gate `protocol.file.allow=always` on a caller-supplied boolean without first validating the actual submodule URLs against an allowlist of protocols (e.g., only allow `file://` when the target path is verified to reside within a directory the user has explicitly consented to, such as during test fixture setup or a locally-initiated `submodule add`). For submodule updates triggered by checking out or pulling from remote-authored content, `protocol.file.allow` should remain at Git's hardened default (deny), matching the intent of the upstream CVE-2022-39253 fix, and any legitimate need for local-path submodules should be surfaced to the user for explicit confirmation rather than silently permitted.

### Proof of Concept
1. Attacker publishes/serves a repository whose `.gitmodules` (or `.git/config` after fetch/merge, depending on the flow that invokes submodule update with `allowFileProtocol=true`) contains:
   ```
   [submodule "evil"]
       path = evil
       url = file:///Users/victim/.ssh
   ```
2. Victim opens/clones this repository in GitHub Desktop and performs an operation that calls `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true`, reaching `updateSubmodulesAfterOperation` [6](#0-5) .
3. Desktop runs `git -c protocol.file.allow=always submodule update --init --recursive`, which clones `/Users/victim/.ssh` into `evil/` inside the repository working tree.
4. The victim's local `.ssh` contents now exist inside the repository; if the victim stages/commits and pushes (or the app auto-syncs), the sensitive files are exfiltrated to the attacker-controlled remote — reproducing the "stuck/leaked value with no interface validation" root cause from the ERC20 report in a Desktop-specific, code-execution-adjacent, credential-exfiltration form.
