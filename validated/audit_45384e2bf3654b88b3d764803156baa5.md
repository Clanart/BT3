### Title
ReceivedOutput deserialization accepts an attacker-chosen offset, letting arbitrary outputs/values be attributed to a multisig key - ([File: networks/bitcoin/src/wallet/mod.rs + processor/src/networks/bitcoin.rs])

### Summary
The external report's bug class is "the validator checks a derived/guessed property instead of the client-provided property, so a mismatched attacker value passes validation." Serai has the same shape across the `ReceivedOutput`/`Output` boundary: the `Scanner` enforces an invariant (the output's `script_pubkey` equals `p2tr(key + offset*G)` for a registered `offset`), but `ReceivedOutput::read` / `Output::read` deserialize an untrusted `offset`, `TxOut`, and `OutPoint` with no check that this invariant holds. `Output::key()` then *derives* the owning key as `even_lift(script_key) - offset*G` instead of verifying the supplied offset against the supplied script. An attacker can therefore craft a serialized output that reports an arbitrary balance owned by any victim group key — the mirror of `shell.php` passing `ext_in[gif]` because only the derived extension was checked.

### Finding Description
`Scanner::scan_transaction` only ever produces a `ReceivedOutput` after matching `output.script_pubkey` against the `scripts` map built by `Scanner::new` / `register_offset`, guaranteeing `script == p2tr_script_buf(scanner.key + GENERATOR * offset)`:

- `networks/bitcoin/src/wallet/mod.rs:199-214` (`scan_transaction`)
- `networks/bitcoin/src/wallet/mod.rs:180-196` (`register_offset`)

However, `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) accepts `offset`, `output` (a full `TxOut`), and `outpoint` as raw attacker-controlled bytes via `Secp256k1::read_F` and `consensus_decode`, with no consistency check.

`processor/src/networks/bitcoin.rs:112-122` then computes:

```rust
fn key(&self) -> ProjectivePoint {
  let script = &self.output.output().script_pubkey;
  ...
  Secp256k1::read_G(&mut key.public_key(Parity::Even).serialize().as_slice()).unwrap() -
    (ProjectivePoint::GENERATOR * self.output.offset())
}
```

The key is *derived* from the claimed script minus the claimed offset — exactly the "trust the derived value" error in the CodeIgniter bug. No code re-verifies `script_pubkey == p2tr_script_buf(key() + offset*G)` (which would be trivially true by construction anyway) nor that the outpoint exists on-chain. `balance()` (`processor/src/networks/bitcoin.rs:128-130`) returns `self.output.value()`, also fully attacker-controlled in the deserialized object.

Attack construction (needs no discrete log): pick any scalar `o`, compute `X = K + o*G` for victim group key `K`, even-lift `X` to get an x-only key, and serialize:

```
ReceivedOutput {
  offset:   o,
  output:   TxOut { value: claimed_sats, script_pubkey: P2TR(x_only(X)) },
  outpoint: arbitrary/duplicated,
}
```

`Output::key()` then returns `K` and `balance()` returns `claimed_sats`, even though no such UTXO exists (or the real outpoint pays someone else entirely). This is reachable wherever `ReceivedOutput::read` / `Output::read` (`processor/src/networks/bitcoin.rs:145-166`) consume bytes not produced by the local `Scanner` — the format is explicitly written/read via `Output::write`/`Output::read`, and `ReceivedOutput` exposes a public `serialize()`/`read()` pair usable across trust boundaries.

### Impact Explanation
Outputs with a forged key attribution and forged `value` flow into the processor's balance/output pipeline (`ScannerDb`, multisig planning). Two concrete consequences:

- **Funds reported received that are not spendable / never existed**: an `Output` attributed to multisig key `K` with an arbitrary `value` inflates the tracked balance for `K` without any on-chain UTXO, matching the accepted "funds reported received that are not spendable" impact.
- Downstream `SignableTransaction::new` consumes `Vec<ReceivedOutput>` and the signers' `multisig()` check (`networks/bitcoin/src/wallet/send.rs:273-285`) only compares the *claimed* `prevouts[i].script_pubkey` to the derived offset key — it never checks the claimed `outpoint` against the chain. A forged input therefore produces signatures over a transaction spending a nonexistent/other-party outpoint (worthless tx, wasted signing round) or lets an attacker inject inputs into a planned spend.

### Likelihood Explanation
Exploitation requires the attacker to get their serialized `ReceivedOutput`/`Output` bytes accepted by a node — i.e., a path where these structures cross a trust boundary (output gossip, DB recovery, or any RPC-fed reconstruction). Within the strictly local scanner→DB path the producer is trusted, so likelihood is conditional on such a boundary existing in deployment; the in-scope rules explicitly designate `ReceivedOutput::read` as an untrusted-bytes sink, so the reachable surface is presumed present. Severity is Medium-to-High depending on whether credited balances gate fund issuance.

### Recommendation
- In `Output::key()`/`Output::read`, re-derive the expected script and reject the object if `self.output.output().script_pubkey` is not in the scanner's registered `scripts` map for that key — i.e., validate the *provided* fields against the registered invariant instead of deriving the key from them.
- Bound `ReceivedOutput::read` to a `Scanner`-like registry, or add a `ReceivedOutput::verify_against(scanner_scripts)` used on every deserialization from an untrusted source.
- Sanity-check `outpoint` existence/unspentness before any balance is credited or input is fed to `SignableTransaction::new`.

### Proof of Concept
```rust
// Attacker knows victim group key K (public).
let o = Scalar::random(&mut OsRng);
let x_point = K + (ProjectivePoint::GENERATOR * o);
// even-lift to an x-only key and build the P2TR script_pubkey
let script = p2tr_script_buf_even_lifted(x_point); // P2TR to x_only(x_point)

let forged = ReceivedOutput_forged(
    offset:   o,
    output:   TxOut { value: Amount::from_sat(1_000_000_000), script_pubkey: script },
    outpoint: OutPoint::new(victim_spend_txid_or_random, 0),
);
let bytes = forged.serialize();

// On the victim node / any untrusted deserialization path:
let output = Output::read(&mut bytes.as_slice()).unwrap(); // processor Output::read
assert_eq!(output.key(), K);                                // attributed to victim
assert_eq!(output.balance().amount.0, 1_000_000_000);       // claimed balance
// No UTXO exists; nothing enforces script == p2tr(K + o*G) at a registered offset.
```

*Caveat:* the exploit path depends on `Output::read`/`ReceivedOutput::read` consuming attacker-supplied bytes in the deployed processor; I verified the read/format and the missing consistency check, but did not trace every caller that feeds these readers from an untrusted source. If all producers are strictly the local trusted `Scanner`, the finding reduces to a missing-invariant hardening issue rather than a live exploit.
