## Finding: `EVMEntryViaWasmdPrecompile` context flag is not scoped/popped after use, permitting unrestricted CW↔EVM re-entry chains beyond the intended single hop

### Title
Context Flag `EVMEntryViaWasmdPrecompile` Is Not Popped/Rescoped After First Nested Use, Allowing Repeated CW→EVM Re-entry in a Single Tx - (File: x/evm/keeper/msg_server.go, x/evm/keeper/evm.go)

### Summary
The WildFly CVE describes a security-context/principal that is not restored ("popped back") after crossing into a nested invocation with a different security domain, letting the wrong privilege persist for subsequent calls. Sei-chain has an analogous "permission flag" pattern: `sdk.Context.EVMEntryViaWasmdPrecompile()`, which is meant to permit exactly one legitimate EVM→CW→EVM re-entry hop, but the flag is set once on the outer transaction context and is only reset to `false` on an internally-derived, throwaway `executionCtx` inside `CallEVM` — never on the outer context that continues to flow through the rest of the transaction's Cosmos SDK message/submessage dispatch tree.

### Finding Description
- When an EVM transaction's top-level destination (`tx.To()`) is the wasmd precompile address, `PrepareCtxForEVMTransaction` marks the context permissive for CW→EVM re-entry: [1](#0-0) 

- This `ctx` (carrying the flag `true`) is the same context subsequently threaded through `applyEVMMessage`, the wasmd precompile's `execute()`, and — critically — CosmWasm's own submessage dispatch machinery whenever the invoked CW contract sends further Wasm messages (e.g. `MsgExecuteContract` calling another contract, which internally may issue an `EncodeCallEVM`/`MsgInternalEVMCall` binding).

- `CallEVM` is the single choke point meant to prevent unbounded EVM↔CW recursion: [2](#0-1) 

  It checks `ctx.IsEVM() && !ctx.EVMEntryViaWasmdPrecompile()` and blocks the call with `"sei does not support EVM->CW->EVM call pattern"` only when the flag is `false`. When it is `true` (which it is for the *entire* remainder of the transaction, since it was set once at the top), the check is bypassed and a brand-new, independent EVM state transition is started via `k.applyEVMMessage(ctx, evmMsg, stateDB, gp, false)` with its own infinite gas meter, its own nonce lookup, its own receipt write, and its own append to deferred surplus/bloom (`k.AppendToEvmTxDeferredInfo`).

- Crucially, the flag is only reset to `false` on the *inner*, single-use `executionCtx` passed into that specific nested EVM execution (`ctx.WithGasMeter(...).WithEVMEntryViaWasmdPrecompile(false)`), not on the outer `ctx` that keeps propagating through the rest of the transaction's CosmWasm submessage graph. Because Cosmos SDK `sdk.Context` values are immutable-by-convention but copied field-by-field, any sibling or downstream CW submessage dispatched later in the same transaction still observes `EVMEntryViaWasmdPrecompile() == true`, so it can independently call back into `CallEVM` again — a second, third, etc. "hop" — even though the guard's error message and the module documentation state only a single, bounded EVM→CW→EVM pattern is supported: [3](#0-2) 

This is the direct analog of the WildFly issue: a context-scoped privilege ("this call chain is allowed to re-enter the EVM") is established once and is never popped back to its original (unprivileged) state once the sanctioned nested invocation completes; it instead keeps leaking forward to unrelated, later invocations within the same top-level call.

### Impact Explanation
Each unauthorized extra `CallEVM` invocation performs its own independent state transition using an infinite gas meter (bounded only after-the-fact by `k.consumeEvmGas`), its own nonce read, and its own transient receipt/bloom/deferred-surplus bookkeeping that is *appended* to the top-level transaction's aggregated `EVMTxDeferredInfo`. A chain of CosmWasm contracts orchestrated by an attacker who directs the top-level EVM tx at the wasmd precompile could trigger multiple such independent re-entries within one transaction (each individually legitimate on its own, but the module intends this pattern to happen at most once per transaction). This can affect fee/surplus accounting correctness (surplus/gas aggregation feeding the deferred EndBlock work) and receipt/log/bloom construction described in the module's own lifecycle documentation, both of which are explicitly in-scope impact categories (fee/refund abuse, receipt/log manipulation).

### Likelihood Explanation
Reachable entirely from a single, unprivileged, externally-submitted EVM transaction targeting the public wasmd precompile address with a CosmWasm payload that fans out into further contract executions — no validator, governance, or operator privilege required. The precondition (top-level `tx.To() == wasmd precompile`) is trivially satisfiable by any EVM transaction sender.

### Recommendation
Scope `EVMEntryViaWasmdPrecompile` so it functions as a true one-shot capability: consume/clear it on the *outer* context immediately after it authorizes a single `CallEVM` re-entry (not merely on the throwaway inner `executionCtx`), or replace the boolean with a strictly decrementing re-entry counter/depth check enforced globally for the transaction, so that no additional CW→EVM hops can be authorized once the sanctioned single hop has been used.

### Proof of Concept
Conceptual PoC path (not independently executed against a running node due to tool limitations in this analysis):
1. Attacker submits an EVM transaction with `to` = wasmd precompile address (`0x0000000000000000000000000000000000001002`) and `data` encoding `execute(contractA, msg, coins)`, where `contractA` is attacker-controlled.
2. `PrepareCtxForEVMTransaction` sets `ctx.WithEVMEntryViaWasmdPrecompile(true)` for the whole transaction (`x/evm/keeper/msg_server.go:48-52`).
3. `contractA`'s `execute` handler dispatches a normal CW `MsgExecuteContract` submessage to `contractB` (a second attacker-controlled contract) — this is ordinary CW→CW dispatch, unrelated to the wasmd precompile, and inherits the same `ctx`.
4. `contractB` issues a `CallEVM` wasm binding (`x/evm/client/wasm/encoder.go:14-30`), routed to `HandleInternalEVMCall` → `CallEVM` (`x/evm/keeper/evm.go:30-44,79-97`).
5. Because `ctx.EVMEntryViaWasmdPrecompile()` is still `true` (never popped on the outer ctx), the guard at `evm.go:80` does not block this second independent CW→EVM re-entry, letting `contractB` call arbitrary EVM contracts, with the transition's surplus/receipt effects merged into the top-level transaction's deferred info.

**Caveat / what remains unverified:** I was unable to confirm within the available tool budget whether CosmWasm's own submessage dispatch depth limits (`sei-wasmd/x/wasm/keeper/keeper.go`, `options.go` — matches for "CallDepth") impose an independent cap that would bound the practical exploitability of chaining multiple hops, nor did I trace the exact quantitative effect on surplus/fee totals to prove concrete fund-loss magnitude. A background engineering session with full repo/test access would be needed to build and run an integration test reproducing the double CW→EVM re-entry and to measure the resulting fee/surplus discrepancy precisely.
