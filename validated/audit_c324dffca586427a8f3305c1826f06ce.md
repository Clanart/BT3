### Title
Payout tx OP_RETURN (operator attribution) is unauthenticated because `SinglePlusAnyoneCanPay` sighash only commits to the withdrawal output, letting an attacker rewrite the payer's `XOnlyPublicKey` and steal/break reimbursement attribution - ([File: core/src/builder/transaction/operator_reimburse.rs], [File: core/src/verifier.rs])

### Summary
The user's withdrawal signature is created with `TapSighashType::SinglePlusAnyoneCanPay`, which per BIP341 only commits to the single spent input and the output at the same index (index 0, the user's payout output). The OP_RETURN output (index 2) that embeds `operator_xonly_pk` and the anchor output (index 1) are completely unsigned, so any party who observes the broadcast payout transaction (mempool or the `RawSignedTx` RPC response) can rebuild a conflicting, still-valid transaction with the *same* input/witness and user output but a different OP_RETURN payload, and win the race to get it mined.

### Finding Description
The claimed binding is: `payout_payer_operator_xonly_pk` (recorded in DB from the mined payout tx's OP_RETURN, `core/src/verifier.rs:2319-2321`) `==` `self.signer.xonly_public_key` of the operator who actually funded/broadcast the withdrawal UTXO spend.

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds a single-input, three-output transaction: output 0 = user payout, output 1 = anchor, output 2 = `op_return_txout(operator_xonly_pk.serialize())`. The witness is `set_p2tr_key_spend_witness(&user_sig, 0)`, i.e., only the *user's* signature is present; nothing signs the operator's own identity.
- The user's signature is required (and enforced, `core/src/operator.rs:637`) to use `SinglePlusAnyoneCanPay`. Under BIP341 rules, `SIGHASH_SINGLE` covers only the output whose index equals the signed input's index (output 0); `SIGHASH_ANYONECANPAY` only fixes the signed input. Outputs 1 (anchor) and 2 (OP_RETURN with `operator_xonly_pk`) are therefore not committed to by the signature at all.
- `Operator::withdraw` (`core/src/operator.rs:560-691`) builds this exact transaction, calls `fund_raw_transaction`/`sign_raw_transaction_with_wallet`/`send_raw_transaction`, broadcasting it to the public Bitcoin P2P network — visible to any node in the mempool before confirmation (the RPCs `internal_withdraw`/`withdraw` in `core/src/rpc/operator.rs:168-258` also directly return `RawSignedTx` to the caller).
- Because the input's witness (schnorr signature) remains valid for *any* output-2 content, an unprivileged attacker who sees the broadcast (or receives the `RawSignedTx`) can construct an alternate transaction: same outpoint, same witness/signature, same output 0, but a tampered OP_RETURN (garbage bytes or another operator's real `XOnlyPublicKey`), and get it mined instead (e.g., by attaching a higher-fee CPFP child to the ephemeral anchor output, or by simple first-seen propagation/miner selection since this is a double-spend of the same UTXO).
- Once the attacker's variant confirms, `update_finalized_payouts` (`core/src/verifier.rs:2312-2342`) parses the tampered OP_RETURN via `parse_op_return_data`/`XOnlyPublicKey::from_slice` (`core/src/verifier.rs:2320-2321`) and stores the wrong (or `None`) `payer_xonly_pk` for that withdrawal in the DB.
- The true operator, when later attempting to be reimbursed, calls `validate_payer_is_operator` (`core/src/operator.rs:1687-1729`), which compares the DB-recorded `payer_xonly_pk` against `self.signer.xonly_public_key` and fails permanently (`payer_xonly_pk != self.signer.xonly_public_key`), or fails outright if `operator_xonly_pk` is `None` (treated as "payer info not found").
- Critically, this corruption is not just a DB bookkeeping bug: the bridge circuit itself (`circuits-lib/src/bridge_circuit/mod.rs:206-229`) re-derives `operator_xonlypk` directly from the *on-chain* payout tx's OP_RETURN via SPV proof and folds it into `deposit_constant`. Since the tampered OP_RETURN is what is actually mined, the true operator's presigned kickoff/assert transactions (built assuming their own pubkey would appear on-chain) can never produce a matching `deposit_constant`, permanently blocking that operator's reimbursement path for this withdrawal.
- No existing guard prevents this: `is_deposit_valid`, `is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`), and `validate_payer_is_operator` all *consume* the OP_RETURN as ground truth; none of them re-derive or authenticate it against the actual funding operator's key, and the presigned transaction graph does not sign the OP_RETURN output at all.

### Impact Explanation
This directly matches the Critical category "an honest operator permanently unable to be reimbursed": the operator who genuinely fronted the withdrawal (spent real BTC to the user) can be locked out of ever proving payer attribution on-chain or in the bridge circuit, while the withdrawal UTXO is nonetheless spent. It is repeatable for every withdrawal an attacker chooses to race, is not limited to a single deposit/operator, and requires no special privilege — any Bitcoin-network observer with fee budget for a CPFP bump can execute it.

### Likelihood Explanation
The attacker needs only: (1) a Bitcoin full node or mempool visibility (or simply relay access) to see the operator's broadcast payout transaction or its `RawSignedTx` response, and (2) enough sats to CPFP-bump their own variant's ephemeral anchor above the operator's real fee-bump, or to win a first-seen propagation race. No verifier, aggregator, or key-share access is needed; the entire exploit stems from the choice of `SinglePlusAnyoneCanPay` leaving the OP_RETURN and anchor outputs unauthenticated. This is a structural signature-coverage flaw, not a probabilistic or DoS-only concern, and is reliably reproducible offline against the transaction-building code without needing a live mainnet broadcast race (the tampered transaction's validity can be proven by signature verification alone).

### Recommendation
Bind the operator identity into what the user signs, or otherwise authenticate the OP_RETURN/anchor outputs:
- Have the operator co-sign (or have the aggregator/verifiers attest) a commitment that includes the intended `operator_xonly_pk` and the full transaction template (all outputs) before broadcast, rejecting any mined transaction whose OP_RETURN doesn't match a pre-registered commitment for that specific `input_outpoint`/`withdrawal_index`.
- Alternatively, require the withdrawal signature to use `SIGHASH_ALL` (or `SIGHASH_ALL|ANYONECANPAY`) so that all outputs, including the OP_RETURN identity output, are committed to by the user's signature, preventing any output substitution post-signing while the input remains spendable only via the original witness.
- Add a DB/consensus rule that once a `payout_txid` candidate for a given `withdrawal_index`/outpoint is seen with a specific `operator_xonly_pk`, any competing spend of the same outpoint with a differing OP_RETURN is flagged and the true operator's kickoff is not penalized by `is_kickoff_malicious`/`validate_payer_is_operator` purely based on the winning chain content.

### Proof of Concept
```rust
// core/src/test/... (offline, no mainnet, no live Citrea)
#[tokio::test]
async fn op_return_malleability_breaks_attribution() {
    // 1. Build the real payout tx exactly as Operator::withdraw does:
    let real_txhandler = create_payout_txhandler(
        input_utxo.clone(), output_txout.clone(), real_operator_xonly_pk, user_sig.clone(), network,
    ).unwrap();
    let real_tx = real_txhandler.get_cached_tx().clone();

    // 2. Attacker crafts a tampered variant re-using the SAME witness/signature,
    //    SAME input, SAME output 0, but a DIFFERENT OP_RETURN (attacker_operator_xonly_pk).
    let tampered_txhandler = create_payout_txhandler(
        input_utxo.clone(), output_txout.clone(), attacker_operator_xonly_pk, user_sig.clone(), network,
    ).unwrap();
    let tampered_tx = tampered_txhandler.get_cached_tx().clone();

    // 3. Prove the user's signature verifies identically for BOTH variants
    //    (i.e. the OP_RETURN is unauthenticated under SinglePlusAnyoneCanPay).
    let sighash_real = real_txhandler.calculate_sighash_txin(0, user_sig.sighash_type).unwrap();
    let sighash_tampered = tampered_txhandler.calculate_sighash_txin(0, user_sig.sighash_type).unwrap();
    assert_eq!(sighash_real, sighash_tampered); // <-- proves OP_RETURN is not committed

    // 4. Simulate update_finalized_payouts on the tampered_tx being the one mined.
    let op_return_output = get_first_op_return_output(&CircuitTransaction::from(tampered_tx.clone())).unwrap();
    let parsed_pk = parse_op_return_data(&op_return_output.script_pubkey)
        .and_then(|b| XOnlyPublicKey::from_slice(b).ok());
    assert_eq!(parsed_pk, Some(attacker_operator_xonly_pk)); // wrong attribution recorded

    // 5. Assert the true operator can never pass validate_payer_is_operator for this deposit:
    // db now holds payer_xonly_pk = attacker_operator_xonly_pk (or None), not real_operator_xonly_pk
    let result = real_operator.validate_payer_is_operator(None, deposit_id).await;
    assert!(result.is_err()); // true payer permanently blocked from reimbursement
}
```
This demonstrates that the sighash used commits identically regardless of OP_RETURN content, and that once a tampered variant is the one confirmed on-chain, the true funding operator's `validate_payer_is_operator` check fails, breaking the ATTRIBUTION binding claimed in the question.
