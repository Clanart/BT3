## Analysis

The TRST‑M‑2 pattern is: a primary trust flag is flipped to "revoked" (`whitelistedRouters[_router] = false`), but *derived* state that was cached from when the flag was `true` (`routerTypes`, `swapInfos`) is never reset, and a downstream function (`getCalldata`) trusts the derived cache instead of re‑checking the primary flag — letting an actor keep using privileges that should have disappeared.

GitHub Desktop has the same shape of bug in how it tracks a repository's GitHub association and permission level.

### Title
Stale GitHub repository permission/association is never invalidated when the repo no longer matches its remote - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/stores/repositories-store.ts`)

### Summary
`Repository.gitHubRepository` (including its cached `permissions` string, used to decide whether the user has write access) is a derived cache built from a remote‑URL‑to‑account match. When that match can no longer be made, or when an API call that refreshes the repo doesn't return permission data, Desktop keeps the previously cached, now‑stale `gitHubRepository`/`permissions` value instead of clearing or re‑validating it — analogous to `routerTypes`/`swapInfos` surviving a `whitelistedRouters` revocation.

### Finding Description
`repositoryWithRefreshedGitHubRepository` re‑derives the GitHub association for a local repository from its current remote URL via `matchGitHubRepository`. If the remote no longer matches any signed‑in account/endpoint (e.g. the remote was changed, the account was removed, or the repo was transferred/deleted), the function explicitly bails out and returns the repository **unchanged**, keeping the old `gitHubRepository` (and its permissions) intact: [1](#0-0) 

The code even documents this as a known, un-fixed limitation, referencing desktop/desktop#1144: "We currently never clear GitHub repository associations... So we can bail early at this point."

Separately, even when a match *is* found and the repository is refreshed, the permission field itself can go stale in another way. `_upsertGitHubRepository` computes the persisted `permissions` value with a fallback to the previously stored value whenever the current API payload doesn't carry permission info: [2](#0-1) [3](#0-2) 

This mirrors the reported bug exactly: `whitelistedRouters[_router]` is the "current truth" (equivalent to "is this remote still associated with an account, and what does the API currently say about permissions"), while `routerTypes`/`swapInfos` (equivalent to `repository.gitHubRepository.permissions`) is the cached derived value. Nothing forces re-validation against the current truth before the cached value is consumed by downstream permission checks (`hasWritePermission` usages in `app.tsx`, `filter-changes-list.tsx`, `error-handlers.ts`), so a repository can keep reporting write access, protected‑branch bypass eligibility, or other GitHub-repo-scoped decisions long after the actual relationship has changed.

### Impact Explanation
Downstream consumers of `gitHubRepository`/`permissions` use it to gate security‑relevant UI/logic (e.g. warning before a force push, whether to suggest co‑authors from the org, whether branch‑protection related warnings apply). If the cached permission/association silently survives a revocation event (account removed, repo transferred to a different owner, access downgraded), the app can present a stale trust state to the user and skip protections that should now apply, e.g. failing to warn about protected-branch/force-push risk on a remote/branch combination that is no longer actually the trusted upstream. Because the underlying `gitHubRepository` record is also keyed by owner/name and reused across repos (parent/fork sharing, per the comment in `_upsertGitHubRepository` about "perpetual race conditions"), the blast radius of one stale/incorrect permission record can extend to other local clones sharing the same GitHub repo association.

### Likelihood Explanation
This requires no local/admin access and no social engineering beyond ordinary usage: any of the following naturally occurring events trigger it — removing/switching a signed‑in account, an org revoking a collaborator's access, a repository being made private/transferred, or the local remote URL being changed (which can happen due to a compromised/attacker‑controlled fetched repository rewriting `.git/config`, or a malicious API redirect). Because the code path is explicitly a documented "never clear" TODO rather than an edge case, the condition is easily reached during normal refresh cycles (`refreshSelectedRepositoryAfterAccountChange`), making likelihood moderate-to-high for silent staleness, though the security-sensitive consequence depends on which permission-gated UI path is reached next.

### Recommendation
When `matchGitHubRepository` fails to find a match for a repository that previously had a `gitHubRepository` association, clear the association (or at minimum, clear/invalidate the cached `permissions`) rather than returning the repository unchanged. Additionally, `_upsertGitHubRepository` should not silently reuse `existingRepo?.permissions` when refreshing from an authoritative endpoint that is expected to know the current permission — the fallback should be scoped strictly to endpoints that are documented to omit `permissions` (e.g. parent‑repo payloads), and any consumer of `permissions` for security‑relevant decisions should treat a missing/unrefreshed value as "unknown" rather than "same as before."

### Proof of Concept
1. Sign in to an account and open a repository whose remote matches that account; Desktop stores `gitHubRepository` with `permissions` reflecting write access, used by `hasWritePermission` checks in `app.tsx`/`filter-changes-list.tsx`.
2. Revoke the user's collaborator access on GitHub, or remove/replace the signed-in account in Desktop, or change the local remote URL to point elsewhere (e.g. via a malicious script or a repository operation that rewrites `.git/config`).
3. Trigger a refresh (`refreshSelectedRepositoryAfterAccountChange` → `repositoryWithRefreshedGitHubRepository`). Because `matchGitHubRepository` no longer matches, the function hits the `if (!match) return repository` branch at [4](#0-3)  and the stale `gitHubRepository`/`permissions` persists unchanged.
4. Any UI decision reading `hasWritePermission`/`gitHubRepository.permissions` continues to reflect the pre-revocation state, since no re-validation occurred.

Note: I could not fully trace every consumer of `hasWritePermission`/`GitHubRepositoryPermission` to confirm the exact user-visible security bypass (e.g., whether it suppresses a force-push confirmation or a protected-branch warning) within the available index; the `app.tsx`, `filter-changes-list.tsx`, and `error-handlers.ts` usages were located but not fully read in this pass. Confirming the precise gated action would require reading those files directly (index size limits may also be truncating some of their content) — a full Devin session with file access would let you verify the exact downstream consequence.
