### Title
JSON Injection via Unescaped `Any.type_url` in ProtoJSON Serialization - ([File: php/src/Google/Protobuf/Internal/Message.php])

### Summary
The PHP protobuf runtime's `Message::serializeToJsonStream()` writes the `google.protobuf.Any` message's `type_url` field directly into the JSON output stream via raw byte writes, with no JSON string escaping applied. Since `type_url` is an ordinary attacker-controlled `string` field (settable by supplying arbitrary bytes for field 1 of an `Any` submessage in a bounded binary Protobuf payload), a value containing `"`, `\`, control characters, or `<`/`>`/`&` can break out of the intended JSON string context, exactly mirroring the CVE-2018-18836 Netdata pattern where an attacker-controlled parameter is written into a JSON response without sanitization.

### Finding Description
`Message::serializeToJsonStream()` special-cases `Any` messages and manually assembles the `@type` field: [1](#0-0) 

```php
if (is_a($this, 'Google\Protobuf\Any')) {
    $output->writeRaw("{", 1);
    ...
    // Serialize type url.
    $output->writeRaw("\"@type\":", 8);
    $output->writeRaw("\"", 1);
    $output->writeRaw($this->getTypeUrl(), strlen($this->getTypeUrl()));
    $output->writeRaw("\"", 1);
```

Unlike every other string-typed field, which is routed through `GPBJsonWire::serializeSingularFieldToStream()` -> `json_encode($value, JSON_UNESCAPED_UNICODE)` (which properly escapes `"`, `\`, control characters, etc.) as seen in the general string case: [2](#0-1) 

```php
case GPBType::STRING:
    $value = json_encode($value, JSON_UNESCAPED_UNICODE);
    $output->writeRaw($value, strlen($value));
    break;
```

the `type_url` value taken from `$this->getTypeUrl()` is written **raw**, with manually-inserted quote characters and no escaping function (`json_encode`, `GPBJsonWire::escapedJson`, etc.) applied at all. `type_url` is populated straight from the wire-format string field of an `Any` submessage parsed from arbitrary, attacker-supplied binary Protobuf input — there is no validation that it is a well-formed type URL, and no length/character restriction is enforced during `Any` unpacking prior to JSON serialization. This is the direct analog of the Netdata `tqx` parameter flaw: an attacker-controlled string is concatenated into a JSON response body without sanitization, because the code path assumed the value was "safe" (there, an internal chart identifier; here, a type URL) and bypassed the standard escaping routine used for all other string fields.

Every other language runtime examined in this codebase (Java `JsonFormat`, C++ `json/internal/writer.cc`, upb's `jsonenc_string`/`jsonenc_stringbody`, Python's `json.dumps`) routes *all* string-typed values — including well-known-type special cases — through the same escaping primitive used for normal fields, and additionally escapes XSS-relevant characters (`<`, `>`, `&`, `=`, `'`) beyond the bare JSON spec requirement: [3](#0-2) [4](#0-3) 

The PHP `Any` handler is the outlier: it is the only place found where a field value bypasses the shared string-escaping function entirely.

### Impact Explanation
An attacker who controls a binary `Any`-wrapping message (a normal, schema-conformant input to any application calling `serializeToJsonStream`/`serializeToJsonString` on that message) can set `type_url` to a value like `evil","injected":true,"x":"` or a value containing raw control characters/newlines. The resulting JSON output is structurally corrupted: keys/values can be injected, sibling fields can be shadowed or overridden, and — since `<` and `>` are not escaped here (unlike in the general string path) — if the JSON is later reflected into an HTML/JS context by a downstream consuming application, this becomes a stored/reflected content-injection or XSS vector, matching the “JSON injection” classification and impact of CVE-2018-18836 (Confidentiality: None, Integrity: High per the CVSS vector — output structure/integrity is compromised, not memory safety). No crash or memory corruption is claimed; this is a pure output-integrity break in a supported public serialization API.

### Likelihood Explanation
Likelihood is high for any application that: (1) accepts serialized `Any` messages (or any message containing an `Any` field) from an untrusted client, and (2) serializes them to ProtoJSON using the PHP runtime for further transmission (e.g., re-exposing via an HTTP API, embedding in a web page, or logging as JSON). This requires no privileged access, no malformed schema, and no protocol violation — `type_url` is a completely ordinary string field that any client constructing a valid, bounded binary payload can set to any byte sequence. Reachability only requires calling the standard public `serializeToJsonStream`/`toJsonString` API on an `Any`-containing message, which is a normal, supported operation.

### Recommendation
Route the `type_url` value in `Message::serializeToJsonStream()` (php/src/Google/Protobuf/Internal/Message.php, `Any` branch) through the same escaping used for other string fields — e.g., call `json_encode($this->getTypeUrl(), JSON_UNESCAPED_UNICODE)` (or `GPBJsonWire::escapedJson()`) instead of writing `"` and the raw string manually. Add a regression test analogous to the Java `testHtmlEscape`/control-character tests that packs an `Any` with a crafted `type_url` containing `"`, `\`, control characters, and `<`/`>`, and asserts the output is valid, correctly-escaped JSON.

### Proof of Concept
Conceptual PoC (not executed against a live checkout, but supported directly by the code paths cited above):
1. Construct any protobuf message `M` containing an `Any` field.
2. Craft the `Any`'s `type_url` bytes (field 1, a `string`) to the value: `type.googleapis.com/x","pwned":"1`
3. Serialize `M` to binary Protobuf (standard wire format, no malformed schema needed) and feed it into a PHP application that decodes it with `M::mergeFromString()` and re-serializes with `$m->serializeToJsonString()` / `serializeToJsonStream()`.
4. Expected (bug) output: the raw string is spliced in unescaped, producing a JSON document with an injected `"pwned":"1"` key/value pair or, depending on payload, unterminated string / malformed JSON — as directly implied by [5](#0-4) , since no escaping call sits between `getTypeUrl()` and `writeRaw()`.
5. Contrast expectation: for a normal `string` field, the same crafted value would be safely escaped via [2](#0-1) , producing valid JSON with the quote/control characters properly escaped.
