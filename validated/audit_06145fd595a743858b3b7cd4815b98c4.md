### Title
`SignableTransaction::new` omits the OP_RETURN output from weight/vsize estimation, producing underpaid fees and potentially non-standard oversized transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying up to 80 bytes of caller-supplied `data` to the transaction, but then computes the transaction weight, virtual size, required fee, and the `MAX_STANDARD_TX_WEIGHT` standardness check using only `payments` — never including the OP_RETURN output. The resulting transaction is larger than estimated, pays a lower effective fee rate than the caller requested, and can exceed the standardness weight limit entirely.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` before the fee/size accounting is performed:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data).expect("data didn't fit into PushBytes ..."),
    ),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` builds a mock transaction from `payments` plus an optional `change` output — `tx_outs` (which contains the OP_RETURN) is never consulted:

```rust
output: payments
  .iter()
  .map(|payment| TxOut { value: Amount::from_sat(payment.1), script_pubkey: payment.0.clone() })
  .collect(),
```

Consequences:
1. `needed_fee = fee_per_vbyte * vbytes` is computed over a vsize missing the OP_RETURN output (~11–93 vbytes for 0–80 bytes of data, plus output overhead). The `TooLowFee` check against `DEFAULT_MIN_RELAY_TX_FEE` also uses this underestimated vsize, so a transaction can pass the check yet broadcast at an effective fee rate below the minimum relay fee.
2. The change amount `input_sat - payment_sat - fee_with_change` is computed against the underestimated fee, so the actual fee paid equals `needed_fee` in absolute sats while the transaction is larger — the realized sat/vbyte rate is strictly lower than `fee_per_vbyte`.
3. The `weight > MAX_STANDARD_TX_WEIGHT` check uses the underestimated `weight`, so a transaction can be built, signed, and emitted that exceeds `MAX_STANDARD_TX_WEIGHT` and is rejected by every standard node — yet `TransactionMachine` signing is bound to that exact transaction via `Prevouts::All` in the taproot sighash.

Because `data` is attacker-influenced in Serai's usage (it carries the user's withdrawal/forward instruction, up to the 80-byte cap enforced at `send.rs:171`), an unprivileged party supplying maximum-length data maximizes the estimation error: roughly +13 WU for the fixed output overhead plus ~4·(1 + len) WU for the script — enough to push a borderline transaction over the relay-fee floor or the standardness cap, or to silently degrade the fee rate of any transaction carrying data.

Since `Prevouts::All` commits each input's signature to this exact transaction (`send.rs:375-390`), a rejected transaction cannot be patched — the inputs cannot be re-spent through this machine without an entirely new FROST signing ceremony, mirroring the report's "temporary DOS of funds requiring recovery" impact.

### Impact Explanation
Two concrete impacts:
- **Effective fee underpayment**: every transaction carrying an OP_RETURN pays a strictly lower sat/vbyte rate than requested. With `fee_per_vbyte` at or near the minimum relay rate, the signed transaction will not relay, and its inputs sit unconfirmed until a re-sign.
- **Standardness violation**: when `weight` is near `MAX_STANDARD_TX_WEIGHT` (400,000 WU), the uncounted OP_RETURN output pushes the real weight over the limit. The transaction is permanently non-standard and invalid for relay; the funds are stuck behind a transaction that can never confirm, requiring a fresh signing round over corrected inputs/outputs — the same class of "funds locked in a mis-routed/incorrectly formed flow" as the reference finding.

### Likelihood Explanation
Any transaction created with `data: Some(..)` (up to 80 bytes, reachable by unprivileged users supplying instruction data) undercounts its size. Whether the transaction actually stalls depends on fee-market conditions and how close to policy limits the transaction is, but the miscalculation occurs deterministically on every OP_RETURN-bearing transaction, and near-limit transactions are realistic for a bridge batching many inputs.

### Recommendation
Include the OP_RETURN output in the size estimation — e.g., pass the fully assembled `tx_outs` (or payments + OP_RETURN + optional change) into `calculate_weight_vbytes` so `vbytes`, `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the final transaction. Also re-derive the change output against the corrected `fee_with_change`.

### Proof of Concept
Conceptual, based on `send.rs`:
```rust
let payments = vec![(dest_script, 10_000u64)];
let data = Some(vec![0xAA; 80]); // max attacker-controlled data

let tx = SignableTransaction::new(
    vec![input], &payments, None, data, fee_per_vbyte
).unwrap();

// tx.transaction().output contains the OP_RETURN output,
// but tx.needed_fee() == fee_per_vbyte * vsize(without OP_RETURN).
assert!(tx.transaction().vsize() as u64 * fee_per_vbyte > tx.needed_fee());
// If payments' weight ≈ MAX_STANDARD_TX_WEIGHT, the real
// tx.weight() exceeds the limit while the check passed.
```
