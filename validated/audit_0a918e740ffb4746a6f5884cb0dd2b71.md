### Title
Silent single-step remote-URL takeover from GitHub API response with no host-pinning confirmation - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` rewrites a repository's local git remote URL automatically whenever a fresh `IAPIRepository` object is fetched from the GitHub/GHES API, provided the URL scheme matches and the previous URL still matched the last known `cloneURL`. Crucially, it never verifies that the new `clone_url` still points at the same host/owner the user originally trusted — it only checks the protocol (`https` vs `ssh`), not the hostname. This mirrors the reported smart-contract bug class: a privileged pointer (there: `market.host`; here: the git remote that receives all future `push`/`pull` traffic and credentials) is reassigned in a single, unconfirmed step driven entirely by external/attacker-influenced input, with no "propose new value, then have the owner/user explicitly claim/confirm it" step.

### Finding Description
`updateRemoteUrl` in [1](#0-0)  performs this logic:
- It reads `apiRepo.clone_url` (attacker-influenceable if the GitHub/GHES API endpoint returns a malicious value for a repository, e.g. a compromised/rogue GHES instance, a repo transfer to a look-alike location, or a proxied/MITM'd API response for `repos/{owner}/{name}`).
- `protocolsMatch` only compares URL **scheme** (`https:` vs `ssh:`), not hostname: [2](#0-1) .
- `remoteUrlUnchanged` only confirms the *current* local remote still matches the *previously cached* `gitHubRepository.cloneURL` (i.e., the user hasn't hand-edited it) — it does **not** constrain the *new* URL to the same host: [3](#0-2) .
- If those two conditions hold and the URL differs, it silently calls `gitStore.setRemoteURL(...)`, rewriting the actual git remote on disk with **no user prompt, confirmation dialog, or two-step "propose/claim" flow**: [4](#0-3) .

This function is invoked from `repositoryWithRefreshedGitHubRepository`, which fetches the repository afresh from the API (`api.fetchRepository(owner, name)`) and immediately applies the update if a `gitHubRepository` is already associated: [5](#0-4) . `API.fetchRepository` simply parses whatever the HTTP response body contains as `IAPIFullRepository`, with no host allow-listing beyond the account's configured endpoint: [6](#0-5) .

Because `urlMatchesRemote`/`urlsMatch` (used elsewhere for comparison) parse and compare hostname/owner/name [7](#0-6) , the codebase clearly has the primitive needed to pin the host, but `updateRemoteUrl` deliberately does not use it to gate the *new* URL — only the scheme is checked. The unit tests confirm the only two guard rails are "protocol match" and "remote hasn't been manually changed," not "same host": [8](#0-7) .

### Impact Explanation
If an attacker can influence the `clone_url` returned for a repository the user is tracking (e.g., a compromised or malicious GitHub Enterprise Server the user is enrolled with, a network-level proxy/MITM of the API response for `repos/{owner}/{name}`, or abuse of a repository-rename/transfer race), Desktop will silently repoint the user's `origin` remote to an attacker-controlled git host. Because this happens with no confirmation dialog, all subsequent operations against that repository — `git push` (with credentials/tokens sent via the git credential helper to the new host), `git fetch`/`pull` (ingesting attacker-controlled objects into the user's working tree/history) — are silently redirected. This can lead to credential/token exfiltration to the attacker's git server and corruption of what the user believes they are pushing/pulling, matching the "silent corruption of what the user commits or pushes" and "credential/token exfiltration" impact categories.

### Likelihood Explanation
The path is reached automatically during normal repository refresh (`repositoryWithRefreshedGitHubRepository`), i.e., without any unusual user action — it fires whenever Desktop refreshes GitHub metadata for an already-tracked repository. The only preconditions are (1) the local remote currently matches the last cached `cloneURL` (true for the vast majority of users who never hand-edit their `origin` URL) and (2) the attacker-controlled `clone_url` uses the same protocol scheme (trivially satisfiable — just serve an `https://` URL). No admin rights, local access, or leaked credentials are required from the victim's side; the trust boundary being crossed is exactly the one called out as valid in the task ("attacker controls ... a GitHub API object"). The main uncertainty is the exact mechanism by which an attacker forces the GitHub/GHES API to return an attacker-chosen `clone_url` for a repo the victim already tracks (e.g., malicious GHES admin, compromised endpoint, or API response tampering) — this constrains it to Medium rather than High confidence without further verification of a concrete network/API compromise vector, but the missing hostname-pinning guard itself is unambiguous from the code.

### Recommendation
Apply the same "two-step, explicit confirmation" principle recommended in the original report to `updateRemoteUrl`:
1. Do not silently rewrite the remote URL when the host/owner in the new `clone_url` differs from the currently configured remote's host — treat that as a **proposed** change only.
2. Require explicit user confirmation (a dialog akin to the existing repository-settings remote URL change flow in `RepositorySettings.onSubmit`, see [9](#0-8) ) before applying any change that alters the hostname, not just cases where the user manually edits it.
3. Reuse `urlMatchesRemote`/`urlsMatch` to explicitly gate on hostname equality, not merely protocol equality, before auto-applying remote URL updates.

### Proof of Concept
1. User has GitHub Desktop tracking `Repository A` with `origin` remote `https://github.com/acme/widgets` and an associated `gitHubRepository.cloneURL` of the same value.
2. Attacker gets the API response for `GET repos/acme/widgets` (served to this user's Desktop instance — e.g. via a compromised/rogue GHES the user is enrolled with, or a network position able to tamper with that specific API call) to return `clone_url: "https://evil-git-host.example/acme/widgets"`.
3. Desktop's periodic/foreground repository refresh calls `repositoryWithRefreshedGitHubRepository` → `api.fetchRepository('acme','widgets')` → returns the attacker's `apiRepo` → `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`.
4. Inside `updateRemoteUrl`: `protocolsMatch` is `true` (both `https:`), `remoteUrlUnchanged` is `true` (local remote still equals the last cached `cloneURL`), `urlsMatch` is `false` (different host) → the function calls `gitStore.setRemoteURL('origin', 'https://evil-git-host.example/acme/widgets')` with no prompt shown to the user.
5. The next time the user pushes, Desktop pushes (and sends git credentials for) `https://evil-git-host.example/acme/widgets` instead of the real GitHub repository. [1](#0-0) [5](#0-4)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
