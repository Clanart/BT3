### Title
`SignableTransaction::new` computes the fee and minimum-relay check from a transaction shape that omits the OP_RETURN data output - (networks/bitcoin/src/wallet/send.rs)

### Summary
The analog to "wrong fee/parameter used to validate the operation" is that `SignableTransaction::new` calculates `weight`, `vbytes`, `needed_fee`, the `TooLowFee` minimum-relay check, and the `MAX_STANDARD_TX_WEIGHT` check using `calculate_weight_vbytes`, which is only ever passed `payments` and the optional `change` output — never the OP_RETURN output created from `data`. The fee actually charged (`sum(inputs) - sum(outputs)`) is fixed at `needed_fee`/`fee_with_change`, so a transaction carrying up to 80 bytes of OP_RETURN data is signed with a real fee rate far below `fee_per_vbyte`, and can fall below the default minimum relay fee despite the `TooLowFee` check passing.

### Finding Description
`SignableTransaction::new` pushes an OP_RETURN `TxOut` containing `data` into `tx_outs` [1](#0-0) , then estimates the transaction size via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` and `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` [2](#0-1) . `calculate_weight_vbytes` reconstructs a template transaction whose outputs are exactly `payments` plus the optional `change` — the OP_RETURN output is never included [3](#0-2) .

Consequently:
- `needed_fee = fee_per_vbyte * vbytes` (and `fee_with_change`) are computed on a `vbytes` that excludes the data output [4](#0-3) .
- The minimum-relay guard `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` compares an underestimated fee against an underestimated vbytes, so it validates a different transaction than the one built [5](#0-4) .
- The change output amount is `input_sat - payment_sat - fee_with_change`, so the final signed transaction pays exactly `fee_with_change` while being ~90+ vbytes larger than estimated [6](#0-5) .
- The `MAX_STANDARD_TX_WEIGHT` check uses the underestimated `weight` [7](#0-6) .

### Impact Explanation
The real fee rate of the produced transaction is `needed_fee / actual_vsize`, which is strictly less than the requested `fee_per_vbyte` whenever `data` is supplied. For `fee_per_vbyte` near 1 sat/vB and 80 bytes of data (~90+ extra vbytes for the OP_RETURN output including script overhead), the effective rate falls below `DEFAULT_MIN_RELAY_TX_FEE` even though `TransactionError::TooLowFee` was checked and passed. The resulting signed transaction is rejected by Bitcoin Core's mempool (`min relay fee not met` / `mempool min fee` / non-standard), i.e., funds are committed to a transaction that cannot propagate — an incorrect-parameter validation causing funds to be sent on an unbroadcastable transaction. This matches the report's class: the guard validates against one parameter set (fee for a tx without the data output) while the operation executes under another (the actual larger tx).

### Likelihood Explanation
`data` is an attacker/user-controllable parameter of `SignableTransaction::new` (public API; the processor currently passes `None`, but any caller supplying an OP_RETURN triggers it). Low fee rates near the relay minimum are the default operating point for consolidation-style transactions, so the underestimated-fee case is realistic whenever `data` is used. Severity is bounded to Medium: funds are not stolen, but the signed transaction silently carries a lower fee rate than requested and can be unrelayable.

### Recommendation
Include the OP_RETURN output in the size estimation — e.g., pass the already-constructed `tx_outs` (or append a `TxOut { value: Amount::ZERO, script_pubkey: <op_return script> }`) into `calculate_weight_vbytes` for both the no-change and with-change calls, so `vbytes`, `needed_fee`, the `TooLowFee` check, and the weight check all reflect the transaction actually being built.

### Proof of Concept
- `inputs` = one `ReceivedOutput` worth e.g. 50,000 sats; `payments` = `[(addr, 1000)]`; `data` = `Some(vec![0; 80])`; `change` = `None`; `fee_per_vbyte` = `1`.
- `calculate_weight_vbytes` returns `vbytes ≈ 144` (1 input + 1 payment output, no data output), so `needed_fee = 144` and the min-relay check `144 < (1000 * 144)/1000 = 144` passes.
- The built `tx` additionally contains the OP_RETURN output (~92 extra vbytes), giving `actual_vsize ≈ 236`.
- `fee()` = `50000 - 1000 - 0`... with `change = None` the leftover becomes fee; to see the fee-rate divergence cleanly use `change = Some(addr)`: change = `50000 - 1000 - fee_with_change`, so the signed tx pays exactly `fee_with_change` over ~236 actual vbytes → ~0.6 sat/vB < 1 sat/vB relay minimum, while `TooLowFee` never fired. `rpc.send_raw_transaction` rejects it; the funds are locked in an unpropagating transaction until re-signed with a correct fee.
