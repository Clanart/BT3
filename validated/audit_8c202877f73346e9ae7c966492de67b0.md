### Title
Tokenfactory denom admin can retroactively update the allow list to permanently freeze existing holders' balances with no seize/recovery mechanism - ([File: sei-cosmos/x/bank/keeper/send.go])

### Summary
`MsgUpdateDenom` lets a tokenfactory denom's admin change the denom's `AllowList` at any time, including after other accounts already hold balances of that denom. Once an address is excluded from the allow list, `IsInDenomAllowList` unconditionally blocks it from sending (and, via the same check on the receiver side, from having new funds routed to it), with no code path to reverse or seize the now-unmovable balance — the same "authorization gate governs already-held funds, and once revoked there is no recovery" bug class as the reported `CToken`/passport issue, where burning a passport (a mutable authorization credential) permanently locks funds with no seize mechanism.

### Finding Description
`x/tokenfactory/keeper/msg_server.go`'s `UpdateDenom` only checks that the caller is the denom's current admin before calling `bankKeeper.SetDenomAllowList`, with no restriction preventing the admin from removing addresses that already hold balances of the denom: [1](#0-0) 

`SetDenomAllowList`/`GetDenomAllowList` store this list keyed only by denom, and `IsInDenomAllowList` is the sole gate used by `bank.MsgServer.Send`/`MultiSend` for any coin whose denom has the `factory/` prefix: [2](#0-1) [3](#0-2) 

If an address is not in a denom's (non-empty) allow list, `IsInDenomAllowList` returns `false` unconditionally for both the `from` and `to` side of a transfer — there is no fallback, appeal, or forced-transfer/seize path anywhere in the bank or tokenfactory modules (`ForceTransfer`/`BeforeSendHook`-style overrides do not exist in this codebase, confirmed by search). Balances already sitting on a now-excluded address for that denom become permanently unsendable by that holder, exactly mirroring the reported bug's root cause: a mutable, admin-controlled authorization check (`getHighestAMLScore()`/passport possession there; allow-list membership here) that is re-evaluated on every action rather than being fixed at mint/deposit time, with no mechanism to recover the locked balance once the credential is revoked.

The identical logic is duplicated in `giga/deps/xbank/keeper/send.go`: [4](#0-3) 

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by a legitimate, unprivileged actor category explicitly in scope (tokenfactory denom creator/admin acting against holders of their own denom). Any account — potentially including EVM pointer contracts or liquidity pools that hold tokenfactory-denom coins — can have its balance of that denom permanently frozen the moment the denom admin submits a normal `MsgUpdateDenom` tx that omits it from a new allow list. Since there is no seize, forced-transfer, or governance override, the coins are unrecoverable by the holder or anyone else, constituting permanent fund freezing (one of the explicitly accepted impact categories).

### Likelihood Explanation
Likelihood is high for any tokenfactory denom that uses an allow list feature, since `MsgUpdateDenom` is a normal, unprivileged (relative to the chain — only denom-admin-privileged) transaction with no additional guardrails against excluding existing balance holders. The only precondition is that the denom has (or later adopts) a non-empty allow list and that the affected account received funds of that denom before being dropped from the list — both of which are ordinary token-factory usage patterns.

### Recommendation
Add a check in `UpdateDenom` (or in `SetDenomAllowList`) that prevents removing an address from a denom's allow list while it still holds a nonzero balance of that denom, or alternatively provide an explicit, permissioned "forced transfer"/"seize" instruction (similar to what the original report recommended for `CToken`) so that governance or the denom admin can migrate/burn a locked balance rather than leaving it permanently stranded. At minimum, document and gate this behavior so wallets/pointers can detect and avoid holding allow-listed tokenfactory denoms without such protection.

### Proof of Concept
1. Denom admin `A` creates `factory/A/X` with no allow list (or an allow list containing address `H`) via `MsgCreateDenom`.
2. Holder `H` receives some `factory/A/X` coins through normal `MsgSend` (see `sei-cosmos/x/bank/keeper/msg_server.go` `Send`, lines 26-49, no allow-list restriction applies while `H` is allowed/unrestricted).
3. Admin `A` submits `MsgUpdateDenom{Denom: "factory/A/X", AllowList: {Addresses: [A]}}` (excluding `H`) — `x/tokenfactory/keeper/msg_server.go` `UpdateDenom` (lines 57-92) accepts this because `A` is still the admin; no check considers existing holders.
4. `H` now attempts `MsgSend` of `factory/A/X`; `IsInDenomAllowList(ctx, H, ...)` (`sei-cosmos/x/bank/keeper/send.go`, lines 484-502) returns `false`, and the bank `Send` handler (lines 43-45) rejects the tx with `"... is not allowed to send funds"`.
5. `H`'s balance of `factory/A/X` is now permanently stuck: there is no `MsgForceTransfer`, seize, or override mechanism in `x/tokenfactory` or `x/bank` to move or burn it, replicating the reported "locked `CToken`s with no way to redeem or liquidate" scenario.

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

func (k BaseSendKeeper) SetDenomAllowList(ctx sdk.Context, denom string, allowList types.AllowList) {
	store := ctx.KVStore(k.storeKey)
	denomAllowListStore := prefix.NewStore(store, types.DenomAllowListKey(denom))

	m := k.cdc.MustMarshal(&allowList)
	denomAllowListStore.Set([]byte(denom), m)
}

func (k BaseSendKeeper) GetDenomAllowList(ctx sdk.Context, denom string) types.AllowList {
	store := ctx.KVStore(k.storeKey)
	store = prefix.NewStore(store, types.DenomAllowListKey(denom))

	bz := store.Get([]byte(denom))
	if bz == nil {
		return types.AllowList{}
	}

	var allowList types.AllowList
	k.cdc.MustUnmarshal(bz, &allowList)

	return allowList
}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

	if err != nil {
		return nil, err
	}

	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
