### Title
Relayer/protocol fee withdrawals on `EvmHost` drain the shared fee-token pool without checking outstanding per-request escrow, enabling loss of undelivered relayer fees and timeout refunds - (File: `evm/src/core/EvmHost.sol`)

### Summary
The DEX report's broken invariant is: an accounting counter (`collected_token_protocol_fee`) is credited from a shared reserve, but the reserve itself is never decremented, so the same underlying tokens back two independent claims. The same shape exists in `EvmHost`/`HostManager`: relayer and protocol-fee withdrawals move tokens out of `EvmHost`'s single fee-token balance based purely on an off-chain-computed `amount`, with no check that the balance remaining still covers the fees already escrowed for requests that are dispatched but not yet delivered or timed out.

### Finding Description
When a user dispatches a request with a fee, the fee token is pulled into `EvmHost` and the amount is recorded per-commitment in `_requestCommitments[commitment]` [1](#0-0) . That per-request fee is a *liability* the contract owes either to the relayer who delivers the message (via `pallet-ismp-relayer`'s accumulate/withdraw flow) or back to the payer on timeout.

Separately, `EvmHost.withdraw()` — invoked only through `HostManager.onAccept` for both `OnAcceptActions.Withdraw` (relayer fee payout) and governance-triggered protocol-fee withdrawals — transfers `params.amount` directly out of the contract's balance with no invariant check against `_requestCommitments`: [2](#0-1) [3](#0-2) 

On the Hyperbridge side, `pallet-ismp-relayer::withdraw` computes `available_amount` purely from the pallet's own `Fees` storage map — a counter accrued during `accumulate()` — and dispatches a `WithdrawalParams { amount: available_amount, .. }` request to `HostManager`, again with no cross-check against `EvmHost`'s actual remaining balance or against fees still reserved for in-flight requests: [4](#0-3) 

Exactly like the DEX bug, `Fees[relayer]` (the accrued-fee counter) and the protocol-fee withdrawal path are bookkeeping entries layered on top of a single shared reserve (`EvmHost`'s fee-token balance), but nothing decrements that reserve to reflect tokens still owed to *other* pending requests' relayers or payer-refund-on-timeout. Any relayer who legitimately accrues and withdraws fees, racing with a governance protocol-fee withdrawal (`pallet-ismp-host-executive::withdraw`) or with another relayer's withdrawal, can drain `EvmHost` below what is needed to satisfy fee payouts/refunds for requests dispatched earlier but not yet delivered/timed out.

### Impact Explanation
Because `EvmHost.withdraw()` performs an unconditional `safeTransfer`/native transfer with no reserve check, once the pool is drained below outstanding commitments:
- A pending request's timeout refund (`onPostRequestTimeout` → payer refund) can fail or be short-paid, causing fund loss for the original fee payer.
- A relayer who delivered a message earlier and is entitled to `_requestCommitments[commitment].fee` may find the shared pool empty when their `accumulate`/`withdraw_fees` payout is dispatched, causing loss of the earned reward — the exact "another pool's balance being lower than its recorded entitlement" failure mode described in the source report.

### Likelihood Explanation
This does not require a malicious relayer, prover, or admin: relayer fee withdrawal (`withdraw_fees`) is a normal, permissionless-by-design action available to any relayer holding a signature over their own accrued balance, and it is entirely decoupled from `EvmHost`'s live balance or from other requests' committed fees. Ordinary operational concurrency — several relayers withdrawing near-simultaneously, or a routine protocol-fee sweep landing between a request's dispatch and its delivery/timeout — is enough to trigger the shortfall, with no single actor needing to behave maliciously.

### Recommendation
- Short term: before executing `EvmHost.withdraw()`, and before dispatching a relayer withdrawal from `pallet-ismp-relayer`, verify the requested amount does not exceed `EvmHost`'s balance minus the sum of fees still outstanding in `_requestCommitments` for requests that are neither delivered nor timed out.
- Long term: track a single, on-chain "free" (non-reserved) balance for `EvmHost` that is atomically debited when a request's fee is escrowed and credited back only when that specific fee is paid out or refunded, so relayer/protocol withdrawals can never touch tokens still earmarked for a different request.

### Proof of Concept
1. User A dispatches `RequestX` on `EvmHost` with `fee = 100 USDC`; `_requestCommitments[X] = {fee: 100, sender: A}` and `EvmHost` balance is credited 100 USDC.
2. Relayer R had earlier accrued 100 USDC of legitimate fees in `pallet-ismp-relayer::Fees[dest_chain][R]` from unrelated prior deliveries, and calls `withdraw_fees` [5](#0-4) ; this dispatches a `WithdrawalParams{amount:100}` to `HostManager`, which calls `EvmHost.withdraw()` and drains the same 100 USDC that is backing `RequestX`'s fee.
3. `RequestX` subsequently times out. `onPostRequestTimeout` succeeds (handler logic), but the fee-refund transfer to A reverts or comes up short because `EvmHost`'s balance no longer contains A's 100 USDC — it was already paid out to R in step 2, even though R's fee was unrelated to `RequestX`.
4. No step above required an admin key, a compromised relayer, or a malicious prover — only ordinary, independently-legitimate withdrawal and timeout flows racing against a shared, unpartitioned token pool.

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }
