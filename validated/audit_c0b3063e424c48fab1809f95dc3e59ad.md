## Title
Clone operation unconditionally disables Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard, enabling hook-based code execution from a malicious cloned repository - (File: `app/src/lib/git/clone.ts`)

### Summary
`GitHub Desktop`'s clone routine explicitly disables the upstream Git safety check that was introduced to close CVE‑2024‑32004 (arbitrary code execution via maliciously crafted repositories/submodules exploited during `--recursive` clone). Instead of leaving the protection active for the default, most exposed operation — cloning an arbitrary user/attacker-supplied URL — Desktop unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for every clone.

### Finding Description
`clone()` in [1](#0-0)  builds the environment for the `git clone --recursive ...` invocation:

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c',
  `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
``` [2](#0-1) 

Git's `GIT_CLONE_PROTECTION_ACTIVE` variable governs the runtime check Git added specifically to prevent a cloned repository (including its recursively fetched submodules) from planting executable hooks (e.g. via crafted `.git`/`gitdir` files, symlinks, or `.gitmodules`/`core.hooksPath` manipulation) that then execute automatically as part of the clone/checkout sequence. Setting this variable to `'false'` disables that protection outright for the entire clone operation, which is the exact attacker-facing entry point the protection was created to guard: cloning a URL the user does not control the content of.

Because the clone is issued with `--recursive`, submodules referenced by the top-level (attacker-controlled) repository are fetched and initialized as part of the same operation, widening the surface for the disabled check (submodule-planted hooks/config were part of the original CVE class this protection addresses).

Existing mitigations in this codebase do not cover this gap:
- `isClonePathSensitive()` only guards against the clone *destination* path being sensitive (e.g. `~/.ssh`), not against malicious *content* fetched into that path [3](#0-2) .
- The hook-interception machinery (`withHooksEnv`/`getRepoHooks`/hooks-proxy) is opt-in per-`git()` call via `opts.interceptHooks`, and the `clone()` function does not pass `interceptHooks` at all, so no hook redirection/sandboxing occurs during clone [4](#0-3) .
- The "untrusted directory" ownership check (`getRepositoryType`/`addSafeDirectory` flow in `missing-repository.tsx` and `add-existing-repository.tsx`) only applies to *existing local directories owned by another OS user*; it has no bearing on content freshly cloned from a remote URL by the same OS user running Desktop [5](#0-4) .

### Impact Explanation
An attacker who controls a Git remote (a public/forked repository, a link shared with the victim, or a compromised proxy/MITM response for a remote the user is convinced to clone) can craft a repository (directly or via a submodule reached through `--recursive`) that, upon `git clone`, plants and triggers execution of a Git hook on the victim's machine — achieving arbitrary code execution as soon as the user clones the repository in GitHub Desktop, with no further action required. This is the class of vulnerability Git's own `GIT_CLONE_PROTECTION_ACTIVE` mechanism exists to stop, and Desktop disables it for every clone unconditionally.

### Likelihood Explanation
Cloning a repository from a URL is one of the most common, low-friction actions in GitHub Desktop (via "Clone repository", "Open in Desktop" deep links, or CLI `--cli-clone`), and it is routinely performed against repositories the user does not control the internal content of (forks, third-party projects, links shared in issues/PRs). No special privileges, local access, or social engineering beyond "clone this repo" is required, making this a realistic and high-likelihood trigger path.

### Recommendation
Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts` and let Git's built-in clone protection remain active for standard clones of remote URLs. If this override was added to work around a specific internal scenario (e.g., trusted local-to-local clones or programmatic re-clone flows), scope the override narrowly to only those call sites, and instead route the general `clone()` path through the existing hook-interception (`interceptHooks`) mechanism so any hooks introduced by the clone are sandboxed through the same proxy used for other Git operations.

### Proof of Concept
1. Attacker publishes/forks a repository containing a submodule crafted per the CVE‑2024‑32004 hook-planting technique (e.g. a `.gitmodules` entry or nested `gitdir`/symlink structure that results in an executable hook file, such as `post-checkout`, being placed under the target repository's hooks directory as part of `--recursive` submodule initialization).
2. Attacker shares the clone URL (or an `x-github-client://openRepo/...` deep link handled by `handleAppURL`/`parseAppURL`) with the victim.
3. Victim clones the repository in GitHub Desktop via the normal "Clone repository" flow, which invokes `clone()` in `app/src/lib/git/clone.ts`.
4. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'`, Git's runtime check that would normally detect and refuse the malicious hook placement is skipped, and the planted hook executes with the victim's OS-level privileges during/after the clone — without the victim running any command beyond "Clone".

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
