### Title
DKG blame proof leaks a reusable ECDH decryption key before proof-of-possession verification - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` can publish an `EncryptionKeyProof` for a message whose per-message key proof-of-possession has not yet been verified. An attacker can copy the ephemeral encryption key from an honest participant’s ciphertext into a malformed share, causing the victim to disclose the ECDH shared point that decrypts the honest ciphertext. [1](#0-0) [2](#0-1) 

### Finding Description
`EncryptedMessage` intentionally includes a Schnorr proof-of-possession because reusing another message’s encryption key can make blame revelation expose the original message’s ECDH key. [3](#0-2) 

`Encryption::decrypt` only queues that proof-of-possession for batch verification; it immediately computes `ecdh(private, msg.key)`, decrypts the ciphertext, and returns an `EncryptionKeyProof` containing the shared ECDH point and a DLEQ proof. [2](#0-1) 

`calculate_share` then parses the decrypted `SecretShare`; if it is not a canonical scalar, it returns `InvalidShare` with `Some(blame)` before `batch.verify_with_vartime_blame()` ever rejects the invalid proof-of-possession. [1](#0-0) [4](#0-3) 

The leaked proof is serializable and contains the raw ECDH point followed by its DLEQ proof. [5](#0-4)  The processor forwards that serialized proof in the public `InvalidShare` response. [6](#0-5) 

The stream cipher derives its ChaCha20 key solely from the DKG context and ECDH point, while using a fixed IV, so disclosure of `msg.key * victim_enc_key` directly reproduces the keystream used by the original ciphertext. [7](#0-6) 

### Impact Explanation
An attacker who observes an honest encrypted share can learn the plaintext secret share sent to another participant without knowing either participant’s encryption private key. This is direct recovery of DKG secret-share material from public protocol messages.

If the attacker is also a DKG participant, the leaked evaluation can be combined with the attacker’s legitimately received evaluations to reconstruct a dealer’s polynomial once enough distinct evaluations are known; in a 2-of-2 execution, one malicious participant already has one evaluation and obtains the second through this leak. [8](#0-7) [9](#0-8) 

The affected DKG attempt will normally abort, limiting this to confidentiality loss for the attempted key generation rather than compromise of an already-confirmed key, so this is most appropriately classified as Medium severity.

### Likelihood Explanation
The attack requires only supplying malformed share bytes whose decrypted value is unlikely to be a canonical scalar and copying the public `key` point from another ciphertext. The attacker does not need to know the copied ephemeral private key because the invalid proof-of-possession is not checked before the early scalar-deserialization error returns the blame proof.

### Recommendation
Do not construct or return an `EncryptionKeyProof` until the message’s proof-of-possession has been verified. In particular:

1. Verify all queued `msg.pop` signatures before scalar deserialization can produce an early `InvalidShare` result containing a proof.
2. Alternatively, have `decrypt` synchronously verify `msg.pop` before calculating the ECDH key, decrypting, or generating `EncryptionKeyProof`.
3. Ensure every error path that returns `Some(blame)` has already established that the associated `msg.key` is possessed by the sender.
4. Add a regression test that reuses an honest message’s `key` with an invalid PoP and malformed share bytes, and asserts that no blame proof or ECDH key is emitted.

### Proof of Concept
Conceptual attack against `KeyMachine::calculate_share`:

```text
A -> B honest share:
  X = xG
  C = ChaCha20(Hash(context || bX)) XOR SecretShare(f_A(B))
  msg_A = EncryptedMessage { key: X, pop: PoP(x), msg: C }

Attacker C observes X and submits to B:
  msg_C = EncryptedMessage {
    key: X,                  // copied from msg_A
    pop: arbitrary SchnorrSignature,
    msg: arbitrary ciphertext likely to decrypt to invalid scalar
  }

B executes calculate_share:
  1. decrypt(msg_C) queues the invalid PoP.
  2. decrypt computes K = bX and creates EncryptionKeyProof(K, DLEQ).
  3. Decrypted msg_C fails C::F::from_repr.
  4. calculate_share returns InvalidShare { participant: C, blame: Some(proof) }
     before checking the queued invalid PoP.
  5. Processor serializes and publishes proof.

Attacker extracts K from the blame proof and computes:
  plaintext_A = ChaCha20(Hash(context || K)) XOR C
              = SecretShare(f_A(B))
```

The decisive ordering flaw is that the proof-of-possession is merely queued at `msg.pop.batch_verify`, while the ECDH proof is generated and returned before the batch result is checked. [2](#0-1) [10](#0-9)

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");
