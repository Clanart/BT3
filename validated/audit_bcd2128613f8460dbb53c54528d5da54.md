### Title
Unauthenticated `SetOperatorKeys` via `Interceptors::Noop` Allows Front-Running Attack That Permanently Corrupts Deposit State — (`core/src/servers.rs`, `core/src/rpc/interceptors.rs`)

### Summary

When `config.client_verification = false`, `create_grpc_server` installs `Interceptors::Noop` as the gRPC interceptor. `Noop` performs zero authentication — it unconditionally passes every request. An unauthenticated attacker who can reach the verifier's TCP port can call `SetOperatorKeys` with a valid deposit outpoint (observable on-chain) and a legitimate operator xonly_pk (observable from the verifier's `GetParams` or the deposit data), but with attacker-crafted WOTS pubkeys and challenge ACK hashes. Because all DB writes use first-write-wins semantics, if the attacker races the aggregator and writes first, the verifier permanently stores the wrong keys. The legitimate aggregator's subsequent call then hits a mismatch error and the deposit flow is broken forever for that deposit outpoint.

**Step 4 — First-write-wins with asymmetric mismatch detection.**

**Attack sequence:**

1. Attacker observes a confirmed deposit UTXO on Bitcoin.
2. Attacker observes the operator xonly_pk from the verifier's `GetParams` or deposit data.
3. Attacker sends `SetOperatorKeys` with valid deposit data but crafted WOTS pubkeys and challenge ACK hashes.
4. Verifier stores attacker's keys (first write wins).
5. Legitimate aggregator calls `SetOperatorKeys` — `insert_operator_challenge_ack_hashes_if_not_exist` detects mismatch → `BridgeError::OperatorChallengeAckHashesMismatch` → deposit flow aborts.
6. The wrong WOTS keys remain permanently in `operator_bitvm_winternitz_public_keys` (no mismatch detection there).
7. Every subsequent retry by the aggregator hits the same mismatch. The deposit is permanently stuck.

### Impact Explanation

The deposit UTXO is on-chain but the move-to-vault tx is never signed. The BTC is permanently locked in the deposit UTXO. The verifier's DB is in a corrupted state for that `(operator_xonly_pk, deposit_outpoint)` pair with no in-code recovery path. This meets the "permanent lock of bridged BTC" impact gate.

### Likelihood Explanation

Requires `client_verification = false` in production (a supported, documented configuration option — not test-only) and the ability to reach the verifier's TCP port before the aggregator completes `collect_and_distribute_keys`. The deposit outpoint and operator keys are publicly observable. The race window is the time between the deposit being confirmed on Bitcoin and the aggregator calling `SetOperatorKeys`, which can be seconds to minutes. Likelihood is **Medium** given the configuration prerequisite.

### Recommendation

1. **Never use `Noop` on sensitive write endpoints in production.** Either enforce `client_verification = true` for all production deployments, or add per-method authorization inside `set_operator_keys` that verifies the caller is the known aggregator (e.g., by checking a shared secret or requiring mTLS even when `client_verification = false`).
2. **Add mismatch detection to `insert_operator_bitvm_keys_if_not_exist`** (matching the pattern used by `insert_operator_challenge_ack_hashes_if_not_exist` and `insert_bitvm_setup_if_not_exists`) so that a corrupted first write is detectable.
3. **Add a DB-level recovery/reset path** for `(operator_xonly_pk, deposit_outpoint)` key entries that can be invoked by an authorized admin to clear corrupted state.

### Proof of Concept

```
1. Start a verifier with client_verification = false.
2. Observe a confirmed deposit UTXO on regtest Bitcoin.
3. Observe the operator xonly_pk from the verifier's GetParams RPC.
4. Construct an OperatorKeysWithDeposit with:
   - valid deposit_params (matching the on-chain UTXO)
   - operator_xonly_pk = observed operator key
   - operator_keys.winternitz_pubkeys = N random/zeroed WPKs (correct count)
   - operator_keys.challenge_ack_digests = M random 20-byte hashes (correct count)
5. Send SetOperatorKeys to the verifier over plain TLS (no client cert).
6. Observe HTTP 200 / Empty response.
7. Now trigger the legitimate aggregator's new_deposit flow.
8. Observe BridgeError::OperatorChallengeAckHashesMismatch on the aggregator side.
9. Query the DB: operator_bitvm_winternitz_public_keys contains the attacker's keys.
10. Retry new_deposit — same error. Deposit is permanently stuck.
```
