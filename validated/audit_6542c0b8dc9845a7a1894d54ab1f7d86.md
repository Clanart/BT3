## Title
Stale `ContractToAsset`/`Precisions` lookups in `on_timeout` (and `on_accept`) permanently lock or mis-value in-flight transfers after `update_token` migration - (`modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
This is the direct Hyperbridge analog of the OriginToken/Marketplace bug: `pallet-hyper-fungible-token` lets governance re-point an asset's EVM contract address and decimal precision per chain via `update_token`. In-flight `send()` requests, however, embed no snapshot of the contract/precision that was active when they were dispatched. When `update_token` runs while a transfer is still pending, the later `on_timeout` (refund) or `on_accept` (receive) callback re-resolves the *current* `ContractToAsset`/`Precisions` storage instead of the values that were valid at dispatch time, causing either a permanently stuck refund or a mis-converted amount.

### Finding Description
`send()` locks/burns the local asset and dispatches a cross-chain `PostRequest` whose `to` field is the contract address read from `TokenContracts` *at that moment*, and whose embedded amount is scaled using the `Precisions` value read *at that moment*: [1](#0-0) [2](#0-1) 

Governance can later call `update_token`, which removes the old `ContractToAsset` reverse mapping for a chain and points the asset at a new contract address, and/or changes `Precisions` for that `(asset_id, chain)` pair: [3](#0-2) 

If the request times out (or is later delivered) *after* this update, both callbacks re-derive the asset and decimals from **current** storage rather than what was in effect when the request was created:

- `on_timeout` re-resolves the asset via `ContractToAsset::<T>::get(dest, &to)` using the *old* embedded `to` address, which was just removed by `update_token`: [4](#0-3) 

- `on_accept` does the analogous fresh lookup of `Precisions::<T>::get(local_asset_id, source)` before minting: [5](#0-4) 

Two concrete consequences:
1. **Fund lock (exact analog of the report).** If `update_token` changes the registered contract address for that chain (`add_chains`), the old reverse mapping is removed. `ContractToAsset::<T>::get(dest, &to)` in `on_timeout` returns `None`, the timeout dispatch fails with `HftError::UnknownContractOnTimeout`, and the escrowed/burned funds for that specific in-flight request can never be refunded — precisely mirroring "Alice's deposit and Charlie's offer funds are unrecoverable" from the report.
2. **Wrong-amount settlement.** If instead only `Precisions` is changed for that `(asset_id, chain)` (e.g. correcting a misconfigured decimals value, a common legitimate migration action), `on_timeout`/`on_accept` will convert the *already-fixed* `message.amount` using the *new* decimals rather than the decimals used at `send()` time, producing a refund/mint amount that does not match what was actually burned/escrowed — a silent accounting break with real fund-loss or over-mint potential.

No part of `send()`, `on_accept`, or `on_timeout` snapshots the precision/contract binding into the dispatched message or into per-request storage; they all trust the live `TokenContracts`/`ContractToAsset`/`Precisions` maps, which is exactly the "broken invariant" identified in the seed report generalized to Hyperbridge's own token bridge.

### Impact Explanation
This breaks the "bridged assets... must move exactly once and only to the rightful beneficiary and amount" invariant. Depending on which field is updated mid-flight, the result is either (a) permanent loss/lock of a user's escrowed or burned funds with no recovery path, or (b) an incorrect refund/receive amount (fund loss or unintended inflation) — both are in-scope impacts (loss of funds, transaction/logic manipulation).

### Likelihood Explanation
Likelihood is tied to normal, expected pallet operation rather than an attacker: `update_token` is a routine governance action (fixing a misconfigured contract address, migrating a token deployment, or correcting decimals) documented as a first-class capability of the pallet. Any pending `send()` request whose timeout window overlaps an `update_token` call for the same `(asset_id, chain)` will hit this path. Given that timeouts are commonly set to reasonably long windows to tolerate relayer delay, and migrations are exactly the kind of operational event this pallet is designed to support, the window for collision is realistic and not a contrived edge case.

### Recommendation
Snapshot the contract address and precision used to build each outgoing `Message`/`DispatchPost` (e.g., store them keyed by request commitment, or encode enough information in the request body) so that `on_timeout` and `on_accept` decode/refund using the values in effect at dispatch time rather than re-querying live, mutable storage. Alternatively, `update_token` should refuse to remove/replace a `(chain, asset)` binding while there are still in-flight (undelivered/untimed-out) requests for that pair, or should retain the old contract mapping until all pending requests referencing it have resolved.

### Proof of Concept
1. Register asset `A` for `StateMachine::Evm(X)` with contract `C_old` and decimals `18` via `register_token`.
2. User calls `send()` for asset `A` to `Evm(X)`; pallet burns/locks funds and dispatches a `PostRequest` with `to = C_old` and an ISMP timeout, say, 1 hour out.
3. Governance calls `update_token` with `add_chains = { Evm(X): { token_contract: C_new, decimals: 18 } }` to migrate the token's deployed address (a routine, non-malicious migration). This removes `ContractToAsset[Evm(X)][C_old]` and inserts `ContractToAsset[Evm(X)][C_new] -> A`.
4. The request from step 2 times out; a relayer submits the timeout proof, invoking `on_timeout`, which calls `ContractToAsset::<T>::get(dest=Evm(X), to=C_old)`.
5. Lookup returns `None` (mapping removed in step 3) → `HftError::UnknownContractOnTimeout` is raised → the timeout call fails, and the user's escrowed/burned funds from step 2 can never be refunded through this path.
