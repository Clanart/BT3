### Title
Unbounded recursion in outer-puzzle driver matching (`match_puzzle`) allows an offer counterparty to hang/crash a wallet processing an untrusted offer or spend bundle - (File: chia/wallet/outer_puzzles.py)

### Summary
`match_puzzle()` and the family of `OuterPuzzle.match()`/`get_inner_puzzle()` implementations (CAT, singleton, ownership, metadata, credential-restricted) recurse once per curried "outer layer" found in an attacker-supplied puzzle reveal, with no depth limit. Since puzzle reveals inside an offer file or spend bundle are fully attacker-controlled, a malicious offer/spend bundle can be crafted with an extremely deep chain of nested outer-puzzle layers (e.g. CAT-wrapping-CAT-wrapping-CAT…), causing unbounded Python-level recursion when a wallet parses the offer. This is conceptually analogous to CVE-2006-4112: an externally supplied "dependency resolution" structure (there: Rails route/dependency resolution; here: puzzle outer-layer resolution) is walked recursively without any bound, leading to a hang or crash rather than to CLVM-cost-limited execution.

### Finding Description
`chia/wallet/outer_puzzles.py:49-54` defines:
```python
def match_puzzle(puzzle: UnknownPuzzle) -> PuzzleInfo | None:
    for driver in driver_lookup.values():
        potential_info: PuzzleInfo | None = driver.match(puzzle)
        ...
``` [1](#0-0) 

Each driver's `match()` (e.g. `CATOuterPuzzle.match`, `SingletonOuterPuzzle.match`, `OwnershipOuterPuzzle.match`, `MetadataOuterPuzzle.match`, `CROuterPuzzle.match`) recursively calls `self._match(UnknownPuzzle(known_program=inner_puzzle))`, i.e. `match_puzzle` again, once per curried layer of the puzzle reveal, with no maximum recursion depth check: [2](#0-1) [3](#0-2) [4](#0-3) 

`get_inner_puzzle()` mirrors this recursion structure through `also()` chaining in `PuzzleInfo`: [5](#0-4) 

This recursive matching is exercised directly on untrusted, externally-supplied puzzle reveals when a wallet parses an offer:
- `Offer.from_spend_bundle()` calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` for every coin spend in the bundle (attacker-controlled bytes from an offer file): [6](#0-5) 
- `Offer._get_offered_coins()` similarly calls `match_puzzle`, `get_inner_puzzle`, and `get_inner_solution` per coin spend when computing the offer's contents: [7](#0-6) 

CAT puzzles can trivially be nested (the codebase's own tests construct a CAT wrapping a CAT, `construct_cat_puzzle(CAT_MOD, tail, cat_puzzle)`), demonstrating that arbitrarily deep nesting of outer layers is a valid CLVM/puzzle structure that `match_puzzle` will attempt to fully unwind recursively: [8](#0-7) 

An offer counterparty who crafts an offer file (or a spend bundle presented for evaluation) containing a coin spend whose puzzle reveal is nested hundreds of layers deep can cause `match_puzzle`/`get_inner_puzzle` to recurse until Python's call-stack limit is hit, raising `RecursionError`, or in the worst case causing a C-level stack overflow that crashes the wallet process, when the victim's wallet loads/evaluates the offer (e.g. via `Offer.from_bytes()` and subsequent summary/validity checks reachable from wallet RPC endpoints that accept offer files).

### Impact Explanation
This is a spend-triggered/offer-triggered processing halt reachable by an untrusted offer counterparty or spend-bundle submitter, without needing to compromise any peer or node — matching the "spend-triggered transaction-processing halt" acceptance criterion. A crash or hang of the wallet process denies service to the wallet operator and could interrupt in-flight trades. Because the recursion occurs in pure Python before any CLVM cost accounting applies, it is not bounded by the mempool's CLVM-cost or 2-second validation-duration guards, which only protect the full node's mempool admission path, not wallet-side offer/puzzle parsing.

### Likelihood Explanation
Constructing a deeply nested outer-puzzle CAT/singleton/ownership/metadata/CR chain requires only combining existing puzzle-construction helpers (e.g. `construct_cat_puzzle` called recursively) and does not require any signature or on-chain state — it is a pure puzzle-reveal construction that can be embedded in an offer file and sent to any wallet user or trade counterparty for parsing.

### Recommendation
Add an explicit maximum recursion/layer-depth bound in `match_puzzle`, `get_inner_puzzle`, `get_inner_solution`, and `PuzzleInfo.also()`/`check_type()` traversal, rejecting puzzle reveals or `PuzzleInfo` structures that exceed a sane layer count (e.g., a small constant reflecting all currently supported outer-puzzle stackings) before recursing, and converting the recursive implementations to iterative loops where practical to avoid relying on Python's stack depth as the only safety net.

### Proof of Concept
Not independently executed; the codebase's own test `test_cat_outer_puzzle` (`chia/_tests/wallet/cat_wallet/test_cat_outer_puzzle.py:17-33`) demonstrates that `construct_cat_puzzle(CAT_MOD, tail, cat_puzzle)` can be nested to build a puzzle with N outer layers, and `match_puzzle` will recurse N times to unwind it. Conceptually, an attacker would repeat this nesting (e.g. N≈2000, mixing CAT/singleton/ownership/metadata/CR layers to stay under any single-layer sanity checks) to build a `puzzle_reveal`, embed it in a `CoinSpend` inside an `Offer`/`SpendBundle`, and send the resulting offer file to a victim wallet; calling `Offer.from_bytes()` (which invokes `Offer.from_spend_bundle()` → `match_puzzle`) or requesting an offer summary would then recurse N times and raise `RecursionError` or crash the process.

**Note on verification limits:** I was unable to execute this PoC or trace the exact call chain to the `wallet_rpc_api.py` `get_offer_summary`/`take_offer` RPC handlers due to index/tool constraints — I confirmed `match_puzzle` is invoked directly from `Offer.from_spend_bundle` and `Offer._get_offered_coins`, but did not verify whether any depth limit or exception handling exists further up the RPC stack (e.g., in `wallet_rpc_api.py`) that might convert a `RecursionError` into a graceful RPC error rather than a process crash. A Devin session with full file access would be needed to confirm end-to-end exploitability and the exact crash/hang behavior.

def test_cat_outer_puzzle() -> None:
    ACS = Program.to(1)
    tail = bytes32.zeros
    cat_puzzle: Program = construct_cat_puzzle(CAT_MOD, tail, ACS)
    double_cat_puzzle: Program = construct_cat_puzzle(CAT_MOD, tail, cat_puzzle)
    uncurried_cat_puzzle = UnknownPuzzle(known_program=double_cat_puzzle)
    cat_driver: PuzzleInfo | None = match_puzzle(uncurried_cat_puzzle)

    assert cat_driver is not None
    assert cat_driver.type() == "CAT"
    assert cat_driver["tail"] == tail
    inside_cat_driver: PuzzleInfo | None = cat_driver.also()
    assert inside_cat_driver is not None
    assert inside_cat_driver.type() == "CAT"
    assert inside_cat_driver["tail"] == tail
    assert construct_puzzle(cat_driver, ACS) == double_cat_puzzle
    assert get_inner_puzzle(cat_driver, uncurried_cat_puzzle) == ACS
