### Title
Payout transaction's operator-attribution OP_RETURN is unsigned, allowing an unprivileged party to front-run/replace it and de-attribute an honest operator's payout - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The `payout_tx` that an operator broadcasts to front a user's withdrawal only signs (via `SIGHASH_SINGLE|ANYONECANPAY`) the withdrawal input and the single user-payout output. The OP_RETURN output that attributes the payout to a specific operator (used later to decide who may claim reimbursement) is **not covered by the signature**, so anyone observing the pending transaction can rebuild a variant with the same protected input/output but a different (or missing) OP_RETURN and get it mined first, stripping or forging the payer attribution before the honest operator's kickoff/reimbursement flow runs.

### Finding Description
`create_payout_txhandler` builds the payout transaction with:
- Input 0: the user's withdrawal UTXO, spent via `SpendPath::KeySpend` with the user-supplied `user_sig`.
- Output 0: user payout.
- Output 1: anchor.
- Output 2: OP_RETURN containing `operator_xonly_pk`, the pubkey that will later be credited as the one who "fronted" the peg-out. [1](#0-0) 

The comments on `Withdraw`/`InternalWithdraw` RPCs and the withdrawal-signature parser explicitly document that the user's signature must be `SinglePlusAnyoneCanPay`: [2](#0-1) 

A `SIGHASH_SINGLE | ANYONECANPAY` signature commits only to the single signed input and the output at the *same index* as that input (index 0, the user payout). It does not commit to any other input or output, meaning the anchor (index 1) and, critically, the operator-attribution OP_RETURN (index 2) are entirely unauthenticated by the user's signature.

Downstream, verifiers determine payout attribution purely by reading whatever OP_RETURN ends up in the *confirmed* transaction, with no check that this data was actually signed: [3](#0-2) 

That attribution is then used to decide whether a later kickoff by an operator is legitimate: [4](#0-3) 

If `operator_xonly_pk` is absent or empty in the OP_RETURN, the kickoff is unconditionally treated as malicious ("assuming malicious"), which triggers the challenge path against the actual, honest operator that funded the withdrawal. [5](#0-4) 

**The break in binding:** the protocol assumes `payout_payer_operator_xonly_pk` (as recorded from the confirmed OP_RETURN) == the operator that actually funded/fronted the withdrawal input. Because the OP_RETURN is outside the signature's commitment, an unprivileged third party can observe the pending payout transaction (e.g., in the mempool, or via any interface where the signed `WithdrawParams`/`input_signature` become visible) and rebroadcast a fee-bumped variant that keeps input 0 and output 0 identical (satisfying the signature) but drops/mutates output 2 (the OP_RETURN). If this variant confirms first, the honest operator who genuinely paid the user is no longer attributable in the on-chain data, and their subsequent legitimate kickoff will be classified as malicious and challenged.

### Impact Explanation
This breaks the custody binding of "operator credited versus the party that actually paid": an operator that genuinely fronted a Bitcoin payment to a user can be denied attribution and consequently have their legitimate kickoff treated as malicious/challenged, matching the Critical-tier impact category "an honest operator permanently unable to be reimbursed" (and potentially "an honest operator's collateral burned" if the resulting challenge is not survivable through the disprove path). No operator, verifier, watchtower, or other privileged role is required by the attacker to strip the attribution — only visibility of the pending signed payout data and the ability to broadcast a competing transaction with a higher fee.

### Likelihood Explanation
Exploitability depends on:
1. The attacker being able to observe the payout transaction (or its signature/outpoint) before it confirms — plausible since `WithdrawParamsWithSig` is exchanged over gRPC/aggregator and the transaction itself is broadcast to the mempool by the fronting operator's `TxSender`, which is public information once relayed.
2. The transaction being replaceable (RBF or race-to-confirm) with a fee-bumped variant that preserves only the signed input/output. Given `NON_STANDARD_V3` transaction versioning and use of `TxSender`'s RBF option noted in `operator.rs::withdraw`'s docstring ("Funding the withdrawal transaction using TxSender RBF option"), replacement of the payout transaction is an expected part of normal operation, making a malicious variant technically straightforward to construct and relay.

I was not able to fully verify the exact TapSighashType construction in `core/src/actor.rs` (signing helper) within the available iterations, so the precise mempool/RBF mechanics of a successful front-run should be validated with a live PoC before treating this as fully confirmed.

### Recommendation
Bind the operator-attribution OP_RETURN into the same signature that authorizes spending the withdrawal UTXO — e.g., require `SIGHASH_ALL` (or at minimum `SIGHASH_SINGLE` covering all payout outputs, not just the user-payout one) for the withdrawal-authorizing signature, or otherwise cryptographically commit the claiming operator's pubkey as part of the signed message that verifiers cross-check before recording `payout_payer_operator_xonly_pk`.

### Proof of Concept
1. Operator A prepares and broadcasts `payout_tx` for a withdrawal, with input 0 = user's withdrawal UTXO (SIGHASH_SINGLE|ANYONECANPAY witness) and OP_RETURN = Operator A's xonly pubkey (see `create_payout_txhandler`).
2. Before `payout_tx` confirms, an unprivileged observer of the mempool copies input 0's witness (which only commits to input 0 + output 0) and constructs `payout_tx'`: same input 0, same output 0 (user payout, satisfying SIGHASH_SINGLE), but drops or mutates the OP_RETURN output.
3. The observer relays `payout_tx'` with a higher fee so it is mined instead of Operator A's original transaction.
4. `update_finalized_payouts` (`core/src/verifier.rs:2311-2342`) parses the OP_RETURN from the *confirmed* transaction, finds no valid xonly pubkey, and records `payout_payer_operator_xonly_pk = NULL` for this withdrawal.
5. When Operator A later performs its legitimate kickoff to be reimbursed for this payout, `is_kickoff_malicious` sees `operator_xonly_pk_opt = None` and unconditionally returns `true` ("assuming malicious"), causing verifiers to challenge Operator A's honest kickoff (`core/src/verifier.rs:1875-1885`).

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
