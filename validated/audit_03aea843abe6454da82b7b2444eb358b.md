## Title
Stale Manual Conflict Resolutions Silently Reapplied to Unrelated Conflicts on the Same Path Across a Rebase — ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
During a rebase, Desktop keeps a single `manualResolutions: Map<string, ManualConflictResolution>` keyed only by file **path**, and this map is carried forward unpruned across every commit replayed in the rebase. When `continueRebase` is invoked it blindly re-applies *every* entry still in that map to whatever file currently has that path, without checking that the entry was created for the conflict currently being resolved. A hostile base/target branch (something the attacker fully controls, e.g. the branch being rebased onto, delivered via a normal fetch/clone) can be crafted so the same path conflicts more than once across the rebase sequence with different desired resolutions, causing the user's earlier "ours"/"theirs" choice to be silently reused for a later, unrelated conflict — corrupting what actually gets committed without ever showing the user the second conflict for confirmation.

### Finding Description
`updateConflictState` explicitly preserves the previous `manualResolutions` map for the whole duration of the rebase, as long as the conflict state kind doesn't change:

```ts
// app/src/lib/stores/updates/changes-state.ts
const manualResolutions =
  prevConflictState !== null
    ? prevConflictState.manualResolutions
    : new Map<string, ManualConflictResolution>()

const newConflictState = getConflictState(status, manualResolutions)
``` [1](#0-0) 

`getConflictState` then just threads this same map into the new `rebase` conflict state object every time status is refreshed [2](#0-1) , and `performEffectsForRebaseStateChange` only inspects tip/branch changes to detect an abort — it never prunes stale path entries from `manualResolutions` [3](#0-2) .

When the user resolves the current commit's conflicts and clicks "Continue", `continueRebase` (git layer) iterates the *entire* `manualResolutions` map — not just resolutions relevant to files reported as conflicted in the current step — and stages each one automatically:

```ts
// app/src/lib/git/rebase.ts
for (const [path, resolution] of manualResolutions) {
  const file = files.find(f => f.path === path)
  if (file !== undefined) {
    await stageManualConflictResolution(repository, file, resolution)
  } else {
    log.error(`[continueRebase] couldn't find file ${path} ...`)
  }
}

const otherFiles = trackedFiles.filter(f => !manualResolutions.has(f.path))
await stageFiles(repository, otherFiles)
``` [4](#0-3) 

Because `files` is simply "whatever `git status` currently reports at path X", there is no check that the file object being resolved is *the same conflict instance* the user actually approved. If a later commit in the rebase reintroduces a conflict at the same path (a very common scenario — e.g. a config/lockfile/README that is touched by several commits, or a merge driver file), the previously chosen `ours`/`theirs` decision from an earlier, unrelated conflict is reapplied automatically. The file is excluded from `otherFiles`/normal staging and instead force-resolved with the stale choice — the new conflict is never surfaced to the user at all, because the UI's "unresolved" filtering (`hasUnresolvedConflicts`, `getConflictedFiles` in `app/src/lib/status.ts:151-174`) treats any path present in `manualResolutions` as already resolved, so it is dropped from the conflicts dialog before the user ever sees the second conflict's actual diff.

### Impact Explanation
This breaks the invariant that a user's manual conflict resolution applies only to the specific conflict they reviewed. An attacker who controls the branch/repository being rebased (a normal, unprivileged fetch — no local access, no malware, no leaked credentials required) can craft a rebase where the same file path conflicts twice with semantically opposite resolutions needed. The first (benign-looking, low-risk) conflict trains the user to pick "theirs"; the second (later) conflict on the same path — which may contain attacker-controlled malicious content the user never gets to review or reject — is then silently force-resolved the same way and gets baked into the commit the user pushes. This is a silent corruption of what the user commits (and subsequently pushes), matching the "silent corruption of what the user commits or pushes" impact category, since the user is shown a "Continue" flow with no indication that a second unresolved conflict on that path exists.

### Likelihood Explanation
Likelihood is moderate-to-high for any workflow where users routinely rebase onto branches they don't fully control (upstream branches, PR branches, forks, dependency-bot branches). The attacker only needs push access or influence over the commit history of the branch being rebased onto/from — a completely unprivileged, remote-content-only primitive. No special local access, admin rights, or social engineering beyond "the user rebases on this branch" is required, and rebasing across multiple commits with repeated conflicts is a common, unremarkable real-world scenario, making the trigger conditions plausible rather than contrived.

### Recommendation
Scope `manualResolutions` to the specific conflict instance instead of just the path. When advancing to a new commit's conflicts (i.e. whenever `continueRebase`/`stageFiles` progresses to the next patch and the underlying `REBASE_HEAD`/`orig-head`/patch index changes), clear any manual resolution entries for paths that are no longer part of the currently reported conflicted files, or better: key resolutions by `(path, conflictedBlobHashes)` so a stale resolution can never match a different conflict. `continueRebase` should also refuse to silently auto-apply a resolution for a path unless that path is present in the *current* status's conflicted-file list, rather than blindly trusting whatever remains in the map.

### Proof of Concept
1. Attacker prepares/controls a branch `feature` with two commits: commit A modifies `notes.txt` to contain `X`, commit B (later in the same rebase) modifies `notes.txt` again to contain attacker-controlled payload `Y`.
2. Victim starts a rebase in Desktop of local branch (with conflicting local changes to `notes.txt`) onto `feature`.
3. First conflict (commit A) surfaces on `notes.txt`; user chooses "Theirs" to accept the incoming, benign-looking change. This sets `manualResolutions.set('notes.txt', ManualConflictResolution.theirs)`.
4. User clicks Continue; `continueRebase` applies the resolution and rebase proceeds to commit B, which again conflicts on `notes.txt` (this time introducing payload `Y`).
5. Because `manualResolutions` (per `updateConflictState`) still contains the stale `notes.txt -> theirs` entry from step 3, and `hasUnresolvedConflicts`/`getConflictedFiles` treat this path as already resolved, the conflicts dialog never shows the second conflict to the user.
6. `continueRebase`'s loop over `manualResolutions` re-applies `theirs` to the new conflict on `notes.txt`, silently staging payload `Y` and completing the rebase — the user commits and later pushes content they never reviewed or approved for that specific conflict.

Note: I was unable to fully trace the exact call chain in `app/src/lib/stores/app-store.ts` (`_continueRebase`) within the available context to confirm whether any additional pruning happens between rebase steps at the store layer before calling into `rebase.ts`; based on the `changes-state.ts` and `rebase.ts` code reviewed, no such pruning is evident, but a full audit of `app-store.ts`'s rebase-continuation path would be needed to rule out a mitigating check there.

```typescript
function performEffectsForRebaseStateChange(
  prevConflictState: RebaseConflictState | null,
  newConflictState: RebaseConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
) {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.targetBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.targetBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the rebase must have been aborted
  if (branchNameChanged) {
    statsStore.increment('rebaseAbortedAfterConflictsCount')
    return
  }

  const { currentTip, currentBranch } = status

  // if the repository is no longer conflicted, what do we think happened?
  if (
    prevConflictState != null &&
    newConflictState == null &&
    currentTip != null &&
    currentBranch != null
  ) {
    const previousTip = prevConflictState.originalBranchTip

    const previousTipChanged =
      previousTip !== currentTip &&
      currentBranch === prevConflictState.targetBranch

    if (!previousTipChanged) {
      statsStore.increment('rebaseAbortedAfterConflictsCount')
    }
  }

  return
}
