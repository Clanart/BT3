Based on the investigation, I found a credible analog in GitHub Desktop's git-hooks execution feature, which broadens the blast radius of a git primitive that is inherently attacker-influenced by repository content.

### Title
Untrusted cloned/fetched repositories can trigger execution of attacker-supplied Git hooks with the user's full interactive shell environment injected - (File: app/src/lib/hooks/with-hooks-env.ts)

### Summary
GitHub Desktop intercepts Git hook execution for common operations (commit, pull, merge, push) and, when enabled, loads the user's full interactive shell environment (sourcing `.bashrc`/`.zshrc`/PowerShell profile, etc.) and injects it into whatever hook scripts are discovered in the repository's hooks directory (`core.hooksPath` or `.git/hooks`) before running them [1](#0-0) . Hook discovery reads `core.hooksPath` from repository config and enumerates executable files there [2](#0-1) . `core.hooksPath` is commonly set by tooling shipped inside a repository (e.g. Husky's `.husky` directory, activated by a `postinstall`/`prepare` script the user runs after cloning), so the hook scripts that end up executed can originate entirely from repository content the user does not control.

### Finding Description
The broken invariant mirrors the external report's core primitive: an attacker who controls content that a trusted process later treats as legitimate (there, order-of-insertion in a matching engine; here, hook scripts discovered from repository-relative paths) can get privileged execution folded into the victim's normal workflow, and the victim's existing safeguards don't cover this specific path.

- `getHooksEnvEnabled()` gates the whole feature only on a global boolean, not on any per-repository trust decision [3](#0-2) , and `enableHooksEnvironment` is unconditionally `true` while `enableHooksByDefault` mirrors `enableBetaFeatures` [4](#0-3) . Release notes confirm hooks support was turned on "by default" for the general population, not just beta users [5](#0-4) .
- Every routine Git operation (`commit`, `pull`, `merge`, `push`) explicitly opts into hook interception (`interceptHooks: [...]`) [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) .
- `withHooksEnv` unconditionally copies every discovered hook into a temp proxy directory and re-points `core.hooksPath` at it via `GIT_CONFIG_PARAMETERS`, so any hook the repository has configured will run through Desktop's proxy [10](#0-9) .
- The proxy then spawns the hook with the loaded shell environment merged in, explicitly to satisfy version managers like `nvm`/`rbenv`/`asdf` that export secrets/tokens into shell startup files [11](#0-10) ; the Preferences UI describes this exact intent [12](#0-11) .
- The only existing per-repository trust gate in Desktop is the "dubious ownership" / unsafe-repository warning, which only fires when the repository directory is owned by a different OS user — it says nothing about, and does not gate, hook content that arrives via normal cloning/fetching under the user's own account [13](#0-12) [14](#0-13) . That guard does not stop this path because a normally-cloned repo (owned by the user, no ownership mismatch) with a committed `.husky`/build-tooling directory and a `postinstall` script that sets `core.hooksPath` sails through it untouched.

### Impact Explanation
This maps to the allowed impact category "credential/token exfiltration" and "code execution" from an attacker-controlled cloned/fetched repository. Because Desktop deliberately sources the full interactive shell profile and passes it to hook execution, a repository-supplied hook gets access to secrets a plain `git commit`/`git pull` invoked from a non-interactive context would never see (cloud CLI tokens, API keys, ssh-agent sockets exported in shell rc files), and can exfiltrate them or write arbitrary files on the host during a routine commit/pull/push the user performs inside Desktop.

### Likelihood Explanation
Requires: (1) the user clones/opens a repository whose build tooling sets `core.hooksPath` to a repo-local directory (a widespread, legitimate pattern via Husky/lint-staged, not something requiring "unnatural steps"), and (2) the hooks environment feature enabled (default in current releases per the changelog note). No local/physical access, admin rights, or prior malware is required — the entire chain is driven by attacker-controlled repository content plus ordinary Desktop usage (commit/pull/push).

### Recommendation
Scope the hooks-environment shell-sourcing behavior to repositories the user has explicitly trusted (extending the existing dubious-ownership/"Trust Repository" prompt to also cover `core.hooksPath` pointing inside the working directory), or strip sensitive-looking environment variables before injecting the sourced shell environment into hook execution, and surface a clear one-time warning when a repository's `core.hooksPath` is first observed to point at repository-relative content.

### Proof of Concept
1. Attacker publishes a repository containing a `.husky/pre-commit` (or any hook name) script that reads process environment variables and POSTs them to an attacker server, plus a `package.json` `postinstall`/`prepare` script running `git config core.hooksPath .husky`.
2. Victim clones the repo in GitHub Desktop and runs the project's normal setup command (e.g. `npm install`) once, which sets `core.hooksPath`.
3. Victim performs a normal commit in Desktop. `withHooksEnv` discovers the `pre-commit` hook via `getRepoHooks` [15](#0-14) , loads the victim's full shell environment, and executes the hook with that environment merged in [16](#0-15) , exfiltrating any secrets exported in the victim's shell profile.

**Caveat / uncertainty:** I was not able to fully confirm within available tool budget which release channels currently ship `enableHooksByDefault` as unconditionally `true` versus tied to `enableBetaFeatures()` at present — the changelog entry documents an intent to "enable by default" but I could not cross-check the live value of `enableBetaFeatures()` for stable channel. If hooks interception is in fact still beta-gated for most users, likelihood is reduced accordingly; a Devin session with full repo access could verify this precisely.

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }

  const ext = __WIN32__ ? '.exe' : ''
  const processProxyPath = join(__dirname, `process-proxy${ext}`)

  const token = crypto.randomUUID()
  const tmpHooksDir = await mkdtemp(join(tmpdir(), 'desktop-git-hooks-'))
  const hooksProxy = createHooksProxy(
    cwd =>
      memoizedGetShellEnv(
        getGitHookEnvShell(),
        cwd,
        // We always cache environment per token (i.e. per operation, e.g commit, apply, etc)
        // but we can optionally cache it over multiple operations in the same repository if the user
        // has enabled that setting.
        getCacheHooksEnv() ? 'global' : token
      ),
    tmpHooksDir,
    opts?.onHookProgress,
    opts?.onHookFailure
  )

  const server = createProxyProcessServer(
    conn =>
      hooksProxy(conn).catch(err => {
        log.error(`hooks proxy failed:`, err)
        conn.exit(1).catch(() => {})
      }),
    { validateConnection: async receivedToken => receivedToken === token }
  )
  const port = await new Promise<number>(resolve => {
    server.listen(0, '127.0.0.1', () =>
      resolve((server.address() as AddressInfo).port)
    )
  })
  try {

      await cp(processProxyPath, join(tmpHooksDir, `${hook}${ext}`))
    }

export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }
