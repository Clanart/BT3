### Title
Fee and weight calculation omits the OP_RETURN output, underpaying the requested fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes `needed_fee` as `fee_per_vbyte * vbytes`, where `vbytes` comes from `calculate_weight_vbytes`. However, the OP_RETURN output (which is added to `tx_outs` when `data` is supplied) is never passed to `calculate_weight_vbytes` — the estimate is built only from `payments` and the optional `change` output. The signed transaction therefore carries an output whose weight was not accounted for, so the actual fee rate is lower than `fee_per_vbyte`, and the `MAX_STANDARD_TX_WEIGHT` check underestimates real weight.

### Finding Description
The data output is pushed to `tx_outs` before the size estimation:

- `send.rs:194-202` appends the OP_RETURN `TxOut` to `tx_outs`.
- `send.rs:204` calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — note `payments`, not the final output list, and no `data` argument exists.
- `send.rs:225-226` repeats the omission in the change case.
- `send.rs:206` sets `needed_fee = fee_per_vbyte * vbytes` from the underestimated `vbytes`, and `send.rs:241` checks `weight > MAX_STANDARD_TX_WEIGHT` against the underestimated `weight`.

`calculate_weight_vbytes` (send.rs:62-127) reconstructs a dummy `Transaction` purely from the provided inputs/payments/change; any output in `tx_outs` not represented there is invisible to the estimate. An OP_RETURN output with the maximum 80-byte payload adds roughly 10 bytes of output overhead plus ~82 payload bytes — on the order of 90+ vbytes (~360 weight units) that is never counted.

### Impact Explanation
The signed transaction's real vsize exceeds the estimate, so `actual_fee / actual_vbytes < fee_per_vbyte`. The uncounted OP_RETURN vsize is effectively paid at 0 sat/vbyte. Since `fee()` is `sum(inputs) - sum(outputs)`, the transaction is still internally consistent, but:

- Transactions that include data (e.g., forwards carrying `InInstruction` data, up to 80 bytes per the `TooMuchData` check at send.rs:171) broadcast at a materially lower feerate than the protocol requested — a ~90 vbyte miss on a small transaction can halve the effective rate, risking non-relay or eviction and leaving funds stuck until re-signed at a higher rate.
- The `TooLowFee` guard (send.rs:211) compares `needed_fee` to the minimum relay fee using the underestimated `vbytes`, and the `MAX_STANDARD_TX_WEIGHT` guard (send.rs:241) may accept a transaction that is actually non-standard and will be rejected by relay policy.

### Likelihood Explanation
Any transaction constructed with non-`None` `data` triggers the miscalculation deterministically — the bug is structural, not input-dependent beyond `data` being present. The processor attaches OP_RETURN data when forwarding outputs that carry instruction data, so the path is exercised by ordinary protocol operation whenever an external deposit includes a data payload.

### Recommendation
Pass the full output set — including the OP_RETURN output — into `calculate_weight_vbytes`. Concretely, change the signature to accept the already-built `tx_outs` (or an additional `data: Option<&[u8]>` parameter that pushes the OP_RETURN `TxOut` into the dummy transaction) at send.rs:204 and send.rs:225-226, so `weight`, `vbytes`, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction that will actually be signed.

### Proof of Concept
```rust
// Conceptual: a payment plus max-size data payload
let payments = vec![(some_script_pubkey, 10_000u64)];
let data = vec![0u8; 80];

let stx = SignableTransaction::new(
    inputs, &payments, None, Some(data), fee_per_vbyte,
).unwrap();

// The returned tx has an OP_RETURN output ~90 vbytes that
// calculate_weight_vbytes never saw, so:
assert!(
    stx.fee() as f64 / actual_vsize(&stx.transaction()) as f64
        < fee_per_vbyte as f64
);
// needed_fee() reports a fee sufficient only for the
// data-less transaction.
```

The deviation scales with `data.len()`; at the 80-byte cap the transaction is ~90+ vbytes larger than estimated, and no code path adds that weight back before broadcasting.
