### Title
Lossy UTF-8 decoding of raw diff output silently corrupts partially-staged/committed file content for non-UTF-8 tracked files - ([File: app/src/lib/git/diff.ts])

### Summary
`diffFromRawDiffOutput` unconditionally decodes the raw `git diff --patch-with-raw` buffer as UTF-8, explicitly acknowledging the assumption is not always correct: [1](#0-0) 
This mirrors the seed report's root cause: an interface/parser assumes a single fixed representation for data (`ByteArray` vs `felt252` in Cairo; UTF-8 vs. the file's real byte encoding in Desktop) even though a large class of real-world inputs (pre-`ByteArray` ERC721 contracts; non-UTF-8 tracked source files, which are extremely common — Shift-JIS/GBK/Big5/Windows-1252 encoded files) don't match that assumption.

### Finding Description
Node's `Buffer.toString('utf-8')` is lossy: any byte sequence that isn't valid UTF-8 is silently replaced with the U+FFFD replacement character (3 bytes: `0xEF 0xBF 0xBD`) rather than throwing. Many legacy/non-English source encodings (Shift-JIS, GBK, Big5, Windows-1252/Latin-1) produce high-bit byte sequences that are *not* NUL bytes, so they pass git's own binary-file heuristic and Desktop's `isValidBuffer`/binary checks, and are treated as ordinary text diffs: [2](#0-1) 

The lossily-decoded string is fed straight into `DiffParser.parse`, which splits it into lines and constructs `DiffLine` objects that retain the (already-corrupted) JS string as `line.text`: [3](#0-2) 

When the user performs a partial (line-level) stage or discard — Desktop's core "stage selected lines" feature — `formatPatch`/`formatPatchToDiscardChanges` reconstruct a brand-new unified diff purely from these `line.text` strings: [4](#0-3) 
This reconstructed patch (containing U+FFFD replacement characters in place of the original non-UTF-8 bytes) is piped as `stdin` into `git apply --cached` to update the index: [5](#0-4) 

Because the patch text is generated from a lossy decode-then-reencode round trip, the bytes that actually land in the git index/commit for the affected lines differ from the bytes physically present in the user's working-tree file. The working directory file itself is untouched (so `git status`/`git diff` against disk may look "clean" for context lines the user didn't touch), but the *staged/committed* content for touched hunks has been silently altered — replacement bytes substituted for the file's real (non-UTF-8) byte sequence. This is exactly the "silent corruption of what the user commits or pushes" category: the user visually reviews a diff rendered from the corrupted string, believes they're committing the shown content, but git actually persists different bytes than what's on disk, and the change is neither validated nor rejected anywhere in the pipeline.

### Impact Explanation
Any repository (cloned or fetched, i.e., attacker-influenced content) containing tracked files in a legacy non-UTF-8 encoding — a very common situation for older/internationalized codebases (Japanese/Chinese/Korean/Cyrillic/Latin-1 comments or strings) — will trigger this on any partial-stage or partial-discard operation touching those bytes. The corruption is silent: no error, no warning, the UI shows a diff that looks plausible (albeit with replacement-character glyphs) and the resulting commit/push contains altered file bytes that were never actually written to disk by the user. This can corrupt source files, license/config files, or checksums/keys embedded in non-ASCII-adjacent binary-adjacent text, and it is done without any explicit consent or unnatural steps — it's the natural product of Desktop's ordinary "select lines to stage" workflow, which is a headline feature of the app.

### Likelihood Explanation
No special local access, malware, or credentials are needed — only a repository (which the attacker fully controls, e.g. a malicious/compromised upstream) containing files in any non-UTF-8, non-binary-flagged encoding, combined with the victim doing routine partial staging/discarding of lines in that file via Desktop's changes view. Existing guards (`isValidBuffer`, `isBufferTooLarge`, `isDiffTooLarge`) only bound buffer/line *size*, not *encoding correctness*, so none of them intercept this path. The code comment itself concedes the UTF-8 assumption is known-incomplete ("for now we just assume the diff is UTF-8"), indicating no downstream validation exists to detect or reject a lossy round trip before it's written into the index.

### Recommendation
Do not treat the diff buffer as always UTF-8. Detect decode losses (e.g., compare byte length after round-tripping `Buffer.from(str, 'utf-8')` back against the original buffer, or use a strict decoder that flags invalid sequences) and, when detected, fall back to `DiffType.Unrenderable`/binary-like handling rather than allowing partial line-selection staging on that file. Alternatively, preserve original bytes per-line (not just decoded strings) so `formatPatch`/`formatPatchToDiscardChanges` can reconstruct patches from the untouched raw bytes instead of from a lossily-decoded and re-encoded string.

### Proof of Concept
1. Create a git repo containing a text file encoded in Shift-JIS (or GBK/Windows-1252) with non-ASCII bytes that do not include `0x00` (so git/Desktop won't flag it as binary), e.g. a Japanese comment block.
2. Modify a line adjacent to the non-UTF-8 bytes and open the repo in Desktop; the Changes view will render `diffFromRawDiffOutput`'s lossy decode, showing U+FFFD replacement glyphs in place of the real characters.
3. Select only some of the changed lines for partial staging (Desktop's per-line stage checkboxes) and commit.
4. Inspect the committed blob with `git show <sha>:<path> | xxd` and compare to the original working-tree file bytes at the same offsets — the non-UTF-8 byte sequences in the staged hunk are replaced with `0xEF 0xBF 0xBD` sequences, differing from the original file, confirming silent corruption of the committed content relative to what was actually on disk and what the "diff" nominally represented.

```typescript
export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })
```
