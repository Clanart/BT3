### Title
Unchecked NULL return from `upb_WireReader_ReadTag`/`upb_WireReader_ReadVarint` in `upb_MiniTable_ParseUnknownMessage` - (File: upb/message/promote.c)

### Summary
The Solidity report's invariant — "a function returns an explicit error/sentinel value on malformed input, but the caller does not check it before deriving pointers/sizes and continuing to process" — has a direct structural analog in upb's unknown-field promotion path. `upb_WireReader_ReadTag()` and `upb_WireReader_ReadVarint()` are documented to return `NULL` on malformed varint/tag data [1](#0-0) , exactly like `getBuyInfo()`/`getSellInfo()` signal failure via an explicit error code that the rest of the outputs become meaningless. `upb_MiniTable_ParseUnknownMessage()` calls both functions and immediately uses their (possibly-NULL) return pointer and the un-validated `message_len` to set `data`/`size` without any NULL/error check [2](#0-1) .

### Finding Description
`upb_MiniTable_ParseUnknownMessage` is reached from `upb_Message_GetOrPromoteExtension` and `upb_MiniTable_PromoteUnknownToMessage`/`upb_MiniTable_PromoteUnknownToMessageArray` when re-parsing bytes that were previously stashed as "unknown fields" of a message during an ordinary `upb_Decode()` call [3](#0-2) [4](#0-3) . The `unknown->value.bytes.data` buffer for a `kUpb_MessageUnknownType_StringView` unknown is not itself re-validated at this point — it is the raw wire bytes captured when the outer message was parsed and stored as "unknown" (e.g., because the field's sub-message type was not yet linked). Inside `upb_MiniTable_ParseUnknownMessage`, the code reads the tag and length-varint of that stashed unknown region with `NULL` passed as the `upb_EpsCopyInputStream*` argument — meaning none of the normal buffering/bounds-check machinery in `upb_EpsCopyInputStream_ConsumeBytes` is engaged for these two calls, and the 10-byte lookahead precondition documented for these functions is not being enforced through a stream object. Both reader functions return `NULL` "if there was an error in the tag/varint data" [1](#0-0) , but the caller does not check `ptr` for `NULL` between the two calls or after the second call before doing `data = ptr; size = message_len;` [2](#0-1) . If `ReadTag` fails, `ptr` becomes `NULL` and is then passed unchecked into `ReadVarint`, which dereferences `*ptr` (`uint8_t byte = *ptr;`) as its first act [5](#0-4)  — a NULL-pointer dereference. Even if `ReadTag` succeeds but `ReadVarint` fails (returns `NULL`), `data = ptr` is set to `NULL` and `size = message_len` is used to call `upb_Decode(data, size, ...)` with an invalid/garbage `size` derived from a partially-consumed varint. This mirrors the report's core failure mode: an error signal ("NULL"/error code) from a lower-level parser is silently dropped, and the calling code proceeds to use the resulting invalid pointer/length pair as if it were valid input.

### Impact Explanation
The unknown-field/extension bytes reaching this code originate from the wire input of an ordinary, successfully-decoded `upb_Decode()` call — i.e., attacker-controlled bytes that a client sends through any public parse entry point that ends up calling `upb_Decode`, and are later routed through `upb_Message_GetOrPromoteExtension` (used whenever application code reads an extension that wasn't linked at decode time) or `upb_MiniTable_PromoteUnknownToMessage`/`Array`. A crafted "unknown" byte region whose tag/length varint is truncated or malformed (e.g., all continuation bits set with no terminating byte within the visible slop) can drive `ptr` to `NULL` and then be dereferenced, or drive `size` to an attacker-influenced, non-length-checked value passed to `upb_Decode`. This is a memory-safety violation (NULL deref / use of unvalidated length) reachable purely through supported public parsing APIs with a bounded, attacker-controlled payload, without any privileged access or malicious schema.

### Likelihood Explanation
Reachability requires the message to contain unlinked/unrecognized sub-message or non-canonical-extension fields that get stored as "unknown," and application code that subsequently calls extension-promotion or lazy sub-message-promotion APIs (`upb_Message_GetOrPromoteExtension`, `upb_MiniTable_PromoteUnknownToMessage(Array)`), which are common in the upb runtime for message types whose sub-tables are linked lazily or that use extensions. This is a normal, supported usage pattern for generated code using upb (Ruby/PHP/Python bindings on top of upb use these promotion paths), so the likelihood of the vulnerable code path being exercised in production is high whenever unresolved fields are present.

### Recommendation
Check the return pointer from both `upb_WireReader_ReadTag` and `upb_WireReader_ReadVarint` for `NULL` in `upb_MiniTable_ParseUnknownMessage` before using `ptr`/`message_len`, mirroring how these functions are checked everywhere else in the codebase (e.g., in `_upb_WireReader_SkipValueForceInline`, which does check `if (!ptr || ...)` after `upb_WireReader_ReadSize` [6](#0-5) ). On failure, `ret.status` should be set to `kUpb_UnknownToMessage_ParseError` and the function should return immediately, exactly as it already does for the other error branches in this function [7](#0-6) .

### Proof of Concept
1. Construct a message whose mini-table has an unlinked message-typed field/extension at field number `N`.
2. In the serialized wire bytes for that message, encode the length-delimited field `N` with a tag byte, followed by a length-varint that is truncated (e.g., ends the buffer immediately after a byte with the continuation bit (`0x80`) set, so no terminating byte exists within the captured "unknown" byte range) — this is legal for `upb_Decode()` to stash as an "unknown field" since only the outer message's own bounds are checked at initial decode time, not the internal structure of what becomes unknown data.
3. Call `upb_Decode()` on the outer message (succeeds, storing the malformed inner bytes as an unknown/non-canonical extension).
4. Call `upb_Message_GetOrPromoteExtension()` (or `upb_MiniTable_PromoteUnknownToMessage`) for field `N`, driving execution into `upb_MiniTable_ParseUnknownMessage` [3](#0-2) .
5. `upb_WireReader_ReadVarint(ptr, &message_len, NULL)` returns `NULL` (truncated varint) at line 59, but this is not checked before `data = ptr; size = message_len;` at lines 60–61 [8](#0-7) , and `upb_Decode(data, size, ...)` is invoked with `data == NULL` and an unvalidated `size`.

Note: I was unable to execute this locally (no filesystem/build access in this session); the trace above is based on static reading of the reader/promote source and the documented NULL-on-error contract of `upb_WireReader_ReadTag`/`upb_WireReader_ReadVarint`. A background Devin session with repository/build access would be needed to compile a concrete minitable and unknown-field byte sequence and confirm the crash empirically.
