### Title
Silent exception swallowing in `Offer.__post_init__` masks CoinSpend hint/addition computation failures - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.__post_init__` in `chia/wallet/trading/offer.py` computes, for every `CoinSpend` in the offer's spend bundle, the set of created coins and their memos/hints via `compute_spend_hints_and_additions`. Any failure other than `ValidationError` or the specific "cost exceeded" `ValueError` is caught with a bare `except Exception: continue`, silently discarding the failure with no logging and no propagation, exactly analogous to the reported `console.error`-suppressed `call` helper.

### Finding Description
In the `__post_init__` cache-population loop:
```
chia/wallet/trading/offer.py:166-181
for cs in self._bundle.coin_spends:
    assert cs.coin not in adds
    try:
        hinted_coins, cost = compute_spend_hints_and_additions(cs, max_cost=max_cost)
        ...
    except ValidationError:
        raise
    except ValueError as e:
        if e.args and e.args[0] == "cost exceeded or below zero":
            raise ValidationError(...) from e
        continue
    except Exception:
        continue
```
`compute_spend_hints_and_additions` (`chia/wallet/util/compute_hints.py:23-66`) runs the coin's puzzle reveal with `run_with_cost` and parses `CREATE_COIN` conditions to build a per-coin map of created coins and hints. Any CLVM execution error, malformed condition, or unexpected exception from a crafted/adversarial `puzzle_reveal`/`solution` inside an `Offer` object is swallowed with `except Exception: continue` — no `log.warning`/`log.exception` call is made, and the loop simply proceeds to the next coin spend as if that spend contributed nothing. This mirrors the reported bug: an error condition is detected (an exception is raised) but is neither captured, logged, nor surfaced to the caller.

The resulting `_additions`/`_hints` caches are used pervasively by the class: `additions()` (`offer.py:224-225`), `fees()` (`offer.py:230-234`, whose docstring itself concedes "Unsafe to use for fees validation!!!"), `hints()` (`offer.py:221-222`), and `_get_offered_coins()` (`offer.py:244-260`), which is used to derive the amounts actually being offered in a trade. Because the failure path is invisible, a coin spend whose true `CREATE_COIN` outputs cannot be computed (due to a crafted puzzle that trips an unexpected exception) is treated as producing zero additions/hints instead of causing the offer to be rejected or flagged, and no diagnostic trail exists for a wallet operator to determine why an offer's advertised amounts don't match its actual on-chain effect.

### Impact Explanation
This is a Medium-severity trust/data-integrity issue reachable by any offer counterparty: a malicious offer-maker can craft an `Offer` containing a coin spend whose puzzle triggers an exception during hint/addition computation (rather than a clean `ValueError`/`ValidationError`), causing that spend's real created coins to be excluded from `_additions`/`_hints` without any error signal. Since `_get_offered_coins()` indexes `self._additions[parent_spend.coin]` per spend, this can also silently corrupt or crash the offer's fee/amount summary path used by the receiving wallet to evaluate trade terms, and because the failure is invisible in logs, victims and developers have no way to detect that the accounting is degraded — undermining confidence in offer settlement correctness for a system that already flags `fees()` as "unsafe."

### Likelihood Explanation
Medium likelihood: it requires an attacker to construct a coin spend whose puzzle reveal raises a non-`ValueError`/non-`ValidationError` exception during CLVM execution or condition parsing in `compute_spend_hints_and_additions` — plausible via malformed/edge-case CLVM (e.g., unexpected atom shapes hitting `condition.at(...)` failures) inside an offer file shared with a counterparty. It does not require special privileges, only the ability to author an offer file.

### Recommendation
**Short term:** Replace `except Exception: continue` with explicit logging (e.g., `log.warning`/`log.exception`) capturing the coin id and exception details before continuing, so failures are diagnosable, and audit whether such failures should instead raise `ValidationError` to reject the malformed offer outright rather than silently omitting data.

**Long term:** Avoid broad `except Exception` blocks in security-relevant paths like offer parsing; enumerate and handle only the specific exceptions expected from `run_with_cost`/CLVM evaluation, and ensure any coin spend that cannot be fully accounted for causes the `Offer` to be treated as invalid rather than partially/incorrectly summarized.

### Proof of Concept
Not independently exploited in this analysis; the finding is based on static code review of `chia/wallet/trading/offer.py:150-186` and `chia/wallet/util/compute_hints.py:23-66`, tracing how a swallowed exception from a crafted coin spend's puzzle reveal propagates into `_additions`/`_hints` and downstream consumers (`additions()`, `fees()`, `_get_offered_coins()`). Constructing a concrete puzzle/solution pair that triggers the generic `except Exception` branch (as opposed to the already-handled `ValueError`/`ValidationError` cases) would require further CLVM-level engineering not verified here.
```python
def compute_spend_hints_and_additions(
    cs: CoinSpend,
    *,
    max_cost: int = DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM,
) -> tuple[dict[bytes32, HintedCoin], int]:
    cost, result_program = run_with_cost(cs.puzzle_reveal, max_cost, cs.solution)

    hinted_coins: dict[bytes32, HintedCoin] = {}
    for condition in result_program.as_iter():
        if cost > max_cost:
            raise ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, "compute_spend_hints_and_additions() for CoinSpend")
        atoms = condition.as_iter()
        op = next(atoms).atom
        if op in {
            ConditionOpcode.AGG_SIG_PARENT,
            ConditionOpcode.AGG_SIG_PUZZLE,
            ConditionOpcode.AGG_SIG_AMOUNT,
            ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT,
            ConditionOpcode.AGG_SIG_PARENT_AMOUNT,
            ConditionOpcode.AGG_SIG_PARENT_PUZZLE,
            ConditionOpcode.AGG_SIG_UNSAFE,
            ConditionOpcode.AGG_SIG_ME,
        }:
            cost += ConditionCost.AGG_SIG.value
            continue
        if op != ConditionOpcode.CREATE_COIN.value:
            continue
        cost += ConditionCost.CREATE_COIN.value

        rf = condition.at("rf").atom
        assert rf is not None

        coin: Coin = Coin(cs.coin.name(), bytes32(rf), uint64(condition.at("rrf").as_int()))
        hint: bytes32 | None = None
        if (
            condition.at("rrr") != Program.NIL  # There's more than two arguments
            and condition.at("rrrf").atom is None  # The 3rd argument is a cons
        ):
            potential_hint: bytes | None = condition.at("rrrff").atom
            if potential_hint is not None and len(potential_hint) == 32:
                hint = bytes32(potential_hint)
        hinted_coins[bytes32(coin.name())] = HintedCoin(coin, hint)

    return hinted_coins, cost
```
