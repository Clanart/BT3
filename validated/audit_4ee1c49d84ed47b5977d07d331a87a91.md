### Title
Re-enabling `protocol.file.allow=always` for submodule updates lets an attacker-controlled `.gitmodules` clone arbitrary local Git repositories into the working tree - (File: `app/src/lib/git/submodule.ts`)

### Summary
`checkoutBranch` and `checkoutCommit` accept an `allowFileProtocol` flag which, when `true`, is forwarded to `updateSubmodulesAfterOperation`, which then runs `git -c protocol.file.allow=always submodule update --init --recursive` [1](#0-0) [2](#0-1) . This explicitly overrides Git's own hardened default (`protocol.file.allow=user`), which was introduced upstream specifically to stop repositories from using submodule URLs with the `file://` scheme to have Git clone arbitrary local paths without the user's intent.

### Finding Description
`.gitmodules` content is fully attacker-controlled: it comes from whatever branch/commit/PR is being checked out, i.e. from a cloned/fetched repository or a fork supplying a pull request. `listSubmodules`/`resetSubmodulePaths`/`updateSubmodulesAfterOperation` operate directly on `.gitmodules` and submodule URLs without validating the scheme [3](#0-2) . When Desktop invokes checkout with `allowFileProtocol=true`, it re-enables the `file://` protocol for submodule clones for that operation, meaning a malicious `.gitmodules` entry such as `url = file:///Users/victim/some-other-local-repo` (or a Windows UNC/drive-letter equivalent) will cause Git itself — not Desktop — to `git clone` that local path into the submodule directory inside the currently open repository, without any additional prompt from Desktop.

The corrupted value is the working tree/submodule directory of the repository the user thinks they are safely checking out: instead of content from the remote the user intended, it can be populated with the full contents of an unrelated local Git repository the attacker has no business accessing (e.g., another private project checked out elsewhere on the same machine). This is precisely the "attacker controls a fetched/cloned repository, result is silent corruption of what the user commits" class described in the report's broken invariant (unconstrained value from an untrusted source flows into a security-relevant operation without a user-controlled bound/check).

### Impact Explanation
If exploited, an attacker can exfiltrate the contents of another local Git repository (potentially containing secrets, credentials, or proprietary code) into the victim's working directory, where the victim may then inspect, commit, and push it — an unintended and silent disclosure/corruption path. This maps to the "silent corruption of what the user commits or pushes" and "file read outside the repo" impact categories in the task's valid-impact list.

### Likelihood Explanation
Likelihood depends entirely on which call sites pass `allowFileProtocol=true`. I found the parameter plumbed all the way through `checkoutBranch`/`checkoutCommit` → `updateSubmodulesAfterOperation`, and test fixtures (`app/test/unit/git/checkout-test.ts`) exercise the `allowFileProtocol=true` path for "initializes an uninitialized submodule when checking out a branch" [4](#0-3) , confirming the flag is a real, reachable feature and not dead code. I was unable to conclusively enumerate every production call site (e.g., pull-request checkout, `_checkoutPullRequest`) that supplies `true` versus the default `false` before running out of iterations, so the exact trigger conditions (does it fire on every PR/branch checkout with submodules, or only in specific flows) remain unverified and should be confirmed by a follow-up code review.

### Recommendation
- Do not blanket-enable `protocol.file.allow=always` for submodule updates triggered by content from untrusted/remote branches or PRs.
- Validate/allowlist submodule URL schemes (reject `file://`, `ext::`, and other non-network schemes) before running `git submodule update` on attacker-supplied `.gitmodules`.
- If `file://` submodules must be supported for legitimate local-development workflows, scope the allowance narrowly (e.g., only for repositories the user explicitly added via local path, never for cloned/fetched/forked content) and require explicit user confirmation.

### Proof of Concept
1. Attacker publishes a repository (or opens a PR against a repo the victim will check out) whose `.gitmodules` contains a submodule with `url = file:///absolute/path/to/another/local/repo/on/victim/machine` (or a path guessable/common on the target, e.g. a path under the user's home directory used by other tools).
2. Victim, using GitHub Desktop, opens/clones this repository or checks out the branch/PR (a normal action).
3. If the checkout path uses `allowFileProtocol=true`, `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, which clones the referenced local repository directly into the submodule path inside the victim's now-active working directory [5](#0-4) .
4. The victim may then stage/commit/push this unintended content, or the attacker gains disclosure indirectly (e.g., if the victim later shares the repo).

Note: full confirmation requires enumerating the exact production call sites that set `allowFileProtocol=true` (e.g., PR checkout flow in `app-store.ts`/`dispatcher.ts`) — this was not completed due to tool-call limits and should be verified in a follow-up pass.

export async function listSubmodules(
  repository: Repository
): Promise<ReadonlyArray<SubmoduleEntry>> {
  const [submodulesFile, submodulesDir] = await Promise.all([
    pathExists(join(repository.path, '.gitmodules')),
    pathExists(join(repository.path, '.git', 'modules')),
  ])

  if (!submodulesFile && !submodulesDir) {
    // repo path + .gitmodules and + .git/modules covers the vast majority of
    // "normal" repositories but if we're in a linked worktree the modules
    // directory is actually in the git common dir so we'll also check for the
    // existence of the modules directory there as well before giving up on the
    // existence of submodules in this repo. We're reading the commondir file
    // ourselves here instead of calling out to git to avoid the cost of
    // spawning a process on Windows
    const commonDirPath = join(repository.resolvedGitDir, 'commondir')
    const commonDir = await readFile(commonDirPath, 'utf8')
      .then(content => content.replace(/\r?\n$/, ''))
      .then(p => (p ? resolve(repository.resolvedGitDir, p) : null))
      .catch(() => null)

    if (!commonDir || !(await pathExists(join(commonDir, 'modules')))) {
      log.info('No submodules found. Skipping "git submodule status"')
      return []
    }
  }

  // We don't recurse when listing submodules here because we don't have a good
  // story about managing these currently. So for now we're only listing
  // changes to the top-level submodules to be consistent with `git status`
  const { stdout, exitCode } = await git(
    ['submodule', 'status', '--'],
    repository.path,
    'listSubmodules',
    { successExitCodes: new Set([0, 128]) }
  )

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
