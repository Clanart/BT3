## Verdict: Valid finding (path traversal, information disclosure / arbitrary file open)

### Title
Path traversal via unsanitized `CommittedFileChange.path` in PR "Files Changed" view allows opening/reading files outside the repository - (File: `app/src/ui/open-pull-request/pull-request-files-changed.tsx`)

### Summary
`PullRequestFilesChanged` builds file-system paths from `CommittedFileChange.path`, which is populated from the diff of an attacker-controlled fork's pull request fetched via the GitHub API. The path is joined to `repository.path` with plain `Path.join`/`Path.normalize`, with no containment check, unlike the codebase's own `resolveWithin` helper that exists precisely to prevent this class of bug.

### Finding Description
`onOpenFile` computes the full path with a raw `Path.join`: [1](#0-0) 

The context menu handler `onFileContextMenu` performs the same unsafe join and only gates enablement on `pathExists`, not on containment within the repository: [2](#0-1) 

If `file.path` is `../../secrets.txt` (or any other value containing `..` segments), `Path.join(repository.path, file.path)` normalizes to a location outside `repository.path`. `pathExists(fullPath)` then simply checks whether that arbitrary filesystem path exists on the reviewer's disk — it performs no verification that the resolved path is still inside the repository. If it exists, the "Open with Default Program" (`onOpenFile` → `openFile`), "Open in \<editor\>", and "Reveal in File Manager" menu items become `enabled: true` and act on `fullPath`, which lies outside the cloned repository directory.

This is a real gap: the codebase already has a purpose-built defense, `resolveWithin`/`resolveWithinPosix` in `app/src/lib/path.ts`, which resolves a path against a root and returns `null` if the resolved path (post-symlink-resolution via `realpath`) escapes the root: [3](#0-2) 

That helper is used elsewhere (e.g., `buildConflictContext` in `app/src/lib/copilot-conflict-context.ts`) specifically to guard against "path traversal and symlink escapes" when handling repository-relative paths from external/generated sources: [4](#0-3) 

`PullRequestFilesChanged`, `SelectedCommits`, and `FilterChangesList` do not use `resolveWithin` and instead rely on unguarded `Path.join` + `pathExists`, making the PR-diff file list (driven by remote, attacker-controlled fork data) the most exposed instance of this pattern since the `path` values there originate directly from a third-party pull request's diff rather than from local git status.

### Impact Explanation
An attacker who opens a pull request against the victim's repository (no write access needed, any fork PR qualifies) can craft a diff entry whose file path contains `../` segments. If the resulting path happens to point to a file that exists on the reviewer's machine, the reviewer, upon inspecting "Files Changed" and choosing "Open with Default Program" / "Open in \<editor\>" from the context menu, will have that out-of-repository file opened — disclosing its existence and, via the default program, its contents. `isSafeFileExtension` gates only the "Open with Default Program" item (not editor-open or reveal-in-file-manager), so paths whose extension is on the "safe" allowlist (e.g., `.txt`, `.md`, images) can be silently opened, potentially exposing sensitive files if their names/locations relative to the clone can be guessed (e.g., sibling directories, dotfiles, common config files).

### Likelihood Explanation
Exploitation requires: (1) the victim to have a repository cloned with a predictable/guessable relative layout, (2) a file that exists at the traversal target, and (3) the reviewer to manually right-click and choose "Open with Default Program" (or similarly gated actions) on the crafted entry. This needs user interaction and some environment-dependent path guessing, so likelihood is moderate rather than high, but it is a genuine unprompted-but-natural reviewer workflow (reviewing PR diffs is core desktop functionality), and no existing check in this code path blocks the traversal — `pathExists` is not a containment check.

### Recommendation
Use `resolveWithin`/`resolveWithinPosix` (already implemented in `app/src/lib/path.ts`) in `onOpenFile` and `onFileContextMenu` of `pull-request-files-changed.tsx` (and similarly in `selected-commits.tsx` / `filter-changes-list.tsx`) to resolve `file.path` against `repository.path`, and treat a `null` result (path escapes the repo) the same as "file does not exist" — disabling all related menu actions.

### Proof of Concept
1. Mock the pull-request "Files Changed" API response so it includes a `CommittedFileChange` with `path: '../../secrets.txt'`.
2. Render `PullRequestFilesChanged` with a `repository.path` such as `/Users/victim/repos/myrepo`.
3. Right-click the file row to trigger `onFileContextMenu`; observe `fullPath = Path.join('/Users/victim/repos/myrepo', '../../secrets.txt')` resolves to `/Users/victim/secrets.txt`, outside the repo.
4. If `/Users/victim/secrets.txt` exists, the context menu enables "Open with Default Program"; selecting it calls `onOpenFile('../../secrets.txt')` → `Path.join(repository.path, path)` → `openFile(fullPath, dispatcher)`, opening the out-of-repo file.
5. Compare against `resolveWithin(repository.path, file.path)` (from `app/src/lib/path.ts`), which would return `null` for this input, demonstrating the missing containment check is the root cause.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
