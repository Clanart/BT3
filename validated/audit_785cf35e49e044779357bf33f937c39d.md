### Title
Remote denial of service via HashMap-index panic on unregistered participant in PedPoP decryption/blame path - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The DKG encryption layer indexes `enc_keys` with a `Participant` index using `HashMap`'s `[]` operator, which panics when the key is absent. A participant index that was never registered (e.g., one supplied inside attacker-influenced blame/decryption data, or a participant who withheld their `EncryptionKeyMessage`) causes a node crash — the same remotely-triggered availability-impact class as CVE-2023-22104 (unauthorized hang/repeatable crash of a network-facing service).

### Finding Description
`Decryption::decrypt_with_proof` looks up the decryptor's encryption key with `self.enc_keys[&decryptor]`:

```rust
// crypto/dkg/pedpop/src/encryption.rs:381-390
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],
  )
``` [1](#0-0) 

`enc_keys` is populated only by `Decryption::register`, called once per participant that actually sent an `EncryptionKeyMessage` (which is parsed from untrusted bytes via `EncryptionKeyMessage::read`). [2](#0-1) [3](#0-2)  If a blame/accusation flow references a `decryptor` participant that never registered — an index derivable from attacker-sent data, since `Participant` is a plain `u16` — the indexing panics instead of returning a `DecryptionError`. The same unchecked indexing pattern exists at `Encryption::encrypt`, where `self.decryption.enc_keys[&participant]` panics if the target participant never registered a key. [4](#0-3) 

The code's own convention treats all other failure modes in this function as recoverable `Result` errors (`InvalidSignature`, `InvalidProof`), so the panic is an unhandled edge rather than an intentional abort. [5](#0-4) 

### Impact Explanation
A panic in these paths crashes the calling thread/process. In a validator/processor context running the PedPoP DKG and its blame machinery over the network, one crafted protocol message (referencing an unregistered participant index during share verification/blame) produces a repeatable, remotely-triggered crash — a complete denial of service for that node, matching the Medium availability-impact severity class of the source CVE. No keys or shares are leaked; the impact is purely availability, analogous to the CVE's `A:H`-only vector.

### Likelihood Explanation
Reachable by an unprivileged protocol participant: `EncryptedMessage::read`, `EncryptionKeyMessage::read`, `EncryptionKeyProof::read`, and participant indexes all originate from wire bytes and attacker messages. The attacker does not need a valid share or key — they only need the blame/decryption path to be evaluated with a `decryptor`/`participant` index absent from `enc_keys`. The panic requires no collusion, no leaked secrets, and no malformed curve encodings. Whether a specific deployment surfaces this depends on whether its driver pre-validates that every referenced participant registered; the library itself does not enforce it. Because it hinges on driver behavior for which callers are in scope but the indexing itself is unconditionally unguarded in the library, this rates Medium rather than High.

### Recommendation
Replace `HashMap` indexing with fallible lookups:

```rust
let enc_key = self
  .enc_keys
  .get(&decryptor)
  .ok_or(DecryptionError::InvalidProof)?;
```

and use `*enc_key` in the DLEq `points` slice. Apply the same fix in `Encryption::encrypt` (`self.decryption.enc_keys.get(&participant)`), returning a protocol error instead of panicking. Additionally, the `assert!(!self.enc_keys.contains_key(&participant))` in `Decryption::register` should return an error rather than panic on duplicate registration. [6](#0-5) 

### Proof of Concept
```rust
// Attacker participates in (or observes) a PedPoP DKG session but
// arranges for the blame/decryption path to be evaluated with a
// decryptor Participant index that never sent an EncryptionKeyMessage.
// Build a syntactically valid EncryptedMessage (any key/pop/msg that
// passes Schnorr PoP verification — attacker can sign their own key):

let key = Zeroizing::new(C::random_nonzero_F(rng));
let pub_key = C::generator() * key.deref();
let pop = SchnorrSignature::sign(&key, nonce, pop_challenge(...)); // passes
let msg = EncryptedMessage { key: pub_key, pop, msg: ciphertext };

// Provide an EncryptionKeyProof whose DLEq references decryptor = P,
// where P's index is valid (<= n) but P never registered enc_keys.
// decrypt_with_proof(from, P, msg, Some(proof)) reaches:
//   &[self.enc_keys[&P], *proof.key]
// HashMap index on missing key -> panic!("key not found") -> crash.
```

Note: I verified the panic sites and the read-path reachability of the attacker-controlled messages/participant indexes, but could not fully trace the PedPoP driver (`crypto/dkg/pedpop/src/lib.rs`) call sites that pass `decryptor`/`participant` into these functions before the iteration limit; if the driver strictly guarantees only registered indexes, this reduces to a latent library footgun rather than a live DoS.
