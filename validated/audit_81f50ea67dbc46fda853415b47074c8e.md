### Title
Infinite loop in `Offer.get_root_removal()` via a crafted cyclic coin-removal graph in an untrusted offer - ([File: chia/wallet/trading/offer.py])

### Summary
CVE-2018-7333 is an infinite loop in Wireshark's RPC-RDMA dissector caused by not validating a size/chunk field, so the parser never makes forward progress and spins forever on attacker-controlled input. The analogous pattern in `chia-blockchain` exists in `Offer.get_root_removal()`, which walks a coin's ancestry chain using `Coin.parent_coin_info` links taken directly from an untrusted offer file, without validating that the chain is acyclic.

### Finding Description
`Offer.get_root_removal()` walks "up" the parent chain of a coin until it finds a non-ephemeral removal: [1](#0-0) 

`non_ephemeral_removals` is computed purely from the removal set's `parent_coin_info`/`name()` fields: [2](#0-1) 

`Coin` is a plain dataclass; `parent_coin_info`, `puzzle_hash`, and `amount` are attacker-controlled values embedded in the `CoinSpend`s of an offer file (`self._bundle.coin_spends`). Nothing in `Offer` (or in `SpendBundle`/`WalletSpendBundle` construction) requires that the parent-coin graph formed by these removals be acyclic before this method runs — that validation only happens later, on-chain, when parent coins are looked up in the actual coin store. An attacker can build an offer with two (or more) removal coins A and B where `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()`. By construction, neither A nor B qualifies as "non-ephemeral" (each one's parent is present in the removal set), so the `while coin not in non_ephemeral_removals` loop in `get_root_removal` never terminates — it bounces between A and B forever, exactly like the RPC-RDMA dissector spinning on a chunk whose size never lets the cursor advance.

`get_root_removal` is called from `get_pending_amounts()` and `get_primary_coins()`, which in turn feed `get_cancellation_coins()`: [3](#0-2) [4](#0-3) 

These are exactly the routines a wallet invokes when a user opens/imports/inspects an offer file before deciding to accept it (pending-amount summaries, cancellation-coin computation for the trade manager). They run on the wallet client, driven entirely by the bytes of an offer file supplied by an untrusted counterparty, before any chain validation of the coin graph occurs.

### Impact Explanation
A malicious offer counterparty can craft an offer file that, when opened or summarized by a victim's wallet (GUI or CLI `chia wallet ... offers` flow, or RPC calls that surface pending-amount/cancellation info), causes the wallet process to hang in an unbounded busy loop. This is a spend/offer-triggered denial of service against the wallet: the process becomes unresponsive (single-threaded Python event loop blocked), preventing the wallet from processing other requests, syncing, or handling other trades until it is killed and restarted. This matches the "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
Likelihood is high for any wallet user who opens offer files from arbitrary/untrusted sources (a normal Chia trading workflow — offer files are routinely shared out-of-band). Constructing the cyclic removal graph requires no cryptography or hash collision: `Coin.parent_coin_info` is just an unvalidated struct field supplied by the offer creator, so producing two coins whose `parent_coin_info` values point at each other's `name()` is trivial and deterministic.

### Recommendation
Add cycle detection (e.g., a visited-set bound by the length of `all_removals`, or a maximum iteration count equal to `len(all_removals)`) in `Offer.get_root_removal()` before dereferencing `coin.parent_coin_info` further, and raise a `ValueError`/reject the offer as malformed if no non-ephemeral ancestor is found within that bound. Apply the same bounding to the dependency-resolution loop in `get_cancellation_coins()`, since it performs similar unbounded graph traversal over attacker-supplied announcement/dependency data.

### Proof of Concept
1. Construct two `CoinSpend`s for coins A and B where `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()` (trivial: these are independent struct fields, not required to match any real chain state for an off-chain offer object).
2. Include both as removals in an `Offer`/`WalletSpendBundle`, with an offered asset routed so that `get_offered_coins()` includes a coin descending from A or B.
3. Serialize this as a standard offer file (bech32m-encoded offer bytes) and send it to a victim.
4. When the victim's wallet calls `offer.get_pending_amounts()`, `offer.get_primary_coins()`, or `offer.get_cancellation_coins()` (as happens when displaying an offer summary or evaluating cancellation coins before accept), `get_root_removal()` enters the A↔B cycle and loops forever, hanging the wallet.     # This returns the non-ephemeral removal that is an ancestor of the specified coin
```python
    # This should maybe move to the SpendBundle object at some point
    def get_root_removal(self, coin: Coin) -> Coin:
        all_removals: set[Coin] = set(self.removals())
        all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
        non_ephemeral_removals: set[Coin] = {
            c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
        }
        if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
            raise ValueError("The specified coin is not a coin in this bundle")

        while coin not in non_ephemeral_removals:
            coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

        return coin
```
