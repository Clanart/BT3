### Title
`WombatStaking.depositLP` mints receipt tokens based on the input amount instead of the actual LP tokens received, causing accounting mismatch for fee-on-transfer LP tokens - (File: `wombat/WombatStaking.sol`)

### Summary
`WombatStaking.depositLP()` transfers the Wombat LP token from the caller via `safeTransferFrom` and then mints the pool's `receiptToken` using the caller-supplied `_lpAmount` parameter directly, rather than measuring the actual token amount received by the contract. This is the same root-cause pattern as the referenced Sherlock finding on Knox's `Queue.sol`, where trusting the nominal transfer amount instead of the balance delta causes over-minting of accounting tokens whenever the underlying token deducts a fee on transfer.

### Finding Description
In `depositLP`, the LP tokens are pulled from the user and immediately used to mint receipt tokens 1:1 with the requested `_lpAmount`, without verifying that this amount was actually received: [1](#0-0) 

```solidity
function depositLP(
    address _lpAddress,
    uint256 _lpAmount,
    address _for
) nonReentrant whenNotPaused _onlyActivePoolHelper(_lpAddress) external {
    Pool storage poolInfo = pools[_lpAddress];

    // Transfer lp to this contract and stake it to wombat
    IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount);

    _toMasterWomAndSendReward(_lpAddress, _lpAmount, true); // triggers harvest from wombat exchange
    IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount);

    emit NewLPDeposit(_for, poolInfo.lpAddress, _lpAmount, poolInfo.receiptToken, _lpAmount);
}
```

This is inconsistent with the rest of the codebase, which correctly guards against this exact issue elsewhere by comparing balances before/after a transfer or deposit call, e.g. in `deposit()` (measuring `lpReceived` via balance diff before minting) and in the pool helpers' `depositLP` wrappers, which measure `afterDeposit - beforeDeposit` on the staking/receipt token balance: [2](#0-1) [3](#0-2) 

If `poolInfo.lpAddress` were ever configured to point at (or the LP asset itself behaved as) a deflationary/fee-on-transfer token, `depositLP` would mint more `receiptToken` than the actual LP backing it, since `_toMasterWomAndSendReward` and the `mint` call both use the untrusted `_lpAmount` rather than the amount actually received.

### Impact Explanation
If the receipt token accounting is inflated relative to actual LP custody, later withdrawals/unstaking by other legitimate depositors of the same pool could fail or be under-collateralized once the shortfall is discovered, since `withdraw()`/`burnReceiptToken()` assume receipt tokens are fully backed by real LP holdings in the contract. This matches the "protocol insolvency / permanent freezing of funds" impact category, mirroring the original Knox finding's outcome, where the accounting unit no longer matches physically-held funds.

### Likelihood Explanation
The likelihood is contingent on `poolInfo.lpAddress` being (or acting like) a fee-on-transfer token, which is admin-configured for whitelisted pools rather than freely chosen by an ordinary user in the current pool set. This limits real-world likelihood to whichever LP tokens are actually onboarded, but the code path itself is directly reachable by any unprivileged pool helper acting on behalf of a normal user, and the missing balance-diff check is a genuine logic flaw independent of whether it is exploited today.

### Recommendation
Mirror the pattern already used in `deposit()`: record the receipt-token-backing balance of the LP token before `safeTransferFrom`, and use the post-transfer balance delta as the amount to forward to `_toMasterWomAndSendReward` and to mint as `receiptToken`, instead of trusting the caller-provided `_lpAmount`.

### Proof of Concept
1. Assume `poolInfo.lpAddress` is (or becomes) a fee-on-transfer ERC20 with e.g. a 2% transfer fee.
2. A pool helper calls `WombatStaking.depositLP(_lpAddress, 100e18, user)` on behalf of `user`, who approved 100e18 LP tokens.
3. `safeTransferFrom` moves only 98e18 LP tokens into `WombatStaking` due to the fee, but `receiptToken.mint(msg.sender, 100e18)` mints receipt tokens for the full 100e18.
4. The pool now has a 2e18 shortfall between minted `receiptToken` supply and actual LP tokens custodied, which will surface as insufficient funds for other users to withdraw against their receipt tokens.
