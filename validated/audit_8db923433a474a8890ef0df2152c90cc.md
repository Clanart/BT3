### Title
Future/skewed oracle publish-time permanently freezes a feed's price via the monotonic-timestamp gate - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` clamps the staleness delta to `u0` whenever the reported feed timestamp `ts` is greater than `stacks-block-time`, and simultaneously the same `ts` is written as the new monotonic floor for the feed (`last-update`). Because the "future timestamp" is never rejected, it is accepted as fresh and becomes the new floor that all subsequent legitimate updates must meet or exceed, permanently blocking future correctly-timed price updates for that feed.

### Finding Description
`price-resolve` gates every price with: [1](#0-0) 
```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```
When `ts > stacks-block-time` (the feed's publish-time is ahead of the Stacks chain's block-time clock — a plausible, non-malicious occurrence given Pyth/DIA publish timestamps are independent of the Stacks block clock, e.g. clock skew or a burst of Stacks blocks lagging real time), `delta` is forced to `u0`, so the freshness check `(<= delta max-staleness)` always passes regardless of how far in the future `ts` is.

Immediately after, in `price-resolve`: [2](#0-1) 
```
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  ...
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```
The accepted future `timestamp` is stored as the feed's new `last-update` floor. On the very next legitimate update — with a correct, present-time `ts'` that is necessarily `< ts` (the poisoned future value) — the monotonic check `(>= ts' prev)` in `oracle-timestamp-fresh` fails, because `prev` is now set to a timestamp that lies in the future relative to real, correctly-timed subsequent publishes. Every call to `price-resolve` (and therefore `price-multi-resolve`) for that `{type, ident}` feed then reverts with `ERR-ORACLE-INVARIANT` until real block-time catches up to the poisoned future timestamp, which itself may never happen if the skew was arbitrarily large.

This is the direct analog of the "Proof Submission Delay Attack" bug class: instead of an attacker withholding a fraud proof until the challenge window edge to jam the system, a timestamp inconsistency near the freshness boundary jams the price-feed gate for the remainder of the window, denying all correctly-timed subsequent submissions rather than the delayed one.

### Impact Explanation
Any market action requiring an oracle price for the affected feed — borrow, withdraw, and liquidation health checks that call `price-resolve`/`price-multi-resolve` — will revert with `ERR-ORACLE-INVARIANT` for as long as `last-update` remains ahead of real block-time-derived publish times. This denies users the ability to withdraw collateral, repay debt, or be liquidated for that asset, i.e. temporary freezing of funds tied to positions relying on that feed, until an intervention (e.g. a DAO/oracle relayer submitting a timestamp that finally exceeds the poisoned value, or `max-staleness` reconfiguration) restores service.

### Likelihood Explanation
Triggering requires only one price update with `ts` ahead of `stacks-block-time` to be accepted by the upstream oracle relay (`pyth-storage-v4`/DIA) and passed through `resolve-pyth`/`resolve-dia` into `price-resolve` — the check does not require any privileged access to Zest contracts, only a naturally occurring or attacker-influenced clock discrepancy between the oracle's publish clock and the Stacks chain's block-time. Given Pyth/DIA publish times are independent of Stacks block production, this is a plausible occurrence rather than a purely theoretical one, though the exact frequency depends on external oracle relay behavior which is outside Zest's control.

### Recommendation
Reject timestamps that are ahead of `stacks-block-time` outright instead of clamping the delta to zero, e.g.:
```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts stacks-block-time)
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```
This prevents any future-dated timestamp from ever being accepted or persisted as the monotonic floor, closing the permanent-freeze path while preserving the intended staleness and monotonicity guarantees.

### Proof of Concept
1. An oracle update for feed `{type, ident}` is relayed with `publish-time = T_future`, where `T_future > current stacks-block-time` (due to clock skew between the external oracle's clock and the Stacks chain).
2. `resolve-pyth`/`resolve-dia` returns `{value, timestamp: T_future}`; `price-resolve` computes `delta = u0` (via the `> ts stacks-block-time` branch), so `oracle-timestamp-fresh` returns `true`, and `(>= T_future prev)` also holds since `prev` is presumably less than `T_future`. [3](#0-2) 
3. `last-update` for the feed key is set to `T_future`.
4. On the next real, correctly-timed oracle update with `ts' ≈ current stacks-block-time < T_future`, `oracle-timestamp-fresh` evaluates `(>= ts' T_future)` as `false`, causing `price-resolve` to `asserts!`-revert with `ERR-ORACLE-INVARIANT`.
5. All subsequent calls into `price-resolve`/`price-multi-resolve` for that feed revert, blocking borrow/withdraw/liquidation flows dependent on that asset's price until block-time surpasses `T_future`.

  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))

        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
