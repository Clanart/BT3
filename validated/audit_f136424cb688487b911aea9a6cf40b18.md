### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` keys causes stack exhaustion / node crash - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
Kaia's account-key RLP decoding path allows an `AccountKeyRoleBased` value to recursively contain another `AccountKeyRoleBased` value (and so on, to arbitrary depth) without any recursion-depth or nesting check performed *during* decoding. The rejection of "composite-inside-composite" keys only happens *after* decoding completes, in validation logic such as `CheckInstallable`/`CheckUpdatable`. An attacker who submits a single `TxTypeAccountUpdate` (or `FeeDelegatedAccountUpdate`/`...WithRatio`) transaction, or calls the `kaia_decodeAccountKey`/related RPC with a crafted, deeply self-nested RoleBased key blob, forces the node to perform deep mutual recursion through `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` → `NewAccountKey` → `AccountKeySerializer.DecodeRLP` → ... This is directly analogous to CVE-2015-9252 in QPDF, where unbounded recursive token resolution in `QPDFTokenizer::resolveLiteral`/`QPDF::resolve` caused stack exhaustion from attacker-controlled nested input.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes each role's key bytes independently and, for each one, constructs a fresh `AccountKeySerializer` and calls `rlp.DecodeBytes` on it: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type and dispatches to `NewAccountKey`, then decodes the concrete key type (which may itself be `AccountKeyTypeRoleBased`), invoking `AccountKeyRoleBased.DecodeRLP` again: [2](#0-1) 

Nothing in this call chain limits recursion depth or the number of nested `AccountKeyRoleBased` levels. The only guard against a "composite key containing a composite key" is `IsCompositeType()` combined with checks such as `CheckInstallable`/`CheckUpdatable`, which run **after** the entire nested structure has already been fully decoded: [3](#0-2) [4](#0-3) 

The decoding of this attacker-supplied key blob happens unconditionally as part of ordinary transaction deserialization for `TxTypeAccountUpdate` (and the fee-delegated variants), via `fromSerializable`, which is invoked from `DecodeRLP` for the tx: [5](#0-4) 

It is also directly reachable via public RPC: `KaiaAPI.DecodeAccountKey` calls `rlp.DecodeBytes` on an arbitrary attacker-supplied byte string with no size/depth restriction: [6](#0-5) 

Because each nested level requires only a few bytes of RLP (`AccountKeyTypeRoleBased` marker + a list of one nested-encoded blob), an attacker can construct a payload with tens of thousands of nesting levels using a payload only kilobytes in size, driving the Go call stack (and heap-backed goroutine stack) to grow without bound during decoding.

### Impact Explanation
Because Go grows goroutine stacks dynamically (not fixed-size like C), the practical effect is not necessarily a classic hard crash from stack overflow in every case, but the recursive decode consumes CPU and memory proportional to nesting depth and, at sufficient depth, will either exceed Go's runtime stack size limit (`runtime: goroutine stack exceeds ... -byte limit`, causing an unrecoverable panic/process crash) or cause severe processing delay/large memory allocation for a single transaction. Because this can be triggered:
- by any unprivileged EOA submitting a single crafted `AccountUpdate`/`FeeDelegatedAccountUpdate` transaction to the txpool or via `eth_sendRawTransaction`,
- or by any caller of the public `kaia_decodeAccountKey` RPC,

it represents a availability-impacting denial-of-service vector against any node that processes/validates the transaction or serves the RPC call (including all full nodes and validators that receive and decode the transaction during block/txpool processing), satisfying the "acceptance of an invalid transaction" / state-divergence risk criteria (a crashing node cannot process the block, while another node with more available stack/heap might, causing divergence in liveness).

### Likelihood Explanation
High likelihood of reachability: transaction decoding of `TxInternalDataAccountUpdate` (and fee-delegated variants) is mandatory for any node that receives the transaction over the p2p network, the txpool, or `eth_sendRawTransaction`; no privileged access or special network position is required — a plain unprivileged transaction sender can trigger it. The RPC path (`kaia_decodeAccountKey`) requires no elevated privileges either. The payload needed (a self-referential nested RLP `AccountKeyRoleBased` blob) is small and simple to construct.

### Recommendation
Add an explicit recursion-depth (or key-nesting) limit inside `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP`, rejecting any account key whose composite nesting exceeds a small fixed bound (e.g., depth 1, since role-based keys are documented to only ever contain non-composite leaf keys) *before* recursing further, rather than deferring the "no composite-inside-composite" rule to post-decode validation in `CheckInstallable`. Additionally, bound the maximum size/length of `[][]byte` accepted by `AccountKeyRoleBased.DecodeRLP` (e.g. cap `len(enc)` to `RoleLast`) as an additional defense-in-depth measure, and add a similar bound to the general RLP `Stream` decoder used by `KaiaAPI.DecodeAccountKey`.

### Proof of Concept
1. Encode `AccountKeySerializer{keyType: AccountKeyTypeRoleBased, key: &AccountKeyRoleBased{ /* itself pointing to a serialized copy containing another RoleBased key */ }}` recursively N times (e.g., N = 100,000), where each level is: `rlp.EncodeToBytes([keyTypeByte, [nestedBytes]])`.
2. Wrap the innermost bytes as the `Key` field of a `TxInternalDataAccountUpdate` (or call `kaia_decodeAccountKey` directly with the raw encoded blob).
3. Submit the resulting transaction via `eth_sendRawTransaction` (or invoke `kaia_decodeAccountKey` with the RLP blob).
4. Observe that the receiving node’s `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recursion consumes excessive stack/CPU, ultimately either crashing the goroutine with `runtime: goroutine stack exceeds ... limit` or causing significant processing delay for a single transaction/RPC call, before any `CheckInstallable`/`IsCompositeType` validation is ever reached.

*(Note: exact goroutine stack limits and observed crash thresholds are runtime/config-dependent and were not empirically verified in this codebase snapshot; a Devin session with execution access would be needed to confirm the precise nesting depth required to trigger a crash versus merely a processing delay.)*

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
