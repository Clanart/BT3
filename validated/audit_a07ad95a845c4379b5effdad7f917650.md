### Title
Unvalidated Wasm event attributes let a malicious CW20 pointer contract forge ERC20 Transfer/Approval logs for arbitrary victims - (File: app/receipt.go)

### Summary
Sei synthesizes ERC20-compatible EVM logs from raw CosmWasm module event attributes (`action`, `from`, `to`, `amount`, `owner`, `spender`) whenever a wasm contract that has a registered CW20→ERC20 pointer executes. `translateCW20Event` builds `Transfer`/`Approval` `ethtypes.Log`s directly from these string attributes without verifying that any real balance or allowance actually changed for the addresses named in the event. Since pointer registration is permissionless, an attacker can deploy their own CW20-like contract, register a pointer to it, and have that contract emit wasm events with attacker-chosen `from`/`to`/`amount` fields for any Sei/EVM address, producing fully synthetic ERC20 `Transfer` logs that appear in the victim's transaction history/receipts and are picked up by wallets, block explorers, and `eth_getLogs`/`eth_subscribe logs` consumers as if the victim received or sent tokens — a forged “notification” that never involved the victim, directly analogous to the Rocket.Chat bug where `stream-notify-user` did not check the sender, allowing an ephemeral fake message to be shown in another user's UI.

### Finding Description
`AddCosmosEventsToEVMReceiptIfApplicable` scans all `wasm` events in a delivered tx, and for any wasm contract address that has a registered ERC20/ERC721/ERC1155 pointer, calls the corresponding translator (`translateCW20Event`, etc.) to convert the contract's own `wasm` event attributes into synthetic EVM logs attached to the tx's receipt. [3](#0-2) 

`translateCW20Event` parses `action`/`from`/`to`/`amount` attributes from the wasm event and unconditionally emits an `ERC20TransferTopic` log using those exact attacker-supplied values — there is no check that `action.From`'s balance actually decreased or `action.To`'s balance actually increased by `action.Amount`, nor any check tying the emitted addresses to genuine state changes recorded elsewhere in the tx: [4](#0-3) 

The attribute parsing itself (`GetActionsFromWasmEvent`) simply reads whatever string values the contract chose to attach to its own emitted `wasm` event and converts them to EVM address hashes via `GetEvmAddressHash`, with no cross-validation against the contract's actual CW20 balance/allowance state: [5](#0-4) 

Because `MsgRegisterPointer`/`addCW20Pointer` allow any sender to point an ERC20 pointer at any CosmWasm contract address they control, an attacker's malicious contract can execute an arbitrary `wasm` event (e.g. via a custom `execute` message) that sets `action=transfer`, `from=<victim>`, `to=<attacker>`, `amount=<huge number>` without moving any real tokens. [1](#0-0) [2](#0-1) 

### Impact Explanation
This is a data-integrity / spoofing issue on the public JSON-RPC surface reachable by any unprivileged wasm contract deployer: forged ERC20 `Transfer`/`Approval` logs appear in receipts and are served through the EVM JSON-RPC (`eth_getLogs`, `eth_getTransactionReceipt`, `eth_subscribe("logs")`), which wallets, exchanges, and indexers commonly trust as proof of token movement. An attacker could forge an incoming-transfer notification to a victim (e.g. to trick an off-chain service into crediting a deposit, or to make a scam token appear to have paid out) — the same "fake ephemeral notification shown in someone else's UI" impact pattern as the Rocket.Chat CVE, but here amplified to on-chain-looking financial event data consumed by automated systems (exchanges, bridges) that key deposit-detection logic off `Transfer` event logs. This does not directly move funds in bank/x/evm state, but forged logs can be leveraged for fund-loss-adjacent abuse against any downstream system that credits balances based on observed `Transfer` events without independently verifying the pointer contract's real CW20 state.

### Likelihood Explanation
High reachability: the entire chain (deploy CW20 contract → `MsgRegisterPointer`/`addCW20Pointer` → execute a message that emits crafted wasm attributes) is achievable by a single unprivileged, unauthenticated transaction sender with no special permissions, matching this scan's "CW20 user / pointer user" reachable-surface criteria. The only constraint is that the attacker's contract must be wasm code that emits a `wasm` event with `action` in `{mint, burn, send, transfer, transfer_from, send_from, burn_from}` plus `from`/`to`/`amount` attributes, which is trivial to construct with a custom CosmWasm contract (it does not need to be a real CW20 implementation, only to emit events matching this pattern).

### Recommendation
In `translateCW20Event` (and the CW721/CW1155 equivalents in `app/receipt.go`), cross-validate the wasm event's claimed `from`/`to`/`amount` against actual queried balance/allowance deltas on the underlying CW20 contract before synthesizing an EVM log, or restrict synthetic log generation to attributes emitted by the canonical, chain-controlled CW20/CW721/CW1155 pointer implementation bytecode rather than arbitrary user-deployed contracts. Alternatively, tie pointer registration/log synthesis to a stronger authenticity check (e.g., verifying code hash equals a known-good CW20 reference implementation) so the "sender" of the event can be trusted before translating it into a native-looking ERC20 log.

### Proof of Concept
1. Attacker deploys a CosmWasm contract `Evil` whose `execute` handler, for a custom message, emits a `wasm` event with attributes: `action=transfer`, `from=<victim_sei_addr>`, `to=<attacker_sei_addr>`, `amount=1000000000000` (no real balance state change occurs).
2. Attacker calls `addCW20Pointer("Evil")` via the pointer precompile (permissionless), registering an ERC20 pointer contract for `Evil`. [2](#0-1) 
3. Attacker calls the custom `execute` message on `Evil` in a normal tx.
4. `AddCosmosEventsToEVMReceiptIfApplicable` finds the pointer for `Evil`'s contract address and calls `translateCW20Event`, which emits a synthetic `ERC20TransferTopic` log with `from=victim`, `to=attacker`, `amount=1000000000000`, attached to the tx's EVM receipt. [6](#0-5) 
5. Any JSON-RPC client filtering on `Transfer` events for `victim`'s address (`eth_getLogs`/`eth_subscribe logs`) observes an apparent outgoing transfer from the victim that never happened, and clients filtering for the attacker's address see a fabricated deposit — with no actual CW20 balance change anywhere in state.

func (server msgServer) RegisterPointer(goCtx context.Context, msg *types.MsgRegisterPointer) (*types.MsgRegisterPointerResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)
	if server.GetRegisterPointerDisabled(ctx) {
		return nil, fmt.Errorf("registering CW->ERC pointers has been disabled")
	}
	var existingPointer sdk.AccAddress
	var existingVersion uint16
	var currentVersion uint16
	var exists bool
	switch msg.PointerType {
	case types.PointerType_ERC20:
		currentVersion = erc20.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW20ERC20Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	case types.PointerType_ERC721:
		currentVersion = erc721.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW721ERC721Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	case types.PointerType_ERC1155:
		currentVersion = erc1155.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW1155ERC1155Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	default:
		panic("unknown pointer type")
	}
	if exists && existingVersion >= currentVersion {
		return nil, fmt.Errorf("pointer %s already registered at version %d", existingPointer.String(), existingVersion)
	}

func (app *App) translateCW20Event(ctx sdk.Context, wasmEvent abci.Event, pointerAddr common.Address, contractAddr string) (res []*ethtypes.Log) {
	defer func() {
		if r := recover(); r != nil {
			fmt.Printf("[Error] Panic caught during translateCW20Event: type=%T, value=%+v\n", r, r)
		}
	}()

	for _, action := range app.GetActionsFromWasmEvent(ctx, wasmEvent) {
		switch action.Type {
		case "mint", "burn", "send", "transfer", "transfer_from", "send_from", "burn_from":
			if action.Amount == nil {
				continue
			}
			res = append(res, &ethtypes.Log{
				Address: pointerAddr,
				Topics: []common.Hash{
					ERC20TransferTopic,
					action.From,
					action.To,
				},
				Data: common.BigToHash(action.Amount).Bytes(),
			})

func (app *App) GetActionsFromWasmEvent(ctx sdk.Context, event abci.Event) (actions []*Action) {
	for _, attr := range event.Attributes {
		key := string(attr.Key)
		value := string(attr.Value)
		if key == "action" {
			actions = append(actions, &Action{Type: value})
			continue
		}
		if len(actions) == 0 {
			continue
		}
		curAction := actions[len(actions)-1]
		switch key {
		case "amount":
			curAction.Amount = safeBigIntFromString(value)
		case "amounts":
			curAction.Amounts = utils.Map(strings.Split(value, ","), safeBigIntFromString)
		case "token_id":
			curAction.TokenId = safeBigIntFromString(value)
		case "token_ids":
			curAction.TokenIds = utils.Map(strings.Split(value, ","), safeBigIntFromString)
		case "sender":
			curAction.Sender = app.GetEvmAddressHash(ctx, value)
		case "recipient":
			curAction.Recipient = app.GetEvmAddressHash(ctx, value)
		case "spender":
			curAction.Spender = app.GetEvmAddressHash(ctx, value)
		case "operator":
			curAction.Operator = app.GetEvmAddressHash(ctx, value)
		case "owner":
			curAction.Owner = app.GetEvmAddressHash(ctx, value)
		case "from":
			curAction.From = app.GetEvmAddressHash(ctx, value)
		case "to":
			curAction.To = app.GetEvmAddressHash(ctx, value)
		}
	}
	return
}
