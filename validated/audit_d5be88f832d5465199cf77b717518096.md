## Finding: Confirmed but with an important caveat

I was able to fully verify two of the three necessary links but ran out of budget to inspect `checkoutLocalBranch` in `dispatcher.ts`, which is the code that turns the raw `branch` string from the deep link into a `Branch` object passed to `checkoutBranch`. I'll present what's confirmed and flag the remaining gap.

### Confirmed: validation asymmetry
`parseAppURL` validates `branch` only with `testForInvalidChars`, which reuses `invalidCharacterRegex` from `sanitize-ref-name.ts`: [1](#0-0) [2](#0-1) 

Note that `sanitizedRefName` (used elsewhere to *create* branches) additionally strips a leading `-`/`+` via `.replace(/^[-\+]*/g, '')`, but `testForInvalidChars` does **not** apply that same rule — it only tests the character-class regex. `-b` therefore passes `testForInvalidChars` cleanly (no control chars, no `..`, no leading `.`, no `.lock`, no trailing `/`), so `parseAppURL('x-github-client://openrepo/<url>?branch=-b')` returns a valid `open-repository-from-url` action with `branch: '-b'`.

### Confirmed: dispatcher routes this to a branch-name checkout path [3](#0-2) 

`openBranchNameFromUrl` calls `this.checkoutLocalBranch(repository, branchName)` with the raw, attacker-supplied string. I was not able to read the body of `checkoutLocalBranch` before running out of tool iterations, so I cannot confirm with certainty whether it (a) looks up an existing `Branch` object matching that name via `getBranches()` (in which case the malicious name would need to already exist as a real ref, e.g. a maliciously pushed branch literally named `-b`), or (b) constructs a `Branch`-like object directly from the untrusted string without requiring it to correspond to a real ref before calling `checkoutBranch`. This materially affects the actual likelihood/severity and needs further verification.

### Confirmed: the sink has a real argv-ordering bug
`checkout.ts` builds the checkout argv as: [4](#0-3) 

For a local branch, the final `git` argv is `['checkout', branch.name, '--']` — note `'--'` is placed **after** `branch.name`, not before it. Since `git` parses arguments left-to-right and hasn't yet reached `--` when it evaluates the first positional token, a `branch.name` of `-b` is parsed as the `-b` option (create-and-checkout-new-branch), not as a ref/pathspec. This means the `'--'` terminator here provides no protection against a hostile ref name at all — it's positioned to guard the (already-safe, hard-coded) trailing pathspec, not the attacker-influenced `branch.name`. This is confirmed directly from the code and is a genuine implementation flaw regardless of how `checkoutLocalBranch` supplies the value.

### Impact
If reachable with an unvalidated/unresolved string (case "b" above), `git checkout -b --` (or `git checkout -b <nameWithoutRemote> --` for the remote-tracking variant) does not check out the intended ref at all — it instead attempts to create a new branch from the current `HEAD`, silently diverging from the user's/link's intended checkout target. If only reachable when a real ref with that literal dash-prefixed name exists (case "a"), the practical severity is lower since it requires the attacker to control the repository's actual ref names in addition to the link, but the corruption of checkout semantics is the same.

### What's needed to close the gap
Confirming this requires reading `checkoutLocalBranch` in `app/src/ui/dispatcher/dispatcher.ts` (referenced at lines 1993 and elsewhere) to see whether it validates against an existing `Branch` from `getBranches()` or constructs the checkout target directly from the untrusted string. Given the index/tool budget for this session was exhausted, I recommend a follow-up look specifically at that function before finalizing severity, or a Devin session to fetch the full file if the index doesn't cover it.

### Recommendation (if pursued)
- Fix `getBranchCheckoutArgs` in `checkout.ts` so `'--'` precedes `branch.name` (and any other user/ref-derived value) in the argv, ensuring git treats it strictly as a pathspec/ref, never as an option.
- Align `testForInvalidChars` with `sanitizedRefName`'s leading `-`/`+` stripping so deep-link branch values can't smuggle option-like tokens through validation. [5](#0-4) [6](#0-5)

const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)
