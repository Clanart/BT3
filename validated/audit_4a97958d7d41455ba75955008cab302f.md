### Title
Stack exhaustion via unbounded recursive RLP decoding of nested `AccountKeyRoleBased` in `AccountUpdate` transactions - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
An unprivileged party can submit a raw `TxTypeAccountUpdate` (or `TxTypeFeeDelegatedAccountUpdate*`) transaction via public RPC (`eth_sendRawTransaction`) whose `AccountKey` field is RLP-encoded as a deeply, recursively nested `AccountKeyRoleBased`. Decoding this field is fully recursive and unbounded in depth, and the only guard against nested composite keys (`ErrNestedCompositeType`) is applied *after* decoding completes, inside `CheckInstallable`/`CheckUpdatable`. A sufficiently deep nesting therefore exhausts the goroutine stack during RLP decoding itself — before any validation runs — matching the CVE-2024-34155 bug class ("Parse functions panic on deeply nested input due to stack exhaustion").

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of raw byte-strings and, for each entry, calls `rlp.DecodeBytes` on a fresh `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type, constructs the concrete `AccountKey` implementation via `NewAccountKey`, and recursively decodes into it with `s.Decode(serializer.key)`: [2](#0-1) 

If the key type is again `AccountKeyTypeRoleBased`, this re-enters `AccountKeyRoleBased.DecodeRLP`, which calls `rlp.DecodeBytes` again — a genuine Go call-stack recursion (`DecodeRLP → rlp.DecodeBytes → Stream.Decode → decodeDecoder → AccountKeySerializer.DecodeRLP → s.Decode → AccountKeyRoleBased.DecodeRLP → …`). Nothing in `rlp/decode.go` enforces a maximum decode depth (no `maxDepth`/recursion-guard constructs were found in that package), so the depth is bounded only by the size of the crafted input.

The only place nested composite keys are rejected is post-decode, in `CheckInstallable`, which walks the *already fully materialized* `AccountKeyRoleBased` slice and returns `kerrors.ErrNestedCompositeType` if any role key `IsCompositeType()`: [3](#0-2) 

This is confirmed by the test `TestAccountUpdateRoleBasedKeyNested`, which shows that a single level of nesting is only rejected at `txpool.AddRemote` / block-apply time, i.e. after the transaction (and thus its `AccountKey`) has already been fully RLP-decoded: [4](#0-3) 

Because the reject-nested-composite check runs strictly after decoding, an attacker does not need it to ever succeed — they only need the decode step to run long enough (i.e., recurse deep enough) to exhaust the stack. Transaction RLP decoding (`TxInternalDataSerializer.DecodeRLP`, which drives decoding of the `AccountKey` field for account-update transactions) is invoked unconditionally on every transaction received by the node, including via public RPC submission and p2p transaction propagation: [5](#0-4) 

### Impact Explanation
A crafted `AccountUpdate` transaction with thousands of nested `AccountKeyRoleBased` layers, when decoded (e.g. on `eth_sendRawTransaction`, tx-pool ingestion, or block re-execution/decoding by any node), triggers unbounded Go-stack recursion. This causes the decoding goroutine to panic with a fatal stack-overflow error, which in Go is not recoverable via `recover()` — it crashes the entire node process. Since transaction decoding happens on every full/validating node that receives or processes the transaction (including via public RPC ingress), this is a repeatable, low-cost, remotely triggerable denial-of-service against block producers and RPC nodes.

### Likelihood Explanation
High: the vector requires only a single, syntactically valid (from an RLP standpoint) transaction submitted through the standard public transaction-submission path. No privileged role, special account state, or specific block timing is required — any unprivileged transaction sender or RPC caller can construct and submit the malicious payload. The nested-composite-type rejection logic exists precisely because the protocol intends to forbid this structure, but it is enforced too late in the pipeline (after decode, not during/before decode), making the bypass straightforward.

### Recommendation
Enforce a maximum recursion/nesting depth for `AccountKey` decoding before or during RLP decode (e.g., pass and decrement a depth counter through `AccountKeySerializer.DecodeRLP`/`AccountKeyRoleBased.DecodeRLP`, rejecting anything beyond a small constant, since role-based nesting is never legitimately more than 1 level deep). Additionally/alternatively, add a general nesting-depth limit to the `rlp` package's list/decoder recursion (mirroring the Go standard library's fix for CVE-2024-34155) so that any recursively-decodable structure across the codebase is protected, not just `AccountKey`.

### Proof of Concept
1. Programmatically build a byte slice `payload` representing `AccountKeyTypeRoleBased` wrapping a single-element list `[serialized_AccountKeyRoleBased]`, and nest this construction N times (e.g., N = 50,000), each outer layer's list element being the RLP bytes of the previous layer (mirroring the structure produced by `AccountKeyRoleBased.EncodeRLP`, i.e. `enc[i] = rlp.EncodeToBytes(NewAccountKeySerializerWithAccountKey(k))`) — this can be done purely via low-level RLP byte construction without calling `CheckInstallable`, so the "no nested composite" rule is never enforced at construction time.
2. Embed this `payload` as the `AccountKey` field of a raw `TxTypeAccountUpdate` transaction and RLP-encode the full transaction.
3. Submit the resulting raw transaction via `eth_sendRawTransaction` to a Kaia node's public RPC endpoint, or otherwise inject it into the node's tx-pool/p2p ingestion path.
4. Observe that decoding of the transaction (`TxInternalDataSerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recursion) exhausts the goroutine stack and crashes the node process before `checkAccountKeyZeroValues`/`CheckInstallable`/tx-pool validation ever execute.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (serializer *TxInternalDataSerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.txType); err != nil {
		// fallback to the original transaction decoding.
		txd := newEmptyTxInternalDataLegacy()
		if err := s.Decode(txd); err != nil {
			return err
		}
		serializer.txType = TxTypeLegacyTransaction
		serializer.tx = txd
		return nil
	}

	if serializer.txType == EthereumTxTypeEnvelope {
		var ethType TxType
		if err := s.Decode(&ethType); err != nil {
			return err
		}
		serializer.txType = serializer.txType<<8 | ethType
	}

	var err error
	serializer.tx, err = NewTxInternalData(serializer.txType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.tx)
}
