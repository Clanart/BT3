### Title
Unchecked ERC20 return-value in Tron `IntentGatewayV2.withdraw()` allows silent transfer failure with escrow already finalized - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) settles escrow releases with a raw low-level `.call` to the ERC20 `transfer` selector and only checks that the *call did not revert* (`success`), never decoding and verifying the boolean return value the ERC20 standard specifies. This is the exact bug class from the external report — trusting an external call's outcome instead of verifying the real balance effect — but reproduced in Hyperbridge's own cross-chain intent settlement path instead of a vault.

### Finding Description
`withdraw()` releases escrowed order inputs (and `TRANSACTION_FEES`) to a beneficiary after a fill or refund is finalized: [1](#0-0) 

For every token it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
This only guarantees the callee didn't revert; it never checks the ABI-decoded boolean returned by `transfer`. Per ERC20, a compliant-but-non-reverting token is allowed to return `false` on failure (insufficient balance/allowance-adjacent policy failures, blacklists, paused states, custom compliance tokens, etc.). When that happens, `success == true` even though no tokens moved, yet the code unconditionally:
1. decrements `_orders[body.commitment][token]` (escrow accounting treats funds as paid out), and
2. (in the caller) sets `_filled[body.commitment] = beneficiary`, permanently finalizing the order.

This is the same root cause identified in the external ERC4626 report: the contract infers real economic outcome from a call's return signal instead of verifying actual balance movement, and it does so in a fund-custody critical path (escrow release), not merely a defensive nicety.

By contrast, the canonical EVM path in `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw()` uses OpenZeppelin's `SafeERC20.safeTransfer`, which enforces the return value is either absent (non-standard token) or `true`, reverting otherwise: [2](#0-1) 

The Tron file imports `SafeERC20` and even applies `using SafeERC20 for IERC20;` at the contract level, but does not use `safeTransfer` in the escrow-release/dust-sweep code paths, instead using raw `.call` with only a success check in multiple places (`withdraw`, `sweepDust`, predispatch-sweep transfer construction): [3](#0-2) [4](#0-3) 

### Impact Explanation
This is fund loss/lock in a production bridge custody path: escrowed user/solver assets are moved from "owed" to "paid" state in accounting while the beneficiary receives nothing, for any ERC20 that can non-revertingly return `false` (a broad, realistic class of tokens used on Tron/EVM, including compliance-gated stablecoin variants and custom tokens). Once `_orders[...][token]` is decremented and `_filled[commitment]` is set, there is no retry path — the tokens are effectively stranded in the gateway contract while the rightful beneficiary's claim is extinguished. This matches the bounty's "stealing or loss of funds" / "unauthorized transaction or execution" impact class and requires no relayer, prover, admin, or malicious-peer assumption — it is purely a function of which ERC20 token is used for the order's input asset, something an ordinary unprivileged user or solver selects when placing/filling an order.

### Likelihood Explanation
Likelihood is contingent on the token used for the order's input assets returning `false` instead of reverting on failure — this is not universal ERC20 behavior, but it is a well-documented, non-exotic category (and the codebase's own fee-on-transfer test suite shows the authors are already aware that non-standard token semantics are in scope for the Intent Gateway's escrow accounting, having built explicit balance-diffing logic for inbound transfers). The outbound path in the Tron contract, however, lacks the equivalent protection.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`, `sweepDust`, and the predispatch sweep-call construction) with `IERC20(token).safeTransfer(...)` via the already-imported `SafeERC20` library, mirroring `IntentsBase._withdraw` in the canonical EVM implementation. As an additional defense-in-depth measure (matching the report's recommendation), verify actual balance deltas via `balanceOf` before/after outbound transfers in the escrow-release path, consistent with how inbound transfers are already balance-diffed elsewhere in the same file.

### Proof of Concept
1. Deploy a token whose `transfer` function returns `false` (instead of reverting) when a transfer condition fails — e.g., a blacklist/pausable/compliance token, or simply a token contract that always returns `false` post some internal check without reverting.
2. User places an order on the Tron `IntentGatewayV2` with this token as input, escrowing it via `placeOrder`.
3. Solver fills the order; the fill path eventually calls `withdraw(body, false)` to release the escrowed token to the solver.
4. Arrange for the token's `transfer(beneficiary, amount)` call to return `false` (e.g., beneficiary temporarily blacklisted by the token's compliance module) while not reverting.
5. `token.call(...)` returns `success = true` (the low-level call succeeded and didn't revert) even though `transfer` internally returned `false` and moved no tokens.
6. `withdraw()` proceeds: `_orders[commitment][token] -= amount` and `_filled[commitment] = beneficiary` are both finalized.
7. Result: the solver/beneficiary never received the tokens, the escrow record shows zero owed, and the order is marked filled — the tokens remain stuck in the `IntentGatewayV2` contract with no code path to reclaim them.
