## Title
Relayer reward double-payment via reward-transfer-before-watermark-update ordering — ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::process_message` transfers the BRIDGE reward to the relayer, deposits the reward event, and only *afterwards* mints the reputation-asset credit and advances the `LastRewardedHeight` watermark that prevents the same block span from being paid twice. If the reputation mint fails after the treasury transfer has already succeeded, the function returns an `Err` before the watermark is advanced, so the next consensus submission recomputes the reward using the same stale baseline and pays out the same (or overlapping) block span again — an unbounded, repeatable double-claim against the treasury.

### Finding Description
`calculate_reward` derives the payable block span from `LastRewardedHeight`, which is the sole state that prevents double-payment for the same height range: [1](#0-0) 

`process_message` executes the irreversible treasury transfer, then the reputation mint, and only writes the anti-double-payment watermark last, gated behind `?` on the mint call: [2](#0-1) 

The sequence is:
1. `T::Currency::transfer(...)` — moves BRIDGE from the treasury to `relayer_account`. This step, once it succeeds, is final and cannot be undone by a later failure.
2. `deposit_event(...)`.
3. `T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())` — this can fail (e.g. `TokenError::BelowMinimum` when a brand-new relayer account receives a reward smaller than the reputation asset's existential deposit, which is entirely plausible for a first-time relayer or a low `block_cost` configuration).
4. Only *after* the mint succeeds does `LastRewardedHeight::<T>::mutate(...)` advance the watermark.

If step 3 fails, `process_message` returns `Err(Error::<T>::ReputationMintFailed)` *after* the treasury transfer in step 1 has already been executed, and the watermark in step 4 is never advanced. `on_executed` swallows this error (`let _ = Self::process_message(...)`), so nothing halts or is retried — but the next time a `StateMachineUpdated` event lands for the same `state_machine_id` (a normal, permissionless consensus-relaying event that happens continuously), `calculate_reward` reads the exact same stale `LastRewardedHeight` baseline and recomputes a reward that re-covers the block span already paid for in the failed attempt, transferring BRIDGE again for a span that was already compensated.

This is structurally the same class of bug as the TokenLocker report: a running, replay-preventing accumulator (`LastRewardedHeight`, analogous to `totalDecayRate`/`totalWeight`) is updated in the wrong order relative to a fallible/irreversible operation, so the ledger becomes permanently desynchronized from the value it is supposed to gate, and a fund-moving computation downstream of that ledger becomes wrong (here: repeatable) rather than merely off by a constant.

### Impact Explanation
Every occurrence of a reputation-mint failure after a successful treasury transfer results in a duplicated relayer reward payout from the Hyperbridge treasury for the same consensus block span — direct, repeatable loss of protocol funds with no admin, prover, or malicious-relayer collusion required. Because this can recur on every subsequent `StateMachineUpdated` batch for the same state machine until a mint eventually succeeds, the drain is not self-limiting.

### Likelihood Explanation
No privileged actor is required. Any ordinary, permissionless relayer whose very first (or any sufficiently small) reward is below the `ReputationAsset`'s existential deposit will trigger `mint_into` to fail while the currency transfer has already gone through, since `calculate_reward` and `T::ReputationAsset` are governance-configured values independent of relayer behavior. Given that `on_executed` runs on every relayed consensus batch and silently discards the error, this is easy to trigger unintentionally and trivially repeatable once discovered.

### Recommendation
Advance `LastRewardedHeight` (and emit the reward event) atomically with, or strictly before, any operation that can fail after the irreversible `T::Currency::transfer` — or make the whole `process_message` transactional so that a `mint_into` failure rolls back the preceding transfer (e.g. wrap in `frame_support::storage::with_transaction` / `TransactionOutcome::Rollback` on error), and only commit once both the transfer and the watermark update have succeeded. Alternatively, decouple reputation minting so its failure cannot block the watermark advance that guards against double payment.

### Proof of Concept
1. Configure `StateMachinesCostPerBlock` for a state machine with a small `block_cost` (or let the very first relayer reward be a small integer).
2. Have a brand-new relayer account (no prior reputation-asset balance) submit a valid consensus message advancing that state machine by a small number of blocks, such that `reward.saturated_into()` is below the `ReputationAsset`'s existential deposit.
3. `T::Currency::transfer` succeeds (relayer receives BRIDGE); `T::ReputationAsset::mint_into` fails with `TokenError::BelowMinimum`; `process_message` returns `Err`, so `LastRewardedHeight` is never updated.
4. Submit another (even trivial) consensus update for the same `state_machine_id`. `calculate_reward` re-uses the old `LastRewardedHeight` baseline, recomputing and paying out a reward that re-covers the block span already paid in step 2/3 — duplicating treasury spend for the same span. [2](#0-1)
