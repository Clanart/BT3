### Title
Payout tx's OP_RETURN operator-pk output is not covered by the user's `SinglePlusAnyoneCanPay` signature, letting anyone splice in a truncated/absent OP_RETURN and falsely mark the honest funder as malicious - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` signs the payout tx input with `TapSighashType::SinglePlusAnyoneCanPay`, which — per BIP341/BIP143 semantics — only commits to input 0 and the single output at the same index (output 0, the withdrawer's payout). It does **not** cover output 2, the OP_RETURN carrying the operator's x-only pubkey. Anyone who observes the honest operator's broadcast, unconfirmed payout tx (mempool, or via any relay) can lift the witness/signature and rebroadcast an alternative transaction reusing input 0 and output 0 verbatim but with the OP_RETURN removed, mangled, or truncated to fewer than 32 bytes, and add their own fee-paying input(s) (also uncovered by `ANYONECANPAY`). If this variant confirms first, `update_finalized_payouts` (`core/src/verifier.rs:2283`) records `operator_xonly_pk = NULL` for that withdrawal, and `is_kickoff_malicious` (`core/src/verifier.rs:1859`) will subsequently treat the honest operator's kickoff as malicious.

### Finding Description
Binding claimed to hold: `withdrawals.payout_payer_operator_xonly_pk` for withdrawal `i` == `Some(funder_pk)`, where `funder_pk` is the operator that actually funded output 0 of the confirmed payout tx for withdrawal `i`.

Root cause / trace:
- `create_payout_txhandler` builds outputs `[user_payout, anchor, OP_RETURN(operator_xonly_pk)]` and signs only input 0 with the user's `SinglePlusAnyoneCanPay` signature [1](#0-0) .
- The sighash for this type, per `calculate_pubkey_spend_sighash`/`calculate_sighash_txin`, uses `Prevouts::One` and (by taproot sighash spec for `SINGLE|ANYONECANPAY`) commits only to the input being spent and the output at the same index — i.e. output 0 [2](#0-1) .
- The tx-sender's own RBF module explicitly exploits/acknowledges this malleability: it detects a 65-byte `S+AP` signature and copies it verbatim into a *different* PSBT/transaction, confirming that outputs beyond index 0 (and other inputs) can be freely varied while the signature stays valid [3](#0-2) .
- `update_finalized_payouts` locates whichever payout tx actually confirms for the withdrawal outpoint and extracts the operator pk purely from the first OP_RETURN output using `parse_op_return_data` + `XOnlyPublicKey::from_slice`; if the pushdata isn't exactly 32 bytes, the result is `None`, silently logged as "optimistic payout or operator constructed payout tx wrong" [4](#0-3) .
- `is_kickoff_malicious` unconditionally treats `operator_xonly_pk_opt == None` as malicious, with no fallback to check whether the real operator's kickoff/collateral chain actually funded the withdrawal [5](#0-4) .
- `parse_op_return_data` only requires `Instruction::Op(OP_RETURN)` followed by any `Instruction::PushBytes`; it accepts any length, including 31 bytes, and `Script::is_op_return()` likewise only checks for the leading OP_RETURN opcode, not pushdata length [6](#0-5) .

Exploit flow: honest operator broadcasts payout tx (input = withdrawal UTXO, output0 = withdrawer payment, output2 = OP_RETURN with its own 32-byte xonly pk) and it sits unconfirmed in the mempool. Attacker copies the witness for input 0 (valid since untouched fields are covered by the signature) into a new transaction with the same input 0 and output 0, but replaces output 2 with a 31-byte OP_RETURN push (still `is_op_return()==true`), adds their own funding input/fee (uncovered by `ANYONECANPAY`), and gets it mined first (via higher fee or RBF/full-RBF). Downstream, `operator_xonly_pk` for this withdrawal becomes `None` in the DB, so `is_kickoff_malicious` returns `true` for the honest operator's subsequent kickoff even though that operator genuinely funded output 0.

Existing guards that fail to stop this: `Operator::withdraw`/`internal_withdraw` only verify the *user's* signature against the payout tx they themselves construct at broadcast time; they never re-verify the OP_RETURN content on-chain after confirmation. `update_finalized_payouts` and `is_kickoff_malicious` trust the OP_RETURN of whichever transaction ends up spending the withdrawal UTXO, without any binding between that OP_RETURN and a signature or commitment from the actual funding operator.

### Impact Explanation
This causes an honest operator to be misclassified as malicious purely because a third party won a fee race for a UTXO the operator did not exclusively control (the withdrawal input is signed with `ANYONECANPAY`, deliberately allowing anyone to add inputs/fees and thus win the mempool race for that outpoint). The consequence: `is_kickoff_malicious` returning `true` leads verifiers to send a `Challenge` (and downstream Disprove path) against the honest operator's kickoff, burning its collateral, or otherwise blocking legitimate `Reimburse` for a payout that operator genuinely funded — a Critical-severity outcome (honest operator's collateral burned / operator permanently unable to be reimbursed). The attack is repeatable per-withdrawal and requires no verifier/operator privilege — only observing a broadcast payout tx and paying a fee to win the confirmation race.

### Likelihood Explanation
Preconditions: an honest operator must have already broadcast (but not yet confirmed) a payout tx for a withdrawal, which is the normal operating flow (`Operator::withdraw`) and thus always reachable. The attacker needs only Bitcoin mempool visibility and enough BTC to outbid the operator's fee (or add their own funding input), both trivially available to an unprivileged attacker per the threat model. This is feasible without any protocol key, and is repeatable across every withdrawal/operator that goes through the standard (non-optimistic) payout path.

### Recommendation
Bind the operator identity to something the *withdrawer's* signature actually commits to, or otherwise make the OP_RETURN unforgeable/un-strippable by a third party:
- Change the payout tx signature scheme so it commits to all outputs (e.g. use `SIGHASH_ALL` for the operator-controlled outputs, or require the operator to co-sign a commitment covering the OP_RETURN), or
- Require the withdrawal UTXO input itself to be spendable only via a script path controlled by the operator (so the operator, not an arbitrary third party, controls which tx confirms), or
- When `operator_xonly_pk` from the confirmed payout tx OP_RETURN is `None`/invalid or mismatched, do not default to "malicious" — instead check independently (e.g., against off-chain records of which operator was given the withdrawal signature) before flagging any operator as malicious, or treat this ambiguous case as "needs additional verification" rather than an automatic malicious verdict.
- At minimum, reject/ignore malformed (non-32-byte) OP_RETURN payouts from a "different funder" perspective by cross-checking that the tx's other inputs/outputs match what was actually distributed to operators for that withdrawal (e.g., store and compare the exact payout tx template/txid the operator committed to, rather than trusting whichever tx happens to spend the UTXO).

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Given a PSBT with inputs, fill in the existing witnesses from the original tx
    /// This allows us to create a finalized PSBT if
    /// the original tx had SinglePlusAnyoneCanPay signatures.  If the original
    /// tx did not have S+AP, these signatures will be added. The expected behavior is for them to be replaced using RbfSigningInfo.
    ///
    /// # Returns
    /// The PSBT as a base64-encoded string.
    pub async fn copy_witnesses(&self, psbt: String, initial_tx: &Transaction) -> Result<String> {
        let mut decoded_psbt = Psbt::from_str(&psbt).map_err(|e| eyre!(e))?;

        for (idx, input) in initial_tx.input.iter().enumerate() {
            if let Some(sig) = input.witness.nth(0) {
                if sig.len() == 65 && sig[64] == 0x83 {
                    // This is a S+AP signature, copy it over
                    decoded_psbt.inputs[idx].final_script_witness = Some(input.witness.clone());
                }
            }
        }

        Ok(decoded_psbt.to_string())
    }

/// Parses the OP_RETURN data from a Bitcoin script. It retrieves the first data push after an OP_RETURN.
pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {
        if let Some(Ok(Instruction::PushBytes(data))) = instructions.next() {
            return Some(data.as_bytes());
        }
    }
    None
}
