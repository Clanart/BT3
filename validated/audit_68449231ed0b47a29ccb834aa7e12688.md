### Title
OP_RETURN data output omitted from weight/fee and standardness calculation, producing under-priced or non-standard transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an `OP_RETURN` output carrying up to 80 bytes of attacker-influenced `data` onto `tx_outs`, but computes the transaction's weight, vbytes, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` standardness check exclusively from `payments` (and optionally `change`). The `data` output is never included in any `calculate_weight_vbytes` call.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- Lines 193-202 append the `OP_RETURN` output to `tx_outs` before any sizing is done.
- Line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — it passes `payments`, not `tx_outs`, so the data output is excluded.
- Lines 224-235 repeat the omission for the change-aware path: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` again ignores the `OP_RETURN` output already sitting in `tx_outs`.
- Line 241 enforces `weight > MAX_STANDARD_TX_WEIGHT` using the under-counted `weight`.
- `needed_fee` (lines 206-213) is therefore `fee_per_vbyte * vbytes` for a transaction that is actually ~90+ weight units larger.

`calculate_weight_vbytes` (lines 62-127) builds a template `Transaction` whose outputs are exactly the `payments` slice it is passed, so the bug is structural, not a rounding issue.

The analog to the referenced bug class (funds enter the vault but are not reflected in the computed accounting value under some conditions): here value committed to the transaction (the data output) is not reflected in the computed fee/weight value whenever `data.is_some()`.

### Impact Explanation
Two concrete consequences when `data` is provided:

1. **Under-priced fee**: the signed transaction's real fee rate is `needed_fee / actual_vbytes`, strictly below the caller-requested `fee_per_vbyte`. If the margin crosses the mempool minimum relay fee, the fully-signed transaction is rejected by Bitcoin nodes — funds remain unspent and the multisig ceremony output is unusable, requiring re-planning/re-signing.
2. **Non-standard transaction**: a transaction with payments totaling weight just under `MAX_STANDARD_TX_WEIGHT` (400,000 WU) plus an OP_RETURN output can exceed the limit on-chain while passing the line-241 check, producing a transaction that is consensus-valid but non-standard and unrelayable.

The `data` field is populated from Serai protocol instructions (outbound transfer memos), so an unprivileged user who causes a large data payload to be attached to an outbound Bitcoin transaction can push the fee below relay minimum or the weight over standardness, stalling the spend.

### Likelihood Explanation
Requires a `data` payload on an outbound transaction combined with either a marginal fee rate or a payment set near the standard-weight limit. The under-pricing happens deterministically whenever `data.is_some()`; whether it causes rejection depends on fee market conditions. Medium likelihood, Medium impact (DoS / stuck funds, not theft).

### Recommendation
Build `tx_outs` (including the `OP_RETURN` output) first, then compute weight/fee over the actual output list — e.g. pass `&tx_outs`-equivalent data into `calculate_weight_vbytes`, or add a dedicated weight term for the data output (`8 + 1 + script_len` bytes serialized). Re-check `needed_fee`/`MAX_STANDARD_TX_WEIGHT` after the change output decision since adding change changes which outputs exist.
