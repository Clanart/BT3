### Title
`ThresholdKeys::new`/`ThresholdKeys::read` trust only the first `t` verification shares when deriving `group_key`, silently accepting attacker-planted shares for indexes `t+1..=n` — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
Analogous to `amportal` searching a non-root-writable directory and executing whatever `freepbx_engine` file it finds there, `ThresholdKeys::new` computes the group key exclusively from `verification_shares[1..=t]` and never validates the remaining `n - t` shares, nor that `secret_share` corresponds to `verification_shares[i]`. Bytes fed to `ThresholdKeys::read` (listed as attacker-reachable) therefore let an unprivileged party "plant" arbitrary verification shares in the slots the group-key derivation never inspects, producing a `ThresholdKeys` that carries the honest group key but inconsistent per-participant verification shares.

### Finding Description
In `ThresholdKeys::new` the group key is interpolated only over participants `1..=t`:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
``` [1](#0-0) 

The only checks on the map are `len() == n` and each index `<= n` — nothing checks that the shares are consistent evaluations of one polynomial, and `secret_share` is never checked against `verification_shares[params.i()]`: [2](#0-1) 

`ThresholdKeys::read` feeds fully attacker-controlled bytes (`t`, `n`, `i`, interpolation coefficients, `secret_share`, and all `n` verification-share points) directly into `ThresholdKeys::new`: [3](#0-2) 

Downstream, `ThresholdKeys::view` interpolates the *planted* `verification_shares[l]` for `l > t` into the per-signer verification map used by FROST share verification: [4](#0-3) 

and `AlgorithmSignatureMachine::complete` verifies each participant's share against `view.verification_share(l)`: [5](#0-4) 

`recover_key` only cross-checks `t`, `n`, `group_key`, `scalar`, `offset` between keys — the planted `> t` shares are invisible to it: [6](#0-5) 

### Impact Explanation
Like the planted `freepbx_engine`, a participant index `> t` is a "writable slot" the trusted derivation never looks at. A party supplying a keys blob (e.g., a redistributed/tampered DKG output consumed via `ThresholdKeys::read`) can set `verification_shares[l]` for `l > t` to a point with known discrete logarithm (or identity). When participant `l` later joins a signing set, their *invalid* secret share still verifies against the planted verification share, so `verify_share` succeeds while the aggregate `verify` fails — the code itself comments this state means a "semantically invalid FrostKeys" and returns `FrostError::InternalError` instead of an attributable `InvalidShare`: [7](#0-6) 

This yields unblamable signing-failure DoS and incorrect verification data accepted under the honest `group_key` — an incorrect verifier formula analog (share acceptance decoupled from the group's committed polynomial).

### Likelihood Explanation
Requires the victim to deserialize attacker-influenced `ThresholdKeys` bytes rather than keys produced by an honest DKG run — comparable to the report's precondition (a member of a group writing into a directory a privileged process trusts). Within the serialization trust model the primitive is deterministic and trivially constructed: copy honest shares `1..=t`, replace any share `> t`.

### Recommendation
In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[params.i()]`, and when `t < n` either commit to all `n` shares in `group_key` derivation (e.g., verify a hash of the full map against a stored commitment) or document that only indexes `1..=t` are meaningful. `ThresholdKeys::read` should reject `i > n` relative to the group key check.

### Proof of Concept
1. Serialize an honest `ThresholdKeys` with `t < n`; deserialize via `ThresholdKeys::read`, then re-serialize with `verification_shares[t+1]` replaced by `G * x` for attacker-known `x`.
2. `read` succeeds; `group_key()` is unchanged since it only reads shares `1..=t`.
3. Have participant `t+1` sign with share `z = d + e·rho + c·λ·x` using preprocess nonce `R = zG - c·λ·(G·x)`; `verify_share` passes, aggregate `verify` fails → `InternalError` (no blame) instead of `InvalidShare(t+1)`.
