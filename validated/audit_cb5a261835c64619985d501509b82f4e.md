### Title
Bridge Circuit Accepts Equal-Work Watchtower Challenge — Operator on Fork Chain Can Claim Reimbursement - (File: `circuits-lib/src/bridge_circuit/mod.rs`)

### Summary

The bridge circuit's work comparison uses a strict-less-than (`<`) guard, which allows an operator's proof to pass when their total work **equals** the maximum watchtower-submitted work. The protocol documentation and design explicitly require the operator's work to be **strictly greater than** the watchtower's maximum work. This is the direct Clementine analog of the GovernorAlpha `>=` vs `>` threshold mismatch.

### Finding Description

In `circuits-lib/src/bridge_circuit/mod.rs`, the work comparison that guards operator reimbursement is:

```rust
// If total work is less than the max total work of watchtowers, panic
if total_work < max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
``` [1](#0-0) 

The condition `total_work < max_total_work` only panics when the operator's work is **strictly less than** the watchtower's maximum. When `total_work == max_total_work`, the circuit continues and the operator's proof is accepted.

The protocol documentation in `docs/bridge-circuit.md` explicitly states the invariant:

> "Asserts that the Operator's `total_work` from their HCP is **greater than** the `max_total_work` from the Watchtowers." [2](#0-1) 

The same requirement is stated in the module-level docstring:

> "4. **Work Comparison:** Asserts that the operator's claimed work is **greater than** the maximum work submitted by any valid watchtower." [3](#0-2) 

The `TotalWork` type derives `PartialOrd`/`Ord`, so a `<=` check is available and the distinction between `<` and `<=` is meaningful. [4](#0-3) 

### Impact Explanation

The bridge circuit is the ZK proof an operator generates when challenged, to prove their payout transaction is on the canonical Bitcoin chain. The canonical chain is defined by the chain with the most cumulative proof-of-work. When a watchtower submits a valid work-only Groth16 proof (`max_total_work`) equal to the operator's claimed work, the two chains are in a tie — neither is definitively canonical. The operator has **not** proven they are on the canonical chain.

With the current `<` guard, the circuit accepts this tie case and the operator's proof passes. This allows an operator who fronted a withdrawal on a fork chain (not the canonical chain) to successfully generate a valid bridge circuit proof and claim reimbursement from bridge-controlled BTC, resulting in loss of bridged funds.

The `total_work_and_watchtower_flags` function selects the highest Groth16-verified watchtower work as `max_total_work`: [5](#0-4) 

This value is then compared against the operator's HCP total work at line 156. The off-by-one boundary (`<` instead of `<=`) is the root cause.

### Impact

**Critical** — An operator on a fork chain with equal cumulative work to the canonical chain can generate a valid bridge circuit proof, pass the disprove challenge, and claim reimbursement for a payout that was not on the canonical Bitcoin chain. This results in theft of bridged BTC from the bridge vault.

### Likelihood Explanation

Two Bitcoin chains reaching exactly equal total work is an extremely rare event under normal network conditions. However:
1. In a targeted attack, a well-resourced adversary could deliberately mine a competing chain to exactly match the canonical chain's work before submitting a challenge.
2. In regtest/testnet environments (where the bridge is currently parameterized), this is trivially achievable.
3. The spec/implementation mismatch itself is a correctness invariant violation regardless of probability.

### Recommendation

Change the comparison from strict-less-than to less-than-or-equal:

```rust
// Operator's work must be STRICTLY GREATER than max watchtower work
if total_work <= max_total_work {
    panic!(
        "Insufficient total work: operator total_work {total_work:?} must be strictly greater than max watchtower work {max_total_work:?}",
    );
}
```

This aligns the implementation with the documented invariant: the operator must prove their chain has **strictly more** cumulative work than any valid watchtower challenge.

### Proof of Concept

1. Operator fronts a withdrawal on fork chain F with total work W.
2. Watchtower submits a valid work-only Groth16 proof for canonical chain C, also with total work W (equal fork).
3. `total_work_and_watchtower_flags` returns `max_total_work = TotalWork(W)`.
4. Operator's HCP has `total_work = TotalWork(W)`.
5. Check: `W < W` → `false` → circuit does **not** panic.
6. Circuit proceeds, SPV and storage proofs verify against fork chain F.
7. Operator's bridge circuit proof is accepted; disprove fails.
8. Operator claims reimbursement for a payout on the non-canonical chain.
9. Bridge BTC is drained for a withdrawal that was never valid on the canonical chain.
