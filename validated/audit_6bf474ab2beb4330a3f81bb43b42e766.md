### Title
UTF-8 validation is silently skipped for `ctype=CORD` string fields in the tail-call parser fast path - (File: `src/google/protobuf/generated_message_tctable_lite.cc`)

### Summary
The generated tail-call parser (`TcParser`) computes a per-field "transform/validation" tag (`xform_val`) that tells the string-parsing fast path whether UTF-8 must be verified. For `ArenaStringPtr`/`MicroString`-backed fields this tag is honored and `utf8_range::IsStructurallyValid()` is actually invoked. For `absl::Cord`-backed fields (i.e., fields declared with `ctype = CORD`), the dedicated overload `TcParser::MpVerifyUtf8(const absl::Cord&, ...)` never inspects the passed-in `xform_val` for the UTF-8 case — it always returns `true`, silently accepting non-UTF-8 bytes even when the field is tagged as requiring mandatory UTF-8 validation. This mirrors the ZKSwap flaw: a "verification" function exists in the code path and is called, but it never performs the check it is supposed to perform.

### Finding Description
The type card for a field is built in `TailCallTableInfo::MakeTypeCardForField` (`src/google/protobuf/generated_message_tctable_gen.cc`). For `TYPE_STRING` fields, the UTF-8 requirement is encoded independently of storage representation: [1](#0-0) 

The storage representation (Cord vs. ArenaStringPtr vs. MicroString) is OR'd into a separate bit range of the same 16-bit `type_card`: [2](#0-1) 

Because `kTvUtf8` (Tv bit field) and `kRepCord` (Rep bit field) occupy disjoint bit ranges, a field that is both strictly UTF-8-checked (`utf8_check_mode == kStrict`, e.g. a proto3 `string` field or a field with `features.utf8_validation = MANDATORY`) and stored as `absl::Cord` (`ctype = CORD`) ends up with `xform_val == field_layout::kTvUtf8` **and** `rep == field_layout::kRepCord` simultaneously.

At parse time, `TcParser::MpString` dispatches on `rep` and, for the Cord case, calls the Cord overload of `MpVerifyUtf8` with that `xform_val`: [3](#0-2) 

But the Cord overload of `MpVerifyUtf8` performs no actual validation for any value of `xform_val`; it merely asserts (in debug builds only) that `xform_val` is `0`, then unconditionally returns `true`: [4](#0-3) 

Contrast this with the `absl::string_view` overload used for `ArenaStringPtr`/`MicroString`, which correctly checks `xform_val == field_layout::kTvUtf8` and calls `utf8_range::IsStructurallyValid`: [5](#0-4) 

`ABSL_DCHECK_EQ` compiles to a no-op in `NDEBUG`/release builds — the build mode used in virtually all production deployments — so in production the assertion never fires and the function simply returns `true` regardless of whether `xform_val` was `kTvUtf8`. The "verifier" is present and is called on the wire path but never verifies.

### Impact Explanation
Protobuf's core, documented invariant is that `string` fields (proto3, or edition fields with `features.string_field_validation = MANDATORY`) contain structurally valid UTF-8 after a successful parse; consuming application code is entitled to rely on this without re-validating. For messages where such a field is declared with `ctype = CORD`, an attacker sending an ordinary, well-formed (length-correct) Protobuf binary payload through a public `ParseFrom*`/`MergeFrom*` API can smuggle arbitrary invalid UTF-8 byte sequences into that field, and the parse will still report success. Downstream code that assumes UTF-8 validity (e.g., text/HTML/log/SQL emission, string-length or codepoint-based security checks, cross-language boundary crossings) can then be fed malformed byte sequences, producing integrity violations or enabling downstream parsing-differential/injection issues in the consuming application — a direct analog to ZKSwap's core guarantee ("only valid proofs are accepted") being silently bypassed by a stub verifier.

### Likelihood Explanation
This requires only two ordinary, attacker-independent preconditions on the trusted schema: (1) a proto3 `string` field (or edition field with mandatory UTF-8 validation) that (2) also has the `ctype = CORD` field option. This is a legitimate, supported, non-exotic schema configuration (Cord is a first-class supported string representation, `kRepCord` is handled throughout the codebase, e.g. `TcParser::InitOneof`'s Cord branch: [6](#0-5) ). No malformed schema, no unusual build flags, and no privileged access are needed — only an ordinary bounded binary payload through the public parse API, matching the report's attacker model exactly. The bug is masked in debug builds by the `DCHECK`, which likely explains why it has not been caught by non-fuzzing functional tests that typically run instrumented/debug builds, while release builds used in production silently accept the invalid data.

### Recommendation
Fix `TcParser::MpVerifyUtf8(const absl::Cord&, ...)` to actually branch on `xform_val` the same way the `absl::string_view` overload does, validating the flattened/iterated Cord bytes with `utf8_range::IsStructurallyValid` (or an equivalent Cord-chunk-aware UTF-8 validator such as the `IsViewValidUTF8WithLeftover` logic already present in `parse_context.cc`) whenever `xform_val == field_layout::kTvUtf8`, and returning `false` (triggering the existing `Error()` path in `MpString`/`MpRepeatedString`) on invalid input, instead of relying on a debug-only `DCHECK`.

### Proof of Concept
1. Define a proto3 message with a `ctype = CORD` string field, e.g.:
   ```proto
   syntax = "proto3";
   message M { string s = 1 [ctype = CORD]; }
   ```
   This produces a type card where `type_card & kTvMask == kTvUtf8` and `type_card & kRepMask == kRepCord` per `MakeTypeCardForField` (`generated_message_tctable_gen.cc:604-665`).
2. Build the generated code in release mode (`NDEBUG` defined, the standard production configuration).
3. Encode a length-delimited field 1 with wire-valid but structurally-invalid UTF-8 bytes, e.g. tag `0x0A`, length `0x01`, payload byte `0xFF` (an invalid UTF-8 lead byte).
4. Call `M::ParseFromString(payload)` (or any public `ParseFrom*` entry point) via `TcParser`'s fast path, which dispatches to `MpString` → `kRepCord` case → `MpVerifyUtf8(const absl::Cord&, table, entry, kTvUtf8)`.
5. Because that overload's `switch` has no case for `kTvUtf8` and its `default` unconditionally `return true;` (with the `ABSL_DCHECK_EQ` stripped out under `NDEBUG`), parsing succeeds (`ParseFromString` returns `true`) and `M.s()` yields the invalid-UTF-8 byte `0xFF`, even though the field is a proto3 string that is supposed to guarantee valid UTF-8 — confirmed by direct code inspection of `generated_message_tctable_lite.cc:2516-2524` versus the correct `string_view` implementation at `2503-2515`. (No test execution was performed here; this is a static-analysis-confirmed code-path trace, not a run test result.)

bool TcParser::MpVerifyUtf8(absl::string_view wire_bytes,
                            const TcParseTableBase* table,
                            const FieldEntry& entry, uint16_t xform_val) {
  if (xform_val == field_layout::kTvUtf8) {
    if (!utf8_range::IsStructurallyValid(wire_bytes)) {
      PrintUTF8ErrorLog(MessageName(table), FieldName(table, &entry), "parsing",
                        false);
      return false;
    }
    return true;
  }
  return true;
}
