### Title
Suspended validators keep earning staking rewards despite being excluded from committee/consensus duty - (kaiax/valset/types.go, kaiax/staking/impl/getter.go, kaiax/reward/impl/getter.go)

### Summary
The reward-eligibility check used to build `StakingInfo` (which feeds staking-reward distribution) only inspects a node's `State` field and ignores the `Suspended` flag that separately gates consensus committee participation. A validator that is `ValActive` but `Suspended` (excluded from signing/proposing blocks) is therefore still counted as reward-eligible and continues to receive staking rewards every block, mirroring the reported bug class where a "blacklisted" entity keeps generating rewards because the reward bookkeeping path does not consult the same exclusion flag used to gate its actual duties.

### Finding Description
`NodeState.IsRewardEligible()` determines reward eligibility purely from the on-chain `State` enum: [1](#0-0) 

Meanwhile, consensus committee membership additionally excludes suspended nodes: [2](#0-1) 

The `Suspended` flag is a separate, orthogonal piece of state (set via `MarkSuspended`, consumed only by `ExcludeSuspended`/`Committee()`): [3](#0-2) 

However, `parsePermissionlessCallResult`, which builds the `StakingInfo` consumed by the reward module, filters candidate nodes solely by `IsRewardEligible()` on the AddressBook-reported `State` — it never consults or receives the `Suspended` flag at all: [4](#0-3) 

The resulting `StakingInfo.NodeIds/StakingAmounts` (including suspended-but-`ValActive` nodes) then flow unfiltered into `assignStakingRewards`/`assignStakingRewardsFlex` via `si.ConsolidatedNodes()`, which distribute staking rewards purely by stake amount, again with no suspension check: [5](#0-4) [6](#0-5) 

This is structurally identical to the reported bug: the exclusion condition (`isBlacklisted` in the report, `Suspended` here) is checked for one purpose (whether the entity participates — deposits in the report, committee/signing here) but is never re-checked before the reward/price-accrual step (`storePriceAndRewards` in the report, `assignStakingRewards`/`GetStakingInfo` here), so the excluded entity keeps accruing value.

### Impact Explanation
A validator that has been suspended — i.e., deliberately removed from block-signing/proposing duties, presumably due to misbehavior or a protocol-level penalty mechanism — continues to receive its full share of staking rewards every block for as long as it remains `ValActive` with sufficient stake. This is a reward-redirection/unauthorized-value-accrual bug: value (KAIA minting rewards) keeps flowing to a node that the protocol has decided should not participate, undermining the incentive/penalty design of the validator lifecycle system and diverging from the intended semantics of "suspension."

### Likelihood Explanation
This triggers automatically and deterministically on every block for as long as any validator is in the `Suspended` state — no attacker action, transaction, or special call is required. Because `FinalizeState` calls `GetDeferredReward` → `assignStakingRewards`/`Flex` on every block via the normal block-assembly/reward-distribution path, the flawed reward computation happens unconditionally whenever the `Suspended` mechanism is engaged, making this a persistent state-divergence/reward-leak condition rather than a rare edge case.

### Recommendation
Propagate the `Suspended` status into the reward-eligibility path: either (a) have `parsePermissionlessCallResult` receive and honor per-node suspension status when filtering `IsRewardEligible` nodes, or (b) have `assignStakingRewards`/`assignStakingRewardsFlex` exclude suspended reward addresses from the `ConsolidatedNodes()` staking-reward split before rewards are computed, consistent with how `Committee()` already excludes them from consensus duty.

### Proof of Concept
1. A validator `V` is `ValActive` and staked above `minStake`.
2. `V` is marked `Suspended` via `NodeMap.MarkSuspended` (e.g., due to a detected violation), removing it from `Committee()` and therefore from block signing/proposing.
3. On the next block, `kaiax/staking/impl/getter.go`'s `GetStakingInfo` (via `parsePermissionlessCallResult`) still includes `V` in `NodeIds`/`StakingAmounts` because its `State` remains `ValActive` and `IsRewardEligible()` returns true.
4. `kaiax/reward/impl/getter.go`'s `assignStakingRewards` (or the Flex variant) computes `V`'s excess stake and allocates it a proportional share of the staking reward budget, crediited in `FinalizeState`'s `state.AddBalance` loop.
5. `V` keeps earning staking rewards block after block despite being excluded from all consensus responsibilities, exactly analogous to the reported "blacklisted protocol keeps generating rewards" issue.

Note: I could not fully verify the exact producer/trigger of the `Suspended` flag (e.g., which violation-detection logic in `kaiax/vrank` or `transition_context.go` sets it) within the available index; the code confirms the flag exists and is excluded from `Committee()` but is never consulted by the staking/reward eligibility path. A Devin session with full repository access would be needed to confirm the full lifecycle of `Suspended` and validate a fix end-to-end.

// MarkSuspended sets the Suspended flag on nodes whose address is in the given list.
// Mutates the receiver in place; the only in-place mutator on NodeMap.
func (v NodeMap) MarkSuspended(suspended []common.Address) {
	set := make(map[common.Address]struct{}, len(suspended))
	for _, addr := range suspended {
		set[addr] = struct{}{}
	}
	for addr, vs := range v {
		_, vs.Suspended = set[addr]
	}
}

// ExcludeSuspended returns a new NodeMap without suspended nodes.
func (v NodeMap) ExcludeSuspended() NodeMap {
	filtered := make(NodeMap, len(v))
	for addr, val := range v {
		if !val.Suspended {
			filtered[addr] = val
		}
	}
	return filtered
}

// assignStakingRewardsFlex assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewardsFlex(config *reward.RewardConfig, budget *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		minStake  = config.MinimumStake.Uint64()
		threshold = config.StakingRewardThreshold.Uint64()
		isPrague  = config.Rules.IsPrague

		cns            = si.ConsolidatedNodes()
		excessInt      = make(map[common.Address]uint64)
		totalExcessInt = uint64(0)
	)

	// Calculate the excess stakes (the amount over the threshold) for each CN.
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it. Even if (CNStaking + CLStaking) could be more than minStake,
		// the CNStaking alone must be at least minStake to be eligible.
		if cn.StakingAmount < minStake {
			continue
		}

		amount := cn.StakingAmount
		if isPrague && cn.CLStakingInfo != nil {
			amount += cn.CLStakingInfo.CLStakingAmount
		}

		// Excess is the amount over the threshold (not over minStake).
		if amount > threshold {
			excessInt[cn.RewardAddr] = amount - threshold
			totalExcessInt += excessInt[cn.RewardAddr]
		}
	}
