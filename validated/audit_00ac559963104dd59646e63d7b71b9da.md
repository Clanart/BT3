### Title
BIP-340 signature shares never negate the key term for odd-Y group keys, producing invalid signatures that leave received funds unspendable - ([File: networks/bitcoin/src/crypto.rs])

### Summary
Analogous to the funding-fee finding — where a value that needed to be signed in either direction was computed unsigned so one side was always credited instead of charged — the Bitcoin `Schnorr` algorithm applies the secret-key contribution with a fixed positive polarity. `Hram::hram` conditionally negates the challenge only for the nonce `R`'s parity (`needs_negation(R)`), and `verify` negates `s` only for `R`'s parity (`networks/bitcoin/src/crypto.rs:72,146`). Nothing ever accounts for the parity of the group key `A`. Under BIP-340 the public key is x-only, i.e. bound to the even-Y lift `P`; when the actual (possibly offset) group key `A` has odd Y, the correct signing equation is `s·G = R + c·(−A)`, which requires the `c·x` term to be effectively negated. It never is.

### Finding Description
`Schnorr::sign_share` delegates to `IetfSchnorr::sign_share`, which computes `SchnorrSignature::sign(secret_share, nonce, c)` = `s_i = r_i + c·x_i` (`crypto/frost/src/algorithm.rs:201-211`, `crypto/schnorr/src/lib.rs:74-84`). The challenge `c` comes from `Hram::hram`, which returns `-c` only when `R` has odd Y (`crypto.rs:59-73`). `verify` then emits `s = ±sum` again keyed solely on `needs_negation(&sig.R)` (`crypto.rs:145-149`). There is no `needs_negation(A)` / `needs_negation(group_key)` path anywhere: a secret share summing to an odd-Y group key is used as `+x` regardless, so the aggregated `s·G = R + c·A` instead of `R + c·P` with `P = −A`. The same wrong-polarity signature is produced for every offset key used by `SignableTransaction::multisig`, which only checks `p2tr_script_buf(offset.group_key()) == prevout.script_pubkey` — an x-only comparison that passes whether the key is even or odd (`send.rs:273-285`).

### Impact Explanation
For any input whose `group_key + offset` point has odd Y (≈50% of offset-registered outputs, change/branch/deposit addresses), the threshold produces a signature that fails BIP-340 verification: `s·G = R + c·A ≠ R + c·P`. The witness is invalid, the spend can never confirm, and `Scanner`/`ReceivedOutput` still reports the output as owned — funds are reported received that are not spendable. This is directly reachable by an unprivileged depositor paying to a Serai-derived x-only address.

### Likelihood Explanation
Parity is essentially random per key/offset, so roughly half of all distinct key/offset combinations are affected. Any `Scanner`-registered offset producing an odd-Y point yields an unspendable output. The internal `verify`/`verify_share` checks don't catch it because they verify shares against the same raw `A`/`c` the signers used, not the even-Y BIP-340 key.

### Recommendation
Apply the key-parity negation symmetric to the nonce-parity negation: in `Hram::hram` (or in `sign_share`), negate the challenge — equivalently the effective secret — when `needs_negation(A)` is set, so shares sign `r + (−c)·x = r + c·(−x)`. Concretely, combine both conditions, e.g. `conditional_select(&c, &-c, needs_negation(R) ^ needs_negation(A))` with the `s` correction in `verify` kept consistent, or normalize the secret share by `−1` when the group key is odd before calling `SchnorrSignature::sign`.

### Proof of Concept
1. Pick `ThresholdKeys<Secp256k1>` whose `group_key()` (or `keys.offset(o).group_key()` for a `Scanner`-registered `o`) has odd Y.
2. Build a `SignableTransaction` spending a prevout whose `script_pubkey` is `p2tr_script_buf(odd_key)`; `multisig(&keys)` accepts since the x-only comparison ignores parity.
3. Run `preprocess`/`sign`/`complete` with an honest threshold signing set; each share is `r_i + c·x_i` with `Σx_i = x`, `x·G = A` odd.
4. `verify` emits `s` (R-parity-negated) serialized as a 64-byte BIP-340 signature. Bitcoin's verifier computes `P = lift_x(x(A)) = −A` and checks `s·G = R_even + c·P`; the produced signature satisfies `s·G = R_even + c·A` instead, so it is unconditionally rejected and the prevout can never be spent.
