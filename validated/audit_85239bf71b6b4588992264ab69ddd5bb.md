Based on my investigation, I found a genuine analog of this bug class in the Kaia reward distribution code.

### Title
Division by zero in `consolidatedNode.Split` can halt block finalization when a validator's CN and CL staking amounts are both zero - (File: kaiax/staking/staking_info.go)

### Summary
The `consolidatedNode.Split` function divides a reward amount by `totalAmount = StakingAmount + CLStakingAmount` without checking for zero, analogous to the GoGoPool `distributeMultisigAllotment` bug where dividing by `enabledCount` panics when it is zero.

### Finding Description
`consolidatedNode.Split` computes the CN/CL reward split as: [1](#0-0) 
When `c.CLStakingInfo != nil`, it unconditionally divides by `totalAmount = cnAmountBig + clAmountBig` with no zero-check. This function is invoked from the reward-assignment paths in `getter.go` (`assignStakingRewardsFlex`, `assignStakingRewards`, `specWithProposerAndFundsFlex`, `specWithProposerAndFunds`) whenever a consolidated node both passes the minimum-stake eligibility check and has a non-nil `CLStakingInfo`: [2](#0-1) 
The eligibility check compares against `config.MinimumStake` (the `reward.minstake` governance parameter). If this governance parameter is configured/voted to `0`, a validator whose `CNStaking` amount is `0` still satisfies `cnTotalStakingAmount >= minStake` (`0 >= 0`). If that same validator also has a `CLStakingInfo` entry with `CLStakingAmount == 0` (e.g., a CL pool registered but with zero staked liquidity), then `totalAmount` becomes `big.NewInt(0)`, and `clAmount.Div(clAmount, totalAmount)` panics with a division-by-zero error, exactly mirroring the `RewardsPool.distributeMultisigAllotment` division-by-zero in the referenced GoGoPool finding.

This is reachable during ordinary `FinalizeState()` deferred-reward block processing — every block must call `GetDeferredReward` → `getDeferredRewardFullKore`/`getDeferredRewardFullFlex` → `assignStakingRewards`/`assignStakingRewardsFlex` → `specWithProposerAndFunds(Flex)`. No attacker-controlled transaction is strictly required; the "attacker" input here is a governance-parameter configuration (`reward.minstake = 0`) combined with the registration of a CL pool with zero stake, both of which are governed by protocol/governance configuration rather than direct EVM transactions.

### Impact Explanation
If triggered, this panics the node during block finalization (`FinalizeState`), which — unlike the Solidity `revert` in the original finding that merely blocks one transaction — would crash/halt the Go node process attempting to finalize the block, causing a chain-halting or node-crashing condition across all nodes processing that block. This is more severe than the original Medium-severity Solidity finding since it affects core state-transition logic reachable on every block, not an isolated function call that can simply be retried later.

### Likelihood Explanation
Likelihood is constrained by two governance-level preconditions: `reward.minstake` must be `0` (unusual but technically valid per `NewRewardConfig`/`paramset.MinimumStake`, no validation against zero was found), and a validator must be registered as a Consolidated Node with `StakingAmount == 0` and an associated `CLStakingInfo` with `CLStakingAmount == 0`. I was not able to verify within the available index whether CL registration flow (`CLRegistry`, `kaiax/staking` CL info collection) enforces a strictly-positive minimum for `CLStakingAmount`, so it's uncertain whether the zero-CL-stake precondition is actually reachable in practice. Since this requires specific governance configuration and CL registration states that I could not fully confirm are attacker/governance-reachable without additional review of the CL staking/registry contracts, I present this with the caveat that the precondition validation could not be fully confirmed from the indexed code.

### Recommendation
Add a zero-check guard in `consolidatedNode.Split` before performing the division — e.g., if `totalAmount.Sign() == 0`, return `(amount, big.NewInt(0))` (all to CN) or `(big.NewInt(0), big.NewInt(0))`, avoiding the panic regardless of upstream eligibility-check assumptions. Additionally, confirm/enforce that `reward.minstake` governance parameter cannot be set to `0` in combination with CL registrations allowing zero stake, or add an explicit `totalAmount > 0` condition to the CN eligibility check in `assignStakingRewards`/`assignStakingRewardsFlex` before calling `cn.Split`.

### Proof of Concept
Conceptual reproduction (unverified in a live test environment, could not run Go tests in ask-only mode):
1. Set governance parameter `reward.minstake = 0`.
2. Register a validator in AddressBook with `StakingAmount = 0`.
3. Register a `CLStakingInfo` for that validator's node with `CLStakingAmount = 0` (via CL registry — precondition not fully verified as reachable).
4. On block finalization, `assignStakingRewards` (or its Flex variant) includes this node since `cnTotalStakingAmount (0) >= minStake (0)`, and calls `cn.Split(reward)` in [2](#0-1) , which invokes `consolidatedNode.Split` in [1](#0-0) , dividing by `totalAmount = 0`, causing a `big.Int` division-by-zero panic during state finalization.

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```
