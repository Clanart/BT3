## Title
Single unprivileged WebSocket client can exhaust the entire global RPC PubSub subscription pool, denying subscription service to all other clients - (File: `rpc/src/rpc_subscription_tracker.rs`)

## Summary
The external report describes a wallet DoS where an unbounded, unauthenticated call (`signMessage`) could be invoked repeatedly by a single caller with no per-caller quota, exhausting shared resources and crashing the extension/browser for everyone. The Agave analog is `rpc/src/rpc_subscription_tracker.rs`'s `SubscriptionControl::subscribe`, which enforces only a single **global** cap (`max_active_subscriptions`, default `1_000_000`) via `SubscriberCountGuard::try_reserve`, with no per-connection, per-IP, or per-client quota. A single unprivileged WebSocket client can therefore issue enough `accountSubscribe`/`logsSubscribe`/`programSubscribe`/`signatureSubscribe` requests (each with unique params to avoid dedup) over one connection to consume the entire global subscription budget, denying the RPC PubSub service to all other legitimate clients on that node.

## Finding Description
`rpc/src/rpc_pubsub_service.rs`'s `handle_connection` accepts any TCP client and, for every parsed JSON-RPC request, calls into `RpcSolPubSubImpl::subscribe` (`rpc/src/rpc_pubsub.rs:380-393`), which calls `SubscriptionControl::subscribe`: [1](#0-0) 

`SubscriptionControl::subscribe` reserves a slot from a single shared counter bounded only by `config.max_active_subscriptions`: [2](#0-1) 

The reservation logic (`SubscriberCountGuard::try_reserve`) checks against `max_active_subscriptions` globally — there is no dimension of the check tied to the connection, socket address, or any per-client identity: [3](#0-2) 

The default value of this global cap is very large (`1_000_000`), explicitly intended to be shared "across all connections": [4](#0-3) [5](#0-4) 

Because subscriptions are keyed by `SubscriptionParams` (pubkey, filters, encoding, commitment, etc.), a single connection trivially avoids dedup by varying the pubkey/filter on each call (e.g., `accountSubscribe` for a large number of distinct random pubkeys, or `programSubscribe`/`logsSubscribe` with varied filters). Each such call consumes one slot from the shared 1,000,000-slot pool via its own `SubscriberCountGuard`, as confirmed by the test explicitly documenting that "duplicate subscribes to the same params each consume their own slot": [2](#0-1) [6](#0-5) 

There is no per-connection or per-IP ceiling anywhere in the pubsub service or its connection handler (`handle_connection` in `rpc/src/rpc_pubsub_service.rs:349-427`) that would stop one client from claiming an arbitrarily large fraction — up to all — of the global cap. Once the pool is saturated, every other client's subscribe attempts fail with `TooManySubscriptions` (mapped to a generic `InternalError` in `rpc_pubsub.rs:384-389`), effectively denying the PubSub service to legitimate users, exactly mirroring the wallet report's pattern: an exposed, individually-cheap operation with no rate/quota limit per caller that, when invoked repeatedly, exhausts a resource shared by all users of the service.

## Impact Explanation
This is a non-RPC-crash but RPC-service-denial condition reachable by a single, unprivileged WebSocket client at a low per-request cost (no special access, no malicious peer/validator assumption, no trusted plugin). It degrades/denies the RPC PubSub subscription service for all other clients connected to the same validator/RPC node, which qualifies under "single-client low-rate RPC crash/degradation" and "non-RPC remote exhaustion" categories of valid impact, since it disables a node capability (subscriptions) for every other consumer without requiring privileged access.

## Likelihood Explanation
The path requires only opening one WebSocket connection to the public RPC PubSub port and sending a sequence of ordinary, publicly-documented subscribe RPC calls (`accountSubscribe`, `programSubscribe`, `logsSubscribe`, `signatureSubscribe`) with varied parameters — no authentication, no elevated privileges, and no race condition needed. The mechanism is deterministic: the global counter monotonically fills as requests succeed, and there is no code path that limits how much of that counter a single connection may claim.

## Recommendation
Add a per-connection (and/or per-IP) subscription quota, separate from and smaller than the global `max_active_subscriptions` cap, enforced in `SubscriptionControl::subscribe` or in `handle_connection`/`RpcSolPubSubImpl`, so that a single client cannot claim a disproportionate share of the shared subscription pool. Consider also rate-limiting subscribe requests per connection to slow rapid slot exhaustion attempts.

## Proof of Concept
1. Configure/run an `agave-validator` with default `--rpc-pubsub-max-active-subscriptions` (1,000,000).
2. From a single unauthenticated WebSocket client connection to the pubsub port, loop sending `accountSubscribe` requests, each with a freshly generated random `Pubkey` string as the parameter (to avoid `SubscriptionParams` dedup), until the client accumulates a very large number of successful subscriptions (or up to the configured cap).
3. From a second, independent client, attempt any subscribe call (e.g., `slotSubscribe`); once the global pool is exhausted, this call fails with `TooManySubscriptions` → `InternalError` ("Node subscription limit reached"), demonstrating denial of the PubSub subscription service to legitimate clients due to one client's unthrottled subscription flood.

```rust
// RAII guard for one subscriber slot. The slot is reserved atomically against
// the configured cap by `try_reserve` (returns `None` if the cap is reached)
// and released on drop. Intentionally not `Clone`: each holder must go through
// `try_reserve` so duplicates cannot bypass the cap.
struct SubscriberCountGuard(Arc<SubscriptionControlInner>);

impl SubscriberCountGuard {
    fn try_reserve(control: &Arc<SubscriptionControlInner>) -> Option<Self> {
        let max = control.max_active_subscriptions;
        control
            .subscriber_count
            .fetch_update(Ordering::Relaxed, Ordering::Relaxed, |current| {
                (current < max).then_some(current + 1)
            })
            .ok()?;
        Some(Self(Arc::clone(control)))
    }
}
```

    fn duplicate_params_consume_separate_subscriber_slots() {
        // Cap of 1 must reject a second subscriber even when params match an
        // existing subscription (GHSA: duplicate-params cap bypass).
        let (sender, _receiver) = bounded(1024);
        let (broadcast_sender, _broadcast_receiver) = broadcast::channel(42);

        let token1 = control.subscribe(SubscriptionParams::Slot).unwrap();
        assert_eq!(control.total(), 1);
        assert_eq!(control.subscriber_total(), 1);

        assert!(matches!(
            control.subscribe(SubscriptionParams::Slot),
            Err(Error::TooManySubscriptions)
        ));
        assert_eq!(control.subscriber_total(), 1);

        drop(token1);
        // After the only holder drops, a fresh subscriber should fit again.
        let token2 = control.subscribe(SubscriptionParams::Slot).unwrap();
        assert_eq!(control.subscriber_total(), 1);
        drop(token2);
