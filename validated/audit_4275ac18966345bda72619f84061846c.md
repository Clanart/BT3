### Title
Weight/fee estimation omits the `OP_RETURN` data output, so a `SignableTransaction` can pass the `MAX_STANDARD_TX_WEIGHT` check and under-fund its fee, producing a transaction that cannot be relayed and whose inputs are locked pending manual re-signing - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` computes the transaction weight and virtual size from only `inputs`, `payments`, and the optional `change` output. The `OP_RETURN` data output — which is appended to `tx_outs` *before* the weight calculation — is never included in `calculate_weight_vbytes`. The result is used both to size `needed_fee` and to enforce `weight > MAX_STANDARD_TX_WEIGHT`. A transaction carrying a data payload therefore weighs more and is larger than what was validated, mirroring the reported bug class: a fixed/incorrectly bounded resource (gas limit ↔ weight/vbyte accounting) lets an operation be treated as valid at construction time and only fail at publish time, with recovery requiring a fresh signing round.

### Finding Description
`tx_outs` gains the data output at `send.rs:194-202`:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data).expect("...")),
  })
}
```

but `calculate_weight_vbytes` is invoked with `payments` (which excludes `data`) at `send.rs:204` and `send.rs:226`:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
...
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
```

The final transaction (constructed at `send.rs:246-251`) contains `tx_outs` — payments + `OP_RETURN` + change — while `weight`, `vbytes`, and `needed_fee` were derived from a strictly smaller output set. The discrepancy is up to ~83 bytes of script pubkey plus the output count/varint overhead (~340–360 additional weight units) per data output.

### Impact Explanation
Two concrete consequences follow:

1. **Standardness check is bypassed.** The `weight > MAX_STANDARD_TX_WEIGHT` check at `send.rs:241` uses the under-counted weight. A transaction that is just under 400,000 WU after accounting but over it once the `OP_RETURN` output is included will be constructed, signed by the FROST `TransactionMachine` (which commits the real transaction via `taproot_key_spend_signature_hash` over `Prevouts::All`), and then rejected by Bitcoin Core's standardness policy. The signed inputs remain unspent — analogous to the destination call failing under a fixed gas limit — and recovery requires the multisig to re-run preprocessing/signing on a corrected transaction (the manual `retryMessageExecution` analog).

2. **Fee rate is under-funded.** `needed_fee = fee_per_vbyte * vbytes` uses the smaller vbytes. The actual published transaction is larger, so its effective feerate is lower than requested and can silently drop below `DEFAULT_MIN_RELAY_TX_FEE` even though the `TooLowFee` check passed — again producing a transaction that cannot enter the mempool despite passing all validation.

An external user controls the `data` field (the `InInstruction`/refund metadata pathway in Serai), so the payload length — the only missing term — is attacker-influenced.

### Likelihood Explanation
Triggering the standardness bound requires a near-maximum-size transaction (many inputs/outputs, reachable under the `MAX_INPUTS`/`MAX_OUTPUTS = 520` scheduling bound in the processor) combined with a maximal 80-byte data output. The fee under-payment variant only needs a transaction whose feerate margin is within ~360 WU of the relay minimum — modest, but only harmful when the operator requests a near-minimum feerate. Funds are not stolen; they are delayed/locked until a correct transaction is re-signed, matching the report's manual-recovery model. Medium-to-low likelihood, Medium impact (liveness of funds, wasted threshold signing rounds).

### Recommendation
Pass the full output set into `calculate_weight_vbytes`. Either:
- construct a `payments`-style slice that includes the `OP_RETURN` script (e.g. push `TxOut`s, then compute weight over the real `tx_outs` vector plus a synthetic change when applicable), or
- add `data.len()` (plus output-size constants: 8-byte value, varint lengths, compact-size count delta) to the weight/vbyte calculation before computing `needed_fee` and before the `MAX_STANDARD_TX_WEIGHT` comparison.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Build a transaction whose accounted weight is just under the limit,
// then attach an 80-byte OP_RETURN.
let payments: Vec<(ScriptBuf, u64)> = /* ~520 outputs sized so
    weight(inputs, payments, change) == MAX_STANDARD_TX_WEIGHT - 1 */;
let data = Some(vec![0u8; 80]);

let stx = SignableTransaction::new(inputs, &payments, change, data, fee_per_vbyte)?;
// Passes: `weight` never counted the OP_RETURN output (~+350 WU).
// The real tx.output includes it:
assert!(stx.transaction().output.len() == payments.len() + 2);
// tx.weight() > MAX_STANDARD_TX_WEIGHT → rejected as nonstandard on broadcast,
// yet FROST shares were already consumed signing it.
```

Note on scope: within `crypto/*` and `networks/bitcoin/src` this is the only place where a resource bound is computed against a different object than the one actually signed/published. Other fixed limits in `send.rs` (`DUST`, 80-byte `TooMuchData`, `TooLowFee`, `NotEnoughFunds`) all return explicit errors rather than failing silently, so they are not analogs.
