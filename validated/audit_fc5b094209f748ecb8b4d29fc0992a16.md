### Title
A single attacker-controlled dust payment poisons construction of the entire spend transaction, permanently stalling the batch - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` in `bitcoin-serai`'s wallet validates every payment in a batch and returns `TransactionError::DustPayment` if any single payment is below the dust threshold. Rather than dropping or flagging the offending payment, the error aborts construction of the entire transaction — identical in shape to the Lombard finding where one failing `processReceipt` bubbled up and stalled `processBatch`. An unprivileged user who can request a withdrawal of a dust (or zero) amount injects a poison pill into the payment set; every subsequent attempt to build the transaction deterministically fails, so the batch is retried forever and no payment in it is ever executed.

### Finding Description
In `SignableTransaction::new`, all caller-supplied payments are iterated and a single invalid one fails the whole call:

```rust
// networks/bitcoin/src/wallet/send.rs:165-169
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```

`DUST` is a fixed constant (`Amount::from_sat(546)`-class relay limit), and `payments` is the untrusted, user-facing set of withdrawals the transaction is meant to satisfy. The same poisoning applies to `TransactionError::TooMuchData` at `send.rs:171-173` for `data.len() > 80`.

The downstream consequence mirrors the external report: the processor's signing flow calls `network.attempt_sign(keys, tx)` which internally constructs this transaction; on error it logs and returns `None` without completing or skipping the item (see `processor/src/signer.rs:435-439` — error → `return None`, leaving the signable entry in place). Because the failing payment is never removed, the next attempt re-runs `SignableTransaction::new` over the identical `payments` set, hits the same `DustPayment` error, and stalls again — an infinite retry loop on a poisoned batch, exactly the "stuck processing this batch" condition in the original report.

There is also a related arithmetic landmine in the same function: `input_sat` is computed as an unchecked `sum::<u64>()` over `input.output.value` at `send.rs:175`; combined with the batch-abort behavior, any untrusted path that can place a malformed `ReceivedOutput` (e.g., via `ReceivedOutput::read` at `wallet/mod.rs:122-134`, which performs no sanity check that the declared `output`/offset correspond to a real scanned output) into the input set aborts construction for the whole transaction.

### Impact Explanation
A single dust withdrawal request bricks the entire batched Bitcoin transaction: all other users' payments in that batch are never signed or broadcast, and the processor retries the same construction indefinitely. This is a permanent availability failure of the withdrawal pipeline reachable by any unprivileged party able to request a payout — no validator, collusion, or key material required. This is the strongest reachable analog of the "one bad item DoSes the whole batch" class in the in-scope crates.

### Likelihood Explanation
Withdrawal/payment requests originate from untrusted users by design. Dust or sub-dust amounts are trivially requested (and can even occur accidentally), so the trigger requires no privilege and no race — the failure is deterministic for any `payments` set containing one amount `< DUST`. The only mitigating factor is whether an upstream component filters dust payments before assembling the batch; if it does not (or a new payment path bypasses the filter), the stall is guaranteed and self-perpetuating since the offending payment is never dropped.

### Recommendation
- Do not fail the whole transaction on an invalid payment. Filter payments `< DUST` out of the set (and emit a warning/event) so the rest of the batch proceeds, mirroring the Lombard fix (log-and-continue instead of bubbling an error).
- Alternatively, reject dust at the point payments are admitted into the batch (per-item validation with per-item rejection), never at transaction construction time.
- Apply the same treatment to `TooMuchData` and bound-check `input_sat`/`fee` arithmetic so one bad input cannot abort construction.

### Proof of Concept
1. Attacker requests a withdrawal of, e.g., 500 sats (< `DUST`) alongside legitimate payments in the same batch.
2. The processor calls `attempt_sign` → `SignableTransaction::new(inputs, payments, ...)`.
3. The loop at `send.rs:165-169` hits the 500-sat payment and returns `Err(TransactionError::DustPayment)` before any `tx_ins`/outputs are built.
4. `signer.rs:435-439` logs the error and returns `None`; the signable transaction remains queued. Every re-attempt replays steps 2–3 on the unchanged payment set → permanent stall; no output is ever produced for any payment in the batch.

Minimal reproduction of the poisoning primitive (in-scope code only):

```rust
// One dust payment fails construction for all payments
let payments = vec![
  (legit_script_1, Amount::from_sat(100_000)),
  (attacker_script, Amount::from_sat(500)), // < DUST
];
let res = SignableTransaction::new(inputs, payments, Some(change), None, fee);
assert_eq!(res.unwrap_err(), TransactionError::DustPayment); // whole batch aborted
```

Confidence note: the exact upstream admission path for payments lives in out-of-scope processor code; the analysis assumes payments reach `SignableTransaction::new` without prior dust filtering, which is consistent with the validation living inside `send.rs` itself rather than at the boundary.
