## Analysis

The reported bug class — an ERC20 blacklist causing an unrecoverable revert when a beneficiary receives a payout mid-settlement — has a direct, structurally proven analog in Hyperbridge's `IntentGatewayV2`/`ExtrinsicIntents` escrow-withdrawal path.

### Title
Permanent lock of escrowed order funds when a blacklist-enabled ERC20 refuses transfer to the order beneficiary during `_withdraw`/`withdraw` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentsBase._withdraw` (mirrored by `IntentGatewayV2.withdraw` on the Tron/legacy variant) is the single function that releases escrowed input tokens back to a beneficiary — either the solver (on fill/`RedeemEscrow`) or the original order user (on cancel/`RefundEscrow`). It performs a direct `IERC20.safeTransfer`/low-level `transfer` call to `beneficiary` with no fallback path. If the input token has a blacklist feature (USDC, USDT, etc.) and the beneficiary is on that blacklist, the transfer reverts, and because the ISMP host deletes the request receipt on any `onAccept` failure to allow a retry, the message will simply be retried and fail identically forever, permanently locking the escrowed funds with no admin sweep or alternate-beneficiary override.

### Finding Description
`_withdraw` decrements escrow accounting and then unconditionally transfers to `beneficiary`: [1](#0-0) 

This is invoked from `onAccept` for both `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund) request kinds: [2](#0-1) 

The beneficiary for `RefundEscrow` is fixed to `order.user` and cannot be redirected by anyone — the cancel-from-destination path hardcodes it: [3](#0-2) 

Once the order is marked cancelled/filled (`_filled[commitment] = ...`), any retry of `cancelOrder`/`fillOrder` for that commitment reverts with `Filled()`, so there is no alternate path to re-target the payout: [4](#0-3) 

Critically, `EvmHost.dispatchIncoming` treats a reverting `onAccept` as retriable rather than fatal — it deletes the request receipt and returns without reverting the whole batch: [5](#0-4) 

This "delete receipt so it can be retried" design assumes transient failures (e.g., out-of-gas, temporary external-call issues). It does not account for a *permanent* failure mode like a blacklist: the message will be resubmitted by relayers indefinitely and will revert identically every time, because `beneficiary` never changes and the token's blacklist state is external to Hyperbridge. There is no try/catch around the transfer, no partial-success/skip-and-continue logic, and no privileged recovery function that lets governance redirect a stuck payout to a different address for a *user* order (the only sweep-style function, `SweepDust`, only handles protocol dust, not user escrow): [6](#0-5) 

The Tron/legacy `withdraw()` implementation has the identical unguarded transfer: [7](#0-6) 

### Impact Explanation
Any input tokens escrowed for an order whose beneficiary (the order's own `user` for a refund, or the filling solver for a redeem) becomes blacklisted by the underlying ERC20 issuer are **permanently and irrecoverably locked** in the `IntentGatewayV2`/`ExtrinsicIntents` contract. This is a direct loss of funds: the escrow can never move again because (a) the commitment is already marked settled/cancelled so no alternate settlement path exists, (b) the transfer will fail identically on every retry since the blacklist state and hardcoded beneficiary never change, and (c) there is no governance/admin function to redirect or rescue a stuck user-order payout. This matches the bounty's pivot that "bridged assets, order escrow, refunds ... must move exactly once and only to the rightful beneficiary and amount" — here they never move at all once the beneficiary is blacklisted, which is functionally equivalent to fund loss for the affected user/solver.

### Likelihood Explanation
No privileged actor, relayer misbehavior, or governance action is required. Any unprivileged user can place an order using a blacklist-capable token (USDC/USDT are common intent-gateway inputs), and the freeze condition (issuer blacklisting the user's own address, which is entirely outside Hyperbridge's control and can happen at any time for any regulatory/compliance reason) is a realistic and previously-acknowledged risk class for exactly this token category, as confirmed by the external report being treated as a viable finding by the original audit's judge despite an "Informative" push-back from the project.

### Recommendation
Wrap the beneficiary transfer in `_withdraw`/`withdraw` in a try/catch (or use a pull-based claim pattern), and on failure move the stuck amount into a per-user withdrawable balance (or emit a recoverable-dust event) rather than repeatedly reverting the same commitment forever. Additionally, add a governance-gated rescue path for permanently stuck escrow tied to a specific commitment, separate from the existing protocol-dust `SweepDust` mechanism, so a blacklisted beneficiary's counterparty (or the beneficiary via an alternate address) can still recover the funds.

### Proof of Concept
1. User places a cross-chain order on the source chain with `order.inputs` in USDC, `order.user = A`.
2. Before the order is filled, USDC issuer blacklists address `A` (unrelated to Hyperbridge).
3. After `order.deadline`, anyone calls `cancelOrder` on the destination chain (`_cancelFromDest`), setting `_filled[commitment] = A` and dispatching `RefundEscrow` back to the source chain.
4. On the source chain, `onAccept` → `_withdraw` attempts `IERC20(USDC).safeTransfer(A, amount)`, which reverts because `A` is blacklisted.
5. `EvmHost.dispatchIncoming` catches this failure, deletes the request receipt, and returns — the message is queued for retry.
6. Every subsequent retry hits the same revert since `A` is still blacklisted and `_filled[commitment]` is already set (blocking any other cancel/fill route). The escrowed USDC is permanently stuck in the `IntentGatewayV2` contract with no available recovery function.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
