### Title
`discardChanges` trusts attacker-controlled `git status` paths without `resolveWithin` containment check, allowing file deletion outside the repository - (File: `app/src/lib/stores/git-store.ts`)

### Summary
GitHub Desktop already has a dedicated path-containment helper, `resolveWithin`, specifically built to stop directory-traversal from untrusted relative paths before they are used in filesystem operations [1](#0-0) . That helper is used in `app-store.ts`, `dispatcher.ts`, and `copilot-conflict-context.ts`, but `GitStore.discardChanges` builds the on-disk path to trash/delete directly with `Path.resolve`/`Path.join` and the raw `file.path` value taken from `git status`, with no `resolveWithin`/`realpath` containment check [2](#0-1) . This mirrors the smart-contract "invalid validation" pattern in the report: a destructive/state-mutating operation (`burn` deleting rental state) that trusts an unchecked precondition instead of validating the object it is about to act on. Here, the destructive operation (moving a file to Trash, or `rm`-ing it) trusts a path string that ultimately originates from parsing the working tree/index reported by `git status --porcelain=2`, which is influenced by the contents of a cloned/fetched repository.

### Finding Description
`WorkingDirectoryFileChange.path` is populated from `IStatusEntry.path`, produced by `status-parser.ts` regexes that simply capture whatever bytes git prints after the status code fields, with no validation against `..`, absolute paths, or other traversal payloads [3](#0-2) [4](#0-3) . These entries flow unchanged into `WorkingDirectoryFileChange(entry.path, ...)` via `buildStatusMap`/`getStatus` [5](#0-4) .

`GitStore.discardChanges` then uses this untrusted `file.path` directly:
```
await this.shell.moveItemToTrash(
  Path.resolve(this.repository.path, file.path)
)
...
await rm(Path.join(this.repository.path, file.path))
``` [2](#0-1) 

Unlike other parts of the codebase that were hardened with `resolveWithin` for exactly this class of bug (e.g. `dispatcher.ts`, `app-store.ts`, `copilot-conflict-context.ts`, and the clone-path sanitizer `sanitizeCloneName` with its dedicated regression tests) [6](#0-5) , `discardChanges` never calls `resolveWithin`/`realpath` to confirm the resolved target stays inside `repository.path` before deleting or trashing it. `Path.resolve`/`Path.join` do not strip `..` segments the way `resolveWithin` normalizes and then verifies with `realpath` — they will happily produce a path outside the repository root if `file.path` contains traversal segments.

### Impact Explanation
If a path containing `../` segments (or an absolute path) can ever reach `WorkingDirectoryFileChange.path` — for example via a maliciously crafted tree/index entry in a cloned or fetched repository, a crafted rename/copy entry, or an untracked-file listing influenced by a symlinked directory inside the working tree — Desktop's "Discard Changes" feature would delete or send-to-Trash an arbitrary file outside the user's repository, using the user's own OS privileges. This is a real "file write/delete outside the repo" primitive triggered purely by opening/using an attacker-supplied repository, matching the allowed impact class (file operations outside the repo boundary caused by a hostile cloned/fetched repository).

### Likelihood Explanation
This requires git itself to be tricked into reporting (via `git status --porcelain=2`) a path containing directory-traversal or absolute segments for a tracked/untracked/renamed entry, which modern git generally guards against for on-disk checkout, but the attack surface here is specifically the *status/rename parsing path*, not checkout — Desktop trusts whatever string appears after the path field in porcelain-v2 output without any of its own defense-in-depth, unlike the analogous clone-path and dispatcher code paths that were explicitly hardened with `resolveWithin`. The presence of `resolveWithinPosix`/`resolveWithinWin32` variants purpose-built for exactly this scenario, plus the fact that `discardChanges` was never migrated to use them, indicates this is a genuine gap rather than a deliberately accepted risk.

### Recommendation
In `GitStore.discardChanges` (and `discardChangesFromSelection`), validate every `file.path`/`file.status.oldPath` with `resolveWithin(repository.path, file.path)` before calling `shell.moveItemToTrash` or `rm`, and abort/skip (or throw) if the resolved path is `null` (i.e., escapes the repository root), consistent with how `resolveWithin` is already used elsewhere in the codebase.

### Proof of Concept
Conceptual PoC (cannot be fully executed without filesystem/terminal access, which is outside this analysis's tool capability):
1. Craft a repository where `git status --porcelain=2 -z` for an untracked/renamed entry reports a path such as `../../../../Library/LaunchAgents/evil.plist` (e.g., via a symlinked directory checked into the repo that git resolves permissively, or a crafted rename/copy entry).
2. Have the victim clone/open this repository in GitHub Desktop and view it in the Changes list; `parseUntrackedEntry`/`parseChangedEntry` will capture the traversal path verbatim into `IStatusEntry.path` [7](#0-6) .
3. Victim selects "Discard Changes" on that entry (or "Discard All Changes"); `GitStore.discardChanges` resolves `Path.resolve(this.repository.path, file.path)` without containment validation and calls `shell.moveItemToTrash`/`rm` on the resulting out-of-repo path [2](#0-1) , deleting/trashing an arbitrary file on the victim's machine.

Note: I was not able to fully confirm within this index whether current git/Desktop status parsing can actually be coerced into emitting a traversal path end-to-end (that would require running git against a crafted repository, which needs filesystem/terminal access beyond this read-only analysis). The structural gap — a destructive filesystem operation on an untrusted, unvalidated path where an equivalent containment check (`resolveWithin`) already exists and is used elsewhere — is confirmed by the code cited above.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

const changedEntryRe =

function parseChangedEntry(field: string): IStatusEntry {

    log.debug(`parseChangedEntry parse error: ${field}`)

  }

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    path: match[8],
  }
}

function buildStatusMap(
  files: Map<string, WorkingDirectoryFileChange>,
  entry: IStatusEntry,
  conflictDetails: ConflictFilesDetails
): Map<string, WorkingDirectoryFileChange> {
  const status = mapStatus(
    entry.statusCode,
    entry.submoduleStatusCode,
    entry.renameOrCopyScore
  )

  if (status.kind === 'ordinary') {
    // when a file is added in the index but then removed in the working
    // directory, the file won't be part of the commit, so we can skip
    // displaying this entry in the changes list
    if (
      status.index === GitStatusEntry.Added &&
      status.workingTree === GitStatusEntry.Deleted
    ) {
      return files
    }
  }

  if (status.kind === 'untracked') {
    // when a delete has been staged, but an untracked file exists with the
    // same path, we should ensure that we only draw one entry in the
    // changes list - see if an entry already exists for this path and
    // remove it if found
    files.delete(entry.path)
  }

  // for now we just poke at the existing summary
  const appStatus = convertToAppStatus(
    entry.path,
    status,
    conflictDetails,
    entry.oldPath
  )

  const initialSelectionType =
    appStatus.kind === AppFileStatusKind.Modified &&
    appStatus.submoduleStatus !== undefined &&
    !appStatus.submoduleStatus.commitChanged
      ? DiffSelectionType.None
      : DiffSelectionType.All

  const selection = DiffSelection.fromInitialSelection(initialSelectionType)

  files.set(
    entry.path,
    new WorkingDirectoryFileChange(entry.path, appStatus, selection)
  )
  return files
