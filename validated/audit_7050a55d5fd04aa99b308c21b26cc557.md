### Title
Withdrawals permanently frozen if a single reward token transfer reverts during forced harvest - ([File: rewards/MasterMagpie.sol], [File: rewards/BaseRewardPool.sol], [File: rewards/BaseRewardPoolV2.sol])

### Summary
`MasterMagpie.withdraw()`/`withdrawFor()` unconditionally bundles a full reward harvest with the return of a user's principal staking token. The harvest step iterates over *every* registered reward token and performs an unconditional `safeTransfer` for each one that has a non‑zero pending amount. If any single reward token in that array reverts on transfer (e.g. it is paused, blacklisted, has a broken/malicious implementation, or the transfer target is disallowed by that token), the entire `withdraw` transaction reverts — including the return of the user's principal LP/staking tokens — with no pull-based fallback to skip the bad token, exactly the class of bug described in the "safeRagequit" report (bundling of an at-risk claim step with an otherwise-safe principal withdrawal).

### Finding Description
`MasterMagpie._withdraw` always calls `_harvestAndUnstake`, which in turn calls `_harvestBaseRewarder` before finally transferring the user's staking token back: [1](#0-0) [2](#0-1) 

`_harvestBaseRewarder` ultimately reaches `BaseRewardPool.getReward` (and the V2 equivalent), which is restricted to being called by MasterMagpie via `onlyMasterMagpie`, and loops through the full `rewardTokens` array performing a `safeTransfer` for each token with a pending non-zero reward: [3](#0-2) [4](#0-3) 

There is no per-token try/catch, no way to specify a subset of reward tokens to skip, and no way for the user to opt out of the harvest during `withdraw`. `getRewards` (plural, allowing a caller-specified subset of `_rewardTokens`) exists in `BaseRewardPoolV2` but is never invoked from the withdrawal path in `MasterMagpie` — only the all-or-nothing `getReward` is used inside `_harvestBaseRewarder`/`_withdraw`. [5](#0-4) 

Because pools can accumulate multiple bonus/bribe reward tokens over time (via `queueNewRewards`, which pushes any new token address into `rewardTokens` the first time it's used), a single problematic token added to a pool's reward token list poisons the withdrawal path for every staker of that pool, not just the token issuer: [6](#0-5) 

This mirrors the "safeRagequit" bug class exactly: an all-or-nothing multi-token payout is coupled with an unrelated, otherwise-safe withdrawal of principal, so one bad token blocks access to funds that have nothing to do with that token.

### Impact Explanation
If any reward token registered on a pool's `BaseRewardPool`/`BaseRewardPoolV2` reverts on `safeTransfer` to some user (blacklisting, pausing, insufficient balance due to accounting drift, or a malicious/broken token added as a bribe reward), that user (and potentially all stakers in the pool, since anyone attempting `withdraw`/`withdrawFor` triggers the same all-tokens harvest) can no longer withdraw their principal staking token from `MasterMagpie`. There is no emergency path that skips reward transfer while paused is only available via `emergencyWithdraw`, which itself is gated `whenPaused` (an admin-controlled global pause), not something an ordinary user can trigger on demand. This constitutes a permanent freeze of user principal funds (LP/staking tokens), satisfying the "24-hour-plus freeze" / "permanent freezing of funds" impact bar.

### Likelihood Explanation
Likelihood is driven entirely by unprivileged conditions reachable from an ordinary wallet's transaction: any ordinary reward/bribe token registered through `queueNewRewards` that has blacklist functionality (e.g. USDC-style tokens), pausability, or a bug causing reverts for a specific recipient will trigger this on the very next `withdraw` call by the affected user, with no admin or governance action required to bring about the initial revert condition.

### Recommendation
Decouple principal withdrawal from reward harvesting. `MasterMagpie._withdraw`/`_harvestAndUnstake` should either:
- Wrap the per-token reward transfer in `getReward`/`_harvestBaseRewarder` in a low-level call with a try/catch (or track pending/unclaimed amounts on failure) so a single failing token cannot block the transfer of the user's staking token, or
- Adopt a pull pattern for reward tokens (similar to the recommended fix for `ragequit`): record the failed/unclaimed reward per token/user, allow the user to withdraw the principal unconditionally, and let them claim (or have to explicitly opt in per-token) rewards separately via a function like `getRewards` that already accepts a caller-specified token subset in `BaseRewardPoolV2`.

### Proof of Concept
1. A pool has `rewardTokenA` (e.g. WOM/MGP) and `rewardTokenB`, a bribe token added via `WombatBribeManager`/`queueNewRewards` that is subsequently blacklist/pausable.
2. User stakes into the pool via `MasterMagpie.deposit`.
3. `rewardTokenB` issuer blacklists the user's address (or pauses transfers), or the reward pool's balance of `rewardTokenB` becomes insufficient for the accrued reward due to any rounding/accounting edge case.
4. User calls `MasterMagpie.withdraw(_stakingToken, _amount)`.
5. `_withdraw` → `_harvestAndUnstake` → `_harvestBaseRewarder` → `BaseRewardPool.getReward` loops the reward tokens; the `safeTransfer` call for `rewardTokenB` reverts.
6. The entire `withdraw` transaction reverts, and the user's principal `_stakingToken` remains locked in `MasterMagpie` indefinitely (no per-user way to bypass the bad reward token), reproducing the "safeRagequit" freeze scenario. [7](#0-6) [3](#0-2)

        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
