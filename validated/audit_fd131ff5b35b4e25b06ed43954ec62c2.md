### Title
Partial-commit line selection is applied against a re-fetched diff without revalidation, allowing silent corruption of committed content - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
GitHub Desktop lets a user select individual lines/hunks of a file to include in a commit ("partial commit"). The selection the user makes in the UI is stored as a bit-vector of absolute line indices (`DiffSelection`) computed against a specific diff snapshot that was fetched and cached when the file was selected in the Changes view. When the user actually commits, Desktop does **not** reuse that reviewed diff. Instead, `applyPatchToIndex` re-runs `git diff` against the working tree at commit time and blindly re-applies the old index-based selection to whatever hunk structure comes back. This mirrors the reported RAAC bug class: a derived/cached value (`reserve.totalLiquidity`, here the user's line selection) is computed from one snapshot of state and then used against a different, later snapshot of the underlying state without being re-synchronized — silently producing an incorrect result (a wrong loan-rate there, a wrong commit here).

### Finding Description
- The diff shown to the user, and against which they make a partial line selection, is fetched and cached once per selection in `updateChangesWorkingDirectoryDiff`: [1](#0-0) 
The resulting diff is stored in `changesState.selection.diff` and the file's `DiffSelection` is defined purely as a set of **absolute line indices** into that diff's hunks (`selectableLines`, `unifiedDiffStart + index`): [2](#0-1) 

- When the user commits, `_commitIncludedChanges` takes the currently selected files (each carrying its `DiffSelection`) as-is and passes them straight to `createCommit`: [3](#0-2) 

- For files with a partial selection, the actual patch is built by `applyPatchToIndex`, which **re-fetches a brand-new diff from disk** at commit time rather than reusing the diff the user reviewed: [4](#0-3) 

- That freshly-fetched diff is then formatted into a patch using `formatPatch`, which walks the *new* diff's hunks and decides what to include purely by asking `file.selection.isSelected(absoluteIndex)` — i.e., it trusts that the line-index numbering from the old diff still lines up with the new diff's hunks: [5](#0-4) 

There is a comment acknowledging that hunk structure can change dramatically between diff loads, but the mitigation applied (`updateChangesWorkingDirectoryDiff`) only prunes indices that no longer exist as includeable lines — it does not prevent the stale selection from being matched against unrelated new hunks that happen to reuse the same absolute-index range: [6](#0-5) 

**Broken invariant:** "the set of lines the user visually selected == the set of lines actually included in the git patch" is assumed to be stable across the time-of-check (diff shown/selected in UI) and time-of-use (diff re-fetched in `applyPatchToIndex` at commit time), but nothing enforces that the two diffs are identical.

**Why existing guards don't stop this:** The only guard that exists is index-set intersection with "still includeable" lines, done for UI consistency, not integrity of the git patch. `applyPatchToIndex` never compares the newly fetched diff against the one the selection was made from, and `formatPatch` has no way to detect a mismatch — it will happily generate a syntactically valid patch from whatever hunks are present.

### Impact Explanation
If working-tree file content changes between the moment the user reviews a diff and selects lines and the moment Desktop actually builds the commit patch (e.g., a build tool, linter/formatter on save, a git smudge/clean filter, or a hook/background process triggered by opening or cloning a malicious repository that keeps mutating a tracked file), the line-index based selection can end up mapped onto entirely different content. This can cause Desktop to silently commit content the user never selected/reviewed (e.g., attacker-injected lines that shifted into the previously-selected index range) or drop content the user believed was included — i.e., "silent corruption of what the user commits," one of the explicitly in-scope impact classes.

### Likelihood Explanation
This requires the working file to change between diff-load time and commit time without the user re-reviewing the diff — a realistic race in normal developer workflows (auto-formatters, watchers, filters) and a plausible vector for a malicious/crafted repository that installs a background process (e.g., via a `postinstall`/build hook commonly run right after cloning) designed to mutate a tracked file shortly after checkout, hoping to land unreviewed content in the victim's next partial commit. It does not require local/physical access, admin rights, or pre-existing malware beyond content shipped in the cloned repository itself.

### Recommendation
Before applying a partial-commit patch, re-validate that the diff used to build the patch is identical (or compatible, hunk-for-hunk) to the diff the user's selection was made against; if the working tree has changed, refuse to auto-commit the stale selection and force the user to re-review/re-select. Concretely, `applyPatchToIndex` should accept and use the diff that was already loaded in `changesState.selection.diff` (with a hash/identity check against a freshly computed status) rather than unconditionally re-fetching a new diff via `getWorkingDirectoryDiff`, and `formatPatch`/`isSelected` should fail closed (throw) rather than silently applying index positions from a stale selection to new hunk content.

### Proof of Concept
1. Modify a tracked file with several hunks; open it in the Desktop Changes view so `updateChangesWorkingDirectoryDiff` fetches and caches the diff, and select only lines from hunk #1 for partial commit.
2. Before clicking "Commit", have an external process append/insert lines earlier in the same file so that hunk boundaries and `unifiedDiffStart` offsets shift (e.g., simulate a formatter/watcher, or, for the malicious-repo variant, a script triggered post-checkout).
3. Click Commit. `_commitIncludedChanges` → `createCommit` → `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`) and `formatPatch` (`app/src/lib/patch-formatter.ts:129-161`) applies the old absolute-index selection to the new hunks.
4. Inspect the resulting commit: it includes/excludes different lines than what the user visually selected in step 1, demonstrating silent corruption of the committed content.
