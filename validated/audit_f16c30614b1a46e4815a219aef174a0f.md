### Title
Malicious repository hooks can exfiltrate the signed-in GitHub token via the trampoline credential helper, which authorizes by host origin only - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The external report's root cause is a signature that omits the resource it should be scoped to (`msg.sender` + `maxMintAmount` but no contract address), letting it be replayed against any contract of the same shape. GitHub Desktop's trampoline credential helper has the same missing-scope pattern: it hands out the user's real GitHub OAuth token to any process that asks for credentials for a matching **host origin**, without verifying that the request originates from the specific repository/operation the user intended. Any git subprocess that can reach the trampoline (including a repository's own hooks) inherits this ability, so a hostile cloned/fetched repository can silently obtain the user's token.

### Finding Description
`withTrampolineEnv` sets `credential.helper=desktop` globally via `GIT_CONFIG_PARAMETERS` plus `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` for the whole git invocation environment: [1](#0-0) 

These environment variables are inherited by every child process git spawns for that operation, including native Git hooks (`post-checkout`, `post-merge`, etc.), unless the operation explicitly opts into the sandboxed hook proxy via `interceptHooks` and the `git-hooks-env-enabled` feature flag: [2](#0-1) 

`clone()` runs `git clone --recursive` without passing `interceptHooks`, so hooks that fire as part of a clone/checkout are executed by Git itself with the raw, un-proxied environment — meaning `DESKTOP_TRAMPOLINE_TOKEN` and the credential-helper wiring reach the hook process directly: [3](#0-2) 

The trampoline server accepts any command bearing a currently-valid token — validity is a simple set-membership check with no binding to a specific repository or remote: [4](#0-3) [5](#0-4) 

When a `get` credential request comes in, `getGitHubCredential` looks up the account purely by matching the requested URL's **origin** against a signed-in account's endpoint origin — it never checks which repository, remote, or operation the credential request is "supposed" to belong to: [6](#0-5) [7](#0-6) 

This is the exact analog of the audited bug: the "signature" (here, the trampoline token + credential-helper wiring) authorizes an action (returning the real GitHub token) based on a check (`origin === origin`) that omits the actual scope that should have been bound — the specific repository or remote the operation belongs to. Just as Bob's signature could be replayed against NFT2 because the contract address wasn't part of the signed data, a hook process spawned from an attacker's cloned repository can "replay" the trampoline token/credential-helper config to request `https://github.com` credentials and receive the real signed-in user's token, even though that hook has nothing to do with the user's authenticated GitHub account.

### Impact Explanation
A hook shipped inside a malicious repository executes with network access to `127.0.0.1:$DESKTOP_PORT` and a valid `$DESKTOP_TRAMPOLINE_TOKEN`. It can invoke `git credential fill` for `https://github.com` (or any GHE host the user is signed into) and receive the user's real OAuth token back from `getCredential`/`getGitHubCredential`, then exfiltrate it over the network from the unsandboxed hook process. This is credential/token exfiltration — the user's full GitHub account access — triggered merely by cloning or fetching (with submodule/hook execution) an attacker-controlled repository, matching the "unprivileged, attacker-controlled cloned/fetched repository leading to credential exfiltration" impact class.

### Likelihood Explanation
The precondition is only that the user clones or fetches a repository containing a hook (e.g. `post-checkout`) and that this operation is not covered by the hook-interception feature (which is opt-in per call site and gated behind `getHooksEnvEnabled()`/`interceptHooks`; `clone()` does not use it). Git executes local hooks automatically as part of `clone --recursive`/`checkout`/`merge`, with no user interaction required beyond the normal act of adding/cloning the repository in Desktop. No admin rights, leaked credentials, or unnatural steps are needed.

### Recommendation
Bind trampoline/credential-helper authorization to the specific git operation and its intended repository/remote (not just token validity + host origin). For example: pass the expected target host(s)/remote through `withTrampolineEnv` and reject/require re-confirmation for `get` credential requests whose requested URL does not match the remote(s) configured for the repository/operation that created the token, and ensure hook execution is always routed through the sandboxed/proxied hooks environment (or otherwise stripped of `DESKTOP_TRAMPOLINE_TOKEN`/credential-helper config) regardless of `interceptHooks` opt-in, especially for clone/checkout/merge which routinely run repository-controlled hooks.

### Proof of Concept
1. Attacker publishes a repository containing a `post-checkout` hook script that:
   - Reads `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` from its environment.
   - Speaks the trampoline credential-helper protocol to request `get` credentials for `https://github.com`.
   - Sends the returned `username`/`password` (the user's real login/token) to an attacker-controlled server.
2. Victim clones the repository in GitHub Desktop (`clone()` in `app/src/lib/git/clone.ts`, no `interceptHooks`).
3. Git runs `post-checkout` automatically after the clone, inheriting the trampoline environment set by `withTrampolineEnv`.
4. The hook's credential-helper request reaches `trampolineServer`, passes the token-validity check, and `getGitHubCredential`/`findGitHubTrampolineAccount` return the victim's real GitHub credential because only the host origin (`github.com`) is checked.
5. The hook exfiltrates the victim's OAuth token to the attacker, who now has full account access.

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
