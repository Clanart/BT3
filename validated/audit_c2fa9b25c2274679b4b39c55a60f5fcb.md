### Title
Transaction-level Serai data extraction lets a co-spender hijack the InInstruction of another party's deposit in the same Bitcoin transaction - (File: processor/src/networks/bitcoin.rs)

### Summary
The referenced bug class is a processing differential: content hidden in a channel one consumer ignores (LFE channel) but another processes (the downmixer), letting an attacker smuggle instructions past the "intended" input. The analog exists in `Bitcoin::get_outputs` / `extract_serai_data`: the InInstruction `data` is extracted from *any* input witness or *any* `OP_RETURN` output of the transaction, then applied unconditionally to *every* `External`-kind output Serai scans in that transaction. A depositor's plain P2TR payment to the multisig carries no instruction of its own (a channel the depositor believes is empty), yet a co-spender's hidden witness/OP_RETURN payload is processed against the depositor's balance.

### Finding Description
`Scanner::scan_transaction` matches outputs purely on `script_pubkey` [1](#0-0) . Then `get_outputs` computes a single `data` value per transaction via `extract_serai_data(tx)` and clones it onto **all** scanned `OutputType::External` outputs [2](#0-1) . `extract_serai_data` accepts the last push of the first `OP_RETURN` output, or, failing that, `witness[len-2]` of the first input whose redeem script matches `OP_SHA256 <hash> OP_EQUALVERIFY ...` [3](#0-2) . Neither source is bound to the specific output paying Serai: the OP_RETURN only has to exist in the same tx, and the witness pattern only requires the attacker to spend a P2WSH output whose script they crafted earlier (they choose the committed hash, so they fully control the revealed `data`).

Downstream, `instruction_from_output` decodes that `data` into a `RefundableInInstruction` and pairs it with `output.balance()` — i.e., the victim output's value [4](#0-3) . The attacker can set `instruction.origin` explicitly (overriding `presumed_origin`, which is taken from `tx.input[0]` regardless of which input actually carried the data [5](#0-4) ).

### Impact Explanation
An attacker who co-authors a transaction containing a victim's deposit to the Serai multisig can attach an arbitrary `InInstruction` that executes against the victim's deposited balance — e.g., `InInstruction::Transfer` to an attacker-controlled `SeraiAddress`, minting sriBTC to themselves from funds the victim deposited with no instruction (or a different one). It can also force an unintended `Refund` plan or other in-instruction effects. This is "funds processed under an instruction the depositor never authored": a concrete signing/execution differential caused by data on a channel (co-spender's witness or a shared OP_RETURN) the depositor's output doesn't reference.

### Likelihood Explanation
Requires the victim's deposit and the attacker's data-bearing input/OP_RETURN to share a transaction. This occurs in batched withdrawal transactions (exchanges/payment processors frequently batch many users' outputs and append an OP_RETURN), coinjoin/collaborative transactions, or any wallet flow where a third party constructs the tx paying Serai. An unprivileged external party with a UTXO in such a batch suffices; no validator, threshold, or key compromise is needed. Mitigating factors: the batching scenario requires a service that pays Serai addresses in shared transactions, and `balance.amount.0` is reduced by `2 * COST_TO_AGGREGATE`.

### Recommendation
Bind the extracted data to the specific deposit: only apply `data` when the transaction provably originates the instruction for that output — e.g., require the OP_RETURN output index/position convention (spec documents "the transaction's last output" [6](#0-5) ) and reject OP_RETURNs when the tx contains inputs not attributable to the depositor, or attribute data only when the deposit output and the data carrier share a verifiable relationship. At minimum, don't apply witness-derived data from inputs other than the one whose prevout funds the deposit, and document that batched/shared transactions paying Serai must not carry OP_RETURN/witness data.

### Proof of Concept
1. Attacker creates a P2WSH output whose redeem script is `OP_SHA256 <sha256(m)> OP_EQUALVERIFY <p2pkh-style tail>` committing to `m = Shorthand::Raw(RefundableInInstruction { origin: None, instruction: InInstruction::Transfer(attacker_serai_addr) }).encode()` (as done in `processor/src/tests/literal/mod.rs` [7](#0-6) ).
2. Attacker participates in a batch/coinjoin transaction in which a victim (or a service acting for the victim) creates output `TxOut { script_pubkey: serai_p2tr, value: V }` — no OP_RETURN, and the victim intends no instruction.
3. Attacker adds their input spending the P2WSH with witness `[..., m, redeem_script]`. `segwit_data_pattern` returns `Some(true)`, so `extract_serai_data` yields `m` [8](#0-7) .
4. `get_outputs` clones `m` onto the victim's `External` output [9](#0-8) ; `instruction_from_output` issues `InInstructionWithBalance { Transfer(attacker), balance: V - 2*COST_TO_AGGREGATE }`.
5. The batch executes a transfer of the victim's deposit value to the attacker's Serai address. Alternatively, a shared `OP_RETURN` achieves the same without any witness scripting.
