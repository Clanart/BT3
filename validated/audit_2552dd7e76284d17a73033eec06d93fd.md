### Title
Panic on out-of-set participant index in generator promotion crashes the node - (File: crypto/dkg/promote/src/lib.rs)

### Summary
Analogous to CVE-2016-9433 (a remote denial of service via an out-of-bounds array access on attacker-crafted input), `GeneratorPromotion::complete` indexes a caller-supplied `HashMap<Participant, GeneratorProof>` with `.unwrap()` for every expected participant. Because the pre-validation only bounds the map's length and each key's maximum value — but never excludes the verifier's own index — a map containing `params.i()` satisfies both checks while missing some other required participant, causing an unconditional panic when the loop reaches the missing index.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` performs two checks on the attacker-supplied `proofs` map:

- `proofs.len() == n - 1` (lines 125–131)
- every key satisfies `u16::from(i) <= params.n()` (lines 132–136)

It then iterates `i in 1..=n`, skips `params.i()`, and unconditionally unwraps `proofs.get(&i)` at line 146.

The flaw: the validation does not reject a map that *includes* the verifier's own index `params.i()`. If a submitting party (or the coordinator assembling proofs) supplies a map of length `n - 1` whose keys are `{params.i()} ∪ (n - 2 other valid indexes)`, both checks pass, yet one required participant `j ∈ 1..=n, j ≠ params.i()` is absent. When the loop reaches `j`, `proofs.get(&j).unwrap()` panics, unwinding through `ThresholdKeys::new(...).unwrap()` territory — a hard crash rather than a returned error.

This matches the CVE class: attacker-controlled indexes drive an unchecked lookup (`Vec`/map indexing) producing a denial of service, reachable purely through public inputs (`GeneratorProof::read` bytes plus a chosen `Participant` key set).

### Impact Explanation
Any participant in a generator-promotion ceremony (or any party able to influence the `proofs` map, e.g., a validator submitting proofs during key rotation between generators such as a Bitcoin `TapTweak`/external-address promotion) can crash the honest party running `complete`. A panic in a validator/processor task aborts the promotion, and depending on the executor, can take down the signing process — a remote, unauthenticated-input-triggered denial of service against threshold-key infrastructure. Severity: Medium (availability only, no secret exposure).

### Likelihood Explanation
The trigger requires only that the `proofs` map be malformed in a specific, easy way: include the verifier's own participant index and omit any other index. No valid proofs, signatures, or secrets are needed — the panic occurs before any `DLEqProof::verify` on the missing index. Reaching it requires only participation in or influence over the promotion message set, i.e., public inputs to a `complete` API.

### Recommendation
Replace the implicit completeness assumption with explicit membership validation. Before the loop, either:
- reject maps containing `params.i()`: `if proofs.contains_key(&params.i()) { Err(...) }`, and/or
- iterate `proofs` directly (zip with expected participants) and return `PromotionError::MissingParticipant`/`` `InvalidParticipant `` instead of `unwrap()` on `proofs.get(&i)`.

The same defensive pattern should be applied anywhere `self.commitments[&l]` / `verification_shares[&l]` style indexing is performed on maps whose key coverage was validated only by length (e.g., `pedpop`'s `self.commitments[&l]` is protected by `validate_map`'s per-key `contains_key` check — `promote` lacks the equivalent).

### Proof of Concept
```rust
// In crypto/dkg/promote, with n-of-n params (t == n as enforced by Constant
// interpolation) and verifier index `params.i() == Participant(1)`, n = 3:
let mut proofs = HashMap::new();
// Attacker supplies n - 1 = 2 proofs keyed by {1, 2} — includes our own index,
// omits Participant(3). Both validations pass:
//   proofs.len() == 2 == n - 1            ✓
//   all keys <= n                         ✓
proofs.insert(Participant::new(1).unwrap(), bogus_proof_a);
proofs.insert(Participant::new(2).unwrap(), bogus_proof_b);
// complete() reaches i = 3:
//   proofs.get(&Participant(3)) -> None -> .unwrap() PANICS
promotion.complete(&proofs);
```
The panic happens regardless of `bogus_proof_*` contents — no valid DLEq proof is needed, so any unprivileged participant in the promotion set can trigger it with arbitrary bytes read via `GeneratorProof::read`.
