This is exactly the analog: `convert_to_balance` in `hyper-fungible-token` uses `saturating_sub` for the decimal exponent, which silently drops the scaling factor whenever the remote ERC20 token has *fewer* decimals than the local asset — mirroring the Pyth report's core defect (a scaling operation that produces the wrong magnitude and that isn't safe against one direction of the input).

### Title
Incoming cross-chain token amount under-scaled when remote ERC20 decimals < local asset decimals, allowing minting of wrong (larger or smaller) balances - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_balance` converts an inbound ERC20 `U256` amount into the local Substrate balance by dividing by `10^(erc_decimals - local_decimals)`. The exponent is computed with `saturating_sub`, so whenever `erc_decimals < local_decimals` the subtraction saturates to `0`, and the function divides by `10^0 = 1` — i.e., it applies **no scaling at all** instead of the required upscaling by `10^(local_decimals - erc_decimals)`. This is the same class of bug as the reported Pyth defect: the code needs to scale in one direction but the implementation only correctly handles (and is only "safe" for) the other direction, and it doesn't error/guard against the disallowed case — it just silently returns a wrong magnitude. [1](#0-0) 

### Finding Description
`convert_to_balance` is documented as scaling *down* from ERC20 precision (assuming `erc_decimals >= local_decimals`): [1](#0-0) 

Its counterpart `convert_to_erc20` correctly documents and multiplies to scale up: [2](#0-1) 

Because `saturating_sub` is used instead of a checked/signed subtraction, `convert_to_balance` has no way to detect or correctly handle `erc_decimals < local_decimals`. In that case, the function treats an ERC20 amount denominated in *fewer* decimal places as if it were already denominated in the *local* (larger) number of decimals, and applies a division by `1`, i.e. **no rescale**. The resulting local balance is `erc_decimals`-scaled magnitude, but it is credited/interpreted as if it were `local_decimals`-scaled — inflating the effective value by a factor of `10^(local_decimals - erc_decimals)` relative to what the sender actually escrowed on the EVM side.

This function is called on the inbound message-handling path when an ISMP message crediting/minting a local asset arrives from a remote EVM chain (the mirror path to `send`, which uses `convert_to_erc20` on the outbound side). `send()` on the outbound path correctly reads `Precisions::<T>::get(asset_id, destination)` for `erc_decimals` and uses `convert_to_erc20`: [3](#0-2) 

The inbound counterpart is symmetric and configured by the same governance-set `Precisions` storage, meaning `erc_decimals` is not attacker-controlled directly, but it is a governance-configured value that can legitimately be smaller than `local_decimals` (e.g., bridging a 6-decimal USDC-style ERC20 into an 18-decimal local asset, or any token pair where the remote token uses fewer decimals). No additional guard rejects or corrects this configuration, so the bug is triggered purely by normal, permissionless bridging traffic for such a token pair — no malicious relayer, prover, or governance actor is needed.

### Impact Explanation
This falls squarely in "unauthorized transaction manipulation / wrong amount minted" — bridged asset custody is violated because the local balance minted to the recipient does not correspond 1:1 in value to the amount escrowed/burned on the source chain. If `local_decimals > erc_decimals`, the pallet fails to scale up the incoming ERC20 amount, so it mints/credits the raw (undersized numeric) value as if it were already in local decimal units — effectively crediting up to `10^(local_decimals - erc_decimals)` times more or less value than what was locked on the source chain (direction and magnitude depends on exactly how the value is interpreted downstream, but in all cases the amount is provably wrong whenever the two chains disagree in that specific direction). This can result in funds being minted beyond what was escrowed (inflationary mismatch, draining the custody backing) or funds being severely under-credited (value loss for the user), both of which are "loss of funds" / "unauthorized value creation" impacts.

### Likelihood Explanation
Likelihood is driven entirely by configuration data (`Precisions`) that governance sets per `(asset_id, destination)` pair — this is a completely realistic, foreseeable configuration for any token whose canonical ERC20 decimals are lower than the local asset's decimals (very common, since Substrate assets are frequently configured with 18 decimals while many ERC20s use 6 or 8). No attacker action beyond a normal token send is required to trigger the mis-scaling once such a pair exists, making this a reliably reproducible defect under standard operating conditions, not an edge case requiring a malicious actor.

### Recommendation
Replace the `saturating_sub`-based division with logic that branches on the sign of `erc_decimals - local_decimals`, mirroring `convert_to_erc20`'s correct multiply-up behavior: if `erc_decimals >= local_decimals`, divide by `10^(erc_decimals - local_decimals)`; if `erc_decimals < local_decimals`, multiply by `10^(local_decimals - erc_decimals)`. Add unit tests covering both directions (`erc_decimals > local_decimals` and `erc_decimals < local_decimals`) to prevent regression, matching the bug-class remediation of "multiply instead of divide" from the cited Pyth report.

### Proof of Concept
1. Governance configures a bridged asset with `local_decimals = 18` and `erc_decimals = 6` (e.g., a USDC-style remote ERC20 bridged into an 18-decimal local asset) via the `Precisions` storage used by `send`/inbound handling. [4](#0-3) 
2. A user sends `1_000_000` (i.e., `1.0` in 6-decimal ERC20 units) from the EVM chain to the Substrate chain via the standard `HyperFungibleToken`/`WrappedHyperFungibleToken` message flow.
3. On receipt, `convert_to_balance(U256::from(1_000_000), 6, 18)` is invoked: `erc_decimals.saturating_sub(local_decimals)` = `6_u8.saturating_sub(18)` = `0`, so the divisor is `10^0 = 1`. [5](#0-4) 
4. The function returns local balance `1_000_000` instead of the correct `1_000_000 * 10^(18-6) = 1_000_000_000_000_000_000` (or, if the resulting value is misinterpreted as already-scaled, the recipient effectively receives `0.000000000000000001` of the asset instead of `1.0`) — a discrepancy of `10^12`, demonstrating the value-mismatch between what was escrowed on the source chain and what is credited on the destination.
