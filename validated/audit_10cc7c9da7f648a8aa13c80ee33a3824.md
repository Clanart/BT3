### Title
Quadratic Lagrange interpolation during `ThresholdKeys` deserialization enables CPU-exhaustion DoS - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts an attacker-controlled participant count `n` (u16, up to 65535) and threshold `t` from the byte stream, then calls `ThresholdKeys::new`, which computes the group key via `interpolation_factor` for each of participants `1..=t`. Under `Interpolation::Lagrange`, each `interpolation_factor` call is O(t) field multiplications plus a field inversion, making the deserialization O(t²) — about 4.3 billion field operations and 65535 inversions — from a ~2 MB input. This mirrors CVE-2024-1493's class: a small, syntactically valid public input triggering disproportionate computation.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` directly from the reader, reads `n` verification shares, and then invokes `ThresholdKeys::new`. `ThresholdParams::new` only enforces `0 < t <= n`, so `t = n = 65535` is accepted. `ThresholdKeys::new` then derives `group_key` by summing `verification_shares[i] * interpolation_factor(i, t_list)` for `i in 1..=t`, and `Interpolation::Lagrange::interpolation_factor` iterates over all `t` included participants performing a field multiply for numerator and denominator each, followed by `denom.invert().unwrap()` — a full field inversion per participant. Total cost is O(t²) multiplications + O(t) inversions + O(n) point decompressions. An unprivileged party feeding these bytes to `ThresholdKeys::read` forces minutes of CPU on a single message. The same quadratic factor computation recurs in `ThresholdKeys::view`, which recomputes `interpolation_factor` for every included signer.

### Impact Explanation
A remote peer able to supply serialized `ThresholdKeys` bytes (e.g., to a key-handling endpoint or recovery path) can stall the victim's CPU with a single ~2 MB message, denying service to signing/key-management operations. Per byte of input the victim expends roughly three orders of magnitude more CPU work than a linear-time parse, and the input is fully valid — it passes all structural checks and produces correct keys, so it cannot be filtered by cheap validation.

### Likelihood Explanation
Reachability depends on `ThresholdKeys::read` being exposed to untrusted bytes; the Serai codebase itself caps on-wire structures (e.g., `TRANSACTION_SIZE_LIMIT` in coordinator transactions, `MAX_LIBP2P_REQRES_MESSAGE_SIZE`) which would truncate a 2 MB payload on those paths, so exploitation requires a path where serialized `ThresholdKeys` cross a trust boundary without such a cap. Within the in-scope crypto libraries alone, the quadratic algorithmic complexity is unconditional: any integrator deserializing attacker-provided `ThresholdKeys` hits it. Medium likelihood.

### Recommendation
Bound `n`/`t` during deserialization to a sane protocol maximum (e.g., the Substrate validator set size, well under 1000) before performing group-key derivation, or cache Lagrange coefficients so `group_key` derivation is O(t) inversions total (batch-invert denominators via Montgomery's trick) instead of O(t²) multiplications with per-participant inversions.

### Proof of Concept
Construct a serialized `ThresholdKeys<Ristretto>` buffer:
1. `u32 LE` = len(`Ristretto::ID`), then `Ristretto::ID` bytes.
2. `t = 0xFFFF`, `n = 0xFFFF`, `i = 1` (u16 LE each).
3. Interpolation byte `1` (Lagrange).
4. One valid scalar encoding for `secret_share`.
5. `65535` valid Ristretto point encodings for `verification_shares`.

`ThresholdKeys::read(&mut buf)` performs `65535` point decompressions, then `ThresholdKeys::new` executes `65535` calls to `Interpolation::Lagrange::interpolation_factor`, each looping `65535` iterations of field multiplications plus one `invert()` — ~4.3×10⁹ field multiplications and 65535 inversions — before returning.   fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
  }
