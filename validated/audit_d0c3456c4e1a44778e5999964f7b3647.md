## Analysis

The core broken invariant in the Monad report is: **a bounded, shared capacity structure evicts entries by insertion order (or not at all) rather than by economic/functional relevance, and a permissionless actor can cheaply saturate that structure to deny others space or destroy state others depend on.**

The closest local analog in Hyperbridge is `pallet-ismp`'s per-`StateMachineId` **state-commitment retention queue** (`StateCommitmentQueue` / `CommitmentQueueStates` / `BoundedStateCommitments`), which the `handle_unsigned` extrinsic feeds for free. [1](#0-0) 

- Anyone can submit consensus/state-machine-update messages via `handle_unsigned`, which is explicitly documented as free/unsigned and permissionless. [2](#0-1) 
- Each state machine's retained commitments are stored in a **fixed-size FIFO queue capped at `MAX_STATE_MACHINE_COMMITMENTS` (10,240) or a per-chain override**, and pushing past the cap **evicts the oldest entry unconditionally** — with no regard for whether that height is still needed by a pending fee/reward claim, relayer withdrawal proof, or timeout proof. [3](#0-2) 
- `update_client` accepts and stores **every intermediate height** returned by consensus verification, inserting one queue entry per height rather than one per batch — so an attacker relaying real (valid) but finely-grained intermediate states for a fast-finality/cheap-to-follow source chain can churn the queue quickly, i.e. attacker-controlled cadence rather than protocol-controlled cadence. [4](#0-3) 

This mirrors the Monad bug class precisely: (1) no differentiation between "important" and "spam" entries when the structure is full — eviction is purely oldest-first, same as Monad's simplistic per-address eviction with no cross-address fee comparison; and (2) the produced entries can never be "consumed"/removed early by their rightful owner, so they just sit and get evicted at a predictable point, analogous to Monad's nonce-gapped transactions that permanently occupy a tracked-pool slot.

The state commitments in this queue are **directly relied upon** by the relayer reward/fee-claim paths — `accumulate_fees`, `claim_outbound_request_delivery_reward`, and `process_outbound_consensus_delivery_claim` — all of which call `verify_withdrawal_proof`/`validate_state_machine` against a **specific historical height's** stored `StateCommitment`. If that height's commitment has been evicted before the relayer submits its claim, the proof verification fails permanently (`OutboundDestinationStateNotKnown`), and the relayer/legitimate claimant loses the ability to ever claim that fee/reward — a real fund-loss outcome, not merely inconvenience. [5](#0-4) [6](#0-5) 

### Title
Free, attacker-triggerable FIFO eviction of `StateCommitmentQueue` can permanently destroy state commitments needed for pending relayer fee/reward proofs - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`pallet-ismp` retains a bounded, per-`StateMachineId` FIFO queue of state commitments (`StateCommitmentQueue`, capped by `StateMachineCommitmentCap`/`MAX_STATE_MACHINE_COMMITMENTS`). Insertion is driven by the permissionless, free `handle_unsigned` extrinsic processing `ConsensusMessage`s, and eviction is strictly oldest-first with no regard for whether a still-unclaimed relayer fee/reward proof depends on that height.

### Finding Description
`update_client` stores one queue entry per intermediate height returned by consensus verification, with no batching limit tied to protocol cadence — an attacker can relay real, validly-provable intermediate heights for any connected chain at a pace they control, since submission is unsigned and fee-free. [7](#0-6) [1](#0-0) 

Each insertion into `BoundedStateCommitments`/`StateCommitmentQueue` evicts the oldest tracked height once the per-chain cap is reached, deleting `BoundedStateCommitments` and `BoundedStateMachineUpdateTime` for that height unconditionally, without checking whether any pending relayer withdrawal/reward claim still needs it. [3](#0-2) 

Downstream, `process_outbound_request_delivery_claim` and `process_outbound_consensus_delivery_claim` both resolve `validate_state_machine(&host, state_proof.height)` and then `verify_withdrawal_proof` against the state commitment stored at that historical height. If the height has already been evicted from `BoundedStateCommitments`, verification fails with `OutboundDestinationStateNotKnown`, permanently blocking that specific claim. [5](#0-4) [6](#0-5) 

The eviction path guards against duplicate/stale index issues (`vetoed_height_that_cannot_be_resubmitted_evicts_as_a_noop`) but that guard is about internal queue consistency, not about protecting heights that outstanding, economically-valuable proofs still depend on — there is no reservation, pinning, or minimum-retention-until-claimed mechanism for heights referenced by outstanding relayer claims. [8](#0-7) 

### Impact Explanation
This meets the bounty's "loss/lock of funds" and "logic attack" impact categories: a legitimate relayer who has already delivered a request/response or a consensus rotation and is entitled to a reward can be griefed out of that reward permanently, with no way to resubmit against a fresher height (the receipt itself is anchored to the original delivery height's commitment being provable, and outbound request/consensus rewards are one-shot, idempotency-gated claims tied to a specific commitment). This is not merely gas-DoS — it directly causes fund non-payment/loss for the rightful claimant, matching the pivot "relayer rewards ... must move exactly once and only to the rightful beneficiary and amount."

### Likelihood Explanation
Likelihood is high for chains where the cap is low relative to real block cadence (or where the attacker floods intermediate heights faster than the default cap can absorb): `handle_unsigned` is explicitly free and unsigned so anyone can submit these consensus updates without cost beyond fetching real headers/proofs from the source chain — no malicious relayer, prover corruption, or governance action is required, only ordinary participation in an already-permissionless message-processing path.

### Recommendation
- Do not evict a height from `BoundedStateCommitments`/`StateCommitmentQueue` if it is still referenced by an outstanding, unclaimed relayer fee/reward record (e.g., cross-check against `RequestCommitments`/`OutboundRequestsClaimed`/`OutboundConsensusRotationsClaimed` before eviction, or maintain a "pinned heights" set).
- Alternatively, increase and rate-limit the growth of `StateCommitmentQueue` insertions per block/consensus-update batch so it cannot be driven to evict recent history faster than legitimate claimants can react, and/or extend the queue depth dynamically based on outstanding claim backlog.
- Emit and monitor for near-cap eviction events so operators can react before economically significant heights are lost.

### Proof of Concept
1. Identify a connected `StateMachineId` whose `StateMachineCommitmentCap` is at (or defaults to) a value the attacker can outpace (e.g., a chain finalizing frequently, or one where cap has not been explicitly raised).
2. A relayer legitimately delivers a request/response at height `H` and is now entitled to submit `claim_outbound_request_delivery_reward`/`accumulate_fees` referencing height `H`'s commitment as proof anchor, but has not yet submitted the claim.
3. An attacker (any unsigned-extrinsic submitter) repeatedly calls `handle_unsigned` with valid `ConsensusMessage`s carrying many intermediate heights for the same `StateMachineId`, each processed for free via `update_client`, each appended to `StateCommitmentQueue`. [7](#0-6) 
4. Once cumulative insertions exceed the cap by enough to evict height `H`, `BoundedStateCommitments::<T>::get(H)` returns `None`. [3](#0-2) 
5. The relayer's subsequent `claim_outbound_request_delivery_reward`/`accumulate_fees`/`process_outbound_consensus_delivery_claim` call against height `H` now fails at `validate_state_machine`/`verify_withdrawal_proof` with `OutboundDestinationStateNotKnown`, permanently denying the reward for that already-completed, legitimate delivery. [5](#0-4)

	/// Per-chain FIFO queue of heights retained in [`BoundedStateCommitments`]
	/// and [`BoundedStateMachineUpdateTime`], keyed by a monotonically
	/// increasing insertion index. Insertion order matches height order because
	/// consensus updates only ever advance a state machine, so evicting at the
	/// head removes the oldest height. Entries whose height was vetoed via
	/// `delete_state_commitment` are left in place and become harmless no-ops
	/// when their index is evicted.
	///
	/// Each insertion touches O(1) small storage items, so the per-chain cap
	/// can grow without adding I/O or PoV weight to the insert path.
	#[pallet::storage]
	pub type StateCommitmentQueue<T: Config> = StorageDoubleMap<
		_,
		Blake2_128Concat,
		StateMachineId,
		Twox64Concat,
		u64,
		u64,
		OptionQuery,
	>;

	/// Head/tail indices for [`StateCommitmentQueue`], per chain.
	#[pallet::storage]
	pub type CommitmentQueueStates<T: Config> =
		StorageMap<_, Blake2_128Concat, StateMachineId, CommitmentQueueState, ValueQuery>;

	/// Per-chain override for the number of state commitments retained. Chains
	/// with faster finality emit state machine updates more frequently and
	/// need a deeper queue to retain the same wall-clock window of provable
	/// heights. Falls back to [`MAX_STATE_MACHINE_COMMITMENTS`] when unset.
	#[pallet::storage]
	pub type StateMachineCommitmentCap<T: Config> =
		StorageMap<_, Blake2_128Concat, StateMachineId, u32, OptionQuery>;

// A height below the latest can never be resubmitted — the consensus handler skips
// anything at or below `previous_latest_height` — so its stale queue entry has no
// live twin and evicting it touches nothing.
#[test]
fn vetoed_height_that_cannot_be_resubmitted_evicts_as_a_noop() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Veto a height below the latest: the commitment goes away immediately while
		// its queue entry stays behind as a stale index. The latest height is
		// untouched, so 10 stays permanently unsubmittable.
		host.delete_state_commitment(StateMachineHeight { id, height: 10 }).unwrap();
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 10 }).is_err());
		assert_eq!(host.latest_commitment_height(id).unwrap(), 11);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 0, tail: 2 }
		);
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 0), Some(10));

		// The stale index is evicted as a no-op on the next insertion.
		store(12);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 1, tail: 3 }
		);
		assert!(StateCommitmentQueue::<Test>::get(id, 0).is_none());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
	})
}
