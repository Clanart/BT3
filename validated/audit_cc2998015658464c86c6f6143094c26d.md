### Title
Permissionless `donateRewards` allows attacker to steal queued rewards via total-staked manipulation - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`donateRewards()` in `BaseRewardPoolV2.sol` is callable by anyone (no `onlyManager`/access control) and triggers `_provisionReward`, which folds any previously accumulated `queuedRewards` into `rewardPerTokenStored` divided by the *current* `totalStaked()`. By becoming the sole staker with a dust amount right after `totalStaked()` returns to zero, an attacker can call `donateRewards` with 1 wei to force the entire `queuedRewards` balance to be distributed as if it belonged 100% to their dust stake, then immediately withdraw and claim it.

### Finding Description
In `_provisionReward` [1](#0-0) , when `totalStaked() == 0` any incoming reward (via `donateRewards` or `queueNewRewards`) is only added to `rewardInfo.queuedRewards`, without updating `rewardPerTokenStored`. The conversion of `queuedRewards` into `rewardPerTokenStored` only happens on the *next* call to `_provisionReward` while `totalStaked() > 0`, and it is divided by the total staked amount **at that moment**, not at the time the reward accrued.

`donateRewards` has no access restriction beyond the token being a registered reward token: [2](#0-1) . Any unprivileged address holding 1 wei of an already-registered reward token can call it at will.

Exploit flow in `BribeRewardPool` (which inherits `BaseRewardPoolV2` and overrides `totalStaked()`/`balanceOf()` with its own accounting) [3](#0-2) :
1. Last legitimate staker calls `withdrawFor`, bringing `totalSupply` (i.e. `totalStaked()`) to 0. Any reward previously queued while stakers existed has already been folded into `rewardPerTokenStored` at that point, but from now on any *new* incoming reward will sit in `queuedRewards` since `totalStaked()==0`.
2. Reward accrues in `queuedRewards` (e.g. a legitimate `queueNewRewards` call by a manager, or the attacker's own dust `donateRewards`) while `totalStaked()==0`.
3. Attacker calls `stakeFor` (via MasterMagpie/WombatBribeManager) with a dust amount (e.g. 1 wei), becoming the sole staker. `updateRewards` modifier in `stakeFor` runs before the stake is recorded, so `userRewardPerTokenPaid` is set to the *pre-fold* value [4](#0-3) .
4. Attacker calls `donateRewards(1, token)` again. Now `totalStaked() = 1` (the attacker's own dust stake), so `_provisionReward` folds `queuedRewards + 1` into `rewardPerTokenStored` by dividing by `totalStaked() = 1`, i.e. `rewardPerTokenStored` jumps by the full queued amount scaled by `10**stakingTokenDecimals`.
5. Attacker calls `withdrawFor(..., claim = true)`. The `updateRewards` modifier computes `_earned` using the attacker's full pre-withdraw balance and the now-inflated `rewardPerToken`, crediting the attacker with (approximately) the entire `queuedRewards` amount, which is then transferred out via `_getReward` [5](#0-4) .

No modifier, `nonReentrant` guard, or minimum-stake/time-weighting check prevents this: `donateRewards` lacks manager restriction, and the reward math distributes strictly based on instantaneous `totalStaked()`, not a time-weighted or snapshot-based measure.

### Impact Explanation
This allows direct theft of yield: an attacker with a dust stake can redirect rewards that accrued for the general pool of future stakers (queued while `totalStaked()==0`) entirely to themselves, at the expense of legitimate stakers who deposit shortly after. This matches "theft or permanent freezing of unclaimed yield" / "direct theft of user funds via first-staker-after-zero-totalStaked capturing 100% of queuedRewards."

### Likelihood Explanation
The attack requires only: (a) the ability to observe/front-run the moment `totalStaked()` becomes 0 (which naturally occurs whenever a pool's sole/last staker withdraws, common in single-user or low-TVL bribe pools), and (b) 1-2 wei of an already-registered reward token plus a trivial staking amount. No special privileges are needed — `donateRewards` is fully permissionless, and `stakeFor`/`withdrawFor` are reachable by any address through the normal MasterMagpie/WombatBribeManager deposit/withdraw entry points. The attack is repeatable every time `totalStaked()` transitions from 0 back to nonzero while `queuedRewards` is nonzero.

### Recommendation
- Restrict `donateRewards` folding logic so a single block's dust stake cannot manipulate the queued-reward distribution ratio, e.g. require a minimum stake duration/checkpoint before rewards accrued during a zero-`totalStaked` window can be claimed, or distribute `queuedRewards` pro-rata based on stake-time-weighted accounting rather than instantaneous `totalStaked()`.
- Alternatively, disallow `donateRewards`/`queueNewRewards` from folding `queuedRewards` into `rewardPerTokenStored` within the same block/transaction as a stake change for the caller (add a cooldown or a minimum staking-token balance threshold before considering `totalStaked()` "reactivated").
- Consider guarding against extremely small `totalStaked()` values (e.g. 1 wei) causing outsized `rewardPerTokenStored` jumps by enforcing a minimum stake amount in `stakeFor`.

### Proof of Concept
Foundry test plan:
1. Deploy `BaseRewardPoolV2`/`BribeRewardPool` with a mock `MasterMagpie` operator and a registered reward token; deploy a mock staking token.
2. Staker A stakes 1000 tokens via `stakeFor`. Manager calls `queueNewRewards(1000e18, rewardToken)` — verify `rewardPerTokenStored` updates and `earned(A)` reflects the full amount pro-rata.
3. Staker A calls `withdrawFor(1000, claim=true)` — `totalStaked()` becomes 0.
4. A third party (or manager) calls `queueNewRewards(1000e18, rewardToken)` again while `totalStaked()==0` — assert `rewards[rewardToken].queuedRewards == 1000e18` and `rewardPerTokenStored` unchanged.
5. Attacker calls `stakeFor(attacker, 1)` (simulate MasterMagpie call), then `donateRewards(1, rewardToken)`.
6. Assert `rewardPerTokenStored` jumped to reflect nearly the entire 1000e18 queued reward divided by `totalStaked()=1`.
7. Attacker calls `withdrawFor(attacker, 1, claim=true)`.
8. Assert attacker received ~1000e18 reward tokens (`earned(attacker, rewardToken)` before withdrawal ≈ `1000e18`), despite having staked only 1 wei for a single transaction, proving disproportionate capture of `historicalRewards` relative to any real stake-time window.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }

        for (uint256 index = 0; index < length; ++index) {

            uint256 reward = earned(_account, rewardToken);
