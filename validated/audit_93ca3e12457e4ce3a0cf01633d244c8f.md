### Title
Outputs sent to internal offset addresses (Branch/Change/Forwarded) are scanned but silently dropped from accounting - ([File: processor/src/multisigs/mod.rs])

### Summary
The ADRIRO finding concerned an internally tracked balance (`trackedCvxBalance`) which failed to account for tokens arriving through an untracked path (reward claims), causing the tracked accounting to diverge from actual owned funds. Serai's Bitcoin integration has the analogous bug class: the `Scanner` tracks which script pubkeys correspond to which logical `OutputType`, and the processor only reports outputs classified as `External` (plus forwarded outputs during rotation). Any funds sent to the multisig's internal offset addresses — `Branch`, `Change`, or `Forwarded` — are successfully scanned yet discarded from accounting, even though they are spendable by the same multisig key.

### Finding Description
`scanner()` in `processor/src/networks/bitcoin.rs` deterministically registers three internal offsets (`BRANCH_OFFSET`, `CHANGE_OFFSET`, `FORWARD_OFFSET`) derived via `Secp256k1::hash_to_F(KEY_DST, ...)` — values anyone can compute — alongside the zero offset used for `External` outputs. [1](#0-0) 

When a block is scanned, `get_outputs` maps every matched output's offset back to its `OutputType` via `kinds[offset_repr_ref]`, so an arbitrary on-chain payment to the change or forward address is labeled `Change`/`Forwarded`, not `External`. [2](#0-1) 

Then `scanner_event_to_multisig_event` handles only `Forwarded` outputs (and only during `ForwardFromExisting` rotation) before retaining `External` outputs exclusively: [3](#0-2) 

Outside of the forwarding window — which is the normal steady state — an output classified `Change`, `Branch`, or `Forwarded` is dropped by the `retain` and never becomes an instruction, plan, or scheduler-visible UTXO. Like `trackedCvxBalance` missing reward-deposited CVX, the tracked set of owned UTXOs now diverges from the actual funds controlled by the key: the coins sit at an address whose spend path requires the multisig key plus a publicly derivable offset, yet no component is ever told they exist.

### Impact Explanation
An unprivileged party (or simply a confused/sophisticated user) can send BTC to the multisig's change or forward script — both trivially derivable from the public group key and the public `hash_to_F` offsets, and also observable on-chain after any spend. Those funds are owned by the protocol and spendable by the threshold key, but are never credited: the scheduler's `utxos` set (`processor/src/networks/bitcoin.rs` → `utxo.rs` `Scheduler::utxos`) never learns of them, so they are permanently unavailable for payments. This is the "funds reported received that are not spendable" acceptance criterion, inverted: funds received that are never reported. If a user mistakenly pays a refund/deposit to the change address observed in a prior transaction, the deposit is irrecoverable from the protocol's accounting even though it confirms on-chain.

### Likelihood Explanation
The trigger requires only a standard P2TR payment to a deterministically computable or publicly visible address — reachable by any Bitcoin sender with no protocol access. Mistaken sends to a change address are a realistic occurrence (users copying a prior output address from a block explorer). The dropped accounting is unconditional: the `retain` filter executes for every block regardless of rotation step outside `ForwardFromExisting`.

### Recommendation
Mirror the report's fix shape — reconcile actual scanned funds with tracked accounting rather than assuming only expected paths deposit funds. Options:
- In `get_outputs`, only treat an output as `Change`/`Branch`/`Forwarded` if the spending transaction is one the protocol itself produced (e.g., match `tx.id()` against eventualities); otherwise classify it `External` so it is reported and refunded/credited normally.
- Alternatively, emit a distinct event for unexpected internal-offset outputs so they can be swept or refunded instead of being silently dropped by `outputs.retain(|o| o.kind() == OutputType::External)`.

### Proof of Concept
1. Compute `change_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change")` and increment per `register_offset` until `group_key + G*offset` is even (all values public — `processor/src/networks/bitcoin.rs:320-344`, `networks/bitcoin/src/wallet/mod.rs:180-196`).
2. Send a normal P2TR payment to `p2tr_script_buf(group_key + G*change_offset)` in a confirmed, non-coinbase transaction.
3. `get_outputs` scans it and assigns `kind = OutputType::Change` via `kinds[offset_repr]` (`bitcoin.rs:693-697`).
4. `scanner_event_to_multisig_event` skips it in the `Forwarded` loop and removes it in the `External` retain (`mod.rs:824-837`). No instruction/plan is created; the UTXO never enters `Scheduler::utxos` despite being spendable by the multisig — identical in effect to CVX reward tokens missing from `trackedCvxBalance`.

    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
