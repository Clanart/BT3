### Title
Integer underflow in `AccountKeyWeightedMultiSig.SigValidationGas` causes gas-accounting corruption for zero-signature transactions - ([File: blockchain/types/accountkey/account_key_weighted_multi_sig.go])

### Summary
The CVE-2017-14496 bug class (integer underflow in a length/count computation reachable from an untrusted, remote-supplied value, leading to DoS) maps to `AccountKeyWeightedMultiSig.SigValidationGas`, which computes `uint64(numSigs-1) * params.TxValidationGasPerKey` using an attacker-influenced signature count without a zero-guard.

### Finding Description
`SigValidationGas` is called from `Transaction.ValidateSender` and `Transaction.ValidateFeePayer` with `numSigs = len(pubkey)`, where `pubkey` is the slice of ECDSA public keys recovered from the transaction's `TxSignatures` via `RecoverTxPubkeys`/`RecoverPubkey`: [1](#0-0) [2](#0-1) 

`RecoverPubkey` builds `pubkeys := make([]*ecdsa.PublicKey, len(t))` directly from the length of the decoded `TxSignatures` slice with no minimum-length check, so `numSigs` can be `0` if a transaction is submitted/decoded with an empty signature list: [2](#0-1) 

In `AccountKeyWeightedMultiSig.SigValidationGas`, when the Istanbul rule is active, the gas cost is computed as:
```go
isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul
if isIstanbul {
    return uint64(numSigs-1) * params.TxValidationGasPerKey, nil
}
``` [3](#0-2) 

`numSigs` is a signed `int`. When `numSigs == 0`, `numSigs-1 == -1`; converting `-1` to `uint64` silently underflows to `18446744073709551615` (2^64-1). This value is then multiplied by `params.TxValidationGasPerKey`, which itself wraps around in unchecked `uint64` multiplication, producing an unpredictable, attacker-uncontrolled but deterministic "signature validation gas" value — an integer underflow directly analogous to the `add_pseudoheader` length-subtraction bug in the reported CVE (subtracting a fixed constant from an attacker-influenced/zero count without a lower-bound check).

This computed value (`gasKey`) is returned up through `ValidateSender`/`ValidateFeePayer` into the transaction pool's `validateTx`, where it becomes part of the intrinsic-gas / floor-gas admission check: [4](#0-3) 

Because `SigValidationGas` is invoked **before** `accountkey.ValidateAccountKey` performs signature-content validation, the underflow occurs purely from the recovered-signature *count*, independent of whether the (missing) signature would ultimately be considered cryptographically valid.

### Impact Explanation
An underflowed/overflowed `sigValGas` corrupts the gas-accounting invariant `tx.Gas() < intrGas + sigValGas` used both in tx-pool admission and in state-transition gas accounting for multisig-keyed accounts. Depending on the wrapped value, this can (a) cause legitimate transactions from multisig accounts to be spuriously rejected (denial of service against that account/DApp), or (b) — if the wrapped product happens to be small — allow a transaction to be admitted with insufficient gas reserved for the actual signature-validation work the EVM/state-transition performs, undermining the gas metering that funds computation cost. Both outcomes fall under gas/fee accounting abuse or availability denial for a specific unprivileged flow (any account owner who is, or is made to interact with, an `AccountKeyWeightedMultiSig` account under Istanbul rules).

### Likelihood Explanation
Reaching `numSigs == 0` requires a transaction whose `TxSignatures` list is empty at the point `ValidateSender`/`ValidateFeePayer` is called. I could not fully confirm within the available context whether `SanityCheckSignatures` (which explicitly rejects `len(sigs) == 0`) is guaranteed to run *before* `ValidateSender` on every ingress path (e.g., `TxPool.AddRemote` → `validateTx`, and RPC `SendRawTransaction`). The code shown for `TxPool.validateTx` calls `tx.ValidateSender` directly without a visible prior signature-count sanity gate in that function. This is the main open uncertainty for exploitability; if such a gate exists earlier in the ingestion pipeline (RLP decode or an earlier `Validate()` call not shown here), likelihood is Low; if not, likelihood is Medium-High for accounts already configured with `AccountKeyWeightedMultiSig`.

### Recommendation
Add an explicit guard in `AccountKeyWeightedMultiSig.SigValidationGas` (and audit all other `SigValidationGas` implementations) to reject or clamp `numSigs <= 0` before the subtraction, e.g.:
```go
if numSigs <= 0 {
    return 0, kerrors.ErrZeroLength // or an explicit "insufficient signatures" error
}
return uint64(numSigs-1) * params.TxValidationGasPerKey, nil
```
Additionally, verify/enforce that `SanityCheckSignatures`/minimum-signature-count validation unconditionally precedes any call into `ValidateSender`/`ValidateFeePayer` across every transaction-ingress path (tx pool, block processing, RPC), and add a unit test asserting `SigValidationGas(_, _, 0)` returns an error rather than a wrapped/huge gas value.

### Proof of Concept
Conceptual (not fully verified end-to-end due to tool-call limits):
1. Configure an account with `AccountKeyWeightedMultiSig` (reachable via a standard `TxTypeAccountUpdate` from an unprivileged sender, see `blockchain/types/accountkey/account_key_weighted_multi_sig.go`).
2. Craft/submit a transaction from that account whose RLP-encoded `TxSignatures` field is an empty list (`[]`), bypassing any prior signature-count check if one is not enforced earlier in the ingestion path.
3. Observe that `Transaction.ValidateSender` calls `AccountKeyWeightedMultiSig.SigValidationGas(currentBlockNumber, RoleTransaction, 0)`, which (post-Istanbul) returns `uint64(-1) * params.TxValidationGasPerKey`, an underflowed/wrapped `uint64` value, corrupting the `intrGas + sigValGas` gas-sufficiency check in `blockchain/tx_pool.go` (`validateTx`).

Given the unresolved question of whether an earlier signature-count sanity check blocks step 2 in all ingress paths, this should be verified with a live Devin session against the full repository (RLP decode paths for `TxInternalData*` and `TxPool.AddRemote`/`add`) before treating this as confirmed-exploitable.

func (t TxSignatures) RecoverPubkey(txhash common.Hash, homestead bool, vfunc func(*big.Int) *big.Int) ([]*ecdsa.PublicKey, error) {
	var err error

	pubkeys := make([]*ecdsa.PublicKey, len(t))
	for i, s := range t {
		pubkeys[i], err = s.RecoverPubkey(txhash, homestead, vfunc)
		if err != nil {
			return nil, err
		}
	}

	return pubkeys, nil
}

func (a *AccountKeyWeightedMultiSig) SigValidationGas(currentBlockNumber uint64, r RoleType, numSigs int) (uint64, error) {
	numKeys := uint64(len(a.Keys))
	if numKeys > MaxNumKeysForMultiSig {
		logger.Warn("validation failed due to the number of keys in the account is larger than the limit.",
			"account", a.String())
		return 0, kerrors.ErrMaxKeysExceedInValidation
	}
	if numKeys == 0 {
		logger.Error("should not happen! numKeys is equal to zero!")
		return 0, kerrors.ErrZeroLength
	}

	isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul
	if isIstanbul {
		return uint64(numSigs-1) * params.TxValidationGasPerKey, nil
	}
	return (numKeys - 1) * params.TxValidationGasPerKey, nil
```
