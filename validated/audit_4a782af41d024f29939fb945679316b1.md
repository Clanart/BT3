### Title
Type-confusion bypass of `session_shop_conflicts_with_params` via non-String `shop` param allows stale session to persist despite shop mismatch - ([File: lib/shopify_app/controller_concerns/login_protection.rb])

### Summary
`session_shop_conflicts_with_params` only flags a shop/session mismatch when `params[:shop].is_a?(String)`. By supplying `shop` as an array or hash (e.g. `shop[]=other-shop.myshopify.com`), an attacker-controlled request can make this guard silently evaluate to `nil`/false, so `login_again_if_different_user_or_shop` never clears the session or redirects to login even though the request's declared shop differs from the shop bound to the existing session cookie.

### Finding Description
`EnsureHasSession` registers `before_action :login_again_if_different_user_or_shop` on the non-token-exchange path [1](#0-0) . That method only takes action if either `session_id_conflicts_with_params` or `session_shop_conflicts_with_params` returns true [2](#0-1) .

`session_shop_conflicts_with_params` is implemented as:
```ruby
def session_shop_conflicts_with_params
  current_shopify_session && params[:shop].is_a?(String) && current_shopify_session.shop != params[:shop]
end
``` [3](#0-2) 

Because Rails parses `shop[]=x` or `shop[a]=b` query strings into an `Array`/`ActionController::Parameters` rather than a `String`, `params[:shop].is_a?(String)` evaluates to `false` for such inputs, short-circuiting the whole expression to `false`/`nil` regardless of any actual mismatch between the request's intended shop and the session's bound shop. This is a purely attacker-controlled request parameter — no JWT, HMAC, or valid session token is needed to shape it, since it is evaluated before any signature check on this path (the guard runs as a `before_action` ahead of `activate_shopify_session`).

By contrast, `session_id_conflicts_with_params` does not have this specific bypass, because when `params[:session]` is an Array it still fails the `!=` comparison against the String `shopify_session_id`, so a mismatch is still (over-)detected in that case [4](#0-3) .

The result: an attacker who can get a victim to load `GET /resource?shop[]=attacker-shop.myshopify.com` (or any non-string `shop` param) while the victim carries a session cookie bound to a different, legitimate shop causes the "different shop" detection to be skipped. `activate_shopify_session` then proceeds using the *existing* session (still correctly bound to its real shop via cookie-derived session id) [5](#0-4) , while the surrounding view/embedded context and any code trusting `params[:shop]`/`current_shopify_domain` (which falls back to `requested_shopify_domain` derived from sanitized params, or to the session's shop) can become inconsistent — `current_shopify_domain` prefers `requested_shopify_domain` first [6](#0-5) . This defeats the intended defense-in-depth check whose entire purpose is to force logout/relogin whenever the URL-declared shop diverges from the session's actual shop (e.g., after switching stores in the Shopify Admin/embedded iframe), enabling continued use of a stale session in a shop context the request claims to be a different one.

### Impact Explanation
This is a session-shop binding integrity weakness (cross-shop/session confusion class). The actual token/session used remains cryptographically bound to its original shop (no forced impersonation of a foreign shop's token), so this does not directly grant access to another shop's access token. The concrete impact is limited to defeating the "log in again if different shop" safety net that normally clears a stale/mismatched session and forces re-authentication — allowing a session tied to shop A to keep being used on requests that declare shop B via `shop[]=`, undermining the invariant the check is meant to enforce (SESSION_BINDING / TENANT_ISOLATION safety net), rather than a full authentication bypass or direct data-exfiltration primitive.

### Likelihood Explanation
Trivially reachable and repeatable: any unauthenticated/unprivileged client can append `shop[]=...` to any URL under `EnsureHasSession` (non-token-exchange path) that carries a valid session cookie. No secrets, JWTs, or HMACs are required to trigger the code path — it only requires crafting the query string shape, which is fully attacker-controlled.

### Recommendation
Change `session_shop_conflicts_with_params` to compare based on the presence of a shop param without relying on `is_a?(String)` gating the entire check — e.g., coerce/sanitize the param first (similar to `ShopifyApp::Utils.sanitize_shop_domain`) and treat any non-normalizable/non-string value as a conflict (or explicitly reject non-string `shop`/`session` params with a 400 before the login-protection check runs).

### Proof of Concept
```ruby
test "shop param as array bypasses conflict detection and session is not cleared" do
  # session cookie bound to shop "session-shop.myshopify.com"
  fake_session = ShopifyAPI::Auth::Session.new(shop: "session-shop.myshopify.com", id: "session-id")
  @controller.stubs(:current_shopify_session).returns(fake_session)

  get :index, params: { shop: ["other-shop.myshopify.com"] }

  # Expected (secure) behavior: session cleared + redirect to login
  # Actual (bypass) behavior:
  assert_response :success
  assert_nil session[:return_to] # clear_shopify_session / redirect_to_login never invoked
end
```
Expected secure behavior: `session_shop_conflicts_with_params` should detect the mismatch and the request should be redirected to login with the session cleared; instead, because `params[:shop].is_a?(String)` is `false` for the array value, `login_again_if_different_user_or_shop` takes no action and the controller action proceeds using the pre-existing session.

    def activate_shopify_session
      if current_shopify_session.blank?
        signal_access_token_required
        ShopifyApp::Logger.debug("No session found, redirecting to login")
        return redirect_to_login
      end

      if ShopifyApp.configuration.check_session_expiry_date && current_shopify_session.expired?
        ShopifyApp::Logger.debug("Session expired, redirecting to login")
        clear_shopify_session
        return redirect_to_login
      end

      if ShopifyApp.configuration.reauth_on_access_scope_changes &&
          !ShopifyApp.configuration.user_access_scopes_strategy.covers_scopes?(current_shopify_session)
        clear_shopify_session
        return redirect_to_login
      end

      begin
        ShopifyApp::Logger.debug("Activating Shopify session")
        ShopifyAPI::Context.activate_session(current_shopify_session)
        yield
      ensure
        ShopifyApp::Logger.debug("Deactivating session")
        ShopifyAPI::Context.deactivate_session
      end
    end
