### Title
Unchecked division by an attacker-controlled zero `Duration` causes integer divide-by-zero crash - (File: `src/google/protobuf/util/time_util.cc`)

### Summary
The imlib2 CVE-2011-5326 root cause is a missing check that a derived arithmetic denominator can be zero when it is computed from otherwise-valid, attacker-controlled geometric input (a "2x1 ellipse"), causing a hardware divide trap that crashes the process. The transferable invariant is: *any bounded, schema-valid, attacker-controlled numeric field that is later used as a raw arithmetic divisor without an explicit non-zero check will crash the process via an integer division trap*, independent of memory-safety exploitation. In upstream Protobuf, `google::protobuf::util::TimeUtil`'s `Duration` arithmetic operators perform exactly this class of unchecked division: `operator/=(Duration&, int64_t)` and `int64_t operator/(const Duration&, const Duration&)` divide a 128-bit accumulator by a value derived directly from parsed field data with no zero check.

### Finding Description
`Duration` and `Timestamp` are standard well-known-type Protobuf messages. Their `seconds`/`nanos` fields are fully attacker-controlled after a normal, bounded `ParseFromString`/`MergeFrom` call — no schema, registry, or plugin trust is required, since these are ordinary `int64`/`int32` scalar fields.

`TimeUtil` exposes public, `PROTOBUF_EXPORT` arithmetic operators for `Duration` that are part of Protobuf's supported utility surface [1](#0-0) . Two of them divide by a value that can be attacker-controlled and zero, with no precondition check anywhere in the implementation:

```cpp
Duration& operator/=(Duration& d, int64_t r) {  // NOLINT
  ...
  value /= static_cast<uint64_t>(r);
  ...
}
``` [2](#0-1) 

```cpp
int64_t operator/(const Duration& d1, const Duration& d2) {
  bool negative1, negative2;
  absl::uint128 value1, value2;
  ToUint128(d1, &value1, &negative1);
  ToUint128(d2, &value2, &negative2);
  int64_t result = absl::Uint128Low64(value1 / value2);
  ...
}
``` [3](#0-2) 

`ToUint128` converts a `Duration` message's `seconds`/`nanos` fields directly into the 128-bit dividend/divisor with no range or non-zero validation [4](#0-3) . `Duration{seconds:0, nanos:0}` (the default, zero-initialized value — trivially producible by parsing an empty/all-default `Duration` message from an attacker) yields `value2 == 0` in `operator/`, or a caller passing `r == 0` directly to `operator/=`. Both invoke `absl::uint128` integer division by zero, which traps (SIGFPE-class abort) rather than raising a catchable C++ exception — this mirrors the "divide-by-zero error and application crash" invariant failure in the imlib2 CVE, where a degenerate-but-valid geometric input (2x1 ellipse) reached an unguarded division.

There is no `IsDurationValid()`/non-zero check performed by these operators; `IsDurationValid` only validates range and sign consistency and is not called from the division operators [5](#0-4) .

Consuming-application exposure assumption: a service that parses an untrusted `Duration` (e.g. a rate/quota/timeout duration field embedded in a request or a `google.protobuf.Duration` well-known-type field of an RPC message) and subsequently divides another `Duration` by it (a common pattern, e.g. computing a ratio/rate: `total_duration / attacker_supplied_interval`) will crash whenever the attacker supplies a zero (or default/unset) `Duration`.

### Impact Explanation
A crash-only, unauthenticated, remotely triggerable denial of service: the attacker supplies a single bounded, well-formed `Duration` message (or an unset/default one) through a normal parse call, and the consuming application's use of the standard `TimeUtil`/`operator/` arithmetic — a documented, supported part of the Protobuf C++ API — aborts the process via an unrecoverable integer-division trap. This matches the CVSS profile of the analog CVE: Availability-only impact, no confidentiality/integrity effect, network-reachable, no privileges/interaction required.

### Likelihood Explanation
High for any service that performs `Duration`/`Duration` ratio arithmetic (a documented, intended use of these operators) on a duration field sourced from client input. The divisor requires no special crafting — the all-zero default `Duration` (i.e., simply omitting the field, since proto3 defaults `seconds`/`nanos` to 0) is sufficient, making this trivially reachable without any malformed wire bytes or parser-hardening bypass.

### Recommendation
Add explicit non-zero validation before performing the division in `operator/=(Duration&, int64_t)` and `operator/(const Duration&, const Duration&)` (and the derived `operator%=`/`operator%`), returning an error/asserting cleanly (or documenting/enforcing via `ABSL_CHECK`-with-message versus silent UB) rather than letting an attacker-controlled zero divisor reach the raw `uint128` division. At minimum, document prominently in `time_util.h` that callers must validate the divisor `Duration` is non-zero before use, since these fields may originate from untrusted parsed input.

### Proof of Concept
1. Attacker sends (or the service simply receives a request omitting) a `Duration` field, e.g. `Duration{}` (default `seconds=0, nanos=0`), parsed via `ParseFromString`/embedded message field — this is valid, bounded wire data requiring no malformed bytes.
2. Application code computes a ratio using the public API: `int64_t ratio = some_duration / attacker_duration;` where `attacker_duration` is the parsed zero `Duration`.
3. This calls `operator/(const Duration&, const Duration&)` at `src/google/protobuf/util/time_util.cc:544-554`, which computes `value1 / value2` with `value2 == 0` via `absl::uint128` division — an integer divide-by-zero trap crashes the process, analogous to imlib2's unchecked division from a degenerate (zero-width) attacker-controlled geometric input.

void ToUint128(const Duration& value, absl::uint128* result, bool* negative) {
  if (value.seconds() < 0 || value.nanos() < 0) {
    *negative = true;
    *result = static_cast<uint64_t>(-value.seconds());
    *result = *result * kNanosPerSecond + static_cast<uint32_t>(-value.nanos());
  } else {
    *negative = false;
    *result = static_cast<uint64_t>(value.seconds());
    *result = *result * kNanosPerSecond + static_cast<uint32_t>(value.nanos());
  }
}
