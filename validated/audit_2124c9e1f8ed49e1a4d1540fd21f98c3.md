### Title
Attacker-controlled Bitcoin transactions can bypass output-kind restrictions, causing external deposits to be misclassified as internal Branch/Change/Forwarded outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` attributes a `ReceivedOutput` purely by matching `output.script_pubkey` against a map of registered offset scripts, and the processor-side `get_outputs` maps the offset back to an `OutputType` (`External`, `Branch`, `Change`, `Forwarded`). There is no validation that internal-kind scripts (`Branch`, `Change`, `Forwarded`) only appear in protocol-created transactions. Because these scripts are deterministically derived from the publicly known group key via `Secp256k1::hash_to_F(KEY_DST, b"branch" | b"change" | b"forward")`, any unprivileged party can craft a Bitcoin transaction paying directly to them and have it reported under an internal `OutputType`. This mirrors CVE-2019-5779's class: an insufficient policy check on which inputs may reach a restricted path, bypassable with crafted public input. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Scanner::new`/`register_offset` build `scripts: HashMap<ScriptBuf, Scalar>` keyed only by the scriptPubKey bytes (`p2tr_script_buf(key + G*offset)`). `scan_transaction` returns a `ReceivedOutput` for *any* transaction output whose scriptPubKey is in that map, with no check on who created the transaction or what the output's intended role is. [4](#0-3) [5](#0-4) 

In `Bitcoin::get_outputs`, the scanned offset is translated to a kind via `kinds[offset_repr_ref]`, and only `OutputType::External` outputs receive `data` (the `InInstruction` payload extracted via `extract_serai_data`) and a meaningful `presumed_origin`. Outputs reported as `Branch`, `Change`, or `Forwarded` skip that processing entirely — yet nothing prevents a third party from creating such outputs, since the offsets and scripts are publicly computable. [6](#0-5) [7](#0-6) 

The implicit policy — "Branch/Change/Forwarded outputs are only produced by protocol spends or designated forward flows" — is never enforced. Any transaction on-chain that happens to pay to one of those scripts is inducted into the internal pipeline.

### Impact Explanation
- Funds sent by an arbitrary party to the `Change` or `Branch` scripts are reported to the processor as `OutputType::Change`/`Branch` rather than `External`. They are recorded without `presumed_origin` and without any `InInstruction` data, entering the same accounting path as the protocol's own internal outputs, which can corrupt balance/output bookkeeping and feed non-protocol outputs into code paths that assume protocol provenance.
- Funds sent to the `Forwarded` script are reported as `OutputType::Forwarded`, i.e., as if they went through the designated forwarding flow, again bypassing external-deposit handling.
- Severity is bounded: the outputs remain spendable by the multisig (the offset math is still correct), so this is a provenance/classification bypass rather than key compromise — consistent with Medium.

### Likelihood Explanation
Any user who knows the Serai Bitcoin group key (public on-chain) can compute `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch")` etc., derive the P2TR script, and broadcast a transaction paying to it. No privileged position, threshold collusion, or timing condition is required — only a standard Bitcoin transaction. Exploitation is therefore straightforward for any blockchain participant.

### Recommendation
Distinguish protocol-created internal outputs from externally-created ones. Options:
- In `get_outputs`, treat any output paying to `Branch`/`Change`/`Forwarded` scripts in a transaction not authored by the multisig as `OutputType::External` (or a dedicated `Unexpected` kind), still crediting the funds but forcing external-deposit handling.
- Alternatively, commit internal outputs to a per-transaction nonce/script (e.g., a script-path leaf or a per-spend offset) so external parties cannot forge the internal classification.
- Document explicitly in `Scanner::register_offset`/`scan_transaction` that script matching carries no provenance guarantee.

### Proof of Concept
1. Observe the Serai multisig's Bitcoin group key `K` (a public, even-Y Taproot key).
2. Compute `offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change")`, incrementing until `K + G*offset` is even (matching `register_offset`'s loop at `networks/bitcoin/src/wallet/mod.rs:184-195`), and build `script = p2tr_script_buf(K + G*offset)` — the exact script `scanner()` registers under `OutputType::Change` (`processor/src/networks/bitcoin.rs:337-344`).
3. Broadcast any transaction paying to `script`.
4. When the processor scans the block, `scan_transaction` matches the output (`networks/bitcoin/src/wallet/mod.rs:205`), `get_outputs` classifies it as `OutputType::Change` (`processor/src/networks/bitcoin.rs:695`), and it is emitted with no `InInstruction` data and no `presumed_origin` (`processor/src/networks/bitcoin.rs:730-736`) — indistinguishable from the protocol's own change output, despite never being created by the protocol.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
