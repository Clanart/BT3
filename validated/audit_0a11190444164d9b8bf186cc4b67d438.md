### Title
CEI-violation in `withdraw()` — external transfer executes before escrow debit, with no local replay/reentrancy guard - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron build of `IntentGatewayV2` implements its own copy of the escrow-release logic instead of reusing the audited `IntentsBase._withdraw` used by the primary EVM contracts. In this copy, `withdraw()` performs the native/ERC20 token transfer to the beneficiary **before** decrementing the corresponding `_orders[commitment][token]` escrow balance, and the cross-chain settlement entrypoint `onAccept()` calls `withdraw()` directly with no local "already processed" check of its own (unlike `cancelOrder`/`fillOrder`, which pre-check `_filled[commitment] != address(0)`). This mirrors the Balancer report's root cause: a value-releasing function is reachable without first locking/finalizing the state that should gate it, so external calls can execute against escrow state that has not yet been updated.

### Finding Description
Compare the two implementations of escrow release:

Canonical EVM contract (`evm/src/apps/intentsv2/IntentsBase.sol`, lines 390-410) decrements before transferring: [1](#0-0) 

Tron contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`, lines 682-705) transfers first, decrements after: [2](#0-1) 

The Tron `cancelOrder` also drops the `nonReentrant` modifier present on the canonical contract's `cancelOrder`: [3](#0-2) [4](#0-3) 

And `onAccept` — the cross-chain settlement handler invoked by the host for `RedeemEscrow`/`RefundEscrow` messages — calls `withdraw()` with **no** `_filled` pre-check of its own; it relies entirely on the per-token `_orders[commitment][token] == 0` check inside `withdraw()`: [5](#0-4) 

Because the native-token payout (`beneficiary.call{value: amount}("")`) executes before `_orders[body.commitment][token] -= amount`, any beneficiary/order.user contract that receives native TRX mid-loop gets code execution while the escrow ledger for that token (and any tokens later in the same `body.tokens` array) is still un-decremented. The only thing preventing a same-commitment double-release is the coarse `_filled[commitment]` flag set at the very top of `withdraw()` — a single point of failure with no defense-in-depth, unlike the canonical contract where the debit itself is the primary guard and happens strictly before interaction.

### Impact Explanation
This is a structural CEI violation on the fund-releasing code path (`withdraw()`), reachable from `cancelOrder` (attacker-controlled, since caller must be `order.user`) and from `onAccept` (host-triggered cross-chain settlement, which has no local double-processing guard beyond the per-token zero check). If the ISMP host layer ever redelivers/replays the same settlement message to `onAccept` (or any future refactor adds a second call path into `withdraw()` before `_filled` is checked), the missing decrement-before-transfer ordering removes the only safety net that would otherwise stop a duplicate token payout, resulting in double release of escrowed user/solver funds — a direct "double-settlement / fund loss" outcome matching the bounty's accepted impact classes.

### Likelihood Explanation
Exploitation requires a beneficiary/order.user that is a contract capable of executing code on receiving native TRX (trivial to construct — attacker fully controls `order.user` for same-chain cancellation) combined with either a multi-input-token order or a scenario where `onAccept` is invoked more than once for the same commitment. This is a genuine, provable deviation from the safer pattern already used elsewhere in the same repository, and it is unique to `evm/tron/contracts/apps/IntentGatewayV2.sol` — the primary EVM/`IntentsBase.sol` implementation does not have this ordering defect and does guard `cancelOrder` with `nonReentrant`.

### Recommendation
- In `withdraw()` (Tron), decrement `_orders[body.commitment][token]` **before** performing the native/ERC20 transfer, matching `IntentsBase._withdraw`'s ordering.
- Add a `nonReentrant` modifier to `cancelOrder`, `fillOrder`, and `onAccept` (or a shared reentrancy lock) in the Tron contract.
- Have `onAccept` explicitly check/set `_filled[commitment]` before calling `withdraw()`, rather than relying solely on the per-token balance check, so cross-chain settlement has the same defense-in-depth as the local cancel/fill paths.

### Proof of Concept
1. Attacker calls `placeOrder` as `order.user` (a contract with a malicious `receive()`), with two inputs: `inputs[0] = native TRX`, `inputs[1] = TRC20 token X`.
2. Attacker calls `cancelOrder(order, options)` for this same-chain order (`isSameChain` branch, `msg.sender == order.user` passes).
3. Inside `withdraw()`: `_filled[commitment]` is set, then the loop processes `inputs[0]` (native): `beneficiary.call{value: amount}("")` fires attacker's `receive()` **before** `_orders[commitment][native] -= amount` executes.
4. In `receive()`, the attacker's contract has code executing while `_orders[commitment][inputs[1].token]` is still fully credited and `_orders[commitment][TRANSACTION_FEES]` has not yet been deleted — demonstrating the CEI violation and the absence of any reentrancy lock (`nonReentrant` is present in the canonical contract's `cancelOrder` but missing here) that would otherwise contain such a callback.
5. This confirms the exploitable code-level defect; full fund-drain requires only a second reachable path into `withdraw()` for the same commitment (e.g., a replayed `onAccept` delivery), which this contract does nothing locally to prevent beyond the single `_filled` flag.
