## Title
Stale line-selection indices applied against a freshly re-fetched diff can silently commit unintended content - (File: `app/src/lib/git/apply.ts`)

### Summary
This is a structural analog of the reported bug class: a value (in the stUSDC case, a share/USD conversion rate) is computed once and then re-applied later against a state that may have drifted, corrupting the final result. In GitHub Desktop, the equivalent "conversion rate" is the `DiffSelection` a user builds while reviewing a rendered diff (a set of absolute line indices, e.g. `hunk.unifiedDiffStart + lineIndex`). That selection is stored on the `WorkingDirectoryFileChange` in application state. When the user commits, `applyPatchToIndex` does **not** reuse the diff the user actually looked at — it fetches a brand-new diff from disk/git and reapplies the old numeric selection to it.

### Finding Description
In `applyPatchToIndex`, the diff used to build the commit patch is fetched fresh at commit time: [1](#0-0) 
and is then passed straight into `formatPatch(file, diff)` along with `file.selection`, which was computed earlier (in the UI) against whatever diff was rendered at selection time: [2](#0-1) 

`formatPatch` decides whether each line of the **new** diff is included based purely on a positional index (`absoluteIndex = hunk.unifiedDiffStart + lineIndex`) matched against the selection bitmap: [3](#0-2) 

There is no verification that the diff used to compute `file.selection` is the same diff being patched here. The application does have logic elsewhere that recomputes *which* line indices are still selectable when a diff changes while it's on-screen: [4](#0-3) 
but this only runs opportunistically when the Changes diff viewer re-renders — it is not invoked as a guard inside `stageFiles`/`applyPatchToIndex` before the patch is generated, and it does not detect content changes that preserve line counts/positions but change content (e.g., another process rewriting the file, an editor autosave, an `.gitattributes`/filter change, or file-watcher-driven refresh racing the click of "Commit").

`stageFiles` (`app/src/lib/git/update-index.ts`) calls `applyPatchToIndex` per file for any partially-selected file: [5](#0-4) 
and `file.selection` there is whatever was cached on the `WorkingDirectoryFileChange` object in `_commitIncludedChanges`: [6](#0-5) 

If the on-disk file (and therefore the true diff/hunk layout) changes between the moment the user finishes selecting lines and the moment `applyPatchToIndex` re-fetches the diff and re-applies those numeric indices, the same absolute index can now point at a different line, a shifted hunk, or a line that no longer exists — causing lines the user never selected to be silently staged/committed, or lines they did select to be silently dropped.

### Impact Explanation
This corrupts what the user actually commits without any error or confirmation — the exact "silent corruption of what the user commits or pushes" impact class called out as valid. An attacker who can cause the working tree to change during the narrow window between diff-render/selection and clicking "Commit" (e.g. a build tool, a pre-existing background process the repo triggers, a symlinked/generated file, or content updated by a concurrent `git checkout`/stash/pull Desktop itself may kick off) can get unintended content included in a commit that then gets pushed, potentially exposing secrets or injecting unreviewed code that the user never explicitly selected.

### Likelihood Explanation
Requires the working directory to change between diff render and commit execution — this is plausible in ordinary developer workflows (auto-formatters, editors with autosave, background scripts, generated files) without any attacker needing local/physical access beyond controlling repository content/tooling that already runs against the working tree, which is within the allowed threat model (attacker-controlled repo content).

### Recommendation
Do not reuse a previously-computed positional `DiffSelection` against a diff fetched at a different point in time. `applyPatchToIndex` should either: (1) re-validate that the diff it just fetched is structurally identical (same hunks/line count/content hashes) to the diff the selection was derived from before applying it, aborting/re-prompting if not; or (2) capture and pass through the exact diff object that was displayed/selected against (as `discardChangesFromSelection` already does by taking `diff` as a parameter) rather than re-fetching inside `applyPatchToIndex`, and refuse to stage if the working tree file has been modified since that diff was generated.

### Proof of Concept
1. Modify a tracked file so it has multiple hunks; open it in Desktop's Changes view and select only specific lines/hunks (this builds a `DiffSelection` keyed to absolute line indices of the diff currently rendered).
2. Before clicking "Commit", have another process (editor autosave, script, `git stash pop`, generated file writer) rewrite the file so hunk boundaries shift (e.g., add/remove a line above the previously selected hunk) without the Changes view being refreshed/re-rendered in time.
3. Click "Commit". `applyPatchToIndex` calls `getWorkingDirectoryDiff` (`app/src/lib/git/apply.ts:60`) and gets the new diff, then applies the stale `file.selection` indices via `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`).
4. Inspect the resulting commit: it contains different lines than what was visually checked/unchecked by the user in step 1, demonstrating silent corruption of committed content.
