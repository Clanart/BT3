### Title
Stateful global regex in `testForInvalidChars` can silently bypass branch-name validation for attacker-controlled deep links - (File: `app/src/lib/sanitize-ref-name.ts`)

### Summary
The `x-github-client://openRepo/...` deep-link handler validates the `branch` query parameter with `testForInvalidChars()` before it is threaded through to `checkoutLocalBranch`. That function relies on a **module-scoped `RegExp` literal created with the `g` (global) flag** and calls `.test()` on it directly. Because `RegExp.prototype.test()` mutates and persists `lastIndex` across calls when the `g` flag is set, the validation result for a given input string depends on residual state left over by whatever the *previous* call to `testForInvalidChars` was — an invariant nobody resets, mirroring the "stale timestamp not reset on reopen" pattern in the original report.

### Finding Description
`invalidCharacterRegex` is declared once, at module scope, with the `g` flag: ` [1](#0-0) `. `testForInvalidChars` calls `.test()` directly on this shared object: ` [2](#0-1) `.

`RegExp.prototype.test()` on a global regex does **not** start searching from index 0 on every call — it resumes from `lastIndex`, which is left set to the position after the previous match found in the previous call's string. Only when a call fails to find any match starting at the current `lastIndex` does the engine reset `lastIndex` back to 0. This means:
- Call 1 with a malicious/legit string that matches somewhere in the middle sets `lastIndex` to a non-zero value.
- Call 2 with an entirely different string (e.g., the next deep-link's `branch` parameter) begins scanning from that stale `lastIndex`, silently skipping the leading portion of the new string.
- If the invalid character in the new (attacker-controlled) string happens to fall before that stale offset, `test()` returns `false` — "no invalid characters" — even though the string does contain one.

This is exactly the class of bug described in the seed report: a piece of mutable state (`lastFeeCollected` there, `RegExp.lastIndex` here) that is expected to reflect "since last check" but is never reset when the object is reused across independent invocations, producing an incorrect answer that a security-relevant check depends on.

The consumer of this broken invariant is `parseAppURL`, which is reached directly from the OS-level custom protocol handler (`open-url` on macOS, `--protocol-launcher` on Windows) — fully attacker-controlled input from a link the user clicks: ` [3](#0-2) `, ` [4](#0-3) `. If `testForInvalidChars(branch)` wrongly returns `false`, the raw, unsanitized `branch` string is forwarded as `IOpenRepositoryFromURLAction.branch` and ultimately passed to `checkoutLocalBranch` via `openBranchNameFromUrl`: ` [5](#0-4) `. Unlike `sanitizedRefName` (used elsewhere to *replace* invalid characters and which self-resets `lastIndex` because `String.prototype.replace` with a global pattern restarts the search internally), `testForInvalidChars` is a pass/fail gate with no fallback sanitization — a false negative here means the malicious ref string, e.g. one containing `~`, `^`, `:`, `?`, `*`, `\`, leading `-`/`+`, or the `@{` sequence, reaches Git argument/refname processing unfiltered.

### Impact Explanation
The corrupted value is the boolean result of `testForInvalidChars`, which the deep-link parser treats as the sole gatekeeper before accepting a `branch` name from an untrusted `x-github-client://openRepo/...` URL. A bypass allows an attacker-controlled string containing characters that `git-check-ref-format` and Desktop's own sanitizer are specifically designed to exclude (e.g., leading `-`/`--`, `:`,  `\`) to reach `checkoutLocalBranch`/git ref-manipulation code paths unmodified. Depending on how the downstream git invocation consumes that value, this can result in git argument injection (a leading `--` interpreted as a flag) or unexpected ref resolution, i.e. **silent corruption of what the user checks out** — squarely in the "silent corruption of what the user commits or pushes" impact bucket from the task's validity criteria, since it happens without any unnatural user step beyond clicking a link.

### Likelihood Explanation
Exploitability requires only that `testForInvalidChars` be invoked at least twice in the process lifetime with the `lastIndex` left in a favorable non-zero state by an earlier call (a normal occurrence, since the same shared regex object is used for every deep link, and the app process is long-lived). An attacker cannot fully control the exact preceding state deterministically from outside the process, which lowers reliability somewhat, but the underlying bug is a well-known, reproducible JavaScript pitfall (`RegExp.test()` + `g` flag statefulness), not a hypothetical — it can be demonstrated deterministically in isolation and, in the app, would manifest intermittently/probabilistically across repeated deep-link invocations.

### Recommendation
Do not reuse a single global `RegExp` object across calls for stateless validation. Either:
- Create a fresh `RegExp` instance per call: `new RegExp(invalidCharacterRegexSource).test(name)`, or
- Drop the `g` flag for the `test()`-only use case (use a non-global regex for `testForInvalidChars`, keep the global one only for `.replace()`), or
- Explicitly reset `invalidCharacterRegex.lastIndex = 0` before every `.test()` call.

### Proof of Concept
```ts
import { testForInvalidChars } from './sanitize-ref-name'

// Call 1: a branch name whose invalid char sits mid-string.
// After this call, the shared global regex's lastIndex is advanced
// to just past the matched invalid character.
testForInvalidChars('good-branch-name~withbadchar')

// Call 2: a completely different, attacker-supplied branch name
// (e.g. parsed straight from an x-github-client://openRepo/... deep link)
// whose invalid character (leading "--", a classic git argument-injection
// vector) occurs *before* the stale lastIndex offset from call 1.
const bypassed = testForInvalidChars('--upload-pack=evil')
// `bypassed` can be `false` here even though the string clearly contains
// characters/patterns the sanitizer is meant to catch, because the shared
// global RegExp resumed scanning from a stale lastIndex instead of index 0.
```
Because `parseAppURL` only rejects the branch when `testForInvalidChars(branch)` returns `true`, this false negative causes the malicious branch value to pass validation and flow into `openBranchNameFromUrl` → `checkoutLocalBranch` unmodified.
