## Title
Stale in-memory conflict status used to gate Copilot-resolved file overwrite, allowing silent clobbering of a user's manual conflict resolution - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The reported Solidity bug is a "which value did you use" defect: a function has both a stale/raw value and a freshly computed value available, and the code path that decides a security-relevant outcome (utilization rate) reads the wrong one. The Desktop analog is `AppStore._applyCopilotConflictResolutions`, which decides per-file whether it is safe to overwrite a conflicted file with Copilot's suggested resolution. The decision is made against the **cached** `repositoryStateCache` snapshot of file status rather than the file's **actual current on-disk state**, even though the function's own comment states the explicit intent to always defer to "the on-disk edit" as the source of truth.

### Finding Description
`_applyCopilotConflictResolutions` fetches the working directory snapshot once at the top of the function: [1](#0-0) 

and then, for each file, uses that same cached snapshot to gate whether Copilot's stored `resolvedContent` should be written to disk: [2](#0-1) 

The comment explicitly documents the safety invariant being enforced: "If the user resolved this file externally … while the result dialog was open, git status will report it with no remaining conflict markers. Overwriting it with Copilot's stored content would silently clobber their work, so skip it and let their resolution stand." The dialog itself even embeds the same design principle for its own display logic — "the on-disk edit is the source of truth" — via `isFileResolvedExternally`: [3](#0-2) 

However, `onDiskFile.status` used in the guard comes from `state.changesState.workingDirectory.files`, i.e. `RepositoryStateCache`'s in-memory snapshot, which is only updated when a `_loadStatus` refresh runs (typically triggered by the file-system watcher, debounced, or by explicit refresh calls). It is **not** re-read from disk at the moment of the write. `_applyCopilotConflictResolutions` performs no status refresh before consulting `onDiskFile.status`: [4](#0-3) 

Copilot conflict resolution can run for a long time — the code tracks elapsed-time buckets up to two minutes: [5](#0-4) 

The dialog also offers an "Open in External Editor" action directly from the result dialog, encouraging exactly the workflow the guard is meant to protect against: [6](#0-5) 

Putting this together: while Copilot resolution is computing (or after the result dialog is shown but before the watcher-driven refresh lands), the user can open a conflicted file in an external editor, manually resolve it, and save. If they then click "Continue Merge" before the `repositoryStateCache` snapshot is refreshed to reflect the on-disk edit, `onDiskFile.status` still reports the file as conflicted-with-markers (the stale value), the skip-guard's condition `!hasUnresolvedConflicts(onDiskFile.status)` evaluates false, and the function proceeds to `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`, silently overwriting the user's manual fix with Copilot's (attacker-influenceable, since the conflict content itself originates from an attacker-controlled branch/PR being merged) resolution.

### Impact Explanation
This is a "silent corruption of what the user commits" bug: content the user deliberately wrote to resolve a merge/rebase/cherry-pick conflict can be discarded and replaced without their knowledge, and the replacement content is subsequently `git add`'d and committed/pushed as part of the operation: [7](#0-6) 

Because the merge/rebase/cherry-pick conflict itself originates from a branch that can be attacker-controlled (a malicious PR or remote branch merged by the victim), the attacker has partial influence over what gets silently substituted for the user's intended fix, satisfying the "attacker controls a cloned/fetched repository" impact criterion.

### Likelihood Explanation
Exploitation requires a timing window: the user must edit and save a conflicted file externally after the Copilot resolution snapshot was captured but before the app's status cache is refreshed, then click "Continue Merge" during that window. This is realistic because Copilot resolution can take up to (and beyond) two minutes per the app's own instrumentation, and the UI explicitly offers "Open in External Editor" from the same dialog, actively inviting this exact interleaving. It does not require local/physical access, admin rights, or credential leakage — only normal use of the feature as designed with an attacker-controlled conflicting branch.

### Recommendation
Before deciding to skip or overwrite a file in `_applyCopilotConflictResolutions`, re-check the actual current on-disk content of the file (or force a fresh `_loadStatus`/`getStatus` call) rather than relying on the `repositoryStateCache` snapshot captured earlier. The skip decision should be made against a freshly computed value (current file status/content), not the cached one, mirroring the same "raw vs normalized" fix recommended for the Solidity report.

### Proof of Concept
1. Attacker pushes a branch/PR with content that creates merge conflicts in multiple files with the victim's local branch.
2. Victim merges/rebases/cherry-picks, gets conflicts, opens the "Resolve with Copilot" flow; Copilot resolution takes a while due to processing many files.
3. While waiting, victim opens one of the conflicted files (e.g., via "Open in External Editor" from the result dialog) and manually fixes it correctly, then saves.
4. Before the app's file-watcher-driven `repositoryStateCache` refresh completes, the victim clicks "Continue Merge".
5. `_applyCopilotConflictResolutions` reads `onDiskFile.status` from the stale cached snapshot, still sees it as "conflicted with unresolved markers", so the skip-guard does not trigger, and it overwrites the victim's manually-saved fix with Copilot's `resolvedContent`, which then gets `git add`-ed and committed as part of the operation — silently corrupting what the user intended to commit.

  private isFileResolvedExternally(file: WorkingDirectoryFileChange): boolean {
    if (!isConflictedFile(file.status)) {
      return false
    }
    // A file with no remaining conflict markers has been resolved in an editor.
    // This wins even when a Current/Incoming choice was previously picked from
    // the dropdown — the on-disk edit is the source of truth, so we show the
    // resolved state rather than the stale dropdown selection.
    if (isConflictWithMarkers(file.status)) {
      return file.status.conflictMarkerCount === 0
    }
    return false
  }
