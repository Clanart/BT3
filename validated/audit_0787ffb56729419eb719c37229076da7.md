### Title
SignableTransaction fee/weight calculation omits the OP_RETURN data output, underestimating the required fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The YoloV2 report's bug class is "value computed over the wrong quantity" — the protocol fee used `currentEntryIndex` instead of the full deposit `count`. The direct Serai analog lives in `SignableTransaction::new`: after the OP_RETURN data output is appended to `tx_outs`, the weight/vbytes and therefore the fee and change computations are performed over `payments` only, silently dropping the data output from the accounted transaction size.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` builds the output list, optionally pushing an OP_RETURN output carrying up to 80 bytes of caller-supplied data:

- Lines 194-202: `tx_outs.push(TxOut { ... script_pubkey: ScriptBuf::new_op_return(...) })` — the data output is added to the real transaction outputs.
- Line 204: `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` — weight is computed from `payments`, which does **not** include the OP_RETURN output.
- Line 206: `let mut needed_fee = fee_per_vbyte * vbytes;` — the fee is scaled off the under-counted vbytes.
- Lines 225-233: when a `change` script is provided, `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` again omits the data output, and the change amount is computed as `input_sat - (payment_sat + fee_with_change)`, locking in the under-estimated fee.
- Line 241: the `MAX_STANDARD_TX_WEIGHT` check is applied to `weight`, which likewise never accounts for the data output.

`calculate_weight_vbytes` (lines 62-127) faithfully builds a mock transaction, but only from the `payments` slice passed in — the already-pushed OP_RETURN `TxOut` in `tx_outs` is never part of the measurement. The result: `needed_fee` equals `fee_per_vbyte * (vbytes - data_output_vsize)`, i.e., computed over the wrong quantity of outputs, exactly mirroring `valuePerEntry * currentEntryIndex` instead of `valuePerEntry * count`.

### Impact Explanation
Reachable by an unprivileged caller: `data` is an ordinary caller-supplied `Option<Vec<u8>>` to `SignableTransaction::new` (an untrusted public input, per the accepted input surface). Consequences:

1. **Fee underpayment**: the transaction actually broadcast pays `needed_fee`, which is short by `fee_per_vbyte * vsize(OP_RETURN output)` (up to ~80 payload bytes + overhead ≈ 90 vbytes ≈ 360+ weight units omitted). At a `fee_per_vbyte` near the minimum relay rate, the realized fee rate can fall below `DEFAULT_MIN_RELAY_TX_FEE`, making the transaction non-relayable/stuck even though `new()` returned `Ok`. The minimum-fee check at line 211 validates the under-estimated `needed_fee`, not the fee against the true size — the guard itself is computed over the wrong quantity.
2. **Weight check bypass**: a transaction can pass the `MAX_STANDARD_TX_WEIGHT` check while its true weight (including the data output) is larger, weakening the `TooLargeTransaction` bound.

`fee()` (lines 138-141) reports the true `inputs - outputs` and `needed_fee()` returns the under-estimate, so downstream accounting (`processor/src/networks/bitcoin.rs` fee amortization) operates on a fee figure that does not match the requested rate times actual size.

### Likelihood Explanation
Any call with `data: Some(..)` triggers the under-count; the magnitude scales with `fee_per_vbyte`. Funds are not directly stolen, but transactions produced at low fee rates can be unbroadcastable or stuck, and internal fee accounting diverges from the intended fee rate — a concrete incorrect-verifier-formula/economic-accounting analog rather than a cosmetic one. Impact is bounded (underestimate ≤ ~90 vbytes), so this maps to Medium.

### Recommendation
Include the data output in the measured output set: either pass the fully-built `tx_outs` (minus change) into `calculate_weight_vbytes`, or push a placeholder OP_RETURN `TxOut` into the mock transaction inside `calculate_weight_vbytes`. Concretely, change lines 204 and 226 to compute weight over `payments` plus the OP_RETURN output, e.g. by constructing the payment list as `tx_outs.iter().map(|o| (o.script_pubkey.clone(), 0))` before change is appended, and also recompute `weight` accordingly so the `MAX_STANDARD_TX_WEIGHT` check covers the data output.

### Proof of Concept

// In SignableTransaction::new semantics:
let data = vec![0u8; 80];
// tx_outs gets an extra ~90-byte OP_RETURN output (line 195)
// but vbytes is computed from `payments` only (line 204):
let (_, vbytes_no_data) =
    SignableTransaction::calculate_weight_vbytes(inputs.len(), payments, None);
// The real tx serializes `payments + OP_RETURN + maybe change`,
// so its true vsize = vbytes_no_data + ~91.
// needed_fee = fee_per_vbyte * vbytes_no_data < fee_per_vbyte * true_vsize.
// With change: change_value = input_sat - payment_sat - needed_fee is
// inflated by fee_per_vbyte * ~91, and the *paid* fee rate is
// needed_fee / true_vsize < fee_per_vbyte.
// At fee_per_vbyte == min relay, the paid rate falls below the relay
