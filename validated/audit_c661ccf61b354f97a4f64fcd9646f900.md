### Title
Scanner reports immature coinbase outputs as spendable, making received funds unspendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` scans every transaction in a block, including the coinbase transaction, and returns matching outputs as `ReceivedOutput`s indistinguishable from normal outputs. Bitcoin coinbase outputs are unspendable for 100 blocks; a `ReceivedOutput` carries no maturity flag, so downstream code treating scanned outputs as spendable inputs will construct transactions that the network rejects, and may account for funds that cannot actually be moved — analogous to counting a blacklisted/frozen balance as usable.

### Finding Description
`scan_block` iterates `block.txdata` unconditionally, starting at index 0, which includes the block's coinbase transaction (networks/bitcoin/src/wallet/mod.rs:221-227). `scan_transaction` matches any output whose `script_pubkey` equals a registered script (lines 199-214), with no check that the containing transaction is a coinbase (`tx.is_coinbase()` is never consulted) and no recording of maturity. If a miner pays to the Serai threshold address — which any unprivileged party/miner can cause by directing coinbase payouts to that script — the resulting `ReceivedOutput` is returned alongside spendable outputs. Any wallet/processor that feeds these outputs into a spend transaction produces an invalid transaction (BIP-30/consensus maturity rule: coinbase outputs require 100 confirmations), and any balance accounting that trusts `value()` overstates immediately available funds.

### Impact Explanation
Funds are reported received that are not spendable. A spend constructed from such outputs is consensus-invalid and rejected by all nodes, so a withdrawal/transfer relying on scanned outputs fails despite the balance appearing present — mirroring the reported class where an asset is present but cannot move.

### Likelihood Explanation
Any miner (or pool) can pay coinbase rewards to the taproot script of the threshold key without permission. More broadly, the scanner API makes this the default path: `scan_block` is the natural way to process blocks, and the immature-output hazard is only mentioned in a doc comment, not enforced in the type system or return value.

### Recommendation
Have `scan_block` skip `block.txdata[0]` (or mark `ReceivedOutput` with the confirming block height / an `immature` flag) so callers cannot mistake a coinbase output for a spendable one; alternatively return maturity metadata and refuse to select immature outputs when building spends.

### Proof of Concept
```rust
// A miner includes a coinbase output paying the threshold key's script.
let block: Block = rpc.get_block(hash); // block.txdata[0] is the coinbase
let scanner = Scanner::new(group_key).unwrap();
let mut outputs = scanner.scan_block(&block);
// `outputs` includes the coinbase ReceivedOutput with no maturity flag.
// A spend selecting it builds a tx whose input spends an immature coinbase:
assert!(block.txdata[0].is_coinbase()); // consensus-forbidden to spend for 100 blocks
```
