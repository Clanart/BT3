### Title
Attacker-controlled length prefix in `SchnorrAggregate::read` enables denial of service via unbounded deserialization loop - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` trusts a 4-byte little-endian count field in the serialized blob and iterates that many times, performing a full point decompression (`C::read_G`) and a `Vec::push` per iteration. An unprivileged party who can cause a `SchnorrAggregate` blob to be deserialized can set the count to `u32::MAX`, forcing up to ~4.3 billion point decompressions and unbounded memory growth — the same bug class as CVE-2023-34966 (unvalidated count field driving a parsing loop → CPU/resource exhaustion DoS).

### Finding Description
In `SchnorrAggregate::read`, the code reads a 4-byte `len` field and loops `for _ in 0 .. u32::from_le_bytes(len)` with no upper bound and no consistency check that the remaining input even contains that many encoded points: [1](#0-0) 

Two resource-exhaustion vectors result:

1. **CPU**: with a sufficiently large (or infinite/streaming) reader, each iteration invokes `C::read_G`, which performs canonicality checks and a full point decompression — an expensive operation repeated up to 4.3 billion times.
2. **Memory**: each successful iteration pushes a `C::G` into `Rs`. For typical group elements (~32–57 bytes plus `Vec` overhead and doubling-growth), `u32::MAX` entries implies on the order of hundreds of gigabytes of allocation, guaranteeing OOM abort long before completion.

By contrast, the analogous count-driven parse in `ThresholdKeys::read` is bounded by `n: u16` (max 65,535 iterations, then rejected by `ThresholdParams::new` / `ThresholdKeys::new` validation): [2](#0-1) 

`SchnorrAggregate` has no such structural bound — the wire format permits any `u32` count regardless of the number of signatures that could legitimately be aggregated.

### Impact Explanation
An attacker supplying a blob beginning with `ff ff ff ff` (count = `u32::MAX`) followed by valid encoded points, or piping a `SchnorrAggregate` from a streaming/unbounded `Read` source, causes the deserializing party to burn CPU in decompression and grow memory until the process is killed or aborts. This is a remote, unauthenticated denial of service against any component that calls `SchnorrAggregate::read` on peer/network-supplied bytes. The host node's signing/coordination capacity is taken down by a single malformed message, matching the severity profile (CVSS 7.5, availability-only) of the reference Samba CVE.

### Likelihood Explanation
`SchnorrAggregate::read` is a public deserialization entry point explicitly intended for untrusted serialized data, and the malformed input is trivially constructible (a 4-byte header plus padding). The only uncertainty is whether a given deployment exposes this `read` path to unauthenticated input; where it does (e.g., half-aggregated signatures relayed between participants), exploitation requires no privileges, keys, or valid signatures — just the ability to transmit bytes.

### Recommendation
Bound the count before looping, e.g.:

```rust
// crypto/schnorr/src/aggregate.rs, in SchnorrAggregate::read
const MAX_AGGREGATE: u32 = /* sane protocol cap, e.g. u16::MAX as u32 */;
let len = u32::from_le_bytes(len);
if len > MAX_AGGREGATE {
  Err(io::Error::other("excessive aggregate length"))?;
}
```

Alternatively, derive the expected count from the caller's `keys_and_challenges` context, or read points until EOF rather than honoring a declared count. The same bounded-loop pattern used in `ThresholdKeys::read` (where `n` is capped by `u16` and semantically validated) should be applied.

### Proof of Concept
```rust
// Attacker-controlled input: count = u32::MAX, followed by valid encodings of C::G
let mut blob = u32::MAX.to_le_bytes().to_vec();
let encoded_point = C::generator().to_bytes(); // or any canonically-encoded point
// Append enough points to sustain the loop; a streaming Read impl makes this unbounded
for _ in 0 .. 1_000_000 {
  blob.extend_from_slice(encoded_point.as_ref());
}
// Triggers up to ~4.3 billion read_G calls / Vec growth -> CPU burn + OOM
let _ = SchnorrAggregate::<C>::read(&mut &blob[..]);
```

Even without gigabytes of payload, a `Read` implementation backed by a network stream (or a generator yielding valid encodings indefinitely) keeps the loop running until process termination, since `read` never compares `len` against remaining input or a protocol cap.
