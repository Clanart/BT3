### Title
File-path context-menu actions ("Reveal in Finder" / "Open with default program") follow attacker-controlled symlinks outside the repository - (File: `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `app/src/lib/app-shell.ts`, `app/src/ui/lib/open-file.ts`)

### Summary
The seed bug is "attacker-controlled input reaches a sensitive operation with no validation." The closest real Desktop analog is that `file.path` values coming from a cloned/fetched repository's tree (including from an untrusted pull request diff) are joined onto the repository root with plain `Path.join` and then handed to filesystem/shell primitives (`shell.showItemInFolder`, `shell.openExternal('file://...')`) **without** the symlink-aware containment check (`resolveWithin`) that the codebase itself already uses elsewhere for the exact same class of problem.

### Finding Description
`revealInFileManager()` builds the target path with a raw join and no post-resolution check: [1](#0-0) 

`PullRequestFilesChanged.onFileContextMenu` (and the equivalent code in `filter-changes-list.tsx`, `selected-commits.tsx`, `unmerged-file.tsx`) does the same for "Reveal in Finder" and "Open with default program", using `file.path` taken directly from `CommittedFileChange` objects that describe files changed in a commit or **pull request** (i.e., content that can come from a third party's fork/PR before the user has reviewed it): [2](#0-1) 

"Open with default program" routes through `openFile()`, which passes the joined path straight to Electron's `shell.openExternal` as a `file://` URL: [3](#0-2) 

Git allows committing symlink blobs (mode `120000`) whose target is an arbitrary string, including absolute paths or `../../` escapes. When such a tree is cloned/checked out, git materializes a real symlink on disk at `repository.path/file.path` pointing wherever the attacker chose (e.g. the user's SSH keys, browser profile, `/etc/passwd`, or a network share). The extension/"safe" checks in this code (`isSafeFileExtension`) only look at the **nominal** git path (e.g. `notes.txt`), not the real target of the symlink, so a symlink can be named with an innocuous extension while pointing at any file on the host.

The application already recognizes this exact hazard and has a dedicated fix, `resolveWithin()`, which normalizes, resolves and then `realpath()`s both the root and the candidate path to reject anything that escapes the root **even via a symlink**, as its own test suite documents: [4](#0-3) [5](#0-4) 

That guard is applied only to the `x-github-client://openrepo` deep-link `filepath` parameter: [6](#0-5) 

It is **not** applied to the structurally identical `Path.join(repository.path, path)` calls used by the file-list context menu actions (`revealInFileManager`, `onOpenFile` → `openFile`) or by `buildSubmoduleDiff`'s `fullPath`: [7](#0-6) 

So the exact broken invariant — "a repo-relative path from untrusted repository content must resolve to a location inside the repository" — is enforced in one call site but not in the others that consume the same kind of attacker-influenced data.

### Impact Explanation
A symlink placed by the repository author (or a PR author, since `PullRequestFilesChanged` renders PR diffs before merge) can cause the "Reveal in Finder/Explorer" or "Open with default program" context-menu actions to operate on a file located outside the working directory that the user believes they are inspecting. For "Open with default program", this results in the OS default handler opening arbitrary host files (potential **read of files outside the repo**, and depending on the target's true type and the associated handler, execution of a script/document handler on attacker-chosen content). This satisfies the required impact class: file read/execution outside the repository triggered purely by content in a cloned/fetched or PR-supplied repository.

### Likelihood Explanation
Moderate-to-high: no special git tricks beyond a normal symlink blob are needed, which any contributor (including a PR author whose diff a maintainer is casually browsing in the "Files changed" pane before ever checking out the branch) can commit. The user only needs to right-click a file in a list they're reviewing and pick a normal, expected context menu item — no unusual steps.

### Recommendation
Route every `Path.join(repository.path, file.path)` computation that feeds `revealInFileManager`, `openFile`/`shell.openExternal('file://...')`, and `buildSubmoduleDiff`'s `fullPath` through `resolveWithin(repository.path, file.path)` (as already done for the URL `filepath` action), refusing the action and logging an error when the resolved path escapes the repository root or does not exist, exactly as `dispatcher.ts`'s `openRepositoryFromUrl` already does.

### Proof of Concept
1. Attacker creates a repo/branch (or opens a PR against a victim's repo) containing a symlink `innocent-notes.txt -> /Users/victim/.ssh/id_rsa` (or an absolute Windows path) committed as a git symlink blob.
2. Victim opens the PR in GitHub Desktop's "Files changed" view (`pull-request-files-changed.tsx`) or checks out the branch and opens History.
3. Victim right-clicks `innocent-notes.txt` and selects "Open with default program" (or "Reveal in Finder").
4. `Path.join(repository.path, 'innocent-notes.txt')` resolves (via the OS-level symlink, not `resolveWithin`) to `~/.ssh/id_rsa`, and `shell.openExternal('file://' + fullPath)` opens the private key file with the OS default handler / reveals it in the file manager — outside the intended repository sandbox, with no warning that the file is a symlink pointing elsewhere.

}

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
