### Title
Deserialized `ThresholdKeys` never check that the secret share matches the verification shares, allowing attacker-chosen group keys - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` deserializes a secret share and a map of `verification_shares` from untrusted bytes, then hands them to `ThresholdKeys::new`, which derives `group_key` purely by interpolating `verification_shares[1..=t]` and never verifies that `C::generator() * secret_share == verification_shares[params.i()]`. The validation issue (the analog of CVE-2022-22589's missing input sanitization) lets a crafted byte stream install keys whose public identity is attacker-controlled while the local secret share is unrelated garbage.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, the interpolation variant, a `secret_share` scalar, and `n` verification-share points, then calls `ThresholdKeys::new` (crypto/dkg/src/lib.rs:574-632). `ThresholdKeys::new` only checks:

- `verification_shares.len() == n` and every participant index `<= n` (crypto/dkg/src/lib.rs:355-365)
- `Constant` interpolation implies `t == n` (crypto/dkg/src/lib.rs:367-374)

It then computes `group_key` as `sum(verification_shares[i] * interpolation_factor(i, {1..=t}))` for `i` in `1..=t` (crypto/dkg/src/lib.rs:376-378). There is no check that the deserialized `secret_share` actually corresponds to `verification_shares[params.i()]` — i.e. that `secret_share * G == verification_shares[i]`. The honest PedPoP path computes `verification_shares[i] = generator * secret` internally (crypto/dkg/pedpop/src/lib.rs:512-521), so the invariant always holds for genuinely generated keys, but nothing enforces it for deserialized ones.

Because `group_key()` returns `(core.group_key * scalar) + generator * offset` (crypto/dkg/src/lib.rs:445-447) and `view()` builds signature shares from `secret_share` while validating other participants' shares against `verification_shares` (crypto/dkg/src/lib.rs:463-533), the deserialized object presents an attacker-controlled public key disconnected from the holder's share.

### Impact Explanation
An unprivileged party feeding crafted bytes to `ThresholdKeys::read` (listed as in-scope untrusted input) can produce `ThresholdKeys` where:

1. **Attacker-chosen group key**: the attacker sets `verification_shares` to a consistent set of points whose interpolated `group_key` corresponds to a secret the attacker knows (e.g., shares of a polynomial the attacker generated). The victim then reports/uses this attacker-owned key as the multisig's key — funds credited to it are spendable by the attacker but not by the honest set ("funds reported received that are not spendable" by the network).
2. **Self-inconsistent keys / false blame**: the attacker sets a valid `group_key` and `verification_shares` but an unrelated `secret_share`. Every signature share the victim produces via `view()`/`ThresholdView::secret_share` fails verification against `verification_shares[i]`, so the honest victim's shares are consistently rejected and the victim is identified as faulty in FROST blame aggregation.
3. **Forged signatures**: with a fully consistent attacker-generated share set, signatures verify under the attacker's known secret — signing of arbitrary unintended messages under the victim's reported key.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ThresholdKeys::read` (e.g., from a peer/coordinator channel rather than locally generated DKG output). The exploit is purely arithmetic — no race or probabilistic condition — so wherever the read path consumes non-local input, the attack is deterministic. Rated Medium: it requires an untrusted deserialization path for key material, but the missing consistency check is unconditional.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349), after the existing checks, verify share/key consistency:

```rust
if verification_shares[&params.i()] != C::generator() * secret_share.deref() {
  Err(DkgError::InvalidSecretShare)?
}
```

Additionally consider validating that `group_key` and all `verification_shares` are non-identity, matching the stricter `Curve::read_G` semantics used elsewhere (crypto/frost/src/curve/mod.rs:123-131).

### Proof of Concept
```rust
// Given any Ciphersuite C and ThresholdParams for (t, n, i):
// 1. Attacker picks t scalars x_1..x_t they know, sets
//    verification_shares[j] = generator * x_j for all j in 1..=n
//    (padding j > t arbitrarily consistent or not).
// 2. Attacker writes bytes per ThresholdKeys::write's format:
//    id_len || C::ID || t || n || i || 1 (Lagrange) || arbitrary_share || points.
//    `arbitrary_share` need not equal x_i — no check exists.
// 3. Victim calls ThresholdKeys::<C>::read(&mut bytes). It succeeds because
//    `new` only validates counts and index bounds.
// 4. keys.group_key() == interpolated attacker key whose discrete log is
//    sum(x_j * lambda_j) — known to the attacker.
// 5. keys.view(included).unwrap() produces a secret share inconsistent with
//    the verification share map, so any FROST signature share from it fails
//    Schnorr share verification against verification_shares[i].
```

Relevant code: `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632), `ThresholdKeys::new` missing consistency check (crypto/dkg/src/lib.rs:349-391), `group_key`/`view` derivation (crypto/dkg/src/lib.rs:445-447, 463-533).
