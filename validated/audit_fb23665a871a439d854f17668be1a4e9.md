### Title
`emergencyWithdraw` skips the base rewarder sync, decoupling rewarder-tracked balance from actual stake - (File: `rewards/MasterMagpie.sol`)

### Summary
`emergencyWithdraw(address _stakingToken)` reduces `user.amount`/`user.available` and recomputes `user.rewardDebt` directly, without first calling `_harvestBaseRewarder()` (as `_deposit`/`_withdraw` do) or `updatePool()`. This leaves the pool's `IBaseRewardPool` rewarder's internal balance for the withdrawing user unchanged (stale/inflated) even though the user's real stake in `MasterMagpie` has just dropped, letting the user keep accruing bonus-token rewards on tokens they no longer have staked.

### Finding Description

Compare this to the normal deposit/withdraw path, which always calls `_harvestBaseRewarder(_stakingToken, _account)` before mutating `user.amount`: [2](#0-1) 

`_harvestBaseRewarder` is the function responsible for calling into `pool.rewarder` (the `IBaseRewardPool`) to sync/update the user's tracked balance there (`updateFor`) before the underlying `user.amount` changes, preserving the invariant that the rewarder's internal accounting for a user always matches `userInfo[_stakingToken][user].amount` at the moment of any balance change. `emergencyWithdraw` reduces `user.amount` and `user.available` and recomputes `user.rewardDebt` off the (possibly stale, since `updatePool` is also never called) `pool.accMGPPerShare`, but never touches `pool.rewarder`. As a result:
- The rewarder (bonus token distributor) still believes the withdrawing user holds their pre-withdrawal balance.
- The user's real stake in `MasterMagpie` (`user.amount`) has been reduced without a preceding reconciliation call to the rewarder, violating the stated invariant that "any change to `UserInfo.amount` must be preceded by a rewarder `updateFor` at the pre-change balance."
- The rewarder continues to accrue bonus rewards to the inflated balance, and since the base rewarder's `getReward`/claim functions are typically callable independent of `MasterMagpie`'s state, the user can later harvest bonus tokens computed against stake they no longer hold, diluting rewards owed to legitimate remaining stakers.

Neither `whenPaused` nor any other modifier on `emergencyWithdraw` prevents this, since pausing is only meant to gate the emergency exit path, not to enforce reward accounting consistency.

### Impact Explanation
This breaks reward accounting invariants between `MasterMagpie` and its base rewarder, allowing a user who calls `emergencyWithdraw` to retain rewarder-side reward-earning power for tokens they've already withdrawn. This is a concrete, quantifiable theft of unclaimed yield from the bonus-token reward pool at the expense of other stakers, matching the "High – Theft of unclaimed yield" Immunefi impact class.

### Likelihood Explanation
The path is reachable by any unprivileged staker: stake into a pool with a base rewarder, wait for the pool to be paused (an expected emergency circuit-breaker state, not an admin favor to the attacker), then call `emergencyWithdraw`. No special role is required to trigger this — pausing is a pre-existing legitimate protocol state that any staker can exploit once it occurs. It is deterministic and repeatable across any paused pool with an attached rewarder.

### Recommendation
Call `updatePool(_stakingToken)` and `_harvestBaseRewarder(_stakingToken, msg.sender)` inside `emergencyWithdraw` before mutating `user.amount`/`user.available`, mirroring the pattern used in `_deposit`/`_withdraw`, so the rewarder's internal balance is always reconciled to the pre-change amount before the stake is reduced.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie` with one pool (`_stakingToken`) that has a non-zero `allocPoint` and an attached `IBaseRewardPool` rewarder, and set all other pools' `allocPoint` to zero so the full `mgpPerSec` stream lands on this pool.
2. Have an attacker EOA deposit staking tokens via `deposit()`, causing `_harvestBaseRewarder` to register their balance in the rewarder.
3. Advance time so both MGP and bonus rewards accrue.
4. Pause the contract (simulating the emergency state) and call `emergencyWithdraw(_stakingToken)` from the attacker.
5. Assert: `userInfo[_stakingToken][attacker].amount` decreased, but `pool.rewarder.balanceOf(attacker)` (or equivalent internal tracked balance) remains unchanged from before withdrawal — i.e., no `updateFor`/`withdrawFor` call occurred.
6. Advance time further and call the rewarder's `getReward`/claim function for the attacker; assert the attacker receives bonus tokens computed against the stale (higher) balance, exceeding what their post-withdrawal real stake should earn, while `unClaimedMgp[_stakingToken][attacker]` and `userInfo[_stakingToken][attacker].rewardDebt` are no longer consistent with the reduced `amount`.

    function emergencyWithdraw(address _stakingToken) external whenPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][msg.sender];
        uint256 availableaAmount = user.available;
        user.available = 0;
        IERC20(pool.stakingToken).safeTransfer(address(msg.sender), availableaAmount);
        emit EmergencyWithdraw(msg.sender, _stakingToken, availableaAmount);
        user.amount = user.amount - availableaAmount;
        user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;
    }
