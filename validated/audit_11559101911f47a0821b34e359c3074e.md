### Title
Unprivileged miner pays multisig via coinbase output; `Scanner::scan_block` reports immature, unspendable funds - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The original bug class is: an unprivileged external party creates an object inside an identifier space a later protocol operation depends on, causing that operation to fail (external `mintWithId` occupies the sale range → `buyNFT` reverts). The analog in Serai is the Bitcoin `Scanner`: `scan_block` iterates over `block.txdata`, including the coinbase transaction at `txdata[0]`, and returns any matching `ReceivedOutput` with no maturity check. Any miner — an unprivileged party — can craft a coinbase payout to the multisig's P2TR script (or any registered offset address derived from `hash_to_F(KEY_DST, …)` offsets), and the scanner will report it as a received output even though consensus forbids spending it for 100 blocks. A downstream wallet/processor that feeds scanned outputs into `SignableTransaction::new` will construct a transaction Bitcoin nodes reject as immature, stalling the spend path — the same shape as `buyNFT` reverting on an id the attacker claimed first.

### Finding Description
`Scanner::scan_block` in `networks/bitcoin/src/wallet/mod.rs:221-227` scans every transaction in the block:

```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

The doc comment on lines 216-220 acknowledges the output "is bound by maturity" and leaves handling to a "post-processing pass," but `scan_block` itself emits the `ReceivedOutput` as indistinguishable from a spendable one (`ReceivedOutput` at lines 90-97 carries only `offset`, `output`, `outpoint` — no maturity flag). The scanner key and all offset addresses are publicly derivable: `register_offset` maps `key + G*offset` to a P2TR script (`mod.rs:180-196`), and in production the branch/change/forward offsets are fixed `Secp256k1::hash_to_F(KEY_DST, …)` constants (`processor/src/networks/bitcoin.rs:308-344`). A coinbase paying `p2tr_script_buf(group_key)` therefore matches `Scanner::new`'s zero-offset script (`mod.rs:162-165`) exactly like a normal deposit.

On the consumption side, `get_outputs` results ≥ `N::DUST` are pushed as received outputs (`processor/src/multisigs/scanner.rs:562-567`) and later become inputs to `BSignableTransaction::new` (`processor/src/networks/bitcoin.rs:446-452`), which performs no coinbase-maturity filtering. The resulting transaction is invalid at the consensus/relay layer (`BIP-68`/coinbase 100-block maturity), so the signing ceremony produces a transaction the network rejects.

### Impact Explanation
An unprivileged miner deposits "phantom" funds: the processor reports a received external/branch output that cannot be spent for 100 blocks. Any plan that selects that output produces an invalid transaction, burning a signing attempt and stalling the outbound flow until maturity — funds reported received that are not (yet) spendable, matching the "external mint intersects the sale range → `buyNFT` fails" class. The attacker's cost is voluntarily paying coinbase rewards to Serai's address, so griefing cost equals the funds sent, but the disruption (failed/invalid spend construction) is real and unearned by honest operation.

### Likelihood Explanation
Reachable by any miner/whoever constructs a coinbase — no privileged access needed; the address is public and the output needs only be ≥ `N::DUST`. Triggering is opportunistic (requires mining a block), but the failure is deterministic once the output is scanned and selected as an input.

### Recommendation
Track maturity in `ReceivedOutput` or filter coinbase-derived outpoints. Concretely: in `scan_block`, skip `txdata[0]` (coinbase) or mark its outputs with a maturity height; in `processor`'s output handling, exclude coinbase outpoints whose `(block_height + 100) > current_height` before they reach `SignableTransaction` construction. Alternatively, move `scan_block` to iterate `block.txdata[1..]` and require explicit opt-in for coinbase scanning.

### Proof of Concept
1. `let mut scanner = Scanner::new(group_key).unwrap();` — `group_key` is the multisig's even-Y Taproot key (`mod.rs:162-165`).
2. An attacker mines a block whose coinbase (`txdata[0]`) contains a `TxOut` paying `p2tr_script_buf(group_key)` with value ≥ `N::DUST`.
3. `scanner.scan_block(&block)` returns a `ReceivedOutput` with `offset == Scalar::ZERO` and the coinbase outpoint (`mod.rs:199-214`, `221-227`); the test helper `send_and_get_output` (`networks/bitcoin/tests/wallet.rs:40-78`) demonstrates precisely this path — it mines a coinbase to the key and scans it back, only succeeding because it then mines 100 additional blocks first (lines 54-61).
4. The processor pushes it via `get_outputs`/`N::DUST` (`scanner.rs:562-567`) and later passes it to `BSignableTransaction::new` (`bitcoin.rs:446-452`). The signed transaction references an immature coinbase input and is rejected by every Bitcoin node, exactly as `nft.mintWithId` reverted on the intersected id.

Note: the `scan_block` doc comment does flag the maturity caveat and suggests post-processing, so whether this is a defect in the wallet crate versus a documented integrator obligation is arguable — but the emitted `ReceivedOutput` carries no maturity metadata, making correct post-processing impossible without re-fetching the block, which strengthens the case this belongs in the library.
