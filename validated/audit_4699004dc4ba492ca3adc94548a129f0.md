### Title
Hardcoded dust threshold can create unspendable outputs and unrelayable transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`DUST` is a hardcoded, immutable `u64` constant (`546`) used as a validity check for both user-specified payments and internally generated change outputs in `SignableTransaction::new`. Bitcoin's dust limit is not a protocol constant — it is derived from a policy fee rate (3000 sat/kvB) multiplied by the serialized size of the output plus its input spend, and therefore differs per output script type and changes whenever Bitcoin Core's relay policy or prevailing fee rates change. Like the report's hardcoded `FAST_GAS_HEARTBEAT`, this threshold may become incorrect, making the check fail to reject amounts that are actually dust.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

```rust
pub const DUST: u64 = 546;          // line 32
...
for (_, amount) in payments {
  if *amount < DUST { Err(TransactionError::DustPayment)?; }   // line 166
}
...
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
  if value >= DUST {
    tx_outs.push(TxOut { value: Amount::from_sat(value), script_pubkey: change });  // lines 229-230
```

The comment above the constant (lines 28–31) acknowledges it does not differentiate by output type ("a lower amount may not be considered dust if contained in a SegWit output... doesn't bother with delineation"), and there is no mechanism to update it. Two failure modes follow:

1. **Payments:** The `payments` list is attacker/user-influenced — burns specify arbitrary destination `ScriptBuf`s and amounts. An amount of `546` sats is accepted even though the true dust limit for many script templates is higher (e.g., the dust threshold at 3000 sat/kvB for a non-SegWit P2PKH output is 546 sats, but rises linearly if the reference fee rate rises; Bitcoin Core has adjusted these policy constants before). Serai will sign a burn transaction whose output the recipient can never economically spend — the user is burned/slashed for value that is unspendable dust.
2. **Change:** If `input_sat - payment_sat - fee` lands between the true dust limit and `546`, or if the effective dust limit rises above 546, Serai creates a change output that is dust, making the entire transaction non-standard and unrelayable — the multisig's transaction (carrying real multisig funds as inputs) stalls and cannot be broadcast.

### Impact Explanation
The consequence mirrors the report: an immutable threshold governing a validity check produces incorrect results when external conditions change. Here the impact is concrete: (a) Serai signs transactions paying amounts the recipient cannot spend (value destroyed while the protocol treats the payment as made), and (b) Serai constructs transactions with dust change outputs that violate `MAX_STANDARD_TX_WEIGHT`-adjacent relay policy — specifically Bitcoin Core's dust relay rule — causing the transaction to be rejected by the mempool. The `fee()` function then reports a valid-looking transaction that cannot confirm, stalling burn execution and tying up multisig inputs. This fits the accepted impact of funds effectively unspendable and an incorrect validation check reachable via publicly supplied transaction parameters (`payments` amounts and scripts in `SignableTransaction::new`).

### Likelihood Explanation
Bitcoin Core's dust/dust-relay-fee-rate constants have changed across versions, and the dust limit is a function of a fee rate the network operators do not control. Any unprivileged user submitting a burn/payment of ~546 sats reaches the `*amount < DUST` check directly through public transaction data. The change-output path triggers automatically on ordinary spends whenever the leftover amount is marginal. No malicious validator, collusion, or leaked key is required — only publicly specified payment amounts.

### Recommendation
Make the dust threshold a configurable network parameter (per `Network` implementation, alongside `CONFIRMATIONS` and `DUST` in the processor), and compute it from the actual output type and a conservative relay fee rate rather than a single `u64`. At minimum, derive it dynamically via `TxOut::minimal_non_dust()`-style logic per `script_pubkey` for both payment and change checks, and set the constant well above the current limit to absorb policy drift, with an explicit comment documenting the update path.
