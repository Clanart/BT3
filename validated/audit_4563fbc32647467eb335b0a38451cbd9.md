### Title
Unauthenticated payments to deterministic scanner offsets are claimed as internal outputs, silently dropping external deposits - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The analog of the `ProofOfEmail::confirm` race — an unauthenticated, first-come binding between a publicly observable value and an internal identity — exists in `Scanner::scan_transaction` / `Scanner::register_offset`. `Scanner` associates an output with an internal role (`offset`) purely by `script_pubkey` match, with no binding to who the output was meant for or who created it. Just as the attacker in the report could submit the victim's observed `code` to bind the email to their own address, any unprivileged party can send a Bitcoin transaction paying a script that maps to a registered offset, and the scanner will bind that output to the corresponding internal role (`Branch`, `Change`, `Forwarded`) rather than an external deposit.

### Finding Description
`Scanner::scan_transaction` iterates `tx.output` and reports a `ReceivedOutput` whenever `output.script_pubkey` is in `self.scripts`, returning the registered `offset` [1](#0-0) . `register_offset` documents that offsets are surjective and registration order determines validity — the first registration wins the script, and any later, colliding registration is denied (`None`), exactly the "delete-then-deny" shape of the report's DoS variant [2](#0-1) .

The offsets used in production are deterministic public constants: `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch" | b"change" | b"forward")`, and the offset key is `key + G * offset` for the publicly known multisig group key [3](#0-2) . Anyone can therefore compute the script pubkeys for `OutputType::Branch`, `OutputType::Change`, and `OutputType::Forwarded` (and the non-offset external address) for a known multisig. Downstream, `get_outputs` classifies each scanned output's `kind` purely from the matched offset [4](#0-3) , and the multisig handler drops non-`External` outputs that have no matching forwarded-output instruction: it retains only `output.kind() == OutputType::External` for instruction processing [5](#0-4) .

So an attacker who sends funds to the `Forwarded`/`Branch`/`Change` script causes the scanned output to be bound to the wrong internal identity — claimed as an internal output it never was — and then discarded from external-instruction handling. The association is unauthenticated: nothing in `scan_transaction` distinguishes "output we created" from "output an arbitrary third party created", mirroring how `confirm` never bound `code` to the requesting sender.

### Impact Explanation
Funds sent to a deterministic internal offset address are reported by the scanner as `Branch`/`Change`/`Forwarded` outputs rather than `External` deposits. They are then filtered out before instruction creation and are never credited or scheduled for spending — effectively burned funds / "received" outputs that are not spendable. Additionally, an attacker can craft the misclassification at will to distort the processor's view of the multisig's balance and output kinds. This mirrors the report's impact: the attacker preempts/misuses an unauthenticated association, causing the victim's legitimate claim (an external deposit) to be denied.

### Likelihood Explanation
Exploitation requires only sending a standard Bitcoin transaction to a publicly computable address — no validator privileges, no collusion, no compromised keys. Cost is a dust-level payment plus transaction fees, and it succeeds deterministically (unlike the report's gas-price race, there is no competition once the internal script is known, since the wallet itself publishes these addresses on-chain in prior transactions). Probability of success per attempt is near-certain; the only limiting factor is that the attacker must fund the malicious outputs.

### Recommendation
Bind outputs to their intended semantic origin rather than to `script_pubkey` alone. Concretely:
- Treat the internal offsets (`Branch`, `Change`, `Forwarded`) as "only valid if this output appears in a transaction this multisig created" — i.e., require the transaction to spend a previously-scanned multisig input (or carry the expected OP_RETURN data) before classifying an output as internal; otherwise classify unknown senders' payments to those scripts as `External` or refuse them.
- Alternatively, make internal offsets non-externally-derivable (e.g., derive per-transaction offsets from secret state) so an attacker cannot address them.
- Document in `Scanner` that matching is unauthenticated and callers must not attribute outputs to internal flows without additional evidence of origin.

### Proof of Concept
1. Observe any transaction from the target multisig to learn its group key `key` (recoverable from prior `key + G*offset` outputs/taproot keys, or from the protocol's published set).
2. Compute `forward_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")` and `forward_script = p2tr_script_buf(key + G*forward_offset)` — the same values produced by `scanner(key)` [6](#0-5) .
3. Broadcast a transaction paying ≥ `DUST` (10,000 sats) to `forward_script`.
4. The scanner emits a `ReceivedOutput` with `offset == forward_offset` [7](#0-6) , and `get_outputs` tags it `OutputType::Forwarded` [8](#0-7) .
5. Since no `ForwardedOutputDb` instruction exists for it, it is not `External` and is dropped by the `retain` [9](#0-8) : the deposit is never credited and no spend plan is created — the association was claimed/misbound by an unauthenticated third party.

  /// Register an offset to scan for.
  ///
  /// Due to Bitcoin's requirement that points are even, not every offset may be used.
  /// If an offset isn't usable, it will be incremented until it is. If this offset is already
  /// present, None is returned. Else, Some(offset) will be, with the used offset.
  ///
  /// This means offsets are surjective, not bijective, and the order offsets are registered in
  /// may determine the validity of future offsets.
  ///
  /// The offsets registered must be securely generated. Arbitrary offsets may introduce a script
  /// path into the output, allowing the output to be spent by satisfaction of an arbitrary script
  /// (not by the signature of the key).
  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });

    }

) -> (Scanner, HashMap<OutputType, Scalar>, HashMap<Vec<u8>, OutputType>) {
  let mut scanner = Scanner::new(key).unwrap();
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

  register(
    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),

    OutputType::Change,

  );
