### Title
Attacker-controlled `ThresholdKeys` can deserialize an identity group key and panic BIP-340 signing - (File: networks/bitcoin/src/crypto.rs)

### Summary
`ThresholdKeys::read` accepts canonical identity verification shares and a zero secret share without rejecting the resulting identity group key. When those keys are used with Bitcoin’s FROST `Schnorr` algorithm, `Hram::hram` unconditionally extracts the x-coordinate of the group key, which panics when the key is the point at infinity. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`ThresholdKeys::new` verifies participant count and interpolation applicability, then derives `group_key` from the supplied verification shares, but it does not reject identity verification shares or the resulting identity group key. [4](#0-3) 

Its deserializer accepts attacker-controlled `t`, `n`, `i`, interpolation coefficients, secret share, and `n` verification shares, then passes them directly to `ThresholdKeys::new`. [5](#0-4) 

During signing, FROST invokes `Algorithm::sign_share` with `params.group_key()`, and the Bitcoin algorithm delegates to `Hram::hram`. [6](#0-5) [7](#0-6) 

`Hram::hram` calls `x(A)`, and `x` panics on the point at infinity. [8](#0-7) [9](#0-8) 

### Impact Explanation
An unprivileged party who can supply serialized `ThresholdKeys<Secp256k1>` bytes to `ThresholdKeys::read` and cause the deserialized key to sign a message can deterministically panic the signing process. [10](#0-9) [11](#0-10) 

This is a malformed-input denial-of-service analogue to the referenced invalid-free crash: Serai is memory-safe, so the equivalent reachable failure is an unchecked panic caused by accepting an invalid identity group state. [12](#0-11) 

### Likelihood Explanation
The malicious encoding is fully deterministic for a one-participant threshold: participant `1` has an identity verification share, a zero secret share, and a constant interpolation coefficient of one. `ThresholdKeys::new` has no check for a zero secret share, identity verification share, or identity aggregate key, so construction succeeds and the first signing attempt reaches the panicking challenge calculation. [13](#0-12) [14](#0-13) 

The likelihood depends on an application deserializing threshold keys from untrusted input, but that parser is an exposed public API and performs no validation preventing this state. [15](#0-14) 

### Recommendation
Reject zero secret shares, identity verification shares, and identity `group_key` values in `ThresholdKeys::new` before returning usable keys. [16](#0-15) 

The Bitcoin `Hram` implementation should also return an error instead of panicking when either `R` or `A` is identity, although API-level validation remains necessary to prevent invalid threshold keys from being constructed. [3](#0-2)

```rust
use std::collections::HashMap;
use rand_core::OsRng;
use zeroize::Zeroizing;
use ciphersuite::{Ciphersuite, group::{ff::Field, Group, GroupEncoding}};
use frost::{
  curve::Secp256k1,
  sign::{AlgorithmMachine, PreprocessMachine, SignMachine},
};
use bitcoin_serai::crypto::Schnorr;

fn encoded_identity_keys() -> Vec<u8> {
  let mut bytes = Vec::new();

  // Curve ID.
  bytes.extend(u32::try_from(Secp256k1::ID.len()).unwrap().to_le_bytes());
  bytes.extend(Secp256k1::ID);

  // t = 1, n = 1, i = 1.
  bytes.extend(1u16.to_le_bytes());
  bytes.extend(1u16.to_le_bytes());
  bytes.extend(1u16.to_le_bytes());

  // Interpolation::Constant([1]).
  bytes.push(0);
  bytes.extend(<Secp256k1 as Ciphersuite>::F::ONE.to_repr().as_ref());

  // secret_share = 0.
  bytes.extend(<Secp256k1 as Ciphersuite>::F::ZERO.to_repr().as_ref());

  // verification_shares[1] = identity.
  bytes.extend(<Secp256k1 as Ciphersuite>::G::identity().to_bytes().as_ref());

  bytes
}

let keys =
  frost::ThresholdKeys::<Secp256k1>::read(&mut encoded_identity_keys().as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity()));

let (machine, _) = AlgorithmMachine::new(Schnorr::new(), keys).preprocess(&mut OsRng);

// For a 1-of-1 signing set there are no external preprocesses.
// This calls Hram::hram(..., A = identity, ...) and panics inside x(A).
let _ = machine.sign(HashMap::new(), b"message");
```

The crafted object is accepted because deserialization only validates syntax and threshold consistency, while the panic occurs when BIP-340 challenge derivation unconditionally extracts the x-coordinate of the identity group key. [17](#0-16) [8](#0-7)
