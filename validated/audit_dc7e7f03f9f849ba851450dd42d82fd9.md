## Title
Owner-controlled `pause()` permanently blocks timeout refunds, causing irrecoverable loss of user funds - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken` (and its `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleToken*` variants) burns a sender's tokens immediately in `send()` and only re-mints them back to the sender in `onPostRequestTimeout()` once a timeout proof is delivered by the ISMP host. `onPostRequestTimeout()` carries the `whenNotPaused` modifier, so the contract owner can call `pause()` at any time and never call `unpause()`, permanently preventing the refund mint from executing. Since the burn already happened irreversibly at send time, this gives the owner the power to permanently strand/rug users' bridged funds — the same broken invariant as the external report (owner pause blocking the only claim/refund path forever).

### Finding Description
`send()` burns the caller's tokens up front and dispatches a POST request: [1](#0-0) 

If the request times out on the destination, the host calls `onPostRequestTimeout()`, which is the *only* code path that re-mints the burned amount back to the original sender: [2](#0-1) 

But that function is gated by `whenNotPaused`: [3](#0-2) 

`pause()`/`unpause()` are `onlyOwner`, with no time bound, no timelock, and no alternate recovery path. Once the owner pauses the contract (maliciously or via a compromised key) and never unpauses, every pending timeout refund permanently reverts. Because the burn in `send()` is unconditional and already committed on-chain, the user has no other way to recover the tokens — there is no vault, no escrow, and no separate withdrawal function that bypasses `whenNotPaused`. The relayer can keep resubmitting the timeout proof, but each call reverts as long as the contract stays paused, and the owner is free to keep it paused indefinitely (exactly the "cannot unpause forever" scenario described in the source report).

The same pattern is duplicated in `HyperFungibleTokenUpgradeable.sol`: [4](#0-3) 

### Impact Explanation
High — the owner (or anyone who compromises the owner key) can permanently lock/rug all in-flight cross-chain transfers that end up timing out, since the burned principal can never be re-minted while paused. This is a direct "loss of funds" / bridged-asset-must-move-exactly-once violation: the refund leg of the bridged-asset lifecycle can be blocked forever, leaving user balances burned with no recovery route.

### Likelihood Explanation
Low, matching the original report's likelihood rating — it requires a malicious or compromised owner. However the impact is total and irreversible for any affected sender once the pause is set and never lifted, and no other safeguard (timelock, governance override, permissionless unpause) exists in this contract to prevent it.

### Recommendation
Remove the `whenNotPaused` modifier from `onPostRequestTimeout()` (and analogously from `onAccept()`, since inbound mints for value already burned/escrowed on the source chain should also not be indefinitely blockable) so refunds/deliveries can always be completed once their proofs are valid, regardless of the pause state. `pause()` should only gate the initiation of new transfers (`send()`, `transfer()`, `transferFrom()`), not the settlement of transfers that already consumed user funds.

### Proof of Concept
1. User calls `send()` with `amount = X`; `_burn(user, X)` executes immediately.
2. The destination request never gets delivered (e.g., relayer outage or malicious withholding) and the message becomes eligible for timeout.
3. Before the timeout proof is submitted, the owner calls `pause()`.
4. Relayer submits the timeout proof; the host calls `onPostRequestTimeout()`, which reverts due to `whenNotPaused`.
5. Owner never calls `unpause()`. Every subsequent retry of the timeout delivery reverts identically.
6. The user's `X` tokens remain burned forever with no code path capable of restoring them — permanent loss of funds under sole control of the owner.

        _burn(msg.sender, params.amount);

        bytes32 commitment;
        if (msg.value > 0) {

            commitment = dispatchWithFeeToken(request);
        }

            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
