### Title
Tier-reward "double counted" correction is derived from the mutable, live `mWomSV.getUserTotalLocked` balance instead of a persistent record, letting an attacker reset the tier basis via `startUnlock` to repeatedly farm the highest-multiplier reward bracket - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3` declares a `bracketRewarded` mapping intended to persistently record how much reward tier an account has already been credited for, but the mapping is explicitly unused (comment: `// not in use`). Instead, `calDoubledCounted` and `getRewardAmount` compute the "already rewarded" correction from the live, attacker-controllable `mWomSV.getUserTotalLocked(_account)` value, so an attacker can temporarily reduce that value with `mWomSV.startUnlock` between two `incentiveDeposit` calls and re-claim the low-tier/high-multiplier reward bracket multiple times.

### Finding Description
In `incentiveDeposit` (mode 2, lock path): [1](#0-0) 
`getRewardAmount` computes `accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)`, derives `rewardAmount` from the tier table, then subtracts `calDoubledCounted(_account)`: [2](#0-1) 
`calDoubledCounted` re-derives the "already rewarded" portion purely from `mWomSV.getUserTotalLocked(_account)` — the *current* live locked balance — not from any persisted record such as `bracketRewarded`, which exists in storage but is never read or written anywhere in the contract: [3](#0-2) 

`mWomSV.getUserTotalLocked` excludes any amount currently in cooldown: [4](#0-3) 
and `startUnlock` immediately moves a chosen amount from "locked" into "cooldown" in the same transaction, with no delay affecting this accounting split (only the final withdrawal via `unlock()` is time-gated): [5](#0-4) 

Exploit flow (all steps by an unprivileged EOA, single block):
1. Call `incentiveDeposit(A, ratio, false, 2)`. This locks mWom into `mWomSV` for the caller via `_deposit`, raising `getUserTotalLocked` from `0` to `L`. Reward is computed with `accuIn1 = 0` at the time of the correction, so the caller is credited the full low-tier bonus for the whole range `[0, L]`. [6](#0-5) 
2. Call `mWomSV.startUnlock(L)`, moving the entire locked amount `L` into cooldown. `getUserTotalLocked(account)` drops back to `0` (the tokens are not actually removed from the user's economic position — they can later be `cancelUnlock`ed — but the accounting basis used by `calDoubledCounted` resets).
3. Call `incentiveDeposit(B, ratio, false, 2)` again in the same block. Now `accumulated = B + 0`, and `calDoubledCounted` again evaluates at `accuIn1 = 0`, so the caller is credited the full low-tier bonus a second time for `[0, B]` instead of the correct marginal bonus for `[L, L+B]`.

This can be repeated (deposit → startUnlock full amount → deposit) to keep resetting the tier basis to zero, letting the attacker collect the highest-multiplier bracket reward on every tranche rather than the diminishing marginal reward that the tier table is designed to enforce. The only cap is the contract's own `mgp` balance (`mgpleft`), which bounds the attacker's take at the entire remaining reward reserve rather than preventing the attack itself: [7](#0-6) 

The `nonReentrant` modifiers on `incentiveDeposit` and `startUnlock` do not stop this because the two calls are sequential, not reentrant — the attacker simply issues them as separate top-level transactions/calls within the same block.

### Impact Explanation
The MGP reward pool held by `ArbWomUp3` (used to fund `vlMGP.lockFor` rewards) can be drained far beyond the amount that legitimately-tiered deposits would earn, because the "already rewarded" correction is keyed to a value the attacker fully controls and can reset at will. This is a direct extraction of protocol-held MGP tokens intended for genuine depositors, matching "Critical - Direct theft of user funds."

### Likelihood Explanation
No privileged role is required — `incentiveDeposit` and `mWomSV.startUnlock` are both externally callable by any EOA holding `wom`/`mWom` tokens. The attack requires only enough capital to perform the initial deposit tranche(s) and gas to sequence a few calls in one block; it is fully repeatable until the contract's `mgp` balance is exhausted.

### Recommendation
Use `bracketRewarded[_account]` (or an equivalent persistent, monotonically-non-decreasing record) as the sole basis for the "already rewarded" correction, updating it inside `_deposit`/`incentiveDeposit` whenever a reward is granted, instead of deriving the correction from the live, reversible `mWomSV.getUserTotalLocked` value. Additionally, `getUserTotalLocked` should not be reducible to zero purely by calling `startUnlock` if that is meant to reflect real economic exposure for reward-tier purposes, or the reward logic must snapshot the pre-deposit locked amount atomically with the reward mint rather than reading a mutable external state twice across separate transactions.

### Proof of Concept
Foundry fork test plan:
1. Deploy/fork `ArbWomUp3`, `mWomSV`, `mWom`, `MasterMagpie`, `SmartWomConvert` with realistic tier/multiplier config (`setMultiplier`) and fund the contract with `mgp`.
2. As attacker EOA: approve `wom`, call `incentiveDeposit(A, ratio, false, 2)`; record `vlMGP` locked amount `R1` and `mWomSV.getUserTotalLocked(attacker)` (= `L`).
3. Call `mWomSV.startUnlock(L)` as attacker in the same block; assert `getUserTotalLocked(attacker) == 0`.
4. Call `incentiveDeposit(B, ratio, false, 2)` again in the same block; record newly locked `vlMGP` amount `R2`.
5. Assert `R2` equals (or approximates) the full low-tier reward for `B` alone rather than the correct marginal reward for range `[L, L+B]`, i.e. `R1 + R2 > getRewardAmount` computed for a single deposit of `A+B` without the intermediate `startUnlock` — demonstrating reward inflation/double-crediting.
6. Assert the attacker's cumulative `vlMGP` reward exceeds the amount a single honest `incentiveDeposit(A+B, ...)` call would have produced, while `IERC20(mgp).balanceOf(address(ArbWomUp3))` decreases correspondingly — showing net protocol fund loss with no corresponding increase in legitimately locked stake.

        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;

                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
