### Title
Predispatch escrow sweeps the shared CallDispatcher's *entire* balance, letting an order steal residual dust as free escrow input - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder()`'s predispatch flow escrows native/ERC20 input amounts by sweeping the **entire current balance** of the shared `CallDispatcher` contract rather than only the amount produced by the caller's own predispatch call. Because `CallDispatcher` is a generic, persistent-balance utility shared across unrelated flows (IntentGatewayV2 predispatch/postdispatch, `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain calldata execution, etc.), any dust left in it from unrelated prior transactions is fair game for the next `placeOrder` caller to claim as their own escrowed input — for the price of a token amount as low as 1 wei.

### Finding Description
In `placeOrder`, when an order carries predispatch calldata, the gateway (1) forwards the caller-declared `predispatch.assets` to the dispatcher, (2) executes the arbitrary `predispatch.call`, then (3) builds sweep calls that pull tokens back from the dispatcher: [1](#0-0) 


This queries `address(dispatcher).balance` / `IERC20(token).balanceOf(dispatcher)` — the dispatcher's **total** balance — not the amount that the current caller's own `predispatch.assets` + `predispatch.call` produced. The subsequent measurement: [2](#0-1) 

```solidity

...
if (received > order.inputs[i].amount) {
    emit DustCollected(token, dust);
} else {
    order.inputs[i].amount = received;

```

directly assigns `order.inputs[i].amount = received`, i.e. the escrow amount credited to the order equals whatever was swept from the dispatcher — including any balance that pre-existed there before this transaction and had nothing to do with the caller's own deposit.

`CallDispatcher` (`evm/src/utils/CallDispatcher.sol`) is a bare utility contract with `receive() external payable {}` and no ownership/accounting of whose funds it holds: [3](#0-2) 

It is intentionally shared across multiple protocols — documentation confirms `HyperFungibleToken`/`WrappedHyperFungibleToken` mint/unlock tokens directly `to: CALL_DISPATCHER` for calldata execution: [4](#0-3) 

Any slippage, partial-fill, failed approval-then-swap remainder, or simply ETH sent directly to the dispatcher by an unrelated transaction leaves persistent dust in this single shared contract's balance across blocks. An attacker can then call `placeOrder` with:
- `predispatch.assets` = a trivially small amount (e.g. 1 wei of native token or an ERC-20 token) sent to the dispatcher,
- `predispatch.call` = a benign call guaranteed to succeed (e.g., a no-op call to a contract they control), and
- `order.inputs[0].amount` = up to whatever dust currently sits in the dispatcher.

Since `balance = address(dispatcher).balance` (or the ERC20 equivalent) includes all pre-existing dust, the `balance < requiredAmount` guard passes trivially, the full balance is swept to the gateway, and `order.inputs[i].amount` is set to that swept amount — crediting the attacker's escrow with value they never contributed.

### Impact Explanation
This is the same broken invariant as the LiFi report: balance-based "amount received" accounting that fails to isolate the caller's own contribution from balance already resident in the intermediary contract, letting one caller absorb funds that belong to someone else (here: the protocol's own uncollected dust, or a subsequent order's expected inputs). The attacker obtains an escrowed order input funded almost entirely by protocol/dust funds rather than their own deposit. A solver later fills this order and delivers genuine, real output tokens in exchange for an input escrow that cost the attacker essentially nothing — a direct value-extraction / loss-of-funds path fitting the "unauthorized transaction / logic attack / wrong amount" bounty categories. It also silently defeats the dust-sweeping mechanism that is supposed to route residual balances to governance-controlled treasury sweeps.

### Likelihood Explanation
`placeOrder` is a fully public, unprivileged entry point; no relayer, prover, admin, or malicious peer is required. The only precondition is that the shared `CallDispatcher` holds a nonzero residual balance at the moment of the attacker's `placeOrder` call — which is realistic given the dispatcher is reused across independent flows (IntentGatewayV2 predispatch/postdispatch sweeps, HyperFungibleToken calldata execution) and any imperfect sweep, failed max-amount approval, or rounding in those flows leaves dust behind indefinitely. An attacker can also proactively seed the dust themselves (e.g., via a prior `placeOrder`/`fillOrder` predispatch/postdispatch call that intentionally leaves a large remainder) and immediately claim it back through this path.

### Recommendation
Do not use the dispatcher's absolute balance as the "received" measure. Snapshot the dispatcher's balance *before* forwarding the caller's own predispatch assets and executing `predispatch.call`, and only sweep/credit the delta produced by that specific call — mirroring the corrected "Swapper.sol" pattern from the original report (subtract the balance that existed prior to this transaction's own contribution, not just prior to the sweep step). Concretely, record `dispatcherBalanceBefore` immediately before sending `predispatch.assets` to the dispatcher, and cap the swept/credited amount to `dispatcherBalanceAfterPredispatchCall - dispatcherBalanceBefore`, treating anything beyond that as belonging to the dispatcher's pre-existing pool (leave it un-swept, or route it exclusively through a governance-gated sweep instead of crediting it to the calling order).

### Proof of Concept
1. Assume the shared `CallDispatcher` at `_params.dispatcher` currently holds 5 ETH of dust (left over from a prior imperfect predispatch/postdispatch sweep or an unrelated HyperFungibleToken calldata execution).
2. Attacker calls `placeOrder` with:
   - `order.predispatch.assets = [{token: address(0), amount: 1 wei}]`
   - `order.predispatch.call` = a trivial call to an attacker-owned no-op contract (guaranteed success)
   - `order.inputs = [{token: address(0), amount: 5 ether}]`
   - sends `msg.value = 1 wei`
3. In `placeOrder`: `dispatcher.call{value: 1 wei}("")` forwards the 1 wei; `ICallDispatcher(dispatcher).dispatch(predispatch.call)` executes the no-op.
4. Sweep phase: `balance = address(dispatcher).balance` reads `5 ether + 1 wei` (dust + attacker's wei) ≥ `requiredAmount (5 ether)`, so the check passes; the full balance is swept to the gateway.
5. `received = 5 ether + 1 wei`, which is `≤ order.inputs[i].amount` is false only if exactly equal-ish; adjust `order.inputs[i].amount` to `requiredAmount = 5 ether` chosen to be ≤ dust so `order.inputs[i].amount = received` credits the attacker's order with 5 ether of escrow funded almost entirely by dust that cost them 1 wei.
6. A solver later fills the order, delivering genuine output tokens for the attacker's beneficiary and receiving the "5 ether" escrow — funds the attacker never actually contributed.

```text
    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
