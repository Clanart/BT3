## Confirmed: `applyPatchToIndex` re-fetches a diff at a different whitespace-fidelity than the one the user's line-selection was computed against

### Title
Whitespace-diff/line-selection mismatch causes silently mis-staged (wrong) commit content - (File: `app/src/lib/git/apply.ts`)

### Summary
The report's bug class is: a value (`beaconChainSlashingFactor`) is recomputed using a base quantity (`prevRestakedBalanceWei`) that was captured under one "view" of state while the authoritative state has since diverged, and no reconciliation/rescaling is performed — producing silently wrong final numbers that don't match either party's expectation. The Desktop analog is structural, not numeric: `WorkingDirectoryFileChange.selection` stores line inclusion as *absolute line indices* into a specific diff view, but the code path that actually turns that selection into staged content re-fetches the diff independently and without guaranteeing it is the same diff the indices were computed against.

### Finding Description
`file.selection` (`DiffSelection`) records included/excluded lines as integer indices (`hunk.unifiedDiffStart + lineIndex`) relative to a specific `IDiff` structure [1](#0-0) . Those indices are only meaningful for the exact diff (hunk layout) they were computed against — hunk boundaries, and therefore `unifiedDiffStart` offsets, shift depending on whether whitespace-only changes are hidden (`git diff -w`).

When committing, `applyPatchToIndex` calls `getWorkingDirectoryDiff(repository, file)` with **no `hideWhitespaceInDiff` argument**, so it defaults to `false`: [2](#0-1) 
`getWorkingDirectoryDiff`'s signature confirms the default: [3](#0-2) 

But the diff shown to the user in the Changes view — the one against which the user actually clicked/dragged to select lines — is loaded with the user's `hideWhitespaceInChangesDiff` preference: [4](#0-3) 

The only reconciliation performed when a diff changes is `withSelectableLines`, which merely intersects the selection with lines that are still "includeable" in the *newly loaded* diff (still fetched with the same whitespace setting) — it does not detect or correct for a hunk-layout shift caused by a *different* whitespace-diff mode being used at a later stage: [5](#0-4) 

`formatPatch`, which builds the actual patch applied with `git apply --cached`, blindly trusts `file.selection.isSelected(absoluteIndex)` against whatever diff it is handed: [6](#0-5) 

If a user enables "Hide whitespace" in the Changes view and a file has whitespace-only edits interleaved with real content edits, the hunk layout the user sees (and picks line numbers from) differs from the layout `applyPatchToIndex` computes when constructing the actual patch (since it always uses the non-whitespace-hidden diff). The stored `absoluteIndex` values from the user's selection therefore point at different lines in the two diffs. `formatPatch` then either includes lines the user never selected or drops lines the user did select — content is silently staged/committed incorrectly, with no error surfaced.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user who partially selects lines under "hide whitespace" mode can end up committing (and pushing) content different from what they intended and verified on screen — including possibly re-including lines they explicitly deselected, or omitting ones they selected. This is not observable in the diff-review UI (which still shows the whitespace-hidden view), so the discrepancy is silent. No exotic privileges are required; a normal user toggling a built-in preference (`hideWhitespaceInChangesDiff`) while doing a partial commit triggers it — it does not require an attacker-controlled repository, credentials, or local/physical access, which the task's valid-impact criteria call out as important. This is a structural application-logic bug, not a numeric-precision one.

### Likelihood Explanation
Moderate. It requires: (1) the whitespace-hiding option enabled in Changes view, (2) a file with a mix of whitespace-only and substantive line changes, and (3) the user selecting/deselecting individual lines (partial commit) rather than committing the whole file. This is a mainstream, documented feature combination (hide-whitespace toggle + partial-line staging), not a contrived edge case, and does not depend on any adversarial input — it can occur from routine developer workflow (e.g., reformatting + logic changes in the same hunk).

### Recommendation
Pass the same `hideWhitespaceInDiff` value used to render the selection UI into `getWorkingDirectoryDiff` inside `applyPatchToIndex` (or otherwise thread the exact diff instance/hash used for selection through to patch construction), and/or invalidate/re-map the `DiffSelection` whenever the effective diff-generation parameters (whitespace mode) differ from those used when the selection was captured, analogous to how `withSelectableLines` already reconciles line existence across diff reloads.

### Proof of Concept
1. Enable "Hide whitespace changes" in Desktop's Changes/diff view.
2. Modify a tracked file with two overlapping edits in one hunk: (a) a whitespace-only change (e.g. trailing space added) on line N, and (b) a substantive content change on line N+1.
3. With whitespace hidden, the diff view collapses/renumbers hunks so line (b) appears at a different `unifiedDiffStart`-relative index than it would in the full diff.
4. Deselect line (b) (uncheck it) intending to leave it out of the commit.
5. Commit. `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` fetches a *fresh, non-whitespace-hidden* diff (`app/src/lib/git/apply.ts:60`) and evaluates `file.selection.isSelected(absoluteIndex)` (`app/src/lib/patch-formatter.ts:157`) against that diff's indices — which no longer correspond to the lines the user checked/unchecked in the UI.
6. Inspect the resulting commit: the whitespace-only change and/or the substantive change end up included/excluded opposite to what the user selected in the UI, with no warning shown.
