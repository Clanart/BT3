### Title
Attacker-supplied `ReceivedOutput` bytes are trusted without binding the outpoint to on-chain data, letting an unprivileged party report unspendable/fabricated outputs under the victim's key - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
CVE-2026-12411 is a broken-access-control flaw: a request claimed ownership of a resource (another guest's storage volume) that was never verified. The analog in `bitcoin-serai` is `ReceivedOutput::read`, which deserializes the three fields that define "a spendable output owned by this key" — the spending `offset`, the `TxOut`, and the `OutPoint` — as fully independent, attacker-controlled values with no consistency or authenticity check (`networks/bitcoin/src/wallet/mod.rs:122-134`). Downstream, the only validation performed is that `p2tr_script_buf(key + G*offset) == output.script_pubkey` in `SignableTransaction::multisig` (`networks/bitcoin/src/wallet/send.rs:273-285`); the `outpoint` and the output `value` are never checked against anything real.

### Finding Description
`ReceivedOutput::read` parses:
1. `offset: Scalar` via `Secp256k1::read_F`,
2. `output: TxOut` via `consensus_decode`,
3. `outpoint: OutPoint` via `consensus_decode`,

and returns them as an authenticated "spendable output" (`mod.rs:120-134`). Nothing binds `outpoint` → `output` (i.e., that the referenced UTXO exists and contains this `TxOut`), nor `offset` → ownership.

When such an output is passed to `SignableTransaction::new`:
- `input_sat` is summed from the attacker-chosen `output.value` (`send.rs:175`), driving payment/change/fee arithmetic (`send.rs:223-235`),
- `tx_ins` is built from the attacker-chosen `outpoint` (`send.rs:177-185`),
- `prevouts` (committed to by every signature via `Prevouts::All`) is built from the attacker-chosen `TxOut`s (`send.rs:253`, `send.rs:375`).

`multisig` only rejects the input if `key + G*offset` doesn't produce the claimed `script_pubkey` (`send.rs:276-279`). An attacker who knows the victim's key (public) and a registered offset trivially satisfies this by copying the real `script_pubkey`. Everything else is unconstrained.

### Impact Explanation
This is a direct analog of "mount/read/overwrite another guest's volume": untrusted bytes cause the system to treat an arbitrary UTXO as belonging to the victim's key.

- **Fabricated funds reported as spendable**: an attacker submits a `ReceivedOutput` with the victim's `script_pubkey`, a real offset (e.g., `Scalar::ZERO`, which `Scanner::new` always registers, `mod.rs:164`), an arbitrary `outpoint` (including another party's UTXO or a non-existent one), and an inflated `value`. The wallet reports these as received funds and will construct/sign a transaction "spending" them — funds that are not spendable. This inflates `input_sat`, corrupting change and fee computation.
- **Unintended signatures**: because `Prevouts::All` commits every signature to the fabricated `prevouts` list (`send.rs:375`), honest signers produce signature shares — and `TransactionSignatureMachine::complete` aggregates a full Schnorr signature (`send.rs:413-428`) — over a transaction committing to prevout amounts/outpoints the signers never agreed to. Whether the resulting tx is consensus-invalid (inflated value/nonexistent outpoint) or validly spends a real victim UTXO under wrong accounting, the signed message does not reflect the signers' intent.

### Likelihood Explanation
`ReceivedOutput::read` is a public deserialization API in-scope per the threat model (untrusted bytes fed to `read`/`sign`/`complete` APIs). It is exercised across serialization round-trips (`mod.rs:137-148`) and is the natural boundary for outputs received from a scanner peer, database, or another process. An attacker needs only the victim's public key (to reuse its `script_pubkey`) and any registered offset — all public information. No key share, collusion, or protocol role is required.

### Recommendation
Authenticate `ReceivedOutput` end-to-end:
1. Verify `outpoint` resolves to the claimed `TxOut` (i.e., the output exists on-chain with matching `script_pubkey` and `value`) before treating a `ReceivedOutput` as received/spendable — either at `read` time by carrying a proof (e.g., merkle/block inclusion) or in `SignableTransaction::multisig`/`new` via a trusted UTXO lookup.
2. At minimum, enforce that the `script_pubkey` in `output` matches `p2tr_script_buf(key + G*offset)` at `ReceivedOutput` construction/`read` time (it currently isn't checked until `multisig`), and reject `offset` values the scanner never registered.
3. Document that `ReceivedOutput` must only originate from the local `Scanner` and must never be deserialized from untrusted sources without revalidation.

### Proof of Concept
Conceptual, using only public inputs:

```rust
// Victim's public group key K (public), base offset = Scalar::ZERO
// (always registered by Scanner::new, mod.rs:164).
let script = p2tr_script_buf(K).unwrap(); // public derivation, mod.rs:80-86

// Attacker fabricates a "received" output: huge value, arbitrary outpoint
// pointing at someone else's (or a nonexistent) UTXO.
let fake = ReceivedOutput {
    offset: Scalar::ZERO,
    output: TxOut { value: Amount::from_sat(1_000_000_000), script_pubkey: script },
    outpoint: OutPoint { txid: arbitrary_txid, vout: 0 },
};

// Serialize -> victim deserializes via ReceivedOutput::read (mod.rs:122-134):
// no error; the fabricated output is accepted as spendable.

// Victim builds a transaction:
let tx = SignableTransaction::new(vec![fake], &payments, Some(change), None, fee_rate)?;
// input_sat counts the fake 1 BTC (send.rs:175); change = fake_value - payments - fee
// is computed as if the funds exist (send.rs:223-235).

// multisig() passes because script_pubkey matches key + ZERO*G (send.rs:276-281).
// Honest signers then sign sighashes committing to the fabricated prevouts
// (Prevouts::All, send.rs:375), producing a signature over a transaction
// spending funds the multisig does not control.
```

Caveat: I could not fully trace whether upstream processor code re-validates `ReceivedOutput` against chain state before signing (the processor scanner path is out of scope). If such revalidation exists and is enforced on every path into `SignableTransaction`, the reachable impact reduces to the API-level integrity gap described above.
