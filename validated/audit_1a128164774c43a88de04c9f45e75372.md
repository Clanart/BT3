### Title
`SignableTransaction::new` omits the OP_RETURN data output when sizing the transaction, undercharging the fee relative to the actual transaction weight - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the UXD report (an amount computed in one unit/scale is used where a different scale is required), `SignableTransaction::new` computes `needed_fee` from a weight/vbyte estimate that excludes the OP_RETURN output it has already decided to append. The resulting transaction pays a fee correct only for a *smaller* transaction, so its effective feerate is below the caller-specified `fee_per_vbyte` and can even fall below the relay minimum that `TooLowFee` is meant to enforce.

### Finding Description
`SignableTransaction::new` builds `tx_outs`, including an OP_RETURN output carrying up to 80 bytes of caller-supplied `data` (`send.rs:193-202`). It then derives the fee from `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (`send.rs:204`), which constructs a template transaction whose `output` vector is built **only from `payments`** (`send.rs:85-93`) plus an optional change output (`send.rs:95-99`). The OP_RETURN output — roughly 9 bytes of overhead plus up to 80 bytes of pushed data, i.e. ~360+ weight units / ~90+ vbytes at maximum size — is never included in the template.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) is computed against a vbyte count that is too small, so the actual fee (`sum(inputs) - sum(outputs)`, `send.rs:138-141`, which equals `needed_fee` plus any non-change leftover) corresponds to a lower feerate than `fee_per_vbyte` once the real, larger transaction is serialized.
2. The minimum-relay guard compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (`send.rs:210-213`) using the same underestimated `vbytes`. A transaction carrying a large `data` payload can therefore pass the `TooLowFee` check while its real feerate is below the default relay minimum, producing an unbroadcastable transaction.
3. The same underestimated `weight` is the value checked against `MAX_STANDARD_TX_WEIGHT` (`send.rs:241`), so the max-size check also ignores the data output (though the later `weight` variable is only swapped to `weight_with_change` when change is added — the OP_RETURN output is never accounted for in either branch, `send.rs:225-235`).

Any caller of this public constructor can reach this by passing `Some(data)` as the `data` argument; no privileged position is required.

### Impact Explanation
Transactions produced with a `data` payload pay a systematically lower feerate than requested, and at the boundary can be outright non-relayable (real feerate < `DEFAULT_MIN_RELAY_TX_FEE`) despite passing the library's own `TooLowFee` validation. For a threshold-controlled wallet, the signed transaction would be rejected by the mempool or languish unconfirmed, leaving the inputs' funds effectively locked until a replacement is negotiated — a funds-availability failure caused purely by using the wrong (smaller) transaction size when converting the feerate into an absolute fee.

### Likelihood Explanation
Deterministic whenever `data` is `Some` and non-trivial in length: the miscalculation is structural, not input-dependent in whether it occurs, only in magnitude. The larger the data payload, the larger the fee/vsize discrepancy, up to ~90 vbytes of unaccounted size. Whether it crosses the relay minimum depends on how close `fee_per_vbyte` is to the floor.

### Recommendation
Include the OP_RETURN output in the weight/vbyte estimate. Either pass the fully constructed `tx_outs` (or at least `payments` plus the data output) into `calculate_weight_vbytes`, or construct the template `Transaction` after `tx_outs` is finalized so the estimate and the real transaction always agree:

```rust
// networks/bitcoin/src/wallet/send.rs
// Build tx_outs (payments + OP_RETURN) BEFORE estimating weight, then:
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs_without_change, None);
```

with `calculate_weight_vbytes` changed to accept pre-built `TxOut`s, and recompute similarly in the `change` branch so `weight`, `needed_fee`, and `MAX_STANDARD_TX_WEIGHT` all reflect the final output set.
