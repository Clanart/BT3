### Title

`ReceivedOutput::read` trusts a claimed scalar offset without re-verifying it against the output's `script_pubkey`, letting untrusted bytes claim a spendable-output "identity" the producer does not satisfy - (`networks/bitcoin/src/wallet/mod.rs`)

### Summary

The Grafana advisory's bug class is: an identifier is verified once (email at signup) but can later be re-set to an unverified value that collides with another principal's identity (email/username squatting). Serai's Bitcoin wallet has the same shape: a `ReceivedOutput` has two identity fields — the `script_pubkey` (the actual on-chain key commitment, analogous to the verified email) and the `offset` scalar (the claimed derivation path, analogous to the username-as-email). `Scanner::scan_transaction` sets `offset` correctly by looking the script up in the registered `scripts` map, but `ReceivedOutput::read` accepts whatever offset the byte stream claims and never checks that `p2tr_script_buf(key + offset·G) == output.script_pubkey` — or even that the offset is one of the registered ones (`External`/`Branch`/`Change`/`Forwarded`).

### Finding Description

`Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) derives `offset` from `self.scripts.get(&output.script_pubkey)`, so a scanned output is internally consistent: the script commits to `key + offset·G` (post-TapTweak parity normalization via `p2tr_script_buf`, lines 80-86).

`ReceivedOutput::read` (lines 122-134) instead deserializes `offset` directly from the input bytes with `Secp256k1::read_F` and stores it alongside an arbitrary `TxOut`/`OutPoint`, with no consistency check:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

This is exactly "change the email after verification": the binding between the script commitment and the offset was validated only at scan time, yet the serialized form lets a producer claim any offset. Downstream consumers trust the claimed offset as identity:

- `Output::key()` (processor/src/networks/bitcoin.rs:112-122) computes `scriptKey - offset·G` to determine which multisig key an output belongs to. A wrong offset attributes the output to a different/incorrect group key.
- `get_outputs` (processor/src/networks/bitcoin.rs:686-699) maps the offset's repr through `kinds[...]` to classify the output as `External`/`Branch`/`Change`/`Forwarded` — a fabricated offset either panics (`kinds[offset_repr_ref]` indexes unconditionally) or misclassifies the output, e.g., claiming `Change`/`Forwarded` semantics for an `External` deposit, bypassing the `data`/origin assignment reserved for external payments (lines 730-736).
- The transaction-building path re-keys each input by `output.offset()` when constructing per-input signing commitments; a mismatched offset makes the threshold signature verify under `key + claimed_offset·G` rather than the key the Taproot output actually commits to, producing an invalid witness.

### Impact Explanation

An unprivileged party feeding bytes into `ReceivedOutput::read`/`Output::read` can cause (a) funds to be reported as received under a group key that does not control them, or (b) an output to be reported received yet be unspendable, because the signer will apply the wrong per-input offset and the BIP-340 signature will not verify against the committed x-only key. This matches the accepted impact class "funds reported received that are not spendable." It also enables class squatting analogous to the username=email trick: the claimed-offset namespace is disjoint from the script namespace but is treated as interchangeable identity, so a crafted record can occupy `Change`/`Forwarded` classification intended only for internally derived offsets.

### Likelihood Explanation

Exploitation requires a path where a `ReceivedOutput`/`Output` is deserialized from bytes an attacker influences (as opposed to produced by `scan_transaction`/`get_outputs`, which are self-consistent). `Output::read` (processor/src/networks/bitcoin.rs:145-166) wraps `ReceivedOutput::read` with attacker-controlled `kind`, `presumed_origin`, and `data` as well, so any consumer that accepts serialized `Output`s rather than rescanning inherits the flaw. Where only scanner-produced outputs are used, the issue is latent rather than triggerable — hence Medium rather than High.

### Recommendation

Re-verify identity at deserialization, not just at registration:

- In `ReceivedOutput::read`, when the group key is in scope, check `p2tr_script_buf(key + offset·G) == Some(output.script_pubkey)`; where the key isn't available, make `offset` private and expose a constructor that only the `Scanner` can call, so the offset can never be asserted independently of the script.
- In `Output::key()` / `get_outputs`, reject offsets not present in the `kinds` map (`kinds.get(offset_repr_ref)` instead of indexing) and cross-check `kind` consistency with the re-derived script.

### Proof of Concept

```rust
// Receive a genuine external output (offset = 0) via Scanner::scan_transaction,
// then rewrite the claimed offset before deserialization.
let real: ReceivedOutput = scanner.scan_transaction(&tx).remove(0); // offset == 0
let mut bytes = real.serialize();
// Overwrite the offset field (first 32 bytes) with Scalar::ONE
bytes[..32].copy_from_slice(k256::Scalar::ONE.to_repr().as_ref());

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap(); // accepted
// forged.output().script_pubkey still commits to `key + 0·G`,
// yet forged.offset() == 1.
//
// Consequence 1 (attribution):
//   Output { output: forged, .. }.key() == scriptKey - 1·G != group key
// Consequence 2 (spending):
//   SignableTransaction::new(vec![forged], ...) re-keys this input by offset 1;
//   the produced schnorr signature verifies under key+1·G, not the committed
//   Taproot key -> witness invalid -> output unspendable.
// Consequence 3 (classification):
//   kinds[Scalar::ONE.to_repr()] is absent -> panic in get_outputs, or
//   choosing an offset equal to the Branch/Change/Forwarded registered offset
//   misclassifies an external deposit as an internal-kind output.
```

Note: I verified the inconsistency directly in `ReceivedOutput::read` and its consumers; the exact production call graph that supplies attacker-controlled bytes to `Output::read` was not fully traced within the indexed code, so the finding is stated at the deserializer trust-boundary where the unverified identity claim is accepted.
