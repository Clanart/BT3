## Finding: `aptos move verify-package` never actually verifies bytecode, only self-reported metadata

The external report is about a "distribution correctness" gap — a protocol accepts and processes data without an adequate validation guarantee, silently producing meaningless/misleading results. The Aptos-native analog I traced is in the **package verification path**: the `verify-package` CLI command, which Aptos documents as *"checks that on-chain bytecode matches a local source tree"* [1](#0-0) , never actually compares any bytecode at all.

### Finding Description

`VerifyPackage::execute` builds the package locally, then fetches the on-chain `PackageMetadata` **without bytecode** (`with_bytecode = false`), and calls `package.verify(&compiled_metadata)`: [2](#0-1) 

`CachedPackageRegistry::verify()` only diffs the `PackageMetadata` struct fields — `name`, `deps`, `modules` (the `ModuleMetadata` struct: `name`, `source`, `source_map`, `extension`), `manifest`, `upgrade_policy`, `extension`, and `source_digest`: [3](#0-2) 

None of these fields is cryptographically or otherwise tied to the actual compiled module bytes that are stored and executed on-chain. On the publish path (`code::publish_package_txn` → `code::publish_package`), the Move framework only checks that each module name in the compiled bytecode bundle is present in the metadata's declared `expected_modules` set: [4](#0-3) 

and the native/VM-side `validate_publish_request` similarly only checks module names and dependency allow-lists against metadata, never any digest of the metadata content against the actual bytecode: [5](#0-4) 

So `source`, `source_map`, `manifest`, and `source_digest` are **arbitrary, unverified, publisher-supplied bytes** with no on-chain linkage to the real module bytecode. A publisher can submit any bytecode alongside metadata claiming to correspond to some other (e.g. benign, previously-audited) source tree. `verify-package` then:
1. Rebuilds that same claimed source locally, producing `compiled_metadata` with matching `source`/`source_digest`/`modules` fields.
2. Fetches only the on-chain metadata (not the deployed `.mv` bytecode, since `with_bytecode=false`).
3. Diffs metadata-to-metadata and reports "Successfully verified source of package" even though the actual on-chain bytecode was never inspected or compared.

This breaks the "mismatch between verified bytes, package metadata... and committed module bytes" invariant called out in the publish pivots: the tool that is supposed to prove committed module bytes match a claimed source tree instead proves nothing about the bytes at all.

### Impact Explanation

Any downstream consumer relying on `aptos move verify-package` for code-safety assurance (auditors, integrators, users deciding whether to trust a contract as matching its published/audited source) can be misled into trusting bytecode that is functionally arbitrary and unrelated to the source it claims to represent. This is a verification/code-safety-invariant bypass on a security-relevant tool that is part of Aptos's documented publish/verification workflow, directly matching the "Bytecode verifier, loader, module-init handling, native publish helpers, and write-set conversion must agree on what is legal" pivot — here, the off-chain verifier does not even attempt to check the on-chain bytecode, let alone reconcile it with the metadata.

### Likelihood Explanation

High likelihood: this is not a race condition or edge case — it is the deterministic, always-true behavior of the `verify-package` command, since `with_bytecode` is hardcoded to `false` in `VerifyPackage::execute` and `CachedPackageRegistry::verify()` structurally never touches bytecode. Any publisher can trivially exploit this by publishing mismatched bytecode/metadata pairs and passing local `verify-package` checks that others may trust.

### Recommendation

`VerifyPackage::execute` should fetch the on-chain bytecode (`CachedPackageRegistry::create(client, account, true)`), extract the locally compiled bytecode units from `pack`, and byte-for-byte compare each module's actual on-chain bytecode against the corresponding locally compiled module — in addition to (not instead of) the existing metadata comparison. Consider also binding `source_digest`/`source` to the real bytecode on-chain (e.g., enforced in `code::publish_package`) so metadata cannot diverge from bytecode even prior to any off-chain verification attempt.

### Proof of Concept

1. Compile package `A` (benign, e.g. matches a public open-source repo) to get `metadata_A` and `code_A`.
2. Compile a different package `B` (malicious bytecode) to get `code_B`.
3. Publish `code_B` on-chain together with `metadata_A` (both are bcs::to_bytes and passed as separate arguments to `code::publish_package_txn`/`resource_account_create_resource_account_and_publish_package`/`object_code_deployment::publish` — nothing ties `metadata.modules[i].source`/`source_digest` to the actual `code[i]` bytes being deployed).
4. Run `aptos move verify-package --account <addr>` against local package `A`'s source tree.
5. Observe the tool prints "Successfully verified source of package" even though the deployed bytecode is `code_B`, not the bytecode compiled from `A`'s source — because `verify()` never inspected `code_B` at all. [6](#0-5) [7](#0-6)

    async fn execute(self) -> CliTypedResult<&'static str> {
        // First build the package locally to get the package metadata
        let build_options = BuildOptions {
            install_dir: self.move_options.output_dir.clone(),
            bytecode_version: fix_bytecode_version(
                self.move_options.bytecode_version,
                self.move_options.language_version,
            ),
            ..self.included_artifacts.build_options(&self.move_options)?
        };
        let w = self.env.writer();
        let pack = BuiltPackage::build_to(&w, self.move_options.get_package_path()?, build_options)
            .map_err(|e| CliError::MoveCompilationError(format!("{:#}", e)))?;
        let compiled_metadata = pack.extract_metadata()?;

        // Now pull the compiled package
        let client = self.rest_options.client(&self.profile_options)?;
        let registry = CachedPackageRegistry::create(client, self.account, false).await?;
        let package = registry
            .get_package(pack.name())
            .await
            .map_err(|s| CliError::CommandArgumentError(s.to_string()))?;

        // We can't check the arbitrary, because it could change on us
        if package.upgrade_policy() == UpgradePolicy::arbitrary() {
            return Err(CliError::CommandArgumentError(
                "A package with upgrade policy `arbitrary` cannot be downloaded \
                since it is not safe to depend on such packages."
                    .to_owned(),
            ));
        }

        // Verify that the source digest matches
        package.verify(&compiled_metadata)?;

        Ok("Successfully verified source of package")

    /// Creates a new registry.
    pub async fn create(
        client: Client,
        addr: AccountAddress,
        with_bytecode: bool,
    ) -> anyhow::Result<Self> {
        // Need to use a different type to deserialize JSON
        let inner = client
            .get_account_resource_bcs::<PackageRegistry>(addr, "0x1::code::PackageRegistry")
            .await?
            .into_inner();
        let mut bytecode = BTreeMap::new();
        if with_bytecode {
            for pack in &inner.packages {
                for module in &pack.modules {
                    let bytes = client
                        .get_account_module(addr, &module.name)
                        .await?
                        .into_inner()
                        .bytecode
                        .0;
                    bytecode.insert(module.name.clone(), bytes);
                }
            }
        }
        Ok(Self { inner, bytecode })
    }

                self_metadata.manifest
