### Title
Independently-implemented conflict-marker regexes in Copilot merge-conflict resolution can desynchronize hunk counting from hunk splicing, silently corrupting committed file content - (File: `app/src/lib/copilot-conflict-context.ts` / `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The seed report's broken invariant is: **a quantity is computed with one formula, then checked/consumed with a different formula**, so a value that passes validation is not actually the value that gets used downstream. In GitHub Desktop's Copilot-assisted merge-conflict resolution feature, the same pattern exists: the number and boundaries of conflict "hunks" in a file are computed twice, by two separately maintained regex-based marker detectors, and the count from the first pass gates the model's response while the second pass is what actually splices content back into the file that the user commits.

### Finding Description
`buildConflictContext` reads each conflicted file from disk and calls `extractConflictHunks` to find conflict-marker blocks, using marker regexes (`oursMarker`, `baseMarker`, `separatorMarker`, `theirsMarker`) defined in `copilot-conflict-context.ts`: [1](#0-0) [2](#0-1) 

The resulting `hunks.length` per file becomes `expectedHunkCounts`, which `validateResolutionPaths` uses as the ground truth to accept or reject the Copilot response: [3](#0-2) 

Separately, `reassembleResolvedFile` — which actually splices the model's per-hunk `resolvedContent` back into `rawContent` to produce the file that is written to disk and committed — re-detects marker blocks using its *own*, independently defined regexes: [4](#0-3) [5](#0-4) 

A `grep` across the repository confirms these are two entirely separate regex definitions (`oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker` vs. `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker`) with no shared constant or single source of truth for the conflict-marker grammar — exactly the "two different formulas for the same quantity" pattern from the seed report. Notably, the reassembly regex explicitly tolerates a bare marker with no trailing label (`/^<{7}(?:\s|$)/`, `/^>{7}(?:\s|$)/`), which is not confirmed to be mirrored in the extraction regex used for hunk counting. If the two detectors ever disagree on where a marker block starts/ends or how many blocks exist for a given adversarial file — e.g. one crafted by a malicious/compromised remote branch containing literal `<<<<<<<`/`=======`/`>>>>>>>`-like text as ordinary content (a plausible artifact of the exact bug class this task targets: attacker-controlled content fetched via `git remote`/branch merge) — the count used to validate the model's response (`extractConflictHunks`) will not match the blocks actually spliced by `reassembleResolvedFile`. Because the splice is matched **by order, not by content or line number** (`hunkIndex < hunkResolutions.length`), any divergence causes hunk resolutions to land in the wrong location, or leaves stray marker text in place, without any error being raised.

### Impact Explanation
Because `resolvedContent` is written to disk and then presented to the user for commit/staging, a desync between the counting pass and the splicing pass results in **silent corruption of what the user commits or pushes** — the exact "Valid Impact" category called out for this task. The corrupted output is not obviously wrong (no exception is thrown; `validateResolutionPaths` sees a plausible hunk count and passes), so a user could stage and push code that differs from what Copilot actually reasoned about, potentially reintroducing removed code, dropping intended changes, or leaving conflict-marker-shaped fragments in shipped source.

### Likelihood Explanation
This requires a conflicted file whose content happens to interact with the differing edge cases of the two regex implementations (e.g. bare vs. labeled markers, or unusual whitespace around markers) — a condition that can be engineered by content in a fetched/merged branch, satisfying the "attacker controls a fetched repository" precondition. It does not require local/physical access, admin rights, or any credential leakage. However, exploiting it precisely (to land a chosen payload in a chosen location) requires the attacker to also control or predict the surrounding "ours"/"theirs" hunk content, and it only manifests when the user opts into Copilot conflict resolution, so likelihood is lower than the original report's "always happens" case, but the underlying architectural flaw (duplicated marker parsing) is present on every Copilot resolution regardless of trigger frequency.

### Recommendation
Extract a single, shared conflict-marker parsing module (marker regexes and hunk-boundary detection) used by both `extractConflictHunks` (context gathering / validation) and `reassembleResolvedFile` (splicing), so the count used to gate the model's response and the blocks used to splice its output are guaranteed to be computed identically. Additionally, `reassembleResolvedFile` should verify that the number of marker blocks it actually finds equals the validated `hunks.length` for that file before writing, and fail closed (falling back to "skip file, resolve manually") rather than silently splicing on a mismatched count.

### Proof of Concept
1. Set up a merge conflict where one side's content (in `oursContent`/`theirsContent`/surrounding context) is a documentation string that itself contains a bare `<<<<<<<` line (no trailing branch-name label), which is valid input to `reassemblyOursMarker`'s `(?:\s|$)` alternative in `copilot-conflict-resolution.ts:524-526` but must be checked against whatever pattern `oursMarker` in `copilot-conflict-context.ts` actually requires.
2. Trigger `buildConflictContext` → `extractConflictHunks`, and observe whether the reported `hunks.length` (used for `validateResolutionPaths`) matches the number of marker blocks that `reassembleResolvedFile` finds when it re-scans the same `rawContent`.
3. If the counts diverge, submit a Copilot response with a hunk count matching the (possibly wrong) `expectedHunkCounts`; `validateResolutionPaths` accepts it, but `reassembleResolvedFile`'s independent block detection splices the resolutions into different marker blocks than intended, corrupting the file that is subsequently written and offered for commit.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
