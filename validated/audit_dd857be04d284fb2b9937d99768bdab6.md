### Title
Missing `validateApprovalEventDoesNotExist` call allows malicious native ERC20 to self-approve escrowed tokens during `ConvertERC20`, enabling later theft of token-pair-backed escrow - (File: x/erc20/keeper/msg_server.go)

### Summary
The docstring of `convertERC20IntoCoinsForNativeToken` explicitly documents a security check — "check for unexpected `Approval` event in logs" — that is never actually invoked in the implementation, mirroring exactly the "misleading docstring vs. actual behavior" bug class from the external report. The helper function that performs this check, `validateApprovalEventDoesNotExist`, exists in the codebase but is dead code, called only from its own test file.

### Finding Description
`ConvertERC20` escrows a user's native ERC20 tokens into the module account (`types.ModuleAddress`) and mints backing native coins 1:1 [1](#0-0) . The function's own documentation states it performs five steps, the last being "check for unexpected `Approval` event in logs" [2](#0-1) .

In the actual implementation, only the `Transfer` event / return value and the resulting balance delta are validated [3](#0-2) . There is no call anywhere to `validateApprovalEventDoesNotExist`, the function that was clearly written for this exact purpose [4](#0-3) . A repository-wide search confirms this helper is referenced only from its unit test, never from production code [5](#0-4) .

`RegisterERC20` for native ERC20 contracts is permissionless when governance enables `PermissionlessRegistration`, meaning an attacker can register an arbitrary, attacker-authored ERC20 contract as a token pair [6](#0-5) . Because `CallEVMWithData` executes the token's `transfer(moduleAddress, amount)` function with full EVM semantics (including arbitrary internal logic, e.g. a malicious `transfer()` override that also calls `_approve(moduleAddress, attacker, hugeAmount)`), a malicious token contract can, within the same `transfer` call, emit both a `Transfer` event (satisfying the existing check) and grant the attacker's address an ERC20 `allowance` over the module account's escrowed token balance. Since the balance-delta invariant only checks the module's own token balance immediately after the call and does not care about allowances, this passes all existing invariant checks (lines 113-130). The bank module then mints and sends native coins 1:1 backed by tokens that are still nominally in escrow but are now attacker-approved [7](#0-6) .

The attacker can subsequently call `transferFrom(moduleAddress, attacker, amount)` directly on the malicious ERC20 contract (outside of the module's control) to drain the escrowed tokens while the previously minted native coins remain in circulation — resulting in unbacked native coin supply for that token pair, a duplication of spendable value.

### Impact Explanation
This breaks the erc20 module's core 1:1 escrow-backing invariant between native coins and locked ERC20 tokens. An attacker can register a malicious contract, convert tokens to mint fully-backed native coins, then separately drain the escrow via a self-granted allowance, leaving native coins circulating with no backing asset. This is unauthorized extraction of escrowed/token-pair-backed value and corruption of the coin-to-token backing accounting — a Critical-class impact under the "unauthorized extraction of escrowed assets" and "irreversible accounting corruption of token-pair-backed balances" categories.

### Likelihood Explanation
Requires either (a) governance-enabled `PermissionlessRegistration` for native ERC20 token pairs, allowing any unprivileged user to register their own malicious contract, or (b) an already-registered but not fully vetted/upgradeable/proxy ERC20 contract behaving maliciously post-registration. Given `RegisterERC20` explicitly supports a permissionless path [8](#0-7) , this is reachable by an ordinary unprivileged user without any privileged action, satisfying the "unprivileged trigger" requirement. Exploitation requires writing a custom ERC20 contract with the described `transfer` override, which is straightforward.

### Recommendation
Restore the call to `validateApprovalEventDoesNotExist` on the logs returned by the escrow `transfer` call in `convertERC20IntoCoinsForNativeToken` (and likewise in `ConvertCoinNativeERC20` / any other CallEVM-based escrow flows), so that any unexpected `Approval` event emitted during the escrow transfer causes the conversion to be rejected, matching the documented and originally intended behavior.

### Proof of Concept
1. With `PermissionlessRegistration` enabled (or using an existing native token pair the attacker controls), deploy a malicious ERC20 contract whose `transfer(address to, uint256 amount)` implementation performs the standard transfer/emits `Transfer`, but additionally calls internal `_approve(to, attackerAddress, amount)` (or a fixed large allowance) whenever `to == moduleAddress`.
2. Register this contract via `MsgRegisterERC20` (permissionless path) to create a token pair.
3. Call `MsgConvertERC20` from the attacker's account, converting `amount` of the malicious ERC20 into native coins. `convertERC20IntoCoinsForNativeToken` executes the transfer (escrowing tokens + secretly approving the attacker), verifies only the `Transfer` event and balance delta (both satisfied), then mints and sends `amount` of native coins to the attacker.
4. From an ordinary EOA, call `maliciousToken.transferFrom(moduleAddress, attacker, amount)` using the allowance granted in step 1, draining the escrowed tokens from `types.ModuleAddress`.
5. The attacker now holds both the freshly minted native coins from step 3 and the drained ERC20 tokens from step 4 — the native coin supply for that token pair is now unbacked, demonstrating the accounting corruption.

// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))

			return nil, err

import (

// validateApprovalEventDoesNotExist returns an error if the given transactions logs include
// an unexpected `Approval` event
func validateApprovalEventDoesNotExist(logs []*types.Log) error {
	for _, log := range logs {
		if log.Topics[0] == logApprovalSigHash.Hex() {
			return errors.Wrapf(
				types2.ErrUnexpectedEvent, "unexpected Approval event",
			)
		}
	}

	return nil
}
