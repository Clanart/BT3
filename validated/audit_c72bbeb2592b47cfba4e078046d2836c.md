### Title
`Scanner::scan_transaction` reports outputs as received funds regardless of their value, crediting outputs whose spend fee exceeds their value — (`File: networks/bitcoin/src/wallet/mod.rs`)

### Summary
In the Zaros report, `_fillOrder` debits the opening fee without reserving the future liquidation fee, so collateral is reported as backing a position while being insufficient to pay the mandatory fee that spending/closing it requires. The analog in `bitcoin-serai` is `Scanner::scan_transaction`: it matches `script_pubkey` only and records every matching output as a spendable `ReceivedOutput`, with no check that the output's value can cover the marginal fee required to spend it. An attacker can send dust (even 1 sat, or any amount below `input_vbytes * fee_rate`) to a Serai address; the scanner reports it as received funds even though the network will never let those satoshis be recovered profitably — or, for sub-dust values, relayed at all.

### Finding Description
`scan_transaction` iterates transaction outputs, looks up `output.script_pubkey` in `self.scripts`, and pushes a `ReceivedOutput` unconditionally — the only check performed is `u32::try_from(vout)`. There is no comparison of `output.value` against `DUST` (546, defined in `send.rs:32`) or against the marginal spend cost.

Every input added to a `SignableTransaction` costs ~57 vbytes of witness/signature data (see the weight model in `calculate_weight_vbytes` and the 230-WU analysis in `processor/src/networks/bitcoin.rs`). `SignableTransaction::new` enforces `input_sat >= payment_sat + needed_fee` *globally* (`send.rs:215`), so a dust input either:
- makes an otherwise-valid transaction fail `NotEnoughFunds` when it is the only/marginal input, or
- silently burns more in fee than it contributes when bundled with other inputs.

Meanwhile `Scanner` (and `ReceivedOutput::read`, which also performs no value validation) surfaces the output to downstream accounting as received, spendable balance. The Zaros pattern — "balance credited as available although it cannot cover the fee required to actually use it" — maps directly: Serai books the output's full `value()` while the mandatory spend fee makes its net contribution zero or negative.

Coinbase immaturity is at least acknowledged in the `scan_block` docs (`mod.rs:218-219`); the insufficient-for-spend-fee case has no such guard or documentation.

### Impact Explanation
Funds are reported received that are not economically spendable. Downstream accounting credits users/protocol the full face value of dust deposits; when a Plan later tries to consume them, the transaction either becomes unfulfillable (`NotEnoughFunds`/`NoOutputs`) or the inputs must be dropped as operating costs — i.e., the credited funds can never be disbursed. An attacker can grief deposits cheaply, creating permanently stranded accounting entries, matching the "funds reported received that are not spendable" severity class.

### Likelihood Explanation
Any unprivileged party can send a Bitcoin transaction to a Serai address. Creating a below-spend-cost output costs only the output value itself (as low as a few hundred satoshis, or even 0-value OP_RETURN-adjacent dust if mined). No validator collusion, leaked keys, or malformed curves are needed — only a normal on-chain payment, exactly the public-input surface allowed.

### Recommendation
In `Scanner::scan_transaction`, skip outputs whose `value` is below a conservative spendable threshold (e.g., `DUST`, or the ~57-vbyte marginal input cost at the minimum viable fee rate), or at minimum surface the value so callers can filter. Correspondingly, `ReceivedOutput::read` should reject outputs that cannot cover their own spend fee, and `SignableTransaction::new` should refuse inputs whose value is below the marginal fee they add.

### Proof of Concept
```rust
// A Scanner registered for `key` scans a TX paying it a dust output.
let mut scanner = Scanner::new(key).unwrap();
// Attacker tx: P2TR output to `key` of 300 sats (< DUST = 546, and below
// ~57 vbytes * fee_rate marginal spend cost).
let outputs = scanner.scan_transaction(&attacker_tx);
assert_eq!(outputs.len(), 1);           // reported as received
assert_eq!(outputs[0].value(), 300);

// Any attempt to spend it fails funding checks — the fee the input adds
// exceeds its value, so it can never be part of a valid SignableTransaction.
let payments = vec![(p2tr_script_buf(dest).unwrap(), 546)];
assert!(matches!(
  SignableTransaction::new(vec![outputs[0].clone()], &payments, None, None, FEE),
  Err(TransactionError::NotEnoughFunds { .. })
));
// Credited 300 sats; spendable 0 sats. Same defect class as the Zaros
// "margin reported sufficient although the liquidation fee cannot be paid".
```
