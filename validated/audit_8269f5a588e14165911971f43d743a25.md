This confirms the intended design contrast: `vlMGPBaseRewarder._calExpireForfeit` (rewards/vlMGPBaseRewarder.sol:386-400) correctly computes `rewardablePercentWAD` via `vlMGP.getRewardablePercentWAD(_account)`, which weights cooldown time-in-progress against fully-locked amounts, so a mid-cooldown vlMGP holder is genuinely penalized. The mWOMSV equivalent never calls the analogous `mWOMSV`/`ILocker` getters — it hardcodes `rewardableAmount = _amount`, permanently returning zero forfeiture. This validates the audit question's premise as an actual code defect rather than a misread.

### Title
Dead `_calExpireForfeit` in mWOMSVBaseRewarder always returns zero forfeiture, letting cooldown mWOM stakers steal pro-rata yield from long-term lockers - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` (lines 385-398) sets `rewardableAmount = _amount` before comparing it to itself, so `forfeitAmount` is unconditionally `0` regardless of the account's lock/cooldown state. Because `balanceOf()` (lines 146-149) delegates to `IMasterMagpie.stakingInfo`, which for `mWomSV` includes both fully-locked and in-cooldown balances (`mWomSV.balanceOf`, wombat/mWomSV.sol:101-103), any holder who has started `startUnlock()` still accrues and can withdraw their full, un-forfeited pro-rata share of rewards distributed via `queueNewRewards`/`donateRewards`, exactly like a fully-locked long-term staker.

### Finding Description
- `donateRewards(uint256 _amountReward, address _rewardToken)` (mWOMSVBaseRewarder.sol:296-301) is unauthenticated (no `onlyManager`/`onlyOwner`), callable by anyone holding an already-registered reward token, and funnels into `_provisionReward`, which updates `rewardPerTokenStored` proportionally across `totalStaked()` [1](#0-0) [2](#0-1) .
- Each user's reward entitlement is computed from `balanceOf(_account)` in `earned`/`_earned`, and `balanceOf` returns `staked` from `IMasterMagpie(masterMagpie).stakingInfo(stakingToken, _account)` — for the `mWomSV` staking token this equals `getUserTotalLocked(_user) + getUserAmountInCoolDown(_user)`, i.e., cooldown balance counts the same as locked balance [3](#0-2) [4](#0-3) .
- On claim, `_sendReward` is supposed to penalize cooldown users by subtracting `_calExpireForfeit(_account, userRewards[...])` before transferring [5](#0-4) . But `_calExpireForfeit` is broken:
```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount) revert InvalidRewardableAmount();
    uint256 forfeitAmount = _amount - rewardableAmount;   // always 0
    ...
    return forfeitAmount;                                  // always 0
}
``` [6](#0-5) 
It never consults `_account`'s cooldown status at all — contrast with the sibling `vlMGPBaseRewarder._calExpireForfeit`, which correctly multiplies `_amount` by `vlMGP.getRewardablePercentWAD(_account)` (a genuine time-weighted cooldown penalty) before comparing [7](#0-6) [8](#0-7) . The mWOMSV variant is dead/no-op code that always returns 0, so `toSend == userRewards[...]` unconditionally in `_sendReward`.

Exploit flow: an attacker (or any regular user) calls `mWomSV.startUnlock(amount)` to place mWOM into cooldown (a normal, permissionless action) [9](#0-8) . Their `balanceOf` in the rewarder is unaffected (cooldown counts fully). When anyone calls `donateRewards`/`queueNewRewards`, `rewardPerTokenStored` increases pro-rata to `totalStaked()`, and the cooldown attacker's `earned()`/`getReward()` pays out 100% of their share with zero forfeiture — identical to a fully-locked long-term staker, despite economically being mid-exit.

### Impact Explanation
This misallocates/diverts protocol yield: reward funds intended (per the sibling vlMGP mechanism's design intent) to penalize short-term/cooldown participants and redistribute the forfeited portion back to long-term lockers instead flow entirely to cooldown gamers. This is a theft of unclaimed yield from long-term stakers to short-term participants — a quantifiable, repeatable economic loss for every `donateRewards`/`queueNewRewards` event as long as any account holds mWOM in cooldown.

### Likelihood Explanation
No privilege is required: `startUnlock` is a normal user action available to any mWOM/mWomSV holder, and `donateRewards` is intentionally permissionless. The bug is deterministic and 100% reproducible for every reward distribution as long as the contract has cooldown participants — it is not dependent on precise front-running timing, since forfeiture is unconditionally zero in all cases (locked or cooldown).

### Recommendation
Fix `mWOMSVBaseRewarder._calExpireForfeit` to actually compute a rewardable fraction based on the account's cooldown state, mirroring `vlMGPBaseRewarder`'s pattern — e.g., add a `getRewardablePercentWAD`-equivalent function to `mWomSV`/`ILocker` weighting `getUserTotalLocked` vs. `getUserAmountInCoolDown` (with a time-decay factor as in `VLMGP.getRewardablePercentWAD`), and use that percentage to scale `rewardableAmount` instead of hardcoding it equal to `_amount`.

### Proof of Concept
Foundry test outline:
1. Deploy `mWomSV`, `MasterMagpie`, `mWOMSVBaseRewarder`, and a reward token; register the reward token via `queueNewRewards` once (or seed `isRewardToken`).
2. Attacker locks `X` mWOM via `mWomSV.lock(X)`, staking into `MasterMagpie`, then immediately calls `mWomSV.startUnlock(X)` to place the full balance in cooldown.
3. A second user (or the test itself) calls `mWOMSVBaseRewarder.donateRewards(rewardAmount, rewardToken)` (no special permission needed, just `approve` + call).
4. Advance no time (attacker is still mid-cooldown, `endTime > block.timestamp`).
5. Call `getReward(attacker, attacker)` through `MasterMagpie` (or directly if test wires `onlyMasterMagpie` mock) and assert `IERC20(rewardToken).balanceOf(attacker) == earned(attacker, rewardToken)` with `calExpireForfeit(attacker, rewardToken) == 0`, i.e., full un-forfeited payout despite active cooldown — proving forfeiture never triggers.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
