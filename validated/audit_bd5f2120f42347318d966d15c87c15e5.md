## Analysis

The reachable analog to the "lack of slippage protection" bug class is in `wombat/ArbWomUp3.sol`, in the `_deposit` internal function invoked from the public, unprivileged entrypoint `incentiveDeposit`.

### Root cause

`ArbWomUp3.incentiveDeposit(uint256 _amount, uint256 _convertRatio, bool _bullMode, uint256 _mode)` is callable by any wallet and, for `_mode == 2`, routes half the user's deposited WOM through `SmartWomConvert.convert()` with a **hardcoded `_minRec` of `0`**: [1](#0-0) 

That `0` flows straight into `SmartWomConvert._convertFor`, where it becomes the slippage check on the WOM→mWOM buyback swap, and the router call itself also passes a literal `0` as `amountOutMin`: [2](#0-1) 

Since `_minRec == 0`, the check `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` can never fail, and the underlying `IWombatRouter.swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)` accepts any output amount, including one degraded by a sandwich attack. This is exactly the "lack slippage protection" bug class from the BabyDogeCoin report: a token swap executed with `amountOutMin = 0`, letting an attacker sandwich the swap and extract value that belongs to the depositing user.

Contrast this with `ArbWomUp2._bullMGP`, `SmartWomConvert.convert`/`convertFor` (external, user-supplied `_minRec`), and `WombatStaking.deposit/withdraw` (user-supplied `_minimumLiquidity`/`_minAmount`) — all of these correctly forward a caller-chosen minimum. `ArbWomUp3._deposit`'s mode-2 branch is the one path where the contract itself overrides that protection with a constant `0`, not the user.

### Title
Zero-slippage WOM→mWOM swap in ArbWomUp3 incentiveDeposit (mode 2) enables sandwich theft of user funds - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.incentiveDeposit` with `_mode == 2` calls `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)`, hardcoding the minimum-receive parameter to `0`. This disables slippage protection on the WOM→mWOM buyback swap executed inside `SmartWomConvert._convertFor`, which itself forwards `0` as `amountOutMin` to `IWombatRouter.swapExactTokensForTokens`.

### Finding Description
`ArbWomUp3._deposit` (called from the public `incentiveDeposit` function) splits the user's WOM 50/50 for `_mode == 2`: half is deposited 1:1 into `mWom`, and half is passed into `SmartWomConvert.convert(toSwap, _convertRatio, 0, 0)`. [3](#0-2)  Inside `SmartWomConvert._convertFor`, this `0` becomes both the on-chain router slippage bound and the post-swap sanity check, meaning the swap will succeed and be accepted no matter how little `mWom`/`WOM` is actually returned. [4](#0-3)  An attacker monitoring the mempool can front-run the `incentiveDeposit` transaction, push the `womMWomPool` price against the victim, let the zero-protected swap execute at the worst rate, then back-run to restore the price and pocket the difference extracted from the victim's own deposited WOM.

### Impact Explanation
This is a direct theft of an ordinary user's deposited funds during their own `incentiveDeposit` (mode 2) transaction — funds meant to be locked as `mWom`/`mWomSV` are instead partially extracted by an MEV sandwicher via price manipulation of the on-chain WOM/mWOM pool, with no on-chain limit to bound the loss.

### Likelihood Explanation
Any wallet can call `incentiveDeposit` with `_mode == 2` at any time; no privileged role is required to trigger the vulnerable code path, and sandwiching an unprotected `swapExactTokensForTokens` call is a standard, low-cost MEV technique on BNB/related chains hosting Wombat pools.

### Recommendation
Do not hardcode `_minRec`/`amountOutMin` to `0` in `ArbWomUp3._deposit`. Either compute an on-chain expected-output-based minimum (e.g., via `SmartWomConvert.estimateTotalConversion` with an acceptable tolerance) before calling `convert`, or expose a user-supplied minimum-receive parameter on `incentiveDeposit` that is threaded through to `SmartWomConvert.convert`'s `_minRec` argument, matching the pattern already used in `ArbWomUp2._bullMGP` and `SmartWomConvert.convert`'s external entrypoints.

### Proof of Concept
1. Attacker observes a pending `incentiveDeposit(_amount, _convertRatio, _bullMode, 2)` transaction from a victim in the mempool.
2. Attacker front-runs by swapping WOM for mWOM (or vice versa) on `womMWomPool` to skew the pool price unfavorably for the upcoming victim swap.
3. Victim's transaction executes: `ArbWomUp3._deposit` calls `SmartWomConvert.convert(toSwap, _convertRatio, 0, 0)`, which calls `IWombatRouter.swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)` — accepting any output amount since `amountOutMin = 0`. [5](#0-4) 
4. Attacker back-runs, reversing their initial swap and capturing the price-impact profit extracted from the victim's WOM, while the victim receives a below-market amount of `mWom` locked via `mWomSV.lockFor`. [6](#0-5)
