### Title
Surjective offset registration in `Scanner` allows an attacker to alias a victim's receive address (destination tampering analog) - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`Scanner::register_offset` silently mutates the caller's requested scalar offset: if `key + G·offset` yields an odd-Y point, the offset is incremented until an even point is found, and the resulting `script_pubkey` is the only identity recorded (`scripts: HashMap<ScriptBuf, Scalar>`). Because offsets are surjective rather than bijective, two distinct requested offsets can map to the same registered script. An unprivileged party who can cause offsets to be registered (e.g., any protocol that derives per-invoice/per-deposit offsets from public data before handing the corresponding Taproot address to a payer) can deliberately pre-register the offset the victim's request will collide into, making the attacker's deposit address byte-identical to the victim's. All subsequent payments are matched purely by `script_pubkey`, so funds sent to the collided address are indistinguishable and are attributed to whichever offset was registered first — the functional equivalent of substituting the recipient address during a multisig receive/spend flow.

### Finding Description
In `register_offset` (networks/bitcoin/src/wallet/mod.rs:180-196):

```rust
loop {
  match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
    Some(script) => {
      if self.scripts.contains_key(&script) { None?; }
      self.scripts.insert(script, offset);
      return Some(offset);
    }
    None => offset += Scalar::ONE,
  }
}
```

Two aliasing behaviors exist:

1. **Increment collision**: if `key + G·o` is odd, requested offset `o` actually registers the script for offset `o+1`. If `o+1` (or any `o+k` chain that increments into it) is later requested, it returns `None`. Conversely, whoever registers first "wins" a shared script.
2. **Direct collision**: any requested offset whose first reachable even point equals an already-registered point is rejected — but an attacker can choose their requested offset freely to target a specific *future* honest offset. Given a registered script `S = p2tr(even(key + G·o'))`, the attacker registers `o' + 1` while `key + G·(o'+1)` happens to be odd (≈50% per registration); when the honest party later requests `o'+1`, the increment loop lands on `o'+2`... — more importantly, an attacker who registers `o'+1` first causes the honest request for `o'` (when `key+G·o'` is odd) to collide and return `None`, or causes the honest request for `o'+1` to be rejected outright.

`scan_transaction` (mod.rs:199-214) keys everything on `output.script_pubkey`, and `ReceivedOutput` carries back the stored scalar. The offset is the sole spend-credential: `SignableTransaction::multisig` re-derives `keys.offset(offset)` and checks it against the prevout script (send.rs:273-285). Since a script is registered once under a single scalar, the alias means the attacker's and victim's logical "addresses" are the same on-chain object; any application-level bookkeeping that treats distinct requested offsets as distinct destinations (invoices, order IDs, deposit accounts) mis-attributes or loses the payment.

### Impact Explanation
This is the Serai-shaped analog of the multisig recipient-address tampering in the reference incident: the *intended* destination (offset/derived address) is silently altered between intent and registration, while everything downstream (scanning, crediting, spending via `TransactionMachine`) proceeds normally because it only sees the final tampered script. Concretely, an attacker who causes their offset to be registered ahead of a colliding honest offset either (a) causes the honest registration to fail (`None`), denying the victim a receive address, or (b) receives a `ReceivedOutput` under their offset for a payment the victim believed was destined for the victim's distinct offset — funds effectively redirected into an address-alias controlled by the attacker's earlier registration, with no distinguishing on-chain evidence. No secret material is required; only public knowledge of `key` and the ability to trigger `register_offset` calls (public input into a public API).

### Likelihood Explanation
Each requested offset whose point is odd (probability ~1/2) is incremented, so collisions with the adjacent offset are not exotic — they occur whenever consecutive offsets are used. An attacker able to choose their registration order or predict honest offsets (e.g., sequential invoice counters, or offsets derived as `hash(invoice_id)` where the attacker can grind `invoice_id`) can force an alias with modest effort: they need a scalar `o_a` whose resolved even point equals the victim's resolved point, which is reachable by picking `o_a` one step ahead/behind a parity boundary the victim will cross. The check `self.scripts.contains_key(&script)` then either silently rejects the honest registration or silently reuses the script. The preconditions (public group key, attacker-influenced offset registration) match the "public inputs only" reachability requirement.

### Recommendation
Make offset registration injective: reject requested offsets whose `key + G·offset` is odd rather than incrementing (return `None` and let the caller pick a new offset), so each returned script corresponds 1:1 to the caller's chosen scalar. If incrementing must be kept for compatibility, the collision is intrinsic and the API must expose it: return the resolved offset *and* the script, and document that a `None` return means "address already issued to another offset" so callers can detect aliasing instead of silently proceeding. Additionally, `Scanner` should store and compare `(offset → script)` bidirectionally and flag when a requested offset resolves to an existing script under a *different* logical offset, turning the silent alias into an explicit error.

let mut scanner = Scanner::new(key).unwrap();

// Honest party intends offset o where (key + G*o) is odd-Y.
// Scanner silently registers script(key + G*(o+1)) and reports "offset o+1".
// Attacker, knowing key and observing/anticipating sequential offsets,
// registers o+1 FIRST:
let attacker_req = o + Scalar::ONE;               // attacker-chosen public input
let a = scanner.register_offset(attacker_req);    // succeeds if point even:
                                                  // a == Some(o+1), script S recorded

// Victim now requests their intended offset o (odd point):
let v = scanner.register_offset(o);
// loop increments o -> o+1; script == S; contains_key(S) -> None
assert_eq!(v, None); // victim's receive address was aliased by the attacker

// Any payer paying to S produces a ReceivedOutput attributed to offset o+1
// (the attacker's registration), indistinguishable from the victim's intent:
//   scan_transaction matches output.script_pubkey == S
//   -> ReceivedOutput { offset: o+1, .. } credited under attacker's offset
