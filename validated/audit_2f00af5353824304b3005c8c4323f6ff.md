### Title
Fee-on-transfer LP tokens cause over-minting of receipt tokens in `depositLP` - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.depositLP()` mints receipt tokens 1:1 based on the caller-supplied `_lpAmount` parameter instead of the actual amount of LP tokens received via `transferFrom`. If the underlying LP token (`poolInfo.lpAddress`) charges a transfer fee, the contract receives less than `_lpAmount` but mints receipt tokens (and stakes into MasterWombat) as if the full amount was received.

### Finding Description
In `WombatStaking.sol`, the `deposit()` function correctly protects against balance discrepancies by measuring the actual LP tokens received before minting: [1](#0-0) 
It transfers the deposit token, deposits into the Wombat pool, computes `lpReceived` as the balance delta, and mints receipt tokens based on `lpReceived`.

However, `depositLP()` does not follow the same pattern: [2](#0-1) 
It calls `safeTransferFrom(_for, address(this), _lpAmount)`, then immediately calls `_toMasterWomAndSendReward(_lpAddress, _lpAmount, true)` and mints `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` — using the nominal `_lpAmount` parameter rather than the tokens actually received by the contract. If `poolInfo.lpAddress` is (or becomes) a fee-on-transfer token, the contract's actual LP balance/stake in MasterWombat will be less than the receipt tokens minted.

The equivalent entry points `WombatPoolHelper.depositLP()` / `WombatPoolHelperV2.depositLP()` / `AnkrBNBPoolHelper.depositLP()` are unprivileged wallet functions any user can call, forwarding straight into this vulnerable `WombatStaking.depositLP()`: [3](#0-2) 

### Impact Explanation
Because receipt tokens (which represent claims on staked LP/MasterWombat positions and drive `MasterMagpie` reward accounting via `BaseRewardPool`) are minted based on the nominal transferred amount rather than the amount actually received, a fee-on-transfer LP token would create a permanent shortfall between total receipt tokens outstanding and actual custodied/staked LP. This is a protocol insolvency condition: later withdrawers (via `withdraw()`, which burns receipt tokens 1:1 and withdraws from the Wombat pool) would find that the pool cannot cover claims for all receipt-token holders, since the underlying MasterWombat stake is short by the accumulated transfer fees, permanently freezing funds for some depositors.

### Likelihood Explanation
This requires `poolInfo.lpAddress` to be a fee-on-transfer token for a registered pool. Pool registration is admin-only (`registerPool`), so likelihood depends on whether any Wombat pool LP token used by the protocol implements transfer fees; standard Wombat LP tokens (via `IAsset`) are not fee-on-transfer under normal operation, making current-state exploitability low. However, the code pattern itself is an unguarded root-cause defect matching the reported bug class, and would immediately manifest as an accounting break for any current or future fee-on-transfer-compatible LP/receipt token.

### Recommendation
In `WombatStaking.depositLP()`, measure the actual amount of LP tokens received by comparing `balanceOf(address(this))` before and after the `safeTransferFrom` call (as already done in `deposit()`), and use that measured amount for both `_toMasterWomAndSendReward` and the receipt token mint, instead of trusting the caller-supplied `_lpAmount`.

### Proof of Concept
1. Admin registers a pool where `_lpAddress` is (or is later upgraded/replaced to be) a fee-on-transfer token.
2. A user calls `WombatPoolHelperV2.depositLP(_lpAmount)` → `WombatStaking.depositLP(lpToken, _lpAmount, msg.sender)`.
3. `safeTransferFrom(_for, address(this), _lpAmount)` transfers `_lpAmount` nominally, but the contract only actually receives `_lpAmount - fee`.
4. `_toMasterWomAndSendReward(_lpAddress, _lpAmount, true)` stakes/accounts for `_lpAmount` (more than actually held) and `mint(msg.sender, _lpAmount)` issues receipt tokens for the full nominal amount.
5. Over repeated deposits, total receipt token supply exceeds the actual LP tokens custodied/staked by the accumulated fee amount, so the last users to call `withdraw()` cannot be paid out in full — funds are permanently stuck. [2](#0-1)
