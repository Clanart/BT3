### Title
`updateEndRemainingAllocation()` can be re-called to re-snapshot the bonus denominator, breaking pro-rata bonus accounting - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is `public`, has no access control and no one-shot guard, so it unconditionally overwrites `totalEndRemainingAllocation = totalRemainingAllocation` any time `block.timestamp >= periodsEndTime[4]`. Because `totalRemainingAllocation` shrinks every time a user claims, calling this function again after some users have already claimed lowers the bonus denominator used by `getBonusAmount()`, while `totalBonus` (the numerator) is never reduced correspondingly, allowing later claimers to receive inflated bonus payouts that were not backed by the actual forfeited-token pool.

### Finding Description
The intended design is that once all periods vest (`periodsEndTime[4]`), `totalEndRemainingAllocation` is snapshotted exactly once, at the moment the last vesting period begins, representing the total allocation of all users who have not yet claimed. Each late claimer's bonus share is computed as:
```
bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation
``` [1](#0-0) 
If the denominator is fixed exactly once (before any of the eligible late-claimers claim), the sum of all bonus shares equals exactly `totalBonus`.

However, `updateEndRemainingAllocation()` has no guard preventing repeated calls:
```
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4]) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
``` [2](#0-1) 
It is invoked automatically inside `claim()` only when `totalEndRemainingAllocation == 0`:
```
function claim() external {
    if (totalEndRemainingAllocation == 0) {
        updateEndRemainingAllocation();
    }
    ...
}
``` [3](#0-2) 
But since the function is `public`, any unprivileged address can call it directly at any time after `periodsEndTime[4]`, bypassing the `== 0` guard entirely. Each such call re-snapshots the denominator to the then-current (smaller) `totalRemainingAllocation`, since `totalRemainingAllocation` only decreases as users claim (`register()`/`claim()` both mutate it, and `claim()` decrements it on every payout: `totalRemainingAllocation -= userAllocation;`). 

Meanwhile `totalBonus` is not decremented when bonus is paid out - it's only ever incremented from early-claimer forfeitures. So each re-snapshot to a smaller denominator inflates the bonus for all subsequent claimants, causing the sum of bonus payouts across all late-claimers to exceed `totalBonus`, and consequently exceed `aidropToken.balanceOf(address(this))`'s allocated backing. The only safety check in `claim()` is a per-transaction balance check (`claimableAmount > aidropToken.balanceOf(address(this))`), which does not prevent this cumulative over-payment across multiple transactions - it only prevents a single claim from exceeding the currently remaining balance, and by then earlier over-paid claimants have already drained tokens that should have remained for others.

### Impact Explanation
A user (or anyone acting on their behalf) can, immediately before their own `claim()`, call `updateEndRemainingAllocation()` to shrink the denominator down to their own remaining pool, inflating their bonus disproportionately relative to `totalBonus`. This directly steals value that should have gone to other pro-rata bonus recipients and can drain the contract's token balance faster than intended, leaving later, legitimate claimants unable to claim their full (or any) allocation - a direct theft of user funds / protocol insolvency for the airdrop pool, matching the "Direct theft of user funds" impact class.

### Likelihood Explanation
This requires no privileged role - any EOA can call the public `updateEndRemainingAllocation()` function directly, and any claimant can front-run their own `claim()` call with it (or bundle both calls in one transaction). The only precondition is that `block.timestamp >= periodsEndTime[4]` and that some users have already claimed (reducing `totalRemainingAllocation`) before the attacker's re-snapshot, which is expected as the natural progression of the airdrop's claim period. No capital is required beyond gas, and the attack is trivially repeatable by any of the remaining claimants.

### Recommendation
Add a one-shot guard so `totalEndRemainingAllocation` can only be set once (e.g., `if (totalEndRemainingAllocation == 0 && block.timestamp >= periodsEndTime[4])`), and/or restrict `updateEndRemainingAllocation()` to be called only internally from `claim()`'s existing `== 0` check (remove `public` visibility / make it `internal`), so the denominator snapshot cannot be redone after the first legitimate claim.

### Proof of Concept
Foundry test plan:
1. Deploy `Airdrop` with `startTime = now + 1`, deploy mock ERC20, mint enough tokens to the airdrop contract to cover total allocations + expected bonus.
2. `register()` three users (Alice, Bob, Carol) with allocation 100 each; also register/simulate an early claimer whose forfeiture builds `totalBonus` (or directly manipulate via early claim before period 4 to have `totalBonus = 300`).
3. Warp to `periodsEndTime[4]`.
4. Alice calls `claim()` — this triggers `updateEndRemainingAllocation()` internally (since `totalEndRemainingAllocation == 0`), snapshotting `totalEndRemainingAllocation = 300` (Alice+Bob+Carol unclaimed). Assert Alice receives `100 + 100 = 200`.
5. Attacker (any address, e.g., Bob himself) calls `updateEndRemainingAllocation()` directly. Assert `totalEndRemainingAllocation` drops to `200` (Bob+Carol only).
6. Bob calls `claim()`. Assert Bob receives `100 + (100*300/200) = 250` instead of the intended `200`.
7. Attacker calls `updateEndRemainingAllocation()` again, dropping denominator to `100`.
8. Carol calls `claim()`. Assert Carol receives `100 + (100*300/100) = 400`.
9. Assert total paid out (`200 + 250 + 400 = 850`) exceeds the intended total (`300` allocations + `300` totalBonus `= 600`), and/or assert `aidropToken.balanceOf(address(this))` is insufficient to pay remaining legitimate obligations, demonstrating `totalBonus` no longer reconciles with actual token backing.
