### Title
PedPoP performs ECDH, decryption, and blame-proof generation on attacker-supplied encrypted shares before verifying their proofs of possession - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to GHSA-g4cf-xj29-wqqr (expensive work performed on unvalidated attacker input before the request is rejected), `Encryption::decrypt` in PedPoP unconditionally performs an ECDH scalar multiplication, ChaCha20 decryption, and a full `DLEqProof::prove` for every `EncryptedMessage` it is handed — including messages whose Schnorr proof-of-possession (`pop`) is invalid. The `pop` is only *queued* into a `BatchVerifier`; the actual rejection happens later, after all per-message proving work has already been spent.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `KeyMachine::calculate_share` iterates every share message in the attacker-influenced `shares` map and calls `self.encryption.decrypt(...)` before any verification concludes [1](#0-0) .

Inside `Encryption::decrypt` (`crypto/dkg/pedpop/src/encryption.rs:469-501`), for each message the code:

1. Queues the `pop` Schnorr signature for batch verification — this does **not** verify it, it only schedules it (`msg.pop.batch_verify(...)`, line 479).
2. Performs `ecdh::<C>(&self.enc_key, msg.key)` — a variable-base scalar multiplication using the node's secret encryption key on an attacker-controlled point `msg.key` (line 487).
3. Runs `cipher(...).apply_keystream(...)` over the ciphertext (line 488).
4. Generates `DLEqProof::prove(...)` over `&self.enc_key` — multiple scalar multiplications plus `hash_to_F` — purely to construct a blame proof (lines 491-499).

Only after all of this does `calculate_share` run `batch.verify_with_vartime_blame()`, which is the first place the invalid `pop` is actually detected [2](#0-1) .

So a garbage `EncryptedMessage` — trivially constructible with `EncryptedMessage::read` (attacker-controlled `key`, `pop`, `msg` bytes, `encryption.rs:171-177`) — still costs the victim ~4–5 group scalar multiplications (ECDH + Schnorr queue weighting + `DLEqProof::prove`) plus transcript/`hash_to_F` work before being discarded. The `blame` path has the same shape: `decrypt_with_proof` runs a DLEq verify and an `n* t`-sized `multiexp_vartime` via `blame_internal` [3](#0-2) , and `AdditionalBlameMachine::blame` is explicitly documented as processing "the same blame statement multiple times" with no deduplication.

### Impact Explanation
An unprivileged party able to feed `EncryptedMessage` bytes into `calculate_share` (a reachable API per the DKG flow) forces the victim to burn expensive scalar-multiplication and proof-generation CPU on inputs that are trivially invalid — work that could have been rejected by verifying the `pop` signature first. The costs are additive per message and per retry of the DKG session, and the eager `DLEqProof::prove` (only ever needed if the sender is actually faulty) is generated for *every* message regardless of validity. Mirroring the advisory, the fix is identical in spirit: validate (verify the PoP) before executing the expensive operation (ECDH + blame-proof generation).

### Likelihood Explanation
Any party whose messages reach `calculate_share` or `blame` can submit malformed encrypted shares. The PoP failure is only discovered in batch verification *after* the proving work is done, so the per-message cost is paid unconditionally. Amplification per message is bounded (~a few scalar multiplications) rather than the unbounded scan of the original advisory, keeping this at Medium.

### Recommendation
In `Encryption::decrypt` (`crypto/dkg/pedpop/src/encryption.rs:469`), verify `msg.pop` synchronously (or pre-verify cheaply) before computing `ecdh`, applying the cipher, and calling `DLEqProof::prove`. If ordering constraints require batching, at minimum generate the `EncryptionKeyProof` lazily — only after the batch fails and a specific `BatchId::Share(l)` needs blaming — rather than eagerly for every message. Similarly, deduplicate/limit `AdditionalBlameMachine::blame` invocations and validate `sender`/`recipient` membership before the `multiexp_vartime` in `blame_internal`.

### Proof of Concept
1. Participant `l` runs `KeyGenMachine::generate_coefficients` normally to reach `KeyMachine`.
2. An attacker constructs an `EncryptedMessage` via `EncryptedMessage::read` with a random `key` point and a `pop` signature that will not verify (e.g., random `R`/`s` bytes, or a `pop` bound to a different `from` participant — note `pop_challenge` binds `sender`, so honest-looking bytes for the wrong sender are enough).
3. Attacker inserts this message into the `shares` map and triggers `calculate_share`.
4. Observe (via instrumentation/benchmark) that `ecdh` and `DLEqProof::prove` are executed for the attacker's message *before* `batch.verify_with_vartime_blame()` returns `Err(InvalidShare)`, confirming the expensive work is performed prior to rejection of input that a cheap `pop` check would have discarded.
