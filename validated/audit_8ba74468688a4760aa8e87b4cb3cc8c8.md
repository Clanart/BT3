### Title
Unbounded recursive AccountKey RLP decoding enables stack-exhaustion DoS via crafted `TxTypeAccountUpdate`/fee-delegated account-update transactions - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
The `AccountKeyRoleBased.DecodeRLP` method decodes its role-key list by recursively invoking `rlp.DecodeBytes` on each embedded key blob through `AccountKeySerializer.DecodeRLP`, with no bound on nesting depth. Because `AccountKeySerializer.DecodeRLP` can itself instantiate another `AccountKeyRoleBased` and recurse into the same decoding path, an attacker can submit a transaction (`TxTypeAccountUpdate` or its fee-delegated variants) whose account-key field is a deeply self-nested RLP structure. Decoding this structure drives unbounded Go call-stack recursion purely during deserialization — before the "no nested composite key" semantic check (`IsCompositeType`) is ever reached — mirroring the ASN.1 BER deep-recursion stack-exhaustion pattern of CVE-2016-4421.

### Finding Description
The decode chain is:
- `TxInternalDataAccountUpdate.DecodeRLP` → `fromSerializable` → `rlp.DecodeBytes(serialized.Key, serializer)` where `serializer` is an `accountkey.AccountKeySerializer`. [1](#0-0) 
- `AccountKeySerializer.DecodeRLP` reads the key type, calls `NewAccountKey(keyType)`, and decodes into it. If `keyType == AccountKeyTypeRoleBased`, `serializer.key` becomes an `*AccountKeyRoleBased`. [2](#0-1) [3](#0-2) 
- `AccountKeyRoleBased.DecodeRLP` decodes a list of byte blobs and, for **each** blob, calls `rlp.DecodeBytes(b, &serializer)` where `serializer` is again an `AccountKeySerializer` — re-entering the same decode chain. [4](#0-3) 

Because each inner blob can itself encode `keyType=RoleBased` followed by more nested blobs, this chain recurses arbitrarily deep with no depth counter anywhere in the RLP package (`rlp/decode.go` only tracks list-size limits via `Stream.stack`, not recursion depth) or in `AccountKeySerializer`/`AccountKeyRoleBased`. [5](#0-4) 

The only defense against nested `RoleBased` keys — `IsCompositeType()` rejection in `CheckInstallable`/`CheckUpdatable` — runs strictly *after* the full RLP structure has already been successfully decoded, so it cannot stop the stack growth that occurs during decoding itself. [6](#0-5) 

This decode path is reachable from a completely unprivileged actor: anyone can submit a raw `TxTypeAccountUpdate` (or `TxTypeFeeDelegatedAccountUpdate`/`...WithRatio`) transaction via public RPC (`eth_sendRawTransaction`) or p2p tx propagation, and every node that receives and RLP-decodes the transaction (txpool admission, block validation) will recurse through this chain.

### Impact Explanation
A deeply nested `AccountKeyRoleBased` payload causes the decoding goroutine to consume stack proportional to nesting depth. Because each RLP nesting level requires only a few bytes of overhead (list header + type tag), an attacker can encode many thousands of nesting levels within a single transaction well under typical transaction size limits, driving Go's goroutine stack to its growth limit and crashing the process (`runtime: goroutine stack exceeds ... - fatal error: stack overflow`). Since the same crafted transaction is processed independently by every full node that receives it (via RPC submission and p2p tx propagation) and by every node validating a block containing it, this is a broadly reachable denial-of-service vector against Kaia nodes, matching the availability impact of CVE-2016-4421.

### Likelihood Explanation
Likelihood is high for an attacker: constructing the nested RLP structure requires no special privileges, no valid signature is even needed to trigger the crash during initial RLP decoding of the raw transaction bytes (decoding happens before signature verification), and the attack can be delivered through the standard public RPC transaction submission endpoint.

### Recommendation
Introduce a nesting-depth limit when decoding `AccountKeySerializer`/`AccountKeyRoleBased` (and any other recursive `AccountKey`/RLP `Decoder` types), e.g., by passing an explicit depth counter through `DecodeRLP` and rejecting decode once a small maximum (matching Kaia's disallowed-nested-composite-key policy, effectively depth 1) is exceeded — before recursing into `rlp.DecodeBytes` on inner blobs. Alternatively, add a general recursion-depth guard to the `rlp` package's `Stream`/`Decoder` invocation path so any custom `Decoder` implementation cannot be abused for unbounded recursion.

### Proof of Concept
1. Build an `AccountKeySerializer`-encoded blob for `AccountKeyTypeRoleBased` whose single "role key" element is itself another RLP-encoded `AccountKeyTypeRoleBased` blob (recursively), repeated N times (N in the thousands), using the same encoding logic as `AccountKeyRoleBased.EncodeRLP`. [7](#0-6) 
2. Place this nested blob as the `Key` field of a `TxTypeAccountUpdate` transaction and RLP-encode the transaction as done in `toSerializable`/`SerializeForSignToBytes`. [8](#0-7) 
3. Submit the raw transaction bytes via `eth_sendRawTransaction` to a Kaia node, or inject via p2p tx propagation.
4. Observe that `TxInternalDataAccountUpdate.DecodeRLP` → `fromSerializable` → `rlp.DecodeBytes` recurses through `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` N times, exhausting the goroutine stack and crashing the node before any `CheckInstallable`/`IsCompositeType` nested-key rejection can occur.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil

// Stream can be used for piecemeal decoding of an input stream. This
// is useful if the input is very large or if the decoding rules for a
// type depend on the input structure. Stream does not keep an
// internal buffer. After decoding a value, the input reader will be
// positioned just before the type information for the next value.
//
// When decoding a list and the input position reaches the declared
// length of the list, all operations will return error EOL.
// The end of the list must be acknowledged using ListEnd to continue
// reading the enclosing list.
//
// Stream is not safe for concurrent use.
type Stream struct {
	r ByteReader

	remaining uint64   // number of bytes remaining to be read from r
	size      uint64   // size of value ahead
	kinderr   error    // error from last readKind
	stack     []uint64 // list sizes
	uintbuf   [32]byte // auxiliary buffer for integer decoding
	kind      Kind     // kind of value ahead
	byteval   byte     // value of single byte in type tag
	limited   bool     // true if input limit is in effect
}
