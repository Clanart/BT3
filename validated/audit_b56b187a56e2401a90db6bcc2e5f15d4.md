## Analysis

The external report's core broken invariant: an oracle price check that validates "not stale" and "not non-positive" but never checks whether the returned value is a `minAnswer`/`maxAnswer`-clamped floor/ceiling rather than the true market price, allowing a flash-crashed (or de-pegged) asset to be valued at a stale, favorable price.

Hyperbridge's `SimplexPaymaster` contains the exact same broken invariant in its Chainlink price-fetching helper. [1](#0-0) 

`_getOraclePrice` only reverts on `answer <= 0` or staleness — it never compares `answer` against the feed's `minAnswer`/`maxAnswer`. This function backs both the per-UserOp pricing path (`_tokenPrice` → `_fetchDetails`, reachable by any unprivileged ERC-4337 sender through the public `paymasterData` mode-1/mode-0 flow) and the treasury-only `swapAndDeposit` recycling path. [2](#0-1) [3](#0-2) 

The contract's own comment acknowledges oracle risk but only mitigates it via an off-chain convention ("keep allowances and permit amounts small"), not an on-chain check — `_executePermit` parses and executes whatever `permitAmount` is encoded in `paymasterData` with no on-chain cap, and `APPROVE` mode (mode `0x01`) trusts whatever pre-existing allowance the caller has already granted, with no size limit enforced by the contract itself. [4](#0-3) [5](#0-4) 

Token registration is governance-controlled (`RegisterToken`), but governance can legitimately register any ERC-20 with a valid Chainlink feed (e.g., a stablecoin) — such feeds commonly retain `minAnswer`/`maxAnswer` bounds, and a de-peg or flash-crash below/above those bounds causes `latestRoundData()` to keep returning the clamped bound value while `updatedAt` continues to advance (the aggregator still posts fresh rounds, it just reports the floor/ceiling), so neither of `_getOraclePrice`'s two checks catches it.

### Title
`SimplexPaymaster._getOraclePrice` doesn't validate against Chainlink minAnswer/maxAnswer, allowing mispriced gas payment during a token de-peg/crash - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` treats any `answer > 0` from a fresh Chainlink round as valid, without checking it against the aggregator's `minAnswer`/`maxAnswer` bounds. If a registered gas token's price feed clamps at its floor during a crash/de-peg, `_tokenPrice` computes a gas cost using the stale floor price instead of the real (near-zero) market price, letting an attacker pay for real native-asset gas with a token acquired for a fraction of the nominal price the paymaster assumes.

### Finding Description
`_getOraclePrice` (`evm/src/utils/SimplexPaymaster.sol:428-442`) fetches `latestRoundData()` and only guards against `answer <= 0` and staleness (`block.timestamp - updatedAt > maxOracleAge`). It never checks `answer` against the feed's configured `minAnswer`/`maxAnswer`. This is used by `_tokenPrice` (line 419-424), which both the native-asset feed and the token feed pass through, and which backs `_fetchDetails` (line 374-393) — the pricing function invoked on every ERC-4337 UserOp that uses this paymaster, a fully public entrypoint reachable by any unprivileged account.

When a registered token's USD feed hits its `minAnswer` floor during a market crash/de-peg, the aggregator continues posting fresh rounds at the clamped floor value rather than the true collapsed price. `_getOraclePrice` passes this stale-but-fresh clamped value straight through, so `tokenUsd` in `_tokenPrice` is computed as far above the real market value of the token.

### Impact Explanation
`tokenPrice = (nativeUsd * 10^tokenDecimals * (10000+markupBps)) / (tokenUsd * 10000)` is inversely proportional to `tokenUsd`. An inflated (clamped) `tokenUsd` produces an under-priced `tokenPrice` (fewer token units charged per unit of gas). An attacker can acquire the de-pegged/crashed token cheaply on the open market at its real price, then use it via the paymaster (mode `0x01` approve, or mode `0x00` permit) to pay for real native-asset gas priced by the protocol as if the token were still worth its pre-crash/floor value. This drains real value from the paymaster's EntryPoint deposit (funded by the treasury) for tokens worth a fraction of what the contract credits them as — a direct loss of funds reachable by an unprivileged attacker with no relayer, prover, or governance compromise required.

### Likelihood Explanation
Governance can register any ERC-20 with a Chainlink feed as a gas token (`RegisterToken`), and many production Chainlink feeds (particularly for less liquid or de-pegging-prone assets) retain `minAnswer`/`maxAnswer` bounds. The docstring's own mitigation ("small permit/allowance amounts") is an off-chain convention that the contract does not enforce on-chain (`_executePermit` has no amount cap; `APPROVE` mode trusts arbitrary pre-existing allowances), so the described bound on exposure is not actually guaranteed by the code.

### Recommendation
In `_getOraclePrice`, fetch and cache each feed's `minAnswer`/`maxAnswer` (via `AggregatorV3Interface`/`aggregator()` extension or a governance-configured bound) and revert if `answer <= minAnswer || answer >= maxAnswer`, mirroring the staleness/non-positive checks already in place. Alternatively, enforce a hard on-chain cap on `permitAmount`/effective allowance usable per UserOp so oracle mispricing cannot be leveraged beyond a bounded exposure, consistent with the intended security model described in the contract's own comments.

### Proof of Concept
1. Governance registers a stablecoin `X` with Chainlink feed `F` (feed `F` has `minAnswer = $0.90`) via `RegisterToken`.
2. `X` de-pegs on secondary markets to $0.05 due to an exploit/run; `F` continues posting fresh rounds but clamps `answer` at `$0.90` (its floor) — `updatedAt` stays within `maxOracleAge`.
3. Attacker buys a large amount of `X` on the open market at ~$0.05 each.
4. Attacker submits a UserOp using `X` as the paymaster gas token (`paymasterData` mode `0x01`, with a pre-existing allowance, or mode `0x00` with a permit signature for a large `permitAmount`).
5. `_fetchDetails` → `_tokenPrice` → `_getOraclePrice(cfg.tokenOracle, ...)` returns `$0.90`-equivalent pricing instead of the real `$0.05`, so the computed `tokenPrice` under-charges `X` by ~18x relative to its real value.
6. `PaymasterERC20` pulls `X` from the attacker at the under-charged amount and the EntryPoint pays out real native-asset gas at full value, letting the attacker extract real gas value while paying with tokens worth a fraction of the assumed price — draining paymaster-funded native asset for near-worthless tokens.

```text
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }
```

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
