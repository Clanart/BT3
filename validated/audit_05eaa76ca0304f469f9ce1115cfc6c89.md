### Title
Hardcoded `DUST` constant rejects/accepts outputs based on 546 sats regardless of output script type - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` applies a single `pub const DUST: u64 = 546` to every payment and change output, regardless of the `script_pubkey` used. Bitcoin's dust policy is a function of the output's serialized size (and the input required to spend it): `dust = 3 * minRelayFee * (input_size + output_size) / 1000`. 546 is only correct for P2PKH-sized outputs. Outputs whose scripts are larger (e.g., bare multisig, large custom scripts, or any non-SegWit pattern Serai doesn't special-case) have a higher dust floor, and SegWit outputs have a lower one. The code comment itself acknowledges the constant is not differentiated ("This doesn't bother with delineation"), mirroring the Derby issue's deploy-time constants that only hold for one asset type. [1](#0-0) 

### Finding Description
In `SignableTransaction::new`, every payment amount is validated as `*amount < DUST` and rejected only below 546 sats, and the change output is only appended `if value >= DUST` — both checks use the single constant for arbitrary `ScriptBuf` script_pubkeys supplied by the caller. [2](#0-1) [3](#0-2) 

Because `payments` is `&[(ScriptBuf, u64)]` and `change` is an arbitrary `ScriptBuf`, nothing constrains the output type. A payment of 546–800 sats to an output whose actual dust threshold is above the paid amount (e.g., a large bare script, or any output whose spend input is expensive) passes the check but produces a transaction that default Bitcoin Core mempool policy will not relay (`dust` rejection in `CTxMemPool`). Similarly, a change output between 546 sats and the script-dependent floor causes the *entire* transaction to be non-standard. Unlike the Derby `minimumPull`/`minimumAmount` constants that were at least adjustable by `dao`, `DUST` here is a compile-time constant with no way to override.

### Impact Explanation
The threshold FROST signature produced by `TransactionSignMachine::sign` / `TransactionSignatureMachine::complete` commits to this exact transaction via `taproot_key_spend_signature_hash` with `Prevouts::All` [4](#0-3) , so the completed, fully-signed transaction cannot be rebroadcast or amended. Funds sent to a sub-dust output are burned (unspendable, unrelayable output), and a sub-dust change output invalidates the whole transaction, leaving all input funds locked until a new signing round is convened — a particularly bad failure mode for a threshold wallet where each re-sign requires coordinating all signers.

### Likelihood Explanation
An unprivileged party only needs to request a payment to a script whose dust floor exceeds 546 sats (e.g., a bare multisig or oversized `script_pubkey`), or induce a change output in the affected range, to trigger the failure. The affected range is narrow per-output, and inputs remain spendable via a corrected re-sign, which keeps this at Medium rather than High.

### Recommendation
Compute the dust threshold per output rather than from a constant: use `script_pubkey.dust_value()` (or replicate `GetDustThreshold` from Bitcoin Core policy: `3 * 1000 * (input_size + output_serialized_size) / 1000`) for each payment and for the change output, sizing the input term for the actual spend type (Taproot key-spend for change, the target script type for payments).

### Proof of Concept
1. Call `SignableTransaction::new` with `payments = [(large_script_pubkey, 600)]` where `large_script_pubkey` is, e.g., a bare 2-of-3 multisig or any script pushing the dust floor above ~800 sats, `change: None`, adequate inputs, and a valid `fee_per_vbyte`.
2. The check `*amount < DUST` passes since `600 >= 546`; the transaction is built and returned.
3. `multisig(...)`, `preprocess`, `sign`, `complete` all succeed, producing a fully-signed transaction.
4. Broadcasting to a default-policy node fails with a `dust` policy rejection; the output is also not economically spendable, so the 600 sats are effectively destroyed and the payment must be re-created and re-signed by the whole threshold.
