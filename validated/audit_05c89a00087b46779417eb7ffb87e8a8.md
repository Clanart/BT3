### Title
Scanner Reports Dust Outputs as Received Balance That Cannot Be Economically Spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Pendle oracle bug class is "the system values an asset at its nominal face value while the amount actually realizable on redemption is lower." The direct analog in `bitcoin-serai` is the receive path: `Scanner::scan_transaction` returns a `ReceivedOutput` for *any* output paying a registered `script_pubkey`, regardless of `value`, and `ReceivedOutput::value()` reports the full face amount. An unprivileged sender can pay a sub-`DUST` (or otherwise unprofitable-to-spend) output to a Serai P2TR address; it is reported as received funds, yet spending it costs more in fees than it is worth — or is outright rejected by relay policy — so the funds are reported received but are not spendable.

### Finding Description
`Scanner::scan_transaction` matches purely on `output.script_pubkey` and pushes a `ReceivedOutput` with no lower bound on `output.value` (networks/bitcoin/src/wallet/mod.rs:199-214). The only dust-related check in the wallet is in `SignableTransaction::new`, which rejects *payments* below `DUST = 546` (networks/bitcoin/src/wallet/send.rs:165-169), but performs no equivalent check on *inputs*: `input_sat` sums every `ReceivedOutput`'s face value (send.rs:175) and each input is unconditionally added to the transaction (send.rs:177-185).

Two concrete consequences of the missing inbound check, both reachable via a public Bitcoin transaction an attacker sends to a registered address:

1. **Unspendable-value inflation**: an output of `value < DUST` matched by the scanner is a `ReceivedOutput` reporting positive `value()` that can never be relayed/spent profitably — a single key-spend input adds ~58 vB of weight, so at any viable `fee_per_vbyte` the marginal `needed_fee` contribution of that input exceeds its value.

2. **Fee-drainage on inclusion**: because `SignableTransaction::new` never verifies `input.value >= marginal_fee(input)`, dust inputs can be swept into a transaction where they silently turn into additional fee, and can push a borderline transaction into `NotEnoughFunds` — i.e., the reported balance cannot be realized even when nominally sufficient.

The over-statement is structural, exactly like the oracle's `TWAP × exchangeRate()` ignoring redemption loss: face value is reported while the realizable value is lower (zero, for sub-dust outputs).

### Impact Explanation
Any downstream consumer crediting deposits from `scan_transaction`/`ReceivedOutput::value()` credits unspendable satoshis as real balance. An attacker can cheaply mint phantom "received" funds and/or force the wallet to burn real funds as extra fee when the dust inputs are later consumed — "funds reported received that are not spendable," the accepted impact class for this analog. Per-instance magnitude is bounded (sub-dust), but the cost to the attacker is the same sub-dust amount plus one transaction, and it is repeatable across many outputs.

### Likelihood Explanation
Requires only that the attacker know a registered `script_pubkey` (derivable from the public group key/offsets) and broadcast a transaction paying it a dust output — fully public, unprivileged input. Whether it becomes exploitable depends on whether the integrating consumer applies its own dust filter before crediting (the library itself provides none and documents none; only `scan_block`'s coinbase-maturity caveat is documented, in mod.rs:216-220).

### Recommendation
Apply a lower bound on the receive side, mirroring the existing outbound check: either skip outputs with `value < DUST` in `Scanner::scan_transaction`, or have `SignableTransaction::new` reject/ignore inputs whose `value` is below their marginal fee cost (`fee_per_vbyte` × per-input vbytes) so reported balance equals realizable balance.

### Proof of Concept
```rust
// key = group key; scanner = Scanner::new(key)
let dust_tx = Transaction {
  output: vec![TxOut {
    value: Amount::from_sat(1), // below DUST
    script_pubkey: p2tr_script_buf(key).unwrap(),
  }],
  .. // attacker-funded input
};
let outputs = scanner.scan_transaction(&dust_tx);
assert_eq!(outputs.len(), 1);
assert_eq!(outputs[0].value(), 1); // reported as received balance
// outputs[0] can never be spent: input weight fee >> 1 sat,
// and SignableTransaction::new will not reject it as an input.
```
