## Title
Stale line-selection reused against a re-fetched, attacker-influenceable working-directory diff silently corrupts partial commits — (File: `app/src/lib/git/apply.ts`)

## Summary
When a user selects only some lines/hunks of a modified file for a commit, GitHub Desktop stores that selection as a set of *absolute line indices* (`DiffSelection`) computed against the diff that was rendered in the UI at selection time. When the commit is actually staged, `applyPatchToIndex` does **not** reuse that diff — it independently re-fetches a brand-new diff from disk/git and blindly re-applies the old index-based selection to it. If the working-directory content backing that diff changes between "user selects lines" and "Desktop stages the commit" (which can be driven by attacker-controlled content via git clean/smudge filters such as Git LFS, whose smudge process fetches blob content from a remote server declared in a cloned repository's `.lfsconfig`/`.gitattributes`), the line indices no longer correspond to the same logical content, and the user silently commits/pushes different content than what they reviewed and selected.

## Finding Description
The reserve-ratio bug in the external report is fundamentally about reusing a value ("balance") computed under one set of assumptions (available liquidity) in a calculation performed under a different, incompatible context (some of that balance is inaccessible "portfolio"), without revalidating the assumption — silently breaking a safety guarantee.

The same broken-invariant pattern exists in Desktop's partial-commit path:

1. The UI computes and stores a `DiffSelection` (a set of "diverging" absolute line indices) against a specific diff snapshot rendered for the user: [1](#0-0) .

2. Desktop is aware that a diff snapshot can go stale relative to the selection, but only handles this for the *currently rendered* file in the Changes tab, by clearing selectable lines that no longer exist: [2](#0-1) 

3. However, when the commit actually executes, `_commitIncludedChanges` just takes whatever `selection` is cached in `repositoryStateCache` for each file — regardless of whether that selection was validated against the file's current on-disk diff: [3](#0-2) 

4. That selection eventually reaches `stageFiles`, which routes any partially-selected file to `applyPatchToIndex`: [4](#0-3) 

5. Critically, `applyPatchToIndex` re-fetches the working directory diff **fresh**, from the file's *current* state, right before staging — it does not reuse the diff the selection was originally validated against, nor does it re-validate the selection against this fresh diff: [5](#0-4) 

6. `formatPatch` then walks this freshly-fetched diff and decides which lines to include purely based on `file.selection.isSelected(absoluteIndex)` — an index into hunks that may have completely different content/positions than the hunks that existed when the selection was made: [6](#0-5) 

Because `DiffSelection` only tracks integer line indices (not content hashes or stable anchors), if hunks shift — because the underlying blob smudge output changed, an autocrlf/line-ending re-normalization occurred, or any other external mutation touched the file — the "included" indices silently point to different content than what the user visually reviewed and clicked to include. There is no check anywhere in `applyPatchToIndex`/`stageFiles`/`_commitIncludedChanges` that the diff used to build the selection matches the diff used to build the patch.

The attacker-controlled entry point that can trigger such a content change between the two diff computations is a cloned/fetched repository that uses a git `clean`/`smudge` filter whose driver is externally invoked and non-deterministic across invocations — most concretely Git LFS, which Desktop natively supports (`app/src/lib/git/lfs.ts`, `isTrackedByLFS`, `isUsingLFS`) and which fetches blob bytes from a server URL that can be supplied by the cloned repository itself (via `.lfsconfig`). A malicious/compromised LFS server can serve different content for the same pointer across two smudge invocations (one performed while the diff pane is rendered, one performed later by `getWorkingDirectoryDiff` inside `applyPatchToIndex`), causing the selection built against the first render to be silently reinterpreted against the second.

## Impact Explanation
This breaks the same invariant class as the external report: a value computed and displayed to the user (which lines will be committed) is silently reused in a context where it no longer holds true (which lines actually get staged), resulting in **silent corruption of what the user commits and subsequently pushes**. A user could unknowingly commit/push attacker-influenced content that was never shown to them in the diff review UI, undermining the core trust guarantee of a partial/interactive commit tool: "what you selected is what you get."

## Likelihood Explanation
The precondition (working tree content diverging between two `git diff`/status reads of the same path) is a well-known and previously-encountered class of bug in Desktop's own code — the developers explicitly commented on and partially mitigated this exact race for the *live diff pane* (`app/src/lib/stores/app-store.ts:3478-3497`), but that mitigation is not applied on the staging path in `app/src/lib/git/apply.ts`. Reaching it does not require local/physical access or leaked credentials — an attacker only needs the victim to clone/open a crafted repository that uses a filter/LFS pointer under attacker control, a scenario squarely within "attacker controls a cloned/fetched repository."

## Recommendation
- Persist (or content-hash) the exact diff/hunk state that a `DiffSelection` was validated against, and re-validate/re-map that selection against the diff fetched at staging time in `applyPatchToIndex` before calling `formatPatch`, failing safe (e.g., re-prompting the user or aborting the partial commit) if the diffs disagree.
- Alternatively, reuse the already-rendered diff (the one the user interacted with) to build the patch at commit time instead of calling `getWorkingDirectoryDiff` again in `app/src/lib/git/apply.ts`, and only fall back to a fresh diff with explicit re-validation if none is cached.
- Add a warning banner (similar to the existing "hidden changes" warning in `app/src/ui/changes/filter-changes-logic.ts`) whenever a file's on-disk diff changes between selection and commit for files with `DiffSelectionType.Partial`.

## Proof of Concept
1. Configure (or have pre-installed) a smudge filter whose output is not idempotent across invocations — e.g., Git LFS pointing at a malicious/compromised LFS server via a repository-supplied `.lfsconfig`, or any custom `clean`/`smudge` filter that embeds externally-fetched or time-varying content.
2. Clone the malicious repository in GitHub Desktop and modify the tracked file so it shows a multi-hunk diff.
3. In the Changes pane, select only specific lines/hunks to include in the commit (leaving other hunks unselected), which builds a `DiffSelection` against the diff rendered at that moment (`app/src/lib/models/diff/diff-selection.ts`).
4. Before pressing "Commit," have the malicious smudge/LFS server return different content for the same blob (simulating a race or deliberate timing), so that the next `getWorkingDirectoryDiff` call produces hunks at shifted line positions.
5. Commit. `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff and applies the stale `DiffSelection` indices to it via `formatPatch`, staging different content/lines than what was visually selected in step 3 — with no warning shown to the user.
