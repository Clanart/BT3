### Title
`smartConvert`'s `_minRec == _amountIn` check in `SmartWomConvert.sol` causes `WombatStaking._sendRewards` to revert on any partial buyback, blocking `deposit`, `depositLP`, `withdraw` and `harvest` - (File: wombat/WombatStaking.sol, wombat/SmartWomConvert.sol)

### Summary
`WombatStaking._toMasterWomAndSendReward` is invoked from `deposit`, `depositLP`, `withdraw` and `harvest` for every pool [1](#0-0) , and it unconditionally routes any harvested WOM fee through `_sendRewards`, which calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)` whenever the `isMWOM` fee is active [2](#0-1) . `smartConvert` sets `_minRec` equal to the full `_amountIn`, even though part of that amount is routed through an AMM swap that will lose value to slippage/fees whenever `mWomToWom < buybackThreshold` [3](#0-2) , so `_convertFor` reverts with `MinRecNotMatch` [4](#0-3) , bubbling up and reverting the entire deposit/withdraw/harvest transaction for that pool.

### Finding Description
The reachable call chain is: `WombatPoolHelper`/`WombatPoolHelperV2`/`AnkrBNBPoolHelper` (all unprivileged, forwarding attacker-supplied `_amount`, `_minimumLiquidity`, `_for`) → `WombatStaking.deposit`/`depositLP`/`withdraw` → `_toMasterWomAndSendReward` → `_sendRewards` → `SmartWomConvert.smartConvert` [5](#0-4) [6](#0-5) .

Inside `smartConvert`, when the WOM/mWOM Wombat pool ratio (`currentRatio()`, itself a spot-price read via `IWombatRouter.getAmountOut`) drops below `buybackThreshold`, a portion of the fee amount is routed to a real AMM swap instead of a 1:1 `mWom.deposit`, and the function still demands `convertAmount + amountRec >= _amountIn` as `_minRec` [7](#0-6) . Because AMM swaps always incur some slippage/fee, `amountRec` will normally be strictly less than the swapped-in amount, so the aggregate output is virtually guaranteed to fall short of `_minRec`, triggering `revert MinRecNotMatch()` in `_convertFor` [8](#0-7) . An attacker can deliberately widen this gap by swapping in the WOM/mWOM pool (pushing it further off peg and increasing the price impact experienced by the buyback swap) in the same transaction (or by front-running/sandwiching a target deposit/withdraw), deterministically forcing the revert.

Because `_sendRewards` is called unconditionally for any pool with `isMWOM` fee active whenever `womRewards > 0` (i.e., pending WOM emissions exist from `MasterWombat`), this DoS affects `deposit`, `depositLP`, `withdraw` (`_onlyPoolHelper`/`_onlyActivePoolHelper`-gated but reachable by any user through the pool helper) and `harvest` for that pool. None of the existing guards (`nonReentrant`, `whenNotPaused`, `_onlyActivePoolHelper`, `_onlyPoolHelper`) prevent this because they only gate caller identity/pause state, not the internal revert from the converter.

### Impact Explanation
Reverting `deposit`/`depositLP`/`withdraw` for the affected pool freezes principal for all users of that pool as long as the attacker (or natural market conditions) keeps the WOM/mWOM ratio below `buybackThreshold` with sufficient price impact on the buyback leg. This matches "Temporary freezing of funds for at least 24 hours" if the attacker (or persistent market divergence) sustains the condition, since the only recovery paths are owner intervention (`setPoolRewardFeeFree`, `setSmartConvert(address(0))`, or removing the `isMWOM` fee) or the pool ratio naturally recovering above threshold with low enough slippage to satisfy `_minRec`.

### Likelihood Explanation
- Preconditions: `smartWomConverter` must be set on `WombatStaking`, the `isMWOM` fee must be active for the target pool, and there must be pending WOM rewards to harvest (normal operating condition once staking accrues emissions) [9](#0-8) .
- The bug is triggerable even without deliberate manipulation once `mWomToWom < buybackThreshold` naturally, since any AMM swap will have some cost; deliberate manipulation (swapping in the WOM/mWOM pool, which is a normal, externally-controllable Wombat pool) only makes the failure deterministic and can be timed to specific transactions (front-run/sandwich).
- Capital requirement scales with the depth of the WOM/mWOM Wombat pool; a thin pool makes this cheap and repeatable every block, sufficient to sustain a >24h freeze.
- No privileged role is required; the attacker only needs to be able to swap in the public Wombat WOM/mWOM pool and call the public pool-helper `deposit`/`withdraw` functions (or simply wait for a victim's transaction and front-run it).

### Recommendation
Do not set `_minRec` to the raw `_amountIn` in `smartConvert`. Instead, compute an expected minimum output that accounts for the swap leg's realistic slippage (e.g., derive it from `estimateTotalConversion` with an acceptable slippage tolerance, or make `_minRec` a caller-supplied/configurable parameter rather than hard-equal to `_amountIn`). Additionally, consider making `_sendRewards`'s call into `smartConvert` fault-tolerant (e.g., wrap in a try/catch and fall back to the plain `mWom.deposit` 1:1 path, mirroring the `else` branch already present) so that a reverting converter cannot block the entire deposit/withdraw/harvest flow.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy mocked `MasterWombat` that reports nonzero pending WOM rewards for a given pool/pid so that `_stakeToWombatMaster`/`withdraw` transfers WOM into `WombatStaking` on each call.
2. Deploy `WombatStaking` with a WOM/mWOM `SmartWomConvert` wired to a mocked `IWombatRouter`/`womMWomPool` whose `getAmountOut` can be parameterized to simulate an off-peg ratio and swap slippage.
3. Configure `WombatStaking.addFee(value, to, isMWOM=true, isAddress=false)` and `setSmartConvert(smartWomConverter)` for the target pool; ensure `isPoolFeeFree` is false.
4. Set the mock router so `currentRatio() < buybackThreshold` and the simulated `swapExactTokensForTokens` output is intentionally less than `amountToSwap` (simulate realistic AMM slippage/attacker-induced price impact).
5. Call `deposit` via the pool's `WombatPoolHelper` with valid `_amount`/`_minimumLiquidity`/`_for` as an unprivileged EOA.
6. Assert the transaction reverts with `MinRecNotMatch` (propagated from `SmartWomConvert._convertFor`), and that no LP/receipt tokens were minted and no `veWom`/`totalAccumulated` state changed — demonstrating deposits (and, in an analogous test, `withdraw`) are blocked purely due to the off-peg WOM/mWOM pool state, satisfying the "temporary freezing of funds" condition.
7. As a control, repeat with `mWomToWom >= buybackThreshold` (no swap leg) and confirm the deposit succeeds, isolating the bug to the swap/`_minRec` interaction.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
