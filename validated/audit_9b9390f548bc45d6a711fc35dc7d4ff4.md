### Title
Silent truncation of the app identifier in `AppKey::truncate_from` allows bandwidth allowance/allowlist key collisions - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
This is a direct local analog of the ConseilJS `encodeTransaction` bug: an unbounded, attacker-influenced byte string (there, the Michelson `entrypoint`; here, the destination `app`/module identifier used to key bandwidth allowances) is silently truncated to a fixed size instead of being length-validated. In `pallet-bandwidth`, `AppKey` is defined as `BoundedVec<u8, ConstU32<32>>` and every storage-key derivation goes through `AppKey::truncate_from(app.to_vec())`, which drops any bytes past index 31 without error. [1](#0-0) [2](#0-1) 

### Finding Description
`BandwidthGate::try_consume`, `Pallet::allowances`, `Pallet::remaining`, and the purchase-accept path (`on_accept`) all derive the storage key for `Allowance`/`Allowlist` the same way:
```rust
let key = AppKey::truncate_from(app.to_vec());
``` [3](#0-2) [4](#0-3) [2](#0-1) 

`truncate_from` is a lossy, non-failing conversion — for any input longer than 32 bytes it keeps only the first 32 bytes and discards the rest, with no error path and no length check anywhere before this call. The `app` value fed into `try_consume` comes from the destination module identity attached to an ISMP message being routed, which is attacker-supplied wire data (a `Vec<u8>` with no length ceiling enforced by this pallet). Because two different app identities that share the same 32-byte prefix collapse to the exact same `AppKey`, they also collapse to the same `Allowance` and `Allowlist` storage row.

This mirrors the ConseilJS flaw precisely: the wire format encodes/keys on a value with an implicit length limit (there, 1-byte length prefix truncating at 255; here, a 32-byte `BoundedVec` truncating silently) but the code never validates the untrusted input against that limit before using it, so distinct logical entities collide.

### Impact Explanation
Any two apps whose identifiers agree on the first 32 bytes (e.g., a legitimate 32-byte app id `A` and an attacker-crafted identifier `A || <arbitrary trailing bytes>`) will:
- Share the same prepaid `SubscriptionList` in `Allowance`, so the attacker's traffic drains the honest app's paid bandwidth allowance (`try_consume` debits the shared FIFO list) — theft/misappropriation of a prepaid resource that was purchased and paid for by someone else.
- Share the same `Allowlist` bypass flag, so if the legitimate 32-byte-prefixed app is allowlisted, the attacker's longer identifier inherits the free-pass and bypasses metering entirely.
- Corrupt the accounting/audit trail (`BandwidthConsumed`/`BandwidthCredited` events) since the emitted `AppKey` is the truncated, ambiguous value rather than the true identity, making it impossible to distinguish the real consumer from the colliding one.

This falls squarely under "bandwidth balances must move exactly once and only to the rightful beneficiary" from the impact gate: no malicious relayer, prover, or governance actor is required — an unprivileged app author choosing its own module identifier is sufficient.

### Likelihood Explanation
High. The identifier length is not bounded or validated anywhere upstream of `AppKey::truncate_from`; the pallet's own doc comment on `AppKey` even acknowledges it is "usually a 20-byte EVM address right-padded" but nothing enforces that assumption. Any module able to set its own module/app id when dispatching a message that flows through this gate can pick a colliding, over-length identifier at zero cost.

### Recommendation
- Short term: reject (return an error / `GateError`) instead of silently truncating when `app.len() > 32`, mirroring the `ByteVector<N>::decode` pattern already used elsewhere in this codebase that explicitly rejects any length that doesn't exactly equal `N` [5](#0-4) .
- Long term: validate all untrusted length-bearing fields before they are used to derive storage keys, and enforce/document a canonical fixed-length encoding for `app` (e.g., always exactly 20 or 32 bytes) at the point the identifier is produced, not only at the point it's consumed.

### Proof of Concept
1. App `X` (a real, funded app) has an on-chain identifier of exactly 32 bytes, e.g. `id_X = [0x01; 32]`.
2. `id_X` legitimately purchases bandwidth: `on_accept` computes `key = AppKey::truncate_from(id_X)` = `id_X`, and credits a subscription under `Allowance[(chain, id_X)]`.
3. An attacker controls a different app whose true identifier is longer than 32 bytes but shares the first 32 bytes with `id_X`, e.g. `id_attacker = [0x01; 32] ++ [0xff; 8]` (40 bytes).
4. When the attacker's messages are routed through `BandwidthGate::try_consume(source, id_attacker, bytes)`, the key is computed as `AppKey::truncate_from(id_attacker)` → `[0x01; 32]`, identical to `id_X`'s key.
5. `try_consume` drains from `Allowance[(chain, [0x01;32])]`, i.e., app `X`'s paid-for subscription, on behalf of the attacker's traffic, until it is exhausted — app `X` is left with insufficient bandwidth despite having paid for it, and the attacker never had to purchase anything.
