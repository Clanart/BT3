### Title
Stale-snapshot conflict resolution silently discards user edits made during Copilot resolution flow - ([File: app/src/lib/stores/app-store.ts])

### Summary
`_applyCopilotConflictResolutions` writes back file content computed from a file snapshot taken before the (long-running, tens-of-seconds) Copilot API call, with no re-validation that the file's *current* on-disk content still matches that snapshot. The only staleness guard checks whether the file *still has unresolved conflict markers at all* — it does not check whether the user made partial edits to the file while conflicts were still present. This mirrors the underlying bug class in the report: an operation commits to a value/state captured earlier with zero tolerance for legitimate drift before it is applied, and the only "protection" present doesn't actually cover the realistic drift window.

### Finding Description
The flow is:
1. `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:376-470`) takes a snapshot of each conflicted file's `rawContent` from disk via `readFile`. [1](#0-0) 
2. This snapshot is sent to the Copilot SDK, which can take a long time to respond — the code itself tracks buckets up to and beyond 120 seconds for this call. [2](#0-1) 
3. `reassembleResolutions` / `reassembleResolvedFile` splice the model's per-hunk output into that **original captured snapshot** (`ctx.rawContent`), not into whatever is currently on disk. [3](#0-2) 
4. When the user clicks "Continue Merge", `_applyCopilotConflictResolutions` writes this reassembled (stale-snapshot-based) content straight to disk with `writeFile`, and stages it. [4](#0-3) 

The only guard against overwriting user work is:
```
// If the user resolved this file externally (e.g. in their editor) while
// the result dialog was open, git status will report it with no remaining
// conflict markers. Overwriting it with Copilot's stored content would
// silently clobber their work, so skip it and let their resolution stand.
``` [5](#0-4) 

This check (`isConflictedFileStatus(...) && !hasUnresolvedConflicts(...)`) only detects the binary case where the user has *fully* removed all conflict markers. It does nothing for the much more likely case: the user opens the file in their editor during the (up to minutes-long) Copilot call or while reviewing the result dialog, and edits some non-conflicted lines, or partially resolves one hunk while other conflict markers remain elsewhere in the file — the file still reports as "has unresolved conflicts," so the guard passes, and `writeFile` overwrites the entire file with content derived from the pre-edit snapshot, silently discarding the user's edits with no diff, no prompt, and no size/content tolerance check comparable to a "slippage" bound.

### Impact Explanation
This causes silent corruption of what the user ultimately commits: legitimate, unstaged manual edits made to a working-directory file during an async LLM round trip are discarded without warning as soon as the user clicks "Continue Merge," and the discarded version is then `git add`-ed and can be committed as part of the merge/rebase/cherry-pick completion. This falls squarely within the accepted impact category of "silent corruption of what the user commits or pushes," is reachable by any ordinary user who happens to edit a conflicted file while the (attacker-independent but self-triggerable, and — more importantly — driven by an externally-influenced, potentially slow/malicious LLM response) resolution is pending, and requires no elevated privileges, local malware, or credential compromise.

### Likelihood Explanation
Medium. The resolution call can legitimately take from several seconds up to multiple minutes (the code buckets timing at 15s/30s/60s/120s), which is a realistic window for a user to alt-tab to their editor and touch a conflicted file — a natural workflow, not an unnatural attacker-crafted step. The trigger condition (file still shows as having unresolved conflicts while having been partially edited) is common, since users often fix one hunk manually before consulting/waiting on tooling for the rest.

### Recommendation
Before writing `resolution.resolvedContent` to disk, re-read the current on-disk content and compare it against the `rawContent` snapshot captured when the context was built (e.g., via hash or direct comparison). If it differs, treat the file the same way as the "no remaining conflict markers" case — skip the overwrite and let the user's on-disk state stand, surfacing a warning that the Copilot resolution for that file is stale and needs to be regenerated or manually merged, rather than silently applying content derived from an outdated snapshot.

### Proof of Concept
1. Start a merge/rebase that produces a conflicted file `foo.ts`.
2. Trigger "Resolve conflicts with Copilot"; the request is in flight (`_resolveConflictsWithCopilot` awaiting, per `app/src/lib/stores/app-store.ts:6968-6995`).
3. While waiting, open `foo.ts` in an external editor and add a new line unrelated to the conflict markers (leaving markers for at least one other conflict in place so `hasUnresolvedConflicts` still reports true), then save.
4. Wait for the Copilot result dialog and click "Continue Merge."
5. `_applyCopilotConflictResolutions` finds `onDiskFile` still conflicted (`isConflictedFileStatus && hasUnresolvedConflicts` both true) at `app/src/lib/stores/app-store.ts:7250-7256`, so the skip guard does not trigger, and `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` at line 7258 overwrites `foo.ts`, discarding the manually added line with no notification.
