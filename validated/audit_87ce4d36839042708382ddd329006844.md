### Title
Untrusted `ReceivedOutput` bytes report phantom unspendable funds and drive FROST signing of transactions committing to fabricated prevouts - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes an arbitrary scalar `offset`, an arbitrary `TxOut`, and an arbitrary `OutPoint` from attacker-controlled bytes without any consistency or on-chain-validity check. Downstream, `SignableTransaction::new` trusts the claimed `output.value` for fee/funding math and feeds the claimed prevouts into `Prevouts::All`, so the FROST threshold ends up signing a Taproot sighash that commits to fabricated prevout data for outpoints that may not exist.

### Finding Description
The bug class in the external report is "attacker-supplied calls/inputs reach a privileged path because the entry point performs no sanity checks on the attacker-controlled fields." In Serai's shape, the reachable analog is the `ReceivedOutput` deserialization path in `networks/bitcoin/src/wallet/mod.rs`.

`Scanner::scan_transaction` is the only path that produces a `ReceivedOutput` whose fields are internally consistent: the `offset` is drawn from `self.scripts`, keyed by the exact `script_pubkey` found on-chain, and `outpoint` is computed from the real transaction (`mod.rs:199-213`). In contrast, `ReceivedOutput::read` (`mod.rs:122-134`) accepts all three fields verbatim from the byte stream:

- `offset`: any scalar, including one whose `key + offset*G` yields an odd point (no `p2tr_script_buf` parity check at read time) or a point unrelated to `output.script_pubkey`.
- `output`: an arbitrary `TxOut` — the claimed value and script need not correspond to any real UTXO.
- `outpoint`: an arbitrary txid/vout — nothing binds it to the claimed `output`.

The phantom output then propagates into `SignableTransaction::new` (`send.rs:150-256`), which:
- sums `input.output.value` as `input_sat` for the `NotEnoughFunds` check and fee math (`send.rs:175`, `send.rs:215`),
- stores the claimed `TxOut`s in `prevouts` (`send.rs:253`).

`SignableTransaction::multisig` (`send.rs:273-285`) does validate that `p2tr_script_buf(keys.offset(offset).group_key())` equals `prevouts[i].script_pubkey`, which catches a *script* mismatch — but a crafted `ReceivedOutput` can carry a real script (a previously registered offset) paired with a fabricated `value` and a fabricated `outpoint`, passing that check. Finally `TransactionSignMachine::sign` (`send.rs:373-397`) computes `taproot_key_spend_signature_hash` over `Prevouts::All(&self.tx.prevouts)`, committing the signature to the attacker's fabricated prevout amounts and the nonexistent outpoint.

### Impact Explanation
Two concrete harms within the accepted classes:

1. **Funds reported received that are not spendable**: a forged `ReceivedOutput` byte stream inflates the wallet's apparent UTXO set/balance with outputs that do not exist on-chain (or exist with different values/scripts). Coin-selection-equivalent logic (`input_sat`, change computation at `send.rs:224-235`) treats phantom value as real.
2. **Concrete signing of an unintended message**: the threshold signature commits, via `Prevouts::All`, to attacker-chosen prevout values. The resulting transaction is consensus-invalid on-chain (sighash commits to amounts/outpoints that differ from reality), so an entire FROST signing ceremony is spent producing a signature over a message whose prevout commitment the signers never actually verified — burning a signing round and, where change is computed off the inflated `input_sat`, mis-accounting real funds within that (ultimately invalid) transaction.

### Likelihood Explanation
Reachable by any party able to feed untrusted bytes into `ReceivedOutput::read` (deserialized UTXO sets, peer/processor-supplied output lists). No key material, validator status, or collusion is required — only control of the serialized bytes. Severity is bounded to Medium: the forged outputs cannot be spent (the signature is invalid on-chain), so the damage is false balance reporting and consumed/aborted signing ceremonies rather than direct theft.

### Recommendation
Add sanity checks mirroring the `Scanner` invariant:

- In `SignableTransaction::multisig` (or in `ReceivedOutput::read` when a key context is available), reject outputs where `p2tr_script_buf(key + offset*G)` is `None` (odd point) or does not equal `output.script_pubkey` — the parity/consistency check currently only happens incidentally at `multisig` time, after fee/funding math already trusted `output.value`.
- Document that `ReceivedOutput::read` must only consume bytes produced by `ReceivedOutput::write` on outputs previously obtained via `Scanner::scan_*`, and that the `outpoint`'s existence and `output` fields must be verified against the chain before use. Prefer a constructor/typed wrapper that makes "scanner-verified" outputs distinguishable from deserialized ones.
- Where feasible, confirm each `outpoint` resolves to a chain UTXO matching `output` before including it in `SignableTransaction::new`.

### Proof of Concept

//   offset   = a scalar previously registered via Scanner::register_offset
//              (so key + offset*G is even and matches a known script_pubkey)
//   output   = TxOut { value: 100_000_000, script_pubkey: <real registered P2TR script> }
//   outpoint = OutPoint { txid: <nonexistent txid>, vout: 0 }
let forged = ReceivedOutput::read(&mut attacker_bytes.as_slice()).unwrap();

// Balance accounting treats the phantom 1 BTC as real:
let stx = SignableTransaction::new(

    &[(payment_script, 90_000_000)],
    Some(change_script),

    fee_per_vbyte,

// multisig passes because output.script_pubkey matches key + offset*G
let machine = stx.multisig(&keys).unwrap();
