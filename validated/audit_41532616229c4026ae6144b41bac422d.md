### Title
Panic in PedPoP blame path via unregistered participant index in `decrypt_with_proof` — ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
The DKG blame/decryption machinery indexes `self.enc_keys` with a participant index using `HashMap`'s `Index` impl, which panics on a missing key, rather than returning an error. A `Participant` is only validated as a non-zero `u16`; nothing bounds it to `1 ..= n`. A malicious (or merely faulty) participant who submits a blame/accusation referencing a `Participant` index that was never registered — e.g., `n + 1`, or any index whose encryption-key message was never delivered — causes an index-out-of-map panic, aborting the process. This is the direct analog of the reported bug class: an internal consistency assumption (index present in map) reachable from attacker-influenced protocol input, crashing the node.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Decryption::decrypt_with_proof` performs:

```rust
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],
)
```

`self.enc_keys` is only populated via `Decryption::register`, which inserts entries for participants whose `EncryptionKeyMessage`s were processed in round 1 (`verify_r1` → `self.encryption.register(l, msg)` for `l` in `all_participant_indexes()`). The `decryptor` parameter is a `Participant` taken from the accusation flow; `Participant::new` only rejects zero, so any `u16` in `1 ..= u16::MAX` is representable. If `decryptor` is an index that was never registered (outside `1 ..= n`, or a real index whose registration was absent/skipped), `self.enc_keys[&decryptor]` panics.

The same unchecked indexing exists in `Encryption::encrypt` (`self.decryption.enc_keys[&participant]`). Additionally, `Decryption::register` uses `assert!(!self.enc_keys.contains_key(&participant), ...)` — a second panic-on-untrusted-state site in the same file.

### Impact Explanation
A panic in the DKG share-verification/blame path aborts the validator/process running PedPoP. Since this code runs during key generation and blame adjudication — driven by messages from other participants — a single faulty participant can crash honest participants, denying key generation or multisig rotation. That is an availability (High/Medium) impact reachable from protocol messages, matching the DoS-via-internal-invariant class of the MongoDB report.

### Likelihood Explanation
The `HashMap` `Index` operator panics unconditionally on a missing key; the only thing preventing the panic is the implicit assumption that `decryptor` was previously registered. `Participant` deserialization permits any non-zero `u16`, and the blame path exists precisely to handle misbehaving/malformed participants, so attacker-controlled indexes reach this code during adversarial operation. The caveat: `decrypt_with_proof` is `pub(crate)`, so the crash depends on the caller in `pedpop/src/lib.rs` passing through an unvalidated `decryptor` index rather than pre-checking membership — that caller path was not fully confirmed within this analysis, but no bounds check on `Participant` exists anywhere in the type itself.

### Recommendation
Replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?`, and `self.decryption.enc_keys[&participant]` with a checked `get` returning an error. Replace the `assert!` in `Decryption::register` with a returned error (e.g., a `DuplicateParticipant` variant). In general, no `Participant` value should reach a panic path; validate `u16::from(p) <= n` at the protocol boundary.

### Proof of Concept
1. Run `KeyGenMachine::new(ThresholdParams::new(t, n, i)?, context).generate_coefficients(rng)` to obtain a `SecretShareMachine`.
2. Proceed through `generate_secret_shares`/`calculate_share` so that `Decryption.enc_keys` holds only the legitimately registered participants `1 ..= n`.
3. Submit a blame/accusation message whose decryptor/accused `Participant` is `Participant::new(n + 1)` — accepted by `Participant::new` since it only rejects zero.
4. When the blame logic calls `decrypt_with_proof(from, decryptor = Participant(n + 1), msg, Some(proof))`, evaluation of `self.enc_keys[&decryptor]` panics (`HashMap` index on absent key), aborting the process. Equivalent panic via `Encryption::encrypt` when encrypting a share to an unregistered index.
