## Analysis

The report's core pattern is: **a value meant to be validated/bound against a dynamic base is instead combined with the base "raw," so the resulting value silently escapes the intended bound.** Looking for that exact class in GitHub Desktop, I found it in the file-path handling used when the user interacts with entries in the Changes list, History file list, PR "Files changed" tab, and conflict-resolution menus.

Desktop already has a purpose-built guard for this class of bug — `resolveWithin()` in `app/src/lib/path.ts`, which joins a relative path to a root, then uses `realpath` to confirm the resolved path (following any symlinks) still lives under the root, rejecting it otherwise: [1](#0-0) 

This guard is correctly used in two hardened call sites: the AI conflict-context file reader and the `open-repository-from-url` deep-link handler: [2](#0-1) [3](#0-2)

The resulting `fullPath` is passed straight to `shell.openExternal('file://...')`/`shell.showItemInFolder`/the external-editor spawn call: [11](#0-10) [12](#0-11) 

### Title
Repo-boundary check missing when opening tracked-symlink targets from Changes/History/PR file lists — (File: `app/src/ui/changes/sidebar.tsx`)

### Summary
A cloned/fetched Git repository can contain a tracked symlink whose target points outside the repository (e.g. `../../../.ssh/id_rsa` or an absolute path). Git checkout on macOS/Linux (and Windows with symlink support enabled) materializes this literal symlink on disk without validating its target. Desktop's "Open with Default Program," "Open in External Editor," and "Reveal in Finder" actions compute `Path.join(repository.path, file.path)` and pass it directly to the OS shell/editor, so the OS transparently follows the symlink to whatever it points to — the intended repo-root binding is never enforced for these code paths, unlike the two locations that already use `resolveWithin`.

### Finding Description
`resolveWithin()` was introduced specifically to prevent a relative path from escaping a root directory, including via symlinks, by comparing `realpath(root)` against `realpath(resolved)`. It is used for the Copilot conflict-context reader and the `x-github-desktop://openRepo?filepath=...` deep-link handler. The equivalent "open this repo file" actions in the Changes sidebar, commit-history file list, PR "Files changed" tab, and manual-conflict-resolution menus were not updated to use it — they still do a plain `Path.join(repository.path, file.path)`. Since `file.path` for these views is a real path from a git tree/working-directory entry, an attacker-controlled repository can commit a symlink at that path pointing anywhere on the victim's filesystem; the naive join yields a path that is textually "inside" the repository but that the OS resolves through the symlink to an arbitrary location.

### Impact Explanation
Clicking "Open with Default Program"/"Reveal in Finder"/"Open in External Editor" on such an entry causes the OS to open, reveal, or load the symlink's target file — potentially disclosing file contents (e.g. SSH keys, credential files) or leaking the existence/path of sensitive files outside the repository, satisfying the "file read outside the repo" impact class from a repository the attacker controls.

### Likelihood Explanation
The only attacker requirement is publishing/sharing a Git repository (or PR) containing one tracked symlink; the only victim action is a normal, expected interaction — opening a changed file from the UI, which is a core Desktop workflow, not an unnatural step. This affects every listed file-opening surface (Changes, History, PR Files Changed, conflict resolution) uniformly.

### Recommendation
Route every `Path.join(repository.path, file.path)` construction used before invoking `shell.openExternal`, `shell.showItemInFolder`, or the external-editor launcher through `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32`, refusing to open the item (surfacing an error, as `copilot-conflict-context.ts` does) when the resolved real path is `null` (i.e., escapes the repository root).

### Proof of Concept
1. Attacker creates a public repository containing a tracked symlink `evil` → `/Users/victim/.ssh/id_rsa` (or a Windows repo with a symlink to `C:\Users\victim\AppData\...`).
2. Victim clones/fetches this repository in GitHub Desktop (or opens a PR that introduces this file, viewed via `pull-request-files-changed.tsx`).
3. Victim right-clicks `evil` in the Changes list / History file list / PR Files Changed view and selects "Open with Default Program" or "Reveal in Finder."
4. `onOpenItem`/`onFileContextMenu` computes `Path.join(repository.path, 'evil')` and calls `openFile`/`revealInFileManager`, which hand the path to `shell.openExternal`/`shell.showItemInFolder` — the OS follows the symlink and opens/reveals the real target file outside the repository, with no `resolveWithin` check ever performed.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
