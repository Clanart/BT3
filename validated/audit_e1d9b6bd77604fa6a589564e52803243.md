### Title
`ThresholdKeys::read`/`new` never validates `secret_share` against `verification_shares[i]`, so deserialized keys can claim a group key the holder cannot sign for (or which an attacker controls) - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::new` validates the shape of its arguments (share count equals `n`, participant indices are in range, interpolation method is applicable) but never checks the essential consistency invariant: that the provided `secret_share` actually corresponds to `verification_shares[params.i()]`, and more generally that the declared `verification_shares`/`interpolation` describe a key set the holder participates in. `ThresholdKeys::read` deserializes all of these fields from untrusted bytes and passes them straight into `new`, deriving `group_key` solely from the attacker-supplied `verification_shares`.

### Finding Description
The analog to the Wagmi `Dispatcher::add(_token0, _token1, _multipool)` issue — where caller-supplied token addresses are stored without checking they match the multipool's real pair tokens — is direct: `ThresholdKeys::read` accepts caller-supplied `t`, `n`, `i`, `interpolation`, `secret_share`, and `verification_shares` claiming to describe a threshold key, then derives the group key as the interpolation of `verification_shares[1..=t]` without ever proving the declared `secret_share` belongs to that key set: [1](#0-0) 

`read` feeds `C::read_F`/`C::read_G` output directly into `new` with no consistency proof: [2](#0-1) 

Nothing downstream repairs this. `view()` interpolates `secret_share` and `verification_shares` mechanically and only enforces participant-set sanity (count, duplicates, `<= n`, self-inclusion), never `G * secret_share == verification_shares[i]`: [3](#0-2) 

The missing check means two independent failure modes from one root cause:

1. **Claimed-but-uncontrolled group key (unspendable reported funds).** Bytes declaring `secret_share = s` together with `verification_shares` whose sum interpolates to group key `P` are accepted even when `G * s != verification_shares[i]`. The holder's software will report `group_key()` = `P`, accept deposits to `P`, and produce signature shares that fail verification against `verification_shares[i]` at signing time — funds reported received that are not spendable.

2. **Attacker-controlled group key (theft).** Since `group_key` is computed purely from attacker-supplied `verification_shares`, an attacker who controls the serialized bytes can set all `n` shares to `G * x_j` for `x_j` they know, making the reported `group_key` a key *they* fully control. Any funds routed to the `group_key` reported by the deserialized `ThresholdKeys` are the attacker's.

The honest path (`musig`, PedPoP DKG) does prove share/share-commitment consistency during generation (`debug_assert_eq!(our_pub_key, verification_shares[&params.i()])` in `musig`), but `read` bypasses all of it — the invariant is enforced at construction-time of honest keys only, never on deserialization. [4](#0-3) 

### Impact Explanation
High. Any component that loads `ThresholdKeys` from bytes an unprivileged party can influence (import, transport, or restore paths) can be made to report and solicit deposits to a group key either (a) the validator set cannot sign for, permanently locking deposits, or (b) the attacker directly controls, enabling outright theft of funds sent to the reported `group_key`. This matches the Wagmi finding's shape exactly: the system records tokens/keys an external party *claims* describe the real object and acts on them.

### Likelihood Explanation
Reachable wherever serialized `ThresholdKeys` cross a trust boundary before use — `read` is a public deserialization API precisely for untrusted bytes, and the accepted inputs fully determine `group_key`. Exploitation requires no secret material and no collusion; only the ability to supply the serialized blob. Even without malicious input, a corrupted store yields mode (a), bricking spendability silently until signing is attempted.

### Recommendation
In `ThresholdKeys::new`, after validating the participant set, verify self-consistency: reject unless `C::generator() * secret_share == verification_shares[&params.i()]` (equivalently applied for the `Constant` interpolation case where binding factors already encode the shares — in that case verify `G * secret_share == verification_shares[&i]` still holds, since `musig` stores plain keys there). This binds the stored secret to the declared key set exactly as Wagmi was advised to bind `_token0`/`_token1` to the real multipool pair, making every deserialized key self-certifying before its derived `group_key` can be trusted.

### Proof of Concept
```rust
// crypto/dkg — conceptual PoC for C = any Ciphersuite
// Attacker-controlled bytes for ThresholdKeys::read:
let mut serialized = vec![];
serialized.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
serialized.extend(C::ID);
serialized.extend(1u16.to_le_bytes());          // t = 1
serialized.extend(2u16.to_le_bytes());          // n = 2
serialized.extend(1u16.to_le_bytes());          // i = 1
serialized.push(1);                              // Lagrange interpolation
// victim's real secret share s_v (or any scalar)
serialized.extend(s_v.to_repr().as_ref());
// verification shares: attacker picks x1, x2 they KNOW
serialized.extend((C::generator() * x1).to_bytes().as_ref());
serialized.extend((C::generator() * x2).to_bytes().as_ref());

let keys = ThresholdKeys::<C>::read(&mut serialized.as_ref()).unwrap();
// Accepted — no check that G * s_v == verification_shares[1].
// group_key = x1*G*λ1 + x2*G*λ2 — a key whose discrete log the attacker
// can compute. Funds sent to keys.group_key() are the attacker's,
// or (if shares are garbage) permanently unspendable.
```

`ThresholdKeys::new` succeeds because it only checks counts and index bounds (lines 355–374), and `group_key` at lines 376–378 is interpolated entirely from the supplied shares — the declared `secret_share` is never bound to them.
