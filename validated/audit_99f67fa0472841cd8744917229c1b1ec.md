### Title
Hard-coded UTF-8 decoding of raw diff buffers silently corrupts committed content for non-UTF-8 encoded files - (`app/src/lib/git/diff.ts`)

### Summary
`FeeController` hard-coded 18 decimals instead of querying each token's real `decimals()`, silently mis-scaling values whenever a token deviated from the assumption. GitHub Desktop has the same class of bug in its diff pipeline: `diffFromRawDiffOutput()` unconditionally assumes every diff buffer is UTF-8-encoded text and calls `output.toString('utf-8')` on the raw `git diff -z --patch-with-raw` output, even though the function's own comment admits this is just a placeholder assumption. [1](#0-0) 

### Finding Description
`diffFromRawDiffOutput` is the single choke point that turns the raw `Buffer` returned by `git diff` into the string later parsed by `DiffParser` into hunks/lines:

```
function diffFromRawDiffOutput(output: Buffer): IRawDiff {
  // for now we just assume the diff is UTF-8, but given we have the raw buffer
  // we can try and convert this into other encodings in the future
  const result = output.toString('utf-8')
  ...
}
``` [1](#0-0) 

This function backs both `getWorkingDirectoryDiff()` (used for partial commit staging) and `getBranchMergeBaseDiff()`. [2](#0-1) [3](#0-2) 

When a repository/file contains bytes that are not valid UTF-8 (e.g. a file authored in Latin-1/Windows-1252, Shift-JIS, or any encoding whose high bytes don't form valid UTF-8 sequences — perfectly legal, common in real-world repos, and fully attacker-controlled since it's just working-tree/blob content), Node's `Buffer.toString('utf-8')` silently replaces the invalid byte sequences with the Unicode replacement character `U+FFFD`, which is a **lossy, irreversible** transformation. The resulting `hunk.lines[i].text` strings — which are later used verbatim to reconstruct patches — no longer represent the original bytes.

Those corrupted line strings feed directly into `formatPatch()`, which builds a textual patch for `git apply --cached` from a user's partial line selection, re-using unselected "context" lines verbatim (`hunkBuf += `${line.text}\n``) and unmodified original bytes for lines the user did not touch: [4](#0-3) 

That patch is then piped to `git apply --cached` in `applyPatchToIndex()`, which writes it straight into the Git index — i.e., into what actually gets committed: [5](#0-4) 

Because `U+FFFD` re-encodes to a completely different 3-byte UTF-8 sequence (`EF BF BD`) than whatever 1-2 original non-UTF-8 bytes it replaced, any hunk/line touched by this path — even "context" lines the user never selected or intended to change — ends up with different bytes in the commit than exist in the actual working-tree file. This is precisely the "assume fixed unit → silently wrong result summed/propagated downstream" pattern from the Solidity report: assuming a fixed encoding (like assuming fixed 18 decimals) instead of detecting the actual one causes irreversible mis-transformation that downstream logic (patch construction, git apply, commit) blindly trusts.

### Impact Explanation
This corrupts what a user believes they are committing/pushing without any warning: Desktop's own `DiffContentsWarning` component only warns about bidi characters and line-ending changes, not about lossy encoding replacement. [6](#0-5) 

A malicious or simply non-UTF-8 repository (attacker controls a cloned/fetched repo) can contain files whose bytes decode with replacement characters; when the victim opens the Changes view and does a partial stage/commit (very common workflow), the bytes actually written to the index/commit for that file differ from the working-tree bytes — silent corruption of committed content, matching the requested impact class ("silent corruption of what the user commits or pushes").

### Likelihood Explanation
Non-UTF-8 encoded files are common (legacy Windows-1252 text, some Asian-language legacy encodings, arbitrary binary-adjacent text files misdetected as text by git). No special git configuration or admin/local access is required — merely opening a repo containing such a file and doing a partial commit triggers the lossy round-trip. The bug is explicitly acknowledged as unfinished in the source comment itself ("for now we just assume the diff is UTF-8"), indicating the developers are aware full-file (non-partial) diffs bypass this issue by using `git apply` against the whole file, but the partial-selection path reconstructs content from the already-decoded string, making it vulnerable.

### Recommendation
Detect/preserve the original encoding when constructing hunks intended for reuse in `formatPatch`, or avoid decoding-then-reencoding by operating on byte offsets/`Buffer` slices for line content instead of a lossily-decoded JS string. At minimum, detect the presence of `U+FFFD` replacement characters introduced by decoding (as opposed to ones present in the original bytes) and block partial-commit patch generation for that file, forcing a full-file stage instead, with a clear warning to the user similar to the existing bidi-character warning.

### Proof of Concept
1. Create a repository containing a tracked text file `notes.txt` with byte `0xE9` (a lone, invalid-as-UTF-8 byte, e.g. "café" encoded in Latin-1) mixed among ASCII context lines.
2. Modify the file, adding one new ASCII line elsewhere while leaving the Latin-1 line unchanged.
3. In Desktop's Changes view, select only the new ASCII line for partial commit (leave the Latin-1 line as unselected context).
4. `getWorkingDirectoryDiff` → `diffFromRawDiffOutput` decodes the raw diff buffer as UTF-8, turning the `0xE9` byte into `U+FFFD`.
5. `formatPatch` emits that context line with `U+FFFD` (re-encoded as `EF BF BD`) instead of the original `E9` byte; `applyPatchToIndex` applies this patch via `git apply --cached`.
6. Inspect the resulting commit blob (`git show HEAD:notes.txt | xxd`): the "unchanged" Latin-1 line now differs byte-for-byte from the working directory file, even though the user never selected it for modification — a silent, undisclosed corruption of committed content.

/**
 * Render the diff for a file within the repository working directory. The file will be
 * compared against HEAD if it's tracked, if not it'll be compared to an empty file meaning
 * that all content in the file will be treated as additions.
 */
export async function getWorkingDirectoryDiff(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  hideWhitespaceInDiff: boolean = false
): Promise<IDiff> {
  // `--no-ext-diff` should be provided wherever we invoke `git diff` so that any
  // diff.external program configured by the user is ignored
  const args = [
    'diff',
    ...(hideWhitespaceInDiff ? ['-w'] : []),
    '--no-ext-diff',
    '--patch-with-raw',
    '-z',
    '--no-color',
  ]
  const successExitCodes = new Set([0])
  const isSubmodule = file.status.submoduleStatus !== undefined

  // For added submodules, we'll use the "default" parameters, which are able
  // to output the submodule commit.
  if (
    !isSubmodule &&
    (file.status.kind === AppFileStatusKind.New ||
      file.status.kind === AppFileStatusKind.Untracked)
  ) {
    // `git diff --no-index` seems to emulate the exit codes from `diff` irrespective of
    // whether you set --exit-code
    //
    // this is the behavior:
    // - 0 if no changes found
    // - 1 if changes found
    // -   and error otherwise
    //
    // citation in source:
    // https://github.com/git/git/blob/1f66975deb8402131fbf7c14330d0c7cdebaeaa2/diff-no-index.c#L300
    successExitCodes.add(1)
    args.push('--no-index', '--', '/dev/null', file.path)
  } else if (file.status.kind === AppFileStatusKind.Renamed) {
    // NB: Technically this is incorrect, the best kind of incorrect.
    // In order to show exactly what will end up in the commit we should
    // perform a diff between the new file and the old file as it appears
    // in HEAD. By diffing against the index we won't show any changes
    // already staged to the renamed file which differs from our other diffs.
    // The closest I got to that was running hash-object and then using
    // git diff <blob> <blob> but that seems a bit excessive.
    args.push('--', ensureRelativePath(file.path))
  } else {
    args.push('HEAD', '--', ensureRelativePath(file.path))
  }

  const { stdout, stderr } = await git(
    args,
    repository.path,
    'getWorkingDirectoryDiff',
    { successExitCodes, encoding: 'buffer' }
  )
  const lineEndingsChange = parseLineEndingsWarning(stderr)

  return buildDiff(stdout, repository, file, 'HEAD', 'HEAD', lineEndingsChange)

  // for now we just assume the diff is UTF-8, but given we have the raw buffer
  // we can try and convert this into other encodings in the future
  const result = output.toString('utf-8')

  return parser.parse(forceUnwrap(`Invalid diff output`, pieces.at(-1)))
