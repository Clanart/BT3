### Title
`redirect_uri_for_embedded` fails to strip attacker-supplied `redirect_uri`/`redirectUri` params, allowing an extra attacker-controlled redirect target to be injected into the embedded-redirect query string - ([File: lib/shopify_app/controller_concerns/redirect_for_embedded.rb])

### Summary
`redirect_uri_for_embedded` builds the target URL by taking `sanitized_params.except(:redirect_uri)` and then setting `query_params[:redirectUri]` to the app's own safe login URL. Because `sanitized_params` is a plain, non-indifferent-access `Hash` built from `request.query_parameters`/`request.request_parameters` (string-keyed), `.except(:redirect_uri)` (a `Symbol`) never removes an attacker-supplied string key such as `"redirect_uri"` or `"redirectUri"`, and the subsequent `query_params[:redirectUri] = redirect_uri` assignment creates a *separate* symbol key rather than overwriting the attacker's string key. The final `.to_query` call can therefore emit two `redirectUri`-named parameters in the resulting URL, one attacker-controlled.

### Finding Description
In `redirect_uri_for_embedded`:
```ruby
query_params = sanitized_params.except(:redirect_uri)
query_params[:redirectUri] = redirect_uri
"#{ShopifyApp.configuration.embedded_redirect_url}?#{query_params.to_query}"
``` [1](#0-0) 

`sanitized_params` is derived directly from Rails' request parameters and cloned, without any indifferent-access conversion:
```ruby
def sanitized_params
  parameters = request.post? ? request.request_parameters : request.query_parameters
  parameters.clone.tap do |params_copy|
    if params[:shop].is_a?(String)
      params_copy[:shop] = sanitize_shop_param(params)
    end
  end
end
``` [2](#0-1) 

`request.query_parameters`/`request.request_parameters` return plain `Hash` objects with **String** keys (Rack/Rails do not use `HashWithIndifferentAccess` for these). Because of that:
- `.except(:redirect_uri)` — a `Symbol` — never matches a `"redirect_uri"` or `"redirectUri"` String key supplied by the attacker in the query string. The attacker's raw value is preserved unmodified in `query_params`.
- `query_params[:redirectUri] = redirect_uri` inserts a **new** Symbol key `:redirectUri`; it does not overwrite the attacker's String key `"redirectUri"` if that was the name used. Both keys can coexist in the same Hash.
- `Hash#to_query` (ActiveSupport) serializes every key/value pair and lexicographically sorts the resulting `"key=value"` strings, so a resulting URL can legitimately contain two params that stringify to the same name (`redirectUri=<attacker_value>` and `redirectUri=<app_safe_value>`), in an order controllable by the attacker (by choosing the string content of the value, which affects the sort order used by `to_query`).

None of the app's existing protections address this: `check_shop_domain`/`check_shop_known` only validate the `shop` param via `ShopifyApp::Utils.sanitize_shop_domain`, and there is no filtering of arbitrary extraneous query params before they are echoed back into the embedded redirect URL. The invariant the question asks about — "`query_params[:redirectUri]` only ever points back into the app's own `login_url`/host" — does not hold: an attacker-controlled `"redirectUri"`/`"redirect_uri"` string-keyed parameter survives untouched alongside the safe symbol-keyed one.

### Impact Explanation
The practical exploitable impact is limited by what the client-side code loaded at `ShopifyApp.configuration.embedded_redirect_url` actually does with the query string — this behavior is external to the repo (a static HTML/JS page, typically App Bridge bounce-page logic) and cannot be fully verified from this codebase. If that page parses the query string with a method that returns the first occurrence of a repeated key (e.g. `URLSearchParams.get`), and the attacker can force their `redirectUri` value to sort before the app's legitimate one in the query string (via `Hash#to_query`'s lexicographic sort of `"key=value"` pairs), the browser can be bounced to an attacker-controlled destination via a link that otherwise looks like it comes from the trusted app domain. This matches an "open redirect" class issue (Shopify HackerOne: Improper redirect / potential token or parameter exfiltration via redirect), scoped to leaking `shop`/`host` query parameters (and, transitively, anything the bounce page attaches on redirect) to the attacker's domain. It does **not** demonstrate direct session/access-token theft from this code alone, since no token is placed in this particular query string by this method.

### Likelihood Explanation
Preconditions: `ShopifyApp.configuration.embedded_redirect_url` must be configured and the app must be embedded, `embedded=1` and `shop`/`host` params present so `redirect_for_embedded` is invoked (reachable, e.g., from `ShopifyApp::EnsureInstalled#check_shop_known`). An attacker only needs to control the query string of a link/iframe request — no authentication, secret, or token is required, and `sanitize_shop_domain` does not touch the `redirect_uri`/`redirectUri` keys. This is straightforward and repeatable to trigger; the residual uncertainty is only in how the destination bounce page consumes duplicate query keys.

### Recommendation
Normalize `sanitized_params` to strip attacker-controlled redirect-target keys robustly, regardless of casing or key type, e.g.:
```ruby
def sanitized_params
  parameters = (request.post? ? request.request_parameters : request.query_parameters)
    .with_indifferent_access
  parameters.except(:redirect_uri, :redirectUri).tap do |params_copy|
    params_copy[:shop] = sanitize_shop_param(params) if params[:shop].is_a?(String)
  end
end
```
and ensure `redirect_uri_for_embedded` only ever sets a single, indifferent-access key for `redirectUri`, so no duplicate or attacker-influenced key can end up in the final `to_query` output.

### Proof of Concept
```ruby
test "#redirect_uri_for_embedded should not leak an attacker-controlled redirectUri" do
  ShopifyApp.configuration.embedded_redirect_url = "/a-redirect-page"
  get :new, params: { shop: "my-shop", embedded: 1, redirectUri: "https://evil.com/steal" }

  redirected = response.headers["Location"]
  # Fails today: redirected contains BOTH the attacker's evil.com value
  # and the app's safe redirectUri as two separate "redirectUri=" occurrences.
  refute_includes redirected, "evil.com"
  assert_equal 1, redirected.scan("redirectUri=").size
end
```
Given the current implementation, this test fails: `redirected` contains two `redirectUri=` occurrences, one of which is `https%3A%2F%2Fevil.com%2Fsteal`, confirming the string-keyed attacker parameter survives `sanitized_params.except(:redirect_uri)` untouched.
