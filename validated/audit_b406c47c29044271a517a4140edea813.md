## Title
Global (non-per-IP) DoS of QUIC connection-tracker capacity via slow-handshake burst — (File: `streamer/src/nonblocking/quic.rs`)

### Summary
An unprivileged, unstaked attacker can perpetually occupy a large fraction of the server's `max_concurrent_connections` capacity by opening a burst of QUIC connections and deliberately withholding the packets needed to complete the handshake, holding each `ClientConnectionTracker` slot for the full `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) before it is released, then immediately repeating the cycle.

### Finding Description
In `run_server`, before a `ClientConnectionTracker` slot is granted, two rate limiters are consulted:
- the global `overall_connection_rate_limiter` (`MAX_CONNECTION_BURST` / `TOTAL_CONNECTIONS_PER_SECOND` token bucket), checked via `current_tokens() == 0` [1](#0-0) 
- the per-IP `rate_limiter.is_allowed(...)` [2](#0-1) 

Both checks are "peek"-only against tokens that are only ever **consumed** later, inside `setup_connection`, and only on the success branch (i.e., after the handshake actually completes): `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` [3](#0-2) . `ConnectionRateLimiter::is_allowed` explicitly returns `true` when no record yet exists for an IP [4](#0-3) , and a record for an IP is only created by `register_connection`, which is only reached on a *successful* handshake [5](#0-4) .

Consequently, an attacker who never completes the handshake never triggers either rate limiter: no tokens are ever debited from the overall bucket or from the per-IP bucket for stalled/incomplete attempts. The only gate that actually bounds the number of concurrent in-flight (incomplete) handshakes is the global `ClientConnectionTracker::new(stats, qos.max_concurrent_connections())` check, which compares a single global `open_connections` counter against `max_concurrent_connections` — with no per-IP/per-peer partitioning [6](#0-5) .

Once a slot is granted, `setup_connection` awaits the connection under `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting)` (2 seconds) before releasing `outstanding_incoming_connection_attempts` and (via `ClientConnectionTracker`'s `Drop`) the global open-connection slot [7](#0-6) [8](#0-7) . `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` is fixed at 2 seconds [9](#0-8) .

The `max_concurrent_connections` value itself is deliberately sized with only a small (25%) headroom above the steady-state connection cap specifically to accommodate in-flight handshakes: `self.config.max_staked_connections * 5 / 4` in `SimpleQos` [10](#0-9) . Because this headroom is shared globally across all peers rather than partitioned per-IP, a single attacker can consume the entire "handshake headroom" (and, since the check is purely against a global counter, potentially crowd out capacity that would otherwise go to legitimate staked/unstaked connections attempting to complete their own handshakes at the same time), by keeping enough stalled `Incoming` streams alive simultaneously.

The code comment in `run_server` acknowledges the general design tension ("our connection/handshake abuse mitigation policy is one of shed fast and bound resource consumption... protect against connection attempt bursts with a global rate-limiter... rate-limit abusive peers by (control-asserted) ip") [11](#0-10) , but as shown, the per-IP and global rate limiters as implemented do not actually bound the count of concurrent *incomplete* handshake attempts — they only throttle the rate of *successful* handshake completions.

### Impact Explanation
This allows a single unprivileged, unstaked remote attacker to occupy a meaningful fraction of the shared, global `max_concurrent_connections` pool indefinitely (bounded only by attacker bandwidth to generate enough separate QUIC `Incoming` streams), by repeatedly reserving slots for ~2s at a time and re-triggering as soon as each slot times out. Since the pool is global rather than per-IP, this can degrade the server's ability to accept genuinely new (staked or unstaked) connections during the attack window, i.e., a "non-RPC remote exhaustion/degradation" impact on the QUIC/TPU connection-establishment path, which is explicitly listed as valid impact in scope.

The severity is bounded (this is a slot-holding/exhaustion issue, not a crash, and existing mechanisms — `max_connections_per_peer`, stream throttling, staked/unstaked partitioning inside `ConnectionTable` — still apply once a connection is *established*), and it does not, by itself, cause fund loss, false execution, or consensus impact. It is a resource-exhaustion/availability degradation at the connection-admission layer.

### Likelihood Explanation
Likelihood is moderate-to-high: no authentication, stake, or special network position is required — the attacker only needs to be able to send UDP packets that cause quinn to yield `Incoming` objects (i.e., valid-looking QUIC Initial packets) and then withhold the packets needed to complete the handshake. This requires no IP spoofing (a normal client that simply stalls after the Initial flight suffices), and the described "peek-not-consume" gap in both rate limiters means the attack is not throttled by either the overall or per-IP limiter, as those are only exercised on the success path.

### Recommendation
- Consume/reserve tokens (or otherwise account for in-flight attempts) from the per-IP and/or overall rate limiters at admission time (before/at `ClientConnectionTracker::new`), not only on handshake success, so that stalled attempts are throttled the same as completed ones.
- Introduce a per-IP cap on concurrent *outstanding* (`ClientConnectionTracker`-held) connection attempts, independent of the existing per-IP completed-connection rate limiter, so a single source cannot monopolize the shared handshake headroom.
- Consider shrinking `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` or making it adaptive under load, and/or scaling the handshake headroom based on observed abuse patterns.

### Proof of Concept
A repo-based test can be constructed similarly to the existing `test_client_connection_tracker` / `test_quic_server_multiple_connections_on_single_client_endpoint` tests [12](#0-11) : spin up `setup_quic_server`, then repeatedly open QUIC client endpoints that send only the Initial packet (or otherwise never let `connecting.await` resolve, e.g. via a raw UDP socket sending a single Initial-shaped datagram) in bursts sized close to `qos.max_concurrent_connections()`, while concurrently attempting a normal legitimate `endpoint.connect(...).await`. Measure `stats.refused_connections_too_many_open_connections` and the increased latency/failure rate of the legitimate connection while the attacker's stalled attempts occupy slots for the ~2s `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` window, and confirm `stats.connection_rate_limited_per_ipaddr` / `stats.connection_rate_limited_across_all` remain at 0 for the attacker's stalled attempts (proving the rate limiters were never triggered).

*Note: I was not able to fully trace whether quinn's own endpoint-level configuration (e.g., default incoming/backlog limits, retry/address-validation settings) imposes any additional implicit cap on the number of simultaneous `Incoming` objects before `endpoint.accept()` is even reached; the `configure_server` function reviewed does not appear to set any such option explicitly [13](#0-12) , but confirming quinn's defaults would require deeper investigation of the `quinn` dependency itself, which is outside this codebase's index.*

    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);

            debug!(
                "There are too many concurrent connections opened already: open: \

            );

        }

        Ok(Self { stats })
    }

pub(crate) fn configure_server(
    identity_keypair: &Keypair,
    quic_server_params: &QuicStreamerConfig,
) -> Result<(ServerConfig, String), QuicServerError> {
    let (cert, priv_key) = new_dummy_x509_certificate(identity_keypair);
    let cert_chain_pem_parts = vec![Pem {
        tag: "CERTIFICATE".to_string(),
        contents: cert.as_ref().to_vec(),
    }];
    let cert_chain_pem = pem::encode_many(&cert_chain_pem_parts);

    let mut server_tls_config =
        tls_server_config_builder().with_single_cert(vec![cert], priv_key)?;
    server_tls_config.alpn_protocols = vec![ALPN_TPU_PROTOCOL_ID.to_vec()];
    server_tls_config.key_log = Arc::new(KeyLogFile::new());
    let quic_server_config = QuicServerConfig::try_from(server_tls_config)?;

    let mut server_config = ServerConfig::with_crypto(Arc::new(quic_server_config));

    // disable path migration as we do not expect TPU clients to be on a mobile device
    server_config.migration(false);

    let config = Arc::get_mut(&mut server_config.transport).unwrap();

    // Set STREAM_MAX_DATA to fit at most 1 transaction.
    // This should match the maximal TX size.
    config.stream_receive_window((quic_server_params.stream_receive_window_size).into());
    // disable uni_streams until handshake is complete
    config.max_concurrent_uni_streams(0u32.into());
    config.receive_window(CONNECTION_RECEIVE_WINDOW_BYTES);
    let timeout = IdleTimeout::try_from(QUIC_MAX_TIMEOUT).unwrap();
    config.max_idle_timeout(Some(timeout));

    // disable bidi & datagrams
    config.max_concurrent_bidi_streams(0u32.into());
    config.datagram_receive_buffer_size(None);

    // Disable GSO. The server only accepts inbound unidirectional streams initiated by clients,
    // which means that reply data never exceeds one MTU. By disabling GSO, we make
    // quinn_proto::Connection::poll_transmit allocate only 1 MTU vs 10 * MTU for _each_ transmit.
    // See https://github.com/anza-xyz/agave/pull/1647.
    config.enable_segmentation_offload(false);

    Ok((server_config, cert_chain_pem))
}
