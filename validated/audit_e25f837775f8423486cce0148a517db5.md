### Title
Unvalidated `ReceivedOutput` permits phantom UTXOs to enter transaction signing - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`ReceivedOutput::read` deserializes the spending offset, claimed `TxOut`, and claimed `OutPoint` without verifying that the outpoint exists or that the supplied `TxOut` is the output at that outpoint. [1](#0-0)  `SignableTransaction::new` subsequently trusts the embedded outpoint for the transaction input and the embedded `TxOut` for the input value and Taproot prevout commitment. [2](#0-1) [3](#0-2) 

### Finding Description
A `ReceivedOutput` is only semantically valid when all three fields correspond to a confirmed UTXO: the `TxOut` must be exactly the transaction output identified by the `OutPoint`, and the offset must derive the key committed to by its script. Scanner-created outputs satisfy this invariant because `scan_transaction` copies the actual transaction output and derives the outpoint from the containing transaction ID and output index. [4](#0-3) 

The byte parser does not preserve that invariant: attacker-controlled bytes can pair a valid Serai P2TR `TxOut` and its correct offset with an arbitrary nonexistent, spent, or unrelated outpoint. [5](#0-4)  Transaction construction then treats the claimed value as available input balance and stores the claimed `TxOut` in `prevouts`. [2](#0-1) [6](#0-5) 

The key check in `SignableTransaction::multisig` only verifies that `key + offset*G` matches the supplied script; it cannot verify that this script or value is present at the supplied outpoint. [7](#0-6)  Signing then commits to `Prevouts::All`, so the fabricated value and script are incorporated into the Taproot sighash even though the referenced UTXO does not authorize the claimed spend. [8](#0-7) 

### Impact Explanation
If untrusted serialized outputs are accepted as wallet inputs, an attacker can cause Serai to account for funds that were never received or are no longer spendable. The signing protocol can produce a complete transaction for the forged input, but Bitcoin consensus will reject it because the outpoint is absent, spent, or has a different `TxOut` than the one committed through `Prevouts::All`. [9](#0-8)  This can stall a planned transfer and cause funds reported as received to be unspendable.

### Likelihood Explanation
The malicious object is a straightforward serialization: a canonical scalar offset, a consensus-encoded `TxOut` paying to the corresponding Serai key, and a fabricated `OutPoint`. No private keys, malformed encodings, hash collisions, or threshold cooperation are needed. The only prerequisite is a path that trusts `ReceivedOutput::read` or `Output::read` results rather than obtaining `ReceivedOutput` exclusively from a scanner over confirmed transactions. [10](#0-9) 

### Recommendation
Do not allow untrusted bytes to construct a semantically authoritative `ReceivedOutput`. Require a checked constructor that resolves `txid:vout` against the confirmed chain and verifies that the returned `TxOut` byte-for-byte equals the supplied output and that its script equals `p2tr_script_buf(group_key + offset*G)`. Alternatively, make `ReceivedOutput` construction private to `Scanner`, which already establishes the transaction/output/outpoint relationship. [4](#0-3)  Any DB recovery path should revalidate persisted outputs against the chain before scheduling or signing a spend.

### Proof of Concept
For a threshold group key `K` and zero offset, create `txout = TxOut { value: 10_000, script_pubkey: p2tr_script_buf(K) }` and `outpoint = OutPoint { txid: arbitrary_txid, vout: 0 }`. Serialize `Scalar::ZERO || consensus(txout) || consensus(outpoint)` and pass it to `ReceivedOutput::read`; it returns `Ok` despite the outpoint being fabricated. [5](#0-4) 

Passing that object to `SignableTransaction::new` creates a transaction spending `arbitrary_txid:0`, records the claimed 10,000-satoshi `TxOut` as a prevout, and passes the script-key check in `multisig`. [2](#0-1) [7](#0-6)  The FROST machines can then complete a transaction containing a valid-looking Schnorr witness, but the transaction is unbroadcastable because the referenced prevout does not exist or does not contain the committed `TxOut`. [11](#0-10)

    }

  }
