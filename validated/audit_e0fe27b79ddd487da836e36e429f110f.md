### Title
Cached FROST preprocess seed reused across every signing session enables secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The tributary coordinator derives FROST nonces deterministically from a `CachedPreprocess` seed stored in `CachedPreprocesses`. That seed is generated exactly once per context, decrypted, and reused on every signing attempt — it is never rotated or deleted after `from_cache` is called. Because `seeded_preprocess` feeds the seed into `ChaCha20Rng::from_seed`, the same hiding/binding nonce scalars (`d`, `e`) are used for every signature the validator ever produces under that context. The FROST crate itself documents that reuse "will presumably cause the signer to leak their secret share" (`crypto/frost/src/sign.rs:216-219`). This is the Serai analog of CVE-2021-37976's "sensitive information obtained from process memory via crafted inputs": a remote party that can cause messages to be signed recovers the validator's private key share purely from public signature shares.

### Finding Description
`preprocess_internal` in `coordinator/src/tributary/signing_protocol.rs:100-148` works as follows:

1. If `CachedPreprocesses::get(txn, context)` is `None`, it runs `AlgorithmMachine::new(...).preprocess(&mut OsRng)`, XORs `machine.cache().0` with a key derived from the validator's private key, and stores it (`signing_protocol.rs:123-135`).
2. It then unconditionally re-reads that same stored seed, decrypts it, and calls `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))` (`signing_protocol.rs:137-145`).

`from_cache` → `seeded_preprocess` instantiates `ChaCha20Rng::from_seed(*seed.0)` and generates the nonce commitments deterministically from it (`crypto/frost/src/sign.rs:121-144`). Nothing ever writes a new value to `CachedPreprocesses` — there is no `set` after signing, no deletion, and no reseeding. Consequently every call to `share_internal` (`signing_protocol.rs:150-181`), which calls `preprocess_internal` again, produces a `SignMachine` with **identical nonce scalars** `d` (hiding) and `e` (binding).

In `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:283-411`), the effective nonce is `base + actual * rho` where `rho` is the public binding factor (`sign.rs:386-396`), and the emitted share is `s_i = d + e·ρ_i + c_i·λ_i·share` (`Schnorr::sign_share` at `crypto/frost/src/algorithm.rs:201-211` → `SchnorrSignature::sign`). `ρ_i`, `c_i`, and `λ_i` are all publicly computable from the published preprocesses, included set, and message. With `d`, `e` constant across sessions and three signing sessions over the same participant set, the system

```
s_1 = d + e·ρ_1 + c_1·λ·x
s_2 = d + e·ρ_2 + c_2·λ·x
s_3 = d + e·ρ_3 + c_3·λ·x
```

is three linear equations in three unknowns (`d`, `e`, `λ·x`), directly yielding the Lagrange-weighted secret share. `share_internal` hands the resulting `SignatureShare` back to be broadcast, so the attacker obtains each equation from data they legitimately receive.

### Impact Explanation
Recovery of a validator's threshold secret share. Combined with shares recovered from (or known to) `t-1` other participants — or used to reduce the effective threshold for an attacker who is already a participant — this enables unauthorized signature/forgery capability against the group key. For bitcoin-serai-backed sets this translates to theft of funds controlled by the threshold key. The disclosure requires only that the victim sign attacker-influenced messages, which is the normal operation of the signing protocol.

### Likelihood Explanation
Deterministic and automatic: the reuse is not contingent on a race or edge case — every signing attempt reuses the same seed because the `is_none()` guard only populates the cache once and it is never cleared. Any unprivileged party able to initiate or influence three signature requests (e.g., via transaction plans the validator signs) collects enough shares. The only mitigating factor is that `attempt`/context separation may scope reuse per context, but `context` here is per-signing-task context (`self.context.encode()`), so repeated signing under the same context is the normal path.

### Recommendation
Rotate or delete the `CachedPreprocesses` entry after each successful `from_cache`/`sign` invocation so a seed is consumed exactly once, matching the documented `MUST only be used once` contract (`crypto/frost/src/sign.rs:85-87, 211-219`). If crash-resilience is required, generate a fresh random seed per session and persist the consumed marker atomically with the signature share, rather than deterministically reusing a static seed.

### Proof of Concept
1. A validator set exists with the coordinator running `SigningProtocol`. Attacker causes three distinct messages `m_1, m_2, m_3` to be signed by participant `i` under the same context and the same `included` set.
2. For each session, `share_internal` → `preprocess_internal` returns identical nonce commitments `D, E` (observable in the republished preprocess) because `ChaCha20Rng::from_seed` is fed the same 32-byte cached seed every time.
3. Attacker collects the three broadcast `SignatureShare` scalars `s_1, s_2, s_3`, computes `ρ_j` via `BindingFactor::calculate_binding_factors` over the public preprocesses and `hash_msg(m_j)`, computes `c_j` via the HRAM challenge, and solves the 3×3 linear system over the scalar field for `λ_i·x_i` — the validator's weighted secret share.
4. With the share recovered (and repeated for other validators or combined with collusion below threshold), the attacker forges signatures or directly computes the group secret.
