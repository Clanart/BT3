### Title
Payments sent to a retired multisig address are permanently locked and never detected - (File: processor/src/multisigs/scanner.rs)

### Summary
Analogous to the Nouns `Stream.sol` issue where tokens sent to the contract outside the "recognized" balance could not be recovered until `cancel()`, Serai's Bitcoin processor permanently drops the retired multisig key from its scan set. Any payment an external party makes to the retired key's external address after the retirement block is never detected, never forwarded, and never scheduled for spending — there is no "rescue" path for these funds even though the threshold shares that could spend them may still exist.

### Finding Description
The scanner maintains `scanner.keys`, a list of `(activation_number, group_key)` pairs; each block is scanned via `network.get_outputs(&block, key)` only for keys in that list. When a multisig rotation completes, `check_multisig_completed` stores `retirement_block = block_number + CONFIRMATIONS` and, once that block is reached, `ScannerDb::retire_key` deletes the keys entry and re-registers only the successor key; the in-RAM copy removes `scanner.keys[0]` and its eventuality tracker in the same pass.

From that block onward, `get_outputs` is never invoked for the retired key, so a transaction paying the retired key's external P2TR address (`Scalar::ZERO` offset) or any of its registered offset addresses (Branch/Change/Forwarded) produces no `Output`, no `ScannerEvent`, no `Plan`, and no refund/forward. Unlike the Nouns case (where `tokenAndOutstandingBalance()` at least allowed distinguishing recoverable excess, and `cancel()` existed as a fallback), Serai has no recovery function at all: the output is spendable only by the retired threshold key, which the processor will no longer use, and `plans_from_block`'s forwarding logic (`ForwardFromExisting`, `ClosingExisting`) only applies while the old key is still tracked.

Note this is worse than temporary locking: it is permanent loss. It also interacts with the race noted in `multisigs/mod.rs` — a `Change` output not tied to a `ResolvedDb` plan is already dropped by `split_outputs_by_key`, but post-retirement *all* output types to the retired key are dropped silently at the scanning layer.

### Impact Explanation
An unprivileged sender (anyone who knows or previously used a Serai deposit/external address — a plausible "accidental send" or stale-address scenario) sends BTC to a retired multisig's address. The funds arrive on-chain at an address only the retired FROST group key can spend, but the processor will never observe or spend them. Funds are permanently locked; equivalent to "funds reported received that are not spendable" (here: not even reported). Matches the Medium-severity profile of the reference issue.

### Likelihood Explanation
Retired addresses remain publicly known and may be cached by integrators, wallets, or payment records. Accidental re-deposits to old addresses are a common operational error; the window is unbounded since the address never expires on-chain.

### Recommendation
Continue scanning retired keys' addresses indefinitely (or for a bounded grace window) and emit the outputs so they can be forwarded to the current multisig or refunded — i.e., treat post-retirement receipts like `OutputType::Forwarded`/`Branch` rather than dropping them at the scan layer. The dedup/`seen` machinery already prevents double-processing, so retaining `scanner.keys[0]`'s scripts only requires a `retired` flag that routes outputs through the forwarding path.

### Proof of Concept
1. Multisig rotation completes: `multisig_completed` fires at block N; `save_retirement_block` sets retirement at N + CONFIRMATIONS.
2. At block N + CONFIRMATIONS, `retire_key` rewrites the DB keys to only the new key, and `scanner.keys.remove(0)` drops the old key from RAM.
3. Attacker/user sends a normal P2TR payment to the retired key's external address in block N + CONFIRMATIONS + k.
4. `for (activation_number, key) in scanner.keys.clone()` no longer iterates the old key → `get_outputs` never called → no `ScannerEvent::Block` carries the output → no `Plan` is scheduled. The UTXO remains unspent and unprocessed forever despite the retired FROST key being able to spend it.
