### Title
Unbounded recursion in `AccountKeyRoleBased`/`AccountKeySerializer` RLP decoding allows stack-overflow crash from a single transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP` are mutually recursive RLP decoders with no depth limit, mirroring the `mdex` bug class (`ex_document_to_comrak_ast`/`comrak_ast_to_ex_document` recursing without a max-depth guard). An attacker can submit a single `TxTypeAccountUpdate` / `TxTypeFeeDelegatedAccountUpdate*` transaction whose `AccountKey` field is a `AccountKeyRoleBased` value nested inside itself thousands of times. Decoding this key drives unbounded Go-native recursion before any structural validation (`IsCompositeType`/`CheckInstallable`) is ever reached, risking an unrecoverable stack-overflow crash of the node process handling the transaction (mempool admission or block execution).

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of opaque byte slices and, for every element, constructs a fresh `AccountKeySerializer` and recursively calls `rlp.DecodeBytes`, which in turn calls `AccountKeySerializer.DecodeRLP`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads a key type, allocates a new `AccountKey` of that type via `NewAccountKey`, and recursively calls `s.Decode(serializer.key)`: [2](#0-1) 

If the decoded `serializer.key` is itself an `AccountKeyRoleBased`, this reenters `AccountKeyRoleBased.DecodeRLP`, and the cycle repeats. Neither function tracks or enforces a maximum recursion/nesting depth — exactly the missing control that the mdex advisory flags in `ex_document_to_comrak_ast`/`comrak_ast_to_ex_document`.

The only defense against nested role-based keys, `IsCompositeType`/`CheckInstallable`, runs *after* the entire structure has already been fully decoded: [3](#0-2) 

and the same check is asserted in `checkAccountKeyZeroValues` only for the top-level key at the RPC/encode layer, not during decode: [4](#0-3) 

So the unbounded recursive decode always executes to completion (or crashes) before the "no nested composite key" rule can reject the value. Because each nesting level only costs the minimal RLP list overhead plus a key-type byte, an attacker can encode thousands of nesting levels within an ordinary-sized transaction payload, analogous to mdex's "thousands of nested block quotes" PoC.

An `AccountKey` value reaches `DecodeRLP` from fully untrusted, attacker-controlled input via:
- `TxInternalDataAccountUpdate` / `TxInternalDataFeeDelegatedAccountUpdate*` RLP decoding, invoked by `types.Transaction.DecodeRLP` → `TxInternalDataSerializer.DecodeRLP` → the specific tx type's `DecodeRLP`, e.g.: [5](#0-4) 
- This decode path is exercised for every transaction submitted over public RPC (`eth_sendRawTransaction`/`klay_sendRawTransaction`) and at block-import time, i.e. reachable by any unprivileged transaction sender.
- It is also directly reachable via the `kaia_decodeAccountKey` RPC method: [6](#0-5) 

### Impact Explanation
Go's runtime grows a goroutine's stack automatically, but on exceeding the configured maximum stack size, it raises an unrecoverable `fatal error: stack overflow`, which — like the SIGSEGV in the mdex NIF — cannot be caught by `recover()` and terminates the entire process. Since this decode path is invoked from the tx-pool ingestion goroutine (for `AddRemote`/`AddLocal`) and from block execution goroutines, and Kaia (like go-ethereum-derived clients) runs many concurrent subsystems in one process, a crash here brings down consensus, RPC, and all other in-process services on that node — not just the single request. Any unprivileged party who can submit a raw transaction or call the account-key RPC can trigger this with no special privileges or authentication, giving it a Medium/High denial-of-service impact consistent with the CVE-2026-54888 class.

### Likelihood Explanation
The precondition is trivial: an attacker only needs to RLP-encode a nested `AccountKeyRoleBased` structure and submit it as the `AccountKey` field of an account-update-style transaction (or pass it to `kaia_decodeAccountKey`). No signature validity, balance, or special account state is required to trigger the decode path itself — decoding happens before signature/other semantic checks in `DecodeRLP`. The only limiting factor is the maximum raw transaction size accepted by the mempool/RPC layer, but because nesting only costs a few bytes per level, that limit still permits very deep nesting, making exploitation straightforward.

### Recommendation
Add an explicit recursion-depth counter (or a per-`rlp.Stream` nesting-depth guard applied generally in the `rlp` package, since `decodeInterface`/`decodeListSlice` in `rlp/decode.go` have the same unbounded-recursion property) that is checked at the start of `AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP`, rejecting the input once a small fixed maximum (e.g., 1, since nested role-based keys are never valid) is exceeded — before recursing further. This mirrors upstream `mdex_native`'s fix of enforcing a maximum AST/document nesting depth during conversion rather than after the fact.

### Proof of Concept
1. Programmatically build a nested `accountkey.AccountKeyRoleBased` value where `Keys[0]` is itself an `AccountKeyRoleBased` value, repeated N times (e.g., N = 100,000), each level minimally sized.
2. RLP-encode the resulting structure via `AccountKeyRoleBased.EncodeRLP` (`blockchain/types/accountkey/account_key_role_based.go:110-118`) into a byte string, and place it as the `Key`/`AccountKey` field of a `TxTypeFeeDelegatedAccountUpdate` (or `AccountUpdate`) transaction, or directly call `kaia_decodeAccountKey` with the raw encoded bytes.
3. Submit the transaction via `eth_sendRawTransaction` (or call `kaia_decodeAccountKey` directly with the crafted bytes).
4. Observe `rlp.DecodeBytes`/`s.Decode` recursing through `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` N times before `CheckInstallable`'s nested-key rejection ever runs, exhausting the goroutine stack and crashing the node process with `fatal error: stack overflow`.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
