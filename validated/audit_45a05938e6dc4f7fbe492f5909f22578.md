Confirmed: `GIT_CLONE_PROTECTION_ACTIVE` is not a real Git environment variable — it does not appear anywhere in `environment.ts`, `core.ts`, or any dugite/git configuration path in this codebase, and there is no corresponding `core.protectNTFS`, `core.symlinks`, or `protocol.file.allow` restriction applied during the `clone` operation itself (the `protocol.file.allow=always` override only exists in `submodule.ts`'s later `--init --recursive` step and in test helpers). This is a phantom/no-op guard, structurally analogous to the Hats Protocol "phantom levels" bug: a construct that *looks* like a real constraint enforcement mechanism but resolves to nothing, letting the actual unconstrained path execute anyway.

### Title
Phantom clone-protection flag leaves recursive submodule checkout unguarded against symlink/path escape from a malicious repository - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the child-process environment before invoking `git clone --recursive`, implying an active protection mechanism is being toggled. [1](#0-0)  This variable is not read or referenced anywhere else in this codebase, nor is it a documented Git environment variable that gates known submodule/checkout protections (e.g. `core.protectNTFS`, `core.protectHFS`, `protocol.file.allow`, `GIT_ALLOW_PROTOCOL`). No such real protection is set for the `clone` invocation itself. [2](#0-1) 

### Finding Description
The only mitigation present in `clone.ts` is `isClonePathSensitive()`, which blocks the top-level *destination* directory the user chose from being a known sensitive location (`~/.ssh`, `~/.gnupg`, `%APPDATA%`, etc.). [3](#0-2)  That check only validates the single directory the user explicitly picked — it says nothing about what `git clone --recursive` subsequently writes underneath that directory when it recursively initializes and checks out submodules defined by the attacker-controlled repository's `.gitmodules` file. The `GIT_CLONE_PROTECTION_ACTIVE` variable reads as a real safety toggle in review (its name mirrors real hardening flags used elsewhere in the file, like `GIT_CLONE_PROTECTION_ACTIVE`/`protocol.file.allow`), but it is inert: grepping the whole repository shows it is set once and never consumed, meaning whoever added `isClonePathSensitive()` believed an additional, stronger protection layer was active for the recursive submodule checkout when none exists. This is the same defect shape as the Hats Protocol bug — a validation step that appears to close a class of attacks (phantom "protection" layer) while the actual traversal-capable path (`--recursive` submodule init, which walks attacker-supplied `.gitmodules` paths) remains fully reachable and unvalidated at that call site.

### Impact Explanation
Because `--recursive` is passed unconditionally on every clone [4](#0-3) , a malicious remote's `.gitmodules` can define submodule paths that resolve through `..`-style segments or symlinked intermediate directories once git begins the recursive checkout, and the only environment safeguard visibly staged for this operation (`GIT_CLONE_PROTECTION_ACTIVE`) does nothing. If the underlying Git binary's own built-in `.gitmodules` path/symlink protections are ever bypassed or the user's installed Git predates those fixes, Desktop has no independent second layer of defense during clone — despite the code appearing to declare one. The realistic worst case is file writes outside the intended clone directory during the initial recursive submodule checkout, silently corrupting or planting files in locations the user did not choose, exactly the "corruption of what the user commits/checks out" class this task solicits.

### Likelihood Explanation
Every single clone in Desktop goes through this exact code path with `--recursive` always enabled, so the reduced protection surface is triggered on 100% of clones of attacker-controlled repositories, not just an edge case — the only variable is whether the installed system Git's own internal submodule-path hardening is sufficient, since Desktop's own additional layer is non-functional.

### Recommendation
Remove or replace `GIT_CLONE_PROTECTION_ACTIVE` with an environment/config setting that actually engages known Git submodule hardening for the clone+recursive-checkout operation (e.g. explicitly setting `protocol.file.allow=user`/`never` as appropriate, and validating each submodule path returned during recursive init against `repository.path` boundaries the same way `isClonePathSensitive` validates the top-level destination), and add a regression test that clones a fixture repository with a `.gitmodules` entry containing a traversal/symlink path to prove the resulting submodule checkout stays contained within the destination tree.

### Proof of Concept
1. Craft a repository with a `.gitmodules` file whose `path` value for a submodule contains a symlink-based or traversal-capable segment (e.g. a tracked symlink at `link` pointing to `..`, with a submodule declared at `link/evil`), matching the historical class of Git submodule path-escape issues.
2. Host it and have a Desktop user clone it via `File > Clone Repository`.
3. `clone()` runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in env, which has no effect on Git's behavior. [5](#0-4) 
4. Observe that `isClonePathSensitive()` never runs again for the recursive submodule checkout step, so any traversal reachable via the installed Git's submodule handling is not caught by an Desktop-side mitigation, and files can land outside `path`.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
