Audit Report

## Title
`DynamicPacketToProcessThreshold` can latch at `0` and never recover, permanently dropping all repair-response packets - (File: `core/src/repair/packet_threshold.rs`)

## Summary
`DynamicPacketToProcessThreshold::update` in `core/src/repair/packet_threshold.rs` adjusts `max_packets` using integer-truncating multiplication/division with no lower-bound clamp. Because both the `Increase` and `Decrease` branches are fixed points at `0` (`0 * 100 / 90 = 0` and `0 * 90 / 100 = 0`), once `max_packets` reaches `0` it can never increase again, and `should_drop` then returns `true` for virtually all future packet counts, permanently disabling ingestion of ancestor-hashes/block-id repair-response packets until process restart.

## Finding Description
The core logic is: [1](#0-0) 

`update()` only mutates `max_packets` when `total_packets >= self.max_packets`: [2](#0-1) , and `should_drop` is a simple `total >= self.max_packets` comparison: [3](#0-2) .

Once `max_packets == 0`, the guard `total_packets >= self.max_packets` is satisfied by any nonzero `total_packets`, and `calculate` maps `0 -> 0` for both `Increase` and `Decrease`, so `max_packets` is stuck at `0` forever with no code path to recover it.

This threshold is used in the block-id repair response path, where `total_packets` (the raw count of received packets in the batch, counted before any validation) and `compute_time` directly drive the throttle update: [4](#0-3) . The same `DynamicPacketToProcessThreshold` construct is also imported and used by the ancestor-hashes repair response path. [5](#0-4) 

Because packets are counted into `total_packets` purely based on batch size (`packet_batch.len()`/`batch.len()`) prior to any nonce or content verification, an unprivileged remote party sending arbitrary UDP traffic to the block-id-repair or ancestor-hashes-repair sockets can inflate `total_packets` and, by causing slower processing (e.g. via volume), sustain `compute_time > Self::TIME_THRESHOLD` across repeated iterations. Each such iteration issues a `Decrease` update (`current * 90 / 100`), and repeated truncating decreases will eventually collapse `max_packets` to `0`, at which point it becomes a permanent fixed point.

## Impact Explanation
Once `max_packets` decays to `0`, `should_drop` returns `true` for essentially all subsequent traffic, so the validator's ancestor-hashes/block-id repair-response ingestion path drops all incoming repair responses indefinitely — a persistent, non-recoverable degradation of the node's ability to resolve forks/duplicates and catch up via repair, until the process is restarted (which resets the in-memory `DynamicPacketToProcessThreshold`). This is triggerable by an unprivileged remote party sending public/plain UDP traffic to a public repair socket, constituting a remote resource-exhaustion/degradation condition on the repair subsystem rather than requiring any privileged or malicious-validator assumption.

## Likelihood Explanation
Reaching `max_packets == 0` requires many consecutive `Decrease` events (each a ~10% reduction, so many rounds are needed to shrink to `1` then truncate to `0`), which is plausible under sustained load — either organic network/load conditions or a remote party flooding the block-id-repair/ancestor-hashes-repair UDP sockets with packets to keep `total_packets` and `compute_time` elevated. No privileged access, malicious validator collusion, or leaked keys are required — only ordinary or adversarial packet volume directed at a publicly reachable socket.

## Recommendation
Clamp `max_packets` with an explicit floor (and ceiling) after each `calculate` call, e.g.:
```rust
self.max_packets = threshold_update.calculate(self.max_packets).max(MIN_PACKETS_THRESHOLD);
```
so that `Decrease` can never drive the value below a safe minimum, guaranteeing the threshold can always recover once load or compute time improves.

## Proof of Concept
1. Construct a `DynamicPacketToProcessThreshold` (default `max_packets = 1024`).
2. Repeatedly call `update(total_packets, compute_time)` with `total_packets >= max_packets` and `compute_time > Duration::from_secs(1)` to force consecutive `Decrease` updates: `1024 -> 921 -> ... -> 1 -> 0`.
3. Once `max_packets == 0`, call `update` again with any `total_packets`; `calculate` returns `0` for both `Increase` and `Decrease`, so `max_packets` remains `0` permanently.
4. Confirm `should_drop(total)` now returns `true` for any `total >= 0`, matching the production call sites in `core/src/repair/block_id_repair_service.rs` (`process_responses`) and the analogous ancestor-hashes-service path, which use this exact threshold object to gate real repair-response packet processing.

```rust
impl PacketThresholdUpdate {
    const PERCENTAGE: usize = 90;

    fn calculate(&self, current: usize) -> usize {
        match *self {
            PacketThresholdUpdate::Increase => {
                current.saturating_mul(100).saturating_div(Self::PERCENTAGE)
            }
            PacketThresholdUpdate::Decrease => {
                current.saturating_mul(Self::PERCENTAGE).saturating_div(100)
            }
        }
    }
}
```

```rust
    pub fn update(&mut self, total_packets: usize, compute_time: Duration) {
        if total_packets >= self.max_packets {
            let threshold_update = if compute_time > Self::TIME_THRESHOLD {
                PacketThresholdUpdate::Decrease
            } else {
                PacketThresholdUpdate::Increase
            };
            self.max_packets = threshold_update.calculate(self.max_packets);
        }
    }
```
