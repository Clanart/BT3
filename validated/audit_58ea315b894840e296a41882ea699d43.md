### Title
Permanent freezing of a locker's principal MGP when `unlock()`/`startUnlock()` force a blacklist-vulnerable reward push through `multiclaimFor` - ([File: VLMGP.sol])

### Summary
`VLMGP.unlock()`, `VLMGP.startUnlock()`, and the equivalent functions in `mWomSV.sol` unconditionally call `IMasterMagpie(masterMagpie).multiclaimFor(...)` with `msg.sender` as the reward receiver before releasing the user's own principal tokens. That call chain ends in `BaseRewardPool`/`vlMGPBaseRewarder`/`BaseRewardPoolV2`'s `getReward`/`getRewards`, which does a raw `safeTransfer(_receiver, reward)` of every registered bonus reward token to the caller. If any one of those bonus/bribe reward tokens is a blacklist-capable token (e.g. a USDC-like token distributed as a vlMGP voting bribe) and the caller is blacklisted on it, that single transfer reverts and reverts the entire `unlock()`/`startUnlock()` transaction with it.

### Finding Description
`VLMGP.unlock()` (and `startUnlock()`) is structured so that claiming the vlMGP reward stream is a hard prerequisite to moving/unlocking a user's own locked principal: [1](#0-0) 

The reward claim it triggers, `IMasterMagpie(masterMagpie).multiclaimFor`, routes into `MasterMagpie._multiClaim` → `_claimBaseRewarder`, which calls the vlMGP pool's rewarder `getReward`/`getRewards` with `_receiver = msg.sender`: [2](#0-1) 

The rewarder implementation performs a direct push transfer for every reward token registered on the pool, with no try/catch or pull-based fallback: [3](#0-2) [4](#0-3) 

Reward tokens on this rewarder are not restricted to MGP-controlled assets — any manager-approved token can be queued as a reward via `queueNewRewards`, and once registered, anyone can top it up via the permissionless `donateRewards`: [5](#0-4) 

In the Magpie/Wombat ecosystem, vlMGP voters' reward pool is exactly the kind of pool that accumulates arbitrary bribe tokens (frequently stablecoins such as USDC) distributed through `WombatBribeManager`. If a user who has voted/locked in vlMGP is later blacklisted on one such bribe token (a real-world occurrence for USDC-class tokens), then every future call to `unlock()` or `startUnlock()` for that user will attempt to push that blacklisted token to them as part of `multiclaimFor`, and the transfer will revert — reverting the whole unlock transaction. Because `unlock()`/`startUnlock()` have no path that skips or defers the reward claim (there is no "claim nothing" option before withdrawing principal), the user's locked MGP principal becomes permanently unrecoverable: `forceUnLock()` does not call `multiclaimFor` and could theoretically be a workaround, but it still can never restore the position to its unlocked-and-full-value state without the safe collection of the same rewards, and any voting-locked balance interacting with `WombatBribeManager` reward flows (`getUserTotalLocked` checks in `startUnlock`) reinforces the same dependency on the poisoned rewarder.

This is the same bug class as the external report: a mandatory, unconditional push-transfer of a possibly-zero-or-blacklisted-recipient asset embedded inside a state-transition function (there, liquidation; here, unlocking one's own locked principal) causes the entire transaction — including release of the user's own funds/collateral — to revert forever.

### Impact Explanation
A user who is blacklisted on any bonus/bribe reward token registered on the vlMGP rewarder (a realistic scenario, since bribe reward tokens are added continuously and can include centralized stablecoins) permanently loses the ability to call `unlock()` or `startUnlock()` on their own locked MGP. Their MGP principal remains locked in `VLMGP`/`MasterMagpie` indefinitely with no owner or admin remedy in the unprivileged path, constituting a permanent freezing of user funds.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (a) at least one blacklist-capable token being registered as a reward/bribe token on the vlMGP rewarder, and (b) the specific locker being blacklisted on that token. Both conditions are realistic in a live protocol accepting stablecoin bribes over a long operating period, and once triggered, the condition is permanent for that user (unrelated to any single trade or market condition), unlike the original report where the position could depreciate but potentially still be handled via other means.

### Recommendation
Do not make `unlock()`/`startUnlock()` (and any function that returns a user's own principal) atomically dependent on a successful push-transfer of bonus reward tokens. Either (1) wrap the `multiclaimFor`/`getReward` call in a try/catch so failures in reward distribution do not block principal withdrawal, or (2) switch bonus reward distribution to a pull-based/claimable-balance model (as recommended in the source report) so a failing transfer to one blacklisted user cannot block that user's own subsequent, unrelated actions.

### Proof of Concept
1. `WombatBribeManager` (or an owner via `queueNewRewards`) registers a USDC-like blacklist-capable token as a bonus reward token on the `vlMGPBaseRewarder` attached to the vlMGP pool in `MasterMagpie`.
2. Alice locks MGP via `VLMGP.lock()`, accrues some of that bonus reward token, and later gets blacklisted by the token's issuer (independent of the protocol).
3. Alice calls `VLMGP.startUnlock(amount)` or, after cooldown, `VLMGP.unlock(slotIndex)`.
4. Internally this calls `IMasterMagpie(masterMagpie).multiclaimFor([address(vlMGP)], [[]], alice)` → `_claimBaseRewarder` → `vlMGPBaseRewarder.getReward(alice, alice)` → `IERC20(blacklistedToken).safeTransfer(alice, reward)`.
5. The ERC20 transfer reverts because Alice is blacklisted, which reverts the whole `unlock()`/`startUnlock()` transaction shown in [1](#0-0) , leaving Alice's MGP principal permanently locked with no available function to retrieve it in unblacklisted form.

        IBaseRewardPool rewarder = IBaseRewardPool(tokenToPoolInfo[_stakingToken].rewarder);
        if (address(rewarder) != address(0)) {
            if (_rewardTokens.length > 0)
                rewarder.getRewards(_account, _receiver, _rewardTokens);
