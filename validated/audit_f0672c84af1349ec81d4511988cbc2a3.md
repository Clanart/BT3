## Title
`_fetchRefspec` bypasses the `withPushPullFetch` concurrency lock, letting an attacker-controlled fork ref update repository state mid push/pull/fetch - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The Reserve `BackingManager` bug is a broken mutual-exclusion invariant: a guard (`tradeEnd[kind]`) that is supposed to serialize sensitive operations for a given kind fails to do so correctly for one code path (Dutch auctions), letting state change out of the expected sequence. GitHub Desktop has the same class of bug: `AppStore.withPushPullFetch` is the single mutex meant to serialize all push/pull/fetch network operations against a repository via the `isPushPullFetchInProgress` flag, but `AppStore._fetchRefspec` deliberately does **not** acquire that lock, as stated explicitly in its own doc comment. [1](#0-0) [2](#0-1) 

### Finding Description
`withPushPullFetch` is the only mechanism that prevents concurrent network/git operations from racing on the same working directory/index: [1](#0-0) 

Every normal push/pull/fetch path (`performPush`, `performPull`, `performFetch`, `fetchForRepositoryIndicator`) goes through this guard: [3](#0-2) [4](#0-3) [5](#0-4) 

`_fetchRefspec`, used when the app needs to fetch a pull-request/fork ref (e.g. opening a PR via a `x-github-client` deep link, or checking out a PR from a fork), explicitly skips that lock: [2](#0-1) 

The refspec itself, and the remotes it is fetched against/added on the user's behalf, are derived from GitHub API pull-request data supplied by the fork owner (`headCloneUrl`, `headRefName`, `headRepoOwner`), i.e. attacker-controlled input reachable via a deep link or PR list click: [6](#0-5) [7](#0-6) 

Because `_fetchRefspec` runs `git fetch` and then `_refreshRepository` (which updates the in-memory tip/branches/working-directory state) without checking or setting `isPushPullFetchInProgress`, it can execute concurrently with a user-initiated push/pull/fetch that *does* hold the lock. Both code paths call `_refreshRepository`, `fastForwardBranches`, and mutate `gitStore` / `repositoryStateCache` state; since one path never observes the mutex, the "no concurrent network operations" invariant the rest of the app relies on for consistent branch/tip state is not actually enforced end-to-end.

This is directly analogous to the Reserve finding's root cause: a state guard intended to fully serialize a class of operations does not correctly apply to a specific case (Dutch auctions there, `_fetchRefspec` here), leaving a window where operations interleave in a way the design did not intend.

### Impact Explanation
If a user opens a PR-from-fork link (or Desktop otherwise triggers `_fetchRefspec`/`_checkoutPullRequest`) while a push/pull/fetch is already in flight, the fork-controlled fetch can race with the user's own operation. Both paths call `fastForwardBranches`/`_refreshRepository`, which fast-forward local branches and refresh the reported tip/branch state; an interleaved refresh driven by attacker-controlled remote data can cause Desktop to report an inconsistent ahead/behind/tip state, or apply a fast-forward update sourced from the attacker's fork content in the middle of another in-flight operation. In the worst case this can lead to Desktop committing on top of, or reporting success against, ref state that was actually mutated by the untrusted fork fetch, i.e. silent corruption of what the user believes they are committing/pushing — this matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
The attacker only needs to control a forked repository referenced by a pull request and get the victim to click a PR/deep link while another network operation might be running (background fetch indicator, manual push/pull, etc.) — no local access, malware, or leaked credentials required. Because `_fetchRefspec` unconditionally skips the guard (it's not an edge case triggered rarely — it's the designed behavior for every PR-from-fork fetch), the race window exists on every such fetch, making likelihood moderate rather than purely theoretical. However, actually observing corruption requires the timing overlap with another concurrent push/pull/fetch, which keeps overall likelihood at medium rather than high.

### Recommendation
Have `_fetchRefspec` participate in the same `withPushPullFetch` serialization as other network operations (or introduce a dedicated per-repository lock that also covers refspec fetches), and audit `_refreshRepository`/`fastForwardBranches` call sites to ensure state mutations from fork/PR fetches cannot interleave with in-flight push/pull/fetch operations on the same repository.

### Proof of Concept
1. Start a long-running push or pull on a repository (e.g., large repo over slow network) so `isPushPullFetchInProgress` is `true`.
2. While that operation is in flight, click a `x-github-client://openPR` deep link (or open a PR from a fork in the PR list) pointing at a fork the attacker controls, exercising `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` → `_fetchRemote`/`_fetchRefspec`. [6](#0-5) 
3. Because `_fetchRefspec` does not check `isPushPullFetchInProgress`, the fork fetch and subsequent `_refreshRepository` run concurrently with the still-in-progress push/pull, both mutating `repositoryStateCache`/`gitStore` state, producing an inconsistent/incorrect tip or ahead/behind report and a fast-forward driven by attacker-supplied fork content mid-operation. [2](#0-1) 

Note: I could not fully trace every UI entry point that invokes `dispatcher.fetchRefspec` beyond the deep-link/PR-checkout paths shown above within the available search iterations; a full audit of all call sites would strengthen confidence in exact reachability from a purely unprivileged attacker surface.

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }
