### Title
`ThresholdKeys::read` accepts semantically inconsistent key shares — crafted key files cause honest signers to produce attributable-invalid shares - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The SpamAssassin bug class is "an attacker-influenced input file is trusted as valid configuration and silently drives privileged behavior". In Serai, `ThresholdKeys::read` plays this role: it reconstructs signing key material purely from attacker-influenced bytes and never verifies that the deserialized `secret_share` corresponds to `verification_shares[i]`, nor that the verification shares lie on a common polynomial consistent with the declared `(t, n, i)`. The resulting `ThresholdKeys` is used directly by the FROST sign machines, which then emit signature shares that fail verification *under the victim's own participant index*, i.e., attributable misbehavior.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, `i`, the interpolation coefficients, `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new`. `ThresholdKeys::new` only checks:

- `verification_shares.len() == n` and all participants `<= n` (`crypto/dkg/src/lib.rs:355-365`)
- `Constant` interpolation requires `t == n` (`crypto/dkg/src/lib.rs:367-374`)

and then derives `group_key` from shares `1..=t` (`crypto/dkg/src/lib.rs:376-378`). It never checks `C::generator() * secret_share == verification_shares[params.i()]`, and never checks that the `n` shares are consistent evaluations of a `t-1` degree polynomial. The code itself acknowledges this hole: `AlgorithmSignatureMachine::complete` comments that "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" (`crypto/frost/src/sign.rs:491-494`).

An attacker who can influence the serialized bytes (key-file/config channel, backup restore, or any path feeding untrusted bytes into `ThresholdKeys::read` — explicitly an in-scope input surface) supplies the victim's *real* public `group_key` / `verification_shares` (all public) but a corrupted `secret_share`. All structural checks pass; the keys load cleanly.

### Impact Explanation
When the victim uses these keys, `ThresholdView::secret_share` (`crypto/dkg/src/lib.rs:495-498`) is computed from the attacker-chosen scalar. Every share the victim emits fails `verify_share` against its real verification share, and the batch verifier attributes blame to the *victim's* `Participant` index (`crypto/frost/src/sign.rs:474-489`), surfacing as `FrostError::InvalidShare(victim_i)`. In the processor paths (`processor/src/batch_signer.rs`, `processor/src/signer.rs`, `processor/src/cosigner.rs`) this is reported as `ProcessorMessage::InvalidParticipant { participant: victim }` — i.e., a crafted data file converts into on-chain-attributable equivocation/misbehavior by an honest validator (slashable offense), plus signing stalls (`InternalError` at `sign.rs:494`). The system "executes" whatever share semantics the input file declares, with no integrity proof — the direct analog of trusted `.cf` files executing attacker semantics.

### Likelihood Explanation
Reachability requires attacker influence over the deserialized key blob. The crate's own serialization round-trips are self-consistent, so exploitation depends on a deployment where the `ThresholdKeys` blob is restorable/importable from an attacker-influenced source — the same precondition the CVE relies on (untrusted `.cf`/update channels). Within the stated threat model (untrusted bytes fed to `ThresholdKeys::read`), it is deterministic: any tampered `secret_share` or inconsistent share vector passes validation and produces attributable invalid shares. Severity is Medium-High: no direct secret recovery, but forced attributable misbehavior/slashing of an honest signer and liveness failure.

### Recommendation
In `ThresholdKeys::new` (or at least in `read`), verify:

```rust
if C::generator() * secret_share.deref() != verification_shares[&params.i()] {
  Err(DkgError::...)
}
```

and, for Lagrange keys, that all `n` verification shares are consistent with a `t-1` degree polynomial (e.g., check interpolation of shares `t+1..=n` from the first `t`). Rejecting inconsistent files at load converts silent misattribution into a clean deserialization error.

### Proof of Concept
```rust
// C = any in-scope ciphersuite, t = 2, n = 3
let real_shares_public: Vec<C::G> = /* victim's public verification shares */;
let evil_secret = C::random_nonzero_F(); // attacker-chosen, NOT matching shares[0]

let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(2u16.to_le_bytes()); // t
buf.extend(3u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes()); // i = victim
buf.push(1);                    // Lagrange
buf.extend(evil_secret.to_repr().as_ref());
for vs in &real_shares_public {
  buf.extend(vs.to_bytes().as_ref());
}

// Succeeds: no consistency check between secret_share and verification_shares[i]
let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();

// group_key() equals the victim's real group key, so the machine accepts signing
// contexts for the real multisig — but every emitted share fails verify_share
// and blame is attributed to participant 1 (the victim).
```
