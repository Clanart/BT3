## Analysis

The external report's core broken invariant: **a fixed/assumed amount is used for a value-moving operation (approve/transfer) instead of validating it against the actual authoritative balance, and the mismatch is not reconciled before the external interaction, so value can be misdirected or lost.**

Searching the Hyperbridge intents codebase, this exact class of bug reappears — but worse — in the Tron variant of the Intent Gateway. Comparing the two parallel implementations of escrow release:

- `evm/src/apps/intentsv2/IntentsBase.sol` `_withdraw()` follows checks-effects-interactions: it reads `escrowed`, decrements `_orders[commitment][token] = escrowed - amount` **before** performing the external transfer. [1](#0-0) 

- `evm/tron/contracts/apps/IntentGatewayV2.sol` `withdraw()` inverts this order: it only checks that `_orders[commitment][token] != 0` (existence, not sufficiency), performs the external token transfer of the attacker/relayer-controlled `body.tokens[i].amount` **first**, and only decrements escrow accounting **after** the interaction. [2](#0-1) 

### Title
Check-Effects-Interactions violation in `IntentGatewayV2.withdraw` (Tron variant) allows escrow-decrement bypass via reentrant token callback - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` transfers the withdrawal amount to the beneficiary via a raw `token.call(...)` **before** updating `_orders[commitment][token]`. If the escrowed token contract can trigger a callback during `transfer` (e.g. ERC-777-style hooks, or any non-standard/hookable token that gateway operators can list as an input asset), the callback can re-enter the Host → module path or otherwise act before the escrow balance is decremented, allowing tokens to be withdrawn against the same escrow entry more than once before its balance is reduced.

### Finding Description
`withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow`, and from `onGetResponse` after a cancellation proof) only guards with `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` — it never validates `amount <= _orders[body.commitment][token]`, and critically performs the transfer before mutating state:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    ...
}
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

This is the exact "fixed amount used for the payout, not reconciled against the authoritative balance before the interaction" bug class from the report — there the adapter approved a stale `swapParams.amountIn` instead of the real `amountLD` before invoking the downstream call; here the gateway pays out `body.tokens[i].amount` from an untrusted cross-chain-decoded `WithdrawalRequest` before the escrow ledger (`_orders`) is updated, so the external call executes while the ledger still reflects the pre-withdrawal state. The sibling non-Tron implementation in `IntentsBase.sol` correctly performs the subtraction (with underflow protection under Solidity 0.8) *before* the external call, proving this ordering is not intentional and is a genuine implementation divergence/regression in the Tron fork. [4](#0-3) 

Because native-token withdrawal also uses a raw `.call{value: amount}("")` before the decrement, a malicious `beneficiary` contract (attacker controls `body.beneficiary` decoding into an arbitrary address via the cross-chain request, or a native-asset order where the filler/user address is attacker-controlled) can reenter during the native transfer's fallback, calling back into the Host with the same or a related pending withdrawal path while `_orders[commitment][token]` still holds its pre-decrement value, allowing another payout to be issued against escrow that has already been (nominally) paid.

### Impact Explanation
This is a bridge-custody/settlement-integrity bug: it can cause escrowed order funds to be paid out more than once against the same commitment/token balance (double-settlement), directly meeting the "stealing or loss of funds" / "replay or double-claim/double-settlement" bar in the Hyperbridge Impact Gate. It is reachable purely by an unprivileged actor who controls the `beneficiary` address (e.g. a filler/solver contract) or by listing a hookable token as an order's escrowed asset — no relayer collusion, prover compromise, or governance action required beyond the standard (permissionless) intent flow.

### Likelihood Explanation
Likelihood depends on whether the deployed Tron environment (or any future non-EVM-strict fork sharing this pattern) permits: (a) native-asset orders where the beneficiary is a contract with a receive/fallback hook, or (b) escrowed ERC-20 tokens with transfer-time callbacks. Since `IntentGatewayV2` is a general-purpose, permissionless intents gateway that accepts arbitrary `TokenInfo.token` addresses for `order.inputs`, and `beneficiary` is attacker-supplied (the filler in `RedeemEscrow`, the user in `RefundEscrow`), the precondition of a malicious/hookable receiving contract is fully within attacker control — no external validator or token allowlist enforcing "no hooks" is visible in the reviewed code. This makes exploitation plausible without any additional privileged assumption.

### Recommendation
In `evm/tron/contracts/apps/IntentGatewayV2.sol` `withdraw()`, mirror the CEI ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`: read `escrowed`, validate `amount <= escrowed`, write `_orders[commitment][token] = escrowed - amount` **before** issuing the native call or token transfer. Additionally, add an explicit `amount <= escrowed` check (rather than relying solely on non-zero) so a mismatched/malformed cross-chain `amount` cannot be paid out regardless of ordering, and consider a reentrancy guard on `onAccept`/`onGetResponse` as defense in depth.

### Proof of Concept
Conceptual PoC (cannot be executed without full Tron test harness in this review):
1. User places an order with a native-token (`address(0)`) input, or an ERC-20 input token that has a transfer-time hook (e.g., ERC-777-like), escrowing `amount` into `_orders[commitment][token]`.
2. Solver fills the order on the destination chain; a `RedeemEscrow` `WithdrawalRequest` naming `beneficiary` = an attacker-controlled contract is dispatched back and delivered via `onAccept` → `withdraw()`.
3. In `withdraw()`, the native `.call{value: amount}("")` (or the hookable token's `transfer`) invokes the attacker beneficiary contract's fallback/hook *before* `_orders[commitment][token] -= amount` executes.
4. From that hook, the attacker triggers re-entry into the Host's incoming-message path for a second withdrawal referencing the same commitment/token (e.g., a duplicate `RedeemEscrow`/`RefundEscrow` message racing the receipt write, or any other reachable path that calls `withdraw()` again) while `_orders[commitment][token]` still shows the pre-decrement balance, causing a second payout before the ledger reflects the first.

Note: full confirmation that a second call into `withdraw()` can be triggered from within the transfer/callback (i.e., that `_requestReceipts`/replay protection at the Host level, shown at `evm/src/core/EvmHost.sol:794-818`, does not fully block a concurrent second entry for a *different* valid commitment sharing the same `_orders[commitment][token]` slot, e.g. via partial-fill paths using the same commitment) requires deeper tracing of the Tron host's replay-protection ordering, which was not fully available in this review; this is flagged as an area needing further verification before treating the exploit path as fully proven end-to-end. The CEI violation itself, however, is confirmed by direct code comparison and is objectively incorrect relative to the sibling `IntentsBase.sol` implementation.
