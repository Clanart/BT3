Based on my investigation, I found a concrete analog: `pull-request-files-changed.tsx` builds file paths for PR files using unguarded `Path.join()`, in contrast to `copilot-conflict-context.ts` and the deep-link handler in `dispatcher.ts`, which both use `resolveWithin()` to enforce a "resolved path must stay inside the repository" invariant. This is the same bug class as the MEME404 report: one code path enforces an invariant (path/tier containment) while a structurally similar path does not, because the check was added in one place but not propagated to the other.

### Title
Path traversal via crafted Pull Request file path escapes repository root when revealing/opening files - ([File: app/src/ui/open-pull-request/pull-request-files-changed.tsx])

### Summary
Two code paths in the codebase build an absolute filesystem path from a repository-relative path taken from external/attacker-influenced data. `copilot-conflict-context.ts` and the `x-github-client://openRepo` deep-link handler in `dispatcher.ts` both invoke `resolveWithin()` [1](#0-0) [2](#0-1)  to guarantee the resolved path stays inside the repository root, rejecting `..` traversal and symlink escapes. `pull-request-files-changed.tsx`, which renders the file list for a PR fetched from the GitHub API, instead builds the path with a plain `Path.join(repository.path, file.path)` and never validates containment before passing it to `openFile`, `revealInFileManager`, or `dispatcher.openInExternalEditor` [3](#0-2) [4](#0-3) .

### Finding Description
`file.path` in `CommittedFileChange` for a PR-diff view is populated from the diff/status data associated with the pull request's head commit — content that originates from a remote/fork the local user does not control. `Path.join('repository/root', '../../.ssh/authorized_keys')` normalizes `..` segments and can escape `repository.path` entirely; unlike `resolveWithin`, `Path.join` performs no root-containment check and does not call `realpath` to catch symlink escapes. The three menu actions built from this path — `Open With Default Program` (`onOpenFile` → `openFile`), `Reveal In File Manager` (`revealInFileManager`), and `Open in <editor>` (`dispatcher.openInExternalEditor`) — all operate on this unguarded `fullPath` [5](#0-4) . This mirrors the reported invariant break: the "stay within repo root" invariant is correctly enforced on one code path (conflict-resolution file reads, deep-link file reveal) but silently absent on a structurally identical path (PR file actions) that consumes the same kind of untrusted, path-shaped input.

### Impact Explanation
If a crafted/malicious commit in a fork used to open a PR (or reviewed via "Open PR in Desktop") contains a file whose reported path includes `..` segments, selecting "Open With Default Program" or "Reveal in File Manager" from the PR file list's context menu can operate on a file outside the repository — the invariant is that all such user actions should be confined to the repository working directory, exactly the class of file-write/read-outside-repo impact flagged as valid in scope.

### Likelihood Explanation
Requires the victim to open a PR in Desktop and interact with the PR Files Changed context menu on the crafted entry — no elevated privileges, no local access, and no unnatural steps beyond normal PR review workflow that GitHub Desktop explicitly supports (`open-pull-request` feature). Whether `git diff`/status output can actually surface a `..`-containing path for a committed file (vs. Git internally rejecting such paths) is not verified from static code alone; this is the primary uncertainty in exploitability and would need runtime confirmation with a crafted tree object.

### Recommendation
Route `file.path` through the same `resolveWithin(repository.path, file.path)` containment check used in `copilot-conflict-context.ts` and `dispatcher.ts` before constructing `fullPath` in `onOpenFile`, `onFileContextMenu`, and `onRowDoubleClick`; refuse the action and surface an error if the resolved path is `null`.
