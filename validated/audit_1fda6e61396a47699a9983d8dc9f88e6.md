### Title
Solo precompile's `claim()` burns the account's one-time signed authorization while leaving CW20/CW721 assets permanently unclaimed - (File: precompiles/solo/solo.go)

### Summary
The `solo` precompile lets an EOA (`caller`) submit a signed Cosmos tx payload (`MsgClaim`/`MsgClaimSpecific`) on behalf of a `sender` account to move that account's assets to the caller's Sei address. `claim()` only moves native bank coins, ignoring any CW20/CW721 tokens the `sender` holds, yet the account-sequence consumption that authorizes the message happens unconditionally in `sigverify`, identically for both `Claim` and `ClaimSpecific`. This mirrors the OpenQ bug class: a contract accepts/represents multiple asset types (here, native + CW20 + CW721 held by `sender`) but the "claim/payout" path (`Claim`) settles only one type (native), and the CW20/NFT assets are effectively stranded once the one authorized signature is consumed.

### Finding Description
`PrecompileExecutor.Claim` transfers only `p.bankKeeper.GetAllBalances(ctx, sender)` (native bank coins) to the caller's Sei address: [1](#0-0) 

`ClaimSpecific`, by contrast, is the only path that can move CW20 balances and CW721 tokens, and it requires the signed message to be a `MsgClaimSpecific` explicitly enumerating the CW20/CW721 contracts to sweep: [2](#0-1) 

Both methods share `validate` → `sigverify`, and `sigverify` unconditionally increments and persists the `sender` account's sequence upon successful signature verification, *before* any asset movement is even attempted, and this happens the same way regardless of whether the call is `Claim` (native-only) or `ClaimSpecific` (CW20/CW721 aware): [3](#0-2) 

Because the account-sequence nonce embedded in the signed payload is single-use (`sig.Sequence != acct.GetSequence()` check at line 296-298), a `MsgClaim` payload signed for sequence N can only ever be consumed once, and consuming it via `claim()` immediately advances the account to sequence N+1 without touching any CW20/CW721 assets that account held. Any subsequent attempt to sweep those tokens requires a brand-new `MsgClaimSpecific` payload signed at sequence N+1 by the same original key.

### Impact Explanation
The `solo` precompile's `print-claim`/`print-claim-specific` CLI tooling is explicitly designed to generate a single pre-signed payload offline for accounts that are not expected to sign further Cosmos transactions going forward (that is the entire "solo"/migration use case: an EOA authorizes exactly one claim operation via a pre-signed legacy-key tx, then transacts only via EVM afterward): [4](#0-3) 

If the account holder (or a migration/custody tool acting on their behalf) only produces and submits a `MsgClaim` payload — reasonably expecting "claim" to sweep the account's assets — any CW20 tokens or CW721 NFTs owned by `sender` are left behind, and the sequence number that would have been required to authorize their transfer is already burned. Since re-signing at the new sequence requires the same original private key (which, per the "solo" migration model, may no longer be used/available once EVM-side operation begins), those CW20/CW721 assets can become permanently unclaimable through this precompile, i.e., permanent freezing of funds for the affected account — matching the accepted "permanent freezing" impact criterion.

### Likelihood Explanation
This requires no adversarial third party: it triggers purely from routine, expected usage of the migration flow (call `claim()` instead of `claimSpecific()`, or naive tooling that always calls `claim()` for legacy-key migrations) whenever the source account also holds CW20/CW721 balances alongside native coins. Given the precompile explicitly supports separate CLI commands to print `claim` vs `claim-specific` payloads, and the two are semantically expected to be interchangeable ways to "claim my assets," the divergence in what each actually transfers combined with the shared, non-reversible sequence consumption in `sigverify` makes accidental fund-stranding plausible for any solo-migration user with CW20/NFT holdings.

### Recommendation
Either (a) make `Claim()` also sweep all CW20/CW721 holdings discoverable for `sender` (mirroring `ClaimSpecific`'s enumeration logic), or (b) do not consume/advance the account sequence in `sigverify` until the asset-transfer type is known to cover the account's full holdings, or (c) reject `Claim()` calls (or clearly document/gas-restrict them) when the sender account is known to hold CW20/CW721 balances, forcing use of `ClaimSpecific` for complete migrations, so a single signature can't be exhausted while leaving non-native assets permanently stranded.

### Proof of Concept
1. Legacy Cosmos-key account `sender` holds native `usei`, a CW20 token, and a CW721 NFT.
2. Using `PrintClaimTxPayloadCmd`, the sender's key signs a single `MsgClaim(sender, claimer)` payload at their current sequence N (no CW20/CW721 fields exist on `MsgClaim`), intending to migrate all assets to `claimer`'s EVM/Sei address. [4](#0-3) 
3. `claimer` submits this payload via `ISolo.claim(payload)`, which reaches `PrecompileExecutor.Claim`.
4. `validate`/`sigverify` verifies the signature against sequence N, transfers native balances only, and increments `sender`'s sequence to N+1. [1](#0-0) [5](#0-4) 
5. `sender`'s CW20 and CW721 assets remain untouched in the account. To claim them now, a new `MsgClaimSpecific` must be signed at sequence N+1 by the same original private key — if that key is unavailable (the intended "solo" end-state), those assets are permanently stuck, with no path to recovery through this precompile.

func (p PrecompileExecutor) ClaimSpecific(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, readOnly bool) (ret []byte, remainingGas uint64, err error) {
	claimMsg, sender, err := p.validate(ctx, caller, args, readOnly)
	if err != nil {
		return nil, 0, err
	}
	claimSpecificMsg, ok := claimMsg.(claimSpecificMsg)
	if !ok {
		return nil, 0, errors.New("message is not MsgClaimSpecific type")
	}
	callerSeiAddr := p.evmKeeper.GetSeiAddressOrDefault(ctx, caller)
	for _, asset := range claimSpecificMsg.GetIAssets() {
		if asset.IsNative() {
			denom := asset.GetDenom()
			balance := p.bankKeeper.GetBalance(ctx, sender, denom)
			if !balance.IsZero() {
				if err := p.bankKeeper.SendCoins(ctx, sender, callerSeiAddr, sdk.NewCoins(balance)); err != nil {
					return nil, 0, err
				}
			}
			continue
		}
		contractAddr, err := sdk.AccAddressFromBech32(asset.GetContractAddress())
		if err != nil {
			return nil, 0, fmt.Errorf("failed to parse contract address %s: %w", asset.GetContractAddress(), err)
		}
		switch {
		case asset.IsCW20():
			res, err := p.wasmViewKeeper.QuerySmartSafe(ctx, contractAddr, CW20BalanceQueryPayload(sender))
			if err != nil {
				return nil, 0, fmt.Errorf("failed to query CW20 contract %s for balance: %w", contractAddr.String(), err)
			}
			balance, err := ParseCW20BalanceQueryResponse(res)
			if err != nil {
				return nil, 0, fmt.Errorf("failed to parse CW20 contract %s balance response: %w", contractAddr.String(), err)
			}
			_, err = p.wasmKeeper.Execute(ctx, contractAddr, sender, CW20TransferPayload(callerSeiAddr, balance), sdk.NewCoins())
			if err != nil {
				return nil, 0, fmt.Errorf("failed to transfer on CW20 contract %s: %w", contractAddr.String(), err)
			}
		case asset.IsCW721():
			allTokens := []string{}
			if token := asset.GetDenom(); token != "" {
				allTokens = append(allTokens, token)
			} else {
				startAfter := ""
				for {
					res, err := p.wasmViewKeeper.QuerySmartSafe(ctx, contractAddr, CW721TokensQueryPayload(sender, startAfter))
					if err != nil {
						return nil, 0, fmt.Errorf("failed to query CW721 contract %s for all tokens: %w", contractAddr.String(), err)
					}
					tokens, err := ParseCW721TokensQueryResponse(res)
					if err != nil {
						return nil, 0, fmt.Errorf("failed to parse CW20 contract %s balance response: %w", contractAddr.String(), err)
					}
					if len(tokens) == 0 {
						break
					}
					allTokens = append(allTokens, tokens...)
					startAfter = tokens[len(tokens)-1]
				}
			}
			for _, token := range allTokens {
				_, err := p.wasmKeeper.Execute(ctx, contractAddr, sender, CW721TransferPayload(callerSeiAddr, token), sdk.NewCoins())
				if err != nil {
					return nil, 0, fmt.Errorf("failed to transfer token %s on CW721 contract %s: %w", token, contractAddr.String(), err)
				}
			}
		}
	}
	bz, err := method.Outputs.Pack(true)
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

func PrintClaimSpecificTxPayloadCmd() *cobra.Command {
	cmd := &cobra.Command{
		Use:   "print-claim-specific [claimer] [[CW20|CW721] [contract addr]]... --from=<sender>",
		Short: `Print hex-encoded claim specific message payload for Sei Solo migration.`,
		Args:  cobra.MinimumNArgs(3),
		RunE: func(cmd *cobra.Command, args []string) error {
			clientCtx, err := client.GetClientTxContext(cmd)
			if err != nil {
				return err
			}
			if len(args)%2 != 1 {
				return errors.New("print-claim-specific takes odd number of arguments (the first argument is the claimer address, and the rest are asset type/address pairs)")
			}
			assets := []*types.Asset{}
			for i := 1; i < len(args); i += 2 {
				var assetType types.AssetType
				switch args[i] {
				case "CW20":
					assetType = types.AssetType_TYPECW20
				case "CW721":
					assetType = types.AssetType_TYPECW721
				default:
					return fmt.Errorf("accepted asset types are CW20 and CW721. Received %s", args[i])
				}
				assets = append(assets, &types.Asset{
					AssetType:       assetType,
					ContractAddress: args[i+1],
				})
			}

			msg := types.NewMsgClaimSpecific(clientCtx.GetFromAddress(), common.HexToAddress(args[0]), assets...)
			if err := msg.ValidateBasic(); err != nil {
				return err
			}

			clientCtx.PrintSignedOnly = true
			return tx.GenerateOrBroadcastTxCLI(cmd.Context(), clientCtx, cmd.Flags(), msg)
		},
	}

	flags.AddTxFlagsToCmd(cmd)

	return cmd
}
