### Title
Gasless swap deadline admission check accepts `deadline == parentBlockTimestamp`, letting a stale/expired swap be lent gas risk-free - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The reported Y2K bug is a boundary-condition flaw: an inclusive (`>`) comparison at an epoch/deadline boundary lets a user perform an action (deposit) that should only be allowed strictly *before* the cutoff, giving them a risk-free window at `block.timestamp == boundary`. The same class of boundary error is reachable in Kaia's gasless module, where the deadline admission check for `GaslessSwapTx` uses an inclusive comparison against the *current* (parent) block's timestamp instead of the timestamp the transaction will actually execute under.

### Finding Description
`checkBalanceForSwap` in `kaiax/gasless/impl/tx_pool.go` enforces the KIP-247 gasless-swap invariant `tx.deadline >= currentTimestamp` as:

```go
// tx.deadline >= currentTimestamp
deadline := swapArgs.Deadline
if deadline.Cmp(g.Chain.CurrentBlock().Time()) < 0 {
    return fmt.Errorf("insufficient deadline: deadline=%s, want=%s", ...)
}
``` [1](#0-0) 

This check is invoked from `TxPool.validateTx`/`Filter` at the moment a `GaslessSwapTx` is admitted to (or retained in) the pool, and it substitutes for the pool's normal balance check via `GetCheckBalance()` — a gasless sender's balance is otherwise **not** checked at all: [2](#0-1) [3](#0-2) 

The comparison uses `g.Chain.CurrentBlock().Time()` — the timestamp of the *already-mined parent block* — not the timestamp of the block in which the swap will actually be executed. Because `deadline == currentBlock.Time()` passes (`< 0` is false), a swap whose deadline exactly equals the parent block's timestamp is accepted into the pool and can be bundled by the proposer (`LendTxGenerator` + `GaslessApproveTx` + `GaslessSwapTx`, per `kaiax/gasless/README.md`) and executed in the *next* block, whose EVM `block.timestamp` will necessarily be `>=` the parent's and typically strictly greater. This mirrors the reported class exactly: the boundary check is evaluated against the wrong reference point (an already-elapsed instant) with an inclusive operator, so a transaction that is effectively already expired relative to its execution context still passes admission and consumes proposer-funded gas (`LendTxGenerator`).

Unlike the Y2K report (a pure Solidity contract check), here the check lives in the Go tx-pool layer and there is no on-chain enforcement mirrored inside `GaslessSwapRouter` binding surfaced in this repo (`contracts/bindings/kip247/GaslessSwapRouter.go` only exposes the compiled ABI/bytecode, not a redundant on-chain deadline guard visible via source in this index) — the pool-level, off-by-boundary check is effectively the only deadline gate a proposer relies on before committing proposer-funded gas.

### Impact Explanation
Because the admission check is the substitute for the sender balance check (`shouldSkipBalanceCheck = true` for gasless-recognized txs), an over-permissive/boundary-mismatched deadline check means the proposer can be induced to fund gas (`LendTxGenerator`) for a swap that is effectively already at/past its intended validity window relative to actual execution time. If downstream repayment/execution assumptions (e.g., price staleness, MEV/sandwiching around the exact deadline second) are violated, this creates a fee-delegation/gasless-lending abuse vector: the proposer's advanced gas is not reliably guaranteed to be repaid by a genuinely "still valid" swap, and users can exploit the exact-boundary second to guarantee inclusion of trades that should have been rejected. This aligns with "gasless or auction settlement theft / fee-delegation abuse" impact categories.

### Likelihood Explanation
Any unprivileged user can submit a `GaslessSwapTx` with `deadline` set to exactly the currently known chain head's timestamp (trivially readable via public RPC), guaranteeing pool admission at the boundary. Because block production is continuous and the parent block used for the check is always slightly stale relative to the block the swap lands in, hitting or exploiting this exact-equality boundary is straightforward and requires no special privileges — only a single submitted transaction.

### Recommendation
Change the comparison to be strict on the correct reference point, or compare against the block that will actually include the transaction rather than the current head:
```go
if deadline.Cmp(g.Chain.CurrentBlock().Time()) <= 0 {
    return fmt.Errorf(...)
}
```
More robustly, validate the deadline against the anticipated next-block timestamp (or re-validate at inclusion time in block building) rather than solely at pool-admission time against the parent block, consistent with how the analogous Solidity fix recommends `>=`/`>` boundary correction.

### Proof of Concept
1. Query current head timestamp `T` via RPC (`eth_getBlockByNumber("latest")`).
2. Craft and sign a `GaslessSwapTx` with `deadline = T`.
3. Submit via `eth_sendRawTransaction`; `checkBalanceForSwap` computes `deadline.Cmp(currentBlock.Time())` which is `0`, not `< 0`, so the tx is admitted at `kaiax/gasless/impl/tx_pool.go:177`.
4. The tx is promoted (`IsReady`) and bundled with a `LendTxGenerator`-funded gas advance and executed in block `N+1`, whose timestamp is `>= T` (usually `> T`), i.e., strictly after the nominal deadline the sender declared relative to their own submission context — the proposer has already funded gas for a swap that is, from the sender's perspective, at/after its stated cutoff.
