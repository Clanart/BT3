### Title
Division by zero in `consolidatedNode.Split` can panic during block reward calculation and via `kaia_getReward` RPC - ([File: kaiax/staking/staking_info.go])

### Summary
`consolidatedNode.Split` in the staking module divides a reward amount by `totalAmount = StakingAmount + CLStakingInfo.CLStakingAmount` without checking whether that sum is zero. This function is invoked from the reward module's `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` for the block proposer's node whenever it has a non-nil `CLStakingInfo`, without first verifying the proposer's combined stake is non-zero (unlike the staker-allocation paths, which do guard against a zero divisor).

### Finding Description
`consolidatedNode.Split()` computes:
```go
cnAmountBig = big.NewInt(int64(c.StakingAmount))
clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
totalAmount = cnAmountBig + clAmountBig
clAmount := new(big.Int).Mul(clAmountBig, amount)
clAmount = clAmount.Div(clAmount, totalAmount)   // panics if totalAmount == 0
``` [1](#0-0) 

`StakingAmount` and `CLStakingAmount` are both derived by rounding down a wei balance to whole KAIA (`Div(amount, params.KAIA)`), so a staking contract or CL pool balance below 1 KAIA is truncated to `0`: [2](#0-1) 

The reward module's proposer/fund assignment calls `cn.Split(proposer)` for the proposer's consolidated node whenever it has a non-nil `CLStakingInfo`, with **no check that `StakingAmount + CLStakingAmount > 0`**:
```go
cns := si.ConsolidatedNodes()
for _, cn := range cns {
    if cn.RewardAddr != config.Rewardbase { continue }
    if cn.CLStakingInfo == nil { break }
    cnAmount, clAmount := cn.Split(proposer)   // reachable even if total stake == 0
    ...
}
``` [3](#0-2) 

This contrasts with the staker-distribution helpers (`assignStakingRewards`/`assignStakingRewardsFlex`), which only call `cn.Split` after confirming the node's total staking amount exceeds `minStake` (thus guaranteeing a non-zero divisor): [4](#0-3) 

`getDeferredRewardFull*` (which eventually calls `specWithProposerAndFunds*`) is invoked both during actual block finalization (`GetDeferredReward`) and via the public `kaia_getReward` / `kaia_getRewardsAccumulated` RPC APIs: [5](#0-4) 

Go's `big.Int.Div` panics with "division by zero" when the divisor is zero — this is not a recoverable error return, it is a runtime panic.

### Impact Explanation
If the block's proposer is a consolidated node that has registered a CL pool (`CLStakingInfo != nil` via CLRegistry) but both its CN staking-contract balance and CL pool balance round down to `0` KAIA (e.g., balances below 1 KAIA, or a freshly registered/drained pool), any call into `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` for that block will panic on division by zero. This function is on the deferred-reward path executed by `FinalizeState()` for every full node processing that block, so:
- It can crash/halt block processing on all nodes (state divergence / consensus-affecting DoS) if triggered during live block finalization, or
- It can be triggered on-demand by any unprivileged caller invoking the `kaia_getReward` / `kaia_getRewardsAccumulated` public RPC methods for a block/proposer meeting this condition, crashing the RPC-serving node process (public-RPC-callable DoS).

### Likelihood Explanation
Likelihood depends on a validator's registered CL pool and CN staking contract both holding less than 1 KAIA at reward-calculation time — a state a permissionless or low-stake CN operator could produce by registering a CL pool without funding it (or draining it) while remaining the reward-address for a proposer slot. Since staking/CL amounts are attacker/operator-controlled contract balances and are rounded down to whole KAIA, reaching `StakingAmount == 0 && CLStakingAmount == 0` while `CLStakingInfo != nil` is plausible without requiring privileged access, making this a realistically triggerable condition rather than a purely theoretical one.

### Recommendation
Guard `consolidatedNode.Split` against a zero divisor, e.g. return `(amount, big.NewInt(0))` (or `(0,0)`) when `totalAmount.Sign() == 0`, mirroring the safety checks already present in `assignStakingRewards`/`assignStakingRewardsFlex`. Additionally, add an explicit zero-check in `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` before calling `cn.Split` for the proposer.

### Proof of Concept
1. Register a validator's `RewardAddr` as the current block proposer such that its CNStaking contract balance and its CL pool balance are both below `1 * params.KAIA` (rounding down to `0` in `StakingAmounts`/`CLStakingAmount`), while the CL pool is still registered in `CLRegistry` so `CLStakingInfo != nil` for that node.
2. During block processing after the Prague hardfork with `DeferredTxFee = true`, `FinalizeState()` calls `getDeferredRewardFull` → `getDeferredRewardFullKore`/`Flex` → `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` → `cn.Split(proposer)`.
3. In `Split`, `totalAmount = 0 + 0 = 0`, and `clAmount.Div(clAmount, totalAmount)` panics with "division by zero", crashing the node processing that block (or, if invoked instead via `kaia_getReward(blockNumber)` RPC for that block, crashing the RPC server handling the call). [1](#0-0) [3](#0-2)

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
