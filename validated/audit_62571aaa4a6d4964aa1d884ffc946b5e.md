### Title
Missing initialization/format-check for `kip71.gastarget` allows division-by-zero panic in base fee calculation - (File: kaiax/gov/param.go, params/kip71_config.go)

### Summary
The Kaia client validates governance parameter updates via per-parameter `FormatChecker` functions before they are accepted into the effective parameter set. Almost all numeric KIP-71 parameters use a `noopFormatChecker` except `Kip71BaseFeeDenominator`, which explicitly requires a non-zero value because it is used as a divisor. `Kip71GasTarget` is also used as a divisor in `NextMagmaBlockBaseFee` but has no such non-zero check, mirroring the "proper constructor initialization checks" class of bug in the reference report (unvalidated numeric parameter that is later used as a divisor).

### Finding Description
`NextMagmaBlockBaseFee` computes the delta of the next block's base fee using `gasTarget` as a divisor in two symmetric branches (`parentGasUsed > gasTarget` and `parentGasUsed < gasTarget`): [5](#0-4) 

The function only special-cases `baseFeeDenominator == 0` by substituting a fallback value [4](#0-3) , but performs no equivalent handling for `gasTarget == 0`. If `GasTarget` is `0`, and the parent block's gas usage is non-zero (`parentGasUsed != gasTarget`, i.e. `parentGasUsed != 0`), the code executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` where `gasTarget` is `0`. Go's `math/big.Int.Div` panics on division by zero.

The parameter validation layer, which is supposed to reject malformed governance parameter values before they are applied, does not catch this case: `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` (always returns true) [2](#0-1) , in contrast to `Kip71BaseFeeDenominator`, which explicitly rejects zero [1](#0-0) . This asymmetry indicates the missing check was an oversight rather than an intentional design choice.

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked during header validation and block base-fee computation for every block once Magma/KIP-71 is active. A panic here during block processing/mining would crash the node process (or at minimum trigger a fatal unhandled panic) on every CN, PN, and EN that processes the affected block, since base fee computation is part of consensus-critical header validation (`VerifyMagmaHeader` calls the same function) [6](#0-5) . This is a network-wide denial-of-service: once a governance vote sets `GasTarget = 0` and it takes effect, all nodes attempting to build or validate the next block would panic, halting the chain.

### Likelihood Explanation
Governance parameter changes for `kip71.gastarget` are submitted via governance voting (header governance / contract governance), which in some Kaia governance modes can be initiated by the governing node or by contract-based governance calls — a class explicitly in scope per the "governance parameters" allowed domain. Since there is no validation rejecting `0` for this specific field (unlike its sibling `BaseFeeDenominator`), a single malformed or malicious governance vote setting `GasTarget` to `0` is sufficient to trigger the panic on the next non-zero-gas-usage block after the parameter takes effect.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0`, consistent with `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
},
```
Additionally, as defense-in-depth, `NextMagmaBlockBaseFee` in `params/kip71_config.go` should guard against `gasTarget == 0` the same way it already guards `baseFeeDenominator == 0`, to avoid a panic even if an invalid value reaches this function through another path (e.g., ChainConfig-supplied defaults or future code paths that bypass the FormatChecker).

### Proof of Concept
1. A governance proposal sets `kip71.gastarget` to `0` (no format check currently blocks this value, per `kaiax/gov/param.go` `Kip71GasTarget` entry).
2. Once the parameter set takes effect at some block `N`, any subsequent block with `parentHeaderGasUsed != 0` calls `NextMagmaBlockBaseFee(N, parentBaseFee, parentGasUsed)`.
3. Inside, `gasTarget := kc.GasTarget` is `0`; since `parentGasUsed != gasTarget` (assuming any nonzero gas was used), execution enters the `parentGasUsed > gasTarget` (or `<`) branch and calls `x.Div(x, new(big.Int).SetUint64(0))`.
4. `math/big.Int.Div` panics with "division by zero", crashing block processing on every node in the network that reaches this code path.
