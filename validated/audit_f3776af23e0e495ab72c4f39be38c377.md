## Analysis: analogous "attacker-controlled asset blocks unrelated settlement" bug in the Intent Gateway

The Augur report's core primitive is: burning/moving one asset triggers an attacker-controlled hook that can be made to always revert, which blocks an otherwise-legitimate operation (`fillOrder`) that has nothing to do with the attacker beyond sharing the same atomic call. The local analog is the Intent Gateway's escrow release loop, which bundles multiple *different, user-chosen* tokens into a single all-or-nothing transfer loop.

### Title
Malicious input token in a multi-asset order can permanently lock a solver's legitimate escrow payout - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`placeOrder` accepts an arbitrary list of `order.inputs` tokens with no allowlist/validation. When escrow is released — either as a `RedeemEscrow` payout to the solver or a `RefundEscrow` to the user — `_withdraw()` iterates over *all* input tokens in one loop and calls `safeTransfer`/`.call` unconditionally for each. If any single token in that list reverts on transfer (e.g. a blacklist-style or "hook"-style token the order creator controls, analogous to the ERC777 revert-on-burn hook in the source report), the entire `_withdraw` call reverts, and every other token bundled into that same order — including genuinely valuable ones like USDC — becomes permanently unrecoverable, because the settlement message can never be replayed successfully.

### Finding Description
`_withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol` (and the equivalent `withdraw` in `evm/tron/contracts/apps/IntentGatewayV2.sol`) processes `body.tokens` as a single atomic loop: [1](#0-0) 

Each token transfer uses `IERC20(token).safeTransfer(beneficiary, amount)` (or a raw `.call` in the Tron variant) with no try/catch and no per-token isolation: [2](#0-1) 

`order.inputs` (the set of tokens escrowed by the *user* at order placement) accepts arbitrary token addresses with no allowlist check — escrow simply pulls whatever ERC20 address is specified: [3](#0-2) 

This `_withdraw`/`withdraw` call is invoked from `onAccept`, which is the host-driven ISMP callback that finalizes `RedeemEscrow`/`RefundEscrow` settlement messages: [4](#0-3) 

Because the order creator (an unprivileged user) fully controls `order.inputs`, they can escrow two tokens together: a legitimate, valuable one (e.g. USDC) and a "poison" token they deploy themselves whose `transfer`/`transferFrom` unconditionally reverts for any beneficiary other than the attacker (a blacklist-style token, or one that self-pauses after the order is placed — functionally identical to weaponizing a transfer-time hook, as in the ERC777 report). A solver who is unaware of this fills the order, delivering real output value on the destination chain and triggering `RedeemEscrow`. When `onAccept → _withdraw` runs on the source chain, the loop hits the poison token, reverts, and the entire settlement — including the USDC the solver has legitimately earned — can never be released. Retried delivery attempts hit the exact same revert every time, since the poison token's behavior is permanent, so the escrow is locked forever.

### Impact Explanation
This is a direct, permanent loss/lock of funds for an honest counterparty (the solver, or symmetrically the user in a `RefundEscrow` scenario), caused entirely by an unprivileged, ordinary user action (placing a mixed-asset order) — no relayer, prover, or admin compromise required. It matches the bounty's explicit "stealing or loss of funds" / "logic attacks" impact categories.

### Likelihood Explanation
High. Placing an order with an attacker-deployed, arbitrary ERC20 as one of several `order.inputs` requires no special privilege — `placeOrder` performs no allowlist or interface check on input tokens. Any solver who fills a multi-input order without independently vetting every token address is exposed. This is a realistic and cheap griefing/loss vector, not a theoretical edge case, and directly mirrors the accepted-as-valid Augur finding's attacker primitive (an attacker-controlled asset's transfer-time behavior blocking settlement for an unrelated party).

### Recommendation
Make escrow release per-token fault-tolerant instead of all-or-nothing: wrap each token transfer in `_withdraw`/`withdraw` in a low-level call with its own success check, and on failure credit the amount to a claimable/sweep balance for the beneficiary (or skip and emit a per-token failure event) rather than reverting the whole settlement. Additionally, consider validating/allowlisting `order.inputs` tokens at `placeOrder` time, or capping the "blast radius" of an order to a single token per escrow unit so a single hostile asset cannot hold hostage the value of a well-behaved one bundled into the same order.

### Proof of Concept
1. Attacker deploys `PoisonToken`, an ERC20 whose `transfer`/`transferFrom` succeeds only when `to == attacker`, and reverts for every other recipient.
2. Attacker calls `placeOrder` with `order.inputs = [ {token: PoisonToken, amount: 1}, {token: USDC, amount: 10_000e6} ]`, escrowing both tokens.
3. A solver, seeing an attractive USDC-denominated order, calls `fillOrder` on the destination chain, delivering real output tokens to the attacker/beneficiary.
4. The cross-chain `RedeemEscrow` message reaches the source chain; `onAccept` calls `_withdraw`, which iterates `body.tokens = [PoisonToken, USDC]`.
5. The `PoisonToken.transfer(solver, 1)` call reverts, causing the entire `_withdraw` (and thus the whole `onAccept`) to revert.
6. Every retry of the same commitment hits the identical revert. The solver's earned 10,000 USDC remains permanently locked in the `IntentGatewayV2`/`ExtrinsicIntents` contract, while the solver has already delivered value on the destination chain — net loss of funds for the solver, triggered solely by an unprivileged order creator.
