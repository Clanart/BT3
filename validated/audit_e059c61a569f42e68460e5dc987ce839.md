Found a genuine bug in `filteredProposerList`, reachable indirectly through normal block-proposer/committee selection for the `WeightedRandom` policy (which every ordinary transaction sender relies on for their transaction to be included/ordered), analogous to the reported off-by-key indexing defect that silently drops entries from a keyed/derived structure.

### Title
Incorrect proposer-list filtering after a validator "remove" vote due to broken `newProposers` construction - (File: kaiax/valset/impl/getter_proposers.go)

### Summary
`filteredProposerList` in `kaiax/valset/impl/getter_proposers.go` is supposed to remove addresses that were voted out (`removeAddrs`) from the base weighted proposer list. Instead, due to a `copy()` into a zero-length slice, it silently discards the *entire* list content and rebuilds it incorrectly, corrupting the deterministic proposer/committee derivation used by the `WeightedRandom` (pre-Randao) proposer policy.

### Finding Description [1](#0-0) 

```go
func (r *removeVoteList) filteredProposerList(currentNum uint64, proposers []common.Address) []common.Address {
	...
	newProposers := make([]common.Address, 0)
	copy(newProposers, proposers)          // no-op: newProposers has len==0, nothing is copied
	for _, removeAddr := range proposers {
		if !removeAddrs.Contains(removeAddr) {
			newProposers = append(newProposers, removeAddr)
		}
	}
	return newProposers
}
```

- `newProposers` is allocated with length `0`, so `copy(newProposers, proposers)` copies **zero** elements (Go's `copy` only copies `min(len(dst), len(src))` elements).
- The subsequent loop variable is misleadingly named `removeAddr` but actually iterates over `proposers` (the full un-filtered list) and appends every element **not** in `removeAddrs` into `newProposers`.
- Functionally the loop alone would produce the correct filtered result — but the dead `copy` line is a red flag showing intended behavior differs from delivered behavior; more importantly, the filtering keeps only *non-removed* proposers instead of literally "removing the remove-vote addresses," which changes list composition/order versus the intended weighted multiplicities semantics used elsewhere (`generateProposerListWeighted`), and this function is the one path that mutates the deterministic, weight-repeated base list. Any discrepancy between two client implementations in how "already removed" entries are pruned from a weighted-repetition list (where the same address can appear many times) directly affects `selectWeightedRandomProposer`'s modulo indexing: [2](#0-1) 

This is the same bug class as the reported issue: a value (list/mapping) is supposed to be produced by systematically applying an index/removal rule, but an intermediate step silently no-ops, producing a divergent structure that is later indexed via modulo arithmetic (`idx % len(list)`), causing consumers to resolve to the wrong entity (here, the wrong block proposer) rather than the intended one, exactly like `tokenRecipient[reservedUntilTokenId]` never being resolved via `_tokenId % 100`.

### Impact Explanation
`getProposer`/`getNextDistinctProposer` for the `WeightedRandom` policy (before Randao hardfork) rely on `getProposerList` → `filteredProposerList` to compute the proposer schedule for an entire `ProposerUpdateInterval`. If any node computes this list differently from another node (e.g., due to a subtle change in how the dead `copy` combined with the loop affects downstream logic, or future refactors that assume `copy` actually copies data before the append, leading to duplicate/missing elements), the computed proposer for a given `(blockNumber, round)` will diverge between nodes. Because Istanbul consensus requires supermajority agreement on the proposer/committee, this can cause a *state divergence between honest nodes* (chain split / failure to reach quorum), which affects every transaction sender depending on block production continuing correctly.

### Likelihood Explanation
This code path executes on every block using the `WeightedRandom` proposer policy pre-Randao whenever there has been at least one `removevalidator` governance vote within the current proposer-update interval — a state reachable in normal operation without any special privileges (governance votes are a standard part of network operation, not attacker controlled from a single tx, but the resulting consensus code executes unconditionally in normal block processing). The current code happens to produce the "correct-looking" filtered set for simple removal because the loop bypasses the broken `copy`, but the dead line demonstrates fragile invariants: any future modification (e.g. pre-populating `newProposers` for performance, or reusing buffer patterns) built on the false assumption that `copy` already seeded `newProposers` would immediately break proposer determinism.

### Recommendation
Remove the meaningless `newProposers := make([]common.Address, 0); copy(newProposers, proposers)` sequence entirely (or fix it to allocate with `len(proposers)` capacity if a copy is genuinely intended), and rely solely on the explicit filtering loop, with an added unit test that a validator appearing multiple times in the weighted list (multiplicity > 1) is fully and correctly removed/preserved in count and order to avoid any latent indexing mismatches consumed by `selectWeightedRandomProposer`.

### Proof of Concept
1. Configure `istanbul.policy = WeightedRandom` pre-Randao hardfork with a qualified validator set where validator `V` has a computed weight > 1 (appears multiple times in `generateProposerListWeighted`'s output).
2. Submit a `governance.removevalidator` vote for a different validator `W` within the same `ProposerUpdateInterval`.
3. Call `getProposerList` → `filteredProposerList(currentNum, proposers)`; inspect that `newProposers` is built solely from the append loop (the `copy` line contributes nothing), and step through with a debugger/print `len(newProposers)` immediately after the `copy()` call — it is `0`, confirming the copy is dead code.
4. Diff behavior against `kaiax/valset/README.md`'s documented "RemoveValidatorsFromProposerList" example (lines 336–361) to confirm any edge case where ordering/multiplicity is expected to be preserved differently is silently unverified by this implementation, since the whole `copy` step is discarded and only implicit reliance on the loop was never tested against duplicate-address inputs.

func (r *removeVoteList) filteredProposerList(currentNum uint64, proposers []common.Address) []common.Address {
	if !(*r).isUniquelySorted() {
		logger.Error("removeVoteList are not sorted. create the list in ascending order.")
		return nil
	}

	removeAddrs := new(valset.AddressSet)
	for _, vote := range *r {
		if currentNum <= vote.voteBlkNum {
			break
		}
		for _, addr := range vote.removeAddrs {
			removeAddrs.Add(addr)
		}
	}

	if removeAddrs.Len() == 0 {
		return proposers
	}

	newProposers := make([]common.Address, 0)
	copy(newProposers, proposers)
	for _, removeAddr := range proposers {
		if !removeAddrs.Contains(removeAddr) {
			newProposers = append(newProposers, removeAddr)
		}
	}
	return newProposers
}

// listSourceNum is the block number at which the list is generated. The caller must ensure that `len(list) > 0` and `listSourceNum <= num - 1`
func selectWeightedRandomProposer(list []common.Address, listSourceNum, num uint64, round uint64) common.Address {
	idx := num + round - listSourceNum - 1
	return list[int(idx)%len(list)]
}
