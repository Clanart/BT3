### Title
Path-containment check in `resolveWithin` uses substring `startsWith` instead of a path-boundary comparison, allowing deep-link `filepath` to escape the repository directory into any sibling directory with a matching name prefix - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin`/`_resolveWithin` is the sole guard used to keep a user/attacker-supplied relative path inside a repository root before the app touches the filesystem. The final containment check compares the resolved real path to the real root with a plain string `startsWith`, which is a broken invariant: any directory whose name has the root path as a *character prefix* (not a path-segment prefix) also passes. This mirrors the report's underlying bug class — a security-gating equality/containment check compares against the wrong reference (here, "prefix of a string" instead of "ancestor path"), so the check silently accepts inputs it was designed to reject.

### Finding Description
`_resolveWithin` computes the real, symlink-resolved root and target paths and then does: [1](#0-0) 

`String.prototype.startsWith` has no notion of path separators. If `realRoot` is `/Users/x/repo`, then `/Users/x/repository-secrets/passwords.txt` also satisfies `realResolved.startsWith(realRoot)` because `"repo"` is a literal character-prefix of `"repository-secrets"`. The function returns this resolved (out-of-root) path as valid instead of `null`, defeating the entire purpose of the helper (the docstring promises the result is "guaranteed to reside at, or underneath" the root). The existing unit tests only cover `..` traversal and symlink traversal, never the sibling-directory-with-shared-prefix case, so this gap is untested: [2](#0-1) 

This helper is used to sanitize the `filepath` parameter of the `x-github-client://openRepo` deep link before revealing a file to the user: [3](#0-2) 

The deep link is attacker-controlled content (a link the user clicks, e.g. from a webpage or email), and `repository.path` (the clone directory) is derived from the user's existing local clone — an attacker only needs to guess or know a sibling directory name that shares the clone directory's name as a prefix (a very common occurrence, e.g. `repo` vs `repo-backup`, `project` vs `project-old`, `app` vs `app.bak`). The `isAbsolute(filepath)` check only rejects absolute paths, it does nothing to stop this relative-path/prefix-collision bypass: [4](#0-3) 

### Impact Explanation
A successful bypass causes `shell.showItemInFolder(resolved)` to be invoked with a path outside the intended repository, revealing/selecting a file that lives in a sibling directory the attacker does not control — a "file read/reveal outside the repo" impact driven purely by a clicked link, matching the required impact class (link/deep-link controlled by attacker leading to access outside the repo boundary). Because the same `resolveWithin` primitive is documented and relied upon elsewhere as a general-purpose containment guard, any other current or future caller that trusts its "underneath root" guarantee inherits the same silent bypass.

### Likelihood Explanation
Exploitability requires only that the user click a maliciously crafted `x-github-client://` deep link while having a sibling directory whose name is a superstring of their repository folder's name — a naming pattern that is common in practice (backups, `-old`, `-copy`, numbered clones, etc.), and requires no local access, no admin rights, and no prior compromise. The existing guard (`isAbsolute` check plus `resolveWithin`) gives a false sense of safety because its test suite never exercises the prefix-collision scenario.

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to compare path segments rather than raw strings, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the platform-appropriate separator from the injected `options`), and add a regression test with a sibling directory that shares the root's name as a substring prefix (as in the PoC below).

### Proof of Concept
1. Attacker prepares two sibling directories: `/Users/victim/project` (the victim's actual clone, opened as a GitHub Desktop repository) and `/Users/victim/project-secrets/creds.txt` (any file the attacker wants revealed/selected — guessable from common naming conventions or previously leaked info).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/org/project?filepath=../project-secrets/creds.txt`.
3. Desktop's protocol handler routes this to `openRepositoryFromUrl` → `resolveWithin(repository.path, filepath)` with `rootPath = /Users/victim/project`.
4. `resolve()` produces `/Users/victim/project-secrets/creds.txt`; `realResolved.startsWith(realRoot)` evaluates to `true` because `"/Users/victim/project-secrets/creds.txt".startsWith("/Users/victim/project")` is true even though `project-secrets` is not inside `project`.
5. `resolveWithin` returns the out-of-root path instead of `null`, and `shell.showItemInFolder(resolved)` opens the OS file browser highlighting `creds.txt` outside the repository, confirming the containment check is bypassed with a single attacker-controlled link click and no other privileges.

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`

      }
