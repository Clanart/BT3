### Title
Cached FROST preprocess is never cleared, so `share()`/`complete()` re-sign with the same nonce — private key share recovery via nonce reuse - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` deterministically caches a FROST preprocess seed in `CachedPreprocesses` keyed by `(b"DkgConfirmer", attempt)` and **never deletes or rotates it**. Every call to `share_internal` (invoked by both `DkgConfirmer::share` and `DkgConfirmer::complete`) rebuilds the sign machine from that same seed via `AlgorithmSignMachine::from_cache`, producing identical nonce commitments. If `share_internal` is ever executed twice over the same context with distinct received preprocesses or a distinct message (`key_pair`), the same nonce is used to sign two different challenges — the classic FROST nonce-reuse condition that allows any observer to algebraically recover the validator's private key share from the two published `[u8; 32]` shares.

### Finding Description
The original report's bug class is "a non-standard completion path fails to clear protocol state, leaving stale state that breaks/poisons subsequent operations." In Serai the same shape appears as stale nonce state: `CachedPreprocesses::get(self.txn, &self.context)` is only `set` when absent (lines 123–135) and there is no code path that removes it — `grep` confirms `CachedPreprocesses` is touched only in this file, and only for `get`/`set`. After the machine consumes the seed in `share_internal` (line 156 → `machine.sign`), the seed remains in the DB and will deterministically regenerate the exact same nonces on any later invocation under the same `attempt`.

The file's own header comment acknowledges this requires an on-chain check that "the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" (lines 50–54) — that check is not implemented. `share()` and `complete()` accept attacker-influenced `preprocesses: HashMap<Participant, Vec<u8>>` and `key_pair` (which determines `msg` via `set_keys_message`, lines 296–301) with no binding that the previously-signed inputs match. `DkgConfirmer::complete` calls `share_internal` a second time (lines 321–324); if the preprocess set or `key_pair` finalized between the two calls differs in any way (a different validator subset's preprocesses, a different `KeyPair`), the same nonce signs a different FROST challenge `rho`/message, yielding two shares `z1 = d + e·ρ1·c1 + s1·λ`, `z2 = d + e·ρ2·c2 + s2·λ` with identical nonce `d + e·ρ` structure but different binding factors — directly leaking the secret share `s`.

This is reachable by any validator able to publish tributary preprocess messages; no collusion threshold, leaked key, or malicious node is required — the honest validator's own re-execution leaks its key.

### Impact Explanation
Recovery of a validator's MuSig/FROST private key share for the validator-set root key. This key is the root of trust used to confirm DKG results on-chain (`set_keys_message`); share compromise enables an attacker who collects enough shares to forge key-confirmation signatures and hijack validator set key generation. Per `crypto/frost/src/sign.rs` lines 84–92, reuse of a cached preprocess "will enable third-party recovery of your private key share" — the code violates its own documented invariant.

### Likelihood Explanation
The failure requires `share_internal` to run twice under one `attempt` context with differing inputs. `complete()` unconditionally re-runs `share_internal` (line 322), so any divergence between the preprocess set/key_pair observed at `share` time and at `complete` time triggers it. Divergence sources include partial rebuilds (explicitly noted as a bound at lines 46–48), re-derived preprocess maps from `threshold_i_map_to_keys_and_musig_i_map` over differently-populated on-chain data, or a changed `key_pair`. The code's safety rests entirely on a BFT assumption plus a check the authors themselves marked TODO and did not implement, making the trigger an unhandled edge rather than a theoretical one.

### Recommendation
- Delete `CachedPreprocesses` (or mark it consumed) the first time `share_internal` successfully produces a share, and refuse to re-sign if the context was already consumed with different inputs.
- Before producing a share, verify the preprocess commitments derived from the cached seed match the preprocess this validator previously published on-chain for this attempt (the TODO at lines 50–54).
- Alternatively, commit the signed inputs (sorted participant list + `msg` hash) alongside the cached seed and abort if a later call presents different inputs.

### Proof of Concept
1. DKG attempt `a` runs; validator V calls `DkgConfirmer::preprocess`, seed `S` stored under `(b"DkgConfirmer", a)`; V publishes preprocess `P` (nonce commitments `D, E`).
2. V calls `share(preprocesses_A, key_pair_X)` → `share_internal` rebuilds machine from `S` → publishes share `z1` over challenge derived from `preprocesses_A` and `msg_X`.
3. `complete(preprocesses_B, key_pair_Y, shares)` is invoked where `preprocesses_B ≠ preprocesses_A` (e.g., a different subset of validators' preprocesses finalized, or `key_pair_Y ≠ key_pair_X` → different `set_keys_message`). `share_internal` rebuilds the machine from unchanged `S` — same nonces — and `machine.sign` computes a share `z2` under a different binding factor `ρ`/challenge.
4. Any observer computes `ρ1`, `ρ2` from the public preprocess sets and recovers V's secret share from `z1`, `z2` via standard FROST nonce-reuse algebra, per the warning in `crypto/frost/src/sign.rs:84-87` and `spec/cryptography/FROST.md:51-55`.
