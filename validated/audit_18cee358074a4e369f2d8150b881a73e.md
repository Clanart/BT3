### Title
MultiEdit `new_text`/`content` field extraction bypasses `contains`/`regex_match` sensitive-content guard rules via keyword fragmentation - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._extract_field` builds the `new_text`/`content` field for `MultiEdit` by joining each edit's `new_string` with a single space (`' '.join(...)`), an approximation that does not reflect how `MultiEdit` actually applies edits to a file. An attacker who controls the `edits` list of a `MultiEdit` tool call (e.g. via prompt injection steering Claude to write secret-like content) can split a blocked keyword such as `API_KEY` across two `new_string` entries so the space-joined string never contains the contiguous substring, defeating a `contains`/`regex_match` block rule meant to stop secrets from being written to disk.

### Finding Description
The relevant code: [1](#0-0) 
```
elif tool_name == 'MultiEdit':
    if field == 'file_path':
        return tool_input.get('file_path', '')
    elif field in ['new_text', 'content']:
        # Concatenate all edits
        edits = tool_input.get('edits', [])
        return ' '.join(e.get('new_string', '') for e in edits)
```
This value is then checked against a rule's `contains`/`regex_match` condition in `_check_condition`: [2](#0-1) 

The block/warn decision (`evaluate_rules`) then either denies the `PreToolUse` call or allows it, before the real `MultiEdit` tool applies the edits to the file. Because the guard's field-extraction logic is a synthetic space-joined approximation of the edits rather than a faithful reconstruction of the post-edit file content, an attacker can supply:
```
edits: [{"old_string": "A", "new_string": "API_"}, {"old_string": "B", "new_string": "KEY=xxxx"}]
```
The engine computes `"API_ KEY=xxxx"` (with an injected space) which does not match `contains: API_KEY` or a regex such as `API_KEY\s*=`. Yet the real `MultiEdit` tool operates on `old_string`/`new_string` pairs applied independently at their respective match locations in the target file — nothing in the tool's actual behavior guarantees a space between fragments, so if the two edits' target locations are adjacent in the file (a condition fully controlled by the attacker via the chosen `old_string` values and file layout), the resulting on-disk content can be the contiguous, un-fragmented secret string `API_KEY=xxxx`. The hook's detection therefore diverges from ground truth and the block rule never fires.

The `e.get('new_string', '')` default itself is not exploitable in isolation (a missing `new_string` key would also mean the real edit writes nothing), but it is part of the same naive-concatenation design that makes the detection logic disconnected from the real MultiEdit semantics.

### Impact Explanation
This breaks the intended guarantee of a hookify sensitive-content block rule (e.g. "block any Edit/MultiEdit that would write `API_KEY`, private keys, or other secret markers to a file"). An attacker who can influence the shape of a MultiEdit tool call (through prompt injection in repository content, issue/PR text, or other automation-driven content Claude ingests) can trivially fragment the flagged token across two `edits[]` entries and get the write approved by the `PreToolUse` hook, resulting in a secret being written to a file that the guard was specifically configured to prevent. This is a guard/trust-boundary bypass of a security control the repository owner explicitly configured via hookify rules, not merely a false negative in a nice-to-have lint.

### Likelihood Explanation
Feasibility is high and requires no privilege beyond the normal ability to get Claude to issue a `MultiEdit` call with attacker-influenceable content (a common outcome of prompt injection in agentic coding flows). The exploit requires only knowledge of the guard's exact keyword/regex (typically documented in the project's own hookify rule config, which is often visible in the repo) and structuring two adjacent replacements. No exception handling, race condition, or timing is needed — it is a deterministic string-matching gap.

### Recommendation
Reconstruct the field value from MultiEdit edits in a way that matches actual post-application semantics instead of joining with an arbitrary separator: either (a) join with an empty string) and also test each adjacent pair combination, or (b) simulate applying each `old_string -> new_string` replacement against `file_path`'s current contents (reading the file) and check the resulting content against rules, or at minimum (c) check each `new_string` individually AND run the check again against `''.join(...)` plus check overlapping windows (e.g., checking the concatenation of every pair of adjacent `new_string`s without a separator) so fragmented keyword injection cannot slip past the boundary.

### Proof of Concept
Unit test for `plugins/hookify/core/rule_engine.py`:
```python
from hookify.core.rule_engine import RuleEngine
from hookify.core.config_loader import Rule, Condition

def test_multiedit_keyword_fragmentation_bypasses_guard():
    rule = Rule(
        name="block-secret",
        enabled=True,
        event="pretooluse",
        action="block",
        conditions=[Condition(field="content", operator="contains", pattern="API_KEY")],
        message="Blocked: secret content detected"
    )
    engine = RuleEngine()

    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "MultiEdit",
        "tool_input": {
            "file_path": "config.py",
            "edits": [
                {"old_string": "A", "new_string": "API_"},
                {"old_string": "B", "new_string": "KEY=supersecret"},
            ],
        },
    }

    result = engine.evaluate_rules([rule], input_data)
    # Expected (per intended guard design): block
    # Actual (bug): {} (allowed) because extracted field is "API_ KEY=supersecret"
    assert result == {}, "Guard was bypassed via keyword fragmentation across MultiEdit edits"
```
This demonstrates that `_extract_field`'s `' '.join(...)` on `new_string` values allows a `contains: API_KEY` rule to be silently bypassed by splitting the token across two edit entries, even though the eventual on-disk MultiEdit result can contain the contiguous flagged string.
