Audit Report

## Title
Ancestor-hashes repair reaches "duplicate confirmed" agreement from spoofable, unauthenticated UDP responses keyed only by source address, with no signature or stake weighting - (File: core/src/repair/duplicate_repair_status.rs)

## Summary
`AncestorRequestStatus::add_response` in `core/src/repair/duplicate_repair_status.rs` deduplicates and counts ancestor-hash responses solely by UDP source `SocketAddr`, and finalizes a `DuplicateAncestorDecision` once `get_minimum_ancestor_agreement_size()` distinct addresses report the same `(Slot, Hash)` chain. The response-handling path in `ancestor_hashes_service.rs` verifies only packet well-formedness, an outstanding nonce, and a response-size bound (`AncestorHashesRepairType::verify_response`), but never checks a signature over the `AncestorHashesResponse::Hashes` payload tied to the claimed sender identity, unlike repair *requests*, which are signed and verified via `ServeRepair::verify_signed_packet`.

## Finding Description
`add_response` keys de-duplication and agreement counting purely by `from_addr: &SocketAddr`: [1](#0-0) . Once `validators_with_same_response.len()` reaches `get_minimum_ancestor_agreement_size().min(self.sampled_validators.len())`, the code calls `handle_sampled_validators_reached_agreement`, treating the agreed `(Slot, Hash)` list as ground truth for repair/dump decisions: [2](#0-1) .

The statistical justification documented in code explicitly assumes the sampled responses come from distinct, independent validators: [3](#0-2) .

The response ingestion path (`verify_and_process_ancestor_response`) only deserializes the packet, checks for no trailing garbage, and validates the nonce via `outstanding_requests.register_response`, then forwards `hashes` and `from_addr` straight into `add_response` — no signature check on the `AncestorHashesResponse::Hashes` payload occurs anywhere in this function: [4](#0-3) . The only content-level validation performed by `register_response` is `status.request.verify_response(response)`, which for `AncestorHashesRepairType` merely bounds the number of ancestor entries (`MAX_ANCESTOR_RESPONSES`) — it does not check any signature: [5](#0-4) .

This is asymmetric with how repair *requests* are handled: `ServeRepair::verify_signed_packet` cryptographically verifies the sender's identity signature over the request payload and rejects legacy/unsigned request variants: [6](#0-5) . No equivalent signature verification exists for `AncestorHashesResponse::Hashes` on the requester side. Since UDP has no source-address authentication, an attacker capable of spoofing source IPs can inject fabricated `AncestorHashesResponse::Hashes` packets appearing to originate from multiple entries in the requester's `sampled_validators` set, as long as the packet's nonce matches an outstanding request (a 32-bit space, though tied to a specific request/slot the attacker would need to observe or guess).

## Impact Explanation
If the attacker satisfies `MINIMUM_ANCESTOR_AGREEMENT_SIZE` distinct spoofed-address responses carrying a consistent fabricated `(Slot, Hash)` ancestor chain, `handle_sampled_validators_reached_agreement` produces a `DuplicateAncestorDecision` (e.g., `EarliestMismatchFound`) derived entirely from attacker-supplied data. This feeds into `AncestorRequestDecision::slot_to_repair`, which can direct `ReplayStage`/repair machinery to dump the locally correct fork and repair toward an attacker-chosen `(Slot, Hash)` pair — a false-rooting/false-acceptance class fault against the local node's chain state, matching the "repair" target scope for false execution/rooting/acceptance.

## Likelihood Explanation
Exploitation requires the attacker to (1) know or guess the `SocketAddr`s selected into `sampled_validators` for a specific ancestor-hashes request, and (2) spoof UDP source addresses matching enough of those addresses while also matching the correct nonce for that outstanding request. Both are achievable without any stake, private key, or privileged role — purely via unauthenticated UDP packet injection — but require a favorable network position (ability to spoof source IPs toward the victim) and either observation or prediction of the request's sampled peer set and nonce, making this a plausible but non-trivial network-level attack rather than a wallet-level or single-packet trivial exploit.

## Recommendation
Bind ancestor-hashes responses to a verifiable identity: require the response to carry (or be wrapped in) a signature from the responding validator's identity keypair over the payload and nonce, verified against the pubkey associated with the corresponding `sampled_validators` entry, so `add_response` counts agreement by verified pubkey instead of raw `SocketAddr`. Consider stake-weighting agreement (as already done via `DUPLICATE_THRESHOLD` elsewhere in the repair path) instead of a flat unauthenticated-address count.

## Proof of Concept
1. Node `V` sends `AncestorHashes(slot)` requests to sampled peers, recording `AncestorRequestStatus.sampled_validators` keyed by `SocketAddr` (`core/src/repair/duplicate_repair_status.rs` L181-194) and an outstanding nonce (`core/src/repair/outstanding_requests.rs` L20-44).
2. Attacker crafts `get_minimum_ancestor_agreement_size()` UDP packets, each an `AncestorHashesResponse::Hashes(fake_chain)` plus the matching nonce, with spoofed source addresses matching distinct `sampled_validators` entries.
3. `verify_and_process_ancestor_response` accepts each packet since nonce/size checks pass with no signature verification (`ancestor_hashes_service.rs` L378-424; `outstanding_requests.rs` L60-94), and `add_response` records them as distinct validator responses by `SocketAddr` (`duplicate_repair_status.rs` L203-223).
4. Once the threshold count is reached, `handle_sampled_validators_reached_agreement` runs on the fabricated chain and can emit a repair decision built entirely from attacker data (`duplicate_repair_status.rs` L225-236, L484-511).

A reproducible unit test can extend `test_add_response_invalid_peer`/`run_add_multiple_correct_and_incorrect_responses` in `core/src/repair/duplicate_repair_status.rs` (L603-720) to demonstrate that `add_response` accepts and finalizes agreement from arbitrary distinct `SocketAddr`s with no identity verification, confirming the missing signature-binding gap.

    pub fn register_response<R>(
        &mut self,
        nonce: u32,
        response: &S,
        now: u64,
        success_fn: impl Fn(&T) -> R,
    ) -> Option<R> {
        let mut should_delete = false;
        let response = self.requests.get_mut(&nonce).and_then(|status| {
            if status.num_expected_responses == 0 {
                // No more expected responses
                return None;
            }

            if now >= status.expire_timestamp || !status.request.verify_response(response) {
                // Invalid/expired response should invalidate this nonce.
                should_delete = true;
                return None;
            }

            status.num_expected_responses -= 1;
            if status.num_expected_responses == 0 && status.metadata.is_none() {
                // No metadata, and no more expected responses safe to delete eagerly.
                should_delete = true;
            }
            Some(success_fn(&status.request))
        });

        if should_delete {
            self.requests
                .pop(&nonce)
                .expect("request must exist when marked for deletion");
        }
        response
    }

                }
