### Title
Scanner reports dust outputs as spendable received funds that the wallet can never spend - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report's bug class is "the protocol assumes the counterparty returns a standard-shaped value and breaks on non-standard ones" — in `Vault_Base_ERC20`, an ERC20 that returns nothing instead of `bool` makes the vault unusable for that token. The analog in Serai's Bitcoin wallet is `Scanner::scan_transaction`, which reports any output paying to a watched `script_pubkey` as a spendable `ReceivedOutput` without checking that the output is actually spendable — most concretely, outputs whose value is below the dust limit.

### Finding Description
`Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) matches received outputs purely on `output.script_pubkey` and pushes a `ReceivedOutput` carrying the output's full `TxOut` value:

```rust
// networks/bitcoin/src/wallet/mod.rs:205-211
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```

There is no check on `output.value`. Meanwhile `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256) enforces the `DUST = 546` minimum **only on payments** (send.rs:165-169); it never validates that *inputs* are non-dust. A received output with `value < 546` sats is therefore:

- Reported to the caller as funds received (`ReceivedOutput::value()`, mod.rs:116-118).
- Practically unspendable: spending it requires a transaction whose fee alone exceeds the input's value, and even if included as an input alongside others, Bitcoin Core's dust policy (`MAX_STANDARD_TX_WEIGHT` / dust relay rules the code itself cites at send.rs:27-32) makes transactions creating dust outputs non-standard — the dust input can never economically be recovered.

This is the same failure shape as the source report: an input that is "valid" on the wire (a real UTXO paying to Serai's key, just as a no-return ERC20 is a real ERC20) is accepted into the protocol's accounting while the downstream machinery cannot actually operate on it. The result is funds reported received that are not spendable.

The coinbase-maturity variant of this class is explicitly documented (mod.rs:218-220 tells callers to post-process coinbase outputs), but nothing in `Scanner`, `ReceivedOutput`, or `SignableTransaction` documents or enforces a minimum input value, so the dust case is an undocumented gap.

### Impact Explanation
An unprivileged third party can send dust-valued outputs to a Serai-registered Taproot script (they need only the public `script_pubkey`, which is visible on-chain after any prior deposit). The scanner will report these as received balance. Those sats are effectively burned — they cannot be spent without paying more in fees than they are worth, and the wallet provides no mechanism to filter them. If a downstream protocol credits deposits based on `Scanner` output, an attacker can inflate perceived deposits, or honest users can be left with permanently stranded reported balance.

### Likelihood Explanation
Triggering requires only that someone broadcast a normal Bitcoin transaction paying a dust amount to the watched script — fully within "Bitcoin transactions they send" per the reachability rules. Dust outputs to known addresses are common (spam/dusting attacks are routine on Bitcoin), so this is not an exotic condition.

### Recommendation
In `Scanner::scan_transaction`, skip outputs whose `output.value.to_sat() < DUST` (or a configurable spendability threshold), or surface a `is_spendable`/minimum-value flag on `ReceivedOutput` so callers can distinguish credited-but-unspendable outputs. Alternatively, `SignableTransaction::new` could accept dust inputs only when their marginal contribution exceeds their marginal fee cost — but filtering at scan time is simpler and matches the documented coinbase post-processing model.

### Proof of Concept
1. Construct a `Scanner` for a valid even Taproot key: `Scanner::new(key)`.
2. Broadcast a transaction with an output `{ value: 100, script_pubkey: <watched p2tr script> }` (100 < `DUST` = 546).
3. `scanner.scan_transaction(&tx)` returns one `ReceivedOutput` with `value() == 100`.
4. Any attempt to spend it via `SignableTransaction::new` requires `input_sat >= payment_sat + needed_fee`; with only dust inputs this fails `NotEnoughFunds`, and including it alongside other inputs yields a transaction whose marginal fee exceeds the input's value — the reported funds can never be spent at a profit.
