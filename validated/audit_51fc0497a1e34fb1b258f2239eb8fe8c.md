## Title
`GetRequestsWithProof.address` reputation-mint field carries no signature, letting anyone self-credit relayer reputation for another party's proof work - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
`pallet-state-coprocessor::handle_get_requests` mints `ReputationAsset` (the token that determines Collator eligibility) to whatever account is placed in the `address` field of the caller-supplied `GetRequestsWithProof` message. That message is submitted as an **unsigned** extrinsic (`ensure_none(origin)`), and neither `validate_unsigned` nor `handle_get_requests` binds `address` to any signature, sender, or the entity that produced the state proofs. This is the same missing-authentication-root pattern as the `StoreChunksRequest` report: a message that determines attribution/crediting carries no signature field tying the claimed identity to the actual work performed.

### Finding Description
`GetRequestsWithProof` is defined with a plain, unauthenticated `address: Vec<u8>` field described as "Address that should be credited with fees": [1](#0-0) 

It is dispatched through `handle_unsigned`, which uses `ensure_none(origin)` — i.e. this is a fully unsigned transaction, with no on-chain signer at all: [2](#0-1) 

`validate_unsigned` re-runs `handle_get_requests` and only dedups on the hash of the requests being fetched; it does **not** validate `address` against any signature or relayer identity: [3](#0-2) 

Inside `handle_get_requests`, after the (legitimate) source/response membership and state proofs verify, the pallet mints reputation directly to `address` with no further check that this account actually produced the proofs or did any of the relaying work: [4](#0-3) 

The proofs themselves (`source` and `response` `Proof`s) are membership/state proofs over already-public source- and destination-chain data — anyone can independently fetch the same storage proofs from public RPC endpoints, exactly as the tesseract relayer does when constructing this message: [5](#0-4) 

Because the extrinsic is unsigned, there is nothing preventing an attacker from observing a pending/mempool `handle_unsigned` call (or independently reconstructing valid proofs for the same requests) and resubmitting an equivalent message with `address` set to their own account before or in place of the genuine relayer. The reputation credit — which the docs confirm is the controlling factor for Collator selection — lands on the wrong beneficiary.

Reputation Asset is explicitly the mechanism that ranks and selects Collators each session: [6](#0-5) 

### Impact Explanation
This breaks the "reward claims ... must move exactly once and only to the rightful beneficiary" invariant. Although the reputation token is soulbound (non-transferable), it directly gates eligibility to become a block-producing Collator, which yields further `$BRIDGE` block-production rewards. An attacker who never ran a relayer, never paid gas to actually deliver a `GetResponse`, and never did the real off-chain proof-fetching work for a *live* delivery can still self-mint reputation by resubmitting publicly-derivable proofs with their own `address`, diverting the credit that should go to the relayer that actually serviced the request. This is a logic/attribution attack on the reward-crediting path, not merely a griefing or DoS issue — it lets an unprivileged party manipulate collator-selection standing without performing the corresponding real work, at the expense of the legitimate operator.

### Likelihood Explanation
Likelihood is high for a technically capable actor: the extrinsic is unsigned (no key/permission needed to submit), the proofs required are just standard Merkle/state proofs over public chain state (independently reconstructible or copyable from the mempool/already-broadcast transaction), and `handle_get_requests`/`validate_unsigned` perform no check correlating `address` with a signer, origin, or delivery attribution. The only race is beating (or replaying alongside) the legitimate relayer's submission, which is a purely mechanical/off-chain timing problem, not a cryptographic barrier.

### Recommendation
Bind the credited `address` to cryptographic proof of relayer identity, mirroring how `pallet-relayer`'s `OutboundRequestDeliveryClaim` and `pallet-messaging-incentives`'s `Self::relayer_for(&mw.message)` recover the relayer from a signature rather than trusting a bare field:
- Require `GetRequestsWithProof` to carry a signature (e.g., over the request/response commitments) from the `address` claiming credit, and recover/verify that signature before minting, analogous to `outbound_request_delivery_message` signature verification in `modules/pallets/relayer/src/outbound_request.rs`.
- Alternatively, tie the unsigned extrinsic's `provides` tag / mint eligibility to the actual submitting relayer key registered off-chain (e.g., require a signed wrapper analogous to the `RequestMessage.signer` used elsewhere in the router), so `address` cannot be set to an arbitrary, unauthenticated value.

### Proof of Concept
1. Monitor the network (mempool or public chain events) for a `StateCoprocessor::handle_unsigned` call built by a legitimate relayer for some batch of `GetRequest`s.
2. Independently query the same source-chain membership proof and destination-chain storage proof for the identical `GetRequest`s from public RPC endpoints (as any relayer would via `get_requests.rs`).
3. Construct an equivalent `GetRequestsWithProof { requests, source, response, address: attacker_account }`, substituting `address` with an attacker-controlled account.
4. Submit this as an unsigned extrinsic (`ensure_none` origin — no signature required) before, or as a race against, the legitimate relayer's submission.
5. If it lands first (or the legitimate one is delayed), `handle_get_requests` mints `total_bytes * MintPerByte` reputation to the attacker's account instead of the relayer that actually assembled/served the real-time delivery, per the mint logic at `modules/pallets/state-coprocessor/src/impls.rs:156-185`.

## The Selection Process & What Happens Next

At the beginning of each new session, `pallet-collator-manager` runs its selection logic:

- It fetches the list of all bonded candidates (Stash accounts) from `pallet-collator-selection`.
- For each candidate, it uses the `Controller` storage map to find the linked Controller account.
- It validates that the Controller has registered valid session keys via `pallet-session`.
- It ranks the remaining candidates from highest to lowest based on their Controller's Reputation Asset balance.
- It selects the top candidates to fill the available collator slots for the new session.
