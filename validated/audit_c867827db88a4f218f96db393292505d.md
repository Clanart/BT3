Based on my research, I found a real local analog of the DYAD decimal-scaling bug in the `hyper-fungible-token` pallet's decimal-conversion helpers.

### Title
Asymmetric decimal scaling in `convert_to_erc20`/`convert_to_balance` causes wrong bridged amount when local decimals exceed ERC20 decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `hyper-fungible-token` pallet converts amounts between a local Substrate asset's decimal precision and the corresponding ERC20 token's decimal precision using `saturating_sub` in the exponent. This only produces correct results when `erc_decimals >= local_decimals`. When the local asset has more decimals than the peer ERC20 token, the scaling factor collapses to `10^0 = 1`, silently skipping the required rescale — the exact same "does not adjust decimals properly" bug class as the external DYAD report, but on the cross-chain minting/dispatch path instead of collateral redemption.

### Finding Description
`convert_to_balance` (incoming path, used in `on_accept`/`on_timeout`) and `convert_to_erc20` (outgoing path) both compute their scaling exponent as: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256, erc_decimals: u8, local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions use `erc_decimals.saturating_sub(local_decimals)` as the sole exponent. This is only mathematically valid for the case `erc_decimals >= local_decimals`:
- `convert_to_balance` divides the incoming ERC20-denominated `value` by `10^(erc_decimals - local_decimals)`, which is correct only when scaling *down* (erc precision higher than local).
- `convert_to_erc20` multiplies the local balance by the same exponent, correct only when scaling *up* (erc precision higher than local).

When `local_decimals > erc_decimals` (e.g., a local asset configured with 18 decimals bridging to a 6-decimal ERC20 like USDC), `erc_decimals.saturating_sub(local_decimals)` saturates to `0`, so the exponent becomes `10^0 = 1` — **no scaling is applied at all** in either direction. `convert_to_balance` then under-credits the local beneficiary by a factor of `10^(local_decimals - erc_decimals)`, and `convert_to_erc20` fails to divide down the local amount before it is embedded in the outgoing ISMP `Message.amount`, over-stating the ERC20-side amount by the same factor.

The `Precisions` storage that supplies `erc_decimals` is populated per (asset, contract) pair and there is no runtime assertion anywhere in `on_accept`/`on_timeout`/the dispatch path that `erc_decimals >= local_decimals`, so a legitimately configured pair with `local_decimals > erc_decimals` silently hits the broken branch — no malicious relayer, prover, or governance actor is required, only a normal user calling the pallet's public entry points with a token pair configured this way. ### Impact Explanation
This directly violates the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" invariant:
- On the outgoing (`convert_to_erc20`) leg, when `local_decimals > erc_decimals`, the amount encoded in the cross-chain `Message` to the EVM side is inflated by `10^(local_decimals - erc_decimals)` versus what was actually locked/burned locally — this can drain the EVM-side custody/reserve balance (or mint an unbacked amount) far beyond what the user actually deposited, a direct loss-of-funds / false-amount-acceptance condition.
- On the incoming (`convert_to_balance`) leg for the same misconfigured decimal pair, beneficiaries are under-credited (funds effectively lost to the protocol), and on the `on_timeout` refund path the same broken conversion means refunds don't match the original escrowed amount.

### Likelihood Explanation
The trigger condition (`local_decimals > erc_decimals`) is a normal, expected configuration — many Substrate assets use 18 decimals while common ERC20 stablecoins (USDC/USDT) use 6, and there's no compensating divide branch or decimals-ordering assertion in `impls.rs` or the calling code to prevent it. Any unprivileged user invoking the pallet's public teleport/transfer entry point for such a pair triggers the miscalculation deterministically, with no reliance on a malicious peer, relayer, or governance actor.

### Recommendation
Replace the one-directional `saturating_sub`-based exponent with a proper two-branch scale that both multiplies and divides depending on which side has more decimals, mirroring the fix pattern from the DYAD report:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and the symmetric fix for `convert_to_balance`. Add a unit test covering `local_decimals > erc_decimals` (e.g., local=18, erc=6) for both conversion directions.

### Proof of Concept
1. Governance/config registers a local asset with `local_decimals = 18` and a peer ERC20 contract with `erc_decimals = 6` (stored via `Precisions::<T>::insert`).
2. A user calls the pallet's outgoing dispatch entry point to bridge `1_000_000_000_000_000_000` (1 whole unit, 18 decimals) of the local asset to the EVM side.
3. Internally, `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, giving `1e18 * 10^0 = 1e18` embedded as the ERC20-side `amount` in the outgoing `Message`, instead of the correct `1e18 / 10^12 = 1e6` (1 unit in 6-decimal terms).
4. The EVM-side `HftGateway`/token contract receives an ISMP message instructing it to release/mint `1e18` units of a 6-decimal token — 1,000,000x more value than was actually escrowed on the Substrate side, directly draining bridge custody or minting unbacked supply. [4](#0-3)
