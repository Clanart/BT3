### Title
Missing index in `GeneratorPromotion::complete` proof map causes an unwrapped panic (crash/DoS) on attacker-influenced input - ([File: crypto/dkg/promote/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary
`GeneratorPromotion::complete` validates only the *length* and *upper bound* of the caller-supplied `proofs: &HashMap<Participant, GeneratorProof<C1>>`, then unconditionally indexes it with `.unwrap()` for every participant index `i != params.i()`. Any map containing `n - 1` entries whose keys are all `<= n` but which does not cover every index in `1 ..= n` except the local index triggers an `unwrap` on `None`, panicking the calling process.

### Finding Description [1](#0-0)  checks two properties of the untrusted map:

1. `proofs.len() == n - 1`
2. Every key `i` satisfies `u16::from(i) <= params.n()`

Neither check guarantees that the key set is exactly `{1..=n} \ {params.i()}`. The subsequent loop [2](#0-1)  then does:

```rust
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();
```

A map like `{params.i(), 2, 3, ..., n-1}` (attacker's proof registered under the victim's own index, omitting index `n`) has `n - 1` entries, all keys `<= n`, and panics on `proofs.get(&n)`.

The rest of the dkg crate is careful about this class of issue: `validate_map` in both `crypto/dkg/pedpop/src/lib.rs:57-83` and `crypto/frost/src/lib.rs:50-73` verifies exact key-set membership against `included`, and `ThresholdKeys::new`/`view` validate participant bounds and duplicates before indexing. `complete` is the one path that substitutes length+bounds checks for membership checks and then panics.

This mirrors CVE-2016-5242's shape: a resource (proof map entry) assumed to exist after counting/bounding references is dereferenced unconditionally during a cleanup/finalization routine, turning a malformed multi-party input into a process crash.

### Impact Explanation
Any caller that builds the `proofs` map from messages submitted by the other promotion participants (the documented usage: each participant broadcasts their `GeneratorProof`, keyed by claimed `Participant` index) can be crashed by a participant who submits a validly-encoded proof under an unexpected-but-in-range index, or whose entry displaces another index so that some `i in 1..=n` is absent. The panic aborts key promotion entirely; in a host that runs promotion inside a long-lived process (key rotation/tweak flows using `promote`/`recover` infrastructure), this is a denial of service of the validator/processor node — matching the external report's availability-only Medium severity.

### Likelihood Explanation
The trigger requires only that a co-participant's proof be recorded under a key the caller did not expect (e.g., the caller keys the map by a self-reported index, or an attacker withholds their entry while another index is duplicated). `proofs.len() == n - 1` is still satisfiable. Medium likelihood: it needs a malicious or misbehaving DKG participant and a caller that trusts sender-supplied indexes, but no cryptographic breakage.

### Recommendation
Replace the length/bounds checks with an exact-membership check: for each `i in 1 ..= params.n()` where `i != params.i()`, require `proofs.contains_key(&i)` (or reuse `dkg::validate_map`-style logic), and replace `proofs.get(&i).unwrap()` with an error return such as `PromotionError::MissingParticipant(i)`.

### Proof of Concept
```rust
// t == n == 3 promotion; our index is 1
let base: ThresholdKeys<C1> = /* valid keys */;
let (promo, _our_proof) = GeneratorPromotion::<C1, C2>::promote(&mut rng, base.clone());

// Attacker-controlled map: n - 1 = 2 entries, all keys <= n,
// but index 3 is missing and our own index 1 is present instead.
let mut proofs: HashMap<Participant, GeneratorProof<C1>> = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof_under_key_1);
proofs.insert(Participant::new(2).unwrap(), honest_proof_from_2);

// proofs.len() == n - 1 == 2  -> passes
// all keys <= 3               -> passes
// proofs.get(&Participant(3)) -> None -> panic
promo.complete(&proofs); // thread panics on `.unwrap()` at promote/src/lib.rs:146
```

Uncertainty note: whether production callers key the `proofs` map by sender-claimed indexes (making this remotely triggerable) versus by authenticated positions (making it defensive-only) could not be fully confirmed within scope; the panic itself is unconditional in the in-scope code.
