Based on the evidence gathered, I found a direct local analog in the Tron variant of the intent-settlement contract.

### Title
Escrow ledger credited with nominal amount instead of actual tokens received for fee-on-transfer tokens, causing under-collateralized escrow - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron build of `IntentGatewayV2.placeOrder` credits the `_orders` escrow mapping with the caller-supplied (fee-reduced) amount without ever measuring the tokens the contract actually received via `safeTransferFrom`. This is the same broken invariant as the `VestingEscrowSimple` report: the contract records a distributable balance that is not verified against the tokens actually held.

### Finding Description
In the non-predispatch branch of `placeOrder`, the contract does: [1](#0-0) 
```
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
// Store reduced amount (after protocol fees) in escrow
_orders[commitment][token] += reducedInputs[i].amount;
```
There is no before/after balance check here. Compare this with the fixed EVM path, which explicitly measures actual receipt to defend against fee-on-transfer tokens: [2](#0-1) 
```
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```
and the associated fee-on-transfer regression tests, e.g. `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, which assert the escrow must equal the actually-received balance: [3](#0-2) 

The Tron contract lacks this correction. For any fee-on-transfer or deflationary ERC20 configured as an order input, `_orders[commitment][token]` is incremented by the pre-fee `reducedInputs[i].amount` while the contract's actual token balance increases by less. Because `_orders` is a shared ledger across all orders denominated in the same token, this creates a systemic shortfall: the sum of values recorded in `_orders[*][token]` can exceed the contract's real `balanceOf(token)`.

### Impact Explanation
This is unauthorized/incorrect fund accounting inside bridge custody: an unprivileged user placing an order with a fee-on-transfer token inflates the escrow ledger beyond what is actually custodied. When solvers later fill orders and the contract pays out based on the `_orders` mapping value (as in the destination-side redeem/fill flow used elsewhere in this contract), the shortfall means either (a) a legitimate solver/beneficiary cannot be paid in full because the token balance is insufficient, or (b) whichever order is settled first drains real tokens backing other still-outstanding orders, causing those later orders to fail/lock or be under-collateralized — a direct loss/lock of bridged funds attributable purely to normal user interaction with `placeOrder`, no relayer or admin compromise required.

### Likelihood Explanation
Likelihood is high for any deployment that lists a fee-on-transfer or rebasing token as a supported input asset on the Tron deployment path, since `placeOrder` is a fully public, unprivileged entrypoint and the discrepancy triggers deterministically on every such transfer — no race condition or malicious relayer needed.

### Recommendation
Apply the same before/after balance measurement used in the fixed `evm/src/apps/IntentGatewayV2.sol::placeOrder` (lines 289–291) to the Tron variant: measure `balanceOf(address(this))` before and after `safeTransferFrom`, and credit `_orders[commitment][token]` (and the commitment/fee computation derived from it) using the actual delta received rather than the caller-supplied nominal amount.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` with a 1% fee-on-transfer ERC20 as a supported input token.
2. User calls `placeOrder` with `inputs[0].amount = 1000e18` for that token; `safeTransferFrom` delivers only `990e18` to the contract (1% burned in transfer), but `_orders[commitment][token]` is set to `reducedInputs[i].amount` computed from the full `1000e18` (minus protocol fee if any) — a value backed by only `990e18` of actual balance.
3. Repeat with a second order using the same token; the contract balance grows by `990e18` per order while the `_orders` ledger total grows based on the nominal `1000e18`-derived amounts, compounding the shortfall across orders sharing the token.
4. When the destination-side redeem/fill logic pays out based on `_orders[commitment][token]`, the contract lacks sufficient real token balance to honor all outstanding escrow records, causing a payout failure or fund misallocation between orders — reproducing the exact "initialized/escrowed without sufficient backing tokens" pattern from the external report, just triggered through fee-on-transfer token transfer semantics instead of a bypassed factory.

Note: I was unable to fully inspect the redeem/withdrawal function body (`RedeemEscrow` handling) in `evm/tron/contracts/apps/IntentGatewayV2.sol` before running out of tool iterations, so the exact downstream payout mechanics (whether it reverts safely or actually allows cross-order fund drain) are inferred from the equivalent flow in `evm/src/apps/IntentGatewayV2.sol` and the shared `_orders` mapping structure, not directly confirmed line-by-line in the Tron file.
