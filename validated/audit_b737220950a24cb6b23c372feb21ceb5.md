### Title
Unhandled `CommitIdentity.parseIdentity` throw from attacker-crafted commit ident string crashes commit-history loading - ([File: app/src/models/commit-identity.ts])

### Summary
`CommitIdentity.parseIdentity` throws a raw `Error` when a git author/committer identity string doesn't match its expected regex, and `getCommits`/`getAuthors` in `app/src/lib/git/log.ts` call it unguarded while mapping over every parsed commit from `git log` output of a repository the user cloned or fetched.

### Finding Description
`CommitIdentity.parseIdentity` parses the `%an <%ae> %ad` formatted string produced by `git log` and requires the trailing date portion to match `(\d+) (\+|-)?(\d{2})(\d{2})`. If it doesn't match, it throws `Couldn't parse identity ${identity}` [1](#0-0) .

This is invoked directly, with no try/catch, inside `getCommits`'s `.map()` over every commit returned by `git log`: [2](#0-1) 
and again in `getAuthors`: [3](#0-2) 

Git commit objects are just content-addressed blobs; an attacker who controls a repository (one the victim clones, or that is fetched via a remote/proxy) can hand-craft a commit object (e.g. via `git hash-object -t commit -w`) with an author/committer line whose date field is missing or non-numeric, or where the `<`/`>` delimiters are arranged so the trailing capture group never resolves to digits. Because Desktop trusts whatever git returns from the object store and only tolerates *some* malformed idents (e.g. broken email addresses, per the existing tests) — see the passing test cases for `<Markus >Olsson>` — but not a malformed/missing date suffix, a corrupt or adversarially constructed commit reaching this code path throws an uncaught exception during history loading rather than degrading gracefully.

### Impact Explanation
Since `parseIdentity` is called synchronously for every commit while building the `Commit` list, a single malicious/corrupt commit anywhere in the fetched/cloned repository's history is enough to make `getCommits` throw. This function backs commit-history loading, blame, and related commit-identity consumers, so opening or refreshing history for a repository containing such a commit results in an unhandled exception that surfaces as a crash/error state in the renderer rather than a rejected UI action — matching the same bug class as the referenced MetaMask report (unsanitized/malformed data reaching a `throw`-on-invalid-input parser with no upstream normalization or guard), except here the untrusted input source is an attacker-controlled git object rather than keyboard input.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control repository content that the victim clones/fetches (a git remote or malicious repo the victim is lured to open in Desktop) and to hand-craft a raw commit object with a malformed ident line, which is straightforward with plumbing commands (`git hash-object`, `git commit-tree`) but does not require any git configuration exploit or social engineering beyond "clone this repo." Ordinary git tooling (`git commit`) always produces a well-formed ident, so this can't happen accidentally — it requires deliberate crafting, which fits the "attacker controls a cloned/fetched repository" impact category.

### Recommendation
Make `CommitIdentity.parseIdentity` tolerant of malformed input instead of throwing, e.g. return a best-effort `CommitIdentity` with `Invalid Date`/empty fields (mirroring how the fiat-input fix normalized bad input at the single ingestion point instead of failing later), and wrap the `.map()` calls in `getCommits`/`getAuthors` to skip or sanitize any commit that still fails to parse, so a single adversarial commit cannot abort loading of the entire history.

### Proof of Concept
1. Attacker creates a git repository and adds a low-level commit object with a corrupted author line, e.g. via:
   `printf 'tree <sha>\nauthor Evil Attacker <evil@evil.com>\ncommitter Evil Attacker <evil@evil.com>\n\nmalicious' | git hash-object -t commit -w --stdin`
   ensuring the author/committer line omits the trailing numeric timestamp/timezone (or otherwise fails the `(\d+) (\+|-)?(\d{2})(\d{2})` capture).
2. Attacker points a branch/tag at this commit and publishes the repository (or a proxy/mirror serving fetch responses) for the victim to clone.
3. Victim clones the repository in GitHub Desktop and opens the History tab (or Desktop calls `getCommits` on refresh).
4. `git log --format=... %an <%ae> %ad ...` returns the malformed ident string for that commit; `CommitIdentity.parseIdentity` throws inside the unguarded `.map()` in `getCommits` [2](#0-1) , producing an unhandled exception while loading history for the repository.

Note: I was not able to trace, within the indexed portion of the codebase, whether the caller of `getCommits` in `app-store.ts`/`git-store.ts` wraps this specific call in a top-level try/catch that would downgrade this to a benign toast versus a full unhandled-rejection crash screen — confirming the exact end-user crash surface would require reviewing `app/src/lib/stores/app-store.ts` and `app/src/lib/stores/git-store.ts` call sites in full, which is recommended before treating this as fully confirmed.

  public static parseIdentity(identity: string): CommitIdentity {
    // See fmt_ident in ident.c:
    //  https://github.com/git/git/blob/3ef7618e6/ident.c#L346
    //
    // Format is "NAME <EMAIL> DATE"
    //  Markus Olsson <j.markus.olsson@gmail.com> 1475670580 +0200
    //
    // Note that `git var` will strip any < and > from the name and email, see:
    //  https://github.com/git/git/blob/3ef7618e6/ident.c#L396
    //
    // Note also that this expects a date formatted with the RAW option in git see:
    //  https://github.com/git/git/blob/35f6318d4/date.c#L191
    //
    const m = identity.match(/^(.*?) <(.*?)> (\d+) (\+|-)?(\d{2})(\d{2})/)
    if (!m) {
      throw new Error(`Couldn't parse identity ${identity}`)
    }
