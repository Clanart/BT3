### Title
Duplicate serialized `ReceivedOutput`s are double-counted as transaction inputs - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

`ReceivedOutput::read` deserializes an offset, claimed `TxOut`, and claimed `OutPoint` without authenticating that the `TxOut` is actually the referenced chain output. `SignableTransaction::new` then accepts these caller-supplied records, sums every claimed value, and emits every supplied `OutPoint` as an input without rejecting duplicates. Consequently, the same serialized received output can be decoded twice and counted twice, while `SignableTransaction::multisig` still authorizes both inputs because it checks only that each claimed `script_pubkey` matches the offset-derived threshold key.

### Finding Description

The externally reachable input path is:

1. Untrusted bytes are supplied to `ReceivedOutput::read`, which accepts an arbitrary `(offset, TxOut, OutPoint)` tuple with no duplicate or chain-authenticity check. [1](#0-0) 
2. `SignableTransaction::new` sums `input.output.value` over the whole input vector. [2](#0-1) 
3. The same function converts each `ReceivedOutput.outpoint` into a `TxIn` without checking whether that outpoint has already been supplied. [3](#0-2) 
4. `SignableTransaction::multisig` validates only that the offset-derived group key produces the claimed `script_pubkey`; it does not compare the claimed `TxOut` or outpoint against blockchain data. [4](#0-3) 
5. Both duplicate inputs are then signed under `Prevouts::All`, producing signatures for a transaction containing the same UTXO twice. [5](#0-4) 

This is the same accounting flaw as the reference issue: a balance-like value is calculated from attacker-controlled data once, while the underlying asset represented by that data can be introduced repeatedly.

### Impact Explanation

An unprivileged party who can supply serialized `ReceivedOutput`s to wallet or signing code can make the wallet account for one UTXO multiple times. A payment can therefore pass the `input_sat >= payment_sat + needed_fee` check even though the unique outpoints do not contain the claimed balance.

The constructed transaction also passes the local key/script check and reaches the FROST signing path, so the threshold participants are induced to sign an unintended transaction containing duplicate inputs. The resulting transaction is not consensus-valid, but the incorrect accounting occurs before signing and the signatures are still produced for the duplicated-input sighashes.

### Likelihood Explanation

The attack requires no malicious validator, compromised node, leaked key, invalid curve implementation, or colluding threshold. It requires only that duplicate copies of attacker-controlled bytes accepted by `ReceivedOutput::read` be included in the `inputs` vector passed to `SignableTransaction::new`.

A valid scanned output can be serialized, submitted twice, and parsed into two indistinguishable `ReceivedOutput`s. Since no duplicate-outpoint rejection exists, both copies are counted and signed.

### Recommendation

Reject duplicate `OutPoint`s in `SignableTransaction::new` before calculating `input_sat` or constructing `tx_ins`. A `BTreeSet`/`HashSet` keyed by `input.outpoint` should return a new `TransactionError::DuplicateInput`.

More importantly, do not treat deserialized `ReceivedOutput` values as authenticated chain data. Either:

- make `ReceivedOutput` constructible only through `Scanner::scan_transaction`/`scan_block`, and avoid accepting it across an untrusted serialization boundary; or
- revalidate each referenced outpoint against the chain before using the claimed `TxOut` value in funding and sighash calculations.

These checks should happen before any payment, fee, or change arithmetic.

### Proof of Concept

```rust
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction};

// `bytes` are attacker-controlled serialized output data.
// For example, they may be two copies of one legitimately scanned output.
let first = ReceivedOutput::read(&mut bytes_first.as_slice()).unwrap();
let second = ReceivedOutput::read(&mut bytes_second.as_slice()).unwrap();

// Both records can reference the same outpoint and claim the same value.
assert_eq!(first.outpoint(), second.outpoint());

let payment_value = first.value() + second.value() - sufficient_fee;
let tx = SignableTransaction::new(
  vec![first, second],
  &[(payment_script, payment_value)],
  None,
  None,
  fee_per_vbyte,
)
.unwrap();

// Local multisig validation succeeds because both claimed scripts match
// the threshold key. The resulting Transaction has the same previous_output
// in inputs[0] and inputs[1], so it is consensus-invalid despite being
// counted as twice the underlying funds.
let machine = tx.multisig(&threshold_keys).unwrap();
```

The decisive defect is that `input_sat` counts both records while `tx_ins` preserves both references to the same outpoint. [6](#0-5)
