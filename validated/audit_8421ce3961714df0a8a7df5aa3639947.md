### Title
`SignableTransaction` omits the OP_RETURN output from weight/fee calculation, producing under-priced transactions that can fail to relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds `tx_outs` including an attacker-influenced `OP_RETURN` data output, but `calculate_weight_vbytes` is only ever called with `payments` and `change` — the OP_RETURN output is never iterated into the weight/vbytes estimate. The resulting `needed_fee`, minimum-fee check, and `MAX_STANDARD_TX_WEIGHT` check are all computed against a transaction smaller than the one actually signed.

### Finding Description
`SignableTransaction::new` pushes an OP_RETURN output carrying up to 80 bytes of caller-supplied `data` into `tx_outs` [1](#0-0) . However, both calls to `calculate_weight_vbytes` pass only `payments` (and optionally `change`), so the constructed estimation transaction never includes the OP_RETURN output [2](#0-1) [3](#0-2) . Inside `calculate_weight_vbytes`, `tx.output` is built solely from `payments` plus the optional change output [4](#0-3) . The under-estimated `vbytes` is then used for `needed_fee` [5](#0-4)  and the weight limit check [6](#0-5) , while `sign` commits `SighashType::Default` signatures over the real, larger transaction [7](#0-6) .

### Impact Explanation
An OP_RETURN output adds ~90 non-witness vbytes (8-byte value + script up to ~82 bytes) that are completely unaccounted for. Because the change output absorbs the residual (`input_sat - payment_sat - fee_with_change`), the signed transaction pays exactly the under-estimated `needed_fee`. The effective fee rate can fall below `DEFAULT_MIN_RELAY_TX_FEE` (1 sat/vB) even though the check at line 211 passed against the smaller estimated size — e.g. a 1-input/1-payment/OP_RETURN tx estimated at ~200 vB but actually ~290 vB. Such a transaction is validly signed but non-standard/unrelayable, leaving the spent inputs' funds stuck (the multisig has already produced a broadcastable-but-unrelayable signature, and a replacement requires a new signing round). This is a reachable DoS on Serai's Bitcoin output pipeline: the `data` field is populated from external request data (e.g. burn/`InInstruction` payloads fed through the signing plan), so an unprivileged party supplying a near-80-byte data field maximizes the fee-rate shortfall.

### Likelihood Explanation
Any signing plan that includes `data` (OP_RETURN) and a change output produces a transaction whose realized fee rate is strictly lower than the requested `fee_per_vbyte`; for small transactions at low fee rates the realized rate falls below minimum relay policy and the transaction will not propagate. No malicious validator or collusion is needed — the defect is entirely in local size estimation triggered by the data-carrying output.

### Recommendation
Include the OP_RETURN output in the size estimation: pass the fully constructed `tx_outs` (or add the `data` output) into `calculate_weight_vbytes` before computing `needed_fee`, the minimum-fee check, and the `MAX_STANDARD_TX_WEIGHT` check. Alternatively, compute `needed_fee` after `tx_outs` is finalized by measuring `tx.weight()` on the actual transaction.
