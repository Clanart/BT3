### Title
Fee-on-transfer reward tokens cause reward-per-token over-crediting and permanent freezing of later claimants' yield - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`, `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`BaseRewardPool._provisionReward()` (and its identical counterparts in `BaseRewardPoolV2.sol` and `mWOMSVBaseRewarder.sol`) pulls a reward token via `safeTransferFrom(msg.sender, address(this), _amountReward)` and then unconditionally credits the full `_amountReward` into `historicalRewards` and `rewardPerTokenStored`, without verifying that the contract's balance actually increased by that amount. [1](#0-0) 

### Finding Description
The public, unprivileged `donateRewards()` function lets any wallet holding a registered reward token add rewards to a pool: [2](#0-1) 

This calls `_provisionReward()`, which performs the transfer and then updates the global `rewardPerTokenStored` accumulator using the nominal `_amountReward` passed in, not the amount actually received: [1](#0-0) 

If the reward token charges a transfer fee (or otherwise delivers less than the requested amount, e.g. rebasing/deflationary tokens), the contract's real token balance increases by less than `_amountReward`, yet the per-token reward accounting is inflated as if the full amount arrived. `queueNewRewards()` (the manager-only counterpart) has the identical flaw, so even manager-provisioned rewards suffer the same accounting mismatch if the token has a fee. [3](#0-2) 

This is the same root cause as Sherlock M-11 in `DonationVotingMerkleDistributionVaultStrategy._afterAllocate()`: crediting an accounting ledger with the pre-fee transfer amount instead of the actual post-fee balance delta, oversubscribing claimable amounts relative to real custody.

`BaseRewardPoolV2._provisionReward()` has the exact same pattern: [4](#0-3) 

as does `mWOMSVBaseRewarder._provisionReward()`: [5](#0-4) 

### Impact Explanation
`rewardPerTokenStored` is a global divisor-based accumulator shared across all stakers; `earned()` computes each user's share proportionally from this value. Once `rewardPerTokenStored` is inflated beyond what the contract actually holds, the sum of all users' `earned()` claims exceeds the pool's actual reward-token balance. `getReward()` pays out via plain `safeTransfer(_receiver, reward)` on a first-come-first-served basis: [6](#0-5) 

Users who claim early receive their full expected share; the pool then runs out of tokens before every accrued claim can be paid, permanently freezing the unclaimed yield of the remaining stakers (their `safeTransfer` calls revert due to insufficient balance, with no mechanism to top up the shortfall). This matches the "theft or permanent freezing of unclaimed yield" impact class.

### Likelihood Explanation
This is triggerable by any ordinary wallet holding a fee-charging/deflationary ERC20 that is registered as a pool's reward token, via the fully permissionless `donateRewards()` entry point — no privileged role required. While the current in-scope reward tokens used by the protocol (WOM, MGP, etc.) may not themselves be fee-on-transfer, the contracts place no restriction on which tokens can be registered/used as reward tokens, and the accounting logic itself is unconditionally unsound for any token exhibiting non-standard transfer behavior.

### Recommendation
In `_provisionReward()` (in `BaseRewardPool.sol`, `BaseRewardPoolV2.sol`, and `mWOMSVBaseRewarder.sol`), measure the contract's balance of `_rewardToken` before and after `safeTransferFrom`, and use the actual received delta (rather than the nominal `_amountReward` parameter) when updating `historicalRewards`, `queuedRewards`, and `rewardPerTokenStored`.

### Proof of Concept
1. Owner/manager registers a fee-on-transfer token `FeeToken` (e.g., 10% transfer fee) as a reward token for a `BaseRewardPool` via `queueNewRewards()`, or any holder calls `donateRewards()` once the token is already registered.
2. Attacker/donor calls `donateRewards(1000e18, FeeToken)`. `safeTransferFrom` moves 1000e18 nominal, but the pool actually receives only 900e18 due to the 10% fee.
3. `_provisionReward` computes `rewardPerTokenStored += (1000e18 * 10**decimals) / totalStaked()`, crediting stakers as if 1000e18 arrived.
4. Early stakers call `getReward()` and successfully withdraw their proportional share computed from the inflated 1000e18 basis.
5. Once cumulative payouts reach the actual 900e18 held by the contract, the pool has insufficient balance to pay remaining stakers; further `getReward()` calls for `FeeToken` revert on `safeTransfer`, permanently freezing that portion of unclaimed yield for the remaining stakers.
