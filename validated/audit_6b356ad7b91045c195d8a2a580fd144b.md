### Title
`SignableTransaction::new` omits the OP_RETURN data output from the fee/weight estimate, so the transaction pays less than the requested fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Perennial issue — where the keeper refund scaled with the number of *requested* prices while the actual work scaled with the number of *callbacks* — `SignableTransaction::new` computes `needed_fee` from a weight estimate that counts only inputs and payment outputs, while the actual transaction additionally carries an OP_RETURN output of up to ~80 bytes whenever `data` is specified. The dimension charged for (payments + inputs) does not match the dimension that makes the transaction larger (the extra data output), so the published transaction systematically underpays relative to the caller-specified `fee_per_vbyte`.

### Finding Description
`SignableTransaction::new` first appends the OP_RETURN output to `tx_outs` (the real transaction) when `data` is provided:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data)
        .expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}
```

However, the weight estimate calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (and later `... Some(&change)`), building a dummy transaction whose outputs are only `payments` plus optional change — the `data` argument is never passed in. `needed_fee = fee_per_vbyte * vbytes` is therefore computed on a transaction that is missing the OP_RETURN output entirely:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

The same omission exists in the change branch: `fee_with_change = fee_per_vbyte * vbytes_with_change` also excludes the data output. Since the actual fee paid is `sum(inputs) - sum(outputs)` and outputs are sized using this underestimated fee, the broadcast transaction's true vsize is larger than estimated and its effective fee rate is strictly below `fee_per_vbyte`. The `TooLowFee` minimum-relay-fee check is also evaluated against the underestimated `vbytes`, so a transaction can pass the check yet fall below `DEFAULT_MIN_RELAY_TX_FEE` on its real size once up to 80 bytes of OP_RETURN data are added.

### Impact Explanation
A transaction constructed with `data` pays a fee corresponding to a smaller transaction than the one actually broadcast. Under congested fee conditions or low `fee_per_vbyte`, the real fee rate can drop below the network's minimum relay fee or below what was intended, making the transaction unbroadcastable or leaving it stuck unconfirmed — freezing the inputs (multisig-controlled funds) until a replacement is constructed. This is the same economic-accounting defect as the referenced report: the refund/fee scales with one measured quantity while the real cost includes an uncounted, attacker-influenceable quantity.

### Likelihood Explanation
`data` is user-influenceable: payments carrying data flow through the scheduler into `SignableTransaction::new` (per `test_data`, an OP_RETURN output is created purely from caller-provided bytes, up to the 80-byte `TooMuchData` bound). Any send carrying data underpays; the deviation grows with data length and fee rate. No malicious validator or collusion is needed — only a transfer that includes data.

### Recommendation
Include the OP_RETURN output in `calculate_weight_vbytes` (e.g., pass the fully-constructed `tx_outs`, or add `data` as a parameter and push the OP_RETURN output into the dummy transaction before measuring weight), for both the change and no-change estimates, so `needed_fee` reflects the transaction actually signed and broadcast.

### Proof of Concept
1. Construct a `SignableTransaction` with a non-empty `data: Some(vec![0u8; 80])`, one input, one payment, and a change address, at a `fee_per_vbyte` marginally above the minimum.
2. After signing via `TransactionMachine`, compare `tx.vsize()` (which includes the OP_RETURN output) with `needed_fee / fee_per_vbyte` (which excludes it): the real vsize exceeds the paid-for vsize by the serialized size of the OP_RETURN output (~9–91 bytes).
3. The actual fee rate `fee() / tx.vsize()` is strictly less than `fee_per_vbyte`; with a large enough `data` payload it can fall below `DEFAULT_MIN_RELAY_TX_FEE` despite the `TooLowFee` check having passed, yielding a transaction the network will not relay while its inputs are locked.
