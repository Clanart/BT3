### Title
Unbounded u32 count drives per-point group decompression loop in aggregate signature deserialization - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` reads an attacker-controlled `u32` length prefix and then loops that many times, calling `C::read_G` — a full point deserialization/decompression — on each iteration, with no upper bound on the claimed count. This mirrors the ASF `ict`-field bug class: a count field in untrusted input dictates the amount of expensive work performed.

### Finding Description
In `crypto/schnorr/src/aggregate.rs:77-88`, the deserializer does:

```rust
let mut len = [0; 4];
reader.read_exact(&mut len)?;
let mut Rs = vec![];
for _ in 0 .. u32::from_le_bytes(len) {
  Rs.push(C::read_G(reader)?);
}
```

The claimed length can be up to `u32::MAX` (~4.3 billion). Two amplification properties make this a real DoS rather than a fast-fail:

1. `reader` is a generic `io::Read`. When backed by a streaming source (network socket), EOF need not arrive; the peer can trickle 32-byte encodings indefinitely and keep the victim decoding points for as long as bytes flow, with no sanity cap anywhere in the read path.
2. Each `C::read_G` performs full group-element decoding (Ristretto/Ed25519 decompression, k256 point validation, etc.), which is orders of magnitude more expensive than the ~32 bytes of input consumed per iteration. Trivially encodable points (e.g., repeated valid encodings) cost the attacker almost nothing to produce while forcing constant-rate heavy CPU on the verifier.

The mismatch is only checked later in `verify` (`self.Rs.len() != keys_and_challenges.len()`, line 129), so all ~billions of decodes happen before any semantic bound is applied. The codebase demonstrates awareness of this exact bug class elsewhere — `networks/ethereum/src/machine.rs:51-52` explicitly comments "A valid DoS would be to claim a 4 GB data is present" and reads in bounded chunks — but `SchnorrAggregate::read` has no equivalent guard. `Block::read` (`coordinator/tributary/src/block.rs:92`) additionally does `Vec::with_capacity(u32)` causing a multi-GB allocation from 4 bytes, but that file is out of scope.

### Impact Explanation
An unprivileged party who can feed bytes to any `SchnorrAggregate::read` call site (e.g., aggregated validator/BFT signatures relayed between nodes) can pin a CPU core performing continuous point decompressions for the duration of the stream, degrading signing/verification throughput of the node. CPU-exhaustion DoS consistent with the referenced CVE's class and Medium severity.

### Likelihood Explanation
Requires the attacker to reach a deserialization path for aggregate signatures over a `Read` stream they control. Generic `io::Read` readers over network connections satisfy this; the attacker only needs to send a 4-byte count of `0xFFFFFFFF` followed by a sustained stream of valid point encodings — all cheap to generate. No keys, collusion, or privileged position needed.

### Recommendation
Bound the count before the loop: either reject `len` exceeding a protocol maximum (e.g., the validator set size / `MAX_KEY_SHARES_PER_SET`, mirroring the check at `coordinator/src/tributary/transaction.rs:431`), or take the expected signature count as a caller-supplied parameter like `MultiDLEqProof::read(r, discrete_logs)` does (`crypto/dleq/src/lib.rs:308`), and error if the claimed length exceeds it. Optionally read points and stop at the first EOF without trusting the count as the loop bound for work.

### Proof of Concept
```rust
// Conceptual PoC: feed a huge claimed count followed by a slow/infinite
// stream of valid point encodings via any io::Read implementation.
let mut bytes = u32::MAX.to_le_bytes().to_vec();
// Append a repeating valid compressed point (e.g., generator encoding)
// as fast or as slow as desired; each 32 bytes forces a full read_G decode.
let gen = Ristretto::generator().to_bytes();
let reader = io::Cursor::new(
    bytes.into_iter().chain(std::iter::repeat(gen.as_ref().to_vec()).flatten())
);
// Loops up to 4 billion times, decompressing a point per iteration.
let _ = SchnorrAggregate::<Ristretto>::read(&mut { reader });
```
