## Analog Confirmed: Unbounded Python Recursion Parsing Attacker-Controlled Memo Data in Custody/PlotNFT Wallet Sync

### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo()` allows an attacker-controlled coin memo to crash wallet sync via stack overflow - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs a custody/`MofN` puzzle tree from CLVM data taken directly from an on-chain coin's `CREATE_COIN` memo field. Nesting depth is controlled entirely by whoever creates the coin (a `further_branching` flag drives recursion into `MofNHint.member_memos`), and there is no depth limit. Any unprivileged spend-bundle submitter can create a coin whose memo encodes thousands of nested `MofN` levels; when a wallet syncing that coin calls `from_memo()` (directly, or transitively via `chia/pools/plotnft_drivers.py:get_next_from_coin_spend()`), the Python call stack recurses once per nesting level with no bound, causing a stack overflow / `RecursionError`, or in the worst case exhausting the real C stack before Python's soft recursion-limit check triggers, crashing the wallet process. This is structurally the same bug class as CVE-2018-11793 in Apache Mesos: unbounded recursive parsing of a nested, attacker-supplied structure leading to denial of service.

### Finding Description
`PuzzleWithRestrictions.from_memo()` at [1](#0-0)  parses the `memo` `Program` supplied on-chain. When `further_branching` is set, it builds `MofNHint.from_program(puzzle_hint_prog)` and recurses:

```
puzzle: MIPSComponent = MofN(
    m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
)
```

There is no cap on `m_of_n_hint.member_memos` depth or count — the attacker fully controls both the branching factor and the nesting depth of the memo bytes, since the memo is simply data attached to a `CREATE_COIN` condition, which any coin owner can set arbitrarily. [2](#0-1) 

This function is reached from production (non-test) code in the PlotNFT driver: `get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` while parsing a coin's `CREATE_COIN` memo to determine the next PlotNFT/pool state during wallet sync. [3](#0-2)  This driver is invoked from `chia/wallet/plotnft_wallet/plotnft_wallet.py` and `chia/wallet/wallet_state_manager.py` during normal wallet coin-processing/sync, meaning a wallet observing a coin whose spend carries a maliciously deep memo will attempt this recursive parse.

This is architecturally the same bug class as the Mesos advisory: a parser that recursively walks an attacker-supplied nested structure with no depth bound, driven purely by input shape rather than a fixed schema — contrasted with `sha256_treehash()` elsewhere in the codebase, which is deliberately implemented iteratively specifically "so we don't have to worry about blowing out the python stack." [4](#0-3)  No such non-recursive safeguard exists for `from_memo()`.

### Impact Explanation
A single, cheaply constructed spend (any coin owner creating a `CREATE_COIN` condition with a deeply nested memo) can cause any wallet that later processes/syncs that coin — via `PlotNFT`/pool wallet flows or other custody-architecture consumers — to hit unbounded Python recursion. Because CPython's recursion-depth tracking is a soft limit checked periodically, sufficiently deep nesting can exhaust the real OS thread stack before `RecursionError` is even raised, causing a hard process crash (not a catchable exception) rather than a clean error. At minimum this is an uncatchable `RecursionError` that halts wallet-sync/transaction-processing for the affected wallet client — a spend-triggered transaction-processing halt, matching the CVE-2018-11793 impact class (availability-only, high severity DoS). No signatures need to be forged, coins need not belong to the attacker beyond the one they spend to plant the malicious memo.

### Likelihood Explanation
Likelihood is high for any deployment exercising the custody-architecture/PlotNFT memo path: constructing the malicious memo requires only assembling nested CLVM data and attaching it as a `CREATE_COIN` memo in a spend bundle the attacker fully controls (no special privileges, no plot/pool participation required beyond submitting one coin spend). The vulnerable code path (`get_next_from_coin_spend`) is on the standard PlotNFT/pool wallet sync flow, so it is triggered automatically as soon as an affected wallet observes the crafted spend on-chain, without further attacker interaction.

### Recommendation
Bound recursion depth (and/or `MofNHint.member_memos` fan-out) explicitly in `PuzzleWithRestrictions.from_memo()`, or rewrite the parse as an iterative worklist/stack-based traversal (mirroring the non-recursive approach already used in `sha256_treehash()`), rejecting memos that exceed a sane maximum nesting depth before recursing.

### Proof of Concept
Conceptually (not run, derived from code reading):
1. Construct a `Program` memo of the form `(CHIP-0043 [0 [] 1 [m [child_memo_1 ... child_memo_n]]])` where each `child_memo_i` is itself a full nested `MofN` memo of the same shape, repeated to a depth of e.g. 50,000–100,000 levels (trivially producible programmatically using `PuzzleWithRestrictions.memo()` recursively before submission, or hand-built CLVM bytes).
2. Submit a spend bundle whose `CoinSpend` creates a coin with `CREATE_COIN ... memo=<that nested structure>` — this requires no special permission, just spending a coin the attacker owns.
3. Any wallet that later processes this coin via `chia/pools/plotnft_drivers.py:get_next_from_coin_spend()` (or any code path calling `PuzzleWithRestrictions.from_memo()` on this coin's memo) recurses once per nesting level in `PuzzleWithRestrictions.from_memo()` / `MofN` construction, exhausting the Python/C call stack and crashing or hanging that wallet process — the analog of the Mesos JSON deep-nesting stack-overflow DoS.

class MofNHint:

    @classmethod
    def from_program(cls, prog: Program) -> MofNHint:
        m, member_memos = prog.as_iter()
