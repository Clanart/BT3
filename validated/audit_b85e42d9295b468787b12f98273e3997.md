### Title
Permanent loss/duplication of user funds when native-ERC20 unescrow fails during `OnRecvPacket` IBC conversion - (File: `x/erc20/keeper/ibc_callbacks.go`, `x/erc20/keeper/msg_server.go`)

### Summary
This is the Cosmos EVM analog of the Ondo `rOUSG` bug: a privileged/expected token-moving operation (there, `BURNER_ROLE.burn`; here, the erc20 module's unescrow-on-receive) can be blocked by logic inside the underlying ERC-20 contract that the surrounding protocol code does not anticipate or roll back for. In `x/erc20/keeper/ibc_callbacks.go`, `OnRecvPacket` calls `ConvertCoinNativeERC20` (`x/erc20/keeper/msg_server.go:237-306`) directly on the live `ctx` (not a `CacheContext`). That function first moves the recipient's freshly-received bank coin into the `erc20` module account (`SendCoinsFromAccountToModule`, line 258) and only afterwards attempts to "unescrow" the equivalent ERC-20 tokens by calling `transfer` on the arbitrary, permissionlessly-registrable ERC-20 contract via `CallEVM` (line 263). If that EVM call reverts — which any token owner can arrange by implementing pausable/blocklist logic in `_beforeTokenTransfer` similar to `rOUSG`'s KYC check — `ConvertCoinNativeERC20` returns an error, and `OnRecvPacket` converts this into `channeltypes.NewErrorAcknowledgement(err)` (`ibc_callbacks.go:137-139`).

### Finding Description [1](#0-0) 
Case 2 of `OnRecvPacket` runs `MintingEnabled` and then `ConvertCoinNativeERC20` directly on `ctx`. There is no `ctx.CacheContext()`/`WriteCache()` pattern wrapping this call, so any state mutation performed before the failure point is committed regardless of the final acknowledgement outcome. [2](#0-1) 
`ConvertCoinNativeERC20` escrows the Cosmos coin from the recipient into the `erc20` module account (`SendCoinsFromAccountToModule`) *before* attempting to unescrow (transfer) the equivalent ERC-20 tokens via an EVM call to the token contract. If that `CallEVM` call reverts — e.g. because the arbitrary, user-registerable ERC-20 contract implements a pausable/blocklist `_beforeTokenTransfer` hook (exactly the class of hook shown in the external `rOUSG` report, and present in this same repo's own `ERC20MinterBurnerDecimals`/`ERC20Pausable` test contracts) that blocks the recipient — the function returns an error without reverting the just-performed `SendCoinsFromAccountToModule`.

Because IBC acknowledgement processing treats an `ErrorAcknowledgement` as a signal for the **source** chain to refund the original sender, while the **destination** chain (this Cosmos EVM chain) has already (a) credited the recipient via the standard ICS-20 transfer logic that ran before this middleware (per the code's own contract comment: "This middleware MUST be executed transfer after the ICS20 OnRecvPacket"), and (b) moved those same coins into the `erc20` module account without successfully delivering the ERC-20 representation or refunding the recipient, the result is:
- The recipient's coins are moved into the module account and never returned to them (no compensating logic exists in this path for a failed unescrow), while
- The source chain independently refunds the original sender's escrowed funds upon seeing the error acknowledgement.

This produces either (depending on the exact accounting on both ends) duplicated spendable value across chains, or a permanent loss/freezing of the destination-side coins in the `erc20` module account with no path for the recipient to recover them.

### Impact Explanation
This falls under the "Critical permanent freezing/locking of user funds" and "Critical unauthorized ... duplication ... of spendable user value across ... IBC escrows" gates. The recipient loses access to coins that were credited to them by the base ICS-20 transfer and then pulled into `types.ModuleName` by `ConvertCoinNativeERC20`, with no refund or retry path once the acknowledgement is already sent as an error (which in turn triggers a second, independent refund on the source chain).

### Likelihood Explanation
Native ERC20 token pairs (`OWNER_MODULE`/self-registered token pairs) can be created by any user deploying an arbitrary ERC-20 contract and registering it (subject to governance/registration parameters in this repo's `x/erc20` module, but the ERC-20 contract logic itself is fully attacker-controlled once registered). An attacker who owns such a token pair, or a legitimate token owner who adds pausable/blocklist functionality after users already hold balances, can trigger this any time they IBC-transfer tokens to a paused/blocked recipient — this requires no elevated privilege over the chain itself, only control of the ERC-20 contract logic, exactly mirroring the `rOUSG` KYC/blocklist scenario.

### Recommendation
Wrap the state-mutating portion of `ConvertCoinNativeERC20` invoked from `OnRecvPacket` (and from `ConvertCoinToERC20FromPacket`) in a `ctx.CacheContext()` and only call `writeCache()` if the ERC-20 unescrow `CallEVM` succeeds; otherwise, return the `ErrorAcknowledgement` without having debited the recipient's already-credited coin balance, so that the coin is safely left in the recipient's account and any subsequent source-chain refund does not create duplicated or permanently locked value.

### Proof of Concept
1. Register a native ERC20 token pair for a contract that inherits `ERC20Pausable`/implements a `_beforeTokenTransfer` block on a specific address (mirroring `contracts/solidity/ERC20MinterBurnerDecimals.sol`'s pause pattern, or a custom blocklist hook).
2. Have the token contract's owner pause the contract or blocklist the intended IBC recipient's address.
3. From a counterparty chain, IBC-transfer the paired denom to that recipient address on the Cosmos EVM chain.
4. Standard ICS-20 logic credits the recipient's bank balance; `OnRecvPacket`'s erc20 middleware then calls `ConvertCoinNativeERC20`, which escrows that balance into the `erc20` module account and calls `transfer` on the paused/blocklisting contract, which reverts.
5. `OnRecvPacket` returns `channeltypes.NewErrorAcknowledgement(err)`. Inspect on-chain state: the recipient's bank balance for that denom is now zero (moved to the `erc20` module account), no ERC-20 tokens were delivered, and the relayer/counterparty chain processes the error acknowledgement and refunds the original sender on the source chain — resulting in value existing on both chains simultaneously or permanently stuck in the destination `erc20` module account.

Note: I was not able to fully trace whether some outer layer of the IBC channel-keeper's `RecvPacket` handling (outside the files reviewed) wraps the entire middleware stack's execution in a branch/cache context that would revert on error acknowledgement; if such a wrapper exists at the `ibc-go` core level, it would mitigate this specific finding. I could not confirm this either way within the indexed code and recommend a background agent verify this call chain (`ibc-go` `Keeper.RecvPacket` and channel handler) before treating this as conclusively exploitable.

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}
