### Title
ProtoJSON parser merges into caller-supplied `Message` without clearing it, causing cross-request field bleed on reused message objects - (File: `src/google/protobuf/json/internal/parser.cc`)

### Summary
`JsonStringToMessage`/`JsonStreamToMessage` (`src/google/protobuf/json/json.cc:114-132`) do not `Clear()` the destination `Message` before parsing JSON into it. Field clearing happens only inside `ParseField()` [1](#0-0) , and only for a field that is actually present ("seen") in the current JSON payload. If an application follows the same performance pattern the curl report calls out for libcurl easy handles — reusing one `Message` object across sequential, independently-triggered JSON parses instead of allocating/clearing a fresh one each time — any field that was populated by a previous JSON payload but is *absent* from the next payload silently survives into the result of the next parse.

### Finding Description
The invariant that fails here is the same class as the curl bug: **per-operation state must not leak across independent uses of a reused handle/object.** In curl, `data->state.digest` computed for origin A survives untouched into the transfer to origin B because `Curl_pretransfer()` never clears it. In protobuf's JSON parser, the analogous per-operation state is the target `Message*` passed to `JsonStreamToMessage`. The API contract at the entry point never calls `message->Clear()`; instead, `ParseField()` only clears a *field* the first time that specific key is seen in *this* JSON document [1](#0-0) . A field that simply does not appear in the new payload is never visited by `ParseField`, so it is never cleared — the stale value from whatever previous parse populated that `Message` remains and is silently included in the merged result, exactly like curl's stale Digest header being silently attached to the next transfer.

This differs from the binary wire-format `Message::ParseFromString`, whose top-level convenience wrapper explicitly performs `Clear()` before merging (matching curl's `curl_easy_reset()`-equivalent hygiene for the CLI tool, which the report notes is *not* affected). ProtoJSON's `JsonStringToMessage`/`JsonStreamToMessage` provide no such guarantee — they are "merge" semantics by default with no opt-out, unlike the C++ `MessageLite::MergeFrom` vs `ParseFrom` split that exists for the binary path.

### Impact Explanation
An application that maps incoming ProtoJSON request bodies onto a pooled/reused `Message` object (a common performance optimization, analogous to libcurl's "reuse the same easy handle" documented best practice) can leak sensitive fields from one logical request into the processing of a later, unrelated request whenever the later JSON omits that field. Depending on what the message models (auth tokens, user identifiers, permission flags, session state), this is an information-exposure / authorization-confusion primitive: data intended for request/user A ends up being interpreted as belonging to request/user B, purely because B's payload didn't happen to re-specify that field. This mirrors the curl impact (stale Digest auth state attributed to the wrong origin) at the application-state level rather than the transport-credential level.

### Likelihood Explanation
Likelihood is Medium: the attacker-controlled input is just a bounded ProtoJSON payload sent through a supported public parsing API (`JsonStringToMessage`/`JsonStreamToMessage`), fully within the threat model (bounded input, trusted schema, no privileged access). The precondition — the host application reusing a `Message` object across independent JSON parses without an explicit `Clear()` — is not mandated or defaulted by protobuf, but it is not discouraged either, and is a natural consequence of common object-pooling/performance patterns, the same "documented best practice" framing used in the original curl report for handle reuse.

### Recommendation
Document explicitly (and ideally enforce) that `JsonStringToMessage`/`JsonStreamToMessage` operate as merge, not parse-and-replace, and that callers must call `message->Clear()` themselves before each independent parse if the `Message` object is reused across logically distinct inputs — mirroring the guidance already given for `TextFormat::Parse` vs `TextFormat::Merge` [2](#0-1) . Consider adding a `Clear()` call at the top of `JsonStreamToMessage`/`JsonStringToMessage` to match the binary `ParseFromString` convenience-wrapper convention, or add an explicit `ParseOptions` flag controlling this behavior, and update documentation/`json.h` accordingly.

### Proof of Concept
Conceptual reproduction (not executed — no test runner available in this session):
```cpp
MyMessage msg;  // application reuses this object across "requests"

// Request 1 (legitimate): populates a sensitive field
json::JsonStringToMessage(R"({"auth_token":"secret-A","payload":"x"})", &msg, {});
// msg.auth_token() == "secret-A"

// Request 2 (attacker-influenced payload, e.g. a webhook callback body,
// omits auth_token entirely):
json::JsonStringToMessage(R"({"payload":"y"})", &msg, {});
// Because JsonStreamToMessage never calls msg.Clear(), and ParseField()
// only clears fields it actually sees in the current payload
// (src/google/protobuf/json/internal/parser.cc:1269-1279),
// msg.auth_token() is STILL "secret-A" after this call,
// now attributed to request 2's context.
```
