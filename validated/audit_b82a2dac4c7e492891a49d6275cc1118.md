### Title
Untrusted `ReceivedOutput` deserialization can report unspendable Bitcoin funds - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Medium. `ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and `OutPoint` without proving that the referenced output exists or that the claimed amount is the on-chain amount. [1](#0-0) [2](#0-1) 

### Finding Description
`Scanner::scan_transaction` normally constructs `ReceivedOutput` only from actual transaction outputs, binding the registered offset to the observed `script_pubkey`, value, and outpoint. [3](#0-2)  The deserializer bypasses that provenance and recreates the same privileged structure directly from untrusted bytes. [4](#0-3)  `SignableTransaction::new` then trusts the embedded `output.value` as the input amount and embeds the supplied `outpoint` in the unsigned transaction. [5](#0-4)  The signing machine checks only that the claimed `script_pubkey` matches the offset-derived key; it does not validate UTXO existence, amount, confirmation depth, or coinbase maturity. [6](#0-5)  Signing subsequently commits to all supplied prevouts and their claimed values through `Prevouts::All`. [7](#0-6) 

### Impact Explanation
An attacker can present a forged serialized `ReceivedOutput` naming a nonexistent outpoint or inflating the amount of an existing deposit while retaining a script matching the threshold wallet. [4](#0-3)  The wallet reports and aggregates those bytes as spendable funds, but the eventual transaction is unspendable because the referenced UTXO is absent or its real amount differs from the sighash-committed prevout. [8](#0-7) 

### Likelihood Explanation
This is reachable wherever serialized `ReceivedOutput` values cross a trust boundary through storage, import, RPC, or another process. [4](#0-3)  The attacker needs only a valid wallet script and can patch a genuine serialized output’s amount and outpoint; no private key or threshold cooperation is required to create the false received-funds record. [5](#0-4) 

### Recommendation
Do not treat `ReceivedOutput::read` as authenticated evidence of receipt. [4](#0-3)  Re-fetch the referenced transaction/output from a trusted Bitcoin node and verify the txid, vout, `script_pubkey`, amount, confirmation status, and coinbase maturity before adding it to spendable funds. [3](#0-2)  Alternatively, authenticate scanner-produced records cryptographically or store only the offset plus outpoint and rebuild the `TxOut` from chain data. [5](#0-4) 

### Proof of Concept
The serialized layout is `offset || consensus(TxOut) || consensus(OutPoint)`, so the value and outpoint can be patched while preserving the wallet-controlled script. [9](#0-8) 

```rust
// `honest` is a ReceivedOutput previously produced by Scanner for this wallet.
let mut encoded = honest.serialize();

// For a P2TR output: 32-byte scalar, 8-byte value, 1-byte script length,
// then a 34-byte script, then the 36-byte OutPoint.
encoded[32 .. 40].copy_from_slice(&1_000_000_000u64.to_le_bytes());

let outpoint_pos = 32 + 8 + 1 + 34;
encoded[outpoint_pos .. outpoint_pos + 36]
  .copy_from_slice(&fake_or_wrong_outpoint_consensus_bytes);

let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
let signable = SignableTransaction::new(
  vec![forged],
  &payments,
  None,
  None,
  fee_per_vbyte,
).unwrap();

// This succeeds because the forged script still matches offset.group_key(),
// even though the referenced outpoint or amount is false.
let machine = signable.multisig(&keys).unwrap();
```

`SignableTransaction::multisig` accepts the forged input because its consistency check is limited to the script and derived group key. [6](#0-5)
