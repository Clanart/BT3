### Title
Missing bounds check on cached unknown-field message length in `upb_MiniTable_ParseUnknownMessage` allows out-of-bounds read during extension/field promotion - ([File: upb/message/promote.c])

### Summary
`upb_MiniTable_ParseUnknownMessage()` in upb parses a previously-stored (cached) unknown-field byte span to recover a length-delimited sub-message. For the `kUpb_MessageUnknownType_StringView` case it reads the tag and the varint length directly from the cached buffer using `upb_WireReader_ReadTag`/`upb_WireReader_ReadVarint` called with a `NULL` `upb_EpsCopyInputStream`, meaning no bounds checking is performed, and then uses the raw decoded `message_len` as the `size` passed to `upb_Decode()` without ever validating it against `unknown->value.bytes.size` (the actual length of the cached buffer). This mirrors the CVE-2026-53246 SCTP pattern: a length field embedded in cached/stored data is trusted and used to bound a later parse without checking it against the real buffer extent.

### Finding Description
`upb_MiniTable_ParseUnknownMessage` (`upb/message/promote.c:39-101`):
```c
if (unknown->type == kUpb_MessageUnknownType_StringView) {
  const char* ptr = unknown->value.bytes.data;
  uint32_t tag;
  uint64_t message_len = 0;
  ptr = upb_WireReader_ReadTag(ptr, &tag, NULL);
  ptr = upb_WireReader_ReadVarint(ptr, &message_len, NULL);
  data = ptr;
  size = message_len;
}
...
upb_DecodeStatus status = upb_Decode(data, size, ret.message, mini_table, NULL, decode_options, arena);
```
`upb_WireReader_ReadTag`/`upb_WireReader_ReadVarint` are documented to require "at least 10 bytes of data available" and rely on the caller performing bounds checks via a supplied `upb_EpsCopyInputStream` (`upb/wire/reader.h:33-49`). Here the `stream` argument is passed as `NULL`, so no bound is enforced against `unknown->value.bytes.size` — the *actual* length of the cached span that was originally captured by `upb_EpsCopyCapture_End` (see `upb/message/promote.c:156-176`, `upb/wire/decode.c:1011-1082`). The decoded `message_len` is attacker-controlled (any varint up to 64 bits, later stored in `size_t size`) and is used directly as the length passed to `upb_Decode(data, size, ...)`, i.e. the sub-decoder is told to read `size` bytes starting at `data`, which can extend far beyond the actual cached unknown-field buffer that was allocated/aliased from the original arena or input buffer.

This is invoked from `upb_Message_GetOrPromoteExtension` (`upb/message/promote.c:118-215`) and `upb_MiniTable_PromoteUnknownToMessage`/`PromoteUnknownToMessageArray`/`PromoteUnknownToMap` (`upb/message/promote.c:264-403`) — all reachable from ordinary public parsing/accessor APIs when an application later resolves an unknown extension field or promotes an unknown field to a known sub-message/array/map field, a common, documented upb usage pattern (lazy extension resolution).

Contrast this with the sibling code path in the same file just a few lines later (`upb/message/promote.c:156-190`), which correctly builds an `upb_EpsCopyInputStream` bound to `unknown_bytes.size` and passes `&stream` to `upb_WireReader_ReadTag`, enforcing bounds. The vulnerable path bypasses that protection entirely by passing `NULL`.

### Impact Explanation
If `unknown->value.bytes.size` (the real cached buffer length) is smaller than the attacker-supplied `message_len` decoded from within that same buffer, `upb_Decode(data, size, ...)` will read `size` bytes starting at `data`, which is beyond the true end of the cached/aliased buffer. Because upb's `upb_EpsCopyInputStream` design relies on either padded "slop bytes" or externally-verified buffer bounds, and this call path supplies no real bound at all, the subsequent decode can walk arbitrary attacker-influenced distances past the legitimate allocation — an out-of-bounds read with the potential for information disclosure or memory corruption depending on adjacent heap/arena layout, closely analogous to the OOB reads possible in the SCTP COOKIE_ECHO cached-INIT-chunk bug.

### Likelihood Explanation
The vulnerable function is reached whenever a consuming application (or generated accessor code) calls `upb_Message_GetOrPromoteExtension`, or promotes an unknown field to a known message/array/map field — normal, supported upb parsing/accessor flows triggered from ordinary bounded binary protobuf input containing an unresolved extension or forward-compatible unknown field with an inflated embedded length. No malicious schema, plugin, or privileged access is required; a standard client sending a bounded, otherwise well-formed message with a crafted length prefix on an unknown/extension field is sufficient to reach this code with `message_len` set arbitrarily large relative to the true captured span.

### Recommendation
In `upb_MiniTable_ParseUnknownMessage`, when handling `kUpb_MessageUnknownType_StringView`, construct a bounded `upb_EpsCopyInputStream` (or equivalent explicit bounds check) over `unknown->value.bytes.data`/`.size` before reading the tag and varint length, and validate that `message_len` does not exceed the number of bytes remaining in `unknown->value.bytes` after the tag+length prefix — mirroring the correctly-bounded pattern already used at `upb/message/promote.c:156-190`. Reject (return `kUpb_UnknownToMessage_ParseError`) if the length is inconsistent with the cached buffer size, before calling `upb_Decode`.

### Proof of Concept
Conceptual reproduction (would need to be executed in the actual checkout to confirm ASan/heap-buffer-overflow detection):
1. Construct a minimal message with a MiniTable extension field of message type that is *not* registered in the `upb_ExtensionRegistry` used during initial decode, so it lands in unknown fields as a `StringView` unknown entry.
2. Encode this unknown entry's payload as: `tag (field_number<<3 | 2)` followed by a varint length field whose value is much larger than the number of bytes actually following it in the captured span (e.g., declare length `0x7FFFFFFF` while only a few real payload bytes exist) — this is legal to construct because `upb_EpsCopyCapture_End` captures whatever bytes were present in the original input up to the (possibly truncated/mis-sized) delimited value as read by the *initial*, correctly-bounded decode; however, the length used later during *promotion* is independently re-derived from the cached bytes and not re-validated.
3. Call `upb_Message_GetOrPromoteExtension` (or trigger promotion via a known sub-message/array/map accessor) with `decode_options` such that the mismatched length is used to call `upb_Decode(data, size, ...)` with `size` exceeding the true `unknown->value.bytes.size`.
4. Under ASan, this should manifest as a heap-buffer-overflow read inside `upb_Decode`/`upb_EpsCopyInputStream_Init` on the arena-allocated or aliased unknown-field buffer.
