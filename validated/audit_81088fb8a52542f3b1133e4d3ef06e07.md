## Title
EVM WebSocket RPC Bypasses the Configured `deny_list`, Allowing Unauthenticated Remote Clients to Reach Methods the Operator Explicitly Disabled - (File: evmrpc/rpcstack.go, evmrpc/server.go)

### Summary
Sei's EVM JSON-RPC layer supports an operator-configured `deny_list` that is supposed to make "EVM RPC... fail fast" for listed methods [1](#0-0) . This is enforced only on the HTTP JSON-RPC surface via `srv.RegisterDenyList` inside `EnableRPC` [2](#0-1) , and `NewEVMHTTPServer` wires `config.DenyList` into `httpConfig.DenyList` [3](#0-2) . The WebSocket surface uses a separate `rpc.Server` instance created in `EnableWS`, which never calls `RegisterDenyList` [4](#0-3) , and `WsConfig` has no `DenyList` field at all [5](#0-4) . `NewEVMWebSocketServer` builds `wsConfig` without ever referencing `config.DenyList` [6](#0-5) . This mirrors exactly the bug class in the external report: a restriction policy is enforced on one RPC transport (HTTP) but is not propagated to a second transport (ZMQ there, WebSocket here) exposing the same underlying daemon capabilities.

### Finding Description
Both `NewEVMHTTPServer` and `NewEVMWebSocketServer` register largely overlapping `eth_`/`net`/`web3` namespace APIs (e.g. `BlockAPI`, `TransactionAPI`, `StateAPI`, `InfoAPI`, `SendAPI`, `SimulationAPI`) against two independent `rpc.Server` instances [7](#0-6) . The HTTP server is configured with the operator's `deny_list` and applies it per-request via `rpc.Server.RegisterDenyList` [8](#0-7) . The WebSocket server's `EnableWS` builds its own fresh `rpc.Server` and registers the same set of APIs, but has no equivalent step to apply a deny list [9](#0-8) , because `WsConfig` was never given a `DenyList` field to carry that intent [5](#0-4) . An operator who sets `deny_list` in `app.toml` expecting it to block a specific method across "EVM RPC" reasonably assumes it also covers the WebSocket endpoint, since the config documentation does not scope it to HTTP only [10](#0-9) .

### Impact Explanation
An unauthenticated remote WebSocket client can invoke any method the operator believed was blocked by `deny_list`, as long as that method's namespace/API is registered on the WS server (e.g. `eth_call`, `eth_estimateGas`, `eth_sendRawTransaction`, or other resource-intensive simulation/state methods present in the WS API set [11](#0-10) ). If the deny-listed method was disallowed specifically because it is expensive or previously caused resource exhaustion, this gap lets an attacker continue to trigger it over WS, undermining an operator-applied hardening control and creating a path to resource exhaustion / crash of a public RPC node whose operator believed the mitigation was chain-wide.

### Likelihood Explanation
Exploitation requires only that the operator has WebSocket RPC enabled (a common, documented configuration for EVM RPC nodes) and has configured a non-empty `deny_list` intending it to apply broadly. No authentication or privileged access is needed — any remote WS client can connect and call the "denied" method, matching the same operational profile as the external report's public-node/`--restricted-rpc` bypass.

### Recommendation
Add a `DenyList` field to `WsConfig`, populate it from `config.DenyList` in `NewEVMWebSocketServer` (mirroring `httpConfig.DenyList`), and call `srv.RegisterDenyList` for each entry inside `EnableWS`, exactly as is already done in `EnableRPC`.

### Proof of Concept
1. Configure `app.toml` with `deny_list = ["eth_call"]` (or any WS-registered method the operator wants blocked) and enable both EVM HTTP and WebSocket RPC.
2. Confirm `eth_call` is rejected via the HTTP JSON-RPC endpoint (deny list enforced by `EnableRPC`/`RegisterDenyList`).
3. Connect a WebSocket JSON-RPC client to the WS endpoint and send the same `eth_call` request.
4. Observe that the WS server executes the request successfully, because `EnableWS` never applied the configured deny list, confirming the policy-bypass across RPC transports.

```go
func (h *HTTPServer) EnableWS(apis []rpc.API, config WsConfig) error {
	h.mu.Lock()
	defer h.mu.Unlock()

	if h.wsAllowed() {
		return fmt.Errorf("JSON-RPC over WebSocket is already enabled")
	}
	// Create RPC server and handler.
	srv := rpc.NewServer()
	srv.SetBatchLimits(config.batchItemLimit, config.batchResponseSizeLimit)
	readLimit := effectiveMaxRequestBodyBytes(config.readLimit)
	srv.SetReadLimits(readLimit)
	// maxConcurrentRequestBytes is passed through raw; rpc.Server.recomputeWSConcurrentBudget
	// raises it to readLimit when smaller, matching
	// newRequestSizeLimiter's max(budget, maxBody) rule on the HTTP protocol.
	srv.SetWSConcurrentRequestBytes(config.maxConcurrentRequestBytes)
	srv.SetWSAdmissionTimeout(config.wsAdmissionTimeout)
	srv.SetWSAdmissionEventHook(func(reason string) {
		// Hook carries no request context, and the fork's own connCtx is context.Background() too.
		recordWSAdmissionRejected(context.Background(), reason)
	})
	logger.Info("Registering apis for evm websocket")
	if err := RegisterApis(apis, config.Modules, srv); err != nil {
		return err
	}
	h.WsConfig = config
	h.wsHandler.Store(&rpcHandler{
		Handler: NewWSHandlerStack(srv.WebsocketHandler(config.Origins), config.JwtSecret),
		server:  srv,
	})
	return nil
}
```
