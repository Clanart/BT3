### Title
Deep-link "Open Repository from URL" PR checkout silently adds an attacker-controlled remote and fetches from it - (File: `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
The DCA report's broken invariant is: a state-mutating, asset-relevant action (ownership/remote binding) is performed on attacker-supplied input without the affected party's consent. In GitHub Desktop, the analogous invariant is that Desktop should not add new git remotes or fetch from attacker-chosen URLs without the user explicitly approving the specific remote/URL. The `x-github-client://openRepo/...?pr=NNN` deep-link handler breaks this: clicking a link controls a `pr` number that Desktop resolves via the GitHub API and then uses to automatically `addRemote` and fetch from the PR's head fork `clone_url` in one of the user's already-open local repositories.

### Finding Description
The protocol handler registers `x-github-client` (and legacy `github-mac`/`github-windows`) as an app URL scheme [1](#0-0) . `parseAppURL` accepts an `openRepo` action with a `pr` query parameter that is only validated to be numeric — the `url` path segment (which repo to operate on) and the `pr` number are both fully attacker-controlled via the link [2](#0-1) .

When this action reaches the dispatcher, `openRepositoryFromUrl` routes it to `openPullRequestFromUrl` [3](#0-2) . That function fetches the PR from the API, tries to match it to an already-open local repository via `getRepositoryFromPullRequest` (matching by origin/upstream URL), and — critically — if a match is found, it proceeds straight to `_checkoutPullRequest` without any additional user confirmation of the PR's head repository/fork: [4](#0-3) 

`_checkoutPullRequest` → `_findPullRequestBranch` then does the actual attacker-influenced mutation: if no remote already points at the PR's `headCloneUrl`, it silently calls `addRemote` with that attacker/fork-controlled URL, and then fetches it: [5](#0-4) [6](#0-5) 

None of this — matching the base repository via `doesRepositoryMatchUrl`/`getRepositoryFromPullRequest` [7](#0-6) , adding the fork remote, or fetching it — requires the user to see or approve the specific fork URL that will be added as a remote and fetched. The only "guard" is that the target PR number and base repo must resolve to a repo the user already has open locally; the fork/head repo URL that gets added as a remote and fetched is entirely determined by whatever the GitHub API returns for that PR, i.e., attacker-controlled if the attacker opens the PR from their own fork against a repo the victim has cloned.

This mirrors the DCA bug's structure: a low-friction, unprivileged action (clicking a crafted link, analogous to transferring DCA ownership) causes a privileged party's existing trusted state (a local repo with stored credentials/remotes, analogous to the token-approved owner) to be silently bound to attacker-supplied data (fork URL as new remote, analogous to attacker-controlled recipient) without an explicit, distinct consent step for that binding.

### Impact Explanation
Adding an unreviewed remote and fetching it from an attacker's fork does not itself execute code, but it does:
- Silently mutate repository state on disk (`.git/config` gets a new `github-desktop-*` remote pointing to an attacker-controlled URL) without a distinct confirmation dialog naming that URL.
- Cause an outbound network fetch to an attacker-chosen host/URL initiated purely by a link click, which can be used for target/IP enumeration or to trigger credential-helper/SSH-agent probing against attacker infrastructure (the trampoline credential helper will attempt to resolve credentials against the fetched host, see `app/src/lib/trampoline/trampoline-credential-helper.ts`).
- If the user later interacts with the PR UI (e.g., "Checkout" from the resulting branch state) they may check out and build/run code from the fork branch believing it's associated with a repo they already trust, since the confusing consent flow never surfaces the actual fork clone URL for explicit approval.

This is lower severity than remote code execution but is a genuine "silent corruption of trusted repo state via an unprivileged, attacker-controlled input" — the same class the DCA bug represents (unconsented binding to attacker data).

### Likelihood Explanation
Requires only that the victim (a) has GitHub Desktop installed with the protocol handler registered (default), (b) has the target base repository already open in Desktop, and (c) clicks a link (e.g., embedded in an issue/PR comment, README, or external site) of the form `x-github-client://openRepo/<repo-url>?pr=<attacker-PR-number>`. No local access, no admin rights, and no prior compromise are needed — matching the report's "Valid Impact" bar of a link-click-triggered primitive.

### Recommendation
- **Short term:** Before calling `_checkoutPullRequest` from `openPullRequestFromUrl`, surface a confirmation dialog showing the actual PR head repository owner/clone URL and require explicit user approval before adding a new remote or fetching from it — do not silently reuse the "already open repository" match as implicit consent for adding a *new*, previously-unseen remote.
- **Long term:** Apply the same "two-step" consent principle to all deep-link-triggered git-state mutations (add remote, fetch, checkout) — treat any transition to an attacker/link-controlled URL as requiring a distinct confirmation step, and add regression tests around `parseAppURL`/`_findPullRequestBranch` that assert a remote is never added without a corresponding user-facing confirmation.

### Proof of Concept
1. Victim has repository `github.com/victim/target` cloned and open in GitHub Desktop.
2. Attacker forks `victim/target`, opens PR #N from their fork against `victim/target`.
3. Attacker sends victim a link: `x-github-client://openRepo/https://github.com/victim/target?pr=N`.
4. Victim clicks the link (e.g., from a chat message or webpage). The OS routes it to GitHub Desktop via the registered `x-github-client` protocol handler [8](#0-7) .
5. `parseAppURL` accepts it since `pr` is numeric [9](#0-8) , and the dispatcher resolves it to the already-open `victim/target` repo and immediately calls `_checkoutPullRequest` with the attacker fork's `clone_url` [10](#0-9) .
6. `_findPullRequestBranch` adds a new remote pointing at the attacker fork and fetches it, with no dialog ever showing the victim the fork's URL [11](#0-10) .

Note: I could not fully trace `fetchPullRequest`'s exact API-side validation (in `app/src/lib/api.ts` / `app-store.ts`) within the available indexed context, so it's not fully confirmed whether any server-side ownership check further restricts which PR numbers/forks can be referenced this way; a Devin session with full file access would be needed to verify that boundary precisely.

  private getRepositoryFromPullRequest(
    pullRequest: IAPIPullRequest
  ): RepositoryWithGitHubRepository | null {
    const state = this.appStore.getState()
    const repositories = state.repositories
    const headUrl = pullRequest.head.repo?.clone_url
    const baseUrl = pullRequest.base.repo?.clone_url

    // This likely means that the base repository has been deleted
    // and we don't support checking out from refs/pulls/NNN/head
    // yet so we'll bail for now.
    if (headUrl === undefined || baseUrl === undefined) {
      return null
    }

    for (const repository of repositories) {
      if (this.doesRepositoryMatchUrl(repository, headUrl)) {
        return repository
      }
    }

    for (const repository of repositories) {
      if (this.doesRepositoryMatchUrl(repository, baseUrl)) {
        return repository
      }
    }

    return null
  }
