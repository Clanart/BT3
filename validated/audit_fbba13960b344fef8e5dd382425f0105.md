### Title
Missing minting/inflation guard before fee subtraction in `MempoolManager.validate_spend_bundle()` can raise an unhandled `ValueError` and abort mempool processing - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle()` computes `fees = uint64(removal_amount - addition_amount)` without first verifying that `addition_amount <= removal_amount`, unlike the equivalent consensus check performed later in block validation. [1](#0-0)  This mirrors the reported Solidity issue: an arithmetic subtraction of independently-derived values that is not validated beforehand, causing the operation to fail/underflow when the subtrahend exceeds the minuend.

### Finding Description
`removal_amount` (sum of spent-coin amounts) and `addition_amount` (sum of amounts of `CREATE_COIN` conditions produced by the spend) are accumulated independently while iterating the coin spends in the submitted `SpendBundle`. [2](#0-1) [3](#0-2)  These two values are then subtracted and cast directly to `uint64`:

```
fees = uint64(removal_amount - addition_amount)
``` [4](#0-3) 

Unlike `chia/consensus/block_body_validation.py`, which explicitly checks `if removed < added: return Err.MINTING_COIN` before computing `fees = removed - added` [5](#0-4) , `validate_spend_bundle()` has no equivalent guard before the `uint64()` cast at line 814. If a submitted spend bundle's `CREATE_COIN` conditions sum to more than the amounts of the coins it spends (i.e. an attempt to mint/inflate value), `removal_amount - addition_amount` is negative. Because `uint64` is a strictly range-checked integer type in this codebase — confirmed by the existing test `test_compute_block_fee`, which expects `ValueError` with message "does not fit into uint64" for negative values [6](#0-5)  — the `uint64()` cast at line 814 will raise an unhandled `ValueError` instead of being rejected with a controlled `Err` code such as `MINTING_COIN`.

This function is invoked directly on every spend bundle a node accepts for mempool admission (i.e., every submitted spend bundle from an unprivileged wallet/RPC caller, before signature/aggsig verification completes the same way `check_removals`/time-lock checks are still to be run afterward at lines 840+). The CLVM `conds`/cost computation (`conds.spends`, `create_coin` outputs) is derived purely from running the puzzle reveals in the bundle, so an attacker only needs to craft a spend bundle whose puzzle/solution produces `CREATE_COIN` outputs summing to more than the coin's own amount — trivially achievable with a standard puzzle solution listing an inflated amount in a `CREATE_COIN` condition.

### Impact Explanation
An unhandled `ValueError` raised mid-way through `validate_spend_bundle()` (called from the mempool add path used by every full node on every spend bundle it receives) propagates out of a core mempool function that is not designed to raise on attacker-supplied, syntactically valid-but-inflationary conditions. Depending on how the caller (`add_spend_bundle`/RPC submission path) handles exceptions, this can manifest as a crash of the mempool-processing coroutine/task or an unhandled exception bubbling up through the full node's spend-bundle intake path — a spend-bundle-triggered transaction-processing halt reachable by any unprivileged submitter, matching the accepted impact class ("a spend-triggered transaction-processing halt"). This is a denial-of-service risk against mempool admission rather than a fund-theft or inflation vulnerability (the actual consensus-level `MINTING_COIN` check in block validation still correctly rejects such spends before they can be included in a block), but it can disrupt normal transaction processing/mempool availability for a node.

### Likelihood Explanation
Likelihood is Medium: any wallet user or spend-bundle submitter can construct a spend bundle whose `CREATE_COIN` conditions exceed the coin's spent amount (no privileged access, valid aggregate signature over arbitrary conditions is achievable using the submitter's own coins/keys, or even unsigned bundles reaching this validation step depending on the call order — this could not be fully confirmed from available context since the exact ordering of signature checks versus `validate_spend_bundle()` invocation from `add_spend_bundle` could not be traced completely in the available index). The main precondition — reaching `validate_spend_bundle()` with a bundle whose additions exceed removals — is straightforward to construct.

### Recommendation
Add an explicit minting/inflation check in `MempoolManager.validate_spend_bundle()` before the fee computation, mirroring `block_body_validation.py`:
```python
if addition_amount > removal_amount:
    return Err.MINTING_COIN, None, []
fees = uint64(removal_amount - addition_amount)
```
This ensures the subtraction is validated before the `uint64()` cast and returns a controlled `Err` result instead of raising an unhandled exception.

### Proof of Concept
Not independently reproduced with a runnable test in this session (index-only investigation); the conceptual PoC is:
1. Create a coin `C` with `amount = 1`.
2. Spend `C` with a puzzle/solution that issues a `CREATE_COIN` condition with `amount = 2` (i.e., additions exceed removals for this coin/bundle).
3. Submit this `SpendBundle` to a full node's mempool via the normal spend-bundle submission RPC path.
4. `MempoolManager.validate_spend_bundle()` computes `addition_amount (2) > removal_amount (1)`, so `removal_amount - addition_amount = -1`, and `uint64(-1)` raises `ValueError: -1 does not fit into uint64` (per the same coercion behavior demonstrated in `test_compute_block_fee`) [6](#0-5) , instead of returning a controlled `Err.MINTING_COIN` result as block validation does.
