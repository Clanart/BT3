### Title
Pointer contract redeploy on version bump reuses storage without verifying layout compatibility - ([File: x/evm/keeper/pointer_upgrade.go])

### Summary
`RegisterPointer` lets any unprivileged caller trigger `UpsertERCPointer`, which — when a pointer for a given CW20/CW721/CW1155/native token already exists — redeploys the *current* pointer bytecode onto the *same* contract address while leaving all of that address's existing EVM storage untouched. There is no verification (not even a partial one, unlike the `verifyState` pattern in the external report) that the new pointer contract's storage layout is compatible with the layout the old bytecode wrote. Any storage-layout change between pointer contract versions is silently applied to whatever data is already sitting in that address's storage slots.

### Finding Description
`UpsertERCPointer` in [1](#0-0)  looks up whether a pointer already exists for the pointee (`getter(liveCtx(), pointee)`); if it does, instead of creating a fresh contract it calls `evm.GetDeploymentCode(evmModuleAddress, bin, suppliedGas, utils.Big0, existingAddr)` and then `k.SetCode(writeCtx, contractAddr, ret)` — i.e. it overwrites the runtime bytecode at the pre-existing address with the newest version's bytecode, but performs no reset or migration of that address's storage trie.

This redeploy path is reachable by an ordinary transaction sender: `MsgServer.RegisterPointer` allows re-registering a pointer whose stored version is behind `CurrentVersion`, which is exactly the path exercised in [2](#0-1)  — the old (lower-version) pointer entry is deleted from the registry and a new `RegisterPointer` call causes the contract at the *same address* to be upgraded to `erc721.CurrentVersion` while `newPointer.String() == pointer.String()` (address retained).

Just as the external report describes for `verifyState` (only one entry checked, casts assumed to prove compatibility), this Sei code path performs **no check at all** that the new pointer implementation's storage slot layout (e.g., balance/allowance/owner mappings, packed booleans, or newly introduced state variables in `precompiles/pointer/legacy/vXXX` successive versions) matches what is already stored at `existingAddr`. If any future or already-shipped pointer version reorders declared state variables, changes a mapping's base slot, or changes value packing (analogous to changing `minLockedPeriods` from `uint8`/`map` to a different primitive in the report), the new bytecode will read/write the old storage under an incompatible interpretation.

### Impact Explanation
Because pointer contracts hold user balances/ownership for wrapped CW20/CW721/CW1155/native assets, a storage-layout mismatch introduced across pointer contract versions and then triggered by any user calling `RegisterPointer` (or the underlying `precompiles/pointer` `AddCW20`/`AddCW721`/`AddERC*` methods) could cause the redeployed contract to misinterpret existing storage as balances, allowances, or ownership records it did not intend to hold — enabling unauthorized transfer of pointer-held value or permanent corruption/freezing of user balances tracked by the pointer. This falls squarely under "unauthorized transfer via precompile or pointer" and "fund loss/freezing" impact categories.

### Likelihood Explanation
The redeploy path itself is trivially reachable today by any transaction sender via `RegisterPointer` whenever a pointee's registered pointer version lags `CurrentVersion` — this is normal, expected behavior after every pointer bytecode bump (which happens routinely, as shown by the long `legacy/vXXX` version list in [3](#0-2) ). The exploitability specifically requires a storage-layout-incompatible change between two pointer versions, which the code provides no safeguard against, so likelihood depends on whether/when such a layout change is (or has been) introduced — the vulnerability is the *absence of the check* itself, not a specific already-triggered incompatible diff.

### Recommendation
Before reusing an existing pointer address's storage across a version bump in `UpsertERCPointer`, either (a) deploy the new pointer implementation to a fresh address and migrate/validate state explicitly, or (b) maintain and enforce an explicit storage-layout compatibility contract between consecutive pointer versions (e.g., a versioned storage struct with fixed slots, checked before `SetCode` is applied), so that a bytecode upgrade at a fixed address never blindly reinterprets pre-existing storage under a new layout.

### Proof of Concept
1. Assume pointer version N+1 changes a storage variable's slot/type relative to version N (e.g., reorders a `mapping(address=>uint256) balances` relative to other state, as in the referenced `MinersEscrow`-style example).
2. A CW20 token has an existing ERC20 pointer registered at version N with real user balances stored in its mapping slot.
3ny.Any unprivileged account calls `RegisterPointer` (or the `pointer` precompile's `AddCW20`) for that CW20 token.
4. `x/evm/keeper/msg_server.go`'s `RegisterPointer` sees the existing pointer's version < `CurrentVersion` and calls `k.UpsertERCCW20Pointer`, which calls `UpsertERCPointer` — this redeploys version N+1 bytecode onto the same contract address via `k.SetCode`, leaving version N's storage untouched.
5. Version N+1's code now reads/writes storage slots under its own (different) layout, misinterpreting stale version-N data (e.g., attacker-controlled slots collide with balance/allowance slots), enabling manipulated balances or ownership on the live pointer contract. [4](#0-3) [2](#0-1)

func (k *Keeper) UpsertERCPointer(
	ctx sdk.Context, evm *vm.EVM, typ string, args []interface{}, getter PointerGetter, setter PointerSetter,
) (contractAddr common.Address, err error) {
	pointee := args[0].(string)
	evmModuleAddress := k.GetEVMAddressOrDefault(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName))

	var bin []byte
	bin, err = artifacts.GetParsedABI(typ).Pack("", args...)
	if err != nil {
		panic(err)
	}
	bin = append(artifacts.GetBin(typ), bin...)
	// GetDeploymentCode / Create take EVM snapshots that Freeze() Multistore layers.
	// Exists-lookup and commits must use the live unfrozen top (sdb.Ctx): cachekv
	// forbids writing a frozen layer, and same-tx readers that skip frozen-empty
	// parents would miss those writes. The precompile Prepare `ctx` is that top at
	// Prepare time, but is frozen once this Upsert snapshots. Always attach the
	// caller's gas meter (finite precompile meter in deliver) — sdb.Ctx() alone
	// carries the infinite EVM meter.
	sdb := state.GetDBImpl(evm.StateDB)
	liveCtx := func() sdk.Context {
		if sdb == nil {
			return ctx
		}
		return sdb.Ctx().WithGasMeter(ctx.GasMeter())
	}
	existingAddr, _, exists := getter(liveCtx(), pointee)
	suppliedGas := k.getEvmGasLimitFromCtx(ctx)
	var remainingGas uint64
	if exists {
		var ret []byte
		contractAddr = existingAddr
		ret, remainingGas, err = evm.GetDeploymentCode(evmModuleAddress, bin, suppliedGas, utils.Big0, existingAddr)
		if err != nil {
			return
		}
		// Only write on success: a failed GetDeploymentCode can leave ret as nil or
		// revert data, which must not clobber live pointer bytecode (even transiently).
		writeCtx := liveCtx()
		k.SetCode(writeCtx, contractAddr, ret)
		if sdb != nil {
			sdb.RefreshCodeCache(contractAddr, ret)
		}
	} else {
		_, contractAddr, remainingGas, err = evm.Create(evmModuleAddress, bin, suppliedGas, uint256.NewInt(0))
	}
