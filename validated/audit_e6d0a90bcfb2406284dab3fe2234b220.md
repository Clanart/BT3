### Title
Payout OP_RETURN operator attribution is not cryptographically bound to the actual fronting operator, allowing an operator to be reimbursed for a payout it never funded - ([File: core/src/verifier.rs], [File: core/src/task/payout_checker.rs], [File: core/src/database/verifier.rs])

### Summary
The withdrawal's `payout_payer_operator_xonly_pk` column, which drives `PayoutCheckerTask::run_once` -> `handle_finalized_payout` -> kickoff/Reimburse, is populated purely by parsing raw OP_RETURN bytes from a confirmed payout transaction, with no signature or authentication proving the named operator actually constructed or funded that transaction. Because the withdrawing user's `SinglePlusAnyoneCanPay` signature only commits to input0 and output0, any party who obtains a valid withdrawal signature (trivially true if the attacker is the withdrawing user itself, since it can choose the UTXO/signature/output for its own Citrea `withdraw()` call) can build its own payout transaction reusing that input/output and stamp an arbitrary operator's xonly public key in the OP_RETURN.

### Finding Description
The claimed binding is: `payout_payer_operator_xonly_pk` for withdrawal idx == the operator that actually authorized/funded that payout. This binding is never enforced anywhere in the code path.

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout tx with the user's input signed `KeySpend`, and the OP_RETURN output carries the caller-supplied `operator_xonly_pk` verbatim — it is not itself signed by that operator's key.
- The user's signature is enforced to be `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:174-187`, `core/src/operator.rs:630-637`). Under this sighash type, `Prevouts::One`/single-output commitment applies (`core/src/builder/transaction/txhandler.rs:222-229`), meaning the signature only commits to input0 and output0 — it says nothing about the OP_RETURN output or any other input/output in the final mined transaction.
- On the verifier side, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) determines the attributed operator purely by scanning the mined tx's OP_RETURN bytes and parsing them as an `XOnlyPublicKey` (lines 2312-2328), with no check that this key corresponds to a party that actually signed or funded the transaction, and stores it via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`).
- `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`) simply trusts this `payout_payer_operator_xonly_pk` column when selecting work for `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`).
- `handle_finalized_payout` (`core/src/operator.rs:839-935`) only checks deposit data, an unused/signed kickoff connector, and round bookkeeping — it never verifies that the operator itself produced or funded the underlying payout transaction; it unconditionally proceeds to sign and broadcast a Kickoff aimed at reimbursement.

Exploit flow: an attacker, acting as the withdrawing L2 user, calls Citrea's `withdraw()` to register a withdrawal (idx k) using a UTXO/output/amount and `SinglePlusAnyoneCanPay` signature it fully controls (per the granted attacker capabilities). It then constructs and broadcasts its own payout transaction on Bitcoin L1 that spends that exact withdrawal UTXO with the valid user signature (input0) and pays out to the intended output (output0) using its own additional funding inputs (fully attacker-signed, so consensus-valid), but places a target operator A's `xonly_pk` bytes in the OP_RETURN output instead of any pubkey belonging to itself. Since this OP_RETURN is outside the committed sighash and unauthenticated on the read side, once this transaction confirms and finalizes, `update_finalized_payouts` records `payout_payer_operator_xonly_pk = A`. Operator A's `PayoutCheckerTask` then picks this up via `get_first_unhandled_payout_by_operator_xonly_pk(A)` and calls `handle_finalized_payout`, which produces a legitimate Kickoff for A and drives the round toward a `Reimburse` payout to A from the deposit's move-to-vault collateral — despite A never having built, signed, authorized, or funded this payout.

No existing guard (`Verifier::is_deposit_valid`, `SECP.verify_schnorr` on the withdrawal signature, `only_aggregator_and_self`, DB uniqueness, etc.) checks that the OP_RETURN-named operator is cryptographically linked to the transaction; the signature verification present in the code only validates the user's withdrawal authorization (input0/output0), not the attribution byte string.

### Impact Explanation
This directly matches the explicit Critical category "an operator reimbursed for a payout it never funded." Operator A's kickoff/Reimburse flow releases the deposit's move-to-vault collateral to A as if A had risked its own capital to front the withdrawal, when in fact the payout was paid from funds outside the sanctioned operator-fronting mechanism (or possibly by a colluding/unrelated third party). This can be repeated for any withdrawal and any operator whose xonly public key is public (all operator keys are discoverable, e.g., via `get_x_only_public_key` RPC or `fetch_operator_keys`), so the blast radius spans every deposit/withdrawal and every operator in the system, not just the specific idx-ordering scenario described in the question.

### Likelihood Explanation
The attacker needs only to be an L2 user able to call Citrea's `withdraw()` (fully within the stated unprivileged capability set: choosing withdrawal UTXO bytes, a Schnorr signature and sighash flag, an OP_RETURN, and broadcasting Bitcoin transactions), plus normal transaction fees. No verifier/operator collusion, key compromise, or majority hashrate is required. The only real cost is the transaction fee to get the maliciously-labeled payout confirmed before/instead of any honest attribution; this is a standard, always-available capability, so the finding is highly likely to be reproducible deterministically in a regtest/test harness.

### Recommendation
Bind the OP_RETURN operator attribution cryptographically to the actual operator that authorizes the payout, e.g., require the operator to co-sign a commitment covering the OP_RETURN (or the whole transaction) with its own key, and have `update_finalized_payouts` verify that co-signature before writing `payout_payer_operator_xonly_pk`, rather than trusting bare parsed bytes from the mined transaction's OP_RETURN.

### Proof of Concept
`cargo test` plan (regtest, `MockCitreaClient`, no mainnet/live Citrea):
1. Set up two operators A and B and one deposit as in `core/src/test/deposit_and_withdraw_e2e.rs`.
2. As the "attacker" (test harness playing the withdrawing user), generate a withdrawal (`generate_withdrawal_transaction_and_signature`) with a `SinglePlusAnyoneCanPay` signature over an attacker-chosen input UTXO/output, and register it via the withdrawal path used in `update_citrea_deposit_and_withdrawals`.
3. Manually construct (bypassing `Operator::withdraw`) a payout transaction using `create_payout_txhandler` but pass operator A's `xonly_public_key` as `operator_xonly_pk`, funding the extra inputs from a wallet that is NOT operator A's, and broadcast/mine it (assert `test_mempool_accept` succeeds, showing the OP_RETURN swap doesn't invalidate the user's signature).
4. Mine to finality; run the verifier's `handle_finalized_block` / `update_finalized_payouts`; assert `db.get_payout_info_from_move_txid(...).0 == Some(A_xonly_pk)`.
5. Run `PayoutCheckerTask::run_once` for operator A; assert it returns `Ok(true)`, calls `handle_finalized_payout`, and `mark_payout_handled` is invoked for this withdrawal — asserting the equality "`payout_payer_operator_xonly_pk == A`" while also asserting "A's wallet balance/UTXO set shows no funds spent by A for this payout," demonstrating the binding "attributed operator == actual funder" is violated.
