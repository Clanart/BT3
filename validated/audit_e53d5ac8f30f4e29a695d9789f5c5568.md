### Title
Unvalidated Arbitrary Input Tokens in `placeOrder` Let a Single Blacklistable/Freezable Token Permanently Lock All Escrowed Assets for an Order - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`placeOrder` in `IntentGatewayV2.sol` accepts any ERC-20 as `order.inputs[i].token` with no check on freeze/blacklist authority, pause capability, or any allowlist — directly analogous to the reported SPL "arbitrary input token/freeze authority" issue. Multiple distinct tokens can be escrowed under one `commitment`. Release of that escrow (`_withdraw` in `IntentsBase.sol`) iterates over *all* escrowed tokens in a single atomic loop and reverts the whole call if any single `safeTransfer`/native call fails — which happens if the beneficiary is blacklisted on, or the token itself pauses, any one of the escrowed tokens. Since `_orders[commitment][token]` is decremented in the same loop before the transfer, a revert rolls back every token's release for that commitment, not just the offending one, permanently locking unrelated healthy tokens together with the broken one.

### Finding Description
`placeOrder` (evm/src/apps/IntentGatewayV2.sol:162-383) escrows arbitrary `order.inputs` ERC-20 tokens with zero validation of token safety properties: [1](#0-0) 
Phase 3 then credits escrow per-token under a single `commitment` key, permitting multiple distinct tokens to be bundled into one order/commitment: [2](#0-1) 

The shared release path, `_withdraw` in `IntentsBase.sol`, loops over `body.tokens` and performs `_orders[..] = escrowed - amount` immediately followed by `IERC20(token).safeTransfer(beneficiary, amount)` (or a native `.call`) with no isolation between tokens — one failing transfer reverts the entire function, undoing the decrement for every token in that call: [3](#0-2) 

This function is the single choke point used by:
- `_fillSameChain` / `_fillCrossChain` releasing escrow to a solver's `beneficiary`,
- `_cancelSameChain` and cross-chain refund flows releasing escrow back to the user,
- the cross-chain `RedeemEscrow`/`RefundEscrow` ISMP message handlers that decode a `WithdrawalRequest` and invoke this same withdraw logic (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`).

If any one of the tokens escrowed for a commitment is (a) a regulated/blacklist-capable stablecoin whose issuer freezes the specific `beneficiary` address (equivalent to the SPL freeze-authority scenario) or (b) a token that becomes paused/non-transferable for any reason, then every call attempting to settle or refund that commitment — fill, cancel, or the cross-chain redeem/refund message — reverts unconditionally. There is no per-token try/catch, no skip-and-continue, and no separate reclaim path for the unaffected tokens bundled in the same order. The escrow credit check `if (_orders[commitment][token] != 0) revert InvalidInput()` (line 337) even guarantees each token slot is unique, so a griefer or naturally-blacklisted token can be intentionally paired with legitimate tokens in the same `order.inputs` array by whoever crafts the order (the order creator controls the full input token list at placement time).

### Impact Explanation
This causes permanent loss of funds and denial of service exactly matching the bounty's "stealing or loss of funds" / "logic attacks" categories: legitimate, otherwise-transferable escrowed tokens become permanently unrecoverable because they are bundled in the same atomic release with a blacklisted/frozen token, and the contract has no mechanism to release tokens independently or to detect/skip a stuck token. For cross-chain orders, the `RedeemEscrow`/`RefundEscrow` ISMP message becomes non-processable (repeated `onAccept` reverts) with no alternate recovery path defined in this contract, since `_filled` is only set on the same call path that must succeed atomically with all transfers.

### Likelihood Explanation
The vulnerability is reachable via the fully public, unprivileged `placeOrder` entrypoint — any user can construct an order whose `order.inputs` includes a widely-used regulated token (e.g., USDC/USDT-style tokens with blacklist functions) alongside other assets, or simply place an order in a token that later becomes frozen for the counterparty. No relayer, prover, admin, or governance compromise is required; the trigger condition (issuer freezing an address, or a token pause) is a normal, foreseeable real-world event for many ERC-20s that the protocol does not filter out at `placeOrder` time.

### Recommendation
- Isolate per-token transfers in `_withdraw` so a single failing transfer does not roll back releases of unrelated tokens for the same commitment (e.g., attempt each transfer independently, tracking failures for later retry/claim rather than reverting the whole batch).
- Add an allowlist or minimal safety check for tokens accepted in `order.inputs`/`order.output.assets` at `placeOrder`/`fillOrder` time, consistent with the recommendation in the source report (reject or flag tokens with known pause/blacklist authorities, or restrict escrow to an approved token registry).
- Provide a per-token emergency-recovery path (e.g., governance-gated force-release of the non-stuck tokens in a commitment) so one problematic token cannot hold hostage the rest of the escrow.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [{token: USDC_LIKE_TOKEN, amount: X}, {token: DAI, amount: Y}]`, both escrowed under one `commitment` (`IntentGatewayV2.sol:334-343`).
2. Order is filled or expires; settlement invokes `_withdraw(body, ...)` with `body.tokens` containing both `USDC_LIKE_TOKEN` and `DAI` for the same `beneficiary`.
3. Before settlement, the `beneficiary` (or `msg.sender`/user in the refund case) gets blacklisted on `USDC_LIKE_TOKEN` by its centralized issuer (a normal, expected event for such tokens — not requiring any compromise of Hyperbridge infrastructure).
4. `_withdraw`'s loop reaches the `USDC_LIKE_TOKEN` transfer, `safeTransfer` reverts (`ERC20: transfer to blacklisted account` style revert), and the whole `_withdraw` call reverts — including the `DAI` transfer and the `_orders[commitment][DAI]` decrement that had already executed earlier in the loop.
5. Every subsequent call to `fillOrder`/`cancelOrder`/the cross-chain redeem-escrow `onAccept` handler for this `commitment` reverts identically, permanently locking the `DAI` escrow (and any other healthy token in the bundle) alongside the frozen `USDC_LIKE_TOKEN`, with no code path in `IntentsBase.sol`/`IntentGatewayV2.sol` to release them independently. [4](#0-3)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
