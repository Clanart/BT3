### Title
Stale line-index-based partial-stage selection is applied against a freshly re-diffed file, silently committing unintended content - (File: `app/src/lib/git/apply.ts`, `app/src/models/diff/diff-selection.ts`)

### Summary
GitHub Desktop's partial-commit ("stage individual lines/hunks") feature stores the user's line selection as a set of numeric line indices (`DiffSelection.divergingLines`), computed against a diff snapshot rendered in the Changes view. When the user commits, `stageFiles` → `applyPatchToIndex` re-fetches the diff from disk *at commit time* and reapplies the old index-based selection to it, with no verification that the line content at those indices is unchanged. If the working-tree file is modified between the moment the diff was rendered and the moment the commit executes, the selection silently binds to different content, mirroring the pattern in the report: a value (YT amount / here, "which lines get committed") computed from one state is executed against a different, later state with no bound/consistency check.

### Finding Description
The commit flow is:
1. UI renders a diff via `getWorkingDirectoryDiff` and lets the user select individual lines; this state is captured in `WorkingDirectoryFileChange.selection`, an instance of `DiffSelection` [2](#0-1) , purely indexed by integer line position (`isSelected(lineIndex)`), with no content hash or anchor.
2. On commit, `_commitIncludedChanges` passes the (possibly stale) `files` array — including their `selection` objects captured earlier — straight to `createCommit` [3](#0-2) .
3. `createCommit` calls `stageFiles`, which for partially-selected files calls `applyPatchToIndex` [4](#0-3) .
4. `applyPatchToIndex` re-fetches a brand-new diff from the working directory (`getWorkingDirectoryDiff`) at commit time [5](#0-4)  and builds the patch using `formatPatch`, which walks the **new** diff's hunks and calls `file.selection.isSelected(absoluteIndex)` using the **old** selection object [6](#0-5) .
5. The only mitigation that exists, `withSelectableLines`, runs on a *different* code path — the periodic Changes-tab diff refresh (`updateChangesWorkingDirectoryDiff`) — and even there it only removes indices no longer "includeable," it does not check that a still-includeable index still corresponds to the same textual content [7](#0-6) . There is no guarantee this refresh has run immediately before every commit, and even when it has, index-based pruning cannot detect a line shifted to a different position with the same "includeable" status but different text (e.g. an edit above the hunk that shifts everything down by N lines).

Because `git apply --cached` (used by `applyPatchToIndex`) applies the hand-built hunks positionally, a shifted diff plus a stale index-based selection produces a syntactically valid patch that stages the wrong lines without any error — exactly the "silent corruption of what the user commits" class called out as valid impact.

### Impact Explanation
If content changes in the working tree between the user reviewing/selecting lines and clicking "Commit" — e.g., a file watcher, build tool, linter/formatter, or an npm script from the cloned repository (`package.json` scripts, husky-style `core.hooksPath` hooks tracked in the repo) rewrites the file — the commit produced by Desktop can silently include lines the user never selected, or exclude lines the user did select, with no warning or error. This is a "silent corruption of what the user commits" impact as scoped by the valid-impact list: the user believes they are committing exactly the lines shown in the diff view, but the actual staged/committed content is determined by stale integer offsets replayed against different text.

### Likelihood Explanation
This requires that the working-tree file changes in the narrow window between diff render and click-Commit, which is plausible for any repo that ships automated tooling (formatters/build watchers/git hooks) the user runs alongside Desktop, but not attacker-triggerable to a chosen outcome — the attacker can only encourage a race, not target specific bytes. This reduces confidence to Medium/Low-severity analog territory (similar to the original Medium-severity slippage report, which likewise depends on external state moving between simulation and execution rather than being a deterministic exploit).

### Recommendation
Bind partial selections to content, not raw indices: store a lightweight content fingerprint (e.g., hash of each selected hunk's context+changed lines) alongside `divergingLines`, and before calling `applyPatchToIndex`/`formatPatch`, re-diff and verify the fingerprints still match; if they don't, abort staging that file and surface a "changes detected, please re-review" error to the user instead of silently applying a positionally-stale selection.

### Proof of Concept
Not independently executable from static analysis alone — reproducing requires: (1) open a modified file with several hunks in Desktop, (2) partially select lines via the line-by-line staging UI, (3) before clicking Commit, externally modify the file above the selected hunk (e.g. via another editor or a running formatter) so that line offsets shift but hunks remain "includeable", (4) click Commit and inspect `git show` on the resulting commit to confirm the staged lines don't match what was visually selected in the UI at selection time. I was not able to run this end-to-end in the current environment; the code paths cited above establish the mechanism but the exact timing window (how often `updateChangesWorkingDirectoryDiff` runs and whether it always precedes a commit click) would need runtime verification, which requires a live Desktop session rather than static code inspection.
