### Title
Batched, all-or-nothing pool/plotNFT reward-claim spend bundle lets a single invalid/stale reward coin block claiming of all other legitimately claimable rewards - (File: chia/pools/pool_wallet.py)

### Summary
`PoolWallet.claim_pool_rewards` gathers every unspent farming-reward coin (up to `max_spends_in_tx`) into a single chained `absorb_spend` sequence and submits them as one atomic `WalletSpendBundle`. Because Chia spend bundles are all-or-nothing, if any single one of the batched reward coins fails to validate (e.g. it was already claimed/spent, is stale in the local coin store, or otherwise fails a condition), the entire spend bundle is rejected, and none of the other, otherwise perfectly valid, reward coins in that batch get claimed. This mirrors the reported `SdtRewardReceiver::_withdrawRewards` pattern, where one problematic reward transfer in a loop prevents legitimate claims of unrelated rewards from completing.

### Finding Description
`claim_pool_rewards` loops over `unspent_coin_records`, builds one `absorb_spend` per reward coin via `create_absorb_spend`, and accumulates them into `all_spends`, which becomes a single `WalletSpendBundle`: [1](#0-0) 

Each `absorb_spend` is chained off `last_solution`, meaning the entire batch is a single dependent, atomic transaction rather than independent, separately-submittable spends. If the coin-store snapshot used to build `unspent_coin_records` is stale relative to full-node state (e.g. a reward coin was already absorbed by a previous unconfirmed/confirmed transaction, or a race/reorg has invalidated one coin), the resulting spend bundle will fail full-node/mempool validation as a whole (e.g. double-spend or coin-not-found), and the transaction that also would have legitimately claimed every other unspent, unclaimed reward coin in that batch is rejected outright.

The `PlotNFT2Wallet.claim_rewards` path exhibits the same structural pattern for `PlotNFT` rewards, using `AssertCoinAnnouncement`-chained delegated spends across every reward coin in one bundle: [2](#0-1) 

In both cases there is no mechanism to detect and exclude the one problematic coin before building/submitting the bundle, nor any fallback to claim the remaining valid coins if one fails; the caller must manually diagnose and remove the offending coin/tx and retry the whole claim.

### Impact Explanation
A user with several outstanding, individually-valid pool or plotNFT rewards can be denied access to ALL of them if even one reward coin in the batch is problematic (stale, already spent by a concurrent partial claim, or otherwise invalid). This is a spend-triggered transaction-processing halt for the wallet's reward-claim flow: legitimate reward coins remain unclaimed and effectively locked behind the one bad coin until the user manually identifies and works around it (e.g., by trimming `max_spends_in_tx` or waiting for chain state to catch up), directly analogous to the original USDT-blacklist DoS pattern.

### Likelihood Explanation
This can occur under ordinary operational conditions without any attacker: stale local coin-store state, a partially-confirmed prior claim, mempool/full-node race conditions, or reorgs are all realistic ways for one reward coin among many to become unspendable while the others remain valid. Because the batching and chaining are unconditional up to `DEFAULT_MAX_CLAIM_SPENDS`, larger batches (more accumulated unclaimed rewards) increase the chance that at least one coin is problematic, making this more likely to manifest for pool operators/farmers who claim infrequently.

### Recommendation
Before aggregating reward coins into a single `WalletSpendBundle`, validate each candidate coin's spendability against current full-node/mempool state (not just local cached records), and drop/skip any that fail this check instead of including them in the atomic bundle. Alternatively, support submitting reward claims in smaller, independently retryable sub-batches so a single bad coin only removes itself (and coins chained after it) from that specific attempt rather than blocking the full claim set, and surface a clear error identifying which coin caused the failure so it can be excluded on retry.

### Proof of Concept
1. A pool farmer accumulates N unclaimed pool reward coins (`p2_singleton` coins) tracked in the wallet's local coin store.
2. One of those N coins becomes actually unspendable from the full node's perspective (e.g., it was already absorbed in a previous transaction that confirmed after the local snapshot was taken, or a reorg reverted its funding).
3. The farmer calls `pw_absorb_rewards` / `PoolWallet.claim_pool_rewards`, which builds one chained `absorb_spend` per coin among all N coins into a single `WalletSpendBundle` per [3](#0-2) .
4. The mempool/full node rejects the entire bundle (e.g. `DOUBLE_SPEND` or coin-not-found for the one bad coin).
5. None of the other N-1 legitimately claimable reward coins are claimed, even though they were all individually spendable; the farmer must manually identify the bad coin/tx before a retry can succeed.
