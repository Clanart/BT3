### Title
Cross-Endpoint HMAC Signature Replay Between Webhook and Extension Verification - (File: `lib/shopify_app/controller_concerns/payload_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` and `ShopifyApp::ExtensionVerificationController` both delegate signature validation to the exact same `PayloadVerification#hmac_valid?` method, computing `HMAC-SHA256(app_secret, request.raw_post)` with no binding to the endpoint, action, topic, or any nonce/order-id. This mirrors the reported bug class: the same signature format and validation logic is reused across functionally distinct endpoints, so a signed payload legitimately produced for one purpose can be replayed against the other endpoint.

### Finding Description
`PayloadVerification#hmac_valid?` computes a raw HMAC over only the request body bytes, using the app's shared secret: [1](#0-0) 

This single verification routine is reused verbatim by two independent, differently-purposed controllers:
- `WebhookVerification#verify_request`, which gates the generic webhook receiver: [2](#0-1) 
- `ExtensionVerificationController#verify_request`, which gates extension endpoints (e.g. marketing activity extensions): [3](#0-2) 

Neither the HMAC input nor the check itself incorporates any value that ties the signature to a specific route, action, topic, or one-time identifier — the "topic" for webhooks is only present as an `X-Shopify-Topic` header, and it is not part of the signed data at all, and no nonce/order-id tracking exists to prevent reuse. Consequently, any raw body whose HMAC validates on one of these endpoints will also validate on the other endpoint, and can be replayed indefinitely (no expiry or single-use enforcement is present), exactly matching the reported "same signature format and validation logic reused across different functions" bug class.

### Impact Explanation
If an attacker can obtain (or influence the content of) any body+HMAC pair that is valid for one verification concern — for instance, a webhook payload delivered to a store they control, or any other integration point sharing the app secret's HMAC — they can replay that exact body and its HMAC header against the other verification-gated endpoint (e.g. the extension controller) and have it accepted as authentic, even though it was never signed for that destination or action. This breaks the intended per-endpoint authenticity guarantee of the HMAC check and is a cross-function accepted forged signed request, matching the class of vulnerability described in the report.

### Likelihood Explanation
Exploitation requires the attacker to obtain a valid (body, HMAC) pair signed with the app secret — this is realistic in multi-tenant or self-service scenarios where the attacker controls their own installed shop and can trigger webhook deliveries with content they influence, then replay the resulting signed payload against the extension endpoint (or vice versa) of the same app instance. The likelihood is moderate: it depends on the specific app's endpoints and whether the replayed body happens to satisfy the target action's business logic, but the underlying signature-validation weakness (no context binding, no replay protection) is unconditionally present in the library code.

### Recommendation
- Bind the HMAC/signature to endpoint- or purpose-specific context (e.g., include a domain separator such as the route/action name or expected topic in the signed data), rather than validating solely `HMAC(secret, raw_post)` shared identically across all verification concerns.
- Track consumed webhook/extension identifiers (e.g., Shopify's `X-Shopify-Webhook-Id`) to reject replays.
- Consider migrating to a stronger typed/structured signing scheme so signatures cannot be reinterpreted across different verification contexts.

### Proof of Concept
1. An attacker-controlled shop installs the app and triggers a webhook delivery whose JSON body content the attacker can shape.
2. The app receives the webhook at the `WebhooksController`/`WebhookVerification` endpoint; the raw body and its `X-Shopify-Hmac-Sha256` header are valid per `hmac_valid?`.
3. The attacker captures this exact `raw_post` body and HMAC header value.
4. The attacker replays the same body and `X-Shopify-Hmac-Sha256` header as a POST to any endpoint protected by `ExtensionVerificationController` (or another `PayloadVerification`-based endpoint) belonging to the same app installation.
5. `hmac_valid?` returns true because it only checks `HMAC(secret, raw_post)` — with no route, topic, or purpose binding — so the forged/replayed request is accepted as authentic on the unrelated endpoint.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
