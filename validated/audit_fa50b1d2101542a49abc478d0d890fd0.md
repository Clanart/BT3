The fee/weight path in `send.rs` looks promising — checking whether the OP_RETURN data output is excluded from the size/fee computation.### Title
`SignableTransaction::new` excludes the OP_RETURN data output from the size/fee computation, causing transactions to pay a lower fee rate than requested and potentially fall below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the KangarooVault bug — where `premiumCollected` was counted in the token price while the `performanceFee` deducted from it was omitted, letting a withdrawal evade a charge — `SignableTransaction::new` adds the caller-supplied `data` OP_RETURN output to the transaction's outputs while omitting it from `calculate_weight_vbytes`, the function that determines `vbytes` and hence `needed_fee` and the minimum-relay-fee check. The charge (fee) is computed on a smaller transaction than the one actually signed and broadcast.

### Finding Description
`SignableTransaction::new` pushes an `OP_RETURN` output into `tx_outs` when `data` is supplied, at `networks/bitcoin/src/wallet/send.rs:194-202`. However, both weight calculations only account for `payments` and the optional `change` output — `calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204 and `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` at line 226 — and `calculate_weight_vbytes` itself (lines 62-99) builds its template transaction solely from `payments` plus `change`, never including an OP_RETURN output. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change` (line 227) are computed on a vsize smaller than the real transaction by the full size of the OP_RETURN output (8-byte value + script length + `OP_RETURN` + push opcode + up to 80 data bytes, ~91 non-witness bytes ≈ 364 weight units ≈ 91 vbytes).
- The `TooLowFee` check at line 211 compares the underestimated `needed_fee` against the minimum relay fee scaled by the underestimated `vbytes`, so a transaction can pass the check while its true fee rate is below `DEFAULT_MIN_RELAY_TX_FEE`.
- When `change` is provided, the change output's value is set to `input_sat - payment_sat - fee_with_change` (line 228-230), so the actual fee paid (`fee()` at lines 138-141, `sum(inputs) - sum(outputs)`) equals the underestimated `fee_with_change`. The underpayment is silently absorbed as a lower effective fee rate rather than being caught anywhere.

Like the original bug, a value legitimately present in one accounting path (the real output set) is missing from the parallel path that computes the deduction applied to it.

### Impact Explanation
A transaction built with `data` pays up to ~`91 * fee_per_vbyte` satoshis less than the caller requested per the actual transaction size, and `needed_fee()`/`fee()` report inconsistent values (`needed_fee` understates what `fee` should be for the real vsize). If `fee_per_vbyte` is at or near the minimum relay boundary, the resulting transaction's true fee rate can fall below `DEFAULT_MIN_RELAY_TX_FEE` despite the explicit guard, making it non-relayable/non-confirming — funds committed as inputs become unspendable via this transaction until a replacement is constructed, and any protocol flow treating `SignableTransaction` as paying a known fee rate is wrong.

### Likelihood Explanation
Deterministic whenever `data` is `Some(_)`: the miscount happens on every construction, no race or adversarial ordering needed. The trigger is fully within the caller's control via the public `data` argument to `SignableTransaction::new`.

### Recommendation
Include the OP_RETURN output in the size estimate. In `SignableTransaction::new`, either pass the `data`-derived `TxOut` (or the already-built `tx_outs` including the OP_RETURN) into `calculate_weight_vbytes` for both the no-change and with-change computations, or change `calculate_weight_vbytes` to accept the full output list. Recompute the min-fee check against the corrected `vbytes`.

### Proof of Concept
Construct two `SignableTransaction`s identical except `data: Some(vec![0; 80])` vs `data: None`, with a `change` address and `fee_per_vbyte` chosen so `needed_fee` exactly equals the min relay fee for the computed `vbytes`:

```rust
let tx_no_data = SignableTransaction::new(inputs.clone(), &payments, Some(change.clone()), None, fee).unwrap();
let tx_data = SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0; 80]), fee).unwrap();

// Both report the same needed_fee despite tx_data being ~91 vbytes larger
assert_eq!(tx_no_data.needed_fee(), tx_data.needed_fee());
// The real transaction is larger than the size the fee was priced for
assert!(tx_data.transaction().vsize() > tx_no_data.transaction().vsize());
// Therefore tx_data's true fee rate (fee() / actual vsize) is strictly lower
// than the requested fee_per_vbyte, and can fall below the relay minimum
// even though TooLowFee was not raised.
```
