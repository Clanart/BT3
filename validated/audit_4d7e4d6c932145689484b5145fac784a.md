### Title
Legacy `url.parse()` host-parsing quirks are used for GitHub-account/token trust decisions on attacker-controlled remote URLs - (File: `app/src/lib/find-account.ts`, `app/src/lib/repository-matching.ts`)

### Summary
The Curve report's root cause was a single logical operation (`get_dy`) being implemented against two incompatible interfaces, so code written for one pool's ABI silently mis-evaluated data from a pool using the other ABI. The same interface-mismatch pattern exists in GitHub Desktop's URL-hostname extraction: the app has two different URL-parsing "interfaces" for the same operation - deriving a hostname from an attacker-influenced string - and it is not guaranteed that they agree with each other or with what Git itself will actually connect to.

### Finding Description
Desktop derives the "hostname" of a remote/clone URL in two structurally different ways:

1. A hand-written regex parser, `parseRemote()`, used to extract `hostname`/`owner`/`name` from an arbitrary, attacker-supplied remote URL string: [1](#0-0) [2](#0-1) 

2. Node's deprecated legacy `url.parse()` (imported as `import * as URL from 'url'`), used to derive the hostname of the *trusted* account endpoint that the regex-derived hostname is compared against: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

These two comparisons (`parsedURL.hostname === parsedEndpoint.hostname`) decide which stored `Account` (and therefore which OAuth token) is considered "the right account" for a remote URL - i.e., they are trust/authorization decisions, not just cosmetic. Elsewhere in the same codebase, the exact same kind of hostname derivation is instead done with the modern, stricter WHATWG `URL` constructor, e.g. `findGitHubTrampolineAccount`: [8](#0-7) 

This shows the codebase treats "get the hostname of a URL for trust purposes" as two different interfaces depending on the call site: the legacy, permissive Node `url.parse()` (used by `parseRemote`'s callers, `enterprise-validate-url.ts`, `untrusted-certificate.tsx`, `update-remote-url.ts`, `api.ts`) versus the modern WHATWG `URL` (used by the trampoline credential path and `getEnterpriseAPIURL`/parts of `getHTMLURL`). Node's own documentation explicitly warns that the legacy URL API's parsing of `host`/`hostname` diverges from the WHATWG algorithm in edge cases (userinfo handling, backslash normalization on "special" schemes, IDNA/punycode handling, and malformed-authority tolerance) and that this divergence has historically been the basis of host-confusion bugs. Because Git itself constructs its actual outgoing connection using its own URL parsing (which, for HTTPS remotes, follows RFC 3986 / browser-like semantics much closer to WHATWG than to Node's legacy parser), any string for which `url.parse()`'s `hostname` disagrees with the hostname Git will actually connect to breaks the invariant "the account we attach to this remote is the account whose token is authorized for the host Git will contact."

### Impact Explanation
If an attacker can craft a remote/clone URL (e.g. distributed via a shared `.git`/`.desktop` project, a "Clone repository" deep link, or a forked repo's remote list) for which:
- `parseRemote()`'s regex (or `url.parse()`) reports `hostname === 'github.com'` (or the user's GHE host), while
- Git's own connection logic actually resolves/connects to a different, attacker-controlled host,

then `findAccountForRemoteURL` / `matchGitHubRepository` would select the user's real GitHub.com/GHE `Account` as "the" account for that remote. Downstream code paths (PR association, "View on GitHub", repo metadata fetch, and update-remote-url logic) treat that association as authoritative. In the worst case this class of bug enables credential/token exposure to a host the user did not intend to trust, or corruption of what the user believes they are pushing to/viewing (e.g., PR/branch association attached to the wrong, attacker-controlled repository) - matching the "silent corruption of what the user commits/pushes" and "credential/token exfiltration" impact categories.

### Likelihood Explanation
This is lower-confidence than a directly reproduced exploit: I was not able to execute Git or Node's legacy `url.parse()` in this environment to confirm a concrete input string where the regex/`url.parse()` hostname and Git's actual connection target diverge. The finding is an architectural analog (two different URL-hostname "interfaces" used for the same trust decision, one of them explicitly deprecated by Node for known parsing-inconsistency reasons) rather than a demonstrated proof-of-exploit. Confirming exploitability requires finding a specific malformed-URL construction (e.g. involving userinfo `@`, encoded characters, or backslashes) that both (a) passes `parseRemote`'s regex/`url.parse()` as `github.com` and (b) causes the installed Git binary to actually connect elsewhere - this needs local Git-version-specific testing that isn't possible from static analysis alone.

### Recommendation
- Standardize on a single, well-defined URL/hostname-parsing interface (the WHATWG `URL` API) for every place a URL's hostname feeds into a trust or account-matching decision, and remove remaining legacy `url.parse()` usages in `find-account.ts`, `repository-matching.ts`, `api.ts`, and `update-remote-url.ts`.
- Where a custom regex (`parseRemote`) must be used because `url.parse`/`URL` cannot parse SSH-style (`git@host:owner/repo`) URLs, explicitly cross-validate its extracted hostname against Git's own interpretation of the remote (e.g., via `git ls-remote --get-url` or `git remote get-url`) before using it for account/token selection, rather than trusting the regex output as ground truth.
- Add fuzz/differential tests that feed the same crafted URL strings to `parseRemote`, `url.parse`, and `new URL()` and assert they always agree on `hostname`, specifically targeting inputs with embedded `@`, backslashes, and percent-encoding.

### Proof of Concept
Not independently reproduced (no Git/Node execution environment available for differential testing). The pattern to test:
```js
import * as URL from 'url'
const legacy = URL.parse('https://github.com\\@attacker.example/owner/repo.git')
const whatwg = new URL('https://github.com\\@attacker.example/owner/repo.git')
console.log(legacy.hostname, whatwg.hostname)
```
and comparing both against the host Git actually contacts when cloning the same string, e.g.:
```
git clone 'https://github.com\@attacker.example/owner/repo.git'
```
would be the concrete next step to confirm or refute exploitability of this analog before treating it as a confirmed vulnerability rather than a plausible bug-class match.

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
