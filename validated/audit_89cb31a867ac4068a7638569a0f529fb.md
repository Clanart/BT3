### Title
Webhook HMAC verification does not bind the `X-Shopify-Shop-Domain` header, enabling cross-shop webhook forgery/replay - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` only HMAC-validates the raw request body (`request.raw_post`). The shop identity used by the app (`shop_domain`, read from the `X-Shopify-Shop-Domain` header) is never included in the HMAC computation. Because the webhook secret used for `hmac_valid?` is the app's single, shop-independent secret, a signature that is valid for one shop's webhook payload is valid for that exact payload for any other shop domain header value. This is the same missing-binding pattern described in the external report (a signature not bound to the executing context — chain ID there, shop identity here — can be replayed in a different context and still validate).

### Finding Description
`hmac_valid?` in `lib/shopify_app/controller_concerns/payload_verification.rb` computes: [1](#0-0) 
using only `data` (the raw POST body) and the app-wide `ShopifyApp.configuration.secret`/`old_secret` — the same secret for every shop that has installed the app.

`verify_request` in `lib/shopify_app/controller_concerns/webhook_verification.rb` only checks this HMAC against the body, and separately exposes an unauthenticated `shop_domain` helper sourced from a request header that is not part of the signed material: [2](#0-1) 

The gem's own documented usage pattern for custom webhook controllers passes this unauthenticated `shop_domain` value directly into background jobs that persist/act on shop data: [3](#0-2) 

Because the HMAC secret is shared across all shops (it is the app's client secret, not a per-shop secret), and the HMAC only covers the body, an attacker who controls any shop that has installed the target app (e.g., their own development/test store) can capture a legitimately-signed webhook body+HMAC pair for their own shop, then resend that exact body and HMAC to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `hmac_valid?` still validates because the header is not covered by the signature, and `verify_request` passes the request through to the controller/job with an attacker-controlled `shop_domain`.

### Impact Explanation
This allows an attacker (any merchant who has installed the vulnerable app) to inject forged, "verified" webhook data attributed to an arbitrary victim shop domain into any app built on `ShopifyApp::WebhookVerification`/`PayloadVerification` that relies on the `shop_domain` helper (as the docs instruct). Depending on what the consuming job does with `shop_domain` (e.g., look up/update `Shop` records, trigger uninstall/redact flows, write per-shop data), this can result in cross-shop data corruption, spoofed privacy/uninstall events for a victim shop, or other cross-tenant state changes — a concrete cross-shop access/forged-signed-request outcome.

### Likelihood Explanation
Exploitation only requires the attacker to have legitimately installed the app on any shop (even their own store) to obtain one valid `(body, HMAC)` pair, and then send an HTTP POST to the app's webhook endpoint with a modified `X-Shopify-Shop-Domain` header. No secret leakage, no host-operator access, and no privileged relationship to the victim shop is required, making this reachable from a low-privilege, unrelated-merchant actor.

### Recommendation
Bind the shop identity into the verified material: either include `shop_domain` (and/or webhook id/topic/timestamp) in the HMAC computation, or independently verify the `X-Shopify-Shop-Domain` header against data actually present in the authenticated payload before trusting it downstream. At minimum, document/enforce that consumers of `WebhookVerification` must not use the unauthenticated `shop_domain` header as a trust anchor without additional shop verification (e.g., cross-checking against `ShopifyApp::SessionRepository` for an existing, matching session before acting on shop-scoped side effects).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body `B` and its `X-Shopify-Hmac-Sha256` header value `H` sent to the app's webhook endpoint.
2. Replay a POST to the same endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `hmac_valid?(B)` in `payload_verification.rb` succeeds because the secret and body are unchanged, so `verify_request` in `webhook_verification.rb` allows the request through.
4. Any controller/job using `shop_domain` (per the pattern in `docs/shopify_app/webhooks.md`) processes the payload as if it originated from `victim.myshopify.com`. [4](#0-3) [5](#0-4)

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
