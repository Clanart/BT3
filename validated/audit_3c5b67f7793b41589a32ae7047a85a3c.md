### Title
Royalty basis-point truncation can zero out required NFT royalty payments during offer settlement - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
The Nouns Builder bug is a "rounds-to-zero" integer-division flaw: `quorum = totalSupply * bps / 10000` can truncate to 0, silently disabling a governance safety check. The `chia-blockchain` NFT royalty machinery has the same arithmetic shape — royalty amounts are computed as `amount * percentage // 10000` (basis points, denominator `MAX_ROYALTY_BASIS_POINTS = 10000`) — and the same truncation-to-zero can occur when the requested/offered fungible amount is small relative to the royalty percentage, silently reducing an intended non-zero royalty obligation to `0`.

### Finding Description
`compute_royalty_amount` performs the basis-point calculation with floor integer division: [1](#0-0) 

`royalty_calculation`, used to summarize/preview royalties for an offer, does the same truncating division: [2](#0-1) 

When constructing an NFT-for-fungible-asset offer, `make_nft1_offer` computes `trade_prices` (the fungible amount divided across NFTs being offered) and then computes royalty payments per required NFT using this same truncating formula: [3](#0-2) 

Because `amount // offer_side_royalty_split` and `percentage // MAX_ROYALTY_BASIS_POINTS` are both floor divisions applied in sequence, a counterparty (maker or taker) that structures an offer with small per-NFT trade prices, or that requests many NFTs royalty-split against a fungible amount, can drive the computed `trade_price * percentage // 10000` result to exactly `0` even though `percentage > 0`. The code is aware of this edge case — it explicitly filters out trade prices whose royalty would be zero before curry-ing them into the outer puzzle's `trade_prices_list`: [4](#0-3) 

This filtering, however, is done unilaterally by the *offering* wallet's own code when constructing its side of the trade. Any spend bundle submitted to the mempool is only constrained by whatever puzzle reveal/solution the submitter (a taker or a hand-crafted client) chooses to provide — the enforcement of "correct royalty was paid" is performed by the on-chain ownership/transfer-program puzzle (`NFT_OWNERSHIP_TRANSFER_PROGRAM_ONE_WAY_CLAIM_WITH_ROYALTIES`, loaded via `NFT_TRANSFER_PROGRAM_DEFAULT`) via announcement matching between the fungible-asset spend and the NFT ownership-layer spend: [5](#0-4) 

Because the underlying royalty math is a `// 10000` floor division with no minimum-payment floor, a spend bundle can legitimately construct `trade_prices_list` entries (or an entire offer) where the resulting royalty amount computed on-chain is `0`, and the on-chain announcement/assert mechanism will accept it as valid — there is no consensus-level minimum-royalty enforcement analogous to what would prevent the Nouns Builder `quorum()==0` case. I was unable to fully verify the exact on-chain CLVM source of `NFT_OWNERSHIP_TRANSFER_PROGRAM_ONE_WAY_CLAIM_WITH_ROYALTIES` (it ships as compiled bytes via `chia_puzzles_py.programs` rather than a `.clsp`/`.clvm` source file visible in the index), so I cannot confirm with certainty whether the on-chain puzzle itself independently re-derives and enforces a non-zero royalty floor beyond what the wallet-side Python computes.

### Impact Explanation
If confirmed at the CLVM layer, this allows an offer counterparty to structure trade amounts/percentages such that a nonzero configured royalty percentage on an NFT resolves to zero royalty payment on settlement, depriving the NFT creator/royalty address of compensation they are otherwise entitled to under the NFT's royalty terms — an economic griefing/theft-of-royalty issue analogous to the "quorum has no effect" finding, though bounded in size by the truncation remainder (at most `percentage/10000` of a small trade amount), similar to how the original report was judged Medium severity due to rounding-bounded impact.

### Likelihood Explanation
Requires no special privilege — any wallet user constructing or responding to an offer (maker or taker) chooses the offered/requested amounts and can pick values that make the basis-point division for royalty resolve to zero for a target NFT while the nominal royalty percentage remains nonzero. This is a normal, permissionless offer-construction interaction, so exploitation likelihood is a function of whether counterparties choose (or a malicious offer script constructs) qualifying small-amount trades.

### Recommendation
- Enforce a minimum non-zero royalty (e.g., round up rather than floor, or require a minimum trade price/royalty amount, or reject offers where a positive royalty percentage resolves to a zero royalty payment) both in the wallet-side calculation (`compute_royalty_amount`, `royalty_calculation`, `make_nft1_offer`) and, more importantly, verify whether the on-chain transfer-program puzzle enforces any such floor; if not, treat this as a puzzle-level gap requiring a CHIP/consensus-level fix rather than a client-side-only mitigation.
- Add an explicit check that rejects/warns when `percentage > 0` but computed royalty `== 0`, rather than silently proceeding (as is partially done today only for the *offering* side's `trade_prices_list` filter).

### Proof of Concept
Not independently reproduced against the compiled on-chain puzzle (source not available in the indexed codebase); the client-side truncation is directly demonstrable via the existing unit test asserting truncation-to-zero: [1](#0-0) 
e.g. `compute_royalty_amount(offered_amount=-50, royalty_split=1, percentage=100)` returns `0` despite `percentage=100` (1%) being nonzero, showing the exact "quorum-style" rounding-to-zero behavior. Full on-chain confirmation (whether the settlement puzzle independently re-validates and rejects zero-royalty trades) requires inspecting the compiled `NFT_OWNERSHIP_TRANSFER_PROGRAM_ONE_WAY_CLAIM_WITH_ROYALTIES` CLVM logic, which was not available for review in this pass — recommend a Devin session with full repository/CLVM decompilation access to confirm.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```

```python
    @staticmethod
    def royalty_calculation(
        royalty_assets_dict: dict[Any, tuple[Any, uint16]],
        fungible_asset_dict: dict[Any, uint64],
    ) -> dict[Any, list[dict[str, Any]]]:
        summary_dict: dict[Any, list[dict[str, Any]]] = {}
        for id, royalty_info in royalty_assets_dict.items():
            address, percentage = royalty_info
            summary_dict[id] = []
            for name, amount in fungible_asset_dict.items():
                summary_dict[id].append(
                    {
                        "asset": name,
                        "address": address,
                        "amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
                    }
                )

        return summary_dict
```
