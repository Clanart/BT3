### Title
Duplicate `ReceivedOutput` inputs inflate `input_sat`, letting unverified claimed UTXO value mint phantom spendable balance - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

Analogous to the Stellar inflation bug (value created from nothing by exploiting a validation gap), `SignableTransaction::new` computes the total spendable input value by summing `input.output.value` over every entry in `inputs` without checking that the claimed `outpoint`s are unique or that the claimed `TxOut` matches the real on-chain output. `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) deserializes `offset`, `output`, and `outpoint` from raw bytes with no consistency or existence checks, so an unprivileged party who can feed bytes into `ReceivedOutput::read` (or cause duplicate scan results to be supplied) can inflate the wallet's accounting of its own funds.

### Finding Description

`SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256) builds the transaction as follows:

- `input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum()` — every entry contributes its *claimed* value, with no dedup on `outpoint` (send.rs:175).
- `tx_ins` is built verbatim from `input.outpoint` for each entry (send.rs:177-185).
- `input_sat` is the sole solvency check: `if input_sat < (payment_sat + needed_fee) { NotEnoughFunds }` (send.rs:215-221).
- Change is allocated from `input_sat - payment_sat - fee_with_change` (send.rs:228-234).

Two independent inflation paths exist:

1. **Duplicate inputs.** If the same `ReceivedOutput` (same `outpoint`) appears twice in `inputs`, its value is counted twice in `input_sat`, yet only one real UTXO exists. The phantom value flows into `payment_sat` headroom and into the change output amount (send.rs:230), which commits to paying out value that was never received.

2. **Forged `TxOut` via `ReceivedOutput::read`.** `ReceivedOutput::read` (mod.rs:122-134) accepts an arbitrary `TxOut` (including an arbitrary `value`) and arbitrary `OutPoint` without verifying the outpoint exists on-chain or that the script corresponds to `offset`. `multisig` (send.rs:273-285) only checks `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — it never validates `value` or `outpoint` against chain state (it cannot). A crafted `ReceivedOutput` therefore inflates `input_sat` by any amount.

Secondary issue: `calculate_weight_vbytes` is called with `payments` only (send.rs:204, 226) and never accounts for the OP_RETURN output pushed at send.rs:194-202, so `needed_fee` is understated when `data` is present, compounding the incorrect fee/change math.

### Impact Explanation

This is the direct analog of an inflation exploit mapped onto Serai's wallet shape: the signer believes it controls more bitcoin than exists.

- The wallet reports funds as spendable that are not spendable: `SignableTransaction` happily constructs (and the threshold then signs, via `TransactionSignMachine::sign` at send.rs:355-398) a transaction whose input set is either duplicated or references nonexistent/misstated UTXOs. Such a transaction is consensus-invalid, so the "received" and allocated value — payments and change sized by phantom `input_sat` — can never be realized.
- In the duplicated-input case, the change output (send.rs:230) is credited `input_sat - payments - fee`, where `input_sat` was inflated by the duplicate's value, so the constructed tx commits to distributing nonexistent coins.
- Because `Prevouts::All` commits to the forged prevout amounts in the BIP-341 sighash, every signature produced over these inputs is for an invalid tx — a wasted signing round and permanently stuck accounting (the real UTXOs remain unspent while the book-keeping believes they funded payments).

Severity: **Medium** — attacker-inflated reported balance and guaranteed-invalid signed transactions (funds reported received that are not spendable), rather than on-chain theft, since consensus rejects the tx.

### Likelihood Explanation

Reachable by an unprivileged party under the stated model: `ReceivedOutput::read` is an explicitly in-scope untrusted-byte API and performs zero validation. Any integrator path that deserializes or aggregates `ReceivedOutput`s from an untrusted source (or that can be induced to pass duplicate scan results into `SignableTransaction::new`) triggers the double-counting deterministically — the sum at send.rs:175 has no `HashSet`/duplicate check and `TransactionError` has no variant for it. The attack requires no collusion, no leaked keys, and no malicious validator.

### Recommendation

- In `SignableTransaction::new`, reject duplicate `outpoint`s (insert into a `HashSet` and error on re-insertion) before computing `input_sat`.
- In `ReceivedOutput::read` / at the scanner boundary, verify `output` against the on-chain UTXO for `outpoint` (or at minimum bind `output` to `outpoint` cryptographically at scan time and refuse externally supplied `TxOut`s).
- Include the OP_RETURN output in `calculate_weight_vbytes` so `needed_fee` reflects the true transaction weight.

### Proof of Concept

```rust
// networks/bitcoin context: signable-tx construction
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction};

// One real output worth 1000 sats at outpoint P
let real: ReceivedOutput = /* from Scanner::scan_transaction */;
assert_eq!(real.value(), 1000);

// Supply the same output twice — no dedup in SignableTransaction::new
let inputs = vec![real.clone(), real.clone()]; // input_sat = 2000, only 1000 exists

let tx = SignableTransaction::new(
  inputs,
  &[(payment_script, 1500)], // passes DustPayment check; exceeds real balance
  Some(change_script),
  None,
  fee_per_vbyte,
).unwrap();
// send.rs:215 NotEnoughFunds check passes because input_sat (2000) >= 1500 + fee
// The resulting tx has two TxIns both spending P -> consensus-invalid,
// yet the wallet accounted a 1500-sat payment as funded.
```

Similarly, via `ReceivedOutput::read`, bytes encoding `{ offset: s, output: TxOut { value: 21_000_000e8, script_pubkey }, outpoint: O }` are accepted verbatim (mod.rs:122-134); only `script_pubkey ↔ offset` consistency is checked later in `multisig` (send.rs:277), never `value` or `outpoint`, so `input_sat` inflates arbitrarily.
