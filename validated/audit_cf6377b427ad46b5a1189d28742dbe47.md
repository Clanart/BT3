## Analog Found

### Title
DeliverTxHookWasmGasLimit hardcoded gas budget can silently drop synthetic EVM Transfer logs for successful CW20/CW721/CW1155 pointer transactions - (File: app/receipt.go)

### Summary
The Sherlock report describes a hardcoded, chain-agnostic gas limit (500k for a Chainlink VRF callback) that is too low on some L2s, causing a downstream operation to fail even though the triggering transaction succeeded. Sei-chain has an analogous fixed/param-bounded gas budget — `DeliverTxHookWasmGasLimit` (default `300000`) — that bounds the post-execution translation of CosmWasm events into synthetic EVM receipt logs for CW20/CW721/CW1155 pointer contracts. If this fixed budget is exhausted mid-translation, the translation silently fails for the remainder of the transaction's events while the underlying (successful, state-changing) CW20/721/1155 transfer still went through.

### Finding Description
`AddCosmosEventsToEVMReceiptIfApplicable` is called as a `DeliverTx` hook after a Cosmos/CosmWasm transaction succeeds [1](#0-0) . It creates a gas meter bounded by `app.EvmKeeper.GetDeliverTxHookWasmGasLimit(ctx)`, whose default value is a hardcoded `300000` [2](#0-1) , and then iterates over every wasm event in the tx, translating CW20/CW721/CW1155 events into synthetic ERC20/721/1155 logs using that bounded gas meter [3](#0-2) . The code comment itself acknowledges the risk: "txs with a very large number of WASM events may run out of gas due to additional gas consumption from EVM receipt generation and event translation" [4](#0-3) .

Each `translateCW20Event`/`translateCW721Event`/`translateCW1155Event` call wraps its own `recover()` [5](#0-4) , so an out-of-gas panic (`sdk.NewGasMeterWithMultiplier` panics via `ConsumeGas` when exhausted) inside one event's translation is silently swallowed — that event's logs are dropped, and because the shared gas meter is already exhausted, every subsequent wasm event in the same loop will likewise panic-and-be-swallowed with no logs generated, all without surfacing any error to the caller.

### Impact Explanation
Because the underlying CW20/CW721/CW1155 state transition (bank balance change, NFT ownership change) already succeeded before this hook runs, an exhausted `DeliverTxHookWasmGasLimit` causes the EVM-visible side (`eth_getLogs`/`eth_getTransactionReceipt` via the pointer contract) to silently omit Transfer/Approval events for transactions with many wasm events (e.g., a single wasm execute batching many CW20/CW721/CW1155 transfers through pointer contracts). Any EVM-side consumer — bridges, indexers, or smart contracts — that relies on these synthetic logs to detect deposits/transfers would fail to observe a state change that has already happened on-chain, which can result in funds being considered "lost" from the EVM-observer's perspective (e.g., a bridge or exchange never crediting a deposit that has already moved on the Cosmos side) while the tx itself reports success with no error.

### Likelihood Explanation
This requires an unprivileged CosmWasm/pointer user to submit a single transaction that emits enough wasm events (e.g., batch mint/transfer/burn calls against CW20/CW721/CW1155 pointer-mapped contracts) to exceed the fixed 300,000 gas budget during log translation — well within reach of a normal user interacting with a contract that batches many token operations in one message, especially as pointer/token adoption grows.

### Recommendation
Do not bound wasm→EVM synthetic event translation with a fixed, low, non-reverting gas budget that silently discards remaining logs on exhaustion. Either use an unbounded/sufficiently large gas meter for this receipt-generation bookkeeping (it's post-consensus-critical-path bookkeeping, not user-chargeable execution), or make the failure mode explicit (e.g., mark the receipt/log set as incomplete, or fail loudly and fall back to a documented degraded mode) instead of silently omitting events from the receipt.

### Proof of Concept
1. Deploy/instantiate a CW20 (or CW721/CW1155) pointer contract registered via `GetERC20CW20Pointer`.
2. Submit a single wasm `Execute` transaction that triggers a large number of CW20 transfer/mint events in one message (e.g., a batch-transfer wrapper contract or many sub-messages), such that the sum of gas consumed while looping through `translateCW20Event` for each event exceeds `DeliverTxHookWasmGasLimit` (300,000 by default).
3. Observe that the underlying CW20 balances update successfully (transaction succeeds).
4. Query the transaction's EVM receipt via `eth_getTransactionReceipt`/`eth_getLogs` and observe that some or all of the expected synthetic ERC20 `Transfer` logs are missing, because `translateCW20Event` began panicking on out-of-gas partway through the loop in `app/receipt.go` and the panics were silently recovered.

func (app *App) AddCosmosEventsToEVMReceiptIfApplicable(ctx sdk.Context, tx sdk.Tx, checksum [32]byte, response sdk.DeliverTxHookInput) {
	// hooks will only be called if DeliverTx is successful
	wasmEvents := GetEventsOfType(response, wasmtypes.WasmModuleEventType)
	if len(wasmEvents) == 0 {
		return
	}
	logs := []*ethtypes.Log{}
	// Note: txs with a very large number of WASM events may run out of gas due to
	// additional gas consumption from EVM receipt generation and event translation
	wasmToEvmEventGasLimit := app.EvmKeeper.GetDeliverTxHookWasmGasLimit(ctx.WithGasMeter(sdk.NewInfiniteGasMeter(1, 1)))
	wasmToEvmEventCtx := ctx.WithGasMeter(sdk.NewGasMeterWithMultiplier(ctx, wasmToEvmEventGasLimit))
