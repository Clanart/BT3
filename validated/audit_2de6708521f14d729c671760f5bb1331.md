## Finding: Escrow release in same-chain partial fills reads the full token balance instead of the per-leg amount, letting one solver drain escrow owed to another leg's solver

### Title
Cross-leg escrow drain via shared input token in `_fillSameChain` full-fill release - (evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntrinsicIntents._fillSameChain` computes the input tokens to release to a solver for a fully-filled output leg by reading `_orders[commitment][token]` directly — the *entire* current escrow balance for that token — rather than the amount specifically escrowed for that leg. `Order.inputs` and `Order.output.assets` are independent, user-controlled arrays with no validation that input token addresses are unique per output leg. When an order's `inputs` array contains the same token address used to back more than one output leg, whichever solver completes their leg first collects the whole pooled escrow balance for that token, leaving nothing for the solver(s) who fill the remaining leg(s) that share the same input token.

### Finding Description
`_fillSameChain` ( [1](#0-0) ) loops over `order.output.assets` and for each leg `i` computes the input tokens to release:

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
``` [2](#0-1) 

On a full-fill of leg `i` (`amountFilled == totalRequired`), the code releases whatever is *currently* stored in `_orders[commitment][token]` — the escrow mapping keyed only by `(commitment, token address)`, not by leg index [3](#0-2) . This is correct only under the implicit assumption that each input token address appears in `order.inputs[]` exactly once, dedicated to a single output leg.

Nothing enforces that assumption. `placeOrder` only checks `order.inputs.length == 0` and otherwise accepts the array as-is, accumulating escrow with `_orders[commitment][token] += reducedInputs[i].amount` [4](#0-3)  — duplicate token entries across legs are explicitly summed into one shared balance, with no length/uniqueness check tying `inputs[i]` to `output.assets[i]`.

Consequently, an order can be constructed (or a partially-adversarial order creator can construct one) where two output legs are backed by the same input token address, e.g. `inputs = [{tokenA, 100}, {tokenA, 50}]` against `outputs = [{tokenX, 200}, {tokenY, 300}]`, giving a combined `_orders[commitment][tokenA] = 150`. If Solver S1 fully fills leg 0 in one `fillOrder` call, `escrowedAmount` reads the full pooled balance (150), which is credited to S1 and later fully debited from `_orders[commitment][tokenA]` in `_withdraw` [5](#0-4) . When Solver S2 subsequently fully fills leg 1 (having already sent the required output tokens to the beneficiary), the same lookup now returns 0 escrow, so `escrowedInputs[1]` carries `amount = 0` — S2 receives no input tokens in exchange for output tokens already delivered.

### Impact Explanation
This causes a legitimate, unprivileged filler (solver) to lose the input-token compensation it is owed after honestly delivering the promised output assets to the order's beneficiary — a direct loss of funds / wrong-amount payout caused purely by escrow-mapping aliasing across output legs, with no reliance on a malicious relayer, prover, or admin. It matches the bounty's "stealing or loss of funds" / "logic attacks" / "false state acceptance of an incorrect amount" categories, and is a same-chain, purely on-chain, unprivileged-actor path (no cross-chain proof or relayer needed).

### Likelihood Explanation
Requires an order whose `inputs[]` array repeats the same token address across two or more output legs, and requires those legs to be filled by different solvers (or the same solver in different transactions) rather than atomically in one call. Nothing in `placeOrder` or `fillOrder` rejects such an order, and multi-asset orders with a shared funding token across legs are a plausible real-world configuration (e.g., using the same stablecoin to reward two different output legs). The race/ordering condition (who fills which leg first) is realistic under normal solver competition for partial fills. Note that if both legs are filled together in the *same* transaction, the second `_withdraw` entry for the same token instead reverts due to insufficient escrow (`UnknownOrder`), so the sharper "drain and short another solver" outcome specifically requires the legs to be filled in separate transactions.

### Recommendation
Track escrow release per output leg (or per `(commitment, leg index)`), not solely per `(commitment, token)`. Either enforce a 1:1, unique correspondence between `order.inputs[]` and `order.output.assets[]` (reject orders with duplicate input tokens spanning multiple legs), or maintain a leg-indexed escrow ledger so releasing leg `i`'s tokens only decrements/reads the portion of escrow attributable to `inputs[i]`, independent of the pooled balance for that token address shared with other legs.

### Proof of Concept
1. User places a same-chain order with `inputs = [{token: tokenA, amount: 100}, {token: tokenA, amount: 50}]`, `output.assets = [{token: tokenX, amount: 200}, {token: tokenY, amount: 300}]`. `placeOrder` escrows `_orders[commitment][tokenA] = 150` (accumulated across both entries).
2. Solver S1 calls `fillOrder` supplying only `tokenX` output fully (leg 0 `amountFilled == totalRequired`). `_fillSameChain` computes `escrowedAmount = _orders[commitment][tokenA] = 150` for leg 0, and this is fully paid out to S1 via `_withdraw`, zeroing `_orders[commitment][tokenA]`.
3. Solver S2 later calls `fillOrder` supplying `tokenY` output fully (leg 1). S2 transfers `tokenY` to the beneficiary as required, but `_fillSameChain` computes `escrowedAmount = _orders[commitment][tokenA] = 0`, so S2's `escrowedInputs[1].amount = 0` — S2 receives nothing in return for its delivered output tokens, while S1 received the entire 150 `tokenA` escrow intended to cover both legs.

This confirms a real fund-loss path stemming from the index/token-keyed mismatch, directly analogous to the GoldLink report's mis-paired value assignment causing an incorrect state read.

        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        bool isFullyFilled = true;

        TokenInfo[] memory escrowedInputs = new TokenInfo[](outputsLen);
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            uint256 alreadyFilled = _partialFills[commitment][outputToken];
            uint256 remaining = totalRequired - alreadyFilled;
            if (remaining == 0 || solverAmount == 0) {
                if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
                continue;
            }
            uint256 fillAmount;

            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;
            if (alreadyFilled == 0 && solverAmount > totalRequired) {
                fillAmount = totalRequired;
                uint256 dust = solverAmount - totalRequired;
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            } else {
                fillAmount = solverAmount > remaining ? remaining : solverAmount;
            }

            uint256 amountFilled = alreadyFilled + fillAmount;
            _partialFills[commitment][outputToken] = amountFilled;
            uint256 beneficiaryTotal = fillAmount + beneficiaryShare;

            if (token == address(0)) {
                if (msgValue < beneficiaryTotal + protocolShare) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }

            if (totalRequired > amountFilled) isFullyFilled = false;
            if (protocolShare > 0) emit DustCollected(token, protocolShare);

            uint256 escrowedAmount;
            if (amountFilled == totalRequired) {
                escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
            } else {
                escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
            }
            escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
            outputFills[i] = TokenInfo({token: outputToken, amount: fillAmount});
        }

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
