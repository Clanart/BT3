### Title
Silent remote-URL rewrite from an unverified GitHub API `clone_url` redirects future pushes/fetches to an attacker-controlled host - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The invariant broken in the Malt report is: a value that is supposed to require explicit, guarded user action (buying at a controlled price) can instead be silently mutated through a "trusted"/whitelisted path (the `UniswapHandler`) that the security check doesn't cover. The Desktop analog is `updateRemoteUrl`, which silently rewrites a repository's `origin` remote URL based on the `clone_url` field of a `GitHubRepository`/`IAPIRepository` object obtained from the GitHub API - a value the app implicitly trusts as authoritative - without confirming the new host belongs to the same, previously-authenticated endpoint.

### Finding Description
`updateRemoteUrl` compares the *current* remote to the *previously cached* `gitHubRepository.cloneURL` and to the *newly fetched* `apiRepo.clone_url`, using `urlMatchesRemote`, and if the protocol string matches and the old cached URL still matches the current remote, it calls `gitStore.setRemoteURL(...)` with the brand-new URL from the API response, with no further validation: [1](#0-0) 

The guard `urlMatchesRemote` (used both for `remoteUrlUnchanged` and `urlsMatch`) only checks `hostname`, `owner`, and `name` extracted via `parseRemote` - it never checks that the new hostname is the same *endpoint/account* the repository was originally associated with: [2](#0-1) 

`parseRemote`'s regexes accept `https?://(?:.+@)?(.+)/([^/]+)/([^/]+?)` as a valid GitHub-shaped URL for *any* hostname, not just `github.com` or the configured GHE hostname: [3](#0-2) 

The only remaining check in `updateRemoteUrl` is `protocolsMatch`, which merely compares the URL *scheme* string (`https:` vs `https:`), not the host: [4](#0-3) 

Because `apiRepo` (an `IAPIRepository`) is data returned by a GitHub API call, and because that call can be answered by a GitHub Enterprise server, a proxy in front of it, or a man-in-the-middle on a redirect chain, an attacker who can influence the API response body's `clone_url` field (e.g., a compromised/malicious GHE instance, a captured redirect, or a server that returns attacker-chosen JSON) can supply any `https://attacker-host/owner/name` value that still parses as an "owner/name" shaped URL. Desktop will then call `git remote set-url origin <attacker-url>` on the user's real, existing local repository automatically - with no user confirmation dialog, no diff shown, nothing.

### Impact Explanation
This is a "silent corruption of what the user commits or pushes" primitive listed as valid impact: after the rewrite, every subsequent `git push`/`git fetch`/`git pull` (unless the user manually notices and reverts the remote) is silently redirected to the attacker's host. Depending on the credential helper's endpoint-matching logic in `findGitHubTrampolineAccount` (which matches by *origin*, i.e., hostname) an attacker-controlled hostname would not automatically receive the user's stored OAuth token, but the user's source code itself (potentially private) would be pushed to the attacker's server, and any fetch would pull attacker-controlled objects into the user's working repository without any host-mismatch warning being shown to the user, exactly mirroring the Malt bug's pattern of "value moves through a nominally-trusted/whitelisted channel that bypasses the intended safety check."

### Likelihood Explanation
Exploitation requires the attacker to control or MITM a GitHub API response for a repository the user already has cloned (e.g., a malicious/compromised GitHub Enterprise server, or a party positioned to tamper with the API response before Desktop parses it) - this fits the allowed threat model ("attacker controls ... a GitHub API object ... or a git remote/proxy response"). It does not require local access, admin rights, leaked credentials, or unnatural user steps: the rewrite happens automatically as part of Desktop's normal repository-refresh/push flow (`withRefreshedGitHubRepository` → `updateRemoteUrl`).

### Recommendation
- In `updateRemoteUrl`, before calling `gitStore.setRemoteURL`, verify that the new `apiRepo.clone_url` hostname matches the hostname of the account/endpoint associated with the `gitHubRepository` (i.e., compare against `gitHubRepository.endpoint`/account host), not merely against the previously cached `cloneURL`.
- Require explicit user confirmation (a dialog showing old vs. new remote URL) before silently rewriting an existing remote, rather than performing the change transparently.
- Add an allowlist check in `urlMatchesRemote`/`parseRemote` consumers used for this purpose so that only the known GitHub.com / configured GHE hostnames are eligible targets for automatic remote rewrites.

### Proof of Concept
1. User has a repository whose GitHub Enterprise account is `https://ghe.example.com` and whose `origin` remote is `https://ghe.example.com/acme/app.git`, matching the cached `gitHubRepository.cloneURL`.
2. Attacker, positioned as (or having compromised) the GHE server or a proxy/redirect in the request path, returns an API repository object where `clone_url` = `https://attacker.example/acme/app.git`.
3. On next refresh/push (`_push` → `withRefreshedGitHubRepository` → `updateRemoteUrl`), `remoteUrlUnchanged` is `true` (matches cached cloneURL), `urlsMatch` is `false` (new host differs), and `protocolsMatch` is `true` (both `https:`), so the guard at [5](#0-4)  fires and Desktop silently runs `git remote set-url origin https://attacker.example/acme/app.git`.
4. Subsequent pushes/fetches transparently go to `attacker.example` with no warning shown to the user, corrupting the destination of what the user believes they are pushing/pulling.

**Note on confidence**: I could not fully trace, within the available index, every call path of `withRefreshedGitHubRepository` and the exact conditions under which `apiRepo` data can be attacker-influenced (e.g., whether Desktop pins/validates GHE TLS certs or API response provenance beyond this function), so the feasibility of an attacker actually injecting a malicious API response depends on assumptions about network positioning (compromised/malicious GHE server or intercepted API traffic) that I was not able to verify further with the tools available.

```typescript
export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
```
