### Title
Unrestricted `compound()` sweeps entire contract reward-token balance to caller, not just value from caller's own claim - ([File: rewards/ManualCompound.sol])

### Summary
`compound()` in `rewards/ManualCompound.sol` has no access control and no requirement that the `multiclaimOnBehalf` call actually produced value for `msg.sender`. The second sweep loop measures `receivedBalance` as `IERC20(_tokenAddress).balanceOf(address(this))` — the contract's total absolute balance rather than a delta attributable to the caller's claim — and then unconditionally converts/locks/deposits that entire balance to `msg.sender`. Any unprivileged caller can invoke `compound()` with staking tokens/pools they have no stake in and still redirect whatever reward-token balance is sitting in the contract to themselves.

### Finding Description
`compound(address[] _lps, address[][] _rewards, uint256 _convertRatio, uint256 _minRec, bool _lockMgp)` is `external` with no modifier restricting the caller: [1](#0-0) 

It first calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)`, which claims on behalf of `msg.sender` for the pools they specify. If `msg.sender` has no stake in those pools (or `_lps`/`_rewards` are empty/irrelevant), this leg yields zero value — nothing enforces otherwise.

The second loop then iterates over the contract's globally configured `rewards` array (independent of `_lps`/`_rewards` supplied by the caller) and computes: [2](#0-1) 

`receivedBalance` is `IERC20(_tokenAddress).balanceOf(address(this))` — the contract's *total* balance of that reward token, not a per-call delta tied to what the caller's claim actually produced. This value is then passed into `IConverter(_convertor).convertFor(receivedBalance, _convertRatio, _minRec, msg.sender, 2)`.

In `SmartWomConvert._convertFor`, the entire `_amount` (here `receivedBalance`) is processed and the resulting `obtainedmWomAmount` is sent/locked entirely for `_for` (which `ManualCompound` sets to `msg.sender`): [3](#0-2) 

So if `ManualCompound` is holding any reward-token balance at the time of the call — from dust/rounding leftovers of previous compounds, tokens sent directly to the contract, or balances belonging to other pending/partial distributions — an attacker who supplies inputs producing zero value from their own claim will still have that entire balance swept, converted (with attacker-chosen `_convertRatio`, and `_minRec = 0` removing any slippage protection), and credited to themselves. Nothing in `compound()` gates the sweep on value the caller generated in this call.

### Impact Explanation
This is a direct theft of funds vector: any accumulated reward-token balance held by `ManualCompound` (which does not belong exclusively to the caller) can be redirected entirely to an unprivileged attacker's address via `convertFor(..., msg.sender, 2)`, matching the "Critical - Direct theft of user funds" class. The attacker controls `_convertRatio` and sets `_minRec = 0`, maximizing their extracted value and bypassing minimum-received protection.

### Likelihood Explanation
Exploitability only requires that `ManualCompound` hold a non-zero balance of a configured reward token at call time (e.g., WOM) — a realistic condition given dust from prior partial conversions, direct token transfers, or timing races between multiple claim/compound calls. `compound()` has no access control (no `onlyOwner`/`onlyCompounder`/similar), so any EOA can call it at zero cost beyond gas, and the attack is repeatable every time the balance is replenished.

### Recommendation
Track reward-token amounts as deltas produced by the specific `multiclaimOnBehalf` call (e.g., snapshot balance before/after the claim, or have `multiclaimOnBehalf` return actual claimed amounts) rather than using `balanceOf(address(this))` for the sweep. Additionally, consider restricting `compound()` to require `_lps`/`_rewards` correspond to stakes actually held by `msg.sender`, and/or add a check that the pre-claim/post-claim delta is what gets converted, not the total resident balance.

### Proof of Concept
Hardhat plan:
1. Deploy `MasterMagpie`, `ManualCompound` (as configured compounder for WOM reward with `SmartWomConvert` as convertor, mode `2`/lock), and `SmartWomConvert`.
2. Simulate a pre-existing balance in `ManualCompound` for the WOM token (e.g., have a legitimate user's earlier `compound()` call leave dust, or directly `transfer` WOM tokens to `ManualCompound` to model leftover/undistributed balance).
3. From an attacker EOA with zero stake in any `_lps` pool, call `compound(_lps=[irrelevantOrEmptyPool], _rewards=[[]], _convertRatio=X, _minRec=0, _lockMgp=false)`.
4. Assert: `multiclaimOnBehalf` yields zero claimable value for attacker (verify via events/balances), yet `mWomSV.lockFor` (or transfer) still credits the attacker with `obtainedmWomAmount > 0` derived from the pre-existing WOM balance.
5. Assert the invariant violation: attacker's realized `obtainedmWomAmount` exceeds the value generated from their own `multiclaimOnBehalf` call in the same transaction (should be 0), proving unconditional access to the contract's resident balance.
