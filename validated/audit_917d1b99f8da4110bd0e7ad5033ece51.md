## Title
Payout transaction's operator-credit OP_RETURN output is not covered by the user's signature, allowing malleation of "who fronted the withdrawal" - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` builds the payout transaction that fronts a Citrea withdrawal, but the only cryptographic commitment binding the transaction is the withdrawing user's Schnorr signature over input 0, which is explicitly documented and expected to use the `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` type. That sighash flavor commits only to input 0 and the output at the *same index* (the user's payout output), leaving the anchor output and — critically — the OP_RETURN output that records the operator's x-only pubkey completely unauthenticated. Any party who obtains this signature can rebuild a payout transaction with a different set of inputs and a different OP_RETURN payload, redirecting the "who paid this withdrawal" credit to an arbitrary operator identity, while still honoring the user's fixed payout output.

### Finding Description
`create_payout_txhandler` in [1](#0-0)  constructs the payout tx with:
1. input 0: the withdrawal UTXO, spent via `SpendPath::KeySpend`
2. output 0: the user payout
3. output 1: anchor (CPFP)
4. output 2: OP_RETURN containing `operator_xonly_pk`

The witness for input 0 is set from `user_sig` only — `txhandler.set_p2tr_key_spend_witness(&user_sig, 0)` — there is no operator signature or any other commitment binding output 2 (the OP_RETURN with `operator_xonly_pk`) to the transaction.

The caller, `Operator::withdraw` in [2](#0-1)  explicitly documents the expected signature type: *"Ensure the signature uses SinglePlusAnyoneCanPay sighash type"*. Under BIP-341/342 Taproot key-path sighash rules, `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`:
- commits only to the single input being signed (not to any other inputs — so anyone can add/replace inputs, i.e. fund the transaction with different money),
- commits only to the output at the same index as that input (output 0) — it does **not** commit to output 1 (anchor) or output 2 (the OP_RETURN operator-credit output).

This means the OP_RETURN payload that identifies which operator "fronted" the withdrawal is entirely malleable by any party holding the withdrawal signature, without invalidating it.

Downstream, this OP_RETURN value is the sole source of truth for operator attribution:
- `Verifier::update_finalized_payouts` parses the OP_RETURN of the confirmed payout tx and records `operator_xonly_pk` as the payer of that withdrawal: [3](#0-2) 
- `Verifier::is_kickoff_malicious` later checks that the operator initiating a kickoff (to claim reimbursement) matches this recorded `operator_xonly_pk`, and treats a mismatch or missing value as malicious: [4](#0-3) 

Because output 2 is unauthenticated, an attacker who intercepts the user's withdrawal signature (which, per the docstring in `withdraw`, is handed to operators off-chain and is then broadcast as a Bitcoin transaction, visible in the mempool before confirmation) can rebroadcast a competing transaction that:
- keeps output 0 identical (so the user still gets paid, satisfying the signature commitment),
- supplies its own additional funding input (permitted by `ANYONECANPAY`),
- sets the OP_RETURN operator pubkey to any value of the attacker's choosing.

If this attacker's version confirms instead of the honest operator's, the protocol's payout-attribution bookkeeping (`update_finalized_payouts`) will record the attacker's chosen `operator_xonly_pk` as the payer, and only that identity will be able to pass `is_kickoff_malicious`'s equality check to claim the kickoff/reimbursement flow for that withdrawal.

### Impact Explanation
This breaks the custody binding: *the operator credited for fronting a withdrawal versus the party that actually funded the withdrawal payment.* Consequences:
- The honest operator who genuinely committed capital to front the payout can be permanently unable to be reimbursed, because the OP_RETURN credit was rewritten to a different xonly pubkey before confirmation, and `is_kickoff_malicious` will reject their kickoff as malicious (operator pubkey mismatch).
- Conversely, whichever party's transaction confirms with the winning OP_RETURN value becomes the exclusive party entitled to initiate the kickoff/reimbursement path for that withdrawal, regardless of whether they were the one who intended to service it.

This matches the Critical impact class: *"an honest operator permanently unable to be reimbursed"* / *"an operator reimbursed for a payout it never funded."*

### Likelihood Explanation
The condition requires only that an unprivileged party observe the withdrawal signature/transaction in the mempool before it confirms and win a fee/replacement race with a competing transaction that reuses the same fixed output 0 but supplies its own funding and OP_RETURN payload — no signing key, operator role, or privileged access is required, satisfying the "unprivileged attacker" constraint. The likelihood is bounded by the attacker's ability to get their transaction mined ahead of/instead of the honest operator's, which is an ordinary mempool/fee race, not a cryptographic or protocol-privileged requirement.

### Recommendation
Require the sighash to cover the OP_RETURN output (e.g., use `SIGHASH_ALL` for the parts of the transaction that determine operator attribution, or otherwise cryptographically bind `operator_xonly_pk` into data that the user's signature commits to), or have the operator co-sign/commit to the OP_RETURN payload so it cannot be altered by a third party while the payout is still unconfirmed.

### Proof of Concept
1. Operator A prepares and broadcasts a payout tx per `create_payout_txhandler`: input 0 = withdrawal UTXO (user signature, `SIGHASH_SINGLE|ANYONECANPAY`), output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN(A's xonly pubkey), funded with A's own additional inputs.
2. Attacker observes this transaction (or the raw signature) in the mempool before confirmation.
3. Attacker builds a new transaction reusing input 0 (same withdrawal UTXO + same valid user signature) and output 0 unchanged, but supplies its own funding inputs (allowed since input 0's signature doesn't cover other inputs) and sets output 2's OP_RETURN to the attacker-chosen xonly pubkey (e.g., an operator identity the attacker controls or an arbitrary honest operator's pubkey to sabotage them).
4. Attacker gets their version confirmed first (e.g., via higher fee/RBF).
5. `Verifier::update_finalized_payouts` records the attacker-chosen `operator_xonly_pk` as the payer of the withdrawal (`core/src/verifier.rs:2319-2335`).
6. When operator A later attempts the kickoff to get reimbursed, `is_kickoff_malicious` finds `operator_xonly_pk != kickoff_data.operator_xonly_pk` and flags A's kickoff as malicious (`core/src/verifier.rs:1887-1890`), permanently denying A reimbursement for the payment A actually made.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
