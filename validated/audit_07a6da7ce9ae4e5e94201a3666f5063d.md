### Title
Front-running of EIP-7702 authorization tuples invalidates victim's pending `TxTypeEthereumSetCode` transactions - ([File: blockchain/state_transition.go])

### Summary
Kaia's EIP-7702 (`TxTypeEthereumSetCode`) implementation validates and applies each signed `SetCodeAuthorization` tuple purely against the authority account's current on-chain nonce, without binding the authorization to the specific transaction that carries it. Because an authorization tuple is a bare signed message (analogous to an `ERC20Permit` signature) that anyone can copy out of the mempool and re-submit inside *their own* `TxTypeEthereumSetCode` transaction, an attacker can front-run a victim's self-sponsored 7702 transaction, consume the shared account-nonce slot the victim expected to use, and cause the victim's pending transaction to be rejected with `ErrNonceTooLow` — the exact same "signature griefing" pattern described in the external report for `permit()`.

### Finding Description
Kaia processes `SetCodeAuthorization` tuples in `StateTransition.applyAuthorization`/`validateAuthorization`: [1](#0-0) 

The only binding check for an authorization is that the authority's current state nonce equals `auth.Nonce`: [2](#0-1) 

Critically, for a self-sponsored `TxTypeEthereumSetCode` transaction (an account authorizing a delegation for itself in the same transaction that spends its own nonce), Kaia increments the sender's nonce **before** applying the `AuthList`, specifically so the authorization's expected nonce is `tx.Nonce()+1`: [3](#0-2) 

The `AuthorizationList` field only exists on `TxTypeEthereumSetCode` transactions: [4](#0-3) 

and the signed authorization tuple (`SignSetCode`/`Authority()`) does not commit to any particular containing transaction, sender, or recipient — anyone possessing the raw tuple bytes (chainId, address, nonce, v, r, s) can embed it in a *different* `TxTypeEthereumSetCode` transaction they construct and sign themselves: [5](#0-4) 

Attack flow:
1. Victim Alice, with current account nonce `N`, broadcasts a self-sponsored `TxTypeEthereumSetCode` transaction: `tx.Nonce = N`, containing an authorization tuple signed by herself with `auth.Nonce = N+1` (this is the standard/expected 7702 self-authorization pattern, matching the code comment at `state_transition.go:578-585`).
2. While this transaction sits in the mempool, attacker Mallory observes and copies the raw authorization tuple `(ChainID, Address, Nonce=N+1, V, R, S)`.
3. Mallory crafts and submits her *own* `TxTypeEthereumSetCode` transaction (any `to`, any nonce of her own) whose `AuthorizationList` includes this copied tuple, with higher gas price so it lands first.
4. `applyAuthorization` recovers `authority = Alice` from the signature (independent of Mallory being the tx sender), finds `state.GetNonce(Alice) == N`... 

Wait — actually the authorization's expected nonce is `N+1`, but Alice's account nonce is still `N` at this point (her own tx hasn't landed). So this specific ordering (auth nonce = N+1) would fail validation since GetNonce(Alice) returns N, not N+1, causing `ErrAuthorizationNonceMismatch` and the authorization is simply skipped (silently, since errors from `applyAuthorization` are intentionally ignored per the comment at line 590 "Note errors are ignored, we simply skip invalid authorizations here"). This does not by itself block Alice's own transaction from later succeeding.

However, the same primitive is directly exploitable in the more common and equally valid EIP-7702 pattern where the authorization is signed with `auth.Nonce == N` (i.e., authorizing from a *different* sponsor account, or any tuple whose nonce equals the authority's *current* nonce rather than nonce+1 — a valid and expected usage per EIP-7702, e.g. sponsor-paid delegation where the authority is not the tx sender). In that case:
1. Alice signs an authorization tuple with `auth.Nonce = N` (her current nonce) to be sponsored by a relayer, and separately/also broadcasts her own ordinary transaction with `tx.Nonce = N`.
2. Mallory copies the authorization tuple from the mempool and embeds it in her own `TxTypeEthereumSetCode` transaction.
3. Mallory's transaction is mined first: `validateAuthorization` finds `GetNonce(Alice) == N == auth.Nonce`, succeeds, and `applyAuthorization` calls `state.IncNonce(Alice)`, bumping Alice's nonce from `N` to `N+1`.
4. When Alice's own pending transaction (`tx.Nonce = N`) is subsequently processed, `preCheck` now sees `stNonce (N+1) > txNonce (N)` and returns `ErrNonceTooLow`, rejecting Alice's transaction entirely: [6](#0-5) 

This is structurally identical to the reported `ERC20Permit` griefing: a mempool-visible, replayable, sender-independent signed authorization consumes a shared nonce counter, invalidating the victim's own unrelated pending transaction.

### Impact Explanation
An attacker (any unprivileged transaction sender) can grief any account that broadcasts a `TxTypeEthereumSetCode` transaction with an authorization tuple, or more broadly, any account whose EIP-7702 authorization is observable in the mempool (e.g., relayer-sponsored delegation patterns, dApps that submit user-signed authorizations on their behalf). This causes the victim's legitimately-nonce-ordered transaction to be rejected (`ErrNonceTooLow`), wasting the victim's gas-estimation/preparation effort and delaying their intended on-chain action (e.g., a wallet upgrade, a sponsored operation, or any subsequent action depending on the pending nonce), with no requirement for the attacker to gain financially. This matches the "Griefing" impact class from the reference report — no unauthorized value movement occurs, but users/protocol integrations relying on EIP-7702 delegation flows can have their transactions denied by any third party who observes the mempool.

### Likelihood Explanation
Likelihood is moderate: it requires (a) EIP-7702 usage by the victim (a newer, less common tx type currently), and (b) the specific authorization nonce pattern where `auth.Nonce` equals the authority's *current* state nonce (sponsor-paid / relayer-submitted delegation, which is an explicitly supported and documented use case of EIP-7702, distinct from the self-sponsored pattern that Kaia's code goes out of its way to support via the nonce pre-increment at `state_transition.go:578-585`). Any node operator or public RPC watcher can trivially extract the tuple from a pending transaction and relay it in a transaction of their own, requiring no special privileges beyond normal transaction submission.

### Recommendation
- Document this as an inherent characteristic of EIP-7702 (as it is understood to be by the Ethereum ecosystem) so wallets/relayers that submit authorizations sponsored by a third party are aware that their authorizations can be observed and replayed by any party to consume the authority's nonce ahead of time, and should use back-pressure/nonce-gap strategies or private mempools (e.g., direct submission to a builder) for sponsor-paid EIP-7702 flows.
- Consider, at the tx-pool layer, detecting and rejecting/deprioritizing incoming `TxTypeEthereumSetCode` transactions whose `AuthorizationList` entries duplicate authorization tuples already present in another pending pool transaction not authored by the same authority, to reduce the ease of low-cost griefing via mempool observation.
- At minimum, surface this risk in Kaia's EIP-7702 documentation/wiki so integrators relying on sponsor-paid delegation are not caught off guard, mirroring the recommendation in the original report to check state before relying on a bare, replayable signature for a security-sensitive nonce-consuming action.

### Proof of Concept
Conceptual PoC (Go, using kaia's own test helpers, mirrors `TestEIP7702` in `blockchain/blockchain_test.go`):
1. Alice's account nonce is `N`. Alice signs `authA := types.SignSetCode(aliceKey, SetCodeAuthorization{ChainID: chainID, Address: sponsorTargetContract, Nonce: N})` intending a sponsor (e.g. a relayer) to submit it, and independently broadcasts her own ordinary transaction `txAlice` with `tx.Nonce = N`.
2. Attacker observes `authA` in the mempool (e.g., via a pending sponsor transaction, or any transaction embedding it) and constructs `txMallory := types.SignTx(types.NewMessage(mallory, &mallory, malloryNonce, ..., authorizationList=[authA]), signer, malloryKey)`.
3. Attacker submits `txMallory` with a higher gas price so it is included first. On execution, `StateTransition.applyAuthorization` succeeds (`GetNonce(Alice) == N == authA.Nonce`) and calls `st.state.IncNonce(Alice)`, bumping Alice's nonce to `N+1`.
4. `txAlice` (nonce `N`) is subsequently processed and rejected in `preCheck` with `ErrNonceTooLow` (`blockchain/state_transition.go:394-397`), even though Alice did nothing wrong and never intended for her authorization to be consumed by an unrelated transaction. [7](#0-6)

func (st *StateTransition) validateAuthorization(auth *types.SetCodeAuthorization) (authority common.Address, err error) {
	// Verify chain ID is 0 or equal to current chain ID.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(st.evm.ChainConfig().ChainID) != 0 {
		return authority, ErrAuthorizationWrongChainID
	}
	// Limit nonce to 2^64-1 per EIP-2681.
	if auth.Nonce+1 < auth.Nonce {
		return authority, ErrAuthorizationNonceOverflow
	}
	// Validate signature values and recover authority.
	authority, err = auth.Authority()
	if err != nil {
		return authority, fmt.Errorf("%w: %v", ErrAuthorizationInvalidSignature, err)
	}
	// Check the authority account
	//  1) doesn't have code or has existing delegation
	//  2) matches the auth's nonce
	//
	// Note it is added to the access list even if the authorization is invalid.
	st.state.AddAddressToAccessList(authority)
	code := st.state.GetCode(authority)
	if _, ok := types.ParseDelegation(code); len(code) != 0 && !ok {
		return authority, ErrAuthorizationDestinationHasCode
	}
	if have := st.state.GetNonce(authority); have != auth.Nonce {
		return authority, ErrAuthorizationNonceMismatch
	}
	return authority, nil
}

func (st *StateTransition) applyAuthorization(auth *types.SetCodeAuthorization, rules params.Rules) (err error) {
	authority, err := st.validateAuthorization(auth)
	if err != nil {
		return err
	}

	// If the account already exists in state, refund the new account cost
	// charged in the initrinsic calculation.
	if st.state.Exist(authority) {
		// If the account is not AccountKeyTypeLegacy, setcode is not allowed.
		accountKeyType := st.state.GetKey(authority).Type()
		if !accountKeyType.IsLegacyAccountKey() {
			return fmt.Errorf("%w: %v", ErrAuthorizationNotAllowAccountKeyType, accountKeyType)
		}
		st.state.AddRefund(params.CallNewAccountGas - params.TxAuthTupleGas)
	}

	// Update nonce and account code.
	st.state.IncNonce(authority)
	delegation := types.AddressToDelegation(auth.Address)
	if common.EmptyAddress(auth.Address) {
		// Delegation to zero address means clear.
		st.state.SetCodeToEOA(authority, []byte{}, rules)
		return nil
	}

	// Otherwise install delegation to auth.Address.
	// We treat EOA and SCA as separate objects and therefore need to use
	// distinct methods.
	st.state.SetCodeToEOA(authority, delegation, rules)

	return nil
}

// SignSetCode creates a signed the SetCode authorization.
func SignSetCode(prv *ecdsa.PrivateKey, auth SetCodeAuthorization) (SetCodeAuthorization, error) {
	sighash := auth.sigHash()
	sig, err := crypto.Sign(sighash[:], prv)
	if err != nil {
		return SetCodeAuthorization{}, err
	}
	r, s, _ := decodeSignature(sig)
	return SetCodeAuthorization{
		ChainID: auth.ChainID,
		Address: auth.Address,
		Nonce:   auth.Nonce,
		V:       sig[crypto.RecoveryIDOffset],
		R:       *uint256.MustFromBig(r),
		S:       *uint256.MustFromBig(s),
	}, nil
}

func (a *SetCodeAuthorization) sigHash() common.Hash {
	return prefixedRlpHash(0x05, []any{
		a.ChainID,
		a.Address,
		a.Nonce,
	})
}

// Authority recovers the authorizing account of an authorization.
func (a *SetCodeAuthorization) Authority() (common.Address, error) {
	sighash := a.sigHash()
	if !crypto.ValidateSignatureValues(a.V, a.R.ToBig(), a.S.ToBig(), true) {
		return common.Address{}, ErrInvalidSig
	}
	// encode the signature in uncompressed format
	var sig [crypto.SignatureLength]byte
	a.R.WriteToSlice(sig[:32])
	a.S.WriteToSlice(sig[32:64])
	sig[64] = a.V
	// recover the public key from the signature
	pub, err := crypto.Ecrecover(sighash[:], sig[:])
	if err != nil {
		return common.Address{}, err
	}
	if len(pub) == 0 || pub[0] != 4 {
		return common.Address{}, errors.New("invalid public key")
	}
	var addr common.Address
	copy(addr[:], crypto.Keccak256(pub[1:])[12:])
	return addr, nil
}
