### Title
Denial of Service via unbounded CLVM/signature validation time on the shared thread pool used for mempool spend-bundle admission - ([File: chia/full_node/mempool_manager.py])

### Summary
`MempoolManager.pre_validate_spendbundle()` submits every incoming spend bundle's CLVM execution + BLS signature verification to a shared, fixed-size thread pool and only measures elapsed time *after* the job returns. There is no pre-emptive cap on how long a single validation job may occupy a worker thread while it is running, and the same pool instance is also used for block validation. An unauthenticated/unprivileged peer or wallet can repeatedly submit spend bundles that are cheap in declared CLVM cost but disproportionately slow to execute (e.g., heavy on AGG_SIG/BLS pairing operations or worst-case CLVM tree shapes relative to their cost), tying up the limited worker threads and degrading transaction-processing throughput for the whole node — directly analogous to the reported Mattermost issue of small-but-expensive uploads saturating a shared extraction worker pool.

### Finding Description
`FullNode._start()` constructs a single `PriorityThreadPoolExecutor` (`self._pool`) sized only to `cpu_count - reserved_cores` threads (minimum 1), and passes the *same* pool object to both `Blockchain.create(..., pool=self.pool, ...)` and `MempoolManager.managed(..., pool=self.pool, ...)`: [1](#0-0) 

Every spend bundle submitted through `add_transaction` (reachable by any connected peer or wallet, with no special permission) is routed to `MempoolManager.pre_validate_spendbundle()`, which schedules the actual CLVM + BLS work on this shared pool via `run_in_loop`, using only a soft `nice` priority derived from the advertised fee-per-cost: [2](#0-1) 

The `nice` value only affects queue *ordering* before a job is picked up by a worker thread — once a worker starts executing `validate_clvm_and_signature`, it cannot be preempted, as shown in the executor's worker loop, which simply calls `item.fn(*item.args, **item.kwargs)` without any timeout wrapper: [3](#0-2) 

Timeout enforcement in `pre_validate_spendbundle` happens only *after* the job has already completed and consumed a worker thread for its full duration: [4](#0-3) 

Because `max_workers = max(cpu_count - reserved_cores, 1)` and only `dedicated = 1 if num_workers > 1 else 0` threads are reserved, on modest hardware (or when `reserved_cores` is configured close to the CPU count) most or all of the pool's general-queue threads can be occupied simultaneously by attacker-submitted spend bundles, each running for up to the `block_creation_timeout` (default 2.0s, configurable) before being flagged as too slow — after the thread was already tied up: [5](#0-4) 

I was not able to confirm within the available tool budget whether block-generator validation calls into this same pool always pass `dedicated=True` to reserve a protected thread; if it does not (or on single/low-core nodes where `dedicated=0`), the same saturation would also delay block validation, not just mempool admission. This should be verified directly in `chia/consensus/multiprocess_validation.py` and `Blockchain`'s call sites into `self.pool`.

### Impact Explanation
An unprivileged peer or wallet client that can submit spend bundles to a full node can repeatedly send spend bundles engineered to have a poor cost-to-execution-time ratio (e.g., puzzles that are cheap by declared CLVM cost metering but slow in the Rust/Python-side signature or condition-processing pipeline). Since:
- the mempool validation pool is shared and small in size,
- worker occupation cannot be pre-empted mid-execution,
- fee-based `nice` priority only affects *queued*, not *running* jobs,

an attacker can degrade or effectively halt transaction admission for all other peers/wallets on that node for as long as the flood continues, matching the "spend-triggered transaction-processing halt" impact criterion. Because it does not create invalid state, corrupt coin sets, or forge value, this is a resource-exhaustion/availability issue rather than a consensus-safety issue — Medium severity, consistent with the analogous Mattermost CVE-2026-10600 rating (CVSS 4.3).

### Likelihood Explanation
Reachable trivially by any connected peer or wallet client via the standard `send_transaction`/`new_transaction` paths with no special privilege — only the ability to submit spend bundles is required, which any wallet user has by design. Constructing spend bundles that are cheap by declared cost but slow to validate requires some puzzle-engineering effort (e.g., maximizing expensive operations per unit of metered cost), but no cryptographic secrets or privileged access are needed.

### Recommendation
- Enforce a real execution-time budget for `validate_clvm_and_signature` jobs (e.g., run in a process pool with a hard timeout/kill, or add cooperative cancellation checks inside the Rust CLVM/BLS runner) rather than only measuring duration after the fact.
- Reserve a larger or separate dedicated worker slice for mempool validation independent of block validation, and consider rate-limiting per-peer spend-bundle submission based on recent validation-time consumption, not just declared fee/cost.
- Audit CLVM cost metering to ensure it more tightly bounds real wall-clock validation cost (closing the gap between "cheap declared cost" and "expensive actual execution").

### Proof of Concept
Conceptual (not exploited against live code, based on static analysis of the shared pool architecture):
1. Attacker connects as an ordinary peer/wallet to a full node and repeatedly calls `send_transaction`/broadcasts `new_transaction` with spend bundles crafted to have low advertised fee/cost but maximally expensive validation relative to that cost (e.g., dense AGG_SIG_UNSAFE conditions or pathological CLVM shapes near the atom/pair density limits enforced only after the run completes, see `chia/full_node/mempool_manager.py:571-575`).
2. Each such bundle is submitted to the shared `PriorityThreadPoolExecutor` via `pre_validate_spendbundle` (`chia/full_node/mempool_manager.py:552-559`), occupying a general worker thread for up to `validation_timeout` seconds before it's detected and rejected.
3. With enough concurrent submissions (bounded by `_add_transaction_semaphore = asyncio.Semaphore(200)` in `full_node.py:268`, still far larger than the pool's worker count), all general-queue worker threads are kept busy, starving legitimate low/medium-fee transactions from being validated and admitted in a timely manner, and — depending on `dedicated` thread allocation — potentially delaying block validation on the same pool.

    def _worker(self, q: queue.PriorityQueue[_WorkItem], is_dedicated: bool) -> None:
        while True:
            item = q.get()
            if item.fn is None:
                return
            if not item._claim.acquire(blocking=False):
                continue
            assert item.future is not None
            if not item.future.set_running_or_notify_cancel():
                continue
            if self._instrument:
                with self._stats_lock:
                    if is_dedicated:
                        self._retired_dedicated += 1
                    else:
                        self._retired_general += 1
            try:
                result = item.fn(*item.args, **item.kwargs)
                item.future.set_result(result)
            except BaseException as e:
                item.future.set_exception(e)
