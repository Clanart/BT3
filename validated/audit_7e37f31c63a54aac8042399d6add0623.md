### Title
Reward split between CN staking and Consensus Liquidity (CL) pool is based on manipulable WKAIA token balance, not verified staked principal - (File: kaiax/staking/staking_info.go, kaiax/reward/impl/getter.go)

### Summary
The Prague/KIP-226 consensus-liquidity reward split treats a CL pool's `WKAIA.balanceOf(clPoolAddr)` as if it represented bona fide staked principal, and splits validator staking rewards between the CN staking contract and its CL pool proportionally to this figure. Because `WKAIA.balanceOf` is a plain ERC-20-style balance that can be inflated by any holder simply calling `transfer()` to the CL pool address (with no corresponding increase in the pool's legitimate delegated/staked shares), an unprivileged actor can skew the CN/CL reward split and redirect protocol reward budget away from legitimately staked validators/delegators — the same "principal used for reward splitting can be inflated by unrelated inbound value" bug class described in the StakeWise report (unbounded ETH deposit inflating `_totalAssets` and thus the legacy/v3 reward split).

### Finding Description
`StakingInfo.CLStakingInfo.CLStakingAmount` is populated straight from the CL registry's on-chain "staking amount" value, which the staking module reads via the CL registry contract and, per the module's own test fixtures/mocks, is defined as the balance held at the CL pool address (`WrappedKaia.balanceOf(clPoolAddr)` — represented in the test mock as `account.balance`) [1](#0-0) . This amount flows unmodified into `CLStakingInfo.CLStakingAmount` via `parseCallResult`/`parsePermissionlessCallResult` [2](#0-1) .

That amount is then used as ground truth "staked principal" in two places:

1. `consolidatedNode.Split`, which divides any reward budget between the CN reward address and the CL pool address strictly proportionally to `StakingAmount` (CNStaking) vs `CLStakingInfo.CLStakingAmount` (CL pool balance): [3](#0-2) 

2. `assignStakingRewards`/`assignStakingRewardsFlex`, which sum `cn.StakingAmount + cn.CLStakingInfo.CLStakingAmount` to compute each validator's "total staking amount" used to proportionally allocate the minting-based staking reward budget among all validators: [4](#0-3) [5](#0-4) 

Unlike the CNStaking amount (which is only increased through the staking contract's controlled staking flow and is subject to unstaking/verification), the CL pool's WKAIA balance is a raw token balance that can be increased by any external WKAIA holder invoking `transfer(dst, wad)` with `dst = clPoolAddr`, with no requirement that the sender receive shares or that the transfer represent a genuine delegation: [6](#0-5) 

This is the exact bug class from the StakeWise report: an unbonded/unrelated deposit ("unbounded ETH" in the report; here, an arbitrary WKAIA transfer) inflates the balance figure used as "principal" in a proportional reward split, without representing real economic stake that should be entitled to rewards.

### Impact Explanation
Any account holding WKAIA (obtainable by wrapping KAIA, a permissionless action) can call `WKAIA.transfer()` to send tokens directly to a target validator's CL pool address. This artificially inflates:
- The proportion of a given validator's minting-reward budget that is attributed to its CL pool over the CN staking side (via `consolidatedNode.Split`), and
- That validator's effective total staking weight relative to other validators when the KIP-82/Flex staking-reward budget is distributed across all validators (via `assignStakingRewards`/`assignStakingRewardsFlex`).

The net effect is reward redirection: an attacker can shift a disproportionate share of the per-block staking reward budget toward a chosen validator's CL pool address at the expense of that validator's own CN reward address and/or at the expense of other validators' legitimate stakers, without staking any KAIA through the legitimate delegation flow and without the attacker's funds actually contributing consensus-liquidity backing. This is unauthorized value redirection consistent with a High-severity finding, matching the reward-redirection outcome category.

### Likelihood Explanation
The action requires only two permissionless transactions — wrap KAIA into WKAIA, then `WKAIA.transfer()` to the target CL pool address — reachable by any transaction sender with no special privileges, and it directly affects the deterministic, consensus-critical reward computation performed at every block for validators with an associated CL pool (post-Prague/KIP-226 chains). The precondition (existence of a CL pool for the targeted validator) is expected to become common as consensus liquidity adoption grows.

### Recommendation
Do not use the CL pool's raw token/native balance as the "staked" amount for reward-splitting purposes. Instead, derive `CLStakingAmount` from the CL pool's authoritative delegated/staked-principal accounting (e.g., a value tracked by the delegation contract itself that only increases through its controlled deposit/delegate entry points and excludes balances received via unrelated token transfers), and reconcile/validate that figure against the registry before using it in `consolidatedNode.Split`, `assignStakingRewards`, and `assignStakingRewardsFlex`.

### Proof of Concept
1. Attacker identifies a validator `V` with an associated CL pool `P` (address `clPoolAddr`) registered in the CL registry, currently holding legitimate staked WKAIA balance `B`.
2. Attacker calls `WKAIA.deposit()` (payable) to wrap `N` KAIA into WKAIA, then calls `WKAIA.transfer(P, N)` [7](#0-6)  — a plain, permissionless call requiring no interaction with the delegation/staking flow.
3. At the next block whose staking-info snapshot is read, the CL registry reports `CLStakingAmount = balanceOf(P) = B + N` for validator `V`'s CL pool [2](#0-1) .
4. `assignStakingRewards`/`assignStakingRewardsFlex` compute `V`'s total staking weight as `StakingAmount + (B+N)` instead of `StakingAmount + B`, increasing `V`'s share of the staking reward budget relative to other validators [8](#0-7) .
5. `consolidatedNode.Split` further attributes a larger fraction of `V`'s own reward allocation to the CL pool `P` rather than `V`'s CN reward address, in proportion to the inflated `B+N` [3](#0-2) , redirecting reward that should have gone to legitimately staked participants toward the pool inflated by the attacker's unrelated transfer.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}

// assignStakingRewardsFlex assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewardsFlex(config *reward.RewardConfig, budget *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		minStake  = config.MinimumStake.Uint64()
		threshold = config.StakingRewardThreshold.Uint64()
		isPrague  = config.Rules.IsPrague

		cns            = si.ConsolidatedNodes()
		excessInt      = make(map[common.Address]uint64)
		totalExcessInt = uint64(0)
	)

	// Calculate the excess stakes (the amount over the threshold) for each CN.
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it. Even if (CNStaking + CLStaking) could be more than minStake,
		// the CNStaking alone must be at least minStake to be eligible.
		if cn.StakingAmount < minStake {
			continue
		}

		amount := cn.StakingAmount
		if isPrague && cn.CLStakingInfo != nil {
			amount += cn.CLStakingInfo.CLStakingAmount
		}

		// Excess is the amount over the threshold (not over minStake).
		if amount > threshold {
			excessInt[cn.RewardAddr] = amount - threshold
			totalExcessInt += excessInt[cn.RewardAddr]
		}
	}

	// Distribute the budget to the CNs based on the excess stakes.
	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(budget)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		if excessInt[cn.RewardAddr] <= 0 {
			continue
		}
		excess := new(big.Int).SetUint64(excessInt[cn.RewardAddr])

		// The KAIA unit will cancel out:
		// reward (kei) = excess (KAIA) * budget (kei) / totalExcess (KAIA)
		reward := new(big.Int).Div(new(big.Int).Mul(excess, budget), totalExcess)
		if reward.Sign() <= 0 {
			continue
		}

		// If Prague and CL is configured for this CN, split the reward between CN and CL.
		if isPrague && cn.CLStakingInfo != nil {
			cnAmount, clAmount := cn.Split(reward)
			alloc[cn.RewardAddr] = cnAmount
			alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
		} else {
			alloc[cn.RewardAddr] = reward
		}
		remaining.Sub(remaining, reward)
	}
	return alloc, remaining
}

// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining

            require(allowance[src][msg.sender] >= wad);
