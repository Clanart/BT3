### Title
PedPoP encrypted-share PoP does not bind the intended recipient, allowing ciphertext redirection and false blame of an honest sender - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to accepting a TLS certificate issued for a different hostname, `EncryptedMessage`'s proof-of-possession binds the sender, the per-message key, and the context — but never the intended recipient (the decryption key it was ECDH'd to). Any party able to relay Alice's `EncryptedMessage<C, SecretShare>` ciphertext into another participant Carol's inbound slot causes Carol to accept the PoP as valid, decrypt to garbage, and emit a blame proof that fatally slashes Alice for a share she never sent Carol.

### Finding Description
`encrypt` produces a `pop` Schnorr signature over `pop_challenge(context, nonce, key, from, msg)` [1](#0-0) . The transcript commits `sender` but contains no commitment to `to` — the recipient's registered encryption key (`self.decryption.enc_keys[&participant]` used at encryption.rs:466). On the receiving side, `Decryption::decrypt` / `decrypt_with_proof` verify the PoP with the claimed `from` and the ciphertext's own `msg.key`, then compute `ecdh(self.enc_key, msg.key)` [2](#0-1) . Because `msg.key` was ECDH'd against Bob's enc key, Carol's derived `shared_key` is wrong, ChaCha20 yields garbage, `C::F::from_repr` or `share_verification_statements` fails in `calculate_share` [3](#0-2) , and the resulting `PedPoPError::InvalidShare { participant: Alice, blame }` blames Alice — `blame_internal` returns `sender` for an invalid share [4](#0-3) . In the processor this becomes `ProcessorMessage::Blame { participant: accused }`, a fatal slash [5](#0-4) .

### Impact Explanation
An honest DKG participant is convicted on an authenticated, verifier-checkable blame proof for a share they never created for the accuser. Since blame leads to slashing in Serai's processor flow, redirection of a legitimately-issued ciphertext (valid signature, wrong "hostname"/recipient) converts one valid message into an execution against the sender — a High-class integrity impact on honest validators.

### Likelihood Explanation
Requires an adversary able to copy a sender's ciphertext into a different recipient's delivery slot. The crate explicitly assumes only sender authentication on the channel ("this still doesn't mean the DKG offers an authenticated channel... other than their existence in the assumed-to-exist external authenticated channel" — encryption.rs:299-301); nothing binds the ciphertext to its intended recipient index, so any relayer/mixer in the delivery path can perform the redirection without forging anything.

### Recommendation
Bind the recipient into `pop_challenge` (e.g., append the recipient `Participant` index and/or the recipient's registered `enc_key` to the transcript), and have both `decrypt` and `decrypt_with_proof` include the local participant/`decryptor` identity when recomputing the challenge, so a ciphertext issued for Bob fails PoP verification when presented to Carol.

### Proof of Concept
1. Run `KeyGenMachine`/`SecretShareMachine` for participants 1..=n. Alice (1) encrypts her share for Bob (2): `EncryptedMessage` E with `pop` over `sender=1`.
2. The adversary forwards E (unmodified bytes) as the `1 -> 3` share to Carol (3): `shares.insert(ONE, E.clone())` in Carol's `calculate_share`.
3. Carol's batch PoP check passes (`pop_challenge` uses `from=1`, `msg.key`, context — all valid). `ecdh(carol_enc_key, msg.key)` yields the wrong cipher key; decrypted bytes are not a valid share of `commitments[1]` evaluated at `3`.
4. `calculate_share` returns `InvalidShare { participant: 1, blame: Some(proof) }`; `blame_internal`/`AdditionalBlameMachine` confirm sender-fault since the share fails `share_verification_statements` — Alice is slashed despite behaving correctly.

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
