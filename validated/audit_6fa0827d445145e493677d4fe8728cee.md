## Analog Found: Index Confusion Between `inputs[]` and `output.assets[]` in `IntrinsicIntents._fillSameChain`

### Title
Same-chain order fill releases escrow using the wrong input's token/amount when `order.inputs.length != order.output.assets.length` - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
This is the same class of bug as the D3UserQuota report: a loop iterates using one index variable that is valid for one array (`order.output.assets`, sized `outputsLen`) but is reused to index into a *different* array (`order.inputs`) that is not guaranteed to have the same length or ordering. Just as `getExchangeRate(token)` silently substituted the wrong token for the exchange-rate lookup, `_fillSameChain` silently substitutes the wrong `TokenInfo` (wrong token address and wrong amount) when computing the escrow amount to release to the solver.

### Finding Description
In `_fillSameChain` [1](#0-0) , the loop bound is `outputsLen = order.output.assets.length`, and the loop index `i` is used throughout to read `order.output.assets[i]` and `options.outputs[i]` — that part is correctly matched.

But at the end of the loop body, the same index `i` is reused to read `order.inputs[i]` in order to compute and record the escrow release: [2](#0-1) 

`order.inputs` is a logically independent array — a single order can have a different number of input tokens than output tokens (e.g., a multi-input → single-output swap, or single-input → multi-output split). Nothing in `placeOrder`/`IntentGatewayV2.sol` or `IntentsBase.sol` enforces `order.inputs.length == order.output.assets.length`; `placeOrder` processes `inputsLen` and `outputsLen` as fully independent quantities [3](#0-2) [4](#0-3) , and no length-equality check exists anywhere in `IntentsBase.sol`'s error/validation set for this relationship.

As a result, when `order.inputs.length != order.output.assets.length`:
- `order.inputs[i]` reads a `TokenInfo` for the wrong input leg (wrong `token`, wrong `amount`), or
- reverts out-of-bounds if `inputs.length < outputsLen`.

This directly parallels the reported bug's root cause: an index/variable that is valid in one context (`token` in the outer function scope) is incorrectly reused inside a loop meant to operate on a different, per-iteration entity (`_token`).

### Impact Explanation
`escrowedAmount` (line 118/120) determines exactly how much of the escrowed input token is released to the solver via `_withdraw`, and `escrowedInputs[i].token` (line 122) determines *which* token address is packaged into the `WithdrawalRequest` that both authorizes the on-chain transfer and is emitted in `OrderFilled`. Corrupting this index means:
- The solver can be paid out against the escrow balance/token of an unrelated input leg — potentially releasing a larger-denomination token's full balance while only having filled a small output, or attempting to release a token the solver never actually earned escrow rights to.
- `_orders[commitment][wrongToken]` gets decremented instead of the intended token's escrow slot, permanently corrupting per-token escrow accounting for that commitment (the correct token's escrow entry is left unspent while the wrong one is drained), which can strand user or protocol funds in the contract or let a solver over-extract from a mismatched token bucket.

This falls squarely under "stealing or loss of funds" / "wrong beneficiary or amount" from the impact gate, since it directly manipulates the token/amount used in escrow settlement between user, solver, and protocol.

### Likelihood Explanation
Any user constructing an `Order` with differing input/output asset counts (a normal, supported shape — the contracts explicitly size `inputsLen` and `outputsLen` independently throughout `placeOrder`, `_execute`, and `_cancelSameChain`) will trigger this on the very first same-chain fill. No malicious relayer, prover, or governance actor is required — it is triggerable by any ordinary user placing an order and any solver filling it through the public `_fillSameChain` path (invoked from the public fill entrypoint).

### Recommendation
Do not index `order.inputs[i]` using the output-loop index. Either:
1. Enforce `order.inputs.length == order.output.assets.length` at `placeOrder` time if the design intends a 1:1 input/output correspondence, or
2. If multi-input/multi-output orders with mismatched lengths are intentionally supported, redesign escrow accounting to release proportionally across the *entire* `order.inputs` set (keyed by token, not by output-loop position) rather than pairing input index `i` with output index `i`.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [TokenA: 1000]` (length 1) and `order.output.assets = [TokenX: 500, TokenY: 500]` (length 2) — a legitimate 1-input/2-output order; no length check rejects this.
2. Escrow is recorded as `_orders[commitment][TokenA] = 1000` (minus fees).
3. A solver calls the same-chain fill function, fully satisfying both outputs (`i = 0` for TokenX, `i = 1` for TokenY).
4. On iteration `i = 1`, the code executes `order.inputs[1]` — but `order.inputs` only has index `0`, so with `inputsLen == 1 < outputsLen == 2` this reverts out-of-bounds (denial of fill), demonstrating the index is unconditionally coupled to the output loop rather than the actual input set.
5. In the inverse case — `order.inputs.length > order.output.assets.length` (e.g., 2 inputs, 1 output) — the loop only ever reaches `i = 0`, so `order.inputs[1]`'s escrow is never referenced in `escrowedInputs`/the withdrawal request at all, while `_execute`/`_cancelSameChain` (which iterate the full `inputsLen`) still expect it to be tracked, leaving that leg's escrow to be resolved by an inconsistent path and demonstrating the token/amount attribution is wrong whenever the two arrays diverge in length.
