### Title
`unvote()` uses inverted `isActive` check, permanently trapping voter weight on deactivated pools - ([File: wombat/WombatBribeManager.sol])

### Summary
`unvote()` is intended to let users pull their vote from a pool that has been deactivated (per its own docstring: "Unvote from an inactive pool"), but it actually reverts with `PoolNotActive` precisely when `pool.isActive` is `false` — the opposite condition. Combined with `vote()`, which also reverts on any `_lps[i]` whose `pool.isActive` is `false`, a user has no code path to zero out `userVotedForPoolInVlmgp[user][pool]` once the admin deactivates that pool.

### Finding Description
In `unvote()`: [1](#0-0) 
the check `if(!pool.isActive) revert PoolNotActive();` reverts exactly when the pool is inactive, which is the inverse of the documented intent. Meanwhile `vote()`: [2](#0-1) 
also requires `pool.isActive == true` for every `_lps[i]` passed in, including entries used solely to reduce (`delta < 0`) an existing vote. Once `poolManager`/`owner` deactivates a pool via normal (non-malicious) `addPool`/pool-state changes elsewhere in the admin flow, any unprivileged user who previously called `vote()` on that pool is left with a non-zero `userVotedForPoolInVlmgp[msg.sender][pool]` and a corresponding portion of `userTotalVotedInVlmgp[msg.sender]` and `totalVlMgpInVote` that can never be reduced through either `vote()` or `unvote()`. This permanently:
- Reduces the user's spendable/votable balance for other active pools, since `vote()` enforces `userTotalVotedInVlmgp[msg.sender] <= getUserVotable(msg.sender)` [3](#0-2) , and the trapped amount stays counted against that cap forever.
- Leaves `totalVlMgpInVote` permanently inflated with vote-weight tied to a now-inactive pool, which is used in `castVotes()` to compute proportional vote allocations to all remaining active pools (`targetVote = targetVoteInLMGP * totalVotes() / totalVlMgpInVote`) [4](#0-3) , permanently skewing vote distribution across the whole system away from the true active-pool weighting.

This is triggered purely by normal admin pool lifecycle management (deactivation is a legitimate, expected operation, not a malicious act) and an unprivileged user's own prior `vote()` call — no elevated privileges are needed to be a victim, and no privileged action is required to trigger the loss besides the routine, expected deactivation.

### Impact Explanation
This causes governance voting result manipulation: `totalVlMgpInVote` is permanently and irreversibly polluted by weight tied to deactivated pools, distorting the proportional vote allocation (`castVotes`) applied to all remaining active pools for the lifetime of the contract. It also permanently freezes the affected user's voting power/rights (their vlMGP weight is stuck against a dead pool and can never be reallocated to active pools), which persists indefinitely (far beyond 24 hours) with no user or admin remediation path in the current code.

### Likelihood Explanation
No special capital or privileges are required: any user who calls `vote()` on a pool that is later deactivated (a routine admin action) is affected. This is fully deterministic and repeatable — every affected user hits the exact same permanently-reverting path.

### Recommendation
Fix the condition in `unvote()` to allow unvoting only from inactive pools (or, more robustly, allow unvoting regardless of `isActive` state), i.e. change `if(!pool.isActive) revert PoolNotActive();` to `if(pool.isActive) revert PoolStillActive();` (or remove the active-check gating and rely on `_lp` validity alone), and ensure `vote()`'s decrease path does not require `pool.isActive == true` when `delta <= 0`, so users can always withdraw/zero their vote from a deactivated pool.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, `vlMGP`, staking mocks; call `addPool(lpA, rewarderA, "poolA")` (pool active by default).
2. User locks MGP, calls `vote([lpA], [1000e18])` — assert `userVotedForPoolInVlmgp[user][lpA] == 1000e18` and `totalVlMgpInVote == 1000e18`.
3. Admin (owner) deactivates `lpA` (e.g., via a `setPoolActive`/`removePool`+`addPool` pattern present in the admin functions, or directly toggling `poolInfos[lpA].isActive = false` in test setup to simulate the existing deactivation mechanism).
4. User calls `unvote(lpA)` — assert it reverts with `PoolNotActive()`.
5. User calls `vote([lpA], [-1000e18])` — assert it also reverts with `PoolNotActive()`.
6. Assert `userVotedForPoolInVlmgp[user][lpA]`, `userTotalVotedInVlmgp[user]`, and `totalVlMgpInVote` remain unchanged (`1000e18`) indefinitely, and that the user cannot vote up to their full `getUserVotable(user)` on any newly added active pool because the trapped amount still counts against `userTotalVotedInVlmgp[user]`.

    /// @notice Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing
    function unvote(address _lp) public {
        Pool storage pool = poolInfos[_lp];
        uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
        if(!pool.isActive)
            revert PoolNotActive();
        
        pool.totalVoteInVlmgp -= uint256(currentVote);
        userTotalVotedInVlmgp[msg.sender] -= uint256(currentVote);
        userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] = 0;
        if (msg.sender != delegatedPool) {
            totalVlMgpInVote -= currentVote;
        }
        
        IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(currentVote), true);
    }
