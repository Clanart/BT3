### Title
Missing slippage protection in `WombatPoolHelperV2.depositFor()` exposes users to sandwich attacks on pool deposit - ([File: wombat/WombatPoolHelperV2.sol])

### Summary
`WombatPoolHelperV2.depositFor()` hardcodes `_minimumLiquidity` to `0` when calling into `_deposit()`, which ultimately invokes `WombatStaking.deposit()` and then `IWombatPool.deposit()`. [1](#0-0)  Unlike the standard `deposit(uint256 _amount, uint256 _minimumLiquidity)` entrypoint, which lets the caller specify a slippage-protection value, `depositFor()` unconditionally passes `0` as the minimum liquidity to receive, removing all slippage protection for callers using this path. [2](#0-1) 

### Finding Description
`WombatStaking.deposit()` calls `IWombatPool(poolInfo.depositTarget).deposit(depositToken, _amount, _minimumLiquidity, address(this), block.timestamp, false)` and then mints the receipt token 1:1 with the actual `lpReceived` amount, whatever it ends up being. [3](#0-2)  The amount of LP received from a Wombat stable pool deposit depends on the pool's internal equilibrium/coverage-ratio pricing at execution time, which can be manipulated within the same block (front-run/back-run) to reduce the LP output for a given input, analogous to the StargatePlugin's `swap()` call passing `0` as the minimum amount out in the referenced report. Because `depositFor()` locks this parameter to `0`, any unprivileged wallet using `depositFor()` has no way to bound the acceptable slippage, and the resulting under-minted receipt tokens are minted directly to the caller with no reversion path if the received LP amount is abnormally low.

### Impact Explanation
A malicious actor can sandwich a `depositFor()` call by manipulating the target Wombat pool's coverage ratio before the deposit executes, causing the depositor to receive fewer LP/receipt tokens than a fair-market deposit would yield. Since receipt tokens directly back the user's staked balance and future reward/withdrawal rights in the WombatStaking/MasterMagpie system, this results in a direct, concrete loss of user funds at the moment of deposit, with no way for the victim to prevent or detect it on-chain (the call simply succeeds with a worse-than-expected minted amount).

### Likelihood Explanation
This is triggerable by any ordinary wallet simply by calling the already-deployed, permissionless `depositFor()` function on `WombatPoolHelperV2` with normal deposit parameters; the attacker's side (a front-running actor manipulating pool coverage ratio) requires no privileged role, matching the "no admin/no privilege" scope required by the rules. The bug is a straightforward oversight, hardcoding `0` instead of exposing/using a caller-supplied minimum, making it easy to exploit whenever there's sufficient liquidity/latency to front-run.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor()` (or otherwise let the caller supply a non-zero minimum) and thread it through to `_deposit()` / `WombatStaking.deposit()` instead of hardcoding `0`, mirroring the protection already present in the standard `deposit(uint256 _amount, uint256 _minimumLiquidity)` function in the same contract. [4](#0-3) 

### Proof of Concept
1. Attacker observes a pending `depositFor()` transaction in the mempool. [1](#0-0) 
2. Attacker front-runs it with a transaction that skews the target Wombat pool's coverage ratio for the deposited asset, temporarily worsening the deposit's effective exchange rate.
3. The victim's `depositFor()` call executes with `_minimumLiquidity = 0` hardcoded, so `IWombatPool.deposit()` succeeds regardless of how little LP is returned. [5](#0-4) 
4. `WombatStaking` mints `poolInfo.receiptToken` to the caller based only on the actual (reduced) `lpReceived`, permanently reflecting the sandwich loss in the user's minted receipt/staked balance. [6](#0-5) 
5. Attacker back-runs to restore the pool ratio and captures the value difference, while the victim's minted receipt tokens (and all downstream staking/reward accounting) reflect a permanently reduced position.
