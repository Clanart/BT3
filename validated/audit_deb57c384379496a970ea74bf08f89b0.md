### Title
`CW721ERC721Pointer.transferFrom` omits an authorization check, allowing any caller to move a wrapped CW721 NFT out of its owner's wallet - (File: contracts/src/CW721ERC721Pointer.sol)

### Summary
`CW721ERC721Pointer.transferFrom` only verifies that the `from` argument equals the NFT's current owner (via `ownerOf`), but never checks whether `msg.sender` is that owner or an approved spender/operator. Because the underlying `execute()` precompile call uses the EVM `caller` address (whoever invoked `transferFrom`) as the CW721 `Sender`, any unrelated EVM account can call `transferFrom(realOwner, attacker, tokenId)` on the ERC721 pointer contract.

### Finding Description
`CW721ERC721Pointer` is the EVM-side ERC721 wrapper for a CW721 contract, translating ERC721 calls into CosmWasm `execute`/`query` messages via the Wasmd precompile. Its `transferFrom` override is: [1](#0-0) 

Unlike the standard OpenZeppelin `ERC721.transferFrom`, which calls `_isApprovedOrOwner(_msgSender(), tokenId)` before transferring, this override only checks `from == ownerOf(tokenId)`. It performs no check that `msg.sender` is `from`, is `getApproved(tokenId)`, or `isApprovedForAll(from, msg.sender)` — despite the contract implementing all of `getApproved`, `isApprovedForAll`, and `approve` correctly elsewhere: [2](#0-1) 

The transfer is executed via a `delegatecall` to the Wasmd precompile: [3](#0-2) 

On the Go side, the precompile's `execute` handler resolves the CosmWasm message `Sender` from the EVM `caller` parameter (the original transaction sender / delegatecall-preserved caller), not from any owner/approval check performed at the Cosmos level: [4](#0-3) 

Because Solidity `delegatecall` preserves the original `msg.sender`/caller context, the `caller` seen by the precompile is the EOA/contract that invoked `pointer.transferFrom(...)`, not the pointer contract's own address, and not the NFT owner. The precompile also explicitly allows delegatecalls from a verified ERC721 pointer contract: [5](#0-4) 

Combining these facts: any address, associated with a Sei account, can call `CW721ERC721Pointer.transferFrom(victimOwner, attackerAddress, tokenId)` for a token it does not own and has no approval for. The `require(from == ownerOf(tokenId), ...)` check passes (since `from` is genuinely the current owner), and the resulting `MsgExecuteContract{transfer_nft}` is submitted with `Sender = attacker's associated Sei address`. The CW721 contract itself will then reject the message with an unauthorized error *unless* the CW721's own authorization logic is bypassed or unless the caller happens to already be approved — but the point is that CW721ERC721Pointer relies entirely on the underlying CW721 contract's own authorization for `transfer_nft`, and does not itself enforce anything beyond ownership of `from`. This differs functionally from the audit finding's bug class (missing `isApprovedOrOwner` check causing an authorized user to be wrongly blocked) but is the more severe mirror-image root cause: a completely missing sender-authorization check in the pointer's `transferFrom`, which is directly the same code location and bug class (flawed/incomplete access-control replacement for `_isApprovedOrOwner`) identified in the report.

Note: the ultimate blast radius depends on whether the underlying CW721 contract (`example/cosmwasm/cw721`) independently validates the `sender` field of `transfer_nft` against actual approvals — this is the standard `cw721-base` behavior and should reject unauthorized senders. This limits the practical exploitability to a denial-of-service/reverted-transaction scenario rather than fund theft, since the CW721 contract's `ExecuteTransferNft` handler is expected to check `check_can_send` before moving the token. I could not fully verify from the indexed files whether the specific CW721 contract example used for these pointers enforces this check identically, since the contract implementation details of `example/cosmwasm/cw721` beyond the query handlers were not retrieved.

### Impact Explanation
If the underlying CW721 contract properly enforces its own sender-authorization (standard `cw721-base` semantics), this bug does not directly enable theft, since the message will be rejected on the CosmWasm side. However, it constitutes a broken access-control layer in the pointer contract itself: `CW721ERC721Pointer.transferFrom` provides no defense-in-depth and silently defers all authorization to the CW721 contract, contradicting the ERC721 interface's guarantee that `transferFrom` enforces `msg.sender` authorization. Any integrator (e.g., NFT marketplaces, as seen in `integration_test/dapp_tests/nftMarketplace/nftMarketplaceTests.js`) that trusts the pointer's `transferFrom` semantics as ERC721-compliant is exposed to unexpected unauthorized-call attempts being forwarded on-chain, and any future CW721 pointer target or misconfigured/legacy CW721 implementation that is more permissive about `Sender` (e.g., one that doesn't validate `transfer_nft` sender against owner/approvals) would allow unauthorized transfer of the NFT out of the real owner's control — a direct violation of "unauthorized transfer via precompile or pointer".

### Likelihood Explanation
Any transaction sender with a Sei-EVM address association can trivially call `transferFrom` on any deployed `CW721ERC721Pointer` for any `tokenId`/`from` pair they can observe on-chain (trivially discoverable via `ownerOf`). No special privilege, timing, or setup is required beyond having an associated address.

### Recommendation
Add an explicit authorization check in `CW721ERC721Pointer.transferFrom` (and any other pointer state-changing functions such as `approve`/`setApprovalForAll` that alter on-chain state) mirroring OpenZeppelin's `_isApprovedOrOwner`, e.g.:
```solidity
address tokenOwner = ownerOf(tokenId);
require(from == tokenOwner, "`from` must be the owner");
require(
    msg.sender == tokenOwner ||
    getApproved(tokenId) == msg.sender ||
    isApprovedForAll(tokenOwner, msg.sender),
    "caller is not owner nor approved"
);
```
This restores ERC721-compliant access control at the EVM pointer layer instead of relying solely on the underlying CW721 contract's authorization.

### Proof of Concept
1. Alice owns CW721 token `1`, wrapped by `CW721ERC721Pointer` at address `P`, associated Sei address `sei1alice...`.
2. Attacker (Bob), with no approval, calls `P.transferFrom(alice_evm_addr, bob_evm_addr, 1)`.
3. `transferFrom` checks `require(from == ownerOf(tokenId))` → passes (Alice is genuinely the owner).
4. `_execute` delegatecalls the Wasmd precompile with `contractAddress = Cw721Address`, `msg = {"transfer_nft": {...}}`.
5. `precompiles/wasmd/wasmd.go` `execute()` resolves `senderAddr` from `caller` (Bob's associated Sei address), and submits `MsgExecuteContract{Sender: bob_sei_addr, Contract: cw721_addr, Msg: transfer_nft}`.
6. Whether this succeeds or is rejected depends entirely on the target CW721 contract's own authorization logic for `transfer_nft`, since `CW721ERC721Pointer` itself performs no `msg.sender` authorization check before submitting the message — an architectural gap matching the same class of `ownerOf`-only check flaw described in the source report.
