I found a concrete local analog: a cross-function signed-message collision in `pallet-relayer` between the fee-accumulation beneficiary-redirect signature and the fee-withdrawal signature. Both are built from the exact same SCALE-encoded tuple and consume the exact same `Nonce` storage slot, so a signature meant to authorize one action is byte-identical to (and thus replayable as) a signature authorizing the other, unrelated, action.

### Title
Cross-function signature replay between `beneficiary_message` and `message` lets a captured relayer signature drain the full `Fees` balance instead of the intended batch redirect - ([File: modules/pallets/relayer/src/accumulate.rs] / [File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-relayer` exposes two unsigned, signature-authenticated extrinsics that both operate on the same `Nonce<T>` double-map keyed by `(address, StateMachine)`:
- `accumulate_fees` → `Pallet::accumulate`, which optionally verifies a `beneficiary_message(nonce, state_machine, beneficiary)` signature to redirect that batch's freshly-proved fee to a beneficiary.
- `withdraw_fees` → `Pallet::withdraw`, which verifies a `message(nonce, dest_chain, beneficiary)` signature to drain the entire `Fees[dest_chain][address]` balance to a beneficiary. [1](#0-0) [2](#0-1) 

Both helper functions hash the identical SCALE-encoded tuple `(nonce: u64, StateMachine, beneficiary bytes)` when a beneficiary is supplied, with no domain separator distinguishing "batch redirect" from "full withdrawal": [3](#0-2) [4](#0-3) 

### Finding Description
`Nonce<T>` is one shared storage map used by both flows: [5](#0-4) 

In `accumulate`, the beneficiary-redirect signature is checked against `Nonce::<T>::get(&delivery_address, state_machine)` where `state_machine = withdrawal_proof.source_proof.height.id.state_id`: [6](#0-5) 

In `withdraw`, the signature is checked against `Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain)`: [7](#0-6) 

Because `message(nonce, dest_chain, Some(bytes))` and `beneficiary_message(nonce, state_machine, bytes)` produce byte-identical hashes when `dest_chain == state_machine`, `nonce` matches, and the beneficiary bytes match, a signature a relayer produces to authorize a small, single-batch fee redirect via `accumulate_fees` is simultaneously a valid signature to authorize `withdraw_fees`, which drains the relayer's *entire* accumulated `Fees[state_machine][address]` balance (built up from many prior deliveries) to that same beneficiary. Both extrinsics are `ensure_none` (unsigned, pool-visible) calls, so the signed payload travels through the public transaction pool before being included on-chain — any observer can extract it and race it into the other call.

There is no cross-context tag (e.g., a leading discriminant byte or distinct hash domain) in either `message` or `beneficiary_message` to prevent one signed payload from being valid input to the other extrinsic, and the shared `Nonce` key space means an attacker who wins the race consumes the nonce for both, but the *action taken* is whichever call landed first — which can be the higher-value, unintended one (full withdrawal) instead of the low-value one the relayer actually meant to authorize (batch redirect).

### Impact Explanation
This is a logic/transaction-manipulation bug in the relayer reward pipeline: an unprivileged party who merely observes a public, unsigned `accumulate_fees` transaction containing a beneficiary-redirect signature can resubmit that exact signature via `withdraw_fees` and force settlement of the relayer's full accrued fee balance rather than the narrowly-scoped batch amount the relayer intended to authorize — an unauthorized reinterpretation/execution of a signed authorization outside its intended scope, matching the bounty's "unauthorized transaction or execution" / "logic attacks" / "transaction manipulation" classes on real relayer funds held in `Fees<T>`.

### Likelihood Explanation
Both `accumulate_fees` and `withdraw_fees` are unsigned extrinsics (`ensure_none`), meaning the signed payloads are necessarily broadcast and visible in the public transaction pool before inclusion, so no privileged access, malicious relayer collusion, or node compromise is required — only public mempool observation and a race to submit the alternate extrinsic first, which is a normal front-running capability on any public chain.

### Recommendation
Add a distinct domain separator (e.g., a fixed prefix byte/string unique to each purpose) into both `message()` and `beneficiary_message()` before hashing, and/or split `Nonce<T>` into two separate maps (one for withdrawal authorizations, one for beneficiary redirects) so a signature valid for one action can never be replayed as authorization for the other.

### Proof of Concept
1. A relayer delivers requests and calls `accumulate_fees` with `beneficiary_details = Some((beneficiary_bytes, signature))`, where `signature` is over `beneficiary_message(nonce, state_machine, &beneficiary_bytes)` [8](#0-7) .
2. This transaction sits in the public transaction pool prior to inclusion.
3. An observer extracts `signature`, `nonce` (read from current `Nonce::<T>::get(relayer, state_machine)`), and `beneficiary_bytes`, and submits `withdraw_fees` with `WithdrawalInputData { signature, dest_chain: state_machine, beneficiary: Some(beneficiary_bytes) }` [7](#0-6) .
4. `withdraw()` recomputes `message(nonce, dest_chain, Some(beneficiary_bytes))`, which hashes identically to the `beneficiary_message` the relayer actually signed, so signature verification succeeds.
5. `withdraw()` proceeds to drain the relayer's entire `Fees[state_machine][address]` balance to `beneficiary_bytes` and increments the shared nonce, all before (or instead of) the originally intended `accumulate_fees` batch-redirect settles as designed.

/// Signed payload authorising a beneficiary redirect on a specific source chain.
/// Including the relayer nonce alongside the state machine keeps the signature usable for
/// exactly one accumulate call on that chain, mirroring how `withdraw_fees` binds its signed
/// payload.
pub fn beneficiary_message(
	nonce: u64,
	state_machine: StateMachine,
	beneficiary: &[u8],

	sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary).encode())

/// Signed payload for [`WithdrawalInputData`]. Includes the per-relayer nonce so a captured
/// signature cannot be replayed.
pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
