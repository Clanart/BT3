Based on the evidence gathered, here is the identified vulnerability.

### Title
Non-monotonic L2 block timestamps in `StateCommitment` allow premature request timeouts (double-settlement) - ([File: modules/ismp/core/src/handlers/timeout.rs])

### Summary
Hyperbridge's ISMP core never enforces that a `StateCommitment.timestamp` is monotonically increasing with respect to previously stored commitments for the same state machine. The timestamp stored per height is taken verbatim from the underlying L2/L1 block header or output-root proposal (e.g. Arbitrum Orbit, OP Stack), which — exactly as described in the external report — can be non-monotonic because these systems mix multiple timestamp sources (sequencer blueprints vs. delayed/forced inbox blocks). Since `handle_timeouts` decides whether a `PostRequest`/`GetRequest` has timed out purely by comparing `post.timeout()` against the `timestamp` field of whichever previously-stored `StateCommitment` height the caller supplies, an inflated (non-monotonic) timestamp at an early height lets anyone trigger a timeout before the destination chain has actually reached that time, while the request can still be legitimately delivered and executed on the destination later — producing a double-settlement (refund on the source + execution on the destination).

### Finding Description
`update_client` in [1](#0-0)  only enforces that new intermediate-state heights are greater than the previously stored `latest_commitment_height`; it never checks that the incoming `StateCommitment.timestamp` is greater than the timestamp already recorded for a lower (or the previous) height:

```
// Only allow heights greater than latest height
if previous_latest_height > commitment_height.height { continue; }
// Skip duplicate states
if host.state_machine_commitment(state_height).is_ok() { continue; }
...
host.store_state_machine_commitment(state_height, commitment_height.commitment)?;
```

The `timestamp` value itself is sourced directly, unchecked, from the proven L2 header/output-root in the consensus-client verifiers, e.g. `verify_arbitrum_payload` in [2](#0-1)  and `verify_optimism_payload` in [3](#0-2) . Neither verifier checks the new timestamp against any previously stored commitment.

This unchecked timestamp is then used as the sole timeliness oracle for the timeout handler. In `handlers::timeout::handle`, for `TimeoutMessage::Post`:

```
let state = host.state_machine_commitment(timeout_proof.height)?;
...
if !post.timed_out(state.timestamp()) {
    Err(Error::RequestTimeoutNotElapsed { ... })?
}
``` [4](#0-3) 

`timeout_proof.height` is attacker-supplied — any state-machine height for which Hyperbridge already stores a `StateCommitment` and for which the caller has a valid non-membership proof of the request. The only gating checks before this comparison are the frozen-client check and the challenge-period elapsed check (`validate_state_machine`), both of which are about Hyperbridge's own ingestion clock, not about whether the referenced height is chronologically consistent with the destination chain's real time. The identical unchecked pattern exists in the EVM equivalent, `handlePostRequestTimeouts`/`handleGetRequestTimeouts` in [5](#0-4) , which compares `request.timeout() > state.timestamp` for a caller-chosen `message.height` and a `StateCommitment` fetched from storage with no monotonicity guarantee.

Because Arbitrum-Orbit-family/OP-Stack-family rollups can legitimately produce non-monotonic block timestamps for the exact reason described in the external report (blueprint timestamp vs. delayed/forced-inbox timestamp), a legitimately-proven, non-malicious block at an earlier height can carry a timestamp that already exceeds `post.timeout()`, even though the true destination-chain time has not.

### Impact Explanation
An unprivileged caller can submit a timeout proof anchored to an early height whose (legitimately proven) `StateCommitment.timestamp` is spuriously ahead of the destination chain's real time. This satisfies `post.timed_out(state.timestamp())`, deletes the request commitment, and invokes the source module's `on_timeout` callback — which typically refunds escrowed relayer fees/funds to the sender/payer (bridge custody, paymaster balances, order escrow). Because the destination chain's `dispatchIncoming`/`handlePostRequests` path is independent of the source's request-commitment bookkeeping (it only checks destination-local `requestReceipts` for duplicates), the same request can still be legitimately delivered and executed on the destination afterward. The result is a genuine double-settlement: funds released back on the source via the timeout path and the cross-chain effect still executed on the destination — a direct loss/duplication of funds matching the bounty's "double-claim/double-settlement" and "logic attack" categories.

### Likelihood Explanation
This does not require a malicious relayer, prover, or Hyperbridge operator — only a permissionless timeout submission referencing a real, correctly-proven state commitment. The precondition (non-monotonic L2/L1 block timestamps for rollup-derived state machines) is a demonstrated, real-world bug class in the exact rollup architectures Hyperbridge integrates as consensus clients (Arbitrum Orbit, OP Stack), as evidenced by the external report itself. Likelihood is therefore tied to how often the integrated L2's sequencer/inbox produces a timestamp regression relative to height — a non-adversarial, protocol-level condition rather than a contrived attacker capability.

### Recommendation
Enforce timestamp monotonicity when persisting new `StateCommitment`s in `update_client` (`modules/ismp/core/src/handlers/consensus.rs`): reject or clamp any incoming commitment whose `timestamp` is not greater than the timestamp stored for the previous (or any higher) already-committed height for the same state machine. Additionally, in `handlers::timeout::handle` and the EVM `handlePostRequestTimeouts`/`handleGetRequestTimeouts`, prefer comparing against the *latest* known commitment's timestamp (or require the supplied height to be the latest/verified-monotonic height) rather than trusting an arbitrary caller-chosen historical height's timestamp for timeout determination.

### Proof of Concept
1. An Arbitrum-Orbit-based (or OP-Stack-based) destination chain configured with Hyperbridge produces two committed heights H1 < H2 where, due to the sequencer-blueprint vs. delayed-inbox timestamp source mismatch (as in the external report), `timestamp(H1) > timestamp(H2)` even though H2 is chronologically later.
2. A `PostRequest` is dispatched from chain A to this destination with `timeout_timestamp = T`, where `timestamp(H1) > T` but the destination chain's true wall-clock time (and `timestamp(H2)`) is still `< T`.
3. Attacker submits `TimeoutMessage::Post` (or EVM `handlePostRequestTimeoutMessage`) referencing `timeout_proof.height = H1`, with a valid non-membership proof (the request truly hasn't been processed at H1's state root).
4. `post.timed_out(state.timestamp())` evaluates true using H1's inflated timestamp; the handler deletes the request commitment and invokes `on_timeout`, refunding escrowed funds/fees on the source chain.
5. Later, a relayer submits the original `PostRequest` with a membership proof at height H2 (or later) via `handlePostRequests`/`dispatchIncoming` on the destination chain — this succeeds because destination-side duplicate checks only look at `requestReceipts`, not the source's now-deleted `requestCommitments` — executing the module logic a second time and completing a double-settlement.

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
