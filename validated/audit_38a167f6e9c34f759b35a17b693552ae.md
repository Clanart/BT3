### Title
Spoofed `WWW-Authenticate` realm header from a git remote/proxy triggers an Enterprise GitHub sign-in flow against an attacker-controlled origin - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
When Git needs credentials for a remote, Desktop's credential-helper trampoline classifies the requesting endpoint as `'github.com'`, `'ghe.com'`, `'enterprise'`, or `'generic'` in order to decide how to source credentials. One of the classification branches trusts a `wwwauth[]` header value forwarded by the remote/proxy itself, with no cross-check against a known GitHub Enterprise install, similar to how the Fintroller report flagged setters that mutate one piece of state (`isLiquidateBorrowAllowed`, `collateralRatio`, etc.) without validating consistency against related state (`isBorrowAllowed`, `liquidationIncentive`). Here, the "configuration" being set inconsistently is the trust classification of a remote endpoint, purely from unauthenticated response data.

### Finding Description
`getEndpointKind()` iterates the credential helper's captured headers looking for a `wwwauth[...]` key and, if its value contains `realm="GitHub"`, unconditionally returns `'enterprise'`: [1](#0-0) 

This value originates entirely from the HTTP response of whatever server git is talking to for a given remote — i.e., attacker-controlled if the user has added (or been redirected/proxied to) a malicious/MITM'd remote. There is no verification that the host is actually a registered/known GitHub Enterprise instance before this branch fires; the check happens *before* the fallback `isGitHubHost(endpoint)` real API probe: [2](#0-1) 

That classification feeds directly into `getCredential()`, which — for any endpoint classified as non-`'generic'` for which there is no matching stored account — calls `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

`promptForGitHubSignIn()` then inspects the (attacker-controlled) endpoint's hostname; since it isn't `github.com`, it calls `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)` using the attacker's origin, and shows a native `SignIn` popup flagged as a credential-helper-triggered sign-in: [4](#0-3) 

This means an attacker who controls the server behind a git remote (a cloned/fetched repository's origin, or any git host/proxy the user interacts with — no local access, no prior credentials, no malware required) can, purely by returning a crafted `WWW-Authenticate: realm="GitHub"` header during a git HTTP auth challenge, cause Desktop to pop up a "Sign in to GitHub Enterprise" dialog whose target endpoint is the attacker's own server. Existing guards (`isDotCom`, `isGHE`, matching against already-stored accounts) do not block this path because the `wwwauth[]` branch is checked before the `isGitHubHost` network probe and is evaluated purely from client-visible header content that the "server" fully controls.

### Impact Explanation
If the user, believing this is a legitimate Enterprise sign-in prompt for a real host, proceeds through the Enterprise sign-in flow, any credentials, OAuth device codes, or PAT entered are sent to the attacker-controlled origin (`setSignInEndpoint(origin)` pins the flow to that origin), resulting in credential/token exfiltration and a spoofed GitHub Enterprise "account binding" inside Desktop. Because the trust decision is baked into the identical code path used for real GHES hosts, no distinguishing UI difference alerts the user that the target is not verified.

### Likelihood Explanation
Any git host (or a machine-in-the-middle for an HTTP remote) can trivially return a custom `WWW-Authenticate` response header on a 401 challenge — this is a single header, not a spoofed TLS cert or complex protocol behavior, and git's credential-helper protocol already forwards `wwwauth[]` values verbatim to helpers, which is what Desktop's trampoline reads. The only user action required is fetching/pushing/pulling against a repository whose remote is attacker-controlled — a completely ordinary Desktop operation, not an "unnatural" step.

### Recommendation
Do not trust the `wwwauth[]` realm hint alone to classify a host as GitHub Enterprise. Require it to be corroborated by an authenticated signal such as `isGitHubHost()`'s real API probe, or a previously-verified enterprise endpoint list, before routing into `promptForGitHubSignIn()`. At minimum, surface the actual endpoint hostname prominently in the sign-in popup and avoid auto-selecting the Enterprise sign-in flow based purely on unauthenticated header content.

### Proof of Concept
1. Set up a git-over-HTTP server (or a MITM proxy for a repo's HTTP remote) that responds to unauthenticated git requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Add this server as a remote in GitHub Desktop and trigger a fetch/pull/push so git invokes the credential helper trampoline.
3. Git captures the `WWW-Authenticate` header and forwards it as `wwwauth[0]=Basic realm="GitHub"` to Desktop's `credential get` trampoline call.
4. `getEndpointKind()` matches `realm="GitHub"` and returns `'enterprise'` [5](#0-4) .
5. Since no stored account matches the attacker's endpoint, `getCredential()` calls `ui.promptForGitHubSignIn(endpoint)` with `endpoint` pointing at the attacker's server [6](#0-5) .
6. Desktop shows a "Sign in to GitHub Enterprise" dialog bound to the attacker's origin via `setSignInEndpoint(origin)` [7](#0-6) , and any credentials the user enters are sent to the attacker's server.
