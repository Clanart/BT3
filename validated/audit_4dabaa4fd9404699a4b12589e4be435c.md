## Title
Line-index-based diff selection allows silent inclusion of unintended lines in a commit when the working-directory diff is refreshed mid-review - (File: `app/src/lib/stores/app-store.ts`, `app/src/models/diff/diff-selection.ts`)

### Summary
GitHub Desktop tracks which lines a user has selected for a partial commit not by line *content* but by a numeric absolute index into the unified diff (`unifiedDiffStart + lineIndex`). When the working-directory diff for the currently selected file is reloaded (e.g. because the file on disk changed while the user was reviewing/selecting lines), Desktop only prunes selection indices that are no longer "includeable" lines — it does not verify that the content at a given index is still the same content the user originally selected. If the file changes shape (lines added/removed) between the initial diff load and the recomputation, a previously-selected index can silently come to refer to a different, unreviewed line, which will then be included in the patch used for `git apply`/commit without the user ever having seen or approved that specific line.

### Finding Description
The selection model `DiffSelection` in [1](#0-0)  stores a `Set<number>` of `divergingLines` — pure integer offsets — with no association to the actual line text. `isSelected()` simply checks membership of the absolute index: [2](#0-1) .

When the diff for the selected file is refreshed, `updateChangesWorkingDirectoryDiff()` in the app store recomputes the new `selectableLines` set purely from the new diff's includeable lines and reconciles it with the *existing* selection object via `withSelectableLines()`, explicitly acknowledging the limitation in its own comment: [3](#0-2) 

`withSelectableLines()` only removes indices that are no longer selectable at all (e.g., turned into context or removed) — it does not check whether the line at a surviving index still represents the same textual change: [4](#0-3) 

Consequently, if the file changes in a way that shifts line numbering but keeps the same relative index "includeable" (e.g. one addition is replaced by a different addition at the same or a nearby position, or a deletion/insertion pair reorders lines), the stale index remains in `divergingLines` and is reported as selected for a completely different line of content.

This selection state is consumed verbatim by `formatPatch()` when building the exact hunk that gets staged/committed, using `file.selection.isSelected(absoluteIndex)` per line with no cross-check against previously reviewed content: [5](#0-4) . The resulting patch is applied to the index via `applyPatchToIndex`/`stageFiles`, which trusts the file's `DiffSelection` completely: [6](#0-5) .

The window for this race is real: a diff reload is triggered any time the app refreshes status while the Changes view is open (e.g. periodic refresh, focus regain, or a git operation running concurrently such as a hook, a background fetch that touches the working tree, or another tool/process writing to a tracked file) — none of which requires the diff panel to be closed or the user to take any unusual action.

### Impact Explanation
This breaks the core commit-review guarantee of GitHub Desktop: what the user visually selects and reviews in the diff view is what gets committed. Because the reconciliation logic re-validates only "is this index still an includeable line" rather than "does this index still refer to the same content," a concurrently modified working tree can cause **content the user never selected or reviewed to be silently staged and committed** (or conversely, cause content the user did select to be dropped). This is a silent corruption of what the user commits — matching the class of impact called out as valid (corruption of committed/pushed content), without requiring any elevated privilege, only a file that is being tracked and can change on disk while Desktop's diff is open (e.g. via a build tool, a git hook triggered by a fetch/checkout of an attacker-influenced repository, or another background process).

### Likelihood Explanation
Likelihood is moderate: it requires (1) the user to have made a partial line selection, and (2) the file's diff to be recomputed with content shifted while that selection is stale but not fully invalidated. Desktop's own architecture makes diff refreshes routine (window focus, timers, status polls, hooks), and the code comment explicitly documents that the "settle for now" fix does not fully solve the staleness problem, indicating the developers were aware this specific gap exists but left it unaddressed.

### Recommendation
Track selections by content-stable identity rather than raw absolute index — e.g., anchor selection to the underlying line's diff-line-type plus a content hash/text snapshot, or diff the old and new hunks structurally and re-map only lines that are unambiguously the same change. At minimum, when `withSelectableLines()` detects that the new diff's line count/structure at a previously-selected index no longer matches the line's original text, that index should be dropped from the selection (fail-closed) instead of silently carried forward.

### Proof of Concept
1. In Desktop, modify a tracked file to produce a diff with an addition at absolute index N; select only that line for partial commit (leaving the file otherwise unstaged).
2. Before committing, have an external process (e.g., a build script, git hook, or another app) rewrite the file so that the diff at the same relative index N now corresponds to a different added line (still an "includeable" Add line), while the app is refreshing its working-directory diff (`updateChangesWorkingDirectoryDiff`).
3. Trigger the diff refresh (e.g. bring the app to foreground / wait for periodic status refresh) — `withSelectableLines()` preserves index N because it is still includeable, `getSelectionType()`/`isSelected()` still report it selected.
4. Commit the partial selection. `formatPatch()` builds the patch using `isSelected(N)`, staging the new, unreviewed line content instead of (or in addition to) the originally selected line, per [7](#0-6) .

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }

  /**
   * Returns a copy of this selection instance with a specified set of
   * selectable lines. By default a DiffSelection instance allows selecting
   * all lines (in fact, it has no notion of how many lines exists or what
   * it is that is being selected).
   *
   * If the selection instance lacks a set of selectable lines it can not
   * supply an accurate value from getSelectionType when the selection of
   * all lines have diverged from the default state (since it doesn't know
   * what all lines mean).
   */
  public withSelectableLines(selectableLines: Set<number>) {
    const divergingLines = this.divergingLines
      ? new Set([...this.divergingLines].filter(x => selectableLines.has(x)))
      : null

    return new DiffSelection(
      this.defaultSelectionType,
      divergingLines,
      selectableLines
    )
  }

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }
