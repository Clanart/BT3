### Title
Silent fail-open of hookify block rules due to cwd-relative glob path in `load_rules()` - ([File: plugins/hookify/core/config_loader.py])

### Summary
`load_rules()` locates rule files with a relative glob pattern `os.path.join('.claude', 'hookify.*.local.md')`, which is resolved against the hook process's current working directory rather than the repository/project root. If Claude Code invokes the `PreToolUse`/`PostToolUse`/`Stop`/`UserPromptSubmit` hooks with a cwd that diverges from where `.claude/` actually lives (subdirectory invocation, worktree, nested repo), `glob.glob()` returns an empty list and all hookify rules — including `action: block` rules — are silently dropped for the session with no warning or fail-closed behavior.

### Finding Description
`load_rules()` in [1](#0-0)  builds the glob pattern from a hardcoded relative path and calls `glob.glob(pattern)` without any anchoring to a known project root, environment variable, or upward directory search. The hook entry point `pretooluse.py` calls this directly: [2](#0-1)  — `rules = load_rules(event=event)` followed immediately by `engine.evaluate_rules(rules, input_data)`. There is no verification that any rule files were found, no comparison against an expected/pinned `.claude` directory, and no signal is surfaced to the user when the rule set is empty. `hooks.json` registers the hook command via `${CLAUDE_PLUGIN_ROOT}/hooks/pretooluse.py` without pinning a `cwd` for the invocation [3](#0-2) , so the effective working directory used for the relative glob depends entirely on how/where Claude Code was invoked. If the cwd differs from the directory containing `.claude/`, `files = glob.glob(pattern)` evaluates to `[]`, the `for file_path in files` loop never executes, and `load_rules()` returns `[]` with no error path, warning, or exception raised. The top-level `except Exception` handler in `pretooluse.py` (lines 61-66) is also not triggered, since no exception occurs — this is a silent, "successful" empty result.

### Impact Explanation
Because `pretooluse.py` treats an empty rule list identically to "no matching rules configured," an attacker who structures a repository with nested directories, submodules, or a git worktree such that Claude Code executes tool calls with cwd not equal to the `.claude`-containing root effectively disables all hookify-based `action: block` guardrails for the entire session, with zero indication to the user that protection was silently bypassed. This directly violates the deny-means-deny and workspace-confinement/state-binding invariants that hookify is meant to enforce, since a security control that is expected to fail closed instead fails open without any signal.

### Likelihood Explanation
The precondition is plausible and requires no special privilege: any repository content can include nested subdirectories or a worktree layout, and Claude Code's per-invocation cwd for hook execution is not something the unprivileged attacker needs to control directly — they only need the victim's session to be operating from a cwd other than the `.claude` root (e.g., user `cd`s into a subpackage, or Claude Code is launched from a worktree checkout). This is a plausible and repeatable scenario, not a one-off edge case, since it depends only on ordinary repository layout choices.

### Recommendation
Anchor rule discovery to a known project root instead of the ephemeral process cwd — e.g., resolve `.claude` relative to `CLAUDE_PROJECT_ROOT`/`CLAUDE_PLUGIN_ROOT`-adjacent project markers, or walk upward from cwd to find the nearest `.claude` directory (similar to git's `.git` discovery), and cache/pin the discovered root for the session. Additionally, `load_rules()` should distinguish "no `.claude` directory found at all" from "found `.claude` but zero matching rule files," and emit a `systemMessage` warning in the former case rather than silently returning `[]`, so the fail-open condition is at least visible to the user/session.

### Proof of Concept
Integration test plan:
1. Create a temporary directory `repo/` containing `repo/.claude/hookify.block-rm.local.md` with `action: block` frontmatter matching `rm -rf`.
2. Create `repo/subdir/`.
3. Invoke `pretooluse.py` (via subprocess, feeding a `Bash` tool-call JSON with `command: "rm -rf /"`) twice:
   - Once with `cwd=repo/` — assert the returned JSON contains a `block`/deny decision.
   - Once with `cwd=repo/subdir/` — currently asserts (bug) that the same dangerous command is allowed (`load_rules()` returns `[]`, `evaluate_rules` produces no block), demonstrating the silent bypass.
4. Expected post-fix behavior: both invocations should discover the rule file (via upward directory walk or pinned root) and return an identical block decision, or the subdir invocation should emit a `systemMessage` warning indicating rules could not be located, rather than silently allowing the operation.
