### Title
`addr` precompile's `associate`/`associatePubKey` can be front-run to force-revert bundled transactions ([File: precompiles/addr/addr.go])

### Summary
The `addr` precompile's `associate()` and `associatePubKey()` methods perform a one-time, signature-authenticated state mutation (EVM↔Sei address association) and unconditionally revert if the target address is already associated. Because the signature (`v`, `r`, `s`) and message used by `associate()` are carried in plaintext transaction calldata, any third party can observe a pending transaction that calls `associate()` (directly or as one leg of a larger contract call, e.g. a batched/sponsored call) and front-run it by calling `addr.associate()`/`addr.associatePubKey()` themselves with the same, already-public signature. This performs the association first, so when the original transaction's call to `associate()` executes, it hits the "already associated" guard and reverts, forcing the whole enclosing transaction (and any gas paid for it) to fail — the same bug class as `PermitSubmitterHook` being front-run with a replayed `permit()` call.

This function is reached by both `associate()` and `associatePublicKey()`: [2](#0-1) 

The precompile's `Execute` dispatch does not restrict who can call `associate`/`associatePubKey` — any EOA or contract can invoke it with arbitrary `(v, r, s, customMessage)`, since the target address is derived from the signature itself, not from `msg.sender`: [3](#0-2) 

Because the signature and message are plain calldata arguments (not secret), once a transaction that calls `associate()`/`associatePubKey()` is broadcast (e.g. as part of a larger contract flow such as an onboarding/batched-call/sponsored transaction, similar in spirit to `contracts/src/BatchCallAndSponsor.sol`), anyone observing the mempool can extract `(v, r, s, customMessage)` and submit their own `associate()` call with a higher gas price to land first. This is functionally identical to front-running an ERC-20 `permit()` signature: the signature is single-use, and reusing it early causes the legitimate, later-arriving call to fail because the guarded state ("already associated") has changed.

This same front-running risk against association was explicitly identified and mitigated for EIP-7702 `SetCode` authorities in the ante-handler pre-association logic, whose comment states the exact concern: replaying a publicly-visible signature to force-associate an address before the original transaction lands. [4](#0-3) 

However, that mitigation only covers the ante-handler's implicit pre-association of `SetCode` authorities; it does not protect explicit, in-contract calls to the `addr` precompile's `associate`/`associatePubKey`, which remain vulnerable to the same front-running-induced revert.

### Impact Explanation
Any transaction that bundles an `associate()`/`associatePubKey()` call together with other logic (e.g., an onboarding flow, a sponsor/relayer-submitted meta-transaction, or a multi-step contract interaction that associates the caller's address as a precondition for further operations) can be forced to revert in its entirety by a third party who extracts the public signature from the pending transaction and submits it first. This wastes the gas fee paid by the legitimate submitter/sponsor and can repeatedly block completion of any workflow that depends on atomically associating an address within a larger transaction, since the attacker can repeat this griefing on every retry.

### Likelihood Explanation
The attack requires no privileged access — only mempool visibility of a pending transaction (or bundle) containing a call to `associate`/`associatePubKey`, which any public RPC client or contract deployer could construct. The signature parameters are necessarily public calldata, so extracting and replaying them is trivial and requires no cryptographic breakage. Likelihood is contingent on the existence of a bundling caller (a contract or sponsor flow that calls `associate()` as one step among others), which is a realistic and encouraged usage pattern (association is meant to be composed with account onboarding).

### Recommendation
Make `associate`/`associatePubKey` idempotent/no-op (rather than reverting) when the target address is already associated with the *same* EVM↔Sei pair that the signature would produce, returning success in that case instead of erroring. Alternatively, expose a "try-associate" variant, or document/require that callers precede the association call with an on-chain `getSeiAddr`/`getEvmAddr` existence check wrapped in a way that does not abort the encompassing transaction, mirroring the recommended try/catch wrapping pattern from the analogous `PermitSubmitterHook` report.

### Proof of Concept
1. Contract `Onboard` (or a sponsored/batched-call contract) calls `addr.associate(v, r, s, customMessage)` as step 1, then performs step 2 (e.g., an airdrop claim) in the same transaction.
2. User Alice signs the association message and submits a transaction calling `Onboard.completeOnboarding(v, r, s, customMessage, ...)`; this transaction sits in the mempool with `v, r, s, customMessage` visible.
3. Attacker Bob extracts `(v, r, s, customMessage)` from Alice's pending transaction and submits his own transaction calling `addr.associate(v, r, s, customMessage)` directly with higher priority fee, landing first.
4. Alice's EVM address becomes associated with her Sei address as a side effect of Bob's transaction.
5. Alice's original transaction executes; `PrecompileExecutor.associateAddresses` (`precompiles/addr/addr.go:239-244`) finds the address already associated and returns `fmt.Errorf("address %s is already associated with evm address %s", ...)`, reverting `Onboard.completeOnboarding` and consuming Alice's (or the sponsor's) gas without completing step 2.

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)

// associateAuthorizationAuthorities associates every EIP-7702 authorization authority in
// the transaction with its true (pubkey-derived) Sei address, so that a subsequent
// SetCode for the authority does not create a mutable direct-cast mapping. It is
// best-effort: authorities with invalid signatures (which EVM execution would also skip)
// or that are already associated are left untouched, and an association failure skips
// only that authority rather than rejecting the transaction, which go-ethereum would
// still accept.
func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
