## Analog Found

### Title
Missing validation that a CAT's `driver_dict` entry actually matches its declared `asset_id` key allows offer summaries and settlement puzzles to diverge from the advertised asset - (File: `chia/wallet/trading/offer.py`)

### Summary
The Treasury.sol bug arises because `invest()` trusts a caller-supplied `collateralIndex` without checking that the `collateralToken` it resolves to is actually the token the target strategy expects, corrupting PnL accounting. The Chia analog is in `chia/wallet/trading/offer.py`: an `Offer` object stores a `requested_payments` dict keyed by `asset_id` and a separate, caller-controlled `driver_dict: dict[bytes32, PuzzleInfo]` that is used to *reconstruct* the actual settlement puzzle for that `asset_id`. Nothing validates that `create_asset_id(driver_dict[asset_id]) == asset_id`, so a maker can advertise one asset identity while the driver info that actually drives settlement construction describes a different asset entirely.

### Finding Description
`Offer.__post_init__` only checks that every non-`None` key of `requested_payments` is *present* in `driver_dict`, never that the driver's own derived identity matches the key it is stored under: [1](#0-0) 

That same untrusted `driver_dict[asset_id]` is what actually builds the settlement puzzle hash used for announcements, valid-spend construction, and the dummy "requested payment" `CoinSpend`s: [2](#0-1) [3](#0-2) [4](#0-3) 

The only place a mismatch is ever caught is in `TradeManager._create_offer_for_ids`, and only for the side of the trade where a party is *sending* an asset from a wallet they locally own (their own `get_puzzle_info` result is compared to the supplied `driver_dict[asset_id]`): [5](#0-4) 

Critically, that check is gated behind `if asset_id is not None and wallet is not None`. When the asset in question is one that is *requested* (the `amount > 0` branch) and the resolving wallet lookup returns `None` (asset unknown/no local wallet — common for `wallet_rpc_api.create_offer_for_ids`, which passes a caller-supplied `driver_dict` straight through with no validation), the corresponding-identity check is skipped entirely: [6](#0-5) [7](#0-6) 

This is the direct analog of the reported bug: just as Treasury.sol's `invest()` accepts a `collateralIndex` without confirming `collateral[collateralIndex].collateralToken` is what the target strategy actually expects, Chia's offer machinery accepts an `asset_id` key without confirming the paired `driver_dict[asset_id]` actually resolves (via `create_asset_id`) back to that same `asset_id`.

### Impact Explanation
`Offer.summary()` (used by wallet RPC `get_offer_summary` and shown to users/counterparties) reports amounts keyed purely by the declared `asset_id`, while `to_valid_spend()`/`to_spend_bundle()` construct the real settlement puzzle from the mismatched `driver_dict` entry. A counterparty inspecting an offer sees one asset identity but the actual on-chain settlement puzzle (and thus which CAT/asset is truly moved) is derived from a different, attacker-chosen driver. This is a coin-identity/asset-identity mismatch that produces incorrect accounting of what is being offered/requested and can mislead a human or automated counterparty into completing a trade for a different asset than advertised — a direct parallel to the reported "incorrect PnL reporting... loss of user or protocol funds."

### Likelihood Explanation
Any unprivileged offer maker/counterparty can construct or accept an `Offer`/call `create_offer_for_ids` supplying an arbitrary `driver_dict`; the vulnerable path is reachable purely through offer creation/summary/response logic with no special privileges, and the only safety net (`trade_manager.py` lines 570–585) is bypassed whenever the resolving wallet for the requested asset is `None`.

### Recommendation
Add an explicit check in `Offer.__post_init__` (and/or in `TradeManager._create_offer_for_ids` for the requested/`amount > 0` branch) that `create_asset_id(driver_dict[asset_id]) == asset_id` for every asset id in `requested_payments`/`driver_dict`, rejecting the offer if the driver's derived identity does not match its declared key.

### Proof of Concept
1. Craft `requested_payments = {asset_id_A: [...]}` where `asset_id_A` is a well-known/trusted CAT asset id.
2. Set `driver_dict[asset_id_A] = PuzzleInfo(...)` describing a different TAIL (`asset_id_B`, e.g. an attacker-controlled shell CAT).
3. Call `wallet_rpc_api.create_offer_for_ids` with this `offer_spec`/`driver_dict` (path shown at `chia/wallet/wallet_rpc_api.py:1958-1976`) — no validation rejects the mismatch.
4. `Offer.__post_init__` accepts it (`chia/wallet/trading/offer.py:157-160`), and `offer.summary()` reports `asset_id_A`'s hex to any viewer, while `to_valid_spend`/`to_spend_bundle` (lines 565-623) build the actual settlement puzzle using `driver_dict[asset_id_A]`, i.e., `asset_id_B`'s outer puzzle — a taker relying on the displayed summary is settling against a different asset than shown.
