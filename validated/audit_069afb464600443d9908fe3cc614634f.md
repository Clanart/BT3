### Title
Unrestricted `CallDispatcher.dispatch()` allows permanent ERC1820 hook poisoning of the shared dispatcher, enabling persistent DoS/griefing of all IntentGatewayV2 and HyperFungibleToken calldata flows - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` is a public, permissionless entry point with no caller restriction. It executes arbitrary calls with the `CallDispatcher` contract itself as `msg.sender`. Because `CallDispatcher` is a single shared singleton reused by every `IntentGatewayV2` order's predispatch/postdispatch calldata and by `HyperFungibleToken`'s calldata execution, an attacker can call it directly (bypassing any order at all) to make the dispatcher register itself with the ERC1820 registry as its own `ERC777TokensRecipient`/`ERC777TokensSender` implementer, pointing to an attacker-controlled contract. This mirrors the exact primitive from the external report (an unrestricted "Executor" that lets anyone make it call `ERC1820Registry.setInterfaceImplementer`), except here the poisoned entity is a chain-wide shared infrastructure contract used by all users, not a single relayer-controlled contract.

### Finding Description
`CallDispatcher.dispatch()`:
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [1](#0-0) 

has no access-control modifier restricting the caller to `IntentGatewayV2` or `HyperFungibleToken` — any EOA can call it directly. The only guard is that `call.to` must have code (`NotContract`).

`IntentGatewayV2`/`IntentsBase` and `HyperFungibleTokenUpgradeable` all invoke this exact same, singleton dispatcher address (`_params.dispatcher` / `_dispatcher`) for predispatch swaps, postdispatch execution and dust sweeping, and cross-chain calldata execution respectively: [2](#0-1) [3](#0-2) 

Because `dispatch()` performs a low-level `.call` from the dispatcher's own address, `msg.sender == account` holds true when the dispatcher calls `ERC1820Registry.setInterfaceImplementer(address(0), interfaceHash, implementer)`. ERC1820 permits an account to set its own interface implementer without any additional authorization. An attacker therefore crafts:
```
Call[] calls = [Call({
  to: 0x1820a4B7618BdE71Dce8cdc73aAB6C95905faD24, // ERC1820Registry (mainnet)
  value: 0,
  data: setInterfaceImplementer(address(0), keccak256("ERC777TokensRecipient"), attackerHook)
})];
CallDispatcher(dispatcher).dispatch(abi.encode(calls));
```
This call succeeds with no privilege check, since the target (ERC1820Registry) is a contract and the call itself does not touch any protocol state protected by `nonReentrant` or ownership checks — it is entirely outside `IntentGatewayV2`/`HyperFungibleTokenUpgradeable`.

Once registered, the poisoning is **persistent state in a canonical, externally-deployed registry**, independent of any single order or transaction. From then on, every ERC777-class token transfer into or out of the dispatcher — triggered by any other, unrelated user's `placeOrder` predispatch swap, any solver's postdispatch fill, or any dust sweep-back in `_execute`/`IntentGatewayV2.placeOrder` predispatch flow (`evm/tron/contracts/apps/IntentGatewayV2.sol:407-443`), and any `HyperFungibleTokenUpgradeable.onAccept` calldata execution — invokes the attacker's hook. The attacker can then unconditionally revert, DoS-ing that fill/order/transfer, or attempt to reenter the flow during the hook window.

### Impact Explanation
This breaks the core invariant "bridged assets, order escrow, refunds, ... must move exactly once and only to the rightful beneficiary," because a single unprivileged, one-time transaction from any attacker permanently corrupts a piece of shared cross-protocol infrastructure (`CallDispatcher`) that every user's intent order and every `HyperFungibleToken` calldata-bearing cross-chain transfer relies on. Unlike the "generic gas/network DoS" the report explicitly asks to discard, this is not per-transaction griefing — it's a **stateful, persistent poisoning of a shared singleton contract** reachable by an unprivileged actor with no relayer, prover, or admin assumption, causing repeatable denial of settlement/fill for any ERC777-compatible token routed through predispatch/postdispatch calldata or HFT calldata execution on that chain, until governance redeploys/reconfigures the dispatcher. It can also open a reentrancy window (the ERC777 hook fires mid-transfer) during the dust-sweep or predispatch asset transfer steps that touch `CallDispatcher`'s balance, which is a novel attack surface never exercised by the CEI fix already applied to `IntentGatewayV2`'s own fill paths (that fix only protects the `_filled` mapping inside `fillOrder`, not the dispatcher's arbitrary-call surface).

### Likelihood Explanation
High. `CallDispatcher.dispatch()` is `external` with zero access control, callable directly by any address without needing to go through `IntentGatewayV2` or `HyperFungibleToken` at all. Registering an ERC1820 implementer is a single, cheap mainnet transaction. The attack requires no relayer, prover, admin, or governance actor — a pure unprivileged EOA can execute it once and then passively wait for any legitimate user to route an ERC777-class token through the shared dispatcher.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to be callable only by the registered `IntentGatewayV2`/`HyperFungibleToken` contract(s) that own it (access-controlled caller allowlist), or deploy a fresh, single-use dispatcher instance per call/order instead of a shared singleton.
- Alternatively/additionally, explicitly block calls whose target is the well-known ERC1820 registry address, or disallow calls where `call.data` matches `setInterfaceImplementer`/`setManager` selectors.
- Ensure the CEI pattern used to guard `_filled` in `IntentGatewayV2` is paired with reentrancy protection around any external call sequence that involves `CallDispatcher` balances (predispatch, postdispatch sweep, HFT calldata execution).

### Proof of Concept
1. Attacker (no special role) calls, directly on-chain:
```solidity
Call[] memory calls = new Call[](1);
calls[0] = Call({
    to: 0x1820a4B7618BdE71Dce8cdc73aAB6C95905faD24,
    value: 0,
    data: abi.encodeWithSignature(
        "setInterfaceImplementer(address,bytes32,address)",
        address(0),
        keccak256("ERC777TokensRecipient"),
        address(attackerHookContract)
    )
});
CallDispatcher(dispatcherAddress).dispatch(abi.encode(calls));
```
This succeeds because `msg.sender` as seen by `ERC1820Registry` is `dispatcherAddress` itself (self-registration is always allowed), and `dispatch()` has no caller restriction.
2. Later, an unrelated user places an `IntentGatewayV2` order whose `predispatch.assets` or `output.assets` include an ERC777-compatible token, or bridges such a token via `HyperFungibleTokenUpgradeable` with non-empty `data`.
3. When that token is transferred to/from `dispatcherAddress` (predispatch escrow transfer, postdispatch sweep in `_execute`, or HFT `onAccept` mint+dispatch), the ERC777 hook on `attackerHookContract` fires.
4. `attackerHookContract` reverts unconditionally, causing `CallFailed`/`InvalidInput` reverts on the entire legitimate order/transfer — repeatable indefinitely for any future ERC777-token flow through the shared dispatcher, with no way for victims to opt out short of governance intervention.
