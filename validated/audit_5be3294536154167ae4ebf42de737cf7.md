### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo()` causes stack-overflow crash when parsing attacker-controlled coin memos - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
`PuzzleWithRestrictions.from_memo()` recursively parses an on-chain `MofN` custody memo structure with no depth limit. A malicious coin creator can memo a `CREATE_COIN` condition with a deeply/self-referentially branching `MofN` hint, which any wallet, PlotNFT, or Data Layer client syncing that coin will parse via unbounded Python recursion, crashing the client process — the same bug class as CVE-2026-9740 (uncontrolled recursion in nested-structure validation causing a pre-auth crash).

### Finding Description
`PuzzleWithRestrictions.from_memo()` reconstructs custody puzzle trees from a `Program` memo attached to a `CREATE_COIN` condition: [1](#0-0) 

When the memo indicates `further_branching` (an `MofN` node), the method recurses once per member with **no depth or size limit**:
```python
if further_branching:
    m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
    puzzle: MIPSComponent = MofN(
        m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
    )
```
The wiki-level test documentation explicitly acknowledges this design: "`from_memo()` must reconstruct unknown members/restrictions, including recursive `MofN`" [2](#0-1) . Unlike `sha256_treehash()`, which was deliberately rewritten as an iterative stack machine specifically "to avoid Python recursion limits on deeply nested CLVM" [3](#0-2) , `from_memo()` has no such protection — it is plain Python recursion bound only by `sys.getrecursionlimit()` (~1000).

This memo is fully attacker-controlled: it comes from the `memo_blob` of a `CREATE_COIN` condition output by any spend. The `PlotNFT` wallet sync path feeds it directly into `from_memo()`: [4](#0-3) 
Only `ValueError` is caught around this call; `RecursionError` (a `RuntimeError` subclass) is not caught and will propagate, aborting the sync task/process. The same `from_memo()` API is the documented mechanism any custody-architecture wallet uses "to sync an unknown inner puzzle from on chain" [5](#0-4) .

### Impact Explanation
Any unprivileged participant can create a coin (e.g. as a plotnft/custody-architecture pool member, or simply an arbitrary spend with a crafted `CREATE_COIN` memo) whose memo, when synced by a PlotNFT/custody wallet client, triggers deep Python recursion via `MofN` nesting and raises an uncaught `RecursionError`. This halts wallet-side transaction/coin-spend processing for that client (a spend-triggered processing halt / DoS against the syncing wallet or pool-tracking process), matching the accepted impact class of "spend-triggered transaction-processing halt."

### Likelihood Explanation
The attack requires only crafting a `Program` memo with many nested `MofN` hints (no signature or special permission required to place a memo on a `CREATE_COIN` output) and getting a victim wallet/plotnft client to sync the coin — a normal, expected part of wallet operation. This is straightforward to construct offline; the recursion depth needed to exceed Python's default limit (~1000) is easily reachable with a memo blob well under typical size limits.

### Recommendation
Bound the recursion depth explicitly (raise a controlled error, e.g. `ValueError`, once a maximum nesting depth is exceeded) or rewrite `from_memo()` as an iterative/stack-based parser analogous to `sha256_treehash()`. Additionally, callers such as `PlotNFT.get_next_from_coin_spend()` should catch `RecursionError`/`RuntimeError` alongside `ValueError` so malformed memos fail gracefully instead of crashing the sync task.

### Proof of Concept
1. Construct a `Program` memo of the form `(CHIP-0043, [nonce, [], 1, [M, [child_memo, ...]]])` where each `child_memo` is itself another such nested `MofN` memo, recursively, to a depth of ~2000+ levels (each level only needs one member so `m=1`).
2. Attach this nested memo as the `memo_blob` on a `CREATE_COIN` condition output by a coin spend (this requires no privileged access — any coin owner can add arbitrary memo data).
3. Have a PlotNFT/custody-architecture wallet client observe/sync that coin, causing `PlotNFT.get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo()` to recurse past Python's stack limit, raising an uncaught `RecursionError` that aborts wallet sync processing.
