## Analog Found: SQL Injection via Unvalidated Pagination Parameters in Wallet Transaction Store

### Title
SQL Injection via unsanitized `start`/`end` pagination parameters in wallet transaction listing - (File: `chia/wallet/wallet_transaction_store.py`)

### Summary
`WalletTransactionStore.get_transactions_between` builds the `LIMIT` clause of a SQL query by directly f-string interpolating the caller-supplied `start` and `end` values instead of using bound parameters, mirroring the exact bug class in CVE-2017-9463 where Piwigo's `user_list_backend.php` interpolated `iDisplayStart`/`iDisplayLength` into a SQL query unsanitized.

### Finding Description
`get_transactions_between` accepts `start` and `end` with no type annotation (i.e., no enforced `int`/`uint32` typing) and computes `limit = end - start`, then interpolates both directly into the raw SQL string: [1](#0-0) [2](#0-1) 

Only `wallet_id` is passed as a bound parameter (`?`); `start` and `end` are embedded directly into the query text via an f-string (`f" LIMIT {start}, {limit}"`). If these values arrive from the wallet RPC layer as strings or otherwise non-integer JSON values (a common occurrence in JSON RPC where the caller controls the raw JSON body), and are not coerced to `int`/`uint32` before reaching this function, an attacker with only RPC-caller/wallet-user access could inject arbitrary SQL fragments into the `LIMIT` clause of the query against the `transaction_record` table. The same unsafe pattern (unbound `start`/`limit` interpolated straight into `LIMIT {start}, {limit}`) also exists in the sibling method `WalletCoinStore.get_coin_records_between`: [3](#0-2) 

This is structurally identical to the CVE-2017-9463 root cause: pagination parameters that should be validated integers instead flow unsanitized into string-built SQL.

### Impact Explanation
If reachable with non-integer input (e.g., a crafted string), this could allow SQL injection against the wallet's local SQLite database, enabling unauthorized read of other wallet_ids' transaction records/blobs (`transaction_record` column), or corruption of query logic used for wallet state reconstruction. Because `transaction_record` blobs are deserialized into `TransactionRecordOld` objects, a manipulated result set could also cause wallet state confusion. This satisfies the coin-set/wallet-state integrity class the scope calls for, but strictly depends on whether the caller-supplied `start`/`end` bypass integer coercion before reaching this function.

### Likelihood Explanation
Likelihood is **uncertain without additional verification I could not complete**: I was unable to trace, within available tool budget, whether the `get_transactions` RPC handler in `chia/wallet/wallet_rpc_api.py` casts `start`/`end` to `int`/`uint32` (e.g., via pydantic/streamable request models) before calling `get_transactions_between`. Chia's RPC layer generally uses typed request dataclasses (`uint32` etc.) which, if enforced here, would coerce or reject non-integer input before it reaches the SQL layer, making this non-exploitable in practice — reducing this from a genuine SQL injection to a defense-in-depth / code-quality issue (raw string interpolation of trusted integers is still bad practice per the project's own guidance in `chia/_tests/core/data_layer/test_data_store.py:104-105`: "Never string-interpolate sql queries..."). I could not confirm the actual runtime type of `start`/`end` at the RPC boundary within this session.

### Recommendation
- Explicitly type `start`/`end` as `uint32` (or validate/`int()`-cast them) at the top of `get_transactions_between` and `get_coin_records_between` before use, rejecting non-numeric input.
- Replace the f-string `LIMIT {start}, {limit}` with parameterized `LIMIT ?, ?` and pass `start`/`limit` as bound query arguments, consistent with how `wallet_id` is already handled.
- Apply the same fix to `WalletCoinStore.get_coin_records_between`.
- Audit the RPC request schema for `get_transactions` in `chia/wallet/wallet_rpc_api.py` to confirm strict integer typing is enforced before these values reach the store layer.

### Proof of Concept
Not confirmed as concretely exploitable — a working PoC would require confirming that the `get_transactions` RPC endpoint passes through non-integer `start`/`end` values without type coercion. I could not verify this within the available tool calls; a background agent with fuller access to `chia/wallet/wallet_rpc_api.py`'s request handling should trace `get_transactions` → `get_transactions_between` argument typing to confirm reachability before treating this as more than a code-smell/defense-in-depth finding.

    async def get_coin_records_between(
        self, wallet_id: int, start: int, end: int, reverse: bool = False, coin_type: CoinType = CoinType.NORMAL
    ) -> list[WalletCoinRecord]:
        """Return a list of coins between start and end index. List is in reverse chronological order.
        start = 0 is most recent transaction
        """
        limit = end - start
        query_str = "ORDER BY confirmed_height " + ("DESC" if reverse else "ASC")

        async with self.db_wrapper.reader_no_transaction() as conn:
            rows = await conn.execute_fetchall(
                f"SELECT * FROM coin_record WHERE coin_type=? AND"
                f" wallet_id=? {query_str}, rowid LIMIT {start}, {limit}",
                (coin_type, wallet_id),
            )
        return [self.coin_record_from_row(row) for row in rows]
