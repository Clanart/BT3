### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` keys allows stack-exhaustion DoS from a single crafted transaction - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
The CVE describes Exim's BDAT handling causing unbounded, attacker-controlled recursion during protocol input parsing (`getc`), leading to stack exhaustion. The equivalent bug-class pattern — recursion depth driven directly by attacker-supplied, unbounded input structure with no depth cap during decoding — exists in Kaia's `AccountKeyRoleBased.DecodeRLP`, which is reachable from any account-update transaction submitted by an unprivileged sender before any composite-type validation is performed.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of raw byte strings and then, for each entry, calls `rlp.DecodeBytes` into a fresh `AccountKeySerializer`, whose `DecodeRLP` dispatches back into `NewAccountKey`/`s.Decode(serializer.key)` based on the encoded `keyType` byte: [1](#0-0) 

If the encoded `keyType` of an entry is again `AccountKeyTypeRoleBased`, this recurses into `AccountKeyRoleBased.DecodeRLP` again — a pure Go call-stack recursion with no depth limiter — via `AccountKeySerializer.DecodeRLP`: [2](#0-1) 

Crucially, this recursive decoding happens purely at the RLP-decode stage (during `TxInternalDataAccountCreation.DecodeRLP` / `TxInternalDataAccountUpdate`'s serializer path, which is invoked whenever a raw transaction is decoded off the wire or via `SendRawTransaction`): [3](#0-2) 

The only defense against nested `RoleBased` keys — `IsCompositeType()` / `ErrNestedCompositeType` — is enforced in `CheckInstallable`/`CheckUpdatable`, which runs *after* successful decoding, not during it: [4](#0-3) 

Because each nesting level only costs a few bytes of RLP overhead (an outer list header + one inner byte-string header + a 1-byte key type tag), an attacker can encode tens of thousands of nesting levels within a single transaction payload well under typical transaction/network size limits. Since decoding recurses through several Go stack frames per level (`AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` → `Stream.Decode` → `AccountKeySerializer.DecodeRLP` → back into `AccountKeyRoleBased.DecodeRLP`), sufficient nesting depth can exhaust the goroutine stack and crash the node process with a fatal, unrecoverable Go runtime stack-overflow error — before any transaction-level semantic/composite-type validation is ever reached.

### Impact Explanation
A crafted `TxTypeAccountUpdate` (or `TxTypeFeeDelegatedAccountUpdate`/its variants) transaction containing a deeply, self-nested `AccountKeyRoleBased` payload can be submitted by any unprivileged sender via public RPC (`eth_sendRawTransaction`) or gossiped over p2p. Decoding this transaction (which every full node performs, including mempool admission and block processing) triggers unbounded recursive decoding that can exhaust the goroutine stack, causing a Go runtime fatal error and crashing the node. Because this is a decode-time bug reachable identically by every node that receives/relays the transaction, a single malicious transaction can potentially crash multiple nodes on the network simultaneously (denial of service), satisfying the "state divergence between honest nodes" / node-crash criteria for network-wide impact.

### Likelihood Explanation
Likelihood is high: crafting the malicious RLP payload requires no special privileges, no valid signature verification is needed before decoding occurs (decoding happens prior to sender/signature checks), and the payload size needed to reach dangerous recursion depth is small and well within standard transaction size constraints. The only mitigating factor is that Go's dynamically growing goroutine stacks (up to ~1 GB by default) mean the required nesting depth is nontrivial, but no code path bounds it, and RLP overhead per level is minimal (~4–6 bytes), making deep nesting cheap to construct.

### Recommendation
Add an explicit recursion-depth (or composite-nesting) limit to `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` that is enforced at decode time (not only in the later `CheckInstallable`/`CheckUpdatable` semantic checks), rejecting any account key whose nesting depth exceeds a small constant (e.g., 1, since Kaia's semantics already disallow nested RoleBased keys). Alternatively, thread a depth counter through the RLP decode path for `AccountKey` and return an error once a maximum depth (e.g., 2–3) is exceeded, mirroring the eventual `IsCompositeType` restriction but applied before the recursive call is made rather than after the object is constructed.

### Proof of Concept
Conceptually: construct RLP bytes representing an `AccountKeySerializer` whose `keyType == AccountKeyTypeRoleBased`, whose payload is `[][]byte` with a single entry that is itself the RLP-encoding of another `AccountKeySerializer` with `keyType == AccountKeyTypeRoleBased`, and repeat this nesting N times (N in the tens of thousands). Embed this payload as the `Key` field of a `TxTypeAccountUpdate` transaction and submit it via `eth_sendRawTransaction` or over p2p transaction gossip. When any node calls `rlp.DecodeBytes`/`Stream.Decode` on the transaction (`TxInternalDataAccountCreation.DecodeRLP` / update variant → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP`, repeated N times), the recursive call chain grows until the goroutine stack limit is reached, crashing the process with a Go runtime `fatal error: stack overflow` before any `ErrNestedCompositeType` check is ever reached.

*Note: I was unable to directly determine the exact maximum transaction/payload size constant (`ErrOversizedData`/`txMaxSize`) enforced in `blockchain/tx_pool.go`/`blockchain/error.go` from the index, so exact minimum nesting depth vs. size-limit feasibility could not be fully confirmed with certainty — a Devin session with full repository access would be needed to compute the precise size-vs-depth feasibility and validate the PoC end-to-end.*

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
