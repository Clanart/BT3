### Title
`EvmHost.dispatch()`/`fundRequest()` swap excess native-token change to the Host instead of the caller, permanently trapping user overpayment - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch()` and `EvmHost.fundRequest()` let a caller pay for cross-chain message fees with native token by routing it through `IUniswapV2Router02.swapETHForExactTokens`. This router call is made with `to = address(this)` (the Host contract) as the refund/output recipient, not the original `msg.sender` of `dispatch()`/`fundRequest()`. Uniswap's `swapETHForExactTokens` refunds any unused ETH to whoever calls the router — which here is the Host, not the end user — so any native token sent above the amount actually needed to buy `post.fee` (or `amount`) units of `feeToken()` is silently absorbed by the Host contract rather than returned to the sender.

### Finding Description
`dispatch()`: [1](#0-0) 

and `fundRequest()`: [2](#0-1) 

both call `swapETHForExactTokens{value: msg.value}(feeAmount, path, address(this), block.timestamp)`. Per the standard UniswapV2Router02 implementation, this function computes `amounts[0] = getAmountsIn(feeAmount)`, requires `amounts[0] <= msg.value`, and then does `if (msg.value > amounts[0]) TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])`. The `msg.sender` seen by the router is the calling contract — `EvmHost` itself — because `EvmHost` is the one invoking the router. As a result:

- Any native token the user sends beyond the exact amount required to purchase `feeAmount` of `feeToken()` is refunded to the Host contract, not back to the original caller.
- There is no code path in `dispatch()` or `fundRequest()` that forwards this refunded dust back to `_msgSender()`.
- The documentation itself confirms callers are expected to estimate a native-token amount to send (`quote()` via `getAmountsIn`) and that this quote is inherently imprecise and sandwich-attack prone: "Use the `quote()` view function from your frontend to estimate how much native token users need to send... It uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks."

This is the same broken invariant as the external report: an on-chain swap used to size a bridge fee payment has no return path for the unspent input, so any imprecision between the off-chain quoted amount and the on-chain executed amount (from block movement, sandwiching, or simply passing a generous `msg.value`) converts directly into permanent loss for the caller of `dispatch`/`fundRequest`, rather than an overcharge that at least stays escrowed for the sender's request.

### Impact Explanation
Any unprivileged user calling `dispatch()` or `fundRequest()` with native token loses the entire delta between `msg.value` and the exact wei consumed by the swap — this ETH is not credited to their request's fee metadata, not returned to them, and not recoverable through any user-facing function. Given the documented sandwich-attack exposure of the `quote()` helper, and the reality that users must send `msg.value` conservatively higher than the live-quoted amount to avoid the transaction reverting on price movement, real loss of user funds is expected on essentially every native-token dispatch. This satisfies the "stealing or loss of funds" impact class in the bounty scope.

### Likelihood Explanation
High. This code path is on the primary, unprivileged, public entry point (`dispatch`) used by any `HyperApp` integrator paying with native token per the documented "Native Token Payment" flow, and by anyone calling `fundRequest` to top up a request fee. No malicious relayer, prover, or governance actor is required — it triggers purely from normal usage combined with the unavoidable quote/execution price gap inherent to `getAmountsIn`-based estimation.

### Recommendation
Do not set the swap recipient/refund target to `address(this)`. Either:
1. Call `swapETHForExactTokens` with `to = address(this)` for the output tokens but wrap the router call so any leftover `msg.value` refunded to the Host is forwarded back to `_msgSender()` in the same transaction, or
2. Use a router pattern where the Host is not itself `msg.sender` to the router (e.g., call via a minimal proxy/relay that is the effective `msg.sender`) and forward dust back, or
3. Simplest fix: after the swap call, check `address(this).balance` delta and transfer any residual native token back to `_msgSender()` before returning from `dispatch`/`fundRequest`.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` requires only `0.9 ether` worth of native token at current pool price (per `getAmountsIn`).
2. `swapETHForExactTokens{value: 1 ether}(post.fee, [WETH, feeToken], address(this), deadline)` executes: consumes `0.9 ether`, and refunds `0.1 ether` to `msg.sender` of the router call, which is `EvmHost` (`address(this)`), not the original caller. [1](#0-0) 
3. The `0.1 ether` now sits in the Host contract's native balance; `dispatch()` returns normally with a valid `commitment`, giving no indication funds were lost.
4. There is no subsequent line in `dispatch()` that inspects the Host's native balance or forwards anything back to `_msgSender()`; the same pattern repeats identically in `fundRequest()`. [2](#0-1) 
5. Over repeated calls this ETH accumulates in the Host contract with no user-facing recovery mechanism, confirming permanent loss of the overpaid amount for every caller who does not send the exact wei amount required by the live pool price.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(

            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
