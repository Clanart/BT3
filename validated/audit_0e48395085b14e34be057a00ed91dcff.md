### Title
Malformed on-chain preprocess poisons persisted signing state, causing a permanent panic in `DkgConfirmer::complete` — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The coordinator's MuSig-based DKG-confirmation signing protocol keeps no in-memory state: it persists a seeded `CachedPreprocess` in the DB and re-executes the whole protocol from finalized tributary data. A malformed preprocess published by any validator is accumulated into `DataDb` (it is only length/commitment-checked at `read_preprocess` time, not at accumulation). `DkgConfirmer::share` then fails with `Err(InvalidParticipant)`, but the poisoned data remains finalized in the DB. When the protocol proceeds to `DkgConfirmer::complete`, it re-runs `share_internal` over the same poisoned data and hits `.expect("trying to complete a machine which failed to preprocess")`, panicking the coordinator — deterministically, on every rebuild, since the state is re-derived from committed DB contents.

### Finding Description
The bug class of CVE-2025-70123 — improper input validation letting a malformed first message place the node in an inconsistent state where a subsequent valid request causes cascading failure — maps directly onto this two-phase re-execution design:

1. `accumulate` in `coordinator/src/tributary/handle.rs:90-167` writes signer data into `DataDb`/`DataReceived` unconditionally once the signer is a non-removed validator, without validating that the bytes parse as a `Preprocess` [1](#0-0) .
2. `DkgConfirmer::share` calls `share_internal`, which parses each preprocess via `machine.read_preprocess(...)` and returns `Err(Participant)` on malformed bytes [2](#0-1) . The bad data is *not* removed from `DataDb`; the `CachedPreprocesses` seed also remains stored [3](#0-2) .
3. `DkgConfirmer::complete` unconditionally re-executes `share_internal` on the same finalized preprocess set and `.expect(...)`s success [4](#0-3) . With the malformed preprocess still present, this panics.

Because the design intentionally re-derives all state from the DB ("Instead of maintaining state in memory, a combination of the DB and re-execution are used", lines 16-23), the crash is not transient: any rebuild replays the same finalized poisoned data and panics again. There is no path to skip or blame-and-exclude the malformed preprocess before `complete` is invoked, and `attempt` is fixed for a `DkgConfirmer` (context `(b"DkgConfirmer", self.attempt)`), so the panic recurs for the life of that attempt [5](#0-4) .

### Impact Explanation
A single validator-controlled malformed preprocess permanently halts DKG confirmation signing for the coordinator: `complete` panics instead of returning `Err(InvalidParticipant)` for blame. This is a denial of service against the validator-set key confirmation flow — the same "accepted malformed request → inconsistent persisted state → cascading failure on the next valid request" shape as the PFCP bug. Unwinding panics in the coordinator's block-handling path kill processing of the tributary block entirely.

### Likelihood Explanation
Reachable by any validator able to publish data to a `Topic::DkgConfirmation`/preprocess `DataSpecification` on the tributary (i.e., any non-removed validator submitting arbitrary bytes — no valid `Preprocess` structure is enforced at accumulation). `share` must have been attempted (or `complete` invoked directly on a set containing the malformed entry) for the panic to fire. Requires one malformed message plus normal protocol progression; no collusion or threshold control needed beyond holding a validator key.

### Recommendation
- In `DkgConfirmer::complete`, propagate the `Err(Participant)` from `share_internal` (return `Result`) instead of `.expect(...)`, mirroring `share`'s API, so malformed preprocesses yield blame rather than a panic [6](#0-5) .
- Preferably, validate preprocess bytes at accumulation time (run `read_preprocess` before `DataDb::set`) so malformed entries are never finalized into the re-executed state.
- Audit the same pattern elsewhere: `share_internal` is also re-run between `share` and `complete`, so any divergence in inputs between the two calls (e.g., differing `key_pair`) also reuses the same cached nonce seed — a second reason to make state advancement explicit rather than re-executed.

### Proof of Concept
Conceptual, driven by the code paths above:

1. Validator `V` participates in DKG confirmation for `attempt = A`. Instead of a valid serialized `Preprocess`, `V` publishes `vec![0xde, 0xad]` under the preprocess `DataSpecification`. `accumulate` stores it in `DataDb` without parsing [7](#0-6) .
2. Once `t` preprocesses accumulate, the coordinator calls `DkgConfirmer::share` → `share_internal` → `machine.read_preprocess(&mut [0xde, 0xad])` fails → returns `Err(V)`. The bytes remain in `DataDb` [8](#0-7) .
3. When shares arrive and `DkgConfirmer::complete(preprocesses, key_pair, shares)` is invoked, `share_internal` re-parses the identical finalized data, fails identically, and `expect("trying to complete a machine which failed to preprocess")` panics [6](#0-5) .
4. On restart, the coordinator reloads `DataDb`/`AttemptDb`, re-derives the same `DkgConfirmer` for attempt `A`, and panics again — a persistent, input-triggered crash loop with no blame path.
