Based on my investigation, this codebase has already patched most of the "obvious" analogs (clone-path traversal into `~/.ssh`, `IOpenRepositoryFromURLAction.filepath` traversal via `resolveWithin`, `sanitizeCloneName` for directory names). However, one place stands out as a genuine, still-present issue: `clone()` in `app/src/lib/git/clone.ts` unconditionally disables Git's built-in recursive-clone re-entrancy protection while cloning **untrusted, attacker-supplied remote URLs**.

### Title
Recursive Clone of Untrusted Remote Disables Git's Anti-RCE Guard via `GIT_CLONE_PROTECTION_ACTIVE=false` - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` builds the environment for every `git clone --recursive` invocation by unconditionally setting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` [1](#0-0) , regardless of whether the remote URL is a trusted first-party repository or an arbitrary, user-supplied/attacker-controlled URL reached via "Clone Repository," "Open in Desktop" deep links, or `--cli-clone`. `GIT_CLONE_PROTECTION_ACTIVE` is Git's internal safeguard that helps prevent the recursive-clone-of-a-hostile-submodule class of remote code execution (the same bug class as CVE-2024-32002), where a maliciously crafted repository/submodule tree — via case-insensitive filesystem collisions or symlinked `.git`/hook paths — can cause arbitrary files to be written into or executed from the real `.git` directory of the just-cloned repository during the recursive submodule checkout. Explicitly forcing this protection off for all clones, including ones of URLs the app itself cannot vouch for, re-opens the exact attack window Git's own fix was designed to close.

### Finding Description
The broken invariant: Git ships a defense specifically to stop hostile repository content (delivered via `git clone --recursive`) from escaping its intended checkout directory and writing/executing files elsewhere. Desktop's `clone()` function forwards the untrusted `url` argument straight into `git clone --recursive -- <url> <path>` [2](#0-1) , while simultaneously constructing an `env` object that always includes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` [1](#0-0) . There is no branch, allowlist, or trust check that limits this override to first-party/GitHub-owned remotes — every caller of `clone()`, including flows driven by the `open-repository-from-url` protocol action and CLI `--cli-clone` argument (both of which accept attacker/remote-controlled URLs) [3](#0-2) , inherits the same disabled protection.

This is the same shape of bug as the seed report: a value that should gate a sensitive downstream operation (`msg.value` gating whether native token transfer logic runs; here, a protection flag gating whether Git's submodule-recursion guard runs) is forced/forwarded unconditionally without checking the context (native-token-vs-not; trusted-vs-untrusted remote), letting attacker-supplied content reach a sink (`Executor.executeRoute`; here, Git's recursive submodule checkout) that has no independent access control of its own.

Notably, Desktop *does* apply defense-in-depth elsewhere for the same "attacker controls the clone target" scenario — `isClonePathSensitive()` blocks cloning into `~/.ssh`, `~/.gnupg`, `~/.config`, etc. [4](#0-3)  — showing the team is already aware that clone URLs/paths can be attacker-influenced, yet this awareness was not extended to the `GIT_CLONE_PROTECTION_ACTIVE` override.

### Impact Explanation
If exploitable in the bundled Git/dugite version, a malicious repository (shared as a plain clone URL, an "Open in Desktop" deep link with `openrepo`, or a GitHub API-returned `clone_url`) can trigger writes to or execution of content inside the real `.git` directory of the freshly cloned repository during the recursive submodule checkout, because the guard meant to prevent exactly that is disabled by Desktop itself. This can lead to arbitrary file write outside the intended checkout tree and, depending on the underlying Git bug class, code execution on the victim's machine — all triggered simply by cloning a repository the user does not control.

### Likelihood Explanation
Any of Desktop's "clone a URL I don't control" entry points reach this code path: manual "Clone repository" URL entry, the `x-github-client://openrepo/...` protocol handler (`parseAppURL` → `openRepositoryFromUrl` → `openOrCloneRepository`) [5](#0-4) , and `--cli-clone` [6](#0-5) . No local access, admin rights, or pre-existing malware is required — only that the victim clones or opens a link to a repository the attacker crafted. Because `GIT_CLONE_PROTECTION_ACTIVE` is unconditionally set to `'false'` for every single clone call with no code path that leaves it enabled, there is no existing guard in this codebase that mitigates it once a vulnerable Git version is present.

### Recommendation
Do not disable `GIT_CLONE_PROTECTION_ACTIVE` for clones of untrusted/user-supplied remotes. At minimum, remove the override so Git's default (protection enabled) applies, or scope any override to a narrow, justified, already-trusted internal use case with an explicit comment referencing why it's safe. If the override exists to work around an unrelated dugite/Git compatibility issue, gate it behind a check that only relaxes protection for remotes verified as first-party/trusted, never for arbitrary user-entered or deep-link-supplied URLs.

### Proof of Concept
1. Attacker crafts a repository containing a submodule structured to exploit the recursive-clone submodule vulnerability class that `GIT_CLONE_PROTECTION_ACTIVE` is designed to stop (e.g., a submodule path colliding with `.git` on case-insensitive filesystems, or a crafted nested repository layout).
2. Attacker shares either a plain HTTPS clone URL, or a GitHub Desktop deep link such as `x-github-client://openrepo/https://github.com/attacker/evil-repo`, or has it surfaced via `pullRequest.head.repo.clone_url` in the PR-checkout flow.
3. Victim clicks "Clone" in Desktop, or clicks the deep link (handled by `handleAppURL` → `parseAppURL` → `openRepositoryFromUrl`) [7](#0-6) .
4. `clone()` runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment [8](#0-7) , disabling Git's guard against the malicious submodule layout during recursive checkout, allowing the crafted repository content to escape the intended clone directory.

**Caveat**: I could not verify from this index alone which underlying Git/dugite version is bundled or whether it is still vulnerable to the specific `GIT_CLONE_PROTECTION_ACTIVE`-gated bug class, since that requires inspecting the vendored Git binary/version metadata, which is outside what the code index surfaces. I recommend confirming the bundled Git version's vulnerability status via a full Devin session before treating this as confirmed-exploitable, though the code-level anti-pattern (forwarding an unconditional protection-disable flag to a recursive clone of an untrusted URL) is clearly present and warrants remediation regardless.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
