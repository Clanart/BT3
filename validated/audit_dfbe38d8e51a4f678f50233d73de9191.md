### Title
Partial-commit staging trusts stale line-selection indices against a freshly re-fetched diff, silently committing/excluding wrong lines - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The reported Move bug is a classic "decrease without corresponding compensating action" defect: `amend_bid_order` mutates order size/remaining-size based on stale/previous state without validating that the accounting stays consistent, silently dropping value the user should have gotten back. The closest verifiable analog in GitHub Desktop is the partial-commit / discard-selection staging pipeline, where a `DiffSelection` (a set of absolute line indices) computed against one version of a file's diff is applied against a **second, independently re-fetched diff** without validating that the two diffs still line up. If the underlying diff shifts between the moment the user made their line selection and the moment Desktop re-diffs the file for staging, the index-based selection silently picks the wrong lines — analogous to the Move contract silently mutating state using indices/sizes that no longer match reality.

### Finding Description
`stageFiles` (`app/src/lib/git/update-index.ts:109-168`) calls `applyPatchToIndex` for every file with a partial `DiffSelection`. `applyPatchToIndex` (`app/src/lib/git/apply.ts`) does not reuse the diff that was shown to the user in the UI; it re-fetches a brand-new diff at commit time: [1](#0-0) 
and then builds the patch with `formatPatch(file, diff)`, where `file.selection` — the `DiffSelection` object holding absolute line indices chosen by the user against the *old* diff — is blindly reused against the *new* diff's hunks: [2](#0-1) 

The selection index is computed purely as `hunk.unifiedDiffStart + lineIndex` (an offset into the current hunk layout), with no correlation to the actual diff content that produced the selection. Desktop's own code acknowledges this exact class of problem elsewhere but only partially mitigates it: in `app-store.ts`, after reloading a diff, the code explicitly says it does *not* fully validate that previously selected lines still correspond to the same content, only that the line index is still "includeable": [3](#0-2) 

This "settle for less validation" comment is the direct textual analog of the Move report's missing-invariant-check: the system updates one piece of state (the diff/lines) without re-deriving the dependent piece of state (the selection) in a way that guarantees correctness, and no user-facing signal (refund/warning) is produced when the mismatch occurs.

`formatPatchToDiscardChanges` (used by "discard selected lines", `app/src/lib/patch-formatter.ts:251-335`) has the identical structure and the identical trust assumption.

### Impact Explanation
If an attacker can cause the working directory content of a tracked file to change between the time Desktop computes/display a diff (and the user selects specific lines to stage or discard) and the time Desktop re-diffs the file to build the git-apply patch, the absolute-line-index selection will silently apply to the wrong lines of the new diff. Because `git apply --unidiff-zero --cached` (staging path) and `git apply` (discard path) will happily apply a syntactically valid patch even if its content doesn't match user intent, the result is **silent corruption of what the user commits (or discards)** — exactly the "silent corruption of what the user commits or pushes" impact class called out as valid. A file could be repointed so the user commits content they never selected, or discards content they meant to keep, with no error, warning, or "refund"/rollback and no diff re-validation step guarding the gap.

Plausible attacker-controlled triggers matching the valid-impact criteria (repository content the attacker controls, not local/physical access) include: a smudge/clean filter, a `post-checkout`/`post-merge`/`post-commit` git hook shipped in a cloned/fetched repository, or a file-system watcher race triggered by activity from a fetched remote that rewrites tracked file content asynchronously while Desktop's diff/selection state is still based on the pre-change content.

### Likelihood Explanation
This requires a window between the diff that produced the `DiffSelection` and the diff `applyPatchToIndex`/`discardChangesFromSelection` re-fetches at commit/discard time, plus a content-changing event under attacker influence (hook, filter, or race with background refresh) landing in that window. Desktop's own comment at `app-store.ts:3478-3493` shows the developers are aware selection state can go stale relative to a changed diff, but the mitigation is limited to index bounds-checking, not content correlation — meaning the described mismatch is a known, currently-unguarded gap rather than a purely theoretical one. Exploitability depends on the timing/hook vector being reliably triggerable, which I was not able to fully verify from the indexed code (I could not access `apply.ts`/`update-index.ts` full call sequencing or hook execution timing in this session due to tool limitations in the final iteration).

### Recommendation
Before applying `file.selection` to a freshly fetched diff, re-validate that the diff's hunk/line content still matches what the selection was computed against (e.g., compare hunk headers/line text, not just index bounds), and if it does not, fail closed (abort the partial-commit/discard operation and force a re-diff/re-selection) rather than silently applying possibly-mismatched line indices. Apply the same content-correlation check in the discard-selection path (`formatPatchToDiscardChanges`) as in the partial-commit path (`formatPatch`).

### Proof of Concept
Conceptual, since I could not execute this in the current session:
1. Open a file with several distinct hunks in Desktop, select specific lines in hunk B only (leaving hunk A unselected) for commit.
2. Before the commit button's `createCommit` call completes, have a process outside Desktop (e.g., a `post-checkout`/background script simulating a malicious repo hook, or a fast file write) change the content around hunk A such that the diff's hunk boundaries/line offsets shift.
3. Desktop's `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`) and applies the stale `file.selection` indices (`app/src/lib/patch-formatter.ts:143-170`) to the new hunk layout.
4. Observe that the resulting commit contains lines from the wrong hunk relative to what the user visually selected, with no warning shown.

This proof-of-concept sketch is based on static code review only; I was unable to run the app or reproduce the timing window directly in this session, so the precise reliability of the race/trigger is unverified.
