## Analysis

Based on the code I was able to inspect, the attack is technically reachable and not blocked by any existing modifier in `WombatBribeManager`:

- `vote()` lets any address with locked vlMGP register a delta for a pool, incrementing both `pool.totalVoteInVlmgp` and `totalVlMgpInVote` [1](#0-0) .
- `castVotes(bool)` is a `public` function with **no access control and no cooldown/time-weighting**. It computes `targetVote = targetVoteInLMGP * totalVotes() / totalVlMgpInVote` purely from the *instantaneous* storage values and pushes it straight to `wombatStaking.vote(...)`, which forwards it to the real Wombat voter [2](#0-1) .
- `unvote()` immediately reverses the bookkeeping (`pool.totalVoteInVlmgp`, `userTotalVotedInVlmgp`, `totalVlMgpInVote`) with no delay and no check tied to `lastCastTime` [3](#0-2) .
- Critically, `vlMGP.lock()` grants `getUserTotalLocked` **instantly** (no vesting) [4](#0-3) [5](#0-4) , so an attacker can buy MGP, lock it, vote, call `castVotes`, and `unvote` all inside a single atomic transaction (via a helper contract), without needing to front-run anyone.

I was unable to locate `WombatStaking.vote()`'s implementation or `IWombatVoter`/`IVeWom` in the indexed context to confirm whether the external Wombat protocol itself enforces an epoch-level vote lock or minimum bribe period that would neutralize the on-chain effect of this rapid vote/unvote cycle. This is a real gap in verification — if Wombat's voter contract rejects vote changes within the same epoch or requires a cooldown, the practical window for exploitation would be constrained by that external mechanism (which per the rules would be an "external-protocol" consideration, but it directly affects feasibility/likelihood here).

Given the rules explicitly reject findings that depend on "external-protocol-bug" behavior, and the *only* way to bound or amplify this issue is by relying on assumptions about Wombat's own voter/veWom contract behavior (which I could not verify from this repo's indexed content), I can only confirm the internal `WombatBribeManager` mechanism lacks a cooldown between `vote`/`castVotes`/`unvote`, but cannot conclusively determine the actual on-chain persistence/impact window without the external Wombat voter code.

### Title
Vote-weight sniping via unbounded vote/castVotes/unvote sequencing - (File: wombat/WombatBribeManager.sol)

### Summary
`castVotes()` computes each pool's share of real veWOM voting power from the instantaneous ratio `pool.totalVoteInVlmgp / totalVlMgpInVote`, with no cooldown or time-weighting tying vote registration to the cast. Because `vlMGP.lock()` grants voting power instantly and `vote()`/`unvote()` have no lockup relative to `castVotes()`, an attacker can atomically inflate a pool's proportional weight, trigger `castVotes()` (a permissionless function) to push a skewed vote to the real Wombat voter, then immediately `unvote()` to remove their registered stake from future rebalances.

### Finding Description
`vote()` increases `pool.totalVoteInVlmgp` and `totalVlMgpInVote` by the caller's chosen delta [6](#0-5) . `castVotes()` is callable by any address, uses only the current storage snapshot to compute `targetVote = targetVoteInLMGP * totalVotes() / totalVlMgpInVote`, and immediately forwards it to `wombatStaking.vote()` [7](#0-6) . `unvote()` then reverts the pool's registered weight with no delay [3](#0-2) . Because `vlMGP.lock()` is instantaneous (no vesting delay before `getUserTotalLocked` reflects the new balance) [4](#0-3) , an attacker-controlled contract can perform lock → vote → castVotes → unvote atomically in one transaction, or across a front-run/back-run pair, with no existing check preventing it.

### Impact Explanation
If effective, this would let an unprivileged holder of real (but only momentarily committed) MGP temporarily skew the proportion of real Wombat gauge votes cast toward a pool of their choosing, matching the "governance voting result manipulation" impact class. The magnitude and persistence of the impact, however, depend on Wombat's own voter/veWom vote-frequency limits, which I could not verify in this repository's indexed content.

### Likelihood Explanation
Requires the attacker to hold/acquire MGP and lock it (real capital, though instantly effective and not consumed—only temporarily allocated), and to either self-call `castVotes()` or race a pending call. No special privileges are needed since `vote`, `castVotes`, and `unvote` are all public/external. Feasibility is repeatable each time `castVotes()` is invoked, since there is no per-user or global cooldown enforced in this contract.

### Recommendation
Introduce a minimum holding period between `vote()` and `unvote()` relative to `lastCastTime` (e.g., disallow `unvote()` of a position that was created after the last successful `castVotes()`, or require votes to be registered for a minimum duration before they count toward `castVotes()`'s ratio calculation). Consider time-weighting `totalVlMgpInVote`/`pool.totalVoteInVlmgp` (e.g., checkpoint-based averaging) rather than using instantaneous snapshots.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, `VLMGP`, and mock `IWombatStaking`/`IWombatVoter`/`IVeWom` (mock `totalVotes()` returning a fixed veWOM balance, and record calls to `wombatStaking.vote()`).
2. Fund attacker with MGP, call `vlMGP.lock(amount)` — assert `getUserTotalLocked` reflects it immediately.
3. In one transaction (attacker contract), call `bribeManager.vote([targetPool], [+largeDelta])`, then `bribeManager.castVotes(false)`, then `bribeManager.unvote(targetPool)`.
4. Assert the mock `wombatStaking.vote()` call recorded a `votes[]` array skewed disproportionately toward `targetPool` based on the transient `totalVoteInVlmgp/totalVlMgpInVote` ratio at cast time.
5. Assert that after `unvote()`, `pool.totalVoteInVlmgp` and `totalVlMgpInVote` return to pre-attack values, while the mocked Wombat voter's recorded vote state remains skewed until a subsequent `castVotes()` call — demonstrating the persistence gap.

Note: This PoC does not model any potential epoch/cooldown restrictions in the real Wombat voter contract; verifying against the actual `IWombatVoter`/`IVeWom` implementations (not available in this index) is necessary to confirm real-world exploitability and impact duration.
