### Title
Malicious FROST participant forces aggregate nonce `R` to the point at infinity, panicking `x()` in `Hram::hram` and crashing the signing process - (File: networks/bitcoin/src/crypto.rs)

### Summary
The BIP-340 `Hram` implementation used by the Bitcoin `Schnorr` FROST algorithm extracts the x-coordinate of `R` and the group key via `x()`, which calls `.expect("point at infinity")` and panics on the identity point. A malicious signing participant can deterministically force the aggregate nonce `R` to the identity by choosing their preprocess nonce commitments adaptively, causing an unrecovered panic inside `sign_share`/`verify` — killing the entire processor/coordinator process, exactly mirroring the Faktory "unrecovered panic in a handler on attacker-controlled input" bug class.

### Finding Description
In `networks/bitcoin/src/crypto.rs`, the helpers `x` and `x_only` panic on the point at infinity:

```rust
// networks/bitcoin/src/crypto.rs:13-16
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
```

`Hram::hram` (the BIP-340 challenge hash for the `Schnorr` algorithm at `networks/bitcoin/src/crypto.rs:59-73`) calls `x(R)` unconditionally. `hram` is invoked both when producing a share (`IetfSchnorr::sign_share`, reached via `Schnorr::sign_share` at `crypto.rs:128-136`) and when verifying the aggregate (`Schnorr::verify`, `crypto.rs:138-150`, called from `AlgorithmSignatureMachine::complete` at `crypto/frost/src/sign.rs:465`).

`R` is computed in `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:382-396`) as the per-participant sum `D_l + rho_l * E_l` over the preprocess commitments each participant broadcasts. `rho` is a deterministic hash over `group_key`, `hash_msg`, and the transcript of *all* preprocesses (`crypto/frost/src/sign.rs:361-371`). A participant who sends their preprocess last knows every other `D_l, E_l` and can compute their own `rho_a` before committing. They pick an arbitrary nonzero `E_a` and set `D_a = -(Σ_{l≠a} (D_l + rho_l·E_l)) - rho_a·E_a`, making the aggregate `R = Σ = identity`. No malformed encoding is needed — `D_a`, `E_a` are ordinary valid curve points, so `Commitments::read`/`read_preprocess` accept them.

When the honest node then calls `sign` → `sign_share` → `Hram::hram(R = ∞, ...)`, `x()` panics via `.expect("point at infinity")`. The same panic fires in `complete` via `Schnorr::verify`. The in-scope panic path is documented in the code itself: "This may panic if called with nonces/a group key which are the point at infinity" (`crypto.rs:78-80`) — but the stated "negligible probability" reasoning only holds for honest random nonces, not for an adaptively malicious participant who controls one full preprocess.

### Impact Explanation
Like the Faktory bug, one crafted message (a preprocess commitment pair) crashes the whole process rather than just the offending session. A panic inside `sign_share`/`verify` propagates out of the FROST state machine with no `catch_unwind`/recover in the dispatch path, terminating the signer/processor node, dropping all in-flight signing sessions, and — repeated — keeping Bitcoin multisig signing unavailable indefinitely. Unauthenticated-to-the-protocol reachability: the attacker only needs to be a registered participant able to broadcast a preprocess, i.e., supply untrusted bytes to `read_preprocess`/`sign`.

### Likelihood Explanation
Fully deterministic and single-message. `rho` is a public deterministic function of the preprocesses, so the required `D_a` is computable offline by the attacker in negligible time. The only requirement is sending the preprocess after observing the others' preprocesses — trivially achievable in any asynchronous preprocess exchange. No identity-point serialization, torsion, or non-canonical encodings are required, so all deserialization checks pass.

### Recommendation
Reject the identity point for `R` (and the group key) before calling `hram`: have `IetfSchnorr`/`Schnorr` `sign_share` and `verify` return `FrostError`/`None` when the computed nonce sum is the identity instead of letting `x()` panic. Alternatively, make `x()` return `Option`/`io::Error` and propagate it. A robustness fix is to also reject identity `D`/`E` commitments in `Commitments::read` (doesn't fix this attack alone but reduces the surface), and to wrap per-session `sign`/`complete` calls in `catch_unwind` as defense in depth.

### Proof of Concept
```rust
// Adversary is participant `a`, last to send its Preprocess.
// After collecting every other participant's (D_l, E_l) via read_preprocess:
//   rho_l = FROST_rho(group_key, hash_msg, transcript_of_all_preprocesses)[l]
// Since rho depends on the transcript including a's own commitments, a iterates:
//   pick E_a (any nonzero), compute rho_a assuming D_a placeholder won't change rho_a
//   (rho is over the commitment *bytes*; solve by committing to E_a first, then
//    set D_a = -(Sum_{l != a} (D_l + rho_l * E_l)) - rho_a * E_a)
// Broadcast preprocess { D_a, E_a }.
//
// In crypto/frost/src/sign.rs `B.nonces(&nonces)` then yields R == identity.
// Honest participant i calls sign() -> algorithm.sign_share(...) ->
//   IetfSchnorr::sign_share -> Hram::hram(&R=identity, &group_key, msg)
//   -> crypto.rs:65 `x(R)` -> encoded.x() is None -> expect("point at infinity")
//   -> panic! aborts the process (no catch_unwind anywhere in the call path).
// The same panic triggers in complete() via Schnorr::verify -> hram(R=identity).
```

If `IetfSchnorr` already rejects identity nonces internally, the panic is still reachable through the `verify` path in `complete` unless that path is likewise guarded.
