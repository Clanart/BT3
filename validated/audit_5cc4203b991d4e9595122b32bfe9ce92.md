Based on my investigation, the closest structural analog to the "Fixed Order Swap" bug class (a hardcoded assumption about which "side" of a value is which, without validating it against the actual runtime ordering) is the `ours`/`theirs` stage mapping used for AI-assisted conflict resolution.

### Title
Hardcoded ours=:2/theirs=:3 git-stage mapping in conflict resolution diffing does not account for git's side-swap during rebase - ([File: app/src/lib/git/diff.ts])

### Summary
`getResolutionDiff` hardcodes `'ours' → :2` and `'theirs' → :3` when reading conflict-index blobs to build the diff used for Copilot-assisted (and manual) conflict resolution. [1](#0-0) 
The function's own documentation explicitly flags that this mapping is *not* stable across operations: "during a rebase, git swaps these — the upstream branch is 'ours' and the rebased commit is 'theirs'. The caller is responsible for mapping user-facing labels to the correct git side." [2](#0-1) 

### Finding Description
Git's own semantics for stage `:2` ("ours") and `:3` ("theirs") flip depending on the operation: during a `merge`, `:2` is the user's current branch and `:3` is the incoming branch; during a `rebase`, git internally replays the user's commits on top of the target, so `:2` becomes the *target/upstream* branch and `:3` becomes the *user's own* commit being replayed. `getResolutionDiff` treats the mapping as fixed and pushes the "figure out which side is semantically which" responsibility onto every caller. [3](#0-2) 
This is architecturally the same broken invariant as the reported "Fixed Order Swap": a value (which git stage corresponds to "ours" vs "theirs") is treated as fixed-order when the true ordering depends on execution context, and correctness depends entirely on external code re-deriving and applying the swap correctly at every call site (in `copilot-conflicts-dialog.tsx` and `copilot-conflicts-changes.tsx`, which I confirmed reference `getResolutionDiff`/stage arguments but was not able to fully trace within the available investigation to confirm whether the rebase-swap is applied consistently at each invocation). [4](#0-3) 
If any call site fails to perform this swap (or a future refactor of these dialogs omits it), the diff and the "ours"/"theirs" content shown to the user — and consumed by Copilot's conflict-resolution model — would be silently reversed for rebases: the model would receive an incoming attacker-controlled commit labeled as "ours" (trusted) and the user's own code labeled as "theirs" (incoming/foreign), producing a resolution that keeps the wrong side while presenting it as validated/trusted content.

### Impact Explanation
Because rebasing onto or merging an attacker-influenced branch is a normal, unprivileged workflow (fetching and rebasing on top of an upstream branch that includes attacker commits, or resolving conflicts against a malicious fork), a mislabeled ours/theirs mapping would cause **silent corruption of what the user commits or pushes** — exactly the impact criteria requested: the user (or the Copilot resolver acting on their behalf) could unknowingly accept the attacker's version of a conflicting hunk while believing they kept their own trusted code, because the UI/model was fed reversed labels.

### Likelihood Explanation
I was able to conclusively confirm the hazardous design (hardcoded stage mapping + explicit doc-comment warning that callers must swap it for rebase), but I exhausted my tool budget before fully verifying whether `copilot-conflicts-dialog.tsx` / `copilot-conflicts-changes.tsx` actually perform the rebase-specific swap correctly at every call site, or whether `app-store.ts`'s `ourBranch`/`theirBranch` derivation (which does appear to swap `targetBranch`/`baseBranch` for rebase around line 3210) is consistently threaded through to the `stage: 'ours' | 'theirs'` calls in `getResolutionDiff`. [5](#0-4) 
This means I cannot state with certainty that the swap is currently missed in shipping code — only that the mechanism for this class of bug exists, is self-documented as fragile, and depends on manual per-call-site correctness rather than being enforced by the type system or a single source of truth.

### Recommendation
Encode the ours/theirs-to-stage mapping as a single, operation-aware helper (taking the `ConflictState`/operation kind as input) rather than letting each caller manually re-derive and pass `'ours' | 'theirs'` into `getResolutionDiff`, so the rebase-swap can't be omitted at a new call site. Add a regression test that runs `getResolutionDiff` under an actual rebase conflict (not just merge, which is the only case currently covered in `diff-stage-test.ts`) to lock in the correct stage-to-label mapping. [6](#0-5)

describe('git/diff/getResolutionDiff (stage mode)', () => {
  it('diffs ours (:2) against the on-disk conflict-marker file', async t => {
    const repo = await setupEmptyRepository(t)

    await makeCommit(repo, {
      entries: [{ path: 'file.txt', contents: 'line 1\nline 2\nline 3\n' }],
      commitMessage: 'base',
    })

    await switchTo(repo, 'feature')
    await makeCommit(repo, {
      entries: [
        { path: 'file.txt', contents: 'line 1\nfeature change\nline 3\n' },
      ],
      commitMessage: 'feature',
    })

    await exec(['checkout', 'master'], repo.path)
    await makeCommit(repo, {
      entries: [
        { path: 'file.txt', contents: 'line 1\nmaster change\nline 3\n' },
      ],
      commitMessage: 'master',
    })

    await exec(['merge', 'feature', '--no-commit'], repo.path)

    // Diff: on-disk (conflict markers) → :2 (master's version)
    const { diff } = await getResolutionDiff(repo, 'file.txt', {
      stage: 'ours',
    })

    assert.equal(diff.kind, DiffType.Text)
    const textDiff = diff as ITextDiff
    assert(textDiff.hunks.length > 0)
    // The conflict markers from the on-disk file should appear as removed
    assert(
      textDiff.text.includes('-feature change'),
      'should remove the other side'
    )
  })
