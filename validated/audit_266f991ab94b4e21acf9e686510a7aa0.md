### Title
Stale `manualResolutions` carry over when the conflict kind changes (merge↔rebase), causing Desktop to silently commit the wrong side of a conflict - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateConflictState` unconditionally reuses the previous `conflictState.manualResolutions` map when building the new conflict state, even when the *kind* of operation has changed (e.g. a merge conflict transitions directly into a rebase conflict, or vice versa, without the app ever observing an intermediate "no conflict" status). Because Git's `ours`/`theirs` semantics are inverted between `merge` and `rebase`, a resolution the user picked to reject a malicious incoming change during a merge can be silently re-applied with the opposite meaning once Desktop's conflict state flips to "rebase", causing the untrusted content to be staged and committed without any further user confirmation.

### Finding Description
`updateConflictState` computes the manual-resolutions map to carry forward before it knows (or checks) whether the new conflict is of the same kind as the previous one: [1](#0-0) 

```

  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null

      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)
  ...
```

`getConflictState` then attaches that same map, keyed only by repository-relative file `path`, to whichever conflict kind the current status reflects (`merge`, `rebase`, or `cherryPick`): [2](#0-1) 

The only place kind-transition is explicitly considered is at the bottom of `updateConflictState`, and even there the comment only concerns *statistics* side effects, not resetting the resolutions map itself: [3](#0-2) 

```
  // Otherwise we transitioned from a merge conflict to a rebase conflict or
  // vice versa, and we should avoid any side effects here
  return newConflictState
```

`newConflictState` here still carries the old `manualResolutions` map verbatim.

Downstream, the UI treats any path present in `manualResolutions` as already resolved (`hasUnresolvedConflicts`), and at commit time `stageManualConflictResolution` mechanically applies `ours`/`theirs` for that path: [4](#0-3) 

Git assigns opposite meanings to `ours`/`theirs` for `merge` vs. `rebase`: during a merge, "ours" is the current branch and "theirs" is the incoming branch; during a rebase, this is reversed ("ours" is the branch being replayed onto, "theirs" is the commit being replayed, i.e. what was originally "ours" pre-rebase). Desktop's `updateConflictState` does not account for this inversion when it silently forwards a resolution chosen under one operation's semantics into a conflict of the other kind.

### Impact Explanation
If the operation kind flips (merge→rebase or rebase→merge) on a file path that had a manual resolution recorded, the leftover choice is applied with the opposite Git meaning. A user who explicitly chose "theirs" during a merge to accept an attacker-controlled remote branch's file, or "ours" to reject it, can have that same stored choice re-interpreted under rebase semantics and staged automatically — without Desktop ever re-prompting the user for that file. Because the file is treated as already resolved, the manual-conflict UI shows no pending decision for it, and `_finishConflictedMerge` / `createMergeCommit` commit the wrong content transparently. This is a silent corruption of what the user ultimately commits/pushes, driven entirely by content in a fetched/cloned repository (conflicting file paths and history shape) that the attacker controls.

### Likelihood Explanation
This requires a specific but reachable sequence: the working copy must go from one conflicted-operation kind directly to a different conflicted-operation kind without an intervening non-conflicted status refresh (e.g. Desktop detects `REBASE_HEAD` immediately after a merge conflict on the same file path, such as when a user or another tool starts a rebase while Desktop's status still reflects the prior merge conflict, or vice versa with cherry-pick/rebase interplay). The `else` branch in `updateConflictState` explicitly acknowledges this transition occurs, but the code was only ever hardened against double-counting telemetry for it, not against carrying over stale per-path resolutions. No test in `update-conflict-state-test.ts` covers a kind-transition case, indicating this path is untested and the state-carryover behavior was not deliberately verified as safe.

### Recommendation
When the conflict kind changes between the previous and new `ConflictState` (i.e. `prevConflictState` is non-null and its `kind` differs from the new status's kind), reset `manualResolutions` to a fresh empty map instead of forwarding the old one. Only preserve `manualResolutions` when `prevConflictState` and the newly computed conflict are the same kind (and ideally also verify targetBranch/currentBranch identity, similar to the abort-detection checks already present in `performEffectsForMergeStateChange`/`performEffectsForRebaseStateChange`).

### Proof of Concept
1. Start a merge into a branch that conflicts on `config.json`; in Desktop's conflict dialog, resolve `config.json` manually as `theirs` (deliberately reviewing and accepting the incoming content) or `ours` (deliberately rejecting it).
2. Before Desktop finishes/aborts that merge (i.e. before a status refresh reports "no conflict"), transition the repository into a rebase that also conflicts on `config.json` (e.g. via a background `git rebase` invoked outside Desktop, or via an app flow that switches operation kind without an intermediate clean-status refresh).
3. On the next `_loadStatus`, `updateConflictState` builds the new `rebase` `ConflictState` while reusing the old `manualResolutions` Map (still containing `config.json -> theirs`/`ours` from the merge).
4. The Copilot/manual conflicts dialog shows `config.json` as already resolved (`hasUnresolvedConflicts` is false), so the user is never re-prompted.
5. On continuing/finishing the rebase, `stageManualConflictResolution` applies the stored resolution using rebase `ours`/`theirs` semantics — the inverse of what the user intended when they made the choice during the merge — silently staging and committing the unintended side of the conflict.

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }
