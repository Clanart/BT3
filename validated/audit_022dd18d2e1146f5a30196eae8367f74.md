### Title
Attacker-controlled participant count in `ThresholdKeys::read` causes unbounded memory allocation / deserialization DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes the `n` (total participants) field as a raw `u16` read directly from the input byte stream, then uses it to pre-allocate a `Vec` and to bound two deserialization loops — all *before* `ThresholdParams::new(t, n, i)` is invoked to validate the parameters. An attacker who supplies bytes to this deserializer can force memory allocation and loop iterations proportional to a fully attacker-controlled 16-bit count from a header of only ~7 bytes.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, `i` as three little-endian `u16`s (lines 591–602). `n` is then used:

1. For `Interpolation::Constant` (tag byte `0`), `Vec::with_capacity(usize::from(n))` pre-allocates room for `n` field elements and a loop reads `n` scalars (lines 604–613).
2. Unconditionally, a `HashMap` is filled by looping `Participant` `1 ..= n` and calling `C::read_G` per entry (lines 620–623).

Only afterwards is `ThresholdParams::new(t, n, i)` called (line 626) to validate the parameters, and only then is `ThresholdKeys::new` invoked. So a malformed blob claiming `n = 0xFFFF` forces an allocation of ~65,535 × `size_of::<C::F>()` (≈2 MB for a 32-byte field element, more for wider fields like ed448/secp256k1 scalars plus `HashMap` overhead for the verification-shares loop) before any sanity check runs. This is the same defect class as CVE-2004-2779: a length/count field parsed from untrusted bytes drives allocation and a parsing loop without an independent bound — the reader trusts the declared count instead of bounding it against the actual input size or the protocol's real participant limits.

The loops themselves terminate on `read_exact` EOF, so this is an allocation/iteration amplification primitive rather than a literal infinite loop; repeated deserialization of crafted blobs (e.g., via any path feeding attacker bytes to `ThresholdKeys::read` / `EncryptedMessage::read`-style sinks) turns a handful of bytes into megabytes of allocation per call, enabling memory-exhaustion DoS of the deserializing party.

### Impact Explanation
An unprivileged party able to get their bytes deserialized as `ThresholdKeys` (or into an equivalent count-prefixed reader) can cause deterministic, asymmetric memory pressure: ~7 input bytes → multi-megabyte allocation. Repeated over many calls this can exhaust memory and crash the victim process (OOM kill), exactly the DoS impact of the reference CVE — the victim allocates far more than the attacker sends. No secret material is required and no signature forgery is needed; availability loss is the impact.

### Likelihood Explanation
Likelihood is moderate: exploitation requires a reachable path where untrusted bytes are fed to `ThresholdKeys::read` (e.g., loading keys received over the wire rather than from local trusted storage). Within the process, the trigger is trivial — a two-byte `n` of `0xFFFF` with interpolation tag `0` suffices, and no cryptographic validity is needed since validation happens only after the allocation/loops. The amplification factor is bounded (~65k elements per call), so sustained input is needed for full OOM, which keeps this below Critical/High severity.

### Recommendation
Validate `t`, `n`, and `i` (construct `ThresholdParams`) *immediately after* reading them and before any allocation or loop bounded by `n`. Additionally:

- Avoid `Vec::with_capacity(n)` / sized pre-allocation driven by untrusted counts; grow incrementally or cap `n` at the protocol maximum (`MAX_KEY_SHARES_PER_SET`-style bound) before allocating.
- Bound deserialization loops by remaining input length where possible, or reject `n` values inconsistent with the serialized size.
- Apply the same pattern anywhere a count/length field read from untrusted bytes drives `with_capacity`, `vec![0; len]`, or a read loop.

### Proof of Concept

use std::io::Cursor;
// Conceptual PoC against ThresholdKeys::<C>::read for a ciphersuite C with a 32-byte scalar:
// Build a blob: [id_len = C::ID.len() as u32 LE][C::ID][t = 1u16][n = 0xFFFFu16][i = 1u16][interp = 0]
let mut blob = vec![];
blob.extend(&(C::ID.len() as u32).to_le_bytes());
blob.extend(C::ID);
blob.extend(&1u16.to_le_bytes());      // t
blob.extend(&u16::MAX.to_le_bytes());  // n = 65535, attacker-controlled
blob.extend(&1u16.to_le_bytes());      // i (valid participant)
blob.push(0);                          // Interpolation::Constant
// No further bytes needed: Vec::with_capacity(65535 * size_of::<F>()) is allocated,
// then the read_F loop errors on EOF. Roughly ~2 MB allocated per call from 7 bytes.
let res = ThresholdKeys::<C>::read(&mut Cursor::new(&blob));
// res is Err(..), but the allocation already happened; repeat in a loop to exhaust memory.
