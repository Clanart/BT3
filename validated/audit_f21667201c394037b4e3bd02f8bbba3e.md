### Title
Forged `ReceivedOutput` encodings can register unspendable Bitcoin funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes an arbitrary scalar offset, `TxOut`, and `OutPoint` without proving that the outpoint exists, belongs to the supplied output, or is spendable by the scanner’s key. A forged encoding can therefore create an apparent received UTXO that later passes `SignableTransaction::multisig`’s script check while referring to a nonexistent or unrelated Bitcoin outpoint. [1](#0-0) [2](#0-1) 

### Finding Description
`ReceivedOutput::read` reads `offset`, `output`, and `outpoint` independently and returns them as a trusted spendable-output object. It performs canonical scalar decoding and Bitcoin consensus decoding, but no semantic validation tying the three fields to a confirmed chain output. [1](#0-0) 

The legitimate construction path is `Scanner::scan_transaction`, which derives the outpoint from the containing transaction and stores the associated script-derived offset. [3](#0-2) 

That provenance is lost when bytes are supplied directly to `ReceivedOutput::read`. An attacker can encode the victim’s known P2TR script with the corresponding public offset, while inventing the transaction ID, output index, and amount. [1](#0-0) 

`SignableTransaction::new` then uses the forged output value and outpoint as transaction inputs, and `multisig` only checks that the stored script equals `p2tr_script_buf(key + offset)`; it does not and cannot establish that the claimed outpoint exists. [4](#0-3) [2](#0-1) 

### Impact Explanation
A caller that accepts serialized `ReceivedOutput` values from an untrusted source can report attacker-selected funds as received even though they cannot be spent. If accounting, liquidity accounting, or threshold-signing orchestration trusts the decoded object before independent chain verification, the forged input can inflate balances or cause the threshold group to sign a transaction that Bitcoin consensus will reject. [5](#0-4) 

The signature itself is not valid for a different existing UTXO because the sighash commits to all supplied prevouts, but the object still falsely represents an unspendable input as spendable. [5](#0-4) 

### Likelihood Explanation
The public group key determines the expected P2TR script, and the base-key output uses the public zero offset, so no secret is needed to construct a syntactically valid forged `ReceivedOutput`. [6](#0-5) 

Exploitation requires an interface that accepts serialized outputs from an unprivileged party and treats them as scanner-produced evidence. The bug does not by itself defeat Bitcoin consensus validation, so the strongest practical impact is incorrect crediting or wasting signing rounds rather than direct theft. [3](#0-2) 

### Recommendation
Do not expose `ReceivedOutput::read` as proof of ownership or chain membership. Require an expected base key during deserialization and verify:

- `output.script_pubkey == p2tr_script_buf(key + GENERATOR * offset)`
- the encoded `outpoint` exists in a confirmed block
- the encoded `TxOut` equals the output at that outpoint
- the output is not coinbase-immature when immediate spending is required

Alternatively, separate a raw transport representation from a validated `ReceivedOutput` type so callers cannot confuse untrusted bytes with scanner-authenticated outputs. [1](#0-0) [3](#0-2) 

### Proof of Concept
```rust
use bitcoin::{
  consensus::encode::serialize,
  hashes::Hash,
  Amount, OutPoint, TxOut, Txid,
};
use k256::Scalar;
use bitcoin_serai::wallet::{p2tr_script_buf, ReceivedOutput};

let victim_script = p2tr_script_buf(group_key).unwrap();

let fake_output = TxOut {
  value: Amount::from_sat(1_000_000_000),
  script_pubkey: victim_script,
};

let fake_outpoint = OutPoint {
  txid: Txid::from_byte_array([0x11; 32]),
  vout: 0,
};

let mut encoded = Scalar::ZERO.to_bytes().to_vec();
encoded.extend(serialize(&fake_output));
encoded.extend(serialize(&fake_outpoint));

let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
assert_eq!(forged.value(), 1_000_000_000);
```

`SignableTransaction::multisig` accepts this object whenever `group_key + G * Scalar::ZERO` maps to `victim_script`, despite `fake_outpoint` being unrelated to the encoded output or absent from the blockchain. [7](#0-6) [2](#0-1)
