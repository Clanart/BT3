### Title
Escrow credited before tokens are actually transferred in predispatch path — reentrant/composed dispatcher call can double-credit `_orders` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the predispatch branch of `placeOrder` (Tron variant), `_orders[commitment][token] += reducedInputs[i].amount` is executed **before** the `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` call that actually moves the tokens from the `CallDispatcher` back into the gateway. This is the same broken-invariant class as the C4 `depositBribeERC20` finding: state (the trusted escrow ledger) is written on the assumption that a transfer will succeed, while the real value-moving call happens afterward, leaving a window where the recorded escrow does not correspond to tokens actually held. [1](#0-0) 

### Finding Description
The predispatch flow is:
1. Transfer `predispatch.assets` to `dispatcher` and run `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` — this is user-supplied, arbitrary calldata executed by the `CallDispatcher` (e.g., to unwrap LP tokens), so it is attacker-influenced.
2. For each input token, compute `balance`/`dust` on the dispatcher and then immediately do `_orders[commitment][token] += reducedInputs[i].amount;` — crediting escrow.
3. Only afterward call `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`, which is the step that actually executes `IERC20.transfer` calls moving the balance from `dispatcher` to `address(this)`. [2](#0-1) 

Compare this to the mainline EVM contract's `placeOrder`, which measures `received` **after** the sweep dispatch completes and only then credits `_orders` in a separate "Phase 3" loop — token custody is confirmed before the ledger is updated: [3](#0-2) [4](#0-3) 

The Tron contract's ordering inverts this: it writes trusted escrow state, then performs the value-moving dispatch. Since step 1's `dispatch(order.predispatch.call)` is attacker-controlled calldata routed through the same `CallDispatcher`, and the escrow write in step 2 happens on the assumption that step 3's transfer will later succeed, any path that lets the attacker cause step 3 to fail, be skipped, or transfer less than expected (e.g., a malicious/fee-on-transfer token on the dispatcher, or a dispatcher call that reverts partway) leaves `_orders[commitment][token]` credited with an amount the gateway never actually received or retained.

### Impact Explanation
`_orders[commitment][token]` is the authoritative escrow ledger consumed later by `withdraw()`/`fillOrder` to release funds to solvers or refund the user. If this value can be inflated relative to actual custody, it directly maps to the Hyperbridge bounty's "stealing or loss of funds" and "false state acceptance" categories: a solver could later drain more from the gateway's real balance than the order ever deposited, at the expense of other users' escrowed funds in the shared `_orders`/contract balance.

### Likelihood Explanation
This requires the attacker to control the `predispatch.call` payload and asset list on `placeOrder`, which is a standard user-facing entrypoint (no privileged role needed) — matching the "unprivileged attacker" bar. However, I was unable to fully verify from the retrieved snippets whether `IERC20.transfer` failures in the second `dispatch` are checked/reverted downstream, or whether the `CallDispatcher.dispatch` guarantees full execution or reverts atomically on partial failure — this needs direct inspection of `ICallDispatcher`/`CallDispatcher.dispatch` and confirmation of whether `placeOrder` in the Tron file carries `nonReentrant` (unresolved due to a tool failure on the final read). Without that confirmation, I cannot assert with certainty that the ordering is exploitable rather than merely non-idiomatic-but-safe (e.g., if `dispatch` internally reverts the whole transaction on any failed transfer, the credited-then-transferred ordering would be unexploitable since the entire tx would revert together).

### Recommendation
Mirror the mainline `evm/src/apps/IntentGatewayV2.sol` pattern: measure actual balances received on the gateway strictly after all transfer dispatches complete, and only credit `_orders[commitment][token]` from that measured, post-transfer value — never before the transfer call is confirmed to have moved tokens.

### Proof of Concept
Not constructible with certainty from the available evidence. The theoretical PoC would be: craft a `predispatch.call` that manipulates the dispatcher's token balance/allowance state such that the subsequent `transferCalls` `dispatch` moves less than `reducedInputs[i].amount` (or a token that silently no-ops/partially transfers) while the earlier `_orders[commitment][token] += reducedInputs[i].amount` has already recorded the full amount — but confirming this requires verifying `CallDispatcher.dispatch`'s failure semantics and `placeOrder`'s reentrancy-guard status, which I could not complete in this session due to a tool error.

**Given the unresolved verification points, I am not fully confident this rises to a provable, exploitable finding** — flagging it as the strongest candidate found, but recommend a Devin session with full file access to confirm `CallDispatcher.dispatch` behavior and the `nonReentrant` status of Tron's `placeOrder` before treating this as confirmed.
