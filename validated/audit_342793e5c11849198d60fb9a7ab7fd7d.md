### Title
`clone()` force-disables Git's post-CVE-2024-32002 clone/submodule protections via `GIT_CLONE_PROTECTION_ACTIVE=false` - ([File: app/src/lib/git/clone.ts])

### Summary
GitHub Desktop's `clone()` function unconditionally sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for every `git clone --recursive` invocation. This is the exact protection mechanism Git introduced (in the fix for CVE-2024-32002 / the recursive-clone RCE class of bugs) to detect and reject repositories whose layout tries to smuggle a malicious `.git`/hooks/config structure through nested submodules during a recursive clone. By hard-disabling this at the top level for every Desktop-initiated clone, the app removes a safety net that upstream Git ships enabled by default, for the entire clone/submodule-init tree — not just the internal nested-submodule case the variable was designed to skip.

### Finding Description
`clone()` in [1](#0-0)  builds the environment for `git clone --recursive` and explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` before ever running the top-level clone (not just as an env var git internally propagates to nested submodule sub-clones). Git upstream added this variable/flag as part of hardening recursive clone/submodule handling against maliciously crafted repositories (the class of bug fixed by CVE-2024-32002, where nested `.git` directories or submodule paths could be crafted to overwrite files such as hooks and later achieve command execution during checkout). The protection is meant to be active by default and only selectively disabled by Git itself for recursive internal sub-clone calls where the top-level check already ran. Desktop instead disables it unconditionally for the whole operation, for every clone, regardless of whether submodules are actually involved and regardless of whether the top-level repository itself is attacker-controlled.

This is structurally the same "broken invariant" pattern as the audited report: a safety check that is supposed to gate a state transition (clone protection $\rightarrow$ trusted checkout) is bypassed under a specific condition (Desktop always sets the flag off) so the invariant ("recursive clones are checked for malicious embedded repository structures") silently does not hold, and the resulting corrupted state (an unchecked, potentially malicious on-disk checkout / hooks layout) cannot be caught by any other guard in the code path — `isClonePathSensitive` only guards the top-level destination directory [2](#0-1) , and `updateSubmodulesAfterOperation` also does not reinstate the protection when invoking `submodule update --init --recursive` [3](#0-2) .

### Impact Explanation
If the underlying Git version's clone-protection check would have rejected a specific malicious repository/submodule layout (crafted `.git` entries, symlink tricks, or nested submodule paths designed to write outside the intended worktree or plant executable hooks), Desktop's forced `GIT_CLONE_PROTECTION_ACTIVE=false` removes that rejection for users cloning attacker-controlled repositories, i.e., an unprivileged attacker who controls a repository the victim clones (a classic Desktop threat model: "attacker controls a cloned/fetched repository"). Depending on the underlying dugite/Git version's checks, this can degrade to file writes outside the intended repository directory or later hook execution during clone/checkout — matching the "file write outside the repo" / "code execution" impact classes.

### Likelihood Explanation
Likelihood is moderate: exploitability is entirely dependent on which class of malicious repository layout the bundled Git version's `GIT_CLONE_PROTECTION_ACTIVE` check actually catches, since I could not verify the exact version of dugite/Git bundled by Desktop or exactly what the check protects against in that version from the available code (this is inherently a Git-internal C-code check, not implemented in this TypeScript codebase). No other code path in the Desktop repo reinstates or narrows the scope of this override, and the flag is applied indiscriminately to `git clone --recursive` — used for all repository clones, not just ones known to contain submodules.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally for the top-level `clone()` call. Only rely on Git's own internal handling of the variable for nested submodule sub-clones (Git sets/propagates it itself when appropriate), or explicitly leave it at its secure default (`true`) unless a specific compatibility issue with a pinned dugite/Git version requires disabling it — in which case document the exact CVE/check being bypassed and gate the override behind that specific condition rather than applying it globally.

### Proof of Concept
Not independently reproducible from the indexed code alone — the actual security check being disabled lives in Git's C implementation (invoked via dugite) and I could not access that implementation from the codebase index to construct a concrete malicious-repository PoC. The finding is based on static evidence that Desktop always passes `GIT_CLONE_PROTECTION_ACTIVE=false` for every clone at [1](#0-0) , which is inconsistent with the variable's documented protective purpose in upstream Git. Confirming actual exploitability requires checking the pinned dugite/Git version's behavior of this flag directly, which is outside what the code index can show — I recommend starting a Devin session with terminal access to inspect the vendored Git binary/version and test a crafted recursive-submodule repository against `clone()` with and without the override to confirm impact.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
