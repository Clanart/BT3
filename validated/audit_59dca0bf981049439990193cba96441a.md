### Title
Honest operator's payout attribution can be hijacked via unsigned outputs of `payout_tx`, causing `is_kickoff_malicious` to burn the honest operator's collateral - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` signs only input 0 and output 0 with the user's `SinglePlusAnyoneCanPay` signature, leaving the anchor output and the operator-attribution `OP_RETURN` output completely unsigned and freely rewritable. `Verifier::update_finalized_payouts` blindly trusts whichever transaction first spends the tracked `withdrawal_utxo` outpoint and extracts the operator xonly pk straight from that transaction's `OP_RETURN`, with no cryptographic binding to the party that actually funded the payout. Any unprivileged party who observes operator A's broadcast payout transaction can rebroadcast a fee-bumped variant that reuses A's signed input/output 0 but swaps the `OP_RETURN` to point at operator B, getting B credited as payer while A actually funded the withdrawal.

### Finding Description
Binding claimed by the protocol: `withdrawals.payout_payer_operator_xonly_pk` for index `i` == the xonly pk of the operator whose funds financed output 0 of the confirmed payout transaction for withdrawal `i`.

Trace:
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout tx with input 0 (`SpendPath::KeySpend`), output 0 (user payout), output 1 (anchor, `NON_EPHEMERAL_ANCHOR_AMOUNT`, used for CPFP with `NON_STANDARD_V3`), and output 2 (`OP_RETURN(operator_xonly_pk)`). Only `set_p2tr_key_spend_witness(&user_sig, 0)` signs input 0.
- The user's signature is `SinglePlusAnyoneCanPay` (verified in `Operator::withdraw`, `core/src/operator.rs:630-637`, with the error message explicitly requiring this sighash type). `SIGHASH_SINGLE` commits only to output index 0; `ANYONECANPAY` allows arbitrary other inputs. Outputs 1 and 2, and any additional inputs, are completely unconstrained by the signature.
- `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) resolves the payer purely from `get_payout_txs_for_withdrawal_utxos`, which is a DB join on `bitcoin_syncer_spent_utxos` keyed only by `(withdrawal_utxo_txid, withdrawal_utxo_vout)` (`core/src/database/verifier.rs:170-196`) — i.e., whichever transaction is actually mined spending that outpoint, regardless of source. It then calls `get_first_op_return_output` + `parse_op_return_data` (`circuits-lib/src/bridge_circuit/mod.rs:608-617, 686-692`) on that mined transaction and stores the resulting pk via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`).
- `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) later compares `kickoff_data.operator_xonly_pk` (A) against the stored `operator_xonly_pk_opt` (now B) and flags a mismatch as malicious (`core/src/verifier.rs:1887-1890`), triggering Challenge/Disprove against A's kickoff.

Exploit flow: attacker observes A's broadcast `payout_tx` (mempool), constructs a variant copying input 0's outpoint/prevout/witness (still valid — the signature does not commit to output 1/2 or extra inputs) and output 0 verbatim, replaces output 2 with `OP_RETURN(B.operator_xonly_pk)`, optionally adds attacker-controlled inputs/adjusts the anchor output, and gets this variant confirmed first (via RBF/CPFP race, since the parent's own fee is minimal by design and confirmation relies on anchor CPFP). No existing guard checks that the operator recorded in the `OP_RETURN` corresponds to the party that supplied the actual value of output 0 or the fee-paying inputs — `SECP.verify_schnorr` only validates the user's own signature over input 0/output 0, and none of `is_deposit_valid`, `verify_storage_proofs`, `SPV::verify` inspect payer attribution beyond parsing this same unauthenticated `OP_RETURN`.

### Impact Explanation
Operator A, who genuinely fronted the withdrawal, has its real subsequent kickoff transaction flagged as malicious because `is_kickoff_malicious` reads the attacker-substituted operator pk (B) from the DB instead of A's. This leads verifiers to treat A's kickoff as fraudulent, triggering the Challenge/Disprove path and burning A's collateral — matching the Critical impact category "an honest operator's collateral burned." The attack is repeatable per withdrawal/operator pair, requires only mempool visibility and fee-bumping capability, and needs no privileged role, key compromise, or majority hashrate.

### Likelihood Explanation
The attacker needs only to: watch the Bitcoin mempool/network for a broadcast `payout_tx` (public data), rebuild a conflicting transaction preserving the signed input/output 0, and win the RBF/CPFP race by paying a higher fee. No aggregator, verifier, or operator role is required, and the sighash restriction (`SinglePlusAnyoneCanPay`) is precisely the mechanism that permits this rewrite — it is inherent to the protocol design, not a bug requiring rare conditions. Cost is limited to normal Bitcoin transaction fees.

### Recommendation
Bind the operator attribution to the actual signed transaction structure rather than an unsigned `OP_RETURN`. Options: (1) have the user's payout signature cover a wider sighash (e.g., `SIGHASH_ALL` or `SIGHASH_SINGLE` combined with a commitment hash that includes the operator pk output), or (2) have the operator co-sign/commit the `OP_RETURN` output (e.g., via a second signature or a taproot script path requiring the operator's own key), so that the payer's identity cannot be altered without invalidating the transaction. Alternatively, attribute payment based on which operator's own UTXOs actually funded the additional payout inputs (verifiable on-chain ownership) rather than a free-text `OP_RETURN`.
