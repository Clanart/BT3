### Title
Type Confusion in `UnpackTxData` During EVM Transaction Deserialization - (File: `x/evm/types/codec.go`)

### Summary
`UnpackTxData` in `x/evm/types/codec.go` (and its duplicate in `giga/deps/xevm/types/codec.go`) deserializes the `Data` field of a `MsgEVMTransaction` by blindly trying `proto.Unmarshal` against six unrelated concrete proto message types in a fixed order and returning the **first one that decodes without error**, completely ignoring the `Any.TypeUrl` that is supposed to identify the real type. This is the same bug class as CVE-2026-21493 (iccDEV type confusion during serialization): the code trusts structural decodability instead of the declared type tag to pick a concrete Go type.

### Finding Description
`MsgEVMTransaction.Data` is a protobuf `Any` whose `Value` bytes are supposed to be tied to a specific concrete `ethtx.TxData` implementation identified by `Any.TypeUrl`. `UnpackTxData` instead does this: [1](#0-0) 

When `any.GetCachedValue()` is not already populated with a typed `ethtx.TxData` (which is the case for every transaction freshly decoded off the wire, since `cachedValue` is a Go-only, non-wire field that is never set by `proto.Unmarshal` of raw bytes), the function tries, **in this fixed order and without ever consulting `TypeUrl`**: `LegacyTx`, `AccessListTx`, `DynamicFeeTx`, `BlobTx`, `AssociateTx`, `SetCodeTx`, and returns the first one for which `proto.Unmarshal` does not error.

gogo-proto's `Unmarshal` is lenient: unknown field numbers are stored as unrecognized bytes rather than causing an error, and any wire-compatible byte sequence for a field number/wire-type pair that happens to exist in an earlier-tried struct will successfully populate that struct — even though the bytes were produced for (and declared via `TypeUrl` as) a semantically different message. Because these six proto messages are unrelated schemas with independently assigned field numbers, a `Value` payload can be simultaneously "valid" under more than one of them, and the function will silently commit to whichever type is tried first, discarding the caller's actual `TypeUrl` intent. This is a textbook interface/type confusion during deserialization.

`MsgEVMTransaction.ValidateBasic`, `AsTransaction`, `GetAssociateTx`, and `IsAssociateTx` all call `UnpackTxData` directly on attacker-controlled `msg.Data`: [2](#0-1) [3](#0-2) 

and the same call is repeated independently throughout the EVM ante/fee/gas pipeline that every submitted EVM transaction passes through: [4](#0-3) [5](#0-4) 

### Impact Explanation
Because the resolved concrete type is chosen by "first structurally-decodable match" rather than by the declared `TypeUrl`, a transaction sender can construct `Data` bytes engineered to be decoded by `EVMFeeCheckDecorator.AnteHandle`, `PreprocessUnpacked`, and gas/priority logic as a different `ethtx.TxData` concrete type than what downstream logic (or a human/tooling auditor relying on `TypeUrl`) believes was submitted. Since `GetGasFeeCap()`, `GetGasTipCap()`, `EffectiveGasPrice()`, signature `V/R/S` extraction, and association/replay logic (`PreprocessUnpacked`) all read fields directly off whichever struct wins the type-confused unmarshal, an attacker can misalign the byte layout of one tx-type's fields onto another type's field getters, letting fee, gas-cap, and priority checks operate on attacker-chosen values that do not correspond to what the "declared" type would have produced — undermining the minimum-fee/base-fee enforcement in `EVMFeeCheckDecorator` and the signature/chain-id checks in `PreprocessUnpacked`, both of which gate fund movement and validator gas accounting.

### Likelihood Explanation
Reachable by any unprivileged EVM transaction sender: the vulnerable code path is exercised on every `MsgEVMTransaction` decoded from wire bytes, since `Any.cachedValue` is never populated straight off `proto.Unmarshal` of a raw transaction and is only used opportunistically. No special privileges, precompile access, or governance action is required — an attacker only needs to craft raw `MsgEVMTransaction.Data` bytes.

### Recommendation
Rewrite `UnpackTxData` to resolve the concrete type strictly from `Any.TypeUrl` via the registered interface implementations (the same mechanism used by `statefulUnpacker.UnpackAny` in `sei-cosmos/codec/types/interface_registry.go`), and reject the message if `TypeUrl` does not match one of the exact six registered EVM tx types, instead of trial-decoding against unrelated schemas.

### Proof of Concept
Exact byte-for-byte demonstration of the colliding encodings for these specific gogo-proto messages could not be constructed with the tools available in this session (no code execution). The finding is based on static analysis of the trial-unmarshal loop in `UnpackTxData` (`x/evm/types/codec.go:93-134`) which structurally permits type confusion by design (ignoring `TypeUrl`, matching purely on successful `proto.Unmarshal`). A concrete byte-collision PoC would require constructing a `Value` payload whose field-number/wire-type sequence is simultaneously valid for `LegacyTx` and a later-listed message type with attacker-favorable field semantics (e.g., `AssociateTx`/`SetCodeTx`), which should be validated with an actual Go harness in a Devin session with code-execution access.

func UnpackTxData(any *codectypes.Any) (ethtx.TxData, error) {
	if any == nil {
		return nil, errors.New("protobuf Any message cannot be nil")
	}

	txData, ok := any.GetCachedValue().(ethtx.TxData)
	if !ok {
		ltx := ethtx.LegacyTx{}
		if proto.Unmarshal(any.Value, &ltx) == nil {
			// value is a legacy tx
			return &ltx, nil
		}
		atx := ethtx.AccessListTx{}
		if proto.Unmarshal(any.Value, &atx) == nil {
			// value is a accesslist tx
			return &atx, nil
		}
		dtx := ethtx.DynamicFeeTx{}
		if proto.Unmarshal(any.Value, &dtx) == nil {
			// value is a dynamic fee tx
			return &dtx, nil
		}
		btx := ethtx.BlobTx{}
		if proto.Unmarshal(any.Value, &btx) == nil {
			// value is a blob tx
			return &btx, nil
		}
		astx := ethtx.AssociateTx{}
		if proto.Unmarshal(any.Value, &astx) == nil {
			// value is an associate tx
			return &astx, nil
		}
		stx := ethtx.SetCodeTx{}
		if proto.Unmarshal(any.Value, &stx) == nil {
			// value is a set code tx
			return &stx, nil
		}
		return nil, fmt.Errorf("cannot unpack Any into TxData %T", any)
	}

	return txData, nil
}
