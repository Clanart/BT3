## Analog Found: No Reserve/Floor Price in KIP-249 Auction Bid Validation Allows Near-Zero Bids to Win Exclusive Execution Rights Under Network Congestion

### Title
Auction bid pool accepts and finalizes a single near-zero bid as the winner with no minimum reserve tied to expected value, mirroring the Dutch-auction/near-zero-bid design flaw - (File: `kaiax/auction/impl/bid_pool.go`)

### Summary
The Kaia auction module (KIP-249) determines the winning bid for a target transaction purely by "highest bid submitted, and greater than zero" — there is no floor, reserve price, or minimum-value requirement tied to the actual worth of the execution slot being auctioned. Under network congestion (the exact scenario described in the external report), when only one searcher/bidder is able to submit a bid before the block deadline, that bid wins the exclusive right to have its transaction executed immediately after the target transaction, no matter how small the bid amount is, as long as it satisfies `bid.Bid.Sign() > 0`.

### Finding Description
`validateBid` in `kaiax/auction/impl/bid_pool.go` enforces only that the bid amount be strictly greater than zero: [1](#0-0) 

`insertBid` then keeps, per `(blockNumber, targetTxHash)`, whichever bid is currently the largest — but if there is exactly one bid, it is accepted unconditionally as the winner regardless of magnitude: [2](#0-1) 

This mirrors the reported design flaw precisely: like Frankencoin's zero-floor collateral auctions, the Kaia auction has no mechanism analogous to a "dutch auction" reserve/decreasing-price floor, or any minimum bid tied to the value of the resource being sold (here, the guaranteed post-target-tx execution slot, which is the basis of MEV/arbitrage/liquidation capture value in the KIP-249 design). The `AuctionEntryPointMock.sol` on-chain contract used for settlement likewise only checks `auctionTx.bid <= 0` and nothing else: [3](#0-2) 

The module's own documentation confirms bid pool validation rule #3 is simply "greater than 0", with no floor logic: [4](#0-3) 

### Impact Explanation
During periods of network congestion — precisely the scenario cited in the external report — competing searchers/bidders may be unable to get their bids accepted by the bid pool in time (rate limiting, propagation delay, or simply fewer active participants). If only a single, near-zero bid reaches the pool for a given target transaction, that bid unconditionally becomes the winner and is granted the exclusive right to execute immediately after the target transaction via `GetBidTxGenerator`: [5](#0-4) 

Because the bid amount is the mechanism by which the protocol (proposer/auctioneer) is meant to be compensated for granting this valuable execution slot, a near-zero winning bid results in the proposer/system receiving negligible payment for a slot that may carry substantial extractable value (e.g., large arbitrage or liquidation opportunities tied to the target transaction), effectively redirecting that value to the sole bidder at the expense of the protocol's intended fee capture.

### Likelihood Explanation
This requires no malicious validator, peer, or consensus-message manipulation — it is purely a function of ordinary network congestion (RPC/mempool propagation delay, rate limiting per `bidsPerSecondPerPeer`) reducing the number of competing bids reaching the pool before block assembly, exactly the "extreme but inevitable" network condition described in the source report. Any unprivileged auction bidder can then submit a minimal (`bid.Bid.Sign() > 0`, e.g. 1 wei) bid and, absent competition, win the slot outright.

### Recommendation
Introduce a minimum reserve or floor requirement for bids in `validateBid` (and enforce it in the on-chain `AuctionEntryPoint` settlement logic) — for example, a value tied to expected MEV/gas cost of the target transaction, or a Dutch-auction-style declining floor over the block's allowed bid window — so that a single near-zero bid cannot unconditionally claim the execution slot when no meaningful competition exists.

### Proof of Concept
1. Network congestion causes only one bidder's bid to reach the `BidPool` for `targetTxHash` at `blockNumber`.
2. The bid is submitted with `bid.Bid = 1` (minimal positive value), satisfying `validateBid`'s only value check at `bid_pool.go:374-377`.
3. `insertBid` accepts it into `bidTargetMap[blockNumber][targetTxHash]` since there is no competing bid to compare against (`bid_pool.go:294-309`).
4. The block builder uses `GetBidTxGenerator` to append the bidder's transaction immediately after the target transaction, granting exclusive access to any value opportunity created by the target tx, in exchange for a payment of `1 wei`.

## Bid pool validation rules

A bid pool is responsible for managing the valid bids from the `Auctioneer`. The bid must satisfy the following rules:

1. The `bid.Sender` must not be in the winner list of the same block number if the new bid doesn't have the same target block and hash as the previous bid.
2. The `bid.BlockNumber` must be in range of `[currentBlockNumber + 1, currentBlockNumber + allowFutureBlock]`.
3. The `bid.Bid` must be greater than 0.
4. The `bid.Data` size must be less than or equal to `BidTxMaxDataSize`.
5. The `bid.CallGasLimit` must be less or equal to `BidTxMaxCallGasLimit`.
6. The `bid.SearcherSig` and `bid.AuctioneerSig` must be valid.
