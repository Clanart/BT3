The original hypothesis (module returns `Ok` with silently inconsistent state) doesn't hold up — that would require a bug in a specific `IsmpModule` implementation returning a "clean" success while actually failing internally, which is a module-author bug rather than a protocol-level flaw. However, tracing the actual code surfaces a closely-related, concrete vulnerability on the **`Err` path** of the same mechanism, in production code.

### Title
Non-atomic custody mutation in `pallet-hyper-fungible-token::on_accept` allows repeated free minting via forced module failure - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`IsmpModule::on_accept` for the hyper-fungible-token pallet performs the fund-moving mutation (mint/transfer to beneficiary) *before* executing optional attached calldata, and a failure in the calldata stage returns `Err` from the whole callback. The core ISMP request handler treats any `Err` from `on_accept` as "never happened" and deletes the just-stored request receipt so the request can be retried/timed out — but it does not, and cannot, undo the mint/transfer that the module already performed.

### Finding Description
In `modules/ismp/core/src/handlers/request.rs::handle`, the receipt is stored first (line 112) then `cb.on_accept(request)` is invoked (line 113). If the callback returns `Err`, the receipt is deleted so the request "can be timed out" (lines 122-125): [1](#0-0) 

The whole `handle` function always returns `Ok(...)` for the batch regardless of individual per-request outcomes: [2](#0-1) 

Because the enclosing pallet extrinsic ultimately succeeds (`Ok`), FRAME's automatic storage-transaction rollback (which only reverts state on an `Err` dispatch result) never fires — any storage writes performed inside a failing `on_accept` before it returned `Err` remain permanently committed.

`pallet_hyper_fungible_token::Pallet::on_accept` exploits exactly this gap: it mints/transfers funds to the beneficiary first, then — only if `message.data` is non-empty — decodes and dispatches an attached runtime call, returning `Err` on any calldata decode/signature/dispatch failure: [3](#0-2) [4](#0-3) 

If the calldata portion is crafted to deterministically fail (e.g. an unparseable `SubstrateCalldata`, a bad signature, or a `RuntimeCall` blocked by `BaseCallFilter`), the mint/transfer at lines 93-117 completes and is committed, but the callback still returns `Err`. Back in `request.rs`, this `Err` triggers `delete_request_receipt` (line 124). Since the receipt no longer exists, the *same* request commitment can be resubmitted with a fresh membership proof and will pass both duplicate checks (`request.rs` lines 58 and 108), invoking `on_accept` again — minting/transferring the funds a second time, and again deleting the receipt on the same deterministic calldata failure. This can be repeated indefinitely.

### Impact Explanation
This is unbounded, repeatable duplicate settlement: an attacker mints/receives the bridged asset amount on every resubmission of the same request while never letting the request settle into a receipted (consumed) state. This directly matches the bounty's "duplicate settlement" / "stealing or loss of funds" impact class, since it lets a single cross-chain transfer be credited to the beneficiary an arbitrary number of times.

### Likelihood Explanation
The attacker only needs to construct one outgoing message whose optional calldata is guaranteed to fail on the destination (trivial: garbage bytes for `SubstrateCalldata`, or a call blocked by `BaseCallFilter`) and then relay/resubmit that same request (with a valid state proof, which is available to any unprivileged relayer once the request is included in the source chain's state) as many times as desired. No privileged operator or malicious relayer/node behavior is required — an ordinary user driving the bridge's normal message-relay flow suffices.

### Recommendation
Make the custody mutation and calldata execution atomic within `on_accept`: either (a) wrap the whole callback body in a storage transaction (e.g. `frame_support::storage::with_storage_layer`) so a later failure rolls back the earlier mint/transfer, or (b) reorder logic so calldata is validated/decoded *before* any funds move, or (c) do not delete the request receipt on `Err` from a module whose on_accept has externally observable side effects — instead mark it as permanently failed/non-retryable rather than open to replay.

### Proof of Concept
1. Register a token in `pallet_hyper_fungible_token` and set up a valid source contract/asset mapping via `ContractToAsset`.
2. From the source chain, dispatch a `PostRequest` whose ABI-encoded `Message.data` is non-empty but decodes to an invalid/unparsable `SubstrateCalldata` (or one whose `runtime_call` is filtered by `BaseCallFilter`).
3. Relay the request to `pallet_ismp`; `on_accept` mints/transfers the amount to `beneficiary` (lines 93-117 in `module.rs`), then fails while decoding/dispatching calldata, returning `Err`.
4. In `handlers/request.rs::handle`, observe the receipt for this request is deleted (`delete_request_receipt`, line 124) despite the mint having already occurred.
5. Resubmit the identical `RequestMessage` (same commitment, fresh valid membership proof) — `host.request_receipt` checks at lines 58 and 108 pass since no receipt exists, `on_accept` runs again, minting the same amount a second time and deleting the receipt again.
6. Repeat step 5 to demonstrate unbounded minting from one source-chain message.
