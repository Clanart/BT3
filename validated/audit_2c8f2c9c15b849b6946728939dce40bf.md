## Analysis

**Reduced bug-class from report:** an ERC20 `transfer` call whose `bool` return value is not checked. Some tokens don't revert on failure — they simply return `false`. Code that treats "call did not revert" as "transfer succeeded" will falsely mark a transfer as complete while the tokens never left the contract.

**Local analog found:** `evm/tron/contracts/apps/IntentGatewayV2.sol`. This contract imports and enables `SafeERC20` (`using SafeERC20 for IERC20;`) and uses `safeTransferFrom` elsewhere in the same file, but in the `withdraw()` function — the function that settles escrowed order funds on `RedeemEscrow`/`RefundEscrow` — and in the `SweepDust` branch of `onAccept`, it deliberately reverts to a raw low-level call and only checks that the *call itself* didn't revert, never decoding/validating the returned boolean: [1](#0-0) [2](#0-1) 

### Title
Non-boolean-checked ERC20 `transfer` in `IntentGatewayV2.withdraw()`/`SweepDust` allows escrow to be marked settled while funds remain stuck - (evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` (invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` messages) and the `SweepDust` branch both settle ERC20 legs with `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`, checking only that the low-level `call` succeeded, not that the ABI-decoded return value is `true`. [3](#0-2)  A non-reverting-on-failure ERC20/TRC20 (returns `false` instead of reverting) causes `success` to be `true` even though no tokens moved, while the code proceeds to decrement `_orders[...]` and mark `_filled[...] = beneficiary`, emitting `EscrowReleased`/`EscrowRefunded` as if settlement occurred. [4](#0-3) 

### Finding Description
The Tron variant of `IntentGatewayV2` imports OpenZeppelin's `SafeERC20` and declares `using SafeERC20 for IERC20;`, and does use `safeTransferFrom` for inbound escrow deposits elsewhere in the same file. [5](#0-4)  However, the outbound settlement path in `withdraw()` — which pays the order beneficiary the escrowed input tokens on refund, and pays out escrowed fee tokens — bypasses `safeTransfer` in favor of a manual low-level call whose only guard is `if (!success) revert TransferFailed();`. `success` here reflects whether the target contract's code executed without reverting, not whether the ERC20's own success semantics (the returned `bool`) indicate the transfer actually happened. Any token that signals failure by returning `false` (rather than reverting) — a well-documented ERC20 non-conformance class, and one that is not unusual among TRC20/Tron-native tokens this contract is deployed to support — passes this check unconditionally.

Once `success` is `true`, the function immediately does `_orders[body.commitment][token] -= amount;` and sets `_filled[body.commitment] = beneficiary`, and for the `SweepDust` case emits `DustSwept`. [6](#0-5)  There is no re-check of `token.balanceOf` before/after, unlike the deposit-side accounting used elsewhere in the same contract (e.g. `IntentGatewayV2.sol` on EVM measures `balancesBefore`/`balanceOf` deltas around dispatcher transfers). The corrupted value is the escrow ledger entry `_orders[commitment][token]` and the terminal state `_filled[commitment]`: both get finalized to "paid out" while the actual token balance held by the contract for that token is unchanged.

### Impact Explanation
This is a genuine fund-loss/fund-lock bug matching the report's bug class: escrowed tokens become permanently stuck in `IntentGatewayV2` because the on-chain accounting (`_orders`, `_filled`) is finalized as settled, so there is no retry path — `RedeemEscrow`/`RefundEscrow` for that commitment cannot be replayed since `_filled[commitment]` is already set and `_orders[commitment][token]` has already been decremented. The beneficiary never receives the funds, and the tokens are unrecoverable through the normal protocol flow.

### Likelihood Explanation
Low-to-moderate: it requires an order to use, as one of its escrowed `inputs`/fee tokens, an ERC20/TRC20 that returns `false` on failed transfer instead of reverting. Token selection for `order.inputs` is attacker/solver-controlled at order-creation time (no allowlist enforcement visible in this snippet), so a solver or order creator can deliberately pick such a token to trigger the stuck-funds condition without needing any privileged role, malicious relayer, or forged proof — the `onAccept` path is reached through normal, correctly-authenticated cross-chain messages via `authenticate(incoming.request)`. [7](#0-6) 

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept` with `IERC20(token).safeTransfer(beneficiary, amount)`, consistent with the `SafeERC20` usage already present in the rest of the file (`using SafeERC20 for IERC20;` is already declared, so this is a drop-in fix).

### Proof of Concept
1. Deploy/select a TRC20/ERC20 token whose `transfer()` returns `false` on failure instead of reverting (e.g., a token with insufficient allowance/balance-check design like the historical `ZRX` pattern, or any custom token deployed by the attacker).
2. Create an intent `Order` using this token as an input, escrowing funds into `IntentGatewayV2` on the source chain.
3. Trigger a refund flow (order not filled by deadline) so a `RefundEscrow` `WithdrawalRequest` is dispatched back to source and delivered via `onAccept` → `withdraw(body, true)`.
4. Have the token's `transfer` return `false` (e.g., because the contract's balance was drained through some auxiliary path, or the token is designed to fail silently under a specific condition the attacker controls).
5. Observe: `success` is `true` (call didn't revert), `_orders[commitment][token]` is decremented to zero, `_filled[commitment]` is set, and `EscrowRefunded` is emitted — yet `beneficiary`'s token balance is unchanged and the tokens remain stranded in `IntentGatewayV2` with no further ledger path to reclaim them. [8](#0-7)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
