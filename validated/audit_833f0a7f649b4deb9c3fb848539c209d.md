### Title
Unguarded fee-refund transfer in `EvmHost.dispatchTimeOut()` lets a single blacklisted/hostile fee payer revert an entire batched timeout delivery, blocking refunds/escrow release for all other bundled requests - (File: `evm/src/core/EvmHost.sol`)

### Summary
`HandlerV2.handlePostRequestTimeouts()` and `HandlerV2.handleGetRequestTimeouts()` iterate over an array of independent, unrelated timed-out requests and call `host.dispatchTimeOut(...)` for each one inside a single external transaction [1](#0-0) , [2](#0-1) . Inside `EvmHost.dispatchTimeOut()`, after the destination app's `onTimeout` callback succeeds, the fee refund to the *original request payer* is sent with a plain `safeTransfer` that is **not** wrapped in a success check the way the app callback itself is [3](#0-2) , [4](#0-3) . If `feeToken()` is a blacklist-capable token (e.g. USDC) and the request's recorded `meta.sender` (fee payer, freely chosen at dispatch time by whoever created the original request) is blacklisted — or is a malicious ERC777-style contract that reverts on receipt — this `safeTransfer` reverts unconditionally and permanently. The revert propagates out of `dispatchTimeOut`, out of the `for` loop in `handlePostRequestTimeouts`/`handleGetRequestTimeouts`, and reverts the *entire* handler transaction, including all other unrelated requests' timeout processing (and any escrow refunds / app-level state changes those other timeouts would have completed) that a relayer bundled into the same call for gas efficiency.

### Finding Description
`dispatchTimeOut` for both `PostRequestTimeout` and `GetRequestTimeout` follows this pattern:
1. Delete the request/response commitment (replay protection).
2. Low-level `.call` into the destination app's `onPostRequestTimeout`/`onGetTimeout`. If this call fails, the commitment is *restored* so the timeout is retryable — this failure path is properly isolated.
3. If the app callback succeeds, unconditionally `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` to refund the relayer/fee-payer — no success check, no isolation. [3](#0-2) 

Because `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts` process a caller-supplied array of timeouts in a single loop and call `dispatchTimeOut` for each entry without a try/catch, a revert on step 3 for *any single entry* aborts the whole array's processing: [5](#0-4) 

This is structurally identical to the reported `UFarmPool.quexCallback()` bug: many independent operations (there: deposit/withdraw requests; here: independent cross-chain timeout deliveries for different apps/users) are batched into one atomic transaction, and a single poisoned recipient (blacklisted USDC address, or malicious token hook) makes the entire batch revert instead of failing only for the poisoned item. The protocol clearly recognizes this exact failure class and defends against it elsewhere — e.g. `EvmHost.dispatchIncoming(PostRequest, ...)` explicitly comments "instead of reverting the entire batch, early return here" and wraps the app call in a low-level `.call` with a success check [6](#0-5)  — but the fee-refund transfer inside `dispatchTimeOut` was left unguarded.

### Impact Explanation
`meta.sender` (the fee payer recorded when the original request was dispatched) is attacker-controllable: any account/app can dispatch a request whose fee payer is an address the attacker later gets blacklisted by USDC (or a contract with a reverting `tokensReceived`/`receive` hook if a non-standard fee token is configured). Once that request times out, any relayer batching this timeout together with unrelated timeouts for other apps/users in the same `handlePostRequestTimeouts`/`handleGetRequestTimeouts` call will have their entire transaction revert. This:
- Blocks fee refunds and blocks the timeout-triggered escrow refunds/state transitions of completely unrelated users bundled in the same batch (e.g. `IntentGatewayV2`/`IntrinsicIntents` cross-chain refund-on-timeout flows depend on `onPostRequestTimeout` succeeding, and its effects get bundled with this fee-refund step).
- Is a pure griefing/DoS vector reachable by an unprivileged attacker with no special relayer, prover, or admin capability — only the ability to dispatch one cheap self-poisoned request.
- Matches the bounty's "logic attacks"/timeout-handling class: request/timeout paths are supposed to isolate per-item state, but this shared-transaction failure mode breaks that isolation for every relayer batch containing the poisoned entry, indefinitely (since the blacklist status doesn't change on retry, the batch will keep failing until the poisoned entry is manually excluded).

### Likelihood Explanation
Relayers batch timeouts for gas efficiency (the codebase's own `HandlerV2.batchCall`/`tesseract` messaging client documents and optimizes for exactly this batching behavior [7](#0-6) ), so multiple independent timeouts frequently land in one transaction in production operation. Triggering the bug requires only: (1) dispatch any request whose `fee` is non-zero and whose `payer`/`meta.sender` is an address the attacker controls and can get blacklisted (or is itself a hostile receiving contract), and (2) let it time out. No relayer, prover, governance, or admin collusion is needed.

### Recommendation
Wrap the fee-refund transfer in both `dispatchTimeOut` overloads (and the analogous fee-reward transfer in `dispatchIncoming(GetResponse, ...)`) in a low-level call with a success check, mirroring the pattern already used for the app callback: on transfer failure, either skip the refund (losing only that batch item's fee, not the whole tx) or leave the fee outstanding/claimable via a separate pull-based mechanism, so a single poisoned recipient cannot revert unrelated entries processed in the same handler call.

### Proof of Concept
1. Deploy/host a fee token that is USDC (or configure `feeToken()` to point at USDC on the target `EvmHost`).
2. From any app/account, dispatch a GET or POST request with `fee > 0` and `payer = attackerAddr` (an address the attacker controls) via the normal `IDispatcher.dispatch` flow.
3. Get `attackerAddr` added to USDC's blacklist (attacker's own address — fully self-controlled precondition, no privileged actor needed).
4. Let the request time out (destination/host chain natural expiry).
5. Wait for (or induce, since relayers batch for gas efficiency) a relayer to submit `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts` containing both the attacker's timed-out request and other legitimate users' timed-out requests in the same call.
6. Observe: `EvmHost.dispatchTimeOut` reaches `IERC20(feeToken()).safeTransfer(attackerAddr, meta.fee)` [8](#0-7) , which reverts due to the blacklist; this reverts the whole `handleGetRequestTimeouts`/`handlePostRequestTimeouts` call, and none of the bundled requests — including unrelated legitimate users' timeout-triggered refunds — get processed, indefinitely, until the relayer manually excludes the poisoned entry.

     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls

    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});

    function dispatchTimeOut(

    }
