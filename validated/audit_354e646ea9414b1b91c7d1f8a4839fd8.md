PedPoP blame proof leaks the ECDH shared key for a message whose proof-of-possession was never verified, letting any participant decrypt another party's encrypted secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The Froxlor report describes an API returning secret fields (password hashes, TOTP seeds) that were never meant to leave the server. The analog in Serai is the PedPoP DKG blame path: `KeyMachine::calculate_share` in `crypto/dkg/pedpop/src/lib.rs` returns an `EncryptionKeyProof` containing the raw ECDH shared point (`enc_key_recipient * msg.key`) for a malformed secret-share message **before** the per-message Schnorr proof-of-possession (`pop`) is ever verified. The PoP exists precisely to prevent this disclosure (the code comments say so explicitly), but because PoP verification is deferred into a `BatchVerifier` that is abandoned on the early-error path, the blame "response" contains secret key material the sender was never authorized to obtain. A malicious DKG participant can copy the ephemeral `key` field out of an honest party's encrypted share message addressed to the victim, wrap it in a message with a non-canonical share body, and receive the ECDH key needed to decrypt the honest party's real ciphertext — recovering their secret share.

### Finding Description
`Encryption::decrypt` in `crypto/dkg/pedpop/src/encryption.rs` (lines 469-501) does two things: it queues `msg.pop` for *batch* verification (`msg.pop.batch_verify(...)`), and it unconditionally computes `key = ecdh::<C>(&self.enc_key, msg.key)` and returns an `EncryptionKeyProof { key, dleq }` alongside the decrypted bytes. The batch statement is only verified later in `KeyMachine::calculate_share` via `batch.verify_with_vartime_blame()` at line 493.

In `calculate_share` (`crypto/dkg/pedpop/src/lib.rs`, lines 476-492), the decrypted `share_bytes` are converted with `C::F::from_repr`. If the bytes are not a canonical scalar, the function immediately errors:

```rust
let share = Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
})?);
```

This `?` exits before `batch.verify_with_vartime_blame()` is reached, so the queued PoP statement for `l` is never checked. The returned `blame` — an `EncryptionKeyProof` whose `key` field is the point `enc_key_victim * msg.key` — is handed to the caller and, per `processor/src/key_gen.rs` (lines 419-425), serialized and broadcast in `ProcessorMessage::InvalidShare { blame: Some(...) }`.

This is the exact side effect the `pop` field was added to prevent. The comment on `EncryptedMessage` (encryption.rs, lines 84-88) states: if the PoP did not exist, Eve could copy Alice's message key `X` and trigger Bob to "reveal bX, revealing Alice's message to Bob." The PoP binds each `msg.key` to knowledge of its discrete log via `pop_challenge` (encryption.rs, lines 302-324), which hashes `context`, nonce, key, and **sender index**. Because the PoP is only batch-verified after share deserialization, an attacker who copies an honest sender's `key` (and therefore cannot forge a valid PoP for it) still receives `bX` on the `from_repr` failure path, defeating the mitigation.

Additionally, `msg.key` is fully attacker-controlled, so the victim's `decrypt` is effectively a static-ECDH oracle `P -> enc_key * P`, and `EncryptionKeyProof` reveals the result publicly with a DLEq proof that it is correct relative to the victim's published `enc_pub_key`. The cipher (`cipher::<C>`, encryption.rs lines 101-133) deterministically derives a ChaCha20 key from `context || shared_key.to_bytes()` with a fixed IV, so possession of the leaked point is sufficient to decrypt any ciphertext sent to the victim under that ephemeral key.

### Impact Explanation
An attacker participating in a DKG who obtains the victim's blame response recovers the ECDH shared secret for an arbitrary ciphertext addressed to the victim. By copying the `key` field of an honest party Alice's `EncryptedMessage` (which transits authenticated — but not necessarily confidential — channels) into a crafted share message with garbage body bytes, the attacker receives `EncryptionKeyProof.key = enc_key_victim * X`, re-derives the ChaCha20 keystream with the public `context`, and decrypts Alice's genuine ciphertext to obtain her `SecretShare` scalar for the victim. A threshold adversary who already controls some shares can thus accumulate additional honest parties' shares; collecting `t` shares total allows unilateral reconstruction of the group secret key, breaking the DKG's threshold security and enabling forged FROST signatures. This is key-share recovery reachable purely through bytes the attacker submits to `EncryptedMessage::read`/`calculate_share`.

### Likelihood Explanation
The attack requires the attacker to be a DKG participant (or able to inject a share message attributed to one) and to observe an honest encrypted-share ciphertext sent to the victim. The PedPoP documentation states shares are sent "over an authenticated channel," which guarantees origin integrity, not confidentiality; a malicious participant in a federated/relayed setting who can see ciphertexts (e.g., a coordinator routing per-recipient messages, or a shared broadcast medium) satisfies this. The crafted message needs only a copied point, any `pop` (it is never checked on this path), and a non-canonical 32-byte body — trivially constructible. The disclosure is deterministic, not probabilistic.

### Recommendation
Verify the message's `pop` (and hence the sender's knowledge of `msg.key`'s discrete log) **before** producing or releasing any `EncryptionKeyProof`. Concretely:

- In `Encryption::decrypt`, verify `msg.pop` eagerly (or on a dedicated pre-check batch that completes before ECDH), and only compute/return the `EncryptionKeyProof` once the PoP is known-valid; or
- In `calculate_share`, when `from_repr` fails, run the queued batch verification first and only attach `blame` if `BatchId::Decryption(l)` was not the failing statement; or
- Have `decrypt` return the proof only on a success path, moving blame-proof generation behind an explicit, PoP-gated step so the ECDH result is never emitted for unauthenticated `msg.key` values.

### Proof of Concept
Setup: `t-of-n` PedPoP DKG, context `ctx`. Attacker is participant `M`; victim `V` publishes `enc_pub_key_V` in its `EncryptionKeyMessage`. Honest participant `A` sends `V` an `EncryptedMessage` `E_A = { key: X, pop: σ_A, msg: C_A }` where `X = xG` and `C_A` is Alice's share encrypted under `k = H(ctx, x·enc_pub_key_V)`.

1. Attacker observes `E_A` (it carries no per-recipient authentication in the payload itself). Attacker constructs `E_M = { key: X, pop: garbage_sig, msg: [0xFF; 32] }` — `0xFF..` is guaranteed non-canonical for all supported fields — and submits it as its share to `V`.
2. `V` runs `calculate_share`. `encryption.decrypt` queues `E_M.pop` under `BatchId::Decryption(M)` (unverified) and returns `(decrypted_garbage, EncryptionKeyProof { key: enc_key_V * X, dleq })`.
3. `C::F::from_repr([0xFF; 32])` → `None` → `calculate_share` returns `PedPoPError::InvalidShare { participant: M, blame: Some(proof) }`; the batch (and therefore the forged PoP) is never verified.
4. The blame is broadcast (`ProcessorMessage::InvalidShare`). Attacker reads `proof.key = enc_key_V * X = x · enc_pub_key_V` — the shared point Alice used.
5. Attacker recomputes `ChaCha20` from `cipher(ctx, proof.key)` (domain `"DKG Encryption v0.2"`, static IV `"DKG IV v0.2\0"`) and applies it to `C_A`, recovering Alice's `SecretShare` scalar for `V`.
6. Repeating per victim/sender, attacker accumulates shares beyond its own; at `t` distinct shares it interpolates the group secret key.

Note: the alternative variant — copying `E_A` wholesale so it decrypts to a valid share that then fails share-verification against the attacker's own commitments — does *not* leak, because `blame_vartime` returns the leftmost failing statement (`Decryption(M)` precedes `Share(M)`), yielding `blame: None`. The exploitable path is specifically the `from_repr` early return, which never consults the batch at all.
