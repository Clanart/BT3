### Title
Hookify hooks fail open on import/parse errors, causing deny rules to be silently bypassed - (File: `plugins/hookify/hooks/userpromptsubmit.py`, `plugins/hookify/hooks/pretooluse.py`, `plugins/hookify/hooks/posttooluse.py`, `plugins/hookify/hooks/stop.py`)

### Summary
All four Hookify hook executors wrap the entire rule-loading/evaluation pipeline in a `try/except Exception` that, on any failure (including `ImportError` at module load, or any exception raised inside `load_rules`/`RuleEngine.evaluate_rules`), prints only a `systemMessage` and unconditionally calls `sys.exit(0)`, which Claude Code interprets as "allow." This means any condition that raises before a blocking decision is computed converts what should be a `permissionDecision: deny` into a silent allow.

### Finding Description
Each hook (`userpromptsubmit.py:21-27`, `pretooluse.py:25-32`) first attempts `from hookify.core.config_loader import load_rules` / `from hookify.core.rule_engine import RuleEngine`; if `CLAUDE_PLUGIN_ROOT` is unset/wrong or the package layout is broken, the `ImportError` handler prints `{"systemMessage": ...}` and calls `sys.exit(0)` — no `hookSpecificOutput.permissionDecision` field is emitted at all, so Claude Code has no denial signal and the tool call proceeds. [1](#0-0) 

Even after import succeeds, `main()`'s runtime block (`pretooluse.py:37-70`, `userpromptsubmit.py:32-54`) catches **any** `Exception` from `load_rules()` or `engine.evaluate_rules()` and, again, only emits `systemMessage` before `sys.exit(0)` in the `finally` block, explicitly commented "ALWAYS exit 0 - never block operations due to hook errors." [2](#0-1) 

Because deny decisions are only produced by `RuleEngine.evaluate_rules` reaching the `blocking_rules` branch and returning `hookSpecificOutput.permissionDecision: "deny"`, any exception raised before that return (e.g., in `_extract_field`, `_check_condition`, malformed `Condition`/`Rule` construction, or a crafted `.claude/hookify.*.local.md` file that raises a `TypeError`/`AttributeError` not otherwise caught inside `config_loader.load_rule_file`) is swallowed by the outer `except Exception` in the hook script, and the process still exits 0 with no `permissionDecision` set — resulting in allow-by-default. [3](#0-2) 

The attacker precondition described (repository-controlled content reaching hook JSON via a normal PreToolUse/PostToolUse/Stop/UserPromptSubmit event) is consistent with how `tool_input` fields (e.g. `command`, `new_string`, `transcript`) are fed into `_extract_field`/`_check_condition` without type validation — a crafted tool_input value (e.g., non-string types where `.startswith`/`.endswith`/`in` are called) or an oddly-formed `.claude/hookify.*.local.md` rule file can trigger an exception path that reaches the outer generic exception handler instead of being turned into a `deny`. [4](#0-3) 

### Impact Explanation
If a blocking rule's condition path throws before `evaluate_rules` returns its `deny` response, or if the import bootstrap fails, the hook still exits 0 with no deny signal, so Claude Code proceeds to execute the tool call (e.g., a `Bash` command) that a hookify rule was meant to block. This is a fail-open design flaw that can degrade an intended local command/file-action block into an allow, matching "Unauthorized local command execution that bypasses Claude Code approval or deny controls."

### Likelihood Explanation
This is a design choice explicitly documented in code comments ("ALWAYS exit 0", "never block operations due to hook errors") rather than an accidental oversight — it is deterministic and repeatable any time an exception occurs during rule loading/evaluation, including via malformed `.claude/hookify.*.local.md` files or unexpected `tool_input` shapes, both of which are attacker/repo-controllable inputs feeding into `load_rules`/`RuleEngine`. However, without the actual Claude Code enforcement layer's fallback behavior visible in this repo, it's not confirmed here whether Claude Code core itself imposes any independent default-deny fallback if a hook emits no `permissionDecision` — this indexed codebase only contains the hookify plugin side, not Claude Code's hook-invocation runtime.

### Recommendation
Change the fail-open behavior to fail-closed for blocking-capable rule sets: on `ImportError` or evaluation `Exception`, emit an explicit `hookSpecificOutput.permissionDecision: "ask"` (or `"deny"`) with a clear `systemMessage` explaining the internal error, rather than silently exiting 0 with no decision. At minimum, narrow the broad `except Exception` blocks in `rule_engine.py`'s `_check_condition`/`_extract_field` call sites and `main()` in each hook script to catch specific, expected exceptions, and treat truly unexpected exceptions as a reason to deny/ask rather than allow, especially when any blocking rule for the current event/tool exists but could not be fully evaluated.

### Proof of Concept
1. Unit test `test_import_error_fails_open`: monkeypatch `sys.path` so `hookify.core.config_loader` cannot be imported (simulate `CLAUDE_PLUGIN_ROOT` misconfiguration), run `pretooluse.py` as a subprocess with stdin `{"tool_name": "Bash", "tool_input": {"command": "rm -rf /"}}`, and assert the process exits with code `0` and stdout JSON lacks `hookSpecificOutput.permissionDecision == "deny"` — confirming the dangerous command would be allowed.
2. Unit test `test_runtime_exception_fails_open`: create a `.claude/hookify.test.local.md` rule with `action: block`, `event: bash`, and a condition whose `field`/`operator` combination triggers a `TypeError` inside `_check_condition` (e.g., a crafted `tool_input.command` value of non-string type causing `.startswith` to throw), run `pretooluse.py` with that input, and assert exit code `0` with no `permissionDecision: deny` in stdout, proving the rule engine's internal crash suppressed the intended block.
3. Invariant assertion to add to CI: for every event type (bash/file/stop/prompt) and every exception path in `config_loader.py`/`rule_engine.py`, assert that if any enabled `action: block` rule exists for that event, hook stdout must contain `permissionDecision: deny` (or equivalent block signal) rather than falling through to an empty/allow response.

    def _check_condition(self, condition: Condition, tool_name: str,
                        tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> bool:
        """Check if a single condition matches.

        Args:
            condition: Condition to check
            tool_name: Tool being used
            tool_input: Tool input dict
            input_data: Full hook input data (for Stop events, etc.)

        Returns:
            True if condition matches
        """
        # Extract the field value to check
        field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
        if field_value is None:
            return False

        # Apply operator
        operator = condition.operator
        pattern = condition.pattern

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
        elif operator == 'contains':
            return pattern in field_value
        elif operator == 'equals':
            return pattern == field_value
        elif operator == 'not_contains':
            return pattern not in field_value
        elif operator == 'starts_with':
            return field_value.startswith(pattern)
        elif operator == 'ends_with':
            return field_value.endswith(pattern)
        else:
            # Unknown operator
            return False
