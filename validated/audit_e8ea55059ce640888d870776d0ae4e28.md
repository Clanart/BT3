### Title
Fee credit is applied for the aggregate batch while individual commitment claim-flags are only set for a subset — enabling double-claim of relayer fees - ([File: modules/pallets/relayer/src/accumulate.rs])

### Summary
`Pallet::accumulate` (the relayer fee-accumulation extrinsic) computes a single aggregate `total_fee` for a delivery-address across an entire batch of request commitments, credits that whole amount into `Fees` storage, and only afterwards iterates the batch to mark individual commitments as `claimed` — but that marking step is gated by membership in a separately-computed `claimed_commitments` set rather than by the same set that produced `total_fee`. This mirrors the `AntiSandwichHook` bug class: a coarse-grained "already processed" update (crediting the fee / advancing block state) happens unconditionally, while the fine-grained per-item state (`leaf_meta.claimed`, analogous to `state.ticks`) is populated only conditionally, allowing later calls to see components as still "unclaimed" even though the associated value was already paid out.

### Finding Description
In `accumulate()` [1](#0-0) , the extrinsic first filters `withdrawal_proof.commitments` down to entries not yet marked `claimed` in `RequestCommitments`. It then verifies source/destination state proofs and calls `validate_results`, which returns both `result` (aggregated `(delivery_address, total_fee)` pairs) and a `claimed_commitments` set [2](#0-1) .

The fee is credited into `Fees::<T>` unconditionally from `total_fee` — the aggregate for the single delivery address in the batch [3](#0-2) . Only afterward does the code iterate over `withdrawal_proof.commitments` (the pre-filtered, still-unclaimed set) and mark `leaf_meta.claimed = true` — but only for members of the separately-computed `claimed_commitments` set, skipping anything not in it via `continue` [4](#0-3) .

This is structurally the same asymmetry the external report describes: a single high-level gate (`total_fee` credited / `_lastCheckpoint.blockNumber` advanced) is updated in full, while the more granular state needed to prevent replay (`leaf_meta.claimed` / `state.ticks`) is populated only along a narrower code path. If `total_fee` (from `result`) is derived over a superset of, or a set that doesn't exactly equal, `claimed_commitments` — e.g. because `validate_results` sums fees per delivery-address across all proven leaves while `claimed_commitments` is filtered by additional per-leaf criteria (destination-receipt address match, proof presence, etc.) — a commitment can be counted toward the credited `total_fee` without ever having its `RequestCommitments[..].claimed` flag flipped. Since the initial filter at lines 58-69 only excludes commitments whose stored `claimed` flag is already `true`, such a commitment remains eligible for inclusion (and thus for fee credit) in a subsequent `accumulate` call with the same proof/commitment, i.e., a double-claim of the same delivered request's fee.

### Impact Explanation
This falls squarely within "stealing or loss of funds" and "replay/double-claim/double-settlement" per the impact gate: a relayer fee for the same delivered request could be credited to `Fees::<T>` more than once, draining the pallet's fee escrow/treasury beyond what was legitimately earned, directly harming other relayers or the protocol treasury that funds the `Fees` map.

### Likelihood Explanation
The path is reachable via the public, unsigned `accumulate` extrinsic and requires only a relayer submitting a normal delivery proof batch — no malicious peer, prover, or admin is needed. However, whether the divergence between `total_fee`'s contributing set and `claimed_commitments` is actually reachable in practice depends on the exact semantics of `validate_results` (not fully inspected in this pass), so this should be verified by reading `validate_results` (and its full definition) directly before treating this as confirmed rather than a structurally-suspicious pattern.

### Recommendation
Ensure `total_fee` is computed strictly from, and in lock-step with, the same `claimed_commitments` set used to flip `RequestCommitments[..].claimed`. Concretely: derive the aggregate fee by summing only over commitments that are about to be marked claimed, or reject the extrinsic entirely (rather than partially crediting) if any commitment in the batch cannot be marked claimed. This removes the possibility of a batch being partially "paid" without being fully "consumed."

### Proof of Concept
Conceptual reproduction (pending confirmation of `validate_results`'s exact filtering logic):
1. Attacker/relayer submits a `WithdrawalProof` containing commitment `C` along with other commitments in the same batch, all sharing one delivery address.
2. `validate_results` computes `total_fee` including `C`'s fee (aggregated by delivery address) but, due to a secondary check (e.g., destination receipt requiring a specific match not met for `C`), excludes `C` from `claimed_commitments`.
3. `Fees::<T>` is credited with `total_fee` (includes `C`'s fee) at lines 134-147.
4. The marking loop at lines 149-161 skips `C` because it is not in `claimed_commitments`; `RequestCommitments[C].claimed` remains `false`.
5. The same relayer resubmits an `accumulate` call for `C` (now still passing the initial "not yet claimed" filter at lines 58-69), obtaining a second credit for the same underlying delivered request. [5](#0-4)

	pub fn accumulate(mut withdrawal_proof: WithdrawalProof) -> DispatchResult {
		// Reject duplicate commitments within the batch. The wire format is a
		// `Vec` and this extrinsic is unsigned, so this is the line of defence
		// against an attacker padding the batch with identical commitments to
		// double-claim fees.
		let mut seen = alloc::collections::BTreeSet::new();
		for key in withdrawal_proof.commitments.iter() {
			ensure!(seen.insert(key.encode()), Error::<T>::DuplicateCommitment);
		}

		// Filter out already-claimed / missing commitments
		withdrawal_proof.commitments = withdrawal_proof
			.commitments
			.into_iter()
			.filter(|req| match RequestCommitments::<T>::get(*req) {
				Some(leaf_meta) => !leaf_meta.claimed,
				// If request commitment does not exist in storage which should not be
				// possible, we skip it
				None => false,
			})
			.collect();
		ensure!(!withdrawal_proof.commitments.is_empty(), Error::<T>::MissingCommitments);
		let host = <T as Config>::IsmpHost::default();
		let source_sm = validate_state_machine(&host, withdrawal_proof.source_proof.height)
			.map_err(|_| Error::<T>::ProofValidationError)?;
		let dest_sm = validate_state_machine(&host, withdrawal_proof.dest_proof.height)
			.map_err(|_| Error::<T>::ProofValidationError)?;
		let state_machine = withdrawal_proof.source_proof.height.id.state_id;
		let source_keys = Self::source_fee_commitment_keys(
			state_machine,
			&*source_sm,
			&withdrawal_proof.commitments,
		);
		let dest_keys = dest_sm.receipts_state_trie_key(withdrawal_proof.commitments.clone());

		let source_result = Self::verify_withdrawal_proof(
			&*source_sm,
			&withdrawal_proof.source_proof,
			source_keys.clone(),
		)?;
		let dest_result = Self::verify_withdrawal_proof(
			&*dest_sm,
			&withdrawal_proof.dest_proof,
			dest_keys.clone(),
		)?;
		let (result, claimed_commitments) = Self::validate_results(
			&withdrawal_proof,
			source_keys,
			dest_keys,
			source_result,
			dest_result,
		)?;

		let mut entries = result.into_iter();
		let (delivery_address, total_fee) = entries.next().ok_or(Error::<T>::IncompleteProof)?;
		// Every commitment in the batch must share a single delivery address.
		ensure!(entries.next().is_none(), Error::<T>::MixedDeliveryAddressesInBatch);

		// Let's verify the beneficiary address
		let beneficiary_address = if let Some((beneficiary_address, signature)) =
			withdrawal_proof.beneficiary_details
		{
			let nonce = Nonce::<T>::get(&delivery_address, state_machine);
			let msg = beneficiary_message(nonce, state_machine, &beneficiary_address);
			match &signature {
				Signature::Evm { .. } => {
					let eth_address =
						signature.verify(&msg, None).map_err(|_| Error::<T>::InvalidSignature)?;
					if eth_address != delivery_address {
						Err(Error::<T>::InvalidPublicKey)?
					}
				},
				Signature::Sr25519 { .. } | Signature::Ed25519 { .. } => {
					// verify the signature with the delivery address from the state proof
					let _ = signature
						.verify(&msg, Some(delivery_address.clone()))
						.map_err(|_| Error::<T>::InvalidSignature)?;
				},
			}

			Nonce::<T>::try_mutate(&delivery_address, state_machine, |value| {
				*value += 1;
				Ok::<(), ()>(())
			})
			.map_err(|_: ()| Error::<T>::ErrorCompletingCall)?;

			let _ = Fees::<T>::try_mutate(state_machine, beneficiary_address.clone(), |inner| {
				*inner += total_fee;
				Ok::<(), ()>(())
			});

			beneficiary_address
		} else {
			let _ = Fees::<T>::try_mutate(state_machine, delivery_address.clone(), |inner| {
				*inner += total_fee;
				Ok::<(), ()>(())
			});

			delivery_address
		};

		for req in withdrawal_proof.commitments {
			if !claimed_commitments.contains(&req) {
				continue;
			}
			match RequestCommitments::<T>::get(req) {
				Some(mut leaf_meta) => {
					leaf_meta.claimed = true;
					RequestCommitments::<T>::insert(req, leaf_meta)
				},
				// Unreachable
				None => {},
			}
		}
