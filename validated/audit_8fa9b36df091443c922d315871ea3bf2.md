### Title
`SchnorrAggregate::verify` accepts an "empty credential": a zero-signer aggregate signature deserializes and verifies as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The referenced bug class (CVE-2018-1000134) is a missing validation of an empty credential: the LDAP SDK's `SimpleBindRequest` accepted an empty password and produced an unauthenticated ("anonymous") bind, letting an attacker impersonate any valid user. The Serai analog is in `SchnorrAggregate`: the deserializer accepts an aggregate signature containing zero `R` values and `s = 0`, and `verify` then returns `true` for that aggregate against an empty signer/challenge list — a signature that `SchnorrAggregator::complete` can never honestly produce is accepted as authenticating "the signers".

### Finding Description
- `SchnorrAggregate::read` reads a `u32` length, loops zero or more times over `C::read_G`, and reads `s` via `C::read_F` — it performs no check that at least one signature is present, so the 36-byte encoding `00 00 00 00 || 00…00` (len = 0, s = 0) parses successfully. [1](#0-0) 
- `SchnorrAggregate::verify` only checks `self.Rs.len() == keys_and_challenges.len()`. With both empty, the pairs vector collapses to a single term `(-s, G)` = `(0, G)`, and `multiexp_vartime(&[(0, G)]).is_identity()` is trivially true, so `verify` returns `true`. [2](#0-1) 
- By contrast, the honest producer path refuses to emit this object: `SchnorrAggregator::complete` returns `None` when `self.sigs.is_empty()`. [3](#0-2) 
- The same "empty input accepted" asymmetry exists in `BatchVerifier`: an empty queue makes `verify`/`verify_vartime` return `true` (`multiexp` of nothing is identity), which is what makes the aggregate case exploitable at the verification layer. [4](#0-3) 

The reachable path for an unprivileged party is exactly the class allowed: untrusted bytes → `SchnorrAggregate::read` → `verify`. `read` accepts canonical-but-identity-adjacent encodings (it uses `C::read_G`, not the identity-rejecting `Curve::read_G` used by FROST). [5](#0-4) [6](#0-5) 

### Impact Explanation
`verify` returning `true` asserts "every listed key produced a signature bound by the listed challenge." With an attacker-supplied encoding of 36 zero bytes, that assertion is satisfied vacuously for a signer set the attacker caused to be empty — a forged aggregate signature, directly paralleling "valid username + empty password authenticates". Whether this translates to concrete authorization bypass depends on the consumer separately enforcing a non-empty/quorum signer set (e.g., weight accounting in the consensus layer); the cryptographic API itself claims success for a signature no signer produced.

### Likelihood Explanation
Exploitation requires a downstream caller that (a) feeds attacker-controlled bytes to `SchnorrAggregate::read`, (b) derives `keys_and_challenges` in a way that can be empty or attacker-aligned with `Rs`, and (c) treats `verify == true` as sufficient authorization without a separate non-emptiness/quorum check. The in-repo consensus consumer checks `signers.len() == aggregate.Rs().len()` but the emptiness/quorum gate lives outside this crate, so the primitive itself is the weak point. [7](#0-6) 

### Recommendation
- Reject `len == 0` in `SchnorrAggregate::read` (and/or return `false` early in `verify` when `Rs.is_empty()`), mirroring `SchnorrAggregator::complete`'s `None` on empty input.
- Consider rejecting identity `R` values and `s == 0` in `read`, and having `BatchVerifier::verify*` return `false` on an empty queue so "verified nothing" can never be reported as "verified".

### Proof of Concept
```rust
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ristretto;
use schnorr::aggregate::SchnorrAggregate;

// 36 zero bytes: len = 0, s = 0 — an aggregate SchnorrAggregator can never emit
let bytes = [0u8; 36];
let agg = SchnorrAggregate::<Ristretto>::read::<&[u8]>(&mut bytes.as_ref()).unwrap();

// Verifies "successfully" against an empty signer/challenge set —
// a signature no signer produced is accepted as valid.
assert!(agg.verify(b"dst", &[]));
```

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }
