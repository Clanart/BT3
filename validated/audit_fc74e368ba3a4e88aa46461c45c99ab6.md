## Title
Missing timestamp/deadline validation in App Proxy signature verification allows indefinite replay of signed requests - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` only checks that the HMAC signature over the query string matches; it never validates that the `timestamp` parameter included in that signed query string is recent. This is the same bug class as the AfEth report: a validly signed request/action has no deadline, so it can be captured and replayed at any point in the future while still passing verification.

### Finding Description
The app proxy verification concern computes an HMAC over all query parameters (including `timestamp`) and compares it against the `signature` parameter, but it does nothing with the `timestamp` value itself once verified — it is never compared to `Time.now` or checked for staleness: [1](#0-0) 

The signature is calculated purely from the sorted query params, with no deadline enforcement: [2](#0-1) 

This is confirmed by the gem's own test suite, which asserts that a request signed with `timestamp=1466106083` (year 2016) is still treated as valid today: [3](#0-2) 

Because Shopify signs the `timestamp` param as part of the app proxy request but `ShopifyApp` never checks it against the current time, any previously-issued signed app proxy URL/query string remains permanently valid — exactly analogous to the AfEth report where lack of a deadline check let a pending, validly-signed transaction be executed arbitrarily late with stale, attacker-favorable parameters.

By contrast, this repo does implement expiry checks elsewhere (e.g. `check_session_expiry_date` for OAuth/token-exchange sessions), showing the pattern is known and applied to sessions, but not to signed app proxy requests: [4](#0-3) 

### Impact Explanation
An app proxy request URL (with its query string and `signature`) that leaks — via browser history, referrer headers, shared links, server/CDN/proxy access logs, or network capture — can be replayed by any unrelated party at any later time and will still pass `verify_proxy_request`, since only the HMAC match is checked and never request freshness. For app proxy endpoints that perform state-changing or shop-context-sensitive actions based solely on this verification, this allows acceptance of a stale, forged-context signed request indefinitely, which matches the CSRF/replay category explicitly in scope (accepted forged signed request).

### Likelihood Explanation
Exploitation requires only that an attacker obtain one previously valid, legitimately-signed app-proxy query string (a request that already occurred) — no secret, no privileged access, and no code execution capability are needed. Because there is no timestamp freshness check anywhere in `AppProxyVerification`, replay works for any captured request regardless of age.

### Recommendation
Add a deadline check in `query_string_valid?` (or a dedicated before_action) that parses the `timestamp` query parameter and rejects the request if it is older than a configurable tolerance window (e.g. a few minutes), mirroring the mitigation pattern used for session expiry (`check_session_expiry_date`). Example:
```ruby
def query_string_valid?(query_string)
  query_hash = Rack::Utils.parse_query(query_string)
  signature = query_hash.delete("signature")
  return false if signature.nil?

  timestamp = query_hash["timestamp"].to_i
  return false if timestamp.zero? || Time.now.to_i - timestamp > ShopifyApp.configuration.app_proxy_timestamp_tolerance

  ActiveSupport::SecurityUtils.secure_compare(calculated_signature(query_hash), signature)
end
```

### Proof of Concept
1. Capture any legitimately signed app proxy request forwarded by Shopify to an app endpoint using `ShopifyApp::AppProxyVerification` (e.g. from server logs), noting its full query string including `timestamp` and `signature`.
2. At any later time — hours, days, or years later — replay the exact same query string to the same endpoint.
3. `query_string_valid?` recomputes the same HMAC over the same params and it matches, so `verify_proxy_request` allows the request through, as demonstrated by the existing test asserting a `timestamp=1466106083` signed request from 2016 still passes verification today: [3](#0-2) .

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
