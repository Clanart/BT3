### Title
Deserialized threshold keys can claim a victim participant while using a different secret share - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts a participant index and secret share independently, while `ThresholdKeys::new` derives the group key solely from the supplied verification shares and never checks that `G * secret_share == verification_shares[i]`. An attacker-controlled serialized key can therefore claim participant `i`/a victim group key while embedding an unrelated private share.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, and participant `i`, then independently parses `secret_share` and `verification_shares` before passing them to `ThresholdKeys::new`. [1](#0-0)  `ThresholdKeys::new` checks participant bounds and share count, then calculates `group_key` from the first `t` verification shares, but it never authenticates that the provided private share belongs to `params.i()`. [2](#0-1) 

During signing, `ThresholdView::view` uses the declared `params.i()` to interpolate the stored `secret_share`, producing a share attributed to the claimed participant even though it was never proven to be that participant's share. [3](#0-2)  This mirrors the external bug's confusion between an identifier used for authorization/indexing and a separately supplied object actually acted upon. [1](#0-0) 

### Impact Explanation
A crafted key can advertise an attacker-selected group key while containing a private share that cannot satisfy that key's verification share. Bitcoin key handling then derives spendable-looking Taproot keys from `group_key`, and `Scanner` registers the resulting script as belonging to the wallet. [4](#0-3) [5](#0-4)  Funds sent to those scripts are reported as received, but signing with the malformed `ThresholdKeys` produces shares inconsistent with the advertised participant and group key. [6](#0-5) [7](#0-6) 

### Likelihood Explanation
The attack requires only attacker-controlled bytes reaching `ThresholdKeys::read`, which is an explicitly reachable input path for imported or persisted key material. [8](#0-7)  A one-of-one serialization can set the lone verification share to a victim's public group key and use any unrelated scalar as `secret_share`; no knowledge of the victim's private key is needed. [9](#0-8) 

### Recommendation
In `ThresholdKeys::new`, reject keys whose private share does not correspond to the declared participant by requiring `C::generator() * secret_share == verification_shares[&params.i()]`. [2](#0-1)  This check must occur before storing the `ThresholdCore`, and deserialization should consequently fail for otherwise well-formed but semantically inconsistent key material. [10](#0-9) 

### Proof of Concept
Construct serialized `Secp256k1` `ThresholdKeys` with:

```text
curve_id_length = len(Secp256k1::ID)
curve_id        = Secp256k1::ID
t               = 1
n               = 1
i               = 1
interpolation   = Lagrange
secret_share    = attacker_random_scalar
verification[1] = victim_group_key
```

`ThresholdKeys::read` accepts this object because the participant index is nonzero and within `n`, while `group_key` becomes `victim_group_key` because that is the only verification share. [1](#0-0)  Since `attacker_random_scalar * G != victim_group_key`, every subsequent view derives a signature share under participant `1` that cannot satisfy the advertised group key. [11](#0-10) [12](#0-11)

      if id != C::ID {

      let mut read_u16 = || -> io::Result<u16> {
        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;
