### Title
`is_deposit_valid` accepts a `ReplacementDeposit` without verifying `old_move_txid`'s `DepositInMove` output was actually spent - (`core/src/verifier.rs`)

### Summary
`Verifier::is_deposit_valid` validates a `DepositType::ReplacementDeposit` purely by checking that the user-supplied `deposit_outpoint`'s on-chain output has the correct amount and taproot scriptPubkey (built from `ReplacementDepositScript(nofn_xonly_pk, old_move_txid)` + security-council multisig). It never checks that the `old_move_txid`'s `DepositInMove` output (`OutPoint{txid: old_move_txid, vout: UtxoVout::DepositInMove.get_vout()}`) has been spent, let alone spent by the transaction containing `deposit_outpoint`. An attacker can therefore self-fund an arbitrary, unrelated output matching that public, deterministic scriptPubkey and claim it "replaces" any real depositor's still-active move-to-vault UTXO.

### Finding Description
The binding that should hold is: `old_move_txid`'s `DepositInMove` output is spent by the transaction that funds `deposit_outpoint` (equivalently, `is_utxo_spent(OutPoint{old_move_txid, DepositInMove}) == true`, spent specifically as an input of the tx containing `deposit_outpoint`).

`is_deposit_valid` ( [1](#0-0) ) runs a sequence of checks for `ReplacementDeposit`, culminating in:
- Building `deposit_scripts` from `deposit_data.get_deposit_scripts()`, which for `ReplacementDeposit` only embeds `old_move_txid` into `ReplacementDepositScript` plus the security council multisig — no chain lookup of `old_move_txid` itself: [2](#0-1) 
- Deriving `expected_scriptpubkey` from those scripts and comparing it against the on-chain output at the attacker-supplied `deposit_outpoint`, and checking the amount equals `bridge_amount`: [3](#0-2) 
- Checking only the confirmation height of `deposit_outpoint`'s tx, then returning `Ok(())`: [4](#0-3) 

At no point is `is_utxo_spent` (or any equivalent check) called on `OutPoint{txid: old_move_txid, vout: UtxoVout::DepositInMove.get_vout()}`. The intended design (visible in the test helper `create_replacement_deposit_txhandler`/`send_replacement_deposit_tx`) is that a legitimate replacement-deposit transaction's *input* actually spends the old move's `DepositInMove` output, requiring either the old nofn signer set or the security council to authorize: [5](#0-4) [6](#0-5) . But `is_deposit_valid` never enforces this input structure — it only inspects the output at `deposit_outpoint`, whose scriptPubkey is fully computable from public data (`new_nofn_xonly_pk`, `old_move_txid`, and the public security-council keys). An attacker can construct any standard, self-funded transaction with an output of that exact scriptPubkey/value and submit it as `deposit_outpoint` via `new_deposit`, choosing any real, unspent `old_move_txid` M belonging to another depositor. `is_deposit_valid` passes, and verifiers presign a fresh move-to-vault flow for this bogus "replacement," believing it legitimately supersedes M.

### Impact Explanation
This is a real gap in `core/src/verifier.rs`: the on-chain enforcement that a replacement can only be created by consuming the old vault's actual UTXO is absent from the verifier's acceptance logic. The attacker gains verifier co-signatures on a "replacement" of a real, unrelated depositor's move-to-vault entry while that depositor's real `DepositInMove` output remains completely untouched (still locked under N-of-N/security-council control). If any downstream consumer (Citrea's `replaceDeposit` accounting, or bridge indexing state built from `get_replacement_deposit_move_txids`/`update_replacement_deposit_move_txid`) treats the presence of this presigned/committed replacement as authoritative proof that M has been replaced, M's genuine BTC becomes permanently unreachable through the intended flow, matching the "move-to-vault UTXO permanently frozen" Critical category. The attack is repeatable against every real, unspent `DepositInMove` output in the system (every legitimate depositor is a potential target) at essentially no cost beyond fee-paying dust to fund the bogus replacement-deposit output.

### Likelihood Explanation
Preconditions are trivial to satisfy: the attacker only needs knowledge of any real `old_move_txid` M (public on-chain data) whose `DepositInMove` output is unspent, and enough BTC to fund one taproot output of `bridge_amount` plus fees — no key shares, no cooperation from verifiers/operators/security council, and no privileged access. The scriptPubkey the attacker must construct is fully public/derivable (`ReplacementDepositScript` + security council `Multisig`, both public), so no guessing or brute force is needed. The call sequence (`new_deposit` → `is_deposit_valid` → presign) is exposed through the aggregator's public gRPC surface, per the existing `NewReplacementDeposit` CLI/RPC command.

### Recommendation
In `is_deposit_valid`'s `ReplacementDeposit` branch (`core/src/verifier.rs`, around line 660), before accepting the deposit, fetch the raw transaction containing `deposit_outpoint`, verify it has an input that directly spends `OutPoint{txid: old_move_txid, vout: UtxoVout::DepositInMove.get_vout()}`, and reject the deposit if no such input exists (or alternatively require `rpc.is_utxo_spent(...)` to be true and cross-reference the spending txid against `deposit_outpoint.txid`). This restores the intended binding that a replacement deposit can only be created by consuming the old vault's real UTXO.
