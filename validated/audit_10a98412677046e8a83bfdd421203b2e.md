### Title
Encrypted DKG shares are not bound to their recipient, letting an unprivileged party replay a share to frame an honest participant — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The external report describes endpoints that perform sensitive actions without authenticating the requester (CWE-862, missing authorization). The analog in Serai is the PedPoP per-message proof-of-possession: `pop_challenge` authenticates the `sender` of an `EncryptedMessage` but never binds the intended `recipient` (or the recipient's registered encryption key). Because the PoP is the only authentication gate checked before blame is evaluated, any party who observes a legitimately encrypted share can replay it to a different participant; that participant will fail to decrypt it and the blame procedure will conclusively identify the honest original sender as faulty.

### Finding Description
`encrypt` signs a Schnorr PoP over `pop_challenge::<C>(context, pub_nonce, pub_key, from, msg)` (encryption.rs:161-165, 302-324). The challenge commits to the context, nonce, per-message key, sender index, and ciphertext — but not to `to` (the recipient's encryption public key), even though `encrypt` has `to` in scope (encryption.rs:135-154).

Downstream, `KeyMachine::calculate_share` accepts a `HashMap<Participant, EncryptedMessage>` keyed purely by claimed sender and calls `encryption.decrypt`, which batch-verifies only this sender-bound PoP (lib.rs:476-490, encryption.rs:469-501). When the batch fails with a `BatchId::Share` fault, the victim produces an `EncryptionKeyProof` (their own ECDH key) enabling public decryption via `BlameMachine::blame` / `AdditionalBlameMachine::blame` → `decrypt_with_proof` (lib.rs:575-609, encryption.rs:366-397).

`blame_internal` attributes fault as follows:
- PoP invalid → sender faulty.
- PoP valid but decrypted bytes are not a canonical scalar or fail `share_verification_statements` → **sender faulty** (lib.rs:590-605).

A replayed message has a perfectly valid PoP (it genuinely came from Alice) but decrypts to garbage under Carol's key, so Alice — an honest participant — is deterministically blamed. In the processor, this maps to `ProcessorMessage::Blame { participant: accused }` for the replayed victim, a fatal misattribution (processor/src/key_gen.rs:504-563).

### Impact Explanation
An unprivileged observer of the DKG's public/authenticated channel (all encrypted shares are broadcast-visible ciphertexts) can take Alice's share-to-Bob and deliver it as Alice's share-to-Carol. Carol's `calculate_share` fails, she emits a blame proof, and every verifier — including the non-participant `AdditionalBlameMachine` (lib.rs:649-662) — concludes Alice is faulty. The result is erroneous attribution of fault to an honest participant (protocol abort and, in the processor, slashing of the wrong party), caused entirely by attacker-supplied public bytes. This is the missing-authentication class mapped onto Serai: a message is accepted as "authenticated for this context" when it was only ever authenticated for a different recipient.

### Likelihood Explanation
Any relay, coordinator, or fellow participant that routes the per-recipient share messages can perform the replay with zero secrets — the ciphertext and PoP are public, and the attack requires no forgery, only copying. The PoP explicitly claims to prevent key-co-option attacks (encryption.rs:83-91) but its challenge omits the recipient, leaving this replay variant open. Success is deterministic: decryption under a different ECDH key always yields invalid plaintext.

### Recommendation
Include the recipient's encryption public key (or participant index) in `pop_challenge` — e.g. `transcript.append_message(b"recipient", enc_keys[to].to_bytes())` — so a message is only valid for the party it was encrypted to. Additionally, `decrypt`/`decrypt_with_proof` could reject messages whose decryption key doesn't correspond to the callee's registered key before share decoding.

### Proof of Concept
1. Participants run PedPoP; Alice encrypts share `s_AB` to Bob: `Enc_{K_AB}(s_AB)` with `key = X`, `pop = SchnorrSign_x(challenge(context, R, X, Alice, ct))`.
2. Attacker relays `Enc` to Carol as Alice's share for her, keeping `from = Alice`.
3. Carol's `decrypt` batch-verifies the PoP — it passes, since sender/key/msg are all authentic.
4. Carol decrypts with `ecdh(enc_key_Carol, X)` → garbage; scalar decode or `share_verification_statements` fails → `PedPoPError::InvalidShare { participant: Alice, blame: Some(proof_Carol) }`.
5. `AdditionalBlameMachine::new(context, n, commitment_msgs).blame(Alice, Carol, Enc, proof)` runs `decrypt_with_proof`: PoP valid, DLEq valid for Carol's key, decrypted share invalid → returns `Alice` as faulty.
6. Alice is slashed despite never sending a malformed message.
