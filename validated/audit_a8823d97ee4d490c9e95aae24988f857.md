### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` keys causes stack-overflow DoS on tx submission - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes account-key data supplied by an unprivileged transaction sender without enforcing a nesting-depth limit before invoking the recursive decode path, analogous to the unbounded-recursion stack-overflow bug class described in CVE-2020-19464 (PDF2JSON `XRef::fetch`), where attacker-controlled recursive structures were parsed without depth checks.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of byte-encoded sub-keys and, for each entry, calls `rlp.DecodeBytes` into a fresh `AccountKeySerializer`, which in turn calls `NewAccountKey(serializer.keyType)` followed by `s.Decode(serializer.key)`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` performs the same generic pattern — decode a key type, construct the corresponding `AccountKey`, and decode into it: [2](#0-1) 

If the `keyType` is again `AccountKeyTypeRoleBased`, `NewAccountKey` produces a new `AccountKeyRoleBased`, and `s.Decode` re-enters `AccountKeyRoleBased.DecodeRLP`, recursing through Go's native call stack. Each `AccountKeyRoleBased` instance can itself hold multiple sub-keys (its encoding is `[][]byte`), so an attacker can craft an account key blob nesting `RoleBased` keys inside `RoleBased` keys inside `RoleBased` keys to an arbitrary depth, causing unbounded Go-stack recursion during RLP decoding.

The rejection of nested composite keys (`IsCompositeType()` check) only happens **after** decoding completes, inside validation routines such as `CheckInstallable`/`CheckUpdatable`: [3](#0-2) [4](#0-3) 

This means the recursive decode of a deeply nested structure fully executes — and can already overflow the stack — before the nested-composite-type rejection logic ever runs.

This decode path is reachable directly from an unprivileged transaction: `TxInternalDataAccountCreation.DecodeRLP`/`fromSerializable` and the fee-delegated account-update transaction types all decode an `AccountKeySerializer` from attacker-supplied `KeyData` bytes as part of standard RLP transaction decoding: [5](#0-4) [6](#0-5) 

Since transaction RLP decoding (`Transaction.DecodeRLP` → `TxInternalDataSerializer.DecodeRLP` → per-type `DecodeRLP`) happens on every submitted transaction — at the tx-pool admission stage (`AddRemote`/`AddLocal`) and again during block/consensus processing — a stack-overflow triggered here would crash (or at minimum abort) the node process handling the transaction, i.e., a straightforward Go crash from unbounded recursion (Go runtime `fatal error: stack overflow`, which is unrecoverable via `defer/recover`).

### Impact Explanation
A single crafted `TxTypeAccountCreation`, `TxTypeAccountUpdate`, or fee-delegated variant transaction, submitted via public RPC (`eth_sendRawTransaction`) or gossiped over the tx pool, can force any node that decodes it (tx-pool admission on every peer, and block-producing/validating nodes) to recurse arbitrarily deep through `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `NewAccountKey`/`s.Decode`. Because Go stack overflows are process-fatal and not recoverable, this can crash node processes network-wide as the transaction propagates — a availability/DoS impact consistent with the CWE-770 (uncontrolled resource consumption) classification of the referenced CVE.

### Likelihood Explanation
The trigger requires only constructing and RLP-encoding a nested `AccountKeyRoleBased` value with no valid signature requirements checked before decode — decoding happens before signature validation and before `CheckInstallable`. Any unprivileged party able to submit a raw transaction bytestream to a node's public RPC or the tx-pool gossip path can attempt this, making it directly and cheaply reachable by "an unprivileged transaction sender." Whether the recursion actually reaches native Go stack limits before other resource limits (e.g. RLP size limits, tx size caps) kick in is not fully verified in this review — the maximum RLP payload size for `KeyData`/transactions and any depth-limiting logic elsewhere in the RLP `Stream`/list decoder were not exhaustively confirmed to bound this recursion. This uncertainty should be validated experimentally (constructing a proof-of-concept encoded transaction) before treating the impact as fully proven.

### Recommendation
Enforce a maximum recursion/nesting depth for `AccountKey` decoding (e.g., pass and decrement a depth counter through `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP`, rejecting any `RoleBased` key found nested inside a `RoleBased` key at decode time — mirroring the already-existing `IsCompositeType`/`ErrNestedCompositeType` check) rather than only rejecting nested composite keys after the fact in `CheckInstallable`/`CheckUpdatable`. Alternatively, reject `AccountKeyTypeRoleBased` as an element type inside `AccountKeyRoleBased.DecodeRLP` immediately upon encountering it, before recursing into `s.Decode`.

### Proof of Concept
Conceptual construction (not independently executed in this review):
1. Build an `AccountKeyRoleBased` value `K0` containing ordinary keys.
2. Build `K1 = AccountKeyRoleBased{K0}`, encode via `NewAccountKeySerializerWithAccountKey(K1)` and `rlp.EncodeToBytes`.
3. Repeat, wrapping `K1` inside `K2 = AccountKeyRoleBased{K1}`, and so on for N iterations (N large, e.g. tens of thousands), producing deeply nested serialized `KeyData` bytes.
4. Embed the resulting `KeyData` into a `TxTypeAccountCreation` (or fee-delegated account-update) transaction and submit it via `eth_sendRawTransaction` or directly to `txpool.AddRemote`.
5. Expect the decode path `Transaction.DecodeRLP` → `TxInternalDataAccountCreation.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` (repeated N times) to exhaust the goroutine stack, triggering a fatal, unrecoverable stack-overflow crash of the node. func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (a *AccountKeyRoleBased) CheckUpdatable(newKey AccountKey, currentBlockNumber uint64) error {
	if newKey, ok := newKey.(*AccountKeyRoleBased); ok {
		lenOldKey := len(*a)
		lenNewKey := len(*newKey)
		// If no key is to be replaced, it is regarded as a fail.
		if lenNewKey == 0 {
			return kerrors.ErrZeroLength
		}
		// Do not allow undefined roles.
		if lenNewKey > (int)(RoleLast) {
			return kerrors.ErrLengthTooLong
		}
		for i := range lenNewKey {
			switch {
			// A composite key is not allowed.
			case (*newKey)[i].IsCompositeType():
				return kerrors.ErrNestedCompositeType
			// If newKey is longer than oldKey, init the new attributes.
			case i >= lenOldKey:
				if err := (*newKey)[i].CheckInstallable(currentBlockNumber); err != nil {
					return err
				}
			// Do nothing for AccountKeyTypeNil
			case (*newKey)[i].Type() == AccountKeyTypeNil:

			// Check whether the newKey is replacable or not
			default:
				if err := CheckReplacable((*a)[i], (*newKey)[i], currentBlockNumber); err != nil {
					return err
				}
			}
		}
		return nil
	}
	// Update is not possible if the type is different.
	return kerrors.ErrDifferentAccountKeyType
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
