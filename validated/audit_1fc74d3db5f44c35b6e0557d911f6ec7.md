### Title
`ThresholdKeys::read` allows attacker-controlled `n`/`t` to amplify parsing into quadratic CPU work via `ThresholdKeys::new`'s Lagrange interpolation - (File: crypto/dkg/src/lib.rs)

### Summary
The baggage-header bug class is "each item parsed is individually bounded, but the count of items is attacker-controlled, so total parse/alloc work is bounded only by the outer input budget." The direct Serai analog is `ThresholdKeys::<C>::read` in `crypto/dkg/src/lib.rs:574`, where `t`, `n`, and `i` are u16 fields read from untrusted bytes and used to drive loops of point deserializations — and, more importantly, a quadratic Lagrange interpolation in `ThresholdKeys::new`.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` directly from the byte stream (lines 591–602), then:

- For `Interpolation::Constant`, reads `n` scalar representations via `C::read_F` in a loop (lines 606–613).
- Reads `n` verification-share points via `C::read_G` in a loop (lines 620–623), each of which performs full point decompression/canonicity checking.
- Calls `ThresholdKeys::new`, which computes the group key as `t` evaluations of `interpolation_factor` (lines 376–378). For `Interpolation::Lagrange`, each `interpolation_factor(i, included)` call iterates over all `included` participants performing a field multiply and inversion accumulation (lines 229–247), making the group-key derivation O(t²) in field multiplications.

There is no cap on `n`/`t` beyond `u16::MAX` and the consistency check `t <= n` in `ThresholdParams::new` (lines 166–179). Each *individual* element parse is bounded (~32-byte scalar, ~32-byte compressed point), exactly like each individual `baggage` header value being within its 8192-byte cap — but the *aggregate* work is only bounded by the attacker-chosen u16 count. The super-linear component makes this worse than the linear baggage case: with `t = n = 65535`, `ThresholdKeys::new` performs on the order of 4×10⁹ field multiplications plus an inversion-per-element construction, triggered by an input of only ~4 MB. Additionally, `ThresholdView`-related interpolation (`view()`, lines 463–533) repeats the same per-participant O(|included|) `interpolation_factor` computation for every included signer, again O(n²).

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (e.g., any integrator deserializing key material or protocol messages embedding `ThresholdKeys`) can cause multi-second-to-worse CPU exhaustion and ~4 MB-of-input → gigabytes-scale intermediate work per call, a remote request-amplification DoS matching the CWE-400/CWE-770 class of the reference advisory. The allocation side (`Vec::with_capacity(n)`, HashMap of n points) is linear; the CPU side is quadratic, which is the dominant amplification.

### Likelihood Explanation
The trigger requires only choosing `interpolation = 1` (Lagrange) and large `t == n`; no valid keys, signatures, or protocol standing are needed — the work happens before/without any proof verification. Reachability depends on the integrator passing untrusted bytes to `ThresholdKeys::read`; the rules explicitly include `ThresholdKeys::read` among the untrusted-byte entry points. Caveat: within Serai's own processor/coordinator, `ThresholdKeys` are generally locally persisted rather than deserialized from peer bytes, so real-world exposure is integrator-dependent.

### Recommendation
Enforce a global budget rather than per-element bounds:

- Cap `n`/`t` at a protocol-realistic maximum (Serai validator sets are bounded well below `u16::MAX`; enforce that bound in `ThresholdKeys::read` before allocating).
- For `ThresholdKeys::new`, the O(t²) Lagrange group-key derivation can be reduced to O(t) by first computing the product of all included indices and dividing (multiplying by inverse of `(share - i)`) per participant, or by precomputing the full denominators via a single product tree. At minimum, document/enforce the quadratic cost bound.
- Alternatively compute group key incrementally without per-participant interpolation factors over the full set.

### Proof of Concept
Conceptual, standalone against `crypto/dkg`:

```rust
// Build a serialized ThresholdKeys blob with t = n = u16::MAX, Lagrange interpolation.
let mut buf = vec![];
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(u16::MAX.to_le_bytes()); // t
buf.extend(u16::MAX.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes());     // i
buf.push(1);                        // Interpolation::Lagrange
buf.extend(<C::F as PrimeField>::ONE.to_repr().as_ref()); // secret_share
for _ in 0 .. u16::MAX {
    buf.extend(C::generator().to_bytes().as_ref()); // valid point each time
}
// ~2.1 MB input → 65535 read_G decompressions + ~4.3e9 field multiplications
// inside ThresholdKeys::new's interpolation_factor loop.
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
```

Expected: parse time and work should be bounded by a small constant multiple of input size. Actual: quadratic Lagrange evaluation makes CPU cost grow as O(n²) while input grows as O(n), yielding unbounded amplification per input byte.
