### Title
`IntentGatewayV2._withdraw()` permanently stuck escrow when the beneficiary is a blacklisted/reverting ERC-20 recipient - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()`, invoked from `ExtrinsicIntents.onAccept()` for both `RedeemEscrow` (fill settlement) and `RefundEscrow` (cancellation) message kinds, releases escrowed input tokens to a hard-coded `beneficiary` address using `IERC20.safeTransfer`. If that transfer permanently reverts (e.g. `beneficiary` is blacklisted on a token like USDC/USDT, or is a contract that unconditionally reverts on `transfer`), the entire `onAccept` call reverts. `EvmHost.dispatchIncoming` treats any `onAccept` revert as "retry later" by deleting the request receipt, so the same message can be resubmitted indefinitely — but since the beneficiary and token are fixed by the immutable `Order`, every retry fails identically. The escrowed tokens remain permanently locked in the `IntentGatewayV2`/`ExtrinsicIntents` contract with no fallback path to redirect or recover them.

### Finding Description
`_withdraw()` iterates the withdrawal tokens and calls `IERC20(token).safeTransfer(beneficiary, amount)` unconditionally: [1](#0-0) 

`beneficiary` is decoded from the cross-chain `WithdrawalRequest.beneficiary`, which for `RedeemEscrow` is `msg.sender` (the solver) captured at fill time on the destination chain, and for `RefundEscrow` is `order.user`: [2](#0-1) [3](#0-2) 

Both request kinds are dispatched to `onAccept`, which calls `_withdraw` without any try/catch or fallback: [4](#0-3) 

On the host side, when `onAccept` reverts, `EvmHost.dispatchIncoming` explicitly deletes the request receipt "so that it can be retried": [5](#0-4) 

This retry design assumes failures are transient (e.g., temporary gas/liquidity issues), matching the documented invariant that a reverted `on_accept` allows replay so the source chain can eventually time out gracefully: [6](#0-5) 

However, this invariant breaks down for a **permanent** error: if the input token has blacklist logic (common in USDC/USDT-style tokens) and the solver or order user's address becomes blacklisted, or the beneficiary is a contract without a working ERC-20 receive path, `safeTransfer` will revert on every retry attempt forever. Unlike the timeout path, there is no mechanism analogous to `onPostRequestTimeout` here — `RedeemEscrow`/`RefundEscrow` messages are not standard ISMP-dispatched requests with a timeout on the destination gateway's `_withdraw` call; the message itself already succeeded in being delivered as a POST request (it's the internal call to `_withdraw` that fails). There is no admin/governance function that can change the beneficiary or manually release the specific escrowed tokens tied to a stuck commitment — the only privileged escrow-moving function is `_sweepDust`, which only sweeps protocol-owned dust balances, not tokens still tracked under `_orders[commitment][token]`: [7](#0-6) 

Because `_orders[commitment][token]` is only decremented inside `_withdraw` itself, and `_withdraw` never completes, the escrow balance sits permanently in the contract with no code path that can move it out.

### Impact Explanation
This falls under the accepted "stealing or loss of funds" impact category. Once a `beneficiary` address becomes non-transferable for a given input token (blacklisting is entirely outside the protocol's control and can occur at any time after order placement/fill), the user's or solver's escrowed principal is permanently locked in the `IntentGatewayV2` contract on the source chain, with no recovery mechanism whatsoever — worse than the original Stargate finding, which at least allowed governance-controlled `retryRevert()`.

### Likelihood Explanation
Medium: this requires a genuinely permanent failure condition (e.g., USDC/USDT blacklisting of the beneficiary address, or a beneficiary contract that always reverts on `transfer`/`transferFrom`), which is outside attacker control in most cases but is a realistic real-world occurrence for regulated stablecoins, matching the "permanent error" likelihood characterization in the original report.

### Recommendation
Wrap the token transfer(s) in `_withdraw()` in a try/catch (or use a low-level `call` and check return data) so a per-token transfer failure does not revert the whole withdrawal and does not block finalization/receipt storage. On failure, credit the amount to an escrow-style "pending withdrawal" balance for that `(beneficiary, token)` pair that the beneficiary (or anyone, paying to the beneficiary) can claim later via a separate `claim()` function once the token allows transfers again, or that governance can redirect via a `SweepStuckEscrow`-style privileged request bound to the specific commitment/beneficiary.

### Proof of Concept
1. User places a cross-chain order on the source chain using an input token with blacklist functionality (e.g., a USDC-like token), specifying themselves as `order.user`.
2. Order times out/never fills, and a `RefundEscrow` message is generated designating `order.user` as `beneficiary` — see `_cancelFromDest`: [8](#0-7) 
3. Before the refund message is relayed and processed, `order.user`'s address becomes blacklisted by the token issuer (independent external event).
4. The relayer submits the `RefundEscrow` POST request; `EvmHost.dispatchIncoming` calls `onAccept` → `_withdraw` → `IERC20(token).safeTransfer(beneficiary, amount)` reverts because the recipient is blacklisted.
5. `EvmHost.dispatchIncoming` catches the revert and deletes the request receipt, allowing indefinite resubmission: [9](#0-8) 
6. Every resubmission of the identical `RefundEscrow` message fails identically since the beneficiary and token never change. The escrow amount in `_orders[commitment][token]` is never decremented and there is no other function capable of releasing it — the funds are permanently stuck in the gateway contract.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

The request `handle` is used to notify onchain `IsmpModule`s of new requests to be processed. A relayer will construct the `RequestMessage` which holds a batch of new `PostRequest`s, as well as a _multi-proof_<sup>[1]</sup> of their existence on the source chain. The handler will perform the following operations

- Assert that the state machine's consensus client is not frozen
- Assert that the configured `challenge_period` for the `StateCommitment` has elapsed
- Assert that the requests have not been previously processed
- Assert that the requests have not timed out
- Assert that the membership proof for the requests verify
- Finally dispatch the requests to the relevant `IsmpModule::on_accept` and store a receipt for each request to prevent requests from being replayed.

<Callout title={'Danger'} type={"warn"}>
It's important to note that if the `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their request handler. This model ensures that if a request cannot be executed successfully on a destination state machine, it can time out gracefully on the source.
</Callout>
