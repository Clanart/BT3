### Title
Attacker-controlled allocation size in `ThresholdKeys::read` enables amplified memory exhaustion - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` in `crypto/dkg/src/lib.rs` trusts a serialized `n` (participant count) field and immediately calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` variant before a single byte of the claimed data is verified to exist. Because `n` is a `u16` fully controlled by the sender, a ~10-byte input triggers an allocation of `65535 × size_of::<C::F>()` (~2 MiB for 32-byte fields) — an amplification of roughly 200,000× per message. Like the BIND CVE (a small crafted query leaking resolver memory), a short untrusted payload here forces disproportionate memory consumption; repeated invocations exhaust process memory.

### Finding Description
In `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632):

1. The reader consumes the curve-ID header, then `t`, `n`, `i` as three `u16` values (lines 591-602). `n` is attacker-controlled and can be up to 65535.
2. The next byte selects the interpolation method. If it is `0` (`Interpolation::Constant`), the code executes `Vec::with_capacity(usize::from(n))` at line 608, unconditionally reserving space for `n` scalars *before* attempting `C::read_F(reader)` in the loop at lines 609-612.
3. If the stream then ends (the attacker sent nothing more), `read_F` errors, but the oversized allocation has already been performed. The allocator work and transient RSS spike are real even though the Vec is dropped on the error path.
4. The same `n` then drives the verification-shares loop at lines 620-623, which performs `n` calls to `C::read_G` — so a valid-but-padded input can also force up to 65535 group-element deserialization and `HashMap` insertions, all proportional to the declared count rather than to any protocol-meaningful bound.

`ThresholdKeys::read` is explicitly on the untrusted-bytes attack surface: it is invoked on serialized key material received from other participants and stored/loaded contexts where the bytes are not trusted a priori. No length bound is applied to `n` before allocation — contrast with `ThresholdParams::new(t, n, i)` validation which only runs *after* the allocations and reads complete (line 626).

### Impact Explanation
An unprivileged party able to feed bytes to `ThresholdKeys::read` (e.g., during DKG coordination, key recovery flows, or any path that deserializes peer-supplied `ThresholdKeys`) can send a ~10-byte prefix (`id_len` + `id` + `t`/`n=0xFFFF`/`i` + interpolation byte `0`) to force each call to allocate ~2 MiB. Issued repeatedly or in parallel, this produces memory pressure and OOM kills of the signing/DKG process — a remote, low-bandwidth denial of service against availability, directly analogous to the BIND memory-leak class (small input → disproportionate/persistent memory cost). It also forces up to 65535 `read_F`/`read_G` deserialization attempts per message, compounding CPU cost.

### Likelihood Explanation
Reachability is confirmed: `ThresholdKeys::read` is part of the enumerated untrusted-input surface, requires no authentication or privileged state, and the size field is read before any semantic validation (`ThresholdParams::new` bounds-checking happens after the allocation). Exploitation requires only sending the crafted prefix — no valid cryptographic material is needed since the allocation precedes the failing `read_F`. The 65535-element cap bounds per-call cost, so sustained traffic is required for OOM, making this a Medium-to-High availability issue rather than a single-request crash.

### Recommendation
Do not pre-allocate based on the untrusted `n`. Replace `Vec::with_capacity(usize::from(n))` with an incremental `Vec::new()` + `push` (bounded by actual bytes read), or validate `n` against `ThresholdParams` bounds (e.g., reject `n` exceeding a protocol maximum) *before* allocating. Apply the same pattern review to other readers that size allocations from untrusted length fields.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;
use dalek_ff_group::Ristretto;

// Crafted input: valid curve ID header, then t=1, n=0xFFFF, i=1, interpolation=0 (Constant)
let mut buf = vec![];
buf.extend(u32::try_from(<Ristretto as Ciphersuite>::ID.len()).unwrap().to_le_bytes());
buf.extend(<Ristretto as Ciphersuite>::ID);
buf.extend(1u16.to_le_bytes());      // t
buf.extend(0xFFFFu16.to_le_bytes()); // n = 65535 -> Vec::with_capacity(65535) ~ 2 MiB
buf.extend(1u16.to_le_bytes());      // i
buf.push(0u8);                       // Interpolation::Constant
// No scalar bytes follow: read_F errors, but the 2 MiB allocation already occurred.

let _ = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice());
// Repeat this call in a loop/concurrently: ~10 bytes in, ~2 MiB allocated per iteration,
// exhausting process memory without the attacker sending proportional data.
```
