## Title
Bandwidth purchase fees are permanently locked with no refund path when the pallet-side tier/manager registration lags the EVM-side price — (File: `evm/src/apps/BandwidthManager.sol`)

## Summary

## Finding Description
`BandwidthManager.purchase()` unconditionally pulls the buyer's fee token *before* any cross-chain confirmation that the purchase can be credited:

```solidity
IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);
...
commitment = IDispatcher(_host).dispatch(DispatchPost({..., timeout: 0, fee: 0, ...}));
``` [1](#0-0) 

The purchase message is dispatched with `timeout: 0`, and `pallet-bandwidth`'s `on_timeout` handler treats any timeout firing as an unrecoverable invariant violation rather than a refund path:

```rust
fn on_timeout(&self, _timeout: Request) -> Result<Weight, anyhow::Error> {
    Err(anyhow::anyhow!("pallet-bandwidth purchases are non-timeouting"))
}
``` [2](#0-1) 

On the destination side, `on_accept` requires both the manager registration (`BandwidthManager::<T>::get(&request.source)`) and a configured `TierConfig` (`Tiers::<T>::get(tier)`) to exist; if either lags behind the EVM-side manager's already-nonzero `tierPrice[tier]`, `on_accept` simply errors out and no `Subscription` is credited:

```rust
let cfg = Tiers::<T>::get(tier)
    .ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;
``` [3](#0-2) 

Governance sets prices/tiers on the two sides via *separate* transactions (`set_manager`, `set_tier` + `dispatch_set_tiers` on the pallet vs. the manager's own `SetTiers` `onAccept` handler), so there is an inherent window where the EVM manager's price for a tier is live (buyers can call `purchase()` successfully and pay) while the pallet has not yet finished registering the matching `TierConfig`/manager binding. The documentation itself acknowledges this bring-up sequencing: "Until every step lands, purchases fail" [4](#0-3) , and separately confirms tiers require "a coordinated upgrade of the pallet enum and the manager contract," implying they are not updated atomically [5](#0-4) .

Because the fee token is pulled into `BandwidthManager` at `purchase()` time regardless of destination-side readiness, and because the purchase message can never time out (`timeout: 0`, and `on_timeout` is explicitly not a refund path), any purchase that lands in this configuration-lag window results in fee tokens permanently stuck inside `BandwidthManager` with no bandwidth credited to the buyer, and no code path returns those funds to the buyer — the only egress for manager-held balances is the governance-only `dispatch_withdraw`, which pays out to an arbitrary `beneficiary` chosen by governance, not automatically or necessarily the original buyer.

This is the same broken invariant as the external report: a reward/credit computed against a snapshot/registration that does not yet exist at the time funds are collected causes those funds to be permanently unclaimable by the rightful party, with no built-in recovery mechanism.

## Impact Explanation
Buyer funds (the ERC-20 fee token) are permanently locked in `BandwidthManager` with no automatic or buyer-initiated recovery path — this is a direct loss of user funds. The only recovery is a privileged governance `dispatch_withdraw` call that can route the stuck balance to any beneficiary, not necessarily the original payer, so buyers have no guaranteed way to recover their payment.

## Likelihood Explanation
This does not require a malicious peer, relayer, or governance actor — it is triggered purely by the normal, documented bring-up sequence (deploy manager → bind host → register on pallet → configure tiers) combined with any ordinary buyer calling `purchase()` before all four steps have landed on both sides, or during any later asynchronous tier-price update where the manager's price update lands before the pallet's `TierConfig` update. Given governance updates the two sides via independent transactions/messages, this window is a realistic and repeatable operational condition, not a contrived edge case.

## Recommendation
- Make `purchase()` verify readiness before pulling funds, e.g., require the manager to know the destination pallet has already registered a matching tier (could be enforced via a two-phase confirm, or by never advertising a nonzero `tierPrice` locally until the pallet-side `TierConfig` is confirmed configured).
- Alternatively/additionally, give purchase messages a non-zero `timeout` and make the pallet's `on_timeout` actually refund by dispatching a credit-refund message back to the manager (paid to the original buyer address carried in the message body) instead of erroring as an "invariant violation."
- As a stopgap, add a buyer-callable escape hatch on `BandwidthManager` to reclaim funds for a purchase whose corresponding `BandwidthCredited` event never landed within some window, rather than relying solely on governance's `dispatch_withdraw`.

## Proof of Concept
1. Deploy `BandwidthManager` on the EVM chain and call `setHost`.
2. Governance calls `pallet-bandwidth::set_manager` to register the manager — but has **not yet** called `set_tier`/`dispatch_set_tiers` for tier `TierOne` on the pallet side; meanwhile (or in a later re-price cycle) the manager's owner already executed the `SetTiers` `onAccept` flow so `tierPrice[TierOne] != 0` on the EVM side.
3. A buyer calls `manager.purchase(app, TierOne, 1, chain)`. `tierPrice[TierOne] != 0`, so the call succeeds: `IERC20(feeToken).safeTransferFrom(buyer, manager, amount)` pulls the fee, and a `DispatchPost` with `timeout: 0` is sent to `pallet-bandwidth`.
4. On Hyperbridge, `on_accept` runs `Tiers::<T>::get(TierOne)`, finds `None`, and returns `Err("tier TierOne is not configured")`. No `Subscription` is credited, no `BandwidthCredited` event fires.
5. Because the request was dispatched with `timeout: 0`, it never times out, and even if it did, `on_timeout` unconditionally errors instead of refunding.
6. The buyer's fee tokens remain in `BandwidthManager` indefinitely. The only way to move them is governance's `dispatch_withdraw`, which can send them to any beneficiary — the buyer has no protocol-level path to reclaim the payment.

    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

        commitment = IDispatcher(_host).dispatch(
            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );

## The Tier Model

A tier is a `(bytes, duration_secs)` SKU on the pallet, paired with an 18-decimal price on the manager. Purchases scale both axes linearly by `months`:

```
allowance.bytes        = tier.bytes        × months
allowance.duration_secs = tier.duration_secs × months
allowance.expires_at    = block_time + allowance.duration_secs
allowance.cost          = tier.price × months   (18-decimal, scaled to fee-token decimals)
```

Tier discriminants are a closed enum on both sides — `TierOne` (1), `TierTwo` (2), `TierThree` (3), `TierFour` (4). Adding a tier requires a coordinated upgrade of the pallet enum and the manager contract; the wire format is just the `uint256` discriminant.

A tier is **unconfigured** until both sides have set it. The pallet rejects purchases against a tier without a `TierConfig`; the manager rejects purchases against a tier with a zero price.
```
