### Title
Unverified `MsgEVMTransaction.Derived` field lets a submitter forge the sender identity of an EVM transaction - (File: x/evm/ante/preprocess.go)

### Summary
`MsgEVMTransaction` carries an optional `Derived` field (`SenderEVMAddr`, `SenderSeiAddr`, `PubKey`) that is supposed to be populated *only* by the node itself after recovering the real signer from the wrapped Ethereum transaction's signature. `ValidateBasic()` and `PreprocessUnpacked()` only check that `Derived.PubKey` is non-nil; when `Derived` is already set with a non-nil `PubKey`, the code treats the message as "already preprocessed" and skips ECDSA signature recovery entirely, trusting the caller-supplied `SenderEVMAddr`/`SenderSeiAddr` at face value. This mirrors the Kong Mesh bug class: an identity claim (`kuma.io/workload` label / here, `SenderEVMAddr`+`SenderSeiAddr`) is validated against the actual credential (dataplane token binding / here, the tx signature) only in one code path, while an alternate, reachable path accepts the claim unconditionally.

### Finding Description
- `MsgEVMTransaction.ValidateBasic` only rejects a pre-set `Derived` if `PubKey == nil`; a non-nil (but arbitrary) `PubKey` passes: [1](#0-0) 
- `PreprocessUnpacked` short-circuits when `msg.Derived != nil` and `PubKey != nil`, explicitly commenting that this is the "already preprocessed" fast path, and returns without recovering the signer from the transaction's V/R/S at all: [2](#0-1) 
- Contrast with the legitimate path a few lines below, where `SenderEVMAddr`/`SenderSeiAddr` are derived cryptographically from `helpers.GetAddresses(V, R, S, txHash)`: [3](#0-2) 
- `MsgEVMTransaction.GetSigners()`/`GetSignBytes()` panic, meaning this message type is explicitly exempted from the standard Cosmos `SigVerificationDecorator` chain — signer authentication is delegated entirely to the EVM-specific ante pipeline: [4](#0-3) 
- The EVM ante chain that a `MsgEVMTransaction` is routed through does not include `ante.NewSigVerificationDecorator`; it relies solely on `EVMPreprocessDecorator` (which trusts pre-populated `Derived`) and `EVMSigVerifyDecorator` (which only checks nonce/chainID against whatever `Derived.SenderEVMAddr` says, not against a recovered signature): [5](#0-4) [6](#0-5) 
- Downstream, `BasicDecorator` and the EVM execution engine both key off `msg.Derived.SenderEVMAddr` as the authoritative sender for nonce bumping and fee/gas accounting: [7](#0-6) 

The net effect: an attacker who submits a raw `MsgEVMTransaction` protobuf directly (i.e., constructs a Cosmos `Tx` containing this message rather than going through the `eth_sendRawTransaction` JSON-RPC flow that always builds `Derived` from a real signature) can set `Derived.SenderEVMAddr`/`SenderSeiAddr` to any victim address while attaching a `PubKey` object of the attacker's choosing (any valid-looking pubkey satisfies the nil check) and a `Data` payload whose embedded V/R/S never gets checked against that claimed identity, because the "already preprocessed" branch never calls `helpers.GetAddresses`.

### Impact Explanation
If reachable, this allows an unprivileged transaction submitter to execute EVM calls (including value transfers, contract calls, and any state-mutating action) as if signed by an arbitrary victim account, without possessing that account's private key — a direct unauthorized-transfer / fund-loss primitive, matching the "unauthorized transfer" acceptance criterion.

### Likelihood Explanation
Likelihood depends entirely on whether the public gRPC/CheckTx broadcast surface accepts a raw, client-constructed `MsgEVMTransaction` (with `Derived` already populated) rather than requiring it to be built exclusively server-side from `eth_sendRawTransaction`. I was not able to fully verify within this session whether an external node input path (e.g., `broadcast_tx`, `CheckTx`, p2p mempool gossip of a Tx) permits a `Derived`-populated `MsgEVMTransaction` to enter `PreprocessUnpacked` from an arbitrary submitter versus `Derived` only ever being set internally by the node's own JSON-RPC transaction builder before being handed to the mempool. This gap needs to be closed by tracing every ingestion point of `sdk.Tx` (CheckTx/DeliverTx/ReCheckTx entrypoints and the EVM tx-pool/JSON-RPC submission code) to confirm whether external bytes can ever reach `PreprocessUnpacked` with `msg.Derived` already non-nil.

### Recommendation
Regardless of the current reachability, defense-in-depth is warranted: `PreprocessUnpacked` (and `EvmDeliverHandleSignatures`/`EvmCheckTxAnte`'s early-return-on-`Derived`) should never trust an externally-supplied `Derived` field without re-deriving and cross-checking `SenderEVMAddr`/`SenderSeiAddr`/`PubKey` against the actual signature bytes in `Data`. Concretely: only allow the "already preprocessed" fast path when the message originated from the node's own internal transaction construction (e.g., via a private, non-serializable flag / separate internal type), or always re-verify `helpers.GetAddresses(V,R,S,txHash) == Derived.{SenderEVMAddr,SenderSeiAddr,PubKey}` even when `Derived` is already set.

### Proof of Concept
Conceptual PoC (contingent on confirming external reachability of a `Derived`-populated message, see Likelihood section):
1. Craft an Ethereum-format transaction (`Data`) with an arbitrary/garbage signature (V/R/S do not need to recover to any particular address, since recovery is skipped).
2. Construct a `MsgEVMTransaction` with `Derived = {SenderEVMAddr: <victim_evm_addr>, SenderSeiAddr: <victim_sei_addr>, PubKey: <any valid pubkey bytes>, Version: <valid>, IsAssociate: false}`.
3. Wrap in a Cosmos `Tx` and submit via the node's transaction broadcast entrypoint.
4. If accepted, `PreprocessUnpacked` short-circuits at [8](#0-7) , `EVMSigVerifyDecorator` validates only nonce/chainID against the claimed `Derived.SenderEVMAddr` [9](#0-8) , and the transaction executes as the victim, moving/spending the victim's funds without their signature.

func PreprocessUnpacked(ctx sdk.Context, msgEVMTransaction *evmtypes.MsgEVMTransaction, chainID *big.Int, isBlockTest bool, txData ethtx.TxData) error {
	if msgEVMTransaction.Derived != nil {
		if msgEVMTransaction.Derived.PubKey == nil {
			// this means the message has `Derived` set from the outside, in which case we should reject
			return sdkerrors.ErrInvalidPubKey
		}
		// already preprocessed
		return nil
	}
