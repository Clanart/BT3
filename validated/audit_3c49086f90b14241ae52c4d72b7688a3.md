### Title
Deterministic FROST nonce reuse via `CachedPreprocesses` re-derivation enables secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`preprocess_internal` caches a 32-byte seed per `context` and deterministically regenerates the full FROST preprocess (including the secret nonces) from that seed on *every* invocation. `share_internal` calls `preprocess_internal` again rather than consuming a single-use machine, so any second signing operation under the same context re-derives the identical nonce pair. Two signature shares produced with reused nonces over different messages/binding factors allow any observer to algebraically recover the signer's private key share — the exact failure mode the codebase itself warns about ("Reuse will enable third-party recovery of your private key share", crypto/frost/src/sign.rs:85). Analogous to CVE-2025-67108's class: a credential whose validity must be revoked/single-use (the preprocess nonce) is accepted a second time, producing insecure communications.

### Finding Description
In `coordinator/src/tributary/signing_protocol.rs`, `preprocess_internal` stores an XOR-encrypted ChaCha seed under `CachedPreprocesses` keyed only by `self.context`:

- First call: `AlgorithmMachine::new(...).preprocess(&mut OsRng)` → `machine.cache()` → encrypted seed written to DB (lines 123–135).
- Every subsequent call for the same context: the cached seed is decrypted and `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))` is invoked (lines 137–145).

`from_cache` calls `seeded_preprocess`, which does `ChaCha20Rng::from_seed(*seed.0)` and feeds it to `Commitments::new` (crypto/frost/src/sign.rs:127–132). The hiding/binding nonces `d, e` are therefore a pure function of `(context, secret_share)`. Nothing deletes or rotates the cached seed after `sign` completes, and `share_internal` (line 156) reconstructs the machine from the cache on every share request.

Consequences:
1. If the same `context` is ever used to sign two distinct messages (e.g., a retried/attempted signing session where the message differs — block proposals, tributary TXs), the honest processor emits shares `s₁ = d + ρ₁e + c₁λxᵢ` and `s₂ = d + ρ₂e + c₂λxᵢ`. Since `d, e` are identical and `ρ, c, R` are public, anyone who sees both broadcast shares (a co-signer, the coordinator, or anyone reading the tributary data) solves the two-equation linear system for `xᵢ`, the FROST secret share.
2. Even absent a message change, a processor restart between the preprocess and share rounds rebuilds the identical machine (the code explicitly supports reboot rebuilding at lines 340–348 of processor/src/key_gen.rs for the DKG path, and the cache exists precisely for recovery). The nonce lifetime is therefore the lifetime of the DB entry, not the lifetime of a single signing attempt — the "single-use" requirement in crypto/frost/src/sign.rs:85 and spec/cryptography/FROST.md:51–55 is enforced by nothing in this layer.

The class maps exactly: like Fast-DDS accepting a revoked ticket, the signer accepts a *revoked* (already-consumed) preprocess as still valid, and produces a share with a reused nonce.

### Impact Explanation
Reuse of a FROST nonce across two different binding factors/challenges is standard share-recovery: given `s₁ − s₂ = (ρ₁ − ρ₂)e + (c₁ − c₂)λxᵢ` and the public bound-nonce identity `Rᵢ = Dᵢ + ρEᵢ`, an observer recovers `xᵢ`. Combined with `t − 1` colluding-free observations this degrades to key-share compromise of an honest validator's share — a critical confidentiality break enabling, with enough recovered shares, forgery of threshold signatures controlling bridged funds.

### Likelihood Explanation
The trigger is any second `share`/`preprocess` pass for the same `context` with different message bytes or binding factors — coordinator retry logic, session re-execution after crash recovery (which the caching mechanism was explicitly designed to support), or a duplicated coordinator message. The nonce reuse is deterministic, not probabilistic: the same seed always yields the same `d, e`. No malicious validator or leaked key is required; the re-derivation happens inside honest code whenever the context repeats.

### Recommendation
Bind the cached preprocess to a single signing attempt: include the message hash (and full participant set) in the cache key or in the seed derivation, and delete/burn the `CachedPreprocesses` entry once `sign` produces a share for that context. Alternatively, derive nonces as `H(seed ‖ msg ‖ included)` so identical seeds cannot produce identical nonces for different messages.

### Proof of Concept
Conceptual; no live test run available in this read-only analysis:

1. Context `C0` reused: call `share_internal(participants, preprocesses, msg_A)` then `share_internal(participants, preprocesses', msg_B)` with `msg_A != msg_B`.
2. Both calls hit `preprocess_internal` → `CachedPreprocesses::get(txn, &C0)` → same decrypted seed → `ChaCha20Rng::from_seed(seed)` → identical `nonces` vector (crypto/frost/src/sign.rs:127–132) → identical `Commitments` in `self.preprocess`.
3. The two emitted `SignatureShare`s satisfy `s₁ − s₂ = (c₁ − c₂)·λ·xᵢ + (ρ₁ − ρ₂)·e` (e recoverable from the public aggregate `R` equation `s·G = R + c·Y`), yielding `xᵢ` — the validator's private key share — from purely broadcast data.

Caveat: exploitability depends on `self.context` recurring across differing messages; the type is generic (`C: Encode`) and the caller that instantiates it was not fully traced in this analysis. The deterministic-reuse mechanism itself is unconditional and directly evidenced by the cited code.
