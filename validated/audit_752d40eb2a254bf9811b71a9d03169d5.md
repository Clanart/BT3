### Title
`ThresholdKeys::read` accepts attacker-controlled key material with no share/verification-share consistency check — the deserialized "data source" fully defines the group key and secret share - ([File: crypto/dkg/src/lib.rs])

### Summary
CVE-2023-31847 is a client trusting an attacker-controlled data source, which then drives secret-sensitive behavior on the client. The Serai analog is `ThresholdKeys::<C>::read`: every field that defines the threshold key — `t`, `n`, `i`, the interpolation coefficients, the `secret_share`, and every verification share — is taken verbatim from the input bytes, and `ThresholdKeys::new` validates only counts and index bounds. Nothing checks that `verification_shares[i] == G * secret_share`, that the shares interpolate to a consistent polynomial, or that the resulting `group_key` corresponds to any established multisig.

### Finding Description
`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) deserializes the curve ID, `t`/`n`/`i`, an `Interpolation` (Constant reads `n` attacker-supplied coefficients), the `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`). `new` enforces only:

- `verification_shares.len() == n`
- each participant index `<= n`
- `t == n` if Constant interpolation is used

It then computes `group_key` as the interpolated sum of `verification_shares[1..=t]` (lines 376-378). The provided `secret_share` is never verified against `verification_shares[i]` — Lagrange-interpolated verification shares are not checked against a commitment polynomial at all, since raw verification shares (not commitments) are what's stored.

The codebase itself acknowledges the consequence: `AlgorithmSignatureMachine::complete` in `crypto/frost/src/sign.rs:491-494` notes the only way "everyone had a valid share yet the signature was still invalid" is "to deserialize a semantically invalid FrostKeys" — i.e., the invariant is expected to be violated through this exact deserialization path.

An attacker who controls the serialized bytes (compromised key store, backup/coordinator-supplied key blob — the "data source" of the CVE analog) can therefore craft a `ThresholdKeys` where:

- `group_key` is an attacker-chosen key. With Lagrange interpolation the attacker picks any `x_j` for `j != i`, sets `verification_shares[j] = G * x_j`, sets `verification_shares[i]` arbitrarily, and the resulting `group_key` is fully attacker-determined (and its discrete log known to the attacker via the Constant-interpolation path, where `group_key = sum(c_j * vs_j)`-equivalent with attacker-known scalars).
- The victim's `secret_share` is inconsistent with `verification_shares[i]`. Every share the victim produces in FROST signing verifies against the attacker-chosen `verification_shares[i]` only if the attacker set it consistently with the planted `secret_share` (which they can, since they chose both); either way the victim is signing for a group key that is not the real multisig's key.

### Impact Explanation
Two concrete impacts:

1. **Key substitution.** The victim's `ThresholdKeys` reports an attacker-defined `group_key` via `group_key()` (line 445-447). Any component that uses these keys as "the" validator-set/multisig key will publish and operate under a key whose discrete log the attacker knows (attacker picks all shares in a `t = n` Constant interpolation, or picks `n-1` shares plus plants the victim's). Funds addressed to that group key are spendable by the attacker, not the threshold.
2. **Griefing / false blame.** Alternatively, setting `secret_share` inconsistent with the real network's verification shares makes the victim emit invalid FROST shares for the genuine group key; `complete` flags `InvalidShare(l)` and blame machinery attributes fault to the victim — an honest node can be blamed/slashed purely because its loaded key blob was corrupted.

### Likelihood Explanation
Reachable whenever serialized `ThresholdKeys` cross a trust boundary — restored from disk/backup, loaded from a DB populated during DKG, or received from a coordinator. The `read` API is public and performs no semantic validation, so any corruption (malicious or accidental) is silently accepted and only surfaces later as invalid signatures or misattributed blame. In the FROST signing flow the inconsistency is detected only at `complete`, where it is misattributed as an internal error / invalid share rather than a key-integrity failure.

### Recommendation
In `ThresholdKeys::new` (or `read`), verify `verification_shares[i] == C::generator() * secret_share` and, for `Interpolation::Constant`, that the coefficients are consistent with the verification shares (e.g., `vs_j == sum_k c_k * j^k * G` via `exponential`). At minimum, cryptographically bind the group key: store/derive `group_key` and check `verification_shares[1..=t]` interpolate to it, and consider authenticating serialized key blobs (MAC/signature) so an attacker-controlled source cannot substitute them.

### Proof of Concept
```rust
// Attacker crafts a blob accepted by ThresholdKeys::<Ed25519>::read for a victim
// with params t=2, n=3, i=1. Attacker chooses x1 (planted as victim share),
// x2, x3 known to attacker; sets vs_j = G * x_j for j=2,3 and vs_1 = G * x1.
// group_key = Lagrange-interpolated sum over vs[1..=2], fully attacker-determined.
let mut buf = vec![];
buf.extend(u32::try_from(Ed25519::ID.len()).unwrap().to_le_bytes());
buf.extend(Ed25519::ID);
buf.extend(2u16.to_le_bytes());                 // t
buf.extend(3u16.to_le_bytes());                 // n
buf.extend(1u16.to_le_bytes());                 // i = victim
buf.push(1);                                    // Interpolation::Lagrange
buf.extend(attacker_known_share.to_repr().as_ref()); // victim's secret_share
for vs in [vs1, vs2, vs3] { buf.extend(vs.to_bytes().as_ref()); }

// Succeeds: no check that vs_1 == G * secret_share, nor share consistency
let keys = ThresholdKeys::<Ed25519>::read::<&[u8]>(&mut buf.as_ref()).unwrap();
// keys.group_key() is now attacker-defined; attacker knows the discrete log.
```
