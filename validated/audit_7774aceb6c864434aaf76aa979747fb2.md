### Title
`WombatStaking._sendRewards` can permanently disable `harvest()`/deposit/withdraw for a pool if a fee/reward token reverts on zero-value transfers - (File: `wombat/WombatStaking.sol`)

### Summary
`WombatStaking._sendRewards()` computes a fee amount as a percentage of the freshly harvested reward and unconditionally transfers/queues that fee amount, without checking that the computed amount is non‑zero, mirroring the root cause of the referenced report (an unguarded zero-amount ERC20 transfer that reverts and blocks a core user-facing operation).

### Finding Description
`_sendRewards` iterates all active `feeInfos` and, for each one, computes:

```solidity
uint256 feeAmount = (originalRewardAmount * feeInfo.value) / DENOMINATOR;
_amount -= feeAmount;
uint256 feeTosend = feeAmount;
...
if (!feeInfo.isAddress) {
    IERC20(rewardToken).safeApprove(feeInfo.to, 0);
    IERC20(rewardToken).safeApprove(feeInfo.to, feeTosend);
    IBaseRewardPool(feeInfo.to).queueNewRewards(feeTosend, rewardToken);
} else {
    IERC20(rewardToken).safeTransfer(feeInfo.to, feeTosend);
    emit RewardPaidTo(feeInfo.to, rewardToken, feeTosend);
}
``` [1](#0-0) 

Unlike the top-level guard `if (_amount == 0) return;` [2](#0-1)  — which only protects against the *total* harvested amount being zero — there is no check that the per-fee `feeTosend` (or the mWOM-conversion-derived `feeTosend`) is non-zero before it is sent. If `feeTosend` rounds down to `0` (small `originalRewardAmount` relative to `DENOMINATOR`/`feeInfo.value`, or a near-zero `smartConvert`/`mWom.deposit` balance delta), the code still executes `safeTransfer(feeInfo.to, 0)` or `queueNewRewards(0, ...)`, which itself performs `safeTransferFrom(msg.sender, address(this), 0)` inside `_provisionReward` [3](#0-2) .

If the reward/bonus token or WOM/mWOM is (or is later swapped for) an ERC20 implementation that reverts on zero-value transfers, this single failed sub-transfer reverts the entire enclosing transaction, since `_sendRewards` is invoked from `_toMasterWomAndSendReward`, which itself is called from the permissionless `harvest()` function as well as from deposit/withdraw flows through the pool helpers [4](#0-3) [5](#0-4) .

This is exactly the same bug class as the report: an unguarded zero-amount transfer nested inside a mandatory step of a core, frequently-invoked user operation (stake/unstake/harvest), which reverts and blocks that operation for the affected pool when the underlying reward token disallows zero-value transfers.

### Impact Explanation
If triggered, every call to `harvest()`, every deposit, and every withdrawal on the affected pool (through `_toMasterWomAndSendReward` → `_sendRewards`) would revert as long as the harvested-reward-to-fee rounding keeps landing on zero, since the reverting fee transfer is unconditionally required for the transaction to succeed. This can freeze staking/unstaking/reward flows on that pool, which is a freeze-of-funds-class impact for users of that pool.

### Likelihood Explanation
Exploitability is highly dependent on protocol configuration that is not attacker-controlled: the reward/bonus token's decimals, the configured `feeInfo.value`, and whether any fee/reward token used actually reverts on zero-value transfers (a known "weird ERC20" behavior, not guaranteed for WOM/mWOM or protocol-selected bonus tokens). An attacker only fully controls the call timing (e.g., spamming permissionless `harvest()` to keep per-call harvested amounts small), not the exact reward amount, which comes from `MasterWombat`'s external accrual — unlike the original report where the attacker could fully drain the balance to exactly zero and then deposit a controlled dust amount, guaranteeing deterministic zero-fee rounding. For typical 18-decimal reward tokens and realistic fee percentages, forcing `feeAmount`/`feeTosend` to exactly `0` via harvesting timing alone is unreliable and not something guaranteed for every configuration. Because reliable, deterministic triggering by an ordinary wallet cannot be established without a specific token/fee configuration that isn't attacker-controlled, this weakens confidence that the analog meets the "concrete, reliably reachable" bar.

### Recommendation
Guard each fee sub-transfer/queue call with `if (feeTosend > 0) { ... }` (as is already consistently done elsewhere in the codebase, e.g. `if (protocolFee > 0)` and `if (callerFeeAmount != 0)` in `WombatStaking.vote` [6](#0-5) , and `if (toSend > 0)` in `mWOMSVBaseRewarder._sendReward` [7](#0-6) ), so a zero fee amount is simply skipped instead of attempted.

### Proof of Concept
Not independently verified against a live deployment/token configuration; the code path lacking the zero-value guard is shown above at `wombat/WombatStaking.sol:733-762` [8](#0-7) . Exploitation would require a configured fee/reward token that reverts on zero-value transfers plus reward-accrual timing small enough to round `feeAmount`/`feeTosend` to zero — conditions this analysis could not confirm are met by any concretely configured token in this codebase given index limitations.
