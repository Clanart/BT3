### Title
Vacuous torsion check in Ed448 `Point::from_bytes` accepts non-prime-order points, enabling Schnorr/DLEq proof forgery via reachable decoders - (File: crypto/ed448/src/point.rs)

### Summary
`crypto/ed448/src/point.rs` implements `is_torsion_free` as `((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()`. `Scalar::ZERO - Scalar::ONE` is `-1`, so the expression is `(-P) + P`, which is the identity for every point on the curve. The check is a no-op, and `GroupEncoding::from_bytes` therefore accepts any valid curve point — including the order-2 and order-4 torsion points present on Ed448 (cofactor 4) — while claiming to reject them. Untrusted bytes reach this decoder through `Ciphersuite::read_G` / `read_point`, which are invoked by `SchnorrSignature::read`, `DLEqProof::read`, `Commitments::read`, `EncryptedMessage::read`, and `ThresholdKeys::read`. Because Schnorr and DLEq verification equations are checked with exact point equality, a point with a torsion component `T` can be folded into a forgery whenever the challenge `c` is a multiple of `ord(T)`; since `c` is bound to attacker-chosen nonce bytes, the attacker grinds the nonce until `c ≡ 0 (mod ord(T))` — 2–4 trials on average.

### Finding Description
The defect is in `crypto/ed448/src/point.rs`:

```rust
impl Point {
  fn is_torsion_free(&self) -> Choice {
    ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
  }
}
```

`-P + P` is identically the identity, so `is_torsion_free` always returns `Choice(1)`. `GroupEncoding::from_bytes` (lines 303–319) gates acceptance on `not_negative_zero & point.is_torsion_free()`, so the torsion half of the gate is dead code. Compare with `crypto/dalek-ff-group/src/lib.rs` (lines 429–437), where the equivalent macro correctly parameterizes a real `$torsion_free` check for Ed25519.

Reachability: `Ciphersuite::read_G` in `crypto/ciphersuite/src/lib.rs` (lines 91–101) only enforces canonical re-encoding — it calls `G::from_bytes`, which for `Ed448` is this broken decoder — and `Curve::read_G` in `crypto/frost/src/curve/mod.rs` (lines 125–131) additionally rejects only the identity, not order-2/4 points. So a 57-byte encoding of, e.g., the order-2 point `(0, -1)`, or any prime-order point plus a torsion component, is accepted as a `PrimeGroup` element wherever Ed448 bytes are parsed from peers: PedPoP `Commitments::read` (`crypto/dkg/pedpop/src/lib.rs:115-127`), `EncryptedMessage::read` (`crypto/dkg/pedpop/src/encryption.rs:171-177`), `DLEqProof::read`, `SchnorrSignature::read`, `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:620-623` reads n verification shares from untrusted bytes), and `GeneratorProof::read` (`crypto/dkg/promote/src/lib.rs:72-77`).

### Impact Explanation
This breaks the `PrimeGroup` contract that all consumers assume: every `C::G` is supposed to have prime order `l`. Concretely, it enables forged Schnorr proofs of knowledge / DLEq proofs for statements that are false in the prime-order group. If a verifier accepts an Ed448 public key, verification share, or commitment `A = a'·G + T` (with `T` a non-identity torsion point) from untrusted bytes — which all of the `read_*` paths above now permit — the prover can satisfy `s·G = R + c·A` by selecting `R = r·G` with `c = H(R, A, m) ≡ 0 mod ord(T)` (grinding `r`, ~2 trials for `ord(T)=2`), then setting `s = r + c·a'`. The torsion term `c·T` vanishes, the equation holds, and the verifier accepts a proof for a "public key" that is not `x·G` for any `x` — i.e., a forged Schnorr signature/PoK or DLEq proof under an adversarially encoded key. In the DKG/PedPoP setting, a malicious participant can register commitments or verification shares carrying torsion components so that keys/proofs validate under Serai's decoder while being invalid under any torsion-rejecting implementation, breaking cross-implementation agreement on the group key and on proof validity.

### Likelihood Explanation
Requires a context where an attacker supplies Ed448-encoded points that are used as verification keys/commitments rather than just signatures. The decoding flaw is deterministic and the challenge grinding is trivially cheap (expected 2–4 hash iterations). The constraint that lowers severity is that the torsion must be embedded in an attacker-influenced key/commitment (torsion in `R` alone cannot be forged past the exact-equality check), and exploitation requires the surrounding protocol to accept attacker-chosen points via `read_G` — which PedPoP commitments, DLEq-based promotion proofs, and deserialized `ThresholdKeys` verification shares all do for in-scope Ed448 usage. Medium-High.

### Recommendation
Replace `is_torsion_free` with a real prime-order check, e.g. multiply by the group order `l` and require identity: `(self * Scalar::from(L)).is_identity()`, or equivalently check `4·P` has order dividing `l`/clear the cofactor and compare. The current `(*self * (Scalar::ZERO - Scalar::ONE)) + self` should never have been used — it can only return true. Additionally, add a `from_bytes` regression test feeding the order-2 point `(0,-1)` (y = p−1, sign = 0) and a `(prime point) + order-4 point` encoding, asserting rejection — the existing `torsion` test (`point.rs:352-368`) only exercises `is_torsion_free` on a manually constructed point and never tests the decoder path that actually enforces it.

use ed448::{Point, Scalar, F};

//    Encode y = p - 1, sign bit 0. from_bytes should reject it (torsion), but doesn't.

assert!(t2.is_some());            // BUG: accepted
assert!(!bool::from(t2.unwrap().is_identity())); // non-identity, order 2

// Also accepted by the higher-level decoders (reject only non-canonical/identity):
// <Ed448 as Ciphersuite>::read_G / Curve::read_G succeed on `enc`.
