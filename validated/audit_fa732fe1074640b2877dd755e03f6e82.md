## Title
Attacker-controlled `WWW-Authenticate` realm header spoofs GitHub host classification and triggers a real GitHub Enterprise OAuth sign-in flow against a malicious remote - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

## Summary
The credential-classification bug in the underlying report is really about a **security-relevant classification value that is derived from an untrusted/attacker-influenced signal and then used, without an independent origin check, to decide how much trust to extend**. In the Solidity report, the health-ratio constant is hardcoded and doesn't track the real, evolving LTV, so a check that's supposed to gate liquidation silently becomes too permissive. The closest concrete analog in GitHub Desktop is `getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts`, which decides whether a git remote should be treated as a GitHub/GitHub-Enterprise host (triggering Desktop's own sign-in UI) based partly on a `WWW-Authenticate` header that is **entirely attacker-controlled**, with no verification that the responding host is actually a GitHub product.

## Finding Description
When Git needs credentials for a remote, Desktop's trampoline credential helper calls `getEndpointKind()`: [1](#0-0) 

The comment itself acknowledges the trust assumption: *"When Git attempts to authenticate with a host it captures any WWW-Authenticate headers and forwards them to the credential helper. We use them as a happy-path to determine if the host is a GitHub host without having to resort to making a request ourselves."* If the header contains `realm="GitHub"`, the function returns `'enterprise'` — with **no check that the URL host is actually a `*.ghe.com`/GitHub-branded domain** (that check, `isGHE`/`isDotCom`, already happened earlier and failed). This branch is purely `WWW-Authenticate`-header driven, and that header is sent by whatever server the remote URL points to — i.e., fully controlled by the operator of an arbitrary HTTPS git remote.

That classification is then consumed in `getCredential()`: [2](#0-1) 

Because `endpointKind !== 'generic'` and no stored account matches this brand-new host, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, which — since the hostname isn't literally `github.com` — invokes `beginEnterpriseSignIn` and `setSignInEndpoint(origin)` with the **attacker's own origin**: [3](#0-2) 

`setEndpoint()` in the sign-in store then validates the URL is `https://` and proceeds directly to the `Authentication` step for that endpoint if there is no existing account collision: [4](#0-3) 

This surfaces a genuine "Sign in to your GitHub Enterprise" dialog inside GitHub Desktop, silently pre-populated with the attacker's host as the enterprise endpoint — the user never typed that URL themselves; it was injected purely from an HTTP response header on a fetch/push attempt.

## Impact Explanation
This is a phishing/credential-confusion primitive delivered entirely by a git remote/proxy response, which matches the accepted impact class ("attacker controls...a git remote/proxy response...result is...unauthorized OAuth or account binding"). The user is shown Desktop's own, trusted-looking GitHub Enterprise sign-in chrome, but the OAuth/basic-auth handshake that follows is directed at the attacker's server, not a real GitHub product. This can lead to:
- The user believing they are authenticating a legitimate "GitHub Enterprise" account inside Desktop, entering enterprise or PAT-style credentials that are captured by the attacker-controlled endpoint (`setEndpoint`/`beginEnterpriseSignIn` do not require any external verification that the target is truly a GitHub Enterprise instance beyond scheme = `https`).
- An `Account` object being bound in Desktop for a host that is not actually GitHub, potentially confusing later credential-fill logic that trusts previously-created accounts (`findGitHubTrampolineAccount`).

The severity is lower than a direct token exfiltration bug because the credentials extended to a legitimate `github.com`/GHE account are still gated by `credWithAccount`/`findGitHubTrampolineAccount`'s endpoint matching, so this does not by itself leak an *existing* GitHub token to the attacker. The primary damage is UI/trust spoofing that can lead to credential phishing and unwanted OAuth/account binding under Desktop's own branding.

## Likelihood Explanation
Triggering this requires nothing beyond convincing a user to add/fetch from an attacker-hosted HTTPS git remote (a very ordinary, "unprivileged" workflow — cloning or adding a remote is exactly the kind of git-remote interaction called out as valid in scope). The attacker only needs to return a 401 response with a crafted `WWW-Authenticate: Basic realm="GitHub"` header; no special git server features, TLS tricks, or local access are required, and this is the documented "happy path" the code explicitly implements rather than an edge case.

## Recommendation
Do not let a value that is fully attacker-suppliable (`WWW-Authenticate` realm content) elevate trust into "enterprise"/"github.com" without also validating the origin using an independent, server-authenticated signal, such as:
- Still requiring the `isGitHubHost()` network probe (which checks for `x-github-request-id`) before trusting a realm-based classification, rather than treating the header as sufficient on its own.
- At minimum, surfacing a clear, unmissable UI distinction in the resulting sign-in dialog showing the literal host being authenticated against, so users aren't led to believe an arbitrary domain is a vetted "GitHub Enterprise" endpoint.

## Proof of Concept
1. Host an HTTPS git server (e.g., a lightweight `smart-http` git backend) at `https://malicious-git.example.com`.
2. Configure it so that any credential-required request responds with HTTP 401 and header `WWW-Authenticate: Basic realm="GitHub"`.
3. In GitHub Desktop, add this URL as a remote (or clone it) and perform a `fetch`/`push` that requires auth.
4. Git invokes Desktop's credential trampoline; `getEndpointKind()` matches the `realm="GitHub"` branch and returns `'enterprise'` (`trampoline-credential-helper.ts:157-165`).
5. `getCredential()` sees no existing account for this endpoint and calls `promptForGitHubSignIn(endpoint)` (`trampoline-credential-helper.ts:109-124`), which calls `beginEnterpriseSignIn` + `setSignInEndpoint(origin)` with the attacker's origin (`trampoline-ui-helper.ts:87-93`).
6. Desktop pops the "Sign in to your GitHub Enterprise" dialog bound to `malicious-git.example.com`, and any credentials/OAuth flow the user completes there is directed at the attacker's server.

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }

  public async setEndpoint(url: string): Promise<void> {
    const currentState = this.state

    if (
      currentState?.kind !== SignInStep.EndpointEntry &&
      currentState?.kind !== SignInStep.ExistingAccountWarning
    ) {
      const stepText = currentState ? currentState.kind : 'null'
      return fatalError(
        `Sign in step '${stepText}' not compatible with endpoint entry`
      )
    }

    /**
     * If the user enters a github.com url in the GitHub Enterprise sign-in
     * flow we'll redirect them to the GitHub.com sign-in flow.
     */
    if (/^(?:https:\/\/)?(?:api\.)?github\.com($|\/)/.test(url)) {
      this.beginDotComSignIn(currentState.resultCallback)
      return
    }

    this.setState({ ...currentState, loading: true })

    let validUrl: string
    try {
      validUrl = validateURL(url)
    } catch (e) {
      let error = e
      if (e.name === InvalidURLErrorName) {
        error = new Error(
          `The GitHub Enterprise instance address doesn't appear to be a valid URL. We're expecting something like https://example.ghe.com.`
        )
      } else if (e.name === InvalidProtocolErrorName) {
        error = new Error(
          'Unsupported protocol. Only https is supported when authenticating with GitHub Enterprise instances.'
        )
      }

      this.setState({ ...currentState, loading: false, error })
      return
    }

    const endpoint = getEnterpriseAPIURL(validUrl)

    const existingAccount = this.accounts.find(x => x.endpoint === endpoint)

    if (existingAccount) {
      this.setState({
        kind: SignInStep.ExistingAccountWarning,
        endpoint,
        existingAccount,
        error: null,
        loading: false,
        resultCallback: currentState.resultCallback,
      })
    } else {
      this.setState({
        kind: SignInStep.Authentication,
        endpoint,
        error: null,
        loading: false,
        resultCallback: currentState.resultCallback,
      })
    }
