### Title
OP_RETURN data output is excluded from weight/vsize used for `needed_fee`, the minimum-relay check, and the max-weight check - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the Blueberry report — where `pendingRewards` returns empty arrays so a portion of a position's real value is silently omitted from the accounting — `SignableTransaction::new` appends an OP_RETURN output carrying up to 80 bytes of caller-controlled data to `tx_outs`, yet computes the transaction weight, virtual size, required fee, minimum-relay-fee check, and `MAX_STANDARD_TX_WEIGHT` check on a template transaction that does not include that output. The fee/size accounting is therefore computed over a different (smaller) transaction than the one that is signed and broadcast.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` before fee/size accounting:

- `networks/bitcoin/src/wallet/send.rs:194-202` — `tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })`.
- `networks/bitcoin/src/wallet/send.rs:204` — `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);`
- `networks/bitcoin/src/wallet/send.rs:225-226` — the change variant `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` likewise only receives `payments`, never the data output.

`calculate_weight_vbytes` (`send.rs:62-127`) constructs its template `Transaction` solely from `payments` plus an optional change output; there is no parameter for a data output, so the OP_RETURN is never represented in `weight` or `vbytes`. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`, `232`) is computed against a vsize smaller than the real transaction's, so the achieved fee rate is strictly lower than `fee_per_vbyte`.
2. The `TooLowFee` check (`send.rs:211`) compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same undercounted `vbytes`. A caller passing exactly the minimum relay rate produces a transaction whose *actual* fee rate is below the minimum relay fee, so Bitcoin nodes reject it and the inputs it spends cannot be moved via that transaction.
3. The `TooLargeTransaction` check (`send.rs:241`) validates `weight` of a transaction missing the data output, allowing a transaction exceeding `MAX_STANDARD_TX_WEIGHT` to be produced.
4. `change` (`send.rs:228-230`) is computed as `input_sat - payment_sat - fee_with_change`, where `fee_with_change` also omits the OP_RETURN size, so the reported `needed_fee()`/`fee()` do not reflect the rate actually paid.

The data input is public, caller-supplied bytes (`data: Option<Vec<u8>>`, up to 80 bytes checked at `send.rs:171`), so the discrepancy is fully reachable by an unprivileged party controlling the transaction parameters.

### Impact Explanation
Any `SignableTransaction` carrying an InInstruction/OP_RETURN payload pays a lower effective fee rate than requested and than what the minimum-relay check validates. In the worst case the produced transaction is non-standard (under the relay minimum fee or over `MAX_STANDARD_TX_WEIGHT`), causing nodes to reject it — funds are locked in the multisig inputs until a replacement transaction is constructed. This mirrors the original bug class: a component of real economic weight (here, transaction size/fee) is omitted from the accounting, producing a systematically wrong valuation.

### Likelihood Explanation
The miscalculation occurs on every transaction that includes `data`; the bytes are bounded (~90 extra weight units for a full 80-byte payload), so the rate error is small but deterministic. It only crosses the reject threshold when the requested fee rate is already at/near the relay minimum or the transaction is already near the weight limit — hence Medium rather than High.

### Recommendation
Pass the serialized OP_RETURN output (or its length) into `calculate_weight_vbytes` so `weight`, `vbytes`, `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all account for the data output that is actually included in `tx_outs`.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs semantics
// Construct a SignableTransaction with a 80-byte data payload:
let data = Some(vec![0u8; 80]);
let stx = SignableTransaction::new(inputs, &payments, change, data, fee_per_vbyte).unwrap();

// stx.transaction() contains the OP_RETURN output (send.rs:194-202),
// but stx.needed_fee() was computed via calculate_weight_vbytes
// (send.rs:204, 226) on a template with NO OP_RETURN output.
// Therefore:
//   actual_vsize = stx.transaction().vsize()  > vbytes_used_for_fee
//   actual_fee_rate = stx.fee() / actual_vsize < fee_per_vbyte
// With fee_per_vbyte == min relay rate, the actual rate falls below
// DEFAULT_MIN_RELAY_TX_FEE and the transaction is rejected by nodes.
```
