### Title
Missing zero-address validation on ERC20 bridge value-transfer requests causes permanent token loss/lock in `BridgeTransferERC20` - (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary
`requestERC20Transfer`/`requestValueTransfer` let any unprivileged caller submit a bridge request with `_to == address(0)`. In mint-burn mode the source-side tokens are burned immediately on request, but the corresponding `handleERC20Transfer` call on the counterpart chain calls the OpenZeppelin-derived `mint(_to, _value)`, which unconditionally reverts on a zero recipient, permanently preventing that nonce from ever completing.

### Finding Description
`_requestERC20Transfer` performs no validation on `_to` before burning the caller's value and emitting the request: [1](#0-0) 

`requestERC20Transfer` (2-step) and `ERC20ServiceChain.requestValueTransfer` (1-step) both funnel into `_requestERC20Transfer` with an attacker/user-controlled `_to`, again with no zero-address check: [2](#0-1) [3](#0-2) 

When the request is processed on the counterpart chain, `handleERC20Transfer` records nonce bookkeeping and emits the event *before* attempting the actual token move, then calls `ERC20Mintable(_tokenAddress).mint(_to, _value)` in mint-burn mode or `IERC20(_tokenAddress).safeTransfer(_to, _value)` otherwise: [4](#0-3) 

`ERC20Mintable` is built on the standard OpenZeppelin `ERC20` base, whose `_mint` and `_transfer` internals unconditionally revert when the target is `address(0)`: [5](#0-4) 

Because the whole `handleERC20Transfer` transaction reverts on this internal revert, the nonce is never marked handled (state updates prior to the revert are rolled back), so the deposit/withdrawal can never be completed by operators. In mint-burn mode this is catastrophic: the source-side value was already destroyed via `ERC20Burnable(_tokenAddress).burn(_value)` at request time, before the `_to` value is ever validated, so the user's tokens are burned with no possibility of the corresponding mint ever succeeding — a permanent, unrecoverable loss of user funds, exactly analogous to the reported `L1ECOBridge`/`ERC20Upgradeable._mint` zero-address revert issue.

### Impact Explanation
Any unprivileged user can trigger this by simply calling `requestERC20Transfer`/`requestValueTransfer` with `_to = address(0)`. In mint-burn deployments this results in real, irreversible loss of user funds (burned on the source chain, unmintable forever on the destination chain due to the permanently-reverting `handleERC20Transfer` call). In non-mint-burn mode, the deposited value remains stuck/locked in the bridge contract with no way to redeem it, since the immutable on-chain request event fixes `_to` at `address(0)` forever.

### Likelihood Explanation
This requires only a single transaction from any ordinary bridge user (accidental UI/integration bug or malicious griefing target) with no special privileges, matching the "reachable by unprivileged transaction sender" criterion. No collusion, timing, or special preconditions are required.

### Recommendation
Add an explicit `require(_to != address(0), "invalid recipient")` check in `_requestERC20Transfer` (and the analogous KLAY/ERC721 request paths) before burning/transferring value, so requests to the zero address are rejected at request time rather than allowing an unrecoverable state on the handle side.

### Proof of Concept
1. Deploy the bridge in `modeMintBurn = true` configuration and register a mint-burn-capable ERC20 token as in `deployBridgeConfiguredMintBurnFixture`.
2. As any unprivileged user, call `token.requestValueTransfer(value, address(0), feeLimit, "0x")` (or `bridge.requestERC20Transfer(token, address(0), value, feeLimit, "0x")`), analogous to the flow exercised in the test suite: [6](#0-5) .
3. This burns the caller's tokens via `ERC20Burnable(_tokenAddress).burn(_value)` in `_requestERC20Transfer` and emits `RequestValueTransfer` with `to = address(0)`.
4. Operators on the counterpart chain call `handleERC20Transfer(...)` with `_to = address(0)`; the call to `ERC20Mintable(_tokenAddress).mint(address(0), _value)` reverts per `ERC20.sol:171`, so the transaction always reverts and the value can never be minted — the user's tokens are permanently lost.

    function _transfer(address sender, address recipient, uint256 amount) internal {
        require(sender != address(0), "ERC20: transfer from the zero address");
        require(recipient != address(0), "ERC20: transfer to the zero address");

        _balances[sender] = _balances[sender].sub(amount);
        _balances[recipient] = _balances[recipient].add(amount);
        emit Transfer(sender, recipient, amount);
    }

    /** @dev Creates `amount` tokens and assigns them to `account`, increasing
