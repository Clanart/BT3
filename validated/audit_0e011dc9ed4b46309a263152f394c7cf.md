### Title
Unbounded Signature Count Enables Excessive ECDSA-Recovery Computation in Mempool Validation — ([File: blockchain/types/accountkey/account_key_weighted_multi_sig.go])

### Summary
Kaia's `AccountKeyWeightedMultiSig.Validate` checks the number of recovered signatures against the number of registered keys (capped at `MaxNumKeysForMultiSig = 10`) only *after* every signature attached to the transaction has already been recovered via expensive ECDSA `ecrecover` operations [1](#0-0) . There is no upfront limit on the number of `TxSignature` entries a submitted transaction may contain other than the generic 128 KB transaction size cap [2](#0-1) . This mirrors the "excessive computation in mempool validation" bug class in the Namada advisory: an attacker-controlled, cheaply-produced input (many repeated/garbage signatures) forces the validating node to perform disproportionately expensive cryptographic work before the transaction can be rejected.

### Finding Description
When a Kaia-typed transaction (e.g. `TxTypeValueTransfer`, `TxTypeAccountUpdate`, etc., all of which use `TxSignatures`) is submitted to the mempool, `TxPool.validateTx` calls `tx.ValidateSender`, which calls `SenderPubkey` → `RecoverTxPubkeys` → `TxSignatures.RecoverPubkey`. This function iterates over **every** signature in the transaction and calls `RecoverPubkey` (secp256k1 `ecrecover`) on each one, unconditionally: [3](#0-2) 

```
func (t TxSignatures) RecoverPubkey(...) ([]*ecdsa.PublicKey, error) {
    pubkeys := make([]*ecdsa.PublicKey, len(t))
    for i, s := range t {
        pubkeys[i], err = s.RecoverPubkey(...)
        ...
    }
    return pubkeys, nil
}
```

Only *after* this full recovery pass does `AccountKeyWeightedMultiSig.Validate` check whether `len(recoveredKeys) > len(a.Keys)` and reject the transaction: [4](#0-3) . Since `MaxNumKeysForMultiSig` bounds the account's keys to 10, but not the number of signatures an attacker can attach to a transaction, an attacker can craft a transaction with hundreds to thousands of dummy signatures (each ~65-96 bytes RLP-encoded) that fits comfortably within `MaxTxDataSize` (128 KB) [2](#0-1) . `NewTxSignaturesWithValues` (used by honest wallets) enforces the `MaxNumKeysForMultiSig` limit at signature-construction time [5](#0-4) , but this is a client-side helper, not a wire-format or mempool-side hard limit — a maliciously-crafted RLP transaction can bypass it entirely, since `TxSignatures` is decoded directly from the wire without a corresponding cap.

Critically, this expensive `ecrecover` pass happens in `pool.validateTx` (blockchain/tx_pool.go:898) *before* the pool has confirmed the sender can pay for the transaction in a way that discourages spam of this type — the transaction is ultimately rejected for free (no gas consumed, since it never reaches inclusion) after the node has already paid the CPU cost of recovering all the attached signatures.

### Impact Explanation
Each `ecrecover` operation costs on the order of tens of microseconds of CPU time. A single 128 KB transaction can carry on the order of ~1,000-1,900 dummy signatures. An attacker can broadcast a stream of such transactions (each with a new nonce or a garbage nonce to avoid pool eviction) to public RPC endpoints or the p2p mempool, forcing every receiving node to perform proportionally excessive signature-recovery work during `TxPool.AddRemote`/`validateTx`, well beyond what is needed for any legitimate multisig transaction (max 10 signatures). This can degrade mempool throughput and CPU availability network-wide — a resource-exhaustion condition reachable by any unprivileged transaction sender, consistent with CWE-770 (Allocation of Resources Without Limits or Throttling), matching the bug class of the referenced Namada advisory.

### Likelihood Explanation
The attack requires no special privileges: any account (even one without a valid multisig setup) can construct and RLP-encode a `TxSignatures` slice with an arbitrary number of syntactically valid (or garbage) `(v, r, s)` tuples and submit it via a public RPC `sendRawTransaction` call or over the p2p network. Constructing garbage `(v,r,s)` tuples is computationally cheap for the attacker (no valid ECDSA signing required, only format validity is checked cheaply via `SanityCheckSignatures`/`ValidateSignature()` prior to expensive recovery) but computationally expensive for the receiving/validating node. This makes the attack low-cost, repeatable, and broadly reachable.

### Recommendation
Enforce `MaxNumKeysForMultiSig` (or an equivalent conservative cap) as a mempool-level and RLP-decode-level bound on the number of entries in `TxSignatures` (and `TxFeePayerSignatures`) *before* performing any ECDSA recovery, rather than only checking after recovery in `AccountKeyWeightedMultiSig.Validate`. This should be enforced in `SanityCheckSignatures` or immediately at the top of `RecoverTxPubkeys`/`TxSignatures.RecoverPubkey`, rejecting transactions with an excessive signature count without paying the cost of recovering each one.

### Proof of Concept
1. Construct a Kaia `TxTypeValueTransfer` (or any non-legacy Kaia tx type) transaction body.
2. Populate its `TxSignatures` field directly (bypassing `NewTxSignaturesWithValues`, e.g. via custom RLP construction) with ~1,500 `(v, r, s)` tuples, each syntactically valid per `validateSignature`/`crypto.ValidateSignatureValues`, but not derived from any real private key correlated with the target account (garbage/random signatures satisfying the low-s / valid-recovery-id format check).
3. Ensure total RLP size stays under `MaxTxDataSize` (128 KB) — feasible since each signature is only ~65-96 bytes.
4. Submit the transaction via `eth_sendRawTransaction` / `AddRemote` to a Kaia node.
5. Observe that `TxPool.validateTx` → `tx.ValidateSender` → `SenderPubkey` → `RecoverTxPubkeys` performs ~1,500 `ecrecover` calls before `AccountKeyWeightedMultiSig.Validate` finally rejects the transaction for `len(recoveredKeys) > len(a.Keys)`.
6. Repeat with many such transactions (varying nonces or dummy senders) to measure aggregate CPU overhead imposed on mempool validation across nodes.

func (t TxSignatures) RecoverPubkey(txhash common.Hash, homestead bool, vfunc func(*big.Int) *big.Int) ([]*ecdsa.PublicKey, error) {
	var err error

	pubkeys := make([]*ecdsa.PublicKey, len(t))
	for i, s := range t {
		pubkeys[i], err = s.RecoverPubkey(txhash, homestead, vfunc)
		if err != nil {
			return nil, err
		}
	}

	return pubkeys, nil
}
