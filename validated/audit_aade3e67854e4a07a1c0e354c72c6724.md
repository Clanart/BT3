### Title
Blame proof leaks ECDH shared key for a message whose proof-of-possession was never verified - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
CVE-2019-5880 concerned insufficient policy enforcement allowing a remote attacker to leak data across a trust boundary. The PedPoP DKG has the same shape: `KeyMachine::calculate_share` returns an `EncryptionKeyProof` — which publicly reveals the ECDH shared key for a message — before the message's Schnorr proof-of-possession (the policy preventing exactly this leak) has actually been verified. The PoP is only queued into a `BatchVerifier` inside `Encryption::decrypt`; if the decrypted share bytes fail `C::F::from_repr`, `calculate_share` returns the blame proof early, without ever running the batch verification that would have rejected the forged PoP.

### Finding Description
`Encryption::decrypt` in `crypto/dkg/pedpop/src/encryption.rs` queues `msg.pop.batch_verify(...)` into a caller-supplied batch verifier, but then unconditionally computes `key = ecdh(&self.enc_key, msg.key)` and constructs an `EncryptionKeyProof` containing that raw shared key plus a DLEq proving its correctness against the recipient's registered encryption key:

```rust
msg.pop.batch_verify(rng, batch, batch_id, msg.key, pop_challenge::<C>(...));
let key = ecdh::<C>(&self.enc_key, msg.key);
cipher::<C>(self.context, &key).apply_keystream(msg.msg.as_mut().as_mut());
(msg.msg, EncryptionKeyProof { key, dleq: DLEqProof::prove(...) })
``` [1](#0-0) 

In `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs`), the PoP verification is deferred: `batch.verify_with_vartime_blame()` is only invoked at line 493, after the per-share loop. If the decrypted bytes are a non-canonical scalar, the function returns early at lines 480–482 with `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` — publishing the `EncryptionKeyProof` even though the message's PoP was queued but never checked. [2](#0-1) 

This is precisely the attack the PoP was added to prevent. The comments on `EncryptedMessage` state: if the PoP weren't enforced, "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X... they'd reveal bX, revealing Alice's message to Bob." The lazy batch verification reintroduces this side-channel: the PoP is enforced only when `from_repr` succeeds and the loop reaches `batch.verify_with_vartime_blame()`. [3](#0-2) 

### Impact Explanation
A DKG participant (Eve) observes victim Alice's encrypted share to Bob, which carries per-message key `X = x·G`. Eve sends Bob a crafted `EncryptedMessage` with `key = X`, a garbage `pop`, and arbitrary ciphertext bytes. Bob computes `key = b·X` (his ECDH with Alice's key) and wraps it into an `EncryptionKeyProof`. With probability ≈ ½ (a random 32-byte string is non-canonical for a ~252-bit field), `from_repr` fails and Bob returns the blame proof — which the processor serializes into `ProcessorMessage::InvalidShare.blame` — revealing `b·X` to all parties before the forged PoP is ever checked. Anyone can then run `cipher(context, bX)` over Alice's original ciphertext to recover Alice's secret share to Bob. Combined with Bob's known share data this leaks a private evaluation of Alice's DKG polynomial to unprivileged observers, and repeated across attempts degrades the confidentiality of the DKG.

### Likelihood Explanation
The attacker needs only to be a participant (or anyone able to submit a share to Bob's `calculate_share` path via `EncryptedMessage::read` on public protocol traffic) and to copy an observed `key` field — the PoP is invalid but never verified on this path. The decryption must be non-canonical, which occurs with ~50% probability per attempt, and failed DKG attempts can be retried. The code path is entirely attacker-controlled: `key`, `pop`, and `msg` all come from the untrusted `EncryptedMessage::read` bytes.

### Recommendation
Do not construct or release the `EncryptionKeyProof` until the PoP for that message has been verified. In `calculate_share`, run (or split) the batch verification of all `BatchId::Decryption(l)` PoP statements before processing share contents, or defer producing `blames` entries until after `batch.verify_with_vartime_blame()` confirms the PoP — e.g., store the ECDH key and only build/publish the `EncryptionKeyProof` if the corresponding PoP verified. Alternatively, verify the PoP eagerly inside `Encryption::decrypt` instead of queuing it, since blame generation already requires the message to be well-formed.

### Proof of Concept
1. Honest Alice runs `generate_secret_shares`; her message to Bob is `EncryptedMessage { key: X, pop: valid, msg: c }`.
2. Eve submits to Bob `EncryptedMessage { key: X, pop: arbitrary-invalid, msg: random 32 bytes }` as her share.
3. Bob's `Encryption::decrypt` queues Eve's invalid PoP into the batch, computes `key = b·X`, builds `EncryptionKeyProof { key: bX, dleq: valid }` (Bob knows `b`, so the DLEq is honest).
4. With ~50% probability the ChaCha20-decrypted bytes are non-canonical; `from_repr` fails, and `calculate_share` returns `InvalidShare { blame: Some(proof) }` at line 481 — before `batch.verify_with_vartime_blame()` at line 493 would have rejected Eve's PoP.
5. The blame proof (containing `bX`) is serialized and published; any observer applies `cipher::<C>(context, &bX)` to Alice's original ciphertext `c` and recovers her secret share to Bob.
