### Title
Retired multisig key is removed from the scan set, so payments to its still-valid addresses are never reported and become unspendable - (File: processor/src/multisigs/scanner.rs)

### Summary
Analogous to the Airdrop report — where a changed locker address is only updated in one place and funds sent to the *old* locker become unclaimable — Serai's scanner drops the retiring multisig key from the scan set entirely once a key rotation completes. Any Bitcoin sent afterward to the retired key's external/branch/forwarded address lands on-chain but is never surfaced as a `ScannerEvent::Block` output, so the coordinator never learns of the funds and they can never be routed into a `SignableTransaction` for spending.

### Finding Description
`ScannerDb::retire_key` deletes the entire `keys` entry list and re-registers only `keys[1]` (the new key):

```rust
fn retire_key(txn: &mut D::Transaction<'_>) {
  let keys = Self::keys(txn);
  assert_eq!(keys.len(), 2);
  txn.del(Self::keys_key());
  Self::register_key(txn, keys[1].0, keys[1].1);
}
``` [1](#0-0) 

The scan loop iterates only `scanner.keys`, so after `retire_key` runs, `network.get_outputs(&block, key)` is invoked solely for the new key: [2](#0-1) 

On Bitcoin, `get_outputs` builds a `Scanner` for that single key and matches outputs by `script_pubkey` only (`self.scripts.get(&output.script_pubkey)` in `networks/bitcoin/src/wallet/mod.rs` `Scanner::scan_transaction`): [3](#0-2) [4](#0-3) 

Retirement is scheduled once a Batch from the old key completes (`check_multisig_completed` saves `block_number + N::CONFIRMATIONS` as the retirement block): [5](#0-4) 

Nothing preserves the old key's scripts as a watch set or emits events for post-retirement payments to them. This mirrors the Airdrop flaw exactly: the "locker" (the spendable key/script set) is overwritten rather than the old locker being retained for claiming.

### Impact Explanation
Any external, unprivileged Bitcoin user can send BTC to the retired key's published addresses (`external_address`, `branch_address`, `forward_address`, change offsets — all computable publicly from the group key via `KEY_DST` hash offsets in `processor/src/networks/bitcoin.rs`). After `retirement_block`, these outputs are silently ignored. Depending on whether the old key's shares remain available, the funds are either permanently unspendable or spendable by a retired quorum that the protocol no longer tracks — i.e., funds received on-chain but never reported, the exact "funds stuck in old locker" consequence of the report.

### Likelihood Explanation
Triggering only requires sending a normal Bitcoin transaction to an already-published address — no collusion, no malicious validator, no malformed input. Delayed/dust-above-threshold payments and forwarded outputs landing after rotation are plausible real-world occurrences since addresses remain valid forever on Bitcoin.

### Recommendation
Retain retired keys' script sets in the scanner (a tombstoned/watch-only state) for a bounded post-retirement window — or permanently — and continue emitting outputs matched to them, rather than dropping them wholesale in `retire_key`. Equivalently, maintain the `script → offset` map for the old key in `networks/bitcoin/src/wallet/mod.rs::Scanner` so late-arriving funds are still claimable, matching the audit recommendation that "previous lockers should not be overwritten."

### Proof of Concept
1. Multisig key `K_old` is registered; `Scanner` watches `K_old`'s four `OutputType` scripts.
2. A new key `K_new` is registered and a Batch completes; `check_multisig_completed` sets `K_old`'s retirement block and `retire_key` removes `K_old` from `scanner.keys`.
3. Any user broadcasts a BTC transaction paying `N::DUST + ε` to `K_old`'s external address (P2TR-tweaked `K_old`).
4. The scan loop calls `get_outputs(&block, K_new)` only; `Scanner::scan_transaction` built for `K_new` contains none of `K_old`'s script_pubkeys, so the output is never inserted into `ram_outputs`, never emitted as `ScannerEvent::Block`, and never acknowledged — the BTC sits unspendable/untracked despite being a valid payment to a protocol-controlled key.

Uncertainty note: I could not fully trace the scheduler-side intent of key retirement (whether `K_old` shares are deliberately destroyed). Even if intentional, late payments to `K_old` are still dropped silently rather than reported/forwarded, which is precisely the "old locker's funds unclaimable" flaw class — the finding stands on the scanner dropping the old key's scripts without retaining a claim path.
