### Title
Attacker-triggerable panic in PedPoP blame evaluation via unregistered `recipient` index (`Decryption::decrypt_with_proof` indexes `enc_keys` without bounds check) - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with `HashMap`'s panicking `Index` implementation before validating that `decryptor` was ever registered. `enc_keys` only ever contains participants `1..=n`, yet `decryptor` is an arbitrary `Participant` supplied by the caller of `BlameMachine::blame` / `AdditionalBlameMachine::blame`. An attacker who submits a blame request naming an out-of-range recipient (any non-zero `u16` greater than `n`), together with an `EncryptedMessage` carrying a valid Schnorr proof-of-possession and `Some(EncryptionKeyProof)`, reaches the indexing operation and crashes the host process. This is the Serai analog of CVE-2021-1093: an assertion-like statement (implicit panic on missing `HashMap` key) triggerable by an unprivileged party, causing denial of service.

### Finding Description
In `decrypt_with_proof`, once the proof-of-possession signature on the message verifies, the code evaluates `self.enc_keys[&decryptor]` to fetch the decryptor's public encryption key for the DLEq check: [1](#0-0) 

`enc_keys` is populated exclusively by `Decryption::register`, which is only invoked for participants in `1..=n` — inside `verify_r1`/`AdditionalBlameMachine::new`: [2](#0-1) [3](#0-2) 

Neither `BlameMachine::blame` nor `AdditionalBlameMachine::blame` validates that `recipient` (or `sender`) is a registered participant before forwarding them to `blame_internal` → `decrypt_with_proof`: [4](#0-3) [5](#0-4) 

The only gates before the panic are (a) `msg.pop.verify(...)` passing — trivially satisfiable since the attacker controls the encryption key and can produce an honestly-formed `EncryptedMessage` — and (b) `proof` being `Some`, which the attacker supplies. `Participant::new` accepts any non-zero `u16`, so `Participant::new(n + 1)` is a well-formed value that was never inserted into `enc_keys`. Indexing a `HashMap` with an absent key panics (`HashMap`'s `Index` impl is documented to panic), aborting the caller's thread/process.

### Impact Explanation
`AdditionalBlameMachine` exists precisely so that a third party can evaluate blame claims in the DKG ("capable of evaluating Blame regardless of if the caller was a member in the DKG protocol"), and `BlameMachine::blame` is the equivalent path for a participant. Any validator/node that processes blame accusations submitted by other parties can be crashed by a single crafted accusation: an attacker claims "participant `n+1` falsely accused participant 1" (or any recipient outside `1..=n`), attaches a self-constructed `EncryptedMessage` with a valid PoP and any `EncryptionKeyProof`, and the victim panics mid-evaluation. This halts DKG completion, blame adjudication, and — because the panic unwinds into whatever the host was doing — can take down the signing/key-management process entirely. It is a pure availability impact matching the CVE's CVSS profile (local/low-privilege trigger, high availability loss, no confidentiality/integrity loss).

### Likelihood Explanation
Reachability requires a deployment that feeds attacker-influenced `sender`/`recipient` indexes into `blame`. The `Participant` arguments are part of the public API precisely because blame is a protocol-level message evaluated over claims from other parties; nothing in the API constrains them to `1..=n`. Constructing the required `EncryptedMessage` is free for the attacker (generate a keypair, encrypt arbitrary bytes, sign the PoP — `pop_challenge` covers attacker-chosen `from`, `key`, `msg`), and `EncryptionKeyProof` just needs to deserialize (`EncryptionKeyProof::read` accepts any well-formed point + DLEq bytes; it is never verified before the panic). The panic occurs before the DLEq is checked, so no valid proof is needed. A process that evaluates even one malicious blame claim crashes deterministically — likelihood is high wherever blame evaluation is exposed.

### Recommendation
Replace the panicking `HashMap` index with a fallible lookup in `Decryption::decrypt_with_proof`:

```rust
let Some(enc_key) = self.enc_keys.get(&decryptor).copied() else {
  // The claimed recipient was never a participant; blame is meaningless
  return Ok(msg.msg); // or a dedicated error/blame result
};
```

(or return `DecryptionError::InvalidProof`, mapping an unregistered recipient to "accuser is faulty"). The same treatment should be applied to `self.commitments[&sender]` in `blame_internal` (crypto/dkg/pedpop/src/lib.rs:599), which has the identical panic shape for an unregistered `sender` once `decrypt_with_proof` succeeds. More broadly, `blame`/`blame_internal` should validate `sender` and `recipient` against `params.all_participant_indexes()` and report the accusing party as faulty when either is out of range.

### Proof of Concept
```rust
// Context: DKG over C with n participants; an AdditionalBlameMachine was
// constructed via `AdditionalBlameMachine::new(context, n, commitment_msgs)`
// where commitment_msgs registered exactly participants 1..=n.

// Attacker crafts a well-formed EncryptedMessage to themselves:
let msg: EncryptedMessage<C, SecretShare<C::F>> = encrypt(
    &mut rng,
    context,
    attacker_i,                    // `from` used inside the PoP challenge
    attacker_enc_pub_key,          // arbitrary public key
    Zeroizing::new(SecretShare::<C::F>(repr)),
);
// `msg.pop` is a valid Schnorr PoP since the attacker knows the key.

// Any deserialized EncryptionKeyProof suffices; the DLEq is never
// verified before the panic:
let proof = Some(EncryptionKeyProof::<C>::read(&mut &attacker_bytes[..]).unwrap());

// `recipient` is a valid Participant that was never registered:
let recipient = Participant::new(n + 1).unwrap();

// Panics inside decrypt_with_proof at `self.enc_keys[&decryptor]`
// after `msg.pop.verify` passes — no out-of-range check exists.
machine.blame(Participant::new(1).unwrap(), recipient, msg, proof);
```

Supporting code: the PoP gate that passes for attacker-formed messages ( [6](#0-5) ), the panicking index ( [7](#0-6) ), and the unbounded `Participant` domain ( [8](#0-7) ).

Note: the secondary panic at `self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs:599) is reachable the same way but additionally requires a *valid* DLEq proof to pass `decrypt_with_proof`, making the `enc_keys[&decryptor]` path the stronger, cheaper trigger.
