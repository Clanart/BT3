### Title
Strip-normalized diff filter reclassifies genuinely new/relocated code as pre-existing context, hiding it from LLM security review - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`filter_preexisting_from_diff` converts any `+` line to a context (unchanged) line whenever its `.strip()`-normalized text matches *any* `-` line's stripped text anywhere in the same file diff, regardless of position, surrounding code, or indentation. An attacker who fully rewrites a file via the Write tool can move an existing dangerous statement out of its original guard (e.g., un-indenting a call out of an `if is_admin:` block) or otherwise relocate/duplicate a line whose trimmed text matches something the diff already shows as removed, and that structurally new/dangerous placement is silently converted to `' '`-prefixed context and dropped from what `analyze_code_security` receives.

### Finding Description
`filter_preexisting_from_diff` (plugins/security-guidance/hooks/gitutil.py, lines 657-722) builds a `removed_lines` set from all `-` lines (stripped) and an `added_lines_set` from all `+` lines (stripped), then rewrites each `+` line to context if `content in removed_lines` [1](#0-0) . The docstring itself flags this as a "known imprecision": `.strip()` matching ignores indentation, and a *single* removed line can mask *N* additions of the same stripped text — i.e., matching is purely by text content, not by diff position/hunk [2](#0-1) .

Attack flow: Claude/attacker uses `Write` to fully rewrite a file, git shows the whole file as removed (`-`) then re-added (`+`) [3](#0-2) . In such a full rewrite, the attacker controls the entire new content and can see the entire old content (removed lines) in the resulting diff. They can then re-place a dangerous statement — whose trimmed text is byte-identical to some line elsewhere in the old file — at a *new, more dangerous* location (e.g., unconditionally instead of behind an authorization check), or introduce a duplicate occurrence of an existing sensitive call outside its original guard. Because matching is content-only and ignores indentation/hunk context, that relocated `+` line strip-matches a `-` line and is rewritten with a `' '` context prefix and excluded from the "new code" the reviewer sees. This filtered diff is what feeds `analyze_code_security` (imported and called from `security_reminder_hook.py`), so the LLM security reviewer never inspects the genuinely new, more dangerous statement. This defeats the "deny means deny / trusted validation must see attacker input" invariant: the automated review is the trust boundary meant to catch newly introduced vulnerable code in a session diff, and this smuggling path causes it to see stale/incomplete input.

### Impact Explanation
Newly introduced or relocated vulnerable/dangerous code (e.g., moving a privileged operation out of an authorization guard, or duplicating a dangerous call to a new unconditional site) can be smuggled past the Stop-hook's automated security review whenever a full-file Write rewrite is involved. This is a security-control bypass of the plugin's core enforcement mechanism (the LLM diff review), directly undermining the "code security review" feature's purpose: it results in the reviewer being blind to genuinely dangerous new code, letting a compromised/malicious agent session commit or persist unreviewed vulnerable code.

### Likelihood Explanation
Preconditions are realistic and match the stated threat model: the attacker only needs the ability to fully rewrite a file via the `Write` tool during an active session (already an assumed capability in this threat model), and needs the target file to already contain, anywhere, a line whose trimmed text they can reuse at a new/different location. This is common for short, generic statements (single function calls, common conditionals, log/print/exec lines) that recur or can be deliberately duplicated in a full rewrite. The bug is deterministic and mechanical (pure string/set matching), so it is reliably repeatable, not probabilistic.

### Recommendation
Make the "pre-existing" filter position/context aware instead of pure content-set matching:
- Require exact-match with unchanged surrounding context (e.g., LCS/diff-alignment-based unchanged-block detection) rather than any-removed-line-matches-any-added-line.
- At minimum, do not allow a single removed line to mask more than one added occurrence, and do not ignore leading-whitespace/indentation differences, since indentation changes can carry semantic meaning (e.g., moving code in/out of a guard).
- Consider tracking line provenance by hunk-relative order (e.g., using `difflib.SequenceMatcher` over the whole file's old/new line lists) to only mark truly unchanged lines as context, rather than heuristically matching disjoint stripped strings.

### Proof of Concept
Unit test in `gitutil.py` test suite:
```python
def test_filter_does_not_hide_reindented_relocated_line():
    diff = (
        "diff --git a/app.py b/app.py\n"
        "--- a/app.py\n"
        "+++ b/app.py\n"
        "@@ -1,2 +1,2 @@\n"
        "-if is_admin:\n"
        "-    run_dangerous()\n"
        "+run_dangerous()\n"
        "+if is_admin:\n"
    )
    diff_files = [("app.py", diff)]
    result = filter_preexisting_from_diff(diff_files, cwd=".", baseline_sha="deadbeef")
    _, filtered_content = result[0]
    # The relocated, now-unconditional call must still be visible as an
    # addition ('+') to the reviewer — it must NOT be silently converted
    # to a context line (' ') just because its stripped text matches the
    # old indented removed line.
    assert "+run_dangerous()" in filtered_content
    assert " run_dangerous()" not in filtered_content.replace("+run_dangerous()", "")
```
Expected (current behavior, demonstrating the bug): the assertion fails because `run_dangerous()` on the new unconditional `+` line strip-matches the removed `    run_dangerous()` line and gets rewritten as a `' '`-prefixed context line, hiding it from `analyze_code_security`.
