### Title
Git flag injection via unguarded branch name in `checkoutBranch` - (File: `app/src/lib/git/checkout.ts`)

### Summary
`checkoutBranch` builds its `git checkout` argument list by placing the branch's ref name as the *first* positional argument, and only appends the `--` pathspec-disambiguator *after* it, rather than before it. Every other place in the codebase that passes an externally-derived ref/pathspec to `git` (e.g. `getCommits`, `getCommitsInRange`, `getAheadBehind`, `unstageAllFiles`, `removeConflictedFile`) places `--` immediately in front of the untrusted value to stop git from parsing it as an option. `checkoutBranch`'s helper, `getBranchCheckoutArgs`, does not follow that pattern.

### Finding Description
`getBranchCheckoutArgs` in `app/src/lib/git/checkout.ts` returns: [1](#0-0) 
i.e. `[branch.name, '-b', branch.nameWithoutRemote, '--']` for a remote branch, or `[branch.name, '--']` for a local branch. `branch.name` is placed as the first token, with the `--` guard positioned *after* it instead of before it, so if `branch.name` begins with `-`, git will try to parse it as a command-line flag to `git checkout` instead of a ref.

`branch.name` is not something Desktop generates or sanitizes — it comes straight from `git for-each-ref`'s `%(refname:short)` output via `getBranches`: [2](#0-1) [3](#0-2) 
This means the branch name displayed and later checked out can be anything present in `refs/heads/*` or `refs/remotes/*` in the repository's object/ref database — including refs that arrived via `git fetch` from a remote the user added (a cloned/forked or malicious remote), since Desktop does not re-validate ref names it reads back from git.

Notably, Desktop *does* recognize this exact class of bug and defends against it — but only for refs the user types by hand in the UI. `sanitizedRefName` explicitly strips a leading `-` (and `+`) from user-entered branch names in the Create/Rename Branch dialogs: [4](#0-3) [5](#0-4) 
That sanitizer is never applied to ref names Desktop reads back from `for-each-ref`/`getBranches`, which is exactly the path `checkoutBranch` consumes.

By contrast, functions that consume untrusted/derived revisions elsewhere in the codebase correctly put `--` before the value, e.g.: [6](#0-5) [7](#0-6) 

### Impact Explanation
If a ref name beginning with `-` can exist in the local ref database (via fetch from an attacker-controlled or compromised remote, or a crafted repository the user clones), checking it out through Desktop's branch list/checkout flow would pass that string as `argv[N]` to `git checkout` before any `--` guard, letting git interpret it as a flag rather than a revision (the same broken invariant as the HackerOne report: a value meant to be a data/ref argument is instead parsed as a git option because the `--` boundary is on the wrong side of it). Depending on which flag is injected this could range from unexpected `checkout` behavior/error to more impactful outcomes depending on which of git's `checkout` options accept attacker-influenced values.

### Likelihood Explanation
Medium-to-uncertain. The code pattern (untrusted value placed before `--` instead of after) is confirmed and stands out compared to every other call site in the codebase that handles this correctly. However, I could not verify within the available tools whether `git`'s own ref-name validation (`check-ref-format`) permits a ref whose short name begins with `-` to be created/fetched in the first place — this is the load-bearing assumption for exploitability and I was unable to confirm it definitively from the indexed code (git's own C source isn't in this repo). Desktop's own `sanitizedRefName` implies the Desktop authors consider such names creatable/dangerous enough to filter for user-typed input, which is suggestive but not conclusive proof that fetched refs can carry this shape.

### Recommendation
In `getBranchCheckoutArgs` (`app/src/lib/git/checkout.ts`), move the `--` immediately before `branch.name` (and before any other ref/commitish argument passed to `git checkout`), matching the pattern already used in `rev-list.ts`, `log.ts`, and `rm.ts`. Consider auditing all other `git` argument builders for the same "value-before-separator" ordering issue.

### Proof of Concept
1. Add/point a remote at a repository containing (or crafted such that `git fetch` creates) a ref whose short name begins with `-`, e.g. `refs/heads/--upload-pack=/tmp/evil.sh`.
2. Fetch it in Desktop so it appears in `getBranches()`'s output as a `Branch` with `name` starting with `-`.
3. Trigger checkout of that branch via the UI, which calls `checkoutBranch` → `getBranchCheckoutArgs` → `git(['checkout', branch.name, '--'], ...)`.
4. Because `branch.name` precedes `--`, git parses it as an option to `checkout` rather than a ref name.

*I was unable to fully confirm within available tools whether git permits creating/fetching a ref with a leading-dash short name (which is required for actual exploitability), so this should be verified against git's `check-ref-format` behavior before treating this as conclusively exploitable.*
