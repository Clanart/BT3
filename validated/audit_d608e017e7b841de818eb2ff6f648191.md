## Finding [1](#0-0) 

### Title
Unauthenticated OP_RETURN operator-attribution in `payout_tx` allows misattributing (stealing) a peg-out reimbursement credit - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The `payout_tx` built by `create_payout_txhandler` commits the user's withdrawal via a `SinglePlusAnyoneCanPay` Schnorr signature, but that sighash type only covers the input and the output at the *same index* (output 0, the user's payout). The second output (`OP_RETURN` carrying the fronting operator's x-only pubkey, used later to attribute reimbursement) is **not covered by the signature** at all. Any unprivileged party who observes the broadcast/mempool transaction can rebuild an equivalent transaction with the identical signed input/output-0, but a different `OP_RETURN` operator pubkey (and different fee-input, which `ANYONECANPAY` explicitly permits them to add and sign themselves), and get it mined before or instead of the original. This breaks the "operator credited == party that paid" binding.

### Finding Description
`create_payout_txhandler` signs only txin 0 via key-path Schnorr with the caller-supplied sighash type: [2](#0-1) 

The sighash type is enforced to be `SinglePlusAnyoneCanPay`: [3](#0-2) 

`SinglePlusAnyoneCanPay` commits only to input 0 and the output at index 0 (per BIP341/BIP143 semantics, confirmed by the sighash-computation helper which special-cases these types for `Prevouts::One`): [4](#0-3) 

Because of `ANYONECANPAY`, other inputs (e.g. fee-funding inputs added via `fund_raw_transaction`) are unsigned by the user and can be freely replaced/added by whoever assembles the final transaction: [5](#0-4) 

The second (anchor) and third (`OP_RETURN` operator pubkey) outputs are outside the signed message entirely — they can be swapped for anything without invalidating the user's signature, since only output 0 is checked: [6](#0-5) 

Downstream, the protocol trusts whatever `OP_RETURN` pubkey ends up in the *confirmed* payout transaction to decide which operator gets reimbursement credit, with no cryptographic binding back to who actually funded output 0: [7](#0-6) 

This attribution is later used to gate reimbursement/kickoff validity — an operator whose xonly pubkey does not match the payer recorded in the DB is flagged malicious, and the reimbursement claim is rejected: [8](#0-7) 

And the `PayoutCheckerTask`/`handle_finalized_payout` flow reimburses strictly the operator recorded as `payout_payer_operator_xonly_pk`, without any further proof that this operator's own funds moved to the user: [9](#0-8) [10](#0-9) 

**The binding broken:** `payer_who_funded_output_0 == operator_credited_via_OP_RETURN`. Before the attack these are equal (the fronting operator constructs and broadcasts its own `payout_tx`). After the attack, an unprivileged third party rebroadcasts (or RBF-replaces) a transaction with the same signed output-0 but an arbitrary `OP_RETURN` pubkey, so `payer_who_funded_output_0 != operator_credited`.

### Impact Explanation
This is Critical: an honest operator (A) who genuinely puts up capital to pay the user (output 0) can have its reimbursement credit rerouted to a completely different (possibly colluding, or simply victim) operator (B) whose xonly pubkey is placed in the substituted `OP_RETURN`. Consequences:
- B is later "reimbursed for a payout it never funded" (explicitly listed Critical impact).
- A's own kickoff for the same deposit is rejected as malicious by `is_kickoff_malicious` (operator xonly pk mismatch with recorded payer), so A — the honest operator who actually paid — becomes permanently unable to be reimbursed (also an explicitly listed Critical impact) and may face slashing of its kickoff/challenge collateral for what looks like an invalid claim.
- Because `ANYONECANPAY` lets any observer supply and sign their own extra fee-input, the attacker needs no protocol privilege, private key material of the vault, or role membership — pure mempool observation and standard RBF/fee-bump capability suffice.

### Likelihood Explanation
Payout transactions are broadcast to the public Bitcoin mempool as part of normal operator flow (`fund_raw_transaction` + RBF-enabled `TxSender`) before confirmation, giving any network observer time to see the signed witness and reconstruct a competing transaction. The construction of the substitute transaction is trivial: copy the signed input/witness (the existing `copy_witnesses` code already demonstrates that S+AP witnesses are portable across differently-constructed PSBTs), keep output 0 identical, replace outputs 1/2, add and sign one's own fee input, and win the fee race or simply broadcast before the original operator's transaction propagates. No cryptographic secret or role is required.

### Recommendation
Bind the operator attribution to the same signature that authorizes the spend, e.g. by:
- Using `AllPlusAnyoneCanPay` (or `Default`) instead of `SinglePlusAnyoneCanPay` so the user's signature commits to *all* outputs of `payout_tx` (payout output, anchor, and `OP_RETURN` operator pubkey), preventing any output substitution; or
- Requiring the operator identity to be committed via a separate mechanism cryptographically tied to the specific broadcast transaction (e.g., verifying the input funding UTXO used for fee-bumping actually belongs to/was signed by the operator claiming credit, and cross-checking that against the recorded `payout_payer_operator_xonly_pk`) before trusting the parsed `OP_RETURN` value for reimbursement decisions.

### Proof of Concept
1. Operator A receives a valid `WithdrawParamsWithSig` (SIGHASH `SinglePlusAnyoneCanPay`) for withdrawal id `W`, and constructs/broadcasts `payout_tx_A` via `create_payout_txhandler` with `OP_RETURN = xonly_pk(A)` (`core/src/builder/transaction/operator_reimburse.rs:407-436`, `core/src/operator.rs:620-674`).
2. Attacker M observes `payout_tx_A` in the mempool. M extracts the witness for input 0 (valid under S+AP, only commits input0+output0).
3. M builds `payout_tx_M`: same input 0 + witness, same output 0 (user payout, untouched — required for signature validity), but a different anchor amount/`OP_RETURN` payload containing `xonly_pk(B)` (any operator, or even a bogus-but-valid-format value), plus M's own additional fee input (signed by M, permitted by `ANYONECANPAY`) at a higher feerate.
4. M broadcasts `payout_tx_M` with RBF, replacing `payout_tx_A` in mempool; `payout_tx_M` confirms.
5. `update_finalized_payouts` (`core/src/verifier.rs:2311-2342`) parses `OP_RETURN` = `xonly_pk(B)` and records B as `payout_payer_operator_xonly_pk` for withdrawal `W`.
6. `PayoutCheckerTask`/`handle_finalized_payout` (`core/src/task/payout_checker.rs:41-79`, `core/src/operator.rs:1284-1296`) subsequently grants B (not A) the reimbursement kickoff path for the deposit, while A's kickoff attempt is rejected by `is_kickoff_malicious` (`core/src/verifier.rs:1885-1890`) due to xonly-pubkey mismatch — A funded the payout but cannot recover reimbursement, and B is reimbursed for a payout it never funded.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
