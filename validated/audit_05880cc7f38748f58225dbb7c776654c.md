### Title
OP_RETURN `data` output excluded from weight/fee calculation causes underpriced transactions that are always rejected by relay - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the reported bug — where a required fee parameter was omitted from a cross-chain call, making it revert every time — `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` appends an OP_RETURN output carrying `data` to the transaction *before* computing the fee, but computes the transaction's weight/vbytes from `payments` only. The OP_RETURN output's size is never accounted for, so `needed_fee` is systematically underpriced. For transactions constructed at or near the minimum relay fee rate, the resulting effective fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`, and every broadcast of the transaction is rejected — the analog of a call that "reverts all the time."

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed into `tx_outs` (lines 194–202), but the fee is computed by `calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204. `calculate_weight_vbytes` (lines 62–127) builds a template `Transaction` whose `output` vector contains only `payments` (and optionally `change`) — the `data` argument is never passed to it. The same omission occurs in the change branch at lines 224–234, where `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` again omits the OP_RETURN output.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) undercounts the true vsize by the serialized size of the OP_RETURN output — roughly 90+ vbytes for up to 80 bytes of data (8-byte amount + script length + opcode + pushdata + data), all non-witness bytes.
2. The `TooLowFee` guard at lines 211–213 checks `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the *underestimated* `vbytes`, so it does not catch the shortfall.
3. When a change output is added (lines 224–234), its value is `input_sat - payment_sat - fee_with_change`, locking in the underpriced fee; the actual fee paid (`fee()`, lines 138–141) equals this underpriced `needed_fee`.
4. The signed transaction (via `TransactionSignMachine::sign` / `complete`) therefore pays less than the requested rate. Whenever `fee_per_vbyte` is near the 1000 sat/kilo-vbyte relay minimum, the *real* fee rate drops below the minimum and the transaction is rejected as non-standard by every node — permanently, since the transaction is fixed once signed.

This mirrors the audit finding's shape exactly: a fee that must be carried by a specific parameter is silently omitted from the calculation, producing a transaction that can never succeed.

### Impact Explanation
Any `SignableTransaction` constructed with `data: Some(_)` pays `fee_per_vbyte * sizeof(OP_RETURN output)` less than intended. At low fee rates the transaction is unrelayable — the signed transaction is rejected by all Bitcoin nodes, so the payment/change outputs never come into existence and the spent inputs' plan stalls (funds are not lost, but the distribution/send path fails every broadcast, and any retry built the same way fails identically). Even at higher fee rates the transaction pays a materially lower effective rate than requested, degrading confirmation reliability. This is a concrete Medium impact: a deterministic, silent fee misconfiguration on a legitimate API path.

### Likelihood Explanation
The bug triggers deterministically whenever `SignableTransaction::new` is invoked with `Some(data)` — no special adversary action is needed beyond the library being used to attach OP_RETURN data (an advertised feature: "If data is specified, an OP_RETURN output will be added with it", and exercised by tests at `networks/bitcoin/tests/wallet.rs`). Whether the transaction becomes unrelayable depends on the chosen `fee_per_vbyte`; at the minimum rate it always fails. The primary caveat on likelihood is that the in-repo processor caller (`processor/src/networks/bitcoin.rs::make_signable_transaction`) currently passes `None` for data, so the reachable severity in production today depends on callers supplying OP_RETURN data.

### Recommendation
Pass the OP_RETURN output into `calculate_weight_vbytes` — e.g., extend its `payments`/output parameters to include the data output (or build the template `tx_outs` identically to the real `tx_outs`, including the OP_RETURN and change outputs) before computing `vbytes`, `needed_fee`, and the `TooLowFee` check. Both call sites (`send.rs` lines 204 and 226) must use the fully-populated output set so the signed transaction's real vsize matches the priced vsize.

### Proof of Concept
Conceptual, against `networks/bitcoin/src/wallet/send.rs`:

```rust
// inputs: a single ReceivedOutput with ample value
// addr: p2tr_script_buf(key).unwrap()
let data = vec![0u8; 80]; // max allowed, adds ~90+ non-witness bytes
let tx = SignableTransaction::new(inputs, &[(addr(), DUST)], None, Some(data), 1 /* sat/vB */)
  .unwrap(); // passes TooLowFee because vbytes was computed WITHOUT the OP_RETURN output

// The real transaction contains the extra OP_RETURN output:
assert_eq!(tx.transaction().output.len(), 2); // payment + OP_RETURN

// Its actual vsize is ~90+ bytes larger than the vsize used to derive needed_fee:
// needed_fee = 1 * vbytes_without_opreturn
// effective rate = needed_fee / real_vsize < 1 sat/vB
// => send_raw_transaction rejects it ("min relay fee not met") on every broadcast.
```

Verification path: construct the transaction, serialize `tx.transaction()`, compare `tx.transaction().vsize()` against `tx.needed_fee()` — the fee corresponds to a vsize that does not include the OP_RETURN output, demonstrating the omitted-parameter/underpriced-fee defect directly.
