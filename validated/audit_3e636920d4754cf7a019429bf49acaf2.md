## Finding: Diff-hunk expansion desyncs line-selection indices from the underlying `DiffSelection` bitmap, silently changing which lines get committed

### Title
Expanding a diff hunk upward shifts line indices without remapping the partial-selection state, causing unintended lines to be included/excluded from a commit - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
The reported Hyper.sol bug is a class of "value computed correctly relative to a *local unit* but never rescaled to the *global total*, so the final result silently diverges from what the user expects." The closest concrete analog in GitHub Desktop is the interaction between `expandTextDiffHunk`/`expandWholeTextDiff` (which mutate the *local* line layout of a diff hunk for display) and `DiffSelection` (which tracks partial line-staging state against *absolute* line indices computed from that layout). Expanding a hunk upward reindexes existing diff lines but the persisted `DiffSelection.divergingLines` set is never remapped, so a user's explicit include/exclude choice on a line can silently flip to the opposite state after expansion, corrupting what actually gets staged/committed.

### Finding Description
Partial-commit selection state is tracked per absolute diff-line index. Both the renderer (`getDiffRowsFromHunk`) and the patch generator (`formatPatch`) compute this index the same way: [1](#0-0) [2](#0-1) 

`absoluteIndex = hunk.unifiedDiffStart + lineIndex`, where `lineIndex` is the position of the line inside `hunk.lines`. The actual selected/deselected state is looked up in `DiffSelection.isSelected(absoluteIndex)`, which consults a `divergingLines: Set<number>` recorded against these same absolute indices: [3](#0-2) 

When a user expands a hunk upward via the "Expand Up" gutter control, `expandTextDiffHunk` inserts the newly revealed context lines **right after the hunk-header line and before the pre-existing lines**: [4](#0-3)  the resulting hunk keeps the *same* `hunk.unifiedDiffStart`: [5](#0-4) 

Because `hunk.unifiedDiffStart` is unchanged but `numberOfNewDiffLines` new lines were spliced in before the original Add/Delete lines, every pre-existing line's *position within `hunk.lines`* increases by `numberOfNewDiffLines`. Consequently its recomputed `absoluteIndex` (`unifiedDiffStart + lineIndex`) also increases by `numberOfNewDiffLines` — the same physical diff line now maps to a different absolute index than it did before expansion.

The expand handler only swaps the diff object in component state; it never updates or remaps `file.selection`: [6](#0-5) 

Compare this to `onClickHunk`, which does correctly call `this.props.onIncludeChanged` to persist selection changes against the *current* diff's indices: [7](#0-6) 

No equivalent step exists for expansion. The `divergingLines` set stored on `WorkingDirectoryFileChange.selection` therefore continues to reference the *old* (pre-expansion) indices while the UI and `formatPatch` query it with the *new* (post-expansion) indices for the very same source lines.

### Impact Explanation
If a user has partially staged a file (e.g., deselected one added/deleted line they don't want committed) and then clicks "Expand Up" on that hunk (or "Expand Whole File", which internally calls the same up-expansion path via `expandWholeTextDiff`), the deselected line's absolute index shifts. `isSelected()` is now evaluated against a stale set:
- For a file whose `defaultSelectionType` is `All` (the common case — most lines selected, a few explicitly excluded), the shifted line no longer matches any entry in `divergingLines`, so `isSelected()` returns `true` (falls back to the default) even though the user explicitly excluded it.
- The opposite can also occur for a `None`-default file with a few explicitly included lines: an intentionally *included* line can silently become excluded.

Either way, `formatPatch` (used to build the `git apply` patch for `git add -p`-style partial commits) will stage content the user did not intend, or drop content they did intend, with **no error, warning, or diff re-review forcing function** — this is a silent corruption of what the user commits, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires no attacker-controlled repository content beyond an ordinary diff with more than a `DefaultDiffExpansionStep` worth of unchanged context above the first shown hunk (a very common real-world layout) plus a user doing an everyday partial-commit workflow (deselect a line, then click "Expand Up" or "Expand whole file" to review context before committing). No malicious input, admin rights, or unusual interaction sequence is needed — this can happen from ordinary developer behavior on any legitimate diff.

### Recommendation
- Short term: When `expandTextDiffHunk`/`expandWholeTextDiff` shift the position of pre-existing lines within a hunk (i.e., "up" expansion or merges that prepend lines), remap the corresponding `DiffSelection.divergingLines` entries by the same offset before/alongside updating the displayed diff, or force the affected file's selection to be recomputed/re-validated (similar to the "selectable lines" repair path already used on diff reload) any time hunk layout changes.
- Long term: Add unit/integration tests asserting that a line's selected/deselected state (as observed via `formatPatch` output) is invariant across hunk expansion for the exact same underlying source line, and fuzz combinations of partial selections + expand-up/expand-down/expand-whole-file/merge-adjacent-hunk paths to catch other index-shifting cases.

### Proof of Concept
1. Modify a file with at least one hunk that has ≥ `DefaultDiffExpansionStep` lines of unchanged context above it, and stage a change with two adjacent added lines.
2. In the Changes view, deselect the second added line only (uncheck it) so the file selection becomes `Partial` with `divergingLines` containing that line's absolute index.
3. Click "Expand Up" on that hunk (or use "Expand whole file").
4. Observe that `expandTextDiffHunk` inserts new context lines ahead of the two added lines in `hunk.lines`, while `hunk.unifiedDiffStart` is unchanged (`app/src/ui/diff/text-diff-expansion.ts`, lines 302-325).
5. Commit the file. Inspect the generated patch produced by `formatPatch` (`app/src/lib/patch-formatter.ts`): the previously deselected added line is now included in the commit (or, in a `None`-default scenario, a previously included line is dropped) — despite no further user action to change its selection state.

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
