Based on my investigation, `precompiles/bank/bank.go`'s `send` method has a bug-class analog to the PROXY-protocol ACL bypass: it authorizes a fund transfer by trusting a caller-supplied address argument as the transfer's true origin, gated only by an incomplete identity check, while other precompiles in the same codebase (`sendNative`, `wasmd.execute`, `staking`/`gov`/`distribution` `Run`) explicitly guard against the exact bypass vector that `send` omits.

### Title
Bank precompile `send` omits the delegatecall guard present in sibling precompiles, allowing the `fromAddress` argument to be trusted without verifying it as the true transaction origin - (File: precompiles/bank/bank.go)

### Summary
The `bank` precompile's `send` method authorizes a `MsgSend` using a `fromAddress` argument taken directly from calldata, gating on `pointer.Cmp(caller) != 0` alone [1](#0-0) . Unlike its sibling method `sendNative` in the same file, which explicitly checks `ctx.EVMPrecompileCalledFromDelegateCall()` and rejects delegatecalls [2](#0-1) , and unlike `wasmd.execute`, which validates the calling contract against the registered pointer specifically when `ctx.EVMPrecompileCalledFromDelegateCall()` is true [3](#0-2) , `send` performs no such check at all.

### Finding Description
In `send`, the only access control is: the ERC20 native pointer registered for `denom` must equal `caller` [4](#0-3) . The `fromAddress` and `toAddress` used to build the `MsgSend` are decoded straight from `args[0]`/`args[1]` via `accAddressFromArg`, with no cross-check that `fromAddress` corresponds to the actual EVM account that initiated the call [5](#0-4) . This mirrors the ProxySQL flaw: an address field supplied in the message is trusted for authorization purposes without independently proving it as the caller's real identity, and the code that should reject the "unverifiable" path (delegatecall context, where `caller` can be manipulated relative to the executing contract) is simply missing here even though the same file demonstrates the correct pattern for a sibling method (`sendNative`).

This pattern is intentional in isolation: the ERC20 native pointer (`NativeSeiTokensERC20.sol`) is expected to be the only contract satisfying `pointer.Cmp(caller)`, and OpenZeppelin's `ERC20.transfer`/`transferFrom` are expected to set `from` to `msg.sender` (or a spender-authorized account) before calling `_update` → `BankPrecompile.send(from, to, denom, value)` [6](#0-5) . The security boundary therefore depends entirely on `caller` reliably identifying "the exact ERC20 pointer contract's own code executing", which is precisely the invariant that a delegatecall guard exists to enforce elsewhere in this codebase (see `sendNative`, `wasmd.execute`, `staking`/`gov`/`distribution.Run`). Because `send` lacks this guard, any code path where `caller` can be set to the pointer's address while the args (`fromAddress`) are attacker-controlled and unconstrained by the pointer's own `_update` logic — e.g., a future or legacy pointer implementation, or any other contract at that call frame — would let an attacker move funds out of an arbitrary `fromAddress` without ever having authorization from that address, exactly as the ProxySQL bug let a spoofed `client_addr` field bypass an ACL keyed on it.

### Impact Explanation
If exploitable, this allows unauthorized transfer of bank-module funds (native `usei`/tokenfactory-denominated tokens with a registered ERC20 pointer) out of arbitrary Sei addresses, i.e., direct fund loss — a "Critical" impact category consistent with the ADO/OSV report's "unauthorized transfer via precompile" bar.

### Likelihood Explanation
Likelihood is **not proven** by this investigation. I was only able to confirm that the delegatecall guard is asymmetrically applied within `precompiles/bank/bank.go` (`sendNative` has it, `send` does not), and that identical protections exist in `wasmd.execute`'s delegatecall branch. I could not confirm from the indexed code whether the currently deployed `NativeSeiTokensERC20.sol` pointer's `_update` fully constrains `from`/`to` in all call paths, nor whether any other contract can ever satisfy `pointer.Cmp(caller)` in a delegatecall frame with attacker-chosen `fromAddress`. Establishing concrete exploitability would require tracing exactly how `caller` is computed by the EVM dispatcher during a delegatecall into the bank precompile address versus a plain call (this mechanism lives in the go-ethereum-derived interpreter/precompile-dispatch code, which I did not have visibility into within the indexed context) and whether a malicious contract could register itself as, or spoof, the ERC20 native pointer for a given denom.

### Recommendation
Add the same guard used in `sendNative` and `wasmd.execute` to `send`: reject the call when `ctx.EVMPrecompileCalledFromDelegateCall()` is true, and/or additionally verify (as `wasmd.execute` does) that in a delegatecall frame the `callingContract` — not just `caller` — matches the registered pointer for `denom`, ensuring the pointer's own code (and its `_update` authorization logic) is unavoidably in the call path before `fromAddress` is trusted.

### Proof of Concept
Not constructed — a concrete PoC would require confirming, via the EVM interpreter/precompile dispatch code (not available in the indexed context), the exact semantics of `caller` vs. `callingContract` during a delegatecall into a precompile address, and whether any contract can be made to satisfy `GetERC20NativePointer(denom) == caller` while supplying an arbitrary `fromAddress`. Given the "Reject ... mocked-only paths" and "Prove root cause with exact file/function support" validation bar, and that I cannot fully prove the exploit path with the tools available, I present this as a structural asymmetry/analog rather than a confirmed working exploit.
