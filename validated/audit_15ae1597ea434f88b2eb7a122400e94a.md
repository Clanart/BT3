## Title
Missing path-separator boundary check in `resolveWithin()` allows sibling-directory prefix collision to escape the intended root — (File: `app/src/lib/path.ts`)

## Summary
`_resolveWithin()` validates that a resolved path stays inside a given root directory by doing a raw string comparison: [1](#0-0) 

```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)

return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` has no notion of path segment boundaries, so a `realResolved` value that merely shares `realRoot` as a *string prefix* — but is actually a sibling path — will incorrectly pass validation. For example, if `realRoot` is `/Users/alice/repo`, a `realResolved` of `/Users/alice/repo-evil/secret.txt` satisfies `startsWith('/Users/alice/repo')` even though `repo-evil` is a completely different, sibling directory outside the intended tree.

## Finding Description
`resolveWithin()` (and its `resolveWithinPosix`/`resolveWithinWin32` wrappers) is used as a security boundary to make sure repository-relative paths coming from untrusted sources (conflict-resolution file lists, deep-link file paths, Copilot conflict resolutions) cannot escape the repository working directory, including via symlinks checked into the repo, as the existing unit tests demonstrate: [2](#0-1) 

The function correctly resolves symlinks via `realpath` for both the root and the target before comparing, which defeats simple `..`/absolute-path traversal and direct symlink escapes that land outside the root entirely. However the final containment check at line 71 only verifies a *string prefix* match rather than verifying that `realResolved` is exactly `realRoot` or is `realRoot + path separator + ...`. This is the classic "prefix without boundary" path-validation flaw (e.g. `/repo` vs `/repo-evil`, or `/repo` vs `/repository`).

A repository can contain a tracked symlink (with `core.symlinks` enabled) whose target, once resolved with `realpath`, lands in a directory that exists on disk as a sibling of the repository root and whose name happens to begin with the root directory's basename (e.g. `repo-backup`, `repository`, `repo.bak`). In that case `realResolved.startsWith(realRoot)` returns `true` even though the resolved path is entirely outside the repository tree, and `resolveWithin()` returns a path pointing outside the intended tree instead of `null`.

## Impact Explanation
Depending on the call site, this can lead to:
- Reading and exfiltrating file contents from outside the repository: `buildConflictContext()` calls `resolveWithin(workingDirectory, file.path)` and, if it returns a non-null path, reads the file and sends its content to the Copilot SDK. [3](#0-2) 
- Writing attacker-influenced content to a file outside the repository: the app store resolves a conflict-resolution path with `resolveWithin(repository.path, resolution.path)` and then `writeFile`s the resolved path. [4](#0-3) 
- Revealing/opening arbitrary file-system locations via `shell.showItemInFolder` from a deep-link `filepath`. [5](#0-4) 

These match the "file write or read outside the repo" valid-impact category when the containment check is bypassed.

## Likelihood Explanation
Likelihood is low-to-moderate in practice. Exploiting this specific boundary flaw requires a `realpath`-resolvable sibling path to *already exist on disk* next to the cloned repository, with a name that is a string-prefix superset of the repository directory's basename (e.g. cloning into `repo` while a `repo-secrets` or `repository` directory happens to already exist alongside it). The attacker fully controls the symlink and its target string (via repository content with `core.symlinks` enabled), but does not control the user's local directory layout or naming, so a reliable, generically-triggerable exploit chain requires either a coincidental/naming-convention-driven sibling directory or some other means of getting such a path to exist. The underlying code defect (missing separator-boundary check) is nonetheless real and should be fixed regardless of how hard a specific instance is to stage, since directory layouts with predictable sibling names (backup folders, `-old`/`-copy`/`.bak` suffixes, multiple related repos cloned side by side) are a plausible real-world condition.

## Recommendation
Change the containment check to require an exact match or that the boundary is a path separator, e.g.:
```ts
const relative = Path.relative(realRoot, realResolved)
return relative === '' || (!relative.startsWith('..') && !Path.isAbsolute(relative))
  ? resolved
  : null
```
or equivalently ensure `realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)`, using the platform-appropriate separator function passed in `options`.

## Proof of Concept
1. On a POSIX system, create `realRootDir = /tmp/x/repo` and a sibling `/tmp/x/repo-evil/secret.txt` containing sensitive content.
2. Inside `repo`, create (and commit, simulating a cloned repo with `core.symlinks=true`) a symlink `dangerzone -> ../repo-evil/secret.txt`.
3. Call `resolveWithin('/tmp/x/repo', 'dangerzone')`.
4. Trace through `_resolveWithin`: `realRoot = '/tmp/x/repo'`, `realResolved = '/tmp/x/repo-evil/secret.txt'`.
5. `realResolved.startsWith(realRoot)` evaluates `'/tmp/x/repo-evil/secret.txt'.startsWith('/tmp/x/repo')` → `true`, so the function returns the resolved symlink path instead of `null`, even though `/tmp/x/repo-evil` is not under `/tmp/x/repo`.

This can be verified directly against the code at [6](#0-5)  and contrasted with the existing negative test case that only covers symlinks resolving to unrelated, non-prefix-colliding paths. [2](#0-1)
