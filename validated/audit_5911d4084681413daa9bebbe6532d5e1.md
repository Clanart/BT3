### Title
`NewContext4096Secure` Ships a KZG Trusted Setup With a Publicly-Documented Secret (`alpha=1337`), Enabling Forged Opening Proofs - (File: `api.go`, `trusted_setup.go`)

### Summary
`NewContext4096Secure` in `api.go` is documented as using "a trusted setup file that was generated in an official ceremony... taken from the ethereum KZG ceremony," and its name strongly signals it is the production-grade, secure entry point for creating a `Context`. However, the function actually unmarshals `testKzgSetupStr`, an embedded JSON blob whose own in-repo documentation in `trusted_setup.go` states plainly: "This is the test trusted setup, which SHOULD NOT BE USED IN PRODUCTION. The secret for this [is] 1337." [1](#0-0) [2](#0-1) 

### Finding Description
KZG's soundness (the property that a "proof" can only verify against the actual polynomial behind a commitment) depends entirely on the toxic-waste scalar `alpha` used to build the SRS being unknown to everyone. `newMonomialSRSInsecureUint64` in `internal/kzg/srs_insecure.go` shows precisely how an SRS is built directly from a known `bAlpha` — `commitKey.G1[0] = gen1Aff`, `openKey.AlphaG2.ScalarMultiplication(&gen2Aff, bAlpha)`, and successive powers of `alpha` multiplied into the generator. The `Secure`-named production path (`NewContext4096Secure`) loads the SRS from `trusted_setup.json` (via `testKzgSetupStr`), which per the adjacent code comment was generated with exactly this kind of known-secret procedure, using `alpha = 1337`.

Once `alpha` is public, anyone can construct `(commitment, z, y, proof)` tuples that satisfy the KZG pairing check `e(C - y·G1, G2) == e(pi, alpha·G2 - z·G2)` for an arbitrary chosen `y` at an arbitrary point `z`, by solving `pi = (C - y·G1) / (alpha - z)` — a simple scalar-field division, entirely independent of the actual polynomial that produced `C`. This breaks the exact equality this library is meant to enforce: that a verified proof corresponds to a *true opening* of the committed polynomial.

The doc comment's claim that this setup came from "the ethereum KZG ceremony" is directly contradicted by the comment two lines above the embed directive in `trusted_setup.go`, confirming the setup shipped as "Secure" is not the real ceremony output but a toy setup with a disclosed secret.

### Impact Explanation
This is a Critical-severity soundness break: any commitment/proof verified through a `Context` obtained via `NewContext4096Secure()` can be forged. An attacker who reads the (openly documented) secret `alpha=1337` can produce a KZG opening proof that verifies successfully for any claimed evaluation `y` at any point `z`, for any commitment `C`, without ever knowing the underlying blob/polynomial. This is exactly the class of bug called out as in-scope: "a proof ... accepted that is not a true opening."

### Likelihood Explanation
The secret is not hidden behind any privilege boundary, side channel, or external compromise — it is stated directly in a source-code comment shipped with the library (`trusted_setup.go:36`), immediately adjacent to the `//go:embed` directive that wires it into the function whose name (`NewContext4096Secure`) implies it is safe for production use. No attacker action beyond reading the public repository and doing elementary scalar-field arithmetic is required.

### Recommendation
- Ensure `NewContext4096Secure` embeds the genuine, ceremony-produced Ethereum KZG trusted setup (the real production SRS matching the consensus-specs / c-kzg reference data), not a toy setup with a known `alpha`.
- Rename or clearly gate the test setup (and any function that loads it) so it cannot be confused with, or accidentally substituted for, the production path.
- Add a CI check that hashes/pins the commitment key produced by `NewContext4096Secure()` against the known-correct public Ethereum ceremony setup so any future swap-in of a test/insecure SRS is caught automatically.
- Correct the doc comment on `NewContext4096Secure` if it is ever legitimately intended for test data, so it does not falsely claim ceremony provenance.

### Proof of Concept
1. `ctx, _ := goethkzg.NewContext4096Secure()` — obtains a `Context` whose G1/G2 points were built from `alpha = 1337` (per `trusted_setup.go:36`).
2. Offline, using the public generator points and `alpha = 1337`, pick any existing commitment `C` (e.g., from a legitimate blob) and an arbitrary desired `(z, y)` pair.
3. Compute `pi = (C - y·G1) · (alpha - z)^{-1} mod r` using standard bls12-381 scalar/point arithmetic (no polynomial or blob data needed).
4. Submit `(C, z, y, pi)` to the context's proof-verification routine (built from `openKey4844`/`openKey7594` derived in `NewContext4096`). Verification succeeds for the forged `y`, even though `C` was never actually a commitment to a polynomial evaluating to `y` at `z`.
