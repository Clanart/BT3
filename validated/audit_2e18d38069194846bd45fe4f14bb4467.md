### Title
Quadratic Lagrange interpolation on attacker-controlled `n`/`t` in `ThresholdKeys::read` enables CPU-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
The external report concerns a small/malformed input triggering disproportionate CPU work (exponential decoding). The Serai analog is `ThresholdKeys::read`, which accepts attacker-chosen `t` and `n` (each a u16, up to 65535) and then calls `ThresholdKeys::new`, which computes the group key by Lagrange-interpolating verification shares `1..=t`. Each `interpolation_factor` call iterates over all `t` included participants, yielding O(t²) scalar multiplications — roughly 4×10⁹ field multiplications for `t = n = 65535` — from a ~2–4 MB input.

### Finding Description
`ThresholdKeys::read` deserializes `t`, `n`, and `i` directly from the stream with no upper bound beyond `u16` (`crypto/dkg/src/lib.rs:591-602`). With `interpolation` byte `1` (Lagrange), it reads `n` verification shares (`crypto/dkg/src/lib.rs:620-623`) and calls `ThresholdKeys::new`. In `new`, the group key is computed as `verification_shares[i] * interpolation_factor(*i, &t)` summed over `i ∈ 1..=t` (`crypto/dkg/src/lib.rs:376-378`). `Interpolation::Lagrange`'s `interpolation_factor` performs a full inner loop over every participant in `included` plus one `invert()` per factor (`crypto/dkg/src/lib.rs:229-247`). Total cost: t × (t iterations + 1 inversion) ≈ t² scalar multiplications.

The same quadratic pattern re-appears in `ThresholdKeys::view`, which calls `interpolation_factor` once per included signer (`crypto/dkg/src/lib.rs:501-506`), so each subsequent signing attempt against crafted keys repeats the cost.

This is an algorithmic-complexity DoS matching the CWE-400/CWE-407 class of the report: work grows quadratically in a length field the attacker supplies, while the input itself stays small (n point encodings ≈ 32–57 bytes each). The sink `ThresholdKeys::read` is explicitly listed as a reachable deserialization entry point.

### Impact Explanation
An unprivileged party who can feed untrusted bytes to `ThresholdKeys::read` (e.g., keys material carried in protocol messages, or any consumer deserializing peer-supplied threshold keys) causes the victim to burn ~10⁹–10¹⁰ scalar operations reconstructing the group key, stalling the thread for a long period per message. Repeated submissions amplify the effect. Availability impact only — no memory corruption or key disclosure — consistent with a Medium severity.

### Likelihood Explanation
Exploitation requires an integration point where remote input reaches `ThresholdKeys::read`. The cost is triggered deterministically by `t = n = 65535` with Lagrange interpolation; all required bytes must be present (the read is linear in bytes), so the asymmetry is quadratic-CPU-per-byte rather than input-free. Because `Participant` indexes are generated as `1..=n`, no validity trick is needed — the computation runs to completion on well-formed input.

### Recommendation
Cap `n` (and hence `t`) at a protocol-level maximum inside `ThresholdKeys::read`/`ThresholdParams::new` before performing interpolation, or bound total interpolation work (e.g., reject `t` above a sane limit such as a few thousand). Alternatively, compute Lagrange denominators via a single batched inversion and share numerator products incrementally to reduce the per-factor cost.

### Proof of Concept
Conceptually: construct a serialized `ThresholdKeys` blob for a ciphersuite `C` with `t = n = 0xFFFF`, `i = 1`, interpolation byte `1` (Lagrange), one scalar for `secret_share`, and `n` valid encodings of arbitrary `C::G` points (e.g., `C::generator()` repeated). Feeding these ~2–4 MB of bytes to `ThresholdKeys::<C>::read` forces `ThresholdKeys::new` to execute ≈ 65535² ≈ 4.3×10⁹ `F` multiplications plus 65535 inversions to derive `group_key` at `crypto/dkg/src/lib.rs:376-378`, blocking the caller.
