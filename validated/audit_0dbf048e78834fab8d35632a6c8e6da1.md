### Title
Bitcoin `OP_RETURN` outputs are omitted from fee/size accounting, causing underpriced signed transactions - ([File: `networks/bitcoin/src/wallet/send.rs`])

### Summary
`SignableTransaction::new` adds the attacker-controlled `data` payload as an `OP_RETURN` output before estimating transaction weight, but the size estimator only receives `payments` and therefore never accounts for that output. A transaction can consequently be signed with a fee below both the requested `fee_per_vbyte` and Bitcoin’s default minimum relay fee, producing a consensus-valid transaction that standard nodes will not relay.

### Finding Description
`SignableTransaction::new` validates that `data` contains at most 80 bytes and appends an `OP_RETURN` output to `tx_outs` before estimating the transaction size. [1](#0-0)  The initial fee estimate calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, passing the payment list rather than the actual `tx_outs` list. [2](#0-1)  The same omission occurs when a change output is considered, because the estimator is again called with `payments` rather than the final output list containing `OP_RETURN`. [3](#0-2) 

Inside `calculate_weight_vbytes`, the mock transaction outputs are generated solely from the `payments` argument, with `change` optionally appended; there is no parameter representing arbitrary data or other zero-valued outputs. [4](#0-3)  The resulting weight and virtual size are used as `fee_per_vbyte * vbytes`, while the eventual transaction contains the additional serialized `OP_RETURN` output. [5](#0-4) 

The code checks the underestimated `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE`, but the signed transaction’s actual virtual size is larger. [6](#0-5)  `fee()` later derives the paid fee from inputs minus final outputs, so adding a zero-valued `OP_RETURN` does not raise the fee to compensate for its added transaction size. [7](#0-6) 

### Impact Explanation
An unprivileged caller controls the `data` argument and can force the largest permitted `OP_RETURN` payload, adding 92 serialized bytes for an 80-byte pushdata output while the estimator ignores it. [1](#0-0)  At a fee rate equal to the default minimum relay rate, the signed transaction pays approximately 92 satoshis less than required for its actual virtual size. [8](#0-7)  The threshold signatures remain valid, but the resulting transaction may be rejected by standard relay policy, leaving the selected UTXOs unspent and the withdrawal unavailable until another spend is constructed and signed. [9](#0-8) 

### Likelihood Explanation
The trigger requires only calling the public `SignableTransaction::new` API with a nonempty `data` value and a fee rate at or near the minimum accepted value. [10](#0-9)  No malformed scalar, invalid signature share, malicious validator, leaked key, or protocol violation is needed; the vulnerable path is reached whenever the caller requests arbitrary data along with a payment. [11](#0-10) 

### Recommendation
Calculate weight and virtual size from the complete output vector actually placed into the transaction, including zero-valued `OP_RETURN` outputs, rather than reconstructing outputs only from `payments`. [12](#0-11)  Alternatively, extend `calculate_weight_vbytes` with a `data: Option<&[u8]>` parameter and append the exact `OP_RETURN` output to its mock transaction before measuring it. [13](#0-12) 

### Proof of Concept
For a transaction with one Taproot input, one ordinary payment, no change output, `data = vec![0; 80]`, and `fee_per_vbyte` equal to the minimum relay rate, `tx_outs` contains both the payment and the `OP_RETURN`. [14](#0-13)  The estimator measures only the payment output, so `needed_fee = fee_per_vbyte * vbytes_without_op_return` while the final signed transaction is `vbytes_without_op_return + 92` virtual bytes. [15](#0-14)  Since the `OP_RETURN` has zero value, `fee()` still reports the unchanged underestimated amount, confirming that the additional bytes were not charged. [7](#0-6)

    inputs: usize,

    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
