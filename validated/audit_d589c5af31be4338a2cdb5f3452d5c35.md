### Title
`DkgConfirmer` deterministically re-derives signing nonces from a cached seed on every `share`/`complete` call, so signing a distinct `set_keys_message` (or distinct signer set) for the same attempt reuses Schnorr nonces and leaks the validator's private key - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
The CVE is a use-after-free: an `sk_buff` remains referenced by a work queue after userspace has already consumed and freed it. The structural analog in Serai is a **use-after-consume of a signing secret**: `SigningProtocol::preprocess_internal` caches a single FROST preprocess seed under `CachedPreprocesses` keyed only by `(context, attempt)`, and `share_internal` regenerates the *identical* nonces from that seed every time it runs — i.e., it keeps referencing nonce material that was already "consumed" by a previous `sign()` call. `DkgConfirmer::share` (via `generated_key_pair`) and `DkgConfirmer::complete` both route through `share_internal` for the same `(b"DkgConfirmer", attempt)` context, and `generated_key_pair` overwrites `DkgKeyPair`/`KeyToDkgAttempt` unconditionally, permitting a second confirmation signature over a different `key_pair`. Two Schnorr signature shares produced under the same nonce scalar but different challenges/bindings yield the validator's Ristretto secret key by linear combination.

### Finding Description
`preprocess_internal` builds an `AlgorithmSignMachine` via `from_cache` with the seed stored in `CachedPreprocesses` under `self.context = (b"DkgConfirmer", attempt)`. `seeded_preprocess` in `crypto/frost/src/sign.rs` deterministically regenerates `nonces` and `commitments` from that seed via `ChaCha20Rng`, so every invocation of `share_internal` for one attempt produces the same nonce scalars `k`. The seed is never rotated, invalidated, or deleted after `sign` consumes it — the direct analog of the backlog queue holding a reference to an skb after `consume_skb` freed it.

Two distinct signing events reuse `k`:

1. `generated_key_pair` (handle.rs:47-60) calls `DkgConfirmer::share`, which signs `set_keys_message(set, removed, key_pair)`. `DkgKeyPair::set` and `KeyToDkgAttempt::set` are unconditional overwrites (handle.rs:54-55), so a second `GeneratedKeyPair` carrying a different `key_pair` for the same `attempt` produces a second share over a *different message* with the same nonce.
2. `DkgConfirmer::complete` calls `share_internal` again (signing_protocol.rs:321-326) to reconstruct the machine; any divergence in `removed` or participant set between the first share and completion produces a second share under `k` with a different Lagrange coefficient/challenge.

For Schnorr shares `s1 = k + c1·λ1·x` and `s2 = k + c2·λ2·x`, the key recovers as `x = (s1 − s2) / (c1·λ1 − c2·λ2)`. Both shares and both signatures are published on the public tributary chain (`DkgConfirmed` transactions), so the inputs needed for recovery are public.

### Impact Explanation
The leaked key is the validator's MuSig/Ristretto signing key — the root of trust for the coordinator (`key` field, signing_protocol.rs:93). Recovery enables forging that validator's signed tributary transactions and its weight in any future validator-set signing, including `set_keys` confirmations. This is secret-key recovery from publicly observable data, matching the acceptance bar for a Critical/High finding.

### Likelihood Explanation
Requires the coordinator to run `share_internal` twice for one attempt over differing inputs. The `complete` path guarantees a second `share_internal` call per attempt; whether its signing set/message differs from the first depends on `removed_as_of_dkg_attempt` stability (uncertain — likely stable). The stronger trigger is a repeated `GeneratedKeyPair` for the same attempt: the code has no guard (`if DkgKeyPair::get(...).is_some() { return }`) preventing it, though I could not fully verify in main.rs whether the processor can realistically emit a second, differing key pair for the same attempt. If repeated emission is reachable, likelihood is meaningful since processor-side retry/restart paths exist.

### Recommendation
Delete or rotate the `CachedPreprocesses` entry after `sign` is invoked (consume-on-use), or key the cache by a value binding the full session (e.g., include a hash of `key_pair`/`removed` or a monotonic per-attempt counter) so re-signing with different inputs derives fresh nonces. Additionally, guard `generated_key_pair` to ignore a second `GeneratedKeyPair` for an attempt that already has `DkgKeyPair` set.

### Proof of Concept
```
// Preconditions: validator V participates in DKG attempt A.
1. Processor emits GeneratedKeyPair(key_pair_1, A).
   Coordinator: DkgKeyPair::set(A, key_pair_1); DkgConfirmer::share(preprocesses, key_pair_1)
     -> sign(set_keys_message(..., key_pair_1)) with cached-seed nonces k
     -> publishes DkgConfirmed { share: s1 }  (s1 = k + c1·λ·x)
2. Processor emits GeneratedKeyPair(key_pair_2, A), key_pair_2 != key_pair_1.
   Coordinator: DkgKeyPair::set(A, key_pair_2)  // unconditional overwrite
     -> DkgConfirmer::share(...) regenerates identical nonces k from the same
        CachedPreprocesses[(b"DkgConfirmer", A)] seed
     -> publishes DkgConfirmed { share: s2 }  (s2 = k + c2·λ·x, c1 != c2 since msg differs)
3. Any observer reads s1, s2 and both set_keys_messages from the tributary chain:
     x = (s1 - s2) * inverse(c1 - c2) * inverse(λ)
   -> recovers V's Ristretto secret key.
```
