Based on the code reviewed, the vulnerability is real and confirmed by `create_payout_txhandler`.

### Title
Payout OP_RETURN operator-pubkey binding is unsigned, letting anyone rewrite the reimbursement payer for a mined payout tx - (core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` signs the payout transaction with a `SinglePlusAnyoneCanPay` key-spend witness that only commits to input 0 and output 0 (the user payout output). Output 2, the OP_RETURN carrying `operator_xonly_pk.serialize()` used to attribute the payout to the funding operator, is unsigned and can be swapped or dropped by anyone who relays a modified copy of the transaction before the honest operator's own broadcast is mined.

### Finding Description
The binding the system relies on is: `payout_payer_operator_xonly_pk` stored for withdrawal `i` == the operator who actually funded output 0 of the mined payout transaction for `i`.

In `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436), the transaction has three outputs — user payout (output 0), anchor (output 1), OP_RETURN with `operator_xonly_pk` (output 2) — but only `set_p2tr_key_spend_witness(&user_sig, 0)` is applied to input 0, using a signature the user produced with `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` semantics (`taproot::Signature`/`SinglePlusAnyoneCanPay`, per the withdrawer-supplied signature described in `Operator::withdraw`). `SIGHASH_SINGLE` only commits the signature to the output at the same index as the input (output 0); `ANYONECANPAY` allows arbitrary other inputs. Critically, neither flag commits to output 2 (the OP_RETURN) or output 1 (anchor), so those bytes can be freely rewritten by any party without invalidating the witness on input 0.

An attacker observes operator O's funded, unbroadcast payout transaction (e.g., in the mempool after O's RBF-funding via `ExtendedBitcoinRpc::fund_raw_transaction`), copies input 0 (same OutPoint + witness) and output 0 (same script_pubkey/amount), and either strips output 2 or writes an arbitrary 32 bytes there, then gets this variant mined first.

`Verifier::update_finalized_payouts` (core/src/verifier.rs:2283-2353) then scans the mined block, extracts the OP_RETURN via `get_first_op_return_output` + `parse_op_return_data`, and derives `operator_xonly_pk` from it (core/src/verifier.rs:2319-2321). If parsing fails or yields an invalid x-only key, `operator_xonly_pk` is `None` and gets persisted as `NULL` via `update_payout_txs_and_payer_operator_xonly_pk` (core/src/verifier.rs:2345-2350) — with no cross-check against who actually supplied output 0's funds.

Downstream, `PayoutCheckerTask::run_once` (core/src/task/payout_checker.rs:39) calls `get_first_unhandled_payout_by_operator_xonly_pk(O)`, which filters strictly on the stored `payout_payer_operator_xonly_pk` column. Since that column is now `NULL` (or a forged key ≠ O), withdrawal `i` never surfaces for O, so O never proceeds to `handle_finalized_payout` / kickoff creation for that withdrawal, permanently losing the ability to be reimbursed for funds O already fronted.

No existing guard intercepts this: `is_deposit_valid`/`SPV::verify`/`lc_proof_verifier` validate deposit and withdrawal existence but not payer attribution; there is no on-chain commitment (e.g., a taproot script requiring the OP_RETURN, or covering it under the signed sighash) binding output 2's content to input 0's spender.

### Impact Explanation
An honest operator who fronted a legitimate withdrawal via their own funds becomes permanently unable to claim Reimburse for that withdrawal, since the finalized-payout record used to gate kickoff eligibility (`payout_payer_operator_xonly_pk`) no longer matches them. This is a direct loss of the operator's collateral/fronted capital with no recovery path in-protocol, matching the "Critical: an honest operator permanently unable to be reimbursed" category. The attack costs the attacker only a small fee bump to get their variant mined first (mining is probabilistic but the attacker only needs to win the race once per targeted withdrawal), and is repeatable across any withdrawal/operator pair since the missing commitment is structural to `create_payout_txhandler`, not specific to one instance.

### Likelihood Explanation
Preconditions are realistic and match normal operation: a withdrawal with a valid Citrea state and a `SinglePlusAnyoneCanPay`-signed input already exists once a user withdraws, and operators regularly compete/race to fund and broadcast payouts (RBF-funding is explicitly part of the design). Any unprivileged party who monitors the mempool for such payout transactions can construct and rebroadcast a fee-bumped variant with a tampered OP_RETURN; this requires no special keys, no majority hashrate, and no privileged role — only mempool visibility and normal fee-bumping. This is feasible today, at low BTC cost (fee difference to win the race), and repeatable for every withdrawal handled this way.

### Recommendation
Bind the OP_RETURN operator-attribution output to the signed sighash so it cannot be altered independently of the user's authorization — e.g., have the withdrawer sign with `SIGHASH_ALL` (or `SIGHASH_ALL|ANYONECANPAY` if third-party funding must remain possible) covering all outputs, or otherwise commit the operator pubkey inside a script/output whose spend the user's signature covers. Alternatively, have verifiers cross-check the funding source of output 0 (e.g., via the specific outpoint/witness structure previously registered by operator O for this withdrawal) rather than trusting an unauthenticated OP_RETURN payload.
