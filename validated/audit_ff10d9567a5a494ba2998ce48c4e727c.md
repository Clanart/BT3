### Title
Price-feed batch update aborts remaining independent feeds on first failure, delaying liquidations - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`write-feeds` folds over an optional list of up to 3 independent Pyth price-feed updates using `write-feed`. Because `write-feed` short-circuits the fold as soon as any single feed update fails, an unrelated failure on one feed silently prevents the remaining, otherwise-valid feed updates from ever being attempted, and the whole `try!`-wrapped call then reverts the entire hot-path transaction (`borrow`, `collateral-add`, `collateral-remove`, `liquidate`, `liquidate-redeem`).

### Finding Description
`write-feed` is defined as a fold accumulator over a `response`: [1](#0-0) 

`write-feeds` folds this over the caller-supplied list of up to 3 feeds: [2](#0-1) 

Because `fold` passes the previous iteration's result as `status` into the next call, once one feed produces an `error-status`, every subsequent `write-feed` invocation hits the `error-status status` branch and returns immediately without even attempting the Pyth `verify-and-update-price-feeds` call for the remaining feeds in the list. The three feeds (e.g. STX, BTC, USDC) are independent price sources for unrelated assets — there is no reason a verification failure on one should prevent updating the others, exactly as in the ZetaChain analog where an error updating one chain's gas price incorrectly aborted updates for the rest.

`write-feeds` is called via `try!` at the very start of the hot-path operations, so any single feed failure reverts the entire call: [3](#0-2) [4](#0-3) 

A realistic failure mode for `update-failed` is not malformed data but simple staleness/ordering: Pyth's `verify-and-update-price-feeds` typically rejects a VAA whose timestamp is not newer than the already-stored on-chain price. In a busy or volatile market, it is common for two transactions in close succession to submit overlapping feed sets (e.g. STX+BTC), where one feed was already advanced by another transaction moments earlier. Under the current fold-abort logic, if the *first* feed in the caller's list has already been updated (yielding `update-failed`/`ERR-PRICE-FEED-UPDATE-FAILED`), the *second*, still-necessary and valid feed for a different asset is never attempted, and the whole transaction — including a legitimate `liquidate` call — reverts via `oracle-timestamp-fresh`/`ERR-ORACLE-INVARIANT` failing downstream on the stale asset that never got updated.

### Impact Explanation
Liquidators depend on `write-feeds` to atomically refresh both the collateral and debt asset prices before `liquidate` computes health. If refreshing one of those independent feeds fails for reasons unrelated to the other (e.g., a race where a third party already advanced that specific feed in the same block), the currently-necessary refresh for the other asset is skipped and the entire liquidation call reverts. During periods of high volatility/congestion — precisely when timely liquidation matters most — this repeatedly blocks liquidation attempts, extending the window an under-collateralized position remains unliquidated. This is a temporary freezing of the ability to liquidate/protect funds and increases bad-debt/insolvency risk for the protocol, landing in the in-scope High impact class (temporary freezing of funds), with a downside risk toward protocol insolvency if unhealthy positions accumulate further losses while liquidation keeps failing.

### Likelihood Explanation
The precondition (two feeds submitted together, one already fresh from a concurrent transaction) is a normal, expected occurrence in any market with concurrent users, not an exotic edge case, so likelihood of the underlying trigger is moderate-to-high in busy markets; the resulting revert requires no attacker action, only ordinary transaction interleaving.

### Recommendation
Change `write-feed`/`write-feeds` so that a failure on one feed does not prevent attempting the remaining, independent feeds — e.g., accumulate per-feed success/failure in the fold state (similar to the pattern already used in `iter-price-multi`) but continue processing every feed regardless of prior failures, only surfacing an error for the specific feed(s) that failed rather than aborting the whole batch, or treat "already up to date" Pyth failures as non-fatal instead of propagating them as `ERR-PRICE-FEED-UPDATE-FAILED`.

### Proof of Concept
1. Two feeds are needed for `liquidate`: `feed_A` (collateral asset) and `feed_B` (debt asset), submitted as `(list feed_A feed_B)`.
2. Another transaction in the same block already advanced the on-chain price for `feed_A` to the same or newer timestamp.
3. `write-feeds` folds: `write-feed feed_A (ok true)` → Pyth's `verify-and-update-price-feeds` returns `update-failed` (not newer) → result becomes `ERR-PRICE-FEED-UPDATE-FAILED`.
4. `write-feed feed_B (err ERR-PRICE-FEED-UPDATE-FAILED)` matches the `error-status` branch and returns the same error immediately — `feed_B` (for the debt asset, which genuinely needed the update and would have succeeded) is never submitted.
5. `(feeds-check (try! (write-feeds price-feeds)))` in `liquidate` propagates the error, reverting the entire liquidation, even though the debt asset's price could have been legitimately refreshed and the position is genuinely liquidatable.
