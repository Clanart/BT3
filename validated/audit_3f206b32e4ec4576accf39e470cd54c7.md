### Title
Coinbase outputs are reported as spendable before maturity - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` scans every transaction in a block, including the coinbase transaction, and returns matching outputs as `ReceivedOutput`s. A miner can send a coinbase output to a registered Taproot script, after which Serai reports it as received even though consensus prevents it from being spent for 100 blocks. Downstream transaction construction treats that result as a normal spendable input and will produce a transaction rejected by Bitcoin consensus.

### Finding Description
`Scanner::scan_transaction` matches only `output.script_pubkey` against registered scripts and constructs a `ReceivedOutput` without checking whether the containing transaction is a coinbase. `Scanner::scan_block` invokes `scan_transaction` for every transaction in `block.txdata`, including `block.txdata[0]`. `SignableTransaction::new` then accepts each `ReceivedOutput`, converts its `outpoint` into a transaction input, and treats its value as available spendable balance. ### Impact Explanation
An attacker mining a block can cause Serai to report funds as received before those funds are spendable. If those funds are selected automatically, Serai can build and threshold-sign an invalid transaction spending an immature coinbase output. This can cause incorrect balance reporting, wasted signing rounds, failed withdrawals, and persistent selection of an unspendable output until maturity is independently accounted for.

### Likelihood Explanation
The condition is directly reachable by any miner that creates a coinbase output to one of Serai's scanned Taproot scripts. No private key material, malformed encoding, collusion, or trusted component is required. The probability depends on whether a miner controls a block containing such an output, but the vulnerable behavior is deterministic once that block is scanned.

### Recommendation
Do not return coinbase outputs from `scan_block`, or carry coinbase status and confirmation height in `ReceivedOutput` so consumers can enforce the 100-block maturity rule. Prefer explicitly iterating `block.txdata[1..]` in `scan_block`, while retaining a separate API for intentionally observing coinbase outputs if needed.

### Proof of Concept

// A miner creates a block whose coinbase pays to a script registered

let block: Block = attacker_mined_block_with_coinbase_to_serai_script();
let outputs = scanner.scan_block(&block);

assert_eq!(outputs.len(), 1);
assert_eq!(outputs[0].outpoint().vout, 0);

// `outputs[0]` is reported as received, but its outpoint references
// the coinbase at block.txdata[0]. Passing it to
// `SignableTransaction::new` creates an input that Bitcoin rejects
// until the coinbase is 100 blocks old.
let tx = SignableTransaction::new(
  vec![outputs[0].clone()],
  &[(payment_script, payment_amount)],
  change_script,
  None,
  fee_per_vbyte,

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
