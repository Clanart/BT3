### Title
Gasless swap admission relies on unprotected spot AMM price with no TWAP, enabling fee-delegation (lend/repay) theft from block proposers - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The `kaiax/gasless` module's fee-delegation flow lets any unprivileged sender submit an unsigned-gas `GaslessSwapTx`, get a `LendTx` (funded by the block proposer's own funds) bundled before it, and later repay the proposer out of the swap output. The check that guards this lending — `checkBalanceForSwap` — validates `amountIn` sufficiency using `GaslessSwapRouter.GetAmountIn(token, minAmountOut)`, which is a live/spot AMM read (Uniswap V2 style `getReserves()`), with no TWAP or other manipulation-resistant pricing, unlike the external report's recommendation that Uniswap-based price oracles use at least a 30-minute TWAP.

### Finding Description
`checkBalanceForSwap` at [1](#0-0)  computes `requiredAmountIn` via a direct on-chain call to the DEX-integrated `GaslessSwapRouter.getAmountIn`, which is backed by the pair's current reserves (spot price), not a time-weighted average. This check is invoked as the *sole* balance-sufficiency gate for gasless swap transactions in two independent places:
1. At tx-pool admission (`validateTx`), where a module's `GetCheckBalance()` replaces the default sender-balance check entirely: [2](#0-1) .
2. At every pool `Filter`/`demoteUnexecutables` pass (i.e., whenever the pool re-validates pending txs against a new head), which re-invokes the same spot-price check: [3](#0-2) .

Because the price source has no TWAP smoothing and is read live at whatever block happens to be current when the check runs, an attacker who also controls (or can transiently influence via a low-liquidity pool) the reserves of the relevant `dexAddress(token)` pair can present the pool with a favorable spot price for one instant — enough to pass `checkBalanceForSwap`'s `requiredAmountIn` check — even though the true/sustained exchange rate implies the declared `amountIn`/`minAmountOut` would not actually satisfy `amountRepay` (the proposer's real cost, computed off-chain as `R1+R2+R3` in `repayAmount`, see [4](#0-3) ). The `LendTx` is generated purely from the declared `Fee()`/gas fields of the approve/swap transactions and is unconditionally bundled ahead of them by `ExtractTxBundles` [5](#0-4) , so once the bundle is admitted the proposer's funds are committed before final swap execution reverts or under-delivers.

This mirrors the root cause in the referenced report: relying on an unprotected, single-block-manipulable AMM price feed as the authorization gate for value that has already been committed by another party (there, oTAP option exercise settlement; here, the block proposer's lent gas).

### Impact Explanation
If the pool backing `dexAddress(token)` has thin liquidity (plausible for newly `allowedTokens`-listed tokens, analogous to "during protocol launch" in the original report), an attacker can manipulate the spot price briefly to make `checkBalanceForSwap` pass with an `amountIn` that will not truly cover `amountRepay` once the price reverts (e.g., after the attacker's own manipulating trades are reversed/arbed by others, or once the swap executes at a different block than admission). Because the proposer has already advanced the `LendTx` value based on the declared fee fields — independent of whether the swap actually succeeds and yields sufficient repayment — a failed/underpaying swap results in the block proposer losing the lent KAIA with no or partial recovery. This is a direct fee-delegation/gasless-settlement value-extraction path reachable by any transaction sender, satisfying the "gasless settlement theft" / "fee-delegation abuse" criteria.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires a token/pool pair with `allowedTokens` status and low liquidity, and precise timing/manipulation of the pool between admission-time check and inclusion/execution (the check is repeated on every pool reset, which somewhat narrows the window, but does not eliminate it since reset happens once per new head and admission itself is a single point-in-time read). This is directly analogous to the referenced report's "Low, this could occur when liquidity is not spread over a wide range (e.g. during protocol launch)" likelihood rating.

### Recommendation
Do not rely solely on the DEX's instantaneous `getAmountIn` (spot reserves) as the authorization/admission gate for gasless lending. Consider: (1) requiring a TWAP-based or otherwise manipulation-resistant price source (or a minimum observation window) when computing `requiredAmountIn` for `ShouldCheckSwapAmount`, mirroring the ≥30-minute TWAP guidance from the referenced report; (2) re-validating the actual realized swap proceeds on-chain before advancing `LendTx` value, or making `LendTx` conditional/reclaimable if the swap fails to produce `amountRepay`; and (3) enforcing minimum-liquidity or maximum-price-impact bounds on `allowedTokens` pools used by `GaslessSwapRouter`.

### Proof of Concept
1. Governance/owner lists a low-liquidity token/pool pair in `GaslessSwapRouter.allowedTokens`/`dexAddress`.
2. Attacker (as an unprivileged trader) transiently skews the pool's reserves via their own trades to make `getAmountIn(token, minAmountOut)` return an artificially low value.
3. Attacker submits `GaslessApproveTx` + `GaslessSwapTx` with `amountIn` just above this manipulated `requiredAmountIn`, `minAmountOut` set to pass `minAmountOut >= amountRepay` (per [6](#0-5) ), during the brief manipulated-price window; `checkBalanceForSwap` admits the transaction.
4. The gasless bundling logic prepends `LendTxGenerator` (funded from the proposer's key) ahead of the approve/swap pair [7](#0-6) .
5. By the time the bundle executes (same or later block, after reserves revert to true price or after further manipulation), the actual on-chain `swapForGas` execution yields less than `amountRepay`, or the swap reverts outright once real reserves are restored, while the `LendTx` value has already been transferred from the proposer.

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}

func (g *GaslessModule) ExtractTxBundles(txs []*types.Transaction, prevBundles []*builder.Bundle) []*builder.Bundle {
	// there are only at most two gasless transactions in pending for a sender
	bundles := []*builder.Bundle{}
	approveTxs := map[common.Address]*types.Transaction{}
	targetTxHash := common.Hash{}
	for _, tx := range txs {
		addr, err := types.Sender(g.signer, tx)
		if err != nil {
			continue
		}
		if g.IsApproveTx(tx) {
			approveTxs[addr] = tx
		} else if g.IsSwapTx(tx) && g.IsExecutable(approveTxs[addr], tx) {
			bundleTxs := builder.NewTxOrGenList(g.GetLendTxGenerator(approveTxs[addr], tx))
			if approveTxs[addr] != nil {
				bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(approveTxs[addr]))
			}
			bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(tx))

			b := builder.NewBundle(
				bundleTxs,
				targetTxHash,
				false,
			)

			targetTxHash = tx.Hash()

			isConflict := false
			for _, prev := range append(prevBundles, bundles...) {
				if prev.IsConflict(b) {
					isConflict = true
					break
				}
			}
			if isConflict {
				// Gasless transactions will just fail even if they aren't bundled.
				continue
			}
			bundles = append(bundles, b)
		} else {
			targetTxHash = tx.Hash()
		}
	}
	return bundles
}
