### Title
TOCTOU race in `resolveWithin` lets a resolved-but-not-yet-verified symlink path escape the repository root before it is read - ([File: app/src/lib/path.ts])

### Summary
`resolveWithin()` validates a repo-relative path against symlink escape by calling `realpath()` on both the root and the candidate path and comparing the *real* paths, but it returns the **un-resolved** logical `resolved` path to the caller instead of `realResolved`. Every caller then performs its actual filesystem operation (`stat`, `readFile`) against that returned logical path at a later point in time. This reproduces the exact "check now, act later" invariant break described in the report: the ratio (safety of the path) is validated once, and a separate, later operation trusts that stale validation instead of re-checking it at the time of use.

### Finding Description
`resolveWithin` in [1](#0-0)  computes:

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

The safety check is performed on `realResolved` (symlinks fully resolved), but the value handed back to the caller — and later used for I/O — is `resolved`, the pre-symlink-resolution logical path. This is a classic TOCTOU split: the "check" (symlink-safe realpath comparison) and the "use" (the caller's `stat`/`readFile` call against `resolved`) are two separate operations, separated by additional `await` points, operating on attacker-influenced disk state (a cloned/fetched Git repository).

The concrete consumer of this is `buildConflictContext` in [2](#0-1) :

```
absolutePath = await resolveWithin(workingDirectory, file.path)
...
const fileStat = await stat(absolutePath)
...
content = await readFile(absolutePath, 'utf8')
```

Each of `resolveWithin`, `stat`, and `readFile` is an independent async filesystem call. If any path component along `file.path` is (or becomes) a symlink pointing outside `workingDirectory` at the moment `stat`/`readFile` runs — even though it pointed inside the repo (or didn't exist yet) at the moment `resolveWithin`'s `realpath` calls ran — the guard is bypassed and an out-of-repo file is read. The attacker fully controls the content of the working directory here because `file.path` values come from Git's own conflict-file listing on a repository the attacker authored (a malicious commit/branch/merge that produces a conflict), and Git allows conflicted trees to contain arbitrary symlink entries in the index/worktree.

### Impact Explanation
`buildConflictContext`'s output (`rawContent`, including this out-of-repo file's bytes) is fed directly into `formatConflictContextForPrompt` and then sent to the Copilot SDK as part of a resolve-conflict-with-AI request (see call sites in `app/src/lib/stores/app-store.ts`). This means a maliciously crafted upstream/fork repository that produces a merge/rebase/cherry-pick conflict can cause Desktop to read a file **outside the repository working directory** (e.g., an SSH key, `.netrc`, or another repo's secrets under the user's home directory) and exfiltrate its contents to an external network service (the Copilot backend) as part of an AI conflict-resolution prompt — satisfying both the "file read outside the repo" and "credential/token exfiltration" impact classes named as valid.

### Likelihood Explanation
Exploitation requires: (1) the victim to open a repository containing an attacker-authored branch/fork, (2) a merge/rebase/cherry-pick to produce a conflict, and (3) the victim to invoke the Copilot conflict-resolution feature — plus winning a narrow timing window between the `realpath` check and the subsequent `stat`/`readFile` (a symlink swap or the target only fully materializing after Git writes it out during checkout). This makes it a real but timing-dependent path, not a guaranteed one-shot exploit, so likelihood is moderate rather than high. No local/admin access or leaked credentials are required — only an attacker-controlled repository and normal Desktop usage of the AI-conflict feature.

### Recommendation
Have `resolveWithin` return (or additionally expose) the fully-resolved real path (`realResolved`), and require all callers to perform their file operations against that real path rather than the logical `resolved` path — eliminating the gap between validation and use. Alternatively, open the file with `O_NOFOLLOW`-equivalent semantics (or re-verify via `realpath` immediately before each `stat`/`readFile` call) so no window exists in which a symlink swap can defeat the guard.

### Proof of Concept
1. Attacker crafts a branch that, when merged/rebased against the victim's branch, produces a conflicted file `evil/link` where `evil` is a directory that Git writes as (or is later transformed by a hook/step into) a symlink pointing to `../../..` (or an absolute path) once checked out.
2. Victim opens the repo in Desktop, triggers a merge conflict, and uses "Resolve with Copilot."
3. `buildConflictContext` calls `resolveWithin(workingDirectory, 'evil/link')`; at that instant `evil` still resolves inside the repo, so the `realpath` check passes and `resolved` (e.g. `<repo>/evil/link`) is returned.
4. Before the subsequent `stat`/`readFile` calls execute, the `evil` path component is a symlink pointing outside the repo (planted by the same commit or a concurrent process the attacker can trigger through repo content, e.g., a submodule/worktree update).
5. `stat(absolutePath)` / `readFile(absolutePath, 'utf8')` follow the symlink and read a file outside the repository, whose contents are then included in the prompt sent to the Copilot SDK. [1](#0-0) [2](#0-1)
