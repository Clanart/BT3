## Analysis

The Mover finding's core invariant is: **a value's trustworthiness/price is assumed rather than verified**, letting an attacker substitute a cheap asset for one implicitly treated as equal-value. GitHub Desktop has no token pricing, so a literal analog doesn't exist. However, the same *"treat an unverified attacker-influenced value as equivalent to a trusted one and act on it silently"* pattern shows up in `updateRemoteUrl`, which auto-rewrites a repository's `origin` remote based on a GitHub API field (`clone_url`) without any user confirmation and with weak equivalence checks. [1](#0-0) 

The "identity" check used to decide whether the new URL is trustworthy, `urlMatchesRemote`/`urlsMatch`, only compares parsed `hostname`/`owner`/`name` components, not full URL equality, and is not any kind of ownership or authenticity proof — it is exactly the kind of "looks equivalent enough" check that is the analog of a missing price oracle. [2](#0-1) [3](#0-2) 

### Title
Automatic remote-URL rewrite trusts unverified GitHub API `clone_url` field, silently redirecting future pushes to an attacker-controlled repository - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl` automatically calls `gitStore.setRemoteURL` to change the `origin` remote whenever the GitHub API's `clone_url` for a repository differs from the locally configured remote, gated only by a same-protocol check and a name/owner/hostname string match — not by any cryptographic or ownership verification. If an attacker can influence what `clone_url` the app receives for a given `GitHubRepository` record (e.g., a "repo-jacking" scenario where a renamed/deleted repo's old `owner/name` is reclaimed by an attacker, or a compromised/malicious GitHub Enterprise endpoint returning attacker-controlled repository metadata), Desktop will silently repoint the user's remote at the attacker's repository.

### Finding Description
`updateRemoteUrl` is invoked when repository metadata is refreshed from the GitHub API. Its logic:
1. Reads the current `origin` URL and the API's `clone_url`.
2. Confirms `protocolsMatch` (same scheme).
3. Confirms `remoteUrlUnchanged` — i.e., the locally configured remote still matches what was *previously* stored as the GitHub repository's `cloneURL`.
4. If the remote hasn't been manually changed and the URLs don't already match, it calls `setRemoteURL` to overwrite `origin` with the new `clone_url` — no user prompt, no diff shown. [4](#0-3) 

The equivalence check (`urlMatchesRemote`) that gates whether the *old* clone URL still "matches" is purely structural (hostname + owner + name, case-insensitively) — it does not verify that the underlying repository is the *same* repository (same ID), only that it has the same textual coordinates: [2](#0-1) 

This means the "price oracle" here — the thing that should authoritatively bind a `GitHubRepository` record to a specific git object graph — is a string comparison of owner/name, which is exactly what an attacker controls when they claim a vacated `owner/name` slug (GitHub's classic repo-hijack primitive: rename/delete a repo, then an attacker claims the freed name). The stored `GitHubRepository.cloneURL` in Desktop's database is keyed by API repository ID internally, but the *validation gate* in `updateRemoteUrl` only checks the string shape of the URL, not the ID, so a same-named attacker repo returned by the API for the same DB row (e.g., after Desktop re-resolves the repository by owner/name on next launch or refresh) can pass the `remoteUrlUnchanged` check.

`setRemoteURL` itself performs no further validation and directly runs `git remote set-url`: [5](#0-4) 

### Impact Explanation
If the remote silently changes, subsequent user actions that rely on "the same remote as always" (fetch, `pull`, and critically **push**) will interact with the attacker's repository instead of the legitimate one. Since Desktop treats `origin` as authoritative for showing branch/PR state and for push targets, a user could unknowingly push commits — including proprietary source code — to a repository the attacker controls. This matches the "silent corruption of what the user commits or pushes" impact class: the user believes they're syncing with their trusted repo, but Desktop has redirected the write target based on an unverified API value, an analog of the "cheap token being treated as the high-value token" from the seed report.

### Likelihood Explanation
Exploitation requires an attacker to control the `clone_url`/repository identity returned to Desktop's API layer for a repository entry the user already has configured — realistically via: (a) reclaiming a renamed/deleted `owner/name` on GitHub.com or a GHE instance the user already trusts (a known, low-effort "repo-jacking" technique, not requiring any special access to the victim), or (b) a compromised/rogue GitHub Enterprise Server that the app is configured to talk to returning attacker-chosen JSON. Both are within the "attacker controls a GitHub API object" category. The gating logic (`protocolsMatch` + string-based owner/name equivalence) does not require any secret or privileged access to bypass, and the rewrite happens with no user interaction, making it plausible once the attacker achieves the API-object precondition. I could not directly trace the call site in `app-store.ts` that supplies `gitHubRepository`/`apiRepo` to `updateRemoteUrl` within the available context, so I cannot fully confirm the exact refresh trigger (e.g., whether it's per-launch or per-fetch) — this should be verified against `app/src/lib/stores/app-store.ts` before treating this as conclusively exploitable end-to-end.

### Recommendation
- Do not silently rewrite `origin` based on API `clone_url` alone. Require the API repository's stable numeric `id` to match the previously stored `GitHubRepository.dbID`/`id` before treating a `clone_url` change as legitimate, rather than relying on structural owner/name/hostname string equality.
- Surface any detected `clone_url` change to the user for explicit confirmation before altering their remote, rather than performing it silently via `setRemoteURL`.
- Consider detecting and warning on "repository identity changed" scenarios (old numeric ID no longer resolves to the same repository) distinctly from ordinary renames.

### Proof of Concept
1. User has Desktop tracking `origin` = `https://github.com/acme/widgets.git`, associated with `GitHubRepository` (owner=`acme`, name=`widgets`).
2. The `acme/widgets` repository is renamed or deleted upstream (freeing the `acme/widgets` slug).
3. Attacker creates a new repository at `acme/widgets` (assuming they can claim the `acme` org/name, e.g. via an expired org or a look-alike scenario against a self-hosted GHE the app talks to) with `clone_url = https://github.com/acme/widgets.git` (structurally identical).
4. On next repository refresh, `updateRemoteUrl` computes `remoteUrlUnchanged = true` (owner/name/hostname string match against the stored `cloneURL`) and `protocolsMatch = true`, `urlsMatch` may be `false` if the DB record's cached `cloneURL` differs in casing/suffix.
5. Desktop calls `gitStore.setRemoteURL('origin', <attacker clone_url>)` with no prompt.
6. The user's next `git push` sends commits to the attacker's repository.

Note: step 3's precondition (attacker reclaiming the exact `owner/name`) is the load-bearing assumption; I was not able to trace the full precondition chain (specifically how `GitHubRepository` records get re-resolved/rebound to a new API repository ID) within the indexed portions of `app-store.ts`, so this should be validated with a full read of that file before treating the PoC as fully verified.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

export function urlsMatch(url1: string, url2: string) {
  const firstIdentifier = parseRepositoryIdentifier(url1)
  const secondIdentifier = parseRepositoryIdentifier(url2)

  return (
    firstIdentifier !== null &&
    secondIdentifier !== null &&
    firstIdentifier.hostname === secondIdentifier.hostname &&
    firstIdentifier.owner === secondIdentifier.owner &&
    firstIdentifier.name === secondIdentifier.name
  )
}
