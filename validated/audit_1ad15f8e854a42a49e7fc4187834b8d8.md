### Title
Signature-replay authentication bypass in the `addr` precompile's `associate` method forces unwanted account association and balance migration - ([File: precompiles/addr/addr.go])

### Summary
The `addr` precompile's `associate` entrypoint (and every legacy copy of it) authenticates an EVM/Sei address-association request purely by ECDSA-recovering a pubkey from an attacker-supplied `(v, r, s)` signature over an attacker-supplied `customMessage`. The recovered pubkey — not the EVM `msg.sender` (`caller`) — determines which accounts get associated and whose balance gets migrated. Because the signed payload has no Sei-specific domain separation (no chain ID, no nonce, no fixed "I want to associate on Sei" prefix) and the code never checks that `caller` matches the recovered EVM address, any unprivileged EVM caller who obtains a victim's `(message, signature)` pair signed for an unrelated purpose elsewhere can replay it into `associate()` to force an association the victim never authorized for Sei, silently migrating that victim's on-chain balance to the newly associated address as a side effect.

### Finding Description
`PrecompileExecutor.associate` in [1](#0-0)  takes `v`, `r`, `s`, and an arbitrary `customMessage` string directly from the calldata, hashes the message with `crypto.Keccak256Hash`, and recovers a pubkey via `helpers.GetAddresses`: [2](#0-1) 

The recovered pubkey alone determines `evmAddr` and `seiAddr`, which are then passed to `associateAddresses`: [3](#0-2) 

Critically, `Execute`/`associate` never compares `caller` (the EVM `msg.sender`, i.e. the account that actually invoked the precompile) against the recovered `evmAddr`. Contrast this with the `solo` precompile's `sigverify`, which explicitly checks `pubkeyAddr` against the expected sender: [4](#0-3) . `addr.associate` has no equivalent check — anyone can submit any third party's valid `(message, signature)` pair.

Because `customMessage` is fully attacker/caller-supplied instead of being a fixed, Sei-specific, chain-bound template, the "authentication" performed here does not prove that the signer intended to authorize *this* action on *this* chain — it only proves that *some* signature over *some* message recovers to a pubkey. This is a textbook CWE-287 analog to the Thelia bug: the mechanism believed to gate a sensitive action (address association + fund migration) validates a signature without binding it to the specific action/context, so a signature obtained for one purpose can be replayed to authenticate an unrelated, sensitive one.

The sensitivity of this bypass is elevated by what `AssociateAddresses` does on success — it migrates **all** spendable coins and wei balance from the implicit direct-cast Sei address (`sdk.AccAddress(evmAddr[:])`) to the new "true" pubkey-derived Sei address, and removes the cast account: [5](#0-4) 

This same fund-migration/state-orphaning risk is explicitly called out and mitigated elsewhere in the codebase for EIP-7702 `SetCode` authorities, via `AuthorityToPreAssociate`'s chain ID / nonce / account-state checks and cross-check against `auth.Authority()`: [6](#0-5) 

No equivalent protection (chain binding, nonce, purpose-specific fixed message, or caller-match check) exists on the `addr` precompile's generic `associate` path, including all its legacy versions: [7](#0-6) , [8](#0-7) , [9](#0-8) .

### Impact Explanation
Any unprivileged EVM caller can trigger an unwanted association for a victim account and force an unauthorized on-chain fund transfer (via the precompile) from the victim's implicit direct-cast Sei address to the freshly associated true Sei address — without the victim submitting or approving this specific Sei transaction. This is an unauthorized state change and fund movement triggered by a third party using a signature never intended for this purpose, which can also permanently remove/orphan the account object at the cast address (`RemoveAccount`) and any pubkey/sequence state tied to it, matching the "unauthorized transfer via precompile" and "permanent freezing/state loss" impact classes.

### Likelihood Explanation
Exploitation requires the attacker to already possess a valid `(customMessage, v, r, s)` tuple signed by the victim's secp256k1 key for some other purpose (e.g., off-chain "sign-in" style message signing, or any signature scheme that does not use EIP-191 prefixing and is publicly observable). Given Sei's architecture intentionally shares the same secp256k1 key between a user's EVM and Sei identities, and many wallets/dApps have users sign plain-text messages, such signatures are plausible to obtain for actively-transacting users, making this a realistic (not merely theoretical) replay vector, though it is not as trivially universal as a same-message double-spend.

### Recommendation
- Require `caller == recoveredEvmAddr` (mirroring the `solo` precompile's `sigverify` check) so only the address owner (or someone the owner explicitly delegates via a fixed on-chain flow) can trigger association for that pubkey.
- Bind the signed payload to a fixed, Sei-specific, chain-bound domain (e.g., a constant prefix plus chain ID and possibly a nonce/expiry) instead of accepting an arbitrary attacker-supplied `customMessage`, eliminating cross-context signature replay.
- Apply the same authoritative-recovery/state-check discipline already implemented for EIP-7702 authorities in `AuthorityToPreAssociate` to the `addr` precompile's `associate` flow.

### Proof of Concept
1. Victim signs some off-chain message `M` (e.g., "Login to ExampleApp", with `keccak256(M)` as the digest) with their secp256k1 key using `personal_sign`-less/raw hashing on another platform that also uses the victim's key; the signature `(v, r, s)` and message `M` become observable (e.g., leaked in a request log, or public on the other platform).
2. Attacker (any unprivileged address) calls the Sei `addr` precompile's `associate(v, r, s, M)` with the captured tuple, without the victim's Sei-transaction involvement.
3. `crypto.Keccak256Hash([]byte(M))` matches the digest the victim actually signed; `helpers.GetAddresses` recovers the victim's pubkey, `evmAddr`, and `seiAddr`.
4. `associateAddresses` proceeds because there is no `caller == evmAddr` check, and `AssociateAddresses` migrates all of the victim's spendable coins/wei from the direct-cast address to the newly-associated Sei address and removes the cast account — all without the victim ever sending a Sei-chain transaction authorizing this specific action.

	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

// AuthorityToPreAssociate returns the authority of an EIP-7702 authorization that should be
// associated with its true (pubkey-derived) Sei address before execution, or ok=false.
//
// It mirrors go-ethereum's StateTransition.validateAuthorization (chain id, nonce overflow,
// authority code, and account-nonce checks) so that pre-association happens only for
// authorizations the EVM will actually apply, and additionally skips authorities that are
// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
