### Title
Aggregator gRPC server installs no-op auth interceptor when `client_verification=false`, allowing unauthenticated calls to `send_move_to_vault_tx`/`internal_send_tx` - (File: core/src/servers.rs)

### Summary
`create_grpc_server` (core/src/servers.rs:106-138) selects `Interceptors::Noop` whenever `BridgeConfig.client_verification` is `false`, and `Noop::call` (core/src/rpc/interceptors.rs:30) returns `Ok(req)` unconditionally with no peer-identity check whatsoever. Any caller who can reach the aggregator's TCP port can then invoke any `ClementineAggregator` RPC, including `send_move_to_vault_tx`/`internal_send_tx`, without holding any certificate.

### Finding Description
The intended binding is: `(caller of send_move_to_vault_tx / internal_send_tx) == (holder of aggregator_cert or our_cert, per OnlyAggregatorAndSelf::only_aggregator_and_self)` [1](#0-0) .

This binding is only enforced when the interceptor variant is `OnlyAggregatorAndSelf`. `create_grpc_server` chooses the interceptor purely from `config.client_verification`:
```
if config.client_verification { OnlyAggregatorAndSelf {...} } else { Noop }
``` [2](#0-1) 

When `Noop` is selected, `Interceptors::call` for that variant is `Ok(req)` with zero checks on peer certificates, method name, or caller identity [3](#0-2) .

`create_aggregator_grpc_server` only emits a `tracing::warn!` when `client_verification` is **true** and otherwise proceeds silently to call `create_grpc_server`, meaning `client_verification=false` is a fully supported, non-error configuration path for standing up the aggregator's public gRPC listener [4](#0-3) .

TLS itself is not the gate here — even with TLS configured (`ServerTlsConfig::new().identity(server_identity)` without `.client_ca_root(...)` at line 111), the server does not require or validate a client certificate at all when `client_verification` is false, so any TCP client that completes the (unauthenticated) TLS handshake reaches the RPC dispatch layer, and the `Noop` interceptor then passes every request through unconditionally.

Root cause: authorization for the aggregator's state-changing/broadcasting RPCs (`send_move_to_vault_tx`, `internal_send_tx`, and by extension every other aggregator method) is entirely delegated to a boolean deployment flag with no additional in-handler authentication check. There is no secondary guard (e.g., an application-level signature check, allow-list, or API key) inside `AggregatorServer`'s RPC implementations that would substitute for the interceptor when it is a no-op.

### Impact Explanation
If an aggregator is deployed with `client_verification=false`, any unprivileged network peer that can reach the aggregator's gRPC port can call `send_move_to_vault_tx`/`internal_send_tx` with an attacker-chosen, already-signed Bitcoin transaction and cause the aggregator's tx-sender to broadcast it — this is an unauthenticated state-changing/broadcasting call, matching the High severity category explicitly listed in the rules ("an unauthenticated state-changing or broadcasting call"). It does not by itself forge N-of-N signatures or move BTC without a valid signature set (the attacker still needs a validly signed transaction to broadcast), but it removes the sole access-control layer that is supposed to restrict who may trigger the aggregator's transaction-sending/orchestration RPCs to the aggregator's own operators/verifiers or itself.

### Likelihood Explanation
Preconditions: a deployment must run with `client_verification=false`. This is a real, non-test configuration branch reachable in production code (`core/src/servers.rs::create_aggregator_grpc_server`), not confined to tests/mocks, and the code explicitly tolerates it (only a warning is logged; no refusal to start). Attacker cost is negligible: no TLS client certificate, no key material, no bitcoin/fees needed to merely reach and call the RPC — only network access to the aggregator's port. Whether this is actually the deployed default cannot be fully confirmed from the files inspected (I found references to `client_verification` in `core/src/config/mod.rs`, `core/src/config/env.rs`, and deployment TOMLs, but did not get to read the actual default/env values before running out of tool iterations), so likelihood depends on real-world deployment configuration, which is out of this repo's direct control but is a supported code path.

### Recommendation
Do not allow `Noop` to be silently selected for production aggregator/operator/verifier servers reachable from untrusted networks. At minimum: (1) make the aggregator refuse to start (hard error, not just `tracing::warn!`) when `client_verification=false` and the bind address is not loopback/localhost; (2) enforce client-certificate verification unconditionally for all state-changing/broadcasting RPCs regardless of the `client_verification` flag, independent of the TLS-level `ServerTlsConfig`; (3) add an explicit in-handler authorization check for `send_move_to_vault_tx`/`internal_send_tx` that does not rely solely on the interceptor layer.

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
