### Title
Missing replay/deadline protection in App Proxy signature verification allows indefinite replay of captured signed requests - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`ShopifyApp::AppProxyVerification` verifies that an incoming app-proxy request's `signature` query parameter matches an HMAC computed over the other query parameters (which includes a `timestamp` field), but it never checks that the `timestamp` is recent or otherwise enforces a validity window/deadline on the request.

### Finding Description
`query_string_valid?` extracts the `signature` parameter and recomputes the HMAC over the remaining query parameters (`timestamp` included as one of the signed fields), comparing it with `ActiveSupport::SecurityUtils.secure_compare`: [1](#0-0) 

The `timestamp` value is part of the signed payload used to *compute* the signature, but nothing in `verify_proxy_request` or `query_string_valid?` compares this timestamp against the current time or rejects requests older than some deadline: [2](#0-1) 

This is the same root cause described in the external report: a value intended to bound the validity/freshness of a signed operation (there, `deadline`; here, `timestamp`) is present in the payload but never actually checked against the current time, so a signature that was valid at generation time remains valid forever. Any request URL that includes a valid `signature` — once observed (e.g., via browser history, proxy/server access logs, Referer headers, shared links, or a leaked screenshot/log line) — can be replayed by an unrelated, unauthenticated caller at any point in the future and will still pass verification.

The same missing-freshness-check pattern also exists in `ShopifyApp::PayloadVerification#hmac_valid?`, used by `WebhookVerification`, which only performs an HMAC digest comparison with no timestamp/deadline enforcement: [3](#0-2) [4](#0-3) 

### Impact Explanation
An anonymous attacker who obtains a previously-valid, fully-signed app-proxy request URL (which is routinely exposed in browser history, HTTP referrers, server/CDN access logs, or analytics tools since it's a GET request forwarded from the storefront) can replay it against the app's app-proxy-protected controller at any later time and have it accepted as authentic, since there is no deadline/expiry check tied to the `timestamp` field. This defeats the intended request-authenticity guarantee of `ShopifyApp::AppProxyVerification` and allows a forged/stale request to be treated as a legitimately fresh, currently-authorized request from Shopify's proxy — enabling replay-based state changes or data access in any endpoint that relies solely on this concern for authorization.

### Likelihood Explanation
Exploitability depends on an attacker being able to capture one valid signed proxy URL, which is a realistic condition given these are unauthenticated GET requests forwarded through storefronts and commonly logged/cached/exposed by intermediaries (proxies, CDNs, browser history, referrer leakage). No merchant credentials or app secret are needed — only observation of one signed request.

### Recommendation
Add a mandatory freshness/deadline check: require a `timestamp` (or dedicated `expires_at`) parameter within the signed payload and reject requests where `Time.now.to_i - timestamp.to_i` exceeds a defined tolerance (e.g., a few minutes), mirroring how nonces/deadlines are enforced elsewhere. Apply the equivalent freshness check to `ShopifyApp::PayloadVerification#hmac_valid?` / `WebhookVerification#verify_request` as well, so that a valid HMAC alone is not sufficient — the signed timestamp must also fall within an acceptable window before the request is accepted.

### Proof of Concept
1. As any user with app-proxy access (e.g., a customer of a storefront that has the app's proxy extension installed), trigger one legitimate app-proxy request, capturing the full URL including `shop`, `path_prefix`, `timestamp`, and `signature` query parameters (visible in browser history/dev tools/logs).
2. Wait an arbitrary amount of time after the request's natural validity window would reasonably have expired (hours, days, or longer).
3. Replay the exact same URL (unmodified) directly, as an unrelated/anonymous actor, against the app's app-proxy-protected controller.
4. Observe that `AppProxyVerificationController`/any controller using `ShopifyApp::AppProxyVerification` accepts the request and responds normally, because `query_string_valid?` only re-validates the signature over the (stale) parameters and never checks `timestamp` freshness: [5](#0-4) .

# frozen_string_literal: true

module ShopifyApp
  module AppProxyVerification
    extend ActiveSupport::Concern
    included do
      skip_before_action :verify_authenticity_token, raise: false
      before_action :verify_proxy_request
    end

    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
