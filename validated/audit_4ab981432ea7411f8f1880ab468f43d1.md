### Title
Missing path-traversal/symlink guard on conflict-file disk access in `unmerged-file.tsx` context menu - (File: `app/src/ui/lib/conflicts/unmerged-file.tsx`)

### Summary
`app/src/lib/copilot-conflict-context.ts`'s `buildConflictContext` treats a conflicted file's repository-relative `path` as untrusted and resolves it with `resolveWithin(workingDirectory, file.path)`, rejecting anything that escapes the repo root via `..` or a symlink [1](#0-0) . The sibling UI code that lets a user act on the very same conflicted-file list — `app/src/ui/lib/conflicts/unmerged-file.tsx` — builds the on-disk path with a plain `join(repository.path, relativeFilePath)` and immediately opens it with the default program or reveals it in the file manager, with no `resolveWithin` check at all [2](#0-1) .

### Finding Description
`resolveWithin` (`app/src/lib/path.ts`) is the app's designated defense against a crafted repository-relative path escaping the repository root, including via a symlink component; its own test suite explicitly checks that "paths that use a symlink to traverse outside of the root" are rejected [3](#0-2) . This guard is applied to the Copilot conflict-resolution flow, and to the "Open Repository from URL" deep-link filepath handler in `dispatcher.ts` [4](#0-3) , but `resolveWithin` is used in only three files total (`dispatcher.ts`, `copilot-conflict-context.ts`, `app-store.ts`) — it is conspicuously absent from the merge/rebase-conflict resolution UI that operates on the same untrusted, repository-relative conflict paths: `makeMarkerConflictDropdownClickHandler` in `unmerged-file.tsx` computes `absoluteFilePath = join(repository.path, relativeFilePath)` and wires it straight into `openFile(absoluteFilePath, dispatcher)` (which does `shell.openExternal('file://' + fullPath)`) and `revealInFileManager(repository, relativeFilePath)` (`Path.join` + `shell.showItemInFolder`) [5](#0-4) [6](#0-5) .

The relevant conflict paths come from `git status`/index entries during an active merge/rebase in a repository the user cloned or fetched — i.e., attacker-controlled content, the same class of input the Copilot conflict code explicitly distrusts. Because `unmerged-file.tsx` uses raw `Path.join` instead of `resolveWithin`, a working-directory entry that resolves (directly or via an intermediate symlink introduced as part of the merge) outside the repository root is not rejected before the app opens it with the OS default handler or reveals it in Explorer/Finder.

### Impact Explanation
If a conflict-path component can point outside the repository (e.g. through a symlink present in one side of the merge), "Open with Default Program" from the conflict resolution UI will hand an out-of-repo file path to `shell.openExternal('file://...')`, and "Reveal in File Manager" will open/select an arbitrary filesystem location chosen by the crafted repository, rather than the intended working-directory file. This is the same class of primitive (`silent corruption of what the user commits`/`file read outside the repo` via a maliciously crafted repository) that the project already treats as security-relevant, evidenced by the dedicated `resolveWithin` guard and its symlink-specific regression tests.

### Likelihood Explanation
Reaching this code path requires the user to be in an active merge/rebase conflict and to right-click a conflicted file to use "Open with Default Program" or "Reveal in Finder/Explorer" — a normal, expected user action during conflict resolution, not an "unnatural" step. The attacker's only requirement is that the victim clone/fetch and attempt to merge a crafted branch/repository, which matches the in-scope threat model (attacker controls a cloned/fetched repository).

### Recommendation
Route `relativeFilePath` through `resolveWithin(repository.path, relativeFilePath)` (or `resolveWithinPosix`/`resolveWithinWin32` as appropriate) in `unmerged-file.tsx` before calling `openFile`/`revealInFileManager`/`join`, mirroring the guard already applied in `copilot-conflict-context.ts`, and refuse the action (surface an error instead of opening) when the resolved path is `null`. The same audit should be extended to any other conflict/diff context-menu code path that still calls `Path.join(repository.path, ...)` directly instead of `resolveWithin`.

### Proof of Concept
1. Craft a repository with two branches such that merging them produces a working-directory entry (conflicted or otherwise reachable via the conflicts UI) whose effective on-disk location, once joined with `repository.path` and resolved by the OS, traverses outside the repository root (e.g. via a symlink component introduced by one side of the merge).
2. Have the victim clone the repository and attempt the merge, producing the conflict.
3. In the "Resolve Conflicts" file list, right-click the affected entry and choose "Open with Default Program" or "Reveal in Finder/Show in Explorer" — both call `join(repository.path, relativeFilePath)` (`app/src/ui/lib/conflicts/unmerged-file.tsx:409`, `app/src/lib/app-shell.ts:62`) with no `resolveWithin` check.
4. Compare with `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:393`), which would reject the identical path via `resolveWithin` and return `skippedReason: 'File path is outside the repository'` instead of touching the resolved location — demonstrating the guard exists for this exact data but is not applied uniformly.

*Note: I was not able to fully verify, within the available tooling, a concrete git-level mechanism (e.g., an actual symlink checked out mid-merge) that produces a conflict-list entry whose relative path escapes the repo root at OS-resolution time — git's tree format itself blocks `..` path components, so the realistic escape vector is limited to symlink-based traversal introduced by working-directory content during the merge. This should be validated with a live repro before treating it as confirmed-exploitable.*
