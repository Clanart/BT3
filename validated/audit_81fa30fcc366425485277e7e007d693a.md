## Finding

The bug-class here is: **a value/state snapshot taken at time T1 is later consumed as authoritative at time T2 without re-validation, letting an attacker who can influence what happens between T1 and T2 make the operation act on stale data while the app believes it reflects current, user-reviewed reality.** In the Sherlock report, the fee snapshot (last-pool output) is taken after the state has already been manipulated. The Desktop analog is in the **Discard Selected Lines** flow.

### Title
Silent working-directory corruption via stale line-numbered diff used with zero-context `git apply` in Discard-Selection flow - (File: `app/src/lib/git/apply.ts`)

### Summary
`discardChangesFromSelection` builds a unified diff patch from a caller-supplied `diff: ITextDiff` snapshot and the user's line selection, then applies it with `git apply --unidiff-zero --whitespace=nowarn -` directly against the working tree. Unlike the sibling function `applyPatchToIndex`, which re-fetches a **fresh** diff immediately before formatting the patch, `discardChangesFromSelection` never re-validates that the passed-in diff still matches the file's current on-disk content. Because `--unidiff-zero` hunks carry no context lines, `git apply` has nothing but line-position bookkeeping to anchor each hunk — if the underlying file changed between when the diff was captured and when "Discard" is invoked, the patch can be applied at the wrong location. [1](#0-0) [2](#0-1) 

### Finding Description
`applyPatchToIndex` (used for partial-commit staging) explicitly re-fetches the diff right before building the patch, precisely to avoid acting on stale state: [3](#0-2) 

`discardChangesFromSelection`, used for the "Discard Selected Lines"/"Discard Selected Hunk" action, has no such guard — it trusts the `diff` argument handed to it by the UI layer: [2](#0-1) 

The UI explicitly documents that it passes a diff captured earlier (from React props), not a freshly-fetched one, when the user triggers a discard: [4](#0-3) 

The patch itself is built purely from `hunk.header.oldStartLine`/`newStartLine` and per-line content taken from that stale diff object, with **zero lines of context** (`--unidiff-zero`): [5](#0-4) [6](#0-5) 

Because there are no context lines, `git apply` cannot verify that the surrounding file content still matches what the diff was computed against — it applies hunks by line offset. If the working-tree file has shifted (lines added/removed elsewhere in the file, or a line's content changed) after the diff snapshot was taken but before the user confirms discard, the patch will remove/insert the wrong lines. This silently corrupts the file: the user believes they discarded a specific hunk they reviewed, but a different region of the file is altered. If unnoticed, the corrupted content is what subsequently gets committed and pushed.

### Impact Explanation
This falls squarely into the allowed impact category "silent corruption of what the user commits or pushes." The user's approved intent (discard exactly these reviewed lines) is not what actually happens; instead an unrelated part of the file is silently mutated with no error surfaced (assuming the line offsets still exist in the file, `git apply --unidiff-zero` will typically succeed without complaint, since there's no context to fail a match against).

### Likelihood Explanation
This requires the working-tree file to change in the window between diff capture (UI render/props) and the user clicking "Discard" — plausible in ordinary developer workflows against a repository whose tooling an attacker controls (e.g., a checked-in file watcher / build / format script, a `lint-staged`/`husky` hook installed via a repo's own `npm install`, or any auto-rewrite tool the repository instructs the user's editor/task runner to run). None of this requires local/physical access, admin rights, prior malware, or leaked credentials — only the repository content itself, consistent with the "attacker controls a cloned/fetched repository" primitive. The likelihood is moderate: it depends on timing and on some external process touching the file, but such background-write tooling is common and can be embedded by a malicious repo author.

### Recommendation
Mirror `applyPatchToIndex`'s pattern in `discardChangesFromSelection`: re-fetch the current working-directory diff for the file immediately before building/applying the discard patch, and abort (or re-prompt) if the fresh diff's hunks/line content differ from the diff the user actually reviewed/selected against. Alternatively, increase context (`-C`/default context instead of `--unidiff-zero`) so `git apply` can reject a patch whose surrounding context no longer matches, turning silent misapplication into a detectable failure.

### Proof of Concept
1. Open a repository in Desktop and modify `file.txt`, producing a diff with several hunks; leave the Changes view open showing this diff (`this.props.diff` snapshot captured in `side-by-side-diff.tsx`).
2. Before clicking "Discard Selected Lines" on a given hunk, an external process (e.g., a watcher/build script shipped with the repository, running because the user has it open in an editor with auto-run tasks) rewrites `file.txt`, shifting line numbers (e.g., adds/removes a blank line elsewhere in the file) without the user re-opening the diff view.
3. User clicks "Discard" on the hunk they originally reviewed. `discardChangesFromSelection` (`app/src/lib/git/apply.ts:102-120`) builds a `--unidiff-zero` patch from the **stale** `diff` prop via `formatPatchToDiscardChanges` (`app/src/lib/patch-formatter.ts:251-335`) and applies it to the now-different file.
4. Because there is no context to validate placement, `git apply` applies the add/remove operations at the recorded line offsets in the *new* file content, silently discarding/reintroducing the wrong lines instead of the ones the user selected — corrupting the file that will subsequently be committed.

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}

export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true
      } else {
        if (line.type === DiffLineType.Add) {
          // An unselected added line will stay in the file after discarding the changes,
          // so we just print it untouched on the diff.
          oldCount++
          newCount++
          hunkBuf += ` ${line.text.substring(1)}\n`
        } else if (line.type === DiffLineType.Delete) {
          // An unselected removed line has no impact on this patch since it's not
          // found on the current working copy of the file, so we can ignore it.
          return
        } else {
          // Guarantee that we've covered all the line types.
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.newStartLine,
      newCount,
      hunk.header.oldStartLine,
      oldCount
    )
    patch += hunkBuf
  })

  if (patch.length === 0) {
    // The selection resulted in an empty patch.
    return null
  }

  return formatPatchHeader(filePath, filePath) + patch
}
