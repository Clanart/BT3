The bug class is "withdrawal omits a component of value owed to the user, so the reported/used amounts don't match what the transaction actually contains." The direct Serai analog is in `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`: the fee/weight accounting is computed from `payments` only and silently omits the OP_RETURN `data` output, even though that output is pushed into the real transaction.

### Title
`SignableTransaction::new` omits the OP_RETURN data output from the weight/fee calculation, underpaying the fee (and overpaying change) - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` accepts an optional `data` payload which is pushed as a real `TxOut` (OP_RETURN) onto the transaction at lines 194-202. However, both weight/vbyte estimates are computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, ...)` (lines 204, 225-226), which rebuilds a template transaction using only `payments` — the OP_RETURN output is never included. Consequently `needed_fee` is underestimated by `fee_per_vbyte * sizeof(OP_RETURN output)` (~11-91 bytes → up to ~91 extra bytes for the maximum 80-byte payload), the change output absorbs that shortfall, and the actual fee paid (`sum(inputs) - sum(outputs)`, see `fee()` at lines 138-141) is exactly the underestimated `needed_fee`. The signed transaction's real feerate is lower than the caller-requested `fee_per_vbyte`, and can fall below `DEFAULT_MIN_RELAY_TX_FEE` even though the `TooLowFee` check at lines 211-213 passed.

### Finding Description
- `SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` (lines 194-202) but computes `vbytes`/`weight` from `payments` alone (lines 204, 226).
- `calculate_weight_vbytes` (lines 62-127) constructs the template transaction's `output` vector solely from `payments` plus optional `change`; there is no parameter for `data`.
- `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change = fee_per_vbyte * vbytes_with_change` (line 227) therefore price a transaction that is smaller than the one actually built and signed (`tx` at lines 246-251 includes the data output).
- The change amount is `input_sat - payment_sat - fee_with_change` (line 228). Since the OP_RETURN output adds real bytes but zero value, the fee *paid* remains `fee_with_change` while the vsize grows — the effective feerate drops by `fee_per_vbyte * data_output_vbytes / actual_vsize`, and the `TooLowFee` guard (lines 211-213) validates the under-measured vbytes, not the real ones.
- Symmetrically, the `TooLargeTransaction` check at line 241 uses `weight`, which also excludes the data output, so a transaction relying on `MAX_STANDARD_TX_WEIGHT` can exceed the limit once the data output is included.
- This is reachable purely from public inputs: `data: Option<Vec<u8>>` is an argument to `SignableTransaction::new`, and the produced `SignableTransaction` is what gets signed by the FROST multisig (`multisig`/signing flow consuming `self.tx`).

### Impact Explanation
Analogous to the report (users withdraw less than owed because one component — the pending fee — is omitted from the accounting), here a real output is omitted from the size accounting: the fee reported by `needed_fee()` and embedded in the transaction is lower than the requested rate requires, and any change output is correspondingly overstated. The resulting signed transaction may (a) pay less than the intended feerate, degrading confirmation, (b) fall below the minimum relay fee and be rejected by the network despite passing `TooLowFee`, or (c) exceed `MAX_STANDARD_TX_WEIGHT`. In all cases the multisig signs a transaction whose fee/change split does not match what `SignableTransaction` reported, and in the rejection case the inputs are temporarily unspendable until the plan is rebuilt — funds accounted as spendable that are not. Impact: Medium.

### Likelihood Explanation
Any caller that passes `data` triggers it deterministically — no attacker cooperation or exotic state needed. The severity of the under-payment scales with payload size (up to ~91 vbytes at the 80-byte `TooMuchData` cap). For `fee_per_vbyte` values near the minimum relay rate, even a small payload flips the transaction below the relay threshold. Likelihood is bounded by how often `data` is used (the in-tree processor passes `None`), so Medium-High at the library level, Medium in the integrated flow.

### Recommendation
Pass the data output into the size estimate: extend `calculate_weight_vbytes` to accept the full output list (or an `data_len`/`Option<&ScriptBuf>` parameter), and call it with the OP_RETURN `ScriptBuf` included for both the no-change and with-change estimates. Alternatively, compute `vbytes`/`weight` directly from the final `tx_outs` vector after pushing the OP_RETURN output, so the estimate can never diverge from the signed transaction again.

### Proof of Concept
```rust
// In networks/bitcoin, construct a SignableTransaction with an 80-byte payload
let data = Some(vec![0u8; 80]);
let st = SignableTransaction::new(inputs, &payments, Some(change_addr), data, fee_per_vbyte)
  .unwrap();

// The committed fee
let committed_fee = st.fee();           // == needed_fee, computed WITHOUT the data output
let reported_vbytes = st.needed_fee() / fee_per_vbyte;

// After signing, the real transaction includes the OP_RETURN output
let signed = /* FROST-sign st */;
let actual_vsize = signed.vsize() as u64;

// The actual feerate is below the requested rate
assert!(committed_fee < fee_per_vbyte * actual_vsize);
// With fee_per_vbyte == ceil(min relay), the tx is below DEFAULT_MIN_RELAY_TX_FEE
// even though SignableTransaction::new did not return TooLowFee.
assert!(
  committed_fee * 1000 / actual_vsize <
    u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE)
);
```
