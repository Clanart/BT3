### Title
Once-granted `safe.directory` exception can never be revoked from within GitHub Desktop, leaving permanent execution trust for untrusted-owner repositories - (File: app/src/lib/git/config.ts)

### Summary
GitHub Desktop lets users "trust" a Git repository directory that is owned by a different user (an "unsafe directory," per Git's ownership check) by writing that path into the global `safe.directory` Git config. There is no corresponding UI or API in the app to remove that entry once added, so the trust grant is permanent regardless of subsequent risk changes — directly analogous to the Rubicon report's un-revocable strategist role.

### Finding Description
The trust-granting flow is implemented in `addSafeDirectory`, which appends the path to the global `safe.directory` config value if not already present: [1](#0-0) . This is invoked from two UI surfaces — adding an existing repository [2](#0-1)  and the "missing repository" recovery view [3](#0-2) .

Both flows only ever call `addSafeDirectory`/`addGlobalConfigValueIfMissing`, and `config.ts` exposes no `removeSafeDirectory`, `unsetConfigValue`, or `--unset` counterpart. Grep across the codebase confirms only additive helpers exist (`addGlobalConfigValue`, `addGlobalConfigValueIfMissing`, `addSafeDirectory`) with no removal analog. Once a path is added, Git will trust that directory (and thus allow it to execute repository-provided hooks/config, per the warning text itself: "Adding untrusted repositories may automatically execute files in the repository") for as long as the entry remains in `~/.gitconfig`, and Desktop provides the user no way to see or revoke that exception later — not in Preferences, not on the repository list context menu (which only offers "Remove," which merely drops the repo from Desktop's own list, not the `safe.directory` config) [4](#0-3) .

If a user later reconsiders (e.g., after learning the directory's real owner is untrusted, after cloning it onto a shared/multi-user machine, or after a mistaken click on "Trust Repository" in the missing-repository recovery flow) the only way to undo the exception is to manually edit the global `.gitconfig` file outside of Desktop — an "unnatural" step most users would not know to take. Any repository at that path opened later by Desktop or plain `git` on the same machine (potentially by a different, compromised, or malicious actor with write access to that directory tree, e.g. a shared build server or CI checkout path) continues to silently benefit from the same trust exception.

### Impact Explanation
The `safe.directory` exception exists specifically because Git treats directories owned by another user as potentially hostile, since such repositories can carry local hooks/config that execute code on Git operations. Once granted, this exception is a standing, host-wide (all repositories at that path, for any account) authorization for execution of repository-controlled content, with no expiry or revocation path inside the product. This mirrors the Rubicon "strategist can't be removed" bug class: a security-sensitive permission grant with no corresponding revoke operation, so a mistaken or stale trust decision becomes a permanent weakening of the local security boundary.

### Likelihood Explanation
Likelihood is moderate: it requires the user to have previously clicked "Trust Repository"/"add an exception for this directory" (an in-product action, not attacker-controlled), but shared/multi-user machines, redirected/symlinked folders, or repositories re-populated with different ownership at the same path are common enough scenarios where a stale exception becomes exploitable by whichever party next controls that path.

### Recommendation
Add a management UI (e.g., in Preferences → Git or Advanced) that lists all paths currently present in the global `safe.directory` config and lets the user remove individual entries (via `git config --global --unset safe.directory <path>` or an equivalent `--replace-all` rewrite excluding that path), mirroring the existing `addGlobalConfigValueIfMissing` addition path with a symmetric removal function in `app/src/lib/git/config.ts`.

### Proof of Concept
1. Clone or copy a Git repository into a directory later owned by a different OS user (or simulate via `GIT_TEST_ASSUME_DIFFERENT_OWNER=1`, as done in the test suite [5](#0-4) ).
2. In GitHub Desktop, add this repository via "Add Existing Repository"; Desktop shows the unsafe-directory warning and offers "add an exception for this directory."
3. Click the link, which calls `onTrustDirectory` → `addSafeDirectory(path)`, appending the path to the user's global `~/.gitconfig` under `[safe] directory = <path>`.
4. Attempt to find any Desktop UI (Preferences, repository context menu, "Remove" repository) that removes this entry — none exists; "Remove" only detaches the repo from Desktop's local repository list.
5. The `safe.directory` entry remains in `~/.gitconfig` indefinitely. Any future content placed at that same path (by another user/process with access to the shared location) is automatically treated as trusted by Git and Desktop, with no additional prompt or warning.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```
