### Title
`ThresholdKeys::read` accepts identity verification shares, allowing a crafted key with an attacker-controlled or identity group key - (File: crypto/dkg/src/lib.rs)

### Summary
The reported bug class is a missing validation that rejects the null/zero value for a security-critical field set from external input (the escrow/token address). The analog in Serai is `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`, which deserializes the verification shares — the values that determine the group key — via `<C as Ciphersuite>::read_G` at line 622. That reader (crypto/ciphersuite/src/lib.rs:91-101) enforces canonicality but does *not* reject the identity point. The FROST layer already recognizes identity as dangerous: `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131) exists solely to reject identity points, and `Signed::read` rejects identity signature nonces — yet `ThresholdKeys::read` bypasses `Curve::read_G` entirely. `ThresholdKeys::new` (lines 349-391) then computes `group_key` as the interpolation-weighted sum of `verification_shares` over participants `1..=t` (lines 376-378) with no check that the result, or any share, is non-identity, and no consistency check between `secret_share` and the shares.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, the interpolation variant, a raw `secret_share` scalar, and `n` verification shares. For every share it calls `<C as Ciphersuite>::read_G(reader)` (crypto/dkg/src/lib.rs:622), which returns the identity point without error. `ThresholdKeys::new` validates only the share count and participant index range (lines 355-365) — it never checks `is_identity` on any share nor on the derived `group_key`. A crafted buffer with all-identity verification shares yields `ThresholdKeys` whose `group_key()` is the identity element — the public key for discrete log 0. Alternatively, the attacker can set shares so the weighted sum equals *any* point whose discrete log they know, while `secret_share` is an arbitrary plaintext scalar the deserializer never checks against the verification shares.

### Impact Explanation
A group key equal to the identity point corresponds to a threshold private key of `0` (plus offset). Schnorr verification `sG == R + cA` with `A = identity` degenerates to `sG == R`, so *anyone* can produce a valid signature `(R = sG, s)` for any message — a universal forgery under the affected key. More generally, because `group_key` is a linear combination of attacker-chosen shares, the attacker can fix it to a key they fully control, so signatures produced under it are unilaterally forgeable and any funds/outputs attributed to that group key are stealable or unspendable. On the Bitcoin side, `x_only`/`x` in networks/bitcoin/src/crypto.rs:13-23 panic on the point at infinity, so an identity group key would additionally crash address derivation. This matches the "forged signature" and "funds reported received that are not spendable" acceptance criteria.

### Likelihood Explanation
`ThresholdKeys::read` is one of the sanctioned untrusted-byte sinks. The check is simply absent — `Curve::read_G` demonstrates the codebase's own intent to reject identity, and the dkg deserialization path skips it. The one caveat: inside the in-scope crates there is no network-facing caller piping peer bytes into `ThresholdKeys::read`; its in-repo callers are the processor's local DB and test-vector import. Exploitability therefore requires a deployment path where serialized keys cross a trust boundary (e.g., keys supplied/relayed by an untrusted party or restored from attacker-influenced storage), which is the exact scenario the bug class covers. Likelihood is moderate; impact if reached is high (Medium overall).

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349), reject any `verification_shares` value for which `is_identity()` holds, and reject when the computed `group_key` is identity. Optionally verify `C::generator() * secret_share == verification_shares[params.i()]` to bind the secret share to the shares. At minimum, use `Curve::read_G`-style identity rejection when `C: Curve`, or perform the identity check directly in `read`/`new` since `dkg` is generic over `Ciphersuite`.

### Proof of Concept
For a 1-of-1 key over any `C: Ciphersuite` (e.g. `Ristretto`):

```rust
// Build a ThresholdKeys serialization with an identity verification share
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(1u16.to_le_bytes());            // t = 1
buf.extend(1u16.to_le_bytes());            // n = 1
buf.extend(1u16.to_le_bytes());            // i = 1
buf.push(1);                               // Interpolation::Lagrange
buf.extend(C::F::ZERO.to_repr().as_ref()); // secret_share = 0 (never checked)
buf.extend(C::G::identity().to_bytes().as_ref()); // verification share = identity — ACCEPTED

let keys = ThresholdKeys::<C>::read::<&[u8]>(&mut buf.as_ref()).unwrap();
assert!(bool::from(keys.group_key().is_identity())); // group key is the identity point

// Any s yields a valid Schnorr signature under this key:
// verify checks sG == R + c*A with A = identity, so (R = sG, s) always verifies.
```

No error is raised by `read` or `ThresholdKeys::new`, demonstrating the missing null-value validation.

Uncertainty note: I could not confirm a concrete in-scope caller that feeds network-attacker bytes into `ThresholdKeys::read` (only trusted DB/test call sites were found), so the finding rests on `ThresholdKeys::read` being a designated untrusted-input boundary per the engagement rules.
