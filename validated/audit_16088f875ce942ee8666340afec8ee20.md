### Title
`ThresholdKeys::new` binds the group key to only the first `t` verification shares, leaving shares for participants `t+1..=n` unverified against the committed secret — ([File: crypto/dkg/src/lib.rs](bsaldua/serai--003/crypto/dkg/src/lib.rs))

### Summary
The external report describes `MultiMerkleDistributor` accepting a Merkle root whose leaf amounts are not verified to equal the rewards allocated to that quest/period, letting one bucket's claims drain another's. The Serai analog is in `ThresholdKeys::new`: the `group_key` — the aggregate "allocation" every participant relies on — is computed solely by interpolating the verification shares of participants `1..=t`. The remaining `n - t` verification shares are stored and later used by `ThresholdView`/`verify_share` without ever being checked for consistency with the polynomial committed by `group_key`, and `secret_share` is never checked against `verification_shares[i]` either. Shares belonging to a different key generation (a different "quest/period") can therefore be mixed into one `ThresholdKeys` without detection.

### Finding Description
In `ThresholdKeys::new` (`crypto/dkg/src/lib.rs`):

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

(Lines 376–378.) The only validation performed on `verification_shares` is a count check (`len() == n`) and a bound check (`participant <= n`) at lines 355–365. Nothing verifies that the shares at indexes `t+1..=n` lie on the same polynomial defined by shares `1..=t`, nor that `group_key * 1 == G * (sum of all interpolated shares)`. This is precisely the reported bug class: the committed aggregate is not checked against the total of all claimed amounts — the "claims" (per-participant verification shares) beyond the first `t` are effectively an unbounded bucket.

This state is reachable through `ThresholdKeys::read`-deserialized (untrusted) bytes — the struct carries private `core` fields populated from the wire — or through any construction path that feeds attacker-influenced `verification_shares` into `ThresholdKeys::new`. `view()` (lines 463–533) then interpolates `secret_share` and the stored `verification_shares` for the caller-supplied `included` set, and `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:447-495`) verifies each participant's share against `self.view.verification_share(l)` before checking the aggregate signature. Because the verification shares for `l > t` were never bound to `group_key`, a view for a signing set containing such a participant mixes buckets: shares verify against one set of commitments while the group key commits to another.

### Impact Explanation
- An attacker who supplies crafted serialized `ThresholdKeys` can set arbitrary verification shares for indexes `t+1..=n`. In a signing session whose `included` set contains such a participant, an honest participant's correct share is rejected (`FrostError::InvalidShare(l)` at `crypto/frost/src/sign.rs:483-488`), misattributing blame to honest signers, or a crafted share can be made to pass per-share verification while the aggregate `sum` fails, producing the `InternalError` path at line 494 — stalling or corrupting the signing session.
- More broadly, the same `group_key` is reported by `group_key()` regardless of which shares are actually committed beyond `t`, so different views of the "same" keys commit to different effective secrets — the direct equivalent of claims for one period being paid from tokens allocated to another.

### Likelihood Explanation
Exploitation requires feeding semantically inconsistent `ThresholdKeys` into the system (e.g., via `ThresholdKeys::read` on untrusted bytes or a bug/malformed input upstream of `ThresholdKeys::new`), analogous to the buggy Merkle-tree-generation precondition in the original report — low likelihood, but the code itself acknowledges this gap: `crypto/frost/src/sign.rs:491-493` notes the only known way to reach the terminal error is "to deserialize a semantically invalid FrostKeys," which is exactly the state `ThresholdKeys::new` fails to reject.

### Recommendation
In `ThresholdKeys::new`, verify full consistency: check that `verification_shares[i] == G * secret_share` for `i == params.i()`, and check that the interpolated group key is identical for every size-`t` subset (or, equivalently, that interpolating over all `n` shares with the expected zero-index evaluation yields `group_key` and that each share at `t+1..=n` equals the polynomial's evaluation at that index — i.e., `verification_shares[l] == sum_j commitments_j * l^j` when commitments are available, or a pairwise-consistency check across an additional `t`-subset drawn from `t+1..=n`). This is the analog of enforcing `sum(amounts) == allocated` per bucket: every share in the map must be bound to the same committed polynomial as `group_key`, not just the first `t`.
