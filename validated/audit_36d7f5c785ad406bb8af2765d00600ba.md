### Title
Empty SchnorrAggregate passes signature verification - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` checks that `self.Rs.len() == keys_and_challenges.len()` but never requires that count to be non-zero. When both are empty, the multiexp reduces to the single pair `(-s) * G`; an attacker who supplies `s = 0` makes that pair the identity, so `verify` returns `true` for an aggregate "signature" that contains no signatures at all. This is the same bug class as the Lombard report: a validation routine that iterates over inputs, finds "no violations", and returns success without checking that at least one element was actually validated.

### Finding Description
In `crypto/schnorr/src/aggregate.rs:127-146`, `verify` builds `pairs` in a loop over `keys_and_challenges` and appends `(-self.s, C::generator())`. With `keys_and_challenges` empty and a crafted `Rs: vec![]`, `pairs` contains only `(-s, G)`. `multiexp_vartime` over `[(0, G)]` yields the identity, so `verify` returns `true`. The attacker-controlled encoding comes from `SchnorrAggregate::read` (`aggregate.rs:77-88`), which accepts a length prefix of `0` and then reads `s`; `read` does not reject `len == 0`, and `s = 0` is a canonically encodable scalar. The honest producer path cannot create this — `SchnorrAggregator::complete` returns `None` when `self.sigs.is_empty()` (`aggregate.rs:176-178`) — so acceptance of the empty aggregate is purely a verifier-side flaw, exactly mirroring `checkProposalIsWellFormed` returning `true` for zero values.

The same shape exists in `crypto/dleq/src/lib.rs`: `DLEqProof::verify` (lines 160-180) and `MultiDLEqProof::verify` (lines 264-294) only check length equality and then compare `self.c` to a transcript challenge. With empty `generators`/`points`, the challenge is over a transcript containing only the `dleq`/`multi_dleq` domain separator — fully public and computable by anyone — so a forged proof `(c = challenge, s = anything)` verifies.

### Impact Explanation
Any caller that verifies a `SchnorrAggregate` against a dynamically-built `keys_and_challenges` list that can end up empty (e.g., no qualifying signers collected) will accept attacker-supplied bytes `00 00 00 00 || 0x00..00` as a valid aggregate signature — a forged signature accepted by a `verify` API on untrusted input. Likewise, a `DLEqProof`/`MultiDLEqProof` verified against an empty statement set is a forged proof that "proves" nothing while returning `Ok(())`. Severity: Medium — the flaw requires a caller reaching `verify` with an empty statement list, so exploitability depends on the integrator, but the verifier formula is incorrect (it vacuously authorizes an empty set).

### Likelihood Explanation
Medium-low. The empty aggregate is trivially forgeable (four zero bytes plus a zero scalar, or `SchnorrAggregate { Rs: vec![], s: C::F::ZERO }`), and no secret or privileged position is needed. However, it only yields a bypass when downstream code calls `verify` with a zero-length `keys_and_challenges` slice and treats `true` as authorization; callers that always supply at least one key are unaffected. Notably, `verify` is `#[must_use]` and documents requirements only on challenge crafting and DST — there is no documented MUST requiring a non-empty input, so this is an undocumented edge case, not documented-misuse.

### Recommendation
Reject empty inputs at the verification boundary:
- In `SchnorrAggregate::verify`, return `false` when `keys_and_challenges.is_empty()` (equivalently when `self.Rs.is_empty()`), and/or reject `len == 0` in `SchnorrAggregate::read`.
- In `DLEqProof::verify` and `MultiDLEqProof::verify`, return `Err(DLEqError::InvalidProof)` when `generators.is_empty()` (and when any inner generator list is empty), matching the fix applied in the upstream remediation (`hasValue` must be true before returning success).

### Proof of Concept
```rust
// crypto/schnorr (e.g., with ciphersuite kp256 / Secp256k1)
// Attacker-controlled bytes fed to SchnorrAggregate::read, then verify:
let mut bytes: &[u8] = &{
    let mut v = 0u32.to_le_bytes().to_vec();      // Rs.len() == 0
    v.extend(<Secp256k1 as Ciphersuite>::F::ZERO.to_repr().as_ref()); // s == 0
    v
};
let agg = SchnorrAggregate::<Secp256k1>::read(&mut bytes).unwrap();
// Verifier with an empty statement list accepts the forgery:
assert!(agg.verify(b"some dst", &[])); // returns true; expected: reject
```
Analogous for DLEq: `DLEqProof { c: challenge(empty_dleq_transcript), s: arbitrary }.verify(&mut t, &[], &[])` returns `Ok(())`.

Uncertainty note: I could not exhaustively confirm which in-scope production caller reaches `verify` with a potentially empty list; the finding stands on the verifier accepting a forgeable empty input, per the bug-class mapping rules.
