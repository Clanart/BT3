Based on my research, I found a concrete gap in how GitHub Desktop parses attacker-controlled deep-link data, which is the closest analog to the "missing owner parameter" bug class (a value that downstream consumers need for safe handling is dropped/unvalidated before being passed on).

### Title
Deep-link `filepath` parameter is passed through `parseAppURL` without sanitization while `branch` is validated - ([File: app/src/lib/parse-app-url.ts])

### Summary
`x-github-client://openrepo/...` deep links (the "Open in Desktop" URL scheme) are parsed by `parseAppURL()`. The function explicitly validates the `branch` query parameter against `testForInvalidChars()` before accepting the action, but the sibling `filepath` parameter is read via `getQueryStringValue()` and forwarded into `IOpenRepositoryFromURLAction.filepath` completely unvalidated.

### Finding Description
`parseAppURL` builds an `IOpenRepositoryFromURLAction` from an externally-controlled URL (clicked by the user, e.g. from a webpage's "Open in Desktop" button or a crafted link): [1](#0-0) 

Note the asymmetry: `branch` is checked with `testForInvalidChars(branch)` (which rejects control characters, `..`, path-like sequences, etc., per `sanitize-ref-name.ts`) and the request is rejected if invalid, but `filepath` has no equivalent check — it is taken verbatim from the query string and placed into the parsed action: [2](#0-1) 

This is confirmed by the existing unit tests, which only exercise well-formed relative paths for `filepath` (e.g. `Octokit.Reactive/Octokit.Reactive.csproj`) and never test traversal sequences like `../../`, absolute paths, or protocol-relative values: [3](#0-2) 

The parsed `filepath` value is documented as "the file to open after cloning the repository": [4](#0-3) 

This value is consumed by `app/src/ui/dispatcher/dispatcher.ts`, which references `filepath`/`IOpenRepositoryFromURLAction` in multiple places to open the file post-clone.

### Impact Explanation
If the consuming code in `dispatcher.ts` joins `filepath` to the freshly-cloned repository path and opens/reveals it (e.g., via the editor or `shell.showItemInFolder`/`shell.openItem`-style APIs) without re-validating for `..` traversal or absolute-path overrides, an attacker who controls a link the victim clicks could cause Desktop to open or reveal an arbitrary file outside the cloned repository directory. This matches the "attacker controls a link/deep link the user clicks" + "file read outside the repo" impact category.

### Likelihood Explanation
I could not confirm within this session whether `dispatcher.ts`'s consumption of `filepath` re-validates the path or safely joins it (path traversal could be neutralized downstream by `path.join`/normalization checks, or the file-open code might already scope the path to the repo directory). The `grep_search` results only returned match counts for `dispatcher.ts` without letting me inspect the actual sink logic, so likelihood is **unconfirmed** — this is a real gap in the parsing layer, but whether it's exploitable depends on code I was unable to view in this session.

### Recommendation
Apply the same validation used for `branch` to `filepath` in `parseAppURL()` — reject or sanitize any `filepath` value containing `..` segments, an absolute path prefix, or characters outside an allow-list, before constructing `IOpenRepositoryFromURLAction`. Additionally, wherever `filepath` is consumed (in `dispatcher.ts`), the resolved path should be normalized and asserted to remain within the cloned repository root before being opened or revealed.

### Proof of Concept
A crafted link such as:
```
x-github-client://openrepo/https://github.com/some/repo?branch=main&filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa
```
would pass `parseAppURL` validation unchanged (only `branch` is checked), yielding `filepath: '../../../../.ssh/id_rsa'` in the resulting `IOpenRepositoryFromURLAction`, as shown by the parsing logic: [5](#0-4) 

**Caveat**: I was not able to inspect the exact code path in `app/src/ui/dispatcher/dispatcher.ts` where this `filepath` is ultimately used within this session (search results only showed match counts, not line content), so I cannot confirm whether a traversal-safe join/normalization already exists there. I recommend a follow-up session read `app/src/ui/dispatcher/dispatcher.ts` (search for `filepath` and `openRepositoryFromUrl`) to verify whether the sink actually opens the resolved path without re-validating it, which would confirm full exploitability.

```typescript
  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
```
