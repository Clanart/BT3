### Title
Untrusted `ReceivedOutput` bytes allow injecting fabricated inputs into `SignableTransaction`, making the FROST multisig sign transactions spending nonexistent / mis-valued prevouts - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction` consumes `ReceivedOutput`s whose `offset`, `output` (`TxOut` value + `script_pubkey`), and `outpoint` are fully deserialized from untrusted bytes by `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`). The only authenticity check performed before signing is `p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey` in `SignableTransaction::multisig` (`send.rs:273-285`), which verifies that the *claimed* script equals `group_key + offset*G` — a relation the attacker satisfies for free because they choose `offset` and write `script_pubkey` themselves. The claimed `outpoint` and `output.value` are never checked against the chain or any scanner record. This is the structural analog of `VeTokenMinter.withdraw(destination, amount)`: arbitrary destination and arbitrary amount fields are trusted and committed to without verification.

### Finding Description
- `ReceivedOutput::read` accepts attacker-controlled `offset`, `TxOut`, and `OutPoint` with no binding to on-chain reality (`mod.rs:122-134`).
- `SignableTransaction::new` sums the claimed `output.value`s into `input_sat` (`send.rs:175`) and derives the change amount as `input_sat - payment_sat - fee_with_change` (`send.rs:228-233`). An inflated claimed value therefore creates a change output worth more than the wallet's real inputs.
- `TransactionSignMachine::sign` computes `taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), TapSighashType::Default)` (`send.rs:373-390`), committing the threshold signature to the fabricated amount, script, and outpoint set.
- `TransactionSignatureMachine::complete` then emits the final signed `Transaction` with valid BIP-340 witnesses for that (fabricated) sighash (`send.rs:413-427`).

### Impact Explanation
Two concrete consequences are reachable solely by feeding crafted bytes to `ReceivedOutput::read`:

1. **Signing an unintended message.** The multisig emits a valid threshold signature over a transaction spending an outpoint that does not pay it (or that was already spent), paying attacker-chosen `payments` — a signature that was never backed by real funds. Any consumer that treats the produced signature/plan as evidence of an authorized spend (e.g., eventuality tracking, accounting that credits the change output) acts on a payment that can never confirm.
2. **Funds reported spendable that are not.** With an inflated `output.value`, the change output is computed from phantom input value (`send.rs:228-233`) and the signature is bound to the fake amount, so the transaction is permanently unbroadcastable while the wallet layer may still account the inflated balance — the direct analog of "withdraw an amount the contract context doesn't actually justify."

### Likelihood Explanation
The reachability is exactly the `ReceivedOutput::read` untrusted-bytes vector whitelisted for this scope; no threshold collusion, malicious validator, or key compromise is required — only the ability to supply the serialized `ReceivedOutput` to the signing path. Severity is bounded to Medium because a forged input cannot produce a *confirmable* drain (BIP-341 commits to the real prevout amount/script), so the impact is mis-signed spends and misaccounted/locked value rather than direct theft.

### Recommendation
Authenticate every `ReceivedOutput` before constructing a `SignableTransaction`: verify `outpoint` resolves to an unspent UTXO whose `script_pubkey` *and* `value` match `output` exactly (e.g., require the output to originate from `Scanner::scan_transaction`/`scan_block`, and carry a proof or re-fetch the prevout via RPC at signing time). In `multisig`, additionally assert `offsets[i]` is a registered offset rather than accepting any scalar that yields a matching script.
