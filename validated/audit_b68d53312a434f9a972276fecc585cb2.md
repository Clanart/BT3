### Title
Missing access control on `WombatStaking.convertWOM`/`convertAllWom` allows anyone to permanently lock WOM held by the contract into veWom with no receipt minted - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.convertWOM(uint256)` and `convertAllWom()` are `external` with only a `whenNotPaused` guard and no caller restriction, so any unprivileged address can trigger locking of whatever WOM balance currently sits in the `WombatStaking` contract into a 1461-day veWom position via `IVeWom(veWom).mint`. Because the caller of `convertWOM` need not be `mWOM`, this lock can happen without any corresponding `mWOM` mint or `totalAccumulated` update, disconnecting the locked WOM from any redeemable claim.

### Finding Description
`convertWOM` performs no caller check: [1](#0-0) 
`convertAllWom` similarly has no restriction and simply forwards the entire WOM balance of the contract to `convertWOM`: [2](#0-1) 

The intended flow is that `mWOM._lockWom` calls `convertWOM` and immediately afterwards updates `totalAccumulated` with the returned `veWom` amount, which is the accounting bridge that ties locked WOM to mintable `mWOM` claims: [3](#0-2) 

Since `convertWOM` has no `onlyMWom`/`onlyOperator` restriction, any address holding no privilege can call it directly against whatever WOM balance the `WombatStaking` contract currently holds (e.g., dust from `_sendRewards` fee rounding, a leftover balance sent to the contract, or a balance created by an admin action such as `mWOM.lockAllWom` before `_lockWom` executes its second internal step). Calling `convertWOM(amount)` directly bypasses `mWOM._lockWom`'s `totalAccumulated` bookkeeping entirely, and the veWom minted goes to `WombatStaking`'s own veWom balance without any `mWOM` being minted to anyone, and without `mWOM.totalAccumulated` reflecting the newly locked veWom.

Note: in the concrete call sites found in this codebase (`mWOM.convert`/`convertAndStake` and `mWOM.lockAllWom`), the WOM transfer into `WombatStaking` and the `convertWOM` call happen within the same atomic transaction/internal call, so a true "front-run between transfer and convert" of a specific pending user transaction is not reachable. The exploitable surface is instead any WOM balance that persists in `WombatStaking` across transactions (dust, accidental/incidental transfers, or admin-triggered balances) — any such balance can be seized and irrevocably locked by an unprivileged third party since `convertWOM`/`convertAllWom` carry no caller restriction.

### Impact Explanation
Locking WOM into a ~4-year veWom position (`lockDays = 1461`) with no corresponding `mWOM` mint and no `totalAccumulated` update permanently orphans the accounting link between locked WOM and its claimable receipt for the duration of the lock, satisfying the "funds frozen ≥24 hours" impact bar. This corresponds to an Immunefi "Temporary freezing of funds" (or worse, permanent loss of accounting backing) impact class, since the WOM is locked for years and, once locked, cannot be un-approved or clawed back by legitimate flows that expect `convertWOM` to only be reachable via the accounted `mWOM._lockWom` path.

### Likelihood Explanation
No special privileges or capital are required — any EOA can call `convertWOM`/`convertAllWom` at any time `WombatStaking` holds a nonzero WOM balance. The precondition is the existence of a nonzero, unlocked WOM balance in `WombatStaking` (e.g., rounding dust from `_sendRewards`, or a transient balance from an admin operation), which is plausible but not deterministically attacker-controllable in every call path examined, since the primary user-facing paths (`mWOM.convert`, `convertAndStake`) perform the transfer-then-convert atomically within a single transaction.

### Recommendation
Restrict `convertWOM` and `convertAllWom` to only be callable by `mWom` (or an authorized operator), e.g. add a modifier `onlyMWom` checking `msg.sender == mWom`, mirroring the pattern used elsewhere (`_onlyPoolHelper`), so arbitrary callers cannot trigger locking of resting WOM balances without the corresponding `mWOM`/`totalAccumulated` accounting update.

### Proof of Concept
Foundry test outline:
1. Deploy/initialize `WombatStaking`, `mWOM`, and a mock `veWom` implementing `IVeWom.mint`.
2. Directly transfer WOM tokens to the `WombatStaking` contract address (simulating dust/residual balance) without going through `mWOM`.
3. From an unrelated EOA with no privileges, call `wombatStaking.convertWOM(amount)` (or `convertAllWom()`).
4. Assert: `IERC20(veWom).balanceOf(address(wombatStaking))` increased by the minted veWom amount.
5. Assert: `mWOM.totalAccumulated()` was NOT updated (still equals its prior value) and no `mWOM` tokens were minted to any address.
6. This demonstrates WOM was locked for `lockDays` (1461 days) with no corresponding claim token issued to any party.

```text
    /// @notice convert WOM to mWOM
    /// @param _amount the number of WOM to convert
    /// @dev the WOM must already be in the contract
    function convertWOM(uint256 _amount) whenNotPaused external returns(uint256) {
        uint256 veWomMintedAmount = 0;
        if (_amount > 0) {
            IERC20(wom).safeApprove(veWom, _amount);
            veWomMintedAmount = IVeWom(veWom).mint(_amount, lockDays);
        }

        emit WomLocked(_amount, lockDays, veWomMintedAmount);

        return veWomMintedAmount;
    }
```

```text
        if (_needSend)
            IERC20(wom).safeTransfer(wombatStaking, _amount);

        uint256 mintedVeWomAmount = IWombatStaking(wombatStaking).convertWOM(_amount);
        totalAccumulated = totalAccumulated + mintedVeWomAmount;
```
