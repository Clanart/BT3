### Title
Order fill has no deadline check, letting `_cancelFromSource`'s stale-height GET proof pay both the user's refund and the solver's redemption for the same escrow - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2.fillOrder()` never checks `order.deadline` before calling `_fillCrossChain`, while `_cancelFromSource()` only allows cancellation once `options.height > order.deadline` and then relies on a **historical** storage-proof snapshot at that specific height to decide whether to refund. Because filling is not blocked by the deadline, a solver can still fill the order at a destination block *after* the queried height while the user's stale "not-filled" proof is still in flight, causing the escrow to be paid out twice conceptually (refund to the user AND the solver already delivered outputs) even though the actual balance-level double-spend of the escrow itself is only avoided by luck of message-arrival order — whichever request lands first at `_withdraw` wins, and the loser silently reverts with `UnknownOrder`, meaning either the user gets a double benefit (destination output tokens from the solver AND their source escrow refund) or the solver's redemption is lost after having already paid out.

### Finding Description
`_cancelFromSource` gates cancellation only on the order creator and on `options.height > order.deadline`: [1](#0-0) 

It dispatches a Hyperbridge GET request that reads the destination's `_filled[commitment]` storage slot **at `options.height`** — a height the caller picks, only required to be one block past the deadline. This is a snapshot proof of state at a single historical block, not a proof that the order is *currently* unfilled.

`onGetResponse` then unconditionally refunds if the slot was empty at that height: [2](#0-1) 

Meanwhile, `_fillCrossChain` — reachable from the public `fillOrder` entrypoint in `IntentGatewayV2.sol` — has no deadline check at all; its only gate against double-use is `_filled[commitment] != address(0)`: [3](#0-2) [4](#0-3) 

So a solver can legally fill an *expired* order at any destination block height, including one *after* `options.height` used in a concurrently in-flight cancellation-from-source. Both paths then race to reach `IntentsBase._withdraw` on the source chain: [5](#0-4) 

`_withdraw` only guards against a *second* claim on the same commitment by checking `escrowed == 0`, i.e. it protects the pooled balance, not the fact that the order state is inconsistent across chains. The two competing settlement paths (RefundEscrow from `_cancelFromSource`/`onGetResponse`, and RedeemEscrow from `_fillCrossChain`) are validated with two structurally different invariants — a stale, attacker-selected historical proof for the refund path versus no timing check at all for the fill path — exactly the same class of bug as the original report: two related state-validity checks (bare vs. weighted collateral there; "unfilled-at-height-H" vs. "no deadline gate on fill" here) diverge, and the weaker one is used to authorize the withdrawal-type action.

### Impact Explanation
Whichever of `RefundEscrow` / `RedeemEscrow` is delivered to the source chain first wins the escrowed input tokens; the second reverts with `UnknownOrder`. If the refund (based on the stale "unfilled at H" proof) lands first even though the order was actually filled afterward:
- The user receives the destination-chain output tokens from the solver's fill AND the full escrowed input-token refund on the source chain — a double payout funded by the solver.
- The solver, who already delivered `order.output` tokens on the destination chain in good faith, gets no reimbursement and permanently loses the value they paid out.

This is direct loss of funds / wrong-beneficiary settlement caused by inconsistent state-acceptance rules between two code paths that should agree on "is this order fillable/cancelable," matching the bounty's "false proof/state acceptance" and "stealing or loss of funds" categories. No malicious relayer, prover, or governance actor is required — an ordinary user (or a user colluding with themselves) triggers `_cancelFromSource` with a low `options.height` right after `order.deadline`, and any solver filling near/at expiry can be exploited by the race.

### Likelihood Explanation
The conditions are fully attacker-controlled and require only two public transactions plus normal relayer message delivery (no special privileges): (1) an order nearing/at its deadline that a solver is willing to fill slightly late (common when solvers race to capture fills before formal cancellation is finalized), and (2) the user submitting `cancelOrder` from the source chain with `options.height = order.deadline + 1`. Because `fillOrder` never checks the deadline, this window is not a rare edge case — it exists for every cross-chain order whenever a fill happens after the deadline but before the (asynchronous, challenge-period-gated) GET response is delivered back to source.

### Recommendation
Make the two invariants consistent:
- Reject fills in `_fillCrossChain`/`fillOrder` once `block.number > order.deadline` (mirroring the check already present for `_cancelFromDest`), so a filled/cancelable state cannot diverge across chains.
- Alternatively/additionally, require `_cancelFromSource`'s GET proof height to reflect the *current* finalized destination height rather than an attacker-chosen `options.height` immediately after the deadline, or have `_withdraw`/`onAccept` cross-check an on-chain "still cancellable" flag rather than trusting a single historical snapshot.

### Proof of Concept
1. User places a cross-chain order with `deadline = D`.
2. At destination block `D+5`, a solver calls `fillOrder` — succeeds because `_fillCrossChain` never checks `order.deadline` (`evm/src/apps/IntentGatewayV2.sol:421-446`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol:89-93`). Solver transfers output tokens to the beneficiary and dispatches `RedeemEscrow`.
3. Concurrently (or just before, off-chain), the user calls `cancelOrder` from the source chain with `options.height = D+1` (`_cancelFromSource`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol:188-223`). At height `D+1`, `_filled[commitment]` was indeed still empty (fill happened at `D+5`), so the GET proof is valid and the request is dispatched.
4. Hyperbridge delivers the `onGetResponse` refund to the source chain before the `RedeemEscrow` post arrives (fully plausible given relayer/proof timing variance): `_withdraw(body, true, true)` pays `order.user` the full escrow (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:319-324`, `evm/src/apps/intentsv2/IntentsBase.sol:391-410`).
5. When the solver's `RedeemEscrow` request later arrives, `_orders[commitment][token]` is already `0`, so `_withdraw` reverts with `UnknownOrder` — the solver receives nothing despite having paid the user's output on the destination chain, while the user has already been refunded the input escrow in addition to receiving the destination payout.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
