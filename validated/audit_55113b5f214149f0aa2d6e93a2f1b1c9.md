### Title
Unauthenticated `send_move_to_vault_tx` accepts a movetx with a mismatched `deposit_outpoint` - ([File: core/src/rpc/aggregator.rs])

### Summary
The aggregator's `send_move_to_vault_tx` RPC validates that a submitted raw transaction has the shape of a move-to-vault transaction (correct output count, correct N-of-N/security-council script pubkey, correct bridge amount and anchor amount), but it never checks that the transaction's actual input (`movetx.input[0].previous_output`) matches the caller-supplied `deposit_outpoint` field [1](#0-0) . The `deposit_outpoint` supplied by the caller is stored as-is in `TxMetadata` and persisted to the database as the attribution key for this move-to-vault transaction [2](#0-1) .

### Finding Description
`send_move_to_vault_tx` deserializes the caller-provided raw transaction and the caller-provided `deposit_outpoint`, independently [3](#0-2) . It checks:
- input/output counts,
- output amounts (bridge amount and 0-sat anchor),
- output script pubkeys (N-of-N/security-council address and anchor script),

but at no point does it decode `movetx.input[0].previous_output` and compare it to the `deposit_outpoint` argument [4](#0-3) . The two values are then bound together only inside `TxMetadata { deposit_outpoint: Some(deposit_outpoint), ... tx_type: TransactionType::MoveToVault }`, which is what downstream bookkeeping (tx-sender persistence, deposit-to-movetx attribution) relies on to know which deposit a given move-to-vault transaction corresponds to [5](#0-4) .

Per the documented authentication model, the aggregator's gRPC server does not enforce client certificates (`config.client_verification` gates whether `OnlyAggregatorAndSelf` or `Noop` interceptor is installed, and the docs explicitly state "The aggregator does not enforce client certificates but does use TLS for encryption") [6](#0-5) [7](#0-6) . This means `send_move_to_vault_tx` is reachable by any unauthenticated caller who can open a TLS connection.

### Impact Explanation
Because the record of "which `deposit_outpoint` this move-to-vault transaction belongs to" is taken purely from an unauthenticated, unvalidated caller parameter, and is disconnected from the transaction's real input, the deposit-outpoint-to-movetx mapping that downstream logic (`get_move_to_vault_txid_from_citrea_deposit`/`upsert_move_to_vault_txid_from_citrea_deposit`) relies on for tracking withdrawal/deposit bookkeeping can be poisoned [8](#0-7) . I was not able to fully trace, within the remaining investigation budget, whether this mismatched attribution is later used to authorize an operator reimbursement or a payout crediting decision (i.e., whether a component trusts this `deposit_outpoint`↔movetx binding as proof that a specific deposit was moved) — that link would need to be confirmed in `core/src/operator.rs` and the reimbursement flow before this can be scored as a concrete "operator reimbursed for a payout it never funded" or "vault UTXO permanently frozen" case per the strict impact rubric.

### Likelihood Explanation
The RPC is reachable without any privileged role given the aggregator's default (no client-cert) configuration, and the mismatch bug requires only the attacker to already possess *some* validly-signed move-to-vault transaction (which any legitimate depositor obtains through the normal `new_deposit` flow) — so the barrier is low, but the concrete custody-breaking consequence of the mislabeling is unconfirmed.

### Recommendation
Decode `movetx.input[0].previous_output` inside `send_move_to_vault_tx` and require it to equal the caller-supplied `deposit_outpoint` before accepting the request, so the `TxMetadata.deposit_outpoint` binding used by downstream reimbursement/withdrawal bookkeeping cannot be forged independently of the actual on-chain input.

### Proof of Concept
Not fully constructible from static analysis alone: an attacker would call `send_move_to_vault_tx` with a validly-signed move-to-vault raw tx (obtained via their own legitimate `new_deposit`) but pass a different, victim `deposit_outpoint` value; the code path shown accepts this without any input-vs-outpoint consistency check [9](#0-8) . Whether this mislabeling is subsequently exploited into an actual reimbursement/attribution violation requires further tracing through `core/src/operator.rs`'s deposit/payout logic, which I could not complete within the available tool budget.

## RPC Authentication

Clementine uses mutual TLS (mTLS) to secure gRPC communications between entities
and to authenticate clients. Client certificates are verified and filtered by
the verifier/operator to ensure that:

1. Verifier/Operator methods can only be called by the aggregator (using
