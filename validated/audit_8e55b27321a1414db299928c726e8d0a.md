## Title
Payout transaction's `SIGHASH_SINGLE|ANYONECANPAY` signature allows an unprivileged party to hijack operator-attribution of a withdrawal in the Bitcoin mempool - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `payout_tx` that fronts a Citrea withdrawal is signed by the user with `SIGHASH_SINGLE|ANYONECANPAY` [1](#0-0) , which only commits to the single input and the output at the same index (the user's payout output). The OP_RETURN output that records "which operator fronted this payout" is left completely unsigned and mutable [2](#0-1) . Anyone who observes the operator's broadcast `payout_tx` in the Bitcoin mempool (i.e., analogous to observing the "reveal") can reuse the same input/signature and re-broadcast a competing version with a different OP_RETURN payload before the original confirms, altering the on-chain record of who is credited as payer for the withdrawal.

### Finding Description
`create_payout_txhandler` builds a transaction with:
1. Input: the withdrawal UTXO, spent with the user's `KeySpend` signature.
2. Output 0: user payout output (covered by `SIGHASH_SINGLE`).
3. Output 1: anchor output.
4. Output 2: OP_RETURN with the fronting `operator_xonly_pk` [2](#0-1) .

`parse_withdrawal_sig_params` explicitly enforces (and even coerces legacy defaults into) `TapSighashType::SinglePlusAnyoneCanPay` for the user's signature [1](#0-0) . Under BIP-341/342 semantics, `SIGHASH_SINGLE|ANYONECANPAY` commits only to input 0 and output 0 of that specific transaction; it places no constraint on any other outputs (or on additional inputs) in a transaction that reuses this exact signed input. This means the OP_RETURN output containing the `operator_xonly_pk` — the sole on-chain artifact used to attribute "who fronted this payout" — can be freely swapped by anyone with access to the input/signature pair, as long as output 0 (the user's payment) is preserved unchanged.

Once an operator broadcasts `payout_tx` to the Bitcoin network (before confirmation), the transaction, including the witness/signature, becomes public mempool data. This is functionally the analog of the UMA "reveal transaction front-running" bug: a value that is later relied upon for economically significant attribution (the operator credit) is finalized only when the transaction confirms, but is observable before that point, allowing a third party to react and substitute their own version with a different attribution before the original is mined (e.g. by rebroadcasting with a higher fee / winning the race, since the input/output-0 pair remains valid for the substituted transaction too).

On the consuming side, `validate_payer_is_operator` and the payout-checker task treat the on-chain `payout_payer_operator_xonly_pk` recorded via this OP_RETURN as ground truth for the reimbursement pipeline [3](#0-2) , [4](#0-3) . If the OP_RETURN is swapped after broadcast but before confirmation, the recorded "payer" no longer matches the operator who actually funded the withdrawal.

### Impact Explanation
This breaks the binding "the operator credited versus the party that paid" explicitly called out in the taxonomy. The honest operator who funded the withdrawal can end up unable to claim reimbursement (`validate_payer_is_operator` will reject them because the on-chain OP_RETURN no longer names them), while whoever wins the mempool race controls the attribution record. This maps to the Critical impact category "an honest operator permanently unable to be reimbursed" (the true funder loses attribution, and depending on the winning attacker's identity, no one — or the wrong entity — is left as the recorded payer for that kickoff/round). Note that actually consuming the false attribution to obtain reimbursement still additionally requires the winning party to run their own valid kickoff/round infrastructure as a registered operator, but the mere corruption of the payer record — deniable, unprivileged, and requiring no protocol role — is itself sufficient to strand the honest fronting operator.

### Likelihood Explanation
Exploitation requires only: (1) monitoring the Bitcoin mempool for the specific spend of a registered withdrawal UTXO, and (2) constructing and broadcasting a substitute transaction reusing the same signed input while only touching outputs 1/2 (which requires no key material, since Taproot key-path witnesses for `SIGHASH_SINGLE|ANYONECANPAY` remain valid across such a substitution). No verifier, operator, watchtower, or aggregator role is required to construct and broadcast this competing transaction, and no chain-of-custody signature from Citrea contract or user re-authorization is needed for the substitute output. The main friction is timing/fee-racing against the original broadcaster, which is a realistic real-world capability (higher feerate, replace-by-fee, or direct relay to miners).

### Recommendation
Change the withdrawal signature request to use `SIGHASH_ALL` (or otherwise cover all outputs, e.g. `SIGHASH_ALL|ANYONECANPAY` if additional flexibility on other inputs is still desired) so the OP_RETURN attribution output cannot be altered without invalidating the user's signature. If `SINGLE|ANYONECANPAY` is required for a specific compatibility reason, bind the operator attribution into a value that IS covered by the signature (e.g., make output 0 itself encode/commit the operator identity, or require the user to separately co-sign the operator attribution).

### Proof of Concept
1. Operator A obtains a valid user withdrawal signature (`SinglePlusAnyoneCanPay`) for UTXO `U`, and constructs `payout_tx_A` per `create_payout_txhandler`: input `U`, output0 = user payment, output1 = anchor, output2 = `OP_RETURN(A's xonly_pk)`. Operator A signs/promotes and broadcasts `payout_tx_A` to the Bitcoin mempool [2](#0-1) .
2. Attacker (no protocol role) observes `payout_tx_A` in the mempool, extracts input `U`, its witness (signature `sig`), and output0.
3. Attacker constructs `payout_tx_B`: same input `U` + `sig`, identical output0 (satisfying `SIGHASH_SINGLE` commitment), but output2 = `OP_RETURN(attacker-chosen xonly_pk)`. Signature verification succeeds unchanged because `SinglePlusAnyoneCanPay` never covered output2 [1](#0-0) .
4. Attacker broadcasts `payout_tx_B` with a higher fee / uses RBF to replace `payout_tx_A`, so `payout_tx_B` confirms instead.
5. When `PayoutCheckerTask`/`validate_payer_is_operator` later processes this withdrawal, the recorded payer no longer matches Operator A [5](#0-4) , so Operator A's `get_reimbursement_txs`/kickoff flow fails to attribute the payout to them, while Operator A already paid the user out of pocket.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// For a deposit_id checks that the payer for that deposit is the operator, and the payout blockhash and kickoff txid are set.
    async fn validate_payer_is_operator(
        &self,
        dbtx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
    ) -> Result<(BlockHash, Txid), BridgeError> {
        let (payer_xonly_pk, payout_blockhash, kickoff_txid) = self
            .db
            .get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id(dbtx, deposit_id)
            .await?;

        tracing::info!(
            "Payer xonly pk and kickoff txid found for the requested deposit, payer xonly pk: {:?}, kickoff txid: {:?}",
            payer_xonly_pk,
            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set
        let (payout_blockhash, kickoff_txid) = match (
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid,
        ) {
            (Some(payer_xonly_pk), Some(payout_blockhash), Some(kickoff_txid)) => {
                if payer_xonly_pk != self.signer.xonly_public_key {
                    return Err(eyre::eyre!(
                        "Payer is not own operator for deposit, payer xonly pk: {:?}, operator xonly pk: {:?}",
                        payer_xonly_pk,
                        self.signer.xonly_public_key
                    )
                    .into());
                }
                (payout_blockhash, kickoff_txid)
            }
            _ => {
                return Err(eyre::eyre!(
                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };

        tracing::info!(
            "Payer xonly pk, payout blockhash and kickoff txid found and valid for own operator for the requested deposit id: {}, payer xonly pk: {:?}, payout blockhash: {:?}, kickoff txid: {:?}",
            deposit_id,
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid
        );

        Ok((payout_blockhash, kickoff_txid))
    }
