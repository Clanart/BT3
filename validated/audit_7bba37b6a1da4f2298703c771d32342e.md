### Title
Webhook HMAC signature does not bind to `X-Shopify-Shop-Domain`/`X-Shopify-Topic` headers, permitting cross-shop webhook replay - ([File: lib/shopify_app/controller_concerns/payload_verification.rb](), [File: lib/shopify_app/controller_concerns/webhook_verification.rb]())

### Summary
This is the same root-cause pattern as the Permit2 report: an authorization credential (there, a Permit2 signature; here, the Shopify webhook HMAC) only commits to a subset of the data that determines the action actually taken, letting the credential be replayed for an unintended target. `ShopifyApp::PayloadVerification#hmac_valid?` computes the HMAC exclusively over `request.raw_post` [1](#0-0) , while the shop and topic that the app actually acts on are read straight from unsigned HTTP headers via `shop_domain` in `WebhookVerification` [2](#0-1) . Because the signature never covers `X-Shopify-Shop-Domain` or `X-Shopify-Topic`, anyone who legitimately receives one valid (body, HMAC) pair for their own store can resend the exact same body/signature with a forged shop-domain header and have it accepted as coming from a different, victim shop.

### Finding Description
`hmac_valid?` verifies only `OpenSSL::HMAC.digest(digest, secret, data)` against `data = request.raw_post`, using the single app-wide client secret shared across all merchants [1](#0-0) . `WebhookVerification#verify_request` calls this same check and, separately, exposes `shop_domain` purely from the `HTTP_X_SHOPIFY_SHOP_DOMAIN` header, with no cryptographic tie to the verified body [2](#0-1) . The default `WebhooksController#receive` forwards `request.headers` (including the unauthenticated shop-domain/topic) straight into `ShopifyAPI::Webhooks::Request`, which is what downstream jobs use to decide "which shop" the webhook is for [3](#0-2) . A concrete consumer of this is the generated `AppUninstalledJob`, which trusts the header-derived `shop_domain` param directly to look up and destroy the shop record: `shop = Shop.find_by(shopify_domain: shop_domain) ... shop.destroy` [4](#0-3) .

Because the app secret is identical for all installs of the app, an unrelated/anonymous attacker can:
1. Install the target app on their own (attacker-controlled) shop and trigger a webhook (e.g. uninstall the app to receive a genuine `app/uninstalled` webhook), capturing the exact raw body and its valid `X-Shopify-Hmac-Sha256` value.
2. Replay that identical body and HMAC to the app's webhook endpoint, but swap the `X-Shopify-Shop-Domain` header to point at a victim merchant's domain (and/or change `X-Shopify-Topic`).
3. `hmac_valid?` still returns true because it only checks the unchanged body against the shared secret; `verify_request` passes.
4. The processing pipeline (and any handler like `AppUninstalledJob`) acts using the attacker-forged `shop_domain`, e.g. destroying/uninstalling the victim shop's stored session or data.

### Impact Explanation
This allows an anonymous, unrelated party (anyone who can install the app on a free/dev store) to forge accepted, "verified" webhooks against any other merchant using the app, without ever compromising Shopify's servers or the app's secret. The concrete consequence via the generated `AppUninstalledJob` template is deletion of an arbitrary victim shop's `Shop` record (and, depending on `has_shopify_session`/session cascade, invalidation of that shop's stored access tokens), i.e. a cross-shop denial-of-service / data-loss primitive triggered purely by a forged HTTP request. Any other webhook-driven job that branches behavior based on `topic` or `shop_domain` (customer/shop redact jobs, custom webhook handlers) is equally exposed, since none of that routing data is authenticated.

### Likelihood Explanation
Likelihood is meaningful because it requires no privileged access: any actor can install the app themselves (installing a Shopify app on one's own store is the normal, unprivileged onboarding flow) to obtain one genuine (body, HMAC) pair, then simply replay it with modified headers to the app's shared webhook endpoint — no signature forgery or secret leak needed. The main constraint is that the replayed *body content* must be something the victim's job accepts as sensible for the header-declared topic; the `app/uninstalled` topic body is generally topic-body-format-independent enough that this is realistic for the shown generator template.

### Recommendation
Bind the parts of the request that determine *what action is taken* into the verified material, mirroring the Permit2 report's fix of using `permitWitnessTransferFrom` to scope the signature to the intended target/action:
- Include the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` header values (or, ideally, the shop/topic fields already embedded in the JSON body) as part of the HMAC-covered comparison in `hmac_valid?`/`verify_request`, rejecting any request where the header-declared shop/topic doesn't match what's cryptographically committed.
- At minimum, document (as Sablier did) that generated job templates such as `AppUninstalledJob` must not treat the unauthenticated `shop_domain` webhook parameter as authoritative without additional shop-existence/ownership checks, and recommend cross-checking the shop domain against data actually present in the signed body where the topic guarantees it (e.g. compare against `id`/domain fields inside the payload where available).

### Proof of Concept
1. Install the target Rails app (using this gem) on attacker-owned dev store `attacker.myshopify.com`; uninstall it to receive a real `app/uninstalled` webhook POST with a valid `X-Shopify-Hmac-Sha256` header computed over the raw body.
2. Capture the raw POST body `B` and header value `H = Base64(HMAC-SHA256(secret, B))`.
3. Send:
```
POST /webhooks HTTP/1.1
X-Shopify-Topic: app/uninstalled
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim.myshopify.com
Content-Type: application/json

B
```
4. `PayloadVerification#hmac_valid?` recomputes `HMAC(secret, B)` and finds it matches `H` (body unchanged) → request passes `verify_request` [1](#0-0) .
5. The controller forwards `victim.myshopify.com` as `shop` to the generated handler, which runs `Shop.find_by(shopify_domain: "victim.myshopify.com").destroy` [5](#0-4) , destroying the victim's shop record despite the attacker never having any relationship to that shop.

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```ruby
      data = request.raw_post
      unless hmac_valid?(data)
        ShopifyApp::Logger.debug("Webhook verification failed - HMAC invalid")
        head(:unauthorized)
      end
    end
```
