### Title
Permissionless `harvestSinglePool` allows flash-vote reward sniping / dilution of pending bribe yield in `BribeRewardPool` - ([File: wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager.harvestSinglePool` is unauthenticated and simply forces a bribe harvest via `wombatStaking.vote(_lps, 0, rewarders, address(0))`, which calls `queueNewRewards` on the pool's `BribeRewardPool`. Because reward accounting in `BaseRewardPoolV2`/`BribeRewardPool` distributes newly queued rewards to `rewardPerTokenStored` based on the **current** `totalStaked()`/`totalSupply` at the instant of harvest (not on time-weighted stake), an attacker can call `vote(pool, +X)` immediately before `harvestSinglePool([pool])` to inflate their share of the harvested bribe and then immediately `unvote(pool)` to withdraw, capturing yield accrued by other long-term voters.

### Finding Description
- `vote()` [1](#0-0)  calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta))` immediately, which (via the `updateRewards` modifier in `BaseRewardPoolV2`) first syncs the attacker's `userRewardPerTokenPaid` to the *current* `rewardPerTokenStored` (so the attacker owes nothing pre-harvest), then increases `totalSupply`/`_balances[msg.sender]` by `X` [2](#0-1) .
- `harvestSinglePool` is public/unprivileged and casts a zero-delta vote purely to trigger a bribe harvest: [3](#0-2) .
- This flows into `WombatStaking.vote`, which harvests the already-accrued bribe from the real Wombat `voter` contract and calls `queueNewRewards` on the rewarder with the harvested amount: [4](#0-3) .
- `queueNewRewards` → `_provisionReward` increases `rewardPerTokenStored` by `amount * 1e18 / totalStaked()`, where `totalStaked()` is read **at harvest time**, i.e. it includes the attacker's just-added `X`: [5](#0-4) .
- The attacker's `earned()` is `userShare * (rewardPerToken - userRewardPerTokenPaid)`, so with `userRewardPerTokenPaid` freshly synced to pre-harvest value and `userShare = X`, the attacker captures `X * increment` of the harvested bribe despite having staked votes for zero elapsed time [6](#0-5) .
- The harvested WOM/bribe amount itself is fixed by Wombat's real voter based on previously-cast vote weight (from `castVotes`), so it is not amplified by the attacker's local vlMGP re-vote — but the *distribution* of that fixed pot among `BribeRewardPool` stakers is diluted by the attacker's just-in-time stake, directly reducing the increment (and thus payout) that legitimate long-term voters accrue for the same harvest event.
- `claimBribe` → `_claimBribeFor` → `IBribeRewardPool.getReward` pays out the attacker's `userRewards` computed above [7](#0-6) .
- `unvote()` has no cooldown or minimum holding period and immediately calls `withdrawFor`, letting the attacker exit atomically: [8](#0-7) .

No modifier, `nonReentrant`, time-lock, or minimum-stake-duration check exists in `vote`, `harvestSinglePool`, `claimBribe`, or `unvote` to prevent this sequence from being executed atomically (single tx or same-block) by any vlMGP holder.

### Impact Explanation
This is a theft-of-unclaimed-yield vulnerability: an attacker with a vlMGP lock can insert a large `X` right before a permissionless harvest and extract a share of the pool's bribe reward proportional to `X`, diluting the `rewardPerTokenStored` increment that all pre-existing, long-term voters were entitled to for that harvest cycle, then withdraw their vote weight instantly. This matches the Immunefi "theft of unclaimed yield" impact class since the diluted reward increment is permanently lost to other voters (they cannot later reclaim the portion the attacker skimmed).

### Likelihood Explanation
- Preconditions: attacker only needs a vlMGP lock with unused votable capacity (`getUserVotable`), obtainable by locking MGP tokens purchased on the open market — no privileged role required.
- `harvestSinglePool` is explicitly designed to be callable by anyone ("this function has a lesser importance... hence no rewards will be given to the caller"), so the trigger step is always available.
- Repeatable every time a pool has unharvested bribes pending and the attacker can front-run/bundle `vote → harvestSinglePool → claimBribe → unvote` in the same block (feasible via a single contract call or MEV bundle).
- Profitability scales with the attacker's capital (`X`) relative to `totalStaked()` of that rewarder and the size of the pending bribe — larger, less-frequently-harvested pools are more attractive targets.

### Recommendation
Decouple reward eligibility from instantaneous balance snapshots at harvest time. Options:
- Require a minimum holding duration (e.g., accrue rewards only for votes held across at least one full epoch/cast cycle) before a voter's stake counts toward `queueNewRewards` distribution.
- Restrict `harvestSinglePool` to only be callable together with, or after, `castVotes` in the same epoch, and disallow `vote`/`unvote` in the same block as a harvest for the same pool (e.g., track `lastVoteBlock` per user and block same-block unvote/claim).
- Alternatively, snapshot `totalStaked()`/user balances used for `_provisionReward` from the state prior to the current block's vote changes (checkpoint-based accounting) rather than the live value at harvest time.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, `WombatStaking`, `BribeRewardPool`, mock `veWom`/`voter`/`bribe` contracts, and a mock vlMGP lock allowing two users: `longTermVoter` (votes `Y` at epoch start) and `attacker` (buys/locks vlMGP, votes 0 initially).
2. Simulate multiple blocks passing with `longTermVoter` holding their vote (no bribe harvested yet), while pending bribe `R` accrues in the mock Wombat `bribe` contract for the pool.
3. In a single test block: `attacker.vote([pool], [X])` with `X` comparable to or larger than `Y`; immediately call `bribeManager.harvestSinglePool([pool])`, causing the mock voter to release `R` into `BribeRewardPool` via `queueNewRewards`.
4. Assert `rewardPerTokenStored` increment equals `R * 1e18 / (Y + X)`.
5. Call `attacker.claimBribe([pool])` and assert `attackerPayout = X * increment > 0` and comparable in magnitude to `longTermVoter`'s pending `earned()` (`Y * increment`), despite `attacker` having zero prior stake duration.
6. Call `attacker.unvote(pool)` and confirm the attacker fully exits with `X` returned to votable capacity and the extracted `attackerPayout` retained.
7. Compare against a baseline run without the attacker's front-run vote and show `longTermVoter`'s realized reward is strictly lower in the attack scenario, quantifying the diverted yield.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
