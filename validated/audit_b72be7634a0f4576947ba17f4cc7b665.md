### Title
Unhandled `IndexError` in CLVM canonical-encoding check crashes spend-bundle validation - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()` / `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` parse the raw bytes of a spend bundle's `puzzle_reveal` and `solution` to check for canonical CLVM atom-length encoding, before any signature/CLVM cost validation happens. Like the OpenEXR `refill()` bug (CVE-2017-9114), these functions read a variable number of trailing length-prefix bytes without first checking that the buffer actually contains that many bytes, so a truncated/crafted atom header causes an out-of-bounds read.

### Finding Description
`is_atom_canonical()` decodes the CLVM atom length prefix based on the high bits of the first byte, then loops `prefix_len` times reading additional bytes via `atom_len |= clvm_buffer[offset]`: [1](#0-0) 
There is no bounds check on `offset` before each `clvm_buffer[offset]` access. If `clvm_buffer` ends exactly where a multi-byte length prefix begins (e.g., last byte is `0xE0` indicating a 2-byte prefix that is not actually present), the loop indexes past the end of the buffer.

This function is invoked from `is_clvm_canonical()`, which itself is called by `MempoolManager.validate_spend_bundle()` directly on attacker-supplied bytes for every incoming spend bundle: [2](#0-1) [3](#0-2) 

In Python, indexing a `bytes` object past its length raises `IndexError` rather than performing a silent OOB memory read like the C/C++ OpenEXR case — but the practical effect for an unhandled exception in this validation path is the same class of impact: the parsing step crashes instead of returning a controlled "not canonical" / rejection result.

### Impact Explanation
`validate_spend_bundle()` is called from `add_spend_bundle()`, which is the mempool transaction-admission authority reachable by any unprivileged node/peer or local wallet submitting a `SpendBundle`. I was not able to fully trace, within the available tool budget, whether every caller up the stack (`FullNode.add_transaction`, RPC `push_tx`, peer `new_transaction`/`respond_transaction` handlers) wraps this call in a broad try/except that would turn an `IndexError` into a graceful rejection instead of an unhandled exception. If such an unhandled exception propagates out of the per-transaction async task, it could halt processing of that spend bundle path (a spend-triggered transaction-processing disruption) rather than being cleanly rejected with `Err.INVALID_COIN_SOLUTION` like other malformed-CLVM cases. This is a crash/DoS-class bug (matching the OpenEXR CVE's own crash impact), not a fund-theft or consensus-fork bug — CVSS-Medium range is appropriate, consistent with the source CVE's severity.

### Likelihood Explanation
High feasibility to trigger: any unprivileged party can submit a `SpendBundle` with a `puzzle_reveal` or `solution` whose serialized bytes end mid-way through a multi-byte atom length prefix (e.g., a truncated `0xE0`, `0xF0`, `0xF8`, or `0xFC` header byte with insufficient trailing bytes). This requires no special privileges, signatures, or valid puzzle logic — the code path is hit before CLVM execution/cost accounting for canonical-form checking.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (and in `is_clvm_canonical()`'s main loop before `clvm_buffer[offset]`), returning "not canonical" / raising a caught `ValueError` instead of allowing `IndexError` to propagate. Confirm (and add if missing) that all call sites of `validate_spend_bundle()`/`add_spend_bundle()` reachable from peer/RPC/wallet input catch unexpected exceptions and convert them into a `MempoolInclusionStatus.FAILED` result rather than crashing the handling task.

### Proof of Concept
Construct a spend bundle whose `solution` (or `puzzle_reveal`) bytes are, e.g., `bytes.fromhex("e0")` — a single byte `0xE0` with no trailing length bytes. Passing this to `is_atom_canonical(buf, 0)` triggers:
```
b = 0xE0  → prefix_len = 2, mask = 0x0F
atom_len = 0
loop i=0: offset=1; atom_len |= clvm_buffer[1]  # IndexError: index out of range
```
Submitting a `CoinSpend` with such a `solution` via a `SpendBundle` reaches this code at `chia/full_node/mempool_manager.py:723-726` during `validate_spend_bundle()`. Whether this crashes the enclosing task or is caught upstream needs verification against the exact caller stack (`FullNode.add_transaction`, RPC push_tx endpoint), which could not be fully confirmed in this session.
