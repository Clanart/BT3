### Title
Single-implementation fail-open in Hookify enforcement hooks silently disables user deny rules on any error - ([File: plugins/hookify/hooks/pretooluse.py](), [plugins/hookify/hooks/posttooluse.py](), [plugins/hookify/hooks/stop.py]())

### Summary
The `hookify` plugin's `PreToolUse`, `PostToolUse`, and `Stop` enforcement hooks are each implemented by a single Python script with no redundancy, monitoring, or health-check mechanism. On any exception — including one triggered by an interface/schema change (e.g. `input_data`/`tool_input` shape changes, a Python-version incompatibility in `config_loader`/`rule_engine`, or an `ImportError`) — the script unconditionally emits only a `systemMessage` and `sys.exit(0)`, which Claude Code treats as "no decision" (allow). This is the direct analog of the reported bug: a single bot/enforcement path with no fallback, whose failure due to an interface change results in the protected action proceeding — except here there is no manual-review backstop, so the failure is silent and permissive rather than caught by a human process.

### Finding Description
`pretooluse.py` wraps its entire rule-evaluation logic in one `try/except Exception`, and in the `finally` block always calls `sys.exit(0)`: [1](#0-0) 

The same pattern exists for `PostToolUse` and `Stop`: [2](#0-1) [3](#0-2) 

There is no redundant enforcement path, no health monitoring of the hook, and no distinction between "no rules matched" (legitimately empty `{}`) and "the engine crashed" — both produce the same permissive JSON output shape, differing only in an easily-missed `systemMessage`. Because `RuleEngine.evaluate_rules` only returns a `deny`/`block` decision when it completes successfully and a blocking rule matches [4](#0-3) , any exception anywhere in the call chain (frontmatter parsing in `config_loader.py`, field extraction, or an upstream interface change to the hook's stdin JSON schema) causes the tool call, file edit, or agent stop to be approved by default rather than blocked.

This mirrors the reported bug class: a single implementation (the hookify script) is the sole enforcement point, has no monitoring for its own execution/health, and an interface change (e.g., Claude Code altering the `hook_event_name`/`tool_input` JSON contract, as changelog entries show has happened for permission-decision schemas) can silently break it. Unlike the liquidation bot case, where a human team caught and manually handled the failure, here the failure mode is fail-open and undetectable to the end user unless they specifically inspect the systemMessage transcript.

### Impact Explanation
A user who relies on `.claude/hookify.*.local.md` rules to block dangerous Bash commands, edits to sensitive files, or premature agent stops has no actual guarantee of enforcement: any bug, encoding issue, missing field, or upstream interface change silently disables all their configured `block` rules for that hook invocation, and the tool/agent proceeds as if no rule existed. This is a local trust-boundary compromise for command approval and hook-based guardrails — the same class as `deny` rules being bypassed, which the project itself treats as security-relevant (see changelog: `deny: ["mcp__servername"]` bypass fixes, PreToolUse `allow` overriding `deny` fixes) [5](#0-4) .

### Likelihood Explanation
Low-to-moderate. This requires either a bug/exception in `config_loader.py`/`rule_engine.py` (e.g., malformed rule files, unexpected field types) or an upstream interface change to the hook stdin contract. The extensive `except (IOError, OSError, PermissionError)`, `except (ValueError, KeyError, AttributeError, TypeError)`, and catch-all `except Exception` blocks in `config_loader.py` show the authors are already aware errors are common enough to need broad handling [6](#0-5) , but they chose "continue silently" over "fail closed."

### Recommendation
1. Distinguish an "error occurred" outcome from a "no rules matched" outcome in the hook's JSON output, and fail closed (`permissionDecision: "ask"` or `"deny"`) for `PreToolUse`/`PostToolUse` when rule loading or evaluation raises, rather than defaulting to allow.
2. Surface hook execution failures prominently (not just a transcript `systemMessage`) so users notice their enforcement rules stopped working.
3. Add a self-test/health-check invoked at `SessionStart` to validate that `hookify.core` imports and a minimal rule loads/evaluates correctly, alerting the user if not.
4. Add test coverage specifically for interface/schema changes to the hook stdin contract (missing fields, renamed fields, type changes) to ensure the failure mode is exercised and remains fail-closed.

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md` with a `block` rule matching `rm -rf` on Bash commands.
2. Cause `load_rule_file`/`extract_frontmatter` to raise an uncaught-type exception not covered by the existing catch clauses (e.g., patch/monkeypatch `hookify.core.config_loader` to raise inside `Rule.from_dict`, or trigger via a malformed frontmatter value causing an `AttributeError` inside `_check_condition`'s `str`/`startswith` calls when a non-string field slips through — e.g. a `tool_input` value that is a list, which `_extract_field` returns via `str(value)` for the top branch but may bypass expected typing in downstream diff branches).
3. Observe that `pretooluse.py`'s outer `try/except Exception` catches it, prints `{"systemMessage": "Hookify error: ..."}`, and exits 0.
4. Run the blocked Bash command (`rm -rf /tmp/test`) — it executes without being denied, because no `hookSpecificOutput.permissionDecision: deny` was ever emitted.
