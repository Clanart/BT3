### Title
Fee/weight calculation omits the OP_RETURN data output, underpaying the intended fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an `OP_RETURN` output carrying caller-supplied `data` into the transaction, but `calculate_weight_vbytes` — the function used to derive `needed_fee` — builds its weight-estimation transaction from `payments` and `change` only, never including the data output. The fee base therefore excludes part of the transaction that is actually signed and broadcast: an asymmetric/incorrect fee base analogous to charging fees on one component while exempting another. The result is that the real fee rate is always lower than `fee_per_vbyte`, and with a large `data` payload the actual fee can fall below the minimum relay fee even though the `TooLowFee` check passed.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

1. The data output is appended to `tx_outs` before the weight calculation:

```rust
// send.rs:193-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data).expect("..."),
    ),
  })
}
```

2. The weight/vbytes used for the fee are computed by `calculate_weight_vbytes(tx_ins.len(), payments, None)` (send.rs:204). Inside that function (send.rs:62-99), the estimation transaction's `output` field is built solely from `payments` plus the optional `change` — there is no parameter and no code path for a data output.

3. The same omission occurs in the change branch: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (send.rs:225-226) again ignores the OP_RETURN output that already sits in `tx_outs`.

4. `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) and the minimum-relay-fee guard (send.rs:211) are both computed against this underestimated vsize. The change output amount is then derived as `input_sat - (payment_sat + fee_with_change)` (send.rs:228), so the shortfall is silently absorbed into change: the transaction signs with a lower actual fee than the caller requested — `self.fee()` (send.rs:138-141) will report less than `fee_per_vbyte * actual_vsize`.

With the maximum allowed 80-byte `data` payload (checked at send.rs:171), the real transaction carries an extra output of roughly 9 + 1 + 80 bytes (~90 weight units beyond the accounted size), so the actual fee rate is meaningfully below the requested one, and the check `needed_fee >= DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` is evaluated against the smaller vsize rather than the true one.

### Impact Explanation
A `SignableTransaction` produced with `data = Some(...)` pays strictly less fee than `fee_per_vbyte` specifies, and `needed_fee()` returns an understated value to any caller (e.g., the processor's `needed_fee`/`amortize` flow). In edge cases — `fee_per_vbyte` near the relay minimum plus a near-maximal `data` payload — the broadcast transaction's real fee rate can drop below the default minimum relay fee, producing a signed transaction that relays reject or that stalls in mempools. This is an incorrect fee-accounting formula: funds end up distributed differently than the caller's parameters dictate (excess lands in change or is underpaid to miners), which is precisely the "fee charged on the wrong base" bug class.

### Likelihood Explanation
Triggering requires the caller of `SignableTransaction::new` to supply `data`. The in-repo processor passes `None` (`processor/src/networks/bitcoin.rs:446-452`), so the flawed path is only exercised by library consumers who attach metadata. When it is exercised, the miscalculation is deterministic — every data-bearing transaction underpays — and needs no adversarial cooperation beyond supplying the `data` argument to a public API.

### Recommendation
Include the data output in the weight/vsize estimate. Either pass the fully-built `tx_outs` (or at least the `data` length) into `calculate_weight_vbytes`, e.g.:

```rust
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs_without_change, None);
```

where the payment slice already contains the OP_RETURN output, or add an explicit `data_len: usize` parameter that constructs the OP_RETURN output inside the estimation transaction. The minimum-fee check at send.rs:211 and the change-value subtraction at send.rs:228 must then operate on the true transaction size.

### Proof of Concept
```rust
// Conceptual: construct with a maximal data payload
let data = Some(vec![0u8; 80]);
let st = SignableTransaction::new(
  vec![input],          // one ReceivedOutput
  &[(payment_script, 10_000)],
  Some(change_script),
  data,
  1,                    // 1 sat/vbyte requested
).unwrap();

// The signed transaction contains an extra ~90-byte OP_RETURN output
// that calculate_weight_vbytes never accounted for.
let actual_vsize = st.transaction().vsize() as u64;
let actual_fee = st.fee();
// actual_fee / actual_vsize < 1 sat/vbyte — underpaid relative to request,
// and may fall below DEFAULT_MIN_RELAY_TX_FEE * actual_vsize / 1000
// despite the TooLowFee check having passed.
```

Since `st.fee()` equals `sum(prevouts) - sum(outputs)` and `sum(outputs)` includes the un-accounted-for OP_RETURN output (value 0) plus change sized using the underestimated `fee_with_change`, the effective fee rate is provably lower than `fee_per_vbyte` whenever `data.is_some()`.
