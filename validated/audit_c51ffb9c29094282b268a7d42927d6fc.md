Based on my research, I found a valid analog in the BPF Loader v3 (upgradeable loader)'s `ExtendProgram` instruction path, which is reachable by any unprivileged user and mirrors the "grief a shared resource's warm-up window for negligible cost" pattern from the Yieldy report.

### Title
Permissionless `ExtendProgram` lets any unprivileged account reset a program's deployment slot, re-triggering `DelayVisibility` and DoS'ing the program for the delay window - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
`common_extend_program()` is invoked for the permissionless `UpgradeableLoaderInstruction::ExtendProgram` variant with `check_authority = false` [1](#0-0) . This function never validates that the caller is the program's upgrade authority when `check_authority` is `false`, and only requires a payer signature if a nonzero rent top-up is actually needed [2](#0-1) . Any account can call it with `additional_bytes = 1` (or the SIMD-0431 minimum) against any upgradeable program's `ProgramData` account, and — as long as that account already holds enough lamports for the new rent-exempt minimum — no signature is required at all.

### Finding Description
Every successful `ExtendProgram` call unconditionally invokes `deploy_program!` and rewrites the `ProgramData` account's `slot` field to the current `clock_slot` [3](#0-2) . This is the exact same code path used for real upgrades, and it resets the program's `deployment_slot` in the `ProgramCache`. Because `effective_slot()` for `Loaded`/`Unloaded` entries is `deployment_slot + DELAY_VISIBILITY_SLOT_OFFSET` [4](#0-3) , any transaction that invokes the program during that offset window will hit `is_implicit_delay_visibility_tombstone()` and get back a `DelayVisibility` tombstone instead of the real program entry [5](#0-4) [6](#0-5) .

This is structurally identical to the referenced Yieldy bug: `stake()` let anyone push back `_recipient`'s `warmUpInfo.expiry` for as little as 1 wei by depositing on their behalf. Here, `ExtendProgram` lets anyone push back a program's `effective_slot` (its "unlock"/visibility point) by "extending" it by 1 byte, at negligible/zero cost, without needing the upgrade authority's permission or signature.

### Impact Explanation
Any transaction that calls the targeted program (directly or via CPI) during the `DELAY_VISIBILITY_SLOT_OFFSET`-slot window will fail with an `UnsupportedProgramId`/tombstone-type error instead of executing, since the cache returns a `DelayVisibility` entry rather than the loaded program [7](#0-6) . An attacker can repeat this every time the window elapses (each call itself doesn't reset until it can be called again — the code blocks a second extend in the *same* slot only: "Program was extended in this block already" [8](#0-7) ), so this can be turned into a rolling, near-permanent denial of service against any target upgradeable program (excluding those with 0 upgrade authority, since `upgrade_authority_address.is_none()` is rejected [9](#0-8) ). This breaks availability of arbitrary on-chain programs for all their users, at attacker cost approaching zero (only the cost of one transaction fee per repetition, no rent payment needed once the account is rent-exempt).

### Likelihood Explanation
High. `ExtendProgram` is a documented, intentionally-permissionless instruction (any account may pay to extend program size), but the code fails to separate "permissionless funding" from "re-triggering deployment/visibility reset." No privileged role, validator behavior, or unusual conditions are needed — a single unprivileged actor with a funded fee payer can trigger this against any target program that is still upgradeable, repeatedly, from a single wallet with a simple script, closely matching the "negligible cost, perpetual grievance" characterization the original finding's judge gave the Yieldy issue.

### Recommendation
Do not run the full `deploy_program!`/redeployment path (which resets `deployment_slot`/visibility) on every `ExtendProgram` call. Only reset `deployment_slot` when the actual byte content of the program image changes (i.e., real upgrades), or gate `ExtendProgram`'s deploy/verify step so it does not touch `ProgramCache` visibility when it is a pure realloc with no authority-signed content change. Alternatively, require that `ExtendProgram` be restricted so it cannot be invoked by non-authority parties when doing so would reset deployment/visibility state, decoupling the "pay for extra space" permissionless feature from the caching/visibility side effects of `deploy_program!`.

### Proof of Concept
1. Deploy an upgradeable program `P` with `ProgramData` account funded above the rent-exempt minimum needed for `len + 1`.
2. From any unprivileged wallet (no authority, no signature needed beyond the transaction itself), submit `extend_program(&P, None, 1)` (or the SIMD-0431 minimum bytes) as `ExtendProgram` (not `ExtendProgramChecked`) — this hits `common_extend_program(.., check_authority=false)` [1](#0-0) .
3. Since `programdata_account` already has sufficient lamports, `required_payment == 0`, so `native_invoke_signed` (and thus any payer signature check) is skipped entirely [10](#0-9) .
4. `deploy_program!` runs and sets `ProgramData.slot = clock_slot` (current slot) [3](#0-2) , resetting `deployment_slot` in the cache entry, so `effective_slot()` becomes `clock_slot + DELAY_VISIBILITY_SLOT_OFFSET`.
5. Any transaction invoking program `P` in the intervening slots receives a `DelayVisibility` tombstone from `ProgramCache`/`ProgramCacheForTxBatch::find()` [11](#0-10) , causing those transactions to fail even though nothing about `P`'s actual code changed.
6. Repeat once per elapsed window (once outside the "same block" restriction) to keep `P` perpetually unusable.

**Uncertainty note:** I was not able to fully trace the exact downstream error surfaced to callers of a program in `DelayVisibility` state (e.g., whether it always manifests as `InstructionError::UnsupportedProgramId` to the calling transaction) due to index/context limits on `invoke_context.rs`. I recommend verifying this precise error path and the exact numeric value of `DELAY_VISIBILITY_SLOT_OFFSET` in a full checkout before treating this as fully confirmed.
