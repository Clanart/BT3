### Title
Off-by-one line-selection desync after diff hunk expansion causes wrong lines to be silently included/excluded from commits - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
`mergeDiffHunks` merges two adjacent hunks by dropping both original hunk-header lines and inserting a single new one, but reuses `hunk1.unifiedDiffStart` as the base offset for the merged hunk. This causes the absolute line indices used to key the user's persisted `DiffSelection` (partial-commit selection) to become misaligned for every line that originated in the second hunk.

### Finding Description
`DiffSelection` is an index-keyed selection state: it tracks a `Set<number>` of line indices whose selection diverges from the default (all-selected or none-selected) state [1](#0-0) , and `isSelected(lineIndex)` is later re-queried against freshly computed absolute indices [2](#0-1) .

`formatPatch` computes those absolute indices dynamically from the *current* diff hunk layout: `const absoluteIndex = hunk.unifiedDiffStart + lineIndex` [3](#0-2) . This means the meaning of a given index number is entirely dependent on how hunks are currently laid out — it is not a stable identifier tied to a specific file line.

When the user expands a hunk's context (a normal, encouraged workflow before committing) and the gap to the adjacent hunk is short enough, `expandTextDiffHunk` merges the two hunks via `mergeDiffHunks`: [4](#0-3) 

The merged hunk strips the first line (header) from *both* hunks and inserts exactly one new header line, but keeps the merged hunk's `unifiedDiffStart` equal to `hunk1.unifiedDiffStart`. Working through the arithmetic: before merging, a line at position `lineIndexInHunk2` inside hunk2 has absolute index `hunk1.unifiedDiffStart + hunk1.lines.length + lineIndexInHunk2` (since `hunk2.unifiedDiffStart = hunk1.unifiedDiffEnd + 1`). After merging, that same line sits at absolute index `hunk1.unifiedDiffStart + hunk1.lines.length - 1 + lineIndexInHunk2` — exactly one less than before. Every line that came from the second (or any subsequently merged) hunk is now off by one relative to the indices recorded in the user's existing `DiffSelection`.

Because `DiffSelection` has no notion of "this index refers to file line N" — it is purely a positional index into the current hunk layout — this reindexing is silent and undetected. There is no code path that re-maps or invalidates existing selection indices when hunks are merged during expansion; the `withSelectableLines` method only filters out lines no longer selectable, it does not shift indices [5](#0-4) .

### Impact Explanation
If a user has made a partial selection (staged only some added/removed lines for commit — a first-class Desktop feature) and then expands hunk context in a way that triggers a merge (`DiffHunkExpansionType.Short`, computed in `getHunkHeaderExpansionType` [6](#0-5) ), the line that ends up selected/deselected in `formatPatch` will be the line *adjacent* to the one the user actually intended, off by one position. This directly matches the "silent corruption of what the user commits or pushes" impact class: the generated patch (via `formatPatch`) will stage a different line than the user visually selected in the UI, with no error or warning, and the resulting commit will silently include or exclude the wrong change. A malicious repository maintainer/contributor can deliberately craft commits with two changed regions separated by a gap just under `DefaultDiffExpansionStep` (20 lines) so that any reviewer who expands context and partially selects lines to stage is affected by this desync, potentially causing them to commit/push content they never intended to include (e.g., silently re-including an unwanted line, or silently dropping a line they meant to keep).

### Likelihood Explanation
This requires no special privileges from the attacker beyond controlling the content/shape of a repository's diff (achievable by any contributor or by crafting a PR/branch), and requires only a normal, expected user action (expanding diff context before doing a partial/line-level commit) — a workflow explicitly supported and encouraged by the "Expand Whole File" UI feature [7](#0-6) . No abnormal or unnatural steps are required.

### Recommendation
Do not reuse positional (hunk-relative) indices as a stable key for `DiffSelection` across diff-mutation operations like hunk expansion/merging. Either: (1) re-map the `divergingLines` set explicitly during `mergeDiffHunks`/`expandTextDiffHunk` by tracking the old-to-new absolute index shift for every original line that survives the merge, or (2) key `DiffSelection` by a stable per-file line identifier (e.g., old/new line number pairs already tracked on `DiffLine`) instead of an index that is invalidated whenever hunks are resegmented.

### Proof of Concept
1. Produce a diff with two hunks separated by fewer than `DefaultDiffExpansionStep` (20) unchanged lines (as in the existing test `merges hunks when the gap between them is shorter than the expansion size` [8](#0-7) ).
2. In the UI, select only specific individual lines belonging to the second hunk for the commit (`DiffSelection.withLineSelection`), leaving other lines in that hunk unselected.
3. Expand the first hunk downward (or the second hunk upward) so that `shouldMergeWithAdjacent` becomes true and `mergeDiffHunks` runs, shrinking every subsequent line's absolute index by one.
4. Call `formatPatch` on the resulting `WorkingDirectoryFileChange`/`ITextDiff` [9](#0-8)  — the generated patch will include/exclude the line adjacent to the one originally selected, rather than the one the user selected before expansion, silently committing the wrong content.

**Note on verification confidence:** I traced the index-shift math directly from the merge/expansion code and the `formatPatch`/`DiffSelection` index usage, and it is internally consistent, but I did not have the ability to run the actual test suite or a live app to observe the UI end-to-end (e.g., whether some higher-level component in `app-store.ts` or `side-by-side-diff.tsx` re-derives/clears selection on every diff update, which could mask this in practice). I was unable to fully inspect `app/src/ui/diff/side-by-side-diff.tsx`'s selection-handling code path in this session due to running out of search iterations, so I cannot rule out an unseen mitigation there with full certainty.

export function getHunkHeaderExpansionType(
  hunkIndex: number,
  hunkHeader: DiffHunkHeader,
  previousHunk: DiffHunk | null
): DiffHunkExpansionType {
  const distanceToPrevious =
    previousHunk === null
      ? Infinity
      : hunkHeader.oldStartLine -
        previousHunk.header.oldStartLine -
        previousHunk.header.oldLineCount

  // In order to simplify the whole logic around expansion, only the hunk at the
  // top can be expanded up exclusively, and only the hunk at the bottom (the
  // dummy one, see getTextDiffWithBottomDummyHunk) can be expanded down
  // exclusively.
  // The rest of the hunks can be expanded both ways, except those which are too
  // short and therefore the direction of expansion doesn't matter.
  if (hunkIndex === 0) {
    // The top hunk can only be expanded if there is content above it
    if (hunkHeader.oldStartLine > 1 && hunkHeader.newStartLine > 1) {
      return DiffHunkExpansionType.Up
    } else {
      return DiffHunkExpansionType.None
    }
  } else if (distanceToPrevious <= DefaultDiffExpansionStep) {
    return DiffHunkExpansionType.Short
  } else {
    return DiffHunkExpansionType.Both
  }
}
