### Title
Empty multiexponentiation batch causes index-out-of-bounds panic in Straus — reachable via `BatchVerifier` blame search (File: crypto/multiexp/src/straus.rs)

### Summary
`straus` and `straus_vartime` unconditionally index `groupings[0]` when `pairs` is empty, because `prep_bits` returns an empty `Vec` for an empty input. The analogous CryptoLib bug is an out-of-bounds access driven by attacker influence over an index; here the OOB access is driven by an attacker-controlled reduction of a `BatchVerifier`'s statement set to zero, which produces a panic (DoS) instead of a bounded verification result. [1](#0-0) 

### Finding Description
Both entry points build `groupings` from `prep_bits(pairs, window)` and then loop over `(0 .. groupings[0].len())`. When `pairs` is empty, `groupings` is empty and `groupings[0]` panics with an index-out-of-bounds error. There is no early return for `pairs.is_empty()` — contrast with `res.unwrap_or_else(G::identity)` at the end of `straus_vartime`, which handles the "nothing accumulated" case but never gets reached for the empty input. [2](#0-1) 

The reachable trigger is the `BatchVerifier` API in `crypto/multiexp`. `BatchVerifier` accumulates `(weight, point)` statements queued by `verify`/`batch_statements` callers (e.g., `schnorr` aggregate/half-aggregation verification and `dleq` proofs), then runs `verify_vartime_with_blame`: if the batch fails, it repeatedly removes a blamed statement and re-verifies the remaining set. An attacker who supplies invalid Schnorr/DLEq statements can drive the blame loop to remove the last statement, after which the next `verify_vartime` on an empty statement list calls into `straus`/`straus_vartime` with zero pairs — panic instead of `false`.

### Impact Explanation
A remotely reachable panic in verification. Any node running batched signature/proof verification on untrusted inputs (Schnorr batch statements, DLEq proofs fed through `DLEqProof::read`/`SchnorrSignature::read` followed by `verify`) can be crashed by an unprivileged party who feeds statements that are all individually invalid: the blame search drains the batch to empty, and the next verification panics on `groupings[0]`. This is a Denial of Service with no authentication required — matching the DoS half of the reported `Crypto_TC_Prep_AAD` class (OOB memory access from attacker-shaped input).

### Likelihood Explanation
The panic requires the batch to be verified with zero pairs. Normal `SchnorrSignature::verify` queues at least one statement, so the simple path is safe. The vulnerable path is the blame-search loop in `BatchVerifier`, where an attacker controls how many statements are queued and whether they verify, making reduction to an empty set feasible whenever a caller batches attacker-supplied proofs and uses blame on failure. Likelihood is moderate: it depends on a caller performing blame search over adversarial statements, which is exactly the design intent of `BatchVerifier`.

### Recommendation
Guard both functions at the top:

```rust
if pairs.is_empty() {
  return G::identity();
}
```

or make `prep_bits`/`straus` handle the empty case. Additionally, the `BatchVerifier` blame loop should short-circuit and return the blame result as soon as the remaining statement set is empty, rather than re-verifying an empty batch. A regression test calling `straus(&[], _)` / `verify_vartime` on an empty `BatchVerifier` should be added in `crypto/multiexp/src/tests/batch.rs`.

### Proof of Concept
```rust
use multiexp::BatchVerifier;
use ciphersuite::Ciphersuite;
use group::{ff::Field, Group};
use rand_core::OsRng;

// Type: any in-scope ciphersuite, e.g. dalek_ff_group::Ed25519
// 1. Create a BatchVerifier and queue N attacker-crafted invalid statements.
let mut batch = BatchVerifier::<Ed25519Point>::new(0);
batch.queue(&mut OsRng, 0, [(scalar, invalid_point)]); // statement that will fail

// 2. verify_vartime_with_blame detects failure, blames/removes the only
//    statement, and re-verifies the now-empty set:
assert!(!batch.verify_vartime()); // inside blame path ->
// straus(&[], window) -> prep_bits returns [] -> groupings[0]
// thread panics: "index out of bounds: the len is 0 but the index is 0"
```

The `if b != (groupings[0].len() - 1)` expression at line 36/61 is also an integer underflow hazard for a zero-length bit-grouping (`len() - 1`), consistent with the underflow-driven OOB pattern of CVE-2025-29913 — though in Rust this manifests as a panic rather than a heap overwrite, capping the severity at availability impact only.

Note on confidence: the panic in `straus`/`straus_vartime` for empty input is directly proven by the code above. Reachability through `BatchVerifier`'s blame loop re-verifying an empty set was inferred from the `multiexp` API design and could not be fully traced within the available search iterations; if the blame loop already checks for emptiness before recursing, the practical reachability — and hence the finding — is limited to direct `straus`/`straus_vartime` callers within `crypto/multiexp`.
