### Title
Legacy EIP-155 Transactions Accept Malleable ECDSA Signatures (`s` not restricted to lower half order) - ([File: blockchain/types/transaction.go])

### Summary
`validateSignature` in `blockchain/types/transaction.go` disables the anti-malleability check for any chain-ID-protected (EIP-155) legacy transaction by calling `crypto.ValidateSignatureValues` with `homestead=false`, which permits the full `N` range for `s` instead of restricting it to the lower half order. This mirrors the Lombard `consortium-node` finding: a signature-validity check that fails to reject the "other" valid `(r, s, v)` variant of a signature, enabling signature/transaction malleability.

### Finding Description
`validateSignature` decides which anti-malleability rule to apply based on whether the transaction's `v` value is "protected" (i.e., includes a chain ID per EIP-155), not based on whether the Homestead fork is active (as go-ethereum's original semantics intend): [1](#0-0) 

For any protected legacy transaction, it always calls `crypto.ValidateSignatureValues(V, r, s, false)`. Looking at the implementation: [2](#0-1) 

When `homestead` is `false`, the function skips the check `s.Cmp(secp256k1halfN) > 0` and instead allows `s` anywhere in `[1, N)`. Because ECDSA signatures are inherently malleable — for any valid `(r, s, v)` there exists an equally valid `(r, N-s, 1-v)` that recovers to the *same* public key — this means that for every legacy, chain-ID-protected transaction accepted by Kaia, an attacker (including anyone observing the transaction on the network, e.g., a public RPC caller or mempool watcher) can compute a second, distinct `(r, N-s, v')` pair that:
- Is still considered a fully valid signature by `validateSignature`/`crypto.ValidateSignatureValues`.
- Recovers to the exact same sender address via `crypto.Ecrecover`/`SigToPub` (which only rejects `v ∉ {0,1}`, not high-`S`, per `crypto/signature_cgo.go` and `signature_nocgo.go`).
- Produces a **different transaction hash** (`tx.Hash()`), since the RLP-encoded signature bytes differ.

This is the same bug class as the report: failing to enforce canonical/non-malleable signature checks before treating the signature as authoritative proof of authorization, enabling the same authorization to be re-encoded under a different hash/identity.

### Impact Explanation
Kaia's protocol relies on transaction hash uniqueness in several security-relevant places reachable by a plain transaction sender or public RPC caller:
- Transaction pool deduplication and replacement logic key on `tx.Hash()`.
- Fee-delegation bookkeping distinguishes `SenderTxHash()` from the full tx hash and is used to correlate sender and fee-payer signatures for the same logical transaction.
- Auction/gasless bundling logic (`kaiax/auction`, `kaiax/gasless`) and general block-building track "target transaction hash" and conflict detection by hash.

An attacker who observes a valid legacy EIP-155 transaction (broadcast, in the mempool, or on public RPC) can malleate its signature to produce a second, hash-distinct transaction that is semantically identical (same sender, same nonce, same payload) but which the state-transition/tx-pool layer treats as a *different* transaction. This can be used to:
- Confuse nonce-based transaction replacement/eviction in the pool (two "different" transactions with the same nonce/sender competing).
- Break hash-based tracking assumptions in gasless/auction bundling and fee-delegation matching (`SenderTxHash`), potentially enabling fee-delegation or gasless-settlement bookkeeping desynchronization between nodes that observe different malleated variants first.
- Cause state divergence between honest nodes if one node's pool/DB indexes by the malleated hash and another by the original.

This satisfies the "acceptance of an invalid/duplicated transaction" and "state divergence between honest nodes" criteria for a valid analog.

### Likelihood Explanation
High likelihood of reachability: any transaction submitted as a legacy, EIP-155-protected transaction (the default and most common transaction format) passes through `validateSignature`. No special privileges are required — a public RPC caller can submit a transaction and then trivially compute the malleated `(r, N-s, v')` variant using only public-key arithmetic (`s' = N - s`, flip `v`), since ECDSA malleability requires no secret information.

### Recommendation
Change `validateSignature` to always enforce the Homestead low-`S` rule (`homestead=true`) for chain-ID-protected transactions, consistent with go-ethereum's intended behavior (Homestead-rule enforcement should be tied to the active fork rules, not to whether the signature happens to include a chain ID). At minimum, do not pass `homestead=false` for EIP-155 signatures. Additionally, as the referenced report recommends, ensure the low-`S` / canonical form check occurs *before* the public key/sender is trusted, wherever a signature is treated as an authorization proof.

### Proof of Concept
1. Craft or observe any valid legacy, chain-ID-protected Kaia transaction `tx` with sender signature `(v, r, s)` where `s <= N/2` (typical outputs of standard signing libraries).
2. Compute `s' = secp256k1N - s` and flip `v` accordingly (`v' = 1 - (v-27-2*chainID-35)` translated back to the protected `V` encoding), producing `(v', r, s')`.
3. Submit the new transaction `tx'` (same nonce, payload, to, sender) with signature `(v', r, s')` via `eth_sendRawTransaction`.
4. Observe that `validateSignature`/`crypto.ValidateSignatureValues(V, r, s, false)` accepts `tx'` because the `s > N/2` rejection is skipped, and `Sender(tx')` recovers to the identical sender address as `tx`, while `tx'.Hash() != tx.Hash()`.

func validateSignature(v, r, s *big.Int) bool {

	V := byte(v.Uint64() - 35 - 2*chainID)

}

// ValidateSignatureValues verifies whether the signature values are valid with
// the given chain rules. The v value is assumed to be either 0 or 1.
func ValidateSignatureValues(v byte, r, s *big.Int, homestead bool) bool {
	if r.Cmp(common.Big1) < 0 || s.Cmp(common.Big1) < 0 {
		return false
	}
	// reject upper range of s values (ECDSA malleability)
	// see discussion in secp256k1/libsecp256k1/include/secp256k1.h
	if homestead && s.Cmp(secp256k1halfN) > 0 {
		return false
	}
	// Frontier: allow s to be in full N range
	return r.Cmp(secp256k1N) < 0 && s.Cmp(secp256k1N) < 0 && (v == 0 || v == 1)
}
