### Title
Unregistered-state-machine identity fallback in `IntentGatewayV2.instance()` lets a forged remote module drain escrowed orders - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` resolves peer-gateway identity with a fallback that returns `address(this)` for any state machine that has never been registered via `NewDeployment`, instead of reverting like the mainline EVM implementation does. Because `IntentGatewayV2` is deployed deterministically (CREATE2, identical bytecode/address across EVM chains — documented explicitly in the mainline `initialize()` comment), an attacker who deploys a lookalike contract at that same address on *any* Hyperbridge-supported-but-unregistered EVM chain can dispatch a forged `RedeemEscrow`/`RefundEscrow` request that `authenticate()` will accept as legitimate, since `module == instance(unregistered_source) == address(this)`.

### Finding Description
`instance()` in the Tron contract: [2](#0-1) 
returns `address(this)` whenever `_instances[keccak256(stateMachineId)]` is unset (i.e., the source chain was never registered), and `authenticate()` accepts the request whenever `module == instance(request.source)`.

Compare this to the mainline EVM `IntentsBase._instance` used by `ExtrinsicIntents._authenticate`: [3](#0-2) 
which explicitly reverts with `UnknownInstance` for any chain not registered — confirmed by the test `testInstance`: [4](#0-3) 

The comment in the mainline `initialize()` makes the deterministic-address design explicit: [5](#0-4) 
"registers the initial cross-chain peers, each bound to `address(this)` ... identical across chains under deterministic CREATE2."

Because every legitimate `IntentGatewayV2` deployment shares the same address, the Tron fallback effectively treats *any unregistered chain* as if it had a peer gateway at that very address. An attacker only needs to get a `PostRequest` accepted by the Tron host with `source` set to a state machine ID that (a) Hyperbridge has a working consensus/state-proof client for, but (b) the Tron `IntentGatewayV2` has never explicitly registered via `NewDeployment`, and with `from` set to the shared deterministic address. This can be satisfied by deploying an attacker-controlled contract at that exact address on such a chain (or reusing any already-deployed unrelated contract that happens to sit at that address) and dispatching an ISMP request from it — no relayer, prover, or admin compromise is required; the state proof for that message is completely genuine.

`onAccept` then decodes the attacker-supplied `WithdrawalRequest` body directly into `withdraw()`: [1](#0-0) [6](#0-5) 
which transfers whatever tokens are escrowed under `body.commitment` to `body.beneficiary` — fully attacker-chosen — as long as any order commitment with a nonzero escrow balance for the specified token exists (the attacker doesn't even need to know the real commitment in advance; they can enumerate live orders and target their escrow).

### Impact Explanation
This is unauthorized execution / false module-identity acceptance leading to direct theft of escrowed bridge funds: an unprivileged attacker can redirect any live order's escrowed `_orders[commitment][token]` balance to an address they control, or trigger premature refunds, purely by controlling a contract on an unregistered chain and getting a legitimate (unforged) ISMP message relayed. This falls squarely within the bounty's "stealing or loss of funds," "unauthorized transaction or execution," and "wrong module bindings" categories.

### Likelihood Explanation
Likelihood is high wherever this Tron gateway is deployed and used for cross-chain orders with peers on chains it has not explicitly whitelisted via `NewDeployment`. The only precondition is the existence of at least one Hyperbridge-supported chain that the Tron gateway hasn't registered as a peer — a very plausible state at any point before/between governance-driven `NewDeployment` registrations, or for any long tail of supported chains that were never intended as peers of this particular deployment.

### Recommendation
Change `instance()` to mirror `IntentsBase._instance`/`_instance` semantics: revert (e.g. with `UnknownInstance`/`Unauthorized`) when `_instances[keccak256(stateMachineId)] == address(0)` instead of falling back to `address(this)`. `authenticate()` should never treat an unregistered source chain as implicitly trusted.

### Proof of Concept
1. Identify a state machine ID `X` supported by Hyperbridge (valid consensus/state proof client exists) but never registered in the Tron gateway's `_instances` mapping (no prior `NewDeployment` for `X`).
2. On chain `X`, deploy (or locate) a contract at the address that matches the Tron `IntentGatewayV2`'s deterministic deployment address, and have it dispatch an ISMP `PostRequest` with `dest` = Tron chain, `to` = Tron `IntentGatewayV2` address, and body = `bytes1(RequestKind.RedeemEscrow) || abi.encode(WithdrawalRequest({commitment: <any escrowed commitment>, tokens: [<escrowed token>], beneficiary: <attacker address>}))`.
3. Relay this (real, provable) message to the Tron host; `onAccept` calls `authenticate(request)` → `instance(X)` returns `address(this)` (fallback) → `module == address(this)` → passes.
4. `withdraw()` executes, transferring the escrowed token balance for that commitment to the attacker's `beneficiary`.
