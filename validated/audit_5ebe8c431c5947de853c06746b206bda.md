### Title
Scanner reports immature coinbase outputs as spendable funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` feeds every transaction in a block — including the coinbase transaction at `block.txdata[0]` — through `scan_transaction`, which returns matching outputs as `ReceivedOutput`s indistinguishable from ordinary, immediately spendable outputs (networks/bitcoin/src/wallet/mod.rs:216-227, 199-214).

### Finding Description
The external report describes a parser that mishandles attacker-supplied file structure, producing a corrupt object. The Serai analog is the block/transaction scanning path: an unprivileged party publishes a Bitcoin transaction (public input) that the scanner parses into `ReceivedOutput { offset, output, outpoint }`. In `scan_block`, the loop `for tx in &block.txdata` includes `txdata[0]`, the coinbase. Coinbase outputs are encumbered by a 100-block maturity rule under Bitcoin consensus; spending them earlier is invalid. The `ReceivedOutput` struct carries no coinbase/maturity marker — only `offset`, `output`, `outpoint` (wallet/mod.rs:90-97) — so downstream code (e.g., `send` in wallet/send.rs which consumes `ReceivedOutput`s to build transactions) cannot tell that the output is unspendable until the constructed spend is rejected by the network.

### Impact Explanation
Funds are reported received that are not spendable: an attacker can send a payment via a coinbase-adjacent flow, or more practically, any scanned block containing a matching coinbase output produces a `ReceivedOutput` the wallet will treat as a valid UTXO. If the wallet selects it for a spend (fee/change/selection logic in `send.rs`), the resulting transaction is consensus-invalid, and the wallet's accounting of balance/confirmed funds is wrong for up to 100 blocks. This matches the accepted outcome class "funds reported received that are not spendable."

### Likelihood Explanation
Likelihood is moderate: it requires the threshold key's P2TR script (or a registered offset script) to appear in a coinbase output — uncommon, but the scanner explicitly supports `scan_block` as the natural API for block processing, and the only mitigation is a doc comment advising callers to post-filter or use `scan_transaction` on `block.txdata[1 ..]`. Callers using the obvious `scan_block` path hit the bug whenever a matching coinbase exists; `scan_transaction` on any attacker-supplied tx is safe only because coinbase-ness is positional, not inherent to the tx.

### Recommendation
Either exclude `block.txdata[0]` inside `scan_block`, or add an `is_coinbase`/maturity flag to `ReceivedOutput` (e.g., record `tx.is_coinbase()` when constructing `OutPoint` at wallet/mod.rs:206-210) so downstream spend construction can enforce the maturity window instead of relying on caller discipline.

### Proof of Concept
```rust
// Conceptual: build a block whose coinbase pays to the scanner's P2TR script.
let keys = /* ThresholdKeys<Secp256k1> */;
let scanner = Scanner::new(keys.group_key()).unwrap();
let script = p2tr_script_buf(keys.group_key()).unwrap();

let coinbase = Transaction {
  input: vec![/* coinbase input with null prevout */],
  output: vec![TxOut { value: Amount::from_sat(50_0000_0000), script_pubkey: script }],
  ..Default::default()
};
let block = Block { header: /* .. */, txdata: vec![coinbase] };

// scan_block returns a ReceivedOutput for the coinbase vout 0,
// which is not spendable until 100 confirmations — yet is indistinguishable
// from a normal output and will be selected by `send` as a valid input.
let received = scanner.scan_block(&block);
assert_eq!(received.len(), 1); // immature, but reported as spendable
```
