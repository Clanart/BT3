### Title
Dishonest Stakers Can Siphon WOM Rewards From Honest `WombatPoolHelper` LPs Via Permissionless `harvest()` And Instant `deposit`/`withdraw` - (File: wombat/WombatStaking.sol, wombat/WombatPoolHelper.sol, rewards/BaseRewardPoolV2.sol)

### Summary
`WombatStaking`/`WombatPoolHelper` distribute WOM rewards to LP stakers pro-rata to their **current** stake balance at the moment of distribution, with no minimum holding period and a fully permissionless reward-triggering function. This reproduces the NFTX `xToken` "dishonest staker" bug class: an attacker can deposit right before (or together with) a reward harvest and withdraw immediately after, capturing a share of rewards they never contributed staking time toward, diluting honest long-term stakers.

### Finding Description
`WombatPoolHelper.harvest()` and `WombatPoolHelperV2.harvest()` are unrestricted, callable by any wallet: [1](#0-0) 

This calls `WombatStaking.harvest()`, which is likewise open to any external caller (guarded only by pool-active state, not by a privileged role), and triggers `_toMasterWomAndSendReward`, which pulls pending WOM rewards from the underlying Wombat `MasterWombat` and pushes them into the `BaseRewardPool`/`BaseRewardPoolV2` via `queueNewRewards`: [2](#0-1) 

`queueNewRewards`/`_provisionReward` distributes the incoming reward strictly pro-rata to `totalStaked()` at the moment of the call, with no time-weighting of individual balances: [3](#0-2) 

Deposits into the pool via `WombatPoolHelper.deposit`/`depositLP` mint receipt tokens and immediately auto-stake them in `MasterMagpie` with no lock or cooldown: [4](#0-3) [5](#0-4) 

`MasterMagpie._deposit`/`_withdraw` (called via `depositFor`/`withdrawFor`) apply no timelock either — a user's staked amount participates in `accMGPPerShare`/base-rewarder accrual the instant it is deposited, and withdrawal (which harvests the base rewarder for the caller) is available immediately in the same or the next block: [6](#0-5) 

Unlike `VLMGP`/`mWomSV`, which enforce a `coolDownInSecs` unlock delay before tokens can leave the lock, `WombatPoolHelper` stakes/receipt-token stakes have no equivalent delay: [7](#0-6) 

This mirrors exactly the reported NFTX `NFTXInventoryStaking`/`XTokenUpgradeable` bug class: an attacker can (1) deposit a large amount of the pool's deposit token/LP right before a WOM reward distribution, (2) trigger (or wait for someone else to trigger) the permissionless `harvest()` which credits `rewardPerTokenStored` proportionally over all currently staked tokens including the attacker's fresh stake, and (3) immediately `withdraw()`, which harvests the attacker's now-inflated share of the base rewarder before returning principal — capturing rewards proportional to capital, not to time actually staked.

### Impact Explanation
Honest long-term LPs in Wombat pools accrue and share WOM (and any other) rewards diluted by well-funded short-term depositors who add no genuine liquidity duration risk. Because `harvest()` is permissionless, an attacker does not even need to front-run someone else's transaction — they can self-trigger the distribution atomically around their own deposit/withdraw within one or two transactions, siphoning a portion of the accrued reward pool that should belong to honest stakers. This is a direct theft of yield that should be distributed to legitimate stakers.

### Likelihood Explanation
Likelihood is capital-dependent (as in the original NFTX finding) but requires no privileged access, no oracle manipulation, and no governance action — only ordinary wallet calls to `deposit`, `harvest`, and `withdraw`, all of which are permissionless and reachable by any user. The larger the pending unclaimed WOM reward relative to `totalStaked()`, the more profitable the attack, and repeat execution is possible every time the harvestable reward accumulates.

### Recommendation
- Add a minimum holding period (or use a snapshot/time-weighted mechanism) before newly deposited stake becomes eligible for reward distribution in `BaseRewardPool`/`BaseRewardPoolV2`, similar to the `VLMGP`/`mWomSV` cooldown pattern.
- Consider restricting `WombatStaking.harvest()`/`WombatPoolHelper.harvest()` to a keeper/manager role, or throttle the frequency of reward-triggering by unprivileged callers, removing the ability of an attacker to self-trigger a reward event around their own deposit/withdraw.
- Alternatively adopt a time-weighted-average-balance reward accrual model so pro-rata shares reflect duration staked, not just balance at distribution time.

### Proof of Concept
1. Wombat pool has accrued pending WOM rewards in `MasterWombat` for the LP pool tracked by `WombatStaking`/`BaseRewardPool`.
2. Attacker calls `WombatPoolHelper.deposit(largeAmount, minLiquidity)`, minting receipt tokens and auto-staking them via `MasterMagpie.depositFor` — instantly counted in `totalStaked()`. [4](#0-3) 
3. Attacker (or anyone) calls `WombatPoolHelper.harvest()` → `WombatStaking.harvest()` → `_toMasterWomAndSendReward` → `BaseRewardPool.queueNewRewards`, crediting `rewardPerTokenStored` pro-rata across all current stakers, including the attacker's freshly-added stake. [2](#0-1) [8](#0-7) 
4. Attacker immediately calls `WombatPoolHelper.withdraw(largeAmount, minAmount)`, which calls `MasterMagpie.withdrawFor` (harvesting the attacker's now-accrued base-rewarder share) before returning principal. [9](#0-8) [10](#0-9) 
5. Attacker walks away with a slice of WOM rewards proportional to capital deployed for a few blocks, diluting genuine long-term stakers, and can repeat this whenever pending rewards accumulate.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);

    function _withdraw(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        _harvestAndUnstake(_stakingToken, _account, _amount, _isVlMgp);

        if (!_isVlMgp)
            IERC20(tokenToPoolInfo[_stakingToken].stakingToken).safeTransfer(address(msg.sender), _amount);
        emit Withdraw(_account, _stakingToken, _amount);
    }

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
