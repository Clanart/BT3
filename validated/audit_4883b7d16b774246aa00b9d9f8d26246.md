### Title
Attacker-controlled `WWW-Authenticate` response is trusted to classify a git remote as a GitHub endpoint, enabling GitHub credential exfiltration via the trampoline credential helper - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
`UniProxy.depositSwap` trusted a caller-supplied `_router` address without verifying it was a legitimate router, letting the caller substitute a malicious contract and steal funds held by `UniProxy`. The same class of bug — trusting an externally supplied value to make a security-relevant trust decision instead of verifying it against a known-good source — exists in Desktop's `getEndpointKind` function used by the Git credential-helper trampoline. It classifies a git host as GitHub Enterprise based solely on the content of the `WWW-Authenticate` HTTP header returned by the remote server, a value fully controlled by whatever server the user's git operation talks to.

### Finding Description
When Git needs credentials, it invokes Desktop's `git-credential-desktop` helper, which is dispatched to `getCredential` in `app/src/lib/trampoline/trampoline-credential-helper.ts`. `getEndpointKind` decides how much trust to place in the connection by parsing the `wwwauth[]` credential-protocol keys — which are populated directly from the server's `WWW-Authenticate` response header — and returning `'enterprise'` if the header contains `realm="GitHub"`: [1](#0-0) 

The comment right above this code explicitly documents the trust assumption: it is used "as a happy-path to determine if the host is a GitHub host without having to resort to making a request ourselves" — i.e., no independent verification is performed: [2](#0-1) 

If `getEndpointKind` returns anything other than `'generic'` and no existing account matches the endpoint, `getCredential` triggers a GitHub sign-in prompt for that arbitrary endpoint: [3](#0-2) 

This is the direct analog of the `UniProxy` bug: just as `_router` was accepted from the caller and used to move funds without verifying it was a real, trusted router, the `wwwauth[]` value is accepted from an untrusted network peer (the git remote/proxy the user is fetching/cloning from) and used to decide whether to treat that peer as a trusted GitHub endpoint, without any independent check (such as `isGitHubHost`, which does perform a real network verification and is only reached later, and only when no `wwwauth[]` match is found): [4](#0-3) 

Once an account is created/bound to that attacker-chosen endpoint via the sign-in flow, subsequent Git operations against the same host will have their credentials filled from that account via `credWithAccount`, and Git will send them over the wire to whatever server responded with the crafted header: [5](#0-4) 

### Impact Explanation
A malicious or compromised HTTP(S) git server/proxy — e.g., a spoofed corporate GHE mirror, a malicious fork host, or a MITM proxy on an open network — can respond to Git's credential negotiation with `WWW-Authenticate: Basic realm="GitHub"`. This causes Desktop to treat the connection as a GitHub Enterprise endpoint and initiate a GitHub sign-in / account-binding flow for that arbitrary host. If the user completes it (or if credentials for a real GitHub Enterprise account happen to be reused against that host due to the endpoint being misclassified), Desktop will subsequently send the user's real GitHub access token/credential to the attacker-controlled server during later fetch/push operations — resulting in credential/token exfiltration, the "leaked funds" analog to the original report.

### Likelihood Explanation
The attacker only needs to control (or MITM) the server that a user's existing remote points to, or induce the user to add/clone from such a remote — no local access, admin rights, or prior malware is required, matching the "attacker controls a git remote/proxy response" impact criterion. The header value is checked purely for a substring/regex match against `realm="GitHub"`, which is trivial to forge.

### Recommendation
Do not use the `wwwauth[]` header content as a trust signal for endpoint classification. Only classify a host as `'enterprise'`/`'github.com'` after performing (or having previously performed and cached) an authoritative check such as `isGitHubHost` (a real network/API verification), or by matching against the user's explicitly configured GitHub Enterprise endpoints. If no verified match exists, always fall back to the `'generic'` credential path rather than prompting a GitHub sign-in for an unverified host.

### Proof of Concept
1. User has GitHub Desktop configured with a GitHub Enterprise account, or is willing to sign in when prompted.
2. Attacker stands up an HTTPS git server (or MITMs one) and configures it to respond to Git's credential probe with header `WWW-Authenticate: Basic realm="GitHub"`.
3. User clones/fetches from this server in Desktop.
4. `getCredential` → `getEndpointKind` sees the crafted `wwwauth[]` value and returns `'enterprise'` [6](#0-5) .
5. Since no account matches this new endpoint, `ui.promptForGitHubSignIn(endpoint)` is shown for the attacker's host [7](#0-6) .
6. Once bound, later git operations to that host will have the real GitHub credential attached via `credWithAccount` and sent to the attacker's server [8](#0-7) .

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.

      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
