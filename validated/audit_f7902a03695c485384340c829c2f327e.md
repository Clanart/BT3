### Title
Escrow accounting computed from pre-transfer declared amounts instead of actual received balance, allowing under-collateralized orders to drain other users' escrow - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Lambo report's core defect is that a caller-controlled parameter (`directionMask`) let an attacker redirect a privileged flow to point at attacker-controlled state, while the contract's bookkeeping ("profit was made") never checked that the *actual* backing state matched what was recorded. The same broken-invariant shape — recorded balance/liability diverging from actual custodied assets because of an unchecked externally-influenced value — reappears in `IntentGatewayV2.placeOrder` on the Tron deployment.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, when an order has predispatch calldata, the function:

1. Computes `reducedInputs` (escrow credit per token) and the order `commitment` **before** executing the predispatch call, using the raw, user-declared `order.inputs[i].amount` [1](#0-0) .
2. Executes the arbitrary predispatch `Call[]` via `CallDispatcher` (fully attacker/user-controlled `to`, `value`, `data`) [2](#0-1) .
3. After execution, only checks that the dispatcher's *pre-final-transfer* balance is `>= requiredAmount` (the original declared amount), then issues a token `transfer` call moving that balance from the dispatcher back to the gateway — but never re-measures what the gateway itself actually received after this transfer [3](#0-2) .
4. Escrow is credited with `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` was derived purely from the user-declared amount, not from any post-transfer measurement [4](#0-3) .

If the token (or any hop in the predispatch flow) applies a fee/haircut on the final dispatcher→gateway `transfer` (fee-on-transfer tokens, rebasing tokens, or a predispatch call engineered to leave a shortfall), the gateway ends up holding **less** than the amount it just credited to `_orders[commitment][token]`. Because `_orders` accounting is per-commitment but the underlying token balance is a **shared pool** across all orders for that token, this creates a phantom liability: the order's recorded escrow exceeds its actual contribution to the pool.

This is exactly the bug-class from the external report: an externally-influenced value (there, `directionMask`; here, the predispatch `Call[]`/token choice) is trusted to represent state ("the pool is `uniswapPool`" / "the escrow equals the declared amount") without validating it against the *actual* resulting on-chain state, letting an attacker manufacture a state where recorded and true amounts diverge.

The mainline EVM contract closes this exact gap: it snapshots balances before the dispatcher-to-gateway transfer and explicitly re-measures `received = balanceAfter - balancesBefore[i]`, mutating `order.inputs[i].amount` to the actual received value *before* computing fees/commitment [5](#0-4) , and this exact scenario is covered by `testPlaceOrder_FeeOnTransferToken_Predispatch` [6](#0-5) . The Tron contract lacks this re-measurement step entirely.

### Impact Explanation
When `fillOrder`/`withdraw` later releases `_orders[commitment][token]` to the solver via `IERC20(token).safeTransfer(beneficiary, amount)` [7](#0-6) , that transfer is paid out of the gateway's aggregate token balance, not a balance earmarked strictly to that order. An order whose escrow was inflated by the missing re-measurement step will, once filled, pull the shortfall from tokens that other users legitimately escrowed for their own orders — i.e., loss of funds for unrelated users, or an underflow/revert that locks other users' legitimate withdrawals/cancellations (DoS on escrow release). This matches the required impact class: unauthorized loss of funds / logic attack against shared custody, reachable by any ordinary user placing an order — no relayer, prover, or admin compromise needed.

### Likelihood Explanation
Likelihood is moderate-to-high: any user can freely choose the input token and construct a predispatch `Call[]` for their own order, and fee-on-transfer or deflationary tokens are common. No privileged role or malicious peer is required — an unprivileged order-placer using a fee-on-transfer token (or a predispatch flow that leaves a shortfall on the final leg) triggers the miscomputation automatically, without needing precise address-grinding (unlike the original Lambo PoC).

### Recommendation
Mirror the mainline EVM implementation in `evm/tron/contracts/apps/IntentGatewayV2.sol`: snapshot the gateway's token balance before the dispatcher-to-gateway transfer call, re-measure the actual amount received after `ICallDispatcher(dispatcher).dispatch(...)` completes, and compute `reducedInputs`/the commitment/the `_orders` credit strictly from that measured, actual-received amount — never from the pre-dispatch declared `order.inputs[i].amount`.

### Proof of Concept
1. Deploy/use a fee-on-transfer ERC20 (`FOT`) with e.g. a 1% transfer fee, analogous to the existing `FeeOnTransferToken` test helper.
2. User places an order on the Tron `IntentGatewayV2` with `predispatch.assets = [{token: FOT, amount: 1000}]` and a no-op predispatch call (empty `Call[]`), and `inputs = [{token: FOT, amount: 1000}]`.
3. In `placeOrder`: `reducedInputs`/`commitment` are computed from the declared `1000` (step 1, before predispatch runs). The dispatcher receives `990` FOT after the user→dispatcher transfer fee. The dispatcher-to-gateway `transfer(address(this), 990)` further applies the 1% fee, so the gateway actually receives `~980.1` FOT.
4. The check `balance < requiredAmount` uses `balance = 990` (dispatcher's balance) versus `requiredAmount = 1000` → **reverts** in this exact numeric example, but the check is only against the dispatcher-side balance, not the gateway's final received amount. A predispatch flow can be constructed (e.g., a swap or double-hop with more path steps) where the dispatcher-side balance clears the `requiredAmount` check while the final gateway-side transfer alone applies an additional, unaccounted haircut — leaving the gateway with strictly less than `reducedInputs[i].amount` while `_orders[commitment][token]` is still credited with the full `reducedInputs[i].amount`.
5. When this order is later filled and `withdraw`/`_withdraw` releases `_orders[commitment][token]` to the solver, the transfer draws on the shared FOT balance held by the gateway across all outstanding FOT orders, paying out more than this order actually contributed and depleting the balance backing other users' escrowed FOT orders.

Note: exact numeric parameters to reproduce the shortfall while passing the `balance < requiredAmount` gate depend on constructing a predispatch call with an intermediate hop; the structural flaw (commitment/escrow computed pre-measurement, unlike the audited mainline EVM fix and its `testPlaceOrder_FeeOnTransferToken_Predispatch` regression test) is directly verifiable from the code cited above.

    /// @notice Fee-on-transfer through the predispatch path: escrow reflects actual received.
    function testPlaceOrder_FeeOnTransferToken_Predispatch() public {
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% transfer fee
        fot.mint(user, 10000 * 1e18);

        uint256 predispatchAmount = 1000 * 1e18;
        // After transferring to dispatcher: 1% fee = dispatcher receives 990
        uint256 dispatcherReceived = predispatchAmount - (predispatchAmount * 100) / 10000;
        // After dispatcher transfers to gateway: another 1% fee = gateway receives ~980.1
        uint256 gatewayReceived = dispatcherReceived - (dispatcherReceived * 100) / 10000;

        // Predispatch: send FOT to dispatcher, the "call" is a no-op (empty calls array)
        TokenInfo[] memory predispatchAssets = new TokenInfo[](1);
        predispatchAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: predispatchAmount});

        // The predispatch call is an empty Call[] dispatch (no-op, tokens just sit on dispatcher)
        Call[] memory emptyCalls = new Call[](0);

        TokenInfo[] memory inputs = new TokenInfo[](1);
