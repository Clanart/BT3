### Title
Duplicate encryption-key registration causes an unrecoverable panic (DoS) during PedPoP DKG key setup — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The QEMU CVE-2016-2197 class is "missing check on attacker-influenced state leading to a null-deref crash (DoS)". In Serai's in-scope code the analogous shape is an unchecked duplicate-registration assertion in the PedPoP encryption layer: `Decryption::register` panics via `assert!` when a `Participant` index is registered a second time. A participant whose encryption-key message is delivered/registered twice (e.g., a malicious relay or participant publishing two `EncryptionKeyMessage`s, or a duplicated message in the aggregation loop) causes every honest node processing the registration round to abort with a panic, killing the DKG session — a remotely-triggerable denial of service reachable with only public protocol messages.

### Finding Description
`Decryption::register` is fed by `Encryption::register`, which is called once per received `EncryptionKeyMessage` during the PedPoP key-derivation round:

```rust
// crypto/dkg/pedpop/src/encryption.rs
pub(crate) fn register<M: Message>(
  &mut self,
  participant: Participant,
  msg: EncryptionKeyMessage<C, M>,
) -> M {
  assert!(
    !self.enc_keys.contains_key(&participant),
    "Re-registering encryption key for a participant"
  );
  self.enc_keys.insert(participant, msg.enc_key);
  msg.msg
}
``` [1](#0-0) 

The `EncryptionKeyMessage` itself is parsed from untrusted bytes via `EncryptionKeyMessage::read` (`M::read` + `C::read_G`), so the *contents* are attacker-controlled; the participant index is the map key under which the message is registered. Nothing in this function returns a recoverable error — duplicate registration is a hard `assert!`, so the host process panics instead of rejecting the offending message.

Comparable panic sites reachable from serialized/untrusted data elsewhere in scope show the same class is systemic, not hypothetical:

- `ThresholdKeys::view` indexes `verification_shares` and `unwrap()`s `included.last()` and `get_mut(&included[0])` after its own validation (`crypto/dkg/src/lib.rs:487`, `:521`), and `AlgorithmSignMachine::sign` calls `self.params.keys.view(included.clone()).unwrap()` (`crypto/frost/src/sign.rs:312`) — safe only because prior checks happen to cover every case; any gap converts directly to panic.
- `BatchVerifier::verify_vartime_with_vartime_blame` does `self.blame_vartime().unwrap()` on the error path (`crypto/multiexp/src/batch.rs:141`); blame returning `None` would panic during signature-share verification in `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:487`).
- `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` (`encryption.rs:388`), panicking if blame is raised for a participant whose key was never registered.

The `Decryption::register` assert is the cleanest of these because the trigger requires only that the same participant index be registered twice — no malformed bytes, no invalid curve points, just protocol-level message duplication.

### Impact Explanation
PedPoP is the DKG used to generate `ThresholdKeys`. If the DKG panics mid-round, no group key is produced and (depending on the integrator's panic handling) the validator/node process aborts, matching CVE-2016-2197's "privileged-in-guest crashes the process → DoS" at Medium severity. The abort occurs on every honest node that processes the duplicated registration, so a single malicious or double-delivered message can stall or crash the whole key-generation ceremony. No secret material is leaked and no signature is forged — impact is availability only, consistent with Medium.

### Likelihood Explanation
Reachability rests on public inputs: the attacker only needs to cause two `EncryptionKeyMessage`s bearing the same `Participant` index to reach `register` — e.g., by publishing a second registration message or by inducing a relay/coordinator to redeliver one. Because the failure mode is a process panic (not an `Err`), any integration that does not catch panics is DoS'd. Caveat: I verified the panic site and that `EncryptionKeyMessage::read` consumes untrusted bytes, but I did not fully trace `pedpop/src/lib.rs`'s outer loop to confirm whether it deduplicates by sender before calling `register`; if the caller already enforces exactly-once registration keyed on the authenticated sender, the reachable trigger narrows to duplicate delivery paths (message replays, multi-message sends). Confidence in the bug's existence is high; confidence in unauthenticated reachability is moderate.

### Recommendation
Replace the `assert!` in `Decryption::register` with a recoverable error returned to the caller (e.g., extend a `DkgError`-style enum with `DuplicatedParticipant`), and apply the same audit to the `enc_keys[&decryptor]` / `enc_keys[&participant]` index operations and to `view(...).unwrap()`/`blame_vartime().unwrap()` call sites, converting each into an explicit validity check with an error result so attacker-influenced ordering or duplication can never abort the process.

### Proof of Concept
Conceptual driver against `Decryption::register` (the public entry is via `Encryption::register` on a received `EncryptionKeyMessage`):

```rust
// Two EncryptionKeyMessage<C, M> values both registered under Participant(2):
let mut decryption = Decryption::<C>::new(context);
let m1: EncryptionKeyMessage<C, M> = EncryptionKeyMessage::read(&mut bytes_1, params)?;
let m2: EncryptionKeyMessage<C, M> = EncryptionKeyMessage::read(&mut bytes_2, params)?; // e.g., relay replay
decryption.register(Participant::new(2).unwrap(), m1);
decryption.register(Participant::new(2).unwrap(), m2); // thread panics: "Re-registering encryption key for a participant"
```

A malicious participant publishes its `EncryptionKeyMessage` twice to the authenticated channel/coordinator (or a relay replays it). Every honest node that registers messages in arrival order hits the `assert!` at `crypto/dkg/pedpop/src/encryption.rs:356` and panics, aborting the DKG. No malformed encodings or invalid proofs are required — `bytes_1`/`bytes_2` are both well-formed messages; only the duplicate participant index triggers the crash.
