### Title
Unauthenticated `kc_user`/`kc_service` request fields let any local daemon client read or delete private keys belonging to another keychain partition - (File: chia/daemon/keychain_server.py)

### Summary
The Chia daemon's `KeychainServer` selects which underlying `Keychain` (i.e. which private-key store partition) to operate on based on the `kc_user`/`kc_service` fields taken directly from the caller-supplied websocket request body, with no authorization check tying those values to the identity of the connecting client. Any local process that can open a websocket session to the daemon can therefore request keychain operations (`get_key`, `get_all_private_keys`, `get_key_for_fingerprint`, `delete_key_by_fingerprint`, etc.) against an arbitrary `kc_user`/`kc_service` pair it does not own, retrieving or destroying private keys that belong to a different keychain partition (e.g. another local Chia installation, network, or simulator instance sharing the same OS keyring backend).

### Finding Description
`KeychainServer.get_keychain_for_request()` builds/returns a `Keychain` instance purely from attacker-controlled request data: [1](#0-0) 

```
def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
    user = request.get("kc_user", self._default_keychain.user)
    service = request.get("kc_service", self._default_keychain.service)
    ...
    keychain = Keychain(user=user, service=service)
    self._alt_keychains[key] = keychain
```

There is no check that the connecting websocket/service is entitled to use the requested `user`/`service` pair — any value supplied in the JSON payload is accepted and used to instantiate (or reuse) a `Keychain` object. This is dispatched directly from the daemon's top-level message handler for any of the `keychain_commands` (`get_key`, `get_all_private_keys`, `get_key_for_fingerprint`, `delete_key_by_fingerprint`, `set_label`, etc.): [2](#0-1) 

The legitimate client-side helper (`KeychainProxy`) only ever sets `kc_user`/`kc_service` to its own configured values before sending a request: [3](#0-2) 

but nothing stops a malicious/compromised local process (which already holds a client cert accepted by the daemon's shared mutual-TLS gate — the daemon does not differentiate permissions per connecting service) from crafting its own request with a different `kc_user`/`kc_service` and sending it directly over the daemon websocket.

Internally, `Keychain(user, service)` uses these strings purely as free-form partition keys into the same underlying encrypted keyring file/OS credential store — there is no secondary secret or per-partition access control: [4](#0-3) 

This mirrors the CVE-2022-30952 bug class: a caller that is only supposed to operate within its own scope can supply an attacker-chosen ID (here, `kc_user`/`kc_service`) to reach a private-per-scope credential store belonging to someone/something else.

### Impact Explanation
An unauthorized local daemon client can enumerate, read, or delete private keys/mnemonics stored under a keychain partition it does not own (e.g. a different Chia network/testnet/simulator profile, or another product/user sharing the same OS keyring backend), by simply supplying different `kc_user`/`kc_service` values. Exposure of a private key/mnemonic allows unauthorized signing and unsigned/unauthorized coin movement for whatever wallet corresponds to that key, and `delete_key_by_fingerprint` on a foreign partition is a spend-relevant denial-of-service against another instance's wallet key material.

### Likelihood Explanation
Exploitation requires the ability to open a websocket to the local daemon, which is gated by mutual TLS using the shared daemon certificates rather than per-service authorization scoping (per the daemon's own design notes, "the primary gate is mutual TLS using daemon private certs plus local config", with no per-command authorization by client identity). Any local service or tool that is trusted enough to hold a daemon cert (farmer, timelord, harvester, GUI, or a compromised/misbehaving plugin) already qualifies, and crafting the `kc_user`/`kc_service` fields requires no special privilege beyond normal daemon protocol knowledge, making this straightforward to trigger once daemon connectivity exists.

### Recommendation
- Do not allow `kc_user`/`kc_service` to be set from client-supplied JSON to select an already existing keychain partition unless the daemon can verify the connecting client is authorized for that partition.
- Tie `kc_user`/`kc_service` resolution to the actual service identity registered for that websocket connection (as recorded during `register_service`) rather than trusting arbitrary request fields.
- If cross-partition access is intentionally needed (e.g. for the simulator), require an explicit, separately-authenticated administrative command rather than allowing it via the generic keychain command surface.

### Proof of Concept
1. Start `chia start daemon` normally; a separate legitimate wallet service registers and stores its keys under the default `kc_user`/`kc_service`.
2. From any local process holding an accepted daemon client certificate (e.g., a farmer/timelord/simulator service, or any other local client not itself needing key access), open a websocket connection to the daemon.
3. Send a `get_all_private_keys` (or `get_key`, `get_key_for_fingerprint`) command with a JSON payload containing `"kc_user"` and `"kc_service"` values guessed/known to correspond to another local Chia keychain partition (e.g. a testnet, simulator, or second profile on the same machine) — for example, reusing the pattern from `KeychainServer.get_keychain_for_request` at [1](#0-0)  — instead of omitting these fields.
4. Observe the daemon returns key/mnemonic data for that foreign partition, or executes `delete_key_by_fingerprint`/`set_label` against keys the caller does not own, with no authorization error, confirming the missing scoping check documented above at [2](#0-1) .

```python
    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
```

```python
    def _get_key_data(self, index: int, include_secrets: bool = True) -> KeyData:
        """
        Returns the parsed keychain contents for a specific 'user' (key index). The content
        is represented by the class `KeyData`.
        """
        user = get_private_key_user(self.user, index)
        key = self.keyring_wrapper.keyring.get_key(self.service, user)
        if key is None or len(key.secret) == 0:
            raise KeychainUserNotFound(self.service, user)
        str_bytes = key.secret

        public_key = G1Element.from_bytes(str_bytes[: G1Element.SIZE])
        fingerprint = public_key.get_fingerprint()
        if len(str_bytes) > G1Element.SIZE:
            entropy = str_bytes[G1Element.SIZE : G1Element.SIZE + 32]
        else:
            entropy = None

        return KeyData(
            fingerprint=uint32(fingerprint),
            public_key=public_key,
            label=self.keyring_wrapper.keyring.get_label(fingerprint),
            secrets=KeyDataSecrets.from_entropy(entropy) if include_secrets and entropy is not None else None,
        )
```
