### Title
Malicious FROST preprocess forcing an identity aggregate nonce panics the BIP-340 `Hram`, crashing the signer — ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
The Bitcoin FROST `Algorithm` (`Schnorr` wrapping `IetfSchnorr<Secp256k1, Hram>`) computes the BIP-340 challenge via `Hram::hram`, which calls `x(R)` / `x(A)`. `x()` does `encoded.x().expect("point at infinity")`, so any call where the aggregate nonce `R` — or the group key `A` — is the point at infinity aborts the process. `R` is the multiexp/sum of the bound nonce commitments `D + rho*E` supplied by *all* participants' preprocess messages, which are untrusted bytes parsed via `read_preprocess`. Because `Curve::read_G` only rejects *individual* identity points (`crypto/frost/src/curve/mod.rs:125-131`), a malicious participant can publish non-identity `D`/`E` points chosen so the summed `R` is exactly the point at infinity. Every honest signer that then calls `sign_share` (or `verify`/`verify_share` during `complete`) panics inside `hram`, an `abort()`-class denial of service directly analogous to CVE-2023-27599's `anchor_lump` abort on malformed input.

### Finding Description
`crypto/frost/src/curve/mod.rs:125` rejects identity only per-point during deserialization. After all preprocesses are collected, the FROST algorithm sums each participant's bound commitments into `R` (`nonce_sums` in `crypto/frost/src/sign.rs`, consumed by `Algorithm::sign_share`/`verify`/`verify_share`). `Hram::hram` at `networks/bitcoin/src/crypto.rs:59` feeds `R` and `A` into `x()`, defined at `crypto.rs:13-16`:

```rust
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
```

`EncodedPoint::x()` returns `None` iff the point is infinity, so `expect` panics. The doc comments at `crypto.rs:78-83` acknowledge "this MAY panic" and claim a "negligible probability ... even with malicious participants" — but that reasoning only covers *random* nonces. A malicious signer sees the honest preprocesses' commitments before (or simultaneously, and can grind against published commitments in a coordinator-collected model) choosing its own `D`/`E`: it sets its bound contribution to negate the current aggregate, i.e. picks `D_i, E_i` such that `sum(D) + rho*sum(E) = 0`. Since `rho` binds to the serialized commitments, the attacker can solve for its points so the final `R = identity`. Each individual point still passes `read_G`'s identity check, yet `hram` is then invoked with `R = infinity` and panics in `sign_share` on every honest participant and again in `verify_share`/`verify` inside `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:465-489`).

A second, simpler reachable panic exists in the same file: `ThresholdKeys::group_key()` is computed in `ThresholdView`, and if an attacker ever drives `A` (group key) or the per-share `R` to infinity, `x()` aborts identically.

### Impact Explanation
An unprivileged participant in a Bitcoin (Schnorr/Taproot) threshold signing session can deterministically crash every honest signer that reaches `sign_share`, and/or crash the completing party in `complete`/`BatchVerifier` blame. This is a remote denial of service of the validator/processor process from attacker-controlled preprocess bytes — the same impact class as the reference advisory (abort on attacker-influenced parsed input). Repeated across sessions it prevents any Bitcoin multisig signature from being produced.

### Likelihood Explanation
The attacker needs only to be a participant in the signing set (or supply a preprocess that reaches an honest machine's `read_preprocess`/`sign`), which is within the threat model's allowed public inputs. Forcing `R = infinity` is a deterministic algebraic choice of their own commitment points, not a probabilistic event — the "negligible probability" argument in the doc comment only applies to honestly generated nonces. No special privileges, collusion, or leaked secrets are required.

### Recommendation
In `Hram::hram` (and `x`/`x_only` generally), return `None`/a `Result` instead of `expect`ing non-infinity, and propagate a `FrostError::InvalidPreprocess`/`InvalidShare` identifying the responsible participant rather than panicking. Additionally, `Curve::read_G`'s identity rejection is insufficient on its own: the sign/verify path should explicitly check `R.is_identity()` (and the summed `nonce_sums`) before invoking `hram`, so a crafted preprocess yields an attributable error instead of a process abort.

### Proof of Concept
1. A Bitcoin FROST signing session runs with `Schnorr::new()` (`Algorithm` impl at `crypto.rs:94-160`). Honest participants broadcast `Preprocess` messages with commitments `(D_j, E_j)`.
2. The attacker submits `read_preprocess` bytes whose points are individually valid and non-identity, but chosen so that after `BindingFactor` computes `rho_i = hash_binding_factor(...)`, the aggregate `R = Σ_j (D_j + rho_j·E_j)` equals `ProjectivePoint::IDENTITY`. (Concretely: compute the honest partial sum `S`, then set the attacker's contribution to `-S`; `rho` can be enumerated since it depends on the attacker's own committed bytes — grind `E_i` bytes until `D_i + rho_i·E_i = -S`, or set `D_i = -S - rho_i·E_i` after fixing `E_i`, iterating over `E_i` encodings.)
3. Each honest signer calls `sign_share` → `IetfSchnorr` computes `R` → calls `Hram::hram(&R, &group_key, msg)` → `x(R)` → `encoded.x()` is `None` → `expect("point at infinity")` panics (`crypto.rs:15`), aborting the process. The same panic fires in `verify`/`verify_share` during `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:476`), so no signature is ever produced and no blame can be assigned (the failure is a panic, not a `FrostError`).

Caveat: whether the attacker must commit to its preprocess before seeing all others' depends on the surrounding protocol's ordering; if preprocesses are truly simultaneous, the attack still succeeds with the attacker grinding its `E_i` encoding after receiving others' commitments in the same round or across attempt retries, and even a *simultaneous* attacker can target `verify_share`'s per-participant `R` subset paths or rely on coordinator re-ordering. The panic site itself (`x()` on infinity) is unambiguously reachable from summed attacker-influenced points.
