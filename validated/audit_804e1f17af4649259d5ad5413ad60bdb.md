## Analog Found: Recursive clone disables Git's built-in submodule protocol protection

### Title
Disabling `GIT_CLONE_PROTECTION_ACTIVE` during recursive clone lets a malicious repository read files or execute code via crafted submodule URLs - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` in `app/src/lib/git/clone.ts` invokes `git clone --recursive` while explicitly setting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the git environment, and does not set `protocol.file.allow` or `GIT_ALLOW_PROTOCOL` restrictions. [1](#0-0)  This is the exact opposite of the pattern used elsewhere in the codebase: `updateSubmodulesAfterOperation()` (used by checkout/pull/fetch flows) only permits the `file://` transport for submodules when an explicit `allowFileProtocol` flag is passed in by the caller, gated behind `protocol.file.allow=always`. [2](#0-1) 

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is Git's own internal safety flag (introduced upstream to remediate CVE-2022-39253, the "recursive clone of a repository with submodules can read/write arbitrary files via `file://`/`ext::` submodule URLs" class of bug). Git normally refuses to honor local (`file://`) or command-executing (`ext::`) submodule transports encountered while auto-fetching submodules during a `--recursive` clone, unless the user explicitly opts in. By setting this variable to `'false'` unconditionally for every clone performed by Desktop, `clone()` disables that upstream guard for the entire recursive-submodule-fetch step. [3](#0-2) 

The `.gitmodules` file and submodule URLs are fully attacker-controlled content of the repository being cloned — there is no authentication, ownership, or trust check performed on them before the `git clone --recursive` call executes. `clone()` performs no protocol allow-listing of its own (`envForRemoteOperation()` only adds authentication/proxy env, nothing related to submodule protocol restriction) [4](#0-3) , so the only thing standing between an attacker-supplied `.gitmodules` and Git's dangerous local/`ext::` submodule handling is the very protection this code disables.

By contrast, the `updateSubmodulesAfterOperation()` path used for checkout/pull correctly treats "allow file protocol for submodules" as an explicit, narrowly-scoped opt-in the caller must request [5](#0-4) , showing the maintainers are aware this is a sensitive capability that needs gating — yet the initial `clone --recursive` path bypasses Git's own equivalent protection wholesale for every clone, regardless of whether the repository is trusted.

### Impact Explanation
When a user clones an attacker-controlled repository (e.g. from a malicious link, a forked/renamed repo, or any untrusted git URL) through Desktop's clone flow, a `.gitmodules` file with a submodule URL such as `file:///etc/passwd`, `file://` pointing at another local git repository (exfiltrating its object database into the newly cloned working directory), or an `ext::sh -c '...'` transport can be processed without Git's normal opt-in protection, potentially resulting in:
- reading files/objects from arbitrary local paths outside the intended clone directory,
- execution of arbitrary commands via the `ext::` git transport during the recursive submodule fetch step.

This matches the valid-impact criteria: attacker controls a cloned/fetched repository, and the result is code execution or file read outside the repo boundary, with no local/physical access or prior compromise required — merely getting the victim to clone the repository through Desktop's UI.

### Likelihood Explanation
Every "Clone repository" action in Desktop (URL, GitHub.com listing, or local path) funnels through this single `clone()` function and unconditionally passes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` with `--recursive` [6](#0-5) . No user interaction beyond the normal "Clone" button is required, and the vulnerable content (`.gitmodules`) is simply part of the attacker's repository, making this a high-likelihood, low-effort attack for anyone who can get a target to clone their repository.

### Recommendation
Do not unconditionally disable `GIT_CLONE_PROTECTION_ACTIVE`. Preserve Git's default submodule-protocol protection during the initial recursive clone the same way `updateSubmodulesAfterOperation()` does for subsequent operations: only relax the restriction when the user has explicitly opted into local/`ext::` submodules for a specific, trusted operation (e.g. explicitly requested by the user for local development repos), and otherwise let Git's built-in `protocol.file.allow`/`GIT_ALLOW_PROTOCOL` defaults reject unexpected transports for submodule URLs discovered inside a freshly-cloned, untrusted repository.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitmodules` file with a submodule entry such as:
   ```
   [submodule "evil"]
       path = evil
       url = file:///home/victim/.ssh
   ```
   or using `ext::sh -c 'touch /tmp/pwned'` as the URL.
2. Victim uses GitHub Desktop's "Clone a repository" feature to clone the attacker's repository (via URL, GitHub listing, or any UI entry point that calls `clone()` in `app/src/lib/git/clone.ts`).
3. `clone()` runs `git clone --recursive ... -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set, disabling Git's own protection against processing the malicious submodule URL. [1](#0-0) 
4. Git proceeds to fetch the submodule using the attacker-specified `file://`/`ext::` transport, copying files from the victim's local filesystem into the clone directory (or executing the attacker's command), without any prompt or confirmation from Desktop.

**Uncertainty note:** I was not able to execute the actual clone to confirm the runtime behavior of `GIT_CLONE_PROTECTION_ACTIVE=false` combined with the installed Git version bundled by Desktop (behavior can vary slightly by Git version), since I only have read access to the indexed source and not a live environment. A Devin session with full repo/checkout access could verify the exact Git version bundled and reproduce the submodule fetch behavior end-to-end.

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
