Based on the investigation, most of the obvious analogs (clone path traversal, `sanitizeCloneName`, `isClonePathSensitive`, protocol-handler URL parsing) are already defended with explicit, separator-aware boundary checks and unit tests. However, the shared low-level primitive that many of those callers rely on for confinement, `resolveWithin()`, contains a boundary-check gap that the other call sites avoided.

### Title
Path-prefix confinement bypass in `resolveWithin()` lets a crafted relative path escape the intended root directory - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is the shared helper used throughout Desktop to confirm that a path derived from untrusted/repo-relative input stays inside a trusted root directory (repository working directory) before that path is used to read, write, or reveal a file. Its final containment check uses a bare `String.prototype.startsWith()` comparison without requiring a path separator boundary, so a resolved path in a *sibling* directory whose name happens to start with the root directory's name is incorrectly treated as "inside" the root.

### Finding Description
The core check is: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`realResolved.startsWith(realRoot)` is a naive string-prefix test. If `realRoot` is e.g. `/Users/victim/Documents/GitHub/proj` and a caller passes a relative segment like `../proj-secrets/notes.txt`, the resolved real path `/Users/victim/Documents/GitHub/proj-secrets/notes.txt` legitimately starts with the string `/Users/victim/Documents/GitHub/proj` (no separator required after `proj`), so the function returns the path as "safe" even though it is a completely different, sibling directory outside the intended root.

This is the exact defect class the report describes: a *missing boundary/exactness guard* on a security-relevant check, which lets an operation succeed with an unintended target. The codebase shows the developers are otherwise aware of this exact pitfall — the sibling helper `isClonePathSensitive()` explicitly appends the separator when doing the same kind of comparison: [2](#0-1) 

but `resolveWithin()`, the far more widely used primitive, does not apply the same fix.

`resolveWithin()` gates a genuine write operation in the Copilot merge-conflict auto-resolution flow: [3](#0-2) 

```
const absolutePath = await resolveWithin(repository.path, resolution.path)
if (absolutePath === null) { ... continue }
...
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
```

`resolution.path` and `resolution.resolvedContent` are attributes attached to the working directory during Copilot-assisted conflict resolution, seeded from file paths gathered by `buildConflictContext()`, which reads attacker-influenced repository content (conflict hunks) and is itself guarded by the same `resolveWithin()` primitive: [4](#0-3) 

It is also used to gate revealing a file from a clickable deep link (`x-github-client://openrepo/...&filepath=...`), where `filepath` comes directly from a URL an attacker can get a user to click: [5](#0-4) 

### Impact Explanation
Any caller that relies on `resolveWithin()` as its sole confinement guard is exposed to a repo-name/sibling-directory collision bypass. The most severe consequence is in `app-store.ts`, where a successful bypass allows `writeFile()` to write attacker-influenced content to a path outside the current repository, on disk, under the logged-in user's file permissions — a "write outside the repo" primitive per the impact criteria. The `dispatcher.ts` deep-link path additionally allows an attacker-supplied `filepath` (from a link a user clicks) to make Desktop reveal a sibling directory/file to the user via `shell.showItemInFolder`, an information-disclosure/confinement bypass reachable purely through a link click.

### Likelihood Explanation
Exploitation requires that a directory whose name is a *prefix superstring* of the repository/root directory name already exists on disk next to it (e.g. `proj` vs `proj-secrets`), which is a real but not universal precondition — it depends on the user's local folder layout (common in practice for people who keep multiple related clones like `myapp` and `myapp-configs` side by side under the same parent, e.g. GitHub Desktop's default `~/Documents/GitHub/` clone root). Because the attacker only needs to control repository content (conflict file contents feeding Copilot resolution) or a link the user clicks, and does not need local/physical access or existing malware, this satisfies the "unprivileged... attacker controls a cloned/fetched repository ... or a link" requirement. Note: full confirmation of whether `resolution.path` is strictly validated against the original conflict-file list before reaching `resolveWithin()` requires reviewing `app/src/lib/copilot-conflict-resolution.ts`, which time constraints did not allow inspecting in this pass — this is a remaining unknown that should be verified.

### Recommendation
Fix the containment check in `_resolveWithin()` (`app/src/lib/path.ts`) to require an exact match or a trailing path separator boundary, mirroring the pattern already used in `isClonePathSensitive()`:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add a regression test asserting that a sibling directory sharing a name prefix with the root (e.g. root `foo`, target `foo-secret/file`) is rejected.

### Proof of Concept
1. Clone a repository to `~/Documents/GitHub/proj`.
2. Ensure a sibling directory `~/Documents/GitHub/proj-secrets/leaked.txt` exists.
3. Trigger a code path that calls `resolveWithin('~/Documents/GitHub/proj', '../proj-secrets/leaked.txt')` (e.g., via the Copilot conflict-resolution write path with a crafted `resolution.path`, or via the `filepath` query parameter of an `x-github-client://openrepo/...` deep link pointing to this repo).
4. Observe that `resolveWithin` returns the resolved path to `leaked.txt` as "safe" (non-null) despite it residing outside `proj`, allowing the file to be written to (Copilot flow) or revealed (deep-link flow).
