Given the constraints on further exploration, here is the strongest locally-provable analog I found to the "wrong `rootHash`, no recovery mechanism" bug class.

### Title
EVM host's state-commitment veto (the only recovery path for a bad state commitment) resets the height floor to `1` instead of the last-known-good height, silently reopening the entire commitment history to being overwritten with fresh challenge-period timestamps - (File: `evm/src/core/EvmHost.sol`)

### Summary
Hyperbridge's own answer to "what if a wrong state root gets committed" is the fisherman-veto mechanism: `deleteStateMachineCommitment`/`deleteStateMachineCommitmentInternal`. This is the intended recovery mechanism the external Keystore report recommends building. On Substrate hosts this recovery correctly rewinds `LatestStateMachineHeight` back to the previously-recorded good height. On EVM hosts, the equivalent logic instead unconditionally resets the height counter to the constant `1`, and the EVM consensus handler (`HandlerV2.handleConsensus`) has no "skip if already stored" guard like the Substrate handler does. The combination means the recovery path itself corrupts the height bookkeeping instead of fixing it.

### Finding Description
Substrate's `delete_state_commitment` restores the correct prior height: [1](#0-0) 

The EVM equivalent, `deleteStateMachineCommitmentInternal`, resets to the hardcoded value `1` instead of the actual previous height: [2](#0-1) 

The Substrate consensus handler (`update_client`) explicitly guards against re-accepting/overwriting a height that already has a stored commitment: [3](#0-2) 

The EVM handler (`HandlerV2.handleConsensus`) has no such duplicate/overwrite guard — it only checks `intermediate.height > latestHeight`: [4](#0-3) 

And `storeStateMachineCommitment` itself unconditionally overwrites whatever was previously stored at that height, refreshing the update timestamp used for challenge-period gating: [5](#0-4) 

Because `_latestStateMachineHeight[id]` is reset to `1` after any veto (even a veto of a single stale, non-latest height whose commitment happens to equal the currently recorded latest), any subsequent consensus proof whose intermediate states satisfy `height > 1` — which is virtually guaranteed — is accepted and stored again, unconditionally overwriting `_stateCommitments` and refreshing `_stateCommitmentsUpdateTime` for that height. `handlePostRequests`/`handleGetResponses` gate solely on `block.timestamp - stateMachineCommitmentUpdateTime(height) >= challengePeriod`: [6](#0-5) 

This lets the challenge-period clock for an already-settled height be refreshed/reset via ordinary (non-malicious) relayer traffic after any veto event, which is exactly the class of guard the external report's "challenge period" pivot warns about: a corrective mechanism for bad state must not itself weaken the invariant that false/stale state can never look freshly-trusted.

### Impact Explanation
The intended safety property — "once vetoed, only the correct next height can move forward, and no height can be silently rewritten" — is broken on EVM hosts. The veto/recovery mechanism, which exists specifically to correct a wrongly-accepted state root (the direct local analog of the Keystore `rootHash` bug), leaves the host's height bookkeeping in a state where old heights can be re-stored with a fresh timestamp, undermining the challenge-period guarantee that gates request/response processing across all EVM deployments of `EvmHost`.

### Likelihood Explanation
Triggering requires only a legitimate fisherman veto (a normal, expected operational event responding to any single bad commitment) followed by ordinary, already-permissionless relayer activity (`handleConsensus` has no caller restriction beyond `notFrozen`). No malicious relayer, prover, or admin action is required — the bug is in the EVM host's own state-transition logic, not in any external actor's behavior.

### Recommendation
Mirror the Substrate implementation: track and restore the actual previous known-good height (e.g., a `_previousStateMachineHeight` mapping) in `deleteStateMachineCommitmentInternal` instead of hardcoding `1`, and add a duplicate/overwrite guard in `HandlerV2.handleConsensus` (or `EvmHost.storeStateMachineCommitment`) so a height that already has a stored commitment cannot be silently rewritten by a later consensus proof.

### Proof of Concept
1. Let state machine `S` have `_latestStateMachineHeight[S] = 100`, with legitimate commitments already stored for heights `2..100`, and requests/responses already relying on those commitments' timestamps for challenge-period accounting.
2. A fisherman vetoes height `100` (fraudulent latest commitment) via `deleteStateMachineCommitment` → `_latestStateMachineHeight[S]` resets to `1` (see `evm/src/core/EvmHost.sol:719-721`).
3. Any relayer submits a normal, valid consensus proof whose `intermediates` include, e.g., height `50` (already legitimately committed and possibly already consumed by `handlePostRequests`). The check `latestHeight != 0 && intermediate.height > latestHeight` passes since `latestHeight` is now `1` (`evm/src/core/HandlerV2.sol:158-163`).
4. `storeStateMachineCommitment` overwrites `_stateCommitments[S][50]` and resets `_stateCommitmentsUpdateTime[S][50] = block.timestamp` (`evm/src/core/EvmHost.sol:687-699`), even though this height was already finalized/consumed.
5. Any pending or delayed `handlePostRequests`/`handleGetResponses` call gated on `challengePeriod` for height `50` now measures the delay from the new timestamp, effectively resetting the challenge-period clock the protocol relies on to prevent premature acceptance of state.

     * @dev Delete the state commitment at given state height.

    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }
