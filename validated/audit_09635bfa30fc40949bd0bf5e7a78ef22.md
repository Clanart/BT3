### Title
Panic on blame evaluation when the accusing recipient is the local participant — unregistered `enc_keys` indexing crashes the node - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
Analogous to the Elasticsearch advisory (malformed input to a processing API crashes the node), PedPoP's blame-resolution path crashes when it evaluates a blame accusation whose recipient (the "decryptor") is the local participant. `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with a `HashMap` that never contains an entry for the local party, so any malformed share sent to a participant — which legitimately triggers blame with that participant as recipient — panics the evaluator instead of attributing fault.

### Finding Description
`Decryption.enc_keys` is populated only via `Decryption::register`, which is called in `SecretShareMachine::verify_r1` for each remote participant's `EncryptionKeyMessage` — never for `self.params.i()` (the local party registers its key only inside `Encryption.enc_pub_key`, not in the `enc_keys` map) [1](#0-0) . When `KeyMachine::calculate_share` detects an invalid share, it returns `PedPoPError::InvalidShare { blame: Some(..) }`, and the protocol proceeds to evaluate the accusation through `BlameMachine::blame` → `blame_internal` [2](#0-1) . `blame_internal` calls `decrypt_with_proof(sender, recipient, msg, proof)`; when `proof` is `Some`, the DLEq verifier's second statement pair is built by indexing `self.enc_keys[&decryptor]` — evaluated eagerly, before any proof validation [3](#0-2) . If `recipient` is the local participant (the natural case: the local node is the accuser claiming its received share was invalid) — or any `Participant` index that was never registered — the `HashMap` index panics. Note `msg.pop.verify` must pass first [4](#0-3) , but an attacker can satisfy this by computing the `SchnorrSignature` PoP over its own ephemeral key, since `pop_challenge` is a public function of the context, sender index, and ciphertext bytes [5](#0-4) .

### Impact Explanation
A single malicious DKG participant can crash any honest party — and any node evaluating the resulting blame proof — simply by sending it a malformed `EncryptedMessage<C, SecretShare<C::F>>` (e.g., a correctly-PoP-signed ciphertext decrypting to a non-canonical or invalid share). Instead of producing `PedPoPError::InvalidShare`/attributing blame to the sender, `blame_internal` panics inside `decrypt_with_proof`. This is a remotely-triggered denial of service on the exact code path meant to handle malicious input — the same failure shape as CVE-2023-46673 (crafted input → node crash). It also degrades accountability: the crash prevents the honest party from obtaining blame attribution.

### Likelihood Explanation
Requires an attacker to be a DKG participant sending one malformed encrypted share to the victim; the victim's standard fault-handling flow (blame evaluation over an accusation where the victim is the recipient) hits the panic deterministically. Any out-of-range or unregistered `recipient`/`decryptor` participant index in a blame call reaches the same `HashMap` index panic. No collusion or privileged access is needed.

### Recommendation
Replace the infallible `self.enc_keys[&decryptor]` index with a fallible lookup (`get(&decryptor).ok_or(DecryptionError::InvalidProof)`), and register the local participant's own encryption public key into `Decryption.enc_keys` (or special-case `decryptor == i` to use `enc_pub_key`) so blame over messages addressed to the local node evaluates correctly. The same defensive lookup should apply to `self.commitments[&sender]` in `blame_internal` [6](#0-5)  and to `self.enc_keys[&participant]` in `Encryption::encrypt` [7](#0-6) , converting all attacker-influenced indexing into returned errors.

### Proof of Concept
1. Run a PedPoP `KeyGenMachine` for params `(t, n, i)`; complete `generate_secret_shares` normally.
2. Attacker `l` builds `EncryptedMessage<C, SecretShare<C::F>>` with a validly-signed PoP (`SchnorrSignature::sign` over a known ephemeral key, using `pop_challenge(context, R, key, l, msg)`) but whose ciphertext decrypts to a non-canonical `SecretShare` (e.g., all-`0xFF` bytes) — mirroring the test helper `invalidate_share_serialization` [8](#0-7) .
3. Victim `i` calls `KeyMachine::calculate_share`; decryption succeeds, `C::F::from_repr` fails → `InvalidShare { participant: l, blame: Some(proof) }` [9](#0-8) .
4. Evaluating the accusation — `BlameMachine::blame(sender=l, recipient=i, msg, Some(proof))` — calls `decrypt_with_proof`, which after the (valid) PoP check evaluates `self.enc_keys[&i]`; `i` was never inserted into `enc_keys`, so the process panics (indexing panic) rather than blaming `l`.

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
