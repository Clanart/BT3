### Title
Unhandled `KeyError` in `Offer.to_valid_spend()` when a crafted offer requests an asset with no matching offered coins - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.to_valid_spend()` indexes the offered-coins map with an unchecked, non-guarded dictionary lookup (`all_offered_coins[asset_id]`) for every asset in `requested_payments`, without verifying that the offered side actually produced a matching entry. A wallet user (offer counterparty) processing a maliciously crafted offer that requests an asset with an empty/zero payment amount, but with no coins detected on the "offered" side for that asset, triggers an unguarded `dict[key]` access that raises an unhandled `KeyError`, analogous to the GPAC bug class of dereferencing a lookup result without a NULL/None check.

### Finding Description
`Offer.is_valid()` only validates that `arbitrage()` values are non-negative: [1](#0-0) 

`arbitrage()` computes, per asset, `offered_amounts.get(asset_id, 0) - requested_amounts.get(asset_id, 0)`: [2](#0-1) 

Both `offered_amounts` and `requested_amounts` use `.get(..., 0)` defaults, so an asset_id present in `requested_payments` with an *empty* payment list (sum == 0) always satisfies `arbitrage[asset_id] >= 0` (0 - 0 = 0) even when `get_offered_coins()` never produced an entry for that asset_id at all (the heuristic in `_get_offered_coins()` only inserts a key when `coins_for_this_spend != []`, see lines 300-303).

`__post_init__` only checks for duplicate payments and that a `PuzzleInfo` driver exists for each requested asset — it does not require a non-empty payment list, and does not require a corresponding entry in the offered-coins map: [3](#0-2) 

`to_valid_spend()` then unconditionally indexes the offered-coins dict for every key in `requested_payments` without a `.get()`/None check: [4](#0-3) 

If `asset_id` is not a key in `all_offered_coins` (which can legitimately happen for an asset with zero requested amount and zero detected offered coins), this line raises an unhandled `KeyError`, aborting the function with an unchecked exception — the Python analog of a NULL pointer dereference on a lookup result that was never validated.

### Impact Explanation
This function is invoked in wallet code paths that process attacker-supplied offer data (a bech32m-encoded `Offer` object received from an untrusted counterparty):
- `TradeManager.respond_to_offer()` calls `complete_offer.to_valid_spend(...)` while accepting an incoming offer: [5](#0-4) 
- `TradeManager.calculate_tx_records_for_offer()` calls `offer.to_valid_spend()` when validating/processing an offer for transaction-record bookkeeping: [6](#0-5) 

A malicious offer counterparty can therefore trigger an unhandled exception in the recipient's wallet process while it is attempting to inspect/accept an offer, halting that request-handling flow (denial of service against the wallet's offer-processing/transaction-building pipeline). This does not directly enable unauthorized fund movement, but it matches the "spend-triggered transaction-processing halt" impact category allowed by scope.

### Likelihood Explanation
Likelihood is Medium: it requires crafting a syntactically valid `Offer` (passing `__post_init__`'s duplicate/driver checks and `is_valid()`'s arbitrage check) with a requested asset entry that has zero net value but for which the offered side never registers a matching key in `get_offered_coins()`. This is achievable by a counterparty directly constructing the serialized `Offer` bytes (bypassing the normal `notarize_payments`/`_create_offer_for_ids` construction path that only wallet code uses), since offers are exchanged as raw serialized data and only reconstructed via `Offer.from_bytes`/`from_bech32`, not built through the higher-level API on the receiving end.

### Recommendation
In `Offer.to_valid_spend()`, use `all_offered_coins.get(asset_id, [])` instead of `all_offered_coins[asset_id]`, and explicitly reject (raise a controlled `ValueError`) offers whose `requested_payments` contain an asset_id with no corresponding offered coins and no arbitrage credit, rather than letting a `KeyError` propagate. Additionally, `Offer.__post_init__`/`is_valid()` should reject requested-payment entries with empty payment lists or otherwise ensure every asset present in `requested_payments` has a corresponding, non-empty entry produced by `get_offered_coins()`.

### Proof of Concept
1. Construct a `WalletSpendBundle` whose coin spends only produce settlement-payment coins for asset A (e.g., XCH), with no coins for asset B.
2. Construct `requested_payments = {A: [<normal payment>], B: []}` (asset B present as a key with an empty payment list) and a `driver_dict` containing a valid `PuzzleInfo` for B (to pass the `__post_init__` check).
3. Serialize this as an `Offer` (bypassing `notarize_payments`, directly constructing the `Offer` dataclass/bytes) and deliver it to a victim wallet as an offer file/bech32m string.
4. Victim calls `respond_to_offer()` (or any flow that calls `calculate_tx_records_for_offer(offer, True)` / `to_valid_spend()`) on the received offer.
5. `arbitrage()[B] == 0 - 0 == 0` passes `is_valid()`, but `all_offered_coins[B]` raises `KeyError` inside `to_valid_spend()`, propagating as an unhandled exception in the wallet's offer-processing code path.

```python
    def arbitrage(self) -> dict[bytes32 | None, int]:
        """
        Returns a dictionary of the type of each asset and amount that is involved in the trade
        With the amount being how much their offered amount within the offer
        exceeds/falls short of their requested amount.
        """
        offered_amounts: dict[bytes32 | None, int] = self.get_offered_amounts()
        requested_amounts: dict[bytes32 | None, int] = self.get_requested_amounts()

        arbitrage_dict: dict[bytes32 | None, int] = {}
        for asset_id in [*requested_amounts.keys(), *offered_amounts.keys()]:
            arbitrage_dict[asset_id] = offered_amounts.get(asset_id, 0) - requested_amounts.get(asset_id, 0)

        return arbitrage_dict
```
