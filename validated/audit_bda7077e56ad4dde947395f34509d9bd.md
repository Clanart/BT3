### Title
`ReceivedOutput::read` accepts an arbitrary scalar `offset` without verifying it derives the output's `script_pubkey`, so untrusted bytes can register outputs the multisig cannot spend - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The Serai analog of "refund claimed by a party that never joined" is an output *credited* to the threshold group without proving the group actually controls it. In `networks/bitcoin`, ownership is expressed as a scalar `offset` such that `key + offset*G` must map to the output's `p2tr` `script_pubkey`. `Scanner::scan_transaction` only produces `ReceivedOutput`s where this invariant holds by construction (`networks/bitcoin/src/wallet/mod.rs:199-214`), but `ReceivedOutput::read` (`mod.rs:122-134`) deserializes `offset`, `output`, and `outpoint` from raw bytes with no consistency check. Any attacker-controlled `ReceivedOutput` encoding is accepted as a spendable received output.

### Finding Description
`ReceivedOutput::read` performs only `Secp256k1::read_F` for the offset and consensus-decodes the `TxOut`/`OutPoint`; it never recomputes `p2tr_script_buf(scanner_key + GENERATOR * offset)` and compares against `output.script_pubkey`, and it stores no binding to the group key at all (`mod.rs:122-134`). Downstream, `send.rs`/`SignableTransaction` re-keys each input by `output.offset()` to produce the TapTweak key for the BIP-341 signature. If the offset does not correspond to the script_pubkey, the tweaked key is wrong and the input is unspendable — yet the scanner/processor path has already accounted it as funds received (`processor/src/networks/bitcoin.rs:686-700` consumes `scanner.scan_transaction`, and the serialized form round-trips through `ReceivedOutput::read` per `networks/bitcoin/tests/wallet.rs:73-75`). This is the same root cause class as the reference bug: a value-bearing claim (refund / received output) is honored without validating that the claimant descriptor (join record / key-deriving offset) actually entitles the party to the funds.

### Impact Explanation
An attacker able to feed crafted bytes to `ReceivedOutput::read` (e.g., any channel carrying serialized outputs into a processor/signer instance) can cause the group to treat outputs as spendable inputs when the implied tweaked key does not match the `script_pubkey`. Depending on the consumer this yields (a) funds reported received that are not spendable — the group signs a transaction spending an input it cannot authorize, stalling or burning fees — or (b) misattribution of a foreign output to the group's balance, corrupting accounting before a `sign_share` round. This is a Medium-severity integrity flaw: it does not leak key material, but it breaks the "received ⇒ spendable" invariant the wallet relies on.

### Likelihood Explanation
Reachability requires attacker influence over bytes passed to `ReceivedOutput::read`; the constructor-side path (`Scanner::scan_transaction`, `mod.rs:199-214`) is safe because it derives `offset` from the registered `scripts` map. I was unable to confirm within this index an external untrusted-byte path calling `ReceivedOutput::read` in production (its only observed use is DB/test round-tripping), so likelihood is moderate-to-low and contingent on integrator/storage exposure of serialized outputs.

### Recommendation
Bind `ReceivedOutput` to its key: either store the group key (or a hash of it) in the encoding, or add a `ReceivedOutput::new(key, offset, output, outpoint)` constructor plus a `verify(key)` method that recomputes `p2tr_script_buf(key + GENERATOR * offset)` and rejects on mismatch, and call it after every `ReceivedOutput::read` of untrusted/DB bytes. Also reject odd-parity derived keys (the `None` case of `p2tr_script_buf`, `mod.rs:80-86`).

### Proof of Concept
```rust
// networks/bitcoin: attacker supplies bytes to ReceivedOutput::read
let key = Scanner::new(group_key).unwrap(); // even group key

// Craft a ReceivedOutput: a real txout paying to an ATTACKER script
// (or a group script) combined with a mismatched offset.
let mut bytes = Vec::new();
bytes.extend(wrong_offset.to_bytes());        // offset != script-derived offset
bytes.extend(serialize(&foreign_txout));      // script_pubkey not key+offset*G
bytes.extend(serialize(&outpoint));

let output = ReceivedOutput::read(&mut bytes.as_slice()).unwrap(); // accepted
// `output.offset()` does not derive `output.output().script_pubkey`;
// any SignableTransaction built on it is unspendable, while the
// pipeline has already counted `output.value()` as received funds.
```
Note: the concrete exploitable consumer of attacker-controlled `ReceivedOutput` bytes could not be confirmed from the indexed code; the finding stands on the missing invariant check in `read` itself.
