### Title
Zero-amount escrow entries created via `placeOrder` predispatch path permanently brick `withdraw()`, locking solver payouts and user refunds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron-targeted `IntentGatewayV2.sol` allows a user to place an order whose predispatch branch escrows a **zero-amount** input token entry under an order commitment. The shared `withdraw()` function used both for cross-chain fill settlement (`RedeemEscrow`) and refund (`RefundEscrow`) unconditionally reverts whenever it encounters a token whose escrowed balance reads as `0`. This is the same broken invariant as the reported UniswapV3 "non-liquidable vault" bug: an unchecked, zero-valued asset is accepted into custody, and a mandatory downstream unwind operation (there `decreaseLiquidity`, here `withdraw`) hard-reverts on exactly that zero value, permanently blocking settlement for a third party who has already provided real value.

### Finding Description
`placeOrder` has two branches for escrowing inputs:

- The non-predispatch branch explicitly rejects zero-amount inputs: [1](#0-0) 

- The predispatch branch, however, computes `requiredAmount`/`reducedInputs[i].amount` and stores it into escrow **without ever checking it is non-zero**: [2](#0-1) 

Because the balance check is `if (balance < requiredAmount) revert ...`, a `requiredAmount` of `0` always trivially passes, and `_orders[commitment][token] += reducedInputs[i].amount` stores a `0` entry for that token under the commitment. Nothing rejects `order.inputs[i].amount == 0` on this path.

Later, when the order is filled cross-chain and the destination dispatches a `RedeemEscrow` (or the user/anyone dispatches a `RefundEscrow`), the source-chain `onAccept()` routes to `withdraw()`: [3](#0-2) 

`withdraw()` iterates every token in the request and, critically, does **not** skip zero-amount entries — it instead uses a zero *escrow balance* as an "unknown order" guard and reverts the entire call: [4](#0-3) 

Because the token entry created above has `_orders[commitment][token] == 0` by construction, `withdraw()` always hits `revert UnknownOrder()` for that token, aborting the whole loop — including the release of the other, legitimately-escrowed, non-zero tokens in the same order. This is functionally identical to the audited bug: an attacker can put a "zero-liquidity" asset into an escrow that is guaranteed to be included in every future settlement/refund message for that commitment, and the mandatory redemption/refund logic (`withdraw`) has a hard requirement (non-zero escrow) that this crafted entry can never satisfy — permanently bricking that code path.

Notably, the newer `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` already defends against exactly this by skipping zero amounts: [5](#0-4) 

The presence of this explicit `if (amount == 0) continue;` guard in the newer contract, absent from the Tron contract's `withdraw()`, indicates the zero-amount escrow hazard is a real, previously-relevant class of bug in this codebase that was not backported to the Tron/legacy `IntentGatewayV2.sol`.

### Impact Explanation
- A solver who fills the crafted cross-chain order on the destination chain delivers real output tokens to the beneficiary, but the `RedeemEscrow` settlement message on the source chain will permanently revert in `onAccept → withdraw`, so the solver's escrowed input payout can never be released — direct loss of funds for the solver.
- Because `_filled[commitment]` is only set on the source chain inside the same reverting `withdraw()` call, the source chain never learns the order was filled. This blocks the legitimate `cancelOrder` "from source" path as well (the destination-side `_filled` state will show it was filled, so the proof-based cancel-from-source flow will also fail with `Filled()`), leaving the escrowed tokens permanently stuck in the contract, benefiting no one — a logic attack producing fund lock/loss, matching the bounty's "stealing or loss of funds" / "logic attacks" impact classes.
- This is reachable by any ordinary, unprivileged order-placing user with no malicious relayer, prover, or admin involvement — it only requires crafting an `Order` with a `predispatch.call` and one zero-amount `inputs[]` entry.

### Likelihood Explanation
High. `placeOrder` is a fully public entrypoint. The zero-amount input is a normal, well-formed field value (`uint256` defaulting to/being explicitly set to `0`) that is never rejected in the predispatch branch, unlike its sibling non-predispatch branch which does check for it — indicating this is an oversight rather than an intended design difference. Triggering the downstream revert requires no special timing or race condition; it fires deterministically the first time `withdraw()` is invoked for that commitment.

### Recommendation
1. In `placeOrder`'s predispatch escrow loop, reject `order.inputs[i].amount == 0` the same way the non-predispatch branch does, and additionally guard against a fee-driven `reducedInputs[i].amount` of zero.
2. In `withdraw()`, skip (`continue`) token entries whose `amount` is `0` instead of relying on `_orders[commitment][token] == 0` as an "unknown order" signal, mirroring the guard already present in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`.
3. Audit all EVM/Tron variants of the Intent Gateway contracts for consistency with the hardened `IntentsBase.sol` logic before/along with Tron deployment.

### Proof of Concept
1. User calls `placeOrder(order, graffiti)` on the Tron `IntentGatewayV2` where:
   - `order.predispatch.call.length > 0` and `order.predispatch.assets.length > 0` (any valid predispatch swap),
   - `order.inputs` contains at least one legitimate non-zero entry (e.g., 1000 USDC) plus one entry with `amount == 0` for another token (e.g., DAI).
   - The predispatch branch (`evm/tron/contracts/apps/IntentGatewayV2.sol:383-440`) escrows `_orders[commitment][DAI] = 0` without reverting.
2. A solver calls `fillOrder` on the destination chain, delivering the requested output assets to the beneficiary and dispatching a `RedeemEscrow` `WithdrawalRequest` back to source that includes the DAI token entry (amount 0) alongside the USDC entry.
3. On the source chain, `onAccept()` → `withdraw()` iterates `body.tokens`; when it reaches the DAI entry, `_orders[commitment][DAI] == 0` triggers `revert UnknownOrder()` (`evm/tron/contracts/apps/IntentGatewayV2.sol:691`), reverting the whole call and permanently blocking release of the USDC escrow to the solver.
4. Because `_filled[commitment]` was never set on source, any later cancel-from-source attempt fails since destination-side state shows the order as filled — the escrowed USDC is now permanently unrecoverable by either party.
