### Title
Scanner reports immature coinbase outputs as received/spendable, letting the wallet build transactions the network will reject - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class in the reference report is "an amount credited for a period is bounded by when a rollover happens to be triggered, not by the actual boundary." In `bitcoin-serai`, the analogous shape is `Scanner::scan_block`, which scans `block.txdata` including `txdata[0]` — the coinbase transaction. Outputs of a coinbase transaction are not spendable until 100 blocks of maturity, yet `scan_block` returns them as ordinary `ReceivedOutput`s indistinguishable from immediately spendable ones.

### Finding Description
`Scanner::scan_block` iterates over every transaction in the block without checking `tx.is_coinbase()`:

```rust
// networks/bitcoin/src/wallet/mod.rs
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

`scan_transaction` (lines 199–214) matches on `output.script_pubkey` only, so a miner-paying output to a registered offset script in the coinbase is pushed into the result set with a valid `offset`, `output`, and `outpoint`. Downstream, `sign`/`TransactionMachine` in `send.rs` treats every `ReceivedOutput` as a spendable input. A transaction built spending an immature coinbase output fails Bitcoin's `bad-txns-premature-spend-of-coinbase` consensus check.

Like the OTLM bug — where `epochRewardsPerTokenStart` of the *next* epoch (sampled at trigger time) was used instead of a value fixed at the epoch end boundary — here the credited set is bounded by what `scan_block` happens to see, not by the spendability boundary (coinbase maturity) of the outputs.

### Impact Explanation
Any unprivileged party can send a Bitcoin transaction paying to the validator set's tweaked Taproot key — and a miner can place such an output in the coinbase transaction of a block. The scanner then reports that output as received, and the wallet's signing pipeline will attempt to spend it before maturity, producing a transaction that is invalid per consensus. Result: funds reported received that are not spendable, and a transaction the processor signs for a spend that cannot confirm.

### Likelihood Explanation
Coinbase outputs paying a registered offset script are uncommon but fully attacker-influenceable: the payer only needs the script (derivable from the known group key plus any registered offset). On regtest/signet mining and in any deployment where miners or pools pay arbitrary scripts, the condition is trivially reachable. The code comment itself acknowledges the gap ("If received outputs must be immediately spendable, a post-processing pass is needed"), but no in-scope caller performs that pass, so the unsafe default stands.

### Recommendation
Split scanning into spendable and immature results: skip `block.txdata[0]` in `scan_block`, or tag `ReceivedOutput` with a maturity flag and have the wallet's `sign` path reject inputs whose outpoint belongs to a coinbase transaction younger than 100 confirmations. Prefer scanning `block.txdata[1 ..]` by default and exposing coinbase scanning only behind an explicit API.

### Proof of Concept
1. Derive the P2TR `ScriptBuf` for the wallet's group key via `p2tr_script_buf` (or via a registered offset).
2. Construct a block whose `txdata[0]` (coinbase) pays to that script.
3. Call `Scanner::scan_block(&block)` — it returns a `ReceivedOutput` for the coinbase output with no maturity distinction.
4. Feed that `ReceivedOutput` into the wallet send path (`send.rs`); the produced transaction spends an immature coinbase and is rejected by `testmempoolaccept`/consensus as `bad-txns-premature-spend-of-coinbase`.
