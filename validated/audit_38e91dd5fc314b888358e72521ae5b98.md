### Title
`eth_getLogs`/`eth_getFilterLogs`/`eth_subscribe("logs")` `FilterCriteria.Addresses` has no upper bound, enabling RPC-node CPU exhaustion - (File: `evmrpc/filter.go`, `evmrpc/ethbloom/bloom.go`)

### Summary
Sei's EVM JSON-RPC log-filtering surface bounds request byte size, block range, log count, and log bytes, but never bounds the number of entries in `FilterCriteria.Addresses`. Any unprivileged client can submit `eth_getLogs`, `eth_getFilterLogs`, or `eth_subscribe("logs")` with tens of thousands of addresses; every candidate log is then matched against the full address list, and every address is Keccak256-hashed on every call to build the bloom index, making the compute cost scale linearly (or worse) with attacker-controlled input size and directly hitting the RPC worker pool for every incoming request.

### Finding Description
`FilterAPI.GetLogs` accepts an arbitrary `filters.FilterCriteria` and forwards it straight to `LogFetcher.GetLogsByFilters` without validating `len(crit.Addresses)`: [1](#0-0) 

The block-range, budget, and backpressure checks that follow only bound `blockRange`, pending task counts, and semaphore usage — none of them look at `len(crit.Addresses)`: [2](#0-1) 

For every block-by-block fallback (and for the range-query normalization path), the address list is fed into `EncodeFilters`, which runs a Keccak256 hash (`calcBloomIndexes`) for **every address in the request**, on every call: [3](#0-2) 

Every candidate log is then checked against the full, unbounded address list with a linear scan in `MatchesCriteria`/`matchLog`: [4](#0-3) [5](#0-4) 

This same unbounded `crit.Addresses` is reused for the tag-index lookup path and for the fallback per-block/per-receipt scan in `collectLogs`/`normalizeRangeQueryLogs`: [6](#0-5) [7](#0-6) 

The same unbounded criteria is also passed straight through for `eth_subscribe("logs")` and the `eth_getFilterLogs`/blockHash single-shot path: [8](#0-7) [9](#0-8) 

Unlike `minievm`'s `maxTopics` constant (referenced in the external report), there is no equivalent `maxAddresses`/`MaxAddresses` config knob anywhere in `evmrpc/config/config.go` — the config exposes `MaxLogNoBlock`, `MaxLogBytes`, `MaxBlocksForLog`, `MaxFilters`, etc., but nothing constrains the size of the `Addresses` (or `Topics`) array supplied in a single request.

The only mitigating control is `MaxRequestBodyBytes` (default 5 MiB rather than the ~10 MiB assumed in the report): [10](#0-9) 

Using the report's own byte-accounting formula (`45n + 1` bytes for `n` 20-byte hex addresses), a 5 MiB body still permits roughly **116,000 addresses** in a single request — comfortably enough to force tens of thousands of Keccak256 hash operations plus O(addresses × logs × blocks) linear scans per RPC call, all executed on the shared worker pool that also serves other RPC clients.

### Impact Explanation
This does not cause fund loss or consensus divergence, but it satisfies the "crash of default-configuration RPC nodes" bar: a single unauthenticated JSON-RPC caller can force massive, repeatable CPU consumption (Keccak256 hashing plus O(n) linear matching per log, multiplied by block range and receipt count) on any default-configured public EVM RPC node, degrading or halting RPC availability for all other users of that node — the same bug class and severity Code4rena rated Medium/High in `minievm`.

### Likelihood Explanation
Trivial to trigger: any public JSON-RPC client can issue `eth_getLogs`/`eth_getFilterLogs`/`eth_subscribe` with a large `address` array in a normal HTTP/WS request within the default 5 MiB body limit, with no authentication, staking, or gas cost required, and can repeat the request indefinitely.

### Recommendation
Add an explicit `MaxAddresses` (analogous to the existing `MaxLogNoBlock`/`MaxBlocksForLog` config knobs) and reject `FilterCriteria.Addresses` (and ideally `Topics` entries) beyond that bound in `FilterAPI.GetLogs`, `SubscriptionAPI.Logs`, `FilterAPI.NewFilter`, and `FilterAPI.GetFilterLogs` before any bloom/hash work is performed, mirroring the fix applied by Initia (`minievm` PR #165) for the same bug class.

### Proof of Concept
1. Configure a Sei EVM RPC node with default settings (`MaxRequestBodyBytes` = 5 MiB, no address limit).
2. Send `eth_getLogs` with `fromBlock`/`toBlock` spanning a modest range and `address` populated with ~100,000 distinct hex addresses (fits within the 5 MiB body limit per the `45n+1` byte formula).
3. Observe that `evmrpc/ethbloom/bloom.go`'s `EncodeFilters` performs a Keccak256 hash per address and `MatchesCriteria`/`matchLog` performs a linear scan per candidate log per address, with no rejection based on `len(crit.Addresses)` anywhere in `evmrpc/filter.go` or `evmrpc/config/config.go`; repeated concurrent requests exhaust the RPC worker pool/CPU for the node.

```go
// EncodeFilters builds bloom-index slices from filter criteria.
// Result semantics: AND on outer level, OR on mid level, AND on inner level (all 3 bits).
func EncodeFilters(addresses []common.Address, topics [][]common.Hash) (res [][]BloomIndexes) {
	filters := make([][][]byte, 1+len(topics))
	if len(addresses) > 0 {
		filter := make([][]byte, len(addresses))
		for i, address := range addresses {
			filter[i] = address.Bytes()
		}
		filters = append(filters, filter)
	}
	for _, topicList := range topics {
		filter := make([][]byte, len(topicList))
		for i, topic := range topicList {
			filter[i] = topic.Bytes()
		}
		filters = append(filters, filter)
	}
```
