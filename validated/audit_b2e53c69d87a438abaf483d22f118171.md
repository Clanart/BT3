### Title
Panic on identity nonce commitments crashes FROST signing via BIP-340 `Hram`/`x_only` - (File: `networks/bitcoin/src/crypto.rs`)

### Summary
CVE-2024-11169 is an unhandled-exception-on-crafted-input → server crash in a file-upload path. The Serai analog is a reachable panic (unhandled `expect` on the point at infinity) triggered by untrusted, unauthenticated preprocess bytes fed to the FROST signing state machine. A malicious signing-set participant submits a `Preprocess` whose `Commitments` are the group identity; `Commitments::read` / `C::read_G` accept the identity encoding, no `is_identity` check exists in `AlgorithmSignMachine::sign`, and the resulting aggregate nonce `R` is the identity point. The Bitcoin Schnorr `Algorithm`'s `Hram::hram` unconditionally calls `x(&R)`, which does `encoded.x().expect("point at infinity")` (`networks/bitcoin/src/crypto.rs:13-16`), and `x_only` does `XOnlyPublicKey::from_slice(...).expect("x_only was passed a point which was infinity or odd")` (`crypto.rs:21-23`). This panics the signing thread — an unhandled exception reachable entirely from peer-controlled bytes.

### Finding Description
- `read_preprocess` deserializes peer preprocesses via `Commitments::read::<_>(reader, &nonces)` (`crypto/frost/src/sign.rs:276-281`). `C::read_G` only rejects non-canonical encodings, not the identity (`crypto/ciphersuite/src/lib.rs:91-101`); the identity is a canonical Ristretto/secp256k1 encoding.
- `sign` validates only set membership/order (`included` bounds, duplicates via `validate_map`) and transcripts each commitment (`crypto/frost/src/sign.rs:290-358`). No code rejects identity `D`/`E` commitments, even though FROST requires it.
- Binding factors `B` are computed via `rho_transcript` (`sign.rs:362-379`) and `Rs = B.nonces(&nonces)` (`sign.rs:383`). If a participant sends `D_l = identity, E_l = identity`, their bound nonce `R_l = D_l + ρ_l·E_l = identity` deterministically — no grinding needed, because `ρ_l` multiplies the identity.
- `IetfSchnorr::sign_share`/`verify`/`verify_share` evaluate `Hram::hram(R, A, m)` over these nonce sums; `hram` calls `x(R)`/`x(A)` which `expect("point at infinity")` (`networks/bitcoin/src/crypto.rs:59-73`, `13-16`). `verify` also runs `needs_negation(&sig.R)` (`crypto.rs:145-149`), but the panic fires earlier in `hram`.
- The file itself documents the hazard — "This may panic if called with nonces/a group key which are the point at infinity (which have a negligible probability... even with malicious participants present)" (`crypto.rs:78-83`) — but the assumption is wrong: with identity commitments the identity nonce is deterministic, not probabilistic.

### Impact Explanation
Any participant in a FROST signing session (an unprivileged party able to send `read_preprocess` bytes, e.g., a co-signer in a Bitcoin multisig using `bitcoin_serai::crypto::Schnorr`) can crash the processor handling the session by broadcasting `Preprocess { commitments: [identity; 2], addendum }`. The panic unwinds through `sign_share`/`complete`/`verify_share`, denying service to the honest node — the same crash-on-crafted-request class as the CVE, mounted through `Commitments::read` → `sign`/`verify` rather than `fs`.

### Likelihood Explanation
Deterministic and low-effort: requires only a valid participant slot and sending two canonical identity-point encodings in a preprocess. Reachability is `read_preprocess` → `sign` → `B.nonces` → `algorithm.sign_share` → `Hram::hram` → `x()` → `expect` panic. Not fully certain items: (a) whether an identity-commitment check exists elsewhere in `Commitments`/`BindingFactor` code I could not fully read (`crypto/frost/src/nonce.rs`); (b) whether callers wrap these calls in `catch_unwind`. If either holds, impact drops.

### Recommendation
Reject identity points in `Commitments::read`/`read_preprocess` (and any nonce contribution to `B.nonces`), per FROST §4.1 ("fail if the commitment is the identity"). Defense in depth: make `x()`/`x_only` return `Option`/`io::Result` and propagate `FrostError::InvalidCommitment` instead of panicking, since `hram` operates on attacker-influenced points.

### Proof of Concept
```rust
// Signer P_malice is in the included set for a Secp256k1 Bitcoin multisig.
// Craft a preprocess whose two nonce commitments are both the identity point.
let identity = Secp256k1::generator() * Secp256k1::read_F(&mut &[0u8;32][..]).unwrap_or(...); // or construct identity directly
let mut bytes = vec![];
bytes.extend_from_slice(ProjectivePoint::IDENTITY.to_encoded_point(true).as_bytes()); // D = I
bytes.extend_from_slice(ProjectivePoint::IDENTITY.to_encoded_point(true).as_bytes()); // E = I
// addendum for bitcoin Schnorr is ()

// Honest node:
let preprocess: Preprocess<_, _> = machine.read_preprocess(&mut bytes.as_slice()).unwrap(); // OK
map.insert(malicious_i, preprocess);
machine.sign(map, msg)?; // B.nonces -> R = I; Hram::hram -> x(&R) -> panic: "point at infinity"
```
The identity point's compressed encoding (`0x02 || 0*32` on secp256k1; the identity encoding on Ristretto) is canonical, so `read_G` accepts it, and `R_l = D_l + ρ_l·E_l = I` for every `ρ_l`.
