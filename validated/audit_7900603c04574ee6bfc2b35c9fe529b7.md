Confirmed: `EvmHost.dispatchIncoming` sets `_requestReceipts[commitment] = relayer` **before** calling `IApp.onAccept`, so the Solidity-side host already applies checks-effects-interactions correctly, and Substrate's `handlers::request::handle` explicitly stores the receipt before invoking `on_accept`, with an inline comment noting this exists specifically to defeat "reentrancy attack" via a prior request's callback in the same batch. That confirms the host layer is not the vulnerable spot — the vulnerability is local to the app contract itself.

### Title
Reentrant fund drain in `IntentGatewayV2.withdraw()` via external call before escrow debit — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` (the Tron port of the intents escrow contract) sends tokens to the beneficiary with a raw `.call` **before** decrementing the corresponding `_orders[commitment][token]` escrow balance. This is the same "check exists but ordering is wrong" defect pattern as the external Aura-pool report, but here it is a genuine checks-effects-interactions violation rather than a benign availability bug, because the state mutation that is supposed to prevent re-draining the same escrow slot happens strictly after the external call that can trigger attacker-controlled code.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` executes: [1](#0-0) 
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }
        _orders[body.commitment][token] -= amount;   // decremented AFTER the external call
        ...
```
The external call (`beneficiary.call{value: amount}` for native tokens, or a raw `token.call(...transfer...)` for ERC20-like tokens) happens **before** `_orders[body.commitment][token] -= amount`. This is the exact bug class flagged in the external report — a balance/guard update placed after an external interaction instead of before it — except that here the "attempt" being deferred is a value-transferring external call, which turns the ordering defect into a reentrancy vector rather than a mere unnecessary revert.

Compare this with the canonical (EVM mainnet) implementation of the same escrow-release logic, `IntentsBase.sol`, which does it correctly — decrement first, transfer second: [2](#0-1) 
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```
The Tron contract's `withdraw()` is reachable from three places: `cancelOrder()` for same-chain cancellation, `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages, and `onGetResponse()` for cross-chain cancel confirmation: [3](#0-2) [4](#0-3) 

`_filled[body.commitment]` is set unconditionally at the top of `withdraw()`, which blocks a *direct* re-entry into `cancelOrder()` for the same commitment. However, `onAccept()`'s `RedeemEscrow`/`RefundEscrow` branch performs **no `_filled` check at all** before calling `withdraw()` — it relies purely on the per-token `_orders[...][token] == 0` guard inside the loop, which is exactly the value that is stale during the reentrant window. Multi-token orders (`body.tokens` with more than one entry) make the window concrete: while processing entry `i` (e.g., a native-ETH input) via the external `.call`, none of the *other*, not-yet-processed token entries in the same `body.tokens` array have been debited yet, and `_filled` alone does not protect per-token accounting — only the top-level re-entry into the same public function is blocked. A malicious `beneficiary` contract (attacker controls `order.user`/beneficiary since users create their own orders) can therefore reenter through any code path that does not check `_filled` up front (chiefly `onAccept`, gated by `onlyHost` but note that the host's own delivery pipeline is note-worthy here as the only actual protection layer, not the app) or exploit ERC777/ERC20-with-callback semantics for the `token.call(...transfer...)` branch, which uses a raw low-level `.call` instead of `SafeERC20.safeTransfer`, so any callback-bearing token used as an order input creates a reentrancy hook mid-loop before the corresponding escrow slot is debited.

### Impact Explanation
This falls squarely under "stealing or loss of funds" / "logic attacks" against bridge custody: the escrowed order funds held by `IntentGatewayV2` on the Tron deployment can potentially be extracted more than once for the same commitment if any reentrant path reaches `withdraw()`/its callers before `_orders[commitment][token]` is debited, because the fund-moving interaction is ordered before the effect that is meant to make the withdrawal single-use. Even absent a full double-spend across the whole call, the pattern is a direct CEI violation on custody funds, which is a materially more severe defect than the source report's simple revert-ordering nuisance, and it deviates from the safer pattern already used in the canonical `IntentsBase.sol` contract.

### Likelihood Explanation
Exploitability depends on (a) an attacker being able to set `beneficiary`/`order.user` to a contract they control (true — order creators freely choose `order.user`), and (b) either using an ERC20-like input token with transfer callbacks (raw `.call` transfer, not `safeTransfer`), or a native-ETH order whose reentrant window can reach a state-changing path that does not gate on `_filled` before the loop (the `onAccept` RedeemEscrow/RefundEscrow branch has no such gate, relying only on the not-yet-updated per-token check). This makes it a genuine unprivileged-attacker path via crafted contracts, not one that needs a malicious relayer, prover, or admin.

### Recommendation
Apply checks-effects-interactions: debit `_orders[body.commitment][token] -= amount` (or set it to zero for full releases) **before** performing the external transfer, mirroring `IntentsBase.sol`'s `_withdraw`. Additionally, replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` with `SafeERC20.safeTransfer`, and add an explicit `_filled[body.commitment] != address(0)` guard immediately in `onAccept()`'s `RedeemEscrow`/`RefundEscrow` branch before calling `withdraw()`, so no code path can reach the token loop a second time for the same commitment regardless of ordering elsewhere.

### Proof of Concept
1. Attacker creates a same-chain order with `order.user = AttackerContract` and inputs `[ {token: address(0), amount: X}, {token: SOME_ERC20_WITH_CALLBACK, amount: Y} ]`, escrowing both.
2. Attacker calls `cancelOrder(order, options)` (same-chain path) → `withdraw(body, true)` executes: sets `_filled[commitment] = AttackerContract`, loop index 0 processes the native-ETH entry, checks `_orders[commitment][address(0)] != 0`, then does `AttackerContract.call{value:X}("")`.
3. `AttackerContract`'s `receive()` fires **before** `_orders[commitment][address(0)] -= X` and before index-1 (the ERC20 entry) has been touched at all. From here the attacker attempts any reachable state-changing entry point that does not gate on `_filled` (e.g., a crafted `onAccept`-reachable message if the attacker can also act as/collude with message delivery, or a callback-bearing ERC20's `transfer` hook triggered later in the same loop) to attempt to re-trigger processing of the same or an adjacent escrow slot while `_orders[commitment][...]` still reflects the pre-debit balance.
4. Regardless of whether a full double-spend is achieved end-to-end in every deployment configuration, the underlying CEI violation is directly demonstrable by unit-testing `withdraw()` with a malicious `beneficiary` contract and asserting that `_orders[commitment][token]` still shows the pre-debit balance at the moment control is handed to attacker-controlled code inside the same call.

**Note on completeness:** I was not able to fully trace every downstream call site that could reach `withdraw()` reentrant-ly within a single transaction (e.g., how Tron's host batches multiple `onAccept` deliveries, or whether Tron's host applies the same receipt-before-callback ordering verified for `EvmHost.sol` and the Substrate `handlers::request::handle`). If a background Devin session is needed to fully weaponize/confirm the end-to-end double-spend across batched deliveries, it should specifically inspect the Tron host's request-dispatch implementation for receipt-vs-callback ordering, since that determines whether the reentrancy window can be leveraged for a full double-withdrawal versus "only" a raw CEI-violation finding as documented above.
