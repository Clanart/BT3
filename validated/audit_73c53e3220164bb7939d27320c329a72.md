### Title
Clone destination "sensitive location" guard is a pure string comparison that git itself does not honor, allowing the same path-traversal-to-sensitive-directory attack it claims to block - ([File: app/src/lib/git/clone.ts])

### Summary
The bootfinance bug is a "sanity check" whose comparison logic doesn't actually enforce the invariant it claims to (comparing values in a way that can never trip for real inputs, so the guard is decorative). The Desktop analog is `isClonePathSensitive` in `app/src/lib/git/clone.ts`, a "backstop against path traversal" that decides whether a resolved clone destination is a sensitive system directory (`~/.ssh`, `~/.gnupg`, `~/.config`, `%APPDATA%`, etc.) purely by lexical string comparison on `Path.resolve(path).toLowerCase()`, with no filesystem canonicalization (no `realpath`, no OS-level normalization). ### Finding Description
`isClonePathSensitive` is invoked at the top of `clone()` and is the only guard preventing a crafted repository URL from directing `git clone` into a sensitive directory such as `~/.ssh` or `~/.gnupg`: [3](#0-2) 

The destination path passed into `clone()` originates from `sanitizeCloneName`, which derives a single path component from an attacker-controlled remote URL (owner/name or clone URL), and is then joined with a base directory chosen in the UI: [4](#0-3) 

`isClonePathSensitive` compares this joined path against a fixed list of sensitive directories using pure string equality/`startsWith`: [2](#0-1) 

Unlike the sibling function `resolveWithin` in `app/src/lib/path.ts`, which calls `fs/promises.realpath` on both the root and the resolved path before comparing them, `isClonePathSensitive` never resolves the real filesystem path. This is the same class of defect as the bootfinance finding: a guard that looks like it enforces a bound, but the comparison operates on a representation of the value that doesn't match what the underlying system actually consults, so it never actually blocks the case it's designed for.

Concretely:
- `Path.resolve()` is purely lexical. On Windows, trailing dots and trailing spaces in a path segment are silently stripped by the OS/filesystem APIs when the directory is actually created (e.g. `C:\Users\victim\.ssh ` and `C:\Users\victim\.ssh.` both physically resolve to `C:\Users\victim\.ssh`), but `isClonePathSensitive`'s string comparison treats these as different, non-matching paths, so `clonePath === sensitive` and `clonePath.startsWith(sensitive + Path.sep)` both fail to match even though `git clone` will ultimately write into the real `.ssh` directory.
- `sanitizeCloneName` does not strip trailing dots/spaces from the last URL path component (it only strips `.git` suffix and rejects `.`/`..`), so a remote URL such as `https://evil.com/owner/.ssh.` or `.../owner/.ssh%20` (a name an attacker fully controls when a victim uses "Clone in Desktop"/"Open in Desktop" or pastes a URL) can pass through both `sanitizeCloneName` and `isClonePathSensitive` unmolested, while the OS-level directory that `git clone` actually creates and populates is `.ssh`.

This aligns with the "Valid Impact" scope: the attacker fully controls the git remote URL (a link/deep link or manually supplied clone URL) and the outcome is a file write outside of the intended repository directory into the user's SSH/GPG/git-config directories.

### Impact Explanation
If exploited, `git clone` (with `--recursive`) can write attacker-supplied file content directly into `~/.ssh` or `~/.gnupg`, e.g. overwriting `authorized_keys`, `config`, or GPG trust files, or populating them with attacker-controlled content (SSH `ProxyCommand`/`Match` config abuse, GPG trust overrides). This is a file-write-outside-intended-directory primitive originating purely from a URL the user is enticed to clone, which is explicitly in-scope for this analysis (git remote controlling destination writes, no local/admin access required).

### Likelihood Explanation
Requires a Windows target (trailing dot/space stripping is a Windows filesystem/Win32 API behavior) and a victim who clones from an attacker-supplied URL — this matches Desktop's normal "Clone repository" / "Open in Desktop" / deep-link flows where the remote URL (and thus the derived folder name) is fully attacker controlled. The guard's intent (blocking exactly this class of attack) is explicit in its own doc comment, confirming this is a real, targeted security boundary rather than incidental code, which raises confidence that a bypass here is meaningful. I could not fully verify at what point `clone()`'s `path` argument is finally computed/joined with the base directory (i.e., whether any additional resolution step intervenes between `sanitizeCloneName` and the call into `git/clone.ts`), since the exact `app-store.ts`/`clone-repository.tsx` join logic wasn't fully traced in this session — this should be confirmed before treating the bypass as fully proven end-to-end.

### Recommendation
Make `isClonePathSensitive` consistent with `resolveWithin`: resolve (or attempt to resolve) the real filesystem path of both the candidate clone path and the sensitive directories (creating them if needed for comparison, or using a normalization routine that mirrors Windows' own trailing dot/space stripping) before comparing, rather than relying on raw string equality/`startsWith` over `Path.resolve()` output. Additionally, harden `sanitizeCloneName` to strip trailing dots and spaces (and other characters Windows silently discards) from the derived directory name so the sanitized name matches what will actually be created on disk.

### Proof of Concept
Conceptual PoC (Windows target):
1. Attacker crafts a repository URL whose "owner/name" is a path-safe wrapper: `https://evil.example.com/owner/.ssh.` (or `.ssh%20` / `.ssh ` in the clone dialog).
2. Victim uses "Clone a repository from the Internet…" (or an "Open in Desktop"/deep link that drives `openOrCloneRepository`) with this URL, base directory `C:\Users\victim\`.
3. `parseRepositoryIdentifier` → `sanitizeCloneName('.ssh.')` returns `.ssh.` unchanged (only `.git` suffix and pure `.`/`..` are stripped).
4. The clone destination becomes `C:\Users\victim\.ssh.`.
5. `isClonePathSensitive('C:\\Users\\victim\\.ssh.')` lexically compares against `C:\Users\victim\.ssh` and fails to match (`.ssh.` ≠ `.ssh`, and `.ssh.` does not `startsWith('.ssh' + sep)`), so `clone()` proceeds.
6. Windows collapses the trailing dot when the directory is actually created by `git clone`, so the repository content lands in the real `C:\Users\victim\.ssh` directory, overwriting/populating SSH configuration and keys with attacker-supplied files. [2](#0-1) [4](#0-3)

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
