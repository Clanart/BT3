### Title
Attacker-controlled UTXO flood makes `SignableTransaction::new` permanently fail with `TooLargeTransaction`, freezing funds - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to `massUpdatePools` iterating an unbounded registry of pools until it runs out of gas, the Bitcoin wallet's `SignableTransaction` iterates over every `ReceivedOutput` the scanner produced and bakes them all into one transaction. There is no input selection, no dust/uneconomical-input filtering, and no chunking. An unprivileged party can send arbitrary numbers of small Taproot outputs to a multisig's scanned script; once enough outputs accumulate, `SignableTransaction::new` fails `weight > MAX_STANDARD_TX_WEIGHT` and returns `TransactionError::TooLargeTransaction`, blocking construction of the spend transaction — the exact "loop/state growth makes the operation fail" shape of the reported bug.

### Finding Description
`Scanner::scan_transaction` registers every output paying to a tracked `script_pubkey` (`networks/bitcoin/src/wallet/mod.rs:199-214`), and any Bitcoin user can create such outputs. The resulting `Vec<ReceivedOutput>` is passed wholesale into `SignableTransaction::new` (`send.rs:150-256`), which:

- maps every element of `inputs` into `tx_ins` (`send.rs:177-185`),
- computes weight/vbytes over all of them (`send.rs:204`, `calculate_weight_vbytes` at `send.rs:62-127`),
- rejects with `TooLargeTransaction` if `weight > MAX_STANDARD_TX_WEIGHT` (`send.rs:241-243`).

There is no cap on `inputs.len()` and no path that subsets inputs. Downstream, `multisig` (`send.rs:273-286`), `preprocess` (`send.rs:302-318`), `sign` (`send.rs:355-398`), and `complete` (`send.rs:413-428`) all iterate `self.sigs` once per input, each iteration performing a full per-input FROST signature (`taproot_key_spend_signature_hash` per input, `shares.remove(0)` per participant per input in `complete`). Like `add(..., withUpdate=true)` in the report, the cost grows with attacker-influenced state until the operation fails outright.

### Impact Explanation
Once the count of received outputs to a scanned address exceeds the weight-derived input bound (roughly ~1,700 inputs at ~232 WU per Taproot input against the 400,000 WU standard limit), every call to `SignableTransaction::new` errors. If the scheduler feeds all known UTXOs (the API surface provides no subsetting), the multisig's accumulated funds cannot be spent — "funds reported received that are not spendable", matching the report's impact class. Even below the hard cap, each dust input costs more in fee than its value at moderate fee rates, and each input multiplies the FROST signing work across all `t` participants.

### Likelihood Explanation
Medium. Any party can send dust-valued P2TR outputs to a publicly known multisig address at a cost of ~546 sat per output; no validator status, collusion, or key material is required. The scanner registers them unconditionally (`scan_transaction` only matches `script_pubkey` and never filters by value or maturity).

### Recommendation
Filter or bound `inputs` before construction in `SignableTransaction::new`: skip inputs whose value is below the marginal fee cost of spending them (`input vbytes * fee_per_vbyte`), cap the input count so `calculate_weight_vbytes` stays under `MAX_STANDARD_TX_WEIGHT`, and prefer largest-value-first selection so `new` degrades gracefully instead of returning `TooLargeTransaction`. Optionally expose pagination so the caller can sweep UTXOs across multiple transactions.

### Proof of Concept
1. Obtain the multisig's P2TR `script_pubkey` (`p2tr_script_buf`, `wallet/mod.rs:80-86`).
2. Broadcast a Bitcoin transaction (or several) creating N outputs of value `DUST` (546 sat, `send.rs:32`) to that script, where N exceeds the input bound implied by `MAX_STANDARD_TX_WEIGHT`.
3. `Scanner::scan_block`/`scan_transaction` returns all N as `ReceivedOutput`s (`wallet/mod.rs:199-227`).
4. `SignableTransaction::new(inputs, payments, change, data, fee)` builds `tx_ins` of length N, computes `weight > MAX_STANDARD_TX_WEIGHT`, and returns `Err(TransactionError::TooLargeTransaction)` (`send.rs:241-243`) — construction of any spend fails while the inputs set remains that large, with no in-API mechanism to drop inputs.

Caveat: whether the higher-level scheduler (outside the in-scope `networks/bitcoin/src`) always passes the full UTXO set could not be verified from the scoped code; the vulnerability stands on the wallet API itself lacking input bounding/selection.
