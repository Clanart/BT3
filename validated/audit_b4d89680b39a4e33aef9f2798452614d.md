### Title
Unbounded recursion in wallet outer-puzzle drivers via attacker-crafted nested puzzle layers causes wallet DoS - (File: chia/wallet/outer_puzzles.py)

### Summary
Chia's `sha256_treehash` was deliberately rewritten as an iterative algorithm specifically "so we don't have to worry about blowing out the python stack" when hashing deeply nested CLVM trees [1](#0-0) . However, the wallet's outer-puzzle driver layer that identifies CAT/singleton/NFT-ownership/NFT-metadata/CR-CAT layers does **not** follow this discipline: `match_puzzle()` and each driver's `get_inner_puzzle()`/`get_inner_solution()`/`construct()` recurse through an unbounded chain of `also` (nested driver) layers with genuine Python call recursion, one stack frame per curried puzzle layer [2](#0-1) .

### Finding Description
Each outer-puzzle driver (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`) is defined identically: when it matches a puzzle layer, it recursively calls `self._match(...)` on the inner puzzle to detect further nested layers, storing the result under the `"also"` key of `PuzzleInfo` [3](#0-2) . Symmetrically, `get_inner_puzzle()` and `get_inner_solution()` walk back down that `also` chain with one Python function call per layer [4](#0-3) ; identical patterns exist in `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, and `CROuterPuzzle` [5](#0-4) [6](#0-5) [7](#0-6) . `PuzzleInfo.also()`/`check_type()` similarly recurse without any depth bound, explicitly documenting "also" as "the supported way to do recursion of PuzzleInfos" [8](#0-7) .

None of these recursive code paths impose a maximum nesting-depth check, unlike `sha256_treehash`, which was intentionally made iterative for exactly this class of concern [1](#0-0) . This is structurally the same "unbounded loop in an otherwise trusted structural traversal" bug class as ALPINE-CVE-2018-14629 (a CNAME loop causing infinite recursion in Samba's LDAP server): a crafted, deeply nested data structure (there, a CNAME chain; here, deeply nested curried outer-puzzle layers such as `CAT(CAT(CAT(...CAT(inner)...)))` or `CR(ownership(CAT(...)))`) drives unbounded native-stack recursion in code that assumes reasonable nesting.

`match_puzzle()` and the `outer_puzzles` module are used directly by the offer/trade path — `chia/wallet/trading/offer.py` imports `construct_puzzle`, `get_inner_puzzle`, `get_inner_solution`, `match_puzzle`, and `solve_puzzle` from `chia.wallet.outer_puzzles` to parse an incoming `Offer`'s driver dictionary and asset structure [9](#0-8)  — as well as by `wallet_state_manager.py`, `cat_wallet.py`, `nft_wallet.py`, `cr_cat_wallet.py`, and `data_layer_wallet.py` when interpreting puzzle reveals for coins the wallet becomes aware of. An offer file or an on-chain coin's puzzle reveal is attacker-controlled data from the perspective of the receiving wallet/offer-counterparty: an attacker can construct a puzzle with an arbitrarily deep chain of recognized outer-puzzle layers (each layer only needs to satisfy the specific curry shape one of the drivers matches) and hand it to a victim as an offer file or as a coin sent to the victim's wallet.

### Impact Explanation
Because the recursion depth is controlled entirely by the untrusted puzzle's structure and there is no depth limit or iterative rewrite (unlike `sha256_treehash`), a sufficiently deep nesting (a few thousand layers, well below Python's default recursion limit margin needed to exhaust the C stack in nested calls across `match_puzzle` → driver `.match()` → `self._match()` → next driver `.match()` → ...) will raise a Python `RecursionError` (or, in worse cases with C-extension interaction, a hard interpreter crash) inside wallet code that is processing an offer or an incoming spend. This can crash or hang the wallet process/RPC handling that transaction or offer, constituting a spend/offer-triggered transaction-processing halt — a Medium-severity, unprivileged-attacker-reachable denial of service against a wallet user or offer counterparty, consistent with the Samba CNAME-loop DoS analog.

### Likelihood Explanation
The attack requires only that a victim's wallet or offer-processing code path examine a crafted puzzle reveal (via an offer file the attacker sends, or a coin the attacker creates and directs at the victim's wallet address). No special privileges, signatures, or mempool acceptance of a full spend are required to trigger the parsing/matching logic in `outer_puzzles.py`/`PuzzleInfo`, since driver `match()`/`also()` traversal is pure Python structural inspection independent of CLVM execution cost accounting.

### Recommendation
Rewrite `match_puzzle()`/driver `.match()`, `.get_inner_puzzle()`, `.get_inner_solution()`, and `PuzzleInfo.also()`/`check_type()` to use iterative loops instead of recursive calls (mirroring the design rationale already applied to `sha256_treehash`), or enforce an explicit maximum "also" nesting depth and raise a clean, catchable error once exceeded, so that malformed/malicious puzzle structures cannot exhaust the Python call stack in wallet or trade-manager code.

### Proof of Concept
Not independently executed; conceptually: construct a puzzle reveal formed by nesting one of the recognized outer-puzzle curry shapes (e.g., CAT-layer curry) inside itself N times (N in the low thousands), embed it in a coin's puzzle reveal referenced by an `Offer` or `CoinSpend`, and have a victim wallet call `chia.wallet.outer_puzzles.match_puzzle()` (as done in `chia/wallet/trading/offer.py`) or the associated `get_inner_puzzle`/`get_inner_solution` on it; the resulting call chain of depth N through `CATOuterPuzzle.match()`/`get_inner_puzzle()` (and equivalents in other drivers) is expected to raise `RecursionError`, aborting whatever wallet operation was in progress.

class PuzzleInfo:
    """
    There are two 'magic' keys in a PuzzleInfo object:
      - 'type' must be an included key (for easy lookup of drivers)
      - 'also' gets its own method as it's the supported way to do recursion of PuzzleInfos
    """

    info: dict[str, Any]

    def __init__(self, info: dict[str, Any]) -> None:
        self.info = info
        self.__post_init__()

    def __post_init__(self) -> None:
        if "type" not in self.info:
            raise ValueError("A type is required to initialize a puzzle driver")

    def __getitem__(self, item: str) -> Any:
        value = self.info[item]
        return decode_info_value(PuzzleInfo, value)

    def __eq__(self, other: object) -> bool:
        for key, value in self.info.items():
            try:
                if self[key] != other[key]:  # type: ignore
                    return False
            except Exception:
                return False
        return True

    def __contains__(self, item: str) -> bool:
        if item in self.info:
            return True
        else:
            return False

    def type(self) -> str:
        return str(self.info["type"])

    def also(self) -> PuzzleInfo | None:
        if "also" in self.info:
            return PuzzleInfo(self.info["also"])
        else:
            return None

    def check_type(self, types: list[str]) -> bool:
        if types == []:
            if self.also() is None:
                return True
            else:
                return False
        elif self.type() == types[0]:
            types.pop(0)
            if self.also():
                return self.also().check_type(types)  # type: ignore
            else:
                return self.check_type(types)
        else:
            return False
