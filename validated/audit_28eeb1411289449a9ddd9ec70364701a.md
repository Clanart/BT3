### Title
Duplicate encryption-key registration triggers an unconditional `assert!` panic, letting a single DKG participant crash every honest node - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::register` in `crypto/dkg/pedpop/src/encryption.rs` enforces single registration with `assert!(!self.enc_keys.contains_key(&participant), "Re-registering encryption key for a participant")`. This is reached through the public `EncryptedMessage`/`EncryptionKeyMessage` deserialization path (`EncryptionKeyMessage::read` → `Encryption::register` → `Decryption::register`), which consumes bytes sent by an unauthenticated peer during PedPoP key generation. A participant who simply sends their `EncryptionKeyMessage` twice (or whose message is replayed) causes a panic in the library rather than an `io::Error`, aborting the victim's key-generation session — analogous to CVE-2017-7607, where a crafted input file crashes the parser.

### Finding Description
The bug class is a crash on malformed/unexpected input in an untrusted-bytes parsing path. All other input-validation failures in this subsystem return `io::Result` (`read_F`, `read_G`, `Commitments::read`, `EncryptedMessage::read`, `ThresholdKeys::read`), so callers reasonably assume peer-controlled messages cannot panic. Three unguarded panic sites exist on the peer-message path:

- `Decryption::register` asserts the participant isn't already present (`encryption.rs:356-359`). Any second `EncryptionKeyMessage` for the same `Participant` index — trivially producible by a faulty/malicious DKG member, since `Participant` is just a u16 read from the wire — panics.
- `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` (`encryption.rs:388`); a blame/decryption flow referencing a participant whose key was never registered panics on HashMap indexing.
- `Encryption::encrypt` indexes `self.decryption.enc_keys[&participant]` (`encryption.rs:466`), panicking if any participant withheld their registration message.

The PedPoP `Commitments` documentation explicitly acknowledges participants "may send multiple sets of commitments" and are "faulty and should be presumed malicious" (`pedpop/src/lib.rs:98-101`), yet the library itself panics on exactly that condition for the encryption-key message instead of returning an error the caller can handle.

### Impact Explanation
Panic in a thread or FFI context aborts the host process. A single malicious (or merely buggy/replayed) DKG participant can crash all honest nodes mid-key-generation, denying service to the threshold-network bootstrap. This matches the Medium-severity DoS impact of the reference CVE (CVSS 5.5, availability-only).

### Likelihood Explanation
Triggering requires only sending a duplicated or out-of-order registration message — a public input any DKG participant controls. No secret knowledge, collusion, or validator privileges are needed. The only mitigating factor is that callers might filter duplicates at the networking layer, but the library does not require or verify this, and its own comments place that burden on the caller while still panicking.

### Recommendation
Replace the `assert!` in `Decryption::register` with a returned error (extend `DecryptionError` or return `io::Result`), and replace `enc_keys[&participant]`/`enc_keys[&decryptor]` indexing with `get().ok_or(...)`. All peer-reachable registration/decryption paths should fail gracefully so a faulty participant produces a blamable error, not a crash.

### Proof of Concept
Conceptually: in a PedPoP session, participant `l` serializes `EncryptionKeyMessage::write` and broadcasts it twice. Each honest node calls `Encryption::register(l, msg)` per received message; the second call hits the `assert!` at `encryption.rs:356-359` and panics. Equivalently, `let mut d = Decryption::<C>::new(ctx); d.register(p, msg.clone()); d.register(p, msg);` panics deterministically.

I note a limitation: I did not fully trace `pedpop/src/lib.rs`'s call sites of `Encryption::register`/`encrypt`, so whether the library deduplicates messages before registration is unverified — but the panic-on-duplicate contract is confirmed in the code itself, and no in-library guard prevents it.
