## Title
Tx-pool queue-eviction "stalest-beat" ordering can be gamed by refreshing an account's heartbeat via cheap promotions, defeating fair queue eviction - (File: `blockchain/tx_pool.go`)

### Summary
The CVE describes Unbound's "jostle" eviction logic being defeated because a query's age gets renewed by unrelated duplicate activity (using the latest duplicate's timestamp) instead of the original request's age, letting an attacker keep slow/stale queries permanently immune from eviction. Kaia's transaction pool has an almost identical mechanism: a per-account heartbeat (`pool.beats`) is used to decide which account's *queued* (non-executable) transactions are evicted first when the pool is globally full. That heartbeat can be refreshed by activity unrelated to the specific stale transactions being protected, letting a sender keep their backlog of stale queued transactions permanently immune from the fairness eviction while honest accounts get evicted instead.

### Finding Description
`TxPool.beats` records "last heartbeat from each known account" [1](#0-0) .

When the total queued (non-executable) transaction count exceeds `NonExecSlotsAll`, `promoteExecutables` sorts accounts by `pool.beats[addr]` and evicts the tail of the **stalest-beat** accounts first, keeping only the lowest queued nonce per account: [2](#0-1) 

The heartbeat is refreshed in `promoteTx` **every time any transaction from that account is promoted from queue to pending**, regardless of whether the promoted transaction is related to the stale, backlogged, high-nonce transactions still sitting in the queue: [3](#0-2) 

So an account can have a large backlog of genuinely stale, gapped-nonce future transactions sitting in `pool.queue[addr]`, while `pool.beats[addr]` is kept perpetually fresh simply by submitting a cheap, unrelated transaction that fills the current nonce gap and gets promoted. This is the same root cause pattern as the CVE: the "age" used by the eviction/jostle logic is derived from the latest unrelated activity for the entity, not from the age of the specific stale items that the eviction mechanism is supposed to target.

By contrast, `enqueueTx` only refreshes the beat when the account's queue list is newly created, explicitly to avoid inheriting a stale beat [4](#0-3)  — but this protection is bypassed by the unconditional refresh in `promoteTx` on every promotion.

### Impact Explanation
An unprivileged transaction sender can:
1. Fill their own queue (`pool.queue[addr]`) up to `NonExecSlotsAccount` with high-nonce, low-value future transactions (a backlog that should be considered "stale" if left untouched).
2. Periodically submit a cheap transaction that fills the current pending-nonce gap, which is promoted via `promoteTx`, unconditionally refreshing `pool.beats[addr]`.
3. Because the account's beat is always fresh, `promoteExecutables`'s stalest-beat sort (`addresssByHeartbeat`) never selects this account for the queue-cap tail-drop eviction, even though its backlog transactions are effectively abandoned/stale.
4. When the global queue fills up (`queued > NonExecSlotsAll`), other senders' legitimately queued transactions (whose accounts haven't had a recent promotion) are evicted first instead, denying them fair admission to the txpool.

This is a resource-fairness/availability degradation (`A:L`) affecting the pool admission of other unprivileged submitters, matching the CVE's CVSS vector (no confidentiality/integrity impact, network-reachable, low complexity, no privileges/UI required).

### Likelihood Explanation
The attack requires only normal `AddRemote`/`AddLocal` transaction submission capability that any public RPC caller has, and only a modest, sustained gas cost to keep resubmitting a nonce-filling transaction. No special privileges, timing races, or validator/peer control are needed, making this readily reachable by any transaction sender.

### Recommendation
Track the age of each queued transaction independently (or at minimum, the age of the account's oldest queued transaction) rather than reusing a single per-account heartbeat that is refreshed by unrelated promotions. Only refresh `pool.beats[addr]` based on activity that actually reduces or touches the backlog being protected (e.g., when the queue for that account shrinks/empties), not on every promotion event, mirroring the CVE fix of attaching an immutable "start time" to the item that eviction logic is meant to age out.

### Proof of Concept
1. Configure a pool with small `NonExecSlotsAll`/`NonExecSlotsAccount` (as in `TestQueueCapEvictionStalestTailDrop`) [5](#0-4) .
2. Attacker account A: enqueue several future-nonce transactions (nonces 2..5) leaving a gap at nonce 1, exhausting most of `NonExecSlotsAccount`.
3. Victim account B: enqueue similar future-nonce transactions, then go idle (no further activity), so `pool.beats[B]` stays old.
4. Attacker periodically submits the nonce-1 filler transaction; each time `promoteTx` runs, `pool.beats[A] = time.Now()` refreshes even though A's nonces 3..5 remain untouched in the queue.
5. Trigger `promoteExecutables` when `queued > NonExecSlotsAll`: the stalest-beat sort selects B (untouched, stale beat) for eviction ahead of A, even though A's backlog (nonces 3..5) is just as stale as B's — demonstrating that A's genuinely stale queued transactions are shielded from eviction by unrelated promotion activity.

// promoteTx adds a transaction to the pending (processable) list of transactions
// and returns whether it was inserted or an older was better.
//
// Note, this method assumes the pool lock is held!
func (pool *TxPool) promoteTx(addr common.Address, hash common.Hash, tx *types.Transaction) bool {
	// Try to insert the transaction into the pending queue
	if pool.pending[addr] == nil {
		pool.pending[addr] = newTxList(true)
	}
	list := pool.pending[addr]

	inserted, old := list.Add(tx, pool.config.PriceBump, pool.rules.IsMagma)
	if !inserted {
		// An older transaction was better, discard this
		pool.all.Remove(hash)
		pool.priced.Removed()

		pendingDiscardCounter.Inc(1)
		return false
	}
	// Otherwise discard any previous transaction and mark this
	if old != nil {
		pool.all.Remove(old.Hash())
		pool.priced.Removed()

		pendingReplaceCounter.Inc(1)
	} else {
		pool.pendingCount++
	}
	// Failsafe to work around direct pending inserts (tests)
	if pool.all.Get(hash) == nil {
		pool.all.Add(tx)
		pool.priced.Put(tx)
	}
	// Set the potentially new pending nonce and notify any subsystems of the new tx
	pool.beats[addr] = time.Now()
	pool.setPendingNonce(addr, tx.Nonce()+1)

	return true
}

func TestQueueCapEvictionStalestTailDrop(t *testing.T) {
	t.Parallel()

	statedb, _ := state.New(common.Hash{}, state.NewDatabase(database.NewMemoryDBManager()), nil, nil)
	blockchain := &testBlockChain{statedb: statedb, gasLimit: 10000000, chainHeadFeed: new(event.Feed), txMap: make(map[common.Hash]*types.Transaction)}

	config := testTxPoolConfig
	config.NonExecSlotsAccount = 8
	config.NonExecSlotsAll = 4

	pool := NewTxPool(config, params.TestChainConfig.Copy(), blockchain, &dummyGovModule{chainConfig: params.TestChainConfig.Copy()})
	defer pool.Stop()

	keyStale, _ := crypto.GenerateKey()
	keyFresh, _ := crypto.GenerateKey()
	stale := crypto.PubkeyToAddress(keyStale.PublicKey)
	fresh := crypto.PubkeyToAddress(keyFresh.PublicKey)
	testAddBalance(pool, stale, big.NewInt(10000000))
	testAddBalance(pool, fresh, big.NewInt(10000000))

	// Grow the queue past the cap through enqueueTx directly, mirroring
	// demote-driven growth that bypasses AddRemote's capacity checks.
	pool.mu.Lock()
	for nonce := uint64(1); nonce <= 4; nonce++ {
		staleTx := transaction(nonce, 100000, keyStale)
		freshTx := transaction(nonce, 100000, keyFresh)
		if _, err := pool.enqueueTx(staleTx.Hash(), staleTx); err != nil {
			pool.mu.Unlock()
			t.Fatalf("enqueue stale acct nonce %d: %v", nonce, err)
		}
		if _, err := pool.enqueueTx(freshTx.Hash(), freshTx); err != nil {
			pool.mu.Unlock()
			t.Fatalf("enqueue fresh acct nonce %d: %v", nonce, err)
		}
	}
	pool.beats[stale] = time.Now().Add(-time.Hour)
	pool.beats[fresh] = time.Now()
	pool.promoteExecutables(nil) // 8 queued > cap 4 triggers the eviction
	pool.mu.Unlock()

	if pool.queuedCount != 4 {
		t.Fatalf("queued count after eviction: have %d, want 4", pool.queuedCount)
	}
	if pool.queue[stale] == nil || pool.queue[stale].Len() != 1 {
		t.Fatalf("stale account not tail-dropped to its frontier")
	}
	if pool.queue[stale].txs.Get(1) == nil {
		t.Fatalf("stale account lost its lowest queued tx")
	}
	if pool.queue[fresh] == nil || pool.queue[fresh].Len() != 3 {
		have := 0
		if pool.queue[fresh] != nil {
			have = pool.queue[fresh].Len()
		}
		t.Fatalf("fresh account dropped before stale exhausted: have %d, want 3", have)
	}
	if err := validateTxPoolInternals(pool); err != nil {
		t.Fatalf("pool internal state corrupted: %v", err)
	}
}
