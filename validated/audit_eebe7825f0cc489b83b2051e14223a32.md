### Title
`ReceivedOutput::read` accepts an arbitrary offset/script pairing, enabling spoofed "received" outputs that are unspendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to CVE-2021-38506 (a UI state entered without the checks that would warn the user, enabling spoofing), `ReceivedOutput::read` deserializes a claimed spendable output without verifying that the encoded `offset` actually derives the output's `script_pubkey` from the scanner's key. Untrusted bytes can therefore fabricate a `ReceivedOutput` that reports funds "received" which either do not exist at the claimed outpoint or cannot be spent under the given offset.

### Finding Description
`ReceivedOutput` consists of `(offset: Scalar, output: TxOut, outpoint: OutPoint)`, all attacker-controlled fields read straight from the stream:

- `offset` is read via `Secp256k1::read_F` [1](#0-0) 
- `output` (`TxOut`) and `outpoint` are consensus-decoded from the same stream [2](#0-1) 

No check binds `offset` to `output.script_pubkey`. By contrast, the honest producer `Scanner::scan_transaction` only emits a `ReceivedOutput` after looking up `self.scripts.get(&output.script_pubkey)`, so `offset` is guaranteed consistent with the script [3](#0-2) . A deserialized output silently bypasses this invariant: the only downstream consistency check is in `SignableTransaction::multisig`, where `p2tr_script_buf(keys.offset(offset).group_key()) != prevouts[i].script_pubkey` returns `None` [4](#0-3) .

### Impact Explanation
- **Spoofed funds**: an attacker who can feed bytes to `ReceivedOutput::read` (e.g., a peer/supplier of output records) causes a `ReceivedOutput` claiming arbitrary value at an arbitrary outpoint to be treated as a real, spendable deposit. `Output::read`/`write` round-trips these into Serai's processor state [5](#0-4) , and `Output::key()`/`balance()` will happily report a key and `ExternalBalance` for it [6](#0-5)  — funds reported received that are not spendable (offset doesn't correspond to the script, or the outpoint is fabricated).
- **DoS / panic**: when such an output is scheduled for spending, `attempt_sign` calls `multisig(&keys).expect("used the wrong keys")` [7](#0-6) , so a mismatched offset aborts signing with a panic rather than a clean rejection.
- This is the direct analog of the Firefox bug: a spoofable "state" (fullscreen UI ⇄ spendable-output record) entered without a binding check, attacker-reachable purely through untrusted bytes.

### Likelihood Explanation
Reachable whenever `ReceivedOutput::read`/`Output::read` is applied to bytes an unprivileged party can influence (the prompt explicitly scopes `ReceivedOutput::read` as attacker-fed). Exploitation requires no key material — just choosing `(offset, TxOut, OutPoint)`. The spoofing benefit (balance/state misrepresentation, or deterministic panic of the signing path) makes this Medium severity, matching the CVSS-4.3 spoofing/integrity-impact shape of the reference CVE.

### Recommendation
Either document `ReceivedOutput::read` as requiring trust in the input (and rename accordingly), or add a validation API — e.g. `ReceivedOutput::read_for(scanner: &Scanner, r)` — that re-derives `p2tr_script_buf(key + G*offset)` and rejects inputs whose `script_pubkey` isn't a registered script, restoring the invariant `scan_transaction` enforces. Downstream, `attempt_sign` should return a `NetworkError` instead of `expect`ing on `multisig()`.

### Proof of Concept
```rust
// Attacker chooses any scalar and any TxOut/OutPoint; no script binding is checked.
let mut buf = Vec::new();
buf.extend(Scalar::ZERO.to_bytes());               // offset (does not match script)
buf.extend(serialize(&TxOut {
    value: Amount::from_sat(1_000_000),
    script_pubkey: attacker_chosen_p2tr_script,    // pays to attacker, not the group
}));
buf.extend(serialize(&OutPoint::new(fake_txid, 0)));// fabricated outpoint

let spoofed = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(spoofed.value(), 1_000_000);            // reported as received funds

// Any spend attempt either never verifies or panics:
// SignableTransaction::multisig returns None (offset mismatched),
// then attempt_sign hits `expect("used the wrong keys")` -> panic.
```

```rust
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
```

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
