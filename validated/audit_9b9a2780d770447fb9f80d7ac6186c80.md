### Title
Silent loss of merge-conflict content when Copilot returns fewer resolved hunks than actual conflict markers in a file - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
`reassembleResolvedFile` splices the AI-generated per-hunk resolutions into the on-disk conflicted file by *positional order*, not by any per-hunk identifier. If the number of `hunkResolutions` returned by the model is smaller than the number of well-formed `<<<<<<< / ======= / >>>>>>>` blocks actually present in the file, every conflict block beyond the last supplied resolution is deleted outright — both "ours" and "theirs" content are dropped with no error, warning, or fallback — and the result is written to disk and staged when the user clicks "Continue Merge".

### Finding Description
`reassembleResolvedFile` walks the raw file, and for each well-formed conflict block increments `hunkIndex` and looks up `hunkResolutions[hunkIndex]`: [1](#0-0) 
If `hunkIndex >= hunkResolutions.length` the `if` guard is false, so *nothing* is pushed into `resultLines` for that conflict block — the code silently drops the block's content entirely rather than falling back to the original markers or raising an error.

This function is called from `reassembleResolutions`, which trusts the model's `raw.hunks` array to correspond 1:1, in order, with the conflicts detected in `ctx.rawContent`: [2](#0-1) 

There is no code anywhere in this path that cross-checks `raw.hunks.length` against the number of conflict blocks actually parseable in `ctx.rawContent` (the count is only established later, dynamically, while reassembling). `validateResolutionPaths` and the "still contains conflict markers" check (seen in tests) validate paths and marker leakage, but not hunk-count parity.

The repository content (i.e., the merge conflict itself) is fully attacker-influenced: a malicious PR author who knows their branch will be merged/rebased/cherry-picked by a maintainer using Desktop's "Resolve with Copilot" feature can craft a file with an unusually structured or very large set of conflict blocks (e.g. deeply nested, oddly formatted, or numerous hunks) that make it likely the LLM undercounts or emits fewer `hunks` entries than the real number of markers in the file — a known LLM failure mode with long/ambiguous structured output, and one an attacker can deliberately amplify by conflict-block design. When that happens, Desktop silently deletes the tail conflict(s)' content (both sides) from the final file without any indication to the user, then writes and stages it.

### Impact Explanation
This results in silent corruption of what the user commits and pushes: whole sections of code (including possibly the user's own intended changes) are deleted from a file at commit time without any diagnostic, malformed-marker warning, or diff callout distinguishing "silently dropped conflict" from "intentional deletion" (the code treats `resolved.length > 0` the same way whether it's a real empty resolution or an out-of-range lookup). Because the write happens via `_applyCopilotConflictResolutions` → `writeFile` and `git add` [3](#0-2) , a user who reviews only the Copilot summary tab (not every line of every file's diff in the Changes tab) can commit/push a file that is missing code with no record that anything went wrong — a direct parallel to the ALCK bug's "burn without claiming" pattern: content is discarded (analogous to burning the token) without any validation step (analogous to claiming rewards) confirming all conflicts were actually resolved before finalizing.

### Likelihood Explanation
The Changes tab diff preview does give the user a chance to notice missing code before clicking "Continue Merge" [4](#0-3) , so this is not a guaranteed-silent loss for every user — it depends on the user actually reviewing the full diff of every conflicted file rather than trusting the AI summary and clicking through. Likelihood is moderate: it requires (1) a repository/PR with attacker-crafted conflict structure, (2) the maintainer using the opt-in Copilot conflict resolution feature, and (3) the model actually undercounting hunks for that file, which is plausible but not deterministic. I was not able to verify from the index whether `validateResolutionPaths` (only partially inspected) performs any hunk-count check, so it's possible some additional guard exists elsewhere that I could not locate.

### Recommendation
In `reassembleResolutions`/`reassembleResolvedFile`, verify that the number of real conflict blocks found in `rawContent` exactly matches `raw.hunks.length` before reassembly; if they don't match, throw a `CopilotValidationError` (as is already done for missing `rawContent`) so the retry path in `copilot-store.ts` kicks in, or mark the file as skipped so the user is forced to resolve it manually rather than silently losing content.

### Proof of Concept
1. Set up a merge/rebase with a file containing 3 well-formed conflict blocks.
2. Have the Copilot model (or a stub) return only 2 entries in `hunks` for that file (simulating an LLM undercount, which an attacker can encourage via conflict-block crafting).
3. Call `reassembleResolutions([...], [{ path, hunks: [...], rawContent }])`.
4. Observe that the third conflict block's content (both ours/theirs sides) is missing entirely from the returned `resolvedContent`, with no error thrown — confirmed directly by the guard logic at [5](#0-4) .

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
