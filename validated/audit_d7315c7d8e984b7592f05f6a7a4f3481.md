### Title
Unbounded ReDoS via user-supplied `MATCHES` regex in Tendermint RPC query filters - (File: sei-tendermint/internal/pubsub/query/query.go)

### Summary
The external report describes mongo-express accepting unsafe, user-controlled query syntax without proper validation (CWE-20), leading to critical impact. The analogous pattern in sei-chain is the Tendermint/CometBFT event-filter query language exposed through the public RPC `/subscribe`, `/tx_search`, and `/block_search` endpoints: the `MATCHES` operator compiles an attacker-supplied string directly as a Go regular expression on every event match, with no length limits, complexity checks, or caching.

### Finding Description
The query grammar accepts a `MATCHES '<pattern>'` condition [1](#0-0) , and the parser accepts any string literal as the pattern argument without validating it is a safe/bounded regex [2](#0-1) .

At compile time, the `TMatches` operator directly wraps `regexp.MatchString` around the raw user string, invoking regex compilation and execution for every event evaluated on every block/tx during the life of the subscription: [3](#0-2) . There is no caching of the compiled regex, no timeout, no restriction on regex complexity (e.g. nested quantifiers), and no length cap on the pattern string. Go's `regexp` package (RE2) generally avoids catastrophic backtracking for typical patterns, but extremely large or deeply nested patterns/inputs can still cause significant CPU and memory consumption per evaluation, and this cost is paid repeatedly (once per attribute per matching event, for every new event as long as the subscription lives), amplifying resource usage far beyond a single request.

This filter path is reachable by any unauthenticated/unprivileged RPC client through the public JSON-RPC/WebSocket surface: `subscribe`, `tx_search`, and `block_search` all take a `query` string parameter that is parsed with this same query engine in `sei-tendermint/internal/rpc/core/events.go`, `tx.go`, and `blocks.go`.

### Impact Explanation
An unprivileged public-RPC client can submit a `subscribe` (WebSocket) request with a `query` containing a `MATCHES` clause with a very large or adversarially constructed pattern (e.g., very long alternation/repetition chains). Because the pattern is recompiled and evaluated against every event attribute for every subsequent block/tx as long as the subscription remains open, the client can force sustained, amplified CPU/memory consumption on the RPC node for the lifetime of the (persistent) subscription, degrading or crashing a default-configuration full/RPC node — a resource-exhaustion / node-availability impact. Because subscriptions are typically evaluated against the shared node event bus, this can also affect other event consumers relying on the same instance and, in aggressive cases, contribute to block-processing delay if the indexer/event-bus goroutines are starved.

### Likelihood Explanation
Likelihood is moderate-to-high for any node exposing the public RPC subscribe/tx_search/block_search endpoints with no dedicated regex-complexity or rate limiting, since the query syntax is a documented, unauthenticated feature and requires no special privilege — only network access to the RPC endpoint and knowledge of the (public) query grammar.

### Recommendation
- Bound the size and complexity of `MATCHES` regex patterns accepted by the query parser (e.g., max pattern length, disallow degenerate patterns).
- Cache compiled regexes per subscription instead of recompiling on every event evaluation, and enforce a hard evaluation timeout/cost budget per match.
- Consider rate-limiting or capping the number of concurrent subscriptions with `MATCHES` clauses per client/IP on public RPC nodes.

### Proof of Concept
1. Connect to a public Tendermint/CometBFT RPC WebSocket endpoint of a sei-chain node.
2. Issue `subscribe` with `query="tm.event='Tx' AND some.attr MATCHES '<very long/complex pattern>'"` (parsed via `syntax.Parse` → `query.New`, compiled via `compileCondition` in query.go).
3. Generate transactions/blocks so the subscription's `matchesEvent`/`match` callback is invoked repeatedly, each time re-running `regexp.MatchString` against attacker-controlled pattern text, driving up CPU usage on the node for the life of the subscription. [3](#0-2) [2](#0-1)
