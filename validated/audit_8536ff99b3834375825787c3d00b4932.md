### Title
Unbounded index read in CLVM canonical-encoding check causes unhandled `IndexError` on crafted spend-bundle solutions - (File: chia/full_node/mempool_manager.py)

### Summary
`is_clvm_canonical()` and its helper `is_atom_canonical()` in `chia/full_node/mempool_manager.py` walk a raw CLVM-serialized buffer byte-by-byte without ever checking the current offset against the buffer length before indexing into it. A truncated/crafted atom length-prefix (analogous to the malformed length fields exploited in the ImageMagick PSD parser, CVE-2016-7532) can drive `offset` past the end of `clvm_buffer`, causing `clvm_buffer[offset]` to raise `IndexError` instead of returning a bounded parse failure.

### Finding Description
`is_atom_canonical()` reads the length-prefix byte at `clvm_buffer[offset]` and, depending on the high bits, computes a `prefix_len` (0–5 additional bytes) that it then reads in a loop with `atom_len |= clvm_buffer[offset]` [1](#0-0) . Nowhere in this function is `offset` checked against `len(clvm_buffer)` before the indexing operations. `is_clvm_canonical()` is the caller: it also indexes `clvm_buffer[offset]` directly in its main loop and calls `is_atom_canonical(clvm_buffer, offset)` for larger atoms, again without a length guard [2](#0-1) .

Per the repo's own architecture notes, this canonical-encoding check exists specifically to validate solutions for DEDUP-eligible mempool spends — i.e., it inspects attacker-controlled solution bytes taken directly from a submitted spend bundle before block building [3](#0-2) . A spend whose solution ends with a truncated multi-byte atom length prefix (e.g., a final byte like `0xFC` indicating a 5-byte length field that is not actually present) will cause `offset` to walk off the end of the buffer, raising `IndexError` deep inside this validation helper rather than returning a controlled `False`/error result.

This mirrors the CVE-2016-7532 bug class: a length-prefixed sub-structure inside attacker-supplied data is trusted without validating that the declared length prefix's bytes actually exist within the buffer, leading to an out-of-bounds read during parsing of a crafted input.

### Impact Explanation
If the `IndexError` raised by `is_atom_canonical`/`is_clvm_canonical` is not caught somewhere upstream in the mempool item processing path, a single unprivileged spend-bundle submitter could craft a spend with a truncated atom-length-prefix solution to trigger an unhandled exception during the DEDUP-eligibility/canonical-form check performed on that spend. This falls into the "spend-triggered transaction-processing halt" impact category: it can disrupt processing of that mempool item (and potentially propagate as an uncaught exception in the mempool manager's processing task, depending on the specific caller's exception handling), rather than causing any coin-state corruption, inflation, or theft. No coin-set divergence or consensus-invalid acceptance is implicated because this check is a Python-level auxiliary optimization gate (canonical/dedup eligibility), not core CLVM execution (which is delegated to the Rust `validate_clvm_and_signature()`).

### Likelihood Explanation
Likelihood is moderate: any wallet or peer can submit a spend bundle with an arbitrary CLVM solution, and constructing a solution byte sequence with a truncated multi-byte atom length prefix is straightforward and requires no special privileges. The precondition is only that the spend attempts to qualify for the DEDUP/fast-forward eligibility path where `is_clvm_canonical()` is invoked.

### Recommendation
Add explicit bounds checks in both `is_atom_canonical()` and `is_clvm_canonical()` before every `clvm_buffer[offset]` access (including inside the `for i in range(prefix_len)` loop), returning a definitive "not canonical" / parse-error result instead of allowing Python's default `IndexError` to propagate. Ensure the caller of `is_clvm_canonical()` treats any parse anomaly as "not eligible" rather than letting an exception escape mempool item processing.

### Proof of Concept
Constructing a CLVM buffer such as `bytes([0xFB])` (a `0b11111011` atom-length lead byte matching the `0b11111000` 4-length-byte-prefix mask with only the single lead byte present, no following bytes) and calling `is_clvm_canonical(bytes([0xFB]))` reaches the `elif (b & 0b11111000) == 0b11110000` branch's `prefix_len = 3` path in `is_atom_canonical`, then attempts `clvm_buffer[offset]` for `offset` values beyond the 1-byte buffer, raising `IndexError` [4](#0-3) . Submitting a spend bundle whose solution serializes to end in such a truncated prefix reaches this code path when the mempool manager evaluates DEDUP/fast-forward eligibility for that spend.

**Note on verification limits:** I was unable to fully trace the exact call site that invokes `is_clvm_canonical()` from the spend-bundle admission pipeline (only the function definitions were found in the indexed content) or confirm whether that specific call site wraps this logic in a try/except that would downgrade the crash to a handled rejection. This limits certainty about whether the impact is a full processing halt versus a caught, benign rejection — a Devin session with full repository access would be needed to confirm the exact caller and its exception handling before treating this as a confirmed high-confidence DoS.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```

```markdown
## Canonical serialization

### `is_clvm_canonical(clvm_buffer)`

Checks that a CLVM program uses shortest-form atom encoding:

- No unnecessary length prefix bytes
- No back-references (`0xFE` byte)
- No trailing garbage

### When enforced

Required for DEDUP-eligible spends. Without canonical form, identical
solutions could have different serializations, breaking dedup.

### `is_atom_canonical(clvm_buffer, offset)`

Validates a single atom's length prefix encoding. The CLVM format uses
variable-length prefixes (1-6 bytes) based on atom size. Each prefix
length has a minimum atom size threshold.
```
