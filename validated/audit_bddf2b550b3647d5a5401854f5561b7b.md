### Title
Fee/size safety checks computed before the OP_RETURN output is accounted for allow a transaction that violates its own validated invariants - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
This is the same bug class as M-22 (a guarantee check applied to a value computed *before* a subsequent addition, so the delivered object fails the checked invariant). In `SignableTransaction::new`, the OP_RETURN `data` output is pushed onto `tx_outs` at line 194, but every fee and size validation — `calculate_weight_vbytes`, the `TooLowFee` minimum-relay check, the `NotEnoughFunds` check, the change-amount/`DUST` check, and the `MAX_STANDARD_TX_WEIGHT` check — is computed over a transaction that contains only `payments` (and optionally `change`). The `data` output (up to 80 payload bytes + overhead) is never included in `weight`/`vbytes`. The result: the transaction is built and signed with a smaller effective fee rate and a larger true weight than the values that passed the checks.

### Finding Description
`calculate_weight_vbytes` constructs the sizing transaction purely from `payments` and `change` (`networks/bitcoin/src/wallet/send.rs:62-99`). The OP_RETURN output is appended to `tx_outs` before sizing (line 194-202), but is excluded from the weight template. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) under-counts by ~`(data.len() + ~10)` vbytes, so the transaction actually achieves a lower fee rate than requested.
- The `TooLowFee` check (line 211) validates `needed_fee` against the minimum relay fee computed on the understated `vbytes`, so a transaction whose *actual* fee rate is below `DEFAULT_MIN_RELAY_TX_FEE` passes.
- The change computation `input_sat - (payment_sat + fee_with_change)` (line 228) uses the same understated `fee_with_change`, overpaying change and underpaying the fee.
- The `MAX_STANDARD_TX_WEIGHT` check (line 241) uses `weight` that omits the data output, so a transaction exceeding the policy weight limit can be produced and signed.

Analog to M-22: a bound is checked on a value (`redeemTokenAmount` / `vbytes`,`weight`) that does not yet reflect a deduction/addition (fee / OP_RETURN output), so the delivered artifact violates the checked guarantee (user receives less than `minRedeemAmount` / the signed TX fails the fee-rate and standardness bounds it was validated against).

### Impact Explanation
An unprivileged party who can cause transaction `data` to be included (a withdrawal/bridge request carrying OP_RETURN data is a caller-controlled input to `SignableTransaction::new`, which then feeds `multisig()`/`TransactionSignMachine`) can produce a signed transaction whose real fee rate is below the mempool minimum relay fee, or whose weight exceeds `MAX_STANDARD_TX_WEIGHT`. The signed transaction will not propagate or confirm: the payments it was built to make are never delivered, while the plan is treated as signed — funds are committed to a transaction that cannot enter the mempool. Worst case, the ~90-byte gap between checked weight and real weight lets a non-standard transaction be produced.

### Likelihood Explanation
Reachable whenever `data: Some(_)` is supplied; the gap scales with `data.len()` (up to 80 bytes allowed by the `TooMuchData` check). Requires the margin between the checked `needed_fee`/weight and the real values to straddle the relay-fee or weight boundary — a narrow but deterministic window, with no privileged access needed.

### Recommendation
Include the OP_RETURN output in the sizing transaction. Change `calculate_weight_vbytes` to take the full output list (payments + data + change), or construct the template with `tx_outs` after the data push instead of `payments`. Re-derive `weight`, `vbytes`, `needed_fee`, and `fee_with_change` from the complete output set so `TooLowFee`, `NotEnoughFunds`, `DUST`, and `MAX_STANDARD_TX_WEIGHT` all validate the transaction actually built — i.e., perform the checks on the post-addition object, mirroring M-22's fix of checking `redeemTokenAmount - redeemFee`.
