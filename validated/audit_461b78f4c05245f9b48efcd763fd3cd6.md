## Analysis

The Recall report's bug class — an actor cheaply enqueuing many tiny stake/unstake operations that are later drained by an **unbounded loop** in a mandatory per-block finalization routine — has a direct structural analog in `sei-chain`'s native Cosmos SDK staking module, which is reachable from any unprivileged caller through the EVM staking precompile.

`x/staking`'s `BlockValidatorUpdates` (invoked every `EndBlock`) drains three time-keyed queues with **no batching or cap**: `DequeueAllMatureUBDQueue`, `DequeueAllMatureRedelegationQueue`, and `UnbondAllMatureValidators`. Each of these does a full iterator sweep over every entry whose maturity time/height has passed and performs a bank transfer per entry, synchronously, inside `EndBlock`. [1](#0-0) 

`DequeueAllMatureUBDQueue` itself has no limit — it concatenates every timeslice up to the current block time: [2](#0-1) 

Compare this to the `x/gov` module's analogous deferred-work queue, `ProcessVoteDelegationUpdatesThrough`, which explicitly caps work per block via `maxUpdates` — showing the codebase is aware of this DoS class elsewhere but the staking EndBlock queues lack the same protection: [3](#0-2) 

Crucially, `MsgDelegate`/`MsgUndelegate`/`MsgBeginRedelegate` are reachable by **any unprivileged EVM caller** through the staking precompile at `0x0000...1005`, not just by validators or CLI users: [4](#0-3) 

Each delegator/validator pair is capped at `MaxEntries` unbonding entries (default 7), but there is **no cap on the number of distinct delegator addresses**. An attacker can programmatically fund and drive an arbitrary number of EVM-derived accounts, each delegating a minimal amount and then undelegating in the same block, so that all resulting `UnbondingDelegation` entries share the same maturity timestamp and are drained together in one `EndBlock` call.

### Title
Unbounded UBD/redelegation queue drain in staking `EndBlock` allows unprivileged EVM callers to stall block processing - (File: `sei-cosmos/x/staking/keeper/val_state_change.go`)

### Summary
`BlockValidatorUpdates`, called every `EndBlock`, drains the entire unbonding-delegation queue, redelegation queue, and validator-unbonding queue via unbounded iterators with no per-block work limit. Any unprivileged account — including EVM contract callers using the staking precompile — can cheaply create a large number of minimal-amount delegations across many synthetic addresses and undelegate them in the same block so they all mature at an identical timestamp, forcing `EndBlock` to process an attacker-controlled, effectively unbounded number of bank transfers synchronously in a single block.

### Finding Description
`k.DequeueAllMatureUBDQueue` and `k.DequeueAllMatureRedelegationQueue` return and process **all** matured entries in one pass with no cap, and `BlockValidatorUpdates` calls `CompleteUnbonding`/`CompleteRedelegation` per pair, each performing a `bankKeeper.UndelegateCoinsFromModuleToAccount` call. [5](#0-4) 
`CompleteUnbonding` further loops over every mature entry for a pair: [6](#0-5) 

Delegation/undelegation is reachable by any unprivileged sender both natively and via the EVM staking precompile at `0x0000000000000000000000000000000000001005`, so an attacker does not need validator privileges, leaked keys, or node compromise — only enough usei to pay minimal delegate/undelegate amounts and gas across many addresses. [7](#0-6) 

Because the queue key is time-based and coarse (per-timestamp buckets), an attacker submitting many minimal delegate+undelegate pairs within the same block(s) causes all resulting entries to mature together, concentrating the drain work into a single `EndBlock` call at a chosen future height.

### Impact Explanation
This maps to the explicitly accepted impact of "block delay beyond 2.5 seconds": an attacker-timed, outsized `EndBlock` workload (bank transfers plus store writes/deletes for each matured entry, all under the deterministic consensus path) can materially slow or, at extreme entry counts, stall block finalization for every node on the network — a chain-wide liveness risk rather than merely a fund-locking issue for a single subnet actor as in the original report.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to fund and drive many distinct addresses through minimal delegate/undelegate transactions (some gas/fee cost per operation, and possibly minimum-delegation-amount checks if configured), but nothing in the reviewed code caps the number of distinct delegator/validator pairs that can mature in the same window, and the staking precompile makes this trivially scriptable from a single EVM-connected wallet cycling through generated addresses.

### Recommendation
Bound per-block work in `BlockValidatorUpdates` analogous to `x/gov`'s `ProcessVoteDelegationUpdatesThrough`: cap the number of unbonding/redelegation entries drained per `EndBlock` (carrying over the remainder to subsequent blocks), and/or enforce a minimum delegate/undelegate amount to raise the cost of flooding the queue with dust entries.

### Proof of Concept
1. Deploy/generate N EVM-derived accounts and fund each with minimal usei.
2. From each account, call the staking precompile's `delegate(validator)` with a minimal `usei` amount, then immediately `undelegate(validator, amount)` in the same or adjacent block, for a large N (e.g., thousands), targeting entries that will mature at the same future block time (`UnbondingTime` after submission).
3. At the maturity height, `EndBlock` → `BlockValidatorUpdates` → `DequeueAllMatureUBDQueue` returns all N pairs at once and `CompleteUnbonding` performs N bank transfers synchronously in that single `EndBlock`, measurably increasing that block's processing time relative to normal blocks.

// DequeueAllMatureUBDQueue returns a concatenated list of all the timeslices inclusively previous to
// currTime, and deletes the timeslices from the queue.
func (k Keeper) DequeueAllMatureUBDQueue(ctx sdk.Context, currTime time.Time) (matureUnbonds []types.DVPair) {
	store := ctx.KVStore(k.storeKey)

	// gets an iterator for all timeslices from time 0 until the current Blockheader time
	unbondingTimesliceIterator := k.UBDQueueIterator(ctx, ctx.BlockHeader().Time)
	defer func() { _ = unbondingTimesliceIterator.Close() }()

	for ; unbondingTimesliceIterator.Valid(); unbondingTimesliceIterator.Next() {
		timeslice := types.DVPairs{}
		value := unbondingTimesliceIterator.Value()
		k.cdc.MustUnmarshal(value, &timeslice)

		matureUnbonds = append(matureUnbonds, timeslice.Pairs...)

		store.Delete(unbondingTimesliceIterator.Key())
	}

	return matureUnbonds
}

// CompleteUnbonding completes the unbonding of all mature entries in the
// retrieved unbonding delegation object and returns the total unbonding balance
// or an error upon failure.
func (k Keeper) CompleteUnbonding(ctx sdk.Context, delAddr sdk.AccAddress, valAddr sdk.ValAddress) (sdk.Coins, error) {
	ubd, found := k.GetUnbondingDelegation(ctx, delAddr, valAddr)
	if !found {
		return nil, types.ErrNoUnbondingDelegation
	}

	bondDenom := k.GetParams(ctx).BondDenom
	balances := sdk.NewCoins()
	ctxTime := ctx.BlockHeader().Time

	delegatorAddress, err := sdk.AccAddressFromBech32(ubd.DelegatorAddress)
	if err != nil {
		return nil, err
	}

	// loop through all the entries and complete unbonding mature entries
	for i := 0; i < len(ubd.Entries); i++ {
		entry := ubd.Entries[i]
		if entry.IsMature(ctxTime) {
			ubd.RemoveEntry(int64(i))
			i--

			// track undelegation only when remaining or truncated shares are non-zero
			if !entry.Balance.IsZero() {
				amt := sdk.NewCoin(bondDenom, entry.Balance)
				if err := k.bankKeeper.UndelegateCoinsFromModuleToAccount(
					ctx, types.NotBondedPoolName, delegatorAddress, sdk.NewCoins(amt),
				); err != nil {
					return nil, err
				}

				balances = balances.Add(amt)
			}
		}
	}

	// set the unbonding delegation or remove it if there are no more entries
	if len(ubd.Entries) == 0 {
		k.RemoveUnbondingDelegation(ctx, ubd)
	} else {
		k.SetUnbondingDelegation(ctx, ubd)
	}

	return balances, nil
}
