### Title
FROST cached-preprocess reuse across repeated `share_internal` calls leaks the MuSig signing key — (File: `coordinator/src/tributary/signing_protocol.rs`)

### Summary
The UAF bug class (use of a resource that should have been consumed/invalidated) maps onto Serai as **reused one-shot signing state**: `SigningProtocol::preprocess_internal` reloads the same `CachedPreprocesses` seed from the DB for every call within a context, so `DkgConfirmer::share()` and `DkgConfirmer::complete()` each rebuild an `AlgorithmSignMachine` from the identical `CachedPreprocess` seed — regenerating identical FROST nonces — and emit signature shares. If the message or the participant/preprocess set differs between two such calls for the same `attempt`, two Schnorr shares are published under the same nonce with different challenges/binding factors, which is the textbook nonce-reuse recovery of the secret key.

### Finding Description
`preprocess_internal` checks `CachedPreprocesses::get(self.txn, &self.context)`; if a seed exists it simply decrypts and reuses it via `AlgorithmSignMachine::from_cache` — it never deletes or rotates the entry [1](#0-0) . `from_cache` feeds that seed into `ChaCha20Rng::from_seed`, deterministically re-deriving the same `nonces` in `seeded_preprocess` [2](#0-1) . The FROST spec in-tree is explicit: "Reusing preprocesses would enable a third-party to recover your private key share. Accordingly, you MUST not reuse preprocesses" [3](#0-2) .

`share_internal` calls `preprocess_internal` every time it runs [4](#0-3) , and `DkgConfirmer::complete` invokes `share_internal` *again* after `share()` may already have run for the same `attempt` context `(b"DkgConfirmer", attempt)` [5](#0-4) . The `msg` passed to `machine.sign` is built from `self.removed` and `key_pair`, and the binding factors are derived from a rho transcript committing to the full preprocess set and `C::hash_msg(msg)` [6](#0-5) [7](#0-6) . Therefore any two invocations for the same attempt that differ in the preprocess set, the `removed` list, or the `key_pair` produce shares of the form `s = λ·x·c + d + ρ·e` with identical `(d, e)` but different `c`/`ρ` — solvable for the MuSig secret share `x`.

### Impact Explanation
Recovery of the coordinator's MuSig secret key share. Shares are broadcast publicly, so any observer who collects two same-nonce shares for differing signing sets/messages solves a linear system for the share — and because MuSig aggregates all participants, repeated reuse across validators collapses the aggregate key, enabling forgery of `set_keys_message` signatures. This is the "key share recovery" impact class explicitly in scope.

### Likelihood Explanation
The cached-seed reuse is unconditional (deterministic `from_cache` on every call); only divergence of inputs between calls is needed. Divergence is reachable when `share`/`complete` are retried with a different preprocess map (e.g., an `InvalidParticipant` error path returning and the tributary later supplying a different set), when `removed` changes between calls, or when `complete` re-signs after `share` was invoked under different parameters. Note the trigger path flows through tributary/validator-supplied preprocesses, so realization plausibly requires a validator-class participant to supply the divergent input — which limits, but does not eliminate, reachability; a crash/restart or retry between `share` and `complete` under changed `removed`/`key_pair` also suffices. Because exploitation conditions partially depend on validator-supplied inputs, this is High rather than Critical.

### Recommendation
Delete or rotate the `CachedPreprocesses` entry atomically the first time `share_internal` runs for a context (e.g., `CachedPreprocesses::kill` after loading, and re-generate via `preprocess(&mut OsRng)` on subsequent calls), or cache the produced `AlgorithmSignMachine`/share itself and return the identical share for identical inputs while rejecting divergent ones. Persist a record of which `(msg, included-set)` was signed so `complete` cannot silently re-sign under a different transcript.

### Proof of Concept
1. For attempt `a`, context `(b"DkgConfirmer", a)` stores seed `S`; `preprocess()` publishes commitments `D = G·d, E = G·e` derived from `ChaCha20Rng::from_seed(S)` [8](#0-7) .
2. Call `DkgConfirmer::share(preprocesses_A, key_pair_A)` → `share_internal` rebuilds the machine from `S`, computes share `s1 = λ·x·c1 + d + ρ1·e`, broadcast publicly.
3. Later call `DkgConfirmer::complete(preprocesses_B, key_pair_B, shares)` (or `share` again) where the preprocess map or `key_pair`/`removed` differs → `share_internal` rebuilds the *same* `(d, e)` from `S` but the rho transcript and `msg` differ, yielding `s2 = λ·x·c2 + d + ρ2·e` with `c1 ≠ c2`.
4. Observer computes `d + ρ1·e = s1 − λ·x·c1`-style elimination: with `ρ1, ρ2, c1, c2` all publicly derivable from the transcripts, the two equations `s1 − s2 = λ·x·(c1 − c2) + (ρ1 − ρ2)·e` combined with the commitment `E = G·e` … more directly, standard two-share nonce reuse solves for the scalar nonce and then for `x` since `s − (d + ρ·e) = λ·x·c`. The recovered `x` is the coordinator's MuSig secret key for that set.

This stands on Serai's own code path (`signing_protocol.rs` → `frost/src/sign.rs::seeded_preprocess`/`sign`), independent of the Chrome UAF report, which served only as the "consumed-state reuse" bug-class hint.
