## Analysis

The reported symbol is real, but the exploit's causal mechanism is misdiagnosed. The zero `KVGasConfig`/`TransientKVGasConfig` set in `ConvertCoinToERC20FromPacket` only waives store-access gas metering to spare relayers extra cost, matching the identical pattern used in `x/ibc/transfer/keeper/msg_server.go` `Transfer`. It does not remove the EVM's own gas accounting: `CallEVM` still executes with a bounded gas limit (`config.DefaultGasCap`) inside a `ctx.CacheContext()` branch, and any revert/out-of-gas inside that branch is discarded without calling `commitState()`. [1](#0-0) [2](#0-1) 

The real defect is independent of gas metering: `ConvertCoinNativeERC20` escrows the coin from the sender to the `erc20` module account on the **real** context *before* invoking the EVM transfer: [3](#0-2) 

If the ERC20 `transfer` call reverts (an ordinary, gas-cheap `require(false)`/blacklist/pause condition — no unbounded gas is needed), `CallEVM`'s internal cache is discarded, but the escrow already committed on the outer `ctx` is **not** rolled back, and `ConvertCoinNativeERC20` returns an error: [4](#0-3) 

For the ordinary `MsgConvertCoin` entrypoint this is safe because baseapp discards the *entire* tx-level cache multistore when a message returns an error, so the escrow never persists. However, `ConvertCoinToERC20FromPacket` (invoked from `OnAcknowledgementPacket`/`OnTimeoutPacket` during IBC refund) explicitly **swallows** this error, only emitting a failure event and returning `nil`: [5](#0-4) 

Because the enclosing IBC callback reports success, the tx that carries the `MsgTimeout`/`MsgAcknowledgement` commits normally — including the earlier escrow write — while the compensating ERC20 transfer/burn never happens. This directly contradicts the function's own documented contract ("the user receives the corresponding bank token from the TokenPair instead"), and permanently strands the refunded coin in the `erc20` module account with no keeper method to recover it, requiring a coordinated upgrade to fix.

### Title
Refund-path error swallowing in `ConvertCoinToERC20FromPacket` permanently strands escrowed coins when the native-ERC20 `transfer` reverts - (File: `x/erc20/keeper/ibc_callbacks.go`)

### Summary
`ConvertCoinNativeERC20` escrows Cosmos coins into the `erc20` module account before calling the backing ERC20 contract's `transfer`. When that call reverts, the earlier escrow is not undone, and `ConvertCoinToERC20FromPacket` (used on IBC timeout/ack-error refund) discards the resulting error instead of propagating it, so the tx still commits and the coins remain locked in module escrow forever.

### Finding Description
`ConvertCoinNativeERC20` performs `SendCoinsFromAccountToModule` directly on the passed-in `ctx` (not a cache context) and only afterward calls `k.evmKeeper.CallEVM(...,"transfer",...)`, whose failures are isolated to their own internal `CacheContext` and don't roll back the earlier escrow write. [6](#0-5) 

For the synchronous `MsgConvertCoin`/`MsgConvertERC20` entrypoints, an error returned here fails the whole message, and baseapp discards the entire tx-scoped cache multistore, so no partial escrow persists — this is the safe path, matching the mocked "force evm fail" tests.

The IBC refund path is different: `ConvertCoinToERC20FromPacket`, called from `OnAcknowledgementPacket` (error ack) and `OnTimeoutPacket`, catches the `ConvertCoinNativeERC20` error, emits `EventTypeFailedConvertERC20`, and returns `nil`. [7](#0-6) [5](#0-4) 

Because the callback reports success, the surrounding IBC message (`MsgTimeout`/`MsgAcknowledgement`) commits normally, persisting the escrow made moments earlier in `ConvertCoinNativeERC20` while never completing the compensating ERC20 transfer, mint, or burn. The coins sit in the `erc20` module account indefinitely with no keeper entrypoint to reclaim them, contradicting the function's documented fallback guarantee.

Note: the zero `KVGasConfig`/`TransientKVGasConfig` context cited in the question is unrelated to the trigger — it only removes store I/O gas costs and does not affect the EVM's own bounded gas accounting or `CallEVM`'s internal cache-context revert isolation, so no unbounded-gas or panic mechanism is required; an ordinary, cheap ERC20 `transfer` revert (e.g. a paused/blacklisted token, or a purpose-built malicious contract) is sufficient.

### Impact Explanation
Any coin whose backing native ERC20 contract can revert its `transfer` call (deliberately, via a malicious/pausable/blacklisting contract, or incidentally) will have refunded IBC value permanently locked in the `erc20` module account whenever a transfer using that denom times out or receives an error acknowledgement. This is a Critical, unrecoverable freezing of user funds/escrowed assets requiring a coordinated fix/hard fork, matching the Allowed Impact Gate.

### Likelihood Explanation
Triggering requires only ordinary, permissionless actions: convert an ERC20 to its Coin representation, send it via ICS-20, and have the packet time out or receive an error ack (both are normal, achievable outcomes, e.g. via a short timeout or an invalid receiver on the counterparty chain) for a token pair backed by a contract whose `transfer` can revert for the module's outbound call. If `PermissionlessRegistration` is enabled, an attacker can deploy and register their own malicious ERC20 to guarantee this deterministically for their own converted balance and any counterparties holding the token; even without permissionless registration, any already-approved native ERC20 with pause/blacklist logic exposes ordinary users to accidental permanent loss on refund.

### Recommendation
In `ConvertCoinToERC20FromPacket`, do not swallow errors from `ConvertCoinNativeERC20`; either propagate the error so the whole refund tx (and its escrow) is rolled back, or perform the escrow/CallEVM sequence inside an explicit `ctx.CacheContext()` and only commit it once the whole `ConvertCoinNativeERC20` operation (escrow + EVM transfer + burn) succeeds, falling back to leaving the coin with the original sender when the ERC20 leg fails, consistent with the documented behavior.

### Proof of Concept
1. Deploy a malicious/pausable ERC20 contract whose `transfer` succeeds for normal calls but reverts when called by `types.ModuleAddress` (or simply pause/blacklist the receiver later).
2. Register it as a native-ERC20 token pair (via `MsgRegisterERC20` if `PermissionlessRegistration` is enabled, or governance for a real pausable/blacklistable token).
3. Convert the ERC20 to its Coin representation with `MsgConvertERC20` (escrows tokens, mints coin) — `x/erc20/keeper/msg_server.go` `convertERC20IntoCoinsForNativeToken`.
4. Send the coin out via IBC `MsgTransfer` with a short timeout, or to an invalid receiver on the counterparty chain to force an error ack.
5. After timeout/ack-error, `OnTimeoutPacket`/`OnAcknowledgementPacket` invokes `ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20`, which escrows the refunded coin to the `erc20` module account then fails the `transfer` call.
6. Assert: the `erc20` module account balance for the denom is non-zero, the original sender's coin balance is zero, and the sender's ERC20 balance was never restored — funds are permanently stuck, with `EventTypeFailedConvertERC20` emitted but the surrounding tx marked successful.

func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}
