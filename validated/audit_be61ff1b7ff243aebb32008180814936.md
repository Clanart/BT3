## Analog Found

### Title
Git-argument injection via `branch` parameter in "Open in Desktop" deep links — the `--` end-of-options separator is placed *after* the untrusted ref name in `getBranchCheckoutArgs` - (File: `app/src/lib/git/checkout.ts`)

### Summary
The Uniswap-style report exploited a mismatch between a `require` guard and the *shape* of attacker-supplied calldata: the check existed but didn't anticipate the alternate input format. GitHub Desktop has an analogous mismatch: the deep-link handler validates a user-supplied `branch` string with a character blacklist that doesn't reject a leading `-`, and the git-invocation code that later consumes that string places the `--` end-of-options marker *after* the ref name instead of before it, so a maliciously shaped branch value can be parsed by `git checkout` as an option rather than a ref.

### Finding Description
`x-github-client://openRepo/...?branch=<value>` deep links are parsed in `parseAppURL` [1](#0-0) . For non-PR branches the only validation is:

```
if (branch != null && testForInvalidChars(branch)) {
  return unknown
}
```

`testForInvalidChars` only rejects control characters, spaces, and a fixed set of git-ref-illegal symbols (`~^:?*[\|""<>`, `@{`, consecutive dots, trailing `.lock`/`/`) — it does **not** reject a leading `-` [2](#0-1) . Note that the sibling function `sanitizedRefName` explicitly strips leading `-`/`+` when *sanitizing* a name, but `testForInvalidChars` (the boolean gate used by the URL parser) performs no such stripping — it only runs the character regex `.test()`.

This attacker-controlled `branch` value flows unmodified through `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl(url, branchName)` [3](#0-2)  and is eventually checked out via `checkoutBranch`, whose git argument list is built as:

```
async function getBranchCheckoutArgs(branch: Branch) {
  return [
    branch.name,
    ...(branch.type === BranchType.Remote ? ['-b', branch.nameWithoutRemote] : []),
    '--',
  ]
}
``` [4](#0-3) 

Here `branch.name` (attacker-controlled) is placed **first**, and the `--` end-of-options guard is placed **last**, after `branch.name` and any `-b <name>`. This is the same class of defect as the report: a protective construct exists (`--` is the canonical git idiom to stop option parsing, used correctly elsewhere in this same codebase, e.g. `clone.ts` line 123: `args.push('--', url, path)` and `checkoutPaths`/`checkoutConflictedFile` in the same file), but here it is positioned *after* the untrusted token instead of *before* it, so it provides no protection for `branch.name` itself. Combined with the deep-link validator's failure to reject a leading `-`, a crafted deep link's `branch` value is parsed by `git checkout` in the option-parsing phase rather than being forced into positional/ref interpretation.

### Impact Explanation
An attacker who gets a victim to click a `x-github-client://openRepo/...&branch=<payload>` link (equivalent to GitHub's "Open in Desktop" flow) can inject a token that `git checkout` interprets as a command-line flag rather than a branch name. Depending on which git-recognized option string is smuggled this can alter checkout behavior unexpectedly (e.g., force/track/orphan-style flags) against the victim's working tree, silently corrupting what gets checked out — matching the "silent corruption of what the user commits/pushes" impact class. The severity is bounded by which `git checkout` options are reachable (this environment doesn't demonstrate arbitrary code execution), but it is a genuine argument-injection primitive stemming from attacker-controlled, insufficiently-filtered input reaching an unguarded git invocation.

### Likelihood Explanation
The trigger is a single link click, which is within the "link the user clicks" attacker model. `testForInvalidChars` is the only gate and it structurally cannot block leading-dash payloads because it never strips or rejects the `-`/`+` prefix (unlike `sanitizedRefName`, which does but is not used on this path). No downstream code re-validates or re-sanitizes `branchName` before it is threaded into `Branch.name` and passed to `getBranchCheckoutArgs`.

### Recommendation
- In `parseAppURL`, reject (or sanitize via `sanitizedRefName`) branch values that begin with `-` before constructing `IOpenRepositoryFromURLAction`, consistent with how `pr`/`branch=pr/\d+` are strictly pattern-matched.
- In `getBranchCheckoutArgs`, move the `--` separator to precede `branch.name` (and any other untrusted ref-like arguments), matching the safe pattern already used in `clone.ts`, `checkoutPaths`, and `checkoutConflictedFile`.

### Proof of Concept
1. Craft a deep link: `x-github-client://openRepo/https://github.com/octocat/Hello-World?branch=--orphan%3Dpwned` (URL-encoded `=`), which decodes to `branch=--orphan=pwned`.
2. `testForInvalidChars('--orphan=pwned')` returns `false` (no disallowed characters present), so `parseAppURL` accepts it as a valid `IOpenRepositoryFromURLAction` with `branch: '--orphan=pwned'` [5](#0-4) .
3. Victim clicks the link; `handleAppURL` → `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl(url, '--orphan=pwned')` runs `checkoutLocalBranch` with the raw string.
4. `checkoutBranch` builds `args = ['checkout', branch.name, '--']`, i.e. `git checkout --orphan=pwned --`, where `--orphan=pwned` is parsed by git as the `--orphan` option rather than a positional branch reference [6](#0-5) .

Note: I was unable to fully trace `Dispatcher.checkoutLocalBranch`'s exact resolution logic (whether it always creates a `Branch` object from the raw string or performs an existence lookup first) before running out of tool iterations; this affects exactly which git-recognized option values are reachable in practice and should be verified against the live `checkoutLocalBranch` implementation in `app/src/ui/dispatcher/dispatcher.ts`.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)
