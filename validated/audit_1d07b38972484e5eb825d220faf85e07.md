### Title
Unauthenticated serialized `ReceivedOutput` is treated as spendable without proving the claimed outpoint exists - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` accepts an attacker-supplied offset, `TxOut`, and `OutPoint` without verifying that the outpoint exists on-chain or that the claimed amount and script match the actual UTXO. [1](#0-0)   
This is analogous to trusting a local package solely because its contents parse: the byte encoding carries no proof of repository or blockchain provenance.

### Finding Description
`ReceivedOutput` explicitly represents “A spendable output,” but its deserializer only performs syntactic scalar and Bitcoin consensus decoding. [2](#0-1) [1](#0-0)   
`SignableTransaction::new` then trusts the decoded `output.value` as available input value and the decoded `outpoint` as a transaction input. [3](#0-2)   
When creating the signer, `SignableTransaction::multisig` checks only that the supplied offset derives the claimed `script_pubkey`; it does not check that the referenced outpoint exists or contains that script and value. [4](#0-3)   
Signing subsequently commits the forged prevout list into every Taproot sighash through `Prevouts::All`. [5](#0-4) 

### Impact Explanation
An unprivileged party who can feed serialized `ReceivedOutput` bytes to the wallet can report funds as received and spendable even when the referenced UTXO does not exist, belongs to a different value, or was never produced by `Scanner`. [1](#0-0)   
The wallet may account for the fake balance and threshold-sign a transaction whose signatures commit to attacker-selected prevout data. [6](#0-5) [5](#0-4)   
Such a transaction is not spendable on Bitcoin unless the claimed outpoint genuinely matches the encoded UTXO, so this can corrupt balance tracking, create invalid transactions, and consume a signing round under false input data.

### Likelihood Explanation
The attack requires only control over bytes passed to the public `ReceivedOutput::read` API and acceptance of the resulting object by transaction construction. [1](#0-0)   
No private key, validator compromise, malformed curve point, or invalid Bitcoin signature is needed; the issue is that syntactically valid bytes are incorrectly treated as authenticated blockchain state.

### Recommendation
Treat serialized `ReceivedOutput` values as untrusted claims rather than proofs of spendability.  
Before accepting one, retrieve the referenced outpoint from a trusted Bitcoin node or verified SPV proof and require the on-chain `TxOut` to exactly match the deserialized script and value.  
Persist and re-authenticate scanner provenance, or make the serialized format carry an authenticated scan result binding the wallet key, offset, outpoint, `TxOut`, block hash, and chain position.

### Proof of Concept
The following construction creates a syntactically valid `ReceivedOutput` for an arbitrary nonexistent `OutPoint`:

```rust
use bitcoin::{
  consensus::Encodable,
  Amount, OutPoint, TxOut,
};
use k256::Scalar;
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction};

let wallet_script = /* even Taproot script for keys.group_key() */;
let forged_outpoint = OutPoint::default();
let forged_output = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: wallet_script.clone(),
};

let mut bytes = Vec::new();
bytes.extend(Scalar::ZERO.to_bytes());
forged_output.consensus_encode(&mut bytes).unwrap();
forged_outpoint.consensus_encode(&mut bytes).unwrap();

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(forged.value(), 1_000_000);
assert_eq!(forged.outpoint(), &forged_outpoint);
```

`ReceivedOutput::read` accepts these bytes because it never consults the blockchain. [1](#0-0)   
`SignableTransaction::new` counts the forged million-satoshi output as spendable input and installs the fake outpoint as a `TxIn`. [3](#0-2)   
`multisig` accepts the input whenever the supplied zero offset derives `wallet_script`, without checking the outpoint. [4](#0-3)   
The resulting signing machine commits to the forged `TxOut` and `OutPoint` via `Prevouts::All`, producing signatures for a transaction the Bitcoin network cannot accept unless that UTXO actually exists with identical data. [5](#0-4)
