## Analysis

The Mute report's broken invariant is: **a permission/trust decision is made once, at a single checkpoint, and then relied upon indefinitely without re-verifying that the underlying state hasn't changed in the interim** (dMute delegation balance checked only at the staking block, never re-validated).

The closest structural analog I found in GitHub Desktop is in the Copilot merge-conflict context builder, where a symlink/path-traversal safety check (`resolveWithin`) is performed once, and its result — a path string that has *not* itself been fully de-referenced — is reused across multiple subsequent filesystem calls (`stat`, `readFile`) that will re-resolve symlinks at call time. This creates the same "checked-once, trusted-forever" gap.

### Title
TOCTOU symlink race between `resolveWithin` safety check and subsequent `stat`/`readFile` in Copilot conflict context builder - (File: `app/src/lib/copilot-conflict-context.ts`)

### Summary
`buildConflictContext` validates each conflicted file's path with `resolveWithin(workingDirectory, file.path)` [1](#0-0)  to guard against path traversal and symlink escapes. However, the value returned and used afterwards is the pre-realpath `resolved` string, not the `realResolved` value that the check itself computed via `fs.realpath` [2](#0-1) . The code then performs a separate `stat` and `readFile` on that same path string later in the same function [3](#0-2) . Each of these operations independently re-resolves any symlink components in the path at the moment they run, rather than reusing the already-validated real path.

### Finding Description
`resolveWithin` computes `realpath(resolved)` to confirm the target sits inside `realRoot`, then returns the *unresolved* `resolved` path if the check passes [4](#0-3) . `buildConflictContext` uses that returned path for two subsequent, independently-scheduled async filesystem operations — `stat(absolutePath)` and `readFile(absolutePath, 'utf8')` [5](#0-4)  — each of which re-walks the path and follows whatever symlink target exists *at that moment*, not the one that existed when `resolveWithin` ran its check. This is the exact "checked-at-T1, used-at-T2-without-re-check" pattern from the Mute finding: a guard is evaluated once, and every later consumer implicitly assumes it still holds.

Because this whole pipeline runs over an attacker-influenced source (a merge/rebase/cherry-pick conflict originating from a cloned or fetched branch), the attacker fully controls `file.path`'s structure, including intermediate path components that resolve to symlinks. If anything in the environment (another concurrent Desktop git operation on the same repository, a background index/checkout step, or a hook-triggered process) can retarget the symlink between the `resolveWithin` check and the later `stat`/`readFile` calls — which run in a `Promise.all` over many files, giving a real scheduling window — the file ultimately read can point outside the repository working directory.

### Impact Explanation
`buildConflictContext`'s output (`rawContent`) is subsequently sent off to the Copilot SDK as part of the conflict-resolution prompt [6](#0-5) . If the symlink race succeeds, the content of an arbitrary file outside the repository (e.g., SSH private keys, `.netrc`, credential helpers, or other sensitive local files) can be read into memory and transmitted to an external API endpoint, constituting credential/token exfiltration and file-read-outside-the-repo impact — squarely in the accepted impact categories.

### Likelihood Explanation
Likelihood is **low-to-moderate**: it requires the attacker-crafted repository to contain conflicting paths with symlink components, and it requires a scheduling window between the `resolveWithin` check and the later `stat`/`readFile` to be won, which is not attacker-triggerable on demand from a static malicious repo alone — it needs some concurrent filesystem mutation (e.g., another operation performed by Desktop on the same working directory during conflict resolution, or a symlink target that legitimately changes as part of the merge/checkout machinery itself). This is weaker than a fully deterministic exploit, but the underlying guard is genuinely unsound: `resolveWithin` returns a value that does not carry the guarantee it just proved, so any future refactor that widens the window (e.g., adding more async steps between validation and use, or reusing `resolved` elsewhere) reintroduces the bug silently.

### Recommendation
Return and use the already-verified `realResolved` path (or re-run `realpath` immediately before each filesystem operation and compare) so that the value trusted by `stat`/`readFile` is the same one that was actually checked against `realRoot`, closing the gap between validation and use — mirroring the report's own recommendation of not trusting a single point-in-time check for something that must remain true until use.

### Proof of Concept
1. Prepare a malicious repository where a conflicted file path (e.g. `dir/link`) is a symlink pointing to a location inside the repo (passes `resolveWithin`'s `realpath` check).
2. Trigger a merge/rebase/cherry-pick against this branch so `buildConflictContext` is invoked with conflicted files including this path [7](#0-6) .
3. Between the `resolveWithin` call and the later `stat`/`readFile` calls (both scheduled as part of a `Promise.all` over potentially many files, widening the timing window), retarget the symlink to point at a sensitive out-of-repo file (e.g. `~/.ssh/id_rsa`).
4. `stat`/`readFile` follow the new symlink target and its contents are folded into `rawContent`, which is then formatted into the Copilot prompt [8](#0-7)  and sent to the Copilot SDK, exfiltrating the file's contents.

export async function buildConflictContext(
  ourLabel: string,
  theirLabel: string,
  workingDirectory: string,
  files: ReadonlyArray<{
    readonly path: string
    /** Which side deleted the file (for delete-vs-modify conflicts). */
    readonly deletedSide?: 'ours' | 'theirs'
  }>
): Promise<ICopilotConflictContext> {
  const results = await Promise.all(
    files.map(async (file): Promise<IFileConflictContext> => {
      // Delete-vs-modify conflicts have no text markers on disk. Include
      // them in the context with metadata so the model can recommend
      // keep or delete — no file content is needed.
      if (file.deletedSide !== undefined) {
        return {
          path: file.path,
          hunks: [],
          deleteConflict: { deletedSide: file.deletedSide },
        }
      }

      // Guard against path traversal and symlink escapes (cross-platform)
      let absolutePath: string | null
      try {
        absolutePath = await resolveWithin(workingDirectory, file.path)
      } catch {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'File path could not be resolved safely',
        }
      }
