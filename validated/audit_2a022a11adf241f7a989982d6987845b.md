Based on the direct code I was able to inspect, the strongest local analog to the "lack of timeout to resolve" bug class is in the Intent Gateway's cross-chain cancel-from-destination path, where a state-finalizing write is not gated on the order's current fill status, combined with the fact that the message that reconciles that state on the source chain (`RedeemEscrow`/`RefundEscrow`) is dispatched with `timeout: 0` — i.e., it has no expiry and can be resolved at an arbitrary, attacker-influenced time.

### Title
Missing "already filled" guard in `_cancelFromDest` combined with untimed `RedeemEscrow`/`RefundEscrow` settlement allows escrow to be redirected away from the solver that already paid out - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`_cancelFromDest` unconditionally overwrites `_filled[commitment]` and dispatches a `RefundEscrow` message to the source chain without checking whether the order was already filled by a solver. Because the settlement messages that reconcile escrow on the source chain (`RedeemEscrow` from a fill, `RefundEscrow` from a cancel) are both dispatched with `timeout: 0` (never expire, can be delivered whenever a relayer chooses), two competing finalization messages can be in flight for the same order simultaneously, and whichever is delivered first wins the escrow.

### Finding Description
In `_fillCrossChain` [1](#0-0) , a solver fills the order, transfers output tokens to the beneficiary, and dispatches a `RedeemEscrow` message back to the source chain with `timeout: 0` [2](#0-1) .

In `_cancelFromDest`, the only guard is on `order.deadline` vs. `msg.sender`; there is no check that `_filled[commitment] == address(0)` before it overwrites `_filled[commitment]` to the order's user and dispatches a `RefundEscrow` message, also with `timeout: 0`: [3](#0-2) 

Because both messages never time out, delivery order to the source chain is purely a function of relayer timing, not protocol logic. If a solver fills the order (setting `_filled` to the solver and queuing `RedeemEscrow`) shortly before `order.deadline`, and the `RedeemEscrow` message has not yet been relayed to the source chain, anyone (after the deadline, cancellation from destination is permissionless: `if (order.deadline >= _blockNumber()) { ... }` else no `Unauthorized` check at all) can call cancel again, overwrite `_filled[commitment]` to the user, and queue a `RefundEscrow` message for the same commitment.

On the source chain, `onAccept` dispatches to `_withdraw` for whichever message arrives first [4](#0-3) , and `_withdraw` decrements `_orders[commitment][token]` and reverts on the second call with `UnknownOrder` once escrow is exhausted [5](#0-4) . This "first message wins" semantics means the payout beneficiary is determined by network/relayer race conditions rather than by which action actually occurred first (fill vs. cancel) — exactly the "resolve at an arbitrary time" pattern in the seed report, except here the resolvable outcome directly controls fund custody.

### Impact Explanation
If the `RefundEscrow` message is delivered to the source chain before the legitimate `RedeemEscrow` message (e.g., because a relayer prioritizes it, or the original relayer is slow/offline), the escrowed input tokens are paid to the order's original user even though the solver has already irrevocably delivered the output tokens to the beneficiary on the destination chain. This is a direct loss of solver funds and an unauthorized/incorrect settlement of escrow to the wrong beneficiary — matching the bounty's "wrong beneficiary or amount" and "logic attack on intent settlement" impact categories.

### Likelihood Explanation
The path requires no privileged role, no malicious relayer/prover assumption, and no admin action — only ordinary permissionless calls (`fillOrder`, `cancelOrder`) plus the natural asynchrony of cross-chain message delivery that Hyperbridge already tolerates for untimed (`timeout: 0`) messages. The precondition (a fill happening close to `order.deadline`, followed by any delay in `RedeemEscrow` delivery) is a normal operational condition, not a contrived edge case, making the race practically triggerable.

### Recommendation
`_cancelFromDest` should revert if `_filled[commitment] != address(0)` before proceeding, mirroring the check already used to gate `fillOrder`. More generally, resolution messages (`RedeemEscrow`/`RefundEscrow`) that finalize escrow custody should not be dispatched with `timeout: 0`; consider a bounded timeout so that stale, out-of-order settlement attempts are automatically invalidated rather than left to race indefinitely, and/or require the source-chain `onAccept` to validate a monotonic sequence/nonce per commitment rather than accepting whichever settlement message arrives first.

### Proof of Concept
1. User places a cross-chain order on chain A with `deadline = D`.
2. Solver calls `fillOrder` on chain B at block `D-1`: `_filled[commitment] = solver`; output tokens sent to beneficiary; `RedeemEscrow` dispatched to chain A with `timeout: 0` (per `_fillCrossChain`, lines 89-171).
3. `RedeemEscrow` relay to chain A is delayed (network conditions, relayer downtime — no timeout enforces urgency).
4. At block `D+1` (deadline passed), any address calls `cancelOrder` targeting the destination path; `_cancelFromDest` runs with no check that `_filled[commitment]` is already non-zero, overwrites it to `user`, and dispatches `RefundEscrow` to chain A with `timeout: 0` (lines 240-267).
5. `RefundEscrow` reaches chain A's `onAccept` before the original `RedeemEscrow`; `_withdraw` pays the escrowed input tokens to `user` and zeroes `_orders[commitment][token]`.
6. When `RedeemEscrow` finally arrives, `_withdraw` reverts with `UnknownOrder` — the solver never recovers the input tokens it was owed for output tokens it already delivered.

Note: I was unable to inspect the outer `cancelOrder` entry point in `evm/src/apps/IntentGatewayV2.sol` in this session to confirm whether it applies a redundant `_filled == 0` check before calling `_cancelFromDest`; if such a check exists there, it would need to be verified against this exact race window (fill and cancel calls interleaved across two separate transactions/chains) before treating this as fully unmitigated. This should be verified directly in the repository.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
