## Title
Commit metadata misalignment via embedded NUL-byte delimiter collision in `createLogParser` - (File: `app/src/lib/git/git-delimiter-parser.ts`)

### Summary
`createLogParser()` builds commit records from `git log --format=...%x00...` output by naively splitting the raw stdout on the NUL (`\0`) byte and grouping records into fixed-size chunks of `keys.length`. It never verifies that the resulting record count is actually a multiple of `keys.length`, nor that each field is free of the delimiter byte it relies on. A commit whose message body/trailers contain a raw embedded NUL byte — fully attacker-controllable content in a git object an attacker crafts and the victim later clones/fetches — desynchronizes the field boundaries for that commit and every subsequent commit parsed in the same batch.

### Finding Description
`createLogParser` is used by `getCommits()` in `app/src/lib/git/log.ts` to parse `git log` output into `sha`, `shortSha`, `summary`, `body`, `author`, `committer`, `parents`, `trailers`, and `refs` fields, using `%x00` as the field separator: [1](#0-0) 

The parser itself blindly walks the split array in fixed strides of `keys.length` without validating that record boundaries line up: [2](#0-1) 

Git commit messages (`%b`, unfolded trailers `%(trailers:unfold,only)`) are raw bytes taken directly from a commit object's content. An attacker who controls a repository (e.g. via a crafted commit created with low-level plumbing such as `git commit-tree` / `hash-object`, bypassing the porcelain's usual text sanitation) can embed a literal `\0` byte inside the commit body or a trailer value. Because `git()` is invoked with `encoding: 'buffer'` and the entire stdout is split solely on `\0` (see `records = ... value.split('\0')` in `git-delimiter-parser.ts`), that embedded byte is indistinguishable from the intended field separator.

This is exactly the "missing equal-length check" bug class from the report, translated to Desktop's domain: the code assumes each parsed "row" contains exactly `keys.length` aligned fields (analogous to assuming `ids.length == to.length == amounts.length`), but never checks this invariant. One malformed/extra field silently shifts every subsequent `keys`-sized grouping by one slot, just as a short array in the Solidity report caused later elements to be silently misassigned rather than rejected.

### Impact Explanation
Because the loop bound is `records.length - keys.length` with no assertion of exact divisibility, the malformed commit's own fields — and every commit's fields after it in that `git log` invocation — get bound to the wrong key names (e.g., what should be `parents` gets assigned to `sha`, `body` bleeds into `author`, etc.), with no error, no crash, and no user-visible warning (unlike `createForEachRefParser`, which at least throws `'Expected newline'` on misalignment; `createLogParser` has no equivalent guard). Downstream, `getCommits()` converts these misaligned fields directly into `Commit` objects used throughout the UI/history views and action flows (revert, cherry-pick, reset, "view on GitHub", diff-against-parent). A user relying on the displayed SHA/summary/parent for a commit could unknowingly trigger a destructive git operation (revert/reset/cherry-pick) against a different commit than what is shown, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitation only requires the victim to clone or fetch a repository containing one attacker-crafted commit object with a raw NUL byte in its message/trailers — no local access, no elevated privileges, and no unnatural workflow beyond normal "browse history in Desktop" usage, satisfying the valid-impact criteria (attacker controls a cloned/fetched repository). The trigger path is the default `History` view (`getCommits`), which every Desktop user exercises on any repo they open.

### Recommendation
Harden `createLogParser`'s `parse()` function in `app/src/lib/git/git-delimiter-parser.ts` to:
1. Assert `(records.length - 1) % keys.length === 0` (or equivalent) and throw/skip on mismatch instead of silently truncating/misaligning.
2. Use a delimiter combination that cannot collide with arbitrary attacker-controlled byte content (e.g., a unique multi-byte marker, or better, invoke `git log` per-record with `-z` and use `%x1e`/record separators plus explicit per-field length prefixes), or sanitize/reject commit content containing the raw delimiter before splitting.

### Proof of Concept
1. Attacker creates a repository and, using plumbing commands (not the normal `git commit` porcelain, which strips such content), crafts a commit whose message contains a literal NUL byte, e.g.:
   ```
   printf 'legit summary\n\nbody-part-1\x00INJECTED' | git hash-object -w --stdin -t blob # (or via commit-tree with a NUL in the message)
   ```
   producing a commit object whose `%b` field contains an embedded `\0`.
2. Victim clones/fetches this repository in GitHub Desktop and opens the History tab, invoking `getCommits()` (`app/src/lib/git/log.ts:120`), which calls `git log ... %x00 ...` and pipes buffer output into `createLogParser().parse()`.
3. In `git-delimiter-parser.ts`'s `parse`, the extra NUL splits `records` into one additional element for the malicious commit, shifting all subsequent `keys.length`-sized groupings for every commit after it in the returned log — while `parse()` returns successfully with no error, and `getCommits()` builds `Commit` objects from the misaligned fields.
4. The History list now displays incorrect SHA/author/parent/summary associations for commits following the malicious one, and any action taken against a listed commit (revert, cherry-pick, reset) resolves to the wrong underlying commit object.

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }
