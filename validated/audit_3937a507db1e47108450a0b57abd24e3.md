## Finding

The reported concern about `RepositoriesDatabase.repositories`' `path` field itself being a symlinked directory isn't exploitable — that value is only ever a directory the *user* selects locally (via "Add local repository" or "Clone"), not something an attacker's repository content can control. However, investigating the same "path-containment" theme surfaced a real, related issue: **paths *within* a cloned repository can be symlinks, and several file-read code paths join them onto `repository.path` and hand them to Node's `fs` APIs without any containment check**, unlike the one place in the codebase that was hardened for this (`resolveWithin`).

### Title
Symlinked tracked files bypass repository path-containment, allowing arbitrary file read via diff/image preview — (File: `app/src/lib/git/diff.ts`, `app/src/ui/diff/syntax-highlighting/index.ts`)

### Finding Description
The codebase has a dedicated helper, `resolveWithin`, that joins a relative path onto a root, then calls `realpath` on both the root and the resolved path and verifies the resolved real path is still contained under the real root — explicitly to guard against symlink escapes: [1](#0-0) 

This is used when building AI/Copilot conflict context, specifically because that content is sent to a model: [2](#0-1) 

However, other code that reads file contents from the working directory using an attacker-influenced relative `file.path` does **not** use `resolveWithin` — it just does `Path.join(repository.path, file.path)` and passes the result straight to `fs`:

- Image preview for a working-directory file change: [3](#0-2) 

- Syntax-highlighting content loader for the diff viewer: [4](#0-3) 

- "Open file" from the Changes sidebar: [5](#0-4) 

Because `file.path` values come from `git status`, they will not themselves contain `..` traversal segments, but a tracked entry can be a symlink (git blob mode `120000`). When such a repository is cloned with `core.symlinks=true` (the default on macOS/Linux), the checked-out leaf is a real OS-level symlink that can point anywhere on the victim's filesystem (e.g. `~/.ssh/id_rsa`, `~/.aws/credentials`, or via a relative `../../../..` target). `Path.join`/`fs.readFile` follow that symlink transparently — there is no `realpath` containment check comparable to `resolveWithin`, so the "resolved path is within the repository" invariant is silently violated.

### Impact Explanation
Viewing the image diff or syntax-highlighted diff/content for such a file (or using "Open file"), causes GitHub Desktop to read and render file content from outside the cloned repository directory. This is explicitly listed as valid impact ("file read... outside the repo"). Impact is bounded by the fact that this only discloses content back into the local Desktop UI for the same local user — there is no automatic network exfiltration path from these three call sites (contrast with the Copilot context path, which is guarded precisely because it's transmitted externally).

### Likelihood Explanation
Moderate. Requires: (1) `core.symlinks` enabled (default true on macOS/Linux, false by default on Windows without Developer Mode/admin — see fixture configs showing `symlinks = false` on Windows-oriented fixtures), (2) the user must open the specific file's diff/image preview or explicitly "Open file", and (3) the attacker must guess a path on the victim's machine to target, since there's no feedback loop for the attacker to know what was read.

### Recommendation
Route all working-directory file reads that are keyed off git-reported relative paths (`getWorkingDirectoryImage`, `getNewFileContent`/`getOldFileContent` in the syntax-highlighting module, and the "Open file" handler) through `resolveWithin`/`resolveWithinPosix`, mirroring the guard already applied in `copilot-conflict-context.ts`, and refuse to read/open when resolution returns `null`.

### Proof of Concept
1. Create a repository containing a tracked symlink, e.g. `evil.png -> ../../../../etc/passwd` (or an absolute path to a known-sensitive file on the target OS), committed with `git add` + `update-index --chmod` semantics (symlink mode `120000`).
2. Have the victim clone this repository on macOS/Linux (default `core.symlinks=true`).
3. Modify `evil.png`'s target file externally (not needed if attacker just wants to view a static file) and open the repository in Desktop; select the file to view its diff/image preview, or use "Open file" from the Changes list.
4. Observe that `getWorkingDirectoryImage`/`getNewFileContent` reads and renders the symlink target's content (outside the repository directory) rather than refusing or restricting to the repo root, unlike the equivalent Copilot-context path which correctly returns `null`/`skippedReason` via `resolveWithin`.
