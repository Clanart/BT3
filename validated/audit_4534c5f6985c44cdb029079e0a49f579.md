## Title
Cross-Function Reentrancy in `_fillSameChain` Allows Order Cancellation Mid-Fill, Draining Solver-Funded Escrow to the Attacker - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
The Lybra report's core lesson is: an external call made to an address the protocol doesn't fully control, before internal accounting is finalized, opens a reentrancy window that can be used to corrupt escrow/balance state. Hyperbridge's `IntentGatewayV2` already found and fixed a *same-function* variant of this (self-refill during `fillOrder`, see `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`). However, that fix only guards against re-entering `fillOrder` itself via the `_filled[commitment]` check. It does not protect the escrow map `_orders[commitment][token]` against being drained by a *different* public entrypoint — `cancelOrder` — during the native-token payout loop in `_fillSameChain`.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:54-149`), for each output asset the function:
1. Sets `_filled[commitment] = msg.sender` up front (CEI for `fillOrder` re-entry only).
2. Inside the per-output loop, for a native-token output, sends ETH directly to `order.output.beneficiary` via a low-level `.call` **before** reading or mutating the input escrow: [1](#0-0) 
3. Only *after* that external call does it read the still-unmodified escrow balance to compute what the solver will be paid: [2](#0-1) 
4. The escrow release to the solver (`_withdraw`) happens later, outside the loop: [3](#0-2) 

Because `order.user` and `order.output.beneficiary` are both attacker-chosen when the order is placed, an attacker can set both to a contract they control. When a legitimate solver calls `fillOrder`, the ETH `.call` to `beneficiary` (step 2) hands control back to the attacker's contract *before* the escrow (`_orders[commitment][token]`) has been decremented. From that callback, the attacker calls the public `cancelOrder` path, which routes to `_cancelSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:161-187`). Its only checks are `order.user == msg.sender` (satisfied, since the reentrant caller is the attacker's own contract) and `order.source == currentChain` (satisfied for a same-chain order): [4](#0-3) 

`_cancelSameChain` calls `_withdraw(body, true, true)` in `IntentsBase.sol`, which reads the *still-full* `_orders[commitment][token]` balance and transfers the entire escrowed input to the attacker, sets `_filled[commitment] = order.user` (finalize), and zeroes the escrow: [5](#0-4) 

When control returns to `_fillSameChain`, the escrow read at line 118 now returns `0` (already drained), so `escrowedInputs[i].amount = 0`. The `_withdraw` call for the solver's payout at line 134 then does nothing (`IntentsBase.sol:398` skips zero amounts). Net effect: the solver already sent real value (ETH/ERC-20) to the attacker's beneficiary contract in step 2, but the input-token escrow — which was supposed to compensate the solver — is stolen by the attacker via the fraudulent cancel, and the solver receives nothing.

### Impact Explanation
This is direct, unauthorized theft of escrowed funds via a reentrancy path that crosses from `fillOrder` into `cancelOrder`, corrupting the shared `_orders[commitment][token]` value between the external call and its use. It matches the bounty's "stealing or loss of funds" and "wrong beneficiary or amount" categories: the solver's payment is captured by the attacker with no compensating input-token transfer, and the attacker also gets the "cancel refund" that shouldn't be payable once a fill is in progress. No malicious relayer, prover, governance action, or leaked key is required — only an ordinary, unprivileged order placer acting as both `order.user` and a malicious `beneficiary` contract, interacting with a normal solver's `fillOrder` call.

### Likelihood Explanation
The `_filled[commitment] = msg.sender` guard set at the top of `_fillSameChain` (line 57) prevents re-entry into `fillOrder`/`_fillSameChain` itself (as covered by `IntrinsicIntentsReentrancyTest.sol`), but does not prevent re-entry into the sibling function `_cancelSameChain`, which checks a *different* precondition (`order.user == msg.sender`, escrow non-zero) that is still true at the time of the callback. Any order with a native-token output and an attacker-controlled beneficiary/user is exploitable; no special timing, front-running, or privileged role is needed — the solver's own `fillOrder{value: ...}` call triggers the callback.

### Recommendation
Apply full checks-effects-interactions across all mutating entrypoints that share `_orders[commitment]`, not just `_filled[commitment]`:
- Decrement/zero the relevant `_orders[commitment][token]` escrow (or otherwise reserve it) before making any external call in `_fillSameChain`'s output loop, or
- Add a reentrancy guard (e.g., OpenZeppelin `nonReentrant`) shared across `fillOrder`, `cancelOrder`, and any other function that reads/writes `_orders[commitment]`, or
- Move all native/ERC-20 output transfers to the very end of `_fillSameChain`, after `_withdraw` has already computed and reserved the solver's escrow release, so a reentrant `cancelOrder` sees a consistent, already-decremented escrow state.

### Proof of Concept
1. Attacker deploys `MaliciousBeneficiary`, a contract with a `receive()` that calls `IntentGatewayV2.cancelOrder(order, ...)` (routing to `_cancelSameChain`).
2. Attacker places a same-chain order with `order.user = address(MaliciousBeneficiary)`, `order.output.beneficiary = bytes32(uint256(uint160(address(MaliciousBeneficiary))))`, a native-ETH output, and an ERC-20 input that gets escrowed via `placeOrder`.
3. A legitimate solver calls `fillOrder{value: outputAmount}(order, options)`.
4. Inside `_fillSameChain`'s output loop, the ETH `.call` to `beneficiary` at `IntrinsicIntents.sol:104` triggers `MaliciousBeneficiary.receive()`.
5. The reentrant call invokes `cancelOrder`, reaching `_cancelSameChain`, which passes both `order.user == msg.sender` and `order.source == currentChain`, and calls `_withdraw(body, true, true)`, transferring the full escrowed input token balance to the attacker and zeroing `_orders[commitment][token]`.
6. Execution returns to `_fillSameChain`; the escrow read at line 118 now returns 0, so the solver's `_withdraw` payout at line 134 is a no-op.
7. Result: solver paid ETH to the attacker for nothing; attacker received both the ETH output and the full input-token escrow.

Note: I did not have tool access to compile/run this scenario in Foundry to confirm no additional guard exists elsewhere in `IntentGatewayV2.sol`'s public `fillOrder`/`cancelOrder` wrapper functions (e.g., a possible top-level `nonReentrant` modifier not visible in the inherited abstract contracts reviewed). This should be verified against the concrete `IntentGatewayV2.sol` entrypoint definitions before treating this as fully confirmed.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
