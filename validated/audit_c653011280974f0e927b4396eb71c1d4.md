## Finding: Valid — Incomplete header denylist in `installSameOriginFilter`

### Title
Cross-origin redirect header sanitization uses an incomplete denylist, allowing non-standard credential headers to leak - (`app/src/main-process/same-origin-filter.ts`)

### Summary
`installSameOriginFilter` strips only three header names — `authentication`, `authorization`, `cookie` — from requests when a redirect changes origin. Any other header carrying a credential or secret (e.g. `Proxy-Authorization`, a custom OTP/session header) is not in this set and will be forwarded verbatim to the new (potentially attacker-controlled) origin.

### Finding Description
The filter records the origin of the initial request in `requestOrigin` and, on `onBeforeSendHeaders`, compares it against the current request's origin: [1](#0-0) 
When the origins differ, it rebuilds the header set, filtering out only the three names in `unsafeHeaders`: [2](#0-1) [3](#0-2) 

This is a hard-coded, narrow allowlist of "unsafe" header names rather than a general check for authentication-carrying headers. Any header not in `{'authentication','authorization','cookie'}` — case-insensitively matched via `k.toLowerCase()` — passes through the `sanitizedHeaders` object unchanged and is sent to the new origin after a cross-origin redirect.

I was not able to confirm, within the indexed portion of the codebase, that GitHub Desktop's `fetch`/API layer (`app/src/lib/api.ts`, `app/src/lib/http.ts`) actually sets a `Proxy-Authorization` header on outbound requests that flow through this filter — `Proxy-Authorization` is typically a header Chromium's network stack manages itself for HTTP proxy authentication challenges, not one applications set directly on `fetch` requests. My search did find a reference to `X-GitHub-OTP` in `app/src/lib/api.ts`, but I could not fully verify from the available index content whether it is used as an outgoing request header (as opposed to a response header being parsed) due to tool-call limits, so I cannot conclusively confirm that a credential-bearing custom header is actually transmitted by the app today.

### Impact Explanation
If the application (now or in a future change) ever attaches any authentication-relevant header other than `Authorization`/`Cookie`/`Authentication` — for example a custom 2FA/OTP header, a bearer token under a non-standard name, or a proxy credential — to a request that can be redirected cross-origin (e.g., via an attacker-controlled PR/issue asset URL or a GHE endpoint issuing a 30x to a different host), that header would not be stripped by this filter and would be exfiltrated to the attacker-controlled destination origin. This matches the stated invariant violation: "no auth-bearing header crosses origins."

### Likelihood Explanation
Likelihood is currently **low/uncertain** rather than confirmed-exploitable, because:
- The denylist gap is a real, verifiable fact in the code (`unsafeHeaders` only has 3 entries).
- However, I could not verify within the indexed codebase that Desktop's own request-construction code (`api.ts`/`http.ts`) currently attaches a non-listed credential header (such as `Proxy-Authorization` or `X-GitHub-OTP`) to outgoing requests that traverse `onBeforeSendHeaders`. `Proxy-Authorization` in particular is usually not something application code sets directly for `fetch`.
- Without confirming an actual credential-bearing header outside the three named ones is emitted by the app today, this is best characterized as a **hardening gap / defense-in-depth weakness** in the denylist design rather than a demonstrated, currently-exploitable credential-exfiltration path.

### Recommendation
Regardless of current exploitability, the denylist approach is fragile: switch to stripping any header whose name matches a pattern indicating sensitivity (e.g., contains `auth`, `token`, `otp`, `cookie`, `proxy-authorization`) or, better, invert the logic to an **allowlist of safe headers** to forward cross-origin, so any newly introduced credential header is stripped by default rather than requiring an explicit addition to `unsafeHeaders`.

### Proof of Concept
A focused unit test against `installSameOriginFilter` (mocking `OrderedWebRequest`) demonstrating that a header named `Proxy-Authorization` (or any header not in `{'authentication','authorization','cookie'}`) survives the `sanitizedHeaders` construction after a simulated cross-origin redirect (same `details.id`, different origin) would confirm the code-level gap, e.g.:
```ts
// initial request to https://a.example with header 'Proxy-Authorization: secret'
// redirect (same request id) to https://b.attacker.example
// assert sanitizedHeaders still contains 'Proxy-Authorization'
```
This proves the denylist gap exists in the code as written; it does not by itself prove the header is attacker-reachable in production traffic, which I could not fully confirm.
