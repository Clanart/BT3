## Title
Unhandled exception in `RepositoryIndicatorUpdater.refreshAllRepositories` permanently stops the periodic sidebar/background-fetch scheduler - (File: `app/src/lib/stores/helpers/repository-indicator-updater.ts`)

### Summary
The Internet Computer fix addresses a class of bug where a periodic task's rescheduling step lives *after* the fallible work in the same call, so a panic/exception in the task body prevents the reschedule call from ever running, silently killing all future executions. Desktop's `RepositoryIndicatorUpdater` has the same structural flaw: the call that recomputes ahead/behind status and drives background fetch for every non-selected repository is `await`-ed with no `try`/`catch`, and the call that reschedules the next tick (`this.scheduleRefresh()`) only executes if that `await` doesn't throw.

### Finding Description
`RepositoryIndicatorUpdater.refreshAllRepositories()` iterates over every repository and awaits the injected `refreshRepositoryIndicators` callback with no error handling: [1](#0-0) 

`this.scheduleRefresh()`, which is the only place the next `window.setTimeout` is armed, is called at the very end of the function: [2](#0-1) 

If the `await this.refreshRepositoryIndicators(repository)` call throws for *any* repository in the loop, the `while` loop and the whole `refreshAllRepositories` async function reject before reaching `scheduleRefresh()`. Since `refreshAllRepositories` is invoked fire-and-forget from a `window.setTimeout` callback, this becomes an unhandled promise rejection and the updater's internal timer (`refreshTimeoutId`) is left `null` forever — no future tick is ever scheduled, and `running` stays `true` so `start()` won't re-arm it either (it only calls `scheduleRefresh` when `!this.running`). This is functionally identical to the reported bug class: "task not rescheduled due to possible panic in the closure."

The callback wired in as `refreshRepositoryIndicators` is `AppStore.refreshIndicatorForRepository`, which performs multiple git operations, including status parsing (`gitStore.loadStatus()`), `inferLastPushForRepository`, and a conditional background fetch: [3](#0-2) 

The status pipeline this depends on (`app/src/lib/git/status.ts` → `app/src/lib/status-parser.ts`) contains multiple `throw new Error(...)` statements when a porcelain v2 status line doesn't match the expected regex — e.g. `parseChangedEntry`, `parsedRenamedOrCopiedEntry`, and `parseUnmergedEntry`: [4](#0-3) [5](#0-4) 

These parsers are invoked directly (uncaught at that layer) from `getStatus`: [6](#0-5) 

An attacker who controls the content or submodule configuration of a cloned/fetched repository controls the working tree/index shape that `git status --porcelain=2 -z` will report for it (unusual submodule states, odd rename/copy scores, pathological file layouts). If that repository ever causes `git status` to emit a line that doesn't match one of the hand-written regexes in `status-parser.ts`, the resulting exception propagates un-caught through `getStatus` → (whatever status wrapper `refreshIndicatorForRepository`/`gitStore.loadStatus` uses) → `refreshAllRepositories`, aborting the shared indicator-refresh loop for *every* repository the user has open, not just the malicious one.

I was not able to fully confirm from the available index whether the specific `gitStore.loadStatus()` wrapper used by `refreshIndicatorForRepository` re-wraps this call in `performFailableOperation` (a pattern used extensively elsewhere in `git-store.ts`) before it reaches `refreshAllRepositories`. If it does, the parser-throw path would be swallowed at that layer and the analog would rest purely on the missing try/catch in `refreshAllRepositories` itself for any other exception source (e.g. `inferLastPushForRepository`, disk errors, etc.) — the scheduler-side structural bug is confirmed regardless.

### Impact Explanation
If triggered, the app permanently stops the periodic `RepositoryIndicatorUpdater` loop for the remainder of the session (until app restart). This is the mechanism that keeps ahead/behind indicators fresh and, per its own comment, drives background fetch (`shouldBackgroundFetch` / `fetchForRepositoryIndicator`) for all repositories other than the currently selected one. A silent, permanent stop of this loop means the user's sidebar can silently go stale and background sync for unselected repositories silently stops, with only a debug-level log line as evidence — no user-facing error or notification is produced, since the rejection is never caught by any UI-facing error handler.

### Likelihood Explanation
The trigger requires an attacker-controlled repository to produce a `git status --porcelain=2 -z` line that doesn't match the app's regexes (or another uncaught exception path inside `refreshRepositoryIndicators`). This is a narrower attacker surface than a full RCE and I could not confirm a concrete, reliable way to make `git status` itself emit a non-conforming line (its output format is generated by git, not directly attacker-authored text), so likelihood is uncertain/low without further investigation of Desktop's `getStatus` failure wrapping. The structural scheduler flaw (missing try/catch before reschedule) is confirmed with certainty; the exploitability of a specific attacker-controlled trigger is not.

### Recommendation
Wrap the `await this.refreshRepositoryIndicators(repository)` call in `refreshAllRepositories` in a `try/catch` (logging and continuing to the next repository) so that a failure processing one repository cannot prevent `scheduleRefresh()` from running, mirroring the recovery-timer approach used in the referenced IC fix (always guarantee rescheduling regardless of a panic/exception in the task body).

### Proof of Concept
1. Add/clone a repository whose working tree or submodule state can cause `git status --porcelain=2 -z` to emit an entry that does not match `changedEntryRe`, `renamedOrCopiedEntryRe`, or `unmergedEntryRe` in `app/src/lib/status-parser.ts` (exact reproduction requires confirming which git states currently escape these regexes; the code path itself is confirmed to throw on any non-match).
2. Add this repository to Desktop alongside other repositories, and ensure it is not the currently selected repository so it's processed by `RepositoryIndicatorUpdater.refreshAllRepositories`.
3. Wait for the periodic 15-minute refresh cycle (`RefreshInterval` in `repository-indicator-updater.ts`) to reach that repository.
4. Observe that the thrown exception is never caught, `refreshAllRepositories` rejects before calling `this.scheduleRefresh()`, and the sidebar indicators/background fetch for all repositories stop updating for the rest of the session. [7](#0-6)

  private refreshIndicatorForRepository = async (repository: Repository) => {
    const lookup = this.localRepositoryStateLookup

    if (repository.missing) {
      lookup.delete(repository.id)
      return
    }

    const exists = await pathExists(repository.path)
    if (!exists) {
      lookup.delete(repository.id)
      return
    }

    const gitStore = this.gitStoreCache.get(repository)
    const status = await gitStore.loadStatus()
    if (status === null) {
      lookup.delete(repository.id)
      return
    }

    this.updateSidebarIndicator(repository, status)
    this.emitUpdate()

    const lastPush = await inferLastPushForRepository(
      this.accounts,
      gitStore,
      repository
    )

    if (await this.shouldBackgroundFetch(repository, lastPush)) {
      const aheadBehind = await this.fetchForRepositoryIndicator(repository)

      const existing = lookup.get(repository.id)
      lookup.set(repository.id, {
        aheadBehind: aheadBehind,
        // We don't need to update changedFilesCount here since it was already
        // set when calling `updateSidebarIndicator()` with the status object.
        changedFilesCount: existing?.changedFilesCount ?? 0,
      })
      this.emitUpdate()

function parseChangedEntry(field: string): IStatusEntry {
  const match = changedEntryRe.exec(field)

  if (!match) {
    log.debug(`parseChangedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for changed entry`)
  }

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    path: match[8],
  }
}
