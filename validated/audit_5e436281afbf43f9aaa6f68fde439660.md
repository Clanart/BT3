### Title
Duplicate `ReceivedOutput` inputs counted multiple times without deduction, producing unspendable/over-funded transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The external report's bug class is "the same balance can be spent/delegated multiple times because the delegated amount is never deducted and there is no tracking of what was already consumed." The direct Serai analog lives in `SignableTransaction::new`: it accepts a `Vec<ReceivedOutput>` and sums `input.output.value` over every element without deduplicating outpoints or tracking which outpoints were already counted. The same UTXO (or a fabricated `ReceivedOutput` carrying an arbitrary `TxOut` value) can therefore be counted N times toward `input_sat`, letting the funding check `input_sat < payment_sat + needed_fee` pass when the real, unique inputs cannot cover the payments plus change. The resulting transaction either contains duplicate inputs (consensus-invalid) or spends more than the inputs actually hold — funds the wallet/accounting believes are spendable are not.

### Finding Description
`SignableTransaction::new` performs no tracking of consumed outpoints:

- `let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();` (send.rs:175) sums every element, including duplicates.
- `tx_ins` is built verbatim from `inputs` (send.rs:177-185) — no outpoint deduplication.
- `prevouts` is likewise drained verbatim (send.rs:253), so the fee calculation `fee()` (send.rs:139) and the `Prevouts::All` sighash commitment (send.rs:375) both inherit the phantom value.
- `multisig` (send.rs:273-285) only checks `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` per index — an attacker-supplied `ReceivedOutput` with `offset = 0` (or any registered offset) and a forged `TxOut { value: X, script_pubkey: p2tr(key) }` passes this check regardless of whether the outpoint exists or carries that value.

`ReceivedOutput` fields are entirely attacker-controlled when the bytes come from `ReceivedOutput::read` (mod.rs:122-134), which deserializes `offset`, `TxOut` (including `value` and `script_pubkey`), and `outpoint` from untrusted input — an in-scope read API.

This is the "multiple delegation without deduction" pattern: the same outpoint/value is credited repeatedly because nothing deducts or tracks already-consumed inputs.

### Impact Explanation
- An unprivileged party who can feed `ReceivedOutput` bytes (or induce duplicate scanned outputs) causes the wallet to sign a transaction that is consensus-invalid (duplicate `TxIn` for the same outpoint — Bitcoin rejects double-spent inputs within one tx) or that claims more input value than exists (fabricated `TxOut.value` in `prevouts`). Either way, the coordinator believes funds were received and spendable when they are not — the "funds reported received that are not spendable" impact class.
- The change-output math (`input_sat.checked_sub(payment_sat + fee_with_change)`, send.rs:228) computes change from phantom value, so even when a tx is structurally valid it commits to outputs the inputs cannot fund.
- Each bogus `SignableTransaction` still drives a full threshold signing round per input (`TransactionSignMachine::sign`, send.rs:355-398), wasting a FROST session on an unbroadcastable transaction.

### Likelihood Explanation
Reachability requires attacker-influenced `ReceivedOutput`s entering `SignableTransaction::new`. `ReceivedOutput::read` is a public deserialization API over untrusted bytes, and `Scanner::scan_transaction` (mod.rs:199-214) emits outputs keyed only by `script_pubkey` with no cross-transaction tracking of already-reported outpoints — so a caller aggregating outputs (or re-scanning a tx/block) can trivially supply the same outpoint twice. Severity is Medium: the result is unspendable/"phantom" funds and burned signing rounds, not direct key compromise.

### Recommendation
- In `SignableTransaction::new`, deduplicate `inputs` by `outpoint` (e.g., insert into a `HashSet`/`BTreeMap` and reject duplicates) before summing `input_sat` and building `tx_ins`/`prevouts`.
- Have `Scanner`/`scan_block` track already-reported outpoints so the same output is never emitted twice to downstream accounting — the analog of "track all delegates assigned to a pool."

### Proof of Concept
Conceptual, mirroring the report's test:

```rust
// A scanner-produced output paying to p2tr(key + 0*G)
let output: ReceivedOutput = scanner.scan_transaction(&tx).swap_remove(0);

// Pass the SAME outpoint twice — its value is counted twice in input_sat,
// and tx_ins contains the same previous_output twice (consensus-invalid).
let stx = SignableTransaction::new(
  vec![output.clone(), output.clone()],
  &[(addr(), output.value() * 2 - 10_000)], // exceeds real balance of one copy
  Some(change_addr()),
  None,
  FEE,
).unwrap(); // NotEnoughFunds is bypassed

// Each input's script check passes because offsets[1] == offsets[0] == output.offset().
let machine = stx.multisig(&keys[&Participant::new(1).unwrap()]).unwrap();
// The threshold network signs a transaction Bitcoin consensus will reject
// for spending the same outpoint twice.

// Alternatively, deserialize a forged input over ReceivedOutput::read with an
// arbitrary TxOut.value and outpoint that doesn't exist:
let forged = ReceivedOutput::read(&mut bytes_with_huge_value.as_slice()).unwrap();
```

Root cause: `networks/bitcoin/src/wallet/send.rs:175-185` (undiscounted sum and undeduplicated `tx_ins`), `send.rs:253` (`prevouts` inherits phantom value), and `networks/bitcoin/src/wallet/mod.rs:199-214` (scanner emits per-script matches with no outpoint tracking).
