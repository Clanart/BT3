### Title
Setting `MAX_COMMIT_REVIEWS_PER_HOUR=0` silently and permanently disables all git commit/push security review — (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The `security-guidance` plugin gates its LLM-based commit/push security review with a rolling-window rate limiter, `atomic_check_rate_limit()`, configured via the env var `MAX_COMMIT_REVIEWS_PER_HOUR` (default `20`). This mirrors the reported bug class: a numeric "limit" setting that accepts zero without validation, and zero causes the gated feature to stop working entirely instead of behaving as "unlimited" — the opposite of the codebase's own established `0 = unlimited` convention used for `MAX_STOP_HOOK_FIRINGS` in the same file.

### Finding Description
`MAX_COMMIT_REVIEWS_PER_HOUR` is read directly into an int with no validation of non-zero/positive value: [1](#0-0) 

It is passed as `max_per_window` into `atomic_check_rate_limit()`: [2](#0-1) 

The gating logic is `if len(ts_list) >= max_per_window: return False, ...`. When `max_per_window` is `0`, `len(ts_list) >= 0` is trivially always `True` (list length is never negative), so the function returns `allowed=False` unconditionally, on every single call, forever — regardless of session, time window, or how long the tool has been idle. This is used identically for both commit review and push-sweep review: [3](#0-2) [4](#0-3) 

This is the exact same bug class as the reported `setDepositsLimit(0)`/`setNftDepositsLimit(0)` issue: a limit setter with no non-zero check, where the "disable the cap" input (0) instead disables the underlying protected function entirely, and does so silently (skip_reason=23 is only recorded in metrics/debug_log, not surfaced to the user as an actionable warning).

### Impact Explanation
This directly falls in the "git automation" trust boundary explicitly named in the report scope. If `MAX_COMMIT_REVIEWS_PER_HOUR` is ever set to `0` — by mistake (e.g., someone assumes the `0 = unlimited` convention seen elsewhere in the very same file for `MAX_STOP_HOOK_FIRINGS`), or by a shared team/CI config change — every future `git commit` and `git push` in that session/environment permanently bypasses the automated LLM security review with no further indication to the developer that reviews stopped running. Malicious or vulnerable code changes (secrets, injected backdoors, unsafe patterns) can then be committed and pushed without ever being scanned by the plugin's core security control, defeating the intended defense-in-depth for the rest of the session/deployment.

### Likelihood Explanation
Low-to-moderate: requires a user or team config to set `MAX_COMMIT_REVIEWS_PER_HOUR=0`, either as an honest mistake (mirroring the sibling `0 = unlimited` convention already present in the same module) or with intent to "disable rate limiting" without realizing it disables the review outright. Because the failure mode is silent (no error, no user-visible warning — only an internal metrics `skip_reason`), a misconfiguration would likely go unnoticed indefinitely.

### Recommendation
Add an explicit guard: treat `MAX_COMMIT_REVIEWS_PER_HOUR <= 0` as invalid input and either (a) fall back to the documented default (`20`) with a visible warning, or (b) explicitly implement `0` to mean "unlimited" (skip the rate-limit check entirely) for consistency with `MAX_STOP_HOOK_FIRINGS`'s documented semantics elsewhere in the file. In `atomic_check_rate_limit()`, change the comparison to only apply the cap when `max_per_window > 0`, and surface a non-debug warning when the effective limit is 0 so the disablement isn't silent.

### Proof of Concept
1. Set `export MAX_COMMIT_REVIEWS_PER_HOUR=0` in the environment used to launch Claude Code (or a shared `.env`/CI config consumed by the hooks).
2. Run any `git commit` in a Claude Code session; `handle_commit_review_posttooluse` calls `atomic_check_rate_limit(session_id, "CommitReview", 0, COMMIT_REVIEW_RATE_WINDOW_S)`.
3. Inside `atomic_check_rate_limit`, `len(ts_list) >= 0` evaluates `True` even when `ts_list` is empty, so `_allowed` is `False` and the review is skipped (`skip_reason=23`) on the very first commit and every commit thereafter [5](#0-4) .
4. The same happens for `git push` via `handle_push_sweep_posttooluse` [4](#0-3) .
5. Result: all future commits/pushes bypass the LLM security review indefinitely, with the only trace being an internal metrics field (`skip_reason: 23`) that is not surfaced as a user-facing alert.

def atomic_check_rate_limit(session_id, key, max_per_window, window_s):
    """Rolling-window rate limit: allow at most `max_per_window` calls per
    `window_s` seconds, per (session_id, key).

    Returns (allowed: bool, count_in_window: int). count_in_window is the
    post-decision count (i.e., includes this call if allowed) so callers can
    emit it directly as a telemetry gauge.

    Replaces session-lifetime `atomic_check_counter` for commit-review and
    push-sweep. Telemetry showed a small but persistent share of sessions hit
    the lifetime cap, and those were multi-day persistent sessions that then
    lost coverage for many subsequent commits — not burst abusers. A rolling
    hour keeps the same cost ceiling for any 1h window while letting long
    sessions regain coverage.

    State key: rate_limits: {"<key>": [ts, ts, ...]}. Timestamps are pruned
    on every call so the list is bounded by max_per_window; no migration
    needed from the old `counters` dict — different key.
    """
    import time as _time
    now = _time.time()
    cutoff = now - window_s

    def _check(state):
        buckets = state.setdefault("rate_limits", {})
        ts_list = buckets.get(key, [])
        # Prune; tolerate non-numeric junk from a corrupted state file.
        ts_list = [t for t in ts_list if isinstance(t, (int, float)) and t > cutoff]
        if len(ts_list) >= max_per_window:
            buckets[key] = ts_list
            return False, len(ts_list)
        ts_list.append(now)
        buckets[key] = ts_list
        return True, len(ts_list)

    result = with_locked_state(session_id, _check)
    # State unavailable → fail-open (same posture as atomic_check_counter).
    return result if result is not None else (True, 0)
