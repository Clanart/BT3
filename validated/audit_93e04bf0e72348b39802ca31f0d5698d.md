### Title
`RuleEngine._matches_tool` uses case-sensitive, unstripped exact matching, letting a subtly malformed `tool_matcher` silently disable a "block" rule - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._matches_tool` (lines 127-142) splits `tool_matcher` on `|` and checks exact membership (`tool_name in patterns`) with no case-folding and no per-segment whitespace trimming. A rule file committed into a shared repository's `.claude/` directory (loaded automatically by `load_rules()`) with a matcher such as `bash` (wrong case) or `Edit|Write| Bash` (embedded leading space on a pipe-separated segment) will never match the real `tool_name` value (`"Bash"`), so a rule that is displayed/believed to be `action: block` silently never fires.

### Finding Description
`config_loader.load_rules()` globs and loads every `.claude/hookify.*.local.md` file in the current working directory without any origin/trust check [1](#0-0) , so any file committed to a repository (e.g., via a PR) becomes an active enforcement rule the moment the repo is checked out. `Rule.from_dict` copies `tool_matcher` directly from frontmatter with no normalization [2](#0-1) . The scalar-value frontmatter parser does call `.strip()` on the whole value [3](#0-2) , which defeats a bare trailing-space attack on a single-tool matcher, but it does **not** normalize case, and it does not trim whitespace on individual segments of a pipe-delimited value (e.g., `Edit|Write| Bash`).

`_matches_tool` then does:
```
patterns = matcher.split('|')
return tool_name in patterns
``` [4](#0-3) 
This is a case-sensitive, exact, unstripped comparison. Meanwhile, the rest of the engine's pattern matching (`compile_regex`) is case-insensitive by design [5](#0-4) , creating an inconsistent mental model for rule authors/reviewers: a matcher like `bash` looks semantically equivalent to `Bash` but silently never matches the real `tool_name` (`"Bash"`) sent by the hook input, and `_rule_matches` short-circuits to `False` with no logging/warning [6](#0-5) .

Note: the documented `/hookify` workflow in `plugins/hookify/commands/hookify.md` does not populate `tool_matcher` at all in its generated templates — it relies on the `event` field (`bash`/`file`/`stop`/`prompt`/`all`), which is filtered via simple string equality in `load_rules` [7](#0-6)  and is not affected by this bug. `tool_matcher` is an undocumented "advanced override" field, so the realistic attack path is a crafted `.claude/hookify.*.local.md` file introduced through ordinary repository content (a PR, a shared dotfiles repo, a template repo) rather than the interactive dialogue itself.

### Impact Explanation
A rule file that appears to enforce `action: block` on dangerous `Bash` commands (e.g., blocking `rm -rf`) can be rendered permanently inert by a one-character case/whitespace defect in `tool_matcher`, while `enabled: true` and the block message remain visible to give the user false confidence that protection is active. This matches the stated invariant violation ("deny means deny") and could enable an attacker who also controls or influences subsequent Bash tool calls (e.g., through a separate content-injection channel) to execute commands the user believed were blocked.

### Likelihood Explanation
Exploitation requires: (1) a `.claude/hookify.*.local.md` file with a `tool_matcher` field reaching the repository/working directory (this field is not emitted by the standard `/hookify` dialogue, so it must come from manual authoring, a copied example, or a malicious repository contribution), and (2) that value having a case mismatch or an un-trimmed pipe segment. The whole-value `.strip()` in the frontmatter parser already blocks the simplest single-value trailing-space case, narrowing the practical trigger to multi-value pipe lists or case typos — plausible but requiring a specific authoring mistake or a deliberately crafted file rather than arbitrary untrusted text flowing straight through the LLM dialogue.

### Recommendation
In `_matches_tool`, normalize both the matcher segments and `tool_name` before comparison, e.g.:
```python
patterns = [p.strip().lower() for p in matcher.split('|')]
return tool_name.strip().lower() in patterns
```
Additionally, consider logging a warning when a rule's `tool_matcher` never matches any known tool name after loading, to surface misconfigured/inert block rules to the user.

### Proof of Concept
Unit test in `plugins/hookify/core/rule_engine.py` test suite:
```python
def test_matches_tool_case_insensitive():
    engine = RuleEngine()
    # Intended: matcher "bash" should match tool_name "Bash"
    assert engine._matches_tool("bash", "Bash") is True  # currently fails (returns False)

def test_matches_tool_trims_pipe_segments():
    engine = RuleEngine()
    # Intended: matcher "Edit|Write| Bash" should match "Bash" despite stray space
    assert engine._matches_tool("Edit|Write| Bash", "Bash") is True  # currently fails (returns False)
```
Both assertions fail against current code, demonstrating that `_matches_tool` silently returns `False` for matcher variants a rule author would reasonably expect to match, causing `_rule_matches` (and therefore `evaluate_rules`) to never block the intended `Bash` tool calls [8](#0-7) .

    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True
```
