### Title
Independent, unsynchronized conflict-marker regexes in extraction vs. reassembly can misalign Copilot's per-hunk resolutions and silently corrupt committed merge output - (File: `app/src/lib/copilot-conflict-resolution.ts`, `app/src/lib/copilot-conflict-context.ts`)

### Summary
The Seaport report's broken invariant is: code precomputes indices/positions assuming a fixed count of items from an untrusted source, then a second, independently-derived count (from the same untrusted input) is used to reconcile those items positionally — if the counts diverge, indices misalign silently or revert unexpectedly. Desktop's Copilot merge-conflict auto-resolution feature has the same shape: `extractConflictHunks` walks a file's raw content once to build the hunks sent to Copilot (and to validate the response count), and `reassembleResolvedFile` walks the *same* raw content a second time, independently, using a different set of marker regexes, to splice the model's per-hunk resolutions back in **by position, not by identity**.

### Finding Description
`extractConflictHunks` in [1](#0-0)  scans file content for conflict markers using `oursMarker`, `baseMarker`, `separatorMarker`, and `theirsMarker`, and produces the hunk list that is sent to Copilot and used by `validateResolutionPaths` to enforce a matching hunk count per file [2](#0-1) .

Later, `reassembleResolvedFile` re-walks the *same* `rawContent` string using a **separately declared** set of regexes (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`) defined independently in `copilot-conflict-resolution.ts` [3](#0-2) , and splices `hunkResolutions[hunkIndex]` into each conflict block it finds, matched purely by the order encountered — explicitly documented as "matched by order, not by line number" [4](#0-3) .

There is no check that the number of conflict blocks `reassembleResolvedFile` finds while re-scanning equals `hunkResolutions.length` (the count validated earlier against `extractConflictHunks`'s output). The guard is only a bounds check (`if (hunkIndex < hunkResolutions.length)`) [5](#0-4) , not an equality assertion. If the two independently-maintained regex sets ever disagree on what counts as a conflict marker (e.g., a bare `<<<<<<<` line, unusual marker spacing, or malformed/nested markers crafted in the source file that one regex accepts as end-of-line/`$` and the other requires trailing whitespace/label for), the number of blocks found during reassembly can differ from the number of hunks that were extracted, sent to Copilot, and validated. This is the same "less consideration items than caller expected" pattern from the Seaport report, just applied to a locally-derived index instead of an external contract call: one pass establishes an expected count that gates validation, and a second, independent pass performs positional reconciliation against attacker-influenced content without re-checking that count.

### Impact Explanation
If the counts diverge, `hunkIndex` walks out of sync with the actual conflict blocks in the file:
- Resolved content from hunk N can get spliced into a different conflict block than the one it was generated for.
- Trailing conflict blocks beyond `hunkResolutions.length` are left with their raw conflict markers untouched, but the function returns normally (no error).
- The corrupted, reassembled content is written back to disk and is what the user will subsequently stage and commit as their merge resolution.

This matches the "Valid Impact" bar: an attacker who controls a cloned/fetched repository can craft a file whose conflicting versions contain irregular conflict-marker formatting so that `extractConflictHunks` and `reassembleResolvedFile` disagree on hunk boundaries, causing **silent corruption of what the user commits** — without any error surfaced to the user, since the write path has no reconciling re-validation of the resulting file.

### Likelihood Explanation
Exploitation is contingent on the actual marker regex definitions (`oursMarker`, `baseMarker`, `separatorMarker`, `theirsMarker`) diverging from `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` for some crafted input. I could not confirm the exact regex source for `oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker` (only their usage was retrieved, not their definitions), so I cannot fully confirm today's byte-for-byte divergence — this is the key open uncertainty. What is confirmed from the code is the architectural weakness: two independently maintained marker-detection implementations operate over attacker-influenced file content, and the reconciliation step has no invariant check that the counts still agree at reassembly time. Given the code already anticipates malformed markers as a real-world case (see the "malformed marker" fallback at lines 574-579), any future or already-existing edge-case divergence between the two regex sets is silently exploitable, not merely theoretical.

### Recommendation
- Use exactly one shared marker-detection implementation (single source of truth) for both hunk extraction and reassembly, rather than two independently declared regex sets.
- In `reassembleResolvedFile`, assert that the number of conflict blocks found while re-scanning `rawContent` equals `hunkResolutions.length`; if not, throw a `CopilotValidationError` instead of silently continuing.
- Consider having `extractConflictHunks` return enough positional metadata (e.g., line offsets) so reassembly doesn't need to re-derive marker boundaries independently.

### Proof of Concept
Conceptual PoC (exact regex definitions unavailable via ask-only tools, so this describes the exploitable pattern rather than a byte-exact malicious file):
1. Attacker crafts/pushes a file to a branch that will be merged, containing a conflict block whose marker line is accepted by `reassemblyOursMarker`/`reassemblyTheirsMarker` (`/^<{7}(?:\s|$)/`, `/^>{7}(?:\s|$)/`) but rejected by whatever stricter pattern `oursMarker`/`theirsMarker` use in `copilot-conflict-context.ts` (or vice versa) — e.g., a bare `<<<<<<<` line with no branch label and no trailing space.
2. User triggers a merge/rebase that conflicts on this file and invokes Copilot auto-resolution.
3. `extractConflictHunks` extracts N hunks (missing the malformed block); Copilot returns N resolutions; `validateResolutionPaths` passes (counts match N).
4. `reassembleResolvedFile` re-scans the same `rawContent` and finds N+1 (or N-1) blocks due to the marker discrepancy, causing `hunkIndex` to desynchronize from `hunkResolutions`, splicing a resolution into the wrong block or leaving a block with raw markers untouched.
5. The corrupted file is written to disk and presented to the user as "resolved," and if committed, silently commits incorrect/broken code. [6](#0-5) [1](#0-0)

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
