### Title
`IntentGatewayV2.placeOrder()` on Tron over-credits escrow with the requested amount instead of the actual ERC20 balance received, causing insolvent escrow and cross-order fund loss for fee-on-transfer/rebasing tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of `IntentGatewayV2.placeOrder()` assumes an ERC20 `transferFrom` always delivers exactly the requested `amount` (the "minted/transferred 1:1" assumption from the reference report). Unlike the canonical EVM implementation, which measures the actual balance delta after `safeTransferFrom` and uses that to size the escrow, the Tron variant credits `_orders[commitment][token]` with the pre-computed `reducedInputs[i].amount` (derived from the user-supplied `order.inputs[i].amount`) without ever checking what the contract actually received.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```

`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` (the value the user *claims* to send), reduced only by the protocol fee percentage — it is never reconciled against the contract's actual token balance change.

Compare this to the canonical EVM contract, which explicitly guards against exactly this class of bug: [2](#0-1) 

```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```

The EVM version mutates `order.inputs[i].amount` to the measured, actual received amount before any fee reduction or escrow crediting is computed (see also the fee-on-transfer regression tests validating this behavior: `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2256-2308`). The Tron contract lacks this balance-delta measurement entirely for the direct-transfer path, so for any fee-on-transfer, rebasing, or otherwise non-1:1-transferring ERC20, the escrow ledger (`_orders` mapping) is credited with more tokens than the contract physically holds.

Because `_orders` is a shared global accounting ledger keyed by `(commitment, token)`, and the actual token balance held by the contract is a single pooled balance shared across all orders using that token, this creates a systemic under-collateralization: the sum of all `_orders[...][token]` entries can exceed `IERC20(token).balanceOf(address(this))`. When `_withdraw()` is later called (via `fillOrder` or `cancelOrder`) to pay out escrow using `IERC20(token).safeTransfer(beneficiary, amount)` (`evm/src/apps/intentsv2/IntentsBase.sol:403-409`), the payout is based on the ledger value, not on-hand balance — so whichever solver/user withdraws first can drain the pool for a legitimate escrow entry, leaving later withdrawals (for other, unrelated orders using the same token) to revert due to insufficient contract balance.

### Impact Explanation
This is a fund-loss / DoS bug directly analogous to the referenced report: an unprivileged user can place an order with a fee-on-transfer (or any non-standard) ERC20 as input, causing the gateway's internal escrow ledger to diverge from its real token balance. This leads to:
- Denial of service on `fillOrder`/`cancelOrder` for other orders sharing the same token, since `safeTransfer` will revert when the pool is insufficient.
- Effective fund loss/theft in a race: whichever solver or canceling user withdraws first receives tokens that were actually escrowed for a different order, at the expense of that other order's beneficiary who can never be paid out.

This matches the bounty's "stealing or loss of funds" / "logic attacks against escrow accounting" categories and requires no malicious relayer, prover, or admin — just an unprivileged user placing an order with a fee-on-transfer token.

### Likelihood Explanation
Likelihood is moderate to high in practice: fee-on-transfer and deflationary/rebasing ERC20 tokens are common on Tron/EVM-compatible chains, and nothing in `placeOrder` restricts which ERC20 tokens can be used as order inputs. Any user (attacker or not) placing an order with such a token silently corrupts the shared escrow ledger for that token across all pending orders.

### Recommendation
Apply the same balance-delta pattern used in the canonical EVM `IntentGatewayV2.sol` to the Tron variant: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` call, mutate `order.inputs[i].amount` (and thus the commitment/fee/escrow computation) to reflect the actual amount received, and only then compute `reducedInputs` and credit `_orders[commitment][token]`.

### Proof of Concept
1. Deploy a 1% fee-on-transfer ERC20 token on the Tron gateway deployment.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch.
3. `safeTransferFrom` moves only 990e18 into the contract (1% fee burned/retained by the token), but `_orders[commitment][FOT]` is credited with `reducedInputs[0].amount` computed from the full `1000e18` (minus only the protocol fee, e.g. 997e18 with a 30bps protocol fee) — i.e., ~7e18 more than the contract actually holds.
4. Repeat for a second, unrelated order using the same FOT token.
5. When solvers/users call `_withdraw` for both orders, the cumulative payout demanded from `_orders` exceeds `IERC20(FOT).balanceOf(gateway)`, so the second `safeTransfer` reverts — reproducing the "M-34-style" DoS, or, if amounts are chosen carefully, the first withdrawer drains funds escrowed for the second order.
