### Title
Missing zero-value validation on `Kip71GasTarget` governance parameter causes division-by-zero panic in Magma base-fee calculation, crashing all nodes ([File: params/kip71_config.go], [File: kaiax/gov/param.go])

### Summary
The Kaia governance parameter `Kip71GasTarget` uses `noopFormatChecker` and therefore accepts a value of `0`, unlike its sibling parameter `Kip71BaseFeeDenominator`, which explicitly rejects zero. When `GasTarget == 0` becomes active governance state and a block with nonzero `GasUsed` is processed, `KIP71Config.NextMagmaBlockBaseFee` divides by `gasTarget` without a zero guard, causing a Go runtime division-by-zero panic during header validation on every node — a chain-halting DoS analogous to the referenced Panoptic division-by-zero report, but here triggered via an unguarded governance parameter rather than an unguarded strike-width computation.

### Finding Description
`Kip71GasTarget` is registered with `FormatChecker: noopFormatChecker` (no validation), in contrast to `Kip71BaseFeeDenominator`, whose checker explicitly enforces `v != 0`: [1](#0-0) 

The parameter flows unvalidated through `ParamSet.Set`/`ToMap` into `ParamSet.ToKip71Config()`, which copies `GasTarget` directly into `params.KIP71Config`: [2](#0-1) 

`KIP71Config.NextMagmaBlockBaseFee` uses `gasTarget := kc.GasTarget` directly as a divisor in the "gas used above target" branch, with only a guard for `BaseFeeDenominator == 0`, but none for `GasTarget == 0`: [3](#0-2) 

If `GasTarget == 0` and `parentGasUsed > 0` (i.e., `parentGasUsed > gasTarget`, true whenever the parent block used any gas), execution reaches:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // division by zero -> panic
```
This is invoked from `VerifyMagmaHeader`, which every full node calls during header validation on every new block once the Magma fork is active: [4](#0-3) 

It is also invoked from `feehistory.go`'s `processBlock` (used by `eth_feeHistory`/`kaia_feeHistory` RPC) and other call sites (`work/worker.go`, `blockchain/tx_pool.go`, `blockchain/chain_makers.go`), all of which would panic identically: [5](#0-4) 

Since `math/big.Int.Div` with a zero divisor panics in Go rather than returning an error, this is an unrecoverable crash in the block validation and block production hot path.

### Impact Explanation
Once a governance vote sets `Kip71GasTarget = 0` and it becomes active in the chain config, every node computing `NextMagmaBlockBaseFee` for a block with nonzero parent `GasUsed` (essentially any real block) will panic. This affects:
- Header validation (`BlockValidator.validateHeader`) — every full node validating new blocks.
- Block production (`work/worker.go`) — proposers building new blocks.
- `feehistory`/RPC callers.

This results in a synchronized crash across all honest nodes processing the same chain state — a consensus-halting denial of service, which is a Critical/High severity impact for a governance-reachable parameter, matching the allowed impact classes (state divergence / acceptance-of-invalid-state via governance parameters).

### Likelihood Explanation
This requires the governance value `Kip71GasTarget` to actually be set to `0` and adopted by the chain (via the governance voting/parameter-update mechanism), and then a subsequent block to have `GasUsed > 0`. The asymmetric validation — `Kip71BaseFeeDenominator` explicitly checks for `!= 0` while `Kip71GasTarget` uses `noopFormatChecker` — strongly suggests this zero-guard is a code defect/oversight rather than an intentional allowance, since `GasTarget` is used identically as a divisor. Likelihood depends on the governance authorization model (who can propose/vote such a parameter), which was not further inspected in this session, but the code path itself contains no additional runtime safety guard once such a value is accepted into `ParamSet`.

### Recommendation
Add a `v != 0` format-checker for `Kip71GasTarget`, mirroring `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, add a defensive zero-guard directly in `NextMagmaBlockBaseFee` (similar to the existing `BaseFeeDenominator == 0` fallback) so that a corrupted or historically-persisted zero value cannot cause a panic in consensus-critical code.

### Proof of Concept
Conceptual reproduction (not executed, based on static code tracing):
1. Governance sets `governance.kip71.gastarget = 0` (accepted because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, per [6](#0-5) ).
2. This value becomes the active `ParamSet.GasTarget` for a subsequent block height via `ParamSet.Set`.
3. A block is produced/validated with `parentHeaderGasUsed > 0` and `Magma` fork active.
4. `BlockValidator.validateHeader` calls `govParamSet.ToKip71Config().VerifyMagmaHeader(...)` → `NextMagmaBlockBaseFee(...)`.
5. Inside, `parentGasUsed(>0) > gasTarget(0)` branch executes `x.Div(x, new(big.Int).SetUint64(0))`, which panics with "division by zero" per Go's `math/big` semantics, crashing the node process during header validation. [7](#0-6)
