## Analysis

The external report's core broken invariant: an inbound cross-chain message triggers execution of attacker-supplied calldata through a shared, unauthenticated "Executor," and that Executor never clears the approvals/allowances it grants while executing that calldata — so a later, unrelated flow that deposits funds into the same Executor can have those funds drained via the stale allowance.

Hyperbridge's exact local analog is `CallDispatcher`, a **single shared, access-control-free contract** used by `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`/`ExtrinsicIntents` to execute attacker/user-supplied `Call[]` payloads on behalf of whichever asset happens to be passing through it at the time. [1](#0-0) 

`dispatch()` has no caller restriction and executes every call `to.call{value: call.value}(call.data)` **as the `CallDispatcher` itself**, and never revokes any approval the executed calldata may have granted.

### Title
Shared, unauthenticated `CallDispatcher` allows stale approvals granted by one cross-chain message to drain funds deposited by an unrelated later flow - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a public entrypoint with zero access control, invoked with attacker-influenced calldata from multiple independent apps (`HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`, `IntentGatewayV2`/`ExtrinsicIntents._fillCrossChain`/`_execute`). Any user can cause `CallDispatcher` to `approve()` an arbitrary spender for an arbitrary token as part of a legitimate-looking cross-chain send or order. That approval is never cleared. Because `CallDispatcher` is a shared singleton across all these apps and all users, any later transaction that transiently deposits the same token into `CallDispatcher` (e.g. another user's `IntentGatewayV2` predispatch escrow, or a `HyperFungibleToken`/`WrappedHyperFungibleToken` postdispatch calldata payload) can have those funds pulled out by the original attacker via the stale allowance before the legitimate sweep-back/transfer executes.

### Finding Description
`HyperFungibleToken.onAccept` mints tokens to the beneficiary and then unconditionally forwards `message.data` (attacker-controlled via the `send()` `params.data` field on the source chain) to the shared `CallDispatcher`: [2](#0-1) 

`send()` lets any caller set `data` freely: [3](#0-2) 

`IntentGatewayV2`/`ExtrinsicIntents` similarly routes user-supplied `Call[]` (`order.predispatch.call`, `order.output.call`) through the same dispatcher pattern: [4](#0-3) [5](#0-4) 

`CallDispatcher` itself performs no cleanup after execution and has no restriction on who may call it: [1](#0-0) 

Because the docs explicitly acknowledge that "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances" as a best-practice mitigation rather than an enforced invariant, the contract relies entirely on well-behaved callers, while the entrypoint (`dispatch`) is open to anyone: [6](#0-5) 

The attack primitive: since `CallDispatcher` is one address shared by every app/user on that chain, an attacker's own legitimate-looking cross-chain send or order can embed a `Call{to: <victimToken>, data: approve(attacker, type(uint256).max)}`. This executes as `CallDispatcher` and grants the attacker unlimited spending rights over any balance of `<victimToken>` that `CallDispatcher` ever holds. No existing guard prevents this — source/from checks in `onAccept` only authenticate that the message came from the registered peer contract, they do not constrain what the forwarded `data` may instruct `CallDispatcher` to do, and `CallDispatcher.dispatch` performs no allowance reset and no caller authentication.

### Impact Explanation
This is a fund-theft primitive that requires no malicious relayer, prover, or admin — only an unprivileged attacker who can call the already-public `send()` (HFT/WHFT) or place an order (`IntentGatewayV2`). Any subsequent legitimate user who transiently routes the same token through `CallDispatcher` (predispatch escrow, postdispatch calldata, HFT calldata payloads) risks having those funds pulled to the attacker via the un-revoked allowance, since `CallDispatcher`'s balance is not exclusive to any one transaction and the contract itself has no reentrancy/ownership boundary between unrelated calls.

### Likelihood Explanation
Medium-to-high: it requires (1) an attacker seeding a malicious approval through a normal, permissionless call path (`send()`/order placement) and (2) waiting for/triggering a subsequent deposit of the same token into the shared `CallDispatcher` by any other user of any of the three integrated apps. Because `CallDispatcher` is shared infrastructure reused across `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`, the token/spender surface is broad and the attacker fully controls the timing and target token of their seeding transaction.

### Recommendation
- Restrict `CallDispatcher.dispatch` to a known/allow-listed set of caller contracts, or deploy per-app dispatcher instances instead of one shared singleton.
- After executing each call batch, explicitly revoke any approvals granted during that batch (e.g., `forceApprove(spender, 0)` for every token/spender touched), rather than relying on caller discipline.
- Alternatively, disallow `approve`-style calldata entirely from the executable `Call[]` surface, or require exact-amount, single-use allowances enforced at the `CallDispatcher` level rather than as documentation guidance.

### Proof of Concept
1. Attacker calls `HyperFungibleToken.send()` on chain A targeting chain B, with `params.data` ABI-encoding `Call[]{ { to: USDC_on_chainB, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max) } }`.
2. A normal relayer delivers the request; `HyperFungibleToken.onAccept` on chain B passes source/from checks (attacker is a legitimate `send()` caller on a registered peer), mints tokens to the beneficiary, then calls `ICallDispatcher(_dispatcher).dispatch(message.data)`.
3. `CallDispatcher` executes `USDC.approve(attacker, MAX)`, granting the attacker unlimited allowance over `CallDispatcher`'s future USDC balance.
4. Later, any other user's `IntentGatewayV2` order with a USDC predispatch step (or another HFT/WHFT calldata payload moving USDC) transiently deposits USDC into `CallDispatcher`.
5. Attacker calls `USDC.transferFrom(CallDispatcher, attacker, amount)` directly, draining the victim's USDC before the legitimate sweep-back/transfer logic runs.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;

            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
