### Title
Missing zero-check on Kip71GasTarget governance parameter can cause a division-by-zero panic in `NextMagmaBlockBaseFee` - ([File: params/kip71_config.go])

### Summary
The KIP-71 base fee update function `NextMagmaBlockBaseFee` performs `big.Int` division using `GasTarget` as a divisor without checking that it is non-zero, and the governance parameter validator for `Kip71GasTarget` uses `noopFormatChecker`, which allows the value `0` to be accepted as a valid governance parameter.

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee based on the parent block's gas usage relative to `GasTarget`: [1](#0-0) 

When `parentGasUsed > gasTarget`, the code computes `gasUsedDelta = parentGasUsed - gasTarget` and then divides by `gasTarget` via `x.Div(x, new(big.Int).SetUint64(gasTarget))`. If `GasTarget == 0`, this is a division by zero, which causes Go's `big.Int.Div` to panic (unlike Solidity's revert, this is a hard process panic since it's Go host code, not an EVM opcode). The same divisor is reused for the "usage below target" branch.

The `Kip71GasTarget` governance parameter definition explicitly opts out of value validation by using `noopFormatChecker`, unlike its sibling parameter `Kip71BaseFeeDenominator`, which does validate non-zero: [2](#0-1)  — compare `Kip71BaseFeeDenominator`'s `FormatChecker` (`v != 0`) with `Kip71GasTarget`'s `noopFormatChecker`.

Note that within `NextMagmaBlockBaseFee` itself, the code already special-cases `BaseFeeDenominator == 0` to prevent this exact class of bug for that parameter: [3](#0-2) 

...but no equivalent guard exists for `GasTarget`. This shows the developers were aware of the zero-divisor hazard for one parameter but missed it for `GasTarget`.

`NextMagmaBlockBaseFee` is called on every block during consensus-critical header verification (`VerifyMagmaHeader`) and fee estimation (`feehistory.go`), so a `GasTarget == 0` value reaching this function is guaranteed to be exercised on essentially every block once the parent's gas usage differs from zero.

### Impact Explanation
If `GasTarget` is ever set to `0` through the governance parameter mechanism (vote/parameter update), every node validating a block header (with `parentGasUsed != 0`, the overwhelmingly common case) will panic in `NextMagmaBlockBaseFee`. Since this function runs identically on all honest nodes during block processing, this is a chain-halting event affecting every node simultaneously — a consensus-critical denial of service, not merely a single-node crash. This satisfies the "acceptance of an invalid transaction or block" / consensus-halting class of impact.

### Likelihood Explanation
The parameter is only reachable through the governance parameter-setting mechanism (`kaiax/gov`), which is intended to be set by authorized governance actors (governing node / vote), not a directly unprivileged transaction sender. I was not able to fully verify within the available context whether `Kip71GasTarget` can be modified through a path reachable by a lower-privilege actor (e.g., a permissionless `GovParamContract` call) as opposed to only through validator/governing-node voting — the contract-based governance path (`kaiax/gov/contractgov`) was not fully explored due to iteration limits. If parameter changes require a governing-node vote, this would fall into the "governance parameters" category the analog scan explicitly permits, but the *actor* setting the value is privileged, which is closer to the excluded "operator/validator-only" category. This uncertainty limits confidence in likelihood being High versus that this may be borderline out of scope.

### Recommendation
Add a zero-check to `Kip71GasTarget`'s `FormatChecker` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check) in `kaiax/gov/param.go`, and additionally add a defensive guard in `NextMagmaBlockBaseFee` (`params/kip71_config.go`) that falls back to a safe default (e.g., treats `gasTarget == 0` similarly to the existing `BaseFeeDenominator == 0` fallback) before performing any division by `gasTarget`.

### Proof of Concept
1. Governance sets `kip71.gastarget` (`Kip71GasTarget`) to `0` via the governance voting mechanism; because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, this value is accepted: [4](#0-3) 
2. On the next block after the parameter takes effect, if `parentHeaderGasUsed > 0` (virtually guaranteed), `NextMagmaBlockBaseFee` executes the `parentGasUsed > gasTarget` branch: [5](#0-4) 
3. `new(big.Int).SetUint64(gasTarget)` is `0`, and `x.Div(x, 0)` panics with a Go runtime "division by zero" error, called from every node's block/header verification path (`VerifyMagmaHeader`) as well as `SuggestPrice`/`feehistory.go` RPC paths, crashing all nodes that process the block.

**Confidence caveat:** I could not conclusively confirm within available context whether the `Kip71GasTarget` parameter is reachable through any unprivileged/permissionless path (e.g., a public contract call) versus requiring privileged governing-node voting only. If it strictly requires governing-node privilege, this finding may fall outside the "unprivileged sender" reachability requirement of the scan rules.
