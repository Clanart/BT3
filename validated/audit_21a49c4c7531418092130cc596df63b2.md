### Title
Cross-shop session hijack via unauthenticated `shop`/`embedded` params in `EnsureInstalled` - (File: app/controllers/concerns/shopify_app/ensure_installed.rb)

### Summary
`current_shopify_domain` and `installed_shop_session` derive the "installed shop" solely from the raw, attacker-controlled `params[:shop]` value (only format-sanitized, never identity-verified). In the legacy (non-token-exchange) flow, the subsequent `validate_non_embedded_session` check can be bypassed entirely by supplying `embedded=1`, since `loaded_directly_from_admin?` only checks that param equals `"1"` with no cryptographic proof of an actual Shopify Admin origin. This lets an unauthenticated attacker who knows/guesses a victim's `*.myshopify.com` domain load any `EnsureInstalled`-protected controller action with the victim's offline session bound to `@shop`/`installed_shop_session`.

### Finding Description
- `current_shopify_domain` (lines 29-38) returns `ShopifyApp::Utils.sanitize_shop_domain(params[:shop])`. `sanitize_shop_domain` [1](#0-0)  only validates that the string resolves to a trusted Shopify domain suffix (`myshopify.com`, etc.) — it performs no verification that the requester actually controls or is authenticated to that shop.
- `installed_shop_session` (lines 40-42) then directly loads `SessionRepository.retrieve_shop_session_by_shopify_domain(current_shopify_domain)` — i.e., whichever offline session the app previously stored for that domain string, keyed purely off this unauthenticated param. [2](#0-1) 
- In the legacy (non-`use_new_embedded_auth_strategy`) flow, `check_shop_known` sets `@shop = installed_shop_session` for that shop and only redirects if no session is found. [3](#0-2) 
- `validate_non_embedded_session` is the only remaining gate before the controller action runs, but it short-circuits entirely (`return`) when `loaded_directly_from_admin?` is true. [4](#0-3) 
- `loaded_directly_from_admin?` is defined as `ShopifyApp.configuration.embedded_app? && params[:embedded] == "1"` — a pure string comparison against an attacker-supplied query param, with no signature, referer enforcement, or session-token check. [5](#0-4) 

Exploit flow: an unauthenticated attacker sends `GET /any_ensure_installed_action?shop=victim-shop.myshopify.com&embedded=1`. `check_shop_domain` passes (shop sanitizes fine). `check_shop_known` finds the previously-installed victim session and assigns `@shop`. `validate_non_embedded_session` immediately returns because `embedded=1` was supplied, skipping the Admin API call that would otherwise have exercised (and potentially invalidated) the token. The controller action then executes with `installed_shop_session`/`@shop` bound to the victim's offline session — i.e., another merchant's store credentials — even though the attacker never proved control of that shop (no OAuth HMAC, no session/ID token, no Referer/App Bridge origin check).

### Impact Explanation
Any controller including `ShopifyApp::EnsureInstalled` (and not using the newer `use_new_embedded_auth_strategy`/token-exchange path) executes attacker-reachable actions under another merchant's offline session, based purely on a guessable/enumerable `shop` domain and a spoofable `embedded=1` flag. Depending on what the action does with `@shop`/`installed_shop_session` (API calls, rendering shop data, background jobs), this yields cross-shop data exposure and unauthorized use of the victim's access token — matching the "cross-shop access: loading/acting with another store's offline session" impact class.

### Likelihood Explanation
- Preconditions: victim shop must have previously installed the app (session exists in `SessionRepository`), app must run the legacy (non-token-exchange) embedded flow, and `ShopifyApp.configuration.embedded_app?` must be true (the default for embedded apps).
- The attacker needs only the victim's shop domain, which is often guessable (company/brand name + `.myshopify.com`) and not treated as a secret by Shopify itself.
- No secrets, tokens, or insider access needed — fully reachable via a single crafted GET request with `shop` and `embedded` query params.

### Recommendation
Do not treat `params[:shop]`/`params[:embedded]` as proof of identity. `loaded_directly_from_admin?` should not bypass validation solely on a client-suppliable flag; the app should require a verified session/ID token (JWT `dest`/`iss` claims cryptographically checked, as in `EnsureHasSession`/`WithShopifyIdToken`) or Shopify's signed session-token before binding `@shop`/`installed_shop_session` to a domain, or at minimum always perform the token-validity API call in `validate_non_embedded_session` regardless of the `embedded` param, and derive the shop from a verified source (session token `dest` claim) rather than the raw `shop` param when a controller intends to act on behalf of a specific merchant.

### Proof of Concept
```ruby
# test/controllers/concerns/ensure_installed_test.rb style test
class FakeController < ActionController::Base
  include ShopifyApp::EnsureInstalled
  def index
    render plain: @shop&.shop || "no-session"
  end
end

test "unauthenticated request with shop+embedded=1 loads another shop's offline session" do
  victim_domain = "victim-shop.myshopify.com"
  ShopifyApp::SessionRepository.store_shop_session(
    ShopifyAPI::Auth::Session.new(shop: victim_domain, access_token: "victim-token")
  )

  get :index, params: { shop: victim_domain, embedded: "1" }

  assert_response :success
  assert_equal victim_domain, response.body # attacker never proved control of victim_domain
end
```
Expected (buggy) behavior: request succeeds and binds the victim's session without any HMAC, session-token, or Admin-origin verification — confirming that a weaker, fully attacker-controlled channel (`shop`/`embedded` query params) overrides what should be the strongest verified identity source (a signed session/ID token).
