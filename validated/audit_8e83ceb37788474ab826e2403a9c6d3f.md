### Title
Out-of-range `Participant` indexes in a blame accusation panic `BlameMachine::blame` / `AdditionalBlameMachine::blame`, crashing the evaluating process - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP blame evaluation path indexes `HashMap`s with `Participant` values taken from the accusation without validating that they are within `1 ..= n`. `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` evaluates `self.commitments[&sender]` via `HashMap`'s `Index` impl, which panics on a missing key. An accusation carrying a valid proof-of-possession message plus `recipient`/`sender` indexes outside the DKG set deterministically panics the process evaluating blame — the same bug class as the referenced report (an externally reachable request path whose panic is uncontained, turning a crafted input into a crash / restart-loop).

### Finding Description
`AdditionalBlameMachine::new` (crypto/dkg/pedpop/src/lib.rs:649-662) explicitly exists so that blame can be evaluated by parties *not* in the DKG, given only a context, `n`, and the commitment messages — i.e., it is designed to adjudicate accusations submitted by arbitrary parties. `AdditionalBlameMachine::blame` (crypto/dkg/pedpop/src/lib.rs:674-682) and `BlameMachine::blame` (crypto/dkg/pedpop/src/lib.rs:623-632) both forward the accusation's `sender` and `recipient` to `blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609), which calls `Decryption::decrypt_with_proof`.

In `decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:366-397):

```rust
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],   // line 388: panics if decryptor not registered
  )
```

`enc_keys` is only populated for `1 ..= n` via `Decryption::register` (encryption.rs:351-362, which itself `assert!`s on re-registration). The index expression is evaluated before `verify` runs, so any `Some(proof)` — valid or not — triggers the panic when `decryptor` is absent. The only gate before this line is `msg.pop.verify(...)` (encryption.rs:374-379), a Schnorr PoP over `pop_challenge(context, R, key, sender, msg)` that any accuser can produce for any `sender` value by choosing their own ephemeral key — no DKG secret is required.

Likewise, if `decrypt_with_proof` returns `Ok`, `blame_internal` indexes `self.commitments[&sender]` (pedpop/src/lib.rs:599), panicking on an out-of-set `sender`.

No bound check on `sender`/`recipient` exists anywhere in the blame path; `Participant::new` only rejects zero (crypto/dkg/src/lib.rs:29-35), so `Participant(0xFFFF)` or any index `> n` is accepted as an argument and reaches the panicking index.

### Impact Explanation
The analog of the fedimint report maps cleanly: there, a panicking iroh handler unwound into the task-group guard and killed the gateway process; here, a panic in `blame`/`blame_internal` unwinds out of the library entirely — the PedPoP API returns `Participant`, not a `Result`, so no `Err` path exists for malformed accusations. Any node (participant or third-party arbitrator via `AdditionalBlameMachine`) that evaluates an accusation containing a validly-signed `EncryptedMessage` and a `recipient`/`sender` outside `1 ..= n` aborts its thread of execution. If blame evaluation runs inside a task that guards a service (the standard `spawn_cancellable`/restart-deployment pattern), this is a remotely triggered, deterministic crash loop: the accuser can re-submit the same poisoned accusation each restart. Since accusations are broadcast/transcript data, one crafted accusation can crash every honest party that evaluates it, permanently stalling abort-slash adjudication for the DKG session.

### Likelihood Explanation
Reachability is high: `AdditionalBlameMachine::blame` is a public API consuming accusation data (`msg: EncryptedMessage`, `proof: Option<EncryptionKeyProof>`, plus two `Participant` indexes) that the crate documents as usable by non-participants. Constructing a passing `msg.pop` requires only a fresh scalar and `SchnorrSignature::sign` — no key share, no collusion, no privileged position. The `Some(proof)` branch needs only any `EncryptionKeyProof` bytes, since the panic precedes `dleq.verify`. Constraints: the accuser must get honest parties to evaluate the accusation (depends on the integrator's blame-gossip path), and `sender`/`recipient` are chosen by the caller — a correctly written integrator could pre-validate them, but nothing in the library or its docs (`blame`'s doc comments, crypto/dkg/pedpop/src/lib.rs:611-622, 664-673) instructs callers to bounds-check the indexes, and `AdditionalBlameMachine::new`'s own doc warns about invalid *commitments* but not invalid accusation indexes.

### Recommendation
Validate `sender` and `recipient` at the top of `blame_internal` (pedpop/src/lib.rs:575): return the accusing party (or a dedicated error/`Option`) when `u16::from(recipient)`/`u16::from(sender)` exceed `n` or are otherwise not registered. Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `HashMap::get` returning an early `Err`/`None` instead of panicking. Consider changing `blame`'s signature to return `Result<Participant, PedPoPError<C>>` so malformed accusations are rejectable rather than fatal.

### Proof of Concept
```rust
// Participant p_evil (or any non-participant, via AdditionalBlameMachine) submits a blame
// accusation naming a recipient index outside 1..= n.

// 1. Craft an EncryptedMessage with a valid proof-of-possession for an arbitrary `from`.
//    pop_challenge binds `sender`, so sign with sender = any in-range participant.
let key = Zeroizing::new(C::random_nonzero_F(&mut rng));
let nonce = Zeroizing::new(C::random_nonzero_F(&mut rng));
let msg: EncryptedMessage<C, SecretShare<C::F>> = EncryptedMessage {
  key: C::generator() * key.deref(),
  pop: SchnorrSignature::sign(
    &key,
    nonce.deref().clone().into(),
    pop_challenge::<C>(context, C::generator() * nonce.deref(), C::generator() * key.deref(),
                       sender, b"garbage-share-bytes"),
  ),
  msg: Zeroizing::new(SecretShare(C::F::ZERO.to_repr())),
};

// 2. Any proof bytes suffice — the panic occurs evaluating verify's arguments.
let proof = Some(attacker_encryption_key_proof);

// 3. `recipient` = Participant::new(n as u16 + 1) (or u16::MAX) — non-zero, so Participant::new
//    accepts it, but it was never registered in `Decryption::enc_keys`.
let recipient = Participant::new(u16::MAX).unwrap();

// 4. Honest node evaluates the accusation:
blame_machine.blame(sender, recipient, msg, proof);
//    -> decrypt_with_proof: msg.pop.verify(...) passes (valid PoP)
//    -> proof.is_some() branch
//    -> self.enc_keys[&decryptor]  // thread 'main' panicked: 'no entry found for key'
```

Equivalent crash via `AdditionalBlameMachine::blame` for a non-participant evaluator, and via `self.commitments[&sender]` (pedpop/src/lib.rs:599) when `decrypt_with_proof` succeeds but `sender` is out of range.
