### Title
`update_token` chain-config rotation permanently strands in-flight escrowed funds because `on_timeout`/`on_accept` re-resolve the asset via the *current* `ContractToAsset` mapping instead of the mapping in effect when the request was dispatched - (File: modules/pallets/hyper-fungible-token/src/lib.rs, modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
The external report's core invariant break is: a system caches/binds to an external contract address, that external contract's address/interface later changes, and the code path that must react to (or unwind) that dependency breaks — funds get stuck and require a "painful," potentially unsafe recovery.

`pallet-hyper-fungible-token`'s `update_token` extrinsic [1](#0-0)  lets `CreateOrigin` rotate a token's EVM contract address per chain. It immediately overwrites `TokenContracts`/`ContractToAsset`/`Precisions` for the asset, deleting the old `(chain, old_contract) → asset_id` reverse mapping. But `on_timeout` (used to refund escrowed/burned funds for requests that never got delivered) looks the asset back up from `ContractToAsset` using the **current** state at execution time, keyed by the `to` address recorded in the original (now-stale) request, not a snapshot taken at dispatch time [2](#0-1) . The same current-state lookup problem exists for `on_accept`, keyed by `from`/`source` [3](#0-2) .

### Finding Description
1. A user calls `send` while the asset's chain config points at contract `C_old`. Funds are escrowed/burned, and a `DispatchPost` is emitted with `to: C_old` [4](#0-3) .
2. Before the message is delivered or timed out, governance calls `update_token` to rotate the chain's contract address to `C_new` (e.g., because the EVM-side `HyperFungibleToken`/`WrappedHyperFungibleToken` contract was redeployed/upgraded — directly analogous to the Angle gauge upgrade in the source report). `update_token` removes `ContractToAsset::(chain, C_old)` and only inserts `ContractToAsset::(chain, C_new)` [5](#0-4) .
3. If the destination never processes the message (or the message was already stuck for any of the normal ISMP reasons — liveness failure, fee spike, etc.) and later times out, `on_timeout` tries `ContractToAsset::<T>::get(dest, &to)` where `to == C_old`. That entry no longer exists, so the call returns `Err(HftError::UnknownContractOnTimeout)` [6](#0-5) .
4. Per the ISMP timeout handler's documented invariant, a failing module callback causes the request commitment (and any escrow bookkeeping) to be restored rather than cleared, explicitly so the timeout "can be retried later" [7](#0-6)  and confirmed in the protocol docs: "if `IsmpModule::on_timeout` does not return `Ok`, the commitment... will not be deleted, allowing the timeout to be replayed" [8](#0-7) .
5. Because the failure is deterministic (the old contract mapping is gone from storage, not a transient liveness issue), **no retry of the timeout can ever succeed** unless governance manually re-inserts the old `(chain, C_old) → asset_id` entry into `ContractToAsset`/`TokenContracts` before processing the timeout — mirroring exactly the "painful shutdown/backwards-compatibility" rescue procedure described in the source report. Until then, the user's escrowed/burned funds are permanently unreachable through the normal protocol path.
6. The same lookup-by-current-state pattern in `on_accept` means a legitimate, still-in-flight message from `C_old` that finally lands after rotation will also be rejected with `UnknownSourceContract`, and (being a failed `on_accept`) it is not receipted and can be endlessly retried but never succeed for the same deterministic reason, again only resolvable by an operator manually restoring the mapping.

### Impact Explanation
This falls squarely within the bounty's "loss/lock of funds" and "logic attacks on request/timeout paths" categories: user funds legitimately escrowed or burned by `send` become permanently unrecoverable through the pallet's own state-transition rules the moment the token's chain configuration is rotated, with no automatic remediation path and no way for the pallet itself to reference the historical binding that was valid when the request was dispatched. This is the direct, local analog of the Angle/veToken issue: an "upgrade" of the paired external contract (the EVM `HyperFungibleToken` deployment) desynchronizes from state that another code path implicitly assumed would remain valid, freezing funds and requiring an out-of-band, ad hoc rescue by privileged operators — exactly the situation the cited report calls Medium severity.

### Likelihood Explanation
Contract rotation via `update_token` is an expected, documented operational action (add/remove/replace chain contract entries), not a hypothetical admin error — the pallet's own README documents `update_token` as a normal maintenance call ("Add or remove chains from an existing token's configuration"). Any in-flight `send`/incoming message that straddles such a rotation is affected; the window is the full round-trip latency of a cross-chain post (dispatch → relay → destination execution or timeout), so this triggers on any config change during normal, non-adversarial pallet operation, not merely a rare edge case.

### Recommendation
Do not resolve the asset/decimals binding for `on_timeout` (and ideally `on_accept`) from the *live* `ContractToAsset`/`Precisions` storage. Instead:
- Snapshot the resolved `(asset_id, decimals, native flag)` into the request's dispatch metadata (via `store_request_commitment`'s metadata blob, already plumbed through `on_request_timeout`) at `send`-time, and have `on_timeout` recover the asset/decimals from that snapshot rather than re-resolving via `ContractToAsset` at execution time.
- Alternatively, make `update_token` additive-only for reverse-lookup purposes: never delete an old `ContractToAsset` entry until all in-flight requests referencing it have either succeeded or timed out (e.g., keep old mappings retained for a grace period, or require an explicit, separate "retire" call gated on no outstanding requests).
- Add an explicit governance-only "manual settle" extrinsic that can pass an explicit historical `(chain, contract) → asset)` binding to force a refund/accept when this situation occurs, so recovery does not require directly mutating pallet storage.

### Proof of Concept
1. Register asset `A` with `chain = Evm(1)`, `token_contract = C_old` via `register_token`.
2. User calls `send { asset_id: A, destination: Evm(1), amount: X, timeout: T }`. Funds are escrowed in `Pallet::pallet_account()`; ISMP dispatches `DispatchPost { to: C_old, ... }`, storing the request commitment.
3. Before `T` elapses, governance calls `update_token { asset_id: A, add_chains: [(Evm(1), ChainConfig { token_contract: C_new, decimals })], remove_chains: [] }`. This deletes `ContractToAsset::(Evm(1), C_old)` and inserts `ContractToAsset::(Evm(1), C_new)` [5](#0-4) .
4. Message never gets delivered (e.g., relayer/network issue) and eventually times out on the source chain.
5. A relayer submits `TimeoutMessage::Post` for the request. The ISMP handler deletes the request commitment, then calls `Pallet::on_timeout`, which executes `ContractToAsset::<T>::get(Evm(1), &C_old)` → `None` → returns `Err(HftError::UnknownContractOnTimeout)` [6](#0-5) .
6. Per `modules/ismp/core/src/handlers/timeout.rs`, the failed callback causes the commitment to be restored so the timeout "can be retried" [7](#0-6) , but every subsequent retry deterministically fails the same way, since `C_old` is never coming back into `ContractToAsset`. The escrowed amount `X` is permanently stuck in `Pallet::pallet_account()` and can never be refunded to the user through the pallet's normal on_timeout path.

			origin: OriginFor<T>,
			update: TokenUpdate<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if update.asset_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					update.asset_id.clone(),
				)
			};

			for (chain, config) in update.add_chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				// Remove old reverse mapping if it exists
				if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone())
				{
					ContractToAsset::<T>::remove(chain, old_contract);
				}

				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					update.asset_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(chain, token_contract, update.asset_id.clone());
				Precisions::<T>::insert(update.asset_id.clone(), chain, config.decimals);
			}
