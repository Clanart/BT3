Audit Report

## Title
Stale, discarded ALT re-resolution lets banking-stage execute a transaction with addresses that no longer match a fresh lookup - ([File: runtime/src/bank.rs])

## Summary
`Bank::resanitize_transaction_minimally` re-resolves address lookup table (ALT) entries only to check that resolution still succeeds, then discards the result (`let (_addresses, _deactivation_slot) = ...`), while the transaction that is actually locked and executed still carries the addresses resolved at ingestion time in `translate_to_runtime_view`/`load_addresses_for_view`. Because ALT account keys are deterministic PDAs derived only from `authority` and `recent_slot` via `create_program_address`, a table can be deactivated, closed, and recreated at the identical address with different content, and a pending transaction can commit against the old, now-incorrect addresses without any mismatch check.

## Finding Description
Banking stage resolves ALT indices once against a root bank at ingestion time and bakes the resulting `LoadedAddresses` into the `ResolvedTransactionView`/`RuntimeTransaction`, alongside a `MaxAge{ sanitized_epoch, alt_invalidation_slot }` computed by `calculate_max_age`/`estimate_last_valid_slot` from the ALT's deactivation slot at that time [1](#0-0) . This transaction can then sit buffered for a period before being consumed on a later, different bank.

Before execution, `process_and_record_aged_transactions` calls `resanitize_transaction_minimally` per transaction using the cached `MaxAge` [2](#0-1) . That function's only ALT-related safety check, when `self.slot() > alt_invalidation_slot`, re-resolves the lookup purely to confirm it still resolves, and explicitly discards the freshly computed addresses:

```rust
if self.slot() > alt_invalidation_slot {
    let (_addresses, _deactivation_slot) =
        self.load_addresses_from_ref(transaction.message_address_table_lookups())?;
}
``` [3](#0-2) 

The transaction handed to `prepare_sanitized_batch_with_results`/execution retains the addresses resolved at ingestion, not the freshly re-resolved ones [4](#0-3) .

Confirmed separately: `Bank::load_addresses_from_ref` resolves ALT lookups against the *current* bank's account state and slot-hashes sysvar, returning both `LoadedAddresses` and the ALT's deactivation slot [5](#0-4) ; this is the same function called at both ingestion and resanitize time, but only the ingestion-time result is retained for execution.

The `alt_invalidation_slot` bound itself is computed once, at ingestion, from the ALT's deactivation slot *at that moment*. If the table was still active (`deactivation_slot == u64::MAX`) when the transaction was buffered, the invalidation slot estimate is based on the current slot rather than any actual deactivation event, so the re-resolution branch (`self.slot() > alt_invalidation_slot`) may not even trigger for a long time even after the referenced table has since been deactivated and closed by its authority — at which point stale, discarded resolution is not even attempted, and execution proceeds unconditionally on ingestion-time addresses.

Existing guards are insufficient because: (1) the resanitize step never compares freshly resolved addresses against the ones embedded in the transaction, only checking they resolve without error; and (2) the invalidation-slot heuristic is derived from ALT state observed at ingestion time, not continuously tracked, so it does not reliably bound the staleness window against a subsequent deactivate/close/recreate cycle by the ALT's authority.

## Impact Explanation
An unprivileged actor who controls an ALT's authority (a legitimate, caller-controlled role, not a privileged validator/node assumption) can cause a pending transaction referencing that ALT to execute against addresses that no longer correspond to the ALT's current, on-chain content. This directly maps to false execution/acceptance: the account keys used for a signed transaction's writable/readonly accounts and CPI bindings diverge from what a fresh resolution against the current ALT state would produce, potentially misdirecting fund transfers or program interactions to unintended accounts named at the original (stale) index in the lookup table.

## Likelihood Explanation
Exploitation requires the attacker to control the authority of the specific ALT referenced by the victim's pending transaction, and requires the victim's transaction to remain buffered/unconfirmed long enough to span a deactivate → cooldown → close → recreate cycle on that table, or to be buffered when the table is still active (bypassing the invalidation check entirely because `alt_invalidation_slot` was computed from an unset deactivation slot). This is timing-sensitive and depends on scheduler/container buffering behavior that is not fully controllable by the attacker, but it does not require any privileged role, malicious validator, or leaked key — only ordinary control of a program-owned ALT account the attacker created. The core code-level defect (discarding the freshly resolved value instead of validating equivalence) is unconditional and independent of timing precision.

## Recommendation
In `Bank::resanitize_transaction_minimally`, when addresses are re-resolved after crossing `alt_invalidation_slot`, compare the freshly loaded `LoadedAddresses` against those already embedded in the transaction and reject the transaction (e.g., via `TransactionError::SanitizeFailure` or a dedicated ALT-mismatch error) if they differ, rather than only checking that resolution succeeded. Additionally, consider re-deriving `alt_invalidation_slot`/deactivation tracking dynamically rather than freezing it at ingestion time, so that a subsequent deactivate/close/recreate cycle on a still-active-at-ingestion table cannot bypass the re-resolution check altogether.

## Proof of Concept
1. Attacker creates ALT `T` with authority `Auth` and `recent_slot = R`; index 0 resolves to address `X`.
2. Victim submits a v0 transaction referencing `T` index 0; banking stage resolves it to `X` at ingestion and buffers it with `MaxAge` computed from `T`'s state at that time.
3. Attacker deactivates `T`, waits out the deactivation cooldown, and closes `T` via `close_lookup_table` (reclaiming the account).
4. Attacker recreates a table at the same derived address by calling `create_lookup_table(Auth, payer, R)` again (identical PDA from identical `authority`/`recent_slot`), then extends it so index 0 now resolves to `Y ≠ X`.
5. If the victim's transaction is consumed after this point, `resanitize_transaction_minimally` either (a) does not re-resolve at all if `self.slot() <= alt_invalidation_slot`, or (b) re-resolves, gets `Y`, discards it, and returns `Ok(())` since resolution succeeded — in both cases the transaction executes with the stale `X`, not the currently valid `Y`. A unit test can construct this sequence directly against `Bank::resanitize_transaction_minimally` and `Bank::prepare_sanitized_batch_with_results` to demonstrate the discarded/stale value being used for execution.

    pub fn resanitize_transaction_minimally(
        &self,
        transaction: &impl TransactionWithMeta,
        sanitized_epoch: Epoch,
        alt_invalidation_slot: Slot,
    ) -> Result<()> {
        if self.vote_only_bank() && !vote_parser::is_valid_vote_only_transaction(transaction) {
            return Err(TransactionError::SanitizeFailure);
        }

        // If the transaction was sanitized before this bank's epoch,
        // additional checks are necessary.
        if self.epoch() != sanitized_epoch {
            // Reserved key set may have changed, so we must verify that
            // no writable keys are reserved.
            self.check_reserved_keys(transaction)?;

            for instr in transaction.instructions_iter() {
                if instr.accounts.len() > solana_transaction_context::MAX_ACCOUNTS_PER_INSTRUCTION {
                    return Err(solana_transaction_error::TransactionError::SanitizeFailure);
                }
            }
        }

        if self.slot() > alt_invalidation_slot {
            // The address table lookup **may** have expired, but the
            // expiration is not guaranteed since there may have been
            // skipped slot.
            // If the addresses still resolve here, then the transaction is still
            // valid, and we can continue with processing.
            // If they do not, then the ATL has expired and the transaction
            // can be dropped.
            let (_addresses, _deactivation_slot) =
                self.load_addresses_from_ref(transaction.message_address_table_lookups())?;
        }

        Ok(())
    }

    pub fn load_addresses_from_ref<'a>(
        &self,
        address_table_lookups: impl Iterator<Item = SVMMessageAddressTableLookup<'a>>,
    ) -> Result<(LoadedAddresses, Slot), AddressLoaderError> {
        let slot_hashes = self
            .transaction_processor
            .sysvar_cache()
            .get_slot_hashes()
            .map_err(|_| AddressLoaderError::SlotHashesSysvarNotFound)?;

        let mut deactivation_slot = u64::MAX;
        let mut loaded_addresses = LoadedAddresses::default();
        for address_table_lookup in address_table_lookups {
            deactivation_slot = deactivation_slot.min(
                self.rc
                    .accounts
                    .load_lookup_table_addresses_into(
                        &self.ancestors,
                        address_table_lookup,
                        &slot_hashes,
                        &mut loaded_addresses,
                    )
                    .map_err(into_address_loader_error)?,
            );
        }

        Ok((loaded_addresses, deactivation_slot))
    }
