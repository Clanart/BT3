### Title
Early scalar-deserialization abort leaks the ECDH blame key for messages with an unverified PoP, enabling decryption of a co-opted participant's secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
In `KeyMachine::calculate_share`, each incoming `EncryptedMessage` is decrypted and its plaintext is parsed with `C::F::from_repr` *before* the batched proof-of-possession (PoP) signatures are ever verified. If the decrypted bytes fail scalar deserialization, the function returns early with `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` — publishing the ECDH shared key (`EncryptionKeyProof.key`) for a message whose PoP was never checked. This recreates the exact attack the per-message PoP was added to prevent: an adversary copies another participant's per-message encryption key into their own message, triggers a blame, and the victim's revealed ECDH key also decrypts the honest participant's real secret-share message.

### Finding Description
`Encryption::decrypt` does not verify the PoP inline; it only queues the Schnorr `pop` statement into the `BatchVerifier` under `BatchId::Decryption(l)` and immediately computes `key = ecdh(self.enc_key, msg.key)`, decrypts the ciphertext, and returns the blame proof containing that ECDH point [1](#0-0) . Back in `calculate_share`, the loop calls `C::F::from_repr(share_bytes.0)` and returns `Err(InvalidShare { blame: Some(blame) })` on failure — before `batch.verify_with_vartime_blame()` at line 493 ever runs [2](#0-1) . Consequently the PoP is a queued-but-never-verified statement whenever deserialization fails first.

The code comments acknowledge the threat model explicitly: if Eve reuses Alice's key `X`, Bob's blame proof reveals `bX`, "revealing Alice's message to Bob"; the PoP "ensur[es] only those actually with per-message keys can claim to use them" [3](#0-2) . The spec repeats this rationale [4](#0-3) . That protection is void on the `from_repr` error path, since the batch verification that enforces the PoP is skipped.

The downstream handler serializes and broadcasts this blame: `key_gen.rs` maps `PedPoPError::InvalidShare { blame }` into `ProcessorMessage::InvalidShare { blame: Some(blame.map(|b| b.serialize())) }` [5](#0-4) , and `VerifyBlame`/`AdditionalBlameMachine::blame` will happily decrypt the message with any supplied `EncryptionKeyProof` whose DLEq verifies — the revealed `key` is a valid proof for both Eve's forged message and Alice's original one (same `msg.key` → same ECDH point) [6](#0-5) .

### Impact Explanation
Information disclosure of a threshold secret share. The revealed ECDH point `bX` decrypts not only Eve's garbage ciphertext but also Alice's genuine `EncryptedMessage` to Bob, exposing the secret share Alice contributed to Bob. Combined with a second compromised/dealt share for the same recipient index (the DKG sums shares from all participants), recovery of another party's polynomial contribution weakens key-share confidentiality and, depending on the number of co-opted messages, can contribute toward key-share recovery. Severity is Medium: it leaks secret key material through an observable response discrepancy (error-with-blame-key vs. error-without), matching the CVE-2021-0089 bug class, but requires a DKG participant slot and a probabilistic deserialization failure.

### Likelihood Explanation
The attacker must be a DKG participant able to send a share message to a victim and observe an honest sender's ciphertext to the same victim — both messages are transmitted over authenticated channels as assumed by the protocol. The leak triggers whenever the garbage plaintext fails `from_repr`; for 255-bit scalar fields (Ristretto/ed25519, k256, p256) random 32-byte output is non-canonical with overwhelming probability (~1 − l/2^256 ≈ 15/16 for ed25519). No collusion or BFT break is needed, only one malicious participant and one honest co-opted `key` point.

### Recommendation
Verify the per-message PoP *before* returning a blame proof that contains the ECDH key. Concretely: in `calculate_share`, defer attaching `blame` to the `from_repr` error until after `batch.verify_with_vartime_blame()` has run — e.g., record the deserialization failure per participant, run the batch PoP verification, and only emit `blame: Some(_)` for senders whose PoP verified (a failed PoP should yield `blame: None`, matching the `BatchId::Decryption` path). Alternatively, verify the PoP inline inside `Encryption::decrypt` before computing/returning the ECDH key.

### Proof of Concept
1. Participants Alice (1), Eve (2), Bob (3) run PedPoP. Bob registers his `enc_key`. Alice sends Bob `EncryptedMessage` with `key = X` (a valid PoP, unknown discrete log to Eve).
2. Eve builds her share message to Bob reusing `key = X` and arbitrary 32 garbage bytes as `msg`, signing a PoP over her own fresh key — or simply attaching any `pop` bytes, since the PoP is never verified on this path.
3. Bob's `calculate_share` calls `encryption.decrypt`, computing `key = bX` (Bob's `enc_key` × Eve's claimed `msg.key` = the same ECDH point as Alice's message), decrypts to garbage, `from_repr` fails (~15/16 odds), and returns `InvalidShare { participant: 2, blame: Some(EncryptionKeyProof { key: bX, dleq }) }`.
4. Bob broadcasts the blame; everyone (including Eve) now holds `bX`, applies `cipher(context, bX)` to Alice's original ciphertext, and recovers Alice's secret share to Bob — the exact disclosure the PoP and comment at `encryption.rs:84-90` were designed to prevent.

While key reuse by a participant is considered as them revealing the messages

adversary claims another participant's encryption key. They'll fail to encrypt
their message, and the recipient will issue a blame statement. This blame
statement, intended to reveal the malicious adversary, also reveals the message
by the participant whose keys were co-opted. To resolve this, a
proof-of-possession is also included with encrypted messages, ensuring only
those actually with per-message keys can claim to use them.
