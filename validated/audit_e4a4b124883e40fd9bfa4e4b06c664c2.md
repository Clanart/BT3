### Title
Unchecked u64 overflow in payment/input summation lets an invalid transaction (outputs exceeding inputs) be constructed and signed - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
The libxml2 report describes integer counters overflowing when attacker-controlled input sizes exceed the width of the counter, producing invalid internal state and a crash. The direct analog in Serai is in `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`, where payment and input satoshi totals are accumulated with plain `u64` `sum()`/`+` arithmetic with no overflow checks. An unprivileged user who can request payments (withdrawal/burn instructions carry a `u64` amount field in `ExternalBalance`/`Payment`) can supply amounts whose sum overflows `u64`, causing the `NotEnoughFunds` sanity check to be bypassed and a consensus-invalid transaction — one whose outputs exceed its inputs — to be produced for threshold signing, or a panic/underflow in `fee()`.

### Finding Description
`SignableTransaction::new` at `networks/bitcoin/src/wallet/send.rs` performs:

- `let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();` (line 175)
- `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();` (line 187)
- `let mut needed_fee = fee_per_vbyte * vbytes;` (line 206)
- `if input_sat < (payment_sat + needed_fee) { Err(NotEnoughFunds) }` (line 215)

Only a lower-bound check (`*amount < DUST` at line 165-169) is applied to each payment amount; there is no upper bound and no checked/saturating arithmetic. If the sum of payment amounts wraps modulo 2^64, `payment_sat` becomes a small value, `input_sat < (payment_sat + needed_fee)` evaluates false, and the function proceeds to build `tx_outs` where each `TxOut` carries `Amount::from_sat(payment.1)` — astronomically large values. The result is a transaction whose declared outputs exceed its inputs, which is consensus-invalid on Bitcoin.

Additionally, `fee()` (lines 138-141) computes `sum(prevouts) - sum(outputs)` with an unchecked subtraction; once the overflow above has occurred this underflows `u64`, panicking in debug builds and returning a wrapped garbage fee in release builds.

### Impact Explanation
- **Availability (matches the libxml2 DoS class):** the overflowing `payment_sat` path yields a `SignableTransaction` that is fed into the FROST signing pipeline (`bitcoin_serai::Schnorr`/`TransactionMachine`). Either the coordinator/processor panics on the `u64` underflow in `fee()` or on `tx.weight()`/serialization handling, or an invalid transaction is signed and broadcast, causing the sign session to fail and the plan to be treated as completed while funds never move.
- Because the plan/scheduler marks outputs per the constructed `SignableTransaction`, user payments can be reported as processed though no valid spend exists — funds are not spendable as reported.

### Likelihood Explanation
Payment amounts originate from external user instructions (`Payment.balance.amount` is a `u64` in `processor/src/plan.rs`, decoded from user-submitted SCALE data). Two payments each slightly above `u64::MAX / 2` (or several large amounts) are sufficient to wrap `payment_sat`. No validator privileges or collusion are needed — only the ability to submit payment requests with large amounts, which is a public input. Exploitation requires amounts exceeding the real Bitcoin supply, so this is primarily a robustness/DoS issue rather than theft: the transaction is consensus-invalid, hence Medium severity.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`: `try_into`-bounded `checked_add`/`checked_sum` for `input_sat`, `payment_sat`, `payment_sat + needed_fee`, and `fee_per_vbyte * vbytes`; reject any overflow with a `TransactionError`. Also bound each payment amount to a sane maximum (e.g., ≤ 21M BTC in satoshis) and use `checked_sub` in `fee()`.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// In release mode arithmetic wraps; in debug it panics.
// Construct two payments whose sum wraps u64:
let payments = [
    (p2tr_script_buf(even_key).unwrap(), u64::MAX - 100),
    (p2tr_script_buf(even_key).unwrap(), u64::MAX - 100),
];
// payment_sat = (2*u64::MAX - 200) mod 2^64 = u64::MAX - 201 -> still huge;
// use three payments of ~u64::MAX/2 so the sum wraps to a *small* value:
let payments = [
    (script.clone(), (u64::MAX / 2) + 10),
    (script.clone(), (u64::MAX / 2) + 10),
    (script.clone(), (u64::MAX / 2) + 10),
];
// payment_sat wraps to ~(u64::MAX/2 + 30), which is still > input_sat for real
// inputs, so pick amounts such that the wrapped sum < input_sat, e.g.
// payments summing to 2^64 + k where k < input_sat.
let tx = SignableTransaction::new(
    vec![received_output_with_1_btc], // input_sat = 100_000_000
    &payments,                        // wrapped payment_sat < input_sat
    None,
    None,
    1,
);
// Ok(...) is returned despite outputs vastly exceeding inputs;
// tx.fee() then underflows u64 -> panic (debug) or wrapped fee (release);
// signing produces a consensus-invalid transaction that is broadcast.
```

Note: the exact wrap condition requires the payment amounts (each ≥ `DUST = 546` sats, unbounded above) to sum to `2^64 + r` with `r + needed_fee ≤ input_sat`; since `input_sat` is at most ~2.1e15 sats this is achievable with two payments of `2^63` plus a small `r`. The root cause is that `payment_sat` (line 187), `payment_sat + needed_fee` (line 215), and the subtraction in `fee()` (lines 139-140) use unchecked `u64` arithmetic on attacker-influenced values — the same bug class as the libxml2 counter overflow, just at the value layer rather than the buffer-offset layer.
