## Confirmed local analog: `withdraw_fees` zeroes relayer `Fees` before the cross-chain payout is confirmed to succeed

### Title
Relayer fees permanently zeroed on Hyperbridge even though the destination-chain payout can revert or never execute - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-ismp-relayer::withdraw` zeroes the relayer's `Fees` entry on Hyperbridge as soon as the outbound ISMP request is *dispatched* (i.e., locally queued), not after the destination chain confirms the payout was actually executed. This is the same broken invariant as the Curve report: a bookkeeping value (`last_update` / here, `Fees`) is unconditionally advanced/reset regardless of whether the underlying value-transfer effect it represents actually landed, permanently blocking (burning) the relayer's reward with no path to reclaim it.

### Finding Description
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs`: [1](#0-0) 

reads `available_amount` from `Fees::<T>::get(...)`, builds a `DispatchPost` to the destination's `HostManager` (EVM) or `HYPERBRIDGE_MODULE_ID` (substrate), calls `dispatcher.dispatch_request(...)`, and — as soon as that local dispatch call returns `Ok` — immediately does:
```rust
Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());
```
`dispatch_request` only commits the request to `RequestCommitments`/offchain storage for later relaying; it does not, and cannot, confirm that the destination chain will actually execute the payout. Execution on the EVM side happens later, asynchronously, in `HostManager.onAccept` → `EvmHost.withdraw`: [2](#0-1) 

That destination-side call can fail for reasons entirely outside the relayer's or Hyperbridge's control at withdrawal time:
- Insufficient fee-token balance on the `EvmHost` contract (confirmed to revert via `SafeERC20`, exercised by the repo's own test `test_host_manager_insufficient_balance`): [3](#0-2) 
- Native-ETH transfer failing (`WithdrawalFailed` revert) if `params.token == address(0)` and the low-level `call` fails.
- `HostManager` params not yet configured/mismatched on that destination (`MissingMangerAddress` guarded only at time of dispatch, not re-checked at execution).

Because `Fees` is zeroed *before* any of this destination-side execution is known to succeed, and because the withdrawal request is dispatched with `timeout: 0` (i.e., it "will not timeout" per the docs, so there's also no timeout-triggered refund path back into `Fees`), a destination-side revert or a stuck/never-delivered message leaves the relayer's fee balance at zero on Hyperbridge permanently, with the actual tokens never disbursed on the destination chain either. This mirrors the Curve bug exactly: a state field that gates future reward retrieval (`last_update` there, `Fees` here) is mutated unconditionally on the "happy path" trigger, without gating on whether the value it's supposed to reflect was actually realized, so rewards become unrecoverable.

### Impact Explanation
This is a genuine fund-loss/lock bug matching the bounty's "stealing or loss of funds" and "logic attacks" categories: an unprivileged relayer who has legitimately earned fees can permanently lose them through no fault of their own (e.g., a temporary EvmHost fee-token balance shortfall, a HostManager misconfiguration, or any transient destination-execution failure), because the accounting entry that represents their claim is destroyed at dispatch time rather than at confirmed-settlement time. There is no compensating retry-from-Hyperbridge-side mechanism once `Fees` is zeroed — the relayer would have to be re-credited by `accumulate` from scratch, which requires re-proving delivery of the *original* request commitments, but those commitments were likely already marked `claimed` in `RequestCommitments` in the prior `accumulate` step, making re-accumulation impossible for the same delivered messages.

### Likelihood Explanation
This does not require a malicious peer, relayer, prover, or admin — it is triggered by ordinary operational conditions (e.g., `EvmHost` temporarily under-funded on the fee token, or the destination `HostManager`/`hostParams` momentarily misconfigured) combined with any relayer simply calling the normal, permissionless `withdraw_fees` extrinsic. It's a systemic assume-success bug in the withdrawal pipeline rather than an exotic attack, making it highly likely to manifest in production over time.

### Recommendation
Do not zero (or decrement) `Fees` until destination-side execution is confirmed. Options:
1. Move the `Fees::<T>::insert(..., U256::zero())` to a confirmation step — e.g., only clear/decrement the fee balance once Hyperbridge observes a receipt/ack that the destination successfully executed the withdrawal (similar to how `accumulate` proves delivery via receipts).
2. Alternatively, keep a pending/escrow sub-state (`Fees` minus `PendingWithdrawal`) so that if the dispatched request later fails or times out, the amount is restored to `Fees` rather than lost, and expose a governance/relayer-triggered reconciliation path for stuck withdrawals.
3. At minimum, use a non-zero timeout on the `DispatchPost` and implement `on_timeout` handling that re-credits `Fees::<T>` for the affected relayer/chain, rather than relying on "will not timeout" semantics that leave no recovery path for a destination-side revert.

### Proof of Concept
1. Relayer accumulates fees for deliveries to `StateMachine::Evm(X)`, so `Fees::<T>::get(Evm(X), relayer) = N > MinWithdrawal`.
2. `EvmHost` on chain `X` has (or is later drained to have) fee-token balance `< N` (a normal, non-adversarial condition — e.g., another withdrawal already consumed the balance, or the host hasn't been topped up yet).
3. Relayer calls `withdraw_fees` with `dest_chain = Evm(X)`. On Hyperbridge: `dispatch_request` succeeds (message queued), and in the same extrinsic `Fees::<T>::insert(Evm(X), relayer, U256::zero())` executes unconditionally.
4. A relayer later delivers the `[Consensus, Request]` batch to chain `X`; `HostManager.onAccept` calls `EvmHost.withdraw`, which reverts per `test_host_manager_insufficient_balance` behavior (confirmed in-repo) because the host lacks sufficient fee-token balance. [4](#0-3) 
5. The ISMP request execution fails on chain `X` and (per docs) carries `timeout: 0`, so no timeout callback fires on Hyperbridge to restore the balance.
6. Result: the relayer's `N` fee tokens were never paid out on chain `X`, and `Fees::<T>::get(Evm(X), relayer)` is now `0` on Hyperbridge — the reward is permanently lost.

        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
