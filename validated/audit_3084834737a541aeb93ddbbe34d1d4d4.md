## Analysis

`purchase()` in `BandwidthManager.sol` is a fully permissionless entrypoint: anyone can call it, targeting an arbitrary `app` and arbitrary `chain` (the sponsorship model), and it only requires paying `tierPrice[tier] * months` in fee token. [1](#0-0) 

On Hyperbridge, `pallet-bandwidth` credits whatever `(app_chain, app)` pair is named in the message body — not validated against `request.source` or any owner of the app — into a FIFO list capped at 1024 entries (`MAX_SUBSCRIPTIONS`). Every purchase, regardless of size, is one queue entry; same-tier repurchases don't stack. [2](#0-1) 
When the list is full, the **oldest** entry is evicted outright with no refund, only an audit event: [3](#0-2) 

This is the direct analog of the "unlimited concurrent requests" bug class: the purchase/credit path has no rate limit, no per-source or per-app throttle, and no cap on how many cheap/small purchases an unprivileged, unrelated third party can fire at a victim's `(app_chain, app)` bucket. An attacker can flood 1024 minimal purchases (lowest configured tier, `months = 1`) at a victim app to push out the victim's genuinely large, still-unconsumed subscription(s) that the victim already paid real fee-token value for. The evicted subscription's `remaining_bytes` are gone permanently — this is a concrete loss of already-paid-for funds/allowance, not merely a resource-exhaustion DoS, satisfying the "stealing or loss of funds" / logic-attack bar in the impact gate.

## Why existing guards don't stop this

- There is no ownership check binding a purchase's `app_chain`/`app` target to `msg.sender`/`request.source` — the docs describe this as an intentional "sponsorship" feature. [4](#0-3) 
- The FIFO cap eviction logic has no minimum remaining-value protection — it always evicts index 0 regardless of the evicted subscription's remaining bytes or expiry, so a large recent-but-oldest-inserted subscription can be evicted by a wave of trivial purchases. [5](#0-4) 
- There is no per-(source, app) purchase rate limiting anywhere in the dispatch or `on_accept` path (only `Allowlist` bypass and manager-address checks exist), so nothing throttles the "concurrent request" volume an attacker can generate.

## Caveat

I could not find the exact `on_accept` handler body that processes `BandwidthPurchaseMsg` (it wasn't returned in the excerpts, only `push_subscription`/`is_purchase_message` helpers and the pallet calls), so I can't 100% confirm there isn't an additional server-side ownership/allowlist gate applied specifically inside `on_accept` before calling `push_subscription`. Given the documentation explicitly describes cross-chain "sponsorship" as intended behavior (crediting any `(app_chain, app)` from any payer), this appears to be a real, if arguably semi-intentional, design gap rather than a straightforward coding bug — worth flagging to Devin/Polytope Labs to confirm whether griefing-via-eviction was considered, but the underlying "no rate limit on the credit/eviction path" issue is directly analogous to the reported unlimited-concurrent-requests class.

### Title
Unthrottled permissionless bandwidth purchases allow eviction/loss of a victim app's paid subscriptions — ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth`'s FIFO subscription list per `(app_chain, app)` is capped at 1024 entries and silently evicts the oldest entry (with its unconsumed `remaining_bytes`) whenever a new purchase lands. Because `purchase()` on `BandwidthManager.sol` is permissionless and its `app`/`chain` targets are attacker-controlled (the "sponsorship" model), and there is no rate limit on purchase-credit messages, an attacker can flood cheap tier purchases at a victim's `(app_chain, app)` to force-evict the victim's larger, still-unconsumed, already-paid subscription.

### Finding Description
`purchase()` lets any caller pay for any `(app, chain)` pair. [6](#0-5) 
On Hyperbridge, each purchase appends a `Subscription` to a `BoundedVec` capped at `MAX_SUBSCRIPTIONS` (1024); pushing past the cap evicts index 0 unconditionally, regardless of its remaining value. [7](#0-6) 
There is no minimum-purchase-value gate, no per-`(source, app)` rate limit, and no check that the purchaser is related to the targeted app — this mirrors the "unlimited concurrent requests" bug class where an unbounded stream of cheap requests degrades/damages a shared resource, except here the resource is the victim's already-paid bandwidth balance rather than server memory.

### Impact Explanation
An unprivileged attacker can permanently destroy a victim app's paid-for, unconsumed bandwidth allowance by filling the FIFO queue with 1024 trivial purchases targeting the victim's `(app_chain, app)` key, evicting the victim's legitimate high-value subscription before it is drained. This is a direct loss of funds already paid to the protocol (the evicted `remaining_bytes` are gone with no refund path — only a `SubscriptionEvicted` event).

### Likelihood Explanation
Moderate to high: the attack requires no special privileges, no relayer/prover/admin collusion, and no wrong assumptions about honest actors — it only needs the attacker to have fee tokens to pay for cheap tier purchases (the lowest tier at `months=1` is minimal cost) and knowledge of the victim's `(app_chain, app)` identity, which is public on-chain information.

### Recommendation
Add per-`(source, app)` purchase rate limiting or a minimum-value/no-op-on-non-owner-purchase gate; alternatively, evict based on remaining value/expiry rather than strict FIFO, or require that only the app itself (or an allowlisted sponsor) can credit its own `(app_chain, app)` bucket, closing the open sponsorship griefing surface while still allowing intentional sponsorship via an explicit opt-in registry.

### Proof of Concept
1. Victim app buys a large tier subscription (e.g., TierFour, many months) crediting `(EVM-8453, victimApp)`, leaving most of `remaining_bytes` unconsumed and sitting at some position in the FIFO list.
2. Attacker calls `BandwidthManager.purchase(app: victimApp, tier: TierOne, months: 1, chain: "EVM-8453")` repeatedly (self-funded, minimal cost) until 1024 entries have been queued after the victim's subscription.
3. Once the list is at cap, each subsequent attacker purchase evicts the oldest entry; by controlling ordering/timing the attacker forces the victim's high-value subscription to reach index 0 and be evicted via `push_subscription`'s `list.remove(0)` path.
4. `SubscriptionEvicted` fires with the victim's `lost_bytes`; the victim's paid bandwidth is unrecoverable while the attacker has spent comparatively little to grief a much larger prepaid balance. [3](#0-2)

    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

        commitment = IDispatcher(_host).dispatch(
            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
