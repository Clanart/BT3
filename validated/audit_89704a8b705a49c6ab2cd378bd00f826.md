Based on my investigation of the `IntentGatewayV2` same-chain fill path, I found a real, provable double-spend analog in `IntrinsicIntents._fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:116-122`).

### Title
Escrow release keyed by token address instead of per-output index lets a duplicate-input-token order over-release escrow on same-chain fills - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_orders` is a `mapping(bytes32 commitment => mapping(address token => uint256))`, aggregated **per token address**, not per output index [1](#0-0) . In `_fillSameChain`, when an output leg reaches full fill (`amountFilled == totalRequired`), the code releases escrow via `_orders[commitment][address(uint160(uint256(order.inputs[i].token)))]` — i.e. it releases the **entire remaining balance stored for that token**, not the amount attributable to output leg `i` [2](#0-1) .

### Finding Description
If a user places an order whose `order.inputs` array contains the **same token address at two different indices** (e.g. `inputs[0].token == inputs[1].token == USDC`, paired respectively with `output.assets[0]` and `output.assets[1]`), the escrow for that token accumulates as one scalar under `_orders[commitment][USDC]`. When a solver fully fills leg `0` first, the "final fill" branch pulls the **entire current `_orders[commitment][USDC]` balance** (which still includes the escrow that legitimately belongs to leg `1`) and sends it all to the solver via `_withdraw`. `_withdraw` then decrements `_orders[commitment][USDC]` by that same amount, zeroing it out [3](#0-2) . When the solver (or another solver) later tries to fill leg `1`, `_withdraw` finds `escrowed == 0` and reverts with `UnknownOrder`, permanently freezing the user's unfulfilled leg's output requirement while the escrow has already been drained to the first solver. This produces unauthorized fund transfer to the solver beyond what output leg `0` earned, and permanently locks/loses the portion of escrow that should have backed output leg `1`.

The bug is structurally identical to the Salty.IO "suboptimal/incorrect closed-form calculation of an intermediate value" bug class: the code substitutes an aggregate quantity (`_orders[commitment][token]`, an approximation of "what leg `i` deserves") for the exact, index-scoped quantity, producing incorrect fund movement in specific input states.

### Impact Explanation
This is a fund-loss / wrong-beneficiary bug reachable by any unprivileged user (the order creator, since they define `order.inputs`) in combination with any solver acting as an unprivileged filler. The solver who fills the first leg receives more escrow than they are entitled to (the full aggregated token balance instead of the proportional/exact amount for their leg), and the escrow meant for the second leg's ultimate output is unrecoverable — it can neither be released to a solver filling leg 2 (reverts) nor refunded (cancel logic also checks `_orders[commitment][token] == 0` and would revert with `UnknownOrder`, per `IntrinsicIntents._cancelSameChain` and `ExtrinsicIntents._cancelFromSource`). This satisfies the bounty's "stealing or loss of funds" / "logic attacks" impact class.

### Likelihood Explanation
Likelihood depends on whether the protocol/SDK permits (or fails to reject) an `Order` with duplicate `inputs[].token` entries mapped to distinct output legs. Nothing in `IntentsBase._validateParams` or the order-placement path found in this scan validates input-token uniqueness across indices; the vulnerability is purely a user-supplied-data condition, not a malicious relayer/prover/admin assumption, and requires only an ordinary user constructing a slightly unusual (but not obviously invalid) order and a normal solver filling it leg-by-leg.

### Recommendation
Track escrow per `(commitment, outputIndex)` (or `(commitment, token, index)`) rather than aggregated solely by `(commitment, token)`, or explicitly reject orders whose `inputs[].token` values are not unique at placement time. The final-fill branch in `_fillSameChain` should compute the exact remaining amount owed to output leg `i` (e.g., tracking a separate escrowed-per-leg accumulator) instead of reading the token-wide aggregate balance.

### Proof of Concept
1. User places a same-chain `Order` with `inputs = [{token: USDC, amount: 600}, {token: USDC, amount: 400}]` and `output.assets = [{token: DAI, amount: 60}, {token: WBTC, amount: 1}]`. Placement escrows a combined `1000 USDC` under `_orders[commitment][USDC] = 1000` (single slot, per `IntentsBase._orders` mapping).
2. Solver A calls `fillOrder` providing `output.assets[0]` (`60 DAI`) in full. In the loop iteration for `i = 0`, `amountFilled == totalRequired` is true, so `escrowedAmount = _orders[commitment][USDC]` reads `1000` (the full combined balance, not the `600` share for leg 0).
3. `_withdraw` transfers `1000 USDC` to Solver A and sets `_orders[commitment][USDC] = 0` (`escrowed - amount` at `evm/src/apps/intentsv2/IntentsBase.sol:403`).
4. Solver B later calls `fillOrder` providing `output.assets[1]` (`1 WBTC`) in full. In the loop for `i = 1`, `_orders[commitment][USDC]` is now `0`, so `_withdraw` reverts with `UnknownOrder`, freezing the fill. The user's second output leg can never be satisfied, and Solver A received `400 USDC` more than they were entitled to for delivering only `60 DAI`. [2](#0-1) [4](#0-3)
