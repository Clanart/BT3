### Title
Stale line-selection index reused against a freshly re-fetched diff causes silent inclusion/exclusion of unintended lines in partial commits/discards - (File: `app/src/lib/git/apply.ts`)

### Summary
`_commitIncludedChanges` uses the `WorkingDirectoryFileChange.selection` object that was computed by the renderer against a diff snapshot taken earlier, but `applyPatchToIndex` re-fetches a brand-new diff from disk (`getWorkingDirectoryDiff`) immediately before building the patch, and then maps the *old* selection's absolute line indices onto the *new* diff's line indices with no re-validation that the two still correspond to the same content.

### Finding Description
`applyPatchToIndex` (used for every partial/line-level commit and by `stageFiles`) does: [1](#0-0) 

It fetches `diff` fresh from the working directory, then calls `formatPatch(file, diff)` — but `file.selection` is the selection state built by the UI against whatever diff was rendered on screen (potentially seconds or longer ago). `formatPatch` and `formatPatchToDiscardChanges` decide whether to keep/drop/reverse a line purely by `absoluteIndex = hunk.unifiedDiffStart + lineIndex` looked up in `selection.isSelected(absoluteIndex)`: [2](#0-1) [3](#0-2) 

These indices are purely positional (hunk start offset + line offset within the hunk) — they carry no content hash or line-content binding. If the on-disk file content changes between the moment the UI diff was rendered/selection recorded and the moment `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` runs (e.g., because a build tool, an editor autosave, a git hook, `.gitattributes`/`core.autocrlf` re-normalization, or a background fetch/checkout touches the tracked file), the newly fetched diff can have different hunk boundaries, line counts, or line ordering than the diff the selection indices were computed against. The stale absolute indices from the old selection will then be blindly matched against unrelated lines in the new diff, causing the generated patch to select/deselect the *wrong* lines.

The application is aware this invalidation problem exists — `updateChangedFiles`/the app-store diff refresh logic explicitly documents that "the diff might have changed dramatically since last we loaded it" and attempts a partial mitigation by recomputing `selectableLines` for the *currently displayed* diff: [4](#0-3) 

However, this mitigation only fixes up the file that is *currently selected/being viewed* in the Changes list at the moment a refresh happens to run; it does nothing to prevent `applyPatchToIndex` from independently re-fetching the diff at commit time and pairing it with a selection object that was never revalidated against that specific re-fetch. There is no guard in `applyPatchToIndex`, `formatPatch`, or `stageFiles` that verifies the diff used to build the patch is the same diff the selection was derived from (e.g., by comparing hunk headers/line text, not just numeric offsets).

### Impact Explanation
Because commit content is derived by git-apply’ing this generated patch straight into the index (`git apply --cached`), a mismatch silently changes what is actually committed and, subsequently, pushed — without any error, warning, or user-visible diff mismatch. This is a "silent corruption of what the user commits" primitive: the user believes they excluded lines X (e.g., secrets, debug statements, unrelated edits) but a stale/attacker-influenced diff timing could result in those lines being included in the commit instead, or vice versa (excluding lines the user intended to include). Since GitHub Desktop repeatedly re-diffs on file-system-watcher events, refreshes, and background operations, and the working tree content of a cloned/fetched repository is attacker-influenced (via hooks, `.gitattributes` normalization, LFS smudge filters, or a colluding co-committer editing the same file), this is reachable without any unusual user action beyond normal partial-staging usage.

### Likelihood Explanation
Likelihood is moderate: it requires a window between diff-render (selection creation) and commit-time diff re-fetch during which the tracked file's on-disk unified-diff shape changes (hunk count/boundaries/line offsets), which can be triggered by normal repository activity (autosave, formatter-on-save, git filters, checkout of another branch touching same file, or another process modifying the file) rather than requiring privileged/local access beyond what a normal Desktop user already has. It does not require the attacker to have prior control of the victim's machine — only of the repository content/filters that shape the diff.

### Recommendation
Do not reuse purely positional line indices across two independently-fetched diffs. Either (a) have `applyPatchToIndex`/`stageFiles` reuse the exact `ITextDiff` object the selection was built from instead of calling `getWorkingDirectoryDiff` again right before staging, or (b) bind selection state to line content (e.g., hash of line text + type) so that `isSelected` lookups can detect and reject/re-validate a diff that has shifted since the selection was captured, surfacing an error to the user rather than silently applying a mismatched patch.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file so it has multiple hunks (e.g., `modified-file.md` as used in `app/test/unit/git/commit-test.ts`).
2. In the Changes view, uncheck an added line inside the second hunk (this builds a `DiffSelection` keyed to `hunk.unifiedDiffStart + lineIndex` from the *currently rendered* diff, as shown by the test at `app/test/unit/git/commit-test.ts:307-338`).
3. Before pressing "Commit," trigger a git operation or filter (e.g., a `.gitattributes`/`core.autocrlf` change, a pre-commit hook editing the file, or another process appending/removing a line) that changes the number/position of hunks or lines in the file without the UI re-deriving `selection`.
4. Click "Commit." `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff, and `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`) reuses the stale `file.selection.isSelected(absoluteIndex)` against the new hunk layout.
5. Inspect the resulting commit content (`git show`): lines the user did not intend to include may be present, or intended lines may be missing, with no error or warning shown to the user.
