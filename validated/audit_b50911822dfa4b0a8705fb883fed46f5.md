### Title
Governance deposit refunds can be permanently frozen for depositors who associate their EVM address after depositing - ([File: sei-cosmos/x/gov/keeper/deposit.go])

### Summary
`RefundDeposits` sends a proposal's deposit back to the recorded `Depositor` address only if that address can currently receive funds. If it cannot, the deposit is silently retained forever, with the code comment explicitly stating recovery "requires a migration." A normal, user-initiated Sei action — explicitly associating an EVM address to a Sei address — can turn a previously-valid depositor address into a permanently unreceivable one, freezing that user's own governance deposit with no transaction-level recovery path, mirroring the Opyn M-3 pattern of user withdrawals being hostage to actions outside the depositor's control at withdrawal time.

### Finding Description
When a user deposits to a governance proposal, the deposit record stores the depositor's `sdk.AccAddress` as-is: [1](#0-0) . On proposal resolution, `RefundDeposits` attempts to pay this address back, but if the bank keeper reports it as blocked or unable to receive, the deposit record and backing module-account balance are simply left in place: [2](#0-1) 

The unreceivability condition is driven by Sei's dual address model. A "cast" address (the direct byte-cast of an EVM address into `sdk.AccAddress` form) can legitimately hold and spend funds until its EVM address is explicitly associated with a *different*, pubkey-derived Sei address. Once that association happens, `CanAddressReceive`/`CanSendTo` permanently blocks the cast address from receiving new funds, because the cast address no longer "belongs" to the newly-associated account: [3](#0-2) 

This transition is triggered by an ordinary `MsgAssociate`/association flow that Sei encourages users to perform to move from implicit cast addresses to explicit associated addresses, executed either directly or via the ante-handler/precompile association path: [4](#0-3)  and [5](#0-4) .

Concretely: a user deposits `usei` into a proposal from their cast address (before ever calling Associate). Later — for entirely legitimate reasons, e.g. wanting to use EVM tooling — they associate that EVM address to their real pubkey-derived Sei address. If the proposal is later rejected/expires and its deposit is refunded, `bankKeeper.CanSendTo(ctx, depositor)` now returns `false` for the cast address, so `RefundDeposits` retains the deposit forever. There is no user-facing message to redirect a stuck deposit's payout address (unlike `x/distribution`'s `SetWithdrawAddr`, which lets delegators pre-register an alternate withdraw address). The code's own comment confirms recovery requires a chain migration, i.e., depends entirely on validator/governance operators, not the user: [6](#0-5) .

The same root-cause pattern (address becomes unreceivable after association) is independently acknowledged and tested for `x/staking` unbonding delegations and `x/distribution` withdraw addresses, which have been hardened with fallback logic to the operator/validator address, but no equivalent fallback exists for `x/gov` deposits: [7](#0-6) [8](#0-7) .

### Impact Explanation
This is a genuine, unprivileged-user-reachable fund-freezing bug: a user's own governance deposit (their `usei`) can become permanently locked in the gov module account, unrecoverable by any transaction the user or any other unprivileged party can send — recovery is explicitly stated to require a chain-level migration, which is outside the user's control (mirroring the "dependent on admin/operator action" theme of the referenced report, but worse because it depends on privileged infrastructure work, not even a callable admin function). This is a fund-freezing bug meeting the "permanent freezing" bar in the validation criteria.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a user to deposit governance funds from an address that is still in "cast" form (i.e., before ever calling Associate) and (2) the same user (or anyone controlling that EVM key) to later associate that EVM address to a different Sei address before the deposit is refunded/returned. Because Sei explicitly promotes explicit association as the normal upgrade path for EVM users, and gov deposit/refund cycles can span the multi-day voting period, this sequence is plausible in ordinary usage, not just a contrived edge case.

### Recommendation
Add a fallback/redirect mechanism for `RefundDeposits` analogous to the one already implemented for `x/staking`/`x/distribution`: when the recorded depositor address is no longer able to receive funds, resolve the refund to the currently-associated Sei address for that EVM identity (if one exists) instead of silently retaining the deposit. Alternatively, expose a permissionless message that lets the holder of the retained deposit re-target the refund to their now-associated address, removing the sole remaining migration-only recovery path.

### Proof of Concept
1. User `U` controls EVM key `E`. Before ever associating, `U` sends a `MsgDeposit` to a governance proposal from the cast address `castAddr(E)` using `AddDeposit` (`sei-cosmos/x/gov/keeper/deposit.go:108`).
2. Before the proposal's voting period ends, `U` submits any Cosmos or EVM transaction that triggers association of `E` to `U`'s true pubkey-derived Sei address `seiAddr`, via the ante-handler flow (`x/evm/ante/preprocess.go:76-101`) or the `addr` precompile's `associate`/`associatePubKey` methods.
3. `SetAddressMapping` records `E -> seiAddr`; `CanAddressReceive(castAddr(E))` now returns `false` because `associatedAddr (seiAddr) != castAddr(E)` (`x/evm/keeper/address.go:81-86`).
4. The proposal is later rejected or removed for insufficient deposit; `EndBlocker` calls `RefundDeposits` (`sei-cosmos/x/gov/abci.go:91` or `:207`).
5. `RefundDeposits` calls `bankKeeper.CanSendTo(ctx, castAddr(E))`, which returns `false`; the deposit entry is retained and the funds stay locked in the gov module account indefinitely, with no further transaction available to `U` to reclaim them (`sei-cosmos/x/gov/keeper/deposit.go:169-192`).

func (keeper Keeper) AddDeposit(ctx sdk.Context, proposalID uint64, depositorAddr sdk.AccAddress, depositAmount sdk.Coins) (bool, error) {
	// Checks to see if proposal exists
	proposal, ok := keeper.GetProposal(ctx, proposalID)
	if !ok {
		return false, sdkerrors.Wrapf(types.ErrUnknownProposal, "%d", proposalID)
	}

	// Check if proposal is still depositable
	if (proposal.Status != types.StatusDepositPeriod) && (proposal.Status != types.StatusVotingPeriod) {
		return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
	}
	if keeper.IncrementalTallyEnabled(ctx) && proposal.Status == types.StatusVotingPeriod {
		if proposal.VotingEndTime.Before(ctx.BlockTime()) || keeper.voteDelegationSnapshotFrozen(ctx, proposal) {
			return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
		}
	}

	// update the governance module's account coins pool
	err := keeper.bankKeeper.SendCoinsFromAccountToModule(ctx, depositorAddr, types.ModuleName, depositAmount)
	if err != nil {
		return false, err
	}

	// Update proposal
	proposal.TotalDeposit = proposal.TotalDeposit.Add(depositAmount...)
	keeper.SetProposal(ctx, proposal)

	// Check if deposit has provided sufficient total funds to transition the proposal into the voting period
	activatedVotingPeriod := false

	if proposal.Status == types.StatusDepositPeriod && proposal.TotalDeposit.IsAllGTE(keeper.GetDepositParams(ctx).GetMinimumDeposit(proposal.IsExpedited)) {
		keeper.ActivateVotingPeriod(ctx, proposal)

		activatedVotingPeriod = true
	}

	// Add or update deposit object
	deposit, found := keeper.GetDeposit(ctx, proposalID, depositorAddr)

	if found {
		deposit.Amount = deposit.Amount.Add(depositAmount...)
	} else {
		deposit = types.NewDeposit(proposalID, depositorAddr, depositAmount)
	}

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
}

// A sdk.AccAddress may not receive funds from bank if it's the result of direct-casting
// from an EVM address AND the originating EVM address has already been associated with
// a true (i.e. derived from the same pubkey) sdk.AccAddress.
func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (k Keeper) canReceiveWithdrawAddr(ctx sdk.Context, withdrawAddr sdk.AccAddress) bool {
	// BlockedAddr mirrors the gate SendCoinsFromModuleToAccount actually enforces:
	// beyond the module-account blocklist it also rejects dynamically-derived
	// addresses such as the EVM coinbase addresses (an "evm_coinbase"-prefixed
	// address), which CanSendTo does not catch. Consulting it here keeps this
	// predicate in lockstep with the send, so AfterValidatorRemoved never concludes
	// an address is receivable and then panics on the resulting bank error.
	return !k.blockedAddrs[withdrawAddr.String()] &&
		!k.bankKeeper.BlockedAddr(withdrawAddr) &&
		k.bankKeeper.CanSendTo(ctx, withdrawAddr)
}
