### Title
OP_RETURN data is omitted from fee-rate accounting, causing signed transactions to underpay fees - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` adds a zero-value `OP_RETURN` output to the actual transaction outputs, but calculates the transaction weight and required fee from only `payments` and optional `change`. As a result, the returned `needed_fee` does not account for up to 80 bytes of caller-controlled `data`, and the produced transaction can have a materially lower effective fee rate than the requested `fee_per_vbyte`.

This is analogous to the reported accounting bug: a value/output that is actually included in the final operation is omitted from one side of the accounting, causing the recorded/expected fee to diverge from the transaction actually signed.

### Finding Description
The constructor first copies all payment outputs into `tx_outs` and then appends an `OP_RETURN` output when `data` is supplied:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data)
        .expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}
```

However, both fee calculations pass `payments` rather than the complete `tx_outs` list:

```rust
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, None);

let mut needed_fee = fee_per_vbyte * vbytes;
```

and, when change is enabled:

```rust
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
let fee_with_change = fee_per_vbyte * vbytes_with_change;
```

`calculate_weight_vbytes` reconstructs a transaction containing only the supplied payment outputs and optional change output. It has no `data` parameter, so the `OP_RETURN` output appended to the real transaction is never included in either weight calculation.

The signed transaction is nevertheless constructed from `tx_outs`, including the `OP_RETURN`:

```rust
Ok(SignableTransaction {
  tx: Transaction {
    version: Version(2),
    lock_time: LockTime::ZERO,
    input: tx_ins,
    output: tx_outs,
  },
  ...
  needed_fee,
})
```

Therefore:

```text
actual_vsize = vsize(inputs + payments + OP_RETURN + optional change)
expected_vsize = vsize(inputs + payments + optional change)
needed_fee = fee_per_vbyte * expected_vsize
actual_fee = input_sum - output_sum = needed_fee
effective_fee_rate = needed_fee / actual_vsize < fee_per_vbyte
```

The minimum-relay-fee check has the same issue: it checks `needed_fee` against the underestimated `vbytes`, not against the final transaction size.

### Impact Explanation
A caller can cause the wallet to build and sign a transaction that does not satisfy the fee rate requested at construction. With a large `OP_RETURN` payload, the actual fee rate can fall below the intended network fee rate and potentially below Bitcoin's default minimum relay fee even though the constructor's `TooLowFee` check passes.

In the surrounding wallet usage, this can produce a transaction that cannot be relayed or remains unconfirmed. Any external outputs expected from that transaction are not actually created/spendable until a replacement transaction is produced, and the committed signing round has already consumed a threshold-signature attempt for an incorrectly parameterized transaction.

Because `fee()` is computed as `sum(inputs) - sum(outputs)`, it will report the same undercharged `needed_fee` when a change output absorbs the remainder as designed. The discrepancy is between the requested fee rate and the final serialized transaction size.

### Likelihood Explanation
The bug is directly reachable through the public `SignableTransaction::new` API by supplying `data: Some(...)`. The constructor explicitly permits up to 80 bytes of data, which is sufficient to add a meaningful number of bytes/vbytes while being excluded from the fee estimate.

No malicious validator, compromised peer, invalid curve input, leaked key, or collusion is required. The triggering input is ordinary caller-supplied transaction data.

The processor path shown in `processor/src/networks/bitcoin.rs` currently passes `None` for the data field, so this issue primarily affects direct users of the in-scope Bitcoin wallet API or future processor functionality that forwards transaction data.

### Recommendation
Calculate the fee over the exact output set that will be serialized.

Concretely:

1. Build the payment outputs and `OP_RETURN` output first.
2. Pass the complete output list, or an explicit `data: Option<&ScriptBuf>`/`data_len` parameter, into `calculate_weight_vbytes`.
3. Perform both the no-change and with-change calculations against the complete output set.
4. Check `TooLowFee` using the final transaction's vsize, not the pre-`OP_RETURN` estimate.
5. Add a regression test asserting:

```rust
assert_eq!(tx.needed_fee(), fee_per_vbyte * u64::try_from(final_tx.vsize()).unwrap());
```

for `data: Some(...)`, both with and without change.

### Proof of Concept
The following conceptual test demonstrates the accounting error without requiring an external signature:

```rust
let data = vec![0xaa; 80];
assert!(data.len() <= 80); // accepted by SignableTransaction::new

let with_data = SignableTransaction::new(
  vec![input.clone()],
  &payments,
  Some(change_script.clone()),
  Some(data),
  fee_per_vbyte,
)
.unwrap();

let without_data = SignableTransaction::new(
  vec![input],
  &payments,
  Some(change_script),
  None,
  fee_per_vbyte,
)
.unwrap();

// Both calls calculate vbytes from only `payments` and `change`.
// Therefore both produce the same `needed_fee`.
assert_eq!(with_data.needed_fee(), without_data.needed_fee());

// But the transaction constructed by `with_data` contains an extra
// OP_RETURN output and therefore has a larger actual vsize.
assert!(
  with_data.transaction().vsize() >
    without_data.transaction().vsize()
);

// The fee paid no longer satisfies the requested fee rate.
assert!(
  with_data.needed_fee() <
    fee_per_vbyte * u64::try_from(with_data.transaction().vsize()).unwrap()
);
```

For sufficiently low-but-accepted `fee_per_vbyte` values, the missing `OP_RETURN` weight can also make the effective fee fall below `DEFAULT_MIN_RELAY_TX_FEE` after serialization, despite the constructor's minimum-fee check succeeding.
