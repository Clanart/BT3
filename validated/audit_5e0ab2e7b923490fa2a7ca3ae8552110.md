### Title
Webhook shop-domain header is not bound to the HMAC signature, enabling cross-shop forged webhook injection - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb](lib/shopify_app/controller_concerns/webhook_verification.rb))

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates only the raw request body against a shared, app-wide secret, while `shop_domain` — the value apps are told to trust for attributing the webhook to a specific merchant — is read directly from the `X-Shopify-Shop-Domain` header, which is not covered by the HMAC at all. This mirrors the `RubiconRouter.withdrawForETH` root cause: a critical value (`withdrawnWETH`/`shop_domain`) is trusted from an unverified source instead of being cryptographically bound to the data that was actually authenticated.

### Finding Description
`hmac_valid?` computes/compares the digest over `request.raw_post` only, using the app's shared secret(s): [1](#0-0) 

`verify_request` gates the action solely on that body HMAC: [2](#0-1) 

`shop_domain`, however, is read straight from the `X-Shopify-Shop-Domain` header, which is never part of the signed payload: [3](#0-2) 

The docs explicitly instruct developers building custom webhook controllers to trust this header value directly for dispatching shop-scoped background work: [4](#0-3) 

Because the app's webhook secret is shared across every shop that installs the app (it is the app's client secret, not a per-shop secret), and the HMAC binds only to the body — not to the shop or topic headers — any actor who can obtain one *valid* `(raw_post, HMAC)` pair for the app (e.g., by installing the app on their own store and triggering a webhook event they control, such as updating their own product/order data) can replay that exact body+HMAC to the app's public webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to name an arbitrary victim shop. `verify_request` will still pass because it only checks the body's HMAC, and the downstream job/controller will process the (attacker-supplied) webhook payload as if it belongs to the victim shop, since `shop_domain` is taken verbatim from the unauthenticated header.

### Impact Explanation
This allows an unprivileged, self-service attacker (merely someone who installs the app on their own store — no special access needed) to inject forged webhook data attributed to any other shop using the app. Depending on how the app's webhook job consumes `shop_domain` (as documented, it's passed straight into background jobs for shop-scoped processing), this can lead to cross-shop data corruption, spoofed events triggering shop-scoped business logic (e.g., fake `orders/create`, `app/uninstalled`, or GDPR data-request/erasure events) for a shop the attacker does not own or control. This is a confused-deputy / cross-tenant integrity issue analogous to the referenced report's "trusting an unverified value to authorize a critical action."

### Likelihood Explanation
Likelihood is non-trivial but requires a prerequisite similar to the referenced medium-severity finding: the attacker needs at least one legitimate app installation (on their own or a compliant shop) to obtain a valid `(body, HMAC)` pair, and the target app must consume `shop_domain` from `ShopifyApp::WebhookVerification` (or the equivalently structured generator template) for shop-scoped side effects without cross-checking it against any authenticated shop identity (e.g., session/shop record lookup). Apps that follow the documented custom-controller pattern verbatim are directly exposed.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or `X-Shopify-Topic`) as authoritative unless it is cryptographically bound to the verified payload. Concretely:
- Include the shop domain and topic headers as part of the data digested in `hmac_valid?`, or
- Cross-verify the header-derived `shop_domain` against an installed/known shop record before using it to key any state-mutating or job-dispatching logic, and
- Update `docs/shopify_app/webhooks.md`'s custom-controller example to stop passing the raw `shop_domain` header value into jobs without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker.myshopify.com`) and configures a webhook subscription to point at a proxy/log they control, or otherwise captures a legitimate webhook `POST` (raw body + `X-Shopify-Hmac-Sha256` header) fired by Shopify for their own shop.
2. Attacker crafts a new HTTP request to the app's public webhook endpoint (e.g. `/webhooks/receive` from `app/controllers/shopify_app/webhooks_controller.rb`) using the exact captured `raw_post` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `verify_request` in `WebhookVerification` computes the HMAC over `raw_post` only, using the app's shared secret; since the body is unchanged, the check passes.
4. Any code (per the documented pattern) that does `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)` now processes attacker-controlled webhook content under `victim-shop.myshopify.com`'s identity, even though the victim shop never sent this webhook.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
