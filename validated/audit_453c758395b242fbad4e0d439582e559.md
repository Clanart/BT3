## Analysis

The Halborn finding's broken invariant is: **a value used to compute a state-changing operation is captured *before* an operation that can be influenced by attacker/external input, but the operation actually consumes *live, possibly-changed* data at execution time, with no check that the two are still consistent.** In the BPLP case, the divisor `Vaults[vid].amtETH` is read early and only updated after `_mint` (which can re-enter), so nested calls see a stale/inconsistent denominator and mint disproportionate shares.

Searching GitHub Desktop's local-changes → commit path for the same "decision made against snapshot A, but applied against live snapshot B" pattern surfaces a structurally identical bug in the partial-commit staging code.

### The analogous invariant break

When a user stages only *some lines* of a modified file, Desktop stores that choice as a set of **absolute line indices** (`DiffSelection`) computed against the diff that was rendered in the UI at that moment. When the commit is actually created, Desktop does **not** reuse that diff. Instead:

- `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches a brand-new diff from disk via `getWorkingDirectoryDiff(repository, file)` right before staging. [1](#0-0) 
- That freshly-fetched diff is then combined with the **old** `file.selection` object using `formatPatch(file, diff)`, which walks the new hunks and asks `file.selection.isSelected(absoluteIndex)` — i.e., it reinterprets old line-index selections against a diff that may have entirely different hunk boundaries/content. [2](#0-1) 

There is **no re-validation** that the diff used to build the selection is the same diff being staged — unlike the UI rendering path, which explicitly re-derives `selectableLines` from a fresh diff before reusing a selection (`app-store.ts:3478-3497`, with the comment "The diff might have changed dramatically since last we loaded it"). That safeguard exists only for what's *displayed*, not for what's actually *staged and committed*. [3](#0-2) 

`_commitIncludedChanges` (`app-store.ts:3681-3699`) captures `selectedFiles` from cached state, then runs `formatCommitMessage` and `createCommit` → `stageFiles` → `applyPatchToIndex` — an async chain during which the working tree can be modified by any concurrently running process the repository itself launches (build watchers, Git LFS smudge/clean filters keyed off attacker-controlled `.gitattributes`, lint-staged/husky-style tooling shipped in the project, etc.). ### Title
Stale line-index reuse in partial-commit staging lets a repository-triggered file change silently corrupt what the user commits - (File: app/src/lib/git/apply.ts, app/src/lib/patch-formatter.ts)

### Summary
`applyPatchToIndex` re-derives a fresh diff from disk at staging time but applies the user's *previously computed* line-index selection (`DiffSelection`) to that new diff without verifying the two still correspond. If the working-tree file changes between when the user picked which lines to include and when Desktop stages the commit, `formatPatch` will silently select/deselect the wrong lines — mirroring the report's core flaw of consuming a value computed at one point in time against state that has since diverged.

### Finding Description
`DiffSelection` tracks inclusion by absolute line index relative to a specific diff snapshot rendered in the Changes view. That selection object is stored on `WorkingDirectoryFileChange` and carried into the commit pipeline (`_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex`). Crucially, `applyPatchToIndex` does not reuse the diff the user actually looked at; it calls `getWorkingDirectoryDiff` again, right before staging, and blindly re-applies the old index-based selection to the new hunk structure via `formatPatch`. Line indices from an old diff have no guaranteed correspondence to lines in a new diff once hunk boundaries shift (insertions/deletions elsewhere in the file, whitespace changes, etc.), so `isSelected(absoluteIndex)` can now point at a completely different logical line than the one the user checked or unchecked.

Desktop's own code acknowledges this exact class of staleness in the UI-refresh path (`updateChangesWorkingDirectoryDiff`), where a fresh diff explicitly triggers recomputation of `selectableLines` before the old selection is reused for *display*. No equivalent reconciliation exists on the *staging* path, meaning the guard exists everywhere except where it actually determines the bytes that end up in the commit and get pushed.

### Impact Explanation
If a tracked file is modified by any process (a watcher, a Git filter driven by attacker-supplied `.gitattributes`, tooling bundled with the repository) in the window between the user reviewing/selecting lines in the Changes view and clicking Commit, Desktop can stage and commit content the user never selected (or omit content they explicitly selected), without any error or warning. This is a silent corruption of what the user commits and subsequently pushes — potentially re-including content a user deliberately excluded (e.g., partially reverted secrets or debug code) or dropping intended changes, which then propagates to the remote/shared history.

### Likelihood Explanation
This requires a concurrent, repository-influenced process to modify a tracked file during the (typically short but non-zero) window between diff render and staging — e.g., project-bundled build/watch tooling, editor autosave triggered by repo-provided config, or Git filter drivers keyed off attacker-controlled `.gitattributes` when a compatible filter (such as Git LFS) is already configured. It does not require local/admin access, leaked credentials, or unnatural user steps beyond normal day-to-day use of a cloned repository with its own build tooling running. Likelihood is moderate rather than trivial because it depends on timing and on some external writer being active during the commit action; there is no attacker-controlled trigger fully internal to Desktop's own execution that guarantees the race window (this uncertainty should be verified against Desktop's actual timing behavior in a live session).

### Recommendation
Before calling `formatPatch`/`applyPatchToIndex`, re-validate that the `DiffSelection` still corresponds to the diff about to be staged (e.g., by hashing/fingerprinting the diff used to build the selection and comparing it to the diff fetched at staging time, similar to the reconciliation already done in `updateChangesWorkingDirectoryDiff`). If they differ, refuse to stage and force the user to re-review the file's diff before it can be committed, rather than silently applying indices from a stale diff.

### Proof of Concept
1. Open a modified tracked file with multiple hunks in Desktop's Changes view and partially select specific lines to include in the commit (leaving others unstaged).
2. Before clicking "Commit," have another process associated with the repository (e.g., a bundled build/watch script, or a Git clean/smudge filter triggered by repo-provided `.gitattributes`) rewrite the file so that hunk boundaries shift (insert/delete lines above the selected hunk).
3. Click "Commit." `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (now shifted) and applies the *old* absolute-index selection via `formatPatch`.
4. Inspect the resulting commit: it contains different lines than what the user visually selected in step 1, demonstrating silent corruption of the committed content — with no error surfaced to the user.

Because reproducing the exact timing/trigger in Desktop's live async scheduler could not be directly executed in this analysis (no runtime/terminal access), the race-window feasibility should be validated with an actual Desktop build; the code-level absence of any staleness check in `apply.ts`/`patch-formatter.ts`, contrasted with the explicit staleness-handling present in `app-store.ts`'s UI-diff-refresh path, is confirmed directly from source.
