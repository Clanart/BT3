### Title
Cross-chain `RedeemEscrow`/`RefundEscrow` withdrawal trusts caller-supplied `Order.inputs` without proving the tokens were ever escrowed on the source chain, enabling fabricated fills to drain pooled escrow — (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2`'s cross-chain fill path lets a solver call `fillOrder()` with any self-constructed `Order` struct, since the destination chain never proves that the order was actually escrowed on the source chain — it only checks that the *destination*-side `_filled[commitment]` slot is empty. The resulting `RedeemEscrow` message that gets dispatched back to the source chain is authenticated purely on module identity (`_authenticate`), and the source-side `_withdraw`/`withdraw()` function then transfers whatever `token`/`amount` pairs are embedded in that message directly out of the gateway's pooled balance, without checking them against the `_orders[commitment][token]` escrow bookkeeping recorded by `placeOrder()`. This is the same broken invariant as the reported issue: an attacker-controlled parameter (there, `vault`; here, the fabricated `Order.inputs`/`commitment`) is accepted and used to compute/transfer value without validating that it corresponds to a real, previously-registered state (there, a registered vault; here, a real escrowed order).

### Finding Description
`fillOrder()` computes `commitment = keccak256(abi.encode(order))` from the calldata `order` the caller passes in, and only guards against replay by checking `_filled[commitment]` on the *current* (destination) chain: [1](#0-0) 

Nothing here proves that a matching order was ever placed and escrowed via `placeOrder()` on `order.source`. For cross-chain fills, `_fillCrossChain` then dispatches a `RedeemEscrow` PostRequest to `order.source` using the attacker-supplied `order.inputs` as the `tokens` field, and `msg.sender` as beneficiary: [2](#0-1) 

On the source chain, `onAccept` authenticates the request only by checking that the sending module address equals the registered gateway instance for that state machine — not that the escrow actually exists: [3](#0-2) [4](#0-3) 

This authentication passes trivially because `IntentGatewayV2` is deployed at the same deterministic address on every chain (per the contract's own documentation), so `_instance(order.source)` on the victim chain legitimately equals the real destination-chain gateway address that dispatched the message — regardless of whether the `order` it encoded was ever real. The withdrawal handler then marks the commitment filled and pays out the attacker-chosen `token`/`amount` pairs directly from the gateway's balance, as shown in the sibling implementation: [5](#0-4) 

No step cross-references `_orders[commitment][token]` (the mapping populated in `placeOrder()` at [6](#0-5) ) to confirm that `commitment` corresponds to actual escrowed value before crediting the beneficiary — exactly the class of bug in the external report, where `getOperatorVotingPower()` computed a value from a caller-supplied address without validating that address referred to a genuinely registered entity.

### Impact Explanation
An unprivileged attacker can fabricate an `Order` (arbitrary `source` chain, arbitrary `inputs` tokens/amounts, trivial `output` requirements payable to themselves) and call `fillOrder()` on any chain. The resulting cross-chain message is legitimately authenticated (it really was dispatched by the canonical gateway contract) and instructs the victim-chain gateway to pay out arbitrary tokens/amounts from its pooled escrow to the attacker — a direct theft of all users' escrowed funds on that gateway. This satisfies the bounty's "stealing or loss of funds" / "unauthorized transaction or execution" / "transaction manipulation" criteria and requires no malicious relayer, prover, or admin — only a standard relayer faithfully relaying the (fraudulent-content but validly-signed/proven) message.

### Likelihood Explanation
The attack only requires calling two public, permissionless entry points (`fillOrder()` on one chain, and the resulting ISMP message being relayed to the source chain — a service any permissionless relayer performs by design) with attacker-chosen calldata. No governance, compromised key, or race condition is needed, and the deterministic cross-chain deployment address is a documented design property that removes what would otherwise be a natural per-chain identity check.

### Recommendation
Before crediting/withdrawing on `RedeemEscrow`/`RefundEscrow`, the source-chain gateway must verify that `_orders[commitment][token] == amount` (and that it hasn't already been consumed) for every `body.tokens[i]`, decrementing/zeroing the escrow entry as it pays out — rather than trusting the `tokens`/`amount` list embedded in the incoming message. This restores the missing binding between the cross-chain withdrawal instruction and the actual escrowed state, analogous to adding the missing vault-registration check recommended in the source report.

### Proof of Concept
1. Attacker deploys/uses the canonical `IntentGatewayV2` on Chain B (destination) — same address as the real gateway on Chain A (victim), per deterministic CREATE2 deployment.
2. Attacker calls `fillOrder(order, options)` on Chain B with:
   - `order.source = ChainA`, `order.destination = ChainB`
   - `order.inputs = [{token: USDC_on_ChainA, amount: 1_000_000e6}]` (never actually escrowed on Chain A)
   - `order.output.assets = [{token: 0, amount: 0}]`, `beneficiary = attacker`
   - `order.deadline` valid, `nonce`/`user` set to satisfy struct requirements
3. `fillOrder` computes a fresh `commitment`; `_filled[commitment]` on Chain B is empty, so it proceeds, trivially satisfies the (near-zero) output requirement, and calls `_fillCrossChain`, dispatching a `RedeemEscrow` PostRequest to Chain A's gateway instance with `tokens = order.inputs`, `beneficiary = attacker`.
4. A relayer delivers this (validly formed, correctly-authenticated) message to Chain A. `onAccept` → `_authenticate` passes (sender module = the real, canonical gateway address). `_withdraw`/`withdraw()` transfers `1_000_000e6` USDC from the Chain A gateway's pooled escrow to the attacker, without ever having verified `_orders[commitment][USDC]` was populated by a genuine `placeOrder` call.

        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();
        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RedeemEscrow)),
            abi.encode(
                WithdrawalRequest({
                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
                })
            )
        );
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        if (options.nativeDispatchFee > 0 && msgValue >= options.nativeDispatchFee) {
            IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request);
            msgValue -= options.nativeDispatchFee;
        } else {
            dispatchWithFeeToken(request);
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
