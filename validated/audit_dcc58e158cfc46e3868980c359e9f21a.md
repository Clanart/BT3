### Title
Out-of-range participant index in PedPoP blame evaluation panics, crashing the evaluator - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
The gnutls advisory is a remote, unauthenticated Denial of Service: a malformed handshake field reaches a NULL dereference and crashes the server. The Serai analog is a reachable panic in the PedPoP DKG blame path. `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `HashMap`s keyed by `Participant` using indices taken verbatim from an accusation — `self.enc_keys[&decryptor]` and `self.commitments[&sender]`. Any participant index greater than `n` (or not registered) causes an unconditional panic, crashing whatever process evaluates the blame — including `AdditionalBlameMachine`, which is explicitly designed to be usable by a party "regardless of if the caller was a member in the DKG protocol". ### Finding Description
`BlameMachine::blame` and `AdditionalBlameMachine::blame` take `sender: Participant` and `recipient: Participant` plus an `EncryptedMessage` and an optional `EncryptionKeyProof`, all sourced from an accusation. Inside `blame_internal`, `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` evaluates `&[self.enc_keys[&decryptor], *proof.key]` whenever `proof` is `Some` — `decryptor` is the attacker-named `recipient`, and `HashMap`'s `Index` impl panics on a missing key [4](#0-3) . Independently, after a message whose PoP verifies and whose ciphertext decrypts to a canonical scalar, `blame_internal` evaluates `&self.commitments[&sender]`, panicking if `sender` isn't a key in the commitments map [5](#0-4) . `Participant::new` only rejects `0`; any `u16` in `1..=u16::MAX` is a valid `Participant`, so indices `n+1 ..= u16::MAX` flow straight into the map lookups [6](#0-5) . No bound check against `n` exists on either path — `AdditionalBlameMachine::new` records `n` but `blame` never compares `sender`/`recipient` to it [7](#0-6) .

### Impact Explanation
Like the gnutls NULL dereference, this is an availability-only bug triggered by a crafted input: a single malformed blame accusation deterministically panics the evaluating party. If blame evaluation runs in-process on a validator, coordinator, or arbiter node, the panic kills that process mid-protocol. The `msg`/`proof` are self-authenticating artifacts (the accuser can generate a valid per-message PoP and DLEq for any claimed `sender`, since `pop_challenge` binds `from` which is attacker-controlled), so the panic is reachable before any signature check would reject the accusation [8](#0-7) .

### Likelihood Explanation
Reachability depends on the integrator passing accusation-supplied `sender`/`recipient` values into `blame` without first range-checking them against the DKG's `n`. The library documents `AdditionalBlameMachine` for evaluating blame of third parties and does not document the panic condition; `blame` returns a bare `Participant`, not a `Result`, so a caller has no error path to handle. The PoP/DLEq requirements are satisfiable by the accuser itself (they possess the encryption key and prove it against their own claimed sender index), so no cooperation from any real participant is needed to reach the panicking indexing expression. Caveat: the fully-trusted path (`BlameMachine::blame` inside a validator's own DKG) may sit behind upstream checks I could not confirm; the `AdditionalBlameMachine` API is the cleanest reachable surface. Medium confidence on reachability, high confidence on the panic itself.

### Recommendation
Validate `sender` and `recipient` against the registered set before indexing: replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get()` and return a defined error/verdict (e.g., blame the accuser or reject the accusation) when the index is `> n` or unregistered. `AdditionalBlameMachine::blame` should take the stored `n` and reject out-of-range participants up front.

### Proof of Concept
```
// After constructing a blame evaluator over n participants:
let mut machine = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs).unwrap();

// Attacker crafts an EncryptedMessage with a valid PoP bound to `from = sender`,
// and an EncryptionKeyProof whose DLEq is valid for (G, msg.key) -> (decryptor_enc_key, proof.key).
// They then submit the accusation naming out-of-range participants:
let oob = Participant::new(n + 1).unwrap();
machine.blame(sender, oob, msg, Some(proof));
//  -> decrypt_with_proof evaluates self.enc_keys[&oob] -> HashMap index panic
```
The `self.enc_keys[&decryptor]` panic needs only `proof: Some(_)` plus an out-of-range `recipient`; the `self.commitments[&sender]` panic needs an out-of-range `sender` with a message whose PoP verifies and whose plaintext is a canonical scalar — both craftable by the accuser alone.

  /// Create an AdditionalBlameMachine capable of evaluating Blame regardless of if the caller was
  /// a member in the DKG protocol.
  ///
  /// Takes in the parameters for the DKG protocol and all of the participant's commitment
  /// messages.
  ///
  /// This constructor assumes the full validity of the commitment messages. They must be fully
  /// authenticated as having come from the supposed party and verified as valid. Usage of invalid
  /// commitments is considered undefined behavior, and may cause everything from inaccurate blame
  /// to panics.
  pub fn new(
    context: [u8; 32],
    n: u16,
    mut commitment_msgs: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>,
  ) -> Result<Self, PedPoPError<C>> {
    let mut commitments = HashMap::new();
    let mut encryption = Decryption::new(context);
    for i in 1 ..= n {
      let i = Participant::new(i).unwrap();
      let Some(msg) = commitment_msgs.remove(&i) else { Err(PedPoPError::MissingParticipant(i))? };
      commitments.insert(i, encryption.register(i, msg).commitments);
    }
    Ok(AdditionalBlameMachine(BlameMachine { commitments, encryption, result: None }))
  }

  /// accusing recipient. This message must have been authenticated as actually having come from
