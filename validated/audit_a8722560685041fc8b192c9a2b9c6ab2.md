### Title
Validator staking amount used for reward distribution and eligibility is derived from a CnStaking contract's raw native balance, allowing unlocked balance inflation to redirect minting rewards - (File: `kaiax/staking/impl/getter.go`)

### Summary
The `SynthVault` bug credited an attacker with mint-and-deposit weight because the vault's mint logic read the *total token balance* of the pool (which the attacker could inflate with a plain, unrelated transfer) instead of only the newly-granted reward, bypassing the deposit lock-up. The analogous pattern exists in Kaia's staking/reward pipeline: a validator's `StakingAmount`, which directly drives KIP-82/Flex minting-reward distribution and `minStake` reward-eligibility, is populated from the AddressBook/MultiCall staking-info call and — as demonstrated by the module's own test fixtures — tracks the plain native-KAIA *balance* of the registered `CnStaking` contract address rather than an amount that only increases through the contract's permissioned, lock-up-governed staking flow (`STAKE_LOCKUP`, withdrawal-approval queue, etc.). Anyone can send an ordinary value-transfer transaction to a publicly-known `CnStaking` address to inflate the amount that is later read as "stake," exactly mirroring the SynthVault pattern of pre-funding a balance that a later accounting step consumes as if it were legitimately committed.

### Finding Description
`kaiax/staking/impl/getter.go`'s `parseCallResult`/`parsePermissionlessCallResult` build `StakingInfo.StakingAmounts` straight from the values returned by the on-chain MultiCall/AddressBook query: [1](#0-0) [2](#0-1) 

The module's own unit test proves that this amount equals the plain native balance placed at the staking-contract address in genesis, with no staking/lockup transaction involved: [3](#0-2) 

This `StakingInfo.StakingAmounts` value then feeds directly into consensus-critical minting-reward distribution, which allocates KIP-82/Flex staking rewards proportionally to each validator's staking amount above `minStake`/`StakingRewardThreshold`, and skips validators below `minStake` entirely: [4](#0-3) [5](#0-4) 

By contrast, the real `CnStaking` contracts implement an explicit staking lock-up and a delayed, approval-gated withdrawal process: [6](#0-5) [7](#0-6) 

Because reward calculation reads the contract's *aggregate native balance* rather than a ledger of properly-staked/locked amounts, sending KAIA to that address via a normal, unprivileged value transfer (not through the contract's staking method, and thus without incurring `STAKE_LOCKUP`) still counts as "staked" for reward-distribution and eligibility purposes at the next block's snapshot. This is the direct analog of `SynthVault.harvestSingle` minting synths based on the pool's whole `BASE` balance (including an attacker's unrelated prior transfer) instead of only the intended reward amount — in both cases, an accounting routine treats "current balance" as a proxy for "legitimately committed value," letting a plain transfer masquerade as a lock-up-protected deposit/stake.

### Impact Explanation
This allows reward redirection without genuine, lock-up-protected staking:
- A validator operator (who needs no special governance/multisig privilege to send a plain transfer) can top up their own `CnStaking` contract's balance right before the staking snapshot block to cross `minStake`/`StakingRewardThreshold` and capture a disproportionate share of the per-block minting reward (`assignStakingRewards`/`assignStakingRewardsFlex`), or to become reward-eligible when they otherwise would not be.
- Because `StakingInfo` is a consensus-critical structure computed identically by every full node from state (see `kaiax/staking/README.md`), this changes actual on-chain reward allocation and Gini-based governance weighting, not merely an off-chain view — i.e., a concrete reward-redirection/supply-misallocation vulnerability, not a cosmetic bug.
- It also undermines the security assumption that reward-share and validator eligibility require genuinely locked, slashable-by-design capital (`STAKE_LOCKUP`), since the balance can be added and later withdrawn/spent by the operator through means outside the "official" stake/withdraw flow if the `CnStaking` implementation ever forwards or allows recovery of un-tracked balance (e.g., via `receive()`/fallback-driven internal top-ups, admin sweep, or accidental compatibility with plain transfers).

### Likelihood Explanation
Reachable by a single, ordinary transaction: a plain native-KAIA transfer to any publicly listed `CnStaking` address (addresses are public in the AddressBook) requires no special permission, matching the "unprivileged transaction sender" scope. The staking-info snapshot is taken every block after the Kaia hardfork (`SourceNum(num) = num - 1`), so the inflated balance is picked up almost immediately: [8](#0-7) 

Uncertainty: the actual production Solidity source of the `MultiCallContract`/`CnStaking` "staking amount" computation is not present in this index (only mock contracts and Go bindings are available); the conclusion that `StakingAmounts` reflects raw contract balance is inferred from the `TestGetStakingInfo_Uncached` fixture where genesis `Balance` on the staking address exactly equals the resulting `StakingAmounts`. This is strong but indirect evidence — confirming against the real `CnStakingV4`/AddressBook logic (not included in this repo's index) is recommended before treating this as fully proven.

### Recommendation
Do not derive `StakingAmounts` from the raw native balance of the `CnStaking` contract address. Instead, have the AddressBook/MultiCall query return an internally tracked "staked amount" ledger value that only changes through the contract's permissioned staking/withdrawal functions (respecting `STAKE_LOCKUP` and the withdrawal-approval queue), analogous to syncing/crediting only the intended value rather than the whole balance, as recommended for the `SynthVault` fix (sync before any external funds arrive so unrelated transfers cannot be misattributed as reward/stake).

### Proof of Concept
1. Identify a registered `CnStaking` contract address for validator V from the AddressBook (`getAllAddress()` / `kaia_getStakingInfo`).
2. From any unprivileged externally-owned account, send a plain native-KAIA transfer of amount X directly to that `CnStaking` address (no interaction with its staking/deposit method, so `STAKE_LOCKUP` and withdrawal-approval logic are never invoked).
3. At the next staking-info snapshot block (`SourceNum(num) = num - 1` post-Kaia HF, per `kaiax/staking/impl/getter.go` `sourceBlockNum`), the staking module's `getFromState`/`parseCallResult` reads the inflated balance and reports `StakingAmounts[V] += X` (as reproduced by `TestGetStakingInfo_Uncached`, where genesis `Balance` on the staking address is echoed verbatim as `StakingAmounts`).
4. The reward module's `assignStakingRewards`/`assignStakingRewardsFlex` then computes V's proportional minting reward (and/or minStake eligibility) using this inflated `StakingAmount`, redirecting more of the block's minting reward to V's `RewardAddr` than V's genuinely locked stake would justify — with no lock-up period ever having applied to the added X.

// assignStakingRewardsFlex assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewardsFlex(config *reward.RewardConfig, budget *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		minStake  = config.MinimumStake.Uint64()
		threshold = config.StakingRewardThreshold.Uint64()
		isPrague  = config.Rules.IsPrague

		cns            = si.ConsolidatedNodes()
		excessInt      = make(map[common.Address]uint64)
		totalExcessInt = uint64(0)
	)

	// Calculate the excess stakes (the amount over the threshold) for each CN.
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it. Even if (CNStaking + CLStaking) could be more than minStake,
		// the CNStaking alone must be at least minStake to be eligible.
		if cn.StakingAmount < minStake {
			continue
		}

		amount := cn.StakingAmount
		if isPrague && cn.CLStakingInfo != nil {
			amount += cn.CLStakingInfo.CLStakingAmount
		}

		// Excess is the amount over the threshold (not over minStake).
		if amount > threshold {
			excessInt[cn.RewardAddr] = amount - threshold
			totalExcessInt += excessInt[cn.RewardAddr]
		}
	}

	// Distribute the budget to the CNs based on the excess stakes.
	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(budget)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		if excessInt[cn.RewardAddr] <= 0 {
			continue
		}
		excess := new(big.Int).SetUint64(excessInt[cn.RewardAddr])

		// The KAIA unit will cancel out:
		// reward (kei) = excess (KAIA) * budget (kei) / totalExcess (KAIA)
		reward := new(big.Int).Div(new(big.Int).Mul(excess, budget), totalExcess)
		if reward.Sign() <= 0 {
			continue
		}

		// If Prague and CL is configured for this CN, split the reward between CN and CL.
		if isPrague && cn.CLStakingInfo != nil {
			cnAmount, clAmount := cn.Split(reward)
			alloc[cn.RewardAddr] = cnAmount
			alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
		} else {
			alloc[cn.RewardAddr] = reward
		}
		remaining.Sub(remaining, reward)
	}
	return alloc, remaining
}

// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
}

- When processing a block at `num`, the StakingInfo from a historic block state is used and the historic block (i.e. source block) is determined by the following:

  - If `num` is before Kaia hardfork, then StakingInfo is drawn from the beginning of the previous staking interval. Note that if the `num` is a multiple of StakingInterval, the staking info is drawn from two epochs ahead (e.g. in the example below, the staking info at block 3000 is drawn from block 1000).
    ```go
    SourceNum(num) = RoundDown(num - 1, StakingInterval) - StakingInterval
    RoundDown(n, p) = n - (n % p)
    ```
  - If `num` is after Kaia hardfork, then StakingInfo is drawn from the previous block.
    ```go
    SourceNum(num) = num - 1
    ```
