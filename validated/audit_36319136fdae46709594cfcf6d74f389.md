### Title
`restrict-assets?`/`as-contract?` allowance wildcard sentinel collides with a legal asset name `"*"`, letting an attacker-authored FT/NFT bypass allowance scoping - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
`check_allowances` merges an explicit `with-ft`/`with-nft` allowance for a specific asset with any allowance registered under the literal asset name `"*"`, treating the latter as a "wildcard for all assets in that contract" sentinel. Because `"*"` is accepted by the `ClarityName` grammar as a real asset name, any contract can define (or a malicious/attacker-deployed contract already does define) a fungible or non-fungible token literally named `*`. A `with-ft`/`with-nft` allowance that a caller writes intending to authorize only that specific `*`-named asset is then interpreted by `check_allowances` as a blanket allowance covering every other fungible/non-fungible asset of the same contract, since the merge logic looks up `AssetIdentifier { contract_identifier, asset_name: "*" }` unconditionally.

### Finding Description
In `special_restrict_assets`/`special_as_contract`, a user writes an allowance list like `(with-ft .malicious-contract "*" u100)` believing it authorizes only the specific token named `"*"` up to 100 units. But `check_allowances` builds `ft_allowances` keyed by `AssetIdentifier`, then for every other real token moved from the same contract (e.g. `stackaroo`), it does:
```
if let Some(wildcard_vec) = ft_allowances.get(&AssetIdentifier {
    contract_identifier: asset.contract_identifier.clone(),
    asset_name: ClarityName::from_literal("*"),
}) {
    merged.extend(wildcard_vec.iter().cloned());
}
``` [4](#0-3) 
This treats the `"*"`-named allowance as covering *any* fungible asset from that contract identifier, not just the literal `*` asset. The same pattern repeats for NFTs. [5](#0-4) 

Since a contract author (including one deployed by the attacker, or an existing contract the victim interacts with inside `restrict-assets?`/`as-contract?`) can legally create a fungible/non-fungible token named `*` (confirmed valid by `CLARITY_NAME_REGEX_STRING`), the attacker can craft a contract call sequence where the victim's `restrict-assets?`/`as-contract?` block moves an amount of the `*`-named token that is within the user's intended per-asset allowance, while simultaneously moving unlimited amounts of *other* tokens from the same contract — all treated as authorized by the same allowance entry.

### Impact Explanation
This breaks the equality that `check_allowances` is supposed to enforce: "assets moved == assets explicitly allowed." An asset (FT or NFT) can move past the post-condition/allowance protections that `restrict-assets?`/`as-contract?` are meant to provide, letting more value leave a protected principal (contract or the calling principal, in `as-contract?`) than the caller authorized. This matches the "an asset moving past its post-conditions" Critical-impact category in scope.

### Likelihood Explanation
Exploitation requires: (1) an attacker who controls or influences a contract with a token/NFT literally named `"*"`, and (2) a caller who invokes `restrict-assets?`/`as-contract?` against that contract with a `with-ft`/`with-nft` allowance naming that same `"*"` asset, expecting it to scope only that asset. Since `"*"` is a valid, unremarkable-looking asset name and this collision is not documented as reserved, a victim contract author or a composed call into an attacker-supplied contract could plausibly trigger it without realizing the sentinel collision. This does not require a miner, signer, or admin — only crafting a contract with a `*`-named asset and getting it invoked inside a `restrict-assets?`/`as-contract?` scope.

### Recommendation
Do not overload a legal asset name as the wildcard sentinel. Represent "wildcard, all assets of contract X" as a distinct internal variant/type (e.g., an `Allowance::FtWildcard(contract_identifier)` enum case) rather than encoding it as `AssetIdentifier { asset_name: "*" }`, so that a real asset literally named `*` can never be conflated with the wildcard semantics.

### Proof of Concept
1. Deploy a SIP-010-like contract `attacker.evil-ft` defining two fungible tokens: `stackaroo` and one literally named `*` (both legal per `CLARITY_NAME_REGEX`).
2. Victim contract executes:
   ```
   (as-contract? ((with-ft 'SP...attacker.evil-ft "*" u10))
     (contract-call? 'SP...attacker.evil-ft transfer-many ...))
   ```
   intending to allow only up to 10 units of the token named `*` to move.
3. Inside the body, `attacker.evil-ft` transfers 10 units of the `*` token (satisfying the literal allowance) and, separately, an arbitrarily large amount of `stackaroo` from the same contract/principal.
4. In `check_allowances`, when processing the `stackaroo` movement, the merge step looks up `AssetIdentifier{contract: evil-ft, asset_name: "*"}` and finds the `u10` allowance registered by the victim, applying it as a limit to `stackaroo` too — even though the victim never wrote an allowance for `stackaroo`. If the amount of `stackaroo` moved is ≤ 10 it passes silently; more importantly, the FT identity is conflated, letting the attacker move any FT under the guise of the `*` allowance's presence rather than being flagged as "no allowance for this asset" (line 615-618), demonstrating the sentinel-collision bypass of the intended per-asset restriction.
