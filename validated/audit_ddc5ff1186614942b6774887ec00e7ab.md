### Title
Liquidation "dust-sweep" check uses `liq-penalty-max` instead of the graduated `liq-penalty`, causing over-seizure of borrower collateral - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
In `liquidate`, the graduated liquidation penalty (`liq-penalty`, bounded between `liq-penalty-min` and `liq-penalty-max` by the LTV curve) is the fee actually applied to size the seized collateral for the primary liquidation. However, the follow-up "is there meaningful collateral left" check that decides whether to sweep 100% of the borrower's remaining balance of that same collateral asset to the liquidator is computed with the fixed `liq-penalty-max` instead of the same graduated `liq-penalty`. This value mismatch — identical in shape to the Peapods report's use of `cleanLiquidationFee` in an optimistic check while `dirtyLiquidationFee` governs the real transfer — biases the dust decision toward sweeping the borrower's full remaining collateral more often than the actual applied penalty would justify.

### Finding Description
The liquidation penalty is computed once, graduated by the position's LTV via `calc-liquidation-params` / `calc-liq-factor-bound`, and is always `<= liq-penalty-max` unless the curve is exactly saturated: [1](#0-0) [2](#0-1) 

This `liq-penalty` is the fee used to derive `coll-actual`/`coll-final-raw`, i.e. the collateral actually seized for the debt repaid: [3](#0-2) 

After that, the code computes how much collateral of the SAME asset remains unseized (`coll-remaining`) and decides whether that remainder is "dust" (round to zero) — but this dust valuation is done with `liq-penalty-max`, not the `liq-penalty` that was actually used moments earlier: [4](#0-3) 

Because `liq-penalty-max >= liq-penalty`, dividing `rem-coll-usd` by `(BPS + liq-penalty-max)` (line 1480) systematically understates how much debt the remaining collateral could still repay compared to what would be computed at the graduated `liq-penalty` that governs the rest of the transaction. This makes `remaining-debt-to-repay` round down to `u0` more often than it should, which triggers the branch that assigns the borrower's ENTIRE remaining balance of that collateral asset to `coll-final` (instead of the smaller, penalty-correct `coll-final-raw`):

```
(coll-final (if (is-eq remaining-debt-to-repay u0) user-coll-balance coll-final-raw))
```

`coll-final` then flows directly into the actual token transfer (`collateral-remove`) and only has to clear the liquidator-supplied `min-collateral-expected` slippage floor — there is no re-check that the swept amount is still consistent with the applied `liq-penalty`: [5](#0-4) 

### Impact Explanation
When the dust branch fires under this mismatched valuation, the liquidator receives the borrower's full remaining balance of the collateral asset rather than the amount proportional to `liq-penalty` (the fee the borrower actually agreed to pay for this liquidation size). This is a direct, uncompensated transfer of the borrower's collateral to the liquidator beyond the protocol's own liquidation-incentive formula — i.e. theft of user funds at rest, landing in the Critical impact category, since it happens purely from an internal fee-value mismatch and is fully within the liquidator's control to trigger (they choose `debt-amount` to leave a "remaining" balance that rounds to dust under `liq-penalty-max` even though it would not round to dust under the true `liq-penalty`).

### Likelihood Explanation
Any liquidator can trigger the affected code path by choosing a `debt-amount` value that leaves a small non-zero leftover of the target collateral (`coll-remaining`). Because `liq-penalty` is graduated (below `liq-penalty-max` for any position that isn't already at `ltv-liq-full`), this size is easy to craft on any partially-liquidatable position, making the mismatch systematically exploitable rather than an edge case.

### Recommendation
Use the same `liq-penalty` value (the one actually applied to size `coll-final-raw`) when computing `rem-debt-usd`/`remaining-debt-to-repay` and `other-debt-repayable`, instead of the fixed `liq-penalty-max`, so the dust-sweep decision is evaluated at the same fee rate that governs the rest of the liquidation.

### Proof of Concept
1. Borrower has 2.3 units of collateral (`user-coll-balance = 2.3e18`) with the position's graduated `liq-penalty` currently at, say, 500 bps, while `liq-penalty-max` is 1000 bps.
2. Liquidator picks `debt-amount` such that `coll-final-raw = 2.2e18`, leaving `coll-remaining = 0.1e18`.
3. `rem-debt-usd` is computed as `rem-coll-usd / (BPS + liq-penalty-max)` i.e. divided by `1.10`, rounding `rem-debt-tokens`/`rem-scaled` down to `0`.
4. `remaining-debt-to-repay` becomes `u0`, so `coll-final` is set to `user-coll-balance = 2.3e18` instead of `coll-final-raw = 2.2e18`.
5. Had the check used the actual `liq-penalty` (500 bps, divisor `1.05`), the same `0.1e18` remainder would very likely still be economically meaningful debt-worth and not round to zero — the correct outcome should keep `coll-final = coll-final-raw = 2.2e18`.
6. The liquidator walks away with `0.1e18` extra collateral units that were never justified by the applied `liq-penalty`, taken directly from the borrower's remaining balance.
