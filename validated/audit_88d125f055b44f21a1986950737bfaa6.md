### Title
`WombatPoolHelperV2.depositFor` hardcodes zero minimum liquidity, exposing depositors to unbounded slippage loss - (File: wombat/WombatPoolHelperV2.sol)

### Summary
`WombatPoolHelperV2.deposit` correctly exposes a `_minimumLiquidity` parameter that lets the caller bound the amount of LP/receipt tokens they must receive for their deposited stablecoins. However, `depositFor`, which performs the same dynamically-priced conversion of `depositToken` into pool liquidity, hardcodes this protection to `0`, giving the depositor no way to guard against price movement between transaction submission and execution.

### Finding Description
`WombatPoolHelperV2.deposit` forwards a user-supplied `_minimumLiquidity` to `_deposit`: [1](#0-0) 

`depositFor`, by contrast, transfers `_amount` of `depositToken` from `msg.sender` and calls `_deposit` with `_minimumLiquidity` hardcoded to `0`: [2](#0-1) 

`_deposit` passes this value straight through to `WombatStaking.deposit`, which forwards it unmodified to the underlying Wombat pool's `deposit` call as `minimumLiquidity`: [3](#0-2) [4](#0-3) 

The amount of LP/receipt tokens minted for a given deposit is dynamically computed from the pool's `cash`/`liability` state at execution time (as shown in the mock pool implementation used for testing): [5](#0-4) 

Because `depositFor` always passes `0` as the minimum, a caller of `depositFor` has no way to bound how few receipt tokens they receive, regardless of how the pool's cash/liability ratio (or a haircut/slippage parameter on the live Wombat pool) shifts between transaction broadcast and execution. This is the exact bug class described in the external report: a user-facing function that dynamically computes an output/input amount from mutable AMM state, but omits the caller-supplied bound (`minRec`/`minimumLiquidity`) needed to make the transaction revert if conditions become unacceptable.

### Impact Explanation
A depositor calling `depositFor` (e.g. to deposit on behalf of themselves or another address) can be sandwiched or simply suffer from natural price movement in the Wombat pool between broadcast and inclusion, receiving fewer receipt tokens (and therefore fewer staked LP shares in MasterMagpie) than expected for the same input amount, with the transaction guaranteed to succeed since the minimum is `0`. This is a direct loss of user funds — the depositor pays full price in `depositToken` but is undercompensated in receipt tokens/LP, and this deficit is not recoverable (the underpriced conversion is finalized on-chain).

### Likelihood Explanation
No privileged role is required. `depositFor` is a public/external, unprivileged-wallet-reachable function, and any transaction targeting Wombat pools with meaningful cash/liability skew or sandwiching activity (routine for AMM pools) can trigger the loss. The likelihood is comparable to any missing-slippage-protection issue on a public AMM-facing function — realistic under normal MEV/sandwich conditions.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (mirroring `deposit`) and forward it to `_deposit` instead of hardcoding `0`:
```solidity
function depositFor(uint256 _amount, uint256 _minimumLiquidity, address _for) external {
    IERC20(depositToken).safeTransferFrom(msg.sender, address(this), _amount);
    IERC20(depositToken).safeApprove(wombatStaking, _amount);
    _deposit(_amount, _minimumLiquidity, _for, address(this));
}
```

### Proof of Concept
1. Wombat pool P has `cash`/`liability` such that depositing `X` `depositToken` currently yields `Y` receipt tokens.
2. Alice calls `depositFor(X, alice)` on `WombatPoolHelperV2`.
3. Before Alice's transaction is mined, another actor's transaction shifts the pool's cash/liability ratio unfavorably (e.g., via a large withdrawal or swap), such that depositing `X` now yields `Y' << Y` liability/receipt tokens.
4. Because `depositFor` always submits `minimumLiquidity = 0` to `WombatStaking.deposit` → `IWombatPool.deposit`, Alice's transaction still succeeds and mints only `Y'` receipt tokens.
5. Alice has permanently received fewer staked shares than expected for her deposit, with no on-chain mechanism to have prevented or reverted the unfavorable execution.
