### Title
Replacement deposit overwrites `withdrawals.move_to_vault_txid`, permanently unbinding an already-paid-out withdrawal from the operator that fronted it - (File: core/src/database/verifier.rs)

### Summary
`update_replacement_deposit_move_txid` in `core/src/database/verifier.rs` blindly rewrites the `move_to_vault_txid` column of an existing `withdrawals` row keyed only by `idx`, without checking whether that row already has a recorded payout (`payout_txid` / `payout_payer_operator_xonly_pk`). Reimbursement lookups are keyed by `move_to_vault_txid` (`get_payout_info_from_move_txid`), so once the column is overwritten, the historical link between the operator's already-fronted payout and its funding vault is severed.

### Finding Description
The custody binding that must hold is: `payout_payer_operator_xonly_pk` (operator who fronted BTC for withdrawal `idx`) is reimbursed from the exact `move_to_vault_txid` vault that was recorded when the payout was verified — i.e. `withdrawals[idx].move_to_vault_txid == vault the operator was checked against at payout time`.

`update_citrea_deposit_and_withdrawals` (`core/src/verifier.rs:2204-2281`) processes, in order: new deposits (`upsert_move_to_vault_txid_from_citrea_deposit`), new withdrawal payouts (`update_withdrawal_utxo_from_citrea_withdrawal`), then replacement deposits (`update_replacement_deposit_move_txid`) — all for the same L2 sync window, with no ordering guarantee tying a replacement to "no payout has occurred yet" for that `idx`. [1](#0-0) 

`update_replacement_deposit_move_txid` performs an unconditional `UPDATE withdrawals SET move_to_vault_txid = $2 WHERE idx = $1`, with no check on the existing `payout_txid`/`payout_payer_operator_xonly_pk` state of the row: [2](#0-1) 

Once an operator has fronted a payout for a given withdrawal `idx`, `update_payout_txs_and_payer_operator_xonly_pk` stamps that row's `payout_txid`, `payout_payer_operator_xonly_pk`, and `payout_tx_blockhash`, keyed only by `idx` — it does not record which `move_to_vault_txid` was in effect at that time: [3](#0-2) 

The verifier/operator side of the reimbursement flow subsequently looks up payout status strictly by `move_to_vault_txid`: [4](#0-3) 

If a `ReplacementDeposit` for the same `idx` lands after a payout has already been fronted and recorded (e.g. a replacement legitimately triggered for an unrelated data-correctness reason, or triggered while a payout is in flight), `update_replacement_deposit_move_txid` rewrites `move_to_vault_txid` to the new deposit's txid. From that point on:
- `get_payout_info_from_move_txid(old_move_txid)` returns `None` (no row matches on the old txid anymore), even though the operator genuinely paid out against the vault identified by `old_move_txid`.
- `get_deposit_data_with_move_tx(old_move_txid)` / kickoff-and-reimbursement machinery that keys off the row's stored `move_to_vault_txid` will now resolve to the new deposit instead of the deposit that was actually verified and paid against.

This is structurally the same class of bug as the SecondSwap report: a piece of state (`stepsClaimed` in SecondSwap, `move_to_vault_txid`/payout linkage here) that should be immutable per-allocation/per-payout is instead overwritten in place by a later, unrelated action, causing the record to misattribute what has already happened.

### Impact Explanation
This breaks the "operator reimbursed for a payout it never funded" / "honest operator permanently unable to be reimbursed" custody binding, which is explicitly listed as a Critical impact. An honest operator that legitimately fronted a withdrawal payout can be locked out of reimbursement (their lookup by the correct `move_to_vault_txid` no longer matches the withdrawal row, since the row was silently repointed to a different vault by an unrelated replacement-deposit event), or, in the other direction, the record could resolve reimbursement processing against the wrong deposit/vault entirely.

### Likelihood Explanation
This requires no privileged role from the attacker's perspective to *trigger the harmful ordering* — a replacement deposit is a legitimate/expected event type (initiated by the security council for a *different* deposit-correctness issue), and nothing in `update_replacement_deposit_move_txid` or its caller enforces that the withdrawal referenced by `idx` has not already had a payout recorded. Whether this is reachable in practice depends on operational timing (a replacement happening for an idx that already has a payout), which I could not fully verify against Citrea-contract-side guards (`replaceDeposit`) since the Citrea contract itself is out of scope of this repo. I am not fully certain the Citrea L2 contract enforces "no replacement after payout" as an invariant; if it does, this finding would be mitigated at the L2 layer rather than in this repo, but nothing in the reviewed Rust code enforces it as a defense-in-depth check.

### Recommendation
In `update_replacement_deposit_move_txid`, reject (or require additional confirmation for) the update if the target `withdrawals` row already has a non-null `payout_txid`/`payout_payer_operator_xonly_pk`, or alternatively preserve the historical `move_to_vault_txid` used at payout time as a separate immutable column so `get_payout_info_from_move_txid` can still resolve reimbursement correctly against whichever vault was actually paid against.

### Proof of Concept
Not runnable from this analysis (no filesystem/DB access) but conceptually:
1. Withdrawal `idx = N` has `move_to_vault_txid = A` (deposit A).
2. Operator O verifies and fronts a payout for `idx = N`; `update_payout_txs_and_payer_operator_xonly_pk` sets `payout_txid`, `payout_payer_operator_xonly_pk = O` on row `idx = N` (still `move_to_vault_txid = A`).
3. A `ReplacementDeposit` referencing `old_move_txid = A` is confirmed on Citrea for the same `idx = N`; `update_citrea_deposit_and_withdrawals` calls `update_replacement_deposit_move_txid(dbtx, N, B)`, rewriting `move_to_vault_txid` to `B` with no check of step 2's state.
4. `get_payout_info_from_move_txid(A)` now returns `None`; operator O's reimbursement claim tied to vault A can no longer be located/validated via this lookup path, even though O genuinely fronted the payout against vault A.

        if payout_txs_and_payer_operator_xonly_pk.is_empty() {

                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))

            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),

                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

    pub async fn get_payout_info_from_move_txid(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        move_to_vault_txid: Txid,
    ) -> Result<Option<(Option<XOnlyPublicKey>, BlockHash, Txid, i32)>, BridgeError> {
        let query = sqlx::query_as::<_, (Option<XOnlyPublicKeyDB>, BlockHashDB, TxidDB, i32)>(
            "SELECT w.payout_payer_operator_xonly_pk, w.payout_tx_blockhash, w.payout_txid, w.idx
             FROM withdrawals w
             WHERE w.move_to_vault_txid = $1
               AND w.payout_txid IS NOT NULL
               AND w.payout_tx_blockhash IS NOT NULL",
        )
        .bind(TxidDB(move_to_vault_txid));

        let result: Option<(Option<XOnlyPublicKeyDB>, BlockHashDB, TxidDB, i32)> =
            execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        result
            .map(|(operator_xonly_pk, block_hash, txid, deposit_idx)| {
                Ok((
                    operator_xonly_pk.map(|pk| pk.0),
                    block_hash.0,
                    txid.0,
                    deposit_idx,
                ))
            })
            .transpose()
    }
