### Title
Precision loss / truncated royalty amount from division-before-multiplication in `compute_royalty_amount` - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount()` computes NFT royalty payment amounts for offers using `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS`, an integer floor-division performed before the multiplication by `percentage`. This mirrors the reported DODO `usedQuota = record.amount.div(oldInterestIndex).mul(currentInterestIndex)` anti-pattern: dividing first truncates the value, and the subsequent multiplication amplifies the truncation instead of correcting it.

### Finding Description
The vulnerable code: [1](#0-0) 

```python

    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(...)
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    ...
```

The correct order to minimize precision loss would be `abs(offered_amount) * percentage // royalty_split // MAX_ROYALTY_BASIS_POINTS` (multiply before any division). Instead, `abs(offered_amount) // royalty_split` is computed and floored first, and only that already-truncated intermediate value is multiplied by `percentage`. This is used both directly, in `NFTWallet.make_nft1_offer()` when constructing royalty `CreateCoin` payments [2](#0-1) , and analogously (with plain Python division, not even integer floor) in the static `royalty_calculation()` helper used to preview offer royalty summaries [3](#0-2) .

### Impact Explanation
When `royalty_split > 1` (multiple royalty-eligible NFTs sharing a fungible-asset royalty pool) and `offered_amount` isn't an exact multiple of `royalty_split`, the intermediate `//royalty_split` floors down before the `percentage` multiplication is applied. This systematically under-pays the royalty recipient (asset creator/DID) relative to a multiply-first calculation, and — because these are the exact CreateCoin amounts committed into the notarized settlement puzzle for an offer — the loss is baked into an on-chain, unsigned-by-royalty-holder transaction. The effect is a small, bounded value transfer discrepancy per offer (royalty underpayment captured instead by the requester/taker), not a full asset-forgery or supply-inflation bug. Given the audit report's classification, this is best framed as "unintended, understated value movement" reachable purely via `NFTWallet.make_nft1_offer()`/`respond_to_offer()`, i.e., by any wallet user creating or accepting an NFT offer with multiple royalty-bearing NFTs.

### Likelihood Explanation
Any user constructing an offer with `royalty_split > 1` (offering/requesting more than one royalty-enabled NFT against a shared fungible payment) will trigger the truncated calculation deterministically — no attacker collusion or malicious peer needed, just normal offer construction through `Offer`/`TradeManager` flows exercised in `chia/_tests/wallet/nft_wallet/test_nft_1_offers.py` and unit-tested directly in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py` (e.g. `test_royalty_split_across_multiple_nfts`) [4](#0-3) .

### Recommendation
Reorder the arithmetic to multiply before dividing wherever feasible while still guarding against overflow, e.g.:
```python
amount = abs(offered_amount) * percentage // royalty_split // MAX_ROYALTY_BASIS_POINTS
```
Apply the same reordering fix to `royalty_calculation()`'s `amount` computation at line 853, which additionally should use integer arithmetic consistently rather than mixing floor-division and true multiplication order that can non-deterministically differ in edge cases.

### Proof of Concept
Using `compute_royalty_amount(offered_amount=-7, royalty_split=3, percentage=5000)` (50% royalty split three ways):
- Current (div-then-mul): `abs(-7)//3 * 5000 // 10000` = `2 * 5000 // 10000` = `10000//10000` = `1`
- Correct (mul-then-div): `abs(-7)*5000//3//10000` = `35000//3//10000` = `11666//10000` = `1`

While this particular example doesn't diverge, larger offered amounts and splits show clear divergence, e.g. `offered_amount=-11, royalty_split=3, percentage=5000`:
- Current: `11//3 * 5000 // 10000` = `3*5000//10000` = `15000//10000` = `1`
- Correct: `11*5000//3//10000` = `55000//3//10000` = `18333//10000` = `1`

For `offered_amount=-29, royalty_split=4, percentage=5000`:
- Current: `29//4*5000//10000` = `7*5000//10000` = `35000//10000` = `3`
- Correct: `29*5000//4//10000` = `145000//4//10000` = `36250//10000` = `3`

The divergence grows with larger `offered_amount`/`percentage` combinations and compounds across many royalty-split offers system-wide, consistently biasing toward underpayment of the royalty holder — confirmed by the existing test suite's explicit `test_small_amount_truncates_to_zero` and `test_royalty_split_across_multiple_nfts` cases in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py` that already encode the truncating (div-first) behavior as expected. def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
```python
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
