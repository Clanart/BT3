### Title
Attacker-controlled participant count in `ThresholdKeys::read` forces a large speculative allocation, enabling deserialization DoS - (File: crypto/dkg/src/lib.rs)

### Summary
The CVE-2021-40609 bug class is "crafted input causes denial of service during parsing." In Serai's in-scope code, the analog is `ThresholdKeys::<C>::read`, which reads the threshold parameters `t`, `n`, `i` directly from attacker-supplied bytes and immediately trusts `n` to size a heap allocation (`Vec::with_capacity(usize::from(n))`) and to drive deserialization loops — before any validation of `n` occurs via `ThresholdParams::new`.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` deserializes:

```rust
let (t, n, i) = { /* three u16s read straight from the reader */ };
...
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  ...
``` [1](#0-0) 

Two issues follow from `n` being fully attacker-controlled (a `u16` up to 65535):

1. **Speculative allocation before validation**: `Vec::with_capacity(usize::from(n))` allocates `n * size_of::<C::F>()` (≈32 bytes/scalar for `Secp256k1`/`Ristretto`, ≈2 MB) immediately upon reading the 1-byte interpolation tag — with as few as ~11 bytes of input — before `ThresholdParams::new(t, n, i)` (which would reject `t > n`, `i > n`, or `n == 0`) is ever called at the end of the function.

2. **Validation happens only at the end**: `ThresholdParams::new` and the `i`/`Participant::new` checks occur after all allocation and reads (`crypto/dkg/src/lib.rs:625-631`), so malformed parameter combinations still cost the allocation work.

Additionally, `read_F` inside the loop is O(1) per element and requires bytes to be present, so the pure-read amplification is bounded — but the `with_capacity` allocation is not; it costs ~2 MB of heap for ~12 bytes of input, per call.

### Impact Explanation
`ThresholdKeys::read` is listed among the entry points fed untrusted bytes. An unprivileged party that can trigger deserialization of a crafted `ThresholdKeys` blob forces an ~2 MB heap allocation per invocation at negligible input cost (a `u16` of `0xFFFF` plus the interpolation byte `0`). Repeated invocations amplify memory pressure / allocator churn and can exhaust memory in constrained environments or when done concurrently — the same impact class as CVE-2021-40609 (resource-exhaustion DoS via crafted input).

Caveat: the amplification is capped at ~2 MB per call because `n` is a `u16`. That bounds the severity to Medium at best; it is not an unbounded (e.g., `u32`/`u64`-driven) allocation like the `u32` length-prefixed reads found in out-of-scope code (`processor/src/plan.rs:56`, `networks/ethereum/src/machine.rs:48` — the latter even carries a comment acknowledging the 4 GB DoS and chunks reads to mitigate it, confirming the project treats this class as a real concern).

### Likelihood Explanation
Reachability depends on the deployment: wherever serialized `ThresholdKeys` cross a trust boundary (received from another participant, restored from shared/untrusted storage, or fed through the listed `ThresholdKeys::read` entry point), any peer can send the ~12-byte prefix `t,n,i` with `n = 0xFFFF`, interpolation tag `0` and trigger the allocation. No valid cryptographic content is needed — the allocation happens before any consistency check. Likelihood is moderate because the impact per call is bounded and the read then fails on the first missing scalar.

### Recommendation
Validate `n` before trusting it:

1. Move `ThresholdParams::new(t, n, i)` (and a sanity bound on `n`, e.g., `n <= MAX_PARTICIPANTS`) to immediately after reading `t, n, i`, and reject early via `map_err(io::Error::other)`.
2. Replace `Vec::with_capacity(usize::from(n))` with `Vec::new()` (or a capped capacity) so allocation grows only as actual bytes are consumed — the same pattern `Call::read` in `networks/ethereum/src/machine.rs` uses to bound a claimed-length DoS to actual input.
3. Apply the same "validate-then-allocate" audit to other readers that take lengths/counts from the wire (`EncryptedMessage::read`/`E::read` paths driven by `ThresholdParams`, `MultiDLEqProof::read(r, discrete_logs)` in `crypto/dleq/src/lib.rs:308` if `discrete_logs` ever comes from untrusted input).

### Proof of Concept
Conceptual (Rust, against `crypto/dkg`):

```rust
use std::io::Cursor;
use dkg::ThresholdKeys;
use ciphersuite::Ciphersuite; // e.g., Secp256k1 via frost::curve

fn poc() {
    // Minimal crafted blob:
    //   id_len (4 LE bytes matching C::ID.len()) || C::ID
    //   t = 0xFFFF... actually any t; n = 0xFFFF; i = 1
    //   interpolation = 0 (Constant)
    let mut blob = Vec::new();
    blob.extend_from_slice(&(C_ID_LEN as u32).to_le_bytes());
    blob.extend_from_slice(C_ID);            // must match target ciphersuite ID
    blob.extend_from_slice(&1u16.to_le_bytes());      // t
    blob.extend_from_slice(&u16::MAX.to_le_bytes());  // n = 65535  <- attacker value
    blob.extend_from_slice(&1u16.to_le_bytes());      // i
    blob.push(0);                                     // Interpolation::Constant

    // Triggers Vec::with_capacity(65535) (~2 MB for a 32-byte scalar)
    // before failing on the first missing read_F and before
    // ThresholdParams::new ever validates t/n/i.
    let _ = ThresholdKeys::<C>::read(&mut Cursor::new(blob));
}
```

The function returns `Err` (out of input), but only after committing the `n`-scaled allocation — demonstrating parse-time resource exhaustion from a crafted input, the direct Serai analog of CVE-2021-40609.
