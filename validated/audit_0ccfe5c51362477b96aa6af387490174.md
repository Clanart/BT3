### Title
Schnorr verification accepts trivially forged signatures for identity public keys - (File: crypto/schnorr/src/lib.rs)

### Summary
`SchnorrSignature::verify` performs only the equation `R + cA - sG = 0` and does not reject the identity public key or identity nonce commitment. Because canonical point decoding also accepts the identity element, an attacker can submit `R = 0, s = 0` for public key `A = 0`; the equation is satisfied for every challenge and message.

### Finding Description
`SchnorrSignature::read` accepts any canonical point `R` and scalar `s`, without excluding the identity point or zero scalar [1](#0-0) . `Ciphersuite::read_G` checks only that a supplied encoding decodes and re-encodes canonically; it does not reject the identity element [2](#0-1) .

Verification constructs the statements `(1, R)`, `(c, A)`, and `(-s, G)` [3](#0-2) . For attacker-supplied `A = 0`, `R = 0`, and `s = 0`, this becomes `0 + c·0 - 0·G = 0`, so verification succeeds regardless of the challenge [4](#0-3) .

### Impact Explanation
Any caller that verifies an attacker-controlled public key without separately rejecting the identity key accepts a forged signature for every message and challenge. This also affects proof-of-possession-style uses in which the public key is carried in an untrusted message, because a signature under the identity key proves no possession of an unpredictable secret.

### Likelihood Explanation
The attack requires the verifier to accept an attacker-supplied identity public key. The decoding and verification APIs expose no internal defense against that case, so applications that treat group membership as sufficient key validity are directly affected. The forgery is deterministic and does not require nonce reuse, secret knowledge, or interaction with an honest signer.

### Recommendation
Reject identity public keys during signature verification or provide a validated public-key type that excludes identity. Also reject `R = 0` during `SchnorrSignature::read` or verification; the coordinator’s `Signed` parser already implements this defense for nonce commitments [5](#0-4) . Key generation should continue rejecting zero secret scalars, while deserialization and verification should independently reject the corresponding public key.

### Proof of Concept
For any ciphersuite whose canonical point encoding supports the identity element, deserialize:

```text
R = identity
s = 0
```

Then call:

```rust
signature.verify(identity_public_key, arbitrary_challenge)
```

The statements produced by `batch_statements` are:

```text
1·R + c·A - s·G
= 1·0 + c·0 - 0·G
= 0
```

Thus `verify` returns `true` for every `arbitrary_challenge` and associated message, even though the supplied signature proves control of only the invalid zero secret key.

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
