## Title
Out-of-bounds backward scan (buffer under-read) when parsing a JSON `Any` message with a leading non-`@type` field - (`File: upb/json/decode.c`, also duplicated in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`)

## Summary
The Wireshark RFC 7468 dissector crash stemmed from a state/position-tracking bug in a text-based decoder: an attacker-controlled boundary condition let the dissector's cursor move into invalid territory, causing an out-of-bounds access and process crash. The transferable invariant is "a decoder's internal pointer/cursor arithmetic must never be walked past the start/end of the attacker-supplied buffer without a bound check." In upb's ProtoJSON `Any` handling (`jsondec_any` in `upb/json/decode.c:1445-1516`, duplicated in `ruby-upb.c:5129-5200` and `php-upb.c:6376-6447`), the helper `jsondec_anyfield`'s caller performs exactly this kind of unguarded backward pointer walk:

```c
if (jsondec_streql(name, "@type")) {
  any_m = jsondec_typeurl(d, msg, m);
  if (pre_type_data) {
    pre_type_end = start;
    while (*pre_type_end != ',') pre_type_end--;
  }
}
``` [1](#0-0) 

## Finding Description
`jsondec_any` decodes `google.protobuf.Any` from JSON by scanning the object for the `"@type"` property, which per spec may occur at any position, not just first: [2](#0-1) 

While scanning, if a non-`@type` key is seen before `@type`, `pre_type_data` is recorded as the byte offset (`start`) where that first "other" field's key begins:
```c
} else {
  if (!pre_type_data) pre_type_data = start;
  jsondec_skipval(d);
}
``` [3](#0-2) 

When `@type` is subsequently found, the code walks *backward* from the `@type` key's start position (`start`) looking for a `,` to determine `pre_type_end` — the end of the "pre-type" field region that needs to be replayed later:
```c
pre_type_end = start;
while (*pre_type_end != ',') pre_type_end--;
```
This loop assumes a comma always precedes `@type` in this scenario (true for well-formed JSON where `@type` is not first). However, the loop has **no lower bound check** against `d->ptr`/buffer start or against `pre_type_data`. It blindly decrements a raw `const char*` and dereferences it until it finds a `,` byte, anywhere in memory. If the byte sequence between the actual buffer start and `@type` never legitimately contains a `,` before reaching before the buffer (an edge condition the whitespace-skip position calculations could produce, e.g. through byte sequences that are almost-but-not-quite what the "always a comma precedes" assumption holds for, or through crafted whitespace/objects that shift `start` unexpectedly), the pointer walks off the front of the heap allocation into unrelated memory, causing an out-of-bounds read and, upon dereferencing unmapped memory, a crash (SIGSEGV) — a direct availability failure analogous to the Wireshark RFC 7468 crash: a decoder trusting positional/structural assumptions about attacker-supplied bytes without bound-checking its own cursor arithmetic.

This same code (byte-for-byte identical) is duplicated in the Ruby and PHP native upb bundles: [4](#0-3) [5](#0-4) 

All are reachable from the public JSON-parsing API (`upb_JsonDecode`, and Ruby's/PHP's `JSON.parse`/`decode` entry points), which is the analogous "public parse API" surface required by this investigation's attacker model (ProtoJSON input from an ordinary client).

## Impact Explanation
A successful trigger results in an out-of-bounds memory read that can crash the process (denial of service) — directly analogous to the Wireshark RFC 7468 CVE's crash impact (CVSS Availability:High, no Confidentiality/Integrity impact). Depending on heap layout, the backward scan could also read adjacent heap memory before crashing, but proving information disclosure would require a much deeper heap-layout analysis; the primary, most reliably demonstrable impact is a crash/DoS via out-of-bounds read when the walk reaches an unmapped page.

## Likelihood Explanation
The `Any` JSON representation with `@type` occurring after another field (e.g., `{"foo": ..., "@type": "..."}`) is a legitimate, spec-permitted JSON shape that any client can send to a public `ParseFromJson`/`JsonDecode` API. Constructing the exact byte layout to make the backward scan run past the buffer start requires deep familiarity with the lexer's whitespace/position bookkeeping, but the code shows no defensive lower bound, so the class of bug (unbounded backward scan keyed off attacker-controlled field ordering) is real and present in three independently-compiled language bindings (C core upb, Ruby, PHP), increasing confidence this is a genuine unguarded pointer-arithmetic defect rather than a one-off typo.

## Recommendation
Bound the backward scan against the known start of the buffer (or against `pre_type_data`, which already marks the earliest position that needs to be re-scanned) instead of assuming a comma will always be found:
```c
pre_type_end = start;
while (pre_type_end > pre_type_data && *pre_type_end != ',') pre_type_end--;
if (*pre_type_end != ',') jsondec_err(d, "malformed Any object");
```
Apply the fix consistently to `upb/json/decode.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`, and `php/ext/google/protobuf/php-upb.c` since all three carry the identical vulnerable pattern.

## Proof of Concept
I could not obtain a build/execution environment through the available (read-only, index-search) tooling to actually run upb's JSON decoder against a crafted payload and capture a crash trace. Based on static analysis, the theorized minimal trigger is a JSON payload for an `Any`-typed field where a non-`@type` key appears first and the byte sequence preceding `@type`'s key start, when scanned backward, does not encounter a `,` before running off the buffer — e.g., carefully crafted via nested `Any` reparsing (`d->ptr`/`d->end` are temporarily repointed to a synthetic buffer in the "pre_type_data" replay branch at lines 1483-1499) where the synthetic buffer's `tmp` allocation lacks a leading comma. I was unable to fully confirm reachability of an exact "no comma found" byte layout without executing the code, so this should be verified with a fuzz harness (e.g., `libFuzzer` target over `upb_JsonDecode`) targeting `Any` messages with reordered/malformed field sequences before treating this as a confirmed, exploitable finding.
