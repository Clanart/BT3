### Title
OP_RETURN data output is excluded from fee and weight accounting, producing transactions that underpay and may exceed policy limits - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the transaction weight, virtual size, and `needed_fee` from `payments` only, after the OP_RETURN `data` output has already been pushed into `tx_outs`. The late-added output is never fed back into the size/fee calculation — the same stale-state pattern as the reference bug, where `hasSaleEnded` is evaluated against an `endTime` that is only corrected on `unpause`.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-202`, the OP_RETURN output carrying `data` (up to 80 bytes, checked at line 171) is appended to `tx_outs`. The weight/vbyte calculation at line 204 then calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds a template transaction containing only `payments` — it never sees `tx_outs`, so the OP_RETURN output is invisible to it. The same omission occurs in the change path at lines 225-226, which again passes `payments` rather than the actual output set.

Consequences, all reachable by an unprivileged caller via the public `data` argument:

1. **Underpaid fee**: `needed_fee = fee_per_vbyte * vbytes` uses `vbytes` of a transaction missing the data output. An 80-byte payload adds an OP_RETURN script of ~84 bytes (≈336+ weight units, ~85+ vbytes). The resulting signed transaction pays materially less than the requested fee rate.
2. **Bypassed relay check**: the `TooLowFee` check at line 211 validates `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`. A transaction can pass this check while its *actual* fee rate falls below the minimum relay rate, so Bitcoin nodes will reject it.
3. **Bypassed weight check**: `TooLargeTransaction` at line 241 compares `weight` (excluding the data output) against `MAX_STANDARD_TX_WEIGHT`; the real transaction can exceed it.

This mirrors the reference report's structure: a correctness-relevant quantity (`endTime` / transaction size) is updated only *after* the predicate that depends on it (`hasSaleEnded` / the fee and policy checks) has already been evaluated, so the predicate's answer is wrong during the window that matters.

### Impact Explanation
A `SignableTransaction` built with `data` produces a Bitcoin transaction whose effective fee rate is lower than `fee_per_vbyte` — potentially below the network minimum relay fee. The transaction is still validly signed (the sighash commits to the real `tx`), so the multisig completes and produces a transaction that cannot be relayed or confirmed as intended, locking the referenced inputs until a corrected transaction is re-signed. `needed_fee()`/`fee()` consumers also receive accounting that omits the data output's marginal cost. Denied broadcast of a signed spend is a concrete availability impact on funds, consistent with Medium severity.

### Likelihood Explanation
Any caller passing `Some(data)` to `SignableTransaction::new` triggers it deterministically — no adversarial timing or collusion required. The miscalculation is proportional to `data.len()`, worst at the 80-byte cap. Whether the effective rate drops below the relay minimum depends on `fee_per_vbyte` and margins, but underpayment relative to the requested rate occurs for every non-empty `data`.

### Recommendation
Include the OP_RETURN output in the size calculation. Either pass `tx_outs` (or the data-bearing script) into `calculate_weight_vbytes` instead of `payments`, or add the data output's serialized size/weight to `weight` and `vbytes` before computing `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check. Apply the same fix in the change branch (lines 225-226).

### Proof of Concept
```rust
// Conceptual: one input, no payments, change None, 80-byte OP_RETURN
let tx = SignableTransaction::new(
  vec![input],            // a ReceivedOutput worth e.g. 50_000 sats
  &[],                    // no payments
  None,                   // no change
  Some(vec![0u8; 80]),    // max-size OP_RETURN
  FEE,                    // e.g. 1 sat/vbyte... wait
).unwrap();

// tx.needed_fee() was computed as fee_per_vbyte * vbytes(payments-only template),
// omitting ~85+ vbytes for the OP_RETURN output.
// The real transaction: tx.transaction().vsize() is ~85+ vbytes larger,
// so effective_rate = tx.fee() / tx.transaction().vsize() < FEE,
// and can fall under DEFAULT_MIN_RELAY_TX_FEE even though TooLowFee passed.
```
Concretely, comparing `tx.transaction().weight().to_wu()` against the `weight` value used internally shows the ~336+ weight-unit discrepancy, and `tx.fee() as f64 / tx.transaction().vsize() as f64` is strictly less than `fee_per_vbyte` whenever `data` is non-empty. (Note: the caller path in `processor/src/networks/bitcoin.rs` currently passes `None` for `data`, so the bug is latent in the library API rather than exercised by the in-repo processor today.)
