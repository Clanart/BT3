Based on the report's core invariant — **"a value recorded as backing a locked receipt/escrow can diverge from what is actually custodied, and the system settles against the recorded (not actual) value"** — I traced this pattern into Hyperbridge's Tron `IntentGateway` deployment and found a direct local analog: the Tron variant of `placeOrder` never measures actual tokens received, unlike the hardened EVM `src` version, which does. This creates the same "recorded value ≠ actual backing" gap that let the veAERO exploiter drain other parties' backing.

### Title
Tron IntentGatewayV2.placeOrder credits escrow ledger with the declared amount instead of the actually-received balance, enabling attackers to siphon other users' escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder` credits the internal escrow ledger `_orders[commitment][token]` with `reducedInputs[i].amount` — a value derived purely from the caller-declared `order.inputs[i].amount` — without ever checking how many tokens the gateway actually received via `safeTransferFrom`. [1](#0-0) 
The audited, non-Tron EVM implementation explicitly guards against this by measuring the gateway's token balance before and after the transfer and writing the *actual received* amount back into `order.inputs[i].amount` before it is used for the commitment and the escrow credit. [2](#0-1) 

### Finding Description
The IntentGateway's escrow is a single, per-token pooled ERC20 balance shared across every open order — there is no real segregation of custody per commitment; `_orders[commitment][token]` is purely bookkeeping used later by `_withdraw`/`withdraw()` to transfer out of that shared pool. This is architecturally the same "receipt records a value, real backing lives in a shared/external system" pattern that broke the veAERO managed-NFT case: the receipt (there, the (m)veAERO NFT; here, the `_orders[commitment][token]` accounting entry) can be made to claim more value than is actually custodied, and once that gap exists, whoever calls `withdraw()`/`fillOrder()` first drains real tokens that belong to someone else's order.

In the hardened EVM path (`evm/src/apps/IntentGatewayV2.sol:281-298`), the gateway snapshots `balBefore`, calls `safeTransferFrom`, and re-derives `order.inputs[i].amount` from the *actual* balance delta — this is exactly the defense needed for fee-on-transfer or other non-standard ERC20s, and the commitment/escrow credit downstream (`evm/src/apps/IntentGatewayV2.sol:333-343`) is computed from that measured amount.

The Tron deployment (`evm/tron/contracts/apps/IntentGatewayV2.sol:444-462`) omits this defense entirely: it calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally does `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is computed from the attacker-declared `order.inputs[i].amount`, not from any measured balance.

An attacker places an order using a fee-on-transfer, rebasing, or otherwise short-transferring ERC20 token as `order.inputs[0]` with a declared amount of, say, 1,000,000 tokens. The gateway's real balance only increases by the post-fee amount (e.g., 990,000), but the escrow ledger records ~1,000,000 (minus protocol fee) as backing that commitment. The gateway's real token balance for that ERC20 is now less than the sum of all `_orders[...][token]` entries across every open order using that token — the shortfall is silently absorbed by the shared pool. When any order (the attacker's own, or another user's legitimate order in the same token) is filled or refunded, `withdraw()` pulls from the shared contract balance using the ledger's recorded amount, not a per-commitment-segregated balance. The attacker's own order settles in full (they get a solver fill for the declared 1,000,000, an amount the gateway never actually held), and the deficit is paid out of tokens that were deposited as backing for other users' unrelated orders — those other orders' eventual `withdraw()` calls either revert (locking funds) or, in commingled-pool draw-down order, receive less than their recorded entitlement.

Existing guards do not stop this: `placeOrder` performs no balance-based measurement on Tron; `_orders[commitment][token] != 0` only rejects duplicate *inputs within the same order*, not cross-order pool insufficiency; and `withdraw()`/`_withdraw()` simply trusts the ledger value and calls `safeTransfer`, only reverting once the pool is already exhausted — at which point the loss has already landed on whichever other order's beneficiary tries to withdraw after the pool is drained.

### Impact Explanation
This causes real fund loss for other order participants, matching the accepted bounty categories directly: an unprivileged attacker using an ordinary, permissionless entrypoint (`placeOrder`) can cause the escrow ledger to record false state (inflated backing) that is later trusted at settlement (`fillOrder`/`withdraw`), resulting in funds being paid out that were never actually escrowed, at the expense of other legitimate depositors sharing the same token pool. This is loss of funds and false-state acceptance of escrow value, not merely a gas/DoS issue.

### Likelihood Explanation
Requires only an unprivileged user placing an order with a non-standard ERC20 (fee-on-transfer, rebasing, or any token whose `transferFrom` delivers less than the requested amount) as input on the Tron deployment — no relayer, prover, admin, or governance action needed. The EVM `src` contract's own test suite (`testPlaceOrder_FeeOnTransferToken_Predispatch`, etc.) demonstrates this exact token class is a realistic, expected input the protocol must handle, and the Tron contract in this repo has no equivalent protection.

### Recommendation
Port the balance-measurement pattern from `evm/src/apps/IntentGatewayV2.sol` (snapshot balance before `safeTransferFrom`, recompute `order.inputs[i].amount` from the actual delta) into `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, for both the direct-transfer and predispatch-sweep code paths, before the value is used to compute `reducedInputs` and credit `_orders[commitment][token]`.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` with a fee-on-transfer ERC20 (e.g., 1% fee) registered as a valid input token.
2. Attacker calls `placeOrder` declaring `order.inputs[0].amount = 1_000_000e18`; `safeTransferFrom` only delivers `990_000e18` to the gateway, but `_orders[commitment][token]` is credited with `reducedInputs[0].amount ≈ 1_000_000e18` (minus protocol fee).
3. A benign user, using the same token, places a separate legitimate order and its full amount is correctly transferred and credited.
4. A solver fills the attacker's order; `withdraw()` transfers the ledger-recorded (inflated) amount out of the gateway's single pooled token balance for that ERC20.
5. When the benign user's order is later filled/refunded, `withdraw()` for that commitment reverts (insufficient contract balance) or receives less than its recorded entitlement — the benign user's escrowed funds have been effectively drained by the attacker's under-collateralized order. [3](#0-2)
