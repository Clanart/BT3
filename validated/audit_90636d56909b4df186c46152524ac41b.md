### Title
Governance-settable `GasTarget=0` causes division-by-zero panic in KIP-71 base fee calculation - ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by `gasTarget` when the parent block's gas usage differs from the target. The governance parameter `Kip71GasTarget` is registered with a `noopFormatChecker`, unlike the sibling parameter `Kip71BaseFeeDenominator`, which explicitly rejects zero. A governance vote (or a malicious/compromised governing node) can therefore set `GasTarget` to `0`, and the very next block that uses any gas at all will trigger an integer division by zero, panicking every node that computes or verifies the header's base fee.

### Finding Description
In `NextMagmaBlockBaseFee`, once `parentGasUsed` (capped by `upperGasLimit`) differs from `gasTarget`, the code computes:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget) // or gasTarget - parentGasUsed
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // divide by gasTarget
``` [1](#0-0) 

If `gasTarget == 0`, `x.Div(x, new(big.Int).SetUint64(0))` is a division by zero, which `math/big.Int.Div` panics on. The only case avoided is when `parentGasUsed == gasTarget == 0`, i.e. a block with literally zero gas used — any transaction inclusion causes `parentGasUsed > gasTarget` and hits the vulnerable branch.

The governance parameter definition for `Kip71GasTarget` uses `noopFormatChecker`, which performs no validation at all, in contrast to `Kip71BaseFeeDenominator`, which is explicitly checked to reject `0`: [2](#0-1) 

This means governance voting/param-set logic accepts `GasTarget = 0` as a valid value, unlike the intentionally-guarded denominator field.

`NextMagmaBlockBaseFee` (and the header verification wrapper `VerifyMagmaHeader`) is invoked from core block-processing / validation paths, including `blockchain/block_validator.go`, `blockchain/tx_pool.go`, `work/worker.go`, and `node/cn/gasprice/*`, meaning every node in the network (validators, full nodes, RPC nodes) executes this calculation while validating each new block header after the Magma fork. [3](#0-2) 

### Impact Explanation
Once a governance vote sets `Kip71GasTarget` to `0` and is applied, the entire network halts: every node that attempts to compute or verify the next block's base fee (proposers building blocks, validators verifying headers, RPC nodes estimating gas/fee history) panics on the very next block containing any gas usage. This is a chain-wide denial-of-service that requires no attacker-controlled transaction — only a single governance parameter value that the current code fails to reject, unlike its sibling `BaseFeeDenominator`. This is analogous to CVE-2017-14518's uncontrolled arithmetic exception from unchecked input, except triggered via an on-chain governance parameter rather than a crafted PDF.

### Likelihood Explanation
Likelihood depends on governance access. Under Kaia's governance model, whoever controls the governing node/council can submit a parameter vote for `Kip71GasTarget`. Because the format checker is a no-op, there is no code-level barrier stopping such a vote from being accepted and eventually applied, unlike other numeric KIP-71 fields (e.g. `BaseFeeDenominator`) which are explicitly guarded against zero. This makes the bug reachable strictly through the governance parameter path explicitly listed as in-scope, but it does require governance-level write access (vote proposal/approval), not an arbitrary unprivileged transaction sender.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check) in `kaiax/gov/param.go`, and/or add a defensive zero-check with a safe fallback inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` before performing the division, so that a governance-approved value of `0` cannot crash consensus-critical code.

### Proof of Concept
1. Governance votes to set `governance.kip71.gastarget = 0` and the vote takes effect at block `N`.
2. Block `N` is produced/validated normally if `parentGasUsed == 0`.
3. Block `N+1` includes at least one transaction (any nonzero gas usage), so `parentGasUsed (>0) > gasTarget (0)`.
4. `NextMagmaBlockBaseFee` executes:
   ```go
   gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - 0)
   x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
   y := x.Div(x, new(big.Int).SetUint64(0))  // panics: division by zero
   ``` [4](#0-3) 
5. Every node computing/verifying the header for block `N+1` (proposer, validators, RPC gas price oracle) panics, halting the chain network-wide.
