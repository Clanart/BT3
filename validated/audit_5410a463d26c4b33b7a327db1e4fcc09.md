### Title
Repeated `share`/`complete` calls under one context reuse the cached FROST preprocess, re-signing with the same nonces and leaking the secret share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The reported bug class is a public, unguarded initialization function that can be invoked repeatedly to keep "minting" value that should have been issued once. The Serai analog is the cached-preprocess mechanism in `SigningProtocol::preprocess_internal`: for a fixed `context`, the same `CachedPreprocess` seed is loaded from the DB and deterministically re-expanded into the same FROST nonce pair every time `preprocess_internal` runs. Each of `share_internal` and `complete` (which internally calls `share_internal` again) rebuilds the sign machine from that seed and calls `machine.sign(...)`, producing a signature share over the *same* nonces. This is safe only if every call signs the identical message with the identical participant set; if two calls differ in either, the nonce reuse allows third-party recovery of the signing key share.

### Finding Description
`preprocess_internal` stores a ChaCha20 seed under `CachedPreprocesses[context]` the first time it runs, then on every subsequent call decrypts that same seed and re-derives the identical `Nonce`s and `Preprocess` via `AlgorithmSignMachine::from_cache` (`seeded_preprocess` regenerates nonces deterministically from `ChaCha20Rng::from_seed`) — coordinator/src/tributary/signing_protocol.rs:123-147 and crypto/frost/src/sign.rs:121-144. `share_internal` calls `preprocess_internal` and then `machine.sign(preprocesses, msg)` — signing_protocol.rs:150-170. `DkgConfirmer` pins the context to `(b"DkgConfirmer", self.attempt)` — signing_protocol.rs:274-277 — while `share_internal` builds `msg` from `set_keys_message(set, removed, key_pair)` — signing_protocol.rs:296-301 — and `complete` re-runs `share_internal` with a freshly supplied `preprocesses` map — signing_protocol.rs:312-327.

Two divergence channels exist within a single attempt/context:

1. Different `key_pair` / `msg`: every call to `DkgConfirmer::share`/`complete` signs `set_keys_message(.., key_pair)`. If more than one key pair is confirmed under the same attempt (e.g., distinct networks' keys confirmed in the same DKG attempt), each call emits a share `s = d + e·ρ + λ·x·c` reusing the same `d, e` but with a different challenge `c` (different `msg`) — a textbook Schnorr/FROST nonce-reuse leak.
2. Different `preprocesses` maps: `share` and `complete` each accept an externally supplied preprocess map; `sign` computes per-participant binding factors `ρ` and the `included` set from it — crypto/frost/src/sign.rs:283-318. If the accumulated set presented to `complete` differs from that presented to `share` (e.g., additional validator preprocesses arriving between the two handler invocations), the second call produces a share over the same nonces but different `ρ`/Lagrange coefficients, again enabling share recovery. Both shares are published as tributary `Share`/`SubstrateShare` messages, i.e., publicly observable.

The `sign.rs` documentation explicitly warns that `CachedPreprocess` "MUST only be used once. Reuse will enable third-party recovery of your private key share" — crypto/frost/src/sign.rs:85-87, 211-213. `preprocess_internal` deliberately reuses it across all calls sharing a context, and nothing in `DkgConfirmer` tracks whether `share`/`complete` were already invoked with a particular `(msg, preprocesses)` combination — the direct analog of the missing "already initialized" check in the report.

### Impact Explanation
Recovery of a validator's FROST/MuSig secret share (`ThresholdKeys` built from `musig(...)` at signing_protocol.rs:118-121) breaks the "voting-while-vesting"-equivalent security invariant here: the DKG confirmation signature is produced by the threshold scheme, and share recovery reduces the threshold. Combined with threshold-1 other compromised or colluded shares — or, in the MuSig context here where shares correspond to the confirmation key — it can enable forging DKG-confirmation signatures (`set_keys` messages) that were never authorized. This is "key share recovery," one of the accepted impact classes.

### Likelihood Explanation
Exploitation requires that `share`/`complete` be executed twice under the same attempt with either a different `key_pair` or a different effective preprocess set. Whether multiple `key_pair`s are confirmed per attempt, and whether the accumulated preprocess map can grow between the `share` and `complete` invocations, could not be fully confirmed from the coordinator's `handle.rs` call sites within the available search depth — this is the main uncertainty. If confirmation is strictly one-key-pair-per-attempt and the preprocess set is fixed before `share`, the leak requires a re-entrant/inconsistent-call path (e.g., crash/retry with a divergent accumulated set), lowering likelihood to Medium; otherwise it is High. Either way, the guard the report recommends (tracking prior initialization) is absent.

### Recommendation
Bind the cached preprocess to the exact thing being signed, not just the attempt: include a hash of `msg` (and ideally the canonical participant/preprocess-set commitment) in `context`, or store alongside `CachedPreprocesses[context]` the `msg`+set hash and refuse to `sign` when a subsequent call presents a different one. Alternatively, after `share_internal` produces a share, record that the context's nonce was consumed and make `complete` reuse the *previously produced* share rather than re-signing. This mirrors the report's fix of making re-initialization a no-op or a delta adjustment rather than a fresh mint.

### Proof of Concept
Under a single DKG attempt, call `DkgConfirmer::share(preprocesses_A, key_pair_1)` — emits `s1 = d + e·ρ_A + λ_A·x·c1` — then `DkgConfirmer::complete(preprocesses_B, key_pair_2, shares)` — its internal `share_internal` re-derives identical `d, e` from `CachedPreprocesses[(b"DkgConfirmer", attempt)]` and emits `s2 = d + e·ρ_B + λ_B·x·c2`. With `s1, s2`, the known messages (hence `c1, c2`), and the public preprocesses (hence `ρ_A, ρ_B`, `λ_A, λ_B`), an observer solves the two linear equations for the secret share `x` and nonce pair `(d, e)`. No code changes to FROST are needed; the reuse is entirely in the deterministic `from_cache` path at coordinator/src/tributary/signing_protocol.rs:137-147.

**Uncertainty note:** I could not fully verify, from the coordinator's `handle.rs` paths, that `share`/`complete` are actually invoked with divergent `key_pair`/`preprocesses` values within one attempt; if protocol invariants guarantee identical inputs on every call, the deterministic reuse is benign and this degrades to a latent hazard rather than a directly exploitable bug.
