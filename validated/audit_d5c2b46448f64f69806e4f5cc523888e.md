### Title
`OP_RETURN` outputs are omitted from Bitcoin fee estimation - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends the caller-controlled `data` output to the transaction before estimating its weight, but `calculate_weight_vbytes` is only given `payments` and optional `change`, so the `OP_RETURN` output is excluded from the calculated virtual size and fee. [1](#0-0) 

### Finding Description
When `data` is supplied, `SignableTransaction::new` adds a zero-value `OP_RETURN` output to `tx_outs`. [2](#0-1)  The initial fee estimate then calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which constructs a temporary transaction containing only the payment outputs, not `tx_outs` or the data output. [3](#0-2)  The same omission occurs when estimating a transaction with change because the second call also receives only `payments` and `change`. [4](#0-3)  The resulting `needed_fee` is therefore `fee_per_vbyte` multiplied by a smaller virtual size than the transaction that is actually stored and signed. [5](#0-4)  During signing, the code generates the Taproot sighash over the final transaction stored in `self.tx.tx`, including the previously appended `OP_RETURN` output. [6](#0-5) 

### Impact Explanation
A transaction requested with a specific `fee_per_vbyte` can be signed with less fee than required for that rate. With the maximum accepted 80-byte payload, the omitted output adds roughly 91 base bytes, or 91 vbytes, meaning the actual fee is approximately `91 * fee_per_vbyte` below the requested amount. If the inputs only cover the underestimated fee, the signed transaction may have an effective fee rate below the requested rate or below the relay minimum and fail to propagate or confirm. This is an inconsistent-output accounting bug analogous to inconsistent decimal handling: one component calculates a safety value using a different representation of the transaction than the component that creates and signs it.

### Likelihood Explanation
The issue is reachable whenever a caller supplies `Some(data)` to `SignableTransaction::new`; payloads up to 80 bytes are explicitly accepted. [7](#0-6) [8](#0-7)  The public test path constructs and signs exactly such a transaction with a randomly sized data payload. [9](#0-8) 

### Recommendation
Calculate the weight from the complete output list that will be signed. In particular, include the serialized `OP_RETURN` output in both the no-change and with-change calls to `calculate_weight_vbytes`, or refactor the helper to accept the final `tx_outs` representation so the estimate cannot diverge from the signed transaction. The minimum-relay check should also use the virtual size of the complete transaction rather than the reduced payment-only estimate. [10](#0-9) 

### Proof of Concept
```rust
// Construct an otherwise valid transaction with an 80-byte OP_RETURN payload.
let data = vec![0u8; 80];
let signable = SignableTransaction::new(
  vec![received_output],
  &[(payment_script, DUST)],
  Some(change_script),
  Some(data),
  fee_per_vbyte,
)?;

// This is the fee derived from a transaction that omits the OP_RETURN output.
let estimated_fee = signable.needed_fee();

// This is the transaction actually signed, including the OP_RETURN output.
let actual_vbytes = signable.transaction().vsize() as u64;
let required_fee = actual_vbytes * fee_per_vbyte;

// The signed transaction underpays relative to the requested fee rate.
assert!(estimated_fee < required_fee);
```

The discrepancy exists because `data` is pushed into `tx_outs` before estimation, while the estimator receives only `payments` and `change`. [11](#0-10)

    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
