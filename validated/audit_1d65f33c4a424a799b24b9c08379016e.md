### Title
Unchecked ERC20 boolean return value in escrow withdrawal lets tokens be marked "released" while beneficiary receives nothing - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` settles cross-chain intents by calling `withdraw()` from `onAccept` (for `RedeemEscrow`/`RefundEscrow` requests) and from `onGetResponse` (cancellation refunds). Token payout in `withdraw()`, and in the `SweepDust` handler, uses a raw low-level `.call` with the `IERC20.transfer` selector and only checks that the *call itself did not revert* — it never decodes/validates the returned `bool`. This is the exact same broken invariant as the external report's `payUser`: an ERC20 `transfer` that returns `false` instead of reverting is treated as a successful payment.

### Finding Description
In `withdraw()`: [1](#0-0) 
and for protocol fee redemption: [2](#0-1) 

the pattern `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); if (!success) revert TransferFailed();` only checks that the external call did not revert. Per the low-level `call` semantics, `success` is `true` as long as the callee executed without reverting — it says nothing about the ABI-encoded return data. Any ERC20 token whose `transfer` function returns `false` on failure (rather than reverting) — a widely known non-standard-but-common ERC20 behavior — will pass this check even though no tokens moved.

Meanwhile, `withdraw()` unconditionally marks the order as settled *before and regardless of* actual token movement:
- `_filled[body.commitment] = beneficiary;` is set unconditionally at the top of the function.
- `_orders[body.commitment][token] -= amount;` is decremented right after the unchecked transfer.
- `emit EscrowReleased(...)` / `emit EscrowRefunded(...)` fires unconditionally at the end.

The same unchecked pattern also exists in the `SweepDust` branch of `onAccept`: [3](#0-2) 

This is a real local analog of the report's core broken invariant ("unchecked ERC20 transfer" → false success signal), and it sits directly in the intent-settlement / escrow-custody path called by the trusted host after proof verification — i.e., it is reachable through the legitimate cross-chain settlement flow without needing a malicious relayer, prover, or admin.

### Impact Explanation
This falls under "loss of funds" and "false state acceptance" in the accepted impact set: the contract's internal escrow accounting (`_orders`, `_filled`) is permanently updated to reflect a completed payout even when the underlying token transfer silently failed. The result is:
- The beneficiary receives no tokens for the fill/refund, yet the order is marked filled/refunded (one-time-settlement state), so retrying is impossible via the same commitment.
- The escrowed balance (`_orders[commitment][token]`) is decremented to zero, so the tokens the contract is still holding become unaccounted-for/stuck, effectively locked in the contract with no linked withdrawal path.
- `EscrowReleased`/`EscrowRefunded` events falsely report success, which is exactly the false-logging scenario the external report describes.

### Likelihood Explanation
This code path executes automatically whenever a `RedeemEscrow`/`RefundEscrow`/`SweepDust` request is delivered by the host after normal proof verification — no malicious relayer or governance actor is required. The only precondition is that one of the escrowed tokens used in an order is an ERC20 implementation that returns `false` (rather than reverting) on a failed `transfer` (e.g., insufficient balance in an edge case, paused/blacklist-style tokens, or any non-standard ERC20 admitted as an input/output token by order creators). Since order `output`/`input` tokens are attacker/user-supplied token addresses (`address(uint160(uint256(order.output.assets[i].token)))`), a user or solver can deliberately choose such a token to trigger the condition deterministically, making this attacker-controllable rather than merely incidental.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, which is already imported and used elsewhere in the same file (e.g., `safeTransferFrom` calls in the fill path). `SafeERC20` decodes the return data and reverts on `false`, ensuring `_orders`/`_filled` state and `EscrowReleased`/`EscrowRefunded` events are only emitted after a verified, successful transfer.

### Proof of Concept
1. An order is created (or a `SweepDust`/refund path is triggered) where one of the escrowed `TokenInfo.token` addresses points to an ERC20 contract that returns `false` on `transfer` failure instead of reverting (e.g., a token low on gas-forwarding tricks, or simply a minimal ERC20 that returns `false` when `balanceOf[from] < amount` rather than reverting — this is valid ERC20 behavior per EIP-20, not a malicious token deployer requirement in the strict sense, though for a decisive PoC the attacker can deploy their own token and use it as the order's `output`/`input` token, which order creators fully control).
2. The order is filled/cancelled and the host relays a legitimate `RedeemEscrow`/`RefundEscrow` request through `onAccept`, calling `withdraw()`.
3. Inside `withdraw()`, `token.call(...)` executes without reverting but the decoded boolean is `false` because the token's internal transfer failed; `success` is `true` since only call-revert status is checked.
4. `_orders[commitment][token]` is decremented to zero and `EscrowReleased`/`EscrowRefunded` is emitted, while the beneficiary's on-chain token balance is unchanged and the tokens remain stuck in the `IntentGatewayV2` contract with no remaining code path to claim them (the commitment's escrow record is already zeroed out).
