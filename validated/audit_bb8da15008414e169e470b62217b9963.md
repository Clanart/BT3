### Title

`ReceivedOutput` deserialization trusts attacker-declared output values, letting unverified balances be credited and invalid transactions signed - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

Analogous to crediting `amount` instead of the actual amount received (fee-on-transfer), `ReceivedOutput::read` deserializes an attacker-controlled `TxOut` (whose `value` field is arbitrary) together with an `OutPoint`, and never verifies that the `OutPoint` actually references an on-chain output with that value or even that script. `Scanner`/`Output` code then reports `balance()`/`value()` from the *claimed* value, and `SignableTransaction` builds and signs a transaction over the *claimed* prevout values — the same "declared vs. actually received" divergence as the Union Finance bug.

### Finding Description

`ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs:122-134` reads three fields from an untrusted byte stream with no consistency check:

- `offset` via `Secp256k1::read_F`
- `output: TxOut` via `TxOut::consensus_decode` — the `value` (in satoshis) and `script_pubkey` are fully attacker-chosen
- `outpoint: OutPoint` via `OutPoint::consensus_decode` — arbitrary txid/vout

Nothing binds the claimed `TxOut` to the real UTXO referenced by `outpoint`. `value()` (`mod.rs:116-118`) and `Output::balance()` (`processor/src/networks/bitcoin.rs:128-130`) return `self.output.value` verbatim, so a deserialized `ReceivedOutput` can claim an arbitrary balance for an outpoint that carries dust, a different amount, or doesn't even belong to the scanner key — mirroring how `stake(amount)` credited `amount` regardless of what actually arrived.

On the spend side, `SignableTransaction::new` sums the claimed values (`send.rs:175`), uses them for `NotEnoughFunds` and change/dust math (`send.rs:215-235`), and stores them in `prevouts` (`send.rs:253`). `TransactionSignMachine::sign` commits to those claimed prevouts via `Prevouts::All` in the Taproot sighash (`send.rs:375-390`), and `SignableTransaction::multisig` only verifies `prevouts[i].script_pubkey` matches the offset key (`send.rs:277`) — the claimed `value` is never validated.

### Impact Explanation

Two consequences, both reachable purely by feeding crafted bytes to `ReceivedOutput::read`/`Output::read`:

1. **Funds reported received that are not spendable** (accepted impact): `balance()` reports the attacker-chosen value. The scheduler plans payments against phantom or inflated balances; the true on-chain funds either don't exist or are smaller, so accounting diverges from spendable reality exactly like crediting `amount` when only `amount - fee` arrived.

2. **Threshold-signed transactions that are permanently invalid**: since `Prevouts::All` commits every prevout's *claimed* value into the sighash, any inflated or deflated value makes every resulting Schnorr signature fail consensus validation. The multisig completes `sign`/`complete` successfully, emits a `Transaction`, and it can never be broadcast — a repeatable liveness denial against the signing pipeline, and planned payments silently fail while the plan machinery believes inputs covered them.

Notably, if a claimed value is *deflated* relative to a real Serai-owned outpoint, `input_sat` is understated, triggering `NotEnoughFunds`/`TooLowFee` (DoS on an otherwise valid spend); if *inflated*, the fee/change computation is satisfied on paper yet the signed sighash is wrong.

### Likelihood Explanation

The `read` path is the designated deserialization entry point for persisted/transported outputs (`Output::read` in `processor/src/networks/bitcoin.rs:156` embeds `ReceivedOutput::read` directly, alongside attacker-influenceable `presumed_origin` and `data` fields). Any channel delivering these bytes — peer messages, restored state, or forwarded outputs — lets an unprivileged party control the value/`OutPoint` pair. The scanner path (`scan_transaction`, `mod.rs:199-214`) is safe because `output` is cloned from the real chain transaction; the vulnerability is strictly the deserialization path trusting declared value, just as `stake` trusted the declared `amount` instead of measuring the actual balance delta.

### Recommendation

When constructing or deserializing a `ReceivedOutput`, verify the claim against the chain: resolve `outpoint` to the real `TxOut` (via the node/RPC or an SPV proof) and reject any `ReceivedOutput` whose serialized `output` differs from the on-chain output — i.e., measure the "actual received" state rather than trusting the declared one, the same fix recommended for the Union report. At minimum, `SignableTransaction::new`/`multisig` should assert that `prevouts[i]` equals the consensus-verified output for `input.previous_output`, not merely that `script_pubkey` matches the offset key. Serialization round-trips could also embed a commitment to the real outpoint→output binding.

// Construct a ReceivedOutput claiming 100 BTC for an outpoint that
// references a real dust output (or a nonexistent one).
let mut bytes = vec![];
bytes.extend(Scalar::ZERO.to_bytes());                     // offset = 0
bytes.extend(serialize(&TxOut {
  value: Amount::from_sat(10_000_000_000),                 // claimed: 100 BTC
  script_pubkey: p2tr_script_buf(key).unwrap(),            // our script so multisig() accepts
}));
bytes.extend(serialize(&OutPoint { txid: real_txid, vout: 0 })); // real value: 546 sats

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(forged.value(), 10_000_000_000); // reports 100 BTC; chain has 546 sats

// multisig() passes since only script_pubkey is checked (send.rs:277), and sign()
// commits the forged 100 BTC prevout amount into the Taproot sighash — producing
