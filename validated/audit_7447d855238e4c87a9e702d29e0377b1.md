### Title
Attacker-controlled Bitcoin transactions cause quadratic transaction hashing during output scanning - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`Scanner::scan_transaction` recomputes `tx.compute_txid()` once for every transaction output whose `script_pubkey` is registered with the scanner. Since `compute_txid()` hashes the complete transaction, a transaction containing many matching outputs causes repeated full-transaction hashing. The resulting CPU cost is quadratic in the number of matching outputs because increasing the number of outputs also increases the transaction size hashed on every match.

### Finding Description
The scanner iterates over all entries in `tx.output`. For every output whose `script_pubkey` exists in `self.scripts`, it constructs a `ReceivedOutput` and calls `tx.compute_txid()` to populate the `OutPoint`. [1](#0-0) 

A transaction with `m` matching outputs and serialized size proportional to `m` therefore performs `m` hashes of `O(m)` data, for total work `O(m²)`. `scan_block` exposes the same behavior for every transaction in an attacker-influenced block by calling `scan_transaction` on each transaction. [2](#0-1) 

### Impact Explanation
An unauthenticated Bitcoin user can make scanning perform substantially more hashing work than is proportional to the transaction's serialized size. A mined transaction containing the maximum practical number of outputs to a watched Serai script forces the processor to hash the full transaction once per output. Repeated across transactions or blocks, this can materially delay or stall deposit scanning and dependent processing. This is a resource-exhaustion issue; it does not by itself forge a signature or alter reported output ownership.

### Likelihood Explanation
The required input is ordinary public Bitcoin transaction data. The attacker only needs a transaction included in a scanned block with many outputs paying to a script registered in `Scanner::scripts`, such as a known Serai deposit script. The matching condition is a simple `HashMap` lookup on `output.script_pubkey`, so all attacker-created outputs can use the same watched script. [1](#0-0) 

### Recommendation
Compute `tx.compute_txid()` once before iterating over `tx.output`, store it in a local variable, and reuse it for every matched `OutPoint`. This changes scanning from quadratic hashing complexity to one transaction hash plus linear output inspection. The output enumeration and `u32` vout bound can remain unchanged.

### Proof of Concept
Conceptually, construct a Bitcoin `Transaction` whose `output` vector contains thousands of copies of a `TxOut` paying to `p2tr_script_buf(key)`, then call:

```rust
let scanner = Scanner::new(key).unwrap();
let outputs = scanner.scan_transaction(&attacker_tx);
```

For every matching output, the code pushes a `ReceivedOutput` whose `outpoint` is created using `tx.compute_txid()`. Thus a 3,000-output transaction triggers 3,000 complete transaction-ID calculations, rather than one calculation reused for all 3,000 `OutPoint`s. [3](#0-2)
