### Title
Missing `idx` constraint in `get_payout_txs_for_withdrawal_utxos` join lets one spent withdrawal UTXO credit two withdrawal indices - (File: core/src/database/verifier.rs, core/src/verifier.rs)

### Summary
`Verifier::update_finalized_payouts` calls `get_payout_txs_for_withdrawal_utxos`, which joins `withdrawals w` to `bitcoin_syncer_spent_utxos bsu` solely on `(w.withdrawal_utxo_txid, w.withdrawal_utxo_vout)`, with no `w.idx` scoping and no DB uniqueness constraint preventing two different withdrawal rows from sharing the same `(withdrawal_utxo_txid, withdrawal_utxo_vout)` pair. Because `update_withdrawal_utxo_from_citrea_withdrawal` (`core/src/verifier.rs:2254`) blindly upserts whatever outpoint Citrea reports for a given `idx` with no dedup check against other indices, an attacker who registers the identical `input_outpoint` for two different Citrea withdrawal IDs causes a single on-chain spend of that outpoint to be joined against both withdrawal rows, resulting in both indices being marked paid by `update_payout_txs_and_payer_operator_xonly_pk`.

### Finding Description
Binding claimed: `count({(idx, payout_txid) rows returned for a given spent withdrawal UTXO}) == 1`.

Code path:
1. `Verifier::update_citrea_deposit_and_withdrawals` (`core/src/verifier.rs:2248-2262`) iterates `new_withdrawals` from Citrea and calls `self.db.update_withdrawal_utxo_from_citrea_withdrawal(dbtx, idx, withdrawal_utxo_outpoint, block_height)` per index, with no check that `withdrawal_utxo_outpoint` is not already used by a different `idx`.
2. `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) calls `self.db.get_payout_txs_for_withdrawal_utxos(dbtx, block_id)`, which (per the question's stated SQL, matched by symbol names found in `core/src/database/verifier.rs`) joins `withdrawals` to `bitcoin_syncer_spent_utxos` only on `(txid, vout)`.
3. When Citrea's `withdraw`/`safeWithdraw` contract accepts an arbitrary user-supplied `input_outpoint` for two distinct withdrawal IDs `i` and `j` (the contract has no visibility into Bitcoin's UTXO set and cannot itself detect reuse — this is not a Citrea defect, the responsibility to prevent cross-index reuse rests with Clementine), both `withdrawals` rows for `i` and `j` end up with identical `(withdrawal_utxo_txid, withdrawal_utxo_vout)`.
4. Once any transaction spends that shared outpoint on Bitcoin, `bitcoin_syncer` inserts exactly one `bitcoin_syncer_spent_utxos` row for it.
5. The unconstrained join in `get_payout_txs_for_withdrawal_utxos` returns both `(i, payout_txid)` and `(j, payout_txid)`, and `update_payout_txs_and_payer_operator_xonly_pk` writes the same `payout_txid`/`operator_xonly_pk` into both `withdrawals` rows.
6. Downstream reimbursement logic (`PayoutCheckerTask`/`handle_finalized_payout`) treats both `i` and `j` as legitimately paid out by the operator, allowing the operator to claim kickoff/Reimburse funds for both, despite having funded only one payout.

No existing guard intercepts this: `Operator::withdraw` (`core/src/operator.rs:560-627`) only checks that the input outpoint matches the DB-registered `withdrawal_utxo` for the specific index being processed (line 594-596) — it never checks whether that same outpoint is already registered under a different index. `sign_optimistic_payout` similarly only checks `is_utxo_spent` and per-index equality, not cross-index uniqueness. No uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` was found in the `withdrawals` table definition.

### Impact Explanation
An operator that fronts a single payout to satisfy withdrawal index `i` can end up being marked as having also paid withdrawal index `j`, entitling it to claim reimbursement (via kickoff/Reimburse) for a payout it never separately funded. This is a credit-to-the-wrong-party bug matching the Critical category "an operator reimbursed for a payout it never funded." The blast radius depends on how many withdrawal indices an attacker can register with a colliding outpoint before either is spent, and applies per operator that processes the colliding withdrawal.

### Likelihood Explanation
Exploitability hinges entirely on whether the Citrea Bridge contract's `withdraw`/`safeWithdraw` accepts the same `input_outpoint` bytes for two separate withdrawal registrations before either is spent on Bitcoin — a precondition about Citrea contract behavior that is outside this repository and not verified here. If that precondition holds, the attacker needs only to control a taproot-keypath UTXO and repeat the `withdraw` call twice with the same outpoint; no verifier/operator/aggregator privilege is required. I could not fully verify the exact SQL text of `get_payout_txs_for_withdrawal_utxos` in `core/src/database/verifier.rs` within the available tool budget, nor the full `withdrawals` table schema/constraints, so the precise absence of any `idx`-scoping or uniqueness constraint is taken from the question's characterization and the confirmed lack of a dedup check in `update_withdrawal_utxo_from_citrea_withdrawal`.

### Recommendation
Scope the join in `get_payout_txs_for_withdrawal_utxos` to also match on the specific `withdrawals.idx` being checked (i.e., select per-idx and verify the specific outpoint for that idx is in `bitcoin_syncer_spent_utxos`, rather than a plain equi-join on `(txid, vout)` alone), and additionally enforce a DB-level uniqueness constraint (or an explicit check in `update_withdrawal_utxo_from_citrea_withdrawal`) preventing two different `idx` values from ever sharing the same `(withdrawal_utxo_txid, withdrawal_utxo_vout)`.

async fn test_duplicate_withdrawal_utxo_only_credits_one_idx() {

    assert_eq!(rows.len(), 1, "one spent UTXO must not credit two withdrawal indices");

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

        Ok(())
    }
