### Title
`ThresholdKeys` accepts a secret share inconsistent with its verification shares, enabling crafted key bytes to misblame/DoS an honest signer - (File: crypto/dkg/src/lib.rs)

### Summary
Every legitimate producer of `ThresholdKeys` (the dealer in `crypto/dkg/dealer`, PedPoP in `crypto/dkg/pedpop`, MuSig in `crypto/dkg/musig`) establishes the invariant `C::generator() * secret_share == verification_shares[i]` — either by construction or by explicit verification. `ThresholdKeys::new` — the single constructor also used by `ThresholdKeys::read`, which is fed attacker-controlled bytes — performs structural checks (share count, participant range, interpolation applicability) but never checks that the caller's own `secret_share` corresponds to `verification_shares[params.i()]`. This is the analog of the CVE-2026-33915 bug class: a security-relevant consistency/authorization check that all sibling paths enforce is missing on one entry point reachable with untrusted input.

### Finding Description
`ThresholdKeys::new` validates `verification_shares.len() == n`, that every participant index is `<= n`, and that `Constant` interpolation is only used when `t == n` — then derives `group_key` purely from the verification shares of participants `1..=t`: [1](#0-0) 

It never verifies `self.core.secret_share` against `verification_shares[params.i()]`. `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) deserializes `t`, `n`, `i`, interpolation coefficients, `secret_share`, and `n` verification shares directly from a byte stream and hands them to `ThresholdKeys::new`, so an attacker who can feed serialized `ThresholdKeys` bytes to a signer controls a secret share that does not match any verification share.

Downstream, `ThresholdKeys::view` happily interpolates this wrong `secret_share` and scales the honest verification shares: [2](#0-1) 

FROST `sign` then produces a signature share from this inconsistent secret share (`crypto/frost/src/sign.rs:283-411`), and `complete` runs `verify_share` against `self.view.verification_share(*l)` for every included participant — including the victim — blaming `params.i()` with `FrostError::InvalidShare` when the crafted secret share's statement fails: [3](#0-2) 

### Impact Explanation
A signer loaded with crafted `ThresholdKeys` bytes (via `ThresholdKeys::read`, one of the listed attacker-reachable deserialization APIs) deterministically produces an invalid signature share under their own `Participant` index while every other signer verifies correctly. In Serai's coordinator flow, an invalid FROST share from a participant is treated as attributable misbehavior (blame/fatal-slash path in `coordinator/src/tributary/signing_protocol.rs` and `handle.rs`), so a victim that imports attacker-influenced key material is reliably self-incriminated: the session fails and the blame is pinned on the victim, not the attacker. The error path even acknowledges the precondition ("The only known way to cause this... is to deserialize a semantically invalid FrostKeys", `crypto/frost/src/sign.rs:491-494`), confirming the constructor was expected to reject such keys. The missing check converts malformed persisted/provisioned key bytes into a liveness failure plus wrongful attribution, fitting the Medium band: authenticated-but-unauthorized input produces a state change (slashing/blame of an honest participant) no other route permits.

### Likelihood Explanation
Requires an attacker to influence the bytes passed to `ThresholdKeys::read` (e.g., a provisioned/restored key file, coordinated DKG output material, or any channel shipping serialized `ThresholdKeys` between components). This is within the stated scope (untrusted bytes fed to `ThresholdKeys::read`) but is not reachable purely from a single public network message; the exploit then triggers deterministically on the next signing attempt. Exploitation does not require collusion, a malicious validator, or leaked keys — only the missing consistency check.

### Recommendation
In `ThresholdKeys::new`, after the existing structural checks, verify `C::generator() * *secret_share == verification_shares[&params.i()]` and return a `DkgError` on mismatch (variable-time/`multiexp_vartime` is acceptable since verification shares are public, though the secret share is secret — use a constant-time scalar mul to be safe). This closes the gap so `ThresholdKeys::read` cannot instantiate semantically invalid keys, matching the invariant every legitimate key-generation path already establishes.

### Proof of Concept
Conceptual reproduction:

1. Serialize a valid `ThresholdKeys<C>` for params `(t=2, n=3, i=1)`, then mutate the `secret_share` field in the byte stream (offset after the ciphersuite ID, `t`, `n`, `i`, and interpolation tag/coefficients) to a different scalar `s'`, leaving `verification_shares` untouched.
2. `ThresholdKeys::<C>::read(&mut bytes)` succeeds — `ThresholdKeys::new` performs no `G * s' == verification_shares[1]` check (`crypto/dkg/src/lib.rs:349-391, 618-631`).
3. Build an `AlgorithmMachine::new(algorithm, crafted_keys)`, run `preprocess`, then `sign(preprocesses, msg)` with `included = {1,2}`. The victim emits `SignatureShare(s'_interpolated + nonce)` which does not satisfy `G * share == verification_share_1 + ...` statements in `verify_share`.
4. `complete` collects shares, `algorithm.verify` fails on the aggregate, and the batch blame loop reports `FrostError::InvalidShare(Participant(1))` — the honest victim — because their secret share never matched their verification share. In the coordinator this is the attributable-fault path that would justify slashing participant 1 for a fault injected by the attacker who supplied the bytes.

  pub fn new(
    params: ThresholdParams,
    interpolation: Interpolation<C::F>,
    secret_share: Zeroizing<C::F>,
    verification_shares: HashMap<Participant, C::G>,
  ) -> Result<ThresholdKeys<C>, DkgError> {
    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }

  fn complete(
    self,
    mut shares: HashMap<Participant, SignatureShare<C>>,
  ) -> Result<A::Signature, FrostError> {
    let params = self.params.multisig_params();
    validate_map(&shares, self.view.included(), params.i())?;

    let mut responses = HashMap::new();
    responses.insert(params.i(), self.share);
    let mut sum = self.share;
    for (l, share) in shares.drain() {
      responses.insert(l, share.0);
      sum += share.0;
    }

    // Perform signature validation instead of individual share validation
    // For the success route, which should be much more frequent, this should be faster
    // It also acts as an integrity check of this library's signing function
    if let Some(sig) = self.params.algorithm.verify(self.view.group_key(), &self.Rs, sum) {
      return Ok(sig);
    }

    // We could remove blame_entropy by taking in an RNG here
    // Considering we don't need any RNG for a valid signature, and we only use the RNG here for
    // performance reasons, it doesn't feel worthwhile to include as an argument to every
    // implementor of the trait
    let mut rng = ChaCha20Rng::from_seed(self.blame_entropy);
    let mut batch = BatchVerifier::new(self.view.included().len());
    for l in self.view.included() {
      if let Ok(statements) = self.params.algorithm.verify_share(
        self.view.verification_share(*l),
        &self.B.bound(*l),
        responses[l],
      ) {
        batch.queue(&mut rng, *l, statements);
      } else {
        Err(FrostError::InvalidShare(*l))?;
      }
    }

    if let Err(l) = batch.verify_vartime_with_vartime_blame() {
      Err(FrostError::InvalidShare(l))?;
    }

    // If everyone has a valid share, and there were enough participants, this should've worked
    // The only known way to cause this, for valid parameters/algorithms, is to deserialize a
    // semantically invalid FrostKeys
    Err(FrostError::InternalError("everyone had a valid share yet the signature was still invalid"))
  }
