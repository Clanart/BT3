### Title
Excess Native-Token Payment for POST/GET Dispatch Is Trapped in `EvmHost` Instead of Being Refunded to the Caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all convert user-supplied native tokens (`msg.value`) into the protocol fee token via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. ### Finding Description
`swapETHForExactTokens` is an "exact-output" swap: the caller specifies exactly how many fee tokens must come out (`post.fee` / `get.fee` / `amount`), and sends `msg.value` as an *upper bound* on the ETH to spend. Per the standard UniswapV2Router02 semantics, any ETH sent beyond what the pool actually needs to produce the exact output is refunded — but that refund goes to `msg.sender` **of the router call**, which here is `EvmHost` itself, not the original external caller (`_msgSender()` / `post.payer`) who funded the transaction.

Because none of the three call sites capture or forward this refund, any ETH a caller overpays (which is unavoidable in practice, since the caller must estimate the required ETH off-chain via `quote()` before the pool price moves, and typically pads `msg.value` for safety) is silently absorbed into the `EvmHost` contract's native balance rather than returned to the payer. There is no accounting of native token balances in `EvmHost`, and no user-facing mechanism to reclaim this stranded ETH. This is the direct structural analog of the reported M-08 pattern: a value-moving cross-chain operation (fee payment for dispatch) that lacks the counterpart bound/refund guarantee (`minOut` in M-08; ETH refund-to-payer here) that exists for the "increase" side of the same operation but not the corresponding leg, causing execution at a de facto unfavorable price for the user with no path to recovery.

Unlike the M-08 report where the missing guard was `minOut`, here the router already protects against paying "too much" for the exact tokens up to `msg.value`, but the protocol fails to complete the equivalent obligation: returning unspent value to its rightful owner. This is not a matter of price manipulation risk from the AMM itself (the exact-output swap already bounds the price the user pays up to `msg.value`), but a fund-custody defect: value legitimately belonging to the payer is misdirected to the contract instead of the payer.

### Impact Explanation
Every unprivileged caller who dispatches a POST/GET request or funds an existing request with native token payment loses any ETH sent above the amount the AMM actually consumed. This is a direct, permanent loss of user funds triggered purely through the normal, documented usage path (native-token fee payment), requiring no malicious relayer, prover, or governance actor — matching the bounty's "stealing or loss of funds" impact category.

### Likelihood Explanation
Likelihood is high: the documentation explicitly recommends estimating fees off-chain via `quote()` before submitting a transaction with `msg.value`, and AMM prices move between quote time and execution time (plus users commonly add a safety buffer to `msg.value` to avoid reverts from underpayment). Every such normal-usage transaction that overpays by even 1 wei permanently strands that ETH in `EvmHost`, with no built-in refund or sweep path back to the payer.

### Recommendation
Track the ETH balance of `EvmHost` before and after the `swapETHForExactTokens` call (or read the router's return array, which reports actual ETH spent) and refund the difference to `_msgSender()` (or `post.payer`/the originating caller) at the end of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, mirroring how relayer fees are refunded elsewhere in the contract on timeout paths.

### Proof of Concept
1. Attacker/user calls `quote(DispatchPost)` off-chain, gets an ETH amount `X` needed for `post.fee` fee tokens at the current pool price.
2. To avoid a revert from a small price move before their transaction lands, the user sends `msg.value = X + buffer` to `dispatch(DispatchPost)`.
3. `EvmHost.dispatch` calls `swapETHForExactTokens{value: X + buffer}(post.fee, path, address(this), block.timestamp)`.
4. The router consumes only the ETH needed (say `Y <= X + buffer`) to produce exactly `post.fee` tokens, and refunds `(X + buffer) - Y` ETH to `msg.sender` of the swap call, i.e., `EvmHost`.
5. `EvmHost` never forwards this refunded ETH back to the user; it accumulates in the contract's native balance with no accounting or user-recovery mechanism, resulting in a permanent loss of the buffer amount for every such caller.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
