### Title
`SignableTransaction::new` excludes the `OP_RETURN` data output from the fee/weight calculation, producing underpriced transactions whose funds become stuck - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` accepts an optional `data` payload that is embedded as an `OP_RETURN` output. The output is appended to `tx_outs`, but the fee computation calls `calculate_weight_vbytes(tx_ins.len(), payments, …)` — using only `payments`, never the data output. The weight/vbytes, and therefore `needed_fee`, are computed for a transaction smaller than the one actually signed. Analogous to the reference bug (the router accounts only for the `amount` argument while ignoring the attached value), the fee accounting ignores one of the value-carrying parameters, so the actual transaction can fall below the requested fee rate — and even below the Bitcoin minimum relay fee — leaving the transaction unrelayable and the inputs' funds trapped.

### Finding Description
In `SignableTransaction::new`:

1. The `OP_RETURN` output is pushed onto `tx_outs` before any fee computation (`networks/bitcoin/src/wallet/send.rs:194-202`).
2. The initial fee is computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204. `calculate_weight_vbytes` builds a dummy `Transaction` whose `output` list is constructed *only* from `payments` (lines 85-93) plus an optional change placeholder (lines 95-99). The data output is never represented.
3. `needed_fee = fee_per_vbyte * vbytes` (line 206) therefore reflects a transaction missing the data output (~up to 91 bytes: 1-byte value, script length, `OP_RETURN` + push of up to 80 bytes, checked at line 171).
4. The minimum-relay-floor check at line 211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) uses the same underestimated `vbytes`, so it cannot detect that the *real* transaction fails the floor.
5. The same omission occurs for the change path: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` at line 226 also ignores `data`, so `fee_with_change` is underestimated, and `input_sat.checked_sub(payment_sat + fee_with_change)` (line 228) can credit the change output with value that is actually consumed by the real (larger) transaction's fee requirement.

The signed transaction (`sign()` at lines 373-397) commits via `Prevouts::All` to the prevouts and to the real, larger `self.tx.tx`, so the produced signature is valid — the fee is simply short. The effective fee rate is `needed_fee / actual_vsize < fee_per_vbyte`, and can drop below `DEFAULT_MIN_RELAY_TX_FEE`, making the transaction non-standard for relay.

### Impact Explanation
Funds committed as inputs to a `SignableTransaction` carrying a `data` payload are priced for a smaller transaction than the one signed. The shortfall is proportional to the data size (up to ~91 vbytes' worth of fee at the requested rate). When the effective rate falls below the relay minimum, no node will propagate the transaction; the threshold-signed transaction is final (`complete` returns the signed `Transaction` at lines 417-427), so the multisig's inputs sit in an unbroadcastable transaction — the same "funds sent but not usable / trapped" outcome as the reference issue. Even when still relayable, the transaction pays a lower fee rate than the caller explicitly requested, which is a silent accounting error between two value inputs (`payments`/`data` vs. `fee_per_vbyte`).

### Likelihood Explanation
`data` is an arbitrary caller-supplied payload of up to 80 bytes (line 171). Any invocation combining `data` with `fee_per_vbyte` near the minimum relay floor produces a transaction whose actual fee rate is below the intended rate and potentially below the relay floor. The bug is deterministic — it requires no adversary beyond the party supplying the `data` bytes (a public input per the threat model) — and triggers on every `SignableTransaction::new` call with non-empty `data`.

### Recommendation
Include the data output in the weight/vbytes calculation. `calculate_weight_vbytes` should take the fully materialized `tx_outs` (payments + `OP_RETURN` + optional change) rather than reconstructing outputs from `payments` alone, e.g. compute `needed_fee` after `tx_outs` is finalized, and recompute `vbytes` with the change output present when evaluating `fee_with_change`. Alternatively, build the candidate `Transaction` once and derive both weight variants from it.

### Proof of Concept
```rust
// In SignableTransaction::new (networks/bitcoin/src/wallet/send.rs):
// tx_outs gains an OP_RETURN output at lines 194-202
// but vbytes is computed from `payments` only at line 204:
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;

// PoC: construct inputs, payments, change=None, data=Some(vec![0xAA; 80]),
// fee_per_vbyte chosen so fee_per_vbyte * vbytes_no_data just passes the
// DEFAULT_MIN_RELAY_TX_FEE floor check at line 211.
let tx = SignableTransaction::new(inputs, &payments, None, Some(vec![0xAA; 80]), fee_rate).unwrap();

// The real transaction includes the OP_RETURN output (~91 extra bytes).
let real_vsize = tx.transaction().vsize() as u64; // includes data output
let paid = tx.needed_fee();                        // computed for smaller tx

// paid / real_vsize < fee_rate, and paid < DEFAULT_MIN_RELAY_TX_FEE * real_vsize / 1000
assert!(paid < real_vsize * fee_rate);                        // underpaid vs. requested rate
assert!(paid < (DEFAULT_MIN_RELAY_TX_FEE as u64) * real_vsize / 1000); // below relay floor
```
With `change` set, the change output's value is additionally overstated by the unpriced data-output fee (lines 226-230), compounding the underpayment.
