## Analysis

The H-02 bug class is: a value that legitimately needs to be scoped/indexed by an entity identifier (`marketIndex`) is instead stored/looked-up using a narrower key, so records belonging to different entities collide and overwrite each other.

The `shopify_app` codebase has a direct structural analog in its **online (per-user) session storage**.

### Root cause

`ShopifyApp::UserSessionStorage.store` persists a user's access token keyed **only** by `shopify_user_id`, with no shop-domain component in the lookup key: [1](#0-0) 

`retrieve_by_shopify_user_id` mirrors this — it fetches a session by `shopify_user_id` alone, again with no shop qualifier: [2](#0-1) 

`ShopifyApp::SessionRepository#load_session`, used by both `LoginProtection#load_current_session` and `TokenExchange#current_shopify_session`, actively **discards the shop-domain part** of the composite session id (`"<shop>_<user_id>"`) and resolves the session using only the trailing user-id fragment: [3](#0-2) 

Because Shopify's per-user (online) `associated_user.id` is the underlying Shopify staff-account id and stays constant for that person across every shop they have staff access to (a common situation for agency/collaborator staff and Plus organizations), two different shops authenticating the *same* staff person will `find_or_initialize_by(shopify_user_id: user.id)` on the **same** row. The second shop's OAuth/token-exchange completion silently overwrites the first shop's `shopify_domain` and `shopify_token` on that row — exactly the "value overwritten by a different market/shop because the composite key collapsed to a single component" pattern from H-02.

### Why this is reachable and impactful

- `TokenExchange#activate_shopify_session` only rejects a domain mismatch when a `shop` request param is present (`reject_mismatched_requested_shopify_domain` returns `false` early otherwise): [4](#0-3) 
Many authenticated App Bridge/JWT-only API calls from the embedded app do not carry a `shop` param, so this guard is not always applied.
- `LoginProtection#login_again_if_different_user_or_shop` provides the same kind of mismatch check, but it is opt-in and only triggered when `params[:shop]` is present: [5](#0-4) 

So once the row is overwritten, any subsequent request resolved via `retrieve_by_shopify_user_id` (i.e., via `load_session`) for that same staff user, on requests that don't pass an explicit `shop` param, activates the *other* shop's session/access token — `ShopifyAPI::Context.activate_session(current_shopify_session)` runs with the wrong shop and wrong token.

### Title
Online user-session storage keyed only by `shopify_user_id` (not scoped by shop) allows cross-shop session/token overwrite - ([File: lib/shopify_app/session/user_session_storage.rb])

### Summary
`UserSessionStorage.store`/`retrieve_by_shopify_user_id` treat `shopify_user_id` as a unique key without also scoping by `shopify_domain`. `SessionRepository.load_session` compounds this by discarding the shop-domain prefix of the session id and looking the session up purely by the trailing user-id. This mirrors the H-02 bug class of using an under-indexed key for a value that is actually per-entity (per-shop) scoped.

### Finding Description
When a Shopify staff account (same underlying `associated_user.id`) completes OAuth/token-exchange on Shop A and later on Shop B, `store(auth_session, user)` does `find_or_initialize_by(shopify_user_id: user.id)` [6](#0-5)  and overwrites the single row's `shopify_domain`/`shopify_token` with Shop B's values. The row is never partitioned by shop. Later, any request that resolves its session through `SessionRepository.load_session` — which strips the shop prefix and resolves solely via `retrieve_user_session_by_shopify_user_id` [7](#0-6)  — will load Shop B's session/token even though the originating request/JWT is for Shop A.

### Impact Explanation
This causes cross-shop token confusion: an app request intended for Shop A can be activated with Shop B's access token and shop context (`ShopifyAPI::Context.activate_session`), leading to actions/data access against the wrong merchant's shop and potential disclosure of one merchant's data/token usage in the context of another merchant's session. This is a cross-shop access issue directly analogous to the confirmed H-02 finding.

### Likelihood Explanation
Requires a staff/collaborator account with access to two shops using the app with online (per-user) tokens enabled (`user_session_repository` configured) — a realistic setup for agencies, Shopify Plus organizations, and app-store collaborator staff. Exploitation additionally requires a request path that resolves sessions without an explicit `shop` param check (e.g., pure JWT/App Bridge session-token calls), which the guards in `TokenExchange` and `LoginProtection` do not universally enforce.

### Recommendation
Scope the online session storage's uniqueness/lookup key by both `shopify_user_id` and `shopify_domain` (e.g., unique index on `[shopify_user_id, shopify_domain]`), and change `SessionRepository.load_session`/`retrieve_user_session_by_shopify_user_id` to require and validate the shop-domain component of the session id rather than discarding it.

### Proof of Concept
1. Configure the app with `user_session_repository` enabled (per-user/online tokens).
2. Staff user U installs/authorizes the app on Shop A → `UserSessionStorage.store` creates row `{shopify_user_id: U, shopify_domain: "shop-a.myshopify.com", shopify_token: TOKEN_A}`.
3. The same staff user U (same underlying Shopify staff id) later authorizes the app on Shop B → `store` finds the same row via `find_or_initialize_by(shopify_user_id: U)` and overwrites it to `{shopify_domain: "shop-b.myshopify.com", shopify_token: TOKEN_B}`.
4. A subsequent authenticated request tied to Shop A's session id (e.g. `"shop-a.myshopify.com_U"`) hits `SessionRepository.load_session`, which strips the prefix to `U` and calls `retrieve_user_session_by_shopify_user_id(U)`, returning the row now pointing at Shop B with `TOKEN_B`.
5. If the request path doesn't pass an explicit `shop` param (common for JWT/App-Bridge XHR calls), no mismatch guard fires, and the app activates Shop B's session/token in what should be a Shop A context.
