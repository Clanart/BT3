## Title
`CompactBitArray.UnmarshalJSON` nil-pointer dereference on 0-bit input causes node panic - (File: sei-cosmos/crypto/types/compact_bit_array.go)

### Summary
`sei-cosmos`'s `CompactBitArray` reimplements the exact bug class fixed upstream in cometbft's `BitArray.UnmarshalJSON` (cometbft/cometbft#2774): `NewCompactBitArray(<=0)` returns `nil`, but `UnmarshalJSON` unconditionally dereferences the value it constructs.

### Finding Description
`NewCompactBitArray` explicitly returns `nil` whenever `bits <= 0`: [1](#0-0) 

`CompactBitArray.UnmarshalJSON` parses the custom `"xxx_"`-style string format, computes `numBits := len(bits)` from the matched string, calls `NewCompactBitArray(numBits)`, and then unconditionally dereferences the result with `*bA = *bA2`: [2](#0-1) 

If the JSON payload is the empty string `""` (a value that is valid against `bitArrayJSONRegexp` since it matches zero or more `[_x]` characters), `numBits` is `0`, `NewCompactBitArray(0)` returns `nil`, and `*bA = *bA2` dereferences a nil pointer, causing a runtime panic. This is exactly the bug class described in the report for cometbft's `BitArray.UnmarshalJSON`.

`CompactBitArray` backs the multisig `Data_Multi.Bitarray` field used for `MultiSignatureData` and is serialized/deserialized through the SDK's legacy Amino JSON signature path, e.g. `StdTxConfig.UnmarshalSignatureJSON` → `StdSignatureToSignatureV2` → `pubKeySigToSigData`, which reads `multiSig.BitArray`: [3](#0-2) [4](#0-3) 

More directly, the type itself implements `json.Unmarshaler`, so any JSON path (Amino JSON tx broadcast payloads, genesis parsing, or any RPC/API surface that JSON-decodes a `CompactBitArray`, e.g. as part of a multisig `MultiSignatureData`) that feeds attacker-controlled bytes into this method can trigger the crash.

### Impact Explanation
A crash triggered by JSON-decoding a `CompactBitArray` in a public-facing code path (legacy Amino JSON tx submission/broadcast, or any REST/RPC endpoint accepting a JSON-encoded multisig signature/tx) causes a runtime nil-pointer-dereference panic. Depending on whether the panic is caught by a recover() at a higher layer (e.g. ante handler / mempool checkTx recovery) or not, this can crash the node process handling the request, which for a public RPC node constitutes a denial-of-service / node-halt condition.

### Likelihood Explanation
The trigger is a single, syntactically valid JSON string (`""`) for a field that is explicitly documented and exercised in legacy Amino JSON code (multisig `bitarray` field). No privileged access, special key material, or complex setup is required — only a JSON payload with an empty bitarray string reaching `CompactBitArray.UnmarshalJSON`.

### Recommendation
Mirror the upstream cometbft fix: in `CompactBitArray.UnmarshalJSON`, handle the case where `numBits == 0` explicitly (e.g. by resetting `bA.ExtraBitsStored = 0; bA.Elems = nil` similar to the `"null"` branch) instead of unconditionally constructing via `NewCompactBitArray` and dereferencing the result, since `NewCompactBitArray` can return `nil`.

### Proof of Concept
```go
package main

import (
	"fmt"
	cryptotypes "github.com/sei-protocol/sei-chain/sei-cosmos/crypto/types"
)

func main() {
	ba := &cryptotypes.CompactBitArray{}
	// A syntactically valid, zero-bit encoding for the custom bitarray JSON format.
	err := ba.UnmarshalJSON([]byte(`""`))
	fmt.Println(err) // panic: nil pointer dereference occurs before this line
}
```
Any JSON payload containing `"bitarray":""` inside a `MultiSignatureData`/legacy Amino tx signature that is JSON-unmarshaled through this type will panic in the same way as the original `NewBitArray(<=0)` bug in cometbft.
