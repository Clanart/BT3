### Title
Unbounded DID Metadata Length Leading to Local Resource-Exhaustion / Transaction-Processing Halt via `did_update_metadata` RPC - ([File: chia/wallet/did_wallet/did_wallet.py])

### Summary
The `did_update_metadata` wallet RPC endpoint accepts an arbitrary-size `dict[str, str]` metadata payload with no length or size validation, unlike other user-supplied strings in the same codebase (e.g. keychain labels, which are capped at `MAX_LABEL_LENGTH = 65`, or notification messages, which are capped at 10KB in `NotificationManager.potentially_add_new_notification`). A local, authenticated RPC caller (the same threat actor the Joplin CVE targets — one with a compromised/leaked RPC auth token or CLI access) can submit an excessively large metadata string, which `DIDWallet.update_metadata` stores verbatim and which is later re-embedded into a curried CLVM inner puzzle every time the DID is used or spent.

### Finding Description
`DIDWallet.update_metadata` only validates that all metadata dict values are strings — no length or total-size check is performed: [1](#0-0) 

This differs sharply from other free-text fields in the wallet stack that do enforce bounds, such as the keyring label length check: [2](#0-1) 

and the notification message size cap: [3](#0-2) 

The RPC layer passes the raw `metadata: dict[str, str]` field straight through to the wallet without any bound: [4](#0-3) [5](#0-4) 

Once stored, this metadata string is JSON-decoded and converted into a CLVM `Program` and curried into the DID's inner puzzle **every time** the wallet needs the current inner puzzle (e.g. `get_did_innerpuz`, `create_update_spend`, or the eve/coin-spend paths): [6](#0-5) 

Because currying and tree-hashing are done locally in the wallet process **before** any consensus-level cost check or mempool admission occurs, an attacker who supplies a sufficiently large metadata blob (megabytes to gigabytes of string data) forces the wallet process to repeatedly build large CLVM programs, hash them, and serialize them to the sqlite-backed `WalletInfo`/`DIDInfo` store on every DID interaction — including background sync/derivation operations that call `get_did_innerpuz`. This is analogous to the Joplin bug class: an unbounded, user-controlled text field is accepted without a length check and later drives unbounded memory allocation/CPU work in a hot path, producing an OOM condition or extreme slowdown that can crash or hang the wallet service, i.e. a spend-triggered/RPC-triggered transaction-processing halt for that wallet.

### Impact Explanation
This maps to the "spend-triggered transaction-processing halt" class explicitly listed as acceptable impact. A successful attack renders the victim's wallet service unresponsive or causes it to be OOM-killed, which halts the wallet's ability to process transactions, sync, and serve RPC calls until manually recovered — a local Denial-of-Service against the wallet node. This does not affect other honest nodes' consensus state; the impact is confined to the local wallet, consistent with the "local RPC caller" reachability class in the report’s allowed set. There is no coin-forging, no inflation, and no offer-theft implication.

### Likelihood Explanation
Likelihood is Medium: the endpoint is reachable by any caller holding the wallet RPC's bearer/cert credential (an already-authenticated local RPC caller, matching the Joplin threat model of a "compromised auth token"). No additional privilege escalation is required once RPC access is obtained, and the vulnerable code path (`update_metadata` → `create_update_spend` / `get_did_innerpuz`) is exercised on nearly every DID operation, including passive derivation/sync paths, increasing the number of opportunities to trigger repeated large currying/hashing operations.

### Recommendation
Add an explicit maximum size check on the DID metadata (both per-key value length and aggregate JSON-serialized size) in `DIDWallet.update_metadata`, mirroring the bound already used for keychain labels (`MAX_LABEL_LENGTH`) and notification messages (10KB cap in `NotificationManager`). Reject the RPC request early in `did_update_metadata` (`chia/wallet/wallet_rpc_api.py`) before any currying/puzzle construction occurs, and consider also bounding total metadata size in `DIDUpdateMetadata`'s streamable definition so oversized payloads are rejected during deserialization rather than after being persisted.

### Proof of Concept
1. Start a `chia-blockchain` wallet with RPC enabled and obtain a valid RPC certificate/token (simulating a compromised auth token, per the CVE's threat model).
2. Create a DID wallet.
3. Call the `did_update_metadata` RPC with a metadata dict containing a single key whose value is a very large string, e.g.:
   ```json
   {"wallet_id": <did_wallet_id>, "metadata": {"note": "<multi-hundred-MB string>"}}
   ```
4. Observe that `DIDWallet.update_metadata` (chia/wallet/did_wallet/did_wallet.py:1207) accepts this metadata without any length check, persists it via `save_info`, and that subsequent calls (including `create_update_spend` and background `get_did_innerpuz` calls during sync) repeatedly curry/hash this oversized string into a CLVM `Program`, spiking memory/CPU. With a sufficiently large payload, this leads to OOM termination or unresponsiveness of the wallet process, consistent with the reported Joplin OOM/DoS pattern.

Note: I was not able to fully trace `create_update_spend`'s exact line range in this session (only located it via `grep_search`, not fully read due to iteration limits), so the precise curry/hash call sites inside that specific function are unconfirmed beyond `get_did_innerpuz`; however, the metadata-to-puzzle conversion at chia/wallet/did_wallet/did_wallet.py:1007-1015 confirms the unbounded-data-into-CLVM-currying pattern that drives the impact.

    async def update_metadata(self, metadata: dict[str, str]) -> bool:
        # validate metadata
        if not all(isinstance(v, str) for v in metadata.values()):
            raise ValueError("Metadata key value pairs must be strings.")
        did_info = DIDInfo(
            origin_coin=self.did_info.origin_coin,
            backup_ids=self.did_info.backup_ids,
            num_of_backup_ids_needed=self.did_info.num_of_backup_ids_needed,
            parent_info=self.did_info.parent_info,
            current_inner=self.did_info.current_inner,
            temp_coin=self.did_info.temp_coin,
            temp_puzhash=self.did_info.temp_puzhash,
            temp_pubkey=self.did_info.temp_pubkey,
            sent_recovery_transaction=self.did_info.sent_recovery_transaction,
            metadata=json.dumps(metadata),
        )
        await self.save_info(did_info)
        await self.wallet_state_manager.update_wallet_puzzle_hashes(self.wallet_info.id)
        return True

        """
        Set a label for the given fingerprint. This will force a write to keyring.yaml on success.

        # First validate the label
        stripped_label = label.strip()
        if len(stripped_label) == 0:

        if len(stripped_label) != len(label):
            raise KeychainLabelInvalid(label, "label can't contain leading or trailing whitespaces")

            raise KeychainLabelInvalid(label, "label can't contain newline or tab")
        if len(label) > MAX_LABEL_LENGTH:
            raise KeychainLabelInvalid(label, f"label exceeds max length: {len(label)}/{MAX_LABEL_LENGTH}")

    async def did_update_metadata(
        self,
        request: DIDUpdateMetadata,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> DIDUpdateMetadataResponse:
        wallet = self.service.wallet_state_manager.get_wallet(id=request.wallet_id, required_type=DIDWallet)
        async with self.service.wallet_state_manager.lock:
            # Update coin with new ID info
            await wallet.update_metadata(request.metadata)
            await wallet.create_update_spend(action_scope, request.fee, extra_conditions=extra_conditions)
            # tx_endpoint wrapper will take care of these default values
            return DIDUpdateMetadataResponse(
                unsigned_transactions=[],
                transactions=[],
                wallet_id=request.wallet_id,
                spend_bundle=WalletSpendBundle([], G2Element()),
            )
