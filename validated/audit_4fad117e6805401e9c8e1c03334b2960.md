Confirmed: `blockCtx.Transfer = core.Transfer` uses standard go-ethereum semantics — for any `CALL` with `value > 0`, geth's `evm.Call()` performs the native balance transfer from caller to callee (via `evm.Context.Transfer`) **before** invoking the target's code/precompile `Run`. This happens regardless of whether the target is a precompiled contract, since precompile dispatch happens after the transfer step in the standard `Call` flow.

Cross-checking the precompile implementations: only `precompiles/erc20/erc20.go` explicitly guards against this (`Execute` rejects `contract.Value() > 0`), and `precompiles/werc20` intentionally accepts value and immediately returns it via `Deposit`. However, `precompiles/staking`, `precompiles/distribution`, `precompiles/gov`, `precompiles/bank`, `precompiles/ics20`, and `precompiles/slashing` (`Execute` functions shown at e.g. [1](#0-0) , [2](#0-1) , [3](#0-2) , [4](#0-3) , [5](#0-4) , [6](#0-5) ) do **not** check or reject `contract.Value()` at all.

### Title
Native token value sent to non-ERC20/WERC20 static precompiles (staking, distribution, gov, bank, ics20, slashing) is irrecoverably locked - (File: precompiles/staking/staking.go, precompiles/distribution/distribution.go, precompiles/gov/gov.go, precompiles/bank/bank.go, precompiles/ics20/ics20.go, precompiles/slashing/slashing.go)

### Summary
The external Ledger report describes funds sent directly to a contract address that has no accounting/recovery path for unsolicited deposits, causing permanent loss. Cosmos EVM's ERC20 precompile explicitly defends against this exact pattern (`ErrCannotReceiveFunds` check in `precompiles/erc20/erc20.go`), and the WERC20 precompile explicitly handles it by immediately returning received value (`precompiles/werc20/tx.go`). However, the other static precompiles — staking, distribution, gov, bank, ics20, and slashing — have no such guard.

### Finding Description
Cosmos EVM configures the EVM block context with the stock go-ethereum `core.Transfer` function: [7](#0-6) . Under standard EVM `CALL` semantics, when a caller sends a call with `value > 0` to an address, the native balance transfer to that address executes as part of the call mechanics before the callee's code (or, for precompiles, `Run`) is invoked. This means a caller can attach `msg.value` to any call targeting one of the static precompile addresses (e.g. `0x...800` staking, `0x...801` distribution, `0x...802` ics20, `0x...804` bank, `0x...805` gov, `0x...806` slashing — addresses listed in [8](#0-7) ) and have that value credited to the precompile's account balance regardless of whether the called method's execution succeeds or is even payable in intent.

None of these precompiles' `Execute` functions check `contract.Value()`, unlike `precompiles/erc20/erc20.go` lines 148-155, which explicitly rejects any call carrying value: [9](#0-8) . The WERC20 precompile is the only one designed to legitimately accept value, and it immediately forwards it back to the caller via `BankKeeper.SendCoins`: [10](#0-9) .

Since these static precompile addresses are not EOA-controlled and have no `Deposit`/`Withdraw`-equivalent recovery mechanism, any native token value attached to a call reaching one of them becomes permanently held under that hex address in the bank/precisebank ledger, with no method in the module's ABI capable of moving it out again. This is functionally identical to the Ledger analog: funds sent to a contract-like account with no accounting hook to reclaim them.

### Impact Explanation
This falls under "Critical permanent freezing, locking, theft, or unauthorized extraction of user funds" per the allowed impact gate. Native EVM token value routed to these precompile addresses is permanently removed from circulation for the sender with no recovery path — it is not stolen by an attacker but irreversibly and unintentionally destroyed/locked from the user's perspective, and it also silently distorts the effective circulating/spendable supply since the precompile address holds a real spendable bank balance nobody can withdraw.

### Likelihood Explanation
Triggering this requires no privilege: any unprivileged EOA or contract can construct a low-level `CALL` (e.g., via `address(precompile).call{value: X}(data)` in Solidity, or a raw JSON-RPC `eth_sendRawTransaction`) targeting a static precompile address with a nonzero `value`. This can happen accidentally (developer error assuming all Cosmos EVM precompiles behave like WERC20/payable wrappers) or be induced by a malicious contract tricking a user into interacting with a precompile through a payable call path. No special conditions or governance actions are required.

### Recommendation
Add a `contract.Value().Sign() == 1` (or equivalent) rejection check to the `Execute` methods of the staking, distribution, gov, bank, ics20, and slashing precompiles — mirroring the guard already present in `precompiles/erc20/erc20.go` — so that calls to any static precompile which is not designed to accept value (i.e., all except WERC20) revert instead of silently absorbing and stranding the native token balance. Alternatively, centralize this check in the shared `precompiles/common/precompile.go` `RunNativeAction`/`runNativeAction` path so all non-payable precompiles get the protection uniformly, with an explicit opt-out for WERC20.

### Proof of Concept
1. Deploy or use any contract, or send directly from an EOA, a raw call: `target = 0x0000000000000000000000000000000000000800` (staking precompile), with `data` encoding a valid method (e.g., `delegate(...)`) and `value = 1 ether`.
2. Because `blockCtx.Transfer = core.Transfer` executes standard value transfer semantics before the precompile's `Run`/`Execute` is invoked, and `precompiles/staking/staking.go`'s `Execute` ( [11](#0-10) ) never inspects `contract.Value()`, the 1 ether native balance is credited to the staking precompile's address in the underlying bank ledger regardless of whether `delegate` succeeds.
3. Query the bank balance of the staking precompile address (`0x...800`) after the transaction — it now holds the attached value with no ABI method available to move it elsewhere, permanently locking the sender's funds.

**Note on verification confidence:** I was not able to directly trace through the vendored go-ethereum `core.Transfer`/`Call` implementation in this repository (it comes from the go-ethereum dependency, not local source) to triple-confirm that value transfer executes unconditionally before precompile dispatch in this specific EVM fork's `Call` path. This is standard, well-documented go-ethereum behavior, but if this codebase forked/patched `core/vm/evm.go`'s `Call` to skip transfer for precompile targets, the finding would not hold. I recommend a background agent trace `github.com/ethereum/go-ethereum/core/vm/evm.go`'s `Call` function as vendored/replaced in this repo's `go.mod` to confirm this precondition before treating this as fully verified.

// Deposit handles the payable deposit function. It retrieves the deposited amount
// and sends it back to the sender using the bank keeper.
func (p Precompile) Deposit(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
) ([]byte, error) {
	caller := contract.Caller()
	depositedAmount := contract.Value()

	callerAccAddress := sdk.AccAddress(caller.Bytes())
	precompileAccAddr := sdk.AccAddress(p.Address().Bytes())

	// Send the coins back to the sender
	if err := p.BankKeeper.SendCoins(
		ctx,
		precompileAccAddr,
		callerAccAddress,
		sdk.NewCoins(sdk.Coin{
			Denom:  evmtypes.GetEVMCoinExtendedDenom(),
			Amount: math.NewIntFromBigInt(depositedAmount.ToBig()),
		}),
	); err != nil {
		return nil, err
	}

	if err := p.EmitDepositEvent(ctx, stateDB, caller, depositedAmount.ToBig()); err != nil {
		return nil, err
	}

	return nil, nil
}
