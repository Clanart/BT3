### Title
BIP-340 signatures are generated with the wrong key-parity formula - ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
`Hram::hram` negates the challenge when the nonce point `R` has odd Y, but BIP-340 requires the effective private key—and therefore the challenge contribution—to be negated when the public key `A` has odd Y. The nonce parity is already handled by negating `s` during signature serialization. This produces a valid BIP-340 signature only for some parity combinations and makes otherwise valid threshold signing sessions fail.

### Finding Description
`Hram::hram` computes the BIP-340 challenge from `x(R)`, `x(A)`, and the message, then conditionally selects `-c` when `R` has odd Y: [1](#0-0) 

The inner FROST Schnorr algorithm then produces `s = nonce + c * secret_share`: [2](#0-1) 

Finally, Bitcoin signature output negates `s` when `R` is odd: [3](#0-2) 

BIP-340 has two independent parity adjustments:

- If `R` is odd, the effective nonce is `-r`, implemented by negating `s` at the end.
- If `A` is odd, the effective private key is `-x`, which requires the challenge term applied to `x` to be negated.

The implementation instead uses `R`'s parity to decide whether to negate the challenge. For an x-only group key whose lifted point is odd, the raw secret share corresponds to the odd point while BIP-340 verification uses the even-lifted equivalent. The challenge therefore has the wrong sign whenever `A` is odd and `R` is even, and also produces the wrong combined result when both `A` and `R` are odd.

### Impact Explanation
A Bitcoin transaction supplied for threshold signing can fail to produce a valid BIP-340 signature solely because of the parity of the aggregate public key and aggregate nonce. The affected transaction commits to publicly controlled transaction data through the Taproot sighash and is signed through the normal `TransactionSignMachine` path. [4](#0-3) 

Because roughly half of possible group keys have odd lifted Y and roughly half of signing sessions have odd `R`, incorrect parity handling affects a substantial fraction of otherwise valid signing attempts. The result is a reachable signing failure for transactions spending Taproot outputs controlled by the threshold key.

### Likelihood Explanation
The bug is deterministic for three of the four `A`/`R` parity combinations under the current formula. An unprivileged party can trigger the path by causing the wallet to sign a Bitcoin transaction; they do not need key material, validator access, or malformed inputs. No control over the nonce is required because naturally occurring nonce parity is enough to trigger incorrect signatures.

### Recommendation
Track the two parity corrections independently:

1. Negate the challenge, or equivalently the private-key contribution, when `A` has odd Y.
2. Negate the final `s` when `R` has odd Y.

Conceptually, `Hram::hram` should receive or determine the parity of `A`, not `R`, while `Schnorr::verify` should continue handling only the `R` parity through final `s` negation. Add parity-matrix tests covering even/odd `A` crossed with even/odd `R`, and verify the resulting 64-byte signature under BIP-340.

### Proof of Concept
Let the raw group secret be `x` and the raw nonce be `r`, with `A = xG` odd and `R = rG` even.

- BIP-340 uses `A_even = -A`, so the expected signature is `s = r - cx`.
- The implementation leaves `c` positive because `R` is even and returns `s = r + cx`.
- Verification against `A_even` requires `sG = R + cA_even = R - cA`, but the produced signature satisfies `sG = R + cA`.

Thus the emitted signature fails even though all participants supplied correct shares.
