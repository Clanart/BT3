### Title
Missing `chain_id` in EIP-712 Domain Allows Cross-Deployment Replay of Withdrawal Verification Signatures — (`core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

`CLEMENTINE_EIP712_DOMAIN` is defined with only `name` and `version`, omitting `chain_id` and `verifying_contract`. A verification signature produced for one Clementine deployment is therefore cryptographically valid on any other deployment that shares the same aggregator ECDSA key, bypassing the intended per-deployment authorization gate on the `withdraw` and `optimistic_payout_sign` RPCs.

---

### Finding Description

**Root cause — `core/src/rpc/ecdsa_verification_sig.rs:42-45`**

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

EIP-712 mandates that `chainId` and `verifyingContract` be included in the domain separator precisely to prevent cross-chain and cross-contract replay. Without them the domain hash is identical across every Clementine deployment, regardless of Bitcoin network or bridge instance.

**Two message types exist** — `OptimisticPayoutMessage` (used by verifier `sign_optimistic_payout`) and `OperatorWithdrawalMessage` (used by operator `withdraw`). They carry identical fields: [2](#0-1) 

The proto comment acknowledges the cross-context risk and claims the different struct names prevent replay between the two flows: [3](#0-2) 

That claim is correct — EIP-712 encodes the struct type name into the type hash, so `OptimisticPayoutMessage` and `OperatorWithdrawalMessage` produce different signing hashes even for identical field values. Cross-context replay between the two flows is therefore blocked.

**What is not blocked** is cross-deployment replay. Because the domain separator contains no `chain_id` or `verifying_contract`, a signature produced for withdrawal W on deployment A is accepted verbatim by deployment B whenever both deployments share the same `aggregator_verification_address` key.

**Exploit path**

1. Aggregator signs `OperatorWithdrawalMessage{withdrawal_id, input_outpoint, …}` for operator on deployment A (e.g., a staging bridge on the same Bitcoin network as production).
2. Attacker captures the hex-encoded `verification_signature` from the gRPC call (e.g., via a compromised staging environment or a public RPC log).
3. Attacker submits the identical `WithdrawParamsWithSig` — same params, same signature — to an operator on deployment B.
4. Operator B's `withdraw` handler recovers the address from the signature using the same domain and the same struct type hash, obtains the same address, and passes the check: [4](#0-3) 

5. Operator B proceeds to execute the payout without the aggregator having authorized it for deployment B.

The verifier path (`sign_optimistic_payout`) is symmetric: [5](#0-4) 

---

### Impact Explanation

**Severity: Low**

The `aggregator_verification_address` field is **optional** (`Option<Address>`); when absent the ECDSA check is skipped entirely and the finding does not apply. [6](#0-5) 

When the check is active and bypassed via replay, the operator still independently validates the withdrawal against Citrea on-chain state (UTXO match, amount bounds, deposit existence): [7](#0-6) 

So the attacker cannot cause the operator to pay out an invalid withdrawal — they can only cause a valid withdrawal to be processed without the aggregator's per-deployment approval. The financial loss to the bridge is zero; the broken invariant is the authorization gate.

Cross-network replay (testnet4 → mainnet) is additionally blocked in practice because Bitcoin UTXOs are network-specific: the same `input_outpoint_txid` cannot exist on two different Bitcoin networks.

---

### Likelihood Explanation

Requires: (a) `aggregator_verification_address` configured on both deployments with the same key, (b) two live Clementine deployments on the same Bitcoin network, (c) attacker access to a signed message from deployment A. All three conditions must hold simultaneously, making exploitation unlikely in a standard single-deployment setup.

---

### Recommendation

Add `chain_id` (Citrea EVM chain ID, already present in config as `citrea_chain_id`) and optionally `verifying_contract` (bridge contract address) to the domain:

```rust
pub fn clementine_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
        verifying_contract: Address::from(hex!("3100000000000000000000000000000000000002")),
    }
}
```

Pass the domain built from `config.citrea_chain_id` into `eip712_signing_hash` at both call sites (`sign_optimistic_payout` in `verifier.rs` and `withdraw` in `rpc/operator.rs`). This binds every signature to a specific Citrea chain and bridge contract, eliminating cross-deployment replay.

---

### Proof of Concept

```
# Deployment A (staging, chain_id=5655, same aggregator key)
grpcurl … Operator/Withdraw '{"withdrawal": {...}, "verification_signature": "0xABCD..."}'
# → succeeds, signature captured

# Deployment B (production, chain_id=5655, same aggregator key)
grpcurl … Operator/Withdraw '{"withdrawal": {...}, "verification_signature": "0xABCD..."}'
# → also succeeds: recover_address_from_ecdsa_signature returns the same address
#   because CLEMENTINE_EIP712_DOMAIN is identical on both deployments
```

The recovered address matches `address_in_config` on deployment B because the domain separator, type hash, and field encoding are all identical — the only missing binding is the deployment-specific `chain_id`/`verifying_contract`.
