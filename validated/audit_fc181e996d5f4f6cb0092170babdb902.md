### Title
Silent, unvalidated rewrite of a repository's Git remote URL from an untrusted GitHub API response — (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` rewrites the user's local `origin` remote based on the `clone_url` field returned by a `fetchRepository()` API call, checking only that the URL *protocol* (https vs ssh) is unchanged. It never verifies that the hostname, owner, or repository name match what the user originally configured, so a malicious or compromised GitHub API response can silently redirect the repository's remote to an entirely different destination without any user confirmation.

### Finding Description
`updateRemoteUrl` is invoked automatically (no user interaction) from `repositoryWithRefreshedGitHubRepository` in `app-store.ts` whenever Desktop refreshes a repository's associated GitHub metadata: [1](#0-0) 

The refresh calls `api.fetchRepository(owner, name)`, which performs a plain `GET repos/{owner}/{name}` against the account's configured endpoint (github.com or a GHES/GHAE host) and parses the JSON response directly: [2](#0-1) 

The returned `apiRepo.clone_url` is then fed straight into `updateRemoteUrl`, which decides whether to rewrite the remote: [3](#0-2) 

The only real gate is `protocolsMatch` — a comparison of `URL.parse(url).protocol` between the existing remote and the server-supplied one. There is **no check that the hostname, owner, or repository name of the new URL match the original remote** (that check, `urlsMatch`, is explicitly required to be **false**, since the whole point of the function is to follow renames/transfers where the URL *changes*). As long as the protocol is preserved and the current remote still matches the repository's previously cached `cloneURL` (i.e., the user hasn't hand-edited the remote), `gitStore.setRemoteURL()` is called with the attacker/server-controlled URL, invoking `git remote set-url origin <new_url>` unconditionally: [4](#0-3) 

Because the API response is the sole source of truth for `clone_url`, any party able to influence that response — a compromised or malicious GitHub Enterprise Server the user has added as an account, or an on-path/MITM actor able to present a response that the HTTPS stack accepts — can point the field at a different repository (even a different owner/repo path on the *same* host, e.g. `github.com/attacker/evil-repo`), and Desktop will rewrite the user's `origin` without any dialog, diff, or confirmation.

This differs qualitatively from the deliberate, user-initiated `_setRemoteURL` path exposed through Repository Settings, where the user explicitly reviews and submits the new URL: [5](#0-4) 

Here, there is no such review step — the change happens as a background side effect of a routine repository metadata refresh.

### Impact Explanation
This is a silent corruption of what the user pushes/fetches, matching the class of “existing guards do not stop the path” issues:
- Once `origin` is rewritten to a same-host-but-different-repo URL, subsequent pushes/fetches transparently target the attacker-designated repository. Because Desktop's credential trampoline (`trampoline-credential-helper.ts`) resolves credentials by **hostname**, not by exact repo path, the user's legitimate GitHub token is used to authenticate against the new destination — meaning any future push silently exfiltrates the user's local commits/history to a repository the user did not intend to push to.
- If the attacker instead points `clone_url` at a different hostname but the same declared protocol, Desktop will also rewrite the remote there; whether credentials leak to that host then depends on whether an account is registered for that hostname, but at minimum the user's future `git fetch`/`pull` will silently retrieve content from an attacker-controlled server, which the user will treat as authentic upstream content.
- No error, diff, prompt, or log-visible warning is surfaced to the user; the rewrite happens as a routine background refresh (e.g., after opening the app, switching repos, or completing other repo operations that trigger `repositoryWithRefreshedGitHubRepository`).

### Likelihood Explanation
Requires the attacker to control the JSON returned by `GET repos/{owner}/{name}` for an account the victim has configured — realistic for a malicious/compromised GitHub Enterprise Server (which many orgs add as a trusted account) or a network position capable of tampering with API responses. It does not require local access, malware, leaked credentials, or unusual user action — it is triggered by Desktop's own normal, automatic background refresh logic. This keeps it within the "attacker controls...a GitHub API object" and "git remote/proxy response" categories the task explicitly allows, while excluding the local-access/malware/social-engineering exclusions.

### Recommendation
In `updateRemoteUrl`, in addition to `protocolsMatch`, require that the parsed hostname (and ideally owner/name) of `updatedRemoteUrl` matches the hostname associated with `gitHubRepository.endpoint`/the account, or at minimum surface a confirmation UI before silently changing a remote URL sourced from a network response. Any automatic remote-URL update should be constrained to the same host the account is authenticated against, and ideally logged/notified to the user rather than applied silently.

### Proof of Concept
1. Add a GitHub Enterprise Server (or dotcom) account to Desktop and clone a repository from it, e.g. `https://ghe.example.com/org/real-repo.git`, associated with `gitHubRepository.cloneURL = https://ghe.example.com/org/real-repo`.
2. Compromise/control that server's (or a MITM's) response to `GET /api/v3/repos/org/real-repo`, so `clone_url` in the JSON body is `https://ghe.example.com/attacker/evil-repo`.
3. Trigger any code path that calls `repositoryWithRefreshedGitHubRepository` for that repository (app-store.ts:4874) — e.g. simply switching to the repository or an automatic background refresh.
4. Observe that `updateRemoteUrl` (app/src/lib/stores/updates/update-remote-url.ts:42-43) determines `protocolsMatch === true`, `remoteUrlUnchanged === true` (remote still equals the previously cached, legitimate `cloneURL`), and `urlsMatch === false` (different repo path) — and unconditionally calls `gitStore.setRemoteURL('origin', 'https://ghe.example.com/attacker/evil-repo')`, silently rewriting the working repository's origin with no prompt.
5. The next `git push`/`git fetch` in Desktop authenticates against `ghe.example.com` using the victim's stored token (matched by hostname in `trampoline-credential-helper.ts`) and interacts with `attacker/evil-repo` instead of `org/real-repo`.

  public async fetchRepository(
    owner: string,

  ): Promise<IAPIFullRepository | null> {
    try {
      const response = await this.ghRequest('GET', `repos/${owner}/${name}`)
      if (response.status === HttpStatusCode.NotFound) {
        log.warn(`fetchRepository: '${owner}/${name}' returned a 404`)
        return null
      }

    } catch (e) {
      log.warn(`fetchRepository: an error occurred for '${owner}/${name}'`, e)
      return null
    }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
