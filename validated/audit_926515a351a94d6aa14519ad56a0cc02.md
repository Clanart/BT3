### Title
Unverified serialized threshold parameters let a single supplied share define the entire group key — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts `t`, `n`, `i`, the secret share, and all `n` verification shares from raw bytes, and `ThresholdKeys::new` computes the group key solely as the interpolation of the first `t` verification shares (`participants 1..=t`). No check binds the local `secret_share` to `verification_shares[i]`, and no check requires `t` to reflect any honest quorum — a crafted blob with `t = 1` produces keys whose group key is a single attacker-chosen verification share. Analogous to the Nouns Builder report where the earliest claimer acquires majority voting power while supply is low, here the "first" (only) interpolated share holds 100% of the group key's weight, silently converting a threshold scheme into unilateral authority.

### Finding Description
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs, lines 376-378):

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

The group key is derived exclusively from `verification_shares[1..=t]`. The constructor validates the share count and participant range (lines 355-365) and that `Constant` interpolation requires `t == n` (lines 367-374), but never verifies `C::generator() * secret_share == verification_shares[i]`, nor that the shares form a consistent polynomial.

`ThresholdKeys::read` (lines 574-632) feeds attacker-supplied bytes straight into this path: `t`, `n`, `i`, the interpolation mode, the secret share, and `n` group elements are all deserialized via `read_F`/`read_G` and passed to `ThresholdKeys::new`. A malicious byte stream can therefore specify:

- `t = 1, n = 1, i = 1`, `Interpolation::Lagrange` (or `Constant(vec![1])`), a verification share `A = G * a` for known `a`, and any `secret_share` value.

`group_key()` then returns `A`, a key whose discrete logarithm the attacker knows. Every downstream consumer — `Scanner::new` on the resulting `group_key`, `tweak_keys` in `networks/bitcoin/src/wallet/mod.rs:46-75`, FROST signing views — treats this as a threshold-controlled key while one party holds the entire secret.

Additionally, for `t > 1` the absence of a `G * secret_share == verification_shares[i]` consistency check means tampered storage produces a group key no honest participant set can actually satisfy: `view()` interpolates `secret_share` against attacker-chosen verification shares, so signatures fail to verify and funds sent to `group_key()` are unspendable — "funds reported received that are not spendable."

### Impact Explanation
Two concrete impacts, both reachable purely through bytes fed to `ThresholdKeys::read`:

1. **Unilateral control (majority-power analog):** with `t = 1`, a single supplied verification share constitutes the whole group key. Any protocol flow that deserializes keys from an untrusted or replayed source attributes threshold security to a key one party fully controls — signatures produced for it are valid yet required no quorum.
2. **Unspendable outputs:** with inconsistent `secret_share` vs. `verification_shares`, `group_key()` commits to a polynomial the holder's share does not lie on. Funds scanned/deposited to that key (e.g., via `Scanner`/`p2tr_script_buf` on `Secp256k1`) cannot be spent by the nominal threshold set, since no combination of real shares evaluates to the group key's discrete log.

### Likelihood Explanation
Exploitation requires an integrator to deserialize `ThresholdKeys` (or bytes later loaded into them) from an input the attacker can influence — e.g., restored/migrated key material, backup blobs, or keys relayed between nodes. `read` explicitly exists as a deserialization API and is listed as an untrusted-bytes sink; the missing consistency check is unconditional, so any such flow is affected. Since it does not require corrupting a live DKG session, this does not fall under the malicious-validator exclusion: it is a deserialization-time assumption violation. Medium severity: needs a specific integration pattern, but the consequence (subverted threshold / unspendable funds) is direct.

### Recommendation
- In `ThresholdKeys::new`, verify `C::generator() * *secret_share == verification_shares[&params.i()]` and reject on mismatch.
- Optionally verify the verification shares lie on a degree-`t-1` polynomial (e.g., check interpolation of shares `t+1..=n` is consistent with the `1..=t` evaluation, or require callers of `read` to supply/verify the expected `group_key` out-of-band).
- Document that `ThresholdKeys::read` output must be authenticated (e.g., compare `group_key()` against the value committed by the DKG) before use.

### Proof of Concept
```rust
use std::io::Write;
use zeroize::Zeroizing;
use ciphersuite::{Ciphersuite, group::ff::Field};
use dkg::{ThresholdKeys, Participant, ThresholdParams, Interpolation};
use dalek_ff_group::Ristretto; // any Ciphersuite

// Attacker-chosen scalar whose point becomes the entire group key.
let a = <Ristretto as Ciphersuite>::F::random(&mut rand_core::OsRng);
let attacker_share = <Ristretto as Ciphersuite>::generator() * a;

let mut bytes = vec![];
// curve ID prefix
bytes.write_all(&(Ristretto::ID.len() as u32).to_le_bytes()).unwrap();
bytes.write_all(Ristretto::ID).unwrap();
// t = 1, n = 1, i = 1  -> lone "early claimer" holds 100% of the key
bytes.write_all(&1u16.to_le_bytes()).unwrap(); // t
bytes.write_all(&1u16.to_le_bytes()).unwrap(); // n
bytes.write_all(&1u16.to_le_bytes()).unwrap(); // i
bytes.write_all(&[1u8]).unwrap();              // Interpolation::Lagrange
bytes.write_all(a.to_repr().as_ref()).unwrap(); // secret_share
bytes.write_all(attacker_share.to_bytes().as_ref()).unwrap(); // vshare[1]

let keys = ThresholdKeys::<Ristretto>::read(&mut &bytes[..]).unwrap();
// group_key == attacker_share: threshold of 1 = unilateral authority
assert_eq!(keys.group_key(), attacker_share);
```

And the unspendable variant: with honest `t, n, i` but a `secret_share` inconsistent with `verification_shares[i]`, `ThresholdKeys::new` still succeeds, `group_key()` reflects only the supplied shares, and `view(..)` produces shares that cannot co-sign for that group key — deposits to it are stranded.
