## Reduction of the external bug to its core primitive

The KarmaAirdrop bug is: a signature meant to authorize a *bundled* side-effect (`delegateBySig`) can be extracted from the mempool and executed on its own by anyone, consuming the signer's nonce before the original bundling transaction lands, causing the original transaction's own use of that same signature to fail because the nonce it was signed against is now stale.

The reusable primitive is: **a signed payload includes a nonce read fresh from storage at verification time, and there exists a second, independently-triggerable code path that can consume that same nonce counter using data the attacker does not control the intent of, but can still supply.**

### Title
Shared per-`(address, StateMachine)` nonce lets a griefer invalidate a relayer's pending fee-beneficiary-redirect signature - (File: `modules/pallets/relayer/src/accumulate.rs`, `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`pallet-relayer` uses a single `Nonce<T>` storage map keyed by `(address, StateMachine)` for two independent signed operations: the beneficiary redirect embedded in `accumulate` (fee accumulation) and the relayer fee `withdraw`. Both read the *current* on-chain nonce at execution time and verify the caller-supplied signature against `message(nonce, ...)`/`beneficiary_message(nonce, ...)` computed from that fresh value. Because both extrinsics that touch this nonce are permissionless/unsigned (the caller only needs *a* valid signed payload, not to be the signer), an attacker who observes a pending `accumulate` call carrying a relayer's `beneficiary_details` signature in the transaction pool can front-run it with any other valid `WithdrawalProof` for the same `delivery_address`/`state_machine` pair (built entirely from public on-chain state and proofs the attacker can generate themselves), consuming the nonce first. When the original transaction executes, `beneficiary_message` is recomputed with the now-incremented nonce, the previously valid signature no longer verifies, and the whole `accumulate` call reverts with `InvalidSignature`/`InvalidPublicKey`, discarding the intended fee-accumulation and beneficiary redirect.

### Finding Description [1](#0-0) 

`accumulate()` fetches the nonce fresh from storage right before verifying the beneficiary signature:

```
let nonce = Nonce::<T>::get(&delivery_address, state_machine);
let msg = beneficiary_message(nonce, state_machine, &beneficiary_address);
... signature.verify(&msg, None) ...
Nonce::<T>::try_mutate(&delivery_address, state_machine, |value| { *value += 1; ... })
``` [2](#0-1) 

`withdraw()` uses the exact same `Nonce<T>` map, keyed the same way (`address`, `StateMachine`):

```
let nonce = Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain);
let msg = message(nonce, withdrawal_data.dest_chain, withdrawal_data.beneficiary.clone());
... signature.verify(&msg, None) ...
Nonce::<T>::try_mutate(address.clone(), withdrawal_data.dest_chain, |value| { *value += 1; ... })
```

`Nonce<T>` is declared once in `modules/pallets/relayer/src/lib.rs` and shared by both modules (`use crate::{..., Nonce, ...}` in both files). Neither call binds the nonce to a specific *purpose* (redirect vs. withdrawal) — it is a single incrementing counter per `(address, StateMachine)`.

Both `accumulate` (fee accumulation with optional beneficiary redirect) and `withdraw` are dispatched as calls that verify an embedded cryptographic signature rather than relying on `ensure_signed(origin)` for authorization — the caller does not need to be the relayer to submit a *valid* `WithdrawalProof`/`WithdrawalInputData` payload; they only need a payload whose signature checks out for the *current* nonce. This is structurally identical to `KarmaAirdrop::claim` relying on `Erc20Votes::delegateBySig`'s embedded signature-plus-nonce rather than `msg.sender`.

An attacker who:
1. observes a pending `accumulate` extrinsic in the transaction pool carrying `beneficiary_details = (beneficiary, signature)` signed by a relayer for nonce `N` on state machine `S`, and
2. independently assembles their own valid `WithdrawalProof` for *any other* unclaimed request commitment delivered by that same relayer on the same `S` (all inputs — `RequestCommitments`, delivery receipts, state proofs — are public),

can submit their own `accumulate` call first. It passes verification (it is a legitimate proof, just for different commitments, with no `beneficiary_details` needed), and its final step unconditionally increments `Nonce::<T>[delivery_address, S]`.

When the victim's original transaction then executes, `beneficiary_message(nonce, S, beneficiary)` is recomputed using the *now-incremented* nonce, the previously-valid signature fails `signature.verify`, and the `?` operator propagates the error up through `accumulate`, reverting the *entire* call — including the unrelated fee crediting for the commitments in that batch that had nothing to do with the beneficiary redirect.

### Impact Explanation
The relayer's legitimate `accumulate_fees`/beneficiary-redirect transaction is blocked and reverted by a third party with no special privileges, no compromised key, and no need to be a relayer/prover/admin themselves — only public mempool visibility and the ability to construct an independent, valid `WithdrawalProof` for the same delivery address. This is a logic/DoS attack on fee settlement: the relayer must detect the failure, re-sign a new beneficiary message against the bumped nonce, and resubmit, delaying (and, if repeated, indefinitely griefing) legitimate reward settlement — matching the bounty's "logic attacks" / transaction manipulation class rather than a pure gas-DoS.

### Likelihood Explanation
Moderate-to-low but realistic: it requires the attacker to notice a pending `accumulate` call with `beneficiary_details` in the pool and to have (or construct) another valid, unclaimed delivery proof for the same relayer address on the same chain — a condition that holds naturally for any active relayer with multiple in-flight, unclaimed commitments. No governance, prover collusion, or leaked keys are needed.

### Recommendation
Bind the beneficiary-redirect signature to a purpose-specific nonce (or a monotonically-unique commitment-batch hash) instead of sharing a single `(address, StateMachine)` counter between `accumulate`'s beneficiary redirect and `withdraw`'s fee withdrawal, and wrap the beneficiary-signature check in a way that a nonce mismatch merely skips the redirect (crediting `delivery_address` instead) rather than reverting the whole `accumulate` call — mirroring the `try/catch`-and-fallback mitigation applied to the original `KarmaAirdrop::claim`/`delegateBySig` bug.

### Proof of Concept
1. Relayer `A` delivers commitments `{c1, c2, c3}` from source chain `S` and signs `beneficiary_message(nonce=N, S, beneficiaryB)` to redirect the batch's fees to `B`, then submits `accumulate(WithdrawalProof{commitments: {c1,c2,c3}, ..., beneficiary_details: Some((B, sig))})`.
2. Attacker watches the pool, sees this pending extrinsic, and independently notices relayer `A` also delivered an unrelated, still-unclaimed commitment `c4` on the same source chain `S` (public via `RequestCommitments`/receipt state).
3. Attacker builds their own valid `WithdrawalProof{commitments: {c4}, source_proof, dest_proof, beneficiary_details: None}` (no signature of `A`'s needed) and submits `accumulate` for it with higher priority/gas.
4. That call succeeds, crediting `Fees[S, A] += fee(c4)` and executing `Nonce::<T>::try_mutate(A, S, |v| *v += 1)`, bumping the nonce from `N` to `N+1`.
5. Relayer `A`'s original transaction now executes: `beneficiary_message(nonce=N+1, S, B)` is recomputed, `sig` (signed for `N`) fails `signature.verify`, and `accumulate` reverts entirely via `Error::<T>::InvalidPublicKey`/`InvalidSignature`, dropping the intended redirect and fee credit for `{c1,c2,c3}` until `A` re-signs and resubmits. pub fn beneficiary_message(
	nonce: u64,
	state_machine: StateMachine,
	beneficiary: &[u8],
