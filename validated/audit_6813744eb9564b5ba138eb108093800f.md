### Title
Missing sighash-type enforcement in `Operator::withdraw` allows a signature with `TapSighashType::None` to authorize an unauthenticated payout output - ([File: core/src/operator.rs])

### Summary
`Operator::withdraw` verifies the user's Schnorr signature against whatever `sighash_type` is embedded in the attacker/caller-supplied `in_signature`, without ever asserting that this type is `SinglePlusAnyoneCanPay`. Because `calculate_sighash_txin` computes the digest according to that same caller-chosen `sighash_type`, a signature produced with `TapSighashType::None` will produce a digest that does not commit to any output, letting the caller pass arbitrary `out_script_pubkey`/`out_amount` values that the signature verification can never reject.

### Finding Description
The intended binding is: `sighash(payout_tx, sighash_type=SinglePlusAnyoneCanPay)` commits to `(out_script_pubkey, out_amount)` at output index 0, and `SECP.verify_schnorr` over that digest with `user_xonly_pk` is meant to prove the user authorized exactly that output [1](#0-0) . The code never checks `in_signature.sighash_type == TapSighashType::SinglePlusAnyoneCanPay` before computing the sighash; it simply forwards the caller-controlled `sighash_type` field of `in_signature` into `calculate_sighash_txin` [2](#0-1) . The only Citrea-sourced check in this function validates the *input* outpoint against `get_withdrawal_utxo_from_citrea_withdrawal`, not the output [3](#0-2) ; `out_script_pubkey`/`out_amount` are taken as direct function/RPC arguments and used to build the payout transaction's output with no cross-check against any Citrea-committed value [4](#0-3) . `create_payout_txhandler` places these caller-supplied values into output 0 of the transaction that is signed via key-spend with `user_sig` [5](#0-4) . If `sighash_type` is `None`, BIP-341/342 semantics mean the resulting sighash does not commit to any transaction output, so the same signature remains valid for `SECP.verify_schnorr` no matter what `out_script_pubkey`/`out_amount` are substituted. The doc-comment at line 637 ("Ensure the signature uses SinglePlusAnyoneCanPay sighash type") shows the author's intent but this is never enforced in code - it's only a wording in the error message shown if `verify_schnorr` itself fails, not an independent assertion.

### Impact Explanation
If this path is reachable with attacker-controlled `in_signature`/`out_script_pubkey`/`out_amount` (e.g. relayed through the aggregator's public gRPC to the operator's `withdraw` handler in `core/src/rpc/operator.rs`), the operator could be made to broadcast (`rpc.send_raw_transaction`, [6](#0-5) ) a payout whose destination/amount was never actually authenticated by the user's signature, i.e. BTC moving from the operator's fronted UTXO to an output the user did not commit to - a custody-binding violation matching the Critical category ("BTC leaving ... without a matching fronted withdrawal actually authorized"). This is repeatable per withdrawal request and does not require compromising any key, since the flaw is a missing check on the caller-supplied `sighash_type`, not a cryptographic break.

### Likelihood Explanation
I was unable to fully verify, within the available tool budget, whether `core/src/rpc/operator.rs`'s `withdraw` gRPC handler applies authentication (e.g. mTLS restricting callers to the aggregator/self) and whether the aggregator validates `in_signature`, `out_script_pubkey`, and `out_amount` against the actual Citrea-committed withdrawal record before forwarding them to `Operator::withdraw`. If such upstream validation exists and independently pins `out_script_pubkey`/`out_amount` to the value approved on Citrea (matching the input outpoint check already present), the missing sighash-type assertion in `operator.rs` may be latent rather than directly exploitable by an unprivileged external attacker. This uncertainty should be resolved by inspecting `core/src/rpc/operator.rs` and `core/src/rpc/aggregator.rs`'s withdraw-forwarding logic, which I could not fully trace in the remaining iterations.

### Recommendation
Explicitly assert `in_signature.sighash_type == TapSighashType::SinglePlusAnyoneCanPay` in `Operator::withdraw` before calling `calculate_sighash_txin`/`verify_schnorr`, rejecting any other sighash type outright, regardless of what upstream callers may or may not already validate.

```rust
    // 3. Assert LHS: sighash_A = calculate_sighash_txin(0, TapSighashType::None) on tx with output A
    //    RHS: sighash_B = calculate_sighash_txin(0, TapSighashType::None) on tx with output B
    //    assert_eq!(sighash_A, sighash_B); // proves no output commitment
    // 4. assert!(SECP.verify_schnorr(&sig, &Message::from_digest(*sighash_B.as_byte_array()), &user_xonly_pk).is_ok());
```

The critical assertion is that `sighash_A == sighash_B` despite differing outputs, proving `verify_schnorr` cannot distinguish the intended payout output from an attacker-substituted one when `sighash_type == None`.

```rust
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
```
