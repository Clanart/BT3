### Title
Permanent freezing of escrowed token-pair collateral via pausable/blacklistable ERC20 contracts with no freeze-capability check on registration - (File: `x/erc20/keeper/proposals.go`, `x/erc20/keeper/msg_server.go`)

### Summary
`x/erc20` allows permissionless registration of arbitrary ERC20 contracts as token pairs and never inspects whether the contract can unilaterally block transfers to/from the module escrow account (e.g. via `pause()`/blacklist logic controlled by the token's own admin). This is the direct Cosmos EVM analog of the SPL "freeze authority" issue: instead of a mint's `freeze_authority` freezing a token account, an ERC20 contract's pauser/blacklist role can freeze the `x/erc20` module account, permanently locking the ERC20 collateral backing already-minted native coins.

### Finding Description
`registerERC20` in `x/erc20/keeper/proposals.go` only checks that the contract is not already registered and that a denom can be derived from `QueryERC20`; it performs no validation of the contract's transfer-restriction capabilities: [1](#0-0) 

Registration can happen without governance when permissionless registration is enabled, as exercised in the test suite (`"ok - non-governance, permissionless true"`): [2](#0-1) 

The repository's own bundled ERC20 template contract demonstrates that a registrable "native ERC20" can carry an owner-controlled `PAUSER_ROLE` capable of halting all transfers at will: [3](#0-2) [4](#0-3) 

Once such a token is registered, `ConvertERC20` escrows user tokens on the module account and mints native coins 1:1: [5](#0-4) [6](#0-5) 

The reverse path, `ConvertCoinNativeERC20`, escrows the native coin first and then calls the ERC20 `transfer` from the module account to the receiver to unescrow the underlying token: [7](#0-6) 

If the token's pauser (or a blacklist-style admin) pauses the contract or blacklists the module escrow address at any point after tokens have accumulated in escrow, every future `ConvertCoinNativeERC20` call for that pair will revert at the `CallEVM` transfer step. Because the coin-side escrow (`SendCoinsFromAccountToModule`) and the token-side unescrow happen in the same message execution, a single call reverts atomically and does not itself lose funds — but this means there is now **no way for any holder of the native coin representation to ever redeem it back into the underlying ERC20 token**. The ERC20 collateral sitting in `types.ModuleAddress` is permanently locked, exactly like an SPL token account rendered permanently unusable by a `FreezeAccount` instruction with no counter-mechanism, since `MintingEnabled`/`ConvertCoinNativeERC20` have no fallback, no timeout-based release, and no path to seize/redistribute the locked collateral.

### Impact Explanation
This matches the "Critical permanent freezing, locking ... of ... token-pair-backed balances" impact category. All native-coin holders for the affected token pair permanently lose access to the value represented by their coins, because the corresponding ERC20 collateral in the module account can never be unescrowed once the token admin pauses/blacklists the module address. Because token pair registration can be permissionless, this attack is reachable by an ordinary unprivileged user who registers a specially crafted pausable token, lets other users convert into it (or converts on behalf of victims who trust the token pair listing), and later pauses transfers — freezing all outstanding collateral indefinitely with no recovery path in the protocol.

### Likelihood Explanation
Likelihood is moderate-to-high in a permissionless-registration deployment: an attacker only needs to (1) deploy an ERC20 with owner-controlled pause/blacklist logic (trivial, and the repo's own reference contracts already include this pattern), (2) register it via `MsgRegisterERC20` under permissionless mode, (3) get users to convert coins/tokens through the pair (e.g., by presenting it as a legitimate wrapped asset), and (4) pause the contract. No chain-level privileged access is required — the "freeze authority" here belongs to the external ERC20 contract admin, mirroring the original SPL finding where the freeze authority is external to the lending protocol itself.

### Recommendation
- At registration time (`registerERC20` / `RegisterERC20Extension`), reject or flag ERC20 contracts that expose pausable, blacklistable, or otherwise unilaterally transfer-restricting logic detectable via bytecode/ABI heuristics, or require an explicit governance allow-list for such tokens rather than permissionless registration.
- Add an escape hatch in `x/erc20` so that if the module's ERC20 balance for a pair becomes non-transferable (e.g., detect persistent `CallEVM` transfer failures), governance can migrate/refund escrowed value or mark the pair as frozen with a documented recovery process, instead of leaving native-coin holders with unredeemable coins indefinitely.
- Document and enforce that permissionless-registered ERC20 token pairs are non-transitively "trust-your-own-risk" and surface this clearly at the query/API layer so wallets and users are warned before converting into such pairs.

### Proof of Concept
1. Attacker deploys an ERC20MinterBurnerDecimals-style contract (or any custom contract) with an owner-controlled `pause()`/blacklist function, using the deployer key as `PAUSER_ROLE`.
2. With permissionless registration enabled, attacker calls `MsgRegisterERC20` to register the contract as a token pair (`x/erc20/keeper/proposals.go` `registerERC20`).
3. Victims call `MsgConvertERC20` to convert their tokens into the native coin representation; ERC20 balance escrows into `types.ModuleAddress` (`convertERC20IntoCoinsForNativeToken`, `x/erc20/keeper/msg_server.go:71-140`), minting native coins for victims.
4. Attacker calls `pause()` on the ERC20 contract (or blacklists `types.ModuleAddress`).
5. Any victim calling `MsgConvertCoin` to redeem native coins back into the ERC20 token now has their transaction revert forever at the `CallEVM(... "transfer" ...)` step in `ConvertCoinNativeERC20` (`x/erc20/keeper/msg_server.go:263-266`), because the module account can no longer transfer the paused/blacklisted token. The ERC20 collateral is permanently stuck in the module account with no protocol-level recovery mechanism.

```go
// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}
```
