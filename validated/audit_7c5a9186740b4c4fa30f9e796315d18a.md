## Analysis

The report's bug class is "state update sequencing" — a status/accounting flag is written to storage *after* an external call whose logic depends on that status, and because a shared piece of intermediate state (`prevEventsLen`/subscription flag) is only valid for one call frame, nested/recursive invocations corrupt it.

The native analog in this repository is the `BalanceHandler` used by every stateful precompile (`staking`, `erc20`, `ics20`, `werc20`, `distribution`, etc.) via `RunNativeAction`/`runNativeAction`.

### Root cause

`BalanceHandler.BeforeBalanceChange` records `prevEventsLen = len(ctx.EventManager().Events())`, and `AfterBalanceChange` later replays only the events *after* that offset to update the EVM `StateDB` balances (`stateDB.AddBalance`/`SubBalance`) from bank `coin_spent`/`coin_received` events:

But a **new `BalanceHandler` instance is created per top-level `runNativeAction` call** via `p.BalanceHandlerFactory.NewBalanceHandler()`: [1](#0-0) 

When a precompile's native action recursively re-enters the EVM (e.g. `evmKeeper.CallEVMWithData`) which triggers another precompile call before the outer call's `AfterBalanceChange` runs, both frames go through `runNativeAction` and instantiate their own `BalanceHandler`s from the *same* `BalanceHandlerFactory` (the factory itself is a field stored once on `Precompile`). Each nested call's `BeforeBalanceChange` overwrites the event-index bookkeeping relative to the shared `ctx.EventManager()`, and the reentrant call commits/consumes events out of the order the outer frame expects when it eventually calls `AfterBalanceChange` — this is exactly what the repo's own test comment documents: *"the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten... leads to balance desync between native bank keeper and EVM stateDB."* [2](#0-1) 

This was reproduced with the test debug precompile that recursively calls itself and emits multiple `bank`/custom events across the recursion boundary: [3](#0-2) [4](#0-3) 

### Why this matters (Critical-impact path)

Every value-moving precompile (`staking.Delegate/Undelegate`, `erc20.Transfer/TransferFrom`, `distribution.WithdrawDelegatorRewards`, `ics20.transfer`, `werc20.Deposit`) relies on `BalanceHandler.AfterBalanceChange` to keep the **EVM StateDB balance in sync with the actual bank-module balance** after a native bank `Send`/mint/burn happens inside `Execute`. If a contract chains/recurses through two or more of these precompiles in a single EVM call (a pattern explicitly exercised in test suites, e.g. `testDelegateAndFailCustomLogic`, `depositValidatorRewardsPoolWithTransfer`, ICS20 caller "before/after transfer" contracts), the `prevEventsLen` desync means `AfterBalanceChange` in the outer frame can replay/skip the wrong slice of bank events — either double-applying a `coin_received`/`coin_spent` event to `StateDB.AddBalance`/`SubBalance`, or skipping the event of the real transfer. Since subsequent EVM opcodes/precompile calls within the *same* transaction read balances from `StateDB` (not from the bank keeper directly), a wrong `StateDB` balance can be leveraged before the transaction commits: e.g., an attacker contract could trigger the corrupted balance credit path in `StateDB` (extra `AddBalance`) and then immediately re-spend/transfer that inflated in-EVM balance through `transfer`/`delegate`/`ics20.transfer` calls before `CommitWithCacheCtx` reconciles state, or cause the reverse (a spender losing balance in `StateDB` while the real bank ledger is unaffected, causing legitimate transfers to spuriously fail — a fund-freezing effect). This directly threatens the "1:1 accounting between native coins, ERC20 views, escrows, and precompile-visible balances" invariant called out in the audit gate.

## Impact Explanation

If exploitable end-to-end, this is a Critical accounting-corruption bug: it can desynchronize `x/vm` `StateDB` balances from real `x/bank` balances for arbitrary user accounts, letting an attacker's EVM-visible balance diverge from their spendable Cosmos-side balance within the same transaction — enabling unauthorized fund extraction/duplication (spend more than actually owned) or permanent balance freezing (inflated ledger vs. real bank ledger going out of sync so genuine transfers subsequently fail/panic).

## Likelihood Explanation

**Uncertain / not fully verified.** I was only able to confirm:
1. The `BalanceHandlerFactory` is shared and a fresh `BalanceHandler` is created per `runNativeAction` invocation, so `prevEventsLen` is frame-local, not globally shared — this actually mitigates cross-nested-call corruption for the *simple* recursive case shown in the test, since each nested call's `BeforeBalanceChange`/`AfterBalanceChange` bracket their own event window.
2. The existing repo test (`TestRecursivePrecompileCallsWithDebugPrecompile`) passes with expected event counts, and does not assert an actual balance desync — its docstring describes a *known/suspected* bug pattern, but I could not confirm from the available code whether the test actually demonstrates a real StateDB/bank balance divergence with fund-theft-level consequences, or whether it is exercising a scenario that the current architecture already handles safely (each nested `runNativeAction` reconciling its own event slice before returning to the outer frame, since `AfterBalanceChange` for the inner call happens before the outer resumes execution).
3. I could not trace a concrete transaction sequence that turns this into an actual double-spend of funds (i.e., a PoC combining two distinct precompiles' balance-changing calls in one EVM transaction, in an order that causes `StateDB` balance to be higher than what the bank module holds and then spending against that inflated balance before commit).

Given the ambiguity — the shared-instance concern the test docstring raises does not clearly match what the code actually does (factory generates fresh handlers per call) — I cannot confidently assert this rises to a reproducible Critical vulnerability without deeper access to `x/vm/statedb` commit/revert semantics for nested precompile calls (`AddPrecompileFn`, `CommitWithCacheCtx`, `RevertMultiStore`) than what the index surfaced.

## Recommendation

Have engineers write/extend a proof-of-concept that chains at least two balance-changing precompile calls (e.g., `staking.Delegate` from within an `erc20.transfer` callback, or nested `ics20.transfer` calls) inside one EVM transaction and assert `StateDB.GetBalance` vs. `bankKeeper.GetBalance` equality after each nested return and after the top-level commit. If a divergence is found, the fix should ensure `BeforeBalanceChange`/`AfterBalanceChange` windows are properly nested/stacked (e.g., using a stack of event offsets keyed to call depth, or reconciling directly against the underlying MultiStore snapshot rather than the shared `ctx.EventManager()` event log) so that reentrant precompile calls cannot cause `StateDB` balance replay to skip or double count bank events.

## Proof of Concept

Not established — I could not confirm a concrete transaction sequence causing actual `StateDB`/bank balance divergence with the tools available (no execution environment, only static code search). The existing repository test `evmd/tests/integration/balance_handler/balance_handler_test.go:45-106` is the closest artifact but does not itself assert a fund-impacting invariant break. Verification requires actually running this test with instrumented balance comparisons and constructing a multi-precompile reentrant chain, which needs a background Devin session with code execution, not achievable in ask-only mode.

contract DebugPrecompileCaller {
    address constant debugPrecompile = 0x0000000000000000000000000000000000000799;
    error CallFailed(bytes data);
    function callback(uint256 counter) public {
        bool result;
        bytes memory data;

        // emit events
        for (uint i = 0; i < counter; i++) {
            (result, data) = debugPrecompile.call(abi.encodePacked(uint8(1)));
            if (!result) {
                revert CallFailed(data);
            }
        }

        if (counter > 3) {
            // stop the recursion
            return;
        }

        // recursive call
        (result, data) = debugPrecompile.call(abi.encodePacked(uint8(0), counter));
        if (!result) {
            revert CallFailed(data);
        }
    }
