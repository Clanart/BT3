### Title
CosmWasm `DelegateCallEvm` custom message trusts a self-reported `info.Sender` field instead of the verified caller to attribute EVM delegatecall identity - (File: `x/evm/client/wasm/encoder.go`)

### Summary
The CVE describes Firefox's WebChannel API accepting a self-declared "sending principal" instead of validating the actual verified sender, enabling privilege escalation. The closest reachable analog in sei-chain is in the CW→EVM bridge's custom message encoder for `DelegateCallEvm`, where the EVM-side identity (`Sender`) used to authorize a delegatecall is taken from a `wasmvmtypes.MessageInfo.Sender` value passed alongside the message rather than from the cryptographically verified contract address parameter that the wasm keeper itself computed for the encoder call.

### Finding Description
`EncodeDelegateCallEVM` receives two identity-related inputs: `sender` (the `contractAddr` that is executing and calling `Encode`, which is the value the wasm keeper verified as the entity emitting this `CosmosMsg::Custom`) and `info` (a `wasmvmtypes.MessageInfo` struct carrying a `Sender` string). Instead of using the verified `sender` as the on-chain identity for the delegatecall, the code silently swaps it out: [1](#0-0) 

```
s := sender
if origSender, err := sdk.AccAddressFromBech32(info.Sender); err == nil {
    s = origSender
}
internalCallEVMMsg := types.MsgInternalEVMDelegateCall{
    Sender:       s.String(),
    ...
    FromContract: sender.String(),
}
```

`s` (derived from `info.Sender`) becomes `MsgInternalEVMDelegateCall.Sender`, which is later used to resolve the EVM identity that the delegatecall executes as: [2](#0-1) 

`HandleInternalEVMDelegateCall` only checks that `req.FromContract`'s registered pointer equals `to` — it never checks that `req.Sender` corresponds to the entity that actually authorized or is *responsible for* this specific delegatecall payload/data: [3](#0-2) 

Only the verified `sender`/`contractAddr` (`FromContract`) is checked against pointer registration; the `Sender` field that ultimately grants EVM authority for the delegatecall is populated from a caller-supplied `info.Sender`, mirroring the CVE's root cause: authority is derived from a value the message *claims* rather than from an independently verified identity.

### Impact Explanation
`HandleInternalEVMDelegateCall` uses the resolved `senderEvmAddr` (derived from the `Sender` field) as the `from` address for `CallEVM`, i.e. the msg.sender context under which arbitrary EVM `data` (fully controlled by the executing contract's logic) runs. If any contract along a wasm execution chain can influence what `info.Sender` is at the point it emits a `DelegateCallEvm` custom message — e.g. via nested contract calls, reply handlers, or by being called on behalf of a different original signer — the EVM identity used to execute delegatecall data is bound to that reported sender rather than to the contract that actually constructed the calldata. This allows the EVM-side authority (and therefore access to token balances or state gated by `msg.sender` in the delegatecall's execution context) to be attributed to a party who never chose or approved the specific EVM call being made, which is unauthorized-transfer-via-pointer territory if the delegatecall path is reachable with attacker-influenced `data`/`info.Sender` combinations.

### Likelihood Explanation
Reaching this code requires only a CosmWasm contract execution via a standard `MsgExecuteContract`, no privileged access — any public tx sender or contract deployer can trigger the `DelegateCallEvm` custom message path (`wasmbinding/encoder.go` → `EncodeDelegateCallEVM`). However, whether `info.Sender` at this call site can diverge from the actual immediate caller of the executing contract (i.e., whether it is genuinely forgeable) could not be fully confirmed — this depends on how the wasmvm bindings and message-dispatch chain populate `MessageInfo` across nested/sub-message executions, which I was unable to trace completely within the available tooling before the iteration limit was reached.

### Recommendation
Verify that `info.Sender` used for `MsgInternalEVMDelegateCall.Sender` is always sourced from a chain-verified identity consistent with the actual invocation context (e.g., require it to equal the direct/verified caller resolved by the keeper, not a value carried inside the message-info struct that could differ across nested calls), and add an explicit authorization check in `HandleInternalEVMDelegateCall` binding `req.Sender` to the verified execution chain rather than trusting the field at face value.

### Proof of Concept
Not able to construct a concrete end-to-end PoC with certainty, because confirming exploitability requires tracing how `wasmvmtypes.MessageInfo.Sender` is populated across nested/sub-message wasm executions in this codebase (i.e., whether a contract can cause its own `info.Sender` to reflect an identity other than its direct, verified caller). This trace could not be completed within the available tool budget; a Devin session with full repository access would be needed to confirm whether `info.Sender` is forgeable at the `DelegateCallEvm` call site.

```go
func EncodeDelegateCallEVM(rawMsg json.RawMessage, sender sdk.AccAddress, info wasmvmtypes.MessageInfo, codeInfo wasmtypes.CodeInfo) ([]sdk.Msg, error) {
	encodedCallEVM := bindings.DelegateCallEVM{}
	if err := json.Unmarshal(rawMsg, &encodedCallEVM); err != nil {
		return []sdk.Msg{}, err
	}
	decodedData, err := base64.StdEncoding.DecodeString(encodedCallEVM.Data)
	if err != nil {
		return []sdk.Msg{}, err
	}
	s := sender
	if origSender, err := sdk.AccAddressFromBech32(info.Sender); err == nil {
		s = origSender
	}
	internalCallEVMMsg := types.MsgInternalEVMDelegateCall{
		Sender:       s.String(),
		To:           encodedCallEVM.To,
		CodeHash:     codeInfo.CodeHash,
		Data:         decodedData,
		FromContract: sender.String(),
	}
	return []sdk.Msg{&internalCallEVMMsg}, nil
```

```go
func (k *Keeper) HandleInternalEVMDelegateCall(ctx sdk.Context, req *types.MsgInternalEVMDelegateCall) (*sdk.Result, error) {
	var to *common.Address
	if req.To != "" {
		addr := common.HexToAddress(req.To)
		to = &addr
	} else {
		return nil, errors.New("cannot use a CosmWasm contract to delegate-create an EVM contract")
	}
	addr, _, exists := k.GetAnyPointerInfo(ctx, types.PointerReverseRegistryKey(common.BytesToAddress([]byte(req.FromContract))))
	if !exists || common.BytesToAddress(addr).Cmp(*to) != 0 {
		return nil, errors.New("only pointer contract can make delegatecalls")
	}
	zeroInt := sdk.ZeroInt()
	senderAddr, err := sdk.AccAddressFromBech32(req.Sender)
	if err != nil {
		return nil, err
	}
	// delegatecall caller must be associated; otherwise any state change on EVM contract will be lost
	// after they asssociate.
	senderEvmAddr, found := k.GetEVMAddress(ctx, senderAddr)
	if !found {
		err := types.NewAssociationMissingErr(req.Sender)
		evmKeeperMetrics.associationError.Add(ctx.Context(), 1, otelmetric.WithAttributes(attribute.String("scenario", "evm_handle_internal_evm_delegate_call"), attribute.String("type", err.AddressType())))
		return nil, err
	}
	ret, err := k.CallEVM(ctx, senderEvmAddr, to, &zeroInt, req.Data)
	if err != nil {
		return nil, err
	}
	return &sdk.Result{Data: ret}, nil
```
