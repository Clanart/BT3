### Title
Payout OP_RETURN operator attribution is unauthenticated, allowing reimbursement credit theft/misdirection - (File: core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs, core/src/task/payout_checker.rs)

### Summary
The binding that must hold is: `payout_payer_operator_xonly_pk` (DB column set by `Verifier::update_finalized_payouts`) == the x-only public key of the operator whose own funds actually left the payout transaction's inputs. `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) signs the withdrawal UTXO input with `TapSighashType::SinglePlusAnyoneCanPay`, which under BIP341 only commits to input 0 and to output 0 (the user payout output) — it never commits to output 2 (the OP_RETURN carrying `operator_xonly_pk`) nor to any of the extra funding inputs added later by whoever finishes constructing/broadcasting the transaction. Anyone who obtains this user signature (any withdrawing user's own signature, or one observed once broadcast/in mempool) can build a competing transaction that reuses the exact same witness, keeps output 0 identical (satisfying the sighash), funds the withdrawal from arbitrary inputs, and writes an arbitrary `operator_xonly_pk` (belonging to a victim operator who never participated) into the OP_RETURN.

### Finding Description
`Operator::withdraw` (`core/src/operator.rs:560-692`) and `AggregatorServer::withdraw_optimistic` build the payout tx and verify the user's Schnorr signature via `payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` (`core/src/operator.rs:630-637`), but this only checks that *a* valid signature exists for input 0 under the given sighash flag — it does not restrict who is allowed to broadcast the resulting transaction or what OP_RETURN payload accompanies it. `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) places `op_return_txout(operator_xonly_pk.serialize())` as output index 2, entirely under the control of whoever assembles the final transaction, since `TapSighashType::SinglePlusAnyoneCanPay` for input 0 (`core/src/builder/transaction/txhandler.rs:210-233`, using `Prevouts::One`) only signs `SIGHASH_SINGLE`-scoped output 0 and `ANYONECANPAY`-scoped input 0.

`Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) trusts whichever transaction actually confirms and spends the withdrawal UTXO: it takes `get_first_op_return_output`/`parse_op_return_data` from that on-chain transaction verbatim and calls `update_payout_txs_and_payer_operator_xonly_pk` to persist that key into `withdrawals.payout_payer_operator_xonly_pk` with no check that the OP_RETURN's key corresponds to whoever actually supplied the additional funding inputs.

`PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) then polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and, for any row where the DB says this operator's key is the payer, automatically calls `Operator::handle_finalized_payout` (`core/src/operator.rs:839`), which starts the kickoff/reimbursement flow — without ever checking that this operator's own wallet/Bitcoin transaction actually funded the payout. `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) only cross-checks `operator_xonly_pk != kickoff_data.operator_xonly_pk`, which trivially passes because both values were forged to be the same victim key.

Exploit flow: an attacker (a normal withdrawing user, requiring no operator/verifier privilege) creates a withdrawal with a `SinglePlusAnyoneCanPay` signature over their own dust UTXO and payout output, as normal. Before/instead of letting the intended operator's payout_tx confirm, they construct their own transaction reusing that exact witness, adding their own funding inputs to pay the same output 0, and set OP_RETURN output 2 to name an arbitrary victim operator's `operator_xonly_pk`. Once mined, `update_finalized_payouts` records the victim operator as payer, and the victim's own `PayoutCheckerTask` automatically drives a kickoff/reimburse flow, releasing move-to-vault-locked BTC to the victim operator's reimbursement address for a payout it never made. ### Impact Explanation
BTC locked in the move-to-vault UTXO for this deposit is released via the reimburse path to an operator that never spent its own funds to front the withdrawal — matching "an operator reimbursed for a payout it never funded." This is repeatable per-withdrawal and can target any operator (real, active, x-only pubkey is public) without their cooperation, since it only requires the attacker to be the withdrawing user (or to race an existing mempool transaction) and to fund the withdrawal output themselves. It can also be aimed to grief an honest operator into automatically consuming a kickoff connector / entering the challenge process for a withdrawal it never intended to front.

### Likelihood Explanation
The attacker needs no special role: any user calling `withdraw` on the Citrea Bridge contract already produces the `SinglePlusAnyoneCanPay` signature themselves and fully controls constructing/broadcasting the final Bitcoin payout transaction with an arbitrary OP_RETURN, since nothing in the signed sighash covers that output. Cost is limited to funding their own withdrawal amount plus transaction fees — no attack against the deposit's escrowed funds is required to pull off the misattribution itself. This is deterministic and repeatable for every future withdrawal.

### Recommendation
Bind the OP_RETURN operator attribution cryptographically to the actual signer of the payout, e.g., have the fronting operator co-sign (or key-path/script-path sign) a commitment that covers the OP_RETURN output (use `SIGHASH_ALL` or a script path enforcing operator-key check plus OP_RETURN equality), or require verifiers to additionally check that the payout transaction's non-output-0 inputs are provably controlled by the operator named in the OP_RETURN before accepting the attribution in `update_finalized_payouts`/before honoring `handle_finalized_payout`.

### Proof of Concept
Add a `cargo test` under `core/src/test` that: (1) generates a withdrawal signature via `generate_withdrawal_transaction_and_signature` (`core/src/test/common/setup_utils.rs:439-448`); (2) builds two `create_payout_txhandler` instances reusing the identical `user_sig`/`input_utxo`/`output_txout`, one with `operator_xonly_pk = A` (the true funder providing extra funding inputs) and one with `operator_xonly_pk = B` (a victim who contributes nothing); (3) broadcasts B's version and confirms it via the verifier's block sync path; (4) asserts `db.get_payout_info_from_move_txid(...).0 == Some(B)` while asserting the actual funding inputs of the mined transaction belong to A's wallet — demonstrating `payout_payer_operator_xonly_pk != true funder`, and that `PayoutCheckerTask` for operator B would proceed to call `handle_finalized_payout`.
