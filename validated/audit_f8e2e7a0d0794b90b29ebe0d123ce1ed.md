### Title
Payout OP_RETURN operator attribution is unauthenticated, letting anyone credit a false operator with a reimbursable payout - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` embeds an `operator_xonly_pk` in a plain OP_RETURN output that is completely outside the scope of the user's `SinglePlusAnyoneCanPay` signature, and `Verifier::update_finalized_payouts` blindly trusts whatever xonly-pubkey bytes appear in the first OP_RETURN of *any* transaction that happens to spend the registered withdrawal UTXO. Since the sighash flag only commits input 0 and output 0, anyone possessing the user's payout signature (including the withdrawing user/attacker themselves) can build and broadcast their own payout transaction with a forged OP_RETURN naming an arbitrary operator, causing that operator to be credited as the payer and later claim a `Reimburse` transaction for funds it never fronted.

### Finding Description
The claimed binding is:
`payout_payer_operator_xonly_pk (DB) == the xonly pubkey of the entity that actually funded output_txout`

Trace:
1. `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout tx with input 0 = withdrawal UTXO (key-spend, signed by the user), output 0 = user payout, output 1 = anchor, output 2 = `op_return_txout(operator_xonly_pk)`. The witness set via `set_p2tr_key_spend_witness(&user_sig, 0)` only covers input/output index 0 because the user signs with `TapSighashType::SinglePlusAnyoneCanPay` (verified in `Operator::withdraw`, `core/src/operator.rs:630-637`). Under `SIGHASH_SINGLE|ANYONECANPAY`, the signature commits to exactly one input and the output at the same index — **it does not sign the OP_RETURN output, the anchor, or any additional funding inputs**.
2. Anyone holding this signature (the withdrawing user is the trivial holder, since they created/authorized it via the Citrea `withdraw` call) can independently reconstruct this exact transaction shape, substitute the OP_RETURN payload with an arbitrary real operator's `XOnlyPublicKey::serialize()`, add their own funding input(s)/change, and broadcast it via any Bitcoin node before the real operator does.
3. On the verifier side, `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) just looks up whichever transaction spent the recorded `withdrawal_utxo_txid`/`vout` in a finalized block — no check on who broadcast it or funded it.
4. `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) then calls `get_first_op_return_output`/`parse_op_return_data` (`circuits-lib/src/bridge_circuit/mod.rs:608-617, 686-692`) on that transaction and writes the parsed bytes directly as `payout_payer_operator_xonly_pk` via `db.update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`) with **no verification that the named key corresponds to any input that funded the transaction**.
5. `Operator::PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) calls `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`), which surfaces this forged withdrawal to the named operator by that DB column alone, then `handle_finalized_payout`/kickoff/`Reimburse` flow proceeds to claim `bridge_amount` from the move-to-vault UTXO.
6. `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) only checks that the OP_RETURN-derived `operator_xonly_pk` equals `kickoff_data.operator_xonly_pk` — i.e., internal self-consistency between the (forged) OP_RETURN and the kickoff's claim — it never checks that the named operator actually supplied funding inputs to the payout tx. The bridge circuit (`circuits-lib/src/bridge_circuit/mod.rs:206-229`, `bridge-circuit-host/src/structs.rs:482-516`) similarly just re-derives `operator_xonlypk` from the same untrusted OP_RETURN and commits it into `deposit_constant` — it verifies consistency, not truth of funding.

No existing guard (`is_deposit_valid`, `SECP.verify_schnorr`, `is_kickoff_malicious`, `verify_storage_proofs`, `SPV::verify`, or any DB uniqueness constraint) ties the OP_RETURN attribution to actual on-chain evidence that the named operator's own UTXOs funded the payout.

### Impact Explanation
A named operator who never fronted a withdrawal can be made the "payer of record" for it purely by an attacker constructing and broadcasting their own competing transaction with a forged OP_RETURN. That operator's automated `PayoutCheckerTask`/`get_reimbursement_txs` flow will then spend its own kickoff/round collateral to eventually claim the `Reimburse` transaction, extracting `bridge_amount` from the shared move-to-vault UTXO for a payout it never paid — matching the Critical category "an operator reimbursed for a payout it never funded." This is repeatable per withdrawal and works against any operator whose xonly pubkey is public (all operator keys are public protocol data), so the blast radius spans every withdrawal and every operator.

### Likelihood Explanation
The only precondition is that the attacker is the withdrawing party itself (they already legitimately possess their own `SinglePlusAnyoneCanPay` signature from calling Citrea's `withdraw`), or has otherwise observed a broadcast/unconfirmed payout signature — both are within the stated unprivileged attacker capabilities. The attacker pays normal Bitcoin transaction fees to fund and broadcast the competing transaction before the legitimate operator's transaction confirms; no special hardware, key compromise, or protocol privilege is required, making this practically exploitable and repeatable across withdrawals.

### Recommendation
Do not derive `payout_payer_operator_xonly_pk` solely from an unauthenticated OP_RETURN payload. Bind the OP_RETURN commitment cryptographically to the funding inputs of the payout transaction (e.g., require the sighash to cover the OP_RETURN output, or require verification that at least one of the additional funding inputs is provably owned/spent by the named operator's known key before crediting the withdrawal to them in `update_finalized_payouts`).

### Proof of Concept
`cargo test` plan (outside `core/src/test/**`, conceptually — to be implemented by engineering):
1. Register a withdrawal (`input_outpoint`, `output_script_pubkey`, `output_amount`) and produce `user_sig` with `TapSighashType::SinglePlusAnyoneCanPay`, exactly as `Operator::withdraw` does.
2. Using `create_payout_txhandler`, build a payout transaction with `operator_xonly_pk = victim_operator_pk` but fund it with attacker-controlled inputs/outputs instead of the real operator's wallet (simulating the forged broadcast).
3. Feed this block through `Verifier::update_finalized_payouts` (or its DB-level equivalent `update_payout_txs_and_payer_operator_xonly_pk`) and assert:
   - LHS: `db.get_payout_info_from_move_txid(...).0 == Some(victim_operator_pk)`
   - RHS (ground truth): the funding inputs of the broadcast transaction do not include any UTXO controlled by `victim_operator_pk`.
4. Assert the equality claimed by the ATTRIBUTION binding is violated (LHS attributes to `victim_operator_pk` while RHS shows attacker-controlled funding), and that `get_first_unhandled_payout_by_operator_xonly_pk(victim_operator_pk)` returns this withdrawal despite `victim_operator_pk` never having spent funds.
