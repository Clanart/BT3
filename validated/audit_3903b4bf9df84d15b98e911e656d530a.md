## Finding

### Title
Consensus relayer rewards use the **current** `cost_per_block` rate for the entire un-rewarded height backlog instead of the rate(s) in effect when those blocks were produced - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::calculate_reward` computes relayer rewards as `(latest_height - baseline) * block_cost`, where `block_cost` is read once, at submission time, from `StateMachinesCostPerBlock`. There is no historical/epoch-scoped rate — the single currently-configured rate is applied retroactively to the *entire* un-rewarded span since `LastRewardedHeight`. This is the exact bug class from the external report: a rate/commission change intended to apply prospectively is instead applied to a backlog that should have been priced (at least partially) at the old rate.

### Finding Description
`update_cost_per_block` overwrites `StateMachinesCostPerBlock` in place with no versioning and no snapshot of "when this rate becomes effective": [1](#0-0) 

`calculate_reward` then multiplies the *whole* backlog of blocks (`latest_height - baseline`, where `baseline` is `LastRewardedHeight` — which only advances when a reward is actually paid) by whatever `block_cost` happens to be configured at the moment the message is processed: [2](#0-1) 

`on_executed` collapses a batch of `StateMachineUpdated` events down to a single highest `latest_height` per state machine and pays once per batch, so a relayer can legitimately withhold consensus message submission across many blocks/epochs, accumulating a large backlog before finally submitting: [3](#0-2) 

Because `block_cost` is a single mutable value with no history, if governance raises the rate (a routine parameter update, not an attack) while a relayer's backlog is outstanding, the *entire* backlog — including all blocks that accrued under the old, lower rate — is paid out at the new, higher rate the instant the relayer submits. This is the same corrupted-value pattern as the reported `staking_pool::advance_epoch` bug: the current settlement calculation reads a rate that was only meant to apply going forward, not to already-elapsed periods.

### Impact Explanation
The reward is paid by `T::Currency::transfer` from `TreasuryAccount` to the relayer: [4](#0-3) 

An inflated `block_cost` applied to a large backlog directly drains the treasury by an amount the protocol never intended to pay for those historical blocks — this is a real "loss of funds" / incorrect-value-used-in-settlement issue, not a griefing or DoS concern. The magnitude scales with how large a backlog the relayer allows to build up and how much the rate increases, and since a single relayer submission pays for the full backlog in one shot, the overpayment is realized atomically and irreversibly (transfer + `ReputationAsset::mint_into`).

### Likelihood Explanation
No malicious relayer, prover, or admin behavior is required. `update_cost_per_block` is an ordinary governance action a chain operator would perform periodically to adjust incentive economics; a relayer needs only to withhold submission (a permissionless choice already possible under the protocol, since consensus messages are batched and submission timing is relayer-controlled) until after a rate increase is announced/executed, then submit the backlog. There is no code path that splits the reward calculation across the rate-change boundary, so this mispricing occurs on essentially every rate increase for any relayer with an outstanding un-rewarded span at the time.

### Recommendation
Track the rate applicable to each block/epoch rather than a single mutable current value, e.g.:
- Store `(effective_from_height, cost_per_block)` history per `StateMachineId`, and when computing `calculate_reward`, split the `[baseline, latest_height]` span at each rate-change boundary, charging each sub-span with the rate that was active during it.
- Alternatively, force relayers to checkpoint/claim rewards synchronously on each `update_cost_per_block` call (paying out the backlog at the old rate before the new rate takes effect) so no backlog can straddle a rate change.

### Proof of Concept
1. Governance calls `update_cost_per_block(state_machine_id, 10)` (rate = 10).
2. State machine `X` advances consensus height from 100 → 1000 over real time, but the relayer withholds submitting the `ConsensusMessage`s (nothing forces immediate submission; `LastRewardedHeight` stays at 100).
3. Governance later calls `update_cost_per_block(state_machine_id, 1000)` for legitimate reasons unrelated to this relayer (e.g. repricing for a different, currently-active relayer set).
4. The withholding relayer now submits a consensus message that advances `latest_commitment_height` to 1000+.
5. `calculate_reward` computes `blocks = 1000 - 100 = 900` and multiplies by the *current* `block_cost = 1000`, yielding `900_000` instead of the `9_000` that should have applied under the rate in effect (10) for those 900 blocks — a 100x overpayment funded directly from `TreasuryAccount`. [5](#0-4)

	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
