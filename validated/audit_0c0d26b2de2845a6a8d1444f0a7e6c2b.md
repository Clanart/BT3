I have enough evidence now. The finding is confirmed: `_orders[commitment][token]` records a fixed, static integer amount at `placeOrder` time, and every release path (`_withdraw` in `IntentsBase.sol`, `withdraw` in the Tron `IntentGatewayV2.sol`, and `IntentGatewayV2.sol`'s fill/cancel flows) transfers exactly that stored integer via `safeTransfer`/`transfer` rather than measuring the contract's actual token balance at release time. This is the precise architectural analog to the stETH bug: any rebasing/interest-bearing ERC-20 used as an order's input token will have its escrowed balance in the gateway grow (or shrink) while the order sits unfilled, and that delta is never reconciled anywhere except the one-time fee-on-transfer/dust check performed inline during the `transferFrom` in `placeOrder` — which cannot see balance changes that accrue *after* escrow, only fee-on-transfer effects that happen *during* the transfer itself.

### Title
Rebasing/interest-bearing ERC-20 input tokens cause escrow surplus (or deficit) to become permanently stranded in IntentGatewayV2/IntentsBase escrow accounting - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The Intent Gateway (`IntentGatewayV2.sol`, and the V2 `intentsv2` variants `IntrinsicIntents.sol` / `ExtrinsicIntents.sol` built on `IntentsBase.sol`) escrows arbitrary ERC-20 tokens for arbitrary durations (bounded only by `order.deadline`, which a user freely chooses) and tracks the escrowed amount as a static integer in `_orders[commitment][token]`. Every withdrawal path pays out exactly that stored integer, never the contract's live token balance. If the escrowed token is a rebasing or interest-accruing ERC-20 (the exact `stETH` class named in the external report, or any similar yield-bearing wrapper), value that accrues to the gateway's balance during the escrow window is never credited to any order and becomes permanently stuck, identical in mechanism to the referenced Sherlock finding on Mellow's `DepositQueue`.

### Finding Description
`_orders` is declared as a flat integer ledger: [1](#0-0) 

At `placeOrder` time, the gateway *does* measure actual balance deltas to correctly account for fee-on-transfer tokens (subtracting transfer fees), e.g.: [2](#0-1) 

But this balance measurement only covers the instant of the `transferFrom` call. Nothing re-measures the contract's balance at release time. `_withdraw` (used by both fill-settlement and refund/cancel paths in `IntentsBase.sol`) transfers the stored `amount` field verbatim: [3](#0-2) 

The same pattern exists in the standalone `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol`) and its Tron port (`evm/tron/contracts/apps/IntentGatewayV2.sol:682-721`), all of which decrement `_orders[...]` by, and transfer, the fixed recorded `amount` rather than the current `balanceOf(address(this))`.

Order lifetimes are attacker/user-controlled and can be arbitrarily long — `order.deadline` is just a block number the placing user picks, with no protocol-enforced maximum, as documented: [4](#0-3) 

So any user can place an order using a rebasing/yield-bearing ERC-20 (e.g., `stETH`, or any similarly-behaved token) as an input, set a long deadline, and let the token's underlying rebase mechanism inflate the gateway's actual balance for that token above the sum of all `_orders[...][token]` entries. When the order is eventually filled, cancelled, or refunded, only the originally recorded (pre-rebase) amount moves; the accrued surplus remains trapped in the gateway contract with no order, user, or automatic mechanism entitled to claim it — the only recovery path is a governance-triggered `SweepDust` request, which is an out-of-band, discretionary redirection to a protocol-chosen beneficiary, not the token's rightful accruer.

This differs from the fee-on-transfer handling already in place: fee-on-transfer is measured synchronously inside the same call that creates the escrow record, so it's fully captured. Rebase accrual happens continuously over the *held* period after that record is fixed, and nothing in `_withdraw`/`withdraw` re-measures against `balanceOf`.

### Impact Explanation
This is a fund-lock issue against the "bridged assets... must move exactly once and only to the rightful beneficiary and amount" invariant: value that rightfully belongs to the order's placer (since they supplied the rebasing collateral) is diverted away from any specific beneficiary and stuck as undifferentiated contract balance, recoverable only through a privileged, discretionary `SweepDust` governance action that pays to whichever address governance names — not necessarily the user whose token accrued the yield. For high-TVL rebasing collateral (stETH-like tokens) held across many concurrent long-lived orders, this can represent continuous, unrecoverable-by-the-rightful-owner value leakage from user funds into unattributed contract dust.

### Likelihood Explanation
Triggering this requires only that an unprivileged user place an order (`placeOrder`) whose input token is a rebasing ERC-20 and let it sit in escrow for any nonzero period before being filled/cancelled/refunded — no malicious peer, relayer, prover, or governance actor is needed. The severity scales with the token's rebase magnitude and the order's dwell time in escrow, both of which the ordinary intent-order lifecycle already permits (long deadlines, unfilled orders awaiting solver bids, cross-chain round-trip latency for fills/cancels).

### Recommendation
For any input token flagged or known to be rebasing/interest-accruing, either (a) reject it at `placeOrder` via an explicit allow/deny-list, (b) measure `balanceOf(address(this))` deltas at withdrawal time the same way `placeOrder` already does for fee-on-transfer tokens and credit any positive surplus back to the order's beneficiary (or split it under a defined policy) rather than to governance-controlled dust, or (c) require only non-rebasing wrapped forms (e.g., `wstETH` instead of `stETH`) as documented mitigation for this exact bug class in the referenced report.

### Proof of Concept
1. Deploy a `MockRebaseERC20` analogous to the one in the referenced Sherlock report (balance = internal shares × sharePrice / 1e18), mint shares to a `user`.
2. `user` calls `placeOrder` with this token as `order.inputs[0]`, escrowing `X` tokens; `_orders[commitment][token] = X` is recorded per [5](#0-4) 
3. Advance the mock token's `sharePrice` upward (simulating stETH's daily positive rebase) — `IERC20(token).balanceOf(address(intentGateway))` now exceeds `X`.
4. Have the order legitimately filled or cancelled; `_withdraw`/`withdraw` releases exactly `X` (per the stored `_orders` value), per [6](#0-5) 
5. Assert `IERC20(token).balanceOf(address(intentGateway)) > 0` after the withdrawal and after `_orders[commitment][token] == 0` — the rebase surplus remains stranded in the gateway with no order referencing it, recoverable only via a governance `SweepDust` call to an arbitrary beneficiary.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
