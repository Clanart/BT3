### Title
Queued bribe backlog is fully assignable to a single post-quiet-period voter due to naive totalSupply==0 flush in `_provisionReward()` - (File: rewards/BaseRewardPoolV2.sol / rewards/BribeRewardPool.sol)

### Summary
`BribeRewardPool` inherits `_provisionReward()` from `BaseRewardPoolV2` unmodified. Whenever `totalStaked()` (i.e. `totalSupply`) is zero, incoming bribe donations are parked in `rewards[_rewardToken].queuedRewards` instead of being distributed, and the *entire* backlog is dumped into `rewardPerTokenStored` at the moment `totalStaked()` becomes non-zero again [1](#0-0) . Because `stakeFor` lets the operator (the `WombatBribeManager`, driven by a voter's own `vote()` call) register an arbitrary `_amount`/`_for` pair as the *first* stake after such a quiet period [2](#0-1) , that single voter's balance becomes the sole denominator dividing the whole backlog, letting them claim a reward vastly disproportionate to the time/weight they actually contributed.

### Finding Description
- `BribeRewardPool.totalStaked()` returns the pool's own `totalSupply`, which is incremented/decremented only through `stakeFor`/`withdrawFor`, both gated by `onlyOperator` (the `WombatBribeManager`) [3](#0-2) [2](#0-1) .
- Bribe donations flow through the inherited `donateRewards`/`queueNewRewards` → `_provisionReward()` path [4](#0-3) .
- In `_provisionReward()`, if `totalStaked() == 0` at the time of a donation, the reward is added to `queuedRewards` and `rewardPerTokenStored` is *not* updated [5](#0-4) . On the next donation where `totalStaked() > 0`, the *entire* accumulated `queuedRewards` balance is added on top of the new donation and divided by whatever `totalStaked()` happens to be at that instant [6](#0-5) .
- There is no time-weighting, vesting, or per-block/per-epoch accrual check — the flush is instantaneous and retroactive to whoever holds `_balances[_for]` at that moment.
- If a bribe pool's `totalSupply` drops to zero (all voters unvote from that pool/gauge) while bribe donations for that reward token keep arriving (a normal occurrence for actively-bribed gauges), the backlog can grow large. The first account to call `vote()` (routed to `stakeFor(_for, _amount)`) after that quiet period — and before/at the moment the next donation flush occurs — captures essentially the whole backlog for a `_amount` that can be minimal relative to what would normally be required to earn that much reward.
- No existing check reconciles `queuedRewards` against the `totalSupply` that existed while it accrued; the modifier `updateRewards` only reads the *current* `rewardPerTokenStored`/`balanceOf`, so it does not protect against this front-running/sniping pattern [7](#0-6) .

**Caveat (unverified):** I was not able to complete reading `WombatBribeManager.vote()` in this session (ran out of tool iterations) to confirm precisely how `_for` and `_amount` passed into `stakeFor` map to a voter's actual veWOM/vote-weight allocation (e.g., whether `_for` is forced to `msg.sender`, whether `_amount` is bounded by the caller's real unused voting power, and whether unvoting/`withdrawFor(claim=true)` can be triggered in the same or an adjacent transaction as the flush). This is material to precisely bounding "how cheaply" an attacker can manufacture the sole-staker condition, though the underlying `_provisionReward` flaw itself is confirmed directly in code.

### Impact Explanation
If exploitable as described, this allows an unprivileged voter to redirect a large backlog of bribe rewards — intended to be shared pro-rata among all voters who supported that gauge over the quiet period — entirely to themselves by being the sole/first staker when the backlog flushes. This matches "Direct theft of user funds" (rewards rightfully belonging to prior/other bribe depositors or to the protocol's reward accounting are diverted to a single attacker).

### Likelihood Explanation
Preconditions: a specific bribe-reward-token pool must have `totalSupply == 0` (no active voters) while bribe donations continue to accrue as `queuedRewards`, which is a plausible, attacker-observable/attacker-waitable on-chain state (not attacker-induced governance abuse). The attacker only needs enough veWOM/voting power to cast a nonzero (even minimal) vote to that pool right as/before the next donation triggers the flush, and the ability to withdraw/claim afterward — all through the standard permissionless `vote()`/`unvote()` flow. This is realistically front-runnable by watching for `queueNewRewards`/`donateRewards` transactions targeting a zero-`totalSupply` bribe pool.

### Recommendation
Redesign `_provisionReward()` to avoid retroactively assigning backlog rewards to whichever balance happens to exist at flush time. Options: (1) timestamp-weight the backlog so it streams/vests over time rather than crediting instantaneously to the current staker snapshot, (2) refuse to flush `queuedRewards` into `rewardPerTokenStored` when totalStaked/`totalSupply` was zero for the entire relevant period and instead route it back to the reward source/treasury or split by measured presence duration, or (3) require a minimum bonding/vote-lock duration before a staker's balance can be credited against previously-queued (pre-existing) rewards.

### Proof of Concept
Hardhat test plan (against `BribeRewardPool` + a mock operator standing in for `WombatBribeManager`):
1. Deploy `BribeRewardPool` with a reward token and a manager; deploy a mock ERC20 reward token and mint to a "briber" account.
2. Ensure `totalSupply() == 0` (no stakers).
3. Briber calls `donateRewards(1000e18, rewardToken)` — assert `rewards[rewardToken].queuedRewards == 1000e18` and `rewardPerTokenStored == 0`.
4. Repeat step 3 a few times to simulate a quiet-period backlog, e.g. total `queuedRewards == 5000e18`.
5. Attacker (via mock operator simulating `vote()`) calls `stakeFor(attacker, 1)` (delta = 1 wei of stake) — table over delta ∈ {1, 1e6, 1e18} and beneficiary ∈ {attacker EOA, attacker-controlled contract}.
6. Briber calls `donateRewards(1e18, rewardToken)` again, triggering the flush since `totalStaked() > 0` — assert `rewardPerTokenStored` jumps by `(5001e18 * 1e18) / totalSupply`.
7. Attacker calls `withdrawFor(attacker, delta, true)` (via mock operator) to claim — assert attacker receives ≈ entire 5001e18 backlog regardless of how small `delta` was, and that no other account (e.g., a "victim" who staked before the quiet period and is expected to have unsettled/pending accounting) receives any share.
8. Assert the invariant violation: `attacker's claimed reward / backlog >> attacker's stake-time-weighted share of total stake-time`, demonstrating the backlog was not reconciled with `totalSupply at the moment of accrual`.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
