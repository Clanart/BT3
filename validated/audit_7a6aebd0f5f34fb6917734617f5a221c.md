## Title
Per-`Repository`-object concurrency guards (`isCommitting`/`isPushPullFetchInProgress`) can be bypassed when the same underlying `.git` directory is added to Desktop under two different paths - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The Solidity bug's broken invariant is: a security/rate-limit check keyed on caller *identity* (`msg.sender`) is trivially defeated when the caller routes the action through a different identity (an intermediary contract) that still reaches the same protected state. Desktop's structural analog is the set of "only one operation in flight" guards in `AppStore` — `withIsCommitting`, `withPushPullFetch`, and `withIsGeneratingCommitMessage` — which are keyed on a `Repository` *object* via `repositoryStateCache`, not on the actual on-disk git directory the operation touches.

### Finding Description
`AppStore` protects git-mutating operations with simple boolean flags stored per `Repository` in `repositoryStateCache`: [1](#0-0) [2](#0-1) 

These guards assume that a `Repository` entity in Desktop's database corresponds 1:1 with a unique git working tree/object database. However, repository de-duplication in `_addRepositories` only compares the *string path* returned by `getRepositoryType` against existing repositories — it does not resolve the underlying git common-dir (`.git` object database, refs, worktree metadata) to a canonical identity: [3](#0-2) [4](#0-3) 

Git supports linked worktrees, where multiple independent working directories (each with its own `.git` *file* pointing at `gitdir: <common>/.git/worktrees/<name>`) share the exact same object database, refs, and index/HEAD lock semantics as the primary repository. A cloned/fetched repository can legitimately contain such a `.git` file. If a user adds two such directories to GitHub Desktop (e.g., the primary clone and a linked worktree pointing back into it, or two clones that happen to share the same `.git` common dir via crafted worktree metadata delivered inside a malicious fetched repo), Desktop creates two distinct `Repository` records with two distinct `path` strings and two distinct entries in `repositoryStateCache`. The "no concurrent push/pull/commit" invariant is enforced independently for each `Repository` object, exactly like `_notSameBlock()` being keyed per `msg.sender` instead of per underlying resource — routing the action through a second "identity" (the second `Repository` entry) sidesteps the guard entirely.

### Impact Explanation
Because `withIsCommitting`/`withPushPullFetch` do not share state across `Repository` objects that resolve to the same underlying `.git` common directory, two Desktop tabs/windows for the "same" repository (attacker-supplied via a crafted worktree layout in a cloned/fetched repo) can run concurrent `git commit`, `git push`, `git pull`, or commit-message-generation operations against shared refs, index, and object database. Git's own locking (`index.lock`, `HEAD.lock`) is per common-dir, but interleaved Desktop-orchestrated multi-step flows (stage → hook → commit → refresh, or fetch → fast-forward → refresh) rely on the app-level mutex, not solely on git's file locks, to sequence safely. Concurrent execution risks partial/failed operations, stale ref updates being pushed, or index corruption — i.e. silent corruption of what the user commits or pushes, which is in-scope per the stated valid-impact criteria.

### Likelihood Explanation
Requires only that a user open/add a maliciously crafted or ordinary linked-worktree repository twice in Desktop (a normal, expected user action when a fetched/cloned repo legitimately contains worktree metadata) and then perform overlapping actions (e.g., two pushes, or a push while a commit-message generation/commit is in flight) across the two "repository" entries. No local/admin access or credentials are needed beyond normal use of Desktop with an attacker-influenced repository, matching the report's requirement that the attacker controls a cloned/fetched repository.

### Recommendation
- Key `repositoryStateCache`'s concurrency flags (`isCommitting`, `isPushPullFetchInProgress`, `isGeneratingCommitMessage`) on the resolved git common directory (`git rev-parse --git-common-dir`), not on the `Repository` object/path, so that multiple Desktop `Repository` entries sharing the same underlying git data are mutually exclusive.
- When adding a repository, resolve and record the git common directory and reject/merge additions that resolve to a common dir already tracked by another `Repository` entry, similar to how `matchExistingRepository` already dedupes by path.

### Proof of Concept
1. Clone/fetch a repository `A` at `~/A`.
2. From `A`, create a linked worktree at `~/B` (`git worktree add ../B`), or receive a malicious fetched archive already structured this way (`~/B/.git` containing `gitdir: ~/A/.git/worktrees/B`).
3. In GitHub Desktop, add both `~/A` and `~/B` as separate repositories (they have different `path` values so `matchExistingRepository` treats them as distinct entries) — see `app/src/lib/stores/app-store.ts:8124-8142`.
4. Trigger a push from `~/A`'s Desktop tab and, before it completes, trigger a commit or push from `~/B`'s tab.
5. Because `withPushPullFetch`/`withIsCommitting` guards are tracked per-`Repository` object (`app/src/lib/stores/app-store.ts:5364-5450`), both operations proceed concurrently against the shared object database/refs, unlike the intended "single operation per repository" invariant.

  private async withIsCommitting(
    repository: Repository,
    fn: () => Promise<boolean>
  ): Promise<boolean> {
    const state = this.repositoryStateCache.get(repository)
    // ensure the user doesn't try and commit again
    if (state.isCommitting) {
      return false
    }

    this.repositoryStateCache.update(repository, () => ({
      isCommitting: true,
      hookProgress: null,
      subscribeToCommitOutput: null,
    }))
    this.emitUpdate()

    try {
      return await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isCommitting: false,
        hookProgress: null,
        subscribeToCommitOutput: null,
      }))
      this.emitUpdate()
    }
  }

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }

  public async addRepository(
    path: string,
    gitDir: string | undefined,
    opts?: AddRepositoryOptions
  ): Promise<Repository> {
    const repository = await this.db.transaction(
      'rw',
      this.db.repositories,
      this.db.gitHubRepositories,
      this.db.owners,
      async () => {
        const existing = await this.db.repositories.get({ path })

        if (existing !== undefined) {
          return await this.toRepository(existing)
        }

        const dbRepo: IDatabaseRepository = {
          path,
          gitHubRepositoryID: null,
          missing: opts?.missing ?? false,
          lastStashCheckDate: null,
          alias: null,
          gitDir,
        }
        const id = await this.db.repositories.add(dbRepo)
        return this.toRepository({ id, ...dbRepo })
      }
    )
