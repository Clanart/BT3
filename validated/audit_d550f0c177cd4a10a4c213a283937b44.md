### Title
Quadratic-time transaction eviction in TxPool via linear heap scan in `txSortedMap.Remove` - ([File: blockchain/tx_list.go])

### Summary
`txSortedMap.Remove` locates a nonce's position in the internal `nonceHeap` by iterating over the entire heap slice before calling `heap.Remove`, making a single removal O(N) in the size of the account's transaction list. Several transaction-pool code paths that are reachable purely from unprivileged transaction submission call this removal function once per transaction in a loop, turning bulk eviction of a large per-account (or pool-wide) transaction set into O(N²) work — the same complexity class as the Envoy HTTP/2 stream-reset CPU-exhaustion bug (CVE-2021-32778), where per-stream reset processing scanned the full active list.

### Finding Description
`txSortedMap.Remove` performs a linear scan of `m.index` (the nonce heap) to find the index of the nonce being removed: [1](#0-0) 

This function is invoked by `txList.Remove`, which is in turn invoked by `TxPool.removeTx` for both the pending and queued transaction lists: [2](#0-1) [3](#0-2) 

An unprivileged sender fully controls the size of their own account's queue/pending list up to `NonExecSlotsAccount` / `ExecSlotsAll` limits by submitting many gapped-nonce transactions. Several pool maintenance paths then iterate over that list and call `removeTx` (and therefore `txSortedMap.Remove`) once per transaction, each call re-scanning the shrinking-but-still-large heap:

1. **Inactive-account (lifetime) eviction** — the pool's main event loop periodically flattens an account's entire queued list and removes each transaction one at a time: [4](#0-3) 

2. **Queue-cap eviction** — when the global queue exceeds `NonExecSlotsAll`, the pool flattens a stale account's list and removes transactions one at a time from the tail: [5](#0-4) 

3. **Underpriced-eviction on pool-full admission** — `add()` calls `pool.removeTx` in a loop over the `drop` set returned by `pool.priced.Discard`: [6](#0-5) 

In all three paths, an attacker who has caused a large `txSortedMap` (via a single account's queue/pending list, since the heap-scan cost is bound to the size of that particular list) to accumulate creates conditions where repeated single-item removals from that same list each cost O(N), yielding O(N²) total CPU time for the eviction/cleanup pass — directly analogous to Envoy's O(N²) HTTP/2 stream-reset handling that caused the CVE.

### Impact Explanation
An attacker submitting transactions to the public transaction pool (a `sendRawTransaction`-style unprivileged caller) can build up a large gapped-nonce queue for a single account (bounded by `NonExecSlotsAccount`/`NonExecSlotsAll`) and then trigger periodic eviction (lifetime ticker, queue-cap eviction, or repeated pool-full admission) to force the node to perform O(N²) work processing that single account's list. Doing this repeatedly (e.g., cycling through refill-and-expire, or keeping the pool at capacity so every new incoming transaction triggers underpriced eviction) can consume disproportionate CPU on every full node processing the mempool, degrading transaction processing and RPC responsiveness pool-wide — a resource-exhaustion / Denial-of-Service condition, matching the "High" severity class of the referenced CVE.

### Likelihood Explanation
The attack requires only submitting ordinary (even underpriced or gapped-nonce) transactions from a wallet the attacker controls — no privileged access, validator role, or peer-level trust is needed. The relevant configuration limits (`NonExecSlotsAccount`, `NonExecSlotsAll`, pool `Lifetime`, `evictionInterval`) are node-operator defaults rather than hard protocol limits, so the achievable list sizes depend on deployment configuration; I was unable to confirm the exact default numeric values for these constants in this pass (grep on the constant definitions did not resolve before the session ended), so the precise magnitude of N achievable by a single attacker under default settings is unverified and should be checked before treating this as immediately practically exploitable at scale.

### Recommendation
Replace the linear scan in `txSortedMap.Remove` with an O(log N) or O(1) lookup, e.g., maintain a `map[uint64]int` recording each nonce's current heap index (updated on `Swap`) so `heap.Remove` can be invoked directly without scanning, mirroring how go-ethereum/most heap-backed sorted-set implementations track positions. This removes the O(N) cost per removal and eliminates the O(N²) worst case in all eviction paths that call `removeTx` in a loop.

### Proof of Concept
Conceptual PoC (would need to be validated in a running node/test harness):
1. From a single funded account, submit N transactions with nonces `1, 3, 5, ..., 2N-1` (all non-executable/gapped) so they land in `pool.queue[addr]`, growing that account's `txSortedMap.index` to size N (bounded by `NonExecSlotsAccount`).
2. Either (a) let the account go idle past `pool.config.Lifetime` so the eviction ticker's `for _, tx := range pool.queue[addr].Flatten() { pool.removeTx(...) }` loop fires (blockchain/tx_pool.go:404-423), or (b) push the global queue past `NonExecSlotsAll` so `promoteExecutables`'s queue-cap eviction loop fires (blockchain/tx_pool.go:1864-1878), or (c) keep submitting transactions while the pool is at capacity so `add()`'s underpriced-eviction loop fires (blockchain/tx_pool.go:1198-1207).
3. Each of the N `removeTx` calls invokes `txSortedMap.Remove`, which does a full O(current heap size) scan to find the nonce's heap index (blockchain/tx_list.go:158-175), producing O(N²) CPU work for a single eviction pass instead of O(N log N).
4. Repeat by refilling the account's queue, amplifying CPU cost over time — analogous to the Envoy HTTP/2 stream-reset O(N²) CPU exhaustion.

// Remove deletes a transaction from the maintained map, returning whether the
// transaction was found.
func (m *txSortedMap) Remove(nonce uint64) bool {
	// Short circuit if no transaction is present
	_, ok := m.items[nonce]
	if !ok {
		return false
	}
	// Otherwise delete the transaction and fix the heap index
	for i := 0; i < m.index.Len(); i++ {
		if (*m.index)[i] == nonce {
			heap.Remove(m.index, i)
			break
		}
	}
	delete(m.items, nonce)
	m.cache = nil

	return true
}

// Remove deletes a transaction from the maintained list, returning whether the
// transaction was found, and also returning any transaction invalidated due to

func (l *txList) Remove(tx *types.Transaction) (bool, types.Transactions) {
	// Remove the transaction from the set
	nonce := tx.Nonce()
	if removed := l.txs.Remove(nonce); !removed {
		return false, nil
	}
	// In strict mode, filter out non-executable transactions
	if l.strict {
		return true, l.txs.Filter(func(tx *types.Transaction) bool { return tx.Nonce() > nonce })
	}
	return true, nil
}

func (pool *TxPool) removeTx(hash common.Hash, outofbound bool) {
	// Fetch the transaction we wish to delete
	tx := pool.all.Get(hash)
	if tx == nil {
		return
	}
	addr, _ := types.Sender(pool.signer, tx) // already validated during insertion

	// Remove it from the list of known transactions
	pool.all.Remove(hash)
	if outofbound {
		pool.priced.Removed()
	}
	// Remove the transaction from the pending lists and reset the account nonce
	if pending := pool.pending[addr]; pending != nil {
		if removed, invalids := pending.Remove(tx); removed {
			// strict-mode Remove also strips invalidated higher-nonce txs from pending.
			pool.pendingCount -= uint64(1 + len(invalids))
			// If no more pending transactions are left, remove the list
			if pending.Empty() {
				delete(pool.pending, addr)
			}
			// Postpone any invalidated transactions (re-enqueue bumps queuedCount).
			for _, tx := range invalids {
				pool.enqueueTx(tx.Hash(), tx)
			}
			pool.updatePendingNonce(addr, tx.Nonce())
			return
		}
	}
	// Transaction is in the future queue
	if future := pool.queue[addr]; future != nil {
		if removed, _ := future.Remove(tx); removed {
			pool.queuedCount--
		}
		if future.Empty() {
			delete(pool.queue, addr)
		}
	}
}
