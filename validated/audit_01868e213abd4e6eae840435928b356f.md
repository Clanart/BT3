## Title
Repo-rules "signed commits required" check relies solely on `commit.gpgsign` without validating that a signing key is actually configured, letting the required-signature warning be silently suppressed - ([File: app/src/lib/helpers/repo-rules.ts])

### Summary
The bug class in the seed report is: a boolean/amount flag (`escrowPortion`) is trusted to imply the existence of a coupled resource (`escrowPool` address) without validating that the resource is actually present, so the invariant "if the flag says X will happen, the resource for X must exist" is silently broken. The same broken-invariant shape exists in GitHub Desktop's repo-rules evaluation: it treats the boolean `commit.gpgsign` config value as proof that "commit signing is configured" and satisfies a `RequiredSignatures` ruleset, without verifying that the coupled resource needed to actually produce a valid signature (`user.signingkey` for OpenPGP, or `user.signingkey`/`gpg.format=ssh` + a usable SSH signing key) exists or is valid.

### Finding Description
`parseRepoRules` in [1](#0-0)  handles the `APIRepoRuleType.RequiredSignatures` case as follows:

```ts
case APIRepoRuleType.RequiredSignatures:
  // check if the user has commit signing configured. if they do, the rule
  // passes and doesn't need to be warned about.
  gpgSignEnabled ??=
    (await getBooleanConfigValue(repository, 'commit.gpgsign')) ?? false

  if (gpgSignEnabled !== true) {
    info.signedCommitsRequired =
      info.signedCommitsRequired !== true ? enforced : true
  }
  break
```

This is the only signal used to decide whether `info.signedCommitsRequired` should be flagged for the UI. The value of `commit.gpgsign` is coupled to (and meaningless without) a working signing key configuration — `user.signingkey` (and, for SSH signing, `gpg.format` plus a valid key/allowed-signers setup). The code never checks that a signing key is actually set or resolvable; it only checks the boolean toggle, exactly mirroring the seed bug's failure to verify that `escrowPool != address(0)` whenever `escrowPortion != 0`.

The resulting `RepoRulesInfo.signedCommitsRequired` value drives the commit UI warning logic in [2](#0-1) , which suppresses the "One or more rules ... require signed commits" `CommitWarning` banner whenever `gpgSignEnabled` is `true`, regardless of whether a real signing key backs that setting.

### Impact Explanation
If a repository or global git config has `commit.gpgsign = true` (e.g., inherited from a template, copied `.gitconfig`, or a stale/removed key) but no valid `user.signingkey` (or a broken `gpg.format=ssh` configuration), Desktop will:
- Report `signedCommitsRequired` as satisfied and hide the compliance warning, giving the user false confidence that their commits meet the branch's signature requirement.
- Allow the user to commit and attempt to push under this false assumption.

This corresponds to the "silent corruption of what the user commits or pushes" impact category: the user believes their commit satisfies a required-signatures rule and proceeds, when in fact the desktop client never validated that a real signing key exists to back that belief.

### Likelihood Explanation
This requires no attacker interaction beyond ordinary git configuration drift (e.g., a user removing/rotating a GPG/SSH signing key, cloning a repo whose local `.git/config` sets `commit.gpgsign=true` without a corresponding key, or a misconfigured global gitconfig). Because `getBooleanConfigValue` is the sole determinant and it consults local/global config that can easily fall out of sync with actual key availability, this is a plausible everyday misconfiguration rather than an exotic scenario.

### Recommendation
When evaluating `APIRepoRuleType.RequiredSignatures`, in addition to `commit.gpgsign`, verify that a usable signing key is actually configured (e.g., check `user.signingkey` is non-empty and, for `gpg.format=ssh`, that the referenced key/allowed-signers file is resolvable), and only treat the rule as satisfied when both the toggle and the coupled signing-key configuration are valid together.

### Proof of Concept
1. In a repository whose branch has a ruleset requiring signed commits, set `git config commit.gpgsign true` without ever configuring `user.signingkey` (or with a stale/removed key).
2. Open GitHub Desktop and view the commit box for that branch.
3. Observe that `parseRepoRules` sets `gpgSignEnabled = true` purely from `commit.gpgsign`, so `info.signedCommitsRequired` stays falsy and the "require signed commits" `CommitWarning` in `commit-message.tsx` is never rendered — even though no valid key exists to actually sign the commit.
