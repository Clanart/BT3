### Title
`git clone` explicitly disables Git's clone protection, re-enabling config/hooks injection via malicious submodules - (File: app/src/lib/git/clone.ts)

### Summary
GitHub Desktop's `clone()` helper invokes `git clone --recursive` while explicitly setting `GIT_CLONE_PROTECTION_ACTIVE=false` in the child process environment. This environment variable is the mechanism Git added to guard against known clone-time RCE/config-injection classes (e.g. the family of issues fixed around CVE-2024-32004/32020/32021/32465 and the general "hostile submodule/.git-config" clone hardening) where a cloned repository's on-disk `.git` contents (via `--recursive` submodules, symlinked git dirs, or crafted repository files) could smuggle configuration or hook state into the outer repository's Git directory. By actively forcing this protection off for every clone, Desktop invites exactly the primitive the report's bug class describes: an untrusted, attacker-controlled object (here, a cloned repository and its submodules) is allowed to influence privileged application state/behavior that the wrapper (Desktop) does not independently re-validate.

### Finding Description

and always passes `--recursive`: [2](#0-1) 

`GIT_CLONE_PROTECTION_ACTIVE` is Git's internal safety switch that detects and refuses to check out repository content that could smuggle hostile `.git` state through symlinks, case-folding tricks, or crafted directory structures during a clone (particularly relevant with `--recursive`, since each submodule is its own clone target under attacker control). Desktop does not merely fail to opt in to this protection — it actively force-disables it (`'false'`) on every single clone, including clones of arbitrary attacker-supplied URLs from the "Clone repository" dialog, "Open in Desktop" deep links, and fork/PR checkout flows.

Compare this to the parallel case in `updateSubmodulesAfterOperation` (used for checkout/pull), which is more conservative and gates `protocol.file.allow=always` behind an explicit `allowFileProtocol` flag: [3](#0-2) 

No equivalent conditional gating exists for `GIT_CLONE_PROTECTION_ACTIVE` — it's unconditionally off.

This mirrors the report's broken-invariant shape precisely: the "wrapper" (Desktop) is supposed to mediate and validate before allowing the "primitive" (Git's own clone/checkout machinery) to trust attacker-supplied repository content, but here the wrapper actively strips out the primitive's own defense, letting the attacker-controlled repository (the analog of "anyone submitting proofs to EigenPod directly") reach a path Desktop assumed was gated off.

### Impact Explanation
If Git's clone protection exists to stop a specific class of hostile-repository techniques from writing/executing outside the intended repository directory or corrupting local Git configuration/hooks during checkout of untrusted content, then disabling it unconditionally means:
- Cloning any attacker-supplied URL (including via Desktop's `x-github-client://openRepo` clone deep link flow) with recursive submodules processes submodule content without this backstop.
- This could result in file writes outside the intended clone directory, or local repository/hook configuration corruption — matching the report's required impact categories ("code execution, file write... outside the repo... or silent corruption of what the user commits").

### Likelihood Explanation
Likelihood is high for exposure (every clone goes through this code path unconditionally, no user interaction beyond initiating a clone of an attacker-supplied URL is required), but the actual exploitability depends on which specific Git version/attack technique `GIT_CLONE_PROTECTION_ACTIVE` currently guards against still being present in the bundled Git binary. I could not verify from the indexed code alone which exact CVE(s) or dugite/Git version this variable maps to, nor find a code comment in this repository explaining why the fix was set to `'false'` instead of left at the default (protection-on). This is a genuine uncertainty: it's possible there is a compensating reason recorded elsewhere (e.g. a Desktop-specific workaround for a benign compatibility issue), but no such justification is present in the searched files.

### Recommendation
- Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts`, or replace it with `'true'`/leave unset so Git's default protection applies.
- If the override exists to work around a real compatibility issue, document the specific issue and scope the override as narrowly as possible (e.g., only for verified same-origin/trusted clone sources), analogous to how `allowFileProtocol` is already gated in `submodule.ts`.
- Audit whether the equivalent protection is disabled anywhere else (e.g., `checkout.ts`'s submodule update path) since checkout also updates submodules recursively.

2. Regardless of the source's trustworthiness, `envForRemoteOperation(url)` result is merged with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` before invoking `git ... clone --recursive -- <url> <path>`: [4](#0-3)

Because `--recursive` is always passed, any submodules declared in the attacker's top-level repository are cloned and checked out with the protection mechanism disabled, giving the attacker's submodule content the same reduced-scrutiny path Git's own maintainers added protection specifically to close.

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
