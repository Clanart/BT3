## Analysis: Missing zero-check on KIP-71 `GasTarget` governance parameter causes divide-by-zero panic

The CVE describes a `cirrusfb` divide-by-zero because `pixclock` was never validated as non-zero before being used as a divisor. Kaia has a directly analogous bug in the KIP-71 dynamic base-fee (Magma) computation: `BaseFeeDenominator` is explicitly protected from being zero, but the equally-required `GasTarget` divisor is not.

### Root cause

`NextMagmaBlockBaseFee` divides by `gasTarget` in both the "gas used above target" and "gas used below target" branches: [1](#0-0) [2](#0-1) [3](#0-2) 

Note that `BaseFeeDenominator == 0` is explicitly guarded against (falls back to 64), but `gasTarget := kc.GasTarget` has **no equivalent guard**. If `GasTarget == 0` and `parentGasUsed > 0` (any block that used gas), execution takes the "above target" branch and computes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor, which panics in Go's `math/big`.

### How `GasTarget` can become zero

`Kip71GasTarget` is registered with a `noopFormatChecker` — unlike `Kip71BaseFeeDenominator`, which explicitly rejects zero: [4](#0-3) 

The header-governance consistency check (`checkConsistency`) also lets `Kip71GasTarget` votes through without any bounds validation — it falls into the catch-all branch that accepts the value as long as it passed `NewVoteData()`'s format check (which is the no-op one above): [5](#0-4) 

Compare this to `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`, which do get dedicated consistency checks in the same function.

### Reachability and impact

This value is set via `governance_vote`, cast by the governing node (or GC in `none` mode), ratified at epoch boundaries, and then affects `NextMagmaBlockBaseFee` used by both block header verification and block assembly: [6](#0-5) [7](#0-6) 

Once a `GasTarget = 0` vote is ratified and takes effect, **every node** (validators and full nodes) computing/verifying the base fee for the next block with `GasUsed > 0` will panic inside `NextMagmaBlockBaseFee`, called from `VerifyMagmaHeader`/`BlockValidator.ValidateHeader` and from the fee-history/gas-price oracle path: [8](#0-7) 

This crashes the node process on every honest node processing that block — a chain-halting consensus-critical DoS, matching the "state divergence / acceptance of invalid transaction or block" impact bar, and directly analogous to the CVE's divide-by-zero-by-unvalidated-input bug class.

### Title
Missing zero-check on KIP-71 `GasTarget` governance parameter causes divide-by-zero panic in `NextMagmaBlockBaseFee` - (File: `params/kip71_config.go`)

### Summary
`NextMagmaBlockBaseFee` divides by `kc.GasTarget` without checking it for zero, while the sibling `BaseFeeDenominator` parameter has an explicit zero-guard. The `Kip71GasTarget` governance parameter uses a `noopFormatChecker` and has no dedicated consistency check, so a `GasTarget = 0` value can be ratified through the normal governance-vote flow.

### Finding Description
`params/kip71_config.go`'s `NextMagmaBlockBaseFee` computes `baseFeeDelta` using `x.Div(x, gasTarget)` when `parentGasUsed != gasTarget`. There is no fallback for `gasTarget == 0` (unlike `baseFeeDenominator`, which defaults to 64 when zero). `kaiax/gov/param.go` registers `Kip71GasTarget` with `noopFormatChecker`, and `kaiax/gov/headergov/impl/header.go`'s `checkConsistency` does not add any additional bound check for it, so nothing in the vote-validation pipeline stops `GasTarget` from being set to 0.

### Impact Explanation
Once ratified, `GasTarget = 0` causes every node computing or verifying the base fee for any block with nonzero `GasUsed` to panic in `math/big.Int.Div`, crashing the node process. Because this function is invoked from block header verification/assembly on every node, this is a chain-halting, consensus-critical denial of service affecting the entire network, not merely a single node.

### Likelihood Explanation
Requires a single ratified governance vote setting `governance.kip71.gastarget` to `0`, cast by the governing node (single mode) or a GC member (none mode) via the standard `governance_vote` API — no code path exists to prevent or reject this value.

### Recommendation
Add a zero-check for `GasTarget` in `kaiax/gov/param.go`'s `Kip71GasTarget` `FormatChecker` (reject zero, mirroring `Kip71BaseFeeDenominator`), and/or add a defensive fallback for `gasTarget == 0` in `NextMagmaBlockBaseFee` symmetrical to the existing `baseFeeDenominator` handling.

### Proof of Concept
1. Governing node calls `governance_vote("governance.kip71.gastarget", 0)`.
2. Vote is ratified at the next epoch boundary (passes `checkConsistency` unchanged, since `Kip71GasTarget` falls into the no-extra-check branch).
3. At the block after the ratification takes effect, any block with `GasUsed > 0` triggers `NextMagmaBlockBaseFee` to execute `x.Div(x, new(big.Int).SetUint64(0))`, panicking every node validating/building that block.
