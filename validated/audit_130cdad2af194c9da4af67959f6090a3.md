### Title
Payout tx's OP_RETURN operator identity is unauthenticated and forgeable — enables an operator to be reimbursed for a payout it never funded - ([File: circuits-lib/src/bridge_circuit/mod.rs])

### Summary
The payout transaction's user-facing output (the actual withdrawer payment) is signed by the user with `SinglePlusAnyoneCanPay`, which under BIP341 only commits to input 0 and the output at the same index (output 0) [1](#0-0) . The OP_RETURN output that encodes `operator_xonly_pk` (the claimed payer identity) sits at a different output index and is never covered by that signature [2](#0-1) . Both the bridge circuit and the verifier's off-chain bookkeeping blindly trust whatever OP_RETURN is found first via `get_first_op_return_output`/`parse_op_return_data`, with no check that the entity who actually funded/broadcast the payout matches the embedded key.

### Finding Description
The binding claimed by the protocol is:
`op_return_operator_xonly_pk (extracted by get_first_op_return_output + parse_op_return_data) == xonly_pk of the party whose funds actually paid the withdrawer in payout_tx`

This binding is never enforced anywhere in the code path.

- `create_payout_txhandler` builds a 3-output payout tx: output 0 = user payment, output 1 = anchor, output 2 = OP_RETURN with `operator_xonly_pk` [3](#0-2) . The only cryptographic commitment protecting this transaction is the user's `SinglePlusAnyoneCanPay` signature over input 0, enforced in `parse_withdrawal_sig_params` [4](#0-3) .
- `calculate_pubkey_spend_sighash`/`calculate_script_spend_sighash` show that for `SinglePlusAnyoneCanPay`, `Prevouts::One` is used and, per BIP341 semantics, `SIGHASH_SINGLE` only binds the output whose index equals the signed input's index (index 0) — outputs 1 and 2 (anchor, OP_RETURN) are completely unbound by the signature [5](#0-4) .
- Anyone possessing this signature (the withdrawer themselves, who legitimately obtains it by calling `withdraw`/`internal_withdraw`) can therefore build an alternative transaction that: keeps input 0 and output 0 unchanged (so the sighash and Schnorr signature still verify), funds any additional inputs from their own wallet (`ANYONECANPAY` permits arbitrary extra inputs), and inserts an arbitrary OP_RETURN (or multiple OP_RETURNs) with any `operator_xonly_pk` of their choosing.
- `get_first_op_return_output` simply returns the first output for which `is_op_return()` is true, with no uniqueness or ownership check [6](#0-5) , and `parse_op_return_data` just extracts the first push after `OP_RETURN` [7](#0-6) . The bridge circuit uses exactly this untrusted value to compute `deposit_constant` [8](#0-7) .
- Off-chain, `update_finalized_payouts` performs the identical unauthenticated extraction and stores it as `payout_payer_operator_xonly_pk` in the DB [9](#0-8) .
- This DB value is then treated as ground truth: `is_kickoff_malicious` only flags a kickoff malicious if the stored OP_RETURN operator key differs from the operator who is running the kickoff — if they match (which the attacker fully controls), the kickoff is accepted as legitimate [10](#0-9) ; `send_asserts` performs the same trust-based comparison [11](#0-10) ; and `get_first_unhandled_payout_by_operator_xonly_pk` lets an operator's own automation locate "its" unhandled payouts purely by this attacker-controlled column [12](#0-11) .

Exploit flow: An attacker who is themselves the withdrawer (or colludes with one) fronts their own withdrawal payout using their own BTC (paying output 0 to their own withdrawal address as usual, using the legitimately-obtained `SinglePlusAnyoneCanPay` signature), but stamps a targeted, uninvolved operator's public `xonly_pk` (operator public keys are exposed via `GetXOnlyPublicKey`) into the payout tx's OP_RETURN instead of their own. Once this transaction confirms and is picked up by `update_finalized_payouts`, the targeted operator's own automation (`get_first_unhandled_payout_by_operator_xonly_pk` → `send_asserts` → kickoff) will believe it fronted this payout and initiate the reimbursement flow. Since `is_kickoff_malicious`'s only identity check trivially passes (both sides equal the attacker-chosen key), verifiers do not challenge, and the targeted operator is credited/reimbursed by the round/kickoff/reimburse transaction graph for a payout it never funded.

No existing guard (`SECP.verify_schnorr` on the user signature, `Verifier::is_kickoff_malicious`, `verify_storage_proofs`, `SPV::verify`) checks that funding inputs of the payout tx, or the OP_RETURN content, originate from or are authorized by the claimed operator.

### Impact Explanation
This directly matches the Critical category "an operator reimbursed for a payout it never funded." The targeted operator's collateral/round-tx chain is used to claim a reimbursement from the bridge's escrow/vault flow for BTC that operator never spent, while the actual withdrawer's payment was funded entirely by the attacker (frequently the withdrawer itself, effectively paying themselves and diverting the operator's protocol-level compensation to a party who never fronted funds). This is repeatable across every withdrawal and every known operator xonly_pk (all public), so the blast radius spans the entire operator set and every future withdrawal.

### Likelihood Explanation
- Preconditions: attacker must be a legitimate withdrawer with a valid `SinglePlusAnyoneCanPay` signature for a withdrawal (trivially available since any user can call `withdraw`), and must be willing to front the withdrawal amount from their own BTC (they need funds equal to the payout amount plus fees — no privileged access required).
- Operator public keys are advertised via gRPC (`GetXOnlyPublicKey`), so the attacker can pick any target operator without insider knowledge.
- No majority-hashrate, key compromise, or verifier collusion is required — this exploits a pure signature/commitment gap (SIGHASH_SINGLE|ANYONECANPAY not covering the OP_RETURN) plus blind trust of `get_first_op_return_output`.
- Fully reproducible offline with `cargo test` (no mainnet, no live Citrea) by constructing two payout tx variants sharing input 0/output 0 and differing only in OP_RETURN content, and observing that `deposit_constant`/`operator_xonly_pk` extraction diverges from the true funder.

### Recommendation
Bind the OP_RETURN operator identity cryptographically to the payout transaction's signature/funding, e.g.:
- Require the payout tx signature to use a sighash type that covers all outputs (e.g., `SIGHASH_ALL`) for the operator-controlled outputs, or have the operator co-sign (in addition to the user) the entire transaction including the OP_RETURN output.
- Alternatively, require `get_first_op_return_output`/`is_kickoff_malicious`/`update_finalized_payouts` to additionally verify that the funding inputs of the payout tx (beyond the user's withdrawal UTXO) are attributable to the operator claimed in the OP_RETURN (e.g., via a signature over the OP_RETURN content by that operator's key, verified with `SECP.verify_schnorr`).
- Reject/flag payout transactions containing more than one OP_RETURN output outright.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,

    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

/// Parses the OP_RETURN data from a Bitcoin script. It retrieves the first data push after an OP_RETURN.
pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {
        if let Some(Ok(Instruction::PushBytes(data))) = instructions.next() {
            return Some(data.as_bytes());
        }
    }
    None
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
