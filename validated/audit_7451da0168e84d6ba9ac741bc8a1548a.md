### Title
Balance-desync between EVM StateDB and native bank balance via shared `BalanceHandler` state across recursive/reentrant precompile calls - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
This is the closest reachable Cosmos EVM analog to the Exactly `checkLiquidation()` bug: a "snapshot then compute-diff-later" pattern (`BeforeBalanceChange` / `AfterBalanceChange`) whose snapshot marker (`prevEventsLen`) can be silently overwritten by a nested/recursive execution before the outer computation runs, causing the derived balance delta applied to `StateDB` to be wrong. The repository itself ships a dedicated regression test acknowledging this exact defect class.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records the current length of the SDK event log into `prevEventsLen` [1](#0-0) , and later `AfterBalanceChange` replays only the events emitted after that index to mirror bank `CoinSpent`/`CoinReceived`/precisebank fractional-balance events into the EVM `StateDB` via `AddBalance`/`SubBalance` [2](#0-1) .

`precompiles/common/precompile.go`'s `runNativeAction` is the call site that brackets a stateful precompile invocation with `BeforeBalanceChange` … `action(ctx)` … `AfterBalanceChange` [3](#0-2) . If a precompile action itself triggers a nested/recursive EVM call that re-enters a precompile method whose handler shares the same `BalanceHandler` instance/state (rather than a fresh index scoped to that specific inner call), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, so when the outer call's `AfterBalanceChange` finally runs it starts replaying events from the wrong offset — either re-processing events already applied by the inner call (double `AddBalance`/`SubBalance`) or skipping events emitted before the inner call reset the marker.

The repository has a dedicated integration test explicitly describing this defect: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB"* [4](#0-3) , using a purpose-built "debug precompile caller" contract that issues a recursive `callback` to exercise the scenario [5](#0-4) .

This is directly analogous to the Sherlock finding: `checkLiquidation()` computed collateral from a stale snapshot (shares) without reflecting a later state change (floating-assets accrual) that occurs before the final settlement, causing incorrect final accounting. Here, the "snapshot" is `prevEventsLen`, and the "later state change" is a nested precompile call re-arming the same snapshot before the outer settlement (`AfterBalanceChange`) runs.

### Impact Explanation
Once `StateDB` balances diverge from actual bank ledger balances, the eventual commit path reconciles them by minting or burning the native EVM denom to force-match the (now incorrect) `StateDB` value: `Keeper.SetBalance` computes `delta = amount - bank.SpendableCoin` and unconditionally mints (`MintAmountToAccount`) or burns (`BurnAmountFromAccount`) that delta [6](#0-5) . A wrong/duplicated `AddBalance`/`SubBalance` replay therefore results in unauthorized minting or burning of the native coin to reconcile to the corrupted value — directly matching the in-scope "Critical unauthorized minting, burning ... corruption of spendable user value" impact class. It can also manifest as funds being credited/debited to the wrong account (theft/loss) if the replayed events belong to an unrelated nested call.

### Likelihood Explanation
Triggering requires only an ordinary, unprivileged transaction: a contract that calls a stateful precompile method, which in turn performs a nested EVM call that re-enters a precompile method sharing the vulnerable balance-handler state (e.g., via callback/fallback patterns or a contract deliberately structured to recurse). This requires no validator, governance, or admin privilege — any user deploying and calling such a contract can attempt to trigger the desync. The repository's own dedicated regression test for "recursive precompile calls" and a purpose-built "debug precompile caller" contract indicate this is a known, reachable code path, not a purely theoretical one.

### Recommendation
Scope the balance-change tracking to each individual precompile invocation rather than a shared/reusable handler state: e.g., use a call-depth-aware stack of `prevEventsLen` values (push before, pop/consume after) instead of a single mutable field, or bind the before/after event window to the specific `precompileCallChange` journal entry (which already tracks a snapshot + events per call, see `precompileCallChange` in `x/vm/statedb/journal.go`) so nested reentrant calls cannot clobber an outer call's marker. Add a strict invariant check post-commit that total per-denom `StateDB` deltas equal actual bank `CoinSpent`/`CoinReceived` deltas for the whole transaction, failing the transaction rather than silently minting/burning to reconcile.

### Proof of Concept
The repository already contains a reproduction harness for this class of bug: `TestRecursivePrecompileCallsWithDebugPrecompile` deploys a "debug precompile caller" contract that invokes `callback(0)` against a debug precompile registered via `RegisterStaticPrecompile`, driving a chain of nested precompile calls and asserting on the resulting event counts [5](#0-4) . To fully confirm exploitability with real fund loss, this test would need to be extended to assert bank-vs-StateDB balance equality after the recursive call and to invoke a real stateful, fund-moving precompile (e.g., `bank`, `staking`, or `distribution`) recursively instead of the debug precompile, then compare `GetBalanceFromBank` against the EVM `eth_getBalance` of the affected accounts.

**Uncertainty**: I could not fully trace, within index limits, the exact code path by which a "shared BalanceHandler instance" is constructed across nested calls (in `precompile.go`, `NewBalanceHandler()` appears to be called fresh per `runNativeAction` invocation, which would suggest per-call isolation). The precise reentrancy mechanism that causes sharing (e.g., whether certain precompiles cache the handler on a struct field, or whether the EVM's precompile dispatch reuses a single `Precompile` instance whose factory-produced handler is retained across a call stack) is not fully visible in the indexed code. Confirming the exact trigger conditions and whether the described bug is already mitigated or still open would require running the existing test (`evmd/tests/integration/balance_handler/balance_handler_test.go`) and instrumenting the precompile dispatch path in a full Devin session with repository access, since some file contents may be excluded from this index.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// SetBalance update account's balance, compare with current balance first, then decide to mint or burn.
func (k *Keeper) SetBalance(ctx sdk.Context, addr common.Address, amount *uint256.Int) error {
	if amount == nil {
		return nil
	}
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	coin := k.bankWrapper.SpendableCoin(ctx, cosmosAddr, types.GetEVMCoinDenom())

	balance := coin.Amount.BigInt()
	delta := new(big.Int).Sub(amount.ToBig(), balance)
	switch delta.Sign() {
	case 1:
		// mint
		if err := k.bankWrapper.MintAmountToAccount(ctx, cosmosAddr, delta); err != nil {
			return err
		}
	case -1:
		// burn
		if err := k.bankWrapper.BurnAmountFromAccount(ctx, cosmosAddr, new(big.Int).Neg(delta)); err != nil {
			return err
		}
	default:
		// not changed
	}
	return nil
}
