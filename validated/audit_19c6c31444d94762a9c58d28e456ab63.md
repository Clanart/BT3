### Title
OP_RETURN data is excluded from Bitcoin fee and weight calculations - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` accepts caller-supplied `data` and adds it as an OP_RETURN output, but calculates the transaction’s virtual size and maximum weight using only the payment outputs and optional change output. A transaction containing an 80-byte OP_RETURN therefore has a materially larger serialized size than the size used to derive `needed_fee`, allowing a signed transaction to pay less than the requested fee rate or bypass the maximum-standard-weight check.

### Finding Description
The `data` parameter is public input to `SignableTransaction::new`, and any supplied bytes are converted into a zero-valued OP_RETURN output appended to `tx_outs`. [1](#0-0) [2](#0-1) 

However, `calculate_weight_vbytes` builds its sizing transaction only from `payments`, with change as the sole optional output. [3](#0-2) 

The initial fee calculation calls that helper without representing the already-created OP_RETURN output, then derives `needed_fee` as `fee_per_vbyte * vbytes`. [4](#0-3) 

The change-enabled calculation repeats the same omission, computes `fee_with_change` from only payments and change, and subtracts that underestimated fee from the change amount. [5](#0-4) 

The final transaction nevertheless contains `tx_outs`, including the OP_RETURN output, so its actual serialized size and weight are larger than the values used for pricing and policy validation. [6](#0-5) 

This is the same bug class as the oracle report: two quantities with different semantics or scales are combined as though they were equivalent, producing an economically incorrect result.

### Impact Explanation
A caller can supply up to 80 bytes, which expands the final transaction without expanding the size used for `needed_fee`, `TooLowFee`, or `TooLargeTransaction` checks. [7](#0-6) [4](#0-3) [8](#0-7) 

The resulting transaction is then signed over the real transaction, including the OP_RETURN output, using the underestimated fee committed by its input and output amounts. [9](#0-8) [10](#0-9) 

For a minimally priced data-only transaction, the actual fee can equal the underestimated `needed_fee` while the actual virtual size is roughly ninety bytes larger, making the actual fee rate below the requested and relay-minimum rate. [11](#0-10) [12](#0-11) 

For transactions already near the standard-weight boundary, the omitted OP_RETURN weight can also cause the final transaction to exceed the checked limit after `TooLargeTransaction` has already been bypassed. [13](#0-12) [14](#0-13) 

### Likelihood Explanation
The issue is deterministically reachable whenever `SignableTransaction::new` receives a non-empty `data` value, and the maximum payload is accepted by the function’s own validation. [1](#0-0) [15](#0-14) 

No malformed encoding, malicious peer, leaked key, or special protocol state is required; the discrepancy follows directly from constructing the fee-estimation transaction without the data output while serializing the final transaction with it. [3](#0-2) [11](#0-10) 

### Recommendation
Pass the OP_RETURN `TxOut`, not merely `payments`, into `calculate_weight_vbytes`, or otherwise include its exact serialized script length in both the no-change and with-change size estimates. [16](#0-15) [17](#0-16) 

The minimum-fee and maximum-weight checks should be evaluated against the complete final transaction shape after all outputs, including data, have been added. [18](#0-17) 

### Proof of Concept
A data-only transaction illustrates the mismatch:

```rust
// From networks/bitcoin/src/wallet/send.rs
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
  vec![input],
  &[],
  None,
  Some(data),
  1, // one satoshi per intended vbyte
)?;
```

The estimate is calculated with no payment output and no representation of the OP_RETURN output, while the returned transaction contains that output. [11](#0-10) [12](#0-11) 

If the input is exactly `needed_fee`, the final transaction pays exactly `needed_fee`, but its actual `vsize` is larger by the serialized OP_RETURN output, so `fee / actual_vsize` is below one satoshi per vbyte and below the relay minimum permitted by the existing check. [19](#0-18) [20](#0-19)
