### Title
Silent, unvalidated remote-URL rewrite from trusted GitHub API repository object - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl()` automatically rewrites a repository's local git remote URL using the `clone_url` field of a `GitHubRepository` object returned by the GitHub API, based only on a protocol-match and "did-the-user-manually-edit-it" heuristic. It never verifies that the new URL points to the same trusted host/endpoint as the repository's associated account, and it performs the change with `git remote set-url` without any user confirmation.

### Finding Description
This mirrors the report's broken invariant: an operation trusts an externally-supplied value (there, DEX reserve state; here, an API-returned `clone_url`) and acts on it without validating that the resulting state is still within the expected trust boundary.

`updateRemoteUrl` computes `protocolsMatch` (scheme equality only) and `remoteUrlUnchanged` (whether the current remote still matches the previously cached `gitHubRepository.cloneURL`), then unconditionally calls `gitStore.setRemoteURL(...)` when those two hold and the URLs differ in owner/repo: [1](#0-0) 

`urlMatchesRemote`/`urlsMatch` only compare `hostname`, `owner`, and `name` extracted via regex from the URL strings — they never check that the *new* URL's hostname equals the *account's* expected endpoint hostname: [2](#0-1) 

`setRemoteURL` shells out directly to git with the untouched string: [3](#0-2) 

This function is invoked automatically, with no user interaction, during routine background repository refresh: [4](#0-3) 
which itself is called from `_selectRepositoryRefreshTasks` (on selecting a repo) and from the periodic background fetcher/account-change refresh path, i.e. it can run silently while Desktop is simply open. `apiRepo` is fetched by `owner`/`name` against the account's configured endpoint: [5](#0-4) 
but nothing after the fetch re-validates that `apiRepo.clone_url`'s hostname is the same GitHub/GHES host the account is bound to — the code trusts the API object's `clone_url` field as-is. This was intentionally added to auto-follow GitHub repo renames (changelog entry "#8590"), but the implementation only guards against protocol drift and manual local edits, not against the returned URL pointing to an entirely different host.

### Impact Explanation
If the API object for a repository (`clone_url`) can be made to return a URL outside the expected host — e.g. via a compromised/malicious GitHub Enterprise Server that a user has already added as an account, a MITM on the API response, or any bug/attacker path that lets a `clone_url` field diverge from the canonical host — Desktop will silently rewrite the user's `origin` remote to that URL with no dialog, confirmation, or diff shown to the user. Consequences:
- All subsequent `fetch`/`pull`/`push` operations run by Desktop's background fetcher (`startBackgroundFetching`) and by explicit user actions transparently target the attacker-controlled remote, allowing injection of malicious commits/refs into the local repository or exfiltration of push credentials to the rogue host.
- This satisfies the "silent corruption of what the user commits or pushes" / "credential exfiltration" impact class, since the change happens without the user ever visiting Repository Settings or knowingly typing a new URL.

### Likelihood Explanation
The code path executes automatically on ordinary app usage (repository selection, periodic background refresh, account-change refresh) — no unusual user action is required beyond having a GitHub-associated repository open. The remaining uncertainty is the precise mechanism by which an attacker forces `apiRepo.clone_url` to diverge from the expected host for a specific `owner/name` pair on a specific account's endpoint; I could not locate, within local code, any additional server-side or client-side validation that would prevent a malicious/compromised API endpoint (e.g., a GHES instance already trusted by the user, or a MITM'd response) from doing so, nor could I confirm (or rule out) whether dangerous git transport schemes (e.g. `ext::`) are blocked via `GIT_ALLOW_PROTOCOL`/`protocol.allow`, since no such setting was found in `app/src/lib/git/environment.ts` or elsewhere in the indexed code — this remains unconfirmed and would need further investigation in a full checkout.

### Recommendation
Before calling `gitStore.setRemoteURL`, validate that the new URL's hostname matches the hostname of the `GitHubRepository`'s known `endpoint`/account (not just that the old and new protocols match), and surface the rename/URL change to the user for confirmation rather than applying it silently — analogous to the report's recommendation of adding an explicit, verifiable parameter (slippage bound) rather than trusting derived state implicitly.

### Proof of Concept
1. User has a repository with `origin` pointing to `https://ghe.example.com/org/repo.git`, associated with a GHES account at endpoint `ghe.example.com`.
2. The GHES instance (compromised, or an attacker with API-serving control on that instance) returns, for `GET repos/org/repo`, a `clone_url` of `https://attacker-mirror.example/org/repo.git` (same owner/name, different host — passes the `owner`/`name` regex-based `urlMatchesRemote` identity check since hostname isn't cross-checked against the account endpoint).
3. On next repository selection or background refresh, `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true`, `urlsMatch === false` (different hostname/owner/name combination as parsed), and calls `gitStore.setRemoteURL('origin', 'https://attacker-mirror.example/org/repo.git')` with no user prompt.
4. Any subsequent fetch/push by Desktop transparently talks to `attacker-mirror.example`, exposing credentials to and importing content from the attacker-controlled host.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
