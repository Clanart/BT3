## Confirmed: repo-jacking via API-driven silent remote URL rewrite

### Title
Silent origin-remote hijack via stale owner/name-keyed GitHub repository matching in `updateRemoteUrl` - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically re-fetches metadata for a repository's associated GitHub API object and, if the API's `clone_url` no longer matches the local `origin` remote, silently rewrites the local git remote to the new URL — with no user confirmation. The identity check that gates this rewrite is anchored to `owner login + repo name`, not to the GitHub repository's immutable numeric ID, so an attacker who can occupy that same `owner/name` slot (classic "repo-jacking": renaming/transferring/deleting-and-recreating a repository, or a username/org name takeover) can cause Desktop to silently repoint a victim's `origin` remote to an attacker-controlled repository.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app-store.ts` re-resolves the account/owner/name for a tracked repository and calls the API to fetch fresh repository data: [1](#0-0) 

The resulting `apiRepo` is fed directly into `updateRemoteUrl`, which will overwrite the local `origin` URL as long as (a) the URL protocol hasn't changed, and (b) the *cached* `gitHubRepository.cloneURL` still matches the current git remote (i.e., the user hasn't manually changed it): [2](#0-1) 

Crucially, none of these checks validate that the API object being merged is *the same underlying repository* the user originally added — there is no check against a stable GitHub repository ID. The local cache (`RepositoriesStore._upsertGitHubRepository`) keys and matches GitHub repository records purely by `[ownerID+name]`: [3](#0-2) 
and the on-disk Dexie index enforces uniqueness only on `[ownerID+name]`, never on the GitHub repo id: [4](#0-3) 

This is the exact "trust current mutable state instead of a stable snapshot/identity anchor" pattern from the report: instead of pinning the association to an immutable identifier captured when the repository was first added (the governance analog of "voting power at proposal creation"), Desktop re-derives trust every refresh from a mutable `(owner, name)` pair supplied by the live API response (the analog of "current voting power"). If that slot changes ownership — the original repo is deleted and a same-named repo is created under the same owner/org (or the owner name itself is reused after being freed up), or the API returns data for what looks like the same owner/name but is actually a different underlying repository — Desktop's periodic refresh will treat the attacker's repository as a continuation of the trusted one and rewrite `origin` in `.git/config` accordingly.

Existing guards do not stop this path:
- `urlMatchesRemote`/`urlsMatch` (`app/src/lib/repository-matching.ts:90-148`) only compares hostname/owner/name strings — they cannot distinguish an attacker-recreated repo with the identical owner/name from the legitimate one, since that's exactly what they're designed to match on.
- The protocol-match check in `updateRemoteUrl` only blocks ssh↔https protocol switches, not same-protocol hijacks.
- The `UpstreamAlreadyExists` dialog (`app/src/ui/upstream-already-exists/upstream-already-exists.tsx`) only prompts the user when updating the *upstream* remote for forks — the `origin` remote update path in `updateRemoteUrl` has no equivalent confirmation UI.

### Impact Explanation
Once `origin` is silently repointed, every subsequent `git push` from Desktop (and any git fetch/pull that follows) targets the attacker's repository instead of the legitimate one. For private repositories this means the user's proprietary source code is exfiltrated to the attacker on the next push; for any repository it means the user's contribution history is silently misdirected without any visual indicator besides the remote URL in settings, which most users never inspect. This satisfies the "silent corruption of what the user commits or pushes" impact category, and because the git remote is used to derive the environment/credentials for the operation (`envForRemoteOperation`, `fetch.ts:39-48`), it can also result in the user's stored GitHub credentials/token being presented to a host that, while still `github.com`, now backs the attacker's repository.

### Likelihood Explanation
The attacker does not need any access to the victim's machine, browser, or credentials. They need only be able to occupy the same `(owner, repo name)` slot the victim's Desktop instance is tracking — achievable through known repo-jacking techniques (deleting and recreating a repo under the same owner/name, or reclaiming a renamed/freed repository or organization name) that are well-documented supply-chain attack vectors independent of Desktop. The victim needs to do nothing except keep Desktop open/running with the repository tracked; the refresh occurs automatically as part of normal repository-refresh flows (`_refreshRepository` → `repositoryWithRefreshedGitHubRepository`), not requiring any unusual user action.

### Recommendation
Anchor the repository identity check to the GitHub repository's immutable numeric `id` (already available on `IAPIRepository`/`GitHubRepository`) rather than `(ownerID, name)`. `updateRemoteUrl` should refuse to update the remote (or should prompt the user, similar to `UpstreamAlreadyExists`) if the API-returned repository's `id` differs from the `id` stored in the local `GitHubRepository` record for that association. The `[ownerID+name]` uniqueness index in `repositories-database.ts` should similarly be supplemented with (or replaced by) a durable GitHub repository ID as the primary matching key, so a name/owner reuse cannot silently splice a new repository into an existing local association.

### Proof of Concept
1. Victim clones `https://github.com/victim-org/secret-repo` in GitHub Desktop; Desktop stores the `GitHubRepository` record keyed by `[ownerID(victim-org)+name(secret-repo)]` with `cloneURL = https://github.com/victim-org/secret-repo`.
2. Attacker (who controls or later gains control of `victim-org`, e.g. via an expired/transferred org, or via legitimate collaborator access that is later revoked) deletes `secret-repo` and immediately creates a new, empty repository also named `secret-repo` under `victim-org` (a different underlying repo ID), with `clone_url` unavoidably identical in string form: `https://github.com/victim-org/secret-repo`.
   - Note: because `clone_url` strings are typically identical for same-owner/name repos, `urlMatchesRemote` would actually show `urlsMatch === true` in this specific sub-case, meaning `updateRemoteUrl` wouldn't even need to fire — the real exposure is the broader class where `apiRepo.clone_url` differs (e.g., attacker takes over just the `owner` login after a rename) while `(owner, name)` still resolves to the attacker's data on next `_upsertGitHubRepository` refresh, silently replacing the cached `cloneURL`/`htmlURL`/`permissions` for that owner/name slot with the attacker's repository's metadata.
3. On Desktop's next background refresh of the victim's repository (`_refreshRepository` → `repositoryWithRefreshedGitHubRepository`), `api.fetchRepository(owner, name)` resolves to the attacker's repository object (same owner/name, different id), and `_upsertGitHubRepository` overwrites the local `GitHubRepository` record's `cloneURL` with the attacker's data.
4. `updateRemoteUrl` sees `remoteUrlUnchanged === true` (the cached `cloneURL` still equalled the local git remote before this refresh) and `urlsMatch === false` (attacker's new `clone_url` differs, e.g. due to a rename step in the takeover), so it calls `gitStore.setRemoteURL('origin', attackerCloneUrl)` — rewriting `.git/config` with no dialog, no confirmation, and no diff shown to the user (`git-store.ts:1533-1543`).
5. The victim's next "Push origin" in Desktop sends commits to the attacker's repository.

Some details of exactly which repo-jacking sequence the live GitHub API permits (e.g., whether a rename leaves a redirect that `fetchRepository(owner, name)` would still resolve to the original id) could not be fully verified from the codebase alone, since that depends on GitHub.com/GHES server-side behavior outside this repository — a background Devin session with API access could validate the exact preconditions end-to-end.

    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
