### Title
Zero-amount escrow input permanently blocks source-side order cancellation, permanently locking user funds - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
The external report's core broken invariant is: a pool computation silently accepts a zero balance for one asset, and a subsequent all-assets computation (division/invariant/loop) either produces a free-token result or unconditionally reverts, bricking the operation. The same defect class exists in Hyperbridge's `IntentGatewayV2` cross-chain order escrow: `placeOrder` allows an input token entry with `amount == 0` whenever no protocol fee is configured for the destination, and `_cancelFromSource` unconditionally reverts the entire cancellation if **any** input token's escrow balance reads zero — with no way to distinguish "legitimately zero at placement" from "already withdrawn."

### Finding Description
`IntentGatewayV2.placeOrder` only validates that `order.inputs[i].amount != 0` inside the `protocolFeeBps > 0` branch: [1](#0-0) 

When `protocolFeeBps == 0` (the default unless governance has configured a per-destination or global fee), the `else` branch skips this check entirely and credits escrow directly from the raw `order.inputs`: [2](#0-1) 

This means a user can place a valid, committed order containing one input `TokenInfo` with `amount == 0`. That escrow slot is stored as `_orders[commitment][token] = 0`, which is bitwise indistinguishable from "never escrowed" or "already fully withdrawn."

`_cancelFromSource` — the trustless cancellation path that proves via a Hyperbridge GET request that the destination never filled the order — gates the entire cancellation on every input having non-zero escrow: [3](#0-2) 

For any order containing a zero-amount input, this loop deterministically reverts with `UnknownOrder`, for every future call, regardless of proof height or order validity. There is no code path that lets the user distinguish or bypass this once the order has been placed with a zero-amount input.

This exactly mirrors the report's `_calcTokenInGivenExactBptOut` / `_getDueProtocolFeeAmounts` pattern: a legitimate zero balance for one asset is never rejected at entry, and a later all-assets check/computation that assumes non-zero balances for every asset either breaks (reverts, as here) or produces an incorrect result (free tokens, in the original report).

### Impact Explanation
The user's only alternative recovery route is `_cancelFromDest`, which requires the destination-chain gateway to cooperate and dispatch a `RefundEscrow` message back: [4](#0-3) 

If the destination chain is congested, paused, censoring, or the relayer infrastructure for that leg is unavailable, the user has no functioning fallback: the trustless, permissionless, proof-based source-cancellation path — which by design should always work once `options.height > order.deadline` — is permanently and deterministically bricked for any order the user placed with a zero-amount input token. This is a logic/availability flaw in the fund-recovery guarantee of escrowed cross-chain orders, directly caused by a missing zero-value guard at order placement, matching the report's "corner case that traps liquidity" pattern.

### Likelihood Explanation
Any unprivileged user calling `placeOrder` can trigger this by including a `TokenInfo{amount: 0}` entry among `order.inputs` on any destination for which `protocolFeeBps` (destination-specific or global default) is zero — which is the default/common state unless governance has explicitly configured a fee for that destination. No relayer, prover, or admin cooperation is needed to create the vulnerable order state; only an uncooperative or unavailable destination chain is needed to make the fund-lock manifest.

### Recommendation
Move the `originalAmount == 0` rejection out of the `protocolFeeBps > 0` branch so it always applies to every `order.inputs[i].amount`, regardless of whether a protocol fee is configured. Additionally, consider tracking escrow existence independently of the amount value (e.g., a separate "escrowed" boolean or requiring `amount > 0` structurally) so that `_cancelFromSource` cannot conflate "legitimately zero" with "unknown/already withdrawn."

### Proof of Concept
1. Ensure `protocolFeeBps` is `0` for a target destination (the default state).
2. User calls `placeOrder` with `order.inputs = [{token: USDC, amount: 1000e6}, {token: DAI, amount: 0}]`. The order is accepted; `_orders[commitment][USDC] = 1000e6`, `_orders[commitment][DAI] = 0`.
3. Destination chain never fills the order (e.g., it becomes unreachable/paused).
4. After `order.deadline`, the user calls `cancelOrder(order, {height: proofHeight, relayerFee: ...})` targeting the source-chain route.
5. `_cancelFromSource` iterates `order.inputs`; on the DAI entry it reads `_orders[commitment][DAI] == 0` and reverts with `UnknownOrder` — see: [3](#0-2) 
6. The 1000 USDC remains escrowed with no way to recover it via the source-side, trust-minimized cancellation path; recovery depends entirely on destination-chain cooperation via `_cancelFromDest`.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
