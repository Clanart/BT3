## Analysis

I found a genuine analog in the packed-repeated-field parsing path of the C++ implementation: an **intentional, uncatchable process abort on integer overflow**, deliberately coded as a fatal `CHECK`, rather than a graceful parse failure — exactly the "availability-only, logic-triggered crash" bug class that CVE-2020-14794 represents (a crash/hang reachable through ordinary operation rather than memory exhaustion or malicious schema abuse). It is also explicitly flagged as a **known, unresolved bug** in the test suite (`DISABLED_MergeFrom`/`DISABLED_MergeFromPacked`, "TODO: Re-enable once parsing overflow is fixed").

### Title
Fatal process abort (uncatchable `CHECK`-failure crash) when a repeated field's element count overflows `int32` during packed-field `MergeFrom`/parse - ([File: src/google/protobuf/port.h])

### Summary
`internal::CheckedAdd` in `src/google/protobuf/port.h` is used throughout the packed-varint parsing path (`EpsCopyInputStream::ReadPackedVarintArrayWithField` in `src/google/protobuf/parse_context.h`) to compute `old_size + count` before growing a `RepeatedField`. When this addition would overflow `int32`, `CheckedAdd` calls the `[[noreturn]]` function `HandleAddOverflow`, which fatally aborts the process instead of returning a parse error. [1](#0-0)  This is invoked directly from the fast packed-parsing code path. [2](#0-1) 

### Finding Description
Nearly every other malformed/oversized input path in this codebase returns `nullptr`/`false` and lets the caller report a catchable parse error (see the extensive `EXPECT_FALSE`/`InvalidProtocolBufferException` conventions used throughout `message_unittest.inc`, `wire_format_unittest.h`, etc.). The packed-field growth arithmetic breaks this invariant: it is guarded by `CheckedAdd`, which on overflow does not return an error — it terminates the process via `ABSL_CHECK`-style `HandleAddOverflow`. [3](#0-2) 

This is reachable whenever a target message's repeated field is already close to `INT32_MAX` elements (attacker-controllable indirectly through the trusted application accumulating results from many bounded `MergeFrom`/`ParseFrom` calls — a normal, valid usage pattern for accumulator/aggregator services that merge many small client-submitted Protobuf payloads into one long-lived message) and a subsequent, fully bounded incoming packed-field chunk is merged. The size check that should gracefully fail is instead an abort.

The test suite proves this is real, current, unfixed behavior:
- `RepeatedFieldIsFullTest.ParsedPackedOverflow` and `RepeatedVarintOverflow` explicitly expect `EXPECT_DEATH(..., "Integer overflow in CheckedAdd: ")` when merging a *small* packed payload (10 or 32 bools) into a message whose repeated field was resized to `INT_MAX - 4`. [4](#0-3) 
- The *desired* graceful-failure behavior is captured in `DISABLED_MergeFrom` / `DISABLED_MergeFromPacked`, both marked with `// TODO: Re-enable once parsing overflow is fixed`, showing this is a known, currently-unaddressed defect where `MergeFromString` should return `false` but instead the process would abort. [5](#0-4) 

### Impact Explanation
Impact is availability-only (process termination/DoS), matching the CVE's `C:N/I:N/A:H` profile. There is no memory corruption, information disclosure, or code execution — `HandleAddOverflow` is a controlled fatal abort, not a memory-safety violation. Any server process embedding this code that accumulates repeated-field data across multiple bounded client requests into one long-lived message can be crashed by a client sending one more small, fully valid packed-field message once the accumulator nears `2^31` elements.

### Likelihood Explanation
Reaching the overflow requires the target repeated field to already contain close to `2^31` elements — this is a legitimate but unusual server-side state (e.g., long-running aggregation/collector services). It is not attacker-triggerable in a single request from scratch (excluding it from pure "huge-input/resource-exhaustion" DoS), but any application that merges many bounded, valid client submissions into a single accumulator message is exposed, and the final triggering payload itself is tiny and fully within normal parse limits — this differs qualitatively from unbounded-allocation/flooding DoS since the crash is a designed `CHECK` in normal, small-input parsing code, not a resource-exhaustion side effect.

### Recommendation
Change the packed-field growth path (`ReadPackedVarintArrayWithField` and related call sites in `parse_context.h`, and any other packed-field/`RepeatedField::Reserve` merge path using `CheckedAdd` during parsing) to detect the overflow and fail the parse gracefully (return `nullptr`/`false`) instead of invoking `HandleAddOverflow`'s fatal abort, consistent with every other malformed/oversized-input handling convention in the parser. This is precisely the fix tracked by the `TODO: Re-enable once parsing overflow is fixed` comment.

### Proof of Concept
The existing regression test in the repository already demonstrates and asserts the crash (not merely a hypothetical): [6](#0-5) 
1. Create `TestPackedTypes msg`, resize `packed_bool` to `INT_MAX - 4`.
2. `MergeFromString` a small, valid serialized packed-bool payload (10 or 32 bool elements) previously produced from the same message type.
3. The merge computes `old_size + count` via `CheckedAdd`, overflows `int32`, and the process aborts with `"Integer overflow in CheckedAdd: "` instead of `MergeFromString` returning `false`.

#if ABSL_HAVE_BUILTIN(__builtin_add_overflow)
template <typename IntType1, typename IntType2>
inline int CheckedAdd(IntType1 a, IntType2 b) {
  int sum;
  bool overflow = __builtin_add_overflow(a, b, &sum);
  if (ABSL_PREDICT_FALSE(overflow)) {
    HandleAddOverflow(a, b);
  }
  return sum;
}
