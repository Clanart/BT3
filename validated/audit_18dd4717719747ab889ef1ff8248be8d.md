### Title
Re-entrancy in Tron `IntentGatewayV2.withdraw()` Allows Double-Withdrawal of Escrowed Order Funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2` implements `withdraw()` with the exact Checks-Effects-Interactions violation described in the external report: it performs the external token/ETH transfer to the beneficiary **before** decrementing the corresponding `_orders[commitment][token]` escrow balance. Unlike the mainline EVM contracts (`evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`), which were hardened against this exact class of bug (state written before the external call, plus a `nonReentrant` guard on `cancelOrder`), the Tron contract retains the vulnerable ordering and has no reentrancy guard at all.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 682-721): [1](#0-0) 

For each token in the withdrawal request, the function checks `_orders[body.commitment][token] == 0`, then makes an external call (native ETH `.call` or ERC-20 `.call` to `transfer`) to the attacker-controllable `beneficiary`, and only **afterwards** does `_orders[body.commitment][token] -= amount`.

This function is reachable directly and unprivileged via `cancelOrder()`'s same-chain branch, which has **no `nonReentrant` modifier**: [2](#0-1) 

The order owner (`order.user == msg.sender`) is the only authorization check — an attacker who placed the order and is also the escrow beneficiary can trigger `cancelOrder()`, and if `beneficiary` is a contract, its `receive()`/fallback can re-enter `cancelOrder()` (or the analogous cross-chain `onAccept`/`onGetResponse` → `withdraw()` paths) for the same `commitment` while `_orders[commitment][token]` is still non-zero (not yet decremented), passing the `== 0` check a second time and draining the same escrow slot again.

This is structurally identical to the reported `UsernameRegistrar.release()` bug: an external call embedded inside a loop, placed before the state mutation that is supposed to prevent re-use.

### Impact Explanation
A successful reentrant call drains escrowed order funds beyond what was legitimately deposited for that commitment — direct loss of user/protocol funds and double-settlement of an order's escrow, matching the bounty's "stealing or loss of funds" / "replay/double-claim/double-settlement" categories.

### Likelihood Explanation
The attack requires only an unprivileged attacker: place an order as both `order.user` and a malicious `beneficiary` contract, then call `cancelOrder()` (or arrange to be the fill/refund beneficiary on the cross-chain paths) so the native-ETH transfer inside `withdraw()` triggers a `receive()` callback that re-enters before `_orders` is decremented. No relayer, prover, or admin collusion is needed — it is directly comparable to the already-demonstrated `IntrinsicIntentsReentrancyTest.sol` exploits against the (now-patched) mainline contracts, which prove this exact pattern is practically exploitable in this codebase when CEI ordering is violated.

### Recommendation
Apply the same fix already present in `evm/src/apps/intentsv2/IntentsBase.sol` and `evm/src/apps/IntentGatewayV2.sol`: decrement `_orders[body.commitment][token]` (Effects) before making the external transfer call (Interaction), and add a `nonReentrant` guard to `cancelOrder()` (and any other externally-reachable entry point that can invoke `withdraw()`), mirroring the CEI remediation described in the external report.

### Proof of Concept
1. Attacker deploys a malicious contract `M` with a `receive()` that calls back into `IntentGatewayV2.cancelOrder(order, options)` once, guarded by a reentry flag.
2. Attacker (as `msg.sender`) calls `placeOrder(order, graffiti)` on the same chain with `order.output.beneficiary = M` and a native-ETH input, escrowing `_orders[commitment][address(0)] = amount`.
3. Attacker calls `cancelOrder(order, options)`. Inside `withdraw()`, the check `_orders[commitment][address(0)] == 0` passes (balance is `amount`), then `beneficiary.call{value: amount}("")` executes, entering `M.receive()`.
4. `M.receive()` re-enters `cancelOrder(order, options)`. `_filled[commitment]` was already set at the top of the outer `cancelOrder`/`withdraw` before the inner transfer in some paths, but the `_orders[commitment][address(0)]` decrement in `withdraw()` has **not yet executed** for the first call, so the inner `withdraw()` call's `== 0` check still passes and pays out `amount` a second time.
5. Both calls succeed, transferring `2 * amount` in ETH out of an escrow that only held `amount` — draining funds belonging to other orders/beneficiaries sharing the contract's balance. [3](#0-2) [2](#0-1) [4](#0-3) [5](#0-4)

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});

            _cancelFromDest(order, options, commitment);

        }
