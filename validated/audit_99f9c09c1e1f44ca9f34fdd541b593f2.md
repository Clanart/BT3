## Title
Escrow Marked Redeemed Even When ERC-20 Transfer Silently Fails, Causing Fund Loss for Order Fillers — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2` redeems intent-order escrow using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the low-level call did not revert, never decoding/verifying the ERC20 `transfer` boolean return value. It also decrements the escrow accounting (`_orders[...][token] -= amount`) and marks the order `_filled` regardless of whether the token actually moved. This lets escrow be permanently "consumed" on-chain while the real beneficiary receives zero tokens whenever the input token is non-standard (returns `false` instead of reverting) — a direct local analog of the reported "amount zeroed/consumed without confirming the transfer actually delivered value" bug class.

### Finding Description
In the mainline EVM contract, escrow release uses `SafeERC20.safeTransfer`, which reverts on a falsy/missing return value: [1](#0-0) 

The Tron variant instead performs a raw low-level call and treats "call did not revert" as success, without inspecting the ABI-encoded boolean return value of `transfer`: [2](#0-1) 

The same unchecked-return pattern is repeated in `onAccept`'s `SweepDust` handling: [3](#0-2) 

Because the input token for an order is chosen by whoever calls `placeOrder` (the order creator), an order creator can escrow a token contract whose `transfer()` function returns `false` under some condition (e.g., a pausable/blacklist/rebasing token, or one deliberately crafted to return `false` after a certain block, balance, or caller) instead of reverting. `_orders[commitment][token]` tracks the escrowed balance and is decremented in `withdraw()` purely based on the "call didn't revert" signal: [4](#0-3) 

When a solver later fills the order and Hyperbridge dispatches the `RedeemEscrow` message back to the source chain, `onAccept` invokes `withdraw(body, false)`: [5](#0-4) 

If the token's `transfer` call returns `false` (not a revert), `withdraw()` still: (1) records `_filled[commitment] = beneficiary`, (2) decrements the escrow accounting to zero, and (3) emits `EscrowReleased` — permanently closing the order as "settled" — while the solver's beneficiary address receives nothing. The tokens remain stuck in the contract with no accounting entry left to recover them, since `_orders[commitment][token]` has already been zeroed and the order is marked filled.

### Impact Explanation
This is a genuine loss-of-funds / wrong-settlement bug reachable by an unprivileged actor (the order creator choosing the input token), not requiring a malicious relayer, prover, or admin. The victim is the solver/filler: they deliver real value on the destination chain to satisfy the order's output, then on the source chain the "successful" `RedeemEscrow` settlement silently fails to pay them while the protocol accounting (`_orders`, `_filled`) treats the order as fully and correctly redeemed. This falls squarely within the bounty's "stealing or loss of funds" and "false state acceptance" categories — the on-chain state falsely records that the escrow was correctly released.

### Likelihood Explanation
Likelihood is high for any deployment using non fully ERC-20-compliant tokens (which are common — deflationary, pausable, blacklist-based, or otherwise non-reverting tokens), and is also trivially triggerable by a malicious order creator who deploys a custom token contract as the escrowed input asset specifically to grief solvers this way, since nothing in `placeOrder` restricts the token to a vetted allowlist.

### Recommendation
Replace the raw `token.call(...)` + `success`-only check in `withdraw()` and in the `SweepDust` handler with `SafeERC20.safeTransfer`, matching the pattern already used in the canonical EVM `IntentsBase.sol` (`IERC20(token).safeTransfer(beneficiary, amount);`), which reverts on a falsy or missing return value so that escrow accounting is never decremented / the order never marked filled unless the transfer genuinely succeeded.

### Proof of Concept
1. Order creator deploys `EvilToken`, an ERC20 whose `transfer()` returns `false` (no revert) whenever `to == knownSolverAddress` or after a configurable flag is flipped by the creator.
2. Creator calls `placeOrder` with `order.inputs = [{token: EvilToken, amount: X}]`, escrowing `X` `EvilToken` into the gateway; `_orders[commitment][EvilToken] = X`.
3. A solver fills the order on the destination chain, delivering the promised output assets to the user.
4. Hyperbridge dispatches the `RedeemEscrow` `PostRequest` back to the source chain; `onAccept` → `withdraw(body, false)` executes:
   - `token.call(transfer(solver, X))` returns `(true, abi.encode(false))` — call succeeds, but token internally declines the transfer.
   - `success` is `true` (only the call outcome is checked), so no revert.
   - `_orders[commitment][EvilToken] -= X` → `0`; `_filled[commitment] = solver`; `EscrowReleased` emitted.
5. Solver's on-chain balance of `EvilToken` is unchanged (received 0), yet the order is permanently marked filled/redeemed and the escrow entry is gone — funds are stuck in the gateway with no remaining accounting path to recover them for the solver.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
