### Title
Legacy bank precompile `send` bypasses `SendEnabled`/allow-list checks by calling `SendCoins` directly instead of the guarded `MsgServer.Send` path - ([File: precompiles/bank/legacy/v555/bank.go], [File: precompiles/bank/legacy/v562/bank.go])

### Summary
In the Cosmos SDK bank module, the `SendEnabled` parameter (per-denom pause on transfers) and the `IsInDenomAllowList`/`BlockedAddr` checks are only enforced in the message-server layer (`msgServer.Send`), not inside the underlying `BaseSendKeeper.SendCoins` keeper function itself. [1](#0-0) [2](#0-1) 

The legacy versions of the EVM bank precompile (`v555`, `v562`) implement their `send` precompile method by calling `p.bankKeeper.SendCoins(...)` directly, completely bypassing the `IsSendEnabledCoins` check (and the allow-list/blocked-address checks) that `msgServer.Send` performs: [3](#0-2) 

Later precompile versions (`v603`, `v610`, `v66`, `v67`) fixed this by routing through `p.bankMsgServer.Send(...)`, which does invoke `IsSendEnabledCoins`: [4](#0-3) 

This is directly analogous to the reported iPT bug class: a "pause" gate (`SendEnabled` denom flag, set via governance/admin as an emergency stop, exactly like `pauseRedemptions`) is enforced on one code path (`MsgSend`/`msgServer.Send`) but not on a second reachable path (the EVM `send` precompile in `v555`/`v562`) that performs the same fund-moving operation.

### Finding Description
The bank precompile at address `0x0000000000000000000000000000000000001001` exposes a `send` method callable by any EVM contract/user, gated only by "caller must be the registered ERC20 pointer for the denom": [5](#0-4) 

This check has nothing to do with `SendEnabled`. It calls `p.bankKeeper.SendCoins(ctx, senderSeiAddr, receiverSeiAddr, ...)` — the raw keeper function — which contains no `IsSendEnabledCoins` gate: [6](#0-5) 

Meanwhile, the "safe"/canonical way to move bank coins, `MsgSend` via `msgServer.Send`, explicitly checks `IsSendEnabledCoins` before transferring: [7](#0-6) 

If governance (or an emergency param-change proposal) disables sending for a denom via `SendEnabled`/`DefaultSendEnabled` — e.g., in response to an active exploit, a compromised token, or a required freeze — any pointer contract on the older precompile version can still move that denom's funds by calling the EVM `send` method, exactly mirroring how `authRedeem`/`autoRedeem` bypassed the iPT pause because the pause check lived only in some functions and not others.

### Impact Explanation
An admin pausing token transfers for a denom via `SendEnabled=false` (e.g., during an active attack or exploit response) would not actually stop fund movement, because the ERC20 pointer contract registered for that denom can still call the bank precompile's `send` in `v555`/`v562`, which calls `SendCoins` directly with no `SendEnabled` check. This defeats the intended freeze/pause mechanism and allows continued fund transfers precisely when the protocol most needs to stop them, resulting in fund loss during an incident response window.

### Likelihood Explanation
Reachability requires: (1) the chain running on a legacy binary version where the bank precompile still routes through `v555`/`v562` code, and (2) governance/admin having set `SendEnabled=false` for a denom. Given that `v603`+ already fixed the pattern by switching to `bankMsgServer.Send`, this is only exploitable if a node/version is still on the vulnerable precompile implementation, or if the vulnerable version is still reachable in the precompile version-dispatch table for historical block replay. I could not fully verify from the index which versions are actually live/selected in current production dispatch versus purely historical/frozen implementations — this would need direct confirmation via `precompiles/bank/setup.go`'s version-selection logic.

### Recommendation
Ensure all legacy/versioned implementations of the bank precompile's `send`/`sendNative` methods route fund transfers through the bank module's `MsgServer.Send`/`InputOutputCoins` path (or explicitly call `IsSendEnabledCoins` and the allow-list/blocked-address checks) rather than calling `BaseSendKeeper.SendCoins` directly, matching what was already done in `v603`/`v610`/`v66`/`v67`. If `v555`/`v562` are still reachable/selectable in production version dispatch, backport the `bankMsgServer.Send` fix to them or remove them from the active dispatch table.

### Proof of Concept
1. Governance/admin sets `SendEnabled=false` for denom `X` via a bank params update (analogous to `pauseRedemptions`).
2. An attacker (or normal user) holding an ERC20 pointer contract registered as the pointer for denom `X` calls the bank precompile's `send(sender, receiver, "X", amount)` method on `0x...1001`.
3. `Precompile.send` in `v555`/`v562` checks only that `caller == pointer` and then calls `p.bankKeeper.SendCoins(...)` directly: [8](#0-7) 
4. `SendCoins`/`IsSendEnabledCoins` is never invoked on this path, so the transfer of denom `X` succeeds despite `SendEnabled=false`, whereas the same transfer attempted via a native `MsgSend` transaction would be rejected with `ErrSendDisabled`. [9](#0-8)

func (p Precompile) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, error) {
	if readOnly {
		return nil, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		return method.Outputs.Pack(true)
	}
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, err
	}

	if err := p.bankKeeper.SendCoins(ctx, senderSeiAddr, receiverSeiAddr, sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount)))); err != nil {
		return nil, err
	}

	return method.Outputs.Pack(true)
}
