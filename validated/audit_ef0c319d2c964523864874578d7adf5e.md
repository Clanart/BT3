### Title
`SignableTransaction::new` computes weight/vsize and fee on a transaction missing the `OP_RETURN` data output, returning an under-priced transaction as valid - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to CVE-2021-22922 (validation performed on the wrong artifact; the resulting object is kept as-if-valid), `SignableTransaction::new` validates the transaction's weight and fee rate against a *reconstructed* transaction that omits the `OP_RETURN` output carrying `data`. The produced `SignableTransaction` therefore pays a lower fee than requested and can fall below the minimum relay feerate, yet is returned as `Ok` and signed/broadcast as-is.

### Finding Description
`calculate_weight_vbytes(inputs, payments, change)` builds a mock `Transaction` whose outputs are derived **only** from `payments` (plus optional `change`):

- `networks/bitcoin/src/wallet/send.rs:85-93` — outputs are `payments.map(...)`.
- `send.rs:194-202` — the `OP_RETURN` output is pushed onto the real `tx_outs` *before* the weight call.
- `send.rs:204` — `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` is called with `payments`, which does not include the data output.
- `send.rs:206-213` — `needed_fee = fee_per_vbyte * vbytes` and the `DEFAULT_MIN_RELAY_TX_FEE` floor check both use this underestimated `vbytes`.
- `send.rs:225-233` — the change-path recomputation also uses `payments` without the OP_RETURN, so `fee_with_change` is underestimated and the change output receives slightly more than it should.

So for any `SignableTransaction::new` invocation where `data: Some(_)` is passed, the fee actually paid (`sum(inputs) - sum(outputs)`, see `fee()` at `send.rs:137-141`) corresponds to a lower sat/vbyte rate than `fee_per_vbyte`, because the real transaction is larger than the one measured. Worse, the minimum-relay sanity check at lines 211-213 is evaluated against the underestimated `vbytes`, so a transaction that *actually* fails the relay floor is accepted and returned `Ok`, mirroring the metalink bug where a failed/incorrect check result leaves the artifact in place.

### Impact Explanation
The returned `SignableTransaction` is later signed by `TransactionMachine`/`TransactionSignMachine` (`send.rs:273-429`) and broadcast. If `data` is large (up to the allowed 80 bytes, checked at `send.rs:171-173`), the fee deficit is `fee_per_vbyte * (~11 + data_len)` vbytes. When `fee_per_vbyte` is at/near the relay minimum, the produced transaction's effective feerate falls below `DEFAULT_MIN_RELAY_TX_FEE` and will be rejected from mempools, leaving the payout unbroadcastable and requiring re-signing — the artifact that "passed" the fee/standardness checks was not actually checked. Even when relayable, the multisig systematically pays less than the caller's specified `fee_per_vbyte` whenever an OP_RETURN output is attached.

### Likelihood Explanation
`data` is a public parameter of `SignableTransaction::new`; any flow attaching an OP_RETURN payload (e.g., refund/forward metadata) triggers it. The bug is deterministic — it does not depend on attacker timing, only on `data.is_some()`. Exploitation impact is bounded to fee under-payment / potential non-propagation rather than theft, placing it at Medium per the accepted classes (incorrect check formula on the produced artifact).

### Recommendation
Include the OP_RETURN output in the size estimation: pass the final `tx_outs` (or an explicit `data` length) to `calculate_weight_vbytes`, or add `tx_outs` built at lines 188-202 into the weight computation at line 204 and into the change-path recomputation at lines 225-226, so `needed_fee`, the `DEFAULT_MIN_RELAY_TX_FEE` floor check, and the change-amount deduction all reflect the actual transaction that will be signed and broadcast.

### Proof of Concept
```rust
// Against networks/bitcoin/src/wallet/send.rs
let data = vec![0u8; 80]; // maximal allowed OP_RETURN payload
let tx_with_data = SignableTransaction::new(
    inputs.clone(), &payments, Some(change.clone()), Some(data.clone()), fee_per_vbyte,
).unwrap();
let tx_without = SignableTransaction::new(
    inputs, &payments, Some(change), None, fee_per_vbyte,
).unwrap();

// needed_fee should be larger for the larger transaction, but both use
// vbytes computed from `payments` alone -> needed_fee is identical,
// while tx_with_data.transaction() is ~91 vbytes heavier.
assert_eq!(tx_with_data.needed_fee(), tx_without.needed_fee());
assert!(tx_with_data.transaction().vsize() > tx_without.transaction().vsize());

// Effective feerate is therefore below fee_per_vbyte:
// tx_with_data.fee() / tx_with_data.transaction().vsize() < fee_per_vbyte
```
