### Title
Malicious branch names containing `]` corrupt commit-SHA parsing after commit/merge - (File: `app/src/lib/git/core.ts`)

### Summary
`parseCommitSHA()` extracts the SHA of a just-created commit by naively splitting Git's human-readable `git commit` stdout on the `]` character. Git allows `]` in ref names (only `[` is disallowed), and Desktop's own ref-name sanitizer likewise only rejects `[`, not `]`. A branch fetched/checked out from an attacker-controlled remote can therefore contain a `]` in its name, which breaks the bracket-based parsing and makes Desktop return a wrong or `undefined` value as the "new commit SHA," corrupting the state the app subsequently relies on to track what was just committed.

### Finding Description
`parseCommitSHA` is defined as: [1](#0-0) 

It assumes `git commit`'s stdout is always of the well-formed shape `[<branch> <sha>] <summary>` and that the first `]` in the output closes that bracket. This function is the sole mechanism used to obtain the resulting commit SHA in both normal commits and merge commits: [2](#0-1) [3](#0-2) 

Git's own ref-name rules (`git-check-ref-format`) reject `[` but allow `]` in branch names. Desktop's local sanitizer mirrors this exact behavior — it strips/rejects `[` but never `]`: [4](#0-3) 

This sanitizer is only applied when the *user* types a new branch name in Desktop's UI (e.g. `testForInvalidChars` in `parseAppURL`/branch-creation flows). It is never applied to branch names that arrive from a remote — branches fetched from a cloned/forked attacker-controlled repository and checked out locally keep their original name verbatim.

If a user checks out and commits on a branch named e.g. `feature]evil`, `git commit` will print something like:
```
[feature]evil abc1234] my commit message
```
`parseCommitSHA` computes `result.stdout.split(']')[0]` → `"[feature"`, then `.split(' ')[1]` → `undefined`, because `"[feature"` contains no space. The function’s declared return type is `string`, but at runtime it silently returns `undefined`.

### Impact Explanation
The corrupted (undefined/garbage) value returned by `createCommit`/`createMergeCommit` is used by higher-level flows as the authoritative "just-created commit SHA" (e.g., to refresh commit state, resolve the commit via `getCommit`, or drive multi-commit-operation bookkeeping that references commit SHAs). Because the corruption happens silently — no exception is thrown, no validation occurs — the app can proceed with an incorrect notion of which commit was just made. This falls into the "silent corruption of what the user commits" impact category: the attacker (via a maliciously named branch in a repository the user clones/fetches) can induce this state without the user taking any unusual action beyond checking out that branch and committing, which is normal Desktop usage.

### Likelihood Explanation
The attacker fully controls branch names in their own public repository, and `]` is trivially includable since neither Git nor Desktop's sanitizer blocks it for pre-existing (remote) branches. The only user action required is checking out that branch and making one commit — an ordinary, unprompted workflow, not requiring local access, admin rights, or social engineering beyond normal collaboration (fork/clone/checkout).

### Recommendation
Do not derive the commit SHA by string-splitting the human-readable summary line, which is inherently ambiguous when refnames contain `]`. Instead, obtain the SHA deterministically, e.g. by running `git rev-parse HEAD` (or `--porcelain`/`--format` machine-readable output) immediately after the commit, or by passing `--quiet` plus a separate `git rev-parse HEAD` call, rather than parsing `[branch sha] summary`.

### Proof of Concept
1. Attacker creates a public repository with a branch literally named `feature]evil` (allowed by Git; `]` is not in the disallowed character set of `git check-ref-format`).
2. Victim clones/fetches the repository in GitHub Desktop and checks out `feature]evil` (Desktop does not re-sanitize remote branch names — `sanitizedRefName`/`testForInvalidChars` only guard user-typed new branch names, see `app/src/lib/sanitize-ref-name.ts`).
3. Victim makes a commit while on that branch. Git emits stdout like `[feature]evil abc1234] commit message`.
4. `parseCommitSHA` (`app/src/lib/git/core.ts:606-608`) computes `"abc1234"`'s slot incorrectly, returning `undefined` instead of the real SHA, which is then propagated as the return value of `createCommit`/`createMergeCommit` (`app/src/lib/git/commit.ts:71`, `:135`) to any caller depending on it.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
