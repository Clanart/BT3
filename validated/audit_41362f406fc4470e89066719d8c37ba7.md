### Title
Deterministic Cached Preprocess Reuse Enables FROST Nonce Reuse and Secret Share Recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The coordinator's MuSig/FROST signing protocol derives signing nonces deterministically from a seed cached in the database under `CachedPreprocesses`, keyed only by `context` (`(b"DkgConfirmer", attempt)`). The cache entry is never deleted after use, and every call to `share`/`complete` re-derives the identical nonces via `AlgorithmSignMachine::from_cache`. The module's own header documents that "it is explicitly unsafe to reuse nonces across signing sessions" and that safety relies solely on BFT finality plus a still-unimplemented check ("TODO: ... check the commitments generated from the decided nonces are in fact its commitments on-chain"). This is the direct analog of CVE-2016-1961's use-after-free: a stale, supposedly-consumed object (the one-time preprocess/nonce state) is silently reused on a later code path.

### Finding Description
In `preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:100-148), the seed for `ChaCha20Rng` is loaded from `CachedPreprocesses::get(self.txn, &self.context)`; if absent it is generated once and stored. The cached value is XOR-"encrypted" with a key derived from the validator's secret key, then passed to `from_cache` → `seeded_preprocess` (crypto/frost/src/sign.rs:121-144), which regenerates the same `nonces` and `commitments` every time the same context is used.

`share_internal` (line 150-181) calls `preprocess_internal` again and then `machine.sign(preprocesses, msg)`. `DkgConfirmer::share` (line 304-310) and `DkgConfirmer::complete` (line 312-327) both reach `share_internal`. The message signed is `set_keys_message(set, removed, key_pair)`, and the FROST binding factor `rho` binds the per-participant preprocesses. If `share` is invoked a second time for the same `(attempt)` context with either:

- a different participant preprocess set (different `included`/`rho`/challenge), or
- a different `key_pair` (different `msg`),

the same secret nonces produce shares for two distinct challenges, satisfying the standard FROST/Schnorr nonce-reuse equation `s1 - s2 = (c1 - c2) * share * lambda`, enabling recovery of the validator's MuSig secret share — the root-of-trust key used to confirm DKG results on-chain.

The documented defense is purely procedural: BFT ordering is assumed to make re-signing with distinct inputs impossible, and the on-chain commitment-match check is an acknowledged TODO. There is no cryptographic or state-machine guard — `CachedPreprocesses` is never cleared, so any logical flaw, message-overwrite edge, or partial-rebuild path that causes `share`/`preprocess` to re-execute under a previously-used context with different inputs produces nonce reuse.

### Impact Explanation
Recovery of a validator's long-term MuSig secret share. Since these are the validators' own keys (the root of trust for DKG confirmation per the module header), a leaked share contributes toward threshold compromise of the entire validator-set signing authority — not just one session. Impact maps to "key share recovery", an accepted impact class.

### Likelihood Explanation
Reachability requires a second `share` execution for an existing context with differing inputs. Under correct BFT operation and no rebuilds, inputs are identical and reuse is benign (deterministic re-execution yields the same share). The risk materializes through paths the code itself flags: reorganization/rebuild divergence (line 41-48), and the missing on-chain commitment verification (line 50-51 TODO) means a rebuilt node can publish commitments/shares inconsistent with what the chain finalized without detection. Because the safety precondition is unenforced in code and rests on an assumption the implementation marks incomplete, this is a real defect; severity is contingent on a triggering edge, placing it at Medium-High rather than confirmed Critical.

### Recommendation
1. Delete or tombstone the `CachedPreprocesses` entry when `share_internal` produces a share, so any second sign attempt under the same context fails loudly instead of silently reusing nonces.
2. Implement the documented TODO: before publishing a share, verify the locally derived preprocess commitments match the commitments attributed to this validator in the finalized on-chain/BFT transcript; abort if they differ.
3. Bind the message digest (or its hash) into the `CachedPreprocesses` key so a different `key_pair`/`msg` under the same attempt cannot reuse the seed.

### Proof of Concept
Conceptual, grounded in the code paths above:

1. `DkgConfirmer::share(preprocesses_A, key_pair_A)` executes → `preprocess_internal` loads seed S (context `(b"DkgConfirmer", attempt)`), derives nonces `k`, signs `msg_A` under binding `rho_A`, publishes share `s_A`. Seed S remains in `CachedPreprocesses`.
2. Any path (rebuild onto a divergent finalized chain, or a message-handling flaw) triggers `share(preprocesses_B, key_pair_B)` with `(rho_B, msg_B) != (rho_A, msg_A)` → identical nonces `k`, published share `s_B`.
3. `share_secret = (s_A - s_B) / ((c_A - c_B) * lambda_i)` over the Ristretto scalar field recovers the validator's secret share, where `c` is the Schnorr challenge and `lambda_i` the Lagrange coefficient — standard nonce-reuse algebra acknowledged in the file header (lines 25-35) and in `spec/cryptography/FROST.md` (lines 51-55).
