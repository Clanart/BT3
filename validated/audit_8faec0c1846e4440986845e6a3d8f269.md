### Title
Native value sent with `rewards()` calls to the distribution precompile is permanently stranded - (File: precompiles/distribution/distribution.go)

### Summary
The distribution precompile at `0x0000000000000000000000000000000000001007` validates that a non-zero `msg.value` is rejected for every mutating ("transaction") method, but the `rewards` view method is missing this check. An EVM caller that sends value alongside a call to `rewards()` will have that value permanently locked at the precompile address, exactly mirroring the pattern in the referenced report where `Market#claimFee` sends the protocol fee to `MarketFactory`, an address with no withdrawal path.

### Finding Description
`PrecompileExecutor.Execute` for the distribution precompile explicitly calls `pcommon.ValidateNonPayable(value)` before executing `WithdrawValidatorCommissionMethod`, and each other transaction handler (`setWithdrawAddress`, `withdrawDelegationRewards`, etc.) enforces `p.validateInput(value, args, N)` which internally checks value is zero, per the pattern seen consistently across every precompile version: [1](#0-0) 

The `RewardsMethod` case, however, is dispatched directly without any payable check: [2](#0-1) 

This gap is explicitly documented in the integration test suite for this precompile, which notes that `rewards()` is "the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)", and for that reason deliberately omits a "view rejects value" test for this method: [3](#0-2) 

In the EVM, a `CALL` with non-zero value transfers that value into the callee's balance before the callee's code (or precompile logic) executes, regardless of what the precompile subsequently does with `value`. Because `rewards()` never validates or rejects the value, and because the precompile is a fixed system address (`0x1007`) rather than a bank module account with a sweep/refund mechanism, any usei/wei sent this way accumulates at that address with no code path in the codebase that reads it back out. Distribution's precompile only implements withdrawal flows for delegator rewards and validator commission that are funded from the on-chain distribution module account — none of them reference or drain the precompile's own EVM balance.

### Impact Explanation
Any unprivileged EVM transaction sender or contract that calls `rewards(address)` on `0x1007` and attaches native value (either directly or unintentionally, e.g. via a wrapper contract that forwards `msg.value` to arbitrary calls) will have those funds permanently and irrecoverably locked, since there is no withdraw/sweep function targeting the precompile's own balance. This is a direct funds-freezing bug analogous to the H-3 finding, satisfying the "permanent freezing of funds" impact criterion.

### Likelihood Explanation
The precompile address is well known and publicly documented, and `rewards()` is a straightforward, commonly-called view function. Any transaction sender (EOA or contract) can trigger this by simply attaching `value` to the call — no special privileges, contract deployment, or specific setup is required. The likelihood is elevated by contracts that generically forward `msg.value` to arbitrary low-level calls (e.g. proxy/router-style contracts) that could inadvertently attach value when relaying a `rewards()` query.

### Recommendation
Add the same `pcommon.ValidateNonPayable(value)` check to the `RewardsMethod` case (and audit all other precompiles for the same gap) so that a non-zero value attached to a view-only precompile call is rejected before the EVM performs the value transfer, preventing funds from ever reaching the precompile's balance.

### Proof of Concept
1. From any funded EVM account, construct a call to the distribution precompile at `0x0000000000000000000000000000000000001007` invoking `rewards(address)` (encoded per `IDistr`/ABI) with `value` set to a non-zero wei amount and a normal gas limit.
2. Submit the transaction; because `Execute` routes `RewardsMethod` straight to `p.rewards(ctx, method, args)` without a non-payable check, the call succeeds and returns the queried rewards data.
3. The attached value was already credited to the precompile address's EVM/StateDB balance as part of standard EVM value-transfer semantics before precompile logic ran.
4. Query the balance of `0x1007` (or the corresponding usei balance via the bank module) — it now holds the sent funds.
5. There is no method on the distribution precompile, nor any other reachable code path, that transfers balance out of `0x1007`; the funds are permanently stuck. [4](#0-3) [3](#0-2)
