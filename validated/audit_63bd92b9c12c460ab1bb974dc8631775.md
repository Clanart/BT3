## Title
Hookify PreToolUse policy engine silently fails open for tool/field combinations not enumerated in `_extract_field`, letting an agent bypass blocking rules by choosing an unvalidated tool path — (File: `plugins/hookify/core/rule_engine.py`)

### Summary
The bug-class in the Brahma report is a validator that checks only a subset of the parameters that actually control a transaction's effect (`to, value, data, operation, signatures`) while `execTransaction` accepts additional unchecked parameters (`safeTxGas, baseGas, gasPrice, gasToken, refundReceiver`) that can redirect funds — the operator picks the unchecked parameters to steal value while still satisfying the checked ones. The `hookify` plugin's `RuleEngine` in this repo has the same root-cause shape at the trust boundary between an agent/operator (the "SubAccount operator" analog is any agent/teammate running with restricted permissions under a user-authored policy) and the enforcement point (the "trusted validator" analog): the engine's field extractor recognizes only a hard-coded subset of tool/field combinations, and any tool call whose effect is carried through a field or tool it doesn't recognize is treated as non-matching (allowed) rather than as unverifiable (denied).

### Finding Description
`RuleEngine._extract_field()` [1](#0-0)  is the single place that maps a rule's declared `field` (e.g. `command`, `content`, `file_path`, `new_text`) to a value pulled from `tool_input`. It hard-codes support only for `Bash` (`command`), `Write`/`Edit` (`content`, `new_string`/`old_string`, `file_path`), and `MultiEdit` (`file_path`, concatenated `new_string`). For any other tool name, or any field/tool combination not explicitly enumerated, the function falls through to `return None` at line 254.

`_check_condition()` treats a `None` field value as an automatic non-match: `if field_value is None: return False` [2](#0-1) . `_rule_matches()` then requires every condition to be true, so a single unmatched condition means the rule as a whole does not fire, and `evaluate_rules()` returns `{}` (i.e., "no matches — allow operation") [3](#0-2) .

This mirrors the Brahma finding precisely: the policy author writes a rule assuming the checked field (analogous to `to/value/data/operation`) fully captures the operation's effect, but the enforcement point silently allows any tool call whose effect flows through a field/tool the checker does not know about (analogous to `safeTxGas/gasPrice/refundReceiver`). Crucially, the engine's default behavior on "unknown" is **allow**, not **deny** — a classic fail-open policy gap, not merely a UX limitation, because `tool_matcher` in a rule's frontmatter can legally list multiple tools (e.g. `"Write|Edit|MultiEdit"` or `"*"`) while `_extract_field` only implements real extraction for a strict subset of tool/field pairs [4](#0-3) .

### Impact Explanation
A user (analogous to the trusted validator/policy owner) who deploys a hookify blocking rule intending to stop an agent from writing secrets or dangerous content expects the rule's `tool_matcher` scope to be fully enforced across the tools it names. Because `_extract_field` only implements `content`/`new_string`/`old_string`/`file_path` for `Write`/`Edit`/`MultiEdit` and `command` for `Bash`, any rule condition referencing a field on a tool outside that enumerated set (e.g. `NotebookEdit`, or a field like `description`, `old_string` on `Write`, or any MCP tool) is unconditionally bypassed — the blocking rule never fires and the operation proceeds as if no policy existed. An agent operating under reduced trust that discovers this gap (e.g. by inspecting the shipped plugin source, which is open and documented) can route the same effect through an unguarded tool/field to defeat the intended safety control, exactly as the SubAccount operator routed value extraction through gas-refund parameters the trusted validator's signature never covered.

### Likelihood Explanation
The hookify plugin and its `rule_engine.py` are shipped, documented plugin code (`plugins/hookify/hooks/pretooluse.py` invokes it directly as a `PreToolUse` gate) [5](#0-4) , so any project relying on it for safety enforcement is exposed. The condition-field/tool enumeration is small and static, so the fail-open gap is deterministic and easily discoverable by reading `_extract_field`; an agent or malicious skill author does not need to guess — they can simply target a tool/field pair absent from the switch-like logic.

### Recommendation
Change `_extract_field` to distinguish "field not applicable to this rule" from "field not recognized/implemented for this tool." When a rule's `tool_matcher` matches the current `tool_name` but `_extract_field` has no explicit extraction logic for the requested `field`, the engine should treat the condition as unverifiable and fail closed (i.e., treat it as a match for a blocking rule, or otherwise surface a warning/ask decision) rather than silently returning `None`/`False`, which is currently indistinguishable from "field explicitly checked and did not match." At minimum, extend the extractor to cover every documented tool (`NotebookEdit`, `Read`, `Grep`, `Glob`, MCP tools) or reject/`ask` when a rule references an unsupported tool/field combination at load time in `config_loader.py`.

### Proof of Concept
1. Author `.claude/hookify.secret-write.local.md` with:
```yaml
---
name: block-secret-write
enabled: true
tool_matcher: "Write|Edit|NotebookEdit"
conditions:
  - field: content, operator: contains, pattern: "AKIA"
action: block
---
Blocks writes containing AWS key material.
```
2. The rule is loaded via `load_rules()` and applies to `NotebookEdit` per `tool_matcher` [4](#0-3) .
3. An agent invokes `NotebookEdit` with a cell body containing `AKIA...` secret material. `_extract_field('content', 'NotebookEdit', tool_input, ...)` falls through every branch (`Bash`, `Write/Edit`, `MultiEdit`) and returns `None` [6](#0-5) .
4. `_check_condition` sees `field_value is None` and returns `False`, so the rule does not match, `evaluate_rules` returns `{}`, and `pretooluse.py` prints an empty allow decision — the secret is written despite the rule the user believed would block it. The same class of gap applies to any field named on `Write`/`Edit` that isn't `content`/`new_string`/`old_string`/`file_path` (e.g. hypothetical future fields), reproducing the "checked-fields vs. actually-effective-fields" mismatch from the Safe.sol finding.

```python
    def _extract_field(self, field: str, tool_name: str,
                      tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> Optional[str]:
        """Extract field value from tool input or hook input data.

        Args:
            field: Field name like "command", "new_text", "file_path", "reason", "transcript"
            tool_name: Tool being used (may be empty for Stop events)
            tool_input: Tool input dict
            input_data: Full hook input (for accessing transcript_path, reason, etc.)

        Returns:
            Field value as string, or None if not found
        """
        # Direct tool_input fields
        if field in tool_input:
            value = tool_input[field]
            if isinstance(value, str):
                return value
            return str(value)

        # For Stop events and other non-tool events, check input_data
        if input_data:
            # Stop event specific fields
            if field == 'reason':
                return input_data.get('reason', '')
            elif field == 'transcript':
                # Read transcript file if path provided
                transcript_path = input_data.get('transcript_path')
                if transcript_path:
                    try:
                        with open(transcript_path, 'r') as f:
                            return f.read()
                    except FileNotFoundError:
                        print(f"Warning: Transcript file not found: {transcript_path}", file=sys.stderr)
                        return ''
                    except PermissionError:
                        print(f"Warning: Permission denied reading transcript: {transcript_path}", file=sys.stderr)
                        return ''
                    except (IOError, OSError) as e:
                        print(f"Warning: Error reading transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
                    except UnicodeDecodeError as e:
                        print(f"Warning: Encoding error in transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
            elif field == 'user_prompt':
                # For UserPromptSubmit events
                return input_data.get('user_prompt', '')

        # Handle special cases by tool type
        if tool_name == 'Bash':
            if field == 'command':
                return tool_input.get('command', '')

        elif tool_name in ['Write', 'Edit']:
            if field == 'content':
                # Write uses 'content', Edit has 'new_string'
                return tool_input.get('content') or tool_input.get('new_string', '')
            elif field == 'new_text' or field == 'new_string':
                return tool_input.get('new_string', '')
            elif field == 'old_text' or field == 'old_string':
                return tool_input.get('old_string', '')
            elif field == 'file_path':
                return tool_input.get('file_path', '')

        elif tool_name == 'MultiEdit':
            if field == 'file_path':
                return tool_input.get('file_path', '')
            elif field in ['new_text', 'content']:
                # Concatenate all edits
                edits = tool_input.get('edits', [])
                return ' '.join(e.get('new_string', '') for e in edits)

        return None
```

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
```
