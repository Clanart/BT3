## Title
Conflict-resolution size guard excludes hunk context lines from its byte/line-length check, allowing oversized/malformed content into the Copilot conflict-resolution prompt - (File: `app/src/lib/copilot-conflict-context.ts`)

### Summary
`getHunkSkipReason` is the guard that decides whether a conflicted file's content is "safe" to send to the Copilot conflict-resolution model, both to bound prompt size and to avoid feeding pathological (e.g. minified/generated) content into a line-oriented resolution. Like the reported MEV-lane bug — which sized a bid transaction without accounting for the bundled transactions that get unpacked and duplicated into the final block — this guard only measures `oursContent`, `theirsContent`, and `baseContent`, but the function that actually builds the prompt payload (`formatConflictContextForPrompt`) also injects `contextBefore` and `contextAfter` for every hunk. Those context fields are completely excluded from both the per-line-length check and the total-size accumulator, so the real payload sent to the model can be arbitrarily larger/more pathological than what the guard verified.

### Finding Description
`extractConflictHunks` produces, per hunk, `oursContent`, `theirsContent`, optional `baseContent`, plus `contextBefore`/`contextAfter` (a few lines of unchanged file content surrounding the conflict marker block): [1](#0-0) 

The size/safety guard, `getHunkSkipReason`, iterates only `oursContent`, `theirsContent`, `baseContent` for both the per-line length check (`MAX_CONFLICT_LINE_LENGTH`) and the cumulative size check (`MAX_CONFLICT_CONTENT_SIZE`): [2](#0-1) 

But when the prompt is actually assembled, `contextBefore` and `contextAfter` are appended unconditionally and unchecked, wrapped in fenced code blocks alongside the vetted content: [3](#0-2) 

This is the same broken invariant as the report: a size/safety check is computed against a partial representation of the data (`ours`/`theirs`/`base`), while a different, larger representation that includes additional unchecked material (`contextBefore`/`contextAfter`) is what is actually used downstream. The guard's own doc comment states its purpose is "what we actually send" to the model, but it demonstrably does not cover all of what is sent.

### Impact Explanation
An attacker who controls a branch/commit that ends up conflicting with the victim's work (e.g. a malicious PR later merged, or a crafted remote branch) can place a single extremely long line (or many long lines) immediately adjacent to — but outside — a conflict marker block. Because `contextBefore`/`contextAfter` bypass `MAX_CONFLICT_LINE_LENGTH` and `MAX_CONFLICT_CONTENT_SIZE` entirely, this content is never flagged as "too large/pathological" and the file is not skipped, yet the actual prompt sent to the LLM balloons or contains minified/adversarial content the guard was specifically designed to filter out. Downstream, `reassembleResolvedFile` splices the model's per-hunk resolutions back into the original file strictly by ordinal index, not by content matching: [4](#0-3) 

If the oversized/unfiltered context degrades the model's output (e.g. it emits a wrong number of hunk resolutions or garbled content for that file), the ordinal splice silently misapplies resolutions into the wrong conflict locations. This is then written straight to disk and staged when the user clicks "Continue Merge": [5](#0-4) 

producing silent corruption of what the user ultimately commits/pushes, with the user only seeing a summarized AI resolution rather than reviewing every spliced line.

### Likelihood Explanation
Requires the attacker to control content that ends up conflicting with the user's local changes (contribution via PR/branch merged by the victim, or a crafted remote), and requires the victim to opt into "Resolve with Copilot" and accept the result. This matches the accepted threat model (attacker controls a fetched/cloned repository or PR content) but depends on model-behavior variance under degraded/oversized prompts, which is probabilistic rather than deterministic.

### Recommendation
Include `contextBefore` and `contextAfter` in both the per-line-length loop and the cumulative `totalContent` computation in `getHunkSkipReason`, since they are unconditionally included in the actual prompt built by `formatConflictContextForPrompt`. Additionally, harden `reassembleResolvedFile`/`reassembleResolutions` to validate that the model returned exactly the expected number of hunk resolutions per file (matching `file.hunks.length`) before splicing, and refuse/flag mismatches instead of silently applying an ordinal best-effort merge.

### Proof of Concept
1. Attacker crafts a file with a normal, small conflict block but adds a single ~500KB unchanged line as the line immediately preceding or following the conflict markers (within `contextLines` distance, e.g. line 1-3 lines away).
2. Victim encounters this file as a merge/rebase/cherry-pick conflict and clicks "Resolve with Copilot".
3. `buildConflictContext` → `extractConflictHunks` captures the huge line inside `contextBefore`/`contextAfter`; `getHunkSkipReason` only measures `oursContent`/`theirsContent`/`baseContent`, which remain small, so the file is not skipped: [6](#0-5) 
4. `formatConflictContextForPrompt` embeds the full oversized context line into the prompt sent to the model: [7](#0-6) 
5. If the model's response for this file is truncated or miscounts hunks due to the oversized/degraded input, `reassembleResolvedFile`'s ordinal splice applies resolutions to the wrong hunk positions, and the corrupted result is written to disk and staged upon "Continue Merge" without further validation.

export function getHunkSkipReason(
  hunks: ReadonlyArray<IConflictHunk>
): string | null {
  let totalContent = 0

  for (const hunk of hunks) {
    const sides = [hunk.oursContent, hunk.theirsContent, hunk.baseContent ?? '']
    for (const side of sides) {
      totalContent += side.length
      for (const line of side.split('\n')) {
        if (line.length > MAX_CONFLICT_LINE_LENGTH) {
          return 'Conflict contains lines too long to resolve automatically'
        }
      }
    }
    if (totalContent > MAX_CONFLICT_CONTENT_SIZE) {
      return 'Conflict region too large to resolve automatically'
    }
  }

  return null
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
