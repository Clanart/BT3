### Title
`extract_frontmatter` naive `str.split('---', 2)` lets embedded delimiter text silently downgrade a `block` rule to `warn` - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` locates YAML frontmatter boundaries using a plain `content.split('---', 2)` instead of matching `---` only at line boundaries. If any frontmatter field value (e.g. a regex `pattern`) contains the literal substring `---`, the parser mis-detects the closing delimiter, truncates the frontmatter early, and the trailing text — including a legitimately written `action: block` line — gets silently absorbed into the rule's message body instead of being parsed as YAML. Because `Rule.from_dict` defaults `action` to `"warn"` when the key is missing, the resulting `Rule` object silently becomes a warn-only rule even though the file visibly says `action: block`.

### Finding Description
`extract_frontmatter` gates on `content.startswith('---')` and then does: [1](#0-0) 
`str.split` matches the substring `---` anywhere in the text, not just at line-start delimiter positions. With `maxsplit=2`, the second delimiter is found at the *first* subsequent occurrence of `---`, which can be inside a quoted field value rather than the actual closing `---` line. For example:

```
---
name: bad
event: bash
pattern: "rm -rf --- foo"
action: block
---
message
```

Here the second `---` match falls inside the `pattern` string, so `parts[1]` (the parsed frontmatter text) ends right after `rm -rf `, and `parts[2]` becomes ` foo"\naction: block\n---\nmessage\n` — this entire remainder is treated as the message body, never re-parsed as YAML. The `action: block` line is therefore never captured into the `frontmatter` dict.

`Rule.from_dict` then does `action=frontmatter.get('action', 'warn')`, defaulting to `"warn"`: [2](#0-1) 

This downstream flows into `RuleEngine.evaluate_rules`, which treats matching rules with `action != 'block'` as warning-only (operation allowed) rather than blocking (operation denied): [3](#0-2) [4](#0-3) 

`load_rule_file`/`load_rules` are invoked directly by the `PreToolUse` (and `Stop`/`PostToolUse`) hook scripts on every `Bash`/`Edit`/`Write`/`MultiEdit` tool call, with no re-validation that the parsed `Rule` matches the visible frontmatter text: [5](#0-4) 

No existing check compares the parsed frontmatter against the raw file, and there is no anchoring of the `---` delimiter to a line boundary (e.g. regex `^---\s*$`), so this ambiguity is unguarded.

### Impact Explanation
An attacker who can influence the content of a `.claude/hookify.*.local.md` rule file (e.g., via a pull request that a maintainer merges, or any repo content path that ends up being loaded by `load_rules`) can craft a pattern value containing `---` that *visually* looks like an innocuous regex fragment but causes the parser to silently drop the `action: block` field. The rule file still reads as "action: block" to a human reviewer, but the actual enforced `Rule` object is `action: "warn"`. This breaks the invariant that rule semantics must not depend on formatting/parsing ambiguity, and it means a security control intended to block a dangerous `Bash`/`Edit` operation (e.g., `rm -rf`, credential exfiltration commands) only warns and does not deny the operation, matching the "Unauthorized local command execution that bypasses Claude Code approval or deny controls" impact class.

### Likelihood Explanation
This is fully triggerable by controlling text content of a rule markdown file without any privileged access — it requires no local shell, only the ability to get such a file's content into the `.claude/` directory that `load_rules` scans via `glob.glob('.claude/hookify.*.local.md')` in the current working directory (e.g., a repository the target user has cloned and on which Claude Code hooks run). The bug is deterministic and 100% reproducible for any rule whose pattern/message text contains the substring `---`, which is plausible for regex patterns matching command flags/ranges or markdown-style separators.

### Recommendation
Replace the naive substring split with a delimiter matcher anchored to line boundaries, e.g. using `re.split(r'(?m)^---\s*$', content, maxsplit=2)` or a proper YAML frontmatter library (`python-frontmatter`/`yaml.safe_load`), so that `---` occurring inside field values is never mistaken for a frontmatter delimiter. Additionally, after parsing, defensively re-validate that `action` is an explicit, expected value and fail closed (treat unparseable/ambiguous frontmatter as `block` or reject the rule) rather than defaulting silently to `warn`.

### Proof of Concept
Unit test to add to `plugins/hookify/core/config_loader.py` tests:
```python
def test_embedded_delimiter_downgrades_block_rule():
    content = '''---
name: bad-rm
event: bash
pattern: "rm -rf --- foo"
action: block
---
Dangerous command blocked!
'''
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # Expected (correct) behavior: action should remain "block"
    assert rule.action == "block", (
        f"Rule action was silently downgraded to {rule.action!r} due to "
        "embedded '---' in frontmatter value; visible file said 'action: block'"
    )
```//
Running this against the current implementation fails: `frontmatter` will not contain the `action` key (it was consumed into `message`), so `rule.action == 'warn'`, demonstrating that the parsed `Rule` object differs from the semantics visibly written in the file — confirming the vulnerability.
