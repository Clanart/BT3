**Analysis summary (not a full report since finding is invalid):**

The attack requires calling `Verifier::optimistic_payout_sign` (via the `ClementineVerifier/OptimisticPayoutSign` gRPC method) directly with a stolen `nonce_session_id`. However, verifier (and operator) gRPC servers are protected by an mTLS interceptor, `Interceptors::OnlyAggregatorAndSelf`, which rejects any request whose peer TLS leaf certificate doesn't match the configured aggregator certificate or the entity's own certificate [1](#0-0) . This is wired into every verifier server via `create_grpc_server`/`servers.rs`, which builds `ServerTlsConfig` with client certificate verification and applies `OnlyAggregatorAndSelf` as the interceptor whenever `client_verification` is enabled [2](#0-1) .

The premise of the question is an "unprivileged attacker" who explicitly "hold[s]... no ... TLS certificate." Since `optimistic_payout_sign` is a `ClementineVerifier` RPC (not exposed by the aggregator's public gRPC surface) and requires a valid client certificate matching the aggregator's pinned cert to be accepted at all [3](#0-2) , such an attacker cannot reach `Verifier::sign_optimistic_payout` directly regardless of whether they know a `nonce_session_id` belonging to another party.

The only legitimate caller capable of invoking `optimistic_payout_sign` on verifiers is the aggregator, and the aggregator itself always pairs a `nonce_gen` session with the `first_response` it obtained for that exact same withdrawal request within `withdraw`/`optimistic_payout` flow, never reusing another caller's session id [4](#0-3) . The aggregator has no public RPC that lets an external, unauthenticated caller supply an arbitrary `nonce_session_id` to be forwarded verbatim to a verifier's `optimistic_payout_sign`.

Therefore, while it's true that `AllSessions`/`NonceSession` has no caller-ownership binding at the data-structure level [5](#0-4) , this is not exploitable by the defined unprivileged attacker because the transport-level mTLS authentication (`only_aggregator_and_self`) already prevents any non-aggregator, non-self party from reaching the vulnerable code path in the first place.

#[allow(clippy::result_large_err)]
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
