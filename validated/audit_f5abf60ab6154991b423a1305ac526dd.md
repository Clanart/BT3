The Python `json_format.Parse` duplicate-key detection is a strict string-equality check on the raw JSON key, not a check keyed on the resolved `FieldDescriptor`. This means the same target field can be set twice under two different accepted spellings (original snake_case name and JSON `camelCase`/`json_name`) without triggering the duplicate-field error, silently taking a "last value wins" outcome — exactly the same class of ambiguity (multiple accepted spellings resolving to one underlying parameter/field, causing silent overwrite/contamination) as CVE-2012-2965's PHP variable-name handling issue.

### Title
JSON parser duplicate-field detection is bypassed by alternate name spellings, enabling silent "last field wins" contamination - (File: `python/google/protobuf/json_format.py`)

### Summary
`json_format.Parse` is Caucho Quercus/Resin's PHP request parser is a public, application-facing entry point that accepts attacker-controlled ProtoJSON text and merges it into a trusted message via `_Parser._ConvertFieldValuePair`. The duplicate-key rejection logic tracks only the literal JSON key string that was seen (`names.append(name)` / `if name in names`), not the `FieldDescriptor` that the key resolves to. Since a single field can be legitimately addressed by more than one JSON spelling (its proto `name` and its `json_name`/camelCase form), an attacker can submit both spellings for the same field in one JSON object and have the second spelling silently overwrite the first, without the "duplicate field" error firing and without any indication to calling application code that two conflicting values were supplied for one field.

### Finding Description
`_ConvertFieldValuePair` builds `fields_by_json_name` from `message_descriptor.fields` and resolves each incoming JSON key to a `FieldDescriptor` via either the `json_name` map or `fields_by_name`: [1](#0-0) . It then performs duplicate detection purely against the raw string `name`: [2](#0-1) . Because the check is `if name in names` (list of literal keys seen) rather than checking the resolved `field`, two different JSON keys that resolve to the same `FieldDescriptor` (e.g. `"int32Value"` and `"int32_value"`) both pass the duplicate check individually, and the second one simply overwrites the value set by the first via `setattr`/field assignment later in the function. This is confirmed directly by the project's own test comments, which acknowledge it as "a non-spec... oversight bug": [3](#0-2) . The same "duplicate key" invariant is intended to be enforced (and is correctly enforced for exact-string duplicates) per `testDuplicateField`: [4](#0-3) , but the check's granularity (string identity) does not match the actual uniqueness domain (field identity), which is the same class of "unspecified/alternate character-mapping of parameter identity" flaw as the Quercus CVE: multiple names alias one underlying value, and the parser's contamination/duplicate check operates on the wrong identity space.

This is not merely a cosmetic parser quirk: the C++ ProtoJSON parser (`src/google/protobuf/json/internal/parser.cc`) correctly performs duplicate detection keyed by the resolved field via `Traits::RecordAsSeen(*field, msg)`: [5](#0-4) , demonstrating that field-identity-based duplicate detection is the intended, correct invariant, and that the pure-Python implementation deviates from it.

### Impact Explanation
An application that relies on `json_format.Parse`'s duplicate-field rejection as an integrity guarantee (e.g., to reject JSON payloads that try to set the same logical field twice, perhaps for idempotency, request validation, or defense against "parameter pollution"-style attacks where a value is set once for validation/logging and once for the actual effect) can be bypassed by an attacker who submits the field under its alternate accepted spelling. This can lead to a value silently taking effect that a validation layer believed was rejected or fixed, an integrity/logic bypass consistent with the "unknown impact" characterization of the original HTTP Parameter Contamination CVE. The same aliasing also applies to map fields (`int32Map` vs `int32_map`), confirmed by `testDuplicateFieldAlternateNamesMap`: [6](#0-5) .

### Likelihood Explanation
Every field in a proto3 (and most proto2) message has at least two valid JSON spellings (raw `name` and `json_name`) by default, so this is trivially reachable by any client sending ProtoJSON to a public `Parse`/`MessageToJson`-consuming API — no special schema, extension, or privileged access is required. This is a Medium/qualitatively-High-likelihood but narrow-impact analog: it requires the calling application to actually rely on protobuf's duplicate-key rejection as a security boundary, which is not guaranteed but is a documented, plausible usage pattern (validate-then-act on a "single value per field" assumption).

### Recommendation
Change the duplicate-detection bookkeeping in `_ConvertFieldValuePair` to track resolved `FieldDescriptor` objects (and their `containing_oneof`) rather than the raw literal JSON key string, so that any two JSON keys resolving to the same field are treated as a duplicate regardless of spelling — mirroring the field-identity-based `RecordAsSeen` behavior already used by the C++ parser at `src/google/protobuf/json/internal/parser.cc:1256`.

### Proof of Concept
Using the pure-Python parser directly (as documented and reproduced by the project's own regression test):
```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2

msg = json_format_proto3_pb2.TestMessage()
json_format.Parse('{"int32Value": 1,"int32_value":2}', msg)
assert msg.int32_value == 2  # second spelling silently wins; no "duplicate field" error
```
This is the exact scenario captured in `testDuplicateFieldAlternateNames`: [7](#0-6) , contrasted with the correctly-rejected exact-duplicate case in `testDuplicateField`: [4](#0-3) .
