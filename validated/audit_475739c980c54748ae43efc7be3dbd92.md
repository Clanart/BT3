### Title
Unrestricted `shell.openExternal` in `open-external` IPC handler enables local file/protocol execution from untrusted content - (File: `app/src/main-process/main.ts`)

### Summary
The `open-external` IPC handler only logs when a URL looks like `http(s)`, but performs no validation or allow-listing before calling `shell.openExternal(path)`. [1](#0-0) 

### Finding Description
`shell.openExternal` is a powerful primitive: on Windows/macOS it can launch other registered protocol handlers or applications (e.g. `file://`, custom URI schemes registered by other installed software), not just a browser. The handler here checks `pathLowerCase.startsWith('http://')`/`https://'` **only to decide whether to log**, then unconditionally calls `shell.openExternal(path)` regardless of scheme: [1](#0-0) 
This handler is invoked from the renderer over IPC. The IPC layer does validate the *sender* (`isTrustedIPCSender`), which blocks untrusted webContents, but it does not validate the *content* of the `path` argument. [2](#0-1) 
Content that reaches this call can originate from attacker-controlled data rendered in the app UI — e.g., links inside PR descriptions, commit messages, or other GitHub API text fields that the renderer turns into "open external link" actions. Because there's no scheme restriction, a crafted value (e.g. a `file://` path, an SMB UNC path, or another installed app's custom protocol) can be forwarded to `shell.openExternal`, which is a well-documented Electron risk (unrestricted `openExternal` calls with attacker-controlled input can lead to local file access or launching of arbitrary registered handlers).

Compare this to the `open-repository-from-url` / `filepath` path in `parseAppURL` and `openRepositoryFromUrl`, which explicitly guards against absolute paths and path traversal using `isAbsolute` + `resolveWithin`: [3](#0-2) 
No equivalent scheme/path validation exists for `open-external`.

### Impact Explanation
If reachable with attacker-influenced input (e.g., a malicious PR body, issue link, or commit trailer rendered as a clickable "open external" action), this can result in launching arbitrary local files or other installed applications' custom URI handlers via `shell.openExternal`, which is exactly the class of "unrestricted external navigation" issue Electron's own security guide calls out. This matches the report's underlying pattern — an entry point with more capability (`payable`/`openExternal` with no scheme allow-list) than the restricted operation it's meant to perform (opening `http(s)` links) actually needs, creating an avenue for unintended side effects.

### Likelihood Explanation
Moderate: exploitation requires the renderer to actually forward attacker-controlled, non-http(s) content to this specific IPC channel (e.g., through a link-rendering path that doesn't itself restrict schemes before calling `dispatcher`/`ipcRenderer.invoke('open-external', ...)`). I was not able to fully trace every renderer call site of `open-external` within the available tool budget to confirm which UI surfaces pass fully attacker-controlled strings versus pre-sanitized `http(s)` URLs, so this should be verified against the renderer call sites before treating it as a confirmed end-to-end exploit chain.

### Recommendation
Enforce an explicit allow-list of schemes (`http:`, `https:`, `mailto:` if needed) in the `open-external` handler itself, rejecting anything else, so the main-process boundary can't be relied upon to trust renderer-supplied assumptions:
```ts
ipcMain.handle('open-external', async (_, path: string) => {
  const allowed = ['http:', 'https:']
  let parsed: URL
  try { parsed = new URL(path) } catch { return false }
  if (!allowed.includes(parsed.protocol)) {
    log.error(`Refusing to open external link with disallowed scheme: ${parsed.protocol}`)
    return false
  }
  ...
})
```

### Proof of Concept
1. Identify (or add) a renderer code path that calls the `open-external` IPC channel with a string derived from untrusted API/repo content (e.g., a markdown link parser that doesn't strip non-http(s) schemes before invoking "open in browser").
2. Trigger that UI action with a payload such as `file:///Users/victim/.ssh/id_rsa` or a locally-registered custom scheme URL.
3. Observe `shell.openExternal` invoked in the main process without any scheme check: [1](#0-0) 
4. Confirm the file/handler is opened outside the intended `http(s)`-only use case.

**Caveat:** I could not confirm within this session whether any current renderer call site actually forwards fully unsanitized, attacker-controlled strings to this handler — that verification (grepping all `open-external` invoke sites, e.g. in link renderers, PR/issue text renderers) should be done to establish a concrete end-to-end trigger before treating this as a fully proven vulnerability.
