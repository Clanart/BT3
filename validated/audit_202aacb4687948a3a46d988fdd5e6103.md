### Title
Division-by-zero panic in KIP-71 base fee calculation via unchecked `governance.kip71.gastarget=0` vote - ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by the `GasTarget` governance parameter without checking for zero. The governance parameter validation for `Kip71GasTarget` uses `noopFormatChecker`, which accepts any `uint64` value including `0`, unlike the sibling parameter `Kip71BaseFeeDenominator`, which explicitly requires `v != 0`.

### Finding Description
`NextMagmaBlockBaseFee` reads `gasTarget := kc.GasTarget` directly from governance config with no zero-guard, unlike `BaseFeeDenominator` which has an explicit `if kc.BaseFeeDenominator == 0 { ... use fallback 64 }` safety net: [1](#0-0) 

When the parent block's gas used exceeds `gasTarget` (true for essentially any nonzero-gas-used block when `gasTarget == 0`), the code computes:
```
gasUsedDelta := parentGasUsed - gasTarget
x := parentBaseFee * gasUsedDelta
y := x.Div(x, gasTarget)   // gasTarget == 0 -> division by zero
``` [2](#0-1) 

The same unguarded division also exists in the gas-used-below-target branch: [3](#0-2) 

`big.Int.Div` with a zero divisor panics in Go, and this is not a `require`/`revert` guarded by validation before execution — it is a direct runtime panic.

The root cause is that the format checker for the `Kip71GasTarget` governance parameter is a no-op, permitting `0` as a valid value: [4](#0-3) 

Compare this to `Kip71BaseFeeDenominator`, which is explicitly protected against zero: [5](#0-4) 

`NextMagmaBlockBaseFee`/`VerifyMagmaHeader` is invoked on the hot path of block header verification and gas price computation across multiple consensus-relevant call sites: `blockchain/block_validator.go`, `blockchain/chain_makers.go`, `blockchain/tx_pool.go`, `work/worker.go`, and `node/cn/gasprice/gasprice.go` / `feehistory.go`. This means the panic would trigger during header verification of every block once GasTarget=0 governance is active and any block uses gas above 0 relative to its (zero) target.

### Impact Explanation
Because `governance.kip71.gastarget` is a governable parameter set via header votes (like other KIP-71 parameters), a validator/governing node (or a passed governance vote) can set `GasTarget=0`. Once active, every node computing/verifying the next block's base fee (block validators, the tx pool for gas price enforcement, block proposers, and RPC gas price oracle callers) will panic on `big.Int.Div` by zero. This causes a chain-wide crash/halt across all full nodes and validators simultaneously — a consensus/availability-critical DoS reachable purely through the governance parameter update path, without requiring any privileged network position, malicious peer, or code beyond a normal governance vote/transaction. This matches the "state transition / gas accounting" and "governance parameters" reachable categories, and produces node crashes on an entire chain (not merely resource exhaustion — it's a guaranteed unrecovered panic on core consensus logic), so it is High severity.

### Likelihood Explanation
Likelihood depends on governance mode: if `governance.governancemode` is "single" (governing-node controlled) or "ballot", a single governing-node vote (or a majority vote in the naive mode) sets `Kip71GasTarget=0`. Because the format checker never rejects 0 (unlike `BaseFeeDenominator`), the value would be accepted into `ParamSet` and applied at the next epoch. This is a config/logic gap rather than a hypothetical attack requiring cryptographic weaknesses — it is directly reachable by a permitted governance actor performing a normal parameter vote, an action within scope of "governance parameters" as listed in the analog validation rules.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0`, consistent with `Kip71BaseFeeDenominator`'s existing pattern (`v, ok := cv.(uint64); return ok && v != 0`). Additionally, as defense-in-depth, add an explicit zero-check fallback for `gasTarget` in `NextMagmaBlockBaseFee` in `params/kip71_config.go` mirroring the existing `baseFeeDenominator == 0` fallback, so that a `0` value (from legacy/misconfigured chains) does not cause a division-by-zero panic.

### Proof of Concept
1. Deploy/operate a Kaia-based chain with Magma (KIP-71) enabled and governance mode allowing the governing node (or ballot majority) to change parameters.
2. Submit a governance vote for `governance.kip71.gastarget = 0` (validated only by `noopFormatChecker`, which never rejects 0). [4](#0-3) 
3. Once the vote is applied (per epoch transition), any subsequent block whose `parentGasUsed > 0` (i.e., `parentGasUsed > gasTarget=0`) triggers `NextMagmaBlockBaseFee`, entering the `parentGasUsed > gasTarget` branch, which computes `x.Div(x, gasTarget)` with `gasTarget = 0`. [6](#0-5) 
4. `big.Int.Div` panics with a division-by-zero runtime error. This function is invoked from block header verification (`blockchain/block_validator.go`), block assembly (`work/worker.go`), and the tx pool's gas price checks (`blockchain/tx_pool.go`), causing all nodes attempting to validate/propose the next block to crash/panic simultaneously — a chain-wide denial of service.
