### Title
Payout OP_RETURN attribution can be forged because it is not covered by the user's SinglePlusAnyoneCanPay signature - (File: core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs)

### Summary
`create_payout_txhandler` embeds the fronting operator's x-only pubkey in an OP_RETURN output (index 2) that is never covered by the user's withdrawal signature, since that signature uses `TapSighashType::SinglePlusAnyoneCanPay`. Because SIGHASH_SINGLE only commits to the output at the same index as the signed input (index 0) and ANYONECANPAY commits to no other inputs, anyone who obtains the signed input/witness for output 0 can construct an entirely different transaction that reuses that input/output but substitutes an arbitrary OP_RETURN, including a real but uninvolved operator's pubkey. `update_finalized_payouts` blindly trusts whatever OP_RETURN ends up confirmed on-chain to attribute the payout.

### Finding Description
The claimed binding is: `operator_credited_and_reimbursed_for_withdrawal_index == party_whose_funds_actually_paid_the_withdrawal_output`.

- `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds the payout transaction with input 0 = the user's dust withdrawal UTXO spent via `SpendPath::KeySpend`, output 0 = user payout, output 1 = anchor, output 2 = `op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()))`. The signature over input 0 is `taproot::Signature` whose sighash type is expected/enforced to be `TapSighashType::SinglePlusAnyoneCanPay` (see `core/src/rpc/parser/operator.rs:161-187` and the `proto` doc comment in `core/src/rpc/clementine.proto:239-253`).
- Per BIP-341, `SIGHASH_SINGLE | ANYONECANPAY` commits only to: the specific signed input's prevout data (via ANYONECANPAY) and the output whose index matches the input (output 0, via SINGLE). It commits to nothing about output 1 (anchor) or output 2 (OP_RETURN operator attribution), nor to the total number of outputs.
- `Operator::withdraw` (core/src/operator.rs:560-637) verifies the schnorr signature only against `sighash = payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` — this check is fully satisfied by any transaction that preserves input 0 and output 0 exactly, regardless of outputs 1/2.
- `Verifier::update_finalized_payouts` (core/src/verifier.rs:2283-2352) reads whichever payout transaction actually confirms on-chain, parses its OP_RETURN, and stores `operator_xonly_pk` as `payout_payer_operator_xonly_pk` in the `withdrawals` table with zero cross-check against who actually funded the transaction.
- `PayoutCheckerTask::run_once` (core/src/task/payout_checker.rs:39-111) polls `get_first_unhandled_payout_by_operator_xonly_pk` (core/src/database/verifier.rs:282-313) keyed purely by that stored pubkey, and if it matches operator C's own key, unconditionally calls `handle_finalized_payout` + `mark_payout_handled` for C — with no verification that C ever called `withdraw`, checked `is_profitable`, or funded anything.

Exploit flow: an unprivileged party observes/obtains the signed input 0 + output 0 for a withdrawal (available once operator A's payout tx is broadcast/visible, e.g. in the mempool, or via the aggregator relaying the same `WithdrawParamsWithSig` to multiple operators). The attacker constructs a new transaction reusing input 0's outpoint, prevout, and witness (still valid because those are exactly what was signed) and output 0 unchanged, but substitutes output 2's OP_RETURN with a real operator C's (uninvolved) x-only pubkey. The attacker funds/covers fees (and the payout amount, since input 0 is only a dust authorization UTXO and the real value must come from additional funding inputs added when constructing the transaction) using their own wallet, and gets this variant confirmed instead of/before A's transaction. `Verifier::update_finalized_payouts` then records C as the payer, `PayoutCheckerTask` for C sees an unhandled payout and processes it as legitimate, and C is reimbursed from the move-to-vault UTXO without ever having called `withdraw`, checked profitability, or spent anything. A's true kickoff, still tagged with A's own xonly pk, no longer matches the DB record and is treated as unauthorized/malicious.

None of the existing checks catch this: `SECP.verify_schnorr` only validates the SIGHASH_SINGLE|ANYONECANPAY digest, which structurally excludes the OP_RETURN output; `is_profitable` is only evaluated by whichever operator calls `withdraw`, not retroactively against the confirmed OP_RETURN; there is no DB uniqueness or wallet-linkage constraint tying `payout_payer_operator_xonly_pk` to the actual funding inputs of the confirmed transaction.

### Impact Explanation
Operator C is credited/reimbursed via the presigned reimbursement path for a payout it never funded, matching the Critical category "an operator reimbursed for a payout it never funded." Simultaneously, operator A's legitimate kickoff for the same withdrawal index no longer matches the DB attribution and gets disproved/flagged malicious, matching "a false claim proved (or a true claim made unprovable)." The attack is repeatable across any withdrawal index and any pair of real operators (attacker just needs a valid, public operator x-only pubkey to embed, which the threat model states is always public). Blast radius: any withdrawal that has not yet been mined can be attacked this way.

### Likelihood Explanation
The attacker must win a race to get their variant transaction confirmed instead of the honest one (e.g., via RBF, since `DEFAULT_SEQUENCE = ENABLE_RBF_NO_LOCKTIME` and `NON_STANDARD_V3`), and must front the withdrawal payout amount and fees from their own wallet — a real BTC cost (up to the bridge amount) with no direct pecuniary gain to the attacker, making this primarily a sabotage/griefing vector rather than a profit-seeking one for the attacker themselves. Feasibility depends only on public information (any real operator's x-only pubkey) and observing a not-yet-confirmed payout transaction, both of which are always available to an unprivileged party per the stated threat model.

### Recommendation
Bind the operator attribution into the signed message. Either (a) require the user's withdrawal signature to use a sighash type that commits to all outputs (e.g., `SIGHASH_ALL`) so the OP_RETURN cannot be altered, or (b) have `update_finalized_payouts` cross-validate that the additional funding inputs of the confirmed payout transaction actually originate from the operator whose pubkey is claimed in the OP_RETURN (e.g., check that the change/funding inputs' scriptPubkeys belong to that operator's known wallet), rejecting/ignoring attribution otherwise.
