### Title
OP_RETURN data output excluded from fee and weight accounting, producing under-priced or non-standard transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes `needed_fee`, the `TooLowFee` relay check, and the `TooLargeTransaction` weight check using a template transaction built from `tx_ins.len()` and `payments` only. The OP_RETURN data output — which is pushed onto `tx_outs` before the weight calculation — is never included in `calculate_weight_vbytes`. The resulting transaction can be up to ~90 vbytes larger than accounted for, so the actual fee rate is lower than the requested `fee_per_vbyte` and can fall below `DEFAULT_MIN_RELAY_TX_FEE`, or the transaction can exceed `MAX_STANDARD_TX_WEIGHT` without `TooLargeTransaction` being raised.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-204`, the OP_RETURN output is appended to `tx_outs`, but `calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204 only measures a transaction containing `payments` — not `tx_outs`. The same omission occurs for the change path at line 226, where `payments` (again, without the data output) is used.

Concretely:
- `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed on a transaction missing the OP_RETURN output (~11 bytes overhead plus the pushed data, up to 80 bytes).
- The `TooLowFee` check at line 211 divides by the under-estimated `vbytes`, so a transaction whose *actual* fee rate is below the relay minimum is accepted.
- The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses `weight` that excludes the data output, so an oversized (non-standard, unrelayable) transaction can be constructed.
- With change, `fee_with_change` (line 227) is also under-estimated, and the change-omission decision at line 228-229 can keep a change output while paying a fee rate below the intended one.

The `data` payload is supplied to `SignableTransaction::new` by the caller (in Serai, the processor embeds `Shorthand`/InInstruction data derived from external users' deposits and OutInstructions), so an unprivileged user influencing the data length causes the multisig to produce transactions below the intended fee rate.

### Impact Explanation
Funds are not directly stolen, but the multisig can sign and emit transactions that the Bitcoin network will not relay (effective fee rate below `DEFAULT_MIN_RELAY_TX_FEE`, or weight above `MAX_STANDARD_TX_WEIGHT` when the omitted ~10–91 bytes pushes it over). Outputs remain locked until a corrected transaction is re-signed, and the fee actually paid is `sum(inputs) - sum(outputs)` at whatever effective rate results — an incorrect verifier/fee formula reachable purely through transaction data supplied by an external party. This is a business-logic flaw in transaction construction analogous to the reported class.

### Likelihood Explanation
Any caller that attaches `data` (up to the 80-byte cap checked at line 171) triggers the miscalculation deterministically — no race or attacker collusion required. Whether the resulting tx is rejected depends on how tight `fee_per_vbyte` and input sizes are, but the accounting error is unconditional whenever `data.is_some()`.

### Recommendation
Pass the fully-built `tx_outs` (or the `data` payload) into `calculate_weight_vbytes` so the fee, `TooLowFee`, and `MAX_STANDARD_TX_WEIGHT` checks all account for the OP_RETURN output:

- In `calculate_weight_vbytes`, take the assembled `Vec<TxOut>` (payments + data output + optional change) rather than reconstructing only payments.
- Alternatively, add the OP_RETURN output to the template before computing `weight`/`vbytes` at both call sites (lines 204 and 226).

### Proof of Concept
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150`):

```rust
// Line 194: data output pushed into the real tx_outs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),  // up to ~91 serialized bytes
  })
}

// Line 204: fee/size template excludes the data output
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;      // under-estimated
```

With `data` of 80 bytes and `fee_per_vbyte` set exactly to the minimum relay rate, `needed_fee` passes the `TooLowFee` check against ~X vbytes while the broadcast transaction is ~X+91 vbytes, yielding an actual fee rate below the relay minimum — a signed transaction no node will accept.
