### Title
OP_RETURN output omitted from fee calculation causes underpaid fees and potential transaction rejection - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the `claimVestEarlyWithPenalty` bug — where a deduction was computed against a stale/incorrect base amount rather than the actual amount being settled — `SignableTransaction::new` computes `needed_fee` against a transaction shape that omits the `OP_RETURN` output which is actually included in the final transaction. The weight/vbytes used for the fee formula do not match the transaction that is built and signed, producing an understated fee whenever `data` is specified.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is pushed onto `tx_outs` before the weight calculation, but `calculate_weight_vbytes` is invoked with `payments` — the list of payment outputs only — so the serialized `OP_RETURN` output (up to 80 bytes of data plus overhead) is never included in the measured weight.

```rust
// send.rs ~L194-204
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

The same omission occurs in the change path at ~L225-226, where `fee_with_change` is computed from `payments` and the change script, again excluding the `OP_RETURN` output that will actually be present. The constructed `Transaction` returned in `SignableTransaction` contains `tx_outs` including the `OP_RETURN`, so its real vsize is larger than the vsize the fee was priced on. Since actual fee = `sum(inputs) - sum(outputs)`, the transaction pays exactly `needed_fee` (or `fee_with_change`) — a fee computed for a smaller transaction than the one broadcast.

This is reachable by an unprivileged party via transaction data they cause to be signed: the `data: Option<Vec<u8>>` parameter is caller-supplied and becomes consensus-visible transaction bytes (the same input class as "transaction data they cause to be signed").

### Impact Explanation
- The realized fee rate (`fee / actual_vsize`) is lower than the `fee_per_vbyte` requested — with a maximal 80-byte OP_RETURN, roughly 83 weight units (~21 vbytes) go unpriced.
- More critically, the minimum-relay check at ~L211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the *underestimated* `vbytes`. A transaction priced exactly at the relay minimum will actually fall below it once the OP_RETURN output is included, making the transaction non-standard/unrelayable — the signed transaction cannot be broadcast, stalling the funds until reconstructed. This is an incorrect-formula bug: `needed_fee()` does not return the fee actually needed for the produced transaction.

### Likelihood Explanation
Any caller passing non-`None` `data` triggers the discrepancy deterministically; it requires no attacker manipulation beyond supplying the data field. The severity is bounded (fee underrun, not direct theft), placing it at Medium.

### Recommendation
Compute weight against the actual output set. Either pass `tx_outs`-equivalent data (payments + OP_RETURN) into `calculate_weight_vbytes`, or build the candidate `Transaction` (including the OP_RETURN output) first and measure its weight directly, for both the no-change and with-change fee paths.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, None, Some(vec![0u8; 80]), fee_per_vbyte)` and compare `tx.needed_fee()` to `fee_per_vbyte * tx.transaction().vsize()`. The latter exceeds `needed_fee` because `calculate_weight_vbytes` measured only `payments` while `transaction().output` additionally contains the OP_RETURN output pushed at ~L195. Setting `fee_per_vbyte` to the minimum relay rate produces a transaction whose effective feerate is below `DEFAULT_MIN_RELAY_TX_FEE`.
