### Title
mWomSV reward forfeiture is dead code, causing early/partially-unlocked stakers to steal yield that should accrue to fully-locked stakers - (File: `rewards/mWOMSVBaseRewarder.sol`)

### Summary
The reported bug class is a broken/non-smooth formula that lets a user get an unintended result relative to what the formula was designed to produce. The direct analog in this codebase is in `mWOMSVBaseRewarder.sol`'s `_calExpireForfeit`, which is supposed to mirror `vlMGPBaseRewarder.sol`'s forfeit logic (which correctly consults the locker's `getRewardablePercentWAD`) but instead is dead code that always returns a forfeit of `0`, regardless of how much of a user's `mWomSV` balance is unlocked/in cooldown.

### Finding Description
In `vlMGPBaseRewarder.sol`, `_calExpireForfeit` correctly computes the forfeitable portion of a reward by querying the locker contract: [1](#0-0) 

The `getRewardablePercentWAD` function in `VLMGP.sol` intentionally reduces the rewardable percentage for the portion of a user's balance that is in cooldown/unlocking, so that a user who has started unlocking (i.e., partially "exiting" the vote-lock) forfeits part of newly accrued rewards, which are redistributed to remaining lockers via `_queueNewRewardsWithoutTransfer`: [2](#0-1) [3](#0-2) 

The `mWomSV` locker (`wombat/mWomSV.sol`) implements the identical `getRewardablePercentWAD` function, meant to serve the same purpose for `mWomSV` holders: [4](#0-3) 

However, `mWOMSVBaseRewarder.sol`'s `_calExpireForfeit` never calls `mWOMSV.getRewardablePercentWAD(_account)`. Instead it sets `rewardableAmount = _amount` unconditionally before the check, making `forfeitAmount = _amount - rewardableAmount` always equal `0`: [5](#0-4) 

This function is invoked on every `getReward`/`getRewards` call via `_sendReward`, which is the ordinary user-facing reward-claim path reachable from `MasterMagpie._claimBaseRewarder` for any wallet holding `mWomSV`: [6](#0-5) 

### Impact Explanation
Because forfeiture is dead code for `mWomSV`, a user who has started (or fully completed) `startUnlock`/is sitting in a cooldown slot — i.e., no longer fully "locked" and by design should only be rewardable at a reduced percentage — instead receives 100% of newly accrued reward tokens on every claim. The forfeited share was designed to be redistributed to the remaining, fully-locked `mWomSV` holders (`_queueNewRewardsWithoutTransfer`); since it is never charged, that redistribution never happens and the loyal, still-locked stakers permanently lose the yield they were entitled to. This is a direct, protocol-wide theft/permanent loss of unclaimed yield transferred from long-term lockers to users who are already unlocking, triggerable by any ordinary wallet with no special privileges.

### Likelihood Explanation
Likelihood is high: any regular `mWomSV` holder who calls `startUnlock` (even partially) and then claims rewards through the normal `getReward`/`getRewards`/`multiclaim*` flow on `MasterMagpie` will trigger this path every time, with no special conditions, timing, or privileged role required.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`, i.e., compute `rewardableAmount` using `mWOMSV.getRewardablePercentWAD(_account)` instead of hardcoding `rewardableAmount = _amount`.

### Proof of Concept
1. User locks `mWOM` into `mWomSV` and accrues `mWomSV` balance in `MasterMagpie`.
2. User calls `mWomSV.startUnlock(amount)` to move part of their balance into cooldown, which per `getRewardablePercentWAD` should reduce their rewardable percentage below 100%.
3. New rewards are queued into `mWOMSVBaseRewarder` via `queueNewRewards`/`donateRewards`.
4. User calls `getReward`/`getRewards` (through `MasterMagpie`), which calls `_sendReward` → `_calExpireForfeit(_account, userRewards[...])`.
5. Because `rewardableAmount` is hardcoded to `_amount`, `forfeitAmount` is always `0`, and the user receives 100% of the reward instead of the reduced, `getRewardablePercentWAD`-based amount — no forfeited amount is ever queued back for remaining lockers via `_queueNewRewardsWithoutTransfer`.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
