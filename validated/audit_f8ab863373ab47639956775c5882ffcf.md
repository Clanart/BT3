## Analog Found

### Title
Cross-Domain Signature Reuse via Unsafe `sign_message` Modes Allows Spend-Authorization Forgery - ([File: chia/wallet/util/signing.py])

### Summary
The jwt-simple bug class is "verifier trusts an attacker-influenceable parameter to pick the verification/decoding scheme, collapsing domain separation between two supposedly-distinct signature contexts." Chia's wallet message-signing RPCs (`sign_message_by_address`, `sign_message_by_id`) exhibit the same class of bug: the caller-controlled `signing_mode` (derived from `is_hex`/`safe_mode` flags) selects whether the wallet signs the raw attacker-supplied bytes with no domain prefix, using the exact same synthetic secret key that is used to satisfy `AGG_SIG_*` spend conditions.

### Finding Description
`SigningMode` defines two "unsafe" modes that sign raw bytes with no domain separation: `BLS_MESSAGE_AUGMENTATION_UTF8_INPUT` and `BLS_MESSAGE_AUGMENTATION_HEX_INPUT` [1](#0-0) , versus the "safe" `CHIP_0002` modes that hash `("Chia Signed Message", message)` before signing [2](#0-1) .

`signing_mode_enum()` picks the mode purely from the caller-supplied `is_hex`/`safe_mode` flags on the RPC request, and two of the four flag combinations route to the unsafe, unprefixed modes [3](#0-2) .

`sign_message()` then signs the caller-controlled bytes directly with no domain separation for those unsafe modes: `hex_message = bytes.fromhex(message)` or `bytes(message, "utf-8")`, followed directly by `AugSchemeMPL.sign(secret_key, hex_message)` [4](#0-3) .

Critically, the key used is not a message-signing-only key — `wallet_rpc_api.py` derives it via `convert_secret_key_to_synthetic`, the same synthetic secret key used to produce `AGG_SIG_ME`/`AGG_SIG_PARENT`/etc. signatures that authorize coin spends [5](#0-4) .

The message format required to satisfy an `AGG_SIG_ME` condition is fully public/derivable: `msg + coin.name() + AGG_SIG_ME_ADDITIONAL_DATA` (and analogous formats for the other `AGG_SIG_*` opcodes with public per-opcode suffixes) [6](#0-5) . Because `coin.name()` and `AGG_SIG_ME_ADDITIONAL_DATA` are public, and the "unsafe" signing modes sign the literal bytes given with zero extra framing, a caller who invokes `sign_message_by_address`/`sign_message_by_id` with `is_hex=True` (or `False`) and `safe_mode=False`, supplying `message = <arbitrary_prefix> + coin_id + AGG_SIG_ME_ADDITIONAL_DATA`, obtains back a `G2Element` signature that is simultaneously a valid "signed message" **and** a valid signature satisfying an `AGG_SIG_ME` (or other `AGG_SIG_*`) condition for that specific coin, under the same public key the wallet already controls that coin with.

### Impact Explanation
An RPC caller who can reach the wallet's `sign_message_by_address`/`sign_message_by_id` endpoints (e.g. a local application/dApp with wallet RPC access, or a UI flow that lets a website request a "message signature" for login/verification) can obtain a genuine spend-authorization signature disguised as an innocuous message-signing request, without the user ever seeing or approving a transaction. That signature, combined with a crafted `CoinSpend`/puzzle solution containing the matching `AGG_SIG_ME` (or other `AGG_SIG_*`) condition and the attacker-chosen `msg` prefix, can be submitted as a valid `SpendBundle` to move the victim's coin — i.e., unauthorized coin movement using a signature the wallet believed it was producing for a different, non-spending purpose. This is the direct analog of the jwt-simple bug: the "verifier" (mempool/consensus, which checks `AGG_SIG_ME` signatures) accepts a signature that was produced under a different intended context because domain separation was optional/caller-selectable rather than enforced.

### Likelihood Explanation
Exploitation requires: (1) RPC/CLI access to the wallet's sign-message endpoints, (2) knowledge of the target coin's id and the network's public `AGG_SIG_ME_ADDITIONAL_DATA` constant (both public), and (3) the caller supplying `safe_mode=False` explicitly — the "safe," domain-separated `CHIP_0002` behavior is the CLI default (`SignMessageCMD`), so exploitation depends on an integrator/dApp/RPC client choosing the unsafe flag combination, which the API exposes without warning callers that it collapses into spend-authorization territory. This lowers likelihood somewhat compared to a fully implicit default, but the vulnerable code paths are live, reachable via RPC (`sign_message_by_address`, `sign_message_by_id`), and require no privileged/network-layer access.

### Recommendation
- Remove or gate the unprefixed `BLS_MESSAGE_AUGMENTATION_UTF8_INPUT` / `BLS_MESSAGE_AUGMENTATION_HEX_INPUT` modes behind an explicit, loudly-labeled "raw signing — do not use for arbitrary third-party messages" warning, or eliminate them entirely in favor of always-domain-separated CHIP-0002 signing.
- Alternatively, before signing in the unsafe modes, reject any message whose bytes end with (or contain) any of the values from `agg_sig_additional_data()` concatenated forms, mirroring the `AGG_SIG_UNSAFE` disallowed-suffix check already done in `pkm_pairs_for_conditions_dict` [7](#0-6) , so a "sign message" call can never produce a signature that also validates as an `AGG_SIG_*` condition.
- Require explicit user/UI confirmation display of the exact raw bytes being signed whenever an unsafe signing mode is used via RPC.

### Proof of Concept
1. Query the target coin id (`coin.name()`) and the network's `AGG_SIG_ME_ADDITIONAL_DATA` constant (both public).
2. Call `sign_message_by_address` (or `sign_message_by_id`) with `is_hex=True, safe_mode=False` and `message = hex(msg_prefix + coin_id + AGG_SIG_ME_ADDITIONAL_DATA)`, per `signing_mode_enum` routing to `BLS_MESSAGE_AUGMENTATION_HEX_INPUT` [3](#0-2) .
3. The wallet signs the raw bytes with the coin's synthetic secret key [8](#0-7) , returning `signature`.
4. Construct a `CoinSpend` for that coin whose puzzle emits `(AGG_SIG_ME pubkey msg_prefix)`; per `make_aggsig_final_message`, the condition's required signed message equals exactly `msg_prefix + coin.name() + AGG_SIG_ME_ADDITIONAL_DATA` [6](#0-5)  — identical to what was signed in step 3.
5. Submit `SpendBundle([coin_spend], signature)` to the mempool; it passes signature validation and spends the coin, despite the owner only having approved what they believed was an unrelated message-signing request.

def signing_mode_enum(request: SignMessageByAddress | SignMessageByID) -> SigningMode:
    if request.is_hex and request.safe_mode:
        return SigningMode.CHIP_0002_HEX_INPUT
    elif not request.is_hex and not request.safe_mode:
        return SigningMode.BLS_MESSAGE_AUGMENTATION_UTF8_INPUT
    elif request.is_hex and not request.safe_mode:
        return SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT

    return SigningMode.CHIP_0002

def sign_message(secret_key: PrivateKey, message: str, mode: SigningMode) -> SignMessageResponse:
    public_key = secret_key.get_g1()
    if mode == SigningMode.CHIP_0002_HEX_INPUT:
        hex_message: bytes = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, bytes.fromhex(message))).get_tree_hash()
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_UTF8_INPUT:
        hex_message = bytes(message, "utf-8")
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT:
        hex_message = bytes.fromhex(message)
    else:
        hex_message = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, message)).get_tree_hash()
    return SignMessageResponse(
        pubkey=public_key,
        signature=AugSchemeMPL.sign(secret_key, hex_message),
    )
```

def make_aggsig_final_message(
    opcode: ConditionOpcode,
    msg: bytes,
    spend_conditions: Coin | SpendConditions,
    agg_sig_additional_data: dict[ConditionOpcode, bytes],
) -> bytes:
    if isinstance(spend_conditions, Coin):
        coin = spend_conditions
    elif isinstance(spend_conditions, SpendConditions):
        coin = Coin(spend_conditions.parent_id, spend_conditions.puzzle_hash, uint64(spend_conditions.coin_amount))
    else:
        raise ValueError(f"Expected Coin or Spend, got {type(spend_conditions)}")  # pragma: no cover

    COIN_TO_ADDENDUM_F_LOOKUP: dict[ConditionOpcode, Callable[[Coin], bytes]] = {
        ConditionOpcode.AGG_SIG_PARENT: lambda coin: coin.parent_coin_info,
        ConditionOpcode.AGG_SIG_PUZZLE: lambda coin: coin.puzzle_hash,
        ConditionOpcode.AGG_SIG_AMOUNT: lambda coin: int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT: lambda coin: coin.puzzle_hash + int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PARENT_AMOUNT: lambda coin: coin.parent_coin_info + int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PARENT_PUZZLE: lambda coin: coin.parent_coin_info + coin.puzzle_hash,
        ConditionOpcode.AGG_SIG_ME: lambda coin: coin.name(),
    }
    addendum = COIN_TO_ADDENDUM_F_LOOKUP[opcode](coin)
    return msg + addendum + agg_sig_additional_data[opcode]
```
