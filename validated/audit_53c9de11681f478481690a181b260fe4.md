### Title
Unvalidated `Participant` in PedPoP blame path panics via HashMap indexing on attacker-chosen `sender`/`recipient` (denial of service) - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `Participant` values that are never bounds-checked against the DKG's participant set. `Participant` is only a non-zero `u16`, so any accusation naming a recipient/sender outside `1..=n` (or, for a participant's own `BlameMachine`, naming itself as `recipient`) causes a HashMap-index panic — the Rust analog of CVE-2021-1095's "dereference of an untrusted pointer from a control call" leading to denial of service.

### Finding Description
The blame protocol exists precisely to adjudicate accusations between mutually distrusting parties, so `sender`, `recipient`, `msg`, and `proof` are all attacker-influenced inputs to `BlameMachine::blame` / `AdditionalBlameMachine::blame`:

- `AdditionalBlameMachine::new` registers `enc_keys`/`commitments` only for `1 ..= n` (`crypto/dkg/pedpop/src/lib.rs:656-659`). `blame` then forwards the caller-supplied `sender`/`recipient` straight to `blame_internal` with no `<= n` check (`lib.rs:674-682`).
- `blame_internal` calls `decrypt_with_proof`, which performs `self.enc_keys[&decryptor]` when a proof is supplied (`encryption.rs:388`). HashMap `Index` panics on a missing key.
- If the proof path is avoided, `blame_internal` later evaluates `self.commitments[&sender]` (`lib.rs:599`), which also panics for an out-of-range sender.
- Even the honest-participant `BlameMachine` (returned by `calculate_share`) never registers its own index `i` in `enc_keys` — `verify_r1` skips `self.params.i()` since the map excludes our own entry (`lib.rs:313-315`). So `blame(sender, recipient = i, msg, Some(proof))` panics on `enc_keys[&i]`.

The attacker can satisfy the gating PoP check trivially: `msg.pop` is a Schnorr signature over `pop_challenge(context, R, msg.key, from, msg)` where `msg.key = k*G` for a key `k` the attacker chooses, so they can produce a valid `pop` themselves and reach the panicking index.

### Impact Explanation
Any node running PedPoP blame arbitration — notably `AdditionalBlameMachine`, which is explicitly constructed "regardless of if the caller was a member in the DKG" to evaluate third-party accusations (`lib.rs:639-648`) — crashes on a single crafted blame statement naming `recipient` or `sender` as a `Participant` value greater than `n`. This aborts blame adjudication and can crash the host process, a remote denial of service triggered entirely by unauthenticated public inputs (an accusation tuple plus a self-signed `EncryptedMessage`/`EncryptionKeyProof`).

### Likelihood Explanation
Blame accusations are exchanged exactly when parties are already suspected malicious, i.e., adversarial input to this path is the designed use case. The exploit needs only: a `Participant` ID outside `1..=n` (a one-line `u16`), any registered sender's `EncryptedMessage` bytes or a freshly forged one (the attacker controls `key` and signs `pop` with it), and an `EncryptionKeyProof` value — deserialization via `EncryptedMessage::read`/`EncryptionKeyProof::read` imposes no validity constraints that would prevent reaching the index. Confidence in reachability via `AdditionalBlameMachine::blame` is high; the panic site itself is certain (`HashMap`'s `Index` impl panics on absent keys).

### Recommendation
Validate `sender` and `recipient` at the top of `blame_internal` (and in `AdditionalBlameMachine::blame`) — e.g., reject any `Participant` not in `params.all_participant_indexes()` / not present in `self.commitments` and `self.enc_keys` — and replace `map[&key]` indexing with `map.get(&key)` returning a `PedPoPError` (or a defined `Participant` blame result) instead of panicking. Also document/handle the `recipient == i` case for `BlameMachine`, whose own encryption key is never registered.

### Proof of Concept
```rust
// Setup: n = 3 DKG completed; arbiter built from the three public commitment msgs.
let mut arbiter = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// Attacker crafts an EncryptedMessage with a key/PoP they control:
let k = <Ristretto as Ciphersuite>::random_nonzero_F(&mut rng);
let key = <Ristretto as Ciphersuite>::generator() * k;
let msg_bytes = SecretShare::<<Ristretto as Ciphersuite>::F>(k.to_repr()); // any E::read-valid bytes
let pop = SchnorrSignature::sign(&k, nonce, pop_challenge(ctx, pub_nonce, key, from, msg_bytes.as_ref()));
let msg = EncryptedMessage { key, pop, msg: Zeroizing::new(msg_bytes) }; // via EncryptedMessage::read on crafted bytes

// Accusation names a non-existent recipient (4 > n = 3); proof value can be any deserialized bytes.
let sender = Participant::new(1).unwrap();
let fake_recipient = Participant::new(4).unwrap();

// Reaches decrypt_with_proof -> self.enc_keys[&Participant(4)] -> panic (index out of map)
arbiter.blame(sender, fake_recipient, msg, Some(proof));
```
