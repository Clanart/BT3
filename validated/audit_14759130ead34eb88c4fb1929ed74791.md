### Title
Stale-snapshot file lookup lets `applyCopilotConflictResolutions` silently overwrite user-resolved/deleted conflict files with cached Copilot content - (File: app/src/lib/stores/app-store.ts)

### Summary
`_applyCopilotConflictResolutions` (invoked as `applyCopilotConflictResolutions` via the `Dispatcher`) writes AI-generated conflict resolutions to disk after a merge/rebase/cherry-pick with Copilot-assisted conflict resolution. Before writing, it looks up each file by path in a `state.changesState.workingDirectory.files` array captured once at the start of the function, using an `Array.prototype.find`-style lookup. If that lookup fails to find the path in a state consistent with the file's *current* on-disk status, the code falls through to writing the stored, potentially attacker-influenced `resolvedContent` — the same "find() returns nothing/wrong-shape entry but the guard doesn't detect that and proceeds as if valid" pattern described in the Solana `finalize_locked_stake` report.

### Finding Description [1](#0-0) 

The function captures a single snapshot of working-directory state at the top: [2](#0-1) 

For each Copilot-produced resolution it re-derives the on-disk file by `path` from that snapshot and only skips (i.e., defers to the user) when the file is *still present* and *still reported as conflicted with no remaining conflict markers*: [3](#0-2) 

```
const onDiskFile = state.changesState.workingDirectory.files.find(
  f => f.path === resolution.path
)
if (
  onDiskFile !== undefined &&
  isConflictedFileStatus(onDiskFile.status) &&
  !hasUnresolvedConflicts(onDiskFile.status)
) {
  continue
}

await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
```

This mirrors the "empty slot passes preliminary checks" flaw: the guard is only designed to detect the *positive* case (file found, conflicted, markers cleared ⇒ user resolved it externally). It never validates the *negative* case — `onDiskFile === undefined`, meaning the entry can no longer be located by path in the stale snapshot (because the user deleted, renamed, or otherwise changed the file, or because it was captured before an intervening refresh). In the original report, an unfilled/uninitialized slot in `locked_stakes` was retrieved by `find()` and, because the code checked only preconditions that happen to be trivially true for an empty slot, was finalized as if it were a valid, resolved entry. Here, a path that can't be matched in `state`'s stale file list is likewise treated as if the "safe to write" precondition holds, and Desktop silently (re)writes the Copilot-cached content to `absolutePath` and stages it for commit — even though the file may have been intentionally deleted or already handled differently by the user.

`getSkippedFileChoice`/`isSkippedFileResolved` in the conflicts dialog use the same pattern to decide when the "Continue" button is enabled, further encouraging the user to believe the operation is safe to finish once files disappear from the conflicted list: [4](#0-3) 

Note the `resolveWithin` path-traversal guard exists, but it only prevents writing outside the repo — it does nothing to validate that the path still legitimately represents a conflicted file the user expects to be resolved this way: [5](#0-4) 

### Impact Explanation
An attacker who controls (or contributes conflicting content to) a fetched branch/fork can craft a merge/rebase/cherry-pick conflict such that Copilot's resolution for a given path embeds attacker-favorable content (e.g., subtly altered logic, backdoored dependency pin, etc.). If the user attempts to override that outcome — by deleting the file, renaming it, or otherwise causing it to no longer match by path in the state snapshot used at write time — the stale, cached `resolution.resolvedContent` is written back to disk and staged anyway. This is silent corruption of what the user commits and subsequently pushes: the user's actual, intended resolution is discarded in favor of content they believed they had removed or replaced.

### Likelihood Explanation
This requires: (1) the victim to be using the Copilot-assisted conflict resolution flow (an opt-in AI feature) on a merge/rebase/cherry-pick that has conflicts against attacker-influenced content, and (2) the user to change the on-disk state of a conflicted path (delete/rename/otherwise diverge from the state snapshot) between the time the multi-commit operation state was captured and the time "Continue" is invoked. This is a plausible but non-trivial timing/usage window — no privilege escalation, malware, or leaked credentials are needed, only normal usage of a shipped feature against a malicious/compromised remote.

### Recommendation
Re-fetch current on-disk/working-directory status (or at minimum re-stat/re-read the target file) immediately before writing each Copilot resolution, rather than relying on a `find()` against a state snapshot captured before the loop. Treat `onDiskFile === undefined` (file no longer present in current state) as a reason to *skip* the write and surface a warning, not as a "found nothing, so it's safe to proceed" default — closing the same class of gap as the original report, where an unmatched/unfound record was implicitly presumed valid.

### Proof of Concept
1. Attacker publishes a branch with a file that will produce a merge conflict when the victim merges it, engineered so Copilot's suggested resolution embeds attacker-controlled content.
2. Victim runs the merge in Desktop with Copilot conflict resolution enabled; Copilot computes and caches `resolvedContent` for the path.
3. Before clicking "Continue", the victim deletes or renames that file in their working directory (e.g., because they decided to resolve it differently or drop the file entirely) and the changes-state snapshot held by `_applyCopilotConflictResolutions`'s `state` variable no longer reflects the file at its original path.
4. Victim clicks "Continue" → `applyCopilotConflictResolutions` iterates `copilotResolutions`, fails to find `onDiskFile` for that `resolution.path` in the stale `state.changesState.workingDirectory.files`, and executes `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` then stages it — resurrecting/overwriting the file with attacker-influenced content the user believed they had removed, which is then committed and can be pushed.

Note: I was not able to fully trace whether `state` is refreshed by an intervening `emitUpdate`/`repositoryStateCache` call between snapshot capture and `onContinue` dispatch (this would need runtime tracing or a Devin session with full repo access to confirm the exact timing window and whether any additional refresh call closes the gap in practice).
