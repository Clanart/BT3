## Title
Fee surplus left stranded in per-tx ephemeral coinbase account when a reverted tx's nonce wasn't bumped - ([File: x/evm/keeper/abci.go])

### Summary
The SafEth report describes residual ETH sitting in a contract balance that is only swept opportunistically via a `before/after` balance delta, so any funds that land outside that delta window are never harvested and become effectively stuck/unaccounted. Sei's EVM `EndBlock` sweep of per-transaction fee surplus into the block's fee collector has the same "conditional sweep, no fallback" shape: for a subset of failed transactions, the code explicitly skips the sweep of the ephemeral per-tx coinbase account's balance, leaving usei/wei that was already credited there un-swept and un-reachable through the normal path.

### Finding Description
`BuyGas`/fee-charging for an EVM transaction credits the transaction's fee surplus into a deterministic, per-tx-index "coinbase" account, `state.GetCoinbaseAddress(idx)`, which is just `evm_coinbase || big-endian(txIdx)` [1](#0-0) . This happens even when the ante pipeline later fails, because `EVMFeeCheckDecorator.AnteHandle` calls `st.BuyGas()` and finalizes/records the ante surplus before the rest of ante processing runs [2](#0-1) .

At `EndBlock`, for every deferred tx info, the keeper is supposed to sweep the per-tx coinbase account's `usei`/`wei` balance to the real coinbase (fee collector or validator) address:
```go
idx := int(deferredInfo.TxIndex)
coinbaseAddress := state.GetCoinbaseAddress(idx)
useiBalance := k.BankKeeper().GetBalance(ctx, coinbaseAddress, denom).Amount
...
if !balance.IsZero() || !weiBalance.IsZero() {
    if err := k.BankKeeper().SendCoinsAndWei(ctx, coinbaseAddress, coinbase, balance, weiBalance); err != nil {
``` [3](#0-2) 

However, this sweep is reached only through an `if/continue` branch that explicitly skips it for a class of failed transactions:
```go
if deferredInfo.Error != "" && txHash.Cmp(ethtypes.EmptyTxsHash) != 0 {
    if !k.GetNonceBumped(ctx, deferredInfo.TxIndex) {
        continue
    }
    _ = k.SetTransientReceipt(ctx, txHash, &types.Receipt{...})
    continue
}
``` [4](#0-3) 

If a tx fails after `BuyGas`/fee-crediting into `coinbaseAddress(idx)` but before nonce bump is recorded (`k.SetNonceBumped`, which is itself set only on a `DeliverTxCallback` guarded by nonce-equality checks in `x/evm/ante/basic.go`) [5](#0-4) , the `!k.GetNonceBumped(...)` branch fires and the loop `continue`s without ever calling `SendCoinsAndWei` for that tx's coinbase address. Unlike SafEth's `rebalanceToWeights()`, there is no subsequent fallback that later sweeps "the entire balance" of the ephemeral coinbase accounts — the sweep only happens per-iteration, keyed to a delta-free but branch-gated code path, exactly analogous to the SafEth `ethAmountBefore/After` delta gating that leaves any funds outside the expected code path unharvested.

Because `state.GetCoinbaseAddress(idx)` is a pure function of `txIdx` with no block-height component [6](#0-5) , the address is reused every block at the same index. Any balance stranded there in block N is not "gone" (no permanent freezing) but is un-swept for block N, and — depending on later scheduling — may sit unaccounted until some future block happens to have index `idx` succeed (nonce bumped) and pulls in the stale prior balance along with the new tx's own surplus, misattributing an older fee credit to a later block's coinbase/fee collector rather than the block it was actually generated in. This is precisely the "residual funds unreachable/unutilized until an unrelated future event sweeps them" pattern described in the SafEth report.

### Impact Explanation
This does not cause permanent freezing (the funds are recoverable by BankKeeper reads and can be swept in a later block that reuses the same index), and it flows to the legitimate fee-collector/coinbase, not to an attacker-controlled address, so it is not classic fund theft. The impact is limited to temporary misaccounting/mis-timing of fee-surplus distribution between blocks: usei/wei belonging to block N's transactions is not credited to block N's fee collector/coinbase, and instead may later land in a completely different block's fee collector once txIdx `idx` is reused and completes with a bumped nonce. This can create small but real discrepancies between per-block fee revenue and the transactions that generated it (auditability/consensus-relevant accounting mismatch), and in edge cases (e.g., if a given `idx` is never reused with a bumped nonce for a long time) funds can remain un-swept and effectively idle in `evm_coinbase`-prefixed accounts for an extended period.

### Likelihood Explanation
The gating condition (`deferredInfo.Error != "" && txHash != EmptyTxsHash && !GetNonceBumped`) requires a tx to fail somewhere in the ante/execution pipeline after `BuyGas` already credited surplus to the per-tx coinbase account, but before the nonce-bump `DeliverTxCallback` fires (which itself only registers when `startingNonce == txNonce` at `x/evm/ante/basic.go` line 32) [5](#0-4) . Any transaction sender can trigger this deterministically and repeatedly by submitting an EVM tx that passes `EVMFeeCheckDecorator` (so gas is bought and surplus finalized) but reverts/fails afterward under conditions where the nonce-bump callback does not fire (e.g., failures unrelated to nonce mismatch, or when the callback's nonce/height not registering as expected) — this is reachable purely from an ordinary transaction sender with no special privileges.

### Recommendation
Remove the unconditional `continue` before nonce-bump check, or move the coinbase-sweep logic (`state.GetCoinbaseAddress(idx)` lookup and `SendCoinsAndWei`) so it always executes for every `deferredInfo.TxIndex`, regardless of whether the transient receipt is written for that iteration. Concretely, restructure `x/evm/keeper/abci.go`'s `EndBlock` loop so that the sweep step (currently only reached in the "else" path) runs unconditionally per `deferredInfo`, and the receipt-writing / nonce-bump branch is handled as an independent side effect rather than an early `continue` that bypasses the sweep.

### Proof of Concept
1. Submit an EVM `DynamicFeeTx` with a valid fee (`GasFeeCap`/`GasTipCap`) that passes `EVMFeeCheckDecorator.AnteHandle`, which calls `st.BuyGas()` and credits `state.GetCoinbaseAddress(txIdx)` with the fee surplus, then calls `stateDB.Finalize()`/`AddAnteSurplus` [2](#0-1) .
2. Craft the transaction/mempool ordering so that a subsequent ante decorator (after `EVMFeeCheckDecorator` but unrelated to the nonce-equality check in `BasicDecorator`) fails the tx, and ensure the nonce-bump `DeliverTxCallback` (registered only when `startingNonce == txNonce`) does not end up calling `SetNonceBumped` for this tx index [5](#0-4) .
3. At `EndBlock`, `deferredInfo.Error != ""`, `txHash != EmptyTxsHash`, and `GetNonceBumped(ctx, txIndex)` is `false`, so the loop `continue`s at `x/evm/keeper/abci.go` line 113 without calling `SendCoinsAndWei` for `state.GetCoinbaseAddress(txIndex)` [4](#0-3) .
4. Query `BankKeeper().GetBalance`/`GetWeiBalance` for `state.GetCoinbaseAddress(txIndex)` after the block commits — the fee surplus credited in step 1 remains there, un-swept to the block's fee collector, confirming the residual-fund handling gap analogous to the SafEth finding.
