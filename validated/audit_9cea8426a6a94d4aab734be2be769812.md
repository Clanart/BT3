### Title
`ThresholdKeys::read` accepts identity / unvalidated verification shares, letting a signer pass per-share verification with no secret-share contribution and evade blame — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The MALOU incident class is a hidden backdoor letting one party act outside the rules everyone else is bound by. The analog in Serai is in threshold-key deserialization: `ThresholdKeys::read` reads each participant's verification share with `Ciphersuite::read_G`, which accepts the identity point, while the rest of the FROST stack deliberately rejects identity points via `Curve::read_G` because identity values degenerate the verification equations. A `ThresholdKeys` blob carrying an identity verification share for a participant whose index is greater than `t` is accepted by `ThresholdKeys::new`, because `group_key` is reconstructed only from shares `1..=t` and shares beyond `t` are never consistency-checked. During `complete()`, the per-share blame equation for that participant degenerates to `s_j·G == R_j` (nonce terms only), so that participant can submit a "share" containing zero secret-share contribution, pass `verify_share`, and corrupt the aggregate signature while the blame machinery reports `InternalError` instead of identifying them.

### Finding Description
`ThresholdKeys::read` builds `verification_shares` with `<C as Ciphersuite>::read_G` (`crypto/dkg/src/lib.rs:620-623`), in contrast to `Curve::read_G`, which explicitly rejects the identity point (`crypto/frost/src/curve/mod.rs:123-131`) precisely because identity points break the security of verification equations. `ThresholdKeys::new` only enforces the count of shares and that indices are `<= n` (`crypto/dkg/src/lib.rs:355-365`); the group key is derived solely as `sum(verification_shares[i] * interpolation_factor(i, 1..=t))` for `i in 1..=t` (`crypto/dkg/src/lib.rs:376-378`), so a corrupt share for any participant `j > t` is never checked against anything. In `AlgorithmSignatureMachine::complete`, when the aggregate signature fails, each participant's share is checked via `verify_share(verification_share, bound_nonces, share)` (`crypto/frost/src/sign.rs:474-489`). `ThresholdView::view` computes `verification_shares[j] = identity * scalar * λ_j = identity` (`crypto/dkg/src/lib.rs:500-507`), so the Schnorr share equation `s_j·G == V_j + D_j + ρ_j·E_j` reduces to `s_j·G == D_j + ρ_j·E_j`, which participant `j` satisfies trivially with `s_j = d_j + ρ_j·e_j` — values `j` generated itself and knows.

### Impact Explanation
An unprivileged participant `j` (index `> t` in the corrupted key set) can halt or sabotage every signing session it joins: it contributes no key-share material to the signature, the aggregate verification in `complete` fails (`crypto/frost/src/sign.rs:465-467`), yet `j`'s share passes the per-share batch verification, so blame resolution either blames an innocent party (if others' shares happen to be queued with the degenerate statement) or falls through to `FrostError::InternalError("everyone had a valid share yet the signature was still invalid")` (`crypto/frost/src/sign.rs:491-494`), leaving the saboteur unidentified and able to repeat the attack indefinitely. This is a backdoor-style exemption from the accountability every other signer is subject to, matching the incident's bug class.

### Likelihood Explanation
Exploitation requires an adversarially serialized `ThresholdKeys` reaching `ThresholdKeys::read` — listed as in-scope untrusted input — plus that the malicious participant holds index `j > t` so its verification share never affects `group_key`. Both conditions are plausible when key material is relayed or restored from untrusted storage. Severity is Medium: the outcome is persistent, unattributable signing failure rather than key recovery or forged signatures.

### Recommendation
In `ThresholdKeys::read` (and in `ThresholdKeys::new` for defense in depth), reject identity verification shares — e.g., use an identity-checking `read_G` for shares, or add an `is_identity` check alongside the index bounds. Additionally, verify in `ThresholdKeys::new` that each participant's verification share is non-identity and, where feasible, that the shares are consistent with `group_key` before accepting the keys.

### Proof of Concept
1. Participant `j` (index `j > t`) serializes a `ThresholdKeys` for params `(t, n, i=j)` with `verification_shares[j]` set to the identity encoding and all other fields valid, and gets the processor to load it via `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`). Deserialization succeeds because `Ciphersuite::read_G` accepts identity and `ThresholdKeys::new` never inspects shares beyond `1..=t`.
2. In a signing session including `j`, `view()` yields `verification_shares[j] = identity` (`crypto/dkg/src/lib.rs:500-521`).
3. `j` broadcasts preprocess `(D_j, E_j)` and later submits `s_j = d_j + ρ_j·e_j` — no `λ_j·secret_share` term.
4. The summed signature fails `algorithm.verify` (`crypto/frost/src/sign.rs:465`); the blame path queues `verify_share` for `j`, whose statements reduce to `s_j·G - R_j = 0` and pass, so `batch.verify_vartime_with_vartime_blame` does not flag `j` (`crypto/frost/src/sign.rs:487-494`) and the session ends with `InternalError`, `j` unidentified.

Uncertainty note: whether `Ciphersuite::read_G` for each concrete ciphersuite accepts identity was inferred from the existence of the separate identity-rejecting `Curve::read_G` wrapper; if a given `Ciphersuite::read_G` already rejects identity, the reachable subset narrows but the missing validation in `ThresholdKeys::new` remains.
