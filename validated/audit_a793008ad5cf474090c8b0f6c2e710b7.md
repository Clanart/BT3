### Title
OP_RETURN data output excluded from fee and maximum-weight policy checks, allowing standardness/weight restriction bypass - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` enforces Bitcoin mempool policy (minimum fee rate via `fee_per_vbyte`/`DEFAULT_MIN_RELAY_TX_FEE`, and `MAX_STANDARD_TX_WEIGHT`) using a weight/vbytes estimate computed by `calculate_weight_vbytes` over only the payment outputs and optional change output. However, the OP_RETURN output carrying `data` is pushed into `tx_outs` *before* the estimate and is never included in `weight`/`vbytes`, so a caller-supplied data blob is completely unaccounted for in both policy checks. This is a direct analog of CVE-2021-21228's bug class: insufficient policy enforcement permits crafted input to bypass a restriction that the code claims to enforce.

### Finding Description
In `SignableTransaction::new`:

- The OP_RETURN output is appended to `tx_outs` at lines 194-202 when `data` is provided (up to 80 bytes).
- The weight/vbytes used for `needed_fee` and the minimum-relay-fee check are computed at line 204 as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — over `payments` only, omitting the already-added data output.
- When a change output exists, the estimate is recomputed at line 226 as `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` — still omitting the OP_RETURN output.
- The standardness check at line 241 (`weight > MAX_STANDARD_TX_WEIGHT`) therefore also omits the data output's ~360+ weight units.
- The resulting `SignableTransaction` (which `TransactionSignMachine::sign` commits to via `taproot_key_spend_signature_hash` with `Prevouts::All`) contains the data output, so the signed transaction's true weight and fee rate diverge from what was validated. [1](#0-0) [2](#0-1) [3](#0-2) 

### Impact Explanation
Two consequences, both reachable purely through the `data` argument (an untrusted input — in Serai's flow it carries cross-chain instruction bytes):

1. **Fee underpayment / policy bypass:** `needed_fee = fee_per_vbyte * vbytes` undercharges by the vbytes of the OP_RETURN output (~35–45 vbytes depending on data length). The transaction's effective fee rate is lower than the caller-specified `fee_per_vbyte`, and the `TooLowFee` check against `DEFAULT_MIN_RELAY_TX_FEE` passes for transactions whose *actual* feerate is below the relay minimum — producing a signed transaction that nodes will not relay or mine.
2. **Standardness check bypass:** A transaction whose real weight exceeds `MAX_STANDARD_TX_WEIGHT` (400,000 WU) passes the check whenever the overage is within the omitted OP_RETURN weight (~360 WU for 80 bytes of data). The threshold signature is then produced for a non-standard transaction that can never confirm, so the inputs remain locked until a new transaction is constructed and re-signed.

This yields concrete signing of a transaction the constructor's own policy declared invalid.

### Likelihood Explanation
Any caller passing `data` (the crate allows up to 80 bytes unconditionally) triggers the fee underpayment deterministically — it is not probabilistic. The weight-check bypass requires the base transaction to already be within ~360 WU of the standardness limit, which is a narrower but deterministic condition an input-shaping party can arrange by supplying many payments/inputs near the bound. No collusion, malicious validator, or broken BFT assumption is needed; the defect is entirely in the local construction logic.

### Recommendation
Include the data output in the weight/vbytes estimate. In `SignableTransaction::new`, build the OP_RETURN `TxOut` first (or pass its size explicitly) and call `calculate_weight_vbytes` with the full output set — e.g., extend the signature to accept the complete `tx_outs` list — so that `needed_fee`, the `TooLowFee` check, the change calculation, and the `MAX_STANDARD_TX_WEIGHT` check at line 241 all account for the data output.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte` equals the minimum relay rate (1000 sat/kvB → `DEFAULT_MIN_RELAY_TX_FEE`).
2. The check at line 211 passes because `vbytes` omits the ~44-byte OP_RETURN output.
3. The signed transaction from `TransactionSignMachine::sign`/`complete` has a real feerate below the minimum relay fee, since the actual fee `sum(inputs) - sum(outputs)` divided by the true vsize is less than what was computed.
4. Alternatively, size `inputs`/`payments` so the computed `weight` is exactly `MAX_STANDARD_TX_WEIGHT`; adding `data` produces a signed transaction whose real weight is ~400,360 WU, failing standardness on every relaying node despite passing the line 241 check.
