### Title
PedPoP accepts identity encryption/per-message keys, making ECDH collapse to a publicly known constant and exposing "encrypted" DKG secret shares to any observer - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The Budibase report is a "dangerous input" check gated behind a conditional (`if (isPublicUser)`), so authenticated lower-privilege users bypass a restriction that exists for the unprivileged path. The direct analog in Serai exists in PedPoP's encryption layer: the identity-point rejection is conditional on which `read_G` variant a caller uses. `Curve::read_G` (crypto/frost/src/curve/mod.rs:125) rejects identity points, but PedPoP is generic over `Ciphersuite` and calls `C::read_G` (crypto/ciphersuite/src/lib.rs:91), which only enforces canonical encoding and accepts the identity element. `EncryptedMessage::read` (crypto/dkg/pedpop/src/encryption.rs:171-177), `EncryptionKeyMessage` registration via `Decryption::register` (encryption.rs:351-362), and `EncryptionKeyProof::read` (encryption.rs:267-269) all accept identity points on these untrusted bytes. Since the ECDH is computed as `public * private` (encryption.rs:95-97), an identity public key forces the shared secret to the identity point, so `cipher()` (encryption.rs:101-133) derives a ChaCha20 key from a constant, publicly computable value — anyone can decrypt the message.

### Finding Description
`EncryptedMessage::read` reads `key` with `C::read_G` with no identity check. The accompanying `pop` Schnorr proof-of-possession does not prevent this: `SchnorrSignature::verify` checks `R + cA - sG == 0` (crypto/schnorr/src/lib.rs:88-99), and for `A = identity` any `s` with `R = sG` verifies — the attacker simply signs with secret scalar 0. Likewise `Decryption::register` stores `msg.enc_key` into `enc_keys` with no identity rejection, and `encrypt`/`decrypt` compute `ecdh(private, public)` unconditionally. With either an identity `enc_key` registered by a participant or an identity per-message `key`, `ecdh()` returns the identity point, `transcript.append_message(b"shared_key", ecdh.to_bytes())` commits a fixed public value, and the resulting ChaCha20 key/IV are computable by any party that knows the (public, participant-shared) `context`. A malicious DKG participant can therefore publish a `SecretShare` `EncryptedMessage` that is effectively plaintext to all observers of the authenticated channel — including the Tributary chain, where Serai's coordinator persists DKG share data for blame handling (`DkgShare::get`, processor/src/key_gen.rs:486-541) — and can register an identity `enc_key` causing all shares addressed to them to be publicly decryptable.

### Impact Explanation
The DKG's stated security property (spec/cryptography/Distributed Key Generation.md:9-17) is that secret shares are confidentially delivered to their intended recipient via ECDH+ChaCha20 over authenticated channels. An unprivileged DKG participant — reachable purely via public inputs fed to `EncryptedMessage::read`/`EncryptionKeyMessage::read` — breaks this unconditionally: every `SecretShare` sent to an attacker who registered an identity `enc_key` is decryptable by any channel observer, and any share a malicious sender chooses to transmit with `key = identity` is world-readable. This publicly exposes secret-share components (the sender's `f_j(victim)` evaluations, or all evaluations addressed to the identity-key registrant), leaking key-share material the protocol is designed to keep secret and weakening the threshold's confidentiality margin — shares that should require the recipient's private key to read become recoverable by anyone who computes `cipher(context, identity)`.

### Likelihood Explanation
Triggerable by any participant in a DKG session with a single malformed message; no collusion, timing, or implementation misuse is required. The identity encoding is canonical, passes `read_G`, and the forged PoP (`s` chosen, `R = sG`, `A = identity`) passes `pop.verify`/`batch_verify` since the discrete log of identity (0) is trivially known. The check that would catch this (`res.is_identity()` in `Curve::read_G`) exists but is only wired into the FROST signing path, mirroring the conditional-check structure of the report.

### Recommendation
Reject identity points at deserialization in the DKG crates: use an identity-rejecting reader for `EncryptedMessage::read`'s `key`, `EncryptionKeyMessage`'s `enc_key`, `EncryptionKeyProof`'s `key`, and `Commitments`' points (or add `is_identity` checks in `Decryption::register`/`Encryption::decrypt`/`decrypt_with_proof`). Aligning PedPoP with the FROST `Curve::read_G` convention removes the asymmetric validation.

### Proof of Concept
```rust
// Attacker (Participant l) registers an identity encryption key:
let enc_key_msg = EncryptionKeyMessage::<C, Commitments<C>> {
  msg: honest_commitments,
  enc_key: C::G::identity(),              // passes C::read_G canonical check
};
// Every other participant i calls encryption.encrypt(rng, l, share):
//   ecdh(key_i, identity) == identity
//   cipher(context, identity-point-bytes) -> ChaCha20 key K, IV "DKG IV v0.2\0"
// K is computable by ANY observer who knows `context`:
let mut t = RecommendedTranscript::new(b"DKG Encryption v0.2");
t.append_message(b"context", context);          // context is public among participants
t.domain_separate(b"encryption_key");
t.append_message(b"shared_key", C::G::identity().to_bytes());
let challenge = t.challenge(b"key");
// key = challenge[..32], iv = b"DKG IV v0.2\0"
// -> observer applies ChaCha20 keystream to the wire ciphertext and recovers f_i(l)
//
// PoP forgery for a sender-controlled EncryptedMessage with key = identity:
// choose any s, set pop = SchnorrSignature { R: s*G, s }
// pop.verify(identity, c) checks s*G == R + c*identity == R -> holds.
```

Note on severity bounds: I verified the validation gap and the ECDH collapse precisely; the end impact is confidentiality loss of secret-share components (dropping the effective secrecy of a share slot to zero), not by itself a full group-key recovery — full recovery would additionally require an observer to also obtain `t-1` other shares. This is the closest Serai analog to the "check gated behind a privilege conditional" class that is reachable from untrusted bytes in the in-scope crates; the DKG coordinator paths (Tributary message handling) were out of scope for proving end-to-end exposure of on-chain share bytes, though `DkgShare` storage in processor/src/key_gen.rs confirms shares are persisted where blame is arbitrated.
