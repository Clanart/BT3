### Title
ThresholdKeys deserialization accepts a secret share inconsistent with its verification shares, causing funds to be reported under an unspendable group key - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts serialized threshold-key material containing a secret share that does not correspond to the participant's verification share. `ThresholdKeys::new` derives `group_key` exclusively from the supplied verification-share map and never verifies `C::generator() * secret_share == verification_shares[i]`. An attacker who supplies malformed key material can therefore make Serai report a receive key controlled by arbitrary verification shares while retaining an unusable local secret share. [1](#0-0) [2](#0-1) 

### Finding Description
The deserializer reads `t`, `n`, and `i`, then reads the interpolation mode, one secret share, and `n` verification shares before passing them to `ThresholdKeys::new`. [3](#0-2)  The constructor checks the number and participant indices of the verification shares, but it does not check that the deserialized `secret_share` matches `verification_shares[params.i()]`. [4](#0-3)  It then derives `group_key` solely from the first `t` verification shares. [5](#0-4) 

This is semantically invalid input: the secret share is the value used for signing, while the verification-share map defines the advertised group key and the public verification relation. [6](#0-5)  The inconsistency survives deserialization and can be used to produce a `group_key()` unrelated to the loaded secret share. [7](#0-6) 

### Impact Explanation
An attacker can feed a malformed `ThresholdKeys` encoding that advertises a valid-looking group key while loading a secret share which does not belong to that group key. Funds sent to addresses derived from the reported `group_key()` can consequently be reported as received but not be spendable by the holder of the deserialized share. [8](#0-7) 

The malformed key is accepted before signing is attempted, so higher-level wallet or network code can expose the attacker-selected group key as the receive key. [9](#0-8)  Later signing will not repair the inconsistency: signing uses `original_secret_share()`, while verification uses the attacker-supplied verification shares. [10](#0-9) 

### Likelihood Explanation
The issue is reachable through the explicitly exposed `ThresholdKeys::read` byte parser; no malformed curve encoding or leaked private key is required. [11](#0-10)  The attacker only needs to control a serialized key bundle accepted by an integrator, such as imported, restored, exchanged, or otherwise untrusted key material.

### Recommendation
In `ThresholdKeys::new`, reject keys where `verification_shares[&params.i()] != C::generator() * secret_share`. For threshold sets, also verify that the supplied verification shares form a coherent public polynomial sufficient to derive the group key under the selected interpolation policy. [12](#0-11)  At minimum, `ThresholdKeys::read` should fail closed when the deserialized local share does not match its own public verification share. [1](#0-0) 

### Proof of Concept
For a one-of-one key, the parser accepts secret scalar `1` with verification share `2G`. The resulting object advertises group key `2G` while its signing secret is `1`, so outputs paid to `2G` are not spendable using the loaded secret share.

```rust
use std::io;
use zeroize::Zeroizing;
use group::{Group, GroupEncoding};
use ff::{Field, PrimeField};
use ciphersuite::Ciphersuite;
use frost::ThresholdKeys;
use dalek_ff_group::Ristretto;

fn malformed_keys() -> io::Result<ThresholdKeys<Ristretto>> {
  let mut bytes = vec![];

  bytes.extend(u32::try_from(Ristretto::ID.len()).unwrap().to_le_bytes());
  bytes.extend(Ristretto::ID);

  // t = 1, n = 1, participant i = 1
  bytes.extend(1u16.to_le_bytes());
  bytes.extend(1u16.to_le_bytes());
  bytes.extend(1u16.to_le_bytes());

  // Interpolation::Lagrange
  bytes.push(1);

  // secret_share = 1
  let one = <Ristretto as Ciphersuite>::F::ONE;
  bytes.extend(one.to_repr().as_ref());

  // verification_shares[1] = 2G, not G * secret_share
  let two_g = Ristretto::generator() * (one + one);
  bytes.extend(two_g.to_bytes().as_ref());

  // Currently succeeds despite the inconsistent private/public share pair.
  ThresholdKeys::read(&mut bytes.as_slice())
}
```

The relevant parser consumes the independent scalar and public share without a consistency check. [1](#0-0)

  pub fn new(

    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
