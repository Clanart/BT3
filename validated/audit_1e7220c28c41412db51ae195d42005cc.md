### Title
Aggregator gRPC server accepts state-changing and fund-broadcasting calls without any client authentication - ([File: core/src/servers.rs])

### Summary
The Aggregator's gRPC server, unlike the Verifier and Operator servers, does not enforce mTLS client-certificate authentication, so any network caller who can reach the Aggregator's listening port can invoke its state-changing and transaction-broadcasting RPCs (`Withdraw`, `OptimisticPayout`, `NewDeposit`, `InternalSendTx`, `SendMoveToVaultTx`, `InternalGetEmergencyStopTx`) that are meant only for the trusted "clementine-backend" coordination service.

### Finding Description
Clementine relies on mTLS to restrict privileged gRPC methods to the correct caller. For Verifier/Operator servers, `create_grpc_server` wires in an `Interceptors::OnlyAggregatorAndSelf` interceptor that checks the client's TLS leaf certificate against `aggregator_cert_path`/`client_cert_path`, and additionally distinguishes "Internal*" methods (self-only) from regular methods (aggregator-or-self) [1](#0-0) , enforced from server setup in `servers.rs` [2](#0-1) .

The documentation for the Aggregator explicitly states this protection is absent there: *"The aggregator does not enforce client certificates but does use TLS for encryption."* [3](#0-2) . `create_aggregator_grpc_server` starts the aggregator's gRPC service via the same generic `create_grpc_server` path but without any per-call identity check equivalent to `OnlyAggregatorAndSelf` [4](#0-3) .

Despite this, the Aggregator exposes numerous state-changing and fund-moving RPCs intended only for the internal "clementine-backend" service, including:
- `Withdraw` — instructs all (or selected) operators to front a Bitcoin payout for a Citrea withdrawal [5](#0-4) [6](#0-5) 
- `OptimisticPayout` — orchestrates verifier MuSig2 signing and constructs/broadcasts an optimistic payout tx [7](#0-6) [8](#0-7) 
- `NewDeposit` — drives the full deposit-signing flow across verifiers/operators [9](#0-8) 
- `InternalSendTx` / `SendMoveToVaultTx` — broadcast pre-signed transactions to the Bitcoin network [10](#0-9) 
- `InternalGetEmergencyStopTx` — creates the emergency-stop transaction [11](#0-10) 

Note that in the Verifier/Operator interceptor model, methods prefixed `Internal` are meant to be callable only by the entity itself, never by an external party [12](#0-11) . On the Aggregator, `InternalSendTx` and `InternalGetEmergencyStopTx` carry the same "Internal" naming convention and intent, yet the Aggregator's service registration applies no such restriction, so these are equally open to any caller.

This is structurally the same class of defect described in the external report: a state-changing/privileged operation checks (or, here, fails to check) the identity of the caller against the wrong (or no) principal, letting a party that was never meant to hold that privilege exercise it.

### Impact Explanation
An unauthenticated caller reaching the Aggregator's network endpoint can:
- Trigger `Withdraw`/`OptimisticPayout` for arbitrary withdrawal IDs/operators, causing operators to front payouts and consume TxSender/broadcast resources for requests not originated by the legitimate backend.
- Call `InternalSendTx`/`SendMoveToVaultTx` to broadcast arbitrary pre-signed protocol transactions at times of the attacker's choosing, which can disrupt the expected sequencing of the reimbursement/challenge/kickoff protocol.
- Trigger `NewDeposit` and `InternalGetEmergencyStopTx` flows that are supposed to be gated to the operator's own coordination service.

This matches the "unauthenticated state-changing or broadcasting call" High-impact category, since any of these actions is normally supposed to require the authenticated backend/aggregator identity, and here no identity is verified at all.

### Likelihood Explanation
Likelihood is high if the Aggregator's gRPC port is reachable over an untrusted network (the config only optionally sets `client_verification`/mTLS for Verifier and Operator, and the docs confirm the Aggregator intentionally skips client certificate enforcement). Any party with network access to the Aggregator's configured host/port can invoke these RPCs without possessing any of the system's private keys or certificates — no verifier/operator/aggregator role, key compromise, or TLS interception is required, since the intended protection (mTLS) is simply not applied on this server.

### Recommendation
Add call-time authorization to the Aggregator's gRPC service, mirroring the `Interceptors::OnlyAggregatorAndSelf` mechanism used for Verifier/Operator: require the Aggregator's client-facing methods to only be reachable from the trusted backend (e.g., by enforcing an equivalent "known caller certificate" check, or moving these coordination RPCs behind a private network / mTLS boundary consistent with the protections already applied to Verifier and Operator servers). At minimum, `Internal*`-prefixed Aggregator RPCs should be gated exactly like `Internal*` Verifier/Operator RPCs are — self/trusted-caller only.

### Proof of Concept
1. Start an Aggregator server per the documented configuration; note it does not require a client certificate (only server-side TLS for encryption) [3](#0-2) .
2. From any machine with network access to the Aggregator's listening address, open a TLS connection without presenting a client certificate.
3. Invoke `ClementineAggregator/Withdraw` (or `OptimisticPayout`, `InternalSendTx`, etc.) with attacker-chosen parameters, following the same request shape used in the aggregator's own CLI helper `AggregatorCommands::NewWithdrawal` [13](#0-12) .
4. Observe the call succeeds and executes the corresponding protocol action (e.g., operators receive `withdraw` requests, or a pre-signed tx is broadcast), confirming the endpoint is reachable without any authentication.

Note: I could not fully inspect `create_grpc_server`'s generic wiring for the Aggregator path (the tool call to read the exact interceptor-selection code for `create_aggregator_grpc_server` failed at the final iteration), so the assertion that literally zero interceptor is applied to the Aggregator server relies on the explicit documentation statement and the absence of any `Interceptors::OnlyAggregatorAndSelf` construction in `create_aggregator_grpc_server` (only `create_grpc_server(addr, svc, "Aggregator", &config)` is called with no separately built `Interceptors` value, unlike the Verifier/Operator paths) [4](#0-3) . A Devin session with full file access should verify this precisely before remediation.

        match self {
            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
            Interceptors::Noop => Ok(req),
        }
    }
}

#[allow(clippy::result_large_err)]
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}

## RPC Authentication

Clementine uses mutual TLS (mTLS) to secure gRPC communications between entities
