### Title
`TendermintEvmStateMachine::verify_membership` omits the storage-key rehash applied by its sibling non-membership/state-proof paths, breaking ISMP request delivery on Ethermint-style chains - (File: `modules/ismp/state-machines/evm/src/tendermint.rs`)

### Summary
This is a structural analog of the SP1 report's root cause: a verification function is missing a step that a sibling verification function in the same file already implements and documents as required, causing systematic false results on otherwise-valid proofs.

### Finding Description
`TendermintEvmStateMachine::verify_membership` (`modules/ismp/state-machines/evm/src/tendermint.rs` lines 99-151) builds the ICS23 storage key directly from the value returned by `commitment_state_trie_key`, without re-hashing it: [1](#0-0) 

```
for (slot, ev) in slot_keys.into_iter().zip(proofs.into_iter()) {
    // slot is expected to be 32 bytes keccak slot
    let key = storage_key_for(
        proof.height.id.state_id,
        &contract_address.0,
        slot.clone().try_into().map_err(|_| TendermintEvmError::UnsupportedKeyLength)?,
    );
```

`slot_keys` comes from `commitment_state_trie_key`, which already keccak256-hashes the request commitment into the Solidity mapping slot: [2](#0-1) 

Both sibling functions in the same file — `verify_non_membership` and `verify_evm_kv_proofs` (used by `verify_state_proof`) — take that same kind of 32-byte slot and explicitly apply a *second* `keccak256` before building the IAVL key, because Ethermint-style Tendermint EVM stores expose EVM storage under `prefix || address || keccak256(slot)`, not `prefix || address || slot`: [3](#0-2) [4](#0-3) 

The comment on the fixed `verify_evm_kv_proofs` path spells out exactly the class of bug this represents: *"Without this, the key resolves to one that never exists in the tree, so a valid ICS23 non-existence proof for the unhashed key falsely reports a present slot as absent... which can release source escrow for an order that was actually filled."* `verify_membership` was never updated to apply the same rehash, so it computes the wrong IAVL key for every commitment on a Tendermint/Ethermint-style EVM chain.

This is invoked directly from the core ISMP request handler with no fallback: [5](#0-4) 

### Impact Explanation
For any state machine using `TendermintEvmStateMachine` (Ethermint-style Tendermint EVM chains), `verify_membership` queries a storage key that structurally cannot match what is actually stored in the IAVL tree (it is missing the mandatory `keccak256(slot)` step that the non-membership and state-proof paths on the very same file apply). Because ICS23 proofs cryptographically bind a specific key/value pair to the root, a proof generated against the *correct* (hashed) key can never validate against the wrong (unhashed) key the code queries. This causes `verify_membership` — and therefore `handle_incoming_message` on request delivery — to deterministically fail for every legitimate PostRequest originating on such a chain, even though the commitment genuinely exists in the chain's Ethermint state. Since request delivery (and hence downstream escrow release / settlement dispatched via that message) can never succeed, any bridged value gated behind delivery of such a request is permanently stuck, which functions as a loss/lock of funds for users relying on that route.

### Likelihood Explanation
This triggers on the plain, unprivileged happy path — no malicious relayer, prover, or governance actor is required. Any legitimate request originating on a Tendermint/Ethermint-style EVM state machine and needing membership proof verification hits this path; the bug is purely a code-correctness defect in key derivation, present as soon as such a chain is configured to use `TendermintEvmStateMachine`. The sibling functions in the same file already had to be patched for the identical root cause, indicating the underlying key-format requirement is well understood but was not propagated consistently across all four uses (membership, non-membership, and state-proof) in this client.

### Recommendation
Apply the same `keccak256(slot)` rehash in `verify_membership` that `verify_non_membership` and `verify_evm_kv_proofs` already perform, so all three verification entry points in `TendermintEvmStateMachine` derive IAVL keys consistently. Add a shared helper (e.g., `ethermint_storage_key(state_id, addr, slot)`) used by all three functions to prevent this drift from recurring, and add a regression test exercising `verify_membership` against a real Ethermint fixture (mirroring the existing comment/test coverage already present for the non-membership fix).

### Proof of Concept
1. Configure a Tendermint/Ethermint-style EVM state machine (e.g. `StateMachine::Evm(chain_id)` backed by `TendermintEvmStateMachine`) as the source of a PostRequest.
2. Dispatch a request on that chain; the request commitment is stored in the chain's EVM contract mapping at Solidity slot `S = keccak256(commitment ++ mapping_index)`. In the IAVL store, that value is actually addressed at `prefix || contract || keccak256(S)`.
3. A relayer submits `handle_incoming_message` on Hyperbridge with a valid ICS23 membership proof for the real key `prefix || contract || keccak256(S)`.
4. `handlers/request.rs::handle` calls `state_machine.verify_membership(..)`, which computes the key as `prefix || contract || S` (missing the extra hash) per lines 122-128 of `tendermint.rs`.
5. `merkle_proof.verify_membership` is checked against a key that does not correspond to what the relayer's proof actually attests to, so verification fails with `MerkleProofVerificationFailed`, and the message is rejected — despite the request commitment genuinely existing on the source chain.
6. Every legitimate request from that chain suffers the same deterministic failure, permanently blocking delivery (and any escrow/settlement gated on it) for as long as the state machine is configured this way.

Note: I could not find evidence of a test harness or live deployment that specifically exercises `TendermintEvmStateMachine::verify_membership` against a real Ethermint fixture in this index, so I cannot confirm whether this path is currently exercised in production versus only in staging/test networks; a Devin session with full repo/test access would be needed to verify current deployment status and add the missing regression test.
