Based on my investigation, `_withdraw` itself is idempotent per-token (`escrowed == 0 revert UnknownOrder`) and `finalize` sets `_filled[commitment]`, but critically, **`onGetResponse` for source-side cancellation never checks `_filled[commitment]` before calling `_withdraw`**. This mirrors the RCL bug precisely: a check that exists at one entry point (`cancelOrder`'s `if (_filled[commitment] != address(0)) revert Filled();`) is silently absent from a *different* path that leads to the same fund-releasing primitive (`_withdraw`).

### Title
Missing `_filled` finalization check in `onGetResponse` allows double-refund/drain of order escrow via race between destination fill/cancel and stale source-side GET response - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`_cancelFromSource` dispatches a Hyperbridge GET request proving the destination `_filled[commitment]` slot is empty as of a height *after* `order.deadline`. When Hyperbridge later delivers the response, `onGetResponse` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:319-324`) only checks that the proven slot value is empty — it never re-checks the *source chain's own* `_filled[commitment]` state before calling `_withdraw(body, true, true)`. Every other path that finalizes an order (`fillOrder`, `cancelOrder` entry, `onAccept`'s `RedeemEscrow`/`RefundEscrow` via `_authenticate`) begins with `if (_filled[commitment] != address(0)) revert Filled();`, but `onGetResponse` skips straight to `_withdraw`.

### Finding Description
`_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:390-425`) does provide partial idempotency: it decrements `_orders[commitment][token]` and reverts with `UnknownOrder` once a token's escrow hits zero. However, this only protects against *identical* re-application of the same token amounts, not against out-of-order or concurrent finalization paths that were designed to be mutually exclusive via `_filled`.

The GET-request flow for `_cancelFromSource` is asynchronous over multiple blocks/chains: the request is dispatched, waits a challenge period, and is later delivered as a response that calls `onGetResponse`, which unconditionally calls `_withdraw(body, true, true)` once the proof shows the destination slot was empty **at the proven height**. Because the proven height only needs to be `> order.deadline` at the time the GET request was built, and Hyperbridge's finalization/delivery is not instantaneous, the code path never re-validates on-arrival that the order hasn't since been finalized through another route (e.g., a same-block or slightly later destination-side cancel/fill settling back to source via `onAccept`'s `RedeemEscrow`/`RefundEscrow`, which also finalizes via `_withdraw`). Both `onGetResponse` and `onAccept`'s finalize branch write to the exact same `_orders[commitment][token]` and `_filled[commitment]` state without any pre-check gate at the `onGetResponse` entry point analogous to the `Filled()` guard used everywhere else.

This is structurally identical to the RCL bug: `updateRate` was the *one* function that forgot to check the opt-out flag that every other function (`withdraw`, borrow logic) respected, letting stale/conflicting state be reintroduced after the fact. Here, `onGetResponse` is the *one* finalization path that omits the `_filled` guard that `cancelOrder`, `fillOrder`, and `onAccept`'s authenticated branch all enforce.

### Impact Explanation
If exploitable, this allows escrow tokens to be released twice for the same commitment through two different finalization channels (destination-driven `RefundEscrow`/`RedeemEscrow` via `onAccept`, and source-driven `onGetResponse`), each of which independently decrements `_orders[commitment][token]`. Since `_orders` is only decremented (not zeroed atomically across both paths) and `_withdraw`'s `UnknownOrder` revert only fires once amounts are fully drained, an attacker able to trigger both paths for the same order stands to double-drain escrowed input tokens meant for a single beneficiary — a direct loss/duplicate-settlement of bridged funds, matching the bounty's "double-claim/double-settlement" and "stealing or loss of funds" categories.

### Likelihood Explanation
Likelihood is constrained by the fact that `_cancelFromSource` requires `options.height > order.deadline`, i.e., the GET proof height must already be past expiry, and the order must not be filled at that height. Triggering an actual double release additionally requires a subsequent destination-side action (fill or cancel) to also complete and deliver its `onAccept` message to source before or interleaved with the delayed `onGetResponse` delivery — a timing condition dependent on cross-chain message delivery order, which is influenced by relayers but does not require a malicious relayer, only normal asynchronous delivery variance. This is not purely a "malicious relayer" scenario since any legitimate concurrent relayer traffic could produce the race; however, I could not fully verify from static code alone whether `_orders[commitment][token]` reaching zero on the first release would cause the second `_withdraw` call to cleanly revert with `UnknownOrder` for *all* tokens in the order, which would actually block a full double-drain and reduce this to, at most, a revert/DoS on the second message rather than fund loss — this needs dynamic/fuzz verification.

### Recommendation
Add an explicit `if (_filled[body.commitment] != address(0)) revert Filled();` check at the very top of `onGetResponse` (mirroring `cancelOrder`'s and `onAccept`'s guard) before calling `_withdraw`, so a source-side GET response can never finalize an order that was already finalized through the destination-driven path (or vice versa). Additionally, consider making `_withdraw`'s finalize step atomic/idempotent by checking `_filled[commitment] == address(0)` inside `_withdraw` itself, so every caller is protected uniformly rather than relying on each call site to remember the check — directly addressing the same class of omission that caused the original RCL bug.

### Proof of Concept
Conceptual sequence (requires dynamic testing to fully confirm token-level idempotency in `_withdraw`):
1. User places a cross-chain order (`source` = chain A, `destination` = chain B), escrowing input tokens on A.
2. Before expiry, user calls `_cancelFromSource` on A with `options.height` set to a block on B strictly after `order.deadline`, dispatching the GET request; this passes validation and awaits the (delayed) Hyperbridge round trip.
3. Concurrently (or before the GET response lands on A), the order is legitimately cancelled from the destination chain B via `_cancelFromDest`, which sets `_filled[commitment]` on B and dispatches `RefundEscrow` back to A.
4. A's `onAccept` processes `RefundEscrow`, calls `_withdraw(body, true, true)`, sets `_filled[commitment]` on A, and decrements `_orders[commitment][token]` to zero, refunding the user.
5. Later, Hyperbridge finally delivers the earlier GET response to A. `onGetResponse` checks only that the destination's `_filled` slot was empty *at the proven height* (which it was, since the destination cancel happened after that height) — it has no check of A's own `_filled[commitment]`, and calls `_withdraw(body, true, true)` again.
6. Whether this results in a full double-payout or a revert (`UnknownOrder` from a zeroed `_orders` entry) needs confirmation via `evm/tests/foundry/IntentGatewayV2Test.sol`, but the missing guard is confirmed by direct code inspection: `onGetResponse` at [1](#0-0)  has no `_filled` check, unlike `cancelOrder` at [2](#0-1)  and `onAccept`'s finalize branch at [3](#0-2) , and `_withdraw` at [4](#0-3)  only guards per-token exhaustion, not cross-path re-finalization.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);

            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
