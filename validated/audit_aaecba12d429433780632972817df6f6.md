### Title
Immature coinbase outputs are reported as spendable received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` scans every transaction in a block, including `block.txdata[0]`, and returns matching coinbase outputs as ordinary `ReceivedOutput` values. A `ReceivedOutput` can subsequently be passed to `SignableTransaction::new`, which treats it as an available input without checking whether its outpoint belongs to an immature coinbase. [1](#0-0) [2](#0-1) 

### Finding Description
`Scanner::scan_transaction` records any output whose `script_pubkey` is registered, deriving an `OutPoint` from the transaction ID and output index, but it does not receive or check the transaction's position within a block. `Scanner::scan_block` iterates over `block.txdata` starting at index zero, so the coinbase is processed exactly like a normal transaction. The resulting `ReceivedOutput` is then accepted by `SignableTransaction::new`, which places `input.outpoint` directly into the unsigned spending transaction and treats `input.output.value` as spendable input value. [3](#0-2) [4](#0-3) [2](#0-1) 

### Impact Explanation
A caller that trusts `scan_block`'s result can report funds as received and construct a transaction spending them before Bitcoin's 100-block coinbase maturity rule allows the spend. The created transaction will be consensus-invalid during the maturity period, even though Serai's wallet code accepted the input as spendable and calculated balances, fees, and signatures for it. This can cause incorrect accounting and rejected withdrawals or payments. [5](#0-4) [2](#0-1) 

### Likelihood Explanation
The condition is reached whenever a block containing a coinbase output to a registered scanner script is passed to `scan_block` before that coinbase has matured. A miner can deliberately target a known scanner script, and ordinary scanning of recent blocks can encounter this state without malformed or out-of-scope inputs. The API also does not mark returned coinbase outputs as immature, so downstream code cannot distinguish them after the scan result is returned. [6](#0-5) 

### Recommendation
Do not scan `block.txdata[0]` in `scan_block`, or return a type that explicitly preserves coinbase-immaturity metadata. Prefer changing the loop to iterate over `block.txdata[1 ..]` and separately exposing immature coinbase matches only through an API that cannot be passed directly to `SignableTransaction::new`. Additionally, `SignableTransaction::new` or its caller should enforce a maturity confirmation count for coinbase-sourced `ReceivedOutput`s. [1](#0-0) [7](#0-6) 

### Proof of Concept
1. Register a Taproot script for the wallet key with `Scanner::new` or `register_offset`.
2. Create or obtain a block whose coinbase transaction contains an output paying that script.
3. Call `Scanner::scan_block` before the coinbase has 100 confirmations.
4. Observe that `scan_block` returns a `ReceivedOutput` for `block.txdata[0]` without maturity metadata.
5. Pass that `ReceivedOutput` to `SignableTransaction::new`; its outpoint and value are used as an ordinary input, producing a transaction Bitcoin consensus rejects as an immature coinbase spend. [8](#0-7) [2](#0-1)

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
