### Title
Attacker-controlled FROST preprocess forces aggregate nonce to identity, panicking the BIP-340 `x()`/`hram()` and crashing the signer - (File: networks/bitcoin/src/crypto.rs)

### Summary
The CVE-2018-11375 bug class is "crafted input → application crash". Serai's Bitcoin Schnorr algorithm (`Schnorr`/`Hram` in `networks/bitcoin/src/crypto.rs`) computes the BIP-340 challenge via `x(R)`/`x(A)`, which `expect()`s the point is not the point at infinity (`crypto.rs:13-16`). A FROST participant can craft their preprocess `Commitments` (parsed via `read_preprocess` → `Commitments::read`, or supplied directly to `SignMachine::sign`) so that the aggregated session nonce `R = Σ (D_l + rho_l·E_l)` is the identity point. The next call into `sign`/`complete`/`verify` then panics instead of returning an error — a reachable, unprivileged denial of service.

### Finding Description
Each participant's preprocess carries `Commitments { nonces: Vec<NonceCommitments> }`, where each `NonceCommitments` holds per-generator `GeneratorCommitments([D, E])` points read straight from the wire by `GeneratorCommitments::read` (`crypto/frost/src/nonce.rs:34-36`) with only canonical-point validation from `C::read_G`. Neither `Commitments::read` (`nonce.rs:133-139`) nor `sign()` (`crypto/frost/src/sign.rs:283-310`) rejects the identity point as a commitment.

In `BindingFactor::nonces` (`nonce.rs:194-211`), the session nonce for (nonce `n`, generator `g`) is computed as `Σ_l (commitments.nonces[n].generators[g].0[0] + rho_l * commitments.nonces[n].generators[g].0[1])`. A malicious participant computes every other signer's bound contribution locally (the `rho` binding factors are deterministically derived from the `FROST_rho` transcript over all commitments, `sign.rs:361-371` and `nonce.rs:161-173`), then sets their own `E = identity` (so `rho_i·E` contributes nothing) and `D = −Σ_{others} (D_l + rho_l·E_l)`. The resulting aggregate `R` is the point at infinity.

`sign()` then calls `self.params.algorithm.sign_share(&view, &Rs, nonces, msg)` (`sign.rs:398`), and for Bitcoin this is `Schnorr` wrapping `IetfSchnorr` with `Hram`, whose `hram` calls `x(R)`:

```rust
// networks/bitcoin/src/crypto.rs:13-16
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
```

`x()` panics on the infinity point. The same panic is reachable in `AlgorithmSignatureMachine::complete` → `algorithm.verify(group_key, &self.Rs, sum)` (`sign.rs:465`) → `Schnorr::verify` → inner verify → `Hram::hram` (`crypto.rs:59-73`), and via `needs_negation`/`x_only` (`crypto.rs:21-28`). The code's own comments acknowledge it: "If either `R` or `A` is the point at infinity, this will panic" (`crypto.rs:54`), justified only by "negligible probability for a well-reasoned caller" — which does not hold when a signer deliberately engineers the nonce sum.

### Impact Explanation
Any participant in a Bitcoin threshold signing session can deterministically crash the signing process of every other participant (and of the aggregator) by broadcasting a malicious preprocess message. The signature is never produced; depending on how the host application handles panics, this aborts the signing session or kills the node thread. This is a remote, unprivileged denial of service using only a public protocol message — directly analogous to CVE-2018-11375's crafted-input crash.

### Likelihood Explanation
Medium-to-high within a session containing any malicious participant: the attack requires no secrets, no race, and no probabilistic grind — the attacker locally computes the required `D` because all `rho_l` and all other commitments are public before they broadcast their preprocess (they can even wait to be the last preprocess sender, since `rho` is a deterministic transcript function). The only prerequisite is that the identity point be expressible as a commitment — trivially true via the in-memory `Preprocess`/`SignMachine::sign` API, and also via bytes where the curve's canonical encoding admits infinity. Attack requires a threshold session the attacker legitimately joins, which is the standard FROST threat model.

### Recommendation
Reject the identity (and more broadly, low-order) points in `C::read_G`/`GeneratorCommitments::read`/`Commitments::read` (`crypto/frost/src/nonce.rs`), or check in `BindingFactor::nonces`/`sign()` that each aggregated `R` is non-identity and return `FrostError` instead of letting it propagate into `x()`. `x()`/`x_only()`/`Hram::hram` in `networks/bitcoin/src/crypto.rs` should return `Option`/`Result` rather than `expect()`/`panic!` on attacker-influenceable inputs.

### Proof of Concept
Conceptual, for a 2-of-2 (or any t-of-n) Bitcoin signing session where the attacker is participant `i_a`:

1. Honest parties broadcast preprocesses; attacker collects all `Commitments` `{D_l, E_l}`.
2. Attacker constructs the `FROST_rho` transcript (`sign.rs:361-368`), computes each `rho_l` via `BindingFactor::calculate_binding_factors` (`nonce.rs:161-173`), and computes each signer's bound contribution `B_l = D_l + rho_l·E_l` exactly as `BindingFactor::bound`/`nonces` do (`nonce.rs:180-209`).
3. Attacker forms `Commitments` with `generators[g] = GeneratorCommitments([D_a, E_a])` where `E_a = ProjectivePoint::identity()` and `D_a = -(Σ_{l≠a} B_l)`, serializes via `Writable::write`, and broadcasts.
4. Each victim calls `read_preprocess` (accepts: only canonicality is checked) then `sign`/`complete`. `B.nonces()` yields `R = Σ B_l = identity`; `IetfSchnorr` calls `Hram::hram(&R, &group_key, msg)` → `x(R)` → `encoded.x().expect("point at infinity")` panics (`crypto.rs:15`), crashing the victim instead of returning `FrostError`.
