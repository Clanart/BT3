## Finding

`GIT_CLONE_PROTECTION_ACTIVE` set to `'false'` in `clone()` in `app/src/lib/git/clone.ts` disables an upstream Git security guard for every recursive clone that Desktop performs — including clones driven entirely by attacker-controlled input (a crafted `x-github-client://openRepo/<url>` deep link, a "Clone in Desktop" GitHub API link, or a `github clone <url>` CLI invocation).

### Title
Recursive Clone Disables Git's Anti-Symlink/Embedded-Repo Clone Protection — (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` builds the `git clone --recursive` invocation and explicitly sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` [1](#0-0) . This is the same env var Git itself toggles internally to protect against known clone-time attacks (the class fixed upstream for CVE‑2024‑32002/32004: symlinked `.git`, case-collision/embedded submodule paths, and nested-repo tricks that let a hostile repository write files — including hooks — outside the intended worktree during a recursive clone). By forcing the flag off, Desktop is voluntarily disabling that guard rail for every clone URL a user opens, whether typed manually or supplied via a deep link/API response.

### Finding Description
The `clone` function only defends against one narrow class of attack: a crafted destination *path* escaping to a sensitive directory, via `isClonePathSensitive()` [2](#0-1) . It does nothing to validate or restrict the *content* of the attacker-supplied repository being cloned. The clone is always run with `--recursive`, meaning submodules are fetched and checked out automatically [3](#0-2) , and the process explicitly turns off `GIT_CLONE_PROTECTION_ACTIVE` [4](#0-3) .

The clone URL itself is fully attacker-influenced in several paths:
- The "Open in Desktop" deep link handler parses `openrepo://` URLs and forwards the embedded `url` query value straight into `openOrCloneRepository()` → the Clone dialog → `dispatcher.clone()` → `clone()` [5](#0-4) [6](#0-5) .
- The CLI `github clone <url>` path also forwards an arbitrary string as the clone URL with no scheme allow-list beyond the owner/name shortcut heuristic [7](#0-6) .

None of the existing guards (`isClonePathSensitive`, `sanitizeCloneName`, `parseRemote`) inspect the *contents* of the remote repository, its submodule definitions, or nested-repo/symlink structure — they only sanitize the destination directory name/path. Disabling `GIT_CLONE_PROTECTION_ACTIVE` removes Git's own internal safety net for exactly this gap.

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE=false` disables Git's built-in clone-time protections against symlinked `.git` directories / colliding submodule paths, an attacker who controls the cloned repository (hosted anywhere, reached via a deep link, "Open in Desktop" button, or CLI clone) could craft a repository whose recursive clone writes files (e.g., hook scripts, `.git/config` entries) outside the intended working directory of the new clone. Since Desktop invokes this with `--recursive` unconditionally and no interactive confirmation step, this can translate into local file write outside the repo boundary and, depending on which files get overwritten (e.g., a Git hook that later executes), potential code execution the next time Git operations run in that directory.

### Likelihood Explanation
Likelihood is high for the trigger conditions: no privileged access, no local file needed, and no unusual user action beyond clicking a link or running `github clone <url>` — both are documented, expected entry points into Desktop [5](#0-4) [8](#0-7) . The only uncertainty is the exact scope of protections that `GIT_CLONE_PROTECTION_ACTIVE` toggles inside the vendored Git/`dugite` binary used by Desktop — this repository does not document or test that variable's semantics anywhere else, so the precise exploitable primitive (which file/path collision classes are bypassed) could not be confirmed purely from local code and would need verification against the specific Git version bundled with Desktop.

### Recommendation
- Do not disable `GIT_CLONE_PROTECTION_ACTIVE` for clones of untrusted/attacker-supplied URLs (deep-link and CLI clone paths in particular). If it was disabled to work around a legitimate compatibility issue, scope the override narrowly and document why, rather than applying it to every clone.
- Add explicit post-clone validation (e.g., verify no submodule or nested `.git` entry escapes the destination directory) if the protection must remain disabled for compatibility reasons.
- Confirm, against the specific `dugite`/Git version Desktop bundles, exactly which upstream CVE the `GIT_CLONE_PROTECTION_ACTIVE` protections address, and add a regression test analogous to the existing `clone-path-safety-test.ts` and `clone-test.ts` suites that exercises a malicious nested-repo/symlink payload.

### Proof of Concept
Not independently reproducible from static analysis alone — reproducing this requires constructing a Git repository that exploits the specific symlink/embedded-repo clone weakness that `GIT_CLONE_PROTECTION_ACTIVE` is designed to block, then verifying against the exact bundled Git version whether disabling the flag allows the write-outside-worktree behavior. The concrete code path is confirmed:
1. Attacker hosts a malicious repository and gets the victim to open `x-github-client://openRepo/<attacker-url>` or run `github clone <attacker-url>`.
2. Flow: `parseAppURL` → `dispatchURLAction` → `openRepositoryFromUrl` → `openOrCloneRepository` → Clone dialog → `dispatcher.clone()` → `clone()` in `app/src/lib/git/clone.ts`, which runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` [1](#0-0) [6](#0-5) .
3. Whether this results in a file write outside the target directory depends on the vendored Git version's behavior with the flag off, which needs a live test environment to confirm.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
