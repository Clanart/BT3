### Title
Broken vesting formula in `_getClaimable` grants instant full-amount lock, enabling premature vlMGP voting power - ([File: rewards/ArbitrumMWomAirdrop.sol])

### Summary
`_getClaimable` in `ArbitrumMWomAirdrop.sol` ignores `startVestingTime`, `vestingPeriodCount`, and `intervals` entirely and always returns `totalAmount - claimed`, meaning a claimant can withdraw their entire merkle-allocated amount the instant `block.timestamp >= startVestingTime`, with no linear vesting whatsoever. When called with `isLock=true`, this full, un-vested amount is passed straight into `locker.lockFor(claimable, msg.sender)`, immediately crediting the attacker with full vlMGP lock/voting weight that should only have accrued gradually.

### Finding Description
`claim()` requires only `block.timestamp >= startVestingTime` and a valid merkle proof [1](#0-0) . It then computes `claimable` via `_getClaimable`:
```solidity
function _getClaimable(address account, uint256 totalAmount) internal view returns (uint256) {
    uint256 claimed = getClaimed(account);
    if (claimed >= totalAmount) return 0;
    uint256 vested = totalAmount;          // <-- always equals totalAmount, no time-based scaling
    if (vested > totalAmount) { ... }      // dead branch, can never trigger
    return vested - claimed;
}
``` [2](#0-1) 

`vestingPeriodCount` and `intervals` are declared state variables [3](#0-2)  but are never read anywhere in the contract — the intended linear-vesting schedule was never implemented. As a result, `vested` is hardcoded to `totalAmount`, so the very first `claim()` call at `startVestingTime` (or any later time) returns the entire allocation, not a fraction of it.

When `isLock=true`, this full `claimable` amount is approved and passed to `locker.lockFor(claimable, msg.sender)` [4](#0-3) . Tracing into `VLMGP.lockFor` → `_lock`, the tokens are transferred in and `IMasterMagpie(masterMagpie).depositVlMGPFor(_amount, _for)` is called immediately, with `totalAmount` (vlMGP supply) incremented in the same transaction [5](#0-4) . `balanceOf`/`getUserTotalLocked` read directly from `MasterMagpie.stakingInfo`, so the attacker's full vlMGP balance — and thus voting weight — is available immediately, with no additional gradual-release mechanism inside `VLMGP` itself [6](#0-5) . No modifier in `claim()` (only `whenNotPaused`/`nonReentrant`) or in `VLMGP.lockFor` (`whenNotPaused`/`nonReentrant`) prevents this — none of them check for vesting-schedule compliance, since the vesting check simply doesn't exist.

The attacker only needs a valid merkle leaf (any legitimate airdrop recipient) — no privileged role required.

### Impact Explanation
This is a governance-voting-result-manipulation impact: an attacker with a merkle-eligible allocation receives 100% of their future-vesting MGP-equivalent tokens as locked vlMGP in a single transaction instead of the gradually-vesting amount intended by `vestingPeriodCount`/`intervals`. That inflated vlMGP balance can be used immediately to vote in `WombatBribeManager`, giving the attacker disproportionate, front-loaded influence over gauge/bribe allocation compared to legitimate stakers whose weight accrues correctly (via normal `VLMGP.lock`/`lockFor` with organically-earned MGP). This directly corrupts vote weight integrity, matching the "governance voting result manipulation" Immunefi impact class named in the prompt.

### Likelihood Explanation
Feasibility is high and requires no special capital or privilege: any address with a valid merkle leaf in `totalRewardMerkleRoot` can call `claim(totalAmount, proof, false, true)` as soon as `block.timestamp >= startVestingTime`. It is fully repeatable by every eligible claimant (the bug is systemic to the contract, not to a specific address), and it's a single, straightforward transaction with no reentrancy or front-running needed — the vulnerability is deterministic on `_getClaimable`'s dead vesting logic.

### Recommendation
Implement the linear vesting formula using `startVestingTime`, `vestingPeriodCount`, and `intervals`, e.g.:
```solidity
uint256 elapsed = block.timestamp - startVestingTime;
uint256 periodsElapsed = Math.min(elapsed / intervals, vestingPeriodCount);
uint256 vested = totalAmount * periodsElapsed / vestingPeriodCount;
```
so `claimable` (and therefore the amount passed to `locker.lockFor`) reflects only genuinely vested tokens at the time of the call, for both the `isStake`/`isLock`/direct-transfer paths.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbitrumMWomAirdrop` with `vestingPeriodCount = 12`, `intervals = 30 days`, `startVestingTime = T`.
2. Fund the contract with `reward` tokens and set a merkle root containing an attacker leaf with `totalAmount = 1_000_000e18`.
3. Deploy/mock `ILocker` as `VLMGP` wired to `MasterMagpie`, and `WombatBribeManager`.
4. Warp to `T` (i.e., 0 of 12 vesting periods elapsed).
5. Call `claim(1_000_000e18, proof, false, true)` from attacker.
6. Assert `claimedAmount[attacker] == 1_000_000e18` (full amount claimed at t=0 vesting periods elapsed) — expected correct behavior would be `claimedAmount == 0` or near-0 since 0 of 12 periods have elapsed.
7. Assert `VLMGP.balanceOf(attacker) == 1_000_000e18` immediately after claim (i.e., full instant voting weight).
8. Call `WombatBribeManager.vote(...)` from attacker using the full weight and assert the bribe/gauge vote outcome tips in the attacker's favor versus a scenario where vesting behaved correctly (attacker would have 0 weight at `t=T`).
