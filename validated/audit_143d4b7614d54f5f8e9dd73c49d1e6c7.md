The closest analog candidate is the processor-side `Scanner`/`register_offset` path in `networks/bitcoin`. Let me check whether outputs sent to a derived (offset) address before the key/scanner activation are silently missed.### Title
Deposits to predictable offset addresses sent before multisig activation are silently missed by the Scanner - ([File: processor/src/multisigs/scanner.rs](processor/src/multisigs/scanner.rs), [File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
The Notional bug class: a valuation function returns a wrong result (zero) during a window where dependent state (the settlement rate) exists logically but is not yet initialized; integrators consuming the result are harmed. The Serai analog: the Bitcoin `Scanner` only begins matching outputs from a key's `activation_number` onward, but the deposit addresses derived for that key — including the deterministic `Branch`/`Change`/`Forwarded` offset addresses — are publicly computable before activation. An unprivileged sender can pay to a future or pending key's offset address in a block earlier than activation; `scan_transaction`/`scan_block` never examine those blocks, so the output is permanently invisible. The protocol's view of received funds is silently zero for a real, on-chain payment, exactly mirroring `totalAssets() == 0` during the unsettled window.

### Finding Description
`ScannerDb::register_key` stores `(activation_number, key)` and `ScannerHandle::register_key` asserts `activation_number > scanner.ram_scanned.unwrap_or(0)` and initializes `ram_scanned = activation_number`, so scanning begins at the activation block [1](#0-0) . The Bitcoin network implementation builds the scan set deterministically: `scanner(key)` registers `OutputType::Branch`, `OutputType::Change`, and `OutputType::Forwarded` at offsets `Secp256k1::hash_to_F(KEY_DST, b"branch"/"change"/"forward")` — constants identical for every key, known to anyone [2](#0-1) . `Scanner::scan_transaction` matches purely on `output.script_pubkey` membership in the registered script map, with no provenance check [3](#0-2) . Therefore the P2TR address `p2tr_script_buf(key + G*offset)` is computable as soon as the next key is public (published on Serai before its Bitcoin activation block), yet any output paying it in a pre-activation block falls before `ram_scanned`/`latest_scanned_block` and is never saved or emitted [4](#0-3) . The same gap applies at retirement: `retire_key` keeps only `keys[1]`, and `is_retirement_block` handling means payments to the retired key's scripts after the retirement block are dropped [5](#0-4) .

### Impact Explanation
Funds sent to a not-yet-active (or just-retired) key's deterministic offset address are real spendable-by-the-set UTXOs that the processor never reports. Analogous to `convertToAssets`/`maxWithdraw` returning zero in the unsettled window, the scanner's result during this window is silently empty while a deposit exists: the depositor is never credited, and the BTC is stranded at an address whose spending requires the threshold set — effectively burned unless manually recovered. If any accounting treats "reported balance" as ground truth, actual wallet balance and credited balance permanently diverge.

### Likelihood Explanation
Medium. Exploitation requires only sending a Bitcoin transaction — fully unprivileged. The window is real: the key must be revealed to Serai (for `register_key`/`signable` setup) before the activation block it is scanned from, and the offsets are fixed public constants, so the future deposit address is derivable off-chain. A user or attacker front-running activation with a branch/forward payment, or a late payer hitting a retired key's script after `retirement_block`, triggers the miss with no error anywhere — the defining property of the bug class (silent wrong result, no revert).

### Recommendation
At minimum document that outputs to a key's derived scripts are only detected in blocks `>= activation_number` and `< retirement_block`. Preferably: on `register_key`, derive the earliest block at which the key was publicly knowable (or rescan a bounded window before activation) rather than starting at `activation_number`; and for retirement, either keep matching retired scripts (flagging outputs as late/invalid) for a defined grace period, or treat post-retirement payments to retired scripts as an explicit alarmed event instead of silently discarding them — i.e., "revert rather than return zero" per the upstream discussion's preferred fix.

### Proof of Concept
1. Let `K_next` be the next Bitcoin multisig key, publicly known on Serai at block `B` with planned activation `A > B`.
2. Compute `off = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")` and `addr = p2tr_script_buf(K_next + G*off)` (incrementing `off` until even, as `register_offset` does) — all public data.
3. Send BTC to `addr` in a block `< A`.
4. `Scanner::scan_transaction` would match this output (script_pubkey is registered once `scanner(K_next)` runs at activation), but the scanner never iterates blocks `< A` since `ram_scanned`/DB `scanned_block` starts at `A` (`register_key` sets `ram_scanned = Some(activation_number)`).
5. Result: the UTXO is never emitted as `ScannerEvent::Block { outputs }`, never marked `seen`, never credited — while remaining spendable only by the threshold set, stranding the depositor's funds with zero reported value.
