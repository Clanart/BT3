Confirmed: `FileChange.id` is derived from `${status.kind}+${path}` (or `+oldPath` for renames), not from file content or any content hash. [1](#0-0) 

### Title
Selection/diff state carried over by path-based file ID lets an attacker-controlled repository silently commit unreviewed content - (File: app/src/lib/stores/updates/changes-state.ts)

### Summary
`updateChangedFiles` reconciles the working-directory selection (which files/lines are staged for commit) across successive `git status` refreshes by matching files solely on `FileChange.id`, which is `${status.kind}+${path}` (same kind + same path == same "file"), with no content hash or blob OID involved. [1](#0-0) [2](#0-1) 

### Finding Description
When Desktop refreshes repository status (`_loadStatus` → `updateChangedFiles`), it looks up each newly reported file by `filesByID.get(file.id)` and, if found, carries over the *previous* `DiffSelection` (all/none/partial line selection) onto the new file object via `file.withSelection(existingFile.selection)`. [3](#0-2) 

Because `id` is keyed only on `AppFileStatusKind + path` (e.g. `"Modified+src/app.ts"`), this reconciliation cannot distinguish between the same path being modified twice with *different content* between two status polls. A background fetch/checkout/rebase against an attacker-controlled remote, or a race where the working tree is touched between two `_refreshRepository`/`_loadStatus` calls (Desktop polls status frequently and also does so after pulls, checkouts, and background indicator fetches via `refreshIndicatorForRepository`), can produce a new working-directory entry at the same path and same status kind but with entirely different diff hunks/content. [4](#0-3) [5](#0-4) 

In that scenario the "partial line selection" or "excluded" state the user set for the *old* content is blindly re-applied to the *new* content, since `withSelectableLines`/line indices are only revalidated against the new diff hunks lazily when a diff is actually re-rendered for the currently selected single file (`updateChangesWorkingDirectoryDiff`), not for every file in the working directory list. [6](#0-5) 
For files that are *not* the single currently-selected/rendered file, the stale `DiffSelectionType.All`/`None`/`Partial` state (including line-level selection bitsets) is preserved verbatim with no diff re-validation at all, so a file whose content changed underneath the user retains its prior "include in commit" decision.

Existing guards do not stop this: `updateChangedFiles` explicitly documents that it treats same-ID files as "the same file" purely for UX continuity (preserving scroll/selection state across quick refreshes), not as a security boundary; there is no check that the underlying git status entry's OID/hash is the same before reusing selection state. [7](#0-6) 

### Impact Explanation
If an attacker can influence the working directory content at a path that the user has already reviewed and included/excluded (e.g. via a malicious `post-checkout`/`post-merge` hook shipped in a cloned/fetched repo, a submodule update, or a race with an automatic background refresh triggered by GitHub Desktop's own polling), the user's next commit can silently include attacker-modified content that was never actually reviewed in the diff view, or silently exclude a file the user intended to commit. This matches the "silent corruption of what the user commits or pushes" impact class — the visual "included" checkbox state does not reflect the actual content that will be committed.

### Likelihood Explanation
Likelihood is moderate: it requires two status refreshes to occur with different content at the same path/status-kind combination while the file is not the one currently rendered in the diff pane (which is the common case when multiple files are changed and the user is not actively looking at that particular file). Desktop refreshes status frequently on its own (after remote operations, background indicator fetches, and timers), so the precondition is not exotic, but a fully passive attacker cannot single-handedly force the timing — some combination of a hook execution or a legitimate git operation on attacker-influenced content is required.

### Recommendation
Include a content-sensitive component (e.g., the git status entry's blob SHA, or at least the raw status code / rename score) in the key used to decide whether to carry over selection state in `updateChangedFiles`, or explicitly invalidate/reset selection for any file whose underlying diff has changed since it was last rendered, rather than only re-validating selectable lines for the single currently-selected file.

### Proof of Concept
Not independently executable from the index alone (requires a live Electron/git environment); however, the unit tests already demonstrate the exact mechanism being relied upon: [8](#0-7) 
This test shows that a "partial" selection is preserved by ID even when a brand-new `WorkingDirectoryFileChange` object is supplied as the new status — nothing in `updateChangedFiles` verifies the new file's diff content matches what the preserved selection was computed against. Swapping the content of `oldWorkingDirectory`'s file between the "prevState" and the "status" argument (same path/kind, different diff hunks) while keeping the test assertion would demonstrate that the selection is still carried over unchanged.
