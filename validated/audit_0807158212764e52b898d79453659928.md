## Title
Stale line-index diff selections are silently re-applied against a freshly regenerated diff during partial-commit staging, causing wrong content to be committed - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user select individual lines/hunks to include in a commit. The selection is stored as a set of *positional* line indices (`DiffSelection`), not tied to the content or a checksum of the diff it was computed against. When the commit is actually created, `applyPatchToIndex` re-fetches the working-directory diff from disk and blindly re-applies the old, cached line-index selection to this brand-new diff. If the tracked file changes between the moment the user made their selection and the moment staging occurs, the indices silently point at different content than what the user reviewed and approved — exactly the "stale-quote-applied-without-revalidation" pattern from the report, but here corrupting the user's commit instead of a token transfer.

### Finding Description
The commit flow is:

1. `_commitIncludedChanges` in the app store reads the **cached** `workingDirectory.files` (each carrying a `DiffSelection` built earlier while the user was looking at a diff snapshot) and passes them straight to `createCommit`. [1](#0-0) 

2. `createCommit` calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex`. [2](#0-1) [3](#0-2) 

3. `applyPatchToIndex` fetches a **new** diff from disk right before formatting the patch — this is a second, independent `git diff` call, unrelated in time to whatever diff the user actually looked at when selecting lines: [4](#0-3) 

4. `formatPatch` walks the hunks of this *newly fetched* diff and decides what to include using `file.selection.isSelected(absoluteIndex)` — a pure index lookup with no relationship to the underlying text: [5](#0-4) 

5. `DiffSelection.isSelected` is implemented purely on line-number set membership; it has no concept of the diff's content, so a line index that meant "delete the malicious line" in the old diff can silently mean "keep this now-different line" in the new diff: [6](#0-5) 

The application does have partial protection for the *rendering* path — when the diff is reloaded for on-screen display, `withSelectableLines` is used to drop selections that no longer correspond to includable lines: [7](#0-6) 

However, this reconciliation only happens on the render/refresh path (e.g. `_changeFileSelection`/status refresh), not on the commit/staging path. `applyPatchToIndex` never calls `withSelectableLines` or otherwise checks that its freshly-fetched diff still matches what the cached `DiffSelection` was built from before blindly indexing into it. There is no revert/abort analogous to the recommended Hashflow fix — the code proceeds and produces a patch regardless of whether the diff has drifted.

### Impact Explanation
If the working-tree content of a tracked file changes between the time a user reviews a diff and selects specific lines and the time they press "Commit" (e.g. because of a hostile `.gitattributes` clean/smudge filter, a `post-checkout`/`post-merge` hook shipped in a cloned/fetched malicious repository, or any background process the app itself triggers as part of git operations), GitHub Desktop will silently stage and commit content the user never reviewed or approved for that selection — i.e. silent corruption of what the user commits, which is explicitly listed as valid impact. Because there is no error, warning, or diff mismatch check, the user has no signal that the committed diff differs from what they intended, and could unknowingly push attacker-influenced content.

### Likelihood Explanation
This requires a timing window between diff generation/selection and the staging re-diff, and a mechanism to modify the tracked file in that window (e.g. a malicious repo-provided smudge/clean filter or hook triggered by a concurrent git operation such as a background fetch/checkout). This is a real, but narrow, race condition — it is not a one-click trigger, so likelihood is moderate rather than high. Nonetheless, the code path itself has no defensive check whatsoever (no hash/staleness comparison of the diff used for selection vs. the diff used for staging), so any successful timing manipulation from an attacker-controlled repository artifact will silently corrupt the commit.

### Recommendation
Before using a cached `DiffSelection` to build a patch in `applyPatchToIndex`/`formatPatch`, verify that the diff being staged is the same one the selection was computed against (e.g. compare hunk headers/content hash, or re-derive `selectableLines` and reject/renegotiate the selection like `withSelectableLines` already does for the render path). If the newly fetched diff differs from the diff underlying the current selection, abort the partial-stage operation and force the UI to refresh the diff and require the user to re-confirm their selection, rather than silently applying stale indices to new content — mirroring the report's recommendation to "revert if the input is not actual" instead of proceeding with a fallback/clamped value.

### Proof of Concept
1. Clone/open a malicious repository containing a working-tree file `foo.txt` and a `.gitattributes`/hook mechanism that rewrites `foo.txt`'s content shortly after checkout or during a `git` background operation Desktop performs.
2. In GitHub Desktop, open the Changes view, view the diff for `foo.txt`, and select a subset of lines to include in the commit (leaving others unselected) — this creates a `DiffSelection` with `divergingLines` tied to the currently rendered hunk's line indices. [8](#0-7) 
3. Before the user clicks "Commit", trigger the attacker-controlled mechanism to rewrite `foo.txt` on disk (e.g. via the hook/filter), changing hunk boundaries/line content without the app re-rendering the diff.
4. Click "Commit". `_commitIncludedChanges` uses the stale `WorkingDirectoryFileChange` (with the old selection) and calls `createCommit` → `stageFiles` → `applyPatchToIndex`, which re-diffs the file (now containing attacker content) and applies the old line-index selection to it via `formatPatch`. [9](#0-8) 
5. Observe that the resulting commit contains content that does not match what was displayed to the user at selection time, with no warning or error surfaced by the application.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }

  // Lower inclusive, upper exclusive. Same as substring
  public withRangeSelection(
    from: number,
    length: number,
    selected: boolean
  ): DiffSelection {
    const computedSelectionType = this.getSelectionType()
    const to = from + length

    // Nothing for us to do here. This state is when all lines are already
    // selected and we're being asked to select more or when no lines are
    // selected and we're being asked to unselect something.
    if (typeMatchesSelection(computedSelectionType, selected)) {
      return this
    }

    if (computedSelectionType === DiffSelectionType.Partial) {
      const newDivergingLines = new Set<number>(this.divergingLines!)

      if (typeMatchesSelection(this.defaultSelectionType, selected)) {
        for (let i = from; i < to; i++) {
          newDivergingLines.delete(i)
        }
      } else {
        for (let i = from; i < to; i++) {
          // Ensure it's selectable
          if (this.isSelectable(i)) {
            newDivergingLines.add(i)
          }
        }
      }

      return new DiffSelection(
        this.defaultSelectionType,
        newDivergingLines.size === 0 ? null : newDivergingLines,
        this.selectableLines
      )
    } else {
      const newDivergingLines = new Set<number>()
      for (let i = from; i < to; i++) {
        if (this.isSelectable(i)) {
          newDivergingLines.add(i)
        }
      }

      return new DiffSelection(
        computedSelectionType,
        newDivergingLines,
        this.selectableLines
      )
