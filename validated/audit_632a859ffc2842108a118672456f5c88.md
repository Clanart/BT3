Based on the investigation, the closest local analog to this bug class is in the Alpenglow block-reward distribution path, where `pending_delegator_rewards` on a vote account is read to compute each staker's share, but nothing found in the searched code decrements/zeroes it after that share is paid out.

### Title
Vote account `pending_delegator_rewards` is never decremented after being paid out as block reward, allowing the same deposited balance to be redistributed across multiple epochs - (runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`calculate_block_reward()` computes each stake account's share of a vote account's block-revenue reward as a fraction of `vote_state.pending_delegator_rewards()`, proportional to that delegation's stake out of `total_active_stake`, and caps the total paid at `pending_delegator_rewards` for that single calculation call. [1](#0-0) 
This mirrors the Trident bug pattern: a "yield source" value (`pending_delegator_rewards`, analogous to `bento.balanceOf`) is read and distributed, but the code never appears to reduce/clear that source value to reflect what was already paid, so a later read of the same underlying account can pay out overlapping amounts.

### Finding Description
`calculate_block_reward` is invoked from `calculate_stake_rewards_and_commissions` during the epoch-boundary reward calculation phase, and again from `recalculate_stake_rewards`, which is explicitly documented to run when rewards distribution has to be recomputed mid-epoch (e.g., after a restart/snapshot restore during active distribution). [2](#0-1) 
The code comments in `calculate_block_reward` explicitly acknowledge that "if stake account has already received rewards, it's possible to have `stake > total_active_stake`" and that the individual reward could look "greater than the pending rewards" — it only clamps the result with `.min(pending_delegator_rewards)`, it does not track or subtract what has already been distributed to other stakers from the same vote account's deposited pool. [3](#0-2) 
Separately, `store_stake_accounts_in_partition` in the distribution phase adds the `block_reward` amount directly to the stake account's lamports and delegation, but the snippet available shows no corresponding write back to the vote account's `pending_delegator_rewards` field to reduce it by the amount just paid out. [4](#0-3) 
An extensive search across `programs/vote/src/vote_state/mod.rs`, `handler.rs`, `vote_processor.rs`, and the reward calculation/distribution files found only one code path that *increases* `pending_delegator_rewards` (`add_pending_delegator_rewards`, called from the unprivileged `deposit_delegator_rewards` SIMD-0123 instruction), and no confirmed decrement/reset path. [5](#0-4) [6](#0-5) 
If this field is indeed never reduced after being consumed as a block-reward numerator, then the *same* deposited pool of lamports backs the block-reward calculation for every subsequent epoch's `calculate_block_reward()` call for that vote account, letting delegators receive multiples of the deposit that was ever CPI-transferred in via `DepositDelegatorRewards`, inflating stake balances and total capitalization beyond what was actually deposited.

### Impact Explanation
If confirmed, this would let unprivileged callers of `DepositDelegatorRewards` (or the vote account's stakers generally) receive stake-account lamport increases that exceed the total lamports ever transferred into the vote account for this purpose, across repeated epochs — a direct inflation/fund-duplication bug affecting `Bank::capitalization` and stake-account balances, analogous to the diluted-yield theft in the original report.

### Likelihood Explanation
Likelihood is uncertain: I was not able to conclusively locate a decrement of `pending_delegator_rewards` anywhere in the reachable code (which would refute this finding), nor a definitive confirmation that block_reward calculation is scoped to a single epoch's deposit delta rather than the cumulative balance. The `min(pending_delegator_rewards)` clamp and the explicit code comment discussing the "stake > total_active_stake" recalculation edge case indicate the authors were aware of a related double-counting risk during recalculation, but dismissed it as "harmless in practice" for the *within-one-calculation* clamp — this doesn't address cross-epoch reuse of the same pool.

### Recommendation
Verify (via full repository access, since the indexed search may be incomplete) whether `pending_delegator_rewards` is decremented anywhere after `calculate_block_reward` results are used — e.g., in `distribute_reward_commissions`, `store_stake_accounts_in_partition`, or a vote-account update triggered at epoch boundary. If no such decrement exists, `pending_delegator_rewards` must be reduced by the total `block_reward` amount distributed for that epoch (mirroring how the Trident fix recommends `burn()` collecting fees explicitly rather than relying on a stale cached value), so that the same deposited lamports cannot be counted as the reward numerator in more than one epoch's calculation.

### Proof of Concept
Not constructed — this requires tracing the full commit history of the vote-account update path across epoch boundaries with actual execution/testing, which was not possible with the available read-only indexed search. A background Devin session with full repository and test-execution access would be needed to (1) confirm whether `pending_delegator_rewards` is ever decremented, and (2) if not, write an integration test creating a vote account with delegated stake, depositing via `DepositDelegatorRewards`, running two reward epochs with `block_revenue_sharing` enabled, and asserting whether total lamports paid out via `block_reward` across both epochs exceeds the single deposit amount.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
