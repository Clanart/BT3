### Title
`_tokenPrice()` integer-division truncation lets gas-token cost round to zero, letting solvers drain sponsored gas for free - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._tokenPrice()` computes the ERC-20-per-wei exchange rate with a single integer division. Like the `IRCalculator._computeIR()` bug (numerator smaller than denominator truncates to `0` before use in a downstream calculation), when the native-asset price is small relative to the registered token's USD price scaled by its decimals, the division truncates to a very small integer or exactly `0`. That value is then fed into the inherited `PaymasterERC20` cost formula (`erc20Cost = weiCost * tokenPrice / 1e18`), so any `weiCost` below `1e18/tokenPrice` truncates to `0` — the paymaster sponsors gas for free.

### Finding Description
`_tokenPrice()` performs: [1](#0-0) 
```solidity
function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
    uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
    uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

    return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
}
```
This is a single integer division producing `tokenPrice`, documented by the contract's own comment as "token base units per wei, scaled by 1e18": [2](#0-1) 

`tokenPrice` flows straight into the base `PaymasterERC20` implementation's `erc20Cost = weiCost * tokenPrice / 1e18` (used in both `_postOp` charging logic and the local view helper): [3](#0-2) 
```solidity
function estimateTokenCost(...) external view returns (uint256) {
    ...
    uint256 weiCost = gasAmount * maxFeePerGas + _postOpCost() * maxFeePerGas;
    return (weiCost * _tokenPrice(cfg)) / _tokenPriceDenominator();
}
```

Exactly mirroring the `IRCalculator` root cause: `_tokenPrice()`'s integer division truncates when `nativeUsd * 10**tokenDecimals * markup < tokenUsd * 10_000`. Unlike the tangent bug (which reverts on `log_2(0)`), here the truncated value silently propagates as a valid (small or zero) price into `erc20Cost`, so instead of a DoS the effect is **loss of funds**: the paymaster charges the solver/user near-zero or zero ERC-20 tokens while it has already fronted real ETH/native gas via the ERC-4337 EntryPoint.

Concretely: for a registered token with a small `tokenDecimals` value (e.g. 0–2, allowed by `RegisterToken` governance action) and a native asset whose USD price is low relative to the token's USD price (e.g. a rollup's native gas token crashing in value, or a token priced far above the native asset, such as a wrapped BTC-style asset with `tokenDecimals = 0`), `tokenPrice` can compute to `1` or `0`. With `tokenPrice = 1`, `erc20Cost = weiCost * 1 / 1e18` truncates to `0` for any `weiCost < 1e18` (i.e., any transaction costing less than 1 native token, which is essentially all normal transactions) — the paymaster subsidizes the entire operation for free, repeatedly, for every UserOp using that token.

No existing guard checks that `tokenPrice` (or the resulting `erc20Cost`) is non-zero or above some minimum before `_postOp` charges the sender; `_getOraclePrice` only guards against `answer <= 0` and staleness — it does not protect against extreme (but legitimate) price ratios producing sub-unit precision loss: [4](#0-3) 

### Impact Explanation
This is a direct fund-loss vector against the paymaster's own EntryPoint deposit: users/solvers pay `0` (or negligible) ERC-20 tokens while consuming real, paymaster-sponsored native gas, draining the contract's `EntryPoint` deposit over repeated transactions. This falls squarely under "stealing or loss of funds" — no malicious relayer, oracle compromise, or admin action is required; it only requires a legitimate, governance-approved token/decimals configuration combined with an ordinary price movement (native asset losing value relative to the registered token), which is exactly the "edge-case price" condition in the seed report.

### Likelihood Explanation
Requires: (1) a token registered with low `tokenDecimals` (a normal governance configuration, not an attack), and (2) the native/token USD price ratio drifting so that `nativeUsd * 10**tokenDecimals * markup` falls below `tokenUsd * 10_000`. This is realistic over the lifetime of a permissionless, "fully onchain" paymaster meant to support "any token with a Chainlink feed" — native-asset price volatility (especially on smaller L2s/appchains with volatile gas tokens) versus a stable, dollar-pegged registered token is a foreseeable market condition, not a contrived one. Once triggered, exploitation requires no privileged capability — any UserOp sender using the affected token gets free-gas transactions.

### Recommendation
Add an explicit floor check in `_tokenPrice()` (or immediately after computing `erc20Cost`) reverting or reverting the UserOp validation if `tokenPrice == 0` or below a governance-configured minimum, and consider scaling the numerator up (e.g., by an additional fixed-point factor) before dividing, then scaling back down at the final cost computation, to preserve precision the way `ABDKMath64x64.divu` is meant to for `IRCalculator`. At minimum, reject in `_validatePaymasterUserOp`/`_fetchDetails` any computed `tokenPrice` that would cause `erc20Cost` to round to `0` for the given transaction's `weiCost`.

### Proof of Concept
```solidity
// Illustrative: tokenDecimals = 0, tokenUsd = $100 (1e10 in 8-dec), nativeUsd = $1 (1e8 in 8-dec), markupBps = 0
// _tokenPrice = (1e8 * 10**0 * 10000) / (1e10 * 10000)
//             = (1e8 * 10000) / (1e10 * 10000)
//             = 1e12 / 1e14 = 0  (truncates to zero)
//
// Downstream: erc20Cost = weiCost * 0 / 1e18 = 0
// => paymaster fronts real gas, sender pays 0 ERC-20 tokens.
```
This mirrors the reproduction pattern in the seed report (`rawNumerator / rawDenom == 0` before scaling), applied to `SimplexPaymaster._tokenPrice()` at [1](#0-0)  instead of `IRCalculator._computeIR()`. Existing tests only exercise "normal" price ratios (`testTokenPriceSixDecimals`, `testTokenPriceEighteenDecimals`) and never assert a non-zero floor on `tokenPrice`, so this truncation path is unguarded and untested: [5](#0-4)

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```

```text
    /// @notice Estimate the token cost for a given gas amount and fee, mirroring
    ///         PaymasterERC20._erc20Cost (including its postOp gas cushion).
    function estimateTokenCost(
        address token,
        uint256 gasAmount,
        uint256 maxFeePerGas
    ) external view returns (uint256) {
        TokenConfig memory cfg = tokenConfigs[token];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(token);

        uint256 weiCost = gasAmount * maxFeePerGas + _postOpCost() * maxFeePerGas;
        return (weiCost * _tokenPrice(cfg)) / _tokenPriceDenominator();
    }
```
