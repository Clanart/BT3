### Title
Wallet RPC `get_private_key` Discloses Mnemonic/Seed for Any Key in the Local Keychain Regardless of the Currently Logged-in Wallet - (File: chia/wallet/wallet_rpc_api.py)

### Summary
The wallet RPC endpoint `get_private_key` accepts an arbitrary `fingerprint` and returns the full private key material (`sk`, derived farmer/pool keys, and the mnemonic `seed`) for that fingerprint, without verifying that the requested fingerprint matches `self.service.logged_in_fingerprint` (the wallet the caller is actually authenticated/logged into). Any caller with access to the wallet RPC can enumerate other fingerprints via `get_public_keys` and then pull the private key/mnemonic for any of them, not just the currently active one.

### Finding Description
`WalletRpcApi.get_private_key` looks up a key by iterating over *all* private keys stored in the keychain, keyed only by the caller-supplied `fingerprint`, with no scoping to the wallet session that is currently logged in: [1](#0-0) 

Compare this with `log_in`, which is the only place that actually checks `self.service.logged_in_fingerprint` before allowing a fingerprint-switch operation: [2](#0-1) 

`get_public_keys` freely enumerates every fingerprint present in the keychain without restricting output to the logged-in key: [3](#0-2) 

The underlying keychain lookup used by `get_private_key` (`_get_private_key` → `keychain_proxy.get_all_private_keys()`) is not scoped to a single owner/session; it walks the entire local keychain store: [4](#0-3) [5](#0-4) 

This is structurally analogous to the MyFinances flaw: a single authenticated/authorized session (one HTTPS/mTLS client of the wallet RPC, or one "logged-in" wallet fingerprint) can read another principal's (another key's) private financial/identity material by supplying its ID — no ownership or session check is enforced at the point where the sensitive data is returned.

### Impact Explanation
`get_private_key` returns the raw mnemonic seed and private scalar key for the requested fingerprint. Since a chia key's mnemonic is the full custody secret for all coins derivable under it, any process/tool that can call this RPC (e.g. a local automation script, a partially-trusted plugin, or a compromised lower-privilege component that is only supposed to operate on the currently logged-in wallet) can exfiltrate the mnemonic of *every other key* stored on the same node — including keys belonging to a different user/profile sharing the same daemon/keyring. That is complete compromise of custody (funds theft) for all non-active keys, not merely a metadata leak. This satisfies the "unauthorized/unsigned coin movement" bar because possession of the mnemonic is equivalent to unrestricted spend authority over all coins under that key.

### Likelihood Explanation
Exploitation only requires the ability to issue two already-existing, unauthenticated-by-fingerprint RPC calls (`get_public_keys` then `get_private_key`) against a wallet RPC session that is not scoped per-key. Any local caller who is allowed to talk to the wallet RPC at all (which is the assumed threat actor here: "local RPC caller") can walk the full list of fingerprints and pull every mnemonic, regardless of which fingerprint is actually logged in. No cryptographic bypass, no race condition, and no chain-state manipulation is needed — it is a direct, deterministic call sequence.

### Recommendation
Scope `get_private_key` (and ideally `get_public_keys`) to only the fingerprint currently returned by `self.service.logged_in_fingerprint`, rejecting requests for any other fingerprint unless the caller has separately authenticated ownership of that other key (e.g., by first successfully calling `log_in` with it). At minimum, add an explicit check in `get_private_key`:
```python
if request.fingerprint != self.service.logged_in_fingerprint:
    raise ValueError("Fingerprint does not match the currently logged-in wallet")
```
and consider filtering `get_public_keys` output or clearly documenting/gating multi-key enumeration behind a stronger authorization boundary if multi-tenant use of a single wallet daemon is intended.

### Proof of Concept
1. Configure a chia node/wallet daemon with two or more keys added to the keychain (e.g., via `add_key`), simulating a shared daemon used by multiple key owners.
2. Log in as fingerprint A (`log_in` with `fingerprint=A`), simulating "user A's session."
3. As the same RPC client (no re-authentication needed), call `get_public_keys` to enumerate all fingerprints, including fingerprint B belonging to a different key owner: [3](#0-2) 
4. Call `get_private_key(GetPrivateKey(fingerprint=B))`. The endpoint returns `B`'s full mnemonic seed and private key even though the session is logged in as `A`: [6](#0-5) 
5. Use the recovered mnemonic to fully restore and spend from wallet B's coins, demonstrating unauthorized custody takeover of another key's funds.

**Caveat**: This finding rests on the assumption that a single wallet RPC daemon/keychain instance can legitimately hold keys belonging to different trust principals (e.g., multiple users of a shared node, or components meant to be restricted to only the active fingerprint). If the deployment model instead guarantees that the wallet RPC and its keychain are always fully single-owner and equally trusted for all stored fingerprints, this would not constitute a cross-principal authorization bypass. I was not able to find explicit documentation in this repo confirming or denying multi-key/multi-owner sharing of one wallet daemon instance, so this assumption should be verified.

```python
    async def _get_private_key(self, fingerprint: int) -> tuple[PrivateKey | None, bytes | None]:
        try:
            all_keys = await self.service.keychain_proxy.get_all_private_keys()
            for sk, seed in all_keys:
                if sk.get_g1().get_fingerprint() == fingerprint:
                    return sk, seed
        except Exception as e:
            log.error(f"Failed to get private key by fingerprint: {e}")
```

```python
    async def get_all_private_keys(self, request: dict[str, Any]) -> dict[str, Any]:
        all_keys: list[dict[str, Any]] = []
        if self.get_keychain_for_request(request).is_keyring_locked():
            return {"success": False, "error": KEYCHAIN_ERR_LOCKED}

        private_keys = self.get_keychain_for_request(request).get_all_private_keys()
        for sk, entropy in private_keys:
            all_keys.append({"pk": bytes(sk.get_g1()).hex(), "entropy": entropy.hex()})

        return {"success": True, "private_keys": all_keys}
```

```python
    def get_all_private_keys(self) -> list[tuple[PrivateKey, bytes]]:
        """
        Returns all private keys which can be retrieved, with the given passphrases.
        A tuple of key, and entropy bytes (i.e. mnemonic) is returned for each key.

        all_keys: list[tuple[PrivateKey, bytes]] = []
```
