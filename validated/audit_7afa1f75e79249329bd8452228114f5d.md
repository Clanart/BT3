### Title
Attacker-controlled participant count in `ThresholdKeys::read` triggers quadratic Lagrange interpolation and tens of thousands of field inversions, exhausting CPU (DoS analog of OOG) - ([File: crypto/dkg/src/lib.rs])

### Summary
The reported bug class is a loop over an attacker-influenced list in which an expensive operation is redundantly recomputed per element, exhausting resources (gas in the EVM report). The Serai analog is `ThresholdKeys::read` → `ThresholdKeys::new`: the `n`/`t` parameters are two attacker-controlled bytes in the serialized blob, and `new` computes a Lagrange `interpolation_factor` for each of the `t` participants, where every factor evaluation itself loops over all `t` participants — an O(t²) computation with `t` separate field inversions, reachable purely from untrusted bytes.

### Finding Description
`ThresholdKeys::read` reads `t` and `n` directly from the byte stream (`crypto/dkg/src/lib.rs` lines 591-602), then reads `n` scalars/`n` points and calls `ThresholdKeys::new` (lines 604-632). `ThresholdParams::new` only enforces `t <= n` and both being nonzero `u16`s (lines 166-178), so an attacker can supply `t = n = 65535`.

`new` then computes the group key as:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```
(lines 376-378)

`Interpolation::Lagrange::interpolation_factor` iterates the entire `included` slice per call — `num *= share; denom *= share - i_f;` for each of `t` elements — plus one field inversion per call (lines 229-246). With `t = 65535`, this is ~4.3 billion scalar multiplications and 65,535 field inversions performed inside a single `read` call, on data entirely controlled by the sender. This is the same shape as the report: an unbounded per-item loop repeatedly performing heavy work (there, `getAccountHealth`/oracle calls; here, a full O(t) interpolation plus inversion per participant), where only a linear amount of work is actually needed.

The same quadratic pattern exists in `ThresholdView` construction: `view()` calls `interpolation_factor` per included signer (lines 500-507), and `ThresholdView::interpolation_factor` re-derives the O(len) factor on every query (lines 657-662).

### Impact Explanation
Any component that deserializes `ThresholdKeys` from unauthenticated input (listed as an untrusted-bytes sink) can be stalled for an effectively unbounded duration by a ~4 MB crafted blob (`65535` points + scalars). This is a CPU/resource-exhaustion DoS against the node processing the message — the Rust analog of the report's out-of-gas revert. Severity Medium: availability impact only, no secret leakage, fully reachable from public input bytes.

### Likelihood Explanation
Requires only that an attacker can get a node to call `ThresholdKeys::read` (or `ThresholdKeys::new`/`view` with a large participant set) on their data. `t`/`n` are 16-bit fields with no cost to the attacker; no valid key material is needed since the shares map is populated from the same attacker bytes (lines 620-623) and validation occurs only after the expensive loop reads `verification_shares` — in fact the interpolation happens after only length/index checks (lines 355-365), so garbage shares still trigger the full quadratic computation.

### Recommendation
- Cap `t`/`n` at a realistic bound (e.g., a few hundred) at deserialization/`ThresholdParams::new` time rather than accepting full `u16` range.
- Amortize the interpolation: compute all Lagrange denominators once and batch-invert them (a single inversion via Montgomery's trick), reducing `new` from O(t²) multiplications + t inversions to O(t²) multiplications + 1 inversion; better, evaluate the interpolated-at-zero product directly instead of per-participant factors when only `group_key` is needed.
- Cache computed factors in `ThresholdView` instead of recomputing per query.

### Proof of Concept
Construct a byte stream: `id_len || C::ID || t=0xFFFF || n=0xFFFF || i=1 || interpolation=1 (Lagrange) || secret_share || 65535 encoded points`. Feed it to `<ThresholdKeys<C>>::read`. After ~4 MB of `read_G` decodes, `ThresholdKeys::new` executes `interpolation_factor` 65,535 times, each looping 65,535 iterations with one inversion — ~4.3e9 field multiplications and 65,535 inversions in one synchronous call from a single untrusted message.

Note: I verified the arithmetic structure in `crypto/dkg/src/lib.rs` directly; I did not confirm which higher-level call sites expose `ThresholdKeys::read` to unauthenticated input, but it is an enumerated untrusted-byte sink in scope.
