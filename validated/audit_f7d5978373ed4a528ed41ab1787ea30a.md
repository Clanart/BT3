### Title
`SignableTransaction::new` omits the OP_RETURN data output from the weight/vbytes estimate, so the signed transaction pays a lower real fee rate than `needed_fee` claims and can fall below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Arcadia issue is about adding two quantities denominated in different units (`openPosition` in pool-token units + `minimumMargin` in a stablecoin) without conversion or consistency checks. The Serai analog: `SignableTransaction::new` computes `needed_fee` from a vbytes estimate that excludes the caller-supplied OP_RETURN output, while the actual signed transaction includes it — the "fee paid" and "fee required" end up denominated against different transaction sizes.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output carrying `data` is pushed onto `tx_outs` [1](#0-0) , but both calls to `calculate_weight_vbytes` pass only `payments` (and optionally `change`) — never the data output [2](#0-1) [3](#0-2) . `calculate_weight_vbytes` builds a mock `Transaction` whose `output` vector is constructed solely from `payments` plus change [4](#0-3) .

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` is computed on an underestimate of up to ~90 vbytes (80-byte `data` plus output overhead, all non-witness) [5](#0-4) .
- The `TooLowFee` check compares this underestimated `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, also using the underestimated `vbytes` [6](#0-5) .
- The change amount is computed as `input_sat - payment_sat - fee_with_change`, so the transaction's actual fee equals `fee_with_change` exactly — but spread over the real, larger vsize, the effective sat/vbyte is lower than requested and can drop below the relay minimum [7](#0-6) .

The `data` parameter is attacker/integrator-controlled bytes on a public API; nothing in the function errors when `data` is supplied, it is simply left out of the size accounting.

### Impact Explanation
A `SignableTransaction` built with `data` passes all of the library's own fee checks yet, once signed by the threshold signing machine and broadcast, pays a real fee rate below `DEFAULT_MIN_RELAY_TX_FEE` (or below the requested `fee_per_vbyte`). Such a transaction is non-standard/will not relay or confirm, so inputs committed to it can be stuck in an unconfirmable plan — the analog of "funds reported fine by internal accounting but not actually usable" caused by inconsistent denominations in the arithmetic.

### Likelihood Explanation
Any caller that supplies a non-empty `data` (the library explicitly supports up to 80 bytes) triggers it deterministically; whether the real rate dips below relay minimum depends on `fee_per_vbyte` and input/change amounts, but the fee rate is always overstated. In-tree callers (e.g., `make_signable_transaction` in `processor/src/networks/bitcoin.rs`) currently pass `None` for data, which limits in-protocol exposure; as a library bug it is reachable by any downstream caller, so Medium rather than High.

### Recommendation
Include the OP_RETURN output in the weight estimate: pass the fully-formed `tx_outs` (or the serialized data length) into `calculate_weight_vbytes` instead of raw `payments`, e.g. add a `data_len: Option<usize>` parameter and push a mock `TxOut` with a `ScriptBuf::new_op_return` of the same size. Then compute `needed_fee`, the `TooLowFee` check, and the change deduction against that inclusive vbytes figure.

### Proof of Concept
Conceptual: call `SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte` is exactly the relay minimum (~1 sat/vB after rounding). `needed_fee` is computed on a mock TX missing the ~90-vbyte OP_RETURN output and passes `TooLowFee`; the resulting real transaction's `fee() / actual_vsize` is below 1 sat/vB, so `send_raw_transaction` rejects it as non-standard. The gap is exactly the OP_RETURN output's weight that `calculate_weight_vbytes` never sees.
