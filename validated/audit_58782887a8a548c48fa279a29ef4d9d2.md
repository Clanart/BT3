### Title
Scanner reports immature coinbase outputs as spendable `ReceivedOutput`s, inflating the reported balance with funds that cannot actually be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` scans every transaction in a block, including `txdata[0]` (the coinbase). Any coinbase output paying to a registered script is returned as an ordinary `ReceivedOutput`, indistinguishable from a normally spendable output. Downstream, `SignableTransaction::new` performs no maturity check, so the protocol's effective balance ("reserves") can include up-to-100-blocks-immature funds — exactly the bug class where an accounting figure includes assets that are not actually available to meet liabilities.

### Finding Description
`scan_transaction` pushes a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script, with no flag for coinbase provenance (networks/bitcoin/src/wallet/mod.rs:199-213). `scan_block` iterates `block.txdata` wholesale, so `block.txdata[0]` — the coinbase — is scanned identically (networks/bitcoin/src/wallet/mod.rs:221-227). Bitcoin consensus forbids spending coinbase outputs for 100 blocks, yet `ReceivedOutput` carries no maturity/height metadata, and `SignableTransaction::new` treats every supplied `ReceivedOutput` as a fungible input (networks/bitcoin/src/wallet/send.rs:175-185). The doc comment acknowledges the caveat ("a post-processing pass is needed"), but the API still hands out these outputs as identical, spendable-looking objects, and nothing in the spend path (`new` → `multisig` → `sign` → `complete`) rejects them.

### Impact Explanation
A miner (an unprivileged party in the threat model) can place an output paying to the scanned vault script inside a coinbase transaction. `scan_block` reports it as received funds. If the consuming protocol sums `ReceivedOutput::value()` as available balance and attempts to satisfy withdrawals with it, `SignableTransaction`/`TransactionSignMachine` will produce and sign a transaction spending the immature outpoint — consensus-invalid, so the withdrawal fails, while books showed sufficient funds. This mirrors the report: the "reserve" includes value that is not in the spendable pool, so obligations cannot be paid in full despite a nominally adequate balance. At minimum it is a forced signing attempt that produces an invalid transaction; at worst the accounting overstates liquid funds.

### Likelihood Explanation
Requires a miner to direct coinbase value to the scanned script (rare in practice but fully permissionless for the miner), plus a consumer that calls `scan_block` rather than filtering `txdata[1 ..]` or enforcing height-based maturity — which the API does not enforce itself. That combination makes the realistic severity Medium: concrete mis-accounting and failed spends, but gated on miner cooperation and integrator usage of `scan_block`.

### Recommendation
Have `scan_block` skip `block.txdata[0]` (or mark `ReceivedOutput`s derived from it as immature by threading the block height through), and/or have `SignableTransaction::new` reject inputs known to be immature. If the coinbase must remain scannable for accounting, return a distinct type so it cannot flow into the spend path unchecked.

### Proof of Concept
```rust
// A miner crafts a coinbase paying to the vault script:
let block = Block { /* txdata[0] = coinbase containing TxOut { value, script_pubkey: vault_script } , ... */ };
let outputs = scanner.scan_block(&block);
// outputs[0] is a ReceivedOutput for the coinbase outpoint — indistinguishable
// from a normal UTXO. Summing outputs[].value() counts immature funds.
let stx = SignableTransaction::new(outputs, &payments, change, None, fee_rate).unwrap();
let machine = stx.multisig(&keys).unwrap();
// The signed transaction spends an immature coinbase outpoint; any node
// rejects it (bad-txns-premature-spend-of-coinbase). Funds were "received"
// but are not spendable for 100 blocks.
```
Key lines: `scan_transaction` matches only `script_pubkey` and pushes `ReceivedOutput` (mod.rs:205-211); `scan_block` scans `block.txdata` including index 0 (mod.rs:221-227); `SignableTransaction::new` consumes `inputs` with no maturity check (send.rs:175-185).
