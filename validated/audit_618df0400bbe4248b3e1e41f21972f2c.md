### Title
Unprivileged `depositFor` with no zero-address check permanently locks user funds to `address(0)` in `MasterMagpie` accounting - (File: `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2.depositFor(uint256 _amount, address _for)` lets any wallet deposit a stablecoin and route the resulting stake to an arbitrary `_for` address with no validation that `_for != address(0)`. If a caller mistakenly (or through a front-end/integration bug) passes `address(0)`, the deposited principal is converted into LP/receipt tokens and staked in `MasterMagpie` under `userInfo[stakingToken][address(0)]`, an account that can never be accessed because `msg.sender` can never legitimately equal `address(0)`.

### Finding Description
`depositFor` transfers the caller's tokens into the helper, then calls the internal `_deposit`, forwarding `_for` unchecked all the way to `MasterMagpie.depositFor`: [1](#0-0) [2](#0-1) 

`MasterMagpie.depositFor` is only gated by `_onlyPoolHelper`, i.e. any registered pool helper (unprivileged, callable by any wallet) can credit stake to any address, including `address(0)`, and there is no zero-address guard: [3](#0-2) 

Internally, `_deposit` updates `userInfo[_stakingToken][_for]`, permanently recording the deposit under the zero address. Meanwhile, on the Wombat side, `WombatStaking.deposit` mints the receipt token to `msg.sender` (the pool helper) rather than to `_for`, and the helper immediately re-stakes it into `MasterMagpie` on behalf of `_for`: [4](#0-3) 

Since normal user-facing withdrawal paths in the pool helpers use `msg.sender` as the identity for `MasterMagpie.withdrawFor`/`withdraw`, and no transaction can ever originate with `msg.sender == address(0)`, the stake recorded for `address(0)` becomes permanently unreachable — nobody, including the depositor, can ever withdraw the underlying principal or claim the accrued rewards tied to that stake entry.

### Impact Explanation
The deposited stablecoin is irrevocably converted into LP inside the Wombat pool and its corresponding claim (the `MasterMagpie` stake record) is locked to an account that no wallet can ever control. This constitutes a permanent freeze of user principal and any future yield accrued on it, satisfying the "permanent freezing of funds" bar. The loss is total for the specific deposit amount routed to `address(0)`.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires a caller (a wallet or an integrating front-end/contract) to pass `address(0)` as `_for`, which can happen due to an uninitialized variable, a misconfigured integration, or bot/script error — the same class of user mistake underlying the original report. No privileged role or governance action is needed; any ordinary wallet can trigger it by calling `depositFor` directly.

### Recommendation
Add a zero-address check at the entry point and propagate it defensively:
```solidity
function depositFor(uint256 _amount, address _for) external {
    if (_for == address(0)) revert InvalidAddress();
    ...
}
```
Similarly add the same guard in `MasterMagpie.depositFor`/`_deposit` as defense-in-depth, since it is the shared entry point used by all pool helpers.

### Proof of Concept
1. Any wallet approves `depositToken` to `WombatPoolHelperV2` and calls `depositFor(amount, address(0))`. [1](#0-0) 
2. `_deposit` forwards `_for = address(0)` to `IWombatStaking(wombatStaking).deposit(...)`, which converts the deposit into pool LP and mints receipt tokens to the helper contract. [5](#0-4) 
3. `_stake` then calls `MasterMagpie.depositFor(stakingToken, amount, address(0))`, which records the stake under `userInfo[stakingToken][address(0)]`. [6](#0-5) 
4. Because no transaction can originate from `msg.sender == address(0)`, none of `MasterMagpie`'s user-facing `withdraw`/`multiclaim*` functions (which key off `msg.sender`) can ever retrieve this stake, permanently freezing the deposited funds and any rewards accrued on them.
