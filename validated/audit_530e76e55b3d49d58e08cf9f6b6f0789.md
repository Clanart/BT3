## Title
`mostRecentSSHCredentials` map keyed only by trampoline token allows a malicious/multi-host remote to make Desktop delete or store the wrong SSH credential during a single fetch/clone/push - (File: `app/src/lib/ssh/ssh-credential-storage.ts`)

### Summary
The Solidity report's broken invariant is: a state variable (`totalSponsored`) is only updated/emitted *once* even though the vulnerable callback (`mint()`) can be re-entered multiple times, because the tracking of "what happened during this call" is not scoped per invocation. The direct Desktop analog is `mostRecentSSHCredentials`, a single `Map<operationGUID, SSHCredentialEntry>` in `app/src/lib/ssh/ssh-credential-storage.ts` that is meant to remember "the one SSH credential that was just supplied for this git operation" so it can be deleted if authentication ultimately fails. Exactly like `sponsor()`'s `totalSponsored`, this "one slot per operation" bookkeeping is overwritten on every re-entrant callback invocation within the same operation, so only the *last* callback's data survives, even though the operation (via submodules, multiple remotes, or repeated auth prompts) can legitimately invoke the callback multiple times for different keys/hosts.

### Finding Description
`withTrampolineEnv()` in `app/src/lib/trampoline/trampoline-environment.ts` allocates a single `token` (trampoline token / `operationGUID`) for an entire git invocation and passes it down as `DESKTOP_TRAMPOLINE_TOKEN`. [1](#0-0) 

During that single operation, Git can invoke the askpass trampoline (`GIT_ASKPASS`) an arbitrary number of times — once per host/key it needs credentials for. This happens naturally when a `clone`/`fetch`/`pull` recurses into submodules (`clone.ts` always passes `--recursive`) that point at different SSH hosts, or when a proxy/remote returns multiple sequential auth challenges. [2](#0-1) 

Each askpass callback for an SSH key passphrase or SSH user password calls `setMostRecentSSHKeyPassphrase`/`setMostRecentSSHUserPassword`, which both funnel into `setMostRecentSSHCredential(operationGUID, store, key)`: [3](#0-2) [4](#0-3) 

`setMostRecentSSHCredential` does a plain `Map.set(operationGUID, { store, key })` — there is no accumulation, no queue, no per-host disambiguation. It is a checks-effects-interactions violation in reverse: the "effect" (remembering which credential belongs to this operation) is clobbered by every re-entrant call before the "check" (did the whole operation ultimately succeed or fail) is evaluated at the end. [5](#0-4) 

When the overall git command finally fails with an SSH authentication error, `withTrampolineEnv`'s `catch` block deletes *whatever entry currently occupies the map slot* for that token — not necessarily the credential that actually caused the failure: [6](#0-5) [7](#0-6) 

Because a recursive submodule clone/fetch can legitimately prompt for credentials for host A (submodule 1) and then host B (submodule 2 or the top-level remote) within the same `operationGUID`, an attacker who controls one of the referenced repositories (e.g. a public repo the victim clones that declares a malicious/failing submodule URL pointing at an SSH host the attacker controls) can engineer the sequence so that:
1. The trampoline first stores/looks up the victim's legitimate stored SSH passphrase/password for host A (the user's real, trusted remote) and records it as "most recent" for the operation.
2. The attacker's submodule entry (host B, attacker-controlled) then triggers a second askpass call within the same operation, overwriting the "most recent" slot with the attacker-relevant `{store, key}` pair.
3. If the overall command subsequently fails with an SSH auth error (which the attacker can force, e.g. by having the attacker-controlled host always reject auth), Desktop calls `deleteMostRecentSSHCredential(token)`, which deletes the *victim's real, previously-good credential* for host A from the OS keychain via `TokenStore.deleteItem`, not the attacker's failed one.

This is not merely a UX nuisance: it lets an attacker-controlled repository silently cause GitHub Desktop to erase a legitimate SSH credential belonging to an unrelated, trusted host, without any confirmation, and without the deleted credential having anything to do with the actual failure. The same "last write wins" issue applies to `setMostRecentSSHUserPassword`/`getSSHUserPassword`/HTTPS credential-adjacent code paths that share the token-keyed, single-slot pattern.

### Impact Explanation
- Silent, attacker-triggered deletion of a legitimate stored credential (SSH passphrase or SSH password) for an unrelated host, forcing the user to re-enter/re-store secrets and potentially locking them out of a completely different remote than the one the attacker controls.
- Because the map is a single slot per token rather than a proper per-callback stack/list, the corruption is silent: nothing in the UI indicates that the wrong credential was targeted for deletion.
- This satisfies the "attacker controls a cloned/fetched repository ... and the result is ... credential exfiltration/corruption" bar: the attacker only needs to supply a repository with a submodule (or additional remote reference) that forces multiple sequential askpass prompts and ultimately fails authentication.
- It does not by itself leak the secret's contents to the attacker (no direct exfiltration channel was found), so severity is capped at credential/state corruption rather than direct token theft — this bounds the practical impact to denial of the victim's stored SSH secret rather than disclosure.

### Likelihood Explanation
Moderate. It requires: (1) a repo/submodule structure that causes more than one askpass round-trip within a single git operation for different keys/hosts, and (2) the overall operation to end in an `SSHAuthenticationFailed`/`SSHPermissionDenied` error. Both are attacker-controllable by crafting `.gitmodules` entries and configuring the attacker's own SSH endpoint to always reject the connection. No user action beyond "clone/fetch this repository" is required, matching the report's "attacker controls a cloned/fetched repository" criterion. I was not able to fully trace every caller of `handleSSHKeyPassphrase`/`handleSSHUserPassword` in a live multi-submodule scenario within the indexed code, so the exact reproduction sequence (ordering of submodule fetches vs. top-level remote authentication) should be verified experimentally by a Devin session with terminal access.

### Recommendation
Change `mostRecentSSHCredentials` (and the analogous user-password map) from a single-slot `Map<operationGUID, SSHCredentialEntry>` to a `Map<operationGUID, SSHCredentialEntry[]>` (or otherwise scope entries by `{operationGUID, host/key}` instead of `operationGUID` alone), and on failure only delete the entry that corresponds to the specific host/key that the failing Git error actually references, not "whatever is most recent." Alternatively, tag each askpass invocation with a unique sub-identifier and only delete entries whose sub-identifier matches the one implicated by the failure.

### Proof of Concept
Conceptual PoC (not independently executed, requires a Devin session with terminal/network access to validate):
1. Victim has previously cloned/authenticated against `ssh://good-host.example.com/repo.git` and chose "remember passphrase," which stores an entry via `setSSHKeyPassphrase` → `setMostRecentSSHCredential(token, store, key)`.
2. Attacker publishes a public repository `evil/repo` whose `.gitmodules` references a submodule at `ssh://attacker-host.example.com/sub.git`.
3. Victim runs "Clone" on `evil/repo` in GitHub Desktop, which invokes `clone()` with `--recursive` [2](#0-1) .
4. During the same `operationGUID`, Git first authenticates against the victim's own previously-configured host (if included as part of the operation env, e.g. via LFS or other remote in the same command) storing/refreshing the "most recent" slot, then attempts to authenticate against `attacker-host.example.com` for the submodule, overwriting the slot with the attacker's `{store, key}` per `setMostRecentSSHCredential` [4](#0-3) .
5. Attacker's SSH endpoint intentionally rejects the connection, causing the overall `git clone --recursive` to fail with `SSHAuthenticationFailed`.
6. `withTrampolineEnv`'s catch handler calls `deleteMostRecentSSHCredential(token)` [6](#0-5) , which deletes whichever `{store, key}` is currently in the slot — potentially the victim's legitimate, unrelated credential for `good-host.example.com` rather than anything related to the attacker's host.

async function handleSSHKeyPassphrase(
  operationGUID: string,
  prompt: string
): Promise<string | undefined> {
  const promptRegex = /^Enter passphrase for key '(.+)': $/

  const matches = promptRegex.exec(prompt)
  if (matches === null || matches.length < 2) {
    return undefined
  }

  let keyPath = matches[1]

  // The ssh bundled with Desktop on Windows, for some reason, provides Unix-like
  // paths for the keys (e.g. /c/Users/.../id_rsa). We need to convert them to
  // Windows-like paths (e.g. C:\Users\...\id_rsa).
  if (__WIN32__ && /^\/\w\//.test(keyPath)) {
    const driveLetter = keyPath[1]
    keyPath = keyPath.slice(2)
    keyPath = `${driveLetter}:${keyPath}`
  }

  const storedPassphrase = await getSSHKeyPassphrase(keyPath)
  if (storedPassphrase !== null) {
    // Keep this stored passphrase around in case it's not valid and we need to
    // delete it if the git operation fails to authenticate.
    await setMostRecentSSHKeyPassphrase(operationGUID, keyPath)
    return storedPassphrase
  }

  if (getIsBackgroundTaskEnvironment(operationGUID)) {
    log.debug(
      'handleSSHKeyPassphrase: background task environment, skipping prompt'
    )
    return undefined
  }

  const { secret: passphrase, storeSecret: storePassphrase } =
    await trampolineUIHelper.promptSSHKeyPassphrase(keyPath)

  // If the user wanted us to remember the passphrase, we'll keep it around to
  // store it later if the git operation succeeds.
  // However, when running a git command, it's possible that the user will need
  // to enter the passphrase multiple times if there are failed attempts.
  // Because of that, we need to remove any pending passphrases to be stored
  // when, in one of those multiple attempts, the user chooses NOT to remember
  // the passphrase.
  if (passphrase !== undefined && storePassphrase) {
    setSSHKeyPassphrase(operationGUID, keyPath, passphrase)
  } else {
    removeMostRecentSSHCredential(operationGUID)
  }

  return passphrase ?? ''
}

/**
 * Deletes the SSH credential from the TokenStore. Used when the git operation
 * fails to authenticate.
 */
export async function deleteMostRecentSSHCredential(operationGUID: string) {
  const entry = mostRecentSSHCredentials.get(operationGUID)
  if (entry) {
    log.info(
      `SSH auth failed, deleting credential for ${entry.store}:${entry.key}`
    )

    await TokenStore.deleteItem(entry.store, entry.key)
  }
}
