### Title
`ReceivedOutput::read` accepts a claimed deposit with no binding between `offset` and `output.script_pubkey`, letting a reader fabricate unspendable "received" funds - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`Scanner::scan_transaction` produces a `ReceivedOutput` whose `offset` is guaranteed (by construction of the `scripts` map in `Scanner::new`/`register_offset`) to satisfy `output.script_pubkey == p2tr(key + offset*G)` — i.e., the recorded offset actually makes the output spendable by the scanned key. `ReceivedOutput::read`, however, deserializes `offset`, `output`, and `outpoint` from untrusted bytes with no consistency check whatsoever. This is the direct analog of the BondEscalationAccounting bug: a "claim" (here, a reported received output) is credited without verifying the claimant actually contributed/matches the underlying resource — the same "data validation: grant not bound to actual entitlement" class.

### Finding Description
`ReceivedOutput::read` at `networks/bitcoin/src/wallet/mod.rs:122-134` calls `Secp256k1::read_F` for the offset and consensus-decodes a `TxOut` and `OutPoint`, then returns them as a valid `ReceivedOutput`. Nothing checks that:
- `output.script_pubkey` equals `p2tr(key + offset * G)` for the key this output is claimed to belong to,
- `output.script_pubkey` is even a P2TR script at all,
- `offset` is a previously `register_offset`-registered value.

By contrast, the legitimate construction path (`Scanner::scan_transaction`, lines 199-214) only yields a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` returns an offset, which by `register_offset` (lines 180-196) is exactly the scalar satisfying the key-relation. The deserialize path bypasses this invariant entirely, so `serialize`/`read` is not round-trip-safe against a malicious writer: any `(offset, TxOut, OutPoint)` triple is accepted as "funds received."

### Impact Explanation
A party able to feed bytes to `ReceivedOutput::read` can cause the consumer to treat an arbitrary `TxOut` as an output received by the threshold key — e.g., an output whose `script_pubkey` belongs to the attacker, or a fabricated `value`/`outpoint`. The recorded `offset` will not produce a key that controls the real UTXO (or no such UTXO exists), yielding "funds reported received that are not spendable." If this output is subsequently aggregated into a spend transaction, the result is at best a consensus-invalid transaction (inflated input value) and at worst bookkeeping crediting deposits that can never be moved — the same theft-of-claim shape as the report, where one pledge-grant was issued without an actual pledge.

### Likelihood Explanation
Reachable wherever `ReceivedOutput` objects transit over an untrusted channel (coordinator ↔ processor messaging or a deserialized database). `read` is a public API with no documented caller-must-authenticate note comparable to PedPoP's `blame` docs, and unlike `ThresholdKeys::read` (which at least round-trips through `ThresholdKeys::new`/`ThresholdParams::new` validation at `crypto/dkg/src/lib.rs:625-631`), no structural validation runs on the read result. The attacker only needs to control bytes handed to `read`; no threshold collusion, malicious validator, or leaked key is required. Severity: Medium — it corrupts the set of outputs believed spendable, but stealing real funds additionally requires the inflated/foreign output to influence value accounting downstream.

### Recommendation
Bind the deserialized fields to each other. Either:
- Have `read` (or the consumer) re-derive `p2tr_script_buf(key + G*offset)` against the expected group key and reject the `ReceivedOutput` unless it equals `output.script_pubkey`, mirroring the `scripts` membership check `scan_transaction` performs; or
- Restrict `ReceivedOutput` construction to the `Scanner` (private fields with a fallible verifier API such as `ReceivedOutput::verify(&Scanner)`) and mark `read` as trusted-inputs-only if an authenticated channel is genuinely assumed.

Note: I did not locate all call sites of `ReceivedOutput::read` within this search; whether a genuinely untrusted writer feeds it in a given deployment should be confirmed, but the API itself carries no such restriction or warning.

### Proof of Concept
```rust
// Attacker-controlled bytes passed to ReceivedOutput::read.
// `offset` = arbitrary scalar (e.g., ZERO),
// `output` = TxOut { value: huge, script_pubkey: attacker's own P2TR script },
// `outpoint` = any OutPoint (real or fabricated).
let mut bytes = Vec::new();
bytes.extend(Scalar::ZERO.to_bytes());            // offset: not a registered offset
bytes.extend(&serialize(&forged_txout));           // script_pubkey unrelated to `key + 0*G`
bytes.extend(&serialize(&forged_outpoint));
let stolen = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// `stolen` is indistinguishable from a Scanner-produced output:
// value() reports the forged amount, yet no key ever controls `stolen`.
```
