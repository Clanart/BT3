### Title
Relayer reward transfer executed before reward-watermark persisted, allowing repeated treasury payout for the same consensus block span - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
The Pyth report's core broken invariant is: a value used to gate/size an economic outcome (mint supply → voter-weight denominator) can be mutated between the moment it backs an action and the moment that action is settled/finalized, so the same underlying "work" gets counted twice against inconsistent state. The local analog in Hyperbridge is `pallet-consensus-incentives`: the treasury→relayer reward transfer is executed *before* the `LastRewardedHeight` watermark (the value that prevents re-paying for the same block span) is persisted, and the watermark update sits behind a fallible step (`ReputationAsset::mint_into`) whose failure is silently swallowed by the caller.

### Finding Description
`calculate_reward` computes a reward as `(latest_height - baseline) * cost_per_block`, where `baseline` is read from `LastRewardedHeight::<T>::get(state_machine_id)` (falling back to `previous_commitment_height` only the first time): [1](#0-0) 

`process_message` then, in order: transfers `reward` from the treasury to the relayer, deposits an event, mints a `ReputationAsset`, and only afterwards advances `LastRewardedHeight`: [2](#0-1) 

If `T::ReputationAsset::mint_into` returns `Err(_)`, the function returns `Error::<T>::ReputationMintFailed` via `?` *after* the `Currency::transfer` has already succeeded, and *before* `LastRewardedHeight` is mutated. The caller, `on_executed`, discards this error entirely: [3](#0-2) 

Because the watermark never advances when `mint_into` fails, the next `ConsensusMessage` delivered for the same `state_machine_id` recomputes `blocks = latest_height - baseline` against the *same, stale* `baseline`. If `mint_into` fails deterministically for a given relayer/asset configuration (e.g., minimum-balance/existential-deposit requirements on the reputation asset, a frozen asset class, or a value that doesn't satisfy the asset's constraints), every subsequent legitimate consensus delivery for that state machine re-triggers a full transfer for the same (or overlapping) block span — a double payment out of the treasury for work that was already paid for. This is functionally the same broken invariant as the report: the guard value meant to prevent re-crediting (`LastRewardedHeight`, analogous to the burn-adjusted mint supply) is decoupled from the moment the payout is irreversibly committed (the `Currency::transfer`, analogous to the vote being cast against the pre-burn supply).

### Impact Explanation
This is a genuine "loss of funds / double-claim" class issue against the live bounty: treasury funds are transferred out per consensus update, and a stuck reputation-mint step lets the same block-span reward be paid repeatedly without any privileged actor, malicious peer, or compromised prover — a normal relayer submitting valid, honest consensus proofs would trigger it. Each additional payout drains `T::TreasuryAccount` for zero additional real work, and the condition can recur on every future consensus message for the affected state machine, making the drain unbounded until governance intervenes.

### Likelihood Explanation
Requires only that `ReputationAsset::mint_into` fail for a reachable set of parameters (e.g., an account/asset combination that violates ED, freeze list, or supply cap) — no attacker collusion, no relayer misbehavior, no proof forgery. A relayer does not even need to intend this; it can be triggered incidentally by whichever account happens to be recovered from the consensus-message signature. Given `let _ = Self::process_message(...)` explicitly discards the error instead of handling it, this failure mode was not treated as unreachable/impossible by the pallet's own error type (`Error::<T>::ReputationMintFailed` exists precisely because minting can fail).

### Recommendation
Reorder `process_message` so `LastRewardedHeight` is durably advanced (or reward calculation is otherwise made idempotent) before or atomically with the `Currency::transfer`, and make the two operations transactional so that a failure in the reputation mint cannot leave the treasury debit committed while the anti-replay watermark rolls back. Concretely: compute and persist the watermark first (or use `frame_support::storage::with_transaction` / `try_mutate`-style atomicity so a mint failure reverts the transfer too), and do not silently discard `process_message`'s `Result` in `on_executed` — log/handle it so operators can detect stuck reputation minting instead of it silently enabling repeat payouts.

### Proof of Concept
1. Configure `StateMachinesCostPerBlock` for some `state_machine_id` with a non-zero `block_cost`, and configure `ReputationAsset` such that `mint_into` fails for the relevant relayer account (e.g., account below existential deposit for that asset class, or asset temporarily frozen/paused).
2. A relayer submits a valid signed `ConsensusMessage` advancing `latest_commitment_height` for that state machine. `on_executed` recovers the relayer key, calls `process_message`: `Currency::transfer(treasury → relayer, reward)` succeeds; `ReputationAsset::mint_into` fails; `LastRewardedHeight` is never updated; the error is swallowed by `let _ = ...` in `on_executed`.
3. The relayer (or any relayer) submits another valid `ConsensusMessage` for the same `state_machine_id` at the same or a higher height. `calculate_reward` again computes `baseline = LastRewardedHeight::get(...)` — unchanged from step 2 — so `blocks` covers the same span (or more), and `Currency::transfer` pays out again from the treasury for work already compensated in step 2.
4. Repeat for as long as `mint_into` keeps failing for that relayer/state machine, draining the treasury each time a legitimate consensus update is relayed.
