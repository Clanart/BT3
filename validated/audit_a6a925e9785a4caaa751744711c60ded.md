### Title
Webhook shop identity is taken from an unauthenticated header that is not covered by HMAC verification, enabling cross-shop action via a replayed signed webhook - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification` only validates the HMAC of the raw request body [1](#0-0)  but the shop identity used to route/act on the webhook is read from the `X-Shopify-Shop-Domain` header, which is not part of the signed data at all [2](#0-1) . This is structurally the same bug class as the ELFI report: a value that determines "which tenant/vault the action is applied to" is decoupled from the value that was actually authenticated/verified, so an attacker can supply a validly-signed payload but redirect its effect to a different, unrelated shop.

### Finding Description
`verify_request` only checks `hmac_valid?(request.raw_post)` against the app secret [3](#0-2) . The HMAC is computed purely over the body and the shared app secret [1](#0-0) , and the app-level client secret is the same across every shop that has this app installed — Shopify does not bind the HMAC to a specific shop domain, and the `X-Shopify-Shop-Domain` header used by `shop_domain` is not included in the signed content [2](#0-1) .

Downstream generated job handlers trust this header value directly to select which shop record to act on, e.g. the mandatory `app/uninstalled` job looks up and destroys the `Shop` record identified purely by the header-derived `shop_domain`: [4](#0-3) . The same pattern is used for the mandatory privacy jobs (`customers/redact`, `customers/data_request`, `shop/redact`) and is explicitly recommended in the gem's own documentation for custom webhook controllers, where `shop_domain` (the raw header) is passed straight to `perform_later` for job dispatch: [5](#0-4) .

Because a shop installer (or anyone who can trigger a webhook event on their own store, e.g. by installing the app on a free development store) can capture a legitimately-signed `(body, HMAC)` pair from Shopify, and because the header carrying the target shop is unsigned, that attacker can replay the captured body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary victim shop domain. `hmac_valid?` will still pass because it only checks the body against the shared secret [1](#0-0) , and the job will then be dispatched with the attacker-chosen `shop_domain`.

### Impact Explanation
For the mandatory `app/uninstalled` job template, this allows an attacker who is an unrelated merchant of the same app to trigger destruction of a victim's `Shop` record (`shop.destroy`) by replaying their own valid uninstall webhook with a forged shop-domain header [4](#0-3) . For the privacy-redaction job templates, the same technique can trigger customer/shop data redaction flows against a shop the attacker does not control, and for custom `SomeJob.perform_later(shop_domain: shop_domain, ...)` patterns documented by the gem, arbitrary app-specific logic can be invoked in the context of a victim shop domain. This is a cross-shop action triggered by an accepted forged (header) but genuinely signed request, matching the "wrong vault"/wrong-tenant-context bug class from the source report.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimately Shopify-signed webhook delivery (trivially available to anyone who installs the app on any shop, including a free development store, and triggers the relevant event) and to know/guess the victim shop's `.myshopify.com` domain (often discoverable). No merchant/session privilege on the victim shop is required, and the request is unauthenticated from the app's perspective beyond the shared-secret HMAC — which the attacker legitimately possesses for their own shop's traffic. This is realistically exploitable but does require external knowledge of the target domain, so likelihood is moderate rather than trivial.

### Recommendation
Do not trust the `X-Shopify-Shop-Domain` header (or any header/query value) as the tenant selector for privileged or destructive actions unless it can be cryptographically tied to the verified payload. Where feasible, cross-check the header-derived shop against a shop identifier embedded in the verified webhook body, or bind webhook verification to a per-shop secret/session rather than the single app-wide client secret, before using it to look up and mutate shop-scoped records.

### Proof of Concept
1. Install the target app on an attacker-controlled development store; trigger an `app/uninstalled` (or other mandatory) webhook event and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends.
2. Replay the exact same body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with the victim's `victim-shop.myshopify.com`.
3. `WebhookVerification#verify_request` validates HMAC successfully (body/secret unchanged) [3](#0-2) , and the generated job is enqueued with `shop_domain: "victim-shop.myshopify.com"`, causing `Shop.find_by(shopify_domain: "victim-shop.myshopify.com").destroy` (or equivalent redaction logic) to execute against the victim's record [4](#0-3) .

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
