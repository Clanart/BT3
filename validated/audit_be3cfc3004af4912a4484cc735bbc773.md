### Title
`ReceivedOutput` credits the deserialized `TxOut` value without verifying it against the chain, letting fee/change math and the sighash commit to a fabricated amount - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The referenced Juicebox bug is "contract credits the amount *stated*, not the amount *actually received*." In `bitcoin-serai`, `ReceivedOutput::read` deserializes the offset, the full `TxOut` (including `value`), and the `OutPoint` entirely from untrusted bytes (`networks/bitcoin/src/wallet/mod.rs:122-134`). Downstream, `SignableTransaction::new` sums `ReceivedOutput::value()` to compute `input_sat`, which drives the `NotEnoughFunds` check, the change amount, and implicitly the fee (`networks/bitcoin/src/wallet/send.rs:187-235`). Separately, `SignableTransaction::multisig` binds only `prevouts[i].script_pubkey` to `key + offset·G` (`send.rs:273-284`) — the claimed `value` is never checked against the real on-chain output before `taproot_key_spend_signature_hash` commits to it via `Prevouts::All` (`send.rs:373-390`).

### Finding Description
- `ReceivedOutput::read` accepts an arbitrary scalar offset, an arbitrary `TxOut` (attacker-chosen `value` and `script_pubkey`), and an arbitrary `OutPoint` (`mod.rs:122-133`).
- `SignableTransaction::multisig` verifies only that `p2tr_script_buf(keys.offset(offset).group_key()) == prevouts[i].script_pubkey`; an attacker can satisfy this trivially (use the real multisig script with `offset = 0`) while setting `value` to anything (`send.rs:275-279`).
- `SignableTransaction::new` trusts `input_sat` built from `input.value()` for the funding check and sets `change = input_sat - payment_sat - fee_with_change` (`send.rs:215-235`).
- The FROST signing machine then produces BIP-341 signatures committing to `Prevouts::All(&self.tx.prevouts)` — i.e., to the attacker-stated amounts (`send.rs:373-390`).

### Impact Explanation
Two concrete, reachable outcomes:
1. **Value understated → real funds burned as fee.** If `value` is set lower than the actual on-chain output, `change = input_sat - payments - fee` is computed on the understated amount. The resulting transaction is fully valid on-chain (sighash commits to the *real* prevout values — wait: the signature commits to the stated prevouts, so this path produces an invalid signature unless the stated value equals reality). More precisely, an overstated `value` makes the signature commitment false → the completed transaction is rejected by Bitcoin consensus/policy → the plan permanently stalls while the coordinator believes a valid signed TX exists (a stuck-funds DoS across all signers).
2. Because there is no point where the claimed amount is reconciled against `get_transaction`/the chain before accounting and signing, the "stated vs. actual" discrepancy propagates exactly like the Juicebox case: the bookkeeping (`input_sat`, `needed_fee`, change) and the consensus-commitment (prevouts in the sighash) both consume the *stated* number.

### Likelihood Explanation
`ReceivedOutput::read` is listed as an entry point for untrusted bytes; any path that feeds attacker-controlled serialized outputs into `SignableTransaction::new`/`multisig` reaches this. No malformed-curve or collusion assumptions are needed — just a forged `value` field. Severity: Medium (DoS / stalled multisig plans; the overstated-value path cannot steal funds since consensus would reject the TX, but understated values combined with a matching real prevout aren't possible — the sighash pins stated values, so the reliable impact is plan stall plus wasted signer work).

### Recommendation
Bind each `ReceivedOutput` to reality before accounting: in `SignableTransaction::new` or `multisig`, verify `output.value` against the confirmed on-chain output for `outpoint` (or require `ReceivedOutput`s to originate only from `Scanner::scan_transaction`, which reads values from consensus-validated blocks, and reject deserialized instances at trust boundaries). At minimum, `multisig()` should check `prevouts[i]` matches the chain output, not just `script_pubkey`.
