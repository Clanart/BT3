### Title
Cross-transaction metadata overwrite lets an attacker hijack Bitcoin deposit instructions - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` accumulates scanned outputs in `outputs`, but applies the *current transaction’s* presumed origin and Serai instruction data to every accumulated output. Consequently, any later transaction in the same block—including one paying nothing to Serai—can overwrite the instruction attached to an earlier deposit and redirect its resulting Serai-side credit.

### Finding Description
`get_outputs` initializes `outputs` before iterating all non-coinbase transactions, then scans each transaction for recognized vault scripts. [1](#0-0) 

After scanning a transaction, it only skips metadata processing if the cumulative `outputs` vector is empty, rather than tracking whether the current transaction produced a matching output. [2](#0-1) 

It then derives `presumed_origin` from the current transaction’s first input and extracts data from that same transaction. [3](#0-2) 

Finally, it assigns that current-transaction data and origin to every accumulated `Output`, including outputs discovered in earlier transactions. [4](#0-3) 

The extracted data can come from an attacker-controlled `OP_RETURN` output, or from a recognized P2WSH witness pattern. [5](#0-4) 

For `OutputType::External`, `instruction_from_output` SCALE-decodes this mutable `data` as `Shorthand`, converts it into a `RefundableInInstruction`, associates the victim output’s balance with it, and returns it for execution. [6](#0-5) 

### Impact Explanation
An attacker can place a transaction after a victim’s deposit in the same block, include `Shorthand::transfer(None, attacker_serai_address)` in their own transaction, and cause the victim’s `External` output to execute the attacker’s transfer instruction. `InInstruction::Transfer` explicitly names the Serai recipient account, so the victim’s deposited balance can be credited to the attacker instead of the victim’s intended destination. [7](#0-6) 

The attacker can alternatively provide empty or malformed data, erasing the victim’s instruction and changing deposit handling/refund behavior. This is transaction-context confusion rather than merely misleading display text: the attacker-controlled bytes become the parsed instruction for an output they did not create. [8](#0-7) 

### Likelihood Explanation
The attack requires the attacker’s transaction to appear after the victim’s deposit within the same confirmed block. An unprivileged observer can monitor the public mempool, identify a transaction paying the current vault address, broadcast a valid transaction carrying malicious metadata, and repeat attempts when ordering is unfavorable.

No private keys, invalid signatures, malformed Bitcoin transactions, compromised RPC node, or validator misbehavior are required. The principal limitation is block-order contention, making the exploit opportunistic rather than deterministic, but the financial impact justifies treating the defect as High severity.

### Recommendation
Process metadata transaction-locally. Specifically:

- Create a fresh `tx_outputs` vector inside `for tx in &block.txdata[1 ..]`.
- Push only outputs discovered by `scanner.scan_transaction(tx)` into `tx_outputs`.
- Skip metadata extraction when `tx_outputs.is_empty()`.
- Apply the current transaction’s `presumed_origin` and `extract_serai_data(tx)` only to `tx_outputs`.
- Append `tx_outputs` to the block-level result.

A regression test should place `victim_tx` before an unrelated attacker transaction containing a conflicting `OP_RETURN`, then assert the victim output retains its own instruction and origin.

let victim_tx = Transaction {

  output: vec![
    TxOut {
      value: Amount::from_sat(100_000),
      script_pubkey: vault_p2tr_script.clone(),
    },
    TxOut {
      value: Amount::ZERO,

      ),
    },
  ],
  // ...
};

let attacker_tx = Transaction {
  // A valid attacker-controlled input.
  input: vec![attacker_input],
  // No output pays the vault.
  output: vec![
    TxOut {
      value: Amount::ZERO,
      script_pubkey: ScriptBuf::new_op_return(
        PushBytesBuf::try_from(attacker_data.clone()).unwrap(),
      ),
    },
  ],
  // ...
};

let block = Block {
  txdata: vec![coinbase_tx, victim_tx, attacker_tx],
  // ...
};

let outputs = bitcoin.get_outputs(&block, vault_key).await;

// Expected: victim instruction.
// Actual: attacker_data overwrote the earlier victim output.

The failure occurs because the attacker transaction’s scan contributes no new output, yet the pre-existing `outputs` collection remains non-empty, so the attacker transaction’s origin and data are copied into it. [9](#0-8)
