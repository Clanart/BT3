### Title
Out-of-bounds index into `Interpolation::Constant` vector via unvalidated participant index - ([File: crypto/dkg/src/lib.rs])

### Summary
The analog of CVE-2020-19668 (unverified index into an array leading to out-of-bounds access) maps onto `Interpolation::interpolation_factor` in the `dkg` crate. For `Interpolation::Constant(c)`, the code indexes `c[usize::from(u16::from(i) - 1)]` using a `Participant` index, while `ThresholdKeys::new` validates only that `t == n` for the Constant variant — it never checks that `c.len() == n`. If a `ThresholdKeys` constructed (or deserialized via `ThresholdKeys::read`, one of the untrusted-byte entry points) carries a `Constant` vector shorter than `n`, any `view()`/`sign()` call computes an out-of-bounds index and panics. In Rust this is a bounds-checked panic rather than memory corruption, so the impact is availability loss (process abort/crash of the signer), mirroring the medium-severity availability impact of the original report.

### Finding Description
- `crypto/dkg/src/lib.rs:228`: `Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)]` — raw indexing by `i - 1` with no bound check against `c.len()`.
- `crypto/dkg/src/lib.rs:367-374`: `ThresholdKeys::new` requires `t == n` for `Interpolation::Constant`, but performs no `c.len() == n` verification.
- `crypto/dkg/src/lib.rs:463-498`: `view()` validates `included` participants are `<= n` and non-duplicate, then calls `interpolation_factor(self.params().i(), &included)` — so if `c.len() < i <= n`, the index is in-range for the declared parameter set yet out-of-range for the vector.

### Impact Explanation
A panic during `view()`/`interpolation_factor` aborts the signing path. Where `ThresholdKeys` is reconstructed from serialized bytes (`ThresholdKeys::read`) or a `Constant` coefficient vector whose length doesn't match `n`, a malformed structure or inconsistent state produces a crash instead of a clean `DkgError`. On the coordinator/processor signing paths that consume these keys, this is a denial of service against the participant.

### Likelihood Explanation
This requires a `ThresholdKeys` (or `ThresholdParams`-paired `Interpolation::Constant`) whose coefficient vector is shorter than `n`. If `ThresholdKeys::read` deserializes the `Constant` vector length from the byte stream without reconciling it against `n`, the condition is reachable from untrusted bytes. I was not able to fully confirm the exact validation performed inside `ThresholdKeys::read` (serialization code was beyond the sections inspected), so reachability from raw bytes is plausible but not fully proven; absent that path, the bug requires integrator-constructed inconsistent keys, which would downgrade it to a misuse concern rather than an externally reachable analog.

### Recommendation
In `ThresholdKeys::new`, for `Interpolation::Constant(c)` additionally enforce `c.len() == usize::from(params.n())` and return a `DkgError` otherwise. In `interpolation_factor`, prefer `c.get(i - 1)` with an error return so a malformed state can never panic. Ensure any deserialization path (`ThresholdKeys::read`) performs the same length check.

### Proof of Concept
Construct a `ThresholdParams` with `t == n == 3`, `i = Participant(3)`, and `Interpolation::Constant(vec![F::ONE, F::ONE])` (length 2 < n). `ThresholdKeys::new` accepts it (t == n check passes; shares count check is on `verification_shares`, not `c`). Calling `.view(vec![P(1), P(2), P(3)])` reaches `interpolation_factor(i = 3)`, computing `c[2]` on a 2-element vector → index-out-of-bounds panic. Equivalently, if `ThresholdKeys::read` accepts a short Constant vector from serialized bytes, feeding such bytes to `read`/`view` triggers the same panic from untrusted input.
