I have enough evidence to write up the finding on the Tron `IntentGatewayV2` escrow accounting.

### Title
Escrow accounting in the Tron `IntentGatewayV2` uses requested amounts instead of actually-received balances, allowing cross-order fund drain with fee-on-transfer/rebasing TRC20 tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder` credits the shared `_orders[commitment][token]` escrow ledger with the fee-reduced *requested* amount (`reducedInputs[i].amount`, derived from `order.inputs[i].amount`), never checking what the contract actually received via `safeTransferFrom`/`ICallDispatcher` sweep. The mainline EVM `IntentGatewayV2.sol` was hardened against exactly this class of bug (balance-before/after measurement, see `evm/src/apps/IntentGatewayV2.sol:198-298` and the `FeeOnTransferToken` regression tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2251-2498`), but the Tron variant was never updated to match, leaving the pre-fix accounting model in place.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the non-predispatch escrow path is: [1](#0-0) 

`order.inputs[i].amount` (the amount the *user requested* be escrowed) is transferred via `safeTransferFrom`, and then `_orders[commitment][token] += reducedInputs[i].amount` credits the ledger with a value derived from that same requested amount — not from any measurement of the token balance the gateway actually gained. `reducedInputs[i].amount` is only ever `originalAmount - protocolFee` computed from `order.inputs[i].amount`: [2](#0-1) 

All withdrawal paths (`withdraw`, called from `onAccept` for `RedeemEscrow`/`RefundEscrow`, from same-chain cancel, and from `onGetResponse`) trust this ledger unconditionally and push out the *escrowed* amount with no balance check: [3](#0-2) 

The predispatch path has the identical gap: it checks `balance < requiredAmount` on the `CallDispatcher`'s balance, but still credits escrow with `reducedInputs[i].amount` (the pre-fee, requested value) rather than the dust-corrected `balance`: [4](#0-3) 

This is structurally the same broken invariant as the `MetaManager.unclaimedRewards` report: an accounting variable is maintained in one unit ("amount requested/notified") while the underlying asset actually moves in a different unit ("amount actually received/transferable", which can drift due to token-level behavior — TRC20 fee-on-transfer, rebasing, or any transfer-hook token). Because `_orders` is a shared ledger across *all* orders/tokens in the single gateway contract, and the contract's real TRC20 balance for that token is the only thing that can ever be paid out, any order placed with a token that delivers less than `amount` on transfer creates a permanent deficit: the contract's real balance for that token is now less than the sum of all `_orders[*][token]` entries for it. The first orders to withdraw succeed fully; whichever order withdraws when the pool is exhausted has its `transfer` fail or, on a lenient/silently-failing token, the accounting mapping is decremented and the order marked filled even though the beneficiary received nothing (fund loss) — while other legitimate escrows have effectively been drained to plug the gap.

### Impact Explanation
This produces a straightforward "loss/lock of funds via wrong-beneficiary/wrong-amount accounting" — squarely inside the required impact list. Because `_orders` is a single shared per-`(commitment, token)` mapping backed by one pooled TRC20 balance per token across the whole gateway, a shortfall introduced by *one* order's fee-on-transfer/rebasing token deduction is not isolated to that order: it silently consumes token balance that other users' orders are relying on for their own escrow accounting, since `withdraw()` never checks its own real balance against what it is about to pay out. Depending on ordering, this leads either to some user's legitimate escrow being unpayable (locked/lost funds) or to a `transfer` call that returns `false`/reverts inconsistently depending on the specific TRC20 implementation.

### Likelihood Explanation
Reachable by any unprivileged user calling the public `placeOrder` entrypoint with any TRC20 input token that is not a strict fixed-1:1 transfer (fee-on-transfer, deflationary/rebasing, or any token with a transfer hook that can reduce the delivered amount) — no relayer, prover, governance, or admin action is required, and no malicious counterparty is needed. The mainline EVM contract's own test suite (`IntentGatewayV2SameChainTest.sol`) demonstrates such tokens are an explicitly anticipated real-world case for this exact contract family, and Tron/TRC20 tokens frequently implement non-standard transfer semantics, making the trigger condition realistic rather than exotic.

### Recommendation
Port the balance-before/after fix already present in `evm/src/apps/IntentGatewayV2.sol::placeOrder` (measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom`, and credit `_orders` with the actual delta) into `evm/tron/contracts/apps/IntentGatewayV2.sol` for both the direct-transfer and predispatch-sweep paths, and add the equivalent `FeeOnTransferToken` regression tests that already protect the mainline EVM contract.

### Proof of Concept
1. Register/deploy a TRC20 token `T` with a 1% transfer fee (mirrors `FeeOnTransferToken` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2501-2547`).
2. User `A` calls `placeOrder` with `inputs = [{token: T, amount: 1000e18}]`. The gateway's actual `T` balance increases by only `990e18` (fee burned/retained by the token), but `_orders[commitmentA][T]` is credited with `~1000e18 - protocolFee` (per `evm/tron/contracts/apps/IntentGatewayV2.sol:456-457`).
3. Repeat for user `B` with a second order, `commitmentB`, same token `T`. Gateway's real `T` balance is now `~1980e18`, but the sum of `_orders[commitmentA][T] + _orders[commitmentB][T]` is `~2000e18` (minus protocol fees) — a permanent `~20e18` deficit versus what the ledger promises.
4. Solver fills `commitmentA` in full; `withdraw()` (`evm/tron/contracts/apps/IntentGatewayV2.sol:682-705`) pays out the full ledgered amount from the shared `T` balance, leaving less than `commitmentB` needs.
5. When `commitmentB` is filled/refunded, `withdraw()` attempts to transfer `_orders[commitmentB][T]`, which now exceeds the gateway's remaining `T` balance — the transfer reverts (order stuck, funds locked) or, for a token with an unusual/non-reverting failure mode, silently fails while `_orders[commitmentB][T]` is decremented and the order is marked filled, leaving the intended beneficiary with less than escrowed while `_filled[commitmentB]` is set (fund loss).
