### Title
Attacker-controlled FROST preprocess forces aggregate nonce `R` to the point at infinity, panicking Bitcoin `Hram`/`x()` during `sign` (DoS) - ([File: networks/bitcoin/src/crypto.rs])

### Summary
The Bitcoin-specific BIP-340 `Hram` implementation calls `x(key)`, which panics via `.expect("point at infinity")` whenever the point it is handed is the identity. The point handed to `hram` is `nonce_sums[0][0]` — the aggregate group nonce `R = Σ (D_l + rho_l · E_l)` across all included signers. While `Curve::read_G` rejects individual identity points inside `read_preprocess`, nothing prevents the *sum* of a malicious participant's commitments from cancelling the rest of the aggregate to the identity. A signer who contributes a crafted preprocess (bytes fed to `SignMachine::read_preprocess` and then `sign`) deterministically crashes the honest signer's process when `Algorithm::sign_share` evaluates `Hram::hram`.

### Finding Description
- `x(key)` in `networks/bitcoin/src/crypto.rs:13-16` unconditionally `.expect()`s that the point has an x-coordinate, i.e., is not the point at infinity.
- `Hram::hram` (`crypto.rs:59-73`) calls `x(R)` and `x(A)` on the aggregate nonce `R` and group key `A`.
- `IetfSchnorr::sign_share` (`crypto/frost/src/algorithm.rs:208`) computes `c = H::hram(&nonce_sums[0][0], &params.group_key(), msg)`, where `nonce_sums` is `B.nonces(&nonces)` produced in `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:383`) by summing every participant's preprocess commitments weighted by their binding factors `rho_l`.
- Remote preprocesses are read via `read_preprocess` (`sign.rs:276-281`) → `Commitments::read`, which uses `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`). That rejects identity for each individual commitment point, but the aggregate `R = Σ D_l + rho_l·E_l` is never checked for identity before `hram` is invoked.
- `sign` only validates participant indexes (`sign.rs:297-310`) and calls `preprocesses.remove(l).unwrap()` on keys it already enumerated — the commitment *values* are unconstrained beyond per-point non-identity.
- A malicious participant who learns the other preprocesses (a rushing adversary, or simply the last to broadcast — preprocesses are exchanged before `sign`) can compute all `rho_l` offline, since `rho` is a public deterministic function of `group_key`, `hash_msg(msg)`, and the commitments transcript (`sign.rs:361-371`). They then choose their own `(D_a, E_a)` so that `D_a + rho_a·E_a = -(Σ_{l≠a} (D_l + rho_l·E_l))`, forcing `R` to identity. Any honest signer then panics inside `sign` → `sign_share` → `hram` → `x()`.
- The documentation comment at `crypto.rs:78-83` claims the infinity case has "negligible probability ... even with malicious participants present"; that reasoning conflates random probability with an adversary who can algebraically cancel the sum, so the panic is deterministically reachable, not negligible.

### Impact Explanation
A single crafted preprocess message causes an unhandled panic (abort of the signing operation / process, depending on panic strategy) in every honest signer that includes the attacker in the signing set. This is a direct analog of the CVE's NULL-deref DoS: attacker-supplied bytes reaching a parsing/processing path cause a crash. It can be repeated to indefinitely stall threshold signing of Bitcoin transactions (denial of service on fund movement), at no cost to the attacker beyond sending malformed protocol messages.

### Likelihood Explanation
Requires the attacker to be a participant whose preprocess is included in a signing session — precisely the untrusted input surface `read_preprocess`/`sign` is exposed to (the reachable-inputs list includes preprocess bytes and `sign`). The attack is deterministic once the attacker sees the other preprocesses, needs no secret knowledge, and the preconditions (signer accepts a preprocess set including the attacker) are the normal operating mode of the protocol. Medium severity, matching the report's classification.

### Recommendation
- In `IetfSchnorr::sign_share`/`verify`/`verify_share` (or in `B.nonces`/the `sign` path), check `nonce_sums[0][0].is_identity()` and return `Err(FrostError)`/filter `None` instead of letting `x()` panic; alternatively make `x`/`x_only`/`hram` return `Option`/`Result` and propagate.
- More robustly, reject an aggregate `R` equal to identity in `AlgorithmSignMachine::sign` (FROST `complete`/`verify` path also indexes `nonces[0][0]` at `algorithm.rs:215,226`), so the fault is attributable before `hram` runs.

### Proof of Concept
Conceptual (requires a running signing session):
1. Honest signer and attacker each run `AlgorithmMachine::<Secp256k1, Schnorr>::preprocess`, producing preprocesses `(D_h, E_h)` and pending `(D_a, E_a)`.
2. Attacker collects all honest preprocesses, computes `rho_l` for each participant via the `FROST_rho` transcript (`group_key`, `hash_msg(msg)`, `hash_commitments(transcript)`).
3. Attacker picks arbitrary `E_a` (non-identity, passes `read_G`) and sets `D_a = -(E_a·rho_a) - Σ_{l≠a}(D_l + rho_l·E_l)`, then serializes `(D_a, E_a)` as its preprocess.
4. Honest signer calls `read_preprocess` (succeeds — both points are non-identity) then `sign(commitments, msg)`.
5. `B.nonces` yields `nonce_sums[0][0] = identity`; `sign_share` calls `Hram::hram`, which calls `x(&identity)` → `.expect("point at infinity")` panics (`crypto.rs:15`).

Relevant code: `x`/`x_only` panic sites (`networks/bitcoin/src/crypto.rs:13-23`), `Hram::hram` (`crypto.rs:59-73`), `sign_share` invocation (`crypto/frost/src/algorithm.rs:208`), aggregate `R` construction (`crypto/frost/src/sign.rs:322-383`), and per-point-only identity rejection (`crypto/frost/src/curve/mod.rs:125-131`).
