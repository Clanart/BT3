### Title
Cross-chain `WithdrawalRequest.tokens` amounts are attacker/solver-controlled and not validated against escrowed bookkeeping in `_withdraw` - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`_withdraw` releases escrow strictly according to the `amount` field carried in the incoming cross-chain `WithdrawalRequest` (built on the *destination* chain from `order.inputs`, the nominal, pre-fee, user-declared amount) rather than the actual per-token amount recorded in `_orders[commitment][token]` (the *source* chain's own bookkeeping, which reflects real deposits after protocol fees/fee-on-transfer deduction). This mirrors the lien report's core defect: an ownership/settlement action (`RedeemEscrow`/`RefundEscrow`) crosses a trust boundary (destination → source) without forcing the receiving side's ledger fields to be recomputed/verified from local state, instead trusting the remote-supplied number.

### Finding Description
`_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:140-146`) builds the settlement message using `tokens: order.inputs` — the raw order-declared amounts — not the amounts actually escrowed in `_orders` on the source chain (which can differ due to protocol fee deduction at `placeOrder` time, and, as covered by the fee-on-transfer tests in `IntentGatewayV2SameChainTest.sol`, due to actual-received-vs-declared mismatches for non-standard tokens).

When this `WithdrawalRequest` arrives at `onAccept` on the source chain and is passed to `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:391-410`):
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
...
IERC20(token).safeTransfer(beneficiary, amount);
```
the code only checks `escrowed != 0` (non-zero), not `amount <= escrowed`. `amount` comes straight from the cross-chain message body, which was populated from `order.inputs` on the *destination* chain — a value that is part of the order struct supplied by whichever address called `fillOrder`/`cancelOrder`, not re-derived from the source chain's own recorded escrow. Because Solidity 0.8's underflow check is the only guard, an amount larger than what was actually escrowed reverts the whole withdrawal (locking funds), while an amount smaller than what was escrowed silently strands the remainder in `_orders[commitment][token]` with no path to reclaim it (the commitment is already `_filled` after the first `RedeemEscrow`/`RefundEscrow`, so a second withdrawal message for the residual amount can never be produced by the normal flow).

### Impact Explanation
This falls in the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" pivot. A mismatch between the destination-supplied settlement amount and the source-chain's true escrow bookkeeping causes either (a) permanent fund lock (order under-escrowed relative to `order.inputs`, e.g., fee-on-transfer tokens or a future protocol-fee change between order placement and settlement) or (b) an inconsistent, unreclaimable residual balance left in the `_orders` ledger that can never be swept back to a beneficiary through the normal order lifecycle, since `_filled[commitment]` is already set. This is a direct analog of the lien-transfer defect: state on the receiving side of a cross-domain ownership/settlement transfer is not kept honest with the ledger that actually backs it.

### Likelihood Explanation
Any solver or user who triggers a legitimate cross-chain fill or cancellation already controls the `Order` struct's `inputs` field value (it is part of the commitment, and its numeric value is set at `placeOrder` time by the user, then echoed unmodified through `_fillCrossChain`/`_cancelFromDest`). No malicious relayer, prover, or admin is needed — the mismatch is triggered purely by normal usage whenever the escrowed amount recorded via `_orders` (post protocol-fee reduction, or reduced due to a fee-on-transfer token as already exercised by the FeeOnTransferToken tests) differs from `order.inputs`, which is the exact value forwarded in `WithdrawalRequest.tokens`.

### Recommendation
`_withdraw` must not trust the `amount` field of an incoming cross-chain `WithdrawalRequest` for state mutation. Either derive the amount to transfer from the source chain's own `_orders[commitment][token]` ledger directly (ignoring/asserting equality with the message-supplied amount), or explicitly bound-check `amount <= escrowed` and only decrement/transfer the intersection, emitting an event and leaving a reclaimable path for any residual rather than silently stranding it.

### Proof of Concept
1. Place a cross-chain order for `100` USDC using a fee-on-transfer variant, or with `protocolFeeBps > 0`, so the actual `_orders[commitment][USDC]` escrow on the source chain is `98` (after fees) while `order.inputs[0].amount` still equals `100`.
2. Fill the order on the destination chain; `_fillCrossChain` dispatches `WithdrawalRequest{ tokens: order.inputs (100), beneficiary: solver }`.
3. On the source chain, `onAccept` → `_withdraw` reads `escrowed = 98`, then executes `_orders[commitment][token] = 98 - 100`, which underflows and reverts under Solidity 0.8 checked arithmetic — the settlement message can never be applied, permanently locking the escrowed `98` USDC (the order is already unfillable elsewhere since it's the canonical settlement path).     /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
