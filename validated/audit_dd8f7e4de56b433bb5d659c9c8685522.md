### Title
Stale global sign-in state read after `await` lets a slow/malicious OAuth endpoint bind its account to a concurrent, unrelated sign-in session - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
`SignInStore.resolveOAuthRequest` validates the pending OAuth `state` (CSRF token) against `this.state` *before* awaiting two network calls, but resolves the flow by re-reading the mutable `this.state` field *after* those awaits instead of using the value it already validated. If the user starts a second sign-in (e.g., cancels a slow Enterprise sign-in and signs into GitHub.com instead) while the first OAuth exchange is still in flight, the delayed response completes against whatever session is *currently* active, not the one it was validated for. This mirrors the reentrancy report's core flaw: a check is performed on shared mutable state, an external/attacker-influenced call happens, and afterward the code trusts the *current* value of that shared state rather than the value it validated, letting an attacker-controlled response smuggle its own object into an unrelated, already-validated operation.

### Finding Description
`resolveOAuthRequest` is invoked from the deep-link/protocol handler pipeline (`app/src/main-process/main.ts` → `parseAppURL` → `dispatchURLAction` → `_resolveOAuthRequest` → `SignInStore.resolveOAuthRequest`) whenever the `x-github-client://oauth?code=...&state=...` URL is opened. [1](#0-0) 

```
public async resolveOAuthRequest(action: IOAuthAction) {
  if (!this.state || this.state.kind !== SignInStep.Authentication) return
  if (!this.state.oauthState) return
  if (this.state.oauthState.state !== action.state) { ...return }

  const { endpoint } = this.state
  const token = await requestOAuthToken(endpoint, action.code)      // await #1 (network, endpoint-controlled)

  if (token) {
    const account = await fetchUser(endpoint, token)                // await #2 (network, endpoint-controlled)
    this.state.oauthState.onAuthCompleted(account)                  // BUG: re-reads mutable `this.state`
  } else {
    this.state.oauthState.onAuthError(new Error(...))
  }
}
```

The CSRF check at line 341 validates `action.state` against `this.state.oauthState.state`, but that check is performed on `this.state` *before* the two `await`s. `this.state` is a single shared, mutable field on `SignInStore`, updated any time the user starts a new sign-in (`beginDotComSignIn`, `beginEnterpriseSignIn`, `authenticateWithBrowser`) or cancels one (`reset`). At line 353, the code does **not** use a value captured before the awaits — it dereferences `this.state.oauthState` again, live, after the network round-trips. `onAuthCompleted`/`onAuthError` are simply the `resolve`/`reject` functions of the `Promise` created in `authenticateWithBrowser`: [2](#0-1) 

If a *second* sign-in flow is started (targeting a different endpoint, e.g. github.com) while the first flow's OAuth exchange is still pending (e.g., because the first endpoint — attacker-controlled or MITM'd GitHub Enterprise server — deliberately stalls its `/login/oauth/access_token` response), `this.state` now points to the second session's `oauthState`. When the first (slow/attacker) endpoint finally answers, `resolveOAuthRequest` calls `this.state.oauthState.onAuthCompleted(account)` — i.e., it resolves the **second** session's promise with an `Account` object whose token/identity was produced entirely by the **first**, attacker-controlled endpoint. `authenticateWithBrowser`'s `.then()` handler only checks that `this.state.kind === SignInStep.Authentication` (true, because the second session is still authenticating) — it has no way to know the resolved account did not actually come from that session's own OAuth exchange — and calls `this.emitAuthenticate(account)`, which persists the account. [3](#0-2) 

Existing guards do not stop this path: the CSRF `state` check only guarantees that whoever fired the deep link knew the token, which the malicious/slow server itself learned when Desktop opened `getOAuthAuthorizationURL(endpoint, csrfToken)` for it — the server round-trips that exact `state` back in its own delayed callback, so the check at line 341 passes for its own (first) session validly. The bug is that by the time the response is *used*, the surrounding session it gets attached to has changed. Nothing re-validates that `this.state.oauthState` is still the same `oauthState` object that was checked at the top of the function (e.g. via captured local reference or a session/generation token compared post-await, as `authenticateWithBrowser`'s own `.catch()` handler does with `this.state.oauthState?.state === csrfToken` at line 320-322 — notably the success path at line 304-317 lacks this same re-check).

### Impact Explanation
This is an unauthorized-OAuth/account-binding issue: an attacker-controlled GitHub Enterprise endpoint (or a network MITM/proxy sitting on that endpoint) can cause its own account object — with its own attacker-issued token and endpoint — to be silently injected into the user's Desktop account list as the result of a completely different, legitimate sign-in attempt (e.g., the user's intended GitHub.com login). This corrupts which credentials the app associates with which provider/session and can mislead the user into operating (browsing, pushing, or authorizing actions) as an account they did not intend to add, or with credentials scoped to an endpoint they didn't choose.

### Likelihood Explanation
Requires the user to (a) have an Enterprise/custom endpoint pointed at a server the attacker controls or can proxy/delay (a realistic "attacker controls a git remote/proxy response" scenario for Enterprise users on untrusted networks or malicious/compromised GHES instances), and (b) start a second sign-in while the first is still pending — a plausible real-world action when a sign-in "hangs" and the user retries with a different account/endpoint. No local access, malware, or leaked credentials are needed; the trigger is purely a slow/malicious server response to a deep-link-driven OAuth callback.

### Recommendation
Capture the validated session reference (the specific `oauthState` object, or its `resultCallback`/`resolve`/`reject` closures) into a local variable at the top of `resolveOAuthRequest`, before the `await`s, and use that captured reference — not `this.state` — when calling `onAuthCompleted`/`onAuthError`. Additionally/alternatively, re-validate after each `await` that `this.state.oauthState === capturedOauthState` (identity or token equality) before invoking the completion callback, mirroring the check already present in `authenticateWithBrowser`'s `.catch()` handler but missing from its `.then()` success path and from `resolveOAuthRequest`.

### Proof of Concept
1. User adds a GitHub Enterprise account pointing at `https://evil-ghes.example` (attacker-controlled or MITM'd).
2. User clicks "Continue with browser" for that endpoint → `authenticateWithBrowser()` sets `this.state.oauthState = { state: csrfA, endpoint: evil-ghes, onAuthCompleted: resolveA, onAuthError: rejectA }` and opens the browser.
3. `evil-ghes` receives the OAuth authorize request, but instead of promptly redirecting back, it holds the connection / delays sending the `x-github-client://oauth?code=...&state=csrfA` callback.
4. User gives up waiting, cancels, and instead clicks "Sign in to GitHub.com" → `beginDotComSignIn()` + `authenticateWithBrowser()` runs again, setting `this.state.oauthState = { state: csrfB, endpoint: github.com, onAuthCompleted: resolveB, onAuthError: rejectB }`.
5. `evil-ghes` now finally fires its deep link with `code=attackerCode&state=csrfA`. `resolveOAuthRequest` is called: the CSRF check at line 341 compares against `this.state.oauthState.state`, which is now `csrfB` — wait, this would fail the check since `this.state` has already moved to session B by the time the deep link arrives.

Correction to the PoC: because the CSRF check itself reads `this.state` live, the race window that matters is *between* the check (line 341) and the resolution (line 353) — i.e., session B must start **after** line 341 passes for session A but **before** line 353 executes. Concretely:
1. `evil-ghes` sends its callback while session A (`csrfA`) is still current, passing the check at line 341.
2. Execution suspends at `await requestOAuthToken(...)` / `await fetchUser(...)`.
3. While suspended, the user cancels/starts a new sign-in to github.com, replacing `this.state.oauthState` with session B (`csrfB`, `resolveB`).
4. `evil-ghes`'s (attacker-controlled) `/login/oauth/access_token` and `/user` endpoints return, so `requestOAuthToken`/`fetchUser` resolve with an attacker-crafted token/account.
5. Line 353 executes: `this.state.oauthState.onAuthCompleted(account)` now calls `resolveB` (session B's resolver) with the attacker's account object, causing `emitAuthenticate` to add the attacker's Enterprise account into the user's account list as if it were the result of the GitHub.com sign-in. [4](#0-3)

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
