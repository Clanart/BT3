### Title
Unbounded-length offer decoding allows spend-triggered CPU/memory exhaustion in `Offer.from_bech32()` - (File: `chia/wallet/trading/offer.py`)

### Summary
`chia/wallet/trading/offer.py::Offer.from_bech32()` calls `bech32_decode(offer_bech32, max_length=len(offer_bech32))`, which explicitly *overrides* the library's normal 90-character safety cap (`bech32_decode`'s default `max_length: int = 90` in `chia/util/bech32m.py`) with the length of the attacker-supplied string itself. This removes any upper bound on the size of data that will be character-validated, checksum-verified, and bit-converted before any cost/size accounting occurs — the same bug class as the Axios `data:` URI issue, where `fromDataURI()` decoded an attacker-controlled payload with no size ceiling before any `maxContentLength`/`maxBodyLength` check could apply.

### Finding Description
`Offer.from_bech32()`:
```python
@classmethod
def from_bech32(cls, offer_bech32: str) -> Offer:
    _hrpgot, data = bech32_decode(offer_bech32, max_length=len(offer_bech32))
    if data is None:
        raise ValueError("Invalid Offer")
    decoded = convertbits(list(data), 5, 8, False)
    decoded_bytes = bytes(decoded)
    return cls.try_offer_decompression(decoded_bytes)
``` [1](#0-0) 

Compare with `bech32_decode`'s intended safety bound:
```python
def bech32_decode(bech: str, max_length: int = 90) -> tuple[str | None, list[int] | None]:
    """Validate a Bech32 string, and determine HRP and data."""
    bech = bech.strip()
    if (any(ord(x) < 33 or ord(x) > 126 for x in bech)) or (bech.lower() != bech and bech.upper() != bech):
        return (None, None)
``` [2](#0-1) 

Every character of the input is scanned (`any(ord(x)...)`), lower/upper-cased, and character-set validated before the length is even checked against the caller-supplied bound — and because `Offer.from_bech32` sets `max_length=len(offer_bech32)`, that bound is always satisfied regardless of input size. `convertbits()` then performs a bit-by-bit re-packing over the entire decoded data with no cap:
```python
def convertbits(data: Iterable[int], frombits: int, tobits: int, pad: bool = True) -> list[int]:
    ...
    for value in data:
        ...
``` [3](#0-2) 

Only *after* this full decode does `try_offer_decompression()` run, which falls into `decompress_object_with_puzzles()` — and that function does cap its own *output* at 6 MiB via `zlib.decompressobj().decompress(blob, max_length=6*1024*1024)` [4](#0-3) . However, that cap only protects the zlib-decompression step; it does nothing to bound the cost of the preceding bech32 character-scan/checksum/`convertbits` pass over the raw attacker-supplied string, nor does it apply at all if the payload is not actually zlib-compressed (`try_offer_decompression` falls back to plain `Offer.from_bytes` on `TypeError`, meaning arbitrarily large uncompressed "offer" blobs are equally accepted for full processing).

This is reachable from every consumer of an offer string as raw untrusted input, notably:
- `WalletRpcApi.take_offer()` / `TakeOffer.parsed_offer` [5](#0-4) 
- `WalletRpcApi.check_offer_validity()` [6](#0-5) 
- `GetOfferSummary.parsed_offer` [7](#0-6) 
- CLI `take_offer` command, which reads an offer file or raw hex/bech32 blob supplied by a counterparty and immediately calls `Offer.from_bech32(offer_hex)` [8](#0-7) 

In all these cases the "offer" is untrusted data received from another party (an offer file shared out-of-band, or a value pasted/loaded by a wallet operator) — analogous to axios's caller-controlled `data:` URI being decoded fully before any protective limit check.

### Impact Explanation
An attacker (any offer counterparty) can craft an extremely large bech32-encoded "offer" string (megabytes to gigabytes) and get it processed by:
1. A victim wallet's RPC endpoint (`take_offer`, `check_offer_validity`, `get_offer_summary`) if the wallet operator is induced to submit it, or
2. The `chia wallet take_offer` CLI tool, which reads the entire file/blob into memory and passes it straight to `Offer.from_bech32()`.

Because `max_length` is set to the string's own length, there is no defensive cap analogous to axios's `maxContentLength`/`maxBodyLength`; the full string is character-scanned, checksum-verified, and bit-repacked in Python before any zlib size limit is reached. This causes excessive CPU consumption (O(n) Python-level character loops over the entire attacker-supplied buffer, potentially many megabytes) and memory allocation (`convertbits` materializes the fully expanded byte list), which can stall or crash the wallet process handling the request — a spend/transaction-processing halt for that wallet, consistent with the "spend-triggered transaction-processing halt" impact class defined in scope.

### Likelihood Explanation
High likelihood of reachability: offers are explicitly designed to be shared with untrusted counterparties and pasted/loaded by wallet users or automated services (e.g., offer-board bots, marketplaces) without any pre-validation of size. No authentication bypass or privileged access is required — an attacker only needs to get a victim wallet (human or automated) to call `take_offer`, `check_offer_validity`, or the offer-summary RPC/CLI paths with a maliciously oversized offer string.

### Recommendation
- In `Offer.from_bech32()`, do not pass `max_length=len(offer_bech32)`; instead enforce a fixed, sane upper bound (e.g., consistent with realistic offer sizes, on the order of tens of KB before compression) and reject longer strings immediately, before calling `bech32_decode`/`convertbits`.
- Add an explicit length check on the raw string (and/or byte size) at the entry points (`Offer.from_bech32`, CLI `take_offer`, and the `TakeOffer`/`GetOfferSummary`/`CheckOfferValidity` RPC handlers) prior to any decoding work.
- Ensure the non-compressed fallback path in `Offer.try_offer_decompression()` also enforces a byte-size ceiling before calling `Offer.from_bytes()`.

### Proof of Concept
```python
from chia.wallet.trading.offer import Offer
from chia.util.bech32m import bech32_encode, convertbits

# Build an oversized, syntactically-valid-looking bech32 "offer" payload
huge_payload = b"\x00" * (200 * 1024 * 1024)  # 200 MB
data = convertbits(list(huge_payload), 8, 5)
bech32_str = bech32_encode("offer", data)  # multi-hundred-MB string

# This call performs an O(n) character scan/lower-upper check, bech32
# checksum verification, and full convertbits() re-packing over the
# entire 200MB+ string with NO length limit (max_length is set to
# len(offer_bech32) inside Offer.from_bech32), before any decompression
# size cap is ever reached.
Offer.from_bech32(bech32_str)
```
Running this against a wallet RPC's `take_offer`/`check_offer_validity`/`get_offer_summary` endpoint (or the CLI `chia wallet take_offer -f <file>` with such a payload as the "offer file") causes large, uncontrolled CPU and memory usage in the wallet process, mirroring the axios `data:` URI DoS pattern of decoding attacker-supplied data fully before any size limit is applied.

def bech32_decode(bech: str, max_length: int = 90) -> tuple[str | None, list[int] | None]:
    """Validate a Bech32 string, and determine HRP and data."""
    bech = bech.strip()
    if (any(ord(x) < 33 or ord(x) > 126 for x in bech)) or (bech.lower() != bech and bech.upper() != bech):
        return (None, None)
    bech = bech.lower()
    pos = bech.rfind("1")
    if pos < 1 or pos + 7 > len(bech) or len(bech) > max_length:
        return (None, None)

```python
def convertbits(data: Iterable[int], frombits: int, tobits: int, pad: bool = True) -> list[int]:
    """General power-of-2 base conversion."""
    acc = 0
    bits = 0
    ret = []
    maxv = (1 << tobits) - 1
    max_acc = (1 << (frombits + tobits - 1)) - 1
    for value in data:
        if value < 0 or (value >> frombits):
            raise ValueError("Invalid Value")
        acc = ((acc << frombits) | value) & max_acc
        bits += frombits
        while bits >= tobits:
            bits -= tobits
            ret.append((acc >> bits) & maxv)
    if pad:
        if bits:
            ret.append((acc << (tobits - bits)) & maxv)
    elif bits >= frombits or ((acc << (tobits - bits)) & maxv):
        raise ValueError("Invalid bits")
    return ret
```
