### Title
NUL-byte desync in `createLogParser` causes commit metadata (SHA, author, body) to be misattributed to the wrong commit row - (File: `app/src/lib/git/git-delimiter-parser.ts`)

### Summary
`createLogParser` builds `git log --format=...` output by joining field format specifiers with the literal `%x00` (NUL) separator and then re-splits the raw stdout buffer on `\0` in fixed-size groups of `keys.length` [1](#0-0) . This assumes every field's *content* never itself contains a NUL byte, but that assumption is never validated. Git does not guarantee commit message bytes are free of NUL — a repository whose commits are crafted directly with plumbing (`git hash-object`/`git commit-tree`) rather than via `git commit` can embed raw `\0` bytes in the commit body used for `%b`. `getCommits` uses this parser for `sha`, `shortSha`, `summary`, `body`, `author`, `committer`, `parents`, `trailers`, and `refs` fields [2](#0-1) .

### Finding Description
Because the parser's field alignment for every subsequent record depends on each record contributing exactly one `\0`-delimited element, a single attacker-crafted commit whose message/body contains an embedded NUL byte will produce extra split segments. `parse()` walks the flat `records` array in fixed strides of `keys.length` [3](#0-2) , so once the stride is off by even one element, every following commit's fields shift by one position: what was `sha` for commit N+1 becomes the `shortSha` field, `body` becomes `author`, etc., for the remainder of the parsed batch. There is no length/format validation of individual field content (analogous to the missing length check on L2 log data in the zkSync report — all downstream data trusts the field boundaries without re-verifying them), so Desktop silently accepts and displays the desynced result. `getCommits` then trustingly builds `Commit` objects straight from these shifted buffer slices [4](#0-3) .

### Impact Explanation
The `Commit.sha` used to populate the History list row is what's passed to `revertCommit` (`git revert <sha>`) [5](#0-4) , `_resetToCommit`, "Create Tag" (`onCreateTag?.(commit.sha)`) [6](#0-5) , cherry-pick, and "View on GitHub". If the SHA field associated with a displayed commit message/author is desynced to belong to a *different* commit than what the user visually inspected, a user who reviews commit N's message/diff in the History pane and then chooses "Revert this commit" or "Create Tag…" or "Reset to this commit" would have the operation applied against the wrong commit object (silently — no error is raised, since the shifted data still parses as valid-looking strings). This is a silent corruption of what the user commits/pushes/operates on, triggered purely by cloning/fetching an attacker-controlled repository — matching the valid-impact class in the task (attacker controls a cloned/fetched repository, result is silent corruption of what the user commits/pushes).

### Likelihood Explanation
Requires an attacker to publish or otherwise get the victim to clone/fetch a repository containing at least one commit object whose message was crafted with a raw NUL byte via low-level git plumbing (not through the ordinary `git commit` CLI, which strips NULs, but achievable by anyone constructing objects directly with `git hash-object -w --stdin` / `git commit-tree`). No admin rights, local access, or social engineering beyond "clone this repo" is needed, satisfying the "attacker controls a cloned/fetched repository" criterion. The likelihood of a user noticing the desync is low because the shifted content is still plausible-looking commit metadata; the corruption is not raised as an error anywhere in `getCommits` or `createLogParser`.

### Recommendation
Add explicit validation in `createLogParser.parse` that the total number of records is an exact multiple of `keys.length` (throwing/logging on mismatch, akin to enforcing a fixed/checked length as the zkSync fix did with `L2_TO_L1_LOGS_COMMITMENT_BYTES`), and additionally reject/escape any field values that themselves cannot legally contain the NUL delimiter (e.g., detect embedded `\0` in `%b`/`%s`/trailers before trusting field boundaries), rather than silently degrading to a garbage parse of the remainder of the batch.

### Proof of Concept
1. In a scratch git repo, craft a commit with an embedded NUL in the message using plumbing:
   ```
   printf 'evil message\0trailing' | git hash-object -w --stdin -t blob   # not directly usable for commit msg
   # more directly: use git commit-tree with a message containing \0 via a temp file
   printf 'legit-looking summary\x00forged-shift' > /tmp/msg
   TREE=$(git write-tree)
   COMMIT=$(git commit-tree $TREE -p HEAD -F /tmp/msg)
   git update-ref refs/heads/main $COMMIT
   ```
2. Push/host this repo, have the victim clone it in GitHub Desktop.
3. Open History; observe (via debugging `createLogParser.parse` output, or by comparing `git log` directly with the app's rendered SHA/author for the commit following the crafted one) that fields for the subsequent commit row are shifted — its displayed `sha` no longer matches what `git log --format=%H` reports for that commit.
4. Right-click that row and choose "Revert Changes in Commit" / "Create Tag…" — the git operation executes against the desynced `commit.sha`, not the commit the user visually selected.

export function createLogParser<T extends Record<string, string>>(fields: T) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%x00')
  const formatArgs = ['-z', `--format=${format}`]

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }
