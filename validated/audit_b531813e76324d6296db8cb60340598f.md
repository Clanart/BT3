### Title
Dust-value outputs are reported as received funds and accepted as transaction inputs, inflating apparent balance and burning fees - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class in the external report is "an attacker manipulates a reported balance upward, causing the protocol to overvalue an asset/share." The Serai analog lives in `bitcoin-serai`'s wallet: `Scanner::scan_transaction` reports every output paying to a registered script as a `ReceivedOutput` with no lower bound on `value`, and `SignableTransaction::new` enforces the `DUST` minimum only on *payments*, never on *inputs*. An unprivileged attacker can therefore send sub-dust outputs to a multisig address, which are reported to integrators as received funds, and — if the integrator consumes them — each such input costs more in transaction fees (≈57.5 vbytes per Taproot input × `fee_per_vbyte`) than it contributes, destroying value and inflating the fee actually paid beyond `needed_fee`-proportional accounting.

### Finding Description
`Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) pushes a `ReceivedOutput` for every `tx.output` whose `script_pubkey` is in `self.scripts`, unconditionally:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
}
```

There is no `output.value >= DUST` (or any) check. `ReceivedOutput::value()` then reports the attacker's chosen amount as received balance (`mod.rs:116-118`).

On the spending side, `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`) validates `*amount < DUST` only for `payments` (lines 165-169). Inputs are summed verbatim: `input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum()` (line 175) and every input is added to `tx_ins` (lines 177-185). `calculate_weight_vbytes` charges each input a fixed Taproot-input weight with a 64-byte witness signature (lines 71-83), so `needed_fee = fee_per_vbyte * vbytes` grows per input regardless of the input's value (line 206).

Additionally, `ReceivedOutput::read` (`mod.rs:122-134`) — a listed untrusted-bytes sink — deserializes `offset`, `TxOut` (including `value`), and `outpoint` with no consistency check between the claimed `output`/`value` and the real on-chain UTXO at `outpoint`. A fabricated `ReceivedOutput` inflates `input_sat` exactly like the inflated Curve `balances()` in the original report: the change calculation `input_sat - payment_sat - fee_with_change` (line 228) and `fee()` (lines 138-141) are computed from attacker-influenced value fields.

### Impact Explanation
1. **Reported-funds inflation**: any party can create arbitrarily many sub-dust or even zero-value outputs to a scanned script. `scan_transaction` reports them as `ReceivedOutput`s; any integrator summing `value()` as "balance received" sees attacker-inflated funds (direct analog of inflated `CURVE_POOL.balances()`).
2. **Fee destruction**: if these dust inputs are fed to `SignableTransaction::new`, each one adds ~57.5 vbytes to the transaction while contributing < 546 sats. With fee rates above ~9.5 sat/vB, each dust input destroys value net-net; the transaction still passes `NotEnoughFunds` and is signed. The attacker pays only the sub-dust output value to inflict a larger fee cost.
3. **Malformed-input DoS**: a `ReceivedOutput` supplied via `ReceivedOutput::read` (or simply stale) that doesn't correspond to a real UTXO produces a fully-signed but consensus-invalid transaction — the multisig burns a signing round on an unbroadcastable tx.

### Likelihood Explanation
The attacker needs only to send Bitcoin transactions to a known multisig address — fully permissionless and cheap (a few hundred sats per poisoned output). Whether the dust is actually spent depends on the integrator's input-selection policy, but nothing in the in-scope API surfaces the distinction: `scan_transaction`/`scan_block` return dust identically to real outputs, and `SignableTransaction::new` accepts the whole `Vec<ReceivedOutput>` without inspection. Notably, the processor-side consumer does apply an external `>= N::DUST` filter, showing the value floor was recognized as necessary but was not enforced in the wallet library itself, where the `DUST` constant is defined and already applied to payments.

### Recommendation
- In `Scanner::scan_transaction` (or on `ReceivedOutput` construction), skip outputs with `output.value.to_sat() < DUST` — or at minimum expose a filter so dust is distinguishable from spendable balance.
- In `SignableTransaction::new`, reject or warn on inputs whose value is below `DUST`, since they can never be economically spent under the same policy the library applies to payments.
- Document that `ReceivedOutput::read` performs no outpoint-to-output consistency check, and have consumers verify `output`/`value` against the actual UTXO set before signing.

### Proof of Concept
```rust
// Attacker crafts a tx paying `dust_amt` sats (< 546) to the multisig script.
let dust_amt = 100u64;
let tx = Transaction {
  version: Version(2),
  lock_time: LockTime::ZERO,
  input: vec![/* any funding input */],
  output: vec![TxOut {
    value: Amount::from_sat(dust_amt),
    script_pubkey: p2tr_script_buf(group_key).unwrap(), // registered script
  }],
};

// Scanner reports it as received funds — no value check.
let outputs = scanner.scan_transaction(&tx);
assert_eq!(outputs.len(), 1);
assert_eq!(outputs[0].value(), 100); // attacker-inflated "balance"

// SignableTransaction accepts it as an input; DUST is only checked on payments.
// needed_fee grows by ~57.5 vbytes * fee_per_vbyte while input_sat grows by 100.
let tx = SignableTransaction::new(
  vec![outputs[0].clone(), real_input],
  &payments,
  change,
  None,
  fee_per_vbyte,
).unwrap();
// fee() = input_sat - sum(outputs) now includes an input that cost more to
// spend than it contributed.
```
