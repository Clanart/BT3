## Finding

### Title
Payout tx `OP_RETURN` operator attribution is unauthenticated, letting anyone front a withdrawal and credit reimbursement rights to an arbitrary operator - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `payout_tx` that fronts a Citrea withdrawal only binds the withdrawing user's `SIGHASH_SINGLE|ANYONECANPAY` signature to input 0 / output 0. The `OP_RETURN` output that declares which operator "fronted" the withdrawal (and is therefore entitled to reimbursement from the move-to-vault N-of-N funds) is not covered by that signature, nor by any operator or N-of-N signature. Any unprivileged party who observes the user's public withdrawal signature (committed on Citrea) can construct and broadcast this transaction themselves, supplying their own funding input, while writing an arbitrary operator's x-only pubkey into the `OP_RETURN`. The bridge blindly trusts this on-chain `OP_RETURN` value to decide which operator gets reimbursed.

### Finding Description
`create_payout_txhandler` builds the payout transaction with:
- Input 0: the withdrawal UTXO, satisfied by the user's `SinglePlusAnyoneCanPay` signature.
- Output 0: user payout (covered by the SIGHASH_SINGLE commitment).
- Output 1: anchor.
- Output 2: `OP_RETURN` containing `operator_xonly_pk` — **not covered by any signature**. [1](#0-0) 

`SIGHASH_SINGLE` only commits to the output at the same index as the signed input (index 0); `ANYONECANPAY` explicitly allows arbitrary extra inputs to be added by anyone. This means the `OP_RETURN` (index 2) and the extra funding input are completely outside the scope of the user's signature — nothing in the protocol requires the entity that supplies the funding input to be the operator named in the `OP_RETURN`.

`parse_withdrawal_sig_params` only enforces that the *user's* signature has the `SinglePlusAnyoneCanPay` sighash type; it enforces nothing about `OP_RETURN` contents or which party funds the transaction: [2](#0-1) 

Once such a transaction confirms, the verifier's block-processing logic reads the `OP_RETURN` and unconditionally attributes the payout to whatever operator key is found there, storing it as `payout_payer_operator_xonly_pk`: [3](#0-2) 

That DB value is then trusted end-to-end:
- `PayoutCheckerTask` looks for "unhandled payouts" keyed by the operator's own xonly pubkey and automatically starts the reimbursement flow when it matches: [4](#0-3) 
- `validate_payer_is_operator` / `handle_finalized_payout` only check that the DB-recorded payer matches `self.signer.xonly_public_key`, i.e. trust the same attacker-controllable field, before proceeding to claim the kickoff/reimburse transactions from the N-of-N move-to-vault funds: [5](#0-4) [6](#0-5) 

Nowhere in this chain is there a check that the operator named in `OP_RETURN` actually supplied the funding input(s) of the payout transaction. The custody binding that should hold is:

`funds fronted by operator X in payout_tx` == `reimbursement paid to operator X from move-to-vault N-of-N funds`

An unprivileged attacker (or a colluding operator) can break this equality by broadcasting a self-funded payout transaction that names a different operator's key in `OP_RETURN`, causing that operator's automation to claim a reimbursement it never actually funded — landing squarely in the "operator reimbursed for a payout it never funded" Critical impact category.

### Impact Explanation
Any observer of the user's public withdrawal signature (available once the withdrawal is registered on Citrea) can:
1. Front the user's payout themselves with their own BTC (satisfying `SinglePlusAnyoneCanPay` + `ANYONECANPAY` extra input rules).
2. Write an arbitrary, real operator's `xonly_pk` into the unsigned `OP_RETURN` output.
3. Broadcast the transaction to Bitcoin.

The bridge's verifier automatically records that operator as the payer, and that operator's own `PayoutCheckerTask`/reimbursement automation will proceed to claim a `Reimburse` transaction from the N-of-N move-to-vault funds for a payout it never actually made. This breaks the "operator credited versus the party that paid" custody binding and directly causes the bridge/N-of-N vault to pay out BTC to an operator with no matching funds it fronted — a Critical impact per the scan's rubric.

### Likelihood Explanation
No privileged role, key, or majority is required. The attacker only needs:
- The publicly committed withdrawal signature (`SinglePlusAnyoneCanPay`) associated with a pending Citrea withdrawal.
- Enough of their own BTC to fund the payout amount (same cost any legitimate fronting operator would pay).
- Standard Bitcoin transaction-construction/broadcast capability — no interaction with any verifier, operator, or aggregator RPC is required, since the transaction is fully self-contained and can be relayed directly to the Bitcoin network.

This makes the attack straightforward for any unprivileged actor motivated to frame/benefit an operator (e.g. a colluding operator funding its own reimbursement through an intermediary, or an attacker seeking to disrupt correct payer attribution and the honest funder's ability to reclaim reimbursement).

### Recommendation
Bind the `OP_RETURN` operator-attribution output to the same signature (or an additional one) that authorizes the payout, e.g. require an operator (or N-of-N) signature over the full transaction including the `OP_RETURN` output, or otherwise cryptographically tie the funding input(s) to the declared operator key so that only the operator that actually supplies the payout funds can be credited as the payer.

### Proof of Concept
1. Observe a pending Citrea withdrawal and its published `WithdrawParams` (`input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`) — these are committed on Citrea and thus public.
2. Build a payout transaction as `create_payout_txhandler` does: input 0 = withdrawal UTXO with the user's `SinglePlusAnyoneCanPay` signature and required output 0; add an additional input from the attacker's own wallet to cover `output_amount`; set the `OP_RETURN` output to the x-only pubkey of any chosen (real) operator.
3. Sign the attacker's own added input with the attacker's own key (per standard `ANYONECANPAY` semantics) and broadcast the transaction to Bitcoin.
4. Once confirmed, `update_finalized_payouts` (`core/src/verifier.rs:2311-2350`) records the chosen operator as `payout_payer_operator_xonly_pk` for this withdrawal.
5. That operator's `PayoutCheckerTask` (`core/src/task/payout_checker.rs:39-79`) treats it as its own unhandled payout and automatically drives the kickoff/reimburse flow (`core/src/operator.rs:839-860`, `1687-1729`), claiming reimbursement from the N-of-N move-to-vault funds — despite that operator never having funded the payout.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

#[allow(clippy::result_large_err)]
pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }

    let input_outpoint: OutPoint = params
        .input_outpoint
        .ok_or_else(error::input_ended_prematurely)?
        .try_into()?;

    let users_intent_script_pubkey = ScriptBuf::from_bytes(params.output_script_pubkey);

    Ok((
        params.withdrawal_id,
        input_signature,
        input_outpoint,
        users_intent_script_pubkey,
        Amount::from_sat(params.output_amount),
    ))
}

        tracing::info!(

            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
