### Title
Embedded NUL byte in commit message desynchronizes record-based `git log` parser, causing misattributed SHA/parents in commit history - (File: app/src/lib/git/git-delimiter-parser.ts)

### Summary
`createLogParser.parse` splits the entire `git log -z --format=...` output on `\0` and reconstructs commit records purely by counting `keys.length`-sized chunks [1](#0-0) . This design assumes each commit contributes exactly `keys.length` NUL-delimited fields. `%s` (`summary`) and `%b` (`body`) are populated from the raw commit message stored in the git object, which — unlike ref/branch names — is not restricted from containing literal NUL bytes. If a crafted commit object contains a raw NUL inside its message, `splitBuffer` (used for the `Buffer` code path in `getCommits`) will treat it as an extra delimiter [2](#0-1) , shifting the field-to-key mapping for every subsequent commit for the remainder of the buffer.

### Finding Description
`getCommits` in `app/src/lib/git/log.ts` invokes `git log` with `-z` and a `%x00`-joined `--format` string, then calls `parse(result.stdout)` on the raw `Buffer` output [3](#0-2) . The parser has no concept of record boundaries other than counting fixed-size groups of NUL-separated tokens: it advances `i` by `keys.length` each loop iteration and blindly assigns `records[i + ix]` to each key [4](#0-3) .

Git commit messages are stored as raw byte content in the object's content section (a length-prefixed blob, not a NUL-terminated C string at the object-storage layer), so it is possible to construct a commit object containing a literal `\0` byte inside the free-form message body via low-level plumbing (e.g., `git hash-object -w --stdin -t commit` with crafted content, followed by `git update-ref`). Git's default configuration does not enforce strict object validation on `fetch`/`clone` (`transfer.fsckObjects` / `fetch.fsckObjects` are off by default, and even when checked, `nulInCommit` is a `warn`-level fsck message by default rather than a hard reject, for backward-compatibility with legacy git implementations). No `fsck` options are configured anywhere in Desktop's git invocation code, confirmed by the absence of any `fsck` references in the codebase. This means a malicious remote/repository can plausibly deliver such an object to a victim's local repository via clone or fetch without Desktop or git rejecting it.

If `%s`/`%b`/trailers text preserves an embedded NUL byte verbatim when written to stdout by `git log`'s pretty-printer (which operates on length-tracked buffers rather than NUL-terminated strings), that extra `\0` becomes indistinguishable from the intentional `%x00` field separators once the whole buffer is split. The result: one extra "phantom" record is introduced starting at the commit containing the malformed field, and every fixed-stride slice computed afterward (`records[i + ix]`) is shifted by one position, misassigning `sha`, `parents`, `refs`, etc., for that commit and all commits parsed after it in the same invocation.

### Impact Explanation
The scoped consequence is that `getCommits`/`getCommit` (consumed throughout Desktop's history, blame, and commit-detail UI) could display incorrect `sha`, `parents`, or `refs` for a commit — attributing another commit's identity/parent graph to the wrong entry in the UI. This is a display-layer integrity issue (silent misattribution in the commit log), not a memory-safety or code-execution bug, and it does not by itself cause the user to commit or push incorrect content — the bounty's "Valid Impact" list requires code execution, out-of-repo file access, credential exfiltration, OAuth/account-binding issues, sandbox/IPC escape, or corruption of what is actually committed/pushed. Misaligned *display* of history metadata sits at the edge of that list; it could escalate to a real issue only if a user takes a git action (e.g., reset/cherry-pick/revert) based on the misattributed SHA shown in the UI, which is not demonstrated here and would depend on additional UI-level trust in the parsed SHA for destructive actions.

### Likelihood Explanation
Requires the victim to fetch/clone a malicious repository whose maintainer has hand-crafted a commit object with an embedded NUL byte via low-level plumbing commands, and requires that git's own fsck defaults do not intercept the object (plausible given `nulInCommit` is a warning, not an error, by default, and Desktop performs no explicit fsck hardening). This is a somewhat exotic but attacker-feasible object-crafting technique; it does not require any unnatural user interaction beyond viewing history of an already-cloned malicious repo.

### Recommendation
Make the record parser resilient to unexpected/extra NUL bytes: use an unambiguous multi-byte or contextual record terminator instead of relying on exact chunk counting (e.g., emit a distinguishable per-commit terminator sequence, or validate/escape field content for embedded NULs before parsing), and add bounds/sanity checks (e.g., verifying `sha`/`parents` fields match expected hex-SHA shape) so a misaligned parse is detected and rejected rather than silently accepted.

export function splitBuffer(buffer: Buffer, delimiter: string): Buffer[] {
  const result = []
  let start = 0
  let index = buffer.indexOf(delimiter, start)
  while (index !== -1) {
    result.push(buffer.subarray(start, index))
    start = index + delimiter.length
    index = buffer.indexOf(delimiter, start)
  }
  if (start <= buffer.length) {
    result.push(buffer.subarray(start))
  }
  return result
}
