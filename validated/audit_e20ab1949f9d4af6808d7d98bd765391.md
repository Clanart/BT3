### Title
`ReceivedOutput::read` accepts an offset/script_pubkey pair with no binding, producing an output record that crashes `Output::key()` or is unspendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The kernel bug creates a debugfs entry unconditionally, so reading it dereferences a `ttm_resource_manager` that was never allocated — the *accessor assumes the resource exists*. The analog in Serai is `ReceivedOutput`: `Scanner::scan_transaction`/`register_offset` guarantee the `offset` field corresponds to `output.script_pubkey` via the `scripts` map, but `ReceivedOutput::read` deserializes `offset`, `TxOut`, and `OutPoint` from raw bytes with no check that `p2tr_script_buf(key + offset*G) == output.script_pubkey`. When the processor later dereferences the record in `Output::key()` (`processor/src/networks/bitcoin.rs:112`), it `assert!(script.is_p2tr())` and unwraps the last script instruction — a panic if the output's script isn't P2TR, mirroring the crash-on-read; and for a P2TR script bound to a *different* offset, `key()` silently returns `x_only_key - offset*G`, i.e., a key that does not match the registered spend key.

### Finding Description
- `Scanner::register_offset` builds `scripts: HashMap<ScriptBuf, Scalar>` where each stored offset is exactly the scalar such that `p2tr_script_buf(self.key + offset*G)` equals the key of the map entry (`networks/bitcoin/src/wallet/mod.rs:180-196`). `scan_transaction` only constructs a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` hits, so every output it emits has a consistent (offset, script) pair (`mod.rs:205-211`).
- `ReceivedOutput::read` (`mod.rs:122-134`) reads `Secp256k1::read_F` for the offset and `TxOut::consensus_decode` for the output independently. Nothing verifies that the script inside `output` is P2TR or that it equals `p2tr_script_buf(scanner_key + offset*G)`. This is the same missing check as the CVE: a handle to a resource is created without confirming the resource it names was allocated/bound.
- The dereference happens in `Output::key()` (`processor/src/networks/bitcoin.rs:112-122`): `assert!(script.is_p2tr())`, then `script.instructions_minimal().last().unwrap().unwrap()`, then `Secp256k1::read_G(...) - GENERATOR * self.output.offset()`. For a non-P2TR `script_pubkey` this panics; for a P2TR script whose registered offset differs from the deserialized one, it yields a "spend key" that was never registered, so the scheduler will try to sign with `key + offset` for an offset that doesn't open the output.
- `Output::read` (`processor/src/networks/bitcoin.rs:145-166`) wraps `ReceivedOutput::read` inside `plan`/scheduler deserialization paths (`processor/src/plan.rs:186-188`, `processor/src/multisigs/scheduler/utxo.rs:92-97`), which is how malformed bytes reach `key()`.

### Impact Explanation
Two concrete outcomes, both matching "funds reported received that are not spendable" / crash-on-access:
1. Non-P2TR `script_pubkey` in the deserialized `TxOut` → `assert!(script.is_p2tr())` panics inside `Output::key()`, crashing the processor while handling a recorded output.
2. P2TR `script_pubkey` inconsistent with the stored `offset` → `key()` computes `script_key - offset*G`, a group key for which the multisig's actual spend scalar (`key_share + real_offset`) does not exist; the output is reported as received yet can never be signed for.

### Likelihood Explanation
The scanner path itself cannot produce the inconsistency (the map enforces it), so exploitation requires feeding crafted bytes into `ReceivedOutput::read`/`Output::read` rather than sending a Bitcoin transaction — i.e., corrupted or injected serialized output data reaching the processor's deserialization sinks listed in scope. It does not require a validator key, collusion, or a broken transport, only untrusted bytes in the documented `read` path.

### Recommendation
In `ReceivedOutput::read`, or in the processor-side `Output::read`, validate the binding before constructing the object: reject outputs where `!output.script_pubkey.is_p2tr()`, and verify `p2tr_script_buf(scanner_key + GENERATOR * offset) == Some(output.script_pubkey)` (or equivalently that the script is present in the scanner's `scripts` map under that offset). This is the direct analog of the kernel fix — only expose the entry when the corresponding resource exists.

### Proof of Concept
```rust
// networks/bitcoin context: craft a ReceivedOutput whose offset does not
// correspond to its script_pubkey, then feed it to ReceivedOutput::read.

let mut buf = vec![];
// offset = 1 (valid scalar)
buf.extend(Scalar::ONE.to_bytes());
// A TxOut whose script_pubkey is NOT P2TR (e.g., OP_RETURN / bare script)
let output = TxOut {
  value: Amount::from_sat(1000),
  script_pubkey: ScriptBuf::new_op_return(&[0u8; 8]),
};
buf.extend(bitcoin::consensus::encode::serialize(&output));
// Any outpoint
buf.extend(bitcoin::consensus::encode::serialize(&OutPoint::null()));

let received = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// received.output.script_pubkey is not P2TR and was never in scanner.scripts

// Processor path (processor/src/networks/bitcoin.rs:112):
//   Output::key() -> assert!(script.is_p2tr())  => panic
// Variant B: use a P2TR script registered under a different offset ->
//   key() returns script_key - 1*G, a key nobody can sign for.
```

Confidence caveat: I verified `Scanner`/`ReceivedOutput` semantics in `networks/bitcoin/src/wallet/mod.rs` and the dereference in `processor/src/networks/bitcoin.rs`; I could not fully trace every caller that feeds network-controlled bytes into these `read` functions beyond the plan/scheduler deserialization paths cited, so reachability rests on the serialized-output path (disk/scheduler data) rather than raw mempool scanning.
