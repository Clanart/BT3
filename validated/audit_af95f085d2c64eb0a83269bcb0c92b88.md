## Analog Found

### Title
`resolveWithin()`'s containment check uses a raw string prefix comparison instead of a path-boundary comparison, allowing a sibling directory to satisfy the "inside repository" invariant - (File: app/src/lib/path.ts)

### Summary
The Solidity report's root cause is a check that validates the wrong relationship between two values (`check.value >= valueToCheck` instead of `valueToCheck >= check.value`), silently inverting an intended invariant. The equivalent class of bug in GitHub Desktop is `_resolveWithin()`'s final containment test, which asserts a path is "inside" a root directory using `realResolved.startsWith(realRoot)` — a raw string-prefix comparison rather than a path-segment-boundary comparison. This mis-implements the stated invariant ("resolved path must reside *underneath*, not merely be *textually prefixed by*, the root") and is reused by multiple callers, including the Copilot AI conflict-resolution write path, as the sole gate against writing/reading files outside the repository.

### Finding Description
`_resolveWithin()` is documented to guarantee that a resolved path "reside[s] at, or underneath" `rootPath`, returning `null` otherwise: [1](#0-0) 

The actual check is:
```
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`startsWith` performs a character-level string comparison with no trailing path separator. This means a sibling directory whose name is textually prefixed by the root's name (e.g. root `/Users/victim/Documents/GitHub/repo` vs. sibling `/Users/victim/Documents/GitHub/repo-secrets`) will incorrectly satisfy the containment check, because `"...repo-secrets/x".startsWith("...repo")` is `true` even though `repo-secrets` is not underneath `repo`. This is structurally the same defect class as the Solidity report: the code implements a check that looks correct in isolation but validates the wrong relationship between the two operands (string-prefix equality vs. actual directory-tree containment), silently breaking the invariant every caller relies on.

This helper is consumed by the Copilot AI merge-conflict-resolution feature without any additional absolute-path guard:
- `copilot-conflict-context.ts` calls `resolveWithin(workingDirectory, file.path)` to read the on-disk conflicted file before sending it to the model, guarding only against `null` (which the flawed prefix check can fail to return for a crafted, prefix-colliding target): [3](#0-2) 
- `app-store.ts` calls `resolveWithin(repository.path, resolution.path)` and then unconditionally **writes** the model's resolved content to the resulting path: [4](#0-3) 

By contrast, the deep-link handler (`dispatcher.ts`) additionally checks `isAbsolute(filepath)` before calling `resolveWithin`, which happens to shield that one call site from the specific "absolute-segment" trigger of this bug: [5](#0-4) 
No equivalent `isAbsolute()` pre-check exists before the two Copilot call sites, so they depend entirely on the flawed `startsWith` comparison for containment safety.

The existing regression tests for `resolveWithin` cover `..`-traversal and symlink-escape scenarios but do not cover the sibling-directory prefix-collision case, so this gap is untested: [6](#0-5) 

### Impact Explanation
If an attacker can influence the `pathSegments` value passed into `resolveWithin` for the Copilot flow such that `Path.resolve(root, segment)` yields an absolute path outside the repository but string-prefixed by the repository's own path (e.g. via a same-named sibling clone directory, a symlinked/mounted directory tree with a colliding prefix, or platform path quirks), the containment check would wrongly pass. In `app-store.ts` this leads to `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` writing AI-resolved file content outside the intended repository, corrupting a file the user did not intend to modify (silent corruption of what the user commits). In `copilot-conflict-context.ts` the analogous read path could leak file contents from outside the repository into the request sent to Copilot.

### Likelihood Explanation
This is a Medium/Low-confidence finding on reachability: to trigger the bypass, an attacker needs `resolution.path`/`file.path` to resolve (via `Path.resolve`) to an absolute path outside `repository.path`/`workingDirectory` that also happens to share the root directory's name as a string prefix. Git working-directory file paths are normally relative and validated elsewhere (`validateResolutionPaths` restricts Copilot's returned paths to the set of expected conflicted files), which reduces — but, given the underlying library defect, does not eliminate — the risk if any future caller reuses `resolveWithin` without the same `isAbsolute()` discipline used in `dispatcher.ts`. I was not able to fully confirm within the available tool budget whether `file.path`/`resolution.path` can ever contain an absolute-looking string (e.g. via crafted submodule/UNC-style names from a malicious cloned repository); this would need further investigation of the git status/porcelain parsing code before treating this as a fully proven exploit chain.

### Recommendation
Fix `_resolveWithin()`'s containment test to check path-segment boundaries rather than a raw string prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Additionally, add an `isAbsolute()` guard before both Copilot call sites (`copilot-conflict-context.ts`, `app-store.ts`), mirroring the existing guard in `dispatcher.ts`, and add a regression test for the sibling-directory prefix-collision case analogous to the existing symlink-escape tests.

### Proof of Concept
```ts
import { resolveWithin } from './app/src/lib/path'

// root: /tmp/repo
// sibling: /tmp/repo-secrets/secret.txt  (attacker/incidentally-named sibling dir)
const result = await resolveWithin('/tmp/repo', '/tmp/repo-secrets/secret.txt')
// Expected: null (outside root)
// Actual (due to startsWith): '/tmp/repo-secrets/secret.txt' — containment check passes
```
Wire this same `pathSegments` value through `app-store.ts`'s Copilot conflict-resolution `writeFile` call to demonstrate an out-of-repository file write once an absolute, prefix-colliding path can be supplied as `resolution.path`.
