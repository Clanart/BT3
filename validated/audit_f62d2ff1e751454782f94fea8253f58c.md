### Title
`SchnorrAggregate::read` allocates an unbounded `Vec` from an attacker-controlled `u32` element count — ([File: crypto/schnorr/src/aggregate.rs])

### Summary
`SchnorrAggregate::read` deserializes a `u32` count and then pushes that many group elements (`C::read_G`) into a `Vec` with no upper bound. An unprivileged party who can get a peer to deserialize an aggregate signature (the listed reachable `read` / `verify` surface) can send a serialized blob claiming up to ~4.3 billion `R` points; the parser will keep allocating and ingesting points with no maximum-size check. This is the same bug class as GHSA-g76f-gjfx-4rpr (unbounded message size → resource exhaustion), and unlike comparable readers elsewhere in Serai — which enforce `MAX_LIBP2P_REQRES_MESSAGE_SIZE` in `coordinator/src/p2p.rs` and `TRANSACTION_SIZE_LIMIT` in `coordinator/src/tributary/transaction.rs` — no cap exists here. [1](#0-0) 

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, `SchnorrAggregate::read` reads a little-endian `u32` length and loops `Rs.push(C::read_G(reader)?)`:

- Line 78-79: `len` is read as a raw `u32` — attacker-controlled, up to `u32::MAX`.
- Line 82-85: the loop performs `C::read_G(reader)` `len` times, growing `Rs` (`Vec<C::G>`) with geometric reallocation. There is no check such as `if len > MAX` comparable to `coordinator/src/p2p.rs:264` (`len > MAX_LIBP2P_REQRES_MESSAGE_SIZE`) or `coordinator/src/tributary/transaction.rs:286` (`commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT`).

The `verify` side is not the bound: `verify` early-returns if `Rs.len() != keys_and_challenges.len()`, but by then the giant `Vec` has already been allocated and populated during `read`. `read` itself also succeeds regardless of the trailing `s` value, so a huge allocation occurs before any semantic validation. ### Impact Explanation
An unprivileged remote party supplying serialized bytes to a code path that calls `SchnorrAggregate::read` (e.g., any serialized aggregate arriving over the network/queue and deserialized on the in-scope crates' behalf) forces allocation proportional to the declared count. With `len = u32::MAX` and a stream of validly encoded points (32 bytes each for Ristretto-class groups), the reader will consume tens of GB of input and heap before hitting EOF — there is no fixed ceiling, so a large but finite message is fully absorbed. This is memory/CPU denial of service reachable purely from untrusted bytes, matching CWE-770 (allocation of resources without limits or throttling).

### Likelihood Explanation
Likelihood is moderate: exploitation requires a reachable path where an attacker controls the serialized bytes handed to `SchnorrAggregate::read` — the rule set explicitly lists `SchnorrSignature`-family `read`/`verify` APIs as untrusted-input surface. `read_G` enforces canonical point encodings, so the attacker must transmit real encodable bytes (32 bytes per element); the amplification is bounded by the bytes actually sent, but there is no protocol-level message-size limit compensating for this inside the deserializer itself — the attacker's message size is the resource consumed, exactly the Vert.x pattern. It is a pure DoS with no secret leakage, hence Medium, not higher.

### Recommendation
Enforce a maximum element count (or total serialized byte budget) in `SchnorrAggregate::read` before the allocation loop, mirroring `MAX_LIBP2P_REQRES_MESSAGE_SIZE`/`TRANSACTION_SIZE_LIMIT` — e.g., reject `len` above a constant proportional to the maximum plausible aggregation set (protocol participant counts are `u16`-bounded elsewhere, so a bound on the order of `u16::MAX` elements is already generous), and/or pre-validate `len` against the remaining stream length before pushing any elements.

```rust
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ristretto;

// Serialize a header claiming u32::MAX R points, followed by as many
// canonically-encoded points as bandwidth allows.
let mut bytes = u32::MAX.to_le_bytes().to_vec();
let one_R = <Ristretto as Ciphersuite>::generator().to_bytes(); // valid encoding
for _ in 0..1_000_000 {
    bytes.extend_from_slice(one_R.as_ref());
}
// SchnorrAggregate::<Ristretto>::read(&mut Cursor::new(bytes))
//   -> allocates/grows a Vec per read_G with no size cap;
//      memory grows linearly with attacker-supplied bytes, unbounded by design.
```

```rust
  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }
```
