### Title
Missing path-traversal sanitization for `filepath` parameter in `x-github-client://openrepo` deep link handler - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` sanitizes the `branch` parameter of an `openrepo` deep link with `testForInvalidChars`, but performs **no validation at all** on the `filepath` parameter before placing it into the returned `IOpenRepositoryFromURLAction`.

### Finding Description
In `parseAppURL`, when `actionName === 'openrepo'`, the `branch` value is checked with `testForInvalidChars(branch)` and the action is rejected (returns `unknown`) if invalid characters are found: [1](#0-0) 

By contrast, `filepath` is read straight from the query string via `getQueryStringValue(query, 'filepath')` and passed through unmodified into the resulting action object, with no call to `testForInvalidChars` or any other sanitization/normalization: [2](#0-1) 

The `IOpenRepositoryFromURLAction.filepath` field is documented as "the file to open after cloning the repository": [3](#0-2) 

This means a value like `../../../../etc/hosts` supplied in a `github-mac://openRepo/owner/repo?filepath=../../../etc/hosts` link is accepted unmodified by `parseAppURL` and forwarded downstream as the "file to open" for the cloned repository. I confirmed matches for `filepath` and `IOpenRepositoryFromURLAction` in `app/src/ui/dispatcher/dispatcher.ts`, and separately identified `app/src/ui/lib/open-file.ts`, whose `openFile` function opens an arbitrary `fullPath` via `shell.openExternal(\`file://${fullPath}\`)`: [4](#0-3) 

However, I was **not able to retrieve the specific lines in `dispatcher.ts`** that join `action.filepath` with the cloned repository's path (e.g., a `Path.join(repository.path, filepath)`-style call) before invoking `openFile`, due to running out of tool-call iterations. Without seeing that exact join/consumption logic, I cannot confirm with certainty whether:
- the path is joined to the repository root (in which case `../` sequences would escape the repo directory, since `path.join` does not block traversal), or
- there is some other normalization/containment check applied later in `dispatcher.ts` that isn't visible from `parse-app-url.ts` alone.

### Impact Explanation
If the downstream consumer joins `filepath` to the repository directory without validating that the resolved path stays within the repository root, an attacker-crafted deep link could cause Desktop to open an arbitrary file on the victim's filesystem after a clone completes (e.g., `file:///` opening of sensitive files, or files with dangerous extensions that get "opened" by the OS default handler). This matches the "file read outside the repo" impact category. The severity depends entirely on the unverified join/validation code in `dispatcher.ts`.

### Likelihood Explanation
Likelihood is currently **unconfirmed** — the vulnerability's existence hinges on `dispatcher.ts` not re-validating or path-confining `filepath` after `parseAppURL`. I found evidence of `filepath` being referenced in that file, but could not read the actual sink logic in the time available.

### Recommendation
- Apply `testForInvalidChars` (or a stronger check that rejects `..`, absolute paths, and drive letters) to `filepath` in `parseAppURL`, mirroring the treatment already given to `branch`.
- Independently, wherever `filepath` is consumed (likely in `dispatcher.ts`), resolve the joined path with `path.resolve` and verify it is still contained within the cloned repository's root directory before passing it to `openFile`.

### Proof of Concept
```ts
import { parseAppURL } from '../../src/lib/parse-app-url'

const action = parseAppURL(
  'github-mac://openRepo/owner/repo?filepath=../../../../etc/hosts'
)
// action.filepath === '../../../../etc/hosts' — accepted unmodified,
// unlike an equivalent malformed `branch` value which would be rejected.
```

**Caveat:** This finding is based on confirmed code in `app/src/lib/parse-app-url.ts` showing the asymmetric validation between `branch` and `filepath`. I was unable to fully trace the consumer in `app/src/ui/dispatcher/dispatcher.ts` before running out of iterations, so I cannot state with certainty whether downstream code re-validates/contains the path before use. Given the index/tool-call limitations, I recommend a Devin session (or direct source review) to inspect the exact `filepath` consumption in `dispatcher.ts` and confirm whether path containment checks exist there.
