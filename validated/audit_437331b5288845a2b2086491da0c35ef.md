### Title
Automatic silent rewrite of the local `origin` remote URL from an unauthenticated GitHub API response allows repo-hijack-style redirection of fetches/pushes - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically re-associates a tracked repository with GitHub by looking up `owner/name` (parsed from the existing `origin` remote) via the GitHub API, then automatically calls `git remote set-url` if the API's `clone_url` differs from what Desktop last recorded — with no user confirmation. Because the `owner`/`name` pair used for that lookup is derived purely from the URL string in the local remote, and GitHub allows both usernames and repository names to be renamed/reused, an attacker who reclaims a stale `owner/name` pair (e.g., after the legitimate owner renames their account or the repository) can cause the GitHub API to return a different, attacker-controlled `clone_url`. Desktop then silently retargets the user's `origin` remote to that attacker-controlled URL.

### Finding Description
`repositoryWithRefreshedGitHubRepository` resolves the repository's owner/name from its current remote URL and asks the GitHub API for fresh metadata: [1](#0-0) 

The `owner`/`name` used in `api.fetchRepository(owner, name)` come from `matchGitHubRepository`, which purely parses the *string* of the existing remote URL against a known GitHub hostname — it does not verify that the repository/owner still corresponds to the same underlying GitHub entity Desktop originally associated: [2](#0-1) 

Once a fresh `apiRepo` is returned, `updateRemoteUrl` is invoked and will call `gitStore.setRemoteURL(...)` — a live `git remote set-url` — **without prompting the user** — as long as (a) the current local remote hasn't been manually edited since the last known API-derived clone URL, and (b) the URL protocol is unchanged: [3](#0-2) 

The actual write to the git config is performed here, with no user-visible confirmation dialog: [4](#0-3) [5](#0-4) 

**Broken invariant:** Desktop assumes that "the `owner/name` string that used to identify a GitHub repository still identifies the same repository" is a stable identity binding. GitHub does not guarantee this — usernames and repository names can be freed and reclaimed by unrelated actors. When Desktop's periodic refresh (`repositoryWithRefreshedGitHubRepository`, run e.g. on repository selection and via background refresh/indicator updaters) re-resolves `owner/name` against the API and gets back a *different* repository's `clone_url`, the code path in `updateRemoteUrl` has no way to distinguish "the legitimate repo was simply renamed and clone_url legitimately changed" from "the old owner/name has been reclaimed by an unrelated/malicious account", and blindly rewrites the tracked repository's remote to match the API response.

Existing guards do not stop this:
- `protocolsMatch` only checks that the URL scheme (https vs ssh-like) didn't change — trivial for an attacker to satisfy by using the same scheme.
- `remoteUrlUnchanged` only verifies the user hasn't manually retargeted the remote — it does not verify the *new* target is trustworthy.
- There is no ownership/identity check (e.g., comparing the API `id` field of the previously known `GitHubRepository` vs the newly fetched `apiRepo`) before rewriting the remote. `GitHubRepository`/database records do store a stable numeric `id`, but `updateRemoteUrl` never consults it — it only compares URL strings.

### Impact Explanation
If successfully triggered, the user's `origin` remote is silently repointed at an attacker-controlled repository. Concretely:
- Subsequent `git fetch`/`git pull` will pull attacker-supplied refs/objects into the user's local repository under the belief it is the same project.
- Subsequent `git push` (including Desktop's own "Push" action, which uses the rewritten `origin`) will silently send the user's local commits/code to the attacker-controlled remote instead of the intended one — this is a direct instance of "silent corruption of what the user commits or pushes" and a potential source-code exfiltration primitive for private repositories.
- Because the credential helper trampoline resolves credentials by endpoint/host (`github.com`) rather than by specific repository, and the host itself doesn't change (only owner/name path does), the user's existing GitHub token continues to be handed to git for operations against the new (attacker) repository path, potentially disclosing that the user has push access to something they didn't intend (and, in the case of a fork/PR-style attack, this could be leveraged to submit a push to an attacker-controlled fork that will later be reviewed/merged upstream).

### Likelihood Explanation
Likelihood is limited by the precondition that an attacker must successfully reclaim a stale `owner/name` combination previously used by the tracked repository (via username-squatting after a rename, or GitHub repository-name reuse after deletion/rename), and that the affected Desktop user has not manually edited the `origin` remote since the last successful API sync. Username/organization renames and abandoned repository name reuse ("repo-jacking") are a documented, real occurrence on GitHub and require no special access — the attacker only needs to register the freed name. Desktop performs this refresh automatically in the background (on repository selection and periodic indicator refresh) without any user action, so the corruption happens silently once the attacker wins the race to reclaim the name.

### Recommendation
- In `updateRemoteUrl`, do not rely solely on URL string comparison. Before rewriting the remote, verify the newly fetched `apiRepo`'s stable identity (`id`) matches the previously stored `GitHubRepository.dbID`/API `id` for that repository; only auto-update the URL when the identity is unchanged (i.e., a legitimate rename of the *same* repo/org).
- If the identity differs (or cannot be verified), do not silently call `setRemoteURL`; instead surface a warning/prompt to the user (similar to how manual remote URL edits are explicit) before repointing `origin`.
- Consider caching/comparing the API repository `id` alongside `cloneURL` in `IDatabaseGitHubRepository` (already tracked) and threading it into `updateRemoteUrl`'s decision logic.

### Proof of Concept
1. User adds/clones `https://github.com/alice/repo` in Desktop; Desktop stores `GitHubRepository` with `cloneURL = https://github.com/alice/repo` and a stable `id`.
2. Alice renames her GitHub account from `alice` to `alice2` (freeing the `alice` username). Attacker registers username `alice` and creates a new public repository named `repo` there, e.g. `https://github.com/alice/repo` (now pointing at an entirely different, attacker-controlled repository object with a different API `id`).
3. On the victim's next Desktop refresh (background indicator refresh or simply reselecting the repository in the sidebar), `repositoryWithRefreshedGitHubRepository` re-parses the local remote (`app/src/lib/repository-matching.ts:29-46`), calls `api.fetchRepository('alice', 'repo')`, and receives the attacker's repo data with `clone_url = https://github.com/alice/repo` (same string as before, textually "unchanged" from Desktop's stored `cloneURL`, so `remoteUrlUnchanged` is true and `urlsMatch` is true too in this trivial case — or, more generally, if the attacker uses a different final URL shape (e.g. different case or path), `urlsMatch` becomes false while `remoteUrlUnchanged` stays true because the pre-existing DB record still shows the old string as expected).
4. `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:42-44`) calls `gitStore.setRemoteURL('origin', updatedRemoteUrl)`, which runs `git remote set-url origin <attacker-url>` with no dialog shown to the user.
5. The user's next Push in Desktop now delivers commits to the attacker's repository; the next Fetch/Pull merges attacker-supplied history into the user's working copy — all without any explicit confirmation step.

Note: full end-to-end confirmation of exactly which background timers invoke `repositoryWithRefreshedGitHubRepository` (vs. only foreground repository-selection) could not be completely enumerated within the available tool budget; the selection-triggered path (`_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository`) is confirmed directly in code. [6](#0-5)

```typescript
  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
```

```typescript
/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
```

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
