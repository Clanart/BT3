### Title
Unauthenticated NFT eve-spend DID assignment lets a minter forge false minter/creator provenance - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
`NFTWallet.generate_new_nft()` lets the caller who mints an NFT set an arbitrary `did_id` as the "owner"/minter DID on the singleton's very first (eve) spend, with no cryptographic proof that the named DID actually approved or participated in the mint. This mirrors the reported "open init" bug class: a state-initializing function (here, the NFT singleton's eve/genesis spend) is left without an access-control check tying the claimed initial owner/minter value to the real controller of that identity.

### Finding Description
When minting an NFT with DID support, `generate_new_nft()` builds the ownership-layer inner puzzle for the eve coin using `create_ownership_layer_puzzle(launcher_coin.name(), b"", p2_inner_puzzle, ...)` — the eve DID field is left empty at puzzle-construction time — and the actual "new owner" DID value is only asserted later via the `-10` (change-owner) magic condition inside the eve spend's solution: [1](#0-0) 

The code comment explicitly documents this as a known trust hazard: [2](#0-1) 

Critically, the eve spend's `-10` condition, which sets the DID field, does **not** require any signature or approval from the DID singleton being named — `get_did_approval_info()` is only invoked to create an announcement from an existing DID wallet the *minter* controls (`self.get_did_approval_info`), but that path is entered only if `did_id != b""`; nothing in the ownership layer/eve-spend puzzle chain cryptographically binds the asserted DID value to actual authorization by that DID's owner: [3](#0-2) 

Downstream, `WalletStateManager.get_minter_did()` reads this same unauthenticated `-10` condition off the eve spend and treats its value as the definitive "minter DID" for the NFT going forward, persisting it into `NFTCoinInfo.minter_did` / `NFTInfo.minter_did`, which is then displayed as provenance to wallet UIs and RPC clients: [4](#0-3) [5](#0-4) [6](#0-5) 

This is directly analogous to the reported bug class: a state-initialization step (the eve/genesis spend that sets the singleton's first ownership value) is reachable and fully controllable by any minter, with no on-chain proof that the referenced DID (an unprivileged third party's identity/authority) actually consented. The in-code warning ("wallets should always ignore DID value for eve coins as they can be set to any DID without approval") confirms the developers know this value is forgeable but the mitigation is advisory (client-side convention), not an enforced puzzle-level check.

### Impact Explanation
Any unprivileged minter can create an NFT that on-chain data (and any consumer that doesn't strictly follow the "ignore eve DID" convention, such as `get_minter_did()`'s persisted `minter_did` field surfaced via RPC/UI) presents as having been minted by/associated with an arbitrary victim DID they don't control. This is a forged-identity/provenance issue: it can be used to impersonate legitimate creators/collections for phishing, fraudulent marketplace listings, or social-engineering offer counterparties into believing an NFT has a specific (reputable) minter or DID owner, when no such approval occurred. Since `minter_did` is stored and exposed through wallet RPC (`chia/wallet/nft_wallet/nft_info.py`, `wallet_state_manager.py`), any tooling or downstream service that trusts this field for authenticity checks is vulnerable to spoofed provenance.

### Likelihood Explanation
High reachability: minting an NFT with an arbitrary `did_id` argument is a standard, unprivileged wallet operation (`generate_new_nft`), reachable by any wallet user through the wallet RPC (`create_new_nft` style calls) with no special permissions and no interaction from the impersonated DID's owner required. The only "protection" is a code comment advising downstream consumers to ignore the value — an easily-missed convention rather than an enforced invariant.

### Recommendation
Do not treat the eve-spend `-10` DID assertion as authoritative minter/owner provenance anywhere in wallet state (`get_minter_did()`, `NFTCoinInfo.minter_did`, `NFTInfo.minter_did`) unless it is cryptographically tied to an announcement/approval spend from the named DID singleton in the same spend bundle (as is already done for subsequent `set_nft_did`/`set_bulk_nft_did` transfers via `get_did_approval_info`). Either: (1) require the eve mint spend to also include a verifiable DID announcement matching the claimed `did_id`, or (2) strip/ignore `minter_did` entirely for eve spends that lack such proof, and clearly mark any stored "minter DID" as unverified in the data model and RPC responses so clients cannot mistake it for verified provenance.

### Proof of Concept
1. Attacker calls the NFT mint flow with `did_id` set to a well-known/reputable DID's launcher ID that the attacker does not control (`NFTWallet.generate_new_nft(..., did_id=<victim_did>)`).
2. Because `create_ownership_layer_puzzle` initializes the eve DID field empty and the actual DID value is only set via the unauthenticated `-10` condition in the eve spend's solution, the spend succeeds without any signature/announcement from the victim DID.
3. `WalletStateManager.get_minter_did()` later reads this eve spend's `-10` condition and records `minter_did = <victim_did>` into the persisted `NFTCoinInfo`/`NFTInfo`.
4. Any wallet UI, marketplace, or RPC consumer that surfaces `minter_did` as "minted by" now falsely attributes the NFT to the victim DID, despite no participation or approval from that DID's actual owner.
