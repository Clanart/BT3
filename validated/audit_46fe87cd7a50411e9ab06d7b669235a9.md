### Title
`SignableTransaction` omits the OP_RETURN output from fee and weight calculation, underpaying the fee and potentially producing an unrelayable transaction - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/Kirstentat/serai--020/blob/main/networks/bitcoin/src/wallet/send.rs#L194-L213))

### Summary
`SignableTransaction::new` pushes the OP_RETURN `data` output onto `tx_outs` before computing the transaction weight, but `calculate_weight_vbytes` is only passed `payments` and `change` — the OP_RETURN output is never included in the measured transaction. The analog of the oracle bug (a wrong parameter wired into a value computation) is a wrong transaction wired into the fee computation: the fee is priced against a smaller transaction than the one that will actually be signed and broadcast.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` at lines 194–202. Immediately afterward, the weight/vbytes used to derive `needed_fee` are computed from a *reconstructed* transaction built only from `inputs`, `payments`, and optionally `change`:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
``` [1](#0-0) 

`calculate_weight_vbytes` builds its measurement `Transaction` exclusively from `payments` (and `change`); it has no `data` parameter and never adds the OP_RETURN output. [2](#0-1) 

The final `SignableTransaction` however embeds `tx_outs`, which *does* contain the OP_RETURN output. [3](#0-2) 

An OP_RETURN output with up to 80 bytes of data adds roughly `9 + 2 + 80 ≈ 91` serialized bytes (all counted at full weight). The resulting transaction's real vsize is therefore up to ~91 vbytes larger than the `vbytes` value used for both `needed_fee` and the `MAX_STANDARD_TX_WEIGHT`/`TooLowFee` checks.

### Impact Explanation
- **Underpaid fee:** the effective fee rate of the signed transaction is `needed_fee / actual_vsize`, strictly less than the caller-requested `fee_per_vbyte`. The divergence scales with the data length.
- **Below minimum relay fee:** if the caller requests `fee_per_vbyte` at or near the relay minimum, the `TooLowFee` check passes against the underestimated `vbytes`, but the real transaction's fee rate falls under `DEFAULT_MIN_RELAY_TX_FEE`. The transaction will be rejected by mempool policy — funds committed to inputs cannot move until a replacement transaction is constructed and re-signed through the threshold ceremony.
- **Weight check bypass:** `MAX_STANDARD_TX_WEIGHT` is checked against a weight missing the OP_RETURN output, so a transaction marginally over the standard limit is accepted as valid and then fails at broadcast.

Like the WBTC/ETH oracle swap, this is a wrong-input-to-valuation bug: the component that prices the transaction is fed a different (smaller) object than the one actually produced, yielding a systematically understated cost.

### Likelihood Explanation
Any caller passing `data: Some(_)` (Serai uses OP_RETURN data for protocol metadata on Bitcoin transactions) triggers this. Underpayment is guaranteed whenever `data` is non-empty; mempool rejection occurs when the requested fee rate is near the relay minimum, which is a normal configuration for cost-sensitive batch transactions.

### Recommendation
Include the OP_RETURN output in the measured transaction — e.g., pass `data` (or the full `tx_outs` list) into `calculate_weight_vbytes`, or construct the measurement `Transaction` from the same `tx_outs` that will be placed in the final `SignableTransaction`. Alternatively, compute the fee against `self.tx.weight()` after the transaction is fully assembled.

### Proof of Concept
1. Construct `SignableTransaction::new(inputs, payments, None, Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte` equals the minimum relay rate (1 sat/vB).
2. `needed_fee()` returns `1 * vbytes_without_opreturn`.
3. `transaction()` returns a `Transaction` containing an additional ~91-byte OP_RETURN output; its actual vsize is `vbytes_without_opreturn + ~91`.
4. Effective fee rate ≈ `vbytes/(vbytes+91)` sat/vB < 1 sat/vB → rejected by `mempool min fee` policy despite `TooLowFee` having passed.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
