Confirmed: `createCommit` in `app/src/lib/git/commit.ts:15-72` calls `unstageAll` then `stageFiles` (four separate, un-transacted git invocations inside `stageFiles`) and then `git commit`, with no rollback if `stageFiles` throws partway.

### Title
Non-atomic multi-step index staging in `stageFiles`/`createCommit` can silently commit a different file set than the user reviewed - (File: app/src/lib/git/update-index.ts)

### Summary
`createCommit` builds a commit in four sequential, independently-failable Git operations — `unstageAll`, then inside `stageFiles`: (1) force-remove renamed-source paths, (2) `update-index` for normal paths, (3) force-remove deleted paths, (4) a per-file loop of `applyPatchToIndex` for partially-selected hunks — followed by `git commit`. None of these steps are wrapped in a transaction/rollback. If any intermediate step throws, the ones already executed remain applied to the index while the remaining ones never run, leaving the index in a state that matches neither "nothing selected" nor "everything the user selected." This mirrors the reported bug class: a multi-step storage mutation not marked `#[transactional]`.

### Finding Description
`stageFiles` documents itself as a three-step process plus a partial-patch loop [1](#0-0) , and `createCommit` chains `unstageAll` → `stageFiles` → `git commit` with no error handling or index rollback between steps [2](#0-1) . The partial-file loop calls `applyPatchToIndex`, which runs `git apply --cached --unidiff-zero -` per file [3](#0-2) . `git apply` can fail (context mismatch, encoding issues, CRLF/CR differences, binary detection, or a hostile working-tree file crafted by the repository author to reliably trip `apply` errors) independent of the earlier `update-index` calls, which have already committed their mutations to the index by the time the loop runs.

Because the three `updateIndex` calls and the `applyPatchToIndex` loop are not guarded as a single atomic unit, a thrown exception partway through the partial-file loop leaves: renamed-source removals and whole-file stages already applied to the index, but only some (or none) of the partially-selected hunks applied for later files in the loop. The resulting index snapshot has never been shown to the user and does not correspond to any diff they reviewed in the UI.

### Impact Explanation
If the caller does not fully unwind this partial index state before retrying or before the user clicks "Commit" again, a subsequent `git commit` can capture a hybrid of previously-staged (from the interrupted attempt) and newly-staged content, silently diverging from what the Changes/diff view displayed and what the user intended to commit and push. This is a "silent corruption of what the user commits or pushes" — the class of impact explicitly listed as valid — because the discrepancy is not surfaced as a conflict or error the user would notice; it just becomes part of history once pushed.

### Likelihood Explanation
The trigger requires only ordinary Desktop usage (opening a repository — potentially attacker-authored/fetched content — with mixed rename/partial-hunk changes and hitting an error mid `apply`, e.g. from unusual line-ending/encoding content an attacker controls in the repo) combined with the app's existing retry/error paths that call `stageFiles` again without first fully resetting the index. No admin rights, local pre-existing malware, or unnatural user steps are required beyond normal commit/partial-commit flows Desktop explicitly supports (renames + partial-hunk staging). However, actually forcing `git apply` to fail deterministically via attacker-supplied file content, and confirming Desktop's retry path doesn't fully reset the index before retrying, could not be fully verified from static code alone within this session — this needs dynamic testing (e.g., a background Devin session reproducing the interrupted `stageFiles` sequence and inspecting the resulting `git status`/index state) to confirm exploitability with certainty.

### Recommendation
Wrap the full `unstageAll` → `stageFiles` → `commit` sequence (and within it, the `oldRenamed`/`normal`/`deletedFiles`/`partial` steps of `stageFiles`) so that any failure resets the index back to its pre-operation state (e.g., `git reset --mixed HEAD` or an equivalent index snapshot/restore) before surfacing the error to the caller, rather than leaving a half-mutated index that a retry or later action might build on unknowingly.

### Proof of Concept
Conceptual reproduction (would need to be validated in a live Desktop build):
1. Create/fetch a repository containing a renamed file plus a second modified file whose diff/encoding is crafted to make `git apply --cached --unidiff-zero` fail (e.g., inconsistent line endings or a crafted no-newline-at-EOF edge case).
2. In Desktop, select the rename for full inclusion and select only some lines of the second file for a partial commit, then commit.
3. `stageFiles` completes the rename-removal and normal `updateIndex` calls, then throws inside `applyPatchToIndex` for the crafted file, aborting the loop before all partial hunks are applied.
4. Inspect `git status`/`git diff --cached` in the repository directly: the index now contains the renamed file and any partial files processed before the failure, but not the intended state and not the pre-commit state — a mutation the user never approved.
5. Retrying the commit without Desktop having reset the index first can fold this stale partial staging into the next commit, silently changing what gets committed/pushed.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
}
