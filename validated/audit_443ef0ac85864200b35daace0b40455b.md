### Title
Empty aggregate signature verifies as valid (`SchnorrAggregate::verify` accepts empty `Rs`/`keys_and_challenges` with `s == 0`) - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
The analog of "an unset `API_TOKEN` silently disables authentication" is a verification routine whose success path degenerates to trivially true when its public input is empty. `SchnorrAggregate::<C>::verify` only checks `self.Rs.len() == keys_and_challenges.len()` before building its multiexp pairs. When both are empty, the loop appends nothing and the sole statement is `(-s) * G`; an attacker who supplies `s = 0` reduces the whole check to `0 * G == identity`, so verification returns `true`. An "aggregate signature" attesting to nothing authenticates as valid — the exact shape of the empty-credential bypass.

### Finding Description
- `SchnorrAggregate::read` deserializes attacker-controlled `Rs` (length-prefixed `u32`) and scalar `s` with no minimum-length or semantic checks, so `Rs = []`, `s = 0` is accepted: `crypto/schnorr/src/aggregate.rs` lines 77-88.
- `verify` short-circuits only on a length mismatch, then builds `pairs` purely from `keys_and_challenges`. With zero entries, `pairs` contains only `(-self.s, C::generator())`, and `multiexp_vartime(&pairs).is_identity()` evaluates to true whenever `s == 0`: `crypto/schnorr/src/aggregate.rs` lines 127-146.
- `SchnorrAggregator::complete` refuses to *produce* an empty aggregate (lines 175-178), but nothing stops an attacker from *submitting* one — `read` + `verify` are fully public-input-driven.
- The same empty-degenerates-to-true pattern exists one level down: `BatchVerifier::verify`/`verify_vartime` return `is_identity()` of an empty multiexp, i.e. `true` for a batch with zero queued statements (`crypto/multiexp/src/batch.rs` lines 93-101), and the test suite codifies this (`crypto/multiexp/src/tests/batch.rs` lines 29-31).
- Callers that route untrusted bytes into this API exist: `Validators::verify_aggregate` reads a `SchnorrAggregate` and a signer list, then calls `aggregate.verify(DST, &keys_and_challenges)` (`coordinator/tributary/src/tendermint/mod.rs` lines 200-229). A commit carrying `validators = []` and an empty aggregate signature (`len = 0`, `s = 0`) passes verification — a "proof of consensus" attested by no one, mirroring a session authenticated by an empty token.

### Impact Explanation
Any protocol reaching `SchnorrAggregate::verify` with an attacker-influenced signer list accepts a forged aggregate signature over an arbitrary message using ~40 bytes of trivially constructible input. For the Tendermint usage, this means a `Commit`/`Signature::Aggregate` claiming zero signers verifies successfully; whether the surrounding weight check rejects it depends on each caller, and the cryptographic primitive itself provides no rejection. More broadly, any integrator batch-verifying statements through `BatchVerifier` (e.g. `SchnorrSignature::batch_verify`, PedPoP `calculate_share`, FROST `complete`'s blame path) treats "no statements" as "all statements valid" rather than an error.

### Likelihood Explanation
Reaching the bug requires an attacker to cause `verify`/`verify_aggregate` to be invoked with an empty signer set — plausible wherever a signer/validator list is deserialized alongside the signature rather than bound to a fixed roster. Constructing the forgery is free: `u32::MAX`-safe 4-byte `0` length plus a zero scalar. No key knowledge, signing participation, or collusion is needed. Severity is bounded by how callers guard the empty-signer case (e.g. `verify_commit` weight checks upstream), so a High–Medium classification fits: a cryptographic verify function returning `true` on vacuous input is an incorrect verifier formula reachable from public inputs.

### Recommendation
- In `SchnorrAggregate::verify` (and/or `read`), reject `Rs.is_empty()` / `keys_and_challenges.is_empty()` explicitly.
- In `SchnorrAggregator::complete`, keep the `None` behavior but make `verify` the defense-in-depth check.
- In `BatchVerifier`, document or assert the non-empty precondition; where feasible, return an error/`false` on empty `verify` so vacuous-truth can't silently authenticate an empty statement set.

### Proof of Concept
```rust
use ciphersuite::{Ciphersuite, Ristretto};
use schnorr::aggregate::SchnorrAggregate;
use group::ff::Field;

// Forged aggregate signature: length = 0, s = 0
let mut bytes = vec![0u8; 4];
bytes.extend(<Ristretto as Ciphersuite>::F::ZERO.to_repr().as_ref());
let agg = SchnorrAggregate::<Ristretto>::read(&mut bytes.as_slice()).unwrap();

// Attacker-supplied empty signer set verifies for ANY dst/message context
assert!(agg.verify(b"any dst", &[]));
```
This passes because `verify` builds `pairs = [(-0, G)]` and `multiexp_vartime` yields the identity. The analogous empty `BatchVerifier` case: `BatchVerifier::<u8, <Ristretto as Ciphersuite>::G>::new(0).verify() == true`.
