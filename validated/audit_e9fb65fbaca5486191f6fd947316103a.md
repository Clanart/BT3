### Title
Hookify `evaluate_rules` silently drops enforcement for `UserPromptSubmit` (and any non-PreToolUse/PostToolUse/Stop) block rules - ([File: plugins/hookify/core/rule_engine.py])

### Summary
In `RuleEngine.evaluate_rules`, the `else` branch (lines 80-84) that handles any `hook_event` other than `'Stop'`, `'PreToolUse'`, or `'PostToolUse'` returns only `{"systemMessage": combined_message}` even when `blocking_rules` were matched. Because `UserPromptSubmit` is not one of the three explicitly handled events, any rule authored with `event: prompt` and `action: block` never actually produces a machine-readable deny signal, so the operation it was meant to stop is effectively allowed.

### Finding Description
`evaluate_rules` builds `blocking_rules` from any rule that matches and has `action == 'block'` [1](#0-0) . When blocking rules exist, the function branches purely on `hook_event`, handling only `'Stop'` (returns `decision: block`) and `'PreToolUse'/'PostToolUse'` (returns `hookSpecificOutput.permissionDecision: deny`) [2](#0-1) . Every other event — including `UserPromptSubmit`, the plugin's fourth registered hook — falls into the `else` branch, which returns only `systemMessage` and no `decision`/`permissionDecision` key at all [3](#0-2) .

The `userpromptsubmit.py` hook script is wired exactly into this path: it loads `event='prompt'` rules and forwards the raw stdin `input_data` (which Claude Code populates with `hook_event_name: "UserPromptSubmit"`) straight into `evaluate_rules`, then prints whatever dict comes back and always exits 0 [4](#0-3) . This is registered in `hooks/hooks.json` as a real, live hook event for the plugin [5](#0-4) .

`.claude/hookify.*.local.md` rule files are auto-discovered from the current working directory via `glob.glob` with no origin/trust check [6](#0-5) , so any repository (including an untrusted one a victim clones) can ship a rule with `event: prompt` and `action: block` intended to stop a dangerous prompt/pattern. Because the hook runner only recognizes `decision`/`hookSpecificOutput.permissionDecision` as enforcement signals (as documented for `PreToolUse`/`Stop` in the plugin's own hook-development skill doc [7](#0-6) ), a `systemMessage`-only response is treated as non-blocking informational output — the prompt proceeds unblocked despite the rule author's explicit `action: block` intent.

### Impact Explanation
Any hookify rule that targets `UserPromptSubmit` (or any hook event outside the three explicitly coded ones) with `action: block` is a silent no-op: it displays a warning message but never stops the operation. This breaks the "deny means deny" invariant across the plugin's rule engine and creates unauthorized-execution risk in the specific case where a user or project relies on hookify to gate `UserPromptSubmit`-triggered behavior (e.g., blocking prompts referencing dangerous patterns) — the intended block silently degrades to an allow, letting the flagged prompt reach the model/agent as if no rule existed.

### Likelihood Explanation
Highly reproducible: it requires no special privilege, only a rule file with `event: prompt` (or any event mapped to `hook_event_name` values outside `Stop`/`PreToolUse`/`PostToolUse`) and `action: block`, which is a normal, documented hookify configuration pattern [8](#0-7) . Every invocation of `userpromptsubmit.py` with a matching block rule exhibits the bug deterministically.

### Recommendation
Add explicit handling for `UserPromptSubmit` in `evaluate_rules`'s blocking branch, returning the field(s) Claude Code's hook contract actually recognizes for blocking that event (per Claude Code's documented `UserPromptSubmit` output, a top-level `decision: "block"` with `reason`), instead of falling into the generic `else` that only sets `systemMessage`. More generally, the `else` branch should not silently claim to enforce a block for events it cannot actually enforce — consider failing loudly (e.g., logging a warning to stderr) so unmapped block rules are not silently defanged.

### Proof of Concept
Unit test in `rule_engine.py`'s test style:
```python
rule = Rule(name="block-prompt", enabled=True, event="prompt", action="block",
            conditions=[Condition(field="user_prompt", operator="contains", pattern="rm -rf")],
            message="Blocked dangerous prompt")
engine = RuleEngine()
input_data = {"hook_event_name": "UserPromptSubmit", "user_prompt": "please rm -rf /"}
result = engine.evaluate_rules([rule], input_data)

assert "decision" not in result
assert "hookSpecificOutput" not in result
assert "systemMessage" in result
```
Integration check: simulate the hook runner's contract (only `decision`/`hookSpecificOutput.permissionDecision` fields stop execution) and assert that this `result` is treated as an allow, confirming the block rule had no enforcement effect despite `action: block` and a matching condition.

```python
def main():
    """Main entry point for UserPromptSubmit hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Load user prompt rules
        rules = load_rules(event='prompt')

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0
        sys.exit(0)
```
