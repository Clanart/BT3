### Title
Git's built-in protection against malicious clones/submodules is explicitly disabled during `clone` - ([File: app/src/lib/git/clone.ts])

### Summary
`AccountV1#flashActionByCreditor` broke an invariant by letting attacker-controlled state (the account owning itself + a malicious creditor) desynchronize "what is recorded as held" from "what is actually held," letting the attacker exfiltrate the real asset while the stale bookkeeping stayed intact and was later leveraged for profit. The Desktop analog with the same broken-invariant/attacker-controlled-object shape is in the clone path: Desktop explicitly disables Git's own clone-time integrity protection (`GIT_CLONE_PROTECTION_ACTIVE`) while still recursively fetching attacker-controlled submodules, so a malicious repository can desynchronize "what the working tree is supposed to contain" from "what actually got written to disk," letting a crafted submodule escape the intended repository boundary.

### Finding Description
`clone()` in [1](#0-0)  builds the environment for the `git clone --recursive ...` invocation and unconditionally sets:

```
GIT_CLONE_PROTECTION_ACTIVE: 'false'
```

`GIT_CLONE_PROTECTION_ACTIVE` is the escape-hatch environment variable Git added for its clone/checkout protections against crafted repositories that contain case-confusable or symlinked `.git` entries in (sub)directories/submodules — the class of vulnerability fixed upstream for CVE-2024-32002 (RCE via malicious repository during recursive clone on case-insensitive filesystems). Setting it to `false` tells Git to skip that check entirely for every clone Desktop performs.

The only local guard applied before the clone is `isClonePathSensitive()` [2](#0-1) , which only validates the *destination directory* (blocking `~/.ssh`, `~/.gnupg`, etc.) — it says nothing about the *contents* of the remote repository or its submodules being cloned. There is no other compensating check anywhere in `clone()` for the specific class of attack the disabled protection exists to stop.

Because Desktop always passes `--recursive` [3](#0-2) , submodules are fetched and checked out automatically as part of the same operation, with the protection turned off, for any URL the user (or a deep link / "Clone in Desktop" flow, or `openOrCloneRepository` triggered from `openRepositoryFromUrl` [4](#0-3) ) supplies.

This mirrors the reported bug-class exactly: an attacker-controlled object (here, a cloned/fetched repository and its submodules, analogous to the malicious "creditor") is allowed to desynchronize the tracked state (the working tree Desktop believes it created) from the real state (files silently written outside the intended repo root via a symlinked/case-variant `.git` path), and the guard that exists elsewhere (`isClonePathSensitive`) does not cover this path at all.

### Impact Explanation
If exploited, a crafted repository (or a crafted submodule referenced by an otherwise innocuous-looking repository) cloned through Desktop could write files outside the cloned repository's working directory — e.g., into a global hooks directory or an existing `.git` config — leading to arbitrary command execution on the next Git operation, or silent corruption of the user's environment/config. This satisfies the "code execution or file write outside the repo" impact bucket, driven purely by an attacker-controlled cloned/fetched repository, with zero local access or pre-existing compromise required.

### Likelihood Explanation
Any user who clones a public/malicious repository, follows an `x-github-desktop://openRepo/...` deep link, or uses "Open in Desktop"/"Clone repository" with an attacker-supplied URL exercises this exact code path, since `GIT_CLONE_PROTECTION_ACTIVE: 'false'` is set unconditionally for every clone, not behind a flag or narrowed to a specific scenario. The `--recursive` flag guarantees submodules (the primary vector for this class of attack) are fetched in the same operation.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in [5](#0-4)  unless Desktop implements its own equivalent verification of submodule/`.git`-entry paths before checkout. If the override exists to work around a specific benign scenario, scope it narrowly (e.g., only for trusted, already-verified local operations) rather than applying it to every remote clone of an arbitrary, potentially attacker-controlled URL.

### Proof of Concept
1. Attacker hosts a Git repository `evil/parent` whose `.gitmodules` references a submodule that is itself a repository containing a case-variant or symlinked `.git` entry (the same construct used in the upstream Git RCE fixed by CVE-2024-32002), designed to write a hook file (e.g. `hooks/post-checkout`) outside the submodule's intended directory on a case-insensitive filesystem (default on macOS/Windows).
2. Victim opens `evil/parent`'s clone URL in GitHub Desktop (via the "Clone repository" dialog, or via an `x-github-desktop://openRepo/?url=...` link routed through `openRepositoryFromUrl` → `openOrCloneRepository`).
3. Desktop calls `clone()` [6](#0-5) , running `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment.
4. Git's normal protection against the malicious submodule layout is skipped because the escape hatch is active; the crafted `.git` entry is followed/written outside the intended path, planting a hook or config file.
5. The planted hook executes on the next Git operation Desktop or the user performs in that (or an adjacent) repository, achieving code execution outside the sandboxed clone directory.

```typescript
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
```

```typescript
export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
```
