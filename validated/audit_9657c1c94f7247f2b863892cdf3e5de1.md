Based on the deep-dive into `plugins/security-guidance/hooks/diffstate.py` and `security_reminder_hook.py`, I found a directly analogous unprivileged-write-then-trust vulnerability, though its impact class is a security-review bypass rather than a pure DoS.

### Title
Unauthenticated `.git/sg-reviewed-shas` trust file lets an unprivileged local writer suppress the security-guidance plugin's commit/push vulnerability scan - (File: plugins/security-guidance/hooks/diffstate.py)

### Summary
The `security-guidance` plugin tracks which commit SHAs it has already reviewed in a plaintext, repo-local file `.git/sg-reviewed-shas`, and trusts the mere presence of a SHA in that file as proof review already happened, with no cryptographic binding, no signature, and only a superficial hex-format check on read.

### Finding Description
`_reviewed_shas_path()` computes a fully deterministic path derived only from the repo root: `.git/sg-reviewed-shas` [1](#0-0) . `_load_reviewed_shas()` reads this file and accepts any 40-hex-character token as a "previously reviewed" SHA, performing no signature, HMAC, or provenance check beyond format validation [2](#0-1) . `_append_reviewed_shas()` writes lines in the format `<sha>\t<ts>\t<pv>\t<vulns_found>` with `fcntl.flock` used only for concurrency safety, not authentication [3](#0-2) . This is structurally identical to the pump-science bug: a trust-establishing record (`lock_escrow` PDA / `sg-reviewed-shas` entry) is derived from a fully public/predictable value (pool+owner / repo root path), created without any signer/authenticity check, and downstream privileged logic (`lock_pool` / push-sweep diff-base computation) blindly trusts its mere existence to skip work it would otherwise perform.

`_compute_push_sweep_base()` consumes this set to advance the diff base past any "reviewed" prefix, and can return `None` (skip entirely) when the whole pushed range is marked reviewed [4](#0-3) . Any process running with the same filesystem privileges as the user's Claude Code session — a malicious build/test script, a compromised dependency's install hook, or any Bash command a prompt-injected instruction gets executed — can append arbitrary commit SHAs (including ones for not-yet-reviewed, malicious commits) to this file before the legitimate push-sweep review runs.

### Impact Explanation
Because the push-sweep hook treats "SHA present in `sg-reviewed-shas`" as equivalent to "the LLM security reviewer already examined and cleared this commit," an attacker who can execute any command in the repo working directory (a much lower bar than needing Claude's own tool-call privileges) can pre-poison this file to make the security-guidance plugin silently skip its automated vulnerability scan on a `git push` containing malicious or vulnerable code. This defeats a security control the user believes is running, allowing unreviewed/malicious commits to be pushed without the expected automated flag, rather than merely denying service.

### Likelihood Explanation
Exploitation requires local code execution with the same privileges as the Claude Code session's filesystem access to the repository (e.g., a supply-chain-compromised dependency, a malicious test/build script, or a prompt-injected Bash command) — this is a plausible unprivileged-automation trust-boundary violation within the repo/`.git` directory, matching the "hook bypass" / "git automation" categories called out as in-scope. It does not require any special OS privilege beyond what a co-located script or subagent already has.

### Recommendation
Do not treat presence-in-file as proof of review. Bind each recorded SHA to the actual review outcome cryptographically (e.g., an HMAC keyed by a secret private to the security-guidance hook process, or by making the file append-only via a mechanism the hook alone can extend, such as writing it only from within the reviewing process and verifying a monotonic counter/signature at load time). At minimum, treat the reviewed-shas file as a performance optimization only, and fall back to full review whenever the file's integrity cannot be independently corroborated (e.g., cross-check against the plugin's own emitted metrics/telemetry log rather than trusting the flat file alone).

### Proof of Concept
1. In a repo with the `security-guidance` plugin enabled, have any process with write access to the working directory (e.g., a malicious `postinstall` script run via `npm install`, or a Bash command executed by Claude under prompt injection) compute the SHA of an upcoming malicious commit (`git rev-parse HEAD` after staging it, or predict it since content/parent/author/committer/timestamp are all attacker-controlled at commit time).
2. Append a forged line to `.git/sg-reviewed-shas`: `printf '%s\t%s\t0\t0\n' "$SHA" "$(date +%s)" >> .git/sg-reviewed-shas`.
3. Push the branch. `_compute_push_sweep_base()` sees the SHA already in the reviewed set and advances/skips the diff base for that commit [4](#0-3) , so the LLM-based vulnerability scan never inspects the malicious diff, even though no genuine review occurred.

Note: I was unable to fully trace every call site that consumes `_compute_push_sweep_base`'s return value to confirm there is no secondary defense-in-depth check elsewhere in `security_reminder_hook.py` (e.g., a full independent re-scan on `Stop`); the index only surfaced the push-sweep-specific consumer. If a full-session `Stop`-hook review independently re-scans all touched files regardless of the push-sweep state, the practical impact would be reduced to "the push-specific fast-path scan is skipped" rather than "no review ever occurs." I'd recommend verifying this interaction directly in the full source before treating severity as final, since the index has size limits and this cross-check spans a large function I could not fully view.

```python
def _load_reviewed_shas(repo_root):
    """Set of full 40-hex shas previously reviewed in this clone."""
    p = _reviewed_shas_path(repo_root)
    if not p or not os.path.exists(p):
        return set()
    out = set()
    try:
        with open(p, "r") as f:
            for line in f:
                sha = line.split("\t", 1)[0].strip()
                if len(sha) == 40 and all(c in "0123456789abcdef" for c in sha):
                    out.add(sha)
    except OSError:
        pass
    return out
```

```python
def _append_reviewed_shas(repo_root, shas, vulns_found=0):
    """Record that `shas` were reviewed. Best-effort; never raises.

    Uses fcntl.flock for the read-gc-write; appends are O_APPEND-atomic but
    GC needs the lock so concurrent CC sessions in the same clone don't race
    each other's truncation.
    """
    p = _reviewed_shas_path(repo_root)
    if not p or not shas:
        return
    import time as _time
    ts = int(_time.time())
    pv = _PV or 0
    lines = [f"{s}\t{ts}\t{pv}\t{int(vulns_found)}\n" for s in shas]
    try:
        import fcntl
        with open(p, "a+") as f:
            fcntl.flock(f.fileno(), fcntl.LOCK_EX)
            try:
                f.seek(0)
                existing = f.read().splitlines(keepends=True)
                # Dedup by sha (first column) — keep newest, then cap.
                seen = set()
                merged = []
                for ln in (existing + lines)[::-1]:
                    sha = ln.split("\t", 1)[0].strip()
                    if sha and sha not in seen:
                        seen.add(sha)
                        merged.append(ln if ln.endswith("\n") else ln + "\n")
                merged = merged[:_REVIEWED_SHAS_CAP][::-1]
                f.seek(0)
                f.truncate()
                f.writelines(merged)
            finally:
                fcntl.flock(f.fileno(), fcntl.LOCK_UN)
    except (OSError, ImportError):
        # fcntl unavailable (Windows) or write failed — degrade to plain
        # append; cap enforcement happens on the next locked write.
        try:
            with open(p, "a") as f:
                f.writelines(lines)
        except OSError:
            pass
```

```python
def _compute_push_sweep_base(prev_upstream, push_range, reviewed):
    """Advance the diff base past the contiguous reviewed prefix.

    Spec: review `git diff B..HEAD` where `B` is the newest commit such that
    `prev_upstream..B` is entirely in `reviewed`. Returns (B, unreviewed_tail).
    `B == None` means the whole range is reviewed (caller should skip).
    `push_range` must be oldest→newest.

    Examples (✓=reviewed, ✗=not):
      [✓1, ✗2, ✓3]  → B=1, tail=[2,3]   (cannot trim suffix; Read is at HEAD)
      [✓1, ✓2, ✓3]  → B=None            (all reviewed → skip)
      [✗1, ✓2, ✗3]  → B=prev_upstream, tail=[1,2,3]
      []            → B=None
    """
    i = 0
    while i < len(push_range) and push_range[i] in reviewed:
        i += 1
    if i == len(push_range):
        return None, []
    base = push_range[i - 1] if i > 0 else prev_upstream
    return base, push_range[i:]
```
