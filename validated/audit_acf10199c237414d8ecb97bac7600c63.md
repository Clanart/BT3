### Title
Lazy module self-init bypasses code-object ownership check when the module was published to an object before `LAZY_MODULE_INITIALIZATION` was enabled - (File: `aptos-move/framework/aptos-framework/sources/init.move`, `aptos-move/framework/aptos-framework/sources/code.move`)

### Summary
The Aptos "lazy module initialization" feature lets a module mint its own `signer` via `init::internal_maybe_initialize`, gated by an `EOWNER_CHANGED_SINCE_DEPLOY` check that compares the object's *current* root owner against the owner recorded at the module's *last publish* (`deploy_owner`). That recording only happens when `code::publish_package` runs **and** the `LAZY_MODULE_INITIALIZATION` feature flag is already enabled at publish time. For any object-hosted module published (or last upgraded) while the flag was off, `deploy_owner` stays `None` forever. The self-init gate treats `None` as the "account address, always allowed" case, so once the feature flag is turned on network-wide, self-init on such pre-existing object modules is unconditionally permitted regardless of any ownership transfers that happened in between.

### Finding Description
In `code.move`, `deploy_owner` is only recorded conditionally: [1](#0-0) 

In `init.move`, the field's semantics are documented as: `deploy_owner` is the object's root owner recorded at last publish, and it is `none` for account addresses: [2](#0-1) 

The test suite makes the intended invariant explicit — a `None` `deploy_owner` is treated as "always allowed" precisely because it's assumed to only occur for a genuine account address that "authorized its own code": [3](#0-2) 

The gap: `record_deploy_owner` is only invoked when `features::is_lazy_module_initialization_enabled()` is true at the moment `publish_package` runs, combined with `object::is_object(addr)`. If a package is published to an object address while the feature is disabled (the default state before the feature is activated on a network, or simply before an operator republishes after activation), `deploy_owner` is never populated for that address's modules — it stays permanently `None`, exactly like a non-object account address. There is no separate marker distinguishing "no owner recorded because this is an account" from "no owner recorded because this object predates the feature."

The explicit adversarial test only covers modules deployed *with the feature already on*: [4](#0-3) 
There is no test covering the sequence: deploy to object (feature off) → transfer object ownership → enable feature → call `run`. Given the code path, that sequence would leave `deploy_owner == None` and the self-init gate (which treats `None` as "no gating needed") would mint a signer for the object regardless of who currently owns it.

### Impact Explanation
This breaks the exact code-object ownership invariant the feature is designed to guarantee: "a module deployed to an object may only self-initialize while the object is still owned by whoever owned it when the code was published." For any object-hosted module published before `LAZY_MODULE_INITIALIZATION` is turned on (the common case immediately after the feature is activated on a live network, since existing deployments cannot be retroactively "re-recorded" without republishing), an attacker who acquires ownership of that code object (e.g., buys/receives it, or it was never firmly attributed) can trigger self-init and obtain a signer for the object address — able to `move_to` resources, seize capabilities, or otherwise take actions as if they were the original deployer. This is a code-object ownership/authority-leak issue with mainnet relevance once the flag is rolled out, matching "code-object ownership change" / "native validation ... reaches protected state mutation" in the publish impact gate.

### Likelihood Explanation
High, once `LAZY_MODULE_INITIALIZATION` is enabled: every object-hosted module published prior to activation is, by construction, in the vulnerable `deploy_owner == None` state, and no republish is required to trigger the bug — merely calling any entry function that calls `internal_maybe_initialize` after the flag flips on is sufficient. The bug requires no special permissions beyond ordinary object transfer/acquisition, which is a standard, permissionless operation.

### Recommendation
Distinguish "never recorded because address is a plain account" from "never recorded because the object predates/missed feature-gated recording." For example: always record `deploy_owner` at publish time regardless of the feature flag (removing the `is_lazy_module_initialization_enabled()` condition around `record_deploy_owner` in `code.move`), or store an explicit sentinel/state variant so `assert_may_self_initialize` can require re-publish (thus re-recording current ownership) before ever permitting self-init on an object address whose owner was never captured.

### Proof of Concept
1. With `LAZY_MODULE_INITIALIZATION` disabled, publish a module to an object address `O` owned by `attacker` (object code deployment flow: `object_code_deployment::publish`).
2. Transfer object `O` to `attacker2` (or any new owner) using standard `object::transfer`.
3. Enable `LAZY_MODULE_INITIALIZATION` (network feature activation).
4. Call the module's entry function that invokes `init::internal_maybe_initialize(false)`.
5. Because `deploy_owner` for `O`'s modules was never recorded (step 1 ran with the feature off), `internal_maybe_initialize` skips the `EOWNER_CHANGED_SINCE_DEPLOY` check and mints a signer for `O`, regardless of the ownership transfer in step 2 — the intended ownership continuity guarantee is bypassed.

Note: I could not retrieve the exact body of `assert_may_self_initialize` (lines ~60-90 of `init.move`) due to a tool output truncation in the final iteration; the conclusion above is based on the documented field semantics, the conditional call site in `code.move`, and the test named `self_init_allowed_for_account_address` that explicitly encodes "`None` deploy_owner → always allowed." I recommend a Devin session inspect that function body directly to confirm the exact branch behavior before treating this as fully confirmed.

#[test]
fn init_maybe_initialize_object_owner_changed_aborts() {
    let mut h = new_harness();
    let attacker = h.new_account_at(AccountAddress::from_hex_literal(ADDR).unwrap());
    let victim = h.new_account_at(AccountAddress::from_hex_literal("0xbeef").unwrap());
    let obj = deploy_object_addr(&h, &attacker);

    assert_success!(deploy_to_object(&mut h, &attacker, obj));

    // The attack: publish -> transfer the code object to the victim -> self-init.
    assert_success!(h.run_entry_function(
        &attacker,
        str::parse("0x1::object::transfer_call").unwrap(),
        vec![],
        vec![
            bcs::to_bytes(&obj).unwrap(),
            bcs::to_bytes(victim.address()).unwrap(),
        ],
    ));

    // Ownership changed since deploy -> self-init must abort (no signer minted).
    assert_abort!(
        run_object(&mut h, &attacker, obj),
        EOWNER_CHANGED_SINCE_DEPLOY
    );
}
