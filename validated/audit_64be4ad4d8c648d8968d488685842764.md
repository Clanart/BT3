### Title
Argument injection via attacker-controlled branch name in `checkoutBranch` — `git checkout <branch.name> ...` invoked without a leading `--` separator - ([File: app/src/lib/git/checkout.ts])

### Summary
`getBranchCheckoutArgs` builds `git checkout` arguments by placing the branch name *before* any `--` end-of-options marker, and `branch.name` is derived directly from ref names read back from `git` for a repository the user cloned or fetched (i.e., attacker-controlled data), with no leading-dash/flag-style rejection anywhere in that path.

### Finding Description
`checkoutBranch` builds its argument vector as: [1](#0-0) 
```
function getCheckoutArgs(...) { return ['checkout', ...] }
async function getBranchCheckoutArgs(branch) {
  return [branch.name, ...(remote ? ['-b', nameWithoutRemote] : []), '--']
}
```
The `--` separator is appended **after** `branch.name`, so `branch.name` (and, for remote branches, `nameWithoutRemote`) is passed to `git checkout` as a plain positional argument with no protection against being interpreted as a command-line option if it happens to start with `-`.

`branch.name` ultimately originates from ref names produced by `git for-each-ref`/similar plumbing on a repository — including a repository the user has cloned or fetched from a remote the attacker controls. Desktop only sanitizes/validates branch names it *itself* creates through the UI (`sanitizedRefName`/`testForInvalidChars` in `app/src/lib/sanitize-ref-name.ts`) [2](#0-1) , but it never re-validates ref names it reads back from an untrusted remote after fetch/clone. Git's low-level ref format does not forbid a leading `-` in a ref name (only `git branch`'s own CLI refuses to *create* such an ambiguous name), so an attacker who controls the remote repository content can push/create a ref such as `refs/heads/--upload-pack=/tmp/evil` or a name matching a real `git checkout` flag (e.g. `--orphan=x`, `-B`, `--recurse-submodules`), and Desktop will read this into a `Branch` object and later execute `git checkout <that literal string> ...` when the user checks it out from the branch list.

This differs from the Sherlock report only in mechanism, not in the broken invariant: both cases pass an attacker-influenced identifier directly into a privileged operation (`bulls[contractId] = recipient` vs. `git(['checkout', branch.name, ...])`) without validating that the value is safe/expected, allowing the attacker-supplied value to be misinterpreted by the downstream consumer (recipient becomes `address(0)`; branch name becomes a `git` option).

### Impact Explanation
If the attacker can select a ref name that collides with a meaningful `git checkout` option (e.g., `--recurse-submodules`, `-b`, `--orphan=<name>`, or `--`-adjacent flags depending on the installed git version), running the checkout could alter checkout behavior unexpectedly (e.g., silently creating an orphan branch or triggering submodule recursion into attacker-controlled remotes), which can lead to corruption of the user's working state or execution of further attacker-controlled operations (submodule URLs are themselves attacker controlled in a hostile repo). This satisfies the "silent corruption of what the user commits/checks out" and potential command-execution-adjacent impact classes called out as valid.

### Likelihood Explanation
Requires the user to open a malicious cloned/fetched repository (a supported valid-impact vector) and then select the maliciously-named branch from the branch list in the UI — a normal, expected user action, not privileged or requiring local/physical access. However, exploitability is bounded by which `git checkout` flags are dangerous versus merely disruptive, and by whether git's ref-creation tooling used by the attacker (e.g., direct `.git/packed-refs` manipulation or `update-ref`) permits such names to survive a fetch into Desktop's ref listing — this could not be fully confirmed from the indexed code alone.

### Recommendation
Prepend `--` (or otherwise clearly separate options from operands) immediately after `checkout`/`branch`, e.g. `['checkout', '--', branch.name]` and `['checkout', branch.name, '-b', nameWithoutRemote, '--']` → `['checkout', '--no-guess', branch.name, ...]`/`['checkout', '-b', nameWithoutRemote, '--', branch.name]`, ensuring untrusted ref names can never be parsed as options. Apply the same treatment to `createBranch` in `app/src/lib/git/branch.ts` (`git(['branch', name, startPoint])`), which has the identical missing-separator pattern. [3](#0-2) 

### Proof of Concept
1. Attacker creates/hosts a git repository containing a ref literally named `--orphan=pwned` (created via low-level `git update-ref refs/heads/--orphan=pwned <sha>`, bypassing `git branch`'s own name validation).
2. Victim clones/fetches this repository in GitHub Desktop; Desktop lists the branch using the raw ref name as `branch.name`.
3. Victim selects this branch to check out; Desktop calls `checkoutBranch`, producing arguments `['checkout', '--orphan=pwned', '--']` (or similar), which `git` parses as the `--orphan` option rather than a ref name, changing checkout semantics without the user's knowledge. [4](#0-3) 

**Uncertainty**: I could not verify from the indexed code (a) how `Branch.name`/`nameWithoutRemote` values are parsed from `for-each-ref` output for edge-case names beginning with `-`, or (b) whether an upstream `dugite`/git version guard already rejects such refs during fetch. A background Devin session with full repo/checkout access would be needed to confirm the exact ref-parsing path in `app/src/lib/git/for-each-ref.ts` and reproduce end-to-end.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,

): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)

  await git(args, repository.path, 'checkoutBranch', opts)

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

export async function createBranch(
  repository: Repository,
  name: string,
  startPoint: string | null,
  noTrack?: boolean
): Promise<void> {
  const args =
    startPoint !== null ? ['branch', name, startPoint] : ['branch', name]

  // if we're branching directly from a remote branch, we don't want to track it
  // tracking it will make the rest of desktop think we want to push to that
  // remote branch's upstream (which would likely be the upstream of the fork)
  if (noTrack) {
    args.push('--no-track')
  }

  await git(args, repository.path, 'createBranch')
}
