### Title
Address-association signature has no chain/domain binding, enabling cross-chain replay of `associate`/Associate-tx signatures - ([File: precompiles/addr/addr.go])

### Summary
The `addr` precompile's `associate` method (and the equivalent Cosmos-level `AssociateTx` path in the EVM ante pipeline) authenticate a caller purely via `keccak256(customMessage)`, where `customMessage` is an arbitrary, caller-supplied string with no chain identifier, contract address, or nonce baked in. This is structurally the same flaw as the reported `ERC20Permit` bug: a signature intended for one deployment/chain can be replayed verbatim on any other chain that shares the same secp256k1 keys (e.g. Sei mainnet vs. testnet/devnet, or a future post-fork chain), because nothing in the signed payload ties it to a specific `chainID`.

### Finding Description
`PrecompileExecutor.associate` recovers the signer purely from `crypto.Keccak256Hash([]byte(customMessage))`: [1](#0-0) 

The `customMessage` is fully attacker/caller controlled and, per the integration test suite, the "canonical" message format used by clients is a fixed, chain-agnostic string with no chain ID or verifying-contract component: [2](#0-1) 

The same absence of chain binding exists in the Cosmos-level `AssociateTx` message type used by the EVM ante preprocessor (`x/evm/ante/preprocess.go` / `AssociateTx.Validate`), which likewise just hashes an EIP-191-wrapped custom message with no chain-id field: [3](#0-2) [4](#0-3) 

Contrast this with the codebase's own EIP-7702 `SetCode` authorization handling, which explicitly recognizes this exact class of bug and defends against it by checking `auth.ChainID` against the local chain before honoring/pre-associating an authority: [5](#0-4) 
The `AuthorityToPreAssociate` doc comment explicitly states the risk this guards against: "a publicly-visible authorization a user signed for another chain ... could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their direct-cast balance and orphaning staking/distribution state." No equivalent chain-id check exists for the `associate` / `associatePubKey` precompile paths or the `AssociateTx` message, despite performing conceptually the same "authenticate then bind an address" operation.

The same unguarded pattern is duplicated across every legacy precompile version (`precompiles/addr/legacy/v575` through `v67`), so the issue is present network-wide across upgrade history, not just in one version.

### Impact Explanation
Association is a security-sensitive, largely irreversible action: it permanently binds an EVM address to a Sei address's pubkey and migrates any pre-existing direct-cast state to the associated account, as the codebase's own EIP-7702 guard comment describes for the sibling code path. Any signature a user produces for one Sei-based network context (e.g. testnet, or a message signed for an unrelated demo/dev environment expecting the "please sign to link" phrase) can be resubmitted verbatim on Sei mainnet (or any other network sharing the message format) by an unrelated third party, since neither the precompile call nor the `AssociateTx` message ever checks a chain identifier. The receiving party has no way to scope their signature to a single deployment. Given the explicit acknowledgment elsewhere in the code that forced association can move balances and orphan staking/distribution state tied to an account, a successful cross-chain replay of an association signature is at minimum an unauthorized-transfer/account-hijack primitive.

### Likelihood Explanation
The `associate`/`associatePubKey` precompile is directly callable by any unprivileged EVM transaction sender at address `0x0000000000000000000000000000000000001004`, requiring only a valid ECDSA signature over an arbitrary string — no special privilege, no interaction with a victim beyond obtaining a previously-published signature (e.g. from a testnet integration, a forked/staging deployment, or another chain that reuses the same "please sign this message" convention). The precondition ("address not already associated" check in `associateAddresses`) limits replay to addresses not yet associated on the target chain, which is the common state for most users before their first Sei transaction, keeping the exploit window wide open.

### Recommendation
Short term: include the chain identifier (and ideally a Sei-specific domain separator/contract address, similar to EIP-712 domain separation) inside the message that is hashed and signed for both the `associate`/`associatePubKey` precompile methods and the `AssociateTx`/legacy Associate paths, mirroring the `ChainID` check already implemented for EIP-7702 `SetCode` authorizations in `AuthorityToPreAssociate`. Long term: standardize all custom signature schemas across the codebase (association, `SetCode` authorizations, any future permit-like flows) with a documented, chain-bound domain-separation scheme, and add regression tests asserting that association signatures crafted for a different `chainID`/network are rejected.

### Proof of Concept
1. On Sei Chain A (e.g. testnet, `chainID = X`), a user signs `customMessage = "Please sign this message to link your EVM and Sei addresses..."` with their private key, producing `(v, r, s)`. Nothing in this signed payload references chain `X`.
2. This signature (and the plaintext `customMessage`) is observed by a third party (e.g. from a public testnet tx, a demo dApp, or a compromised RPC log).
3. On Sei Chain B (mainnet, `chainID = Y`), the third party calls `addr.associate(v, r, s, customMessage)` at `0x...1004` before the victim's address has been associated there.
4. `PrecompileExecutor.associate` recomputes `keccak256(customMessage)` (no chain check), recovers the same pubkey/EVM/Sei address pair, and calls `associateAddresses`, permanently binding the victim's address on chain B without their consent on that chain — exactly analogous to the `ERC20Permit` chain-fork replay scenario in the original report. func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

// AuthorityToPreAssociate returns the authority of an EIP-7702 authorization that should be
// associated with its true (pubkey-derived) Sei address before execution, or ok=false.
//
// It mirrors go-ethereum's StateTransition.validateAuthorization (chain id, nonce overflow,
// authority code, and account-nonce checks) so that pre-association happens only for
// authorizations the EVM will actually apply, and additionally skips authorities that are
// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true
