### Title
Malformed participant proof set causes panic (node crash) in `GeneratorPromotion::complete` — ([File: crypto/dkg/promote/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary
`GeneratorPromotion::complete` validates only the count and upper bound of the supplied `proofs` map, then indexes it with `.unwrap()` for every participant `1..=n` other than itself. A participant who submits a proof set that includes the completer's own index `params.i()` while omitting a different participant triggers an unconditional panic, crashing the process. This is the Serai analog of CVE-2023-22068's reachable-crash / availability bug class: untrusted input reaching an unchecked indexing path causes a complete denial of service of the node.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` performs two checks on the attacker-influenced `proofs: &HashMap<Participant, GeneratorProof<C1>>`:

- `proofs.len() == params.n() - 1` (line 125)
- every key satisfies `u16::from(key) <= params.n()` (lines 132–136)

It never checks that the keys are exactly the set `{1..=n} \ {params.i()}`. The loop at lines 140–156 then does:

```rust
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();   // line 146 — panics
```

A malicious participant can construct a map of size `n - 1` whose keys are all `<= n` but which contains `params.i()` (the completer's own index) and omits some other participant `j`. All validation passes, and `proofs.get(&j).unwrap()` at line 146 panics. `Participant` keys are attacker-chosen message fields, so this is reachable purely from a participant-supplied message during the promotion ceremony — the same reachability class as `read_share`/`read_preprocess` inputs in the signing flow.

### Impact Explanation
Serai's binaries install panic hooks that terminate the whole process on any task panic (e.g., `std::process::exit(1)` in the relayer's hook), so this is not a contained error — it is a repeatable crash of the validator/processor node, directly analogous to the CVE's "hang or frequently repeatable crash (complete DOS)". Because the attacker's malformed proof set is deterministic, the crash is reliably repeatable across retries of the promotion, letting one participant indefinitely stall a key-promotion/key-rotation session by crashing each victim node every time it processes the message set.

### Likelihood Explanation
- Reachability: `GeneratorProof::read` (lines 72–77) deserializes participant-supplied bytes, and `complete` is called on the collected map. The `Participant` keys of the map are entirely controlled by the submitting peer.
- The required condition is trivial to satisfy: submit `n - 1` proofs keyed to any `n - 1` participant indexes `<= n` that aren't exactly the expected set — no valid proofs, forgeries, or collusion needed, since the panic happens before any proof verification for the missing entry.
- Constraints: the attacker must be a participant in the DKG/promotion session (a validator holding a key share slot). Given the crash aborts the victim's process mid-ceremony, one malicious participant per attempt suffices. This maps to Medium severity: high-privileged (registered participant) attacker, availability-only impact — matching the source CVE's 4.9 profile.

### Recommendation
Replace the length+bound validation with an exact set-membership check: verify that `proofs.keys()` equals `{Participant(p) | p in 1..=n, p != params.i()}`, or replace `proofs.get(&i).unwrap()` at line 146 with `proofs.get(&i).ok_or(PromotionError::IncorrectAmountOfParticipants { .. })` / a dedicated `MissingParticipant` error so a malformed set is rejected instead of crashing the node. The same pattern (`HashMap` indexed by `Participant` after only a length check) should be audited elsewhere in the DKG crates.

### Proof of Concept
Conceptual trigger against `GeneratorPromotion::<C1, C2>::complete` for a completer with `params.i() = 1`, `n = 3` (so `t = n = 3`):

1. Attacker (participant 2) submits a `proofs` map with keys `{1, 2}` — i.e., one entry keyed to the completer's own index `1` and one to itself `2`, omitting participant `3`.
2. `proofs.len() == 2 == n - 1` passes; both keys `<= n` pass.
3. Loop iteration `i = 3`: `i != params.i()`, so `proofs.get(&Participant(3)).unwrap()` executes on a missing key → `panic!` → process abort under Serai's panic hook.

No forged cryptography is required; the panic occurs before `proof.proof.verify` is reached for participant 3, so even garbage `GeneratorProof` bytes suffice.

```rust
// n = 3, our params.i() = 1
let mut proofs = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof_a); // completer's own index
proofs.insert(Participant::new(2).unwrap(), attacker_proof_b); // participant 3 omitted
promotion.complete(&proofs); // panics at crypto/dkg/promote/src/lib.rs:146
```

    if proofs.len() != (usize::from(params.n()) - 1) {
      Err(PromotionError::IncorrectAmountOfParticipants {
        t: params.n(),
        n: params.n(),
        amount: proofs.len() + 1,
      })?;
    }
    for i in proofs.keys().copied() {
      if u16::from(i) > params.n() {
        Err(PromotionError::InvalidParticipant { n: params.n(), participant: i })?;
      }

    verification_shares.insert(params.i(), self.proof.share);
