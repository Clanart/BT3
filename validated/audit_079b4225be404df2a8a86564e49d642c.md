This confirms the analog: contract addresses generally are NOT auto-associated (only `wasm` contracts can call `AssociateContractAddress`, and only for existing wasm contracts). Regular EVM contracts deployed via CREATE/CREATE2 have no automatic Sei-address association unless someone explicitly deploys them via a Sei-signed tx that itself does the sender association — but the *contract address itself* (the `to` recipient) has no pubkey to sign an association message, so it can never call `associate()`. This means any pointer-token (`CW20ERC20Pointer.sol`, and the reverse `ERC20CW20Pointer` CW20 contract) `transfer()`/`transferFrom()` sent to such a contract address reverts permanently via `AddrPrecompile.getSeiAddr()`.

### Title
CW20 pointer ERC20 token transfers permanently revert (and can permanently freeze funds) when sent to unassociated EVM addresses, including un-associable contract addresses - (File: contracts/src/CW20ERC20Pointer.sol)

### Summary
The `CW20ERC20Pointer` contract, which wraps a CW20 token as an ERC20 (and symmetrically the ERC20→CW20 pointer path), enforces an implicit "valid recipient" restriction: `transfer`/`transferFrom` resolve the EVM `to`/`from` address to a Sei address via the `addr` precompile's `getSeiAddr`, which reverts with "EVM address ... is not associated" whenever the target has never associated [1](#0-0) [2](#0-1) . This mirrors the reported Liquity `_requireValidRecipient` pattern: a token-level restriction on which addresses may receive transfers, invisible to 3rd-party integrators who treat the pointer as a standard ERC20.

### Finding Description
`CW20ERC20Pointer.transfer`/`transferFrom` call `AddrPrecompile.getSeiAddr(to)` (and `from`) before executing the CW20 `transfer`/`transfer_from` message [1](#0-0) . `getSeiAddr` unconditionally reverts if the EVM address has no stored Sei-address mapping [2](#0-1) , confirmed by the integration tests exercising "transfer to unassociated address should fail" [3](#0-2) .

Association only happens automatically for EOAs the first time they sign/send a Sei-side transaction (`EVMPreprocessDecorator.AnteHandle` associates the tx sender) [4](#0-3) . For contracts, the only path is the explicit `MsgAssociateContractAddress`, which requires the address to already be a **deployed wasm contract** — plain EVM contracts (deployed via CREATE/CREATE2, e.g. a DEX router, vault, or smart-contract wallet) can never be associated this way, and since a contract cannot produce an ECDSA signature over the association message, it can never call `addr.associate()` either [5](#0-4) .

Consequently, any 3rd-party contract that accepts arbitrary `to` addresses and forwards a CW20-pointer ERC20 balance to them (e.g., a router, vault, or any composable DeFi primitive) will unconditionally revert whenever the target EVM contract/address has not been associated — exactly the "3rd-party interaction disturbance" pattern described in the report, since the restriction is enforced deep in the pointer contract/precompile rather than being visible or avoidable by the integrator.

### Impact Explanation
Beyond simple reverted calls (composability breakage/DoS for integrators), this can cause **permanent freezing of funds**: if pointer-token balances are ever transferred to (or accrue at) a contract address that can never obtain a Sei-address association (any non-wasm EVM contract), those balances become permanently unrecoverable through the pointer's standard `transfer`/`transferFrom` — the contract itself cannot initiate a signed association, and no third party can associate on its behalf outside the wasm-contract-only `MsgAssociateContractAddress` path.

### Likelihood Explanation
Any user or integrator can trivially trigger this by calling `pointer.transfer(contractAddress, amount)` or by having an unaware DeFi contract forward CW20-pointer tokens to an unassociated recipient (which is the common case for freshly deployed EVM contracts) — no special privileges are required, and the test suite already demonstrates unassociated transfers silently/explicitly fail [3](#0-2) .

### Recommendation
Short term: have the pointer contracts fall back to a deterministic cast-address balance/transfer path (as bank/native transfers already do via `GetSeiAddressOrDefault`/cast-address semantics) instead of hard-reverting on `getSeiAddr` failure, so transfers to unassociated EVM addresses still land in a recoverable location [6](#0-5) . Long term, provide a permissionless mechanism to associate arbitrary (non-wasm) contract addresses, or document/guard the pointer's ERC20 interface so integrators can detect and avoid sending to un-associable recipients before funds become stuck.

### Proof of Concept
1. Deploy a `CW20ERC20Pointer` for an existing CW20 token, and separately deploy any plain EVM contract `C` (e.g. a minimal forwarder) that is never sent a Sei-signed transaction as its own sender (so it has no chance to self-associate, and it is not a wasm contract, so `MsgAssociateContractAddress` cannot target it).
2. Call `pointer.transfer(C, amount)` from a funded holder.
3. The call reverts inside `AddrPrecompile.getSeiAddr(C)` with "EVM address ... is not associated" [7](#0-6) , exactly as reproduced by the existing "transfer to unassociated address should fail" test [3](#0-2) .
4. If tokens are instead delivered to `C` via a mechanism that does not go through this `require`-style guard (or once already inside `C`), `C` can never call `associate()` (no private key) and is not eligible for `MsgAssociateContractAddress` (not a wasm contract), permanently blocking any pointer-token transfer out of or into `C` via the standard ERC20 interface.

func (p PrecompileExecutor) getSeiAddr(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}

	seiAddr, found := p.evmKeeper.GetSeiAddress(ctx, args[0].(common.Address))
	if !found {
		metrics.IncrementAssociationError("getSeiAddr", types.NewAssociationMissingErr(args[0].(common.Address).Hex()))
		return nil, 0, fmt.Errorf("EVM address %s is not associated", args[0].(common.Address).Hex())
	}
	ret, err = method.Outputs.Pack(seiAddr.String())
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

func (server msgServer) AssociateContractAddress(goCtx context.Context, msg *types.MsgAssociateContractAddress) (*types.MsgAssociateContractAddressResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)
	addr := sdk.MustAccAddressFromBech32(msg.Address) // already validated
	// check if address is for a contract
	if server.wasmViewKeeper.GetContractInfo(ctx, addr) == nil {
		return nil, errors.New("no wasm contract found at the given address")
	}
	evmAddr := common.BytesToAddress(addr)
	existingEvmAddr, ok := server.GetEVMAddress(ctx, addr)
	if ok {
		if existingEvmAddr.Cmp(evmAddr) != 0 {
			logger.Error("unexpected associated EVM address exists for contract", "existing", existingEvmAddr, "contract", addr, "expected", evmAddr)
		}
		return nil, errors.New("contract already has an associated address")
	}
	server.SetAddressMapping(ctx, addr, evmAddr)
	return &types.MsgAssociateContractAddressResponse{}, nil
}
