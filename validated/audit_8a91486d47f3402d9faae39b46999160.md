### Title
Stale line-selection race in partial-commit staging allows silent corruption of what gets committed - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages only some lines/hunks of a file ("partial commit"), GitHub Desktop stores the user's approved selection as a set of *line indices* (`DiffSelection`) relative to a diff that was rendered earlier in the UI. At actual staging time, `applyPatchToIndex` in `app/src/lib/git/apply.ts` does **not** reuse that diff — it calls `getWorkingDirectoryDiff` again to fetch a brand-new diff from disk, and then re-applies the old index-based selection (`file.selection.isSelected(absoluteIndex)`) against this newly-fetched diff in `formatPatch` (`app/src/lib/patch-formatter.ts`). If the tracked file's contents on disk change between the moment the user reviewed/selected lines and the moment the commit is actually executed, the hunk/line layout of the new diff can differ from the one the selection indices were computed against, so the wrong lines get included in the patch that is `git apply --cached`'d into the index.

### Finding Description
The commit flow is:
1. UI renders a diff via `getWorkingDirectoryDiff` and the user toggles individual lines/hunks, producing a `DiffSelection` keyed by `absoluteIndex` (an offset into that specific diff's line array) — see `app/src/lib/stores/app-store.ts:3444-3448` (`updateChangesWorkingDirectoryDiff`).
2. When the user commits, `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts:3681-3714`) passes the selected `WorkingDirectoryFileChange` objects (which just carry the `DiffSelection`, not the diff content) straight to `createCommit` → `stageFiles` (`app/src/lib/git/update-index.ts:109-168`).
3. For any file with a partial selection, `stageFiles` calls `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`), which **re-fetches the diff from disk right then**:

There is no check anywhere in this path comparing the diff used to build the selection against the diff used to build the patch (no hash/oid pinning, no "diff changed, abort" guard). Contrast this with `updateChangesWorkingDirectoryDiff`, which does perform exactly this kind of staleness check, but only for refreshing the *displayed* diff — not for the staging/commit code path that actually writes to the index.

The corrupted value is the **`DiffSelection` line-index mapping applied to a different diff than the one it was computed from**, and by extension the contents of the resulting Git blob/commit. Because the file lives in the user's working directory of a cloned/fetched repository, any process capable of writing to tracked files during the (arbitrarily short but nonzero) window between diff render and commit execution can influence which lines end up staged — e.g. a build tool, linter/formatter with "fix on save", file watcher, or another already-running tool operating on the repository. None of the existing size/type guards (`MaxDiffBufferSize`, `isBufferTooLarge`, `isDiffTooLarge`, the `DiffType.Unrenderable`/`Binary`/`Submodule` checks in `apply.ts:62-78`) address this — they only gate on diff *size*, not on diff *staleness relative to the selection*.

### Impact Explanation
This matches the "silent corruption of what the user commits or pushes" impact category directly: the user visually reviews and approves specific lines in the Desktop UI, clicks "Commit", and the tool can end up staging/committing content the user never saw or approved — without any error, warning, or indication that something different was committed. Because Desktop is often used against repositories with active build/watch tooling (webpack, linters, code generators, LFS smudge filters, etc.), the window for such a mutation is realistic and does not require local/physical access, admin rights, or a compromised host — only a normal, already-running development tool (or another instance of the same app, or a slow filesystem sync tool like Dropbox/OneDrive) writing to the working tree.

### Likelihood Explanation
Moderate. It requires a concurrent write to the exact file being partially staged during the small window between the last diff refresh and the actual `git apply --cached` call. This is not exotic in real development environments (format-on-save, auto-generators, sync clients, other git/IDE tooling) and does not require attacker control of network responses — merely something writing into the working directory of the opened repository while Desktop is mid-commit. The severity of the outcome (silently different committed content, potentially re-including code the user explicitly deselected, or vice versa) is high even though it is not deterministically attacker-triggerable on demand.

### Recommendation
Before applying the patch in `applyPatchToIndex`, compare the diff fetched at staging time against the diff the selection was computed from (e.g., by comparing hunk headers/content or an explicit hash of the diff text) and abort the partial-commit for that file with a clear error if they differ, forcing the user to re-review. Alternatively, capture and reuse the exact diff object used to build the `DiffSelection` (passed alongside the file) rather than re-fetching a fresh diff inside `applyPatchToIndex`, eliminating the possibility of index-selection/diff-content mismatch entirely.

### Proof of Concept
1. Open a repository in Desktop with a large text file tracked by git, and have some other process able to modify it (e.g., a script or a second terminal).
2. Modify the file to create hunk A and hunk B differences from `HEAD`. In the Changes view, deselect hunk B (only stage hunk A).
3. Before clicking "Commit", from a separate process rewrite the file so that hunk B's location/content shifts (e.g., insert/remove lines earlier in the file, changing all subsequent line offsets), without touching hunk A's semantic content but changing its absolute line offsets in the new diff.
4. Click "Commit" in Desktop. `applyPatchToIndex` calls `getWorkingDirectoryDiff` again, obtaining a diff with shifted hunk offsets; `formatPatch` reapplies the old `absoluteIndex`-based selection to this new hunk layout.
5. Inspect the resulting commit (`git show`): it will not exactly correspond to "only hunk A as originally displayed" — depending on the shift, unintended lines from hunk B (or partial/misaligned content) can be included or excluded relative to what was shown and approved in the UI, without any warning from Desktop. export async function applyPatchToIndex(
  repository: Repository,
  file: WorkingDirectoryFileChange
): Promise<void> {
  // If the file was a rename we have to recreate that rename since we've
  // just blown away the index. Think of this block of weird looking commands
  // as running `git mv`.
  if (file.status.kind === AppFileStatusKind.Renamed) {
    // Make sure the index knows of the removed file. We could use
    // update-index --force-remove here but we're not since it's
    // possible that someone staged a rename and then recreated the
    // original file and we don't have any guarantees for in which order
    // partial stages vs full-file stages happen. By using git add the
    // worst that could happen is that we re-stage a file already staged
    // by updateIndex.
    await git(
      ['add', '--update', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    // Figure out the blob oid of the removed file
    // <mode> SP <type> SP <object> TAB <file>
    const oldFile = await git(
      ['ls-tree', 'HEAD', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    const [info] = oldFile.stdout.split('\t', 1)
    const [mode, , oid] = info.split(' ', 3)

    // Add the old file blob to the index under the new name
    await git(
      ['update-index', '--add', '--cacheinfo', mode, oid, file.path],
      repository.path,
      'applyPatchToIndex'
    )
  }

  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
