### Title
`calculate_share` emits the ECDH blame proof for a message whose proof-of-possession was never verified, leaking the decryption key for a third party's encrypted share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` returns `PedPoPError::InvalidShare { blame: Some(EncryptionKeyProof) }` on the non-canonical-scalar path **before** the batched proof-of-possession (PoP) verification ever runs. The `EncryptionKeyProof` contains the raw ECDH shared point (`enc_key_recipient * msg.key`) plus a DLEq binding it to the recipient's long-term encryption key. The code comments in `encryption.rs` explicitly state the PoP exists to prevent an attacker from co-opting an honest party's per-message key `X` and tricking the recipient into revealing `b·X`, which would decrypt that honest party's message. That protection is bypassed on this early-return path.

### Finding Description
In `Encryption::decrypt`, the PoP is only *queued* into the caller's `BatchVerifier` (`msg.pop.batch_verify(...)`, encryption.rs:479-485); it is not verified until `batch.verify_with_vartime_blame()` at lib.rs:493. Meanwhile `decrypt` unconditionally computes and returns the `EncryptionKeyProof` containing `key = ecdh(enc_key, msg.key)` (encryption.rs:487-499).

Back in `calculate_share` (lib.rs:479-482), if the decrypted bytes fail `C::F::from_repr`, the function early-returns `InvalidShare { participant: l, blame: Some(blame) }` — **before the batch (and therefore the PoP) is ever checked**. An attacker Eve therefore crafts an `EncryptedMessage` to Bob with `msg.key = X` copied from Alice's honest `EncryptedMessage` to Bob, an arbitrary ciphertext, and any (invalid) PoP. The decrypted "share" is uniform from Eve's viewpoint, so `from_repr` fails with probability ~50% per attempt (for a ~252-bit scalar field). When it does, Bob produces a blame object revealing `b·X`, the exact shared key that decrypts Alice's secret share to Bob — the side channel the PoP comment at encryption.rs:84-88 was designed to eliminate. ### Impact Explanation
Any participant in a PedPoP DKG session can cause the victim recipient to emit an `EncryptionKeyProof` revealing the ECDH shared key for *another* participant's encrypted share message. If the blame proof is published (its intended use — it is transmissible to `BlameMachine::blame` / `AdditionalBlameMachine::blame` and to the coordinator's `VerifyBlame` handler), every observer can derive the ChaCha20 key via `cipher()` and decrypt Alice's `SecretShare` to Bob. This leaks an honest participant's polynomial evaluation `f_alice(bob)` — a confidential DKG share — purely from attacker-supplied message bytes, matching the information-disclosure bug class. Combined with t−1 other compromised shares it contributes to key-share recovery. [4](#0-3) [5](#0-4) 

### Likelihood Explanation
Triggering requires only that the attacker be a DKG participant sending a malformed `EncryptedMessage` (read via `EncryptedMessage::read`, fully attacker-controlled). Eve needs one observation of any honest message to the same recipient to copy `msg.key`, then retries until the decrypted bytes happen to be a non-canonical scalar (~50% probability per attempt, since no verification occurs before this check). Whether the recipient propagates the blame proof depends on integration, but the library's own blame flow (`InvalidShare` → `blame` → coordinator `VerifyBlame`) is built around publishing it. The normal batch path is protected (a failed PoP surfaces as `BatchId::Decryption(l)` → `blame: None`, and `blame_vartime` returns the leftmost failing statement which is the PoP), but that protection never engages on the early-return path. [6](#0-5) [7](#0-6) 

### Recommendation
In `KeyMachine::calculate_share`, do not attach the `EncryptionKeyProof` until the PoP for that message has been verified. Concretely: either (a) verify each `msg.pop` synchronously (or via a batch that is checked) before the `from_repr` early-return, returning `InvalidShare { participant: l, blame: None }` on PoP failure; or (b) defer the non-canonical-scalar error until after `batch.verify_with_vartime_blame()`, recording a per-participant "invalid scalar" flag that produces `InvalidShare` only for messages whose PoP passed. `Decryption::decrypt_with_proof`/`blame_internal` should likewise never be given a proof for a message whose PoP failed.

### Proof of Concept
1. Run a PedPoP session with `ThresholdParams` (t, n ≥ 3). Honest Alice sends Bob `EncryptedMessage { key: X, pop: σ_A, msg: c_A }` encrypting `f_alice(bob)`.
2. Malicious Eve observes Alice's message and sends Bob `EncryptedMessage { key: X, pop: garbage, msg: random_bytes }`.
3. Bob calls `calculate_share`. In `Encryption::decrypt`, `pop` is queued under `BatchId::Decryption(Eve)`; the ECDH `key = b·X` and a valid `EncryptionKeyProof` (DLEq for `enc_key_bob` w.r.t. `X`) are produced regardless.
4. With probability ≈ 1/2, `C::F::from_repr(decrypted)` fails and `calculate_share` returns `Err(InvalidShare { participant: Eve, blame: Some(proof) })` without ever running `batch.verify_with_vartime_blame()`.
5. Bob's integration publishes `proof`. Anyone runs `cipher(context, proof.key)` over Alice's ciphertext `c_A`, recovering `SecretShare` = `f_alice(bob)` — a plaintext secret share leak, defeating the PoP mitigation described at encryption.rs:84-90.

Repeat from step 2 until the `from_repr` failure occurs; expected ~2 attempts.

  pub fn blame_vartime(&self) -> Option<Id> {

      if multiexp_vartime(&flat(&slice[.. split])).is_identity().into() {

      }
