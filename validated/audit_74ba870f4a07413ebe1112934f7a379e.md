### Title
Reward donation via `queueNewRewards`/`donateRewards` distributes instantly against current stake, allowing flash-deposit sandwich to steal LP reward share - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`BaseRewardPoolV2` distributes newly harvested/donated reward tokens as an immediate lump-sum split across whatever balance is currently staked at that exact block, with no time-weighted streaming (no `periodFinish`/`rewardRate`). This mirrors the root cause of the reported FTC issue: a reward is granted based on a single discrete action's size (there, position-open size; here, current stake at harvest time) rather than being accrued proportionally to the duration/risk the actor actually bore, and there is no penalty/clawback for immediately reversing the action.

### Finding Description
`_provisionReward` in `BaseRewardPoolV2.sol` computes `rewardPerTokenStored` as an immediate function of `totalStaked()` at the moment reward is pushed in: [1](#0-0) 

There is no time-weighted accrual mechanism (e.g., a `rewardRate` streamed over `periodFinish`); the entire incoming reward is divided by whoever is staked right now. `totalStaked()`/`balanceOf()` read live values from `MasterMagpie`'s `stakingInfo`, which are updated the instant a user calls `deposit`/`depositFor`: [2](#0-1) [3](#0-2) 

The reward feed itself is permissionless and predictable: anyone can call `WombatPoolHelper.harvest()` / `WombatStaking.harvest()`, which pulls WOM (and bonus token) rewards from the underlying Wombat exchange and immediately pushes them into the LP's `BaseRewardPool` via `queueNewRewards`: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

Because `deposit`/`withdraw` in `MasterMagpie`/`WombatPoolHelper` carry no cool-down, minimum-holding-time, or forfeiture-on-immediate-exit logic (unlike, e.g., `vlMGP`'s `_calExpireForfeit` mechanism used for locked positions), a wallet can:
1. Deposit LP (via `WombatPoolHelper.deposit`) immediately before calling (or being front-run/back-run around) `harvest()`.
2. Let `harvest()` push the freshly earned WOM/bonus rewards into `BaseRewardPoolV2`, which instantly credits `rewardPerTokenStored` proportional to the depositor's now-inflated share of `totalStaked()`.
3. Immediately call `withdraw()` to unstake and claim the earned reward in the same block (or very shortly after), having borne essentially zero time-at-risk in the pool.

This is structurally identical to the FTC bug: a reward computed from a point-in-time action size, with `onDecreasePosition`/`withdraw` doing "nothing" to claw the reward back, letting a bot capture a disproportionate share of rewards meant to be earned by genuine, sustained liquidity providers.

### Impact Explanation
Every harvest event dilutes and effectively transfers a portion of genuine LPs' earned WOM/bonus-token rewards to an opportunistic depositor who bears no meaningful holding-time risk. Because harvests recur (any user can trigger `harvest()`, and it also runs implicitly on deposit/withdraw flows via `_toMasterWomAndSendReward`), this can be repeated across every pool and every harvest cycle, resulting in a continuous drain of unclaimed/yet-to-be-earned yield away from long-term stakers - a theft of user's earned yield.

### Likelihood Explanation
Medium: it requires the attacker to time a deposit closely around a harvest call (which they can trigger themselves permissionlessly via `harvest()`), and to have enough capital to dominate `totalStaked()` at that instant to capture a meaningful share (large LP pools reduce the attacker's relative share, similar to how the FTC report's severity was downgraded to medium due to assumptions about magnitude/likelihood). No governance, oracle, or privileged role is needed — any ordinary wallet can execute the deposit→harvest→withdraw sequence.

### Recommendation
Stream rewards over a fixed duration (a `rewardRate`/`periodFinish` model as in standard Synthetix-style `StakingRewards`) instead of crediting `rewardPerTokenStored` instantly against the current stake snapshot, and/or impose a minimum staking duration or exit fee analogous to `vlMGP`'s `_calExpireForfeit` before a depositor is eligible to withdraw and claim freshly queued rewards, so that reward accrual is proportional to actual time-at-risk rather than an instantaneous balance around a harvest event.

### Proof of Concept
1. Attacker calls `WombatPoolHelper.deposit(largeAmount, minLiquidity)`, which stakes into `MasterMagpie` and instantly updates `balanceOf`/`totalStaked()` in `BaseRewardPoolV2` (`rewards/BaseRewardPoolV2.sol:126-136`, `rewards/MasterMagpie.sol:482-505`).
2. Attacker (or anyone) calls `WombatPoolHelper.harvest()` → `WombatStaking.harvest()` → `_toMasterWomAndSendReward` → `_sendRewards` → `IBaseRewardPool.queueNewRewards` (`wombat/WombatStaking.sol:331-335,671-696,755-760`), which calls `_provisionReward` and instantly bumps `rewardPerTokenStored` based on the current `totalStaked()` that now includes the attacker's large deposit (`rewards/BaseRewardPoolV2.sol:290-313`).
3. Attacker calls `WombatPoolHelper.withdraw(largeAmount, minAmount)`, which unstakes from `MasterMagpie` (harvesting/crediting the attacker's `userRewards` at the just-inflated `rewardPerTokenStored`) and returns the attacker's principal LP tokens, having captured a share of the harvested reward proportional to their momentary stake rather than actual time-weighted contribution.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
