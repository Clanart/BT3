### Title
Integer overflow in `EpsCopyInputStream::ReadPackedFixed` when accumulating packed fixed-width elements into a near-`INT_MAX`-sized `RepeatedField` - (File: `src/google/protobuf/parse_context.h`)

### Summary
The Guacamole CVE-2023-43826 invariant is: a length/size value taken from attacker-controlled protocol data is used in arithmetic that determines a buffer size/offset without being checked for integer overflow, leading to memory corruption. The Protobuf analog is in `EpsCopyInputStream::ReadPackedFixed()` (the binary-wire parser used for packed `fixed32/fixed64/sfixed32/sfixed64/float/double` repeated fields), where the element count derived from an attacker-controlled packed-field length is added to the pre-existing `RepeatedField` size using plain `int` addition instead of the overflow-checked `internal::CheckedAdd` used by the sibling varint-array path, then used to size a reservation and drive a `memcpy`.

### Finding Description
`ReadPackedFixed<T>` computes, from the wire-supplied packed length: [1](#0-0) 
```
int num = size / sizeof(T);
int block_size = num * sizeof(T);
if (num == 0) return size == block_size ? ptr : nullptr;
int old_entries = out->size();
out->ReserveWithArena(arena, old_entries + num);
auto dst = out->AddNAlreadyReserved(num);
...
std::memcpy(dst, ptr, block_size);
```
`old_entries + num` is a plain signed-`int` addition with no overflow check. Compare this to the sibling packed-varint path in the same file, which explicitly guards the equivalent addition: [2](#0-1) 
```
out.ReserveWithArena(arena, internal::CheckedAdd(out.size(), count));
...
out.ReserveWithArena(arena, internal::CheckedAdd(old_size, count));
```
`ReadPackedFixed` has no such `CheckedAdd` call — the missing invariant is exactly analogous to Guacamole's missing overflow check on VNC-server-supplied lengths before they're used in buffer-size arithmetic.

The `size` argument to `ReadPackedFixed` comes directly from the wire-encoded packed-field length (`ReadSize`/`ReadVarintSizeAsInt`), attacker-controlled and bounded only by the default total-bytes parse limit (~2^31-1 bytes, i.e. up to `INT32_MAX`). `old_entries` is the current size of the target `RepeatedField<T>`, which a client-facing application can grow close to `INT_MAX` via repeated `MergeFrom`/`ParseFrom` calls that repeatedly append packed data into the same message field (a supported, ordinary use of the public parsing API — e.g. streaming/merging multiple wire-format chunks into one message). When `old_entries + num` overflows `int32`, the wrapped (small or negative) value is passed to `ReserveWithArena`, causing the underlying array to be under-allocated relative to the `num` elements about to be written by `AddNAlreadyReserved`/`memcpy`, corrupting heap memory beyond the actual allocation.

This exact scenario is captured, and left explicitly unresolved, by two disabled unit tests in the repository: [3](#0-2) 
```
// TODO: Re-enable once parsing overflow is fixed.
TEST(RepeatedFieldIsFullTest, DISABLED_MergeFromPacked) {
  ...
  msg.mutable_packed_bool()->resize(std::numeric_limits<int>::max(), false);
  ...
  EXPECT_FALSE(msg.MergeFromString(serialized));
  EXPECT_EQ(msg.packed_bool_size(), std::numeric_limits<int>::max());
}
```
and the analogous `DISABLED_MergeFrom` for non-packed repeated fields, both annotated `TODO: Re-enable once parsing overflow is fixed`, confirming this is a known, currently unresolved overflow class in this checkout, not a hypothetical one.

### Impact Explanation
If reachable, the wrapped/undersized reservation followed by an unchecked `memcpy` of `block_size` bytes into a too-small allocation is a classic heap buffer overflow, matching Guacamole's "memory corruption, possibly allowing arbitrary code execution" impact class. The consuming application only needs to expose an ordinary `ParseFrom`/`MergeFrom` call over a repeated packed fixed-size field on a message that is (or can be driven to be) close to `INT_MAX` elements — plausible for long-lived server processes that accumulate repeated-field data from many parses into one message object.

### Likelihood Explanation
Likelihood is constrained: it requires the target `RepeatedField` to already contain on the order of `INT_MAX` elements (requiring ~8GB+ of prior data for 4-byte elements, more for 8-byte), which is an unusual but not impossible operational condition (e.g., a long-running aggregation service). The repository's own disabled tests demonstrate the developers are aware this overflow is currently unfixed for both packed and non-packed repeated-field merges, which raises confidence this is a real, currently-present gap rather than a speculative one — but it is also gated behind a large pre-existing allocation, which is why the tests are marked to skip on low-memory environments and are disabled rather than enabled-and-expected-to-fail-safely.

### Recommendation
Apply `internal::CheckedAdd(old_entries, num)` (matching the pattern already used in `ReadPackedVarintArrayWithField`) before calling `ReserveWithArena` in `ReadPackedFixed`, and reject the parse (return `nullptr`) on overflow. Apply the same fix to the analogous non-packed repeated-fixed accumulation path, then re-enable the `DISABLED_MergeFrom` / `DISABLED_MergeFromPacked` tests in `repeated_field_unittest.cc` as regression coverage.

### Proof of Concept
A full end-to-end trigger was not executed (it requires allocating and populating a `RepeatedField` to near `INT_MAX` elements, which is memory-prohibitive to run in this environment and is exactly why the existing tests are gated behind `RunLargeMemoryTests()`/`GTEST_SKIP()`). The reachable code path and missing check are demonstrated directly by the repository's own (currently disabled) test: [4](#0-3) 
which constructs `msg.mutable_packed_bool()->resize(INT_MAX, false)` then merges a serialized single-element packed-bool payload into it — the exact `old_entries + num` overflow condition in `ReadPackedFixed`/packed-bool parsing — and expects (once fixed) that the parse fails safely rather than overflow silently. No sanitizer run was performed; this is a static code-path/invariant analysis, not an executed reproduction.
