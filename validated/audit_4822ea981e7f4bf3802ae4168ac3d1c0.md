### Title
Global disabling of Git's clone symlink/embedded-repository protection via `GIT_CLONE_PROTECTION_ACTIVE=false` - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment for every `git clone --recursive` invocation, regardless of the remote's transport (`https`, `ssh`, `git`, or `file`). This environment variable is Git's own internal signal used by the embedded-repository/symlinked-`.git` protection machinery added to defend against the class of vulnerabilities behind CVE-2024-32002 (and related fixes), where a maliciously crafted repository/submodule can place a symlink at the location Git expects a `.git` directory (or an embedded `.git` inside a working tree entry) so that subsequent checkout/hook-writing operations follow the symlink and write files outside the intended clone destination — leading to code execution (e.g. by overwriting hook files or configuration outside the repo).

### Finding Description
The comment in the code ("to allow local/file transports") suggests the intent was to relax Git's local-clone hardlink/protocol restrictions for `file://`-style local clones. In practice, though, the override is applied to the whole `env` object passed into every `git clone` call, with no branching on the URL scheme [3](#0-2) . Because environment variables are inherited by the Git process itself and any subprocesses it spawns (including recursive submodule fetch/checkout operations triggered by `--recursive`), setting this variable to `'false'` disables Git's protections process-tree-wide for the entire clone, not just for the local-transport code path that presumably motivated the change. This means a malicious repository hosted on any remote (GitHub-hosted HTTPS included) with a submodule or tree entry engineered to exploit the symlinked-`.git`/embedded-repository class of attack would not be blocked by Git's built-in defenses when cloned through Desktop.

### Impact Explanation
If exploited, a crafted repository could redirect Git's checkout/hook-writing logic to write files outside the intended clone directory (e.g., into a symlinked `.git` that points elsewhere on the filesystem), which is the core primitive behind CVE-2024-32002-class remote code execution: planting or overwriting hook scripts or configuration files that get executed on subsequent Git operations. This satisfies the "code execution / file write outside the repo" impact criteria for attacker-controlled repository content cloned via Desktop.

### Likelihood Explanation
Every clone Desktop performs (not just local ones) passes through this code path, since `envForRemoteOperation` returns no transport-specific gating and the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` line runs unconditionally before branch/URL arguments are even added [4](#0-3) . Any user cloning a malicious public repository (or a repository containing a malicious nested submodule) through the normal "Clone repository" flow would be affected without any unusual steps.

### Recommendation
Scope the `GIT_CLONE_PROTECTION_ACTIVE` override so it is only applied for `file://` (or otherwise verified local-filesystem) URLs, and leave Git's default protections active for all remote transports. Ideally, avoid disabling this protection at all; if local-clone functionality requires it, gate it behind an explicit check of the URL protocol before constructing `env`.

### Proof of Concept
1. Set up a malicious Git repository (or one containing a submodule) engineered per the CVE-2024-32002 technique: a tree entry causing a symlink to be created at the location a `.git` directory/hook path would normally reside for a nested repository, so that the recursive submodule checkout follows the symlink.
2. Host it over `https://` (a normal GitHub-style remote), not `file://`.
3. Clone it via Desktop's clone flow, which invokes `clone()` in `app/src/lib/git/clone.ts`, injecting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into the environment for the `git -c init.defaultBranch=... clone --recursive -- <url> <path>` invocation.
4. Compare against running the same clone with a stock Git CLI (which sets/relies on its own internal protection state) — Git should refuse or neutralize the symlink; verify whether Desktop's forced `GIT_CLONE_PROTECTION_ACTIVE=false` env causes Git to instead follow the symlink and write outside `<path>`.

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
