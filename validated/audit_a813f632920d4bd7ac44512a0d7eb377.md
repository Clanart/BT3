### Title
Attacker-controlled participant indexes in PedPoP blame evaluation panic the evaluating node via unchecked `HashMap` indexing - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` accept an accusation tuple `(sender, recipient, msg, proof)` that is fully attacker-influenced. `blame_internal` passes `recipient` into `Decryption::decrypt_with_proof`, which indexes `self.enc_keys[&decryptor]` without a membership check. `enc_keys` is only populated for participants `1 ..= n` (in `AdditionalBlameMachine::new`) or for registered DKG participants. Supplying a `recipient` (or `sender`, which indexes `self.commitments[&sender]` in `blame_internal`) outside that set causes a `HashMap` index panic, aborting the process evaluating blame — a denial of service triggered entirely by untrusted protocol input, analogous in class to CVE-2023-33202's crash-on-crafted-input DoS.

### Finding Description
`Decryption::new` starts with an empty map and `Decryption::register` inserts one key per registered participant [1](#0-0) . `AdditionalBlameMachine::new` registers only indexes `1 ..= n` derived from commitment messages [2](#0-1) . When blame is evaluated, `decrypt_with_proof` first checks the message's Schnorr PoP — which the sender of the message legitimately produced, so an accusation carrying a real captured message passes [3](#0-2) . It then dereferences `self.enc_keys[&decryptor]` inside the DLEq verification call, which panics if `decryptor` was never registered [4](#0-3) . The public entry points take `recipient: Participant` with no bounds validation [5](#0-4) . The same pattern exists for `sender` via `self.commitments[&sender]` [6](#0-5) , and via `self.commitments[&l]` in `calculate_share` is guarded by `validate_map` but the blame path is not [7](#0-6) .

### Impact Explanation
Any party able to submit a blame accusation (a DKG participant, or anyone relaying a malformed accusation to a node running blame evaluation) can crash the evaluating process by naming a `recipient` (or `sender`) index `> n` or `0`-adjacent-but-valid `Participant` not in the map. Rust panics across this path unwind/abort the caller; in a coordinator/processor context this kills the key-generation or dispute-resolution flow. It is a remotely triggerable, deterministic panic — a Medium-severity DoS on liveness, matching the report's bug class of denial of service from processing crafted structured input.

### Likelihood Explanation
The attacker needs only a valid `Participant` value not registered in `enc_keys`/`commitments` and a `msg` whose PoP verifies — trivially satisfied by replaying a legitimate `EncryptedMessage` the attacker sent, or one they observed. `blame` is explicitly documented as callable by non-participants (`AdditionalBlameMachine::new` supports third-party blame evaluation [8](#0-7) ), so the attacker need not be a DKG member to supply the accusation.

### Recommendation
Validate `sender` and `recipient` against `enc_keys`/`commitments` membership at the top of `blame_internal` (returning a defined error or defaulting blame to the accusing party), replacing `map[&key]` indexing with `map.get(&key).ok_or(...)`. Apply the same guard to `self.commitments[&sender]` and to `self.encryption.decrypt`'s `enc_keys[&participant]` lookup [9](#0-8) .

### Proof of Concept
1. Run a PedPoP DKG with `n = 3` (or construct `AdditionalBlameMachine::new(context, 3, msgs)`).
2. Attacker (participant 2) crafts an accusation: `blame(sender = Participant(2), recipient = Participant(7), msg, Some(proof))`, where `msg` is a real `EncryptedMessage` participant 2 previously sent (PoP verifies for `from = 2`).
3. `blame_internal` → `decrypt_with_proof` → `self.enc_keys[&Participant(7)]` → `HashMap` index panic → process abort.
4. Variant: `proof = None` is rejected before the index, so use `Some(proof)` with a valid DLEq over the registered key; or use a `sender` index `> n` to panic at `self.commitments[&sender]` after decryption succeeds.

Note on residual uncertainty: whether the panic aborts or merely unwinds depends on the embedding binary's panic strategy, and whether blame evaluation runs in the same critical process is deployment-dependent; the unchecked indexing itself is confirmed in code.
