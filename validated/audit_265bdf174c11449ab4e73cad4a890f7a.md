### Title
Hunk-index misalignment between `extractConflictHunks` and `reassembleResolvedFile` can silently corrupt the Copilot-resolved merge result before commit - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's "Resolve with Copilot" feature parses conflict markers from a file twice, using two **independent, hand-written line-scanners**: once when building the prompt (`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts:179-`), and once when splicing the model's per-hunk answers back into the file on disk (`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts:549-599`). The two scanners are not guaranteed to agree on what counts as a "hunk" for the same input, which is exactly the class of bug described in the seed report: a value (the hunk count / hunk-to-content mapping) is computed in one place and consumed in another place under a different accounting rule.

### Finding Description
`extractConflictHunks` walks the raw file content and, for each `<<<<<<<` line it finds, extracts ours/base/theirs content for the hunk to send to the Copilot model [1](#0-0) . The resulting `hunks.length` for each file becomes the *expected* hunk count that the model's response must match, enforced by `validateResolutionPaths` [2](#0-1) .

Later, `reassembleResolvedFile` re-parses the **same raw content** from scratch, independently, to decide where to splice each of the model's `hunkResolutions[]` entries. Critically, this second parser contains extra validation that the first one is not shown to share: it only treats a `<<<<<<<` block as a real conflict hunk if it can find both a `=======` separator and a `>>>>>>>` closer before the next marker/EOF; otherwise it explicitly falls back to copying the line through as ordinary content **without** advancing `hunkIndex` [3](#0-2) . The function's own doc comment acknowledges this divergence is possible: "A `<<<<<<<` line that is not followed by both a `=======` separator and a closing `>>>>>>>` before EOF is treated as regular file content ... to avoid data loss from malformed or stray markers" [4](#0-3) .

Because the two functions are separately implemented regex/line scanners over attacker-influenced file bytes (the conflicted file's content is determined by the merge of a fetched/pulled branch, PR, or remote that an attacker can fully control), any input that the two scanners disagree on — e.g. an unbalanced/malformed marker sequence, markers embedded in content that only one scanner treats specially, or edge cases in how each scanner walks past a marker — produces a **mismatch between the number of hunks the model was asked to resolve and the number of hunk-slots `reassembleResolvedFile` actually fills in**. When this happens, `hunkResolutions[hunkIndex]` (the model's answer meant for conflict block *N*) gets spliced into a different conflict block position than the one it was generated for, because `hunkIndex` in the splice function no longer corresponds 1:1 with the hunk index used when building the prompt.

This mirrors the root cause of the seed report precisely: `tick()` computes/mints against one accounting frame (StabilityPool) while `mintRewards()` consumes against a different accounting frame (RAACMinter's own balance) — here, `extractConflictHunks` establishes the "N hunks" contract that is enforced by `validateResolutionPaths`, while `reassembleResolvedFile` applies a *different* rule for what counts as hunk N, breaking the 1:1 correspondence the whole pipeline assumes.

### Impact Explanation
The final write is applied via `_applyCopilotConflictResolutions`, which writes `resolution.resolvedContent` directly to the working-tree file and stages it with `git add` before the merge/rebase/cherry-pick is continued [5](#0-4) . There is no diff/hunk-count re-verification at write time — the guard that exists only checks whether the file is still marked conflicted, not whether the reassembled content is internally consistent [6](#0-5) . If a hunk-index mismatch occurs, the user's "Continue Merge" click silently commits/pushes a file where AI-resolved code from one part of the file has been written into an unrelated location, while the user sees (and approves) a diff/preview built from the *correctly* paired hunk content shown separately via `getResolutionDiff`/`buildFileContents` in the dialog. This is a silent corruption of what the user commits and pushes — the exact "Valid Impact" category called out in the task (attacker controls the merged/fetched repository content; result is silent corruption of committed code), without requiring local access, admin rights, or social engineering beyond a normal merge/rebase against attacker-controlled content.

### Likelihood Explanation
Likelihood is moderate and depends on being able to construct a conflicted file whose marker sequence is parsed differently by the two scanners (e.g., unmatched/nested `<<<<<<<`/`=======`/`>>>>>>>` sequences, or a file that legitimately contains marker-like lines as data). An attacker who controls one side of a merge (a PR branch, a malicious remote, or content merged from a compromised dependency's repo) fully controls the bytes fed to both parsers and can iterate offline against the same regexes (the `oursMarker`/`separatorMarker`/`theirsMarker` patterns are simple and visible in the source) to find an input that both (a) is still accepted as N well-formed hunks by `extractConflictHunks`/`validateResolutionPaths`, and (b) is treated as fewer/differently-bounded hunks by `reassembleResolvedFile`. I was not able to view the remainder of `extractConflictHunks` (past its 200-line excerpt) in this session to confirm whether it performs the identical closing-marker validation as `reassembleResolvedFile`; this is the key open question that determines whether the divergence is trivially reachable or requires a more contrived edge case.

### Recommendation
- Use a single, shared hunk-boundary parser for both prompt-building (`extractConflictHunks`) and result-splicing (`reassembleResolvedFile`) so the two phases can never disagree on what constitutes hunk *N*.
- Have `reassembleResolvedFile` fail closed (throw, forcing the file into the "skipped/manual resolution" path) rather than silently falling back to raw-copy when it cannot find a matching number of well-formed hunks, instead of only relying on the pre-flight `validateResolutionPaths` count check that runs against the *other* parser's count.
- Add a post-splice integrity check that verifies no conflict markers remain in the written file (similar to the check already done on model output at `/^<{7}\s/m` in the validation step [7](#0-6) ) before writing to disk, and abort/flag the file for manual resolution if markers remain or hunk counts don't reconcile at splice time.

### Proof of Concept
Not independently verified end-to-end due to tool-call exhaustion (I could not view the full body of `extractConflictHunks` past line 200 to confirm the exact malformed-marker input that triggers divergence). Conceptually:
1. Attacker crafts a branch/PR such that merging it produces a conflicted file containing a marker sequence where `extractConflictHunks` counts, e.g., 2 hunks (sent to the model, 2 `resolvedContent` entries returned and validated by `validateResolutionPaths`), but `reassembleResolvedFile`'s stricter look-ahead (requiring both a `=======` and a `>>>>>>>` before treating a block as a hunk) only recognizes 1 of those 2 blocks as well-formed.
2. `reassembleResolvedFile` skips the malformed block as raw content without consuming a `hunkResolutions` entry, so `hunkResolutions[1]` (meant for the second/real hunk) is spliced in place of a different one, or leftover raw conflict-marker content remains in the "resolved" file.
3. The user reviews the Copilot result dialog (which computes its preview diff independently via `getResolutionDiff`), sees a plausible diff, clicks "Continue Merge", and `_applyCopilotConflictResolutions` writes/stages the misaligned content, which is then committed and potentially pushed.
