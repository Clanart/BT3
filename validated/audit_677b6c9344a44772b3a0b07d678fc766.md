### Title
Stale line-selection indices are silently re-applied to a freshly-fetched diff when creating a partial commit, causing wrong lines to be committed - (File: app/src/lib/git/apply.ts, app/src/lib/patch-formatter.ts, app/src/models/diff/diff-selection.ts)

### Summary
GitHub Desktop's partial-commit feature (select-lines-to-commit) tracks which lines a user has included/excluded by storing *absolute line indices* in a `DiffSelection` object, independent of the diff content itself. When a commit is actually created, `applyPatchToIndex` fetches a **brand-new** diff (`getWorkingDirectoryDiff`) and blindly re-applies the **old** `DiffSelection` (computed against the diff the user visually reviewed) to that new diff via `formatPatch`. If the working tree changes between the time the user made their line selection and the time the commit patch is built, the index-based selection can point at completely different lines than the ones the user actually reviewed and chose, silently corrupting the resulting commit.

### Finding Description
`formatPatch` (and `formatPatchToDiscardChanges`) determine whether a line is included by calling `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex = hunk.unifiedDiffStart + lineIndex`: [1](#0-0) 

`DiffSelection` itself has no notion of *what* line content a given index corresponds to — it only stores a set of "diverging" absolute indices relative to the diff that was in effect when the user made their selections: [2](#0-1) 

The commit path does not use the diff that was rendered/selected against in the UI. Instead, `applyPatchToIndex` re-fetches the diff immediately before building the patch: [3](#0-2) 

The only place that reconciles a `DiffSelection` against a newer diff is `updateChangesWorkingDirectoryDiff` in the Changes UI store, and even that reconciliation is a coarse *filter*, not a content-aware remap: it recomputes the set of "includeable" absolute indices for the new diff and just intersects the user's existing diverging-index set against it — it does not verify that the line found at a given index is still the same line the user selected: [4](#0-3) [5](#0-4) 

Because this reconciliation is asynchronous (tied to the Changes list UI refresh) and is not invoked on the commit-time code path at all, there is a TOCTOU (time-of-check/time-of-use) gap: the diff a user visually reviewed and selected lines against (diff v1) can differ from the diff fetched at commit time (diff v2), yet the same `DiffSelection` (built from absolute indices of v1) is applied to v2 without any validation that the line identity is preserved.

### Impact Explanation
This breaks the invariant that "the lines the user explicitly checked/unchecked in the diff view are the lines that end up in the commit" — directly matching the impact category of "silent corruption of what the user commits or pushes." A concrete attacker path: a cloned/fetched repository can ship a `clean`/`smudge` filter, `post-checkout`/`post-merge` hook, or any background tool (build watcher, linter/formatter-on-save, LFS smudge) that rewrites tracked files after the user has opened the Changes view and started curating a partial commit (e.g., deselecting a suspicious/malicious hunk). If the file content shifts (lines inserted/removed) before the user clicks "Commit," the fresh diff fetched by `applyPatchToIndex` has different line content at the same absolute indices. The stale selection is then applied to the new diff, so the hunk the user explicitly excluded can be silently re-included (or an intended change silently dropped) with no re-confirmation or warning shown to the user. The commit dialog gives no indication that the diff changed underneath the selection.

### Likelihood Explanation
This does not require local/physical access or an already-compromised host beyond what's already in the accepted threat model (attacker controls repository content / hooks / filters that execute as part of normal clone/checkout/build workflows). It only requires: (1) the user to use the partial-commit feature (select/deselect specific lines — a heavily used Desktop feature), and (2) file content to change between selection and commit, which is a realistic condition given file watchers, format-on-save, LFS smudge filters, and git hooks that Desktop already invokes as part of checkout/fetch. There is no explicit guard in `applyPatchToIndex` or `formatPatch` comparing the diff used to build the selection against the diff used to build the patch, so once the precondition is met the corruption happens deterministically and silently.

### Recommendation
- Bind `DiffSelection` to an identity of the diff it was computed against (e.g., a hash of the diff text/blob OIDs) and refuse to apply a selection to a diff with a different identity; force UI re-selection instead.
- Alternatively, at commit time in `applyPatchToIndex`, compare the newly-fetched diff against the diff currently held by the UI/selection state; if they differ, abort and prompt the user to re-review their selection.
- Make `withSelectableLines` (or an equivalent invoked right before `formatPatch`) content-aware, not just index-aware, so that a diverging index is only preserved if the line text/type at that index is unchanged.

### Proof of Concept
1. In a repository tracked by Desktop, modify a file so it produces multiple hunks.
2. In the Changes view, partially select the file: deselect a specific hunk/line (e.g., a line containing malicious code) so it is excluded from the commit — this stores that line's absolute index as a diverging (non-default) entry in `DiffSelection`.
3. Before clicking "Commit," trigger an external change to the same file that shifts line offsets without changing the total selectable-line count at the same indices (e.g., a smudge filter/hook/format-on-save that reorders or renumbers hunks, or simply insert/delete lines elsewhere in the file via an external editor or script).
4. Click "Commit." `applyPatchToIndex` calls `getWorkingDirectoryDiff` again (fresh diff) and reuses the old `DiffSelection` object built in step 2: `formatPatch(file, diff)` in `app/src/lib/git/apply.ts` line 80.
5. Inspect the resulting commit: the line the user deliberately deselected in step 2 is present (or an unrelated line is now excluded), even though the Desktop UI never displayed the new diff to the user for re-review before committing.

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
