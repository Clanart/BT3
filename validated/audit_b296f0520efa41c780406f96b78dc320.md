### Title
`ThresholdKeys::read` accepts inconsistent key material — a type-confused `Interpolation` tag and an unverified `secret_share`/`verification_shares[i]` binding produce keys whose advertised `group_key` is unspendable - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes attacker-controlled bytes into live threshold key material. A single tag byte selects between `Interpolation::Constant` and `Interpolation::Lagrange` — the analog of the CVE-2024-8638 type-confusion class: the same byte stream is reinterpreted as a different algebraic object based on a discriminator. Neither `read` nor `ThresholdKeys::new` verifies that `C::generator() * secret_share == verification_shares[&params.i()]`, so the deserialized "object" is internally corrupt yet passes all validation and is used for signing and key advertisement.

### Finding Description
`ThresholdKeys::read` reads `(t, n, i)`, then a one-byte interpolation tag: `0` yields `Interpolation::Constant` with `n` attacker-supplied scalar coefficients, `1` yields `Lagrange`. It then reads `secret_share` and `n` verification shares and hands everything to `ThresholdKeys::new`.

`ThresholdKeys::new` checks only: count of verification shares equals `n`, indices `<= n`, and `t == n` for `Constant` (crypto/dkg/src/lib.rs:355-374). The group key is then computed *purely* from the verification shares: `t.iter().map(|i| verification_shares[i] * interpolation_factor(*i, &t)).sum()` over participants `1..=t` (crypto/dkg/src/lib.rs:376-378). At no point is the deserialized `secret_share` checked against `verification_shares[i]` or the resulting `group_key`.

So an attacker supplying bytes to `ThresholdKeys::read` can:
1. Choose `secret_share = x` and set `verification_shares[i] = G*y` with `y != x` — accepted.
2. Flip the interpolation tag (or supply arbitrary `Constant` coefficients when `t == n`) to reinterpret identical point data under a different interpolation, silently changing the derived `group_key` — a tag-driven reinterpretation of the same encoding, the structural analog of V8 object-type confusion.

`view()` then interpolates `secret_share` (crypto/dkg/src/lib.rs:495-497) while `group_key()` and `verification_shares` reflect the attacker-chosen points. `AlgorithmSignatureMachine::complete` even acknowledges this failure mode: "The only known way to cause this ... is to deserialize a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:492-494) — confirming deserialization can produce semantically invalid keys that are otherwise accepted.

### Impact Explanation
The corrupted `ThresholdKeys` advertises a `group_key` that no coalition can sign for: `original_secret_share()` does not correspond to `verification_shares[params.i()]`, so every signing set's summed share fails `algorithm.verify`, and each party's share *does* pass `verify_share` if crafted consistently with the points — yet the aggregate is invalid, or the derived group key belongs to a polynomial nobody shares. In deployment, a node that ingests a `ThresholdKeys` blob (key import, share-distribution, or recovery path) will publish the attacker-chosen `group_key` as its deposit/validator address. Outputs sent to it are reported received but are permanently unspendable — an accepted impact class. Alternatively an attacker crafts keys where the group key embeds their own verification shares while blaming honest shares, corrupting recovery via `recover_key` which trusts `group_key()` and `view()` outputs.

### Likelihood Explanation
Requires an attacker to control bytes fed to `ThresholdKeys::read` — reachable wherever serialized threshold keys are ingested from an untrusted source (key distribution, backup restore, coordinator-supplied key material). Not exploitable against honestly generated in-memory keys, which caps severity at Medium.

### Recommendation
In `ThresholdKeys::new` (or at minimum `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. Also verify for `Interpolation::Constant` that coefficients are consistent (e.g., `interpolation_factor` sanity: sum of `verification_shares[i] * c[i]` over `1..=n` should equal `verification_shares` interpolation and `group_key`), and reject deserialization of keys where `G * secret_share` does not reproduce the claimed share.
