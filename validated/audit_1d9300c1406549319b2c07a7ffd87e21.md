Based on my investigation, the strongest analog I found for the "front-run privilege change" bug class — an attacker-controlled input reaching a security-sensitive operation before existing guards can stop it — is a **git argument-injection gap in the `x-github-client://openrepo` deep-link handler**, not an account/permission race (Desktop has no admin-role model to front-run).

### Title
Git branch-name argument injection via `openRepo` deep link - (File: `app/src/lib/parse-app-url.ts`)

### Summary
The `openrepo` URL action lets a remote attacker (via a crafted deep link the victim clicks) supply an arbitrary `branch` query parameter that flows almost unvalidated into `checkoutLocalBranch`, which ultimately invokes `git checkout <branch>`. The validation used, `testForInvalidChars`, only rejects a fixed set of illegal ref characters and does not reject a leading `-`, so a value such as `--upload-pack=/bin/sh` or other `git checkout`-recognized flags can be smuggled in as the "branch name."

### Finding Description
`parseAppURL` accepts an `openrepo` deep link and only guards the `branch` parameter with `testForInvalidChars(branch)`: [1](#0-0) 

That check uses `invalidCharacterRegex`, defined in `sanitize-ref-name.ts`, which strips control chars, spaces, and a handful of git-refname-illegal symbols (`~^:?*[\|"<>`, `..`, leading/trailing `.`, `.lock`) — but a leading `-` is **not** in that set: [2](#0-1) 

Notably, the sibling function `sanitizedRefName` in the same file *does* strip leading `-`/`+` via `.replace(/^[-\+]*/g, '')`, but `parseAppURL` calls only `testForInvalidChars`, which performs no such stripping and does not fail validation for a leading dash. This means the accepted `branch` value can start with `-`.

The accepted branch string is then routed unmodified through `Dispatcher.openBranchNameFromUrl` into `checkoutLocalBranch`: [3](#0-2) 

This is the identical `openRepositoryFromUrl` path also reachable from the CLI clone-url action: [4](#0-3) 

The parallel PR-checkout branch value is far more strictly constrained to `^pr\/\d+$`, showing the project is aware such values must be format-locked — but the free-form `branch` parameter used for the non-PR case is not: [5](#0-4) 

I was not able to retrieve the exact body of `checkoutLocalBranch`/the underlying git invocation (e.g., whether it prefixes arguments with `--` before the ref) within this session's index, so I cannot confirm with certainty whether the eventual git call is `git checkout -- <branch>` (safe) or `git checkout <branch>` (unsafe, vulnerable to option injection). This is the one piece of the chain I could not verify from local code.

### Impact Explanation
If the underlying checkout call does not use a `--` end-of-options separator before the branch argument, an attacker-controlled deep link (`x-github-client://openrepo/<repo-url>?branch=<malicious-flag>`) that the victim clicks could inject arbitrary `git checkout` options. Depending on the git version and available flags, this can range from confusing/corrupting the checked-out working tree to more severe outcomes via option abuse. This satisfies the "valid impact" bar of attacker-controlled deep link leading to unauthorized file write or corruption of what the user has checked out/commits.

### Likelihood Explanation
Likelihood is **low-to-medium**: it requires the victim to click a crafted `x-github-client://` link (Desktop registers this protocol handler, see `possibleProtocols` in `app/src/main-process/main.ts`), and requires that the downstream checkout call does not already neutralize a leading `-` (unverified). The validation gap itself is concrete and demonstrable independent of the downstream call.

### Recommendation
- In `parseAppURL` (or `testForInvalidChars`), explicitly reject branch values that start with `-` or `+` (mirroring the existing `sanitizedRefName` stripping logic), the same way the `pr` and PR-branch formats are already tightly anchored with regexes.
- Confirm (and if missing, add) a `--` separator before the branch argument in the underlying git checkout invocation so any future validation gap cannot become argument injection.

### Proof of Concept
1. Attacker crafts and distributes a link:
   `x-github-client://openRepo/https://github.com/some/repo?branch=--upload-pack=touch%20/tmp/pwned`
2. Victim, with GitHub Desktop installed and registered as the protocol handler, clicks the link.
3. `parseAppURL` passes `testForInvalidChars('--upload-pack=touch /tmp/pwned')` (dash and `=` are not in the invalid-char set) — the action is accepted as `open-repository-from-url` with `branch: '--upload-pack=touch /tmp/pwned'`.
4. `Dispatcher.openRepositoryFromUrl` → `openBranchNameFromUrl` → `checkoutLocalBranch(repository, branchName)` is called with the attacker string unmodified. [6](#0-5) 

**Caveat:** Step 4's actual exploitability depends on how `checkoutLocalBranch` constructs the git argv, which I could not confirm from the indexed code in this session. If that call already isolates the ref with `--`, this reduces to a (still real) input-validation defect without confirmed code-execution impact, rather than a confirmed argument-injection RCE. I recommend a Devin session with full repo access to inspect `app/src/lib/stores/app-store.ts` / the checkout implementation used by `_checkoutBranch` to close this gap definitively.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
