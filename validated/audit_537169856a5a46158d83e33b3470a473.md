### Title
Unclaimed self-farmed rewards can be permanently redirected to a pool by any unprivileged submitter after `join_pool` - ([File: chia/pools/plotnft_drivers.py])

### Summary
The plotnft v2 pooling reward coin's spending puzzle hash (`RewardPuzzle`) is derived only from the singleton's `launcher_id`, not from the pool epoch/state under which it was farmed. Whether a given unclaimed reward coin can be swept to the user (self-custody) or forwarded to the pool is decided entirely by the *current* live `PlotNFT` state at claim time, and the pool-forwarding path (`forward_pool_reward`) requires no signature from the owner at all. This lets any unprivileged spend-bundle submitter permanently redirect a user's previously self-farmed, unclaimed rewards to a pool the user just joined.

### Finding Description
`PlotNFTPuzzle.reward_puzhash()` computes the address that pool/self-farming rewards are paid to, keyed solely on `self.launcher_id` [1](#0-0) . This address is fixed for the lifetime of the singleton, independent of whether the PlotNFT is currently self-pooling or joined to a pool.

Two different spend paths exist for claiming a reward coin sent to this address:
- `claim_pool_rewards()` — usable only when `self.pooling` is `False` (self-custody), and requires the user's BLS signature via `self.bls_member.solve()` [2](#0-1) .
- `forward_pool_reward()` — usable only when `self.pooling` is `True`, and is built from `pool_proven_spend()`, whose member solution comes from `FixedPuzzleMember` rather than the owner's BLS key [3](#0-2) [4](#0-3) . Tests confirm this path is pushed with an empty aggregate signature `G2Element()` [5](#0-4) [6](#0-5) .

Because `pool_config` (and thus whether `pooling` is `True`/`False`) is a property of the *current* live singleton state rather than being bound to the specific epoch during which a given reward coin was farmed, a reward coin that was farmed while the plot was self-pooling (rightfully belonging entirely to the user) becomes eligible for the signature-free `forward_pool_reward` path as soon as the user's singleton transitions into `FARMING_TO_POOL`/pooling state (e.g. via `join_pool`) — even if the user has not yet claimed it. `PlotNFT.get_next_from_coin_spend()` builds the next `PlotNFTPuzzle` purely from the just-observed singleton state, again with no memory of which past rewards belong to which past state [7](#0-6) .

The `wallet_rpc_api.py` `pw_absorb_rewards()`/`PlotNFT2Wallet.claim_rewards()` path explicitly blocks the user from self-claiming while pooling ("Cannot claim rewards while pooling...") [8](#0-7) , so a user cannot race to claim their old self-farmed rewards once they've joined a pool — but any third party can immediately submit `forward_pool_reward` for those same coins, since it needs no private key and only the (unrelated) singleton coin id/pool config as public knowledge.

### Impact Explanation
This is a concrete unauthorized coin movement: reward funds that were earned by the user while self-pooling — and thus solely theirs — get swept away to the pool's `pool_puzzle_hash` without the user's signature, the moment the singleton transitions to a pooling state, by anyone who observes the pending reward coin and current singleton state on chain (fully public information). The user has no way to protect these funds except claiming them before ever joining a pool, and there is no atomicity/ordering guarantee between "claim old self-farmed rewards" and "join pool" transactions — if the join-pool transaction confirms first (e.g., due to mempool ordering, fee competition, or the user simply forgetting), the funds are irreversibly redirected. This matches the "extra rewards lost when a state-changing action occurs before the user claims" bug class, but is strictly worse than the original report because no privileged/governance action is required — any unprivileged spend-bundle submitter can trigger the loss once the state has changed.

### Likelihood Explanation
Likelihood is Medium-High: any user who farms rewards while self-pooling, does not claim promptly, and later joins a pool (a very ordinary workflow) is exposed. No special timing/race beyond "join_pool spend confirms before user's own claim spend" is required, and the exploiting party (forwarding the reward to the pool) doesn't even need to be malicious — the pool itself has an economic incentive to sweep any reward addressed to the plot's reward puzzle hash, since `forward_pool_reward` is exactly the mechanism a pool operator is expected to use.

### Recommendation
Bind claimability of a reward coin to the pool state that was active when it was farmed (e.g., include the pool state's provable identity — the specific `PoolState`/pool epoch, `heightlock` transition height, or a per-transition commitment — in the reward coin's puzzle/solution constraints), so that `forward_pool_reward` can only sweep rewards farmed under the *current* pool relationship, and rewards farmed while self-pooling remain claimable only by the user via `claim_pool_rewards` regardless of subsequent `join_pool` transitions. Alternatively, require the join_pool transition itself to first sweep/claim any outstanding self-pooling rewards atomically before allowing the state to change.

### Proof of Concept
1. User creates a `PlotNFT2Wallet` in self-custody state and farms several blocks to `p2_singleton_puzzle_hash`, accruing unclaimed reward coins at `reward_puzhash()` (bound only to `launcher_id`) — as in `test_plotnft_lifecycle` [9](#0-8) .
2. Instead of claiming immediately, the user calls `join_pool`, transitioning the singleton to `pool_config != None` (pooling=True) [10](#0-9) .
3. Once the join transaction confirms, self-claim via `claim_rewards`/`claim_pool_rewards` is rejected with "Cannot claim rewards while pooling..." [8](#0-7) .
4. Any third party constructs `PlotNFT.forward_pool_reward(reward)` for the previously self-farmed (pre-join) reward coins and broadcasts it signed with an empty `G2Element()` — exactly as demonstrated in `test_plotnft_pooling_claim`/the "LOSE REWARDS (while pooling)" step of `test_plotnft_lifecycle` [11](#0-10) [6](#0-5) . This succeeds and permanently sends the user's previously self-earned rewards to `guaranteed_pool_config.pool_puzzle_hash`, with the user's `plotnft` wallet balance decreasing accordingly and no compensation.

        self,
