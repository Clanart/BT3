### Title
`_calExpireForfeit` in `mWOMSVBaseRewarder` never forfeits rewards despite `mWomSV.getRewardablePercentWAD` existing to compute partial-lock dilution - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` computes `rewardableAmount = _amount` unconditionally and never calls `mWOMSV.getRewardablePercentWAD(_account)`, so `forfeitAmount` is always `0` regardless of how much of a user's `mWomSV` balance is diluted by being in cool-down. This lets any user who starts a partial `startUnlock` still claim 100% of accrued rewards through `getReward`/`getRewards`, when the intended mechanism (present in `mWomSV.getRewardablePercentWAD`) is to reduce reward eligibility for cool-down/diluted balances.

### Finding Description
`mWomSV` tracks lock dilution and exposes `getRewardablePercentWAD(_user)` [1](#0-0)  which computes a percentage strictly less than `1e18` (100%) whenever part of a user's balance is in cool-down (`startUnlock`) and not yet fully aged past `endTime`. This is the mechanism intended to forfeit a portion of rewards to fully-locked holders and redistribute it via `_queueNewRewardsWithoutTransfer` in the rewarder.

However, `mWOMSVBaseRewarder._calExpireForfeit` never reads this percentage: [2](#0-1) 
It sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount = _amount - rewardableAmount` is always `0` (the `> _amount` revert check and dust-rounding branch are dead code that never affects the outcome). This function is invoked by `_sendReward`, called from both `getReward` and `getRewards`, meaning `toSend = userRewards[...] - forfeitAmount = userRewards[...]` always — full payout, no forfeiture, no rebalancing to fully-locked holders via `_queueNewRewardsWithoutTransfer` (which is only entered when `forfeitAmount > 0`, never true here) [3](#0-2) .

None of the existing guards (`onlyMasterMagpie`, `updateReward`, `nonReentrant`) address this — they gate calling context and prevent reentrancy/double-accounting, but do not enforce forfeiture logic, since the forfeiture computation itself is a no-op.

### Impact Explanation
This falls under theft of unclaimed yield: users who initiate `startUnlock` for any portion of their `mWomSV` position (which normally should reduce their share of the current epoch's rewards) instead collect 100% of accrued `getReward`/`getRewards` payouts. The yield that should have been forfeited and redistributed to fully-locked holders (via `_queueNewRewardsWithoutTransfer`) is permanently retained by the diluted-lock user instead, i.e., permanently misallocated/stolen unclaimed yield away from fully-locked holders.

### Likelihood Explanation
No special privileges are required — any unprivileged holder of `mWomSV` can trigger `startUnlock` for a partial amount (leaving some balance locked, some in cool-down), accrue rewards over time, and then call `getReward` through `MasterMagpie`. This is a normal, expected user flow (partial cool-down is explicitly supported by `startUnlock`), so the precondition is trivially met by any staker, with no flash-loan or reentrancy needed, and is repeatable every reward cycle.

### Recommendation
Modify `_calExpireForfeit` to call `mWOMSV.getRewardablePercentWAD(_account)` and derive `rewardableAmount = _amount * percent / 1e18`, with `forfeitAmount = _amount - rewardableAmount`, mirroring the intended dilution logic that exists in `mWomSV` (and presumably the analogous, correctly implemented `_calExpireForfeit` pattern used in `vlMGPBaseRewarder.sol`, which should be reviewed/compared for the correct reference implementation).

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `MasterMagpie`, and `mWOMSVBaseRewarder`; register a reward token.
2. User locks `100e18` mWom via `lock`, receiving `mWomSV` balance of `100e18` (fully locked, `getRewardablePercentWAD` returns `1e18`).
3. User calls `startUnlock(50e18)`, putting half into cool-down; immediately (or well before `endTime`), `getRewardablePercentWAD(user)` returns a value less than `1e18` (roughly `0.5e18` plus small time-decayed cool-down credit, still `< 1e18`).
4. Manager calls `queueNewRewards` to distribute reward tokens; time passes so rewards accrue to the user via `rewardPerTokenStored`.
5. Call `mWOMSVBaseRewarder.calExpireForfeit(user, rewardToken)` and assert it returns `0` even though `mWomSV.getRewardablePercentWAD(user) < 1e18` — demonstrating the bug.
6. Call `getReward(user, user)` via `MasterMagpie` and assert the user receives the full `earned(user, rewardToken)` amount with no forfeiture credited to `rewards[rewardToken].queuedRewards`/`rewardPerTokenStored` via `_queueNewRewardsWithoutTransfer`, confirming permanent yield leakage to fully-locked holders never occurs.

```text
    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
```

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```
