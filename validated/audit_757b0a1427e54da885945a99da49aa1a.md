## Finding [1](#0-0) 

### Title
Submodule `file://` protocol restriction can be overridden for attacker-controlled `.gitmodules` URLs, enabling arbitrary local file read - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` accepts an `allowFileProtocol` boolean that, when true, passes `-c protocol.file.allow=always` to `git submodule update --init --recursive` [2](#0-1) . This flag disables Git's built-in mitigation (added after CVE-2022-39253) that normally blocks submodules from using `file://` URLs without explicit user opt-in. The value of `allowFileProtocol` is a boolean threaded through from `checkoutBranch`/`checkoutCommit` with no runtime check against the content of the `.gitmodules` file or the submodule URLs actually being fetched [3](#0-2) .

### Finding Description
This mirrors the PoolTogether bug class: a critical, security-relevant "parameter" (`allowFileProtocol` / `protocol.file.allow`) is threaded through the code with no sanity/threshold checks and no way to scope it — it's all-or-nothing at the call site, just like `maxExitFee`/`maxTimelockDuration` being set once with no validation of the values being enabled.

In Desktop, `submodule.<path>.url` in `.gitmodules` is fully attacker-controlled content from a cloned/fetched repository [4](#0-3) . `buildSubmoduleDiff` already demonstrates that Desktop reads this value directly from repository config without validation [5](#0-4) . If a code path invokes `checkoutBranch`/`checkoutCommit` (or any caller of `updateSubmodulesAfterOperation`) with `allowFileProtocol=true`, Git will honor a `file://` (or path-like) submodule URL and clone directly from the local filesystem into the working tree of the repository — including files outside the repo's own boundaries, e.g. `file:///Users/victim/Documents/id_rsa-folder` or arbitrary paths accessible to the user. The existing guard (`protocol.file.allow=always` used deliberately) is precisely the guard that was added upstream to prevent this exact class of attack; Desktop re-enables it wholesale rather than validating individual submodule URLs before allowing the override.

### Impact Explanation
If this override is reachable with attacker-influenced submodule content (e.g., cloning/checking out a branch from a malicious remote whose `.gitmodules` references `file://` paths), the victim's local files could be copied into their own working directory as a "submodule," where the user might then inspect, commit, or push them — effectively exfiltrating local file contents outside the intended repo boundary via a UI action (checkout) the user takes normally. This satisfies the impact bar: file read/exfiltration outside the repo triggered by a repository the attacker controls.

### Likelihood Explanation
Medium-to-Low confidence: the vulnerable primitive (`protocol.file.allow=always` gated behind a boolean with no per-URL validation) is confirmed in the codebase, but I was not able to fully trace, within the available tool budget, every caller that supplies `allowFileProtocol=true` to `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` to confirm whether any such caller passes untrusted/attacker-influenced input (versus e.g. only being set `true` for trusted, first-party operations like forking one's own repo). This should be verified by searching all call sites of `checkoutBranch(`, `checkoutCommit(`, and `updateSubmodulesAfterOperation(` with `allowFileProtocol: true` to determine whether the `true` branch can ever be reached while operating on an untrusted/attacker-supplied repository or branch.

### Recommendation
- Before setting `protocol.file.allow=always`, parse `.gitmodules`/`submodule.*.url` values and only allow the override for URLs that resolve to paths known to be safe (e.g., within the same repository's already-trusted remote, or that don't point to `file://`+arbitrary host paths).
- Treat `allowFileProtocol` as a threshold-checked capability rather than a raw pass-through boolean: require an explicit, path-scoped allowlist instead of `protocol.file.allow=always` for the whole submodule update.
- Audit and document every call site that sets `allowFileProtocol = true` to confirm it's only used for repositories/branches under the current user's control, not for content originating from a remote/fork the attacker controls.

### Proof of Concept
1. Attacker publishes a repository with a `.gitmodules` entry: `[submodule "x"] url = file:///Users/victim/Library/Application Support/GitHub Desktop/some-secret-file` (or any local path with attacker-guessable/known location).
2. Victim clones/fetches this repository in Desktop and performs a checkout of a branch/commit that triggers `updateSubmodulesAfterOperation` with `allowFileProtocol=true` [6](#0-5) .
3. `git submodule update --init --recursive` runs with `-c protocol.file.allow=always` [7](#0-6) , bypassing Git's normal `file://` submodule protection and copying the referenced local path's contents into the repo's working tree, where the user may inadvertently commit/push it or otherwise expose it.

**Note on uncertainty:** I could not confirm within this session which specific caller(s) pass `allowFileProtocol=true` with attacker-controlled repository content — this is the critical missing piece to fully validate exploitability, and should be checked directly in the repository (e.g., via `grep -rn "allowFileProtocol"` at all call sites) before treating this as confirmed rather than a plausible analog.
