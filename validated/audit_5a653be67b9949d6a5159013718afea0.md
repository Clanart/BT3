### Title
Permanent dilution of MGP emission rewards via direct token donation to MasterMagpie - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie._calLpSupply()` computes the denominator used to update `accMGPPerShare` for a pool using the raw ERC20 `balanceOf(address(this))` of the staking token, rather than an internally tracked total of deposits. Any unprivileged wallet can transfer staking tokens directly into `MasterMagpie` (bypassing `deposit()`), permanently inflating this denominator and diluting the MGP reward rate for all legitimate depositors of that pool going forward — an accounting-manipulation bug in the same class as the referenced PancakeHunny report, where a direct token transfer to a contract that derives reward math from its own balance was used to corrupt the reward/mint calculation.

### Finding Description
`updatePool()` and `_calMGPReward()` both derive the pool's LP supply via: [1](#0-0) 

For any staking token that is not `vlmgp` or `mWomSV`, `_calLpSupply` returns `IERC20(_stakingToken).balanceOf(address(this))` — the contract's raw token balance — instead of a sum of tracked `user.amount` values.

`updatePool()` uses this value directly as the divisor when accruing rewards per share: [2](#0-1) 

Meanwhile, individual deposits are tracked separately via `user.amount`/`user.available` in `_deposit()`, which are only incremented when tokens flow in through `deposit()`/`depositFor()`: [3](#0-2) 

Because `_calLpSupply` reads the contract's live token balance rather than the sum of `user.amount`, any ordinary wallet holding the pool's staking token can call `IERC20(stakingToken).transfer(masterMagpieAddress, amount)` directly, without going through `deposit()`. This immediately and permanently increases the `lpSupply` divisor used in every subsequent `updatePool()` call for that pool, while `totalAllocPoint`/`mgpPerSec` remain fixed. As a result, `accMGPPerShare` accrues more slowly forever, diluting the MGP yield accrued by every real depositor in that pool. There is no mechanism observed in `MasterMagpie.sol` to net out or sweep such donated balances back out of the `lpSupply` calculation, so the dilution is permanent (well beyond the 24-hour threshold) unless the pool is reconfigured.

This mirrors the PancakeHunny bug class: a contract's reward/emission math is derived from a raw token balance that any wallet can manipulate via a plain transfer, rather than from internally accounted deposit amounts.

### Impact Explanation
This causes a permanent reduction (freezing) of unclaimed MGP yield for every current and future depositor of the affected pool, since the emission-per-share denominator is inflated indefinitely by a cost the attacker (or anyone) can trivially impose. This satisfies the "permanent freezing of unclaimed yield" impact criterion. The attack does not require any privileged role — only holding/acquiring the pool's staking token and doing a bare ERC20 transfer.

### Likelihood Explanation
High likelihood: the action requires only an ERC20 `transfer` call to `MasterMagpie`'s address, no special permissions, and no interaction with other pool logic. Any wallet holding the staking token of a pool (obtainable via the normal LP/staking-token pipeline) can trigger it at any time, and the effect compounds with every `updatePool()` call thereafter.

### Recommendation
Track total deposited principal per pool internally (e.g., a `pool.totalStaked` counter incremented/decremented in `_deposit`/`_withdraw`) and use that value in `_calLpSupply()` instead of `IERC20(_stakingToken).balanceOf(address(this))`, consistent with how `BaseRewardPool`/`BaseRewardPoolV2` already track `totalStaked` internally rather than relying on raw balances.

### Proof of Concept
1. Identify a `MasterMagpie` pool whose `stakingToken` is a normal LP/receipt token (not `vlmgp`/`mWomSV`).
2. From any unprivileged wallet holding that staking token, call `IERC20(stakingToken).transfer(masterMagpie, X)` directly (no `approve`/`deposit()` needed).
3. Call `MasterMagpie.updatePool(stakingToken)` (or let any subsequent deposit/withdraw/harvest trigger it).
4. Observe `tokenToPoolInfo[stakingToken].accMGPPerShare` accrues at a permanently reduced rate because `_calLpSupply()` now includes the donated `X` tokens in its `balanceOf` reading, diluting `mgpReward * 1e12 / lpSupply` for all existing and future depositors in that pool indefinitely.

```text
    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }    
```

```text
    function _calLpSupply(address _stakingToken) internal view returns (uint256) {
        if (_stakingToken == address(vlmgp)) {
            return IERC20(address(vlmgp)).totalSupply();
        }
        if (_stakingToken == address(mWomSV)) {
            return IERC20(address(mWomSV)).totalSupply();
        }
        return IERC20(_stakingToken).balanceOf(address(this));
    }
```
