## Title
Consensus-incentive rewards attributed to the wrong relayer via multi-message batch attribution - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

## Summary
`pallet_consensus_incentives::on_executed` is invoked once per `handle_unsigned` batch with the *entire* list of processed `messages` and the *entire* list of resulting `events`. It determines the relayer to pay by reading only `messages.get(0)` [1](#0-0) , then iterates over **all** `StateMachineUpdated` events in the batch — regardless of which message in the batch actually produced each event — and pays the single messages[0] signer for every one of them [2](#0-1) .

## Finding Description
`handle_unsigned` accepts an unsigned, permissionless batch of `ismp::messaging::Message` values (any relayer can submit any combination of valid `ConsensusMessage`s in one call, since consensus proofs are publicly obtainable per the protocol docs). `FeeHandler::on_executed` is called with the full `messages` vector and the full `events` vector produced by processing that batch [3](#0-2) .

Inside `on_executed`, the relayer identity used for the reward is derived **only from `messages[0]`**:
```rust
let maybe_relayer_account = messages.get(0).and_then(|first_message| {
    if let Message::Consensus(consensus_msg) = &first_message.message {
        ...
        .map(|pub_key| pub_key.into())
    } else { None::<[u8; 32]> }
});
``` [4](#0-3) 

If that single signer is recovered, the code then collapses **all** `StateMachineUpdated` events in the batch (for every state machine, not just the one message[0] belongs to) into `highest_per_state_machine` and pays the `messages[0]` signer for each one via `process_message` → `calculate_reward` (`(latest_height - baseline) * block_cost`) [2](#0-1) [5](#0-4) .

Because `handle_unsigned` lets a caller submit an arbitrary array of `Message::Consensus` entries in one transaction, and the embedded `signer` field of each `ConsensusMessage` is a signature over the specific `consensus_proof` bytes (not tied to `msg.sender`/transaction origin — the call is `ensure_none`), an unprivileged attacker can:

1. Observe/collect any already-signed, publicly-broadcast `ConsensusMessage` for chain Y that advances `StateMachinesCostPerBlock` significantly (these proofs are, by design, "freely provided by connected chains" and get gossiped/queued before landing on-chain).
2. Craft their own trivial `ConsensusMessage` for chain X, signed with their own key, and place it at index 0 of the batch.
3. Append the chain Y message (with someone else's signature) after it.
4. Submit the whole batch via `handle_unsigned`.

`on_executed` only inspects `messages[0]` for attribution, so the attacker's account is credited with **the reward for the chain-Y advance too**, even though the attacker did not produce that consensus proof — they merely reordered a public message into their own transaction.

This mirrors the MasterChef bug class exactly at the invariant level: **a shared reward-rate calculation is applied without correctly attributing/settling which principal actually earned it**, so the wrong party captures value that belongs to someone else, rather than the "half the reward" miscalculation in the original report — here the mis-happening is 100% diversion of another relayer's chain-Y reward to the batch's index-0 signer.

## Impact Explanation
This is a direct "wrong beneficiary" fund-movement bug matching the required Hyperbridge impact class: relayer rewards must move exactly once and only to the rightful beneficiary. Here, `T::Currency::transfer` moves treasury funds to an account that did not do the work for the state-machine advance being paid, and mints reputation tokens to that same wrong account [6](#0-5) . Because the amount can be `blocks * block_cost` for a large block span, the diverted amount can be economically significant, and it is entirely unprivileged and requires no malicious peer, prover, or governance action — only ordinary batching of otherwise-legitimate, publicly available consensus messages.

## Likelihood Explanation
Likelihood is moderate-to-high in a live network: `handle_unsigned` batches are the normal way consensus messages are submitted, ConsensusMessages (and their embedded signatures) are inherently public once broadcast/gossiped (they must be, so any relayer can deliver them), and nothing in the extrinsic or `on_executed` binds the paid-out reward to the specific message that produced each `StateMachineUpdated` event. Any relayer motivated to intercept another relayer's in-flight consensus submission and front-run it inside a larger batch (with their own message first) can capture the reward.

## Recommendation
Attribute each `StateMachineUpdated` event's reward to the signer of the specific `ConsensusMessage` that produced it, not to `messages[0]`. Concretely, `on_executed` should pair each consensus message with the resulting event(s) for its own `state_machine_id` (e.g., by tracking which message updated which state machine during message processing and passing that mapping into the fee handler), instead of collapsing `events` against a single globally-selected signer.

## Proof of Concept
Conceptual sequence (constrained by the fact this analysis is code-level only, not a live-network reproduction):
1. Relayer B produces and broadcasts a valid `Message::Consensus` proof advancing chain Y from height 1000 → 2000, signed with B's key. This message becomes visible (e.g., via mempool/gossip or a prior failed/delayed submission) before it lands on-chain.
2. Attacker A crafts their own trivial `Message::Consensus` for chain X (advancing by 1 block, or reusing an already-rewarded span so the actual X reward is 0), signed with A's key.
3. Attacker A submits `pallet_ismp::handle_unsigned(origin=None, messages=[A_message_for_X, B_message_for_Y])`.
4. `pallet-ismp` processes both messages, producing `StateMachineUpdated` events for both X (span≈1) and Y (span=1000).
5. `pallet_consensus_incentives::on_executed` reads `messages[0]` = A_message_for_X, recovers A's account, and — because it iterates over `highest_per_state_machine` for **all** events in the batch — pays A the reward for both the 1-block advance on X and the 1000-block advance on Y: `reward_Y = 1000 * StateMachinesCostPerBlock[Y]` is transferred to A instead of B [7](#0-6) [2](#0-1) .
6. `LastRewardedHeight` for chain Y is now advanced to 2000, so B — the party who actually produced and signed the Y proof — is permanently unable to claim any reward for that span, since the watermark only moves forward [8](#0-7) .

This test path can be validated directly against the existing test harness in `modules/pallets/testsuite/src/tests/pallet_consensus_incentives.rs`, which already demonstrates the single-message reward-and-watermark flow [9](#0-8) ; extending it to a two-message batch with distinct signers and distinct `state_machine_id`s would confirm the cross-attribution.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
