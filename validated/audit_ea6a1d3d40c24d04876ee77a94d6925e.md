### Title
Stale line-index diff selection is silently re-applied against a freshly recomputed diff when staging, allowing hook-driven working-tree edits to corrupt what gets committed - (File: app/src/lib/git/apply.ts)

### Summary
`applyPatchToIndex` builds the patch that is actually staged from a *fresh* `git diff` of the file, but interprets it using a `DiffSelection` (absolute line indices) that was captured earlier against whatever diff the UI showed the user. Nothing re-validates that the two are still in agreement, mirroring the report's core flaw: two values that are supposed to describe the same state (`_amount`/`_maxIn` in the Connext report, "diff shown to user"/"diff used to build the patch" here) are computed at different times and allowed to diverge, and the divergence is silently accepted rather than rejected.

### Finding Description
`WorkingDirectoryFileChange.selection` stores a `DiffSelection` whose `isSelected(absoluteIndex)` calls are keyed on line positions within a specific diff (`hunk.unifiedDiffStart + lineIndex`), as consumed by `formatPatch`/`formatPatchToDiscardChanges`: [1](#0-0) 

That selection object is created by the UI against the diff that was rendered/expanded at review time, e.g. in `side-by-side-diff.tsx`: [2](#0-1) 

When the user actually commits, `applyPatchToIndex` does **not** reuse that reviewed diff. It re-fetches the current working-directory diff from disk at staging time and feeds the old selection into it: [3](#0-2) 

The whole commit pipeline (`_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex`) never re-diffs against what the user actually looked at before selecting lines; it only re-diffs at the moment of staging: [4](#0-3) [5](#0-4) [6](#0-5) 

Both the staging patch and the "discard changes" patch are then applied with `git apply --unidiff-zero`, which uses zero-context hunks and is more permissive about exactly where a hunk needs to land than a normal context-checked patch: [7](#0-6) [8](#0-7) 

Git operations that Desktop performs on an attacker-controlled repository (checkout, pull, merge) execute the full repository hook chain natively, and Desktop already treats several hook types as first-class citizens it must intercept for progress reporting, confirming hook execution is expected/normal as part of routine Desktop operations, not something requiring an "unnatural" step: [9](#0-8) 

Because `getWorkingDirectoryDiff` is invoked fresh at `applyPatchToIndex` time (line 60) rather than reusing the diff the user actually reviewed, any working-tree mutation that happens between "user selects hunks/lines to commit" and "user clicks Commit" (e.g. a repo-shipped git hook that fires on checkout/merge and schedules a delayed background write to a tracked file) changes the hunk boundaries and line numbering that the stale, index-based `DiffSelection` gets replayed against. The same absolute indices then select different content than what the user reviewed, and `--unidiff-zero` makes it more likely this mismatched hunk still applies rather than failing loudly.

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits primitive: a malicious repository can arrange for a tracked file to change after the user has reviewed and selected specific lines/hunks for a partial commit, causing Desktop to stage and commit lines the user never actually reviewed/approved (or drop lines the user intended to include). Because partial-line commit review is core to Desktop's UX (it's how users build precise, reviewed commits), an attacker exploiting this can smuggle unreviewed content into a commit that the user believes only contains what they explicitly selected, undermining the integrity guarantee that "what I checked in the diff view is what gets committed."

### Likelihood Explanation
Exploitation requires the attacker to control repository content that includes automatically-invoked git hooks (or otherwise arrange for the working tree to be modified between diff review and commit), and to win a timing race against the user's natural review→commit workflow. This is plausible but not trivial: Desktop does execute repo hooks as part of normal checkout/merge/commit flows, and users routinely leave uncommitted partial selections open for some time while composing a commit message, but the attacker has no direct signal for exactly when the user will click "Commit," so reliable exploitation is probabilistic rather than deterministic. I was not able to fully verify, within the available index, whether `post-checkout`/`post-merge` hooks are executed unmodified by Desktop's git wrapper (only a subset of hook names are explicitly intercepted for progress UI in `commit.ts`); this would need to be confirmed via a live Desktop session for a complete exploitability assessment.

### Recommendation
Persist and reuse the exact diff object (content-addressed, e.g. hashed hunk text or file OID) that was shown to the user at selection time, and pass that same diff — not a freshly recomputed one — into `formatPatch`/`applyPatchToIndex`. If the on-disk file has changed (e.g. by comparing the blob/mtime or the diff's hunk headers) since the selection was captured, refuse to stage/commit and force the UI to refresh the diff and require the user to re-confirm the selection, rather than silently replaying stale line indices against new content.

### Proof of Concept
Conceptual PoC (not verified end-to-end due to index limitations):
1. Attacker publishes a repository containing a `post-checkout` (or `post-merge`) hook script that, when triggered, spawns a detached background process which sleeps for a short interval and then appends/edits lines in a tracked file (e.g. `config.js`) that the victim is likely to review and partially stage.
2. Victim clones the repo in GitHub Desktop, checks out a branch (triggering the hook), and opens the Changes view; Desktop renders the diff and the victim selects specific lines to include in a commit via `side-by-side-diff.tsx`'s `onDiscardChanges`/line-selection UI, populating a `DiffSelection` keyed to absolute line indices of the diff shown at that moment (`app/src/ui/diff/side-by-side-diff.tsx:1590-1607`).
3. Before the victim clicks "Commit", the hook's background process fires and mutates the tracked file's content/line layout.
4. Victim clicks "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) recomputes the diff fresh from the now-mutated working tree and replays the stale `DiffSelection`'s absolute line indices against it, producing a patch whose selected content differs from what the victim actually reviewed; `git apply --cached --unidiff-zero` applies it without erroring if hunk offsets still coincidentally align.
5. The resulting commit contains content the user never explicitly reviewed/approved, demonstrating silent corruption of what was committed.
