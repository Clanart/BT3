### Title
Denial-of-service via unbounded recursive puzzle-driver matching when parsing a crafted offer/spend bundle - (File: `chia/wallet/outer_puzzles.py`)

### Summary
Similar to the binutils `readelf` bug class (crash/hang while parsing a crafted, untrusted, deeply-structured input before any resource limiting is applied), Chia's wallet-side offer/spend-bundle puzzle matching recursively descends into curried "outer puzzle" layers (CAT, singleton, metadata/state, ownership, CR) with no depth limit and no CLVM-cost gating. A malicious offer file or spend bundle containing a puzzle reveal with many nested curried layers can drive this recursion past Python's interpreter stack limit, crashing the wallet process (`RecursionError`) purely during puzzle-shape inspection, before any cost-metered CLVM execution or validation occurs.

### Finding Description
`Offer.from_spend_bundle()` iterates every `CoinSpend` in an incoming spend bundle and immediately calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` to build the `driver_dict`, with no cost or size accounting at that point: [1](#0-0) 

`match_puzzle()` in turn tries each registered driver's `match()`: [2](#0-1) 

Every driver's `match()` implementation recursively calls `self._match(UnknownPuzzle(known_program=inner_puzzle))` — which is `match_puzzle` itself — on whatever it uncurries as the "inner puzzle," with no bound on nesting depth. This pattern repeats identically across every outer-puzzle driver: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Each `UnknownPuzzle.mod`/`.curried_args` access lazily calls `uncurry_puzzle()` on the (attacker-controlled) inner puzzle program: [7](#0-6) 

Because a CLVM program with e.g. `CAT_MOD.curry(tail, CAT_MOD.curry(tail, CAT_MOD.curry(tail, ...)))` repeated thousands of times can be constructed at a manageable byte size (curry nesting grows roughly linearly in serialized size but each layer adds one full Python-level recursive call across `match_puzzle` → `driver.match` → `self._match`), an attacker can craft an offer/coin spend whose `puzzle_reveal` triggers Python's default recursion limit (~1000 frames, multiplied by several stack frames per layer) well before the wallet ever reaches CLVM execution/cost enforcement (`Offer.conditions()`, `MAX_BLOCK_COST_CLVM` checks) that exist later in the same class: [8](#0-7) 

No `sys.setrecursionlimit` adjustment or recursion-depth guard exists anywhere in the codebase to bound this. The entry points are fully unprivileged: `Offer.from_bytes()`/`Offer.from_bech32()` (used by `take_offer`, `get_offer`, examine-only CLI/RPC flows) call straight into `from_spend_bundle()`: [9](#0-8) 

The CLI `take_offer` path reads a user- or peer-supplied offer file/bech32 string and passes it directly to `Offer.from_bech32()`, before any cost-based rejection: [10](#0-9) 

### Impact Explanation
An offer counterparty (or anyone who can get a wallet operator to load/examine an offer, e.g. via `take_offer`, `--examine-only`, `get_offer_summary`, or the Data Layer offer summary path that also calls puzzle matching/uncurrying) can crash the wallet process with a single crafted offer file, without spending any funds or needing a valid signature. This matches the CWE-400 (resource exhaustion / stack overflow) and effectively CWE-476-adjacent crash-on-parse behavior of the reported binutils bug class, translated to the wallet's puzzle-matching code path — a spend-triggered transaction-processing halt reachable from a single submitted artifact.

### Likelihood Explanation
High for a determined attacker: constructing deeply nested curried CAT/singleton/metadata/ownership layers is straightforward with the existing `curry()` helper and requires no cryptographic material, signatures, or on-chain state — only building a byte blob and encoding it as a bech32 offer or a coin spend inside a spend bundle. The victim wallet performs the vulnerable recursive matching purely as part of parsing/summarizing the offer, before any signature or cost validation would reject it.

### Recommendation
Add an explicit recursion/iteration depth bound to `match_puzzle()` and each outer-puzzle driver's `match()`/`get_inner_puzzle()` chain (e.g., convert the mutual recursion into an explicit iterative loop with a maximum layer count, or track and cap depth explicitly), and/or enforce a maximum puzzle_reveal size/layer count before invoking driver matching in `Offer.from_spend_bundle()`, `Offer.from_bytes()`/`from_bech32()`, and `DataLayerWallet.get_offer_summary()`.

### Proof of Concept
1. Build `inner = ACS` (accept-any puzzle).
2. Repeatedly wrap: `puzzle = CAT_MOD.curry(tail_hash, puzzle)` (or similarly nest `SINGLETON_MOD`/`NFT_STATE_LAYER_MOD`/CR layers) several thousand times to construct a `puzzle_reveal`.
3. Construct a `CoinSpend` using this `puzzle_reveal` with a dummy solution and parent id `bytes32.zeros` (to be recognized as a requested/offered payment, per `Offer.from_spend_bundle`'s parent_coin_info check) inside a `WalletSpendBundle`.
4. Serialize as an `Offer` (`bytes(offer)` / `to_bech32()`) and deliver it to a victim wallet via `take_offer <file> --examine-only` or the `take_offer`/`get_offer_summary` RPC.
5. `Offer.from_bech32()` → `Offer.from_spend_bundle()` → `match_puzzle()` recurses through all nested layers, exceeding Python's recursion limit and raising an uncaught `RecursionError`, crashing the wallet RPC worker/process before any signature or cost check runs.
