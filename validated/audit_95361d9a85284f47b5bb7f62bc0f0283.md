## Analysis

The Spearbit finding is about a **scattered, path‑dependent guard**: `reconcile()`'s "already called back" check only fires inside specific `if (config.needsX())` branches, so certain flag combinations skip the check entirely and the invariant is enforced only accidentally, not structurally.

The local analog is in the `IntentGatewayV2` cross‑chain cancellation flow: `_cancelFromDest` marks `_filled[commitment]` immediately to prevent re‑entry, but the sibling function `_cancelFromSource` has **no equivalent state marker** — its only guard is an escrow-balance check performed at *dispatch* time, not at *settlement* time. [1](#0-0) 

### Title
Missing in-flight cancellation lock in `_cancelFromSource` allows duplicate GET-response settlement - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`_cancelFromSource` dispatches a Hyperbridge GET request to check whether an order was filled on the destination chain, then relies on the later `onGetResponse` callback to refund escrow. Unlike `_cancelFromDest`, which immediately sets `_filled[commitment]` to block re-entry, `_cancelFromSource` sets no such flag. Its only check — that `_orders[commitment][token] != 0` — is evaluated once, at dispatch time, and is not re-validated or locked until the asynchronous response actually executes `_withdraw`. [2](#0-1) [3](#0-2) 

### Finding Description
`cancelOrder` only blocks re-entry via `_filled[commitment] != address(0)` at its top level: [4](#0-3) 

For a cross-chain order cancelled from the source chain, `_filled[commitment]` is never set by `_cancelFromSource` — it is only ever set by `_fillCrossChain` (on fill) or `_cancelFromDest` (on destination-side cancel). Nothing on the source chain marks "a cancellation GET request is already in flight" for this commitment. The only protection is the per-input escrow check:

```solidity
for (uint256 i; i < inputsLen;) {
    if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();
    unchecked { ++i; }
}
```

This check reads `_orders[commitment][token]`, which is only zeroed when `_withdraw` actually executes — i.e., only after a GET response comes back and `onGetResponse` runs: [5](#0-4) 

Because GET request/response round trips are asynchronous (they require state proofs, challenge periods, and relaying), the order creator (the only caller authorized by `order.user != msg.sender` check) can call `cancelOrder` → `_cancelFromSource` **multiple times before the first GET response is delivered**. Each call passes the same escrow check (since `_orders` hasn't been zeroed yet) and dispatches an independent `DispatchGet` request with its own commitment/fee. If the order was indeed never filled on the destination, each of the resulting GET responses independently satisfies `onGetResponse`'s only guard (`incoming.response.values[0].value.length != 0`) and each one calls `_withdraw(body, true, true)` for the full escrowed input amounts.

Whether this results in duplicate fund release depends entirely on `_withdraw` (defined in `IntentsBase.sol`, not included in the reviewed slices) providing its own idempotency by zeroing `_orders[commitment][token]` and reverting on a second call with the same commitment. `_cancelFromSource` itself provides **no upfront protection** against this duplicate-dispatch pattern — the asymmetry with `_cancelFromDest` (which locks immediately via `_filled`) shows the gap is a real asymmetric design, not an intentional invariant.

### Impact Explanation
If `_withdraw` does not independently enforce single-settlement semantics per commitment/token, this pattern permits the order creator to trigger duplicate escrow refunds for the same cancelled order — a direct double-claim/double-settlement of bridged/escrowed funds, matching the "duplicate settlement or claim" impact category.

### Likelihood Explanation
The path requires only the unprivileged order creator (`order.user`) calling a public entrypoint (`cancelOrder`) multiple times after the order's deadline has passed — no relayer, prover, or admin collusion is needed. The attacker fully controls the timing of the duplicate dispatches (before the first response lands), which is a normal and easily reproducible condition given challenge-period delays inherent to the ISMP GET-response flow.

### Recommendation
Add an in-flight cancellation marker for `_cancelFromSource`, mirroring `_cancelFromDest`'s `_filled[commitment]` lock — e.g., set a `_cancelling[commitment] = true` flag (or reuse `_filled`) before dispatching the GET request, and reject subsequent `_cancelFromSource`/`cancelOrder` calls for the same commitment until the response is processed or the request is provably dead. Additionally, confirm `_withdraw` unconditionally zeroes `_orders[commitment][token]` before any external transfer and reverts if invoked twice for the same commitment, so no single point of failure exists.

### Proof of Concept
1. User places a cross-chain order via `placeOrder`, escrowing input tokens on the source chain.
2. Order deadline elapses without being filled on the destination chain.
3. User calls `cancelOrder` → `_cancelFromSource` twice in quick succession (two transactions), each passing the `_orders[commitment][token] != 0` check because neither GET response has landed yet, generating two independent `DispatchGet` requests for the same commitment.
4. Both GET requests resolve (destination `_filled` slot is empty in both), so both trigger `onGetResponse` → `_withdraw(body, true, true)`.
5. If `_withdraw` lacks a check that zeroes and re-validates `_orders[commitment][token]` atomically per call, the user receives the escrowed refund twice for the same order. [1](#0-0) [6](#0-5) 

**Note:** `_withdraw`'s implementation lives in `IntentsBase.sol`, which was not retrievable within the available index/tool budget for this session — confirming whether it independently blocks the second settlement requires reading that file directly (e.g., via a Devin session with full repo access).

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        _filled[commitment] = address(uint160(uint256(order.user)));

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
