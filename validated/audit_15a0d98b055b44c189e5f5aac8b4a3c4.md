### Title
`resolveWithin()` uses a bare `startsWith()` prefix check without a path-separator boundary, allowing conflict-resolution writes to escape the repository root - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` / `_resolveWithin()` is the shared guard Desktop uses to keep file paths that originate from repository content (conflict file paths, deep-link filepaths) confined to the repository (or a designated root) directory before performing filesystem reads/writes. Its containment check is a plain string `startsWith()` comparison between the `realpath`-resolved candidate and the `realpath`-resolved root, with no trailing path-separator appended to either side.

### Finding Description
`_resolveWithin()` in `app/src/lib/path.ts` computes:
```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
``` [3](#0-2) 

Because `realRoot` has no trailing separator, any sibling path that merely shares the root's name as a string prefix — e.g. root `.../repo` and a target `.../repo-secrets/token` or `.../repository/id_rsa` — satisfies `realResolved.startsWith(realRoot)` even though it is a completely different directory tree outside the intended root. This is the classic CWE-22/`path.join`+`startsWith` boundary bug: a correct implementation must compare against `realRoot + path.sep` (or use `path.relative()` and check for no leading `..`).

The unit tests for this helper only exercise the "traverse-out-and-back" and "symlink escape" cases; there is no test asserting rejection of a same-prefix sibling directory, so this gap is unguarded in the test suite as well. [4](#0-3) 

This guard is used on attacker-influenced input in two places:
1. `buildConflictContext()` calls `resolveWithin(workingDirectory, file.path)` to decide which on-disk file to `readFile()` for AI conflict-resolution context, where `file.path` comes from the merge/rebase/cherry-pick conflict list (derived from the two branches being merged — attacker-controlled if the user merges a hostile branch/fork). [5](#0-4) 
2. `AppStore._applyCopilotConflictResolutions()` calls `resolveWithin(repository.path, resolution.path)` and then `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` — writing content back to disk once the user clicks "Continue Merge". [2](#0-1) 

If a hostile branch/fork introduces a conflicted path whose resolved real path happens to fall under a sibling directory sharing the repository's directory name as a prefix, the guard will incorrectly treat it as "inside the repository" and permit the read (leaking file contents into the Copilot prompt) or the write (clobbering an arbitrary file under that sibling path) — both without ever tripping the `null` rejection branch that the code relies on as its sole enforcement point.

### Impact Explanation
This breaks the invariant the rest of the codebase depends on: "a path that passes `resolveWithin` is guaranteed to be inside the repository root." Existing call sites (`app-store.ts`, `dispatcher.ts`, `copilot-conflict-context.ts`) treat a non-null return as sufficient authorization to read or write the file with no further containment check, so the bug directly yields file read outside the repo (context exfiltration to the Copilot backend) or file write outside the repo (silent corruption of unrelated files) — matching the "file write or read outside the repo" and "silent corruption of what the user commits" impact classes.

### Likelihood Explanation
Exploitability is conditioned on a coincidental (or attacker-engineered) sibling directory sharing the root path as a string prefix, which is not guaranteed for every clone location but is a well-known and previously-exploited bug pattern (many real-world CVEs) whenever users clone repositories into siblings such as `repo`/`repo-old`/`repository`, or into directories under a shared parent with predictable naming. Because the check operates purely on the resolved string without a separator boundary, no filesystem race or symlink privilege is required beyond what the existing tests already show is achievable (an attacker-crafted conflicting file path/symlink entry in the merged branch).

### Recommendation
Fix `_resolveWithin()` in `app/src/lib/path.ts` to enforce a proper path-boundary check, e.g.:
```ts
return (realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep))
  ? resolved
  : null
```
and add a regression test with a sibling directory sharing the root's name as a prefix (e.g. `root` vs `root-evil`) to `app/test/unit/path-test.ts`.

### Proof of Concept
1. Create `root = /tmp/x/repo` and a sibling `/tmp/x/repo-evil/secret.txt` outside the intended repo.
2. Call `resolveWithin('/tmp/x/repo', '../repo-evil/secret.txt')`.
3. `resolve()` produces `/tmp/x/repo-evil/secret.txt`; `realpath()` of both `normalizedRoot` and `resolved` succeed (no symlinks needed).
4. `realResolved.startsWith(realRoot)` evaluates `'/tmp/x/repo-evil/secret.txt'.startsWith('/tmp/x/repo')` → `true`, so the function returns the path instead of `null`.
5. In `_applyCopilotConflictResolutions`, an equivalent conflicted-file path crafted by a hostile merge branch would cause `writeFile()` to write attacker-controlled content to `secret.txt` outside the repository root. [6](#0-5)

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
