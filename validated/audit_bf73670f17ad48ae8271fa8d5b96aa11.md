### Title
Nil-Dereference-style Crash via Untrusted Offer Driver Dict in `get_dl_offer_summary` / `check_for_owner_change_in_drivers` - ([File: chia/wallet/trade_manager.py])

### Summary
`TradeManager.get_dl_offer_summary()` and `TradeManager.check_for_owner_change_in_drivers()` both call `puzzle_info.also()` (and chained `.also().also()`) on `PuzzleInfo` objects reconstructed from an attacker/counterparty-controlled `Offer.driver_dict`, without first verifying the full expected layer chain is present, then immediately index into the result with `[...]` or `.info[...]`. This mirrors the reported Incus bug class: a loop/branch checks one condition (here, `check_type` for a *prefix* match) but does not verify all preconditions needed before dereferencing a value that can be `None`, causing an unhandled `AttributeError`/`KeyError` crash when processing untrusted, structurally malformed data.

### Finding Description
`PuzzleInfo.also()` returns `None` when the `"also"` key is absent from the info dict: [1](#0-0) .

In `get_dl_offer_summary`, the code checks only a two-layer prefix (`SINGLETON`, `METADATA`) via `check_type`, then unconditionally calls `.also()["updater_hash"]`: [2](#0-1) 

`Offer.driver_dict` is populated directly from an untrusted, attacker-supplied `WalletSpendBundle` via `Offer.from_bytes` → `Offer.from_spend_bundle`, using `match_puzzle` on each coin's puzzle reveal: [3](#0-2) [4](#0-3) 

`check_type` only validates a *prefix* of the layer chain and, in the recursive base case, actually asserts `self.also() is None` (no extra trailing layers) — it does not guarantee a specific number of layers exist when the type list is shorter than the real chain, and separately, `also()["key"]` will raise a `KeyError`/`AttributeError` if the returned `PuzzleInfo`'s dict lacks the expected key or if `also()` itself returns `None`: [5](#0-4) 

This function is directly reachable from the wallet RPC `get_offer_summary` endpoint, which is called with a caller-controlled, unauthenticated-content offer (`request.parsed_offer`, parsed straight from bech32 offer bytes) before any deeper validation of trade legitimacy occurs: [6](#0-5) [7](#0-6) 

Similarly, `check_for_owner_change_in_drivers` performs `driver_info.also().also().info["owner"]` after only calling `check_type` on both `puzzle_info` and `driver_info`, again relying on `check_type`'s prefix semantics rather than confirming the exact `"owner"` key exists at that layer: [8](#0-7) 

### Impact Explanation
An attacker can craft an offer whose CLVM puzzle reveals produce a `PuzzleInfo`/`driver_dict` entry that satisfies `check_type([SINGLETON, METADATA])` (i.e., a singleton wrapping an NFT-metadata-layer puzzle with `updater_hash == ACS_MU_PH`) but whose `"also"` sub-dict is missing the `"updater_hash"` key or is otherwise shaped so the subsequent index/attribute access raises. Since `get_offer_summary` and other trade-processing paths do not appear to catch this specific exception, an unauthenticated-content offer (accepted by any wallet RPC caller, including automated services showing offer previews) can raise an unhandled exception mid-processing, denying service for offer summary/preview and trade decision flows. This matches CWE-476-class impact of a spend/offer-triggered processing halt rather than being a pure crash bug in an isolated peer path.

### Likelihood Explanation
Likelihood is Medium: constructing a malformed but syntactically valid `driver_dict` entry (matching the `SINGLETON`→`METADATA` prefix while omitting `updater_hash` or providing a broken "also" chain) requires only crafting puzzle reveals recognized by `match_puzzle`'s driver-matching heuristics (`SingletonOuterPuzzle`, `MetadataOuterPuzzle`) — no signature bypass or consensus-level exploit needed, since offers are pre-signature client-side objects processed via RPC before broadcast.

### Recommendation
Harden `get_dl_offer_summary`, `check_for_owner_change_in_drivers`, and `check_for_special_offer_making` to defensively check `.also()` is not `None` and that required keys exist (using `.info.get(...)`/`in` checks) before indexing, mirroring the incus fix pattern of explicitly handling the "malformed / incomplete" case instead of assuming success after a partial validation. Alternatively, wrap these driver-dict inspections in a `try/except (KeyError, AttributeError, ValueError)` and treat malformed entries as "no match" rather than letting the exception propagate to RPC callers.

### Proof of Concept
1. Construct a `WalletSpendBundle` whose coin spends drive `match_puzzle` to build a `driver_dict` entry recognized as `SingletonOuterPuzzle` wrapping `MetadataOuterPuzzle`, but manually strip/omit the `"updater_hash"` key from the metadata layer's constructor dict (or make the metadata layer's `"also"` chain end early) before wrapping into an `Offer`.
2. Serialize with `Offer.__bytes__`/`to_bech32()`.
3. Submit via wallet RPC `get_offer_summary` (or any path invoking `TradeManager.get_dl_offer_summary`) with `advanced=False`.
4. Observe an unhandled `KeyError`/`AttributeError` raised from `puzzle_info.also()["updater_hash"]`, crashing/erroring the RPC call.

Note: I was unable to fully confirm within available context whether `match_puzzle`'s CLVM-level matching heuristics in `SingletonOuterPuzzle`/`MetadataOuterPuzzle` (`chia/wallet/nft_wallet/singleton_outer_puzzle.py`, `chia/wallet/nft_wallet/metadata_outer_puzzle.py`) can actually produce a `PuzzleInfo` missing `updater_hash` while still satisfying `check_type` — this would require tracing `match_metadata_layer_puzzle`'s constructor-dict construction against all possible curried argument permutations, which is not fully covered by the indexed code snippets. If confirmed exploitable, this qualifies as the "spend/offer-triggered transaction-processing halt" impact category.
