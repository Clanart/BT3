Based on my investigation, the closest architectural analog to CVE-2020-26029 is in the local daemon's keychain RPC boundary, where a client-supplied identity field (`kc_user`/`kc_service`) — not the caller's authenticated identity — decides which keychain the request operates on.

### Title
Keychain RPC authorizes and partitions requests by client-supplied `kc_user`/`kc_service` fields instead of the caller's authenticated identity - ([File: chia/daemon/keychain_server.py])

### Summary
`KeychainServer.get_keychain_for_request()` selects the target `Keychain` instance purely from attacker/client-controlled fields (`kc_user`, `kc_service`) embedded in the request body, rather than from any property of the authenticated websocket connection. Every keychain command handler (`add_key`, `delete_all_keys`, `delete_key_by_fingerprint`, `get_all_private_keys`, `get_first_private_key`, and the streamable `run_request` commands like `get_key`/`get_keys`) calls this same function to resolve "whose keychain" to act on.

### Finding Description
`get_keychain_for_request()` reads `kc_user`/`kc_service` straight out of the incoming JSON dict and, if they don't match the daemon's own default keychain identity, creates or reuses a separate `Keychain(user=user, service=service)` instance keyed by that pair: [1](#0-0) 

This mapping is invoked unconditionally by every keychain operation before checking anything about who is making the request, e.g. `add_key`: [2](#0-1) 

and destructive/sensitive operations such as `delete_all_keys`, `delete_key_by_fingerprint`, and `get_all_private_keys` (which returns raw private key material — `pk`/`entropy` pairs): [3](#0-2) [4](#0-3) 

The daemon's own documentation confirms this design: `kc_user`/`kc_service` are treated as a *data-partitioning* key, not an authorization boundary — `KeychainServer` "maps request `kc_user`/`kc_service` pairs to cached `Keychain` instances," and `KeychainProxy.format_request()` is the only normal code path that sets these fields, based on the constructor args a caller chose: [5](#0-4) 

The daemon's transport-level protection is mutual TLS with the shared private CA (`ssl_context_for_server()` in `chia/daemon/server.py`), which authenticates "some locally-trusted Chia service/client," not a specific `kc_user`. Any connected client that reaches `handle_message()` and issues a command in `keychain_commands` is dispatched straight to `KeychainServer.handle_command()` without any check that the `kc_user`/`kc_service` in the request data corresponds to the connecting service's own identity: [6](#0-5) 

This is structurally identical to the Zammad bug class: the system has an impersonation/identity-selection field in the request (`X-On-Behalf-Of` there, `kc_user`/`kc_service` here), but authorization is anchored to the wrong subject — the field's claimed value instead of the authenticated connection's real identity.

### Impact Explanation
Any local process that can open the mTLS daemon websocket (any of the several private-cert holders: wallet, farmer, harvester, data_layer, or a CLI/GUI client acting through `KeychainProxy`) can supply an arbitrary `kc_user`/`kc_service` pair and thereby read or delete private key material belonging to a different keychain namespace it does not legitimately own — including `get_all_private_keys` (full private key + entropy exfiltration) and `delete_all_keys`/`delete_key_by_fingerprint` (destructive key loss, potential fund loss if no wallet-side backup exists). This crosses the intended boundary between separately-scoped keychains, and since private keys map directly to standard-puzzle and singleton spend authority, this can enable unauthorized coin movement once a foreign fingerprint's key is exfiltrated via `get_all_private_keys`/`get_first_private_key`.

### Likelihood Explanation
Reaching this code path only requires the ability to complete the daemon's mTLS handshake with a valid private cert — a bar met by any already-installed local Chia service/CLI, not a remote/untrusted network attacker. All such holders share the same daemon-facing trust domain per `chia/ssl/create_ssl.py`/`ssl.md`, so any one of them (or a compromised one) can freely specify identity fields belonging to a different `kc_user`/`kc_service` partition with no additional authentication step, making exploitation straightforward once local code execution or a malicious/compromised peer service is present in the trust domain.

### Recommendation
Bind the effective keychain identity to a property of the authenticated connection (e.g., the registered service name recorded at `register_service` time, or the TLS certificate's CN/fingerprint) rather than to attacker-supplied `kc_user`/`kc_service` request fields. If cross-namespace access is an intentional daemon feature (e.g. for admin tooling), require an explicit, separately-authenticated administrative capability before honoring a `kc_user`/`kc_service` override that differs from the caller's own identity.

### Proof of Concept
1. A local process (e.g., a compromised harvester process, which only needs a private cert to connect) opens a websocket to the daemon at `wss://<self_hostname>:<daemon_port>` using its own valid private cert.
2. It sends a `get_all_private_keys` command with a forged `data.kc_user`/`data.kc_service` pair matching another local service/user's keychain namespace, per `KeychainProxy.format_request()`'s wire format: [5](#0-4) 
3. `WebSocketServer.handle_message()` routes the command to `KeychainServer.handle_command()` since `"get_all_private_keys"` is in `keychain_commands`: [7](#0-6) 
4. `get_keychain_for_request()` resolves the forged `kc_user`/`kc_service` to that other keychain's storage and returns its private keys/entropy in the response, without ever checking that the forged identity matches the caller's actual authenticated identity.

**Note:** I was unable to fully verify how `chia.util.keychain.Keychain(user=..., service=...)` maps `user`/`service` onto the underlying OS keyring storage backend (Windows Credential Manager / macOS Keychain / Linux Secret Service / file-based fallback) in this index, since `chia/util/keychain.py`'s constructor body wasn't retrievable in full detail. This affects how impactful cross-namespace access is in practice (e.g., whether `kc_user` values correspond to real OS-level user accounts, or are Chia-internal service names only) — a Devin session with full repo access would be needed to confirm the exact blast radius per platform.

```python
    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
```

```python
    async def get_all_private_keys(self, request: dict[str, Any]) -> dict[str, Any]:
        all_keys: list[dict[str, Any]] = []
        if self.get_keychain_for_request(request).is_keyring_locked():
            return {"success": False, "error": KEYCHAIN_ERR_LOCKED}

        private_keys = self.get_keychain_for_request(request).get_all_private_keys()
        for sk, entropy in private_keys:
            all_keys.append({"pk": bytes(sk.get_g1()).hex(), "entropy": entropy.hex()})

        return {"success": True, "private_keys": all_keys}
```

```python
    def format_request(self, command: str, data: dict[str, Any]) -> WsRpcMessage:
        """
        Overrides DaemonProxy.format_request() to add keychain-specific RPC params
        """
        if data is None:
            data = {}

        if self.keychain_user or self.keychain_service:
            data["kc_user"] = self.keychain_user
            data["kc_service"] = self.keychain_service

        return super().format_request(command, data)
```

```python
        command = message["command"]
        destination = message["destination"]

            if destination in self.connections:
                sockets = self.connections[destination]
                return dict_to_json_str(message), sockets

            return None

        data = message["data"]

            "is_running",

        ]
        if len(data) == 0 and command in commands_with_data:
```
