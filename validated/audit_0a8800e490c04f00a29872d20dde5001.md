### Title
Aggregator gRPC service accepts state-changing and tx-broadcasting calls from any TLS client without certificate authentication - (File: core/src/servers.rs)

### Summary
The verifier and operator gRPC servers restrict callers via the `OnlyAggregatorAndSelf` mTLS interceptor, which pins the caller's leaf certificate against the configured `aggregator_cert_path` or the entity's own `client_cert_path` [1](#0-0) . The aggregator's own gRPC server, however, is documented and implemented to skip this client-certificate check entirely: "The aggregator does not enforce client certificates but does use TLS for encryption" [2](#0-1) , and `create_aggregator_grpc_server` only logs a warning if `client_verification` happens to be set, while `create_grpc_server`'s `InterceptedService` falls back to `Noop` whenever `config.client_verification` is false [3](#0-2) [4](#0-3) . This mirrors the HackerOne report's root cause: a permission/identity check exists for a set of privileged operations, but the specific route through which the state-changing action can be triggered (`create_managed_store` there; the aggregator's `ClementineAggregator` service here) does not enforce it.

### Finding Description
The `ClementineAggregator` gRPC service exposes state-changing, fund-moving, and broadcast-triggering RPCs, including `NewDeposit`, `Withdraw`, `OptimisticPayout`, `InternalSendTx` ("Send a pre-signed tx to the network"), and `SendMoveToVaultTx` [5](#0-4) . These are implemented as unauthenticated-by-identity unary/streaming RPCs on `AggregatorServer`, e.g. `new_deposit` [6](#0-5)  and `withdraw` [7](#0-6) .

Whereas the verifier/operator servers are wrapped in `InterceptedService` with `OnlyAggregatorAndSelf`, which checks the TLS leaf certificate of the peer against pinned certs before allowing any RPC (public methods require the aggregator cert; `Internal*` methods require the entity's own cert) [8](#0-7) , the aggregator server intentionally omits this identity check by design, relying only on transport-layer TLS encryption rather than client-certificate authorization [2](#0-1) .

I was unable to fully confirm within the available index whether `InternalSendTx`'s handler (`aggregator.rs`, `internal_send_tx`) performs any additional authorization or restricts which pre-signed transactions can be broadcast (e.g., only those the aggregator itself produced) — the exact function body was not returned by search before the iteration budget was exhausted. This limits certainty about whether an unauthenticated caller can trigger the broadcast of *arbitrary* attacker-supplied transactions versus only aggregator-known ones.

### Impact Explanation
This matches the accepted High-severity class: "an unauthenticated state-changing or broadcasting call." Any network-reachable client that can complete a TLS handshake with the aggregator (no possession of `aggregator_cert_path`/`client_cert_path` required) can invoke `NewDeposit`, `Withdraw`, `OptimisticPayout`, `SendMoveToVaultTx`, and `InternalSendTx`. Since the aggregator is the sole orchestrator that coordinates verifiers' MuSig2 signing and instructs operators to broadcast reimbursement transactions, an unauthenticated caller reaching these endpoints can initiate deposit-processing, withdrawal, and transaction-broadcast flows that are meant to be triggered only by the "clementine-backend service" as documented in the proto comments [9](#0-8) .

### Likelihood Explanation
This is the actual as-shipped/documented configuration (not a misconfiguration to be excluded per the "ignoring documented configuration" rule) — the docs explicitly state the aggregator does not enforce client certificates [10](#0-9) , and the code path exists to allow it (`Noop` interceptor branch) even when other server types default to enforcement [11](#0-10) . Any party with network access to the aggregator's exposed TCP port can exploit this without needing key compromise, a privileged role, or a misconfigured deployment — this is the documented default behavior of the aggregator entity itself.

### Recommendation
Apply the same `OnlyAggregatorAndSelf`-style (or a dedicated "authorized backend caller") client-certificate check to the aggregator's own gRPC server for all state-changing/broadcasting RPCs (`NewDeposit`, `Withdraw`, `OptimisticPayout`, `InternalSendTx`, `SendMoveToVaultTx`), rather than relying purely on TLS-for-encryption without peer identity verification. At minimum, pin an expected "backend service" certificate analogous to `aggregator_cert_path` and enforce it via an interceptor mirroring `only_aggregator_and_self` in `core/src/rpc/interceptors.rs`.

### Proof of Concept
1. Deploy the aggregator per `docs/usage.md`/`scripts/docker/docker-compose.full.regtest.yml`, exposing its gRPC port (e.g., 17000) to the network, using default config (`client_verification` irrelevant since aggregator server does not gate on it per `create_aggregator_grpc_server`).
2. From an arbitrary client machine, establish a TLS connection to the aggregator (any client cert, or none, is accepted since the server does not pin against `aggregator_cert_path`/`client_cert_path`).
3. Call `ClementineAggregator/NewDeposit`, `ClementineAggregator/Withdraw`, or `ClementineAggregator/InternalSendTx` directly, without possessing the certificate normally required by verifiers/operators to accept calls from "the aggregator."
4. Observe the aggregator processes the request and coordinates with verifiers/operators exactly as if the call originated from the legitimate backend service, since no caller-identity check gates these RPCs on the aggregator side.

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }

## RPC Authentication

Clementine uses mutual TLS (mTLS) to secure gRPC communications between entities
and to authenticate clients. Client certificates are verified and filtered by
the verifier/operator to ensure that:

1. Verifier/Operator methods can only be called by the aggregator (using
   aggregator's client certificate `aggregator_cert_path`)
2. Internal methods can only be called by the entity's own client certificate
   (using the entity's client certificate `client_cert_path`)

The aggregator does not enforce client certificates but does use TLS for encryption.
