### Title
Silent, unconfirmed rewrite of a repository's git remote URL driven by GitHub API data - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The `FETH` report's broken invariant is that an ERC20 `approve()` call can be silently overwritten by a value the caller did not consent to (a stale/racing approval), because the contract updates a sensitive state value directly instead of requiring a "reset to zero" or atomic increase/decrease. The closest reachable analog in GitHub Desktop is `updateRemoteUrl` in [1](#0-0) , which silently rewrites the local `origin` remote URL (a sensitive, trust-bearing value that determines where the user's future `git push`/`git fetch` operations go) whenever the GitHub API's `clone_url` for the tracked repository changes — with no explicit user confirmation.

### Finding Description
`updateRemoteUrl` compares the currently configured local remote URL against `gitHubRepository.cloneURL` (the value previously cached from the API) and the freshly fetched `apiRepo.clone_url`. If the *old* API-cached URL still matches the local remote (i.e. the user hasn't manually customized it) and the *new* API `clone_url` differs, it calls `gitStore.setRemoteURL(...)` to overwrite the local `origin` remote with the new URL, provided only that the URL protocol (`https`/`ssh`) is unchanged: [2](#0-1) .

This value — `apiRepo.clone_url` — originates from a GitHub API response object for the tracked repository, which is refreshed on normal repository-info refresh cycles. The equality/ownership checks performed are limited to `urlMatchesRemote`, which only checks hostname/owner/name equality via `parseRemote` [3](#0-2) ; there is no re-confirmation from the user, no diffing against a known-good allow-list, and no requirement that the new `clone_url`'s owner match the previous owner exactly beyond string equality of the current in-memory value.

Because Desktop trusts the GitHub API repository object to silently drive a git-state mutation (`git remote set-url`) that determines the destination of all future pushes/fetches for that repository — analogous to a value ("approved spender/amount") being overwritten based on new external input without requiring the user to zero-and-reset or explicitly re-approve — the same "stale-approval overwrite" class of bug applies here: whichever value the app is trusting (`apiRepo.clone_url`) can change between two states the user is unaware of, and Desktop applies the new value transparently via `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` [4](#0-3) .

### Impact Explanation
If a repository the user tracks in Desktop is renamed/transferred/forked on GitHub (a repo-owner-level action, not requiring the Desktop user's own credentials or local access) such that the API-reported `clone_url` changes while the hostname/owner/name-matching heuristic still considers it a "match" against the previously cached clone URL, Desktop will rewrite the user's local `origin` remote without any prompt. Since credential resolution and trampoline authentication key off of remote/endpoint URLs (see `findGenericTrampolineAccount`/`envForRemoteOperation`) [5](#0-4) [6](#0-5) , an unexpected silent remote rewrite risks the user's next push/fetch/pull silently targeting a different repository than the one they believe they're working with — i.e., silent corruption of what the user pushes to, or credentials being sent to an unintended endpoint.

### Likelihood Explanation
This path requires no local access, no admin rights, and no prior malware — only a scenario where the tracked GitHub repository's `clone_url` changes (rename, ownership transfer, or similar API-driven change) while the local remote still nominally "matches" per the loose `urlMatchesRemote` heuristic. This is a normal Desktop background refresh operation (`updateRemoteUrl` is called from routine repository-info refresh in `app-store.ts`), so it triggers automatically without unnatural user steps. The confidence here is moderate rather than certain, because I could not fully trace every caller/guard around `updateRemoteUrl` in `app-store.ts` before running out of search iterations — some additional confirmation dialog or gating logic may exist elsewhere in the refresh pipeline that I was unable to verify.

### Recommendation
Require explicit user confirmation before silently rewriting a repository's `origin` remote URL in response to GitHub API data changes, especially when the change implies a different owner/name than what the user originally cloned. Treat the previous remote URL as authoritative unless the user affirmatively acknowledges the rename/transfer, mirroring the "reset-then-set" mitigation pattern recommended for the `approve()` race (i.e., don't silently overwrite a trusted value based on new external input — surface the change and require acknowledgment).

### Proof of Concept
1. User clones and tracks `github.com/owner-A/repo` in Desktop; Desktop caches `gitHubRepository.cloneURL` = `https://github.com/owner-A/repo`.
2. `owner-A` renames/transfers the repository (or an attacker with control over the API-reported repository object achieves an equivalent effect) causing the GitHub API to report a new `clone_url` (e.g. `https://github.com/owner-B/repo`), while Desktop's background refresh calls `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)` [1](#0-0) .
3. Since `remoteUrlUnchanged` is true (local remote still matches the previously cached `cloneURL`) and `urlsMatch` is now false, and the protocol is unchanged, Desktop calls `gitStore.setRemoteURL(...)` and silently updates the local `origin` remote [7](#0-6) , verified by the corresponding test asserting the remote URL is updated automatically [8](#0-7) .
4. The user's next `git push`/`git fetch` transparently targets the new remote without ever being shown or asked to confirm the change.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
```

export async function findGenericTrampolineAccount(
  trampolineToken: string,
  remoteUrl: string
) {
  const parsedUrl = new URL(remoteUrl)
  const endpoint = urlWithoutCredentials(remoteUrl)

  const login =
    parsedUrl.username === ''
      ? getGenericUsername(endpoint)
      : parsedUrl.username

  if (!login) {
    return undefined
  }

  const token = await memoizedGetGenericPassword(
    trampolineToken,
    endpoint,
    login
  )

  if (!token) {
    // We have a username but no password, that warrants a warning
    log.warn(`credential: generic password for ${remoteUrl} missing`)
    return undefined
  }

  return { login, endpoint, token }
```
