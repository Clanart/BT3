### Title
Spoofed `WWW-Authenticate` realm header from an attacker-controlled remote/proxy causes Desktop to treat an arbitrary host as GitHub Enterprise and initiate GitHub sign-in against it - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The external report is about an untrusted, attacker-supplied value (a peer's BLS voting key) being trusted and used to make a security-relevant decision without validating its provenance, causing incorrect/unsafe behavior. The Desktop analog is `getEndpointKind()` in the git-credential trampoline, which classifies a remote endpoint as GitHub/GitHub Enterprise based on an HTTP response header (`WWW-Authenticate`) that is fully controlled by the remote server (or any on-path proxy), without any cryptographic or origin verification.

### Finding Description
When Git performs HTTP authentication it forwards any `WWW-Authenticate` response headers to the configured credential helper as `wwwauth[N]=...` parameters. Desktop's trampoline credential helper parses these values from `command.stdin` via `parseCredential` and uses them, unauthenticated, to decide the "kind" of endpoint being contacted: [1](#0-0) 

If an attacker-controlled HTTPS git remote (or an on-path/malicious proxy for any remote) returns a header such as `WWW-Authenticate: Basic realm="GitHub"`, `getEndpointKind` classifies the endpoint as `'enterprise'` even though the host has nothing to do with GitHub: [2](#0-1) 

This classification then drives `getCredential`, which - if there is no existing account matching the (attacker-controlled) API endpoint derived from the spoofed host - directly calls `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

`getGitHubCredential`/`findGitHubTrampolineAccount` are checked first using the real (attacker) host string, so they correctly find no existing GitHub.com account, and control falls through to the spoofable `getEndpointKind` branch. The invariant that is broken is: "an endpoint is only treated as a first-party GitHub/GHE endpoint if it was actually contacted via a GitHub API/host," but this invariant is instead derived from an unauthenticated string reflected by the remote server itself. Just like the nimiq report where the corrupted value (a bad BLS key) reached security-critical logic (`voting_key.uncompress().unwrap()`) without validation, here the corrupted value (a forged `realm="GitHub"` string) reaches security-critical logic (`ui.promptForGitHubSignIn`) without validation of its source.

### Impact Explanation
Triggering the GitHub sign-in UI flow against what the user believes is a legitimate GitHub Enterprise instance - but is actually attacker infrastructure reachable only because the user added/fetched from a malicious git remote - can result in:
- The user completing an OAuth/device-code sign-in flow that is bound to the attacker's endpoint, allowing account binding to attacker infrastructure.
- Confusion/social pressure to enter credentials into a flow that Desktop itself initiated, increasing the chance of credential exfiltration if the "enterprise" flow falls back to any code path that accepts direct credentials.

This satisfies the "unauthorized OAuth or account binding" category in valid impact, and it is triggered purely by an attacker-controlled git remote/proxy response, not by any local/privileged access.

### Likelihood Explanation
The `wwwauth[N]` mechanism is a documented, standard part of Git's credential helper protocol - any HTTP git server (or transparent proxy sitting in front of one) fully controls the `WWW-Authenticate` header it returns, so forging `realm="GitHub"` requires no special privilege. Desktop performs this classification any time an unauthenticated HTTP git operation (clone/fetch/push) is attempted against a remote that requests authentication, which is a common occurrence, making the trigger path realistic. However, whether `promptForGitHubSignIn` can be driven all the way to a credential-exfiltrating end state (vs. the user simply seeing a GitHub sign-in dialog and calling it out as suspicious) is not verified from static code alone — this would need runtime confirmation of what `trampolineUIHelper.promptForGitHubSignIn` renders for spoofed enterprise endpoints and whether it distinguishes a legitimate GHE from a spoofed one.

### Recommendation
Do not trust the `wwwauth[N]` realm string alone to classify a host as GitHub/GHE. Cross-check the header-based classification against the actual hostname (e.g., only treat `realm="GitHub"` as meaningful for hosts already known to be GitHub Enterprise via `isGHE`/an existing account, or require confirmation of the GitHub-specific API probe `isGitHubHost(endpoint)` before offering a GitHub-branded sign-in flow for a previously-unknown host).

### Proof of Concept
1. Stand up an HTTPS server (attacker-controlled) that serves a normal git-http-backend but responds to authentication challenges with `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, add this server as a remote (e.g., `git remote add origin https://attacker.example/some/repo.git`) or open/clone it directly, with no existing account configured for that host.
3. Trigger a fetch/push against that remote so Git requests credentials; Desktop's trampoline credential helper (`createCredentialHelperTrampolineHandler`) is invoked with `wwwauth[0]=Basic realm="GitHub"` in `command.stdin`.
4. Observe that `getEndpointKind` returns `'enterprise'` for `attacker.example` and Desktop calls `ui.promptForGitHubSignIn('https://attacker.example')`, presenting a GitHub-branded sign-in flow for a host that is not GitHub Enterprise at all. [4](#0-3)

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}
