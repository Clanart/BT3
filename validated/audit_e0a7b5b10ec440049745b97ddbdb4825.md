### Title
Unauthenticated transient memory amplification via attacker-controlled participant count in `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts the serialized participant count before validating the threshold parameters and immediately allocates `Vec::with_capacity(n)` when the interpolation variant is `Constant`. An attacker supplying untrusted bytes to `ThresholdKeys::read` can therefore trigger an allocation for up to `u16::MAX` scalar elements with a message containing little more than the serialized header.

### Finding Description
The deserializer reads the curve identifier, `t`, `n`, and participant index, then branches on the interpolation variant before constructing `ThresholdParams` or calling `ThresholdKeys::new`. For interpolation byte `0`, it executes `Vec::with_capacity(usize::from(n))` and then attempts to read `n` field elements. [1](#0-0) 

Parameter validation is deferred until after this allocation and all field/point decoding are attempted. `ThresholdKeys::new` is only reached near the end of `read`, where it constructs `ThresholdParams` and validates the assembled key material. [2](#0-1) 

Because `n` is a serialized `u16`, a tiny prefix can specify `n = 65,535`. On a 256-bit-field ciphersuite, the resulting vector capacity is approximately 2 MiB, before considering allocator overhead or larger fields such as Ed448. The input can terminate immediately after the interpolation byte; the allocation still occurs before the first attempted `read_F` returns an EOF error.

### Impact Explanation
This is a remote resource-consumption amplification primitive. An attacker who can feed untrusted bytes into `ThresholdKeys::read` can repeatedly create multi-megabyte transient allocations from requests only tens of bytes long. Repeated concurrent requests can increase allocator pressure, memory churn, and process memory footprint, potentially causing denial of service under sustained load.

The impact is bounded by the `u16` participant count and the field element size, but it does not require malformed data beyond a valid curve identifier and parameter prefix.

### Likelihood Explanation
The vulnerable path is reachable whenever an application accepts serialized `ThresholdKeys` from an unauthenticated source or otherwise exposes `ThresholdKeys::read` to attacker-controlled input. The probability of exploitation is high on such an interface because the attacker directly controls the serialized `n` value and selects interpolation variant `0`.

The issue does not require authentication, valid threshold parameters, valid shares, or a complete serialized key. It is not dependent on malicious peers colluding or on compromising secret material.

### Recommendation
Validate `t`, `n`, and `i` with `ThresholdParams::new` before allocating or decoding any variable-sized field. Additionally:

- Do not use attacker-controlled `n` for `Vec::with_capacity`; use incremental `Vec::push` or cap the initial reservation.
- Reject implausible serialized `n` values according to the protocol’s actual maximum participant count.
- Enforce a maximum serialized `ThresholdKeys` length at the API boundary.
- Reject `t > n`, `t == 0`, `n == 0`, and invalid participant indexes before reading interpolation data.
- Add a regression test that supplies `n = u16::MAX` with interpolation variant `0` and truncated input, asserting no large allocation occurs.

### Proof of Concept
The following conceptual Rust PoC targets `ThresholdKeys::<Secp256k1>::read`. The input is intentionally truncated immediately after selecting `Constant` interpolation, but `Vec::with_capacity(65_535)` is executed before the first scalar read fails:

```rust
use std::io;
use frost::curve::{Ciphersuite, Secp256k1};
use frost::ThresholdKeys;

fn malformed_threshold_keys() -> Vec<u8> {
    let mut bytes = Vec::new();

    // Serialized C::ID.
    bytes.extend_from_slice(
        &(u32::try_from(Secp256k1::ID.len()).unwrap()).to_le_bytes(),
    );
    bytes.extend_from_slice(Secp256k1::ID);

    // t = 1, n = 65535, i = 1.
    bytes.extend_from_slice(&1u16.to_le_bytes());
    bytes.extend_from_slice(&u16::MAX.to_le_bytes());
    bytes.extend_from_slice(&1u16.to_le_bytes());

    // Interpolation::Constant.
    bytes.push(0);

    // No scalar bytes follow. The allocation has already been made.
    bytes
}

fn main() {
    let input = malformed_threshold_keys();
    let result: io::Result<ThresholdKeys<Secp256k1>> =
        ThresholdKeys::read(&mut input.as_slice());

    assert!(result.is_err());
}
```

A custom global allocator or memory profiler can demonstrate the large reservation made by `Vec::with_capacity(usize::from(n))` before the function returns the expected EOF/invalid-scalar error.
