### Title
Attacker-controlled participant count in `ThresholdKeys::read` causes excessive allocation and scalar/point parsing — uncontrolled resource consumption ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The `graphql` advisory (CVE-2023-26144) is a parser-side resource-exhaustion bug: insufficient checks when parsing attacker-influenced input let an unbounded structure drive disproportionate work. The Serai analog lives in `ThresholdKeys::read`, which trusts a raw `u16` `n` field from untrusted bytes to size allocations and drive two `n`-iteration parse loops, plus a downstream `O(n)`-plus `ThresholdKeys::new` reconstruction, all before any semantic validation can reject the input.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` as little-endian `u16`s directly from the reader, with `n` fully attacker-controlled up to 65535. [1](#0-0) 

If the interpolation tag is `0` (`Constant`), it executes `Vec::with_capacity(usize::from(n))` and then calls `C::read_F(reader)` `n` times. [2](#0-1) 

It then unconditionally performs `n` `C::read_G(reader)` calls — each a point decompression plus validity/subgroup verification — into a `HashMap`. [3](#0-2) 

Finally it calls `ThresholdKeys::new(ThresholdParams::new(t, n, i), ...)`, which rebuilds the group key from verification shares `1..=t` via interpolation, adding further scalar arithmetic proportional to `t`. [4](#0-3) 

The `n`-bound work happens *before* `ThresholdParams::new` can reject anything — and `n = 65535` is a *valid* parameter (`t <= n <= u16::MAX`), so nothing rejects it. The only bound is the `u16` encoding, not any protocol-realistic limit. For comparison, `Commitments::read` in pedpop bounds its parse loop by `params.t()` derived from negotiated `ThresholdParams`, not by a raw bytes-controlled length. [5](#0-4) 

### Impact Explanation
An unprivileged party supplying crafted bytes to `ThresholdKeys::read` (per the engagement's reachable-surfaces list) can force, per invocation:

- an immediate `Vec::with_capacity(65535)` allocation of field elements (~2 MB for a 32-byte field) triggered by a 2-byte field,
- up to 65535 `read_F` canonical-scalar checks,
- up to 65535 `read_G` point decompressions — each involving field inversion and (on torsion-safe curves) a cofactor/subgroup multiplication — if the attacker actually supplies the ~4 MB of point encodings,
- `ThresholdKeys::new` interpolation work over the supplied shares.

Repeated calls (e.g., during key-import/session-setup handling where several key blobs are processed, as in the `while !keys_ref.is_empty()` loop pattern used by callers of `ThresholdKeys::read`) multiply this linearly. Consistent with the advisory, this degrades node performance via CPU and allocator pressure; it is not proven to crash the process.

### Likelihood Explanation
Reachability requires an attacker to get bytes into `ThresholdKeys::read` — e.g., a DKG/threshold-setup message, a key-exchange payload, or storage loaded from data an untrusted participant influenced. Within that surface, the exploit needs no secrets, no valid signature, and no collusion: setting `n = 0xFFFF` and padding the buffer suffices. The cost asymmetry is real but bounded (~4 MB input buys ~65k point ops, and a truncated buffer still buys the upfront `with_capacity` allocation), which is why this is Medium, not High.

### Recommendation
- Bound `n` before allocating: enforce a protocol-level `MAX_PARTICIPANTS` (e.g., the real tributary-set size, on the order of hundreds) in `ThresholdKeys::read` prior to `Vec::with_capacity` and the share loop, not just `u16::MAX` via `ThresholdParams::new`.
- Replace `Vec::with_capacity(n)` with incremental `push` (or chunked reading as done in `networks/ethereum/src/machine.rs`'s `Call::read`, which reads a claimed `u32` length in 1 KB chunks specifically to cap amplification) so allocation tracks bytes actually present.
- Fail fast on `Participant::new`/`ThresholdParams` inconsistency before the `read_G` loop where possible.

### Proof of Concept
```rust
// Conceptual: feed ThresholdKeys::read a buffer with n = u16::MAX.
// Requires: a Ciphersuite C (e.g., Ristretto) and a caller path that
// hands untrusted bytes to ThresholdKeys::read.
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(1u16.to_le_bytes());        // t = 1
buf.extend(u16::MAX.to_le_bytes());    // n = 65535 — attacker-controlled
buf.extend(1u16.to_le_bytes());        // i = 1
buf.push(0);                           // Interpolation::Constant
// Even with NO further bytes, Vec::with_capacity(65535) scalars (~2 MB)
// is already allocated before the first read_F fails.
// Supplying 65535 * repr scalar bytes then forces 65535 read_F checks,
// and appending 65535 * repr point bytes forces 65535 read_G
// decompressions + validity checks before ThresholdKeys::new runs.
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
```

Caveat: reachability depends on an integration path that feeds untrusted input to `ThresholdKeys::read`; the deserialize-then-loop pattern used by `read_keys` callers confirms such multi-entry parsing exists, but the exact untrusted entry point is integrator-dependent.
