### Title
Non-USDT-compliant re-approval in `WombatBribeManager::_approveTokenIfNeeded` can permanently freeze bribe reward distribution - (File: `wombat/WombatBribeManager.sol`)

### Summary
`WombatBribeManager` swaps collected bribe reward tokens into BNB via `PancakeZapper` inside `_swapFeesForBnb`, using a helper `_approveTokenIfNeeded` that performs a raw, non-standard-compliant `approve()` call whenever the current allowance is insufficient, without ever resetting the allowance to zero first [1](#0-0) . This is the exact bug class described in the referenced Astaria `ClearingHouse` report: re-approving a non-zero amount over an existing non-zero allowance reverts for non-compliant EIP-20 tokens such as USDT.

### Finding Description
`_approveTokenIfNeeded` only approves when the current allowance is below the amount needed, and when it does, it sets a `type(uint256).max` approval directly with `IERC20(token).approve(_to, type(uint256).max)`:

```solidity
function _approveTokenIfNeeded(
    address token,
    address _to,
    uint256 _amount
) private {
    if (IERC20(token).allowance(address(this), _to) < _amount) {
        IERC20(token).approve(_to, type(uint256).max);
    }
}
``` [2](#0-1) 

Because `PancakeZapper.zapInToken` consumes only the exact `feeAmounts[i][j]` passed to it (via `safeTransferFrom(msg.sender, address(this), amount)` followed by a swap) rather than the full `type(uint256).max` approval, some non-zero allowance almost always remains after the first swap of a given `rewardToken` [3](#0-2) . On a subsequent bribe-harvesting cycle for the same `rewardToken`, if the remaining allowance happens to be less than the new `_amount` needed, `_approveTokenIfNeeded` will try to set a new non-zero approval over the still-non-zero remaining allowance. For tokens that enforce the "no non-zero-to-non-zero approval" restriction (e.g., USDT and similar tokens), this `approve()` call reverts.

`_swapFeesForBnb` is invoked from `WombatBribeManager` as part of processing bribe rewards for pools that any bribe manager/voter interacts with, and bribe reward tokens are arbitrary ERC20s chosen by bribe depositors/pool creators, not something the contract can restrict to "safe" tokens [4](#0-3) .

### Impact Explanation
If any bribe reward token behaves like USDT (reverts on non-zero-to-non-zero `approve`), the swap-to-BNB path for that specific token in `_swapFeesForBnb` becomes permanently unusable once a partial allowance remains from a previous cycle. Since this call is embedded in the bribe processing flow, this can cause reverts that block distribution of bribe rewards denominated in or routed through such a token, freezing that portion of unclaimed yield for the affected pool indefinitely (no `safeApprove(0)` reset path exists to recover).

### Likelihood Explanation
Likelihood depends on: (1) a bribe reward token being added that has the USDT-style approval restriction, and (2) `PancakeZapper.zapInToken` leaving a non-zero dust allowance smaller than a subsequent swap amount. Both conditions are plausible in normal operation since bribe tokens are permissionlessly chosen by third-party bribers and the zapper only consumes the exact amount needed, not the full approval — this is not an admin-triggered or malicious-admin scenario, it is a consequence of ordinary repeated bribe-harvesting transactions.

### Recommendation
Replace the raw `approve()` in `_approveTokenIfNeeded` with a safe reset-then-approve pattern, e.g.:
```solidity
uint256 currentAllowance = IERC20(token).allowance(address(this), _to);
if (currentAllowance < _amount) {
    if (currentAllowance != 0) {
        IERC20(token).safeApprove(_to, 0);
    }
    IERC20(token).safeApprove(_to, type(uint256).max);
}
```
This matches the pattern already correctly used elsewhere in the codebase (e.g., `WombatStaking::_sendRewards` resets to zero before re-approving) [5](#0-4) .

### Proof of Concept
1. A bribe reward token behaving like USDT (revert on non-zero→non-zero `approve`) is added as a bribe reward for a pool tracked by `WombatBribeManager`.
2. During a bribe-harvest cycle, `_swapFeesForBnb` calls `_approveTokenIfNeeded(token, PancakeZapper, feeAmount1)`, which sets approval to `type(uint256).max`, then `PancakeZapper.zapInToken` consumes only `feeAmount1`, leaving a large but non-zero remaining allowance.
3. On a following cycle, a new `feeAmount2` bribe is processed for the same token; if remaining allowance from step 2 is less than `feeAmount2` (allowance decreases over time/consumption), `_approveTokenIfNeeded` calls `approve(PancakeZapper, type(uint256).max)` again over the existing non-zero allowance, causing the transaction to revert for the USDT-style token, blocking further bribe swap/distribution for that token.
