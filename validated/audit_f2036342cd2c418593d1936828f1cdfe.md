### Title
Payout transaction's operator attribution (OP_RETURN) is unsigned, letting anyone reassign or void reimbursement credit for a withdrawal that a different operator actually pays - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` builds the on-chain `Payout` transaction that fronts a Citrea withdrawal. Its only committed authorization is the user's off-chain signature over the withdrawal UTXO input and the user output, using `SinglePlusAnyoneCanPay` sighash (confirmed by the comment in `core/src/rpc/aggregator.rs` and `parser::operator::parse_withdrawal_sig_params`). That sighash type binds only input 0 and output 0; it does **not** cover the OP_RETURN output that carries the `operator_xonly_pk` used everywhere downstream to decide *which operator gets credited for having fronted the payout*. Anyone who obtains the signed payout transaction/witness (e.g. from the mempool) can therefore rewrite or strip that OP_RETURN output, and rebroadcast a still-valid transaction that pays the user identically but attributes (or fails to attribute) the payout to a different operator than the one who actually completed it, breaking the "operator credited == party that paid" binding.

### Finding Description
`create_payout_txhandler` at [1](#0-0)  constructs the payout transaction with three outputs: the user payout output (index 0, signature-committed), an anchor output (index 1), and an OP_RETURN output embedding `operator_xonly_pk` (index 2). The single input is signed by the user with `set_p2tr_key_spend_witness(&user_sig, 0)`.

The RPC layer explicitly documents and checks that this user signature uses `SinglePlusAnyoneCanPay`: [2](#0-1) . `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` commits only to the input being spent and the output at the same index (index 0). Outputs 1 and 2 - including the OP_RETURN operator attribution - are outside the commitment.

Downstream, the protocol trusts this unsigned OP_RETURN field as ground truth for who fronted the payout:
- `update_finalized_payouts` extracts `operator_xonly_pk` straight from the mined payout tx's OP_RETURN and stores it as `payout_payer_operator_xonly_pk` in the DB: [3](#0-2) .
- `is_kickoff_malicious` later compares this stored value against the operator that is trying to claim reimbursement via its Kickoff transaction, and treats any mismatch (or `None`) as malicious: [4](#0-3) .
- The operator-side `validate_payer_is_operator` also depends on this same DB field to decide whether an operator may proceed with reimbursement transactions for a deposit: [5](#0-4) .
- Even the BitVM bridge circuit (used for the SNARK disprove/assert path) re-derives `operator_xonlypk` from this same OP_RETURN field and folds it into the `deposit_constant`, so the misattribution propagates into on-chain-verifiable proofs as well: [6](#0-5)  and [7](#0-6) .

Because the OP_RETURN is not covered by any signature, an unprivileged party who sees a valid, still-unconfirmed payout transaction in the mempool (which must be publicly relayable, since paying out the user is the entire point of the transaction) can clone it, keep output 0 identical (satisfying the user), and substitute a different (or invalid) OP_RETURN payload, then get their version mined instead (e.g. by paying a higher CPFP fee on their own anchor spend). This decouples the operator that is credited with the reimbursement right from the operator (or party) whose funds/attestation actually completed the front.

### Impact Explanation
This breaks exactly the "operator credited versus the party that paid" binding called out as in-scope. Concretely:
- An honest operator who genuinely fronted a withdrawal can have their OP_RETURN attribution stripped or reassigned before confirmation, after which `is_kickoff_malicious` will flag their subsequent Kickoff as malicious (payout info missing or mismatched operator pubkey), leaving that operator unable to be reimbursed for a withdrawal it legitimately paid — this matches the Critical impact "an honest operator permanently unable to be reimbursed."
- Conversely, an attacker can name an arbitrary operator's pubkey in the substituted OP_RETURN, which can be used to grief a targeted operator by making the system record them as the payer of a withdrawal they never funded, corrupting reimbursement bookkeeping across the operator/verifier state machine and the bridge-circuit's public inputs.

### Likelihood Explanation
No privileged role, key, or authorization is required — only the ability to observe a broadcast-but-unconfirmed payout transaction (a public mempool event by design, since the payout must reach miners) and to relay a variant transaction with sufficient fee/priority to be mined first or via replacement. The vulnerable field (OP_RETURN operator attribution) is provably outside the `SinglePlusAnyoneCanPay` signature commitment, so no signature check anywhere in the shown code paths (`update_finalized_payouts`, `is_kickoff_malicious`, `validate_payer_is_operator`, bridge circuit deposit constant derivation) protects it.

### Recommendation
Bind the operator attribution to the same authorization that pays the user, e.g. by having the user's signature cover all outputs (`SIGHASH_ALL` variant, or `SIGHASH_SINGLE` is not applicable since attribution must be operator-chosen after signing) — or, since attribution is chosen per-operator after the user signs, require the operator to independently sign the OP_RETURN + anchor portion of the transaction (e.g. a second, operator-controlled input/output covered by an operator signature) so that whichever operator's key completed the payout is cryptographically bound to that specific broadcast transaction, and any relay of a modified attribution invalidates the transaction.

### Proof of Concept
Not independently reproducible as a runnable exploit within this review; the analysis is based on static code inspection of the transaction construction and downstream trust:
1. Operator A obtains the user's `SinglePlusAnyoneCanPay` signature and constructs the `Payout` tx via `create_payout_txhandler` (`operator_reimburse.rs:407-436`), naming itself in OP_RETURN, and broadcasts it.
2. Before confirmation, an unprivileged observer copies the transaction, keeps input 0 and output 0 unchanged (so the signature remains valid, per `SIGHASH_SINGLE|ANYONECANPAY` semantics confirmed at `aggregator.rs:1852-1855`), and replaces the OP_RETURN output (index 2) with a different/invalid `operator_xonly_pk`, then gets this variant mined instead (e.g., via a higher-fee anchor CPFP or RBF race).
3. `update_finalized_payouts` (`verifier.rs:2311-2350`) records the attacker-chosen `operator_xonly_pk` (or `None`) as the payer for this withdrawal.
4. When Operator A submits its Kickoff to claim reimbursement, `is_kickoff_malicious` (`verifier.rs:1875-1890`) finds no match and flags the honest operator's kickoff as malicious, denying reimbursement.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

fn host_deposit_constant(
    input: &BridgeCircuitInput,
) -> Result<DepositConstant, BridgeCircuitHostParamsError> {
    let first_op_return_output = get_first_op_return_output(&input.payout_spv.transaction)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&input.sp.storage_proof_deposit_txid).map_err(|e| {
            BridgeCircuitHostParamsError::StorageProofDeserializationError(e.to_string())
        })?;

    let round_txid = input.kickoff_tx.input[0]
        .previous_output
        .txid
        .to_byte_array();

    let kickoff_round_vout = input.kickoff_tx.input[0].previous_output.vout;

    let operator_xonlypk: [u8; 32] = parse_op_return_data(&first_op_return_output.script_pubkey)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?
        .try_into()
        .map_err(|_| BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

    Ok(deposit_constant(
        operator_xonlypk,
        input.watchtower_challenge_connector_start_idx,
        &input.all_tweaked_watchtower_pubkeys,
        deposit_value_bytes,
        round_txid,
        kickoff_round_vout,
        input.hcp.genesis_state_hash,
    ))
}
