## Findings

`PlotNFT2Wallet.identify()` calls `PlotNFT.get_next_from_coin_spend()` for **every observed singleton coin spend that matches the PlotNFT/pool singleton mod during wallet sync**, i.e. any coin spend a full node reports to the wallet with the matching curried singleton structure — this is not restricted to coins the wallet already owns. [1](#0-0) 

That function parses the CREATE_COIN memo via `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())`, an attacker-controlled CLVM blob attached to an on-chain coin. [2](#0-1) 

`PuzzleWithRestrictions.from_memo()` is an unbounded **Python-level recursive function**: when the `further_branching` flag is set, it recurses into `MofN.from_memo()`-equivalent parsing for every member, and each member itself calls `PuzzleWithRestrictions.from_memo()` again. [3](#0-2) 

This is the same bug class as CVE-2018-9996 (recursive-descent parsing of untrusted structured data with no depth limit, causing a native/interpreter stack exhaustion) — except the target here is a Python function stack instead of libiberty's C stack. Unlike CLVM's own tree-hash helper, which was deliberately written iteratively "so we don't have to worry about blowing out the python stack" [4](#0-3) 
, `from_memo()` has no such protection and no depth cap.

Because the memo is just a CLVM atom pair structure with no consensus-level nesting-depth limit (only overall byte-size/cost limits enforced by mempool/CLVM), an attacker can spend a coin whose puzzle unciphers to the PlotNFT/pool singleton mod and attach a deeply nested `MofN`-shaped memo (thousands of nesting levels are cheap in CLVM bytes — each level costs only a few bytes of `ff`/atom overhead). When any wallet observing this coin (via normal wallet sync / hint matching) calls `identify()` → `get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo()`, the recursive descent exhausts the Python call stack and raises an uncaught `RecursionError`, since no `sys.setrecursionlimit`/depth-guard exists anywhere in the codebase. [5](#0-4) 

I could not fully verify how this `RecursionError` propagates through `identify()`'s exception handling — only `GetNextPlotNFTError` is caught there [6](#0-5) 
— meaning an unhandled `RecursionError` would likely propagate up through the wallet sync path and crash or halt wallet-side transaction/coin-state processing for any wallet that observes the malicious coin, which matches the "spend-triggered transaction-processing halt" impact category.

### Title
Unbounded recursive CLVM memo parsing in PlotNFT custody `from_memo()` causes wallet stack exhaustion - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
`PuzzleWithRestrictions.from_memo()`, used to parse the memo attached to PlotNFT/pool singleton coins, recurses without any depth limit into nested `MofN` structures. An attacker can craft a plotnft-mod-matching coin spend with a deeply nested memo, causing any wallet that syncs/observes the coin to blow the Python call stack while decoding it.

### Finding Description
`PlotNFT2Wallet.identify()` is invoked during wallet sync for any coin spend whose puzzle matches the plotnft/pool singleton mod, regardless of ownership, calling `PlotNFT.get_next_from_coin_spend()`. [1](#0-0) 
That function extracts the memo from the `CreateCoin` condition and calls `PuzzleWithRestrictions.from_memo()` on attacker-supplied bytes. [2](#0-1) 
`from_memo()` recursively parses `MofN` member memos with `[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]`, with each `PuzzleWithRestrictions` able to embed further `MofN` nesting, and no maximum recursion/nesting depth is enforced anywhere in the class or its call chain. [3](#0-2) 
This mirrors the CVE-2018-9996 bug class: unbounded recursive-descent decoding of attacker-controlled nested data with recursive stack frames, but here reachable through the CHIA wallet sync/PlotNFT parsing path in Python rather than a C demangler.

### Impact Explanation
A malicious actor can create a coin whose puzzle reveal matches the plotnft singleton mod curry shape and attach a maliciously deep-nested memo. Any wallet that observes this coin during normal sync (hint-matching or singleton-mod matching) will attempt `from_memo()` parsing and hit Python's recursion limit, raising `RecursionError`. Since `identify()` only special-cases `GetNextPlotNFTError`, the unhandled exception can propagate and disrupt wallet-side transaction/coin processing for any wallet syncing the chain — a spend-triggered processing halt reachable by an unprivileged coin creator.

### Likelihood Explanation
Medium-likelihood: the attacker only needs to submit one on-chain spend whose puzzle reveal matches the plotnft singleton curry structure with a crafted deep-memo; this requires curried-mod matching but not any privileged access, key material, or victim interaction beyond normal wallet sync.

### Recommendation
Add an explicit maximum nesting-depth check in `PuzzleWithRestrictions.from_memo()` (and `MofNHint.from_program()`), rejecting memos beyond a small fixed depth, and/or convert the recursive descent to an iterative worklist implementation (following the pattern already used in `sha256_treehash()`). Additionally, wrap `get_next_from_coin_spend()`/`from_memo()` calls in wallet sync with a broad exception guard so malformed/hostile memos cannot terminate wallet sync.

### Proof of Concept
Conceptually: construct a `CoinSpend` whose puzzle reveal curries to the plotnft singleton mod and whose `CREATE_COIN` memo encodes `(spec_namespace [nonce restriction_hints 1 (m [member_memo, member_memo, ...])])` where each `member_memo` is itself another `further_branching=1` `MofNHint` nested thousands of levels deep (each level a few bytes of CLVM). Submitting/observing this coin causes any syncing wallet's `PlotNFT2Wallet.identify()` → `get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo()` chain to recurse until `RecursionError` is raised. [3](#0-2)

    @classmethod
    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(
            nonce=nonce.as_int(),
            restrictions=[UnknownRestriction(hint) for hint in restriction_hints],
            puzzle=puzzle,
            additional_memos=additional_memos,
        )
