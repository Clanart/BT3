### Title
Unchecked fee multiplication can turn user input into an unintended miner fee - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` computes transaction fees with unchecked `u64` multiplication and addition before constructing the transaction to sign. In a release build, these operations wrap modulo `2^64`; in a checked build they panic. An attacker who can influence the fee rate, payment, input set, or omission of a change output can make the calculated `needed_fee` tiny while the actual transaction fee remains `sum(inputs) - sum(outputs)`. If no change output is produced, essentially all unspent input value is signed away as a miner fee.

### Finding Description
The vulnerable path calculates virtual transaction size, then multiplies it directly by `fee_per_vbyte` at `networks/bitcoin/src/wallet/send.rs:204-207`. It later performs unchecked addition in the solvency check at `networks/bitcoin/src/wallet/send.rs:215`. The transaction retains only the explicitly requested payment outputs when `change` is absent, while `fee()` defines the real fee as total prevout value minus total output value at `networks/bitcoin/src/wallet/send.rs:137-140`. The resulting transaction is then signed with Taproot sighashes committing to all prevouts at `networks/bitcoin/src/wallet/send.rs:373-390`. [1](#0-0) [2](#0-1) [3](#0-2) 

Because `fee_per_vbyte * vbytes` is not checked, a large public fee parameter can wrap to a small value. For example, if the estimated transaction is 100 vbytes and `fee_per_vbyte = 184467440737095518`, the product wraps to `100` modulo `2^64`. That wrapped value can satisfy the minimum-fee comparison even though the requested arithmetic fee was astronomically high. With `change == None`, no change output is added, so the signed transaction pays the entire input remainder as the actual fee. [4](#0-3) [5](#0-4) [6](#0-5) 

### Impact Explanation
This causes the threshold wallet to sign a transaction with a materially different economic effect from the checked fee calculation. The signature remains cryptographically valid for the generated sighash, so this is not a signature forgery; it is an arithmetic valuation flaw that produces an unintended transaction for signing. A 1 BTC input used to make a dust-sized payment without change can donate nearly the entire input to miners while `needed_fee()` reports only the wrapped, small fee. The signer cannot recover the burned value after broadcast. [7](#0-6) [6](#0-5) 

### Likelihood Explanation
The arithmetic values are ordinary `u64` API inputs and Bitcoin amounts rather than secret validator state. The attacker only needs a transaction-construction path that accepts or relays a manipulated fee rate and omits change. The wrapped result must merely pass the minimum relay check; no cryptographic assumption, malformed curve point, colluding signer, or validator misbehavior is required. The impact is limited by the amount of input selected for the transaction, so this is a Medium-severity funds-loss/valuation issue rather than a total key compromise. [8](#0-7) [1](#0-0) 

### Recommendation
Use checked arithmetic for every amount involved in fee and balance accounting:

- Replace `fee_per_vbyte * vbytes` and `fee_per_vbyte * vbytes_with_change` with `checked_mul`.
- Replace `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`.
- Use `checked_sum` or explicit accumulation for `input_sat`, `payment_sat`, and `fee()`.
- Reject a wrapped or overflowing fee with a new `TransactionError`, rather than continuing to transaction construction.
- Independently verify `self.fee() >= needed_fee` before returning `SignableTransaction`, and reject unexpectedly excessive actual fees.

The affected expressions are localized to `SignableTransaction::new` and `fee()` in `networks/bitcoin/src/wallet/send.rs`. [9](#0-8) [10](#0-9) 

### Proof of Concept
The following arithmetic demonstrates the flaw without requiring a Bitcoin node:

```rust
let vbytes: u64 = 100;
let fee_per_vbyte: u64 = (u64::MAX / vbytes) + 3;

// In a release build, this wraps to 100.
let needed_fee = fee_per_vbyte.wrapping_mul(vbytes);
assert_eq!(needed_fee, 100);

// This satisfies the minimum relay check at 1 sat/vbyte.
let minimum_relay = (1000u64 * vbytes) / 1000;
assert!(needed_fee >= minimum_relay);

// With no change output, the actual fee is still input - payment.
let input: u64 = 100_000_000;
let payment: u64 = 546;
assert!(input >= payment + needed_fee);

let actual_fee = input - payment;
assert_eq!(actual_fee, 99_999_454);
assert!(actual_fee > needed_fee);
```

At the API level, call `SignableTransaction::new` with a valid received input worth `100_000_000` sats, one valid payment of at least `DUST` sats, `change = None`, `data = None`, and `fee_per_vbyte = (u64::MAX / 100) + 3` for a layout whose calculated `vbytes` is 100. The constructor records a wrapped `needed_fee` of 100 sats but returns a transaction containing only the payment, causing `fee()` to report `99_999_454` sats. Subsequent `multisig`, `preprocess`, and `sign` calls commit the threshold signature to that high-fee transaction. [8](#0-7) [4](#0-3) [11](#0-10) [12](#0-11)
