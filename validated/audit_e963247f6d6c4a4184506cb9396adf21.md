### Title
Unchecked payment-total overflow permits signing a malformed Bitcoin transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` sums attacker-controlled payment amounts and input values with unchecked `u64` arithmetic, then adds the fee using unchecked addition. [1](#0-0) [2](#0-1) 

### Finding Description
The public transaction-construction API accepts arbitrary `payments: &[(ScriptBuf, u64)]` and `Vec<ReceivedOutput>` inputs. [3](#0-2)  Each payment must individually be at least `DUST`, but the code does not impose a total-output or Bitcoin `MAX_MONEY` bound. [4](#0-3) [5](#0-4)  `payment_sat` is calculated with `.sum::<u64>()`, and the solvency check uses `payment_sat + needed_fee` rather than checked arithmetic. [6](#0-5) [7](#0-6) 

A request containing multiple individually-valid payments whose sum exceeds `u64::MAX` wraps the total in release builds or panics where overflow checks are enabled. [8](#0-7)  The transaction still stores the original unwrapped amounts in its `TxOut` values, so the balance check can pass against a tiny wrapped total while the actual unsigned transaction contains enormous outputs. [6](#0-5) [9](#0-8) 

The resulting `SignableTransaction` can be converted into per-input FROST machines after `multisig` verifies only that each offset-adjusted group key corresponds to the referenced prevout script. [10](#0-9)  Signing commits each input to `Prevouts::All`, and completion inserts the resulting Schnorr signatures into the malformed transaction's witnesses. [11](#0-10) [12](#0-11) 

### Impact Explanation
An unprivileged party who can submit withdrawal/payment data can cause threshold signers to produce a validly signed transaction whose semantics were never actually validated. [13](#0-12)  This is a concrete signing of an unintended message: the signatures bind to a transaction containing outputs far beyond the checked `payment_sat`, the real input total, and Bitcoin's monetary range. [6](#0-5) [11](#0-10) 

Where overflow checks are enabled, the same input causes a panic during transaction construction, matching the report's crafted-input integer-overflow crash class. [1](#0-0)  Where wrapping arithmetic is used, the more severe outcome is returning a signable malformed transaction instead of rejecting it. [14](#0-13) 

### Likelihood Explanation
The attacker only needs to influence the payment list supplied to the public `SignableTransaction::new` API. [3](#0-2)  No validator compromise, leaked key, malformed curve point, or threshold collusion is required; the values are ordinary `u64` payment amounts, and each can satisfy the existing dust check. [5](#0-4) 

The trigger is deterministic because two non-dust amounts are sufficient to wrap `payment_sat`. [6](#0-5)  The attack does require an integration path that forwards externally supplied payment amounts to this constructor, which is the normal role of this transaction-building API. [3](#0-2) 

### Recommendation
Use checked arithmetic for `input_sat`, `payment_sat`, `payment_sat + needed_fee`, `payment_sat + fee_with_change`, `fee_per_vbyte * vbytes`, and `fee_per_vbyte * vbytes_with_change`. [1](#0-0) [15](#0-14) 

Reject any individual output or aggregate amount exceeding Bitcoin's maximum money supply before constructing `TxOut`s, and return `TransactionError` rather than panicking or wrapping. [16](#0-15)  The final `fee()` implementation should also use checked subtraction/addition so malformed state cannot panic or wrap during accounting. [17](#0-16) 

### Proof of Concept
```rust
use bitcoin::{Amount, OutPoint, ScriptBuf, TxOut, Txid};
use k256::Scalar;
use serai_bitcoin::wallet::{p2tr_script_buf, ReceivedOutput, SignableTransaction};

fn received_output(script: ScriptBuf, value: u64) -> ReceivedOutput {
    let mut bytes = Vec::new();

    // Zero HDKD offset.
    bytes.extend([0u8; 32]);

    // Consensus-encoded TxOut: value || compact-size script length || script.
    bytes.extend(value.to_le_bytes());
    bytes.extend([script.as_bytes().len() as u8]);
    bytes.extend(script.as_bytes());

    // Consensus-encoded OutPoint: txid || vout.
    bytes.extend([0u8; 32]);
    bytes.extend(0u32.to_le_bytes());

    ReceivedOutput::read(&mut bytes.as_slice()).unwrap()
}

fn overflow_payments(group_key: k256::ProjectivePoint) {
    let wallet_script = p2tr_script_buf(group_key).unwrap();
    let input = received_output(wallet_script.clone(), 10_000);

    let payments = [
        // Both satisfy amount >= DUST.
        (wallet_script.clone(), u64::MAX - 545),
        (wallet_script, 1_092),
    ];

    // payment_sat wraps to 546:
    // (u64::MAX - 545) + 1092 == 2^64 + 546.
    //
    // With a typical two-output transaction under ~428 vbytes and
    // fee_per_vbyte = 1, needed_fee is low enough that:
    // input_sat (10_000) >= payment_sat (546) + needed_fee.
    let tx = SignableTransaction::new(
        vec![input],
        &payments,
        None,
        None,
        1,
    )
    .unwrap();

    // The checked total was only 546 sats, but the actual first output is
    // u64::MAX - 545 sats.
    assert_eq!(tx.transaction().output[0].value, Amount::from_sat(u64::MAX - 545));
    assert_eq!(tx.transaction().output[1].value, Amount::from_sat(1_092));

    // If valid ThresholdKeys for wallet_script are supplied, this proceeds to
    // create FROST signature machines for the malformed transaction.
    // tx.multisig(&keys).unwrap().preprocess(rng);
}
```
