### Title
Blame verification swaps accuser/accused roles, causing honest accusers to be blamed and malicious share-senders to escape — (`processor/src/key_gen.rs`)

### Summary
The Traefik report concerns an authenticated party reading sensitive data through an API that lacks proper checks. The analogous surface in Serai is the coordinator-driven blame-verification path, which accepts attacker-influenced ordering of `accuser`/`accused`. In `CoordinatorMessage::VerifyBlame` handling, `AdditionalBlameMachine::blame` is invoked with the arguments swapped: `blame(accuser, accused, ...)` even though the signature is `blame(sender, recipient, ...)`. The sender of the disputed share is the `accused` and the recipient (who produced the ECDH proof) is the `accuser`. [1](#0-0) [2](#0-1) 

### Finding Description
`BlameMachine::blame` / `blame_internal` takes `(sender, recipient, msg, proof)` and calls `decrypt_with_proof(sender, recipient, msg, proof)`. Inside `decrypt_with_proof`, the per-message Schnorr proof-of-possession is verified with `pop_challenge(context, R, msg.key, from = sender, msg)`, and the DLEq proof is verified against `enc_keys[&decryptor]` (the recipient's registered encryption key). [3](#0-2) [4](#0-3) 

The PoP challenge binds `sender` into the transcript (`transcript.append_message(b"sender", sender.to_bytes())`), and `encrypt` signs the PoP with `from` = the actual share sender. [5](#0-4) 

In `processor/src/key_gen.rs`, the handler passes `accuser` as `sender` and `accused` as `recipient`:

```rust
.blame(accuser, accused, substrate_share, substrate_blame);
.blame(accuser, accused, network_share, network_blame);
``` [1](#0-0) 

The correct call is `blame(accused, accuser, ...)`. With the swap:

- PoP verification fails (the PoP was bound to `from = accused`, but `from` is set to `accuser`), so `decrypt_with_proof` returns `InvalidSignature`.
- `blame_internal` maps `InvalidSignature` to `return sender`, i.e. it returns `accuser`.
- The handler then emits `ProcessorMessage::Blame { participant: accuser }`, since neither `substrate_blame` nor `network_blame` equals `accused`. [6](#0-5) 

Additionally, the DLEq inside an `EncryptionKeyProof` is proven against `enc_keys[&decryptor]`; even if the PoP somehow passed, the accuser's proof is bound to the accuser's encryption key — which sits under `recipient = accused` here — so `InvalidProof` also maps back to blaming `recipient` = `accused` incorrectly in the other direction. The check `if (substrate_blame == accused) || (network_blame == accused)` can never be satisfied for a legitimate accusation.

### Impact Explanation
Every `VerifyBlame` evaluation returns the honest accuser as the faulty party. Two consequences:

1. A participant who correctly reports an invalid secret share is themselves fatally blamed/slashed — an unprivileged participant (the malicious sender) causes an honest party to be punished merely by sending a malformed `EncryptedMessage` readable via `EncryptedMessage::read`/`calculate_share`. [7](#0-6) 
2. A malicious DKG participant who broadcasts invalid shares can never be blamed through this path; `blame` can only ever return `accuser` (on `InvalidSignature`) or `accused` (on `InvalidProof`, which is also wrong because it blames the accused when the accuser supplied a bad proof). Blame accountability is fully inverted.

This is an incorrect verifier/arbitration formula over publicly submitted bytes, matching the accepted impact classes (an incorrect verifier formula / funds-equivalent punishment of the wrong party).

### Likelihood Explanation
Reachable entirely through public coordinator inputs: `VerifyBlame { id, accuser, accused, share, blame }` is a `CoordinatorMessage` carrying raw bytes (`share: Vec<u8>`, `blame: Option<Vec<u8>>`). [8](#0-7)  Any blame accusation routed through this handler deterministically produces the wrong verdict — no race, no cryptographic assumption, just swapped arguments. The DKG's in-crate tests exercise `machine.blame(ONE, TWO, ...)` with the correct ordering, so the inversion is only present at the processor integration layer. [9](#0-8) 

### Recommendation
Swap the argument order at both call sites to `.blame(accused, accuser, ...)`:

```rust
.blame(accused, accuser, substrate_share, substrate_blame);
.blame(accused, accuser, network_share, network_blame);
``` [1](#0-0) 

Also consider renaming the `blame` parameters from `(sender, recipient)` to `(accused, accuser)` or adding a typed wrapper so the integration layer cannot silently invert roles, and add a regression test in the processor covering `VerifyBlame` for both a genuinely-invalid share (must blame `accused`) and a false accusation (must blame `accuser`).

### Proof of Concept
1. Run a PedPoP DKG where participant `TWO` sends participant `ONE` an encrypted share whose ciphertext is corrupted but carries a valid PoP (as `invalidate_msg` does in tests). [10](#0-9) 
2. `ONE` calls `calculate_share`, gets `PedPoPError::InvalidShare { participant: TWO, blame: Some(proof) }`, and submits `InvalidShare { accuser: 1, faulty: 2, blame }`. [11](#0-10) 
3. The coordinator dispatches `VerifyBlame { accuser: 1, accused: 2, share, blame }`.
4. Handler calls `blame(sender=1, recipient=2, ...)`; `decrypt_with_proof` checks the PoP with `from = 1`, but the PoP was created with `from = 2`, so it returns `InvalidSignature`; `blame_internal` returns `sender = 1` = the accuser. [12](#0-11) 
5. `ProcessorMessage::Blame { participant: 1 }` is emitted — the honest accuser is blamed and the malicious sender `TWO` escapes. [6](#0-5)

  pub fn calculate_share<R: RngCore + CryptoRng>(
    mut self,
    rng: &mut R,
    mut shares: HashMap<Participant, EncryptedMessage<C, SecretShare<C::F>>>,
  ) -> Result<BlameMachine<C>, PedPoPError<C>> {
    validate_map(
      &shares,
      &self.params.all_participant_indexes().collect::<Vec<_>>(),
      self.params.i(),
    )?;

    let mut batch = BatchVerifier::new(shares.len());
    let mut blames = HashMap::new();
    for (l, share_bytes) in shares.drain() {
      let (mut share_bytes, blame) =
        self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
      let share =
        Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
          PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
        })?);
      share_bytes.zeroize();
      *self.secret += share.deref();

      blames.insert(l, blame);
      batch.queue(
        rng,
        BatchId::Share(l),
        share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share),
      );
    }
    batch.verify_with_vartime_blame().map_err(|id| {
      let (l, blame) = match id {
        BatchId::Decryption(l) => (l, None),
        BatchId::Share(l) => (l, Some(blames.remove(&l).unwrap())),
      };
      PedPoPError::InvalidShare { participant: l, blame }
    })?;

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}

  pub(crate) fn decrypt_with_proof<E: Encryptable>(
    &self,
    from: Participant,
    decryptor: Participant,
    mut msg: EncryptedMessage<C, E>,
    // There's no encryption key proof if the accusation is of an invalid signature
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Result<Zeroizing<E>, DecryptionError> {
    if !msg.pop.verify(
      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),
    ) {
      Err(DecryptionError::InvalidSignature)?;
    }

    if let Some(proof) = proof {
      // Verify this is the decryption key for this message
      proof
        .dleq
        .verify(
          &mut encryption_key_transcript(self.context),
          &[C::generator(), msg.key],
          &[self.enc_keys[&decryptor], *proof.key],
        )
        .map_err(|_| DecryptionError::InvalidProof)?;

      cipher::<C>(self.context, &proof.key).apply_keystream(msg.msg.as_mut().as_mut());
      Ok(msg.msg)
    } else {
      Err(DecryptionError::InvalidProof)
    }
  }
