## Analog Found: Unchecked Low‑Level Call Return Value in `IntentGatewayV2.withdraw()` Permanently Marks Escrow as Settled Even When the Token Transfer Silently Fails

### Title
Escrow withdrawal trusts raw call success instead of the ERC20 return value, permanently burning escrow accounting on a false-success transfer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core defect is trusting the mere non-revert of a low-level `.call()` (to `token0()`) as a proxy for a token's real behavior, without validating what was actually returned/executed — causing tokens to become permanently stuck with no recovery path. The same defect class exists locally in `IntentGatewayV2.withdraw()`: it uses a raw `.call()` to invoke `IERC20.transfer` and gates all escrow-accounting state exclusively on whether the call reverted, never decoding/verifying the boolean return value.

### Finding Description
In `withdraw()`, escrowed input tokens are released via: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

The success check only verifies that the call did not revert (`success == true`); it never decodes/validates the `bytes` return data as a `bool`. Non-standard ERC20 tokens that signal failure by returning `false` instead of reverting (e.g. legacy tokens, some deflationary/fee tokens, tokens with a pausable or blacklist mode that returns `false` rather than reverting) will make this call return `success = true` with a `false` payload. The contract proceeds as if the transfer succeeded: it decrements `_orders[commitment][token]`, sets `_filled[body.commitment] = beneficiary` (line 684, unconditionally at function entry), and emits `EscrowReleased`/`EscrowRefunded` — permanently finalizing the withdrawal state even though the beneficiary received nothing.

This mirrors the SushiMakerAuction bug exactly: a critical state transition (there, "reject as LP token"; here, "escrow considered settled") is derived solely from the *success* of a low-level call, without accounting for tokens whose actual behavior diverges from a plain revert/success signal. Once `_filled`/`_orders` are updated, there is no other path in the contract to reclaim the un-transferred tokens for the beneficiary — same "stuck funds, no manual intervention path" outcome described in the report.

Unlike the `newOrder()` escrow deposit path, which correctly uses `SafeERC20.safeTransferFrom` (line 453) — a library that decodes and validates the boolean return — the `withdraw()` release path bypasses `SafeERC20` entirely and uses a bare `.call()` with an incomplete check.

### Impact Explanation
This falls under "stealing or loss of funds" and "false proof/state acceptance" in the bounty's impact list: the escrow-accounting state (`_orders`, `_filled`) is irreversibly marked as settled while the actual asset transfer to the rightful beneficiary silently failed. Funds remain locked in the `IntentGatewayV2` contract with no reclaim mechanism, and this can be reached through both `cancelOrder` (refund path) and cross-chain `onAccept` `RedeemEscrow`/`RefundEscrow` handling — both of which call the same vulnerable `withdraw()`.

### Likelihood Explanation
Triggering this requires only that one of the order's escrowed `input` tokens be a non-standard ERC20 that returns `false` on failure instead of reverting — a real, still-in-use category of tokens on EVM chains. No malicious relayer, prover, or governance actor is needed; a normal user creating an order with such a token, or the token later entering a failure state (e.g., paused, blacklisted recipient) during withdrawal, is sufficient to trigger permanent fund loss through this exact code path.

### Recommendation
Replace the raw `.call()` in `withdraw()` (and the analogous fee-token transfer at line 711) with `SafeERC20.safeTransfer(beneficiary, amount)`, consistent with the deposit path's use of `safeTransferFrom`. This ensures both non-reverting `false`-return tokens and non-standard no-return tokens are handled correctly, and that escrow accounting state is never advanced on a transfer that did not actually deliver funds.

### Proof of Concept
1. Deploy a token `T` with a `transfer()` implementation that returns `false` on certain conditions (e.g., recipient blacklisted, or below-minimum transfer) without reverting.
2. Create an order in `IntentGatewayV2` with `T` as an input token, escrowing real balance via `newOrder()` (uses `safeTransferFrom`, succeeds normally).
3. Trigger a refund/withdrawal path (e.g. `cancelOrder` same-chain path or a `RefundEscrow`/`RedeemEscrow` `onAccept` message) that calls `withdraw(body, true)`.
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` but with return data encoding `false` (transfer did not occur).
5. `withdraw()` does not decode this return value, so it proceeds: `_orders[commitment][token] -= amount` and marks `_filled[commitment] = beneficiary`, emitting `EscrowRefunded`.
6. The beneficiary never received `T`, and the contract's accounting shows the order as fully settled with no path to retry or reclaim the tokens — permanent fund loss. [2](#0-1) [3](#0-2) [4](#0-3)
