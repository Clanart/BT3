### Title
Farmer-facing YAML pool-config mirror (`PoolingShareState`) can diverge from the wallet's on-chain-derived `PlotNFT` pool state, allowing pool reward payouts to be redirected to a stale destination - ([File: chia/wallet/plotnft_wallet/plotnft_wallet.py])

### Summary
This is a plausible analog of the reported bug class (an authority value duplicated across two components that can drift out of sync), but I could not fully verify the exploit path within the available tool budget. The wallet's on-chain `PlotNFT` state (in `PlotNFT2Wallet.coin_added`) is the chain-derived source of truth for pool/target puzzle hash, while a separate on-disk YAML mirror (`PoolingShareState`, accessed via `pool_config.target_puzzle_hash` / `pool_config.payout_instructions`) is read back later (e.g. `rewards_claim_puzhash`) to decide where self-pooled rewards are ultimately paid.

### Finding Description
`PlotNFT2Wallet.coin_added()` treats the wallet's synced singleton state (`coin_data: PlotNFT`) as authoritative and pushes updates into the YAML-backed `PoolingShareState` mirror: [1](#0-0) 
and elsewhere a property reads the payout destination back out of that same mirror rather than the current chain-verified `PlotNFT` state: [2](#0-1) 

This mirrors the structural pattern in the original report exactly: one authority value (governor / here, payout/target puzzle hash) is stored and updated in two places — the durable/chain-derived wallet record and a secondary side-channel file (`pooling_share_state.yaml`) — and a downstream consumer (`rewards_claim_puzhash`, used when claiming self-pooled rewards) trusts the side-channel copy instead of re-deriving it from the authoritative source at use time. The project's own module notes call this out directly as a known risk area: [3](#0-2) 

### Impact Explanation
If the YAML mirror update is skipped, interrupted, or executed against a stale action-scope/derivation index (as the pools.md fragility note warns), `pool_config.payout_instructions`/`target_puzzle_hash` in the mirror can point to an address that no longer matches the wallet's actual current pool/self-pooling target. Because `claim_pool_rewards()`-style flows use this mirror value to pick the payout destination for absorbed pool rewards, this could redirect farmed rewards away from the address the user actually controls on-chain, which matches the "reward redirection" impact class explicitly allowed by the validation rules.

### Likelihood Explanation
Low-to-moderate. This requires a wallet-local desync between the DB-confirmed singleton state and the YAML mirror (e.g., missed/aborted `coin_added` mirror update, rollback edge cases, or concurrent YAML writes), not an attacker-controlled remote input. It is a local wallet-state consistency bug rather than a directly attacker-triggerable one from an external spend bundle or peer, which weakens its severity relative to the reported Isle finding.

### Recommendation
Do not treat the YAML `PoolingShareState` mirror as authoritative for reward-claim destination decisions. `rewards_claim_puzhash` (and any other read of `payout_instructions`/`target_puzzle_hash` used for fund-moving decisions) should re-derive the destination from the current wallet-confirmed `PlotNFT`/pool singleton state (the same authority `PlotNFT2Wallet.coin_added` uses to populate the mirror), using the YAML file only as a farmer-facing convenience cache, consistent with the module's own stated design intent that "the blockchain is the authority for pool singleton history."

### Proof of Concept
Not independently constructed/verified — I was unable to complete tracing the exact call sites that consume `rewards_claim_puzhash` during a live reward-claim transaction before the tool budget was exhausted, so this should be treated as an analog hypothesis requiring further verification (specifically confirming whether `claim_pool_rewards()` for `PlotNFT2Wallet` actually uses `rewards_claim_puzhash` as the paid-to address, and under what conditions the YAML mirror update in `coin_added` can be skipped or made stale relative to confirmed chain state) rather than a fully proven vulnerability.
