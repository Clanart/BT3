Based on my research, the strongest local analog to the "price oracle / unchecked value source" bug class is in `modules/pallets/state-coprocessor/src/impls.rs`, where a reward-beneficiary field is trusted without being bound to any verified message signer — a broken-invariant class that mirrors the report's "unauthenticated/unchecked value feeds a payout" theme.

### Title
Unauthenticated `address` field in `GetRequestsWithProof` allows self-minting of relayer reputation rewards - (File: modules/pallets/state-coprocessor/src/impls.rs)

### Summary
`Pallet::handle_get_requests` accepts a caller-supplied `GetRequestsWithProof.address: Vec<u8>` field described only as "Address that should be credited with fees," and mints `ReputationAsset` reputation tokens proportional to the batch's byte size directly to that address — without validating that `address` is bound to the account that authored, signed, or paid for the extrinsic. [1](#0-0) [2](#0-1) 

### Finding Description
`handle_get_requests` verifies source/destination state proofs for the `GetRequest`/`GetResponse` pair and meters bandwidth correctly via `BandwidthGate::try_consume` [3](#0-2) . All of that is proof-anchored and sound. However, the reputation-minting step at the end of the function reads the per-byte `MintPerByte` rate shared with `pallet-messaging-incentives` and mints straight to whatever 32-byte `address` the caller embedded in the `GetRequestsWithProof` payload, with no signature check tying that address to the actual submitter:

```
let rate = pallet_messaging_incentives::MintPerByte::<T>::get();
if !rate.is_zero() && total_bytes > 0 {
    if let Ok(bytes32) = <[u8; 32]>::try_from(address.as_slice()) {
        let relayer: T::AccountId = bytes32.into();
        ...
        ReputationAsset::mint_into(&relayer, amount)
    }
}
``` [4](#0-3) 

This is architecturally different from `pallet-messaging-incentives::on_executed`, which explicitly recovers the relayer's account from the sr25519 signature on the message before minting [5](#0-4) . The state-coprocessor path has no equivalent authentication step for `address` — it is taken as-is from the submitted call data.

### Impact Explanation
Any account able to construct a valid state proof for a `Get` request/response pair (which does not require being the relayer that actually delivered anything — the proofs are derived from public source/destination chain state) can set `address` to their own account and repeatedly mint `ReputationAsset` proportional to `total_bytes` of the batch. This breaks the "reward the party that did the work" invariant underpinning the reputation/incentive system, directly matching the impact-gate category of "logic attacks" and "unauthorized... transaction manipulation" against a reward-accounting surface (bandwidth/relayer incentives), analogous to how an unchecked price value can be steered to benefit an attacker in the seed report.

### Likelihood Explanation
This does not require a malicious relayer, prover, or governance actor — an ordinary chain user who can produce the requisite state proofs (public data, not privileged) can call this path and choose an arbitrary reward beneficiary. The likelihood depends on confirming the pallet's dispatchable wraps `handle_get_requests` with a plain signed origin and no additional origin-to-`address` binding; I found strong evidence of this pattern in `impls.rs` but did not get to fully read `modules/pallets/state-coprocessor/src/lib.rs`'s dispatchable/call_index definition before the tool budget ran out, so it is not 100% confirmed that no origin check exists at the call-site level. This should be verified directly against `modules/pallets/state-coprocessor/src/lib.rs`.

### Recommendation
Bind `address` to a verified signer the same way `pallet-messaging-incentives::relayer_for` does (sr25519 signature recovery over the message), or drop the free-form `address` field entirely and mint to `ensure_signed(origin)` instead of an attacker-chosen `Vec<u8>`.

### Proof of Concept
1. Attacker observes public source-chain state and constructs a valid `GetRequest`/`GetResponse` proof pair for real Get requests they did not relay.
2. Attacker submits `handle_get_requests` (or its wrapping extrinsic) with `GetRequestsWithProof.address` set to their own 32-byte account id.
3. Proof verification and bandwidth metering succeed as normal (they only check proof validity, not who submitted it).
4. `ReputationAsset::mint_into(&attacker_account, amount)` mints reputation proportional to `total_bytes`, with `amount` unbounded by any check that the attacker actually relayed anything — repeatable for every valid proof set the attacker can assemble.

**Caveat:** confirmation that no origin-binding check exists at the pallet's dispatchable boundary requires reading `modules/pallets/state-coprocessor/src/lib.rs` (not fully reviewed here); if such a check exists at the call site, this finding would need re-scoping.
