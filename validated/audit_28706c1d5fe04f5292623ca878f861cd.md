### Title
Panic in PedPoP blame adjudication via unregistered participant index enables denial of service - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` index `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with participant indexes taken from an attacker-controlled blame accusation. A participant can supply a `sender`/`recipient` `Participant` index that was never registered, causing a HashMap-index panic that kills the process evaluating blame — the same class as CVE-2023-7258 (a bookkeeping/lookup defect turning untrusted input into a crash).

### Finding Description
`AdditionalBlameMachine::blame` delegates to `BlameMachine::blame_internal`: [1](#0-0) 

`blame_internal` calls `Decryption::decrypt_with_proof`, which indexes the decryption-key map by `decryptor` before verifying the DLEq proof: [2](#0-1) 

and later indexes `self.commitments[&sender]`: [3](#0-2) 

Neither `sender`, `recipient`, nor `decryptor` is validated against the registered participant set (`enc_keys` is populated only for `1..=n` in `AdditionalBlameMachine::new`, lines 656–660; `commitments` likewise). `Participant::new` accepts any nonzero u16 up to 65535, so indexes `> n` parse fine: [4](#0-3) 

A panic occurs on the `HashMap` `Index` impl (`self.map[&key]` panics on absent key) in two places:

1. `enc_keys[&decryptor]` — reachable if the accuser names a `recipient` outside `1..=n`. This path triggers before proof validity is checked, since the slice `[self.enc_keys[&decryptor], *proof.key]` is evaluated as an argument to `dleq.verify`.
2. `commitments[&sender]` — reachable by a malicious accuser who is a legitimate participant: they build an `EncryptedMessage` with a valid PoP (they control `msg.key` and can sign `pop_challenge` themselves) plus a valid `EncryptionKeyProof` (they know their own `enc_key` scalar, so they can produce the DLEq over `generator`/`msg.key`), then accuse a `sender` index that never registered.

The panic propagates out of `blame`/`blame_internal` uncaught — the function signature returns `(AdditionalBlameMachine<C>, Participant)` with no error channel — aborting the host (e.g., the processor's `handle_machine`/`AdditionalBlameMachine` flow in `processor/src/key_gen.rs`, which calls `AdditionalBlameMachine::new(...).unwrap().blame(accuser, accused, ...)`).

### Impact Explanation
Any node that evaluates a blame accusation (DKG participants via `BlameMachine::blame`, or third-party adjudicators via `AdditionalBlameMachine::blame`) crashes on the malformed-but-parseable accusation. This aborts key generation adjudication and, depending on the host, kills the whole processor — a denial of service analogous to the gVisor sandbox panic. Because the crash is triggered by peer-supplied `Participant` fields and `EncryptedMessage`/`EncryptionKeyProof` bytes, it is reachable with public inputs.

### Likelihood Explanation
Requires a protocol participant (or anyone able to submit a blame accusation to an `AdditionalBlameMachine` adjudicator) to craft the message. Constructing the PoP signature and DLEq proof is fully within the attacker's ability when the accuser is a registered participant; no secret material beyond their own encryption key is needed. No timing or probabilistic conditions apply — the panic is deterministic on the out-of-range index. Consistent with the source advisory's Medium severity: an authenticated attacker with protocol privileges kills the process.

### Recommendation
Validate `sender`, `recipient`, and `decryptor` against the registered participant set before indexing, and return a determinate fault rather than panicking. Specifically:

- In `Decryption::decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:388), replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor)` and return `Err(DecryptionError::InvalidProof)` (or a dedicated fault) on `None`.
- In `BlameMachine::blame_internal` (crypto/dkg/pedpop/src/lib.rs:599), fetch `self.commitments.get(&sender)` and treat a missing entry as sender fault (or reject the accusation as malformed) instead of indexing.
- Consider asserting `sender`/`recipient` are within `1..=n` at the `blame` API boundary so garbage accusation fields are rejected before any map lookups.

### Proof of Concept
```rust
// Setup: DKG with n = 3, t = 2. An adjudicator builds an
// AdditionalBlameMachine from the three registered commitment messages.
let mut machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// Attacker is participant 1 (registered, knows their enc_key).
// They craft an EncryptedMessage with a valid PoP under a key they control,
// and a valid EncryptionKeyProof proving knowledge of the ECDH shared key
// for *their own* enc_key (they know its discrete log).
let msg: EncryptedMessage<Ristretto, SecretShare<...>> = /* valid msg */;
let proof: EncryptionKeyProof<Ristretto> = /* valid DLEq for accuser's enc_key */;

// The accused sender index was never registered (n = 3, but sender = 7).
let sender = Participant::new(7).unwrap();
let recipient = Participant::new(1).unwrap(); // the accuser

// blame_internal passes pop.verify and dleq.verify, then evaluates
// self.commitments[&sender] -> HashMap index panic.
machine.blame(sender, recipient, msg, Some(proof));
// panics: "key not found" — process aborts instead of returning a fault.
```

Equivalently, naming a `recipient`/`decryptor` outside `1..=n` panics earlier at `self.enc_keys[&decryptor]` inside `decrypt_with_proof`, before the DLEq is even verified.
