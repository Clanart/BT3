## Analysis Result

Analog found: the EIP‑7702 authorization‑admission logic in the transaction pool identifies a "reserved" delegated account purely by the `authority` address recovered from a `SetCodeAuthorization`, without binding that reservation to a specific transaction the authorizing user actually intended to submit. This mirrors the Meson `encodedSwap` flaw: the identifier used for admission control (the authority address) is decoupled from any specific initiator-bound transaction, so a third party who observes a signed authorization can submit a transaction carrying it first and consume the "one in-flight tx" slot, blocking the legitimate transaction that was supposed to accompany it.

### Title
Authority-based tx-pool admission slot for EIP-7702 SetCode authorizations can be front-run to censor a specific account's transaction - (File: blockchain/tx_pool.go)

### Summary
`TxPool.validateAuth` / `checkDelegationLimit` enforce "at most one in-flight transaction" for any address that is either a delegated (7702) account or named as `authority` in an authorization list, keyed solely by that address [1](#0-0) . A `SetCodeAuthorization` is a standalone signed tuple `(chainId, address, nonce)` that is not bound to any particular sponsoring transaction, sender, or gas parameters [2](#0-1) . Anyone who has seen a victim's authorization (e.g., in the mempool, or obtained via a wallet/dApp flow before the sponsor transaction propagates) can repackage it into their own `TxTypeEthereumSetCode` transaction and submit it first, occupying the sole pending/queued slot reserved for that authority and causing the victim's intended sponsored transaction to be rejected with `ErrAuthorityReserved` / `ErrInflightTxLimitReached`.

### Finding Description
`checkDelegationLimit` short-circuits only when the sender has neither existing delegated code nor a pending authorization tracked via `pool.all.hasAuth(from)` [3](#0-2) ; otherwise it requires the new tx to either have the current pending nonce or already be a pending nonce/replacement, else returns `ErrOutOfOrderTxFromDelegated` / relies on `ErrInflightTxLimitReached`. Separately, `validateAuth` iterates `tx.SetCodeAuthorities()` and rejects the tx with `ErrAuthorityReserved` if the authority address already has more than one transaction counted across `pool.pending`/`pool.queue` [4](#0-3) .

Crucially, the admission key is the `authority` address recovered from the authorization signature — not any property tying the authorization to a specific sponsor or transaction content. `SetCodeAuthorization.Authority()` only recovers the ECDSA signer over `(chainId, address, nonce)` [5](#0-4) ; the same authorization can legally be embedded by any transaction sender/sponsor, since EIP-7702 was explicitly designed to allow a third party to submit the sponsoring transaction. Because the pool reserves the slot by `authority` alone (the "primary identifier" analogous to Meson's `encodedSwap`, which likewise omits any binding to the true initiator), a malicious observer can copy the authorization out of the mempool (or otherwise obtain it before the legitimate sponsor broadcasts) and submit a cheap/garbage `TxTypeEthereumSetCode` transaction carrying that authorization first. This occupies the sole reserved slot for that authority, so when the legitimate sponsor's transaction (which was supposed to carry the same authorization to deploy the intended delegation target) arrives, it is rejected by `validateAuth`/`checkDelegationLimit`.

### Impact Explanation
This allows a censorship/denial-of-service attack targeting a specific victim account's EIP-7702 delegation setup: the victim's sponsor cannot get their intended `SetCode` transaction (which installs the account's smart-account delegation) admitted to the pool for as long as the attacker's competing transaction using the same authorization occupies the pending slot, and once mined, the state's nonce for `authority` advances, invalidating the original authorization outright and forcing the victim to re-sign and restart the whole sponsored-account setup flow. Given Kaia's block-building/gasless/auction bundling paths depend on `SetCode` transactions being admitted promptly (e.g., account abstraction / smart-account onboarding flows), this is a meaningful availability/censorship impact reachable purely by an unprivileged transaction sender who is able to observe a pending authorization.

### Likelihood Explanation
Likelihood is moderate: authorizations are only visible pre-confirmation if propagated through gossip/mempool or otherwise exposed (e.g., via off-chain relay services, similar to how the original Meson bug required observing `encodedSwap` in the mempool). No cryptographic secret is required to reuse the authorization — only the previously-signed authorization bytes, which are not bound to a specific sponsor. The check is purely address-keyed and applies uniformly regardless of who submits the competing transaction.

### Recommendation
- **Short term:** Monitor `ErrAuthorityReserved` / `ErrInflightTxLimitReached` occurrences for authorities whose competing transaction is not the expected sponsor, to detect front-running/censorship in the wild.
- **Long term:** Consider deriving the pool admission slot not from the bare `authority` address alone (i.e., the raw `(chainId, address, nonce)` signature), but from a stronger identifier that also factors in intended usage (e.g., only displace/occupy the slot with lower priority or allow replacement by higher-fee/originally-intended transactions), and/or allow the legitimate sponsor to replace an occupying low-value transaction that uses the same authorization, analogous to how MesonPools uses `swapId` instead of a bare, unbound identifier.

### Proof of Concept
1. Victim signs `SetCodeAuthorization{ChainID, Address: <delegationTarget>, Nonce: N}` via `SignSetCode` [6](#0-5)  intending for a sponsor to submit a `TxTypeEthereumSetCode` transaction carrying this authorization.
2. Attacker observes/obtains this authorization (e.g., from mempool propagation) before the sponsor's transaction is broadcast.
3. Attacker crafts and submits their own `TxTypeEthereumSetCode` transaction embedding the identical authorization tuple, targeting `pool.queue`/`pool.pending[authority]`.
4. `validateAuth` counts this transaction against `authority` [4](#0-3) , occupying the one allowed in-flight slot.
5. When the legitimate sponsor's transaction later arrives with the same authority, `checkDelegationLimit`/`validateAuth` rejects it (`ErrInflightTxLimitReached`/`ErrAuthorityReserved`), and if the attacker's tx is mined first, `applyAuthorization`'s nonce check (`GetNonce(authority) != auth.Nonce`) invalidates the victim's original authorization entirely [7](#0-6) , forcing the victim to restart the delegation setup.

// validateAuth verifies that the transaction complies with code authorization
// restrictions brought by SetCode transaction type.
func (pool *TxPool) validateAuth(tx *types.Transaction) error {
	// Allow at most one in-flight tx for delegated accounts or those with a
	// pending authorization.
	if err := pool.checkDelegationLimit(tx); err != nil {
		return err
	}

	// For symmetry, allow at most one in-flight tx for any authority with a
	// pending transaction.
	for _, auth := range tx.SetCodeAuthorities() {
		var count int
		if pending := pool.pending[auth]; pending != nil {
			count += pending.Len()
		}
		if queue := pool.queue[auth]; queue != nil {
			count += queue.Len()
		}
		// Replace the existing in-flight transaction for delegated accounts
		// are still supported
		if count > 1 {
			return ErrAuthorityReserved
		}
	}
	return nil
}

// SignSetCode creates a signed the SetCode authorization.
func SignSetCode(prv *ecdsa.PrivateKey, auth SetCodeAuthorization) (SetCodeAuthorization, error) {
	sighash := auth.sigHash()
	sig, err := crypto.Sign(sighash[:], prv)
	if err != nil {
		return SetCodeAuthorization{}, err
	}
	r, s, _ := decodeSignature(sig)
	return SetCodeAuthorization{
		ChainID: auth.ChainID,
		Address: auth.Address,
		Nonce:   auth.Nonce,
		V:       sig[crypto.RecoveryIDOffset],
		R:       *uint256.MustFromBig(r),
		S:       *uint256.MustFromBig(s),
	}, nil
}

// Authority recovers the authorizing account of an authorization.
func (a *SetCodeAuthorization) Authority() (common.Address, error) {
	sighash := a.sigHash()
	if !crypto.ValidateSignatureValues(a.V, a.R.ToBig(), a.S.ToBig(), true) {
		return common.Address{}, ErrInvalidSig
	}
	// encode the signature in uncompressed format
	var sig [crypto.SignatureLength]byte
	a.R.WriteToSlice(sig[:32])
	a.S.WriteToSlice(sig[32:64])
	sig[64] = a.V
	// recover the public key from the signature
	pub, err := crypto.Ecrecover(sighash[:], sig[:])
	if err != nil {
		return common.Address{}, err
	}
	if len(pub) == 0 || pub[0] != 4 {
		return common.Address{}, errors.New("invalid public key")
	}
	var addr common.Address
	copy(addr[:], crypto.Keccak256(pub[1:])[12:])
	return addr, nil
}

func (st *StateTransition) validateAuthorization(auth *types.SetCodeAuthorization) (authority common.Address, err error) {
	// Verify chain ID is 0 or equal to current chain ID.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(st.evm.ChainConfig().ChainID) != 0 {
		return authority, ErrAuthorizationWrongChainID
	}
	// Limit nonce to 2^64-1 per EIP-2681.
	if auth.Nonce+1 < auth.Nonce {
		return authority, ErrAuthorizationNonceOverflow
	}
	// Validate signature values and recover authority.
	authority, err = auth.Authority()
	if err != nil {
		return authority, fmt.Errorf("%w: %v", ErrAuthorizationInvalidSignature, err)
	}
	// Check the authority account
	//  1) doesn't have code or has existing delegation
	//  2) matches the auth's nonce
	//
	// Note it is added to the access list even if the authorization is invalid.
	st.state.AddAddressToAccessList(authority)
	code := st.state.GetCode(authority)
	if _, ok := types.ParseDelegation(code); len(code) != 0 && !ok {
		return authority, ErrAuthorizationDestinationHasCode
	}
	if have := st.state.GetNonce(authority); have != auth.Nonce {
		return authority, ErrAuthorizationNonceMismatch
	}
	return authority, nil
}
