## Title
Nil-pointer dereference crash in public EVM JSON-RPC nodes when reading a block containing a malformed `MsgEVMTransaction` - (File: evmrpc/utils.go, evmrpc/tx.go)

### Summary
`MsgEVMTransaction.AsTransaction()` (in `x/evm/types/message_evm_transaction.go`) returns `(nil, nil)` whenever `UnpackTxData(msg.Data)` fails to unpack the `Any`-encoded transaction payload: [1](#0-0) 
Several public-facing EVM JSON-RPC code paths call `AsTransaction()` and then immediately dereference the returned `*ethtypes.Transaction` (calling `.Hash()`, etc.) without checking for a `nil` result, e.g. in `filterTransactions`: [2](#0-1) 
and in `GetEvmTxIndex`: [3](#0-2) 

### Finding Description
This mirrors the CVE-2017-17850 bug class: a message that is missing/lacks a field the receiver's dialog-processing code implicitly assumes is present, causing the server to dereference a null value and crash. Here, `MsgEVMTransaction.Data` is an `Any` that is supposed to unpack into `ethtx.TxData`; if it fails to unpack (e.g., malformed/unsupported inner type or corrupted bytes), `AsTransaction()` silently swallows the error and returns `nil` for both the `*ethtypes.Transaction` and `ethtx.TxData`: [1](#0-0) 

Downstream RPC code that iterates block transactions to serve `eth_getTransactionByHash`, `eth_getTransactionByBlockNumberAndIndex`, `eth_getBlockByNumber` (with full transactions), etc. calls `AsTransaction()` and immediately calls `.Hash()` on the result without a nil check:
- `filterTransactions`, used by `getFilteredMsgs`/`GetTransactionByHash`/block transaction listing, does `ethtx, _ := m.AsTransaction(); hash := ethtx.Hash()` [2](#0-1) 
- `GetEvmTxIndex`, used by `GetTransactionByHash` for committed transactions, does `etx, _ = m.AsTransaction(); txHash = etx.Hash()` [3](#0-2) 

If `etx`/`ethtx` is `nil`, `.Hash()` panics with a nil-pointer dereference. Because `GetTransactionByHash` and other RPC handlers only wrap the handler in `recover()` for metrics purposes via `recordMetricsWithError(..., recover())` at the top-level defer (see `evmrpc/tx.go` `GetTransactionByHash`), whether the panic is safely recovered per-request depends on whether this recover actually re-panics or swallows it. I could not fully verify (due to index truncation) whether `recordMetricsWithError`'s `recover()` call effectively suppresses the panic for the whole process or only records it and still lets it propagate/crash the request goroutine (and potentially the HTTP server if unrecovered elsewhere).

The open question that limits full certainty here is whether a transaction whose `Data` field fails `UnpackTxData` can actually be included in a committed block in the first place. `MsgEVMTransaction` message decoding and its `ValidateBasic`/ante-handler pipeline (`EvmStatelessChecks`, `EVMPreprocessDecorator`, `EVMSigVerifyDecorator`) call `AsTransaction()` in several places and generally reject a `nil` transaction, but I was unable to confirm from the index whether there's a decode/execution path where a message with an un-unpackable `Data` can slip past ante checks and mempool validation yet still be persisted in a block that RPC nodes must later read back and iterate over (e.g. via a `UnpackInterfaces` call that used a different, laxer registry, or via a giga-executor fast-path). Because of this uncertainty in reachability of the exact "malformed but committed" precondition, I cannot assert with full confidence that this is exploitable by an ordinary external submitter of a single transaction without also being caught earlier by validation.

### Impact Explanation
If reachable, a single crafted transaction with a `Data` payload that fails to unpack into valid EVM tx data, once committed to a block, would cause every public RPC node serving `eth_getTransactionByHash`/`eth_getTransactionByBlockNumberAndIndex`/block-with-full-tx queries for that block to nil-pointer-dereference and potentially crash the RPC-serving goroutine or process, rather than returning an RPC error — a denial-of-service against default-configuration RPC nodes.

### Likelihood Explanation
Low-to-medium confidence. The nil-check gaps in `filterTransactions` and `GetEvmTxIndex` are real code defects, but I could not confirm (within available context) that a message with unparseable `Data` can pass the full ante/preprocessing/consensus pipeline and be persisted to a block, which is the necessary precondition for the RPC-read code path to be hit. Ante-handler code (`EVMPreprocessDecorator`, `EVMSigVerifyDecorator`, `EvmDeliverTxAnte`) all call `AsTransaction()`/`MustGetEVMTransactionMessage` early and appear designed to reject malformed data before execution, which likely prevents the malformed tx from ever reaching a committed block in the normal path.

### Recommendation
Add explicit nil checks after every call to `AsTransaction()` in `evmrpc/utils.go` (`filterTransactions`), `evmrpc/tx.go` (`GetEvmTxIndex`, `getEthTxForTxBz`, `getTransactionWithBlock`), and any other public-RPC code path that dereferences the returned `*ethtypes.Transaction`, treating a `nil` result as "skip/exclude this entry" or return a proper JSON-RPC error rather than panicking. Additionally, verify end-to-end that a `MsgEVMTransaction` whose `Data` fails `UnpackTxData` can never be committed to a block (i.e., confirm ante/mempool/consensus-level rejection is unconditional and cannot be bypassed), and add a regression test that constructs such a malformed message, forces it into a block cache/test app state, and confirms RPC read paths return an error instead of panicking.

### Proof of Concept
Not fully verified end-to-end due to inability to confirm that a `MsgEVMTransaction` with unparseable `Data` can be persisted into a committed block (this would require bypassing or exploiting a gap in the ante/mempool pipeline, which I could not confirm exists from the available code). If such a bypass exists, the PoC outline would be:
1. Construct a `MsgEVMTransaction` whose `Data` `Any` has a `TypeUrl` matching a registered `ethtx.TxData` implementation but with a payload that fails to unmarshal within `UnpackTxData`.
2. Get this message committed into a block (mechanism unconfirmed).
3. Call `eth_getTransactionByHash` (or `eth_getBlockByNumber` with full transactions) against a public RPC node for that block/tx; the node's `filterTransactions`/`GetEvmTxIndex` code calls `AsTransaction()` (returns `nil, nil`) and immediately calls `.Hash()` on the nil result, panicking the RPC-serving goroutine.
