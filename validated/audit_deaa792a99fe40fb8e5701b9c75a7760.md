### Title
OP_RETURN data output excluded from weight/vbytes calculation, producing under-funded or non-standard transactions - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` pushes an `OP_RETURN` output into `tx_outs` before calling `calculate_weight_vbytes`, but that function reconstructs the transaction from `inputs`/`payments`/`change` only — it never sees the data output. The result is the same class of bug as the Nouns `Auction._computeTotalRewards` issue: a total (fee/weight) computed over one decomposition of components while the actual object contains an additional component, so the strict invariant the caller relies on (`weight <= MAX_STANDARD_TX_WEIGHT`, `fee >= fee_per_vbyte * actual_vbytes`) silently fails.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-202`, the `OP_RETURN` output is appended to `tx_outs`. Immediately after, at line 204:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (lines 62-127) builds a throwaway `Transaction` whose `output` list is derived solely from `payments` plus the optional `change` script — the `data` output is absent. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) undercharges by the serialized size of the `OP_RETURN` output (up to ~90 bytes for the allowed 80 bytes of data).
2. The `TooLowFee` check at line 211 and the `NotEnoughFunds` check at line 215 validate a fee the final transaction does not actually pay per-vbyte.
3. When change is added, `fee_with_change` (line 227) and `weight = weight_with_change` (line 231) are likewise computed without the data output, so the change amount is overpaid and the weight check is still wrong.
4. The `MAX_STANDARD_TX_WEIGHT` guard at line 241 is evaluated against an undercounted weight, so a transaction whose real weight exceeds the standardness limit is accepted and signed.

This mirrors H-2: the "total" (weight/fee charged) is derived from a subset of the parts that make up the real artifact, so the sum-of-parts (actual serialized outputs) no longer equals the whole that was validated.

### Impact Explanation
Two concrete failure modes, both reachable purely from caller-supplied `data`, `payments`, and input selection:

- **Permanent DoS / bricked spend**: if `payments` already push the transaction near `MAX_STANDARD_TX_WEIGHT`, the uncounted `OP_RETURN` output pushes the real transaction over the limit. The returned `SignableTransaction` produces a signed transaction no relay policy will accept — it can never be broadcast, so the inputs it consumes are effectively frozen (analogous to the auction settlement brick).
- **Under-priced fee**: the transaction pays `fee_per_vbyte * vbytes_underestimated`, i.e., an effective feerate strictly below the caller-specified rate and potentially below `DEFAULT_MIN_RELAY_TX_FEE`, causing relay rejection despite `TooLowFee` passing.

### Likelihood Explanation
Any caller invoking `SignableTransaction::new` with `data: Some(_)` (a public, unprivileged input — the API explicitly supports up to 80 bytes, checked at line 171) triggers the undercount unconditionally. The weight-limit escape additionally requires many payments/large scripts, which are also caller-controlled. Crafting inputs to land just under the checked weight while exceeding it in reality is straightforward, exactly like the "bid ending in 19" engineering in H-2.

### Recommendation
Include the data output in the weight/vbytes estimate — e.g., extend `calculate_weight_vbytes` to accept the `data` length (or build the output list from `tx_outs` directly) so every component of the final transaction is counted. Alternatively, compute `weight`/`vbytes` once from the fully assembled `tx_outs` after both the `OP_RETURN` and change outputs are finalized, so the validated whole and the signed artifact are identical by construction.

### Proof of Concept
Construct a `SignableTransaction` with:

- one input `ReceivedOutput`,
- `payments` chosen so the computed `vbytes` yields `weight` just below `MAX_STANDARD_TX_WEIGHT` (or so the fee rate margin is < ~90 bytes worth of sats),
- `data = Some(vec![0; 80])`.

`SignableTransaction::new` returns `Ok(...)`, `needed_fee()` reflects `fee_per_vbyte * vbytes` excluding the ~90-byte `OP_RETURN` output, while `tx.output` contains it. The signed transaction's real vsize exceeds the estimate; its effective feerate is below `fee_per_vbyte` (and can fall below `DEFAULT_MIN_RELAY_TX_FEE`), or its weight exceeds `MAX_STANDARD_TX_WEIGHT`, making it non-standard and unbroadcastable — funds committed to it are unspendable until an entirely new plan is constructed and re-signed.
