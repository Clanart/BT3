### Title
Overfill ceiling is computed but not enforced in FXFiller — the resulting fill can exceed the intended safety bound - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The Hyperbridge reference Intent-Gateway filler (`simplex`) computes an "overfill ceiling" meant to bound how much output a solver will ever pay relative to a user's requested amount, mirroring the AMO pattern of gating an action on a pre-check without validating that the actual executed amount lands within the intended bound. In `FXFiller.calculateProfitability`, the ceiling is computed and compared, but the enforcement (clamp) has been explicitly removed, leaving only a warning log. The filler proceeds to fill the order using the unclamped `policyMaxOutput`, so any pricing error — stale cache, a bug in curve math, or a manipulated/thin on-chain venue (e.g. Uniswap V4) feeding `resolveLegRates` — flows straight through to an on-chain `fillOrder()` call that transfers solver funds to the order beneficiary.

The comment on this code block states plainly that "the clamp is DISABLED" and that this "removes the per-leg loss bound that previously protected against a bug / stale cache / manipulated venue price." `policyMaxOutput` is set to the raw, unclamped value (`rawPolicyMaxOutput`) regardless of whether it breaches `overfillCeiling`; the only consequence of exceeding the ceiling is a `logger.warn` call. This value then flows into `finalOutputAmount`, which is what the filler actually commits on-chain via `fillOrder()`.

The pre-check (comparing against `overfillCeiling`) exists and is evaluated, exactly analogous to the AMO's `preRebalanceCheck()` — but just as `preRebalanceCheck()` never re-validates that the resulting xETH percentage lands back inside the thresholds after the mint/burn, `calculateProfitability` never re-validates that the resulting `finalOutputAmount` stays inside `overfillCeiling` after pricing. The safety invariant is checked but not enforced.

The remaining defense, `priceGuard`/`checkPriceGuard`, is optional per-chain configuration (`this.priceGuard?.get(chain)`) that only applies to venue-priced pairs where an operator has configured a `reference` price and `maxDeviationBps` for that chain; it returns `true` (pass) whenever no guard is configured for the chain in question. Offline-curve-priced pairs (no `[vault.uniswapV4]` position for that chain) have no price guard at all, so a stale/incorrect curve config or a curve computation bug has nothing standing between it and an unclamped, on-chain fund transfer.

### Impact Explanation
This directly matches the bug class in the seed report: a bound is computed and checked but the corrupted/out-of-range value is used anyway instead of being clamped or rejected. Here the corrupted value is `policyMaxOutput`/`finalOutputAmount`, which is executed as the solver's on-chain output in `fillOrder()` — an ERC20/native transfer to the order's beneficiary. Because IntentGateway settlement releases escrow proportionally to solver-provided output [2](#0-1) , an unclamped overfill causes real, uncapped loss of solver funds beyond the amount the solver's own policy intended to commit, triggered by any pricing anomaly (stale cache, curve misconfiguration, or a manipulated/thin venue quote on chains without a configured `priceGuard`).

### Likelihood Explanation
No privileged, colluding, or malicious relayer/operator role is required: any user placing an order that lands on a mispriced leg (stale internal cache, curve edge case, or an on-chain venue quote from a thin/manipulable pool on an unguarded chain) can trigger the unclamped path purely by the normal, permissionless `fillOrder` flow. The code comments confirm this was previously guarded and the removal was deliberate but incomplete — the halt/tracking subsystem (`recordOrderOutcome`) is left in place but "dormant (always recorded as a clean, unclamped outcome)" [3](#0-2) , meaning the intended circuit-breaker (`maxConsecutiveClamps` halt) can never fire either.

### Recommendation
Re-enable the clamp: when `rawPolicyMaxOutput > overfillCeiling`, cap `policyMaxOutput` to `overfillCeiling` before it is used to size `finalOutputAmount`, and feed the clamped/unclamped outcome back into `recordOrderOutcome` so the `maxConsecutiveClamps` halt logic functions again. If intentional overfilling is desired for competitiveness on some markets, gate it behind an explicit, per-pair opt-in rather than a blanket, silent removal of the bound.

### Proof of Concept
1. Configure `FXFiller` with a pair that has no `[vault.uniswapV4]` price-guard entry for the destination chain (or one venue-priced leg where `priceGuard` is unset for that chain).
2. Cause `resolveLegRates`/the pair's curve (or venue quote) to return a rate far above the pair's intended book price — e.g. via a stale cached price, a curve misconfiguration, or (for venue-priced legs on the ungoverned chain) a thin-pool price manipulation.
3. Place an order whose requested `output.amount` is small; the mispriced rate causes `computeLegPolicyOutput` to return a `rawPolicyMaxOutput` far exceeding `overfillCeiling = output.amount * (10000 + maxOverfillBps) / 10000`.
4. Observe in `calculateProfitability` (`sdk/packages/simplex/src/strategies/fx.ts:600-617`) that only a `logger.warn` fires — `policyMaxOutput` remains `rawPolicyMaxOutput`, unclamped.
5. `finalOutputAmount` (bounded only by wallet/funding-venue balance, not by `overfillCeiling`) is used to build and submit the `fillOrder()` UserOperation, transferring the unclamped, oversized output on-chain to the order beneficiary at the solver's expense.
