### Title
Frozen RPC router's HTTP server has no timeout on reading the request body, letting a stalled client park a goroutine indefinitely - ([File: cmd/frozen-rpc-router/main.go])

### Summary
`cmd/frozen-rpc-router` is a public-facing JSON-RPC proxy that fronts the live/frozen EVM RPC nodes. Its `http.Server` sets `ReadHeaderTimeout` but never sets `ReadTimeout`, so once request headers are accepted there is no deadline on reading the rest of the body. The handler then blocks in `io.ReadAll` on the request body with only a size cap, not a time cap, allowing a client that trickles bytes (or stops sending entirely) after a valid `Content-Length` header to park the connection-handling goroutine forever — the same bug class as the reported inets `httpd` issue, where a request that passes header parsing but stalls mid-body is never reclaimed.

### Finding Description
The router's HTTP server is constructed with: [1](#0-0) 

Only `ReadHeaderTimeout` (10s) and `WriteTimeout`/`IdleTimeout` are set; `ReadTimeout` — the field that Go's `net/http` documents as bounding "the entire request, including the body" — is left at its zero value, meaning no deadline governs body reads once headers succeed. There is also no `MaxOpenConnections`-style cap on this server, unlike the equivalent EVM RPC surface.

The handler then reads the body synchronously with only a size limit: [2](#0-1) 

`http.MaxBytesReader` bounds how many bytes can be read, but places no bound on how long the read may take. `io.ReadAll(request.Body)` blocks until the full (size-capped) body arrives or the connection errors — which, with `ReadTimeout` unset, can be indefinite for a client that sends a large declared `Content-Length` and then stalls or trickles data below any enforced rate.

This directly mirrors the CVE root cause: valid headers are accepted, the header-timeout is satisfied, but the subsequent per-request body-read has no overall deadline, so the server-side worker (here, a Go per-connection goroutine, not an Erlang process, but architecturally equivalent) is parked waiting on a stalled peer.

By contrast, the main EVM JSON-RPC surface (`evmrpc/`) explicitly hardens exactly this class of bug with `BodyReadIdleTimeout`, incremental budget charging, and `MaxOpenConnections`: [3](#0-2) [4](#0-3) 

The frozen-rpc-router does not reuse any of these protections.

### Impact Explanation
Each stalled connection ties up one server goroutine indefinitely inside `io.ReadAll`. Because the server has no `ReadTimeout` and no connection/goroutine cap, an unauthenticated remote client can open many such connections (bounded only by OS file-descriptor/ephemeral-port limits) and send well-formed request headers with a plausible `Content-Length`, then withhold or trickle the remaining body. This exhausts goroutines and file descriptors on the router process at negligible attacker bandwidth cost, denying legitimate clients access to the proxy that fronts the live/frozen EVM RPC nodes — a public-RPC-surface availability failure consistent with the accepted "crash/hang of default-configuration RPC nodes" impact class.

### Likelihood Explanation
The path is reachable by any unauthenticated network client that can open a TCP connection to the frozen-rpc-router's listen address and issue a normal HTTP POST with a `Content-Length` header, requiring no authentication, no valid JSON-RPC payload, and no interaction with chain state. The only friction is that the router must be deployed and reachable (it is a purpose-built public proxy component in this repo), and the attack is trivially automatable and repeatable across many connections.

### Recommendation
Set an explicit `ReadTimeout` (and ideally a maximum-connections limiter, mirroring `evmrpc/config.Config.MaxOpenConnections`) on the `http.Server` in `cmd/frozen-rpc-router/main.go`, or wrap `request.Body` in `router.go`'s `ServeHTTP` with a per-chunk idle-read guard (analogous to `evmrpc`'s `budgetBody`/`BodyReadIdleTimeout`) so that stalled body reads are aborted with an HTTP 408 and release the goroutine instead of blocking indefinitely.

### Proof of Concept
1. Start `frozen-rpc-router` with default flags/config (only `ReadHeaderTimeout` is set on the server).
2. From an attacker-controlled client, open a raw TCP connection to the router's listen address and send:
   ```
   POST / HTTP/1.1
   Host: <router>
   Content-Length: 10000000
   Content-Type: application/json

   ```
   (valid headers, terminated by `\r\n\r\n`), then send zero or a few bytes of body and stop.
3. Because `ReadHeaderTimeout` was already satisfied by the header write, and `ReadTimeout` is unset, the server's per-connection goroutine blocks in `io.ReadAll(request.Body)` in `router.go` `ServeHTTP` indefinitely (or until the OS TCP keepalive/OS-level timeout, which is far longer and not controlled by the application).
4. Repeat step 2 across many parallel connections up to the process's file-descriptor limit; each parks a goroutine and holds a socket, exhausting router capacity and denying legitimate JSON-RPC clients service.

```go
func (r *router) ServeHTTP(w http.ResponseWriter, request *http.Request) {
	if request.Method != http.MethodPost {
		r.liveProxy.ServeHTTP(w, request)
		return
	}

	request.Body = http.MaxBytesReader(w, request.Body, r.maxRequestBodySize)
	body, err := io.ReadAll(request.Body)
	if err != nil {
		var maxBytesErr *http.MaxBytesError
		if errors.As(err, &maxBytesErr) {
			http.Error(w, "request body too large", http.StatusRequestEntityTooLarge)
			return
		}
		http.Error(w, "failed to read request body", http.StatusBadRequest)
		return
	}
```
