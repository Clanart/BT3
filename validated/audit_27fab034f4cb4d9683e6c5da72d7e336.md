### Title
Line-index diff selection is not re-validated against a freshly-fetched diff before staging, allowing silent corruption of partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
The Watchpug report describes a derived value (`ibRatio`) that is not kept in sync with a mutated base value (`totalSupply`), so a value computed against stale state is later used to release funds, permanently freezing the difference. The Desktop analog is `WorkingDirectoryFileChange.selection`, a `DiffSelection` whose semantics are *pure line-index offsets into a specific diff snapshot* (`hunk.unifiedDiffStart + index`, see `app/src/models/diff/diff-selection.ts:41-136`). This selection is built while the user views one diff, but `applyPatchToIndex` re-fetches a brand new diff from disk immediately before staging and reapplies the old index-based selection to it without validating that the indices still refer to the same content.

### Finding Description
`applyPatchToIndex` in `app/src/lib/git/apply.ts:60` calls `getWorkingDirectoryDiff(repository, file)` to obtain a *fresh* diff right before formatting the patch, and then calls `formatPatch(file, diff)`, which walks `diff.hunks` and tests `file.selection.isSelected(absoluteIndex)` [1](#0-0) [2](#0-1) . The `DiffSelection` object, however, carries no reference to the diff it was created against — it is just a `Set<number>` of "diverging" line indices relative to whatever diff was on screen when the user made their selection [3](#0-2) [4](#0-3) .

Desktop does have one place where it re-validates a selection against a newly-loaded diff — `updateChangesWorkingDirectoryDiff` recomputes `selectableLines` and calls `withSelectableLines` when the diff shown in the Changes view is refreshed [5](#0-4) . But this reconciliation only happens for the diff *displayed in the UI*; it is not performed a second time on the diff `applyPatchToIndex` re-fetches at staging time. The code comment even acknowledges the general fragility of this design: *"The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines."* [6](#0-5) 

If the working-tree file's content changes between the moment the diff was rendered/selected in the UI and the moment `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` runs, the absolute line indices in the freshly-fetched diff no longer correspond to the same lines the user selected. Because `formatPatch` blindly indexes into the new hunks with the old `divergingLines` set, the resulting patch can select/deselect the wrong additions or deletions, or silently include unrelated changes, without any error — analogous to `ibRatio` staying at 1e18 while `totalSupply` moved out from under it.

Triggers for the file changing between selection and staging include: a `.gitattributes` `filter=lfs` smudge rewrite during a background fetch/checkout of the same branch, an external editor autosave, a build tool, or another git client concurrently modifying the working tree — none of these require the user to take any unnatural step, and the repository content (`.gitattributes`, LFS tracking) can be fully attacker-controlled by whoever authored the cloned/fetched repo.

### Impact Explanation
The user believes they are committing exactly the lines they selected in the diff viewer. If the underlying diff shifts before `applyPatchToIndex` runs, the actual committed/pushed content can silently diverge from what was shown and approved — corrupting what the user commits, matching the "silent corruption of what the user commits or pushes" impact category. Because `git apply --cached --unidiff-zero` will happily apply the patch as long as it's structurally valid against the current file, there is no crash or visible warning; the user will only discover the mismatch after the commit (or push) has already happened.

### Likelihood Explanation
This requires a real race between (a) the diff snapshot used to build the line selection and (b) the diff re-fetched at staging time, and it is bounded by how a repository's `.gitattributes`/LFS configuration or a concurrent tool rewrites tracked files. This is a narrower window than the confirmed WatchPug bug, and I could not find in-repo evidence of an automatic trigger (e.g., a background LFS smudge running mid-selection) that reliably produces the race without any coincidental timing, so likelihood should be treated as low/uncertain until validated with a live repro.

### Recommendation
`applyPatchToIndex`/`formatPatch` should not silently reuse a `DiffSelection` computed from one diff against a different, later-fetched diff. Either (a) pass the exact diff object that was used to build the selection all the way through to staging (instead of re-fetching), or (b) re-run the same `withSelectableLines` reconciliation performed in `updateChangesWorkingDirectoryDiff` against the freshly-fetched diff immediately before formatting the patch, and abort/re-prompt the user if the reconciled selection differs materially from what was shown.

### Proof of Concept
Not independently verified against a live build; this is a code-path analysis based on:
- `app/src/lib/git/apply.ts:52-84` (fresh diff fetched at stage time, old selection reused)
- `app/src/lib/patch-formatter.ts:132-221` (`isSelected(absoluteIndex)` indexing)
- `app/src/models/diff/diff-selection.ts:41-332` (index-based selection with no diff identity)
- `app/src/lib/stores/app-store.ts:3466-3497` (comment acknowledging the diff can change dramatically, reconciliation only applied to UI-displayed diff)

Given the effort constraints of this pass, I was not able to construct or run an end-to-end reproduction (e.g., using an LFS smudge filter or a concurrent writer) to confirm the race is exploitable in practice; a Devin session with terminal access would be needed to build a fixture repository and time the race to confirm this produces an actually-wrong committed patch.
