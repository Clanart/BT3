### Title
Silent Merge-Conflict Corruption via Independent Marker-Parsing Divergence Between Extraction and Reassembly - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
GitHub Desktop's Copilot-assisted conflict resolution extracts conflict hunks from a file using one hand-written marker scanner (`extractConflictHunks`) to build the model prompt, then later re-scans the *same file content from scratch* using a second, independently implemented marker scanner (`reassembleResolvedFile`) to splice the model's per-hunk resolutions back in — matched purely by array order/index, with no cross-check that both scanners agreed on the number or location of conflict blocks. A conflicted file whose content (attacker-controlled via a merged/fetched branch) causes the two regex-based scanners to disagree on hunk boundaries will cause resolutions to be spliced into the wrong location in the file, silently corrupting the result that the user then commits and pushes.

### Finding Description
`extractConflictHunks` in [1](#0-0)  walks the raw file text using `oursMarker`, `baseMarker`, `separatorMarker`, and `theirsMarker` regexes to identify each conflict block, and this determines both how many hunks are sent to the model and the "Conflict N of M" ordering shown in the prompt built by `formatConflictContextForPrompt` ( [2](#0-1) ).

Later, `reassembleResolvedFile` in `copilot-conflict-resolution.ts` re-walks the **original raw file content again**, using its own separately declared regex constants (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`), to find conflict marker blocks and splice in the model's `hunkResolutions[]` **by order only** (`hunkIndex` incremented per detected block), not by any shared identifier: [3](#0-2) 

`reassembleResolutions` calls `reassembleResolvedFile(ctx.rawContent, raw.hunks)` directly, with no assertion that the number of blocks `reassembleResolvedFile` will discover matches `ctx.hunks.length` (the count `extractConflictHunks` found and that the model was told about): [4](#0-3) 

Because these are two separately maintained parsers over the same conflict-marker grammar, any input that makes them disagree on hunk boundaries (e.g. literal content on the "ours"/"theirs" side that itself contains a line matching one of the marker regexes, such as a 7-character `=======` divider used as a code comment, or a malformed/unterminated marker block that one scanner treats as "skip" and the other treats as "regular content") causes the resolved-content-to-block mapping to shift. The final content is written straight to disk and staged without any diffing or verification against the original hunks: [5](#0-4) 

### Impact Explanation
This falls squarely into the "silent corruption of what the user commits or pushes" impact category. The attacker only needs to control the content of a branch, PR, or file that the victim merges/rebases/cherry-picks (an ordinary git operation, not requiring local/physical access or credentials). If the two hunk-boundary scanners diverge, Copilot's resolved content for one conflict hunk is silently written into the wrong location in the file — potentially reintroducing conflict markers, dropping intended changes, or splicing unrelated code — while the app reports success and the user proceeds to commit and push the corrupted merge, unaware of the mismatch.

### Likelihood Explanation
Exploitability depends on constructing file content that reliably makes `extractConflictHunks`'s incremental marker-collection loops (which do not treat an intervening `oursMarker`/`theirsMarker` occurring while collecting "theirs" content specially) diverge from `reassembleResolvedFile`'s independent well-formedness check (which requires a `=======` before a `>>>>>>>`). I was not able to fully verify, within the given tool budget, whether `parseCopilotConflictResolution` enforces a hunk-count equality check between the model's raw response and the original context (`ctx.hunks.length`) before calling `reassembleResolvedFile`; if such a check exists elsewhere and rejects mismatched counts, this reduces (but does not eliminate — a count-preserving boundary shift is still possible) the exploitability. This should be verified in the full `parseCopilotConflictResolution` implementation, which the available index snippets did not fully surface.

### Recommendation
Have `extractConflictHunks` and `reassembleResolvedFile` share a single marker-parsing implementation (or have reassembly consume the exact hunk boundaries computed at extraction time, e.g. by returning marker byte/line offsets from `extractConflictHunks` and passing them through the model response identity, rather than re-deriving them from a second regex walk). Additionally, before writing resolved content to disk, verify that the number of hunk blocks found during reassembly exactly matches `ctx.hunks.length` from the original extraction, and abort/report the file as unresolved (falling back to manual resolution) on any mismatch.

### Proof of Concept
Concrete reproduction requires constructing a conflicted file where one side's literal content contains a line matching `^={7}$` (e.g., a source file using a `=======` divider comment) positioned such that `extractConflictHunks`'s "collect theirs content until closing marker" loop and `reassembleResolvedFile`'s independent lookahead-based well-formedness check parse a different number/position of conflict blocks for the same raw text, then observing that the model's ordered `hunkResolutions[]` gets spliced against the wrong block in `reassembleResolvedFile`. Verifying an exact failing input would require running both parsers side-by-side against crafted fixtures, which was not completed within the available tool budget — this PoC should be constructed and confirmed by a follow-up engineer with test-execution access.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
