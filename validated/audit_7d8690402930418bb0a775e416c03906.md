### Title
Line-index-based partial-commit/partial-discard selection can silently apply to the wrong diff lines when the working tree changes between selection and staging - (File: `app/src/lib/patch-formatter.ts`)

### Summary
GitHub Desktop's partial-commit ("stage selected lines") feature stores which lines a user wants staged as a `Set` of **positional line indices** (`DiffSelection.divergingLines`), not as content-addressed lines. When the commit is actually staged, Desktop re-fetches a **fresh** diff from disk and re-applies the old index-based selection to it without validating that the line at each index still contains the content the user actually selected. This is the same bug class as the Babylon report: a value (the "selection") captured at one point in time (against one version of the diff) is applied later using the "current" underlying data (a newer diff) instead of the historical data it was computed against.

### Finding Description
The selection object is a positional bitmap over diff line indices: [1](#0-0) [2](#0-1) 

When staging a partial file, Desktop fetches the diff **again** at commit time and blindly reuses the file's existing `selection`: [3](#0-2) 

`formatPatch` then walks the hunks of that freshly-fetched diff and decides what to include purely by absolute line index, with no comparison of the line's actual text against what was shown when the user made the selection: [4](#0-3) 

Separately, when a background working-directory refresh occurs, Desktop explicitly acknowledges that the diff content backing a selection may have changed, but only prunes indices that are no longer "includeable" — it does not verify that surviving indices still refer to the same line content: [5](#0-4) 

And when the working-directory status is refreshed, the old `DiffSelection` object is carried forward onto the new file object regardless of whether the diff itself changed underneath it: [6](#0-5) 

Put together: a user reviews a diff, selects specific lines to include in a commit (or to discard), and clicks "Commit"/"Discard". Between that moment and the actual `git apply --cached` (staging) or discard operation, if the on-disk content changes — for example due to a repository-controlled `.gitattributes` clean/smudge/filter driver, a build tool, editor autosave, or another background process writing to the file — the hunks and line offsets in the diff fetched inside `applyPatchToIndex`/`formatPatch` can differ from the diff the user actually reviewed. Because selection is purely index-based, the same numeric indices are silently re-applied to different line content, so lines the user never intended to commit (or discard) can be committed/discarded instead, and vice versa.

### Impact Explanation
This falls into "silent corruption of what the user commits or pushes." A user could believe they are staging only a reviewed subset of changes, but Desktop can silently commit or discard different lines than what was shown, without any error or warning. Because commit content and history become part of the permanent Git record (and can be pushed), this can leak or alter code the user never intended to record, or discard changes the user wanted to keep, without any indication to the user that a mismatch occurred.

### Likelihood Explanation
This requires the working tree content to change between the diff the user visually selected lines from and the moment Desktop performs the `git apply --cached`/discard-and-restage sequence. Repository-controlled Git filter drivers (`clean`/`smudge` in `.gitattributes`) are a realistic attacker-controlled vector because they execute automatically during `git apply`/`add`/checkout on files from a cloned/fetched repository, and their behavior can be non-deterministic or content-dependent. Purely local race conditions (e.g. editor autosave) are also possible but are not attacker controlled. Overall likelihood is moderate-to-low: it requires a timing window and either an attacker-supplied filter driver in the repo or an external process touching the file mid-flow; there's no direct single-click trigger demonstrated here.

### Recommendation
Make `DiffSelection` content-aware instead of purely index-based: when re-applying a selection to a newly-fetched diff, validate that the line text at each selected/deselected index matches what was originally captured (or better, snapshot and diff against the exact diff instance used to build the selection, refusing to stage/discard if the diff has changed underneath). At minimum, before calling `applyPatchToIndex`/`formatPatch`, re-diff and compare hash/content of the hunks against what was rendered in the UI, and prompt the user to re-review if they differ, rather than silently proceeding with stale index-based selection state.

### Proof of Concept
1. Clone a malicious repository containing a `.gitattributes` entry with a `clean` filter for `*.txt` that rewrites file content non-deterministically (e.g., appends a timestamp or reorders lines) on `git add`.
2. Modify `notes.txt` in the working directory; open Desktop's Changes view, and use partial-line selection to select only specific lines to commit (leaving others unselected).
3. Before clicking "Commit," have the filter driver's underlying trigger fire (e.g., another tool touches the file, or the clean filter is invoked non-deterministically causing a different byte-for-byte diff on the next `git status`/`add`).
4. Click "Commit." Desktop's `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff and `formatPatch` (`app/src/lib/patch-formatter.ts:143-171`) re-applies the old index-based `file.selection` to the new hunk content.
5. Inspect the resulting commit (`git show`) — verify it does not correspond to the lines that were visually highlighted/selected as "included" in the Desktop UI at the time of clicking Commit.

    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {

        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
