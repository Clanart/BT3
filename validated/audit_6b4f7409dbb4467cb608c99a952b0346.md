### Title
Unhandled `IndexError` in `is_clvm_canonical()` on a truncated CLVM buffer causes a spend-triggered mempool validation crash - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_clvm_canonical()` and its helper `is_atom_canonical()` parse raw, attacker-controlled CLVM bytes (`puzzle_reveal` / `solution`) using unchecked `bytes` indexing while walking a length-prefix state machine. This mirrors the CVE-2024-34250 bug class: a bytecode/serialization loader that advances an offset/branch cursor based on attacker-supplied length fields without validating the cursor stays within the buffer, leading to an out-of-bounds read during "loading" (here, during canonical-form validation of a spend bundle at mempool admission).

### Finding Description
`is_atom_canonical()` reads `clvm_buffer[offset]` to determine the atom's length-prefix encoding, then loops `prefix_len` times, incrementing `offset` and reading `clvm_buffer[offset]` again to build `atom_len`, with no bounds check that `offset` stays under `len(clvm_buffer)`: [1](#0-0) 

`is_clvm_canonical()` drives this loop over the whole buffer, and on each token also indexes `clvm_buffer[offset]` and adds `atom_len` (a value entirely controlled by the submitted bytes) to `offset` without checking it is still inside the buffer before the next iteration reads `clvm_buffer[offset]` again: [2](#0-1) 

Because Python `bytes` objects raise `IndexError` on out-of-range access instead of returning garbage/corrupting memory, this is not itself a memory-corruption bug, but it is the direct analog of the reachable-crash aspect of `wasm_loader_check_br`: a length/branch value taken from untrusted input is used to advance a cursor with no upper-bound validation against the buffer size, and the subsequent read at the invalid position throws.

This function is invoked directly on attacker-supplied spend bundle data during mempool admission, inside `validate_spend_bundle()`: [3](#0-2) 

which is called from `add_spend_bundle()` while the blockchain lock is held: [4](#0-3) 

A crafted `puzzle_reveal` or `solution` byte string — e.g., an atom whose length-prefix header claims `prefix_len` bytes of encoded length but the buffer ends before those bytes are present, or whose computed `atom_len`/pair nesting pushes `offset` past `len(clvm_buffer)` right before the next loop iteration's `clvm_buffer[offset]` read — triggers an unhandled `IndexError` deep inside mempool validation, rather than being turned into a clean `Err.INVALID_COIN_SOLUTION` rejection.

### Impact Explanation
`is_clvm_canonical()` is called synchronously and unguarded by any `try/except` inside `validate_spend_bundle()`. An `IndexError` raised here is not one of the two paths the surrounding code anticipates (`Err` returned, or `ValidationError`/`ValueError` from `pre_validate_spendbundle`'s CLVM/signature step). This is a spend-triggered exception in transaction-processing logic that runs under the blockchain lock while handling every submitted spend bundle, matching the allowed "spend-triggered transaction-processing halt" impact class: a single crafted spend bundle from any unprivileged submitter can throw an uncaught exception in the mempool's coin-solution-canonicality check instead of being cleanly rejected.

### Likelihood Explanation
The precondition is a specific truncated/malformed byte sequence for `puzzle_reveal` or `solution` where the high-order bits of a leading byte indicate a 1–5 byte length-prefix continuation (`0xC0`–`0xFE` range) but the buffer ends mid-prefix or the derived `atom_len` overruns the buffer exactly on the next iteration's index read. This is fully attacker-controlled: any wallet/RPC caller can submit a `SpendBundle` with such a `CoinSpend.puzzle_reveal`/`solution`, so the trigger condition is directly reachable without any special privilege, though it requires carefully constructing the byte pattern that survives the earlier CLVM parse steps up to the point of the out-of-bounds index.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (verify `offset < len(clvm_buffer)` before reading the prefix-continuation bytes, and verify the computed `1 + prefix_len + atom_len` does not exceed the remaining buffer), and add an analogous bounds check in `is_clvm_canonical()`'s main loop before indexing `clvm_buffer[offset]`. On any bounds violation, return "not canonical" (`False`) rather than letting an `IndexError` propagate, and ensure `validate_spend_bundle()`/`pre_validate_spendbundle()` treat malformed canonicality input as `Err.INVALID_COIN_SOLUTION` uniformly.

### Proof of Concept
Construct a `CoinSpend` whose `puzzle_reveal` bytes are, e.g., `bytes([0xC0])` (a byte announcing a 5-bit+8-bit length prefix, i.e. `prefix_len = 1`) with no following byte. Calling `is_atom_canonical(b"\xc0", 0)` executes `offset += 1` then attempts `clvm_buffer[1]`, which is out of range and raises `IndexError` instead of returning a clean not-canonical result. Submitting a `SpendBundle` containing such a `puzzle_reveal` (padded appropriately to pass earlier CLVM/cost validation up to the canonicality check) drives execution into `validate_spend_bundle()` → `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` → `is_atom_canonical()`, producing the unhandled `IndexError` during mempool admission of that spend bundle: [3](#0-2)

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
