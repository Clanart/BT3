### Title
Ed448 torsion rejection always succeeds, enabling forged Schnorr proofs and ECDH low-order key leakage - ([File: crypto/ed448/src/point.rs](crypto/ed448/src/point.rs))

### Summary
`Point::is_torsion_free` computes `(-P) + P`, which is identity for every valid curve point. Consequently, `Point::from_bytes` accepts non-identity low-order Ed448 points even though the crate advertises a `PrimeGroup` and explicitly claims to reject torsion. Untrusted inputs reach this parser through `Ed448::read_G`, `SchnorrSignature::read`, `EncryptedMessage::read`, `EncryptionKeyMessage::read`, `DLEqProof`, and PedPoP messages.

### Finding Description
The subgroup check is implemented as:

```rust
((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
```

Because `Scalar::ZERO - Scalar::ONE` is `-1`, the expression is always `-P + P = 0`. The returned choice therefore always indicates that the point is torsion-free. `GroupEncoding::from_bytes` combines this result with curve validity and negative-zero checks, so any validly encoded torsion point is accepted as a `PrimeGroup` element. [1](#0-0) 

This violates the `Ciphersuite::G: PrimeGroup` assumption used throughout Serai. Generic scalar parsing is canonical, and generic point parsing relies on `GroupEncoding::from_bytes`, so the missing subgroup check is the root cause. [2](#0-1) 

The resulting Schnorr verifier checks `R + cA - sG == 0` directly, without cofactor handling. [3](#0-2)  For an order-2 public key `A = T`, a forged signature with `s = 0` and `R = T` verifies whenever the scalar challenge is odd:

```text
R + cA - sG = T + cT = (1 + c)T = 0   when c ≡ 1 mod 2
```

PedPoP exposes this to attacker-controlled bytes: `EncryptedMessage::read` accepts `key` through `C::read_G`, and `Encryption::decrypt` verifies a Schnorr proof of possession under that attacker-selected key. [4](#0-3) [5](#0-4)  The PoP challenge binds the nonce, key, sender, and ciphertext, but the attacker can vary ciphertext bytes until the challenge has the needed parity. [6](#0-5) 

After accepting such a message, `decrypt` computes `ecdh = msg.key * enc_key` and returns it inside an `EncryptionKeyProof`. If `msg.key` has order 2, the revealed ECDH point is identity or `T` according to the victim encryption scalar’s parity; an order-4 point similarly leaks the scalar modulo 4. [7](#0-6) [8](#0-7) 

### Impact Explanation
An unauthenticated sender can create an `EncryptedMessage` whose ephemeral key is a non-identity torsion point and whose Schnorr PoP verifies without knowing a discrete logarithm. This defeats the PoP protection described by the code and lets the sender force the victim’s ECDH output onto a small set of values. When the victim returns or publishes the `EncryptionKeyProof` for blame, the proof’s `key` field reveals the victim’s static encryption scalar modulo the torsion order.

More generally, every API assuming `Ed448::G` is a prime-order group can accept points outside that subgroup. This is an incorrect verifier/parser invariant and produces forged proof acceptance under attacker-selected keys.

### Likelihood Explanation
The bypass is deterministic in the parser and the forged signature condition only requires controlling a challenge modulo the small torsion order. For PedPoP, the ciphertext is attacker-controlled and transcript-bound, so the attacker can iterate ciphertext bytes until the challenge satisfies the required low-order congruence. The attack requires Ed448 usage; the crate and FROST bindings mark Ed448 as available but not recommended/unaudited. [9](#0-8) [10](#0-9) 

### Recommendation
Implement a real prime-subgroup membership check for Ed448 points. Do not test with scalar `-1`; either:

- multiply by the subgroup order `l` and require identity, using an implementation capable of representing `l`; or
- verify that the point equals its cofactor-cleared representative, e.g. `P == (4P) * 4⁻¹ mod l`.

Add vectors covering the order-2 point `(0, -1)`, non-identity order-4 points, mixed torsion/subgroup points, identity, negative zero, and non-canonical encodings. `Curve::read_G` rejects identity but does not reject other torsion points, so subgroup validation must remain in `Point::from_bytes`. [11](#0-10) 

### Proof of Concept
Mathematical PoC for the order-2 point:

```text
T = Ed448 point (x = 0, y = -1), so 2T = 0 and T != 0.
A = T
R = T
s = 0

Schnorr verification:
R + cA - sG
= T + cT
= (c + 1)T
= 0 whenever c is odd
```

For PedPoP:

1. Encode `T` as an Ed448 compressed Edwards point with `x = 0`, `y = -1`, and sign bit `0`.
2. Place that encoding in `EncryptedMessage.key`.
3. Set `pop.s = 0` and `pop.R = T`.
4. Vary the attacker-controlled ciphertext/message bytes until `pop_challenge(...)` returns an odd scalar.
5. `EncryptedMessage::read` accepts `T`, and `pop.verify(T, challenge)` succeeds.
6. `Encryption::decrypt` computes `enc_key * T` and returns it in `EncryptionKeyProof`, exposing whether the private encryption scalar is even or odd.

The same construction generalizes to an order-4 torsion point by testing the four possible `R = kT` values and accepting when `c ≡ -k mod 4`, leaking the victim scalar modulo 4 through the returned ECDH point.

  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt

  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
