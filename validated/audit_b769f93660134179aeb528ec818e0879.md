### Title
Open Redirect via unvalidated `return_to` parameter in OAuth callback redirect - ([File: app/controllers/shopify_app/callback_controller.rb])

### Summary
The `redirect_to_app` method in `CallbackController` redirects the freshly-authenticated merchant's browser to `session[:return_to]` without validating that it is same-origin with the embedded app or the app's `root_url`. An attacker can plant an absolute external URL as `return_to` (e.g. by getting the victim to click a link to the app's `/login` route with `return_to=https://evil.example.com`), which `SessionsController#copy_return_to_param_to_session` stores into `session[:return_to]` and which survives through the OAuth flow into the post-callback redirect.

### Finding Description
`SessionsController#copy_return_to_param_to_session` stores `params[:return_to]` into `session[:return_to]` using `RedirectSafely.make_safe(params[:return_to], "/")`. [1](#0-0) 
`RedirectSafely.make_safe` only guards against malformed/dangerous schemes (e.g. `javascript:`); it does not enforce that the URL is same-origin with the app, so a well-formed absolute URL like `https://evil.example.com` passes through unchanged.

After OAuth completes, `CallbackController#redirect_to_app` pulls this value back out of the session and checks only whether it is a "fully formed URL" (has a scheme and host), not whether it belongs to a trusted origin: [2](#0-1) 

The only additional safety check, `deduced_phishing_attack?`, validates the **`host`** query parameter (the base64-encoded shop admin host) against `ShopifyApp::Utils.sanitize_shop_domain`, not the `return_to` value itself: [3](#0-2) 

So as long as `host` is a legitimate/valid embedded host, `deduced_phishing_attack?` returns `false` and the attacker-controlled `return_to` is used verbatim as the redirect target, with `allow_other_host: true` explicitly permitting cross-origin redirects.

Exploit flow: attacker crafts `GET /login?shop=<victim-shop>.myshopify.com&host=<valid-host>&return_to=https://evil.example.com` and gets the victim (the shop's merchant/admin) to open it. `copy_return_to_param_to_session` stores the attacker URL in `session[:return_to]`. The victim proceeds through the normal OAuth authorize/callback flow (this part isn't attacker-controlled and doesn't require any secret). On successful callback, `redirect_to_app` redirects the victim's browser — which now carries the fresh Shopify session cookie/App Bridge session token context — to `evil.example.com`.

### Impact Explanation
This is an open redirect immediately following a successful OAuth authentication, landing the merchant on an attacker-controlled page in the context of just having completed login. Depending on how the attacker page is built (e.g., mimicking Shopify or the app's UI, or using `document.referrer`/postMessage tricks with the embedded App Bridge context), this enables phishing of the freshly authenticated merchant and can be leveraged to harvest follow-up credentials or trick the merchant into further actions. This matches Shopify's "Open Redirect" impact class — typically a lower/medium severity issue on its own, but elevated here because it fires right after authentication completes with `allow_other_host: true` explicitly bypassing Rails' built-in open-redirect protection.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs to get the victim to click/open a URL to the app's own `/login` endpoint with a crafted `return_to` and valid-looking `host`/`shop` parameters (no secrets, tokens, or shop insider access required). This is fully reachable from an anonymous/unprivileged position — the attacker only crafts a link; the victim's own real Shopify OAuth flow does the rest. The `deduced_phishing_attack?` guard does not inspect `return_to` at all, so it never blocks this path.

### Recommendation
In `CallbackController#redirect_to_app` (and/or `fully_formed_url?`), validate that a fully-formed `return_to` URL's host matches the app's configured embedded-app domain / `root_url` host (or the shop's `myshopify.com`/admin host) before redirecting, and fall back to `ShopifyApp.configuration.root_url` otherwise — mirroring the same-origin intent of `deduced_phishing_attack?` but applied to `return_to`, not just `host`. Alternatively, restrict `return_to` to relative paths only (strip any `return_to` that parses with a scheme/host) rather than allowing `allow_other_host: true` for arbitrary absolute URLs.

### Proof of Concept
```ruby
test "redirect_to_app redirects to attacker-controlled external return_to" do
  session[:return_to] = "https://evil.example.com"
  # simulate successful OAuth callback for an embedded app with valid host param
  get :callback, params: { shop: "shop.myshopify.com", host: valid_base64_host, code: "code", timestamp: Time.now.to_i, hmac: valid_hmac, state: valid_state }

  assert_redirected_to "https://evil.example.com"
  # Expected (fixed) behavior: redirect should be restricted to the embedded app / root_url domain,
  # e.g. assert_redirected_to ShopifyApp.configuration.root_url
end
```
This demonstrates that with a valid callback (real preconditions satisfied — valid `host`, HMAC, state, cookie), the only attacker-controlled input `session[:return_to]` fully determines the post-auth redirect target, with no origin check performed. [4](#0-3)

    def redirect_to_app
      if ShopifyAPI::Context.embedded?
        return_to = session.delete(:return_to)
        redirect_to = if fully_formed_url?(return_to)
          return_to
        else
          "#{decoded_host}#{return_to}"
        end

        redirect_to = ShopifyApp.configuration.root_url if deduced_phishing_attack?
        redirect_to(redirect_to, allow_other_host: true)
      else
        redirect_to(return_address)
      end
    end

    def fully_formed_url?(return_to)
      uri = Addressable::URI.parse(return_to)
      uri.present? && uri.scheme.present? && uri.host.present?
    end
