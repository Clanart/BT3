## Title
Missing minting/underflow guard before `uint64()` cast in mempool fee calculation causes unhandled exception on spend bundles that create more value than they consume - (File: chia/full_node/mempool_manager.py)

### Summary
`MempoolManager.validate_spend_bundle` computes the transaction fee as `uint64(removal_amount - addition_amount)` without first checking that `removal_amount >= addition_amount`. If `addition_amount > removal_amount` (i.e., the submitted spend bundle's `CREATE_COIN` conditions sum to more than the coins it spends — an inflation/minting attempt), the Python subtraction produces a negative `int`, and casting a negative value to the Rust-backed `uint64` type raises an unhandled `ValueError` ("does not fit into uint64") instead of returning a controlled `Err`.

### Finding Description
In `chia/full_node/mempool_manager.py`, `validate_spend_bundle` accumulates `addition_amount` from each spend's `CREATE_COIN` conditions and `removal_amount` from the coin records being spent, then computes: [1](#0-0) 

There is no prior check equivalent to the `MINTING_COIN` guard used during full block validation. Compare with `chia/consensus/block_body_validation.py`, which explicitly validates `removed >= added` **before** subtracting: [2](#0-1) 

The `uint64` constructor used in `mempool_manager.py` is confirmed to raise `ValueError` for negative inputs, as demonstrated by the equivalent helper `compute_block_fee` and its test: [3](#0-2) [4](#0-3) 

Because `mempool_manager.py`'s `validate_spend_bundle` never checks `removal_amount < addition_amount` before the cast (unlike the block-validation code path, and unlike `estimate_fees()`/`Offer.fees()` which intentionally return a signed `int` without casting), a spend bundle with `CREATE_COIN` conditions totaling more than the spent coin amounts will raise an uncaught `ValueError` inside `validate_spend_bundle` rather than returning `Err.MINTING_COIN` or similar. This is the same root-cause pattern as the reported Solidity bug: performing subtraction in a context that cannot represent negative values, and casting/converting after the subtraction instead of validating sign before it.

### Impact Explanation
An unhandled exception raised deep inside `validate_spend_bundle` (called from `add_spend_bundle`, which is invoked from the full node's transaction-intake path) means a single crafted, unsigned or partially-signed spend bundle submitted to the mempool can turn a should-be-rejected transaction (`Err.MINTING_COIN`) into an unhandled Python exception. Depending on how far up the call chain the exception propagates uncaught, this can disrupt mempool transaction admission processing for that request — a spend-triggered transaction-processing halt — rather than being cleanly rejected the way the analogous block-body validation path handles it.

### Likelihood Explanation
Likelihood is high for triggering the code path: any unprivileged party can submit a spend bundle via RPC/mempool with `CREATE_COIN` conditions summing to more than the coins it spends; CLVM execution and cost accounting do not by themselves prevent constructing such conditions before this fee computation runs. The only uncertainty is exactly how far the exception propagates and whether some outer try/except in the full-node request-handling layer (not fully inspected here) ultimately intercepts it — this could not be fully confirmed by the available index within remaining budget.

### Recommendation
Mirror the pattern already used in `chia/consensus/block_body_validation.py`: check `if removal_amount < addition_amount: return Err.MINTING_COIN, None, []` (or equivalent) before computing `fees = uint64(removal_amount - addition_amount)` in `chia/full_node/mempool_manager.py`, so that an inflation attempt is turned into a controlled rejection instead of an unhandled `ValueError`.

### Proof of Concept
1. Construct a `CoinSpend` for a coin with amount `X`.
2. Craft the puzzle/solution so that CLVM execution returns `SpendBundleConditions` containing one or more `CREATE_COIN` conditions whose total amount is `X + 1` (or more) — i.e., minting extra value.
3. Submit this as a `SpendBundle` via the normal mempool intake path (e.g., `respond_transaction` / RPC `push_tx`).
4. In `validate_spend_bundle`, `addition_amount` (`X+1`) exceeds `removal_amount` (`X`), so `fees = uint64(removal_amount - addition_amount)` evaluates `uint64(-1)`, raising `ValueError: -1 does not fit into uint64` (as demonstrated by the equivalent path in `chia/_tests/core/consensus/test_block_creation.py:21-23`) instead of returning `Err.MINTING_COIN`. def compute_block_fee(additions: Sequence[Coin], removals: Sequence[Coin]) -> uint64:
```python
    removal_amount = 0
    addition_amount = 0
    for coin in removals:
        removal_amount += coin.amount
    for coin in additions:
        addition_amount += coin.amount
    return uint64(removal_amount - addition_amount)
```
