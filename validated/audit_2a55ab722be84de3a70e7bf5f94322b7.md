### Title
Hand-rolled YAML frontmatter parser is case-sensitive and comment-unaware, causing `action: block` rules to silently degrade to `warn` - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter` (plugins/hookify/core/config_loader.py, lines 87-195) is a hand-rolled key/value parser that preserves the exact case of keys and does not strip inline comments or extraneous trailing text from values. `Rule.from_dict` then does `frontmatter.get('action', 'warn')` and `rule_engine.py` compares with a strict `rule.action == 'block'` equality check, so any near-miss spelling of the `action` key or value (e.g. `Action: block`, or `action: block  # dangerous`) silently falls through to the `warn` default instead of blocking, with no error, warning, or fail-closed behavior surfaced to the user.

### Finding Description
`load_rule_file` (plugins/hookify/core/config_loader.py:244-274) reads a `.claude/hookify.*.local.md` file, calls `extract_frontmatter` to parse the YAML-like block, and passes the resulting dict into `Rule.from_dict` (line 44-84). The top-level key parsing at line 136-152 does `key = key.strip()` without any case normalization, so a rule file with `Action: block` (capitalized) produces `frontmatter['Action'] = 'block'`, not `frontmatter['action']`. `Rule.from_dict` line 81 (`action=frontmatter.get('action', 'warn')`) then silently falls back to `'warn'`, because the lookup key doesn't match.

Similarly, the parser does not strip inline comments: `value = value.strip('"').strip("'")` at line 147 does nothing to remove trailing text like `# blocks the operation`, so `action: block # blocks dangerous rm` becomes `action = "block # blocks dangerous rm"`. `rule_engine.py` line 55 does a strict equality check `if rule.action == 'block':`; anything other than the exact string `'block'` routes the rule into `warning_rules` instead of `blocking_rules` (lines 55-58), and `evaluate_rules` (rule_engine.py:35-94) only produces a `permissionDecision: deny` / `decision: block` response for rules in `blocking_rules`. A `warn`-only rule always returns just a `systemMessage` and allows the tool call to proceed (lines 86-91).

Crucially, none of this is surfaced: `load_rule_file` only raises/logs on I/O or type errors (lines 263-274) and `load_rules` swallows `ValueError/KeyError/AttributeError/TypeError` per-file (lines 228-239) — a misspelled/miscased `action` key is not an error at all, it's valid-looking data that silently resolves to the default. There is no schema validation, no unknown-key warning, and no fail-closed behavior anywhere in the loader.

### Impact Explanation
A rule file that a human reviewer reads and believes enforces `action: block` (e.g. blocking `rm -rf`, `dd`, credential exfiltration commands, etc., per the documented examples in plugins/hookify/README.md) can, due to a subtle casing/formatting mistake, actually only warn. Since the `PreToolUse` hook (plugins/hookify/hooks/pretooluse.py) always exits 0 and only blocks via the `hookSpecificOutput.permissionDecision: deny` path, a downgraded-to-warn rule allows Claude Code to execute the dangerous Bash/file operation the reviewer believed was blocked. This is a false sense of a deny-by-default guard — the security control silently no-ops while looking intact in the repo/PR diff.

### Likelihood Explanation
This requires only that a plausible-looking rule file (e.g., committed to a repo's `.claude/` directory, or generated by hand rather than by the `/hookify` command template) contain a subtle key-casing typo or trailing comment — a very easy, low-effort mistake to introduce or plant, since the parser gives no feedback that anything is wrong. The `/hookify` command's own generated templates always use lowercase `action:` with no comments, so this specific bug would not manifest from the tool's own auto-generated files, but any manually edited or externally supplied rule file is at risk, and there's no validation step anywhere in the load path to catch it.

### Recommendation
Harden `extract_frontmatter`/`Rule.from_dict` to fail closed rather than silently defaulting:
- Normalize/validate frontmatter keys against an explicit allow-list of recognized keys (case-insensitively matching `action`, `enabled`, `event`, etc.) and raise/reject unknown top-level keys rather than silently ignoring them.
- Strip inline comments (`#`) from scalar values before assignment, matching real YAML behavior, or reject values containing unexpected trailing content.
- Validate `action` against an explicit enum (`{'warn', 'block'}`); if the value does not exactly match, raise an error (fail closed) instead of defaulting to `'warn'`, and surface that error prominently (not just to stderr, which is easily missed) — e.g. via `print(..., file=sys.stderr)` plus refusing to silently continue and treating the malformed rule as `block` instead of `warn` when in doubt, or better, replacing the hand-rolled parser with a real YAML parser (`yaml.safe_load`) that enforces standard tokenization rules.

### Proof of Concept
Fuzz/unit test plan for `plugins/hookify/core/config_loader.py`:
```python
import pytest
from hookify.core.config_loader import extract_frontmatter, Rule

NEAR_MISS_CASES = [
    "Action: block",       # wrong case key
    "ACTION: block",
    " action: block",      # leading whitespace -> non-zero indent, dropped silently
    "action: block  # never allow this",  # inline comment not stripped
    "action:block",        # (should still parse correctly - control case)
]

@pytest.mark.parametrize("action_line", NEAR_MISS_CASES)
def test_action_block_not_silently_downgraded(action_line):
    content = f"""---
name: test-rule
enabled: true
event: bash
pattern: rm\\s+-rf
{action_line}
---

Dangerous rm detected.
"""
    fm, msg = extract_frontmatter(content)
    rule = Rule.from_dict(fm, msg)

    # Invariant: a file containing a recognizable "block" intent must
    # either resolve to action == 'block' or the loader must raise/reject.
    assert rule.action == 'block', (
        f"Rule with {action_line!r} silently degraded to "
        f"action={rule.action!r} instead of failing closed or blocking"
    )
```
Expected result today: the test fails for the `Action:`, `ACTION:`, leading-whitespace, and inline-comment cases — `rule.action` resolves to `"warn"` (or, for the comment case, a non-`"block"` string) with no exception raised and no indication to the caller that the rule wasn't understood, confirming the deny-means-deny invariant is violated by silent default-fallback. def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
