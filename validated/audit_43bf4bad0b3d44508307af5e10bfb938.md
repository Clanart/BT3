### Title
Panic (out-of-bounds slice read) on untrusted message length in `SchnorrkelHram::hram` - ([File: crypto/schnorrkel/src/lib.rs](crypto/schnorrkel/src/lib.rs))

### Summary
Analogous to the iccDEV heap out-of-bounds read in `CIccPcsXform::pushXYZConvert()` — where an unchecked length field drives a read past the end of a heap buffer — `SchnorrkelHram::hram` trusts a length prefix embedded in attacker-influenceable message bytes and slices the message buffer at offsets derived from it, without any bounds check. Any input to `SignMachine::sign`/`SignatureMachine::complete` shorter than 4 bytes, or carrying a `ctx_len` field larger than the remaining buffer, panics the signer/verifier.

### Finding Description
The FROST Schnorrkel algorithm computes its challenge in `hram` by treating the first 4 bytes of the message `m` as a little-endian `u32` context length, then slicing `m[4 .. 4 + ctx_len]`:

```rust
// crypto/schnorrkel/src/lib.rs:41-46
fn hram(R: &RistrettoPoint, A: &RistrettoPoint, m: &[u8]) -> Scalar {
  let ctx_len =
    usize::try_from(u32::from_le_bytes(m[0 .. 4].try_into().expect("malformed message")))
      .unwrap();

  let mut t = signing_context(&m[4 .. (4 + ctx_len)]).bytes(&m[(4 + ctx_len) ..]);
```

Two unchecked reads exist:

1. `m[0 .. 4]` — if `m.len() < 4`, `.try_into().expect("malformed message")` panics.
2. `m[4 .. (4 + ctx_len)]` — `ctx_len` is fully attacker-controlled (it is simply `u32::from_le_bytes(m[0..4])`). Any `ctx_len > m.len() - 4` produces an out-of-bounds slice panic; `4 + ctx_len` can also overflow `usize` on 32-bit when `ctx_len` is near `u32::MAX` → wrapping arithmetic panic in debug / wrong slice in release.

`hram` is reached from `Schnorr::sign_share` (`crypto/frost/src/algorithm.rs:208`) with `msg` being exactly the byte string passed by the coordinator to `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:283-398`). In a FROST deployment the message to be signed is supplied by an external/coordinating party and is not length-validated anywhere in the FROST state machine — `read_preprocess`/`read_share` parse commitments and scalars, but `msg` flows straight into `hram`. Note `Schnorrkel::sign_share` does prepend the algorithm's own `context` length (`crypto/schnorrkel/src/lib.rs:122-127`), which makes `m` start with the honest `context` — but the honest `context` is a `&'static [u8]` whose length is itself encoded; the panic path via `m[0..4]` is only avoided because of that prefix, while `&m[(4 + ctx_len) ..]` still slices at an attacker-influenced boundary determined by `context`, and any downstream user-facing `msg` content sits at `m[4+ctx_len..]` where the nested `signing_context(...).bytes(...)` call parses it further. More directly, `Schnorrkel::verify` re-parses `self.msg` through `signing_context(self.context).bytes(...)` — and `EthereumHram`/other HRAM implementors are free to be added; the class issue is that `hram` assumes a length-prefixed layout on bytes it does not validate.

The crash-only variant is unambiguous: a coordinator (or any party that can influence the agreed message) that causes `sign`/`complete` to run over a malformed `m` aborts the process — an availability failure matching the CVSS A:H impact of the reference CVE.

### Impact Explanation
Every participant running the Schnorrkel FROST algorithm panics inside `hram` when fed a short or length-lying message. Since `panic` is not caught, this aborts the signing session and potentially the host process (availability loss across all honest signers simultaneously, since they all evaluate `hram` on the same `msg`). In Rust the invalid access is a bounds-check panic rather than a silent heap read, so memory disclosure (the C:L half of the CVE) does not apply — the honest severity is crash/DoS, consistent with Medium under the reference scoring.

### Likelihood Explanation
Reachable by an unprivileged party that can influence the message being threshold-signed (a coordinator proposing the signable payload, or any peer able to drive `sign(commitments, msg)`/`complete` with arbitrary bytes). No collusion, no leaked keys, and no malformed curves are needed — only a byte string whose first 4 bytes encode a `ctx_len` larger than the buffer, or a buffer shorter than 4 bytes in any caller path that does not prepend the context. The guard `expect("malformed message")` documents that malformed input was anticipated but is handled by panicking rather than returning an error.

### Recommendation
Validate the buffer before slicing in `SchnorrkelHram::hram` (`crypto/schnorrkel/src/lib.rs:41-46`):

```rust
let len_bytes = m.get(0 .. 4).ok_or(/* malformed */)?;
let ctx_len = usize::try_from(u32::from_le_bytes(len_bytes.try_into().unwrap()))
  .map_err(|_| /* malformed */)?;
let ctx = m.get(4 .. 4 + ctx_len).ok_or(/* malformed */)?;
let rest = m.get(4 + ctx_len ..).unwrap_or(&[]);
```

Since `Hram::hram` returns `C::F` (no `Result`), either change the `Hram` trait to return `Option<C::F>`/`io::Result<C::F>` and propagate a `FrostError::InvalidSigningSet`-style error from `Schnorr::sign_share`, or at minimum replace the panicking slice with a checked `get` that hashes a canonical error encoding instead of indexing — and reject `msg` inputs shorter than the required framing at the `sign` entry point.

### Proof of Concept
```rust
// Requires: modular-frost-schnorrkel, threshold keys for Ristretto with t <= n signers.
use frost_schnorrkel::frost::{algorithm::Schnorr, sign::AlgorithmMachine, PreprocessMachine};
use frost_schnorrkel::Schnorrkel;
use ciphersuite::Ristretto;

// After threshold keys exist and each participant has a SignMachine:
// `msg` is supplied by the coordinator. Passing fewer than 4 bytes:
let msg: &[u8] = b"";           // or b"\xff\xff\xff\xff..." with ctx_len > buffer
let (_machine, _share) = sign_machine.sign(preprocesses, msg).unwrap();
// -> panics at crypto/schnorrkel/src/lib.rs:43 with "malformed message"
//    (m[0..4].try_into().expect) or out-of-bounds slice at line 46.
```

The same panic is reachable in `Schnorrkel::verify`/`verify_share` during `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:465-489`), since `hram` is re-evaluated on the stored `self.msg` when validating the aggregated signature.
