### Title
`ThresholdKeys::read` accepts a secret share inconsistent with its verification shares — the only consistency check that exists never actually binds the secret to the participant's public share - (File: crypto/dkg/src/lib.rs)

### Summary
The Snowflake bug class is a permission/ownership check that nominally exists but always succeeds, letting an attacker plant a malicious object that the code then trusts. Serai's `ThresholdKeys::new` — the sole validation gate for `ThresholdKeys::read` (untrusted bytes) — checks the count of verification shares, participant index bounds, canonical encodings, and interpolation-mode applicability, but never verifies that `C::generator() * secret_share == verification_shares[i]`. A serialized `ThresholdKeys` blob whose `secret_share` field is unrelated to participant `i`'s verification share deserializes successfully and is treated as fully valid.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) parses `t`, `n`, `i`, the interpolation variant, the `secret_share` scalar, and `n` verification-share points, then calls `ThresholdKeys::new`. `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) performs the following validation:

- `verification_shares.len() == n` and every key `<= n` (lines 355-365)
- `Constant` interpolation requires `t == n` (lines 367-374)
- `ThresholdParams::new` enforces `t <= n`, `i <= n`, non-zero (lines 166-179)

It then derives `group_key` purely from the supplied verification shares (line 377-378) and returns `Ok`. At no point is `self.core.secret_share` checked against `self.core.verification_shares[&params.i()]`. The code even acknowledges this class of corruption exists: `AlgorithmSignatureMachine::complete` in crypto/frost/src/sign.rs:491-494 notes that "the only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" — confirming the deserialization layer is expected to reject such input but does not.

The analogous "ownership check that always succeeds": like the Snowflake driver checking a cache file was "accessible only by the user" without verifying ownership, `ThresholdKeys::new` checks that `i` is a valid participant index without checking that the claimed secret share actually belongs to participant `i`.

### Impact Explanation
An attacker who can feed bytes to `ThresholdKeys::read` (listed in-scope as an untrusted-bytes sink) produces a `ThresholdKeys` that passes all validation while carrying an arbitrary/mismatched secret share. Consequences:

- When used in FROST signing (`view()` → `sign` → `complete`), the victim emits shares that fail `verify_share`, and `AlgorithmSignatureMachine::complete` attributes `FrostError::InvalidShare` to the victim's own participant index — the honest holder of the corrupted blob is blamed as faulty, enabling mis-attribution of fault and denial of signing service.
- `recover_key` (crypto/dkg/recovery/src/lib.rs:80) catches inconsistency only at the final `generator()*res == group_key` check, failing recovery after the shares are already aggregated.
- `view()` computes `secret_share` and the group key from attacker-chosen verification shares with an unrelated secret, so any consumer trusting `group_key()` sees an attacker-controlled group key paired with a share that can never sign for it.

### Likelihood Explanation
Requires an attacker to control serialized `ThresholdKeys` bytes presented to a deserializing consumer (e.g., imported/backup key material or any path where serialized keys cross a trust boundary). It does not enable forging signatures or recovering shares — impact is integrity/availability plus false blame attribution, which matches the medium severity of the source advisory.

### Recommendation
In `ThresholdKeys::new`, reject keys where `C::generator() * secret_share != verification_shares[&params.i()]` (accounting for the fact that `scalar`/`offset` are post-hoc and not serialized). This binds the private component to the public commitment set, restoring the invariant the deserialization validation claims to enforce.

### Proof of Concept
```rust
// In-scope sink: untrusted bytes -> ThresholdKeys::read
// Build a serialization where secret_share does not match verification_shares[i]
let mut buf = vec![];
// valid ThresholdKeys for params t=2,n=3,i=1, then overwrite the secret_share
// field with an arbitrary scalar (e.g. F::ONE + 1) while keeping the original
// verification shares.
let keys: ThresholdKeys<Ed25519> = ThresholdKeys::read(&mut buf.as_slice()).unwrap();
// Succeeds: no check that generator()*secret_share == verification_shares[&i]
assert_eq!(keys.params().i(), Participant::new(1).unwrap());
// keys.group_key() is attacker-controlled via the supplied verification shares.
// When the holder signs, view(i=1..) yields shares that fail verify_share, and
// AlgorithmSignatureMachine::complete returns InvalidShare(i) blaming the victim.
```
