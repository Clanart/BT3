### Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw`/SweepDust allows silent transfer failure and fund loss - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron `IntentGatewayV2` diverges from the canonical EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`) by moving off OpenZeppelin's `SafeERC20.safeTransfer` and instead issuing raw low-level calls to the `transfer` selector, checking only that the call did not revert — never validating the ABI-decoded boolean return value.

### Finding Description
In `withdraw()` and the `SweepDust` branch of `onAccept`, ERC20 payouts are executed as: [1](#0-0) [2](#0-1) 

Only `success` (whether the external call reverted at the EVM level) is checked; the actual `bool` returned by the token's `transfer` function is discarded. Standard-conforming-but-non-reverting tokens that return `false` on failure (e.g. due to blacklist, paused state, or custom transfer restrictions) will make `success == true` even though no tokens moved. The escrow accounting is unaware of this: `_filled[body.commitment] = beneficiary` is set and `_orders[body.commitment][token] -= amount` is decremented unconditionally right after the call: [3](#0-2) 

By contrast, the reference EVM path (`IntentsBase._withdraw`) uses `SafeERC20.safeTransfer`, which reverts the whole transaction on a `false` return, preserving escrow integrity: [4](#0-3) 

This is a direct structural analog of the M-04 report's "unchecked return value on value transfer" class — the low-level call succeeds at the EVM level but the actual asset movement can silently fail, and the code proceeds as if it succeeded.

### Impact Explanation
Once the token transfer silently fails, the order commitment is marked filled/refunded (`_filled[commitment] = beneficiary`) and the escrow ledger entry is zeroed out, but the beneficiary never received the tokens. The tokens remain trapped in the `IntentGatewayV2` contract with no accounting path to reclaim them (the order is already "filled", so `UnknownOrder()` will trip on any retry), resulting in permanent loss of escrowed user/solver funds — matching the bounty's "stealing or loss of funds" impact category.

### Likelihood Explanation
This path is reached through the normal, unprivileged intent-settlement flow: any order routed through the Tron `IntentGatewayV2` whose escrowed token is a non-reverting-on-failure ERC20 (a real-world category including several deployed tokens) will trigger this on `withdraw()` calls originating from `onAccept`/`onGetResponse`, both externally triggered by legitimate host message delivery — no malicious relayer, prover, or admin action is required, only a token whose `transfer` can return `false`.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`, `SweepDust` branch, and the fee-token payout) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the already-correct implementation in `IntentsBase._withdraw`. If `SafeERC20` cannot be used due to Tron-specific tooling constraints, explicitly decode and require the returned boolean (`success && (returndata.length == 0 || abi.decode(returndata, (bool)))`) before mutating `_orders`/`_filled` state.

### Proof of Concept
1. A solver escrows an ERC20 token whose `transfer()` returns `false` on failure instead of reverting (e.g. the token owner blacklists the `IntentGatewayV2` contract or the beneficiary after order placement).
2. The order is filled/timed-out and the host delivers a `WithdrawalRequest` via `onAccept`/`onGetResponse`, invoking `withdraw()`.
3. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the low-level call itself doesn't revert) even though the token internally returned `false` and moved no funds — see [5](#0-4) .
4. `_orders[commitment][token] -= amount` executes and `_filled[commitment] = beneficiary` is already set, permanently closing out the order.
5. The beneficiary never receives tokens, and the escrowed balance is now unrecoverable — the contract silently retains funds with no ledger entry pointing to them.
