### Title
Unbounded attacker-controlled allocation in `ThresholdKeys::read` via serialized `n` parameter - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` deserializes the participant count `n` directly from untrusted bytes and immediately sizes heap allocations and iteration counts from it — before any `ThresholdParams` validation — allowing an attacker supplying crafted bytes to a `ThresholdKeys::read` / `read_F` / `read_G` path to force repeated multi-megabyte allocations from a tiny input, analogous to the unbounded `orig_value` allocation in QEMU's `v9fs_list_xattr` (CVE-2017-8086).

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::<C>::read` reads three raw `u16`s (`t`, `n`, `i`) from the reader (lines 591–602). `n` is then used before `ThresholdParams::new(t, n, i)` is ever validated:

- `Interpolation::Constant` branch: `Vec::with_capacity(usize::from(n))` is allocated and `n` scalars are read (lines 607–613).
- The verification-shares loop iterates `1 ..= n` calling `C::read_G` per element into a `HashMap` (lines 620–623).
- Only at the end is `ThresholdParams::new(t, n, i)` invoked to check consistency (lines 625–631).

The same pattern appears in `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs`, lines 78–88), which reads a `u32` count and pushes `C::read_G` results in a loop, and in `SignData::read`/`Transaction::read` style loops where each element count is attacker-chosen. The `with_capacity(usize::from(n))` call is the purest analog: a 2-byte field instantly reserves `n × size_of::<F>()` (≈2 MB for a 32-byte scalar at `n = 65535`), before a single element is read or any bound is checked against the remaining input.

### Impact Explanation
An unprivileged party who can cause serialized `ThresholdKeys` bytes to be deserialized (e.g., submitting key material, blame/share payloads, or any message reaching `ThresholdKeys::read`) controls `n` up to 65535. Each malicious call allocates ~2 MB for the `Constant` interpolation vector plus drives a 65535-iteration `HashMap`/`read_G` loop for as long as input bytes are supplied. Repeated submission yields sustained CPU and memory-amplification DoS (a few dozen input bytes → megabytes of allocation), matching the "local attacker causes memory-consumption DoS" shape of CVE-2017-8086. The allocation is not bounded by actual input length at reservation time, unlike the chunked read used in `Call::read` (`networks/ethereum/src/machine.rs`, lines 51–60), which shows the codebase is aware of this exact DoS class elsewhere.

### Likelihood Explanation
Reachability requires an attacker-controlled byte stream reaching `ThresholdKeys::read` — plausible wherever serialized keys or recovery material are accepted — but the per-call amplification is bounded (~2 MB + `n` point decodings proportional to bytes actually provided), keeping this Medium rather than High.

### Recommendation
Validate `t`, `n`, `i` via `ThresholdParams::new` immediately after reading them, cap `n` before allocating, and drop `Vec::with_capacity(n)`/loop bounds driven by unvalidated input — or bound allocations by the remaining reader length (as `Call::read` does with its 1 KB chunked read).

### Proof of Concept
Serialize a header for a valid curve `C::ID`, then `t = 1`, `n = 0xFFFF`, `i = 1`, interpolation tag `0` (Constant), followed by minimal bytes. `ThresholdKeys::<C>::read` executes `Vec::with_capacity(65535)` (~2 MB reserved) and begins a 65535-iteration `read_F`/`read_G` loop before `ThresholdParams` validation ever runs — each request costing orders of magnitude more memory than the input size.
