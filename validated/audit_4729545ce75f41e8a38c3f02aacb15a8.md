## Title
Sybil attack via sqrt-based boost factor accumulation dilutes legitimate referrer's boosted yield share - (File: rewards/ReferralStorage.sol)

### Summary
`ReferralStorage.updateTotalFactor()` computes each referrer's `factor` as `sqrt(vlMGPLockedAmount)` and simply sums these factors into `totalBoostFactor`, which is then used as the denominator in `_calBoosted()` to compute a referrer's share of `BoostPoint`. Because square root is a concave function, the sum of many small `sqrt()` contributions from Sybil accounts is strictly greater than the `sqrt()` of the same total capital locked by one account, so an attacker can inflate `totalBoostFactor` far out of proportion to actual capital committed, diluting a legitimate high-locking referrer's boosted share of unclaimed yield.

### Finding Description
`_calBoosted()` returns `BoostPoint * userInfos[_account].factor / totalBoostFactor` [1](#0-0) , and `updateTotalFactor()` sets `userInfo.factor = DSMath.sqrt(vlMGPLockedAmount)` before adding it into the shared `totalBoostFactor` accumulator [2](#0-1) .

`updateTotalFactor` is reachable unprivileged: it's called from `VLMGP._lock()` on every `lock()`/`lockFor()` call, and from `startUnlock()`, both public/external functions with no admin gating [3](#0-2) [4](#0-3) . `lock()` has no minimum-amount check [5](#0-4) , and `registerCode()` is permissionless with no cost besides picking an unused `bytes32` code [6](#0-5) .

Because `sqrt` is concave, `sqrt(a) + sqrt(b) > sqrt(a+b)` for positive `a, b`. An attacker who splits a fixed amount of MGP across N sybil accounts (each registering a code and locking even a minimal, e.g. 1-wei, amount) contributes `N * sqrt(amount/N) = sqrt(N) * sqrt(amount)` to `totalBoostFactor` — growing with `sqrt(N)` — while a single legitimate referrer locking the same total amount only contributes `sqrt(amount)`. Locking a token amount as small as 1 wei still yields `factor = sqrt(1) = 1` per Babylonian-method implementation [7](#0-6) , meaning the attacker can inflate `totalBoostFactor` arbitrarily by creating many synthetic accounts each locking negligible MGP and registering a code, at near-zero capital cost (only gas plus dust MGP per account). This directly and disproportionately shrinks the legitimate high-locker's `_calBoosted()` share, since their `factor` numerator stays fixed while the shared denominator `totalBoostFactor` is inflated. Since `trigger()` uses `_calBoosted(_referer)` to compute `refererAmount`/`refereeAmount` splits of real MGP reward claims [8](#0-7) , this dilution translates into real economic loss of unclaimed referral yield for the legitimate referrer, redirected proportionally toward inflating the denominator (i.e., effectively wasted/undistributed, and the attacker's own sybil accounts also gain a nonzero unearned boosted share for negligible capital).

No existing modifier or check prevents this: `updateTotalFactor` only requires `msg.sender == vlMGP` (satisfied trivially by any account calling `lock`), and there is no minimum lock size, no per-account registration cooldown, and no Sybil-resistance mechanism (e.g., KYC, one-code-per-verified-identity, or linear rather than concave factor weighting).

### Impact Explanation
This causes theft/dilution of unclaimed yield: the `BoostPoint` allocation intended to reward referrers proportionally to their locked MGP is redistributed disproportionately toward accounts that fragment capital, directly reducing the boosted-yield share (and thus claimable `rewardAmount` via `claimReward()`) owed to a legitimate high-value referrer. This matches the "theft or permanent freezing of unclaimed yield" Immunefi impact class.

### Likelihood Explanation
The attack requires no privileged role — any EOA/contract can call `registerCode()` and `lock()`/`lockFor()` repeatedly. Capital cost per sybil account can be as low as 1 wei of MGP (still yielding `factor = 1` due to integer sqrt rounding), so the attacker's cost scales with the number of accounts (gas + dust MGP) rather than meaningful locked capital, making this cheap, repeatable, and highly feasible for anyone wanting to dilute or manipulate the referral boost pool.

### Recommendation
Redesign the boost-factor aggregation so it isn't Sybil-manipulable by concavity: e.g., weight by locked MGP linearly instead of `sqrt`, require identity/code registration to be tied 1:1 with a single vlMGP position enforced at the protocol level, impose a meaningful minimum lock amount for factor eligibility, or track `totalBoostFactor` as `sqrt(sum of all locked amounts)` computed from a global total rather than a sum of individual `sqrt()` values, so it reflects true proportional stake rather than account count.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `ReferralStorage`, `MasterMagpie`/mocks as needed; set `BoostPoint` and `totalBoostFactor` state via normal flows.
2. Legitimate referrer `Alice` registers a code and locks `X` MGP via `lock()`, triggering `updateTotalFactor(Alice)`; record `_calBoosted(Alice)` = `BoostPoint * sqrt(X) / totalBoostFactor`.
3. Attacker deploys/controls `N` synthetic EOAs; each registers a unique code via `registerCode()` and locks a minimal amount `x = 1` wei of MGP via `lock()`, each triggering `updateTotalFactor(sybil_i)`, adding `sqrt(1) = 1` to `totalBoostFactor` per account.
4. Assert `totalBoostFactor` after Sybil registration `>> sqrt(X)` for sufficiently large `N`, and that `_calBoosted(Alice)` after Sybil registration is significantly smaller than before (disproportionate to the negligible capital `N` wei added by the attacker relative to Alice's `X` MGP).
5. Optionally simulate a `trigger()` call on a referee of Alice before/after the Sybil registration and assert `refererAmount` drops disproportionately, demonstrating concrete yield dilution.

    function updateTotalFactor(address _account) external override _onlyVlMGP {
        UserInfo storage userInfo = userInfos[_account];
        if (userInfo.myCode == bytes32(0)) return; // user did not activate referral feature
        
        totalBoostFactor -= userInfo.factor;
        uint256 vlMGPLockedAmoubnt = IVLMGP(vlMGP).getUserTotalLocked(_account);
        userInfo.factor = DSMath.sqrt(vlMGPLockedAmoubnt);

        totalBoostFactor += userInfo.factor;
    }
