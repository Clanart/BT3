### Title
Malicious git host can spoof a `WWW-Authenticate: realm="GitHub"` header to force GitHub Desktop's credential helper to trust it as a GitHub Enterprise endpoint - (`File: app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Malt finding is really about a **trust decision that is derived from data the untrusted counterparty controls, and is never re-validated/reset before being acted on again**. In GitHub Desktop's credential-helper trampoline, `getEndpointKind()` decides whether an arbitrary git remote should be treated as a GitHub/GitHub-Enterprise endpoint (and therefore be handed the real GitHub sign-in flow) by inspecting the `wwwauth[]` fields of the credential request. Those fields are populated straight from the `WWW-Authenticate` HTTP header returned by the remote git server itself, i.e. by the attacker.

### Finding Description
`getEndpointKind` is used by `getCredential`, `storeCredential`, and `eraseCredential` to branch between "GitHub-managed" and "generic" credential handling: [1](#0-0) 

Note lines 153-165 in particular: if none of the hostname-based checks (`isGist`, `isDotCom`, `isGHE`) match, and no existing `Account` is already stored for that origin, the code falls back to trusting the `wwwauth[...]` value supplied in the credential request:

```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
```

These `wwwauth[]` values come from Git's credential-helper protocol, which in turn populates them from the actual `WWW-Authenticate` response header sent by whatever server the connecting remote points to [2](#0-1) . A remote server fully controlled by an attacker (an evil clone/fetch target, or a MITM proxy sitting in front of any HTTPS remote) can therefore return `WWW-Authenticate: Basic realm="GitHub"` for a completely unrelated host and have Desktop classify that host as `'enterprise'`.

Once classified as `'enterprise'`, `getCredential` checks whether any existing `Account` already matches that (attacker-controlled) API endpoint; if not, it calls the real GitHub sign-in UI, bound to the attacker's endpoint: [3](#0-2) 

This is the direct analog of the reported bug: a downstream decision (in Malt, the size of an ERC20 approval; here, whether to treat a host as a trusted GitHub endpoint and hand it Desktop's real sign-in machinery) is made from a value that the counterparty supplies and that is never independently re-verified, so residual/unwarranted trust can be steered by the attacker.

### Impact Explanation
A malicious or MITM'd git remote can make Desktop pop its own GitHub/"Enterprise" sign-in dialog while performing what looks like an ordinary clone/fetch/push, with the endpoint field populated to the attacker's host. Because the dialog and OAuth/device flow are rendered by Desktop's own trusted UI, a user who is used to seeing Desktop prompt for GitHub credentials on "corporate" GHE instances has no reliable way to tell that this prompt is being triggered by remote-controlled data. In the worst case this can be used to harvest GHE credentials/tokens or to get a legitimate-looking OAuth authorize page to open against an attacker-controlled endpoint.

### Likelihood Explanation
Triggering this requires only that the victim add/clone/fetch from a git remote whose HTTP endpoint is attacker-controlled (or sits behind an attacker proxy) — a normal, unprivileged git workflow that fits the "attacker controls a git remote/proxy response" impact class. No local access, admin rights, or prior credential leakage is required; the only "unusual" action from the user is completing an otherwise ordinary git authentication flow, not an out-of-band social-engineering step.

### Recommendation
Do not use remote-supplied `WWW-Authenticate` realm strings as a security-relevant trust signal. Restrict the `'enterprise'`/`'github.com'` classification to hosts that are either hard-coded (`isDotCom`, `isGHE`, `isGist`) or already explicitly registered as an `Account` endpoint by the user via Preferences (`findGitHubTrampolineAccount`). For any other host, always fall back to the `'generic'` credential-helper path so that an unrecognized remote can never trigger Desktop's built-in GitHub sign-in UI without the user having first explicitly added that GHE instance themselves.

### Proof of Concept
1. Stand up an HTTP(S) git server (or a MITM proxy in front of any remote) that, on an unauthenticated request, returns `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, clone/fetch a repository from this server's URL (e.g. `https://evil.example.com/some/repo.git`) without having any account configured for that host.
3. Git invokes the trampoline credential helper `get` command; `getEndpointKind` sees `wwwauth[0]=Basic realm="GitHub"` and returns `'enterprise'` per `app/src/lib/trampoline/trampoline-credential-helper.ts` (lines 153-165).
4. Since no `Account` matches `evil.example.com`, Desktop calls `ui.promptForGitHubSignIn('https://evil.example.com')` (line ~118), opening the real GitHub Enterprise sign-in flow bound to the attacker's host, instead of falling back to the generic username/password prompt that a truly unknown host should receive.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'

import { exec as git } from 'dugite'

export const parseCredential = (value: string) => {
  const cred = new Map<string, string>()

  // The credential helper protocol is a simple key=value format but some of its
  // keys are actually arrays which are represented as multiple key[] entries.
  // Since we're currently storing credentials as a Map we need to handle this
  // and expand multiple key[] entries into a key[0], key[1]... key[n] sequence.
  // We then remove the number from the key when we're formatting the credential
  for (const line of value.split(/\r?\n/)) {
    const eqIx = line.indexOf('=')
    if (eqIx === -1) {
      continue
    }

    const k = line.slice(0, eqIx)
    const v = line.slice(eqIx + 1)

    if (k.endsWith('[]')) {
      let i = 0
      let newKey

      do {
        newKey = `${k.slice(0, -2)}[${i}]`
        i++
      } while (cred.has(newKey))

      cred.set(newKey, v)
    } else {
      cred.set(k, v)
    }
  }

  return cred
}
