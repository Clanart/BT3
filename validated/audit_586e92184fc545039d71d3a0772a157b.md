### Title
Deterministic preprocess reuse across `share`/`complete` invocations within a DKG-confirmation attempt enables nonce reuse and validator key-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The DKG-confirmation signing protocol caches a FROST preprocess seed under a context key that only varies by `(b"DkgConfirmer", attempt)`. Every call to `preprocess()`, `share()`, or `complete()` re-derives the identical nonce pair from that cached seed. If `share_internal` is invoked twice within the same attempt with different signer sets, preprocesses, or a different `key_pair` (which changes the signed `set_keys_message`), the validator's MuSig private key share is recoverable from the two published signature shares. This is the Serai analog of the Jenkins bug class: a security-sensitive secret operation (here, a Schnorr signature using the validator root key share) is executed in a context wider than intended — one attempt's context spans multiple potentially-divergent signing invocations rather than binding to the exact message and signing set.

### Finding Description
`SigningProtocol::preprocess_internal` encrypts and stores the `CachedPreprocess` seed keyed by `self.context` (`coordinator/src/tributary/signing_protocol.rs:123-145`). For `DkgConfirmer`, `context = (b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:274-277`). The message signed is `set_keys_message(set, removed, key_pair)` (`signing_protocol.rs:296-300`), where `key_pair` and the preprocess `HashMap` come from transaction data. `share()` calls `share_internal` once (`signing_protocol.rs:304-310`), and `complete()` calls `share_internal` *again* before completing (`signing_protocol.rs:321-324`).

The file's own header admits nonce reuse is "explicitly unsafe" and argues safety from BFT ordering plus identical inputs (`signing_protocol.rs:25-51`), and lists an unimplemented TODO: "check the commitments generated from the decided nonces are in fact its commitments on-chain" (`signing_protocol.rs:50-51`). Because the cache key does not commit to `key_pair`, `removed`, or the preprocess set, any execution path producing a distinct `msg` or distinct `preprocesses` under the same `attempt` (e.g., `share()` evaluating a different `key_pair` than the one later fed to `complete()`, or conflicting `DkgShares`-carried values within one attempt) produces two FROST shares `s1 = d + e·ρ1 + c1·x_i` and `s2 = d + e·ρ2 + c2·x_i` over the same nonce commitment `D + E·ρ` per `Schnorr::sign_share` (`crypto/frost/src/algorithm.rs:201-211`) and the nonce combination in `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:385-398`). Since ρ is bound to the message via `hash_msg` (`crypto/frost/src/sign.rs:362-371`), a differing `key_pair` yields a different challenge `c` with the same underlying nonce, enabling `x_i` recovery.

### Impact Explanation
`self.key` is the validator's long-term MuSig/Ristretto private key (`signing_protocol.rs:93`, used in `musig(...)` at line 119). Recovery of this key share compromises the validator root-of-trust key used to confirm DKG results on Substrate — the equivalent of the controller's secret material being disclosed to a party who was only supposed to trigger a computation, not learn the secret.

### Likelihood Explanation
Exploitation requires the node to evaluate two divergent signing inputs under one DKG-confirmation attempt. The code explicitly relies on BFT message ordering for safety and contains a TODO acknowledging the missing commitment-matching check that would enforce it (`signing_protocol.rs:34-54`). Because the design's safety invariant is asserted rather than enforced (no check that the published preprocess matches the presumed preprocess, no binding of `key_pair`/`removed` into the cache context), a logical-path divergence — distinct `key_pair` values or distinct preprocess maps reaching `share` vs. `complete` in the same attempt — directly yields key recovery. Reachability is through public transaction data (`key_pair`, preprocesses, shares all arrive via `Transaction::DkgShares`/`Transaction::Sign` per `coordinator/src/main.rs:485-586`). Uncertain: whether the tributary actually routes two different `key_pair` values into `share()`/`complete()` within one attempt was not fully confirmed, but the missing TODO check indicates the protection is intentionally absent.

### Recommendation
Bind the exact signing inputs into the cached-preprocess context — e.g., key the `CachedPreprocesses` DB entry by `(context, key_pair, removed-set digest, preprocess-set digest)` or commit them into the transcript — and implement the pending check that the on-chain preprocess equals the locally decided preprocess before publishing shares (`signing_protocol.rs:50-54`). If inputs diverge from the cached decision, abort rather than re-sign with the same nonce.

### Proof of Concept
1. Run a `DkgConfirmer` for `attempt = A`; `preprocess()` stores `CachedPreprocess` under `(b"DkgConfirmer", A)` and publishes commitments `D, E`.
2. Cause `share()` to be invoked with `key_pair = K1` → internally `share_internal` signs `set_keys_message(.., K1)` producing `s1 = d + e·ρ1 + c1·x_i`.
3. Cause `complete()` (or a second `share()`) to run in the same attempt with `key_pair = K2 ≠ K1` (or a different preprocess map, yielding different ρ) → `preprocess_internal` returns the same `(d, e)` from the cache, and `share_internal` produces `s2 = d + e·ρ2 + c2·x_i`.
4. With `D, E, s1, s2, ρ1, ρ2, c1, c2` all public/derivable, solve the two equations for `d` and the share `x_i`, recovering the validator's MuSig secret key share. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

  As for safety, it is explicitly unsafe to reuse nonces across signing sessions. This raises
  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from
  the nonces being context-bound under a BFT protocol. The flow is as follows:

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  Additionally, to ensure a rebuilt service isn't flagged as malicious, we have to check the
  commitments generated from the decided nonces are in fact its commitments on-chain (TODO).

  fn preprocess_internal(&mut self) -> (AlgorithmSignMachine<Ristretto, Schnorrkel>, [u8; 64]) {
    let participants = self.spec.validators().iter().map(|val| val.0).collect::<Vec<_>>();
    self.signing_protocol().preprocess_internal(&participants)
  }
  // Get the preprocess for this confirmation.
  pub(crate) fn preprocess(&mut self) -> [u8; 64] {
    self.preprocess_internal().1
  }

  fn share_internal(
    &mut self,

    key_pair: &KeyPair,

      threshold_i_map_to_keys_and_musig_i_map(self.spec, &self.removed, self.key, preprocesses).1;
    let msg = set_keys_message(
      &self.spec.set(),
      &self.removed.iter().map(|key| Public::from(key.to_bytes())).collect::<Vec<_>>(),
      key_pair,
    );
    self.signing_protocol().share_internal(&participants, preprocesses, &msg)
  }
  // Get the share for this confirmation, if the preprocesses are valid.
  pub(crate) fn share(
    &mut self,
    preprocesses: HashMap<Participant, Vec<u8>>,
    key_pair: &KeyPair,
  ) -> Result<[u8; 32], Participant> {
    self.share_internal(preprocesses, key_pair).map(|(_, share)| share)
  }

  pub(crate) fn complete(
    &mut self,
    preprocesses: HashMap<Participant, Vec<u8>>,
    key_pair: &KeyPair,
    shares: HashMap<Participant, Vec<u8>>,
  ) -> Result<[u8; 64], Participant> {
    let shares =
      threshold_i_map_to_keys_and_musig_i_map(self.spec, &self.removed, self.key, shares).1;

    DkgConfirmerSigningProtocol::<'_, T>::complete_internal(machine, shares)
