### Title
`WombatBribeManager.removePool` fails to deactivate `poolInfos`, permanently corrupting vote allocation to active pools - ([File: wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager.removePool()` removes a pool's address from the `pools` array but never updates the corresponding `poolInfos[_lp].isActive` flag or clears `poolInfos[_lp]`. Because `vote()` only checks `poolInfos[_lp].isActive` (not membership in the `pools` array), ordinary users can keep voting for a pool that has been "removed," permanently inflating the global `totalVlMgpInVote` denominator without those votes ever being included in `castVotes()`'s iteration (which loops strictly over `pools`). This silently and permanently dilutes the vote weight sent to Wombat's voter for every remaining active pool, reducing WOM emissions/bribes routed to them.

### Finding Description
`removePool` only pops the pool address out of the `pools` array: [1](#0-0) 

It never sets `poolInfos[_lp].isActive = false`, unlike `addPool` which explicitly sets `isActive: true` when creating the `Pool` struct: [2](#0-1) 

`vote()`, which is callable by any unprivileged wallet holding locked vlMGP, gates on `poolInfos[_lps[i]].isActive` only: [3](#0-2) 

Since `isActive` is never flipped by `removePool`, users can continue to submit votes (`pool.totalVoteInVlmgp += delta`, `userVotedForPoolInVlmgp[...] += delta`, and crucially `totalVlMgpInVote += delta`) for a pool that has already been stripped from the `pools` array.

`castVotes()`, however, only iterates over `pools` when computing and forwarding vote deltas to `wombatStaking.vote`: [4](#0-3) 

The per-pool target allocation is `targetVote = targetVoteInLMGP * totalVotes() / totalVlMgpInVote`. Any vlMGP votes cast toward the removed pool remain counted in `totalVlMgpInVote` forever (they can only be removed via `unvote`, and nothing forces or even signals users to call it, since the pool is invisible from `getPoolsLength()`/`pools` and thus effectively hidden from front-ends that enumerate `pools`). This inflates the denominator used for every remaining, legitimately active pool, permanently shrinking the numerator-to-denominator ratio and thus the real votes forwarded to Wombat's on-chain voter for all active pools — with no way for the protocol or unprivileged users to correct it short of discovering and manually calling `unvote` on an address that is no longer discoverable via the public `pools` list.

This is a direct analog of the reported "market not properly removed from list" bug class: an entity is removed from the primary iteration list (`marketsList` / `pools`) but the flag structure that individual downstream functions actually check (`Market.isActive` / `Pool.isActive`) is left in the old permissive state, producing state that is neither fully active nor fully inactive and causing incorrect accounting in reachable downstream logic.

### Impact Explanation
This causes a permanent, protocol-wide misallocation of governance/bribe vote weight: every future `castVotes()` call sends systematically reduced vote allocations to all currently-active Wombat pools, because the denominator (`totalVlMgpInVote`) is inflated by votes locked against a pool that is no longer part of the numerator computation. This directly reduces bribe/yield revenue harvested by all vlMGP voters for the lifetime of the protocol (or until the orphaned votes happen to be manually unwound), constituting governance voting-result manipulation and permanent degradation/freezing of unclaimed yield for the entire active voter base — not merely the user who voted for the removed pool.

### Likelihood Explanation
`removePool` is a routine, expected admin maintenance operation (pools get delisted from Wombat regularly) and is not a malicious action — it is the intended way to retire a pool. Once it is called even once while any user vote remains allocated to that pool (or a new unprivileged user is simply not aware the pool address is delisted and calls `vote()` again for it, which is trivially callable since `isActive` still reads `true`), the corruption becomes permanent. Given `removePool` is a normal, expected lifecycle operation for the bribe manager, likelihood of triggering this is high.

### Recommendation
Update `removePool` to also set `poolInfos[_lp].isActive = false` (and ideally revoke/zero out `poolInfos[_lp].rewarder` linkage safely), so that `vote()` immediately rejects new votes toward the removed pool. Additionally, consider automatically netting out any outstanding `userVotedForPoolInVlmgp`/`totalVlMgpInVote` contributions tied to the removed pool during `removePool`, rather than requiring an unreachable/undiscoverable manual `unvote` call.

### Proof of Concept
1. Owner calls `addPool(lpA, rewarderA, "poolA")` and `addPool(lpB, rewarderB, "poolB")`. [2](#0-1) 
2. User locks vlMGP and calls `vote([lpA, lpB], [100, 100])`, contributing 200 to `totalVlMgpInVote`.
3. Owner calls `removePool(indexOfLpA)`, removing `lpA` from `pools`, but `poolInfos[lpA].isActive` remains `true`. [1](#0-0) 
4. Any user (including new users unaware `lpA` was delisted) can still call `vote([lpA], [50])` successfully, since the `isActive` check passes; `totalVlMgpInVote` grows to 250. [3](#0-2) 
5. `castVotes()` iterates only over `pools = [lpB]`, computing `targetVote = pool.totalVoteInVlmgp(=100) * totalVotes() / totalVlMgpInVote(=250)` instead of the correct `100/200` ratio — permanently under-allocating votes (and resulting WOM emissions/bribes) to `lpB` and any other genuinely active pool, for as long as the orphaned 50-vote allocation toward the delisted `lpA` remains uncorrected. [5](#0-4)
