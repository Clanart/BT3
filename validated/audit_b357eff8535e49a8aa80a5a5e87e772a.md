### Title
IBC timeout/ack refund path bypasses `TokenPair.Enabled` check, allowing conversion through governance-disabled ERC20 contracts - (File: `x/erc20/keeper/ibc_callbacks.go`)

### Summary
`OnRecvPacket` explicitly checks `pair.Enabled` before auto-converting an incoming IBC coin into its native ERC20 representation, but the mirrored refund path used on IBC timeout / error-acknowledgement (`ConvertCoinToERC20FromPacket`, invoked by `OnTimeoutPacket` and `OnAcknowledgementPacket`) never checks `pair.Enabled`. This asymmetry lets an ordinary user force an EVM call (`transfer`) into a token-pair's ERC20 contract even after governance has disabled that pair via `ToggleConversion`, which is exactly the check `ToggleConversion` is meant to prevent.

### Finding Description
`MintingEnabled`, used by the `ConvertCoin`/`ConvertERC20` message handlers and also inlined manually in `OnRecvPacket`, enforces `pair.Enabled`: [1](#0-0) 

`OnRecvPacket` explicitly re-implements this same guard for the IBC receive path: [2](#0-1) 

However, `ConvertCoinToERC20FromPacket` — the function that runs on `OnTimeoutPacket` and on `OnAcknowledgementPacket` error acks to refund the sender by converting the coin back into its native ERC20 form — only checks the *global* `params.EnableErc20` flag and whether the denom is registered; it never checks `pair.Enabled`: [3](#0-2) 

Both `OnRecvPacket` and `ConvertCoinToERC20FromPacket` ultimately call the same underlying function, `ConvertCoinNativeERC20`, which performs the actual EVM `transfer` call into the token pair's ERC20 contract as `types.ModuleAddress`: [4](#0-3) 

Because `toggleConversion` (triggered by governance `MsgToggleConversion`) is the chain's mechanism to stop *all* further interaction with a token pair's ERC20 contract (e.g., after a malicious, reentrant, or otherwise compromised ERC20 contract has been detected): [5](#0-4) 

the missing `pair.Enabled` check in `ConvertCoinToERC20FromPacket` means any user can still cause a `CallEVM`/`transfer` execution against a governance-disabled ERC20 contract simply by triggering an IBC timeout or error acknowledgement on a transfer that uses that denom (e.g., sending to an unreachable channel/receiver on the counterparty chain). If the contract was disabled because it is malicious/unsafe (arbitrary code executing as `types.ModuleAddress`), this reintroduces the exact attack surface governance intended to shut off, potentially resulting in loss/theft of the escrowed bank coins or of other module-held ERC20 balances reachable from that malicious contract's `transfer` implementation.

### Impact Explanation
This matches the "Critical … theft, or unauthorized extraction of user funds, contract balances, escrowed assets … or token-pair-backed balances" allowed-impact category: the `Enabled` toggle is the chain's sole circuit breaker for a compromised token-pair contract, and this code path silently bypasses it, allowing continued EVM execution as the module account into a contract governance has explicitly disabled.

### Likelihood Explanation
Any unprivileged user holding, or able to route, funds denominated in a disabled token pair can trigger the vulnerable path deterministically by initiating (or having previously initiated) an IBC transfer of that denom and causing a timeout or error acknowledgement (both are ordinary, permissionless IBC outcomes, not privileged/relayer-malicious behavior).

### Recommendation
Add the same `pair.Enabled` check used in `OnRecvPacket` to `ConvertCoinToERC20FromPacket` before calling `ConvertCoinNativeERC20`, e.g.:
```go
if !pair.Enabled {
    return nil // or refund only the native coin, skip ERC20 conversion
}
```

### Proof of Concept
1. Governance registers a token pair for denom `ibc/XXXX` mapped to ERC20 contract `C`.
2. A user converts/holds funds in `ibc/XXXX` and initiates an outbound IBC transfer of that denom to a channel/receiver that will time out or return an error ack.
3. Before the timeout/ack is processed, governance discovers contract `C` is malicious and calls `MsgToggleConversion` to disable the pair (`pair.Enabled = false`), expecting all further conversions to be blocked.
4. The IBC timeout/error-ack fires, invoking `OnTimeoutPacket`/`OnAcknowledgementPacket` → `ConvertCoinToERC20FromPacket`, which does not check `pair.Enabled` and proceeds to call `ConvertCoinNativeERC20`, executing `transfer` on the now-disabled/malicious contract `C` as `types.ModuleAddress`. [6](#0-5)

// ToggleConversion toggles conversion for a given token pair
func (k Keeper) toggleConversion(
	ctx sdk.Context,
	token string,
) (types.TokenPair, error) {
	id := k.GetTokenPairID(ctx, token)
	if len(id) == 0 {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered by id", token,
		)
	}

	pair, found := k.GetTokenPair(ctx, id)
	if !found {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered", token,
		)
	}

	pair.Enabled = !pair.Enabled
	k.SetTokenPair(ctx, pair)
	return pair, nil
}
