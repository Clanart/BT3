### Title
`canBeExpanded` diff-expansion guard is calculated from the wrong quantity and cannot detect content truncation, letting fabricated partial context lines flow into `git apply` patches - (File: `app/src/ui/diff/syntax-highlighting/index.ts`)

### Summary
The reported GoodEntry bug is a broken invariant: a safety guard (`addDust`) is derived from a value on the wrong scale (oracle-price-based dust vs. tick-based consumption), so it silently fails to guarantee the property it was supposed to enforce. GitHub Desktop has a structurally identical pattern in its diff-expansion "load full file to allow context expansion" gate: `canBeExpanded` compares a **line count** to a **byte-count threshold**, which can never actually detect that content was truncated.

### Finding Description
`getNewFileContent`/`getOldFileContent` read at most `MaxHighlightContentLength` (1,048,576) bytes of a file's contents via `readPartialFile` (`app/src/lib/file-system.ts:61-77`, uses `createReadStream(path, { start, end })`) or `getPartialBlobContents` (`app/src/lib/git/show.ts:55-88`, uses `maxBuffer`). Both silently truncate at an arbitrary byte offset with no signal that truncation occurred: [1](#0-0) [2](#0-1) 

`getFileContents` then decides whether the diff is allowed to be expanded to the "whole file" by comparing the *line count* of the possibly-truncated buffer to `MaxDiffExpansionNewContentLength` (`MaxHighlightContentLength - 1`, a byte-count constant): [3](#0-2) [4](#0-3) 

Because the minimum size of a line is 1 byte (a bare `\n`), the maximum number of lines obtainable from a buffer capped at `MaxHighlightContentLength` bytes is bounded by that same byte count. That means `newContents.length <= MaxDiffExpansionNewContentLength` is true for essentially all real-world truncated text (any file with lines averaging more than ~1 byte will always satisfy this), regardless of whether the actual tracked file is far larger than 1MB and got truncated mid-line. The flag that is supposed to certify "we loaded the complete, untruncated file" therefore cannot distinguish a truncated read from a genuinely small file — exactly the "the calculation does not take into account the actual result" flaw from the seed report.

When `canBeExpanded` is (wrongly) `true`, the UI enables "Expand Whole File" / per-hunk expansion, which calls `expandWholeTextDiff`/`expandTextDiffHunk` using the truncated `newContentLines` array as if it were the complete file: [5](#0-4) [6](#0-5) 

Since the byte-limited truncation point is unrelated to line boundaries, the last element of `newContentLines` can be a partial/garbled line. `expandTextDiffHunk` wraps it into a `DiffLine` of type `Context` with no marker that it is synthetic/truncated. `formatPatch` and `formatPatchToDiscardChanges` in `app/src/lib/patch-formatter.ts` treat every `DiffLineType.Context` line as ground truth and copy it verbatim into the unified diff used with `git apply` for partial staging/discarding: [7](#0-6) [8](#0-7) 

That patch is fed to `git apply --unidiff-zero --whitespace=nowarn -` for discards (or the equivalent staging path): [9](#0-8) 

### Impact Explanation
An attacker who controls a cloned/fetched repository can commit a tracked text file larger than 1MB with a modification located near/after the 1MB boundary. When the victim opens that diff in GitHub Desktop and uses "Expand Whole File" or expands the last hunk, the truncated read causes a fabricated partial-line `Context` entry to be inserted into the in-memory diff. If the victim then performs a line-range stage or discard action near that hunk, `formatPatch`/`formatPatchToDiscardChanges` will embed that non-matching context line into the patch handed to `git apply`. This can silently corrupt what is staged/committed (mismatched context causing `git apply` to reject/only partially apply the hunk, or — depending on git's fuzzy-context tolerance — apply against a shifted location) which falls squarely under "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Requires only an attacker-controlled repository with a single large tracked file and a change positioned near the 1MB read boundary, plus the victim using the built-in "Expand Whole File"/hunk-expansion and partial line staging/discard features on that file — no local access, no admin rights, no pre-existing malware, and no unnatural steps beyond normal Desktop usage (viewing a diff and staging/discarding part of it).

### Recommendation
Do not derive `canBeExpanded` from a line-count vs. byte-count comparison. Instead, have `readPartialFile`/`getPartialBlobContents` (or their callers) explicitly report whether the read was truncated (e.g., compare bytes actually read against the real file/blob size, or request `length + 1` bytes and check if more than `length` were returned), and only allow full-file diff expansion when the content is verified complete and line-boundary aligned.

### Proof of Concept
1. In a repository, create/commit a text file `big.txt` > 1MB where the diff hunk of interest sits at/after the byte offset corresponding to the 1MB mark, with a line that straddles that exact byte offset in the new content.
2. Fetch/clone that repository into GitHub Desktop and open the working-directory or commit diff for `big.txt`.
3. Observe `getFileContents` (`app/src/ui/diff/syntax-highlighting/index.ts:107-129`) returns `canBeExpanded: true` because `newContents.length` (line count of the 1MB-capped buffer) is always ≤ `MaxDiffExpansionNewContentLength` — verify by instrumenting/logging that the buffer was truncated (`Buffer.byteLength` == `MaxHighlightContentLength`) while `canBeExpanded` is still `true`.
4. Trigger "Expand Whole File" (`onExpandWholeFile`, `side-by-side-diff.tsx:1498-1519`) or expand the last hunk; inspect the resulting `ITextDiff.hunks` for a `Context` line whose text is a truncated/partial line (does not match the real file content past the 1MB boundary).
5. Select a line range spanning that fabricated context line and invoke "Discard changes"/partial stage; confirm `formatPatchToDiscardChanges`/`formatPatch` (`app/src/lib/patch-formatter.ts:151-156, 274-280`) embeds the bad context line verbatim and that `git apply --unidiff-zero --whitespace=nowarn -` (`app/src/lib/git/apply.ts:115-119`) either fails or applies against mismatched content.

```typescript
export async function readPartialFile(
  path: string,
  start: number,
  end: number
): Promise<Buffer> {
  return await new Promise<Buffer>((resolve, reject) => {
    const chunks = new Array<Buffer>()
    let total = 0

    createReadStream(path, { start, end })
      .on('data', (chunk: Buffer) => {
        chunks.push(chunk)
        total += chunk.length
      })
      .on('error', reject)
      .on('end', () => resolve(Buffer.concat(chunks, total)))
  })
```

```typescript
export async function getFileContents(
  repo: Repository,
  file: ChangedFile
): Promise<IFileContents> {
  const [oldContents, newContents] = await Promise.all([
    getOldFileContent(repo, file).catch(e => {
      log.error('Could not load old contents for syntax highlighting', e)
      return null
    }),
    getNewFileContent(repo, file).catch(e => {
      log.error('Could not load new contents for syntax highlighting', e)
      return null
    }),
  ])

  return {
    file,
    oldContents: oldContents?.toString('utf8').split(/\r?\n/) ?? [],
    newContents: newContents?.toString('utf8').split(/\r?\n/) ?? [],
    canBeExpanded:
      newContents !== null &&
      newContents.length <= MaxDiffExpansionNewContentLength,
  }
```

```typescript
export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
```
