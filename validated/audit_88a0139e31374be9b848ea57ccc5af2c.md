### Title
Gasless swap admission uses a manipulable spot AMM price (`getAmountIn`) allowing minAmountOut griefing / value-extraction analogous to market-rate oracle arbitrage - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The stETH/ETH finding is about using a live *market rate* feed (rather than a robust/pessimistic exchange rate) to gate deposit/withdraw economics, which lets an attacker exploit the gap between the feed and true value for arbitrage. In this repo, the closest reachable analog is the `kaiax/gasless` module's `swapForGas` admission check, `checkBalanceForSwap`, which validates a user-submitted `SwapTx`'s declared `amountIn`/`minAmountOut` against the *current on-chain spot AMM price* returned by `GaslessSwapRouter.GetAmountIn(token, minAmountOut)` [1](#0-0) . Because this price is a live, single-block spot price from an AMM (Uniswap-style reserves) rather than a robust/time-weighted rate, any unprivileged sender can manipulate it within the same block/bundle to pass admission while the actual execution settles against different (attacker-favorable) reserves.

### Finding Description
`checkBalanceForSwap` is the mempool-time admission check for `GaslessSwapTx` (`swapForGas`) [2](#0-1) . It fetches the router's *current* spot exchange rate via a view call, `GetAmountIn`, and only requires `amountIn >= requiredAmountIn` computed from that instantaneous price [1](#0-0) ; the router itself derives this from live AMM reserves, mirroring the same pattern used by `UniswapV2Router02.GetAmountOut`/`GetAmountsIn`, which are pure functions of the reserves passed to them at call time [3](#0-2) .

The comment inside the code itself explicitly frames this as a "market rate": *"Required token amountIn, given the current exchange rate and the declared minAmountOut."* [4](#0-3) . This is the exact bug-class parallel to the report: the check is performed against a spot/market rate rather than a manipulation-resistant rate (e.g. TWAP or a pessimistic bound), and the same underlying reserves are readable/writable by any address prior to inclusion of the gasless swap. A single unprivileged transaction sender (or an auction bidder/bundler under `kaiax/auction`, since `FilterTxs`/`ExtractTxBundles` explicitly coordinate gasless and auction bundles [5](#0-4) ) can move the pool's reserves with a preceding swap in the same block, causing:
- Their own `GaslessSwapTx` to be admitted to the pool/pending queue using a favorable (pre-manipulation) `requiredAmountIn` check, then executed post-manipulation against worse reserves, extracting the difference from the AMM's LPs/counterparties (i.e., moving value from the pool to themselves) while the protocol's own admission gate never re-validates against final settlement price.
- Because `swapForGas` settles `amountRepay` to the block proposer from swap proceeds (see `SwapForGas`/`SwappedForGas` in `GaslessSwapRouter.go` and `LendTxGenerator` flow) [6](#0-5) , if the manipulated price causes `swapForGas` to fail or under/over pay the repay amount, this directly affects proposer/lender repayment accounting, i.e., fee-delegation-like value flow (`LendTxGenerator` lends KAIA to cover fees, expecting repayment from the swap) [7](#0-6) .

### Impact Explanation
An attacker sending a single transaction (a router swap) immediately followed/preceded by their own `GaslessSwapTx` in the same block can arbitrage the gap between the price used for admission (`checkBalanceForSwap`) and the price at execution time, similarly to how a stETH/ETH market-feed depeg lets a depositor arb the exchange-rate gate. This can (a) cause admitted swaps to revert at execution due to `minAmountOut` no longer being satisfiable (denial of gasless service / wasted proposer-lent gas if the lend tx already executed), or (b) let the attacker extract value from AMM liquidity that the gasless mechanism was relying on as a "price oracle" for solvency checks, undermining the repayment guarantee the mechanism assumes. This is a Medium-severity issue: it does not directly mint tokens, but it breaks an economic assumption (spot price ≈ fair price at execution) baked into a fee-delegation/gasless settlement flow reachable by any transaction sender.

### Likelihood Explanation
Medium. It requires the attacker to control both a preceding manipulating swap and the target `GaslessSwapTx` within the same block, or coordinate via the auction/bundling module (`kaiax/auction`), which is designed to allow exactly this kind of atomic multi-tx execution ordering around target transactions [8](#0-7) . Low liquidity pools for whitelisted gasless tokens make this cheaper to execute; `ShouldCheckSwapAmount` can also be disabled by config, but when enabled it still only checks against the manipulable spot price.

### Recommendation
Do not rely on a single spot-price view call (`GetAmountIn`) for solvency/admission checks of `GaslessSwapTx`. Use a manipulation-resistant reference price (e.g., a TWAP window, or bound the maximum price impact allowed per swap, or require a pessimistic/discounted rate similar to the mitigation proposed for the stETH report) before admitting or lending on a `GaslessSwapTx`, and re-validate the price bound again at actual execution time rather than only within the tx-pool `checkBalanceForSwap` admission gate.

### Proof of Concept
1. Attacker identifies the whitelisted AMM pool backing `GaslessSwapRouter` for a whitelisted token.
2. Attacker submits (or bundles via `auction_submitBid`) a swap on the underlying Uniswap-style router that shifts reserves in their favor for their target token.
3. In the same block, attacker's `GaslessSwapTx` (`swapForGas`) is validated by `checkBalanceForSwap`, which calls `GetAmountIn` against the *current* (soon-to-be-stale or just-manipulated) reserve state [1](#0-0) .
4. Depending on manipulation direction, either: (a) the swap tx is wrongly admitted using a favorable price and reverts or extracts extra value on execution, or (b) proposer-lent gas (`LendTxGenerator`) is not fully recovered via `amountRepay`, shifting cost onto the fee-delegation/lending mechanism.

func (g *GaslessModule) checkBalanceForSwap(swapArgs *SwapArgs, swapNonce uint64) error {
	token := swapArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	g.gaslessInfoMu.RLock()
	swapRouter := g.swapRouter
	g.gaslessInfoMu.RUnlock()

	// tx.minAmountOut >= tx.amountRepay
	minAmountOut := swapArgs.MinAmountOut
	amountRepay := swapArgs.AmountRepay
	if minAmountOut.Cmp(amountRepay) < 0 {
		return fmt.Errorf("insufficient minAmountOut: minAmountOut=%s, amountRepay=%s", minAmountOut.String(), amountRepay.String())
	}

func (a *AuctionModule) FilterTxs(txs map[common.Address]types.Transactions) {
	if atomic.LoadUint32(&a.bidPool.running) == 0 {
		return
	}

	curBlock := a.Chain.CurrentBlock()
	if curBlock == nil {
		return
	}

	targetTxHashMap := a.bidPool.getTargetTxHashMap(curBlock.NumberU64() + 1)
	edOffset := a.AuctionConfig.EDOffset

	now := time.Now()
	deadline := now.Add(-edOffset)
	// filter txs that are after the auction early deadline
	for addr, list := range txs {
		for i, tx := range list {
			if tx.Time().After(deadline) && !a.isGaslessTx(tx) {
				// if the tx is a target tx, skip it
				if _, ok := targetTxHashMap[tx.Hash()]; ok {
					continue
				}

				if i == 0 {
					// if first transaction exceeds deadline, remove the address
					delete(txs, addr)
				} else {
					// keep only transactions before the deadline
					txs[addr] = list[:i]
				}
				break
			}
		}
	}

	edOffsetGauge.Update(int64(edOffset))
}

func (a *AuctionModule) isGaslessTx(tx *types.Transaction) bool {
	if a.gaslessModule == nil {
		return false
	}

	return a.gaslessModule.IsBundleTx(tx)
}
