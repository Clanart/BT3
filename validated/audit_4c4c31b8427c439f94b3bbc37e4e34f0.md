## Title
Uncontrolled recursion in `AccountKeyRoleBased.DecodeRLP` allows stack-exhaustion DoS via deeply nested AccountKey structures - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
Kaia's `AccountKeyRoleBased` RLP decoder recursively decodes nested account-key blobs without any nesting-depth limit, mirroring the exact bug class in the Faraday advisory (`Faraday::NestedParamsEncoder#dehash`): an attacker-controlled, arbitrarily-deep nested structure is walked by unbounded recursive decode calls, eventually exhausting the goroutine stack and crashing the node process with an unrecoverable fatal runtime error.

### Finding Description
`AccountKeySerializer.DecodeRLP` reads a key type and then decodes the concrete key body via `NewAccountKey(keyType)` followed by `s.Decode(serializer.key)`: [1](#0-0) 

When the key type is `AccountKeyTypeRoleBased`, this dispatches to `AccountKeyRoleBased.DecodeRLP`, which decodes a list of raw byte blobs and then, for **each** blob, calls `rlp.DecodeBytes(b, &serializer)` — a brand-new top-level RLP decode that re-enters `AccountKeySerializer.DecodeRLP`: [2](#0-1) 

Because a role entry can itself be another `AccountKeyRoleBased`, this creates a fully attacker-controlled recursive call chain: `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → `NewAccountKey`/`s.Decode` → `AccountKeyRoleBased.DecodeRLP` → ... with **no depth counter or limit anywhere in the decode path**. The only place nested `RoleBased` keys are rejected (`ErrNestedCompositeType` / "roleBasedKey cannot contains a roleBasedKey") is in post-decode semantic validation (`CheckInstallable`, `CheckUpdatable`, `checkAccountKeyZeroValues`), which runs only *after* the decode has already completed: [3](#0-2) [4](#0-3) 

This decode path is reachable from a single, unauthenticated, unprivileged input in two ways:
1. **Public RPC** — `KaiaAPI.DecodeAccountKey` directly RLP-decodes attacker-supplied bytes with no size limit at all: [5](#0-4) 
2. **Raw transaction submission** — `KaiaTransactionAPI.SendRawTransaction` RLP-decodes the entire transaction *before* any pool validation (including `MaxTxDataSize`, signature, or nonce checks) runs: [6](#0-5) 
For `TxTypeAccountUpdate`/`TxTypeFeeDelegatedAccountUpdate*`, `Transaction.DecodeRLP` decodes the full internal data (including the `Key` field) before signature sanity checks occur: [7](#0-6) [8](#0-7) 

The `MaxTxDataSize` bound is enforced only inside `TxPool.validateTx`, which executes strictly after `rlp.DecodeBytes` has already returned in `SendRawTransaction` — so the recursive decode (and the crash) happens before that size guard is ever reached: [9](#0-8) 

Note that the generic `rlp.Stream` decoder for statically-typed Go structs bounds recursion by the Go type's fixed field structure at compile time; that is not the vulnerable pattern here. The vulnerability is specific to `AccountKeyRoleBased`, where the recursion depth is driven by the *attacker-supplied byte content*, not by a fixed Go type — exactly analogous to Faraday's `dehash` walking an attacker-controlled `Hash` built from an arbitrarily nested query string.

### Impact Explanation
Because Go stack overflows raise a fatal, unrecoverable runtime error (not a normal panic catchable via `recover()`), a single crafted RLP blob can crash the entire node process — not just one goroutine or RPC request. Any full node (validator or non-validator) that RLP-decodes such a blob via its public RPC endpoint (`kaia_decodeAccountKey`) or via `eth/kaia_sendRawTransaction`, or that receives the corresponding transaction/message through normal transaction propagation, would crash. This is a direct, unauthenticated denial-of-service against node availability/liveness (CWE-674), matching High severity per the CVSS vector in the report (`AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`).

### Likelihood Explanation
Likelihood is high: no authentication, no special privileges, and no prior state are required. An attacker only needs to construct a byte string encoding deeply nested `AccountKeySerializer`/`AccountKeyRoleBased` blobs (each level trivially wraps the previous one) and submit it to a public JSON-RPC endpoint or broadcast it as a raw transaction.

### Recommendation
Add an explicit recursion-depth counter/limit to the account-key decode path (e.g., pass a depth parameter through `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP`, rejecting decoding once a small maximum depth, e.g. 1–2, is exceeded), enforced *during* decode rather than only in post-decode `CheckInstallable`/`CheckUpdatable` validation. Consider also imposing a general nesting/recursion depth limit in the shared `rlp` package for any `Decoder` implementations that recursively re-enter `rlp.DecodeBytes`/`rlp.Decode`.

### Proof of Concept
1. Construct account key blob `L0 = RLP([keyTypeByte(Public), pubkeyBytes])` (a valid leaf `AccountKeyPublic`).
2. Build `L1 = RLP([keyTypeByte(RoleBased), RLP([L0])])` — a `RoleBased` key containing one role entry that is itself `L0`... but to nest `RoleBased` inside `RoleBased`, set the role-entry's `keyType` byte to `RoleBased` and its body to another `RoleBased`-encoded list, i.e. `Ln = RLP([keyTypeByte(RoleBased), RLP([ RLP([keyTypeByte(RoleBased), RLP([ Ln-1 ]) ]) ]) ])`.
3. Repeat this wrapping tens of thousands of times to produce a single byte string `L_N`.
4. Submit `L_N` via `kaia_decodeAccountKey` (or embed it as the `Key` field of a raw `TxTypeAccountUpdate` transaction and submit via `eth_sendRawTransaction`/`kaia_sendRawTransaction`).
5. `rlp.DecodeBytes` recurses through `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` N times, exhausting the goroutine stack and crashing the node with a fatal `runtime: goroutine stack exceeds ... limit` error before any `MaxTxDataSize` or signature check is reached.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
