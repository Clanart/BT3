### Title
`revealInFileManager`/`openInExternalEditor` build file paths with `Path.join` instead of the repo's own `resolveWithin` containment check, letting a committed symlink in a cloned/fetched repo redirect "Reveal"/"Open" actions outside the repository - (File: `app/src/lib/app-shell.ts`)

### Summary
The Lambo.win bug is fundamentally: a trusted value (`uniswapPool`) is combined with an attacker-controlled value (`directionMask`) via a bitwise operator without verifying that the *result* still refers to the intended trusted target, so the attacker can substitute a completely different (malicious) destination. The codebase already recognizes this exact class of bug for one code path — `IOpenRepositoryFromURLAction.filepath` is joined with the repository root using `resolveWithin()`, which does a `realpath()`-based containment check specifically to defend against symlink-based escapes [1](#0-0) . However, several other call sites that build a "full path" from `repository.path` (trusted root) + `file.path` (untrusted, repo-content-derived) still use plain `Path.join`, with **no** containment/realpath check, before handing the result to the OS shell or an external editor.

### Finding Description
`revealInFileManager` computes the on-disk path purely with `Path.join` and immediately passes it to the OS shell: [2](#0-1) 

The same unguarded pattern is used to build `fullPath` for "Open in External Editor" / "Open with Default Program" in the pull-request file list and the working-directory changes list, both of which are driven by `file.path` taken from `WorkingDirectoryFileChange`/`CommittedFileChange` objects (i.e., paths derived from the content of a cloned/fetched repository): [3](#0-2) [4](#0-3) 

Contrast this with the deep-link `filepath` handler, which the project deliberately hardened with `resolveWithin` (real-path containment) plus an `isAbsolute` rejection specifically to stop a crafted value from escaping the repository root: [1](#0-0) [5](#0-4) 

The test suite even documents that `resolveWithin` is specifically meant to catch the symlink-escape case that plain `Path.join`/`Path.resolve` cannot: [6](#0-5) 

Git allows tracked entries to be symbolic links. A malicious/compromised remote can commit a tracked symlink (e.g. `evil-link -> /Users/victim/.ssh` or a relative `../../../../.ssh`). Git's fsck rejects literal `..` path *components* in tree entry *names*, but it does not forbid a *symlink's target* from pointing outside the working tree — that's exactly the scenario `resolveWithin`'s symlink test is written to defend against. After the victim clones/fetches such a repository and the file shows up as a change (e.g. renamed/added `evil-link`), `file.path` is just `"evil-link"` — a perfectly normal-looking single path component that passes any naive validation. `Path.join(repository.path, "evil-link")` yields a path that, when opened via `shell.showItemInFolder`/`shell.openPath`/the external editor launcher, is resolved by the OS through the symlink to the attacker-chosen destination outside the repository.

### Impact Explanation
An attacker who controls a cloned/fetched repository's content (a fork, a malicious PR, or content added by a supply-chain-compromised dependency repo) can plant a symlink that, once the victim right-clicks "Reveal in Finder/Explorer" or "Open in External Editor"/"Open with Default Program" on that changed file, causes GitHub Desktop to reveal or open a file/folder *outside* the intended repository (e.g., `~/.ssh`, `~/.aws`, browser profile directories, or other sensitive locations). Depending on the target and OS behavior, this can result in disclosure of file contents (open in editor), or in launching arbitrary executables if the symlink target is made to resolve to a script/binary opened via "Open with Default Program". This matches the report's "attacker substitutes the trusted target via an unvalidated composed value" pattern, mapped onto Desktop's file-path composition rather than Solidity's pool-address composition.

### Likelihood Explanation
This requires only that the victim clone/fetch an attacker-controlled or attacker-contributed repository (or view a malicious PR via "Open Pull Request") and then take one ordinary UI action (right-click → Reveal/Open) on a listed changed file — no local access, no admin rights, and no unnatural steps beyond normal GitHub Desktop usage of reviewing changes/PRs. Because the vulnerable code paths use `Path.join` directly while the sibling deep-link path was explicitly patched with `resolveWithin`, this looks like an inconsistently-applied fix rather than a hardened boundary — a strong indicator the gap is real and reachable through the normal Changes/PR-review UI.

### Recommendation
Route every place that turns a repo-relative `file.path` into a filesystem path for the shell/editor (`revealInFileManager` in `app/src/lib/app-shell.ts`, `onOpenFile`/`onFileContextMenu` in `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, and the equivalent handlers in `app/src/ui/changes/filter-changes-list.tsx`) through the existing `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` helper (already implemented in `app/src/lib/path.ts`) instead of raw `Path.join`, and refuse to reveal/open the file if the resolved real path is not contained within the repository root — exactly as is already done for the `IOpenRepositoryFromURLAction.filepath` case.

### Proof of Concept
1. Attacker creates a public repository containing a tracked symbolic link `evil-link` whose target is `../../../../.ssh` (or an absolute path to a sensitive directory), then removes it (or renames a real file to it) so it shows up as a change, or opens a PR that adds this symlink.
2. Victim clones the repository in GitHub Desktop, or opens the PR via "Open Pull Request" (`PullRequestFilesChanged`), and sees `evil-link` in the changed-files list.
3. Victim right-clicks `evil-link` and chooses "Reveal in Finder/Explorer" (`getRevealInFileManagerMenuItem`/`onFileContextMenu`) or "Open in External Editor".
4. `revealInFileManager`/`Path.join(repository.path, file.path)` builds `<repo>/evil-link` and passes it straight to `shell.showItemInFolder`/the editor launcher, which the OS resolves through the symlink to the attacker-chosen target outside the repository — with none of the `resolveWithin` real-path containment checks that protect the analogous deep-link `filepath` flow in `dispatcher.ts`.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
