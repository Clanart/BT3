Audit Report

## Title
Permissionless `DepositDelegatorRewards` griefing permanently blocks vote-account closure/withdrawal for un-delegated vote accounts - (File: `programs/vote/src/vote_state/mod.rs`)

## Summary
`deposit_delegator_rewards` allows any signer to transfer an arbitrary amount (even 1 lamport) into any vote account and unconditionally increments that account's `pending_delegator_rewards` field via `add_pending_delegator_rewards`, with no relationship required to the vote account's authorized voter/withdrawer. `withdraw()` then refuses full closure whenever `pending_delegator_rewards > 0`, and the only mechanism that reduces this value, `calculate_block_reward`, is driven by active delegated stake and returns `0` unconditionally when `total_active_stake` for that vote account is zero, so a vote account with no delegated stake can never have `pending_delegator_rewards` reduced.

## Finding Description
`deposit_delegator_rewards` at `programs/vote/src/vote_state/mod.rs:936-988` only requires `verify_authorized_signer(&source_address, signers)` on the sending account, then performs a CPI transfer and calls `vote_state.add_pending_delegator_rewards(deposit)`, which in `programs/vote/src/vote_state/handler.rs:196-209` does a `checked_add` with no minimum threshold, no cap, and no authorization tied to the vote account itself. [1](#0-0) [2](#0-1) 

`withdraw()` at `programs/vote/src/vote_state/mod.rs:1084-1122` reads `pending_delegator_rewards` and, when `remaining_balance == 0` (i.e., an attempt to fully close/withdraw), rejects the operation outright with `InstructionError::InsufficientFunds` if `pending_delegator_rewards > 0`; for partial withdrawals it additionally enforces `remaining_balance >= rent_exempt_minimum + pending_delegator_rewards`. [3](#0-2) 

The only redemption path for `pending_delegator_rewards` is `calculate_block_reward` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-232`, which is invoked per stake `Delegation` pointing at the vote account. It looks up `total_active_stake` from `reward_epoch_delegated_stakes.delegated_stakes` for the vote account's pubkey and returns `0` immediately if that stake is zero — without any distribution occurring — leaving `pending_delegator_rewards` untouched. [4](#0-3) 

Since this function is only ever invoked once per stake delegation that targets the vote account (there is no iteration path for vote accounts with zero delegations), a vote account with no active delegated stake has no code path in the indexed reward-distribution or withdrawal logic that can ever reduce `pending_delegator_rewards` back to zero. The permission check in `verify_authorized_signer` only requires the *depositing* account to sign — it enforces nothing about the *target* vote account, confirming the deposit path is fully unprivileged with respect to the vote account being griefed.

The instruction is gated only by feature flags (`commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing`), not by any permission check relative to the target vote account, as seen in `programs/vote/src/vote_processor.rs:409-426`. [5](#0-4) 

## Impact Explanation
An unprivileged attacker can pay a negligible cost (a 1-lamport deposit plus transaction fee) to permanently set `pending_delegator_rewards > 0` on any target vote account that currently has no (or a to-be-fully-deactivated) delegated stake. Because `withdraw()` treats this field as an untouchable reserve, and because zero delegated stake means the field is never reduced, the vote account's authorized withdrawer is permanently prevented from fully closing the account and reclaiming its rent-exempt reserve. This is a fund-lock/denial-of-service against the vote account's withdrawable lamports and account-closure capability — a violation of fund/accounting correctness for the targeted account, at negligible and repeatable attacker cost.

## Likelihood Explanation
High. The `DepositDelegatorRewards` instruction is permissionless (only the depositor's own signature is required), inexpensive (arbitrarily small deposit amount, e.g. 1 lamport), and requires no privileged access — only that the relevant SIMD features (`commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing`) are activated network-wide, which are feature-set gates rather than permission checks. Any vote account without active delegated stake (newly created vote accounts, or ones in the process of winding down after deactivating all stake) is a viable and repeatable target.

## Recommendation
- Restrict `DepositDelegatorRewards` deposits to be bounded by an actual expected/owed reward amount, or require the caller to be an authorized party (e.g., the runtime itself during reward distribution) rather than any arbitrary signer.
- Alternatively, add a code path allowing the vote account's authorized withdrawer to reclaim, burn, or otherwise clear a stranded `pending_delegator_rewards` balance when the vote account has zero active delegated stake, so the reserve cannot become permanently unspendable and block account closure.

## Proof of Concept
1. Attacker submits `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` targeting a vote account with zero currently-delegated stake, signing only with an arbitrary funded source account (`programs/vote/src/vote_state/mod.rs:936-988`).
2. This increments the target's `pending_delegator_rewards` to `1` via `add_pending_delegator_rewards` (`programs/vote/src/vote_state/handler.rs:196-209`).
3. Because no stake `Delegation` targets this vote account, `calculate_block_reward` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-231`) is never invoked for it during epoch reward distribution, so `pending_delegator_rewards` is never reduced.
4. The vote account's authorized withdrawer calls `withdraw()` attempting to fully close the account (`remaining_balance == 0`); the call fails with `InstructionError::InsufficientFunds` because `pending_delegator_rewards > 0` (`programs/vote/src/vote_state/mod.rs:1084-1122`), and this failure persists indefinitely as long as no stake is delegated to the account, permanently blocking closure/rent reclamation.
