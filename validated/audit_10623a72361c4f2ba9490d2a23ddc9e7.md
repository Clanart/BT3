## Title
Asymmetric decimal-scaling formula in `pallet-hyper-fungible-token` mismints/misreleases cross-chain token amounts whenever a registered token's remote decimals are lower than local decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` and `convert_to_erc20` in the `hyper-fungible-token` pallet compute the decimal-scaling exponent as `erc_decimals.saturating_sub(local_decimals)`. `saturating_sub` silently clamps to `0` whenever `erc_decimals < local_decimals`, meaning that direction of the conversion performs **no scaling at all** instead of scaling in the opposite direction. This is the exact bug class from the seed report: a formula that only correctly accounts for one side of a two-sided decimal relationship, corrupting a value used to move real funds. [1](#0-0) 

### Finding Description
`convert_to_erc20` is used in the outbound `send` extrinsic to convert an escrowed/burned local balance into the amount encoded in the cross-chain `Message.amount` field that the destination contract will mint or release: [2](#0-1) 

`convert_to_balance` is used symmetrically in `on_accept` (minting/crediting the beneficiary on receipt) and in `on_timeout` (refunding the original sender): [3](#0-2) [4](#0-3) 

Both helpers use `erc_decimals.saturating_sub(local_decimals)` as the scaling exponent:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
    dec_str.parse::<B>()
}
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

This is only correct when `erc_decimals >= local_decimals`. When the *registered* remote token has **fewer** decimals than the local asset (e.g. a native/local asset with 18 decimals bridged against a 6-decimal ERC20, a completely ordinary, admin-configured pairing via `Precisions`/`register_token`), `saturating_sub` returns `0`:

- `convert_to_erc20`: multiplier becomes `10^0 = 1` instead of the required `1/10^(local-erc)` scale-down, so the erc20 amount encoded in the outbound `PostRequest` is inflated by `10^(local_decimals - erc_decimals)` relative to what was actually escrowed/burned on the source chain.
- `convert_to_balance`: divisor becomes `10^0 = 1` instead of the required `10^(local-erc)` scale-up, so the amount minted to the beneficiary (`on_accept`) or refunded to the sender (`on_timeout`) is deflated by the same factor.

Existing decimals are configured per-chain via `register_token`/`Precisions`, and every existing test only exercises the safe direction (`erc_decimals=18 > local_decimals=10`): [5](#0-4) 

No test exercises `local_decimals > erc_decimals`, so the broken branch is untested and unnoticed.

### Impact Explanation
This directly corrupts the amount of value moved across the bridge, matching the "stealing or loss of funds" / "unauthorized transaction / execution" bounty categories:
- Outbound direction (`send` → `convert_to_erc20`): the message dispatched to the destination chain instructs the peer contract to release/mint an amount inflated by `10^(local_decimals-erc_decimals)` relative to the value actually escrowed/burned on the source chain — a bridge insolvency / unbacked-mint condition triggerable by any ordinary user, not just a privileged or malicious actor.
- Inbound direction (`on_accept`/`on_timeout` → `convert_to_balance`): the beneficiary or refunded sender receives an amount deflated by the same factor — a direct, silent loss of funds for legitimate users completing an otherwise correct transfer or timeout refund.

Neither path requires a compromised relayer, prover, or governance actor — it is triggered purely by the ordinary flow of `send`/`on_accept`/`on_timeout` whenever the token pair's configured decimals happen to have `local_decimals > erc_decimals`, which is a foreseeable, non-malicious configuration (native Substrate assets commonly use 10-18 decimals; many real ERC20s use 6 decimals).

### Likelihood Explanation
Likelihood is high: it fires deterministically for any token registration where `local_decimals > erc_decimals` — no attacker manipulation, race, or malicious peer is needed, only calling the public `send` extrinsic or the normal `on_accept`/`on_timeout` message flow on an admin-registered token pair with this (unremarkable) decimals relationship. The existing test suite's exclusive use of the opposite decimals relationship (`18 > 10`) shows this configuration was never validated.

### Recommendation
Compute the scaling factor symmetrically instead of via a single-direction `saturating_sub`:
```rust
if erc_decimals >= local_decimals {
    value * 10^(erc_decimals - local_decimals)   // convert_to_erc20 scale-up
} else {
    value / 10^(local_decimals - erc_decimals)   // convert_to_erc20 scale-down
}
```
and the mirrored logic for `convert_to_balance`, then add regression tests covering `local_decimals > erc_decimals` for `send`, `on_accept`, and `on_timeout`.

### Proof of Concept
Using the pallet's own test harness (`modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs`) as a base, register a token whose remote `decimals` is *lower* than the local asset's decimals (e.g. local asset decimals = 18, remote/erc decimals = 6, the inverse of the existing tests which use `18, 10`), then:
1. Call `HyperFungibleToken::send` with `amount = 10^18` (1 unit of an 18-decimal local asset).
2. Inspect the dispatched `Message.amount`: with the current code, `convert_to_erc20(10^18, erc_decimals=6, local_decimals=18)` yields `10^(6.saturating_sub(18)) * 10^18 = 10^0 * 10^18 = 10^18`, instead of the correct `10^18 / 10^12 = 10^6`. The destination contract is instructed to release/mint `10^18` units of a 6-decimal token — a 10¹²× inflation relative to the 1 unit actually escrowed.
3. Symmetrically, feeding that same erc20 amount back through `on_accept`/`on_timeout` via `convert_to_balance(value, erc_decimals=6, local_decimals=18)` yields `value / 10^0 = value`, i.e. the beneficiary/refund receives `10^(-(local-erc))` times too little relative to the correct scaled-up amount — demonstrating the loss on the inbound side. /// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
