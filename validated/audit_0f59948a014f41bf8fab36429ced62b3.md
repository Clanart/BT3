### Title
Untrusted `ReceivedOutput` records can create unspendable Bitcoin inputs - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and `OutPoint` without cryptographically binding the claimed output contents to the referenced outpoint. `SignableTransaction` then uses the attacker-controlled `TxOut` as the BIP-341 prevout while spending the attacker-selected outpoint, causing the resulting signature to be invalid when the claimed `TxOut` differs from the chain’s actual output. This is analogous to rewards accruing to a dead gauge: bytes representing a dead or nonexistent asset are counted as spendable balance even though they cannot be spent.

### Finding Description
`ReceivedOutput` advertises a spendable output and stores `offset`, `output`, and `outpoint` as independent fields. [1](#0-0) 

`ReceivedOutput::read` deserializes all three fields directly and returns the object without checking that `outpoint` identifies a confirmed UTXO containing `output`. [2](#0-1) 

Transaction construction converts `input.outpoint` into a `TxIn`, while separately preserving the deserialized `input.output` in `prevouts`. [3](#0-2) [4](#0-3) 

The only ownership check in `multisig` compares the offset group key’s script to `prevouts[i].script_pubkey`; it does not and locally cannot establish that the supplied `TxOut` is the real output at the supplied `OutPoint`. [5](#0-4) 

During signing, `Prevouts::All(&self.tx.prevouts)` commits to the attacker-supplied output amount and script, so altering the amount or script relative to the actual chain output changes the sighash. [6](#0-5) 

### Impact Explanation
An attacker who can provide serialized `ReceivedOutput` bytes can report a nonexistent, already-spent, or materially incorrect output as spendable balance. If the script remains the wallet’s script but the amount is forged, the threshold wallet can produce a transaction that consensus rejects because the BIP-341 prevout commitment does not match the actual UTXO. [7](#0-6) [6](#0-5) 

The practical result is funds reported as received that are not spendable, with potential wallet liveness loss if invalid records are used to fund transactions. [1](#0-0) 

### Likelihood Explanation
The exposed boundary is the explicitly supported `ReceivedOutput::read` API, so the input does not require a malicious validator, private-key access, or an invalid curve encoding. Exploitation requires an integrator or processor to deserialize an untrusted `ReceivedOutput` and subsequently use it to construct a `SignableTransaction`. [2](#0-1) [8](#0-7) 

Severity is Medium because the primitive can produce false spendable balance and invalid transactions, but it does not by itself reveal key shares or authorize spending another UTXO.

### Recommendation
Do not treat deserialized `ReceivedOutput` values as spendable without an authenticated UTXO proof or trusted scanner lineage.

At minimum:

1. Mark `ReceivedOutput::read` as serialization-only and prevent conversion of deserialized records into spendable inputs unless the outpoint has been resolved against consensus state.
2. Extend `SignableTransaction::new` or a wallet-facing wrapper to accept a verified UTXO lookup and compare the chain-returned `TxOut` byte-for-byte with the `ReceivedOutput.output`.
3. Track provenance in `ReceivedOutput`, such as block height/transaction position or an authenticated scanner record, rather than accepting an arbitrary `(TxOut, OutPoint)` pair.
4. Return a distinct `UnverifiedOutput` type from untrusted deserialization so `SignableTransaction::new` cannot accidentally consume it.

### Proof of Concept
The following demonstrates the root cause by mutating a scanned output’s serialized amount while retaining the legitimate script and outpoint:

```rust
// A legitimate output discovered by Scanner.
let real: ReceivedOutput = /* scanner output */;
let mut encoded = real.serialize();

// ReceivedOutput::write emits:
// [32-byte offset][consensus TxOut][consensus OutPoint].
// The TxOut amount is the first eight bytes after the offset.
let forged_value = real.value() + 1_000_000;
encoded[32 .. 40].copy_from_slice(&forged_value.to_le_bytes());

// Accepted without checking the outpoint's actual contents.
let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();

// The forged amount is counted as spendable balance.
let stx = SignableTransaction::new(
  vec![forged],
  &[(payment_script, payment_amount)],
  None,
  None,
  fee_rate,
).unwrap();

// Ownership validation passes because script_pubkey was unchanged.
let machine = stx.multisig(&keys).unwrap();
```

`ReceivedOutput::read` accepts the modified object because it does not bind `output` to `outpoint`. [9](#0-8) 

`SignableTransaction::new` places the real outpoint in the transaction input but stores the forged `TxOut` as the prevout used for sighash generation. [3](#0-2) [6](#0-5) 

Because `multisig` validates only the script against the offset group key, the forged amount is not detected before signing. [5](#0-4)
