### Title
Payment destinations in `SignableTransaction::new` are never validated, so user-supplied out instructions can irreversibly burn multisig funds to unspendable scripts - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Mirroring the SolverVaults issue where a withdrawal `receiver` is accepted unchecked and tokens are burned before an irreversible payout, `bitcoin-serai`'s `SignableTransaction::new` accepts each payment's `ScriptBuf` verbatim and builds a multisig-signed transaction sending funds to it, with no validation that the destination script is standard, well-formed, or spendable.

### Finding Description
`SignableTransaction::new` iterates `payments: &[(ScriptBuf, u64)]` and copies each `script_pubkey` directly into the transaction outputs. [1](#0-0) 

The only checks applied are dust amount (`< DUST`), total funds sufficiency, fee rate, and transaction weight. [2](#0-1) [3](#0-2) [4](#0-3) 

There is no validation that the destination script is a recognized/standard script type (P2TR/P2WPKH/etc.), is non-empty, or is even spendable. The `TransactionMachine`/`TransactionSignMachine` then has the whole FROST threshold sign `taproot_key_spend_signature_hash` over `Prevouts::All` committing to these outputs. [5](#0-4) 

Likewise, the optional `change` script is used unchecked. [6](#0-5) 

The spec confirms the design stance: "No validation of external addresses/data is performed on-chain." [7](#0-6) 

A user's burn/out-instruction supplies the external address; the processor converts it into a `ScriptBuf` payment and the multisig signs it. Once broadcast, the spend is irreversible — there is no edit/cancel path, exactly as in the reported bug class.

### Impact Explanation
A user (or anyone relaying a malformed out-instruction on their behalf) can cause the threshold network to sign a transaction paying to a garbage, non-standard, or unspendable `script_pubkey` (e.g., a provably-burned `OP_RETURN`-style script, a malformed witness program, or a script for the wrong network encoding). The funds are destroyed/locked forever; the user's Serai-side coins were already burned, and no recovery or amendment mechanism exists. Analogous to the original report, the loss is borne by the requester, so the practical severity is Medium rather than a theft vector — but mistakes are unrecoverable and undetectable until the signed tx confirms.

### Likelihood Explanation
Any unprivileged user issuing a burn/out-instruction with a malformed or mistyped external address reaches this path: `Payment::read` only requires `N::Address::try_from` on raw bytes, and `SignableTransaction::new` performs no destination sanity check before signing. Fat-fingered addresses that deserialize but encode a wrong script, or encodings accepted by `try_from` yet unspendable on Bitcoin, will be signed and broadcast by the honest threshold.

### Recommendation
In `SignableTransaction::new` (or at the `Payment` → `ScriptBuf` boundary in the processor), validate each payment script: reject empty/non-standard scripts, require recognized templates (P2TR, P2WPKH/P2WSH, P2PKH/P2SH) with correct program lengths, and reject provably-unspendable outputs carrying nonzero value. Additionally record the request initiator so a payout to an unclaimed/unspendable destination can be reverted within a timeout, mirroring the upstream recommendation.

### Proof of Concept
```rust
// In-scope path: networks/bitcoin/src/wallet/send.rs
// Construct payments with an unspendable script_pubkey carrying real value.
let burn_script = ScriptBuf::new_op_return(PushBytesBuf::try_from(b"lost".to_vec()).unwrap());
let payments = vec![(burn_script, 100_000u64)]; // passes: amount >= DUST
let stx = SignableTransaction::new(inputs, &payments, None, None, fee_per_vbyte).unwrap();
// stx.multisig(keys) -> sign -> complete produces a valid, signable TX
// whose output is provably unspendable; the threshold will sign it and the
// funds are permanently burned with no cancellation path.
```
No code path between `SignableTransaction::new` and the produced witness signatures inspects the destination script's spendability.
