### Title
ProtoJSON `Any.@type` field bypasses XSS-hardening escaping used for all other string fields - (File: `java/util/src/main/java/com/google/protobuf/util/JsonFormat.java`)

### Summary
Devise Token Auth's flaw was a Rails controller reflecting an attacker-controlled `message` parameter into an HTML/JS response without proper output encoding, enabling reflected XSS (`fallback_render`, CVE-2019-16751). The transferable invariant is "attacker-controlled string data must be output-encoded for every context it may be consumed in before being emitted from a supported public API." Java `JsonFormat.printer()` deliberately hardens `STRING` fields against exactly this class of downstream HTML/JS embedding by escaping `<`, `>`, `&`, `=`, `'` in addition to standard JSON escapes (see the comment "escaped to prevent XSS risks" at lines 1583-1591). However, the `Any.type_url` field, which is fully attacker-controlled (it comes straight from a client-supplied binary Protobuf or ProtoJSON `Any` message parsed via `JsonFormat.parser()` / `Message.parseFrom`), is emitted via `gson.toJson(typeUrl)` in both `printAny` (line 1067) and the generic message printer (line 1307), completely bypassing `printStringEscapedAndQuoted`/the XSS-safe replacement table.

### Finding Description
`printSingleFieldValue` routes every `STRING`-typed field value through `printStringEscapedAndQuoted`, which consults `getReplacementOrNull` and replaces `<`, `>`, `&`, `=`, `'` with `\u003c`, `\u003e`, `\u0026`, `\u003d`, `\u0027` respectively — this exists specifically so that ProtoJSON output remains safe if later embedded in an HTML `<script>` context by a consuming application [1](#0-0) [2](#0-1) . But `type_url`, itself just a plain `STRING` field on the `Any` well-known type, never enters that code path when printed as the `@type` key: `printAny` writes `"\"@type\":" + blankOrSpace + gson.toJson(typeUrl) + ","` directly [3](#0-2) , and the fallback "unknown type" printer does the same via `generator.print("\"@type\":" + blankOrSpace + gson.toJson(typeUrl));` [4](#0-3) . `Gson`'s default `toJson` for a `String` only escapes `"`, `\`, and control characters — not `<`/`>`/`&`/`'`/`=` — so an attacker who controls the bytes of a `google.protobuf.Any.type_url` field (trivial: it's just length-prefixed bytes in the wire format, or a JSON string in ProtoJSON input) can inject those characters verbatim into the printed `@type` value.

### Impact Explanation
If the application takes the result of `JsonFormat.printer().print(...)` on a message containing an attacker-supplied `Any` (a common pattern for generic/plugin/event payloads) and embeds that JSON text into an HTML page or a `<script>` block — exactly the scenario the existing `<`/`>`/`&` escaping in `printStringEscapedAndQuoted` was added to prevent — the unescaped `@type` value can break out of the string literal/JSON context and inject markup or script, i.e., a reflected XSS in the consuming application's rendering surface. This mirrors the "unauthenticated attacker crafts a URL value that is reflected unescaped into a browser context" pattern of GHSA-mvqr-r76c-wm5f. Severity is limited to Medium because the impact requires (a) the client-side application to actually render `type_url`-derived JSON as HTML/JS, which is application-specific, and (b) it is fully consistent with the transferred CWE-79/reflected-XSS impact class of the report — client-side script injection in a browser context, not memory corruption or RCE.

### Likelihood Explanation
Likelihood is Medium: `type_url` is a completely attacker-controlled string with no format validation before printing (only used as a lookup key in the `TypeRegistry`), reachable through the standard public `JsonFormat.printer().print()` API on any message that (transitively) contains a `google.protobuf.Any` field — a very common pattern for polymorphic protobuf payloads (e.g., generic gRPC error details, event envelopes). No additional privilege or malicious schema is required; a bounded, valid `Any` submessage from an ordinary client is sufficient.

### Recommendation
Route the `@type` value through the same `printStringEscapedAndQuoted` (or equivalent) escaping used for all other `STRING` fields instead of `gson.toJson`, in both `printAny` and the generic `print(message, typeUrl)` path, so that `<`, `>`, `&`, `'`, `=` are consistently escaped for every string emitted by `JsonFormat`.

### Proof of Concept
Construct (conceptually — not executed in this analysis) an `Any` message where `type_url` is set to a value such as `type.googleapis.com/foo</script><script>alert(1)</script>` (this is a plain length-delimited string field in the wire format, so no validation prevents arbitrary bytes). Call `JsonFormat.printer().print(messageContainingAny)`. Because `printAny`/`print(message, typeUrl)` uses `gson.toJson(typeUrl)` rather than `printStringEscapedAndQuoted`, the resulting JSON's `"@type"` value will contain literal `<`, `>` characters unescaped (unlike every other string field printed by the same formatter, which would render them as `\u003c`/`\u003e`) — confirmable by comparing against the existing regression test `testHtmlEscape` for ordinary string fields [5](#0-4) , which passes only because it exercises `optionalString`, not `Any.type_url`. I was not able to execute this against a live build in this analysis; this is a code-level proof based on tracing the two distinct escaping code paths.
