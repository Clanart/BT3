## Finding

The report's core pattern — an **accounting value computed at time T₁ is silently reused/combined with fresh state recomputed at time T₂ without re-validating alignment**, causing an outcome the user did not intend — has a direct analog in GitHub Desktop's **partial-commit (line-selection) staging path**.

### Title
Stale line-selection indices applied against a freshly re-fetched diff during partial-commit staging can silently commit unreviewed content - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages a partial commit (selecting only some lines/hunks of a file), Desktop stores the selection as a set of *line indices relative to the diff that was on screen when the selection was made* (`WorkingDirectoryFileChange.selection`) [1](#0-0) . At actual commit time, `stageFiles` calls `applyPatchToIndex`, which does **not** reuse that diff — it re-fetches a brand-new diff straight from disk via `getWorkingDirectoryDiff` [2](#0-1)  and then builds the patch by indexing into the *new* diff's hunks using the *old* selection's line indices [3](#0-2) . If the file on disk changed between the moment the user reviewed/selected lines and the moment `_commitIncludedChanges` actually executes staging, the old (now-stale) index positions get reinterpreted against different hunk content.

### Finding Description
`_commitIncludedChanges` captures the file/selection snapshot synchronously from `repositoryStateCache` [4](#0-3)  and passes it straight to `createCommit` → `stageFiles` → `applyPatchToIndex` [5](#0-4) [6](#0-5) . Inside `applyPatchToIndex`, the diff used to build the actual `git apply --cached` patch is re-fetched from the working tree at that instant [7](#0-6) , not the diff the user actually looked at. `formatPatch` then calls `file.selection.isSelected(absoluteIndex)` where `absoluteIndex` is derived from the *new* diff's hunk offsets [3](#0-2) , but the selection bitmap itself was built against the *old* diff's line layout.

Desktop does have a partial mitigation for the **UI**: `updateChangesWorkingDirectoryDiff` revalidates selectable lines whenever the diff panel is reloaded (e.g., after a background status poll) [8](#0-7) . However, this revalidation only happens on discrete refresh events; there is no synchronous re-diff/re-validation immediately before `stageFiles` runs, and the guard comment even acknowledges the underlying idea only "settle[s] on just updating the selectable lines" heuristically rather than proving the selection still corresponds to the same content [9](#0-8) . Between the last background refresh and the user pressing "Commit," the on-disk file can change again, and that window is not re-checked before `applyPatchToIndex` fetches its own fresh diff.

### Impact Explanation
This can cause **silent corruption of what the user commits**: the git-apply patch built from stale indices against a differently-shaped diff can select unintended lines (including content the user never reviewed or explicitly excluded), or fail to include lines the user intended to commit. Since `git apply --unidiff-zero` is used with zero context lines [10](#0-9) , there is minimal opportunity for git itself to reject a mismatched patch by context-line failure, increasing the chance the corrupted patch applies "successfully" but with wrong content. This matches the "silent corruption of what the user commits or pushes" impact category exactly.

### Likelihood Explanation
This requires a narrow race: the tracked file must be modified on disk (same or overlapping line ranges) in the window between the user's last-reviewed diff and the actual commit execution, without an intervening status refresh invalidating the selection. This can be triggered by anything that rewrites files during active editing/staging — file watchers, formatters, build tools, or scripts included in a cloned/fetched repository (e.g., a `package.json` script or dev-server the project's README instructs the victim to run alongside Desktop). It does not require local malware, admin rights, or leaked credentials — only a repository whose tooling naturally touches tracked files during the commit workflow. Likelihood is moderate: it depends on specific timing and workflow, but the underlying missing invariant (stale selection reused against freshly fetched diff without alignment check) is a real, demonstrable gap in the code, not a theoretical one.

### Recommendation
Before calling `applyPatchToIndex`/`formatPatch`, re-fetch and re-validate that the diff used to build the selection bitmap is still equivalent (e.g., compare hunk boundaries/line hashes) to the diff about to be staged; if they differ, abort the partial-stage for that file and force the user to re-review, analogous to how `updateChangesWorkingDirectoryDiff` already treats a changed diff as invalidating stale line indices for display purposes [8](#0-7) . Alternatively, always re-fetch and re-validate immediately before staging rather than relying on the last background-refresh snapshot.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file to introduce two hunks (A and B).
2. In the Changes view, select only hunk A for a partial commit; Desktop stores that selection as indices against the currently displayed diff [1](#0-0) .
3. Before pressing "Commit," have an external process (e.g., a watch-mode formatter/build script bundled with the repository) rewrite the file so hunk B grows/shrinks in line count while hunk A's on-screen content is superficially unchanged. This shifts absolute line offsets without the app performing a synchronous re-diff.
4. Click "Commit." `_commitIncludedChanges` uses the old selection object [4](#0-3) ; `applyPatchToIndex` re-fetches a new diff from disk [7](#0-6)  and applies the stale index-based selection to the new hunk layout [3](#0-2) .
5. Inspect the resulting commit: it includes lines the user never selected/reviewed (from what is now misaligned hunk content), confirming silent corruption of the committed content relative to user intent.
