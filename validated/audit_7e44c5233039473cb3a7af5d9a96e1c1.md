### Title
Malformed `conditions:` YAML in hookify rule files silently parses to an empty list, making the rule permanently inert while `enabled: true` still displays - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter`'s hand-rolled YAML parser silently drops condition entries that omit the leading `-` list marker (or otherwise fail its narrow indentation heuristics), producing `frontmatter['conditions'] = []` with no error or warning. `Rule.from_dict` then sets `Rule.conditions = []`, and `RuleEngine._rule_matches`'s guard `if not rule.conditions: return False` makes the rule never fire for any input, even though the file visually looks like a fully specified, enabled security rule.

### Finding Description
`extract_frontmatter` in [1](#0-0)  parses the YAML `conditions:` block line-by-line using three exclusive branches: a top-level `key:` branch (`indent == 0`), a list-item branch that only fires when `stripped.startswith('-')`, and a continuation branch that only fires when `indent > 2 and in_dict_item`. If a rule author writes the conditions block without the leading dash — e.g.

```yaml
conditions:
  field: file_path
  operator: regex_match
  pattern: \.ts$
```

then after `conditions:` is seen, `in_list=True` but `in_dict_item=False`. The subsequent lines have `indent == 2`, don't start with `-`, and `in_dict_item` is false, so they match none of the branches in [2](#0-1)  and are silently skipped. At the end of parsing, `frontmatter['conditions']` is assigned the still-empty `current_list` ( [3](#0-2) ).

`Rule.from_dict` then sees `'conditions' in frontmatter` is true and `isinstance(cond_list, list)` is true, so it builds `conditions = [Condition.from_dict(c) for c in cond_list]` over an empty list, yielding `Rule.conditions == []` ( [4](#0-3) ). Because `pattern:` (legacy field) is absent, the legacy fallback in the same method never populates `conditions` either ( [5](#0-4) ).

`load_rule_file` performs no semantic validation that a rule intending block conditions actually produced any — it only checks that `frontmatter` itself is non-empty ( [6](#0-5) ), so the malformed file loads successfully, `enabled: true` is parsed correctly as a simple top-level key/value pair, and the rule is included by `load_rules` ( [7](#0-6) ).

Finally, `RuleEngine._rule_matches` unconditionally returns `False` whenever `rule.conditions` is empty ( [8](#0-7) ), so this rule can never block or warn on any tool call, Bash command, file edit, or Stop event, regardless of how dangerous the matched input is.

### Impact Explanation
A hookify rule intended to deny/block dangerous operations (e.g., `rm -rf`, writes to sensitive files, dangerous bash patterns) can be silently neutralized by a single indentation/formatting slip in its `conditions:` block — with `enabled: true` still shown and no parse error surfaced to the user. This directly violates "deny means deny": the operator believes a guardrail is active, but `_rule_matches` always returns `False`, so `evaluate_rules` returns `{}` (no block, no warning) for every input ( [9](#0-8) ). This is a false sense of protection that can be delivered via a cloned repository's `.claude/hookify.*.local.md` files or a plugin-generated rule template (e.g. from `create-plugin`) that an unprivileged contributor supplies, causing the victim's actual safety hooks to be dead code without their knowledge.

### Likelihood Explanation
This is highly feasible and repeatable: it only requires a rule file where the `conditions:` list items are written without the leading `-` (a very plausible, easily-introduced formatting mistake, or one an attacker can deliberately craft to look legitimate while being inert), and no special privileges beyond providing a file the victim loads via a cloned repo or generated template. The bug is deterministic given the parser logic — every rule file using this format will silently degrade to `conditions == []`.

### Recommendation
Rewrite `extract_frontmatter` to use a real YAML parser (e.g. `yaml.safe_load`) instead of the hand-rolled line-based state machine, eliminating this entire class of silent-parse-failure bugs. At minimum, add validation in `load_rule_file`/`Rule.from_dict` that rejects (with a loud warning, not silent skip) any rule where `'conditions' in frontmatter` but the resulting `Rule.conditions` list is empty and no legacy `pattern` is present — this configuration should be treated as a malformed/invalid rule file rather than a validly parsed rule with zero conditions.

### Proof of Concept
Add a unit test to `plugins/hookify/core/config_loader.py`'s test suite (or a new fuzz test):

```python
def test_conditions_without_dash_not_silently_empty():
    content = """---
name: block-rm-rf
enabled: true
event: bash
action: block
conditions:
  field: command
  operator: regex_match
  pattern: rm\\s+-rf
---

Blocked dangerous rm -rf command!
"""
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # Fails today: rule.conditions == [] even though the author
    # clearly intended one condition, making the rule permanently inert.
    assert rule.conditions, (
        "conditions block was silently dropped; rule will never match"
    )

    engine = RuleEngine()
    matched = engine._rule_matches(rule, {
        "tool_name": "Bash",
        "tool_input": {"command": "rm -rf /"}
    })
    assert matched is True, "block rule for rm -rf did not fire"
```

A broader fuzz test can generate random combinations of dash-presence/indentation for `conditions:` blocks and assert that whenever the source YAML clearly specifies at least one `field/operator/pattern` triple, `Rule.conditions` produced by `Rule.from_dict(*extract_frontmatter(content))` is non-empty.
