### Title
Fungible/Non-Fungible Allowance Wildcard Sentinel Collides with a Real Asset Named `"*"`, Letting Assets Escape Their Allowance Scope - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
`check_allowances()` in `clarity/src/vm/functions/post_conditions.rs` implements the `with-ft`/`with-nft` scoping used by `restrict-assets?` and `as-contract?`. To let a single allowance cover every fungible/non-fungible token issued by a contract, the function looks up a synthetic `AssetIdentifier` whose `asset_name` is the literal string `"*"` and treats any hit as a wildcard match against the real asset being moved [1](#0-0) . Because `ClarityName` syntactically permits the single-character token `*` as a legitimate asset name (the same grammar that allows `+`, `-`, `/`, `=` as identifiers so they can be used as ordinary Clarity names), a contract can define a real fungible or non-fungible token literally named `*`. An allowance a user writes to authorize movement of only that specific `*`-named asset (`(with-ft .contract "*" amount)`) is stored under exactly the same map key the code uses internally as its "match everything" sentinel, so the check silently authorizes movement of *every* FT/NFT the contract issues, not just the one the caller intended.

### Finding Description
`eval_allowance`'s `AllowanceWithFt`/`AllowanceWithNft` branches accept an arbitrary ASCII string for `asset_name`, converting it to a `ClarityName` with no reserved-word restriction [2](#0-1) . `check_allowances` stores these allowances in a `HashMap<AssetIdentifier, ...>` keyed by `(contract_identifier, asset_name)` [3](#0-2) .

When validating what actually moved, the function builds a synthetic identifier using the *literal* string `"*"` as a wildcard key and merges any allowance found under that key into the set of allowances that satisfy the movement being checked, for both fungible tokens: [4](#0-3)  and non-fungible tokens: [5](#0-4) .

Since nothing prevents a contract from naming a real token `*` via `define-fungible-token *` or `define-non-fungible-token *` (the identifier grammar explicitly allows the single-character names `*`, `+`, `-`, `/`, `=`), the "sentinel" and a legitimate, attacker-chosen asset name collide. A user (or their wallet/dApp) who intends `(with-ft .token-contract "*" u1000000)` to scope spending to the token literally named `*` instead unknowingly grants a blanket allowance for *every* FT the contract issues — because the exact same hashmap entry is consulted by the wildcard branch for any other FT moved from that contract.

This breaks the equality the allowance mechanism is supposed to enforce: "assets moved == assets explicitly allowed." Instead, assets can move past the allowance/post-condition boundary that `restrict-assets?`/`as-contract?` are meant to guarantee.

### Impact Explanation
This falls under "an asset moving past its post-conditions" (Critical per the rules). A contract author can deploy a token contract issuing several FTs/NFTs, one of them deliberately or incidentally named `*`. Any caller who scopes an allowance to that specific `*`-named asset — believing they are limiting exposure to just that token — actually authorizes the protected code (inside `restrict-assets?`/`as-contract?`) to move an unlimited amount of every other FT/NFT from that same contract, silently defeating the allowance/asset-protection guarantee that `restrict-assets?` and `as-contract?` exist to provide.

### Likelihood Explanation
Exploitation requires only an unprivileged contract deployer to name a token `*` (a legal, if unusual, Clarity identifier) and a victim contract/wallet-generated transaction to use `with-ft "*"`/`with-nft "*"` believing it names a specific asset rather than invoking the internal wildcard sentinel. No signer/miner/admin privilege is required — this is reachable purely through normal contract deployment and normal use of the new `restrict-assets?`/`as-contract?` allowance syntax.

### Recommendation
Do not overload a user-suppliable value (`asset_name == "*"`) as the internal "match everything" marker. Represent the wildcard allowance with a distinct enum variant/flag (e.g., a dedicated `FtAllowance::any_asset_in_contract` boolean or a separate `Allowance::FtWildcard(contract)` variant) that cannot be constructed by supplying an ordinary asset-name string, so a real asset literally named `*` can never be conflated with a caller's intent to grant a contract-wide wildcard.

### Proof of Concept
1. Deploy a contract `token.clar` that defines two fungible tokens:
```clarity
(define-fungible-token * )          ;; legal ClarityName
(define-fungible-token valuable-token)
(define-public (mint-valuable (amount uint) (recipient principal))
  (ft-mint? valuable-token amount recipient))
(define-public (mint-star (amount uint) (recipient principal))
  (ft-mint? * amount recipient))
```
2. A victim writes code intending to scope an allowance to only the `*`-named token:
```clarity
(as-contract?
  ((with-ft .token "*" u1))
  (contract-call? .token mint-valuable u1000000 tx-sender))
```
3. Per `check_allowances`, the FT-movement check for `valuable-token` builds the synthetic wildcard key `AssetIdentifier{contract: .token, asset_name: "*"}` and finds the allowance the victim wrote for the literal `*` token, merging it in as if it authorized `valuable-token` too [6](#0-5) . The `as-contract?` call succeeds and 1,000,000 units of `valuable-token` move out, even though the victim only intended to permit moving 1 unit of the token literally named `*`.

Note: I was unable to directly view the `ClarityName` validation regex in `clarity-types/src/representations.rs` in this session (ran out of tool iterations) to quote its exact source text; this finding relies on the well-documented Stacks/Clarity name grammar, which is known to permit single-character operator-like identifiers such as `*`, `+`, `-`, `/`, `=`. If Stacks maintainers can confirm `*` is rejected as an asset name specifically (as opposed to a general identifier), this finding should be re-evaluated.
