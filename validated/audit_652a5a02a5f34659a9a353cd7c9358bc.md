### Title
Objective-C `skipMessage`/`skipField:` recursion into nested unknown groups bypasses `recursionDepth` limit enforcement - (File: objectivec/GPBCodedInputStream.m)

### Summary
The Sherlock finding's root defect is a state variable (`allocator.voiceCredits`) that exists specifically to be checked against a hard cap on every call, but the code path that is actually exercised never updates it, so the enforcement is a no-op and the invariant "cumulative usage ≤ cap" never holds. The structural analog in this Protobuf checkout is `GPBCodedInputStream`'s `state_.recursionDepth` counter: it is correctly checked and incremented/decremented on every message/group/map-entry parsing path (`readMessage:`, `readGroup:message:`, `readMapEntry:...`), but the "skip an unknown/unrecognized group field" path (`-skipField:` → `-skipMessage`) recurses into nested groups without ever calling `CheckRecursionLimit` or touching `state_.recursionDepth` at all.

### Finding Description
`CheckRecursionLimit`/`state_.recursionDepth` is the security invariant that bounds nested-message/group depth to `kDefaultRecursionLimit` (100) to prevent uncontrolled recursion on attacker-supplied wire bytes: [1](#0-0) 

Every "real" descent path enforces and tracks this invariant correctly, e.g. `readMessage:`, `readGroup:message:`, and `readMapEntry:...`: [2](#0-1) [3](#0-2) 

However, `-skipField:` for a `GPBWireFormatStartGroup` tag calls `-skipMessage` directly — with no call to `CheckRecursionLimit` and no increment of `state_.recursionDepth` — and `-skipMessage` loops on `-skipField:` again, so nested unknown/unregistered `START_GROUP`/`END_GROUP` pairs recurse purely through native Objective-C call frames with zero bookkeeping against the recursion budget: [4](#0-3) [5](#0-4) 

This is exactly the same class of bug as the reported issue: the accounting variable that is supposed to be updated on every relevant call (`allocator.voiceCredits` / `state_.recursionDepth`) is skipped on one specific, reachable code path (`_allocate` / skip-unknown-group), so the "limit" check that exists elsewhere in the code becomes vacuous for that path. Just as an ordinary allocator can call `Allo.allocate` repeatedly without ever exhausting `maxVoiceCreditsPerAllocator`, an ordinary client can send a bounded, well-formed-at-the-wire-level binary Protobuf message consisting purely of unknown/skippable `START_GROUP` fields nested arbitrarily deep, and the parser will recurse without ever hitting `kDefaultRecursionLimit`, because the enforcement variable is never incremented on this path.

### Impact Explanation
An attacker who controls bytes fed to any public Objective-C parse entry point (`-parseFromData:`/`GPBMessage` `mergeFrom...`, which internally builds unknown fields via `GPBCodedInputStream`) can force unbounded native call-stack recursion using only nested unknown `START_GROUP`/`END_GROUP` tag pairs — no large payload, no huge allocation, just deep nesting, defeating the intended, explicitly-designed recursion-depth cap (`kDefaultRecursionLimit = 100`). Depending on stack size and platform, this manifests as a stack overflow inside the process handling the message (crash of the consuming application's Protobuf-decoding thread), the same category of impact the recursion limit was added to prevent for the "normal" message/group/map-entry paths. Unlike an ordinary memory-growth DoS, this is a direct bypass of an existing, purpose-built safety check due to a missing increment in one path, mirroring the audited bug's "check exists but the accumulator feeding it is never touched" pattern.

### Likelihood Explanation
High. Producing nested, unknown `START_GROUP` fields is trivial hand-crafted wire-format data (tag = `(field_number << 3) | 3`, immediately followed by another such tag, repeated, then matching `END_GROUP` tags) — no special schema knowledge, no compiler/plugin access, and no privileged position is required; it is exactly the kind of input an "ordinary client sending bounded binary Protobuf through a supported public parse API" can supply. The bug is reachable any time the parsed message type does not define the given field number as a group/message (so it falls into the unknown-field skip path), which is common for any message with fewer/older fields than the tag numbers used by the attacker.

### Recommendation
In `objectivec/GPBCodedInputStream.m`, make `-skipField:`'s `GPBWireFormatStartGroup` case call `CheckRecursionLimit(&state_)` and increment/decrement `state_.recursionDepth` around the `[self skipMessage]` call, exactly as `readGroup:message:` and `readMessage:extensionRegistry:` already do, e.g.:
```objc
case GPBWireFormatStartGroup:
  CheckRecursionLimit(&state_);
  ++state_.recursionDepth;
  [self skipMessage];
  --state_.recursionDepth;
  GPBCodedInputStreamCheckLastTagWas(...);
  return YES;
```

### Proof of Concept
Construct a binary payload consisting solely of `N` nested unknown groups on a field number not defined by the target message's schema, e.g. for field number 15 (arbitrary, unused by the schema):
- Tag byte for `START_GROUP` on field 15: `(15 << 3) | 3 = 123` (`0x7B`)
- Repeat this tag byte `N` times (e.g., `N = 100000`), then append `N` matching `END_GROUP` tag bytes: `(15 << 3) | 4 = 124` (`0x7C`)

Feeding this buffer to any `GPBMessage` `parseFromData:` / `mergeFromData:` call where the message does not define field 15 drives execution into `-skipField:` → `-skipMessage` → `-skipField:` recursively `N` times with `state_.recursionDepth` remaining at 0 throughout (verifiable by instrumenting/logging `state_.recursionDepth` inside `-skipMessage`), in contrast to the same nesting depth applied to a schema-defined group field, which would throw `GPBCodedInputStreamErrorRecursionDepthExceeded` after 100 levels via `CheckRecursionLimit`. I was not able to execute this against a live build in this environment (read-only code index), so severity should be confirmed by an engineer running this payload against an Objective-C target and observing whether the process crashes via stack overflow at a depth well beyond `kDefaultRecursionLimit` (100).
