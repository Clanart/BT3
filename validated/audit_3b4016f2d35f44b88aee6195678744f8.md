### Title
Unauthenticated disclosure of encrypted emergency-stop transactions via `internal_get_emergency_stop_tx` when `client_verification=false` - ([File: core/src/rpc/interceptors.rs])

### Summary
`ClementineAggregator::internal_get_emergency_stop_tx` is meant to be reachable only by the aggregator's own certificate, enforced by `only_aggregator_and_self`'s `is_internal` branch. When `client_verification=false`, `servers.rs` installs the `Noop` interceptor instead, which passes every request through unconditionally regardless of method prefix, so the "internal-only" restriction never executes and any unauthenticated caller can invoke this method.

### Finding Description
The binding that should hold is: `reachable(internal_get_emergency_stop_tx) == (peer_leaf_cert == our_cert)`, enforced only inside `only_aggregator_and_self` at [1](#0-0) . This check is entirely bypassed when the interceptor installed is `Noop`, which just returns `Ok(req)` for any request: [2](#0-1) .

Which interceptor is installed is controlled purely by `config.client_verification` in `create_grpc_server`: if true, `OnlyAggregatorAndSelf` is built from configured certs; if false, `Noop` is used with no other substitute check [3](#0-2) . There is no fallback authentication (e.g., no re-check of `is_internal` outside of the `OnlyAggregatorAndSelf` variant), so when `client_verification=false` the "Internal"-prefixed methods -- which are supposed to be self-only regardless of general aggregator/verifier access rules -- become fully public, reachable by anyone who can open a gRPC connection to the aggregator's port. This includes `InternalGetEmergencyStopTx`, which builds and returns encrypted emergency-stop transactions for attacker-supplied `move_txid`s, letting anyone enumerate on-chain move-to-vault confirmations and fetch the corresponding encrypted emergency-stop artifacts ahead of their intended reveal.

### Impact Explanation
This is a premature disclosure of a protocol commitment (the encrypted emergency-stop transaction), which matches the High-severity category defined in the rules ("premature disclosure of a protocol commitment"). It does not directly move BTC or forge signatures, so it does not rise to Critical, but it defeats the intended caller-authority restriction for an entire class of `Internal`-prefixed aggregator RPCs whenever `client_verification=false`, and is repeatable across every deposit whose `move_txid` is public (all confirmed deposits).

### Likelihood Explanation
The only precondition is that the deployment runs the aggregator with `client_verification=false` -- a configuration flag that exists and is exercised in this codebase (`BridgeConfig.client_verification`, referenced in `servers.rs` and test config `core/src/test/data/bridge_config.toml`). Given that precondition, the attack costs nothing beyond a plain gRPC connection: no Bitcoin transaction, no fees, no privileged role. It is fully repeatable for any number of deposits.

### Recommendation
Do not rely solely on TLS-peer-cert interception for internal-method gating; enforce the internal-only restriction independent of `client_verification`. For example, always check `is_internal(&req)` and reject with `Unauthenticated`/`PermissionDenied` when the interceptor is `Noop` (or otherwise ensure `Internal`-prefixed methods are never exposed on a public-facing service/port, e.g., by serving them on a separate internal-only listener that is always used regardless of `client_verification`).

### Proof of Concept
```rust
// core/src/rpc/aggregator_internal_auth_test.rs (illustrative)
#[tokio::test]
async fn internal_get_emergency_stop_tx_unauthenticated_when_client_verification_false() {
    // Start aggregator with client_verification = false (Noop interceptor path)
    let mut config = create_test_config().await;
    config.client_verification = false;
    let (addr, _shutdown) = create_aggregator_grpc_server(config).await.unwrap();

    // Connect without any client certificate (unauthenticated channel)
    let mut client = get_unauthenticated_aggregator_client(addr).await;

    let resp = client
        .internal_get_emergency_stop_tx(GetEmergencyStopTxRequest {
            txids: vec![known_move_txid.into()],
        })
        .await;

    assert!(resp.is_ok());
    assert!(!resp.unwrap().into_inner().encrypted_emergency_stop_txs.is_empty());
}

#[tokio::test]
async fn internal_get_emergency_stop_tx_rejected_when_client_verification_true() {
    let mut config = create_test_config().await;
    config.client_verification = true;
    let (addr, _shutdown) = create_aggregator_grpc_server(config).await.unwrap();

    let mut client = get_unauthenticated_aggregator_client(addr).await; // no matching cert

    let resp = client
        .internal_get_emergency_stop_tx(GetEmergencyStopTxRequest {
            txids: vec![known_move_txid.into()],
        })
        .await;

    assert!(matches!(resp, Err(status) if status.code() == tonic::Code::Unauthenticated));
}
```

Note: I was unable to directly view the body of `internal_get_emergency_stop_tx` in `core/src/rpc/aggregator.rs` within available tool calls (search results confirmed its existence and the method name matched in `only_aggregator_and_self`'s `is_internal` gating logic, but the full handler implementation was not retrieved). This does not affect the finding, since the vulnerability is in the authorization bypass at the interceptor layer (`Noop` vs `OnlyAggregatorAndSelf`), independent of the handler's internal logic.
