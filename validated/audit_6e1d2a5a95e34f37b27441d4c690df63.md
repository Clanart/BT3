### Title
Full node crash via oversized `CREATE_COIN` hint/memo bypassing the unenforced 32-byte precondition - (File: `chia/full_node/hint_management.py`)

### Summary
`get_hints_and_subscription_coin_ids()` documents a *comment-only* precondition ("all hints passed in are max 32 bytes long") and then asserts it in code (`assert len(hint) <= 32`). Nothing on the actual admission/validation path (mempool admission or block body validation) truncates or rejects a `CREATE_COIN` memo/hint longer than 32 bytes. A spend bundle with an oversized third `CREATE_COIN` argument can be admitted to the mempool, included in a block by any farmer, and once that block becomes the new peak, `FullNode.peak_post_processing()` calls this function under `blockchain.priority_mutex` and hits the assertion, crashing the full node process. This mirrors the reported Squid pattern: a size limit assumed to be enforced upstream is not actually enforced, and the oversized item causes a crash when it reaches the downstream caching/processing code that trusts the limit.

### Finding Description
- CLVM `CREATE_COIN` conditions accept an arbitrary-length third argument (the memo/hint atom). Neither `chia/full_node/mempool_manager.py::validate_spend_bundle()` nor `chia/consensus/block_body_validation.py` enforce a 32-byte cap on this value; the only cost constraint is the generic `COST_PER_BYTE` charge, which permits atoms far larger than 32 bytes within `MAX_BLOCK_COST_CLVM`. [1](#0-0) 
- `ForkInfo.include_spends()` forwards the raw `hint` value from `spend.create_coin` into `ForkAdd` without any length validation, and this flows into `StateChangeSummary.additions`. [2](#0-1) 
- `get_hints_and_subscription_coin_ids()` only *comments* that hints are precondition-guaranteed to be ≤32 bytes, then hard-asserts it for any non-empty hint, with no graceful handling of a violation: [3](#0-2) 
- This function is invoked from `FullNode.peak_post_processing()`, which runs under `self.blockchain.priority_mutex` for every new peak (including normally farmed blocks, not just attacker-controlled ones): [4](#0-3) 
- Wallet-side code (`compute_spend_hints_and_additions`) does check `len(potential_hint) == 32` before treating a value as a hint, but that check is client convenience logic, not a consensus/mempool validation rule, so it provides no protection against a maliciously crafted spend bundle: [5](#0-4) 

The result is the same bug class as CVE-2023-5824: a size limit assumed to already be enforced ("precondition") is not actually validated at admission, and the oversized object later reaches code that unconditionally relies on the limit, causing a crash (assertion failure) instead of a controlled rejection.

### Impact Explanation
An `AssertionError` inside `peak_post_processing()`, called while holding `blockchain.priority_mutex`, will propagate up and crash (or leave in a corrupted/stalled state) the full node process that processes the offending block. Since this runs on every full node that accepts the block as its new peak, a single spend bundle can cause a network-wide denial of service against any node that syncs the block containing it — a spend-triggered transaction-processing halt, which is explicitly in scope as an acceptable impact.

### Likelihood Explanation
Likelihood is high: an unprivileged wallet/spend-bundle submitter only needs to construct a `CoinSpend` whose puzzle produces a `CREATE_COIN` condition with a memo/hint atom longer than 32 bytes (trivial with any custom puzzle, e.g. `(51 <ph> <amount> ("...>32 bytes..."))`), pay ordinary CLVM cost for the larger atom, and submit it via `push_tx`/`respond_transaction`. No special mempool bypass is required — the value only needs to survive mempool/body validation, both of which are silent on hint length. Once any farmer includes the bundle in a block, every node that processes that block as its new peak crashes deterministically.

### Recommendation
Enforce (and reject, not assert) a maximum hint/memo length at spend-bundle admission (`MempoolManager.validate_spend_bundle`) and in block body validation, mirroring the wallet-side 32-byte convention, so oversized hints are refused before entering the mempool/chain. Additionally, harden `get_hints_and_subscription_coin_ids()` to defensively truncate/drop hints longer than 32 bytes instead of asserting, so that even if an oversized hint somehow reaches this function (e.g. via a future code path or database import), it cannot crash `peak_post_processing()`.

### Proof of Concept
1. Craft a `CoinSpend` whose puzzle solution returns `(CREATE_COIN <puzzle_hash> <amount> (<hint_bytes_of_length_64>))`, e.g. using the identity puzzle: `Program.to([[51, puzzle_hash, amount, [b"A" * 64]]])`.
2. Build a `SpendBundle` with this coin spend and submit it via `push_tx`/`respond_transaction`; confirm it passes mempool admission (no length check occurs in `validate_spend_bundle`, see `chia/full_node/mempool_manager.py:748-763`).
3. Farm a block including this transaction (e.g. in a simulator via `farm_new_transaction_block`).
4. Observe that when the full node processes the resulting new peak, `FullNode.peak_post_processing()` calls `get_hints_and_subscription_coin_ids()` (`chia/full_node/full_node.py:2060-2065`), which raises `AssertionError` on `assert len(hint) <= 32` (`chia/full_node/hint_management.py:47-49`), crashing the peak-processing path under `blockchain.priority_mutex`.
