### Title
Unauthenticated OP_RETURN operator-attribution in payout tx lets anyone frame an operator into fronting a payout it never made - ([File: circuits-lib/src/bridge_circuit/mod.rs])

### Summary
`parse_op_return_data` (`circuits-lib/src/bridge_circuit/mod.rs:608-617`) blindly returns the first push-data after `OP_RETURN` in a payout transaction, and `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) stores those bytes verbatim as `payout_payer_operator_xonly_pk` with zero cryptographic binding to whoever actually funded the withdrawal. Because the payout tx's user signature only covers the withdrawal input and the user-output (`SIGHASH_SINGLE|ANYONECANPAY`), the OP_RETURN output is unsigned and attacker-controlled, letting anyone front their own withdrawal while naming an arbitrary registered operator as the "payer."

### Finding Description
The claimed binding is: `payout_payer_operator_xonly_pk` (DB column populated from OP_RETURN bytes of the on-chain payout tx) == the operator whose private key/collateral actually funded (fronted) that withdrawal.

Trace:
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout tx with 3 outputs: user payout (idx 0), anchor (idx 1), OP_RETURN with an xonly-pk (idx 2). It signs only input 0 with `user_sig`.
- The user's signature is required to use `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:161-187`), which per BIP-341 covers only the spent input and the single output at the same index (output 0). Outputs 1 (anchor) and 2 (OP_RETURN) are **not covered** by this signature.
- Consequently, whoever broadcasts the payout tx — using the user-provided `input_outpoint`/`in_signature` and adding their own funding inputs via `fund_raw_transaction` (`core/src/operator.rs:560-674`) — can freely choose the OP_RETURN bytes. Nothing requires the OP_RETURN xonly-pk to correspond to the party who supplied the additional funding inputs.
- `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) scans the payout tx, calls `parse_op_return_data`/`XOnlyPublicKey::from_slice`, and stores whatever 32 bytes are found as `payout_payer_operator_xonly_pk` — with no signature check, no proof-of-funding check, and no requirement that the named pubkey correspond to anything real beyond being a valid x-only point.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:31-111`) runs per-operator and calls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` (`core/src/database/verifier.rs:282-313`). If an attacker's OP_RETURN names a victim operator's real xonly_pk, the victim's *own* automation will pick this up as "its" unhandled payout.
- It then calls `Operator::handle_finalized_payout` (`core/src/operator.rs:839-916`), which grabs an unused, already-presigned kickoff connector for that deposit belonging to the operator's real signing key (`get_unused_and_signed_kickoff_connector`) and creates and broadcasts a *real*, validly-signed Kickoff tx using the victim operator's own protocol keys/collateral.
- Eventually `create_reimburse_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:341-385`) spends the deposit's `MoveToVault` `DepositInMove` output (the real bridge funds for that specific deposit) directly to the operator's reimbursement address.
- `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) only checks that `operator_xonly_pk` from the (attacker-controlled) OP_RETURN equals `kickoff_data.operator_xonly_pk` (the operator who sent the kickoff) — it never checks that this operator actually put up capital on L1 for the withdrawal. Since the victim operator sent the kickoff using its own key (believing it was the payer), this check trivially passes.

No existing guard (`is_kickoff_malicious`, `validate_payer_is_operator`, `SECP.verify_schnorr` on the user's `SinglePlusAnyoneCanPay` signature, or the presigned transaction graph) ties the OP_RETURN pubkey to the entity that supplied the actual withdrawal funds. The signature verification in `Operator::withdraw`/aggregator `withdraw` only authenticates the withdrawer's intent for the input/output-0 pair, never the payer identity in OP_RETURN.

### Impact Explanation
An attacker who is also the withdrawer can self-fund their own withdrawal payout (from their own wallet, to their own destination) yet frame any registered operator by writing that operator's real xonly_pk into the unsigned OP_RETURN output. The framed operator's own automation (`PayoutCheckerTask`) will legitimately execute a full kickoff/reimburse cycle for a payout it never funded, ultimately spending real BTC out of the deposit's move-to-vault UTXO into the framed operator's reimbursement address. This matches the Critical category "an operator reimbursed for a payout it never funded" (and, depending on who else expected to be reimbursed for that same deposit, can also result in "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" from that operator's own capital). This is repeatable for every deposit/withdrawal where the attacker controls the withdrawal request and knows any registered operator's public xonly_pk (which is public protocol metadata).

### Likelihood Explanation
The attacker only needs to be a normal, unprivileged user who can: deposit into the bridge, call `withdraw` on the Citrea bridge contract (choosing their own `input_outpoint`/signature/output), and broadcast a Bitcoin transaction. No verifier, operator, or aggregator privilege is required, and no signature forgery is needed — the OP_RETURN is simply unsigned data. Every registered operator's xonly_pk is public. The only cost is the attacker's own withdrawal-front funds (which they recover to themselves) plus normal transaction fees, making this cheap and fully repeatable per deposit.

### Recommendation
Bind the OP_RETURN operator attribution to something cryptographically verifiable: e.g., require the operator's Schnorr signature over the payout tx (or over the OP_RETURN payload) using a sighash that also covers the OP_RETURN output, or otherwise have the verifier only trust `payout_payer_operator_xonly_pk` when it is provably signed/committed by that operator, instead of storing raw OP_RETURN bytes as authoritative "payer" metadata. Additionally `handle_finalized_payout`/`PayoutCheckerTask` should not treat DB `payout_payer_operator_xonly_pk` as sufficient evidence of funding without corroborating proof (e.g. that the operator's own wallet actually supplied the extra payout inputs).
