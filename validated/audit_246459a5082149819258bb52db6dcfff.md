## Analog Identified: Automatic `DeleteTokenPair` on ERC20 "self-destruct detection" corrupts 1:1 coin-backing invariant

The `cancelPromotion` bug class is: a state-clearing operation (`delete _promotions[_promotionId]`) is executed unconditionally on a terminal event, wiping out bookkeeping needed to reconcile/settle already-accrued value, with no fallback to let it be claimed or reconciled. The Cosmos EVM analog is the automatic, unconditional `DeleteTokenPair` call embedded inside `ConvertERC20`/`ConvertCoin` in `x/erc20`.

### Title
Unconditional `DeleteTokenPair` on "self-destructed" native-ERC20 pairs wipes pair/allowance bookkeeping while leaving already-minted, 1:1-backed native coins outstanding - ([File: x/erc20/keeper/msg_server.go])

### Summary
`ConvertERC20` and `ConvertCoin` each contain a side check: if the paired ERC20 contract account is `nil` or has no code hash, the keeper silently calls `k.DeleteTokenPair(ctx, pair)` and returns `nil, nil` (success) instead of erroring. [1](#0-0) [2](#0-1) 

`DeleteTokenPair` removes the pair record, the ERC20-address map, the denom map, **and** all allowances in one shot: [3](#0-2) 

### Finding Description
For a "native ERC20" pair (`pair.IsNativeERC20()`), the conversion flow escrows the external ERC20 token balance into the module account and mints/burns a 1:1-backed native bank coin against it: [4](#0-3) 

The escrowed-balance accounting (`balances[moduleAddr]`) lives entirely inside the ERC20 contract's own storage. When that contract is destroyed (`SELFDESTRUCT`), `DeleteAccount` wipes the contract's code, all of its storage (including the module's escrow-balance slot), and removes the auth account: [5](#0-4) 

Any unprivileged caller who subsequently calls `ConvertERC20` or `ConvertCoin` against that pair triggers the `acc == nil || !acc.HasCodeHash()` branch, and the entire token pair (mappings + allowances) is deleted in a single state transition — mirroring `cancelPromotion`'s `delete _promotions[_promotionId]`. Just like the PoolTogether bug, this deletion is unconditional: it does not reconcile or burn the native bank coin supply that was already minted against the now-destroyed escrow, and it does not preserve any record that would let governance or users settle the outstanding balance. The result is a permanent, silent break of the erc20 module's core invariant — that native coin supply for a token-pair denom must always be redeemable 1:1 against real escrowed collateral. After deletion, `GetCoinAddress`/`GetTokenPair` can no longer resolve the denom, so the already-circulating native coin becomes an orphaned, unbacked balance that can still be freely transferred, staked, or used across the chain, while the corresponding ERC20-side accounting is irrecoverably gone.

This is the same failure shape as `cancelPromotion`: a single, unprivileged-reachable code path deletes all state needed to settle value tied to a "cancel"/"terminal" condition, with no intermediate accounting step (e.g. burning the outstanding coin supply, or blocking further mint/transfer of the orphaned denom) to preserve the 1:1 invariant.

### Impact Explanation
This breaks the "Asset-representation path" invariant explicitly called out in scope: `x/erc20` flows must preserve 1:1 accounting between native coins, ERC20 views, and escrows. Once triggered, the affected denom's native coin balance is permanently decoupled from any backing, is not burned, and remains fully spendable — an irreversible accounting corruption of spendable user value across native balances and ERC20 representations, matching the Critical "irreversible accounting corruption ... across native balances, EVM balances, ERC20 representations" impact bucket.

### Likelihood Explanation
No governance or privileged action is required to *trigger* the deletion path — the deletion executes inside `ConvertERC20`/`ConvertCoin`, which are permissionless `MsgServer` entry points callable by any account. The only precondition is that the paired ERC20 contract account has no code (selfdestructed or otherwise cleared), a condition entirely controllable by whoever holds admin/upgrade/backdoor logic in the (governance-registered) external ERC20 contract, or by any contract that self-destructs in the same creation transaction. Once that precondition exists, exploitation by an ordinary unprivileged user is a single call to `ConvertERC20`/`ConvertCoin`.

### Recommendation
Do not unconditionally delete the token pair when the underlying contract is found without code. Instead:
- Compute and burn/reconcile the exact outstanding native coin supply for the affected denom before (or instead of) deleting the pair, or
- Keep the pair record (or a tombstone/paused state) rather than fully deleting mappings, so that outstanding balances can be identified, and follow-on conversion attempts fail safely instead of silently succeeding with `nil, nil`.

### Proof of Concept
1. Register (via governance) an external ERC20 contract `T` as a native-ERC20 token pair.
2. A user calls `ConvertCoin`/`ConvertERC20` to mint native coin `erc20/T` backed by escrowed `T` tokens held by the erc20 module account.
3. The `T` contract's admin/backdoor logic calls `SELFDESTRUCT`, wiping `T`'s code/storage (including the module's escrow balance entry) via `DeleteAccount`. [6](#0-5) 
4. Any unprivileged user now calls `ConvertERC20`/`ConvertCoin` again for the `erc20/T` pair; the keeper detects `acc == nil || !acc.HasCodeHash()` and calls `DeleteTokenPair`, wiping the pair/denom/erc20 maps and allowances. [1](#0-0) 
5. All previously-minted `erc20/T` native coin balances (from step 2) remain in holders' bank balances, fully transferable, with no path to reconcile or burn them against the now-destroyed collateral — a permanent accounting break.

// DeleteTokenPair removes a token pair.
func (k Keeper) DeleteTokenPair(ctx sdk.Context, tokenPair types.TokenPair) {
	id := tokenPair.GetID()
	k.deleteTokenPair(ctx, id)
	k.deleteERC20Map(ctx, tokenPair.GetERC20Contract())
	k.deleteDenomMap(ctx, tokenPair.Denom)
	k.deleteAllowances(ctx, tokenPair.GetERC20Contract())
}

// DeleteAccount handles contract's suicide call:
// - clear balance
// - remove code
// - remove states
// - remove the code hash
// - remove auth account
func (k *Keeper) DeleteAccount(ctx sdk.Context, addr common.Address) error {
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	acct := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	if acct == nil {
		return nil
	}

	// NOTE: only Ethereum contracts can be self-destructed
	if !k.IsContract(ctx, addr) {
		return errors.New("only smart contracts can be self-destructed")
	}

	// set account to a base account to set the whole balance as spendable
	baseAccount := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	k.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(cosmosAddr, baseAccount.GetPubKey(), baseAccount.GetAccountNumber(), baseAccount.GetSequence()))

	// clear balance
	if err := k.SetBalance(ctx, addr, new(uint256.Int)); err != nil {
		return err
	}

	var keys []common.Hash

	// clear storage
	k.ForEachStorage(ctx, addr, func(key, _ common.Hash) bool {
		keys = append(keys, key)
		return true
	})

	for _, key := range keys {
		k.DeleteState(ctx, addr, key)
	}

	// clear code hash
	k.DeleteCodeHash(ctx, addr)

	// remove auth account
	k.accountKeeper.RemoveAccount(ctx, acct)

	k.Logger(ctx).Debug(
		"account suicided",
		"ethereum-address", addr.Hex(),
		"cosmos-address", cosmosAddr.String(),
	)

	return nil
}
