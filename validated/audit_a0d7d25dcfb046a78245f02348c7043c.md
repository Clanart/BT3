### Title
`ReceivedOutput::read` accepts outputs whose `script_pubkey` is unrelated to the declared spend offset, enabling unspendable/mismatched outputs to be recorded as spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The reference bug (CVE-2025-71095) is a missing type check: `stmmac_xdp_xmit_back()` assumed every `xdp_frame` was `MEM_TYPE_PAGE_POOL` and never verified the actual memory type, so a frame of a different type (`MEM_TYPE_PAGE_ORDER0`) was processed with the wrong semantics and crashed the kernel. The analog in Serai is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`: it deserializes a `ReceivedOutput` — a scalar `offset`, a `TxOut`, and an `OutPoint` — without ever checking that `output.script_pubkey` is actually the P2TR output key corresponding to `key + G * offset`. The type/invariant "this output is spendable by this offset" is assumed, not verified, exactly like the unchecked memory type.

### Finding Description
`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) performs only:

1. `Secp256k1::read_F(r)` for `offset` — canonical scalar check only.
2. `TxOut::consensus_decode` and `OutPoint::consensus_decode` — syntactic checks only.

There is no call to `p2tr_script_buf(offset_key)` or any comparison binding `offset` to `output.script_pubkey`. The only place the binding is enforced is `SignableTransaction::multisig` (networks/bitcoin/src/wallet/send.rs:273-285), which returns `None` if `p2tr_script_buf(offset.group_key()) != self.prevouts[i].script_pubkey`. So an attacker-supplied `ReceivedOutput` (e.g., one with an arbitrary `script_pubkey` and `offset = 0`, or a real `TxOut` paying to an unrelated script) is accepted as a spendable received output, inflating the wallet's apparent balance, but fails — or worse, only fails at signing time.

By contrast, outputs produced honestly via `Scanner::scan_transaction` (mod.rs:199-214) always have the script/offset binding because the scanner only emits outputs whose `script_pubkey` was registered via `register_offset` (mod.rs:180-196). The deserialization path bypasses that invariant.

### Impact Explanation
An untrusted byte stream fed to `ReceivedOutput::read` can plant an output that:

- Is counted toward spendable balance (`input_sat` in `SignableTransaction::new`, send.rs:175), so the wallet believes it holds funds it cannot spend — "funds reported received that are not spendable."
- Is selected as a transaction input, causing `multisig()` to return `None` and the whole transaction construction to abort (DoS on withdrawal/batch signing).
- Masks real funds: `NotEnoughFunds` decisions and change/fee math (`needed_fee`, `fee()`) are computed over phantom input value.

This is a consistency/type-confusion flaw in a deserialization path, not a secret-leak. Impact: Medium — integrity of the wallet's output set and liveness of transaction construction, reachable purely by supplying crafted bytes to `read`.

### Likelihood Explanation
`ReceivedOutput::read` is explicitly an untrusted-bytes sink. Any party able to supply or corrupt the serialized output stream (a compromised datastore, an untrusted backup/import path, or a peer supplying claimed outputs) can inject mismatched records with trivial effort — no cryptographic work is required since the binding is simply never checked. Detection is deferred to `multisig()` returning `None`, which aborts the transaction rather than identifying the poisoned record.

### Recommendation
Validate the offset/script binding inside `ReceivedOutput::read` (or in a constructor the deserializer must call): derive the spend key and require `p2tr_script_buf(key + G * offset) == Some(output.script_pubkey)`, rejecting otherwise. Alternatively, store the registration data and re-derive via `Scanner`. Additionally, `SignableTransaction::new` should drop or error on inputs that fail this check rather than deferring to `multisig()`, so phantom inputs are rejected at plan-construction time.

### Proof of Concept
1. Take any valid `TxOut` paying to an attacker-controlled script (e.g., a P2PKH `script_pubkey`), any valid `OutPoint`, and `offset = Scalar::ZERO`.
2. Serialize via `ReceivedOutput { offset: 0, output, outpoint }.write(...)` layout: `offset.to_bytes() || serialize(txout) || serialize(outpoint)` (mod.rs:136-141).
3. Feed those bytes to `ReceivedOutput::read` — it returns `Ok` since there is no binding check.
4. The wallet's balance now includes `output.value`; including it in `SignableTransaction::new` succeeds (fee math uses `input_sat`), but `multisig()` returns `None` at send.rs:277-279 because `p2tr_script_buf(group_key) != output.script_pubkey`, aborting the transaction.

Note: I verified the deserialization and signing paths directly; I did not fully trace which upstream component feeds untrusted bytes into `ReceivedOutput::read` in production (it appears to be a wallet/processor persistence or import path), so the concrete exposure surface is inferred from the read API being an untrusted-bytes sink rather than from a traced call chain.
