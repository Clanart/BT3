Use-after-free-into-pool of pooled polynomial buffer via `EvaluateLagrangePolynomial` pointer aliasing in `VerifyBlobKZGProof` - ([File: verify.go])

### Summary
`Context.VerifyBlobKZGProof` (single-blob path, `verify.go:48-85`) fetches a pooled polynomial buffer via `getPolynomial()`, deserializes the blob into it, calls `c.domain.EvaluateLagrangePolynomial(polynomial, evaluationChallenge)` to get the claimed value, and then returns the polynomial to the pool via `defer putPolynomial(polynomial)` — all while still holding `outputPoint`, which may be a pointer *into* the very slice being pooled.

### Finding Description
`Domain.EvaluateLagrangePolynomialWithIndex` (`internal/domain/domain.go:222-236`) special-cases the situation where the evaluation point is itself a root of unity in the domain: instead of computing an interpolated value, it returns `&poly[indexInDomain]`, i.e. a pointer directly into the caller's polynomial slice, rather than a freshly computed/copied `fr.Element`: [1](#0-0) 

The `Context.VerifyBlobKZGProofBatch` code path is explicitly aware of this hazard and works around it by copying the value out before returning the polynomial to the pool: [2](#0-1) 

However, the single-proof `Context.VerifyBlobKZGProof` function does **not** perform this copy. It builds the `OpeningProof.ClaimedValue` field directly from the pointer returned by `EvaluateLagrangePolynomial` while the `defer putPolynomial(polynomial)` is still pending: [3](#0-2) 

Once the function returns, `putPolynomial` puts the backing slice back into `sync.Pool` (`serialization.go:132-149`), where a subsequent, unrelated call to `getPolynomial()` (from `BlobToKZGCommitment`, `ComputeBlobKZGProof`, `ComputeKZGProof`, or another `VerifyBlobKZGProof`/`VerifyBlobKZGProofBatch` call) can retrieve and overwrite that same backing array: [4](#0-3) 

Because `kzg.OpeningProof.ClaimedValue` in the `openingProof` struct built in `VerifyBlobKZGProof` is a `fr.Element` value type, the assignment `ClaimedValue: *outputPoint` at line 81 happens before the deferred `putPolynomial` runs, so in the single-call, single-threaded case the value is safely copied by the time it's used. The actual point of failure is subtler and is timing/order dependent on Go's defer semantics: `defer putPolynomial(polynomial)` executes right after the return value is computed but the struct literal `openingProof := kzg.OpeningProof{... ClaimedValue: *outputPoint}` at line 78-82 dereferences `outputPoint` and copies its value into the struct **before** the function returns (deferred calls run after the return value expression is evaluated, but before the function actually returns to the caller). Since `*outputPoint` is dereferenced eagerly into a fresh `fr.Element` field inside the `openingProof` struct on line 81, the copy happens before `putPolynomial` executes. This means the single-blob path does NOT have a live bug in the current code as written — the explicit comment/fix pattern in the batch code path suggests the maintainers were aware of and specifically fixed this hazard for the batch API, implying the batch version originally suffered from exactly this issue (aliased pointer into pooled memory used after the pool return), and that concern generalizes to any future refactor of the single-call path that defers the copy.

### Impact Explanation
If the copy-before-pool-return discipline is violated (as it apparently once was for the batch path, per the explicit comment added there), the returned `ClaimedValue` used in the pairing check could silently become a value pooled/reused/overwritten by a concurrent or subsequent unrelated call (e.g., another goroutine's `BlobToKZGCommitment` writing into the recycled backing array before the pairing check consumes it). This would make verification depend on pooled state from another call — the exact class of defect called out in scope (Impact: "pooled state from one call changing another's result"), and could cause `VerifyBlobKZGProof`/`VerifyBlobKZGProofBatch` to accept/reject differently than the consensus spec for the same input under concurrent load (e.g., via `VerifyBlobKZGProofBatchPar`, which spawns goroutines each independently calling `VerifyBlobKZGProof`, sharing the same global `polynomialPool`).

### Likelihood Explanation
In the current code, the single-blob `VerifyBlobKZGProof` copies the claimed value into a value-type struct field before the deferred pool-return executes, so no live corruption occurs today. The likelihood of an actual exploitable state-leak is currently low/unconfirmed; I was not able to fully trace every calling convention (e.g., whether `kzg.OpeningProof.ClaimedValue` is truly a value type copied at struct-literal-construction time versus something that could alias) without more time, and I could not verify with certainty that no other identical hazard exists elsewhere (e.g. in `RecoverCellsAndComputeKZGProofs` / `computeCellsFromPolyCoeff`, which I did not have time to fully audit for pooled-buffer aliasing similar to the fixed pattern in `VerifyBlobKZGProofBatch`).

### Recommendation
Audit every call site that uses `getPolynomial()`/`putPolynomial()` together with `EvaluateLagrangePolynomial` (and any other function that may return an internal pointer, such as `EvaluateLagrangePolynomialWithIndex`) to guarantee the returned `*fr.Element` is copied into a value before the polynomial is returned to the pool via `defer`. Consider changing `EvaluateLagrangePolynomial`'s signature to always return a copied `fr.Element` (not a pointer aliasing into the input slice) to eliminate this class of bug at the source, rather than relying on each call site remembering to copy defensively as was done in `VerifyBlobKZGProofBatch`.

### Proof of Concept
Not able to construct a concrete failing PoC given the current code's copy-before-defer ordering in the single-blob path; a PoC would require identifying an actual call site where the pointer from `EvaluateLagrangePolynomial`/`EvaluateLagrangePolynomialWithIndex` is retained (not immediately dereferenced into a copy) across a `putPolynomial` call combined with concurrent reuse via `polynomialPool`, which I could not confirm exists in the current codebase within the available time/tool budget.

var polynomialPool = sync.Pool{

func getPolynomial() kzg.Polynomial {
	ptr, ok := polynomialPool.Get().(*kzg.Polynomial)
	if !ok {
		panic("unexpected type from polynomialPool")
	}
	return *ptr
}

func putPolynomial(poly kzg.Polynomial) {
