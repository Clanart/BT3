### Title
Sybil accounts inflate `totalBoostFactor` via concave sqrt-of-individual-balance summation, diluting legitimate referrers' boosted yield share - ([File: rewards/ReferralStorage.sol])

### Summary
`ReferralStorage.updateTotalFactor()` computes each account's `factor` as `sqrt(getUserTotalLocked(_account))` and adds it to a single global `totalBoostFactor`, which is used as the shared denominator in `_calBoosted()` (`BoostPoint * factor / totalBoostFactor`). Because `sqrt` is concave, splitting a fixed amount of MGP across many attacker-controlled accounts that each `registerCode()` and lock a fraction of the capital produces a combined factor sum strictly greater than locking the same total in one account, letting an attacker inflate the shared denominator (and their own aggregate numerator) at the expense of legitimate referrers' boosted share.

### Finding Description
`registerCode()` at [1](#0-0)  lets any address register a referral code with no cost or Sybil resistance. Locking or unlocking MGP in `VLMGP` calls `IReferralStorage(referralStorage).updateTotalFactor(_for)` from `_lock()` and `startUnlock()` [2](#0-1) [3](#0-2) .

`updateTotalFactor()` recomputes the caller's factor from scratch and updates the single shared `totalBoostFactor` accumulator: [4](#0-3) 

`_calBoosted()` divides `BoostPoint` by this shared, system-wide `totalBoostFactor`: [5](#0-4) 

Since `factor = sqrt(lockedAmount)` (Babylonian sqrt, a concave function) [6](#0-5) , splitting a fixed capital `C` into `N` synthetic accounts each locking `C/N` and each registering a code yields `N * sqrt(C/N) = sqrt(N) * sqrt(C)`, which is strictly greater than `sqrt(C)` for `N > 1`. This means the same capital, split into Sybil identities, contributes `sqrt(N)` times more to `totalBoostFactor` than if consolidated in one account. Every existing legitimate referrer's `boosted()` share (`BoostPoint * factor / totalBoostFactor`) is therefore diluted purely because of the attacker's account count, not their proportional capital — violating the intended "boost share reflects proportional locked MGP" invariant. No modifier, cap, or per-identity normalization (e.g., capping the number of registrable codes per real capital unit, or computing `sqrt` on aggregated ownership) prevents this; `_onlyVlMGP` only checks the caller is the `VLMGP` contract, not that `_account` corresponds to a unique real economic actor.

### Impact Explanation
Any registered referrer's future accrual via `trigger()` — `boostesd = _calBoosted(_referer)` used to compute `refererAmount`/`refereeAmount` added to `rewardAmount` [7](#0-6)  — is permanently reduced whenever an attacker inflates `totalBoostFactor` via Sybil splitting, since the denominator grows disproportionately. This matches "theft or permanent freezing of unclaimed yield": legitimate referrers' future `rewardAmount` accrual is durably suppressed below the value proportional to their locked MGP, and by the same concavity argument the attacker's own aggregate boosted share (summed across their Sybil-referrer identities, assuming they also route some referee claims through their own codes) increases relative to consolidating in one account, capturing value that would otherwise accrue to the honest high-locker.

### Likelihood Explanation
The attack requires only unprivileged actions: deploying/controlling multiple EOAs, calling public `registerCode()`, and locking MGP via `VLMGP` (which the attacker must already hold, e.g., minimal per-account amounts of the same total capital they would otherwise lock in one account). No special role or governance access is needed, and the attack is fully repeatable — the more accounts an attacker splits into, the larger the `sqrt(N)` inflation factor, with diminishing marginal gas cost per additional account being the only real limiting factor.

### Recommendation
Decouple boost-factor computation from raw per-address `sqrt(lockedAmount)` summation. Options: require KYC/identity binding is infeasible on-chain, but the design should instead compute `totalBoostFactor` based on `sqrt` of aggregated, Sybil-resistant metrics (e.g., apply `sqrt` only once at the system level using total locked supply and per-user linear locked share, e.g. boost proportional to `lockedAmount_i` directly, or use a formula like Curve's `min(lockedAmount_i, boostedByVeBalance)` gauge-boost style that caps individual boost by a veToken-weighted formula tied 1:1 to locked balance rather than sqrt-summed per free-form identity), or restrict `registerCode`/factor accrual to one code per unique locked position aggregated globally rather than per arbitrary address, or enforce a minimum lock threshold and code registration fee scaling to make Sybil splitting capital-inefficient.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `ReferralStorage`, mint MGP to a "legitimate" referrer `L` and an attacker.
2. `L` registers a code, locks `A` MGP in `VLMGP` (triggers `updateTotalFactor(L)`), record `refBoosted_before = ReferralStorage.boosted(L)`.
3. Attacker splits capital `C` into `N` fresh EOAs; each calls `registerCode()` with a unique code, then locks `C/N` MGP via `VLMGP.lock` (triggers `updateTotalFactor` per Sybil account).
4. Record `refBoosted_after = ReferralStorage.boosted(L)` and compare to a control run where the attacker instead locks the full `C` in a single account and registers one code.
5. Assert `refBoosted_after(split case) < refBoosted_after(single-account case)`, demonstrating `L`'s boosted share is diluted disproportionately purely due to the attacker's account count rather than their total locked capital, and assert `totalBoostFactor(split) > totalBoostFactor(single)` for the same total attacker capital `C`, confirming the `sqrt`-concavity Sybil amplification.
