### Title
BIP-340 FROST algorithm never negates the secret share / key for odd-Y output keys, producing signatures Bitcoin rejects - ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
The BIP-340 `Hram` implementation in `networks/bitcoin/src/crypto.rs` handles parity for the nonce `R` (negating the challenge when `R` is odd), but neither `sign_share` nor `verify` ever normalizes the *key* parity. Under Taproot (BIP-341), the output key `Q = P + t·G` must be treated as an x-only, even-Y key; when `Q` has odd Y, the effective signing scalar must be `-d`. The FROST `Schnorr::sign_share` unconditionally signs with the raw `params.secret_share()`, so whenever the tweaked group key is odd-Y the produced "BIP-340" signature is actually valid for `-Q`, not `Q`, and fails BIP-340 verification on-chain.

### Finding Description
- `Hram::hram` computes `c = H(R || A || m)` and negates `c` only when `R` is odd (`needs_negation(R)`), then `verify` negates `s` when `R` is odd to emit an even `R` — handling nonce parity correctly. `networks/bitcoin/src/crypto.rs:59-73`, `crypto.rs:139-150`. [1](#0-0) 
- `sign_share` delegates to `SchnorrSignature::sign(params.secret_share(), nonce, c)`, i.e. `s = c·x + r` with the raw secret share `x`. There is no conditional negation of `x` based on `needs_negation(group_key)`. `crypto/frost/src/algorithm.rs:201-211`, `crypto/schnorr/src/lib.rs:74-84`. [2](#0-1) 
- The internal `verify` reuses `c` from `sign_share` against `group_key` as-is, so the signature is internally self-consistent for `s·G = R + c·A` — but a BIP-340 verifier lifts `x(A)` to the *even* point, effectively verifying against `-A` when `A` is odd, so `s·G = R + c·(-A)` fails. `algorithm.rs:214-217`. [3](#0-2) 
- Analogous to the report: the component manages low-level key/signature material directly and fails to replicate a security-critical control of the surrounding protocol (BIP-340 even-Y key normalization), yielding signatures for a key that is not the intended output key.

### Impact Explanation
Any unprivileged party who can cause a transaction to be signed under a TapTweak/offset that yields an odd-Y output key (≈50% of tweaks by chance, and deterministic given the key and tweak) obtains a threshold signature the Bitcoin network will reject — funds cannot be moved with that signature, and the produced signature is cryptographically a valid signature for the *negated* key `-Q` rather than the intended output key `Q`.

### Likelihood Explanation
Triggered deterministically whenever the aggregated (tweaked/offset) group key has odd Y, which occurs with ~1/2 probability per key/tweak. Reachable purely through public inputs (the transaction/sighash the signer is asked to sign); no malicious participant required — honest signers produce the invalid signature.

### Recommendation
In `Schnorr::sign_share`, negate the secret share when `needs_negation(&params.group_key())` is set (or fold key parity into the offset application in the `ThresholdView`), and in `verify` verify against the even-Y lift of `group_key` (negate `group_key` before checking) so the emitted signature is valid under BIP-340 for the actual Taproot output key.

### Proof of Concept
Set up a `ThresholdKeys`/`ThresholdView` over `Secp256k1` with an offset (TapTweak) such that `group_key()` has odd Y. Run `AlgorithmMachine`/`PreprocessMachine` → `sign(preprocesses, sighash)` and `complete(shares)`; the returned 64-byte signature satisfies `s·G = R + c·A` internally but fails `bitcoin::secp256k1`/`schnorr::verify` against `x_only(Q)`, because the BIP-340 verifier checks `s·G = R + c·lift_x(Q)` with `lift_x(Q) = -Q`.

Caveat: I could not read `networks/bitcoin/src/wallet/mod.rs`/`send.rs` or the `ThresholdView` offset-application code within this iteration budget, so I could not confirm whether key parity is normalized elsewhere (e.g., at tweak-application time or inside `ThresholdView`). If the tweaked key is already negated upstream, this is correct-by-composition and no bug exists — but nothing in `crypto.rs` or `crypto/frost` performs that negation.

    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
