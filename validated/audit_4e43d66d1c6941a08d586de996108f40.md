### Title
Wrong price feed used for stSTXbtc asset in protocol-data valuation helper - ([File: mainnet/contracts/utility/v0-1-data.clar])

### Summary
`get-asset-price` in `v0-1-data.clar` prices the `stSTXbtc` asset using the `PYTH-STX` feed instead of `PYTH-BTC`, despite the accompanying comment stating it should return the BTC price. This is a price-attached-to-the-wrong-asset defect analogous to the reported zkSync formula/constant mismatch, where the wrong constant (`MAX_PUBDATA_PER_BLOCK` instead of `L2_TX_MAX_GAS_LIMIT`) was substituted into a calculation.

### Finding Description
In `mainnet/contracts/utility/v0-1-data.clar`, the price-resolution branch for `stSTXbtc` is: [1](#0-0) 
```
;; stSTXbtc - BTC price (liquid staked STX with BTC yield)
(if (is-eq aid stSTXbtc) (default-to u0 (get-pyth-price PYTH-STX))
```
The comment explicitly states the intent is to fetch the BTC price, but the code calls `get-pyth-price PYTH-STX`, using the STX/USD feed constant instead of `PYTH-BTC`. The identical bug is duplicated in `local-testing/contracts/utility/protocol-data.clar` at the analogous `get-asset-price` branch. [2](#0-1) 

This exactly matches the report's bug class: a constant that resolves to a different underlying quantity than the one intended by the comment/documentation, silently substituted into a price/value calculation.

However, I was unable to fully verify within the remaining budget whether this `get-asset-price` function in `v0-1-data.clar` (described in its header comment as a "read-only utility contract" that "provides optimized read-only functions to query protocol state") is actually consumed by any collateral-valuation, borrowing-limit, or liquidation code path that moves real funds, or whether the authoritative pricing for loans is instead resolved independently inside `v0-4-market.clar`'s own oracle-callcode system (`resolve-pyth`/`resolve-callcode`/`CALLCODE-ZSTSTXBTC`), which appears structurally separate and was not confirmed to share this bug.

### Impact Explanation
If this function is only used by an off-chain/read-only reporting path (as its own comments suggest), the impact is limited to displaying an incorrect price for `stSTXbtc`/`zstSTXbtc`, with no direct fund-movement consequence — this would not meet the in-scope impact bar (Critical/High requiring theft, freezing, or insolvency). If, contrary to what I could confirm, this helper's output is consumed anywhere in a collateral/LTV/liquidation calculation that determines borrowing power or liquidation eligibility, substituting the STX price for the BTC price would misvalue stSTXbtc collateral, potentially permitting under-collateralized borrowing (protocol insolvency risk) or incorrect liquidation health verdicts.

### Likelihood Explanation
The bug is deterministic and always triggers whenever `get-asset-price` is called with `aid = stSTXbtc`; no attacker action is required. Likelihood of the defect existing is confirmed; likelihood of financial exploitability depends entirely on whether this function's output feeds into on-chain funds-moving logic, which I could not confirm before running out of iterations.

### Recommendation
Change `get-pyth-price PYTH-STX` to `get-pyth-price PYTH-BTC` in the `stSTXbtc` branch of `get-asset-price` in both `mainnet/contracts/utility/v0-1-data.clar` and `local-testing/contracts/utility/protocol-data.clar`. Additionally, trace and confirm every caller of this function to determine whether any on-chain funds-moving logic (borrow limits, liquidation) consumes it, and add a regression test asserting `stSTXbtc` price tracks the BTC feed, not the STX feed.

### Proof of Concept
1. Register `stSTXbtc` with a Pyth BTC feed as collateral (per `v0-init.clar`/proposal setup).
2. Call `(contract-call? .v0-1-data get-asset-price stSTXbtc)` (or the equivalent `get-all-assets`/collateral-sum helper).
3. Observe the returned price equals the current STX/USD price rather than the BTC/USD price — confirmed directly from the code at [1](#0-0) , where the branch documented for BTC pricing invokes the STX feed constant.
4. **Unverified/incomplete step**: I could not conclusively trace whether any collateral-valuation or liquidation call path in `v0-4-market.clar` calls into this specific helper for `stSTXbtc` pricing, versus resolving price independently via its own `resolve-pyth`/callcode system — this determines whether step 3's misvaluation is merely cosmetic or fund-affecting, and should be verified by a follow-up code review.
