Confirmed: `_cancelFromDest` in `ExtrinsicIntents.sol` never checks whether the order was already filled before overwriting `_filled[commitment]` and dispatching a duplicate `RefundEscrow` message. This is the exploitable analog to the report's "order-of-operations lets state be mutated on an invalid/already-settled precondition" bug class.

### Title
Destination-chain `cancelOrder` can override an already-filled cross-chain order and race the legitimate settlement, causing solver fund loss - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`_cancelFromDest` marks an order cancelled and dispatches a `RefundEscrow` message to the source chain without ever checking `_filled[commitment]`. If a solver has already filled the order (delivering output tokens to the beneficiary on the destination chain and triggering a `RedeemEscrow` dispatch back to source), anyone can still call `cancelOrder()` on the destination chain once `order.deadline` has passed and force a second, conflicting `RefundEscrow` message to the source chain.

### Finding Description
`fillOrder()` sets `_filled[commitment] = msg.sender` and dispatches `RedeemEscrow` to the source chain [1](#0-0) . Separately, `_cancelFromDest()` is reachable through the public `cancelOrder()` entrypoint and, once `order.deadline < block.number`, drops its authorization check and allows **anyone** to call it, unconditionally rewriting `_filled[commitment]` and dispatching a `RefundEscrow` request: [2](#0-1) 

There is no guard such as `if (_filled[commitment] != address(0)) revert Filled();` before this overwrite, so it does not matter that the order was already legitimately filled — the function proceeds to mark it "cancelled" (`_filled[commitment] = user`) and dispatch a competing withdrawal instruction to the source chain.

On the source chain, both messages (`RedeemEscrow` for the solver and `RefundEscrow` for the user) are handled by the same `_withdraw`/`withdraw` routine, which pays out based on whichever message is delivered/proven first and zeroes the escrow (`_orders[commitment][token]`) on execution: [3](#0-2) . Because message delivery order across Hyperbridge is not guaranteed to match on-chain event order (it depends on relayer timing and proof availability), the `RefundEscrow` triggered by the bogus destination-side "cancel" can be delivered and settle **before** the legitimate `RedeemEscrow`. Once `_orders[commitment][token]` is zeroed by the refund, the subsequent `RedeemEscrow` withdrawal for the solver hits `escrowed == 0` and reverts with `UnknownOrder()`, permanently failing the solver's payout while the user has already received the solver's output tokens on the destination chain.

### Impact Explanation
This is unauthorized state mutation and fund redirection: a solver that already performed its obligation (delivering output tokens to the beneficiary) can be denied its escrowed input-token payment because an unrelated, unprivileged caller (anyone, post-deadline) can retroactively "cancel" an order that was already filled. The result is the user receiving both the solver's output tokens and a refund of their own escrowed inputs, while the solver's legitimate `RedeemEscrow` settlement is starved of funds — a direct loss of funds to the rightful beneficiary (the solver) and an unauthorized/duplicate settlement race on escrow, matching the bounty's "loss of funds" and "logic attack / duplicate settlement" categories.

### Likelihood Explanation
The trigger requires only that: (1) a solver fills an order shortly before its deadline (routine, not adversarial), and (2) any address calls `cancelOrder()` on the destination chain after the deadline has passed — no privileged role, relayer collusion, or malicious prover is needed, since post-deadline cancellation is explicitly open to "anyone" by design. The attacker only needs to win the cross-chain message race for `RefundEscrow` vs `RedeemEscrow` delivery on the source chain, which is plausible given relayers process both concurrently and delivery/proof timing is not synchronized with fill events.

### Recommendation
Add a guard at the top of `_cancelFromDest` (and ideally in the shared `cancelOrder` entrypoint) that reverts if `_filled[commitment] != address(0)` before proceeding, mirroring the existing "already filled" check used in `fillOrder()`. This prevents any cancellation — authorized or post-deadline "anyone" cancellation — from being dispatched once the order has already been filled by a solver.

### Proof of Concept
1. User places a cross-chain order on the source chain with `order.deadline = D`.
2. A solver calls `fillOrder()` on the destination chain at block `D-1`, delivering output tokens to `order.output.beneficiary` and dispatching `RedeemEscrow` back to source; `_filled[commitment]` is set to the solver's address on the destination chain [4](#0-3) .
3. At block `D+1` (deadline passed), any third-party address calls `cancelOrder()` on the destination chain; because `order.deadline >= _blockNumber()` is now false, the authorization check is skipped and `_cancelFromDest` proceeds unconditionally, overwriting `_filled[commitment]` to `order.user` and dispatching `RefundEscrow` to the source chain [5](#0-4) .
4. If the relayer delivers `RefundEscrow` to the source chain before `RedeemEscrow`, `withdraw()`/`_withdraw()` pays the user and zeroes `_orders[commitment][token]` [3](#0-2) .
5. When `RedeemEscrow` for the solver subsequently arrives, `escrowed == 0` causes `revert UnknownOrder()` — the solver never receives payment despite having already delivered the output tokens.

**Note on scope/uncertainty:** I verified this ordering in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` and `IntentsBase.sol`, which is the actively CEI-hardened contract set (confirmed by the reentrancy fix tests). I was not able to fully confirm whether the same missing `_filled` check exists identically in the parallel `evm/tron/contracts/apps/IntentGatewayV2.sol` deployment within the tool budget available; that file's `_cancelFromDest`-equivalent should be checked for the same gap if this is fixed.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
