### Title
`SignableTransaction::new` excludes the OP_RETURN `data` output from the fee/vsize estimate, so transactions carrying data pay an insufficient fee and can be rejected or stuck — analogous to `.transfer()`'s fixed stipend causing delivery failure — (File: networks/bitcoin/src/wallet/send.rs)

### Summary

The reported bug class is "a fixed, underestimated resource stipend causes a funds transfer to fail even though the sender acted correctly." In `bitcoin-serai`, `SignableTransaction::new` builds an OP_RETURN output when `data` is supplied, but computes `needed_fee` from `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which only models the payment outputs — never the OP_RETURN output. The resulting transaction's true vsize is larger than estimated, so the actual fee paid (`sum(inputs) - sum(outputs)`, exactly `needed_fee`) yields a lower effective feerate than `fee_per_vbyte`, potentially below the network's minimum relay feerate.

### Finding Description

`SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` before the weight is computed, but the weight/vbytes computation is performed only over `payments`:

```rust
// networks/bitcoin/src/wallet/send.rs
194|    if let Some(data) = data {
195|      tx_outs.push(TxOut {
196|        value: Amount::ZERO,
197|        script_pubkey: ScriptBuf::new_op_return(...)
198|      })
199|    }
204|    let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
206|    let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` constructs a `Transaction` whose `output` list is built solely from `payments` (plus optional change); the OP_RETURN output is never represented. The minimum-relay check at line 211 and the change calculation at lines 224–235 (`fee_with_change = fee_per_vbyte * vbytes_with_change`, also computed without the data output) inherit the same underestimate.

With `data` up to the permitted 80 bytes, the OP_RETURN output adds roughly 91 bytes (~91 vbytes) that are never charged for. A caller using the minimum acceptable `fee_per_vbyte` produces a transaction whose absolute fee is `needed_fee` but whose true vsize is ~91 vbytes larger, so its effective feerate falls below `DEFAULT_MIN_RELAY_TX_FEE` even though the `TooLowFee` check passed. Like `.transfer()`'s 2300-gas stipend, a fixed/under-provisioned resource amount silently makes the delivery fail.

### Impact Explanation

The signed transaction underpays the feerate the caller requested and can be rejected by relay policy (below minimum relay feerate) or sit unconfirmed indefinitely while the inputs remain locked to that plan. Funds are not stolen, but the withdrawal/payment fails despite correct inputs — a Medium-severity availability failure matching the original report's impact profile. Additionally, the `MAX_STANDARD_TX_WEIGHT` check at line 241 uses the underestimated `weight`, so a maximally-sized transaction with data could exceed standardness weight while passing validation.

### Likelihood Explanation

Any caller of `SignableTransaction::new` supplying `data` (the API exists precisely to embed up to 80 bytes, and only errors above that) combined with a low `fee_per_vbyte` triggers this deterministically. The gap scales with data size; at the 80-byte maximum and minimum feerate the shortfall is on the order of ~91 sats against the relay minimum.

### Recommendation

Include the OP_RETURN output in the weight/vbytes estimation: extend `calculate_weight_vbytes` to accept the full output list (or a `data: Option<&[u8]>` parameter that appends a zero-value OP_RETURN `TxOut` to the modeled transaction), and use that estimate for `needed_fee`, the `TooLowFee` check, `fee_with_change`, and the `MAX_STANDARD_TX_WEIGHT` check.

### Proof of Concept

```rust
// Any inputs; one dust-valid payment; 80 bytes of data; minimal relay feerate.
let fee_per_vbyte = 1; // sats/vbyte
let data = vec![0u8; 80];

let stx = SignableTransaction::new(inputs, &payments, Some(change), Some(data), fee_per_vbyte)?;
// stx.needed_fee() == 1 * vbytes(inputs + payments + change)
// But the real transaction contains an extra ~91-vbyte OP_RETURN output.
// Effective feerate = needed_fee / actual_vsize < DEFAULT_MIN_RELAY_TX_FEE
// => bitcoind rejects with "min relay fee not met" / the TX never propagates,
// even though `TooLowFee` was not returned.
```

Concretely: a 1-input, 1-payment, 1-change transaction is ~191 vbytes, so `needed_fee ≈ 191` sats. The signed transaction is ~282 vbytes and needs ~282 sats at 1 sat/vbyte to relay; it pays only ~191 and fails relay despite passing the internal `TooLowFee` gate. [1](#0-0) [2](#0-1) [3](#0-2)
