## Analysis

The external report describes a class of bug: **excess payment tokens accepted from a user are not refunded when the ERC20/native payment path skips the "return leftover" step that the other path does.** A direct local analog exists in the Tron deployment of the IntentGateway contract.

### The corrupted value

`evm/src/apps/IntentGatewayV2.sol::placeOrder()` (the canonical EVM version) correctly tracks unspent native value through the whole function and refunds it at the end: [1](#0-0) 

Specifically it decrements `msgValue` by the actual amount consumed by the Uniswap swap (`amounts[0]`), then refunds whatever native token remains to `msg.sender`.

The **Tron variant** of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder()`, implements the identical fee-swap logic but drops both the `amounts[0]` bookkeeping and the final refund block entirely: [2](#0-1) 

Compare against the equivalent block in the canonical version which explicitly refunds: [1](#0-0) 

### Why this is exploitable / a real fund-loss path

`placeOrder` is a `public payable` entrypoint callable by any unprivileged user. Any native ETH sent as `msg.value` that is not exactly consumed becomes `msgValue` leftover in two ways:
1. Any surplus beyond what's needed to fully fund the native input legs (`order.inputs`) — tracked in `msgValue` but with no downstream refund on the ERC20/no-fee-swap path (only `if (order.fees > 0)` triggers any further use of `msgValue`).
2. When `order.fees > 0` and native token is used to pay the solver fee, `swapETHForExactTokens{value: msgValue}(...)` consumes only the exact ETH required to produce `order.fees` of the fee token and Uniswap's router refunds all unused ETH back to the caller (the `IntentGatewayV2` contract itself, since it invoked the swap). That refunded ETH lands in the contract's own balance — it is never routed back to the user because the Tron variant never re-checks `address(this).balance` or `msgValue` and never issues a final `.call{value: ...}` refund like the canonical version does.

There is no sweep, `withdraw`, or refund logic anywhere later in the Tron `placeOrder` function to recover this value for the depositing user. Every user who slightly overestimates the native ETH needed for the fee swap (a very common client-side estimation pattern, since exact swap cost has slippage) permanently loses that difference — it becomes stuck, unrecoverable contract balance. This directly mirrors "M-03 Excess Base Tokens Not Refunded," except here the asymmetry is between the fixed EVM deployment (which refunds) and the Tron deployment (which does not), for the native-token fee-payment leg of `placeOrder`.

### Title
Unrefunded Excess Native Token in Tron `IntentGatewayV2.placeOrder()` Fee Swap Path - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron build of `IntentGatewayV2.placeOrder()` omits the `msgValue` decrement and final native-token refund present in the canonical EVM contract. Any leftover `msg.value` — including ETH refunded by Uniswap's `swapETHForExactTokens` when paying `order.fees` — is silently retained by the contract instead of being returned to the caller.

### Finding Description
`placeOrder()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` accepts `msg.value`, spends part of it on native input legs and/or the `order.fees` fee-token swap via `swapETHForExactTokens{value: msgValue}(...)`, but never captures the swap's returned `amounts[0]` and never performs the final `msg.sender.call{value: msgValue}("")` refund that exists in `evm/src/apps/IntentGatewayV2.sol` lines 356 and 365-368. Because Uniswap refunds unused ETH to the caller (the gateway contract) rather than the original transaction sender, this ETH becomes stranded contract balance with no code path to reclaim it for the user.

### Impact Explanation
Direct, silent loss of user funds on every `placeOrder` call that either (a) sends native input with slight overpayment, or (b) pays `order.fees` in native token with any safety margin above the exact swap cost. No admin, relayer, or malicious peer is required — this triggers under completely normal usage by an unprivileged caller of the public `placeOrder` entrypoint.

### Likelihood Explanation
High. Fee-token swaps via Uniswap inherently require sending more native value than the exact cost to tolerate price movement between quote and execution; users/integrators routinely add a buffer. Every such call on the Tron deployment permanently strands the buffer amount.

### Recommendation
Port the fix already present in `evm/src/apps/IntentGatewayV2.sol` (capture `amounts[0]` from `swapETHForExactTokens`, decrement `msgValue` accordingly, and refund any remaining `msgValue` to `msg.sender` at the end of `placeOrder`) into `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with an order that has `order.fees = F` and pays with native token, sending `msg.value = requiredNativeForInputs + X` where `X` is safety margin greater than the actual ETH needed to acquire `F` fee tokens via `swapETHForExactTokens`.
2. `swapETHForExactTokens{value: msgValue}(F, path, address(this), block.timestamp)` executes, spending only the exact ETH needed and refunding the rest to `address(this)` (the gateway contract).
3. Function proceeds to `emit OrderPlaced(...)` and returns without ever sending the leftover ETH back to `msg.sender`.
4. The user's transaction succeeds, the order is placed correctly, but the ETH surplus (`X` minus actual swap cost) remains permanently in the `IntentGatewayV2` contract balance with no function to withdraw it back to the user.
