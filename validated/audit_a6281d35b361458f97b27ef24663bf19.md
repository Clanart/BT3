### Title
Intent order session private keys persisted unencrypted in client storage, enabling unauthorized solver selection - (File: `sdk/packages/sdk/src/storage/index.ts`)

### Summary
The IntentGatewayV2 solver-selection mechanism relies on an ephemeral "session key" whose sole purpose is to cryptographically authorize which solver may fill a user's cross-chain order [1](#0-0) . The SDK generates this key and persists it via `createSessionKeyStorage`, writing the plaintext `privateKey` field as JSON into whatever local driver `detectEnvironment()` resolves — `localStorage` in browsers, a file-backed/in-memory driver in Node — with no encryption, passphrase, or OS keychain integration anywhere in the path. This is the same broken invariant as the ZecWallet report: a key that authorizes movement/control of value is written to disk/browser storage in the clear, so any code or process with read access to that storage (XSS, malicious browser extension, another origin under a relaxed CSP, a compromised local process, or a stolen device/backup) can read it and act as the legitimate order owner.

### Finding Description
`OrderPlacer.placeOrder` generates a fresh key with `generatePrivateKey()` and immediately stores it unencrypted: [2](#0-1) 

`createSessionKeyStorage` writes/reads it as plain JSON with no cryptographic protection, keyed by both order commitment and session address for easy lookup: [3](#0-2) 

The driver selection defaults to `localStorage` in any browser context: [4](#0-3) 

That session key is not cosmetic — it is the sole authorization credential the protocol trusts for solver selection. `BidImpl.signSelection` pulls the raw `privateKey` out of storage and signs the `SelectSolver` EIP-712 message with it: [5](#0-4) 

On-chain, `IntentsBase._select` recovers the signer from that signature and stores it as the sole authorization gate that `fillOrder` checks before releasing escrowed input assets: [6](#0-5) [7](#0-6) 

Whoever holds the session private key can, at any time before the order deadline, sign a `SolverSelection { commitment, solver }` message for an arbitrary solver address of their choosing — including one they control — and that signature is fully sufficient on-chain to authorize that solver as the exclusive filler for the order.

### Impact Explanation
This breaks "unauthorized transaction or execution" for the intent-settlement path: an attacker who reads the plaintext session key from browser/local storage does not need to compromise the user's main wallet, the relayer, or any operator — they only need read access to the storage the SDK already writes the key into unencrypted. With it they can:
- Call `select()` themselves to bind the order's escrowed input assets to a solver of their choosing, hijacking the legitimate solver-selection auction the mechanism exists to protect.
- Front-run or replace legitimate bid selection with a colluding solver, subverting the price-discovery guarantee `solverSelection` is designed to enforce (docs explicitly describe this key as protecting "orders...from unauthorized fills") [8](#0-7) .
- Grief/DoS a legitimate solver, since `SolverAccount.validateUserOp` binds validation to `keccak256(commitment ‖ sessionKey)` — a maliciously re-selected session authorization invalidates the honest solver's already-signed bid nonce binding [9](#0-8) .

This lands squarely in the "unauthorized transaction or execution" / "logic attacks" bucket of the bounty scope for the intent-settlement subsystem, exactly mirroring the wallet.dat report's root cause (a credential that authorizes value movement stored unencrypted at rest, readable by anyone with local access).

### Likelihood Explanation
Medium. It does not require compromising Hyperbridge infrastructure, a relayer, prover, or governance — only client-side storage access, which is a common attacker capability (XSS in the hosting dApp, malicious browser extension, shared/compromised device, or unsanitized `localStorage` exposure through a supply-chain-compromised script on the same origin). Because the SDK's own `detectEnvironment()` defaults to `localStorage` with zero prompts or warnings about encryption, most integrating dApps will unknowingly ship this exposure by default.

### Recommendation
Never persist raw session private keys in plaintext. Options: (1) encrypt the `privateKey` field at rest using a key derived from a user-supplied passphrase or a platform secure-storage API (WebCrypto + non-extractable keys, OS keychain on Node) before calling `baseStorage.setItem`; (2) avoid storing the raw key at all — use a non-extractable `CryptoKey`/hardware-backed signer so the private material never touches serializable storage; (3) at minimum, warn integrators loudly when the resolved driver is `localstorage`/`memory` and document that they must wrap `SessionKeyStorageOptions` with an encrypting driver.

### Proof of Concept
1. A user places an intent order through the SDK in a browser dApp; `OrderPlacer.placeOrder` generates a session key and calls `ctx.sessionKeyStorage.setSessionKeyByAddress`, which writes `{"privateKey":"0x...","address":"0x...","createdAt":...}` in plaintext to `localStorage` under key `session-key-address:<addr>` [10](#0-9) [11](#0-10) .
2. Any script with access to that origin's `localStorage` (e.g. via a stored-XSS payload in the dApp, or a malicious browser extension) reads the key: `JSON.parse(localStorage.getItem("session-key-address:0x..."))`.
3. The attacker calls `CryptoUtils.signSolverSelection(commitment, attackerSolverAddress, domainSeparator, stolenPrivateKey)` to produce a valid `SolverSelection` signature [12](#0-11) .
4. The attacker submits `IntentGatewayV2.select(SelectOptions{commitment, solver: attackerSolverAddress, signature})` on-chain, which recovers the session key and binds `attackerSolverAddress` as the sole authorized filler in transient storage [6](#0-5) , then calls `fillOrder` from that address, passing the `_filled[commitment]`/`Unauthorized` check that was supposed to require the legitimate solver's session authorization [7](#0-6) .

export function createSessionKeyStorage(options: SessionKeyStorageOptions = {}) {
	const key = options.env ?? detectEnvironment()
	const driver = loadDriver({ key, options }) ?? inMemoryDriver()
	const baseStorage = createStorage({ driver })

	const SESSION_KEY_PREFIX = "session-key:"
	const SESSION_KEY_ADDRESS_PREFIX = "session-key-address:"

	/**
	 * Gets a session key by order commitment
	 */
	const getSessionKey = async (commitment: HexString): Promise<SessionKeyData | null> => {
		const storageKey = `${SESSION_KEY_PREFIX}${commitment}`
		const value = await baseStorage.getItem<string>(storageKey)
		if (!value) return null

		try {
			return JSON.parse(value) as SessionKeyData
		} catch {
			return null
		}
	}

	/**
	 * Gets a session key by session key address
	 */
	const getSessionKeyByAddress = async (address: HexString): Promise<SessionKeyData | null> => {
		const storageKey = `${SESSION_KEY_ADDRESS_PREFIX}${address.toLowerCase()}`
		const value = await baseStorage.getItem<string>(storageKey)
		if (!value) return null

		try {
			return JSON.parse(value) as SessionKeyData
		} catch {
			return null
		}
	}

	/**
	 * Stores a session key for an order commitment
	 */
	const setSessionKey = async (commitment: HexString, data: SessionKeyData): Promise<void> => {
		const storageKey = `${SESSION_KEY_PREFIX}${commitment}`
		await baseStorage.setItem(storageKey, JSON.stringify(data))
	}

	/**
	 * Stores a session key for a session key address
	 */
	const setSessionKeyByAddress = async (address: HexString, data: SessionKeyData): Promise<void> => {
		const storageKey = `${SESSION_KEY_ADDRESS_PREFIX}${address.toLowerCase()}`
		await baseStorage.setItem(storageKey, JSON.stringify(data))

	/**
	 * Signs a `SelectSolver` EIP-712 message with a session key.
	 *
	 * The session key authorises the selection of a specific solver for the
	 * given order commitment. The resulting signature is appended to the
	 * solver's UserOperation signature before bundle submission.
	 *
	 * @param commitment - The order commitment (bytes32) being fulfilled.
	 * @param solverAddress - Address of the solver account selected to fill the order.
	 * @param domainSeparator - EIP-712 domain separator for the IntentGatewayV2 contract.
	 * @param privateKey - Hex-encoded private key of the session key that signs the message.
	 * @returns The ECDSA signature as a hex string, or `null` if signing fails.
	 */
	static async signSolverSelection(
		commitment: HexString,
		solverAddress: HexString,
		domainSeparator: HexString,
		privateKey: HexString,
	): Promise<HexString | null> {
		const account = privateKeyToAccount(privateKey as Hex)

		const structHash = keccak256(
			encodeAbiParameters(
				[{ type: "bytes32" }, { type: "bytes32" }, { type: "address" }],
				[SELECT_SOLVER_TYPEHASH, commitment, solverAddress],
			),
		)

		const digest = keccak256(concat(["0x1901" as Hex, domainSeparator as Hex, structHash]))
		const signature = await account.sign({ hash: digest })

		return signature as HexString
	}

    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }
