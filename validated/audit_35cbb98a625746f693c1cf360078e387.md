### Title
Stale line-selection indices cause silent corruption of partially-committed content - ([File: app/src/lib/patch-formatter.ts])

### Summary
When a user performs a partial commit (selecting individual lines/hunks to stage), Desktop stores the selection as a set of *absolute line indices* (`DiffSelection`) computed against the diff that was loaded when the user made the selection. At commit time, Desktop re-fetches a brand-new diff of the file and blindly re-applies the old index-based selection to it without verifying the underlying content still matches. If the tracked file changes on disk between "select lines" and "click Commit" (a window that is normally open for as long as it takes the user to write a commit message), the new diff's line indices can silently point at different content than what the user reviewed, producing a commit that does not match what the user intended to stage.

### Finding Description
`formatPatch` builds the patch that is fed to `git apply --cached` purely from `hunk.unifiedDiffStart + lineIndex` (an absolute integer offset) checked against `file.selection.isSelected(absoluteIndex)`: [1](#0-0) 

This `file.selection` object is created/mutated in the renderer while the user is looking at a diff that was fetched earlier and cached in `changesState.selection.diff`. The commit path, however, does not use that cached diff — `applyPatchToIndex` re-runs `getWorkingDirectoryDiff` fresh at commit time and feeds the *old* selection object into `formatPatch` against this *new* diff: [2](#0-1) 

`_commitIncludedChanges` reads whatever `file.selection` currently sits in `changesState.workingDirectory.files` and passes it straight to `createCommit` without first forcing a synchronous re-validation of the selection against a fresh diff: [3](#0-2) 

The only reconciliation that exists, `updateChangesWorkingDirectoryDiff`, is asynchronous, triggered only by file/selection changes, and — even when it does run — merely intersects the old diverging-line set with the new diff's *selectable line count*, not with the actual content at each index: [4](#0-3) 

`DiffSelection` itself is a bare set of integer indices with no notion of line content, so as long as the new diff happens to have a line at the same offset that is still "includeable," the selection is considered valid regardless of whether that line is the same line the user actually reviewed: [5](#0-4) 

This mirrors the reported bug class exactly: a numeric result (`sharesToMint` / here, the set of "selected" absolute indices) is computed against one snapshot of mutable state (`totalSupply()` / the diff at selection time) and then applied after that state has changed (`totalSupply()` post-mint / the diff at commit time), producing a value that no longer reflects the original intent — silently.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes," an explicitly valid impact category. A working-directory file that is modified by an external, attacker-influenced process (e.g., a build/watch script or git hook shipped in a cloned/fetched malicious repository) between the moment the user makes a partial-line selection and the moment they finish typing their commit message and click Commit can cause Desktop to stage and commit different content than what the user reviewed and explicitly selected — potentially including attacker-injected lines or omitting lines the user intended to keep, with no visual warning that the selection is stale relative to the freshly fetched diff.

### Likelihood Explanation
Partial-line commit selection combined with a commit-message-typing delay is a common workflow, giving a realistic window for a concurrently running process (spawned by repository tooling from the cloned/fetched repo, e.g. lint-staged/watchers/hooks) to mutate the file. No local/physical access or leaked credentials are required — only that the victim opens/uses a repository whose tooling can touch tracked files during normal use, and that they use the standard partial-staging feature. The guard code that exists (`updateChangesWorkingDirectoryDiff`) only prunes indices that no longer exist; it does not re-verify content identity, so the race is not actually closed.

### Recommendation
Before applying `file.selection` in `applyPatchToIndex`/`formatPatch`, re-diff the file synchronously as part of the commit operation and compare it (e.g., via content hash of the diff/hunks, or by validating that each selected line's exact text matches what was selected) against the diff that produced the current selection state. If the diff has changed, either abort and force the user to re-review, or remap indices based on line content rather than raw integer offsets. At minimum, `_commitIncludedChanges` should perform this freshness check right before staging, not rely solely on the best-effort background reconciliation in `updateChangesWorkingDirectoryDiff`.

### Proof of Concept
1. In a cloned repository, tracked file `foo.txt` contains 10 lines; user opens the diff view and partially selects lines 3–5 to stage for commit, intending to leave lines 6-10 unstaged.
2. Before the user clicks "Commit," an external process (e.g., a git hook, editor auto-format, or watch script triggered by repository tooling from the cloned repo) rewrites `foo.txt`, shifting/altering content such that the new diff still has an includeable line at absolute indices 3–5, but that line now contains different (attacker-influenced) content, while the "same-looking" selection state is preserved because `updateChangesWorkingDirectoryDiff`'s reconciliation only checks that indices 3–5 are still "selectable," not that they are the same text.
3. User clicks Commit. `applyPatchToIndex` (app/src/lib/git/apply.ts:60) re-fetches the diff and `formatPatch` (app/src/lib/patch-formatter.ts:143-157) stages whatever now occupies absolute indices 3–5 in the new diff — silently committing unintended content the user never reviewed or approved.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
