Based on my investigation, I found a concrete local analog in the Tron variant of the Intent Gateway's escrow-release logic. I was not able to fully close the loop on a complete unprivileged exploit chain within my exploration budget (see caveats at the end), so I present this with appropriate confidence qualifiers rather than an unconditional confirmed exploit.

### Title
Escrow ledger updated after external token transfer in `withdraw()` (checks-effects-interactions violation) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The seed report's core defect is a state transition to a "final/successful" status that fails to verify the invariant it is supposed to guarantee before committing to it (raising to `ICOSuccessful` without checking `raisedWei >= minRaiseWei`). The closest locally provable analog in Hyperbridge is in the Tron `IntentGatewayV2.withdraw()` function, which finalizes escrow release (transfers funds to `beneficiary`) **before** updating the escrow ledger (`_orders[...] -= amount`), and only guards against total depletion with an `== 0` check rather than confirming `amount <= escrowed` beforehand.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` performs the external transfer first and decrements accounting state second: [1](#0-0) 

Compare this to the sibling, more defensive implementation in the primary EVM app, `IntentsBase._withdraw()`, which updates `_orders[...]` **before** making the external call: [2](#0-1) 

The Tron version's check `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` only rejects a fully-drained escrow slot — it does not verify `amount` (taken from the `WithdrawalRequest` decoded from a cross-chain `RedeemEscrow`/`RefundEscrow` message body) against the actual escrowed balance before dispatching funds, and the ledger write that would normally prevent reentrant double-spend happens only after the external call/transfer completes.

### Impact Explanation
If `order.inputs` includes a token contract that the order's own creator/solver controls (attacker-supplied ERC-20, e.g. with ERC-777-style transfer hooks), the low-level `token.call(...)` in the withdraw loop hands control to attacker code before `_orders[body.commitment][token]` is decremented. This is the same class of bug as the seed report: an irreversible state effect (fund transfer) is executed before the invariant that is supposed to gate it (sufficient/consistent escrow accounting) is finalized. This maps to the bounty's "stealing or loss of funds" / "double-claim or double-settlement" categories, since the accounting write that should prevent re-entrant reuse of the same escrow slot trails the external interaction.

### Likelihood Explanation
Medium-to-low confidence. `_filled[body.commitment]` is set to the beneficiary at the very top of `withdraw()`, before the token loop, which blocks the most obvious reentrant path back into `cancelOrder()`/`fillOrder()` for the *same* commitment (both check `_filled != address(0)` and revert `Filled()`). I was not able to identify, within the available exploration, another public unguarded entry point that reads/writes the same `(commitment, token)` escrow slot mid-transfer, so I could not fully confirm a working double-spend chain — only the structural CEI violation and the weaker `== 0` (vs. `< amount`) balance check, which is a real deviation from the safer pattern used elsewhere in the same codebase (`IntentsBase._withdraw`).

### Recommendation
- In `evm/tron/contracts/apps/IntentGatewayV2.sol` `withdraw()`, mirror `IntentsBase._withdraw()`: decrement `_orders[body.commitment][token]` **before** performing the native/ERC-20 transfer, and revert if `amount > escrowed` rather than only checking `== 0`.
- Add a reentrancy guard (`nonReentrant`) to `withdraw()`/`onAccept()` for defense in depth, consistent with other value-moving entry points in the codebase.
- Audit all `_orders`/`_filled` mutation sites in the Tron contract for other checks-effects-interactions ordering issues, since this file appears to have drifted from the safer pattern in the primary EVM implementation.

### Proof of Concept
Not fully constructed — I could not identify, within the available tool budget, a concrete unguarded re-entrant call path (given the early `_filled` write) to complete an end-to-end double-withdrawal. A conclusive PoC would require tracing `placeOrder`, `fillOrder`, and all `_orders`-mutating functions in `evm/tron/contracts/apps/IntentGatewayV2.sol` in full (not all of which I was able to read), ideally in a Devin session with file/terminal access to compile and fuzz-test the contract against a malicious ERC-777-style token as `order.inputs[i].token`.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
