## Confirmed status parsing (`git status --porcelain=v2 -z`)

`git status` is invoked with `-z` / porcelain v2 machine-readable format so paths there are **not** quoted/escaped, giving raw byte paths in `entry.path` [1](#0-0) . But `getFilesWithConflictMarkers()` shells out to `git diff --check` — a **human-readable** porcelain-less command that has no `-z`/machine mode — and parses its text output with a naive regex, keying the resulting map by whatever string the regex captured [2](#0-1) . Git has no `core.quotepath=false` override configured anywhere in the codebase (confirmed no occurrences of `quotepath` or `-c core.` in the tree), so Git's default path-quoting/C-style escaping for special/non-ASCII bytes applies to this command's output. That means the key produced by `getFilesWithConflictMarkers` can differ from the raw `entry.path` used everywhere else, causing the lookup `conflictCountsByPath.get(path) || 0` in `parseConflictedState`/`getMergeConflictDetails`/`getRebaseConflictDetails`/`getWorkingDirectoryConflictDetails` to silently miss and fall back to `0` [3](#0-2) [4](#0-3) .

This `conflictMarkerCount` is the exact "queuedShares"-style accounting field: `hasUnresolvedConflicts()` treats `conflictMarkerCount > 0` as the sole ground truth for "this file still needs resolving" [5](#0-4) , and `getConflictedFiles`/`getResolvedFiles` (which gate the Continue/Commit button in the Conflicts dialog) rely on it directly [6](#0-5) . `stageManualConflictResolution` also short-circuits and skips checking out ours/theirs whenever `conflictMarkerCount === 0`, assuming the user already fixed it in an editor [7](#0-6) .

### Title
Miscounted conflict markers for quoted/escaped file paths lets Desktop commit files with unresolved conflict markers - (File: `app/src/lib/git/diff-check.ts`)

### Summary
`getFilesWithConflictMarkers()` parses the human-readable text of `git diff --check` with a regex and keys the resulting count map by the captured string. Git quotes/C-escapes paths containing special or non-ASCII bytes in this human output (no `-z`/porcelain flag is used, and `core.quotepath` is never disabled by Desktop). Every other code path (`git status --porcelain=v2 -z`) uses the raw, unescaped path. For a conflicted file whose path triggers Git's default quoting, the two path representations don't match, so `conflictCountsByPath.get(path)` misses and `conflictMarkerCount` silently defaults to `0` even though the file still contains live `<<<<<<<`/`=======`/`>>>>>>>` markers.

### Finding Description
`getFilesWithConflictMarkers` regex `^(.+):\d+: leftover conflict marker` captures group 1 verbatim from `git diff --check` stdout [8](#0-7) . That map is later consulted with the plain path taken from `git status` entries: `conflictDetails.conflictCountsByPath.get(path) || 0` [9](#0-8) . If the two strings differ — which happens whenever `git diff --check`'s path rendering diverges from the porcelain-v2 path (e.g. quoting/escaping of special characters) — the lookup returns `undefined` and the `|| 0` fallback silently reports zero conflict markers for a file that is, in fact, still full of raw conflict markers on disk.

This corrupted `conflictMarkerCount` of `0` then propagates through the single function the whole conflict-resolution UI/flow trusts as ground truth, `hasUnresolvedConflicts()` [10](#0-9) :
- The Conflicts dialog computes `conflictedFiles.length` via `getConflictedFiles()` to decide whether the "Continue"/commit button is enabled [11](#0-10)  — the file will appear as already resolved and no longer block the flow.
- `stageManualConflictResolution` explicitly bails out and does not perform any `checkout --ours/--theirs`, assuming "the user manually resolved the conflicts via an editor" whenever `conflictMarkerCount === 0` [7](#0-6) , leaving the file's raw, marker-laden content untouched on disk and in the index.
- `createMergeCommit`/`continueRebase`/`continueCherryPick` then stage and commit whatever is on disk for that file without further validation [12](#0-11) [13](#0-12) .

The net effect: the user clicks "Continue"/commits believing the merge/rebase is fully resolved, but Desktop actually commits and can subsequently push a file containing literal, uncompiled/unbuildable conflict-marker text — a silent corruption of what the user commits and pushes, exactly the class of impact called out as valid (silent corruption caused by an attacker-controlled repository/branch that the victim merges).

### Impact Explanation
An attacker who controls a branch/fork that the victim merges, rebases onto, or pulls (a very ordinary collaboration action) can craft a commit that conflicts with the victim's branch in a file whose name triggers Git's default path quoting (non-ASCII characters, embedded control/special bytes, etc.). When Desktop reports the merge conflict, this file is shown as already resolved (`0` conflicts) regardless of its real content. If the user trusts the UI and proceeds, Desktop silently commits — and the user may subsequently push — a file that still contains raw conflict markers, which can break builds, silently reintroduce or hide the attacker's or victim's intended change, or (in interpreted contexts, e.g. config/script files) execute unintended, malformed code paths. This is a genuine "silent corruption of what the user commits or pushes" bug driven purely by attacker-controlled repository content, no elevated privileges or local access required.

### Likelihood Explanation
Triggering it only requires the attacker to name a conflicting file with characters Git considers "special" for its default human-readable quoting (which is Git's out-of-the-box behavior and not overridden anywhere in this codebase), and get the victim to merge/rebase/cherry-pick against that branch — a routine, unprivileged, single-click Desktop workflow. No social engineering beyond a normal PR/branch merge is needed, and the corrupted state is invisible in the UI (the dialog reports "All conflicted files have been resolved").

### Recommendation
Do not rely on parsing `git diff --check`'s human-oriented text output for anything used to gate resolution decisions. Either:
- Pass `-z` (or another machine-parseable option) to `git diff --check` if available and update the parser to consume the NUL-delimited stream, or
- Run Git with `-c core.quotepath=false` (and handle backslash/other必须 escapes explicitly) so paths are not ambiguously encoded, or
- Cross-validate: never let a path lookup miss silently degrade to "0 conflicts" — instead, if a conflicted file (per `git status`) has no corresponding entry in `conflictCountsByPath`, treat it as still unresolved (fail closed) rather than resolved (fail open), and log/report the mismatch as a non-fatal exception for investigation.

### Proof of Concept
1. Attacker creates a repo/branch with a file whose name contains a Git-quotable character (e.g. a filename with an accented/non-ASCII character or an embedded double-quote), and edits it so that merging it against the victim's branch produces a real text conflict with `<<<<<<<`/`=======`/`>>>>>>>` markers.
2. Victim, using GitHub Desktop, merges/rebases/cherry-picks the attacker's branch. `getStatus` reports the file as `Conflicted` via `git status --porcelain=v2 -z` with its raw (unescaped) path [14](#0-13) .
3. `getMergeConflictDetails`/`getRebaseConflictDetails` call `getFilesWithConflictMarkers`, which runs `git diff --check`; because of the special character, Git quotes/escapes the path in this output, so the regex-captured key differs from the raw path.
4. `conflictCountsByPath.get(path)` misses, `conflictMarkerCount` is set to `0` for the file even though it still contains conflict markers [9](#0-8) .
5. The Conflicts dialog's `getConflictedFiles()` excludes this file from the "still conflicted" count and enables Continue/commit [15](#0-14) ; `stageManualConflictResolution` (if invoked) is a no-op for it due to the `conflictMarkerCount === 0` short-circuit [7](#0-6) .
6. The user clicks Continue; `createMergeCommit`/`continueRebase` stages and commits the file's on-disk content verbatim — including the literal conflict markers — producing a corrupted commit that the user may then push [12](#0-11) .

Note: I was not able to execute Git locally to empirically confirm the exact quoting trigger set (this analysis is based on Git's documented default `core.quotepath=true` behavior and the absence of any override in this codebase); a Devin session with terminal access would be needed to reproduce the exact byte-for-byte PoC against a live Desktop build.

export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files
}

 * Determine if we have any conflict markers or if its been resolved manually

export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}
