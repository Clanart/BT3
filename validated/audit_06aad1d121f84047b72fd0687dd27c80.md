## Title
`aptos move verify-package` never fetches or compares actual on-chain bytecode, so a package with substituted module bytecode is reported as "verified" - (File: aptos-move/cli/src/commands.rs)

## Summary
The `VerifyPackage` CLI command documents itself as "verif[ying] the bytecode matches a local compilation of the Move code," but `VerifyPackage::execute` calls `CachedPackageRegistry::create(client, self.account, false)` with `with_bytecode = false`, and the subsequent `package.verify(&compiled_metadata)` call in `CachedPackageMetadata::verify` (`aptos-move/cli/src/stored_package.rs`) only diff-checks the on-chain `PackageMetadata` struct fields (`name`, `deps`, `modules`, `manifest`, `upgrade_policy`, `extension`, `source_digest`) against a freshly-built local `PackageMetadata`. It never fetches, deserializes, or compares the actual deployed module bytecode. Since `PackageMetadata` (including its `source`, `source_map`, and `source_digest` fields) is arbitrary, attacker-controlled data passed by the publisher to `code::publish_package_txn`, and is never derived from or checked against the real bytecode bundle by the Move VM or the `aptos_framework::code` module, a malicious publisher can submit legitimate-looking source metadata alongside a completely different compiled bytecode bundle. `verify-package` will report "Successfully verified source of package" while the code actually executing on-chain differs from what was verified.

## Finding Description
`aptos_framework::code::publish_package` (`aptos-move/framework/aptos-framework/sources/code.move:159-231`) and the underlying native `request_publish`/`request_publish_with_allowed_deps` (`aptos-move/framework/natives/src/code.rs:264-360`, validated in `aptos-move/aptos-vm/src/aptos_vm.rs::validate_publish_request` at lines 1803-1863) only check:
- that compiled module addresses match the sender,
- that module *names* in the bytecode bundle match the `expected_modules` set derived from `PackageMetadata.modules[].name`,
- dependency/allowed-dep and upgrade-policy/compatibility rules.

None of these checks validate that `PackageMetadata.modules[].source` / `source_map` / the package-level `source_digest` actually correspond to the submitted bytecode blobs (`code: vector<vector<u8>>`). These metadata fields are pure user-supplied annotations, stored verbatim in the on-chain `PackageRegistry` resource<cite repo="blackvul/aptos-core--014" path="aptos-move/framework/aptos-framework/sources/code.move" start="27="47" /> [1](#0-0) , and are only intended to let downstream tooling reconstruct/verify the source.

The reconstruction/verification tooling is `aptos move verify-package`: [2](#0-1) 

Note line 2121: `CachedPackageRegistry::create(client, self.account, false)` — bytecode fetching is explicitly disabled (`with_bytecode = false`), even though `CachedPackageRegistry::create` supports fetching real module bytecode via `client.get_account_module` when `with_bytecode` is `true`: [3](#0-2) 

The actual comparison performed by `verify()` is purely metadata-to-metadata: [4](#0-3) 

Every field compared here (`name`, `deps`, `modules` — which is `ModuleMetadata{name, source, source_map, extension}`, `manifest`, `upgrade_policy`, `extension`, `source_digest`) originates from the same `PackageMetadata` BCS blob that the original publisher freely constructed and submitted in the publish transaction; none of it is cross-checked by the VM against the real bytecode bytes at publish time. Consequently, an attacker can:
1. Compile and publish a package where the actual `code: vector<vector<u8>>` bundle contains malicious logic (as long as module names match the declared `expected_modules` and it type-/compat-checks against any prior version).
2. Populate `PackageMetadata.modules[].source`/`source_map` and `source_digest` with the gzip of an entirely different, benign-looking source tree (or an intentionally-crafted one that compiles to a distinct semantic result but produces a matching `source_digest`/module-name set).
3. Anyone running `aptos move verify-package --account <addr>` gets `"Successfully verified source of package"` because the tool never downloads or compares the real deployed bytecode.

This directly matches the required impact: "Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes."

## Impact Explanation
This breaks the code-safety guarantee that the CLI's `verify-package` — the mainnet-documented mechanism third parties and auditors rely on to confirm "the on-chain copy matches" a locally built, audited package (see `third_party/move/documentation/book/src/cli-deploy.md:70-83`) — actually reflects the code executing on-chain. Users, auditors, indexers, and dependent-package developers who trust a "verified" package (e.g., before adding it as a dependency, or before treating a `compatible`/`immutable` package as safe to build on) can be misled into trusting bytecode that was never actually inspected. Given that source-code verification is explicitly promoted in the docs as the tool to establish trust for dependency packages ("If you have a dependency on a `compatible` package, it is highly recommended you know and understand the entity publishing the package" — verify-package is the tool meant to support that), a successful "verified" result with divergent real bytecode is a high-impact trust/authenticity failure, though it does not directly let an attacker seize governance or forge signatures.

## Likelihood Explanation
Likelihood is high for any package published permissionlessly (which is the norm on Aptos): nothing in the VM, natives, or `aptos_framework::code` module ties `PackageMetadata.source`/`source_digest` to the actual bytecode. Any publisher who wants to mislead auditors into trusting mismatched bytecode simply needs to submit metadata independent from the code bundle — no special privilege or governance step is required, and the current `VerifyPackage::execute` implementation (with `with_bytecode = false`) guarantees this is never caught by the tool advertised for exactly this purpose.

## Recommendation
- In `VerifyPackage::execute` (`aptos-move/cli/src/commands.rs`), call `CachedPackageRegistry::create(client, self.account, true)` to fetch real on-chain bytecode for every module.
- Extend `CachedPackageMetadata::verify` (or add a new check in `VerifyPackage::execute`) to compile the local package to bytecode and byte-for-byte compare each module's fetched on-chain bytecode against the freshly compiled local bytecode, in addition to the existing metadata-field comparisons.
- Update the CLI documentation/help text to accurately state what is verified until the code-level fix lands, since currently the doc-string overstates the guarantee.

## Proof of Concept
1. Build package `Legit` locally; compute its `PackageMetadata` (`extract_metadata()`), including `source_digest` and gzip'd sources.
2. Compile a semantically different bytecode bundle `Malicious` (same module names as `Legit`, so `expected_modules` checks pass; ensure it's a valid upgrade or fresh publish satisfying `Compatibility`/`check_upgradability`).
3. Publish via `code::publish_package_txn(owner, bcs::to_bytes(&legit_metadata), malicious_code_bundle)` — the VM only validates module names/compatibility/dependencies, not that `malicious_code_bundle` matches `legit_metadata.modules[].source`.
4. Run `aptos move verify-package --account <owner-address>` against a local checkout of `Legit`'s real source: `VerifyPackage::execute` fetches only `PackageRegistry` metadata (`with_bytecode=false`), compares it field-by-field to the locally rebuilt `Legit` metadata, finds all fields equal (since the publisher used `Legit`'s real metadata), and prints `"Successfully verified source of package"` — despite the deployed bytecode actually being `Malicious`.

Note: this analysis is based on static code reading of `aptos-move/cli/src/commands.rs`, `aptos-move/cli/src/stored_package.rs`, `aptos-move/framework/aptos-framework/sources/code.move`, `aptos-move/framework/natives/src/code.rs`, and `aptos-move/aptos-vm/src/aptos_vm.rs` in this indexed snapshot; I was not able to execute the CLI or a live devnet to empirically confirm the exact output string/behavior, so the PoC steps above are traced from source rather than observed at runtime.

#[async_trait]
impl CliCommand<&'static str> for VerifyPackage {
    fn command_name(&self) -> &'static str {
        "VerifyPackage"
    }

    async fn execute(self) -> CliTypedResult<&'static str> {
        // First build the package locally to get the package metadata
        let build_options = BuildOptions {
            install_dir: self.move_options.output_dir.clone(),
            bytecode_version: fix_bytecode_version(
                self.move_options.bytecode_version,
                self.move_options.language_version,
            ),
            ..self.included_artifacts.build_options(&self.move_options)?
        };
        let w = self.env.writer();
        let pack = BuiltPackage::build_to(&w, self.move_options.get_package_path()?, build_options)
            .map_err(|e| CliError::MoveCompilationError(format!("{:#}", e)))?;
        let compiled_metadata = pack.extract_metadata()?;

        // Now pull the compiled package
        let client = self.rest_options.client(&self.profile_options)?;
        let registry = CachedPackageRegistry::create(client, self.account, false).await?;
        let package = registry
            .get_package(pack.name())
            .await
            .map_err(|s| CliError::CommandArgumentError(s.to_string()))?;

        // We can't check the arbitrary, because it could change on us
        if package.upgrade_policy() == UpgradePolicy::arbitrary() {
            return Err(CliError::CommandArgumentError(
                "A package with upgrade policy `arbitrary` cannot be downloaded \
                since it is not safe to depend on such packages."
                    .to_owned(),
            ));
        }

        // Verify that the source digest matches
        package.verify(&compiled_metadata)?;

        Ok("Successfully verified source of package")
    }

impl CachedPackageRegistry {
    /// Creates a new registry.
    pub async fn create(
        client: Client,
        addr: AccountAddress,
        with_bytecode: bool,
    ) -> anyhow::Result<Self> {
        // Need to use a different type to deserialize JSON
        let inner = client
            .get_account_resource_bcs::<PackageRegistry>(addr, "0x1::code::PackageRegistry")
            .await?
            .into_inner();
        let mut bytecode = BTreeMap::new();
        if with_bytecode {
            for pack in &inner.packages {
                for module in &pack.modules {
                    let bytes = client
                        .get_account_module(addr, &module.name)
                        .await?
                        .into_inner()
                        .bytecode
                        .0;
                    bytecode.insert(module.name.clone(), bytes);
                }
            }
        }
        Ok(Self { inner, bytecode })
    }

    pub fn verify(&self, package_metadata: &PackageMetadata) -> anyhow::Result<()> {
        let self_metadata = self.metadata;

        if self_metadata.name != package_metadata.name {
            bail!(
                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name
            )
        } else if self_metadata.deps != package_metadata.deps {
            bail!(
                "Dependencies don't match {:?} : {:?}",
                package_metadata.deps,
                self_metadata.deps
            )
        } else if self_metadata.modules != package_metadata.modules {
            bail!(
                "Modules don't match {:?} : {:?}",
                package_metadata.modules,
                self_metadata.modules
            )
        } else if self_metadata.manifest != package_metadata.manifest {
            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
            )
        } else if self_metadata.upgrade_policy != package_metadata.upgrade_policy {
            bail!(
                "Upgrade policy doesn't match {:?} : {:?}",
                package_metadata.upgrade_policy,
                self_metadata.upgrade_policy
            )
        } else if self_metadata.extension != package_metadata.extension {
            bail!(
                "Extensions doesn't match {:?} : {:?}",
                package_metadata.extension,
                self_metadata.extension
            )
        } else if self_metadata.source_digest != package_metadata.source_digest {
            bail!(
                "Source digests doesn't match {:?} : {:?}",
                package_metadata.source_digest,
                self_metadata.source_digest
            )
        }

        Ok(())
    }
