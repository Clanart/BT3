## Finding

### Title
Live decimals re-fetch after decimal validation is only checked once at registration allows silent mis-scaling of bridged amounts - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The Hyper Fungible Token pallet's decimal-scaling invariant (`erc_decimals >= local_decimals`) is enforced only once, at `register_token`/`update_token` time, using a snapshot of the asset's decimals read from `fungibles::metadata::Inspect`. Every subsequent `send`, `on_accept`, and `on_timeout` call re-reads the asset's *live* decimals from the same `Inspect` trait rather than trusting a stored, immutable value, and feeds it into `convert_to_erc20`/`convert_to_balance`, which use `saturating_sub` to compute the scaling exponent.

### Finding Description
`register_token` and `update_token` validate the decimal relationship once: [1](#0-0) 

But the actual amount conversion used on every transfer re-derives `local_decimals` live rather than from a stored snapshot: [2](#0-1) [3](#0-2) 

The conversion helpers use `saturating_sub`, which silently clamps to zero instead of erroring when the assumed ordering (`erc_decimals >= local_decimals`) no longer holds: [4](#0-3) 

If the underlying local asset's decimals metadata is mutated after registration (e.g. via `pallet-assets::set_metadata`, which is controlled by the asset's `Issuer`/owner — a role separate from `T::CreateOrigin` that governs this pallet) such that `local_decimals` becomes greater than the `erc_decimals` value frozen in `Precisions` storage, `convert_to_erc20`'s `erc_decimals.saturating_sub(local_decimals)` silently evaluates to `0`. Instead of dividing the value down by `10^(local_decimals - erc_decimals)` as correctness would require, the function multiplies by `10^0 = 1`, encoding an ERC20 amount that is `10^(local_decimals - erc_decimals)` times too large into the outgoing ISMP `Message` dispatched to the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract. On accept, that inflated amount is minted/released to the beneficiary on the destination chain, while only the original (much smaller) local amount was burned/escrowed on the source chain.

This is structurally identical to the referenced ZCToken bug: a decimal assumption baked in at one point in time is not re-validated on the code path that actually determines the token amount that moves, producing a silent order-of-magnitude accounting mismatch.

### Impact Explanation
An amount mismatch between what is burned/escrowed on the source chain and what is minted/released on the destination chain is a direct fund-creation/fund-loss bug. If exploitable, it lets a party controlling an under-decimaled bridged asset over-mint on the destination chain relative to what was actually locked/burned on the source, i.e., unauthorized value creation across the bridge — squarely within "stealing or loss of funds" / "transaction manipulation" per the bounty scope.

### Likelihood Explanation
The likelihood is moderate to low and depends on facts not fully verifiable from the indexed code: (1) whether the runtime's configured `Assets` implementation (a generic `fungibles::Mutate + metadata::Inspect` type) permits the decimals of an already-registered asset to be changed post-registration, and (2) whether the actor able to make that change (the asset's `Issuer`, not `T::CreateOrigin`) is considered untrusted relative to the HFT pallet's registration admin. If asset decimals are immutable once fixed in the concrete runtime's `pallet-assets` configuration, this path is not exploitable and the register-time check is fully sufficient. This uncertainty could not be resolved from the indexed code, since the parachain runtime's concrete `Assets` type configuration and its metadata-mutation permissions were not located in the available index.

### Recommendation
- Snapshot and store `local_decimals` (or the resulting scaling factor) in pallet storage at `register_token` time rather than re-deriving it live from `fungibles::metadata::Inspect` on every `send`/`on_accept`/`on_timeout`.
- Replace `saturating_sub` in `convert_to_erc20`/`convert_to_balance` with checked/`ensure!`-based arithmetic that hard-fails (rather than silently defaulting to a zero exponent) whenever `erc_decimals < local_decimals` is observed at conversion time, matching the invariant enforced at registration.
- Re-verify the `erc_decimals >= local_decimals` invariant defensively inside `send`/`on_accept`/`on_timeout`, not only in `register_token`/`update_token`.

### Proof of Concept
Not independently executable from the indexed code alone — a concrete PoC requires confirming that the concrete `Assets` implementation used by a live Hyperbridge parachain runtime allows an asset's `decimals` metadata to be changed after `register_token` has fixed a lower `erc_decimals` in `Precisions` storage. Conceptually:
1. Register asset `T` (non-native, `native=false`) with `local_decimals = 6` at registration time, and `erc_decimals = 6` for destination chain `C` (passes `ErcDecimalsBelowLocal` check).
2. Asset `Issuer` calls the underlying assets pallet's metadata-update extrinsic to raise `T`'s decimals to `18`.
3. Call `HyperFungibleToken::send` with `asset_id = T`, `destination = C`. `local_decimals` is now read live as `18`; `erc_decimals` from `Precisions` is still `6`. `convert_to_erc20` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so the encoded ERC20 amount equals the raw local (18-decimal) balance value instead of being divided down by `10^12`.
4. The destination `HyperFungibleToken` contract mints/releases an amount `10^12`x larger than the value actually burned/escrowed on the source chain.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
