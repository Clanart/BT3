### Title
Malformed MultiEdit `tool_input` triggers unhandled TypeError that fail-open bypasses a matching block rule - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field` builds the `new_text`/`content` field for `MultiEdit` by joining `e.get('new_string', '')` over each edit dict without validating types, so a crafted `edits` entry (e.g. `{'new_string': None}`, or a non-dict entry) raises a `TypeError`/`AttributeError`. That exception propagates out of `evaluate_rules()` into `pretooluse.py`'s blanket `except Exception` handler, which always exits `0` and never emits a `permissionDecision: deny`, so the operation proceeds even though a `block` rule was configured to match it.

### Finding Description
`_extract_field` for `MultiEdit` does: [1](#0-0) 
`e.get('new_string', '')` only substitutes the default `''` when the key `new_string` is *absent*; if the key is present but its value is `None` (attacker-controlled `tool_input.edits = [{'new_string': None}]`), `.get` returns `None`, and `' '.join(...)` over a generator containing `None` raises `TypeError: sequence item 0: expected str instance, NoneType found`. If an `edits` entry is not a dict at all (e.g. a string), `e.get` raises `AttributeError` instead. Both exceptions occur while `_check_condition` calls `_extract_field`: [2](#0-1) 
This propagates unhandled through `_rule_matches` and `evaluate_rules` up to `pretooluse.py`'s `main()`, which wraps the whole evaluation in a generic `try/except Exception` that always logs a `systemMessage` and unconditionally calls `sys.exit(0)` in the `finally` block: [3](#0-2) 
Because the exception is caught before `evaluate_rules` can return a `hookSpecificOutput.permissionDecision: "deny"` for a matching `block`-action rule, the hook output degrades to a mere informational `systemMessage` with exit code `0`, which Claude Code treats as "no denial" — i.e., the tool call is allowed to proceed. An attacker who can influence the content of a `MultiEdit` (e.g., via generated file-edit instructions coming from repository content, or any flow where `edits` entries are built from untrusted input) can shape one `edits` entry to have `new_string: None` (or a non-dict item) specifically to crash rule evaluation and bypass a configured block rule on that same `MultiEdit` call.

### Impact Explanation
This is a `DENY_MEANS_DENY` invariant violation / security-control bypass: a hook-level `block` rule intended to prevent a dangerous file edit (e.g. writing secrets, disabling a security check, editing a protected file) can be silently neutralized by malformed `MultiEdit.edits` content, allowing the underlying disallowed edit to execute anyway. This maps to an unauthorized file action / approval-bypass class of impact.

### Likelihood Explanation
Trigger requires only that an ordinary (unprivileged) automation or an attacker-influenced `MultiEdit` call include an `edits` entry with `new_string: null` (or a non-object edit entry) — no special privileges are needed, and `tool_input` shape for `MultiEdit` calls is fully attacker/agent-controlled content that reaches `pretooluse.py` before any type validation. The condition is deterministic and reproducible every time such a malformed edit accompanies a `MultiEdit` invocation matched by a configured hookify rule with `field: new_text`/`content`.

### Recommendation
In `_extract_field`, defensively coerce/validate each edit entry before joining, e.g.:
```python
parts = []
for e in edits:
    if not isinstance(e, dict):
        continue
    ns = e.get('new_string')
    parts.append(ns if isinstance(ns, str) else '')
return ' '.join(parts)
```
More broadly, wrap `evaluate_rules()` invocation (or each condition check) so that any internal extraction/comparison failure defaults to treating the affected rule as matched/deny-safe (fail-closed for `block` rules) rather than allowing `pretooluse.py`'s top-level handler to silently downgrade a deny to an allow-with-message.

### Proof of Concept
Unit test in a new/existing test module for `rule_engine.py`:
```python
def test_multiedit_none_new_string_crashes_extraction():
    engine = RuleEngine()
    rule = Rule(
        name="block-secret-edit",
        enabled=True,
        event="file",
        action="block",
        conditions=[Condition(field="new_text", operator="contains", pattern="API_KEY")],
        message="Blocked!"
    )
    input_data = {
        "tool_name": "MultiEdit",
        "tool_input": {
            "file_path": "secret.py",
            "edits": [{"old_string": "x", "new_string": None}]
        }
    }
    with pytest.raises(TypeError):
        engine.evaluate_rules([rule], input_data)
```
Integration test simulating `pretooluse.py`: pipe the same `input_data` as stdin JSON into `pretooluse.main()`; assert the hook prints a JSON object without `hookSpecificOutput.permissionDecision == "deny"` and exits with code `0`, confirming the block rule was bypassed instead of denying the `MultiEdit`.
