I found a concrete analog: `clone()` in `app/src/lib/git/clone.ts` explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` on every clone, which disables Git's built-in clone-time protections that were added specifically to stop malicious repository content (submodule/symlink filesystem tricks such as CVE-2024-32002) from executing code or corrupting files outside the intended checkout tree during `--recursive` clone.

### Title
Git clone-time protection is explicitly disabled for every clone, re-exposing malicious-repository submodule/symlink attacks - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` always runs `git clone --recursive` with the environment variable `GIT_CLONE_PROTECTION_ACTIVE` hard-set to `'false'`. This variable exists in modern Git specifically to let `clone` (and its recursive submodule initialization) enforce protections against maliciously crafted repositories — e.g. submodules or symlinks whose paths collide with `.git` on case-insensitive/normalizing filesystems, which was the root cause of CVE-2024-32002 (arbitrary code execution via clone of a crafted repository). Desktop turns this protection off unconditionally for every clone it performs.

### Finding Description [1](#0-0) 

The `clone` function builds an execution environment and always includes `GIT_CLONE_PROTECTION_ACTIVE: 'false'`, then invokes `git clone --recursive -- url path`. Because `--recursive` is always passed, any submodules declared by the untrusted, attacker-supplied remote (`url` — fully attacker-controlled input, since Desktop clones arbitrary user-supplied GitHub/remote URLs) are initialized and checked out automatically as part of the same operation, and the safety check Git added to guard exactly this scenario is disabled.

This mirrors the structural pattern in the Notional bug report: a safety invariant that the surrounding code is *supposed* to rely on (`pr.supplyFactor == 0` while unsettled / Git's clone protection while cloning untrusted content) is not actually enforced at the moment it matters, and the calling code does not compensate — it just proceeds as if the guard were doing its job. Here, Desktop does not add any of its own equivalent protections (no case-collision path validation, no rejection of symlinked/nested `.git` paths in submodules) before disabling Git's own check.

The custom guard that does exist, `isClonePathSensitive`, only validates the top-level destination directory (`path`) against a fixed list of sensitive locations (home dir, `.ssh`, `.gnupg`, `.config`, `.gitconfig`) — it does nothing to validate the *contents* written by a recursive clone/submodule checkout, so it provides no protection against the class of attack `GIT_CLONE_PROTECTION_ACTIVE` was designed to stop. ### Impact Explanation
If a user clones (or Desktop performs any clone-and-recurse-submodules flow for) a malicious repository, and the underlying Git version's built-in mitigation for crafted submodule paths would normally kick in, that mitigation is deliberately switched off by this environment variable. Depending on the Git client version in use and filesystem case-sensitivity, this can allow a crafted repository to write files outside the intended submodule directory during the recursive clone (the class of bug `GIT_CLONE_PROTECTION_ACTIVE` exists to block), i.e. file write outside the repo boundary from cloning attacker-controlled content — squarely in the "attacker controls a cloned/fetched repository … result is code execution/file write outside the repo" category called out as valid impact.

### Likelihood Explanation
Likelihood depends on the installed Git version and platform (case-insensitive/case-normalizing filesystems such as default macOS/Windows are most exposed), and requires the user to clone attacker-controlled content, which is core, everyday Desktop functionality (any public/malicious repo URL a user is tricked into cloning). There is no other Desktop-side mitigation for the submodule/path-collision class of attack once this flag is disabled.

### Recommendation
Do not unconditionally disable `GIT_CLONE_PROTECTION_ACTIVE`. Remove the explicit override (letting Git's default of `true`/protection-enabled apply), and if there is a specific compatibility reason it was disabled, document it and add an equivalent explicit validation step (e.g., reject submodule paths that collide with `.git` under case-insensitive comparison, or defer submodule initialization to a separate, validated step) before performing `--recursive` clones of untrusted URLs.

### Proof of Concept
1. Take a Git version where `GIT_CLONE_PROTECTION_ACTIVE` is Git's mitigation toggle for crafted submodule/`.git`-colliding paths (post CVE-2024-32002 fix).
2. Host a malicious repository containing a submodule (or nested path) engineered to collide with `.git` on a case-insensitive filesystem, following the public disclosure pattern for CVE-2024-32002.
3. In GitHub Desktop, clone that repository URL via the normal Clone Repository flow, which calls `clone()` in `app/src/lib/git/clone.ts`.
4. Because `GIT_CLONE_PROTECTION_ACTIVE=false` is forced and `--recursive` is used, Git's protective check for this exact path-collision condition is bypassed during the automatic submodule checkout, allowing the malicious repository content to write into locations outside the intended submodule/clone directory. ` [1](#0-0) `

Note: I was not able to fully confirm from the indexed code why `GIT_CLONE_PROTECTION_ACTIVE` was explicitly set to `'false'` here (no comment or commit history was available in the index), so it's possible there is an undocumented compatibility rationale (e.g. a dugite/Git bundling version mismatch) — a Devin session with full repo/history access would be needed to check commit history and any related discussion before treating this as a confirmed regression rather than an intentional (if risky) workaround.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
