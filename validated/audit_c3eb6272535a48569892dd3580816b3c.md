### Title
Silent, unconfirmed rewrite of a repository's git remote URL from untrusted GitHub API metadata - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl()` compares the locally configured remote URL against the `clone_url` field of the `IAPIRepository` object returned by the GitHub API for the tracked `GitHubRepository`, and — if a small set of heuristic conditions hold — silently rewrites the user's local `origin` (or default) remote to the new URL via `gitStore.setRemoteURL()`, with no user confirmation, prompt, or diff view. [1](#0-0) 

### Finding Description
The function pulls `clone_url` straight from the API repository object and treats it as trustworthy input for rewriting the local git remote: [2](#0-1) 

The only checks performed before rewriting are: (1) the URL protocol (http/https/ssh) hasn't changed, and (2) the *previous* value of the remote still structurally matched the previously known `cloneURL` (owner/name/hostname triple via `urlMatchesRemote`): [3](#0-2) 

`urlMatchesRemote` only compares parsed hostname/owner/name components for structural equality — it never verifies that the *new* clone_url still refers to a repository the user actually intended to trust, nor does it ask the user before switching what future `git push`/`git fetch` operations will target: [4](#0-3) 

Because Desktop periodically refreshes `GitHubRepository` metadata from the API (e.g., after the repository is renamed or transferred on GitHub, which is fully controlled by whoever administers that GitHub repo — not necessarily the original user), the `clone_url` value is an attacker-influenceable "GitHub API object" per the task's valid-impact definition. If a repository the user has cloned is renamed/transferred (a routine, permission-having operation on GitHub, e.g. a maintainer handoff, or a case where an abandoned repo name is reclaimed by a different account), the next metadata refresh will cause Desktop to automatically call `setRemoteURL` and rewrite the user's local remote to the new address — with no diff, warning, or opt-in.

### Impact Explanation
This causes silent corruption of what the user pushes/fetches: their local remote configuration is changed to a new URL without their explicit awareness, driven purely by data returned from the API for the associated repository. Combined with credential helpers/cached tokens tied to the account, subsequent pushes could go to a different network endpoint/owner than the user believes, without ever showing them the change in the Repository Settings remote field (`app/src/ui/repository-settings/repository-settings.tsx` shows the remote URL is normally something the user edits explicitly and deliberately) [5](#0-4) . This matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
The precondition is an attacker (or any actor) having write/admin access to rename/transfer a GitHub repository the victim has previously cloned/tracked (e.g., a maintainer takeover, or a name being reclaimed after the original owner deletes their account/repo — a known GitHub "repojacking" scenario). No local access, malware, or leaked credentials are required by the victim; the trigger is purely the normal background repository-metadata refresh combined with a routine GitHub-side rename/transfer, both of which are within the "attacker controls a GitHub API object" threat model.

### Recommendation
Before silently rewriting a remote URL from API-sourced data, Desktop should surface the change to the user (e.g., a notice/dialog showing old vs. new remote URL) and require explicit confirmation, rather than calling `gitStore.setRemoteURL` automatically. At minimum, additional verification (e.g., cross-checking the repository's database ID rather than owner/name string matching alone) should be used to avoid conflating "renamed same repository" with "different repository now occupying the URL."

### Proof of Concept
1. User clones `github.com/org/project` in Desktop; Desktop tracks the associated `GitHubRepository` and its `origin` remote.
2. The repository is later renamed or transferred (or the name is reclaimed by a different account) on GitHub — an action entirely under the control of whoever administers the repo, not the victim.
3. On the next background repository refresh, `updateRemoteUrl` receives the updated `IAPIRepository.clone_url` and, because protocol matches and the previous remote matched the previous `cloneURL`, calls `gitStore.setRemoteURL(...)` and rewrites the user's local `origin` remote — with no prompt. [6](#0-5) 
4. The user's next `git push`/`fetch` silently targets the new, attacker-influenced remote.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
