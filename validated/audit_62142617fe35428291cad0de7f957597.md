Based on the investigation, there is a direct analog of the "empty committee accepted" bug class in Agave's precompile signature-verification programs.

### Title
Zero-signature secp256k1 / ed25519 precompile instructions are accepted as successfully verified - (File: `precompiles/src/secp256k1.rs`, `precompiles/src/ed25519.rs`)

### Summary
The `secp256k1::verify()` and `ed25519::verify()` precompile-verification functions accept an instruction that declares `num_signatures = 0` (an "empty committee" of signatures) as successfully verified, returning `Ok(())` without performing any cryptographic check. This mirrors the `setupCommittee()` bug class exactly: a required-signature count of zero combined with an empty signature set is treated as a valid, fully-verified state rather than being rejected.

### Finding Description
In `precompiles/src/secp256k1.rs::verify`, the guard against a zero signature count only triggers when there is *extra* trailing instruction data: [1](#0-0) 
If `count == 0` and `data.len() == 1` (i.e., only the count byte is present, no offsets/signature data), the check `count == 0 && data.len() > 1` is false, so execution falls through, the `for i in 0..count` loop body never runs, and the function returns `Ok(())`.

The same pattern exists in `precompiles/src/ed25519.rs::verify`: [2](#0-1) 
Here the guard is `num_signatures == 0 && data.len() > SIGNATURE_OFFSETS_START`; a minimal instruction with `data.len() == SIGNATURE_OFFSETS_START` and `num_signatures == 0` again falls through the empty loop and returns `Ok(())`.

Notably, the third precompile, `secp256r1`, was hardened against exactly this case and unconditionally rejects zero signatures regardless of trailing data: [3](#0-2) 
This inconsistency demonstrates the missing check is a genuine gap in `secp256k1`/`ed25519`, not an intentional universal design choice across all three precompiles.

These `verify()` functions are invoked from `verify_if_precompile`, which is the trust boundary any transaction-included precompile instruction must pass: [4](#0-3) 
A malicious, fully unprivileged user can submit a transaction containing a bare `secp256k1_program`/`ed25519_program` instruction whose data is just `[0]` (or `[0, 0]` up to `SIGNATURE_OFFSETS_START` bytes for ed25519). The instruction passes `verify_if_precompile` with no signature ever having been checked, exactly analogous to `CDKDataCommittee.verifySignatures()` succeeding on an empty `signaturesAndAddrs` when `requiredAmountOfSignatures = 0`.

### Impact Explanation
Any on-chain program that relies on the presence of a *successful* `secp256k1`/`ed25519` precompile instruction in the same transaction as an implicit proof that "some signature was cryptographically verified" (a common integration pattern for bridges, oracles, and off-chain-signed message schemes) can be fooled into treating a vacuous, unverified zero-signature instruction as valid attestation. This is a forged/vacuous-signature-acceptance class bug reachable by any unprivileged transaction sender, with the precompile's `Ok(())` return being indistinguishable from a genuine, fully-checked signature unless the downstream program also independently re-validates `num_signatures > 0`.

### Likelihood Explanation
Trivially reachable: any unprivileged user can craft and submit a transaction with a 1-byte (secp256k1) or minimal (ed25519) precompile instruction data payload with no signers, with no compute cost of note and no special permissions required.

### Recommendation
Add an explicit `num_signatures == 0` rejection at the top of `secp256k1::verify` and `ed25519::verify`, mirroring the already-correct check in `secp256r1::verify` at `precompiles/src/secp256r1.rs:27-29`, so a zero-signature instruction is always rejected as `PrecompileError::InvalidInstructionDataSize` regardless of trailing data length.

### Proof of Concept
1. Construct a transaction containing an instruction targeting `solana_sdk_ids::secp256k1_program::id()` with `data = vec![0u8]` (just the count byte, no offsets/signature data).
2. Submit the transaction; `verify_if_precompile` routes it to `secp256k1::verify`, where `count == 0` and `data.len() == 1`, so the `count == 0 && data.len() > 1` guard is false and the function returns `Ok(())` with zero signatures examined.
3. Equivalently, for `ed25519_program`, use `data = vec![0u8; SIGNATURE_OFFSETS_START]` to trigger the analogous fall-through in `ed25519::verify`.

/// Check that a program is precompiled and if so verify it
pub fn verify_if_precompile(
    program_id: &Pubkey,
    precompile_instruction: &CompiledInstruction,
    all_instructions: &[CompiledInstruction],
    feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    for precompile in PRECOMPILES.iter() {
        if precompile.check_id(program_id, |feature_id| feature_set.is_active(feature_id)) {
            let instruction_datas: Vec<_> = all_instructions
                .iter()
                .map(|instruction| instruction.data.as_ref())
                .collect();
            return precompile.verify(
                &precompile_instruction.data,
                &instruction_datas,
                feature_set,
            );
        }
    }
    Ok(())
}
