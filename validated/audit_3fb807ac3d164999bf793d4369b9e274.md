## Summary

The Solidity finding's broken invariant is: **a state-tracking map (`vaultOwners`) keyed by an identifier is trusted across operations without verifying it still corresponds to the *same* underlying event/instance that created it, and a time/scope boundary (auction length) is never re-checked before the map entry is used to authorize an action.**

GitHub Desktop has a structurally identical pattern in its conflict-resolution state machine: `updateConflictState` carries the `manualResolutions: Map<string, ManualConflictResolution>` forward from `prevConflictState` into a brand-new conflict state **before** checking whether the operation itself (target branch / rebase instance) actually changed, and even after detecting that change it still returns the stale map.

### Finding Description

`getConflictState` builds the new conflict state using the *previous* operation's `manualResolutions` map, keyed only by file path: [1](#0-0) [2](#0-1) 

`updateConflictState` only detects that the operation changed (`branchNameChanged`, meaning a different rebase/merge target than before — i.e., an aborted operation followed by a fresh one) *after* `newConflictState` was already computed with the inherited map, and it does not purge or rebuild the map when that happens — it just logs a stat and returns: [3](#0-2) [4](#0-3) 

That inherited map directly gates whether a conflicted file is treated as "resolved": `hasUnresolvedConflicts` returns `false` the moment a `manualResolution` entry exists for the path, with no validation that the entry was produced for *this* conflict/content: [5](#0-4) 

And when the rebase is continued, the stale resolution is applied blindly by path to whatever file currently sits at that path and is force-checked out (`ours`/`theirs`) and staged, with no re-comparison against the earlier decision's content: [6](#0-5) [7](#0-6) [8](#0-7) 

Same pattern exists for merges via `createMergeCommit` / `_finishConflictedMerge`, which also apply a caller-supplied `manualResolutions` map keyed only by path: [9](#0-8) [10](#0-9) 

### Impact Explanation

**Corrupted value**: the `manualResolutions` `Map<string,ManualConflictResolution>` — it persists across distinct rebase/merge instances keyed only by file path, with no binding to the commit SHAs, branch, or content that produced the original decision.

**Why existing guards don't stop it**: the only guard (`branchNameChanged` in `performEffectsForRebaseStateChange`/`performEffectsForMergeStateChange`) exists purely to increment a telemetry counter (`rebaseAbortedAfterConflictsCount` / `mergeAbortedAfterConflictsCount`); it never resets or discards `manualResolutions`, and it runs *after* `newConflictState` (containing the stale map) has already been constructed and is what gets returned and stored in application state.

**Path to silent corruption**: If a user starts a rebase/merge onto an attacker-influenced branch (e.g., a PR branch, a shared/collaborative fork, or a branch updated by a git proxy/MITM response), hits a conflict on file `X`, and manually resolves it (e.g., "theirs"), then that rebase is aborted (by user, crash, or Desktop restart) and a new rebase/merge against a *different* target is started that also produces a conflict at the same path `X` (trivial for an attacker who controls the remote content to arrange, since the path is attacker-influenced too), Desktop's UI will show file `X` as already "Resolved" (`hasUnresolvedConflicts` → `false`) without ever displaying the new conflicting content to the user. Continuing the operation runs `git checkout --theirs -- X` / stages it automatically using the leftover decision, so the attacker's new content is silently committed and can be pushed without the user ever reviewing it — corrupting exactly "what the user commits or pushes," the same class of blind-trust-in-stale-state that the original report flags for the vault-liquidation `settle` path.

### Likelihood Explanation

Requires a specific sequence (conflict → manual resolution → operation restart/abort → new conflict at same path) but nothing beyond normal Desktop usage on a repository whose remote content an attacker influences (fork/PR workflows are common). No local access, no elevated privileges, no pre-existing malware needed — the attacker only needs control over the branch/remote content being rebased/merged, matching the "attacker controls a fetched repository" threat model.

### Recommendation

Invalidate/clear `manualResolutions` whenever `updateConflictState` detects the underlying operation changed (branch name changed, target tip changed, or transition between merge/rebase/cherry-pick kinds), instead of only recording a telemetry stat. Consider binding each manual resolution to the specific conflict instance (e.g., include `originalBranchTip`/`baseBranchTip` or a content hash) rather than keying purely by file path, so a resolution from a prior aborted operation can never be silently reapplied to a new conflict.

### Proof of Concept

Not independently executable from the index alone (requires running Desktop against a live repo/remote), but the flow is fully traceable in-repo:
1. Start a rebase of `feature` onto `main`; conflict occurs on `config.json`; user selects "theirs" → `manualResolutions.set('config.json', theirs)` recorded in `RebaseConflictState`.
2. Abort/interrupt that rebase (network drop, app restart, or user cancel) without clearing the change store's `conflictState.manualResolutions`.
3. Start a new rebase of `feature` onto a different/attacker-controlled `malicious-base`; a new conflict occurs, again touching `config.json` with entirely different, attacker-crafted content.
4. `updateConflictState` (`app/src/lib/stores/updates/changes-state.ts:263-311`) builds `newConflictState` reusing the old `manualResolutions` map (line 270-275) before `performEffectsForRebaseStateChange` even runs; `branchNameChanged` is detected but only bumps a stat counter (lines 229-238) and the stale map is still returned.
5. UI (`hasUnresolvedConflicts`, `app/src/lib/status.ts:68-84`) shows `config.json` as resolved; continuing the rebase (`continueRebase`, `app/src/lib/git/rebase.ts:438-458`) runs `checkout --theirs -- config.json` and stages it automatically, committing the attacker's new content without user review.

function performEffectsForRebaseStateChange(
  prevConflictState: RebaseConflictState | null,
  newConflictState: RebaseConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
) {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.targetBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.targetBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the rebase must have been aborted
  if (branchNameChanged) {
    statsStore.increment('rebaseAbortedAfterConflictsCount')
    return
  }

  const { currentTip, currentBranch } = status

  // if the repository is no longer conflicted, what do we think happened?
  if (
    prevConflictState != null &&
    newConflictState == null &&
    currentTip != null &&
    currentBranch != null
  ) {
    const previousTip = prevConflictState.originalBranchTip

    const previousTipChanged =
      previousTip !== currentTip &&
      currentBranch === prevConflictState.targetBranch

    if (!previousTipChanged) {
      statsStore.increment('rebaseAbortedAfterConflictsCount')
    }
  }

  return
}

    prevConflictState !== null

export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}

export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

  switch (chosen) {
    case GitStatusEntry.Deleted:
      return removeConflictedFile(repository, file)
    case GitStatusEntry.Added:
    case GitStatusEntry.UpdatedButUnmerged:
      return addConflictedFile(repository, file)
    default:
      assertNever(chosen, 'unaccounted for git status entry possibility')
  }

  public async _finishConflictedMerge(
    repository: Repository,
    workingDirectory: WorkingDirectoryStatus,
    manualResolutions: Map<string, ManualConflictResolution>
  ): Promise<string | undefined> {
    /**
     *  The assumption made here is that all other files that were part of this merge
     *  have already been staged by git automatically (or manually by the user via CLI).
     *  When the user executes a merge and there are conflicts,
     *  git stages all files that are part of the merge that _don't_ have conflicts
     *  This means that we only need to stage the conflicted files
     *  (whether they are manual or markered) to get all changes related to
     *  this merge staged. This also means that any uncommitted changes in the index
     *  that were in place before the merge was started will _not_ be included, unless
     *  the user stages them manually via CLI.
     *
     *  Its also worth noting this method only used in the Merge Conflicts dialog flow, not committing a conflicted merge via the "Changes" pane.
     *
     *  *TLDR we only stage conflicts here because git will have already staged the rest of the changes related to this merge.*
     */
    const conflictedFiles = workingDirectory.files.filter(f => {
      return f.status.kind === AppFileStatusKind.Conflicted
    })
    const gitStore = this.gitStoreCache.get(repository)
    return await gitStore.performFailableOperation(() =>
      createMergeCommit(repository, conflictedFiles, manualResolutions)
    )
