Let me check the schnorr batch verifier and frost sign for attacker-controlled zero/identity handling.### Title
`SchnorrAggregate::verify` accepts an empty aggregate (`Rs = []`, `s = 0`) as valid, instead of rejecting zero-length aggregates - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
The analog of the OTLM "zero-amount transfer causes revert / should have been skipped" bug is a *zero-length aggregate propagated into verification*. `SchnorrAggregator::complete()` explicitly refuses to produce an empty aggregate (returns `None` when `self.sigs.is_empty()`), establishing the invariant that an aggregate must contain at least one signature. However, `SchnorrAggregate::read()` imposes no such constraint: it accepts a 4-byte length of `0` followed by a scalar `s`. When `verify()` is then called, the statement loop iterates zero times, the `pairs` vector reduces to the single term `(-s, C::generator())`, and for `s = 0` the multiexp is the identity — so `verify` returns `true` for a byte string that attests to nothing.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`:

- `SchnorrAggregate::read` deserializes `u32`-many `R` points and one scalar `s`, with no lower bound on the count (lines 77-88).
- `verify` checks only `self.Rs.len() != keys_and_challenges.len()` (line 128). With both empty, `pairs` contains only `(-self.s, C::generator())` (line 144), and `multiexp_vartime` of `0*G` is the identity, so it returns `true` (line 145).
- `SchnorrAggregator::complete` returns `None` for empty `sigs` (lines 175-178), showing the protocol intends empty aggregates to be invalid — but the same check is missing on the read/verify path.

This mirrors the report's class precisely: a degenerate (zero) quantity flows into a downstream operation that does not guard for it. Where the OTLM issue is a DoS from an unskipped zero-transfer, here the failure direction is worse: the zero case is *accepted* rather than skipped or rejected. An unprivileged party reaches this purely through untrusted bytes fed to `SchnorrAggregate::read`, which is one of the enumerated public-input surfaces.

### Impact Explanation
Any verifier that derives `keys_and_challenges` from the aggregate itself (e.g., building the challenge list by iterating `self.Rs`, or indexing a per-signer table keyed by position) can be handed `len=0, s=0` and will see `verify` return `true` while zero signatures were actually checked — a forged aggregate acceptance. Even where the caller supplies the challenge list, an attacker who can force the expected set to empty (e.g., all expected signers filtered out earlier) gets a passing verification of nothing. The asymmetry with `complete()`'s explicit `None`-on-empty demonstrates this acceptance is unintentional.

### Likelihood Explanation
Reachability requires an integrator to verify a deserialized `SchnorrAggregate` where the statement set can be empty or is attacker-influenced. It is not exploitable against a caller that always supplies a fixed non-empty `keys_and_challenges`, since the length check at line 128 fails. Severity is Medium: a concrete forged-acceptance primitive reachable from untrusted bytes, gated on integration shape.

### Recommendation
Reject empty aggregates at both trust boundaries:
- In `SchnorrAggregate::read`, error if the deserialized `Rs` length is `0`.
- In `SchnorrAggregate::verify`, return `false` if `self.Rs.is_empty()` (or if `keys_and_challenges.is_empty()`), matching the `complete()` invariant.

### Proof of Concept
```rust
use ciphersuite::Ciphersuite;
use schnorr::SchnorrAggregate;

// Any Ciphersuite C; serialize a zero-length aggregate:
//   u32 LE len = 0, then s = 0 scalar encoding
let mut bytes = 0u32.to_le_bytes().to_vec();
bytes.extend(C::F::ZERO.to_repr().as_ref()); // s = 0

let agg = SchnorrAggregate::<C>::read(&mut &bytes[..]).unwrap();
assert_eq!(agg.Rs().len(), 0);

// Verifies as "valid" despite attesting to zero signatures.
// Also passes for any caller that builds `keys_and_challenges` from agg.Rs().
assert!(agg.verify(b"some dst", &[]));

// Meanwhile, the honest aggregation path refuses to ever produce this object:
assert!(SchnorrAggregator::<C>::new(b"some dst").complete().is_none());
```
