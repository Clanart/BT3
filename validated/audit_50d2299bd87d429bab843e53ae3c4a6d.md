### Title
Unbounded-length numeric literal drives O(N²) `BigInteger` construction in `TextFormat.parseInteger()` — (File: `java/core/src/main/java/com/google/protobuf/TextFormat.java`)

### Summary
`TextFormat.parseInteger()` (lines 3021–3105) mirrors the exact bug class described in the pretext advisory: an attacker-controlled string of bounded but attacker-chosen length is fed into a known-quadratic operation with no length cap, while an analogous code path in the same codebase (`JsonFormat.parseBigDecimal()`) already has this exact guard. The invariant that failed in `pretext` — "verify/transform an accumulated attacker-controlled buffer using an algorithm whose cost grows non-linearly with buffer length, with no upper bound on that length" — transfers directly to `TextFormat`'s use of `java.math.BigInteger(String, int)` for tokens ≥16 characters.

### Finding Description
`TextFormat.parseInteger(String text, boolean isSigned, boolean isLong)` at [1](#0-0)  switches to `BigInteger` parsing whenever the numeric token is 16 characters or longer: [2](#0-1) 

`new BigInteger(numberText, radix)` has quadratic (or worse, depending on JDK/algorithm thresholds) time complexity in the number of digits for large inputs on JDKs prior to the Karatsuba/Toom-Cook optimizations landing for the plain string constructor path (the same class of algorithmic-complexity issue Java's own `JsonFormat.parseBigDecimal()` was hardened against, citing `BigDecimal(String)` having "O(N^2) time complexity for N-digit strings on JDK < 18").

Critically, this same file's sibling utility, `JsonFormat.java`, already contains the fix for this exact bug class: [3](#0-2) 

That guard caps the numeric string length to 1000 characters *before* constructing a `BigDecimal`, and there is a dedicated regression test (`testParserRejectOverlyLongNumericStrings`) proving the fix: [4](#0-3) 

`TextFormat.parseInteger()` has no equivalent length check before calling `new BigInteger(numberText, radix)`. The `numberText` value originates from a text-format integer literal tokenized by `TextFormat`'s tokenizer, whose digit-run length is not itself bounded by any TextFormat-level input-size limit distinct from the caller-supplied text size — i.e. any attacker who can get an arbitrarily long numeric literal (a string of many digits) into a message field parsed via `TextFormat.getParser().merge(...)` reaches the unguarded `BigInteger` construction, exactly as the pretext report's attacker reaches the unguarded `isRepeatedSingleCharRun` full rescan by supplying repeated punctuation.

### Impact Explanation
This is the direct, currently-un-mitigated analog of the reported bug class within this repository: same failed invariant (missing length cap before a known-quadratic string-to-number conversion), same attacker control (ordinary bounded text supplied to a public parsing API — `TextFormat.merge`/`TextFormat.Parser`), same class of impact (CPU-bound main-thread/worker-thread blocking proportional to the square of a moderate-size attacker-chosen digit run, without any memory-growth or crash). Because `TextFormat` parsing is a supported public API that applications may expose to external input (e.g., debug endpoints, config ingestion, RPC payloads formatted as text proto), a single large-int/uint/int64/uint64 literal (tens of thousands of digits, well within ordinary text-size limits) can consume disproportionate CPU relative to its size, causing per-request latency amplification. This does not corrupt memory or crash the process; the impact is CPU-time amplification (algorithmic complexity), matching the reported CWE-407 class exactly.

### Likelihood Explanation
High confidence that the code path exists and is unguarded (grep of `TextFormat.java` for a numeric-string length check comparable to `MAX_NUMERIC_STRING_LENGTH` in `JsonFormat.java` returned nothing). Moderate-to-high confidence in reachability from an ordinary bounded text-format payload: the digit run's length is controlled purely by how many digit characters the attacker places in the literal, and nothing in `parseInteger` itself bounds it before the `BigInteger` construction. I was not able to fully trace, within the available iterations, whether `TextFormat`'s tokenizer enforces any independent maximum token/identifier length elsewhere in the file that would cap `numberText.length()`; that check should be explicitly ruled out (or confirmed absent) before filing, since if such a tokenizer-level cap already exists at a small bound, the practical exploitability would be reduced. This uncertainty is called out explicitly since I could not read the tokenizer's number-literal consumption logic in the remaining iterations.

### Recommendation
Apply the same mitigation already used in `JsonFormat.parseBigDecimal()` to `TextFormat.parseInteger()`: reject (`throw NumberFormatException`) numeric literals whose digit-string length exceeds a small, generous bound (e.g., a few hundred characters — legitimate 64-bit integers never exceed ~20 digits, even with radix 8/16 representations) before calling `new BigInteger(numberText, radix)`. This closes the same class of algorithmic-complexity DoS the JSON path was hardened against, applied consistently across all of Protobuf's text-based parsing entry points (TextFormat, JSON).

      }
      ++pos;
      negative = true;

    if (text.startsWith("0x", pos)) {
      pos += 2;
      radix = 16;
    } else if (text.startsWith("0", pos)) {
      radix = 8;
    }

    final String numberText = text.substring(pos);

    long result = 0;
    if (numberText.length() < 16) {
      // Can safely assume no overflow.
      result = Long.parseLong(numberText, radix);

        result = -result;

    // BigDecimal(String) has O(N^2) time complexity for N-digit strings on JDK < 18,
    // allowing a DoS with a single long numeric JSON value. Valid protobuf numeric
    // values never exceed ~350 characters, so 1000 is a generous upper bound.
    private static final int MAX_NUMERIC_STRING_LENGTH = 1000;

    private static BigDecimal parseBigDecimal(String value) throws InvalidProtocolBufferException {
      if (value.length() > MAX_NUMERIC_STRING_LENGTH) {
        throw new InvalidProtocolBufferException(
            "Numeric value is too long: " + value.length() + " characters");
      }
      return new BigDecimal(value);
    }
