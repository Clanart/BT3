### Title
Copilot merge-conflict resolution can silently delete a conflict block instead of resolving it, due to two independently-implemented conflict-marker parsers that can disagree on hunk count - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The reported oracle bug is a classic "two parallel data structures that must stay in lockstep but can drift, and the consumer has no safe fallback when they do" issue. GitHub Desktop's AI conflict-resolution feature has the same shape of bug: the number of conflict "hunks" a file is believed to contain is computed once by `extractConflictHunks()` and used to validate the model's response, but the code that actually **splices the resolved content back into the file that gets written to disk and `git add`-ed** re-parses the same raw file content with a second, independently written marker scanner in `reassembleResolvedFile()`. These two parsers are not the same code and are not guaranteed to agree on how many conflict blocks exist. When they disagree, `reassembleResolvedFile()` has no error path - it silently drops the un-matched conflict block entirely.

### Finding Description
Two data structures are meant to stay "the same length":

1. `extractConflictHunks()` [1](#0-0)  walks the on-disk file once and returns an array of `IConflictHunk`. Its length becomes `IFileConflictContext.hunks.length`, which is captured once during context gathering [2](#0-1) .
2. `validateResolutionPaths()` enforces that the model's response contains exactly that many hunks per file [3](#0-2) .
3. The actual write-to-disk path, `reassembleResolvedFile()`, does **not** reuse `extractConflictHunks()` or its result. It re-scans the same `rawContent` string with its own, separately implemented and separately defined marker regexes (`reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker`, distinct constants from `oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker` in the other file) [4](#0-3) .

The splicing loop matches each conflict block it *finds* against `hunkResolutions` **by array index, not by identity**:

```
if (hunkIndex < hunkResolutions.length) {
  const resolved = hunkResolutions[hunkIndex].resolvedContent
  ...
}
hunkIndex++
``` [5](#0-4) 

If the reassembly parser's independent walk finds a conflict block for which `hunkIndex >= hunkResolutions.length`, the block's marker lines and both its `ours`/`theirs` content are still consumed and removed from the output (`i = closingIndex + 1`, line 582), but **no replacement text is inserted** - the entire section is silently deleted from the final file content with no error, no log visible to the user, and no validation catching it, because `validateResolutionPaths()` only checked the count against the *other* parser's (`extractConflictHunks`) result, not against what `reassembleResolvedFile()` will actually find.

This is structurally identical to the reported bug: `asset_list` vs `expiration` in the oracle contract are two parallel structures assumed to be the same length; here, "hunk count per `extractConflictHunks`" vs "conflict blocks per `reassembleResolvedFile`'s independent scan" are two parallel structures assumed to be the same length. In the oracle case the mismatch causes a panic; here, because the consumer has no bounds error at all, the mismatch instead causes **silent data loss** in the exact content that is about to be `git add`-ed and committed [6](#0-5) .

### Impact Explanation
The resolved file is written straight to disk and staged without further diffing against the user's expectations:
```
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
...
await git(['add', '--', ...pathsToStage], ...)
``` [7](#0-6) 

If the two parsers disagree on hunk boundaries/count for a file whose conflicting content (attacker-controlled "theirs" branch from a malicious fork/PR being merged, or content that merely contains marker-like text such as a Markdown heading underline `=======`, or documentation about git conflict syntax) causes `reassembleResolvedFile` to detect a different number of well-formed blocks than `extractConflictHunks` did, an entire hunk - both sides of the conflict - can vanish from the committed file with zero warning. This is exactly the class of impact called out as valid: "silent corruption of what the user commits or pushes," triggered purely by content in a fetched/merged branch under an attacker's control, with no local access, admin rights, or social engineering required beyond the user resolving conflicts via the built-in Copilot conflict-resolution feature.

### Likelihood Explanation
This requires: (a) the user to be merging/rebasing against a branch/fork whose content the attacker controls, and (b) that content to contain conflict-marker-like text or a genuinely malformed/edge-case conflict layout that makes `extractConflictHunks`'s strict, stateful, per-marker-type walk disagree with `reassembleResolvedFile`'s looser "find a `=======` then a `>>>>>>>` anywhere further down" lookahead (which, unlike the extractor, never validates the diff3 base marker and never restarts scanning on an unexpected marker type). Because the two parsers are maintained as separate, un-shared implementations with separately duplicated regex constants, any future edit to one without the other silently reintroduces or widens this drift. I was not able to construct a single minimal input that I could fully hand-verify triggers divergent counts against both parsers' full state machines in the time available, so this should be validated with fuzzing/property-testing both parsers against the same corpus of conflict files (particularly diff3 three-way conflicts and files containing marker-look-alike text) before treating exploitability as proven end-to-end.

### Recommendation
- Make `reassembleResolvedFile()` consume the *same* `IConflictHunk[]` array produced by `extractConflictHunks()` (e.g., by storing hunk start/end line offsets in `IConflictHunk` at extraction time) instead of independently re-scanning `rawContent` with a second regex-based state machine.
- If the two counts can ever legitimately diverge, fail loudly (throw `CopilotValidationError`) rather than silently dropping content when `hunkIndex >= hunkResolutions.length`.
- Add a post-condition assertion in `reassembleResolvedFile()`: if it finds more or fewer well-formed conflict blocks than `hunkResolutions.length`, abort the reassembly and surface an error to the user instead of writing a partially-deleted file to disk.

### Proof of Concept
Not fully constructed/verified end-to-end within this investigation. The structural flaw is directly demonstrable from the code: `extractConflictHunks()` [8](#0-7)  and `reassembleResolvedFile()`'s inline lookahead [9](#0-8)  are two separate, non-shared marker parsers, and the splice loop's `if (hunkIndex < hunkResolutions.length)` guard has no error path for the "too many blocks found" case - it silently deletes content instead. A concrete triggering input (e.g., a conflicted file containing diff3 `|||||||` markers, or content lines that coincidentally match `/^={7}$/`/`/^>{7}(?:\s|$)/`) would need to be constructed and run against both parsers to confirm a specific divergent-count scenario; this should be treated as the next verification step rather than a confirmed exploit.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }
