Good — `BandwidthManager.purchase()` on the EVM side does check `months == 0` (`InvalidPurchase`). But the pallet-side `on_accept` handler in `pallet-bandwidth` performs no equivalent validation of its own on the decoded `PurchaseMessage`, and it trusts only that `request.from` matches the registered manager — it never re-derives or bounds `msg.months`, `msg.app`, or `msg.chain`. This is the same class of bug as `preallocate`: a privileged-looking, single-purpose entrypoint with no defensive sanity checks of its own, relying entirely on an external actor (there, the crowdsale owner; here, the EVM-side `purchase()` guard) to enforce invariants that the receiving function should enforce itself.

### Title
Unbounded push_subscription on repeated zero/duplicate purchases lets a spammer evict paid bandwidth for other apps at negligible cost - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth`'s `on_accept` (analogous to `preallocate`: an unchecked internal state-mutation function reached without its own sanity gates) computes `bytes`/`duration` from an ISMP message and unconditionally calls `push_subscription`, which evicts the oldest live subscription once a `(chain, app)` bucket reaches the 1024-entry cap [1](#0-0) . Unlike `BandwidthManager.purchase()` on the EVM side, which checks `months == 0` before charging [2](#0-1) , the pallet's `on_accept` performs no independent validation of the decoded `PurchaseMessage` fields (`months`, `app`, `chain`) and no cap/rate check before calling `push_subscription`, which silently evicts the FIFO head with `list.remove(0)` [3](#0-2) .

### Finding Description
`on_accept` only checks that the sender is the registered `BandwidthManager` for the source chain; it never checks `msg.months != 0`, minimum purchase size, or throttles push frequency [4](#0-3) . Because `is_purchase_message`/`on_accept` key the credited bucket by `(msg.chain, msg.app)` taken from the message body — independent of `request.source` — a single manager on one cheap chain can dispatch purchase messages crediting *any* `(chain, app)` pair repeatedly [5](#0-4) . Each accepted purchase, however tiny (`months = 1`, cheapest tier), unconditionally calls `push_subscription`, which evicts index 0 of the FIFO list once the bucket is at the 1024 cap [6](#0-5) . The existing guard (`months == 0` check) lives only in the EVM `BandwidthManager.purchase()` entrypoint and protects nothing on the pallet side — the pallet trusts whatever `request.body` a *registered* manager contract sends, but the manager itself is fully permissionless to call from any account, so any attacker with minimal fee-token balance can drive an unbounded number of cheap purchases against a victim's `(chain, app)` bucket, each evicting one already-paid-for subscription belonging to a legitimate buyer.

### Impact Explanation
This is a logic attack causing loss of a paid-for asset: legitimate buyers' bandwidth (`remaining_bytes`) is evicted (`SubscriptionEvicted`) and permanently lost before it is consumed, even though they already paid the fee token for it. An attacker who buys the cheapest tier 1024+ times against a victim's `(chain, app)` bucket can evict the victim's entire prepaid bandwidth allotment, effectively locking the victim's paid app out of the bridge (since bandwidth gates every non-purchase POST request) — matching the bounty's "loss of funds" / "logic attack" categories. The relative cost asymmetry (attacker pays the cheapest tier price per push vs. victim losing possibly-large prepaid subscriptions) makes this economically viable.

### Likelihood Explanation
Likelihood is moderate: it requires no privileged role, prover, relayer, or admin — any account holding the fee token can call `BandwidthManager.purchase()` with `months=1` against the cheapest configured tier and repeat it 1024+ times to fill and then evict a targeted `(chain, app)` bucket. This is entirely achievable via the standard, unprivileged purchase flow described in the docs [7](#0-6) , and the pallet's `on_accept` never rate-limits, deduplicates, or bounds purchase frequency per app.

### Recommendation
Add pallet-side sanity checks in `on_accept` before calling `push_subscription`: reject `msg.months == 0` server-side rather than relying solely on the EVM caller; consider a minimum bytes/duration threshold per push, a per-source rate limit, or requiring that eviction only be allowed by the same payer/manager pair that owns the oldest entry, and emit a hard failure (or require governance re-authorization) rather than silent eviction when a bucket is under active attack from an unrelated payer.

### Proof of Concept
1. Governance registers `BandwidthManager` for `SourceChain` and configures the cheapest tier (`TierOne`) with minimal `bytes`/`duration_secs` and minimal price.
2. Attacker repeatedly calls `BandwidthManager.purchase(app = victim_app, tier = TierOne, months = 1, chain = victim_chain)` — each call passes the `months == 0` check trivially since `months = 1`, and dispatches a `BandwidthPurchaseMsg` [8](#0-7) .
3. Once delivered, `pallet-bandwidth::on_accept` credits the `(victim_chain, victim_app)` bucket with a small subscription each time, with no check on how many buckets/pushes the same manager has already made [9](#0-8) .
4. After 1024 such purchases the bucket is full; the 1025th purchase evicts index 0 — the victim's legitimately paid, larger subscription — via `list.remove(0)` in `push_subscription` [6](#0-5) , confirmed by the existing test `subscription_cap_evicts_oldest` demonstrating the eviction mechanics [10](#0-9) .
5. Repeating this against the victim's bucket drains all of the victim's prepaid bandwidth, at a fee-token cost to the attacker of 1024× the cheapest tier price, versus the loss of the victim's full paid subscription value.

Note: I was not able to fully verify whether governance-configured tier prices in production deployments make this economically infeasible (i.e., whether the cheapest tier price is set high enough to deter this) — that is a deployment/governance parameter outside the indexed code, so the actual cost-asymmetry depends on live `set_tier` configuration not visible in this repository snapshot.

```rust
			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
```

```text
    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

        commitment = IDispatcher(_host).dispatch(
            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );
```

```text
## Subscription Lifecycle

Each `(chain, app)` row holds a FIFO list of subscriptions, capped at **1024** entries. Every purchase appends a new subscription — same-tier repurchases don't stack, they queue.

A subscription is immutable across its lifetime:

| Field             | Behavior                                                                       |
| ----------------- | ------------------------------------------------------------------------------ |
| `tier`            | Recorded at purchase time. Used for events and analytics, not for gating.      |
| `remaining_bytes` | Drains as the gate consumes messages. Pops once it hits zero.                  |
| `expires_at`      | Fixed at purchase. Never extends — a repurchase is a _new_ row, not a renewal. |
| `purchased_at`    | Insertion timestamp. Fixes FIFO order under same-block buys.                   |

### Drain order

The gate drains from the **head** of the list. Once the head is fully consumed it pops and continues into the next. If the next entry is expired it's swept silently — what you paid for is yours only until it expires.

This matters when you queue multiple tiers: the cheapest/oldest entry is consumed first regardless of which tier it came from. Plan top-ups so a higher tier doesn't sit behind a soon-to-expire lower tier you'd rather burn last.

### Eviction

Pushing onto a full list (1024 entries) evicts the **oldest** entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain. In practice this only happens under pathological repeat-buy behavior — at the default of one purchase per cycle, 1024 buys is years of headroom.
```

```rust
/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");

		// One more push: evicts the oldest, appends the new one.
		Bandwidth::force_credit(
			RuntimeOrigin::root(),
			ForceCreditParams {
				app_chain: APP_CHAIN,
				app: app_key(),
				tier: TIER1,
				bytes: cap + 1,
				duration_secs: MONTH_SECS,
			},
		)
		.unwrap();

		assert_eq!(sub_count(APP_CHAIN), cap as usize, "still capped");
		assert_eq!(
			sub_at(APP_CHAIN, 0).unwrap().remaining_bytes,
			2,
			"former second-oldest is now front",
		);
		assert_eq!(
			sub_at(APP_CHAIN, (cap - 1) as usize).unwrap().remaining_bytes,
			cap + 1,
			"new sub is at the back",
		);
	});
}
```
