## Title
Delimiter-based `FileChange.id` construction allows attacker-controlled filenames to collide, corrupting the working-directory file index/lookup map - (File: `app/src/models/status.ts`)

### Summary
`FileChange.id` (used as the key for `WorkingDirectoryStatus`'s internal `fileIxById` index map) is built by naively concatenating status kind, path, and old-path with a bare `+` delimiter, with no escaping: [1](#0-0) 

Because file paths originate from `git status --porcelain=2` output for a cloned/fetched repository, an attacker who controls repository content controls the `path`/`oldPath` values fed into this concatenation. Two distinct files can be crafted so that their `${kind}+${path}+${oldPath}` strings are identical even though `(path, oldPath)` differ, e.g. `path="x", oldPath="y+z"` vs `path="x+y", oldPath="z"`. This is the same class of bug as the NFTFloorOracle report: an ever-growing/attacker-influenced input (file paths in a repo) is folded into a bookkeeping key without sufficient collision-resistance, silently corrupting the index structure that tracks which array slot belongs to which logical entity.

### Finding Description
`WorkingDirectoryStatus` builds a `Map<string, number>` (`fileIxById`) mapping each file's `id` to its position in the `files` array: [2](#0-1) 

`files.forEach((f, ix) => this.fileIxById.set(f.id, ix))` overwrites any prior entry that has the same `id`. If two `WorkingDirectoryFileChange` objects produce the same `id` string (via the delimiter-collision shown above), the map will only retain the index of the *last* file processed for that id — exactly analogous to the Solidity report's truncated `index` field silently pointing `_removeAsset`/`_removeFeeder` at the wrong array slot. `findFileWithID()` and `findFileIndexByID()` then return the wrong file object / wrong row index for one of the two colliding entries: [3](#0-2) 

This corrupted mapping is not a purely cosmetic bug — it feeds directly into commit/stage/discard flows that trust `id`-based lookups instead of the array itself:
- Selection & checkbox state changes use ids and a `Set` built from selected files' ids, so if the id is shared, toggling inclusion for one file silently also toggles the other: [4](#0-3) 
- Diff loading, context menus ("open in external editor", "discard changes") and row-click handling all resolve the target file via `findFileWithID`/`findFileIndexByID`: [5](#0-4) [6](#0-5) 
- The diff-refresh path in `updateChangesWorkingDirectoryDiff` re-resolves the "currently selected" file purely by id after an async gap, trusting the id to be unique: [7](#0-6) 

None of these call sites validate uniqueness of `id`; they all assume `id` is a faithful, collision-free identifier for `(kind, path, oldPath)`.

The colliding entries are attacker-reachable because `git status --porcelain=2` performs rename/copy detection automatically (no explicit opt-in needed beyond default git config), and the command Desktop issues is a plain `status --porcelain=2 -z`: [8](#0-7) [9](#0-8) 

A malicious repository can be constructed with commits/content such that after a normal user action (clone + checkout of a branch, applying a stash, or merge) the working directory ends up with two rename/copy entries whose crafted paths collide under the `id` scheme, entirely through git's own automatic rename-similarity detection — no unnatural steps required of the victim beyond routine repository operations.

### Impact Explanation
When two files' computed `id`s collide, Desktop's file-level operations (stage/unstage a file for commit, discard changes, open a specific file, select a file to preview its diff) can silently act on the wrong file. Most importantly, the "include in commit" checkbox state is applied via an id-keyed `Set`, so checking/unchecking one file can unintentionally also flip the staged state of the colliding file — meaning the user may commit or discard content they never intended to touch. This matches the report's core impact category: silent corruption of what the user commits, driven purely by content of a repository the attacker controls, without any need for local/physical access.

### Likelihood Explanation
Exploitability requires the attacker to author repository content that (a) produces two working-directory entries of matching `kind` whose `path`/`oldPath` concatenate to equal strings under the bare `+` delimiter, and (b) triggers git's automatic rename/copy detection during a normal operation (checkout, merge, stash pop) so that Desktop's `git status --porcelain=2` reports both entries simultaneously. This is a crafting exercise for the attacker (choosing filenames with literal `+` characters and controlling content similarity so rename detection fires) but requires no exploit primitives beyond normal git usage, and no local/admin access from the victim beyond cloning and interacting with the repo as usual. Because it depends on precise filename crafting and git's rename-similarity heuristics, likelihood is moderate rather than trivial, but the underlying design flaw (unescaped delimiter-based id construction) is a real, exploitable bug once these conditions are met.

### Recommendation
Do not build `FileChange.id` by naive string concatenation of untrusted path components with a bare delimiter. Use a structure that can't collide across different inputs, e.g.:
- Encode field lengths or escape the delimiter (`+`) within `path`/`oldPath` before concatenation, or
- Use an array/tuple-based composite key (or a JSON-stable-stringify of `{kind, path, oldPath}`) instead of manual `+`-joined strings, or
- Track file identity structurally (index-stable object identity) rather than via a derived string id, especially in `WorkingDirectoryStatus.fileIxById` and every `findFileWithID`/`findFileIndexByID` consumer.

### Proof of Concept
1. Craft a git repository, `Repo`, containing (in some prior commit) two files `A` and `B` with content chosen so that after a subsequent commit, git's default rename-similarity detection (invoked implicitly by `git status --porcelain=2`) reports two `renamed` entries in the working tree such that:
   - Entry 1: `path = "x"`, `oldPath = "y+z"`
   - Entry 2: `path = "x+y"`, `oldPath = "z"`
2. Victim clones/fetches `Repo` and performs the ordinary action that produces this working-directory state (e.g. checking out the branch, or applying a stash) so Desktop calls `getStatus()`: [10](#0-9) 
3. Both entries are converted via `convertToAppStatus` into `AppFileStatusKind.Renamed` with the given `path`/`oldPath`: [11](#0-10) 
4. `FileChange.id` for entry 1 is `"Renamed+x+y+z"`; for entry 2 it is `"Renamed+x+y+z"` — identical strings despite different `(path, oldPath)` pairs: [12](#0-11) 
5. `WorkingDirectoryStatus`'s constructor overwrites `fileIxById.get("Renamed+x+y+z")` with the array index of whichever entry is processed last, so `findFileWithID`/`findFileIndexByID` for that id now resolve to only one of the two files: [13](#0-12) 
6. If the victim selects/stages entry 1 via the Changes list checkbox, `_changeFileIncluded`'s `modifiedIds.has(f.id)` matches both files sharing the colliding id, silently including entry 2 in the commit as well: [14](#0-13)

export class WorkingDirectoryStatus {
  /** Create a new status with the given files. */
  public static fromFiles(
    files: ReadonlyArray<WorkingDirectoryFileChange>
  ): WorkingDirectoryStatus {
    return new WorkingDirectoryStatus(files, getIncludeAllState(files))
  }

  private readonly fileIxById = new Map<string, number>()
  /**
   * @param files The list of changes in the repository's working directory.
   * @param includeAll Update the include checkbox state of the form.
   *                   NOTE: we need to track this separately to the file list selection
   *                         and perform two-way binding manually when this changes.
   */
  private constructor(
    public readonly files: ReadonlyArray<WorkingDirectoryFileChange>,
    public readonly includeAll: boolean | null = true
  ) {
    files.forEach((f, ix) => this.fileIxById.set(f.id, ix))
  }

  /**
   * Update the include state of all files in the working directory
   */
  public withIncludeAllFiles(includeAll: boolean): WorkingDirectoryStatus {
    const newFiles = this.files.map(f => f.withIncludeAll(includeAll))
    return new WorkingDirectoryStatus(newFiles, includeAll)
  }

  /** Find the file with the given ID. */
  public findFileWithID(id: string): WorkingDirectoryFileChange | null {
    const ix = this.fileIxById.get(id)
    return ix !== undefined ? this.files[ix] || null : null
  }

  /** Find the index of the file with the given ID. Returns -1 if not found */
  public findFileIndexByID(id: string): number {
    const ix = this.fileIxById.get(id)
    return ix !== undefined ? ix : -1
  }
}
