### Title
SSRF: DataLayer mirror-URL sync makes unauthenticated outbound HTTP requests to attacker-supplied hosts without any private/loopback/link-local address filtering - (File: chia/data_layer/data_layer.py)

### Summary
Chia's DataLayer service resolves mirror URLs published on-chain by any wallet (via `dl_new_mirror`/`create_new_mirror`) and, once a node is subscribed to a store, automatically pulls those URLs into its local subscription table and issues outbound HTTP requests to them during periodic sync. Unlike Typebot's `validateHttpReqUrl`, chia's URL-fetch path (`download_file`/`http_download`) performs **no address validation at all** — there is no check against loopback, link-local, unique-local, unspecified (`::`), or metadata-service ranges before the request is made. This is the same bug class as CVE-2026-49213 (server making outbound requests to attacker-influenced URLs without blocking internal address space), except in chia's case the gap is a complete absence of validation rather than an incomplete one.

### Finding Description
`DataLayer.update_subscriptions_from_wallet()` reads mirror URLs for a subscribed store id directly from chain state via `wallet_rpc.dl_get_mirrors()` and writes them into the local subscription table with no filtering: [1](#0-0) 

Any wallet user can create a mirror coin advertising an arbitrary URL for **any** existing store id, since mirror coins are their own on-chain objects funded by whoever spends to create them (`dl_new_mirror` / `create_new_mirror` in `chia/data_layer/data_layer_wallet.py`); mirror ownership of a store is not required to publish a mirror URL for that store's launcher id.

Once a victim's DataLayer service is subscribed to that store, `periodically_manage_data()` → `update_subscription()` syncs mirror URLs from the wallet and calls `fetch_and_validate()`, which randomly selects one of the available server URLs and downloads a delta file from it: [2](#0-1) [3](#0-2) 

The actual network call goes through `download_file()` → `http_download()` in `chia/data_layer/download_data.py`, which builds an `aiohttp` request against the raw, attacker-supplied URL string with no host/IP validation step anywhere in the call chain: [4](#0-3) 

`DataLayer.get_downloader()` similarly POSTs a `request_json` containing the attacker-controlled `url` to any configured downloader plugin without inspecting or restricting that URL's target: [5](#0-4) 

The codebase does contain IP-address utilities (`chia/util/ip_address.py`, `chia/util/network.py`) that could gate such requests (`IPAddress.is_private`, `is_localhost`), but these are only used for peer/RPC trust decisions in `chia/server/` — none of them are invoked anywhere in the DataLayer mirror-fetch path. The project's own internal documentation acknowledges mirror/plugin URLs are untrusted for **data integrity** purposes but does not treat them as an SSRF vector requiring network-destination validation: [6](#0-5) [7](#0-6) 

### Impact Explanation
A Data Layer client node that subscribes to any store can be coerced into making outbound HTTP requests to attacker-chosen internal targets (e.g., cloud metadata endpoints, internal admin services, `localhost` RPC ports) merely by another user publishing a mirror coin with a malicious URL against the same store id — no compromise of the victim's wallet or store ownership is required. This can be used to probe/attack internal network services reachable from the DataLayer host, or to exfiltrate internal service responses indirectly (e.g., through error/log side channels), and matches the "S3/plugin support is an extension boundary" trust gap already flagged internally. It is High severity because it is remotely triggerable by an unprivileged chain participant against any node that subscribes to the targeted store, with no authentication or special privilege required from the attacker.

### Likelihood Explanation
Likelihood is high: creating a mirror coin is a normal, permissionless DataLayer wallet operation available to any user with a small amount of XCH; subscribing to public stores is a normal, encouraged DataLayer usage pattern; and mirror-URL sync/fetch runs automatically and periodically (`periodically_manage_data()`) without any manual review of the URL by the operator.

### Recommendation
Add an SSRF-style URL validator to the DataLayer HTTP fetch paths (`http_download` in `chia/data_layer/download_data.py`, and the downloader-plugin POST in `DataLayer.get_downloader()`), resolving the hostname and rejecting loopback, link-local, unique-local/private, unspecified (`0.0.0.0`/`::`), and cloud-metadata addresses (`169.254.169.254`, `fd00:ec2::254`, etc.) before issuing any request — reusing/extending `chia/util/ip_address.py`'s `IPAddress` and `is_private`/`is_localhost` helpers from `chia/util/network.py`. Apply the same validation when mirror URLs are ingested in `update_subscriptions_from_wallet()` so malicious mirror entries are rejected before being stored, not just at request time, and re-validate on every redirect hop if `aiohttp` redirects are followed.

### Proof of Concept
1. Attacker identifies a DataLayer `store_id` (launcher id) that a target operator is known/likely to subscribe to (public stores are advertised).
2. Attacker runs `dl_new_mirror`/`create_new_mirror` for that `store_id`, publishing a mirror URL such as `http://169.254.169.254/latest/meta-data/` or `http://127.0.0.1:8555/` with minimal on-chain amount, per `chia/data_layer/data_layer_wallet.py`.
3. Victim node has (or later obtains) a subscription to that `store_id` via `DataLayer.subscribe()`.
4. On the next `periodically_manage_data()` cycle, `update_subscriptions_from_wallet()` pulls the malicious URL into the victim's subscription table (`chia/data_layer/data_layer.py:979-985`), and `fetch_and_validate()` selects it as a server and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, causing the victim node to issue an outbound HTTP request to the attacker-chosen internal/loopback/metadata address (`chia/data_layer/download_data.py:110-145`).
5. Response handling/backoff behavior (`server_misses_file`/`received_correct_file`) can be used by the attacker as an oracle for reachability/response characteristics of the internal target.

    async def get_downloader(self, store_id: bytes32, url: str) -> PluginRemote | None:
        request_json = {"store_id": store_id.hex(), "url": url}
        for d in self.downloaders:
            async with aiohttp.ClientSession() as session:
                try:
                    async with session.post(
                        d.url + "/handle_download",
                        json=request_json,
                        headers=d.headers,
                        timeout=self.client_timeout,
                    ) as response:
                        res_json = await response.json()
                        if res_json["handle_download"]:
                            return d
                except Exception as e:
                    self.log.error(f"get_downloader could not get response: {type(e).__name__}: {e}")
        return None
```

async def download_file(
    data_store: DataStore,
    target_filename_path: Path,
    store_id: bytes32,
    root_hash: bytes32,
    generation: int,
    server_info: ServerInfo,
    proxy_url: str | None,
    downloader: PluginRemote | None,
    timeout: aiohttp.ClientTimeout,
    client_foldername: Path,
    timestamp: int,
    log: logging.Logger,
    grouped_by_store: bool,
    group_downloaded_files_by_store: bool,
    max_delta_file_size: int,
) -> bool:
    if target_filename_path.exists():
        return True
    filename = get_delta_filename(store_id, root_hash, generation, grouped_by_store)

    if downloader is None:
        # use http downloader - this raises on any error
        try:
            await http_download(
                target_filename_path, filename, proxy_url, server_info, timeout, log, max_delta_file_size
            )
        except (asyncio.TimeoutError, aiohttp.ClientError, MaxDeltaFileSizeExceededError):
            new_server_info = await data_store.server_misses_file(store_id, server_info, timestamp)
            log.info(
                f"Failed to download {filename} from {new_server_info.url}."
                f"Miss {new_server_info.num_consecutive_failures}."
            )
            log.info(f"Next attempt from {new_server_info.url} in {new_server_info.ignore_till - timestamp}s.")
            return False
        return True
```
