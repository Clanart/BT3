### Title
Unchecked payment-sum overflow signs transactions exceeding available inputs - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` sums attacker-supplied payment amounts and compares that sum against the collected input value using unchecked `u64` arithmetic. In a release build, the payment total can wrap modulo `2^64`, causing the insufficient-funds check and later change calculation to evaluate a tiny wrapped total while the transaction actually contains outputs worth far more than the inputs. An unprivileged party able to submit payment data can therefore cause the threshold wallet to produce signatures for an unintended transaction. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Each payment is only checked against the dust threshold; there is no `MAX_MONEY` bound and no checked accumulation of `payment_sat`. [4](#0-3)  The funding check uses `input_sat < payment_sat + needed_fee`, where both the earlier summation and this addition can overflow. [2](#0-1)  If change is present, `input_sat.checked_sub(payment_sat + fee_with_change)` repeats the unchecked wrapped sum before subtraction. [3](#0-2)  The resulting `SignableTransaction` is passed to Taproot signing machines, which sign every input sighash without rechecking total output value. [5](#0-4) 

### Impact Explanation
An attacker can make an honest signing set produce threshold signatures over a transaction whose declared outputs exceed the actual inputs or even Bitcoin’s valid money range. This is a direct signature on unintended transaction data; depending on integration behavior, it can also corrupt accounting by representing an impossible spend as funded. If overflow checks are enabled, the same paths become a denial-of-service panic instead.

### Likelihood Explanation
The trigger only requires control of requested payment amounts. No validator compromise, private-key access, malformed curve encoding, or network-level privilege is needed. It depends on release arithmetic wrapping rather than trapping, which is the normal Rust release configuration.

### Recommendation
Reject each payment outside Bitcoin’s valid amount range and compute all input, payment, output, fee, and change totals with `checked_add`/`checked_sub`. Treat overflow as `NotEnoughFunds` or a dedicated amount-validation error. Additionally assert `payment_sat <= input_sat` before fee handling and have `fee()` use checked subtraction.

### Proof of Concept
Conceptually, with one funded input of `1000` sats and two requested payments:

```rust
let payments = vec![
  (attacker_script.clone(), u64::MAX),
  (attacker_script, 2),
];

// u64::MAX + 2 wraps to 1 on a normal release build.
let tx = SignableTransaction::new(
  vec![funded_output],          // 1000 sats
  &payments,
  None,
  None,
  min_relay_fee_per_vbyte,
).unwrap();
```

`payment_sat` wraps to `1`, so `input_sat < payment_sat + needed_fee` is false for an ordinary fee, despite the transaction containing an output for `u64::MAX` sats. Calling `tx.multisig(keys)` and completing the FROST protocol then produces Taproot signatures for that transaction.
