### Title
Attacker-controlled serialized verification shares rebind a Bitcoin multisig’s deposit address - (File: `crypto/dkg/src/lib.rs`)

### Summary
`ThresholdKeys::read` accepts attacker-controlled threshold parameters, a secret share, and verification shares, then derives the group key solely from the first `t` verification shares. It never verifies that the supplied secret share corresponds to this participant’s supplied verification share. An attacker who can submit the untrusted bytes consumed by `ThresholdKeys::read` can therefore register a group key they fully control while giving the victim an unusable secret share. When Bitcoin deposits are scanned under that group key, the resulting P2TR outputs are spendable by the attacker rather than by Serai.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, participant index, interpolation data, a secret share, and `n` verification shares directly from untrusted input, then passes all of those fields to `ThresholdKeys::new`. [1](#0-0) 

`ThresholdKeys::new` checks only the number and range of verification shares and the applicability of the interpolation mode. [2](#0-1)  It then derives `group_key` by interpolating verification shares `1..=t`. [3](#0-2)  No check establishes `verification_shares[i] == G * secret_share`, nor that the secret shares form a valid threshold sharing of that group key.

For example, an attacker can encode `t = 1`, `n = 1`, `i = 1`, a zero or otherwise unrelated local secret share, and a verification share equal to the attacker’s public key. The decoded `ThresholdKeys` will report the attacker’s public key as `group_key`. The Bitcoin scanner converts `group_key` directly into the P2TR script it watches. [4](#0-3) [5](#0-4) 

When a deposit transaction contains that script, `Scanner::scan_transaction` reports the output as received and associates it with offset zero. [6](#0-5)  Because the deposit is locked to the attacker-controlled public key, the attacker can spend it independently of Serai’s signing machines.

### Impact Explanation
The attacker can redirect funds accepted by Serai to a Bitcoin key they control. The injected local secret share does not have to correspond to the attacker-controlled verification share, so Serai cannot later produce valid signatures while the attacker retains unilateral spending authority. This is a loss-of-funds condition equivalent to registering a validator whose withdrawal credentials resolve to an operator-controlled address.

### Likelihood Explanation
The exploit only requires an attacker to control serialized bytes passed to `ThresholdKeys::read`. The deserializer performs field-level and participant-index validation but no cryptographic consistency check between the encoded secret share, the participant’s verification share, and the resulting group key. [1](#0-0) 

### Recommendation
`ThresholdKeys::read` should reject key material whose encoded local secret does not match its encoded verification share. At minimum, after constructing the shares map, require:

```rust
C::generator() * secret_share == verification_shares[&params.i()]
```

Preferably authenticate serialized threshold key state before accepting it and, where the intended group key is known independently, compare the derived `group_key` against that trusted key before registering deposit scripts or accepting funds.

### Proof of Concept
The following constructs a syntactically valid serialized `ThresholdKeys<Secp256k1>` whose group key is an attacker public key while the encoded local secret is unrelated:

```rust
use ciphersuite::{group::{ff::Field, GroupEncoding}, Ciphersuite};
use frost::{curve::Secp256k1, ThresholdKeys};
use k256::{ProjectivePoint, Scalar};

fn attacker_key() -> ProjectivePoint {
    let mut private = Scalar::random(&mut rand_core::OsRng);
    let mut public = ProjectivePoint::GENERATOR * private;
    if Scanner::new(public).is_none() {
        private = -private;
        public = -public;
    }
    public
}

fn malicious_serialized_keys(public: ProjectivePoint) -> Vec<u8> {
    let mut bytes = vec![];
    bytes.extend(u32::try_from(Secp256k1::ID.len()).unwrap().to_le_bytes());
    bytes.extend(Secp256k1::ID);

    bytes.extend(1u16.to_le_bytes()); // t = 1
    bytes.extend(1u16.to_le_bytes()); // n = 1
    bytes.extend(1u16.to_le_bytes()); // i = Participant(1)
    bytes.push(1);                    // Lagrange interpolation

    bytes.extend(Scalar::ZERO.to_repr().as_ref()); // unrelated secret share
    bytes.extend(public.to_bytes().as_ref());      // attacker verification share
    bytes
}

let public = attacker_key();
let keys = ThresholdKeys::<Secp256k1>::read(&mut malicious_serialized_keys(public).as_slice())
    .unwrap();
assert_eq!(keys.group_key(), public);
```

`group_key` is attacker-controlled because `t = 1` makes the first supplied verification share the entire group key. [3](#0-2)  Registering that key in the Bitcoin scanner watches the P2TR script derived from the attacker key. [5](#0-4)  Any transaction paying that script is reported as a received output even though the attacker can spend it. [7](#0-6)
