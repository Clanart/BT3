### Title
Unconditional script-pubkey classification routes unsolicited external payments into the multisig's spendable UTXO pool without crediting any depositor - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` classifies any transaction output paying to a registered script purely by `script_pubkey`, with no check on who sent it or why. This is the same bug class as Kinetiq's `receive() external payable { stake(); }`: incoming value is unconditionally routed into an internal accounting bucket. Any unprivileged party who sends BTC to the multisig's `Branch`, `Change`, or `Forwarded` address has their output classified as an internal output, added to the scheduler's spendable UTXO pool, and spent on behalf of other users' payments — while generating no `InInstruction` and no deposit credit. The funds are irrecoverable to the sender and silently inflate the multisig's balance, mirroring how misrouted HYPE inflated the kHYPE exchange ratio.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` mapping each registered offset script to an offset, and `scan_transaction` emits a `ReceivedOutput` for every output whose `script_pubkey` is in the map — unconditionally, for any tx in the block [1](#0-0) . The processor registers four well-known, publicly derivable scripts per key: `External` (offset 0), `Branch`, `Change`, and `Forwarded`, all computed via `Secp256k1::hash_to_F(KEY_DST, ...)` — anyone can derive and pay to these addresses [2](#0-1) . `get_outputs` then tags each scanned output with its `OutputType` solely from the offset [3](#0-2) .

Downstream, only `OutputType::External` outputs become deposit instructions; `Forwarded` outputs without a matching `ForwardedOutputDb` entry produce nothing [4](#0-3) . Yet all scanned outputs — regardless of kind — flow into `Scheduler::schedule` → `add_outputs`, where non-Branch outputs are pushed into `self.utxos`, the spendable pool [5](#0-4) . `OutputType::Change` is explicitly documented as "added to the available UTXO pool with no further action" [6](#0-5) .

### Impact Explanation
An unsolicited external payment to the `Change` or `Forwarded` address is swept into the multisig's UTXO set and spent to fund other users' withdrawals, with the sender receiving no Serai-side credit (no `InInstruction`, no refund path since `refund_plan` asserts `OutputType::External` [7](#0-6) ). The multisig gains spendable BTC that is backed by no minted liability — the direct analog of kHYPE being minted to the system address and locked forever, inflating the exchange ratio. Additionally, a payment to the `Branch` address with an amount matching a queued plan's amount is auto-consumed by `add_outputs` to execute that plan, spending the attacker's/user's funds on protocol payments [8](#0-7) .

### Likelihood Explanation
The addresses are deterministic and public (`hash_to_F` offsets over the group key). Any user who derives the deposit-address logic incorrectly, or any external wallet/explorer that reuses a previously seen change/forward address (address reuse is common on Bitcoin), triggers permanent loss. No attacker profit is needed for the honest-user-loss and unbacked-funds inflation impacts. The code partially acknowledges the class ("Eve ... has sent us a forged TX which is ... equally as usable? so who cares?") but only analyzes Branch; the unbacked-funds and uncredited-deposit consequences for Change/Forwarded are unhandled [9](#0-8) .

### Recommendation
Mirror the report's fix (`if (msg.sender != systemAddress)`) by distinguishing provenance: for `Change` outputs, only accept them into the UTXO pool when the spending tx was created by a known Plan (extend the `ResolvedDb`/`PlanDb` gating already used during rotation to all steps). For `Forwarded`, only treat outputs whose tx is an expected forwarding Plan as `Forwarded`; classify unexpected payments to internal addresses as `External` (crediting them) or refuse to pool them. At minimum, emit a refund instruction for any non-External output whose tx is not protocol-created.

### Proof of Concept
1. Derive the multisig's change address: `change_addr = address_from_key(key + G * hash_to_F(KEY_DST, "change"))` via `scanner(key)` in `processor/src/networks/bitcoin.rs`.
2. External user broadcasts a BTC tx paying `change_addr` with amount > `N::DUST`.
3. `get_outputs` scans it, tags it `OutputType::Change` from `kinds[offset]` [3](#0-2) .
4. In `scanner_event_to_multisig_event`, the output is filtered out of instruction processing (`kind() != External` → no `InInstruction`, no credit) [10](#0-9) .
5. In `plans_from_block` → `Scheduler::schedule` → `add_outputs`, the output is pushed to `self.utxos` and later spent as an input in an aggregation/payment Plan — funding other users' withdrawals while the sender is never credited [11](#0-10) .
