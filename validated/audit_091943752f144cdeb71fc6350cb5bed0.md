### Title
Untrusted `ReceivedOutput` bytes are accepted without proving the output belongs to the wallet - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` accepts an offset, `TxOut`, and `OutPoint` without validating that the claimed output script is derived from the wallet key and offset. Publicly supplied bytes can therefore be deserialized into a “received” output that the wallet cannot spend.

### Finding Description
`ReceivedOutput` stores the three values needed to identify and later spend an output: `offset`, `output`, and `outpoint` [1](#0-0) . Its deserializer independently accepts all three attacker-controlled fields and returns the object without checking whether `output.script_pubkey` equals the wallet's P2TR script for `key + offset * G` [2](#0-1) .

The legitimate derivation exists in `Scanner`: `Scanner::new` registers the base-key script with offset zero, `register_offset` derives scripts from `self.key + GENERATOR * offset`, and `scan_transaction` only creates a `ReceivedOutput` after matching `output.script_pubkey` against that authenticated map [3](#0-2) [4](#0-3) . `ReceivedOutput::read` bypasses this validation and reconstructs the trusted output record directly.

The mismatch is only detected later: `SignableTransaction::multisig` applies the claimed offset and rejects the input if the resulting group key's P2TR script differs from `prevouts[i].script_pubkey` [5](#0-4) . Thus arbitrary serialized data can be reported as a received balance, but cannot be signed and spent.

### Impact Explanation
An attacker who can provide serialized `ReceivedOutput` data can cause an application to record an arbitrary Bitcoin output and value as received funds. The record can reference someone else's P2TR output, a nonexistent outpoint, or an output whose script is unrelated to the claimed offset. Any attempted spend through `SignableTransaction::multisig` fails because the wallet key plus claimed offset does not produce the claimed script. This creates false received funds and potential accounting or deposit-crediting inconsistencies.

### Likelihood Explanation
The attacker only needs to reach a call site that deserializes untrusted data with `ReceivedOutput::read`. No private key, valid transaction history, signature, or consensus control is required. The serialized fields are a canonical scalar followed by consensus-encoded `TxOut` and `OutPoint` values.

### Recommendation
Do not treat deserialized `ReceivedOutput` values as authenticated scan results. Store the expected wallet key or scanner identity alongside the record and validate `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey` during reconstruction. Alternatively, expose deserialization only through a scanner-bound method such as `Scanner::read_received_output`, and ensure persisted scan results are integrity/authenticity protected if they cross an untrusted boundary.

### Proof of Concept
Conceptually:

```rust
let offset = Scalar::ZERO;

// A P2TR script for an unrelated attacker key, not the wallet key.
let unrelated_key = ProjectivePoint::random(&mut OsRng);
let unrelated_script = p2tr_script_buf(unrelated_key).unwrap();

let forged_output = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: unrelated_script,
};

let forged_outpoint = OutPoint::default();

let mut encoded = Vec::new();
encoded.extend(offset.to_bytes());
encoded.extend(serialize(&forged_output));
encoded.extend(serialize(&forged_outpoint));

// Accepted without proving the script belongs to the wallet or offset.
let received = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
assert_eq!(received.value(), 100_000);

// Spending fails because wallet_key + offset does not derive the attacker's script.
assert!(
  SignableTransaction::new(
    vec![received],
    &[(wallet_payment_script, 1_000)],
    None,
    None,
    1,
  )
  .unwrap()
  .multisig(&wallet_keys)
  .is_none()
);
```

The root cause is the absence of scanner-key binding in `ReceivedOutput::read`, while legitimate production of this type requires a `script_pubkey` match in `Scanner::scan_transaction` [6](#0-5) .

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }
