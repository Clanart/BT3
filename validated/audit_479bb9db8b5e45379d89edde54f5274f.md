### Title
Scanner credits outputs created and spent within the same block as received, reporting unspendable funds - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`Scanner::scan_transaction` (and `scan_block`) match outputs purely by `script_pubkey` and emit a `ReceivedOutput` for every matching outpoint, without checking whether that outpoint is spent again by a later transaction in the same block. The processor's `get_outputs` then forwards every such `ReceivedOutput` as a credited deposit. An unprivileged user can therefore make Serai report funds as received that are not spendable, mirroring the audited bug class where accrued value is claimable/sent onward even though it can no longer be legitimately claimed.

### Finding Description
In `Scanner::scan_transaction`, each transaction output is looked up in `self.scripts` by `script_pubkey` alone and immediately pushed as a `ReceivedOutput` keyed to `OutPoint::new(tx.compute_txid(), vout)`. [1](#0-0)  `scan_block` simply concatenates results over every transaction in the block, with no cross-transaction spentness check. [2](#0-1) 

The processor consumer `Bitcoin::get_outputs` iterates `block.txdata[1 ..]` and collects every scanned output, filtering only on the `DUST` threshold, never on whether the outpoint survives the block. [3](#0-2)  The returned `ReceivedOutput` stores the offset, `TxOut`, and `OutPoint` with no block-context validity flag. [4](#0-3) 

Later, `SignableTransaction::new` treats each `ReceivedOutput` as a real spendable UTXO, summing `input.output.value` into `input_sat` and building `TxIn`s from `input.outpoint`. [5](#0-4)  `multisig` verifies only that the stored `prevouts[i].script_pubkey` corresponds to `key + offset*G`, i.e., key spendability — not on-chain existence. [6](#0-5) 

An attacker who knows Serai's deposit script (public, derivable from the group key) can publish in one block: (a) a transaction paying to Serai's script_pubkey, and (b) a transaction spending that same outpoint (if they control the key, e.g. by first receiving to an offset address they arrange) — or more practically, double-spend races aside, the simplest reachable case is an output created and spent in the same block by anyone who momentarily controls it. The scanner still reports it; the outpoint no longer exists.

### Impact Explanation
The processor credits a deposit whose UTXO does not exist. Any `SignableTransaction` built including that `ReceivedOutput` will produce a fully-signed transaction that Bitcoin rejects (`bad-txns-inputs-missingorspent`), burning the entire signing round and stalling all other payments batched with it (all inputs are committed via `Prevouts::All` at `send.rs:375`). Repeatedly feeding such outputs causes sustained failure of withdrawal/batch signing — value is "received" on Serai's books while the underlying funds are unspendable, the direct analog of fees being claimable when they can no longer be paid out.

### Likelihood Explanation
Reachable by any unprivileged party able to get two transactions (or one spending a registered-script output) into the same Bitcoin block. Requires the attacker to control an output at a registered script at least briefly, which is achievable by depositing and then spending before/within block inclusion boundaries. Likelihood is moderate; impact is a repeatable signing liveness/accounting failure rather than direct theft, so Medium.

### Recommendation
In `get_outputs` (or `scan_block`), build the set of all outpoints spent within the block (`tx.input[*].previous_output`) and drop scanned outputs whose `OutPoint` appears in that set. Alternatively, verify each scanned `OutPoint` against the node's UTXO set (`gettxout`) before emitting it.

### Proof of Concept
Conceptual test flow (regtest):
1. `let mut scanner = Scanner::new(even_key).unwrap();`
2. Craft `tx_a` in a block with `output[0].script_pubkey == p2tr_script_buf(key)` (attacker controls the destination, e.g. deposits and immediately re-spends via `tx_b` in the same block consuming `tx_a:0`).
3. `scanner.scan_block(&block)` returns a `ReceivedOutput` for `OutPoint(tx_a.txid, 0)` even though it is spent by `tx_b` in the same block — `scan_transaction`/`scan_block` never inspect `tx.input` prevouts (`mod.rs:199-227`).
4. `Bitcoin::get_outputs` pushes it into `outputs` (only `DUST` filtered, `bitcoin.rs:686-700`), and `SignableTransaction::new` will build an input referencing the nonexistent outpoint (`send.rs:175-185`), yielding a transaction the network rejects.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
