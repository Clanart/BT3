### Title
Path-boundary check in `resolveWithin` uses substring comparison instead of segment-aware comparison, allowing traversal into sibling directories - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` in `app/src/lib/path.ts` are the app's central guard for "make sure this attacker-influenced relative path stays inside this root directory" and are used to validate paths coming from untrusted sources such as the `filepath` parameter of the `x-github-client://openRepo/...` deep link and conflict file paths built from repository contents. The final containment check is a raw string-prefix comparison, `realResolved.startsWith(realRoot)`, with no path-separator boundary check. [1](#0-0) 

### Finding Description
The broken invariant is identical in shape to the Lido bug: a boundary/limit test is computed with one term missing, so the guard is more permissive than intended. Here the "limit" is the root directory boundary, and the missing term is the path separator that should terminate the prefix match.

`realResolved.startsWith(realRoot)` returns `true` whenever `realResolved`'s string begins with the exact characters of `realRoot`, even if the next character is not a path separator. This means a resolved path in a *sibling* directory whose name simply starts with the same characters as the root directory's name will pass the check.

Example: if `rootPath` is `/Users/victim/Documents/GitHub/repo`, a `realResolved` value of `/Users/victim/Documents/GitHub/repo-evil/secret.txt` also satisfies `startsWith(realRoot)`, because `"repo-evil"` textually starts with `"repo"`. The function will happily return this out-of-root path as valid instead of `null`.

The reachable attacker-controlled path is `dispatcher.ts`'s handling of the `open-repository-from-url` deep-link action, which is parsed by `parse-app-url.ts` from a URL the user clicks (`x-github-client://openRepo/<url>?filepath=<attacker string>`). The `filepath` query value is passed essentially unsanitized (only an `isAbsolute` check is applied) into `resolveWithin(repository.path, filepath)`: [2](#0-1) 

By crafting `filepath` to contain `..` segments that resolve into a sibling directory whose name begins with the target repository's directory name (e.g. `../repo-evil/...`, or more reliably by controlling the query itself, `../<reponame_prefix_of_something_sensitive>/...`), an attacker can make `resolveWithin` accept a path that is *not* actually inside the cloned repository. The existing guards (`isAbsolute(filepath)` check, and the traversal-rejecting `resolve()`/`normalize()` calls inside `_resolveWithin`) do not stop this: `resolve()` intentionally collapses `..` segments (that's how legitimate "traverse out, then back in" paths are supported, per the existing test suite), and the final acceptance decision relies solely on the flawed `startsWith` comparison, which has no notion of path-component boundaries.

This same helper (`resolveWithin`) is also used in `app/src/lib/copilot-conflict-context.ts` to gate which conflicting file paths get read from disk and sent to a (potentially user-configured, BYOK) LLM endpoint: [3](#0-2) 

### Impact Explanation
- Via the `open-repository-from-url` deep link path, the resolved (but actually out-of-repo) path is passed to `shell.showItemInFolder(resolved)` — revealing an unintended, attacker-chosen filesystem location in Finder/Explorer instead of the intended repo file. This is a real deep-link-triggered guard bypass of the "stay inside repo root" invariant.
- More seriously, the same primitive is reused by `buildConflictContext` to decide which on-disk files are safe to read and forward to an AI/Copilot backend during conflict resolution. If a maliciously crafted repository/merge state can cause a conflicting "file path" whose sibling-prefix trick escapes the intended working directory, file contents from outside the repository could be read and exfiltrated to a remote (possibly attacker-controlled, if BYOK base URL is attacker-influenced) LLM endpoint — a credential/token or arbitrary local file exfiltration path, matching the "attacker controls a cloned/fetched repository ... result is ... credential/token exfiltration" impact class in the report criteria.
- Whether git conflict metadata can actually produce a `file.path` value containing the necessary `..` traversal segments (as opposed to always-clean repo-relative paths from `git status`) could not be fully confirmed from the available code; this is the main source of remaining uncertainty for the conflict-context vector. The deep-link `filepath` vector, by contrast, is unambiguous and fully attacker-controlled end-to-end (report clicks a link → `parseAppURL` → `dispatchURLAction` → `resolveWithin`).

### Likelihood Explanation
The `filepath` query parameter of the `openRepo` deep link is fully attacker-controlled string content reachable purely by the victim clicking a link (no local access, no admin rights, no prior compromise required), satisfying the report's "unprivileged... a link or deep link the user clicks" criterion. The only pre-existing mitigation on this parameter is a check for a leading absolute path; relative traversal strings are not filtered before reaching `resolveWithin`, and the vulnerable comparison inside `resolveWithin` does not stop them if the resulting path happens to land in a sibling directory with a matching name prefix. The existing unit tests in `app/test/unit/path-test.ts` only cover clean-root-escape and symlink-escape cases — never a same-prefix sibling-directory case — indicating this exact bypass class was not covered by the guard's own test suite. [4](#0-3) 

### Recommendation
Change the final containment check in `_resolveWithin` (`app/src/lib/path.ts`, line 71) to require a path-separator boundary, not just a string prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the platform-appropriate separator from the `options` parameter, matching `Path`, `Path.posix`, or `Path.win32`). Add a regression test asserting that a sibling directory whose name is a superstring of the root's basename (e.g. root `.../repo`, target `.../repo-evil/file`) is correctly rejected.

### Proof of Concept
1. Suppose Desktop has a repository cloned at `/Users/victim/Documents/GitHub/repo`.
2. Attacker hosts/sends a link: `x-github-client://openRepo/https://github.com/owner/repo?filepath=..%2Frepo-evil%2Fsecret.txt` (i.e., `filepath=../repo-evil/secret.txt`), where `/Users/victim/Documents/GitHub/repo-evil/secret.txt` is an arbitrary file/directory that happens to exist alongside the real repo (or is otherwise reachable via a crafted relative path whose resolved sibling name is a superstring of the repo directory name).
3. Victim clicks the link; Electron's `open-url`/protocol-launcher handling calls `handleAppURL` → `parseAppURL` → `dispatchURLAction` → `openRepositoryFromUrl`.
4. `filepath` passes the `isAbsolute` check (it's relative) and is passed to `resolveWithin(repository.path, filepath)`.
5. Inside `_resolveWithin`, `resolve()` collapses the `..`, yielding `/Users/victim/Documents/GitHub/repo-evil/secret.txt`; `realResolved.startsWith(realRoot)` (`realRoot` = `/Users/victim/Documents/GitHub/repo`) evaluates to `true` due to the missing separator, so the function returns the out-of-root path instead of `null`.
6. `shell.showItemInFolder(resolved)` reveals the out-of-repository file/location to the attacker-controlled deep link, demonstrating the guard bypass. (The higher-impact file-content-exfiltration variant via `copilot-conflict-context.ts` uses the identical flawed primitive but requires further confirmation of whether conflict-derived `file.path` values can be induced to contain the needed traversal segments.)
