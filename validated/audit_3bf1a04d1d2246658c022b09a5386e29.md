### Title
Change outputs below the processor's dust threshold are created but never re-scanned, stranding funds forever - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` emits a change output whenever the leftover exceeds the wallet crate's `DUST` constant of 546 sats, but the processor's Bitcoin `Network` implementation defines `DUST` as 10_000 sats and the multisig scanner silently drops every output below that amount. Any change in the range [546, 10_000) sats is created on-chain yet permanently invisible to the scheduler — the same class of bug as the Derby report (residual value left behind after a funds-moving operation).

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the local relay-level constant `DUST = 546` is the only gate for whether change is created:

```rust
// networks/bitcoin/src/wallet/send.rs:228-234
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
  if value >= DUST {                     // DUST = 546 (line 32)
    tx_outs.push(TxOut { value: Amount::from_sat(value), script_pubkey: change });
```

The doc comment even frames the choice as "all leftover funds will become part of the paid fee" only when no change address is given or the leftover is sub-dust — i.e., creating change is supposed to preserve the leftover.

Downstream, however, the processor defines a much larger dust bound for Bitcoin — `const DUST: u64 = 10_000` in `processor/src/networks/bitcoin.rs:638` (justified by a 5 sat/vbyte spendability margin) — and the multisig scanner filters out every scanned output under it:

```rust
// processor/src/multisigs/scanner.rs:562-566
for output in network.get_outputs(&block, key).await {
  assert_eq!(output.key(), key);
  if output.balance().amount.0 >= N::DUST {
    outputs.push(output);
  }
}
```

The change address used by `make_signable_transaction` (`processor/src/networks/bitcoin.rs:417-472`, which passes `change` straight into `BSignableTransaction::new`) is a scanner-registered offset script, so the change output will be matched by `Scanner::scan_transaction` — and then discarded by the `>= N::DUST` check. It is never pushed into `outputs`, never becomes a schedulable input, and since `register_offset` is surjective and consumed, the offset/script is also burned.

### Impact Explanation
Every time a Bitcoin plan leaves a remainder between 546 and 9,999 sats, the wallet library dutifully creates a change output that the system's own accounting layer then refuses to track. Those satoshis are still controlled by the multisig key plus the change offset, but no code path will ever re-select them as inputs — they are stranded exactly like the unclaimed COMP rewards in the Derby report. The alternative (letting the <10_000 remainder roll into the fee) is what the code intends; instead it mints an unspendable-in-practice output. Over many transactions this is a slow, silent bleed of vault funds.

### Likelihood Explanation
The window is wide: it triggers whenever `input_sat - payment_sat - fee_with_change` lands in [546, 10_000), i.e. ~9,454 sats of a typical remainder distribution — a sub-0.0001 BTC range hit routinely for small withdrawals. No attacker action is needed; it is reachable purely through ordinary payment data submitted by users. The scheduler's amortization logic (`processor/src/multisigs/scanner.rs` / `scheduler/utxo.rs`) already drops sub-10_000 payments, but nothing checks that the *change* survives the same bound.

### Recommendation
In `SignableTransaction::new`, either accept a configurable `dust` parameter (so the processor can pass `Bitcoin::DUST = 10_000`) or create the change output only when `value >= DUST` where `DUST` matches the network-level spendability bound rather than the relay bound. Alternatively, have `make_signable_transaction` in `processor/src/networks/bitcoin.rs` pass the change only if the expected leftover can exceed `Self::DUST`. Keep the 546 check solely as a protocol-validity floor.

### Proof of Concept
1. Register a change offset so `change = Some(script)` in `make_signable_transaction`.
2. Choose inputs/payments such that `input_sat - payment_sat - fee_with_change = 5_000` (≥ 546, < 10_000).
3. `BSignableTransaction::new` succeeds and appends `TxOut { value: 5_000, script_pubkey: change }` (send.rs:230); the transaction is signed and broadcast.
4. On scan, `network.get_outputs` returns the change output, but `processor/src/multisigs/scanner.rs:564` drops it because `5_000 < 10_000`.
5. The 5,000 sats remain under the multisig key yet are never presented to the scheduler — funds left in the "protocol" forever, while the plan's accounting already treated them as recouped change.
