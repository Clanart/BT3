## Analysis Result

I traced the external report's core invariant — *"a state-mutating operation must use bounded/consistent authorization logic, or previously-recorded state can be silently invalidated or exploited"* — into the Aptos publish path. The strongest local analog I found is not in the classic `code.move` package registry (whose ownership/upgrade-policy checks are consistent and well-tested), but in the newer lazy-module-initialization feature (`aptos_framework::init`), which is wired directly into `code::publish_package`'s object-hosted publish flow.

### Title
Unbounded loop in `object::root_owner()` used by the code-publish and module self-init gate can render an object's code permanently unpublishable/uninitializable - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::root_owner()` walks the object ownership chain with **no depth bound**, unlike its sibling traversal functions `owns()` and `verify_ungated_and_descendant()`, which both explicitly cap traversal at `MAXIMUM_OBJECT_NESTING` (8) specifically because "objects may have cyclic dependencies." `root_owner()` is called from two security-critical, newly-added paths: `code::publish_package` (to record the deploy owner of object-hosted modules) and `init::assert_may_self_initialize` (to gate self-initialization). Because object ownership can legitimately be made cyclic (the codebase's own comment on `verify_ungated_and_descendant` acknowledges this), triggering `root_owner()` on a cyclic chain causes an unbounded loop that only terminates via gas exhaustion, permanently blocking `code::publish_package` (thus `object_code_deployment::upgrade`/`publish`) and `init::internal_maybe_initialize` for that object.

### Finding Description
`root_owner()`:
```move
// aptos-move/framework/aptos-framework/sources/object.move:742-748
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```
has no iteration cap.

Contrast with `owns()` (object.move:707-737) and `verify_ungated_and_descendant()` (object.move:608-639), both of which explicitly bound the walk at `MAXIMUM_OBJECT_NESTING` and document: *"Note, this is limited to a depth of 8 objects may have cyclic dependencies."* — i.e., the codebase treats cyclic ownership as an expected, reachable state, and every other traversal function defends against it except `root_owner()`.

`transfer_raw()`/`transfer()` (object.move:572-594) only verify that the *signer* transferring an object is an ancestor of that object (via the bounded `verify_ungated_and_descendant`); they do **not** check that the new owner (`to`) is not a descendant of the object being moved. An owner who controls both ends of a small object graph can therefore construct a cycle: transfer object B to be owned by A, then (still authorized, since A is directly owned by the same signer) transfer A to be owned by B, producing `A -> B -> A`.

### Impact Explanation
If the code-object address (or one of its owning ancestors) sits on a cyclic ownership chain, both `code::publish_package` (and therefore every entry point that funnels through it: `object_code_deployment::publish`, `object_code_deployment::upgrade`, `code::publish_package_txn`, `code::freeze_code_object`'s `check_dependencies` closure indirectly if run against such an object) and `init::internal_maybe_initialize`/`assert_may_self_initialize` will loop until the transaction runs out of gas. Because `check_and_set_initialized` marks the module "initialized" *before* `assert_may_self_initialize` runs and an out-of-gas abort rolls back all state changes, the module is left in an unrecoverable state where every subsequent legitimate call also loops forever — a permanent denial of upgrade/publish/init capability for that code object, once `LAZY_MODULE_INITIALIZATION` is enabled and the cycle exists. This corrupts the availability of a "protected state mutation" path (module publish/init) reachable from the code-safety-relevant `code.move`/`init.move` logic.

The exploit does not grant an attacker unauthorized ownership or code changes on a *victim's* object — the cycle must be built from objects the caller controls at the time of transfer (`verify_ungated_and_descendant` still gates transfers). So the practical blast radius is self-inflicted (or self-inflicted by a deployer who later wants to upgrade), not third-party fund theft. This caps the severity below "Critical," but it is still a genuine missing-bound/code-safety defect directly reachable from the object-code-deployment publish path, asymmetric with the rest of the module's own defensive design.

### Likelihood Explanation
Creating the cycle requires only two `object::transfer` calls by the same signer over objects they legitimately own (no privileged capability needed), and enabling the affected code path requires the `LAZY_MODULE_INITIALIZATION` feature flag to be active. Given the feature is part of the current framework surface (feature id 127) and explicitly designed for code objects that self-initialize, it is plausible this path is exercised in normal usage of `object_code_deployment` combined with nested object ownership patterns (e.g., DeFi vaults, aggregator objects) that developers commonly build with sub-objects.

### Recommendation
Bound `root_owner()`'s traversal the same way `owns()` and `verify_ungated_and_descendant()` are bounded (cap at `MAXIMUM_OBJECT_NESTING` and fail closed, e.g. abort with `EMAXIMUM_NESTING`, or return the address reached once the cap is hit) so it can never diverge from the rest of the module's cycle-tolerant design, and re-validate that `init::assert_may_self_initialize`/`code::publish_package` behave safely (fail with a clear, cheap error) when `root_owner()` cannot resolve within the bound.

### Proof of Concept
Conceptual reproduction (requires `LAZY_MODULE_INITIALIZATION` enabled):
1. Deployer creates object `A` (owned by deployer) and deploys a lazily-self-initializing module to it via `object_code_deployment::publish`; `code::publish_package` records `deploy_owner = deployer` for the module, using `root_owner()` on `A` (no cycle yet, resolves fine).
2. Deployer creates object `B`, transfers `B` to be owned by `A` (`object::transfer(deployer, B, A_addr)` — passes `verify_ungated_and_descendant(deployer, B)` since deployer directly owns `B`).
3. Deployer transfers `A` to be owned by `B` (`object::transfer(deployer, A, B_addr)` — passes `verify_ungated_and_descendant(deployer, A)` since deployer directly owns `A`). Ownership graph is now `A -> B -> A`.
4. Deployer calls `object_code_deployment::upgrade` on `A`, or any user calls the module's entry point that invokes `init::internal_maybe_initialize`. Both paths call `object::address_to_object<ObjectCore>(A).root_owner()`, which loops forever between `A` and `B`, consuming all transaction gas and aborting — publish/upgrade/self-init at `A` is now permanently unusable.

I was not able to run this end-to-end in a harness within this investigation; the trace above is derived directly from the cited source and existing framework unit tests confirming that (a) cycles are an accepted state (`verify_ungated_and_descendant` doc comment) and (b) `root_owner()` lacks the same depth guard used elsewhere in the same file.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }
