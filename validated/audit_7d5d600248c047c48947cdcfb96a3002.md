### Title
Locale-agnostic `String.prototype.toLowerCase()` length expansion causes commit-message text corruption on autocompletion insert - ([File: app/src/ui/autocompletion/autocompleting-text-input.tsx])

### Summary
`attemptAutocompletion` runs the autocompletion regexes against `str.toLowerCase()` [1](#0-0) , and the resulting `range.start`/`range.length` (positions computed against the lowercased string) are later used by `insertCompletion` to splice into `element.value`, which is the **original, non-lowercased** string [2](#0-1) . JavaScript's non-locale `toLowerCase()` performs a length-changing, unconditional Unicode special-case mapping for `İ` (U+0130 LATIN CAPITAL LETTER I WITH DOT ABOVE) → `i̇` (`i` + combining dot above, U+0307), turning one UTF-16 code unit into two. If such a character appears anywhere in the textarea content *before* the autocomplete-triggering token (`@`, `#`, `:`), every subsequent regex match index computed from `lowercaseStr` is offset by the accumulated length delta relative to the untransformed `str`/`element.value`. `insertCompletion` then slices the untransformed text at the wrong offsets: `originalText.substr(0, range.start - 1)` and `originalText.substring(range.start + range.length)` [3](#0-2) , either duplicating trailing characters into the completed text or silently dropping characters adjacent to the insertion point.

### Finding Description
The vulnerable path requires attacker-controlled text to appear in the same input as an autocomplete trigger:
1. `attemptAutocompletion` lowercases the whole string with the locale-independent `toLowerCase()` (line 739) before running the `EmojiAutocompletionProvider`/`IssuesAutocompletionProvider`/`UserAutocompletionProvider` regexes [4](#0-3) , all of which are `RegExp.exec` loops over the **whole lowercased string**, not just the token being completed.
2. `range.start`/`range.length` are derived from `regex.lastIndex` and `text.length`, both measured in `lowercaseStr` coordinates.
3. `insertCompletion` uses these same numeric offsets against `element.value` (`originalText`), which was never lowercased [5](#0-4) .
4. Any prior text containing `İ` (U+0130) causes `lowercaseStr.length > str.length` from that point on (since JS's unconditional `SpecialCasing` mapping applies even without locale), shifting all subsequent match indices by the accumulated delta.
5. The commit-message description textarea is pre-populated from attacker-influenced repository data: squash pre-fills the description via `getSquashedCommitDescription`, which directly joins `commit.summary`/`commit.bodyNoCoAuthors` from commits in the local repository history [6](#0-5) , and that value is passed straight into the `AutocompletingTextArea`'s `value` for the commit message description field [7](#0-6) . A commit authored by an attacker (in a cloned/fetched repo) can therefore inject `İ` into the pre-filled description, and any `onChange`/`open()` call re-lowercases the *entire* current field value including that injected text, misaligning offsets for whatever mention/issue/emoji token the user is currently typing/selecting nearby.

### Impact Explanation
Exploiting this does not achieve code execution, credential exfiltration, or sandbox escape. Its worst-case, reachable effect is corruption of the text spliced in/around an autocompletion insertion — duplicated or dropped characters in the commit summary/description the user is about to commit and push — which matches the program's "silent corruption of what the user commits or pushes" impact category, but only in this narrow, cosmetic-text sense (it does not corrupt already-committed history, diffs, or file contents outside the textarea being edited).

### Likelihood Explanation
Likelihood is low. It requires: (a) an attacker-authored commit reachable via squash/rebase description pre-fill (or any other flow that seeds textarea content from repo/API data) containing `İ` (U+0130) before an autocomplete trigger, (b) the victim to then interact with autocompletion (type `@`/`#`/`:` and accept a suggestion) in that same field, and (c) the corruption is a one-or-few-character-offset splice, not attacker-directed content injection — the attacker cannot control *what* text gets duplicated or dropped, only that misalignment occurs near the completion point. There's no indication of any existing safeguard (e.g., Unicode-normalization-aware indexing or code-point-safe lowercasing) preventing this.

### Recommendation
Compute autocompletion regex matches against `str` while making the matching itself case-insensitive without changing string length/offsets — e.g., use case-insensitive regex flags (`i`) instead of pre-lowercasing the whole string, or lower-case only within provider-side comparison (`getAutocompletionItems`/`getMentionableUsersMatching`, as `EmojiAutocompletionProvider` and `UserAutocompletionProvider.exactMatch` already do at lines 73 and 110) rather than mutating the string used for index math in `attemptAutocompletion`.

2. In the pre-filled commit description textarea, position the caret after some text following the `İ` and type `@oc` to trigger `UserAutocompletionProvider`.
3. Select a suggested user from the popup.

export function getSquashedCommitDescription(
  commits: ReadonlyArray<Commit>,
  squashOnto: Commit
): string {
  const commitMessages = commits.map(
    c => `${c.summary.trim()}\n\n${c.bodyNoCoAuthors.trim()}`
  )

  const descriptions = [
    squashOnto.bodyNoCoAuthors.trim(),
    ...commitMessages,
  ].filter(d => d.trim() !== '')
