### Title
Duplicate-field detection in Python `json_format.Parse` misses same-field aliasing (camelCase vs. proto-name), allowing an untrusted JSON key to silently override a previously-set map field - (File: `python/google/protobuf/internal/json_format_test.py`)

### Summary
`AshOban`'s CVE stems from a trust boundary being defeated because two representations of the *same logical key* (an atom vs. a JSON-round-tripped string) are not recognized as colliding, so an attacker-controlled value silently displaces a trusted one under "last-key-wins" semantics. The closest verified analog in this Protobuf checkout is in the Python JSON parser (`google.protobuf.json_format`): its duplicate-field/duplicate-map-key rejection logic recognizes *exact* string matches of a field's name but fails to recognize that the camelCase JSON name (`int32Map`) and the underlying proto field name (`int32_map`) refer to the identical field. Consequently, when a JSON payload contains both spellings, they are not treated as a collision, and the value provided under the second spelling silently wins over the first — the same "distinct key representation, same logical target" failure mode as the AshOban bug, just realized as JSON key-aliasing rather than atom/string aliasing.

### Finding Description
Protobuf's documented, intentional wire-format semantics allow "last one wins" for duplicate *singular* fields [1](#0-0) . Both the Java and C++ JSON parsers implement this deliberately, and explicitly *reject* payloads that specify the same logical field twice under different valid name spellings (`optional_nested_message` vs `optionalNestedMessage`), which is the correct trust-preserving behavior [2](#0-1)  and is likewise enforced in the C++ binary/JSON conformance suite via explicit `FieldNameDuplicateDifferentCasing` cases that expect a specific merged/last-wins result rather than silent divergence [3](#0-2) .

The Python implementation of the same "reject/merge duplicate field name" invariant is broken for **map fields**: the duplicate-key checker only catches keys that are exact string matches, not alternate spellings (camelCase JSON name vs. original snake_case proto name) that resolve to the same underlying `FieldDescriptor`. This is explicitly acknowledged as an implementation oversight in the test suite itself: [4](#0-3) 

```
def testDuplicateFieldAlternateNamesMap(self):
    # Note: this behavior is non-spec and an oversight bug in the
    # implementation, but would be a breaking change to fix. The duplicate field
    # checker intends reject inputs with duplicate key names, but it only
    # catches keys that are exact matches and not alternate spellings that
    # correspond to the same field.
    parsed_message = json_format_proto3_pb2.TestMap()
    json_format.Parse(
        '{"int32Map": {"1": 2}, "int32_map": {"3": 4}}', parsed_message
    )
    self.assertEqual(parsed_message.int32_map, {3: 4})
```

The failed invariant maps directly onto the AshOban bug class:
- **AshOban**: trusted `:primary_key`/`:tenant` (atom keys) vs. attacker `:args` (string keys, post-JSON-round-trip) — same logical key, different representation, `Map.merge`/JSON dedup fails to see the collision, attacker value wins.
- **Protobuf (Python JSON parser)**: the same logical map field addressed via its canonical proto name (`int32_map`) vs. its camelCase JSON name (`int32Map`) — same logical field, different textual representation, the duplicate-key/"already seen" tracking set only stores the literal string seen, so it fails to see the collision, and the second occurrence's value silently replaces the first's.

### Impact Explanation
Whether this rises to a security impact depends entirely on the consuming application: if application code parses two syntactically different JSON payloads or JSON fragments from different trust levels (e.g., a trusted, server-populated seed object using the canonical proto field name merged with a second, attacker-supplied fragment using the camelCase alias) into the same `Message` via `json_format.Parse`/`ParseDict`, an attacker can silently overwrite a "trusted" map entry that the application assumed could not be affected by their input, because the parser gives no error and no signal that a collision occurred. This is analogous to the AshOban authorization/tenant-isolation bypass in spirit (silent override of a value the caller believed was protected from external influence), though the blast radius here is limited to whatever data lives in the specific map field being parsed, not an arbitrary primary key / tenant scope. The Python maintainers themselves classify it as a known, low-severity implementation quirk that they have declined to fix due to backward-compatibility concerns, which caps its practical severity below the AshOban CVE (which enabled cross-tenant, cross-record authorization bypass on database mutations).

### Likelihood Explanation
Exploitability requires: (1) an application using the Python protobuf runtime's `json_format.Parse`/`ParseDict`/`MergeMessage` to merge JSON derived even partially from attacker input into a message that also contains trusted map data using the canonical field name, and (2) the specific field being a `map<>` field (the bug is scoped to map fields per the test; regular singular/message fields ARE correctly detected as duplicates across camelCase/snake_case per `testParserRejectDuplicatedFields` in Java, and Python's own general duplicate-field checks for non-map fields were not shown to have this gap). This is a narrow, already-documented condition rather than a general parsing vulnerability, and it requires a specific application pattern (merging trusted+untrusted JSON into the same message) to become security-relevant, similar to how the AshOban bug required an app to forward `:args` from user input.

### Recommendation
For Protobuf: track "seen" field identity by resolved `FieldDescriptor` object (or field number) rather than by the raw JSON key string when performing duplicate-map-key rejection in `python/google/protobuf/json_format.py`'s map-field handling, mirroring what the Java/C++ implementations already do for non-map singular fields. At minimum, document prominently that `json_format.Parse` map-field duplicate detection is name-literal and can be bypassed via the camelCase/snake_case alias, so applications must not rely on it as a trust boundary. Applications should never merge trusted and untrusted JSON fragments into a single message via `json_format`; trusted values should be set programmatically via the message API after parsing untrusted JSON, not merged via a second `Parse`/`MergeMessageInto` call.

### Proof of Concept
The existing regression test is itself a reproducible PoC of the missing-collision condition (no crash, but demonstrates the invariant break): [5](#0-4) 

```python
parsed_message = json_format_proto3_pb2.TestMap()
json_format.Parse(
    '{"int32Map": {"1": 2}, "int32_map": {"3": 4}}', parsed_message
)
self.assertEqual(parsed_message.int32_map, {3: 4})
```

If an application constructs the first `int32Map` fragment from a trusted source and concatenates/merges a second, attacker-controlled `int32_map` fragment (or vice versa) into the same JSON object before calling `Parse`, the parser raises no duplicate-key error, and the attacker-supplied entry (`{3: 4}`) silently wins over the trusted one — reproducing, at the scope of a single map field, the "different key representation defeats trusted-value precedence" pattern described in the AshOban report. I was not able to independently confirm the equivalent behavior for the Java or C++/upb JSON parsers' map-field duplicate detection in this pass (only the Python maintainers' own acknowledgment was found); this should be verified against those runtimes if a broader claim across languages is desired.
