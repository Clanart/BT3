### Title
Payout tx OP_RETURN and anchor outputs are unsigned under SIGHASH_SINGLE|ANYONECANPAY, letting anyone strip the operator OP_RETURN and cause a funded standard payout to be misclassified as attribution-less, burning the operator's collateral - (File: `core/src/verifier.rs`, `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The withdrawal signature enforced by `parse_withdrawal_sig_params` must be `TapSighashType::SinglePlusAnyoneCanPay`, which under BIP341 only commits to input 0 (via `ANYONECANPAY`) and output 0 (via `SINGLE`) — it does not cover the anchor output or the operator's OP_RETURN output added by `create_payout_txhandler`. Anyone who observes operator A's broadcast (but unconfirmed) `payout_tx` can reuse that exact witness for input 0/output 0 in a new transaction that omits the OP_RETURN and anchor outputs, and race it into a block ahead of A's original, making `Verifier::update_finalized_payouts` record `operator_xonly_pk = None` for a withdrawal that A actually funded.

### Finding Description
Binding claimed correct: `payout_payer_operator_xonly_pk_for_withdrawal(i) == operator who actually fronted the withdrawal(i)`.

`Operator::withdraw` (`core/src/operator.rs:620-637`) builds the payout tx via `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`), which adds three outputs: user payout (0), anchor (1), OP_RETURN with the operator's x-only pubkey (2). The single spent input (the user's withdrawal UTXO) is verified against `in_signature` with `sighash_type` taken directly from the wire signature and enforced to be `SinglePlusAnyoneCanPay` by `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:161-187`). `calculate_pubkey_spend_sighash`/`calculate_sighash_txin` (`core/src/builder/transaction/txhandler.rs:210-233`, `365-377`) implement the BIP341 semantics correctly: for `*PlusAnyoneCanPay` types only the single spent prevout is committed (`Prevouts::One`), and `SIGHASH_SINGLE` only commits output index 0 - outputs 1 and 2 (anchor, OP_RETURN) are excluded from the sighash by construction.

Since the signature never covers the anchor or OP_RETURN outputs, or any other input, an attacker who observes A's broadcast (but unconfirmed) `payout_tx` in the public mempool can extract the witness for input 0 (the withdrawal UTXO + valid Schnorr signature) and build a competing transaction: input 0 = same outpoint + same witness (valid, since ANYONECANPAY permits swapping/adding any other inputs), input 1 = attacker's own fee UTXO, output 0 = the identical user payout output (required, since SIGHASH_SINGLE commits to it), and no OP_RETURN, no anchor. This is a valid, standalone-relayable transaction requiring no privileged key material — only the publicly-observable witness and the attacker's own funds for fees.

If this attacker transaction reaches a miner/gets propagated ahead of A's original payout_tx, it confirms first, spending the withdrawal UTXO. `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2354`) then looks up whichever tx actually spent the tracked withdrawal UTXO, extracts `get_first_op_return_output`, finds none, and stores `operator_xonly_pk = None` (`core/src/verifier.rs:2314-2342`, `core/src/database/verifier.rs:198-251`). When A later legitimately sends its kickoff (having genuinely intended and prepared to front the withdrawal), `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) fetches payout info via `get_payout_info_from_move_txid`, sees `operator_xonly_pk_opt == None`, and unconditionally returns `true` ("No operator xonly pk found in payout tx OP_RETURN, assuming malicious"), regardless of whether A's own broadcast attempt actually funded the withdrawal amount identically. This triggers a Challenge against A's kickoff, burning A's collateral.

None of the existing guards prevent this: `Verifier::is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr`, and `verify_storage_proofs`/`SPV::verify` operate earlier in the flow and never re-validate that the confirmed spending tx of the withdrawal UTXO matches the exact tx A intended to broadcast (only the enforced sighash type, which is precisely what leaves this hole open).

### Impact Explanation
An honest operator's collateral is burned via the Challenge/Disprove flow despite that operator having correctly fronted the withdrawal amount to the user — this matches the Critical category "an honest operator's collateral burned." The attack is repeatable for every standard-path withdrawal any operator processes; the attacker's cost per attempt is only competitive fee-bumping to win the mempool/mining race, no BTC value is lost by the attacker beyond fees, and the blast radius spans every operator and every withdrawal handled via the standard (non-optimistic) payout path.

### Likelihood Explanation
Preconditions: an operator must process a standard withdrawal (this is the common path) and broadcast `payout_tx` to the network before confirmation; the attacker only needs to observe the mempool (public data) and have enough BTC to outbid or race the fee. Given the enforced `SinglePlusAnyoneCanPay` sighash type is a protocol requirement (not an edge case), this vulnerability applies to every standard payout, making it broadly and repeatably exploitable, limited only by the attacker's ability to win a transaction-relay/fee race, which is a normal and inexpensive Bitcoin mempool operation, not majority hashrate.

### Recommendation
Do not rely solely on the presence/absence of an OP_RETURN in the confirmed spending transaction to attribute a payout. Either (a) commit the OP_RETURN and anchor outputs to the same signature by requiring an additional operator-controlled input/output that is fully committed (e.g., use `SIGHASH_ALL` for an operator-signed portion, or require the operator's own funding input to be part of a taproot commitment covering all outputs), or (b) have `update_finalized_payouts`/`is_kickoff_malicious` compare the full recorded/expected payout transaction (input, exact output set, and operator identity) against the confirmed transaction rather than trusting an unauthenticated OP_RETURN, treating a match on the committed input+output0 that lacks the expected OP_RETURN as a mutation of a known-good payout instead of an automatic "no attribution / assume malicious" verdict.

### Proof of Concept
```
cargo test forge_no_op_return_payout_misattribution -- --nocapture
```
Plan:
1. Run a standard deposit + withdrawal setup (reuse helpers from `core/src/test/deposit_and_withdraw_e2e.rs`), obtaining a valid `SinglePlusAnyoneCanPay` user signature for a withdrawal UTXO.
2. Call `Operator::withdraw` for operator A to build (but not yet mine) `payout_tx` via `create_payout_txhandler`; capture its witness for input 0 and output 0.
3. Construct a second transaction ("attacker tx") reusing that exact input 0 + witness, adding a locally-owned funding input/signature, with only output 0 identical to A's, omitting the anchor and OP_RETURN outputs. Assert `test_mempool_accept` accepts it.
4. Mine the attacker tx instead of A's `payout_tx` (simulate winning the race), assert both binding sides:
   - `db.get_payout_info_from_move_txid(...).0 == None` (misattributed, no operator pk) — should be `Some(A.xonly_pk)` had A's real tx confirmed.
5. Have operator A broadcast its real subsequent kickoff for this deposit; call `Verifier::is_kickoff_malicious` (or dispatch `Duty::CheckIfKickoffMalicious`) and assert it returns `true`, confirming a Challenge is queued against A despite A having genuinely funded the withdrawal.
