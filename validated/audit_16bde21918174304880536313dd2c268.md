### Title
Path-confinement bypass via missing separator boundary check in `resolveWithin` - (File: `app/src/lib/path.ts`)

### Summary
The reported Vault bug is a broken boundary invariant: a `>` comparison used where an inclusive/`+1` check was needed, letting one extra element slip past a size limit. The same broken-boundary pattern exists in GitHub Desktop's `_resolveWithin()` helper, which is the app's core "stay inside the repository root" guard used when handling attacker-influenced paths (e.g. deep-link file paths). Instead of an off-by-one on a count, it is an off-by-one on a *path prefix*: the containment check uses a raw string `startsWith(realRoot)` with no trailing separator, so a sibling path whose name merely begins with the root directory's name is incorrectly treated as "inside" the root.

### Finding Description
`_resolveWithin()` is meant to guarantee that a resolved path is "at, or underneath" `rootPath`, per its own doc comment [1](#0-0) . The final containment decision is:

```ts
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`String.prototype.startsWith` performs a plain character-prefix comparison with no path-separator boundary. This means `realResolved` such as `/Users/victim/Documents/GitHub/myrepo-secrets/token.txt` satisfies `startsWith('/Users/victim/Documents/GitHub/myrepo')` even though `myrepo-secrets` is a *sibling* directory, not something "underneath" `myrepo`. The invariant the function documents ("resolved path... resides at, or underneath this path") is broken exactly the same way the Vault check was broken: the boundary comparison (`>` vs `>=`, `startsWith` vs `startsWith(root + sep)`) fails to treat the boundary value correctly, letting a value that should be rejected pass through.

The existing regression tests in `app/test/unit/path-test.ts` only cover `..`-traversal and symlink-traversal cases [3](#0-2) ; none of them test the sibling-directory-name-prefix case, so this class of bypass is not guarded against by the current test suite.

`resolveWithin` is called from the deep-link/URL handler in `Dispatcher.openRepositoryFromUrl`, where `filepath` comes directly from an `x-github-client://` URL/deep link that the user clicks, and `repository.path` is the local clone directory:
```ts
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
} else {
  log.error(`Prevented attempt to open path outside of the repository root: ${filepath}`)
}
``` [4](#0-3) 

This is a real Desktop analog of the report's attacker model ("a link or deep link the user clicks", combined with "a cloned/fetched repository" providing the directory layout/symlinks needed to realize the containment bypass).

### Impact Explanation
If an attacker can get a victim to (a) have a repository directory whose real path is a prefix of another sensitive sibling path (e.g. a backup folder, an adjacent repo, or a symlink inside the repo that resolves to such a path), and (b) click a crafted deep link containing a `filepath` targeting that sibling, `resolveWithin` will incorrectly validate the escape and `shell.showItemInFolder` will reveal/operate on a file outside of the intended repository root — the exact "file... read outside the repo" class of impact called out as valid. Because `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` are the generic containment primitive exported from `app/src/lib/path.ts`, any other current or future caller that uses it to gate a write, execute, or read operation on an attacker-influenced relative path inherits the same bypass — this is a foundational, shared security boundary, not a one-off check.

### Likelihood Explanation
Likelihood is Medium: it requires the coincidence (or attacker-engineered condition, e.g. via a symlink placed inside a cloned repository) that a real path be a character-level prefix match of the intended root without a following separator. This is a realistic naming collision in practice (`repo` vs `repo-backup`, `repo` vs `repo.old`, `repo` vs `repo2`), and the attacker fully controls the `filepath` segment of the deep link, so exploitation only depends on the directory-name coincidence/symlink setup, not on any additional user action beyond clicking a link — matching the report's severity profile (an invariant that "silently" fails at a boundary, without needing local/admin access or already-present malware).

### Recommendation
Change the containment check to compare against the root plus a trailing path separator (or use `path.relative()` and reject results starting with `..` or being absolute):
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests mirroring the existing `path-test.ts` suite specifically for sibling-directory-name collisions (e.g. root `/tmp/foo`, resolved `/tmp/foo-evil/bar`) to lock in the fix, matching how the Vault team's fix closed the `>`-vs-`>=` gap.

### Proof of Concept
1. Suppose `repository.path` (root) resolves to `/Users/victim/Documents/GitHub/project`.
2. Elsewhere on disk (or via a symlink committed inside the cloned repo that a `realpath()` resolves to) there exists `/Users/victim/Documents/GitHub/project-secrets/credentials.txt`.
3. Attacker sends the victim a GitHub Desktop deep link such as `x-github-client://openRepo/<url>?filepath=../project-secrets/credentials.txt` (or a filepath through a symlink inside the repo pointing to that sibling).
4. `Dispatcher.openRepositoryFromUrl` calls `resolveWithin(repository.path, filepath)` [5](#0-4) .
5. Inside `_resolveWithin`, `resolve()` combined with the symlink's real path yields `realResolved = '/Users/victim/Documents/GitHub/project-secrets/credentials.txt'` and `realRoot = '/Users/victim/Documents/GitHub/project'`.
6. `realResolved.startsWith(realRoot)` evaluates `true` (string prefix match) even though `project-secrets` is not under `project`, so the function returns the resolved path instead of `null`.
7. `shell.showItemInFolder(resolved)` reveals the out-of-repo file to the attacker's chosen deep link target, defeating the "Prevented attempt to open path outside of the repository root" guard entirely.

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
