### Title
Cross-chain escrow release binds solver reward to `msg.sender`'s destination-chain address with no way to redirect it, risking permanent fund loss for non-EOA solvers - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`_fillCrossChain()` fills an order on the destination chain and dispatches a `RedeemEscrow` message back to the source chain that hard-codes the escrow beneficiary as `bytes32(uint256(uint160(msg.sender)))` — i.e., whatever address called `fillOrder` on the destination chain. [2](#0-1)  `FillOptions` provides no field to specify an alternate source-chain receiver. [1](#0-0)  When this message arrives on the source chain, `onAccept()`/`_withdraw()` sends the escrowed input tokens directly to that same address value on the source chain without any additional verification that the address is controlled there. [3](#0-2) 

### Finding Description
This is the local analog of the external report's core invariant break: the protocol assumes an address that is valid/controlled on one chain (the destination, where `fillOrder` is called) is also controlled by the same party on a different chain (the source, where the escrow payout lands), with no user-settable override.

The docs explicitly describe solvers as smart accounts using ERC-4337 + EIP-7702 + ERC-7821 batching (`SolverAccount`), which combine `gateway.select(...)` and `gateway.fillOrder(...)` into one UserOperation submitted through an ERC-4337 EntryPoint. In that flow, `msg.sender` inside `fillOrder` on the destination chain is the `SolverAccount` contract address, not necessarily the solver's raw EOA. The gateway then blindly reuses that exact address as the fund-receiving beneficiary on the source chain:

- `_fillCrossChain` sets `beneficiary: bytes32(uint256(uint160(msg.sender)))` in the `WithdrawalRequest` dispatched to `order.source`. [4](#0-3) 
- On the source chain, `onAccept()` authenticates only that the *sender module* (the registered IntentGateway instance) is correct — it never validates anything about the beneficiary itself. [5](#0-4) 
- `_withdraw()` then unconditionally transfers escrowed tokens to `address(uint160(uint256(body.beneficiary)))`. [3](#0-2) 

If the solver's on-chain identity at that address is not equivalently controlled on the source chain (e.g. it is a proxy/wallet contract deployed via `CREATE`/`CREATE2` with source-chain-specific deployment state, a delegatecall-based smart account not yet initialized on the source chain, or simply an address whose control differs cross-chain), the escrow payout is sent to an address the solver cannot access there. There is no `FillOptions.receiver`-style field, and no on-chain check that the destination-chain caller is an EOA (unlike the report's suggested mitigation of "allow cross-chain buy operations just for EOAs").

### Impact Explanation
This causes unauthorized/incorrect fund destination and potential permanent fund loss/lock for the exact class of solver the protocol's own documentation promotes (ERC-4337/EIP-7702 smart accounts), matching the bounty's "stealing or loss of funds" / "wrong beneficiary" categories. It is not merely a UX inconvenience — funds already left escrow and were sent irreversibly to an address the solver cannot control on the source chain, with no recovery path since `_filled[commitment]` is finalized and the order cannot be re-claimed.

### Likelihood Explanation
Medium: this requires a solver using a smart-contract account (which the protocol explicitly supports and documents as the intended pattern via `SolverAccount`) whose address on the source chain is not equivalently deployed/controlled — a realistic operational scenario for solvers running multi-chain infrastructure, but not automatically triggered for solvers using plain EOAs.

### Recommendation
Add an explicit receiver field to `FillOptions` (or to the `WithdrawalRequest`/fill call) that lets the solver designate the source-chain address that should receive the escrow release, decoupled from `msg.sender` on the destination chain. Alternatively, restrict cross-chain fills to EOAs only, mirroring the report's suggested mitigation, until an explicit-receiver mechanism is implemented.

### Proof of Concept
1. Solver deploys/operates a smart-contract wallet (`SolverAccount`) at address `S` on the destination chain via ERC-4337/EIP-7702, per the documented flow.
2. Solver calls `fillOrder(order, options)` on the destination chain; `msg.sender == S`.
3. `_fillCrossChain` builds and dispatches `WithdrawalRequest{beneficiary: bytes32(uint256(uint160(S))), ...}` to `order.source` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:140-155`).
4. On the source chain, `onAccept()` authenticates the sender module only (not the beneficiary) and calls `_withdraw()`, which transfers the escrowed input tokens to address `S` on the source chain (`evm/src/apps/intentsv2/IntentsBase.sol:390-409`).
5. If `S` on the source chain is an uninitialized/unowned address (e.g., the counterfactual smart-account address was never deployed there, or belongs to a different, unrelated entity due to differing deployment nonces/salts), the solver's payout is irretrievable — demonstrating loss of funds through the assumed cross-chain address equivalence.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
