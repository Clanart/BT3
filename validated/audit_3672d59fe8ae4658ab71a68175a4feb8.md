### Title
Malicious git remote can spoof `WWW-Authenticate: realm="GitHub"` to force Desktop into treating an attacker's server as a trusted GitHub Enterprise host, hijacking the browser-based OAuth flow - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
When Git needs credentials for an HTTPS remote, GitHub Desktop's credential-helper trampoline decides whether the remote is a "real" GitHub/GHE host or a generic host. One of the classification paths trusts the `WWW-Authenticate` header returned by the remote server itself: if it contains `realm="GitHub"`, the endpoint is unconditionally classified as `'enterprise'` [1](#0-0) . Because the remote server is exactly the attacker-controlled input in a clone/fetch scenario, an attacker can trivially make an arbitrary domain be treated as an "enterprise GitHub" endpoint, which causes Desktop to launch its enterprise sign-in / browser OAuth flow against that attacker domain, exchanging the app's `client_id`/`client_secret` and eventually binding whatever "account" the attacker's server returns as an authenticated Desktop account.

### Finding Description
`getEndpointKind` is used by the credential-helper handler to decide whether to show the generic-git-auth prompt or the full GitHub-style sign-in flow [2](#0-1) . Before doing any network probing, it inspects Git-forwarded `wwwauth[...]` credential fields (populated from the server's own `WWW-Authenticate` response header) and returns `'enterprise'` as soon as it sees `realm="GitHub"`, with no further verification of the actual host:

```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } ...
``` [3](#0-2) 

Since Git forwards whatever `WWW-Authenticate` header the remote HTTP server sends on a 401 challenge, any attacker running a git-over-HTTPS server fully controls this value. This lets the attacker force `getEndpointKind` to return `'enterprise'` for a domain that has nothing to do with GitHub.

Once classified as non-generic, and if the user has no existing account for that endpoint, `getCredential` routes straight into the sign-in UI with the attacker's endpoint:

```
const account = await ui.promptForGitHubSignIn(endpoint)
``` [4](#0-3) 

`promptForGitHubSignIn` then begins an "enterprise" sign-in session using the attacker-controlled `origin` and shows the standard sign-in popup:

```
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
``` [5](#0-4) 

When the user clicks "Sign in using your browser" (the expected/only action in that dialog) [6](#0-5) , `authenticateWithBrowser()` opens the OS browser to a URL built directly from the attacker's endpoint, embedding the real Desktop app `client_id` and a CSRF `state` value that is visible in that same URL:

```
shell.openExternal(getOAuthAuthorizationURL(endpoint, csrfToken))
``` [7](#0-6) 

Because the attacker's server is the destination of that navigation, it already knows `client_id`, `scope`, and the `state` CSRF token straight out of the URL — no phishing of the user is required. The attacker can immediately issue Desktop's own deep-link callback themselves:
`x-github-client://oauth?code=<attacker-code>&state=<state-read-from-url>`
which passes the CSRF check unchanged, since the check only verifies that the `state` in the callback matches the one that was generated for this flow — both of which the attacker already possesses:

```
if (this.state.oauthState.state !== action.state) { ...return }
const { endpoint } = this.state
const token = await requestOAuthToken(endpoint, action.code)
``` [8](#0-7) 

`requestOAuthToken` and the subsequent `fetchUser` call both target `endpoint`, i.e. the attacker's own server:

```
export async function requestOAuthToken(endpoint: string, code: string) {
  const urlBase = getHTMLURL(endpoint)
  const response = await request(urlBase, null, 'POST', 'login/oauth/access_token',
    { client_id: ClientID, client_secret: ClientSecret, code })
  ...
}
``` [9](#0-8) 

The attacker's server thus (a) receives Desktop's `client_id`/`client_secret` in the POST body, and (b) can return any access token and any `fetchUser` response it likes, which then gets bound into Desktop as a legitimate, authenticated Account via `onAuthCompleted(account)` [10](#0-9) .

### Impact Explanation
- Unauthorized OAuth/account binding: an attacker fully controls both ends of the OAuth exchange (authorize page and token/user endpoints), letting them make Desktop "sign in" as an arbitrary, attacker-fabricated identity/token that the app will subsequently treat as a real authenticated account for that endpoint.
- Credential/secret exfiltration: Desktop's OAuth `client_id`/`client_secret` are POSTed to the attacker's server as part of the token exchange, since the request target is derived from the attacker-controlled `endpoint`.
- The whole chain is triggered purely by cloning/fetching from, or adding, a malicious HTTPS git remote that returns a crafted `WWW-Authenticate` header — an entirely git-protocol-level action, no local access, no leaked credentials, and no unnatural user steps (the user is only asked to click the normal "Sign in using your browser" button that Desktop shows for any private-repo authentication prompt).

### Likelihood Explanation
Any server operator can trivially set a custom `WWW-Authenticate: Basic realm="GitHub"` header on 401 responses for their git-over-HTTPS remote; this requires no special server software and works with any generic git HTTP backend that allows custom headers. The only user action required is attempting to clone/fetch a repository requiring auth and clicking through the sign-in prompt Desktop shows them, which is standard behavior for connecting to any private/enterprise remote.

### Recommendation
Do not classify an endpoint as `'enterprise'` (or otherwise privileged) purely from a server-supplied `WWW-Authenticate` realm string. At minimum, before initiating the enterprise sign-in/browser OAuth flow, independently verify the endpoint is a real GitHub/GHE instance (e.g., via the existing `isGitHubHost` API probe against a hardcoded well-known GitHub API path/response signature) rather than trusting attacker-controlled header text, and surface the actual endpoint hostname prominently in the sign-in dialog/browser prompt so users can recognize an unexpected domain before proceeding.

### Proof of Concept
1. Stand up an HTTPS git server (e.g., a minimal git-http-backend) at `https://evil.example.com/repo.git` that responds to unauthenticated requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Also host a fake OAuth authorize page at `/login/oauth/authorize` and a fake `/login/oauth/access_token` + `/user` endpoint on `evil.example.com`.
3. In GitHub Desktop, clone/add `https://evil.example.com/repo.git` as a remote and trigger a fetch/clone requiring credentials.
4. `getEndpointKind` sees the spoofed header and returns `'enterprise'` [3](#0-2) ; Desktop shows the Sign-In popup with `credentialHelperUrl: 'https://evil.example.com'` [11](#0-10) .
5. User clicks "Sign in using your browser"; Desktop opens `https://evil.example.com/login/oauth/authorize?client_id=...&state=...` [7](#0-6) .
6. The attacker's page immediately redirects to `x-github-client://oauth?code=attacker123&state=<state-from-query>`.
7. Desktop's `resolveOAuthRequest` accepts it (state matches) and POSTs `client_id`/`client_secret`/`code` to `https://evil.example.com/login/oauth/access_token` [8](#0-7) [9](#0-8) ; the attacker's fake token/account response gets bound into Desktop as a signed-in account.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
