## Title
Main-process IPC handlers bypass the `isTrustedIPCSender` sender-verification gate - (File: `app/src/main-process/main.ts`)

## Summary
GitHub Desktop implements a dedicated trust boundary for main-process IPC per Electron's security guidance: `app/src/main-process/trusted-ipc-sender.ts` tracks trusted `WebContents` IDs, and the wrapped `on`/`handle` helpers in `app/src/main-process/ipc-main.ts` reject any message that doesn't come from a trusted sender. `app/src/main-process/main.ts`, however, registers dozens of privileged handlers directly on Electron's raw `ipcMain` instead of using these wrapped helpers, so those handlers never call `isTrustedIPCSender` and accept messages from any `WebContents` in the process.

## Finding Description
The security-sensitive pattern is defined once: [1](#0-0) 

and enforced only for callers that go through the wrapper: [2](#0-1) 

`app/src/main-process/main.ts` imports `ipcMain` directly and registers over 50 channels with `ipcMain.on`/`ipcMain.handle`, none of which pass through `safeListener`/`isTrustedIPCSender`. Examples include file-system and shell-level operations: [3](#0-2) 

`move-to-trash` invokes `shell.trashItem(path)` and `unsafe-open-directory` invokes `UNSAFE_openDirectory(path)`, whose own doc comment states it "should never be used with user-provided paths" because no verification is performed: [4](#0-3) 

`open-external` similarly calls `shell.openExternal(path)` with no allow-list and no sender check: [5](#0-4) 

The broken invariant is: *"every privileged main-process IPC handler must verify `isTrustedIPCSender` before acting,"* which the codebase itself established via `trusted-ipc-sender.ts` as the recommended Electron mitigation. `main.ts`'s raw registrations violate that invariant for the majority of its handlers, so any `WebContents` capable of reaching `ipcMain` — for example a compromised or attacker-influenced secondary window/webview created for sign-in, avatar loading, or other GitHub-hosted content — is treated identically to the trusted main renderer.

## Impact Explanation
If any non-main `WebContents` in the process gains the ability to send IPC (e.g., through a preload/context leak in a secondary window, or a future renderer that loads externally-influenced content), it can trigger file deletion via `move-to-trash`, open arbitrary local directories/paths via `unsafe-open-directory` (a function explicitly documented as unsafe for untrusted paths), or launch arbitrary external URLs/protocol handlers via `open-external`. These map to the report's core bug class — a caller that should be restricted (an authorized/owner-only action) is instead reachable by an unprivileged/attacker-influenced caller — resulting in file write/execution effects outside the intended scope, matching the program's "IPC escape" impact category.

## Likelihood Explanation
Exploitability depends on the existence of a reachable untrusted `WebContents` in the running process (e.g., a webview/BrowserWindow that loads externally-controlled or repo-derived content with IPC access). This condition could not be fully confirmed from the indexed code — I could not verify from available files whether any secondary window (sign-in webview, crash-window, etc.) exposes the same preload/IPC bridge to non-first-party content. This is the deciding factor for exploitability, and the index may not contain every window/preload configuration; a Devin session with full repo access would be needed to confirm whether an actual untrusted sender exists that can reach these channels today.

## Recommendation
Route all privileged channels in `app/src/main-process/main.ts` (especially `move-to-trash`, `unsafe-open-directory`, `open-external`, `show-item-in-folder`, `resolve-proxy`, and the dialog/window-management handlers) through the wrapped `on`/`handle` exported by `app/src/main-process/ipc-main.ts` so `isTrustedIPCSender` is uniformly enforced, closing the gap between the documented defense and its actual coverage.

## Proof of Concept
Not independently reproducible from the indexed code alone, since confirming exploitability requires identifying a concrete untrusted `WebContents` that can call these channels (not found via the available index). Conceptually: any `WebContents` object obtained in the main process (not registered via `addTrustedIPCSender`) can call `ipcRenderer.invoke('move-to-trash', '<path>')` or `ipcRenderer.send('unsafe-open-directory', '<path>')` and have it executed, because `main.ts`'s registrations at [6](#0-5)  never call `isTrustedIPCSender`, unlike the channels wrapped in `app/src/main-process/ipc-main.ts`.

```typescript
import { WebContents } from 'electron'

// WebContents id of trusted senders of IPC messages. This is used to verify
// that only IPC messages sent from trusted senders are handled, as recommended
// by the Electron security documentation:
// https://github.com/electron/electron/blob/main/docs/tutorial/security.md#17-validate-the-sender-of-all-ipc-messages
const trustedSenders = new Set<number>()

/** Adds a WebContents instance to the set of trusted IPC senders. */
export const addTrustedIPCSender = (wc: WebContents) => {
  trustedSenders.add(wc.id)
  wc.on('destroyed', () => trustedSenders.delete(wc.id))
}

/** Returns true if the given WebContents is a trusted sender of IPC messages. */
export const isTrustedIPCSender = (wc: WebContents) => trustedSenders.has(wc.id)
```

```typescript
function safeListener<E extends IpcMainEvent | IpcMainInvokeEvent, R>(
  listener: (event: E, ...a: any) => R
) {
  return (event: E, ...args: any) => {
    if (!isTrustedIPCSender(event.sender)) {
      log.error(
        `IPC message received from invalid sender: ${event.senderFrame?.url}`
      )
      return
    }

    return listener(event, ...args)
  }
}
```
