## Analysis

The Popcorn bug is fundamentally about a **stateful checkpoint variable** (`feesUpdatedAt`) that is read to compute a delta, but which is not scoped correctly to the operation being accounted for — it can be silently mutated/reset by unrelated calls (including reentrant/nested ones), causing the delta computation to be wrong and producing incorrect (and exploitable) accounting.

The closest reachable Cosmos EVM analog is the `BalanceHandler.prevEventsLen` checkpoint used to reconcile native `x/bank` events with the EVM `StateDB` balance mirror during precompile execution. This checkpoint plays exactly the same structural role as `feesUpdatedAt`: it marks "the last position observed," and any subsequent processing computes a diff from that checkpoint forward. The codebase's own regression test proves this checkpoint can be desynchronized by nested/recursive precompile invocations.

### Title
Shared/overwritten `BalanceHandler.prevEventsLen` checkpoint during recursive precompile calls desynchronizes EVM StateDB balances from `x/bank` ledger - (File: precompiles/common/balance_handler.go)

### Summary
`BalanceHandler` records an event-log checkpoint (`prevEventsLen`) in `BeforeBalanceChange`, then in `AfterBalanceChange` replays only the bank events emitted after that checkpoint to apply corresponding `StateDB.AddBalance`/`SubBalance` calls, keeping the EVM's balance view consistent with the native `x/bank` ledger. If a single `BalanceHandler` instance is reused/shared across nested or recursive precompile invocations within one EVM transaction, the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, corrupting the checkpoint the outer call relies on — analogous to how `feesUpdatedAt` in the Popcorn report could be reset by an unrelated call before the intended accrual computation completed.

### Finding Description
`BalanceHandler.BeforeBalanceChange` sets `prevEventsLen = len(ctx.EventManager().Events())` [1](#0-0) , and `AfterBalanceChange` only processes `events[bh.prevEventsLen:]` to update `StateDB` balances for `CoinSpent`/`CoinReceived`/fractional-balance-change events [2](#0-1) .

In the standard/production precompile call path, `Precompile.runNativeAction` creates a **fresh** `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()` [3](#0-2) , which normally scopes the checkpoint correctly per call. However, the repository's own integration test (`BalanceHandlerTestSuite`) demonstrates that when a `BalanceHandler` instance is instead held/reused across recursive precompile invocations (as in the test's `debug` precompile, which calls `p.GetBalanceHandler()` — a persistent handler stored on the precompile — rather than obtaining a new one per call) [4](#0-3) , a nested/recursive call's `BeforeBalanceChange` overwrites `prevEventsLen`, so the outer call's `AfterBalanceChange` processes the wrong window of events. The test explicitly documents this as: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [5](#0-4) 

Because this diff-based reconciliation is the mechanism that keeps the authoritative `x/bank` coin ledger and the EVM `StateDB` balance in sync for every stateful precompile (bank, erc20, staking, distribution, gov, ics20, slashing all wire up a `BalanceHandlerFactory`) [6](#0-5) , an overwritten checkpoint causes either double-application of an inner call's already-applied balance delta to `StateDB`, or a lost delta window, producing a `StateDB` balance that diverges from the true `x/bank` balance.

### Impact Explanation
A `StateDB`/`x/bank` balance desync is a direct accounting-corruption issue: `StateDB.Commit()` persists the (possibly inflated or deflated) EVM-side balance back into the account state via `commitWithCtx`/`SetAccount` [7](#0-6) , and `Keeper.SetBalance` reconciles that against the bank balance by minting or burning the delta [8](#0-7) . If the EVM-side balance is wrongly inflated due to a double-counted event window, this reconciliation step will **mint** native coins to make the bank balance match the corrupted (too-high) `StateDB` balance — an unauthorized creation of spendable value. Conversely, an under-counted window can cause coins to be silently burned/lost. This matches the allowed Critical impact of "unauthorized minting... or irreversible accounting corruption of spendable user value across native balances, EVM balances."

### Likelihood Explanation
Likelihood depends on whether any precompile in the shipped set (not just the `debug` test precompile) constructs its `BalanceHandler` once and reuses it across nested/reentrant calls rather than obtaining a fresh instance per call through `RunNativeAction`. All production precompiles found (`distribution`, `erc20`, `gov`, `ics20`, `slashing`, `staking`) reference `BalanceHandlerFactory` exactly once in their source, which is consistent with the safe pattern (factory stored, fresh handler created per call in `runNativeAction`) — but I was not able to fully verify, within the remaining tool budget, that no code path bypasses `RunNativeAction`/`runNativeAction` (e.g., a `Run()` override or a precompile that calls another precompile re-entrantly within the same EVM call frame, causing `runNativeAction` to be invoked twice with a shared cached `BalanceHandler`). This uncertainty should be resolved before treating this as a confirmed production-exploitable finding.

### Recommendation
- Verify that every stateful precompile in production strictly uses `RunNativeAction`/`runNativeAction`, which creates a new `BalanceHandler` per invocation, and audit for any precompile implementation that stores/reuses a `BalanceHandler` as instance state across calls (mirroring the pattern reproduced by the `debug` test precompile).
- Make `BalanceHandler` re-entrancy-safe regardless of call pattern: track checkpoints as a stack (push on `BeforeBalanceChange`, pop on `AfterBalanceChange`) instead of a single overwritable `prevEventsLen` field, so nested precompile calls cannot clobber an outer call's checkpoint.
- Add an invariant check after every `StateDB.Commit()` / `SetBalance` reconciliation comparing total precompile-affected account balances against the sum of `x/bank` events processed, failing the transaction rather than silently minting/burning on mismatch.
- Extend `BalanceHandlerTestSuite`-style tests to cover all production precompiles handling nested calls (e.g., ICS20 precompile calling back into ERC20 precompile, or staking precompile invoked from within a distribution callback) to confirm the fresh-handler-per-call invariant holds end-to-end.

### Proof of Concept
The repository already contains a proof of concept demonstrating the root-cause mechanism: `evmd/tests/integration/balance_handler/balance_handler_test.go`'s `TestRecursivePrecompileCallsWithDebugPrecompile` deploys a caller contract that recursively invokes the `debug` precompile (which reuses a single `BalanceHandler` via `p.GetBalanceHandler()`), triggering repeated `BeforeBalanceChange`/`AfterBalanceChange` cycles that overwrite `prevEventsLen` mid-recursion [9](#0-8) . A concrete exploit against a production precompile would require identifying (not yet confirmed here) a shipped precompile that similarly persists a `BalanceHandler` instance across a reentrant call chain within a single EVM transaction, then structuring a contract that triggers nested precompile calls (e.g., precompile A calling into precompile B which calls back into A) to reproduce the same checkpoint-overwrite and observe `StateDB` balance diverge from `x/bank` balance after `Commit()`.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)

// commitWithCtx writes the dirty states to keeper
// using the provided context
func (s *StateDB) commitWithCtx(ctx sdk.Context) error {
	for _, addr := range s.journal.sortedDirties() {
		obj := s.stateObjects[addr]
		if obj.selfDestructed {
			if err := s.keeper.DeleteAccount(ctx, obj.Address()); err != nil {
				return errorsmod.Wrapf(err, "failed to delete account %s", obj.Address())
			}
		} else {
			if obj.code != nil && obj.dirtyCode {
				if len(obj.code) == 0 {
					s.keeper.DeleteCode(ctx, obj.CodeHash())
				} else {
					s.keeper.SetCode(ctx, obj.CodeHash(), obj.code)
				}
			}
			if err := s.keeper.SetAccount(ctx, obj.Address(), obj.account); err != nil {
				return errorsmod.Wrap(err, "failed to set account")
			}

			for _, key := range obj.dirtyStorage.SortedKeys() {
				valueBytes := obj.dirtyStorage[key].Bytes()
				if len(valueBytes) == 0 {
					s.keeper.DeleteState(ctx, obj.Address(), key)
				} else {
					s.keeper.SetState(ctx, obj.Address(), key, valueBytes)
				}
			}
		}
	}
	return nil

// SetBalance update account's balance, compare with current balance first, then decide to mint or burn.
func (k *Keeper) SetBalance(ctx sdk.Context, addr common.Address, amount *uint256.Int) error {
	if amount == nil {
		return nil
	}
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	coin := k.bankWrapper.SpendableCoin(ctx, cosmosAddr, types.GetEVMCoinDenom())

	balance := coin.Amount.BigInt()
	delta := new(big.Int).Sub(amount.ToBig(), balance)
	switch delta.Sign() {
	case 1:
		// mint
		if err := k.bankWrapper.MintAmountToAccount(ctx, cosmosAddr, delta); err != nil {
			return err
		}
	case -1:
		// burn
		if err := k.bankWrapper.BurnAmountFromAccount(ctx, cosmosAddr, new(big.Int).Neg(delta)); err != nil {
			return err
		}
	default:
		// not changed
	}
	return nil
}
