### Title
Uninitialized-repo History crash via unguarded `CommitIdentity.parseIdentity` on attacker-crafted commit author date - ([File: app/src/models/commit-identity.ts])

### Summary
`CommitIdentity.parseIdentity()` parses the raw `%an <%ae> %ad` / `%cn <%ce> %cd` identity strings that `git log --date=raw` produces for every commit in a repository's history, including commits from a cloned or fetched remote that the local user does not control.

### Finding Description
The parser extracts the raw Unix timestamp with `parseInt(m[3], 10)` (where `m[3]` is matched by the unbounded `\d+` group), multiplies by 1000, and constructs a `Date`: [1](#0-0) 
A crafted commit whose author/committer date field contains a very large digit string (e.g., dozens of digits) causes `parseInt(...) * 1000` to exceed `Number.MAX_SAFE_INTEGER` or produce `Infinity`, which makes `new Date(...)` return an `Invalid Date`. The function does check for this via `isNaN(date.valueOf())`, but instead of failing gracefully it **throws**: [2](#0-1) 
This mirrors the structure of the reported libp2p bug: the original insertion path for a similarly attacker-controlled numeric field (commit author timestamps used elsewhere, e.g. `getBranchCheckouts` reflog parsing) is guarded in some call sites but not uniformly across all paths that consume the same untrusted data. Specifically, `getAuthorIdentity()` in `app/src/lib/git/var.ts` wraps the call in `try/catch` and safely returns `null` on failure: [3](#0-2) 
But `getCommits()` in `app/src/lib/git/log.ts`, which is the primary function used to populate commit history from any repository (including freshly cloned ones), calls `CommitIdentity.parseIdentity()` directly with no surrounding try/catch: [4](#0-3) 

### Impact Explanation
If the thrown error is not caught further up the call chain (e.g., in `git-store.ts`), it would propagate as an unhandled rejection/exception during history loading, disrupting commit-history rendering for the affected repository — a remotely-triggerable denial-of-service condition reachable simply by cloning or fetching a maliciously crafted repository/commit. I was not able to fully verify with the available searches whether the calling code in `git-store.ts` catches this exception generically, which would reduce the severity to a non-issue (silently dropped commit) rather than a crash.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to clone/fetch a repository containing at least one commit with a maliciously long numeric date field, which is easy for an attacker who controls the repository content (e.g., via `git commit --date`, or by fabricating a raw commit object). No user interaction beyond the normal clone/fetch/open-history flow is required.

### Recommendation
1. In `CommitIdentity.parseIdentity()`, avoid throwing for malformed/oversized dates; instead clamp or fall back to a default epoch value and log a warning, consistent with how other parts of the codebase handle malformed git metadata defensively.
2. Audit all callers of `CommitIdentity.parseIdentity()` (`log.ts`, `var.ts`) to ensure consistent error handling — either all callers should tolerate a thrown parse error, or the function itself should never throw for attacker-reachable inputs.
3. Add a regression test with a crafted commit containing an oversized author-date numeric field to confirm history loading does not crash.
