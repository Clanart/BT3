### Title
`consensus_deserialize` accepts non-canonical `version` bytes that re-serialize differently, breaking `serialize(deserialize(b)) == b` - (`stacks-codec/src/transaction.rs`)

### Summary
`StacksTransaction::consensus_deserialize_with_len` decodes the leading version byte using a bitmask (`version_u8 & 0x80`) instead of checking for exact canonical values, so any byte in `0x01..=0x7F` is silently accepted as `TransactionVersion::Mainnet` and any byte in `0x81..=0xFF` is accepted as `TransactionVersion::Testnet`. `consensus_serialize` always re-emits the canonical byte (`0x00` for Mainnet, `0x80` for Testnet), so a non-canonical wire encoding accepted by the node does not round-trip to the bytes the attacker actually sent.

### Finding Description
The broken equality is: `consensus_serialize(consensus_deserialize(b)) == b` for every `b` accepted by `consensus_deserialize`.

    TransactionVersion::Mainnet

Serialize path: [2](#0-1) 
```
fn consensus_serialize<W: Write>(&self, fd: &mut W) -> Result<(), codec_error> {
    write_next(fd, &(self.version as u8))?;
```

`TransactionVersion::Mainnet` and `TransactionVersion::Testnet` have fixed discriminants (`0x00` and `0x80` respectively, per the standard Stacks wire convention reflected in the mask check above). Because the deserializer only inspects bit 7 of `version_u8` and discards the other 7 bits, any of the 254 non-canonical byte values (e.g. `0x01`, `0x7F`, `0x81`, `0xFF`) parses successfully into the same `StacksTransaction { version: Mainnet | Testnet, .. }` struct as the canonical `0x00`/`0x80` byte. Re-serializing that struct always emits the canonical byte, not the one the attacker sent.

Exploit flow: An attacker signs a transaction, then flips the low 7 bits of the version byte (a byte that is not covered by fee/nonce/post-condition checks and is outside any signed hash's exact-value constraint at the codec layer — the auth signature itself does cover this byte via the transaction sighash, so *this specific byte cannot be freely mutated post-signature without invalidating the signature*). However, the attacker can pick the non-canonical version byte *before* signing (they fully control the bytes they sign), producing a transaction whose signature is valid and whose wire bytes contain `version_u8 = 0x01` instead of `0x00`. The node's RPC/mempool accepts this transaction (`consensus_deserialize` succeeds, signature verifies since it's computed over whatever bytes were actually signed by the attacker's own signer), computes `txid()` from the deserialized (canonicalized) struct, and — depending on whether any component stores/re-transmits the *raw* bytes versus the *canonicalized* bytes — a receiving peer that computes a hash over the raw relayed bytes (rather than calling `txid()` on the reconstructed struct) would get a different digest than the txid used for mempool bookkeeping.

### Impact Explanation
This falls under "txid/sighash over different bytes than transmitted" (High). The concrete effect: the same logical transaction has (at least) two distinct valid wire encodings that are treated as identical by `consensus_deserialize`/`txid()`, but the canonicalized re-serialization differs from what was submitted. This can cause relay/dedup logic that compares raw bytes (or hashes of raw bytes) instead of consistently using the `txid()` accessor to diverge from nodes that re-canonicalize before storing/relaying — i.e., mempool-vs-relay admissibility or identity confusion. It does not, by itself, allow moving funds outside post-conditions or forging another party's signature (the version byte is covered by the signed digest, so this is not a signature-stripping attack), and is repeatable per crafted transaction.

### Likelihood Explanation
Low cost, fully attacker-controlled: the attacker just needs to sign a transaction whose serialized `version` byte is a non-canonical value in `0x01-0x7F` or `0x81-0xFF` before submitting. No special account state or epoch gating is required, since the check in `consensus_deserialize_with_len` applies universally. Exploitability of the *actual network-visible impact*, however, depends on whether any component in the relay/mempool path uses raw-byte hashing instead of `StacksTransaction::txid()` consistently — I could not fully confirm within this repo whether such a divergent raw-byte-hash consumer exists on the mempool/RPC/relay path (this would require tracing `mempool.rs`, `net/p2p.rs`, and RPC handlers for any place that hashes the raw POST body instead of the canonicalized transaction). This remains unverified and should be checked before treating this as a confirmed, actionable severity.

### Recommendation
In `consensus_deserialize_with_len`, reject any `version_u8` that isn't exactly `TransactionVersion::Mainnet as u8` or `TransactionVersion::Testnet as u8`, instead of masking with `0x80`.

### Proof of Concept
```rust
#[test]
fn version_byte_does_not_roundtrip() {
    let auth = TransactionAuth::from_p2pkh(&StacksPrivateKey::random()).unwrap();
    let mut tx = StacksTransaction::new(
        TransactionVersion::Mainnet,
        auth,
        TransactionPayload::TokenTransfer(
            StacksAddress::new(22, Hash160([0; 20])).unwrap().into(),
            1,
            TokenTransferMemo([0u8; 34]),
        ),
    );
    let mut bytes = vec![];
    tx.consensus_serialize(&mut bytes).unwrap();
    // Flip low bits of the version byte to a non-canonical mainnet-lookalike value.
    bytes[0] = 0x01;

    let decoded = StacksTransaction::consensus_deserialize(&mut &bytes[..]).unwrap();
    let mut re_serialized = vec![];
    decoded.consensus_serialize(&mut re_serialized).unwrap();

    // FAILS: re_serialized[0] == 0x00 (canonical Mainnet) != bytes[0] == 0x01
    assert_eq!(re_serialized, bytes, "serialize(deserialize(b)) != b");
}
```
