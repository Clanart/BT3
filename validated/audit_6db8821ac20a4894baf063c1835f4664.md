## Analysis

The QuailFinance bug is a single-invariant class: **an action required to unlock funds depends on one party's willingness to act, there's no timeout, and if that action never happens, the funds are stuck forever.** The strongest local analog in Hyperbridge is the relayer fee withdrawal flow in `pallet-ismp-relayer`.

### Title
Relayer fees are zeroed before delivery is confirmed, and the withdrawal dispatch can never time out or be reclaimed — ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` zeroes a relayer's accumulated `Fees` balance immediately after dispatching a cross-chain `DispatchPost` instructing the destination chain's host manager to pay out the funds. The dispatched request is created with `timeout: 0` (never times out) and `FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }` (zero fee, zero payer), meaning no relayer has an economic incentive to actually deliver it. If it is never delivered, the relayer's fee balance is permanently lost with no recovery path — mirroring the `potCreator`/`rotateLiquidity()` pattern where a required action that isn't guaranteed to happen locks funds forever with no timeout-based escape hatch.

### Finding Description
`withdraw()` performs, in order:
1. Increments `Nonce` [1](#0-0) 
2. Builds a `DispatchPost` with `timeout: 0` targeting the destination `host_manager`/`HYPERBRIDGE_MODULE_ID`, and dispatches it with zero fee/payer metadata [2](#0-1) 
3. Immediately zeroes `Fees::<T>` for that relayer/chain, treating the dispatch call succeeding (i.e., the request commitment being recorded) as equivalent to the funds having been paid out [3](#0-2) 

`dispatch_request` succeeding only means the outbound request commitment was recorded on Hyperbridge — it says nothing about whether any relayer will ever deliver it to the destination chain. Because `timeout: 0` is used, the request can never time out, so there is no `on_timeout` path that could restore the `Fees` balance if delivery never happens. And because this system-originated dispatch carries a zero fee/zero payer, there is no economic incentive for any relayer to deliver it — a gap the project's own documentation explicitly identifies: [4](#0-3)  This same file lists `modules/pallets/relayer/src/lib.rs:638`'s withdrawal path by name as one of the affected zero-fee, zero-payer dispatch sites [5](#0-4) .

The public documentation for the relayer withdrawal flow confirms this design: "This request will not timeout, allowing it to be submitted to the destination chain at any time." [6](#0-5)  — i.e., the never-timing-out property is intentional, but it removes any protocol-level guarantee that delivery ever completes, and the balance has already been debited from `Fees` before delivery is confirmed.

### Impact Explanation
This is a direct loss-of-funds path: a relayer's legitimately earned, accumulated protocol fees (`Fees::<T>`) are debited to zero at dispatch time, not at confirmed-delivery time. If the outbound request is never picked up by any relayer (there is no fee incentive attached to it, and altruism is the only thing keeping such system messages flowing, per the project's own tracking doc), the funds are permanently unrecoverable — the relayer cannot re-withdraw (balance is already zero), and there is no timeout mechanism to trigger a refund back into `Fees`.

### Likelihood Explanation
This does not require a malicious actor, a compromised relayer, or governance error — it is a straightforward consequence of the zero-fee/zero-payer, zero-timeout design applied to a fund-disbursing dispatch. Any relayer who calls `withdraw()` when no other relayer happens to deliver the resulting request is exposed. This is exactly analogous to the QuailFinance case: a required action (delivery, or `rotateLiquidity()`) that depends on some other party's discretionary behavior, with no timeout to fall back on, permanently locking already-committed funds.

### Recommendation
Do not zero `Fees` until delivery is confirmed (e.g., mirror the source-chain deduction/destination-credit two-phase pattern used elsewhere in ISMP, or restore the balance via an `on_timeout` handler). If a non-zero timeout cannot be attached to this dispatch, retain the balance and instead record a "pending withdrawal" that can be retried or cancelled/reclaimed after some duration if delivery never lands — consistent with the recommendation in the QuailFinance report of introducing a time bound after which participants can reclaim funds rather than remain permanently dependent on an external actor's action. Adopting the `outbound-request-incentivization` reward mechanism the repo is already tracking would also reduce the likelihood of non-delivery, but does not by itself fix the "zero before confirmed" ordering bug.

### Proof of Concept
1. Relayer accumulates fees via `accumulate_fees`, then calls `withdraw()` for `dest_chain`.
2. `withdraw()` dispatches a `DispatchPost` with `timeout: 0`, `fee: 0`, `payer: 0` to the destination host manager, then immediately zeroes `Fees::<T>::get(dest_chain, address)`.
3. No relayer has economic incentive to carry this specific request to the destination (confirmed by `docs/outbound-request-incentivization.md`'s description of the exact same code path).
4. The request is never delivered. Because `timeout: 0`, it can never time out, so no compensating `on_timeout` credit-back logic can ever run.
5. The relayer's fee balance, already reduced to zero in step 2, is permanently unrecoverable — the funds are effectively locked/lost analogous to `QuailFinance`'s `rotateLiquidity()` dependency on `potCreator`.

A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer.
