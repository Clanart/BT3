### Title
Quadratic interpolation loop in `ThresholdKeys::read` enables CPU-exhaustion DoS from a small attacker-controlled blob - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes the multisig parameters `t` and `n` directly from untrusted bytes, then calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` for each of the participants `1..=t`. Under `Interpolation::Lagrange`, `interpolation_factor` is O(t) per participant, making group-key derivation O(t²) scalar operations plus O(t) point multiplications — a ~2.1 MB input declaring `t = n = 65535` forces billions of field operations, matching the "hang or frequently repeatable crash" DoS class of CVE-2020-2923.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` as raw `u16`s from the reader and then reads `n` verification shares, with no cap beyond `u16::MAX` [1](#0-0) . It passes these to `ThresholdKeys::new` [2](#0-1) .

`ThresholdKeys::new` validates only that `t <= n`, `i <= n`, and the share count matches `n`; `ThresholdParams::new` accepts any `t = n` up to 65535 [3](#0-2) . It then derives `group_key` as `sum(verification_shares[i] * interpolation_factor(i, 1..=t))` [4](#0-3) .

With `Interpolation::Lagrange`, `interpolation_factor` iterates over every participant in `included`, performing a scalar multiply per element [5](#0-4) . For `t = 65535` that is ~4.3 billion scalar multiplications plus 65535 scalar-point multiplications, all triggered before any signature/proof validity is checked — a pure CPU/availability cost fully determined by two attacker-chosen bytes.

### Impact Explanation
Any code path that feeds attacker-supplied bytes to `ThresholdKeys::read` (e.g., a keys blob relayed between validators/processors, or deserialized from an untrusted store/peer message) lets an unprivileged sender pin a core for an effectively unbounded duration. The MySQL analog is direct: a small, cheap-to-produce input forces disproportionate computational work, yielding a complete hang of the victim's processing (threshold operations, signing setup, or any deserialization-driven pipeline). No secret is needed; the input is entirely public bytes.

### Likelihood Explanation
Requires a reachable `ThresholdKeys::read` on bytes the attacker can supply — the prompt-scoped sink list explicitly includes `ThresholdKeys::read` as an untrusted-bytes entry point, so the exposure exists wherever serialized key material crosses a trust boundary. The cost asymmetry (~2 MB input → ~10⁹ ops) makes this a practical DoS even once per invocation; no malformed-curve, collusion, or validator-privilege assumptions are needed. Rated Medium, mirroring the CVE's availability-only, network-reachable CVSS 4.9 profile.

### Recommendation
Cap `t`/`n` in `ThresholdKeys::read` to the protocol's real maximum validator-set size (e.g., `MAX_KEY_SHARES_PER_SET`) before performing any interpolation, and/or compute `group_key` with a linear-cost combination (precompute the Lagrange denominator products once, or reuse the constant-interpolation form) so deserialization cost is linear in input size.

buf.extend(65535u16.to_le_bytes());

// Lagrange interpolation
buf.push(1);
// secret share
buf.extend(C::F::ONE.to_repr().as_ref());
// n verification shares = identity points (must still be valid encodings)
for _ in 0 .. 65535 { buf.extend(C::G::generator().to_bytes().as_ref()); }
// ~2.1 MB of input -> O(65535^2) scalar muls in ThresholdKeys::new
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
