### Title
Division-before-multiplication truncation in `compute_royalty_amount` underpays NFT creator royalties on offer settlement - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount`, used by `NFTWallet.make_nft1_offer` to compute the royalty coin amount owed to NFT creators when an offer is created, performs integer division before multiplication, truncating the result more than necessary. This is the same arithmetic-ordering bug class flagged in the referenced Asymmetry Finance mitigation review (`(a/b)*c` truncates more than `a*c/b`), applied here to royalty payout computation instead of slippage `minOut`.

### Finding Description
`compute_royalty_amount` computes:
```python
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
``` [1](#0-0) 

This performs `(a // b) * c // d` where `a = abs(offered_amount)`, `b = royalty_split`, `c = percentage`, `d = MAX_ROYALTY_BASIS_POINTS (10000)`. Mathematically the correct (maximum-precision) computation is `a * c // (b * d)`, and even the report's less-aggressive fix `(a // b) * c // d` vs `a * c // b // d` shows that division should be deferred as long as possible. Doing `a // b` first discards up to `b - 1` mojos before the multiplication even happens, and then the subsequent `* percentage // MAX_ROYALTY_BASIS_POINTS` discards additional precision on the already-truncated value — compounding the loss described as case (1) in the referenced report (`(a/b)*c <= a*c/b`).

This function is invoked in the offer-construction pipeline, once per required royalty asset, whenever an offer includes an NFT with a royalty-enabled ownership layer and multiple royalty-eligible NFTs are being requested/offered together (`royalty_split` = count of same-side royalty NFTs, i.e. `request_side_royalty_split`):
```python
extra_royalty_amount = compute_royalty_amount(amount, request_side_royalty_split, percentage)
payment_list.append((launcher_id, CreateCoin(address, extra_royalty_amount, [address])))
``` [2](#0-1) 

The royalty payment amount produced here is baked directly into the `CreateCoin` condition placed in the offer's spend bundle (via `royalty_payments`), i.e., it directly determines the mojos actually paid to the royalty address on-chain — it is not independently re-derived or checked by CLVM against a higher-precision reference, so any truncation loss here is a permanent, unrecoverable reduction of the amount paid to the NFT creator/royalty address, silently accepted by the counterparty who did not initiate the offer.

### Impact Explanation
Any wallet user (maker) constructing an NFT offer with `create_offer_for_ids`/`make_nft1_offer` controls the values of `offered_amount` and, indirectly via which/how many royalty-bearing NFTs are grouped in the same offer, the `royalty_split` divisor. A larger `royalty_split` combined with a modest `percentage` increases the fraction of the true intended royalty that is discarded by the first `//`. This causes systematic underpayment (theft, in effect) of the royalty owed to NFT creators relative to what the sale price and royalty percentage entitle them to — the taker unknowingly accepts an offer whose embedded royalty payout is lower than the specification/percentage implies. Because the truncated royalty amount is committed directly as a `CreateCoin` in the settlement spend bundle, the loss is realized on-chain and cannot be corrected after the fact.

### Likelihood Explanation
This triggers deterministically any time an offer/request includes more than one royalty-eligible NFT on the same side (`royalty_split > 1`) together with fungible payment — a normal, unprivileged wallet action fully reachable by any offer maker, requiring no special permissions or malicious peer behavior.

### Recommendation
Refactor `compute_royalty_amount` to defer division as long as possible, e.g.:
```python
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```
guarding against overflow the same way `uint64` bounds are already checked, consistent with the correct-precision refactor pattern given in the referenced report for `SafEth.stake()`/`Reth.deposit()`.

### Proof of Concept
```python
from chia.wallet.nft_wallet.nft_wallet import compute_royalty_amount

# offered_amount indivisible by royalty_split loses extra precision
# true intended royalty (no premature truncation): 999 * 500 // 10000 = 49
# actual result with premature division by royalty_split=2:
result = compute_royalty_amount(offered_amount=-999, royalty_split=2, percentage=500)
print(result)  # -> 999 // 2 * 500 // 10000 = 499 * 500 // 10000 = 24 (vs. correct 999*500//(2*10000)=24.9->24)
```
While in this particular numeric example the difference is small, the compounding truncation (`//` then `*` then `//`) systematically biases the result downward compared to a single deferred division, and the loss grows with larger `royalty_split` values and offer amounts, directly reducing the on-chain `CreateCoin` royalty payout below the mathematically correct amount. Full verification of the on-chain CLVM-side royalty enforcement (to confirm whether any independent floor check exists) was not completed within the available tool budget; this should be additionally verified in the NFT ownership-layer transfer program CLVM source before treating this as fully conclusive.

def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
