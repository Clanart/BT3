### Title
Unauthenticated `shop` param drives cross-shop Admin API calls via `EnsureInstalled#validate_non_embedded_session` - (File: app/controllers/concerns/shopify_app/ensure_installed.rb)

### Summary
`ShopifyApp::EnsureInstalled` is explicitly documented as *not authenticating* the request — it derives shop context purely from the user-controllable `params[:shop]` query string. In the legacy (non-token-exchange) code path, this unauthenticated shop value is used to look up an arbitrary shop's **stored offline access token** and immediately use it to make a live Shopify Admin API call, without confirming the requester is actually that shop.

### Finding Description
`current_shopify_domain` in `EnsureInstalled` resolves directly from `params[:shop]` with no verification of the caller's identity: [1](#0-0) 

That value is then used to fetch the shop's persisted session/token from storage: [2](#0-1) 

When the legacy `check_shop_known`/`validate_non_embedded_session` flow is active (i.e., `use_new_embedded_auth_strategy?` is false), and the request is not detected as loaded directly from the Shopify admin, the code builds an authenticated Admin API client using that looked-up session/token and performs a live request: [3](#0-2) 

The controller-concerns documentation itself flags this design as unauthenticated and warns against using it for anything beyond bootstrap/routing: [4](#0-3) 

This mirrors the `coverDefault` bug class: a caller-supplied identifier (`provider`/`shop`) that was never verified to belong to the requester is used to pull and spend another party's previously-granted credential (an approved token balance / a stored offline OAuth access token) on their behalf.

### Impact Explanation
An unauthenticated actor can supply an arbitrary `shop=` value for any shop that has installed the app. If that shop's non-embedded/direct-load check fails (`loaded_directly_from_admin?` is false — trivial for any request not coming from `myshopify.com` referer or top-level frame heuristics used there), the app will use that other shop's stored offline access token to issue a `GET shop` Admin API call. This is a confused-deputy pattern: the attacker doesn't see the shop's data directly, but they can (a) force API usage/rate-limit consumption against another merchant's install, and (b) use the differing behavior (redirect-to-login on `401` vs. no redirect) to enumerate which shops are currently installed and have valid tokens, leaking install/session-validity state for arbitrary shop domains they don't own.

### Likelihood Explanation
Any app built with `shopify_app` that still uses the legacy (non–token-exchange) `EnsureInstalled` flow and includes it on a controller reachable without prior authentication (its documented use case, e.g., serving the app shell) is affected by a trivial, single, unauthenticated GET request with an attacker-chosen `shop` parameter.

### Recommendation
Do not use the requester-supplied `shop` parameter to select and use another party's stored access token for live API calls. `validate_non_embedded_session` should only run once shop identity has been authenticated (e.g., only reachable behind `EnsureHasSession`/token exchange verified context), or it should be removed from the unauthenticated `EnsureInstalled` flow entirely, consistent with the existing guidance in `docs/shopify_app/controller-concerns.md` that `EnsureInstalled` must never be used to authorize access to shop data or tokens.

### Proof of Concept
1. Attacker sends `GET /some_installed_only_route?shop=victim-shop.myshopify.com` without any session token, auth header, or admin-embedded context.
2. `EnsureInstalled#check_shop_domain` passes because `current_shopify_domain` is derived purely from the query string.
3. `check_shop_known` loads `victim-shop`'s stored offline session via `SessionRepository.retrieve_shop_session_by_shopify_domain`.
4. `validate_non_embedded_session` (since the request isn't recognized as loaded from the Shopify admin) builds `ShopifyAPI::Clients::Rest::Admin.new(session: installed_shop_session)` and calls `client.get(path: "shop")` using the victim shop's access token — an API call the attacker never had permission to trigger, driven entirely by an unauthenticated, attacker-controlled `shop` identifier.

## EnsureInstalled — Installation Check Only
Use this concern to verify that the app has been installed on a given shop. It is designed for unauthenticated entry points in embedded apps, such as serving the app shell or redirecting to OAuth.

> ⚠️ **This concern does not authenticate the request.** The shop is resolved from the `shop` query string parameter, which is user-controllable. Do not use this concern to gate access to shop data, access tokens, or Shopify API calls. For authenticated actions, use `EnsureHasSession`.

If the app is not installed for the provided `shop` parameter, the request will be redirected to login or the `embedded_redirect_url`.
