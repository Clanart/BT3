Confirmed: `check_session_expiry_date` has no default set in `initialize` [1](#0-0) , meaning it is `nil`/falsy unless the app operator explicitly opts in, so expiry validation is not enforced by default.

Analysis of the strongest analog: `ShopifyApp::AppProxyVerification#query_string_valid?` validates only that the HMAC signature over the query string (including `shop`, `path_prefix`, `timestamp`, etc.) matches, but never checks that the `timestamp` parameter is recent [2](#0-1) . This is the direct analog of the oracle-staleness bug class: a validly-signed but stale set of parameters is accepted indefinitely because there is no freshness/expiry check, only a signature check.

### Title
Missing timestamp freshness check allows indefinite replay of signed App Proxy requests - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` verifies only that the HMAC signature matches the query parameters; it never validates that the `timestamp` query parameter (which Shopify includes and signs specifically to bound request freshness) is recent. Any previously-observed valid signed proxy request (e.g., leaked via logs, browser history, referrer headers, or a shared/compromised link) remains fully valid forever and can be replayed by anyone, exactly analogous to the reported oracle-staleness class of bug where a signature/validity check exists but the "freshness" dimension is never verified.

### Finding Description
`query_string_valid?` extracts the `signature` param, computes the expected HMAC over the remaining sorted query params (`shop`, `path_prefix`, `timestamp`, etc.) using `ShopifyApp.configuration.secret`, and does a `secure_compare`: [3](#0-2) 

The `timestamp` field is treated as just another signed parameter, but its value is never compared against `Time.now` or any freshness window. There is no code path anywhere in this concern that rejects a request whose `timestamp` is old. As a result, once a valid `(shop, path_prefix, timestamp, signature)` tuple exists, it remains a fully accepted, authenticated App Proxy request indefinitely — the analog of "outdated prices" being accepted because only the signature (not the staleness) is checked.

### Impact Explanation
An attacker who obtains a previously valid, fully-formed proxy request URL (e.g., from browser history, shared support tickets, proxy/CDN logs, or a `Referer` header leak) can replay it at any later time and have it treated by `verify_proxy_request` as an authentic, current request from Shopify's app proxy on behalf of the shop [4](#0-3) . Depending on what the app-proxy-protected controller does with parameters like `shop`, `logged_in_customer_id`, or other business-logic query params, this can enable replay-based logic abuse, stale customer-context actions, or repeated triggering of state-changing operations under the guise of a legitimately-signed Shopify request.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one valid signed query string (not forge one, since the secret is unknown), which lowers likelihood compared to a full signature bypass. However, because app proxy URLs are often embedded in storefront pages, links, or logs, and because there is no time-boxing at all, the exposure window is unbounded rather than the few-minute window Shopify's own admin normally expects for proxy requests.

### Recommendation
Enforce a freshness check on the `timestamp` parameter in `query_string_valid?` (e.g., reject if `Time.at(query_hash["timestamp"].to_i) < Time.now - ALLOWED_CLOCK_SKEW`), similar to the reported recommendation of storing/checking a "last update" or freshness bound before accepting a signed value as current, rather than relying on signature validity alone.

### Proof of Concept
1. Legitimate request occurs: `GET /app_proxy/basic?shop=some-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid-hmac>`.
2. This exact query string is captured (browser history, proxy log, shared link).
3. Days/months later, an unrelated party replays the identical URL.
4. `query_string_valid?` recomputes the same HMAC over the same params and it matches, so `verify_proxy_request` allows the request through with `head(:ok)`/normal controller execution, as demonstrated by the passing test using the same fixed `timestamp=1466106083` value long after that time has passed [5](#0-4) .

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
