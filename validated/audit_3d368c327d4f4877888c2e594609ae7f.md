### Title
`ReceivedOutput::read` accepts an arbitrary offset/output binding without verifying the offset actually derives the output's script - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`Scanner::scan_transaction` only produces a `ReceivedOutput` after confirming `output.script_pubkey` is a registered script in `self.scripts` (i.e., `p2tr_script_buf(key + offset * G)`), so the returned `offset` is guaranteed to be the scalar that makes the output spendable by the wallet's key. `ReceivedOutput::read` performs no such binding check: it deserializes a `Scalar` offset, a `TxOut`, and an `OutPoint` and returns them as a valid spendable output regardless of whether the offset corresponds to the output's script. This mirrors the reported bug class: the production path (`scan_transaction`, analogous to `_allocate`) enforces a validity condition on the data, while the alternative path (`read`, analogous to `distribute`) acts on the same object type without enforcing it.

### Finding Description
`Scanner::new`/`register_offset` build a map `scripts: HashMap<ScriptBuf, Scalar>` where each key is the P2TR script of `key + offset * G` [1](#0-0) [2](#0-1) . `scan_transaction` only emits a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` returns an offset, so scanning guarantees `offset` correctly identifies the spend key for that exact output [3](#0-2) .

`ReceivedOutput::read` instead accepts untrusted bytes and reconstructs `{ offset, output, outpoint }` with no check that the offset is the one the scanner bound to `output.script_pubkey`, nor even that `output.script_pubkey` is a P2TR script of the wallet's key family at all [4](#0-3) .

The send path then trusts this binding: `offset()` is used to derive the spending key for the output (via `keys.offset(...)`/tweak), so a mismatched offset produces a signature under the wrong key — the output cannot be spent [5](#0-4) .

### Impact Explanation
An unprivileged party that can feed bytes into `ReceivedOutput::read` (e.g., a peer relaying serialized scanner results over an untrusted channel) can report funds as received that are not spendable by the wallet: either outputs whose script does not correspond to `key + offset*G` (permanently unspendable, yet counted as wallet balance and potentially selected as inputs, producing transactions that can never be validly signed), or outputs whose real offset differs (spendable under a different offset the wallet may not know). This is a concrete integrity violation of the wallet's view of its own funds — value credited but not spendable, plus wasted fees on doomed spend attempts.

### Likelihood Explanation
The exploit requires only that serialized `ReceivedOutput`s cross a trust boundary (network sync, coordinator/processor handoff, or persisted scanner state tampered by another process) — a realistic deployment pattern for a scanner/wallet split. Crafting the malicious bytes is trivial since no cryptographic check gates the constructor. It does not allow theft of existing funds, only false accounting and stuck spends, so Medium severity.

### Recommendation
Verify the offset↔script binding on deserialization. Since `read` currently has no access to the wallet key, either:
- change the signature to `ReceivedOutput::read(r, key: &ProjectivePoint) -> io::Result<Option<ReceivedOutput>>` and require `p2tr_script_buf(key + GENERATOR * offset) == Some(output.script_pubkey)`, or
- add `ReceivedOutput::verify(&self, key) -> bool` / `Scanner::verify_output(&self, &ReceivedOutput)` checking `self.scripts.get(&output.script_pubkey) == Some(&offset)`, and require callers to invoke it on any deserialized output before use.

### Proof of Concept
```rust
// Given a Scanner for some key K with registered offset o for script S:
// Attacker crafts bytes: offset = o (or any scalar), TxOut { script_pubkey: S' != S, value: V }
// ReceivedOutput::read accepts it.
let mut bytes = offset.to_bytes().to_vec();
bytes.extend(serialize(&TxOut { value: Amount::from_sat(50_000), script_pubkey: arbitrary_p2tr }));
bytes.extend(serialize(&OutPoint::new(txid, 0)));
let ro = ReceivedOutput::read(&mut &bytes[..]).unwrap(); // succeeds
// ro.offset() is now claimed to spend an output whose script it does not correspond to.
// wallet send path calls keys.offset(ro.offset()) -> wrong key -> unspendable input,
// while ro.value() is counted as received balance.
```

Note: `scan_block` also returns coinbase outputs before maturity [6](#0-5) , but that is explicitly documented behavior and was excluded per the rules; the `read` gap is undocumented.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
