### Title
`ReceivedOutput::read` accepts forged deposit claims without verifying the output belongs to the scanned key or exists on-chain - (networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report (GHSA-xq8r-r72r-pqwm) describes data fetched over an unauthenticated channel being substituted by an attacker, so the consumer executes/uses attacker-chosen content. The analog in Serai is `ReceivedOutput`: it is a claim "the protocol received spendable funds," it has `read`/`write`/`serialize` methods clearly designed for transport across an unauthenticated boundary, yet `ReceivedOutput::read` performs no consistency check whatsoever. The serialized `offset`, `TxOut`, and `OutPoint` are accepted verbatim — the code never verifies that `output.script_pubkey` equals `p2tr(scanner_key + offset * G)`, that the script was ever registered, or that the `outpoint` corresponds to a real, unspent transaction. Any party able to supply these bytes can fabricate a deposit.

### Finding Description
`ReceivedOutput` bundles three attacker-controlled fields: a scalar `offset` (read via `Secp256k1::read_F`), a `TxOut` (consensus-decoded, arbitrary `script_pubkey` and `value`), and an `OutPoint` (arbitrary txid/vout). [1](#0-0) 

Legitimate `ReceivedOutput`s are only ever produced by `Scanner::scan_transaction`, which constructs them by matching `output.script_pubkey` against the registered `scripts` map and binding the `outpoint` to `tx.compute_txid()`. [2](#0-1)  Critically, `Scanner` holds `key` — the group key — precisely so this binding can be checked, but `ReceivedOutput` does not carry the key or a proof of binding, and `read` cannot re-derive or verify it. Deserialization is therefore fully decoupled from the only code path that establishes authenticity. [3](#0-2) 

A forged serialization can therefore encode:
- An `outpoint` pointing to a nonexistent or already-spent output (funds "received" that are not spendable).
- A `TxOut` whose `script_pubkey` is not `p2tr(key + offset*G)` — e.g., an output paying the attacker — paired with any `offset`, so the credited "deposit" is spendable by someone else, not the threshold key.
- An inflated `value`, since `ReceivedOutput::value()` simply returns `output.value` with no sanity check. [4](#0-3) 

### Impact Explanation
Any downstream code that deserializes a `ReceivedOutput` from an untrusted transport (peer message, DB entry written by a less-trusted component, coordinator relay) and treats it as a confirmed received output will credit funds that were never received, or credit an output the threshold key cannot spend. The acceptable-impact criterion "funds reported received that are not spendable" is met exactly: the fabricated outpoint/output pair produces a `ReceivedOutput` indistinguishable from a genuine scanned one.

### Likelihood Explanation
The struct exposes `read`, `write`, and `serialize` specifically to move outputs between components; serialization exists precisely because the object crosses a trust boundary. The attacker needs only the ability to supply bytes to a `read` call — listed as in-scope untrusted input. No privileged validator position, collusion, or key material is required; a network attacker or any peer feeding serialized outputs to a consumer suffices, mirroring the privileged-network-position attacker of the original advisory.

### Recommendation
Either treat `ReceivedOutput` as untrusted until re-validated — i.e., document and enforce that consumers must re-run `Scanner::scan_transaction`/`scan_block` against the referenced outpoint, checking `output.script_pubkey` against `p2tr(key + offset*G)` and confirming the outpoint exists and is unspent — or make deserialization self-authenticating by binding the group key into the type (store `key`/`script_pubkey` inside `ReceivedOutput` and have `read` verify `script_pubkey == p2tr(key + offset*G)`, rejecting mismatches).

### Proof of Concept
1. Victim component accepts serialized `ReceivedOutput`s from a network peer and calls `ReceivedOutput::read`.
2. Attacker serializes: `offset = 1` (any valid scalar), `TxOut { value: 21_000_000_00000000, script_pubkey: <attacker's own P2TR script> }`, `outpoint = OutPoint::new(<random txid>, 0)`.
3. `ReceivedOutput::read` succeeds — `read_F` accepts the canonical scalar and `consensus_decode` accepts the well-formed `TxOut`/`OutPoint`.
4. The consumer now holds a `ReceivedOutput` whose `value()` reports a huge deposit and whose `outpoint()` references nothing on-chain; any attempt to build a spend transaction references a nonexistent/non-spendable UTXO, while the balance was already credited. [5](#0-4) 

Caveat: severity depends on integrators actually deserializing `ReceivedOutput` from unauthenticated sources rather than producing it solely via `Scanner`; the absence of any consistency check in `read` is verified, but no in-repo consumer of `ReceivedOutput::read` was located within the in-scope crates, so the exploit path assumes the documented serialization API is used over a trust boundary.

    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);

        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
