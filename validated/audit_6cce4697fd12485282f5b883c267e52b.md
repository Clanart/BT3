### Title
DID recovery list (`backup_ids`) not reset after DID transfer, allowing seller to reclaim a sold DID - (File: `chia/wallet/did_wallet/did_wallet.py`)

### Summary
The DID recovery mechanism lets a set of "backup" DIDs regain control of a DID singleton if the current owner's key is unavailable, using signed attestations rather than the current owner's own key. When a DID is sold/transferred with `DIDWallet.transfer_did`, the `backup_ids` list (and the required verification count) are carried over unchanged unless the seller explicitly clears them via `reset_recovery`. This is directly analogous to the Arcadia `approvedCreditor` bug: a privileged backdoor list configured by the *previous* owner is not reset on ownership transfer, letting the previous owner (or any entity in the stale recovery list) regain control of the asset after it changes hands.

### Finding Description
`DIDWallet.transfer_did` builds the new DID inner puzzle hash while defaulting to keep the existing `backup_ids`/`num_of_backup_ids_needed`: [1](#0-0) 

The seller must explicitly invoke a "reset recovery" flow to clear the list; the CLI even exposes this as an opt-in flag defaulting to *not* resetting: [2](#0-1) 

The default RPC-level command (`chia wallet did transfer`) passes `with_recovery_info=True` by default and does not force clearing the recovery configuration, matching the pattern seen in tests where recovery info is preserved across a transfer: [3](#0-2) 

Additionally, `get_innerpuz_for_new_innerhash` explicitly documents that the recovery list is *not* cleared by design, and offloads the responsibility for cleaning it up entirely to the seller: [4](#0-3) 

Because the recovery/backup mechanism is driven by attestation signatures from the `backup_ids` (not from the current p2 owner key), any DID present in a stale `backup_ids` list retains the ability to recover/take over the DID coin after a sale if that list is not proactively reset by the seller. `DIDWallet.create_new_did_wallet_from_recovery` and `WalletStateManager.find_lost_did` show how this recovery path is completed using only backup signatures/attestations, independent of the current owner's private key: [5](#0-4) 

This is conceptually identical to the reported bug class: a secondary/backup authority configured by a prior owner is not reset upon ownership transfer, creating a persistent backdoor that outlives the transfer of the underlying asset.

### Impact Explanation
If a buyer purchases a DID (and by extension any assets whose provenance/ownership is tied to that DID, such as NFTs minted or owned under that DID) without independently verifying and resetting the `backup_ids`/recovery configuration, the previous owner (or any address they placed in the recovery list) can later initiate a DID recovery spend and regain control of the DID coin, effectively stealing back the asset from the new owner. This is a fund/asset-theft-capable backdoor reachable purely through the standard wallet transfer flow and DID recovery flow — no privileged, malicious-peer, or protocol-layer access is required.

### Likelihood Explanation
Medium. Exploitation requires: (1) the DID having a non-empty `backup_ids`/non-zero `num_of_backup_ids_needed` recovery configuration set by the seller prior to sale, and (2) the seller (or buyer, if unaware) not explicitly resetting the recovery configuration during transfer (which is the default/opt-in-to-reset behavior in the CLI and API). Given that resetting recovery is not the default and requires explicit action (`--reset_recovery` flag or equivalent), a seller acting in bad faith can trivially set up this backdoor before selling a DID, or an unsuspecting seller may simply forget to reset it, both of which are realistic occurrences on secondary markets for DID-based assets (e.g. NFT collections gated by a DID).

### Recommendation
- Default `chia wallet did transfer` (and the underlying `DIDWallet.transfer_did` / `get_innerpuz_for_new_innerhash`) to reset the recovery list (`backup_ids = []`, `num_of_backup_ids_needed = 0`) unless the caller explicitly opts to preserve it, inverting the current opt-in-to-reset default.
- Surface a clear warning in wallet RPC/CLI responses when transferring a DID that still has a non-empty recovery list, requiring explicit buyer/seller acknowledgment.
- Consider making buyer-side tooling (e.g. offer acceptance flows for DID-gated NFTs) validate that the recovery list is empty (or contains only entities the buyer trusts) before accepting a DID transfer, analogous to how marketplaces are expected to check "approvedCreditor" timing in the original report.

### Proof of Concept
1. Alice creates a DID with `backup_ids = [Alice_backup_DID]`, `num_of_backup_ids_needed = 1` (a legitimate, common recovery configuration).
2. Alice sells/transfers the DID to Bob via `chia wallet did transfer` without passing `--reset_recovery` (the default).
   - See `chia/wallet/did_wallet/did_wallet.py` `transfer_did`, which reuses `self.did_info.backup_ids` unchanged (lines 820-832 above).
3. Bob now legitimately owns the DID's p2 (spend) key, unaware the old `backup_ids` entry (`Alice_backup_DID`) is still active in the puzzle.
4. Alice, using `Alice_backup_DID`, creates a recovery attestation (`create_spend_for_message` / `create_recovery_message_puzzle`) and completes a recovery spend via the standard DID recovery flow (`DIDWallet.create_new_did_wallet_from_recovery`, `WalletStateManager.find_lost_did`), assigning the DID's new p2 puzzle hash to an address Alice controls.
5. This spend is valid on-chain because the recovery mechanism only requires signatures from `backup_ids`, not from Bob's current owner key — Alice regains full control of the DID coin (and any NFTs/assets whose ownership provenance depends on that DID), effectively stealing the asset back from Bob.

    async def get_innerpuz_for_new_innerhash(self, pubkey: G1Element) -> Program:
        """
        Get the inner puzzle for a new owner
        :param pubkey: Pubkey
        :return: Inner puzzle
        """
        # Note: the recovery list will be kept.
        # In a selling case, the seller should clean the recovery list then transfer to the new owner.
