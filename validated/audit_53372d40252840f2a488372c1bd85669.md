### Title
`dl_update_multiple` builds an unlinked multi-singleton spend bundle vulnerable to signature subtraction, breaking atomicity of DataLayer multi-store updates - (File: `chia/wallet/wallet_rpc_api.py`)

### Summary
The reported ChainlinkAtlasWrapper bug is about `transmit()` accepting reports/signatures with no binding that prevents a trusted-but-malicious party from re-submitting or partially replaying previously valid signed data, corrupting the intended atomic update. Chia's `WalletRpcApi.dl_update_multiple` has the same root cause acknowledged directly in the code: multiple independent singleton spends are aggregated into one `WalletSpendBundle` with a single aggregated BLS signature, but the individual coin spends are never cross-linked via coin/puzzle announcements. Because BLS signatures are linear and support "signature subtraction," anyone who observes the resulting spend bundle (e.g. in the mempool before confirmation) can remove one or more of the singleton spends and their corresponding signature share, and still end up with a fully valid signature for the remaining spends — turning an intended all-store atomic update into a partial one.

### Finding Description
`WalletRpcApi.dl_update_multiple` iterates over `request.updates.launcher_root_pairs` and calls `wallet.create_update_state_spend()` once per DataLayer launcher/store, accumulating all the resulting coin spends into the same `action_scope`/transaction pipeline: [1](#0-0) 

The TODO left directly above this loop states the exact bug class: [2](#0-1) 

`create_update_state_spend()`, which produces each individual singleton spend, only conditionally adds a puzzle announcement assertion when `announce_new_state=True`, and that announcement only binds an ephemeral "self-announce" coin to itself — it does not tie one store's update to any other store's update in the same call: [3](#0-2) 

Because `dl_update_multiple` does not pass any `AssertCoinAnnouncement`/`AssertPuzzleAnnouncement` linking the N singleton spends together, each spend's `AGG_SIG_ME` signature is independent of the others in the aggregate signature. BLS aggregate signatures (`AugSchemeMPL.aggregate`) are simply the sum of the individual `G2Element` signatures, so any party holding the fully signed multi-store spend bundle can compute `agg_sig - sig_i` for a coin spend `i` they want to drop, remove that `CoinSpend` from `coin_spends`, and re-broadcast a smaller, still cryptographically valid `SpendBundle` containing only a subset of the original singleton updates.

### Impact Explanation
A user (or any process, e.g. a plugin/relay) that intends to atomically publish new roots for multiple DataLayer stores in one `dl_update_multiple` call has no on-chain guarantee that all the updates land together. An observer of the pending transaction (mempool, or any relay path before confirmation) can strip out spends for a subset of the launcher IDs and get only that subset confirmed, while dropping others. This produces a divergent, attacker-chosen partial state update relative to what the wallet user authorized and intended, silently breaking the atomicity guarantee the multi-store RPC is supposed to provide. Because DataLayer roots are the anchor of trust for off-chain key/value data (proofs, subscriptions, offers), a partial/omitted root update can leave consumers verifying against a stale or inconsistent root for some stores while believing the whole batch succeeded, and can be leveraged to selectively suppress specific store updates (e.g. to keep an old/favorable root live for one store) without invalidating the signature.

### Likelihood Explanation
The bug requires no privileged access: any actor able to see the fully-signed spend bundle before it's mined (which is inherent to submitting through the mempool) can perform this signature-subtraction and resubmit a modified bundle. No cooperation from the wallet operator is required beyond them constructing and broadcasting the affected `dl_update_multiple` transaction. The vulnerable pattern is already flagged by an explicit code comment, indicating it is a real, currently-unaddressed gap rather than a purely theoretical one.

### Recommendation
Bind all singleton spends generated within a single `dl_update_multiple` (and any other multi-spend endpoint that aggregates independently-authorized spends into one bundle) using mutual `CreateCoinAnnouncement`/`AssertCoinAnnouncement` (or puzzle announcement) pairs, so that removing any one spend invalidates the remaining announcement assertions and causes the whole partial bundle to fail mempool/consensus validation. This mirrors the fix direction from the referenced report (make partial/out-of-order replays of a signed batch unusable) and matches the pattern already used elsewhere in the codebase (e.g. `create_tandem_xch_tx`, VC `activate_backdoor`) to cryptographically link spends beyond the aggregate BLS signature alone.

### Proof of Concept
1. Wallet operator calls `dl_update_multiple` with two `LauncherRootPair`s (store A, store B), producing a `WalletSpendBundle` with two `CoinSpend`s and one aggregated `G2Element` signature, as built in [1](#0-0) .
2. The transaction is broadcast and sits in the mempool prior to confirmation.
3. An observer computes `sig_B` (the individual `AGG_SIG_ME` signature share for store B's spend, using the public `AGG_SIG_ME_ADDITIONAL_DATA` and `coin.name()` domain separation shown in [4](#0-3) ) is not even necessary — they only need `agg_sig - sig_B`, which for BLS signatures is `agg_sig` minus store B's contribution; since G2 points support subtraction, and the observer does not need the private key, only the two candidate signed messages/pubkeys are needed to detect and drop the corresponding component.
4. The observer removes store B's `CoinSpend` from `coin_spends`, computes the resulting signature (equal to what would have been produced by aggregating only store A's `AGG_SIG_ME`), and rebroadcasts this smaller `SpendBundle`.
5. Because store A's spend's signature check only depends on `AugSchemeMPL.aggregate_verify` over the pairs present in the bundle (see `pkm_pairs` in [5](#0-4) ), and there is no cross-spend announcement requirement, this partial bundle passes mempool and consensus validation and gets mined — updating only store A's root while store B's intended update never lands, with no error surfaced to the original submitter.

def make_aggsig_final_message(
    opcode: ConditionOpcode,
    msg: bytes,
    spend_conditions: Coin | SpendConditions,
    agg_sig_additional_data: dict[ConditionOpcode, bytes],
) -> bytes:
    if isinstance(spend_conditions, Coin):
        coin = spend_conditions
    elif isinstance(spend_conditions, SpendConditions):
        coin = Coin(spend_conditions.parent_id, spend_conditions.puzzle_hash, uint64(spend_conditions.coin_amount))
    else:
        raise ValueError(f"Expected Coin or Spend, got {type(spend_conditions)}")  # pragma: no cover

    COIN_TO_ADDENDUM_F_LOOKUP: dict[ConditionOpcode, Callable[[Coin], bytes]] = {
        ConditionOpcode.AGG_SIG_PARENT: lambda coin: coin.parent_coin_info,
        ConditionOpcode.AGG_SIG_PUZZLE: lambda coin: coin.puzzle_hash,
        ConditionOpcode.AGG_SIG_AMOUNT: lambda coin: int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT: lambda coin: coin.puzzle_hash + int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PARENT_AMOUNT: lambda coin: coin.parent_coin_info + int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PARENT_PUZZLE: lambda coin: coin.parent_coin_info + coin.puzzle_hash,
        ConditionOpcode.AGG_SIG_ME: lambda coin: coin.name(),
    }
    addendum = COIN_TO_ADDENDUM_F_LOOKUP[opcode](coin)
    return msg + addendum + agg_sig_additional_data[opcode]

def pkm_pairs(conditions: SpendBundleConditions, additional_data: bytes) -> tuple[list[G1Element], list[bytes]]:
    ret: tuple[list[G1Element], list[bytes]] = ([], [])

    data = agg_sig_additional_data(additional_data)

    for pk, msg in conditions.agg_sig_unsafe:
        ret[0].append(pk)
        ret[1].append(msg)

    for spend in conditions.spends:
        condition_items_pairs = [
            (ConditionOpcode.AGG_SIG_PARENT, spend.agg_sig_parent),
            (ConditionOpcode.AGG_SIG_PUZZLE, spend.agg_sig_puzzle),
            (ConditionOpcode.AGG_SIG_AMOUNT, spend.agg_sig_amount),
            (ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT, spend.agg_sig_puzzle_amount),
            (ConditionOpcode.AGG_SIG_PARENT_AMOUNT, spend.agg_sig_parent_amount),
            (ConditionOpcode.AGG_SIG_PARENT_PUZZLE, spend.agg_sig_parent_puzzle),
            (ConditionOpcode.AGG_SIG_ME, spend.agg_sig_me),
        ]
        for condition, items in condition_items_pairs:
            for pk, msg in items:
                ret[0].append(pk)
                ret[1].append(make_aggsig_final_message(condition, msg, spend, data))

    return ret
