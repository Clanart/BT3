## Title
Auto-rewrite of a repository's Git remote URL trusts an unvalidated `clone_url` from a (possibly attacker-controlled) GitHub API/Enterprise response - (`File: app/src/lib/stores/updates/update-remote-url.ts`)

## Summary
This is a genuine bug-class analog of the EigenPod issue, not a coincidental match: both defects stem from a validator that only checks a *shape/format* property (withdrawal-credential prefix vs. URL protocol scheme) instead of the *substantive identity* the check is supposed to protect (which pod owns the funds vs. which host the remote actually points to). In EigenPod, the incomplete check makes the system fail to recognize a legitimate new credential format. In GitHub Desktop, the analogous incomplete check makes the system accept a *different* but same-scheme URL as "safe to auto-apply," silently rewriting the user's real Git remote.

## Finding Description
`updateRemoteUrl()` in `app/src/lib/stores/updates/update-remote-url.ts` is invoked from `repositoryWithRefreshedGitHubRepository()` in `app/src/lib/stores/app-store.ts` every time Desktop refreshes GitHub repository metadata via `api.fetchRepository(owner, name)`: [1](#0-0) 

The function decides whether to silently rewrite the local remote to the server-supplied `clone_url`: [2](#0-1) 

The guard only checks that the **scheme** (`https:`/`https:`) of the old and new URLs match (via the legacy, deprecated `URL.parse`) and that `urlMatchesRemote()` previously matched the *old* clone URL - it never validates that the **new** `clone_url`'s hostname belongs to a trusted GitHub/GHE endpoint the account is actually configured for. Just like EigenPod's `_podWithdrawalCredentials()` only checks the `0x01` prefix and never checks whether the full 32-byte value legitimately identifies "this pod," this code only checks the URL *scheme* and never checks whether the full authority/host legitimately identifies "this account's server."

`urlMatchesRemote()` (`app/src/lib/repository-matching.ts:90-118`) and `parseRemote()` (`app/src/lib/remote-parsing.ts:27-64`) are regex-based, format-specific parsers, structurally similar to EigenPod's prefix-only check - they only recognize a fixed set of URL shapes and compare owner/name/hostname components, but nothing downstream cross-checks the resulting hostname against the account's actual endpoint before calling `gitStore.setRemoteURL()`, which executes `git remote set-url` directly: [3](#0-2) 

If a user has added a GitHub Enterprise Server account (`app/src/lib/api.ts`'s `getEnterpriseAPIURL`/`getAPIEndpoint`), and that server is attacker-controlled or compromised (i.e., "the attacker controls...a GitHub API object" per the accepted impact model), the JSON returned by `GET repos/{owner}/{name}` is trusted verbatim. Setting `clone_url` to `https://attacker.example/owner/repo.git` satisfies `protocolsMatch` (both `https:`) and, once written, is used for every future `git push`/`git fetch` performed by Desktop for that repository via the credential-helper trampoline (`app/src/lib/trampoline/trampoline-credential-helper.ts`), which resolves credentials per-endpoint using `isGitHubHost()`/`findGitHubTrampolineAccount()` host-origin matching. Because the corrupted remote no longer matches the user's stored account origin, Desktop can end up prompting the user to "sign in" to what looks like their normal GitHub host, or invoking the generic-credential flow (`app/src/lib/generic-git-auth.ts`) against the attacker's host.

## Impact Explanation
- Silent corruption of what the user pushes/fetches: their `origin` remote is rewritten to an attacker-controlled URL without any confirmation dialog.
- Potential credential/token exfiltration: subsequent authenticated operations (or user-driven "sign in" prompts triggered because the corrupted host is unrecognized) can result in credentials or sign-in flows being directed at the attacker's server.
- This satisfies the accepted impact categories "the attacker controls...a GitHub API object" and "silent corruption of what the user commits or pushes."

## Likelihood Explanation
Requires the user to have an account configured against a GitHub Enterprise Server that is attacker-controlled/compromised (an accepted attacker primitive, distinct from local/physical access or leaked credentials), and for the repository being refreshed to be one Desktop already tracks. Desktop performs this refresh automatically in the background (`repositoryWithRefreshedGitHubRepository`), so no unusual user action beyond normal app usage is required once the malicious/compromised endpoint is present.

## Recommendation
In `updateRemoteUrl()`, before calling `gitStore.setRemoteURL()`, validate that the new `clone_url`'s hostname matches the hostname of the account's configured endpoint (the same trust boundary that `findAccountForRemoteURL`/`matchGitHubRepository` use elsewhere), not merely that the URL scheme is unchanged. Reject (or prompt the user to confirm) any auto-update where the resulting hostname differs from the expected, previously-trusted endpoint host.

## Proof of Concept
1. Add a GitHub Enterprise Server account in Desktop pointing at a server the attacker controls (or a legitimate GHES that becomes compromised).
2. Clone/track a repository from that server; Desktop stores `gitHubRepository.cloneURL` pointing at the real server.
3. The attacker-controlled server later returns, for `GET repos/{owner}/{name}`, a JSON body with `clone_url: "https://attacker.example/owner/repo.git"` (same `https:` scheme).
4. On the next background refresh, `repositoryWithRefreshedGitHubRepository()` → `updateRemoteUrl()` evaluates `protocolsMatch = true`, `remoteUrlUnchanged = true`, `urlsMatch = false`, and calls `gitStore.setRemoteURL('origin', 'https://attacker.example/owner/repo.git')`, silently repointing the repository's remote as confirmed by the existing test `"updates the repository's remote url when the github url changes"` in `app/test/unit/stores/updates/update-remote-url-test.ts:68-81`.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
