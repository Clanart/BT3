### Title
`ReceivedOutput::read` fabricates "received" funds with no offset↔script binding, producing outputs reported as spendable that cannot be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` is the type `Scanner` produces to assert "this key received N satoshis spendable via `offset`". Its deserializer `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) accepts an arbitrary scalar `offset`, an arbitrary `TxOut`, and an arbitrary `OutPoint` from raw bytes, with no check that the `offset` actually derives the `TxOut`'s `script_pubkey` under the group's key, and no check the `OutPoint` exists on-chain. This mirrors the ERC1155Bridgable bug class (a receive/claim path that cannot actually deliver the funds it accounts for): a `ReceivedOutput` produced this way reports `value()` sats as received, yet `SignableTransaction::multisig` (networks/bitcoin/src/wallet/send.rs:273-285) will silently return `None` because `p2tr_script_buf(offset.group_key()) != prevouts[i].script_pubkey`, so the "received" funds can never be spent.

### Finding Description
`scan_transaction`/`scan_block` are the *safe* producers: they only emit `ReceivedOutput`s whose `script_pubkey` is a registered script and whose `offset` is the stored map entry (networks/bitcoin/src/wallet/mod.rs:199-214), and `register_offset` guarantees each script was built from an even-Y point the key can spend (mod.rs:180-196).

`ReceivedOutput::read` bypasses all of that:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  let output = TxOut::consensus_decode(&mut buf_r)...;
  let outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

Three independently attacker-controlled fields are decoded with zero cross-validation:

1. `offset` is any scalar — it is never checked that `p2tr_script_buf(group_key + offset·G) == output.script_pubkey`.
2. `output.script_pubkey` need not be a P2TR script the group controls at all.
3. `outpoint` need not correspond to any real UTXO.

The type's contract ("A spendable output", mod.rs:88) is therefore violated: `value()` (mod.rs:116-118) reports the crafted amount as received funds, while the spend path cannot complete. `SignableTransaction::multisig` computes `keys.clone().offset(self.offsets[i])` and requires `p2tr_script_buf(offset.group_key()) == self.prevouts[i].script_pubkey` (send.rs:276-278); for a crafted `ReceivedOutput` this is unsatisfiable unless the attacker deliberately picks an offset matching the script — which just yields the already-checked honest case — so any inconsistent output aborts signing of the *entire* transaction (`None?` on line 278 rejects the whole `multisig`, poisoning every co-spent honest input).

### Impact Explanation
Two consequences, both reachable purely through untrusted bytes passed to `ReceivedOutput::read` (or any higher-level `read` that embeds it):

- **Phantom received funds**: `output.value()` reports arbitrary satoshis "received" that have no on-chain outpoint — funds reported received that are not spendable, the direct analog of `claimRoyalties` reporting a claimable balance the contract can never actually hold/pay.
- **Spend-path denial of service**: a single malformed `ReceivedOutput` inside the `inputs` vec of `SignableTransaction::new` causes `multisig` to return `None` (send.rs:278), bricking the transaction even though all other inputs are valid, and `NotEnoughFunds`-style accounting (send.rs:175, 215-221) counts the phantom `input_sat` toward covering payments, so the wallet can be made to commit honest inputs to a transaction that can never be signed.

This is not a documented-misuse issue: `read`/`write`/`serialize` are the type's own public round-trip API, and nothing in the type documentation tells callers they must re-verify offset↔script consistency after deserialization — an invariant `scan_transaction` enforces but `read` silently drops.

### Likelihood Explanation
Any pipeline that round-trips `ReceivedOutput`s through `serialize`/`read` (storage, network relay of scanned outputs, recovery from exported output lists) and accepts bytes from a less-trusted party can be fed inconsistent outputs. The malformed bytes decode successfully — `read_F`, `TxOut::consensus_decode`, and `OutPoint::consensus_decode` all succeed on well-formed encodings of malicious values — so the corrupted state propagates until it either inflates a balance or fails at `multisig`. Requires no key material, no validator collusion, only control of deserialized bytes.

### Recommendation
Either:

1. Make `ReceivedOutput::read` verify consistency: it needs the scanning key (or the recovered spend key) to check `p2tr_script_buf(key + offset·G) == output.script_pubkey`, returning an error on mismatch — i.e., change the signature to take the group key, or store/verify a commitment binding the fields.
2. Alternatively, move the existing `multisig` consistency check earlier: validate each `ReceivedOutput` in `SignableTransaction::new` rather than at signing-machine construction, so phantom inputs are rejected before `input_sat` accounting and `prevouts` are committed to.

### Proof of Concept
```rust
use k256::{Scalar, ProjectivePoint};
use bitcoin::{TxOut, OutPoint, ScriptBuf, Amount, absolute::LockTime,
              transaction::Version, Transaction, TxIn, Sequence, Witness};
use bitcoin::consensus::encode::serialize;
use bitcoin_serai::wallet::ReceivedOutput;
use frost::curve::Secp256k1;

// An outpoint which never existed on-chain
let fake_outpoint = OutPoint::null();

// A TxOut paying to an arbitrary P2TR-looking script we do NOT control
let fake_txout = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: ScriptBuf::from_bytes(
    // OP_1 <32-byte x-only key not related to any registered offset>
    [&[0x51, 0x20][..], &[0xAAu8; 32][..]].concat()
  ),
};

// Crafted byte stream: offset || TxOut || OutPoint
let mut bytes = Scalar::from(7u64).to_bytes().to_vec();
bytes.extend(serialize(&fake_txout));
bytes.extend(serialize(&fake_outpoint));

// Decodes cleanly — no consistency check
let output = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// Reports 1 BTC "received"
assert_eq!(output.value(), 1_000_000);

// When fed into SignableTransaction::new as a spend input and .multisig(&keys)
// is called, it returns None: p2tr_script_buf(keys.offset(7).group_key())
// != fake_txout.script_pubkey — the reported funds are unspendable and the
// whole transaction (including any honest co-inputs) cannot be signed.
```

Root cause confirmed at `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) — field-by-field decode with no binding — versus the enforcing producers `register_offset`/`scan_transaction` (mod.rs:180-214) and the late, all-or-nothing check in `SignableTransaction::multisig` (networks/bitcoin/src/wallet/send.rs:273-285).

*Caveat*: the in-scope list restricts citable production code to `networks/bitcoin/src` (`crypto.rs`, `wallet/`); the higher-level `Output::read` wrapper in `processor/` that consumes this type was reviewed for context but is outside the citable scope, and the exact upstream call sites feeding untrusted bytes into `ReceivedOutput::read` could not be fully traced within scope — the finding stands on the deserializer itself dropping the invariant its own producers guarantee.
