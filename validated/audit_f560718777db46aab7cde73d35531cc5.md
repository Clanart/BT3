## Title
Unchecked return value of external system-contract call in `ProcessParentBlockHash` (EIP-2935 history storage write) - (File: blockchain/state_processor.go)

### Summary
`ProcessParentBlockHash`, which is invoked on every block during `StateProcessor.InitializeState` to write the parent block hash into the EIP-2935 History Storage system contract, calls `vmenv.Call(...)` and discards the returned error, unlike the sibling function `SystemTxCall` in the same file which explicitly propagates the call error to its caller.

### Finding Description
`ProcessParentBlockHash` builds a synthetic system message targeting `params.HistoryStorageAddress` and executes it via `vmenv.Call`, but ignores the returned `error` (and the returned data) entirely, then unconditionally finalizes state and returns `nil`: [1](#0-0) 

This is called unconditionally for every block once Prague is active, from `InitializeState`: [2](#0-1) 

By contrast, the nearly identical helper `SystemTxCall`, used for AddressBookV2 lifecycle transitions (`ABv2.initialize`, `ABv2.processSystemTransition`), correctly captures and returns the call error to the caller so that the caller can react to failures: [3](#0-2) 
and its callers in `kaiax/valset/impl/transition.go` do check and propagate that error: [4](#0-3) [5](#0-4) 

This is the same bug class flagged in the external report: an external/system call whose return value/success status is not checked, so a failed call is silently treated as if it succeeded and execution proceeds.

### Impact Explanation
If the EIP-2935 history-storage write reverts or otherwise fails for any reason (e.g., the storage contract missing/corrupted at a node, unexpected state at the target address, or a future contract change that adds revert conditions), `ProcessParentBlockHash` still returns `nil` and the block-processing pipeline proceeds as if the parent hash was successfully recorded. Because `header.Root` is computed from `statedb.IntermediateRoot(true)` right after `FinalizeState`/`InitializeState` runs, and this call's failure is silently swallowed, this could allow a block whose history-storage write did not actually happen to still be accepted into the canonical chain, while any state consumer relying on EIP-2935 (`BLOCKHASH`-extended lookups) gets stale/incorrect historical block hash data. It also removes the possibility of the node halting/erroring on this failure the way the analogous `SystemTxCall` path does, an inconsistency that undermines defense-in-depth around system-contract writes during state transition.

### Likelihood Explanation
Likelihood is lower than a directly attacker-triggerable path because inputs to this call (parent hash, fixed gas limit, fixed target address) are protocol-determined rather than attacker-controlled, and under normal conditions the History Storage system contract call should succeed. However, the missing error check is a genuine, reachable code defect on every single block once Prague is enabled, and any future change to the History Storage contract, or any edge case causing the call to revert (e.g., gas metering edge cases, contract not yet installed on certain network states), would be silently masked rather than surfaced — making this a real but conditional risk to state-transition correctness and consensus consistency.

### Recommendation
Mirror `SystemTxCall`'s pattern: capture the `error` returned by `vmenv.Call` in `ProcessParentBlockHash`, log/return it to the caller, and have `InitializeState` (and its own caller `Process`) treat a failed history-storage write as a processing error rather than silently continuing.

### Proof of Concept
1. Deploy/activate Prague fork so `InitializeState` calls `ProcessParentBlockHash` every block.
2. Cause the call to `params.HistoryStorageAddress` to fail (e.g., in a private/test network, remove or corrupt the code at that address, or craft a scenario where the contract reverts).
3. Observe that `ProcessParentBlockHash` still returns `nil`; `Process` and `FinalizeState` continue normally, and the block is finalized/accepted despite the history-storage write never having taken effect.
4. Contrast with the AddressBookV2 write path (`writeTransitionToABv2`/`installAndInitializeABv2`), where an equivalent failure via `SystemTxCall` is correctly detected and returned as an error, halting block processing.

// SystemTxCall executes a system transaction (e.g., state transition contract writes) within the EVM.
func SystemTxCall(
	msg *types.Transaction,
	from common.Address,
	header *types.Header,
	vmenv *vm.EVM,
	statedb vm.StateDB,
	rules params.Rules,
) ([]byte, error) {
	gasLimit := params.UpperGasLimit
	vmenv.Reset(NewEVMTxContext(msg, header, vmenv.ChainConfig()), statedb)
	statedb.AddAddressToAccessList(*msg.To())
	ret, _, err := vmenv.Call(vm.AccountRef(from), *msg.To(), msg.Data(), gasLimit, common.Big0)
	statedb.Finalise(true, true)
	return ret, err
}
