### Title
Front-running `queueNewRewards()`/`donateRewards()` in BaseRewardPool allows theft of newly added rewards - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`)

### Summary
`BaseRewardPool`/`BaseRewardPoolV2._provisionReward()` instantly folds newly added rewards into `rewardPerTokenStored` in proportion to the *current* `totalStaked()` at the moment the call executes. [1](#0-0)  Unlike the Merit Circle codebase referenced in the external report, `MasterMagpie.deposit()`/`withdraw()` have no `MIN_LOCK_DURATION`, cooldown, or timestamp check preventing a user from depositing and withdrawing in immediate succession. [2](#0-1)  This reproduces the exact "front-run distributeRewards()" attack class described in the report.

### Finding Description
`queueNewRewards()` (manager-only) and `donateRewards()` (fully permissionless, callable by any wallet) both route through `_provisionReward()`, which computes:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked();
```
using `this.totalStaked()`, i.e. `IERC20(stakingToken).balanceOf(operator)` at call time. [3](#0-2) [4](#0-3) 

Because `MasterMagpie._deposit()`/`_withdraw()` impose no lock/cooldown for the base (non‑vlMGP/mWomSV) staking flow — an ordinary user calls `deposit()` and later `withdraw()` at any time, limited only by `user.available` [5](#0-4)  — an attacker can:
1. Monitor the mempool for an upcoming `queueNewRewards()` call from a reward manager (or self-trigger via the permissionless `donateRewards()` on a related pool to bait/observe timing).
2. Front-run it with a large `deposit()` of the staking token into the same pool, inflating `totalStaked()` right before the reward injection.
3. Let the manager's/attacker's transaction execute `_provisionReward()`, which credits `rewardPerTokenStored` based on the now-inflated `totalStaked()`, so the attacker's freshly-deposited (undeserving) balance captures a large share of `_amountReward`.
4. Immediately call `withdraw()` to exit, since `earned()` is computed purely from current `balanceOf(_account)` and `rewardPerTokenStored` deltas with no vesting/lock period. [6](#0-5) 

This is functionally identical to the Merit Circle `BasePool`/`AbstractRewards` bug: a pointsPerShare/rewardPerTokenStored surge on each reward-injection call lets a large, freshly-deposited, un-vested stake steal a disproportionate share of the newly distributed reward from the long-term stakers who actually earned it.

### Impact Explanation
This results in direct theft of unclaimed yield: legitimate long-term stakers in the pool lose a portion of every reward distribution to attackers who deposit right before and withdraw right after `queueNewRewards()`/`donateRewards()`, with no time-weighting or vesting to prevent it.

### Likelihood Explanation
Likelihood is high for any pool with meaningfully-sized `queueNewRewards()` injections: reward manager transactions (or public `donateRewards()` calls) are visible in the mempool, deposit/withdraw are permissionless and unlocked for ordinary wallets, and the attack requires only sufficient capital for a temporary deposit — no privileged role, oracle manipulation, or governance is needed.

### Recommendation
Switch to a rate-based/streaming reward release (e.g., Synthetix `StakingRewards`-style `rewardRate` over a duration) instead of crediting the full `_amountReward` into `rewardPerTokenStored` in a single step, and/or introduce a minimum lock/cooldown between deposit and withdrawal (as Merit Circle did by raising `MIN_LOCK_DURATION`) so that a single-block or same-day deposit cannot capture rewards it did not economically earn.

### Proof of Concept
1. Pool `P` has `totalStaked() = 100` and existing long-term stakers.
2. Attacker observes a pending `queueNewRewards(1000, rewardToken)` transaction in the mempool.
3. Attacker front-runs with `MasterMagpie.deposit(P, 900)`, making `totalStaked() = 1000`.
4. `queueNewRewards` executes `_provisionReward()`: `rewardPerTokenStored += 1000 * 1e_dec / 1000` — attacker's 900 tokens (90% of the pool) now entitle them to ~90% of the 1000 reward tokens, despite having staked for zero time.
5. Attacker calls `MasterMagpie.withdraw(P, 900)` (no lock prevents this) and claims via `getReward()`, netting ~900 reward tokens that should have accrued to the original stakers. [7](#0-6) [8](#0-7)

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
