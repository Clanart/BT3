### Title
Path-boundary check in `resolveWithin` uses unanchored `startsWith`, allowing escape to sibling directories that share a name prefix - (File: app/src/lib/path.ts)

### Summary
The invariant broken here mirrors the smart-contract report's core lesson: a "safety check" that looks correct but has a boundary condition that an attacker can walk through. In the Moloch report, the invariant was "tribute tokens always return to the proposer unless the proposal is approved"; the code silently violated it under `emergencyProcessing`. In GitHub Desktop, the invariant is "a resolved file path must always live under the intended repository root before the app treats it as trusted disk content" (used to gate opening files, and to gate what content is read from disk and fed into the Copilot AI session). `_resolveWithin` in `app/src/lib/path.ts` enforces that invariant with a plain string `startsWith` comparison instead of a path-boundary-aware comparison, so a sibling directory whose name happens to be a superset of the root directory's name defeats the check.

### Finding Description
`_resolveWithin` computes the canonicalized real path of both the root and the candidate, then does: [1](#0-0) 

`realResolved.startsWith(realRoot)` is a naive string-prefix test with no separator boundary check. If `realRoot` is `/Users/alice/Documents/GitHub/repo` and a symlink (or `..`-based relative segment) inside the repository resolves to `/Users/alice/Documents/GitHub/repo-secrets/token.txt`, the check passes because the string `"/Users/alice/Documents/GitHub/repo-secrets/token.txt"` starts with `"/Users/alice/Documents/GitHub/repo"` — even though `repo-secrets` is a completely different, sibling directory. The existing unit tests for `resolveWithin` only cover `..`-traversal and single/double-dot symlink escapes back into the same root; they never test the "prefix-but-not-child" sibling case, so this gap is unguarded: [2](#0-1) 

`resolveWithin` is used as the sole safety gate in at least two attacker-reachable, repo-content-driven code paths:
1. Deep-link/"Open in Desktop" file opening — `filepath` comes straight from an untrusted URL/deep link and is checked only for being non-absolute before being resolved and passed to `shell.showItemInFolder`: [3](#0-2) 
2. Merge/rebase/cherry-pick conflict resolution — file paths come from the conflicted files in a cloned/fetched repository (fully attacker-influenced via crafted merge conflicts and symlinked paths) and their contents are read from disk and forwarded into a Copilot AI prompt: [4](#0-3) 

Both callers trust `resolveWithin`'s `null`/non-`null` result as an authoritative "is this inside the repo" answer, but the boundary flaw means a `non-null` (i.e., "safe") result can be returned for content that lives entirely outside the cloned repository, in a sibling directory that merely shares a name prefix.

### Impact Explanation
This falls under "file write or read outside the repo" from an attacker-controlled cloned/fetched repository (conflicted file content is attacker-influenced via a malicious branch merged/rebased by the victim) or an attacker-controlled deep link (the `filepath` query parameter of an `x-github-client://openRepo/...` URL). Depending on which caller is hit:
- Via `buildConflictContext`, arbitrary file content from a sibling directory outside the repo can be silently read and exfiltrated into the Copilot prompt/session (and from there potentially into the AI response shown to the user, or logged/telemetered upstream) — this is disclosure of local files outside the intended sandboxed repo folder.
- Via `openRepositoryFromUrl`, a crafted deep link can cause Desktop to reveal (`shell.showItemInFolder`) a file located in a directory adjacent to, but not part of, the cloned repository, undermining the explicit intent of the `isAbsolute`/`resolveWithin` guard that was added specifically to stop this class of issue.

### Likelihood Explanation
Exploitability depends on the existence of a real, on-disk sibling directory whose name is a superset/prefix of the target repository's directory name (e.g., `repo` vs. `repo-backup`, `repo2`, `repository`). This is a real-world condition, not a contrived one: GitHub Desktop's default clone root places all repositories as siblings under a single parent folder (e.g., `~/Documents/GitHub/`), so users who have cloned multiple related repositories (forks, renamed copies, `<name>` and `<name>-archive`, `<name>` and `<name>2`) are naturally in the vulnerable configuration. The attacker only needs to control repository content (a symlink or crafted merge conflict introducing a path with `..` segments resolving into the sibling) or a link the user clicks — both squarely within the valid impact scope. No local/physical access, admin rights, or pre-existing malware is required.

### Recommendation
Fix the boundary check in `_resolveWithin` to require an exact match or a match followed immediately by the platform path separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(with the platform-appropriate separator for the `posix`/`win32` variants). Add regression tests covering sibling directories that share a name prefix with the root (e.g., root `.../repo` vs. candidate resolving to `.../repo-evil`) to lock in the fix, mirroring the existing symlink-escape tests in `app/test/unit/path-test.ts`.

### Proof of Concept
1. Create `root = /tmp/test/repo` and a sibling `/tmp/test/repo-evil/secret.txt`.
2. Call `resolveWithin('/tmp/test/repo', '../repo-evil/secret.txt')`.
3. `_resolveWithin` normalizes/resolves to `/tmp/test/repo-evil/secret.txt`, then `realpath`s both root and candidate; `realResolved.startsWith(realRoot)` evaluates `"/tmp/test/repo-evil/secret.txt".startsWith("/tmp/test/repo")` → `true`, so the function returns the resolved path instead of `null`, incorrectly treating `secret.txt` (outside the repo) as safely inside it.
4. In `buildConflictContext`, an attacker crafts a branch that, when merged/rebased by the victim, introduces a conflicted "file" path such as `../repo-evil/secret.txt` (or a symlink inside the repo pointing there); `resolveWithin` approves it, `readFile` reads the out-of-repo file, and its contents are embedded in the Copilot prompt sent for automatic conflict resolution — reading a file outside the repository sandbox as a direct consequence of attacker-controlled repository content.
