### Title
Unverified `context` bytes in GET-response cancel flow allow fund-release parameters to diverge from the cryptographically proven state - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
The external report's core issue is that `FirewallConsumerBase` lets arbitrary, non-`msg.data` bytes be handed to a policy as "the call context," creating a mismatch between what is cryptographically/contextually verified and what is actually acted upon. The same pattern exists in `ExtrinsicIntents.onGetResponse`: it decodes the fund-release parameters (`beneficiary`, `tokens`, `commitment`) from `incoming.response.request.context` — an opaque `bytes` field that is never checked by Hyperbridge's core proof-verification path — while the only thing actually proven by the GET response's Merkle/storage proof is the *value at a single storage key* (`_filled[commitment]` being empty).

### Finding Description
`_cancelFromSource` dispatches a `DispatchGet` whose `keys[0]` is derived from `commitment` (the storage slot to prove empty) and whose `context` independently encodes a `WithdrawalRequest{commitment, tokens, beneficiary}`: [1](#0-0) 

When the response returns, `onGetResponse` checks only that the proven value is empty, then blindly trusts `context` to determine who gets paid and how much, with no re-derivation or cross-check against the actual proven storage key or against the escrow ledger's own commitment-to-order binding: [2](#0-1) 

`_withdraw` then transfers funds strictly according to the untrusted `body` (`beneficiary`, `tokens[i].amount`) decoded from that `context`: [3](#0-2) 

The cryptographic guarantee from the ISMP proof only attests that "the storage value at this specific key is empty" — nothing in the Host/Handler layer ties `context` to `keys`, to the `commitment` used for the proof, or to the amounts actually escrowed under that `commitment`. This is structurally identical to the report's finding: `firewallProtectedCustom`/`firewallProtectedSig` let a consumer pass unrelated bytes to a policy as if it were `msg.data`, so the policy's decision is made on data that was never part of the verified call. Here, `onGetResponse`'s "policy" (the withdrawal engine `_withdraw`) is fed `context`, which was never part of the verified state, only of the *user-submitted request envelope* at dispatch time.

`_cancelFromSource`'s only defense is checking `_orders[commitment][token] != 0` for tokens listed in the caller-supplied `order` argument, and that `order.user == msg.sender` — it does not recompute `commitment` from `order` via a canonical hash function within this file, so nothing here proves that the `order` struct (and thus the `tokens`/`beneficiary` embedded into `context`) actually corresponds to the escrow record at `commitment`. I could not verify from the code reviewed whether the external wrapper function that calls `_cancelFromSource` (in `evm/src/apps/IntentGatewayV2.sol`, not fully inspected due to iteration limits) independently enforces `commitment == keccak256(abi.encode(order))` before invoking this internal function — this is the one open question that determines whether the gap is only architectural (relying on off-chain discipline, as with the firewall modifiers) or directly exploitable end-to-end from this contract alone.

### Impact Explanation
If the external `commitment`/`order` binding is not enforced, an attacker could supply a legitimately-escrowed `commitment` value alongside an `order` struct whose `inputs`/`user` fields differ from the original order that created that escrow (as long as `_orders[commitment][token] != 0` for at least one listed token), causing `context` to encode an inflated amount or attacker-controlled beneficiary. On GET-response delivery, `_withdraw` would then release the wrong amount to the wrong beneficiary while only a narrow, unrelated fact (`_filled` slot emptiness) was ever cryptographically proven — a direct instance of "false state acceptance" and "wrong beneficiary or amount" fund loss, matching the bounty's core impact categories.

### Likelihood Explanation
Even absent full exploitability at the entry-point layer, this remains a real design-level violation of the invariant that only cryptographically proven data should drive fund movement: `context` is dispatcher-time-supplied bytes carried through Hyperbridge's generic GET-response infra without protocol-level integrity binding to the proof's subject key or to the escrow's authoritative commitment-to-order mapping. This mirrors exactly the report's flagged risk of confusion between what a modifier/callback claims is "the call context" versus what is truly bound to the verified execution, and Hyperbridge's own onchain-firewall analog was rated valid and fixed for the identical class of confusion.

### Recommendation
- In `_withdraw`/`onGetResponse`, do not trust `context.tokens`/`context.beneficiary` for amounts; instead re-derive or store the authoritative withdrawal parameters at `_orders[commitment]` time when the order was placed, and use `context` only to identify `commitment`, not amounts/beneficiary.
- At the external cancel entry point, require `commitment == keccak256(abi.encode(order))` (or equivalent canonical order hash) before allowing `_cancelFromSource` to proceed, closing any gap between the caller-supplied `order` and the escrow ledger.
- Document that `DispatchGet.context` is unauthenticated, dispatcher-supplied data — analogous to documenting `firewallProtectedCustom`'s risk — and audit every `onGetResponse`/`onAccept` handler in the repo for the same pattern of trusting `context`/`body` fields as if they were proof-verified.

### Proof of Concept
Conceptual (blocked on unverified external entry-point validation):
1. User A places an order, escrowing tokens under `commitment = C` (`_orders[C][tokenX] = 100`).
2. Attacker (or anyone) calls the external cancel-from-source function with `commitment = C` but supplies an `order` argument whose `order.inputs` amount for `tokenX` is inflated (e.g., 100 → 1000) and/or whose `order.user` is set to the attacker's address, while `order.destination`/`order.deadline` still make `_orders[C][tokenX] != 0` pass and `options.height > order.deadline`.
3. Because `_cancelFromSource` never recomputes `C` from `order`, the constructed `context = abi.encode(WithdrawalRequest{C, inflatedTokens, attackerBeneficiary})` is accepted and dispatched.
4. Once the destination `_filled[C]` slot is proven empty, `onGetResponse` decodes this attacker-influenced `context` and calls `_withdraw`, transferring the inflated amount to the attacker beneficiary — `_orders[C][tokenX]` underflows/reverts only if `escrowed - amount` would underflow, but for exact-boundary or under-escrowed tokens this still allows fund misdirection to the wrong beneficiary at the correct amount. [4](#0-3)

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
