### Title
Unbounded Unicode Normalization on Keychain `add_key`/`add_private_key` Causes RPC-Triggered CPU Denial of Service - (File: `chia/util/keychain.py`)

### Summary
The `mnemonic_to_seed()` function performs an unbounded, unauthenticated-length Unicode `NFKD` normalization on a caller-supplied string before any length or word-count validation occurs, directly mirroring the CWE-770 pattern described in the Frigate advisory (costly `secure_filename()`/NFKD normalization on unvalidated length input). In Chia, this function is reachable from the daemon/keychain RPC `add_key` / `add_private_key` commands with a fully attacker-controlled string.

### Finding Description
`mnemonic_to_seed()` in `chia/util/keychain.py` (lines 154-168) is:
```python
def mnemonic_to_seed(mnemonic: str) -> bytes:
    if not any(ord(c) >= 128 for c in mnemonic):
        mnemonic = mnemonic_from_short_words(mnemonic)
    salt_str: str = "mnemonic"
    salt = unicodedata.normalize("NFKD", salt_str).encode("utf-8")
    mnemonic_normalized = unicodedata.normalize("NFKD", mnemonic).encode("utf-8")
    seed = pbkdf2_hmac("sha512", mnemonic_normalized, salt, 2048)
``` [1](#0-0) 

The length/format validation (`mnemonic_from_short_words`, which enforces mnemonic word counts of `{12,15,18,21,24}`) is **only** executed when the input is pure ASCII (`ord(c) < 128` for all characters). If the caller supplies any non-ASCII character (e.g. a single very long Unicode string composed of compatibility-decomposable code points), that validation branch is skipped entirely and the raw, unbounded string is passed straight into `unicodedata.normalize("NFKD", mnemonic)` — the exact costly operation flagged in the external report.

This function is called directly, with no upstream length limit, from `Keychain.add_key()`:
```python
def add_key(self, mnemonic_or_pk: str, label: str | None = None, private: bool = True) -> PrivateKey | G1Element:
    if private:
        seed = mnemonic_to_seed(mnemonic_or_pk)
        entropy = bytes_from_mnemonic(mnemonic_or_pk)
``` [2](#0-1) 

`mnemonic_to_seed` is invoked *before* `bytes_from_mnemonic` (which would reject overly long/malformed inputs), so the costly normalization always runs first on the raw attacker string.

This is reachable via the daemon RPC keychain command handler:
```python
async def add_key(self, request: dict[str, Any]) -> dict[str, Any]:
    ...
    mnemonic_or_pk = request.get("mnemonic_or_pk", None)
    ...
    key = self.get_keychain_for_request(request).add_key(mnemonic_or_pk, label, private)
``` [3](#0-2) 

and the `add_private_key`/`add_key` daemon commands are exposed as standard WS-RPC commands: [4](#0-3) 

Additionally, `KeychainProxy.add_key()` (used by services proxying to the daemon) also calls `mnemonic_to_seed(mnemonic_or_pk)` directly on the response path: [5](#0-4) 

None of these code paths impose a length limit on `mnemonic_or_pk` prior to the normalization call, so a caller able to reach the daemon RPC (an authorized local RPC caller per the allowed "daemon/keychain/RPC authorization" surface) can submit a multi-megabyte non-ASCII string and force the daemon process into an expensive single-threaded Unicode decomposition pass, exactly as in the original Frigate report.

### Impact Explanation
`unicodedata.normalize("NFKD", ...)` on a very large string (e.g., millions of decomposable code points) is CPU-intensive and blocks the running event loop/process. Since the daemon handles all keychain operations for every Chia service (wallet, farmer, full node, harvester) synchronously per request, a single malicious `add_key`/`add_private_key` RPC call with a huge crafted Unicode string can hang the daemon process, halting keychain operations and any other RPC traffic multiplexed through the same daemon connection — an application-level denial of service, consistent with the "spend-triggered transaction-processing halt" class of impact allowed by scope (here, RPC-triggered process halt for the local Chia RPC surface).

### Likelihood Explanation
Likelihood is high for any caller with access to the daemon/keychain RPC interface (a caller within the allowed "daemon/keychain/RPC authorization" surface): the vulnerable code path requires no valid mnemonic, key, or prior authentication beyond daemon RPC access, and the payload construction (a long string containing at least one non-ASCII character) is trivial.

### Recommendation
Enforce a strict maximum length (and character-set sanity check) on `mnemonic_or_pk` at the earliest point of entry — in `KeychainServer.add_key()`, `Keychain.add_key()`, and `mnemonic_to_seed()` itself — before performing `unicodedata.normalize`. Reject any input exceeding the expected mnemonic length (e.g., well under a few hundred characters) prior to any Unicode processing, mirroring the mitigation referenced in the report (Django's filename length cap commit).

### Proof of Concept
1. Establish a WebSocket connection to the Chia daemon RPC (as any RPC-authorized caller).
2. Send:
```json
{
  "command": "add_key",
  "data": {
    "mnemonic_or_pk": "℀℀℀℀℀℀... (repeated ~5,000,000 times)",
    "private": true
  }
}
```
3. Because the string contains a non-ASCII character, `mnemonic_from_short_words` validation in `mnemonic_to_seed` is skipped, and `unicodedata.normalize("NFKD", mnemonic)` executes on the full multi-million character string, consuming CPU and blocking the daemon event loop until it completes.

def mnemonic_to_seed(mnemonic: str) -> bytes:
    """
    Uses BIP39 standard to derive a seed from entropy bytes.
    """
    # If there are only ASCII characters (as typically expected in a seed phrase), we can check if its just shortened
    # 4 letter versions of each word
    if not any(ord(c) >= 128 for c in mnemonic):
        mnemonic = mnemonic_from_short_words(mnemonic)
    salt_str: str = "mnemonic"
    salt = unicodedata.normalize("NFKD", salt_str).encode("utf-8")
    mnemonic_normalized = unicodedata.normalize("NFKD", mnemonic).encode("utf-8")
    seed = pbkdf2_hmac("sha512", mnemonic_normalized, salt, 2048)

    assert len(seed) == 64
    return seed
```
