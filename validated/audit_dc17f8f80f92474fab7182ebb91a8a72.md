Based on the investigation, I found a concrete local analog of the reported bug class in `EvmHost.sol`'s native-token fee payment path, rather than in `NestedWallet.sol` (which doesn't exist in this repo).

### Title
Excess native ETH sent to `EvmHost.dispatch()`/`dispatch(DispatchGet)`/`fundRequest()` is silently absorbed by the contract instead of refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all accept `msg.value` and swap the *entire* `msg.value` for an exact amount of fee token via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`. Uniswap V2's `swapETHForExactTokens` refunds any unspent ETH to `msg.sender` of the swap call — which is `EvmHost` itself, not the original external caller who sent the transaction. Any ETH sent above what's needed to acquire the exact fee amount is therefore retained inside `EvmHost` with no accounting and (in the code sections examined) no exposed function to reclaim or refund it to the original sender.

### Finding Description
In all three functions, the pattern is identical: [1](#0-0) [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` is called with the caller's full `msg.value` but only needs to spend enough to acquire `post.fee` / `get.fee` / `amount` units of fee token. The Uniswap V2 router's `swapETHForExactTokens` implementation always refunds the leftover ETH back to whoever called it — in this call chain that is `EvmHost`, not the original `_msgSender()` who funded the transaction. Compare this to the sibling `IntentGatewayV2.placeOrder`/`_fillSameChain`/`_fillCrossChain` functions in this same codebase, which meticulously track a local `msgValue` variable, decrement it as it's spent, and explicitly refund any leftover to `msg.sender` at the end: [4](#0-3) [5](#0-4) 

`EvmHost.dispatch`/`fundRequest` have no equivalent refund step — any ETH beyond what the swap consumes simply becomes stranded in the host contract's balance.

### Impact Explanation
This is a genuine, unconditional loss-of-funds bug for any caller who overestimates the ETH needed to cover a POST/GET dispatch fee or a `fundRequest` top-up (e.g., due to normal slippage-safety margins, price movement between quote and execution, or simply passing a round `msg.value`). The overpaid ETH is not reverted (so the transaction doesn't fail the way `NestedWallet.executeCall` did), but it is also not returned to the payer — it is absorbed into `EvmHost`'s balance with no on-chain accounting of whose funds they were, and (from the sections reviewed) no user-callable path to recover it. This directly matches the bounty's "stealing or loss of funds" impact category since it moves value away from the rightful owner without their consent.

### Likelihood Explanation
Likelihood is high for the loss to occur incidentally, since any caller providing `msg.value` even slightly above what's strictly required (which is the common case — exact fee amounts require an off-chain quote+chain-state race that's rarely hit exactly) will lose the difference. It requires no malicious actor, relayer, or governance involvement — an ordinary user calling `dispatch()` or `fundRequest()` with native ETH triggers it.

### Recommendation
Track a local `msgValue` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, similar to `IntentGatewayV2`, and explicitly refund any unspent native ETH to `_msgSender()` after the swap completes (rather than relying on the router's refund-to-caller behavior, which returns funds to `EvmHost` instead of the original payer).

### Proof of Concept
1. A user calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` (in fee-token units) is actually satisfiable by swapping much less than 1 ether of the current price.
2. `IUniswapV2Router02.swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)` spends only what's needed and refunds the remainder ETH to `msg.sender`, i.e., to `EvmHost`.
3. `EvmHost`'s native balance increases by the refunded amount with no corresponding state update; the user who sent 1 ether receives no refund and has no way to reclaim the surplus.
4. Repeating this across many dispatches/fundings accumulates stranded ETH inside `EvmHost` with no accounting of it.

**Caveat:** I could not fully review the entirety of `EvmHost.sol` within the tool-call budget — it's possible there is a governance-only sweep/withdraw function elsewhere in the file that reclaims this stray ETH for the protocol treasury (which would reduce this to a "funds go to protocol instead of user" issue rather than complete loss). I did not find such a function in the sections I inspected (grep for `receive()`, `withdraw`, `address(this).balance` only matched the dispatch/fundRequest functions themselves). This should be verified against the full file before treating the finding as final.
