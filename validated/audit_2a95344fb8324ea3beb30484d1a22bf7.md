### Title
Vacuous torsion check in `Point::from_bytes` accepts non-prime-order Ed448 points fed to `read_G` - (File: crypto/ed448/src/point.rs)

### Summary
`Point::is_torsion_free` computes `(*self * (Scalar::ZERO - Scalar::ONE)) + self`, i.e. `(-P) + P`, which is the identity for every point on the curve. The check therefore always returns true, so `GroupEncoding::from_bytes` accepts points with a nonzero torsion component. Because `Ciphersuite::read_G` (and `Curve::read_G`) rely on `from_bytes` for canonical decoding, any untrusted Ed448 point read via `Ed448::read_G` — PedPoP `Commitments::read`, FROST preprocess/share decoding, `DLEqProof::read`, `SchnorrSignature::read`, `ThresholdKeys::read` — may carry an order-4 torsion component while being treated as a prime-order group element.

### Finding Description
In `crypto/ed448/src/point.rs:294-298`:

```rust
impl Point {
  fn is_torsion_free(&self) -> Choice {
    ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
  }
}
```

`Scalar::ZERO - Scalar::ONE` is the scalar `-1` modulo the group order `l`. So the expression is `P*(-1) + P = identity` for **every** `P`, including points with a torsion component (Ed448 has cofactor 4). A correct check must multiply by the subgroup order `l` (or the cofactor and check for identity). As written, `CtOption::new(point, not_negative_zero & point.is_torsion_free())` at `point.rs:316` only rejects negative-zero encodings; torsion points deserialize successfully. The negative sign encoding and canonicity are still enforced by `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-100`), but that check re-encodes the same torsion-bearing point and does not enforce subgroup membership.

Reachability: an unprivileged counterparty supplies these bytes in any Ed448 ciphersuite context — e.g., PedPoP `Commitments::read` (`crypto/dkg/pedpop/src/lib.rs:110-128`), FROST preprocess `Commitments::read` (`crypto/frost/src/nonce.rs:133-139`), or signature shares — since `read_G` only bans the identity in `crypto/frost/src/curve/mod.rs:125-131`, not torsion.

### Impact Explanation
Torsion components corrupt every downstream group equation while remaining undetected:

- **DKG share verification (PedPoP):** a malicious participant's commitments `Am[j]` can include a torsion offset `T`. Honest parties' share-verification `s_i·G == Σ i^j·Am[j]` is checked against the prime-order component, but the resulting `verification_share`/group key differs from a prime-order point by `T`, corrupting the established group key.
- **FROST verification equation:** `verify` checks `z·G == R + c·A`. If `R` or `A` carries a torsion term, shares verify against a point off the prime-order subgroup, producing signatures whose `R` is not in the prime-order group — invalid under RFC 8032-style verification (which checks `[4]R` consistency / canonical subgroup membership), i.e. funds/signatures reported valid by the threshold that are not actually valid, or honest shares blamed as invalid.
- **Small-subgroup confinement:** with cofactor 4, an attacker-controlled commitment `A + T` lets them steer `R` across 4 cosets while satisfying the prime-order check, the classic torsion-component attack on Schnorr-type verification.

### Likelihood Explanation
Any unprivileged party that can send a PedPoP commitments message, a FROST preprocess, a signature share, or any `read_G`-decoded Ed448 point reaches this path — no collusion or validator status required within the library's own trust model. Crafting the input is trivial: take a valid encoding and add a known order-2 or order-4 point (e.g., the "old generator" point used in the `torsion` test at `point.rs:352-368`, which is exactly the kind of point `is_torsion_free` should reject but provably cannot).

### Recommendation
Replace the vacuous check with a real subgroup-membership test, e.g. multiply by the prime subgroup order `l` and require identity, or equivalently multiply by the cofactor 4 and reject if the result is identity for prime-order inputs' complement:

```rust
fn is_torsion_free(&self) -> Choice {
  // l = group order; check l*P == 0 by testing P against the prime-order subgroup
  // Cheapest correct check for cofactor 4: reject if 4*P has torsion, i.e.
  // ensure (self * Scalar::from(4)) is not identity except when self is identity-free,
  // or multiply by l directly.
  (*self * Scalar::from(4u64)).is_identity().not() // placeholder — use l*P == identity
}
```

The correct form is `(*self * MODULUS_as_scalar).is_identity()` where the multiplier is the group order `l` (i.e., `l·P == identity`), not `-1`. Also add a test asserting `Point::from_bytes` rejects a torsion point encoding end-to-end.
