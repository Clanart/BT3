### Title
Unauthenticated OP_RETURN operator identity in payout transactions allows any unprivileged broadcaster to frame an operator for a payout it never funded - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` builds the Bitcoin payout transaction that fronts a Citrea withdrawal with an `OP_RETURN` output carrying an `operator_xonly_pk` value, but this value is never bound by any signature. [1](#0-0)  The verifier network later reads this self-declared, unsigned field directly out of the chain and treats it as ground truth for "who paid the withdrawal" [2](#0-1) , exactly mirroring the FlasherFTM bug class where an unauthenticated `initiator`/`sender` field is trusted as an authorization signal.

### Finding Description
`create_payout_txhandler` only binds the user's taproot key-spend signature (`user_sig`) to input 0; the identical `user_sig` value is accepted by the e2e test harness against two different operators' payout transactions with two different `operator_xonly_pk` OP_RETURN payloads in the same test run [3](#0-2) , which proves the OP_RETURN output (index 2) is *not* covered by the user's signature. The `operator_xonly_pk` is therefore attacker-controllable free-form data appended by whoever constructs and broadcasts the transaction.

The verifier's `update_finalized_payouts` extracts this unauthenticated value straight from the on-chain OP_RETURN and stores it in the `withdrawals` table as `payout_payer_operator_xonly_pk`: [4](#0-3) [5](#0-4) 

The operator side then trusts this DB value as authoritative proof-of-payment: `validate_payer_is_operator` only checks whether the stored `payer_xonly_pk` equals the local operator's own key, and if so proceeds as though this operator genuinely fronted the withdrawal: [6](#0-5) . This directly feeds `PayoutCheckerTask::run_once`, which calls `handle_finalized_payout` and marks the payout handled, initiating the reimbursement/kickoff flow: [7](#0-6) . Separately, `is_kickoff_malicious` only cross-checks that the OP_RETURN operator matches the kickoff's own operator key — it never verifies that the named operator actually authorized or produced the OP_RETURN output — so a framed kickoff sails through as non-malicious: [8](#0-7) .

Binding broken (equality that should hold but doesn't):
`operator credited for a payout == operator that actually broadcast/funded the payout` — instead the system enforces only `operator credited == whatever xonly_pk byte-string appears in an unsigned OP_RETURN output`, which any third party controls.

### Impact Explanation
Since `input_signature` (`user_sig`), the withdrawal UTXO, and the required payout output (script_pubkey/amount) are all public information originating from the Citrea withdrawal request (the on-chain data any operator needs to front the withdrawal, per the code comments "committed in Citrea side, with the signature given to operators off-chain"), and operator identities (`xonly_pk`) are public protocol configuration, any external, unauthenticated party can construct and broadcast this exact Bitcoin transaction directly — completely bypassing the operator's gRPC `withdraw`/`internal_withdraw` endpoints and their signature checks [9](#0-8)  — while writing an arbitrary (real, targeted) operator's `xonly_pk` into the OP_RETURN. This causes the verifier network and the targeted operator's automation to misattribute the fronted payout to that operator, triggering `handle_finalized_payout`/kickoff and ultimately reimbursement from the bridge vault to an operator that never funded the withdrawal. This matches the Critical impact category "an operator reimbursed for a payout it never funded" and constitutes a misattributed reimbursement — a custody/attribution binding is broken by an unprivileged party with no key, role, or authorization.

### Likelihood Explanation
Exploitation requires no special role: it only needs public withdrawal data (UTXO, user signature, output requirements) that already circulates for the purpose of letting any operator front the payment, plus the target operator's public key. No verifier/operator/aggregator secret or role is needed to broadcast the crafted Bitcoin transaction. The only non-trivial requirement is that the attacker fund the payout output amount themselves (they pay the user out of pocket), which is a cost but not a barrier for an attacker aiming to disrupt a specific operator's round bookkeeping or to test/probe the reimbursement pipeline.

### Recommendation
Do not derive payer attribution from an unsigned OP_RETURN output. Instead:
1. Have the operator's own signature cover the OP_RETURN output (e.g., include it under the taproot sighash, or require a second signature from the operator over the whole transaction) so the identity claim is cryptographically bound to the party that actually broadcasts/funds the payout.
2. In `update_finalized_payouts` / `validate_payer_is_operator`, verify that the claimed `operator_xonly_pk` is backed by a valid signature from that operator over the payout transaction (or over the specific withdrawal index + move-to-vault txid), not merely present as free-form OP_RETURN bytes.
3. Reject payout transactions whose OP_RETURN operator claim cannot be cryptographically verified, rather than silently accepting `None`/spoofed values as valid attribution.

### Proof of Concept
1. Attacker observes a pending Citrea withdrawal: withdrawal UTXO, `output_script_pubkey`/`output_amount` (payout to user), and the associated `input_signature` (public/off-chain data intended for any operator to front the payout), plus a target operator's public `xonly_pk`.
2. Attacker calls `create_payout_txhandler(input_utxo, output_txout, target_operator_xonly_pk, user_sig, network)` locally (or replicates its logic) — this only needs the public inputs above — producing a fully valid, broadcastable payout transaction with the target operator's `xonly_pk` embedded in the unsigned OP_RETURN output: [1](#0-0) .
3. Attacker funds and broadcasts this transaction on Bitcoin, paying the user themselves.
4. The verifier network's `update_finalized_payouts` scans the block, extracts `target_operator_xonly_pk` from the OP_RETURN, and records it as `payout_payer_operator_xonly_pk` for that withdrawal: [4](#0-3) .
5. The target operator's `PayoutCheckerTask` sees the unhandled payout, `validate_payer_is_operator` matches its own key, and it proceeds through `handle_finalized_payout` to kick off the reimbursement flow for a payment it never made or authorized: [6](#0-5) [10](#0-9) .

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        );

        // if verification address is set in config, check if verification signature is valid
        if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
            let verification_signature = params

                .map(|sig| {
                    PrimitiveSignature::from_str(&sig).map_err(|e| {
                        Status::invalid_argument(format!("Invalid verification signature: {e}"))
                    })
                })
                .transpose()?;
            // check if verification signature is provided by aggregator
            if let Some(verification_signature) = verification_signature {

                        input_outpoint,

                input_signature,
                input_outpoint,
                output_script_pubkey,
                output_amount,
