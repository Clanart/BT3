### Title
Fixed per-opcode `computationCost` for data-size-scaling opcodes (SHA3/KECCAK256, CODECOPY, EXTCODECOPY, CALLDATACOPY, RETURNDATACOPY, MCOPY, CREATE/CREATE2, LOG0-4) enables real-execution-time DoS despite Kaia's computation-cost throttle - ([File: blockchain/vm/gas_table.go])

### Summary
Kaia implements its own analog of the wasmvm "gas benchmarking" mechanism: an `opcodeComputationCostSum` that is compared against `ComputationCostLimit` specifically to bound the *real wall-clock execution time* of a transaction, independent of gas. [1](#0-0)  Each opcode's `computationCost` is meant to "approximate execution time," per the field's own doc comment. [2](#0-1)  However, several opcodes whose actual CPU cost scales linearly with the size of data they process (memory copy / hashing opcodes) are assigned a **fixed constant** `computationCost`, while their gas cost correctly scales with data size via `dynamicGas`. This exactly mirrors the reported wasmvm bug class: benchmarked/static costs that don't track real per-operation work, letting a contract consume far more actual CPU time than the throttle assumes.

### Finding Description
The interpreter loop accumulates `operation.computationCost` — a constant fixed at jump-table construction time — once per executed opcode, and compares the running sum to `ComputationCostLimit` to abort long-running executions: [3](#0-2) 

For SHA3/KECCAK256, the *gas* dynamic cost correctly scales with the number of words hashed (`Sha3WordGas` per word) [4](#0-3) , but the opcode's `computationCost` entry is the flat constant `params.Sha3ComputationCost` regardless of how many bytes/words are hashed: [5](#0-4) 

The same pattern holds for the memory-copy opcodes (CALLDATACOPY, CODECOPY, MCOPY, EXTCODECOPY, RETURNDATACOPY), whose gas cost is computed by `memoryCopierGas`, scaling with `words * params.CopyGas`: [6](#0-5)  while their jump-table `computationCost` fields are fixed constants such as `CallDataCopyComputationCost = 100`, `CodeCopyComputationCost = 898`, `ExtCodeCopyComputationCost = 1000`, `ReturnDataCopyComputationCost = 40` [7](#0-6)  and are wired into the jump table without any size-dependent scaling: [8](#0-7) 

Likewise CREATE/CREATE2 use `pureMemoryGascost`/`gasCreate2` for gas (scaling with init-code size) [9](#0-8)  but a flat `CreateComputationCost` in the jump table [10](#0-9) , and LOG0-4 similarly use `makeGasLog` scaling with log data size for gas [11](#0-10)  but a constant `Log0ComputationCost` etc. for the time-throttle accounting [12](#0-11) .

Because `CopyGas`/`Sha3WordGas` are cheap per word relative to the actual memcpy/keccak CPU cost of large buffers, a contract can cheaply (in gas terms) invoke these opcodes over very large memory regions (bounded only by the block gas limit and memory-expansion quadratic gas cost, which permits multi-hundred-KB buffers), each call only incrementing the computation-cost sum by the fixed per-opcode constant instead of a value proportional to bytes processed. The real CPU time consumed by hashing/copying large buffers is therefore drastically underestimated by the throttle intended to bound it, exactly reproducing the "operations take significantly more time than benchmarks indicated" class of bug from the advisory.

### Impact Explanation
Any unprivileged transaction sender can deploy and call a contract that repeatedly executes SHA3/CODECOPY/EXTCODECOPY/MCOPY/CREATE2 (or LOGs) over large memory regions within a single transaction/block. Because the per-opcode `computationCost` used for the time-based throttle does not scale with buffer size while gas cost is comparatively cheap per byte, the transaction can consume real execution time far exceeding what `ComputationCostLimit` is designed to bound, causing block processing to take substantially longer than expected — a temporary chain-wide DoS during that block's execution/validation, matching CWE "Improper Restriction of Power Consumption."

### Likelihood Explanation
High reachability: this only requires deploying ordinary EVM bytecode and sending a normal transaction (no special privileges), using standard opcodes (SHA3, CODECOPY, MCOPY, CREATE2, LOG) that are always available in the instruction set. The gas cost of the exploit is bounded by the block gas limit, so an attacker only needs to pay normal transaction fees.

### Recommendation
Scale the `computationCost` charged for SHA3/KECCAK256, CALLDATACOPY, CODECOPY, EXTCODECOPY, RETURNDATACOPY, MCOPY, CREATE/CREATE2, and LOG0-4 proportionally to the number of words/bytes processed (mirroring their `dynamicGas` functions), similar to how precompiles like `bigModExp` already scale `computationCost` with input-derived gas (`gas/100 + BigModExpBaseComputationCost`) [13](#0-12) . Re-benchmark actual CPU cost per byte for these operations and add a per-word/per-byte `computationCost` component analogous to `dynamicGas`, then re-validate that `OpcodeComputationCostLimit`/`OpcodeComputationCostLimitCancun` still bound worst-case per-tx execution time under the corrected model.

### Proof of Concept
1. Deploy a contract with a fallback/entry function containing a loop (bounded by JUMP/JUMPI, itself cheap in both gas and computationCost) that:
   - Expands memory to a large size (e.g., pushes memory to tens/hundreds of KB, amortizing quadratic memory gas across many calls or reusing an already-expanded memory region), then
   - Repeatedly executes `KECCAK256` (SHA3) or `CODECOPY`/`MCOPY` over that large memory region.
2. Because gas cost per word (`Sha3WordGas`/`CopyGas`) is cheap, many such large-buffer operations fit inside the block gas limit.
3. Each SHA3/CODECOPY/MCOPY call adds only the fixed `Sha3ComputationCost`/`CodeCopyComputationCost`/etc. to `evm.opcodeComputationCostSum`, per [1](#0-0) , regardless of the actual buffer size hashed/copied.
4. The transaction executes without hitting `ErrOpcodeComputationCostLimitReached`, yet its real CPU time (proportional to total bytes hashed/copied) significantly exceeds the time budget the `ComputationCostLimit` mechanism was designed to enforce, delaying block processing for all nodes validating it.

func memoryCopierGas(stackpos int) gasFunc {
	return func(evm *EVM, contract *Contract, stack *Stack, mem *Memory, memorySize uint64) (uint64, error) {
		// Gas for expanding the memory
		gas, err := memoryGasCost(mem, memorySize)
		if err != nil {
			return 0, err
		}
		// And gas for copying data, charged per word at param.CopyGas
		words, overflow := stack.Back(stackpos).Uint64WithOverflow()
		if overflow {
			return 0, errGasUintOverflow
		}

		if words, overflow = math.SafeMul(toWordSize(words), params.CopyGas); overflow {
			return 0, errGasUintOverflow
		}

		if gas, overflow = math.SafeAdd(gas, words); overflow {
			return 0, errGasUintOverflow
		}
		return gas, nil
	}
}

func makeGasLog(n uint64) gasFunc {
	return func(evm *EVM, contract *Contract, stack *Stack, mem *Memory, memorySize uint64) (uint64, error) {
		requestedSize, overflow := stack.Back(1).Uint64WithOverflow()
		if overflow {
			return 0, errGasUintOverflow
		}

		gas, err := memoryGasCost(mem, memorySize)
		if err != nil {
			return 0, err
		}

		if gas, overflow = math.SafeAdd(gas, params.LogGas); overflow {
			return 0, errGasUintOverflow
		}
		if gas, overflow = math.SafeAdd(gas, n*params.LogTopicGas); overflow {
			return 0, errGasUintOverflow
		}

		var memorySizeGas uint64
		if memorySizeGas, overflow = math.SafeMul(requestedSize, params.LogDataGas); overflow {
			return 0, errGasUintOverflow
		}
		if gas, overflow = math.SafeAdd(gas, memorySizeGas); overflow {
			return 0, errGasUintOverflow
		}
		return gas, nil
	}
}
