### Title
Quadratic CPU denial of service in Lagrange `ThresholdKeys` deserialization - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts attacker-controlled `t` and `n` values up to `u16::MAX` and then calls `ThresholdKeys::new`, which calculates the group key by evaluating a Lagrange interpolation factor for every participant `1..=t`. Each interpolation factor loops over all `t` included participants, making deserialization `O(t²)` in field arithmetic. An untrusted serialized key with `t = n = 65535` therefore triggers more than 4 billion inner-loop iterations from an input only a few megabytes in size. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The serialized `ThresholdKeys` format reads attacker-supplied `t`, `n`, participant index `i`, an interpolation selector, one secret-share scalar, and `n` verification-share points. [4](#0-3) 

When the selector is `1`, deserialization selects `Interpolation::Lagrange`. [5](#0-4) 

`ThresholdKeys::new` then constructs `t` as participants `1..=params.t()` and maps every participant through `interpolation_factor`. [6](#0-5) 

For Lagrange interpolation, each `interpolation_factor` call iterates over every participant in `included`, performing field multiplication for each and an inversion at the end. [7](#0-6) 

Consequently, the group-key calculation has quadratic complexity in `t`: `t` outer interpolation factors multiplied by `t` inner-loop steps. With the maximum attacker-controlled value `t = n = 65535`, this is approximately `4.29 billion` field operations plus `65535` scalar inversions. [6](#0-5) [8](#0-7) 

### Impact Explanation
An unprivileged party that can supply serialized `ThresholdKeys` bytes can cause a disproportionate CPU denial of service. The required input consists of roughly `65535` encoded group elements plus a small header and scalar, while the resulting computation performs billions of field operations. This matches the malformed-input-to-service-disruption class of the external report, mapped to Serai’s deserialization path. [1](#0-0) [6](#0-5) 

Because the expensive computation occurs during `ThresholdKeys::new`, the resource exhaustion happens before a caller can reject the struct for policy reasons. [9](#0-8) 

### Likelihood Explanation
The issue is reachable whenever `ThresholdKeys::read` is exposed to persisted, network-delivered, or otherwise untrusted bytes. It does not require invalid cryptography, signature forgery, leaked secrets, or control over participant indexes beyond setting `t`, `n`, `i`, and selecting Lagrange interpolation. The main constraint is that the stream must contain enough parseable field and group encodings for the declared `n`, but that input remains small relative to the quadratic work it triggers. [4](#0-3) 

### Recommendation
Reject or bound expensive Lagrange `ThresholdKeys` deserializations before calling `ThresholdKeys::new`. Prefer an explicit maximum threshold/participant count for untrusted input, or derive the group key with a non-quadratic construction. At minimum, perform the size and interpolation checks before reading the `n` verification shares and avoid evaluating `t` separate `O(t)` Lagrange factors during construction. [10](#0-9) [6](#0-5) 

### Proof of Concept
Conceptually construct a serialized `ThresholdKeys` object for an in-scope ciphersuite as follows:

1. Write the correct curve-ID length and `C::ID` expected by `ThresholdKeys::read`. [11](#0-10) 
2. Write `t = 65535`, `n = 65535`, and `i = 1` as little-endian `u16` values. [12](#0-11) 
3. Write interpolation selector byte `1` for `Interpolation::Lagrange`. [5](#0-4) 
4. Write any canonical secret-share scalar. [13](#0-12) 
5. Write `65535` canonical verification-share encodings, for example repeated valid non-identity points only if the ciphersuite permits the desired bytes; otherwise write distinct valid encodings for participants `1..=65535`. [14](#0-13) 
6. Pass the stream to `ThresholdKeys::<C>::read`. Deserialization reaches `ThresholdKeys::new`, where `t` Lagrange factors each iterate over `t` participants. [9](#0-8) [6](#0-5) [8](#0-7) 

The critical path is:

```text
ThresholdKeys::read
  -> read t = n = 65535 and interpolation = Lagrange
  -> read n verification shares
  -> ThresholdKeys::new
     -> for each participant in 1..=65535
        -> Interpolation::interpolation_factor
           -> loop over all 65535 participants
```

This produces approximately `65535 × 65535 = 4,294,836,225` inner-loop field operations from a multi-megabyte serialized input.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
