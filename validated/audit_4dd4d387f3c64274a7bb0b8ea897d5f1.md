### Title
Payout-to-withdrawal join omits `idx`, letting a duplicated withdrawal UTXO credit two withdrawal indices from a single fronted payout - (File: core/src/database/verifier.rs)

### Summary
`Database::get_payout_txs_for_withdrawal_utxos` joins `withdrawals` to `bitcoin_syncer_spent_utxos` solely on `(txid, vout)`, without also constraining on `withdrawals.idx`. If two distinct `withdrawals` rows are ever populated with the identical `withdrawal_utxo_txid`/`withdrawal_utxo_vout` pair, one on-chain spend of that UTXO will be reported as a payout for both indices, and `update_payout_txs_and_payer_operator_xonly_pk` will persist the same `payout_txid` onto both rows.

### Finding Description
The broken binding: `count(distinct BTC payout UTXOs spent) == count(withdrawals rows marked paid)`. The query is: [1](#0-0) 
It joins purely on `(bsu.txid, bsu.vout) = (w.withdrawal_utxo_txid, w.withdrawal_utxo_vout)`, with no `w.idx` in the join predicate. `withdrawal_utxo_txid`/`vout` are written per-`idx` via a plain `UPDATE ... WHERE idx = $1` with no uniqueness check against other rows: [2](#0-1) 
Nothing in this function, nor in the schema definitions found (`core/src/database/schema.sql`), enforces a `UNIQUE(withdrawal_utxo_txid, withdrawal_utxo_vout)` constraint across rows — the update is index-scoped only. This means if the Citrea Bridge contract permits two different withdrawal ids to carry the identical BTC outpoint bytes (an application invariant outside this repo, not verifiable here), the verifier-side ingestion path (`update_withdrawal_utxo_from_citrea_withdrawal`, invoked once per Citrea withdrawal event during `update_citrea_deposit_and_withdrawals`) will happily store the same outpoint twice under two different `idx` values.

Once an operator broadcasts a single payout transaction spending that UTXO, `bitcoin_syncer` records exactly one row in `bitcoin_syncer_spent_utxos` for that `(txid, vout)`. When `update_finalized_payouts` calls `get_payout_txs_for_withdrawal_utxos`, the join fans out: the one `bitcoin_syncer_spent_utxos` row matches both `withdrawals` rows sharing the outpoint, producing two `(idx, spending_txid)` result rows for a single physical spend. `update_payout_txs_and_payer_operator_xonly_pk` then writes `payout_txid` for both `idx=i` and `idx=j`, making both withdrawal indices appear "paid" by the same operator.

The regression test at lines 391-521 of the same file only exercises the single-idx-per-outpoint case and does not test the duplicate-outpoint scenario, so this divergence is not caught by existing tests.

### Impact Explanation
If reachable, an operator that fronted a single BTC payout would become eligible to be reimbursed twice — once from `move_i`'s vault and once from `move_j`'s vault — via the operator's reimbursement/kickoff flow that consults `get_payout_info_from_move_txid`/`get_first_unhandled_payout_by_operator_xonly_pk`, which key off `payout_txid`/`is_payout_handled` per `idx`. This would match the Critical impact class ("operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal") — but only if the precondition (two Citrea withdrawal ids sharing an identical BTC outpoint) is actually achievable, which is a question about the Citrea Bridge contract's `withdraw` validation, not this repository.

### Likelihood Explanation
This repository's code alone does not prevent duplicate `(withdrawal_utxo_txid, withdrawal_utxo_vout)` pairs across `idx` values reaching the database — the join and the update path shown above are consistent with the exploit description. However, I could not verify within this repo whether the Citrea Bridge contract's `withdraw` function actually permits an attacker to register two different withdrawal ids with byte-identical UTXO outpoints (this is an off-repo precondition per the audit's own scoping, and I do not have access to the Citrea contract source in this index). Absent confirmation of that precondition, the SQL-join weakness is a real code defect but its exploitability depends entirely on a contract-side invariant outside `core/src/database/verifier.rs` that I cannot confirm or refute with available tools.

### Recommendation
Add `AND bsu.` — more precisely, include `w.idx` semantics implicitly by ensuring uniqueness: either (a) add a database-level `UNIQUE(withdrawal_utxo_txid, withdrawal_utxo_vout)` constraint on `withdrawals` so `update_withdrawal_utxo_from_citrea_withdrawal` fails/conflicts when a duplicate outpoint is written for a different `idx`, or (b) change the ingestion logic to reject/flag a withdrawal registration if the chosen UTXO outpoint already exists for another `idx`. Additionally, `get_payout_txs_for_withdrawal_utxos` should defensively assert/guard against one-to-many fan-out (e.g., add a uniqueness check or `DISTINCT ON (bsu.txid, bsu.vout)` with an error if multiple `withdrawals.idx` rows match the same spent UTXO), rather than silently propagating duplicates into `update_payout_txs_and_payer_operator_xonly_pk`.

```rust
// core/src/database/verifier.rs test module
#[tokio::test]
async fn duplicate_withdrawal_utxo_fans_out_payout() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();
    let mut dbtx = db.begin_transaction().await.unwrap();

    let move_i = Txid::from_byte_array([0xAA; 32]);
    let move_j = Txid::from_byte_array([0xBB; 32]);
    let shared_utxo = bitcoin::OutPoint {
        txid: bitcoin::Txid::from_byte_array([0xCC; 32]),
        vout: 0,
    };
    let payout_txid = Txid::from_byte_array([0xDD; 32]);

    // two distinct deposits/withdrawal indices
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), 1, &move_i).await.unwrap();
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), 2, &move_j).await.unwrap();

    // attacker registers the SAME outpoint for both withdrawal ids
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), 1, shared_utxo, 100).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), 2, shared_utxo, 100).await.unwrap();

    // one real spend of the shared utxo
    let block_id = db.insert_block_info(Some(&mut dbtx), &BlockHash::all_zeros(), &BlockHash::all_zeros(), 100).await.unwrap();
    db.insert_txid_to_block(&mut dbtx, block_id, &payout_txid).await.unwrap();
    db.insert_spent_utxo(&mut dbtx, block_id, &payout_txid, &shared_utxo.txid, shared_utxo.vout.into()).await.unwrap();

    let rows = db.get_payout_txs_for_withdrawal_utxos(Some(&mut dbtx), block_id).await.unwrap();

    // BINDING CHECK: 1 physical spend should map to 1 withdrawal credited, not 2
    assert_eq!(rows.len(), 1, "one spend fanned out to {} withdrawal rows", rows.len());
}
```
This test demonstrates the join fan-out at the database layer. It does **not** demonstrate that an unprivileged attacker can actually cause two Citrea withdrawal ids to be registered with byte-identical BTC outpoints via the real `withdraw` call path (`Verifier::update_citrea_deposit_and_withdrawals` sourcing data from Citrea storage proofs) — that precondition depends on the Citrea Bridge contract, which is outside this repository and was not verifiable with the tools available.

```rust
    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }
```
