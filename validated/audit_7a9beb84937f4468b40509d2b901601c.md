### Title
Untrusted preprocess/share length causes uncaught index-out-of-bounds panic in `TransactionSignMachine` - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
The node-tar bug class: a value parsed from attacker-controlled bytes is treated as a trusted, correctly-shaped type, and code downstream assumes its structure — crashing with an uncaught error that bypasses all error-returning APIs. The analog in Serai is `TransactionSignMachine::sign`, which indexes a peer-supplied `Vec<Preprocess>` with no length check, and `TransactionSignatureMachine::complete`, which calls `shares.remove(0)` on a peer-supplied `Vec<SignatureShare>` with no length check.

### Finding Description
`TransactionSignMachine::sign` receives `commitments: HashMap<Participant, Vec<Preprocess<Secp256k1, ()>>>`. Each preprocess vector was deserialized from arbitrary bytes via `TransactionSignMachine::read_preprocess`, which reads however many `Preprocess` items the byte stream encodes — there is no binding between the number of preprocesses read and `self.sigs.len()`. `sign` then transposes the map with:

```rust
commitments.iter().map(|(l, commitments)| (*l, commitments[c].clone()))
```

for `c` in `0 .. self.sigs.len()`. If a participant supplies a `Vec<Preprocess>` shorter than the number of inputs (e.g., empty), `commitments[c]` panics with an index-out-of-bounds. This panic occurs before any `FrostError` can be returned: it propagates out of `SignMachine::sign` as an uncaught panic, exactly like the TypeError that bypasses `strict: false` and `'error'` handlers.

The same pattern exists in `TransactionSignatureMachine::complete`, which does `shares.remove(0)` per input on peer-supplied `Vec<SignatureShare>` read via `read_share`; an empty or short share vector panics before `FrostError` is produced. [1](#0-0) [2](#0-1) 

### Impact Explanation
A single malformed preprocess or signature-share message (~tens of bytes) deterministically panics the signing process. Since each party's `Vec<Preprocess>` / `Vec<SignatureShare>` is read with a length derived entirely from the peer's serialization, any participant — including one holding a zero-value or rogue preprocess — can crash every honest signer that attempts `sign`/`complete`. For a threshold Bitcoin wallet this is a denial of service against the signing session and, since the panic escapes `FrostError`, potentially of the calling process itself. This is a direct analog of "a small crafted input crashes the process and no error handling can intercept it."

### Likelihood Explanation
Reachable by any unprivileged party who can submit a preprocess or share message to a signer (a standard part of the FROST protocol flow). No collusion, no leaked keys, and no malformed curve encodings are required — only a truncated length in an otherwise parseable message. The panic is deterministic on every attempt.

### Recommendation
Validate lengths before indexing: in `sign`, check `commitments.len() == self.sigs.len()` for every entry (or zip with `get(c).ok_or(FrostError::...)`); in `complete`, use `shares.first()/drain` with an explicit length check against `self.tx.input.len()`. Alternatively, enforce the count at deserialization time in `read_preprocess`/`read_share` by reading exactly `self.sigs.len()` items, so the malformed-length type confusion can never reach `sign`/`complete`.

### Proof of Concept
1. Construct a `SignableTransaction` with ≥1 input and call `multisig` then `preprocess` to obtain `TransactionSignMachine`.
2. Have a peer serialize a preprocess with one fewer `Preprocess` than inputs (e.g., `vec![]`); read it via `read_preprocess`.
3. Insert it into `commitments` and call `sign(&commitments_map, b"")` — panics at `commitments[c]` (index 0 out of bounds) instead of returning `Err(FrostError)`.
4. Symmetrically, supply `vec![]` as a participant's `SignatureShare` list to `complete` — panics at `shares.remove(0)`.

Caveat: I could not confirm whether `read_preprocess`'s underlying `Preprocess::read` or the caller enforces a per-input count elsewhere in `crypto/frost`; the indexing sites themselves perform no check, so the panic path exists unless an outer layer bounds the vector length.
