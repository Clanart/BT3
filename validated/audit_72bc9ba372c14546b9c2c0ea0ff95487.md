### Title
Discard Changes trusts unsanitized `git status` paths and can delete/trash files outside the repository - (File: app/src/lib/stores/git-store.ts)

### Summary
`GitStore.discardChanges()` builds trash/delete targets directly from `file.path`, which originates from parsed `git status --porcelain -z` output, without ever validating that the resolved path stays inside the repository root. Every other path-consuming operation in this codebase (`clone.ts`'s `isClonePathSensitive`, `copilot-conflict-context.ts`'s `resolveWithin` guard, `dispatcher.ts`'s `openRepositoryFromUrl` `resolveWithin`/`isAbsolute` check) treats untrusted, repo-derived paths as needing containment verification before touching the filesystem. `discardChanges` does not.

### Finding Description
`parsePorcelainStatus` in [1](#0-0)  captures the path field straight from the regex match with no rejection of `..` segments, absolute paths, or unusual separators, and the untracked-entry parser at [2](#0-1)  similarly takes the raw substring as `path`.

`GitStore.discardChanges` then consumes that value directly: [3](#0-2) 

Both the trash call (`Path.resolve(this.repository.path, file.path)`) and the permanent-delete fallback (`rm(Path.join(this.repository.path, file.path))`) skip the `resolveWithin` containment check that this same codebase applies everywhere else a repository-relative path is turned into an absolute path, e.g. [4](#0-3)  and its use in [5](#0-4) .

Normally `git status` paths cannot contain `..` because git tracks files under the worktree, but the invariant that "a path reported by `git status` is safe to join with the repo root" is not actually enforced anywhere in this data flow — it is assumed. If that assumption is ever violated (e.g., through a crafted index/tree that git itself would normally reject via `core.protectNTFS`/`core.protectHFS`-style checks, through a case-insensitive or Unicode-normalizing filesystem trick, or through a future git parsing edge case), there is no secondary guard in Desktop to stop the resulting path from resolving outside the repository before the file is trashed or deleted.

### Impact Explanation
If `file.path` (or `file.status.oldPath`, also used unchecked for the checkout side at [6](#0-5) ) ever resolves to a location outside the repository root, `discardChanges` will silently move an arbitrary file into the trash (data loss / corruption of files the user did not intend to touch) or, in the permanent-delete path, `rm` it outright — both outside the guarded, sandboxed area of the repo. This matches the "silent corruption of what the user commits or pushes" / unauthorized file write-outside-the-repo class from the Valid Impact criteria, driven entirely by content of a cloned/fetched repository (attacker-controlled tree/index), with no local access or social engineering required.

### Likelihood Explanation
Exploitability depends entirely on finding a way to make git report a status path containing traversal segments or an absolute path — something git's own protections (`core.protectNTFS`, `core.protectHFS`, path normalization) are designed to prevent, and I could not find in this index a concrete bypass demonstrated in-repo (no test or code path constructs such a payload). This is therefore a defense-in-depth gap rather than a confirmed, immediately triggerable exploit: the missing `resolveWithin` guard is real and inconsistent with the rest of the codebase's hardening, but I could not verify a git-side path that currently produces an escaping `file.path` value. This should be treated as **moderate-likelihood at best**, contingent on an as-yet-unidentified git status/index edge case.

### Recommendation
Apply the same `resolveWithin(this.repository.path, file.path)` (and `oldPath`) containment check used elsewhere in the codebase before calling `shell.moveItemToTrash` or `rm` in `GitStore.discardChanges`, and skip/report any file whose resolved path falls outside the repository root, mirroring the pattern already used in `app/src/lib/copilot-conflict-context.ts` and `app/src/ui/dispatcher/dispatcher.ts`.

### Proof of Concept
Not independently reproducible from the indexed code alone — I was not able to construct or confirm a git status/index state that causes `parsePorcelainStatus` to emit a `path` containing `..` or an absolute path, which would be required to actually trigger the unguarded `Path.resolve`/`rm` in `discardChanges`. A full PoC would require experimentation against real `git status --porcelain -z` behavior (e.g., crafted trees, case/Unicode-folding filesystems, or `core.protectNTFS`/`core.protectHFS` bypass) that is outside what static code inspection can confirm; a Devin session with terminal/git access would be needed to test this empirically.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
