## Analysis

The seed bug (H-7) describes a **partial application of cross-chain decimal transformation**: some amount fields were converted between chain decimal precisions while nested ones were left untransformed, causing magnitude-sized misrepresentation of value.

Searching Hyperbridge's own cross-chain decimal-conversion logic, the `pallet-hyper-fungible-token` module (the direct successor to `pallet-token-gateway`) implements the analogous conversion helpers, and they contain a genuine, one-directional conversion bug — not just an incomplete field list, but an asymmetric formula that silently fails to convert in one direction.

### Title
Asymmetric ERC20↔local decimal conversion in `convert_to_erc20`/`convert_to_balance` causes amount misrepresentation across chains - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_erc20` and `convert_to_balance`, used by `pallet-hyper-fungible-token` to translate token amounts between a local asset's decimal precision and the registered remote-chain ERC20 precision, only implement one direction of the decimal delta using `saturating_sub`. When the decimal delta runs the opposite way (local decimals greater than the destination's registered `erc_decimals`, or vice versa on receipt), the exponent collapses to zero and **no scaling is applied at all**, sending/crediting an amount that is off by many orders of magnitude — the same "partial transformation" defect class as H-7, but rooted in the conversion primitive itself rather than a missing field. [1](#0-0) 

### Finding Description
`convert_to_erc20` (used in `send()`) computes:
```
erc20_amount = value * 10^(erc_decimals.saturating_sub(local_decimals))
``` [2](#0-1) 

This only correctly scales up when `erc_decimals > local_decimals`. If `local_decimals > erc_decimals` (a legitimate, admin-permitted registration via `update_asset_precision`/`AssetRegistration.precision`, which per the pallet's own docs supports arbitrary per-chain precision maps, not restricted to 18), `saturating_sub` yields `0`, so the multiplier is `10^0 = 1` — the raw, finer-grained local amount is dispatched unscaled as the message amount: [3](#0-2) 

Symmetrically, `convert_to_balance` (used in `on_accept` and `on_timeout`) does:
```
local_amount = value / 10^(erc_decimals.saturating_sub(local_decimals))
```
This is only correct when `erc_decimals > local_decimals`. When `local_decimals > erc_decimals`, the divisor again collapses to `1`, so the amount received from the remote chain is **not scaled up** to local precision — it is credited to the beneficiary at 10^(diff) too small a value: [4](#0-3) [5](#0-4) 

Both helpers implement only a single direction of decimal delta; there is no `if erc_decimals >= local_decimals { mul } else { div }` branch. This is precisely analogous to H-7's core broken invariant: cross-chain decimal transformation is applied incompletely, producing magnitude-sized amount misrepresentation.

### Impact Explanation
- On `send()`: if the asset's local decimals exceed the destination's registered `erc_decimals`, the dispatched `Message.amount` is left at full local-precision magnitude instead of being scaled down. The receiving `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract or destination pallet will mint/unlock that raw, un-scaled value to the beneficiary — an amount inflated by `10^(local_decimals - erc_decimals)`, i.e. tokens minted far in excess of what was escrowed/burned on the source chain (unauthorized token creation / fund theft from the bridge's backing).
- On `on_accept`/`on_timeout` (receive/refund path): if local decimals exceed the source's registered `erc_decimals`, the credited/refunded amount is under-scaled by the same factor, permanently locking/losing the difference for the user.

Both cases move funds to a wrong amount, directly matching the bounty's "stealing or loss of funds" / "transaction manipulation" impact classes, and require no malicious relayer, prover, or admin — only a legitimately registered asset pair where local decimals differ from remote precision in the unhandled direction (a normal, expected configuration in a multi-chain deployment, exactly as the docs themselves illustrate with "10-decimal DOT on Polkadot vs 18-decimal DOT on Ethereum" — the reverse pairing is equally valid and unguarded).

### Likelihood Explanation
Medium-to-high: it requires an asset to be registered where local decimals exceed the counterpart chain's registered precision — a normal, permitted configuration reachable simply by an ordinary user calling the public `send` extrinsic once such an asset pair exists (e.g. a locally-issued 18-decimal asset bridged to a 6-decimal representation, or any substrate↔substrate pair with differing precisions). No attacker privilege beyond calling the public entrypoint is needed.

### Recommendation
Fix both helpers to branch on the sign of the decimal delta instead of relying on `saturating_sub`:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}

pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}
```

### Proof of Concept
1. Admin registers a local asset (via `create_erc6160_asset`/`AssetRegistration`) with `local_decimals = 18`, and configures `Precisions::<T>::insert(asset_id, dest_chain, 6)` (a valid, permitted call for `CreateOrigin`, and a realistic config for a stablecoin-style asset with fewer remote decimals).
2. A regular user calls `send(SendParams { asset_id, destination: dest_chain, amount: 1_000_000_000_000_000_000 /* 1 token, 18 decimals */, .. })`. [6](#0-5) 
3. Inside `send`, `erc_decimals = 6`, `decimals = 18`. `convert_to_erc20(1e18, 6, 18)` computes `10u128.pow(6u8.saturating_sub(18) as u32) = 10^0 = 1`, so `erc20_amount = 1e18` is dispatched unchanged instead of the correct `1e6`. [7](#0-6) 
4. The destination contract/pallet mints/unlocks `1e18` units to the beneficiary at 6-decimal precision — a 10^12x inflation relative to the 1 token that was actually escrowed on the source chain, resulting in a massive unauthorized token mint on the destination chain.
