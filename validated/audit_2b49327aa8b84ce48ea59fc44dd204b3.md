### Title
Deterministic cached-preprocess nonce reuse in `DkgConfirmer` leaks the validator's MuSig/Ristretto private key - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The coordinator's DKG-confirmation signing protocol caches a FROST preprocess seed keyed only by `(b"DkgConfirmer", attempt)` in `CachedPreprocesses`, and re-derives the exact same nonces every time `preprocess_internal` runs for that context. `share()` and `complete()` both funnel through `share_internal`, which signs whatever `msg`/`preprocesses` it is handed. If `share_internal` executes twice for the same attempt with any difference in inputs — a different `KeyPair`, or a different confirmation-preprocess map — the same nonce `(base, actual)` is used to produce two signature shares, enabling recovery of the validator's long-term Ristretto secret key. The overwrite-prone `generated_key_pair` path makes the double-sign reachable without breaking BFT.

### Finding Description
`preprocess_internal` stores a 32-byte `CachedPreprocess` per `context = (b"DkgConfirmer", attempt)` and never deletes or rotates it [1](#0-0) . Each call rebuilds `AlgorithmSignMachine::from_cache` with that same seed, so `self.nonces` are identical across invocations.

`share()` calls `share_internal` directly, and `complete()` calls `share_internal` again to rebuild the machine [2](#0-1) . The signed `msg` is `set_keys_message(set, removed, key_pair)`, so a different `key_pair` produces a different message [3](#0-2) . The `preprocesses` map comes from `ConfirmationNonces`, which are bytes each validator embedded in its `DkgShares` transaction — untrusted bytes fed to `read_preprocess` [4](#0-3) .

`generated_key_pair` unconditionally overwrites `DkgKeyPair`/`KeyToDkgAttempt` and emits a share on every invocation, with no guard against being called more than once per attempt, nor any check that the stored `key_pair` matches a previously signed one [5](#0-4) . The file's own safety argument admits nonce reuse is catastrophic and is prevented only if inputs are guaranteed identical: "it is explicitly unsafe to reuse nonces across signing sessions… In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again… A logical flaw exists, letting new messages over write prior messages" [6](#0-5) . `generated_key_pair` is exactly such an overwrite: a processor reboot/re-report, or the documented race where `DkgKeyPair` is written in a txn whose commit isn't guaranteed [7](#0-6) , yields a second `share()`/`complete()` call over the same seed with a different `key_pair` or preprocess set.

Inside `sign`, the share is `base + rho*actual + c*λ*secret_share` with `rho` and `c` both depending on the preprocess bytes and message [8](#0-7) . Two shares over the same `(base, actual)` with distinct `(rho, c)` (and a third, or known preprocess control, to close the system) let an observer solve for the nonce scalars and then the `secret_share` — which here is the validator's actual `key`, the root-of-trust Ristretto key used for `musig(...)`.

### Impact Explanation
Recovery of a validator's private key — not merely a threshold share. The `key` field is the validator's long-term Ristretto key that signs all tributary `Transaction`s (`tx.sign(&mut OsRng, genesis, self.our_key)` [9](#0-8) ) and forms the MuSig root of trust for `set_keys` [10](#0-9) . Once recovered, the attacker can forge that validator's signatures on arbitrary messages, including `set_keys` confirmations, votes to remove other validators, and slash reports — a full impersonation enabling unauthorized key rotation and theft of funds controlled by the threshold network. Severity: High.

### Likelihood Explanation
The trigger is any second `share_internal` execution for an existing `(DkgConfirmer, attempt)` context with differing inputs. Concretely reachable paths:

1. `generated_key_pair` is invoked per processor key-pair report and always re-signs; a rebooted or re-synced processor reporting the same attempt, or competing processors reporting different `key_pair`s for one attempt, produces two shares over one nonce [5](#0-4) .
2. `complete()` re-executes `share_internal` after `share()`; while currently fed the same `ConfirmationNonces`, it takes `preprocesses` and `key_pair` as arguments with no equality assertion against the earlier call, so any DB divergence between the two reads (the code itself flags the commit-ordering race at handle.rs:527) signs a distinct message with the reused nonce [11](#0-10) .
3. The preprocess bytes are supplied by external participants' `DkgShares` transactions, so an outsider influencing those bytes changes `rho`/`R`/`c` while the local nonce stays fixed [4](#0-3) .

Requiring only a second signing call — not collusion, BFT failure, or key leakage — and with observed shares published publicly on the tributary chain, likelihood is Medium.

### Recommendation
- Make the cached-preprocess context unique per signing *instance*, not per attempt: bind `CachedPreprocesses` to the full tuple `(context, key_pair_hash, participants/preprocess-set hash)` or store a fresh seed per invocation.
- In `generated_key_pair`, refuse to sign if `DkgKeyPair` is already set to a different value, and record (e.g., `ShareEmitted`) that a share was already published for the attempt so any later call is a no-op.
- In `complete`, pass the previously computed share/machine forward instead of re-running `share_internal` from the cached seed; at minimum, assert the reconstructed share equals the one already emitted before completing.
- Enforce the `SignMachine::cache` contract ("this cached preprocess MUST only be used once") by deleting or marking the `CachedPreprocesses` entry consumed after `share` is produced [12](#0-11) .

### Proof of Concept
1. Attempt `a` begins; `preprocess()` generates and caches seed `S` under key `(b"DkgConfirmer", a)` [1](#0-0) .
2. `generated_key_pair(..., key_pair_A, a)` stores `key_pair_A` and calls `share(preprocesses, key_pair_A)`, emitting share `s1 = base + rho1*actual + c1*λ*x` where `x` is the validator's secret key, `c1 = hram(R1, A, set_keys_message(..., key_pair_A))` [3](#0-2) .
3. A second report arrives (processor reboot/re-report, or a different `key_pair_B` from a competing DKG outcome). `DkgKeyPair::set` overwrites without checking, and `share()` runs again: `preprocess_internal` decrypts the same `S`, `from_cache` reconstructs identical `nonces`, and `s2 = base + rho2*actual + c2*λ*x` is emitted with `c2 ≠ c1` (different `key_pair` ⇒ different `msg` ⇒ different `R`/`c`) [13](#0-12) .
4. Both `s1`, `s2` are published on-chain in `DkgConfirmed` transactions. With `rho1, rho2, c1, c2` recomputed from public data and a third share (or control of one's own preprocess bytes to fix `rho`), solve the linear system for `base`, `actual`, then `x = (s1 - base - rho1*actual) / (c1*λ)` — recovering the validator's private key.
5. Alternatively, without any second report: `complete(preprocesses', key_pair', shares)` re-signs via `share_internal`; if `preprocesses'`/`key_pair'` read from the DB diverge from those used in step 2 (overwritten `ConfirmationNonces`/`DkgKeyPair`), the same nonce is signed under different binding factors — same extraction.

Note on scope: I verified the coordinator-side paths above. I did not exhaustively confirm whether the processor-side `signer.rs`/`batch_signer.rs` cached preprocesses are also re-consumed across `attempt`s with attacker-influenced `id.attempt` values; if `attempt` reuse is possible there, the same primitive applies to the network threshold keys rather than only the validator key.
