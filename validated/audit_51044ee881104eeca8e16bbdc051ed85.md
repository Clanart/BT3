### Title
Stale line-index selection re-applied against a freshly re-fetched diff can silently commit/omit the wrong lines - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The reported bug's broken invariant is: a value computed against one snapshot of state (user-entered `n0`/`n1`) is later applied against a different, re-derived snapshot of the same state (the actual pool ratio), producing a mismatch that silently corrupts the outcome. `formatPatch` and `applyPatchToIndex` have the same shape of bug: partial-commit line selection is stored as a set of *positional indices* into a diff (`DiffSelection`, `absoluteIndex = hunk.unifiedDiffStart + lineIndex`), but at commit time the diff is **re-fetched from disk** rather than reusing the diff snapshot the user actually looked at when selecting lines.

### Finding Description
`DiffSelection` tracks selected lines purely by numeric index (`app/src/models/diff/diff-selection.ts:41-320`), with no binding to the actual line content. `formatPatch` walks the hunks of *whatever diff is passed in* and calls `file.selection.isSelected(absoluteIndex)` to decide whether each line is included [1](#0-0) .

Critically, `applyPatchToIndex` (invoked from `stageFiles` for every partially-selected file just before `git commit` runs) **independently re-fetches the diff from the working directory** at commit time instead of using the diff that was displayed to the user when they made their line selections: [2](#0-1) 

The `WorkingDirectoryFileChange.selection` object carrying the user's chosen indices is constructed earlier in the UI/app-store flow against a diff loaded by `updateChangesWorkingDirectoryDiff` [3](#0-2) . The code itself acknowledges that the diff can change between the time selection state is established and the time it's consumed, but only partially compensates by dropping indices that no longer exist — it does **not** verify that surviving indices still refer to the *same content*: [4](#0-3) 

Because hunks can shift, merge, or renumber when file content changes (e.g., due to autocrlf/smudge filters, a background `git fetch`/checkout, a concurrently running LFS filter, or content rewritten by a hook), an index that was "line 12, the malicious `curl | sh` addition" in the old diff can become "line 12, an innocuous context line" in the new diff fetched by `applyPatchToIndex`, or vice versa. `formatPatch` will blindly honor whatever `isSelected(absoluteIndex)` says against the *new* hunk layout, exactly mirroring the C4 report's flaw where the fee ratio computed from one state (`n0`,`n1`) was applied against a different state (actual pool ratio at time of the real deposit).

### Impact Explanation
If an attacker can influence working-directory content between diff-load and commit-time (e.g., a malicious `clean`/`smudge` filter defined in a fetched `.gitattributes`, a `post-checkout`/background LFS process, or a crafted file that a build tool touches during the commit flow), Desktop can silently include lines the user never selected, or drop lines the user did select, without any error — corrupting exactly "what the user commits or pushes," which is explicitly in scope. This is worse than a UI-only staleness bug because the mismatch is invisible: `formatPatch` has no cross-check that the diff it operates on is the same diff the selection was built from (unlike `updateChangesWorkingDirectoryDiff`, which at least checks file/selection identity before applying results back to state).

### Likelihood Explanation
Moderate/low-but-plausible. It requires a timing window where file content changes between the moment the user finished selecting lines in the UI and the moment `git commit` triggers `stageFiles` → `applyPatchToIndex`. Attacker-controlled Git attributes (`filter`, `clean/smudge`, checked out from a cloned/fetched repo) or LFS content-substitution processes are a realistic vector fully within the stated "attacker controls a cloned/fetched repository" threat model, and Desktop performs no re-validation of the diff identity in the commit path (only in the interactive selection-preservation path). Exploiting it reliably to target a *specific* line requires some determinism about hunk layout, which lowers likelihood somewhat, but the underlying invariant break (index-based selection re-applied to a different diff instance) is unconditionally present in the code path.

### Recommendation
- In `applyPatchToIndex`/`stageFiles`, do not re-fetch a fresh diff at commit time; use (or re-validate against) the exact diff the user's `DiffSelection` was built from, rejecting/aborting the partial commit if the diff has changed in a way that isn't purely "some previously selected lines no longer exist."
- Bind selection state to line content hashes (or at least full hunk-header+content fingerprints) rather than bare integer indices, so a changed diff invalidates the selection instead of silently reinterpreting it against new content.
- Add a guard in `formatPatch`/`applyPatchToIndex` analogous to the one in `updateChangesWorkingDirectoryDiff` that fails loudly (throws) if the diff handed to it doesn't match the diff for which the selection's `selectableLines` set was computed.

### Proof of Concept
Conceptual, not fully verified end-to-end due to inability to run the app in this environment:
1. Clone/open a repository containing a `.gitattributes` with a `filter=malicious` entry backed by a script that rewrites tracked file content shortly after checkout/fetch (attacker-controlled repo content — in scope).
2. User opens the Changes view; Desktop loads the diff via `updateChangesWorkingDirectoryDiff` and the user selects specific lines to commit (e.g., unchecking a suspicious added line), building a `DiffSelection` bound to indices of that diff.
3. Before the user clicks "Commit," the attacker's filter/background process mutates the file on disk, shifting hunk boundaries.
4. User commits. `stageFiles` → `applyPatchToIndex` re-fetches the diff fresh via `getWorkingDirectoryDiff` [5](#0-4) , and `formatPatch` applies the stale `DiffSelection` indices to this new hunk layout [1](#0-0) , silently including the line the user intended to exclude (or excluding one they intended to include) in the resulting commit/push — with no error surfaced to the user.

Confidence caveat: I could not execute the app or git filters to empirically confirm the exact hunk-shift scenario reproduces a mismatch; this is derived from static code-path analysis of `apply.ts`, `patch-formatter.ts`, `diff-selection.ts`, and `app-store.ts`, and the comment at `app-store.ts:3480-3493` which acknowledges the underlying staleness risk is only partially handled.
