### Title
Unchecked `u64` accumulation and addition in `SignableTransaction::new` permits signed transactions whose outputs exceed inputs - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` sums attacker-influenced payment amounts with `sum::<u64>()` and then performs unchecked `u64` additions (`payment_sat + needed_fee`, `payment_sat + fee_with_change`) to validate solvency and compute change. In release builds these wrap modulo `2^64`, so a crafted set of payments can wrap `payment_sat` to a small value, bypass the `NotEnoughFunds` check, and cause the FROST `TransactionMachine` to produce signatures over a consensus-invalid transaction (outputs exceeding inputs). Each payment only needs to individually pass the `DUST` check; per-payment upper bounds are never enforced before `Amount::from_sat` is used.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:187`, `payment_sat` is computed as `payments.iter().map(|payment| payment.1).sum::<u64>()`. This sum overflows `u64` for sufficiently large payment lists (e.g., two payments of `2^63` sats each, which sum to `0`). The solvency check at line 215, `if input_sat < (payment_sat + needed_fee)`, then uses the wrapped value, so construction succeeds even though the true output total far exceeds the inputs. Similarly, the change computation at line 228 uses `input_sat.checked_sub(payment_sat + fee_with_change)`, where `payment_sat + fee_with_change` can itself wrap before `checked_sub` is applied, yielding a change output close to the full input value while the payment outputs remain at their individually huge (but `TxOut`-encodable) amounts. The `TxOut` values at lines 190 and 230 are built via `Amount::from_sat` directly from the raw `u64` amounts. `fee()` at lines 138–141 performs a bare `u64` subtraction of summed outputs from summed inputs and can underflow-panic on such a transaction. Additionally, `fee_per_vbyte * vbytes` at lines 206 and 227 is unchecked multiplication; a large caller-controlled `fee_per_vbyte` wraps `needed_fee` to a value that can still pass the `TooLowFee` minimum check, silently underpaying fees.

### Impact Explanation
The `TransactionSignMachine::sign` path (lines 373–397) sighashes the transaction exactly as constructed and has each participant produce FROST signature shares for it. An unprivileged party that can influence payment amounts in data destined for signing (e.g., withdrawal instructions routed to the bitcoin wallet) can cause the validator set to sign a transaction that Bitcoin consensus rejects (sum of outputs > sum of inputs), or a transaction that commits essentially all input funds to a change output while paying a wrapped-near-zero fee that will not relay. The result is a signed-but-unspendable/stuck spend attempt: the intended payments never confirm, and the wallet's UTXOs remain locked to inputs the network will not accept, requiring manual recovery of the signing session state. This is a denial-of-spend / liveness fault against the threshold wallet reachable from signing-request data, matching the unchecked-math class (missing overflow checks on economic amounts) from the reference report.

### Likelihood Explanation
Reachability requires influencing the `payments` slice passed to `SignableTransaction::new`. Payment amounts originate from the processor's interpretation of user-initiated instructions, so an unprivileged user controls these `u64` values subject only to the per-payment `DUST` floor at lines 165–169 — there is no upper bound or total-supply sanity check. No collusion or privileged access is needed. Impact is bounded to producing an invalid or uneconomic signed transaction rather than direct theft, since Bitcoin consensus rejects the tx; hence Medium, not High.

### Recommendation
Use `checked_add`/`checked_sum` (or `Amount::checked_add`) when accumulating `payment_sat` and `input_sat`, reject with a new `TransactionError` variant on overflow, and bound each payment by `Amount::MAX_MONEY`-equivalent (21M BTC in sats). Compute `needed_fee`/`fee_with_change` with `checked_mul`/`checked_add` and reject on overflow rather than wrapping. In `fee()`, use `checked_sub` and surface an error instead of panicking on underflow.

### Proof of Concept

```rust
// networks/bitcoin context: assume `input` is a ReceivedOutput worth
// input_sat = 100_000 sats, and fee_per_vbyte = 1 with a small vbytes so
// needed_fee is small and passes the TooLowFee check.

let payments: &[(ScriptBuf, u64)] = &[
    (script_a.clone(), u64::MAX / 2 + 1), // >= DUST, passes line 165-169
    (script_b.clone(), u64::MAX / 2 + 1), // >= DUST, passes
];
// payment_sat = (u64::MAX + 2) mod 2^64 = 1  (wraps in release, send.rs:187)

let tx = SignableTransaction::new(
    vec![input],
    payments,
    Some(change_script),
    None,
    1,
).unwrap(); // line 215 check: 100_000 < (1 + needed_fee)  -> false, no error

// tx.transaction().output now contains two TxOuts of ~9.2e18 sats each
// plus a change output of ~input_sat - fee, i.e. ~100_000 sats.
// Calling tx.multisig(&keys) -> preprocess -> sign produces Schnorr signature
// shares over taproot sighashes for a transaction whose outputs (≈1.8e19 sats)
// vastly exceed its inputs (100_000 sats): consensus-invalid, yet signed.
// tx.fee() at line 138 computes 100_000 - (1 mod 2^64 wrapped output sum)
// which underflows or returns a nonsense fee.
```
