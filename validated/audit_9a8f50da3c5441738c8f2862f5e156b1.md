### Title
Unprivileged participant crashes `GeneratorPromotion::complete` by keying the proof map with the victim's own index - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` validates only the *count* and *upper bound* of the participant-keyed proof map, not its exact key set. A malicious DKG participant can supply a `proofs` map containing the victim's own participant index (`params.i()`) in place of another participant's entry, causing `proofs.get(&i).unwrap()` to panic — a remotely triggerable denial of service analogous to the CVE-2020-14814 crash class.

### Finding Description
`complete` performs two checks on the attacker-influenced `proofs` map:

```rust
// crypto/dkg/promote/src/lib.rs:125-136
if proofs.len() != (usize::from(params.n()) - 1) { ... }
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() { ... }
}
```

Both invariants can be satisfied while the map is missing a required entry: supply `n - 1` entries, all with keys `<= n`, but include `params.i()` itself and omit some other participant `j` in `1..=n`. Since `proofs` is a `HashMap`, the keys are distinct, so `{i_self} ∪ (1..=n \ {i_self, j})` has exactly `n - 1` elements and passes both checks.

The subsequent loop iterates `i` over `1 ..= params.n()`, skips only `params.i()`, and unconditionally unwraps:

```rust
// crypto/dkg/promote/src/lib.rs:140-156
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();   // panics on missing j
```

When `i == j`, `proofs.get(&j)` returns `None` and `.unwrap()` panics.

### Impact Explanation
A single malformed promotion message deterministically panics the victim's node/thread executing `GeneratorPromotion::complete` (a `complete` API reachable with untrusted peer-supplied data). If the panic is not caught, the processor aborts the promotion session and crashes, matching the "unauthorized ability to cause a hang or frequently repeatable crash" impact class of the reference CVE. The crash is repeatable: the attacker can replay the same keying on every retry/attempt.

### Likelihood Explanation
Any participant able to send promotion proofs to a peer controls the `proofs` map keys (they are `Participant` values, not authenticated sender identities bound to the map). No collusion, threshold control, leaked keys, or invalid curve/hash inputs are required — only a mislabeled map. The bypass is trivial to construct: replace one honest participant's entry with an entry keyed by the victim's own index. Cost to the attacker is negligible; success is deterministic (not probabilistic).

### Recommendation
Replace the count-and-bound validation with an exact-set check: verify that `proofs.keys()` equals `all_participant_indexes() \ {params.i()}`, e.g., reject any key `== params.i()` and confirm every `i` in `1..=params.n()` other than `params.i()` is present before indexing. Alternatively, change `proofs.get(&i).unwrap()` to return `PromotionError::MissingParticipant(i)` / `InvalidParticipant` instead of panicking.

### Proof of Concept
Setup: `params = ThresholdParams::new(t, n, i_self)` with `n >= 2`; attacker calls `complete` on a victim's `GeneratorPromotion` instance.

Construct `proofs` as a `HashMap<Participant, GeneratorProof<C1>>` containing:
- one entry keyed `params.i()` (the victim's own index — not rejected by either check),
- one valid entry for each participant in `1..=n` except `params.i()` and one chosen victim index `j`.

Then `proofs.len() == n - 1` (passes line 125), all keys `<= n` (passes line 133), but at `i == j` in the loop at line 146, `proofs.get(&j)` is `None` and `.unwrap()` panics — a repeatable crash from a single unauthenticated participant-controlled input.
