### Title
Uncaught `zlib.error` in offer decompression causes unhandled exception on malformed/malicious offer data - (File: `chia/wallet/util/puzzle_compression.py`, `chia/wallet/trading/offer.py`)

### Summary
The CVE describes an LZO decompression routine crashing on malformed/crafted compressed data because the decompressor did not properly validate attacker-controlled input before processing it. Chia has a structurally analogous pattern: offers exchanged between wallet counterparties are zlib-compressed with a shared dictionary and decompressed via `decompress_with_zdict`/`decompress_object_with_puzzles`, and the calling code only guards against one specific exception type, leaving other decompression failures able to propagate as unhandled exceptions.

### Finding Description
`chia/wallet/util/puzzle_compression.py` decompresses offer bytes using raw `zlib.decompressobj().decompress()`: [1](#0-0) 

This is invoked from `Offer.from_compressed`, and the top-level entry point `Offer.try_offer_decompression` (used when parsing any offer string/bech32 supplied by an offer counterparty) only catches `TypeError`, not the `zlib.error`/`ValueError` classes that `zlib.decompressobj().decompress()` can raise on malformed, truncated, or corrupted compressed streams: [2](#0-1) 

`Offer.from_bech32`, which decodes an untrusted bech32-encoded offer string supplied by any offer counterparty (e.g. pasted into a wallet CLI/RPC/GUI "take offer" flow), feeds the decoded bytes directly into `try_offer_decompression`: [3](#0-2) 

Because a crafted byte stream with a valid-looking version prefix but corrupted zlib payload (bad header, truncated stream, or bad checksum) causes `zlib.decompressobj().decompress()` to raise `zlib.error`, and that exception type is not caught anywhere in the decompression call chain, an attacker-supplied offer string reaches an unhandled exception path in the wallet process that parses it — the same class of "decompressor of untrusted input doesn't validate/handle malformed data gracefully" bug as the LZO CVE.

### Impact Explanation
An unprivileged offer counterparty can hand a victim wallet a crafted offer string (bech32 offer file/text) that, when the victim's wallet attempts to inspect/take the offer via `Offer.from_bech32` → `try_offer_decompression`, raises an uncaught `zlib.error` instead of a handled `ValueError`. Depending on how the RPC/CLI/GUI caller handles exceptions, this can surface as an unhandled server-side exception in the wallet RPC request-processing path, disrupting the offer-viewing/taking flow (denial of service for that operation), analogous to the crash described in the CVE. It does not, based on what is visible, lead to unsigned spend, forged asset identity, or fund loss — the impact is limited to a processing-halt/exception on the offer path.

### Likelihood Explanation
Likelihood is high for triggering the exception (any external byte string ending up in this call path with a corrupted zlib body after a well-formed 2-byte version prefix will trigger it), but the resulting severity depends on whether the wallet RPC dispatcher (`wallet_rpc_api.py`) has a generic top-level exception handler around offer-parsing calls, which was not able to be fully verified due to the limits of the available context. If such a generic handler exists, the practical impact is reduced to a benign error response rather than a service crash.

### Recommendation
- In `decompress_with_zdict`/`decompress_object_with_puzzles` (`chia/wallet/util/puzzle_compression.py`), wrap the `zlib.decompressobj().decompress()` call and re-raise as a well-defined exception type (e.g. `CompressionVersionError` or a new `OfferDecompressionError`).
- In `Offer.try_offer_decompression` (`chia/wallet/trading/offer.py`), broaden the caught exception types beyond `TypeError` to include `zlib.error` (and any other exception the decompression path can raise) so malformed offer data always falls through to the plain `from_bytes` parse (or a clean `ValueError`) instead of propagating an unexpected exception type.
- Ensure the wallet RPC layer (`wallet_rpc_api.py`) that accepts externally supplied offer strings has explicit, tested handling for decompression failures so a malformed offer cannot cause an unhandled exception in the RPC/wallet service.

### Proof of Concept
1. Construct `data = b"\x00\x01" + b"<corrupted-zlib-bytes>"` where the first two bytes are a valid version prefix (e.g. version `1`, within `len(ZDICT)`), and the remaining bytes are not a valid zlib stream (e.g. random bytes or a truncated real zlib stream).
2. Bech32-encode `data` with the `offer` HRP to produce an offer string, or directly call `Offer.try_offer_decompression(data)`.
3. Observe that `zlib.decompressobj(zdict=zdict).decompress(blob, max_length=...)` raises `zlib.error: Error -3 while decompressing data: incorrect header check` (or similar), which is not caught by `except TypeError` in `try_offer_decompression`, causing the exception to propagate uncaught out of the offer-parsing call chain used by `Offer.from_bech32`.

def decompress_with_zdict(blob: bytes, zdict: bytes) -> bytes:
    do = zlib.decompressobj(zdict=zdict)
    return do.decompress(blob, max_length=6 * 1024 * 1024)  # Limit output size


def decompress_object_with_puzzles(compressed_object_blob: bytes) -> bytes:
    version = int.from_bytes(compressed_object_blob[0:2], "big")
    if version > len(ZDICT):
        raise CompressionVersionError(version)
    zdict = zdict_for_version(version)
    object_bytes = decompress_with_zdict(compressed_object_blob[2:], zdict)
    return object_bytes
