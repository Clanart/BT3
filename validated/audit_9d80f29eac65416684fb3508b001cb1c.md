### Title
Unauthenticated `ReceivedOutput` deserialization credits outputs whose claimed value/offset are never verified against the vault key - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external report describes a protocol that trusts a manipulable valuation source (`vault_additionalOwnedAssets()`) to decide how much backing it has, letting an attacker inflate perceived assets and extract value. The analogous shape in Serai is `ReceivedOutput::read`, which deserializes the three pieces of data that define "a spendable deposit belonging to this vault" — the scalar `offset`, the `TxOut` (value + `script_pubkey`), and the `OutPoint` — purely from attacker-supplied bytes, with no cryptographic check binding them together or to the vault's group key. The resulting object is treated as ground truth for how much value was received (`ReceivedOutput::value()`, `mod.rs:116-118`) and for which key controls it (`offset`, `mod.rs:101-103`).

### Finding Description
`Scanner::scan_transaction` (`mod.rs:199-214`) is the only honest producer of `ReceivedOutput`s, and it enforces the critical invariant: `output.script_pubkey` is a key in `self.scripts`, i.e. `script_pubkey == p2tr(key + offset·G)` for a *securely generated, registered* `offset`. `register_offset` (`mod.rs:180-196`) documents that arbitrary offsets "may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script (not by the signature of the key)."

`ReceivedOutput::read` (`mod.rs:122-134`) reconstructs this trusted structure from raw bytes:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
```

It performs no check that the claimed `script_pubkey` equals `p2tr_script_buf(vault_key + offset·G)`, that the `offset` was one produced by `register_offset` rather than an arbitrary scalar, or that the `outpoint`/`TxOut` correspond to a real confirmed output. The offset↔script binding — the entire substance of "this output backs the vault and is spendable by it" — is lost on deserialization, exactly as the yield manager loses the binding between reported asset value and actual redeemable assets.

### Impact Explanation
Any consumer that calls `ReceivedOutput::read` on bytes influenced by an external party will accept a fabricated deposit: a `TxOut` of arbitrary `value` paired with an `offset` that either (a) does not correspond to the script's key (making the credited funds unspendable — the multisig path in `send.rs:273-285` will later fail or bind to the wrong key), or (b) corresponds to an offset embedding a script path, making the output spendable by an arbitrary script rather than the threshold key. Downstream, `value()` is summed directly as input funds in `SignableTransaction::new` (`send.rs:175`) and exposed via `balance()` in the processor's `Output` wrapper, so the system records backing value that was never received or is not under vault control — the direct analog of minting shares against inflated backing.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ReceivedOutput::read`; the scanner's on-chain path is safe, but the serialized `ReceivedOutput`/`Output` format is a network/storage interchange format (used by `processor/src/networks/bitcoin.rs::Output::read`), so any peer-fed or unauthenticated deserialized output is exploitable. Impact severity follows the bug class (credited-but-unspendable or script-spendable funds); likelihood is bounded by whether deployments deserialize outputs from untrusted sources rather than locally produced scanner results, so Medium is the appropriate ceiling.

### Recommendation
Bind the offset to the script on deserialization: store the vault key (or require it as a parameter, e.g. `ReceivedOutput::read_with_key(r, key)`), and after decoding verify `p2tr_script_buf(key + GENERATOR * offset) == Some(output.script_pubkey.clone())`. This mirrors the report's "limit vaults to verifiably sound strategies" recommendation: only accept offsets/scripts producible by `register_offset`'s surjective mapping, and reject arbitrary scalars that could carry a script path.

### Proof of Concept
1. Let `K` be the vault's tweaked group key and `S = p2tr_script_buf(K)` its primary script.
2. Attacker chooses an arbitrary scalar `o` such that `p2tr_script_buf(K + o·G)` is `Some(script')` — or simply reuses `S` with an `offset` that was never registered (e.g. `Scalar::ZERO` paired with a script belonging to a *different* key, since nothing binds them).
3. Attacker serializes `offset.to_bytes() || TxOut { value: 10_000_000, script_pubkey: chosen_script } || fake_outpoint` and feeds it to `ReceivedOutput::read` (`mod.rs:122-134`). Decoding succeeds — no consistency check exists.
4. The resulting `ReceivedOutput` reports `value() == 10_000_000` sats; `SignableTransaction::new` (`send.rs:175`) adds this to `input_sat`, and any crediting logic treats the vault as having received 0.1 BTC that is either nonexistent or spendable by a script path the attacker controls — inflating perceived backing exactly as the manipulated `additionalOwnedAssets()` did.

Uncertainty note: I could not fully confirm within the iteration limit which in-repo callers feed untrusted bytes to `ReceivedOutput::read` (the processor's `Output::read` at `processor/src/networks/bitcoin.rs:156` is one such consumer but is outside the listed in-scope files). The defect — absence of the offset↔script↔key integrity check in `read` — is verifiable directly in `mod.rs:122-134`.
