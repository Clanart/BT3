## Title
Stale decimal-invariant check lets asset owners inflate cross-chain mint amounts in `pallet-hyper-fungible-token::send` - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `pallet-hyper-fungible-token` pallet enforces the invariant `erc_decimals >= local_decimals` only at `register_token`/`update_token` time. The `send()` extrinsic re-fetches the asset's *current* decimals live via `fungibles::metadata::Inspect::decimals()` every time a transfer is dispatched, and feeds it into `convert_to_erc20`, whose scaling arithmetic silently degrades to a no-op via `saturating_sub` if the invariant is later violated. Because ordinary `pallet-assets` asset owners can change an asset's `decimals` metadata after the pallet's one-time registration check, an attacker who owns a registered asset can inflate the cross-chain amount encoded in the outbound ISMP message relative to what was actually escrowed/burned locally.

### Finding Description
`register_token` and `update_token` both gate configuration with: [1](#0-0) 

```
ensure!(
    config.decimals >= local_decimals,
    Error::<T>::ErcDecimalsBelowLocal
);
```

This check is evaluated once, using the `local_decimals` value read at that moment from `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(...)`. The result (`erc_decimals`) is persisted in `Precisions<T>` and never re-validated afterward.

`send()` re-derives `local_decimals` fresh on every call: [2](#0-1) 

```
<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
    params.asset_id.clone(),
)
...
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);
```

`convert_to_erc20` scales up assuming `erc_decimals >= decimals` always holds: [3](#0-2) 

```
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

If `local_decimals` (the asset's *current* decimals) has since grown larger than the `erc_decimals` value frozen in `Precisions` at registration, `erc_decimals.saturating_sub(local_decimals)` clamps to `0` instead of going negative — the function silently stops scaling at all, rather than dividing down. The correct conversion in that case would be to *divide* `value` by `10^(local_decimals - erc_decimals)`; instead the raw, unscaled `value` is forwarded as-is inside the `Message.amount` field of the outbound `DispatchPost`.

Since `pallet-assets` typically allows an asset's owner/admin (a role the asset creator holds, not governance/`CreateOrigin`) to call `set_metadata` and change `decimals` after the asset already exists, an attacker who is the owner of an asset that was legitimately registered with the HFT pallet (e.g. `local_decimals=6`, `erc_decimals=18`, satisfying `18 >= 6` at registration) can later bump the asset's own decimals metadata upward past `erc_decimals` (e.g. to `19`). The next `send()` call then computes `erc_decimals.saturating_sub(local_decimals) = 18.saturating_sub(19) = 0`, so the raw integer amount the attacker burns/escrows (now denominated at 19-decimal precision, i.e. a small real value) is forwarded unscaled as the 18-decimal ERC20 amount to the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, which will mint/unlock 10x the intended value there relative to what was actually removed from the attacker's local balance.

### Impact Explanation
This directly produces unauthorized value creation across the bridge: the amount minted or released on the destination EVM chain no longer matches the amount escrowed or burned on the source chain, allowing the attacker to extract more real value on the destination than they gave up on the source — a fund-theft / fund-creation primitive that falls squarely within the bounty's "stealing or loss of funds" and "logic attacks" categories.

### Likelihood Explanation
The path only requires that an attacker (1) own/control a `pallet-assets` asset already registered with the HFT pallet at a valid `erc_decimals >= local_decimals` configuration, and (2) be permitted to update that asset's `decimals` metadata afterward — a standard, non-privileged asset-owner capability in most `pallet-assets` configurations, not requiring governance, a malicious relayer, or a compromised prover. The public `send()` extrinsic is the only additional step needed to trigger the mis-scaled dispatch, making this reachable by any ordinary user who is the owner of a registered asset.

### Recommendation
Re-validate `erc_decimals >= local_decimals` inside `send()` (and `on_accept`/`on_timeout`) immediately before calling `convert_to_erc20`/`convert_to_balance`, rejecting the transfer with `ErcDecimalsBelowLocal` if the live asset decimals have drifted past the value frozen in `Precisions`. Alternatively, make `convert_to_erc20`/`convert_to_balance` symmetric — handle both `erc_decimals >= local_decimals` and `erc_decimals < local_decimals` explicitly (dividing in the latter case) instead of relying on `saturating_sub` to silently clamp to zero.

### Proof of Concept
1. Governance/`CreateOrigin` registers asset `X` (owned by attacker in `pallet-assets`) via `register_token` with `local_decimals=6`, `erc_decimals=18` for destination chain `D` — passes the `ErcDecimalsBelowLocal` check (`18 >= 6`).
2. Attacker, as the asset's `pallet-assets` owner, calls `pallet_assets::set_metadata` (or equivalent) to change asset `X`'s decimals from `6` to `19`.
3. Attacker calls `send(params { asset_id: X, destination: D, amount: 1, ... })`. Inside `send()`:
   - `decimals` = `19` (read live).
   - `erc_decimals` = `18` (from `Precisions`, unchanged).
   - `convert_to_erc20(1, 18, 19)` → `18u8.saturating_sub(19u8) = 0` → `erc20_amount = 1 * 10^0 = 1`.
   - Correct scaled value should have been `1 / 10^(19-18) = 0` (or rejected), not `1`.
4. The `Message{ amount: 1 }` dispatched to chain `D`'s `HyperFungibleToken` contract is interpreted at 18-decimal precision — 10x the real value that was actually burned/escrowed locally (a value denominated at 19-decimal precision).
5. Repeating this with larger `amount` values and a larger decimal gap magnifies the discrepancy by `10^(local_decimals - erc_decimals)`, letting the attacker mint arbitrarily more value on the destination chain than what they gave up locally.
