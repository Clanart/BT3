### Title
Escrowed funds can be permanently locked when a settlement beneficiary is blacklisted by the escrowed token - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()` (and its Tron sibling `IntentGatewayV2.withdraw()`) releases escrowed order tokens by pushing an ERC-20 `transfer`/`safeTransfer` directly to the beneficiary address baked into the cross-chain settlement message (`RedeemEscrow`/`RefundEscrow`). If that beneficiary is later added to the token's blocklist (a routine compliance action for tokens like USDC/USDT), the transfer reverts every time the message is processed, and `EvmHost.dispatchIncoming` only clears the request receipt "so it can be retried" — it never succeeds, so the escrow is locked forever with no pull-based fallback. This is the same broken invariant as Sherlock H-4 in Cooler.sol: settlement is defined by a push-transfer to an address that a third party (the token issuer) can render permanently un-payable, and there is no `withdrawBalance`/`withdraw()` escape hatch.

### Finding Description
`IntentsBase._withdraw` is the single settlement primitive used for both cross-chain fills (`RedeemEscrow`, beneficiary = the filling solver) and cross-chain/refund cancellations (`RefundEscrow`, beneficiary = the original order user): [1](#0-0) 

Escrow decrement (`_orders[body.commitment][token] = escrowed - amount;`) happens *before* the transfer, and the transfer is a hard `safeTransfer`/native `.call` with no fallback accounting. The same pattern exists in the Tron port of the gateway: [2](#0-1) 

This function is only reachable through `onAccept`/`onGetResponse`, which are invoked by `EvmHost.dispatchIncoming`. When the inner call to `IApp.onAccept` reverts (as it will if the ERC-20 transfer to a blacklisted beneficiary reverts), the host does **not** treat this as a permanent failure — it silently deletes the request receipt so the message "can be retried": [3](#0-2) 

Because the underlying blacklist condition is persistent, every retry hits the exact same revert. There is no code path that lets the affected party pull their entitled tokens once the push fails — unlike, e.g., `Fees`/`available_amount` accounting used for relayer rewards, `IntentsBase` has no escrow "credit" ledger separate from the push-transfer. The escrowed input tokens (for a filled cross-chain order) or the refunded tokens (for a cancelled order) become permanently stuck in the `IntentGatewayV2` contract, exactly mirroring the Cooler.sol `repay()`/lender-blacklist scenario: a routine, non-malicious third-party action (a stablecoin issuer blacklisting an address) turns a settlement path into a dead end, and the funds cannot ever be recovered by the rightful owner through the existing contract logic.

### Impact Explanation
This is a direct "loss of funds" / fund-lock impact on bridge/custody logic, matching the bounty's accepted impact categories. Both settlement destinations are affected:
- **Solver's redeemed input tokens** (`RedeemEscrow`, cross-chain fill settlement) — if the filling solver's own address is later blacklisted by the input token before the fill message is delivered/processed, their earned tokens lock in the gateway forever.
- **User's refunded escrow** (`RefundEscrow`, cancel-from-destination flow, which is callable by *anyone* after the order deadline) — if the user's receiving address is blacklisted by the input token, their refund locks forever, and — critically — the permissionless post-deadline `cancelOrder()` call can be used by any unrelated party to *trigger* this dead-end state deterministically once the condition exists, since there is no way to redirect or pull the funds afterward.

Because the escrow accounting (`_orders[body.commitment][token]`) is decremented unconditionally before the transfer attempt inside `_withdraw`, the funds are neither returned to the sender nor recoverable — they are simply orphaned in the contract with no state pointing to them anymore in a way any function can act on.

### Likelihood Explanation
The precondition (token issuer blacklisting an address) is a realistic, non-attacker event for any token that supports a blocklist (USDC, USDT, and similar centrally-administered stablecoins are explicitly the intended fee/input tokens for this gateway). No malicious peer, relayer, prover, or governance actor is required — the trigger is an ordinary compliance action on a supported ERC-20, combined with the permissionless retry/cancel paths that are part of the normal, documented settlement flow (`onAccept`, `onGetResponse`, post-deadline `cancelOrder`).

### Recommendation
Do not make settlement (`_withdraw`/`withdraw`) depend on an unconditional push-transfer succeeding. Instead:
1. Wrap the ERC-20 transfer in a try/catch (or low-level call check) and, on failure, credit an internal `withdrawable[beneficiary][token] += amount` ledger instead of reverting the whole `onAccept`/`onGetResponse` call.
2. Add a permissionless `claim(token)` / `withdraw()` function that lets the beneficiary pull their credited balance (or redirect it to another address they control) once the push fails, so a blacklist on one address doesn't permanently strand protocol-custodied funds.
3. Apply the same fix to the Tron sibling contract's `withdraw()` function.

### Proof of Concept
1. User places a cross-chain order on chain A with input token `USDC_A`; solver fills it on chain B, escrow crediting `beneficiary = msg.sender` (the solver) is dispatched back to chain A as a `RedeemEscrow` message.
2. Before the relayer delivers the `RedeemEscrow` message to chain A, the solver's address is added to `USDC_A`'s blocklist (a normal compliance action, unrelated to this protocol).
3. The relayer submits the proof; `EvmHost.dispatchIncoming` calls `IntentGatewayV2.onAccept` → `_withdraw`, which calls `IERC20(USDC_A).safeTransfer(solver, amount)`; the call reverts because `USDC_A.transfer` reverts for a blacklisted recipient.
4. `dispatchIncoming` catches the revert, deletes `_requestReceipts[commitment]`, and returns without emitting `PostRequestHandled` — the message is now marked as retryable.
5. Any subsequent retry of the same proof/message hits the identical revert forever (the blacklist doesn't change), so the escrowed `amount` of `USDC_A` remains locked in the `IntentGatewayV2` contract indefinitely, with `_orders[commitment][USDC_A]` already decremented and no other code path granting access to it.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
