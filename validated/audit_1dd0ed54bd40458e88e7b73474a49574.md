### Title
Scanner accepts arbitrarily small deposits, letting an attacker drain the multisig via aggregation fees - (File: networks/bitcoin/src/lib.rs)

### Summary
The bug class: a participant/action is accepted without any minimum-value requirement, and the protocol spends shared resources (a per-action refund pool in FrankenDAO; transaction fees in Serai) servicing it. In Serai, an unprivileged attacker can send dust-value outputs to the multisig's Bitcoin address. The `Scanner` matches outputs purely by `script_pubkey` and reports them as received funds, regardless of value. Each such output must later be aggregated/spent by the validator set, and the fee to spend a Taproot input can exceed the output's value — a net drain on the vault with no stake or contribution required from the attacker.

### Finding Description
`Bitcoin::DUST` is defined as 10,000 sats and `COST_TO_AGGREGATE` as 800 sats (the estimated fee for a 2-in/1-out aggregation transaction) in `processor/src/networks/bitcoin.rs`. These constants are only enforced on *outgoing* flows: `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` rejects payments below `DUST` and only emits a change output when the leftover is `>= DUST`. Nothing on the *incoming* path requires that a received output be worth more than the cost of spending it. The `scanner()`/`Scanner` in `networks/bitcoin/src` registers only the tweaked `script_pubkey`s (external, branch, change, forward) and reports any matching output as a received `Output`, so a 546-sat (bare-dust) deposit is indistinguishable from a valuable one. The processor-side scan loop then treats every reported output as real balance to be forwarded/refunded/aggregated, pushing `PlanFromScanning` items that consume fees.

### Impact Explanation
Each accepted sub-spendable output forces the multisig to eventually include it as an input in an aggregation or rotation transaction. A Taproot input adds ~57 vbytes; at any nonzero feerate the marginal fee exceeds the attacker's deposit when the deposit is below that marginal cost. An attacker with no stake — the "zero-vote voter" — can therefore burn an unbounded amount of vault funds, one dust output at a time, paying less than the fees destroyed. This mirrors the FrankenDAO finding where refund-per-address let zero-vote accounts drain a fee pool.

### Likelihood Explanation
Fully public and unprivileged: sending a Bitcoin transaction to the published multisig deposit address requires no key material, no participation in the DKG, and no stake. Cost to the attacker is strictly less than the damage inflicted. (Note: I could not fully read the `Scanner` matching internals within this iteration; the claim that value is not filtered relies on `script_pubkey`-only matching consistent with `scanner()` usage in `branch_address`/`change_address` and the processor scan loop, which never checks `output.balance()` against `DUST`/`COST_TO_AGGREGATE` before creating plans.)

### Recommendation
Have the `Scanner` (or the scan-processing layer consuming it) ignore outputs below a threshold derived from `DUST`/`COST_TO_AGGREGATE`, or at minimum flag them so they are never selected as inputs for aggregation — analogous to reverting on `votes == 0`. An alternative mitigation is to only aggregate inputs whose value exceeds their marginal spend cost.

### Proof of Concept
1. Attacker computes the multisig's external P2TR address (public knowledge, derivable from the group key via `p2tr_script_buf`/`address_from_key`).
2. Attacker broadcasts N transactions each paying ~600 sats to that address — total cost ~600N sats.
3. `Scanner` reports all N outputs as received balance; they enter `outputs` and produce plans.
4. Rotation/aggregation must spend them; each input costs ~57+ vbytes of fee (≥ hundreds of sats, and in aggregate far more than 600 sats once output overhead is included), so the vault loses more than the attacker spent. With N large, cumulative drain is unbounded.
