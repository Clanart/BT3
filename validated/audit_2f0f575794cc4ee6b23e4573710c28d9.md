### Title
Payout transaction's operator-attribution `OP_RETURN` is not covered by the user's signature, allowing anyone to reassign reimbursement credit and get an honest operator wrongly challenged - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The bug class in the external report is a control that is *supposed* to bind a value/attribute to a specific party but can be bypassed because the enforcement mechanism does not actually cover all the representations/paths that matter. In Clementine, the analogous binding is: **the operator credited for a withdrawal payout (`payout_payer_operator_xonly_pk`) must equal the operator who actually fronted/broadcast that payout**. This binding is not enforced cryptographically — the operator identity is embedded in a plain, unsigned `OP_RETURN` output of the payout transaction, while the user's signature only covers the withdrawal input and the withdrawal output (via `SIGHASH_SINGLE | ANYONECANPAY`). Because `ANYONECANPAY|SINGLE` leaves all other inputs/outputs of the transaction unauthenticated, any unprivileged party who observes the (unconfirmed) payout transaction can rebroadcast a variant of it with a different `OP_RETURN` payload — including a bogus xonly public key — while still spending the exact same signed withdrawal input/output. Whichever version confirms determines `payout_payer_operator_xonly_pk` in the verifier's database, breaking the credited-operator ↔ actual-payer binding.

### Finding Description
The payout transaction is built in `create_payout_txhandler`: [1](#0-0) 

Only input 0 (the withdrawal UTXO) is signed via `set_p2tr_key_spend_witness(&user_sig, 0)`; the `op_return_txout` carrying `operator_xonly_pk` (output index 2) is added as plain, unsigned data.

The user's signature is required to use `SinglePlusAnyoneCanPay`, as documented in `Operator::withdraw`: [2](#0-1) 

`SIGHASH_SINGLE | ANYONECANPAY` commits only to: (a) the single input being signed, and (b) the single output at the same index as that input. It explicitly does **not** commit to any other input or any other output (including the anchor output and, crucially, the `OP_RETURN` attribution output). Any party that funds the transaction (adds inputs via `ANYONECANPAY`) is therefore free to swap out the `OP_RETURN` output for one containing an arbitrary xonly public key, while keeping the identical signed withdrawal input/output — i.e., the payout to the user is unaffected, but the recorded "who fronted this" attribution is entirely unauthenticated.

The sync logic that later reads this data does not validate it against who actually broadcast/funded the transaction — it just parses whatever `OP_RETURN` ends up in the version that gets mined: [3](#0-2) 

This value is persisted as `payout_payer_operator_xonly_pk` and later used to decide whether a specific operator's kickoff is legitimate: [4](#0-3) 

If the operator xonly pk parsed from the (attacker-substituted) `OP_RETURN` does not match `kickoff_data.operator_xonly_pk`, the kickoff is treated as malicious and a `Challenge` transaction is queued: [5](#0-4) 

So the honest operator who actually fronted the withdrawal (paid the user, and whose own capital funds the reimbursement flow via `Kickoff`/`Reimburse`) can be permanently blocked from a legitimate reimbursement by anyone who races/RBFs the mempool with a modified `OP_RETURN`, because the DB's `payout_payer_operator_xonly_pk` will no longer match `kickoff_data.operator_xonly_pk` for the honest operator's subsequent kickoff.

### Impact Explanation
This breaks the custody-attribution binding `credited_operator == party_that_fronted_the_payout`, matching the Critical impact category "an honest operator permanently unable to be reimbursed." An unprivileged party observing mempool/broadcast traffic (no verifier/operator/watchtower role required) can rewrite the unsigned portion of an in-flight payout transaction and get a modified version mined instead, corrupting the on-chain attribution record that the verifier's reimbursement-validity check depends on.

### Likelihood Explanation
Exploitation requires only: (1) visibility into the mempool/broadcast payout transaction (public, unprivileged), and (2) ability to construct and get mined a competing transaction that spends the same `ANYONECANPAY`-signed input with a different `OP_RETURN` output and its own fee-paying input(s) — standard permissionless Bitcoin transaction construction and fee-bumping/racing, not requiring any protocol-privileged role, key compromise, or majority hashrate. The likelihood is bounded mainly by whether the original operator's transaction confirms first (a race), but this is not a defense the protocol relies on — the codebase provides no cryptographic protection of the `OP_RETURN` attribution field at all.

### Recommendation
Bind the operator attribution to the user-authenticated portion of the payout transaction, e.g., by having the user's signature cover the `OP_RETURN` output as well (e.g., using `SIGHASH_ALL|ANYONECANPAY` scoped appropriately, or committing the operator pubkey into the signed output's script instead of a separate unsigned `OP_RETURN`), or by having verifiers independently attest/sign which operator is entitled to credit rather than trusting unauthenticated transaction data parsed post-hoc from the chain.

### Proof of Concept
1. Operator A obtains the user's `SinglePlusAnyoneCanPay` signature for a withdrawal and constructs/broadcasts `payout_tx_A`: input = withdrawal UTXO (signed), output0 = user payout (signed), output1 = anchor, output2 = `OP_RETURN(operator_A_xonly_pk)` (both unsigned).
2. Before `payout_tx_A` confirms, an unprivileged observer extracts the signed input/output pair (public in the mempool) and constructs `payout_tx_B`: same signed input/output0, but output2 = `OP_RETURN(bogus_or_other_xonly_pk)`, funded with the observer's own extra input and a higher fee.
3. `payout_tx_B` gets mined instead (via fee race or RBF).
4. `update_finalized_payouts` (`core/src/verifier.rs:2311-2343`) parses `bogus_or_other_xonly_pk` from `payout_tx_B`'s `OP_RETURN` and stores it as `payout_payer_operator_xonly_pk`.
5. When operator A later sends its legitimate `Kickoff` transaction for that deposit, `is_kickoff_malicious` (`core/src/verifier.rs:1857-1890`) finds `operator_xonly_pk != kickoff_data.operator_xonly_pk` and returns `true`, causing verifiers to treat operator A's kickoff as malicious and queue a `Challenge` transaction (`core/src/verifier.rs:1966-2017`), denying operator A the reimbursement for a payout it actually funded.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()

    /// Checks if the kickoff is malicious and sends the appropriate txs if it is.
    /// Returns true if the kickoff is malicious.
    /// Sends a challenge tx if the kickoff is first malicious one in the current round, and the network is not mainnet or testnet4.
    pub async fn handle_kickoff<'a>(
        &'a self,
        dbtx: DatabaseTransaction<'a>,
        kickoff_witness: Witness,
        mut deposit_data: DepositData,
        kickoff_data: KickoffData,
        challenged_before: bool,
    ) -> Result<bool, BridgeError> {
        let is_malicious = self
            .is_kickoff_malicious(kickoff_witness, &mut deposit_data, kickoff_data, dbtx)
            .await?;

        let deposit_outpoint = deposit_data.get_deposit_outpoint();

        let (_signed_txs, tx_metadata, challenge_tx) = self
            .get_signed_txs_for_kickoff(dbtx, kickoff_data, deposit_data)
            .await?;

        if is_malicious {
            tracing::warn!(
                "Malicious {} detected. {} Challenge tx: {} for deposit {}",
                kickoff_data,
                match challenged_before {
                    false => "This is the first malicious kickoff in the current round.",
                    true => "This is not the first malicious kickoff in the current round.",
                },
                bitcoin::consensus::encode::serialize_hex(&challenge_tx),
                deposit_outpoint
            );
            // do not automatically send challenge txs on mainnet or testnet4
            if !challenged_before
                && !matches!(
                    self.config.protocol_paramset().network,
                    bitcoin::Network::Bitcoin | bitcoin::Network::Testnet4
                )
            {
                #[cfg(feature = "automation")]
                self.tx_sender
                    .add_tx_to_queue(
                        dbtx,
                        TransactionType::Challenge,
                        &challenge_tx,
                        &[],
                        Some(tx_metadata),
                        self.config.protocol_paramset(),
                        None,
                    )
                    .await?;
            }
