### Title
Signature-replay force-association via the `addr` precompile's `associate` — no chain/domain binding on `customMessage` allows off-chain signature reuse to hijack address linkage and drain cast-address balances (File: precompiles/addr/addr.go)

### Summary
The `associate` (and `associatePublicKey`) methods of the `addr` precompile recover an ECDSA public key from a caller-supplied `(v, r, s, customMessage)` tuple and unconditionally use it to permanently bind an EVM address to a Sei address, sweeping any balance held under the cast address into the newly linked address. Like the PocketMine-MP flaw, a cryptographically valid signature is treated as sufficient proof of "current, intended" authorization, without any binding to Sei chain ID, precompile-specific domain separator, or nonce — so a signature captured or observed in an unrelated context can be replayed by *anyone* to trigger association on behalf of a victim who never intended to interact with Sei.

### Finding Description
`PrecompileExecutor.associate` takes `v`, `r`, `s`, and an arbitrary `customMessage` string directly from calldata, hashes `customMessage` with Keccak256, and recovers `(evmAddr, seiAddr, pubkey)` from the signature over that hash: [3](#0-2) 

There is no restriction on what `customMessage` may contain — no chain ID, no precompile address, no purpose tag, no nonce, and no requirement that `msg.sender`/`tx.origin` correlate with the recovered address. Any transaction submitter can present a signature the address owner produced for an entirely different purpose (e.g., a `personal_sign`/EIP-191 message signed for another dApp, another EVM chain, or a message accidentally reused with the same `"\x19Ethereum Signed Message:\n..."` envelope Sei expects), as long as the exact bytes and signature are known to the caller.

Once recovered, `associateAddresses` immediately calls `AssociationHelper.AssociateAddresses`, which:
- Sets the permanent, irreversible `evmAddr <-> seiAddr` mapping via `SetAddressMapping`.
- Calls `MigrateBalance`, which sweeps *all* spendable coins and wei balance from the direct-cast address (`sdk.AccAddress(evmAddr[:])`) into the newly associated `seiAddr`, and removes the cast account if it has no locked coins. [1](#0-0) [2](#0-1) 

This is architecturally identical to the reported PocketMine-MP bug class: the system verifies "was this signed by the claimed private key" but never verifies "was this signature intended for *this* action/context," so a valid signature captured elsewhere can be replayed to force state-changing side effects (address linkage + balance migration) the true key holder never authorized for Sei.

Notably, the codebase has already recognized and patched this exact bug class for the EIP-7702 `SetCodeAuthorization` pre-association path, adding an explicit chain-ID check specifically to prevent "a publicly-visible authorization a user signed for another chain... replayed... to force-associate them — migrating their direct-cast balance": [4](#0-3) [5](#0-4) 

But the `associate`/`associatePublicKey` precompile entry points that also invoke `AssociateAddresses`/`MigrateBalance` have no analogous chain-binding or domain-separation checks on the attacker-controlled `customMessage`, leaving the same underlying replay/impersonation vector open through this alternate call path.

### Impact Explanation
If a victim's EVM address has already received funds via direct address-casting (i.e., before ever associating on Sei — a normal and common scenario for any address that receives a token transfer or receives usei prior to onboarding), and the victim's public key/signature has been exposed in any off-chain or cross-chain context using the same EIP-191-style envelope, an attacker can:
1. Replay that signature and message through `addr.associate(v, r, s, customMessage)`.
2. Trigger `AssociateAddresses`, which force-migrates the victim's cast-address balance to the recovered `seiAddr` and deletes the cast account.

Because `seiAddr` is deterministically derived from the victim's own public key, the funds land in an address only the victim controls — so this is not a direct fund-theft vector by itself, but it does allow an unauthorized, irreversible state change (forced permanent association, balance sweep out of the direct-cast address, deletion of the cast account, and blocking the victim from ever independently controlling the direct-cast address's balance/nonce/staking history) without the victim's consent or awareness at a time of the attacker's choosing. This matches the "unauthorized transfer via precompile" and "permanent freezing" impact classes for the account's prior direct-cast identity and any staking/distribution state tied to it.

### Likelihood Explanation
Exploitation requires the attacker to have observed one valid signature+message pair from the target over the specific EIP-191 hash format the precompile accepts. This is a realistic bar to clear (e.g., a message signed for a different dApp using the same client library/envelope, or a signature leaked via a malicious or compromised front-end), consistent with the original report's threat model where the attacker "tricks" the victim into producing a capturable credential. Given `customMessage` is fully attacker-controlled and unauthenticated against Sei's own domain, exploitation is directly reachable by any public RPC client submitting a transaction to the precompile — no privileged access required.

### Recommendation
Bind the `associate` signature to an explicit Sei/domain-specific and chain-ID-bound message format (mirroring the fix already applied to `SetCodeAuthorization` pre-association), and/or require a nonce or nonce-like nonaction constant scoped to this precompile so signatures cannot be replayed from unrelated contexts. Reject `customMessage` values that don't match a fixed, precompile-owned template.

### Proof of Concept
1. Victim signs any EIP-191 message `M` for a different application/chain using their EOA key, producing `(v, r, s)`; this signature+message becomes observable to the attacker (e.g., logged by a compromised or malicious front-end, or reused from a public transaction on another chain using the same signing scheme).
2. Victim's EVM address has previously received `usei`/tokens via direct address-casting on Sei (common before the victim ever associates).
3. Attacker submits `addr.associate(v, r, s, M)` from any account.
4. `helpers.GetAddresses` recovers `(evmAddr, seiAddr, pubkey)` from `(v,r,s)` over `keccak256(M)` — [6](#0-5)  — succeeding regardless of the victim's intent for Sei.
5. `associateAddresses` → `AssociationHelper.AssociateAddresses` → `MigrateBalance` sweeps the victim's cast-address balance to `seiAddr` and deletes the cast account, all without the victim ever submitting a Sei transaction — [2](#0-1) .

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)

// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true
