## Title
Attacker-Controlled `WWW-Authenticate` Realm Header Redirects Users Into an Enterprise Sign-In Flow Bound to an Arbitrary Host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

## Summary
When Git needs credentials for an HTTPS remote, it forwards any `WWW-Authenticate` response headers it received to Desktop's credential-helper trampoline. `getEndpointKind` in `trampoline-credential-helper.ts` trusts the string `realm="GitHub"` in that header — which is fully controlled by the remote server the user is fetching/cloning/pulling from — to classify an arbitrary, non-GitHub host as an `'enterprise'` GitHub endpoint.

## Finding Description
`getEndpointKind` first checks static hostname patterns (`isDotCom`, `isGHE`), then falls back to inspecting credential map entries returned by Git: [1](#0-0) 

Because this loop runs before any real verification (`isGitHubHost`, which performs an actual network probe, only runs afterward as a fallback and is bypassed entirely once a `wwwauth[...]` entry matching `realm="GitHub"` is found), an attacker who controls the HTTP(S) server for a git remote (e.g., a malicious or compromised git host, a spoofed corporate mirror, or a MITM/malicious proxy) can simply respond to Git's initial unauthenticated request with `WWW-Authenticate: Basic realm="GitHub"` on any domain they own, and Desktop will treat that arbitrary domain as `'enterprise'`.

That classification flows into `getCredential`: [2](#0-1) 

Since no `Account` exists for the attacker's fake endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, which invokes `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)` using the **attacker-controlled origin** as the GitHub Enterprise API endpoint, then shows the standard `SignIn` popup: [3](#0-2) 

The resulting dialog explicitly frames this as a normal credential-helper prompt ("Git requesting credentials to access…") rather than warning the user that authentication data will be sent to a host the user did not knowingly choose: [4](#0-3) 

If the user completes the Enterprise sign-in (basic auth or browser/OAuth flow) believing it relates to the legitimate service they cloned from, their username/password or OAuth authorization is directed at the attacker's endpoint (`setSignInEndpoint(origin)` drives subsequent `fetchUser`/`requestOAuthToken`/`getEnterpriseAPIURL` calls against that origin), and Desktop may persist an `Account` bound to that attacker-controlled endpoint via `AccountsStore`.

## Impact Explanation
This lets an attacker-controlled git remote/proxy response spoof Desktop's UI into initiating an authentication flow (basic credential entry or OAuth) scoped to an arbitrary domain the attacker controls, potentially resulting in credential/token exfiltration or the creation of a spoofed/attacker-bound "Enterprise" `Account` inside Desktop — matching the "unauthorized OAuth or account binding" / "credential exfiltration" categories of valid impact. The underlying broken invariant is the same class as the report's seed: a value meant to be constrained by trusted, verified state (a properly-vetted GitHub/GHE endpoint) is instead derived from unauthenticated, attacker-supplied input (the `WWW-Authenticate` header text) without cross-checking, similar to how the seed report's approval TTL was implicitly bounded by an unverified/uncontrolled external constraint.

## Likelihood Explanation
Any git operation against an attacker-hosted or MITM'd HTTPS remote naturally triggers a `get` credential-helper request whenever the server returns 401; setting a custom `WWW-Authenticate` header is trivial for a server operator. No local access, malware, or unusual user action beyond a normal clone/fetch and (for full impact) completing a familiar-looking sign-in dialog is required, which fits the "unprivileged" and "git remote/proxy response" attacker model.

## Recommendation
Do not classify an endpoint as GitHub/Enterprise based solely on a self-reported `WWW-Authenticate` realm string. Require independent verification (e.g., the existing `isGitHubHost` network probe against well-known GitHub API markers, or matching against an explicitly user-added Enterprise endpoint) before routing the user into `beginEnterpriseSignIn`/`setSignInEndpoint` with an untrusted origin, and surface a clear warning in the sign-in dialog when the endpoint was derived from an untrusted server-supplied hint rather than a previously configured account.

## Proof of Concept
1. Host an HTTPS server for a repo URL, e.g. `https://evil.example.com/repo.git`.
2. Configure the server so that on Git's unauthenticated request it responds `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
3. In GitHub Desktop, clone/fetch `https://evil.example.com/repo.git`.
4. Git forwards the header to the credential helper; `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`) returns `'enterprise'` for `evil.example.com`.
5. No matching `Account` exists, so `ui.promptForGitHubSignIn('https://evil.example.com')` fires, opening the Sign-In dialog bound to `evil.example.com` as if it were a legitimate GitHub Enterprise server.
6. If the user proceeds, their credentials/OAuth flow are directed at the attacker's server.

Note: I was unable to execute this PoC in a live app instance (no filesystem/runtime access here); the analysis is based on the source code paths cited above. To confirm exploitability end-to-end (browser OAuth callback handling, `isGitHubHost` fallback ordering under real network conditions), a Devin session with full app execution would be needed.

```typescript
  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
```

```typescript
  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
```
