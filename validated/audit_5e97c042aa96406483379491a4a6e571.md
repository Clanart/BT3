### Title
Missing existence check on `proofs` map causes panic (NULL-deref analog) in `GeneratorPromotion::complete` - ([File: crypto/dkg/promote/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary
Analogous to CVE-2023-31129 (a lookup result used without verifying it exists), `GeneratorPromotion::complete` indexes an attacker-influenced `HashMap<Participant, GeneratorProof>` with `.unwrap()` without first confirming the required participant key is present. A peer participant in the DKG/promotion ceremony can supply a proof keyed under the victim's own index (`params.i()`), satisfying the count/bounds checks while leaving another participant's entry missing, causing `proofs.get(&i).unwrap()` to panic and abort the promotion.

### Finding Description
`complete` validates only two properties of the peer-supplied `proofs` map before iterating `1 ..= n` and unwrapping each entry:

```rust
// crypto/dkg/promote/src/lib.rs
if proofs.len() != (usize::from(params.n()) - 1) {
  Err(PromotionError::IncorrectAmountOfParticipants { ... })?;
}
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() {
    Err(PromotionError::InvalidParticipant { ... })?;
  }
}
...
let proof = proofs.get(&i).unwrap();   // line 146
```

The loop at line 140–146 assumes the `n - 1` distinct keys (`HashMap` keys are unique, all `<= n`) exclude exactly `params.i()` and therefore cover every `i != params.i()`. But nothing rejects a proof submitted under `params.i()` itself. In that case, some other participant `j` is missing from the map, and `proofs.get(&j).unwrap()` at line 146 dereferences a `None` — the direct Rust analog of dereferencing the NULL `uip_ds6_nbr_t` returned by the failed neighbor lookup in `uip-nd6.c`.

This mirrors the same missing-check pattern elsewhere in the DKG surface (`self.commitments[&l]` in `KeyMachine::calculate_share` panics if a participant skipped round 1 but sends a share, and `self.commitments[&sender]` in `BlameMachine::blame_internal` panics on an out-of-range `sender`), but `GeneratorPromotion::complete` is the cleanest reachable instance: the `GeneratorProof` values are attacker-controlled bytes parsed via `GeneratorProof::read` and the map keys are chosen by the submitting party.

### Impact Explanation
A single malicious or faulty participant can panic any honest peer running `GeneratorPromotion::complete`, aborting the generator-promotion ceremony for that party. In a threshold network this prevents the key set from being promoted to the alternate generator, denying service to the signing group; repeated across `t` victims it can stall the entire ceremony. Panics in Serai's signing nodes take down the process mid-protocol, which is the same availability impact class as the NULL dereference in the reference advisory.

### Likelihood Explanation
Reachable by any participant in a DKG session who reaches the promotion phase: they submit `n - 1` proofs total but include one keyed under the victim's `params.i()` rather than their own index. The count check (`n - 1`) and the upper-bound check (`<= n`) both pass, so the panic is deterministic. No collusion or control of other parties is required.

### Recommendation
Before the `for i in 1 ..= params.n()` loop, reject a proof keyed under `params.i()` and require every other index to be present — e.g. `if proofs.contains_key(&params.i()) { Err(...) }` and replace `proofs.get(&i).unwrap()` with `let Some(proof) = proofs.get(&i) else { Err(PromotionError::MissingParticipant(i))? }` (adding a `MissingParticipant` variant, as `PedPoPError` already has). Apply the same `get`-with-error pattern to `self.commitments[&l]` in `crypto/dkg/pedpop/src/lib.rs` `calculate_share`/`blame_internal` and to `self.decryption.enc_keys[&participant]` in `encryption.rs`.

### Proof of Concept
```rust
// Let params = ThresholdParams { t: n, n: 5, i: Participant(1) } for the victim.
// Attacker (participant 2) produces a GeneratorProof but the coordinator/caller
// inserts it into `proofs` under key Participant(1) instead of Participant(2).
let mut proofs = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof); // victim's own index
for p in 3 ..= 5 {
  proofs.insert(Participant::new(p).unwrap(), honest_proof[p]);
}
// proofs.len() == 4 == n - 1, all keys <= n: checks pass.
// Loop reaches i = Participant(2), proofs.get(&2) == None -> unwrap() panics.
promotion.complete(&proofs); // thread panic, promotion aborted
```
