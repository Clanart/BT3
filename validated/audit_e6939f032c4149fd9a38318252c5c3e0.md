### Title
Selector Collision Between `CW20ERC20Pointer.transferFrom()` and `CW721ERC721Pointer.transferFrom()` Allows an ERC721 Pointer to Be Accepted Wherever an ERC20/CW20 Pointer Is Expected - (File: `contracts/src/CW20ERC20Pointer.sol`, `contracts/src/CW721ERC721Pointer.sol`)

### Summary
Sei-chain auto-deploys wrapper contracts (via the `pointer` precompile / `RegisterPointer` msg) that let EVM contracts interact with CosmWasm CW20 and CW721 tokens: `CW20ERC20Pointer.sol` and `CW721ERC721Pointer.sol`. Both expose a `transferFrom(address,address,uint256)` function, which produces the identical 4-byte selector `0x23b872dd`, exactly the collision class described in the referenced Putty finding (ERC20 vs ERC721 `transferFrom` selector overlap). Because sei-chain itself does not force downstream integrators to disambiguate pointer type before use, any protocol built on Sei that generically calls `IERC20(token).transferFrom(...)` against a caller-supplied token address can be tricked into accepting a CW721 pointer address in place of a CW20 pointer address, moving an NFT into the protocol under `transfer_from` (NFT) semantics while the protocol believes it received fungible tokens, then being unable to withdraw it because `CW721ERC721Pointer` never implements `transfer(address,uint256)` (selector `0xa9059cbb`), which is the withdrawal path used for ERC20/CW20 pointers.

### Finding Description
`CW20ERC20Pointer.transferFrom(address from, address to, uint256 amount)` [1](#0-0)  and `CW721ERC721Pointer.transferFrom(address from, address to, uint256 tokenId)` [2](#0-1)  both compile to the exact same function selector `0x23b872dd`, since Solidity selectors are derived purely from parameter types (`address,address,uint256`), not parameter names or the underlying CW20/CW721 semantics they proxy to.

These two pointer types are created permissionlessly through the `pointer` precompile's `addCW20Pointer`/`addCW721Pointer` (or `RegisterPointer` msg) entry points [3](#0-2) [4](#0-3) , and are tracked in separate keeper namespaces (`GetERC20CW20Pointer` vs `GetERC721CW721Pointer`) [5](#0-4) . Nothing in the EVM itself, nor in a naive Solidity-level integration, prevents a contract from calling `transferFrom(address,address,uint256)` on a `CW721ERC721Pointer` address while believing it is dealing with an ERC20/CW20 pointer — the call succeeds and silently executes `transfer_nft` on the wrapped CW721 contract, using the `uint256` parameter as a `tokenId` rather than an amount.

Critically, `CW721ERC721Pointer.sol` has no `transfer(address,uint256)` function (selector `0xa9059cbb`) — its only egress path is `transferFrom`/`approve`+`transferFrom` [6](#0-5) . Any protocol that receives assets via `transferFrom` and later attempts to release them via `IERC20.transfer()` (the common ERC20 withdrawal idiom, exactly as in the original Putty report) will permanently fail to move the NFT back out, exactly mirroring the referenced vulnerability class.

The precompile team does provide a disambiguation mechanism — the `pointerview` precompile's `getCW20`/`getCW721`/`getCW1155` view functions [7](#0-6)  — but nothing forces third-party contract developers on Sei to use them before whitelisting a token address as "ERC20-compatible."

### Impact Explanation
Any unprivileged contract deployer building a DeFi protocol (lending, escrow, DEX, order-book/OTC contracts analogous to Putty) on Sei that accepts a caller-supplied token address and treats it generically as ERC20 (calling `transferFrom`) is exposed: a user can supply a `CW721ERC721Pointer` address instead of a `CW20ERC20Pointer`/native ERC20 address. The `transferFrom` call succeeds due to selector collision, transferring an NFT into the protocol under fungible-token bookkeeping assumptions, with no compatible egress path (`transfer(address,uint256)` does not exist on the CW721 pointer), resulting in the NFT being permanently stuck in the protocol contract — a concrete, permanent freezing of user funds/assets, satisfying the "permanent freezing" impact bar.

### Likelihood Explanation
Likelihood is moderate: the flaw requires a downstream integrator to (a) accept caller-supplied token addresses without an ERC165 `supportsInterface` or `pointerview` type check, and (b) call the shared `transferFrom` selector generically. This mirrors exactly how the original Putty Finance bug was reachable — via ordinary user-submitted parameters at `fillOrder()`-equivalent entry points — and Sei's pointer architecture intentionally deploys both pointer types with the same interface shape, making this a systemic risk for the wider Sei EVM ecosystem rather than a one-off contract bug in the core protocol.

### Recommendation
- Document and strongly recommend (or enforce at the pointer-contract level) that integrators verify pointer/token type via ERC165 `supportsInterface` (`IERC721` interface ID) or via the `pointerview` precompile's `getCW20`/`getCW721` lookups before accepting a token address as ERC20-compatible.
- Consider adding an explicit `type()`/`tokenStandard()` view function to both `CW20ERC20Pointer.sol` and `CW721ERC721Pointer.sol` that returns a machine-checkable discriminator, and have `CW721ERC721Pointer` revert distinctively (not merely lack) any two-argument `transfer`-like call so downstream integrators fail closed rather than silently succeed.
- Where sei-chain ships reference/example integration contracts or SDKs for pointer usage, ensure they demonstrate type-checking before calling `transferFrom`.

### Proof of Concept
1. Deploy (or locate) a `CW721ERC721Pointer` for some CW721 collection via `addCW721Pointer`/`RegisterPointer`.
2. Build (or use an existing) protocol contract `P` that accepts a user-specified `token` address and calls `IERC20(token).transferFrom(msg.sender, address(P), amount)` to pull collateral/payment, without checking `supportsInterface(type(IERC721).interfaceId)`.
3. Attacker owns an NFT tracked by the CW721 pointer and calls into `P`, passing the CW721 pointer's address as `token` and the NFT's `tokenId` as `amount`.
4. `P`'s call to `transferFrom(attacker, P, tokenId)` resolves to selector `0x23b872dd` on the CW721 pointer, which executes `transfer_nft`, moving the NFT into `P`.
5. `P` later attempts `IERC20(token).transfer(attacker, amount)` to refund/withdraw — this reverts or does nothing meaningful because `CW721ERC721Pointer` has no compatible `transfer(address,uint256)`, leaving the NFT permanently stuck in `P`.

func (p PrecompileExecutor) AddCW20(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, suppliedGas uint64, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	cwAddr := args[0].(string)
	existingAddr, existingVersion, exists := p.evmKeeper.GetERC20CW20Pointer(ctx, cwAddr)
	if exists && existingVersion >= 1 {
		return nil, 0, fmt.Errorf("pointer at %s with version %d exists when trying to set pointer for version %d", existingAddr.Hex(), existingVersion, cw20.CurrentVersion(ctx))
	}
	cwAddress, err := sdk.AccAddressFromBech32(cwAddr)
	if err != nil {
		return nil, 0, err
	}
	res, err := p.wasmdKeeper.QuerySmart(ctx, cwAddress, []byte("{\"token_info\":{}}"))
	if err != nil {
		return nil, 0, err
	}
	formattedRes := map[string]interface{}{}
	if err := json.Unmarshal(res, &formattedRes); err != nil {
		return nil, 0, err
	}
	name := formattedRes["name"].(string)
	symbol := formattedRes["symbol"].(string)
	constructorArguments := []interface{}{
		cwAddr, name, symbol,
	}

	packedArgs, err := cw20.GetParsedABI().Pack("", constructorArguments...)
	if err != nil {
		panic(err)
	}
	bin := append(cw20.GetBin(), packedArgs...)
	if value == nil {
		value = utils.Big0
	}
	ret, contractAddr, remainingGas, err := evm.Create(caller, bin, suppliedGas, uint256.MustFromBig(value))
	if err != nil {
		return
	}
	err = p.evmKeeper.SetERC20CW20Pointer(ctx, cwAddr, contractAddr)
	if err != nil {
		return
	}

	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypePointerRegistered, sdk.NewAttribute(types.AttributeKeyPointerType, "cw20"),
		sdk.NewAttribute(types.AttributeKeyPointerAddress, contractAddr.Hex()), sdk.NewAttribute(types.AttributeKeyPointee, cwAddr),
		sdk.NewAttribute(types.AttributeKeyPointerVersion, fmt.Sprintf("%d", cw20.CurrentVersion(ctx)))))
	ret, err = method.Outputs.Pack(contractAddr)
	return
}
