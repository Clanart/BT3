Panic on out-of-bounds index into `Interpolation::Constant` coefficients via untrusted `ThresholdKeys` deserialization - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to CVE-2022-29224 — where Envoy held a reference to a host that was removed while a health check was pending and then dereferenced a null pointer — `ThresholdKeys` construction and use in Serai's `dkg` crate dereferences coefficient entries of `Interpolation::Constant` by participant index without ever checking that the coefficient vector is long enough. An attacker who can cause `Interpolation::Constant(vec![])` (or any short vector) to be deserialized inside `ThresholdKeys` — e.g., through the in-scope `ThresholdKeys::read` entry point — crashes the process with a slice index panic, the Rust analog of Envoy's segmentation fault.

### Finding Description
`ThresholdKeys::new` validates only the *count* and *upper bound* of the verification-share map and that `t == n` for `Interpolation::Constant`; it never validates `c.len()`. Immediately afterward it computes the group key by calling `interpolation_factor` for participants `1..=t` [1](#0-0) , and `interpolation_factor` indexes `c[usize::from(u16::from(i) - 1)]` unconditionally [2](#0-1) . The only Constant-specific check is `params.t() != params.n()` [3](#0-2) , so a `Constant(Vec::new())` with `t == n` passes all validation and then panics on `c[0]` inside the same constructor. The same unchecked index is hit again in `ThresholdKeys::view`, which calls `interpolation_factor` for every included participant [4](#0-3)  — the "held object removed/failed check then dereferenced" pattern: a structure that is missing data it is assumed to contain is dereferenced on the delayed-use path. Like the Envoy fix, the missing piece is a validity check at ingestion; the panic is an uncontrolled abort of the host process rather than a returned `DkgError`.

### Impact Explanation
A panic in Rust aborts or unwinds the calling thread; in the coordinator/processor context where `ThresholdKeys`/`ThresholdView` are used for every signature, this crashes the node handling the malformed keys — a denial of service directly analogous to the Envoy null-pointer dereference crash. It is reachable purely from attacker-controlled bytes supplied to `ThresholdKeys::read`, one of the explicitly in-scope untrusted-input surfaces. No secret material is leaked, so this is a Medium-severity availability bug, matching the source advisory's severity.

### Likelihood Explanation
`Interpolation::Constant` is constructed from a serialized `Vec<F>` whose length is whatever the bytes encode; nothing in the deserialization path (`Participant`'s borsh guard aside) bounds it to `n`. `ThresholdKeys::new`'s checks (map length `== n`, keys `<= n`, `t == n`) [5](#0-4)  all pass for a short or empty coefficient vector, making the panic deterministic once the malformed keys are read or constructed. A caveat: I could not fully confirm the exact wire path by which external bytes reach `ThresholdKeys::read` in production (the `read` implementation itself was not located in the indexed `dkg/src` files), so reachability rests on the documented in-scope entry point rather than a traced call chain.

### Recommendation
In `ThresholdKeys::new` (`crypto/dkg/src/lib.rs`), extend the `Interpolation::Constant` arm to reject `c.len() != usize::from(params.n())` with a `DkgError` (e.g., `InapplicableInterpolation` or a new variant) before computing `group_key`. Additionally, `interpolation_factor` could defensively return `Option<F>` or use `c.get(i - 1)` to convert any residual out-of-bounds access into an error rather than a panic.

use ciphersuite::Ristretto;

// t == n == 2, Constant interpolation with an EMPTY coefficient vector
let params = ThresholdParams::new(2, 2, Participant::new(1).unwrap()).unwrap();

shares.insert(Participant::new(1).unwrap(), <Ristretto as Ciphersuite>::generator());
shares.insert(Participant::new(2).unwrap(), <Ristretto as Ciphersuite>::generator());

// Passes validation (t == n, shares.len() == n, keys <= n),
// then panics on `c[0]` inside `interpolation_factor` while computing `group_key`.
let _ = ThresholdKeys::<Ristretto>::new(
    params,
    Interpolation::Constant(vec![]),          // deserialized from attacker bytes: zero coefficients
    Zeroizing::new(<Ristretto as Ciphersuite>::F::ONE),
    shares,
);
