### Title
Division-by-zero panic in `consolidatedNode.Split` can crash block finalization when a zero-staked validator is elected proposer - (File: `kaiax/staking/staking_info.go`)

### Summary
`kaiax/staking/staking_info.go`'s `consolidatedNode.Split()` divides by `totalAmount = StakingAmount + CLStakingAmount` with no zero-guard. This is directly analogous to the gALCX `bumpExchangeRate` bug: a divisor derived from a supply/stake total that the code assumes is always positive can, under normal (non-malicious-node, non-privileged) protocol conditions, become zero, causing the division to fail. In Go's `math/big`, `Int.Div` by a zero divisor panics, which — unlike Solidity's revert — crashes the node process executing `FinalizeState`/reward distribution for that block, i.e. every honest full node that processes the block.

### Finding Description
`consolidatedNode.Split` is defined as: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)  // <-- panics if totalAmount == 0
	...
}
```

This function only guards against the case `CLStakingInfo == nil`; it does **not** guard against `StakingAmount == 0 && CLStakingInfo.CLStakingAmount == 0` while `CLStakingInfo != nil` (i.e., the node is registered for consensus-liquidity staking but currently has zero CN stake and zero CL stake).

This function is invoked unconditionally for the block proposer inside `specWithProposerAndFundsFlex`, regardless of the proposer's staking amount: [2](#0-1) 

```go

}

	cnAmount, clAmount := cn.Split(proposer)   // panics if cn.StakingAmount==0 && CLStakingAmount==0

}
```

Documented explicitly in `kaiax/valset/README.md`: [4](#0-3) 

This fallback is confirmed by the unit test `"none mode, all demoted"` expecting `demoted: numsToAddrs()` (empty) when every validator's stake is `0`: [5](#0-4) 

If every council member's CN staking amount drops below `MinimumStake` at once (e.g. via ordinary unstaking through the staking contracts, or simply because most validators temporarily have low stake while new ones haven't staked yet), the "if all are demoted, then no one is demoted" fallback makes even a validator with `StakingAmount == 0` "qualified", allowing it to be selected as the round's proposer under `WeightedRandom` policy. If that same validator has previously been registered in the CL registry (`CLStakingInfo != nil`, e.g. it once configured consensus liquidity but has since had its CL stake fully withdrawn, `CLStakingAmount == 0`), then when `FinalizeState` builds the deferred reward spec, `specWithProposerAndFundsFlex`/the analogous Kore path will call `cn.Split(proposer)` with `totalAmount == 0`, triggering a `big.Int` division-by-zero panic during state finalization.

### Impact Explanation
A panic inside `FinalizeState`/reward-distribution logic is not a Solidity `revert` — it crashes the Go process. Because every full node (not just the proposer) executes `FinalizeState` to validate/finalize the block, this constitutes a **network-wide denial of service**: all honest nodes attempting to process the offending block would panic and halt, effectively stopping the chain until the code is patched or the situation is manually worked around. This satisfies "acceptance of an invalid transaction or block" / catastrophic availability impact criteria, and is a direct structural analog of the "attacker can make the contract unusable" gALCX finding — except the blast radius here is the entire network rather than a single ERC-20-like contract.

### Likelihood Explanation
Reaching this requires: (1) a validator to have `CLStakingInfo != nil` with `CLStakingAmount == 0` (achievable by any staker who registers CL and then withdraws all CL stake — an ordinary, permissionless staking-contract operation), (2) that validator's CN `StakingAmount` to also be `0`, and (3) all *other* council members to simultaneously be below `MinimumStake` so the "if all demoted, none demoted" fallback fires, and (4) that validator to actually be selected as proposer for the affected round. Conditions (1)-(2) are fully within the control of any unprivileged staker (a normal staking/unstaking action), while (3)-(4) depend on protocol/network state (all validators under-staked) that is plausible especially on smaller or newly-launched Kaia-based networks with few validators, or during validator set churn. This is a lower-likelihood but concrete, code-verified, and unprivileged-triggerable path (no malicious node/validator/consensus-message assumption needed — it only requires ordinary staking transactions and normal proposer-selection outcome), matching a Medium severity classification analogous to the original gALCX finding.

### Recommendation
Add an explicit zero-guard in `consolidatedNode.Split` (and correspondingly in the non-flex `specWithProposerAndFunds` path if it shares the same call pattern): if `totalAmount.Sign() == 0`, return `(amount, big.NewInt(0))` (or another well-defined values) instead of dividing. Additionally, consider whether validators with zero stake should be allowed to hold a non-nil `CLStakingInfo` entry with amount 0 at all, and re-examine whether the "if all are demoted, then no one is demoted" fallback in `getDemotedValidatorsIstanbul` should instead handle the zero-total-stake case defensively across all reward-splitting divisions (`assignStakingRewards`, `assignStakingRewardsFlex`, `ComputeGini`, `consolidatedNode.Split`) rather than relying on incidental non-zero-guarantees from qualification checks.

### Proof of Concept
1. Set up a small council (WeightedRandom policy, Istanbul active) where a validator `V` registers CL staking (`CLStakingInfo != nil`) and later withdraws its CL deposit to `0`; `V`'s CNStaking amount is also `0` (either never staked or fully unstaked) — all via ordinary permissionless staking-contract transactions.
2. Arrange (or wait) for a block where **every** council member's `StakingAmount < MinimumStake` (e.g., during validator churn or on a network with few validators). Per `getDemotedValidatorsIstanbul`, `demoted` becomes empty, making `V` "qualified" for proposer selection.
3. Have `V` be selected as proposer for a round after the Prague hardfork (`config.Rules.IsPrague == true`, `si.CLStakingInfos != nil`).
4. When honest nodes call `FinalizeState` to build the deferred reward spec for `V`'s block, `specWithProposerAndFundsFlex` (or the Kore-non-flex equivalent) finds `V`'s `consolidatedNode` with `CLStakingInfo != nil`, and calls `cn.Split(proposer)`, where `totalAmount = 0 (StakingAmount) + 0 (CLStakingAmount) = 0`, causing `big.Int.Div` to panic and crash every node processing the block.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}

func getDemotedValidatorsIstanbul(council *valset.AddressSet, si *staking.StakingInfo, pset gov.ParamSet) *valset.AddressSet {
	var (
		demoted        = valset.NewAddressSet(nil)
		singleMode     = pset.GovernanceMode == "single"
		governingNode  = pset.GoverningNode
		minStake       = pset.MinimumStake.Uint64() // in KAIA
		stakingAmounts = collectStakingAmounts(council.List(), si)
	)

	// First filter by staking amounts.
	for _, node := range council.List() {
		if uint64(stakingAmounts[node]) < minStake {
			demoted.Add(node)
		}
	}

	// If all validators are demoted, then no one is demoted.
	if demoted.Len() == len(council.List()) {
		demoted = valset.NewAddressSet(nil)
	}

	// Under single governance mode, governing node cannot be demoted.
	if singleMode && demoted.Contains(governingNode) {
		demoted.Remove(governingNode)
	}
	return demoted
}
