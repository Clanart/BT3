## Analysis

The Compound report's bug class is: an unbounded list (`allMarkets`) that is fully iterated in-band by protocol logic, with no enforced cap (`maxAssets` exists but is unused), risking out-of-gas failure as the list grows.

The Agave analog is the `stake_delegations` list processed during epoch-boundary reward calculation in `runtime/src/bank.rs` and `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`.

### Title
Unbounded, unprivileged growth of `stake_delegations` can blow the epoch-boundary compute/time budget during reward calculation - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
At every epoch boundary, `Bank::process_new_epoch` synchronously computes rewards for *every* stake delegation in the system in a single slot. Unlike vote accounts — which are explicitly capped via VAT filtering (`MAX_ALPENGLOW_VOTE_ACCOUNTS`) before being used in reward calculation — the list of stake delegations (`stakes.stake_delegations_vec()`) has no equivalent cap and is fully iterated by any unprivileged user simply creating stake accounts.

### Finding Description
`Bank::compute_new_epoch_caches_and_rewards` fetches the *entire* set of stake delegations from `StakesCache` and passes it, unfiltered, into the reward pipeline: [1](#0-0) 

Note the VAT filter (`clone_and_filter_for_vat(MAX_ALPENGLOW_VOTE_ACCOUNTS, ...)`) is applied only to `unfiltered_distribution_vote_accounts` (vote accounts), not to `stake_delegations`. The full, unbounded `stake_delegations` vector is then passed to `calculate_rewards` → `calculate_rewards_for_partitioning` → `calculate_validator_rewards`, which runs two full-list parallel scans:

- `calculate_reward_points_partitioned`, iterating `stake_delegations.par_iter()` to sum points: [2](#0-1) 

- `calculate_stake_rewards_and_commissions`, iterating `stake_delegations.par_iter()` to redeem rewards for every single delegation: [3](#0-2) 

The code's own comment acknowledges the list can be enormous: *"For N stake delegations, where N is >1,000,000, we produce..."* [4](#0-3) 

Crucially, only the **distribution** (storing) phase of rewards is spread across multiple blocks, via `get_reward_distribution_num_blocks`, which partitions *already-computed* rewards over up to 10% of an epoch's slots: [5](#0-4) 

The **calculation** phase (`calculate_reward_points_partitioned` + `calculate_stake_rewards_and_commissions`) is *not* partitioned — it must complete entirely within the single epoch-boundary slot, for every validator replaying that block (not just the leader), because it determines the deterministic bank state (capitalization, `EpochRewards` sysvar, stake account rewards) that all nodes must agree on.

The only "cap" that exists — `MAX_ALPENGLOW_VOTE_ACCOUNTS` — bounds vote accounts, not stake accounts, and is therefore analogous to the Compound report's unused `maxAssets`: a cap exists conceptually for a related list, but the list that actually dominates the iteration cost (`stake_delegations`) has no such enforcement.

### Impact Explanation
An unprivileged attacker can create an arbitrarily large number of stake accounts (each costing only the rent-exempt reserve plus the minimum delegation — currently 1 SOL after `stake_raise_minimum_delegation_to_1_sol`, defined in `runtime/src/stake_utils.rs`): [6](#0-5) 

As `stake_delegations` grows, the wall-clock cost of the mandatory, non-partitioned, per-epoch reward-calculation scan grows proportionally for *every* validator on the network, not just the leader producing that block. If this computation cannot complete within the fixed time budget of the epoch-boundary slot, it risks causing skipped/delayed slots, degraded validator performance across the cluster at every epoch transition, or in the worst case a network-wide processing stall at epoch boundaries — a non-RPC, remote, protocol-level resource-exhaustion vector triggered purely through permissionless account creation, with no privileged/malicious-validator assumption required.

### Likelihood Explanation
Medium. The attack requires nontrivial SOL capital (≈1 SOL + rent reserve per stake account) to grow `stake_delegations` to a scale that meaningfully threatens slot-time budgets, so it is not a trivial/free attack. However, it requires no special privileges, no validator collusion, and no code path beyond standard `CreateAccount` + `DelegateStake` instructions repeated at scale. The maintainers' own comment anticipating N > 1,000,000 delegations, combined with the fact that only the distribution (not calculation) phase was engineered to be partitioned, indicates this scaling risk was only partially mitigated.

### Recommendation
Perform the same gas/compute simulation the audit report recommended for Compound: determine the maximum number of stake delegations that can be safely processed within the epoch-boundary slot time budget, and either (a) partition the reward *calculation* phase (not just distribution) across multiple blocks like `get_reward_distribution_num_blocks` already does for storage, or (b) apply an analogous cap/filter to `stake_delegations` (parallel to the existing `MAX_ALPENGLOW_VOTE_ACCOUNTS` VAT filter for vote accounts) before they enter `calculate_reward_points_partitioned` / `calculate_stake_rewards_and_commissions`.

### Proof of Concept
1. Using unprivileged funds, repeatedly submit `system_instruction::create_account` + `stake_instruction::delegate_stake` transactions to create N stake accounts (each with the minimum required balance — rent-exempt reserve + minimum delegation), delegated to any vote account(s).
2. As N grows large (the codebase's own internal comment references N > 1,000,000 as an anticipated case), observe growth in the `calculate_activated_stake_time_us` / `update_rewards_with_thread_pool_time_us` metrics reported in `report_new_epoch_metrics` at `runtime/src/bank.rs:1885-1897`, which directly measure the cost of the unbounded, unpartitioned `stake_delegations` scans in `compute_new_epoch_caches_and_rewards` and `calculate_rewards`.
3. Extrapolate/benchmark (e.g., using `runtime/benches/epoch_turnover.rs`'s `bench_epoch_rewards_period`, which already benchmarks this exact code path across varying `STAKE_ACCOUNTS` counts) to show the calculation phase's wall-clock time approaches or exceeds the epoch-boundary slot's allotted processing time as N increases, with no cap in place to stop it.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
