## Title
Attacker-controlled `WWW-Authenticate` header spoofs a git remote as "GitHub Enterprise", forcing Desktop to bind an Enterprise/OAuth sign-in flow to an attacker origin - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The seed report's broken invariant is: a value that should only be reachable/valid in a trusted state (the `initialized` storage slot) is instead derived from an unauthenticated, attacker-influenced position, letting the attacker unlock a privileged code path (re-initialization) that drains funds. The Desktop analog is `getEndpointKind()` in the trampoline credential helper: it classifies an arbitrary git remote's host as a trusted **`'enterprise'`** (GitHub Enterprise Server) endpoint based solely on the content of an HTTP `WWW-Authenticate` response header that the *remote server itself* controls, then uses that classification to drive a real sign-in/OAuth popup bound to the attacker's origin.

### Finding Description
`getEndpointKind` first performs legitimate, unspoofable hostname checks (`isGist`, `isDotCom`, `isGHE`) which correctly reject an arbitrary attacker domain [1](#0-0) . It then falls back to a heuristic that trusts data forwarded by git from the remote's own HTTP response:

```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
``` [2](#0-1) 

The comment explicitly frames this as a shortcut to avoid a real verification request: "We use them as a happy-path to determine if the host is a GitHub host without having to resort to making a request ourselves" [3](#0-2) . This `wwwauth[...]` value originates from the `WWW-Authenticate` header of the actual HTTP response sent by whatever server the remote points to — fully attacker-controlled if the attacker operates that remote/proxy.

In `getCredential`, once `endpointKind !== 'generic'` and no stored account matches the endpoint, Desktop prompts the user to sign in: `const account = await ui.promptForGitHubSignIn(endpoint)` [4](#0-3) , where `endpoint` is built directly from the credential's `host`/`protocol` fields, i.e., the attacker's actual URL [5](#0-4) .

`promptForGitHubSignIn` then binds a real sign-in flow to that attacker origin:
```
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
``` [6](#0-5) 

Existing guards do not stop this path: the strict hostname checks (`isDotCom`/`isGHE`/`isGist`) only cover the *legitimate* classification branch [7](#0-6) ; the `wwwauth` fallback runs before the final network-verified `isGitHubHost(endpoint)` check and short-circuits it entirely, so the one check that could actually confirm the remote is a real GitHub instance is never reached once the spoofed header is present.

### Impact Explanation
This is triggered purely by adding/cloning/fetching from a **git remote the attacker controls** — no local access, no leaked credentials, and no unnatural extra steps beyond a normal "clone/fetch this repo" action that Desktop users perform constantly. Desktop's own UI vouches for the attacker's origin as a legitimate "GitHub Enterprise" instance and opens the standard `SignIn` popup (`isCredentialHelperSignIn: true`) against it [8](#0-7) . Since the endpoint used for the sign-in/OAuth flow (`setSignInEndpoint(origin)`) is the attacker's real origin, any credentials or OAuth authorization completed through that flow are sent to the attacker, not GitHub — matching the "unauthorized OAuth or account binding" / credential exfiltration impact class.

### Likelihood Explanation
Any server the attacker controls (a malicious remote host, a compromised/forged proxy, or a MITM on plain HTTP) can trivially add `WWW-Authenticate: Basic realm="GitHub"` to a 401 response; this requires no interaction from the victim beyond a routine clone/fetch, and the classification logic is reached automatically whenever git needs credentials for a non-github.com/non-ghe.com host. The only pre-condition is that no stored account already matches the apparent endpoint, which is the normal case for any repo hosted somewhere new.

### Recommendation
Never let `wwwauth[...]` header content alone elevate trust to `'enterprise'`/GitHub classification. At minimum, require the final authoritative `isGitHubHost(endpoint)` network probe (which actually queries a known GitHub-only API surface) before trusting a non-dotcom/non-ghe.com host, and/or clearly warn the user in the sign-in popup that the endpoint they are about to authenticate against is unverified/unknown when it wasn't derived from a hostname allowlist. Do not use attacker-suppliable response headers as a "happy path" bypass for identity checks.

### Proof of Concept
1. Attacker stands up `https://attacker.example/foo/bar.git` (any git server) or a MITM/proxy for an HTTP remote.
2. Attacker configures it to respond `401` with header `WWW-Authenticate: Basic realm="GitHub"` on Git's credential probe.
3. Victim adds/clones this remote in GitHub Desktop; Git contacts the server, gets the 401, and (per the git credential protocol) forwards the `wwwauth[]` header data to Desktop's credential helper via `trampolineCredentialHelper`.
4. `getEndpointKind` matches `realm="GitHub"` and returns `'enterprise'` [9](#0-8) .
5. `getCredential` finds no existing account for this endpoint and calls `ui.promptForGitHubSignIn('https://attacker.example')` [4](#0-3) .
6. Desktop opens a "Sign in" popup, calls `beginEnterpriseSignIn` and `setSignInEndpoint('https://attacker.example')`, binding the credential/OAuth flow to the attacker's origin [10](#0-9) .
7. If the victim completes the sign-in, their credentials/OAuth exchange target the attacker's server instead of a real GitHub Enterprise instance.

I could not fully trace what happens deeper inside `beginEnterpriseSignIn`/OAuth authorization-URL construction (e.g., in `sign-in-store.ts`) within the remaining tool budget to confirm whether device-flow/basic-auth or full OAuth-with-token-exchange is used for this attacker-bound endpoint — that would refine exactly which secret (password vs. OAuth code/token) is exposed, but the core broken invariant (unauthenticated header content granting "GitHub Enterprise" trust classification) is confirmed directly in the code shown above.

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}
```

export const isDotCom = (ep: string) => {
  if (ep === getDotComAPIEndpoint()) {
    return true
  }

  const { hostname } = new URL(ep)
  return hostname === 'api.github.com' || hostname === 'github.com'
}

export const isGist = (ep: string) => {
  const { hostname } = new URL(ep)
  return hostname === 'gist.github.com' || hostname === 'gist.ghe.io'
}

/** Whether or not the given endpoint URI is under the ghe.com domain */
export const isGHE = (ep: string) => new URL(ep).hostname.endsWith('.ghe.com')
