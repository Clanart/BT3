### Title
Untrusted `ReceivedOutput` amounts can trigger an integer-overflow panic during transaction construction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`ReceivedOutput::read` accepts a consensus-decoded `TxOut` containing an attacker-controlled 64-bit amount, while `SignableTransaction::new` sums those amounts with unchecked `u64` arithmetic. Because the workspace enables release-mode overflow checks, supplying multiple large encoded output values causes an integer-overflow panic instead of returning `TransactionError`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`ReceivedOutput::read` calls `TxOut::consensus_decode` and stores its `value` without checking that the amount is economically plausible or bounded for later summation. [1](#0-0) 

`SignableTransaction::new` later computes `input_sat` using `sum::<u64>()` over every supplied `ReceivedOutput`. [4](#0-3) 

The release profile sets `overflow-checks = true`, so overflowing that summation deterministically panics. [3](#0-2) 

The same unchecked pattern appears in `payment_sat + needed_fee`, `fee_per_vbyte * vbytes`, and `fee()` subtraction, but the earliest directly reachable panic is the sum of untrusted input amounts. [5](#0-4) [6](#0-5) 

### Impact Explanation
An unprivileged party who can cause serialized `ReceivedOutput` values to be deserialized and used for transaction construction can crash the signing or wallet process rather than merely producing an invalid transaction. [1](#0-0) [4](#0-3) 

This is a remotely triggerable denial of service of the signing path, and repetition can prevent a signing operation from completing. [3](#0-2) 

### Likelihood Explanation
The attacker only needs to make two encoded `TxOut` values large enough that their sum exceeds `u64::MAX`; canonical scalar offsets and otherwise valid serialized outpoints do not prevent this. [1](#0-0) 

The constructor does not need unusual threshold participants or malformed curve encodings because the panic occurs before FROST signing is reached. [2](#0-1) [7](#0-6) 

Likelihood is limited by the requirement that the application passes attacker-controlled `ReceivedOutput` objects into `SignableTransaction::new`; outputs produced solely by `Scanner::scan_transaction` from a valid blockchain cannot contain consensus-invalid amounts. [8](#0-7) 

### Recommendation
Use checked arithmetic for all input, payment, change, and fee calculations in `SignableTransaction::new` and `fee()`. [5](#0-4) [9](#0-8) 

Replace `sum::<u64>()`, `payment_sat + needed_fee`, `payment_sat + fee_with_change`, and `fee_per_vbyte * vbytes` with `try_fold`/`checked_add`, `checked_add`, and `checked_mul`, returning `NotEnoughFunds`, `TooLowFee`, or a dedicated overflow error instead of panicking. [10](#0-9) 

Optionally reject `TxOut` values above Bitcoin’s maximum money supply during `ReceivedOutput::read`, although checked arithmetic remains necessary because deserialized wallet data may not be consensus-validated. [1](#0-0) 

### Proof of Concept
A source-level trigger is:

```rust
// Construct two serialized ReceivedOutput values whose TxOut.value fields are
// u64::MAX, then deserialize them.
let a = ReceivedOutput::read(&mut encoded_output_with_u64_max_value.as_slice())?;
let b = ReceivedOutput::read(&mut another_encoded_output_with_u64_max_value.as_slice())?;

// Any ordinary nonempty payment reaches the unchecked input summation.
let payments = [(ScriptBuf::new(), DUST)];

// Panics at `inputs.iter().map(...).sum::<u64>()`.
let _ = SignableTransaction::new(vec![a, b], &payments, None, None, 10_000);
```

The first deserialization step succeeds because `TxOut::consensus_decode` is accepted without a local amount bound, while `input_sat` evaluates `u64::MAX + u64::MAX` and panics under the workspace’s enabled overflow checks. [1](#0-0) [2](#0-1) [3](#0-2)
