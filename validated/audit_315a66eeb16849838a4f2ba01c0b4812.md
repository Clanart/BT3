### Title
Unconditioned Python `assert` on spend/condition count mismatch in `MempoolManager.validate_spend_bundle` can be reached with an attacker-supplied spend bundle, crashing transaction processing - (File: chia/full_node/mempool_manager.py)

### Summary
`MempoolManager.validate_spend_bundle()` builds a `coin_id -> SpendConditions` map from the Rust-produced `SpendBundleConditions.spends` list and then asserts that this map has exactly as many entries as the number of `CoinSpend`s in the submitted `SpendBundle`: [1](#0-0) 
This is a bare Python `assert` reachable from network/RPC-submitted spend bundles, not a `ValueError`/`ValidationError` that is caught and converted into a rejection status.

### Finding Description
Like CVE-2016-2571 (Squid continuing to process/store data after a response-parsing mismatch and hitting an internal assertion that kills the daemon), this code path assumes the shape of Rust-validated `conds.spends` always agrees 1:1 with the coin spends the submitter provided, and enforces that assumption with a raw `assert` rather than a recoverable validation error. `spend_conditions` is built as a dict keyed by `bytes32(spend.coin_id)`: [2](#0-1) 
Dict construction silently collapses duplicate keys. If the underlying `SpendBundleConditions.spends` list (produced in `validate_clvm_and_signature`, called from `pre_validate_spendbundle`) ever contains two entries with the same `coin_id` — e.g. from a spend bundle that spends the same coin twice, or from ephemeral-coin edge cases where a computed coin_id collides — `len(spend_conditions)` will be smaller than `len(new_spend.coin_spends)`, and the `assert` on line 712 raises `AssertionError`.

Unlike the other error paths in this function (`Err.INVALID_COIN_SOLUTION`, `Err.UNKNOWN_UNSPENT`, `Err.INVALID_SPEND_BUNDLE`, etc., which are returned as tuples and safely converted to `MempoolInclusionStatus.FAILED`), an `AssertionError` is an uncaught exception. Tracing the call chain up to `FullNode.add_transaction()`: [3](#0-2) 
only `ValueError` and `ValidationError` are caught here; `add_spend_bundle()` (which calls `validate_spend_bundle()`) is invoked separately and is not wrapped in equivalent exception handling in the visible flow, so an `AssertionError` raised inside `validate_spend_bundle` propagates uncaught out of the transaction-processing task.

Similarly, `pop(coin_id)` immediately after the assert at line 721 assumes each `coin_id` is unique and present in `spend_conditions`; if the assert did not fire but the mapping is nonetheless inconsistent (e.g., two identical coin_ids collapsed to one entry that gets popped once, then a `KeyError` on the second pop attempt), that is an additional unguarded failure mode along the same code path: [4](#0-3) 

### Impact Explanation
An uncaught `AssertionError` (or `KeyError`, in the related `pop()` case) thrown from a single, attacker-submitted spend bundle during mempool admission constitutes a spend-triggered halt of transaction processing — precisely the "spend-triggered transaction-processing halt" category called out as in-scope impact. Because `validate_spend_bundle` is invoked from `add_spend_bundle`, which is called both from the direct RPC/gossip transaction path and from mempool re-validation on `new_peak` (rebuilding the whole mempool from `old_pool.all_items()`), a single malformed/duplicate-coin bundle accepted into (or replayed through) the mempool could cause repeated crashes during block-transition mempool rebuild: [5](#0-4) 
This matches the CVE's "assertion failure and daemon exit" DoS pattern, translated to Chia's mempool admission path.

### Likelihood Explanation
Exploitability depends on whether it is actually possible to submit a `SpendBundle` whose `coin_spends` contains a coin spent twice (same `coin.name()`) while still passing Rust CLVM validation with a `SpendBundleConditions.spends` list that collapses to fewer unique `coin_id`s than `len(new_spend.coin_spends)`. The Rust-side `validate_clvm_and_signature` (not visible in this Python-level review) is expected to reject a bundle with a literal double-spend of the identical `Coin` object before returning `conds`, and normal well-formed bundles will never hit this mismatch — which is why the code comment above the assert says "if this happens ... doesn't match", i.e., the authors treat it as an invariant violation rather than a validated-input condition. Because I could not inspect the Rust `chia_rs` implementation of `validate_clvm_and_signature`/condition parsing in this index, I cannot confirm whether a crafted bundle (e.g., duplicate identical `CoinSpend`s, or two `CoinSpend`s whose puzzle/solution reveal produces colliding announced/created coin identities interpreted as the same "coin_id" in `conds.spends`) can actually reach this mismatch at the Python layer. This is the key uncertainty limiting confidence in exploitability.

### Recommendation
Replace the bare `assert len(new_spend.coin_spends) == len(spend_conditions)` (and the subsequent unguarded `.pop(coin_id)`) with an explicit, catchable validation check that returns `(Err.INVALID_SPEND_BUNDLE, None, [])` (or similar) instead of raising `AssertionError`/`KeyError`. This mirrors how every other malformed-input branch in this function is handled and prevents any input-triggered invariant mismatch from becoming an unhandled exception that can terminate the transaction-processing task. Additionally, ensure Python is not run with `-O` (which strips asserts) in production so this doesn't silently disable a safety check either way — but the underlying fix is to not rely on `assert` for externally-influenced-input invariants at all.

### Proof of Concept
Not fully constructible from this review: reproducing this requires crafting (or fuzzing) a `SpendBundle` whose Rust-computed `SpendBundleConditions.spends` list yields duplicate/fewer unique `coin_id` entries than `len(new_spend.coin_spends)`, which requires access to the `chia_rs` condition-parsing/dedup logic that is not present in this index. A concrete PoC would submit such a spend bundle via `full_node_rpc_api`'s push_tx / gossip path and observe an unhandled `AssertionError` surfacing from `MempoolManager.validate_spend_bundle` at [6](#0-5)  instead of a `MempoolInclusionStatus.FAILED` response.
