### Title
Missing chain-binding in the `addr` precompile / `AssociateTx` `customMessage` signature enables cross-chain/cross-deployment replay of address association - (File: precompiles/addr/addr.go, app/ante/evm_checktx.go)

### Summary
The `associate` precompile method and the raw EVM `AssociateTx` both recover the caller's EVM/Sei address pair by hashing an arbitrary, caller-chosen `customMessage` string with `crypto.Keccak256Hash` and ECDSA-recovering against `(v, r, s)`. Unlike every other signing path in sei-chain (Cosmos `SignerData.ChainID`, EIP-155/protected EVM tx signatures, EIP-7702 `SetCodeAuthorization.ChainID`), this signed payload contains no chain identifier, contract address, or nonce.

### Finding Description
`PrecompileExecutor.associate` in `precompiles/addr/addr.go` builds `customMessageHash := crypto.Keccak256Hash([]byte(customMessage))` from a plain, un-namespaced string supplied by the caller, then calls `helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)` to recover the account's EVM address, Sei address and pubkey, immediately followed by `associateAddresses`, which performs the on-chain address linking. The exact same construction is used in `HandleAssociateTx` in `app/ante/evm_checktx.go` for the dedicated `AssociateTx` message type. Contrast this with every other signature-checking path in the codebase, which explicitly bind the chain ID into what's signed: Cosmos tx signing includes `SignerData.ChainID` (`sei-cosmos/x/auth/signing/sign_mode_handler.go`), EIP-1559/legacy EVM transactions have their `ChainId()` validated against the node's chain ID before signature recovery (`x/evm/ante/sig.go`, `app/ante/evm_checktx.go` `EvmStatelessChecks`), and EIP-7702 `SetCodeAuthorization` explicitly embeds `ChainID` in its RLP-encoded sig-hash and is validated against the local chain (`utils/helpers/address.go` `AuthorityToPreAssociate`). The `customMessage` used for association has no analogous protection — the hash a user signs off-chain to prove ownership of an EVM key is not tied to any specific Sei chain-id, deployment, or genesis.

### Impact Explanation
Because a user's signature over a given `customMessage` string is valid on any Sei deployment (mainnet, a testnet, a devnet, or any future fork/hard fork sharing the same secp256k1 key), an attacker who observes a legitimate association signature (these calls are public on-chain, or a dApp may prompt users to sign a fixed/predictable message off-chain for association) can replay that exact `(v, r, s, customMessage)` tuple via `associate`/`associatePubKey` on a different chain instance to force-associate the victim's EVM address with their Sei address there too, without the victim's consent for that specific chain. Address association triggers automatic migration of any direct-cast balance (`associationHelper.AssociateAddresses` → `MigrateBalance`), so an unwanted forced association could move/lock funds under the attacker-chosen association context, and prevents the victim from independently controlling whether/when their addresses are linked on that chain, and can permanently occupy the association slot (`associate` and `HandleAssociateTx` both refuse if `GetEVMAddress`/`GetSeiAddress` is already associated) — griefing the victim by consuming their EVM address's one-time-only association before they can perform it themselves under intended conditions.

### Likelihood Explanation
Likelihood is limited by the fact that a valid `customMessage` signature must first exist and become known/reachable — but since the signature bytes are the entire input to a public precompile call and to the public `AssociateTx` message type, any tx or precompile call visible on one chain (mempool, block explorer, or the AssociateTx broadcast itself) trivially exposes the `(v,r,s,customMessage)` for anyone to resubmit against another Sei-based chain instance (e.g., testnet vs. mainnet, or a future upgrade fork) as long as the target account isn't already associated there. Given sei-chain explicitly maintains multiple environments (localnet/devnet/testnet/mainnet) with shared genesis/tooling, and association is a one-shot, security-relevant operation, this is a realistically reachable, unprivileged replay path.

### Recommendation
Bind the local chain ID (and ideally a fixed domain separator/contract identifier) into the `customMessage` hash before recovery, e.g. `keccak256(abi.encode(chainID, customMessage))` or equivalent, mirroring the protections already used for EVM tx signatures (`ethtx.ChainId()` check) and EIP-7702 authorizations (`SetCodeAuthorization.ChainID`). Apply the same fix consistently to both the `addr` precompile's `associate` method and the `AssociateTx`/`HandleAssociateTx` path (and their `giga` counterparts in `giga/deps/xevm/...`).

### Proof of Concept
1. On chain A (e.g. Sei testnet with chain ID `713715`), victim signs `customMessage = "associate-me"` off-chain and submits it via `addr.associate(v, r, s, "associate-me")`, which recovers their EVM/Sei address pair from `keccak256("associate-me")` and links them (`precompiles/addr/addr.go` lines 160-202).
2. Attacker observes the calldata `(v, r, s, "associate-me")` from the mined transaction (public data).
3. Attacker resubmits the identical `(v, r, s, "associate-me")` to the `associate` precompile (or as an `AssociateTx`) on chain B — a different Sei deployment sharing the same signature-verification code path (e.g. mainnet, or a future hard fork of the same chain) where the victim's EVM address is not yet associated.
4. Because the signed hash contains no chain identifier, `helpers.GetAddresses` recovers the same victim keys on chain B, and `associateAddresses`/`HandleAssociateTx` links them there too — an association the victim never authorized for chain B, migrating any direct-cast balance under that unintended association.

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)

func HandleAssociateTx(ctx sdk.Context, ek *evmkeeper.Keeper, atx *ethtx.AssociateTx, readOnly bool) (sdk.Context, error) {
	V, R, S := atx.GetRawSignatureValues()
	V = new(big.Int).Add(V, utils.Big27)
	// Hash custom message passed in
	customMessageHash := crypto.Keccak256Hash([]byte(atx.CustomMessage))
	evmAddr, seiAddr, seiPubkey, err := helpers.GetAddresses(V, R, S, customMessageHash)
	if err != nil {
		return ctx, err
	}
	_, isAssociated := ek.GetEVMAddress(ctx, seiAddr)
	if isAssociated {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInvalidRequest, "account already has association set")
	}
	if !IsAccountBalancePositive(ctx, ek, seiAddr, evmAddr) {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInsufficientFunds, "account needs to have at least 1 wei to force association")
	}
	if !readOnly {
		if err := AssociateAddress(ctx, ek, evmAddr, seiAddr, seiPubkey); err != nil {
			return ctx, err
		}
	}
	return ctx.WithPriority(antedecorators.EVMAssociatePriority), nil
}

package ethtx

import (
	"math/big"

func NewAssociateTx(tx *ethtypes.Transaction, customMessage string) (*AssociateTx, error) {
	v, r, s := tx.RawSignatureValues()
	txData := &AssociateTx{
		V:             v.Bytes(),
		R:             r.Bytes(),
		S:             s.Bytes(),
		CustomMessage: customMessage,
	}
	return txData, nil
}
