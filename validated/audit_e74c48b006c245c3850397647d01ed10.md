### Title
Missing URL-scheme allowlist in `open-external` IPC handler permits arbitrary URI-scheme dispatch via `shell.openExternal` - (File: `app/src/main-process/main.ts`)

### Summary
The `open-external` IPC handler in the main process logs (but does not enforce) an `http(s)` check before invoking Electron's `shell.openExternal`, and the renderer-side call sites that reach this handler (e.g. `LinkButton`) perform no scheme validation either, so any attacker-controlled URL string that reaches a clickable link/URI prop is passed unchecked to `shell.openExternal`.

### Finding Description
The IPC handler only inspects the URL to decide whether to log it — it never rejects non-`http(s)` values: [1](#0-0) 

Regardless of whether `pathLowerCase.startsWith('http://')`/`'https://'` is true, execution falls through to `shell.openExternal(path)`.

On the renderer side, the generic `LinkButton` component — used throughout the UI, including the check-run detail views that render links derived from API objects such as check-run `html_url`/`details_url` — forwards its `uri` prop straight to `shell.openExternal` with no scheme check: [2](#0-1) 

`shell` here resolves to the `app-shell.ts` wrapper, whose `openExternal` is proxied to the main process via IPC: [3](#0-2) 

`app/src/ui/check-runs/ci-check-run-popover.tsx` was confirmed to reference `LinkButton`/`openExternal`, and `app/src/lib/ci-checks/ci-checks.ts` builds its check-run model fields (including the URL surfaced to the UI) from the raw API `html_url`/`details_url` values, i.e. server-controlled/attacker-influenceable data for a malicious repository's checks. I was not able to fully read `ci-check-run-popover.tsx` and `ci-checks.ts` in this session due to iteration limits, so I cannot cite the exact line where the check-run URL is bound to a `LinkButton`'s `uri` prop — this should be verified directly in those files.

There is no scheme allowlist ("only `http:`/`https:` may leave the sandbox") enforced anywhere in this chain: not in `main.ts`'s IPC handler, and not in `LinkButton`. Nothing prevents a `javascript:`, `file:`, or an OS-registered custom/deep-link scheme (e.g. `ms-officecmd:`, `search-ms:`, or a third-party app's registered protocol) from being handed to Electron's `shell.openExternal`, which on Windows ultimately delegates to `ShellExecute`/`ShellExecuteEx` and can invoke arbitrary registered protocol handlers.

### Impact Explanation
If a malicious repository or its CI provider supplies a crafted `details_url`/`html_url` (or any other attacker-influenced field rendered through `LinkButton`) with a non-`http(s)` scheme, clicking the resulting link in GitHub Desktop causes the main process to call `shell.openExternal` on that raw string. Depending on the scheme and what's installed/registered on the victim's OS, this can range from launching an arbitrary installed application to triggering known OS-level URI-handler exploit chains (several of which have historically achieved code execution via Windows `ShellExecute` argument-injection through registered protocol handlers). This breaks the intended invariant that only vetted `http(s)` links can leave the Electron sandbox.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is that the attacker controls a field surfaced by the GitHub API (or repository/CI content) that GitHub Desktop renders as a clickable external link, and that the user clicks it — a normal, expected user action, not an "unnatural" step. The check happens purely client-side/main-process side with no server-side sanitization guaranteed, and the `open-external` handler's own comment/logic shows the intent was to restrict to `http(s)` but the implementation never enforces it.

### Recommendation
- In `app/src/main-process/main.ts`, make the `open-external` IPC handler actually reject (return `false`/throw) when the scheme is not `http:`/`https:`, instead of only logging.
- Add the same scheme validation inside `IAppShell.openExternal`/`app-shell.ts` so all call sites are protected even if the IPC handler changes.
- Optionally, centralize this check in `LinkButton` so any URI passed to it that isn't `http(s)` is rejected before even issuing the IPC call, providing defense in depth for future callers that render API-derived URLs (check runs, PR links, notifications, etc.).

### Proof of Concept
1. Stub a check-run API response so its `details_url`/`html_url` is `javascript:alert(1)` or an OS-registered custom scheme such as `mailto:` chained with exploit parameters, or a Windows deep-link like `ms-officecmd:...`.
2. Render the Checks list so `ci-check-run-popover.tsx` displays a `LinkButton` bound to that URL.
3. Click the link; `LinkButton.onClick` (`app/src/ui/lib/link-button.tsx:76-92`) calls `shell.openExternal(uri)` unconditionally.
4. This reaches the `open-external` IPC handler in `main.ts:581-597`, which performs no scheme rejection and calls Electron's `shell.openExternal(path)` on the untrusted string, dispatching it to the OS.

Note: I could not directly inspect the specific line in `ci-check-run-popover.tsx`/`ci-checks.ts` that binds the API-sourced URL to `LinkButton`'s `uri` prop within the available tool iterations — this binding should be confirmed by reading those two files in full before treating the PoC as fully verified end-to-end.

```typescript
  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
```
