### Title
`Verifier::sign_optimistic_payout` never checks `output_amount` against the Citrea-recorded withdrawal amount - only an upper bound is enforced - ([File: core/src/verifier.rs])

### Summary
`Verifier::sign_optimistic_payout` gates optimistic-payout co-signing on an ECDSA `verification_signature` from `aggregator_verification_address`, but that signature only proves the aggregator's key signed the exact `(deposit_id, input_signature, input_outpoint, output_script_pubkey, output_amount)` tuple it was handed - it proves nothing about whether `output_amount` matches what the Citrea Bridge contract actually recorded for that withdrawal. The subsequent check at lines 1635-1644 only enforces `output_amount <= bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT`, and the later check at 1646-1659 only compares the withdrawal `OutPoint` (txid:vout), never the amount, against the verifier's own DB record. No code path in this function queries Citrea (or any locally-synced Citrea state) for the real entitled amount.

### Finding Description
The binding that should hold is: `output_amount == CitreaBridgeContract.withdrawal[deposit_id].amount`. Tracing `sign_optimistic_payout` (core/src/verifier.rs:1570-1680):

- [1](#0-0)  — the ECDSA gate calls `recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>` over the caller-supplied `output_amount` and merely checks the recovered address equals the configured aggregator key. This is authentication of "the aggregator signed this message," not validation that the message's amount is correct.
- [2](#0-1)  — the only numeric bound on `output_amount` is the static upper cap `bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT`, unrelated to the specific withdrawal's real entitlement.
- [3](#0-2)  — the withdrawal-utxo check compares only the `OutPoint` (`txid:vout`) pulled from `get_withdrawal_utxo_from_citrea_withdrawal`, never the payout amount, so it cannot catch an inflated `output_amount`.

Because the referenced companion finding establishes that `Aggregator::optimistic_payout` (aggregator.rs:1010-1126) also never cross-checks `output_amount` against Citrea before producing its ECDSA co-signature, the aggregator's signature degenerates into an attestation of "the aggregator forwarded whatever `WithdrawParams` it was given," not "the aggregator verified this amount against Citrea." The verifier then treats that hollow attestation as sufficient authorization to add its MuSig2 partial signature toward an N-of-N optimistic payout, up to the protocol's static cap, regardless of the real Citrea-recorded amount.

Exploit flow: attacker creates/controls a withdrawal UTXO and its unlocking Schnorr signature (permitted under the threat model), performs a genuine small-value Citrea `withdraw()` call to obtain a real `deposit_id`, then calls the aggregator's public `OptimisticPayout` gRPC with `output_amount = bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT` (the cap) instead of the true withdrawal amount. Because neither the aggregator nor any verifier cross-checks the amount against Citrea's stored withdrawal record, each verifier's ECDSA gate passes, the upper-bound check passes (attacker picked exactly the cap), and the outpoint check passes (same UTXO, correct outpoint) — none of these guards examine the true entitled amount, so N-of-N partial signatures are produced authorizing a payout larger than Citrea ever recorded.

### Impact Explanation
This allows BTC to leave a move-to-vault UTXO for an amount exceeding the matching fronted/entitled withdrawal, i.e., "N-of-N partial signatures for an unauthorised spend" — a Critical-severity outcome per the stated impact taxonomy. It is repeatable per deposit: any deposit that undergoes a genuine but small-value Citrea withdrawal can be inflated up to the bridge-amount cap during its optimistic payout, draining the excess to an attacker-chosen `output_script_pubkey`. The blast radius spans every deposit that uses the optimistic-payout path while `aggregator_verification_address` is configured, since the flaw is structural (missing amount cross-check), not deposit-specific.

### Likelihood Explanation
Requires `aggregator_verification_address` to be configured (an explicitly supported deployment mode, not a hypothetical one) and requires the companion aggregator-side flaw (no Citrea amount cross-check in `Aggregator::optimistic_payout`) to also hold, which is asserted as a given precondition here. The attacker needs only: (1) ability to perform a legitimate Citrea `withdraw()` for a real UTXO/amount they control, and (2) access to the aggregator's public `OptimisticPayout` gRPC — both within the stated unprivileged threat model. Cost is limited to normal bridge/deposit fees; no key compromise, no majority hashrate, no TLS interception is needed. This is fully repeatable across deposits and withdrawals.

### Recommendation
`sign_optimistic_payout` must independently bind `output_amount` to the real Citrea-recorded withdrawal amount rather than trusting the ECDSA `verification_signature` as sufficient authorization. Concretely, verifiers should query their own synced Citrea state (or an SPV/storage-proof-backed record) for `deposit_id`'s withdrawal amount and require `output_amount == citrea_recorded_amount` (not merely `<= cap`), independent of whether the aggregator supplies a verification signature. The aggregator-side fix (cross-checking against Citrea before signing) should also be applied, but the verifier is the final backstop and must not rely solely on the aggregator's attestation for a value binding.

                    return Err(BridgeError::InvalidECDSAVerificationSignature);
