### Title
`IetfTranscript` satisfies the `Transcript` trait with stub implementations, so `challenge()` returns identical, label-independent outputs and never advances transcript state - (File: crypto/frost/src/algorithm.rs)

### Summary
The reported bug class is a base/interface method with a default or stub implementation that silently returns a wrong result, where the type system accepts the conforming type but the semantics are broken. In Serai, `IetfTranscript` (crypto/frost/src/algorithm.rs:102-125) implements the `Transcript` trait (crypto/transcript/src/lib.rs:28-54) in a way that violates the trait's contract: `domain_separate` is a no-op, `append_message` discards its `label`, `challenge` ignores its `label`, returns the entire accumulated buffer, and — critically — does not update the transcript, despite the trait documenting "Implementors MUST update the transcript as it does so, preventing the same challenge from being generated multiple times" (lib.rs:41-44). `rng_seed` is left `unimplemented!()`. Any code path that draws two or more challenges from an `IetfTranscript` receives the identical byte string each time, and `rng_seed` panics at runtime — the exact "inherited function returns wrong result" failure of the report.

### Finding Description
`Transcript` is the interface consumed by `Algorithm<C>` (algorithm.rs:31) to derive binding factors and Fiat-Shamir challenges inside `AlgorithmSignMachine`/`AlgorithmPreprocessMachine` in crypto/frost/src/sign.rs. `IetfTranscript` claims conformance:

- `fn domain_separate(&mut self, _: &[u8]) {}` — silently does nothing, so two domain-separated protocols produce identical state.
- `fn append_message<M>(&mut self, _: &'static [u8], message: M)` — appends raw bytes with no label or length framing, so `append_message(a || b)` collides with `append_message(a) ++ append_message(b)` boundaries and distinct labels are indistinguishable.
- `fn challenge(&mut self, _: &'static [u8]) -> Vec<u8>` — returns `self.0.clone()` without mutating `self.0`, directly violating the "MUST update the transcript" requirement. Two consecutive `challenge` calls at the same point return byte-identical output regardless of label.
- `fn rng_seed(&mut self, _: &'static [u8]) -> [u8; 32]` — `unimplemented!()`, so any algorithm that relies on the interface (e.g., DKG-style seeded randomness) panics instead of returning an error.

This mirrors the report exactly: just as `Certifier::getData` returned `0` under an interface signature and `SimpleCertifier`/`ProofOfSMS` silently inherited it, `IetfTranscript` silently provides broken semantics under the `Transcript` interface, and it is exposed for real use via `IetfSchnorr::ietf()` (algorithm.rs:168-170), which is a supported constructor for `AlgorithmSignMachine<IetfSchnorr<C, H>>`.

### Impact Explanation
When `IetfSchnorr` is used inside the FROST signing machine, the algorithm transcript drives the binding-factor/challenge derivation (`B`/challenge values in sign.rs). Because `challenge()` neither binds the label nor advances state:

1. Any algorithm layered on `IetfTranscript` that draws two distinct challenges (e.g., a per-nonce binding factor and a message challenge, or domain-separated sub-challenges) receives the same output, collapsing two independent Fiat-Shamir random oracles into one — equivalent to the transcript-collision / challenge-reuse class that makes shares or proofs forgeable under cross-context replay.
2. Domain separation is absent, so a transcript value produced in one protocol context verifies in another, enabling an unintended message to be signed when an attacker controls the messages/transcript elements fed into the machine.

The crate comments acknowledge the format is naive and single-purpose, but the type itself is `pub`, implements the general `Transcript` interface, and is usable with the generic signing machines — nothing at the type level prevents the misuse the trait's contract was written to forbid.

### Likelihood Explanation
An unprivileged participant who can cause a FROST session built on `IetfSchnorr` to run with attacker-influenced messages can exploit the lack of domain separation/framing (challenges identical across contexts) without any privileged position. Full key-share recovery additionally requires the same challenge value to be consumed twice in a forking position; since `challenge` never advances state, any consumer that calls it twice obtains the collision for free. The panic in `rng_seed` is a guaranteed availability failure for any integrator using the interface generically.

### Recommendation
Same remedy as the report: do not provide stub/broken conformance under a general interface.

- Either implement `IetfTranscript::challenge`/`domain_separate`/`append_message` faithfully per the IETF draft (with label and length framing, and state advancement), or remove `IetfTranscript`'s `Transcript` impl and keep it as a sealed, single-purpose helper usable only inside `IetfSchnorr` where exactly one challenge is drawn.
- At minimum, make `rng_seed` return a real derived seed or a compile-time-impossible path (remove the method requirement for this transcript via a narrower trait bound) rather than `unimplemented!()`.
- Consider preventing generic `Algorithm` consumers from instantiating `IetfTranscript` (seal the trait or restrict `IetfSchnorr` to the machines that draw a single challenge), so a wrong-result conformance cannot be silently inherited by future algorithms.

### Proof of Concept
Conceptual, against `crypto/frost/src/algorithm.rs:102-125`:

```rust
let mut t = IetfTranscript(vec![]);
t.append_message(b"label_a", b"msg");
let c1 = t.challenge(b"challenge_one");
let c2 = t.challenge(b"challenge_two");
// Per the Transcript contract, c1 and c2 must differ and both differ from
// the pre-challenge state. In reality c1 == c2 == b"msg" and the transcript
// is unchanged, so every subsequent challenge is also identical.
assert_eq!(c1, c2); // contract violation: challenges collide

let mut u = IetfTranscript(vec![]);
u.domain_separate(b"other_protocol");
// domain_separate is a no-op; u and t differ only by raw appended bytes,
// and append_message drops labels, so framing collisions are trivial.
u.rng_seed(b"seed"); // panics: unimplemented!()
```

Any `Algorithm<IetfTranscript>` that draws two challenges — or an integrator who composes `IetfSchnorr` in a larger protocol — gets identical challenges and cross-context-valid signatures/proofs, with the trait's own documentation promising the opposite.

Note: I verified the `IetfTranscript` implementation and the `Transcript` contract directly. I could not fully trace every call site of `challenge` within the sign.rs machine path to confirm how many times it is invoked per IETF session; if it is drawn only once and only for the binding factor, the concrete exploitability narrows to the framing/domain-separation and panic issues, which would reduce severity to Medium.
