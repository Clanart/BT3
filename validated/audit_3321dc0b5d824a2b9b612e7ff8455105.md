### Title
Deserialized `ReceivedOutput`/`Output` accepts an arbitrary scalar offset without verifying it derives the output's `script_pubkey`, letting forged outputs be attributed to (and reported as received by) an unrelated group key - (networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes a missing-validation bug: the TON router treats `proxyTonWallet` as the *sender* of a jetton whenever the attacker merely names it as `receiver`, without checking that the jetton wallet actually used in the swap is the proxy TON wallet — letting an attacker claim privileged identity and drain the wrong asset. The structural analog in Serai is the scanner/output pipeline: `ReceivedOutput::read` (and the processor's `Output::read` wrapper) accepts an arbitrary scalar `offset` plus an arbitrary `TxOut`/`OutPoint`, and downstream code computes the owning key as `script_key − offset·G` without ever checking that `key + offset·G` actually produces the output's `script_pubkey`. A forged byte stream therefore claims funds under a group key that cannot spend them.

### Finding Description
`Scanner::scan_transaction` is safe because it only emits a `ReceivedOutput` when `output.script_pubkey` matches a registered script, so `offset` and `script_pubkey` are bound by construction [1](#0-0) . The deserialization path has no such binding: `ReceivedOutput::read` reads `offset = Secp256k1::read_F(r)`, then consensus-decodes any `TxOut` and `OutPoint`, returning the pair unchecked [2](#0-1) . The processor's `Output::read` wraps this directly, again with no consistency check [3](#0-2) . Downstream, `Output::key()` recovers the purported owner by subtracting `offset·G` from whatever key sits in the attacker's chosen `script_pubkey`, yielding an arbitrary group key [4](#0-3) , and `balance()` reports the attacker-chosen `value` as Bitcoin received by that key [5](#0-4) . In-scope `networks/bitcoin/src` code confirms the only place the offset↔script binding is ever enforced is `SignableTransaction::multisig`, which merely refuses to sign (`None`) when the offset doesn't reproduce the prevout's script [6](#0-5)  — so the forged output is credited but unspendable.

### Impact Explanation
An attacker who supplies bytes to `ReceivedOutput::read`/`Output::read` can fabricate a `ReceivedOutput { offset: a, output: TxOut{script_pubkey: S, value: V}, outpoint }` such that `key()` returns a chosen victim group key `K` (choose `offset` so `S − a·G = K`, i.e. pick any `a` and read `key()` accordingly, or pick `S` as a P2TR output paying `K + a·G` for arbitrary `a`). The processor then reports balance `V` attributed to `K` while the real `offset` needed to spend `S` differs, so the funds are unspendable — directly mirroring the report where a swap is credited as if it involved `proxyTonWallet` while the actual wallet differs. Phantom balance inflates the scheduler's apparent holdings and can wedge the UTXO scheduler into plans that can never be signed.

### Likelihood Explanation
Medium. Exploitation requires the attacker to influence the byte stream feeding `Output::read`/`ReceivedOutput::read` (persisted/eventuality data paths in the processor deserialize attacker-influenced `Output`s, and the audit scope explicitly treats these `read` APIs as exposed to untrusted bytes). No cryptography is broken and no secret is needed; the flaw is a pure missing-integrity-check on deserialized data.

### Recommendation
In `ReceivedOutput::read` (or immediately at `Output::read`), verify the offset actually derives the output: given the scanner's group key context, check `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey` (equivalently, have `read` take the expected `Scanner`/key and reject mismatches), mirroring the check already performed in `SignableTransaction::multisig` [7](#0-6) . Short of that, store a checksum/binding of the expected `script_pubkey` alongside the offset.

### Proof of Concept
1. Attacker picks group key `K` (a victim multisig's key) and any nonzero scalar `a`.
2. Compute `P = K + a·G`; if `P` is odd, use `a+1` per `p2tr_script_buf` semantics [8](#0-7) . Build `S = p2tr_script_buf(P)`.
3. Forge bytes: `offset = a` serialized via `to_bytes`, then consensus-encoded `TxOut{value: large, script_pubkey: S'}` where `S'` is a *different* attacker-owned P2TR script `p2tr_script_buf(P')` with `P' != P` (i.e., an output not controlled by `K` at all).
4. `ReceivedOutput::read` succeeds; `Output::key()` returns `P' − a·G` — with `S'` chosen as `p2tr_script_buf(K + a·G)` the reported key is `K` even though the on-chain output pays a key whose discrete-log offset from `K` is not `a`.
5. The processor records `balance = large` for `K`; `SignableTransaction::multisig` later returns `None` because `p2tr_script_buf(keys.offset(a).group_key()) != prevouts[i].script_pubkey`, proving the reported funds were never spendable.
