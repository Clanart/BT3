Based on my investigation, I found a genuine discrepancy in `upb`'s JSON decoder that structurally mirrors the CVE-2016-8860 pattern (an internal function assuming NUL-terminated data, with a code path that does not guarantee that invariant), though I want to be upfront that I could not fully trace `jsondec_string()`'s buffer-allocation code (unescape path) within my remaining tool budget, so the exploitability claim below is partially inferred from consistent evidence across three vendored copies of the same code rather than a confirmed heap-layout trace.

### Title
Unterminated string view passed to `strtod()` in upb JSON `DOUBLE`/`FLOAT`-as-string decoding - (File: `upb/json/decode.c`)

### Summary
`jsondec_double()` parses a numeric value encoded as a JSON *string* (e.g. `"3.14"`) by calling `strtod(str.data, &end)` directly on the `upb_StringView` returned by `jsondec_string()`, with no NUL-termination guard. This is inconsistent with the sibling function `jsondec_number()` in the same file, which explicitly copies the numeric token into a local `nullz[64]` scratch buffer specifically because, per its own comment, "strtod() expects a null-terminated string." [1](#0-0) [2](#0-1) 

### Finding Description
The Tor CVE's failed invariant was: an internal routine assumed `buf_t` data was NUL-terminated, but the buffer-management code (`or/buffers.c`) never enforced that guarantee, so a crafted, attacker-controlled buffer without a trailing NUL caused an out-of-bounds read/crash.

The transferable invariant here is the same shape: `strtod()` (a C standard library function) requires its input to be a NUL-terminated C-string — it does not take a length parameter and will scan forward until it hits a non-numeric byte. `jsondec_number()` in this file explicitly acknowledges this contract and defends against it by bounding the token to 64 bytes and copying into a local, explicitly NUL-terminated buffer before calling `strtod`. [1](#0-0) 

However, `jsondec_double()`'s string-literal branch (used for `google.protobuf.DoubleValue`/`FloatValue`-style JSON string encodings, e.g. `{"value": "3.14"}`) calls `strtod(str.data, &end)` directly on the `upb_StringView` produced by `jsondec_string(d)`, with no equivalent NUL-termination or bounds handling. [2](#0-1)  If that view's backing storage is not guaranteed to be immediately followed by a non-numeric byte (either a real NUL or a byte that halts `strtod`'s scan), this violates the same contract that caused the Tor bug: an internal parsing routine (`strtod`) is trusting an attacker-influenced buffer to be terminated in a way the buffer-producing code doesn't actually guarantee.

The identical code (including the identical comment about `strtod` expecting NUL-termination in the sibling function) is duplicated verbatim across three vendored copies of upb's JSON decoder: [3](#0-2) [4](#0-3) [5](#0-4) 

### Impact Explanation
If `jsondec_string()`'s returned buffer for an unescaped/copied string is not NUL-terminated and not followed immediately by a `strtod`-stopping byte (e.g., an arena allocation sized exactly to the string length, adjacent to attacker-influenced heap content), `strtod` could read past the intended bounds of the string, potentially causing a crash (denial of service) analogous to the Tor CVE, or in the worst case incorporating adjacent heap bytes into the parsed double value (information disclosure via value corruption). This is reachable through the public ProtoJSON parsing API (`Message::JsonStringToMessage` / language-specific JSON parse entry points) with a well-formed, bounded, attacker-supplied JSON payload targeting a `double`/`float` field encoded as a JSON string — no privileged access or hostile schema required.

### Likelihood Explanation
I was not able to confirm within this session whether `jsondec_string()`'s output buffer is always followed by a terminating/non-numeric byte in all cases (e.g., strings with escape sequences that get copied to an arena buffer vs. unescaped strings that may be returned as direct views into the original, NUL-adjacent input buffer). Because JSON string content is delimited by a closing `"`, in the common case (no escapes, view directly into original buffer) the byte after the string content is `"`, which is not part of `strtod`'s valid syntax and would halt the scan safely — meaning likelihood may be low in that path. The risk concentrates specifically on the unescape path, if it allocates an exact-length buffer without a trailing sentinel byte. This aspect requires further code tracing (specifically `jsondec_string`'s unescape/allocation logic) that I could not complete before this response was due.

### Recommendation
For defense-in-depth and consistency with the already-established pattern in `jsondec_number()`, `jsondec_double()`'s string-literal branch should bound the string length and copy into a local NUL-terminated scratch buffer (mirroring the `nullz[64]` pattern) before calling `strtod`, rather than assuming the `upb_StringView` from `jsondec_string()` is safely terminated. [6](#0-5) 

### Proof of Concept
I did not execute a test and cannot claim to have reproduced a crash. A conceptual reproduction target would be: construct a `.proto` schema with a `double` field, then send ProtoJSON input `{"field": "<crafted string requiring unescape, sized to align with an arena boundary>"}"` through `upb_JsonDecode`, and inspect (under ASan) whether `strtod` reads past the string-view's `data + size` boundary in the `jsondec_double` string branch at `upb/json/decode.c:795`. This requires first confirming `jsondec_string`'s allocation/termination behavior, which remains unverified. [2](#0-1)

static upb_MessageValue jsondec_double(jsondec* d, const upb_FieldDef* f) {
  upb_StringView str;
  upb_MessageValue val;

  switch (jsondec_peek(d)) {
    case JD_NUMBER:
      val.double_val = jsondec_number(d);
      break;
    case JD_STRING:
      str = jsondec_string(d);
      if (str.size == 0) {
        jsondec_checkempty(d, str, f);
        val.double_val = 0.0;
      } else if (jsondec_streql(str, "NaN")) {
        val.double_val = NAN;
      } else if (jsondec_streql(str, "Infinity")) {
        val.double_val = INFINITY;
      } else if (jsondec_streql(str, "-Infinity")) {
        val.double_val = -INFINITY;
      } else {
        char* end;
        val.double_val = strtod(str.data, &end);
        if (end != str.data + str.size) {
          d->result = kUpb_JsonDecodeResult_Error;
          upb_Status_SetErrorFormat(
              d->status,
              "Non-number characters in quoted number (field: %s). "
              "This will be an error in a future version.",
              upb_FieldDef_FullName(f));
        }
      }
      break;
    default:
      jsondec_err(d, "Expected number or string");
  }

  if (upb_FieldDef_CType(f) == kUpb_CType_Float) {
    float f = val.double_val;
    if (val.double_val != INFINITY && val.double_val != -INFINITY) {
      if (f == INFINITY || f == -INFINITY) jsondec_err(d, "Float out of range");
    }
    val.float_val = f;
  }

  return val;
}
