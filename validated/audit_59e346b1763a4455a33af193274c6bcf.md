Based on my investigation, I found the strongest analog. The pattern in `findGenericTrampolineAccount` mirrors the referral bug's core invariant: an "unset" identifier (empty username, analogous to `0x0`) is resolved to a stored default value scoped only by host, not by the full context the user actually intended.

### Title
Credential-helper falls back to any username stored for a host, letting an attacker-controlled repo/remote on a shared host silently harvest a previously-saved generic credential - ([File: app/src/lib/trampoline/find-account.ts])

### Summary
`findGenericTrampolineAccount` resolves the login for a non-GitHub ("generic") remote URL by using the URL's embedded username if present, or otherwise falling back to whatever username was last stored for that endpoint via `getGenericUsername(endpoint)`. `endpoint` is computed by `urlWithoutCredentials`, which only strips the username/password from the URL — it keeps scheme, host, port, and full path. Because the fallback path is triggered simply by the remote URL lacking a username (the "default"/unset value, analogous to the referral hash defaulting to `0x0`), any repository or remote whose URL omits a username on a host the user has previously stored credentials for will silently receive that stored username, and then the associated stored password/token is fetched and handed to Git.

`getGenericUsername`/`getGenericPassword` are keyed purely by `endpoint` (scheme+host+port+path with credentials stripped) via `localStorage`/`TokenStore`: [3](#0-2) 

The broken invariant is the same shape as the referral report: `parsedUrl.username === ''` is the "unset/default" state (the `0x0` hash), and instead of requiring explicit, per-repository consent, Desktop transparently substitutes a *previously stored* identity for that default state. In the referral bug, anyone claiming the `0x0` slot becomes referral-of-record for every user who never set one; here, whichever URL/host combination first causes the user to save generic credentials becomes the implicit identity for every subsequent remote on that same host that also omits a username — including remotes introduced by a cloned/fetched repository (e.g., a submodule URL, a rewritten `insteadOf` remote, or a repo whose maintainer changes `origin`/adds a new remote pointing at the same self-hosted Git server without a username). Desktop's credential trampoline (`createCredentialHelperTrampolineHandler` → `getCredential` → `getGenericCredential` → `findGenericTrampolineAccount`) performs this substitution automatically, with no re-prompt and no indication to the user that credentials for a different repository/path on the same host are being reused: [4](#0-3) 

Existing guards do not stop this path: the only scoping is `endpoint` (host+path), and there is no check that the *previous* repository that stored the credential is the *same* repository/remote now requesting it. `getEndpointKind` only decides between "generic" vs GitHub/GHE handling based on the host, not on repository identity, so any generic host (self-hosted GitLab/Gitea/Bitbucket Server, etc.) is subject to this reuse regardless of which repo the remote belongs to.

### Impact Explanation
If a user has ever authenticated to a self-hosted Git server (non-GitHub) from within Desktop and chosen to store the credential, then adds, clones, or fetches from *any other repository or remote* that resolves to the same host and omits a username in its URL (a very common URL style, e.g. `https://git.internal.example.com/other-team/other-repo.git`), Desktop's trampoline will silently hand the stored username/token to Git for that unrelated repository. Since the trigger is simply "a repo the attacker controls (or a remote/URL the attacker can set, e.g. via a malicious submodule, `.gitmodules`, or a shared internal Git host used by many teams) matches that host and lacks credentials in the URL," this can result in unauthorized use of the victim's stored token against a repository they never intended to authenticate to — a credential-scope confusion / unauthorized use of stored authentication.

### Likelihood Explanation
Requires only that (a) the user has previously saved a generic (non-GitHub) credential for a host in Desktop, and (b) a new remote/repo pointing at the same host without embedded credentials is opened, cloned, or fetched — both of which are ordinary, unprivileged Desktop usage flows (adding a remote, cloning a repo, or a repo's own `.gitmodules`/config directing Desktop to fetch from an additional path on that host). No local/admin access, malware, or leaked credentials are required; the "attacker" only needs to control a repository/remote URL sharing a host with one the victim already authenticated to.

### Recommendation
Scope stored generic credentials (and the fallback lookup) to the account/repository context actually establishing trust — at minimum warn/re-prompt when a generic credential is being reused for a different repository path than the one it was originally saved for, rather than silently keying the fallback purely by host+path with an implicit "no username = use whatever was last saved."

export async function findGenericTrampolineAccount(
  trampolineToken: string,
  remoteUrl: string
) {
  const parsedUrl = new URL(remoteUrl)
  const endpoint = urlWithoutCredentials(remoteUrl)

  const login =
    parsedUrl.username === ''
      ? getGenericUsername(endpoint)
      : parsedUrl.username

  if (!login) {
    return undefined
  }

  const token = await memoizedGetGenericPassword(
    trampolineToken,
    endpoint,
    login
  )

  if (!token) {
    // We have a username but no password, that warrants a warning
    log.warn(`credential: generic password for ${remoteUrl} missing`)
    return undefined
  }

  return { login, endpoint, token }
}

export function urlWithoutCredentials(remoteUrl: string | URL): string {
  const url = new URL(remoteUrl)

  return url.toString()
