## Title
Silent, un-prompted rewrite of a repository's git remote URL based on unverified GitHub API data - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The Algebra report describes a "detached" state: after `crossTo` reverts, `activeIncentive` is zeroed but the dependent state (`rewardRates`, `deactivated`) is *not* updated to match, so the system keeps acting on frozen, no-longer-valid data instead of re-validating or safely tearing down. The closest analog I can support with local evidence in this Desktop codebase is `updateRemoteUrl` in [1](#0-0) , which silently mutates the user's local git `origin` remote URL to whatever `clone_url` the GitHub API returns for the repository, without any user confirmation, whenever a set of heuristic conditions are met.

### Finding Description
`repositoryWithRefreshedGitHubRepository` (invoked on nearly every git operation via `withRefreshedGitHubRepository`, on repository selection, and on account changes) fetches the repository's info from the GitHub API using the owner/name association Desktop already has cached, then calls `updateRemoteUrl`: [2](#0-1) 

Inside `updateRemoteUrl`, the code compares the *current* remote URL to the *previous* cached `gitHubRepository.cloneURL`, and to the *new* `clone_url` returned by the API: [3](#0-2) 

If the protocol matches and the remote "looks unchanged" relative to the old cached association, but the new API-provided clone URL differs, Desktop calls `gitStore.setRemoteURL(...)` and rewrites the local `origin` remote to the API-supplied URL — with no dialog, confirmation, or diff shown to the user, unlike the explicit `UpstreamAlreadyExists` dialog used elsewhere for a very similar scenario (upstream remote drift), which does prompt the user: [4](#0-3) .

The broken invariant mirrors the Algebra bug precisely: the "association" (which GitHub repository entity backs this local clone — the analog of `activeIncentive`) can change server-side (rename, transfer, or a stale/incorrect API response), and the dependent "trusted" value (the local git remote used for all future pushes/fetches/pulls — the analog of `rewardRates`) is silently updated to follow that association *without* re-establishing user trust or verifying that this is actually the repository the user intended to be working with. There is no re-authentication, no ownership/ACL re-check beyond "the API returned a repo for this owner/name," and no UI surfacing, unlike the "upstream already exists" flow which handles the conceptually identical case explicitly with a warning dialog.

### Impact Explanation
If the association between the local clone and the "matched" GitHub repository becomes stale or attacker-influenced (e.g., a repository is renamed/transferred and the vacated owner/name is later re-registered/squatted, or the API's `fetchRepository` call resolves to an unexpected repository due to a rename), Desktop will automatically point the user's `origin` remote at a new URL and the user's subsequent `git push`/`git fetch`/`git pull` operations silently target a different remote than the one they configured — a silent corruption of what the user pushes and fetches. Because the credential trampoline chooses credentials per-host at request time (`findGitHubTrampolineAccount` in [5](#0-4) ), if the new remote still resolves to the same GitHub host, the user's existing GitHub token would be used against a repository the user never explicitly agreed to interact with — enabling data disclosure (private commits/branches pushed to the wrong destination) without any user prompt.

### Likelihood Explanation
This code path runs automatically and frequently — it's invoked from `withRefreshedGitHubRepository`, which wraps push, fetch, pull, revert, checkout-commit, and repository-selection flows [6](#0-5) , so the rewrite can happen passively during normal usage, not requiring any unusual local action by the user. Exploitability, however, depends on an attacker being able to influence what `api.fetchRepository(owner, name)` returns for the owner/name Desktop already associates with the repository (e.g., via repository rename + name-squatting on GitHub, which is a documented general git-hosting risk, not something requiring local/physical access or malware). I could not fully verify from static code alone how `matchGitHubRepository`/`upsertGitHubRepositoryFromMatch` resolve the owner/name (i.e., whether they re-derive owner/name from the *current* remote URL each time, which would make the squatting scenario more or less exploitable) — this is a gap in what I was able to confirm from the indexed code, and would need direct testing/tracing in a full checkout.

### Recommendation
Before silently rewriting a tracked remote's URL based on GitHub API data, surface an explicit confirmation dialog to the user (mirroring the existing `UpstreamAlreadyExists` pattern), and additionally verify the API-returned repository's stable identifier (GitHub repository ID) still matches the ID Desktop has cached for that association, not just owner/name/protocol heuristics, before treating the new `clone_url` as trustworthy.

### Proof of Concept
Not independently reproducible from static analysis alone. Based on code inspection: (1) clone/add a repository so Desktop associates it with `GitHubRepository` X (owner/name, `cloneURL`); (2) cause the upstream GitHub repository at that owner/name to actually change identity in a way the API reflects, while owner/name based lookup still succeeds (e.g., via repository rename/transfer + name reuse); (3) trigger any tracked git operation (fetch/push/checkout) that runs through `withRefreshedGitHubRepository`; (4) observe that `origin`'s URL is silently rewritten via `gitStore.setRemoteURL` with no prompt, as shown by the existing test asserting exactly this rewrite behavior: [7](#0-6) .

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

    fn: (repository: Repository) => Promise<T>

    let updatedRepository = repository
    const account: Account | null = getAccountForRepository(
      this.accounts,
      updatedRepository
    )

    // If we don't have a user association, it might be because we haven't yet
    // tried to associate the repository with a GitHub repository, or that
    // association is out of date. So try again before we bail on providing an
    // authenticating user.

        repository
      )
