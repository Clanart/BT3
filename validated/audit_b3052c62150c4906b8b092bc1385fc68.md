### Title
`SignableTransaction` omits the OP_RETURN data output from its weight/fee estimation, so the reported `needed_fee` and effective fee rate are wrong - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an OP_RETURN output into `tx_outs` (up to 80 bytes of caller-supplied data), but calculates the transaction weight and virtual size via `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which only expands `payments` — never the OP_RETURN output. Every reported and budgeted fee (`needed_fee`, the `TooLowFee` floor check, and the implicit effective fee rate when a change output is created) is therefore computed against a smaller transaction than the one actually signed and broadcast. This mirrors the DODO bug class: the value reported to the caller (`needed_fee`, and the "leftover" implicitly retained) does not match the value the finalized transaction actually uses.

### Finding Description
In `SignableTransaction::new`, outputs are assembled first — payments and then the OP_RETURN: [1](#0-0) 

Yet the weight/vbyte estimation used for `needed_fee` is computed only over `payments`: [2](#0-1) 

`calculate_weight_vbytes` builds the synthetic transaction purely from `payments` plus an optional change output; it has no parameter for and never includes the OP_RETURN output: [3](#0-2) 

The same undercount occurs for the change path, which again passes only `payments`: [4](#0-3) 

Consequences:

- `needed_fee()` understates the fee required to hit the requested `fee_per_vbyte` by `data_len + ~11` vbytes worth of fee (an OP_RETURN output with 80 bytes of data adds ~91–93 vbytes).
- The `TooLowFee` relay-floor check at lines 211–213 passes on the underestimated vbytes, so a caller requesting the minimum viable `fee_per_vbyte` produces a transaction whose *actual* effective rate falls below `DEFAULT_MIN_RELAY_TX_FEE`, making it unrelayable/unconfirmable — funds "sent" that are not actually spendable on schedule.
- With a change output, the change amount is `input_sat - payment_sat - fee_with_change`, so the effective fee paid is `fee_with_change` — below the caller-requested rate by the entire OP_RETURN size. `fee()` will truthfully report the lower actual fee, but `needed_fee()` advertises a number that was never the real requirement for the requested rate.

This is reachable entirely through public inputs: `data` is an untrusted `Option<Vec<u8>>` supplied by the caller of `SignableTransaction::new`, and the transaction is signed by the FROST `TransactionMachine` and broadcast.

### Impact Explanation
The reported fee accounting diverges from reality on every transaction carrying data. Callers relying on `needed_fee()` (e.g., accounting layers that escrow or report the fee, or that pass `fee_per_vbyte` near the relay minimum) get an understated figure; the signed transaction either pays less than the requested rate or fails the relay floor in practice, leaving signed payments stuck — the "reported received/spent amount is not the actual amount" class. Severity: Medium — no permanent loss, but systematically incorrect reported values and potentially unbroadcastable transactions.

### Likelihood Explanation
Any code path constructing a `SignableTransaction` with `data: Some(..)` (the intended Serai use is OP_RETURN metadata for cross-chain protocols) triggers it deterministically; no attacker cooperation is needed beyond supplying `data`, which is a normal public input.

### Recommendation
Pass the OP_RETURN output (or its serialized size) into `calculate_weight_vbytes` for both the change and no-change estimations so `needed_fee`, the `TooLowFee` check, and the change residual reflect the real transaction. Alternatively, push the `TxOut` list itself into the estimator rather than reconstructing from `payments`.

### Proof of Concept

// and fee_per_vbyte exactly at the minimum relay floor.

let payments = vec![(addr(), 5_000)];
let data = Some(vec![0u8; 80]);
let min_fpv = /* sats/vbyte meeting DEFAULT_MIN_RELAY_TX_FEE */;

let tx = SignableTransaction::new(inputs, &payments, Some(change), data, min_fpv).unwrap();
// needed_fee was computed WITHOUT the ~92 vbytes of OP_RETURN output.

assert!(tx.fee() < actual_vsize(&tx) * min_fpv_required); // under-priced, unrelayable

The `TooLowFee` check at send.rs:211 passes because `vbytes` excludes the data output, while the broadcast transaction includes it — the reported `needed_fee()` never equals the fee the transaction would need at the requested rate.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
