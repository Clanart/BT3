### Verdict

No vulnerability found for this question.

**Reasoning:** The proposed exploit path is already blocked by two independent layers, neither of which can be bypassed by a crafted `account_infos_len`:

1. **`saturating_mul`/`saturating_add` never wrap.** In `translate_account_infos`, the feature-gated check computes `account_infos_addr.saturating_add(account_infos_len.saturating_mul(size_of::<T>() as u64))` [1](#0-0)  — since these are *saturating* (not wrapping) operations, an attacker cannot make an enormous length "wrap around" to a small value; the result simply saturates at `u64::MAX`, which is `>= ebpf::MM_INPUT_START` and gets rejected when the feature is enabled.

2. **`translate_slice` enforces real memory-mapping bounds regardless of the feature flag.** `translate_slice_inner!` independently computes `total_size = len.saturating_mul(size_of::<T>())`, rejects it via `isize::try_from(total_size).is_err()` if it saturated to an out-of-range value, and then calls `memory_mapping.map(...)` [2](#0-1) . This underlying sBPF memory-region `map()` call performs the actual bounds validation against the VM's mapped regions unconditionally — it does not depend on `syscall_parameter_address_restrictions`. If the requested `(addr, len)` doesn't correspond to a validly mapped region, `translate_slice` returns `Err` before `translate_account_infos` ever reaches the indexing loop at [3](#0-2) .

3. Additionally, `check_account_infos` caps the number of account infos at `MAX_CPI_ACCOUNT_INFOS` (255) [4](#0-3)  before the indexing loop runs, and since `translate_slice` only succeeds when it can actually produce a slice of the requested length, `account_infos.len()` is guaranteed to equal `account_infos_len` when the loop executes, making `account_infos[account_index]` always in-bounds.

So whether `syscall_parameter_address_restrictions` is on or off, an adversarial `(account_infos_addr, account_infos_len)` pair that would exceed mapped-region bounds is rejected by `translate_slice`'s call into the memory-mapping layer before any indexing occurs — the feature flag only adds an *earlier* rejection path, it is not the sole line of defense the question assumes.

macro_rules! translate_slice_inner {
    ($memory_mapping:expr, AccessType::Store, $vm_addr:expr, $len:expr, $T:ty, $check_aligned:expr $(,)?) => {{
        if $len == 0 {
            Ok(std::ptr::slice_from_raw_parts_mut(
                std::ptr::dangling_mut::<$T>(),
                0,
            ))
        } else {
            let total_size = $len.saturating_mul(size_of::<$T>() as u64);
            if isize::try_from(total_size).is_err() {
                Err($crate::memory::MemoryTranslationError::InvalidLength.into())
            } else {
                match $crate::translate_inner!(
                    $memory_mapping,
                    map,
                    $crate::solana_sbpf::memory_region::AccessType::Store,
                    $vm_addr,
                    total_size
                ) {
                    Err(e) => Err(e),
                    Ok(host_buf) if $check_aligned && !host_buf.ptr().cast::<$T>().is_aligned() => {
                        Err($crate::memory::MemoryTranslationError::UnalignedPointer.into())
                    }
                    Ok(host_buf) => Ok(std::ptr::slice_from_raw_parts_mut(
                        host_buf.ptr_mut().cast(),
                        $len as usize,
                    )),
                }
            }
        }
    }};
