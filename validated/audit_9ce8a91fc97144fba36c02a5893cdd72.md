### Title
Copilot conflict-resolution hunk-boundary mismatch causes silent corruption of merged commit content - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
The "Resolve with Copilot" merge-conflict feature parses a conflicted file's marker structure twice, using two independently-implemented, non-identical parsers: once to build the AI prompt (`extractConflictHunks`) and once to splice the AI's per-hunk answers back into the file (`reassembleResolvedFile`). When a merge/rebase brings in attacker-crafted file content that contains conflict-marker-*like* text inside an actual conflicting region, the two parsers can disagree on how many hunks exist and where their boundaries lie. The only consistency check performed (`validateResolutionPaths`) compares the model's hunk count against `extractConflictHunks`'s count — never against what `reassembleResolvedFile` will actually find when it re-walks the raw content. This lets a misaligned resolution get spliced into the wrong location of the file, which is then written to disk and staged/committed with no markers left and no warning to the user.

### Finding Description
`extractConflictHunks` (app/src/lib/copilot-conflict-context.ts) splits a conflicted file into hunks using: [1](#0-0) 
and a hand-rolled state machine that treats *any* line matching those regexes as a marker, including lines that occur inside `oursContent`/`theirsContent` themselves: [2](#0-1) 

Separately, `reassembleResolvedFile` (app/src/lib/copilot-conflict-resolution.ts) re-parses the *same* raw file content with a different, simpler marker set that has no notion of the diff3 base marker (`|||||||`) and a different lookahead algorithm for locating the closing marker: [3](#0-2) 

The only guard that ties the two together is `validateResolutionPaths`, which checks that the *count* of hunks Copilot returned matches `extractConflictHunks`'s count — it never re-validates against how many marker blocks `reassembleResolvedFile` will actually locate: [4](#0-3) 

Because the two parsers use different logic to decide where a conflict block starts/ends, a conflicting hunk whose `oursContent`/`theirsContent`/`baseContent` happens to contain a line matching `^<{7}`, `^\|{7}`, `^={7}`, or `^>{7}` (e.g. a documentation file, a CI/test fixture, or a tutorial about resolving git conflicts — all plausible content in a repository an attacker gets the victim to merge) will be split by `extractConflictHunks` into more (or differently-bounded) hunks than `reassembleResolvedFile` will find when it walks the same content looking only for the outermost `<<<<<<<` … `=======` … `>>>>>>>` triple. The model answers according to the boundaries it was shown (from `extractConflictHunks`), but `reassembleResolvedFile` splices those answers into boundaries it computed independently and increments `hunkIndex` per outer block it finds, not per prompt-hunk. The result: `hunkResolutions[hunkIndex].resolvedContent` for one conflict gets written into a different conflict's location, or resolved text belonging to a later hunk is dropped/duplicated.

### Impact Explanation
This is silent corruption of what the user commits: the reassembled file has no remaining conflict markers (so it looks fully resolved) and is fed directly into the merge-completion / commit flow, but its content is not what either side or the AI intended for that region. Because there's no diff review step that re-parses markers, a user relying on Desktop's Copilot conflict resolution can push a merge commit whose code silently combines the wrong logical pieces — e.g., swapping the resolved content of two unrelated conflicting functions — without any error or warning surfaced by `validateResolutionPaths`, which only checks aggregate hunk counts, not reassembly alignment.

### Likelihood Explanation
Requires a merge/rebase/cherry-pick against attacker-influenced branch content (a cloned/fetched repository or a PR branch) that produces at least one real conflict whose ours/theirs/base text contains a line coincidentally matching a 7-character marker pattern — plausible in documentation, test fixtures, or any file that itself discusses/demonstrates git conflict markers, and easy for an attacker to engineer deliberately in a branch offered for merge. No special privileges, admin rights, or social engineering beyond "the victim merges/rebases with this branch and uses the AI conflict-resolution feature" are needed.

### Recommendation
Make `reassembleResolvedFile` reuse the exact same boundary-detection state machine as `extractConflictHunks` (including diff3 base-marker handling) so hunk counts and offsets are guaranteed to agree, or have `reassembleResolvedFile` accept the hunk boundaries computed once (line offsets) instead of re-deriving them from raw content a second time. Additionally, `validateResolutionPaths` should assert that a subsequent dry-run of `reassembleResolvedFile` produces exactly the number of splice points expected, failing closed (falling back to manual conflict resolution) rather than silently misapplying resolutions.

### Proof of Concept
1. Set up a merge that produces a real conflict in `docs/example.md`, where the "theirs" side's conflicting text itself contains a line such as `<<<<<<< sample` (e.g., copied from a tutorial about resolving conflicts) inside the theirs block.
2. Trigger Desktop's Copilot conflict resolution; `extractConflictHunks` will treat the embedded `<<<<<<< sample` line as a nested marker and split what is really one conflict into two "hunks" in the prompt sent to the model.
3. The model responds with two hunk resolutions matching the prompt's split.
4. `reassembleResolvedFile` re-scans the raw file with its own simpler marker logic, which does not split on the embedded line the same way, and finds a different number of outer conflict blocks (or the same count but different boundaries).
5. `hunkResolutions[hunkIndex]` is spliced at the wrong marker boundary, producing a merged file containing swapped/misplaced resolved content with no markers left — this file is written to disk and offered to the user as fully resolved, then committed. [5](#0-4)

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

// Conflict markers used by reassembleResolvedFile to locate marker blocks.
const reassemblyOursMarker = /^<{7}(?:\s|$)/
const reassemblySeparatorMarker = /^={7}$/
const reassemblyTheirsMarker = /^>{7}(?:\s|$)/

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
