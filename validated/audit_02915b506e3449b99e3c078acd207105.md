## Analysis

The Rust BEEFY verifier (`modules/consensus/beefy/verifier/src/lib.rs`) mirrors the exact same pattern as the Solidity `EcdsaBeefy.sol`: it counts `signatures_length` (raw vote count) against the participation threshold and builds `authority_indices`/`authority_leaves` directly from the submitted signature list, without deduplicating `sig.index`. Neither implementation rejects a `votes`/`signatures` array that repeats the same `authorityIndex` multiple times. This is the same missing-uniqueness-check pattern as the DIA `addGuardian`/`addOracle` report, applied to consensus supermajority counting instead of an oracle/guardian registry.

I could not verify, without access to the external `solidity-merkle-trees` / Rust `merkle-proof` library source, whether `MerkleMultiProof.VerifyProof` (Solidity) or `MerkleProof::verify` (Rust) itself rejects duplicate indices in the leaves array. That library-level behavior is the deciding factor for exploitability and sits outside this repository (and per the task's exclusion rules, "imported dependency bugs" are out of scope) — this is a real limitation of what I can confirm.

### Title
Missing duplicate-signer check in BEEFY supermajority threshold counting - ([File: evm/src/consensus/EcdsaBeefy.sol])

### Summary
`EcdsaBeefy.verifyMmrUpdateProof` (and the analogous Rust `verify_mmr_update_proof` in `modules/consensus/beefy/verifier/src/lib.rs`) computes the 2/3+1 supermajority threshold from the raw length of the submitted `votes`/`signatures` array [1](#0-0)  without ever checking that each `vote.authorityIndex` is unique. This is structurally identical to the DIA report's "add without uniqueness check" flaw — here the "list being added to" is the set of votes counted toward consensus finality, rather than a guardian/oracle registry.

### Finding Description
`checkParticipationThreshold(sigLen, authoritySet.len)` at [2](#0-1)  treats `sigLen` (`relayProof.signedCommitment.votes.length`) as the count of distinct participating authorities. The loop that follows recovers a signer address per vote and builds a `MerkleMultiProof.Leaf` keyed by `vote.authorityIndex` [3](#0-2) , but there is no `seen`/`BTreeSet` style check across `vote.authorityIndex` values, unlike other duplicate-sensitive paths in this same codebase, e.g. `pallet-ismp-relayer`'s explicit `seen.insert(key.encode())` guard against padded batches [4](#0-3) , `IntentGatewayV2.placeOrder`'s explicit duplicate-output-token rejection [5](#0-4) , and the Pharos/Tendermint verifiers' explicit `DuplicateParticipant`/`ensure_unique_addresses` checks [6](#0-5) [7](#0-6) . The Rust BEEFY verifier has the identical gap [8](#0-7) .

### Impact Explanation
If the underlying merkle multi-proof library does not itself enforce unique leaf indices (unverifiable from this repo alone), an attacker who obtains even one legitimate authority's signature over a given `commitmentHash` (BEEFY signed commitments are broadcast publicly, so this requires no key compromise or malicious relayer) could pad the `votes`/`signatures` array with repeated copies of that single vote to satisfy `checkParticipationThreshold`. This would let a state/consensus update pass the "2/3+1 supermajority" gate without an actual supermajority of distinct authorities having attested to it, undermining the core Hyperbridge invariant that "consensus proofs...must never let false remote state become trusted."

### Likelihood Explanation
Whether this is exploitable depends entirely on the external merkle-multiproof implementation's handling of duplicate leaf indices, which is outside this repository. Given that this is unverified, I present it as a structural gap (missing an explicit, local uniqueness guard that the rest of the codebase consistently applies elsewhere) rather than a confirmed exploit.

### Recommendation
Add an explicit duplicate check on `vote.authorityIndex` (Solidity) / `sig.index` (Rust) before computing `sigLen`/`signatures_length` for the participation threshold and before building the merkle leaves — e.g., collect indices into a set and revert/error if the set size differs from the array length, mirroring the pattern already used in `pallet-ismp-relayer::accumulate` and the Pharos/Tendermint verifiers.

### Proof of Concept
Not constructible without confirming the duplicate-index behavior of `MerkleMultiProof.VerifyProof` / `MerkleProof::verify`, which live in an external dependency not present in this repo's index. A concrete PoC would require: (1) a valid BEEFY signed commitment with N authorities where N < 2/3+1 of the authority set actually signed, (2) padding `votes` with repeated entries from the same signer(s) until `sigLen >= 2N_required`, and (3) confirming the multiproof verification still succeeds against `authoritySet.root` with duplicated `(index, hash)` leaf entries.

fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
