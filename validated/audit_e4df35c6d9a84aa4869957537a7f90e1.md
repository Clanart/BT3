### Title
Unsynchronized `MemNode`/tree mutation across `Tree.Copy()` during EndBlock snapshotting can corrupt or crash SC nodes - ([File: sei-db/state_db/sc/memiavl/tree.go])

### Summary
The `nouveau` report is a bug-class hint about missing locking around a shared object tree that concurrent operations traverse and mutate, leading to a general-protection fault / use-after-free style corruption. The analogous reachable pattern in sei-chain is in the memiavl SC tree used to back state commitment for the EVM/Cosmos state trie: `Tree.Copy()` hands out a shallow copy of the tree that shares the same underlying `MemNode` objects with the live tree, but the copy gets its **own** mutex, so the live tree's ongoing `ApplyChangeSet`/`SaveVersion`/`RootHash` work is not serialized against readers or snapshot-writers operating on the copy `Kirstentat/sei-chain--008/sei-db/state_db/sc/memiavl/tree_race_test.go:107-153,155-252`.

### Finding Description
`RootHash()` and the proof builders in memiavl take a write lock because `MemNode.Hash` fills a shared hash cache in place (this was already fixed once for the intra-tree race, tracked as "Immunefi 83246 / STO-601") [1](#0-0) . However, `Tree.Copy()` only gives the copy its own mutex; it does not serialize the copy against the live tree it was copied from, even though both instances still reference the same `MemNode` graph [2](#0-1) .

This matters because `DB.Copy()` / `CommitStore.Copy()` are used by the EndBlock snapshot path (`SnapshotSCStore`): a copy is taken mid-version, between `ApplyChangeSets` and `Commit`, meaning the copy can still hold nodes that the live tree's `cowVersion` floor considers mutable [3](#0-2) . While the background snapshot writer traverses the copy's nodes, the live tree keeps committing new blocks, and `Mutate` clears `MemNode.hash` under the writer while `writeLeafDirect` emits the node header and hash as two separate writes — a torn read during this unsynchronized access can write a leaf record with the header but no hash, truncating the leaves file by exactly one hash-length (32 bytes short of a multiple of 48) [4](#0-3) . This corrupted snapshot file is documented to surface at node restart as a fatal parse error ("leaves file size N is not a multiple of 48") [5](#0-4) , i.e., the node panics/refuses to start from that snapshot.

I was not able to fully confirm from the available index whether `Tree.Copy()` currently freezes/deep-copies mutable nodes before handing the copy to the snapshot writer (i.e., whether this race is already closed in the shipped code) — the `Copy`/freeze implementation in `tree.go` and the exact call sites in `db.go`/`multitree.go`/`store.go` that invoke `Copy()` during `SnapshotSCStore` could not be retrieved in full within the available tool budget. The `_race_test.go` file frames this explicitly as a still-open gap relative to the write-lock fix ("one lock away from the fix for it"), which strongly suggests it is either unfixed or only partially mitigated.

### Impact Explanation
If unmitigated, a torn/corrupted background snapshot write can make the on-disk state-commitment snapshot unreadable, which crashes/halts a node on restart from that snapshot (`OpenSnapshot` failure), and if this occurs across enough validators taking snapshots around the same block window, it can cause a chain halt or the affected nodes to permanently diverge/refuse to sync — satisfying the "validator halt" / "block delay" bar. It is not attacker-triggered via a single transaction; it is a background timing race inherent in the concurrent snapshot pipeline, not something a transaction sender can directly force, which limits it to a systemic reliability bug rather than a directly exploitable fund-theft vector.

### Likelihood Explanation
The race requires specific timing (a mid-version `Copy()` landing between `ApplyChangeSets` and `Commit`, combined with continued high-throughput commits mutating the same nodes the writer is serializing). The repository's own stress test (`TestSnapshotWriteRaceWithLiveCommits`) needed hundreds of change-sets across many rounds to reliably reproduce the corruption, indicating the window is narrow under normal block cadence but becomes more likely under sustained high transaction throughput (which an unprivileged sender can induce by spamming transactions to increase commit frequency/size, thereby widening the exposure window for background snapshot rewrites).

### Recommendation
Verify that `Tree.Copy()` (and any snapshot-serving code path reached from `SnapshotSCStore`/`CommitStore.Copy`) either (a) deep-copies or freezes every `MemNode` reachable from the copy before handing it to a background writer, or (b) shares a single mutex (or otherwise serializes) between a tree and all copies derived from it, consistent with the fix already applied to `RootHash`/`GetProof` for the intra-tree race. Add the corruption check as a hard invariant (reject/re-snapshot on `errCorruptedSnapshot` rather than silently starting from a partial file), and ensure `TestSnapshotWriteRaceWithLiveCommits`/`TestCopyReadRaceWithLiveCommits` are run under `-race` in CI to catch regressions.

### Proof of Concept
The repository already contains a targeted regression harness demonstrating the mechanism end-to-end: `TestSnapshotWriteRaceWithLiveCommits` takes a `Copy()` mid-version, starts `WriteSnapshot` on the copy in a goroutine, and concurrently keeps applying change-sets and calling `SaveVersion` on the live tree; it asserts the resulting snapshot files are a multiple of the fixed record size and that the reopened snapshot matches the hash captured at copy time [6](#0-5) . Running this test under `go test -race` on the current tree/copy implementation would confirm whether the underlying `MemNode` sharing between a live tree and its `Copy()` is still unsynchronized in production code.

func TestSnapshotWriteRaceWithLiveCommits(t *testing.T) {
	const (
		rounds           = 6
		blocksPerRound   = 30
		keysPerChangeSet = 400
	)

	dir := t.TempDir()
	tree := seedTree(t, copyTestSeedKeys)
	roundDir := func(round int) string {
		return filepath.Join(dir, fmt.Sprintf("snapshot-%d", round))
	}

	var (
		wg       sync.WaitGroup
		errMtx   sync.Mutex
		writeErr []error
	)

	// Root hash of each copy at the moment it was handed to the writer.
	wantHash := make([][]byte, rounds)

	for round := 0; round < rounds; round++ {
		tree.ApplyChangeSet(changeSet(round*137, keysPerChangeSet, fmt.Sprintf("pre%02d", round)))
		frozen := tree.Copy()
		wantHash[round] = frozen.RootHash()

		snapshotDir := roundDir(round)
		wg.Add(1)
		go func() {
			defer wg.Done()
			if err := frozen.WriteSnapshot(context.Background(), snapshotDir); err != nil {
				errMtx.Lock()
				writeErr = append(writeErr, err)
				errMtx.Unlock()
			}
		}()

		_, _, err := tree.SaveVersion(true)
		require.NoError(t, err)
		for block := 0; block < blocksPerRound; block++ {
			tree.ApplyChangeSet(changeSet(block*29, keysPerChangeSet, fmt.Sprintf("r%02db%02d", round, block)))
			_, _, err := tree.SaveVersion(true)
			require.NoError(t, err)
		}
	}
	wg.Wait()
	require.Empty(t, writeErr, "snapshot writer failed while the live tree committed")

	for round := 0; round < rounds; round++ {
		snapshotDir := roundDir(round)

		info, err := os.Stat(filepath.Join(snapshotDir, FileNameLeaves))
		require.NoError(t, err)
		require.Zerof(t, info.Size()%int64(SizeLeaf),
			"round %d: leaves file size %d is not a multiple of %d", round, info.Size(), SizeLeaf)

		info, err = os.Stat(filepath.Join(snapshotDir, FileNameNodes))
		require.NoError(t, err)
		require.Zerof(t, info.Size()%int64(SizeNode),
			"round %d: nodes file size %d is not a multiple of %d", round, info.Size(), SizeNode)

		// The published snapshot must reopen, which is the check that panics the
		// node on restart when a rewrite raced a commit.
		snapshot, err := OpenSnapshot(snapshotDir, Options{})
		require.NoErrorf(t, err, "round %d: snapshot written during live commits does not reopen", round)

		// A well-formed snapshot holding the wrong nodes reopens fine, so compare
		// contents: the serialized tree must be the one that was copied.
		require.Equalf(t, wantHash[round], snapshot.RootHash(),
			"round %d: snapshot contents drifted from the copy the writer was given", round)

		require.NoError(t, snapshot.Close())
	}
