### Title
Unhandled `ValueError` in condition-opcode parsing crashes wallet signing on a malformed offer/spend puzzle output - (File: `chia/consensus/condition_tools.py`)

### Summary
`ConditionOpcode(op)` in `parse_sexp_to_condition` raises a plain `ValueError` (not `ConsensusError`) whenever a puzzle's output condition list contains an opcode byte that isn't a member of the `ConditionOpcode` enum. `conditions_for_solution`, the only guard around this parsing path, only catches `Program.EvalError`, so a `ValueError` from an unrecognized opcode propagates uncaught.

### Finding Description
`parse_sexp_to_condition` builds a `ConditionWithArgs` from each condition emitted by a puzzle's output: it validates the op-length is a single byte, then calls `ConditionOpcode(op)` directly [1](#0-0) . If `op` is a single byte that is not one of the enumerated opcode values (e.g. any of the many unused byte values below/above/between the assigned ones such as `2`-`42`, `53`-`59`, `68`-`69`, `77`-`79`, `88`-`89`, `91`+), the `bytes, enum.Enum` constructor raises `ValueError: <byte> is not a valid ConditionOpcode` rather than a handled error. The full enum surface is defined in `chia/types/condition_opcodes.py` [2](#0-1) .

The only caller wrapping this call, `conditions_for_solution`, only catches `Program.EvalError`: [3](#0-2) 
A `ValueError` raised by `ConditionOpcode(op)` is not a `Program.EvalError`, so it is not caught here and propagates to the caller.

This function chain (`conditions_for_solution` → `conditions_dict_for_solution` → `parse_sexp_to_conditions` → `parse_sexp_to_condition`) is exercised from `WalletSigner.gather_signing_info`, which is invoked for every coin spend when signing a transaction, signing a bundle, or — critically — signing an **offer received from a counterparty** via `sign_offers` / `gather_signing_info_for_trades`: [4](#0-3) [5](#0-4) 

An offer's `puzzle_reveal`/`solution` pairs are attacker-controlled data supplied by an offer counterparty. Because `conditions_dict_for_solution` runs the puzzle with `run_with_cost` and then parses whatever CLVM condition list the puzzle emits, a counterparty-crafted puzzle can be designed so that, at signing time, one of its output conditions uses an opcode byte outside the known enum range. This directly parallels TROVE-2017-010 in the external report: a remotely supplied, malformed/unexpected data value (an unrecognized condition opcode) is deserialized without a catch-all guard, producing an unhandled exception in a component (`WalletSigner`) that processes untrusted input from other parties (offer counterparties).

### Impact Explanation
An unhandled exception raised while processing an incoming offer during `sign_offers` aborts the signing coroutine with a raw traceback instead of a clean rejection. Depending on how the wallet RPC/CLI layer surrounds this call, this can crash/hang the signing flow for any offer containing such a puzzle, denying the wallet user the ability to process that (or potentially subsequent, if unhandled at a task-supervision level) offer — a spend/action-triggered processing halt reachable by an unprivileged offer counterparty, without requiring any signature or funds movement to trigger.

### Likelihood Explanation
Likelihood is moderate: constructing a CLVM puzzle whose output list contains a condition with an opcode byte outside the enum's assigned values is straightforward for any offer-crafting party, and no cost/mempool admission gate blocks this at the wallet-signing stage (it happens before broadcast, during `gather_signing_info`). However, this legacy condition-parsing path (`conditions_dict_for_solution`/`parse_sexp_to_conditions`) is not the same code path used for full-node mempool/block consensus validation (which uses the Rust `SpendBundleConditions`/`pkm_pairs` path), so the blast radius is limited to wallet-side signing rather than full network consensus.

### Recommendation
In `parse_sexp_to_condition`, catch the `ValueError` from `ConditionOpcode(op)` and convert it into a `ConsensusError`/well-defined "unknown opcode" result (mirroring how the Rust-side `UnknownCondition` classes already tolerate unrecognized opcodes elsewhere in `chia/wallet/conditions.py`), and/or broaden the `except` clause in `conditions_for_solution` to catch generic parsing errors so malformed puzzle output cannot escape as an unhandled exception during wallet signing of offers/transactions.

### Proof of Concept
1. Construct an offer whose settlement puzzle's output conditions include a CLVM value `(op ARGS...)` where `op` is a single byte not in `ConditionOpcode` (e.g. `2`, `59`, `69`, `79`, `89`, or any value ≥ 91 not equal to an assigned constant).
2. Have the victim wallet receive/import this offer and call `WalletSigner.sign_offers()` (or any flow reaching `gather_signing_info_for_trades` → `gather_signing_info`).
3. `conditions_dict_for_solution` runs the puzzle and reaches `parse_sexp_to_conditions` → `parse_sexp_to_condition`, which executes `ConditionOpcode(op)` on the crafted byte.
4. Because `conditions_for_solution`'s `except Program.EvalError` does not catch the resulting `ValueError`, the exception propagates unhandled out of `gather_signing_info`, aborting offer signing instead of returning a graceful rejection.

**Uncertainty note:** I could not fully trace how the wallet RPC/CLI or task-supervision layer surrounds `sign_offers`/`gather_signing_info_for_trades` calls in this snapshot (whether an outer handler catches all exceptions and returns a clean RPC error, which would reduce this to a non-impactful, already-mitigated case). This should be verified against the RPC dispatch code (e.g. `wallet_rpc_api.py`) before treating this as a confirmed denial-of-service; based purely on the reachable code shown here, the parsing path itself lacks a guard against this specific malformed input.

```python
def parse_sexp_to_condition(sexp: Program) -> ConditionWithArgs:
    """
    Takes a ChiaLisp sexp and returns a ConditionWithArgs.
    Raises an ConsensusError if it fails.
    """
    first = sexp.pair
    if first is None:
        raise ConsensusError(Err.INVALID_CONDITION, ["first is None"])
    op = first[0].atom
    if op is None or len(op) != 1:
        raise ConsensusError(Err.INVALID_CONDITION, ["invalid op"])

    # since the ConditionWithArgs only has atoms as the args, we can't parse
    # hints and memos with this function. We just exit the loop if we encounter
    # a pair instead of an atom
    vars: list[bytes] = []
    for arg in Program(first[1]).as_iter():
        a = arg.atom
        if a is None:
            break
        vars.append(a)
        # no condition (currently) has more than 3 arguments. Additional
        # arguments are allowed but ignored
        if len(vars) > 3:
            break

    return ConditionWithArgs(ConditionOpcode(op), vars)
```

```python
def conditions_for_solution(
    puzzle_reveal: Program | SerializedProgram, solution: Program | SerializedProgram, max_cost: int
) -> list[ConditionWithArgs]:
    # get the standard script for a puzzle hash and feed in the solution
    try:
        _cost, r = run_with_cost(puzzle_reveal, max_cost, solution)
        return parse_sexp_to_conditions(r)
    except Program.EvalError as e:
        raise ConsensusError(Err.SEXP_ERROR, [str(e)]) from e
```

```python
    async def gather_signing_info(self, spends: list[Spend]) -> SigningInstructions:
        pks: list[bytes] = []
        signing_targets: list[SigningTarget] = []
        for spend in spends:
            coin_spend = spend.as_coin_spend()
            # Get AGG_SIG conditions
            conditions_dict = conditions_dict_for_solution(
                coin_spend.puzzle_reveal,
                coin_spend.solution,
                self.max_block_cost_clvm,
            )
            # Create signature
            for pk, msg in pkm_pairs_for_conditions_dict(
                conditions_dict, coin_spend.coin, self.agg_sig_me_additional_data
            ):
                pk_bytes = bytes(pk)
                pks.append(pk_bytes)
                fingerprint: bytes = pk.get_fingerprint().to_bytes(4, "big")
                signing_targets.append(SigningTarget(fingerprint, msg, std_hash(pk_bytes + msg)))

        return SigningInstructions(
            await self.key_hints_for_pubkeys(pks),
            signing_targets,
        )
```

```python
    async def sign_offers(
        self,
        offers: list[Offer],
        additional_signing_responses: list[SigningResponse] = [],
        partial_allowed: bool = False,
    ) -> tuple[list[Offer], list[SigningResponse]]:
        unsigned_txs: list[UnsignedTransaction] = await self.gather_signing_info_for_trades(offers)
        new_offers: list[Offer] = []
        all_signing_responses = additional_signing_responses.copy()
        for unsigned_tx, offer in zip(unsigned_txs, [offer for offer in offers]):
            signing_responses: list[SigningResponse] = await self.execute_signing_instructions(
                unsigned_tx.signing_instructions, partial_allowed=partial_allowed
            )
            all_signing_responses.extend(signing_responses)
            new_bundle = self.signed_tx_to_spendbundle(
                await self.apply_signatures(
                    unsigned_tx.transaction_info.spends,
                    [*additional_signing_responses, *signing_responses],
                )
            )
            new_offers.append(Offer(offer.requested_payments, new_bundle, offer.driver_dict))
        return new_offers, all_signing_responses
```
