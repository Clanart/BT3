### Title
Reentrant escrow double-payout via CEI-violating `withdraw()` and missing reentrancy guard - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2` pays out escrowed funds to an attacker-controlled `beneficiary` address via a raw `.call{value: amount}` **before** decrementing the corresponding `_orders[commitment][token]` accounting entry, and — unlike the canonical EVM implementation — none of its state-changing entrypoints carry a reentrancy guard.

### Finding Description
In `withdraw()`, for each token in the withdrawal body the native-asset branch does: [1](#0-0) 
the external call happens first, and `_orders[body.commitment][token] -= amount` is only applied afterward. The only guard checked prior to the call is `_orders[body.commitment][token] == 0` — a non-zero check, not an exact-amount check — so re-entering before the decrement lands still passes the same guard.

Compare this to the canonical EVM `IntentsBase._withdraw`, which reduces escrow **before** making the external call: [2](#0-1) 

That mainline contract also imports and applies `ReentrancyGuardTransient` (`nonReentrant`, 6 occurrences) on its state-changing entrypoints: [3](#0-2) 
whereas a repo-wide search shows the Tron variant of `IntentGatewayV2.sol` has **zero** `nonReentrant`/`ReentrancyGuard` usages, i.e. its `withdraw()`, `onAccept`, and `onGetResponse` paths are unprotected.

`withdraw()` is reachable from two `onlyHost`-gated but attacker-influenceable entrypoints:
- `onAccept` for `RedeemEscrow`/`RefundEscrow` messages (attacker controls the encoded `beneficiary` inside the message body that they themselves constructed as `order.user` when creating the order): [4](#0-3) 
- `onGetResponse`, which decodes the same attacker-supplied `WithdrawalRequest` body and calls `withdraw(body, true)`: [5](#0-4) 

Because `beneficiary` is derived from `order.user` — a value the order creator fully controls — an attacker can deploy a contract as `order.user`/beneficiary. When their escrow is redeemed or refunded, the native-token payout calls into that contract's `receive()`/fallback before `_orders[commitment][token]` is decremented. With no `nonReentrant` modifier anywhere in this file, that fallback can re-enter any other public/external state-mutating function on the same contract (e.g. a second withdrawal-triggering path, or any function touching the same `_orders[commitment]` mapping) while the stale (non-decremented) escrow balance is still observable, enabling a double payout of the same escrowed amount before the first invocation's bookkeeping completes.

### Impact Explanation
This is a direct loss-of-funds / double-settlement path in the bridge's fund-custody logic (`_orders` escrow accounting), matching the bounty's "double-claim/double-settlement" and "stealing or loss of funds" categories. The escrowed value being drained is the intent-order's locked collateral, not just gas or a side effect — a successful reentrant call can extract more native token than was ever legitimately escrowed for that commitment.

### Likelihood Explanation
The attacker does not need a malicious relayer, prover, or admin: they only need to create their own order with a smart-contract beneficiary they control, which is standard usage of the public order-creation API. The trigger conditions (native-token order, standard fill/cancel/refund flow reaching `withdraw()`) are part of normal, unprivileged usage of the contract. The only missing precondition for full exploitation is confirming a second reachable state-mutating path that reads/writes the same `_orders[commitment][token]` slot within the reentrant call — this wasn't fully enumerable within the available investigation but the CEI violation and total absence of reentrancy guards in this specific file are directly confirmed in code, unlike the sibling mainline contract that explicitly guards against exactly this class of issue.

### Recommendation
- In `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`, decrement `_orders[body.commitment][token]` (and the `TRANSACTION_FEES` entry) **before** performing the external `.call{value:}`/token transfer, mirroring `IntentsBase._withdraw` in the mainline EVM implementation.
- Add `ReentrancyGuardTransient` (or an equivalent guard) to `onAccept`, `onGetResponse`, and any other externally reachable entrypoint that can call `withdraw()`, consistent with the mainline `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Attacker creates an order via the Tron `IntentGatewayV2` with `order.user` set to a malicious contract `Evil` (so `body.beneficiary` in the eventual `WithdrawalRequest` resolves to `Evil`), and native token (`token == address(0)`) as an input asset.
2. The order is cancelled/refunded or filled normally, causing the host to deliver a `RedeemEscrow`/`RefundEscrow` message to `onAccept`, which calls `withdraw(body, ...)`.
3. Inside `withdraw()`, `_orders[commitment][token]` is still non-zero when `beneficiary.call{value: amount}("")` executes (line 694), transferring control to `Evil.receive()`.
4. `Evil.receive()` re-enters the gateway contract (e.g. re-invoking `onGetResponse`/`onAccept` for the same commitment if the host layer allows re-entrant delivery within the same call, or any other function reading `_orders[commitment][token]` before the pending decrement at line 701 has executed), causing the non-zero check to pass again and a second native transfer to be issued for the same escrow entry.
5. Only after both re-entrant calls unwind does `_orders[body.commitment][token] -= amount` finally apply, at which point more native token has already left the contract than was ever escrowed for that commitment.
