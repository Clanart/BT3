### Title
Permissionless, unrestricted `CallDispatcher.dispatch()` allows any caller to hijack in-flight assets routed through the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The external report's root cause is a public function that performs `target.call(attackerControlledCalldata)` with no allowlist of contracts/selectors, letting anyone move assets that pass through the vulnerable contract. Hyperbridge's `CallDispatcher` is architecturally the same primitive: a single, shared, standalone contract with a fully public `dispatch(bytes)` function and zero access control, zero allowlist of `to`/selector, used by `IntentGatewayV2` (predispatch/postdispatch order calldata) and `WrappedHyperFungibleToken`/HFT (post-bridge calldata execution) to route real ERC-20 balances and native ETH.

### Finding Description
`CallDispatcher.dispatch()` decodes an attacker-suppliable `Call[]` and executes `to.call{value: call.value}(call.data)` for every entry, with the only check being that `to` has code: [1](#0-0) 

The contract is explicitly documented as dispatching "untrusted call(s)" and has no `onlyOwner`/`onlyGateway` modifier, and it also accepts arbitrary ETH via a bare `receive()`: [2](#0-1) 

It is used as a shared execution sink across multiple products: `IntentGatewayV2` sends escrowed/output tokens through it for pre- and post-fill calldata execution (`IntentsBase._execute`), and `WrappedHyperFungibleToken` delivers bridged tokens/ETH directly to the dispatcher address (`to = CALL_DISPATCHER`) before invoking `dispatch(message.data)`: [3](#0-2) [4](#0-3) 

Because `dispatch()` imposes no restriction on `to` or `data`, and the contract is reused across every order/message that carries calldata, **any balance the dispatcher is holding at the moment it is called — including balances left over from a partially-swept batch, rounding dust, or tokens delivered to it as an intermediate hop by one app while another app's flow is mid-execution — can be redirected by any third party** simply by calling `dispatch()` themselves with a `Call` that transfers that balance to an attacker-chosen address. The existing "sweep" logic in `IntentsBase._execute` only sweeps balances for the specific `order.output.assets` token list of the order that just ran; it has no knowledge of, and does not protect, balances belonging to other concurrent or partially-failed calldata executions routed through the same shared dispatcher instance: [5](#0-4) 

This is exactly the missing-allowlist pattern flagged in the external report (`callTakerTokenAndFillOrder`): a public function that performs `.call()` to attacker-specified targets/calldata with no per-contract/per-selector permission mapping, operating on a contract designed to transiently hold real funds.

### Impact Explanation
Any ERC-20 or native-ETH balance sitting in the shared `CallDispatcher` outside the exact atomic transaction that placed it there is unauthorized-execution-reachable and can be stolen by an unprivileged attacker, since `dispatch()` has no caller restriction and no allowlist of destination contracts or function selectors. This matches the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories, because value routed through the dispatcher for legitimate order/bridge calldata execution is exposed to redirection by anyone.

### Likelihood Explanation
Exploitability depends on a window where the dispatcher holds a balance that is not swept/consumed within the same atomic call that deposited it (e.g., a partial sweep failure, rounding dust from token transfers, or overlapping usage by multiple apps sharing one dispatcher deployment). Within the reviewed `IntentGatewayV2` and `WrappedHyperFungibleToken` flows, deposit-then-dispatch-then-sweep normally happens atomically in one transaction, which reduces — but given the complete absence of access control on `dispatch()`, does not eliminate — the risk that any residual balance (dust, failed sweep, or a shared dispatcher instance reused by another app) becomes instantly and permanently drainable by a third party.

### Recommendation
Add an allowlist mechanism to `CallDispatcher` (as recommended in the original report) mapping `(caller, target, selector) => bool`, restrict `dispatch()` to be callable only by the registered gateway/app contracts (`onlyAuthorizedCaller`), and ensure the dispatcher never has a standing balance between transactions — either by enforcing a strict "sweep-or-revert" invariant at the end of every `dispatch()` call, or by deploying a fresh, single-use dispatcher instance per calldata execution instead of a long-lived shared singleton.

### Proof of Concept
1. Deploy/observe the shared `CallDispatcher` address configured in `Params.dispatcher` for `IntentGatewayV2` (and/or shared with `WrappedHyperFungibleToken`).
2. Identify a transaction where the dispatcher ends up holding a non-zero token/ETH balance that is not fully consumed by its own sweep logic in the same call (e.g., a token whose `transfer` in the sweep loop reverts or under-transfers due to fee-on-transfer behavior, leaving dust; or a cross-app scenario where two flows briefly overlap on the same dispatcher instance).
3. As an unprivileged attacker, call `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly — this succeeds because `dispatch()` has no caller check, per [1](#0-0) .
4. The attacker receives the dispatcher's balance, which belonged to an in-flight order/beneficiary, not the attacker.

Note: full confirmation that a persistent-balance window actually occurs in production configurations (e.g., whether `Params.dispatcher` is ever shared across multiple concurrently-active apps, or whether any sweep path can legitimately leave dust) requires deeper runtime/deployment inspection than the indexed code allows; a Devin session with full repo/deployment access is recommended to verify concrete triggering conditions before treating this as fully weaponized.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
