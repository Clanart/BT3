### Title
Unsigned Fee Cast on Unvalidated Coin Amount Difference Can Raise an Unhandled Exception - (File: chia/full_node/mempool_manager.py)

### Summary
`MempoolManager.validate_spend_bundle` computes the transaction fee as `fees = uint64(removal_amount - addition_amount)` without first verifying that `removal_amount >= addition_amount` [1](#0-0) . This mirrors the reported bug class: an operation whose mathematical result can be negative is fed directly into an unsigned integer type without a prior sign check, which is exactly the pattern flagged in the source report (`uint256 priceChange` from a subtraction that can be negative).

### Finding Description
`addition_amount` is accumulated from the `CREATE_COIN` outputs declared in the spend bundle's conditions, and `removal_amount` is accumulated from the actual coin records being spent [2](#0-1) [3](#0-2) . Nothing in `validate_spend_bundle` checks that `addition_amount <= removal_amount` before computing `fees`. In the equivalent consensus-level check performed on full blocks, this exact comparison is explicitly guarded: `if removed < added: return Err.MINTING_COIN` before the `fees = removed - added` subtraction [4](#0-3) . That guard is present at block-validation time but is absent from the mempool admission path in `mempool_manager.py`, where the difference is passed straight into `uint64()`.

`chia_rs` sized integers reject negative values by raising `OverflowError` rather than silently wrapping (`Coin(H1, H2, -1)` raises `OverflowError: can't convert negative int to unsigned`) [5](#0-4) . Consequently, a spend bundle that creates coins whose total value exceeds the value of the coins it spends (a "minting" spend bundle, which is easy for an unprivileged submitter to construct — no signature check prevents specifying arbitrary `CREATE_COIN` amounts) will cause `uint64(removal_amount - addition_amount)` to raise an unhandled `OverflowError` at line 814, instead of returning a clean `Err` code the way the equivalent block-level path does.

The same unguarded pattern (`uint64(removals_amount - additions_amount)`) also appears in the test helper `make_bundle_spends_map_and_fee`, showing that fee computation from raw sums without a prior comparison is a repeated pattern in this codebase, not an isolated one-off [6](#0-5) .

### Impact Explanation
`respond_transaction` in the full node API only catches `ValidationError` around `add_transaction` [7](#0-6) ; an `OverflowError` raised deep inside `validate_spend_bundle` is not a `ValidationError` and would propagate unhandled. This matches the allowed impact category of a "spend-triggered transaction-processing halt": a single unprivileged spend-bundle submitter can trigger an unhandled exception in the transaction-validation pipeline by crafting a spend bundle whose declared `CREATE_COIN` outputs exceed its input coin value.

### Likelihood Explanation
High reachability: any wallet user or RPC/network peer can submit a `SpendBundle` with a `CREATE_COIN` condition whose amount is larger than the coin being spent — CLVM puzzle execution does not itself forbid declaring such a condition; it is the mempool/consensus layer's job to reject it via a `MINTING_COIN`-style check, which is present at the block level but missing at this mempool admission call site.

### Recommendation
Add the same guard used in `block_body_validation.py` before the fee subtraction in `mempool_manager.py`: compare `addition_amount` to `removal_amount` and return a defined `Err` (e.g., `Err.MINTING_COIN`) if `addition_amount > removal_amount`, instead of relying on the unsigned cast to fail. Apply the same fix to the `make_bundle_spends_map_and_fee` test helper pattern to prevent future regressions.

### Proof of Concept
I was unable to fully trace whether the asynchronous `transaction_queue` worker that ultimately calls `add_transaction`/`validate_spend_bundle` (enqueued from `respond_transaction`, see `full_node_api.py` lines 402-410) has any broader exception guard around the whole processing loop, so I cannot state with certainty whether this crashes the specific worker task or is silently swallowed at a higher level — this would need to be confirmed by tracing `full_node.transaction_queue`'s consumer loop, which was not fully covered by the available index. The concrete reachable defect — an unguarded subtraction of unsigned coin-amount sums fed into `uint64()` without the `MINTING_COIN`-style check present elsewhere in the codebase — is confirmed at [1](#0-0) .
