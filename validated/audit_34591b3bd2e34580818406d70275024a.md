### Title
Ed25519 precompile CU cost is flat per-instruction regardless of `num_signatures`, permitting cheap amplification of `ed25519_dalek::PublicKey::verify_strict` calls - ([File: precompiles/src/ed25519.rs])

### Summary
`agave_precompiles::ed25519::verify` loops over `num_signatures` (attacker-controlled `u8`, up to 255) and performs one `ed25519_dalek::PublicKey::verify_strict` per iteration, with offsets that can all alias the same small signature/pubkey/message bytes. This work is charged through the flat, non-CU-metered builtin instruction cost model rather than a per-signature cost, so the number of elliptic-curve verifications an attacker can force per unit of charged cost is not linearly bounded.

### Finding Description
`verify()` reads `num_signatures = data[0]` and iterates `0..num_signatures`, parsing an `Ed25519SignatureOffsets` per iteration and calling `get_data_slice` to fetch signature/pubkey/message bytes, then `publickey.verify_strict(message, &signature)` [1](#0-0) . Because `signature_instruction_index`/`public_key_instruction_index`/`message_instruction_index` can all be set to `u16::MAX` (meaning "use this instruction's own data"), a single small instruction can define one signature/pubkey/message triple and have all `num_signatures` offset entries point at that same triple, minimizing instruction-data size while maximizing verification count.

This verification runs outside the sBPF VM's per-syscall compute metering: `InvokeContext::process_precompile` simply calls the `epoch_stake_callback.process_precompile` callback directly, with no `compute_meter.consume_checked` calls surrounding the `ed25519_dalek` work [2](#0-1) . `Bank::process_precompile` dispatches straight into `precompile.verify(...)` [3](#0-2) .

Instead, precompile instructions are priced through the flat builtin-instruction cost table (`BUILTIN_INSTRUCTION_COSTS`), which is not permitted to vary by instruction data (`DEVELOPER WARNING: this map CANNOT be modified without causing a consensus failure`) [4](#0-3) . The `core/tests/scheduler_cost_adjustment.rs::test_builtin_ix_precompiled` test explicitly documents this behavior: "VM Execution: consume 0 from CU-meter" and the cost/compute allocation is the constant `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` (3000 CU) regardless of the precompile instruction's contents [5](#0-4) . Nothing in `verify()` or the cost model scales the charge with `num_signatures`.

Fee accounting (`calculate_signature_fee` in `fee/src/lib.rs`) does add `lamports_per_signature` per counted ed25519 signature to the transaction *fee*, but this is a lamport fee, not a compute-unit/cost-model charge that bounds per-block/per-slot CPU-time budgeting via the cost tracker [6](#0-5) . The cost model (`cost-model/src/cost_model.rs`) uses `programs_execution_cost` derived from the same flat builtin cost table for precompiles, so the block-cost-limit enforcement also does not scale with `num_signatures`.

### Impact Explanation
An attacker can craft a single ed25519-program instruction with `num_signatures` up to 255, all offsets aliasing one small signature/pubkey/message, causing every validator that processes the transaction (during both `check_transactions`/verification and bank execution) to perform up to 255 `ed25519_dalek::PublicKey::verify_strict` calls while being charged only the flat builtin cost (3000 CU) that a single-signature instruction would incur. This is a materially underpriced-compute condition: real CPU cost scales with `num_signatures`, but the cost-model/compute-budget charge does not, allowing a validator to be forced to perform disproportionate elliptic-curve verification work relative to the compute units billed and accounted against block cost limits. This falls into Agave's "compute unit/cost model underpricing leading to CPU DoS" bounty category.

### Likelihood Explanation
This requires no special privilege — any unprivileged user can submit a normal transaction containing a single ed25519-program instruction; the instruction data needed is small (roughly `2 + 255*14 + 64 + 32 + msg_len` bytes ≈ 3.7KB for 255 signatures aliasing one message), which must still fit under the transaction/packet size limit; the number of realizable duplicated verifications per instruction is bounded by that packet size (in practice much less than 255, since packet size (1232 bytes) limits `num_signatures` to roughly ~85 given the 14-byte offset struct plus header/sig/pubkey/message overhead), but the disproportion between charged flat cost (3000 CU) and real work (tens of elliptic-curve verifications) is real and repeatable in every transaction, at zero marginal cost increase per added signature within a single instruction. No account writes, no validator/leader control, and no external dependency/interpreter bug are required — this is a self-contained repeat-per-transaction primitive.

### Recommendation
Charge compute/cost proportional to `num_signatures` (and message length) for precompile instructions instead of (or in addition to) the flat builtin-instruction cost, e.g., add a per-signature cost component to the cost model / compute-budget accounting keyed off `get_num_signatures_in_instruction`-style parsing of precompile instruction data (already computed in `runtime-transaction/src/signature_details.rs` for fee purposes) so that both the fee and the CU/cost-tracker budget scale with the number of verifications actually performed.

```rust
// precompiles/src/ed25519.rs (integration-style bench/test)
use {
    agave_feature_set::FeatureSet,
    ed25519_dalek::{Signer, Keypair, SecretKey},
    solana_ed25519_program::{Ed25519SignatureOffsets, SIGNATURE_OFFSETS_START,
        SIGNATURE_OFFSETS_SERIALIZED_SIZE, SIGNATURE_SERIALIZED_SIZE, PUBKEY_SERIALIZED_SIZE},
    agave_precompiles::ed25519::verify,
    std::time::Instant,
};

fn build_max_amplification_ix(num_signatures: u8) -> Vec<u8> {
    // Build ONE message+sig+pubkey blob, then repeat offsets `num_signatures` times
    // all pointing at the same bytes (instruction_index = u16::MAX).
    let secret = SecretKey::from_bytes(&[7u8; 32]).unwrap();
    let public = (&secret).into();
    let keypair = Keypair { secret, public };
    let message = b"x";
    let signature = keypair.sign(message).to_bytes();
    let pubkey = keypair.public.to_bytes();

    let data_start = SIGNATURE_OFFSETS_START
        + (num_signatures as usize) * SIGNATURE_OFFSETS_SERIALIZED_SIZE;
    let pubkey_offset = data_start;
    let sig_offset = pubkey_offset + PUBKEY_SERIALIZED_SIZE;
    let msg_offset = sig_offset + SIGNATURE_SERIALIZED_SIZE;

    let mut data = vec![0u8; data_start];
    data[0] = num_signatures; // up to 255

    let offsets = Ed25519SignatureOffsets {
        signature_offset: sig_offset as u16,
        signature_instruction_index: u16::MAX,
        public_key_offset: pubkey_offset as u16,
        public_key_instruction_index: u16::MAX,
        message_data_offset: msg_offset as u16,
        message_data_size: message.len() as u16,
        message_instruction_index: u16::MAX,
    };
    let offsets_bytes = bytemuck::bytes_of(&offsets);
    for i in 0..num_signatures as usize {
        let start = SIGNATURE_OFFSETS_START + i * SIGNATURE_OFFSETS_SERIALIZED_SIZE;
        data[start..start + SIGNATURE_OFFSETS_SERIALIZED_SIZE].copy_from_slice(offsets_bytes);
    }
    data.extend_from_slice(&pubkey);
    data.extend_from_slice(&signature);
    data.extend_from_slice(message);
    data
}

#[test]
fn test_ed25519_cost_disproportion() {
    let feature_set = FeatureSet::all_enabled();

    // Baseline: 1 signature.
    let data1 = build_max_amplification_ix(1);
    let t0 = Instant::now();
    verify(&data1, &[&data1], &feature_set).unwrap();
    let cost1 = t0.elapsed();

    // Attacker: max signatures achievable within packet-size bound (e.g. 80).
    let n = 80u8;
    let data_n = build_max_amplification_ix(n);
    let t1 = Instant::now();
    verify(&data_n, &[&data_n], &feature_set).unwrap();
    let cost_n = t1.elapsed();

    // Both instructions are billed the SAME flat builtin cost
    // (MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT), per
    // core/tests/scheduler_cost_adjustment.rs::test_builtin_ix_precompiled,
    // yet wall-clock verification cost scales ~linearly with `n`.
    assert!(
        cost_n.as_nanos() > cost1.as_nanos() * (n as u128) / 2,
        "expected near-linear scaling of real verification cost with num_signatures \
         while charged compute cost stays flat: cost1={:?} cost_n={:?}",
        cost1, cost_n
    );
}
```
Expected result: wall-clock cost scales approximately linearly with `num_signatures` while the compute/cost-model charge (as asserted in `test_builtin_ix_precompiled`) remains the constant `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT`, confirming the cost/real-work mismatch.

```rust
/// Calculate fees from signatures.
pub fn calculate_signature_fee(
    SignatureCounts {
        num_transaction_signatures,
        num_ed25519_signatures,
        num_secp256k1_signatures,
        num_secp256r1_signatures,
    }: SignatureCounts,
    lamports_per_signature: u64,
) -> u64 {
    let signature_count = num_transaction_signatures
        .saturating_add(num_ed25519_signatures)
        .saturating_add(num_secp256k1_signatures)
        .saturating_add(num_secp256r1_signatures);
    signature_count.saturating_mul(lamports_per_signature)
}
```
