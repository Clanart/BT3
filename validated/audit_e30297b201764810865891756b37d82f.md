### Title
Out-of-bounds read (unhandled `IndexError`) when parsing attacker-controlled CLVM solution bytes for canonical-encoding checks - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_clvm_canonical()` / `is_atom_canonical()` in `chia/full_node/mempool_manager.py` parse the raw CLVM byte encoding of a coin-spend solution to decide whether a mempool item is eligible for spend dedup. Both functions index directly into the caller-supplied `bytes` buffer while walking length-prefix fields, with no bounds check against `len(clvm_buffer)`. A spend bundle whose solution bytes contain a truncated/overrun atom-length prefix causes an out-of-bounds `bytes` index access and an unhandled `IndexError`, mirroring the ClamAV OLE2 bug class of trusting an attacker-supplied length field without validating it against the actual buffer size.

### Finding Description
`is_atom_canonical()` reads the length-prefix byte(s) that follow the current offset without ever checking that `offset` stays within `len(clvm_buffer)`: [1](#0-0) 

`is_clvm_canonical()` drives the same unchecked walk at the top level: after consuming an atom it advances `offset` by the just-computed `atom_len` (itself derived from attacker-controlled prefix bytes) and immediately re-indexes `clvm_buffer[offset]` on the next loop iteration, with no check that the new offset is still inside the buffer: [2](#0-1) 

Both functions are documented as parsing solution bytes to determine DEDUP eligibility for spends admitted from externally submitted spend bundles: [3](#0-2) 

Because the length-prefix value (`atom_len`) and the number of prefix-extension bytes read are taken directly from the untrusted buffer, an attacker can supply:
- a final byte that declares a multi-byte length prefix but provides fewer trailing bytes than required (triggers OOB read inside the `for i in range(prefix_len)` loop of `is_atom_canonical`), or
- an atom whose declared `atom_len` causes `offset` to jump past `len(clvm_buffer)`, so the very next `b = clvm_buffer[offset]` in `is_clvm_canonical`'s loop raises `IndexError`.

This is analogous to the ALPINE-CVE-2019-1788 pattern: parsing a length/record field from an untrusted binary blob and using it to index into the buffer without validating it stays within the buffer's actual bounds, leading to an out-of-bounds access and a crash/DoS condition rather than graceful rejection.

### Impact Explanation
An unhandled `IndexError` in the code path that inspects a submitted spend bundle's solution bytes turns a single malformed (but otherwise unauthenticated/unsigned-check-independent) spend into a transaction-processing exception instead of a clean `Err` rejection. Because this logic executes during mempool admission for every candidate spend eligible for dedup consideration, a single crafted spend bundle can raise an uncaught Python exception on the code path responsible for admitting transactions, which is a spend-triggered halt/crash of that processing path rather than a normal validation-error rejection. This matches the "spend-triggered transaction-processing halt" class explicitly called out as in-scope.

### Likelihood Explanation
The bug is reachable by any unprivileged actor who can submit a spend bundle to a node's mempool (wallet RPC caller, peer relaying a transaction, or any spend-bundle submitter). No signature bypass or special permission is needed — only a solution program whose serialized bytes end with a truncated/overrunning atom-length prefix, which is trivial to construct. The main uncertainty (not fully verifiable with available tooling) is the exact call site and whether an outer `try/except` wraps this specific check before it reaches this code, which would determine whether the crash is contained to a single item or propagates further; I could not conclusively trace the calling function's exception-handling within the available iterations.

### Recommendation
Add explicit bounds checks in both `is_atom_canonical()` and `is_clvm_canonical()` before every indexing operation (e.g., `if offset >= len(clvm_buffer): return ...append a non-canonical/invalid result...` rather than raising), and ensure any exception from this canonicalization check is caught and translated into a mempool rejection (`Err`) rather than allowed to propagate as an unhandled exception during spend-bundle processing.

### Proof of Concept
Directly exercising the vulnerable function with a truncated multi-byte length prefix triggers an out-of-bounds `IndexError`:

```python
from chia.full_node.mempool_manager import is_atom_canonical

# 0xC0 signals a "5+8 bits length prefix" atom (prefix_len = 1 extra byte expected),
# but the buffer contains no further bytes.
buf = bytes([0xC0])
is_atom_canonical(buf, 0)  # raises IndexError: index out of range
```

Embedding such a truncated atom as the tail of a coin spend's solution bytes and submitting the resulting `SpendBundle` causes `is_clvm_canonical()` (invoked while evaluating dedup eligibility for that spend during mempool admission) to raise the same unhandled `IndexError` when it reaches the malformed atom, instead of returning `False`/rejecting the spend cleanly.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```

## Canonical serialization

**Location**: `mempool_manager.py:185`

### `is_clvm_canonical(clvm_buffer)`

Checks that a CLVM program uses shortest-form atom encoding:

- No unnecessary length prefix bytes
- No back-references (`0xFE` byte)
- No trailing garbage

### When enforced

Required for DEDUP-eligible spends. Without canonical form, identical
solutions could have different serializations, breaking dedup.

### `is_atom_canonical(clvm_buffer, offset)`

Validates a single atom's length prefix encoding. The CLVM format uses
variable-length prefixes (1-6 bytes) based on atom size. Each prefix
length has a minimum atom size threshold.
