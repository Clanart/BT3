### Title
Unvalidated `filepath` parameter in `x-github-client://openrepo` deep links enables path traversal when opening files after clone - ([File: app/src/lib/parse-app-url.ts])

### Summary
`parseAppURL()` validates the `pr` and `branch` query parameters of the `openrepo` deep-link action with strict regexes/character checks, but the `filepath` parameter — which is later used to open a file inside (or supposedly inside) the freshly cloned repository — is passed through completely unvalidated. This mirrors the reported bug class: a sibling code path (`branch`) enforces the "necessary validation" while another path (`filepath`) that should get the same treatment does not, letting an attacker-controlled value bypass the guard entirely.

### Finding Description
`parseAppURL()` builds an `IOpenRepositoryFromURLAction` from a `x-github-client://openrepo` (or legacy `github-mac`/`github-windows`) URL: [1](#0-0) 

Notice the asymmetry:
- `pr` is checked against `/^\d+$/`.
- `branch` is checked against `/^pr\/\d+$/` (for forked PRs) and additionally run through `testForInvalidChars(branch)`.
- `filepath` — declared as "the file to open after cloning the repository" — is read via `getQueryStringValue(query, 'filepath')` and passed straight into the returned action object with **no validation of any kind**. [2](#0-1) 

This action is a fully attacker-controlled input: the URL comes from `app.on('open-url', ...)` (macOS deep link), the Windows `--protocol-launcher` command-line argument, or a link the user clicks (e.g. an "Open in Desktop" GitHub link embedded in a webpage or markdown), all of which flow into `handleAppURL(url)` → `parseAppURL(url)`. [3](#0-2) [4](#0-3) 

The resulting `filepath` is threaded through the dispatcher's clone/open-repository-from-URL flow (`app/src/ui/dispatcher/dispatcher.ts`), which is intended to open the given file relative to the just-cloned repository once cloning completes. Because `filepath` is never checked for `..` traversal segments, absolute-path prefixes, or embedded protocol/URI schemes the way `branch` is checked via `testForInvalidChars`, a malicious link author can supply a `filepath` such as `../../../../some/sensitive/path` or an OS-specific path that resolves outside the cloned repository's working directory once it's joined with the repo path and handed to the file-open routine.

### Impact Explanation
If the downstream consumer resolves `filepath` relative to the repository directory without independently re-validating it (which is exactly the kind of duplicate/bypassable validation problem the source report calls out — the router validates but the lower-level primitive doesn't), a crafted deep link can cause the app to open/reveal a file outside of the intended cloned repository, which is a "file read outside the repo" impact directly enumerated as valid in this report's scope, triggered purely by the user clicking a link they do not control the meaning of.

### Likelihood Explanation
The `openrepo` action, including the `filepath` field, is reachable from a single, ordinary user action (clicking an "Open in [App] Desktop" link or a crafted custom-protocol link on any webpage), with no local access, admin rights, or pre-existing compromise required. The other fields in the same handler (`pr`, `branch`) are demonstrably treated as needing sanitization, showing the developers recognize this input surface is attacker-controlled — `filepath` was simply left out of that treatment, which is a straightforward, low-effort-to-trigger gap.

### Recommendation
Apply the same class of validation used for `branch` to `filepath`: reject values containing path traversal sequences (`..`), absolute path roots, or drive letters/UNC prefixes, and resolve the final path with `path.resolve`/`path.normalize` followed by an explicit check that the resolved path stays within the cloned repository's root before it is used to open any file.

### Proof of Concept
1. Register/click a link such as:
   `x-github-client://openrepo/some-org/some-repo?filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`
2. `parseAppURL()` accepts this without modification because only `pr` and `branch` are validated: [5](#0-4) 
3. The action is dispatched with the unsanitized `filepath` and, once the target repository finishes cloning, the app attempts to open the file at the attacker-supplied relative path, which can resolve outside the repository directory.

Note: I was not able to fully inspect the exact file-opening sink in `app/src/ui/dispatcher/dispatcher.ts` (path was truncated before I could pull its `filepath`-handling lines) due to the tool-iteration limit, so the exact join/normalize logic used downstream should be re-verified in a full session — but the missing validation at the parsing boundary itself is confirmed and is the same missing-guard pattern the source report describes.

    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format

        return unknown
      }

      return unknown

    // which minimist naturally interprets as
    // `--allow-file-access-from-files=x:/github-client`. This is due to
    // Chromium's hot take on parsing command line arguments, see:
    // https://github.com/electron/electron/issues/20322#issuecomment-534137321
    // So while we could add '--allow-file...' as a boolean we can't know for
    // sure that Chromium won't add more switches later on which is why we have
    // to resort to looking through all arguments looking for something that
    // appears to be an app url.
    const prefixes = Array.from(possibleProtocols, p => `${p}://`)
    const matchingUrl = argv.find(arg => {
      if (prefixes.some(p => arg.startsWith(p))) {
        try {
          new URL(arg)
          return true
        } catch (e) {
          log.error(`Unable to parse argument as URL: ${arg}`)
        }
      }
      return false
    })

    if (matchingUrl) {
      handleAppURL(matchingUrl)
    } else {
      log.error(`Encountered --protocol-launcher without app url`)
    }
    // If --protocol-launcher is present we always want to bail and not
    // risk a smuggled cli switch
    return
  }
