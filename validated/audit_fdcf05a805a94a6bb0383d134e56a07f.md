### Title
Inconsistent Fee-on-Transfer/Deflationary LP Token Accounting in `WombatStaking.depositLP()` - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.deposit()` correctly measures actual received LP tokens via before/after balance checks before minting receipt tokens, but the sibling function `WombatStaking.depositLP()` skips this check entirely and mints receipt tokens (and forwards accounting) based on the caller-supplied `_lpAmount` parameter rather than the tokens actually received.

### Finding Description
In `WombatStaking.deposit()`, the actual LP tokens received from the underlying Wombat pool are measured with a before/after balance diff (`lpReceived`), and that measured value — not the requested amount — is used to mint receipt tokens and update accounting: [1](#0-0) 

By contrast, `depositLP()` transfers the LP token directly from the user via `safeTransferFrom`, but immediately uses the caller-supplied `_lpAmount` (not an actual-balance-received check) both to stake into master wombat via `_toMasterWomAndSendReward` and to mint receipt tokens: [2](#0-1) 

If `poolInfo.lpAddress` behaves as a fee-on-transfer/deflationary token (or any token whose `transferFrom` does not deliver the full nominal amount), `WombatStaking` will custody strictly less LP than `_lpAmount`, yet it mints `_lpAmount` worth of receipt tokens to the caller via `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)`. This receipt token is then staked 1:1 in `MasterMagpie` through the pool helper's `depositLP`, which itself only checks the receipt-token balance delta (which is unaffected, since the receipt token itself is not deflationary) rather than validating it against real LP custody: [3](#0-2) 

This exactly mirrors the reported bug class: the team implemented the before/after balance-diff mitigation in one code path (`deposit`) but failed to apply it consistently to another code path (`depositLP`) handling the same asset type, producing over-minted receipt tokens relative to the LP tokens actually custodied by the contract.

### Impact Explanation
Over-minting receipt tokens against under-collateralized LP custody creates a permanent shortfall: the sum of receipt tokens (and downstream MGP-pool shares) outstanding exceeds the actual LP token balance held by `WombatStaking`. When later users attempt `withdraw()`, `WombatStaking` will not have sufficient LP tokens to service all receipt-token holders, resulting in insolvency of the pool and permanent freezing/loss of some users' funds. This is not limited to the depositor of the deflationary token — it degrades the shared LP-token pool used by all receipt-token holders for that pool.

### Likelihood Explanation
Reachable by any ordinary wallet: `depositLP()` is a public, unprivileged, permissionless entry point on `WombatStaking`, invoked indirectly through `WombatPoolHelper.depositLP()` / `WombatPoolHelperV2.depositLP()`, both of which are open to any user. The pool's `lpAddress` and `depositToken` addresses are chosen at pool-registration time by governance/owner (`registerPool`), so likelihood depends on whether a fee-on-transfer/deflationary asset (or its LP wrapper) is ever onboarded — the same precondition acknowledged as realistic in the original Rubicon Finance report, and the codebase itself demonstrates awareness of this class of bug by mitigating it in `deposit()` but not in `depositLP()`.

### Recommendation
Apply the same before/after balance-diff pattern already used in `deposit()` to `depositLP()`: measure `poolInfo.lpAddress` balance before and after `safeTransferFrom`, and use the measured delta (not the caller-supplied `_lpAmount`) for both `_toMasterWomAndSendReward` and the receipt-token `mint` call.

### Proof of Concept
1. Governance registers a pool where `lpAddress` is (or becomes) a fee-on-transfer token that deducts, e.g., 5% on transfer.
2. User calls `WombatPoolHelper.depositLP(100)`, which calls `WombatStaking.depositLP(lpToken, 100, user)`.
3. Inside `depositLP`, `safeTransferFrom(_for, address(this), 100)` results in `WombatStaking` receiving only 95 LP tokens due to the transfer fee, per `wombat/WombatStaking.sol` lines 272-287.
4. `_toMasterWomAndSendReward(_lpAddress, 100, true)` and `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, 100)` proceed using the full 100 amount, not the actual 95 received.
5. The receipt-token supply now represents 100 LP-equivalent units while `WombatStaking` custodies only 95 real LP tokens — a 5-unit shortfall that compounds with every such deposit, eventually preventing full withdrawal by legitimate receipt-token holders.
