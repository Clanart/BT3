### Title
Quadratic Lagrange interpolation in `ThresholdKeys::new`/`view` enables CPU-exhaustion DoS from attacker-supplied serialized keys - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts an attacker-controlled `n` (u16, up to 65535) with no cap, then `ThresholdKeys::new` computes `group_key` by evaluating `interpolation_factor` for each of `t` participants — and each `Interpolation::Lagrange` factor evaluation is itself O(t) field multiplications plus an inversion. This makes key deserialization O(t²) ≈ 4.3×10⁹ scalar multiplications for a ~4 MB input, a severe asymmetric CPU-DoS analog of the unbounded-work-on-untrusted-bytes class in the python-zeroconf report.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the byte stream (`crypto/dkg/src/lib.rs:591-602`), reads `n` verification-share points (`crypto/dkg/src/lib.rs:620-623`), then calls `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:625`). Inside `new`, the group key is derived as `t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum()` where `t = 1..=params.t()` (`crypto/dkg/src/lib.rs:376-378`). For `Interpolation::Lagrange`, `interpolation_factor` loops over every element of `included`, performing a scalar multiply and accumulating a denominator per element, then inverts (`crypto/dkg/src/lib.rs:229-247`). The same quadratic pattern is reachable again via `ThresholdKeys::view`, which calls `interpolation_factor` once per included participant (`crypto/dkg/src/lib.rs:500-507`), and is invoked from `AlgorithmSignMachine::sign` on the attacker-influenced `included` set (`crypto/frost/src/sign.rs:312`).

There is no bound check on `n` beyond `t <= n <= 65535`. A single crafted serialization with `t = n = 65535`, `Interpolation::Lagrange`, and ~65k encoded points (a few MB) forces ~4.3×10⁹ `C::F` multiplications and 65535 inversions inside `new` alone — before any signature work even begins — and any subsequent `view()` call repeats the quadratic cost. The caller is only reading bytes; the attacker pays linear bandwidth while the victim pays quadratic CPU.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (the explicitly in-scope deserialization sink) can stall a validator/processor for an effectively unbounded duration with a single small message — starving the event loop and preventing all other signing/DKG work, mirroring the scheduler-starvation impact in the original advisory. Memory is also linearly consumed (~65k `C::G`/`C::F` heap objects per call) with no cap. In a consensus context this can halt threshold signing and liveness-dependent operations. Additionally, the same path permits `n` up to 65535 while `Participant` is u16-indexed, so nothing distinguishes a legitimate 150-validator set from a malicious 65535-participant blob.

### Likelihood Explanation
The cost is fully deterministic and triggered purely by input bytes — no secret, no race, no collusion required. The only requirement is a code path that deserializes `ThresholdKeys` from data an attacker can influence (backups, replicated state, message payloads). CPU exhaustion of this magnitude is reliably reproducible; even `n = 4096` yields ~16.7M multiplications plus 4096 field inversions per `read`/`view`, enough to cause noticeable stalls at message-rate volume.

### Recommendation
Enforce a sane maximum on `t`/`n` in `ThresholdParams::new`/`ThresholdKeys::read` (e.g., the protocol's actual maximum validator-set size) before any allocation or interpolation work. Reject serializations whose declared `n` exceeds the expected set size. Alternatively, precompute Lagrange denominators via the standard O(n) prefix/suffix product trick rather than O(n²) per-participant evaluation, so deserialization cost is linear in input size.
