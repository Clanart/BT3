### Title
Concurrent Map Write Panic in Gasless Module's `knownTxs` Due to Inconsistent Mutex Usage - (File: `kaiax/gasless/impl/tx_pool.go`)

### Summary
The `GaslessModule` maintains a shared, map-backed tracking structure `knownTxs` (implemented in `kaiax/gasless/impl/tx_counter.go`) that is guarded by `g.knownTxsMu sync.RWMutex`. Two different code paths access this shared state with inconsistent lock strength: one path takes only a read lock (`RLock`) while still performing a mutation, and another correctly takes a write lock (`Lock`) before mutating. This mismatch mirrors exactly the "read/write paths guarded inconsistently" bug class described in the reference advisory (GHSA-f5p9-j34q-pwcc), and can lead to a `fatal error: concurrent map writes` panic that crashes the Kaia node process.

### Finding Description
`PreAddTx` is the per-transaction admission hook invoked whenever a transaction (including from an unprivileged RPC caller / remote sender) is submitted to the pool: [1](#0-0) 

It acquires only `g.knownTxsMu.RLock()` — a *read* lock, which multiple goroutines may hold simultaneously — and then, if the tx is a bundle tx, calls `g.knownTxs.add(tx, TxStatusQueue)`, which mutates the underlying `knownTxs` map/structure.

By contrast, the promotion path `IsReady`, which mutates the exact same structure via the same `add` method, correctly takes the *write* lock: [2](#0-1) 

Because `PreAddTx` only takes `RLock`, two or more goroutines processing different incoming transactions concurrently (e.g., multiple RPC `eth_sendRawTransaction` / `SendRawTransaction` calls handled by concurrent TxPool `AddRemote`/`AddRemotes` invocations) can simultaneously enter `PreAddTx`, both pass the `RLock` gate concurrently, and both call `g.knownTxs.add(...)` at the same time — an unsynchronized concurrent write into the shared map. This is the identical class of "mixed access pattern (iteration/mutation without a single lock policy)" flagged in the external advisory for emp3r0r's `OPERATORS`/`PortFwds`/`FTPStreams` maps.

### Impact Explanation
A concurrent write can trigger the Go runtime's built-in map-corruption detector, panicking with `fatal error: concurrent map writes`, which is unrecoverable and crashes the entire Kaia node process (both `PreAddTx`/tx-admission goroutines and the whole node, since Go map-corruption panics are process-fatal, not recoverable via `recover()`). Since the gasless module's `PreAddTx` hook runs on every transaction pool admission for bundle-eligible transactions, and public-facing RPC entry points allow unauthenticated remote submission of many transactions concurrently, this is reachable by any transaction sender able to submit multiple bundle-shaped transactions in parallel. A crashed node stops processing transactions, producing a denial-of-service condition, consistent with the CVSS profile of the reference advisory (`VA:H`, availability impact, no confidentiality/integrity impact).

### Likelihood Explanation
Triggering the race only requires two or more approve/swap ("bundle") transactions to be submitted concurrently to the same node's TxPool from different senders (or via pipelined RPC connections), which any public RPC caller can do without special privileges, staking, or governance access. No malicious peer, validator, or node compromise is required — a single external actor submitting a burst of gasless-bundle-shaped transactions concurrently can hit the race window.

### Recommendation
Change `PreAddTx` to take the same lock discipline as `IsReady`: acquire `g.knownTxsMu.Lock()` (write lock) instead of `RLock()` whenever the code path may call a mutating method (`g.knownTxs.add`) on the shared structure. More generally, audit all accessors of `knownTxs` to ensure every mutating call path (`add`, and any future delete/update operations) is only ever reached while holding the exclusive write lock, and that read-only paths (`get`, `numQueue`, `numExecutable`) are the only ones permitted to use `RLock`.

### Proof of Concept
1. Start a Kaia node with the gasless module enabled and `MaxBundleTxsInQueue` set high enough to not immediately reject bundle txs.
2. From two or more concurrent RPC connections, submit distinct valid "approve" or "swap" gasless-bundle transactions (`g.IsBundleTx(tx) == true`) for different sender accounts at high frequency, so that many calls into `TxPool.AddRemote`/`AddRemotes` → `GaslessModule.PreAddTx` occur concurrently.
3. Because `PreAddTx` only takes `g.knownTxsMu.RLock()` before calling the mutating `g.knownTxs.add(...)`, concurrent goroutines can execute the `add` mutation simultaneously without mutual exclusion against each other.
4. Observe the node crash with `fatal error: concurrent map writes` (or similar map-corruption panic) in the node logs, terminating the process and halting block/tx processing for all users — reproducible more reliably when built/run with `-race` or under sustained parallel submission load.

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

func (g *GaslessModule) IsReady(txs map[uint64]*types.Transaction, next uint64, ready types.Transactions) bool {
	g.knownTxsMu.Lock()
	defer g.knownTxsMu.Unlock()

	tx, ok := txs[next]
	if !ok {
		return false
	}

	if !g.isReady(txs, next, ready) {
		return false
	}

	if g.IsBundleTx(tx) {
		// If prev tx is bundle tx, there's no need to check the knownTxs limit because it has been checked in the previous `IsReady()` execution.
		isPrevTxBundleTx := len(ready) != 0 && g.IsBundleTx(ready[len(ready)-1])
		if isPrevTxBundleTx {
			g.knownTxs.add(tx, TxStatusPending)
			return true
		}

		maxBundleTxsInPending := g.GetMaxBundleTxsInPending()
		if maxBundleTxsInPending != math.MaxUint64 {
			numExecutable := uint(g.knownTxs.numExecutable())

			numSeqTxs := uint(1)
			for i := next + 1; i < next+uint64(len(txs)); i++ {
				if tx, ok := txs[i]; ok && g.IsBundleTx(tx) {
					numSeqTxs++
				} else {
					break
				}
			}

			// false if there is possibility of exceeding max bundle tx num
			if numExecutable+numSeqTxs > maxBundleTxsInPending {
				logger.Trace("Not promoting a tx because of exceeding max bundle tx num", "tx", tx.Hash().String(), "numExecutable", numExecutable, "maxBundleTxsInPending", maxBundleTxsInPending)
				return false
			}
		}

		g.knownTxs.add(tx, TxStatusPending)
	}

	return true
}
