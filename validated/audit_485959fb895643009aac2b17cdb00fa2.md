### Title
`ReceivedOutput::read` deserializes unauthenticated `(offset, TxOut, outpoint)` triples without binding the offset to the output's `script_pubkey`, enabling forged "received" records that report unspendable funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
CVE-2021-33840 describes a system inserting attacker-controlled records (COVID-19 contact data) that lacked a digital signature binding them to a real identity, letting unauthenticated parties poison the dataset. The structural analog in Serai is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`: it accepts three attacker-controlled fields — a scalar `offset`, a `TxOut`, and an `OutPoint` — as a single "funds received" record, yet never verifies that `TxOut.script_pubkey` actually equals `p2tr(key + offset·G)` for any known key, nor that the outpoint exists. The offset/script binding that `Scanner::scan_transaction` establishes on-chain is silently assumed, not enforced, on deserialization.

### Finding Description
`Scanner::scan_transaction` creates a `ReceivedOutput` only after proving the binding `output.script_pubkey == p2tr_script_buf(self.key + GENERATOR * offset)` via the `self.scripts` map lookup (wallet/mod.rs:205-211). That binding is what makes the output spendable: `offset` is "the scalar offset to obtain the key usable to spend this output" (wallet/mod.rs:91-92).

`ReceivedOutput::read`, however, reads `offset` via `Secp256k1::read_F` and the `TxOut`/`OutPoint` via `consensus_decode` and returns the record unconditionally (wallet/mod.rs:122-134). There is no field carrying the scanner key and no recomputation of the expected script. Consequently, the serialized form is completely unauthenticated: any party that can feed bytes to `ReceivedOutput::read` — the prompt-listed reachable surface — can forge a record claiming an arbitrary balance at an arbitrary outpoint under an arbitrary offset. This mirrors the luca flaw exactly: an unsigned, self-asserted record (phone number there; offset/outpoint/TxOut here) is accepted into a trusted dataset.

### Impact Explanation
Two concrete harms:

1. **Funds reported received that are not spendable.** A forged `ReceivedOutput` with `offset ≠ the real offset for that script_pubkey` (or an outpoint that doesn't exist / isn't owned) inflates the reported balance. If the record is later spent via `SignableTransaction`/FROST signing, the offset-derived key will not match the output's P2TR key, so the produced BIP-340 signature is invalid — the funds can never move.
2. **Denial of service via record insertion.** Like the luca fake records, an attacker can inject many forged `ReceivedOutput`s (arbitrary outpoints, dust or fake values), polluting the wallet's UTXO set and causing constructed transactions to reference nonexistent outpoints — every signing round built on them produces an invalid transaction.

### Likelihood Explanation
Anywhere serialized `ReceivedOutput`s cross a trust boundary (relayed between components, stored, or provided by a counterparty claiming a deposit was made), a remote unauthenticated party can supply the forged bytes. The parser itself performs only canonical-decoding checks (`read_F` scalar validity, consensus decoding), so no malformed-encoding rejection will catch it — the record is well-formed, just false. Exploitation requires no key material and no validator status.

### Recommendation
Bind the record to its provenance on deserialization. Options:

- Include the expected `script_pubkey`-derivable key (or the scanner key) in the serialized record and recompute `p2tr_script_buf(key + GENERATOR * offset)` on read, rejecting mismatches.
- Alternatively, make `ReceivedOutput::read` private and expose a `verify`/`re-derive` API that takes the `Scanner`/`ProjectivePoint` and confirms the output matches a registered script before returning the record.
- Document that serialized `ReceivedOutput`s are self-asserted claims requiring re-validation against chain state before being treated as spendable balance.

### Proof of Concept
```rust
use bitcoin::{TxOut, OutPoint, Txid, Amount, ScriptBuf, hashes::Hash};
use bitcoin_serai::wallet::ReceivedOutput;
use k256::Scalar;

// Attacker forges a "received" record: offset=1, a TxOut paying to an arbitrary
// script (e.g. OP_RETURN-burn or a key we don't control), and a fake outpoint.
let mut bytes = Vec::new();
bytes.extend(Scalar::ONE.to_bytes());                       // offset
let fake_txout = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: ScriptBuf::new_op_return(&[0xde, 0xad]),   // not our P2TR script
};
bytes.extend(bitcoin::consensus::serialize(&fake_txout));
let fake_outpoint = OutPoint { txid: Txid::all_zeros(), vout: 0 };
bytes.extend(bitcoin::consensus::serialize(&fake_outpoint));

// Accepted unconditionally: no offset ↔ script_pubkey binding is checked.
let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(forged.value(), 1_000_000); // phantom balance reported
// Any spend attempt signs with key + 1·G, which cannot satisfy fake_txout,
// yielding invalid BIP-340 signatures / nonexistent outpoints => DoS.
```
