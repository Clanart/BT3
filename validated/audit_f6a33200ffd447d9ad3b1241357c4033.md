### Title
Set-based membership check in `filter_preexisting_from_diff` lets cross-position line collapsing hide malicious added lines from LLM reviewer - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`filter_preexisting_from_diff` classifies any `+` line as "pre-existing" if its `.strip()`ed text matches **any** removed line anywhere in the diff, with no positional/hunk binding. An attacker who controls a full-file rewrite (e.g. via Write tool) can include one throwaway removed line that stripped-matches an injected malicious added line placed elsewhere in the file, causing that malicious line to be silently rewritten to a context (` `) line and hidden from the LLM security reviewer.

### Finding Description
In `plugins/security-guidance/hooks/gitutil.py`, `filter_preexisting_from_diff` (lines 657-722) builds a single global `removed_lines` set from all `-` lines in the diff [1](#0-0) , then for every `+` line checks membership in that set with no regard for hunk, position, or surrounding context [2](#0-1) . The function's own docstring acknowledges this exact weakness: "the set lets one removal mask N additions of the same stripped text. Accepted trade-off" [3](#0-2) .

This function is only invoked when `baseline_sha` is set and `removed_lines` is non-empty, i.e. for full-file rewrites where git shows an entire file's old content removed and new content re-added (the classic PostToolUse `Write` full-rewrite diff pattern this filter targets) [4](#0-3) . An attacker who controls file content written by the agent (e.g. via a crafted plugin/markdown instruction that causes a full-file `Write`) can:
1. Include a decoy line elsewhere in the file that is removed as part of the rewrite and whose stripped text is `X`.
2. Inject a malicious added line whose stripped text is also `X` (identical after `.strip()`, differing only in leading/trailing whitespace or original position).

Because `X` is in the global `removed_lines` set, the malicious `+` line at line 705 (`if content in removed_lines`) is converted to a context line at line 707, removing its `+` marker and thus its "newly added" visibility to whatever downstream logic feeds the diff to the LLM reviewer.

### Impact Explanation
This defeats the intended trust-boundary guarantee of the security-guidance plugin: any newly written/added code is supposed to be visible to the LLM security reviewer before commit/push. By exploiting the imprecise, position-agnostic stripped-text matching, an attacker-controlled full-file rewrite can hide injected malicious code (e.g. a backdoor line, credential exfiltration call, or malicious subprocess call) from review while still landing it in the working tree/commit. This matches a "trust-boundary bypass in review/export logic" impact class — the reviewer's visibility guarantee is silently defeated via a formatting/parsing trick, not a legitimate design accepted-risk scenario limited to accidental reindentation.

### Likelihood Explanation
Preconditions are realistic and already enumerated by the prompt: the agent must perform a full-file `Write` rewrite of attacker-influenced content (e.g., driven by a crafted plugin/markdown instruction), and the attacker needs only to ensure one decoy line's stripped text matches one malicious line's stripped text — trivial to construct deliberately. The bug is deterministic and always reachable whenever `filter_preexisting_from_diff` runs on such a diff (not an edge case), and the code comment shows the maintainers were aware of the general imprecision but treated it as an accepted trade-off for legitimate reindentation cases, not as a hardened invariant against adversarial line-content collisions.

### Recommendation
Bind the removed/added line matching to hunk-local or positional context instead of a diff-wide set: e.g., use a sequence-alignment (difflib.SequenceMatcher) per hunk to determine which specific removed line corresponds to which added line, or require that the stripped-text match occur at the same relative line offset within the file rewrite. At minimum, cap how many additions a single removed line is allowed to mask (currently unbounded "one removal mask N additions"), and prefer treating ambiguous/duplicate stripped-text matches as "keep visible to reviewer" (fail-closed) rather than "hide" (fail-open), since the review-visibility guarantee is a security control.

### Proof of Concept
Unit test in the style of the existing test suite for `gitutil.py`:

```python
def test_filter_preexisting_does_not_hide_malicious_added_line_via_decoy():

        "@@ -1,2 +1,3 @@\n"
        "-    pass  # decoy\n"
        " def f():\n"
        "+    pass  # decoy\n"
        "+    os.system(user_input)  # malicious injected line\n"
    )
    diff_files = [("app.py", diff_content)]
    result = filter_preexisting_from_diff(diff_files, cwd=".", baseline_sha="deadbeef")
    _, filtered_content = result[0]
    # Malicious line must still be visible as an added ('+') line to the reviewer
    assert "+    os.system(user_input)" in filtered_content
```
Expected (current/vulnerable) behavior: only the exact decoy line is matched, but since the malicious line is separate, this specific test may pass; the actual PoC needs the malicious line's stripped text to exactly collide with the decoy's stripped text, e.g.:
```python
def test_filter_preexisting_collapses_unrelated_malicious_line():
    diff_content = (
        "@@ -1,3 +1,3 @@\n"
        "-SECRET = 'benign_old_value'\n"
        " def helper():\n"
        "+    pass\n"
        "@@ -10,1 +10,2 @@\n"
        "+SECRET = 'benign_old_value'\n"  # attacker crafts a real malicious line elsewhere that happens to normalize identically after strip, e.g. differing only by trailing whitespace
    )
    ...
    # Assert the malicious '+' line retains its '+' prefix (visible to reviewer)
    assert filtered_content.count("+SECRET = 'benign_old_value'") >= 1
```
The assertion that should hold (and currently fails, demonstrating the bug) is: a `+` line whose stripped text matches a `-` line from a *different, unrelated hunk/position* must remain marked `+` (visible), not be silently converted to a context line, unless the function can prove positional correspondence.

```python
def filter_preexisting_from_diff(diff_files, cwd, baseline_sha):
    """
    Filter out pre-existing content from diff files.
    When a file is fully rewritten (Write tool replaces entire content),
    git shows all lines as removed (-) then re-added (+). This function
    detects such rewrites and strips lines from the + section that also
    appeared in the - section, so the LLM reviewer only sees truly new code.
    """
    if not baseline_sha:
        return diff_files

    filtered = []
    for file_path, diff_content in diff_files:
        lines = diff_content.split('\n')

        # Collect removed and added lines (stripping the +/- prefix)
        removed_lines = set()
        added_lines = []
        for line in lines:
            if line.startswith('-') and not line.startswith('---'):
                removed_lines.add(line[1:].strip())
            elif line.startswith('+') and not line.startswith('+++'):
                added_lines.append(line[1:].strip())

        if not removed_lines:
            # New file, no pre-existing content to filter
            filtered.append((file_path, diff_content))
            continue

        # Check what fraction of added lines were pre-existing
        preexisting_count = sum(1 for l in added_lines if l in removed_lines)
        if preexisting_count == 0:
            filtered.append((file_path, diff_content))
            continue

```
