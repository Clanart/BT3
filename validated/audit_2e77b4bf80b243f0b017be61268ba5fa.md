Based on my research, I found a strong structural analog to the Mantra DEX bug in GitHub Desktop's Copilot merge-conflict-resolution pipeline: a validation function that checks quantity in only one direction (non-empty) but never cross-checks the count against the actual number of hunks extracted from the file, and a reassembly step that splices resolved content back into the file by array position/order.

### Title
Missing hunk-count validation in Copilot conflict resolution allows positional resolvedContent mismatch to silently corrupt merged files - (File: app/src/lib/copilot-conflict-resolution.ts, app/src/lib/copilot-conflict-context.ts)

### Summary
`extractConflictHunks` parses attacker-influenceable, on-disk conflict-marker content (`<<<<<<<`/`=======`/`>>>>>>>`) from a file being merged/rebased/cherry-picked, in order, into an ordered array of hunks [1](#0-0) . The array of hunks is sent to Copilot, and the response is validated by `parseCopilotConflictResolution`, which only asserts each file's `hunks` array is non-empty (`rawHunks.length === 0` → throw) and validates the shape of each entry, but never validates that the **count** of returned hunk resolutions matches the number of hunks actually extracted from the on-disk file for that path [2](#0-1) . Reassembly (`reassembleResolvedFile`) then splices resolutions back into the raw file content positionally/in-order, per the accompanying tests ("replaces multiple conflicts in order") [3](#0-2) . This mirrors the reported bug class exactly: a bound/count check exists for one side (reject zero-length) but the symmetric check (reject mismatched, over/under-length) is absent, and downstream code assumes correspondence that was never enforced.

### Finding Description
The invariant that must hold before positional splicing is: `resolutions[j]` for file `path` corresponds 1:1, in order, to the hunk extracted at position `j` by `extractConflictHunks` for the same file on disk. `parseCopilotConflictResolution` enforces only `rawHunks.length !== 0` — it has no knowledge of, and never receives, the actual hunk count extracted from the working-directory file for that path [4](#0-3) . If a conflicted file contains unusual or adversarially-crafted conflict-marker sequences (e.g. content in a merged-in branch/commit designed to make `extractConflictHunks` split hunks differently than the model perceives, or the model simply returns a different count due to how it read the prompt), the resulting `resolutions` array can have a different length or ordering than the true hunk array, yet no guard rejects this before the resolved content is written to disk in `_applyCopilotConflictResolutions`, which writes `resolution.resolvedContent` straight to the file and stages it with `git add` [5](#0-4) . The path/size/marker-presence guards in `buildConflictContext` (path traversal via `resolveWithin`, file-size cap, "no conflict markers found") protect against unrelated attack surfaces but do nothing to verify hunk-count/order correspondence between what was extracted and what is echoed back for reassembly [6](#0-5) .

### Impact Explanation
If a mismatch occurs, positional splicing can substitute the wrong resolved block into the wrong conflict location, drop content, or duplicate content — all without an error, because the only rejected case is "empty hunks array." Since the tool writes the result directly to the working tree and immediately runs `git add` to stage it for the ongoing merge/rebase/cherry-pick [7](#0-6) , this is a silent-corruption-of-what-the-user-commits scenario: the user clicks "Continue Merge" believing the shown resolution was applied faithfully, but the actually staged/committed content can differ from what was reviewed, matching the report's "user leaks value/gets wrong result despite guard existing" pattern.

### Likelihood Explanation
The conflicted file's content, and therefore the exact conflict-marker layout `extractConflictHunks` will observe, is fully attacker-influenceable by whoever authored the branch/commit being merged, rebased, or cherry-picked (a classic "attacker controls a fetched/cloned repository" primitive). No local/admin access or pre-existing malware is required — only that the victim merges/rebases against an attacker-authored branch and uses the Copilot conflict-resolution feature. I was not able to fully inspect the body of `reassembleResolvedFile` in this session (only its call sites and unit tests) to confirm there is no independent length-equality assertion elsewhere in the pipeline; this is a gap in my verification that should be checked directly in the source before treating this as fully confirmed.

### Recommendation
In `parseCopilotConflictResolution` (or immediately before/inside `reassembleResolvedFile`), thread through the actual extracted hunk count per file and assert `rawHunks.length === extractedHunks.length` for that path, rejecting the whole response (or falling back to "skip file, resolve manually") on any mismatch, rather than only rejecting the zero-length case.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }
