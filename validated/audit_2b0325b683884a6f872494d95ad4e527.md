### Title
Attacker-Controlled `WWW-Authenticate` Realm Header Spoofs GitHub Endpoint Classification, Causing GitHub Token Exfiltration to Untrusted Hosts - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The stablecoin bug's broken invariant is "treat two non-equivalent assets as fungible based on an unverified label." GitHub Desktop's git-credential trampoline has the same shape: it classifies an arbitrary remote endpoint as a trusted GitHub/GitHub-Enterprise host based on a **self-declared, attacker-controlled string** (`WWW-Authenticate: realm="GitHub"`) instead of a cryptographically or authoritatively verified identity. That misclassification routes real GitHub OAuth credentials to hosts that are not actually GitHub.

### Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` decides how to treat a credential request for a given endpoint. After checking known dotcom/GHE hostnames, it falls back to a "happy path" heuristic: [1](#0-0) 

Any HTTP(S) server that a user's git remote points to (a cloned/fetched repo's origin, a submodule URL, or a URL a user pastes to add a remote) can return a `401` with a `WWW-Authenticate` header containing `realm="GitHub"`. Git captures that header and forwards it into the credential-helper protocol as a `wwwauth[]=...` field, which Desktop parses via `parseCredential`: [2](#0-1) 

Because the string comparison in `getEndpointKind` is purely syntactic and unauthenticated (no TLS pinning, no call to the real GitHub API, no origin allow-list), any attacker-controlled server can force the endpoint to be classified as `'enterprise'` regardless of its actual identity.

Once classified as non-`'generic'`, `getCredential` treats the host as a GitHub endpoint. If the user has no matching account, it invokes `promptForGitHubSignIn`: [3](#0-2) 

`promptForGitHubSignIn` starts a real GitHub Enterprise sign-in flow bound to the attacker's endpoint/origin string (taken directly from the spoofed request), not to any verified GitHub Enterprise instance: [4](#0-3) 

After a successful sign-in (or if an existing account is coincidentally scoped to that same origin), `credWithAccount` places the account's real OAuth token into the credential map that is returned to git: [5](#0-4) 

Git then sends that credential over HTTP(S) to the URL/host that originally issued the spoofed `WWW-Authenticate` header — i.e., the attacker's server — as part of the authenticated request retry.

### Impact Explanation
This corrupts the value "destination of the user's GitHub OAuth token": instead of the token only ever reaching `github.com`/a genuine GHE instance (whose identity was previously verified via `isDotCom`/`isGHE`/`findGitHubTrampolineAccount` origin matching or a real `isGitHubHost` API probe), the token can be sent to an arbitrary attacker-controlled endpoint whose only "proof" of being GitHub is a self-reported HTTP header. A stolen OAuth token grants the attacker whatever scopes Desktop requested (repo read/write, etc.), enabling data exfiltration from private repositories and unauthorized pushes/commits under the victim's identity — directly analogous to the report's "attacker substitutes an undesirable asset for a desirable one because the contract trusts a declared equivalence instead of verifying real value."

### Likelihood Explanation
The attacker only needs to control the server behind a git remote URL the victim's Desktop instance talks to (a malicious/compromised remote, a MITM-free but attacker-operated HTTP endpoint added as a remote, or a repo containing a submodule pointing at an attacker server) and respond to an HTTP auth challenge with a crafted `WWW-Authenticate` header — no local access, no prior credential leak, and no unnatural interaction beyond normal fetch/clone/push operations that Desktop performs automatically. Existing guards (`isDotCom`, `isGHE`, `findGitHubTrampolineAccount` origin equality) don't stop this path because the vulnerable code explicitly falls through to the unauthenticated `wwwauth[]` heuristic when those checks fail, and that heuristic is evaluated *before* the safer `isGitHubHost(endpoint)` network check.

### Recommendation
Remove or drastically restrict the `wwwauth[]` realm heuristic in `getEndpointKind`; never let attacker-supplied header content elevate an unknown endpoint to `'enterprise'`/`'github.com'` trust level. Require a positive identity check (an authoritative API probe via `isGitHubHost`, or user-configured endpoint allow-list) before ever surfacing an existing GitHub account's token or initiating a GitHub sign-in bound to a remote-supplied origin string. At minimum, gate the heuristic behind an explicit user confirmation showing the actual endpoint before any token is released to it.

### Proof of Concept
1. Attacker hosts a git-over-HTTP(S) server at `https://attacker.example` and configures it to answer unauthenticated requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds/clones a repository whose remote (or a submodule inside a legitimately-cloned repo) points at `https://attacker.example/foo/bar.git`.
3. Desktop's dugite/git credential helper flow calls the trampoline; git forwards the captured header as `wwwauth[0]=Basic realm="GitHub"` in the `get` request's stdin, handled by `parseCredential`.
4. `getEndpointKind` matches `realm="GitHub"` and returns `'enterprise'` for `attacker.example` — [6](#0-5) .
5. `getCredential` finds no existing account for `attacker.example` and calls `promptForGitHubSignIn('https://attacker.example')`, which begins an Enterprise sign-in bound to that origin — [7](#0-6) .
6. Once the user completes what looks like a normal "sign in to your GitHub Enterprise" prompt (using their real GitHub credentials/OAuth), the resulting token is merged into the credential map and returned to git — [8](#0-7) .
7. Git sends that Authorization header directly to `https://attacker.example`, exfiltrating the victim's GitHub token to the attacker.

Note: I was not able to fully trace `getAPIEndpoint`/`getCredentialUrl` implementations (in `app/src/lib/api.ts` and `app/src/lib/trampoline/trampoline-environment.ts`) due to index limits on file content, so the exact normalization of `apiEndpoint` used in the account-match check in `getCredential` could not be independently verified line-by-line; a Devin session with full repo access would be needed to confirm that detail precisely.

```typescript
export const parseCredential = (value: string) => {
  const cred = new Map<string, string>()

  // The credential helper protocol is a simple key=value format but some of its
  // keys are actually arrays which are represented as multiple key[] entries.
  // Since we're currently storing credentials as a Map we need to handle this
  // and expand multiple key[] entries into a key[0], key[1]... key[n] sequence.
  // We then remove the number from the key when we're formatting the credential
  for (const line of value.split(/\r?\n/)) {
    const eqIx = line.indexOf('=')
    if (eqIx === -1) {
      continue
    }

    const k = line.slice(0, eqIx)
    const v = line.slice(eqIx + 1)

    if (k.endsWith('[]')) {
      let i = 0
      let newKey

      do {
        newKey = `${k.slice(0, -2)}[${i}]`
        i++
      } while (cred.has(newKey))

      cred.set(newKey, v)
    } else {
      cred.set(k, v)
    }
  }

  return cred
}
```
