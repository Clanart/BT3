### Title
Relayer fee balance is zeroed on Hyperbridge before the cross-chain payout is guaranteed, permanently burning fees when the destination-side transfer fails - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-ismp-relayer::withdraw` (invoked via the `withdraw_fees` extrinsic) dispatches an ISMP POST request instructing the destination chain's `HostManager`/`EvmHost` to pay out a relayer's accrued fee, and then immediately zeroes the relayer's `Fees` storage entry on Hyperbridge — before the destination-side payout has executed or been confirmed. The actual payment is a separate, unconditional external call (`EvmHost.withdraw` → `IERC20.safeTransfer`) on another chain that can permanently revert (insufficient shared host balance, blacklisted/paused fee token, transfer-hook failure). When that happens, the relayer's accounting on Hyperbridge already shows zero balance, with no compensating re-credit or refund path — an irreversible loss of the fee, structurally the same class of bug as the VotiumStrategy report: a withdrawal path unconditionally invokes a downstream call that can fail, while state has already been mutated as if it succeeded.

### Finding Description
The withdrawal flow is:

1. `Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs:81-187`) reads `available_amount = Fees::<T>::get(dest_chain, address)`, builds a `WithdrawalParams`/`DispatchPost` body, and calls `dispatcher.dispatch_request(...)`. [1](#0-0) 
2. Immediately after the *local* dispatch call succeeds (which only enqueues the request commitment for a relayer to later deliver — it does **not** confirm destination execution), the pallet zeroes the balance: [2](#0-1) 
3. The actual payment only happens later, when some relayer submits a proof of this request to the destination chain, where `HostManager.onAccept` unconditionally calls `IHostManager(_params.host).withdraw(...)`: [3](#0-2) 
4. `EvmHost.withdraw` performs the transfer with no balance pre-check or fallback — it just reverts on failure: [4](#0-3) 
5. The project's own test suite confirms this call reverts outright when the host's fee-token balance is insufficient, with no recovery/state change: [5](#0-4) 

Because the `EvmHost` fee-token balance is a single shared pool (protocol revenue and all relayers' unwithdrawn fees comingled, with no per-relayer reservation), and because governance can independently drain it via `pallet-host-executive::withdraw` → the same `HostManager`/`EvmHost.withdraw` path: [6](#0-5) 
there is no invariant guaranteeing the pool still holds at least `available_amount` by the time a relayer's withdrawal request is actually delivered. If it doesn't (balance drawn down by other withdrawals/sweeps, or the fee token itself reverts the transfer — e.g. a blacklist/pause on the configured ERC-20), the destination call fails every time it's retried, yet the relayer's `Fees` entry on Hyperbridge was already zeroed at step 2, with no on-timeout or on-failure callback anywhere in the withdrawal/dispatcher code that re-credits the balance.

This exactly mirrors the seed report's broken invariant: a withdrawal path performs bookkeeping (zeroing the debt / "unlocking" the balance) as if a *forced*, unconditionally-executed downstream call had already succeeded, when that call (`lock()` in the original report; `EvmHost.withdraw`'s `safeTransfer`/native `call` here) can revert for reasons entirely outside the withdrawer's control and with no way to unwind the optimistic state update.

### Impact Explanation
A relayer's earned, legitimately-accrued cross-chain delivery fee can be permanently and irrecoverably lost — the exact "loss of funds" impact required by the bounty scope. This is not a griefing-only DoS: because `Fees` is zeroed before delivery is confirmed, and there is no compensating credit-back mechanism, the loss is final once the destination-side payout condition (insufficient balance, blacklisted beneficiary, paused/frozen fee token) is unrecoverable or persists indefinitely.

### Likelihood Explanation
This does not require a malicious peer, relayer, or admin — it can be triggered by ordinary, permissionless protocol operation: any window where the shared `EvmHost` fee-token balance dips below a relayer's `available_amount` (e.g., concurrent withdrawals or a legitimate `pallet-host-executive::withdraw` sweep occurring between a relayer's fee accumulation and their `withdraw_fees` call) causes the destination leg to fail while the source-side debt has already been erased. Given `dispatch_request` on Hyperbridge and execution on the destination are two separate, asynchronous, non-atomic transactions on different chains with no two-phase commit or rollback, this ordering bug is reachable under normal usage, not just contrived edge cases.

### Recommendation
Do not zero `Fees::<T>` optimistically at dispatch time. Instead:
- Only clear (or decrement) the relayer's fee balance once a destination-chain delivery *receipt/ack* is proven back to Hyperbridge (mirroring the pattern already used for `accumulate_fees`, which requires a delivery proof before crediting), or
- Keep the debit and the dispatch atomic by holding the funds in an explicit escrow keyed to the specific commitment, releasing it back to `Fees` if the request times out or the destination confirms failure, rather than deleting the record permanently on local dispatch alone.
- Separately, `EvmHost`/`HostManager` should track a reserved-for-relayers balance distinct from sweepable protocol revenue so `pallet-host-executive::withdraw` cannot drain funds already owed to relayers.

### Proof of Concept
1. Relayer R accumulates a fee of `X` tokens for `dest_chain = C`, reflected in `Fees::<T>::get(C, R) = X` on Hyperbridge (`modules/pallets/relayer/src/accumulate.rs`).
2. At/around the same time, either (a) another relayer's withdrawal or (b) a `pallet-host-executive::withdraw` governance sweep drains `EvmHost`'s fee-token balance on chain `C` below `X` (`modules/pallets/host-executive/src/lib.rs:276-319`, `evm/src/core/EvmHost.sol:651-660`).
3. R calls `withdraw_fees` on Hyperbridge. `dispatch_request` succeeds locally (it only records a commitment), and `Fees::<T>` for R on `C` is immediately set to `0` (`modules/pallets/relayer/src/withdrawal.rs:169-177`).
4. Any relayer later submits the proof to deliver this request to `HostManager` on chain `C`. `HostManager.onAccept` calls `EvmHost.withdraw`, which reverts because the balance is insufficient — as directly reproduced by the repo's own test `test_host_manager_insufficient_balance` (`evm/tests/rust/src/tests/host_manager.rs:143-172`).
5. Every subsequent delivery attempt reverts identically (no fix to the underlying insufficiency occurs), while R's `Fees` entry on Hyperbridge remains permanently `0`. R's fee is lost with no code path to restore it.

        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));

        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
