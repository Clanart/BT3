Based on my analysis, I've identified a concrete analog to the "Unsafe Identifiers" bug class within the CW↔EVM pointer registry.

### Title
Truncated identifier collision in CW↔EVM pointer reverse registry allows bypass of pointer-to-pointer protection - (File: x/evm/keeper/pointer.go)

### Summary
The GHSA-w29m-fjp4-qhmq advisory describes Opencast using unsafe/loosely-validated identifiers directly for security-sensitive operations, and notes that inconsistent identifier representations (`Id.toString()` vs `Id.compact()`) can cause identifier mismatches that break intended invariants. Sei-chain's pointer registry has an analogous flaw: when mapping a CosmWasm bech32 address to an EVM `common.Address` key, the code does not decode the canonical account bytes — it instead reinterprets the raw ASCII string of the bech32 address via `common.BytesToAddress([]byte(addr))`.

### Finding Description
`SetCW20ERC20PointerWithVersion`, `SetCW721ERC721PointerWithVersion`, and `SetCW1155ERC1155PointerWithVersion` compute the reverse-registry key for a CW address by calling `common.BytesToAddress([]byte(addr))` [1](#0-0)  and the symmetric CW721/CW1155 setters do the same [2](#0-1) [3](#0-2) . `common.BytesToAddress` truncates its input to the last 20 bytes when the input is longer than 20 bytes (Go-Ethereum's `Address.SetBytes`), so this takes the **last 20 ASCII characters of the bech32 address string**, not the actual 20-byte canonical account ID. The same lossy transform is used symmetrically for the `cwAddressIsPointer` check that guards against creating a "pointer to a pointer" [4](#0-3) , and for `GetERC20Pointee`/`GetERC721Pointee`/`GetERC1155Pointee` reverse lookups [5](#0-4) .

Because the reverse-registry key is derived from a truncated/aliased representation of the identifier rather than its canonical bytes, two distinct CW contract addresses that happen to share the same last-20-character ASCII suffix collide to the identical reverse-registry key. This directly mirrors the GHSA's root cause: an identifier that is not canonically/consistently derived is used for a security-relevant lookup (here, the "is this address already a pointer" anti-double-wrapping check, and reverse pointer resolution used by `GetAnyPointeeInfo`/`GetCW20Pointee` etc. that other keepers/precompiles rely on to route ERC20/CW20 calls).

### Impact Explanation
If a colliding CW address is registered as a pointer, `cwAddressIsPointer` will spuriously (or exploitably, depending on which side is written second) allow bypassing the `ErrorPointerToPointerNotAllowed` invariant [6](#0-5) , or cause `GetERC20Pointee`/`GetCW20Pointee`-style reverse resolution to return the wrong counterpart contract for a given address. Since these pointer mappings are consulted by the EVM/CW bridge and pointer precompiles to decide how ERC20/CW20/CW721/CW1155 calls get routed and rendered (transfers, balance queries, minting), a collision could let an attacker's crafted CW contract be resolved as if it were the pointer/pointee of an unrelated, legitimate token, enabling confusion between two different assets in the pointer graph — a scenario the codebase treats as invalid ("cannot create a pointer to a pointer") specifically because it can break token accounting invariants.

### Likelihood Explanation
Exploitation requires an attacker to control (or grind via CosmWasm instantiate salts/labels) a wasm contract address whose bech32 string ends with the same last-20 ASCII characters as a specific target address. Because bech32 addresses are base32-encoded (~5 bits/char), the effective search space for matching a *specific* target's 20-character suffix (~100 bits) is still very large, making a targeted preimage attack computationally impractical for a single victim contract. However, this is a broken invariant/defense-in-depth failure in code explicitly designed to prevent pointer aliasing, and it is reachable purely by an unprivileged CosmWasm/EVM pointer user via the standard pointer-creation precompiles — no privileged access is required to trigger the flawed path.

### Recommendation
Derive the reverse-registry key from the canonical decoded account bytes (`sdk.AccAddressFromBech32(addr)`) rather than the raw ASCII bytes of the bech32 string, or use a fixed-length hash (e.g., first 20 bytes of `sha256(canonicalAccAddressBytes)`) so that the mapping from CW identifier to EVM-style key is collision-resistant and consistent with how the address is decoded elsewhere (e.g., in `GetCW20ERC20Pointer` via `sdk.MustAccAddressFromBech32`) [7](#0-6) .

### Proof of Concept
1. Compute two CosmWasm contract addresses `A` and `B` (via instantiate salt/label grinding) whose bech32 string representations share identical last-20 ASCII characters but differ elsewhere.
2. Register `A` as a CW20→ERC20 pointer via `SetCW20ERC20Pointer`, which stores the reverse key `PointerReverseRegistryKey(common.BytesToAddress([]byte(A)))` [8](#0-7) .
3. Attempt to register `B` as a CW721→ERC721 (or any other) pointer; `evmAddressIsPointer`/`cwAddressIsPointer` will resolve to the same truncated key as `A`, causing the "pointer to a pointer" check or subsequent lookups to treat `B` as aliased to `A`'s registry entry, corrupting pointer resolution for one of the two contracts.
