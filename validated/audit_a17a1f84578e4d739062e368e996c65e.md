### Title
Textual `grep '\[gone\]'` substring match conflates branch *name* content with git's semantic "gone" tracking status, causing deletion of live branches - ([File: plugins/commit-commands/commands/clean_gone.md])

### Summary
The `/clean_gone` command's cleanup pipeline (`git branch -v | grep '\[gone\]' | sed 's/^[+* ]//' | awk '{print $1}'`) matches the literal string `[gone]` anywhere in a `git branch -v` output line, without checking that the match falls in git's semantic tracking-status column rather than inside the branch's own name text. A branch whose name contains the literal substring `[gone]` (e.g. `feature-[gone]-x`) will be flagged and deleted via `git branch -D` even though it is not actually stale/gone from its remote, causing unauthorized deletion of a live branch.

### Finding Description
`git branch -v` prints one line per branch: leading marker (`  `, `* `, `+ `), branch name, commit hash, optional tracking annotation such as `[gone]`/`[ahead N]`, then the commit subject. The command in `plugins/commit-commands/commands/clean_gone.md` runs `grep '\[gone\]'` on the whole line, which is a pure substring search with no positional/column awareness of where the `[gone]` marker legitimately appears [1](#0-0) . If a branch is literally named something like `feature-[gone]-x`, the line `  feature-[gone]-x  abc1234 some commit message` contains the substring `[gone]` as part of the branch name itself, so `grep` matches it regardless of actual upstream tracking state. `sed 's/^[+* ]//'` then strips only the leading marker character, and `awk '{print $1}'` extracts the first whitespace-delimited field, which is the branch name (`feature-[gone]-x`) — correctly parsed as a token, but incorrectly classified as "gone" purely due to the coincidental substring in its name. This token is then passed to `git worktree remove --force` / `git branch -D`, deleting a branch that is not actually gone from its remote. There is no check anywhere in the command to confirm the `[gone]` text is git's real annotation (e.g., by checking column position, using `git for-each-ref --format='%(upstream:track)'`, or anchoring the match to the end of the line after the hash) rather than arbitrary branch-name text, so nothing stops this differential.

Additionally, the subsequent worktree-matching step `grep "\[$branch\]"` interpolates the extracted branch name directly into a grep pattern without escaping regex metacharacters, so a branch name containing `[`/`]` characters can further distort the worktree lookup, though the branch-deletion path alone is sufficient for the described impact.

### Impact Explanation
Any branch (local or one whose name is chosen by an external contributor and later fetched/checked out locally, e.g., via `gh pr checkout` naming a local branch after the contributor's branch) that happens to contain the literal substring `[gone]` in its name will be silently deleted by `git branch -D` the next time the victim runs the `/clean_gone` slash command, even though the branch has a live, tracked, non-gone upstream. This is unauthorized, unrecoverable deletion of a live branch (data loss), matching the "unauthorized command or file action" / data-loss impact class.

### Likelihood Explanation
Exploitation requires only that a branch with a `[gone]`-substring name exist locally when the user invokes `/clean_gone` — no elevated privilege, secret, or social engineering is needed beyond naming a branch (something any collaborator, or contributor whose PR branch gets fetched, can do). The command is executed verbatim as instructed by the slash-command markdown with no allowlist or validation of matched tokens, so the bug is deterministically triggered every time such a branch name is present.

### Recommendation
Replace the textual substring match with a check anchored to git's actual tracking metadata, e.g. use `git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads/` and filter lines where the track field is exactly `[gone]`, rather than grepping the free-form `git branch -v` line. At minimum, anchor the `grep` pattern to only match `[gone]` immediately following the commit hash field (not anywhere in the line), and quote/escape any branch name before interpolating it into subsequent `grep` patterns for worktree lookup.

### Proof of Concept
Differential/integration test:
1. In a temp git repo, create a branch `feature-[gone]-x` with a valid upstream (e.g., `origin/feature-[gone]-x`) that still exists remotely (i.e., not actually gone).
2. Run `git branch -v | grep '\[gone\]' | sed 's/^[+* ]//' | awk '{print $1}'` and capture the extracted set A.
3. Independently compute the true gone-branch set B via `git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads/ | awk '$2=="[gone]"{print $1}'`.
4. Assert `A == B`. The PoC demonstrates `A` contains `feature-[gone]-x` while `B` does not, proving the parser misclassifies a live branch as gone.
5. Execute the full script from `clean_gone.md` and assert that `git branch -D feature-[gone]-x` is invoked, confirming deletion of a non-gone branch.

   ```bash
   # Process all [gone] branches, removing '+' prefix if present
   git branch -v | grep '\[gone\]' | sed 's/^[+* ]//' | awk '{print $1}' | while read branch; do
     echo "Processing branch: $branch"
     # Find and remove worktree if it exists
     worktree=$(git worktree list | grep "\\[$branch\\]" | awk '{print $1}')
     if [ ! -z "$worktree" ] && [ "$worktree" != "$(git rev-parse --show-toplevel)" ]; then
       echo "  Removing worktree: $worktree"
       git worktree remove --force "$worktree"
     fi
     # Delete the branch
     echo "  Deleting branch: $branch"
     git branch -D "$branch"
   done
```
