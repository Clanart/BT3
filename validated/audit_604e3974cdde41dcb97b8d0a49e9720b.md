Based on my investigation, I found a concrete decimal-scaling analog to the C4 report inside `pallet-hyper-fungible-token`. I was unable to fully confirm the exact `pallet-assets` metadata-origin configuration in the Gargantua/Nexus runtimes before running out of iterations (I found `impl pallet_assets::Config` references in `parachain/runtimes/gargantua/src/ismp.rs` and `parachain/runtimes/nexus/src/ismp.rs` but could not read the origin bindings for `set_metadata` in the time remaining). That said, the pallet-level flaw is fully self-contained and provable purely from the pallet's own source, independent of that runtime detail.

### Title
Decimal-scaling invariant (`erc_decimals >= local_decimals`) is checked only at registration but consumed live, allowing bridge amount inflation on `send`/`on_accept`/`on_timeout` - (File: modules/pallets/hyper-fungible-token/src/lib.rs, modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`pallet-hyper-fungible-token` scales token amounts between a local asset's decimals and a remote EVM contract's decimals using `convert_to_erc20`/`convert_to_balance`, both of which use `saturating_sub` and silently produce a no-op scale factor (`10^0 = 1`) whenever `erc_decimals < local_decimals`. The pallet only enforces `erc_decimals >= local_decimals` as a one-time check inside `register_token`/`update_token`, while the actual `local_decimals` value used in `send`, `on_accept`, and `on_timeout` is re-read live from the mutable `Assets` metadata (`fungibles::metadata::Inspect::decimals`) on every call. This is the same class of bug as the C4 finding: a hard assumption about relative precision (here, `erc_decimals >= local_decimals`) is checked once but not re-validated at the point where the math that depends on it actually executes.

### Finding Description
`convert_to_erc20` and `convert_to_balance` implement decimal scaling this way: [1](#0-0) 

Both functions compute the scale exponent with `erc_decimals.saturating_sub(local_decimals)`. This is only correct when `erc_decimals >= local_decimals` — that's the entire premise baked into the design, exactly analogous to the C4 report's fixed `PRECISION = 1e6` assumption that broke once an AMM with different decimals was whitelisted.

The invariant is enforced as a snapshot check inside `register_token` and `update_token`: [2](#0-1) [3](#0-2) 

Note that `local_decimals` here is read *at registration time* via `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(...)`, and compared against the operator-supplied `config.decimals` (which becomes `erc_decimals`, stored in `Precisions`).

However, every subsequent operation that actually performs the scaling re-reads `local_decimals` **live** from the same mutable `Assets` metadata, not from a value locked in at registration:

- `send`: [4](#0-3) 
- `on_accept`: [5](#0-4) 
- `on_timeout`: [6](#0-5) 

`Precisions` (the `erc_decimals` side) is never re-derived or re-checked against the current `local_decimals` outside of `register_token`/`update_token`. If the underlying asset's decimals metadata in the `Assets` pallet (`pallet-assets`, per the runtime integration in `modules/pallets/hyper-fungible-token/README.md`) is changed *after* registration — via `pallet_assets::set_metadata`, which is governed by that asset's own metadata-setting origin (the asset's Owner/Issuer or a `ForceOrigin`), a permission scope entirely separate from this pallet's `CreateOrigin` — the checked invariant `erc_decimals >= local_decimals` silently becomes false for that asset going forward, without the pallet's own `ErcDecimalsBelowLocal` guard ever firing again.

Once `local_decimals > erc_decimals`, `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so:
- In `send`, `convert_to_erc20` stops scaling the outgoing ERC20 amount down at all: the raw local-precision balance (e.g. `1e18`-magnitude) is written straight into the `Message.amount` field that the destination EVM contract will treat as `erc_decimals`-precision (e.g. 6). The destination contract then unlocks/mints `10^(local_decimals - erc_decimals)` times more tokens than the amount actually escrowed locally.
- In `on_accept`/`on_timeout`, `convert_to_balance` symmetrically fails to scale up incoming amounts correctly, corrupting mint/refund amounts on the receiving side.

### Impact Explanation
This directly matches the required impact categories: unauthorized transaction/execution and stealing/loss of funds. A user (or the asset issuer themselves) can escrow or burn a small, correctly-priced amount of the local asset via the public `send` extrinsic, and have the ISMP message instruct the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract to release or mint an amount inflated by a factor of `10^(local_decimals - erc_decimals)` — potentially draining destination-side custody or minting unbacked wrapped supply. This is a silent numeric corruption, not a revert, so it isn't caught by any existing guard once the registration-time invariant has been invalidated.

### Likelihood Explanation
Likelihood is conditioned on the local asset's decimals metadata being changeable after `register_token`/`update_token` runs — a capability of standard `pallet-assets` (`set_metadata`), whose origin I could not fully confirm from the runtime configuration files (`parachain/runtimes/gargantua/src/ismp.rs`, `parachain/runtimes/nexus/src/ismp.rs`) in the time available. If that origin is anything other than the bridge's own `CreateOrigin` (e.g., the asset's own Issuer/Owner, which is the normal `pallet-assets` model), this is directly triggerable without any Hyperbridge admin, relayer, or prover involvement — only the `send` extrinsic, a public entrypoint. Regardless of that runtime-specific detail, the structural bug — a "checked-once, consumed-live" invariant with a silent `saturating_sub` fallback instead of an error — is present in the pallet code itself.

### Recommendation
- Do not re-derive `local_decimals` live in `send`/`on_accept`/`on_timeout`; snapshot and store the local asset's decimals in `Precisions` (or a parallel storage item) at `register_token`/`update_token` time, so the value used for scaling is exactly the value that was invariant-checked.
- Replace `saturating_sub` with checked/`ensure!`-style arithmetic in `convert_to_erc20`/`convert_to_balance` so that `erc_decimals < local_decimals` errors out instead of silently returning a `10^0` no-op scale factor.
- If asset decimals metadata can legitimately change post-registration, require the bridge operator to re-run `update_token` (which re-checks the invariant) before the asset is transferable, or block `send`/`on_accept` when the currently observed `local_decimals` no longer satisfies `>= erc_decimals`.

### Proof of Concept
1. Register asset `X` via `register_token` with `local_decimals = 6` and `config.decimals (erc_decimals) = 18` for an EVM chain — passes the `ErcDecimalsBelowLocal` check (18 ≥ 6). `Precisions[X][EVM] = 18`.
2. The asset's decimals metadata in `pallet-assets` for `X` is later changed to `24` (e.g. via `pallet_assets::set_metadata` under the asset's own Owner/Issuer origin, a capability independent of this pallet's `CreateOrigin`).
3. A user calls `send` with `asset_id = X`, `amount = 1_000_000` (1 unit at the new 24-decimal local precision — the pallet burns/locks this amount successfully).
4. Inside `send`, `decimals = <Assets as Inspect>::decimals(X) = 24` is read live; `erc_decimals = Precisions::get(X, EVM) = 18`. `convert_to_erc20` computes `erc_decimals.saturating_sub(decimals) = 18.saturating_sub(24) = 0`, so `erc20_amount = amount * 10^0 = 1_000_000` unchanged — instead of the correct downscale by `10^6`.
5. The destination EVM contract receives `Message.amount = 1_000_000` and, interpreting it at its configured 18-decimal precision, unlocks/mints `1_000_000 / 10^18` ... — more precisely, the destination amount is `10^6` times larger than the amount actually escrowed on the source chain, resulting in an inflated release/mint of tokens to the recipient with no revert anywhere in the call path.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
