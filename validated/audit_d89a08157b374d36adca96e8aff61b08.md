### Title
Deserialized Bitcoin outputs are not bound to their claimed outpoint or offset - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an offset, `TxOut`, and `OutPoint` as three independent fields and reconstructs a supposedly spendable output without proving that the encoded transaction actually contains that output or that the output corresponds to the encoded offset. This lets crafted bytes represent an existing or nonexistent outpoint as a higher-value output controlled by the wallet. [1](#0-0) 

### Finding Description
`Scanner::scan_transaction` creates a valid `ReceivedOutput` only after matching `output.script_pubkey` against a registered script and binding the result to the real transaction ID and output index. [2](#0-1) 

`ReceivedOutput::read` bypasses those checks entirely: it accepts any canonical scalar, any consensus-valid `TxOut`, and any consensus-valid `OutPoint`, then returns them as one object. [3](#0-2) 

There is no base-key or scanner parameter, no verification that `TxOut.script_pubkey` equals the script produced by the offset, and no lookup proving the encoded `OutPoint` resolves to the encoded `TxOut`. [1](#0-0) 

Downstream code treats the decoded object as authoritative: `Output::balance` returns `self.output.value()`, while `Output::id` and `Output::tx_id` derive the reported transaction identity from the separately supplied outpoint. [4](#0-3) 

### Impact Explanation
An unprivileged party who can supply serialized `ReceivedOutput` or serialized Bitcoin `Output` bytes can cause an output to be reported with an amount and outpoint that were never scanned together. For example, the bytes can name a real wallet-looking `TxOut` and inflated amount while pointing at a nonexistent, spent, or lower-value outpoint. The result is funds reported received that are not spendable as represented. [5](#0-4) 

The mismatch can also affect spending decisions because `SignableTransaction::new` calculates available funds from `input.output.value` while constructing inputs from `input.outpoint`. [6](#0-5) 

### Likelihood Explanation
The attack requires the attacker to reach a deserialization boundary for `ReceivedOutput` or the enclosing Bitcoin `Output`, not merely send a normal Bitcoin transaction. Normal scanning is not vulnerable because `Scanner` establishes the offset-to-script relationship and records the transaction-derived outpoint itself. [2](#0-1) 

Where serialized outputs are supplied across an untrusted boundary, exploitation only requires producing three independently valid encodings; no cryptographic break or control over validator keys is needed. [1](#0-0) 

### Recommendation
Do not expose `ReceivedOutput::read` as a constructor for trusted spendable outputs. Deserialize it through a scanner-aware API such as `Scanner::read_received_output`, which must verify that:

- the decoded `TxOut.script_pubkey` is registered in `scripts`;
- the decoded offset equals the registered offset for that script; and
- the decoded outpoint resolves to the identical `TxOut` on the authenticated Bitcoin chain.

At minimum, store or transmit the scanner context needed to recompute `p2tr_script_buf(key + G * offset)` and reject records whose script or registered offset differs. Consumers should also resolve `outpoint` against a trusted Bitcoin view before using `ReceivedOutput::value` as available funds. [7](#0-6) 

### Proof of Concept
Conceptually, construct bytes containing:

```rust
// offset belonging to a registered wallet script
let forged_offset = Scalar::ZERO;

// A valid TxOut paying to the wallet, but with an attacker-chosen amount.
let forged_txout = TxOut {
    value: Amount::from_sat(1_000_000),
    script_pubkey: wallet_p2tr_script,
};

// An outpoint which does not commit to forged_txout: it can be spent,
// nonexistent, or reference a lower-value output.
let forged_outpoint = OutPoint { txid: unrelated_txid, vout: 0 };
```

`ReceivedOutput::read` accepts this combination even though `Scanner::scan_transaction` would never produce it unless the referenced transaction actually contained that exact output at that index. [3](#0-2) 

The resulting object reports `1_000_000` sats through `value`, while spending uses the unrelated `outpoint`, so the represented funds are not spendable. [8](#0-7)

/// A transaction scanner capable of being used with HDKD schemes.
#[derive(Clone, Debug)]
pub struct Scanner {
  key: ProjectivePoint,
  scripts: HashMap<ScriptBuf, Scalar>,
}

impl Scanner {
  /// Construct a Scanner for a key.
  ///
  /// Returns None if this key can't be scanned for.
  pub fn new(key: ProjectivePoint) -> Option<Scanner> {
    let mut scripts = HashMap::new();
    scripts.insert(p2tr_script_buf(key)?, Scalar::ZERO);
    Some(Scanner { key, scripts })
  }

  /// Register an offset to scan for.
  ///
  /// Due to Bitcoin's requirement that points are even, not every offset may be used.
  /// If an offset isn't usable, it will be incremented until it is. If this offset is already
  /// present, None is returned. Else, Some(offset) will be, with the used offset.
  ///
  /// This means offsets are surjective, not bijective, and the order offsets are registered in
  /// may determine the validity of future offsets.
  ///
  /// The offsets registered must be securely generated. Arbitrary offsets may introduce a script
  /// path into the output, allowing the output to be spent by satisfaction of an arbitrary script
  /// (not by the signature of the key).
  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
