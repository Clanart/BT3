### Title
Governing node (single-governance admin) can set unbounded `governance.unitprice` and `reward.mintingamount` to steal transaction fees or inflate token supply - ([File: kaiax/gov/param.go])

### Summary
In Kaia's `governance.governancemode: single` (the mode used on Mainnet and Kairos), a single privileged address — the `GoverningNode` — has unilateral, unchecked authority to ratify governance parameter changes via header governance votes. Two of the most economically sensitive parameters, `governance.unitprice` (the network gas price) and `reward.mintingamount` (the per-block token minting amount), have **no upper-bound format validation** (`FormatChecker: noopFormatChecker`). This mirrors the external report's "malicious admin" bug class: a single privileged actor can set critical financial parameters to extreme values, extracting value from ordinary users (via inflated gas price) or diluting/inflating the entire token supply (via unbounded minting), with no multi-sig or timelock protection beyond the normal epoch-based ratification delay.

### Finding Description
The `kaiax/gov` module defines governance parameters and their validation rules in `kaiax/gov/param.go`. For `GovernanceUnitPrice`: [1](#0-0) 
the `FormatChecker` is `noopFormatChecker`, which always returns `true` regardless of value: [2](#0-1) 

Similarly, `RewardMintingAmount` also uses `noopFormatChecker`, allowing any non-negative-looking `*big.Int` value with no upper bound: [3](#0-2) 

These parameters are voted on and ratified through header governance. In `single` governance mode (the mode configured for Mainnet/Kairos per the module documentation), only the `GoverningNode` address may cast valid votes, and its votes are ratified deterministically each epoch: [4](#0-3) 

The `checkConsistency` function in header governance validates only a few specific parameters (`GovernanceGoverningNode`, `Kip71LowerBoundBaseFee`, `Kip71UpperBoundBaseFee`, `AddValidator`/`RemoveValidator`); all other listed parameters — including `GovernanceUnitPrice` and `RewardMintingAmount` — fall into the default-accept case with no additional bound checking: [5](#0-4) 

Once ratified, the new `UnitPrice` becomes the network's mandatory gas price for transactions (used to compute fees in `StateTransition.buyGas`), and `MintingAmount` becomes the amount minted every block via the reward module. There is no on-chain circuit breaker, multi-sig requirement, or additional timelock beyond the standard epoch delay (`(k+1)*epoch` blocks) before a ratified parameter takes effect.

### Impact Explanation
- **Fee theft (`governance.unitprice`)**: The governing node can ratify an extreme `UnitPrice` (e.g., orders of magnitude above the current 25 Gwei default), forcing every subsequent transaction sender/fee-payer on the network to pay an inflated gas price for the same computation, effectively extracting value from all users of the chain until the parameter is reverted (also subject to the same one-epoch delay).
- **Supply inflation (`reward.mintingamount`)**: The governing node can ratify an arbitrarily large `MintingAmount`, causing the protocol to mint outsized rewards every block, hyperinflating the native token supply and diluting all existing holders — a direct analog of the audit's "malicious admin steals from the protocol" concern, but applied at the chain level rather than a single dApp.

Both changes take effect automatically from the next epoch boundary with no additional governance gate, multi-sig, or veto mechanism described in the module.

### Likelihood Explanation
Exploitation requires control of the `GoverningNode` private key — the same "if the admin account is hacked or an internal admin becomes malicious" precondition explicitly cited in the referenced report. Given `single` mode is the configuration used on Mainnet and Kairos, this is a single point of failure: no other validator or user vote is needed to ratify the malicious value, and the format-checker layer (the only automated technical safeguard) explicitly performs no bound validation for these two parameters.

### Recommendation
Add bounded `FormatChecker` implementations for `GovernanceUnitPrice` and `RewardMintingAmount` (e.g., maximum multiplier relative to the previous value, or absolute caps), analogous to the bound checks already implemented for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` and `RewardRatio`. Consider extending `checkConsistency` to reject implausible jumps in `UnitPrice` or `MintingAmount` between consecutive ratifications, and evaluate additional governance safeguards (e.g., requiring `none` mode multi-party ratification, or a longer timelock) for parameters with direct value-extraction or supply-inflation impact.

### Proof of Concept
1. Deploy/operate a Kaia network in `governance.governancemode: single` with a designated `GoverningNode`.
2. From the `GoverningNode`, call `governance_vote` with `("governance.unitprice", <extremely large value>)` (or `("reward.mintingamount", <extremely large *big.Int>)`).
3. Because `Params[GovernanceUnitPrice].FormatChecker` / `Params[RewardMintingAmount].FormatChecker` is `noopFormatChecker`, the vote passes `NewVoteData` format validation.
4. At the next epoch boundary block, the node (as sole proposer of votes in `single` mode) ratifies the vote into `header.Governance`, per `checkConsistency` (`kaiax/gov/headergov/impl/header.go:214-223`), which performs no bound check for these parameter names.
5. Starting from block `(k+1)*epoch`, `GetParamSet` returns the malicious `UnitPrice`/`MintingAmount`, and the state transition / reward logic apply it network-wide — forcing inflated fees on every transaction sender or minting inflated block rewards, with no additional on-chain safeguard blocking it.

```markdown
The ratification condition is determined by the `governance.governancemode` parameter. Mainnet and Kairos both operate in `single` mode. There are two governance modes:

- `none` mode: all members of the GC can vote. For each governance parameter, the last vote in the epoch will be ratified.
- `single` mode: only one member of the GC, stipulated in the parameter `governance.governingnode`, can vote. All valid votes from the governing node in the epoch are ratified in block order. For each governance parameter, the last vote in the epoch will be ratified.

Parameter change ratified at `k*epoch` block takes effect starting from `(k+1)*epoch` block.
It is worth noting that the effective time of the ratification is `(k+1)*epoch + 1` before Kore.
```
