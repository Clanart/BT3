### Title
Rounding down in capped-collateral liquidation lets liquidator underpay debt relative to collateral seized - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
In `calc-final-liquidation-amounts`, when a borrower's available collateral is insufficient to cover the "expected" seizure (`coll-actual < coll-expected`), the debt obligation that the liquidator must repay for that seized collateral is recomputed via `calc-liq-debt-repay-real`, which rounds down, and the resulting USD figure is converted to token units via another round-down division. This mirrors the reported `VaultV2.forceDeallocate` bug class: a value that should be maximized in favor of the protocol (the vault/borrower side) is instead minimized in favor of the counterparty extracting value (the liquidator), via `mulDivDown`-style truncation on a penalty/discount ratio.

### Finding Description
`calc-liq-debt-repay-real` computes the debt that must be repaid for a given amount of collateral value, dividing by `(BPS + liq-penalty)` with round-down semantics: [1](#0-0) 

This is invoked inside `calc-final-liquidation-amounts` specifically for the branch where the user's actual collateral balance falls short of what the liquidation bonus math expected (`coll-actual < coll-expected`): [2](#0-1) 

Here `coll-actual-usd` (the USD value of the collateral actually being seized, itself rounded down via `normalize ... false`) is divided by `(BPS + liq-penalty)` to derive `debt-final-usd`, then converted to token units through `mul-div-down` again — a double round-down compounding the truncation. `debt-final-usd`/`debt-final` is the amount of debt the liquidator is credited with repaying for the collateral they receive. Because the ratio (BPS+liq-penalty) represents "collateral value per unit debt repaid, including the liquidator's bonus," rounding this quotient down means the liquidator is required to repay *less* debt than the collateral they are actually seizing corresponds to under the intended bonus ratio — the shortfall is truncated away rather than carried by the liquidator. This is exactly the reported bug class: a discount/penalty-style ratio computed with `mulDivDown` (via `div-bps-down`) instead of rounding up in favor of the protocol.

Downstream, `scale-debt-for-liquidation` converts `debt-final` to scaled debt units also via `mul-div-down`, then converts back with `mul-div-up` for the actual `debt-to-repay` amount used in `vault-system-repay`: [3](#0-2) 

The final `mul-div-up` on `debt-to-repay` only re-inflates the scaled-debt→token conversion; it does not correct the earlier collateral-USD → debt-USD round-down in `calc-final-liquidation-amounts`, so the core truncation from `calc-liq-debt-repay-real` and the subsequent `debt-final` conversion survives into the executed repayment.

The liquidation entrypoint wires these helpers together and executes the repay/seize with `vault-system-repay` and collateral transfer based on these truncated amounts: [4](#0-3) 

### Impact Explanation
This lands in the "temporary freezing of funds" / protocol-loss category analogous to the original report: in the collateral-capped liquidation path, the protocol/borrower side gives up collateral value that is not fully offset by the debt actually written off, because the debt-to-collateral ratio conversion rounds in favor of the liquidator instead of the vault. Each individual truncation is small (sub-unit, bounded by decimal precision), but it is a systematic bias that always favors the liquidator over the protocol on every collateral-capped liquidation, analogous in root cause and direction to the referenced `VaultV2.sol#L575` finding (rounding down a penalty/discount ratio that should round up to protect the protocol).

### Likelihood Explanation
This only triggers on the "collateral capped" branch of liquidation (`coll-actual < coll-expected`), i.e., when the borrower doesn't have enough of the specific collateral asset to cover the liquidator's full bonus-adjusted seizure. This is a routine, non-adversarial occurrence during normal liquidations of small/partially-collateralized positions, and requires no privileged access or oracle manipulation — any liquidator naturally benefits from the rounding each time this path executes.

### Recommendation
Round in favor of the vault/borrower along this specific path: use round-up (`div-bps-up`/`mul-div-up`) instead of round-down when computing `debt-final-usd` in `calc-liq-debt-repay-real`'s call site and when converting `debt-final-usd` to `debt-final` token units in `calc-final-liquidation-amounts`, so the liquidator's debt credit for a given collateral seizure is never under-stated.

### Proof of Concept
Given `coll-actual-usd` and `liq-penalty` such that `(coll-actual-usd * BPS) / (BPS + liq-penalty)` has a non-zero remainder — e.g. `coll-actual-usd = 1099`, `liq-penalty = 1000` (10%) → `div-bps-down(1099, 11000) = (1099*10000)/11000 = 999` (floor of 999.09), discarding the fractional remainder in the liquidator's favor. The subsequent `mul-div-down` conversion to `debt-final` (token units) truncates again. Over many small/capped liquidations this systematically credits liquidators with slightly less debt repayment than their seized collateral value warrants, leaking value from the protocol side, matching the root cause pattern of the referenced report (rounding down a penalty ratio instead of up).

  (debt-final uint)
  (coll-actual uint)
  (curr-scaled uint)
  (asset-id uint))
  (let (;; convert debt amount to scaled units for storage
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        (scaled-debt (mul-div-down debt-final INDEX-PRECISION borrow-index))
        ;; cap at current debt (prevent over-repayment)
        (scaled-to-remove (if (> scaled-debt curr-scaled) curr-scaled scaled-debt))
        (debt-to-repay (mul-div-up scaled-to-remove borrow-index INDEX-PRECISION))

        (coll-final (if (< scaled-to-remove scaled-debt)
                        (mul-div-down coll-actual scaled-to-remove scaled-debt)
                        coll-actual)))

      debt-to-repay: debt-to-repay,
