### Title
Aggregator gRPC server installs a no-op auth interceptor when `client_verification=false`, letting unauthenticated callers invoke `InternalSendTx` and broadcast attacker-chosen transactions - ([File: core/src/servers.rs])

### Summary
`create_grpc_server` chooses the TLS/interceptor configuration purely from `config.client_verification`; when that flag is `false` it installs `Interceptors::Noop`, which returns `Ok(req)` for every request with no identity check at all. Because the aggregator is documented to run with `client_verification=false`, its `ClementineAggregatorServer` — including the `Internal*` methods such as `InternalSendTx` — is reachable by any TCP client with no certificate.

### Finding Description
The binding claimed to hold is: `caller_identity_required_by_proto_doc('InternalSendTx') == caller_identity_actually_enforced_by_Interceptors::Noop`. Tracing the code shows this is false.

In `create_grpc_server` [1](#0-0) , the TLS config and the interceptor are both derived from `config.client_verification`. When it is `false`, `ServerTlsConfig` is built with only the server identity (no `client_ca_root`), and the wrapped service uses `Noop` instead of `OnlyAggregatorAndSelf`. `Interceptors::call` for `Noop` unconditionally returns `Ok(req)` [2](#0-1) , so no certificate, no `is_internal` check, and no `only_aggregator_and_self` comparison ever runs for that connection — the `is_internal`/leaf-cert equality check in `only_aggregator_and_self` [3](#0-2) [4](#0-3)  is entirely bypassed since that code path is never entered.

`create_aggregator_grpc_server` only emits a `tracing::warn!` when `client_verification` is *enabled*, and otherwise calls `create_grpc_server` with the same config, so the aggregator's `ClementineAggregatorServer` (exposing `Setup`, `NewDeposit`, `Withdraw`, `OptimisticPayout`, `InternalSendTx`, `SendMoveToVaultTx`, `InternalGetEmergencyStopTx` per `core/src/rpc/aggregator.rs`) is served with the `Noop` interceptor whenever `client_verification=false` [5](#0-4) . There is no additional authorization check inside the `Aggregator` service implementation itself — the only gate for "internal" methods is the interceptor, which does not run.

### Impact Explanation
Any unauthenticated TCP client that can reach the aggregator's gRPC port can call `InternalSendTx` (and other exposed methods) directly, causing the aggregator's tx-sender/fee-payer wallet to broadcast an attacker-chosen transaction, or drive other state-changing aggregator flows (`Setup`, `NewDeposit`, `Withdraw`, `OptimisticPayout`, `SendMoveToVaultTx`, `InternalGetEmergencyStopTx`) with no proof of identity. This matches the "High" category: an unauthenticated state-changing or broadcasting call. It is repeatable per request and not scoped to a single deposit/operator — every call the aggregator accepts is affected while `client_verification=false`.

### Likelihood Explanation
The only precondition is the aggregator running with `client_verification=false`, which the codebase's own comment/warning logic treats as the expected/default operating mode (the warning fires only when verification is *on*, implying off is the normal path) [6](#0-5) . No key material, certificate, or prior session is required by the attacker — only network reachability to the TCP port, which matches the attacker capabilities defined in scope (send requests to the aggregator's public gRPC port). This is highly feasible and does not require any Bitcoin transaction cost to trigger the exposure itself.

### Recommendation
Do not tie authentication solely to `client_verification`; enforce the `Interceptors::OnlyAggregatorAndSelf` check (or an equivalent mandatory caller-identity check) unconditionally for all `Internal*`/state-mutating RPCs regardless of the TLS client-verification setting, or require `client_verification=true` as a hard invariant for aggregator/operator/verifier servers rather than an optional, silently-defaulted-off configuration flag.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
