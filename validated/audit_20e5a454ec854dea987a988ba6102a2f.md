### Title
Scanner credits sub-dust outputs that can never be economically spent — funds reported received that are unspendable - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_transaction` / `scan_block` match outputs **only** on `script_pubkey` and return a `ReceivedOutput` for any value, including outputs of 1 sat or any amount below the dust threshold / below the marginal fee needed to spend the input. There is no minimum-value check anywhere in the scan path. This is the direct analog of the Notional rounding issue: a depositor "deposits" value that the vault credits, but the credited amount is worth zero (or negative) to the vault — the Bitcoin-side equivalent of depositing assets and receiving no usable shares.

### Finding Description
The scanner builds a `HashMap<ScriptBuf, Scalar>` of recognized scripts (`Scanner::new`, `register_offset`) and `scan_transaction` pushes a `ReceivedOutput` for every output whose `script_pubkey` matches — with no check on `output.value`:

```rust
// networks/bitcoin/src/wallet/mod.rs
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
}
```

Meanwhile, the spend path in `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`) enforces `DUST = 546` on *payments* and requires `input_sat >= payment_sat + needed_fee`, where `needed_fee = fee_per_vbyte * vbytes` grows ~58 vbytes per input. An output worth less than the fee its own input consumes (e.g., 1 sat, or anything under ~`58 * fee_per_vbyte` sats):

- cannot fund any payment (`DustPayment` if it were used as a payment amount; `NotEnoughFunds` if it's the sole input), and
- consumes more fee than it contributes when bundled with other inputs — including it strictly *decreases* the value of any transaction that spends it.

So the output is credited/reported as received value while being permanently unspendable at any positive fee rate, and negatively-valued (a liability) at fee rates above `value / 58` sats/vbyte. The `ReceivedOutput::read` deserialization path likewise has no value check, so such outputs persist through serialization and are indistinguishable from real deposits downstream.

### Impact Explanation
Any unprivileged party can craft a Bitcoin transaction paying a tiny amount (down to 1 sat, or any below-dust amount) to the multisig's P2TR `script_pubkey`. The scanner reports it as a received output. If the credited amount is propagated as a balance (the intended use of `ReceivedOutput::value()`), the system credits the sender for coins the multisig can never recover — minting/issuing value against unspendable dust. Repeating this also poisons the input set with negative-value UTXOs that, if selected by `SignableTransaction::new`, silently increase the fee paid by the multisig (the leftover change path at `send.rs:224-235` absorbs the difference).

### Likelihood Explanation
Trivially reachable: it requires only sending a standard Bitcoin transaction to a known, public multisig address — the exact public input the scanner exists to consume. No validator cooperation, no malformed encodings, no race conditions. Cost to the attacker is bounded by the dust amount itself (a few hundred sats per polluted UTXO).

### Recommendation
Enforce a minimum value in the receive path, mirroring the `DUST` constant already used on the send path: have `Scanner::scan_transaction` skip outputs with `output.value.to_sat() < DUST` (or better, `value < marginal_input_fee` at the prevailing fee rate), and have `ReceivedOutput::read` reject sub-threshold outputs so previously-scanned dust cannot be re-ingested. This is the "revert if minted shares == 0" fix applied to the Bitcoin input side: refuse to acknowledge deposits whose value cannot cover their own spend cost.

### Proof of Concept
1. Compute the multisig's `script_pubkey` via `p2tr_script_buf(group_key)`.
2. Broadcast a transaction with an output `{ value: 1 sat, script_pubkey }` to that address.
3. `Scanner::scan_transaction(&tx)` returns `ReceivedOutput { offset: Scalar::ZERO, value: 1, ... }` — the deposit is "received".
4. `SignableTransaction::new(vec![output], &payments, change, None, fee_per_vbyte)` returns `Err(NotEnoughFunds)` since `input_sat (1) < payment_sat + needed_fee`. Bundling it with other inputs adds ~58 vbytes × `fee_per_vbyte` sats of fee against 1 sat of value — strictly a loss.
5. The credited sat is permanently locked; the depositor obtained credit for value that cannot leave the vault, and each such UTXO is a fee liability if ever selected.

Caveat: the final crediting decision (turning a `ReceivedOutput` into a minted balance) lives in the processor, which is outside the indexed in-scope crates; the in-scope root cause is that the scanner/`ReceivedOutput` layer provides no minimum-value guarantee, and the wallet layer itself defines `DUST` yet never applies it on receipt — leaving the gap for any integrator that consumes `scan_transaction` directly.
