### Title
Copilot conflict-marker parsing can silently absorb and discard user file content when a malicious repository contains decoy `<<<<<<<`-like text - (File: app/src/lib/copilot-conflict-context.ts, app/src/lib/copilot-conflict-resolution.ts)

### Summary
Both `extractConflictHunks` (used to build the prompt/count expected hunks) and `reassembleResolvedFile` (used to splice the model's output back into the file) scan a conflicted file line-by-line for `<<<<<<<` / `=======` / `>>>>>>>` markers using a naive forward search, with no way to distinguish a genuine merge-conflict marker from marker-like text that already exists in tracked file content (e.g. in a string literal, comment, or documentation about git).

### Finding Description
`extractConflictHunks` walks the file and, upon finding an "ours" marker, keeps consuming subsequent lines until it finds the next separator/base marker and then the next "theirs" marker — regardless of how far away they are or whether they "belong" to that opening marker. [1](#0-0) 

`reassembleResolvedFile` performs the identical kind of unbounded forward lookahead when splicing the model's resolved content back into the original file, treating everything from the "ours" marker to the next matching separator/closing marker as a single conflict block to be replaced wholesale. [2](#0-1) 

Because a repository under an attacker's control (a fork or branch a user merges/rebases from) can freely contain a file whose *non-conflicted* content happens to include a stray `<<<<<<<`-shaped line (for example a code sample about git conflict markers, or a crafted comment), that decoy line will be picked up by both functions as the start of a conflict block. Both functions will then advance forward past the attacker's decoy content into a real conflict elsewhere in the file and treat the whole span — including legitimate, non-conflicted code the user never intended to touch — as one indivisible hunk. `validateResolutionPaths` only checks that the *number* of hunks returned by the model matches the number `extractConflictHunks` computed; since both parsers agree on hunk *count* in this scenario, the mismatch is never caught. [3](#0-2) 

The model then receives a corrupted view of "ours"/"theirs" content for that hunk (which actually contains a mix of real user code and the real conflict), and its single `resolvedContent` for that hunk is spliced in place of the *entire* absorbed span when the resolution is written to disk. [4](#0-3) 

### Impact Explanation
This results in silent corruption of what the user ultimately commits and pushes: legitimate, non-conflicted code between the decoy marker and the real conflict can be deleted or rewritten without any error, warning, or visual conflict indicator, since the operation is reported as a normal successful AI-assisted resolution. This matches the impact criteria for "silent corruption of what the user commits or pushes," directly caused by attacker-controlled content in a cloned/fetched repository.

### Likelihood Explanation
Likelihood is moderate: it requires (1) the user to opt into "Resolve with Copilot," (2) a file that legitimately conflicts during a merge/rebase/cherry-pick, and (3) that same file (on either side of history) to contain marker-shaped text that isn't a real conflict marker. Codebases that discuss or test git tooling, or that embed example diffs/conflict markers in fixtures, docs, or string literals, are realistic vectors for an attacker to smuggle such decoy content in without it looking suspicious. There is precedent for this exact bug class already having caused data loss in this feature (see the changelog fix for "Copilot conflict resolution data loss where file content outside conflicted regions was overwritten," 3.5.13-beta3), which suggests the marker-parsing logic in this area is fragile and prone to exactly this class of mismatch. [5](#0-4) 

### Recommendation
Make hunk boundary detection structurally identical and unambiguous in both `extractConflictHunks` and `reassembleResolvedFile` — e.g., require that an "ours" marker's matching "theirs" marker be the *nearest* one with no intervening unmatched "ours" marker, and validate that the byte-offsets/line-ranges (not just counts) of hunks used to build the prompt exactly match the ranges used to splice results back in. Consider also requiring `git` itself (via `checkConflicts` machinery) to be the sole source of truth for conflict boundaries rather than re-parsing raw markers twice with two independently-written scanners.

### Proof of Concept
1. Attacker maintains a branch/fork containing a file, e.g. `docs/conflict-example.md`, with content such as:
```
Example of a git conflict marker:
<<<<<<< example
some sample text that is not a real conflict
=======
```
   placed *before* an area of the file that will later genuinely conflict when merged.
2. Victim merges/rebases this branch into their repository; git reports a real conflict further down in the same file, producing genuine `<<<<<<< HEAD ... ======= ... >>>>>>> branch` markers after the decoy text.
3. Victim clicks "Resolve with Copilot." `extractConflictHunks` starts at the decoy `<<<<<<<` line and, finding no real closing marker nearby, keeps consuming lines until it hits the real `=======`/`>>>>>>>` pair from the genuine conflict further down, merging the decoy region and the real conflict (plus any intervening legitimate code) into a single reported hunk.
4. The model resolves what it believes is one hunk; `validateResolutionPaths` only checks hunk *count*, which matches.
5. `reassembleResolvedFile` performs the same forward-scan and splices the model's single resolution across the same absorbed span, discarding all of the victim's legitimate code that fell between the decoy marker and the real conflict — silently, with no error or visual diff review forcing the user to notice, before the file is written and staged. [6](#0-5)

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
