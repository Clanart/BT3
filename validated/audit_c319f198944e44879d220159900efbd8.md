### Title
Malicious HTTP `WWW-Authenticate` response header can force GitHub Desktop's credential helper to treat an arbitrary attacker-controlled host as a trusted GitHub Enterprise endpoint - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`PasswordStore::setPassword` failed because it trusted an unauthenticated caller to set a security-sensitive value with no ownership check. The Desktop analog is `getEndpointKind` in the credential-helper trampoline, which trusts an unauthenticated, attacker-controlled signal — an HTTP response header from the remote Git server — to decide whether a host should be treated as "enterprise" (a first-party GitHub/GHE endpoint), instead of verifying that the host is actually a GitHub-owned host.

### Finding Description
When Git needs credentials for a remote, it invokes Desktop's credential helper (`createCredentialHelperTrampolineHandler`) with data captured from the HTTP exchange, including any `WWW-Authenticate` headers the *remote server* sent back. `getEndpointKind` uses this attacker-controlled header content as a "happy path" classification signal: [1](#0-0) 

If a server the user is fetching/cloning from (which can be any arbitrary git remote URL configured by a repository, e.g. a spoofed/typosquatted host, an untrusted fork's remote, or a malicious proxy sitting in the request path) returns `WWW-Authenticate: realm="GitHub"`, this function immediately classifies the endpoint as `'enterprise'` — with **no verification that the host is actually a GitHub-owned domain** — before falling through to the `isGitHubHost` network check that exists later in the function: [2](#0-1) 

That classification is then used in `getCredential` to decide the trust path: [3](#0-2) 

Because `endpointKind !== 'generic'` and no existing account matches, Desktop calls `ui.promptForGitHubSignIn(endpoint)` for the attacker's arbitrary endpoint. That, in turn, calls `dispatcher.beginEnterpriseSignIn` / `setSignInEndpoint(origin)` using the attacker's origin verbatim and shows a `SignIn` popup labeled as a legitimate "GitHub Enterprise" authentication flow: [4](#0-3) 

The only real safeguard — `validateURL` in `enterprise-validate-url.ts` — merely checks that the URL uses `https:` and is syntactically valid; it does not verify the target is a genuine GitHub/GHE instance: [5](#0-4) 

The broken invariant: "only a verified GitHub/GHE host should be routed into the enterprise sign-in / OAuth flow" — analogous to "only the owner should set the password" — is not enforced. An unauthenticated response header from the remote is sufficient to flip the trust classification, similar to how `setPassword` had no `msg.sender == s_owner` check.

### Impact Explanation
An attacker who controls (or man-in-the-middles, or gets a victim to add) a git remote/proxy can trigger Desktop's Enterprise sign-in / OAuth flow against a domain of their choosing by simply returning a crafted `WWW-Authenticate` header on an authentication challenge. Consequences:
- The victim is presented with what looks like a legitimate GitHub Enterprise sign-in prompt bound to the attacker's origin, which can be used to phish OAuth credentials, or lead to an "Enterprise account" being bound to an attacker-controlled endpoint (`setSignInEndpoint(origin)` sets `this.state.endpoint` for the subsequent OAuth exchange).
- This satisfies the report's valid-impact category of "unauthorized OAuth or account binding" resulting from an attacker-controlled git remote/proxy response, without requiring local access, admin rights, or leaked credentials — only a git remote the user fetches from.

### Likelihood Explanation
Moderate. The classification is a "happy path" shortcut explicitly intended to avoid a network round-trip (`isGitHubHost`) — the code comment itself acknowledges it is a heuristic, not a proof. Any HTTP(S) git server the victim adds as a remote (including a compromised or malicious fork host, or a MITM-capable network proxy for a non-HTTPS-pinned connection) can return this header on a 401 challenge during a normal `fetch`/`clone`/`push`, which is a very ordinary part of Git-over-HTTP’s authentication protocol. No unusual user action is needed beyond the app performing a routine fetch/clone against that remote.

### Recommendation
Do not use the `WWW-Authenticate` header alone as sufficient evidence to classify a host as an `enterprise` (trusted GitHub) endpoint. At minimum:
- Require the `isGitHubHost(endpoint)` network verification (which independently probes the host) to succeed before trusting a non-`github.com`/`ghe.com` host as "enterprise", even when a `WWW-Authenticate: realm="GitHub"` header is present.
- If the header-based heuristic is kept for UX/performance reasons, still show the user the literal endpoint origin prominently and warn if it does not match a previously known/verified GitHub Enterprise host, before initiating any `SignIn`/OAuth flow.

### Proof of Concept
1. Set up an HTTP(S) server at an attacker-controlled domain, e.g. `https://attacker.example`.
2. Configure the server to respond to Git's credential probe (a request without credentials) with HTTP 401 and header `WWW-Authenticate: realm="GitHub"`.
3. In GitHub Desktop, add/clone/fetch a repository whose remote URL points at `https://attacker.example/some/repo.git`.
4. Git invokes the trampoline credential helper's `get` command; `getEndpointKind` sees the `wwwauth[...]` entry containing `realm="GitHub"` and returns `'enterprise'` for `attacker.example`, per [6](#0-5) .
5. Since no account exists for `attacker.example`, `getCredential` calls `ui.promptForGitHubSignIn('https://attacker.example/...')`, which starts an Enterprise sign-in flow bound to `attacker.example` and shows a "GitHub sign in" popup, per [4](#0-3) .

Note: I was not able to execute this end-to-end in a live environment (no filesystem/terminal access here), so the flow above is derived directly from reading the referenced source files; a Devin session with repo/build access would be needed to run and confirm the PoC interactively.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}
