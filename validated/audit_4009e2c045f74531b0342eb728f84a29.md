### Title
Panic on unregistered participant index in PedPoP blame path (`HashMap` index on `enc_keys` / `commitments`) - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2023-6683 is a use-before-initialization NULL dereference: `qemu_clipboard_request()` could be invoked before the VNC clipboard peer was initialized, and dereferencing the uninitialized pointer crashed the daemon.

The Serai analog is `Decryption::decrypt_with_proof` in `crypto/dkg/pedpop/src/encryption.rs:388`. It dereferences `self.enc_keys[&decryptor]` via `HashMap`'s `Index` impl, which panics when the key is absent. `enc_keys` is only populated by `Decryption::register` (encryption.rs:351-362), i.e., the "initialized" state. Any code path that reaches `decrypt_with_proof` with a `decryptor` that was never registered hits the equivalent of a NULL/uninitialized dereference and panics the host process. The same pattern exists at `crypto/dkg/pedpop/src/lib.rs:599` (`self.commitments[&sender]`).

### Finding Description
`blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575-609`) is reachable through two public APIs:

- `BlameMachine::blame(sender, recipient, msg, proof)` (lib.rs:623-632)
- `AdditionalBlameMachine::blame(sender, recipient, msg, proof)` (lib.rs:674-682), where `AdditionalBlameMachine::new` is explicitly designed for non-participants evaluating blame.

Neither function validates that `sender`/`recipient` are within `1 ..= n`. `Participant::new` accepts any nonzero `u16` (up to 65535), while `enc_keys`/`commitments` only contain `1 ..= n`. To reach the panicking line, the caller must supply:

- a `msg` whose `pop` Schnorr signature verifies against `pop_challenge` (encryption.rs:374-379) — freely constructible by anyone holding a key, or reusable from a real DKG share message, and
- `proof: Some(EncryptionKeyProof)` so execution reaches line 388, `&[self.enc_keys[&decryptor], *proof.key]`, where `decryptor = recipient = Participant(n + 1)` → panic (key not found).

If `proof` is `None`, `blame_internal` returns early (encryption.rs:394-396). Alternatively, with a valid `proof` and `decryptor` present but `sender > n`, execution proceeds to `self.commitments[&sender]` at lib.rs:599 and panics there instead. Notably, the DLEq verification at lines 383-390 does not run before the `enc_keys` lookup — the lookup itself is the first use of `decryptor`, so no valid proof is actually required to reach the panic if the signature check passes: `decrypt_with_proof` indexes `enc_keys[&decryptor]` *inside* the arguments to `dleq.verify`, before any proof validity is established.

This mirrors the CVE exactly: a routine is reachable with attacker-supplied identifiers before the referenced state (the per-participant encryption-key entry) was ever initialized, producing a crash instead of an error.

### Impact Explanation
A panic in `blame`/`AdditionalBlameMachine::blame` aborts the calling process. For a coordinator/processor evaluating blame accusations during a PedPoP DKG (or an external observer using `AdditionalBlameMachine` to adjudicate accusations), submitting an accusation naming a `recipient` or `sender` index outside `1 ..= n` crashes the node rather than returning a blame verdict or an error. This is a denial of service matching the CVE's impact class (authenticated-party-triggered crash; CVSS 6.5, A:H).

### Likelihood Explanation
The panic requires the caller to route an accusation with an out-of-range `Participant` into `blame()`. `Participant` is a plain `u16` newtype with no upper bound enforced at construction (`Participant::new` only rejects 0), and neither `blame_internal` nor its callers bounds-check `sender`/`recipient` against `n`. Any integration that forwards accusation parameters derived from unauthenticated or peer-supplied data (validator index, session index) reaches the panic directly. Confidence is somewhat reduced because reachability depends on the surrounding orchestration feeding arbitrary participant indexes into `blame`, which lives outside the in-scope crates; within the library itself the panic is unconditional once reached.

### Recommendation
Replace the panicking `HashMap` index operations with fallible lookups:

- In `Decryption::decrypt_with_proof` (encryption.rs:388), use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` (or a dedicated `UnknownParticipant` error).
- In `blame_internal` (lib.rs:599), use `self.commitments.get(&sender)` and return a defined result (e.g., blame `sender`, or error) when absent.
- Additionally, bound-check `sender` and `recipient` in `BlameMachine::blame` / `AdditionalBlameMachine::blame` against `1 ..= n` before processing, since a `Participant` outside the set is meaningless.

### Proof of Concept
```rust
// In-scope crates: dkg, pedpop, ciphersuite (e.g. C = Ristretto)
// Assume an honest 2-of-3 DKG completed, yielding `blame_machine` /
// or build an external adjudicator:
let mut msgs: HashMap<Participant, EncryptionKeyMessage<Ristretto, Commitments<Ristretto>>> =
    /* the three authenticated round-1 commitment messages */;
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, msgs).unwrap();

// Attacker-controlled accusation: recipient index 4 was never registered (n = 3)
let sender = Participant::new(1).unwrap();
let recipient = Participant::new(4).unwrap(); // valid Participant, > n

// `msg` = any EncryptedMessage whose `pop` Schnorr signature verifies
// (e.g. a real share message relayed with attacker-chosen indexes).
// `proof` = Some(arbitrary EncryptionKeyProof::read(...) bytes);
// its DLEq proof is never checked before the panic.
machine.blame(sender, recipient, msg, Some(proof));
// PANIC at crypto/dkg/pedpop/src/encryption.rs:388:
//   self.enc_keys[&decryptor]  -> HashMap index panic (key not found)
// Equivalently, with recipient in-range but sender = Participant(4),
// panic occurs at crypto/dkg/pedpop/src/lib.rs:599 (self.commitments[&sender]).
```

Analogous to CVE-2023-6683, the fix is to ensure the lookup cannot execute on state that was never initialized — i.e., treat an absent `enc_keys`/`commitments` entry as a defined error rather than relying on `Index` semantics that panic.
