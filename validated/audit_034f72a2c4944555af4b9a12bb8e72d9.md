### Title
Payout OP_RETURN operator attribution is malleable via `SIGHASH_SINGLE|ANYONECANPAY`, letting anyone rewrite who gets credited for a fronted withdrawal - (File: `core/src/verifier.rs`, `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` builds the payout transaction so that the user's signature (`SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`) only commits to `input[0]` and `output[0]`, leaving all other inputs and outputs — including the OP_RETURN that encodes the fronting operator's x-only pubkey — completely unconstrained. `update_finalized_payouts` in `verifier.rs` trusts whatever OP_RETURN ends up in the block-confirmed transaction as the sole source of truth for "which operator fronted this withdrawal," with no cross-check against who actually supplied the non-input0 funding.

### Finding Description
The binding the system relies on is:
`stored payout_payer_operator_xonly_pk[withdrawal_idx] == xonly_pk(operator who funded output[0] of the mined payout tx)`

Tracing the code:

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds `payout_tx` with `output[0]` = user payout, `output[1]` = anchor, `output[2]` = `op_return_txout(operator_xonly_pk.serialize())`, and signs only `input[0]` with the user-supplied `taproot::Signature` via `set_p2tr_key_spend_witness`.
- `Operator::withdraw` (`core/src/operator.rs:560-637`) verifies this user signature with `SECP.verify_schnorr` over the taproot sighash of `input[0]` computed with `in_signature.sighash_type` — intended to be `SinglePlusAnyoneCanPay`, per the doc comment and error message at line 637. Under BIP341/342, `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` commits only to the signed input and the single output at the same index (`output[0]`); it commits to **no other input and no other output**.
- The operator funds the transaction via `fund_raw_transaction` (`core/src/operator.rs:652-674`), adding operator-owned inputs/change, but none of this is bound by the user's signature.
- `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) scans the confirmed block, locates the payout tx via `get_payout_txs_for_withdrawal_utxos`, and derives the credited operator purely from `get_first_op_return_output` + `parse_op_return_data` + `XOnlyPublicKey::from_slice` on whatever is in the mined transaction's OP_RETURN (`core/src/verifier.rs:2314-2321`), then persists it via `update_payout_txs_and_payer_operator_xonly_pk`.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:41-47`) only acts on withdrawals returned by `get_first_unhandled_payout_by_operator_xonly_pk(operator_xonly_pk)` — i.e., only for the operator whose pubkey is currently stored for that withdrawal index.

Because `input[0]`'s witness and `output[0]` are the only signature-covered elements, an attacker can copy them verbatim into a new transaction, attach their own ANYONECANPAY-compatible funding input(s), replace `output[2]`'s OP_RETURN payload with arbitrary/garbage 32 bytes, and relay it with a higher fee so it replaces (via RBF or straightforward mempool/miner competition) the honest operator's broadcast before confirmation. None of the existing guards intervene: `Verifier::is_deposit_valid`, `SECP.verify_schnorr` (only checks input0/output0, which are unchanged), `is_kickoff_malicious` (only runs later, at kickoff time, and only checks whatever `operator_xonly_pk` is already stored from the OP_RETURN — it does not independently verify who funded the tx), and `SPV::verify`/`verify_storage_proofs` in the bridge circuit only check the withdrawal outpoint reference, not the OP_RETURN funding attribution. No component reconciles "who supplied the top-up/fee inputs" against "whose pubkey appears in OP_RETURN."

### Impact Explanation
The confirmed payout tx now either credits no operator (`None`, if the garbage bytes fail `XOnlyPublicKey::from_slice`) or an attacker-chosen pubkey, while the honest operator who actually intended to (and, in a race, may partially have) front the withdrawal is never recorded. `get_first_unhandled_payout_by_operator_xonly_pk` will never surface this withdrawal for the honest operator, so `handle_finalized_payout`/`mark_payout_handled` never run for them, and the withdrawal can never be advanced to `Reimburse` on their behalf — matching the Critical category "an honest operator permanently unable to be reimbursed." The withdrawal itself is fulfilled to the user, but the specific operator that would have earned the corresponding move-to-vault reimbursement is permanently locked out for that deposit/withdrawal pair. This is repeatable per withdrawal/operator, since it stems from the inherent BIP341 semantics of `SIGHASH_SINGLE|ANYONECANPAY`, not a one-off bug.

### Likelihood Explanation
Preconditions: an honest operator must broadcast their `payout_tx` for a real, finalized Citrea withdrawal, and the attacker must observe it in the mempool before confirmation and win a fee race (their tx must confirm instead). The attacker must front real BTC equal to the withdrawal's shortfall (comparable to what the honest operator would have paid) to keep `output[0]` intact and get their replacement mined — a materially costly attack per attempt, and the operator's own automated fee-bumping (if implemented) could make winning the race economically unattractive to the attacker. No key compromise, majority hashrate, or privileged access is required — only mempool visibility, standard RBF, and sufficient fee capital, all within the stated attacker capabilities (broadcasting transactions, paying fees, choosing a script/OP_RETURN).

### Recommendation
Bind the payout's OP_RETURN to the signed portion of the transaction, or otherwise make operator attribution tamper-evident/unforgeable, e.g.: have the operator's own signature (not just the user's) cover the entire transaction including the OP_RETURN output (operator signs with `SIGHASH_ALL` over their funding inputs and all outputs), or require `update_finalized_payouts`/`is_kickoff_malicious` to additionally verify that the extra funding inputs of the mined payout tx are provably controlled by the pubkey claimed in the OP_RETURN (e.g., checking a signature from that key over the whole tx), rather than trusting an unauthenticated OP_RETURN byte string.

### Proof of Concept
`cargo test` (regtest, `core/src/test`) plan:
1. Set up a finalized deposit with move_txid `M`, register a Citrea withdrawal index `i` pointing to outpoint `O`.
2. Have the honest operator (`operator_pk`) call `withdraw`, producing `payout_tx_honest` (via `create_payout_txhandler`) with `output[2]` OP_RETURN = `operator_pk`; broadcast it but do not mine it.
3. Construct `payout_tx_attacker`: copy `input[0]` (same witness/prevout) and `output[0]` verbatim from `payout_tx_honest`; add a new funding input from an attacker-controlled UTXO; replace `output[2]` with OP_RETURN containing 32 attacker-chosen bytes (garbage, not a valid xonly pubkey); set a higher fee.
4. Broadcast `payout_tx_attacker` and mine it (ensuring `payout_tx_honest` is evicted/never confirms).
5. Run the block-finalization path (`Verifier::handle_finalized_block` → `update_finalized_payouts`).
6. Assert: `db.get_first_unhandled_payout_by_operator_xonly_pk(operator_pk)` returns `None` for withdrawal `i`, while a direct query of `get_payout_txs_for_withdrawal_utxos`/`get_payout_info_from_move_txid` shows the withdrawal is finalized with `operator_xonly_pk = None` (or an unrelated pubkey), demonstrating `stored payout_payer_operator_xonly_pk[i] != operator_pk` despite `operator_pk` being the party who constructed and intended to front `output[0]`.
