## Title
Confused-deputy in the bank precompile's `send` — pointer contract can move funds on behalf of an arbitrary `from` address if allowance/approval validation is bypassed - ([File: precompiles/bank/bank.go])

### Summary
The PrismaFi exploit was a confused-deputy bug: `MigrateTroveZap.onFlashloan()` accepted an attacker-controlled target address and performed privileged actions (`closeTrove`/`openTrove`) on that arbitrary address without validating that the caller was authorized to act on it. The Sei bank precompile's `send()` function exhibits the same structural pattern: it accepts an arbitrary `from` address parameter and moves real bank-module coins from that address, trusting the caller (an ERC20-native-pointer contract) to have already validated authorization (ERC20 allowance) before invoking it.

### Finding Description
`precompiles/bank/bank.go`'s `send` function only checks that `caller` equals the denom's registered pointer contract, then blindly executes a `MsgSend` from an arbitrary `senderSeiAddr` decoded from `args[0]`: [1](#0-0) 

The precompile itself performs no allowance/ownership check on the `from` address — it delegates that responsibility entirely to the calling pointer contract. The reference pointer implementation, `NativeSeiTokensERC20`, relies on OpenZeppelin `ERC20._update`, which is invoked from `transferFrom` (which does perform `_spendAllowance`) as well as from `transfer` — and critically, `_update` itself calls `BankPrecompile.send(from, to, denom, value)` directly with the `from` parameter forwarded, with the correctness of `from` resting entirely on the OpenZeppelin base-contract's internal call-site validation: [2](#0-1) 

This is architecturally identical to the PrismaFi flaw: a single trusted "deputy" contract (the pointer, analogous to `MigrateTroveZap`) is granted a privileged capability (moving funds from any address) by the underlying system (bank precompile, analogous to `TroveManager`), and the security of every account's funds hinges entirely on that one deputy contract never being tricked into executing `send`/`_update` with a caller-supplied `from` it hasn't verified. Any custom pointer contract deployed via `AddNativePointer` (see `precompiles/pointer/legacy/v610/pointer.go`) inherits this same trust requirement — if a future/alternate pointer implementation's `transfer`/`transferFrom`/callback logic has a validation gap (e.g., missing `_spendAllowance`, a reentrancy path, or a callback that lets an attacker supply an arbitrary `from`), the bank precompile provides no defense-in-depth and will move any account's coins.

### Impact Explanation
If a pointer contract registered against a native denom has any authorization-check gap in its transfer path, the bank precompile will execute unauthorized `MsgSend` transfers of that denom from arbitrary Sei accounts, directly resulting in fund loss — the same class of impact as the $11.6M PrismaFi loss (confused deputy draining arbitrary users' collateral).

### Likelihood Explanation
Likelihood is bounded by the correctness of the pointer contract's own authorization logic, since the precompile itself performs no independent check that `caller` was actually authorized by `senderSeiAddr` to move funds — it only checks that `caller` is the registered pointer. The shipped `NativeSeiTokensERC20` pointer relies on OpenZeppelin's own well-audited allowance/`_update` invariants, which reduces the likelihood in the current code today, but the precompile's design does not independently enforce this: any new pointer type or an upgrade to `NativeSeiTokensERC20` that introduces a callback, batch-transfer, or migration-style function analogous to `MigrateTroveZap` could reintroduce exactly this bug class without the bank precompile catching it.

### Recommendation
Add defense-in-depth at the precompile boundary: require `send()`/`_update`-style calls to only move funds where `senderSeiAddr` resolves to `caller`'s associated Sei address, or explicitly pass and verify an allowance/authorization proof (already-spent-allowance receipt) at the precompile layer rather than trusting the calling contract's internal bookkeeping unconditionally.

### Proof of Concept
Not directly reproducible against the current shipped `NativeSeiTokensERC20` pointer, because its `_update` path is only reached through OpenZeppelin `ERC20.transfer`/`transferFrom`, both of which correctly gate on `msg.sender`/allowance before calling `_update(from, to, value)`. The vulnerability is a latent architectural gap in `precompiles/bank/bank.go`'s `send` (no independent `from`-authorization check), which would be directly exploitable by any current or future pointer implementation, migration helper, or upgraded pointer logic that calls `BankPrecompile.send(from, to, denom, value)`/`_update` with an attacker-influenced `from` without first validating allowance — mirroring exactly how `MigrateTroveZap.onFlashloan()` let an attacker supply an arbitrary trove owner for `closeTrove`/`openTrove`.
