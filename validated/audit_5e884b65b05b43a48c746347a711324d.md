## Analysis Result

### Title
Data Layer mirror-coin URLs are unauthenticated attacker input that trigger outbound HTTP requests (SSRF) - (File: chia/data_layer/data_layer_wallet.py)

### Summary
Any wallet user can create a "mirror" coin that attaches an arbitrary `launcher_id` and arbitrary URL strings as memos, without any check that the creator owns or controls that `launcher_id`. When a Data Layer node that tracks that store id later syncs, it fetches URLs taken directly from those attacker-supplied memos via plain HTTP `GET`/plugin `POST` requests, with no allowlist or private-network restriction — a classic SSRF triggered purely by a spend bundle.

### Finding Description
The Data Layer "mirror" mechanism is implemented as a generic puzzle (`create_mirror_puzzle()` = `P2_PARENT.curry(1)`) that anyone can spend into by creating a coin with `CREATE_COIN` memos `[launcher_id, url1, url2, ...]`. `get_mirror_info()` extracts `launcher_id` and the URL list purely from the spend's memos, with no signature or ownership check tying `launcher_id` to the spender: [1](#0-0) 

`DataLayerWallet.coin_added()` observes any coin whose puzzle hash matches the mirror puzzle, decodes `launcher_id`/`urls` from the parent spend, and — as long as the local node happens to be tracking that `launcher_id` (e.g., because a user subscribed to that store) — stores the mirror URLs verbatim, with no validation of who created the coin: [2](#0-1) 

The Data Layer service pulls these wallet-tracked mirror URLs and treats them as sync servers with no filtering: [3](#0-2) 

During `fetch_and_validate()`, these URLs are randomized and then fetched: [4](#0-3) 

The actual outbound request has no SSRF protection — it directly performs an HTTP GET to `server_info.url + "/" + filename` (or, for downloader plugins, POSTs the raw URL string to a plugin), with only file-size limits and no host/IP allowlisting or blocking of private/link-local/metadata addresses: [5](#0-4) [6](#0-5) 

The module's own documentation explicitly notes mirror URLs are external, untrusted input, but this untrusted-input handling stops at "don't trust the *downloaded data*" — it does not address the request destination itself being attacker-controlled: [7](#0-6) 

### Impact Explanation
Any unprivileged party who can submit a spend bundle (i.e., anyone with a small amount of XCH to create the mirror coin) can force Data Layer nodes subscribed to a given `launcher_id` to make outbound HTTP requests to attacker-chosen URLs/hosts — including internal network addresses, localhost services, or cloud metadata endpoints (e.g., `169.254.169.254`) — whenever those nodes next sync that store. This is a genuine SSRF: the request destination is fully attacker-controlled and requires no interaction beyond publishing a mirror-coin spend bundle for a store id the target node is subscribed to. It can be used for internal network reconnaissance/pivoting or to trigger side effects on internal services reachable from the DataLayer host. This does not directly enable coin theft or consensus divergence, but it is a legitimate node-compromise vector via unauthenticated attacker input reaching outbound network I/O — consistent with a Medium-severity SSRF, matching the referenced CWE-918 report.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the attacker to know/target a `launcher_id` a victim's Data Layer node is subscribed to (subscriptions are typically public/discoverable since users must know a store id to subscribe), and (b) the victim's node to actually run the periodic sync loop (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`), which happens automatically for any subscribed store. No privileged access or malicious peer/node control is needed — an ordinary spend bundle submission suffices to plant the malicious mirror URL on-chain.

### Recommendation
- Validate mirror-coin `launcher_id` ownership/authorization before trusting attached URLs, or at minimum treat unverified mirror URLs as lower-trust and require explicit user opt-in per URL/host rather than automatic sync.
- Before issuing outbound requests in `http_download()` and `get_downloader()`/`download_file()`, resolve and validate the target host against an SSRF-safe allowlist (reject loopback, link-local, private, and multicast ranges; reject cloud metadata addresses; optionally require `https` and a domain allowlist for automatic mirror following).
- Consider requiring manual approval (RPC-side confirmation) before a newly-observed mirror URL for a subscribed store is added to the automatic sync list.

### Proof of Concept
1. Attacker crafts a spend bundle that creates a coin with puzzle hash `create_mirror_puzzle().get_tree_hash()` and `CREATE_COIN` memos `[victim_launcher_id, "http://169.254.169.254/latest/meta-data/", ...]`, using any of the attacker's own spendable coins (no relation to `victim_launcher_id` needed).
2. Attacker submits the spend bundle to the mempool; it is accepted since `create_mirror_puzzle()` is a generic, unrestricted puzzle (`P2_PARENT.curry(1)`), and the memo content isn't validated by consensus.
3. Once confirmed, any Data Layer node tracking `victim_launcher_id` (via `DataLayerWallet.coin_added()`) picks up the mirror record and, on its next sync cycle (`update_subscriptions_from_wallet` → `fetch_and_validate` → `http_download`/`get_downloader`), issues an outbound HTTP request to the attacker-controlled URL — demonstrating SSRF triggered entirely by an unprivileged spend bundle.

```python
def create_mirror_puzzle() -> Program:
    return P2_PARENT.curry(Program.to(1))


MIRROR_PUZZLE_HASH = create_mirror_puzzle().get_tree_hash()


def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
