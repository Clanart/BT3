## Title
Clone operation explicitly disables Git's built-in clone-hook protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: app/src/lib/git/clone.ts)

## Summary
The C4 report's core primitive is a trusted component (`operator`) that is allowed to trigger unrestricted, unguarded execution (`execute`) against attacker-influenced input. The GitHub Desktop analog is `clone()` in [1](#0-0) , which unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and passes `--recursive` for every clone, while never enabling the hook-interception/sandboxing path (`interceptHooks`) that every other Git-invoking operation in the app (`commit`, `merge`, `pull`, `push`) uses.

## Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced to guard against malicious repository content triggering hook execution during (recursive) clone operations. Desktop explicitly forces it to `'false'` for every clone: [2](#0-1) 

This clone call also always passes `--recursive`, meaning any submodules declared in the attacker-controlled remote repository are automatically initialized and checked out as part of the same operation: [3](#0-2) 

Crucially, unlike `commit.ts`, `merge.ts`, `pull.ts`, and `push.ts` — all of which set `interceptHooks` so that `withHooksEnv` swaps `core.hooksPath` to a sandboxed proxy directory before Git ever runs a hook — the clone options object `opts: IGitStringExecutionOptions = { env }` never sets `interceptHooks`: [4](#0-3) [5](#0-4) 

Because `opts.interceptHooks` is undefined for clone, `withHooksEnv` takes the early-return branch and runs the clone with the caller-supplied environment unmodified — Desktop's own hook sandbox is a no-op for this operation, and Git's own clone-time hook safeguard has been deliberately turned off via the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override.

The corrupted value here is the process environment passed to `dugite`'s `git clone --recursive` invocation, specifically the forced `GIT_CLONE_PROTECTION_ACTIVE=false`, which is attacker-reachable content only in the sense that the remote repository and its submodules being cloned are fully attacker controlled (the "cloned/fetched repository" object named in the Valid Impact section).

## Impact Explanation
If Git's clone-time hook protection exists specifically to stop repository content from causing hook execution during (recursive) clone, unconditionally disabling it for every Desktop-initiated clone reintroduces that execution path for any repository/URL a user clones or forks with Desktop — including public repos a user is merely browsing/cloning, not repos they already trust. Combined with `--recursive` and the total absence of Desktop's hook-interception sandbox for this code path, a malicious repository (directly or via a submodule) is positioned to have its hook-triggering content executed with the same protections as if the safeguard were absent, rather than the more restrictive posture Git itself ships with.

## Likelihood Explanation
Every single clone performed through Desktop's `clone()` function (`app/src/lib/git/clone.ts`) hits this code path unconditionally — there is no feature flag or opt-in check gating the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override, unlike other hardening in the file (`isClonePathSensitive`, `sanitizeCloneName`) which are conditionally applied guardrails. The likelihood is high for any user cloning an untrusted/attacker-supplied URL, which is a normal, expected Desktop workflow (cloning public repos, forks, or PR branches).

## Recommendation
- Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in [6](#0-5)  unless there is a verified, narrowly-scoped reason it must be disabled (e.g., a specific compatibility issue), and if so, gate it behind the same kind of safety checks already used elsewhere in this file (`isClonePathSensitive`).
- Route the `clone()` git invocation through the same `interceptHooks`/`withHooksEnv` sandboxing mechanism used by `commit.ts`, `merge.ts`, `pull.ts`, and `push.ts` so hooks introduced by cloned content (including submodules pulled in via `--recursive`) are proxied and subject to the same `onHookFailure`/`onHookProgress` controls.
- Add a regression test asserting that clone operations do not disable Git's clone-time protections and that hook execution during `git clone --recursive` is intercepted identically to other Git operations.

## Proof of Concept
1. Attacker publishes/serves a repository (top-level or as a `.gitmodules` submodule target) crafted to trigger hook execution during `git clone --recursive` under the conditions Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard is designed to block.
2. Victim uses GitHub Desktop's "Clone repository" (or "Clone with Desktop" deep link) feature to clone the attacker's URL.
3. `app/src/lib/git/clone.ts` builds the environment with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and invokes `git -c init.defaultBranch=... clone --recursive ... -- <url> <path>` via `git()` in `core.ts`, with no `interceptHooks` set, so `withHooksEnv` performs no sandboxing (`app/src/lib/hooks/with-hooks-env.ts:29-42`).
4. Because Desktop's clone-time invocation both disables Git's own protection and skips its own hook-proxy sandbox, the hook-triggering content in the attacker's repository (or a recursively-cloned submodule) executes with the same lack of restriction that existed before Git's clone-time hardening was introduced.

**Caveat**: I was unable to execute a live end-to-end PoC (e.g., against a specific vulnerable Git version/hook trigger sequence) within this environment; the analysis above is based on static code review of `app/src/lib/git/clone.ts`, `app/src/lib/hooks/with-hooks-env.ts`, and comparison against the hook-interception pattern consistently used in `commit.ts`/`merge.ts`/`pull.ts`/`push.ts`. Confirming exploitability would require testing against the specific Git version bundled with this Desktop build to verify the precise scenario `GIT_CLONE_PROTECTION_ACTIVE` guards against and whether it remains reachable when disabled.

  ]

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
