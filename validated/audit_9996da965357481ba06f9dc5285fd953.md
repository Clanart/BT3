### Title
FROST signing accepts `Participant(0)` in the signing set, injecting a non-existent signer into Lagrange interpolation - (File: crypto/frost/src/sign.rs)

### Summary
The Haven bug class is injection of attacker-controlled input into a sink that interprets it as trusted structure. The Serai analog lives in `AlgorithmSignMachine::sign`: the `included` set is built from attacker-supplied `preprocesses` map keys, and while it checks `> n` and duplicates, it never rejects `Participant(0)`, even though the crate's own error text defines valid participants as `0 < participant <= n`. A `Participant(0)` preprocess therefore passes all validation and is fed into `ThresholdKeys::view` / Lagrange interpolation and the binding-factor transcript.

### Finding Description
In `crypto/frost/src/sign.rs` (`sign`, lines 283-313), `included` is assembled from `self.params.multisig_params.i()` plus every key of the caller-provided `preprocesses` map, then sorted. The only bounds checks are:

- `included.len() < t` -> `InvalidSigningSet`
- `included.last() > n` -> `InvalidParticipant`
- adjacent equality -> `DuplicatedParticipant`

`included[0] == Participant(0)` satisfies all three: `0 <= n`, and it is distinct from honest indexes `1..=n`. `validate_map` (`crypto/frost/src/lib.rs` lines 50-72) also accepts it, since it only checks quantity, duplicates of `ours`, and presence in the map. The set is then passed to `self.params.keys.view(included)` (line 312), which interpolates verification shares and computes Lagrange coefficients using `u16::from(*l)` as the x-coordinate. Index 0 is not a valid share index (shares are issued at `1..=n`); the coefficient formula divides/multiples by `0 - x_j` terms producing a bogus interpolation weight, and `participant 0` is appended into the per-participant transcript (`append_message(b"participant", ...)`, lines 327-332) and into `B` (BindingFactor map), altering `rho`/`R` derivation for the whole session.

### Impact Explanation
An attacker-supplied preprocess keyed under `Participant(0)` corrupts the signing session: the `ThresholdView` is constructed over an impossible signer set, binding factors and `Rs` are computed with a phantom participant, and the aggregate signature either fails verification with blame misattributed to honest signers, or produces a signature over a view whose verification-share mapping no longer corresponds to the real DKG shares. Reachable purely through public inputs: untrusted bytes fed to `read_preprocess` under a chosen `Participant` key, matching the allowed reachability surface.

### Likelihood Explanation
Any party that can place an entry into the `preprocesses` map delivered to `sign` controls the key directly; no collusion or special position is required beyond submitting a preprocess under index 0. The missing lower-bound check is a single-line omission, and the crate's error message (`0 < participant <= n`) shows the intent was to reject it.

### Recommendation
In `AlgorithmSignMachine::sign`, after sorting `included`, reject `included[0] == Participant(0)` with `FrostError::InvalidParticipant(0, included[0])`, and/or enforce `Participant(u16)` nonzero at construction in the `dkg` crate so `Participant(0)` is unrepresentable.

### Proof of Concept
```rust
// sketch: n >= t honest participants 1..=n; attacker inserts preprocess under index 0
let mut preprocesses = HashMap::new();
preprocesses.insert(Participant::from(u16::MAX - 1) /* or raw 0 via deserialize */, forged);
// included becomes [0, i, ...] after sort; sign() proceeds past all checks
// view() interpolates shares at x=0, BindingFactor gets a rho for phantom participant 0
```
Note: exact exploitability depends on `Participant` constructors in `crypto/dkg` and how callers populate the map keys; I verified the missing zero-check in `sign` and `validate_map`, but did not confirm every upstream path that maps serialized input to `Participant` values within the iteration budget.
