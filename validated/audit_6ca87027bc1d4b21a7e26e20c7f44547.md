### Title
Sub-economical/dust outputs are reported as spendable wallet inputs with no per-input value or dust check, enabling forced transaction failure / withdrawal DoS — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The JOJO bug is a "zero-value action still mutates state and blocks a legitimate operation" flaw: `requestWithdraw` accepts `primaryAmount == secondaryAmount == 0` under a `>=` allowance check yet still bumps `withdrawExecutionTimestamp`, letting an attacker lock a user's withdrawals. The Serai analog lives in bitcoin-serai's wallet: `Scanner::scan_transaction`/`scan_block` register *any* output paying to a watched `script_pubkey` as a `ReceivedOutput` with no minimum-value test, and `SignableTransaction::new` accepts those as `inputs` while its only amount checks are on *payments* (`*amount < DUST → DustPayment`), never on inputs. An unprivileged party who dusts the public multisig address forces these uneconomical inputs into the withdrawal transaction, causing `NotEnoughFunds`/`TooLargeTransaction` or value-burning fees — a griefing/DoS of withdrawals reachable purely from attacker-sent Bitcoin transactions.

### Finding Description
- `Scanner::scan_transaction` pushes every output whose `script_pubkey` is in `self.scripts` into `res`, regardless of `output.value` — including zero-value or sub-dust outputs.
- `ReceivedOutput` serializes that value straight through (`read`/`write` perform no value validation).
- `SignableTransaction::new` rejects empty inputs, `NoOutputs`, and payments `< DUST`, but never checks that any `input.output.value` exceeds the marginal fee cost of spending it (~57 vbytes × `fee_per_vbyte`, per the commentary at send.rs L606–638). `input_sat` is summed blindly and `prevouts` are committed wholesale.
- Consequences in this code path: many attacker outputs → `weight > MAX_STANDARD_TX_WEIGHT` → `TooLargeTransaction`; or `input_sat < payment_sat + needed_fee` → `NotEnoughFunds`; or the tx is built spending more in fees than the dust is worth. Unlike FROST's `sign`, which validates the participant set before mutating signing state, there is no gate here.

### Impact Explanation
Funds are reported received (a `ReceivedOutput` the scanner yields) that are not economically spendable, and an attacker can permanently poison the input set used to build withdrawal transactions: enough dust inputs either exhaust `MAX_STANDARD_TX_WEIGHT`/input budgets or push `needed_fee` above `input_sat`, so every attempted spend errors out — matching the "DoS of withdrawals" impact class with attacker cost bounded by the dust value alone.

### Likelihood Explanation
The multisig's P2TR `script_pubkey` is publicly observable on-chain; any unprivileged party can broadcast transactions paying to it. `Scanner::scan_transaction` will pick every such output up on any value ≥ 0. Note: the out-of-scope processor wrapper filters `output.balance().amount.0 >= N::DUST` (10,000 sats), which mitigates this in the full system — but within the in-scope `networks/bitcoin/src` library API the flaw stands on its own, and the constant/`>=` boundary also means an output valued exactly at the filter still may not cover its marginal spend cost at high `fee_per_vbyte`.

### Recommendation
- Enforce a minimum input value in `SignableTransaction::new`: require each `ReceivedOutput`'s value ≥ `DUST` (and ideally ≥ the marginal fee to spend it, `57 * fee_per_vbyte` at the passed rate), returning a new `TransactionError::DustInput` otherwise.
- Alternatively/additionally, have `Scanner::scan_transaction` skip outputs below a configurable spendable threshold so sub-economical outputs never reach `SignableTransaction::new` as inputs — the mirror of "don't increment `withdrawExecutionTimestamp` when the amounts are zero."

### Proof of Concept
```rust
// Attacker broadcasts N transactions paying tiny amounts to the wallet's
// publicly known p2tr_script_buf(key). Then:

let mut scanner = Scanner::new(key).unwrap();
let mut dust_inputs = vec![];
for tx in attacker_txs {
    dust_inputs.extend(scanner.scan_transaction(&tx)); // every output accepted, no value check
}

// Victim withdrawal construction:
let res = SignableTransaction::new(
    dust_inputs,                                     // includes 1..330 sat outputs
    &[(payment_script, payment_amount)],
    Some(change_script),
    None,
    fee_per_vbyte,
);
// Either TooLargeTransaction (weight > MAX_STANDARD_TX_WEIGHT),
// or NotEnoughFunds (input_sat < payment_sat + needed_fee),
// or a tx where fee consumed exceeds the dust inputs' value.
```
The attacker spends only the dust value to force every subsequent spend attempt to fail, while `scan_transaction` continues reporting the poisoned outputs on every scan.
