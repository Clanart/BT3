### Title
Escrow release/refund can permanently lock all multi-token order funds if any single token transfer reverts - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`_withdraw()` in `IntentsBase.sol` and its Tron equivalent `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` release or refund every escrowed token of a cross-chain intent order (plus accumulated relayer fees) to a single beneficiary inside one loop, with no per-token isolation. This is the same "single-transaction, multi-transfer, all-or-nothing" pattern flagged in the external report's `MintingHub.end()`: any one leg failing (a non-standard ERC20 reverting, a blacklisted/zero beneficiary, or a token with unusual transfer semantics) reverts the entire call, and because this function is only reachable via a one-shot Hyperbridge message delivery (`onAccept`/`onGetResponse`), the failure is not retryable the way a timeout is, permanently locking the escrowed funds for the order.

### Finding Description
`_withdraw` iterates over `body.tokens` and calls either a native `.call{value:}` or `IERC20.safeTransfer` for each token to `beneficiary`, and — when `finalize` is true — also forwards accumulated `TRANSACTION_FEES` to the same beneficiary in the same call: [1](#0-0) 

The Tron variant (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements the identical pattern, looping over all escrowed tokens and the fee token in a single `withdraw()` call: [2](#0-1) 

This function is invoked from the message-handling path (`RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow` in `onAccept`, and from `onGetResponse` for cancellations), which is triggered by a single, non-repeatable Hyperbridge POST/GET response delivery. Unlike the POST-request-timeout path in `EvmHost.sol`, where the module callback failure is caught and the commitment is *restored* so the caller can retry (`dispatchTimeOut`, see `if (!success) { _requestCommitments[commitment] = meta; return; }`) [3](#0-2) 
there is no analogous per-token retry or partial-completion mechanism in `_withdraw`/`withdraw`: it's a plain `for` loop over heterogeneous token transfers with no try/catch, no isolation, and no fallback "pull" mechanism.

If an order escrows multiple output/input tokens (which the `Order`/`TokenInfo[]` structure explicitly supports) and any one of them:
- reverts on a specific transfer to `beneficiary` (blacklist-style tokens, or ones that revert on zero-value transfers when a partial fill leaves a zero remaining balance for one leg),
- or the beneficiary address cannot receive native value (a non-payable/self-destructed contract, or `address(0)` derived from a corrupted/zeroed `body.beneficiary`),

then the entire `_withdraw`/`withdraw` call reverts. Because `_filled[body.commitment]` is set at the very start of the function, the revert also unwinds that state change (EVM semantics), so the order commitment is never finalized — yet the message that authorized this payout was a single, non-repayable Hyperbridge response/request. All remaining, otherwise-valid tokens escrowed for that commitment (including tokens that would have transferred fine) become stuck in the gateway contract indefinitely, since there is no separate per-token "claim" or "pull" entry point analogous to `MintingHub.returnPostponedCollateral()`.

### Impact Explanation
This directly causes loss/locking of bridged/escrowed user and solver funds, matching the bounty's "stealing or loss of funds" and "bridge custody" categories. A single misbehaving or non-standard token in a multi-asset intent order can brick the entire escrow release for that order, locking both compliant-token balances and relayer fees that were otherwise fully redeemable. This is a real fund-custody defect independent of any relayer/prover/admin misbehavior — it's triggered purely by ordinary token semantics or beneficiary configuration once a legitimately relayed message reaches the gateway.

### Likelihood Explanation
Likelihood is realistic but conditional: it requires an order with multiple output/input tokens where at least one has non-standard transfer behavior (deny-list, revert-on-zero, or a beneficiary unable to receive native ETH). This is plausible in production given intents can specify arbitrary ERC20 tokens and arbitrary beneficiary addresses supplied by the order creator/solver, and the code path is reached by the ordinary, permissionless message-delivery flow (`handlePostRequests`/GET response handling), not by any privileged or malicious-actor assumption.

### Recommendation
Decouple escrow settlement from the single atomic loop:
- Isolate each token transfer (e.g., wrap each in a low-level call and record failures) so one failing leg does not roll back the whole withdrawal.
- On a failed leg, credit the beneficiary's balance in a `pendingWithdrawals[beneficiary][token]` mapping and still finalize `_filled[commitment]`, exposing a separate permissionless `claim()`/`sweep()` function for pull-based recovery — mirroring `MintingHub.returnPostponedCollateral()`'s design intent from the source report.
- Ensure fee-token transfers to the beneficiary are similarly isolated from the main token loop.

### Proof of Concept
1. A user creates a cross-chain `Order` with two output tokens: `TOKEN_A` (standard ERC20) and `TOKEN_B` (a token that reverts on transfers to a blacklisted or zero-balance address, or beneficiary is a contract that cannot receive ETH for the native leg).
2. The order is filled/cancelled and a Hyperbridge message (`RedeemEscrow`/`RefundEscrow` POST, or a GET response for cancellation) is delivered once via `onAccept`/`onGetResponse`, invoking `_withdraw`/`withdraw`.
3. Inside the loop, the transfer for `TOKEN_A` succeeds, but the transfer for `TOKEN_B` reverts (e.g., `require(recipient != blacklisted)` or `.call{value:}` fails against a non-payable beneficiary). [4](#0-3) 
4. The whole `_withdraw` call reverts; `_filled[commitment]` is never persisted (state rollback), and — since the authorizing Hyperbridge message was a one-time, non-replayable delivery with no retry path analogous to `dispatchTimeOut`'s commitment-restoration — both `TOKEN_A` and `TOKEN_B` (and any accrued relayer fee) remain locked in the gateway with no way to re-trigger or pull the funds.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
