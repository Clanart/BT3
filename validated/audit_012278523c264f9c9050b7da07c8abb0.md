### Title
`ReceivedOutput::read` accepts a claimed output/offset pair without verifying the output is actually payable to the offset key — funds reported received that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The reported bug class is "perform a transfer/action and never check that it succeeded": the contract trusts that tokens moved when they may not have. The Serai analog lives in `ReceivedOutput::read`, which deserializes an untrusted `(offset, TxOut, outpoint)` triple that *claims* "this UTXO was received and is spendable under this key offset" — yet performs no verification that the claim is true. Unlike `Scanner::scan_transaction`, which only emits a `ReceivedOutput` after matching `output.script_pubkey` against the registered `p2tr_script_buf(key + G * offset)` scripts map, `read` accepts any arbitrary combination of offset, output script, and outpoint with zero consistency checks.

### Finding Description
`ReceivedOutput` couples three fields: `offset` (scalar added to the group key to derive the spending key), `output` (the `TxOut`), and `outpoint`. The only way a `ReceivedOutput` is legitimately produced is via `Scanner::scan_transaction`, which guarantees the invariant `output.script_pubkey == p2tr_script_buf(key + GENERATOR * offset)` — i.e., the output is genuinely spendable by the threshold key tweaked by `offset`.

`ReceivedOutput::read` (lines 122–134) decodes `offset` via `Secp256k1::read_F`, then `TxOut` and `OutPoint` via `consensus_decode`, and returns the struct directly:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  ...
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

It never checks that the declared offset actually maps the group key to the output's `script_pubkey`. An unprivileged party feeding bytes to `read` can therefore fabricate a `ReceivedOutput` referencing a real third-party UTXO (whose `script_pubkey` commits to a key nobody in the multisig controls) while attaching an arbitrary offset. Downstream, `SignableTransaction::new`/`multisig` treats the output as a spendable input owned by the threshold group: it builds sighashes over the supplied prevouts and produces a threshold signature for a transaction spending an output the group does not own.

This is exactly the unchecked-success pattern: a success-claiming artifact ("funds received under offset X") is accepted without validating the underlying condition that makes it spendable.

### Impact Explanation
Funds are reported received that are not spendable. A forged `ReceivedOutput` makes the wallet/protocol account for a UTXO belonging to an arbitrary external script_pubkey as if it were owned by the tweaked threshold key. Any spend attempt produces a transaction the network will reject (the actual prevout's script doesn't commit to the group's key), permanently locking whatever accounting credited the deposit. Alternatively, a real deposit's outpoint can be paired with a mismatched offset, causing `SignableTransaction` to sign with a wrong `prevouts`/key-offset binding and yield an invalid spend — denying the protocol use of genuinely received funds.

### Likelihood Explanation
Reachable by any unprivileged party able to supply bytes to `ReceivedOutput::read` (the serialized form is a fixed-size, trivially constructible blob — no valid signature or key knowledge required). Exploitation requires a consumer that trusts deserialized `ReceivedOutput`s rather than scanner-produced ones; the crate exposes the type and reader publicly specifically for transport, so this trust assumption is plausible for integrators relaying scanned outputs between components.

### Recommendation
Enforce the spendability invariant on deserialization. Either:
- Have `ReceivedOutput::read` take the group key and verify `output.script_pubkey == p2tr_script_buf(key + GENERATOR * offset)` (rejecting on mismatch or `None`), or
- Split the type into a `ClaimedOutput` (untrusted deserialization) and `ReceivedOutput` (only constructible via `Scanner` or explicit verification), so the "verified spendable" guarantee is enforced by the type system.

### Proof of Concept
```rust
// key: the multisig group key (even Y); attacker knows it, controls nothing
let scanner = Scanner::new(key).unwrap();

// Attacker picks any victim UTXO on-chain paying to script_pubkey S != p2tr(key + G*offset)
let fake = {
  let mut bytes = vec![];
  bytes.extend(Scalar::ONE.to_bytes());            // arbitrary offset
  bytes.extend(serialize(&victim_txout));          // someone else's TxOut
  bytes.extend(serialize(&victim_outpoint));       // real outpoint on chain
  ReceivedOutput::read(&mut bytes.as_slice()).unwrap() // accepted, no check
};

// fake passes every downstream API as a "spendable output owned by the group":
```
