## Analysis

The external report's core broken invariant: **a signature authorizing a claim does not bind the *scope/amount* being claimed — only the claimant's identity — so an unprivileged third party can replay the signature against a smaller/different scope, consuming the one-time authorization (nonce) and preventing the rightful party from ever claiming the full amount under that authorization.**

The direct Hyperbridge analog is in the relayer fee accumulation path, specifically the optional "beneficiary redirect" signature used inside `accumulate_fees`.

### Title
Relayer fee beneficiary-redirect signature does not bind claimed commitments/amount, allowing partial-claim replay that burns the authorization nonce - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`Pallet::accumulate` lets any unsigned caller submit a `WithdrawalProof` containing an arbitrary subset of request commitments delivered by a given relayer (`delivery_address`), plus an optional `beneficiary_details: (beneficiary_address, signature)` that redirects the accrued fee to a chosen account. The signed payload is `beneficiary_message(nonce, state_machine, beneficiary)` [1](#0-0)  — it commits only to the nonce, chain, and beneficiary, never to which commitments or how much fee is being accumulated. The commitment/amount is instead derived by the caller's own `WithdrawalProof.commitments` list, entirely independent of the signature.

### Finding Description
In `accumulate()`:
1. The caller supplies an arbitrary `commitments: Vec<H256>` and proofs; the pallet computes `total_fee` purely from those proofs. [2](#0-1) 
2. If `beneficiary_details` is present, the pallet checks the signature against `beneficiary_message(nonce, state_machine, beneficiary_address)` and, on success, increments `Nonce` and credits `total_fee` to `beneficiary_address`. [3](#0-2) 
3. Nothing in the signed message references `total_fee` or the specific `commitments` set. The nonce is the only replay guard, and it is consumed the moment any (even trivially small) batch is accumulated under that signature.

Because `accumulate_fees` is `ensure_none` (unsigned, no sender authentication) [4](#0-3) , and the delivery relayer's beneficiary-redirect signature travels in plaintext calldata to authorize a *future* accumulate call, any unprivileged observer who sees that signature (e.g., in the mempool, in a prior failed attempt, or in on-chain history before the intended larger batch lands) can independently construct their own `WithdrawalProof` — using only one or a few low-value commitments delivered by the same `delivery_address` (all such state is public and independently provable) — and submit it first with the captured signature and nonce. This satisfies every check: same `delivery_address`, same `nonce`, same `beneficiary_address`, valid signature, since none of those checks constrain which/how many commitments are being claimed.

This mirrors exactly the H-01 pattern: the signed authorization was meant to cover a specific quantity of value (in this case, the relayer's full pending batch of fees for that beneficiary redirect), but because the signature is scope/amount-agnostic, it can be "spent" for an unintended (smaller) amount, permanently exhausting the nonce for that `(delivery_address, state_machine)` pair. The remaining, larger set of legitimately-delivered commitments now requires the relayer to sign an entirely new message at the next nonce to redirect them — an availability/consumption issue on the one-time authorization construct.

### Impact Explanation
The relayer's intended redirection is only partially honored (smallest-possible amount attacker chooses), while the authorization token (nonce) is irrecoverably consumed. This is a fund-routing/amount integrity flaw in the reward-claim critical path called out by the bounty scope ("relayer rewards ... must move exactly once and only to the rightful beneficiary and amount"): the transferred amount is not the amount the relayer authorized, and the excess remains unclaimed by that authorization, requiring the relayer to notice and re-sign — during which the underlying commitments could similarly be intercepted again.

### Likelihood Explanation
The only prerequisite is visibility of a pending `beneficiary_details` signature (a normal unsigned extrinsic sitting in the public mempool, or previously broadcast) — no privileged key, relayer collusion, or governance action is needed. Any unprivileged chain observer can construct a competing `WithdrawalProof` using strictly public state (source/destination chain state roots already trusted by Hyperbridge) and race the transaction, exploiting the pallet's own value-agnostic signature scheme rather than a general network race condition external to the protocol logic.

### Recommendation
Bind the claimed scope into the signed payload, e.g., `beneficiary_message(nonce, state_machine, beneficiary, commitments_hash)` or `beneficiary_message(nonce, state_machine, beneficiary, total_fee)`, so a captured signature cannot be repurposed for a different (smaller) set of commitments/amount than the relayer actually authorized. Apply the same fix pattern to `withdrawal::message` if it is ever changed to support partial amounts.

### Proof of Concept
1. Relayer `R` (delivery_address) accumulates delivery receipts for commitments `[c1, c2, ..., c100]` on chain `S`, worth `total_fee = 1000`, and wants to redirect the proceeds to `beneficiary B`. It signs `beneficiary_message(nonce=5, S, B)` and submits `accumulate_fees(WithdrawalProof{ commitments: [c1..c100], ..., beneficiary_details: Some((B, sig)) })` as an unsigned extrinsic.
2. Attacker `A` observes the pending extrinsic's `(B, sig)` in the mempool before it lands. `A` independently builds source/destination state proofs for just `c1` (fee = 1, publicly derivable, no special keys), and submits `accumulate_fees(WithdrawalProof{ commitments: [c1], ..., beneficiary_details: Some((B, sig)) })` with a higher priority/earlier inclusion.
3. The pallet verifies `sig` against `beneficiary_message(5, S, B)` — which matches, because the signed payload never referenced `c1..c100` or `1000`. `Nonce::<T>[R, S]` becomes `6`, and `Fees[S][B] += 1`.
4. `R`'s original extrinsic for the full batch now recomputes `msg` with `nonce = 6`, which no longer matches the already-broadcast `sig` (signed for nonce 5) — the transaction fails on `InvalidSignature`/`InvalidPublicKey`, per the checks at [5](#0-4) . `R` must re-sign a new message for the remaining 99 commitments, and this can be repeated by any observer indefinitely to keep fragmenting/delaying the relayer's beneficiary redirection.
