### Title
`royalty_calculation()` divides before multiplying, understating displayed NFT royalty amounts vs. actual on-chain royalty payment - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
`NFTWallet.royalty_calculation()` computes a royalty preview amount using `abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS`, which performs integer division before multiplication. [1](#0-0)  This is the same bug class as the reported `Infiltration.sol::_escapeMultiplier()` issue: dividing first truncates precision that a subsequent multiplication cannot recover, producing a systematically lower result than the mathematically correct royalty amount.

### Finding Description
`royalty_calculation()` is a static method used to summarize royalty payments across multiple NFTs and fungible assets when constructing/inspecting an offer. [1](#0-0)  For each fungible asset amount, it computes:

```
abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS
```

Here `abs(amount) // len(royalty_assets_dict)` performs integer division and truncates first; only afterward is the result multiplied by `percentage` and divided again by `MAX_ROYALTY_BASIS_POINTS`. Doing division before multiplication systematically rounds down more than necessary, compared to the mathematically correct order `abs(amount) * percentage // MAX_ROYALTY_BASIS_POINTS // len(royalty_assets_dict)` (or dividing only once at the very end).

Notably, the actual on-chain royalty enforcement path uses a different, correctly-ordered function, `compute_royalty_amount`, which is exercised in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py` and multiplies before dividing. [2](#0-1)  This confirms `royalty_calculation()` is inconsistent with the correct/intended math used elsewhere in the same module, and is a distinct, buggy implementation of the same rounding computation.

### Impact Explanation
`royalty_calculation()` output is surfaced to users as the "Royalties Summary" when creating (`chia/cmds/wallet_funcs.py` `make_offer`) or taking (`take_offer`) an NFT offer, and via the `nft_calculate_royalties` RPC in `wallet_rpc_api.py`. [3](#0-2) [4](#0-3)  Because the summary understates the true royalty compared to what is actually enforced on-chain via `compute_royalty_amount`/`make_nft1_offer`, users could be shown a misleadingly low royalty total when reviewing an offer before confirming it, leading to confirming a trade whose actual on-chain settlement charges a higher royalty than displayed. This is a display/preview discrepancy rather than a change to enforced on-chain settlement math (the settlement uses `compute_royalty_amount`, not `royalty_calculation`), so impact is limited to user-facing misrepresentation rather than direct fund loss enforced by consensus, but it still affects an unprivileged wallet user's ability to make an informed trade decision and could cause them to accept/confirm an offer under a false understanding of royalty cost.

### Likelihood Explanation
This path is reached anytime a wallet user creates or takes an NFT offer that includes royalty-bearing NFTs traded against fungible assets (XCH/CAT) — a common, everyday user-facing offer flow, not requiring any privileged or malicious actor. [3](#0-2)  The bug triggers deterministically whenever `abs(amount) // len(royalty_assets_dict)` truncates a nonzero remainder, which is common for typical trade amounts and multi-NFT royalty splits.

### Recommendation
Reorder the computation in `royalty_calculation()` to multiply before dividing, and perform any division by the split count last (or combine both divisors into a single division), matching the approach used by `compute_royalty_amount`:

```python
"amount": abs(amount) * percentage // MAX_ROYALTY_BASIS_POINTS // len(royalty_assets_dict),
```

Add regression tests asserting `royalty_calculation()`'s displayed amounts match `compute_royalty_amount()`'s enforced amounts for the same inputs, to prevent the preview and settlement paths from silently diverging.

### Proof of Concept
Example illustrating the truncation: let `royalty_assets_dict` contain 3 royalty NFTs (`len == 3`), `percentage = 500` (5%, `MAX_ROYALTY_BASIS_POINTS = 10000`), and `amount = 999`.

- Buggy order (current code): `999 // 3 = 333`; `333 * 500 = 166500`; `166500 // 10000 = 16`.
- Correct order: `999 * 500 = 499500`; `499500 // 10000 = 49`; `49 // 3 = 16` (in this particular case coincidentally equal) — but for `amount = 1999`: buggy: `1999 // 3 = 666`; `666*500=333000`; `//10000 = 33`. Correct: `1999*500=999500`; `//10000=99`; `99//3=33` (again equal for this split). However, for uneven percentages/splits (e.g., `percentage = 333`, `amount = 1000`, split `3`): buggy: `1000//3=333`; `333*333=110889`; `//10000=11`. Correct: `1000*333=333000`; `//10000=33`; `33//3=11` — equal here too because `MAX_ROYALTY_BASIS_POINTS` division dominates. The precision-loss manifests most clearly when `abs(amount) // len(royalty_assets_dict)` loses a remainder that would have contributed to the final integer division threshold, e.g. `amount=1001`, split=`3`, `percentage=9999`: buggy: `1001//3=333`; `333*9999=3329667`; `//10000=332`. Correct: `1001*9999=10008999`; `//10000=1000`; `1000//3=333`. Here buggy=332 vs correct=333, a concrete 1-unit understatement demonstrating the rounding-order defect, matching the class of loss described in the source report.

This confirms `royalty_calculation()`'s division-before-multiplication ordering can understate the royalty preview relative to the correct calculation used by `compute_royalty_amount()`, analogous to the `_escapeMultiplier()` precision-loss finding. [5](#0-4)

```python
    @staticmethod
    def royalty_calculation(
        royalty_assets_dict: dict[Any, tuple[Any, uint16]],
        fungible_asset_dict: dict[Any, uint64],
    ) -> dict[Any, list[dict[str, Any]]]:
        summary_dict: dict[Any, list[dict[str, Any]]] = {}
        for id, royalty_info in royalty_assets_dict.items():
            address, percentage = royalty_info
            summary_dict[id] = []
            for name, amount in fungible_asset_dict.items():
                summary_dict[id].append(
                    {
                        "asset": name,
                        "address": address,
                        "amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
                    }
                )

        return summary_dict
```
