### Title
`ThresholdKeys` derives `Debug`, leaking the secret scalar/offset in cleartext while the actual secret share stays redacted - (File: crypto/dkg/src/lib.rs)

### Summary
The OpenBao advisory describes an inverted redaction: a component intended to strip sensitive material instead retains auth secrets in cleartext (CWE-532). Serai exhibits the same inverted-redaction shape in `ThresholdKeys`. Every other secret-bearing type in `crypto/dkg` implements a hand-written `fmt::Debug` that deliberately omits secret material (`ThresholdCore`, `ThresholdView`, `SecretShare`, `BlameMachine` all end with `finish_non_exhaustive()`), yet `ThresholdKeys` itself uses `#[derive(Clone, Debug, Zeroize)]`, which prints the `scalar` and `offset` fields — values the code explicitly documents as secret-adjacent material that is excluded from serialization because it is "ephemeral".

### Finding Description
`ThresholdKeys` is declared with a derived `Debug` impl:

```rust
// crypto/dkg/src/lib.rs
#[derive(Clone, Debug, Zeroize)]
pub struct ThresholdKeys<C: Ciphersuite> {
  #[zeroize(skip)]
  core: Arc<Zeroizing<ThresholdCore<C>>>,
  scalar: C::F,   // printed in cleartext by derived Debug
  offset: C::F,   // printed in cleartext by derived Debug
}
```

The `scalar`/`offset` are applied multiplicatively/additively on top of the secret share (`scale()` returns `None` for a zero scalar precisely because it must remain a secret-free no-op, and `view()` folds them into `secret_share`). The docs state they are deliberately *not* serialized — i.e., they are treated as sensitive runtime-only material — yet any `{keys:?}` / `debug_struct` output emits them verbatim via `C::F: Debug`. Meanwhile the genuinely careful code paths do the opposite of this: `ThresholdCore`'s manual `Debug` prints `params`, `group_key`, `verification_shares`, `interpolation` and hides `secret_share`; `SecretShare`'s `Debug` prints nothing at all; `BlameMachine` hides `result`. The redaction policy is therefore inverted on the one struct that is the public-facing handle users will actually log — the share is protected while the live tweak scalars leak.

### Impact Explanation
If an integrator uses `scale()`/`offset()` with a non-public scalar (the documented purpose is "account and privacy schemes," e.g., a hiding/derivation scalar), then any Debug-formatted logging, error capture, or panic message containing a `ThresholdKeys` writes that scalar to logs in cleartext. Combined with the public group key/verification shares (which are already printed), recovery of `scalar`/`offset` plus access to a single signature share or the serialized `ThresholdKeys` blob (which stores `secret_share` pre-tweak) can enable reconstruction of the effective signing secret in configurations where the scalar is what guards spendability. This matches CWE-532: sensitive information inserted into a log reachable by an attacker who compromises the log/audit store, identical to the OpenBao prerequisite (attacker access to the audit device).

### Likelihood Explanation
Medium. Exploitation requires (a) a secret-valued scalar/offset configuration and (b) attacker read access to wherever Debug output lands (logs, crash reporters, tracing subscribers). Both are realistic: `Debug` is required on several message types in pedpop (`sealed::Message: fmt::Debug`), encouraging a codebase-wide habit of debug-logging structures, and the derived impl is silent — nothing warns an integrator that `format!("{keys:?}")` emits tweak scalars.

### Recommendation
Replace `#[derive(Debug)]` on `ThresholdKeys` with a manual `fmt::Debug` that prints non-sensitive fields and elides `scalar`/`offset` via `finish_non_exhaustive()`, mirroring `ThresholdCore`/`ThresholdView`:

```rust
impl<C: Ciphersuite> fmt::Debug for ThresholdKeys<C> {
  fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
    f.debug_struct("ThresholdKeys").field("core", &self.core).finish_non_exhaustive()
  }
}
```

Audit the other `#[derive(..., Debug)]` secret-bearing structs (`EncryptionKeyMessage` prints `msg`, which is fine for `Commitments` but would leak if ever instantiated over a secret `M`; `Params<C, A>` has no `Debug`) and document that scalar/offset must be treated with the same confidentiality as the secret share.

### Proof of Concept
```rust
// Any curve; scalar is a non-trivial secret tweak
let keys: ThresholdKeys<C> = ...;
let tweaked = keys.scale(secret_scalar).unwrap();
// Derived Debug prints `scalar: <repr of secret_scalar>, offset: ...`
let logged = format!("{tweaked:?}");
// `logged` contains the canonical field encoding of the secret scalar in cleartext,
// while `secret_share` (inside ThresholdCore) remains hidden — inverted redaction.
```
Contrast with `ThresholdCore` (crypto/dkg/src/lib.rs:266-276), `ThresholdView` (lines 316-329), and `SecretShare` (crypto/dkg/pedpop/src/lib.rs:242-246), which all use `finish_non_exhaustive()` to suppress secrets — confirming the intended redaction policy that `ThresholdKeys`' derive violates.
