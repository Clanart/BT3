### Untrusted `ThresholdKeys` can encode an identity group key and panic Bitcoin signing - (File: `crypto/dkg/src/lib.rs`)

### Summary

`ThresholdKeys::read` accepts a zero secret share and an identity verification share. This constructs a mathematically consistent, but semantically invalid, threshold key whose group key is the point at infinity. If the resulting keys are used with Bitcoin's `crypto::Schnorr` FROST algorithm, signing reaches `Hram::hram`, which calls `x(A)` on the identity group key. `x` unconditionally expects an affine x-coordinate and panics on infinity.

An unprivileged party who can cause a processor to deserialize a malicious `ThresholdKeys` object can therefore crash the signing process. This is the same externally reachable crash/OOM-style bug class as the referenced report: malformed protocol state is accepted during deserialization and later triggers a fatal panic.

### Finding Description

`ThresholdKeys::read` deserializes the secret share with `C::read_F` and all verification shares with `<C as Ciphersuite>::read_G`. The scalar decoder accepts zero, and the generic ciphersuite point decoder accepts any canonical group encoding; it does not reject the identity. Only `frost::Curve::read_G` rejects identity, but `ThresholdKeys::read` deliberately uses `Ciphersuite::read_G` instead.

For example, a malicious serialized object can contain:

- `t = 1`
- `n = 1`
- `i = 1`
- Lagrange interpolation
- `secret_share = 0`
- `verification_shares[1] = identity`

These values are internally consistent: `0 * G == identity`, and the participant-1 group key is therefore the identity. The object is then passed to `ThresholdKeys::new`.

The Bitcoin Schnorr implementation explicitly documents that `Hram::hram` panics when `R` or `A` is infinity. During `sign_share`, `A` is `params.group_key()`. With the malicious deserialized keys, `A` is the identity and `x(A)` reaches:

```rust
(*encoded.x().expect("point at infinity")).into()
```

That `expect` aborts/panics the process or task.

Relevant code:

- Zero scalars are accepted by `Ciphersuite::read_F`: `crypto/ciphersuite/src/lib.rs:74-82`
- Canonical identity points are accepted by `Ciphersuite::read_G`: `crypto/ciphersuite/src/lib.rs:91-100`
- `Curve::read_G` would reject identity, but is not used here: `crypto/frost/src/curve/mod.rs:123-131`
- `ThresholdKeys::read` uses the permissive scalar/point readers: `crypto/dkg/src/lib.rs:604-623`
- The parsed values are passed to `ThresholdKeys::new`: `crypto/dkg/src/lib.rs:625-630`
- Bitcoin `Hram::hram` calls `x(A)`: `networks/bitcoin/src/crypto.rs:59-67`
- `x` panics on infinity: `networks/bitcoin/src/crypto.rs:13-15`

### Impact Explanation

A maliciously serialized `ThresholdKeys<Secp256k1>` can make a Bitcoin signing operation panic. Since threshold key material may be persisted, restored, imported, or otherwise deserialized through `ThresholdKeys::read`, this provides a deserialization-triggered denial of service.

The panic occurs only after the malformed object is accepted and used to sign, but that path does not require the attacker to know any private key share. The constructed object itself supplies the invalid secret share and verification share.

### Likelihood Explanation

Exploitation requires an attacker to influence bytes passed to `ThresholdKeys::read` and then cause those keys to be used by the Bitcoin Schnorr algorithm. That is a narrower reachability condition than a network packet parser, but it is within the exposed `ThresholdKeys::read` API.

Once reached, the condition is deterministic. No rare hash result, malformed curve encoding, race, or consensus failure is required: zero is a canonical scalar, identity is a canonical point, and the downstream x-coordinate extraction has an unconditional panic for infinity.

### Recommendation

Reject semantically invalid key material in `ThresholdKeys::new`/`ThresholdKeys::read`:

- Reject a zero `secret_share`.
- Reject identity verification shares.
- Reject an identity computed `group_key`.
- Prefer `Curve::read_G` where the serialized type is known to be a FROST `Curve`.
- Additionally, make Bitcoin `Hram::hram` return an error or explicitly fail verification rather than panic on infinity.

Defense in depth should enforce both deserialization validity and non-panicking signing behavior.

### Proof of Concept

The malicious logical input is a serialized `ThresholdKeys` object equivalent to:

```text
curve_id_len = len(Secp256k1::ID)
curve_id     = Secp256k1::ID
t            = 1u16
n            = 1u16
i            = 1u16
interpolation = 1
secret_share = 0
verification_share[1] = identity
```

After `ThresholdKeys::<Secp256k1>::read` accepts it, instantiate `AlgorithmMachine::new(bitcoin_serai::crypto::Schnorr::new(), keys)`, produce a preprocess, and invoke `sign`. `Schnorr::sign_share` calls `Hram::hram`, which calls `x(&params.group_key())`; because the group key is infinity, `encoded.x().expect("point at infinity")` panics.
