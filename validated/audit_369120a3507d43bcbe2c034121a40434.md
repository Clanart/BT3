### Title
Unchecked u64 arithmetic on unbounded payment/amount fields allows overflow-wraparound, bypassing `NotEnoughFunds` and producing invalid, signable transactions (DoS) - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` performs unchecked `u64` sums and additions over attacker-influenced `payments` amounts and `fee_per_vbyte`. `payment_sat` is a `sum::<u64>()` over an unbounded list of `(ScriptBuf, u64)` payments, and `payment_sat + needed_fee` is a plain `u64` addition. Either can overflow. In release builds the wrap-around defeats the `input_sat < payment_sat + needed_fee` solvency check, letting `SignableTransaction::new` return `Ok` for a transaction whose outputs exceed its inputs and exceed Bitcoin's `MAX_MONEY` consensus limit — a transaction that can never confirm but will still be passed to the FROST signing flow. In debug builds it panics outright. This is the Serai analog of the original finding: unbounded/under-constrained numeric parameters whose bad values cause a revert/DoS or a wrong outcome instead of an early, clean rejection.

### Finding Description
The relevant code is `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`:

- `payments` is `&[(ScriptBuf, u64)]` with only a per-payment dust check (`*amount < DUST`, line 165-169); there is no upper bound on `payment.1` or on the number of payments other than a transaction-weight check performed *after* the arithmetic.
- `payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>()` (line 187) — unchecked `u64` summation.
- `needed_fee = fee_per_vbyte * vbytes` (line 206) — unchecked `u64` multiplication.
- `input_sat < (payment_sat + needed_fee)` (line 215) — unchecked `u64` addition guarding `TransactionError::NotEnoughFunds`.
- `fee()` (lines 138-141) computes `sum(prevouts) - sum(tx.output)` with unchecked `u64` subtraction, which underflows whenever the constructor's wrapping accepted an output set larger than the inputs.

With two payments of, e.g., `u64::MAX / 2 + 1` each plus a valid fee, `payment_sat + needed_fee` wraps to a small value, `input_sat < wrapped` is false, and `Ok(SignableTransaction)` is returned even though the outputs vastly exceed the inputs. Downstream, the processor's `make_signable_transaction` (`processor/src/networks/bitcoin.rs:446-470`) treats `Ok` as success and proceeds to `attempt_sign`, producing a threshold signature over a transaction Bitcoin consensus will never accept (`Amount > MAX_MONEY` / outputs > inputs). `fee()` also returns a garbage wrapped value. Any code path that hits the raw overflow panics (debug) or produces a permanently unconfirmable plan (release), stalling the associated payments and locking the inputs.

This mirrors the reported bug class — missing bounds/ordering constraints on parameters — mapped onto Serai's real attack surface: a public, unprivileged-input API (`SignableTransaction::new` on `payments`/`fee_per_vbyte`) whose under-constrained arithmetic converts "values the caller can choose" into an incorrect solvency decision and a DoS.

### Impact Explanation
A plan/payment set whose amounts overflow `u64` in aggregate either crashes the processor path (panic on overflow) or produces a `SignableTransaction` that is signed by the threshold group yet is invalid on-chain, so the payment can never complete. The inputs backing the plan remain consumed/pending while the output can never be spent, i.e., funds are reported as sent in a transaction that is not spendable/confirmable — a concrete signing of an unintended (invalid) message plus a liveness DoS. Secondary impact: `fee()` underflow-wrap returns a meaningless enormous fee for any accepted oversized-output transaction, corrupting accounting that relies on `needed_fee`/`fee()`.

### Likelihood Explanation
Triggering requires only payment amounts whose `u64` sum (plus fee) exceeds `2^64`, or a `fee_per_vbyte`/`vbytes` product that overflows — all fields are direct inputs to `SignableTransaction::new`. There is no `MAX_MONEY` or total-supply bound anywhere in the constructor (the only bound is dust on the low side and weight on size), so this is reachable purely through public inputs. Whether a real integrator plumbs arbitrary user-chosen amounts into `payments` determines practical frequency; the library itself does not constrain it. This is why it is Medium rather than High: it yields DoS/invalid-signature, not direct key-share or secret leakage.

### Recommendation
Bound and constrain the monetary variables before arithmetic, exactly as the original report advised:

- Use `checked_add`/`checked_mul`/`checked_sub` for `payment_sat`, `input_sat`, `needed_fee`, and `payment_sat + needed_fee`, and map overflow to `TransactionError` (e.g., `NotEnoughFunds` or a new `AmountOverflow`).
- Reject any individual payment or aggregate exceeding Bitcoin `MAX_MONEY` (`bitcoin::Amount::MAX_MONEY` / 21,000,000 BTC in sats).
- Make `fee()` use `checked_sub` and assert/return an error instead of underflowing.
- Apply the same hardening to the amortization arithmetic in `processor/src/networks/mod.rs` (`total_fee` accumulation, `actual - expected` in `scheduler/utxo.rs`), which performs similar unchecked `u64` math over plan-derived amounts.

### Proof of Concept
Reachable path (no keys or collusion needed, only control of `payments`/`fee_per_vbyte`):

```rust
// networks/bitcoin/src/wallet/send.rs — SignableTransaction::new
let huge = u64::MAX / 2 + 1;
let payments = vec![(addr.clone(), huge), (addr.clone(), huge)];
// payment_sat = u64::MAX + 1  → wraps to 0 (release) or panics (debug)
// payment_sat + needed_fee wraps to ~needed_fee
SignableTransaction::new(inputs, &payments, None, None, fee_per_vbyte)
// → Ok(SignableTransaction) with outputs >> inputs (release)
// → fee() underflow-wraps to ~u64::MAX
```

Supporting code locations:

- `payment_sat` unchecked sum: `networks/bitcoin/src/wallet/send.rs` line 187
- `payment_sat + needed_fee` unchecked addition guarding `NotEnoughFunds`: line 215
- `needed_fee = fee_per_vbyte * vbytes` unchecked multiplication: line 206

- Constructor returns `Ok` onward to signing; processor only errors on enumerated `TransactionError` variants and panics/accepts otherwise: `processor/src/networks/bitcoin.rs:446-470`

The fix belongs in `SignableTransaction::new`: checked arithmetic plus an explicit upper bound (`MAX_MONEY`, and a cap on `payments.len()`/fee product) so that oversized amounts are rejected with a `TransactionError` before any sum is computed, rather than wrapping into a false solvency result or panicking.
