## Analysis Result

Based on the investigation, I found a plausible analog in `chia/daemon/server.py`'s service-registration/message-routing logic, which lacks any binding between a connecting websocket's actual identity and the service name it claims.

### Title
Daemon accepts unauthenticated service-name self-registration, enabling routing hijack of privileged local RPC traffic - (File: chia/daemon/server.py)

### Summary
The chia daemon (`WebSocketServer`) forwards any message whose `destination` is a registered service name to *all* websockets registered under that name, but `register_service()` performs no check that the requesting websocket actually corresponds to that service — any connected client can register itself under any service string (e.g. `"wallet_ui"`, `"chia_wallet"`, `"chia_full_node"`), analogous to GitLab's "Incorrect Access Control" class of bug where a client can access/claim resources outside its intended scope.

### Finding Description
`register_service()` blindly trusts the client-supplied `service` field and adds the websocket to the routing table without verifying the caller's actual role: [1](#0-0) 

`handle_message()` then routes any message whose `destination != "daemon"` purely by this attacker-controlled table, without re-checking sender identity, and forwards the raw payload to every socket registered for that destination: [2](#0-1) 

The daemon module's own documentation flags this as a known fragility point — "registered service names become routing authorities for all local daemon clients" — but no code enforces that a connection is limited to its legitimate service identity: [3](#0-2) 

Because the only gate for reaching the daemon at all is mutual TLS with the shared local daemon certs (not a per-service identity check), any local client already permitted to connect (for example a plotter, CLI utility, or third-party integration holding the daemon's private cert) can register under `wallet_ui`, `chia_wallet`, or `chia_full_node` and thereby: (1) receive push `state_changed` notifications meant for the wallet UI (balance/sync/transaction state), and (2) receive RPC-relay commands/responses that legitimate services would normally answer, since routing is destination-name based rather than connection-identity based.

### Impact Explanation
An unprivileged local process that can reach the daemon socket can hijack message routing intended for the wallet or full-node RPC surface, intercepting sensitive wallet/full-node state or RPC traffic (e.g., transaction/balance state notifications, RPC command/response pairs relayed through the daemon) that it was never authorized to see, and can potentially answer on behalf of a legitimate service. This is an access-control failure over routing/state exposure within the local RPC boundary described in `rpc.md`/`daemon.md`.

### Likelihood Explanation
Reaching this requires only a local websocket connection to the daemon (mutual TLS with locally available certs) plus sending a `register_service` command with an arbitrary `service` value — no additional secret or elevated privilege is checked beyond daemon-level TLS, which is already the only daemon-wide gate for any local caller in this design.

### Recommendation
Bind service registration to verified connection identity (e.g., require a per-service credential/token issued at service startup, or validate the registering process against an allow-list tied to that specific service's certificate/identity) rather than trusting a client-supplied `service` string; reject/limit registrations for privileged service names (`wallet_ui`, `chia_wallet`, `chia_full_node`, etc.) from connections that cannot prove that identity.

### Proof of Concept
1. Start the chia daemon normally.
2. From any local process holding the daemon's shared private TLS cert (e.g., a plotter helper or any local integration script), open a websocket to the daemon and send:
   `create_payload("register_service", {"service": "wallet_ui"}, "attacker", "daemon")`
3. The daemon adds this websocket to `connections["wallet_ui"]` per `register_service()` at [4](#0-3) .
4. Any subsequent daemon-routed message destined for `wallet_ui` (state-change notifications, or RPC relay traffic) is now also delivered to the attacker's socket via the destination-based forwarding in `handle_message()` at [5](#0-4) , with no verification that the registering socket is the genuine wallet UI.
