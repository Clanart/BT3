## Analysis

The Telcoin report describes a constructor accepting an unvalidated numeric "period" value (a `FormatChecker`/require-style gap) that later feeds into interval arithmetic, producing undefined/incorrect behavior. Kaia's `kaiax/gov` module has a structurally identical pattern: governance parameters that represent time/block intervals are declared with a `noopFormatChecker` (no positivity/non-zero bound), and that unchecked value is later used as a divisor in period-rounding arithmetic in the staking module. [1](#0-0) [2](#0-1) 

### Title
Unvalidated `reward.stakingupdateinterval` governance parameter can be set to zero, causing a divide-by-zero panic in `sourceBlockNum`/`roundDown` (File: kaiax/staking/impl/getter.go)

### Summary
`RewardStakingUpdateInterval` is registered with `FormatChecker: noopFormatChecker`, meaning any `uint64` value — including `0` — is accepted as a canonical governance value [1](#0-0) . This value flows unchecked into `staking.impl.GetStakingInfo` as `s.stakingInterval`, which is passed to `sourceBlockNum(num, isKaia, interval)` [3](#0-2) .

### Finding Description
For pre-Kaia-fork block processing, `sourceBlockNum` computes `roundDown(num-1, interval) - interval`, and `roundDown` performs `n - (n % p)` [2](#0-1) . In Go, integer modulo/division by zero is a runtime panic, not a silent wraparound as in the original Solidity report's "negative value" scenario — but the root cause class is identical: a duration/interval-typed governance value is accepted into the parameter set with no validation (`noopFormatChecker`) before being used in period-based arithmetic (compare to the unchecked `challengePeriod` used in `TelcoinDistributor`'s time-window logic).

Every full/consensus node evaluating `GetStakingInfo` for a block number where `num > 2*interval` and `interval == 0` will panic and crash inside `roundDown`. Because this executes deterministically as part of ordinary state/staking-info retrieval (not a privileged-only code path), any node — not just validators — that processes blocks under such a governance configuration is affected identically, which is a shared/network-wide liveness failure rather than a single-node bug.

### Impact Explanation
A network-wide `reward.stakingupdateinterval = 0` governance parameter causes all nodes that must resolve staking info via `sourceBlockNum`/`roundDown` for a pre-Kaia-fork block to panic, halting block processing across the fleet. This is a chain-halt/DoS class impact stemming purely from a missing bound check on a governance-configurable duration parameter, directly analogous to the reported missing bound check on `challengePeriod`.

### Likelihood Explanation
Likelihood is constrained by the fact that this path only executes when `isKaia` (post-Kaia-fork) is false — i.e., it is reachable on pre-Kaia-fork network configurations (or during a hypothetical governance-driven rollback/replay of that logic), and setting the parameter still requires it to pass through the governance vote/finalization flow, which is a privileged governance-side action, not a plain unprivileged transaction. I could not fully verify within the available search whether any code path re-derives or replays `stakingInterval == 0` on current, post-Kaia mainnet configurations, so applicability to already-forked networks is uncertain.

### Recommendation
Add a `FormatChecker` for `RewardStakingUpdateInterval` (and any other interval/duration-typed governance parameters currently using `noopFormatChecker`) that rejects `0`, mirroring the fix recommended in the source report (`require(period > 0, ...)`). Additionally, harden `roundDown`/`sourceBlockNum` in `kaiax/staking/impl/getter.go` with an explicit `interval != 0` guard so a misconfigured parameter degrades gracefully instead of panicking.

### Proof of Concept
1. Configure `params.ChainConfig.Governance.Reward.StakingUpdateInterval = 0` (accepted because `RewardStakingUpdateInterval`'s `FormatChecker` is `noopFormatChecker`) [1](#0-0) .
2. Run a pre-Kaia-fork chain and call `GetStakingInfo(num)` for any `num > 0`.
3. `sourceBlockNum` takes the `else` branch (`isKaia == false`), and since `num <= 2*0` is false for `num > 0`, it calls `roundDown(num-1, 0)` [4](#0-3) .
4. `roundDown` executes `n % p` with `p == 0`, panicking with `runtime error: integer divide by zero` [5](#0-4) , crashing the node.

**Note on confidence:** I was not able to fully confirm whether the vulnerable `roundDown`/`sourceBlockNum` code path is reachable on current post-Kaia-fork mainnet (the `isKaia` branch appears to bypass `interval` entirely), so this analog's real-world exploitability on live mainnet is uncertain and should be verified with a running Devin session against the actual `IsKaiaForkEnabled` logic and any legacy/private-net deployments still pre-fork.

func sourceBlockNum(num uint64, isKaia bool, interval uint64) uint64 {
	if isKaia {
		if num == 0 {
			return 0
		} else {
			return num - 1
		}
	} else {
		if num <= 2*interval {
			return 0
		} else {
			// Simplified from the previous implementation:
			// if (num % interval) == 0, return num - 2*interval
			// else return num - interval - (num % interval)
			return roundDown(num-1, interval) - interval
		}
	}
}

func roundDown(n, p uint64) uint64 {
	return n - (n % p)
}
