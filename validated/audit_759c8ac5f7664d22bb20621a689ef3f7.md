### Title
Single-step, unvalidated `HostManager.setIsmpHost` binding permanently zeroes admin and can irrecoverably brick the cross-chain governance/withdrawal channel - (File: evm/src/core/HostManager.sol)

### Summary
`HostManager.setIsmpHost` performs the exact anti-pattern flagged in the external report: a single, irreversible transaction both sets a critical address binding and simultaneously destroys the only privileged account that could correct a mistake, with zero validation of the new address.

### Finding Description
`HostManager` is the module authorized to receive cross-chain governance requests from the Hyperbridge parachain and relay them into `EvmHost.updateHostParams`/`EvmHost.withdraw`, both of which are gated by `restrict(_hostParams.hostManager)` [1](#0-0) [2](#0-1) . Because `EvmHost` and `HostManager` reference each other, the deployment flow requires a one-time "seal" call, `setIsmpHost`, to bind the manager to its host: [3](#0-2) 

This function:
1. Performs no validation whatsoever on `hostAddr` (no zero-address check, no code-size check, no `IERC165`/interface check) — contrast this with `EvmHost.updateHostParamsInternal`, which validates `hostManager`, `handler`, and `consensusClient` are non-zero, contain code, and implement the expected interface before accepting them [4](#0-3) .
2. Immediately and unconditionally sets `_params.admin = address(0)` in the same transaction, permanently removing the only account capable of calling `setIsmpHost` again (guarded by `restrict(_params.admin)` at line 90) — an irrecoverable single-step transfer, the exact bug class in the external report.

`onAccept`, the entry point for genuine cross-chain governance messages, is gated by `restrict(_params.host)`, i.e. it only accepts calls from the address stored as `_params.host` [5](#0-4) . If `setIsmpHost` is executed with an incorrect address (typo, wrong deployment artifact, wrong chain's host address, etc.), the binding is wrong and unfixable because `admin` is already zeroed, so `setIsmpHost` can never be called again to correct it.

### Impact Explanation
Once mis-bound, the real `EvmHost` can never successfully reach `onAccept` on this `HostManager` (since the manager will reject calls from the actual host, whose address doesn't match the stored `_params.host`), permanently severing the only channel through which cross-chain governance can call `EvmHost.withdraw` and `EvmHost.updateHostParams`. This produces:
- Permanent loss/lock of protocol bridge revenue accumulated in `EvmHost` (unreachable `withdraw`).
- Permanent inability to rotate `handler`, `consensusClient`, `hostManager`, or `stateMachines` via legitimate governance, effectively freezing the host's critical parameters forever, mirroring the "onlyOwner() functions blocked forever" impact described in the source report.

This matches the required impact categories of fund loss/lock and unauthorized-state freezing of critical bridge parameters.

### Likelihood Explanation
This requires the legitimate `admin` (deployer) to execute `setIsmpHost`, which happens exactly once per deployment as documented ("can only be called once ... to seal the cyclic dependency") [6](#0-5) . There is no on-chain safeguard preventing an incorrect address from being supplied and no way to recover afterward, so likelihood is tied entirely to deployment-script/operational error, with no attacker action needed to trigger — only to observe and exploit the resulting frozen state (e.g., no legitimate governance actor can ever again change misconfigured parameters, including a wrong `consensusClient` accepted before the freeze).

### Recommendation
Adopt a two-step commit pattern analogous to `Ownable2Step`:
1. `setIsmpHost` should first validate `hostAddr` is non-zero, has code, and implements the expected `IHost`/interface check (mirroring `updateHostParamsInternal`'s checks).
2. Do not zero `admin` in the same call that sets `host`. Instead, require a confirmation step — e.g., have the target `EvmHost` (or a second admin transaction) acknowledge the binding, or add a `pendingHost`/`confirmHost` two-transaction flow — before revoking admin's ability to change it, so an incorrect binding can be corrected prior to being finalized.

### Proof of Concept
1. Deploy `HostManager` with `admin = deployer`, `host = address(0)`.
2. Deploy `EvmHost` (or `MainnetTestHost`) expecting to bind to this manager.
3. Deployer mistakenly calls `setIsmpHost(wrongAddress)` (e.g., a typo'd address, or the address of a not-yet-deployed/incorrect host contract) as shown in `evm/tests/foundry/EvmHostTest.sol` deployment helper `_newMainnetHost` [7](#0-6) .
4. `_params.host = wrongAddress; _params.admin = address(0);` executes — no revert, no validation.
5. Any subsequent legitimate cross-chain governance message dispatched by the real `EvmHost` to this `HostManager.onAccept` reverts with `UnauthorizedAction` because `msg.sender != _params.host`.
6. `admin` is `address(0)`, so `setIsmpHost` can never be called again — the binding, and therefore the entire governance/withdrawal channel, is permanently broken.

    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
