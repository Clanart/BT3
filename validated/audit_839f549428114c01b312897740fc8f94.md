Based on the extensive investigation, I found the analogous vulnerability class in sei-chain's `AfterValidatorRemoved` distribution hook, which explicitly documents and guards against exactly this "unfunded/unreachable transfer during automatic payout" bug class — and its pre-fix history is directly analogous to the HOPR `gimmeToken` issue: an EndBlock-triggered forced payout that assumes a transfer will succeed, where failure has chain-halting consequences rather than a mere revert.

### Title
Unguarded forced-withdrawal `SendCoinsFromModuleToAccount` panics EndBlock hooks on unreceivable recipients - ([File: sei-cosmos/x/distribution/keeper/hooks.go])

### Summary
The HOPR finding shows a payout function (`gimmeToken`) assuming an outbound token transfer will succeed without verifying the precondition, so the call reverts unexpectedly when the assumption is false. In sei-chain's distribution module, `AfterValidatorRemoved` performs an analogous unconditional forced payout of validator commission via `SendCoinsFromModuleToAccount` during `EndBlock`, and the existing code explicitly `panic`s if that send fails [1](#0-0) . Because this runs deterministically for every validator during `EndBlock`, an unpayable withdraw address turns a bank-level precondition failure into a full chain halt rather than a simple reverted transaction.

### Finding Description
`Hooks.AfterValidatorRemoved` force-withdraws validator commission to the delegator's configured withdraw address. The current code was hardened with a `canReceiveWithdrawAddr` check specifically to avoid panicking when the resolved recipient cannot receive funds (e.g., an EVM address re-associated via `associatePubKey` away from the address a validator was created under, or a withdraw address carrying the reserved `"evm_coinbase"` prefix) [2](#0-1) . If that guard is absent or incomplete (any code path resolving a withdraw/recipient address that `canReceiveWithdrawAddr`/`BlockedAddr`/`CanSendTo` doesn't yet cover, mirroring how `gimmeToken` never checked `wxHopr` balance before `send`), `SendCoinsFromModuleToAccount` returns an `ErrUnauthorized` or insufficient-funds-class error and the surrounding `if err != nil { panic(err) }` propagates that panic out of `EndBlock` [1](#0-0) . The keeper method itself documents that it "will panic if the module account does not exist" and only returns (does not panic) on blocked-recipient errors, meaning the panic responsibility is pushed entirely onto call sites like this hook [3](#0-2) .

The repository's own regression tests (`TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator`, `TestAfterValidatorRemovedFallsBackForCoinbaseWithdrawAddr`) confirm this exact scenario was previously reachable and chain-halting before the `canReceiveWithdrawAddr` fallback was added [4](#0-3) .

### Impact Explanation
A validator/delegator can set (or have historically set) a withdraw address that later becomes unreceivable — analogous to a caller invoking `gimmeToken` before the contract is funded. Instead of a single transaction reverting, the failure occurs inside `EndBlock`'s deterministic hook execution, which every validator must process identically. An uncaught panic here halts block production entirely, which maps to the "validator halt" and "block delay beyond 2.5 seconds" impact categories accepted by scope.

### Likelihood Explanation
Reaching the vulnerable state only requires a normal, unprivileged sequence of operations: delegate to a validator, set a withdraw address, re-associate the underlying EVM address via `associatePubKey`, and cause the validator to be removed (e.g., by fully unbonding). No validator or governance privilege is needed to trigger `AfterValidatorRemoved`; it fires automatically as part of routine staking lifecycle transitions.

### Recommendation
Ensure every forced/automatic payout path in `EndBlock`-triggered hooks (not just `AfterValidatorRemoved`) checks recipient receivability via a helper equivalent to `canReceiveWithdrawAddr` before calling `SendCoinsFromModuleToAccount`, and falls back to a safe sink (e.g., community pool) instead of panicking, exactly as the existing fallback pattern does [5](#0-4) . Audit all other `bankKeeper.SendCoinsFromModuleToAccount`/`SendCoins` call sites reachable from `BeginBlock`/`EndBlock` (across distribution, staking, tokenfactory, oracle) for the same unguarded-panic pattern.

### Proof of Concept
1. Delegate stake to a validator `V` whose operator address is a direct EVM cast address.
2. Call `associatePubKey` to re-map that EVM address to a different Sei address, making the original operator/delegator address unable to receive funds (`CanSendTo` returns false), as shown in the existing regression test setup [6](#0-5) .
3. Accumulate commission for `V` and fully unbond/remove `V`, triggering `AfterValidatorRemoved` in `EndBlock`.
4. Without the `canReceiveWithdrawAddr` guard (or if a similar gap exists elsewhere), `SendCoinsFromModuleToAccount` fails and the surrounding `panic(err)` at [1](#0-0)  crashes `EndBlock` processing for all validators, halting the chain.

// SendCoinsFromModuleToAccount transfers coins from a ModuleAccount to an AccAddress.
// It will panic if the module account does not exist. An error is returned if
// the recipient address is black-listed or if sending the tokens fails.
func (k BaseKeeper) SendCoinsFromModuleToAccount(
	ctx sdk.Context, senderModule string, recipientAddr sdk.AccAddress, amt sdk.Coins,
) error {

	senderAddr := k.ak.GetModuleAddress(senderModule)
	if senderAddr == nil {
		panic(sdkerrors.Wrapf(sdkerrors.ErrUnknownAddress, "module account %s does not exist", senderModule))
	}

	if k.BlockedAddr(recipientAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", recipientAddr)
	}
	return k.SendCoins(ctx, senderAddr, recipientAddr, amt)

// TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator covers the
// case where the validator operator address itself cannot receive funds — its EVM
// address was re-associated (e.g. via associatePubKey) away from the direct-cast Sei
// address it was created under. The withdraw-address fallback in GetDelegatorWithdrawAddr
// resolves back to that same unreceivable operator address, so the commission
// force-withdraw fails. AfterValidatorRemoved runs during EndBlock, so it must not panic:
// the commission is routed to the community pool instead, which conserves value because
// the coins already back the distribution module account.
func TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator(t *testing.T) {
	app := seiapp.Setup(t, false, false, false)
	ctx := app.BaseApp.NewContext(false, tmproto.Header{})

	// The validator operator is the direct-cast Sei address of an EVM address.
	evmAddr := common.HexToAddress("0x3333333333333333333333333333333333333333")
	castAddr := sdk.AccAddress(evmAddr[:])
	valAddr := sdk.ValAddress(castAddr)
	valAccAddr := sdk.AccAddress(valAddr) // == castAddr

	require.True(t, app.BankKeeper.CanSendTo(ctx, castAddr))

	// Re-associate the EVM address to a different true Sei address, mirroring
	// associatePubKey after a validator was created under the direct-cast address.
	associatedAddr := seiapp.AddTestAddrs(app, ctx, 1, sdk.NewInt(1000000000))[0]
	app.EvmKeeper.SetAddressMapping(ctx, associatedAddr, evmAddr)

	// The operator/delegator address can no longer receive funds, and the
	// withdraw-address fallback resolves back to that same unreceivable address.
	require.False(t, app.BankKeeper.CanSendTo(ctx, castAddr))
	require.Equal(t, valAccAddr.String(), app.DistrKeeper.GetDelegatorWithdrawAddr(ctx, valAccAddr).String())

	commission := sdk.DecCoins{sdk.NewDecCoin("usei", sdk.NewInt(10))}
	coins := sdk.NewCoins(sdk.NewCoin("usei", sdk.NewInt(10)))
	distrAcc := app.DistrKeeper.GetDistributionAccount(ctx)
	require.NoError(t, apptesting.FundModuleAccount(app.BankKeeper, ctx, distrAcc.GetName(), coins))
	app.AccountKeeper.SetModuleAccount(ctx, distrAcc)

	app.DistrKeeper.SetValidatorOutstandingRewards(ctx, valAddr, types.ValidatorOutstandingRewards{Rewards: commission})
	app.DistrKeeper.SetValidatorAccumulatedCommission(ctx, valAddr, types.ValidatorAccumulatedCommission{Commission: commission})

	communityBefore := app.DistrKeeper.GetFeePool(ctx).CommunityPool.AmountOf("usei")
	moduleBalanceBefore := app.BankKeeper.GetBalance(ctx, distrAcc.GetAddress(), "usei")

	require.NotPanics(t, func() {
		app.DistrKeeper.Hooks().AfterValidatorRemoved(ctx, sdk.ConsAddress{}, valAddr)
	})

	// The commission could not be paid out, so it stays in the distribution module
	// account and is accounted to the community pool. No value leaves the module and
	// the unreceivable operator address receives nothing.
	communityAfter := app.DistrKeeper.GetFeePool(ctx).CommunityPool.AmountOf("usei")
	require.Equal(t, communityBefore.Add(sdk.NewDec(10)), communityAfter)
	require.True(t, app.BankKeeper.GetBalance(ctx, castAddr, "usei").IsZero())
	require.Equal(t, moduleBalanceBefore, app.BankKeeper.GetBalance(ctx, distrAcc.GetAddress(), "usei"))
}
