## Title
Entry-function signature legality check is fully skipped for modules with `version < VERSION_5`, allowing publish of modules with illegally-signed `entry` functions - (File: `third_party/move/move-bytecode-verifier/src/script_signature.rs`)

### Summary
`script_signature::verify_module` unconditionally returns `Ok(())` without inspecting a single function definition when `module.version < VERSION_5`, whereas for `module.version >= VERSION_5` it iterates every `is_entry` function and calls `verify_module_function_signature` to reject illegal signatures (e.g. reference return types, non-signer-first parameters, etc.). [1](#0-0) 

### Finding Description
`module.version` is populated directly from the binary's own version header during deserialization (`cursor.version()`), not derived from any compiler-enforced or protocol-enforced minimum: [2](#0-1) 

The publish-path deserialization (`aptos_vm.rs::deserialize_module_bundle`, and the analogous logic in `move-vm/runtime/src/storage/publishing.rs`) only constrains the *maximum* accepted binary format version via `deserializer_config`/`features.get_max_binary_format_version()`; I found no code enforcing a *minimum* module version on publish. [3](#0-2) [4](#0-3) 

`script_signature::verify_module` is invoked from the main verifier pipeline (`verifier.rs::verify_module_with_config`) as the *only* pass responsible for checking entry-function signature legality (reference returns, signer-argument ordering, etc.): [5](#0-4) 

The comment "important for not breaking old modules" indicates this version gate is a deliberate legacy-compatibility carve-out, added because the `entry`/`is_entry` concept was introduced together with the `VERSION_5` binary-format bump — old modules compiled before that point could not legitimately contain `is_entry` functions, so the check was historically unnecessary for them.

### What I could not fully verify
- I was unable to inspect the exact byte-level encoding logic in `deserializer.rs` (function-definition attribute/flags parsing) to confirm whether the `is_entry` bit is *structurally* readable/settable in a hand-crafted binary whose header declares `version < VERSION_5`, or whether the format for that version range omits/ignores the field entirely. If the format for old versions simply cannot encode `is_entry = true`, this bypass is unreachable in practice even for hand-crafted bytes.
- I did not confirm whether there is an independent runtime check (at entry-function dispatch/execution time, separate from the static bytecode verifier) that would reject a bad-signature "entry" function when actually invoked as a transaction entry point. The `2-script-visibility.md` doc suggests analogous `public(script)` functions were historically checked dynamically at call time, which — if an equivalent mechanism exists for `entry` functions today — would provide a second layer of defense not captured by this file alone.

### Impact Explanation
If the bypass is reachable (pending the two unverified points above), an unprivileged publisher could store a module where an `entry` function has an illegal signature (e.g., returns a reference), which the general bytecode verifier passes (reference returns are legal for ordinary functions) but which the entry-specific check exists specifically to forbid. This would desync "what verification guarantees" from "what is actually stored and potentially executable as an entry point."

### Likelihood Explanation
Requires the attacker to hand-craft raw module bytes with a manipulated version header — not achievable through the standard Move compiler, but within scope since raw bytecode publishing is an explicit unprivileged entry point per the review scope. Likelihood of actual exploitability is uncertain pending confirmation of the two open questions above.

### Recommendation
Verify whether `is_entry` can be structurally encoded as `true` for `version < VERSION_5` in the deserializer, and whether entry-function dispatch performs an independent runtime signature check. If both confirm the bypass is real and unmitigated, either (a) enforce a minimum accepted module version at publish time equal to `VERSION_5`, or (b) make `script_signature::verify_module` check `is_entry` functions regardless of `module.version`, only special-casing pre-`VERSION_5` modules if the format genuinely cannot represent `is_entry` there.

### Proof of Concept
1. Hand-construct a `CompiledModule` with a function definition where `is_entry = true` and whose return type in its `FunctionHandle` signature is a reference type (or any signature illegal per `no_additional_script_signature_checks`).
2. Set `module.version` to a value `< VERSION_5` (e.g. by using `serialize_for_version(Some(VERSION_5 - 1), ...)` if the serializer permits emitting `is_entry` at that version — unverified).
3. Publish the module through the standard publish flow; deserialization only enforces a maximum version, not a minimum.
4. Confirm `move_bytecode_verifier::verify_module` (specifically `script_signature::verify_module`) returns `Ok(())` without ever calling `verify_module_function_signature`/`no_additional_script_signature_checks` for that function, per the `if module.version < VERSION_5 { return Ok(()); }` short-circuit. pub fn verify_module(
    module: &CompiledModule,
    check_signature: FnCheckScriptSignature,
) -> VMResult<()> {
    // important for not breaking old modules
    if module.version < VERSION_5 {
        return Ok(());
    }

    for (idx, _fdef) in module
        .function_defs()
        .iter()
        .enumerate()
        .filter(|(_idx, fdef)| fdef.is_entry)
    {
        verify_module_function_signature(
            module,
            FunctionDefinitionIndex(idx as TableIndex),
            check_signature,
        )?
    }
    Ok(())
}
