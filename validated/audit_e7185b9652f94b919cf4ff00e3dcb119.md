### Title
Tron `IntentGatewayV2.withdraw()` trusts raw `.call()` success instead of validating the ERC20 return value, silently burning escrowed funds on non-standard tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The external report's core defect is: an amount taken from an untrusted/derived source (the auction `consideration.amount`) is used to move value without confirming it actually corresponds to a real, successful transfer. The Tron port of the Intent Gateway has the same broken invariant in its settlement path: `withdraw()` moves escrowed tokens using a raw low-level `.call()` to the ERC20 `transfer` selector and only checks that the *call did not revert* — it never decodes/validates the boolean return value. It then unconditionally decrements the internal escrow ledger (`_orders[commitment][token] -= amount`) as if the transfer succeeded.

### Finding Description
`onAccept()` on the Tron `IntentGatewayV2` decodes a `WithdrawalRequest` from an authenticated cross-chain `RedeemEscrow`/`RefundEscrow` message and calls `withdraw()`: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {

            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
```

The same pattern recurs in the fee-release branch (line 711) and in `SweepDust` handling (lines 652-673). All of these treat `success` from the raw `.call()` as proof the token moved. On EVM, TRC20/ERC20-like tokens that are not fully standards-compliant can return `false` (instead of reverting) on a failed `transfer` — this is a long-documented category of non-standard tokens. In that case `success` is `true` (the call didn't revert), the `if (!success)` guard passes, and the contract proceeds to permanently zero out the corresponding escrow slot even though the beneficiary received nothing.

Contrast this with the canonical EVM `IntentsBase._withdraw()`, which uses OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and enforces the boolean return (or absence thereof) and reverts on failure: [2](#0-1) 

The Tron contract deliberately replaces `SafeERC20` calls with raw `.call()` + selector encoding, dropping the return-value validation that the EVM implementation relies on for exactly this invariant.

### Impact Explanation
Once `_orders[body.commitment][token]` is decremented without the token actually moving, the beneficiary (the solver being paid for a fill, or the user being refunded on a cancellation) never receives their funds, and the escrow accounting for that token is now zero — there is no other mechanism to re-trigger payout for that commitment (the request has already been marked processed / `_filled` is set, and a fresh cross-chain message for the same commitment would be rejected as already handled by the source-side logic). The funds become permanently stuck in the contract, recoverable only via a privileged `SweepDust` message from Hyperbridge governance — which does not restore the affected user's claim, it merely lets governance sweep the balance to an arbitrary beneficiary. This is a direct, unauthorized loss of user/solver funds triggered purely by token behavior, with no dependency on a malicious relayer, prover, or governance actor.

### Likelihood Explanation
Triggering this does not require any privileged actor: it only requires the Intent Gateway's configured input/fee token on the Tron deployment to be one of the (well-known, widely used) tokens that return `false` rather than reverting on a failed transfer condition (e.g., insufficient balance/allowance edge cases, blacklist/pausable tokens, or bespoke TRC20 implementations common on Tron). Given Tron's ecosystem includes several such non-standard TRC20 tokens, and the gateway's `feeToken`/input tokens are configurable via governance (`UpdateParams`) rather than hardcoded to a known-safe token, this is a realistic operational condition rather than a contrived edge case.

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`, the fee-release branch, and `SweepDust` handling) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the EVM `IntentsBase.sol` implementation. This ensures a `false` return value (or missing return data misinterpreted as success) causes a revert instead of silently marking escrow as spent while no tokens moved.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with an input/fee token contract whose `transfer()` returns `false` on failure instead of reverting (a real, documented TRC20 pattern).
2. A user places a cross-chain order; tokens are escrowed and `_orders[commitment][token]` is credited.
3. Craft a state where the token's `transfer` call to the beneficiary fails "silently" (e.g., temporarily paused/blacklisted beneficiary, or a token quirk causing `transfer` to return `false` under specific conditions) at the moment `withdraw()` executes from an authenticated `RedeemEscrow`/`RefundEscrow` message.
4. `token.call(...)` returns `success = true` (no revert) with return data encoding `false`; the `if (!success) revert TransferFailed();` guard does not catch this because it only checks call-level success.
5. `_orders[body.commitment][token] -= amount` executes, zeroing the escrow slot, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — even though the beneficiary's token balance did not change.
6. The beneficiary has no path to reclaim the tokens; they remain stuck in the contract, recoverable only through a privileged Hyperbridge governance `SweepDust` message to an address of governance's choosing, not the original beneficiary.

```text
        address beneficiary = address(uint160(uint256(body.beneficiary)));
```

```text
        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
```
