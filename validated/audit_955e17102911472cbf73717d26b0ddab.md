### Title
Attacker-controlled participant count in `ThresholdKeys::read` causes disproportionate speculative memory allocation (uncontrolled resource consumption) - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` trusts a serialized `n` field (a `u16`) and immediately performs `Vec::with_capacity(usize::from(n))` before a single scalar byte is read or validated. An unprivileged party who can feed untrusted bytes to `ThresholdKeys::read` (an explicitly reachable deserialization API) can force a ~2 MB heap allocation from a handful of input bytes, on every invocation. This is the same bug class as the referenced Mattermost advisory (CWE-400, uncontrolled resource consumption via a small crafted input crashing/exhausting the server), mapped onto Serai's own code.

### Finding Description
In `ThresholdKeys::read`, the header is parsed and then `t`, `n`, and `i` are read as raw `u16`s: [1](#0-0) 

`n` is used unchecked as a capacity hint for the `Interpolation::Constant` coefficient vector: [2](#0-1) 

`Vec::with_capacity` allocates `n * size_of::<C::F>()` bytes immediately. For a 32-byte scalar (k256/ed25519 via `dalek-ff-group`), declaring `n = 65535` allocates roughly 2 MB; the backing store is committed before the first `C::read_F(reader)?` even touches the input. Only afterward does `ThresholdParams::new(t, n, i)` validate `n` (line 626), and the `verification_shares` loop (lines 621-623) additionally trusts `n` to bound how many group elements it attempts to deserialize.

So roughly 10 bytes of attacker-controlled input (curve ID check + `t`, `n`, `i` + interpolation tag `0`) deterministically trigger a multi-megabyte allocation. The allocation is freed when a subsequent `read_F` hits EOF, but an attacker who can issue many serialized-key inputs — or keep many parses in flight concurrently — can multiply this into sustained memory pressure and eventual OOM/abort, matching the "crafted input crashes the server" shape of CVE-2022-1982.

### Impact Explanation
- **Memory amplification**: ~6 attacker-controlled bytes → up to `65535 * size_of::<C::F>()` (≈2 MB per call for 32-byte fields) of committed heap memory, before any byte of the declared content is required to exist.
- **Repeated invocation**: each call to `ThresholdKeys::read` on attacker-supplied bytes re-triggers the allocation; there is no cap other than the `u16` width. Sustained requests produce sustained multi-MB-per-request churn, enabling resource exhaustion of the host process.
- The same `n` also sizes the `verification_shares` `HashMap` insert loop (lines 620-623), so the attacker controls parse work proportional to the claimed — not actual — participant set.

### Likelihood Explanation
`ThresholdKeys::read` is a public deserialization API intended for untrusted serialized key material; the rules explicitly list it as reachable by untrusted bytes. Triggering requires only flipping the interpolation byte to `0` (`Constant`) and setting `n = 0xFFFF`; no valid signature, key share, or threshold participation is needed to reach the allocation, since it precedes all validation (`ThresholdParams::new` runs only at line 625-626, after the allocation). The per-call amplification is bounded (~2 MB), so a single input is unlikely to crash a host on its own; impact requires repeated/concurrent malicious inputs, consistent with a Medium-severity DoS rather than a single-shot crash.

### Recommendation
Validate before allocating:

```rust
// in crypto/dkg/src/lib.rs, ThresholdKeys::read
let params = ThresholdParams::new(t, n, i).map_err(io::Error::other)?; // validate t/n/i first

let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::new(); // or with_capacity bounded by a sane threshold max
    for _ in 0 .. params.n() {
      res.push(C::read_F(reader)?);
    }
    res
  }),
  ...
};
```

Concretely: move `ThresholdParams::new(t, n, i)` (and any protocol-level `MAX_SHARES` check) ahead of the interpolation read, and either drop `with_capacity(n)` or clamp it to a small constant so the declared count cannot drive speculative allocation. The same ordering should apply to the `verification_shares` loop so it iterates a validated `n`.

### Proof of Concept
Conceptual byte stream fed to `ThresholdKeys::<Ristretto>::read` (or `Secp256k1`/`kp256`):

```
[ID_LEN_LE = len(C::ID) as u32][C::ID bytes]
[t = 0x0001][n = 0xFFFF][i = 0x0001]   // u16 LE
[interpolation = 0x00]                  // Constant
<EOF>
```

Trace:
1. Lines 578-588 pass the curve-ID check.
2. Lines 591-602 read `t=1, n=65535, i=1` without any bound check.
3. Line 608 executes `Vec::with_capacity(65535)` → ~2 MB committed for a 32-byte `C::F`, with zero payload bytes consumed.
4. The subsequent `C::read_F` fails on EOF and the allocation is released — but each new attacker-supplied blob repeats the allocation, and N concurrent parses commit N×2 MB.

Note on scope of verification: I was unable to fully audit `crypto/dkg/musig/src/lib.rs`, `crypto/dkg/recovery`, `crypto/dkg/dealer`, and `networks/bitcoin/src` for similar declared-length-driven allocations within this pass; the `ThresholdKeys::read` path is confirmed directly from source. A fuller pass over the remaining in-scope `read` implementations may reveal additional instances of the same pattern (e.g., `u32`-prefixed vectors elsewhere).
