### Title
SignableTransaction accepts arbitrarily small attacker-created inputs whose spend cost exceeds their value, draining multisig funds via fees - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes an unbounded `requestLiquidity` path where an unprivileged party can force a shared pool to move/absorb liquidity in a way that reduces everyone else's returns. The Serai analog lives in `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`. It accepts any `ReceivedOutput` as an input with only aggregate solvency checks (`input_sat >= payment_sat + needed_fee`), and no per-input minimum-value or profitability check. Since each Taproot key-spend input adds a fixed marginal weight (~230 WU, ~58 vbytes) to the transaction — a cost the transaction pays via `needed_fee = fee_per_vbyte * vbytes` — an input worth less than its marginal fee is net-negative: spending it burns more of the multisig's value in fees than it contributes.

### Finding Description
`SignableTransaction::new` (send.rs lines 150–256) builds a transaction from externally supplied `inputs: Vec<ReceivedOutput>`. The only checks are:

- `payments` amounts ≥ `DUST` (546 sats) — line 165–169; outputs are checked, **inputs are not**.
- Aggregate solvency: `input_sat < (payment_sat + needed_fee)` → `NotEnoughFunds` (line 215).
- Max standard weight (line 241) — bounds total size, not per-input value.

`calculate_weight_vbytes` (lines 62–127) correctly prices every input's fixed weight into `needed_fee`, so the fee charged scales with input count. But nothing rejects an input whose `output.value` is below that marginal cost. Any Bitcoin user can send arbitrarily small outputs (including below-dust-value, still consensus-valid if above ~294 sats for relay, or any value ≥ 1 sat if miner-included) to the multisig's `p2tr_script_buf` script_pubkey; the `Scanner`/`ReceivedOutput` path registers them as Serai-owned. When later spent, each such input subtracts from the fee pool or forces the `NotEnoughFunds` error path, denying the withdrawal.

This mirrors the reported bug class: an unbounded, permissionless action (create outputs / request liquidity) that forces a shared resource (multisig balance / vault liquidity) into an economically lossy state borne by other users.

### Impact Explanation
Attackers can manufacture Serai-owned inputs that are guaranteed net-negative to spend: a 300-sat input at 10 sat/vB costs ~580 sats of weight to include. Including it burns ~280 sats of other depositors' funds per input; at scale (hundreds of outputs under `MAX_STANDARD_TX_WEIGHT`) the loss is additive, and the aggregation transactions themselves (per `spec/processor/UTXO Management.md`) multiply it. Alternatively, dust inputs can be used to push `input_sat < payment_sat + needed_fee` and stall burn payouts. This is a Medium-severity economic drain / griefing vector against the shared multisig.

### Likelihood Explanation
Requires only that the attacker broadcast Bitcoin transactions to the multisig address — fully unprivileged, no validator or collusion needed. Realization of the loss depends on the processor's input-selection policy including attacker outputs, which the spec (`spec/processor/UTXO Management.md`, "Attacks by a Malicious Miner") acknowledges occurs and attempts to offset via a flat per-input fee charged at mint time — but `SignableTransaction::new` itself performs no validation, and outputs minted before fee policy or with manipulated fee estimates remain unfiltered at this layer.

### Recommendation
In `SignableTransaction::new`, reject or allow flagging inputs whose `output.value.to_sat()` is below the marginal vbyte cost of an input at the given `fee_per_vbyte` (the per-input vbytes derivable from `calculate_weight_vbytes(1, &[], None)` vs `(0, &[], None)`), plus `DUST`-adjacent margin. Also document that `ReceivedOutput`s below the spend threshold must be quarantined rather than aggregated.

### Proof of Concept
1. Attacker sends N outputs of ~330 sats each to the multisig's `p2tr_script_buf` script_pubkey (a normal anyone-can-pay Bitcoin send).
2. Scanner registers each as a `ReceivedOutput`.
3. A withdrawal `SignableTransaction::new(inputs=[victim UTXO] + dust inputs, payments, change, fee_per_vbyte=10)` computes `needed_fee` including ~58 vB × 10 sat/vB ≈ 580 sats per dust input.
4. Each dust input contributes 330 sats and consumes 580 sats of fee budget → ~250 sats of depositor value burned per input, all checks pass; alternatively with enough dust, `NotEnoughFunds` aborts the withdrawal.

Note: I was unable to read `networks/bitcoin/src/wallet/mod.rs` (the `Scanner`/`ReceivedOutput` definitions) in the available iterations, so the precise upstream filtering (if any) of sub-economical outputs is unverified; the finding stands on `send.rs` performing no such check itself.
