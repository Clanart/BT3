### Title
Peer-supplied preprocess/signature-share vectors are indexed without length checks, enabling an out-of-bounds panic that aborts the Bitcoin signing session - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` treat each participant's `Vec<Preprocess>` / `Vec<SignatureShare>` — deserialized from untrusted bytes via `read_preprocess` / `read_share` — as having one element per transaction input. They index or `remove` elements without validating the vector length, so a malicious signer can send a truncated vector and trigger an index-out-of-bounds panic, a denial of service analogous to the out-of-bounds read in `gd_gif_out.c` (CVE-2016-6161).

### Finding Description
In `TransactionSignMachine::sign`, the code iterates over `self.sigs` (one `AlgorithmSignMachine` per transaction input) and slices each participant's preprocess vector at position `c`: [1](#0-0) 

`commitments[c]` panics if the peer supplied fewer preprocesses than inputs. The peer's preprocesses arrive over the wire and are deserialized by `read_preprocess`, which reads `self.sigs.len()` preprocesses from the stream — but a malicious participant can simply end the stream early, or, more importantly, any aggregation layer passing a correctly-deserialized but shorter `Vec<Preprocess<Secp256k1, ()>>` reaches this unchecked index: [2](#0-1) 

The same defect exists in `TransactionSignatureMachine::complete`, which pops one share per input with `shares.remove(0)` — panicking on an empty/short `Vec<SignatureShare>` supplied by that participant: [3](#0-2) 

Neither site validates `commitments.len()`/`shares.len()` against `self.sigs.len()` before indexing.

### Impact Explanation
An unprivileged signing participant can crash the assembling node (or the sign machine) by submitting a preprocess or share vector shorter than the transaction's input count. Like the libgd bug, this is a remotely triggered out-of-bounds access caused by a crafted message; in Rust it manifests as a panic (DoS) rather than a memory read. For a threshold signer, aborting the session mid-aggregation wastes the round and, if the panic isn't caught, takes down the signer process — an availability failure reachable purely from public protocol input.

### Likelihood Explanation
Any participant in the FROST signing set for a Bitcoin spend can send a malformed `Vec<Preprocess>`/`Vec<SignatureShare>` — no collusion, leaked key, or privileged position required. The panic path is deterministic and trivially reachable whenever `commitments.len() < sigs.len()` (index panic at line 368) or `shares.is_empty()` when inputs remain (`remove(0)` panic at line 419). Severity is Medium: availability only, no secret leakage.

### Recommendation
Validate lengths before indexing:
- In `sign`, check `commitments.len() == self.sigs.len()` for every participant's preprocess vector and return `Err(FrostError::...)` instead of indexing `commitments[c]` blindly (or use `.get(c).ok_or(...)`).
- In `complete`, replace `shares.remove(0)` with a length-checked pop (e.g., `if shares.is_empty() { Err(...) }` or drain with a pre-check that each share vector has exactly `self.sigs.len()` elements).

// In TransactionSignMachine::sign, when c == 1:
