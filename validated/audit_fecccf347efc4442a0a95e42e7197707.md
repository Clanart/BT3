### Title
An unrelated later transaction overwrites a Bitcoin deposit’s instruction and can steal its mint - (File: `processor/src/networks/bitcoin.rs`)

### Summary

`Bitcoin::get_outputs` accumulates matching outputs across all transactions in a block, but reapplies each subsequent transaction’s `presumed_origin` and Serai data to every previously accumulated output. As a result, an attacker can place an ordinary transaction after a victim’s deposit in the same block and overwrite the victim output’s instruction metadata with attacker-controlled data, causing the victim’s deposit to be minted to the attacker or treated as an invalid instruction. [1](#0-0) [2](#0-1) 

### Finding Description

`get_outputs` initializes `outputs` once before iterating over `block.txdata[1 ..]`, then pushes every scanned output into that shared vector. [3](#0-2) 

After each transaction, the function only skips metadata assignment when `outputs` is empty; it does not require the current transaction to have produced an output. [4](#0-3) 

Consequently, when a later transaction contains no Serai output, `outputs.is_empty()` remains false because it still contains outputs from earlier transactions, so the later transaction’s first input and extracted data are assigned to all earlier outputs. [5](#0-4) 

When a later transaction does contain a Serai output, the same shared vector causes its metadata to be applied not only to that transaction’s outputs but also to every earlier output in the block. [6](#0-5) 

The attacker-controlled metadata can be supplied through an `OP_RETURN` output because `extract_serai_data` returns the pushed bytes from the first `OP_RETURN` output it finds. [7](#0-6) 

The downstream processor decodes `output.data()` as a `Shorthand`, converts it into a `RefundableInInstruction`, deducts aggregation costs, and emits an `InInstructionWithBalance`; a malformed instruction causes the output to be skipped, while a valid attacker instruction controls the mint destination. [8](#0-7) 

### Impact Explanation

An attacker can replace a victim deposit’s instruction with an attacker-controlled instruction, such as a transfer to the attacker’s Serai address, causing the victim’s external Bitcoin amount to be credited to the attacker. [2](#0-1) 

Alternatively, an attacker or even an unrelated later transaction can erase the victim’s valid instruction metadata, causing `instruction_from_output` to return no instruction while the underlying Bitcoin output remains under multisig control. [9](#0-8) [10](#0-9) 

This creates the same accounting-ownership failure as the reference bug: an asset transfer alters the claim associated with assets already received but not yet fully processed. [1](#0-0) 

### Likelihood Explanation

The attacker only needs to submit a normal Bitcoin transaction that is ordered after the victim’s deposit transaction in the same block; no validator key, leaked secret, malformed curve input, or privileged access is required. [1](#0-0) 

The later transaction does not need to pay the multisig because the metadata rewrite occurs whenever the shared `outputs` vector is non-empty. [11](#0-10) 

The attack requires winning same-block ordering after the victim transaction, which is possible by racing mempool inclusion but is less reliable without miner cooperation; however, unrelated ordinary traffic can also unintentionally corrupt earlier deposit metadata. [6](#0-5) 

### Recommendation

Maintain a per-transaction output vector and apply `presumed_origin` and `data` only to outputs produced by that transaction. [6](#0-5) 

For example, `get_outputs` should scan into `tx_outputs`, skip the transaction if that vector is empty, populate only `tx_outputs`, and then extend the block-level result. [6](#0-5)

      output.data.clone_from(&data);
    }
    output.presumed_origin.clone_from(&presumed_origin);

A regression test should place a valid deposit transaction and a later unrelated transaction carrying attacker-controlled `OP_RETURN` data in the same block and assert that the deposit retains its original data. [7](#0-6) [1](#0-0) 

### Proof of Concept

The following sequence demonstrates the flaw using only public Bitcoin transactions. [1](#0-0) 

1. The victim creates a transaction paying the multisig’s external Taproot script and carrying valid Serai instruction data. [12](#0-11) [7](#0-6) 
2. The attacker creates an unrelated transaction, with no output to the multisig, carrying an `OP_RETURN` encoding a `Shorthand` that mints the deposit to the attacker. [7](#0-6) 
3. Both transactions are included in the same block, with the attacker transaction ordered after the victim transaction. [13](#0-12) 
4. During the victim transaction iteration, the victim’s output is pushed into `outputs`. During the attacker transaction iteration, `outputs` remains non-empty even though the attacker transaction contributed no outputs, so the attacker’s origin and data are assigned to the victim output. [11](#0-10) 
5. `instruction_from_output` then decodes the attacker’s overwritten data and produces an instruction for the victim’s Bitcoin balance. [8](#0-7) 

```rust
// Conceptual regression test:
let victim_tx = transaction_paying_script(
  vault_external_script.clone(),
  100_000,
  valid_serai_data_for_victim(),
);

let attacker_tx = unrelated_transaction_with_op_return(
  shorthand_transfer_to(attacker_serai_address),
);

let block = block_with_transactions(vec![
  coinbase_tx,
  victim_tx,
  attacker_tx,
]);

let outputs = bitcoin.get_outputs(&block, vault_key).await;

assert_eq!(outputs.len(), 1);
assert_eq!(outputs[0].kind(), OutputType::External);

// Currently fails: the victim's data was overwritten by the attacker's
// transaction even though the attacker transaction paid no Serai output.
assert_eq!(outputs[0].data(), valid_serai_data_for_victim());
```

The decisive assertion follows because `outputs` is shared across transaction iterations and every output in it is overwritten with the latest transaction’s `presumed_origin` and `data`. [6](#0-5)
