### Title
Server-Side Request Forgery in DataLayer mirror subscription downloads via attacker-controlled on-chain mirror coins - ([File: chia/data_layer/data_layer_wallet.py])

### Summary
Any wallet can broadcast a spend bundle that creates a coin with the DataLayer mirror puzzle hash and arbitrary URL memos. If the victim's wallet is tracking the referenced `launcher_id` (e.g., because the victim subscribed to that DataLayer store), the wallet unconditionally records the attacker-supplied URLs as a "mirror" for that store. The DataLayer service periodically pulls these URLs from the wallet and uses them, without any allow-listing or validation, as HTTP endpoints to fetch delta/full files, causing the DataLayer node to issue outbound HTTP requests to attacker-chosen hosts.

### Finding Description
`DataLayerWallet.coin_added()` fires for *any* coin observed on chain whose puzzle hash equals `create_mirror_puzzle().get_tree_hash()`, regardless of who created it: [1](#0-0) 

It decodes `launcher_id` and `urls` straight from the parent spend's puzzle/solution memos via `get_mirror_info()`: [2](#0-1) 

The only gate is `is_launcher_tracked(launcher_id)` — true whenever the wallet is subscribed to (or owns) that store id, which is normal, expected DataLayer-client behavior. There is no check that the coin, the amount, or the memo URLs originated from the store owner, the subscriber themselves, or any trusted party. The `ours` flag is only used for bookkeeping, not to reject or filter untrusted mirrors: [3](#0-2) 

The `DataLayer` service then periodically calls `update_subscriptions_from_wallet()`, which fetches these mirror records via `dl_get_mirrors` and stores their URLs as subscription server candidates with zero filtering: [4](#0-3) 

`fetch_and_validate()` then randomly selects one of these (attacker-influenced) server URLs and passes it into `insert_from_delta_file()` → `download_file()`: [5](#0-4) 

When no downloader plugin is configured (the default HTTP path), `download_file()` calls `http_download()`, which performs an unrestricted `aiohttp` GET against `server_info.url + "/" + filename` — the URL is fully attacker-controlled and no scheme/host/IP validation (e.g., blocking link-local/metadata/private ranges) is performed: [6](#0-5) [7](#0-6) 

This is structurally the same bug class as the referenced Shopware SSRF: a feature that fetches remote content by URL supplied through an untrusted, user-influenced channel, with no destination validation, causing the server to issue requests wherever the attacker points it. Here the "untrusted channel" is on-chain mirror coin creation, reachable by anyone who can submit a standard spend bundle creating a coin with the well-known mirror puzzle hash and appropriate `CREATE_COIN` memos — no special node/peer privilege is required.

The `.cursor/context/data-layer.md` doc itself flags this exact pattern: "Plugin and mirror URLs are external trust inputs. Downloaded data must continue to be verified against wallet-advertised roots" — confirming mirror URLs are explicitly understood as untrusted, yet the URL destination itself is not validated before an outbound request is made.

### Impact Explanation
Any Chia full-node/wallet operator running the DataLayer service and subscribed to (or owning) at least one DataLayer store can be coerced into making outbound HTTP requests to arbitrary attacker-chosen hosts/ports (e.g., internal service endpoints, cloud metadata services, or other hosts on the operator's network) by anyone able to submit a cheap spend bundle. While the downloaded content is later hash-validated before being committed as data-store state (limiting direct data-poisoning), the SSRF itself lets an attacker: (1) probe/port-scan internal infrastructure reachable from the victim's DataLayer node, (2) trigger requests against internal admin/metadata endpoints that have side effects on GET, and (3) cause resource consumption / repeated outbound connections at low cost to the attacker (a single low-value mirror coin). This satisfies CWE-918 SSRF and is High severity per the same class as the referenced Shopware advisory, though full data exfiltration back to the attacker is constrained by the merkle-root validation step in `insert_into_data_store_from_file()`.

### Likelihood Explanation
Likelihood is high for any user who runs the DataLayer service and subscribes to third-party DataLayer stores (a normal, documented DataLayer-client workflow). The attacker only needs to: (1) know a `launcher_id` the victim tracks (store ids are public), and (2) submit one on-chain spend creating a coin with the mirror puzzle hash and a `CREATE_COIN` condition whose memos encode `[launcher_id, url, ...]`, at minimal cost (low coin amount/fee). No malicious peer, node compromise, or leaked key is required — this is pure spend-bundle crafting reachable by any wallet.

### Recommendation
Do not blindly trust arbitrary on-chain mirror URLs as network destinations:
- In `DataLayerWallet.coin_added()` / `DataStore`/`DataLayer` mirror handling, restrict automatic HTTP fetches to `ours=True` mirrors (self-created) or store-owner-attested mirrors by default, requiring explicit opt-in/allow-listing before an untrusted third-party mirror URL is used for network fetches.
- In `download_data.http_download()`, validate the resolved URL against an SSRF-safe policy (block loopback, link-local, private/internal, and cloud-metadata IP ranges) before issuing the request, and enforce allowed schemes (`http`/`https` only).
- Surface an explicit user-facing warning/config flag when the DataLayer service is about to contact a URL learned only from chain data rather than user-provided subscription URLs.

### Proof of Concept
1. Victim runs `chia data subscribe -i <public_store_launcher_id>` (or owns that store), causing `is_launcher_tracked(launcher_id)` to become true. [8](#0-7) 
2. Attacker crafts and submits a standard spend bundle that spends any owned coin, creating a new coin with `puzzle_hash == create_mirror_puzzle().get_tree_hash()` and a `CREATE_COIN` condition whose memo list is `[launcher_id, b"http://169.254.169.254/latest/meta-data/"]` (mirroring the format `create_new_mirror()` normally produces). [9](#0-8) 
3. Once confirmed, the victim's `coin_added()` handler records this as a tracked mirror for `launcher_id` regardless of who created it. [10](#0-9) 
4. On the victim's next `periodically_manage_data()` cycle, `update_subscription()` calls `update_subscriptions_from_wallet()` then `fetch_and_validate()`, which may select the attacker's URL and issue an HTTP GET from the victim's DataLayer node via `http_download()`. [11](#0-10) 

Note: I was not able to execute this end-to-end in a live environment (no filesystem/terminal access in this mode); the trace above is based on static code-path analysis across `data_layer_wallet.py`, `dl_wallet_store.py`, `data_layer.py`, and `download_data.py`. Confirming exact runtime behavior (e.g., minimum coin amount accepted, exact backoff/selection probability among multiple mirrors) would require running the existing test harness (`chia/_tests/core/data_layer/test_data_rpc.py::test_mirrors`, `chia/_tests/wallet/rpc/test_dl_wallet_rpc.py`) with a crafted non-`create_new_mirror` spend bundle.

```python
def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```

```python
async def download_file(
    data_store: DataStore,
    target_filename_path: Path,
    store_id: bytes32,
    root_hash: bytes32,
    generation: int,
    server_info: ServerInfo,
    proxy_url: str | None,
    downloader: PluginRemote | None,
    timeout: aiohttp.ClientTimeout,
    client_foldername: Path,
    timestamp: int,
    log: logging.Logger,
    grouped_by_store: bool,
    group_downloaded_files_by_store: bool,
    max_delta_file_size: int,
) -> bool:
    if target_filename_path.exists():
        return True
    filename = get_delta_filename(store_id, root_hash, generation, grouped_by_store)

    if downloader is None:
        # use http downloader - this raises on any error
        try:
            await http_download(
                target_filename_path, filename, proxy_url, server_info, timeout, log, max_delta_file_size
            )
        except (asyncio.TimeoutError, aiohttp.ClientError, MaxDeltaFileSizeExceededError):
            new_server_info = await data_store.server_misses_file(store_id, server_info, timestamp)
            log.info(
                f"Failed to download {filename} from {new_server_info.url}."
                f"Miss {new_server_info.num_consecutive_failures}."
            )
            log.info(f"Next attempt from {new_server_info.url} in {new_server_info.ignore_till - timestamp}s.")
            return False
        return True
```

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
