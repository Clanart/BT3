### Title
SSRF via unvalidated on-chain mirror URLs fetched by Data Layer HTTP downloader - (File: chia/data_layer/download_data.py)

### Summary
Any wallet user can publish an arbitrary URL on-chain as a Data Layer "mirror" for a store, and any other node subscribing to that store will automatically issue outbound HTTP GET requests to that attacker-chosen URL with no scheme, host, or destination validation — a server-side request forgery analogous to CVE-2017-14323's unvalidated `upfile`/remote-URL fetch.

### Finding Description
`DataLayerWallet.create_new_mirror` lets any wallet holder create an on-chain "mirror" coin whose puzzle memo embeds an arbitrary list of URL strings with no format/scheme restriction: [1](#0-0) 

This is exposed directly via the `dl_new_mirror` wallet RPC (and the `add_mirror` CLI/DataLayer RPC), which any authorized wallet client can call with attacker-chosen `urls`: [2](#0-1) [3](#0-2) 

Any full/DataLayer node that subscribes to that `store_id` reads these mirror URLs back off-chain via `update_subscriptions_from_wallet`, which stores them verbatim as `ServerInfo.url` with only a `rstrip("/")` — no scheme allowlist, no check against internal/loopback/link-local/cloud-metadata addresses: [4](#0-3) 

Later, `fetch_and_validate` iterates these stored server URLs and triggers a download attempt against each one: [5](#0-4) 

The actual network request is performed by `http_download`, which does an unauthenticated `aiohttp` GET to `server_info.url + "/" + filename` with no validation that the URL points to a legitimate external mirror server rather than an internal service: [6](#0-5) 

The only place any URL-scheme validation exists in the Data Layer codebase is the separate, opt-in `s3_plugin_service.py`, which is not used for the default HTTP path.

### Impact Explanation
Any user who can send a small transaction (a mirror coin with dust/minimal amount) can force every other node that subscribes to that Data Layer store to make outbound HTTP requests to attacker-chosen hosts/ports — including `127.0.0.1`, internal RPC ports, cloud metadata endpoints (e.g. `169.254.169.254`), or other internal-network services reachable from the DataLayer host. This can be used for internal network reconnaissance/port-scanning, triggering unauthenticated internal admin actions, or leaking response data/headers into DataLayer logs (`log.info`/`log.warning` include the URL and errors), and can be repeated at will since mirrors persist on-chain and are re-fetched by every syncing peer. This satisfies the "invalid/attacker-triggered transaction-processing/internal-request" impact class analogous to the referenced CVE.

### Likelihood Explanation
High reachability: creating a mirror only requires a funded wallet and calling `dl_new_mirror`/`add_mirror`, both are standard, unprivileged, already-documented Data Layer wallet operations. Any Data Layer participant subscribing to the malicious store will automatically trigger the SSRF without further interaction, and the mirror URL persists on-chain so it will be reprocessed on every sync attempt.

### Recommendation
Validate mirror URLs before storing/using them for downloads: restrict to `http`/`https` schemes, reject loopback/link-local/private/multicast/metadata IP ranges (or require explicit operator opt-in / allowlist for such destinations), and consider allowing operators to configure a mirror URL allowlist. At minimum, apply the same `urlparse`-based scheme/host checks that `s3_plugin_service.py` already performs to the default `http_download` path in `chia/data_layer/download_data.py` and `chia/data_layer/data_layer.py`.

### Proof of Concept
1. Attacker with a funded wallet calls `dl_new_mirror` (RPC or `chia data add_mirror`) for a `store_id`, with `urls=["http://169.254.169.254"]` (or `http://127.0.0.1:<internal-port>`), and a minimal amount/fee.
2. Once confirmed on-chain, any node that runs `chia data_layer` and subscribes to that `store_id` (e.g., because it wants the store's data) calls `update_subscriptions_from_wallet`, which stores the attacker's URL as a `ServerInfo`. [4](#0-3) 
3. On the next sync cycle, `fetch_and_validate` picks this `server_info` and calls `insert_from_delta_file` → `download_file` → `http_download`, causing the victim node to issue `GET http://169.254.169.254/<filename>` (or the internal target) from its own network position. [6](#0-5) 
4. The attacker observes side effects (timing, error messages, logged URLs) or, if the internal target accepts unauthenticated GETs with side effects, triggers unintended internal actions — classic SSRF.

    """

    async with aiohttp.ClientSession() as session:
