### Title
Crafted DKG blame message panics node via unchecked HashMap index in `Decryption::decrypt_with_proof` - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` directly instead of using `.get()`. `enc_keys` is only populated for participants that successfully registered an `EncryptionKeyMessage` (registration asserts on duplicates but never guarantees presence). If the blame/decryption path is invoked with a `decryptor` participant that never registered a key — e.g., a participant index supplied inside a crafted `InvalidDkgShare` / blame message — the indexing panics, crashing the signer, analogously to CVE-2017-7244's invalid-memory-read DoS via crafted input.

### Finding Description
`enc_keys` is a `HashMap<Participant, C::G>` populated only by `Decryption::register`, which inserts one entry per participant that sends a well-formed `EncryptionKeyMessage`. Nothing guarantees every valid `Participant` index has an entry — a participant who never sent (or whose registration was rejected for) a key message leaves no entry. In `decrypt_with_proof`, the code evaluates `&self.enc_keys[&decryptor]` when building the DLEq points to verify:

```rust
// crypto/dkg/pedpop/src/encryption.rs
&[self.enc_keys[&decryptor], *proof.key],
```

`HashMap`'s `Index` impl panics on missing keys. The same pattern exists in `Encryption::encrypt` (`self.decryption.enc_keys[&participant]`, encryption.rs:466). Since `Participant` values are attacker-influenced (parsed from network messages via `Participant::new`, which only bounds the value, not membership in the registered set), a malicious validator can trigger a panic on an honest processor during blame verification by causing a `decryptor` participant that has no registered encryption key to be referenced.

### Impact Explanation
A panic in this path aborts the DKG/blame-handling task. Depending on how the caller isolates the panic, this can kill the key-generation attempt or crash the processor node — a remote denial of service caused purely by crafted protocol input, matching the bug class (untrusted input → unchecked access → crash) of the reference CVE. No secret material is leaked, so impact is availability-only.

### Likelihood Explanation
Reachability requires the blame/decrypt path to be invoked with a `decryptor` absent from `enc_keys`. This happens when an accusation is processed against/among participants for whom no `EncryptionKeyMessage` was ever registered (e.g., a participant removed mid-attempt, or an index validated as a `Participant` but never registered). `InvalidDkgShare` transactions carry attacker-controlled `accuser`/`faulty` fields, so an adversary participating in or observing the DKG can plausibly steer execution into this branch. Moderate likelihood: it needs a specific protocol state (pending blame against an unregistered decryptor), but no privileged position.

### Recommendation
Replace indexing with checked lookups and return `DecryptionError::InvalidProof` (or a new variant) when the decryptor/participant has no registered key:

```rust
let Some(dec_key) = self.enc_keys.get(&decryptor) else {
  Err(DecryptionError::InvalidProof)?
};
```

Also validate `accuser`/`faulty` participant membership against the registered key set before calling `decrypt_with_proof`.

### Proof of Concept
Conceptually: during a DKG attempt, have one participant withhold or corrupt their `EncryptionKeyMessage` so `enc_keys` has no entry for them. Then submit a blame/`InvalidDkgShare` naming that participant (or arrange for `decrypt_with_proof` to run with `decryptor` = an index in `1..=n` that never registered). `self.enc_keys[&decryptor]` at `crypto/dkg/pedpop/src/encryption.rs:388` evaluates `HashMap::index` on the missing key and panics with "key not found", aborting the verifier — reproducible in a unit test by constructing a `Decryption`, registering a subset of participants, and calling `decrypt_with_proof` with an unregistered `decryptor`.

Caveat: `decrypt_with_proof` is `pub(crate)`; the exact upstream caller passing `decryptor` (in pedpop's share-blame verification) was not fully traced within the available search iterations, so end-to-end reachability from a serialized `InvalidDkgShare` is inferred from the blame flow (`ProcessorMessage::InvalidShare`/blame handling in `processor/src/key_gen.rs`) rather than fully verified line-by-line.
