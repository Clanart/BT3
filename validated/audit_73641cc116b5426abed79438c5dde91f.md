### Title
Bank precompile `sendNative` bypasses `SendEnabled` and `BlockedAddr` checks enforced by `MsgSend` - (File: `precompiles/bank/bank.go`)

### Summary
The bank precompile exposes two similar value-transfer entry points, `send` and `sendNative`. `send` routes through `bankMsgServer.Send`, which enforces the same guard checks as any bank message. `sendNative` instead calls the send keeper directly, skipping those same guards — this is the same bug class as the missing `whenNotPaused` modifier in the original report: one of several functionally-equivalent transfer paths omits a check its siblings enforce.

### Finding Description
`PrecompileExecutor.send` builds a `banktypes.MsgSend` and executes it through `p.bankMsgServer.Send(...)`, which is `msgServer.Send` in `sei-cosmos/x/bank/keeper/msg_server.go`. That handler enforces `IsSendEnabledCoins`, sender/receiver `IsInDenomAllowList`, and `BlockedAddr` on the receiver before calling `SendCoins`: [1](#0-0) 

`PrecompileExecutor.sendNative`, however, moves `usei`/`wei` value directly via `p.bankKeeper.SendCoinsAndWei(...)`, bypassing `msgServer.Send` entirely: [2](#0-1) 

`SendCoinsAndWei` in the send keeper performs no `IsSendEnabledCoins` check and no `BlockedAddr` check on the receiver — it only checks `CanSendTo` (registered recipient checkers) inside `AddWei`/`AddCoins`: [3](#0-2) [4](#0-3) 

Both `send` (via `MsgSend`) and `sendNative` are declared as transactional (state-mutating) methods of the same precompile and are reachable by any EVM caller: [5](#0-4) 

So `IsSendEnabledCoins`/`BlockedAddr`/allow-list enforcement, which exists specifically so governance/operators can disable transfers of `usei` (the same base denom moved by `sendNative`) or protect specific addresses, has no effect on value moved through the `sendNative` EVM path. `BlockedAddr` in particular also blocks synthetic "coinbase" addresses used for EVM fee accounting: [6](#0-5) 

### Impact Explanation
If the `usei` (or any other denom moved through the same code path) `SendEnabled` param is turned off — the operational lever intended for emergencies such as a hack or exploit affecting the bank module — value can still be transferred between EVM-associated Sei addresses via `Bank.sendNative(...)` (i.e., sending `msg.value` through the precompile), completely defeating the pause/disable mechanism for that class of transfer. Additionally, because `BlockedAddr` is not checked on the receiver, `sendNative` can move funds directly into addresses the protocol has deliberately blocked from receiving funds (e.g., module accounts, the reserved EVM coinbase address prefix), which the `MsgSend` path explicitly forbids. This can enable unauthorized transfers/fund manipulation that the rest of the bank module's controls are designed to prevent.

### Likelihood Explanation
`sendNative` is a public, unprivileged, non-static (state-mutating) precompile method reachable by any EVM transaction sender with a Sei-associated address; no special privileges are required, and the discrepancy exists in the base transfer code path used whenever value is sent through the bank precompile.

### Recommendation
Route `sendNative` through the same enforcement used by `MsgSend`/`msgServer.Send` before moving funds: call `IsSendEnabledCoins` for the transferred denom, and check `BlockedAddr` (and, if applicable, `IsInDenomAllowList`) on the receiver, returning an error and aborting the precompile call if any check fails — mirroring the guards already present in `sei-cosmos/x/bank/keeper/msg_server.go`.

### Proof of Concept
1. Governance/operator disables `SendEnabled` for `usei` in bank params (e.g., in response to an ongoing exploit) to halt native transfers.
2. An attacker calls the `Bank` precompile's `sendNative` method (`0x0000000000000000000000000000000000001001`) with `msg.value` set, sending native `usei`/wei from their EVM-associated Sei account to another address.
3. `PrecompileExecutor.sendNative` calls `bankKeeper.SendCoinsAndWei` directly; since this path never calls `IsSendEnabledCoins`, the transfer succeeds despite `SendEnabled=false`.
4. Separately, an attacker can call `sendNative` to move funds into an address on the `BlockedAddr` list (e.g., a module account or the reserved EVM coinbase address range), which would be rejected if attempted via a normal `MsgSend`, because `sendNative` never calls `BlockedAddr`.

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

	err = k.SendCoins(ctx, from, to, msg.Amount)

// IsSendEnabledCoin returns the current SendEnabled status of the provided coin's denom
func (k BaseSendKeeper) IsSendEnabledCoin(ctx sdk.Context, coin sdk.Coin) bool {
	return k.GetParams(ctx).SendEnabledDenom(coin.Denom)
}

// BlockedAddr checks if a given address is restricted from
// receiving funds.
func (k BaseSendKeeper) BlockedAddr(addr sdk.AccAddress) bool {
	if len(addr) == len(CoinbaseAddressPrefix)+8 {
		if bytes.Equal(CoinbaseAddressPrefix, addr[:len(CoinbaseAddressPrefix)]) {
			return true
		}
	}
	return k.blockedAddrs[addr.String()]
}

func (k BaseSendKeeper) SendCoinsAndWei(ctx sdk.Context, from sdk.AccAddress, to sdk.AccAddress, amt sdk.Int, wei sdk.Int) error {
	if err := k.SubWei(ctx, from, wei); err != nil {
		return err
	}
	if err := k.AddWei(ctx, to, wei); err != nil {
		return err
	}
	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.EventTypeWeiTransfer,
			sdk.NewAttribute(types.AttributeKeyRecipient, to.String()),
			sdk.NewAttribute(types.AttributeKeySender, from.String()),
			sdk.NewAttribute(sdk.AttributeKeyAmount, wei.String()),
		),
	})
	if amt.GT(sdk.ZeroInt()) {
		return k.SendCoinsWithoutAccCreation(ctx, from, to, sdk.NewCoins(sdk.NewCoin(sdk.MustGetBaseDenom(), amt)))
	}
	return nil
}
