## Title
Payout tx's `SIGHASH_SINGLE|ANYONECANPAY` signature leaves the OP_RETURN operator-attribution output unauthenticated, allowing anyone to hijack or destroy reimbursement credit via mempool replacement - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The withdrawal (`payout_tx`) construction signs the user-provided input/output pair with `TapSighashType::SinglePlusAnyoneCanPay`, which only commits to input #0 and its matching output #0 (the user's payout). The anchor output and, critically, the OP_RETURN output that records *which operator fronted the withdrawal* are left completely outside the signed message. The system later determines who gets reimbursement credit purely by parsing that unauthenticated OP_RETURN from whichever version of the transaction actually confirms. Anyone observing the transaction on the network (no operator/verifier role required) can therefore replace an honest operator's broadcast payout tx with one that reuses the same signed input/output but swaps in an arbitrary operator's (or no operator's) xonly public key in the OP_RETURN, stealing or destroying reimbursement credit while the user still gets paid.

### Finding Description
`create_payout_txhandler` builds the payout transaction with exactly one signed input (the withdrawal UTXO) and three outputs: the user's payout, an anchor, and an OP_RETURN naming the operator that "fronted" the peg-out: [1](#0-0) 

The witness placed on this transaction is the *user's* signature, using `TapSighashType::SinglePlusAnyoneCanPay`, enforced by the RPC parser: [2](#0-1) 

`SIGHASH_SINGLE` only binds input #0 to its same-index output (the user payout output); `ANYONECANPAY` only authorizes the specific signed input. Neither the anchor output nor the OP_RETURN output (holding the fronting operator's xonly pubkey) is covered by this signature — confirmed by the test/setup helper computing the sighash the same way: [3](#0-2) 

Downstream, the protocol determines "who gets reimbursed" purely by re-parsing this unauthenticated OP_RETURN from whichever transaction version actually confirms on-chain, with no check that the named operator ever produced or signed that specific transaction: [4](#0-3) 

That value is persisted as the "payer" and later used to find "unhandled payouts" for a given operator and drive reimbursement: [5](#0-4) [6](#0-5) 

Because the input outpoint, its scriptPubkey/value, and the user's output are the only things cryptographically bound by the witness, **any unprivileged party who observes the still-unconfirmed payout transaction in the Bitcoin mempool can copy that witness onto a new transaction** that spends the identical input to the identical user output, but with a different anchor value (to bump the fee for RBF) and an arbitrary OP_RETURN payload — naming a different registered operator, or no valid operator at all. Once that replacement confirms:
- The honest operator who actually broadcast the original tx will never be recorded as `payout_payer_operator_xonly_pk` for this withdrawal, and can never claim reimbursement for a payout it did in fact front — breaking the equality `credited operator == party that funded the payout` on the "honest operator wronged" side.
- An arbitrary third-party-named operator (who did nothing) becomes the DB-recorded payer, and its `PayoutCheckerTask` will treat this as its own unhandled payout, proceed to kickoff, and be reimbursed from the shared vault for a payout it never funded — breaking the same equality on the "unauthorized credit" side.

This directly mirrors the reported ERC20 bug class: the contract/protocol infers "who paid" from a signal (a balance delta / here, an OP_RETURN field) that is not cryptographically bound to the actual paying party, so it can be forged or hijacked by an unrelated actor.

### Impact Explanation
This breaks the binding "the operator credited for a payout versus the operator that actually fronted it," matching the Critical impact criteria: an operator can be reimbursed for a payout it never funded, and/or an honest operator can be permanently unable to be reimbursed for a payout it legitimately fronted, once its transaction is replaced before confirmation.

### Likelihood Explanation
No privileged role (verifier/operator/watchtower/aggregator/security council) is required — the attack only needs the ability to observe the Bitcoin P2P mempool (any node/peer) and broadcast a fee-bumped replacement transaction that reuses the honest party's still-valid, unmodified witness for input #0. This is standard, unprivileged RBF behavior; the attacker pays only the marginal extra fee needed to win replacement, and never needs any private key.

### Recommendation
Bind the operator attribution (OP_RETURN) and the fee-paying output cryptographically to the transaction's economic authorization, e.g., by having the fronting operator co-sign the whole transaction (covering the OP_RETURN and anchor outputs) rather than leaving them outside of any signature, or by requiring an additional operator-signed commitment (e.g., a signature over the payout txid plus the intended operator pubkey) that the verifiers/`update_finalized_payouts` logic checks before trusting the OP_RETURN as proof of who paid.

### Proof of Concept
1. Operator A calls `withdraw()` with a valid user `in_signature` (`SinglePlusAnyoneCanPay`), broadcasting a `payout_tx` that pays the user and embeds Operator A's xonly pubkey in the OP_RETURN (per `create_payout_txhandler`).
2. Before the transaction confirms, an unprivileged attacker observes it in the mempool and extracts the witness for input #0 (the only signed part).
3. The attacker constructs a new transaction spending the same input with the identical user-payout output (output #0, unchanged, still validates against the SIGHASH_SINGLE commitment), but changes the anchor output value (to increase the fee for RBF) and swaps the OP_RETURN to embed a different registered operator B's xonly pubkey (or garbage), then broadcasts it with a higher fee.
4. The attacker's transaction replaces Operator A's in the mempool and confirms.
5. `update_finalized_payouts` (`core/src/verifier.rs`) parses the OP_RETURN of the confirmed tx and records Operator B as `payout_payer_operator_xonly_pk` in the DB.
6. Operator B's `PayoutCheckerTask` discovers the "unhandled payout" credited to it and proceeds to kickoff and get reimbursed from the vault for a withdrawal it never fronted, while Operator A — who actually paid the user — is never credited and can never be reimbursed for that withdrawal.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
