### Title
Self-destructing a native-ERC20 contract permanently strands module-escrowed native coins with no recovery path - (File: `x/erc20/keeper/msg_server.go`)

### Summary
`ConvertCoin` and `ConvertERC20` both contain a "cleanup" branch that fires the moment the underlying ERC20 contract for a native-ERC20 `TokenPair` is found to be self-destructed (`acc == nil || !acc.HasCodeHash()`). In that branch the module unconditionally calls `k.DeleteTokenPair(ctx, pair)` and returns, permanently erasing the denom↔contract mapping that is the *only* lookup path used by `MintingEnabled`/`GetTokenPairID` to reach the escrowed native coins held by the `erc20` module account. [1](#0-0) 

### Finding Description
The `erc20` module backs every native-ERC20 token pair with a 1:1 escrow: whenever a user converts native `Coin` → ERC20 via `ConvertCoinNativeERC20`, the coins are locked in the module account and an equivalent ERC20 balance is unescrowed/transferred out of the module's own ERC20 holdings. [2](#0-1) 

That escrow can only ever be reversed by the symmetric `ConvertERC20` → `convertERC20IntoCoinsForNativeToken` path, which requires the `TokenPair` record (looked up by `MintingEnabled`/`GetTokenPairID`) to still exist.

If the ERC20 contract self-destructs (an ordinary, unprivileged action any contract owner or malicious contract logic can trigger), the very next unrelated user who calls `ConvertCoin` or `ConvertERC20` for that pair causes the module to detect the missing code hash and call `DeleteTokenPair`, which wipes the denom map, the ERC20-address map, and the allowances map in one shot: [3](#0-2) 

Once the mapping is gone, `MintingEnabled` can never resolve `pair.Denom` or `pair.Erc20Address` again, so there is no code path left in `x/erc20` (or anywhere else in the module) that can move the module-account's escrowed native coins back to the original depositor(s). The coins are not burned outright (unlike the `removeListing` pattern in the report), but they are rendered permanently unreachable/frozen in the module account — functionally equivalent to a forced, un-refundable loss of the depositor's stake, since no withdrawal or migration mechanism exists once the `TokenPair` record is deleted.

Note: any user (not just the contract owner) can be the one whose `ConvertCoin`/`ConvertERC20` call triggers the `DeleteTokenPair`, so the destructive state transition (deletion of the escrow's only reference) is reachable by an ordinary, unprivileged transaction — it does not require governance or any privileged role.

### Impact Explanation
This matches the "Critical permanent freezing, locking, theft, or unauthorized extraction of user funds ... or token-pair-backed balances" allowed-impact category: native coins escrowed in the `erc20` module account to back a native-ERC20 token pair become permanently unrecoverable once the pair record is deleted following contract self-destruction, with no code path (via `ConvertERC20`, governance `ToggleConversion`/`RegisterERC20`, or otherwise) to redeem or reclaim them. Every prior depositor who escrowed coins against that ERC20 (and had not yet converted back before the self-destruct) permanently loses access to those funds.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a native-ERC20 token pair with outstanding escrowed coins, and (2) the paired ERC20 contract to become code-less (self-destructed, or — depending on `HasCodeHash` semantics — never deployed/failed deployment). Self-destructing a contract is a normal, permissionless EVM operation available to the contract's own logic/owner, and the deletion trigger itself only requires any user to submit an ordinary `MsgConvertCoin`/`MsgConvertERC20` afterward. No governance or validator collusion is needed.

### Recommendation
- Short term: Before calling `DeleteTokenPair` on detecting a code-less ERC20 contract, refund/unwind any outstanding native-coin escrow held by the module account for that pair (e.g., by tracking and returning it to a recovery pool, or blocking deletion until the module's escrowed balance for that denom is verified to be zero).
- Alternatively, do not delete the mapping outright; instead mark the pair "disabled/orphaned" while preserving the denom↔contract mapping so a governance-gated recovery/refund flow can still resolve outstanding escrow.
- Long term: Add an invariant check (fuzzing/property test) asserting that `x/erc20` module-account coin balances always remain fully redeemable by some transaction path for every currently-registered or previously-deleted token pair, and add automated tests that self-destruct an ERC20 mid-escrow to confirm depositors can still recover funds.

### Proof of Concept
1. Governance/permissionless registration creates a native-ERC20 `TokenPair` for contract `C` and denom `erc20/<addr>`.
2. Alice calls `MsgConvertCoin` to convert `1000 erc20/<addr>` coins into ERC20 tokens: `ConvertCoinNativeERC20` escrows 1000 coins in the `erc20` module account and unescrows 1000 ERC20 tokens to Alice.
3. Contract `C`'s owner (or malicious/buggy logic reachable from Alice or a third party) calls `selfdestruct` on `C`.
4. Any user (Bob) submits a small, unrelated `MsgConvertCoin` or `MsgConvertERC20` referencing the same denom/contract. `ConvertCoin`/`ConvertERC20` detects `acc == nil || !acc.HasCodeHash()` and calls `k.DeleteTokenPair(ctx, pair)`, wiping the denom map, ERC20 map, and allowances map.
5. The 1000 coins Alice escrowed in step 2 remain in the `erc20` module account balance, but `GetTokenPairID(ctx, "erc20/<addr>")` now returns nothing, so `MintingEnabled` fails for any future `ConvertERC20` attempt referencing that denom or contract address — there is no remaining code path to move those coins out of the module account back to Alice.

// DeleteTokenPair removes a token pair.
func (k Keeper) DeleteTokenPair(ctx sdk.Context, tokenPair types.TokenPair) {
	id := tokenPair.GetID()
	k.deleteTokenPair(ctx, id)
	k.deleteERC20Map(ctx, tokenPair.GetERC20Contract())
	k.deleteDenomMap(ctx, tokenPair.Denom)
	k.deleteAllowances(ctx, tokenPair.GetERC20Contract())
}
