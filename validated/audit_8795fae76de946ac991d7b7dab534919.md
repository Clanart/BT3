### Title
Instantaneous, unweighted `boostesd` factor in `ReferralStorage._calBoosted` lets an unprivileged referrer flash-lock MGP to steal a disproportionate share of referral rewards - ([File: rewards/ReferralStorage.sol])

### Summary
`ReferralStorage.updateTotalFactor` snapshots a referrer's boost `factor` as `sqrt(currentLockedAmount)` with no time-weighting, and this factor is read live by `_calBoosted` inside `trigger()`, which fires synchronously whenever *anyone* calls the fully permissionless `MasterMagpie.multiclaimFor`. An attacker who owns a referral code can, in a single atomic transaction, lock a large amount of MGP into `VLMGP` to spike their `factor`/`totalBoostFactor` ratio, immediately trigger a referee's claim to harvest an inflated `refererAmount`, then call `startUnlock` to begin reversing the lock — extracting more of the shared, finite referral reward pool than their sustained lock duration justifies.

### Finding Description
`updateTotalFactor` recomputes the boost factor purely from the instantaneous locked balance, with no checkpointing or time-average: [1](#0-0) 

`_calBoosted` uses this live snapshot directly as a share of a fixed `BoostPoint` constant relative to `totalBoostFactor`: [2](#0-1) 

`trigger()` is called synchronously on every referee claim and uses `_calBoosted(_referer)` at that exact block to compute `refererAmount`, which is added to the referrer's `rewardAmount` (payable via `claimReward()` from the contract's MGP balance): [3](#0-2) [4](#0-3) 

Both `VLMGP.lock` and `VLMGP.startUnlock` are unprivileged, unrestricted entry points that call `updateTotalFactor` as a side effect with no delay or cooldown before the new factor takes effect: [5](#0-4) [6](#0-5) [7](#0-6) 

Critically, `MasterMagpie.multiclaimFor` is fully permissionless — any address can trigger a claim (and therefore `trigger()`) on behalf of *any* account, with no access control tying the caller to `_account`: [8](#0-7) [9](#0-8) 

This means the entire attack can be executed atomically inside a single attacker-controlled transaction:
1. Attacker (registered referral code owner) calls `VLMGP.lock(largeAmount)` — this instantly sets `userInfo.factor = sqrt(largeAmount)` and inflates `totalBoostFactor`, both as the numerator (attacker's own factor) and the shared denominator used by all other active referrers.
2. In the same transaction, attacker calls `MasterMagpie.multiclaimFor` for the referee (their own second wallet, or any referee using their code), which internally calls `ReferralStorage.trigger()` while the factor is still spiked, computing an inflated `boostesd` and crediting an inflated `refererAmount`.
3. Attacker then calls `VLMGP.startUnlock(largeAmount)` to begin reversing the lock.

No existing modifier prevents this: `whenNotPaused`/`nonReentrant` do not gate against same-block manipulation, there is no minimum lock duration before a factor counts, and `_calBoosted` has no historical/time-weighted averaging. The attacker only needs momentary capital for one transaction (not a sustained lock), yet is credited as if they had a proportionally large sustained stake, at the expense of the shared `totalBoostFactor` denominator that determines every other active referrer's boosted share, and at the expense of `ReferralStorage`'s finite MGP reward balance that funds `claimReward()`.

### Impact Explanation
This is a theft of unclaimed yield: the attacker drains a disproportionate share of the referral reward pool (funded MGP balance in `ReferralStorage`) relative to their actual sustained commitment, both by inflating their own numerator and diluting the shared `totalBoostFactor` denominator that other genuine, sustained-lock referrers rely on for their own `trigger()` payouts. Repeated exploitation can deplete the finite reward balance, causing other legitimate referrers' later `claimReward()` calls to revert with `InsufficientRewardBalance` — a direct, quantifiable value transfer from honest users to the attacker.

### Likelihood Explanation
- Fully permissionless: requires only registering a referral code (`registerCode`, no owner gating) and controlling/colluding with a referee wallet using that code (`useCode`).
- No special privileges needed: `lock`, `startUnlock`, and `multiclaimFor` are all public/external with no access-control restriction tying caller to the referee's identity.
- Repeatable: the attacker can repeat this flash-boost cycle around every referee claim event, and capital is only needed transiently within a single transaction (not permanently locked), making it cheap and highly repeatable.
- The only friction is the `startUnlock` → `unlock` cooldown to fully reclaim principal, but this does not prevent the reward extraction, which already occurred atomically before cooldown begins.

### Recommendation
Replace the instantaneous `sqrt(currentLockedAmount)` snapshot with a time-weighted / checkpointed boost factor (e.g., accumulate factor based on lock-duration-weighted average, or require a minimum holding period before a locked amount counts toward `factor`). Additionally, consider restricting `multiclaimFor`'s caller to the account itself or an approved operator, and/or snapshot `totalBoostFactor`/`factor` at a delayed checkpoint (e.g., only updated once per epoch) so it cannot be manipulated within the same transaction as a claim.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `ReferralStorage`; fund `ReferralStorage` with MGP reward balance; set a referrer tier and share percent.
2. Attacker registers a referral code; referee (second attacker-controlled wallet) calls `useCode`.
3. Set up referee with a pending MGP claim in `MasterMagpie` (via staking/locking flow) large enough to be claimable.
4. Baseline run: attacker locks a small, "fair" sustained amount well before the claim, waits, then referee calls `multiclaimFor`; record `refererAmount` emitted via `RefererRewardHarvested`.
5. Attack run: in a single transaction (via an attacker contract), call `VLMGP.lock(largeAmount)`, then `MasterMagpie.multiclaimFor(referee)`, then `VLMGP.startUnlock(largeAmount)`; record `refererAmount` from `RefererRewardHarvested`.
6. Assert attack-run `refererAmount` significantly exceeds baseline `refererAmount` despite the locked capital being held for effectively zero time (single block), demonstrating that the boosted-reward share is decoupled from sustained lock duration and drains disproportionate value from the shared `ReferralStorage` MGP balance.
