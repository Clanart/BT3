### Title
Full-fill escrow release in `_fillSameChain` pays out the entire per-token balance instead of the per-leg share, allowing over-release when an order's inputs share a token address - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
The Niftyswap bug class is "integer-math rounding lets a party receive less/more than their true proportional share because a per-unit calculation is truncated/aggregated incorrectly." The local analog is in `IntentGatewayV2`'s same-chain partial-fill settlement: `_fillSameChain` computes the escrow to release for a *completed* output leg by reading the entire remaining `_orders[commitment][token]` balance rather than the proportional remainder owed for that specific output leg, because `_orders` is keyed only by `(commitment, token address)` and aggregates all input entries that share a token.

### Finding Description
In `evm/src/apps/intentsv2/IntrinsicIntents.sol` (`_fillSameChain`, lines ~116-122):

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [1](#0-0) 

This branch was clearly added to fix the "rounding dust" issue described in `IntentGatewayV2SameChainTest.sol` (Finding #4): instead of releasing the truncated proportional share on the final fill, the code releases *whatever remains* in `_orders[commitment][token]` for that token, guaranteeing no dust is left behind.

The problem is that `_orders` is declared as `mapping(bytes32 => mapping(address => uint256)) public _orders;` — keyed by commitment and **token address only**, not by output/input index: [2](#0-1) 

If an order's `inputs[]` array contains two (or more) entries that use the same token address (nothing in the code inspected prevents this — validation of `placeOrder`'s input array for duplicate tokens was not found), the escrow amounts for both entries are summed into a single `_orders[commitment][token]` slot at placement time. The `_fillSameChain` loop iterates per **output** index `i`, and when the output at index `i` reaches full completion (`amountFilled == totalRequired`), it releases the **entire** `_orders[commitment][token]` balance to the solver completing that leg — even though part of that balance backs a *different* output leg (at a different index) that has not yet been filled.

The result: the first solver to complete any output leg backed by that shared token receives the full combined escrow (its own leg's fair share plus the other leg's unearned escrow). When the second leg is later completed, `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol`, lines 400-403) computes `_orders[commitment][token] - amount`, which reverts on underflow because the balance was already drained to zero — but the underflow-revert happens *after* the first (over-)payment already went out, so funds already transferred to the first solver cannot be recovered from that revert.

### Impact Explanation
This is a direct fund-diversion / wrong-amount bug: a solver who completes one output leg of a same-chain order can walk away with escrow that was meant to back a different, still-unfilled leg of the same order, at the expense of the user (whose order is left unable to be fulfilled — the counter-leg's solver cannot be paid, permanently reverting that leg) and any other solver expecting to service the remaining leg. This falls squarely within the bounty's "stealing or loss of funds" / "wrong beneficiary or amount" categories, is triggered by an ordinary unprivileged order-placer/solver interaction (no malicious relayer, prover, or admin needed), and requires no proof forgery — only crafting an `Order` whose `inputs[]` entries reuse the same token address across legs.

### Likelihood Explanation
Likelihood depends entirely on whether `placeOrder`/order validation rejects duplicate token addresses across `inputs[]` entries; this could not be confirmed from the code available. If duplicates are permitted (which the storage design — token-keyed aggregation rather than index-keyed escrow — suggests is the case, since a per-index design would have been more natural if duplicates were disallowed), any order-placer/solver pair can trigger the miscalculation deterministically, making this a straightforward, repeatable exploit rather than a probabilistic rounding edge case. This should be verified against the `placeOrder` implementation (not present in the indexed context) before treating it as fully confirmed.

### Recommendation
- Key `_orders` (or an auxiliary tracking structure) by `(commitment, input index)` rather than `(commitment, token address)` so that escrow for each input/output leg is tracked independently even when token addresses repeat.
- Alternatively, explicitly reject orders whose `inputs[]` array contains duplicate token addresses during `placeOrder` validation.
- When computing the full-completion `escrowedAmount`, bound the release to the specific leg's own remaining share (e.g., `order.inputs[i].amount - alreadyReleased[i]`) rather than reading the shared per-token running total.

### Proof of Concept
1. User calls `placeOrder` with an `Order` whose `inputs` array has two entries both referencing token `T` (e.g., `inputs[0] = {T, 600}`, `inputs[1] = {T, 400}`), and `output.assets` has two legs (`outputs[0]` requiring asset `A` for 600, `outputs[1]` requiring asset `B` for 400). This causes `_orders[commitment][T] = 1000` (aggregated).
2. Solver S1 fully fills `outputs[0]` (provides 600 of `A`). In `_fillSameChain`, for `i = 0`, `amountFilled == totalRequired` becomes true, so `escrowedAmount = _orders[commitment][T] = 1000` (the full combined balance, not just S1's fair 600 share) is released to S1.
3. `_orders[commitment][T]` is now `0`.
4. Solver S2 attempts to fill `outputs[1]` (provides 400 of `B`). When `_fillSameChain` reaches `i = 1` with `amountFilled == totalRequired`, `escrowedAmount = _orders[commitment][T] = 0`; `_withdraw` then computes `escrowed - amount` where `escrowed == 0` and reverts with `UnknownOrder`/underflow, or releases `0` — S2 receives nothing for their delivered output, while S1 has already been paid the full 1000 (400 more than earned).
5. Net effect: S1 gains 400 units of `T` that were not backed by their fill, and the order for `outputs[1]` becomes permanently unfulfillable/reverting, locking B's solver out and leaving the user's second leg unsettled.
