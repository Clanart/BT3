Confirmed: `getSigner` in `kaiax/auction/bid.go` indexes into the signature byte slice without any length check before use, exactly analogous to the `aes_key_unwrap` bug class (subtraction/index-out-of-range panic on undersized attacker-controlled input).

### Title
Panic (index out of range) in auction bid signature recovery when `SearcherSig`/`AuctioneerSig` is shorter than 65 bytes - (File: kaiax/auction/bid.go)

### Summary
`getSigner()`, used by `Bid.ValidateSearcherSig` and `Bid.ValidateAuctioneerSig`, directly indexes and slices the attacker-supplied `SearcherSig`/`AuctioneerSig` byte slices (`copiedSig[crypto.RecoveryIDOffset]`, `copiedSig[0:32]`, `copiedSig[32:64]`) without first checking `len(sig) == crypto.SignatureLength` (65 bytes). A caller can submit a `Bid` whose `SearcherSig` or `AuctioneerSig` field is shorter than 65 bytes (including empty), causing a runtime panic (index out of range) instead of a graceful error, mirroring the Sequoia PGP `aes_key_unwrap` bug where a too-short ciphertext bypasses bounds checking before slicing/subtracting.

### Finding Description
`getSigner` clones the raw signature and immediately accesses fixed offsets: [1](#0-0) 
There is no `len(sig) != crypto.SignatureLength` guard prior to these accesses (compare to the guarded pattern used elsewhere, e.g. `crypto/signature_cgo.go` `Ecrecover` which checks `len(sig) != SignatureLength` before touching `sig[RecoveryIDOffset]` [2](#0-1) , and `api/api_kaia_transaction.go`'s `RecoverFromMessage` which checks `len(sig) != crypto.SignatureLength` before use [3](#0-2) ). `Bid.ValidateSearcherSig` and `Bid.ValidateAuctioneerSig` call `getSigner` unconditionally on the bid's raw fields: [4](#0-3) 

`Bid` is populated directly from untrusted input via RLP in `DecodeRLP` (no field-length validation) [5](#0-4) , and is received from the network in `handleBidMsg`, which only checks total message size, not per-field signature length, before decoding and forwarding to the auction module: [6](#0-5) . Additionally, the RPC-facing `SubmitBid` path in `kaiax/auction/impl/bid_pool.go` uses `ErrInvalidSearcherSig`/`ErrInvalidAuctioneerSig`, suggesting some call sites perform a length check before invoking `ValidateSearcherSig`/`ValidateAuctioneerSig`, but `getSigner` itself has no defensive check, so any code path (present or future) that calls `ValidateSearcherSig`/`ValidateAuctioneerSig` directly on attacker-supplied bids without first checking `len(SearcherSig) == 65` / `len(AuctioneerSig) == 65` will panic.

### Impact Explanation
A panic in bid validation reachable from a p2p `BidMsg` (`handleBidMsg`) or an RPC `SubmitBid` call can crash the goroutine/node processing the bid if the length check that exists in `bid_pool.go` is bypassed or missing on any call path (including future refactors), since the guard is not colocated with the vulnerable function `getSigner` itself — the safety currently depends entirely on callers remembering to check length beforehand, which is a fragile invariant.

### Likelihood Explanation
Reachable by any peer that can send a `BidMsg` (validators/CNs per `handleBidMsg`'s peer-type check) or any RPC caller invoking bid submission with a short `SearcherSig`/`AuctioneerSig`. Whether this currently panics in practice depends on whether all current call sites (e.g., `bid_pool.go`) perform the length check before calling `getSigner`; I could not fully confirm this from the available search results — the length check appears to exist somewhere producing `ErrInvalidSearcherSig`/`ErrInvalidAuctioneerSig` in `bid_pool.go`, but I was not able to verify whether `getSigner` is ever reached with unvalidated length directly (e.g., through `ValidateAuctioneerSig` being called separately from `ValidateSearcherSig` with different validation ordering).

### Recommendation
Add an explicit `len(sig) != crypto.SignatureLength` check at the top of `getSigner` in `kaiax/auction/bid.go`, returning `ErrInvalidSignature` (or a dedicated error) immediately, so the function is safe regardless of caller discipline — matching the defensive pattern already used in `crypto.Ecrecover`/`crypto.SigToPub`.

### Proof of Concept
1. Construct a `Bid` (or `auction.BidData`) with `SearcherSig` set to a byte slice shorter than 65 bytes (e.g., `[]byte{0x12, 0x34}`) and valid other fields.
2. Send it via `BidMsg` to a consensus-node peer through `handleBidMsg`, or submit via the RPC bid-submission API if that path calls `ValidateSearcherSig`/`ValidateAuctioneerSig` without a prior length check.
3. When `getSigner` executes `copiedSig[crypto.RecoveryIDOffset]` (index 64) on a slice shorter than 65 bytes, or `copiedSig[32:64]` on a slice shorter than 64 bytes, Go runtime raises "index out of range" / "slice bounds out of range", panicking the calling goroutine.

func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}

func (b *Bid) ValidateAuctioneerSig(auctioneer common.Address) error {
	digest := b.GetEthSignedMessageHash()

	recoveredAuctioneer, err := getSigner(b.AuctioneerSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover auctioneer sig: %v", err)
	}

	if recoveredAuctioneer != auctioneer {
		return fmt.Errorf("invalid auctioneer sig: expected %v, calculated %v", auctioneer.String(), recoveredAuctioneer.String())
	}

	return nil
}

// handleBidMsg handles bid message.
func handleBidMsg(pm *ProtocolManager, p Peer, msg p2p.Msg) error {
	if pm.IsAuctionModuleDisabled() {
		return nil
	}
	if p.ConnType() != common.CONSENSUSNODE {
		return errResp(ErrInvalidMsgCode, "bid message from a non-CN peer: conntype %d", p.ConnType())
	}

	if uint64(msg.Size) > maxBidMsgSize {
		return errResp(ErrMsgTooLarge, "msg %v: %v > %v", msg, msg.Size, maxBidMsgSize)
	}

	var data *auction.Bid
	if err := msg.Decode(&data); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}

	pm.auctionModule.HandleBid(p.GetID(), data)

	return nil
}
