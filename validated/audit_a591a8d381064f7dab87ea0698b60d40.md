### Title
Hardcoded Network Gate in `handle_kickoff` Permanently Suppresses Automated Challenge Submission on Mainnet and Testnet4, Allowing Malicious Operators to Steal Bridged BTC — (File: `core/src/verifier.rs`)

---

### Summary

`Verifier::handle_kickoff` contains a hardcoded `matches!` guard that unconditionally skips queuing the `Challenge` transaction whenever the configured network is `bitcoin::Network::Bitcoin` (mainnet) or `bitcoin::Network::Testnet4`. Because the same function is the sole code path reached by both the automation state-machine duty (`CheckIfKickoffMalicious`) and the `InternalHandleKickoff` gRPC endpoint, there is no automated route by which a verifier can challenge a malicious kickoff on either production network. A malicious operator can therefore commit an invalid payout blockhash in a kickoff, wait out the `operator_challenge_timeout_timelock`, send `ChallengeTimeout`, and proceed to `Reimburse`—draining the bridged BTC from the vault—without any automated resistance.

---

### Finding Description

In `core/src/verifier.rs`, `handle_kickoff` (lines 1987–2017):

```rust
if is_malicious {
    // do not automatically send challenge txs on mainnet or testnet4
    if !challenged_before
        && !matches!(
            self.config.protocol_paramset().network,
            bitcoin::Network::Bitcoin | bitcoin::Network::Testnet4
        )
    {
        #[cfg(feature = "automation")]
        self.tx_sender
            .add_tx_to_queue(
                dbtx,
                TransactionType::Challenge,
                &challenge_tx,
                ...
            )
            .await?;
    }
}
``` [1](#0-0) 

The outer `if is_malicious` branch is entered whenever `is_kickoff_malicious` returns `true`—i.e., when the operator's committed blockhash does not match the payout blockhash stored in the DB, or when no payout info exists at all. [2](#0-1) 

The inner guard then silently drops the challenge on mainnet and testnet4. The function still returns `Ok(true)` (malicious), so the state machine records the kickoff as malicious, but no `Challenge` transaction is ever queued or broadcast.

The `InternalHandleKickoff` gRPC handler calls the same function with `challenged_before = false`: [3](#0-2) 

The gRPC proto comment confirms this is the intended behavior: *"on networks other than mainnet and testnet4, it will send the challenge tx."* [4](#0-3) 

The `ChallengeTimeout` transaction spends the same `UtxoVout::Challenge` UTXO that the `Challenge` transaction would spend, but it is operator-signed and time-locked by `operator_challenge_timeout_timelock` blocks. If no `Challenge` is ever broadcast, the operator can unilaterally send `ChallengeTimeout` after the timelock expires, spending the kickoff finalizer and proceeding to `ReadyToReimburse` → `Reimburse`. [5](#0-4) 

The `Reimburse` transaction spends the `DepositInMove` UTXO—the vault output holding the bridged BTC—and pays it to the operator's reimbursement address. [6](#0-5) 

---

### Impact Explanation

On `bitcoin::Network::Bitcoin` (mainnet) and `bitcoin::Network::Testnet4`, a malicious operator can:

1. Front a withdrawal with an invalid payout (wrong blockhash committed in the kickoff witness).
2. Verifiers detect the kickoff as malicious but the `Challenge` transaction is never queued.
3. After `operator_challenge_timeout_timelock` blocks (~144 blocks, ~1 day), the operator sends `ChallengeTimeout`, spending the kickoff finalizer.
4. The operator advances to `ReadyToReimburse` and then `Reimburse`, extracting the full bridge amount from the vault UTXO.

This is a direct theft of bridged BTC with no automated countermeasure on the two production networks.

---

### Likelihood Explanation

The suppression is unconditional and applies to every verifier instance on mainnet and testnet4. Any operator who is willing to act maliciously can exploit this with certainty—there is no probabilistic element. The only mitigation would be a human operator manually constructing and broadcasting the challenge transaction out-of-band, which is not part of the automated protocol and is not documented as a required operational procedure.

---

### Recommendation

Remove the network-specific guard. The `Challenge` transaction must be queued on all networks, including mainnet and testnet4, whenever a malicious kickoff is detected and `challenged_before` is false:

```rust
// Before (broken):
if !challenged_before
    && !matches!(
        self.config.protocol_paramset().network,
        bitcoin::Network::Bitcoin | bitcoin::Network::Testnet4
    )
{ ... }

// After (correct):
if !challenged_before { ... }
```

If the intent was to require human review before challenging on mainnet, that policy must be enforced at the operational layer (e.g., an alert + manual approval flow), not by silently suppressing the only automated defense against malicious operators in the production code path.

---

### Proof of Concept

1. Deploy Clementine on `bitcoin::Network::Bitcoin` with the `automation` feature enabled.
2. Operator performs a deposit and registers a withdrawal on Citrea.
3. Operator sends a kickoff transaction committing an **invalid** payout blockhash in the WOTS witness.
4. Each verifier's state machine fires `Duty::CheckIfKickoffMalicious` → `handle_kickoff`.
5. `is_kickoff_malicious` returns `true` (blockhash mismatch at line 1906).
6. The inner guard at line 1999–2003 matches `bitcoin::Network::Bitcoin` → the `add_tx_to_queue` call is skipped.
7. No `Challenge` transaction appears on-chain.
8. After `operator_challenge_timeout_timelock` (144) blocks, the operator broadcasts `ChallengeTimeout`.
9. Operator sends `BurnUnusedKickoffConnectors`, `ReadyToReimburse`, advances the round, and sends `Reimburse`.
10. The vault UTXO (`DepositInMove`) is spent to the operator's address—bridged BTC stolen.
