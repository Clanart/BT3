### Title
IBC callback gas-limit checks are dead code because `infiniteGasMeterWithLimit.IsOutOfGas()` always returns `false` - (File: `x/vm/types/gasmeter.go`)

### Summary
The bug class in the Astaria report (`timeToEpochEnd()` hard-coded to a wrong branch, causing a threshold check that should sometimes be true to always evaluate to the same constant) has a direct analog in `x/vm/types/gasmeter.go`: `infiniteGasMeterWithLimit.IsOutOfGas()` is hard-coded to `return false` unconditionally, regardless of `consumed` vs `limit`. This same meter type is used both as the top-level EVM transaction gas meter (via `CheckBlockGasLimit` in `ante/evm/08_gas_consume.go`) and inside `x/ibc/callbacks/keeper/keeper.go` for IBC ack/timeout/receive-packet EVM callback execution, where the code explicitly relies on `ctx.GasMeter().IsOutOfGas()` after `ConsumeGas()` to bound total computation.

### Finding Description
`infiniteGasMeterWithLimit` in [1](#0-0) :
```go
func (g *infiniteGasMeterWithLimit) IsPastLimit() bool { return false }
func (g *infiniteGasMeterWithLimit) IsOutOfGas() bool { return false }
```
Both methods are hard-coded constants, never comparing `g.consumed` to `g.limit`. `GasRemaining()` does compute correctly [2](#0-1) , but `ConsumeGas()` itself only panics on `uint64` overflow, not on exceeding `limit` [3](#0-2) .

This meter is installed as the primary transaction gas meter after ante-handler validation via `CheckBlockGasLimit` in `ante/evm/08_gas_consume.go`, which wraps `ctx` with `evmtypes.NewInfiniteGasMeterWithLimit(gasWanted)`. It is separately used inside `x/ibc/callbacks/keeper/keeper.go` (`IBCReceivePacketCallback`, `IBCOnAcknowledgementPacketCallback`, `IBCOnTimeoutPacketCallback`), where after invoking `k.evmKeeper.CallEVM(...)`, the code does:
```go
ctx.GasMeter().ConsumeGas(res.GasUsed, "callback ...")
if ctx.GasMeter().IsOutOfGas() {
    return errorsmod.Wrapf(types.ErrCallbackFailed, "out of gas")
}
```
seen at [4](#0-3)  and similarly at [5](#0-4) . Because `IsOutOfGas()` is a hard-coded `false`, this guard can never trigger — it is dead code, structurally identical to `timeToEpochEnd()` always returning `0` regardless of the real time-remaining state.

### Impact Explanation
The intended invariant is that gas consumed during nested EVM callback executions (triggered on every ICS-20 packet ack/timeout/receive with a `src_callback`/`dest_callback` memo) must not exceed the enclosing transaction/message gas budget, so a malicious or buggy callback contract cannot cause unbounded computation relative to the fee paid and the declared gas limit. Since the enforcement check never fires, an attacker who is the original IBC packet sender (an ordinary, unprivileged user, per `x/ibc/callbacks/README.md` "only the IBC packet sender can set the callback") can chain repeated relayed ack/timeout callback invocations (each internally capped only by its own `cbData.CommitGasLimit`, which they also control) inside processing paths that rely on the outer `ctx.GasMeter()` to bound aggregate work. However, I could not fully verify within the available exploration whether any other independent, redundant enforcement path (e.g., a raw geth `GasPool`/`StateTransition` gas accounting or CometBFT-level block gas metering unrelated to `ctx.GasMeter()`) still bounds total block computation, which is necessary to establish a genuine chain-halt/consensus-fork Critical impact rather than a lower-severity fee/gas-accounting deviation.

### Likelihood Explanation
The trigger requires only a standard, unprivileged ICS-20 transfer with a `src_callback`/`dest_callback` memo pointing at an attacker-controlled contract, and relaying/timing out that packet — both purely user-controlled, no validator or admin privilege needed. The dead code condition is deterministic and always present (100% of the time `IsOutOfGas()` is called, it returns `false`), so likelihood of triggering the broken check is high whenever this code path executes. The uncertainty is not in triggering the bug but in whether it corresponds to a **Critical** allowed impact (chain halt / fund theft / minting) versus a bounded fee-accounting or gas-refund deviation.

### Recommendation
Fix `infiniteGasMeterWithLimit.IsOutOfGas()` (and `IsPastLimit()`) to compare `consumed` against `limit` instead of hard-coding `false`, e.g. `return g.consumed >= g.limit`, and audit every caller (ante handler tx gas enforcement, IBC callback keeper) that relies on `IsOutOfGas()`/`IsPastLimit()` to confirm the correct out-of-gas behavior is restored without breaking the "infinite" semantics intentionally used elsewhere (if any caller intentionally depends on it never panicking, that dependency needs to be re-evaluated and made explicit).

### Proof of Concept
Could not be fully constructed/verified within the remaining investigation budget. A conceptual PoC would:
1. Deploy a contract implementing `onPacketAcknowledgement`/`onPacketTimeout` that loops to consume large EVM gas up to `cbData.CommitGasLimit`.
2. Send an ICS-20 transfer with `memo` specifying `src_callback` pointing to this contract with a large `gas_limit`.
3. Trigger multiple acknowledgements/timeouts in a single block/tx context so that the aggregate `ConsumeGas` calls on `ctx.GasMeter()` exceed the outer transaction's declared `gasWanted`/limit.
4. Observe that `ctx.GasMeter().IsOutOfGas()` at [4](#0-3)  never returns `true` and the guard never aborts execution, confirming the enforcement gap. Whether this translates into a block-processing time/consensus impact large enough to be Critical (vs. a fee-accounting-only issue, which is explicitly out of scope) was **not conclusively determined** given the remaining tool budget.
