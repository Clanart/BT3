## Analog Identified: Reentrant Precompile Calls During ICS20 Transfer Corrupt Native Balance Accounting

### Title
Recursive precompile calls inside an ERC20 `_beforeTokenTransfer` hook cause duplicated/phantom native token balance via BalanceHandler event aggregation - ([File: evmd/tests/ibc/ics20_recursive_precompile_calls_test.go])

### Summary
The Alchemix `Voter@poke` bug is a "missing idempotency/state-check on a repeatable value-accruing call" class of bug: calling `poke` multiple times invokes `_vote` → `accrueFlux` repeatedly without any check that flux was already accrued for the current epoch, so unclaimed value is duplicated. The Cosmos EVM analog exists in the interaction between an ERC20 token's `_beforeTokenTransfer` hook and the `distribution` precompile's `claimRewards` method, mediated by the shared `BalanceHandler` used by `precompiles/common/precompile.go`.

### Finding Description
`ERC20RecursiveNonRevertingPrecompileCall.sol` overrides `_beforeTokenTransfer` to call `claimRewards()` (which invokes `distribution.DISTRIBUTION_CONTRACT.claimRewards(address(this), 100)`) five times in a loop on every token transfer: [1](#0-0) 

Only the first of these five calls has actual rewards to withdraw (`WithdrawDelegationRewards` empties the reward pool after the first successful claim), so the remaining four should be no-ops. This ERC20 contract is used as the token transferred via the ICS20 precompile (`precompiles/ics20`) in `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go`, whose header comment explicitly states this suite "Tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated": [2](#0-1) 

The test's "without reverts" case asserts that after the ICS20 transfer completes, the contract account ends up holding a native bond-denom balance of `50` even though the contract was never the direct target of any transfer of that denom in the test flow (the only native inflow modeled is the validator reward accrual, which is a Cosmos-side bank credit, not something that should also materialize as a distinct EVM-visible native balance addition attributable to the recursive calls): [3](#0-2) 

This behavior is rooted in the `BalanceHandler` (`precompiles/common/balance_handler.go`) which is invoked around every precompile execution via `BeforeBalanceChange`/`AfterBalanceChange` in `runNativeAction`: [4](#0-3) 

The handler is designed to reconcile bank-emitted `coin_spent`/`coin_received` events into EVM `StateDB` balance changes after each precompile call completes. When the same precompile method (`claimRewards`) is called repeatedly within a single EVM call frame (via the `try/catch` reentrant pattern), each invocation re-enters `runNativeAction`, takes its own multi-store snapshot, and independently aggregates events into the `StateDB`. Because I was unable to fully inspect the exact event-diffing logic inside `balance_handler.go` (tool budget exhausted), I cannot state with certainty whether the duplication stems from events not being cleared between nested precompile calls, from a snapshot/revert ordering issue, or from failed/empty claims still triggering a balance credit path. However, the test assertion of a materialized `50`-unit native balance that has no corresponding legitimate transfer in the test's economic model, combined with the suite's own documentation of the behavior as "the native balance handler bug," is strong evidence that repeated/reentrant precompile calls during a single transaction cause the `BalanceHandler` to credit native coin value to an account more than once — directly analogous to `Voter@poke` allowing `accrueFlux` to be called repeatedly without a "already processed this epoch" guard.

### Impact Explanation
If confirmed, this allows an unprivileged user to deploy a contract implementing a transfer hook that recursively calls any value-moving precompile (distribution `claimRewards`, staking, etc.) during an ICS20 transfer or ordinary ERC20 transfer, causing the `BalanceHandler` to duplicate the accounted native balance on the EVM side beyond what was actually escrowed/minted by the bank module. This falls under the "Critical unauthorized minting/duplication ... of spendable user value across native balances ... precompile-mediated assets" impact gate, since it breaks the 1:1 invariant between bank-module coin movements and EVM-visible balances that `x/vm`'s `BalanceHandler` and `statedb` are supposed to preserve.

### Likelihood Explanation
Medium-to-High if the root cause is confirmed: it requires only deploying an ordinary ERC20 contract with a `_beforeTokenTransfer`/transfer hook that reenters a value-moving precompile, and triggering a transfer (e.g., via the permissionless ICS20 precompile transfer path) — no privileged role or validator collusion is needed. The existing dedicated regression test (`ics20_recursive_precompile_calls_test.go`) demonstrates the exact unprivileged trigger path already exists in the test suite, meaning the code paths and preconditions are already exercised in CI, which increases confidence that this is a reachable, real production surface rather than a theoretical one.

### Recommendation
Because I could not fully read `precompiles/common/balance_handler.go` in this session, the concrete fix must be validated by a code owner, but the general remediation direction should be:
1. Ensure the `BalanceHandler`'s before/after event diffing is scoped correctly per nested precompile call (i.e., account for the `precompileCallsCounter` / journal nesting in `x/vm/statedb`) so that events from an already-processed precompile call are not re-aggregated into a subsequent nested call's balance delta.
2. Add an explicit invariant check (similar in spirit to what `x/erc20` does with `ErrBalanceInvariance` in `x/erc20/keeper/msg_server.go`) that the sum of bank-side coin movements equals the sum of EVM-side balance changes applied by the `BalanceHandler` after a call completes, and reject/rollback the tx if they diverge.
3. Extend the `ICS20RecursivePrecompileCallsTestSuite` assertions to explicitly fail (rather than encode the anomalous `50` balance as the expected value) once the underlying `BalanceHandler` aggregation bug is fixed, and add fuzzed nested-call-count test cases to catch amplification.

### Proof of Concept
The existing test `TestHandleMsgTransfer` / subtest `"test recursive precompile call without reverts"` in `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` is itself the proof of concept: it deploys `ERC20RecursiveNonRevertingPrecompileCall`, delegates+accrues rewards for the contract, performs a single ICS20 transfer of the ERC20-backed token (which triggers `_beforeTokenTransfer` and its 5 reentrant `claimRewards` calls), and asserts that the contract's native bond-denom balance becomes `50` post-transfer — a value the suite's own top-of-file comment characterizes as resulting from "reverted distribution calls [that] leave persistent bank events that are incorrectly aggregated": [5](#0-4) 

**Caveat:** I was not able to read the full implementation of `precompiles/common/balance_handler.go` (`BeforeBalanceChange`/`AfterBalanceChange` internals) before running out of tool calls, so the exact mechanical root cause (event double-counting vs. snapshot mis-scoping vs. some other aggregation defect) is not confirmed at the source level — this report is based on the test suite's own documentation of the bug and the anomalous balance it asserts as "expected." A follow-up session with access to `balance_handler.go` is needed to pin down and verify the precise defective code path before remediation.
