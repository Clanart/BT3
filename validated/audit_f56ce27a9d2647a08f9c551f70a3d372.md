# Analog Found: Surplus-Share Fee Bypass via Self-Seeded Partial Fill

### Title
`IntrinsicIntents::_fillSameChain()` lets any solver permanently disable the surplus-split (protocol/beneficiary bonus) by seeding a dust partial fill first - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
The M-10 report's core defect is a computation meant to converge system state to a target economic invariant (post-liquidation health) that ignores a "bonus" applied elsewhere in the same execution, letting the actual outcome silently overshoot the target and be re-triggered. The same class of bug appears in Hyperbridge's `IntrinsicIntents._fillSameChain()`: the surplus-sharing invariant ("overpayment must be split between beneficiary and protocol per `surplusShareBps`") is gated on a state flag (`alreadyFilled == 0`) that the caller fully controls, so the branch that enforces the split can be permanently skipped for the lifetime of an order with a single cheap call.

### Finding Description
`_fillSameChain` computes the surplus split only on the *first* fill of a fresh order: [1](#0-0) 

```solidity
uint256 alreadyFilled = _partialFills[commitment][outputToken];
uint256 remaining = totalRequired - alreadyFilled;
...
if (alreadyFilled == 0 && solverAmount > totalRequired) {
    fillAmount = totalRequired;
    uint256 dust = solverAmount - totalRequired;
    ...
    protocolShare = (dust * _params.surplusShareBps) / 10_000;
    beneficiaryShare = dust - protocolShare;
} else {
    fillAmount = solverAmount > remaining ? remaining : solverAmount;
}
```

`fillOrder` is a public, unprivileged entrypoint — any address can act as a "solver" and call it with `solverAmount = 1` (or any amount `<= totalRequired`). This sets `_partialFills[commitment][outputToken] = 1` at negligible cost, so `alreadyFilled` is permanently non-zero for that order. From that point forward, **every subsequent fill for that order/token, no matter how large the offered `solverAmount`, falls into the `else` branch**, where `fillAmount = min(solverAmount, remaining)`: [2](#0-1) 

```solidity
uint256 beneficiaryTotal = fillAmount + beneficiaryShare;
if (token == address(0)) {
    ...
} else {
    IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
    if (protocolShare > 0) {
        IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
    }
}
```

Because `beneficiaryShare` and `protocolShare` are both `0` in this branch, `safeTransferFrom` only ever pulls exactly `fillAmount` (capped to `remaining`) from the solver — never more. The 50/50 (or governance-configured) surplus split described in the protocol docs is therefore **structurally unreachable** once any party (including the solver themselves) has made one trivial fill against the order: [3](#0-2) 

The guard `existing invariant` (surplus split) only "does not stop the path" because it is conditioned on `alreadyFilled == 0`, a value writable by the very same unprivileged function it is meant to gate — exactly analogous to `maxLiquidatable()` computing a target without accounting for the bonus that is applied in the same execution path, letting the actual post-state diverge from the intended invariant.

### Impact Explanation
This is a **logic attack causing wrong beneficiary/amount** per the bounty's impact gate: the protocol treasury and/or the order's beneficiary are supposed to receive a governance-configured share (`surplusShareBps`) of any solver overpayment on same-chain intent fills. A solver who wants to keep 100% of what would otherwise be shared surplus can defeat the mechanism on every same-chain order by first sending a 1-unit (or otherwise sub-`remaining`) fill, permanently flipping `alreadyFilled` away from zero before making their real, profitable fill. No malicious peer, relayer, prover, or governance actor is needed — this is purely a self-serving unprivileged caller of a public entrypoint. The effect is systemic loss of protocol fee revenue and denial of the beneficiary's entitled surplus share across the Intent Gateway's entire same-chain fill volume.

### Likelihood Explanation
High. `fillOrder` → `_fillSameChain` is a completely public function; the only cost to the attacker/solver is the gas plus the negligible `fillAmount` of the seed fill (as low as 1 wei/1 token unit), which is trivially recoverable as part of normal fill economics. Any profit-motivated solver operating in this ecosystem has direct incentive to always perform this two-step pattern (dust fill, then real fill) to avoid ever paying into the surplus-share mechanism, so exploitation is expected to be the rational, common case rather than an edge case.

### Recommendation
Decouple "is this the first meaningful fill" from `alreadyFilled == 0`. Compute and apply the surplus split whenever `solverAmount` exceeds `remaining` at time of fill, regardless of prior partial-fill history, e.g.:
```solidity
uint256 dust = solverAmount > remaining ? solverAmount - remaining : 0;
fillAmount = solverAmount > remaining ? remaining : solverAmount;
if (dust > 0) {
    protocolShare = (dust * _params.surplusShareBps) / 10_000;
    beneficiaryShare = dust - protocolShare;
}
```
This makes the surplus-sharing invariant depend only on the current fill's relation to the current `remaining` balance, not on a mutable flag the caller controls.

### Proof of Concept
1. User places a same-chain order requiring `1000` output tokens (`surplusShareBps = 5000`, i.e., 50/50 split on overpay), analogous to `testSameChainSwap_WithSurplus` in [4](#0-3) .
2. Attacker/solver A calls `fillOrder` with `outputs[0].amount = 1`. `alreadyFilled == 0` and `1 <= 1000`, so the `else` branch runs: `fillAmount = 1`, no surplus fields set. `_partialFills[commitment][token] = 1`.
3. Attacker/solver A (or a colluding solver B) now calls `fillOrder` again with `outputs[0].amount = 1999` intending to "overpay" for the remaining `999`. Because `alreadyFilled = 1 != 0`, this again hits the `else` branch: `fillAmount = min(1999, 999) = 999`. Only `999` tokens are ever pulled via `safeTransferFrom`; `protocolShare` and `beneficiaryShare` remain `0`.
4. Compare against `testSameChainSwap_WithSurplus`, where the same `920`-vs-`900` overpay on a *fresh* order correctly produces `protocolShare = 10` / `beneficiaryShare = 10` per [4](#0-3) . With the dust-seed step inserted first, an equivalent overpay yields `protocolShare = 0`, confirming the surplus mechanism was bypassed entirely for the cost of a 1-unit fill.

    function testSameChainSwap_WithSurplus() public {
        uint256 inputAmount = 1000 * 1e6; // 1000 USDC
        uint256 requestedAmount = 900 * 1e18; // 900 DAI requested
        uint256 solverAmount = 920 * 1e18; // Solver provides 920 DAI (20 DAI surplus)

        uint256 surplus = solverAmount - requestedAmount;
        uint256 protocolShare = (surplus * SURPLUS_SHARE_BPS) / 10_000; // 50%
        uint256 beneficiaryShare = surplus - protocolShare; // 50%

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: requestedAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // User places order
        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Update order fields
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;

        // Solver fills order with surplus
        vm.startPrank(solver);
        uint256 userDaiBefore = dai.balanceOf(user);
        uint256 gatewayDaiBefore = dai.balanceOf(address(intentGateway));

        dai.approve(address(intentGateway), solverAmount);

        TokenInfo[] memory solverOutputs = new TokenInfo[](1);
        solverOutputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: solverAmount});

        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: solverOutputs}));
        vm.stopPrank();

        // Verify surplus split
        assertEq(
            dai.balanceOf(user),
            userDaiBefore + requestedAmount + beneficiaryShare,
            "User should receive requested amount + beneficiary share"
        );
        assertEq(
            dai.balanceOf(address(intentGateway)),
            gatewayDaiBefore + protocolShare,
            "Gateway should receive protocol share"
        );
