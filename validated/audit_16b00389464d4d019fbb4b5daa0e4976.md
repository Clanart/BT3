### Title
Cross-Shop Webhook Forgery via Unbound `shop_domain` Header in HMAC Verification (Denial of Service / Cross-Tenant State Corruption) - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` (used by `WebhooksController` and every generated webhook controller) authenticates an inbound webhook solely by validating an HMAC over `request.raw_post`. The shop that a webhook is attributed to — `X-Shopify-Shop-Domain` — is read directly from an unauthenticated HTTP header and is never included in the HMAC computation. Because the HMAC secret is the app's single shared client secret (not shop-specific), a valid `(body, hmac)` pair captured from one installed shop remains cryptographically valid when replayed with an arbitrary `X-Shopify-Shop-Domain` header value. This mirrors the reported bug class: a critical parameter that determines the effect of a signed action (`effective_token_from_amount` in the report; `shop_domain` here) is excluded from the signed payload, letting an unrelated party rebind the signed message to a different target and cause unintended state changes / denial of service.

### Finding Description
`WebhookVerification#verify_request` only checks the body digest: [1](#0-0) 

`shop_domain` is derived purely from a header, outside the signed data: [2](#0-1) 

The core HMAC check (`hmac_valid?`) is computed exclusively over the raw payload bytes using the app's static shared secret — no header, including shop domain or topic, is bound into it: [3](#0-2) 

`WebhooksController#receive` (and every generated declarative webhook controller) builds the `ShopifyAPI::Webhooks::Request` directly from the untrusted headers and forwards its `shop`/`shop_domain` to background jobs: [4](#0-3) [5](#0-4) 

The scaffolded jobs (e.g. `app_uninstalled_job`, `shop_redact_job`) then perform destructive, shop-scoped actions based purely on that unverified `shop_domain` value: [6](#0-5) 

Because the app secret is shared across all shops using the app (it is not per-shop), any actor who can obtain one valid `(raw_body, X-Shopify-Hmac-Sha256)` pair — trivially achievable by installing the app on their own store and triggering/observing any webhook delivery — can replay that exact body and HMAC to the shared public webhook endpoint while substituting an arbitrary victim `X-Shopify-Shop-Domain` value. `verify_request` will accept it because the header is never part of the signed content.

### Impact Explanation
An attacker with no relationship to the victim merchant can forge a webhook that the app believes originated from the victim's shop. Depending on the webhook topic replayed, this can:
- Trigger `app/uninstalled` handling for the victim shop, causing the app to purge the victim's stored session/access token — a denial of service against the legitimate merchant, who did not uninstall the app.
- Trigger `shop/redact` or `customers/redact` handling scoped to the victim's `shop_domain`, causing unwanted data deletion for that shop.
- More generally, inject/replay any topic's body under a false shop identity, corrupting per-shop state in the host app (cross-shop state corruption).

This satisfies the "cross-shop access" / accepted forged signed request criteria: the signature is accepted by the verification concern, but the effective target (which shop is affected) is attacker-controlled and unbound from the signature.

### Likelihood Explanation
The attacker only needs to be able to install the app on any shop (free, unauthenticated relative to the victim) and capture one legitimate webhook delivery for that shop (readily triggerable, e.g. by uninstalling the app or editing shop settings for topics the app is subscribed to). No secret material needs to be leaked — only a single previously-valid signed payload needs to be replayed with a different header. This is a comparatively low-effort, self-serve attack path reachable from an unrelated-merchant HTTP request to the app's public webhook endpoint.

### Recommendation
Do not treat `X-Shopify-Shop-Domain` as authoritative purely because `hmac_valid?` passed. Before performing any shop-scoped/destructive action in webhook jobs:
- Cross-check that the `shop_domain` from the header corresponds to a shop that currently has a live, matching session/installation record via `SessionRepository`, and reject/no-op if the shop is unknown or the relationship state is inconsistent with the topic (e.g., an `app/uninstalled` webhook for a shop that has no active session already, or received while the same shop's most recent OAuth activity is inconsistent).
- Where feasible, bind topic/shop context by also validating against Shopify's published webhook source IP ranges, and add idempotency/replay protection keyed on the `X-Shopify-Webhook-Id` header to prevent reuse of a previously captured payload for a different shop context.
- Document explicitly (and enforce in generated templates) that `shop_domain` must never be trusted as a tenant boundary based solely on `hmac_valid?`, since Shopify's webhook signature does not cover headers.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (self-serve, no privileges required).
2. Attacker triggers a webhook the app is subscribed to (e.g. uninstalls the app to fire `app/uninstalled`, or edits a resource to fire another subscribed topic), and captures the exact `raw_post` body and the accompanying `X-Shopify-Hmac-Sha256` header value delivered to the app's webhook endpoint.
3. Attacker crafts a new `POST /webhooks/app_uninstalled` (or equivalent generated path) request to the app, reusing the identical captured body and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` → `hmac_valid?(request.raw_post)` succeeds because the body is unmodified. [1](#0-0) 
5. `WebhooksController#receive` queues the job with `shop_domain: "victim-shop.myshopify.com"`, and the app-uninstalled/shop-redact handler executes destructive logic against the victim's stored session/data, even though the victim never uninstalled or requested redaction. [6](#0-5)

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
