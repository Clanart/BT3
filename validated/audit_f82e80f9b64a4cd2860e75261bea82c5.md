### Title
Payout attribution derived solely from attacker-controlled OP_RETURN, no link to actual funder - `update_finalized_payouts` in ([File: core/src/verifier.rs])

### Summary
`bitcoin_syncer`'s `update_finalized_payouts` attributes a payout to an operator purely by reading the OP_RETURN payload of whichever transaction spends the registered withdrawal UTXO on-chain, with no check that the named operator's key/funds signed anything beyond the user's own `SinglePlusAnyoneCanPay` input. Because the withdrawer's own signature (`SIGHASH_SINGLE|ANYONECANPAY`) only commits to input 0 and the output at index 0, an attacker who is the withdrawer can broadcast their own transaction spending `input_outpoint` with an arbitrary/spoofed OP_RETURN naming a victim operator, causing `payout_payer_operator_xonly_pk` to be set to that operator even though it funded nothing.

### Finding Description
The claimed binding: `withdrawals.payout_payer_operator_xonly_pk == xonly_pk of the party whose BTC funded/fronted the withdrawal payout output`.

Trace:
- `Operator::withdraw` (`core/src/operator.rs:560-675`) builds the payout tx via `create_payout_txhandler(input_utxo, output_txout, self.signer.xonly_public_key, in_signature, ...)`. The OP_RETURN is built purely from the caller-supplied `operator_xonly_pk` argument: `op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()))` — [1](#0-0) . Nothing in `create_payout_txhandler` verifies this key matches any signer of the extra inputs.
- The user's payout signature uses `SinglePlusAnyoneCanPay` (`SIGHASH_SINGLE|ANYONECANPAY`), verified only against `user_xonly_pk` for the sighash over input 0 (`core/src/operator.rs:630-637`). SIGHASH_SINGLE|ANYONECANPAY only commits the signer to their own input and the output at the same index (output 0, the withdrawal payout); all other inputs/outputs (anchor, OP_RETURN) are unconstrained by that signature.
- The user's `in_signature` and `in_outpoint` (the withdrawal UTXO) are established through the Citrea `withdraw` contract call, which the withdrawer themselves controls and knows — this is public/known to the withdrawer since they created it.
- `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) scans confirmed blocks: it joins `withdrawals` to `bitcoin_syncer_spent_utxos` purely on which transaction spent the registered `withdrawal_utxo_txid`/`vout` (`get_payout_txs_for_withdrawal_utxos`, `core/src/database/verifier.rs:170-196`), then reads the OP_RETURN of *whatever transaction actually spent it* to extract `operator_xonly_pk`, with no cross-check against the transaction's other inputs' ownership: [2](#0-1) .
- `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`) then blindly writes this OP_RETURN-derived key into `payout_payer_operator_xonly_pk`.
- Downstream, `PayoutCheckerTask::run_once` polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` for the operator's *own* key (`core/src/task/payout_checker.rs:41-47`) and, if found, calls `Operator::handle_finalized_payout`, which allocates a kickoff connector and proceeds through the reimbursement flow (`core/src/operator.rs:839-885`), eventually broadcasting `reimburse_tx` which pays the operator's reimbursement address the full deposit `bridge_amount` from the deposit's `MoveToVaultTx` output (`core/src/builder/transaction/operator_reimburse.rs:341-385`).

Exploit: an attacker who is the withdrawer knows/owns `in_signature`, `in_outpoint`, and the exact output required at index 0 (fixed by their own SIGHASH_SINGLE commitment). They construct a raw transaction spending `input_outpoint` with output 0 = the legitimately required payout, output 1 = an anchor, and output 2 = a spoofed OP_RETURN containing an arbitrary victim operator's `xonly_pk` serialization, funding any extra fee input themselves (not via any operator), and broadcast it directly to the Bitcoin network — bypassing `Operator::withdraw`/`create_payout_txhandler` entirely. Once this transaction confirms, `update_finalized_payouts` credits the named victim operator, who never signed, funded, or was aware of this transaction. `is_kickoff_malicious` only cross-checks that the payout OP_RETURN's operator matches the *kickoff*'s operator (`core/src/verifier.rs:1887-1890`) — it never verifies that the credited operator actually funded/broadcast the payout tx.

### Impact Explanation
If the named victim operator's automation (`PayoutCheckerTask`) later picks up this fabricated `unhandled_payout` entry, it proceeds through the kickoff/round-tx state machine and eventually spends the deposit's `MoveToVaultTx` output plus its own bonded collateral connectors via `create_reimburse_txhandler`, paying itself the full `bridge_amount` — reimbursement for a payout it never funded. This matches the Critical impact category "an operator reimbursed for a payout it never funded." Alternatively, if the named operator currently has no available/unused kickoff connector, the withdrawal becomes permanently orphaned (unhandled forever, since `is_payout_handled` stays false and no other operator can claim it once `payout_payer_operator_xonly_pk` is fixed to the spoofed key), also a Critical outcome ("permanently unable to be reimbursed" style faulted withdrawal). This is repeatable per withdrawal the attacker controls (every withdrawal they themselves initiate as withdrawer), and the blast radius spans any operator whose `xonly_pk` the attacker chooses to embed.

### Likelihood Explanation
The attacker only needs to be an ordinary Citrea bridge user: deposit, call `withdraw` on the Citrea bridge contract with a self-chosen withdrawal UTXO/signature, then race any operator to broadcast their own crafted spending transaction with the spoofed OP_RETURN before a legitimate operator's payout tx confirms. Constructing this transaction requires only standard Bitcoin transaction-building tools and normal fees; no privileged key, no aggregator/verifier/operator role, and no Citrea sequencer/prover collusion is needed. This is straightforwardly reproducible offline against `bitcoin_syncer`'s block-scanning logic without needing live Citrea, matching the required PoC constraints.

### Recommendation
Do not attribute payouts based solely on an unauthenticated OP_RETURN chosen by whoever broadcasts the spending transaction. Instead require the operator to prove authorship/funding of the payout transaction — e.g., have the aggregator/verifiers require the operator to first register/commit the exact payout transaction (or its funding inputs, or a signature over the full transaction with the operator's key) via an authenticated RPC path before the bitcoin_syncer accepts the on-chain OP_RETURN as attribution, and reject or ignore payout transactions whose additional funding inputs cannot be tied cryptographically to the claimed operator's key/address (e.g., check that non-user inputs spend from the operator's registered reimbursement/withdrawal-funding wallet, or require an operator N-of-N/co-signature over the OP_RETURN commitment before the payout tx is considered valid for attribution).
