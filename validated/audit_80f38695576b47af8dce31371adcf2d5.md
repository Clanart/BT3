## Finding

### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` causes stack-exhaustion DoS - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
The bug class from the picotls advisory — a decoder that recursively descends into attacker-controlled nested structures with no depth limit, exhausting the process stack — has a direct analog in Kaia's `accountkey` package. `AccountKeyRoleBased.DecodeRLP` decodes each role slot through `AccountKeySerializer`, which in turn calls `NewAccountKey` and re-invokes RLP decoding on the resulting key. Nothing in this decode path prevents a role slot from itself being `AccountKeyTypeRoleBased`, allowing an attacker to nest `RoleBased` keys arbitrarily deep inside a single `TxTypeAccountUpdate` (or fee-delegated account-update) transaction payload and crash any node that decodes it.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` reads a list of raw byte blobs and, for each one, decodes it via `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type, constructs a new `AccountKey` via `NewAccountKey(serializer.keyType)`, and then decodes the payload directly into that key: [2](#0-1) 

If `serializer.keyType == AccountKeyTypeRoleBased`, `NewAccountKey` returns a fresh `*AccountKeyRoleBased`, and `s.Decode(serializer.key)` calls `AccountKeyRoleBased.DecodeRLP` again — recursing back into the same code path. The only guard against nested composite keys, `IsCompositeType()` / `ErrNestedCompositeType`, is enforced solely in `CheckInstallable`/`CheckUpdatable`, which run *after* decoding completes: [3](#0-2) 

Because the RLP decode itself (`s.Decode(&enc)` / `rlp.DecodeBytes`) has no recursion-depth limit anywhere in the `rlp` package (confirmed by searching for any depth counter across `rlp/decode.go`), an attacker can craft a `TxTypeAccountUpdate` (or `TxTypeFeeDelegatedAccountUpdate*`) transaction whose `AccountKey` field is a `RoleBased` key nested inside `RoleBased` inside `RoleBased`, N levels deep. Decoding this transaction — which every node must do as soon as the raw transaction bytes are received, well before signature/validity checks reject it for being a composite-in-composite key — drives the Go call stack N frames deep through `DecodeRLP` → `NewAccountKey` → `s.Decode` → `DecodeRLP` ..., eventually exhausting the goroutine stack and crashing the process.

### Impact Explanation
This is directly reachable by an unprivileged transaction sender or any public-RPC caller submitting a raw transaction (`eth_sendRawTransaction`) or gossiping a transaction into the pool — no special privileges, prior account state, or validator/peer position required. A single malicious transaction can crash a full node's process (denial of service), matching CVSS AV:L/AC:L/PR:N/UI:R... in the analog report, here reachable network-wide via a broadcastable transaction rather than a local file.

### Likelihood Explanation
High: constructing the nested RLP payload requires no cryptographic material or special account state — the recursive structure is pure encoding, and the type check that would reject nested composite keys occurs only after the crash-inducing decode has already unwound (or overflowed) the stack. Any node that decodes the transaction from the p2p tx-pool gossip or from an RPC submission is affected.

### Recommendation
Add an explicit recursion/nesting-depth limit when decoding `AccountKeyRoleBased`/`AccountKeySerializer` (e.g., pass and check a depth counter through `DecodeRLP`, or reject `keyType == AccountKeyTypeRoleBased` when already inside a `RoleBased`/composite decode, enforcing the same "no nested composite" rule at decode time that `CheckInstallable` enforces post-decode). Alternatively, add a general nesting-depth guard to `rlp.Stream` for custom `Decoder` implementations akin to the picotls fix (`c14231d`), which added a maximum ASN.1 nesting depth.

### Proof of Concept
1. Construct an `AccountKeyRoleBased` value at depth 0 whose single role element is itself an `AccountKeyRoleBased` (depth 1), whose role element is again `AccountKeyRoleBased` (depth 2), and so on, to a depth of e.g. 100,000+.
2. Serialize this nested structure via `AccountKeyRoleBased.EncodeRLP` (or hand-craft the RLP bytes directly, since `EncodeRLP` places no depth restriction either).
3. Embed the resulting bytes as the `AccountKey` field of a `TxTypeAccountUpdate` transaction and submit it via `eth_sendRawTransaction` or p2p tx gossip.
4. Any node calling `rlp.DecodeBytes`/`tx.DecodeRLP` on the transaction recurses through `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `NewAccountKey` → `s.Decode` at each nesting level, exhausting the stack and crashing the process before `CheckInstallable`'s `ErrNestedCompositeType` check is ever reached. func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
