### Title
`unvote()` underflows and permanently reverts after `removePool` + `addPool` re-adds the same LP address, freezing prior voters' staked bribe funds - (`File: wombat/WombatBribeManager.sol`)

### Summary
`WombatBribeManager.removePool` only pops the LP address out of the iteration array `pools`; it never resets `poolInfos[_lp]` or any user's `userVotedForPoolInVlmgp[user][_lp]` balance. If the owner later calls `addPool` with the same `_lp` address, a fresh `Pool` struct is written with `totalVoteInVlmgp = 0` and `isActive = true`, while stale `userVotedForPoolInVlmgp[user][_lp]` entries from before removal survive. Any user who voted for that pool before removal can then call `unvote(_lp)`, which passes the `isActive` check but underflows `pool.totalVoteInVlmgp -= currentVote` (0 minus a nonzero value), causing a permanent revert and blocking withdrawal of the user's bribe stake.

### Finding Description
`removePool` at [1](#0-0)  only mutates the `pools` array (swap-and-pop) and never touches `poolInfos[_lp]` or clears any `userVotedForPoolInVlmgp` entries. As a result, `poolInfos[_lp].isActive` remains `true` and `poolInfos[_lp].totalVoteInVlmgp` remains whatever it was even after "removal" — the pool is simply no longer iterated by `castVotes`/`claimAllBribes`, but its `poolInfos` state is untouched.

When the owner subsequently calls `addPool` with the same `_lp` address to re-list it (e.g., to change the rewarder), a brand-new `Pool` struct is written that resets `totalVoteInVlmgp` to `0` and sets `isActive = true`: [2](#0-1) . This overwrite does not touch `userVotedForPoolInVlmgp[user][_lp]` for any user who had voted prior to removal — that mapping is keyed independently and is never cleared by either `removePool` or `addPool`.

Now consider `unvote`: [3](#0-2) . It reads `currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress]` (the stale nonzero value from before removal), checks only `pool.isActive` (true, since `addPool` reset it), and then executes `pool.totalVoteInVlmgp -= currentVote`. Since the freshly re-added pool's `totalVoteInVlmgp` is `0`, subtracting any nonzero `currentVote` underflows under Solidity 0.8's checked arithmetic and reverts unconditionally for that voter. Because `currentVote` and `totalVoteInVlmgp` are fixed on-chain state that doesn't change without another `vote()`/`unvote()` call succeeding first, the revert is deterministic and permanent for that user on that pool, and it also blocks `IBribeRewardPool(pool.rewarder).withdrawFor` from ever being reached to release the user's staked bribe balance.

### Impact Explanation
This is a permanent freezing-of-funds condition for any voter whose `userVotedForPoolInVlmgp[user][lp]` balance survives a `removePool` + `addPool(same lp)` cycle: their `unvote(lp)` call reverts forever due to arithmetic underflow, and their vote-locked stake in `BribeRewardPool` (accessible only via `withdrawFor` inside `unvote`) can never be withdrawn through this path. This matches the "permanent freezing of funds" / "unclaimed yield" Immunefi impact category, satisfying the ≥24h freeze bar trivially since it is unbounded.

### Likelihood Explanation
This requires the owner to perform a normal, plausible pool-management sequence: `removePool(index)` to delist an LP, followed later by `addPool(sameLp, newOrSameRewarder, name)` to relist it (e.g., after swapping out a rewarder contract) — no malicious admin intent needed, just an admin oversight combined with a missing cleanup in `removePool`. Any attacker/user only needs to have voted for that pool prior to removal (a normal, permissionless `vote()` call) and then call the permissionless `unvote(lp)` afterward. No special capital, flash loans, or privileged role is required from the attacker's side; the precondition is entirely a benign admin pool-management action plus normal prior user voting.

### Recommendation
In `removePool`, before removing the LP from the `pools` array, iterate/zero out or otherwise migrate `poolInfos[_lp]` (e.g., set `isActive = false`, and require `totalVoteInVlmgp == 0` / force a mass `unvote` or reward-pool migration before removal) so that stale `userVotedForPoolInVlmgp` balances cannot outlive the pool's lifecycle. Alternatively, prevent `addPool` from being called with an `_lp` address that still has outstanding `userVotedForPoolInVlmgp` balances from a prior incarnation, or have `addPool` carry forward the previous `totalVoteInVlmgp` for that address instead of resetting to `0` when re-adding a previously-used LP address.

### Proof of Concept
Foundry test outline:
1. Deploy `WombatBribeManager`, a `BribeRewardPool` rewarder, and `vlMGP`; owner calls `addPool(lpA, rewarderA, "poolA")`.
2. Attacker locks MGP, calls `vote([lpA], [1000e18])` — asserts `userVotedForPoolInVlmgp[attacker][lpA] == 1000e18` and `poolInfos[lpA].totalVoteInVlmgp == 1000e18`.
3. Owner calls `removePool(indexOf(lpA))` — assert `pools` no longer contains `lpA`, but `poolInfos[lpA].isActive == true` and `poolInfos[lpA].totalVoteInVlmgp == 1000e18` still (untouched).
4. Owner calls `addPool(lpA, rewarderB, "poolA-v2")` — assert `poolInfos[lpA].totalVoteInVlmgp == 0` and `isActive == true`, while `userVotedForPoolInVlmgp[attacker][lpA]` is still `1000e18`.
5. Attacker calls `unvote(lpA)` — expect revert (arithmetic underflow / panic 0x11) on `pool.totalVoteInVlmgp -= currentVote`.
6. Assert attacker's staked bribe balance in the original `BribeRewardPool` (or the vote credit) remains permanently inaccessible via `unvote`, demonstrating the freeze.
