## Title
Stateful global regex in `testForInvalidChars` allows malicious branch names from `x-github-client://openRepo/...?branch=` deep links to bypass validation - (File: `app/src/lib/sanitize-ref-name.ts`)

### Summary
`app/src/lib/parse-app-url.ts` validates the `branch` query-string parameter of an attacker-controlled deep link (`x-github-client://openRepo/...`) by calling `testForInvalidChars(branch)` before accepting it as a real branch name to check out. [1](#0-0) 
That function delegates to a **module-level regex literal that carries the `g` (global) flag** and is reused across calls with `.test()`: [2](#0-1) 

Because `invalidCharacterRegex` is declared once at module scope and both `sanitizedRefName` (`.replace`) and `testForInvalidChars` (`.test`) reuse the *same* regex object, its `lastIndex` property is mutated as a side effect of matching. A `RegExp` with the global flag used via `.test()` remembers where the previous match ended and resumes searching from there on the next call — this is the well-known JavaScript "stateful global regex" pitfall. Depending on the call sequence (e.g., a previous validation call on an earlier value left `lastIndex` pointing partway into the string, or beyond the string length), a subsequent call to `testForInvalidChars` on a *new*, attacker-supplied string can incorrectly return `false` even though the string contains characters that should be rejected (control characters, `~^:?*[\|"<>`, `..`, `@{`, `.lock` suffix, etc.).

### Finding Description
The broken invariant is: *"`testForInvalidChars(name)` truthfully reports whether `name` contains any character/sequence forbidden by git's ref-name rules, independent of prior calls."* This invariant does not hold because the regex object's `lastIndex` is shared and mutated across invocations:

- `RegExp.prototype.test()` with the `g` flag starts scanning from `lastIndex` and updates `lastIndex` to just after the match (or resets to `0` only when a match attempt from a non-zero `lastIndex` fails to find anything and reaches end-of-string with no match, or when the regex reaches the end without a match after previously matching).
- Because the *same exact* `RegExp` instance (`invalidCharacterRegex`) is used both by `sanitizedRefName`'s `.replace()` (which, for a global regex, always resets `lastIndex` to `0` at the start and processes the whole string) and by `testForInvalidChars`'s `.test()` (which does **not** reset `lastIndex` at the start, and leaves a non-zero `lastIndex` behind whenever a match is found short of the string's end), interleaved calls corrupt each other's state.
- Concretely: if `testForInvalidChars` is called once with a string where a forbidden character appears mid-string (e.g. `"ok<part"`), `.test()` returns `true` and leaves `lastIndex` set past the match. A subsequent call to `testForInvalidChars` with a *different* attacker-supplied string that also contains a forbidden character **earlier than `lastIndex`** will have the scan start mid-string (at the stale `lastIndex` offset) and can miss the offending character entirely, returning `false` — i.e., "no invalid characters found" for a string that actually contains one.

This directly feeds `parseAppURL`'s deep-link handler: [3](#0-2) 
An attacker who controls the value of the `branch` parameter in a crafted `x-github-client://openRepo/...` URL (delivered as a normal web link the victim clicks, matching the OS-registered protocol handler in `app/src/main-process/main.ts`) can therefore get a branch string containing forbidden ref characters accepted as valid, past the one guard (`testForInvalidChars`) that exists specifically to reject it. The value then flows into `IOpenRepositoryFromURLAction.branch` and ultimately into the app's clone/checkout flow (`dispatchURLAction` → `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts`), where it is expected to already be a validated, safe git ref.

### Impact Explanation
Ref names are normally used to build git command arguments and are also derived into file-system paths in the checkout/clone flow. Because the guard is bypassable and the poisoned value depends on unrelated prior calls (nondeterministic to the app but fully within an attacker's control if they can trigger repeated deep-link clicks or predict the ordering, e.g. by embedding a first "priming" deep link followed by the payload deep link), a crafted branch value containing characters the check is supposed to strip (e.g. `..`, control characters, or characters with special meaning to git ref parsing) can reach downstream git/checkout logic unsanitized. This falls squarely in the reported bug class: a validation function that is *supposed* to enforce a security boundary but, due to an implementation defect (stateful global regex reused via `.test()`), silently fails to enforce it for certain inputs — exactly analogous to the Solidity report's setter that checks against the wrong bound and thus never actually constrains the value.

### Likelihood Explanation
The attacker-controlled surface (a clickable custom-protocol link) is exactly the kind of unprivileged, remote-trigger vector the task requires — no local access, no prior malware, no leaked credentials. Triggering the stateful bug reliably requires the attacker to control (or predict) the sequence/content of prior `testForInvalidChars` calls in the same process lifetime, which somewhat lowers reliability compared to a single-shot check, but the underlying defect is deterministic and reproducible: `RegExp.prototype.test` with a `g`-flagged, module-shared regex is a textbook bug, and `parseAppURL` is the only gate on `branch` before it's trusted as a safe ref.

### Recommendation
- Do not reuse a single module-level `RegExp` instance with the `g` flag across multiple stateless validation calls. Either:
  - Remove the `g` flag from `invalidCharacterRegex` for the `testForInvalidChars` use case (a non-global regex's `.test()` does not carry `lastIndex` state), keeping a separate global-flagged regex (or resetting `lastIndex = 0` before each `.test()` call) for `sanitizedRefName`'s `.replace()`.
  - Or construct a fresh `RegExp` object per call.
- Add unit tests that call `testForInvalidChars` multiple times in sequence with different inputs (including inputs where an earlier call left a non-zero `lastIndex`) to catch regressions of this class.

```typescript
// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
```
