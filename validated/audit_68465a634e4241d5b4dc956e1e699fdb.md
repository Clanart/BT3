### Title
Deterministic CachedPreprocess reused across distinct `share`/`complete` invocations enables private key share recovery via nonce reuse - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` stores a FROST preprocess seed (`CachedPreprocess`, a 32-byte ChaCha20 seed) in the DB keyed only by `context`, and on every call re-derives the *identical* signing nonces from that seed. The cache is never consumed or invalidated. `share_internal` re-creates the machine from this seed for each signing attempt, and `DkgConfirmer::complete` calls `share_internal` a second time to rebuild the signature machine. If `share`/`complete` are ever evaluated with a different attacker-supplied preprocess set or `key_pair` (hence a different `msg` and different binding factors `rho`) under the same `(b"DkgConfirmer", attempt)` context, the same raw nonces `(d, e)` are signed against two distinct equations, directly yielding the secret key share.

### Finding Description
The external report describes a TOCTOU-style flaw: an object is validated under one state, then swapped before use. The Serai analog is a state-reuse/check-then-reuse flaw in nonce lifecycle management:

- `preprocess_internal` (`coordinator/src/tributary/signing_protocol.rs:123-145`) writes `CachedPreprocesses[context]` only if absent, then unconditionally reloads it and calls `AlgorithmSignMachine::from_cache`. There is no deletion, no "already used for message X" marker, and no binding of the seed to the preprocess set or message. [1](#0-0) 
- `from_cache` → `seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`) derives all nonces deterministically via `ChaCha20Rng::from_seed(*seed.0)`; identical seed ⇒ identical `(hiding_nonce, binding_nonce)` scalars `d, e`. [2](#0-1) 
- `share_internal` (`signing_protocol.rs:150-181`) accepts a `HashMap<Participant, Vec<u8>>` of serialized preprocesses and a `msg` — both derived from on-chain data including the attacker-influenced `key_pair` via `set_keys_message` (`signing_protocol.rs:296-301`) — and calls `machine.sign(preprocesses, msg)`. [3](#0-2) 
- `DkgConfirmer::complete` calls `share_internal` *again* (`signing_protocol.rs:321-324`), meaning `sign` runs once during share generation and once during completion. The file's own header acknowledges the danger: "it is explicitly unsafe to reuse nonces across signing sessions… In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" (`signing_protocol.rs:25-35`), and lists an unimplemented TODO to check that presumed preprocesses match on-chain preprocesses (`signing_protocol.rs:50-54`). [4](#0-3) 

The safety argument rests entirely on BFT finality guaranteeing identical inputs; nothing in the code enforces that the `(preprocesses, msg)` pair bound to a cached seed is unique. If any path (the documented handover/batch races, a second confirmation transaction for the same attempt with a different `key_pair`, or differing `removed`/`participants` composition) feeds distinct values into `share_internal` under the same context, the guard fails silently.

### Impact Explanation
A FROST signature share is `z = d + rho·e + s·λ·c`, where `rho` is the binding factor over all commitments and `c` the transcript challenge. With the same `d, e` and two runs differing in `preprocesses` or `msg`, an observer obtains `z₁, z₂` with known `rho₁≠rho₂`, `c₁≠c₂` — two linear equations in `e` and `s·λ` — recovering the validator's MuSig private key share. This key is the validator's root-of-trust Ristretto key used for on-chain DKG confirmation signing, so recovery compromises the validator's identity across the protocol, not just one signature.

### Likelihood Explanation
The exploit requires two executions of `share_internal` under one `(attempt)` context with differing preprocess sets or messages. Preprocesses and `key_pair` are public, attacker-influenced inputs published to the tributary. Whether a second distinct input set can be finalized for the same attempt depends on tributary ordering guarantees not verifiable from the crypto code alone; the code itself explicitly flags this assumption with TODOs and acknowledges "a race between Tributary ack and the availability of all Preprocesses" elsewhere. Rated Medium-High: the primitive violation is real and deterministic; the trigger depends on consensus-layer edge cases the codebase itself documents as unresolved.

### Recommendation
Bind the cached seed to its consuming inputs: store a hash of the exact `(sorted serialized preprocesses, msg)` alongside `CachedPreprocesses[context]`, and in `share_internal` reject (or use a fresh nonce via `preprocess(&mut OsRng)` instead of `from_cache`) if the tuple differs from the first-recorded one. Alternatively, delete the cache entry on first `sign` and persist the resulting `AlgorithmSignatureMachine` state for `complete`, rather than re-deriving nonces by re-execution.

### Proof of Concept
```rust
// Same context → same seed → identical nonces d, e
let protocol = SigningProtocol { key, spec, txn, context: (b"DkgConfirmer", attempt) };

// First call: honest preprocess set P1, message m1
let (_, share1) = protocol.share_internal(&participants, P1, &m1).unwrap();

// Second call (e.g., complete() with a different finalized key_pair / preprocess set):
// from_cache regenerates the SAME d, e, but rho2 != rho1 and c2 != c1
let (_, share2) = protocol.share_internal(&participants, P2, &m2).unwrap();

// z_i = d + rho_i*e + s*lam*c_i  →  solve 2x2 linear system for e, then s*lam
// e = (share1 - share2 - s_lam*(c1 - c2)) / (rho1 - rho2)
// two equations, two unknowns → validator private key share recovered
```

  2) A reorganization occurred from chain A to chain B, and with it, different messages

  fn share_internal(
    &mut self,
    preprocesses: HashMap<Participant, Vec<u8>>,
    key_pair: &KeyPair,

    let participants = self.spec.validators().iter().map(|val| val.0).collect::<Vec<_>>();
    let preprocesses =

    let msg = set_keys_message(
      &self.spec.set(),
      &self.removed.iter().map(|key| Public::from(key.to_bytes())).collect::<Vec<_>>(),
      key_pair,
    );
    self.signing_protocol().share_internal(&participants, preprocesses, &msg)
  }

    &mut self,
    preprocesses: HashMap<Participant, Vec<u8>>,
    key_pair: &KeyPair,
  ) -> Result<[u8; 32], Participant> {
    self.share_internal(preprocesses, key_pair).map(|(_, share)| share)
  }

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
