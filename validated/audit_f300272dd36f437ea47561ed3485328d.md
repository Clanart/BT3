### Title
Fungible/non-fungible token literally named `"*"` collides with the wildcard-allowance sentinel in `restrict-assets?`/`as-contract?`, letting movements escape their declared allowance - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
`restrict-assets?` and `as-contract?` let a caller enumerate exact `with-ft`/`with-nft` allowances plus an optional wildcard form `(with-ft <contract> "*" <amount>)` meant to cover *all* fungible tokens of a contract. `check_allowances` implements that wildcard by constructing a sentinel `AssetIdentifier { contract_identifier, asset_name: "*" }` and merging it into every asset's allowance lookup [1](#0-0) . Because Clarity's `ClarityName` grammar accepts the single character `"*"` as a legal token/asset name (the same rule that allows operator names like `+`, `-`, `/`), a contract can legitimately `define-fungible-token`/`define-non-fungible-token` an asset whose real name is `"*"`. `eval_allowance` never rejects this name when building an `Allowance::Ft`/`Allowance::Nft` from `with-ft`/`with-nft` [2](#0-1) . Consequently an allowance the caller wrote to protect only the asset literally named `"*"` is indistinguishable, at the `AssetIdentifier` level, from the engine's own "allow every fungible/non-fungible token in this contract" sentinel, and is applied as a blanket allowance to every other token in that contract.

### Finding Description
`check_allowances` builds a map `ft_allowances: HashMap<AssetIdentifier, Vec<(usize,u128)>>` keyed by the `AssetIdentifier` produced from each `with-ft` allowance (`contract_identifier` + `asset_name`) [3](#0-2) . When checking each fungible token actually moved, it merges the exact-match entry with whatever is stored under the synthetic key `asset_name = "*"` for the same contract [4](#0-3) . This is the intended implementation of the documented wildcard feature (`with-ft <contract> "*" <amount>` covers all FTs of that contract), as shown by the passing test `test_restrict_assets_with_ft_wildcard_ok` [5](#0-4) .

The bug is that this synthetic key is not reserved: nothing in `eval_allowance`'s FT/NFT parsing path validates or special-cases the `asset_name` string beyond requiring it to be a syntactically valid `ClarityName` [2](#0-1) , and `ClarityName`'s grammar accepts single-character operator-style names, including `"*"`, for `define-fungible-token`/`define-non-fungible-token` asset names. A contract author can therefore deploy `(define-fungible-token * )` (an asset literally named `*`) alongside other, unrelated tokens (`token-a`, `token-b`, ...). Any allowance a user writes as `(with-ft .contract "*" u10)`, intending to restrict spending of only the token named `*`, is stored under the exact same `AssetIdentifier` the engine treats as the "allow all FTs in this contract" wildcard. The FT-movement check loop at lines 598-627 then applies that allowance to every fungible token of the contract, not just the one literally named `*`, because the exact-match lookup and the wildcard lookup for that contract resolve to the identical map entry. The same collision exists for NFTs via the analogous sentinel construction at lines 637-642.

This breaks the equality the post-condition/allowance mechanism is supposed to enforce: *only assets covered by an allowance may move, and only up to the declared amount*. Here, an allowance nominally scoped to one specific asset (`"*"`) is silently promoted to cover the entire contract's token set, so assets outside the allowance's intended scope can move without violating the check — i.e., an asset moves past its post-condition/allowance.

### Impact Explanation
This falls under "an asset moving past its post-conditions" (Critical, per the scan rules), because a `restrict-assets?`/`as-contract?` scope that a signer or contract author explicitly wrote to constrain a specific asset ends up granting unrestricted movement of every other fungible (or non-fungible) token belonging to the same contract, without any corresponding authorization for those other assets. Funds/assets not intended to be exposed by the allowance can be moved inside the protected scope and the violation will not be detected, since `check_allowances` will report `Ok(None)` (no violation) for those movements.

### Likelihood Explanation
Exploitation requires: (1) a contract that defines a fungible or non-fungible token literally named `*` (legal Clarity syntax, but an unusual naming choice a contract author would need to make, whether intentionally or by accident) alongside other tokens, and (2) a `restrict-assets?`/`as-contract?` caller who writes `(with-ft <that-contract> "*" <amount>)` intending to scope the allowance to the `*`-named asset specifically. This is a narrow but concrete scenario: a malicious or careless contract could deliberately name a token `*` specifically to weaponize this collision against any code that later tries to `restrict-assets?` its use of that contract's tokens, turning what looks like a tight allowance into a blanket one.

### Recommendation
Reserve `"*"` as a wildcard sentinel that cannot also be a real asset name in this API: either (a) reject `asset_name == "*"` when constructing the exact-match `AssetIdentifier` in `eval_allowance`'s FT/NFT branches (forcing users to use the dedicated wildcard syntax and preventing any exact match from colliding with it), or (b) represent the wildcard internally with a value that is not a valid `ClarityName` (e.g., an `Option<ClarityName>` field on `AssetIdentifier`/`FtAllowance` instead of overloading the `asset_name` string), so an exact match on a literal `"*"`-named asset can never be conflated with the "all fungible tokens in contract" case.

### Proof of Concept

;; one literally named "*", and a real token "gold" that should be protected.
(define-fungible-token *)
(define-fungible-token gold)
(ft-mint? * u1000 tx-sender)
(ft-mint? gold u1000 tx-sender)

;; A caller wants to allow spending up to 10 units of the token literally
;; named "*", and nothing else, inside a protected scope:
(restrict-assets? tx-sender ((with-ft .this-contract "*" u10))
  ;; Because AssetIdentifier{contract, "*"} is also the engine's wildcard key,
  ;; this call moving 500 "gold" tokens is NOT flagged as a violation,
  ;; even though "gold" was never named in the allowance list.
  (try! (ft-transfer? gold u500 tx-sender 'SP000000000000000000002Q6VF78))
)

;; has no allowance.
