### Title
Copilot merge-conflict resolution splices AI content using a second, independently-implemented marker parser that can desynchronize from the one used to build the prompt, silently corrupting committed file content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's "Resolve with Copilot" feature reads a conflicted file once to build the model prompt (`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts`), sends only the per-conflict text to the LLM, then reassembles the final file by splicing the model's per-hunk output back into the *original on-disk content* using a second, independently written marker-matching routine (`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts`). The only safety check tying these two together (`validateResolutionPaths`) compares hunk **counts**, not hunk **boundaries/content**. Because the two marker parsers are separate implementations with different scanning rules, a conflicted file whose "ours"/"theirs" regions legitimately contain literal conflict-marker-like text (e.g. `<<<<<<<`, `=======`, `>>>>>>>` appearing in documentation, patch/diff fixtures, or code that discusses Git conflicts — all fully attacker-controlled content in a fetched/cloned branch) can cause the reassembly parser to draw different splice boundaries than the extraction parser used to produce the prompt, even when the reported hunk counts happen to match. The result is that AI-approved-looking content is written to the wrong location in the file and silently staged into the user's next commit.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks the raw file once using regexes `oursMarker` (`^<{7}`), `baseMarker` (`^|{7}`), `separatorMarker` (`^={7}$`), `theirsMarker` (`^>{7}`), stopping "ours" collection at the *first* base/separator match, then collecting base/theirs similarly. This produces `N` `IConflictHunk`s that are sent to the model.

`validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:473-521`) only asserts `resolution.hunks.length === expectedCount`, where `expectedCount` is `N` from `extractConflictHunks`. It never checks that the boundaries the model responded to are the same byte ranges that a second walk of the file will find.

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) is a *separate* state machine over the *same raw string*, using its own regexes (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`). It finds `<{7}` lines, then scans forward for a `={7}` line (setting a boolean, not stopping) and finally an `>{7}` line to close the block, and splices `hunkResolutions[hunkIndex]` into that span **by array index only**, per its own explicit comment: *"matched by order, not by line number."*

Because both parsers are independently implemented, any content in the conflicting file that is legitimately shaped like a Git conflict marker (a `<<<<<<<`, `|||||||`, `=======`, or `>>>>>>>` line appearing as ordinary file content rather than a genuine Git-inserted marker — e.g. in a Markdown doc explaining how to resolve conflicts, a fixture file for a merge tool, or a text file with a Setext-style `=======` heading underline) can make the two scanners disagree about how many marker "blocks" exist or where they begin/end, while still reporting the same overall hunk count `N` to the coarse count check in `validateResolutionPaths`. When that happens, `reassembleResolvedFile` will splice `hunkResolutions[i].resolvedContent` — which the model computed for a *different* conflict, based on the boundaries from `extractConflictHunks` — into the wrong span of the file.

This is applied without further review: `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7171-7269`) writes `resolution.resolvedContent` straight to disk with `writeFile` and runs `git add` on the path [1](#0-0) , so the corrupted content is staged into the user's next commit. The `resolveWithin` path-traversal guard [2](#0-1)  and the "user resolved it externally" skip check [3](#0-2)  address different problems and do nothing to catch a boundary mismatch between the two marker parsers.

### Impact Explanation
The attacker only needs to control the content of a branch/PR/fork that the victim merges, rebases, or cherry-picks in Desktop (a clone/fetch object the attacker fully controls, per the valid-impact scope). If they can make the "theirs" (or "ours") side of a conflict contain text that legitimately matches a conflict-marker regex, they can cause the reassembly step to mis-align the AI's per-hunk output with the wrong region of the file. This silently corrupts what the user commits and pushes — e.g. dropping/duplicating a code block, moving another developer's code out of its intended file section, or splicing AI-authored text into an unrelated part of the file — without the discrepancy being visible unless the user manually diffs the fully reassembled file against their expectation (the result dialog shows the model's own claimed hunk boundaries/reasoning, not necessarily a diff against the true reassembled boundaries).

### Likelihood Explanation
The only two structural preconditions are (1) the Copilot conflict-resolution feature being enabled/used, and (2) a conflicted file containing incidental content matching one of the 4 marker regexes — a realistic occurrence in documentation about Git, in test fixtures, in ASCII dividers, or in files that themselves discuss/example conflict markers. This requires no local access, no credentials, and no unusual user action beyond the normal "Resolve with Copilot" flow that Desktop already promotes for conflict resolution.

### Recommendation
- Make `reassembleResolvedFile` reuse the exact same marker-extraction pass as `extractConflictHunks` (ideally have `extractConflictHunks` return the line index ranges of each hunk, and have reassembly consume those ranges directly) instead of re-deriving them with separate regex logic.
- Strengthen `validateResolutionPaths` to validate structural equivalence (e.g., a hash/fingerprint of each hunk's original `oursContent`/`theirsContent`) rather than only comparing counts, so any parser disagreement is rejected before the resolution is applied.
- After reassembly, diff the final result against the original file outside conflict-marker regions and refuse to stage if unexpected non-conflict lines changed.

### Proof of Concept
1. Set up a repository whose `README.md` (or any tracked file) legitimately contains a block of text such as:
   ```
   Example of a Git conflict:
   <<<<<<< HEAD
   foo
   =======
   bar
   >>>>>>> branch
   ```
   as ordinary documentation content (not an actual conflict) in a file that will *also* end up with a real conflicting region elsewhere from a merge.
2. Craft two branches such that merging them produces a real conflict in the same file, positioned so that `extractConflictHunks`'s "stop at first marker" scanning and `reassembleResolvedFile`'s "scan forward for closing marker" scanning walk the combined marker-like content differently (e.g., by having the genuine conflict's `<<<<<<<`/`>>>>>>>` markers sit near the documentation block so the two independent walks compute different block boundaries while still reporting the same total hunk count).
3. In Desktop, trigger the merge, invoke "Resolve with Copilot", and accept the suggested resolution.
4. Inspect the resulting file on disk / staged diff: the AI-resolved content for one conflict ends up spliced into the wrong span (either overlapping the documentation block or offset from the real conflict), which is then committed via `git add` without further validation.

Note: I was not able to execute the code to confirm a concrete byte-for-byte divergent test case (no runtime/tooling access in this session); the analysis above is based on static comparison of the two marker-parsing implementations and the validation logic that connects them, which do not share a single source of truth for hunk boundaries.
