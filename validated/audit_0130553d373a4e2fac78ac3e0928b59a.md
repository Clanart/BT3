### Title
Session fixation of `session[:shopify_user_id]` bypasses re-binding on offline OAuth callback, enabling cross-user scope-check oracle - ([File: app/controllers/shopify_app/callback_controller.rb])

### Summary
`CallbackController#update_rails_cookie` only overwrites `session[:shopify_user_id]` when the freshly-validated `api_session` is **online**; for **offline** sessions it leaves whatever value was already present in the Rails session untouched. Since `start_user_token_flow?` (and the `update_user_access_scopes?` it calls) is only reached when `shopify_session.online?` is `false`, an attacker who pre-plants a victim's `shopify_user_id` in their own session cookie before completing an offline OAuth callback for their own shop can make the app query `user_access_scopes_strategy.update_access_scopes?(shopify_user_id: victim_id)` using the victim's id while impersonating no one but their own shop context.

### Finding Description
The relevant code: [1](#0-0) 

```ruby
session[:shopify_user_id] = api_session.associated_user.id if api_session.online?
```

This line only fires for online sessions. For offline sessions (the ones that flow into `start_user_token_flow?`), `session[:shopify_user_id]` is never reset from the just-verified OAuth result: [2](#0-1) 

```ruby
def start_user_token_flow?(shopify_session)
  return false unless ShopifyApp::SessionRepository.user_storage.present?
  return false if shopify_session.online?

  update_user_access_scopes?
end

def update_user_access_scopes?
  return true if session[:shopify_user_id].nil?

  user_access_scopes_strategy.update_access_scopes?(shopify_user_id: session[:shopify_user_id])
end
```

`update_access_scopes?` with a `shopify_user_id` calls `retrieve_user_session_by_shopify_user_id(shopify_user_id)` and compares its `scope` against the configured scopes: [3](#0-2) 

If the attacker can make `session[:shopify_user_id]` hold a victim's numeric id at the time the offline callback runs (e.g., via a stale/forged Rails session cookie set before initiating their own login/OAuth), then `update_user_access_scopes?` is evaluated against the victim's id, not the attacker's just-authenticated identity. The result (`true`/`false`) drives whether the controller redirects to `respond_with_user_token_flow` (re-triggering login) versus continuing normal flow — this is directly observable by the attacker as a response/redirect difference, making it an oracle for whether a given `shopify_user_id` has a stored session with scopes matching (or not) the app's configured scopes.

I was not able to locate `LoginController`/`SessionsController` in the indexed codebase to confirm whether `session` is reset (e.g., `reset_session`) at the start of the `/login` flow before the callback runs; the grep for `reset_session`/`session.clear` returned no hits in application source files (only in tests/docs), suggesting no such reset exists in the shipped controllers. This is a gap in what I could verify — if a reset does happen at some other reachable point in the request lifecycle it would neutralize this issue, but no such code was found via search.

### Impact Explanation
This is a cross-user information-disclosure oracle scoped to the `user_access_scopes_strategy` check: an attacker (any user with an unrelated shop) can determine, per numeric `shopify_user_id`, whether that user's stored online-session scopes differ from the app's currently configured scopes, without needing that user's token. It does not directly hand over the victim's access token, but it breaks the invariant that user/session binding must derive solely from the just-verified OAuth result, and creates a targeted cross-user probing primitive tied to Shopify's "Broken Authentication and Session Management" / information disclosure impact class.

### Likelihood Explanation
Requires the attacker to control or retain a stale/forged `session[:shopify_user_id]` value across a fresh, otherwise-legitimate OAuth login for their own shop (classic session-fixation precondition), and requires the app to use the offline-token flow with a configured `user_storage`/`user_access_scopes_strategy` (opt-in feature). It is repeatable since the branch condition (`shopify_session.online? == false`) is deterministic per app configuration.

### Recommendation
Always derive `session[:shopify_user_id]` (or clear it) based on the outcome of the current OAuth callback, regardless of whether the resulting session is online or offline — e.g., explicitly delete/reset `session[:shopify_user_id]` when the new session is offline, rather than leaving a previously-set value in place. More broadly, call `reset_session` (or clear all identity-bearing session keys) at the start of the login/callback flow before trusting any session-derived identifier.

### Proof of Concept
```ruby
test "offline callback does not clear a pre-existing session[:shopify_user_id]" do
  session[:shopify_user_id] = "victim_id_123"

  # attacker's own valid offline OAuth callback for their own shop
  api_session = mock_offline_shopify_api_session # session.online? == false

  get :callback, params: { shop: "attacker-shop.myshopify.com", code: "...", timestamp: "...", hmac: "..." }

  # Expected (secure) behavior: session[:shopify_user_id] should be nil/cleared for offline sessions
  # Actual behavior: session[:shopify_user_id] remains "victim_id_123",
  # and update_user_access_scopes? is evaluated against the victim's id.
  assert_not_equal "victim_id_123", session[:shopify_user_id]
end
```
This asserts that `session[:shopify_user_id]` must never be left as an attacker-preset victim id when the resulting session is offline, matching the stated invariant in the question.
