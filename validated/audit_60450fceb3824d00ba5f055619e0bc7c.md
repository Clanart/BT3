### Title
Same-block transaction metadata poisoning overwrites earlier Bitcoin deposit instructions - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` accumulates `outputs` across all transactions in a block, but computes `presumed_origin` and `extract_serai_data(tx)` from only the latest matching transaction and applies those values to every accumulated output. An unprivileged Bitcoin user can therefore place a malicious Serai-paying transaction after a victim’s deposit in the same block and overwrite the victim output’s origin/data with attacker-controlled metadata.

### Finding Description
The `outputs` vector is declared before iterating `block.txdata[1 ..]` and is not scoped to the current transaction. After each transaction, if the cumulative vector is non-empty, the implementation derives metadata from `tx.input[0]` and `Self::extract_serai_data(tx)`, then mutates every element in `outputs`, including outputs emitted by earlier transactions. A second transaction paying any registered scanner output causes the earlier external output’s `data` field to be replaced.

The scanner itself identifies deposits solely by `script_pubkey`, so an attacker can create a matching output without possessing the threshold key.

### Impact Explanation
A deposit transaction’s Serai instruction data can be replaced by attacker-controlled instruction data. If downstream processing credits `OutputType::External` outputs using `data`, the victim’s confirmed BTC deposit can be processed with the attacker’s destination/instruction, causing funds to be minted or credited to the wrong account.

### Likelihood Explanation
The attacker only needs to broadcast a transaction that appears in the same block after the victim transaction and pays any registered scanner script. This requires favorable block inclusion/ordering, but does not require validator compromise, key disclosure, malformed encodings, or control of Serai infrastructure.

### Recommendation
Populate output metadata transaction-locally. For each transaction, collect `tx_outputs` independently, derive `presumed_origin` and `data` for that transaction, mutate only `tx_outputs`, then append them to the block-level result.

### Proof of Concept
1. For active key `K`, construct victim transaction `T_v` with:
   - an external deposit output matching `Scanner::new(K)`;
   - an OP_RETURN Serai instruction crediting `victim_account`;
   - a first input controlled by the victim.
2. Construct attacker transaction `T_a`, ordered after `T_v` in the same block, with:
   - any output matching a registered scanner script;
   - an OP_RETURN Serai instruction crediting `attacker_account`;
   - a first input controlled by the attacker.
3. Call `Bitcoin::get_outputs` on the block.
4. `T_v`’s scanned output is first populated from `T_v`, but when `T_a` is processed, `outputs` remains non-empty and the loop mutates the earlier victim output with `T_a`’s `presumed_origin` and `data`.
5. Both outputs are returned with attacker-derived metadata, while the victim output retains its victim outpoint and amount.
