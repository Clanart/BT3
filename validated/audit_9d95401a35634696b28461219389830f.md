## Title
Unbounded recursive descent parsing of on-chain PlotNFT/custody memos causes wallet stack-overflow DoS - (`chia/wallet/puzzles/custody/custody_architecture.py`)

## Summary
`PuzzleWithRestrictions.from_memo()` recursively parses an attacker-controlled CLVM memo tree with no depth limit. Because nested `MofN` puzzle nodes cause the parser to recurse once per nesting level, a coin creator (e.g. a PlotNFT/pool-owner or anyone constructing a custody-style coin with a crafted `CREATE_COIN` memo) can force any wallet that later tries to sync/interpret that coin's memo to recurse until the Python interpreter raises `RecursionError`/crashes, halting wallet transaction processing for that coin. This is the same bug class as CVE-2022-43358 in libsass's `has_placeholder`: an unbounded recursive walk over an attacker-supplied nested tree structure leading to stack exhaustion.

## Finding Description
`PuzzleWithRestrictions.from_memo()` is a classmethod that parses a `Program` memo into a `PuzzleWithRestrictions` object: [1](#0-0) 

When the parsed structure indicates `further_branching` (i.e., the puzzle is an `MofN` node), the code decodes an `MofNHint` and then calls `PuzzleWithRestrictions.from_memo()` again for *every member memo*:

```python
if further_branching:
    m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
    puzzle: MIPSComponent = MofN(
        m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
    )
```

Each member memo can itself encode a nested `MofN`, so an attacker who controls the memo (i.e., anyone who creates a coin and sets its memo, or who submits a `CoinSpend` with a `CREATE_COIN` condition carrying a crafted memo blob) can nest `MofN` structures to an arbitrary depth. There is no depth or size limit enforced anywhere in `from_memo`, `MofNHint.from_program`, or `RestrictionHint.from_program`.

This code path is reached by production, non-test code: `PlotNFT.get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` directly on the memo of a coin observed in a spend, when trying to recognize a PlotNFT's evolving custody puzzle from on-chain data: [2](#0-1) 

This mirrors the pattern that the project's own test suite documents as an intentional recursive feature (`from_memo()` reconstructing "unknown members/restrictions, including recursive `MofN`"), but the recursion is unbounded: [3](#0-2) 

Compare this with the project's own defensive pattern elsewhere: `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py` is deliberately implemented as an iterative stack machine specifically to avoid Python recursion-limit crashes on attacker-influenced/deeply nested CLVM trees: [4](#0-3) [5](#0-4) 

`PuzzleWithRestrictions.from_memo()` does not follow this same non-recursive discipline, despite operating on data that, like tree-hash input, is attacker-influenced.

## Impact Explanation
A malicious pool operator, PlotNFT participant, or any coin creator can craft a coin whose memo encodes a deeply nested `MofN` custody structure. When a wallet (or any code path that calls `PuzzleWithRestrictions.from_memo()` on that memo, such as `PlotNFT.get_next_from_coin_spend()`) attempts to parse it, the unbounded recursion will exhaust the Python call stack, raising `RecursionError` (or, depending on interpreter/recursion limit settings, crashing the process). Because PlotNFT syncing walks the singleton's spend history to reconstruct the current custody state, a single such malicious coin can repeatedly halt processing for any wallet that tries to follow that PlotNFT's lineage — a spend-triggered denial-of-service against wallet transaction processing, matching the "spend-triggered transaction-processing halt" impact category.

## Likelihood Explanation
Likelihood is high for any actor able to create a coin with an attacker-chosen memo (trivial — memos are unrestricted arbitrary CLVM data attached to `CREATE_COIN` conditions) and who can get a victim wallet to observe/sync that coin (e.g., by using it in a PlotNFT-style custody lineage, or by convincing a counterparty's wallet to inspect the coin, e.g. via offers or general DL/PlotNFT sync flows that walk custody memos). No signature or special privilege is required — only the ability to submit a spend bundle with a crafted memo.

## Recommendation
- Enforce an explicit recursion/nesting depth limit in `PuzzleWithRestrictions.from_memo()` (and `MofNHint.from_program`), raising a clean `ValueError` once a configured maximum depth is exceeded, before recursing further.
- Alternatively, rewrite `from_memo()` as an iterative parser using an explicit work-stack (mirroring the pattern already used in `sha256_treehash()`), so parsing untrusted memo trees cannot exhaust the Python call stack regardless of nesting depth.
- Apply the same bound to any other CLVM-derived structure that is recursively parsed from untrusted/on-chain memos (e.g., `RestrictionHint`/`MofNHint` parsing chains) throughout `chia/wallet/puzzles/custody/custody_architecture.py` and its consumers in `chia/pools/plotnft_drivers.py`.

## Proof of Concept
1. Construct a base leaf `MemberHint`/`UnknownMember` memo, e.g. `UnknownMember(MemberHint(puzhash=bytes32.zeros, memo=Program.to(None)))`.
2. Wrap it repeatedly in `MofN(m=1, members=[PuzzleWithRestrictions(nonce=i, restrictions=[], puzzle=<previous>)])` for N iterations (N large enough to exceed Python's default recursion limit, e.g. a few thousand nestings), producing a `PuzzleWithRestrictions` object `deep_pwr`.
3. Call `deep_pwr.memo()` to serialize it into a `Program` memo, and attach that memo bytes to a `CREATE_COIN` condition's memo field of a coin spend (as done for real PlotNFT singleton children).
4. Have a victim call `PuzzleWithRestrictions.from_memo(coin_spend_memo)` (directly, or transitively via `PlotNFT.get_next_from_coin_spend()` when syncing the singleton lineage) — the call recurses once per nesting level with no depth check and raises `RecursionError`, halting the wallet's processing of that coin/singleton lineage.
