### Title
Unbounded buffer read in `is_atom_canonical` causes an unhandled `IndexError` on malformed spend-bundle puzzle/solution bytes, crashing mempool transaction processing - (File: chia/full_node/mempool_manager.py)

### Summary
`is_clvm_canonical()` / `is_atom_canonical()` in `chia/full_node/mempool_manager.py` parse the raw CLVM serialization of a `CoinSpend`'s `puzzle_reveal` and `solution` to detect non-canonical atom length prefixes, ahead of accepting a spend bundle into the mempool. `is_atom_canonical` reads `clvm_buffer[offset]` in a loop, walking `prefix_len` bytes forward based on a length value taken from attacker-controlled bytes, with no bounds check against `len(clvm_buffer)`. A crafted, truncated multi-byte atom length prefix at (or near) the end of the buffer causes `offset` to run past the end of the buffer and raise an unhandled `IndexError`, analogous to the BuildKit frontend-triggered panic (CVE-2024-23650), where malformed but syntactically-parseable input crashes processing instead of being rejected gracefully.

### Finding Description
`is_atom_canonical` computes a length-prefix size (`prefix_len`, 0–5 bytes) from the leading byte of an atom encoding, then loops `prefix_len` times reading successive bytes to build `atom_len`: [1](#0-0) 

Note there is no check that `offset + prefix_len < len(clvm_buffer)` before indexing `clvm_buffer[offset]` inside the loop. It is called from `is_clvm_canonical`, which itself indexes `clvm_buffer[offset]` in a `while True` loop with no upper bound comparison until after the loop exits: [2](#0-1) 

`is_clvm_canonical` is invoked directly on attacker-supplied bytes for every coin spend in a submitted spend bundle, inside `MempoolManager.validate_spend_bundle()`: [3](#0-2) 

This path is reached by any unprivileged submitter of a spend bundle through `FullNode.add_transaction()` → `MempoolManager.add_spend_bundle()` → `MempoolManager.validate_spend_bundle()`. Unlike the CLVM cost/signature validation performed by `validate_clvm_and_signature` (Rust, called earlier in `pre_validate_spendbundle`), this canonical-encoding check is plain Python and does not appear to be guarded against out-of-bounds reads. If a `puzzle_reveal` or `solution` byte string is constructed with a multi-byte atom-length prefix (e.g. leading byte `0xF8`–`0xFF` pattern indicating 2–5 length bytes) whose declared prefix bytes are truncated right at the buffer boundary, `is_atom_canonical` will index past `len(clvm_buffer)` and raise `IndexError`.

Because `pre_validate_spendbundle()`'s call into the Rust validator does not perform this specific canonical-form check itself (it is a separate, later Python-side check in `validate_spend_bundle`), a spend bundle can pass CLVM execution/signature validation and still trigger the unguarded Python parser. `FullNode.add_transaction()` only catches `ValueError` and `ValidationError` around the `pre_validate_spendbundle` call: [4](#0-3) 

The `IndexError` raised deeper inside `add_spend_bundle`/`validate_spend_bundle` (called after `pre_validate_spendbundle` succeeds) is not wrapped in a similar try/except in the code paths inspected, so it propagates as an unhandled exception out of `add_transaction`. The project's own tests confirm the intended behavior for "unexpected" exceptions is to propagate rather than be swallowed: [5](#0-4) 

An uncaught `IndexError` propagating from spend-bundle admission logic — code that also runs when the mempool re-validates cached pending/conflicting items during `new_peak()` block-acceptance processing, not just from a single client's inbound RPC/peer message handler — constitutes the same bug class as the BuildKit report: malformed-but-parseable client input reaching an unguarded array/buffer access and panicking (crashing) the process/handler responsible for transaction processing, rather than being rejected with a normal validation error.

### Impact Explanation
This is a Medium-severity availability issue rather than a fund-theft issue, matching the CVSS profile of the referenced CVE (`AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L`). A successful trigger halts transaction processing for the affected code path: `add_transaction()` (called for every new tx from wallet or peer) or mempool re-validation during `new_peak()` would raise an unhandled `IndexError`, and depending on how far up the call stack the exception is caught (or not), this can crash the async task handling transaction submission or block acceptance, disrupting mempool availability for legitimate spend bundles. This matches the report's category "spend-triggered transaction-processing halt."

### Likelihood Explanation
Likelihood is high for a knowledgeable attacker: constructing a `CoinSpend` with a puzzle_reveal/solution whose serialized bytes end mid-way through a multi-byte atom length prefix is straightforward and requires no special access — the bundle is otherwise a normal syntactically valid, signed (or unsigned, since `is_clvm_canonical` runs regardless of whether the puzzle is ever executed correctly) spend that a wallet or RPC client can submit like any other.

### Recommendation
Add explicit bounds checking in `is_atom_canonical` (and the calling loop in `is_clvm_canonical`) before every `clvm_buffer[offset]` access — e.g., verify `offset < len(clvm_buffer)` and `offset + prefix_len < len(clvm_buffer)` prior to reading, and return `False` (non-canonical/invalid) instead of raising, so malformed encodings are rejected as ordinary validation failures (`Err.INVALID_COIN_SOLUTION`) instead of causing an unhandled exception. Additionally, wrap the `is_clvm_canonical` calls in `validate_spend_bundle` in a try/except that converts unexpected parsing exceptions into a proper `Err` result, consistent with how `pre_validate_spendbundle` converts `ValueError`s from the Rust validator into `ValidationError`.

### Proof of Concept
Construct a `CoinSpend` whose `solution` (or `puzzle_reveal`) bytes end with a single byte such as `0xF8` (indicating a "3 + 8 + 8 + 8 bits length prefix", i.e., `prefix_len = 3`) placed as the very last byte of the buffer, with no subsequent bytes for the declared prefix. When `MempoolManager.validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.solution))` on this buffer:
1. `is_clvm_canonical` reads the terminal `0xF8` byte, calls `is_atom_canonical(clvm_buffer, offset)` with `offset` pointing at the last valid index.
2. `is_atom_canonical` matches the `0b11111000` mask branch, sets `prefix_len = 3`, then loops `for i in range(prefix_len): offset += 1; atom_len |= clvm_buffer[offset]` — the first iteration already indexes one past the end of `clvm_buffer`, raising `IndexError: index out of range`.
3. This exception is not caught by the `ValueError`/`ValidationError` handlers in `FullNode.add_transaction()` [4](#0-3) , so it propagates unhandled out of the mempool admission call for this transaction (and would similarly propagate if hit while mempool re-validates pending items during `new_peak()`), producing exactly the "processing halt on malformed input" failure mode analogous to GHSA-9p26-698r-w4hx.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
