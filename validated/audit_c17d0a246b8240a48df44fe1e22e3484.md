### Title
`ThresholdKeys::read` accepts semantically invalid keys — identity verification shares and shares inconsistent with `secret_share` — bypassing the validity restrictions enforced by the DKG - (File: crypto/dkg/src/lib.rs)

### Summary
The Keycloak flaw is a second entry point (IdP-initiated SSO) that skips a restriction check enforced on the normal login path. The Serai analog is `ThresholdKeys::read`, the serialization/deserialization "endpoint" for obtaining `ThresholdKeys`. The protocol path (PedPoP DKG) enforces two restrictions before keys are usable: every point comes through identity-rejecting readers, and every secret share is proven consistent with its verification share via `share_verification_statements`. `ThresholdKeys::read` enforces neither: it reads verification shares with `Ciphersuite::read_G` (no identity rejection, unlike `Curve::read_G`), and `ThresholdKeys::new` never checks `G * secret_share == verification_shares[i]` or that the share set is mutually consistent. Untrusted bytes can therefore instantiate "keys" that could never have resulted from the protocol.

### Finding Description
`Curve::read_G` rejects the identity point for all wire-read protocol points [1](#0-0) . However, `ThresholdKeys::read` deserializes verification shares with `<C as Ciphersuite>::read_G`, which performs no identity check [2](#0-1) . `ThresholdKeys::new` validates only counts, index bounds, and interpolation applicability — never the consistency between `secret_share` and `verification_shares`, and never rejects identity shares [3](#0-2) . The group key is then derived solely from `verification_shares[1..=t]` [4](#0-3) .

By contrast, the DKG path proves every received share against the sender's commitments before building `ThresholdKeys` [5](#0-4) [6](#0-5) , and builds `verification_shares[i]` as `G * secret` [7](#0-6) . The FROST `complete()` code itself concedes this hole: "the only known way to cause this ... is to deserialize a semantically invalid FrostKeys" [8](#0-7) .

### Impact Explanation
An attacker who feeds crafted bytes to `ThresholdKeys::read` obtains `ThresholdKeys` whose `group_key` is fully attacker-chosen (sum of attacker-supplied verification shares, possibly including identity points that contribute nothing) while `secret_share`/`verification_shares[i]` are mutually consistent under a scalar the attacker knows. Any consumer that uses these keys — a `SignMachine`, `view()`, or an address/outputs derivation keyed off `group_key()` — will operate under a group key whose discrete log the attacker holds. Signatures produced are valid Schnorr shares under the attacker's verification shares, so `complete()`'s fast path accepts them; the resulting aggregate signature verifies under the attacker-controlled group key, i.e. signatures are issued for (and forgeable for) a key the victim never actually shares. Equivalently, funds/outputs attributed to that `group_key` are not spendable by the real threshold set — only by the attacker. This is concrete key-replacement reachable purely through attacker-controlled bytes to an in-scope read API.

### Likelihood Explanation
Exploitation requires the integrator to deserialize `ThresholdKeys` from an attacker-influenced source (restored/corrupted key store, migrated backup, RPC-supplied blob). The library documents no warning that `read` performs weaker validation than the DKG; `read` silently accepts encodings the protocol could never produce. Where key blobs cross trust boundaries, the bypass is deterministic — no probability, no races.

### Recommendation
In `ThresholdKeys::new` (and hence `ThresholdKeys::read`), additionally: (1) reject identity verification shares — read via `Curve::read_G`-equivalent checks or test `is_identity` in `ThresholdKeys::new`; (2) verify `C::generator() * secret_share == verification_shares[&params.i()]`; (3) document that full share-set consistency (all `n` shares lying on a degree-`t-1` polynomial matching `group_key`) cannot be established from a single share, so deserialized keys should only be trusted from authenticated storage. At minimum, align the deserialization path's restrictions with the DKG path's.

### Proof of Concept
1. Attacker picks `x` known to them, sets `group_key = G * x`, `t = n = 2`.
2. Crafts serialized `ThresholdKeys`: `secret_share = x_1`, `verification_shares = {1: G*x_1, 2: G*(x - x_1)}` (and may set `verification_shares[2]` to the identity encoding — accepted because `Ciphersuite::read_G` doesn't reject it).
3. Victim deserializes via `ThresholdKeys::read` → `group_key() == G*x` (attacker-known).
4. Victim runs `AlgorithmSignMachine`/`sign` on an attacker-chosen `msg`; `view()` interpolates and `complete()` succeeds, emitting a valid signature under `G*x` — which the attacker could equally produce alone, while the victim believes it co-signed as a threshold participant. Conversely, deposit addresses derived from `group_key` attribute funds to a key the honest "threshold" never controlled.

fn share_verification_statements<C: Ciphersuite>(
  target: Participant,
  commitments: &[C::G],
  mut share: Zeroizing<C::F>,
) -> Vec<(C::F, C::G)> {
  // This can be insecurely linearized from n * t to just n using the below sums for a given
  // stripe. Doing so uses naive addition which is subject to malleability. The only way to
  // ensure that malleability isn't present is to use this n * t algorithm, which runs
  // per sender and not as an aggregate of all senders, which also enables blame
  let mut values = exponential::<C>(target, commitments);

  // Perform the share multiplication outside of the multiexp to minimize stack copying
  // While the multiexp BatchVerifier does zeroize its flattened multiexp, and itself, it still
  // converts whatever we give to an iterator and then builds a Vec internally, welcoming copies
  let neg_share_pub = C::generator() * -*share;
  share.zeroize();
  values.push((C::F::ONE, neg_share_pub));

  values
}
