## Analysis

The external report's core broken invariant: an attacker can cheaply and repeatedly append entries to a victim's per-user array with **no minimum amount and no access control**, and the array's bounded/unbounded handling causes previously-earned value to be destroyed or become unusable — a griefing/fund-loss primitive triggered by an unprivileged caller acting "on behalf of" a victim who never authorized the action.

The Hyperbridge analog lives in `pallet-bandwidth`'s subscription ledger, fed by the deliberately-open `BandwidthManager.sol::purchase()` entrypoint.

### Title
Unauthenticated `purchase()` lets an attacker grief any app's paid bandwidth allowance via FIFO eviction - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`BandwidthManager.sol::purchase()` lets **any caller** credit a bandwidth subscription to **any** `(chain, app)` pair by simply paying the cheapest tier price, with no relationship required between the caller and the targeted `app`. On Hyperbridge, `pallet_bandwidth::push_subscription` appends every purchase to a FIFO `BoundedVec<Subscription, MaxSubscriptions>` capped at 1024 entries per `(app_chain, app)`, and when full it **silently evicts the oldest entry** — even if that entry belongs to a legitimate app that has real, unexpired, high-value bandwidth remaining. An attacker can therefore burn a victim app's already-paid-for bandwidth allowance by spamming cheap `TierOne` purchases against the victim's `(chain, app)` key until the FIFO cap is reached and the victim's real subscriptions are evicted out from under it.

### Finding Description
`purchase()` is public and unauthenticated with respect to the `app` parameter: [1](#0-0) 

It only checks `app.length != 0`, `chain.length != 0`, `months != 0`, and that the tier price is configured — there is no check that `msg.sender` is, owns, or is authorized by `app`: [2](#0-1) 

This is an intentional "sponsorship" feature (per the docs, anyone can top up anyone's app), but it also means an attacker fully controls the `(chain, app)` key that `on_accept` will push into: [3](#0-2) 

On Hyperbridge, every purchase — regardless of who paid or how small — appends unconditionally to the same bounded FIFO list keyed only by `(app_chain, app)`: [4](#0-3) 

`push_subscription` evicts the oldest entry once the list hits the 1024 cap, regardless of whether that oldest entry still has a large `remaining_bytes` balance and a far-future `expires_at`: [5](#0-4) 

Because the FIFO cap and eviction policy are keyed purely by count, not by remaining value or by payer identity, an attacker who is unrelated to the victim app can:
1. Determine (or predict) the victim's `(app_chain, app)` key — public on-chain via `BandwidthCredited` events.
2. Repeatedly call `purchase(app=victim_app, tier=TierOne, months=1, chain=victim_chain)` — the cheapest configured tier.
3. Each call dispatches a real ISMP message that `on_accept` unconditionally appends to the victim's list via `push_subscription`.
4. Once the list count reaches 1024, each further attacker purchase evicts the oldest entry — which, once the attacker has filled the queue past the victim's remaining slots, is the victim's own paid-for, unexpired subscription.
5. `SubscriptionEvicted` fires with the victim's `lost_bytes`, but the loss is irreversible — the gate (`try_consume`) can no longer draw against those evicted bytes.

There is no minimum-purchase threshold beyond "months > 0" and no rate limit, so the cost floor for the attacker is `TierOne` months=1 (≈$50 per docs), while the destroyed value can be an arbitrarily larger, previously-paid tier (e.g., $1000/8MB). This exactly mirrors the reported bug class: **no minimum amount, no access control on who can push entries into another party's accounting array, and array-eviction/handling semantics that destroy legitimately earned/paid value belonging to someone else.**

### Impact Explanation
This breaks the "bandwidth balances must move exactly once and only to the rightful beneficiary" invariant from the impact gate: the victim app paid real fee-token value for a byte allowance, and an unrelated, unprivileged attacker can force that allowance to be destroyed (evicted) before it is consumed, without the victim's `remaining_bytes` ever being drawn down through the gate. This is a direct fund-loss/DoS vector reachable by any unprivileged EVM account against any Hyperbridge-metered app, requiring no relayer, prover, governance actor, or leaked key — purely a public-entrypoint interaction.

### Likelihood Explanation
High for any app the attacker wants to specifically target: the attack requires only (a) knowing the victim's `(app_chain, app)` key, which is public via `BandwidthCredited`/`BandwidthPurchased` events, and (b) funding enough `TierOne` purchases to fill the remaining FIFO headroom and start evicting. Since a purchase is a single unauthenticated EVM call plus ISMP delivery (no cross-chain relayer collusion assumption beyond the normal, honest delivery path already required to reach `on_accept`), this is straightforward to execute against any known target with sufficient budget.

### Recommendation
- Do not evict entries with `remaining_bytes > 0` and `expires_at` in the future purely by FIFO position; either cap subscriptions per `(chain, app)` in a way that rejects new purchases (or requires the payer to be the app / an allowlisted sponsor) once the list is full, or evict by lowest remaining value / soonest expiry rather than strict insertion order.
- Consider requiring `purchase()` sponsorship to be explicitly opt-in by the target `app` (e.g., an allowlist of permitted sponsors per app), rather than open to any caller.
- Alternatively, aggregate same-tier purchases into a single running-balance entry per `(chain, app, tier)` instead of appending a new FIFO row per purchase, removing the bounded-array eviction surface entirely (mirroring the referenced Radiant fix's "merge same-day claims into one entry" approach).

### Proof of Concept
1. Victim's app `A` on chain `C` has one active, unexpired `TierFour` subscription (8MB) with far-future `expires_at`, appended to `Allowance::<T>::get(C, A)`.
2. Attacker observes `A`/`C` via emitted `BandwidthCredited` event.
3. Attacker calls `BandwidthManager.purchase(A, TierOne, 1, C)` up to `1024` times (funding each with the `TierOne` price), each producing a purchase message that `on_accept` pushes via `push_subscription` into the same `Allowance::<T>` row for `(C, A)`.
4. Once the row reaches the `MAX_SUBSCRIPTIONS = 1024` cap, subsequent attacker purchases evict the oldest entry — first the attacker's own cheap entries, then, once those are gone, the victim's `TierFour` subscription, emitting `SubscriptionEvicted { lost_bytes: <victim's remaining 8MB tier> }`.
5. The victim's app can no longer draw on the evicted bytes through `BandwidthGate::try_consume`, despite having paid for them and despite them not having expired — a pure loss of already-purchased, undelivered service caused entirely by an unrelated third party. [5](#0-4) [1](#0-0)

        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,

            })
        );

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
