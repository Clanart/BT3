## Analysis

The Sherlock report's core pattern: a shared custody contract holds a value that only an **authorized claimant** should be able to withdraw, but a generic public-entrypoint function (`redeem`/`swap`) that operates on "any item matching the commitment" doesn't verify caller authorization, so an arbitrary unprivileged user can redirect the asset to themselves.

The Hyperbridge `IntentGatewayV2` has a directly analogous authorization gap in its solver-selection mechanism.

### Title
Solver-selection restriction is gated by a global config flag instead of the order's own intent, letting any unauthorized filler steal escrowed order funds - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`fillOrder()` only enforces the "authorized solver" restriction when the *gateway-wide* `_params.solverSelection` flag is `true`, rather than checking whether the specific order (`order.session != address(0)`) actually requested restricted fulfillment. [1](#0-0) 

### Finding Description
Users who want their order fulfilled only by a solver they've authorized (via a `session` key and off-chain signature, per the `select()`/`SolverAccount` flow documented in the Intent Gateway overview) rely on this check inside `fillOrder`:
```solidity
if (_params.solverSelection) {
    bytes32 storedSelectionHash;
    assembly { storedSelectionHash := tload(commitment) }
    bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
    if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
}
``` [1](#0-0) 

This gate is keyed on `_params.solverSelection`, a single boolean stored in the gateway's `Params` struct and set at `initialize()`/governance-update time — it applies to *every* order on that deployment, not to the individual order that specified a `session` key. [2](#0-1) 

If the destination-chain gateway instance has `solverSelection == false` (its default/initial state, or if it's simply never turned on for that deployment — same-chain gateways, test deployments, or any instance where governance hasn't explicitly enabled it), the entire authorization block is skipped unconditionally, **even for orders that populated `order.session` expecting exclusive fulfillment**. Any address can then call `fillOrder(order, options)` directly with no `select()` call at all and have `_filled[commitment]` set to itself, exactly like the ERC721 airdrop bug where Bob calls `redeem()`/`swap()` without being the authorized claimant. [3](#0-2) 

Once through this check, `_fillSameChain`/`_fillCrossChain` immediately deliver the escrowed input tokens (`_orders[commitment][token]`) to `msg.sender` as the filler, and set `_filled[commitment]`, finalizing the trade in the attacker's favor. [4](#0-3) 

### Impact Explanation
An order creator who used `session` to restrict fulfillment to a specific, presumably better-priced or trusted solver has that restriction silently voided on any gateway deployment (or period) where `solverSelection` is off. An unprivileged attacker can front-run the intended solver, fill the order with the bare minimum output required, and claim the escrowed input tokens/fees that the intended solver was meant to receive — a direct, unauthorized transfer of bridged/escrowed value to the wrong beneficiary. This maps to the bounty's "unauthorized transaction or execution" / "wrong beneficiary or amount" categories.

### Likelihood Explanation
This requires no malicious peer, relayer, prover, or governance actor — only a normal EOA calling the public `fillOrder` entrypoint. The only precondition is that the destination gateway's `solverSelection` flag is not enabled, which is plausible for gateways that haven't opted into (or have paused) solver selection while still accepting orders that set `order.session`, since nothing in `placeOrder`/`OrderPlaced` prevents a user from populating `session` on a gateway where selection is disabled. [5](#0-4) 

### Recommendation
Tie the authorization check to the order's own intent rather than a global flag: enforce the selection check whenever `order.session != address(0)`, independent of `_params.solverSelection`, or reject `placeOrder` calls that set `order.session` when the destination gateway does not support solver selection.

### Proof of Concept
1. Deploy/observe an `IntentGatewayV2` instance where `_params.solverSelection == false` (default/initial state per `initialize()`).
2. User places a cross-chain (or same-chain) order with `order.session = <sessionKeyAddress>`, intending only a solver holding a valid session signature to fill it.
3. Attacker, with no `select()` call and no session signature, calls `fillOrder(order, options)` directly on the destination gateway, supplying the minimum required output amounts.
4. Because `_params.solverSelection` is `false`, the block at `evm/src/apps/IntentGatewayV2.sol:428-436` is skipped entirely; `_filled[commitment]` is set to the attacker, and the escrowed input tokens are transferred to the attacker via `_fillSameChain`/`_fillCrossChain`, even though `order.session` was populated expecting exclusive fulfillment.

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        if (order.deadline < _blockNumber()) revert Expired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
        if (order.inputs.length != outputsLen) revert InvalidInput();

        if (isSameChain) {
            _fillSameChain(order, options, commitment);
        } else {
            _fillCrossChain(order, options, commitment);
        }

        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {

            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            uint256 alreadyFilled = _partialFills[commitment][outputToken];
            uint256 remaining = totalRequired - alreadyFilled;
            if (remaining == 0 || solverAmount == 0) {
                if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
                continue;
            }
            uint256 fillAmount;

            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;
            if (alreadyFilled == 0 && solverAmount > totalRequired) {
                fillAmount = totalRequired;
                uint256 dust = solverAmount - totalRequired;
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }

                fillAmount = solverAmount > remaining ? remaining : solverAmount;

                msgValue -= (beneficiaryTotal + protocolShare);
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();

                IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);

            if (protocolShare > 0) emit DustCollected(token, protocolShare);

                escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
