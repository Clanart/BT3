### Title
V2 params migration for `x/vm` recovers only a subset of `Params` fields and never re-derives `EvmCoinInfo`, leaving stale/default decimals in place for a chain whose bank denom is non-18-decimal - ([File: x/vm/migrations/v2/migrate_params.go])

### Summary
This is the closest analog I could substantiate in this repo to the reported "schema/migration type mismatch" class of bug (an on-disk representation that the current code cannot correctly read/rebuild after a schema change). Here, `x/vm`'s v1→v2 store migration hand-parses the old protobuf `Params` layout and re-encodes it into the new layout [1](#0-0) , but it never calls `InitEvmCoinInfo`/`SetEvmCoinInfo` to refresh the persisted `EvmCoinInfo` (denom/decimals) entry that the scaling logic depends on. `EvmCoinInfo` is only (re)computed from bank `DenomMetadata` in `InitGenesis` [2](#0-1)  or in a chain's custom `UpgradeHandler` (as shown in the reference upgrade example) [3](#0-2) . If a chain runs the v2 params migration without also calling `InitEvmCoinInfo` in its upgrade handler, `GetEvmCoinInfo` silently falls back to `defaultEvmCoinInfo` (typically 18 decimals) rather than the chain's actual configured decimals [4](#0-3) .

### Finding Description
`GetEVMCoinDecimals()` reads a package-level singleton (`evmCoinInfo`) that is only set once at startup via `SetGlobalConfigVariables` from whatever `EvmCoinInfo` was loaded from the KV store [5](#0-4) . All balance scaling between the native bank denom and the 18-decimal EVM view goes through `ConvertAmountTo18DecimalsBigInt` / `ConvertBigIntFrom18DecimalsToLegacyDec`, which multiply/divide by `evmCoinDecimal.ConversionFactor()` derived from this singleton [6](#0-5) . The `BankWrapper` used by every EVM-triggered bank operation (mint/burn/send/query balance) relies on exactly this conversion factor to keep native-coin and EVM-visible balances at 1:1 parity (per the wrappers documentation) [7](#0-6) .

The v2 migration only restores `EvmDenom`, `ExtraEIPs`, `EVMChannels`, `AccessControl`, and `ActiveStaticPrecompiles` from the old wire format into `types.DefaultParams()` [8](#0-7) ; it does not touch the separate `EvmCoinInfo` KV entry at all. For a non-18-decimal chain (e.g. 6-decimal bond denom, which requires `ExtendedDenomOptions` to be set per `LoadEvmCoinInfo`) [9](#0-8) , if the operator's upgrade handler runs `MigrateStore` for the params schema change but forgets the separate, undocumented-as-required step of calling `k.InitEvmCoinInfo(ctx)` (unlike the reference v0.4.0→v0.5.0 upgrade example that explicitly calls it) [10](#0-9) , `GetEvmCoinInfo` returns `k.defaultEvmCoinInfo` from before the upgrade, or an unrelated cached value, rather than the value actually reflecting `params.EvmDenom`/bank metadata. Since `GetEVMCoinDecimals()` is a process-global singleton set once via `SetGlobalConfigVariables`/`Configure()` at boot and cannot be re-set later (`setEVMCoinInfo` explicitly errors if already set: "EVM coin info already set") [11](#0-10) , a decimals mismatch introduced this way propagates to every subsequent EVM-side balance conversion for the life of the process — corrupting the 1:1 accounting between native coin balances and their EVM-visible (18-decimal) representation used by every precompile, `eth_getBalance` derivation, and internal EVM value transfer.

### Impact Explanation
If the effective EVM decimals differ from the true native denom decimals (e.g. off by 10^12 for a 6-decimal chain treated as 18-decimal, or vice versa), every EVM-side value transfer, precompile balance read, and `ConvertCoin`/native transfer scaling computed via `ConvertAmountTo18DecimalsBigInt`/`ConvertBigIntFrom18DecimalsToLegacyDec` becomes systematically wrong by a fixed power-of-ten factor. This can let unprivileged users move/mint an amount in the EVM view that does not match the actual escrowed/minted native coin amount, or silently truncate/inflate withdrawals — an irreversible accounting corruption of spendable value across native and EVM balances, matching the "Critical unauthorized minting/duplication/accounting corruption" impact category.

### Likelihood Explanation
This requires: (1) a chain using a non-18-decimal EVM denom, and (2) an operator who runs the `x/vm` v2 params-schema migration without separately re-initializing `EvmCoinInfo` in the same upgrade handler. I could not directly confirm within this repo's evidence that `RegisterMigration` in `x/vm/module.go` (unread due to iteration limit) omits an automatic call to `InitEvmCoinInfo` after `MigrateStore`, nor could I confirm whether `evmd`'s own production upgrade handler (`evmd/upgrades.go`) actually invokes the v2 `MigrateStore` function at all — the sample handler shown only performs `DenomMetaData`/`ExtendedDenomOptions`/`InitEvmCoinInfo` setup for the v0.4→v0.5 app-level upgrade, not the v1→v2 `x/vm` consensus-version migration. Given this gap in verification, likelihood is best characterized as **uncertain/Medium** rather than confirmed — the root cause (migration not touching `EvmCoinInfo`) is real and documented in the migration's own comments, but whether the automatic module migration framework calls `InitEvmCoinInfo` as part of `RegisterServices`/`RegisterMigration` wiring was not confirmed before the iteration budget ran out.

### Recommendation
Have the `x/vm` v2 migration (or the `RegisterMigration` wiring in `x/vm/module.go`) explicitly call `k.InitEvmCoinInfo(ctx)` after `MigrateStore` completes, so `EvmCoinInfo` is always re-derived from the (possibly-migrated) `Params.EvmDenom` and current bank `DenomMetadata` rather than depending on operators remembering this as a separate manual upgrade-handler step. Additionally, document this requirement explicitly in `x/vm/migrations/v2/migrate_params.go`'s package comment, and add an invariant/assertion at the end of migration that verifies `GetEvmCoinInfo(ctx).Decimals` matches the exponent recorded in bank `DenomMetadata` for `Params.EvmDenom`, panicking the upgrade if they diverge rather than silently proceeding.

### Proof of Concept
Not independently reproduced against running code within the tool-call budget available; the trace below is based on static code inspection:
1. Chain X runs pushchain/evm v0.2.x with a 6-decimal bond denom and `ExtendedDenomOptions` configured.
2. Operator upgrades to a version that bumps `x/vm` consensus version to 2, running `v2.MigrateStore` to fix the `Params` wire-format incompatibility [12](#0-11) , but does **not** additionally call `k.InitEvmCoinInfo(ctx)` in the upgrade handler (unlike the documented v0.4→v0.5 example).
3. `SetGlobalConfigVariables` at boot loads the stale/default `EvmCoinInfo` (18 decimals) instead of the chain's true 6-decimal configuration.
4. Every subsequent EVM transaction scaling native coin amounts via `ConvertAmountTo18DecimalsBigInt` under- or over-scales value by 10^12, corrupting balances visible via precompiles/JSON-RPC relative to actual bank-module holdings.

I was unable to fully verify step 2 (whether `RegisterMigration` calls `InitEvmCoinInfo` automatically) within the remaining tool budget, so this finding should be treated as a plausible but not fully confirmed critical analog, and a background Devin session with terminal/build access would be needed to trace `x/vm/module.go`'s migration registration end-to-end and confirm exploitability.

func migrateParams(store storetypes.KVStore) error {
	bz := store.Get(types.KeyPrefixParams)
	if bz == nil {
		// No params stored yet; nothing to migrate.
		return nil
	}

	old, err := parseOldParams(bz)
	if err != nil {
		return err
	}

	// Decode the AccessControl sub-message that was at field 9.
	var ac types.AccessControl
	if len(old.accessControlRaw) > 0 {
		if err := ac.Unmarshal(old.accessControlRaw); err != nil {
			return err
		}
	}

	// Start from DefaultParams so any newly-added fields get sensible values,
	// then overwrite with the values we recovered from the old encoding.
	newParams := types.DefaultParams()
	newParams.EvmDenom = old.evmDenom
	newParams.ExtraEIPs = old.extraEIPs
newParams.EVMChannels = old.evmChannels
	newParams.AccessControl = ac
	newParams.ActiveStaticPrecompiles = old.activeStaticPrecompiles

	newBz, err := newParams.Marshal()
	if err != nil {
		return err
	}

	store.Set(types.KeyPrefixParams, newBz)
	return nil
}

// LoadEvmCoinInfo load EvmCoinInfo from bank denom metadata
func (k Keeper) LoadEvmCoinInfo(ctx sdk.Context) (types.EvmCoinInfo, error) {
	var decimals types.Decimals

	params := k.GetParams(ctx)
	evmDenomMetadata, found := k.bankWrapper.GetDenomMetaData(ctx, params.EvmDenom)
	if !found {
		return types.EvmCoinInfo{}, fmt.Errorf("denom metadata %s could not be found", params.EvmDenom)
	}

	for _, denomUnit := range evmDenomMetadata.DenomUnits {
		if denomUnit.Denom == evmDenomMetadata.Display {
			decimals = types.Decimals(denomUnit.Exponent)
		}
	}

	var extendedDenom string
	if decimals == 18 {
		extendedDenom = params.EvmDenom
	} else {
		if params.ExtendedDenomOptions == nil {
			return types.EvmCoinInfo{}, fmt.Errorf("extended denom options cannot be nil for non-18-decimal chains")
		}
		extendedDenom = params.ExtendedDenomOptions.ExtendedDenom
	}

	return types.EvmCoinInfo{
		Denom:         params.EvmDenom,
		ExtendedDenom: extendedDenom,
		DisplayDenom:  evmDenomMetadata.Display,
		Decimals:      decimals.Uint32(),
	}, nil

// GetEvmCoinInfo returns the EVM Coin Info stored in the module
func (k Keeper) GetEvmCoinInfo(ctx sdk.Context) (coinInfo types.EvmCoinInfo) {
	store := ctx.KVStore(k.storeKey)
	bz := store.Get(types.KeyPrefixEvmCoinInfo)
	if bz == nil {
		return k.defaultEvmCoinInfo
	}
	k.cdc.MustUnmarshal(bz, &coinInfo)
	return
}

func ConvertAmountTo18DecimalsLegacy(amt sdkmath.LegacyDec) sdkmath.LegacyDec {
	evmCoinDecimal := GetEVMCoinDecimals()

	return amt.MulInt(evmCoinDecimal.ConversionFactor())
}

// ConvertAmountTo18DecimalsBigInt convert the given amount into a 18 decimals
// representation.
func ConvertAmountTo18DecimalsBigInt(amt *big.Int) *big.Int {
	evmCoinDecimal := GetEVMCoinDecimals()

	return new(big.Int).Mul(amt, evmCoinDecimal.ConversionFactor().BigInt())
}

// ConvertAmountTo18Decimals256Int convert the given amount into a 18 decimals
// representation.
func ConvertAmountTo18Decimals256Int(amt *uint256.Int) *uint256.Int {
	evmCoinDecimal := GetEVMCoinDecimals()

	return new(uint256.Int).Mul(amt, uint256.NewInt(evmCoinDecimal.ConversionFactor().Uint64()))
}

// ConvertBigIntFrom18DecimalsToLegacyDec converts the given amount into a LegacyDec
// with the corresponding decimals of the EVM denom.
func ConvertBigIntFrom18DecimalsToLegacyDec(amt *big.Int) sdkmath.LegacyDec {
	evmCoinDecimal := GetEVMCoinDecimals()
	decAmt := sdkmath.LegacyNewDecFromBigInt(amt)
	return decAmt.QuoInt(evmCoinDecimal.ConversionFactor())
}

## BankWrapper

This package contains the `BankWrapper`, a wrapper around the Cosmos SDK bank keeper that is designed
to manage the EVM denomination with a custom decimal representation. The primary purpose of the
`BankWrapper` is to handle conversions between Cosmos SDK's default decimal system and the 18-decimal
representation commonly used in EVM-based systems.

## Features

- **Balance Conversion:** Automatically converts balances to 18 decimals, the standard for EVM coins.
- **Send and Receive Coins:** Handles sending coins between accounts and modules, ensuring proper conversion
  to and from the 18-decimal system.
- **Mint and Burn Coins:** Provides methods for minting and burning coins, with conversions applied
  as necessary.

#### UpgradeHandler

As the configs have been moved to state and genesis, you must include an UpgradeHandler if your chain does
not satisfy the following conditions.
1. Your EVM Denom set in the `x/vm` params must have `DenomMetadata` registered for it in `x/bank`.
2. Your EVM Denom must have a display denom associated with it in `DenomMetadata`.
   1. The display denom for the EVM Denom must have an accurate decimal value (i.e. for `uatom`, `atom` must have a decimal value of 6.
3. Your chain is an 18-decimal chain.
4. Call `InitEvmCoinInfo` to initialize EVM coin metadata in the module store.

In your UpgradeHandler:

- **If your chain does not have DenomMetadata set for the EVM Denom, you must include it.**
- **If your chain's EVM denom is *not* 18 decimals, you must add ExtendedDenomOptions to your `x/vm` params.**

Please refer to the [upgrade example](https://github.com/cosmos/evm/blob/0995962c2fd77a7a23e93001d5a531abbb1b61e5/evmd/upgrades.go) for more information.
