## Finding: Cancel/refund path in IntentGatewayV2 uses pre-fee order amounts against post-fee escrow balances, permanently locking user funds

### Title
Order cancellation permanently reverts (locks escrowed funds) due to amount mismatch between escrowed (post-fee) balance and refunded (pre-fee) amount - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` escrows the **protocol-fee-reduced** amount per token in `_orders[commitment][token]`, but every cancellation/refund path (`cancelOrder` same-chain, cross-chain source, and cross-chain destination `RefundEscrow`) builds the `WithdrawalRequest.tokens` array from the **original, pre-fee** `order.inputs` amounts. `withdraw()` subtracts the pre-fee amount from the post-fee escrow balance, which underflows and reverts under Solidity 0.8 checked arithmetic whenever `protocolFeeBps > 0`, permanently locking the user's escrowed tokens with no recovery path.

### Finding Description
In `placeOrder`, when a protocol fee applies, the contract computes a reduced amount per input and stores **that reduced amount** as the escrow balance: [1](#0-0) [2](#0-1) 

However, every cancellation path builds the refund body from `order.inputs` — the full, **pre-fee** amount — instead of the reduced amount actually escrowed:

- Same-chain cancel: [3](#0-2) 
- Cross-chain source-side cancel (GET query context): [4](#0-3) 
- Cross-chain destination-side cancel (`RefundEscrow` dispatch): [5](#0-4) 

All three converge on `withdraw()`, which subtracts the request's `amount` (pre-fee, larger value) from `_orders[commitment][token]` (post-fee, smaller value): [6](#0-5) 

Since `reducedAmount = originalAmount - protocolFee` is always strictly less than `originalAmount` whenever `protocolFeeBps > 0`, the line `_orders[body.commitment][token] -= amount;` always underflows and reverts in this scenario. The corrupted value is the amount encoded into `WithdrawalRequest.tokens[i].amount` — it should be the reduced/escrowed amount, but is instead the original order amount.

### Impact Explanation
Any order placed while a nonzero protocol fee is configured (`_params.protocolFeeBps` or a per-destination override in `_destinationProtocolFees`, both settable via governance `UpdateParams`) cannot be cancelled/refunded through **any** of the three cancel paths: the transaction always reverts. Because `withdraw()` performs the transfer and the balance decrement in the same call with no partial-success path, the user's entire escrowed principal becomes permanently unrecoverable — a direct loss/lock of user funds in bridge custody, which matches the bounty's "stealing or loss of funds" impact category.

### Likelihood Explanation
This is trivially triggerable by any unprivileged user: place an order while `protocolFeeBps > 0` (a normal governance-configured, non-zero protocol setting) and call `cancelOrder()` before or after the deadline — no malicious relayer, prover, or admin is required. The same-chain path reverts within a single transaction, requiring no cross-chain machinery at all.

### Recommendation
In `cancelOrder` (all three branches) and anywhere a `WithdrawalRequest` is constructed for refund purposes, use the same protocol-fee-reduced amounts that were actually escrowed (i.e., recompute or store `reducedInputs` alongside the order, and use it consistently for `WithdrawalRequest.tokens`) instead of the raw `order.inputs`. Ensure the amount used in `withdraw()` always matches what was actually credited to `_orders[commitment][token]` in `placeOrder`.

### Proof of Concept
1. Governance sets `_params.protocolFeeBps = 100` (1%) via `UpdateParams`.
2. User calls `placeOrder` with a single ERC20 input of `amount = 1000`. `reducedInputs[0].amount = 990` is stored in `_orders[commitment][token] = 990`, while `order.inputs[0].amount` remains `1000`.
3. Before the order is filled, the user calls `cancelOrder(order, options)` on the same chain (`orderSource == orderDest`).
4. `cancelOrder` builds `WithdrawalRequest{tokens: order.inputs}` with `amount = 1000` and calls `withdraw(body, true)`.
5. Inside `withdraw`, `_orders[commitment][token] -= amount` computes `990 - 1000`, which underflows and reverts under Solidity ≥0.8 checked arithmetic.
6. The transaction always reverts; the user's 990 escrowed tokens remain locked in the contract with no successful cancellation path available.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
