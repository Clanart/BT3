### Title
`ThresholdKeys::new`/`read` validates shares individually but never binds `secret_share` to `verification_shares[i]`, accepting inconsistent key sets - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::new` performs per-component validation — the number of verification shares equals `n`, participant indexes are `<= n`, interpolation kind is applicable — and `ThresholdKeys::read` canonicalizes every scalar and point via `C::read_F`/`C::read_G`. Yet at no point does either function assert the recomposition equation `C::generator() * secret_share == verification_shares[i]`. Exactly like the cited `KoalaBearRangeCheck` bug, each limb is range-/validity-checked in isolation while the constraint tying the parts to the whole is missing.

### Finding Description
`ThresholdKeys::read` (lib.rs:574-632) reads `t`, `n`, `i`, interpolation coefficients, `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new`. `new` (lib.rs:349-391) only checks:
- `verification_shares.len() == n` (L355)
- every participant index `<= n` (L361-365)
- `Constant` interpolation only when `t == n` (L367-374)

and then computes `group_key` purely from `verification_shares` interpolated over participants `1..=t` (L376-378). The supplied `secret_share` is stored verbatim into `ThresholdCore` (L384) with no proof or check that it corresponds to `verification_shares[i]` or to the interpolation coefficients (for `Interpolation::Constant`, the coefficients `c` are also never checked: no assertion that `sum(c_j * share_j)`-style consistency, nor that `share_i` matches share `i`'s commitment).

The correct "recomposition" pattern exists elsewhere in Serai (e.g., PedPoP share verification via `C::generator() * share == verification_share` in `dkg`), but `ThresholdKeys::new` — the final gate for both internally generated keys and attacker-influenced `ThresholdKeys::read` bytes — omits it.

### Impact Explanation
Any untrusted byte stream reaching `ThresholdKeys::read` (key backups, coordinator-supplied key packages, recovered/shared key material) can encode a `secret_share` that does not match `verification_shares[i]` nor the `group_key`. Consequences:

- **Unspendable funds**: the victim loads keys whose `group_key` is computed from attacker-chosen `verification_shares`. Deposits to that group key (e.g., the bitcoin-serai `Scanner` matching the tweaked group key's script_pubkey) are reported as received, yet the victim's `secret_share` cannot produce a valid share — or worse, the attacker picks verification shares with known discrete logs and controls the group key outright.
- **Silent misbinding for `Constant` interpolation**: the coefficient vector `c` read at lib.rs:607-612 is never bound to `secret_share` or `verification_shares`; arbitrary coefficients shift `interpolation_factor` results, detaching the effective share from any committed polynomial.

This is a concrete "funds reported received that are not spendable" / inconsistent-witness acceptance analog: individual encodings pass all checks while the composed object is invalid.

### Likelihood Explanation
Medium-High. It requires an attacker to influence the serialized `ThresholdKeys` bytes loaded by a victim (untrusted backup, migration, or coordinator-delivered key package). The rules explicitly list `ThresholdKeys::read` as an attacker-reachable surface; no key leakage or malicious validator beyond supplying bytes is needed.

### Recommendation
In `ThresholdKeys::new`, after validating counts and indexes, assert `C::generator() * *secret_share == verification_shares[&params.i()]` (before any interpolation/tweak). For `Interpolation::Constant(c)`, additionally verify the share against the committed coefficients rather than trusting `c` blindly. Return a `DkgError` on mismatch so `ThresholdKeys::read` rejects inconsistent encodings.

### Proof of Concept
Construct a byte stream for `ThresholdKeys::<C>::read` where `verification_shares` are `n` honestly generated points `G * x_j` but `secret_share` is an arbitrary scalar `y != x_i` (or, for `Constant`, supply random coefficients). `read`/`new` succeeds: all encodings are canonical, count and index checks pass. `group_key()` returns a key unrelated to `y`; `view()` produces a `secret_share` whose `s·G` does not equal `verification_share(i)`, so every FROST signature share fails verification — while the attacker (knowing the `x_j` for participants `1..=t`) controls `group_key` and any funds sent to it.
