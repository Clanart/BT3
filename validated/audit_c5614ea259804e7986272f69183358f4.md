### Title
Attacker-controlled length prefix in `SchnorrAggregate::read` enables unbounded per-element deserialization loop that stalls verification (no total bound, only per-item progress) - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` reads a `u32` element count from untrusted bytes, then performs that many `C::read_G` calls in a loop with no cap on the total count and no check that the claimed count is consistent with the data actually present. An unprivileged party who can get serialized aggregate bytes parsed (the aggregate signature is a public, wire-transmitted object) can claim up to ~4.29 billion `R` points and then drip-feed or truncate the input. This is the exact shape of CVE-2021-43173: the work bound/timeout is applied per element (each `read_G` is bounded and may individually succeed or fail), while the total request — driven by an attacker-supplied count — is unbounded, so a stalled or malformed aggregate forces the victim to burn up to billions of point decodings and `Vec` growth before `verify` is ever reached.

### Finding Description
In `crypto/schnorr/src/aggregate.rs` at lines 77–88:

```rust
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    #[allow(non_snake_case)]
    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }

    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

The `len` field is fully attacker-controlled and is trusted to drive a `0 .. u32::MAX` loop. There is:

- No upper bound on the number of elements (contrast with `Commitments::read` in `crypto/dkg/pedpop/src/lib.rs` lines 110–128, which is bounded by `params.t()`, or the `TRANSACTION_SIZE_LIMIT` check in `coordinator/src/tributary/transaction.rs` lines 286–290 — the codebase's own correct pattern).
- No streaming/chunked handling — `Rs` is grown in memory for the full claimed count.
- No total-work bound: each `read_G` is an independent bounded read, exactly like Routinator's per-read-op timeout. A source that yields bytes slowly, or a count of `0xFFFFFFFF` followed by billions of valid point encodings (or one byte at a time), keeps the loop alive and progressing indefinitely.

The same class also appears in the unsigned count field consumed by `verify`/`complete` paths: `verify` (lines 127–146) iterates `keys_and_challenges` and builds a `2n+1`-element multiexp pair list — if `read` is allowed to populate an arbitrarily large `Rs`, the cost is front-loaded into `read` before `verify`'s length-equality check (line 128) can even reject it.

### Impact Explanation
An unprivileged party supplying a serialized `SchnorrAggregate` (or any byte stream reaching `SchnorrAggregate::read`) can cause the decoding side to perform up to ~4.29 billion elliptic-curve point decodings plus `Vec` reallocation, or — if the reader is backed by a stream that yields data gradually — hold the deserializer in the `read_G` loop indefinitely by trickling bytes, exactly mirroring the Routinator drip-feed. The caller is stalled inside `read` before any validation occurs, delaying or preventing the signing/verification pipeline from proceeding and causing the validator to continue serving its prior state (or never produce a signature), matching the CVE's "validation stalls" outcome.

### Likelihood Explanation
Reachability is high in any deployment where aggregate signatures or the messages embedding them are exchanged between mutually distrusting parties — the aggregate signature is inherently a public-input object meant to be deserialized from peer-supplied bytes. The attack requires no key material, no valid signature, and no protocol role: four bytes (`0xFF 0xFF 0xFF 0xFF`) followed by a slow or simply large stream of point encodings. Severity is Medium: it is a liveness/DoS analog of a High-severity CVE, bounded in the worst case by ~4 billion decodings rather than truly infinite, and requires a path where untrusted bytes reach this `read`.

### Recommendation
Bound `SchnorrAggregate::read` the way the rest of the codebase bounds attacker-driven loops:

1. Enforce a maximum element count before the loop (e.g., the maximum aggregate size the protocol permits, analogous to `MAX_KEY_SHARES_PER_SET` checks and `TRANSACTION_SIZE_LIMIT`).
2. Wherever the reader is backed by a fixed buffer, pre-validate that `remaining_len / repr_size >= claimed_count` before iterating — claiming more points than bytes available can be rejected in O(1).
3. Apply a total-time/total-bytes budget at the I/O layer rather than per-`read_exact`, so drip-feeding cannot extend a single message indefinitely.

### Proof of Concept
```rust
use std::io;
use frost::curve::Ristretto;
use schnorr::aggregate::SchnorrAggregate;

// A reader that never ends: yields a valid-encoded Ristretto point forever.
struct DripFeed;
impl io::Read for DripFeed {
    fn read(&mut self, buf: &mut [u8]) -> io::Result<usize> {
        // Feed the canonical generator encoding (or just slow bytes) forever
        let g = <Ristretto as frost::curve::Ciphersuite>::generator().to_bytes();
        let n = buf.len().min(g.as_ref().len());
        buf[..n].copy_from_slice(&g.as_ref()[..n]);
        Ok(n)
    }
}

fn main() {
    // Attacker-controlled prefix: claim u32::MAX R points
    let mut prefix = u32::MAX.to_le_bytes().to_vec();
    let mut chained: &[u8] = &prefix;
    let mut reader = io::Read::chain(&mut chained, DripFeed);
    // This loops ~4.29 billion times; with a slow source it stalls indefinitely.
    let _ = SchnorrAggregate::<Ristretto>::read(&mut reader);
}
```

Root cause confirmed at `crypto/schnorr/src/aggregate.rs:77-88`: the `u32` count read at lines 78–79 directly controls the `read_G` loop at lines 83–85 with no ceiling, no remaining-length check, and no total budget — a direct per-operation-vs-total analog of CVE-2021-43173.
