## Title
Unvalidated `clone_url` from GitHub API PR object passed into `git remote add`/fetch enables git remote-helper protocol injection - (File: app/src/ui/dispatcher/dispatcher.ts)

## Summary
`Dispatcher.openPullRequestFromUrl` takes `pullRequest.head.repo.clone_url` — a field taken verbatim from the GitHub API `IAPIPullRequest` object, which is fully controlled by whoever opened the pull request — and forwards it unvalidated into `AppStore._checkoutPullRequest` → `_findPullRequestBranch`, where it is used as the URL argument to `addRemote()` and subsequently `_fetchRemote()`.

and then into `_findPullRequestBranch`, where the URL is used as-is to add a remote and fetch it: [3](#0-2) [4](#0-3) 

No code in this traced path (`openPullRequestFromUrl`, `_checkoutPullRequest`, `_findPullRequestBranch`, `addRemote`, `_fetchRemote`) performs any scheme allow-listing (e.g. restricting to `https://`/`ssh://`/`git://`) before the value is written to `.git/config` as a remote URL and handed to the git binary. Git's own protocol allow-list (`protocol.allow`) treats URLs configured explicitly as a remote (via `remote add`) as "user"-trusted, not "remote"-untrusted, so protocol restrictions that git applies to redirects/submodule URLs do not block this path — a `clone_url` value such as `ext::sh -c "...")` or `fd::N` would be accepted by `git remote add` and executed on the subsequent `fetch`.

The same unvalidated pattern also exists in the "checkout PR" flow reachable from the pull request list UI: [5](#0-4) 

## Impact Explanation
If confirmed to reach an unfiltered `git remote add`/`git fetch` invocation, an attacker who opens a pull request against any repository the victim has open (or entices the victim to click a GitHub Desktop deep link such as `x-github-client://openRepo/...?pr=NNN`) could set `head.repo.clone_url` to a git remote-helper string. Historic git versions execute such strings as shell commands during `fetch`, giving arbitrary code execution on the victim's machine — no local access, admin rights, or credentials required, only that the victim clicks the link or has Desktop configured to auto-handle it.

## Likelihood Explanation
The `clone_url` field of a PR's head repo is populated from the forked repository's remote URL as reported by the GitHub API. Whether GitHub's API itself constrains this field to `https://github.com/...` values (which would neutralize the issue server-side) is outside of Desktop's source and was not verified here. Within GitHub Desktop's own code, however, no additional validation of the scheme/format of `clone_url` was found anywhere in the traced path before it is used as a remote URL.

## Recommendation
Add scheme/host validation before using any PR-derived `clone_url` (or any externally supplied remote URL) as a git remote: restrict to `https://` and `ssh://` (or the specific allow-listed hosts of the GitHub instance), reject `ext::`, `fd::`, `file://`, and other non-network schemes, and reuse this validator uniformly in `_checkoutPullRequest`/`_findPullRequestBranch`/`addRemote` and any other place that adds remotes from API-sourced data.

## Proof of Concept
1. Construct a mocked `IAPIPullRequest` fixture where `head.repo.clone_url = "ext::sh -c touch$IFS/tmp/pwned"`.
2. Invoke `dispatcher.openPullRequestFromUrl(url, pr)` (or trigger via the `x-github-client://openRepo/...` deep link handler that resolves to `openRepositoryFromUrl`).
3. Observe that `_checkoutPullRequest` → `_findPullRequestBranch` calls `addRemote(repository, forkRemoteName, headCloneUrl)` with the unmodified `ext::` string, and then `_fetchRemote` invokes `git fetch` against that remote, which (on git builds vulnerable to the `ext::`/`fd::` helper class of issues) will execute the embedded command.

**Caveat / what remains unverified:** I was not able to inspect the implementation of `addRemote()` / the lower-level git wrapper (`app/src/lib/git/remote.ts` or equivalent) within the available tool budget to confirm there is no scheme filtering added at that layer, nor could I verify whether the GitHub API itself constrains `clone_url` to `https` values before it ever reaches Desktop. These would need to be checked to fully confirm exploitability end-to-end.
