Based on my investigation, the strongest analog to the reported bug class ("a validation check has an incomplete condition, letting a dangerous value slip through and defeat a prior safety assumption") is a **ref-name/argument-injection gap** in GitHub Desktop's "Open Repository from URL" deep-link handling.

### Title
Deep-link `branch` parameter validation does not reject leading-dash values, enabling git argument injection during checkout - (File: `app/src/lib/sanitize-ref-name.ts`, `app/src/lib/parse-app-url.ts`, `app/src/lib/git/checkout.ts`)

### Summary
`parseAppURL` validates the `branch` query parameter of the `x-github-client://openrepo` protocol handler using `testForInvalidChars`, which only rejects control characters and a fixed set of special glob/ref-format characters. [1](#0-0) [2](#0-1)  The regex never checks whether the value *starts with a dash* (`-`), so a string such as `--upload-pack=/tmp/evil` passes as a "valid" branch name. That value is later placed as the first positional token passed to `git checkout` in `getBranchCheckoutArgs`, with the `--` end-of-options marker appended only *after* the branch name — too late to stop git from treating a leading-dash value as an option rather than a ref. [3](#0-2) 

### Finding Description
The trust boundary is: **attacker-controlled URL → `parseAppURL` → dispatcher → git checkout invocation**. An attacker can craft a link like `x-github-client://openrepo/owner/repo?branch=--upload-pack=/tmp/evil.sh` (a link the victim clicks, satisfying the "link the user clicks" attacker model). `parseAppURL` requires `testForInvalidChars(branch)` to be false to accept it: [4](#0-3)  that regex blocks control chars and `~^:?*[\|"<>`, `@{`, consecutive dots, leading/trailing dot, `.lock` suffix, and trailing slash — but not a leading `-`. [5](#0-4) 

The action is routed to `openRepositoryFromUrl` → `openBranchNameFromUrl` → `checkoutLocalBranch`, ultimately reaching `checkoutBranch` in `app/src/lib/git/checkout.ts`. The final argv is built as `['checkout', branch.name, '--']` (or with `-b nameWithoutRemote` inserted). [6](#0-5)  Since `branch.name` is positioned immediately after `checkout` and the `--` separator is only appended at the *end* of the args array, git's own argv parser sees the dash-prefixed value before it ever reaches `--`, so it is parsed as an option/flag rather than a ref name. This is the same class of bug as the Solidity report: a validation gate ("no dangerous chars") passes on a value that still satisfies a *different*, unguarded condition (leading `-`), silently bypassing the invariant the downstream code relies on (that everything before `--` is a plain ref).

### Impact Explanation
If reachable end-to-end (see Likelihood), this allows an attacker who only controls a URL the victim clicks to inject arbitrary `git checkout`/`git branch` options, potentially including options like `--upload-pack=<path>` or other flags accepted by the git subcommand being invoked. Depending on which flags are accepted by the specific git subcommand context, this can range from unexpected command behavior to more severe consequences (e.g., invoking an attacker-specified executable via option values that take a path/program argument). At minimum this is an integrity violation of the checkout/open-repository flow: input that should be a pure ref name is treated as executable git configuration.

### Likelihood Explanation
Moderate-to-uncertain. The `testForInvalidChars` gap is concretely demonstrated in the code and is trivially triggerable by any external actor who can get a victim to click a `x-github-client://openrepo?...&branch=...` link — no local access, credentials, or privileges are required. [7](#0-6)  However, I was not able to fully trace `checkoutLocalBranch` in `app/src/ui/dispatcher/dispatcher.ts` within the available tool budget to confirm whether it (a) only checks out a branch that must already exist as a local/remote-tracking ref (in which case the attacker-controlled string would need to already match a real, git-created ref name, largely neutralizing the injection because git itself would have already rejected a dash-prefixed ref on creation), or (b) creates a new local branch directly from the untrusted string via `git checkout -b <name>`, in which case the injection is directly reachable. This distinction materially changes exploitability and should be verified by a full trace of `checkoutLocalBranch` before treating this as an immediately exploitable finding.

### Recommendation
- In `sanitize-ref-name.ts`, extend `invalidCharacterRegex` (or add a dedicated check) to reject ref names beginning with `-`, consistent with git's own `check-ref-format` guidance and defense-in-depth practice for any argv token derived from untrusted input.
- In `checkout.ts`, place the `--` end-of-options marker immediately after the subcommand and before the untrusted branch name (i.e., `['checkout', '--', branch.name, ...]` restructured appropriately for the `-b` case), so that git parses the name as a positional argument even if a dash slips through validation.
- Apply the same fix pattern anywhere else a `Branch`/ref name sourced from `parseAppURL` or other external input is interpolated into git argv without a preceding `--`.

### Proof of Concept
1. Register/observe that GitHub Desktop handles the `x-github-client://` protocol (`app/src/main-process/main.ts`). [8](#0-7) 
2. Craft a link: `x-github-client://openrepo/owner/repo?branch=--upload-pack=/tmp/evil.sh`.
3. `parseAppURL` accepts it because `pr` is absent and `testForInvalidChars('--upload-pack=/tmp/evil.sh')` returns `false` (no blocked characters). [4](#0-3) 
4. Victim clicks the link; Desktop routes to `openBranchNameFromUrl` → `checkoutLocalBranch` → `checkoutBranch`, which builds `['checkout', '--upload-pack=/tmp/evil.sh', '--']` (or similar) and executes it via `git(...)`. [9](#0-8) 
5. Verify with `strace`/argv logging that the dash-prefixed string is parsed by git as an option rather than a ref.

**Caveat**: This PoC assumes `checkoutLocalBranch` passes the raw URL-supplied string through to a real checkout invocation without first requiring the ref to pre-exist as a git-validated ref. That step needs confirmation in `app/src/ui/dispatcher/dispatcher.ts` (not fully retrievable within this session) before treating this as a confirmed, fully reachable vulnerability rather than a validation-gap-with-uncertain-reachability finding.

export function parseAppURL(url: string): URLActionType {
  const parsedURL = URL.parse(url, true)
  const hostname = parsedURL.hostname
  const unknown: IUnknownAction = { name: 'unknown', url }
  if (!hostname) {
    return unknown
  }

  const query = parsedURL.query

  const actionName = hostname.toLowerCase()
  if (actionName === 'oauth') {
    const code = getQueryStringValue(query, 'code')
    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }
  }

  // we require something resembling a URL first
  // - bail out if it's not defined
  // - bail out if you only have `/`
  const pathName = parsedURL.pathname
  if (!pathName || pathName.length <= 1) {
    return unknown
  }

  // Trim the trailing / from the URL
  const parsedPath = pathName.substring(1)

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
  }

  return unknown
}

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
