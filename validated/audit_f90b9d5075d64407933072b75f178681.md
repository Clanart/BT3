## Analysis

The bug-class core invariant from the report: **a share/ratio computed via integer division can silently round to zero for a legitimate contributor, while the last party to complete the pool/order collects the full remaining balance — including the portion that should have gone to the rounded-down contributor.**

The local analog lives in the Intent Gateway's same-chain **partial-fill** path.

### Title
Same-chain partial-fill escrow release rounds to zero and the final filler drains prior fillers' unreleased escrow - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes the escrow released to a partial filler as `(order.inputs[i].amount * fillAmount) / totalRequired`. When this truncates to `0`, `_withdraw` skips the transfer *and skips decrementing* `_orders[commitment][token]` (it has an explicit `if (amount == 0) continue;` guard). The filler's contribution to `_partialFills` is still recorded, so the order still moves toward completion, but the corresponding escrow is never released to that filler. When the order is finally completed, the completing filler is paid `escrowedAmount = _orders[commitment][token]` — the entire *undiminished* remaining escrow — rather than their proportional share. This lets the order creator (or a colluding filler) design an order where intermediate partial fillers are paid `0` escrow for real output tokens delivered, while the filler who lands the completing fill sweeps everything, including the value that should have gone to the earlier fillers.

### Finding Description [1](#0-0) 
```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```
For any non-final fill, `escrowedAmount` truncates to `0` whenever `order.inputs[i].amount * fillAmount < totalRequired`. This value flows into `_withdraw`: [2](#0-1) 
```solidity
for (uint256 i; i < len; i++) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (amount == 0) continue;

    uint256 escrowed = _orders[body.commitment][token];
    if (escrowed == 0) revert UnknownOrder();

    _orders[body.commitment][token] = escrowed - amount;
```
The `if (amount == 0) continue;` guard means a rounded-to-zero fill leaves `_orders[commitment][token]` completely untouched — none of the escrow is consumed for that fill, even though the filler already sent real output tokens to the beneficiary and `_partialFills[commitment][outputToken]` was permanently incremented by `fillAmount`: [3](#0-2) 
```solidity
uint256 amountFilled = alreadyFilled + fillAmount;
_partialFills[commitment][outputToken] = amountFilled;
uint256 beneficiaryTotal = fillAmount + beneficiaryShare;
```
So the order's "progress" advances irreversibly while the matching escrow never leaves `_orders`. Whoever lands the fill that pushes `amountFilled == totalRequired` receives the *entire* leftover `_orders[commitment][token]` balance — which now includes every prior filler's un-released share — not just their own proportional slice.

This mirrors the reported bug exactly: the order creator plays the role of the "pool," `inputs.amount` vs `totalRequired` plays the role of the manipulable share ratio, intermediate fillers play the role of the second depositor whose minted shares round to zero, and the completing filler plays the role of the attacker who drains the excess.

### Impact Explanation
An unprivileged order creator (`placeOrder`) can pick `inputs.amount` small relative to `totalRequired` such that any partial `fillAmount` below the full amount truncates the proportional release to `0`. A real solver who partially fills such an order transfers genuine output tokens to the beneficiary via `IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` (or native ETH) but receives `0` escrowed input tokens back — an unauthorized transfer/loss of the filler's funds with no compensating credit. The filler who eventually completes the order (who may be the order creator's own second address, or complicit with them) is paid the full, unreduced `_orders` balance, i.e., strictly more than their fair share — a wrong-amount/wrong-beneficiary fund transfer. This satisfies the bounty's "stealing or loss of funds," "transaction manipulation," and "logic attack" categories, reachable purely through the public `placeOrder`/`fillOrder` entrypoints with no relayer, prover, or governance involvement.

### Likelihood Explanation
The exploit needs no cross-chain proof forgery, no compromised keys, and no privileged role — only an order with a skewed `inputs.amount`/`totalRequired` ratio and at least one partial fill below the full amount. Same-chain intents explicitly support "any portion" partial fills (`docs/content/developers/evm/intent-gateway/overview.mdx`: "solvers can fill any portion of the output"), so the vulnerable code path is reached by design, not by a corner case. The existing test suite already documents rounding dust *within a single completed order* (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol` "ROUNDING DUST IN PARTIAL FILLS (Finding #4)") but that fix only guarantees the *final* filler recovers the dust — it does not check that a fill in between can be diluted to `0` while still advancing `_partialFills`, which is the actual exploitable gap.

### Recommendation
Track escrow release by the cumulative proportion actually owed at each fill (e.g., `owed = order.inputs[i].amount * amountFilled / totalRequired; escrowedAmount = owed - alreadyReleased[commitment][token]`) rather than releasing a fresh independent ratio per fill, so rounding dust accrues to the *next* filler proportionally rather than being silently withheld until the last filler sweeps the whole remaining balance. Alternatively, reject fills whose computed `escrowedAmount` would be `0` for a non-final, non-trivial `fillAmount`, forcing the filler either to complete the order or to fill a large-enough chunk that a nonzero share is guaranteed.

### Proof of Concept
1. Attacker calls `placeOrder` escrowing `inputs[0].amount = 100` units of USDC, with `output.assets[0].amount = totalRequired = 1_000_000` units of DAI (an exaggerated but valid ratio the contract does not sanity-check).
2. Solver A (victim) calls `fillOrder` with `solverAmount = 999_999` (99.9999% of the requested output), providing ~999,999 DAI-equivalent value to the beneficiary.
   - `fillAmount = 999_999`, `amountFilled = 999_999 != totalRequired`.
   - `escrowedAmount = (100 * 999_999) / 1_000_000 = 99` (rounds down from 99.9999) — actually pick numbers so it rounds to `0`, e.g. `inputs.amount = 1`, `totalRequired = 1_000_000`, `solverAmount = 999_999`: `escrowedAmount = (1 * 999_999) / 1_000_000 = 0`.
   - `_withdraw` is called with `amount = 0` for that token → `continue`, so `_orders[commitment][token]` remains `1` (untouched), and Solver A gets zero USDC despite delivering nearly the full requested DAI amount.
3. Attacker (or a colluding second address) calls `fillOrder` with `solverAmount = 1` to complete the remaining `1` unit.
   - `amountFilled = 1_000_000 == totalRequired` → `escrowedAmount = _orders[commitment][token] = 1` (the entire un-decremented escrow).
   - Attacker/completer receives the full `1` unit of escrow for contributing only the last `1` unit of output, while Solver A — who contributed 999,999 units of real value — received nothing.

This demonstrates the fund-loss primitive: escrow that should have been split proportionally across fillers is instead captured entirely by whichever filler happens to complete the order, at the direct expense of prior partial fillers.
