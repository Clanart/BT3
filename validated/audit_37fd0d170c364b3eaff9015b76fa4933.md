### Title
`SchnorrAggregate::verify` accepts a signature from an empty signer set, allowing unauthenticated forgeries - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The half-aggregate Schnorr verifier in `crypto/schnorr` reduces to a single `-s·G` statement when zero signatures are aggregated. An aggregate with `Rs = []` and `s = 0` therefore verifies as valid for an empty `keys_and_challenges` list — i.e., a "signature" produced by nobody is accepted. This is the direct analog of the CVE-2022-0668 authentication-bypass class: a verification routine that can be satisfied without any legitimate signer.

### Finding Description
`SchnorrAggregate::verify` checks only that `self.Rs.len() == keys_and_challenges.len()` [1](#0-0) , then builds the multiexp pairs `z·R_i + z·c_i·A_i` per signer and finally pushes `(-s, G)` [2](#0-1) . With an empty signer list, `pairs` is exactly `[(-s, generator)]`, and `multiexp_vartime` on that single pair is identity iff `s == 0` [3](#0-2) . So the byte encoding `[0x00,0x00,0x00,0x00] || 0x00…00` (len = 0, s = 0) deserializes via `SchnorrAggregate::read` [4](#0-3)  and verifies against an empty signer set.

The honest aggregation path deliberately refuses to produce this: `SchnorrAggregator::complete` returns `None` when `sigs` is empty [5](#0-4) . The verifier accepting a value the prover-side API refuses to construct is an asymmetric acceptance hole — the same shape as the Artifactory bug, where a crafted request satisfied an auth check that was supposed to require valid credentials.

The reachable public-input path is concrete: `Validators::verify_aggregate` reads attacker-controlled bytes with `SchnorrAggregate::read`, checks `signers.len() == aggregate.Rs().len()`, then calls `aggregate.verify` [6](#0-5) . Any caller that passes an empty `signers`/`keys_and_challenges` (e.g., an edge case where a commit or key list resolves to nobody) accepts a forgery with `s = 0`.

### Impact Explanation
Any protocol layer relying on `SchnorrAggregate::verify` as an authentication gate ("these validators signed this message") can be bypassed by an unauthenticated party when the expected signer set is empty or collapsible to empty: the attacker supplies a zero-length aggregate with `s = 0` and the verifier returns `true`. This yields acceptance of unsigned data — e.g., a Tendermint-style commit or an authorization message — with no key material at all, which is precisely privilege escalation via verification bypass.

### Likelihood Explanation
Exploitation requires a code path that invokes `verify` with an empty key list on attacker-controlled bytes. That is a plausible degenerate case (empty validator subset, filtered-out signers, or a caller that computes `signers` from the aggregate itself), and the cryptographic primitive itself is unconditionally wrong for this input. Because the bug lives in the library verifier rather than a single call site, every consumer inherits it.

### Recommendation
Reject empty aggregates in `SchnorrAggregate::verify` (return `false` when `self.Rs.is_empty()`), matching the `None` returned by `SchnorrAggregator::complete`. Consider also rejecting `Rs.is_empty()` at `read` time or documenting/enforcing a non-empty invariant. Callers such as `Validators::verify_aggregate` should additionally require `signers.len() >= 1` before calling `verify`.

### Proof of Concept
```rust
// crypto/schnorr — no key material needed
let mut buf: Vec<u8> = vec![0, 0, 0, 0];            // u32 len = 0 -> Rs = []
buf.extend(C::F::ZERO.to_repr().as_ref());           // s = 0
let agg = SchnorrAggregate::<C>::read(&mut buf.as_slice()).unwrap();
assert!(agg.verify(b"any dst", &[]));                // verifies with zero signers
```
Root cause: with `keys_and_challenges == []`, the statement list is just `[(-s, G)]`, and `multiexp_vartime` returns `G::identity()` when `s == 0`, so `is_identity()` is true [7](#0-6) .
