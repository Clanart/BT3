### Title
Unhandled uint64 underflow in `combine_coins` causes transaction-processing crash when fee exceeds selected coin amount - ([File: chia/wallet/fungibility_manager.py])

### Summary
`FungibilityManager.combine_coins` computes the primary output amount for a coin-combining transaction by subtracting the fee from the total combined coin amount without first checking that the amount is sufficient to cover the fee. When the fee equals or exceeds the primary output amount, the `uint64()` cast raises an unhandled `ValueError`, crashing the wallet RPC call instead of returning a clean, expected error. This mirrors the reported analog-report bug class: an arithmetic operation that can underflow and should be checked/clamped before being cast into an unsigned type, rather than allowed to throw uncontrolled.

### Finding Description
In `combine_coins`, after selecting coins to combine, the code computes: [1](#0-0) 

```
primary_output_amount = (
    uint64(sum(c.amount for c in coins)) if target_coin_amount is None else target_coin_amount
)
if isinstance(wallet, Wallet):
    primary_output_amount = uint64(primary_output_amount - fee)
```

There is no check anywhere in the function that `primary_output_amount >= fee` before this subtraction. `fee` and `target_coin_amount` (or the sum of user-specified/selected coin amounts) are both caller-controlled inputs to this wallet operation (invoked, e.g., via the wallet RPC `combine_coins` endpoint reachable by any local wallet-owning RPC caller). If a caller requests to combine coins with `target_coin_amount` smaller than `fee` (or supplies `target_coin_ids` whose summed amount is smaller than `fee`), `primary_output_amount - fee` becomes negative, and `uint64(negative_value)` raises `ValueError: ... does not fit into uint64`, exactly as demonstrated by the project's own test pattern for this class of bug (`test_compute_block_fee` in `chia/_tests/core/consensus/test_block_creation.py`, which documents that `uint64()` on a negative value raises `ValueError: does not fit into uint64`).

Unlike `chia.wallet.wallet._generate_unsigned_transaction`, which explicitly validates `total_amount > total_balance` before constructing amounts and asserts `change >= 0`, `combine_coins` performs no equivalent bounds check prior to the unsigned cast, exposing the underflow directly to the caller as an unhandled exception rather than a controlled `ValueError` with an informative message (as is done elsewhere in the same file, e.g., the `len(coins) > number_of_coins` check).

### Impact Explanation
This causes an unhandled/uncontrolled exception in wallet transaction-processing logic when the fee exceeds the coin-combination target amount. Depending on caller behavior and how the wallet RPC layer surfaces such exceptions, this can halt in-flight coin combination logic with an unclean crash instead of a graceful, informative rejection — a spend-triggered transaction-processing halt affecting the wallet's local RPC path. It is a local, single-caller-triggered denial/crash rather than consensus-breaking or fund-stealing, limiting severity, but it represents a real robustness bug matching the reported bug class exactly (missing bounds check before subtraction/cast).

### Likelihood Explanation
Any local wallet RPC caller (an unprivileged local caller of the wallet's `combine_coins` functionality) can trigger this simply by specifying a `fee` value greater than or equal to the amount being combined (via `target_coin_amount` or via selecting low-value `target_coin_ids`). No special privileges, network position, or malicious peer/farmer/node access is required — this is a straightforward parameter-driven crash.

### Recommendation
Add an explicit check before the subtraction, mirroring the pattern used elsewhere in the codebase (e.g., in `Wallet._generate_unsigned_transaction`) and consistent with the referenced report's recommended fix pattern:

```python
if isinstance(wallet, Wallet):
    if primary_output_amount < fee:
        raise ValueError(
            f"Combined coin amount {primary_output_amount} is less than the fee {fee}"
        )
    primary_output_amount = uint64(primary_output_amount - fee)
```

This raises a clear, controlled `ValueError` instead of letting the uncaught underflow from `uint64()` propagate.

### Proof of Concept
1. Call the wallet's coin-combine functionality (`FungibilityManager.combine_coins`) as a local wallet RPC caller with `wallet` as a standard `Wallet` instance, `target_coin_amount` set to a small value (e.g., `1000`), and `fee` set to a larger value (e.g., `10000`).
2. `primary_output_amount` is set to `1000` (from `target_coin_amount`).
3. Execution reaches: [2](#0-1) , computing `uint64(1000 - 10000)` → `uint64(-9000)`.
4. This raises `ValueError: ... does not fit into uint64`, an unhandled exception surfacing from the wallet's transaction-processing path instead of a controlled rejection.
