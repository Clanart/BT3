### Title
Unchecked `u32` subtraction in header-chain difficulty retarget lets an out-of-order timestamp wrap the epoch timespan, corrupting the canonical total-work computation used to authorize operator reimbursement - (File: circuits-lib/src/header_chain/mod.rs)

### Summary
`calculate_new_difficulty` computes the elapsed epoch time as plain, unchecked `last_timestamp - epoch_start_time` on `u32` values. [1](#0-0) 
Unlike other arithmetic on untrusted chain data in this codebase, which consistently uses `checked_sub`/`saturating_sub`/`wrapping_sub` (e.g. `Operator::is_profitable`, the bitcoin syncer height math), this subtraction has no underflow guard. [2](#0-1) [3](#0-2) 

### Finding Description
`apply_block_headers` is the state-transition function of the Header Chain Circuit (HCC). For every block it validates PoW and the difficulty `bits` field, but timestamp validity is only checked against the *median of the previous 11 timestamps* (`validate_timestamp`), not against the epoch-start timestamp that was recorded up to ~2016 blocks earlier. [4](#0-3) 
This is the same bug class as the cited firedancer report: a value derived from a peer/attacker-influenced field (`block_header.time`) is subtracted from a reference value without a bounds check, and the local monotonicity rule (median-of-11) does not guarantee `last_timestamp >= epoch_start_time` over a much longer window (2016 blocks). At the epoch boundary, `epoch_start_time` and the final block's `time` are fed straight into `calculate_new_difficulty`: [5](#0-4) 
If `last_timestamp < epoch_start_time`, `last_timestamp - epoch_start_time` wraps to a value near `u32::MAX`. The subsequent clamp (`> EXPECTED_EPOCH_TIMESPAN*4` ⇒ clamp to `EXPECTED_EPOCH_TIMESPAN*4`) forces the *maximum allowed* 4x difficulty easing regardless of the true (near-zero or negative) elapsed time, instead of the correct minimum-clamp (4x tightening) that a legitimate long/duplicated-timestamp epoch would require: [6](#0-5) 
This flips the direction of the retarget for that epoch. The resulting `ChainState.total_work` and `current_target_bits` are exactly the values the rest of the protocol trusts as ground truth for "the canonical Bitcoin chain": the Bridge Circuit compares an operator's `hcp.chain_state.total_work` against watchtowers' proven work to decide whose chain is canonical, and uses `hcp.chain_state.block_hashes_mmr` to verify SPV inclusion of the payout transaction. [7](#0-6) 
Because HCC output is itself a recursively-verified zkVM proof (`guest.verify`) that the Bridge Circuit trusts, corrupting the difficulty/target progression inside the HCC directly corrupts what block hash / total-work claim can be "proved" by the Bridge Circuit — i.e. it breaks the binding between the block hash actually committed on Bitcoin and the block hash that is provable/acceptable inside the circuit.

### Impact Explanation
The Bridge Circuit's core custody guarantee is: an operator may only be reimbursed if their claimed chain (via HCP `total_work`) is heavier than any watchtower's challenge, and the payout transaction is included in that same claimed chain via SPV/MMR. A corrupted difficulty ratchet lets a chain of headers with an adversarial timestamp ordering (still individually PoW-valid and passing the local median-of-11 check) inherit an incorrect, maximally-eased target for the following 2016 blocks instead of the correct target. This shifts the total-work/target computation that the operator-vs-watchtower and SPV/MMR canonical-chain checks are built on, which maps to the "block hash committed vs. block hash proved" and "false circuit claim proved" custody bindings called out in scope, with the ultimate exposure being an operator being reimbursed against a chain state that does not reflect the real Bitcoin chain.

### Likelihood Explanation
Triggering the bug requires producing ~2016 headers with valid PoW at the correct running difficulty where the final block's timestamp is less than the epoch's first block's timestamp — feasible because Bitcoin's own timestamp rule (median-time-past) only constrains against the last 11 blocks, not the whole 2016-block epoch, so a legitimate/adversarial timestamp pattern satisfying local validity while decreasing overall across the epoch is not excluded by any check in `apply_block_headers`. No privileged role (verifier/operator/watchtower key, majority hashrate, or node compromise) is required beyond what any header-chain prover already needs — the header sequence itself is the "unprivileged" input to this circuit.

### Recommendation
Replace the raw subtraction in `calculate_new_difficulty` with `last_timestamp.checked_sub(epoch_start_time)`, and if it is `None` (i.e., `last_timestamp < epoch_start_time`), treat the actual timespan as the minimum allowed (`EXPECTED_EPOCH_TIMESPAN / 4`) rather than silently wrapping — mirroring the `checked_sub` patterns already used elsewhere in this codebase for untrusted subtraction (`core/src/operator.rs`, `core/src/database/bitcoin_syncer.rs`).

### Proof of Concept
1. Build a sequence of 2016 `CircuitBlockHeader`s that satisfy PoW at the epoch's `current_target_bits` and each satisfy `validate_timestamp` (strictly greater than the median of the previous 11), but whose overall timestamp trend decreases so that the header at position `BLOCKS_PER_EPOCH - 1` has `time < epoch_start_time` (the `time` recorded when `block_height % BLOCKS_PER_EPOCH == 0`).
2. Feed this sequence through `ChainState::apply_block_headers`; at line 500 `calculate_new_difficulty(epoch_start_time, block_header.time, current_target_bits)` computes `last_timestamp - epoch_start_time`, which underflows to a value near `u32::MAX`. [5](#0-4) 
3. Inside `calculate_new_difficulty`, the wrapped huge value exceeds `EXPECTED_EPOCH_TIMESPAN * 4` and gets clamped to that maximum, forcing the maximal difficulty-easing branch instead of the correct minimal-timespan (difficulty-tightening) branch that the true near-zero/negative elapsed time warrants. [8](#0-7) 
4. `current_target_bits` for the next epoch is now wrong, silently corrupting `ChainState.total_work`/`current_target_bits` that downstream `bridge_circuit` trusts unconditionally via `guest.verify(input.hcp.method_id, &input.hcp)` for the total-work and SPV/MMR canonical-chain checks. [9](#0-8)

fn calculate_new_difficulty(
    epoch_start_time: u32,
    last_timestamp: u32,
    current_target: u32,
) -> [u8; 32] {
    let mut actual_timespan = last_timestamp - epoch_start_time;
    if actual_timespan < EXPECTED_EPOCH_TIMESPAN / 4 {
        actual_timespan = EXPECTED_EPOCH_TIMESPAN / 4;
    } else if actual_timespan > EXPECTED_EPOCH_TIMESPAN * 4 {
        actual_timespan = EXPECTED_EPOCH_TIMESPAN * 4;
    }

    let current_target_bytes = bits_to_target(current_target);
    let mut new_target = U256::from_be_bytes(current_target_bytes)
        .wrapping_mul(&U256::from(actual_timespan))
        .wrapping_div(&U256::from(EXPECTED_EPOCH_TIMESPAN));

    if new_target > NETWORK_CONSTANTS.max_target {
        new_target = NETWORK_CONSTANTS.max_target;
    }
    new_target.to_be_bytes()
