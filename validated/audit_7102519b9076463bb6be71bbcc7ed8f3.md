### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates `block.txdata` including `txdata[0]` (the coinbase transaction) and emits a `ReceivedOutput` for any coinbase output paying to a registered Serai script. Coinbase outputs are consensus-unspendable for 100 blocks, yet they enter the wallet's input set identically to mature outputs. This mirrors the `FeeWrapper` bug class: value is returned to a component that is not in a position to actually accept/use it, breaking the downstream operation. Here, the scanner "receives" funds that cannot be spent, and `SignableTransaction::new` will happily consume them as inputs, producing a transaction that fails BIP-30/COINBASE_MATURITY consensus validation.

### Finding Description
`scan_block` calls `scan_transaction` on every transaction in the block, including the coinbase:

```rust
// networks/bitcoin/src/wallet/mod.rs:221-227
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

The doc comment acknowledges the issue ("This will also scan the coinbase transaction which is bound by maturity") but provides no enforcement — no maturity timestamp, no coinbase flag on `ReceivedOutput`, no height tracking in `Scanner`. `ReceivedOutput` (mod.rs:90-97) carries only `offset`, `output`, `outpoint`, so consumers cannot distinguish an immature coinbase output from a normal one.

`SignableTransaction::new` (send.rs:150) sums `input.output.value` for all inputs (send.rs:175), builds `TxIn`s from their outpoints (send.rs:177-185), and produces a transaction committing those prevouts via `Prevouts`/sighash at signing time (send.rs:273-285 `multisig`). A transaction spending a coinbase output younger than 100 blocks is invalid by consensus; `send_raw_transaction` / mempool acceptance will reject it, and any FROST signing ceremony built around it is wasted.

An unprivileged external party can trigger this: any miner (or anyone constructing a block template they get mined) can set a coinbase output paying to one of Serai's published/registered P2TR scripts. Deposits to the vault script are attacker-initiable by design, so the script is public. Once scanned, the immature output is indistinguishable and will be scheduled into a spend plan.

### Impact Explanation
A reported `ReceivedOutput` that cannot actually be spent causes `SignableTransaction::new` + `TransactionMachine` to produce and sign a transaction that is consensus-invalid (coinbase maturity violation). Effects: wasted signing sessions, a permanently-rejected completion transaction, and — because the immature output is lumped into `input_sat` — potential over-estimation of spendable balance that either burns the "balance" as fee or stalls payment batches until maturity. Severity: Medium — funds are not stolen and the output becomes spendable after 100 blocks, but every spend plan incorporating it fails in the interim, and the invalid-input selection is repeatable every block by fresh coinbases paying to the vault script.

### Likelihood Explanation
Requires a mined block whose coinbase pays to a registered Serai script. This does not require Serai cooperation or validator compromise; any party capable of mining (or paying a miner/pool, e.g. via publicly-sold block-space services) can set arbitrary coinbase outputs. The trigger condition is entirely external-input-driven, matching the report's "target contract refunds ETH the wrapper can't accept" shape: the chain "refunds/deposits" value to a receive path that mishandles it.

### Recommendation
Track maturity. Either:
- Have `scan_block` skip `block.txdata[0]` (documented as an option in the comment at mod.rs:218-220) and require callers to scan coinbases separately after maturity, or
- Record the block height in `Scanner`/`ReceivedOutput` and filter inputs in `SignableTransaction::new` whose outpoint is a coinbase younger than 100 blocks.

A `is_coinbase`/birth-height field on `ReceivedOutput` is the robust fix since `read`/`write` (mod.rs:122-141) would need to round-trip it.

### Proof of Concept
```rust
// Construct a block whose coinbase pays to the vault script
let vault_script = p2tr_script_buf(vault_key).unwrap();
scanner.register_offset(offset); // or base script via Scanner::new

let coinbase = Transaction {
  // coinbase input: prevout = OutPoint::null(), script_sig = height
  input: vec![TxIn { previous_output: OutPoint::null(), /* coinbase sig */ .. }],
  output: vec![TxOut { value: Amount::from_sat(5_000_000_000), script_pubkey: vault_script }],
  ..
};
let block = Block { header: .., txdata: vec![coinbase, other_txs..] };

let outputs = scanner.scan_block(&block);
// outputs[0] is a ReceivedOutput for the coinbase output — immature.
let stx = SignableTransaction::new(vec![outputs[0].clone()], &payments, change, None, fee).unwrap();
// stx spends the coinbase outpoint; signing succeeds, but the resulting TX is
// consensus-invalid until 100 blocks elapse (rejected by mempool: "bad-txns-premature-spend-of-coinbase").
```
The gap is that `Scanner` performs no coinbase-vs-normal discrimination in `scan_block` (mod.rs:221-227) while `SignableTransaction::new` trusts every `ReceivedOutput` as a mature input (send.rs:150-256).
