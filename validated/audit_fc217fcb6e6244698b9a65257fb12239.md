### Title
`WombatPoolHelperV2.depositFor` hardcodes `_minimumLiquidity` to zero, removing slippage/sandwich protection on user deposits - (File: `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2.depositFor()` is a public, unprivileged entry point that transfers the caller's deposit token and forwards it to Wombat's underlying pool through `_deposit`, but it always passes `0` as `_minimumLiquidity` instead of accepting a user-supplied slippage bound, unlike the sibling `deposit()` function in the same contract.

### Finding Description
`deposit(uint256 _amount, uint256 _minimumLiquidity)` lets the caller specify their own minimum-LP-received slippage guard and forwards it unchanged to `WombatStaking.deposit`, which in turn forwards it as the real AMM slippage parameter to `IWombatPool.deposit(...)`: [1](#0-0) [2](#0-1) 

However, `depositFor(uint256 _amount, address _for)` — meant to let anyone deposit on behalf of another address — bypasses this protection entirely by hardcoding the slippage parameter to `0` when calling `_deposit`: [3](#0-2) 

That `0` is then propagated unchanged as `_minimumLiquidity` all the way to the underlying Wombat pool's `deposit` call inside `WombatStaking.deposit`: [4](#0-3) 

This is functionally the same bug class as the referenced report: a user-callable function silently zeroes out a slippage-protection parameter that the AMM relies on to guard depositors against price/coverage-ratio manipulation, so anyone calling `depositFor` — which has no reason to differ from `deposit` other than allowing the caller to specify a different recipient — is left with zero slippage protection regardless of what a rational value would have been.

### Impact Explanation
Because `_minimumLiquidity` is forced to `0`, an attacker can sandwich a `depositFor` call: front-run it with a trade that skews the Wombat pool's coverage ratio/exchange rate unfavorably for the depositor, let the victim's deposit mint far fewer LP (staking) tokens than fair value, then back-run to restore the price and capture the difference. Since `WombatPoolHelperV2` mints/stakes exactly `afterDeposit - beforeDeposit` staking tokens for the `_for` address, the victim directly and permanently loses the value skimmed by the attacker — this is a direct theft-of-user-funds path, not merely un-favorable pricing recoverable elsewhere.

### Likelihood Explanation
`depositFor` is a normal external function with no access control beyond `msg.sender` providing the funds; any wallet can call it for themselves or on behalf of another address without any special privilege. Since Wombat pools are constant-sum/coverage-ratio based AMMs whose exchange rate is directly influenced by trade flow, sandwiching a zero-slippage deposit is a standard, low-cost MEV strategy, making exploitation straightforward and repeatable against any user of this pathway.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (as already done for `deposit`) and forward the caller-supplied value instead of the hardcoded `0`, so depositors retain the same slippage protection regardless of which entry function they use.

### Proof of Concept
1. Attacker monitors the mempool for a pending `WombatPoolHelperV2.depositFor(amount, victim)` transaction.
2. Attacker front-runs with a large swap against the same Wombat pool to worsen the pool's coverage ratio for the deposit token.
3. Victim's `depositFor` executes with `_minimumLiquidity = 0`, so `IWombatPool.deposit` succeeds despite minting a much smaller amount of LP than fair value, per `WombatStaking.deposit` at [5](#0-4) .
4. Attacker back-runs, restoring the pool ratio and extracting the value difference, while the victim's minted/staked balance permanently reflects the sandwiched (reduced) LP amount.
