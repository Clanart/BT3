## Analysis

The Radiant bug class is: **a helper contract expects tokens to be pre-deposited by a trusted party, then exposes an unrestricted "second step" function that moves whatever balance is currently sitting in the contract to the caller.** The direct analog in Hyperbridge is `CallDispatcher.sol`. [1](#0-0) 

Unlike essentially every other privileged app entry point in this codebase — `HostManager.setIsmpHost`/`onAccept` (`restrict(_params.admin)`/`restrict(_params.host)`), `BandwidthManager.onAccept` (`onlyHost` + source check), `EvmHost.initialize` (`restrict(admin)`) — `CallDispatcher.dispatch(bytes memory encoded)` has **no caller restriction whatsoever**: [2](#0-1) 

`CallDispatcher` is a single shared, persistently-deployed contract wired into multiple apps (`IntentGatewayV2`, `HyperFungibleToken`) via the deploy script: [3](#0-2) 

`IntentGatewayV2` relies on the assumption that only *it* will call `dispatch()` on the tokens it just transferred to the dispatcher. It transfers `order.predispatch.assets` to the dispatcher, then calls `dispatch(order.predispatch.call)`, then sweeps back only the tokens listed in `order.inputs` by reading the dispatcher's *current* balance and moving all of it: [4](#0-3) 

Any token that ends up on the `CallDispatcher` as a side effect of `order.predispatch.call` (or `order.output.call` in `_execute`) but is **not** one of the tracked `order.inputs`/`order.output.assets` tokens is never swept back — it is simply left sitting in the shared `CallDispatcher` contract's balance, exactly like RDNT/WETH sitting in `UniswapPoolHelper` before `initializePool()` was called. [5](#0-4) 

Because `dispatch()` is public and unrestricted, and operates in the `CallDispatcher`'s own storage/balance context (not `delegatecall`), any unprivileged address can call `CallDispatcher.dispatch()` directly at any time with a `Call[]` of the form `{to: token, data: transfer(attacker, balance)}` to sweep out **any** token or native-ETH dust currently resident in the shared dispatcher — regardless of which app or order deposited it. The same document confirms the trust assumption that `dispatch()` is only ever invoked by a trusted caller, which the contract itself does nothing to enforce: [6](#0-5) 

### Title
Unrestricted `CallDispatcher.dispatch()` allows anyone to drain dust/residual tokens deposited by other apps' order flows - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a shared, unowned contract used by `IntentGatewayV2` (predispatch/postdispatch calldata execution) and `HyperFungibleToken` (mint-time calldata execution). Its sole entry point, `dispatch(bytes memory encoded)`, executes an arbitrary `Call[]` with no access control on the caller. Multiple call sites transfer tokens to this contract in advance of calling `dispatch()` and then sweep back only a subset of tracked tokens, leaving any other token balance permanently resident in the dispatcher. Because `dispatch()` is callable by anyone, any attacker can directly invoke it to sweep such residual balances to themselves.

### Finding Description
`CallDispatcher.dispatch()` has zero authentication — no `onlyOwner`, no `restrict()`, no `onlyHost` check — unlike every comparable governance/execution entrypoint elsewhere in the codebase (`HostManager.onAccept`, `BandwidthManager.onAccept`, `EvmHost.initialize`). It executes each `Call{to, value, data}` directly from the `CallDispatcher`'s own address/balance context.

`IntentGatewayV2.placeOrder` and `IntentsBase._execute`/`_withdraw`-adjacent flows transfer order-specific assets to the dispatcher, invoke user- or solver-supplied calldata via `dispatch()`, and then sweep back *only* the tokens explicitly enumerated in `order.inputs`/`order.output.assets` by reading the dispatcher's balance at sweep time. Any token that is not part of that enumerated set — e.g., a byproduct of the predispatch/postdispatch calldata's own intermediate swap steps, fee-on-transfer remnants, or native ETH dust — is left sitting in the `CallDispatcher`'s balance indefinitely, since no generic "sweep everything" path exists.

Because `CallDispatcher` is deployed once and shared across apps/orders, and its `dispatch()` function is unrestricted, any external account can call it directly with a crafted `Call[]` (`to: <leftover token>, data: transfer(attacker, IERC20(token).balanceOf(address(this)))`) to redirect any such stranded balance to itself — exactly analogous to an attacker calling the unrestricted `initializePool()` after tokens were pre-funded by the protocol owner.

### Impact Explanation
Any residual token or native ETH balance accumulated on the shared `CallDispatcher` from any app's predispatch/postdispatch calldata execution can be stolen by an unprivileged attacker, resulting in direct loss of funds that belonged to intent-gateway users/solvers or other apps sharing the same dispatcher instance.

### Likelihood Explanation
Likelihood depends on residual balances actually accumulating on `CallDispatcher` (e.g., predispatch calldata producing an untracked token, fee-on-transfer dust, or partial execution paths). Since the contract is shared across multiple apps and chains and is a long-lived singleton, any such accumulation — even accidental — is permanently exposed to theft by anyone monitoring its balance, with no privileged actor, relayer, or governance action required to exploit it.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allowlist (e.g., only registered app contracts), or make `CallDispatcher` non-shared/ephemeral per call so it never holds a balance between transactions boundaries it doesn't fully sweep. Alternatively, add a generic, permissioned sweep-all mechanism and ensure every caller (`IntentGatewayV2`, `HyperFungibleToken`, etc.) fully drains all token types it could have introduced to the dispatcher before returning control.

### Proof of Concept
1. An order's `predispatch.call` (defined by the order creator, executed via `CallDispatcher.dispatch`) performs a swap that leaves a small amount of an intermediate token, `X`, on the `CallDispatcher` (not part of `order.inputs`).
2. `IntentGatewayV2.placeOrder` sweeps back only the tokens listed in `order.inputs`; token `X` remains on `CallDispatcher`.
3. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: X, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(X).balanceOf(address(callDispatcher)))})]))` directly — no restriction prevents this — and receives the stranded `X` balance.

contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
