### Title
Security-review hook crashes and skips code review when a diff contains a filename with invalid UTF-8 bytes - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`_git_name_only` runs `git diff --name-only -z` with `subprocess.run(..., text=True)`, which decodes stdout using the platform's default text codec with strict error handling. A tracked file whose name contains a byte sequence that is not valid UTF-8 makes the decode step raise `UnicodeDecodeError`, which is not one of the exception types (`subprocess.TimeoutExpired`, `FileNotFoundError`, `OSError`) caught by the surrounding `try/except` in `_git_name_only` [1](#0-0) , so the exception propagates uncaught.

### Finding Description
`_git_name_only`'s inner `_run` helper calls `subprocess.run([...], text=True, ...)` and then does `result.stdout.split("\0")` [2](#0-1) . With `text=True`, Python decodes the subprocess's raw stdout bytes using the platform's preferred encoding (typically UTF-8) with the default `errors="strict"` policy — this decoding happens inside `subprocess.run` itself, before the function body's own `try/except` block even executes any of the code that could raise. The catch clause around the call site only lists `(subprocess.TimeoutExpired, FileNotFoundError, OSError)` [1](#0-0) ; `UnicodeDecodeError` is a `ValueError` subclass, not `OSError`, so it is not caught here.

`_git_name_only` is called directly from `compute_v2_review_set` in `diffstate.py` with no local exception handling around either call site: `dirty_now |= _git_name_only(repo, f"{head_at_capture}..HEAD") or set()` and `changed_since = _git_name_only(repo, baseline_sha)` [3](#0-2) . If any file that changed in the reviewed range has a filename that is not valid UTF-8 (POSIX filenames may contain arbitrary non-NUL bytes, so this is trivially constructible, e.g. via `git mv` to a name containing a raw `0xff` byte, or simply having such a file already present in the repository and letting Claude edit it), the exception propagates out of `compute_v2_review_set` uncaught.

Git's `-z` NUL-delimited, unquoted (`core.quotePath=false`) output format is otherwise correct for preserving arbitrary path bytes — the vulnerability is not in the `-z`/NUL splitting logic itself (that's sound), but in decoding the byte stream as text before the NUL-split ever runs, defeating the purpose of using `-z`/`quotePath=false` to preserve raw bytes.

### Impact Explanation
This is the Stop-hook's final security-review computation path (`compute_v2_review_set` → Haiku vulnerability scan). If the crash is not caught further up the call stack with a fail-open handler, the Stop hook's `PostToolUse`/`Stop` review either exits abnormally or (if the outer hook wraps broad exceptions, which the surrounding codebase does extensively elsewhere) silently degrades and skips the LLM security review for that turn. Either way, a diff that legitimately contains an actual vulnerability introduced alongside an oddly-named file would go unreviewed — a security-enforcement bypass of the plugin's core protection (the Stop-hook vulnerability scan described in the module's own docstring) [4](#0-3) .

I was not able to fully confirm, within this investigation, whether the ultimate caller of `compute_v2_review_set` wraps it in a broad `except Exception` that fails open (skips review) versus failing closed (blocks the turn) — this would need to be verified in the Stop-hook handler in `security_reminder_hook.py` to establish the precise downstream behavior.

### Likelihood Explanation
Trivially reproducible: any tracked file whose repo-relative path contains an invalid UTF-8 byte sequence and that is included in the diff range passed to `_git_name_only` (either `head_at_capture..HEAD` or the baseline SHA) triggers this unconditionally, with no special privileges — a filename is attacker/repo-content controlled and requires no admin or maintainer access.

### Recommendation
Decode subprocess output explicitly and tolerantly instead of relying on `text=True`'s strict decoding: capture stdout as bytes (`capture_output=True` without `text=True`, or pass `errors="surrogateescape"`) and decode with `errors="surrogateescape"` or `errors="replace"` before splitting on `"\0"`, consistent with how `_git_diff_range` already does `r.stdout.decode("utf-8", errors="replace")` [5](#0-4) . Apply the same fix to `_git_status_porcelain`, which has the identical `text=True` decoding issue [6](#0-5) .

### Proof of Concept
Unit test plan for `plugins/security-guidance/hooks/gitutil.py::_git_name_only`:
1. In a temp git repo, create and commit a file whose name is a valid-on-POSIX-but-invalid-UTF-8 byte sequence, e.g. `b"weird-\xffname.py"` (using `os.fsencode`/raw `os.rename`/`subprocess` with `os.environb` to avoid Python-side UTF-8 validation on the path itself).
2. Modify the file's content on top of an earlier commit `base`.
3. Call `_git_name_only(repo_dir, base)`.
4. Expected (buggy) behavior: an unhandled `UnicodeDecodeError` is raised out of `_git_name_only`, instead of the function returning `None`/logging via `debug_log` like other git-failure paths.
5. Expected (fixed) behavior: the function returns a set containing the fsdecoded/surrogate-escaped path (or at minimum degrades to `None` cleanly without raising), matching the error-handling contract documented for this function ("None if git failed").
