### Title
Checks-Effects-Interactions violation and missing reentrancy guard in `IntentGatewayV2.withdraw` allow escrow double-spend on Tron - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron build of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reimplements the escrow-release logic in its internal `withdraw` function, but diverges from the canonical EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`) in two ways that combine into a real fund-safety gap: (1) it sends value to `beneficiary` *before* decrementing `_orders[commitment][token]`, and (2) unlike the canonical EVM contract, none of the Tron contract's state-mutating entrypoints (`placeOrder`, `fillOrder`, `cancelOrder`) carry a `nonReentrant` guard.

### Finding Description
The canonical EVM `_withdraw` in `IntentsBase.sol` correctly follows checks-effects-interactions: it computes `escrowed`, checks it, updates `_orders[body.commitment][token]` first, and only then performs the external transfer: [1](#0-0) 

The Tron variant's `withdraw` reverses this order — the external call (native `.call{value:...}` or a raw, unchecked-return `token.call(transfer(...))`) happens first, and the escrow accounting is only decremented afterward: [2](#0-1) 

The guard that exists — `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` — only verifies the escrow slot is *non-zero*, not that it is *sufficient* for `amount`, and it is evaluated once per token before the external call rather than being re-validated after. Because `_orders[body.commitment][token] -= amount` executes only after the external send, the escrow slot for that commitment/token pair is stale (still holding its pre-withdrawal value) for the full duration of the external call. Solidity 0.8's checked arithmetic prevents a literal underflow, but it does not stop reentrancy during that window.

Crucially, the Tron contract's public order-lifecycle entrypoints have no reentrancy lock at all — `grep` for `nonReentrant`/`ReentrancyGuard` across `evm/tron/contracts/apps/IntentGatewayV2.sol` matches nothing, whereas the canonical EVM `cancelOrder` explicitly declares `nonReentrant`: [3](#0-2) 

`withdraw` is reached from `onGetResponse` (cross-chain cancel confirmation) and from `onAccept`'s `RedeemEscrow`/`RefundEscrow` branches, both of which resolve `beneficiary` from attacker-influenced fields — `order.user` (set by whoever placed the order) for refunds, or `msg.sender` of the filling solver for redemptions. A user who places an order naming a malicious contract as `order.user`/beneficiary, or a solver who fills orders from a malicious contract, controls code that runs during the native-ETH `.call` or during an ERC20 token's transfer hook, before `_orders[commitment][token]` is decremented and before the enclosing call stack returns to update `_filled`/other order state in `withdraw`'s own scope — and since the calling contract has no `nonReentrant` modifier anywhere, that malicious code is free to re-enter `placeOrder`, `fillOrder`, or `cancelOrder` on the same contract while global storage (`_orders`, `_partialFills`) is in this stale, not-yet-decremented state.

### Impact Explanation
This breaks the "bridged assets/order escrow must move exactly once and only to the rightful beneficiary and amount" invariant. Because the escrow debit for a given commitment/token is delayed past an external call with no reentrancy protection anywhere in the contract, a malicious beneficiary (attacker-controlled order user or solver) can attempt to re-trigger fill/cancel paths against the same still-fully-escrowed balance before it is reduced, risking double release of the same escrowed funds. This is a direct fund-loss/duplicate-settlement vector in bridge custody logic, matching the bounty's "stealing or loss of funds" and "double-settlement" categories.

### Likelihood Explanation
Medium. It requires no privileged role — any user can place an order naming a contract they control as `order.user` (beneficiary for refunds) or fill an order from a contract they control (beneficiary for redemptions/native-ETH payouts), and native-ETH escrow types are natively reentrant via the `.call{value:...}("")` sink. The only constraint is crafting the reentrant call to land on a state window where `_orders`/`_partialFills` for the affected commitment have not yet reflected the in-flight withdrawal — feasible given `withdraw` never uses a lock and processes multiple tokens in a loop.

### Recommendation
Bring the Tron `withdraw` in line with the canonical EVM `_withdraw`: decrement `_orders[body.commitment][token]` before performing any external call, use `SafeERC20.safeTransfer` instead of raw `.call` with unchecked return data, and add a `ReentrancyGuard`/`nonReentrant` modifier to `placeOrder`, `fillOrder`, and `cancelOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, matching the guard already present in `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.destination == order.source` (same-chain) is not required; use the cross-chain cancel path: attacker places an order with `order.user` set to a malicious contract `M`.
2. Attacker triggers cancellation from source (`_cancelFromSource`), producing a Hyperbridge GET request that eventually calls `onGetResponse` → `withdraw(body, true)` with `body.beneficiary = order.user = M`.
3. In `withdraw`, for a native-ETH input token, `beneficiary.call{value: amount}("")` invokes `M`'s `receive()`/fallback *before* `_orders[commitment][token] -= amount` executes.
4. `M`'s fallback re-enters the `IntentGatewayV2` contract (e.g., calling `fillOrder` or `placeOrder` for a crafted order that reads/writes `_orders`/`_partialFills`), operating against escrow state that has not yet been decremented for the in-flight commitment/token — no `nonReentrant` modifier exists anywhere in the contract to block this.
5. Depending on the crafted reentrant call, this can be used to extract additional value against the same not-yet-updated escrow slot before the original `withdraw` call completes its decrement, violating the "moves exactly once" invariant.

Note: full exploitation depth (i.e., the exact reentrant call sequence needed to net extra funds beyond what `_filled` already blocks for the *same* commitment) was not traced end-to-end in this session and would benefit from a Foundry-based PoC against `evm/tron/contracts/apps/IntentGatewayV2.sol` to confirm the precise drainable amount; the CEI violation and total absence of reentrancy guards on this contract's public entrypoints are, however, directly confirmed in the code cited above.
