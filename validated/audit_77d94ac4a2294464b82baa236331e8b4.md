## Title
Division-before-multiplication truncation in `compute_royalty_amount()` causes NFT offer royalty payments to systematically underpay the intended royalty percentage - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount()` mirrors the exact bug class from the external report: it divides before multiplying, truncating an intermediate integer-division result before applying the percentage, producing a smaller (and in some cases zero) royalty than the mathematically correct floor(amount * percentage / royalty_split / MAX_ROYALTY_BASIS_POINTS) would give when computed with multiplication ordered first.

### Finding Description
The function is: [1](#0-0) 

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(...)
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
`abs(offered_amount) // royalty_split` is evaluated first, truncating any remainder before the value is multiplied by `percentage`. This is precisely the "division before multiplication" precision-loss pattern in the external Solidity report (`floorTick = (tick / tickSpacing) * tickSpacing`), applied here as `(amount // split) * percentage // 10000` instead of `(amount * percentage // 10000) // split` or `amount * percentage // (split * 10000)`.

The same pattern also appears in `NFTWallet.royalty_calculation()`: [2](#0-1) 
computing `abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS`, and in the CLI helper `calculate_nft_royalty_amount` (`chia/cmds/wallet_funcs.py:1506`), which additionally uses floating-point division (`* nft_royalty_percentage / 10000`), compounding the precision issue.

`compute_royalty_amount()` is the value used to actually construct the on-chain royalty payment coin in `NFTWallet.make_nft1_offer()`: [3](#0-2) 
`extra_royalty_amount = compute_royalty_amount(amount, request_side_royalty_split, percentage)` is used directly as the `CreateCoin` amount paid to the royalty address in the settlement spend bundle that gets pushed to the mempool.

### Impact Explanation
This truncation is a wallet-side (offering-side) computation, not an amount enforced by consensus/CLVM validation of the NFT ownership/transfer-program layer — I was unable to locate the on-chain CLSP/CLVM enforcement logic for royalty amounts in the indexed codebase (the `.clsp`/`.clvm` NFT transfer program search returned no matches, likely due to index size limits excluding CLVM source files), so I cannot confirm whether the chain-side puzzle independently validates the exact royalty amount or merely accepts whatever `CreateCoin` the offering wallet constructs.

If the on-chain ownership-layer puzzle does not independently recompute and enforce the royalty amount (which is the typical NFT1 royalty design — the transfer program only asserts a `trade_price`-derived minimum, and the maker constructs the actual payment), then this bug results in NFT creators/royalty recipients being systematically underpaid on multi-way splits (`royalty_split > 1`) or fractional-percentage trades, since the value is only ever rounded down further than intended, never allowing a counterparty to extract more value than owed. This is a fund-shortfall/economic-correctness issue for royalty recipients rather than a fund-theft or supply-inflation vulnerability, since `floor(floor(a/b)*p/10000) <= floor(a*p/(b*10000))` always holds for non-negative integers — the bug can only make payments smaller, never larger, so it does not enable double-spend, unauthorized withdrawal, or asset forgery.

### Likelihood Explanation
Any NFT offer with `royalty_split > 1` (multiple NFTs from the same/`request_side_royalty_split` bucket) or with a percentage/amount combination that doesn't divide evenly will trigger the underpayment deterministically, every time such an offer is created — this is not a rare edge case but a systematic rounding bug reachable by any wallet user creating an NFT offer that includes royalty-bearing assets split across multiple counterparties.

### Recommendation
Reorder the arithmetic to multiply before dividing, matching the report's fix pattern, and perform division only once at the end to minimize truncation:
```python
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```
Apply the same fix to `NFTWallet.royalty_calculation()` and to `calculate_nft_royalty_amount()` in `chia/cmds/wallet_funcs.py` (which should also be converted from floating-point to integer arithmetic to avoid separate float-precision issues).

### Proof of Concept
Using the existing test file `chia/_tests/wallet/nft_wallet/test_nft_royalty.py`: [4](#0-3) 
`compute_royalty_amount(offered_amount=-2_000_000, royalty_split=2, percentage=1000)` returns `100_000` mojos (5% of 2,000,000). With `offered_amount = -2_000_001`, `royalty_split = 2`, `percentage = 1000`:
- Correct (multiply-first): `2_000_001 * 1000 // (2 * 10000) = 100_000` (still rounds the same here, but consider `offered_amount = -1_000_003, royalty_split = 3, percentage = 3000`)
- Current buggy order: `1_000_003 // 3 = 333_334` → `333_334 * 3000 // 10000 = 100_000`
- Multiply-first order: `1_000_003 * 3000 // (3 * 10000) = 3_000_009_000 // 30_000 = 100_000` — for larger discrepancies (e.g. `offered_amount = 7, royalty_split = 3, percentage = 3000`): buggy gives `7 // 3 = 2`, `2 * 3000 // 10000 = 0`; multiply-first gives `7 * 3000 // 30000 = 0` as well in this case, but for `offered_amount = 10000, royalty_split = 3, percentage = 100`: buggy gives `10000 // 3 = 3333`, `3333*100//10000 = 33`; correct gives `10000*100//30000 = 33` — the discrepancy grows with larger percentages and smaller splits/amounts, confirmed conceptually by the general inequality `floor(floor(a/b)*p/M) <= floor(a*p/(b*M))`, i.e. the current code can only ever pay the royalty recipient less than or equal to the mathematically correct amount.
