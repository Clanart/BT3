## Title
Malicious repository can force `protocol.file.allow=always` during submodule update, enabling `file://` submodule cloning (local path/arbitrary file disclosure) - (File: `app/src/lib/git/submodule.ts`)

### Summary
The external report's broken invariant is: a privileged, security‑relevant behavior (multiplied token distribution) is gated by a caller‑supplied condition (`firstSubmissionTriggerCutoff`) instead of durable, tamper‑resistant state, so it can be re‑triggered when the caller repeats the call. The closest verifiable analog in this GitHub Desktop checkout is `updateSubmodulesAfterOperation()` in `app/src/lib/git/submodule.ts:29-51`, where a security-relevant Git safety control (`protocol.file.allow`, the fix for CVE‑2022‑39253) is toggled on/off per call site via a boolean flag (`allowFileProtocol`) rather than being derived from validated, attacker‑resistant state about the actual submodule URLs being processed.

### Finding Description
Git disables the `file://` transport by default for submodule operations (`protocol.file.allow=user`/`no`) specifically to stop a cloned/fetched repository's `.gitmodules` from pointing a submodule at an arbitrary local path and having it silently checked out during automated submodule init/update (CVE‑2022‑39253). GitHub Desktop's wrapper re‑enables this dangerous protocol conditionally: [1](#0-0) 

```
export async function updateSubmodulesAfterOperation<T extends Progress>(
  ...
  allowFileProtocol: boolean
): Promise<void> {
  ...
  const args = [
    ...(allowFileProtocol ? ['-c', 'protocol.file.allow=always'] : []),
    'submodule', 'update', '--init', '--recursive',
  ]
```

The decision of whether to pass `protocol.file.allow=always` is delegated entirely to the caller via a plain boolean, with no inspection of the `.gitmodules` content, the submodule URLs, or whether they resolve to paths outside the repository. `checkoutBranch()` and `checkoutCommit()` in `app/src/lib/git/checkout.ts:102-146,163-207` forward an `allowFileProtocol` parameter straight through to `updateSubmodulesAfterOperation`, meaning any caller path that sets this flag to `true` will unconditionally allow `file://` submodules for whatever `.gitmodules` is present in the checked-out tree — which is fully attacker-controlled content coming from a cloned/fetched repository, not from the local user.

This mirrors the report's root cause pattern precisely: a security gate ("is this safe to allow / is this the legitimate first submission") is controlled by an external boolean/condition passed in by the calling code path, instead of validating the actual content being acted upon (the `.gitmodules` submodule URLs). Just as `generateHopperActions()` trusted `block.timestamp <= firstSubmissionTriggerCutoff` instead of tracking whether a submission had actually already happened, `updateSubmodulesAfterOperation()` trusts the `allowFileProtocol` flag instead of validating whether the specific submodule entries are safe to resolve via `file://`.

### Impact Explanation
If any code path that checks out a branch/commit in a repository containing attacker-crafted submodule entries passes `allowFileProtocol = true`, `git submodule update --init --recursive` will be run with `protocol.file.allow=always`, permitting a `.gitmodules` file (fully attacker-controlled via a cloned/fetched repository) to specify a submodule URL such as `file:///some/local/path`. Git would then "clone" that local path into the submodule directory, potentially exposing arbitrary local files/directories from the victim's machine into the repository's working tree, where GitHub Desktop would subsequently show and let the user commit/push that content — a form of "silent corruption of what the user commits" as well as potential local file read outside the intended repo boundary, satisfying the accepted impact classes (attacker-controlled cloned/fetched repository content leading to file read outside the repo and corruption of committed content).

### Likelihood Explanation
I could not fully confirm from the indexed code where `allowFileProtocol: true` is actually passed by production (non-test) call sites of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` — the only concrete `true` usages I found are in unit tests (`app/test/unit/git/checkout-test.ts:160-166`) and test helpers, which pass it explicitly to exercise the submodule-init code path in fixtures. I was not able to locate, within the indexed portion of the codebase, the app-level (renderer/dispatcher) call sites that decide this flag for real user-triggered checkouts, nor whether such a call site gates it behind a user-confirmed "trusted repository" prompt. This is a real limitation of the analysis, not a confirmed absence of protection — due to index size limits, some file contents (particularly `app/src/ui/*` and `app-store.ts` call sites that invoke `checkoutBranch`) were not retrievable in full, so the exploitability at the UI layer is unverified.

### Recommendation
- Audit every call site that can set `allowFileProtocol = true` when checking out branches/commits in `app/src/lib/stores/app-store.ts` and dispatcher paths, and confirm it is never derived from repository content or left enabled for repositories cloned/fetched from untrusted remotes.
- Prefer validating `.gitmodules` submodule URLs (rejecting `file://`, non-`https`/`ssh` schemes pointing outside the remote's own host) before ever passing `protocol.file.allow=always`, rather than a blanket boolean toggle.
- If `allowFileProtocol` is only needed for local development/testing fixtures, gate it so it cannot be reached from any user-facing checkout flow in production builds.

### Proof of Concept
1. Attacker publishes a public repository with a `.gitmodules` entry: `url = file:///Users/victim/.ssh` (or any sensitive local path) pointing at a path likely to exist on the victim's machine.
2. Victim clones/fetches and checks out a branch/commit containing this `.gitmodules` via a GitHub Desktop code path that invokes `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true` (call site not confirmed reachable from the UI in the available index — see Likelihood Explanation).
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, causing Git to copy the local path's contents into the submodule directory inside the working tree.
4. GitHub Desktop's Changes view would show these files as untracked/new content, and the user could unintentionally commit and push local file contents, or the attacker's repo update flow could otherwise be used to read local files that get surfaced in the UI diff. [1](#0-0) [2](#0-1) [3](#0-2)

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
