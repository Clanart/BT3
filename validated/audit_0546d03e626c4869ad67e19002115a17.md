### Title
Untrusted serialized threshold keys can replace the restored participant, threshold policy, and group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts the serialized threshold parameters, interpolation mode, secret share, and all verification shares without binding them to the DKG session or checking that the secret share corresponds to the participant’s verification share. An attacker-controlled restore blob can therefore substitute a completely attacker-known one-of-one threshold key.

### Finding Description
The deserializer accepts attacker-supplied `t`, `n`, and `i`, selects either Constant or Lagrange interpolation, then reads the private scalar and every verification share directly from the input [1](#0-0) . `ThresholdKeys::new` validates only basic parameter consistency and derives `group_key` from the supplied verification shares; it never verifies `C::generator() * secret_share == verification_shares[i]` nor compares the parameters/group key with authenticated DKG output [2](#0-1) .

This is analogous to trusting checkpoint metadata during restoration: fields that should have been fixed by the original DKG execution are taken from untrusted serialized state instead.

### Impact Explanation
A crafted blob can declare `t = n = i = 1`, a known `secret_share`, and `verification_shares[1] = secret_share * G`. The resulting object has an attacker-known group key and can complete a FROST signature for a caller-supplied message without any other participant [3](#0-2) [4](#0-3) . If the restored key is used as a validator identity, custody account, or authorization key, the attacker can replace the intended key with one they control and produce valid signatures under it.

### Likelihood Explanation
Any restore, migration, import, or recovery path that feeds attacker-influenced bytes to `ThresholdKeys::read` is reachable. The parser accepts canonical encodings only, but does not require the encoded data to be consistent with any previously established key or DKG transcript [5](#0-4) . Exploitation requires the attacker to control or modify the serialized key state, not to know an existing private share.

### Recommendation
Authenticate serialized `ThresholdKeys` before use and bind them to the expected DKG session/context, participant set, `t`, `n`, participant index, interpolation method, and resulting group key. During construction or restoration, verify that the secret share matches its declared verification share. Restoration should reject arbitrary threshold-policy changes rather than reconstructing a new key solely from untrusted bytes.

### Proof of Concept
Conceptually, for any in-scope `Ciphersuite` `C`:

```rust
// Attacker chooses a known share. Zero is accepted, but any known scalar works.
let x = C::F::ZERO;
let verification_share = C::G::identity(); // x * G

let mut serialized = vec![];
serialized.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
serialized.extend(C::ID);
serialized.extend(1u16.to_le_bytes()); // t
serialized.extend(1u16.to_le_bytes()); // n
serialized.extend(1u16.to_le_bytes()); // i
serialized.push(1);                    // Lagrange
serialized.extend(x.to_repr().as_ref());
serialized.extend(verification_share.to_bytes().as_ref());

let keys = ThresholdKeys::<C>::read(&mut serialized.as_slice()).unwrap();
assert_eq!(keys.params().t(), 1);
assert_eq!(keys.params().i(), Participant::new(1).unwrap());
assert_eq!(keys.group_key(), verification_share);
```

Because no peer preprocesses are required for a one-of-one signing set, passing this restored object to `AlgorithmMachine::new(...).preprocess(...)`, then `sign(HashMap::new(), msg)` and `complete(HashMap::new())`, produces a signature valid for the attacker-selected group key.
