Analysis found a valid analog: the webhook verification path in this repo checks the HMAC signature of the **body** but exposes/recommends a **shop domain identifier taken from an unverified request header**, which is not covered by that signature. This mirrors the reported bug class ("check exists for one value but not the correlated value that actually determines ownership/scope, letting an attacker manipulate the unchecked value to bypass the intended protection").

### Title
Webhook `shop_domain` is read from an unsigned header while only the request body is HMAC-verified, allowing shop-domain spoofing on replayed/forged webhook requests - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates the HMAC signature over `request.raw_post` only, via `PayloadVerification#hmac_valid?`. The concern also exposes a `shop_domain` helper that simply reads `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]` — a value that is **not included in the HMAC computation** and is therefore fully attacker-controlled. [1](#0-0) [2](#0-1) 

The official documentation instructs app developers building custom webhook controllers to trust this exact `shop_domain` value to scope background job work: [3](#0-2) 

### Finding Description
The HMAC secret used to sign webhooks is the app's single client secret, shared across every shop that has the app installed — it is not shop-specific. Consequently, a valid HMAC over a request body only proves the request body was signed by Shopify for *some* shop using this app; it proves nothing about which shop the request pertains to. That binding is supposed to come from the `X-Shopify-Shop-Domain` header, but that header sits entirely outside the signed payload.

Just as `GoatV1Pair.takeOverPool()` checked `tokenAmountIn` but left `initialEth` unchecked — letting an attacker manipulate the unchecked field to satisfy/bypass the check meant to prevent unfair takeovers — this concern checks the HMAC of the body but leaves the `shop_domain` header completely outside verification, letting an attacker who controls a body/HMAC pair for their own shop cheaply substitute a victim shop's domain in that header field.

### Impact Explanation
A merchant who has legitimately installed the app on their own shop receives real, correctly-signed webhooks. They can capture one such request (body + valid `X-Shopify-Hmac-Sha256` value) and replay it directly at the app's webhook endpoint while substituting an arbitrary victim `X-Shopify-Shop-Domain` header value. `verify_request` still passes because it only checks the body's HMAC, not the header. If the receiving job (per the documented pattern `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)`) uses `shop_domain` to select which shop's record/session to act on, the attacker can cause the app to process a job attributed to a shop they do not own — a cross-shop data-confusion / spoofing issue.

### Likelihood Explanation
This requires an attacker to have (or briefly have) the app installed on any shop (unprivileged/unrelated-merchant relative to the victim) and simply replay a captured webhook with a modified header — no secret knowledge, no privileged access to the victim shop is needed, and the documented custom-controller pattern actively encourages using the unverified `shop_domain` value.

### Recommendation
Derive the shop identity from data that is covered by the HMAC signature (e.g., the parsed JSON payload body via `ShopifyAPI::Webhooks::Request`, which the default `WebhooksController` already uses) rather than from the unauthenticated `X-Shopify-Shop-Domain` header. If the header must be supported for backward compatibility, cross-check it against the shop domain embedded in the verified body and reject mismatches, and update the documentation example accordingly.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and capture a genuine webhook delivery (e.g. `orders/create`), noting the raw body and its `X-Shopify-Hmac-Sha256` header.
2. Replay the exact same body and valid HMAC header to the app's custom webhook endpoint (built per `docs/shopify_app/webhooks.md`'s example using `ShopifyApp::WebhookVerification`), but change `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb`) validates only the body HMAC, which is still valid, so the request passes.
4. The custom job is enqueued with `shop_domain: "victim.myshopify.com"`, causing the app to process/act on behalf of a shop the attacker does not control.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
```
