### Title
Transient mWomSV lock inflation lets attackers capture oversized, doubled vlMGP rewards in `ArbWomUp3.incentiveDeposit` mode=2 without durable backing - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.getRewardAmount` (called from `incentiveDeposit` with `_mode==2`) computes the reward tier using a live, unguarded read of `mWomSV.getUserTotalLocked(_account)`, then doubles the resulting MGP reward and permanently mints it as a `vlMGP` lock via `vlMGP.lockFor`. Because `mWomSV.startUnlock` can be called in the very same block right after the lock is registered (no minimum holding period), an attacker can transiently inflate `getUserTotalLocked` to push the marginal-reward calculation into a much higher reward tier, capture the doubled `vlMGP` mint, and then immediately begin unwinding the inflating balance — with no code path that claws back the already-minted `vlMGP`.

### Finding Description
In `incentiveDeposit`, the reward is computed *before* any new mWomSV backing from the current call is added: [1](#0-0) 

`getRewardAmount` for the lock path builds `accumulated` from the caller-supplied `_amountToConvert` plus the account's *current* `mWomSV.getUserTotalLocked`, then subtracts `calDoubledCounted(_account)` (which itself is computed from the same live `getUserTotalLocked` value) to get a marginal reward, which is only correct if that pre-existing locked balance is durable: [2](#0-1) 

`mWomSV.getUserTotalLocked` is a simple spot read of the MasterMagpie staking balance minus whatever is currently queued in cooldown — it carries no notion of "how long has this been locked" or minimum holding period: [3](#0-2) 

Locking is registered immediately in `MasterMagpie`, and `startUnlock` has no cooldown-before-you-can-start-unlocking check — it only checks that the amount is currently counted as locked: [4](#0-3) [5](#0-4) 

Exploit flow:
1. Attacker locks a large amount `L` of mWom into `mWomSV` (real capital, real transfer), instantly bumping `getUserTotalLocked(attacker)` to `L`.
2. In the same block, attacker calls `incentiveDeposit(_amount, _convertRatio, false, 2)`. `getRewardAmount` computes `accumulated = _amount + L`, applies the (likely higher) tier multiplier associated with that large accumulated value, computes the marginal reward `f(L+_amount) - f(L)`, doubles it (`rewardToSend * 2`), and `vlMGP.lockFor(rewardToSend, attacker)` mints it — permanently.
3. Immediately after, attacker calls `mWomSV.startUnlock(L)` to begin withdrawing the temporary balance `L`. Nothing in `ArbWomUp3` or `mWomSV` reduces or reclaims the already-minted `vlMGP` reward.
4. Note also that `_deposit` for `_mode==2` only actually locks `_amount/2` into `mWomSV` (the rest is swapped), yet the reward calculation used the full `_amount`, compounding the overcounting: [6](#0-5) .

Existing checks (`whenNotPaused`, `nonReentrant`, `_checkAmount`) do not address this because they don't validate that the locked balance used for tier computation is durable/vesting-enforced — this is a logic/economic flaw, not a reentrancy or pausing issue.

### Impact Explanation
This breaks the intended invariant that the doubled lock-mode bonus and tier-based multiplier are proportional to durable, sustained mWomSV backing. An attacker can capture a disproportionately large, permanently-minted `vlMGP` position (Immunefi class: theft/permanent misallocation of unclaimed protocol yield / protocol insolvency risk for the reward pool), funded by MGP tokens held in `ArbWomUp3` (`mgpleft` cap in `getRewardAmount` limits the payout to the contract's MGP balance, so worst case is draining the entire incentive MGP balance at a discount relative to real capital committed).

### Likelihood Explanation
Requires real capital `L` (must be genuinely transferred into `mWomSV`, and remains committed for `coolDownInSecs` once `startUnlock` is called, so it is not a zero-cost flash-loan attack), but no privileged role is needed — any EOA holding/buying WOM/mWom can execute it, and it is repeatable across `coolDownInSecs` cycles or with borrowed capital for short-term leverage. The attack is bounded only by tier design (how steep `rewardMultiplier` increases) and the MGP balance held by `ArbWomUp3`.

### Recommendation
Do not use a live/instantaneous `getUserTotalLocked` read to determine reward tiers for a bonus that is minted immediately and irrevocably. Options: (a) require a minimum holding/vesting period on the locked balance before it counts toward tier calculation (e.g., snapshot balance from N blocks/days prior), (b) make the reward mint itself vest/claim-back proportional to sustained locked balance over time instead of an instant `vlMGP.lockFor`, or (c) base the accumulated tier calculation only on the amount actually newly locked in this same transaction (`_amount/2` for mode 2) plus a time-weighted average of prior locked balance rather than the spot value.

### Proof of Concept
Foundry test outline:
1. Deploy `mWomSV`, `VLMGP`, `ArbWomUp3` with tiered `rewardMultiplier`/`rewardTier` where higher locked amounts map to higher multipliers; fund `ArbWomUp3` with MGP.
2. Attacker acquires `L` mWom (large) and calls `mWomSV.lock(L)` (or via a helper depositing wom→mWom then `lock`).
3. Call `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, false, 2)`; record `vlMGP.getUserTotalLocked(attacker)` (call it `R1`).
4. In the same test (same block or next tx), call `mWomSV.startUnlock(L)` for the full `L`.
5. Assert `vlMGP.getUserTotalLocked(attacker) == R1` (unchanged) — confirming the reward is not clawed back despite the backing balance `L` being withdrawn.
6. Compare `R1` against the reward that would have been produced by calling `incentiveDeposit` for the same `_amount` with `getUserTotalLocked(attacker) == 0` beforehand (no pre-lock) — showing `R1` is disproportionately larger due to the transient `L` inflation, quantifying the excess/unbacked `vlMGP` minted.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }

    function calDoubledCounted(address _account) public view returns (uint256) {
        uint256 accuIn1 = mWomSV.getUserTotalLocked(_account);
        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accuIn1 > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }

        rewardAmount += (accuIn1 - rewardTier[i - 1]) * rewardMultiplier[i - 1];
        return rewardAmount / DENOMINATOR;
    }
