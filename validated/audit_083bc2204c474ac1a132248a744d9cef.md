## Analysis

The seed report's core invariant break is: **a value that must represent `A - B` where `A ≥ B` is not always true is stored in/derived through a type or operation that silently clamps instead of failing loudly**, causing incorrect on-chain behavior instead of an honest revert.

The `tick_spacing: u8` bug forced a hard revert (DoS on legitimate configuration). The Hyperbridge codebase has a stronger local analog: the `hyper-fungible-token` pallet's decimal-scaling arithmetic uses `u8::saturating_sub` to compute an exponent for `10^exponent`, and that exponent is trusted to always be computed correctly. The invariant `erc_decimals >= local_decimals` is enforced **only at `register_token`/`update_token` time**, against a **transient, re-queryable value** (`fungibles::metadata::Inspect::decimals`), not a value pinned at registration. When that invariant is later violated, `saturating_sub` returns `0` silently (instead of erroring), turning the scale factor into `10^0 = 1` and corrupting the ERC20 amount computed by `convert_to_erc20` in `send()` — producing a wrong (inflated) minted amount on the destination EVM `HyperFungibleToken` contract relative to what was actually escrowed/burned on the Substrate side.

### Title
Stale-decimals invariant + silent `saturating_sub` clamp in `convert_to_erc20`/`convert_to_balance` corrupts cross-chain mint amounts - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`register_token`/`update_token` enforce `config.decimals >= local_decimals` only at call time [1](#0-0) , storing the checked `erc_decimals` in `Precisions` permanently. But `local_decimals` for non-native assets is re-derived live from `fungibles::metadata::Inspect::decimals` on every `send()`, `on_accept()`, and `on_timeout()` call [2](#0-1) , rather than being pinned at registration. If the local asset's decimals later increase (a normal, permissionless action available to that asset's own metadata-setter in a standard `pallet-assets` deployment, unrelated to this pallet's `CreateOrigin`), the once-valid `erc_decimals >= local_decimals` invariant silently breaks.

### Finding Description
`convert_to_erc20`/`convert_to_balance` compute the scaling exponent as:
```rust
U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
``` [3](#0-2) 

`saturating_sub` on `u8` clamps to `0` whenever `local_decimals > erc_decimals`, instead of propagating an error. The correct behavior in that case is to *divide* by `10^(local_decimals - erc_decimals)`; the code instead silently substitutes a no-op scale factor (`10^0 = 1`). This is functionally identical in kind to the seed bug's root cause — an arithmetic/type boundary that should be validated or widened is instead allowed to silently produce a wrong-but-plausible value rather than failing safely.

The guard that is supposed to prevent this state, `Error::ErcDecimalsBelowLocal` [4](#0-3) , only runs inside `register_token`/`update_token` [5](#0-4)  and is never re-checked in the hot paths (`send`, `on_accept`, `on_timeout`) that actually perform the scaling — those simply re-fetch current decimals and call the unguarded helper.

### Impact Explanation
Once `local_decimals` exceeds the stored `erc_decimals`, every subsequent `send()` mis-scales the outbound ERC20 amount upward by a factor of `10^(local_decimals - erc_decimals)` relative to the amount actually locked/burned on Substrate [6](#0-5) . The dispatched cross-chain `Message.amount` sent to the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract will therefore be far larger than what was escrowed, causing the destination contract to mint/unlock an inflated amount to the beneficiary — a direct fund-creation/drain vector against the destination-side custody, matching the bounty's "unauthorized execution / wrong amount / stealing of funds" categories. The inbound path (`on_accept`, `on_timeout`) is symmetrically affected and could under/over-credit Substrate-side beneficiaries the same way.

### Likelihood Explanation
Triggering requires only that a non-native local asset's decimals be increased after this pallet's `register_token` recorded a lower-or-equal `erc_decimals`. In a standard `pallet-assets` configuration, decimals are part of asset metadata and can be updated by the asset's own metadata-setter — an action entirely independent of, and not gated by, this pallet's `CreateOrigin`. No relayer, prover, or Hyperbridge governance compromise is needed; only an ordinary metadata update on the already-registered local asset. This is a plausible operational sequence (e.g., correcting a previously-wrong decimals value at asset creation), giving it non-negligible real-world likelihood, comparable to the "medium" rating applied to the seed finding.

### Recommendation
- Pin `local_decimals` at `register_token`/`update_token` time into the same `Precisions`-style storage (rather than re-deriving it live), so the checked invariant cannot silently drift out of sync.
- Replace `saturating_sub` with a checked subtraction that hard-errors (`Error::ErcDecimalsBelowLocal`) whenever `erc_decimals < local_decimals` is observed at conversion time in `send`, `on_accept`, and `on_timeout`, instead of only at registration.
- Alternatively, widen the scaling logic to correctly support the `local_decimals > erc_decimals` case (dividing instead of defaulting to a no-op multiplier) so a legitimate decimals change degrades gracefully instead of corrupting amounts.

### Proof of Concept
1. Register asset `X` with `local_decimals = 6` and `erc_decimals = 6` for chain `Evm(1)` via `register_token` (passes the `config.decimals >= local_decimals` check).
2. The local asset's decimals are later updated to `18` (via the underlying `Assets` pallet's own metadata-setter, independent of this pallet).
3. User calls `send()` with `params.amount = 1_000_000` units of `X` (now interpreted at 18 decimals), which burns/locks the correct amount locally [7](#0-6) .
4. `convert_to_erc20(1_000_000, erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so `erc20_amount = 1_000_000 * 10^0 = 1_000_000` — instead of the mathematically correct value scaled down by `10^12`.
5. The dispatched ISMP message carries `amount = 1_000_000` (raw, unscaled) to the EVM contract, which mints/unlocks `1_000_000` raw ERC20 units — `10^12`× more than the equivalent value actually escrowed, inflating the destination-side payout.

	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
