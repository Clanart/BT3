### Title
Copilot conflict-hunk reassembly matches resolutions positionally, allowing prompt-injected content in a conflicting commit/PR to silently splice merged code into the wrong conflict block - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The bug-class from the report is an identifier-substitution error: an operation that should key off a specific id instead uses a fixed/positional value, so it silently acts on the wrong object. The closest analog in GitHub Desktop is in the Copilot merge-conflict resolution feature: `reassembleResolvedFile` splices the model's per-hunk resolutions into a conflicted file purely by encounter order (`hunkIndex`), not by any stable identifier tied to the specific conflict block, and `validateResolutionPaths` only checks that the *count* of hunks matches, never that they correspond to the correct blocks.

### Finding Description
`reassembleResolvedFile` walks the raw file line-by-line, and for every `<<<<<<<` conflict marker block it finds, it takes `hunkResolutions[hunkIndex]` and increments `hunkIndex`: [1](#0-0) [2](#0-1) 

The docstring itself states the resolution is "matched by order, not by line number." The only guard on the model's output, `validateResolutionPaths`, checks that a file's hunk *count* equals the expected count - it never verifies that hunk 1's content corresponds to the conflict actually at position 1 in the file: [3](#0-2) 

The content fed to the model - and therefore the values it can be induced to reorder or mis-produce - comes from data in the repository being merged: conflict hunks, commit messages, and PR titles/descriptions, all of which are attacker-influenced when merging/rebasing a branch from an untrusted fork or PR (`app/src/lib/copilot-conflict-context.ts`, referenced via `ourCommits`/`theirCommits`/PR context and consumed in `app-store.ts`'s Copilot resolution flow).

Because the LLM output is untrusted (it is explicitly a "model's raw response" that must be parsed and validated, per `parseCopilotConflictResolution`), and the array-index-based splicing has no cross-check that resolution *i* actually corresponds to conflict block *i*'s content (e.g., no hash/fingerprint of the original marker block, no line-range anchor), a model response that is correct in shape (same hunk count, no leftover markers) but has resolutions shuffled or mismatched relative to actual blocks will pass validation and be silently written to disk via the write path in `app-store.ts` (`_acceptCopilotConflictResolution`), then staged with `git add`: [4](#0-3) 

This mirrors the TBY `burn` bug precisely: the code has a correct identifier available in principle (the specific conflict block/content) but the actual operation is keyed on a bare sequential index, so once the sequence is perturbed, actions silently apply to the wrong target — here, wrong resolved code gets written into a different conflict block in the file the user is about to commit/push.

### Impact Explanation
If the positional hunk-to-resolution mapping is defeated (whether via a model reordering resolutions when reasoning about a specially crafted/prompt-injected commit message, PR body, or conflicting hunk content that is entirely attacker-supplied by a forked branch/PR being merged), the reassembled file silently contains incorrect code: content intended for one conflict block ends up in a different, unrelated location in the file. Since Desktop's write path stages the result automatically (`git add`) and the whole point of the feature is to reduce manual review, this is a realistic path to silent corruption of what the user commits or pushes — the exact impact class called out as valid ("silent corruption of what the user commits or pushes"). The attacker's foothold is exactly the required primitive: content the attacker controls in a repository the victim clones/fetches/merges (a fork, PR, or set of commits).

### Likelihood Explanation
The likelihood is bounded by how reliably an attacker can induce an LLM to shuffle or misalign hunk order while still passing the shape-only validation (matching path, count, and "no leftover marker" regex check). This is a prompt-injection-dependent bug, not a deterministic logic flaw like the original TBY report — I could not verify from local code alone whether the model consistently preserves conflict order in practice, or whether any additional runtime safeguard exists beyond what's shown in `copilot-conflict-resolution.ts`. The static code fact that is certain, however, is that **no structural safeguard exists** to prevent misordering: matching is purely by array index, with no anchor to the actual position/content of each conflict block once past the surface-level count/path checks.

### Recommendation
Anchor each hunk resolution to a stable identifier derived from the original conflict block (e.g., a hash of the ours/theirs/base content, or the block's original line offset) rather than array position, and have `validateResolutionPaths` (or a new validation step) verify that each returned resolution's derived identifier matches the corresponding expected conflict block before splicing. This removes the reliance on ordinal position as an implicit "id" and prevents a shape-valid-but-shuffled model response from silently corrupting unrelated regions of the file.

### Proof of Concept
Local-code evidence only (I do not have access to run the LLM to demonstrate end-to-end exploitation, so this is a structural PoC based on the validated code path):
1. Attacker prepares a fork/PR with conflicting changes plus commit messages/PR description crafted to (via prompt injection) bias the model into returning `resolutions[].hunks` in a shape that still has the correct file path and correct hunk *count* for one or more files, but with hunk 1 and hunk 2 content transposed (or otherwise decoupled from the conflict block they actually belong to).
2. `parseCopilotConflictResolution` accepts the response (valid JSON, correct field types) — see the parsing/validation loop at [5](#0-4) .
3. `validateResolutionPaths` passes because it only compares hunk counts per path, not per-hunk correctness — see [3](#0-2) .
4. `reassembleResolvedFile` splices `hunkResolutions[0]` into the first conflict block encountered and `hunkResolutions[1]` into the second, purely by encounter order — see [2](#0-1) , silently producing a file where resolved content lands in the wrong conflict region.
5. `_acceptCopilotConflictResolution` in `app-store.ts` writes this reassembled content to disk and stages it with `git add` without any further per-hunk correctness check, so the corrupted content becomes what the user commits/pushes: [6](#0-5) .

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
