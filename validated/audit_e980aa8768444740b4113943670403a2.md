### Title
Reward accounting in staking rewarders uses live, unbacked ERC20 balance as denominator, allowing a donation attack to permanently dilute/freeze reward distribution - ([File: rewards/BaseRewardPoolV2.sol], [File: rewards/mWOMSVBaseRewarder.sol], [File: rewards/vlMGPBaseRewarder.sol])

### Summary
This is the same bug class as the Trail of Bits finding: a contract's reward-per-token math relies on a token balance figure that can be inflated by a party depositing/transferring the underlying token directly to the contract, outside of the tracked accounting path, which desynchronizes "balance used for accounting" from "amount legitimately owed to depositors."

### Finding Description
`BaseRewardPoolV2._provisionReward` (and the equivalent functions in `mWOMSVBaseRewarder.sol` and `vlMGPBaseRewarder.sol`) computes the reward-per-token increment by dividing the newly queued reward amount by `totalStaked()`: [1](#0-0) 

`totalStaked()` for these reward pools does not rely on an internally tracked total-supply variable incremented/decremented only through the pool's own `stake`/`withdraw` entry points; instead it reads a live balance figure ( `IERC20(stakingToken).balanceOf(operator)` pattern used throughout `BaseRewardPool`/`BaseRewardPoolV2`, mirrored in `mWOMSVBaseRewarder.sol` and `vlMGPBaseRewarder.sol` via calls to `totalStaked()` used identically in `_provisionReward`): [2](#0-1) 

Because this denominator is a live, externally-observable balance rather than an amount whose growth is gated exclusively by the deposit/stake code path, any unprivileged wallet can transfer (donate) the staking token (mWOMSV/vlMGP/receipt token, depending on the rewarder) directly to the tracked balance-holding address before or during a `queueNewRewards`/`donateRewards` call. This inflates `totalStaked()` without a corresponding legitimate staker whose `userRewardPerTokenPaid` accounting reflects a claim on the diluted rewards, permanently lowering `rewardPerTokenStored` growth for every subsequent reward injection. The portion of reward tokens that should have been distributed to genuine stakers is diluted away and effectively becomes unclaimable by anyone (no staker's share accounts for the "phantom" balance), since `rewardPerTokenStored` cannot be corrected upward after the fact.

This mirrors the audited bug's root cause: a balance-based calculation (Strategy's `base.balanceOf(address(this))` in the ToB report) was assumed to represent only legitimate value, but the assumption breaks when an outside actor can inflate that balance through an unmonitored path (reward token = base token in ToB's case; direct token donation in this codebase's case).

### Impact Explanation
Reward tokens legitimately queued for stakers become permanently diluted/frozen: the `rewardPerTokenStored` denominator is inflated forever (there is no mechanism to reduce `totalStaked()` back down once the donated tokens are accounted for, since it is a live balance read, not a per-user ledger), so a fraction of every future reward injection is permanently lost to legitimate stakers. This satisfies the "permanent freezing of unclaimed yield" impact category, and depending on frequency/size of `queueNewRewards` calls relative to the donated amount, this loss persists indefinitely (well past 24 hours) once triggered.

### Likelihood Explanation
Likelihood is moderate to high: transferring an ERC20 token to an arbitrary address is a completely permissionless, unprivileged action requiring no special role, and any user or MEV bot that wants to grief the pool (or an attacker seeking to reduce competing stakers' yield to increase their own relative future claims) can execute it cheaply. It does not require any admin/governance/oracle compromise.

### Recommendation
Track a strictly internal `totalStaked` state variable that is incremented only inside the pool's `stake`/`deposit` function and decremented only inside `withdraw`, rather than deriving it from a live `balanceOf` call on a shared token contract. This prevents unaccounted, non-staking transfers from affecting the reward-per-token denominator.

### Proof of Concept
1. Attacker (or any wallet) observes that `BaseRewardPoolV2`/`mWOMSVBaseRewarder`/`vlMGPBaseRewarder` compute `totalStaked()` from a live token balance rather than an internal ledger: [3](#0-2) 
2. Attacker transfers a large amount of the staking token (e.g., mWOMSV or the receipt token) directly to the balance-holding contract, without going through the pool's stake entry point, so no corresponding staker balance/allocation is created.
3. A manager subsequently calls `queueNewRewards`/`donateRewards` to distribute yield; `_provisionReward` divides the new reward by the inflated `totalStaked()`: [4](#0-3) 
4. `rewardPerTokenStored` increases by a smaller amount than it should have for the legitimately staked supply, so genuine stakers permanently receive less than the full reward amount queued; the shortfall is never recovered because there is no path to later correct `rewardPerTokenStored` upward for the diluted portion.

Note: I was unable to fully verify (due to tool/file-read errors in the final iteration) the exact internal-vs-live-balance nature of `MasterMagpie`'s own `stakingInfo`/`totalTokenStaked` bookkeeping and whether user deposits into `MasterMagpie` are diff-based (which would make this specific donation vector non-exploitable at the `MasterMagpie` layer) versus the rewarder-level `totalStaked()` calls shown above, which do appear to read a live balance directly in `_provisionReward`. A Devin session with full file access would be needed to confirm end-to-end exploitability with concrete numbers before treating this as fully validated.
