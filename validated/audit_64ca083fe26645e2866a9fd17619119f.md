### Title
Incorrect Taproot tweak derives a different output key for odd group keys - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`tweak_keys` applies the TapTweak scalar to the group key before normalizing that key to BIP-340’s even-Y internal-key representative. For an odd group key `P`, Serai derives `x(P + tG)`, while BIP-341 derives `x(-P + tG)`, producing a different output key and deposit address whenever the group key is odd.

### Finding Description
The function hashes the x-coordinate of the current group key and applies that scalar as a key offset. [1](#0-0)  It only negates the keys after the offset has been added, and only when the resulting output point is odd. [2](#0-1)  BIP-341 instead interprets the x-only internal key as its even-Y representative before applying `TapTweak(x(P))`; therefore, an odd original `P` must be negated before the offset is added. [3](#0-2) 

This is a normalization mismatch: Serai uses the raw affine parity of `P` during the tweak, while the Bitcoin x-only key normalization uses `P`’s even representative. The scanner subsequently watches only the script produced from Serai’s incorrectly derived even output key. [4](#0-3) [5](#0-4) 

### Impact Explanation
An external sender can calculate the standard BIP-341 Taproot output for the published x-only group key and send funds to it. For an odd group key, that output commits to `x(-P + tG)`, while Serai watches and attempts to spend `x(P + tG)` after final parity normalization. [6](#0-5) 

`Scanner::scan_transaction` recognizes outputs only by exact `script_pubkey` membership, so the standard Taproot output is not reported as received. [7](#0-6)  Even if the outpoint is supplied manually, `SignableTransaction::multisig` requires the claimed previous output script to equal the script generated by Serai’s offset key before creating signing machines. [8](#0-7)  Deposits sent to the standard BIP-341 address can therefore remain uncredited and unspendable by the threshold key.

### Likelihood Explanation
The condition is deterministic and occurs whenever the untweaked threshold group key has odd Y parity. An unprivileged sender only needs to submit an ordinary Bitcoin transaction paying the standard x-only-derived Taproot script; no validator, signer, RPC, or key-material compromise is required. [7](#0-6) 

### Recommendation
Normalize the internal key to even parity before calculating and applying the TapTweak offset. The sequence should be:

1. Negate the original `ThresholdKeys` if `group_key` is odd.
2. Calculate `TapTweakHash` over that normalized key’s x-coordinate.
3. Apply the tweak with `offset`.
4. Negate the tweaked key if needed so its encoded group key is even.

Equivalently, replace the current “offset then normalize” order with “normalize internal key, then offset, then normalize output key.” [9](#0-8) 

### Proof of Concept
The following crate-local test demonstrates the divergence. It constructs an odd group key, obtains Serai’s output script, independently applies the BIP-341 order, and shows that the two watched scripts differ.

```rust
#[test]
fn odd_internal_key_uses_wrong_taproot_tweak() {
  use k256::{
    ProjectivePoint, Scalar, U256,
    elliptic_curve::{ops::Reduce, sec1::{Tag, ToEncodedPoint}},
  };
  use bitcoin::{hashes::Hash, TapTweakHash};
  use crate::{crypto::needs_negation, wallet::{tweak_keys, p2tr_script_buf}};

  // Generate or select ThresholdKeys whose group_key() is odd.
  let keys = odd_group_key_threshold_keys();
  let p = keys.group_key();
  assert!(bool::from(needs_negation(&p)));

  // Serai's implementation.
  let serai_keys = tweak_keys(keys.clone());
  let serai_script = p2tr_script_buf(serai_keys.group_key()).unwrap();

  // BIP-341: use the even representative of the x-only internal key.
  let internal_even = -p;
  let tweak_hash = TapTweakHash::hash(
    &internal_even.to_encoded_point(true).as_bytes()[1 ..],
  );
  let tweak = Scalar::reduce(U256::from_be_bytes(
    *tweak_hash.to_raw_hash().as_ref(),
  ));

  let mut standard_output = internal_even + (ProjectivePoint::GENERATOR * tweak);
  if bool::from(needs_negation(&standard_output)) {
    standard_output = -standard_output;
  }
  let standard_script = p2tr_script_buf(standard_output).unwrap();

  assert_ne!(serai_script, standard_script);
}
```

A Bitcoin transaction paying `standard_script` will not appear in `Scanner::scan_transaction` for the tweaked Serai key because the scanner indexes only `serai_script` and its registered offsets. [10](#0-9) [7](#0-6)

  // Adds the unspendable script path per

  let keys = {
    use k256::elliptic_curve::{
      bigint::{Encoding, U256},
      ops::Reduce,
      group::GroupEncoding,
    };
    let tweak_hash = TapTweakHash::hash(&keys.group_key().to_bytes().as_slice()[1 ..]);
    /*
      https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki#cite_ref-13-0 states how the
      bias is negligible. This reduction shouldn't ever occur, yet if it did, the script path
      would be unusable due to a check the script path hash is less than the order. That doesn't
      impact us as we don't want the script path to be usable.

      *tweak_hash.to_raw_hash().as_ref(),
