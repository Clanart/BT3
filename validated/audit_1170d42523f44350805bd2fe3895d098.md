### Title
`ReceivedOutput::read` deserializes unverified (offset, script_pubkey, outpoint) tuples, allowing fabricated "spendable" outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts a scalar `offset`, a `TxOut`, and an `OutPoint` entirely from the input byte stream and returns a `ReceivedOutput` documented as "A spendable output," without verifying that `output.script_pubkey` actually corresponds to `key + G * offset` for the scanning key, or that the claimed outpoint/script pairing is coherent. This is the same bug class as ALPINE-CVE-2021-29133: a missing verification step that lets an untrusted input cause the system to treat arbitrary attacker-chosen data as an authoritative object.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs:122-134`, `ReceivedOutput::read` performs three unchecked deserializations and returns the object:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...
outpoint = OutPoint::consensus_decode(&mut buf_r)...
Ok(ReceivedOutput { offset, output, outpoint })
```

Contrast with the legitimate construction path, `Scanner::scan_transaction` (lines 199-214), which only produces a `ReceivedOutput` after `self.scripts.get(&output.script_pubkey)` proves the script was registered under that offset for the scanner's key. The `read` path skips this binding entirely:

- The `offset` is not verified against `output.script_pubkey`. An attacker can supply any `offset` so that the derived spend key (`script_key - G*offset`, or equivalently `group_key + offset` used at signing time) is attacker-influenced.
- The `outpoint` is not verified to reference a real UTXO, nor that the claimed `TxOut` matches the outpoint's contents on-chain.
- There is no check that `script_pubkey` is even a P2TR output; consumers such as `Output::key()` assume it and derive the key from the embedded x-only key minus `G * offset`.

When these bytes are consumed downstream (e.g., `SignableTransaction::new` sums `input.output.value` and builds `TxIn`s from `input.outpoint`, and the per-input offset re-keys the FROST signing commitment), the attacker controls the claimed value, the claimed UTXO, and the effective signing key tweak for that input.

### Impact Explanation
An unprivileged party who can feed bytes into `ReceivedOutput::read` (a whitelisted untrusted-bytes entry point) can fabricate a `ReceivedOutput` that:

- Claims ownership of any outpoint on the chain with any value, causing funds to be reported as received/credited to the multisig that are not spendable by it — including pointing at real UTXOs belonging to third parties.
- Decouples `offset` from `script_pubkey`, so the spend key derived for the input does not match the key that actually controls the on-chain output. A transaction built and threshold-signed over such an input is unspendable/invalid, while the balance was already credited — the accepted "funds reported received that are not spendable" outcome.
- Alternatively, crafts `offset`/`script_pubkey` pairs so the derived key equals the multisig group key for an output that is not actually locked to the multisig, producing signatures over unintended input sets.

### Likelihood Explanation
Reachability is limited to contexts where serialized `ReceivedOutput`s transit trust boundaries (e.g., persisted outputs re-read from storage, or output descriptors relayed between components). Within those contexts the attack needs only byte-level control of the serialized object — no collusion, no malicious validator, no broken BFT. The cryptographic primitive itself is sound; the flaw is purely the missing structural verification on deserialization. Rated Medium: the fabricated output cannot directly steal funds (the real script_pubkey still gates on-chain spendability), but it corrupts credited balances and can stall or misdirect multisig spends.

### Recommendation
Add a verifying constructor/read that takes the scanner key (or the registered `ScriptBuf → offset` map) and rejects any `ReceivedOutput` where `output.script_pubkey` is not a P2TR script whose x-only key equals `key + G * offset` (i.e., `output.script_pubkey == p2tr_script_buf(key + G * offset)`). Downstream consumers should reject `ReceivedOutput`s not produced through `Scanner::scan_transaction`/`scan_block` or the verifying read.

### Proof of Concept
```rust
// Attacker-controlled bytes: offset = 0, a TxOut paying to the multisig's
// external script, but an outpoint naming someone else's real UTXO.
let mut bytes = Vec::new();
bytes.extend(Scalar::ZERO.to_bytes());                       // offset
bytes.extend(serialize(&TxOut {
    value: Amount::from_sat(1_000_000),
    script_pubkey: p2tr_script_buf(group_key).unwrap(),      // looks like ours
}));
bytes.extend(serialize(&OutPoint::new(victim_txid, 0)));     // not ours

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// forged.value() == 1_000_000 credited; forged.outpoint() names a UTXO the
// multisig cannot spend. No error is raised because no verification occurs.
```
