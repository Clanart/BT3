### Title
Deterministic `CachedPreprocess` reuse across repeated signing calls leaks the FROST secret share (nonce reuse / "use-after-consumed" analog of CVE-2021-30548 UAF) - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
CVE-2021-30548 is a use-after-free: an object is consumed/freed and then used again. The direct Serai analog is a **one-time-use cryptographic object used more than once**: the FROST preprocess seed (`CachedPreprocess`). The DKG-confirmation signing protocol stores the preprocess seed in the DB keyed only by `context = (b"DkgConfirmer", attempt)` and regenerates identical nonces `(d, e)` on every subsequent call. `preprocess()`, `share()`, and `complete()` each rebuild a machine from that same seed, and `share()`/`complete()` accept externally supplied preprocess maps. Two signing operations under the same attempt that see different peer preprocess bytes (or a different message) reuse `(d, e)`, which is exactly the FROST nonce-reuse condition the code itself warns "enable[s] third-party recovery of your private key share" (`crypto/frost/src/sign.rs`, `CachedPreprocess` docs; `spec/cryptography/FROST.md` §Caching).

### Finding Description
In `SigningProtocol::preprocess_internal` (`coordinator/src/tributary/signing_protocol.rs:100-148`):

- If `CachedPreprocesses::get(txn, &context)` is empty, a fresh random seed is generated, XOR-encrypted, and stored (lines 123-135).
- On **every** call — including repeat calls — the stored seed is decrypted and passed to `AlgorithmSignMachine::from_cache` (lines 137-145), which feeds it into `ChaCha20Rng::from_seed` and re-derives the *same* nonces `d` and `e` (`crypto/frost/src/sign.rs:121-144`, `seeded_preprocess`).

Call graph that re-signs with the same nonces:

- `DkgConfirmer::share` → `share_internal` → `preprocess_internal` → `machine.sign(preprocesses, msg)` (lines 288-309).
- `DkgConfirmer::complete` → **calls `share_internal` a second time** (line 322), re-signing the message with the same cached nonces, then aggregates shares.

Each of `share` and `complete` takes an independent `preprocesses: HashMap<Participant, Vec<u8>>` argument populated from network messages (after `threshold_i_map_to_keys_and_musig_i_map`). Nothing verifies that the preprocess set used in `complete` is identical to the one used in `share`. FROST signature shares have the form `s_i = d_i + e_i·ρ_i + c·λ_i·share_i`. If the peer preprocess map differs between the two calls, the per-participant binding factor `ρ_i` changes while `d_i`, `e_i`, `c` (same message) and `λ_i` stay fixed:

```
s1 - s2 = e_i·(ρ1 - ρ2)        →  e_i = (s1 - s2)/(ρ1 - ρ2)
d_i     = s1 - e_i·ρ1 - c·λ_i·share_i   (still unknown share)
share_i = (s1 - d_i - e_i·ρ1)/(c·λ_i)
```

With `e_i` recovered from the difference, `d_i` follows, and then the long-lived secret share `share_i` is solved linearly. The same leak occurs if `removed`/`key_pair` (and hence `msg`/`c`) differs between two calls for the same `attempt`, since the nonces are still identical — classic two-message Schnorr nonce reuse: `share_i = (s1 - s2)/((c1 - c2)·λ_i)` when `ρ` is unchanged, or a 2×2 linear solve otherwise.

The file's own header acknowledges this is the load-bearing safety assumption: "it is explicitly unsafe to reuse nonces across signing sessions" and "to ensure a rebuilt service isn't flagged as malicious, we have to check the commitments generated from the decided nonces are in fact its commitments on-chain **(TODO)**" plus a second TODO to "implement the same on-chain-preprocess-matches-presumed-preprocess check before publishing shares" (`signing_protocol.rs:25-54`). Those checks are unimplemented, and `share()`/`complete()` provide a second in-protocol signing path under the same context that the BFT-ordering argument does not cover.

### Impact Explanation
The key being signed with is the coordinator's MuSig validator key — the root of trust used to confirm new validator set key pairs on Substrate (`musig_context`, `set_keys_message`). Recovery of a validator's share lets an attacker participate in/forges the `set_keys` confirmation signature, which installs attacker-controlled threshold keys for the next validator set. That is a full compromise path to custody of all bridged funds controlled by the set's Bitcoin/Substrate keys. Severity: **Critical/High**.

### Likelihood Explanation
Requires two `share_internal` invocations for the same `(b"DkgConfirmer", attempt)` context where either (a) the preprocess map differs, or (b) the signed message differs (different `removed` set or `key_pair`). Reachable surfaces:

- `share()` then `complete()` are separate calls each accepting a separately supplied preprocess map; a peer who publishes a *second* valid preprocess (or whose preprocess is remapped differently by `removed` changes between the calls) flips `ρ_i` while nonces stay fixed.
- Any retry path where `share()` is invoked again for the same attempt (the function is not guarded by an "already signed" flag — unlike `batch_signer.rs`, which at least tracks `AttemptDb`/`CompletedDb`).

An unprivileged validator can feed arbitrary preprocess bytes via `read_preprocess`, controlling `ρ_i`. Likelihood is gated by needing the coordinator to execute two share-generating passes per attempt, which the `share`/`complete` structure provides; medium.

### Recommendation
- Consume the cached preprocess: delete `CachedPreprocesses[context]` in `share_internal` *before* calling `machine.sign`, and fail closed if it is absent (prevents `complete`'s re-sign and any retry from reusing nonces).
- Persist the exact serialized preprocess map used for the first `sign` and require byte-equality on any subsequent `share`/`complete` call for the same context (the TODO'd "on-chain-preprocess-matches-presumed-preprocess" check).
- Include a binding to the message/`key_pair`/`removed` in the `context` key so distinct messages can never share a nonce domain.

### Proof of Concept
1. For `attempt = k`, a validator set member causes `DkgConfirmer::share(preprocesses_A, key_pair)` to run: coordinator loads cached seed, derives `(d, e)`, emits `s1 = d + e·ρ1 + c·λ·share_i`.
2. The same participant causes `complete(preprocesses_B, key_pair, shares)` where `preprocesses_B` is identical to `preprocesses_A` except the attacker's own preprocess bytes differ (still parses via `read_preprocess`). `share_internal` re-derives the same `(d, e)` and emits `s2 = d + e·ρ2 + c·λ·share_i` (same `msg` ⇒ same `c`; `λ` unchanged if the signer set is unchanged).
3. `ρ1`, `ρ2` are public (recomputed from `hash_binding_factor` over the preprocesses the attacker themselves supplied). Solve `e = (s1 − s2)/(ρ1 − ρ2)`, then `share_i = (s1 − d − e·ρ1)/(c·λ)` with `d = s1 − e·ρ1 − c·λ·share_i` substituted — recover the validator's MuSig secret share and forge future `set_keys` confirmations.
