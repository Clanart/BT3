Confirmed: `StreamingYieldVault` is deployed in production and used by Simplex fillers as a live stablecoin treasury (e.g. `ycNGN` on Base per `config-mainnet.json`), and its `remaining`/`maxWithdraw`/`previewRedeem` accounting in `VaultLiquidityState.ts` is trusted to plan real fund withdrawals. This makes the accounting flaw in the vault's `totalAssets()` a real, fund-affecting local analog to the reported bug class.

### Title
Direct token transfers to `StreamingYieldVault` bypass the vesting lock and instantly inflate `totalAssets`, defeating the anti-sniping guarantee - (File: `sdk/packages/core/contracts/vaults/StreamingYieldVault.sol`)

### Summary
The reported bug is a "balance-diff mistaken for revenue" class: a contract computes backing/accrued value from a raw token balance rather than from value it actually tracked as belonging to it, so anyone can inflate that computed value with an unsolicited direct transfer. `StreamingYieldVault` has the exact same broken invariant: `totalAssets()` is `asset.balanceOf(vault) − lockedYield`, where `lockedYield` is derived only from the internal `_vestingAmount`/`_vestingStart` state set by `addYield`/`onTransferReceived`. Any plain ERC-20 `transfer()` straight to the vault address is *not* tracked by `_vestingAmount`, so it is not subtracted out — it is counted as fully vested `totalAssets` in the very same block.

### Finding Description
`totalAssets()` [1](#0-0)  is:
```
return IERC20(asset()).balanceOf(address(this)) - _lockedYield();
```
`_lockedYield()` only masks the specific tranche amount that was armed through `addYield()` (which pulls funds via `safeTransferFrom` and then calls `_startVesting`) [2](#0-1)  or through the ERC‑1363 `onTransferReceived` hook, which is gated to `msg.sender == asset()` and `from == owner()` [3](#0-2) .

Nothing gates a bare `IERC20.transfer(vaultAddress, amount)` from an arbitrary, unprivileged account. Such a transfer raises `asset.balanceOf(vault)` immediately, and because `_lockedYield()` has no knowledge of it, the full amount is counted as unlocked `totalAssets()` in the same block. This directly violates the two invariants the contract's own documentation claims as its security model:
- "No instant jump. Adding yield never moves `totalAssets` in the same block" [4](#0-3) 
- "No yield sniping... a deposit and withdrawal in the same block observe an identical share price" [4](#0-3) 

Deposits are open whenever no tranche is vesting (`maxDeposit` returns `type(uint256).max` when `!_isVesting()`) [5](#0-4) . An attacker can, in the deposit window, in one transaction: (1) `deposit()` a large amount to mint shares at the pre-donation price, (2) `asset.transfer(vault, X)` directly (uncontrolled by any access check), which instantly raises `totalAssets()`/share price by `X` with zero vesting delay, then (3) `redeem()` immediately — capturing a share of `X` proportional to the attacker's now-inflated ownership, at the expense of the other legitimate holders who were present before the donation and had no chance to react (all inside one block, so no other party can intervene). This is the same "external balance mistaken for owned/vested value" defect as the CollateralManager report, just manifesting as an instant, uncontrolled totalAssets jump instead of an ERC‑4626 vault's yield.

This is distinct from — and not addressed by — the documented "first-depositor inflation attack" mitigation (decimals offset + seed‑and‑burn): that mitigation only protects a near-empty vault's first depositor from being diluted to zero shares. It does nothing to prevent an attacker with existing shares from using a same-block donation to redistribute the donated value toward themselves and away from other pre-existing holders, exactly reproducing the "yield sniping" the vault's whole design (`VEST`/`_lockedYield`) exists specifically to prevent.

### Impact Explanation
Funds held in this vault are real, production funds — the vault type is configured as a live treasury/yield source for Simplex fillers (`ycNGN` StreamingYieldVault entry on Base in `config-mainnet.json`, sourced/redeemed by `VaultLiquidityState`/`VaultFundingPlanner` which trust on-chain `previewRedeem`/`maxWithdraw` values). Because `totalAssets()` can be manipulated in a single transaction by any unprivileged address, an attacker holding shares can extract value that should accrue proportionally to all long-term holders (or to nobody until legitimately vested), directly causing loss of funds to other depositors/the treasury owner. This is a direct violation of "bridged assets... must move exactly once and only to the rightful beneficiary and amount," since donated capital is redirected disproportionately to the attacker's temporarily-inflated share position rather than being locked/vested as the design intends.

### Likelihood Explanation
High. The `transfer()` function is a standard universal ERC-20 entry point on any token; there are no allowlists or hooks preventing an arbitrary account from sending tokens to the vault contract address. The only requirement is that the vault is not mid-vest (deposits open), which per the design happens every cycle for at least `MIN_WINDOW` (2 hours) — a large, predictable, recurring window. No relayer, prover, governance, or admin involvement is needed; it is entirely a self-contained deposit → donate → redeem sequence executable by anyone with capital and existing (or freshly minted) shares.

### Recommendation
Do not derive `totalAssets()`/vesting state from the token's raw `balanceOf`. Track protocol-owned assets explicitly with an internal accounting variable (e.g., `uint256 private _accountedAssets`) that is incremented only through `addYield`/`onTransferReceived`/`deposit`/`mint` and decremented on `withdraw`/`redeem`, and compute `totalAssets()` as `_accountedAssets - _lockedYield()` instead of `asset.balanceOf(address(this)) - _lockedYield()`. This mirrors the CollateralManager fix (track owned shares/assets, not the vault's total observed balance) and fully removes the ability of an arbitrary direct transfer to affect the share price.

### Proof of Concept
1. Deploy `StreamingYieldVault` for asset `USDC`; seed-and-burn per documented deployment steps.
2. Wait until outside any vesting window (`maxDeposit(alice) == type(uint256).max`).
3. Alice (legitimate holder) has an existing deposit of `1,000e18`.
4. Attacker calls `vault.deposit(1,000,000e18, attacker)` to mint a large share position at the current (pre-donation) price.
5. In the same transaction/block, attacker calls `USDC.transfer(address(vault), 100,000e18)` directly (not through `addYield`).
6. `vault.totalAssets()` immediately increases by `100,000e18` — `_lockedYield()` returns 0 for this amount since it was never armed as a tranche.
7. Attacker calls `vault.redeem(attackerShares, attacker, attacker)` in the same block and receives back their principal plus a large share of the `100,000e18` donation, proportional to their share of `totalSupply` at redemption — value that other, pre-existing holders (e.g., Alice) never see because the attacker's shares dominate the pool at redemption time and the "donation" is captured entirely inside one block, contradicting the contract's documented "no instant jump / no same-block sniping" guarantees.
