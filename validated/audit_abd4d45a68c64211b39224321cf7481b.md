## Analysis

The bid-tx generator confirms the vulnerability: `bid.MaxGasPrice` is signed by the searcher (included in the EIP-712 `AuctionTx` typehash for v3.0) and passed on-chain via `EncodeAuctionCallData`, but the Kaia client (CN) itself never enforces it. The `BidTx` that the client builds for execution uses `tx.GasFeeCap()`/`tx.GasTipCap()` (the target transaction's fee values), completely independent of `bid.MaxGasPrice`, and `validateBid` in the bid pool checks only sender/blockNumber/bid-amount/data-size/gas-limit/signatures — never the `MaxGasPrice` cap.

### Title
Auction module never enforces searcher-signed `MaxGasPrice` cap when building or admitting bid transactions - ([File: kaiax/auction/impl/bid_pool.go], [File: kaiax/auction/impl/getter.go])

### Summary
Analogous to the UniV3Adapter issue where a user-facing slippage/price-protection parameter (`sqrtPriceLimitX96`) is hardcoded/ignored instead of being honored, the Kaia auction module (KIP-249) defines a searcher-signed protection parameter, `Bid.MaxGasPrice`, that is included in the EIP-712 signed payload and forwarded to the on-chain `AuctionEntryPoint` contract, but the client-side bid pool and bid-transaction builder never check or apply it.

### Finding Description
`auction.BidData` carries `MaxGasPrice *big.Int` and it is part of the v3.0 EIP-712 typehash (`auctionTypeV3`), meaning the searcher explicitly signs a cap on the gas price they are willing to pay for their bid to be executed: [1](#0-0) [2](#0-1) 

`EncodeAuctionCallData` forwards this `MaxGasPrice` to the v3.0 `AuctionEntryPoint` contract call data: [3](#0-2) 

However, when the CN builds the actual `BidTx` for a winning bid, `GetBidTxGenerator` derives `GasFeeCap`/`GasTipCap` purely from the target transaction (`tx.GasFeeCap()`, `tx.GasTipCap()`), with no reference to `bid.MaxGasPrice` at all: [4](#0-3) 

Furthermore, `BidPool.validateBid`, which is the sole gatekeeper for admitting a bid into the pool, checks sender-winner conflicts, block-number range, positive bid amount, data size, and call gas limit — it never inspects `bid.MaxGasPrice`: [5](#0-4) 

Because the base fee (via KIP-71/Magma dynamic pricing) or the target transaction's fee cap can rise between the time the searcher signs their bid and the block in which it is executed, the searcher has no client-side protection: the field they signed to protect themselves against fee-price movement is silently discarded by the very component (the CN) that assembles and submits the transaction on their behalf.

### Impact Explanation
A searcher/bidder who signs a bid with a specific `MaxGasPrice` under the reasonable assumption (backed by the KIP-249 EIP-712 schema and the v3.0 contract ABI) that the client will not execute their bid at a higher gas price is exposed to unbounded fee extraction: the proposer-controlled CN can (or, due to this bug, always will) submit the `BidTx` using whatever `GasFeeCap`/`GasTipCap` the target transaction happens to carry, regardless of the searcher's signed cap. This can cause the searcher to pay materially more in gas fees than they agreed to, which is a concrete instance of fee abuse enabled by ignoring a signed, on-chain-relevant protection parameter — reachable by any bidder submitting `auction_submitBid` and by any block proposer building the block.

### Likelihood Explanation
This is not a rare edge case — it happens on every v3.0-style bid that includes a non-trivial `MaxGasPrice`, since the check is structurally absent from both bid validation and bid-tx generation. Given normal KIP-71 base fee fluctuation, gas price at inclusion time frequently differs from the price at bid-signing time, making this reachable in ordinary operation, not merely under adversarial conditions.

### Recommendation
Enforce the searcher-signed `MaxGasPrice` at two points:
1. In `BidPool.validateBid`, reject bids (or bids that would currently exceed protection) where the current/next block base fee already exceeds `bid.MaxGasPrice`, mirroring how `bid.Bid` and other bounds are validated.
2. In `AuctionModule.GetBidTxGenerator` (`kaiax/auction/impl/getter.go`), cap the constructed `BidTx`'s `GasFeeCap`/`GasTipCap` at `bid.MaxGasPrice` (when set) instead of blindly inheriting the target transaction's fee cap, and fail/skip bid inclusion if the required fee to be included exceeds the searcher's signed cap.

### Proof of Concept
1. A searcher signs a v3.0 `AuctionTx` bid with `MaxGasPrice = X` via `auction_submitBid`, intending to cap their execution cost.
2. `BidPool.validateBid` admits the bid without checking `MaxGasPrice` against the current or projected base fee: [5](#0-4) .
3. The target transaction is included with a `GasFeeCap`/`GasTipCap` higher than `X` (e.g., due to KIP-71 base fee increase between bid signing and block building).
4. `AuctionModule.GetBidTxGenerator` builds and signs the `BidTx` using `tx.GasFeeCap()`/`tx.GasTipCap()` from the target transaction, ignoring `bid.MaxGasPrice` entirely: [4](#0-3) .
5. The searcher's bid transaction executes and pays gas fees exceeding their explicitly signed `MaxGasPrice`, with no client-side enforcement ever having been applied.

func EncodeAuctionCallData(bid *auction.Bid, version string) ([]byte, error) {

func (bp *BidPool) validateBid(bid *auction.Bid) error {
	blockNumber := bid.BlockNumber

	bp.bidMu.RLock()

	// Check if the auction tx is already in the pool.
	if _, ok := bp.bidMap[bid.Hash()]; ok {
		bp.bidMu.RUnlock()
		return auction.ErrBidAlreadyExists
	}

	// 1. The `bid.Sender` must not be in the winner list of the same block number if the new bid isn't equal to the previous bid.
	if bp.senderHasDifferentWinner(bid) {
		bp.bidMu.RUnlock()
		return auction.ErrBidSenderExists
	}
	bp.bidMu.RUnlock()

	curBlock := bp.Chain.CurrentBlock()
	if curBlock == nil {
		return auction.ErrBlockNotFound
	}

	// 2. The `bid.BlockNumber` must be in range of `[currentBlockNumber + 1, currentBlockNumber + allowFutureBlock]`.
	curNum := curBlock.NumberU64()
	if blockNumber <= curNum || blockNumber > curNum+allowFutureBlock {
		return auction.ErrInvalidBlockNumber
	}

	// 3. The `bid.Bid` must be greater than 0.
	if bid.Bid.Sign() <= 0 {
		return auction.ErrZeroBid
	}

	// 4. The data size must be less than the maximum limit.
	if uint64(len(bid.Data)) > BidTxMaxDataSize {
		return auction.ErrExceedMaxDataSize
	}

	// 5. The gas limit must be less than the maximum limit.
	if bid.CallGasLimit > BidTxMaxCallGasLimit {
		return auction.ErrExceedMaxCallGasLimit
	}

	// 6. The `bid.SearcherSig` and `bid.AuctioneerSig` must be valid.
	if err := bp.validateBidSigs(bid); err != nil {
		return err
	}

	return nil
}
