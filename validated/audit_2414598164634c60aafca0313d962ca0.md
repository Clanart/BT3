### Title
Hardcoded `msg.sender` as escrow-redemption beneficiary in `_fillCrossChain` breaks for solvers with asymmetric addresses across chains - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentGatewayV2.fillOrder()` routes cross-chain fills to `_fillCrossChain`, which delivers output tokens to the beneficiary on the destination chain, then dispatches a `RedeemEscrow` message back to the **source** chain to release the escrowed input tokens to the solver. The beneficiary of that redemption is hardcoded to `msg.sender` — the solver's address on the *destination* chain — with no way to specify a different source-chain payout address.

### Finding Description
In `_fillCrossChain`, the escrow release request is built as: [1](#0-0) 

```
bytes memory body = bytes.concat(
    bytes1(uint8(RequestKind.RedeemEscrow)),
    abi.encode(
        WithdrawalRequest({
            commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
        })
    )
);
```

This is functionally identical to the reported bug class: an address observed on one chain (`msg.sender`, the solver's fill-transaction sender on the destination chain) is baked in as the payout recipient address on a different chain (the source chain, where escrowed input tokens live), with the implicit and unenforced assumption that the solver controls the identical address on both chains.

`fillOrder` and `FillOptions` provide the caller no parameter to designate an alternate source-chain payout address — `_fillCrossChain` only reads `options.outputs`, `options.relayerFee`, and `options.nativeDispatchFee`: [2](#0-1) 

On the source chain, `onAccept` authenticates the request came from the registered peer gateway and then unconditionally releases the escrowed tokens to whatever address is embedded as `beneficiary` in the `WithdrawalRequest`: [3](#0-2) [4](#0-3) 

Solvers are routinely smart-contract wallets, multisigs, `SolverAccount` ERC‑4337/EIP‑7702 accounts (the docs describe a dedicated `SolverAccount` design for solvers), or deployed via CREATE with per-chain nonces — all cases where the solver's contract address legitimately differs between the destination chain (where it calls `fillOrder`) and the source chain (where the escrow payout lands). Since `beneficiary` is forced to equal the destination-chain `msg.sender`, the source-chain escrow redemption is sent to an address the solver may not control there.

### Impact Explanation
A solver using an Account Abstraction wallet, multisig, or any contract whose address is not identical across the source and destination chains will have its escrowed input-token reward on the source chain sent to an address it cannot access, resulting in permanent loss of the filled order's reward. This is a direct fund-loss condition triggered purely by normal, unprivileged usage (no malicious peer, relayer, or governance actor required), matching the bounty's "stealing or loss of funds" / "wrong beneficiary" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: any solver operating through a smart-contract wallet (increasingly common for solver infrastructure, including the project's own documented `SolverAccount` ERC‑4337/EIP‑7702 pattern) that fills a cross-chain order will trigger this path on every single cross-chain fill, since there is no way in the public `fillOrder`/`FillOptions` API to correct the beneficiary before the `RedeemEscrow` message is dispatched.

### Recommendation
Add an explicit, solver-specified `beneficiary` (or `recipient`) field to `FillOptions` used only for the cross-chain escrow-redemption payout, defaulting to `msg.sender` when unset for backward compatibility, and use that value instead of hardcoding `bytes32(uint256(uint160(msg.sender)))` when constructing the `RedeemEscrow` `WithdrawalRequest` in `_fillCrossChain`.

### Proof of Concept
1. Deploy the same solver logic contract at address `A` on the destination chain and address `B` (different nonce/deployment order) on the source chain — a realistic scenario for any CREATE-deployed or AA solver contract.
2. Solver calls `fillOrder()` on the destination chain from address `A`, delivering output tokens to the order beneficiary.
3. `_fillCrossChain` dispatches `RedeemEscrow` with `beneficiary = bytes32(uint256(uint160(A)))`.
4. On the source chain, `onAccept` → `_withdraw` sends the escrowed input tokens to address `A`.
5. Because the solver contract is deployed at address `B` (not `A`) on the source chain, the solver has no way to retrieve the escrowed tokens sent to `A` — permanent loss, mirroring the referenced `test_POC_HardcodedRecipient_Prevents_Multisig_Migration` scenario from the external report.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
