### Title
Legacy `pattern`-only Stop rules silently default to the `content` field, which is never populated for Stop events, making the rule a permanent no-op - ([File: plugins/hookify/core/config_loader.py])

### Summary
`Rule.from_dict` in `config_loader.py` infers a condition's `field` from `event` when only a legacy `pattern` key is present, but for any event other than `bash`/`file` (including `stop`) it defaults to `field='content'`. `RuleEngine._extract_field` in `rule_engine.py` never populates `content` for Stop events (it only recognizes `reason`, `transcript`, and `user_prompt`), so the resulting condition always evaluates to `None` and the rule can never match, regardless of how dangerous the actual Stop `reason`/`transcript` content is.

### Finding Description
When a `.claude/hookify.*.local.md` rule file has `event: stop` and a legacy `pattern:` key but no explicit `field`/`conditions`, `Rule.from_dict` infers the field via: [1](#0-0) 

Since `event == 'stop'` matches neither `'bash'` nor `'file'`, the `else` branch sets `field = 'content'` and builds `Condition(field='content', operator='regex_match', pattern=simple_pattern)`.

At evaluation time, `stop.py` loads `stop` rules and runs `RuleEngine.evaluate_rules`, which calls `_check_condition` → `_extract_field('content', tool_name='', tool_input={}, input_data=<Stop payload>)`: [2](#0-1) 

`'content'` is not in `tool_input` (empty for Stop events), it isn't one of the recognized Stop fields (`reason`, `transcript`, `user_prompt`), and `tool_name` is empty so none of the `Bash`/`Write`/`Edit`/`MultiEdit` branches apply either. The function falls through and returns `None`: [3](#0-2) 

Back in `_check_condition`, `field_value is None` short-circuits to `False`: [4](#0-3) 

Because `_rule_matches` requires *all* conditions to match, this single unmatchable condition makes the rule permanently unmatchable, and `stop.py`'s `main()` will silently emit `{}` (allow) for every Stop event no matter what the malicious `reason` or `transcript` contains: [5](#0-4) 

No error, warning, or validation is surfaced anywhere in `load_rule_file`/`load_rules`/`Rule.from_dict` to indicate that the field inference produced a dead condition — the rule loads successfully and is reported as "enabled," giving a false impression that Stop-time enforcement is active.

### Impact Explanation
This is a security-enforcement-bypass bug in the hookify plugin's own detection logic: any Stop-event rule authored with the natural/legacy shorthand (`event: stop` + `pattern:` only, without an explicit `field:`) never fires, regardless of how blatant the malicious `reason`/`transcript` text is. A defender who reasonably expects hookify to block or flag dangerous agent-stop reasons gets silent, permanent non-enforcement — undermining the trust boundary the plugin is meant to provide and letting malicious/undesired agent termination reasons or transcript content pass through unchecked.

### Likelihood Explanation
Highly feasible and deterministic: any user writing a Stop rule via the documented/legacy `pattern` shorthand without specifying `field: reason` or `field: transcript` explicitly hits this path every time — no attacker privilege escalation or special conditions are needed beyond authoring (or being tricked into using/copying) such a rule file. Given `bash` and `file` are the only two special-cased events, `stop` (and any other non-bash/file event) is silently mis-inferred.

### Recommendation
In `Rule.from_dict`, extend the field-inference logic to also handle `stop` explicitly (e.g., default to `reason` or require both `reason`/`transcript` conditions), and raise a validation warning/error in `load_rule_file` when a `pattern`-only rule's inferred field is not actually populated by `_extract_field` for the given event (e.g., maintain a whitelist of valid fields per event and reject/warn on mismatch at load time rather than failing silently at match time).

### Proof of Concept
Integration test (pytest-style) targeting `hookify`'s public loader + engine APIs:

```python
from hookify.core.config_loader import Rule, load_rule_file
from hookify.core.rule_engine import RuleEngine
import tempfile, os

RULE_MD = """---
name: block-bad-stop
enabled: true
event: stop
pattern: "malicious_marker"
action: block
---

Blocked dangerous stop reason.
"""

def test_legacy_stop_pattern_rule_is_unmatchable(tmp_path):
    rule_file = tmp_path / "hookify.test.local.md"
    rule_file.write_text(RULE_MD)
    os.chdir(tmp_path.parent)  # load_rule_file uses relative path
    rule = load_rule_file(str(rule_file))
    assert rule is not None
    # Inferred field is 'content', not 'reason'/'transcript'
    assert rule.conditions[0].field == 'content'

    engine = RuleEngine()
    malicious_input = {
        "hook_event_name": "Stop",
        "reason": "malicious_marker: agent is exfiltrating secrets",
    }
    result = engine.evaluate_rules([rule], malicious_input)
    # Bug: rule never matches even though malicious content is present
    assert result == {}  # currently passes, proving silent no-op instead of blocking
```

Expected fixed behavior: either `load_rule_file` should raise/warn that the inferred field is invalid for `event: stop`, or the rule should match and `result["decision"] == "block"`.
