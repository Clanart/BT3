### Title
Coinbase outputs reported as received/spendable despite being unspendable for 100 blocks - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in a block, including the coinbase transaction (`block.txdata[0]`). A coinbase output paying to a registered Serai script is returned as a `ReceivedOutput` — indistinguishable from a mature, spendable output — even though consensus rules forbid spending it for 100 blocks. This mirrors the GroupBuy bug class: a "contribution" (here, an incoming output) is accepted and recorded as usable balance, but the funds are locked until a future event (coinbase maturity) that the tracking code never models.

### Finding Description
`Scanner::scan_block` (networks/bitcoin/src/wallet/mod.rs:221-227) calls `scan_transaction` on `block.txdata` wholesale rather than `block.txdata[1 ..]`. `scan_transaction` (lines 199-214) matches any output whose `script_pubkey` equals a registered script and emits a `ReceivedOutput` carrying the spending offset, `TxOut`, and `OutPoint` — with no marker indicating immaturity. Any caller that feeds the returned outputs into a UTXO set will later construct a `SignableTransaction` (`networks/bitcoin/src/wallet/send.rs:150-256`) spending the immature outpoint. Such a transaction is consensus-invalid (`bad-txns-premature-spend-of-coinbase`); `sendrawtransaction`/block inclusion will fail until the coinbase matures. A code comment (lines 218-220) acknowledges the hazard, but the API still returns the output with no `is_coinbase` flag and `ReceivedOutput::read`/`write` (lines 122-141) persist it with no maturity data, so the immature output is durably tracked as spendable funds.

### Impact Explanation
Funds are reported received that are not spendable. Downstream, an immature `ReceivedOutput` can be selected as a plan input, producing a transaction the network will reject for up to ~100 blocks — locking the credited balance and any co-spent inputs' plans until maturity, and crediting deposits against value that cannot yet move.

### Likelihood Explanation
Requires a miner (or a pool operator) to place an output to a Serai P2TR script in a coinbase transaction. A miner can do this cheaply with a small output while collecting the reward to their own address, so triggering it is feasible but requires mining a block — low-to-moderate likelihood, with impact bounded by the coinbase output's value and the 100-block window.

### Recommendation
In `scan_block`, either skip `block.txdata[0]` entirely or tag `ReceivedOutput`s originating from the coinbase transaction (e.g., an `immature: bool` / `coinbase` flag serialized in `read`/`write`) so callers can exclude them from the spendable UTXO set until maturity.

### Proof of Concept
1. Register offset via `Scanner::register_offset`, obtaining a Serai P2TR `ScriptBuf`.
2. A miner mines a block whose coinbase pays amount `a` to that script.
3. `scanner.scan_block(&block)` returns `ReceivedOutput { offset, output, outpoint }` for the coinbase output with no indication of immaturity.
4. `SignableTransaction::new(vec![received], payments, change, None, fee)` succeeds and `multisig`/`sign`/`complete` produce a signed transaction spending the coinbase outpoint.
5. `sendrawtransaction` (or block template inclusion) rejects it: coinbase spends are invalid for 100 blocks — the "received" funds are locked despite being tracked.
