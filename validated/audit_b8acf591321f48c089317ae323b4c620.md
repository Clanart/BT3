### Title
Native tokens sent to the `rewards()` view in the distribution precompile are permanently stuck - (File: `precompiles/distribution/distribution.go`)

### Summary
The `distribution` precompile at `0x0000000000000000000000000000000000001007` exposes a `rewards(address)` view method. Unlike every other view/transaction method in this precompile, `rewards()` never validates that `msg.value == 0` and never routes any received native value through the payment-refund helper (`pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei`). Because the EVM's standard `CALL` semantics transfer `value` from the caller to the precompile's account before precompile logic executes, any usei/wei sent alongside a `rewards()` call is absorbed into the precompile address's balance and never returned or used — an exact analog of the Gitcoin Allo `allocate()` issue where native tokens sent to a strategy that doesn't handle them become stuck.

### Finding Description
In `precompiles/distribution/distribution.go`, the `Execute` dispatcher routes `RewardsMethod` directly to `p.rewards(ctx, method, args)` — notably `value` is not even passed as an argument: [1](#0-0) 

Every other read-only method in the same file calls `p.validateInput(value, args, N)`, which enforces `pcommon.ValidateNonPayable(value)` before proceeding: [2](#0-1) 

For example `params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, and `communityPool` all call `validateInput` and thus reject any non-zero `value`: [3](#0-2) 

`rewards()` itself performs no such check — it only validates argument length and proceeds straight to querying delegation rewards: [4](#0-3) 

This is also explicitly documented as a known quirk in the precompile's integration test suite: [5](#0-4) 

For comparison, transactional precompile methods that legitimately accept payment (e.g. `bank.sendNative`, `gov.deposit`, `wasmd.execute`) always call `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` to refund the value from the precompile's account back to the payer before re-debiting it correctly: [6](#0-5) [7](#0-6) 

`rewards()` has neither the non-payable guard used by all its sibling views, nor the payment-handling refund logic used by payable methods — it simply ignores `value`.

### Impact Explanation
Any EVM caller that mistakenly (or as a UI bug) attaches `msg.value > 0` to a `rewards(address)` call on the distribution precompile will have that usei/wei transferred to the precompile's Sei address as part of standard EVM `CALL` value-transfer semantics. Because the precompile logic performs no refund or accounting for this value, the funds remain stuck at the precompile's associated account and are effectively unrecoverable through this precompile's normal `withdraw*` paths, which only debit balances they explicitly track. This is a genuine permanent loss/freezing of user funds, matching the Medium severity of the reported analog.

### Likelihood Explanation
`rewards()` is a commonly-called, unauthenticated, value-agnostic view function intended to be used off-chain/staticcall style, but it is also directly reachable via a normal state-changing transaction with non-zero value from any EVM account (associated or not — it doesn't require sender association, only the `args[0]` delegator to be associated). Wallets/dApps that reuse a "value" field defaulting to non-zero, or scripts that mistakenly attach value to a read-style call, would trigger this without any special privilege — a single ordinary transaction is sufficient.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to `rewards()` (i.e., pass `value` into `p.rewards` from `Execute` and validate it, consistent with `validateInput` used by all sibling view methods `params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, and `communityPool`), rejecting any call carrying non-zero value before executing the query.

### Proof of Concept
1. Attacker/user calls the distribution precompile at `0x0000000000000000000000000000000000001007` via `rewards(delegatorAddress)` with `msg.value = 1 sei` (or any non-zero wei/usei amount) set on the EVM transaction.
2. `Execute` dispatches to `RewardsMethod` case, which calls `p.rewards(ctx, method, args)` without checking or forwarding `value`. [1](#0-0) 
3. Standard EVM value-transfer semantics for the `CALL` already moved the sent native balance to the precompile's account before `Execute` runs.
4. `rewards()` completes successfully, returning reward data, but never calls `HandlePaymentUsei`/`HandlePaymentUseiWei` to refund or account for the received value.
5. The sent usei/wei remains held by the precompile's account indefinitely, unreachable through any of the distribution precompile's withdraw functions.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}

func HandlePaymentUsei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper utils.BankKeeper, evmKeeper utils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Coin, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	if !wei.IsZero() {
		return sdk.Coin{}, fmt.Errorf("selected precompile function does not allow payment with non-zero wei remainder: received %s", value)
	}
	coin := sdk.NewCoin(sdk.MustGetBaseDenom(), usei)
	// refund payer because the following precompile logic will debit the payments from payer's account
	// this creates a new event manager to avoid surfacing these as cosmos events
	if err := bankKeeper.SendCoins(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, sdk.NewCoins(coin)); err != nil {
		return sdk.Coin{}, err
	}
	if hooks != nil {
		newCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))
		if hooks.OnEnter != nil {
			hooks.OnEnter(depth+1, byte(vm.CALL), evmKeeper.GetEVMAddressOrDefault(newCtx, precompileAddr), evmKeeper.GetEVMAddressOrDefault(newCtx, payer), []byte{}, GetRemainingGas(newCtx, evmKeeper), value)
		}
		if hooks.OnExit != nil {
			hooks.OnExit(depth+1, []byte{}, 0, nil, false)
		}
	}
	return coin, nil
