### Title
Native-token overpayment to `EvmHost.dispatch()`/`fundRequest()` is permanently lost — no dust refund unlike the audited `IntentGatewayV2` pattern - (File: `evm/src/core/EvmHost.sol`)

### Summary
The external report's core defect is: a fee-paying code path handles `msg.value` incorrectly, so value sent by an unprivileged user to pay a required cross-chain fee is not correctly accounted for, breaking the fund-flow invariant ("every native-token payment must end up either consumed for its purpose or refunded to the payer"). In Hyperbridge, the local analog is not a missing `payable` keyword (those functions are already `payable`), but a missing **refund of unused native token** after the Uniswap swap used to acquire `feeToken`, in `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()`.

### Finding Description
`EvmHost` accepts native token payment for dispatch fees and internally swaps it for the configured `feeToken` via `swapETHForExactTokens`, which by design only spends the exact amount of ETH needed to produce `post.fee` (or `get.fee`, or `amount`) output tokens and refunds any unused ETH to the **caller of the router**: [1](#0-0) [2](#0-1) [3](#0-2) 

In all three functions, the router call is made with `{value: msg.value}` inside `EvmHost` itself, so the router's leftover-ETH refund is sent back to `address(this)` (the `EvmHost` contract) — **not** to `_msgSender()`, the actual fee payer. None of these three functions subsequently forward any residual native balance back to the caller.

This is confirmed to be a known, deliberately-handled invariant elsewhere in the same codebase: the `IntentGatewayV2` / `ExtrinsicIntents.sol` / `IntrinsicIntents.sol` contracts explicitly track `msgValue` and refund any unspent native token to `msg.sender` after every swap or escrow operation, with dedicated tests verifying this behavior: [4](#0-3) [5](#0-4) 

`EvmHost.sol` has no equivalent refund logic in `dispatch()`/`fundRequest()`, meaning any ETH sent above what `swapETHForExactTokens` actually needs to buy `post.fee`/`get.fee`/`amount` worth of `feeToken` is silently retained by the `EvmHost` contract with no mechanism visible in these functions to return it to the payer.

### Impact Explanation
Any unprivileged user who pays dispatch fees in native token (the documented and encouraged "Native Token Payment" flow) permanently loses the difference between `msg.value` sent and the actual ETH cost of the swap whenever they cannot predict the exact swap price at execution time (price movement between quote and execution, minor overestimation for safety margin, etc.). This is a direct, unconditional loss of user funds triggered purely by normal usage of a public entrypoint — matching the bounty's "stealing or loss of funds" category. It requires no malicious relayer, prover, or governance actor.

### Likelihood Explanation
High. `dispatch()`, `dispatch(DispatchGet)`, and `fundRequest()` are the primary public entrypoints for paying Hyperbridge fees in native token, as documented and recommended throughout the SDK/docs. Users naturally add slippage margin above the `quote()`-returned amount since fees can move between quoting and execution, making overpayment a common, not edge-case, occurrence.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture and refund any residual native balance to `_msgSender()`/the intended payer — mirroring the pattern already implemented in `ExtrinsicIntents.sol`/`IntrinsicIntents.sol` (track remaining `msgValue`, or check `address(this).balance` delta before/after the swap, and forward the difference back with a low-level call, reverting on failure).

### Proof of Concept
1. User calls `IHyperFungibleToken`/any `HyperApp` helper that ultimately triggers `EvmHost.dispatch(DispatchPost memory post)` with `msg.value = X`, where `X` is intentionally larger than the currently required ETH cost to acquire `post.fee` worth of `feeToken` (e.g., quoted moments earlier, then gas/price moves favorably, or user pads for slippage safety as commonly recommended).
2. `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` executes at [6](#0-5) , spending only `Y < X` ETH and refunding `X - Y` back to `EvmHost` (the router's caller).
3. `dispatch()` proceeds and returns normally; the `X - Y` residual ETH remains stuck in `EvmHost`'s balance with no accounting entry (`FeeMetadata` only records `post.fee` in `feeToken`, not leftover native token) and no function in this flow to reclaim it for the original payer.
4. Compare with `IntentGatewayV2SameChainTest.testFillOrder_RefundsSolverExcessNativeToken` at [5](#0-4) , which proves the team's own standard for this exact scenario is a full refund — a standard not applied in `EvmHost`.

    /// @notice Solver overpaying native ETH on fillOrder gets the excess refunded.
    function testFillOrder_RefundsSolverExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6; // 1000 USDC
        uint256 outputAmount = 1 ether;
        uint256 overpayment = 0.5 ether;

        // User places order: USDC -> ETH
        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(0), amount: outputAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;

        // Solver fills with overpayment
        TokenInfo[] memory solverOutputs = new TokenInfo[](1);
        solverOutputs[0] = TokenInfo({token: bytes32(0), amount: outputAmount});

        uint256 solverBalBefore = solver.balance;

        vm.prank(solver);
        intentGateway.fillOrder{value: outputAmount + overpayment}(
            order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: solverOutputs})
        );

        // Solver should only have spent outputAmount, overpayment refunded
        assertEq(solver.balance, solverBalBefore - outputAmount, "Solver overpayment should be refunded");
    }
