### Title
`clone()` explicitly disables Git's clone-time hook/symlink protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) while doing recursive submodule clones - (File: `app/src/lib/git/clone.ts`)

### Summary
Git added the `GIT_CLONE_PROTECTION_ACTIVE` safety mechanism (introduced alongside the fix for the "malicious repository can run hooks during clone/checkout of recursive submodules" class of bugs, e.g. CVE-2024-32004/32020/32021/32465-era hardening) so that when a clone recurses into submodules, Git refuses to follow attacker-controlled configuration/symlinks (such as a submodule whose `.git` is a symlink pointing at a location containing an executable `hooks/post-checkout` or similar) that would otherwise let a cloned repository execute arbitrary code as part of the clone/checkout sequence. GitHub Desktop's `clone()` function unconditionally sets this variable to `'false'` for every clone it performs.

### Finding Description
`clone()` builds its execution environment like this: [1](#0-0) 

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c', `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
```

The broken invariant is: *content coming from an untrusted, attacker-controlled remote repository (including nested submodules referenced by that repository) must never be able to run code or influence filesystem operations during the clone itself.* Git's own clone-protection guard exists specifically to enforce this invariant for the `--recursive`/`--recurse-submodules` path, where a malicious top-level repository can point a submodule at crafted paths (symlinks, embedded `.git` directories, or hook-bearing directories) that get followed during recursive checkout. By force-setting `GIT_CLONE_PROTECTION_ACTIVE=false` in the child process environment for *every* clone (there is no gating on trust level, source, or user opt-in), Desktop removes this guard for all clones performed through the app, including cloning arbitrary third-party/public repositories a user is onboarded into (via URL paste, "Clone repository" dialog, or the `x-github-client://` deep-link/CLI clone path shown in `app/src/cli/main.ts` and `app/src/main-process/main.ts`).

This is the same bug class as the external report's root cause: an attacker-supplied object (there, a claim hook; here, a submodule/`.git` reference inside a cloned repository) is allowed to run/be followed in a context where the invariant "attacker input cannot re-enter/redirect trusted execution" is supposed to hold, and the existing guard that was built specifically to prevent this (there: gas-limited hook + `onlyClaimer`; here: `GIT_CLONE_PROTECTION_ACTIVE`) is bypassed/disabled by the surrounding code rather than actually enforced.

### Impact Explanation
If Git's clone-protection guard is meant to stop a crafted repository/submodule structure from causing hook execution or out-of-tree file writes during `--recursive` clone, disabling it removes that mitigation across the entire application for every repository a user clones — this is exactly the "attacker controls a cloned/fetched repository ... result is code execution [or] file write ... outside the repo" impact category called out as valid in this task. Since GitHub Desktop is explicitly a tool for cloning arbitrary/untrusted third-party repositories (its core use case), the blast radius is every clone operation, not an edge case.

### Likelihood Explanation
Likelihood is high in terms of reachability: `clone()` is the single code path used for all UI-driven clones, CLI `github clone` invocations (`app/src/cli/main.ts`), and protocol-launcher/deep-link clones (`x-github-client://`, handled in `app/src/main-process/main.ts`), and the disabling flag is unconditional — there is no code path in `clone.ts` where `GIT_CLONE_PROTECTION_ACTIVE` remains enabled. The remaining uncertainty is the exact current Git-version behavior/semantics of `GIT_CLONE_PROTECTION_ACTIVE` (this couldn't be independently re-verified against the embedded `dugite`/Git binary version bundled with this build), so the practical exploitability depends on which underlying Git release ships with this build and what protections that variable currently gates.

### Recommendation
Do not disable `GIT_CLONE_PROTECTION_ACTIVE` for normal clones. If it was disabled to work around a specific compatibility issue (e.g. progress parsing or `--recursive` behavior), scope the override narrowly, document the exact Git bug/version it works around, and re-enable the protection once the embedded Git version no longer needs the workaround. At minimum, add a regression test cloning a crafted repository with a malicious submodule reference (symlinked `.git`, embedded hooks) to confirm no hook execution or out-of-tree writes occur.

### Proof of Concept
Conceptual reproduction (requires validating against the exact bundled Git/dugite version, which is outside what could be confirmed via static code search):
1. Create a "victim" repository containing a `.gitmodules` entry pointing a submodule to a crafted path/symlink structure known to trigger the hook-execution issue that `GIT_CLONE_PROTECTION_ACTIVE` was designed to prevent in the target Git version.
2. Have a user clone this repository through GitHub Desktop's normal "Clone repository" flow (which invokes `clone()` in `app/src/lib/git/clone.ts` with `--recursive`).
3. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'`, the guard that would otherwise abort/sanitize the risky submodule structure is bypassed, and the embedded hook/script executes (or writes outside the intended clone directory) as part of the clone, with no additional user action beyond clicking "Clone."
```typescript
export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
```
