## Title
Out-of-order delivery of unordered `PostRequest` governance messages lets stale parameters silently overwrite newer ones — `PaymasterUpdateParams` / `SetHostParam` / `SetTiers` absolute-overwrite handlers - (File: `evm/src/utils/SimplexPaymaster.sol`, `evm/src/core/HostManager.sol`, `evm/src/apps/BandwidthManager.sol`)

### Summary
The external report's core broken invariant is: a system accepts a cross-chain message that **unconditionally overwrites** a cumulative/absolute on-chain value, with no check that the incoming update is newer than what is already stored, while the underlying transport (Optimism's Cross Domain Messenger) permits messages to be replayed/delivered in **any order** by anyone. Hyperbridge's ISMP transport has the identical property for `PostRequest`s: each request is committed and delivered independently (keyed by its own commitment hash), and delivery to the destination is performed by permissionless relayers with no protocol-level guarantee that two distinct requests from the same source/module land in dispatch order. Several `onAccept` handlers on Hyperbridge apps perform **absolute overwrites** of governance/administrative state from decoded request bodies without any monotonic sequence check, exactly mirroring the `l1BurntAmountOf[...] = totalAmountBurntOnL1` pattern that caused the original bug.

### Finding Description
`SimplexPaymaster.onAccept` (dispatch site in `modules/pallets/intents-coprocessor/src/lib.rs`, `update_paymaster_params`) applies `RequestKind::PaymasterUpdateParams(params)` by decoding a full `Params` struct — including `treasury`, `markupBps`, `nativeOracle`, `maxOracleAge`, `swapSlippageBps` — and assigning it wholesale, replacing the entire previous configuration [1](#0-0) . Likewise `HostManager.onAccept` applies `SetHostParam` by calling `IHostManager(_params.host).updateHostParams(hostParams)` with a full `HostParams` struct decoded from the message body [2](#0-1) , and `BandwidthManager.onAccept`'s `SetTiers` branch does `tierPrice[updates[i].tier] = updates[i].price` for each entry [3](#0-2) .

None of these handlers include a version/sequence field that is checked to be monotonically increasing before the write is accepted — unlike the `l1BurntAmountOf` fix the dHEDGE team implemented, none of these three governance paths defend against reordering. Each `PostRequest` dispatched from Hyperbridge's governance pallets is committed independently in `pallet_ismp::child_trie::RequestCommitments` and delivered to the destination by whichever relayer submits first; delivery is not sequenced against other requests to the same module (the `nonce` field on a `PostRequest`, as documented, is only "a monotonically increasing nonce" used for commitment uniqueness/replay-protection at dispatch time, not a destination-side ordering gate — see the `PostRequestEvent`/tracking docs describing `nonce` purely as a per-request field for hashing) [4](#0-3) . Delivery order across distinct commitments is controlled entirely by permissionless relayer submission timing, which the design explicitly acknowledges elsewhere (e.g. the outbound-request-incentivization doc notes "There is a first-wins race on the destination side: whichever relayer lands the delivery transaction first...") [5](#0-4) .

Concretely: if Hyperbridge governance issues two successive `update_paymaster_params` calls — e.g., first to rotate `treasury` away from a compromised/incorrectly-configured address, then later corrections — an ordinary relayer can deliver the *older* `PostRequest` after the *newer* one lands, silently reverting `treasury` (and `markupBps`, oracle addresses, slippage tolerance) back to the stale value. Because `SimplexPaymaster.onAccept` only checks `request.source == hyperbridge()`, not any freshness/version field, both messages are individually valid and accepted, and the last-delivered one wins regardless of intended sequence. The same applies to `HostManager.updateHostParams` (which can change `hostManager`, `admin`, `feeToken`, `challengePeriod` wholesale) and to `BandwidthManager`'s per-tier price table.

### Impact Explanation
`SimplexPaymaster`'s `treasury` field controls where every markup surplus and EntryPoint deposit withdrawal is swept (`_withdrawAssets`) [6](#0-5) , and where recycled swap proceeds are deposited. If governance rotates `treasury` off a stale/compromised address and a relayer (with no special privilege beyond normal permissionless delivery) later delivers the earlier `PaymasterUpdateParams` message, the treasury silently reverts to the old address, redirecting future protocol fee sweeps to the wrong beneficiary — a direct fund-misdirection with no additional authentication bypass required. `HostManager.updateHostParams` similarly controls `feeToken` and `hostManager` addresses used for relayer/governance withdrawals via `IHostManager(_params.host).withdraw(...)` [7](#0-6) , so a reordered `SetHostParam` delivery can revert withdrawal routing parameters to a stale configuration, again misdirecting funds without any relayer/prover compromise.

### Likelihood Explanation
No malicious relayer, prover, or admin key compromise is required — any permissionless, honest relayer choosing to submit a queued/backlogged message after a newer one (e.g., due to retry after a transient RPC failure, congestion, or simply picking up an older unprocessed commitment from the mempool of pending ISMP deliveries) triggers the overwrite. Because Hyperbridge's own documentation acknowledges delivery order across distinct request commitments is a race determined by relayer submission timing, this is a native protocol property, not an edge-case assumption. The likelihood is proportional to how often governance issues back-to-back parameter updates to the same module (which does happen operationally — e.g. sequential `set_tier`/`dispatch_set_tiers` calls, or successive `update_paymaster_params` during incident response).

### Recommendation
Add an explicit monotonic sequence/version number to each of these governance-update payload types (`PaymasterParams`, `HostParams`, `SetTiers`), have the pallet increment it on every dispatch, and have each `onAccept` handler reject any incoming update whose sequence number is not strictly greater than the last one applied — mirroring exactly the `l1BurntAmountOf` monotonicity check added in the referenced fix. Store the last-applied sequence number per module/state-machine and compare-and-reject rather than compare-and-overwrite.

### Proof of Concept
Conceptual reproduction (matches the referenced PoC's structure):
1. Governance calls `update_paymaster_params(EVM(x), ParamsA)` where `ParamsA.treasury = OLD_TREASURY` (dispatch commitment `C1`).
2. Governance immediately calls `update_paymaster_params(EVM(x), ParamsB)` where `ParamsB.treasury = NEW_TREASURY` (dispatch commitment `C2`), intending this to be the final state.
3. A relayer, due to normal network conditions (retry, backlog, RPC hiccup), delivers `C2` to the `SimplexPaymaster` on EVM chain `x` first, then delivers the earlier-dispatched `C1` afterward — both are independently valid, distinctly-committed `PostRequest`s and `onAccept` places no ordering constraint between them.
4. After both deliveries, `SimplexPaymaster.treasury == OLD_TREASURY`, silently undoing the governance-intended rotation with no error emitted and no additional privilege needed by the relayer beyond ordinary message delivery.
5. Subsequent `swapAndDeposit`/`_withdrawAssets` calls route funds to `OLD_TREASURY` instead of the intended `NEW_TREASURY`, exactly mirroring the `l1BurntAmountOf` regression in the L2Comptroller report where the wrong absolute value silently won based on delivery order rather than intended sequence.

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }

## Open questions

1. **One commitment, one reward, regardless of message size.** The consensus claim is a flat per-destination value. Do we want the request claim flat too, or scaled by request body size? Flat is simpler and matches the creator's wording ("award BRIDGE tokens"). Recommend flat for v1 and revisit if operators report it under or overpaying.
2. **Payee account type.** Sr25519 only (matches consensus claim) or also support Ed25519 / EVM addresses on the payee side? Recommend Sr25519 only for v1.
3. **Claim ordering vs delivery race.** There is a first-wins race on the destination side: whichever relayer lands the delivery transaction first has its address written into `RequestReceipts[commitment]`, and every later delivery of the same commitment no-ops. The race winner is unambiguous because the receipt slot records exactly one address, and `process_outbound_request_delivery_claim` only pays the address proven in that slot, so a relayer that delivered second fails `OutboundRequestSignerMismatch`. Idempotency is automatic and no extra logic is needed, but operators should understand the reward goes to the fastest deliverer, not the first to claim.
4. **Treasury funding model.** The same `T::TreasuryPalletId` already used by the consensus claim. Governance tops it up. No new account.
