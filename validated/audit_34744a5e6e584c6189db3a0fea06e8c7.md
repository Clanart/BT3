## Title
Missing HTML/script-context escaping (`<`, `>`) in upb JSON encoder enables output-side script injection — ([File: upb/json/encode.c])

## Summary
NagVis's CVE-2017-6393 failed to filter user-supplied data before it was rendered into an HTML/JS context, allowing an attacker-controlled string to break out of its intended context and execute as script. Protobuf's own JSON encoders defend against exactly this class of bug: several official implementations deliberately escape `<` and `>` in string field values (in addition to the RFC-required JSON escapes) specifically because ProtoJSON output is commonly embedded verbatim into `<script>` blocks or JS literals by consuming web applications. The upb-based JSON encoder — which backs Python's C++/upb runtime, the PHP C extension, the Ruby C extension, and Lua bindings — omits this HTML-safety escaping, creating a cross-implementation inconsistency that reproduces the underlying invariant failure from the external report inside Protobuf's own supported public JSON-encoding surface.

## Finding Description
Three of Protobuf's official JSON writers explicitly escape `<`, `>` (and in Java's case `&`, `=`, `'`) as defense-in-depth against script injection when JSON is embedded in HTML:

- C++ core JSON writer: `MustEscape` treats `<`/`>` as must-escape, with comment "These are not required by the JSON spec, but help to prevent security bugs in JavaScript." [1](#0-0) 
- Java `JsonFormat`: escapes `<>&='` "to prevent XSS risks", with an explicit regression test `testHtmlEscape`. [2](#0-1) [3](#0-2) 
- C# `JsonFormatter`: "Escaping of < and > are required for HTML security." [4](#0-3) 

In contrast, the upb JSON encoder's character-escaping routine `jsonenc_put_escaped_char` only handles the RFC-mandated escapes (`\n`, `\r`, `\t`, `"`, `\f`, `\b`, `\\`) and control characters below `0x20`; any other byte, including `<` and `>`, is written through unmodified: [5](#0-4) 

This function is called unconditionally for every string field value via `jsonenc_stringbody`/`jsonenc_string`: [6](#0-5) 

The identical vulnerable routine is embedded (via amalgamation) in the PHP C extension: [7](#0-6) 

and in the Ruby C extension (`ruby-upb.c`), confirmed present via the same symbol names. This upb encoder backs `MessageToJson`/`json_format` for Python's upb-based runtime, PHP's `serializeToJsonString`, and Ruby's native JSON serialization — all official, supported public APIs that a consuming application calls after parsing attacker-controlled binary Protobuf or ProtoJSON input.

**Failed invariant transferred from the CVE**: user-supplied data must be neutralized before being placed into an HTML/script-consuming context. **Attacker-controlled value**: any string field populated from parsed binary/ProtoJSON input (e.g., `optional_string = "</script><script>evil()</script>"`). **Missing check**: `<`/`>` escaping, present in C++/Java/C# but absent in upb. **Impact**: when the application's JSON serialization path uses the upb backend and the resulting JSON is embedded into an HTML document or `<script>` block (a well-known and Google-documented protobuf-JSON usage pattern, which is exactly why the C++/Java/C# writers added this escaping), the unescaped `</script>` sequence breaks out of the script context, enabling arbitrary script execution in the victim's browser — the same class of impact as CVE-2017-6393.

## Impact Explanation
This is a Medium-severity, consumer-side script-injection primitive: the actual XSS execution occurs in a browser rendering the application's page, not inside Protobuf itself, so Protobuf's contribution is producing HTML-unsafe output where its sibling implementations deliberately produce safe output. The impact requires the "consuming-application exposure assumption" that the application places raw JSON encoder output into an HTML/JS-consuming context (a documented, common pattern this exact escaping was added to protect), consistent with why the C++/Java/C# maintainers treat `<`/`>` escaping as a security-relevant hardening measure rather than a cosmetic behavior. Confidentiality/Integrity impact is bounded to script-context confusion (matching the CVE's CVSS vector C:L/I:L/A:N).

## Likelihood Explanation
Likelihood is high for any application using Python's upb runtime, PHP, Ruby, or Lua bindings that serializes attacker-influenced message content to JSON and embeds it in HTML without additional application-level escaping — a reasonable expectation given that other official Protobuf JSON writers already perform this escaping unconditionally, so users of the upb-backed writers are likely unaware they lack this protection.

## Recommendation
Add `<`/`>` (and ideally the same character set already covered by the C++ `MustEscape`/Java `replacementChars` tables) escaping to `jsonenc_put_escaped_char` in `upb/json/encode.c`, and propagate the fix through the amalgamated/vendored copies in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`, so all officially supported JSON encoders apply consistent HTML-safety escaping.

## Proof of Concept
1. Define/parse a message with `optional string s = 1;` and set `s = "</script><script>alert(1)</script>"` via a bounded ProtoJSON or binary parse using upb (e.g. Python's default C++/upb backend, or the PHP extension).
2. Serialize with `MessageToJson`/`serializeToJsonString`, which routes through `jsonenc_string` → `jsonenc_put_escaped_char` in `upb/json/encode.c` (lines 268-317).
3. Observe the emitted JSON contains the literal, unescaped substring `</script><script>alert(1)</script>` rather than the `\u003c...\u003e` form produced by the equivalent C++ (`writer.cc`), Java (`JsonFormat.java`), or C# (`JsonFormatter.cs`) encoders for the same input, as demonstrated by Java's own regression test `testHtmlEscape` expecting `\u003c/script\u003e` output for an identical string. static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

static void jsonenc_string(jsonenc* e, upb_StringView str) {
  jsonenc_putstr(e, "\"");
  jsonenc_stringbody(e, str);
  jsonenc_putstr(e, "\"");
}
