### Title
Stale fork `parentID` reused when a `GitHubRepository` record is upserted with `ignoreParent=true`, silently redirecting fork contribution/push target - (`app/src/lib/stores/repositories-store.ts`)

### Summary
`RepositoriesStore._upsertGitHubRepository` resolves and persists `GitHubRepository` records keyed by `[ownerID+name]` [1](#0-0) . When the API data used to upsert doesn't include reliable parent information (`ignoreParent = true`, e.g. when loading pull requests or non-full API objects), the code deliberately reuses whatever `parentID` was already stored for that `[owner, name]` row instead of clearing it [2](#0-1) . This is the same "association not cleared on disassociation" pattern as the `_marketWeightsByToken` bug: a per-key mapping (`parentID`) that should reflect the *current* upstream relationship is instead left over from a *previous* state of the same `[ownerID+name]` slot.

### Finding Description
`GitHubRepository` rows are looked up by owner+name, not by a stable GitHub numeric repository id [1](#0-0) . If a repository under a given owner/name is deleted and later a different repository is created with the exact same owner and name (fully controllable by any GitHub account owner, including an attacker who owns the account), Desktop's local `existingRepo` lookup will match the *old* database row for that owner/name and inherit its fields.

The `parentID` field specifically is preserved rather than cleared whenever the upsert call doesn't carry authoritative parent data (`ignoreParent === true`) [3](#0-2) . The code comment explicitly acknowledges this is a deliberate but risky trade-off: *"Since going from having a parent to not having a parent is incredibly rare (deleting a forked repository and creating it from scratch again with the same name or the parent getting deleted, etc) we assume that the value we've got is valid until we're certain its not."* [4](#0-3) 

This `parentID` directly drives `GitHubRepository.parent`, which `getNonForkGitHubRepository`/`getForkContributionTarget` use to decide whether the "non-fork" contribution target for a repository is the repo itself or a **different, cached parent repository** [5](#0-4) . This value feeds fork-contribution routing used elsewhere in the app (dispatcher/pull-request/fork-settings flows), and a stale parent silently changes where "contribute to parent" actions are targeted, without any user-visible warning, because the app-level TODO in `app-store.ts` confirms associations are "currently never cleared" once established [6](#0-5) .

Existing guards do not stop this: `shallowEquals` short-circuiting in `_upsertGitHubRepository` only prevents redundant DB writes/emits when nothing "changed" per the comparison — it does not validate that a *stale* `parentID` is actually still correct, since the ignore-parent path never attempts to reconcile it against current data [7](#0-6) .

### Impact Explanation
If a local repository's `GitHubRepository` association resolves (via owner+name reuse) to a stale row that still carries an old `parentID`, contribution-target logic (`getNonForkGitHubRepository`) can silently point at the wrong upstream repository. Any Desktop feature relying on this (auto-adding the `upstream` remote via `GitStore.addUpstreamRemoteIfNeeded`, or determining the base repo for "contribute to parent" pushes/PRs) can be misdirected to a repository the user did not intend, which matches the "silent corruption of what the user commits or pushes" impact category. Because this is entirely driven by owner/name reuse (attacker fully controls their own account's repo lifecycle) with no user prompt or unusual steps required beyond normal interaction with the repository in Desktop, it is plausible without local/physical access or leaked credentials.

### Likelihood Explanation
Low-to-moderate. It requires: (1) the victim to have previously interacted with a fork whose parent got cached under a given `[owner, name]`, (2) that repository being deleted/recreated (or the name reused) by its owner, and (3) a subsequent upsert call that takes the `ignoreParent = true` path (loading PRs or a non-full API repository) rather than a full repository fetch that would recompute the parent. This is a narrower trigger window than the original report's "remove and re-add" reward token flow, but the root cause — an association keyed by a reusable identifier that isn't invalidated on disassociation — is structurally identical.

### Recommendation
Do not persist a previously known `parentID` across upserts unless the API response confirms the fork relationship still holds. When `ignoreParent` is used because the API payload lacks parent info, prefer treating parent status as "unknown-keep-until-next-full-fetch" but attach a freshness/verification check (e.g., re-verify via a full repository fetch before using `parentID` in contribution-routing decisions), or invalidate `parentID` when the underlying repo's other identifying attributes (e.g., `created_at`, `id` from GitHub) indicate it's not the same physical repository as before.

### Proof of Concept
1. Victim adds `attacker/repo` (a fork of `victim/upstream`) in Desktop; Desktop upserts a `GitHubRepository` row for `[ownerID=attacker, name=repo]` with `parentID` = `victim/upstream`'s dbID.
2. Attacker deletes `attacker/repo` and creates a brand-new, unrelated repository also named `repo` under the same account (no longer a fork of anything).
3. Victim later interacts with pull requests or other lightweight API objects referencing `attacker/repo`, triggering `upsertGitHubRepositoryLight`/`_upsertGitHubRepository(..., ignoreParent = true)` [8](#0-7) .
4. The lookup by `[ownerID+name]` matches the old DB row, and `parentID` is preserved from step 1 [3](#0-2) , so Desktop continues to treat the new, unrelated `attacker/repo` as a fork of `victim/upstream`, affecting `getNonForkGitHubRepository`/contribution-target resolution for any local repository pointing at it.

Note: I could not fully trace every downstream consumer of `getNonForkGitHubRepository` in this session (e.g., exact push/PR-creation call sites) due to the final-iteration constraint, so the precise blast radius (which specific push/PR flows are affected) should be verified with a background agent before treating this as fully confirmed exploitable.

export function getNonForkGitHubRepository(
  repository: RepositoryWithGitHubRepository
): GitHubRepository {
  if (!isRepositoryWithForkedGitHubRepository(repository)) {
    // If the repository is not a fork, we don't have to worry about anything.
    return repository.gitHubRepository
  }

  const forkContributionTarget = getForkContributionTarget(repository)

  switch (forkContributionTarget) {
    case ForkContributionTarget.Self:
      return repository.gitHubRepository
    case ForkContributionTarget.Parent:
      return repository.gitHubRepository.parent
    default:
      return assertNever(
        forkContributionTarget,
        'Invalid fork contribution target'
      )
  }
}

/**
 * Returns a non-undefined forkContributionTarget for the specified repository.
 */
export function getForkContributionTarget(
  repository: Repository
): ForkContributionTarget {
  return repository.workflowPreferences.forkContributionTarget !== undefined
    ? repository.workflowPreferences.forkContributionTarget
    : ForkContributionTarget.Parent
}
