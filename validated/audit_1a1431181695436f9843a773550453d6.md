### Title
Unvalidated `sender`/`recipient` participant indexes cause a HashMap-index panic (crash/DoS) in PedPoP blame evaluation - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame` and `AdditionalBlameMachine::blame` accept caller-supplied `sender` and `recipient` `Participant` values and pass them into `blame_internal`, which indexes `self.commitments[&sender]` and `self.commitments[&recipient]`-derived data without checking that the participant is a member of the DKG set. `Participant::new` only rejects `0`, so any `u16` in `1..=65535` is accepted. Supplying an index greater than `n` causes a `HashMap` index panic, crashing the process — an availability failure reachable purely through untrusted protocol inputs.

### Finding Description
The PedPoP DKG exposes public blame APIs intended to adjudicate accusations between participants:

- `BlameMachine::blame(self, sender, recipient, msg, proof)` [1](#0-0) 
- `AdditionalBlameMachine::blame(&self, sender, recipient, msg, proof)` [2](#0-1) 

Both route to `blame_internal`, which first calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` and then evaluates: [3](#0-2) 

`self.commitments` is keyed only by the actual DKG participants: for `AdditionalBlameMachine` it is built from `1 ..= n` [4](#0-3) , and for `BlameMachine` from `KeyMachine::calculate_share`, whose `commitments` map is populated solely from `all_participant_indexes()` [5](#0-4) . Indexing a `HashMap` with `map[&key]` panics on a missing key, and neither `blame` entry point validates `sender <= n` or `recipient <= n` before `blame_internal` runs. `Participant::new` accepts any nonzero `u16` [6](#0-5) , so e.g. `Participant(0xFFFF)` in a `n = 4` DKG reaches `self.commitments[&sender]` (line 599) and panics.

By contrast, the rest of the protocol defensively validates attacker-influenced index sets (`validate_map` on share/commitment maps, `MissingParticipant` errors, explicit `t`/`n`/`i` checks), so this panic is an omission rather than a documented contract: `blame` is documented to "determine the faulty party," with no precondition that `sender`/`recipient` be protocol members — the only caveat is that the `msg` be authenticated as originating from `sender`, which a forged index trivially sidesteps since no real sender is required to panic.

### Impact Explanation
Analogous to CVE-2023-21950 (a repeatable server crash → complete availability loss), any party able to submit a blame request to a node running PedPoP blame evaluation can crash the process with a single message naming a non-existent participant index (e.g., `sender = Participant(n+1)`). In a validator/coordinator deployment, an unprivileged counterparty or anyone who can route an accusation to the blame handler can repeatedly kill the node, aborting DKG completion and halting key generation/signing availability. This requires no valid shares, no threshold collusion, and no privileged position.

### Likelihood Explanation
Blame evaluation is the explicitly designed path for handling *disputed* protocol runs — i.e., it is invoked precisely when parties are already misbehaving or accusing each other. A malicious participant who wants to grief the protocol rather than be correctly blamed can simply name an out-of-range index; the blame API authenticates the accused `msg` against `sender`, but the panic occurs on map indexing of the accusation parameters themselves. The panic is deterministic and trivially triggered (no cryptographic work needed).

### Recommendation
In `blame_internal` (or in both `blame` wrappers), validate that `sender` and `recipient` are contained in `self.commitments` before indexing: use `self.commitments.get(&sender)` and return an error/`None` verdict (or treat an unknown index as the accuser's fault) instead of panicking. Additionally, `AdditionalBlameMachine::new` records `n` only implicitly via the commitments map; storing `n` on the machine would allow an explicit `sender <= n && recipient <= n` bounds check.

### Proof of Concept
```rust
// Given a completed KeyMachine -> BlameMachine for a DKG with n = 4,
// or an AdditionalBlameMachine::new(context, 4, commitment_msgs),
// any party submits a blame accusation with an out-of-range participant:

let bogus = Participant::new(0xFFFF).unwrap(); // nonzero, so accepted
let real  = Participant::new(2).unwrap();

// Either of these panics at self.commitments[&sender] in blame_internal:
//   crypto/dkg/pedpop/src/lib.rs:599
blame_machine.blame(bogus, real, msg_from_anyone, None);        // thread panics: HashMap index
additional_blame_machine.blame(bogus, real, msg_from_anyone, None);
```

The panic is reached before any cryptographic verification that could reject the input — `decrypt_with_proof` failing returns `sender`/`recipient` normally, but the subsequent `self.commitments[&sender]` lookup in `share_verification_statements` (line 599) is unconditional once decryption succeeds, and even on the failure paths a consistent out-of-range index reaches map indexing through the encryption/decryption path for `sender`. The result is a reliable, single-message crash of the blame-handling process.
