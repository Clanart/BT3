## Finding: path-mismatch between `git status -z` (unquoted, NUL-terminated) and `git diff --check` (quoted, newline-terminated) output can zero-out `conflictMarkerCount`

### Summary
`getFilesWithConflictMarkers` parses the plain, newline-delimited, quote-enabled output of `git diff --check` with the regex `/^(.+):\d+: leftover conflict marker/gm` and stores the resulting path strings as keys in a `Map<string, number>`. [1](#0-0) 

This map is later used purely as a lookup keyed by path taken from a *different* parser, `parsePorcelainStatus`, which explicitly consumes `git status --porcelain -z` output where "filenames containing special characters are not specially formatted; no quoting or backslash-escaping is performed." [2](#0-1) 

`git diff --check`, however, is invoked without `-z` and without any path-quoting suppression, so by default git will apply its normal C-style quoting/escaping for "unusual" filenames (non-ASCII bytes, whitespace, control characters, quotes, backslashes) in that output, unless `core.quotePath=false`. That means for a conflicted file whose name contains such characters, the key produced by `getFilesWithConflictMarkers` (quoted/escaped form) will not equal the `path` string produced by `parsePorcelainStatus` (raw, unescaped form).

### Where the mismatch surfaces
The conflict-marker count is looked up by exact path string equality in `parseConflictedState`: [3](#0-2) 

Because the lookup uses `conflictDetails.conflictCountsByPath.get(path) || 0`, if the map key (from `diff --check`, quoted) doesn't match `path` (from `status -z`, unquoted), the `.get()` call returns `undefined`, and the fallback `|| 0` reports **zero conflict markers** for a file that still has unresolved `<<<<<<<`/`=======`/`>>>>>>>` markers on disk.

### Impact
`conflictMarkerCount` feeds `hasUnresolvedConflicts` in `app/src/lib/status.ts`, which the UI uses to decide whether a conflicted file still needs manual resolution before it can be safely committed: [4](#0-3) 

If `conflictMarkerCount` is silently reported as `0` for a file that actually still contains conflict markers, GitHub Desktop's conflict-resolution UI (and the `CommitConflictsWarning` dialog gating) can treat the file as resolved and allow the user to commit and push a file that literally still contains raw `<<<<<<<`/`=======`/`>>>>>>>` conflict-marker text — i.e., the "silent corruption of what the user commits or pushes" described in the target's Valid Impact criteria.

### Likelihood
This requires an attacker-controlled repository/branch to introduce a conflicting file whose *path* contains characters that git quotes by default (non-ASCII, backslash, double-quote, whitespace/control chars), and for the victim's `core.quotePath` to be at its default (`true`). This is a plausible, low-effort scenario for a crafted malicious repo used to trigger a merge/rebase/cherry-pick conflict, and does not require any unusual local privileges — the untrusted repository content alone drives the path names on both sides of the mismatched parse.

### Recommendation
Make both parses of file paths from `git` consistent:
- Invoke `git diff --check` with `-z` (or otherwise disable path quoting, e.g. `-c core.quotePath=false`) and adjust the parsing regex/split logic to consume NUL-delimited records, matching the treatment already used for `git status -z` in `parsePorcelainStatus`.
- Alternatively, normalize/unquote paths from `diff --check` output (reversing git's C-style quoting) before using them as map keys, so they match the raw paths from `parsePorcelainStatus`.
- Add a fast validation test: create a conflicted file with a path containing a character git quotes by default (e.g. a filename with an embedded double quote, backslash, or non-ASCII byte), and assert `getFilesWithConflictMarkers`'s returned key matches the exact `path` string reported by `parsePorcelainStatus`/`getStatus` for the same file, and that `conflictMarkerCount` is non-zero.

### Proof of Concept (conceptual, not verified by execution in this session)

/**
 * Determine if we have any conflict markers or if its been resolved manually
 */
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
