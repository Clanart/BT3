### Title
Unchecked u64 arithmetic on attacker-influenced amounts causes overflow panic / invalid signed transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` performs plain (non-checked) `u64` addition and multiplication on values derived from caller-supplied payment amounts and the fee rate (`payment_sat + needed_fee`, `fee_per_vbyte * vbytes`). This mirrors CVE-2017-7961's class — numeric values outside the representable range of the target type producing a crash — mapped onto Serai's Rust shape where overflow panics in debug and wraps in release. [1](#0-0) 

### Finding Description
Three unchecked operations exist on externally influenced integers:

1. `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();` — the sum of payment amounts, which are supplied per-payment by the caller and can each be up to `u64::MAX`. [2](#0-1) 
2. `let mut needed_fee = fee_per_vbyte * vbytes;` — `fee_per_vbyte` is an unconstrained `u64`; on the processor path it derives from `self.median_fee(&block_for_fee)`, i.e. data taken from a chain block. [3](#0-2) [4](#0-3) 
3. `if input_sat < (payment_sat + needed_fee)` — the solvency check adds two unchecked `u64`s. In release builds this can wrap to a small value, defeating the `NotEnoughFunds` check. The later `input_sat.checked_sub(payment_sat + fee_with_change)` in the change branch wraps identically before the `checked_sub`. [5](#0-4) 

In debug builds any of these panics (DoS of the signing process). In release builds, a wrapping `payment_sat + needed_fee` lets `new` succeed while producing a transaction whose outputs exceed its inputs, and `SignableTransaction::fee()` then underflows (`sum(inputs) - sum(outputs)` at line 139). [6](#0-5) 

### Impact Explanation
- Crash/DoS: a payment set whose summed amounts (or a fee rate × vbytes product) exceeds `u64::MAX` panics the transaction-construction path, which the processor treats as fatal — `make_signable_transaction` panics on most `TransactionError`s and an arithmetic panic aborts signing entirely. [7](#0-6) 
- If wrap-around occurs instead, the threshold multisig proceeds to sign a transaction that is consensus-invalid (outputs > inputs), permanently stalling those inputs' withdrawal plan until manual intervention.

### Likelihood Explanation
Payment amounts and fee rate are the public-input analogue of the CVE's crafted CSS numeric tokens: withdrawal payment amounts originate from user-submitted requests, and `fee_per_vbyte` originates from block fee data (`median_fee`). Reaching the wrap requires a total payment sum near `u64::MAX` or a fee rate of ~`u64::MAX / vbytes`, which upstream balance checks may bound — this limits likelihood. The panic variant (debug builds, or via `TryFrom` unwraps such as `u64::try_from(...).unwrap()` at lines 121–125) is reachable whenever any caller passes extreme values. The upstream balance validation and the `DustPayment`/dust-filtering in `amortize_fee` constrain but do not cap the sum to `< u64::MAX`. [8](#0-7) 

### Recommendation
Use `checked_add`, `checked_mul`, and `checked_sum` (or `u128` intermediates) for `payment_sat`, `needed_fee`, `fee_with_change`, and the solvency comparison, returning a `TransactionError` on overflow. Apply the same treatment to `SignableTransaction::fee()` (use `checked_sub` or `saturating_sub`) so a malformed construction cannot panic.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// With a single funded input and a payment amount near u64::MAX:
let payments = vec![(p2tr_script_buf(key).unwrap(), u64::MAX - 1000)];
// payment_sat + needed_fee overflows u64:
//   - debug build: panic at `payment_sat + needed_fee` (line 215)
//   - release build: wraps; NotEnoughFunds check is bypassed,
//     `new` returns Ok with outputs >> inputs, and `fee()`
//     (line 139) underflows/panics when called.
let tx = SignableTransaction::new(inputs, &payments, None, None, u64::MAX);
```

Caveat: I could not fully verify whether the processor bounds individual payment amounts to values small enough that `payment_sat` cannot approach `u64::MAX` before reaching `SignableTransaction::new`; if a strict upstream cap exists (e.g., total supply limits), the wrap-around variant reduces to the debug-build panic (DoS) only.
