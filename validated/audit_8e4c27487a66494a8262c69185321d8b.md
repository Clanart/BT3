### Title
Stale/unbacked vote weight persists in `pool.totalVoteInVlmgp` after vlMGP is unlocked - ([File: wombat/WombatBribeManager.sol])

### Summary
`getUserVotable()` at [1](#0-0)  only queries the user's *currently* locked vlMGP balance and is used strictly as a point-in-time gate inside `vote()`. Once a vote is cast, the resulting weight recorded in `userTotalVotedInVlmgp`, `userVotedForPoolInVlmgp`, and `pool.totalVoteInVlmgp` is never re-validated or automatically reduced if the user later reduces or removes their vlMGP lock, so `castVotes()` can allocate real veWOM voting power based on vlMGP that no longer exists. Note: the file referenced in the prompt, `rewards/Airdrop.sol`, does not contain this function — the actual code lives in `wombat/WombatBribeManager.sol`.

### Finding Description
`vote()` enforces the invariant only at call time: [2](#0-1) 

The check `userTotalVotedInVlmgp[msg.sender] > getUserVotable(msg.sender)` reverts if the *new* total exceeds the user's *currently* locked vlMGP amount at the moment `vote()` executes. However, nothing in the contract subscribes to vlMGP lock-state changes (there is no callback/hook from `VLMGP` into `WombatBribeManager`), and no other function re-checks this invariant later. Once the transaction that calls `vote()` completes, `pool.totalVoteInVlmgp`, `userTotalVotedInVlmgp[user]`, and `totalVlMgpInVote` are static state variables that persist independent of the user's future lock status.

`castVotes()` then uses these stale, un-reconciled values directly to compute proportional vote weight sent to the underlying Wombat voter: [3](#0-2) 

If a user locks vlMGP, calls `vote()` to record `X` units of vote weight for a pool, and subsequently unlocks/withdraws their vlMGP (assuming `VLMGP` permits unlocking that lock, e.g. after expiry), the weight `X` in `pool.totalVoteInVlmgp` and `userTotalVotedInVlmgp[user]` is not reset. The only way to clear it is if that same user calls `vote()` or `unvote()` again themselves — which they have no incentive to do — or if `removePool` is called by the admin (which is an admin action, out of scope). As a result, the next `castVotes()` call will continue to attribute `X` worth of real veWOM voting weight (and future bribe distribution) to the pool, backed by nothing.

### Impact Explanation
This is a governance voting result manipulation: aggregate votes recorded in `totalVlMgpInVote` and per-pool `totalVoteInVlmgp` can permanently exceed the vlMGP actually locked across all voters, skewing `castVotes()`'s proportional allocation of veWOM voting power (`targetVote = targetVoteInLMGP * totalVotes() / totalVlMgpInVote`) toward pools with phantom votes. This diverts real bribe/reward allocation away from pools that should legitimately receive it based on currently-locked vlMGP, which matches the "governance voting result manipulation" impact category.

### Likelihood Explanation
Feasibility depends on details of `VLMGP`'s lock/unlock mechanics (whether `getUserTotalLocked()` reflects a lock reduction immediately upon initiating unlock, versus only after a cooldown/withdrawal completes) — I was not able to fully confirm this within the available search budget, since `VLMGP.sol`'s unlock implementation was not retrieved in time. Regardless of that timing detail, the structural issue stands: `WombatBribeManager` has no mechanism to reconcile recorded votes against current vlMGP locks other than the one-time check inside `vote()`. Any user who locks vlMGP, votes, and later reduces/removes that lock through normal (unprivileged) `VLMGP` functions will leave stale vote weight in the system with no forced cleanup, and this requires no special privileges — only holding MGP and using standard lock/unlock/vote flows.

### Recommendation
Re-validate (or cap) each user's outstanding vote weight against their live `getUserTotalLocked()` balance at `castVotes()` time (or lazily on any subsequent interaction), pruning/clamping `userTotalVotedInVlmgp`, `userVotedForPoolInVlmgp`, and `pool.totalVoteInVlmgp` down to the user's current lock before using these values to compute `targetVote`. Alternatively, add a callback/hook from `VLMGP` to `WombatBribeManager` on unlock/withdraw that automatically calls an internal unvote for the affected user.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, `VLMGP`, and a mock `IWombatVoter`/`IWombatStaking`.
2. Have `userA` lock a minimal amount of MGP in `VLMGP`.
3. `userA` calls `vote([lp], [X])` where `X == getUserVotable(userA)`; assert `pool.totalVoteInVlmgp == X` and `userTotalVotedInVlmgp[userA] == X`.
4. `userA` calls `VLMGP`'s unlock/withdraw path to fully remove their lock (using whatever unprivileged path `VLMGP` exposes for expired/ended locks); assert `IVLMGP(vlMGP).getUserTotalLocked(userA) == 0` (i.e., `getUserVotable(userA) == 0`).
5. Call `castVotes(false)`; assert that `pool.totalVoteInVlmgp` (and hence the `targetVote` sent to `wombatStaking.vote`) still equals `X`, exceeding the recomputed real vlMGP backing (`0`), demonstrating unbacked votes are counted.
