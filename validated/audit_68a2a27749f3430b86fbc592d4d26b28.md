### Title
Cross-context signature replay between `withdraw_fees` and `accumulate_fees` beneficiary redirection due to identical SCALE-encoded message and shared nonce — (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet-relayer` uses two different signed-message constructors, `message()` (for `withdraw`) and `beneficiary_message()` (for `accumulate`), that hash to byte-identical preimages for the same `(nonce, state_machine, beneficiary)` inputs, and both draw from the *same* `Nonce<T>` storage map keyed by `(address, state_machine)`. There is no purpose/action tag distinguishing "authorize a fee withdrawal disbursement" from "authorize redirecting this accumulation's beneficiary." A signature a relayer produces for one of these two entry points is therefore valid input for the other, as long as the shared nonce has not yet been consumed.

### Finding Description
`withdrawal.rs::message()` builds the signed payload for `Pallet::withdraw`: [1](#0-0) 

`accumulate.rs::beneficiary_message()` builds the signed payload for `Pallet::accumulate`'s optional beneficiary redirect: [2](#0-1) 

Both compute `keccak_256(&(nonce, state_machine/dest_chain, beneficiary).encode())`. SCALE encoding of `Vec<u8>` and `&[u8]` are identical (length-prefix + bytes), so for the same `(nonce, chain, beneficiary_bytes)` triple, `message(nonce, chain, Some(beneficiary))` and `beneficiary_message(nonce, chain, &beneficiary)` produce the exact same 32-byte hash. Neither function includes a domain separator, action discriminant, or contract/pallet identity tag to bind the signature to a specific call.

Both call sites read and later increment the *same* `Nonce<T>` map, keyed by `(address, state_machine)`:
- `withdraw()`: `Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain)` then `Nonce::<T>::try_mutate(address.clone(), withdrawal_data.dest_chain, ...)` [3](#0-2) [4](#0-3) 
- `accumulate()`: `Nonce::<T>::get(&delivery_address, state_machine)` then `Nonce::<T>::try_mutate(&delivery_address, state_machine, ...)` [5](#0-4) 

Both `withdraw` and `accumulate` are dispatchables whose call arguments (including the raw `Signature`) travel through the public transaction pool and are visible on-chain once included — nothing about the arguments is private to the signer. Because the same nonce/message scheme feeds two functionally different, differently-scoped actions:

- `withdraw`'s signed payload authorizes disbursing the entire currently-accumulated `Fees[dest_chain][address]` balance to `beneficiary`.
- `accumulate`'s `beneficiary_details` signed payload authorizes redirecting only the fee just proven-and-credited by that specific `WithdrawalProof` to `beneficiary`.

A signature the relayer creates for one context is accepted by the other's verification path (`signature.verify(&msg, ...)` in each), since the verification code only checks that the recovered signer matches the expected address — it never checks *which function* the message was meant for.

### Impact Explanation
An attacker who observes (in the mempool or on-chain) a relayer's `accumulate` call carrying `beneficiary_details = (beneficiary, signature)` at nonce `N` can extract that `(dest_chain, beneficiary, signature)` tuple and, before the relayer's own next `withdraw`/`accumulate` call consumes nonce `N`, submit a `withdraw` extrinsic with `WithdrawalInputData { signature, dest_chain, beneficiary: Some(beneficiary) }`. Since the message hash and nonce match, `withdraw`'s signature check passes, and the *entire* currently accumulated `Fees<T>[dest_chain][relayer_address]` balance is disbursed to `beneficiary` — an action of far larger scope (full fee-pool withdrawal) than the relayer intended when it signed only a single-delivery accumulation redirect. Symmetrically, a `withdraw`-signed message (which also uses the same `(nonce, chain, beneficiary)` shape when a beneficiary is specified) can be replayed into `accumulate`'s beneficiary field to redirect an entirely unrelated delivery's freshly-accumulated fee.

This is a genuine fund-routing/logic vulnerability: an unprivileged third party (no relayer, prover, or admin compromise required) can trigger a scope-widened disbursement using a signature the relayer only authorized for a narrower purpose, causing funds to move earlier/differently than the signer intended and racing the legitimate relayer's own follow-up call. It falls under "logic attacks / unauthorized transaction execution / transaction manipulation" against the relayer reward/fee-accounting subsystem.

### Likelihood Explanation
Likelihood is moderate: it requires the beneficiary named in a relayer's genuine signed message to be attacker-observable (which it always is, since call arguments are public) and requires racing the nonce before the relayer's own subsequent transaction lands. No cryptographic forgery, malicious relayer, or privileged role is needed — a plain mempool watcher/front-runner using an unprivileged account is sufficient. The main "flaw" is architectural (shared message format/nonce with no domain tag), so it is exploitable whenever any relayer chooses to use a non-default `beneficiary` on either code path.

### Recommendation
Add a distinct domain/action byte (or the extrinsic/module name) into both `message()` and `beneficiary_message()` preimages so a signature over one action can never validate for the other, e.g. hash `(b"withdraw_fees", nonce, dest_chain, beneficiary)` vs `(b"accumulate_beneficiary", nonce, state_machine, beneficiary)`. Additionally consider splitting the nonce namespaces per action (or including the action tag as part of the nonce key) so consumption in one path cannot be raced against the other.

### Proof of Concept
1. Relayer R delivers a request and calls `accumulate()` including `beneficiary_details = (B, sig)` where `sig` is R's signature over `beneficiary_message(nonce=N, state_machine=X, beneficiary=B)` — this transaction is visible in the mempool/block before finalization.
2. Attacker extracts `(X, B, sig)` from R's call and immediately submits `withdraw(WithdrawalInputData { signature: sig, dest_chain: X, beneficiary: Some(B) })`.
3. `withdraw()` computes `message(Nonce::<T>::get(R, X), X, Some(B))`, which is byte-identical to the `beneficiary_message` R actually signed (assuming the attacker's transaction lands while the nonce is still `N`), so `signature.verify` succeeds.
4. `withdraw()` disburses the *entire* `Fees<T>[X][R]` balance to `B` and increments the shared nonce — consuming R's `accumulate` authorization for an unrelated, broader-scope withdrawal that R never explicitly signed for.

Note: full exploitation timing (whether the attacker's `withdraw` can reliably land before R's own next call increments the nonce) depends on runtime/tx-pool ordering behavior not fully inspectable from the indexed source; this should be validated experimentally on a testnet by a background agent with access to the full runtime and a local node.

pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
