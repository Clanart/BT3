### Title
Permissionless `purchase()` "app" targeting lets any third party evict a victim's paid bandwidth subscriptions via FIFO cap eviction - (File: `evm/src/apps/BandwidthManager.sol` / `modules/pallets/bandwidth/src/lib.rs`)

### Summary
The bandwidth-subscription system is Hyperbridge's local analog to the reported "rate limiter DOS" primitive: a shared, capped accounting structure — the per-`(app_chain, app)` FIFO subscription list, bounded to 1024 entries — can be filled by anyone at will because `BandwidthManager.purchase()` lets **any caller credit any `app` on any `chain`** with no relationship check to the target. Once the list is full, `push_subscription` evicts the oldest entry unconditionally, regardless of its remaining value, duration, or the fact that the victim already paid for it.

### Finding Description
`purchase()` in [1](#0-0)  accepts an arbitrary `app` byte-string and `chain` from any caller, pulls the tier price from `msg.sender`, and dispatches a `BandwidthPurchaseMsg` naming that `app`/`chain` as the credit target. This is intentional "sponsorship" (any payer chain can top up any app), but it also means an unrelated, unprivileged attacker can push purchases into a victim's queue at will.

On the pallet side, `on_accept` unconditionally appends a new `Subscription` for the message's `(app_chain, app)` via `push_subscription`, which evicts index `0` (the oldest entry) once the list hits `MAX_SUBSCRIPTIONS` (1024), with no regard for the evicted entry's `remaining_bytes` or `expires_at`: [2](#0-1) [3](#0-2) 

The FIFO drain/eviction ordering is purely insertion-order — never by value — as documented in the pallet's own module docs: [4](#0-3) 

The corrupted value is the victim's `Allowance::<T>` entry for `(app_chain, app)`: legitimate, already-paid, high-value subscriptions sitting near the head of the queue get force-evicted by attacker-purchased low-tier entries that only need to fill remaining queue capacity, not out-bid the victim on value.

### Impact Explanation
This is a loss-of-funds condition: a victim app that already paid for bandwidth (potentially a high tier, e.g. the $1000/8MB plan) can have that paid allowance permanently destroyed by a third party who never interacted with the victim, simply by repeatedly calling the public `purchase()` entrypoint targeting the victim's `app` identifier with the cheapest configured tier. The eviction emits `SubscriptionEvicted { lost_bytes }` — the pallet acknowledges the loss is real and auditable, but does not prevent it: [5](#0-4) 

This directly matches the report's broken invariant: a bounded/shared accounting resource that legitimate protocol usage depends on can be consumed/disrupted by an unrelated attacker, denying service (bandwidth availability) to the rightful party and destroying value they already paid for — an unauthorized-loss/DOS-via-shared-limit pattern, not merely front-running or node/relayer misbehavior.

### Likelihood Explanation
Exploitation cost is non-zero (attacker must pay the cheapest tier price per purchase, e.g. $50 per entry) and scales with how far the victim's queue is from the 1024 cap — filling an empty/near-empty queue to evict one victim entry is expensive (~1024 × tier price), which meaningfully reduces likelihood versus the "gas-fee-only" cost in the original report. However, likelihood rises sharply for any app whose `(chain, app)` queue is already populated with many entries (e.g., an app with frequent small top-ups, or one deliberately targeted after being partially filled by the same attacker in a prior transaction) — in that case only a handful of cheap purchases are needed to evict the entries about to be consumed. Because `purchase()` performs no allowlisting or relationship check on `app`, the attack requires no privileged role, no relayer/prover compromise, and no governance action — it is reachable from a fully public, unprivileged entrypoint.

### Recommendation
- Restrict eviction so that unauthenticated/unrelated third-party purchases cannot displace a target's own paid subscriptions ahead of their consumption, e.g. by evicting by lowest-value/soonest-expiring entry rather than strict FIFO, or by capping how much third-party ("sponsored") credit can be queued per app relative to self-purchased credit.
- Consider requiring `app`-side opt-in/allowlisting for cross-chain sponsorship (mirroring the existing `Allowlist` mechanism already used for gate bypass) so arbitrary addresses cannot credit (and thus indirectly evict) an app's queue without consent.
- Alternatively, increase `MAX_SUBSCRIPTIONS` dynamically or track "protected" (self-purchased, unexpired, high-value) entries separately from sponsor-purchased ones so a flood of cheap sponsor purchases cannot evict genuinely valuable entries.

### Proof of Concept
1. Victim (or a sponsor on its behalf) calls `BandwidthManager.purchase(app=VICTIM_APP, tier=TIER_FOUR, months=1, chain=...)`, paying $1000 for an 8MB subscription; pallet appends it to `Allowance[app_chain][VICTIM_APP]` at index N.
2. Attacker, with no relation to `VICTIM_APP`, calls `BandwidthManager.purchase(app=VICTIM_APP, tier=TIER_ONE, months=1, chain=...)` repeatedly (paying only the cheapest configured tier price each time) until `Allowance[app_chain][VICTIM_APP].len() == MAX_SUBSCRIPTIONS` (1024).
3. Attacker issues one more `purchase()` call for `VICTIM_APP`; `push_subscription` (`modules/pallets/bandwidth/src/lib.rs:404-437`) evicts index `0` — the victim's real 8MB subscription — emitting `SubscriptionEvicted { lost_bytes: 8_388_608*... }`, before the victim's app ever got to use it.
4. Victim's app dispatches a message expecting bandwidth; `BandwidthGate::try_consume` (`modules/pallets/bandwidth/src/lib.rs:509-565`) now sees a shrunk/altered queue, and the previously-paid bandwidth is gone — the victim must re-purchase to regain service, while the attacker's cheap entries occupy/consume the queue instead.

//! # pallet-bandwidth
//!
//! Prepaid `(chain, app)` byte balances credited by tier purchases
//! from `BandwidthManager.sol`. Each purchase carries its own
//! `app_chain`, so any deployment can sponsor any app on any chain.
//!
//! Each `(chain, app)` row holds a FIFO list of [`Subscription`]s

//! subscription with a fixed `expires_at`; expiry never extends and
//! same-tier repurchases don't stack — they queue. The gate drains

//! next. Subscriptions that aren't reached before their expiry are
//! swept silently — what you paid for is yours only until it expires.
//! Pushes onto a full list evict the oldest entry and emit
//! [`Event::SubscriptionEvicted`].

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
