### Title
Cross-chain "sponsorship" purchase lets any unrelated buyer evict a victim app's paid bandwidth allowance - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth`'s `Allowance` storage is keyed purely by `(app_chain, app)` taken from attacker-controlled purchase-message fields, with no binding to the payer/source chain that funded the entry, exactly the missing-initiator pattern in the FIVA `RedeemDeposit` report: any party can write into another party's shared, recipient-keyed state and disturb it. Because the per-`(chain, app)` subscription list is a hard-capped FIFO (1024 entries) that silently evicts the *oldest* entry on overflow, an unrelated purchaser can flood a victim app's bucket with cheap purchases to force-evict the victim's already-paid-for, unexpired bandwidth subscription.

### Finding Description
`BandwidthManager.purchase()` lets **any caller** dispatch a `BandwidthPurchaseMsg` naming an arbitrary `app` and arbitrary `chain` (the credit chain) that is completely independent of `msg.sender` and independent of the chain the purchase was made from: [1](#0-0) 

On Hyperbridge, `pallet-bandwidth::on_accept` only authenticates that the message came from the *registered manager contract* on its source chain — it performs no check tying the purchase to the app owner, and credits the subscription under a key taken from the message body (`msg.chain`, `msg.app`), not from `request.source`: [2](#0-1) 

This is a documented, intentional "sponsorship" feature — "a buyer on Ethereum can credit an app on Base" — but it means the `Allowance` map has no concept of *who owns* a given `(app_chain, app)` slot; anyone able to call `purchase()` on any registered `BandwidthManager` can write into it: [3](#0-2) 

`push_subscription` enforces a 1024-entry cap per `(app_chain, app)` and evicts the **oldest** entry (FIFO head) when the cap is hit, regardless of who purchased it or how much value it represents: [4](#0-3) 

The eviction event comment itself states the corrupted invariant: *"The 1024-cap pushed out the oldest subscription. `lost_bytes` is what the user paid for and won't get to use."* [5](#0-4) 

**Corrupted value:** the FIFO ordering/occupancy of `Allowance::<T>[app_chain][app]` — a resource that a legitimate app paid real fee-token value for — can be mutated by an attacker who has no relationship to that app or chain, exactly as the FIVA `RedeemDeposit` contract could be mutated by anyone who knew only the victim's recipient address. There is no "initiator/owner" field gating who may append to a given app's queue, mirroring the missing token-sender field in `RedeemDeposit`'s `init_state`.

### Impact Explanation
An attacker can force `SubscriptionEvicted` on a victim's still-valid, unconsumed subscription by repeatedly calling `purchase()` targeting the victim's `(app_chain, app)` pair with the cheapest tier until the queue reaches 1024 entries, then continuing to push, evicting the victim's larger/still-unexpired subscription. This destroys bandwidth capacity the victim already paid for in real fee tokens, causing outright loss of prepaid funds and, functionally, denial of the app's cross-chain message throughput once its allowance is gone — the app's real dispatches will then be rejected by `BandwidthGate::try_consume` (`GateError::NoAllowance` / `Insufficient`) since the router "silently" gates non-purchase requests on the drained allowance. This is a direct funds-loss/wrong-beneficiary-of-a-paid-resource impact matching the bounty's "stealing or loss of funds" / "logic attacks" categories, not a mere gas/network DoS, because it destroys already-purchased, non-refundable value belonging to a third party.

### Likelihood Explanation
Any unprivileged actor can call the public, unauthenticated `purchase()` entrypoint on any registered `BandwidthManager` for any chain/app, no relayer, prover, governance, or malicious-peer assumption is needed. The only cost is the tier price (as low as $50 per 100 KB purchase) times however many purchases are needed to reach or exceed the current queue depth for the target `(chain, app)` — for an app with only a handful of subscriptions this is inexpensive, and it scales linearly, not requiring any race condition or privileged timing.

### Recommendation
- Bind subscriptions to a verifiable owner: either require `request.source == app_chain` for self-purchases and put sponsorship purchases into a **separate**, non-evicting queue/allowance bucket, or track `payer` per subscription and only allow eviction of entries whose remaining bytes are below some minimum / whose payer matches the evictor.
- Alternatively, protect existing paid subscriptions from third-party eviction by making the FIFO cap per-payer (or per source-chain) rather than global per-`(app_chain, app)`, so an unrelated sponsor cannot displace another payer's entries.
- At minimum, require governance opt-in per `(app_chain, app)` before a *different* source chain may credit (sponsor) that bucket, closing the "anyone can write to your queue" primitive analogous to including the missing sender/initiator identity that the original FIVA fix recommended.

### Proof of Concept
1. Victim app `A` on chain `C` buys one `TierFour` subscription (8 MB, largest, priciest) for itself via `BandwidthManager.purchase(app=A, tier=4, months=1, chain=C)` from chain `C`. This lands as the sole entry in `Allowance::<T>[C][A]`.
2. Attacker, from any chain with a registered `BandwidthManager` (can be the same chain `C` or a different one — sponsorship is chain-agnostic), calls `purchase(app=A, tier=1, months=1, chain=C)` 1024 times (or however many are needed to fill the remaining capacity of `Allowance::<T>[C][A]` up to `MAX_SUBSCRIPTIONS = 1024`), each a cheap `TierOne` (100 KB) purchase.
   - Each call passes `pallet-bandwidth::on_accept`'s only check (`request.from == BandwidthManager::<T>::get(request.source)`), since the attacker is a legitimate caller of a legitimate, registered manager contract — the check never verifies the attacker owns `app`. [6](#0-5) 
3. On the 1025th push into `Allowance::<T>[C][A]`, `push_subscription` evicts the FIFO head — which, because `A`'s `TierFour` subscription was inserted first (or ends up at the head once its own front entries drain/expire), is now evicted, emitting `SubscriptionEvicted` and permanently destroying `A`'s paid 8 MB allowance before it was consumed or expired. [7](#0-6) 
4. App `A`'s subsequent legitimate dispatches through Hyperbridge's ISMP router are now throttled/rejected by `BandwidthGate::try_consume` far earlier than `A` planned, and the fee tokens `A` spent on the evicted `TierFour` purchase are unrecoverable.

            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

                to: PALLET_BANDWIDTH_MODULE_ID,

            })

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
