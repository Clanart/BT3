### Title
Giga-path EVM balance check double-counts split cast/derived balances but debit only draws from one account, causing spurious insufficient-funds failures for unassociated senders - (File: app/app.go)

### Summary
In the fast ("giga") EVM validation path, `validateGigaEVMTx` computes an *unassociated* sender's spendable balance by summing balance held at the EVM-derived cast address and balance held at a second, separately-derived Sei address view, then compares that combined total against `gas*gasFeeCap + value`. However, the actual debit performed later during execution (`SubBalance` in the EVM `StateDB`) only withdraws funds from a single Sei address resolved via `getSeiAddress`/`GetSeiAddressOrDefault`. This mirrors the C4 finding pattern: a balance-sufficiency check that aggregates funds from two different "buckets" while the actual spend can only draw from one of them, so a transaction can pass validation yet fail (or a user's funds remain effectively unusable for that transaction) even though the aggregate balance is nominally sufficient.

### Finding Description
`validateGigaEVMTx` performs the balance check exactly like this: [1](#0-0) 

- `senderBalance := stateDB.GetBalance(sender)` reads the balance associated with the EVM `sender` address (which internally resolves via `s.getSeiAddress(evmAddr)` → `s.k.GetSeiAddressOrDefault(...)`, i.e., the cast/default Sei address for an unassociated EVM address).
- For unassociated senders (`!isAssociated`), the code *additionally* adds the balance of `seiEVMAddr := common.BytesToAddress(seiAddr)` — the EVM-address view of a second, distinct Sei address (`seiAddr`) that was derived earlier in the ante pipeline (e.g., from a Cosmos-signed tx's pubkey-derived Sei address).
- This produces a combined `senderBalance` used solely for the "have enough funds" `Cmp` check.

The actual debit that happens during EVM execution, however, is single-bucket: [2](#0-1) 

`SubBalance` resolves `addr := s.getSeiAddress(evmAddr)` for the `sender` EVM address only, and calls `SubUnlockedCoins`/`SubWei` against that single Sei account. It never looks at the second `seiAddr`/`seiEVMAddr` bucket that was included in the validation-time sum. The address resolution used both in validation and in execution is the same helper: [3](#0-2) 

So for an unassociated sender whose usable funds are split between the cast-address balance (`sender`) and the "true" Sei address's EVM-cast balance (`seiEVMAddr`), the validation step can conclude the transaction is affordable (sum of both buckets ≥ cost), but the state-transition step will only be able to pull funds from the `sender`-resolved bucket and will fail with `ErrInsufficientFunds` if that bucket alone is short — an inconsistency directly analogous to the report's core defect: a balance check that accounts for funds the debit logic cannot actually reach.

### Impact Explanation
This causes a legitimate, funded transaction to be rejected/fail with an insufficient-funds error despite the sender's aggregate on-chain balance being sufficient, because part of that balance is locked into a different address bucket than the one the debit routine draws from. For affected unassociated users (dual balance views by design of the Sei/EVM address model, as documented in the module notes), this produces unusable/inaccessible value that is only recoverable once the user goes through Explicit Association/`MigrateBalance` to consolidate their balances — a state where funds are functionally frozen for the purposes of transacting, mirroring the "user cannot make use of these locked funds even though they may be needed for a successful sale" issue in the original report. This is a functional/availability defect for the affected address class, not a base fee, consensus, or fund-theft issue.

### Likelihood Explanation
Likelihood is moderate: any EVM sender that has not yet completed explicit address association and holds balance in both the EVM-cast bucket and the pubkey-derived Sei-address bucket (a state achievable simply by receiving funds to both address representations before ever signing a Cosmos-format tx that triggers association) will hit this on the giga fast validation path when its cost exceeds either bucket individually but not their sum. No adversarial condition is required beyond ordinary usage of the dual-address model that the module itself documents.

### Recommendation
Ensure the "have funds" check in `validateGigaEVMTx` (app/app.go, balance-check block) mirrors exactly what the debit path in `x/evm/state/balance.go`'s `SubBalance` can actually withdraw. Concretely, either (a) restrict the validation check to only the single bucket resolved by `getSeiAddress` (removing the additive combination for `!isAssociated` senders), matching debit behavior, or (b) before/at the point of debit, migrate/consolidate the `seiEVMAddr` balance into the bucket used for `SubBalance` (analogous to `AssociationHelper.MigrateBalance`) so that the funds validated as available are the same funds actually withdrawn. The fix must guarantee that any balance counted during fee/value sufficiency checks is reachable by the subsequent `SubUnlockedCoins`/`SubWei` calls in the same transaction.

### Proof of Concept
1. Create EVM address `E` with no prior Sei/EVM association.
2. Fund the EVM-cast bucket for `E` (`sender`) with `X` usei-equivalent, insufficient alone to cover `gas*gasFeeCap + value`.
3. Independently fund the second bucket, i.e., the account at `seiEVMAddr = common.BytesToAddress(seiAddr)` where `seiAddr` is the pubkey-derived Sei address computed earlier in the ante pipeline for this same signer, with `Y` usei-equivalent such that `X < cost` but `X + Y ≥ cost`.
4. Submit an EVM transaction from `E` via the giga fast path (`Cosmos`-signed EVM message, keeping the account unassociated) with `gas*gasFeeCap + value = cost`.
5. `validateGigaEVMTx`'s balance check at `app/app.go:2937-2948` computes `senderBalance = X + Y ≥ cost` and passes validation.
6. During execution, `SubBalance` (`x/evm/state/balance.go:15-46`) resolves only the `sender`-bucket address and attempts `SubUnlockedCoins`/`SubWei` for `cost` against a bucket holding only `X < cost`, returning `ErrInsufficientFunds` and failing the transaction despite validation having approved it — demonstrating the mismatch between the validated balance and the actually spendable balance.

func (s *DBImpl) SubBalance(evmAddr common.Address, amtUint256 *uint256.Int, reason tracing.BalanceChangeReason) uint256.Int {
	s.k.PrepareReplayedAddr(s.ctx, evmAddr)
	amt := amtUint256.ToBig()
	if amt.Sign() == 0 {
		return *ZeroInt
	}
	if amt.Sign() < 0 {
		return s.AddBalance(evmAddr, new(uint256.Int).Neg(amtUint256), reason)
	}

	ctx := s.ctx
	var oldBalance *uint256.Int
	if s.logger != nil && s.logger.OnBalanceChange != nil {
		oldBalance = s.GetBalance(evmAddr)
	}

	// this avoids emitting cosmos events for ephemeral bookkeeping transfers like send_native
	if s.eventsSuppressed {
		ctx = ctx.WithEventManager(sdk.NewEventManager())
	}

	// Hook for mock balances (no-op in production builds)
	s.ensureSufficientBalance(evmAddr, amt)

	usei, wei := SplitUseiWeiAmount(amt)
	addr := s.getSeiAddress(evmAddr)
	err := s.k.BankKeeper().SubUnlockedCoins(ctx, addr, sdk.NewCoins(sdk.NewCoin(s.k.GetBaseDenom(s.ctx), usei)), true)
	if err != nil {
		s.err = err
		return *ZeroInt
	}
	err = s.k.BankKeeper().SubWei(ctx, addr, wei)

func (k *Keeper) GetSeiAddressOrDefault(ctx sdk.Context, evmAddress common.Address) sdk.AccAddress {
	addr, ok := k.GetSeiAddress(ctx, evmAddress)
	if ok {
		return addr
	}
	return sdk.AccAddress(evmAddress[:])
}
