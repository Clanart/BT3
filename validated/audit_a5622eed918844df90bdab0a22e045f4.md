### Title
Unauthenticated `ReceivedOutput::read` allows an attacker to redirect signing to a different UTXO - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` accepts an offset, full `TxOut`, and `OutPoint` as independent attacker-controlled fields without proving that the claimed outpoint actually contains the claimed output. `SignableTransaction::multisig` verifies only that the supplied `TxOut.script_pubkey` corresponds to the offset key; it does not authenticate that the referenced outpoint is the UTXO originally scanned or even that it exists. An attacker can therefore copy the `script_pubkey` and amount from a valid Serai-controlled output but substitute another outpoint paying the same key and amount, causing the threshold signers to authorize spending the substituted UTXO.

### Finding Description
`ReceivedOutput::read` deserializes `offset`, `output`, and `outpoint` independently and returns them without checking consistency or chain state. [1](#0-0) 

`SignableTransaction::new` copies the attacker-controlled `outpoint` into the transaction input and preserves the separately supplied `output` as the claimed prevout for sighash calculation. [2](#0-1) [3](#0-2) 

Before signing, `SignableTransaction::multisig` validates only that `keys.offset(input.offset).group_key()` maps to the supplied `script_pubkey`; it never validates that `input.outpoint` is the output bearing that script or amount. [4](#0-3) 

Signing then commits to the attacker-controlled transaction and the claimed prevouts list with `Prevouts::All`, producing a signature for the attacker-selected outpoint if that outpoint actually resolves to the same script and amount. [5](#0-4) 

This is the direct analog of accepting a cryptographically valid credential for the wrong identity: the key/script credential checks out, but the UTXO identity being authorized is not checked against the credential presented for signing.

### Impact Explanation
An unprivileged party who can supply serialized `ReceivedOutput` bytes to a signing workflow can cause Serai threshold signers to sign a transaction spending an unintended Serai-owned UTXO. If the attacker learns another unspent outpoint controlled by the same threshold key with the same amount and script, they can substitute it and have the resulting signed transaction broadcast, redirecting funds according to the transaction’s outputs.

The issue is not a consensus-level theft of an arbitrary UTXO: the replacement outpoint must really exist and match the committed `TxOut` for the Taproot signature to be valid. Within that constraint, the signature is nevertheless concrete authorization for a transaction the signers did not scan or intend to fund.

### Likelihood Explanation
The attacker only needs knowledge of another current UTXO controlled by the same Serai key with an identical amount and script, plus the ability to feed crafted `ReceivedOutput` bytes into `SignableTransaction::new` and the resulting signing flow. Repeated equal-value deposits make finding such an outpoint practical. The vulnerable path is entirely reachable through public deserialization and signing APIs.

### Recommendation
Treat `ReceivedOutput` as authenticated scanner output rather than a self-authenticating untrusted structure. At minimum, `SignableTransaction::multisig` should require a proof or trusted lookup that `outpoint` resolves to the exact supplied `TxOut`, including amount and script. Better, keep the scanner’s observed `OutPoint -> TxOut` binding in authenticated storage and reject deserialized `ReceivedOutput` values unless they match that authenticated record.

### Proof of Concept
```rust
use bitcoin::{OutPoint, Transaction, TxOut};
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction};

// An attacker obtains bytes describing one legitimate Serai output.
let legitimate = ReceivedOutput::read(&mut attacker_supplied_bytes)?;

// The attacker copies the legitimate TxOut but substitutes another existing
// outpoint controlled by the same Serai key and carrying the same value/script.
let redirected = ReceivedOutput::read(&mut {
    let mut bytes = Vec::new();
    // offset: same scalar as the legitimate output
    bytes.extend(legitimate.offset().to_bytes());
    // output: copied legitimate TxOut
    bytes.extend(bitcoin::consensus::serialize(legitimate.output()));
    // outpoint: another same-key/same-value UTXO selected by the attacker
    bytes.extend(bitcoin::consensus::serialize(&attacker_selected_outpoint));
    bytes.as_slice()
})?;

let tx = SignableTransaction::new(
    vec![redirected],
    &attacker_payments,
    attacker_change,
    None,
    fee_per_vbyte,
)?;

// This succeeds because the copied script_pubkey still matches the offset key.
let machine = tx.multisig(&threshold_keys).unwrap();
```

The resulting transaction names `attacker_selected_outpoint` as its input while the signature commits to the copied `TxOut`. If that outpoint exists with the same script and amount, Bitcoin validates the signature, demonstrating authorization of a different UTXO than the one represented by the original scanned output.
