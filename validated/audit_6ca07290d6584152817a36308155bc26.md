### Title
Hardcoded zero slippage protection in `ArbWomUp3._deposit` mode-2 flow exposes users to sandwich-attack fund loss during WOM→mWOM conversion - (File: `wombat/ArbWomUp3.sol`)

### Summary
`ArbWomUp3.incentiveDeposit` allows any user to deposit WOM and choose `_mode == 2`, which routes half of the deposited WOM through `SmartWomConvert.convert()` with the `_minRec` slippage parameter hardcoded to `0`, completely disabling the only slippage safeguard in the conversion pipeline. This mirrors the reported bug class (a user-facing withdraw/convert flow forwarding a hardcoded `minOut`/`minRec` of `0` into a swap, exposing users to sandwich attacks and fund loss), except here it occurs on the WOM→mWOM buyback leg of `SmartWomConvert`.

### Finding Description
`ArbWomUp3._deposit`, called from the external, unprivileged entrypoint `incentiveDeposit`, for `_mode == 2` splits the user's deposited WOM and sends half through `SmartWomConvert.convert(toSwap, _convertRatio, 0, 0)`: [1](#0-0) 

The `0` passed as `_minRec` flows into `SmartWomConvert._convertFor`, where it is used as the sole aggregate slippage check `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();`. With `_minRec == 0` this check can never revert: [2](#0-1) 

Additionally, the underlying router call inside `_convertFor` itself also hardcodes `minimumToAmount` to `0`: [3](#0-2) 

Because both the router-level minOut and the caller-level `_minRec` are zero in this specific call path, there is no slippage protection anywhere in the WOM→mWOM buyback swap triggered by `ArbWomUp3.incentiveDeposit` with `_mode == 2`. Unlike the `convert`/`convertFor` public entrypoints on `SmartWomConvert` (which let the caller freely choose a nonzero `_minRec`) or `smartConvert` (which forces `_minRec = _amountIn`), this specific caller in `ArbWomUp3` strips away the protection entirely regardless of what the calling user intends.

### Impact Explanation
Any unprivileged user calling `incentiveDeposit(_amount, _convertRatio, _bullMode, 2)` has their WOM routed into a swap with zero minimum output enforcement. An attacker can sandwich this transaction on the `womMWomPool` route (front-run to move the WOM/mWOM price, let the victim's swap execute at an unfavorable rate, then back-run to restore price and capture the difference). The victim silently receives materially less mWOM than expected and the transaction does not revert, resulting in direct, permanent loss of user funds — this is not a swap-then-check-then-revert pattern (as in `smartConvert`), so the loss is realized and non-reversible.

### Likelihood Explanation
Likelihood is moderate-to-high: MEV/sandwich bots actively monitor mempools for swaps with no slippage protection, and any wallet using the `_mode == 2` branch of `incentiveDeposit` is affected automatically without any special conditions, misconfiguration, or privileged actor required. The bug is deterministic and always present for that code path.

### Recommendation
Replace the hardcoded `0` in `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` with a user-supplied `_minRec` parameter threaded through `incentiveDeposit`/`_deposit`, and similarly ensure the router call inside `SmartWomConvert._convertFor` uses a meaningful non-zero minimum output derived from an oracle/quote rather than always `0`.

### Proof of Concept
1. Attacker monitors mempool for calls to `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, _bullMode, 2)`.
2. Attacker front-runs by swapping WOM for mWOM on `womMWomPool` to skew the pool price against the pending WOM→mWOM leg.
3. Victim's transaction executes `_deposit` → `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` → `_convertFor`, which swaps `buybackAmount` WOM for mWOM via `IWombatRouter.swapExactTokensForTokens(..., 0, ...)` — no revert occurs regardless of output because both the router minOut and `_minRec` are `0`.
4. Attacker back-runs, restoring the pool price and extracting the value lost by the victim.
5. Victim ends up locked/holding less mWOM than a fair-price conversion would have produced, with no recourse since the transaction succeeded. [4](#0-3)
