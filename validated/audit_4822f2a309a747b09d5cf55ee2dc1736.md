### Title
Unauthenticated `ReceivedOutput` metadata can report foreign outputs as spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes an offset, a `TxOut`, and an `OutPoint`, but never validates that the referenced transaction output actually contains the serialized `TxOut` or corresponds to the offset-derived Taproot script. [1](#0-0)  An attacker who can feed bytes to this parser can therefore claim that an arbitrary foreign or nonexistent outpoint pays to the wallet. [1](#0-0) 

### Finding Description
`Scanner::scan_transaction` creates internally consistent outputs by deriving the `OutPoint` from the containing transaction and cloning the actual output. [2](#0-1)  `ReceivedOutput::read` bypasses that invariant and trusts all three serialized fields independently. [1](#0-0) 

`SignableTransaction::new` then trusts the forged `output.value` as available funds and uses the forged `outpoint` as the transaction input. [3](#0-2)  During signing, `SignableTransaction::multisig` verifies only that the supplied offset produces the forged `prevouts[i].script_pubkey`; it does not verify that the referenced outpoint contains that script. [4](#0-3) 

This is analogous to trusting attacker-controlled MIME metadata while ignoring the actual extension: the code validates the attacker-supplied `TxOut` metadata against the offset, while the outpoint identifying the real chain output remains unauthenticated. [4](#0-3) 

### Impact Explanation
An attacker can cause funds to be reported or accounted for as received even though the corresponding UTXO is not spendable by the wallet. [1](#0-0)  The wallet can then construct and threshold-sign a transaction committing to the fabricated prevout amount and script while spending the unrelated attacker-selected `OutPoint`, producing a transaction that consensus rejects. [5](#0-4) 

### Likelihood Explanation
The attack requires an application to deserialize an attacker-controlled `ReceivedOutput` instead of only accepting objects produced by `Scanner` from authenticated blockchain data. [1](#0-0)  Within that supported input path, exploitation is deterministic because no proof-of-inclusion or output consistency check is performed. [1](#0-0) 

### Recommendation
Do not expose `ReceivedOutput::read` for unauthenticated data, or extend the serialized format to include the containing transaction and Merkle/block evidence proving `tx.output[vout] == output`. [1](#0-0)  At minimum, document the type as trusted-only and ensure constructors verify `p2tr_script_buf(base_key + offset * G)` against the real chain output associated with `outpoint`, not merely against the serialized `TxOut`. [4](#0-3) 

### Proof of Concept
```rust
use bitcoin::{
  consensus::encode::serialize,
  hashes::Hash,
  OutPoint, TxOut, Amount, Txid,
};
use serai_bitcoin::wallet::{ReceivedOutput, p2tr_script_buf};
use frost::curve::Secp256k1;
use k256::Scalar;

// wallet_group_key is the Scanner's base group key.
let script = p2tr_script_buf(wallet_group_key).unwrap();

// Foreign UTXO whose actual on-chain script_pubkey is unrelated to `script`.
let foreign_outpoint = OutPoint {
  txid: Txid::from_byte_array(attacker_selected_txid),
  vout: 0,
};

let forged_txout = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: script,
};

let mut encoded = Vec::new();
encoded.extend(Scalar::ZERO.to_bytes());
encoded.extend(serialize(&forged_txout));
encoded.extend(serialize(&foreign_outpoint));

// Accepted even though foreign_outpoint does not contain forged_txout.
let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
```

Passing `forged` to `SignableTransaction::new` makes the forged value available for spending and installs the foreign `OutPoint` as an input. [3](#0-2)  `multisig` accepts it because the fabricated `TxOut` contains the offset-derived wallet script, while the actual chain output referenced by `foreign_outpoint` is never checked. [4](#0-3)
