### Title
File-open actions in commit/PR file lists resolve attacker-controlled paths without symlink/traversal containment - ([File: app/src/ui/history/selected-commits.tsx], [File: app/src/ui/open-pull-request/pull-request-files-changed.tsx])

### Summary
The report's broken invariant is: a security check (accounting for the mutable conversion rate) exists in one code path (`ERC4626PartnerManager`) but is missing from a sibling path (`vMaia`) that reaches the same sensitive operation, causing the guard to be silently bypassed. The same *pattern* — a containment guard implemented in one place but omitted in a parallel code path that consumes the same attacker-influenced data — exists in GitHub Desktop around opening files whose paths originate from git history/diff data.

Desktop already recognizes that git-reported file paths are not safe to blindly `Path.join()` with the repository root: `resolveWithin()` in [1](#0-0)  performs a `realpath()`-based containment check specifically to catch directory traversal *and symlink escapes*, and it is deliberately used both for deep-link file paths in the dispatcher and for the new Copilot conflict-resolution feature, with an explicit comment "Guard against path traversal and symlink escapes (cross-platform)" [2](#0-1) , and for `openRepositoryFromUrl` deep links [3](#0-2) .

However, the "Open File" actions for the commit history file list and the pull-request files-changed list build the on-disk path with a bare `Path.join(repository.path, path)` and never call `resolveWithin`/`realpath` before invoking `openFile` (which shells out to the OS's default handler), `openInExternalEditor`, or `revealInFileManager`: [4](#0-3) [5](#0-4) [6](#0-5) 

### Finding Description
`file.path` in both components is not user-typed input — it comes from git's reported changed-file list for a selected commit/PR (`CommittedFileChange`), i.e. it is fully attacker-controlled content of a cloned/fetched repository or a viewed pull request diff. Git permits committing symlink blobs (mode `120000`) that, once checked out, become real filesystem symlinks pointing anywhere the OS user has access to (e.g. `link -> /` or `link -> C:\`). A malicious repository can:

1. Commit a directory `link/secret.txt` in an early commit.
2. In a later commit, replace `link` with a symlink pointing outside the repository.
3. Ship both commits so that when the *current* checkout has `link` as a symlink, but the *history/PR file list* still shows an older commit's entry `link/secret.txt`.

When the user opens the file list for that older commit (or a PR whose base/head lays out this way) and double-clicks/opens `link/secret.txt`, `selected-commits.tsx`/`pull-request-files-changed.tsx` compute `fullPath = Path.join(repository.path, 'link/secret.txt')`. Because `Path.join` performs pure string concatenation and does not resolve symlinks, the OS opens the path by following the on-disk `link` symlink, landing outside the repository root — exactly the class of escape that `resolveWithin`'s `realpath()` comparison was built to stop, but which is not applied here.

`openFile` then calls `shell.openExternal('file://' + fullPath)` [7](#0-6) , which hands the resolved path to the OS's default-handler mechanism — for certain extensions (e.g. `.desktop`, `.scpt`, `.bat`/`.cmd` via shell association, or documents with active content) this is a read/open of a file outside the repo and, depending on OS file-type handling, can escalate to execution of attacker-placed content outside the sandboxed repo directory.

### Impact Explanation
This breaks the same invariant class as the referenced report: a containment check that exists in one place (`resolveWithin` in the dispatcher deep-link handler and the Copilot conflict-context reader) is not applied uniformly to a structurally identical operation (opening a git-reported file path) in the history and pull-request file viewers. The result is file open/read outside the intended repository directory driven purely by content of a cloned/fetched repository or a rendered pull request — matching the "file write or read outside the repo" / "renderer triggers OS action on attacker path" impact category. No local access, admin rights, or social engineering beyond normal repository browsing/PR review is required.

### Likelihood Explanation
Requires the victim to clone/fetch a malicious repository (or open a malicious PR) and interact with the History or "Files Changed" view for the crafted commit — a standard, expected Desktop workflow, not an unnatural user action. The attacker fully controls the git object graph (symlink content, commit ordering) needed to set up the escape. This is a plausible but non-trivial path requiring a specific commit-history layout; it is not confirmed working end-to-end (I could not execute or trace `shell.openExternal`'s exact per-OS symlink-following/execution semantics), so likelihood should be treated as moderate rather than certain.

### Recommendation
Route `fullPath` construction in `onOpenItem` (`selected-commits.tsx`), `onOpenFile`/`onFileContextMenu` (`pull-request-files-changed.tsx`), and any other file-list "open"/"reveal"/"copy path" actions through `resolveWithin(repository.path, file.path)` (already implemented in `app/src/lib/path.ts`), rejecting and refusing to open when the resolved real path escapes the repository root — mirroring the guard already applied in `dispatcher.ts` and `copilot-conflict-context.ts`.

### Proof of Concept
Conceptual reproduction (not independently executed, based on code-path analysis):
1. Attacker repo, commit A: adds `link/secret.txt` as a normal file.
2. Attacker repo, commit B: deletes the `link` directory and adds `link` as a symlink pointing to a sensitive location (e.g. the user's home directory or an attacker-planted executable path).
3. Victim clones/fetches the repo; working tree is checked out at commit B, so `link` is now a symlink on disk.
4. Victim opens History (or a PR diff) and selects commit A, whose file list still reports `link/secret.txt`.
5. Victim double-clicks/opens that file entry: `selected-commits.tsx`/`pull-request-files-changed.tsx` compute `Path.join(repository.path, 'link/secret.txt')` and call `openFile`, which follows the on-disk symlink and opens/executes content outside the repository — without ever calling `resolveWithin`/`realpath` to detect the escape, unlike the equivalent Copilot conflict-context and deep-link code paths.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

```typescript
export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
```
