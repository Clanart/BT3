Based on my investigation, most of the decimals-handling code I found in this repo (`VWAPOracle.sol`, `BandwidthManager.sol`, `SimplexPaymaster.sol`) explicitly normalizes decimals or reverts on non-representable values (e.g. `PriceNotRepresentable()`), unlike the original Alchemix bug. However, I found a structurally identical flaw in the cross-chain decimal-scaling helpers used by `hyper-fungible-token`.

### Title
Asymmetric decimals conversion silently clamps to a 1:1 scale when the EVM side has fewer decimals than the local asset - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`convert_to_erc20` and `convert_to_balance` compute the scaling exponent with `erc_decimals.saturating_sub(local_decimals)` / the implicit reverse, exactly mirroring the Alchemix bug's core flaw: an unguarded plain-amount arithmetic path that silently breaks whenever the two sides' decimal precisions diverge in a particular direction.

### Finding Description [1](#0-0) 

`convert_to_erc20(value, erc_decimals, local_decimals)` multiplies by `10^(erc_decimals.saturating_sub(local_decimals))`, and `convert_to_balance` divides by the same saturating exponent in the other direction. `saturating_sub` returns `0` whenever `erc_decimals < local_decimals` — instead of the (negative) exponent that correct scaling requires. In that case both helper functions silently degrade to a **no-op** (multiplier/divisor of `10^0 = 1`) rather than erroring or applying the correct inverse scale, exactly as the ThreePoolAssetManager/EthAssetManager bug used plain, un-scaled amounts whenever the fixed-18-decimals assumption didn't hold.

`send()` calls `convert_to_erc20(amount, erc_decimals, decimals)` after already debiting `amount` in the local asset's native precision: [2](#0-1) 

If the destination EVM token is configured with **fewer** decimals than the local Substrate asset (`erc_decimals < local_decimals`), the multiplier collapses to `1`, so the wire `Message.amount` field carries the same raw integer that was valid at the local asset's finer precision, but the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract will interpret that integer at its own coarser decimal scale — inflating the minted value by `10^(local_decimals - erc_decimals)` relative to what was actually locked/burned on the source chain.

The symmetric failure exists on the receive path: `on_accept` (tested at [3](#0-2)  using `convert_to_erc20(SEND_AMOUNT, 18, 10)`) relies on `convert_to_balance` to scale the incoming ERC20 `U256` amount back down; if `erc_decimals < local_decimals` there, the same saturating clamp means the incoming raw ERC20 units get credited 1:1 into the local balance without down-scaling, over-crediting the beneficiary by the same `10^(local_decimals - erc_decimals)` factor.

A benchmarking comment (`modules/pallets/hyper-fungible-token/src/benchmarking.rs:36-38`) states `register_token` is supposed to reject configuring an EVM side with fewer decimals than the local asset, implying an intended invariant `erc_decimals >= local_decimals`. I was not able to fully verify from the code I retrieved whether this invariant is actually enforced at runtime in `register_token`/`update_token` for every governance-configured `(asset, chain)` pair, or only assumed by the benchmark setup — this is the key open question that would confirm or refute exploitability from an unprivileged path.

### Impact Explanation
If the decimals invariant is not enforced (or can be misconfigured for even one legitimate chain/asset pair), a user bridging via `send()`/`on_accept` would mint or receive tokens at a value inflated by a power-of-ten factor relative to what was locked or burned — a direct fund-creation/fund-loss bug identical in mechanism to the referenced Alchemix finding, and squarely within the bounty's "stealing or loss of funds" / "false proof or state acceptance"-adjacent value-mismatch category, since it is the escrow/mint bookkeeping invariant, not proof verification, that breaks.

### Likelihood Explanation
Exploitability is entirely conditional on whether `register_token`/`update_token` actually enforces `erc_decimals >= local_decimals` for every configured chain at every governance update, which I could not confirm from the excerpts retrieved. If that guard is missing or bypassable for any configured asset/chain pair (e.g. via a later `update_token` that doesn't re-validate), this becomes a systemic, unprivileged-user-triggerable bug the moment such a misconfigured pair exists; if the guard is airtight at every mutation point, this reduces to a defense-in-depth gap rather than a directly exploitable path.

### Recommendation
Replace `saturating_sub`-based scaling in `convert_to_erc20`/`convert_to_balance` with an explicit signed comparison that always applies the correct direction of scaling (multiply when `erc_decimals > local_decimals`, divide when `erc_decimals < local_decimals`), and add a runtime assertion/hard error path (not just an off-chain benchmarking comment) enforced in both `register_token` and `update_token` that rejects any configuration violating the intended `erc_decimals >= local_decimals` invariant — mirroring the C4 recommendation to control decimals at construction time rather than relying on an unstated assumption.

### Proof of Concept
Given `local_decimals = 12`, and an admin (or a misconfigured/updated chain entry) registers a destination EVM contract with `erc_decimals = 6`:
1. `saturating_sub(6, 12)` = `0` → `convert_to_erc20` multiplies by `10^0 = 1` instead of dividing by `10^6`.
2. A user calls `send()` with `amount = 1_000 * 10^12` (1000 units at 12 local decimals), locking/burning that amount correctly on the source chain.
3. The dispatched `Message.amount` wire value is `1_000 * 10^12` unchanged (should have been `1_000 * 10^6` at the destination's 6-decimal precision).
4. The destination contract mints `1_000 * 10^12` raw units at 6 decimals = `1,000,000,000 ` tokens instead of `1,000` — a `10^6`-times over-mint relative to the value actually locked, as demonstrated by the existing test pattern at [4](#0-3)  which exercises `convert_to_erc20`/`on_accept` round-tripping with mismatched decimals (`18` vs `10`) without asserting the invariant direction is enforced upstream.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
