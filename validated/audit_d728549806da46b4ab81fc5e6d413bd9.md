### Title
`cancelUnlock` allows retroactive forfeiture bypass on already-accrued cooldown-period rewards - ([File: wombat/ArbWomUp2.sol -> VLMGP.sol / vlMGPBaseRewarder.sol])

### Summary
`VLMGP.cancelUnlock` resets `slot.amountInCoolDown` to `0` and decrements `totalAmountInCoolDown` without ever calling `updateFor`/`getReward` on the linked `vlMGPBaseRewarder` to snapshot the user's rewards under the still-active cooldown state. Because reward forfeiture in `vlMGPBaseRewarder._calExpireForfeit` is evaluated using `vlMGP.getRewardablePercentWAD(_account)` **at claim time** rather than being time-weighted per accrual period, an attacker can call `cancelUnlock` immediately before `getReward` to make the entire accumulated reward bucket appear 100% "fully locked" and skip forfeiture on rewards that accrued while the amount was actually in cooldown.

### Finding Description
- `cancelUnlock` (VLMGP.sol:339-349) only mutates local cooldown-slot state; it does not call `IMasterMagpie(masterMagpie).multiclaimFor` or `vlMGPBaseRewarder.updateFor`, unlike `startUnlock` (VLMGP.sol:275-311) and `unlock` (VLMGP.sol:315-337), which both call `multiclaimFor` (forcing an immediate settlement) before mutating cooldown state: [1](#0-0) 

- `getRewardablePercentWAD` (VLMGP.sol:193-218) computes the forfeit-exempt percentage from `getUserTotalLocked` / `getUserAmountInCoolDown` **evaluated at call time**: [2](#0-1) 

- In `vlMGPBaseRewarder`, per-user reward accrual (`_updateFor`) is deferred until the next call that triggers `updateReward`/`updateRewards`/`updateFor` (e.g. `getReward`, `getRewards`, `MasterMagpie._harvestBaseRewarder`). It accumulates the *entire* `rewardPerToken` delta since the last snapshot into `userRewards`, regardless of how the user's cooldown status varied during that interval: [3](#0-2) 

- The forfeiture is then computed once on the whole accumulated bucket using the account's *current* `getRewardablePercentWAD`: [4](#0-3) 

Exploit flow:
1. Attacker holds vlMGP and calls `startUnlock(partialAmount)`. This triggers `multiclaimFor` which settles rewards immediately at the pre-cooldown (100%) state, so no loss yet, and then commits the slot to cooldown.
2. Reward managers call `queueNewRewards`/`queueMGP` over time, increasing `rewardPerTokenStored` while the attacker's `getRewardablePercentWAD` is `<100%` due to the active cooldown slot. The attacker does not call anything that triggers `_updateFor` during this window, so `userRewardPerTokenPaid` stays stale and the full delta accumulates unrealized.
3. Immediately before claiming, attacker calls `cancelUnlock(slotIndex)`, zeroing `slot.amountInCoolDown` and decrementing `totalAmountInCoolDown` with no reward-state synchronization.
4. Attacker calls `getReward` (via `MasterMagpie.multiclaim` → `_claimBaseRewarder` → `rewarder.getReward`). The `updateReward` modifier invokes `_updateFor`, crediting the *entire* stale reward delta to `userRewards`. `_sendReward` then computes `_calExpireForfeit` using `getRewardablePercentWAD`, which is now 100% because `amountInCoolDown == 0`, yielding `forfeitAmount == 0` for a bucket that should have been partially forfeited for the cooldown-period accrual.

No existing modifier (`whenNotPaused`, absence of `nonReentrant` on `cancelUnlock`) or accounting step prevents this, because the vulnerability is a state-synchronization gap, not a reentrancy or access-control issue.

### Impact Explanation
This is theft of unclaimed/forfeited yield that is meant to be redistributed to other lockers via `_queueNewRewardsWithoutTransfer` (called from `_sendReward`/`queueMGP` when `forfeitAmount > 0`). By timing `cancelUnlock` right before `getReward`, any vlMGP holder with an active cooldown slot can capture 100% of rewards that accrued during their cooldown, at the expense of the forfeit pool that would otherwise go to fully-locked users. This breaks the reward-conservation invariant and constitutes theft of unclaimed yield belonging to other lockers.

### Likelihood Explanation
- No privileged role is required; any vlMGP holder can call `startUnlock`, wait for reward emissions, then call `cancelUnlock` and `getReward`/`multiclaim` themselves.
- The only precondition is having an active cooldown slot with `rewardablePercentWAD < 100%` while reward-per-token increases via routine `queueNewRewards`/`queueMGP` calls, which happen regularly as part of normal protocol operation.
- The attack is fully repeatable: `startUnlock`→wait→`cancelUnlock`→`getReward` can be looped indefinitely for any vlMGP position.

### Recommendation
Force a reward settlement (`_updateFor`) on the account inside `cancelUnlock` (as is already done in `startUnlock`/`unlock` via `multiclaimFor`) before mutating `slot.amountInCoolDown`/`totalAmountInCoolDown`, so any pending reward that accrued during the cooldown period is snapshotted and forfeited proportionally under the still-in-cooldown `getRewardablePercentWAD`. More robustly, `vlMGPBaseRewarder` should track and apply forfeiture per reward-accrual interval (time-weighted against the user's cooldown status during each interval) rather than applying a single point-in-time percentage retroactively to an entire accumulated bucket.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `VLMGP`, `vlMGPBaseRewarder`; register vlMGP pool with the rewarder.
2. User A locks `1000 MGP`, calls `startUnlock(500)` to put 500 into cooldown (settles pre-cooldown rewards to 0 forfeiture baseline).
3. Manager calls `queueNewRewards(rewardAmount, rewardToken)` (or `queueMGP`) multiple times over simulated time while User A's slot remains in cooldown; do **not** call anything that triggers `_updateFor` for User A in between.
4. Assert `vlMGP.getRewardablePercentWAD(userA) < 1e18` at this point (confirms forfeiture should apply).
5. Call `vlMGP.cancelUnlock(slotIndex)` as User A.
6. Assert `vlMGP.getRewardablePercentWAD(userA) == 1e18` immediately after.
7. Call `masterMagpie.multiclaim([vlMGPAddress])` (or `rewarder.getReward`) as User A.
8. Assert `_calExpireForfeit`/emitted `RewardPaid` shows `forfeitAmount == 0` and the full accrued reward is transferred to User A, instead of a proportional forfeiture matching the cooldown-period accrual — demonstrating the stolen forfeit-pool yield.
