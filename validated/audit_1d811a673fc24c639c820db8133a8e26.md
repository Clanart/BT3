### Title
OP_RETURN `data` output excluded from transaction weight/fee accounting — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

In `SignableTransaction::new`, the transaction's vsize/weight is computed by `calculate_weight_vbytes`, which rebuilds a candidate transaction from only `payments` and the optional `change` output. The `data` OP_RETURN output — pushed onto `tx_outs` before the weight call — is never passed into the accounting, so the size that determines `needed_fee`, the minimum-relay check, and the `MAX_STANDARD_TX_WEIGHT` check is undersized by the exact bytes that are later emitted into the signed transaction.

### Finding Description

`SignableTransaction::new` builds `tx_outs`, pushes the OP_RETURN output carrying `data` at `send.rs:194-202`, then computes size at `send.rs:204`:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (send.rs:62-94) constructs its throwaway `Transaction` with `output: payments.iter().map(...)` — only the payment outputs plus the optional change (`send.rs:95-99`). The OP_RETURN output (up to 80 bytes of payload plus `OP_RETURN`, pushdata opcode, CompactSize length, and the 9-byte TxOut header — roughly 90–100 weight/vbytes for max-size data) exists in the final `tx` but is absent from the measured one.

This mirrors the kernel bug class exactly: `datalen` (the final transaction) includes the carried `fraggap` bytes (the data output), but `alloclen` (the weight/vbytes used to size the fee and validate limits) does not, so the "linear region" (vsize budget) is undersized while the emitted artifact is oversized by the same amount.

The same omission occurs in the change path at `send.rs:226`, where `fee_with_change` is computed with `payments` only. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` understates the fee required for the requested feerate; when a change output exists, `change = input_sat - payment_sat - fee_with_change` is correspondingly **overstated** (the change value absorbs the unaccounted fee for the data output).
- The `TooLowFee` check at `send.rs:211` compares against the understated vbytes, so a transaction at the boundary can be produced whose *actual* fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` and is rejected by relays.
- The `TooLargeTransaction` check at `send.rs:241` uses `weight` excluding the data output, so a transaction near `MAX_STANDARD_TX_WEIGHT` (400,000 WU) can pass the check while the signed transaction exceeds it and is non-standard/unbroadcastable.

### Impact Explanation

The FROST multisig completes `taproot_key_spend_signature_hash` signing over the real transaction (send.rs:373-397) and produces a fully signed Bitcoin transaction that is either (a) paying a lower effective feerate than requested and possibly below the relay minimum, or (b) over the standard weight limit — in both cases network-rejected, stalling the spend until reconstructed without data. If change is present, the change output value is inflated by the unaccounted fee delta, so accounting relying on `needed_fee()`/`fee()` diverges from the on-chain result. This is an incorrect size/accounting formula producing a signed artifact that does not meet the constraints it was checked against — a reachable Medium: the `data` argument is caller/protocol-supplied transaction data (the processor builds these transactions from user-initiated plans), not something requiring privileged access.

### Likelihood Explanation

Triggered whenever `SignableTransaction::new` is called with `Some(data)` of non-trivial length — the only precondition. The impact materializes when the understated vbytes crosses a boundary: `fee_per_vbyte` at/near the relay minimum, payments+inputs near the weight limit, or change margin near `DUST`. Since `data` is capped at 80 bytes, the fee delta is bounded (~90 vbytes × fee rate), limiting severity to Medium.

### Recommendation

Include the OP_RETURN output in the measured transaction inside `calculate_weight_vbytes` — either pass `data` (or the fully-built `tx_outs`) into it instead of `payments`, or add the data output's weight (`TxOut` with `ScriptBuf::new_op_return(...)`) to the computed `weight`/`vbytes`. Apply the same fix to both the initial call (send.rs:204) and the change-variant call (send.rs:226), and to the `weight` used for the `MAX_STANDARD_TX_WEIGHT` check.

### Proof of Concept

```rust
// networks/bitcoin context: any ReceivedOutput, change, and 80-byte data
let data = vec![0xaa; 80];
let tx = SignableTransaction::new(
    vec![output],            // funded input
    &payments,               // payments totalling input_sat - needed_fee - DUST
    Some(change_script),     // force the change path
    Some(data.clone()),      // OP_RETURN output pushed at send.rs:195-202
    fee_per_vbyte,
).unwrap();

// The fee actually paid
let actual = tx.fee();
// vbytes used in accounting excludes the data output
let (_, accounted_vbytes) = SignableTransaction::calculate_weight_vbytes(
    tx.transaction().input.len(), payments, Some(&change_script));
// Real vsize includes the ~92-byte OP_RETURN output
let real_vbytes = tx.transaction().vsize() as u64;

// 1) Effective fee rate is below requested:
assert!(actual < fee_per_vbyte * real_vbytes);

// 2) If fee_per_vbyte * accounted_vbytes == min_relay_floor,
//    actual / real_vbytes < DEFAULT_MIN_RELAY_TX_FEE / 1000 -> relay rejects.

// 3) With inputs/payments crafted so accounted weight == MAX_STANDARD_TX_WEIGHT
//    minus ~300 WU, the check at send.rs:241 passes while the real
//    tx.weight() exceeds the standard limit -> unbroadcastable signed tx.
```

The check at `send.rs:171` caps `data` at 80 bytes but does not compensate the weight accounting, so `PushBytesBuf::try_from(data)` at send.rs:198 always succeeds while its ~92 vbytes are never billed.
