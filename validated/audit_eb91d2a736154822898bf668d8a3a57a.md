### Title
Unspendable `OP_RETURN` payment scripts are accepted and signed, burning funds - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` validates only that each payment amount is at least `DUST`, but does not validate that the supplied `ScriptBuf` represents a spendable output. An `OP_RETURN` script can therefore be supplied as a payment destination, copied into the signed transaction, and irrevocably burn the associated amount.

### Finding Description
The payment loop checks `amount < DUST` but ignores `payment.0`, the destination script. [1](#0-0)  The unchecked script is then cloned directly into a value-bearing `TxOut`. [2](#0-1)  `data` is the only path intentionally converted to an `OP_RETURN`, and that output is correctly assigned zero value, showing that the code recognizes `OP_RETURN` as non-payment data rather than a fund destination. [3](#0-2)  After construction, `multisig` validates only that the prevout scripts correspond to the threshold keys, not that the new outputs are spendable. [4](#0-3)  `sign` then produces threshold signature shares over the Taproot sighash committing to the transaction containing the burn output. [5](#0-4) 

### Impact Explanation
A payment carrying any amount at or above `DUST` can be sent to `OP_RETURN`, which is provably unspendable under Bitcoin rules. Once threshold signing completes and the transaction is confirmed, the output value is permanently burned. This is the Bitcoin analogue of accepting `address(0)` as a fee or payment recipient.

### Likelihood Explanation
The destination script is a public caller-controlled input to `SignableTransaction::new`. No malformed encoding, private state, validator collusion, or special network access is required: a validly encoded `OP_RETURN` script reaches the vulnerable path directly.

### Recommendation
Reject known-unspendable destination scripts for value-bearing payments and change outputs. At minimum, reject `script_pubkey.is_op_return()` before constructing `tx_outs`; preferably require destinations to be an explicitly supported spendable output type such as P2TR.

### Proof of Concept
```rust
use bitcoin::{
  script::{PushBytesBuf, ScriptBuf},
  transaction::Transaction,
};
use bitcoin_serai::wallet::{Scanner, SignableTransaction};

// funding_tx pays to scanner's registered P2TR script.
let input = scanner.scan_transaction(&funding_tx).remove(0);

// This script is valid to encode but impossible to spend from.
let burn_script = ScriptBuf::new_op_return(PushBytesBuf::new());

// Accepted because only the amount is checked.
let signable = SignableTransaction::new(
  vec![input],
  &[(burn_script, 10_000)],
  None,
  None,
  4,
).unwrap();

assert!(signable.transaction().output[0].script_pubkey.is_op_return());
assert_eq!(signable.transaction().output[0].value.to_sat(), 10_000);

// multisig/sign will produce signatures committing to this burn output.
let machine = signable.multisig(&threshold_keys).unwrap();
```
