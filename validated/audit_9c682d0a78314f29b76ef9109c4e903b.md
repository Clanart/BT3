### Title
Missing binding of payout output value to withdrawal amount enables reimbursement without a real payout - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
`bridge_circuit` only checks that the payout transaction's **input** at `payout_input_index` matches the `(txid, vout)` pair (`user_wd_outpoint`/`vout`) proven via `verify_storage_proofs`; it never inspects `input.payout_spv.transaction.output[..].value`. Because `deposit_constant` and `journal_hash` are computed purely from txids, pubkeys and block hashes, a payout transaction that spends the correct withdrawal input but sends 0 sats to the withdrawer (paying everything to fees) produces an identical, accepted `journal_hash`.

### Finding Description
The intended binding should be: `value paid to the withdrawer's output in the payout tx == bridge_amount_sats recorded for that withdrawal on Citrea`. This equality is never checked.

Tracing `bridge_circuit` in [1](#0-0) , the only assertions tying the payout tx to the withdrawal are on the **input** side:
- `user_wd_txid == input.payout_spv.transaction.input[payout_input_index].previous_output.txid`
- `vout == input.payout_spv.transaction.input[payout_input_index].previous_output.vout`

`verify_storage_proofs` ( [2](#0-1) ) only returns `(WithdrawalOutpointTxid, vout, MoveTxid)` — no amount is read from the Bridge contract storage or bound into the circuit at all.

`get_first_op_return_output` ( [3](#0-2)  and used at [4](#0-3) ) only extracts the operator's x-only pubkey from an OP_RETURN, and `deposit_constant` ( [5](#0-4) ) hashes `move_txid`, watchtower pubkeys digest, `operator_xonlypk`, connector index, `round_txid`, `kickoff_round_vout`, and `genesis_state_hash` — none of which is a Bitcoin amount. `journal_hash` ( [6](#0-5) ) further hashes only block hashes, watchtower flags and `deposit_constant`.

Root cause: the withdrawal UTXO registered on Citrea (`user_wd_outpoint`/`vout`) is documented as "User's withdrawal input" ( [7](#0-6) ) — i.e., an identity-linking input the withdrawer controls — not the output that pays them. The actual payout output (`output_txout`) is freely chosen by whoever builds the payout tx (the operator's `withdraw()` RPC accepts `out_script_pubkey`/`out_amount` as caller-supplied parameters, see [8](#0-7) ), and nothing downstream — neither `bridge_circuit` nor any BitVM/disprove script derived from it — re-checks that this output actually paid the recorded `bridge_amount` to the withdrawer.

The only amount sanity check in the whole path is `Operator::is_profitable` ( [9](#0-8) ), which is (a) purely an off-chain, operator-side self-interest check with no cryptographic enforcement, and (b) itself buggy: if `out_amount` (e.g. 0) is less than `input_amount`, the `checked_sub` underflows and the function returns `true` ("profitable") at [10](#0-9) , i.e. it does not reject a 0-value payout output. This check is not part of the zk circuit's constraints and provides no protection against a malicious operator who deliberately skips or bypasses it when constructing host params for the prover.

Because operators are precisely the untrusted party this optimistic BitVM/challenge design is meant to constrain (that is the entire reason the Assert → ChallengeTimeout → Reimburse path exists), and because `bridge_circuit` is the sole artifact that gates whether a claimed payout is valid, the missing amount binding means a malicious operator can submit `BridgeCircuitInput` for a payout transaction that spends the correct withdrawal input but pays ~0 to the withdrawer, obtain the same `journal_hash` that would be produced for a legitimate full-value payout, and proceed through kickoff/assert/challenge-timeout to Reimburse.

### Impact Explanation
An operator (or any party able to submit host params for the bridge circuit, e.g., during proving/disprove) can be reimbursed the full `bridge_amount` from the presigned move-to-vault UTXO without having fronted any real value to the withdrawer. This is exactly the scoped Critical impact: "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal." It is repeatable per deposit/withdrawal and per operator, since the missing check is structural (in the shared `bridge_circuit` logic used by every operator/deposit), not specific to one instance.

### Likelihood Explanation
Preconditions are modest and match the operator's own normal workflow: a completed deposit with a `bridge_amount` UTXO in move-to-vault, a Citrea `withdraw` call registering a `user_wd_outpoint`/`vout`, and a payout transaction spending that exact outpoint (which the operator or attacker-with-correct-signature can construct, subject only to the withdrawer's own signature over their input — the withdrawer's signature does not force any particular output value/structure beyond what the signer signs, and if the withdrawer signs with a sighash flag such as `ANYONECANPAY`/`SINGLE`/`NONE`, or if the operator itself is the attacker in the collusive/self-serving case, outputs can be freely rewritten). No mainnet, verifier collusion, key compromise, or Citrea sequencer complicity is required — only the ability to produce `BridgeCircuitInput` accepted by the guest, which is entirely determined by locally reproducible Bitcoin/Citrea data.

### Recommendation
Bind the payout's actual paid amount into the circuit's committed output. Concretely, `bridge_circuit` should read the payout transaction's designated withdrawer output (e.g., a well-defined output index/convention) and assert its `value` equals (or is at least `bridge_amount - allowed_fee_tolerance`, matching whatever amount was proven via the withdrawal's storage proof or a newly added storage proof of the withdrawal amount on Citrea). This value should then be folded into `deposit_constant` or `journal_hash` so any discrepancy changes the committed journal and can be caught/disproven.

```rust
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant {
    // pubkeys are 32 bytes long
    let pubkey_concat = watchtower_pubkeys
        .iter()
        .flat_map(|pubkey| pubkey.to_vec())
        .collect::<Vec<u8>>();

    let watchtower_pubkeys_digest: [u8; 32] = Sha256::digest(&pubkey_concat).into();

    let pre_deposit_constant = [
        &move_txid,
        &watchtower_pubkeys_digest,
        &operator_xonlypk,
        &watchtower_challenge_connector_start_idx.to_be_bytes()[..],
        &round_txid,
        &kickoff_round_vout.to_be_bytes()[..],
        &genesis_state_hash,
    ]
    .concat();

    DepositConstant(Sha256::digest(&pre_deposit_constant).into())
}
```

```rust
pub fn journal_hash(
    payout_tx_blockhash: PayoutTxBlockhash,
    latest_blockhash: LatestBlockhash,
    challenge_sending_watchtowers: ChallengeSendingWatchtowers,
    deposit_constant: DepositConstant,
) -> blake3::Hash {
    let concatenated_data = [
        payout_tx_blockhash.0,
        latest_blockhash.0,
        challenge_sending_watchtowers.0,
    ]
    .concat();

    let binding = blake3::hash(&concatenated_data);
    let hash_bytes = binding.as_bytes();

    let concat_journal = [deposit_constant.0, *hash_bytes].concat();

    blake3::hash(&concat_journal)
}
```

```rust
pub fn verify_storage_proofs(
    storage_proof: &StorageProof,
    state_root: [u8; 32],
) -> (WithdrawalOutpointTxid, u32, MoveTxid) {
    let utxo_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_utxo)
            .expect("Failed to deserialize UTXO storage proof");

    let vout_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_vout)
            .expect("Failed to deserialize vout storage proof");

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_deposit_txid)
            .expect("Failed to deserialize deposit storage proof");

    let storage_address: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(UTXOS_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let storage_key_utxo: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2);

    let storage_key_vout: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2 + 1);

    let storage_address_deposit: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(DEPOSIT_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let deposit_storage_key: alloy_primitives::Uint<256, 4> =
        storage_address_deposit + U256::from(storage_proof.index);

    let deposit_storage_key_bytes = deposit_storage_key.to_be_bytes::<32>();

    if deposit_storage_key_bytes != deposit_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid deposit storage key. left: {:?} right: {:?}",
            deposit_storage_key_bytes,
            deposit_storage_proof.key.as_b256().0
        );
    }

    if storage_key_utxo.to_be_bytes() != utxo_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid withdrawal UTXO storage key. left: {:?} right: {:?}",
            storage_key_utxo.to_be_bytes::<32>(),
            utxo_storage_proof.key.as_b256().0
        );
    }

    if storage_key_vout.to_be_bytes() != vout_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid withdrawal vout storage key. left: {:?} right: {:?}",
            storage_key_vout.to_be_bytes::<32>(),
            vout_storage_proof.key.as_b256().0
        );
    }

    storage_verify(&utxo_storage_proof, state_root);

    storage_verify(&deposit_storage_proof, state_root);

    storage_verify(&vout_storage_proof, state_root);

    let buf: [u8; 32] = vout_storage_proof.value.to_be_bytes();

    // ENDIANNESS SHOULD BE CHECKED THIS FIELD IS 4 BYTES in the contract
    let vout = u32::from_le_bytes(
        buf[28..32]
            .try_into()
            .expect("Vout value conversion failed"),
    );

    let wd_outpoint = WithdrawalOutpointTxid(utxo_storage_proof.value.to_be_bytes());

    let move_txid = MoveTxid(deposit_storage_proof.value.to_be_bytes());

    (wd_outpoint, vout, move_txid)
}
```

```rust
    /// Checks if the withdrawal amount is within the acceptable range.
    fn is_profitable(
        input_amount: Amount,
        withdrawal_amount: Amount,
        bridge_amount_sats: Amount,
        operator_withdrawal_fee_sats: Amount,
    ) -> bool {
        // Use checked_sub to safely handle potential underflow
        let withdrawal_diff = match withdrawal_amount
            .to_sat()
            .checked_sub(input_amount.to_sat())
        {
            Some(diff) => Amount::from_sat(diff),
            None => {
                // input amount is greater than withdrawal amount, so it's profitable but doesn't make sense
                tracing::warn!(
                    "Some user gave more amount than the withdrawal amount as input for withdrawal"
                );
                return true;
            }
        };

        if withdrawal_diff > bridge_amount_sats {
            return false;
        }

        // Calculate net profit after the withdrawal using checked_sub to prevent panic
        let net_profit = match bridge_amount_sats.checked_sub(withdrawal_diff) {
            Some(profit) => profit,
            None => return false, // If underflow occurs, it's not profitable
        };

        // Net profit must be bigger than withdrawal fee.
        // net profit doesn't take into account the fees, but operator_withdrawal_fee_sats should
        net_profit >= operator_withdrawal_fee_sats
    }
```
