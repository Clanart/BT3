### Title
Consensus-incentive reward misattribution: batching multiple `ConsensusMessage`s lets the first message's signer collect rewards for every state machine advanced in the batch - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives` rewards relayers for delivering ISMP consensus updates. Its `FeeHandler::on_executed` extracts the reward recipient from **only the first message** in the batch (`messages.get(0)`), then pays that single relayer for **every** `StateMachineUpdated` event produced by the **entire batch**, regardless of which message (and which signer) actually produced each event.

### Finding Description
`on_executed` derives `relayer_account` solely from `messages[0]`, requiring it to be a `Message::Consensus` whose embedded `signer` field verifies: [3](#0-2) 

It then collapses **all** `StateMachineUpdated` events in the batch — which may originate from other `Message::Consensus` entries with different embedded signers — into `highest_per_state_machine`, and pays the single `relayer_account` (from message 0) a reward for each state machine represented: [4](#0-3) 

The `handle_unsigned` extrinsic that invokes this path is a permissionless unsigned call: `messages: Vec<Message>` is entirely attacker-controlled, and each `Message::Consensus` carries its own self-authenticating `signer`/`consensus_proof` — the extrinsic itself has no signed origin binding it to one relayer. [1](#0-0) 

Because consensus proofs are public and freely reproducible by anyone (any node can construct a valid consensus proof for any tracked chain once the underlying finality/justification data is available), an attacker can:
1. Construct their own trivial/cheap `Message::Consensus` for a low-cost state machine, placed as `messages[0]`.
2. Append one or more additional, independently valid `Message::Consensus` entries for expensive-to-reward state machines (built from publicly available consensus data, using an arbitrary/attacker-chosen `signer` value since nothing ties reward eligibility for messages[1..] to their own signer check).
3. Submit the whole batch via `handle_unsigned`.

Since `calculate_reward` re-derives `latest_commitment_height`/`previous_commitment_height` from the (now-updated) `IsmpHost` state rather than from anything tied to the specific message that produced the event, and the payout loop iterates `highest_per_state_machine` without re-verifying which signer is entitled to which state machine's reward, the attacker's single `relayer_account` (from message 0) collects the **full reward and reputation mint** for every state machine advanced in the batch — including advances that a legitimate, unrelated relayer's proof would have produced had it been submitted alone.

### Impact Explanation
This is a direct fund-diversion bug in the treasury-funded relayer incentive system: `T::Currency::transfer` moves treasury funds to the attacker-controlled account for state-machine advances the attacker did not uniquely earn, and `T::ReputationAsset::mint_into` mints reputation to the wrong beneficiary. It matches the "stealing/loss of funds" and "wrong beneficiary" bounty categories, since real relayer rewards move to an account other than the one whose proof actually did the qualifying work, at no cost beyond batching messages in a single unsigned extrinsic (which itself is free by design).

### Likelihood Explanation
No privileged access, relayer collusion, or private key compromise is required — the exploit only needs the ability to submit a `handle_unsigned` extrinsic with a crafted `Vec<Message>`, which any unprivileged network participant can already do, and consensus proofs for any tracked chain are public data by protocol design ("proofs...are freely provided by its connected chains" per the relayer documentation). The comment in the code even acknowledges the multi-event-per-batch collapsing behavior but only fixes double-payment to the *same* relayer, not misattribution across *different* relayers within one batch.

### Recommendation
Track the relayer/signer per individual `Message::Consensus` and its resulting `StateMachineUpdated` event(s), instead of collapsing to a single `relayer_account` for the whole batch. Verify and pay each state machine's reward to the signer of the specific consensus message that produced its `StateMachineUpdated` event, rather than assuming `messages[0]`'s signer is responsible for all events in the batch.

### Proof of Concept
1. Attacker controls account `R` and knows a valid, publicly reconstructable consensus proof `P_B` for state machine `B` (high `CostPerBlock`), originally producible by any relayer, plus their own trivial proof `P_A` for cheap state machine `A`.
2. Attacker submits `handle_unsigned([Message::Consensus{proof: P_A, signer: sig_R}, Message::Consensus{proof: P_B, signer: sig_R_or_anything}])` (single unsigned extrinsic, both messages valid so `execute` succeeds).
3. `on_executed` reads `messages[0]` (`P_A`), recovers `relayer_account = R`, and finds `StateMachineUpdated` events for **both** `A` and `B` in `events`.
4. `highest_per_state_machine` contains both `A` and `B`; the loop calls `process_message` for each, transferring `CostPerBlock_A * blocks_A` and `CostPerBlock_B * blocks_B` treasury funds to `R`, plus minting reputation for both — even though `R` did not need to independently prove entitlement to `B`'s reward.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
