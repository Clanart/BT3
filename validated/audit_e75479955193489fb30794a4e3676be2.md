### Title
Any user paying tx fees can panic-halt block finalization via `WriteDeferredBalances` when a per-tx deferred deposit hits a blocked recipient/allow-list check - (File: `sei-cosmos/x/bank/keeper/keeper.go`)

### Summary
`WriteDeferredBalances` aggregates per-transaction deferred module-account credits (fees, tokenfactory mints, etc.) and, at the very end of every block, iterates once per destination module account calling `AddCoins`. If `AddCoins` returns an error for *any single* module account in that block, the function `panic(err)` instead of skipping/handling that entry, exactly the same "single bad actor halts everyone's batch operation" bug class as the Sherlock `SherXERC20.payOffDebtAll` finding — except here the blast radius is the entire block's finalization rather than a single protocol's payments.

### Finding Description
`DeductFees` (called by the standard Cosmos ante `DeductFeeDecorator` on essentially every fee-paying transaction) calls `BankKeeper.DeferredSendCoinsFromAccountToModule`, which subtracts the fee from the payer immediately but only records the module-account credit in an in-memory `deferredCache` keyed by module address and tx index: [1](#0-0) [2](#0-1) 

At the end of block processing, `app.go`'s `ProcessBlock` unconditionally calls `app.BankKeeper.WriteDeferredBalances(ctx)` once, after all transactions in the block have executed: [3](#0-2) 

`WriteDeferredBalances` iterates over every module address that accumulated a deferred credit in the block and calls `k.AddCoins` for each one. If `AddCoins` returns an error (e.g., `ErrInvalidRecipient` from `CanSendTo`, or `ErrInvalidCoins`), the function does not skip or retry that single account — it panics, aborting the *entire* end-of-block deferred settlement for that block: [4](#0-3) 

`AddCoins` itself can fail for reasons unrelated to the sender's intent, most notably `CanSendTo` returning false (blocked-address / recipient-checker rejection): [5](#0-4) 

This mirrors the Sherlock pattern precisely: a batch operation (`payOffDebtAll` there, `WriteDeferredBalances` here) iterates over multiple independent entities (protocols there, module accounts here) and a single entity's failure condition aborts processing for all the others in the same batch — except here the "batch" is the whole block, not just one keeper call for one user, so the potential impact (panic during `ProcessBlock`/deliver-tx finalization) is more severe.

### Impact Explanation
A panic thrown from `WriteDeferredBalances` propagates out of `ProcessBlock`. `ProcessBlock` has a `recover()` that converts panics into an `err` return value, which will cause block processing to fail rather than crash the node outright, but it still means the block cannot be finalized as intended and consensus-critical state transition logic aborts non-deterministically depending on which module accounts received deferred credits that block: [6](#0-5) 
If any validator's local state differs (e.g., only some validators have added a given address to `blockedAddrs` via a runtime recipient-checker or genesis config), this can also create disagreement between nodes about whether the block finalized, which is a chain-halt/liveness risk — squarely in the accepted "validator halt" / "block delay" impact category.

### Likelihood Explanation
Likelihood is bounded because triggering the failure requires the destination module account (fee collector or a similarly-deferred module account) to actually fail `AddCoins`/`CanSendTo` in a given block, which today's default configuration may not allow an ordinary user to force directly (blocked addresses are typically module accounts configured by governance, not user-controlled recipients). This makes the finding closer to Medium: it identifies a real code-level fragility analogous to the report (single-entity failure aborts a shared batch operation covering many independent parties, and does so at block-finalization scope rather than a narrow keeper call), but I could not fully verify a concrete unprivileged path that forces `AddCoins` to fail for a targeted module account within `WriteDeferredBalances` — that requires further investigation of `CanSendTo`/`RegisterRecipientChecker` usage and whether any deferred-credit recipient module address can be made to fail via user-supplied denoms (e.g., interaction with `IsInDenomAllowList`/`SetDenomAllowList` restricted-denom checks feeding into `AddCoins`, which was not fully traced within the available context).

### Recommendation
In `WriteDeferredBalances`, do not `panic` on a per-module `AddCoins` failure. Instead, either (a) skip that module's deferred credit while still processing and clearing all other modules' credits, then surface the failure via a returned error/event without aborting the whole call, or (b) fail closed only for that single deferred entry (e.g., re-queue or drop with a logged invariant-check event) so that one problematic module address cannot block settlement for every other module and block finalization as a whole. This mirrors the Sherlock-recommended mitigation of preventing one bad entity from blocking all iteration participants.

### Proof of Concept
Not independently reproduced against a running node within the scope of this analysis; the control-flow proof is the direct code path traced above:
1. `DeductFeeDecorator.AnteHandle` → `checkDeductFee` → `DeductFees` → `BankKeeper.DeferredSendCoinsFromAccountToModule(ctx, payer, types.FeeCollectorName, fee)` for essentially any fee-paying transaction. [1](#0-0) 
2. At end of block, `app.BankKeeper.WriteDeferredBalances(ctx)` is called once for the whole block. [3](#0-2) 
3. `WriteDeferredBalances` calls `k.AddCoins(ctx, moduleAddr, amount, true)` for each module address with accumulated deferred credit and `panic(err)` on any failure. [7](#0-6) 

Confirming a concrete unprivileged trigger for `AddCoins` failure on a fee-collector-class module account requires additional investigation into `CanSendTo`/allow-list configuration, which was not completed here.

func DeductFees(bankKeeper types.BankKeeper, ctx sdk.Context, acc types.AccountI, fees sdk.Coins) error {
	if !fees.IsValid() {
		return sdkerrors.Wrapf(sdkerrors.ErrInsufficientFee, "invalid fee amount: %s", fees)
	}

	err := bankKeeper.DeferredSendCoinsFromAccountToModule(ctx, acc.GetAddress(), types.FeeCollectorName, fees)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInsufficientFunds, "%s", err.Error())
	}

	return nil

func (k BaseKeeper) DeferredSendCoinsFromAccountToModule(
	ctx sdk.Context, senderAddr sdk.AccAddress, recipientModule string, amount sdk.Coins,
) error {
	if k.deferredCache == nil {
		panic("bank keeper created without deferred cache")
	}
	// Deducts Fees from the Sender Account
	err := k.SubUnlockedCoins(ctx, senderAddr, amount, true)
	if err != nil {
		return err
	}
	// get recipient module address
	moduleAcc := k.ak.GetModuleAccount(ctx, recipientModule)
	if moduleAcc == nil {
		panic(sdkerrors.Wrapf(sdkerrors.ErrUnknownAddress, "module account %s does not exist", recipientModule))
	}
	// get txIndex
	txIndex := ctx.TxIndex()
	if txIndex < 0 {
		return fmt.Errorf("negative tx index: %d", txIndex)
	}
	err = k.deferredCache.UpsertBalances(ctx, moduleAcc.GetAddress(), uint64(txIndex), amount) //nolint:gosec // bounds checked above
	if err != nil {
		return err
	}

	return nil
}

// WriteDeferredDepositsToModuleAccounts Iterates on all the deferred deposits and deposit them into the store
func (k BaseKeeper) WriteDeferredBalances(ctx sdk.Context) []abci.Event {
	if k.deferredCache == nil {
		panic("bank keeper created without deferred cache")
	}
	ctx = ctx.WithEventManager(sdk.NewEventManager())

	// maps between bech32 stringified module account address and balance
	moduleAddrBalanceMap := make(map[string]sdk.Coins)
	// slice of modules to be sorted for consistent write order later
	var moduleList []string

	// iterate over deferred cache and accumulate totals per module
	k.deferredCache.IterateDeferredBalances(ctx, func(moduleAddr sdk.AccAddress, amount sdk.Coin) bool {
		currCoins, ok := moduleAddrBalanceMap[moduleAddr.String()]
		if !ok {
			// add to list of modules
			moduleList = append(moduleList, moduleAddr.String())
			// set the map value
			moduleAddrBalanceMap[moduleAddr.String()] = sdk.NewCoins(amount)
			return false
		}
		// add to currCoins
		newCoins := currCoins.Add(amount)
		// update map
		moduleAddrBalanceMap[moduleAddr.String()] = newCoins
		return false
	})
	// sort module list
	sort.Strings(moduleList)

	// iterate through module list and add the balance to module bank balances in sorted order
	for _, moduleBech32Addr := range moduleList {
		amount, ok := moduleAddrBalanceMap[moduleBech32Addr]
		if !ok {
			err := fmt.Errorf("failed to get module balance for writing deferred balances for address=%s", moduleBech32Addr)
			logger.Error(err.Error())
			panic(err)
		}
		err := k.AddCoins(ctx, sdk.MustAccAddressFromBech32(moduleBech32Addr), amount, true)
		if err != nil {
			logger.Error("Failed to add coin to module address", "coin", amount, "address", moduleBech32Addr, "err", err)
			panic(err)
		}
	}

	// clear deferred cache
	k.deferredCache.Clear(ctx)
	return ctx.EventManager().ABCIEvents()
}

func (k BaseSendKeeper) AddCoins(ctx sdk.Context, addr sdk.AccAddress, amt sdk.Coins, checkNeg bool) error {
	if !k.CanSendTo(ctx, addr) {
		return sdkerrors.ErrInvalidRecipient
	}
	if !amt.IsValid() {
		return sdkerrors.Wrap(sdkerrors.ErrInvalidCoins, amt.String())
	}

	for _, coin := range amt {
		balance := k.GetBalance(ctx, addr, coin.Denom)
		newBalance := balance.Add(coin)

		err := k.setBalance(ctx, addr, newBalance, checkNeg)
		if err != nil {
			return err
		}
	}

	// emit coin received event
	ctx.EventManager().EmitEvent(
		types.NewCoinReceivedEvent(addr, amt),
	)

	return nil
}
