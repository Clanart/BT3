### Title
Missing `log_stacking` calls for `delegate-stack-stx`/`delegate-stack-extend`/`delegate-stack-increase` let PoX position changes bypass `Staking` post-conditions - ([File: pox-locking/src/pox_4.rs])

### Summary
`check_transaction_postconditions` enforces that, in `Deny`/`Originator` modes, every principal whose PoX stacking position changed during a transaction must be covered by a `Staking` post-condition, using `AssetMap::get_all_stacking()` as the source of truth for "what actually got staked." The PoX-4 (and PoX-5) contract-call handlers that lock or increase a *stacker's* STX populate this asset-map "stacking" ledger via `global_context.log_stacking(...)`, but only when the call is the *direct* stacking entry point (`stack-stx`, `stack-extend`, `stack-increase`). The *delegated* counterparts (`delegate-stack-stx`, `delegate-stack-extend`, `delegate-stack-increase`) apply the exact same real STX lock/increase to the stacker's account, yet never call `log_stacking`, so the asset map records nothing for that principal.

### Finding Description

This loop only sees principals present in `asset_map.get_all_stacking()`, i.e. principals for which `AssetMap::add_stacking` (exposed as `global_context.log_stacking`) was called during transaction execution.

Looking at PoX-4's lock-up handlers:
- `handle_stack_lockup_pox_v4` applies the real STX lock via `pox_lock_v4` for both `stack-stx` and `delegate-stack-stx` (dispatched together at [3](#0-2) ), but only logs the stacking amount into the asset map `if function_name == "stack-stx"` [4](#0-3) .
- `handle_stack_lockup_extension_pox_v4` applies the real lock extension via `pox_lock_extend_v4` for both `stack-extend` and `delegate-stack-extend`, but only logs `if function_name == "stack-extend"` [5](#0-4) .
- `handle_stack_lockup_increase_pox_v4` applies the real lock increase via `pox_lock_increase_v4` for both `stack-increase` and `delegate-stack-increase`, but only logs `if function_name == "stack-increase"` [6](#0-5) .

In every case the STX-lock side effect on the *stacker's* account (`pox_lock_v4`/`pox_lock_extend_v4`/`pox_lock_increase_v4`) is unconditional and identical for both the direct and delegated entry points; only the asset-map bookkeeping used for post-condition enforcement is conditioned on `function_name`, silently dropping the entry for `delegate-stack-*` calls. `AssetMap::add_stacking` itself has no such distinction and would correctly record any amount it's given [7](#0-6) ; the omission is purely at the call sites in `pox_4.rs` (and mirrored in `pox_2.rs`/`pox_3.rs`, which use the same pattern).

This is structurally the same bug class as the ApeStaking report: a balance/position aggregator (`getTokenIdStakingAmount` there, `asset_map.get_all_stacking()` here) is fed by only a subset of the code paths that actually change the underlying quantity, so downstream logic that trusts the aggregator (collateral `balanceOf` there, the post-condition "unchecked-asset" enforcement here) under-counts the true effect and a required check can be silently skipped.

### Impact Explanation
When a transaction's origin sets `TransactionPostConditionMode::Deny` (or `Originator` and the stacker happens to be the origin) and relies on a `Staking` post-condition to bound/gate a `delegate-stack-stx`, `delegate-stack-extend`, or `delegate-stack-increase` call, the enforcement loop that is supposed to reject any unchecked stacking action never sees the change, because `asset_map.get_all_stacking()` has no entry for that stacker. The transaction is accepted as if no stacking position changed, even though the stacker's STX was actually locked/extended/increased. This is a mempool/consensus-relevant divergence between the documented guarantee of "Deny mode requires every stacking action to be covered by a `Staking` post-condition" and what the code actually enforces — a High-severity issue matching "a transaction accepted despite the guaranteed check not covering the real state change," which is exactly the class of bug the post-condition mechanism exists to prevent (an asset/position moving past the declared post-conditions).

### Likelihood Explanation
No special privilege is required beyond what any wallet/contract already has to call `delegate-stack-stx`/`delegate-stack-extend`/`delegate-stack-increase` (which itself is gated by a prior `delegate-stx` authorization at the Clarity level, but that authorization has nothing to do with whether the *transaction-level* post-condition enforcement fires). Any contract or wallet flow that composes a `delegate-stack-*` call together with `TransactionPostConditionMode::Deny` and expects the runtime to force a `Staking` post-condition will always be silently bypassed, since the omission is unconditional on this code path, not dependent on adversarial timing or race conditions.

### Recommendation
Make `log_stacking` calls unconditional on the actual STX-lock side effect rather than on `function_name`. Concretely, in `pox-locking/src/pox_4.rs` (and the analogous `pox_2.rs`/`pox_3.rs`/`pox_5.rs` handlers), remove the `if function_name == "stack-stx"`/`"stack-extend"`/`"stack-increase"` guards around `global_context.log_stacking(&stacker, ...)` so that `delegate-stack-stx`, `delegate-stack-extend`, and `delegate-stack-increase` also record the affected stacker's locked amount in the asset map, matching the real economic effect that `pox_lock_v4`/`pox_lock_extend_v4`/`pox_lock_increase_v4` already produce for both call variants.

### Proof of Concept
Not exploitable purely by inspection of state (it requires driving the Clarity VM/AssetMap end-to-end), but the code-level reasoning is directly reproducible:
1. Stacker `S` calls `delegate-stx` to authorize delegate `D` for up to `N` uSTX (Clarity-level authorization, unrelated to the transaction-level post-condition bug).
2. `D` submits a transaction whose payload contract-calls `delegate-stack-stx` for `S`, with `TransactionPostConditionMode::Deny` and *no* `Staking` post-condition for `S` (or one that doesn't match).
3. `handle_contract_call` → `handle_stack_lockup_pox_v4` runs; `pox_lock_v4` locks `S`'s STX for real [4](#0-3) , but because `function_name == "delegate-stack-stx" != "stack-stx"`, `global_context.log_stacking` is never called.
4. `check_transaction_postconditions` runs its Staking-coverage loop over `asset_map.get_all_stacking()` [2](#0-1) ; since `S` has no entry in `stacking_map`, the loop finds nothing to flag, and the transaction is accepted despite `Deny` mode and no covering `Staking` post-condition — contradicting the documented "every staked amount must be covered" invariant.

    /// Records an amount stacked or delegated for stacking by `principal`.
    ///
    /// Before Epoch 4.0, a later entry replaces an earlier entry. Starting in
    /// Epoch 4.0, entries are accumulated.
    pub fn add_stacking(
        &mut self,
        principal: &PrincipalData,
        amount: u128,
        epoch_id: StacksEpochId,
    ) -> Result<(), AssetMapError> {
        match self.stacking_map.entry(principal.clone()) {
            Entry::Occupied(mut occupied_entry) => {
                let amount = if epoch_id.sums_stacking_assetmap() {
                    occupied_entry
                        .get()
                        .checked_add(amount)
                        .ok_or(AssetMapError::AmountOverflow)?
                } else {
                    amount
                };
                occupied_entry.insert(amount);
            }
            Entry::Vacant(vacant_entry) => {
                vacant_entry.insert(amount);
            }
        }
        Ok(())
    }
