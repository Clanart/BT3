Based on my investigation, the analog identified is the immutable `authorized_providers` list curried into the CR-CAT (Credential Restricted CAT) puzzle, which cannot be updated or extended once the asset is created.

### Title
Immutable `authorized_providers` list in CR-CAT puzzle can permanently lock funds if all listed VC providers become unusable - (File: chia/wallet/vc_wallet/cr_cat_drivers.py)

### Summary
`construct_cr_layer()` curries a fixed `authorized_providers` list and `proofs_checker` program directly into every CR-CAT coin's puzzle at mint time [1](#0-0) . There is no mechanism in the CR-CAT driver, `CRCATWallet`, or the CLVM layer to change this list for coins that already exist on-chain, analogous to the backstop pool's covered-pool list that could be added to but never pruned.

### Finding Description
Every CR-CAT coin bakes its `authorized_providers` (a list of DID launcher IDs permitted to issue the Verified Credential (VC) required to move the coin) and `proofs_checker` into the puzzle hash itself via `construct_cr_layer`/`construct_cr_layer_hash` [2](#0-1) . This list is fixed for the lifetime of the coin and is propagated unchanged to every descendant coin through `do_spend`/`get_next_from_coin_spend`, which always carries forward `self.authorized_providers` [3](#0-2) .

To spend a CR-CAT, the spender must find a VC issued by one of the `authorized_providers` and produce a valid proof-of-inclusion satisfying `proofs_checker`. `VCWallet.get_vc_with_provider_in_and_proofs` and `add_vc_authorization` in the offer/trade flow explicitly require a VC whose provider is in this fixed list, and raise `ValueError` if none is found [4](#0-3) . `TradeManager.check_for_requested_payment_modifications` similarly rejects requesting CR-CATs when no VC can approve them [5](#0-4) .

If every DID provider in the curried `authorized_providers` list ceases to be usable (provider DID retired/compromised/unable to issue proofs, or the referenced `proofs_checker` flags become semantically stale), there is no owner or protocol path to add a new authorized provider or remove/replace the defunct one — the puzzle hash, and therefore the spend condition, is permanently fixed on-chain. This mirrors the reported bug class: an append-only allow-list with no removal/rotation path, where a single bad/deprecated entry can brick the ability to move funds, except here the "list" is baked directly into consensus-enforced puzzle reveals rather than a mutable pool registry.

### Impact Explanation
Any CR-CAT coin (and, transitively, all descendants of that lineage, since the list is propagated unchanged on every spend) becomes permanently unspendable if none of its curried `authorized_providers` can issue a currently valid VC. This is a direct, protocol-level lock of legitimate user funds with no recovery path other than a hard fork or CLVM curry-migration tooling that does not exist today.

### Likelihood Explanation
Likelihood is low: it requires that every provider DID in a given CR-CAT's `authorized_providers` list becomes unusable, which for CR-CATs configured with multiple providers is unlikely absent a broader compromise, but for single-provider deployments (a realistic configuration for a private/permissioned asset) is entirely plausible if that one DID's operator stops issuing VCs or its keys are lost.

### Recommendation
Introduce a governance mechanism analogous to what the report recommends for backstop pools: allow an authorized party (e.g., the asset issuer via TAIL logic, or a dedicated migration puzzle) to rotate/extend the `authorized_providers` list for existing CR-CAT lineages without requiring a hard fork, or document/enforce a minimum-provider-redundancy requirement at mint time so that no single point of provider failure can permanently strand funds.

### Proof of Concept
Not applicable — this is a design-level analysis of the immutable curried list in `construct_cr_layer` [1](#0-0)  and the strict VC-provider matching in `get_vc_with_provider_in_and_proofs`/`add_vc_authorization` [4](#0-3) , not a runnable exploit against a specific test harness.

```python
def construct_cr_layer(
    authorized_providers: list[bytes32],
    proofs_checker: Program,
    inner_puzzle: Program,
) -> Program:
    first_curry: Program = CREDENTIAL_RESTRICTION.curry(
        CREDENTIAL_STRUCT,
        authorized_providers,
        proofs_checker,
    )
    return first_curry.curry(first_curry.get_tree_hash(), inner_puzzle)


def construct_cr_layer_hash(
    authorized_providers_hash: bytes32,
    proofs_checker_hash: bytes32,
    inner_puzzle_hash: bytes32,
) -> bytes32:
    first_curry_hash: bytes32 = curry_and_treehash(
        Program.to((1, CREDENTIAL_RESTRICTION_HASH)).get_tree_hash_precalc(CREDENTIAL_RESTRICTION_HASH),
        CREDENTIAL_STRUCT_HASH,
        authorized_providers_hash,
        proofs_checker_hash,
    )
    first_curry_hash_hash: bytes32 = Program.to(first_curry_hash).get_tree_hash()
    final_hash: bytes32 = curry_and_treehash(
        Program.to((1, first_curry_hash)).get_tree_hash_precalc(first_curry_hash),
        first_curry_hash_hash,
        inner_puzzle_hash,
    )
    return final_hash
```
