### Title
Aggregator `Internal`-prefix authorization is fully bypassed when `client_verification=false`, exposing `InternalGetEmergencyStopTx` to any unauthenticated caller - (File: `core/src/rpc/interceptors.rs`, `core/src/servers.rs`)

### Summary
The self-only protection for `Internal`-prefixed RPCs (e.g. `/clementine.ClementineAggregator/InternalGetEmergencyStopTx`) is implemented entirely inside the `only_aggregator_and_self` interceptor, which is only installed when `config.client_verification == true`. When it is `false`, `create_grpc_server` installs `Interceptors::Noop` instead, so `is_internal()` and the `leaf_cert == our_cert` check are never evaluated, and any unauthenticated caller can invoke the RPC.

### Finding Description
The binding the codebase intends to hold is: `caller reaches a path prefixed "Internal"` ⇒ `caller's leaf_cert == our_cert` (aggregator's own client certificate), enforced only by `only_aggregator_and_self` in `core/src/rpc/interceptors.rs:36-77`, gated by `is_internal()` at `core/src/rpc/interceptors.rs:12-20`.

This binding is only wired up conditionally in `create_grpc_server` (`core/src/servers.rs:106-139`):
```
let service = InterceptedService::new(
    service,
    if config.client_verification {
        ... OnlyAggregatorAndSelf { aggregator_cert, our_cert: client_cert }
    } else {
        Noop
    },
);
``` [1](#0-0) 

`create_aggregator_grpc_server` (`core/src/servers.rs:293-317`) does not force `client_verification` on; it merely emits a `tracing::warn!` when the flag happens to be `true`, and unconditionally delegates to `create_grpc_server`, which then falls back to `Noop` whenever the flag is `false`: [2](#0-1) 

With `Noop` installed, no interceptor logic runs at all — `is_internal()` is never called and no certificate comparison ever happens: [3](#0-2) 

An attacker with only network access to the aggregator's gRPC port, and no TLS client certificate, can therefore call any RPC exposed by `ClementineAggregatorServer`, including `InternalGetEmergencyStopTx` (confirmed present in `core/src/rpc/aggregator.rs` and `core/src/rpc/clementine.rs`), by simply issuing a normal HTTP/2 gRPC request to that path. The `grpc-method` metadata header referenced by `is_internal()` is irrelevant here because the interceptor performing that check is never invoked in the `Noop` path — the entire self-only gate is dead code under this configuration.

Existing guards that would normally prevent unauthenticated access (`only_aggregator_and_self`, mTLS peer-cert checks) are architecturally bypassed rather than defeated by a logic flaw within them — the flaw is that the *selection* of interceptor in `create_grpc_server`/`create_aggregator_grpc_server` ties the "Internal-only" authorization entirely to the unrelated `client_verification` TLS toggle, with no independent enforcement.

### Impact Explanation
Any unauthenticated network caller who can reach the aggregator's gRPC port can invoke RPCs that are architecturally intended to be reachable only by the aggregator process itself (the `Internal` prefix convention exists specifically to mark such self-referential calls). This is a generic authentication-bypass affecting every `Internal`-prefixed RPC on the aggregator when `client_verification=false`, not just `InternalGetEmergencyStopTx`, so the blast radius extends to any other internal-only aggregator endpoint. I was not able to fully confirm within this session the exact downstream effect of `internal_get_emergency_stop_tx`'s implementation (i.e., whether it returns a fully valid, broadcastable signed transaction versus a partial artifact), so the precise mapping to a Critical bridge-fund-freezing outcome versus a High unauthenticated-privileged-call outcome could not be fully verified against the emergency-stop transaction's construction code.

### Likelihood Explanation
This requires only the standard, code-supported precondition `config.client_verification == false` on the aggregator — a state the code itself treats as ordinary (it only warns when the flag is enabled, never when disabled), suggesting disabled client verification is a commonly deployed/default configuration path rather than a misconfiguration. No Bitcoin fees, deposits, or withdrawals are needed; the attacker only needs network reachability to the aggregator's gRPC port and the ability to send a raw HTTP/2 request, both explicitly within the stated attacker capabilities.

### Recommendation
Decouple `Internal`-prefix authorization from the `client_verification` TLS toggle: always enforce the `leaf_cert == our_cert` (or an equivalent authenticated-channel) check for any `Internal`-prefixed method regardless of whether general client verification is enabled, e.g. by having `create_grpc_server` always install an interceptor that at minimum applies `is_internal` gating (rejecting any Internal call when no verified peer certificate/self-identity is present), and by making `create_aggregator_grpc_server` fail closed (return an error) instead of merely warning if it cannot guarantee this gating for Internal RPCs.
