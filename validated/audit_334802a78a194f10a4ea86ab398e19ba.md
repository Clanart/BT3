### Title
Attacker-planted dust outputs permanently inflate the wallet's spendable set, forcing `TooLargeTransaction`/`NotEnoughFunds` and DoSing all future payments - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` registers any output whose `script_pubkey` matches a registered key/offset as a `ReceivedOutput`, with no minimum-value, spendability, or provenance check. An unprivileged attacker can send arbitrarily many dust-value (or zero-relayable) P2TR outputs to the multisig's publicly known addresses. Because `SignableTransaction::new` treats every `ReceivedOutput` as a fungible input — summing values and adding a full Taproot input's weight each — these poisoned outputs cannot be "deleted" (they exist on-chain forever) and either inflate the transaction past `MAX_STANDARD_TX_WEIGHT` or add more fee cost than their value, denying service to legitimate payments. This mirrors CVE-2018-11084: an attacker creates resources with crafted attributes (dust/satoshis) that cannot be removed, blocking creation of new instances.

### Finding Description
`Scanner` is keyed purely by `script_pubkey`: `self.scripts.get(&output.script_pubkey)` at `scan_transaction` (mod.rs:205-212). Anyone can compute the P2TR script for the group key (it is a public Taproot address) and send outputs to it. The resulting `ReceivedOutput`s are indistinguishable from honest deposits.

In `SignableTransaction::new` (send.rs:150-256):

- Every input contributes weight: `calculate_weight_vbytes` builds a `TxIn` per input and `needed_fee = fee_per_vbyte * vbytes` scales with input count (send.rs:175-213).
- A dust input worth < ~ its marginal fee contribution (≈57.5 vbytes × fee rate, i.e. thousands of sats at normal rates) reduces net spendable funds — `input_sat` is credited while `needed_fee` grows more than the input's value (send.rs:215-221).
- Enough inputs trips `weight > MAX_STANDARD_TX_WEIGHT` → `TooLargeTransaction` (send.rs:241-243), permanently: there is no code path to drop, filter, or consolidate poisonous `ReceivedOutput`s. Since the UTXOs exist on-chain under the multisig's key, rescanning reproduces them.

There is no minimum-value check on *inputs* (only `DustPayment` for payments at send.rs:165-169) and no coin-selection that could exclude unprofitable inputs.

### Impact Explanation
An attacker spends a small amount (thousands of dust outputs at ~few hundred sats each, or fewer, larger unprofitable ones) to permanently pollute the multisig's UTXO set. Consequences:

- `SignableTransaction::new` returns `TooLargeTransaction` or `NotEnoughFunds` for any payment attempting to use the full output set, blocking withdrawals/scaling — the exact DoS shape of CVE-2018-11084.
- The pollution is irreversible: unlike an app environment that could be deleted once the bug is fixed, the dust UTXOs live under the threshold key forever and any scanner restart re-discovers them.
- Even before the hard limit, honest deposits' value is silently burned into fees covering worthless attacker inputs.

This satisfies the acceptance bar: funds are reported received (`ReceivedOutput`/`scan_transaction`) that are not economically spendable, and legitimate signing (`SignableTransaction::new` → `TransactionMachine`) is denied.

### Likelihood Explanation
- Reachability: fully public. The Taproot script_pubkey is derivable from the group key; sending a Bitcoin transaction requires no authentication.
- Cost: bounded only by the attacker's willingness to fund dust outputs; each output costs < 546 sats worth of value (it can even be exactly dust) plus the attacker's own fee.
- Deterministic: no race or validator misbehavior required; any downstream consumer that feeds the scanned output set into `SignableTransaction::new` hits the error.

### Recommendation
- In `scan_transaction`/`ReceivedOutput` handling, reject or quarantine outputs below a spendability threshold (value < marginal input fee at a reference fee rate, or below `DUST`).
- Implement coin selection in `SignableTransaction::new`: sort inputs by value, add inputs only while marginal value > marginal fee, and stop before `MAX_STANDARD_TX_WEIGHT`, leaving remainder for consolidation transactions.
- Consider a dedicated consolidation path that spends many small inputs to change with no payments.

### Proof of Concept
1. Obtain the multisig's P2TR `script_pubkey` from the public group key via `p2tr_script_buf(tweaked_group_key)` (mod.rs:80-86,164).
2. Broadcast N transactions each paying 546 sats (or less) to that script. Each is picked up by `scan_transaction` as a `ReceivedOutput` (mod.rs:199-214).
3. Downstream, construct `SignableTransaction::new(all_outputs, payments, change, None, fee_rate)`:
   - With ~1750+ inputs, `calculate_weight_vbytes` exceeds `MAX_STANDARD_TX_WEIGHT` → `TooLargeTransaction` (send.rs:241).
   - With fewer inputs but at a high `fee_per_vbyte`, `input_sat < payment_sat + needed_fee` since each 546-sat input adds ~57.5 vbytes of fee → `NotEnoughFunds` (send.rs:215-221).
4. Deleting the outputs is impossible: they are confirmed UTXOs under the group's own key, so every rescan repopulates them — the DoS persists until code changes add filtering.
