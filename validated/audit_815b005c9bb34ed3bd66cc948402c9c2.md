## Analog Found: Unbounded recursive puzzle-layer matching in wallet outer-puzzle drivers can hang/crash the wallet processing an attacker-crafted offer or synced coin — analogous to GitLab's unbounded blockquote-nesting parser hang.

### Title
Unbounded recursive puzzle-driver matching on attacker-controlled curried layers causes wallet DoS - ([File: chia/wallet/outer_puzzles.py])

### Summary
The GitLab report describes a parser that recurses/loops without a depth bound over attacker-controlled nested markdown constructs (block-quotes), causing a processing timeout. Chia's wallet has an analogous unbounded-recursion pattern: `match_puzzle()` and the various `*OuterPuzzle.match()`/`get_inner_puzzle()`/`solve()` implementations recurse once per curried layer of a puzzle reveal, with no depth limit, and this code runs in pure Python on data supplied by an untrusted counterparty (an offer file or a synced coin's puzzle reveal) *before* any CLVM cost metering applies.

### Finding Description
`match_puzzle()` in [1](#0-0)  iterates over `driver_lookup` and calls `driver.match(puzzle)`. Each driver's `match()` — e.g. `CATOuterPuzzle.match()` [2](#0-1) , `OwnershipOuterPuzzle.match()` [3](#0-2) , `SingletonOuterPuzzle.match()` [4](#0-3) , `MetadataOuterPuzzle.match()` [5](#0-4) , and `CROuterPuzzle.match()` [6](#0-5)  — unconditionally calls `self._match(UnknownPuzzle(known_program=inner_puzzle))` on the next inner layer, which is `match_puzzle` again. There is no maximum-depth check anywhere in this recursive chain.

This recursive matching is invoked on untrusted data through `Offer._get_offered_coins()`, which calls `match_puzzle(parent_puzzle)` on the puzzle reveal of every coin spend in an offer bundle received from a counterparty [7](#0-6) . The same recursive pattern also exists in `UncurriedNFT.uncurry()`, which recursively uncurries ownership/transfer-program layers [8](#0-7) , and in `recursive_uncurry_dump()` used by debug/logging tooling [9](#0-8) .

Because curry layers are cheap to stack (each additional layer only adds a small curried wrapper of bytes), an attacker can construct a puzzle reveal with a very large number of nested curried layers within a size that is otherwise unremarkable (well under mempool/transaction size limits), and hand it to a victim wallet as part of an offer file or a coin's puzzle reveal seen during sync. Because this recursion happens in Python (not CLVM execution), it is not covered by any `MAX_BLOCK_COST_CLVM` / `max_tx_clvm_cost` accounting described in the CLVM execution docs [10](#0-9) . The Chia codebase elsewhere shows explicit awareness that Python recursion on attacker-influenced CLVM trees is dangerous — `sha256_treehash()` was deliberately made iterative "so we don't have to worry about blowing out the python stack" [11](#0-10)  — but the outer-puzzle driver matching chain was not given the same treatment.

### Impact Explanation
A sufficiently deep chain of nested curried layers in an offer's puzzle reveal (or a coin's puzzle reveal observed during wallet sync/hinting) can drive the Python call stack past its recursion limit, raising an unhandled `RecursionError` (or consuming excessive CPU/stack before that), when the victim wallet tries to parse/display/validate the offer via `Offer._get_offered_coins()` or similar driver-matching call sites. This is a spend/offer-triggered processing halt reachable by any offer counterparty without needing to be a network peer, node operator, or key holder — matching the "spend-triggered transaction-processing halt" impact class.

### Likelihood Explanation
Constructing a puzzle reveal with many nested curry layers is inexpensive for an attacker (curry wrapping is cheap and does not require CLVM execution cost to build), and delivering it only requires sending an offer file or being observed by the victim's wallet during coin sync — well within reach of an "offer counterparty" or "wallet user" threat actor as scoped by this analysis. No signature or mempool admission is required to trigger the recursive matching, since it happens client-side during offer inspection.

### Recommendation
Add an explicit maximum recursion/nesting depth (and/or convert the driver-matching chain to an iterative loop, following the precedent already set by `sha256_treehash()`) in `match_puzzle()` and each `*OuterPuzzle.match()`/`get_inner_puzzle()`/`get_inner_solution()`/`solve()` implementation in `chia/wallet/outer_puzzles.py`, `chia/wallet/cat_wallet/cat_outer_puzzle.py`, `chia/wallet/nft_wallet/*_outer_puzzle.py`, and `chia/wallet/vc_wallet/cr_outer_puzzle.py`, and reject puzzle reveals exceeding that depth before they are matched or uncurried.

### Proof of Concept
1. Programmatically construct a puzzle by nesting `CAT_MOD.curry(...)` (or `NFT_OWNERSHIP_LAYER.curry(...)`) around itself N times (e.g., N = a few thousand), similar to how `double_cat_puzzle` is built in the existing test [12](#0-11) , but iterated far beyond two layers.
2. Wrap this puzzle reveal as the coin's puzzle in an `Offer`/`SpendBundle` and send it to a victim wallet (e.g., as an offer file).
3. Have the victim wallet call `Offer._get_offered_coins()` (as happens automatically when inspecting/accepting an offer), which calls `match_puzzle()` recursively once per curry layer.
4. Observe the wallet process crash with `RecursionError` or hang/consume excessive CPU well before any CLVM cost accounting is invoked, denying the wallet's ability to process the offer or other spends.

```python
def recursive_uncurry_dump(puzzle: Program, layer: int, prefix: str, uncurried_already: UncurriedPuzzle) -> None:
    mod = uncurried_already.mod
    curried_args = uncurried_already.args
    if mod != puzzle:
        print(f"{prefix}- Layer {layer}:")
        print(f"{prefix}  - Mod hash: {mod.get_tree_hash().hex()}")
        for arg in curried_args.as_iter():
            uncurry_dump(arg, prefix=f"{prefix}  ")
        mod2, curried_args2 = mod.uncurry()
        if mod2 != mod:
            recursive_uncurry_dump(mod, layer + 1, prefix, UncurriedPuzzle(mod2, curried_args2))
    else:
        print(f"{prefix}- {bu_disassemble(puzzle)}")
```
