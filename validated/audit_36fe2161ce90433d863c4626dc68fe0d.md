### Title
Unbounded `object::root_owner()` traversal reachable via cycle created through `TransferRef`/`LinearTransferRef`, bypassing the nesting-depth/cycle guard used by ordinary `transfer()` - (File: aptos-move/framework/aptos-framework/sources/object.move)

### Summary
`code::publish_package` (the core entry point for all module publish/upgrade flows, including `object_code_deployment::publish/upgrade`) calls `object::root_owner()` to compute the current transitive owner of an object address and records it via `init::record_deploy_owner` for later authorization checks (`init::assert_may_self_initialize`). `root_owner()` walks the ownership chain with **no depth limit and no cycle detection**: [1](#0-0) 

By contrast, every other ownership-chain walker in the same module (`owns`, `verify_ungated_and_descendant`) explicitly caps traversal at `MAXIMUM_OBJECT_NESTING` (8) and aborts on cycles: [2](#0-1) [3](#0-2) 

The cycle-safety of `root_owner()` therefore depends entirely on the invariant that no ownership cycle can ever be created. That invariant is enforced only in `transfer_raw`/`transfer_raw_inner`, which calls `verify_ungated_and_descendant` before mutating `owner`: [4](#0-3) 

However, `TransferRef`-based transfers (`transfer_with_ref`, consuming a `LinearTransferRef`) mutate `ObjectCore.owner` directly and **never call `verify_ungated_and_descendant`**: [5](#0-4) 

This is a second, independent object-mutation code path that does not share the cycle/depth-limit guard that the rest of the ownership-authority model (including the publish flow) implicitly relies on.

### Finding Description
`code::publish_package` records `object::address_to_object<ObjectCore>(addr).root_owner()` as the authorization anchor for a published/upgraded module's future lazy self-initialization: [6](#0-5) 

`init::assert_may_self_initialize` later re-derives `root_owner()` again to compare against the recorded value: [7](#0-6) 

Both of these call sites assume `root_owner()` terminates. That assumption is only true if ownership chains are acyclic and bounded — an invariant that the codebase enforces for the `transfer()`/`transfer_call`/`transfer_to_object` entry points via `verify_ungated_and_descendant`'s explicit counter and `exists<ObjectCore>`/cycle abort logic, but does **not** enforce for the `TransferRef`/`LinearTransferRef` path (`transfer_with_ref`). Since `TransferRef` can be generated by any object's `ConstructorRef` owner and used to move ownership to an arbitrary address (including an address that is itself part of the same object's ancestor chain), it is possible to construct an ownership graph where `owner` fields form a cycle that `verify_ungated_and_descendant` would have rejected, but that `transfer_with_ref` does not check for.

Once such a cycle exists, any call into `code::publish_package` for an address on that cycle (either the object itself being republished, or an object that owns a module and is later chained) causes `root_owner()` to loop indefinitely, since `is_object(obj_owner)` will always be true along the cycle and there is no counter to break out.

### Impact Explanation
This directly corrupts the code-ownership/authorization state written by the publish path: `record_deploy_owner`'s target value (the "owner" used to gate self-init) can never be computed once a cycle exists, so any publish/upgrade transaction targeting an object on (or transitively owned through) that cycle can no longer complete normally — it will run out of gas or loop without the depth-bounded abort semantics the rest of the object model relies on. This breaks the code-safety invariant that publish/upgrade/freeze flows must be able to reliably determine code ownership (per the Publish Pivots requirement that "Object code deployment and resource-account publish flows must not leak upgrade or freeze authority to unprivileged callers" — here the authority computation itself becomes unreliable/DoS-able for affected object addresses), and it is a genuine divergence between two owner-mutation code paths (`transfer_raw` vs `transfer_with_ref`) that the loader/publish code implicitly assumes are equivalent in their cycle-safety guarantees.

### Likelihood Explanation
Reaching this requires the attacker to control a `TransferRef` for at least one object in a chain and to be able to arrange addresses so that `transfer_with_ref` sets an object's `owner` back to one of its own descendants/ancestors. `TransferRef` is generated via `ConstructorRef::generate_transfer_ref()` by whoever creates the object, and objects can be nested (owner of object A being object B, whose owner is set back to A via a `LinearTransferRef`). This is plausible for any application built on top of the object model that exposes `TransferRef`-based transfers (a common pattern for token/collection contracts), making the precondition realistic without requiring privileged access.

### Recommendation
Add the same nesting-depth cap and self/cycle rejection used in `verify_ungated_and_descendant` to `transfer_with_ref` (and any other place that mutates `ObjectCore.owner` directly), or, defensively, bound `root_owner()`'s loop with `MAXIMUM_OBJECT_NESTING` and fail closed (abort) if the bound is exceeded, mirroring `owns()`'s pattern. This closes the gap between the two owner-mutation code paths and ensures `code::publish_package`/`init::assert_may_self_initialize` can never enter an unbounded loop regardless of how ownership was last changed.

### Proof of Concept
Conceptual repro (not executed, given tool limitations in this session):
1. Create object `A` via `create_object`, obtaining `ConstructorRef_A`; create object `B` similarly.
2. Use `ConstructorRef_A.generate_transfer_ref()` → `TransferRef_A`; generate a `LinearTransferRef` and call `transfer_with_ref(linear_ref_A, B_address)` — sets `A.owner = B`.
3. Use `ConstructorRef_B.generate_transfer_ref()` → `TransferRef_B`; generate a `LinearTransferRef` and call `transfer_with_ref(linear_ref_B, A_address)` — sets `B.owner = A`. Since `transfer_with_ref` never calls `verify_ungated_and_descendant`, this 2-cycle is not rejected (unlike calling `transfer(owner, obj_B, A_address)` after `transfer(owner, obj_A, B_address)`, which the existing test `test_cyclic_ownership_transfer_should_fail` shows aborts when done via the guarded `transfer` path).
4. Publish or upgrade a module at address `A` (or `B`) with `LAZY_MODULE_INITIALIZATION` enabled — `code::publish_package` calls `object::address_to_object::<ObjectCore>(A).root_owner()`, which loops forever alternating between `A` and `B` since `is_object(owner)` is always true.

Note: I was not able to execute this in a live Move test harness within this session (no filesystem/terminal access), so this should be validated by writing a `#[test]` analogous to the existing `test_cyclic_ownership_transfer_should_fail`/`self_init_blocked_when_owner_transferred` tests in `object.move`/`init.move`, but using `transfer_with_ref` to construct the cycle instead of `transfer`.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }
