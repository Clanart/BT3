### Title
Copilot conflict-resolution reassembly blindly trusts LLM-returned hunk order/count, allowing a poisoned repository (via PR title/body or commit messages fed into the prompt) to silently corrupt merged file content before it is committed and pushed - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Synthetix report's root cause is that code trusts a returned value (`amountReceived`) to exactly equal an assumed value (`amount`) without verifying it, and downstream logic (`transferMargin`) uses the unverified assumption, breaking the operation. The structural analog in GitHub Desktop is the Copilot conflict-resolution reassembly path: `reassembleResolvedFile` matches model-returned hunk resolutions to conflict blocks **by order only, not by identity/content**, and the upstream validation (`validateResolutionPaths`) only checks that the *count* of hunks per file matches the expected count — not that each hunk's content actually corresponds to the conflict it claims to resolve.

### Finding Description
`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` walks a conflicted file and produces an ordered array of hunks per file, which is sent to the Copilot SDK, along with attacker-influencable context: PR titles/bodies and commit messages from both sides of the merge (`gatherCommitContext`, `appendPullRequest` in `app/src/lib/copilot-conflict-context.ts:326-618`). This text is untrusted content originating from a cloned/fetched repository or a PR the user is merging.

The model's response is parsed by `parseCopilotConflictResolution` and then checked only for:
- file paths matching (`validateResolutionPaths`, `app/src/lib/copilot-conflict-resolution.ts:473-521`)
- hunk **count** per file matching the expected count
- that returned `resolvedContent` doesn't literally contain the two specific conflict-marker regexes it checks for [1](#0-0) 

None of this validates that hunk *i* in the response actually corresponds to conflict *i* in the file, nor that the resolved content is semantically consistent with the ours/theirs/base content of that specific hunk. `reassembleResolvedFile` then splices hunks back into the raw file **purely by positional order** (`hunkIndex`), trusting the model's return value the same way `borrowLiquidation.sol` trusts `amount` instead of validating `amountReceived`: [2](#0-1) [3](#0-2) 

Because the underlying LLM ingests attacker-controlled text (PR body/title, commit summaries from the "theirs" side of a merge — content that comes from a remote/fetched branch the user is merging), a prompt-injection payload embedded in a PR description or commit message could manipulate the model into returning hunks in a shuffled order, or with content lifted from the wrong hunk/file, while still satisfying the shallow checks (right path, right count, no literal marker strings). The reassembly path has no way to detect this because it never re-derives which resolved block belongs to which original hunk except by array index.

### Impact Explanation
If exploited, this causes **silent corruption of what the user commits and pushes** — explicitly listed as a valid impact category. The corrupted content is written directly to disk and staged without further review gates beyond the diff shown in the result dialog (`_applyCopilotConflictResolutions`, `app/src/lib/stores/app-store.ts:7169-7268`), and if the user trusts the AI-authored merge and clicks "Continue Merge," incorrect code (e.g., silently reverting a security fix, reintroducing a bug, or swapping unrelated logic between hunks) is committed and can be pushed upstream. This mirrors the mitigation gap in the Synthetix report: the code proceeds with an unverified value where verification was possible and necessary.

### Likelihood Explanation
This requires: (1) the user to opt into "Resolve with Copilot" for a merge/rebase/cherry-pick with a repository controlled or influenced by an attacker (a fork PR, or a branch/commit message the attacker pushed), and (2) a successful prompt-injection payload against the underlying model that survives the JSON schema validation. Devin has not verified that such a prompt-injection payload is achievable in practice (that depends on the specific LLM's robustness, which is outside the local codebase), so likelihood is **uncertain/moderate** rather than confirmed — the code path itself provides no defense-in-depth beyond count/path matching, which is the concrete gap, but exploitability further depends on LLM behavior that could not be verified from static code alone.

### Recommendation
- Have the model echo back an unambiguous per-hunk identifier (e.g., a hash of `oursContent`/`theirsContent` for that hunk) instead of relying purely on array order, and reject/re-prompt if the echoed identifier doesn't match the hunk at that position.
- After reassembly, diff the resolved file against the original ours/theirs hunk content to assert each resolved hunk plausibly derives from one of the two known sides (or flag as "novel" content for stronger user review) rather than accepting any returned string verbatim.
- Treat commit-message/PR-description context passed into the prompt as data, not instructions, and strip/neutralize instruction-like patterns before inclusion in `formatConflictContextForPrompt`.

### Proof of Concept
Devin could not execute a live LLM prompt-injection test in this environment (no access to the Copilot SDK backend). The concrete, verifiable code-level gap demonstrated from static analysis is:
1. A file has 2 conflict hunks; `extractConflictHunks` returns `[hunkA, hunkB]` in file order.
2. Attacker's PR description (included verbatim in the prompt via `appendPullRequest`) contains an injection instructing the model to return hunk resolutions in swapped order or with content from the wrong hunk.
3. `parseCopilotConflictResolution` + `validateResolutionPaths` accept the response because path count (1) and hunk count (2) match — no content-identity check exists. [4](#0-3) 
4. `reassembleResolvedFile` splices `resolutions[0]` into the first marker block and `resolutions[1]` into the second purely by index, producing a file with hunk content silently transposed or altered relative to what either branch actually intended. [3](#0-2) 
5. `_applyCopilotConflictResolutions` writes this content directly to disk and stages it for commit. [5](#0-4) 

This chain is confirmed by reading the source directly; whether a real-world prompt can reliably induce this exact model misbehavior was **not verified** in this session.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through

 * line number). This guarantees that all non-conflicted code is preserved

 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
