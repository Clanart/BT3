### Title
Signature oracle via 32-bit fingerprint collision in `WalletSigner.execute_signing_instructions` - (File: `chia/wallet/wallet_signer.py`)

### Summary
`WalletSigner.execute_signing_instructions` matches BLS public keys that need signatures using only their 32-bit `get_fingerprint()` value as the lookup key into `sk_lookup`/`pk_lookup`, instead of the full public key. This is the same bug class as GHSA-fpw7-8gjc-jwqj: a short, attacker-influenceable identifier (fingerprint / credential ID) is used as the cache/lookup key for sensitive key material, so an attacker who can produce a colliding identifier can cause the wrong (legitimate, victim-owned) credential to be used.

### Finding Description
`gather_signing_info` extracts `(pk, msg)` pairs from `AGG_SIG_*` conditions found in the puzzle reveal/solution of *every* coin spend being signed, via `pkm_pairs_for_conditions_dict` [1](#0-0) . Both `pk` and `msg` here are fully attacker-controlled when the spend comes from an untrusted source such as an offer counterparty's half-completed offer bundle (`gather_signing_info_for_trades` walks `offer._bundle`) [2](#0-1) .

Only the 32-bit `pk.get_fingerprint()` is carried forward as `SigningTarget.fingerprint`, and `execute_signing_instructions` later resolves which secret key to use purely by this 32-bit fingerprint:

```
for target in signing_instructions.targets:
    pk_fingerprint: int = int.from_bytes(target.fingerprint, "big")
    ...
    elif pk_fingerprint in sk_lookup:
        responses.append(
            SigningResponse(
                bytes(AugSchemeMPL.sign(sk_lookup[pk_fingerprint], target.message)),
                target.hook,
            )
        )
``` [3](#0-2) 

Nowhere in this lookup path is the actual public key (`pk_parsed` from the AGG_SIG condition) compared against `pk_lookup[pk_fingerprint]` before signing. The fingerprint is a 32-bit value, so it is only a partial, low-entropy identifier for the key — analogous to the Jenkins plugin using the credential ID (also attacker-influenceable and non-unique across scopes) as the cache key for sensitive credential material rather than validating the full credential identity. An attacker who crafts (or brute-forces) a BLS public key whose 32-bit fingerprint collides with a fingerprint already present in `sk_lookup`/`pk_lookup` (built from the wallet's own root/path/sum-hint keys) will cause the wallet to sign `target.message` — an attacker-chosen arbitrary byte string taken directly from the attacker's crafted `AGG_SIG_ME`/`AGG_SIG_UNSAFE` condition — using the wallet's real private key, without any correctness check that the message actually corresponds to the colliding key.

### Impact Explanation
This produces a **signature oracle** for the victim wallet's real signing key: an attacker (e.g., an offer counterparty submitting a crafted `Offer` for the victim to sign, or any caller that triggers `sign_transactions`/`gather_signing_info_for_trades` on attacker-influenced spends) can obtain a valid BLS signature from a legitimate wallet key over an arbitrary attacker-chosen message. Because Chia's AGG_SIG conditions and offer/DID/singleton authorization schemes rely on the *message content* (coin id, delegated puzzle hash, DID announcement, etc.) rather than on any implicit binding to a particular in-flight transaction, a signature obtained this way could potentially be replayed to satisfy an unrelated `AGG_SIG_ME`/`AGG_SIG_UNSAFE` condition on a different coin controlled by the same underlying key (e.g., another one of the victim's coins, or a DID/singleton authorization), enabling an unauthorized/unsigned coin movement or unauthorized action performed with the victim's key. This aligns with the "concrete unsigned or unauthorized coin movement" and "offer settlement theft" categories called out in the validation criteria.

### Likelihood Explanation
Exploitation requires the attacker to find a public key whose 32-bit fingerprint collides with a specific target fingerprint already known to the victim (a preimage-style search over a 32-bit space, expected ~2^31 keypair generations for a single specific target). This is computationally nontrivial but not infeasible for a motivated, well-resourced attacker (particularly against high-value wallets, or when many victim fingerprints are targeted simultaneously, which lowers the effective work via a birthday-style search across all of a victim's derived keys). The attack surface (crafting a malicious `Offer`/spend bundle and getting the victim to run `gather_signing_info_for_trades`/`sign_transactions` on it) is reachable by any offer counterparty or RPC caller supplying transaction data to be signed, without special privilege.

### Recommendation
In `execute_signing_instructions` (and the corresponding hint-expansion code), verify the *full* public key — not just the 32-bit fingerprint — before selecting a secret key to sign with. Concretely, store `sk_lookup`/`pk_lookup` keyed by full serialized `G1Element` bytes (or verify `pk_lookup[pk_fingerprint].get_g1() == pk_parsed` reconstructed from the original condition) prior to calling `AugSchemeMPL.sign`, and reject/skip any target whose declared fingerprint does not correspond to the actual public key that produced the AGG_SIG condition.

### Proof of Concept
1. Attacker enumerates BLS keypairs offline until finding one, `pk_evil`, whose `pk_evil.get_fingerprint()` (32-bit) equals the fingerprint of a public key, `pk_victim`, known to belong to the target wallet (e.g., observed on-chain from a prior spend or address).
2. Attacker crafts an `Offer`/spend bundle containing a coin spend whose puzzle output includes condition `AGG_SIG_ME pk_evil <attacker_chosen_message>`.
3. Victim wallet processes the offer via `TradeManager`/`gather_signing_info_for_trades` → `gather_signing_info`, which extracts `(pk_evil, attacker_chosen_message)` from the crafted condition and records `SigningTarget(pk_evil.get_fingerprint(), attacker_chosen_message, ...)` [4](#0-3) .
4. `execute_signing_instructions` finds `pk_evil.get_fingerprint() in sk_lookup` (matching `pk_victim`'s real secret key by fingerprint collision) and returns `AugSchemeMPL.sign(sk_victim, attacker_chosen_message)` [5](#0-4) .
5. Attacker now possesses a valid signature from the victim's real key over an arbitrary message, without ever needing the victim's private key, which can potentially be replayed against other conditions requiring a signature from `pk_victim`.

    async def gather_signing_info(self, spends: list[Spend]) -> SigningInstructions:
        pks: list[bytes] = []
        signing_targets: list[SigningTarget] = []
        for spend in spends:
            coin_spend = spend.as_coin_spend()
            # Get AGG_SIG conditions
            conditions_dict = conditions_dict_for_solution(
                coin_spend.puzzle_reveal,
                coin_spend.solution,
                self.max_block_cost_clvm,
            )
            # Create signature
            for pk, msg in pkm_pairs_for_conditions_dict(
                conditions_dict, coin_spend.coin, self.agg_sig_me_additional_data
            ):
                pk_bytes = bytes(pk)
                pks.append(pk_bytes)
                fingerprint: bytes = pk.get_fingerprint().to_bytes(4, "big")
                signing_targets.append(SigningTarget(fingerprint, msg, std_hash(pk_bytes + msg)))
