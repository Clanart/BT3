### Title
Unvalidated `Participant` index in PedPoP blame evaluation causes remotely triggerable panic - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The CVE-2022-42121 bug class is the injection of an attacker-controlled field into a security-sensitive operation without validating it against the allowed domain. The analog in Serai is `BlameMachine::blame` / `AdditionalBlameMachine::blame` in `crypto/dkg/pedpop/src/lib.rs`: the `sender` and `recipient` `Participant` values are attacker-supplied protocol fields (they name which party is accused/accusing), and they are used to index `self.commitments` and `self.encryption.enc_keys` via `HashMap`'s `Index` impl — which panics on a missing key — with no check that the participant is within `1..=n`.

### Finding Description
`blame_internal` computes:

```rust
let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) { ... }
```

and later `self.commitments[&sender]` in `share_verification_statements`. Neither `sender` nor `recipient` is range-checked against the participant set:

- `Decryption::decrypt_with_proof` does `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs), panicking when `decryptor` was never registered.
- `blame_internal` does `self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs), panicking when `sender` isn't a DKG participant.

`Participant` only guarantees non-zero (`Participant::new` rejects 0 in `crypto/dkg/src/lib.rs`); a `Participant` with index `> n` is a perfectly valid `Participant` value. The upstream consumer of this API does pass network-controlled values straight through: the `VerifyBlame` handler reads `accuser` and `accused` from a `CoordinatorMessage` and calls `AdditionalBlameMachine::new(...).blame(accuser, accused, ...)` (processor/src/key_gen.rs `VerifyBlame` arm) — so the values reach `blame` unvalidated in real usage.

By contrast, every other place `Participant` values enter the protocol they are checked: `ThresholdParams::new` rejects `i > n`, `ThresholdKeys::new` rejects verification-share keys `> n`, `view()`/`sign()` reject `included.last() > n` and duplicates, and `validate_map` enforces exact membership. `blame` is the sole path where attacker-chosen participant indexes reach a `HashMap` index directly.

### Impact Explanation
An unprivileged participant (or any party able to submit a blame/`VerifyBlame` message naming an arbitrary `accuser`/`accused`, such as `Participant(n+1)` or `u16::MAX`) causes a panic inside `blame_internal` — first at `self.enc_keys[&decryptor]` or `self.commitments[&sender]`. In a validator/processor context this aborts blame adjudication and crashes the task handling the message, preventing correct attribution of DKG faults and denying availability of the node handling the message. This is a remotely triggerable panic reachable purely through public protocol inputs (the participant fields and a blame payload), matching the "crafted value injected into a trusted field" shape of the Liferay SQLi (input passed unvalidated into an operation that trusts it).

### Likelihood Explanation
Triggering requires only sending a blame message with a sender or recipient index outside `1..=n`. No key material, threshold cooperation, or valid proof is needed — the panic occurs before any cryptographic check on the message contents. The only mitigating factor is that panic handling depends on the integrator (whether the panic unwinds into a recoverable error path), keeping this at Medium rather than High.

### Recommendation
Validate `sender` and `recipient` in `blame_internal` (and in `AdditionalBlameMachine::new`'s consumers) against the commitment set — e.g., return the caller/accuser as faulty, or return a `Result` with an explicit invalid-participant error — instead of indexing `self.commitments[&sender]` and `self.enc_keys[&decryptor]` directly. Alternatively, bound-check against `params.n()` at `blame` entry.

### Proof of Concept
Conceptual, on the library API:

```rust
// Assume a completed DKG with n participants; `machine: BlameMachine<C>`
// or an `AdditionalBlameMachine` built from the n commitment messages.
let forged_sender = Participant::new(n + 1).unwrap(); // nonzero, so valid Participant

// Any syntactically well-formed EncryptedMessage; contents irrelevant since
// indexing happens on the participant index, not the payload.
machine.blame(forged_sender, honest_recipient, msg, proof);
// -> panics at `self.commitments[&sender]` (index out of map),
//    or earlier at `self.enc_keys[&decryptor]` if `recipient` is forged instead.
```

The panic is in `HashMap`'s `Index` impl (`EncryptedMessage`/commitment lookups in `blame_internal` and `Decryption::decrypt_with_proof`), reached entirely with attacker-chosen `Participant` fields.

Caveat: I verified the indexing sites (`self.commitments[&sender]`, `self.enc_keys[&decryptor]`) and the absence of any `<= n` check on `blame`'s arguments, but did not exhaustively confirm whether `blame`'s in-scope callers elsewhere pre-validate participant indexes; the reachable processor path (`VerifyBlame`) does not.
