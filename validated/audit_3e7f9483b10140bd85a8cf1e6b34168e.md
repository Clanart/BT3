### Title
Hand-rolled YAML frontmatter parser silently drops indented `action`/`enabled` keys and falls back to fail-open defaults, downgrading `block` rules to `warn` - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` implements a hand-rolled, whitespace-sensitive line parser instead of a real YAML parser. Any top-level key (e.g. `action: block`, `enabled: false`) that is indented by even a single space, or accidentally absorbed as a continuation of a preceding list/dict block, is silently dropped with no warning and no exception. `Rule.from_dict` then falls back to the fail-open default `action = frontmatter.get('action', 'warn')`, so a rule that a human reviewer reads as `action: block` in a `.claude/hookify.*.local.md` file actually gets loaded and enforced as `action: warn`, letting the matched Bash/Write operation execute instead of being denied.

### Finding Description
`extract_frontmatter` (`plugins/hookify/core/config_loader.py:87-195`) classifies each frontmatter line by exact indentation:
- `indent == 0` and not starting with `-` → treated as a new top-level key [1](#0-0) 
- `stripped.startswith('-') and in_list` → list item [2](#0-1) 
- `indent > 2 and in_dict_item and ':' in line` → continuation field of a multi-line dict item inside a list [3](#0-2) 

Any line that doesn't fall into one of these three exact buckets is silently ignored — there is no `else` branch, no error, no log line. In particular:
- A top-level key such as `action: block` or `enabled: false` written with 1–2 leading spaces (indent 1 or 2) matches none of the branches: it is not `indent == 0`, does not start with `-`, and `indent > 2` is false for indent 1 or 2. The key is dropped entirely.
- If it happens to follow a still-open multi-line dict item from a preceding `conditions:` list and has `indent > 2`, it gets absorbed as a bogus field of that dict item (e.g. `Condition.field`/`operator`/`pattern`) instead of becoming a top-level rule field.

`Rule.from_dict` (`plugins/hookify/core/config_loader.py:75-84`) then reads:
```
action=frontmatter.get('action', 'warn'),
``` [4](#0-3) 
so when `action` was dropped by the parser, the rule silently becomes `action='warn'` even though the file's visible text says `action: block`.

Downstream, `RuleEngine.evaluate_rules` (`plugins/hookify/core/rule_engine.py:53-58`) only places a matching rule into `blocking_rules` (which produces `permissionDecision: deny` for `PreToolUse`) when `rule.action == 'block'`; otherwise it is treated as a non-blocking warning that still allows the tool call to proceed [5](#0-4) . `load_rule_file` (`plugins/hookify/core/config_loader.py:244-274`) catches only I/O/parsing exceptions; since `extract_frontmatter` never raises on this malformed input, no warning is ever surfaced to indicate the rule was mis-parsed [6](#0-5) .

Attack flow: an attacker contributes a `.claude/hookify.*.local.md` rule file (via a plugin example or a PR) whose frontmatter visually reads `action: block` but has the key indented by one or two stray spaces (or nested under a preceding `conditions:` list continuation). A reviewer approving the PR believes a hard block was added for a dangerous Bash/Write pattern. In reality `load_rules` → `load_rule_file` → `extract_frontmatter` → `Rule.from_dict` silently loads the rule with `action='warn'`, so `RuleEngine.evaluate_rules` never denies the matching operation — it only prints a warning message while the disallowed command/file write proceeds.

### Impact Explanation
This is a hook-enforcement bypass: an approval gate that appears (by source inspection) to `block` disallowed `Bash`/`Write`/`Edit` operations is silently downgraded to a non-blocking `warn`, letting the operation execute. Because `extract_frontmatter` never errors and `load_rule_file`'s exception handling never fires, there is no diagnostic signal that the intended enforcement action was lost, making this both a silent security-relevant behavioral change and a plausible source of a false sense of security for anyone reviewing/approving these rule files.

### Likelihood Explanation
This is trivially reachable: it requires no special privilege beyond the ability to add/modify a `.claude/hookify.*.local.md` rule file (a plugin example or PR-committed file), which is explicitly one of the stated attacker capabilities. The trigger is a single stray leading space (or nesting under a list) on the `action:` (or `enabled:`) line — an easily-hidden, visually subtle formatting difference in a markdown/YAML-like file that a human reviewer is unlikely to notice, and no automated validation exists to catch it (no schema check, no re-serialization diff against the parsed result).

### Recommendation
Replace the hand-rolled frontmatter parser with a real YAML parser (e.g. `yaml.safe_load`) for the frontmatter block, or at minimum add an explicit `else` branch in `extract_frontmatter` that raises/logs on any unrecognized line so malformed indentation cannot silently vanish. Additionally, make `Rule.from_dict` fail closed: if the parsed frontmatter dict does not contain an explicit `action` key, either reject the rule (return `None`/raise) rather than defaulting to `'warn'`, or default unspecified rules to `'block'` so parser ambiguity favors safety instead of allowing bypass.

### Proof of Concept
Differential/unit test comparing `extract_frontmatter` to PyYAML and asserting the resulting `Rule.action`:

```python
import yaml
from plugins.hookify.core.config_loader import extract_frontmatter, Rule

MALFORMED = """---
name: block-dangerous-curl
enabled: true
event: bash
pattern: "curl .* \\| sh"
 action: block
---
This must be blocked!
"""

def test_indented_action_silently_dropped():
    fm, msg = extract_frontmatter(MALFORMED)
    # Reference parse of the same frontmatter body via PyYAML
    fm_text = MALFORMED.split('---', 2)[1]
    ref = yaml.safe_load(fm_text)

    # PyYAML either errors on the bad indentation or preserves 'action: block'
    # depending on strictness; the hand-rolled parser must not silently
    # diverge from the intended semantics.
    rule = Rule.from_dict(fm, msg)

    # BUG: action key is dropped by the hand-rolled parser, rule.action
    # falls back to 'warn' even though the file clearly states action: block
    assert rule.action == 'block', (
        f"Expected action='block' but parser produced action='{rule.action}' "
        "- approval gate silently downgraded to warn-only"
    )
```

Expected result (demonstrating the bug): the assertion fails, showing `rule.action == 'warn'` instead of `'block'`, confirming that `extract_frontmatter`/`Rule.from_dict` silently downgrades the enforcement action for a visually-correct `action: block` line, and that `RuleEngine.evaluate_rules` would consequently treat a matching dangerous command as a warning instead of denying it.
