### Title
Integer underflow in `AccountKeyWeightedMultiSig.SigValidationGas` when `numSigs` is zero yields near-infinite gas charge instead of a bounded value - (File: blockchain/types/accountkey/account_key_weighted_multi_sig.go)

### Summary
`AccountKeyWeightedMultiSig.SigValidationGas` computes `uint64(numSigs-1) * params.TxValidationGasPerKey` on the Istanbul-and-later path, where `numSigs` is a signed `int` parameter supplied by the caller (transaction-validation code that determines how many signatures were used to satisfy an account's multisig role). If `numSigs` is ever `0`, the subtraction `numSigs-1` evaluates to `-1` in signed `int` arithmetic and is then coerced to `uint64`, producing `18446744073709551615` (max uint64) rather than a small bounded gas amount. This mirrors the analog bug class in the external report: an unchecked subtraction that can go negative and, once reinterpreted as unsigned, silently "wraps" to a huge value instead of reverting or being clamped, corrupting a value that gates transaction processing (in this case, `IntrinsicGas`/`SigValidateGas`). ### Finding Description
`SigValidationGas` is defined as:
```go
func (a *AccountKeyWeightedMultiSig) SigValidationGas(currentBlockNumber uint64, r RoleType, numSigs int) (uint64, error) {
	numKeys := uint64(len(a.Keys))
	if numKeys > MaxNumKeysForMultiSig {
		return 0, kerrors.ErrMaxKeysExceedInValidation
	}
	if numKeys == 0 {
		return 0, kerrors.ErrZeroLength
	}

	isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul
	if isIstanbul {
		return uint64(numSigs-1) * params.TxValidationGasPerKey, nil
	}
	return (numKeys - 1) * params.TxValidationGasPerKey, nil
}
``` [1](#0-0) 

The function guards against `numKeys == 0` but performs **no validation on `numSigs`** before computing `numSigs-1`. `numSigs` is threaded through from transaction-sender/fee-payer validation (`tx.ValidateSender` / `tx.ValidateFeePayer` → `AsMessageWithAccountKeyPicker`), which combines the resulting `SigValidateGas` into the transaction's `IntrinsicGas`/`ValidatedGas.SigValidateGas`, a value used both in tx-pool admission (`tx.IntrinsicGas`, `sigValGas := gasFrom + gasFeePayer`, `tx.Gas() < intrGas+sigValGas`) and in state-transition intrinsic-gas deduction (`st.gas -= validatedGas.IntrinsicGas`). [2](#0-1) [3](#0-2) [4](#0-3) 

Normal operation relies on `numberOfValidAndUniqueSigs >= 1` whenever `Validate()` returns true, because `Validate()` requires `weightedSum >= a.Threshold` and `CheckInstallable` rejects `Threshold == 0`, so a satisfied multisig implies at least one contributing signature counted toward `numSigs`. However, the `SigValidationGas` function itself contains **no defensive check** that `numSigs >= 1` — it trusts the caller. Since `numSigs` is derived independently from the actual signature-count logic elsewhere in the tx/account-key pipeline (separate call path from `Validate()`), any code path, edge case, or future refactor that calls `SigValidationGas` with `numSigs == 0` (e.g., a role-based key lookup returning a default key with zero matched signatures for that specific role, or an internal call from RPC-side gas estimation using a synthetic/zero signature count) will silently underflow to `uint64` max, rather than erroring out as the `numKeys == 0` branch does.

This is exactly analogous to the reported Fertilizer bug: an unchecked subtraction (`MAX_RAISE - balance` in Solidity vs. `numSigs - 1` in Go) that, when the subtrahend exceeds the minuend, wraps to a maximal unsigned value instead of failing safely, and that wrapped value then feeds directly into a value gating further transaction processing (`remaining()` gating minting vs. `SigValidateGas` gating gas sufficiency/deduction).

### Impact Explanation
If triggered, the wrapped value (`~1.8e19`) would multiply by `params.TxValidationGasPerKey`, itself overflowing `uint64` again (multiplication overflow, further undefined-looking wraparound) or producing an astronomically large `SigValidateGas`. This value is added into `IntrinsicGas`/`sigValGas` used in:
- Tx pool admission checks (`tx.Gas() < intrGas+sigValGas`) — could cause legitimate transactions to be rejected (denial of gas-sufficiency check), or, depending on the overflow wraparound arithmetic, could cause the opposite: an artificially small final sum that bypasses the intended gas-sufficiency check, letting under-priced transactions be admitted and later fail/abort mid-execution in a way that diverges from what other honest nodes computed (state divergence risk) if the wraparound behaves differently across two logically-equivalent code paths.
- State transition's intrinsic gas deduction (`st.gas -= validatedGas.IntrinsicGas`) — an incorrect intrinsic gas value can cause `ErrIntrinsicGas` to fire unexpectedly or gas accounting to be wrong, which is a core state-transition/gas-metering invariant.

Because this affects gas/fee accounting integrity for an entire class of accounts (weighted-multisig, reachable by any AccountKeyWeightedMultiSig user submitting a transaction), and can potentially cause acceptance of transactions with incorrect gas cost or unexpected rejection of valid ones — both are within the accepted impact categories (state transition / gas metering integrity, acceptance of invalid transactions).

### Likelihood Explanation
The precondition (`numSigs == 0` reaching `SigValidationGas`) is guarded indirectly by `Validate()`'s threshold logic in the currently-visible call chain, so exploiting this from a single, ordinarily-signed transaction may not be directly reachable through the primary sender/fee-payer validation path as currently wired. The `numKeys == 0` case is explicitly checked and errors out, but the symmetric `numSigs <= 0` case has no such guard, which is inconsistent defensive coding and indicates the underflow was not intentionally considered safe by design — only incidentally prevented by call-site invariants that are not enforced within the function itself. Because I could not fully trace every call site that supplies `numSigs` (e.g., default-key fallback in `AccountKeyRoleBased.SigValidationGas`, RPC gas-estimation paths, or `MultiSig` accounts where the role key differs from the signing role and a default/nil key substitution occurs), I cannot confirm with full certainty that `numSigs == 0` is unreachable from an attacker-controlled transaction shape. This should be treated as **medium likelihood pending full call-graph verification** by the Kaia team, since the missing guard is a real robustness gap regardless.

### Recommendation
Add an explicit guard in `AccountKeyWeightedMultiSig.SigValidationGas` (and any other `SigValidationGas` implementations using `numSigs - 1`) to reject or clamp `numSigs <= 0` before performing the subtraction, mirroring the existing `numKeys == 0` check:
```go
if numSigs <= 0 {
    return 0, kerrors.ErrZeroLength // or a dedicated error
}
```
This prevents the signed-to-unsigned underflow regardless of whether current call sites can produce `numSigs == 0`, closing the same class of defect described in the external report (unchecked subtraction feeding directly into a value that gates transaction/consensus-critical logic). Additionally, audit all callers of `SigValidationGas` across `AccountKeyRoleBased`, `AccountKeyPublic`, and RPC/gas-estimation code paths to confirm `numSigs` is always derived from an actual non-negative signature count before being passed in.

func (tx *Transaction) AsMessageWithAccountKeyPicker(s Signer, picker AccountKeyPicker, currentBlockNumber uint64) (*Transaction, error) {
	intrinsicGas, err := tx.IntrinsicGas(currentBlockNumber)
	if err != nil {
		return nil, err
	}

	gasFrom, err := tx.ValidateSender(s, picker, currentBlockNumber)
	if err != nil {
		return nil, ErrSender(err)
	}

	tx.mu.Lock()
	tx.checkNonce = true
	tx.mu.Unlock()

	gasFeePayer := uint64(0)
	if tx.IsFeeDelegatedTransaction() {
		gasFeePayer, err = tx.ValidateFeePayer(s, picker, currentBlockNumber)
		if err != nil {
			return nil, ErrFeePayer(err)
		}
	}

	sigValidationGas := gasFrom + gasFeePayer
	intrinsicGas = intrinsicGas + sigValidationGas

	tx.mu.Lock()
	tx.validatedGas = &ValidatedGas{IntrinsicGas: intrinsicGas, SigValidateGas: sigValidationGas}
	tx.mu.Unlock()

	return tx, err
}
