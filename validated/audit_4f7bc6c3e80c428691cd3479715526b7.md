I have enough evidence to write up the finding. The Tron variant of `IntentGatewayV2.placeOrder` never got the fee-on-transfer fix that the mainline EVM contract received, creating an escrow-accounting mismatch that is a direct local analog of the reported bug class.

### Title
Escrow over-crediting for fee-on-transfer tokens in `placeOrder` — Tron `IntentGatewayV2` never adopted the balance-diff fix ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The mainline EVM `IntentGatewayV2.placeOrder` explicitly measures actual token balance received before crediting escrow, specifically to defend against fee-on-transfer tokens [1](#0-0) . The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, still escrows the *nominal* requested amount rather than the amount actually transferred in, exactly reproducing the "Avoid transfer fee" bug class from the external report: the contract can receive less token than it credits to escrow.

### Finding Description
In the non-predispatch branch of `placeOrder`, the Tron contract does: [2](#0-1) 

`IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` moves at most `order.inputs[i].amount`, but for a fee-on-transfer token the gateway's actual balance increase is smaller. Despite this, `_orders[commitment][token] += reducedInputs[i].amount` credits escrow using `reducedInputs[i]`, which is derived purely from the nominal `order.inputs[i].amount` minus the protocol fee [3](#0-2)  — never from the contract's measured balance delta.

The predispatch branch of the same function is no better: it computes `dust = balance - requiredAmount` from `IERC20(token).balanceOf(dispatcher)` (the call dispatcher's balance) and still credits `reducedInputs[i].amount`, not the amount actually swept into the gateway itself via the `transferCalls` — which is a second `IERC20.transfer` that can itself be fee-on-transfer-lossy [4](#0-3) .

Compare this to the mainline EVM contract, which snapshots `balBefore`/`balancesBefore`, re-reads `balanceOf` after the transfer, and mutates `order.inputs[i].amount` to the *actual received* amount before computing `reducedInputs` and the commitment [5](#0-4) . This is precisely the guard the tron contract lacks.

`_orders[commitment][token]` is a shared global ledger across all orders using that token. Withdrawal pays out of this ledger without ever re-checking the contract's real token balance: [6](#0-5) 

Once escrow bookkeeping (`_orders[...]`) collectively exceeds the gateway's actual token holdings — which happens automatically the first time a fee-on-transfer token is used in `placeOrder` — the contract is insolvent for that token by the fee amount. `withdraw()` performs a low-level `token.call(...transfer...)` and only checks `success`; it does not verify the beneficiary actually received the escrowed `amount`, and it decrements `_orders[body.commitment][token] -= amount` unconditionally. There is no per-user segregation of "real" balance versus "credited" balance.

### Impact Explanation
This directly falls into the bounty's "stealing or loss of funds" and "double-settlement" categories: the escrow ledger commits to paying out more of a token than the contract actually holds. Whichever order's withdrawal happens to be settled last for that token will either:
- revert (fund lock for that user, since actual balance is short), or
- if the shortfall is subtle and balances happen to be commingled across orders using the same token, an earlier withdrawal can consume balance that was actually funded by a *different* user's escrowed deposit, meaning some user's principal is paid out to someone else while their own order's real backing has evaporated to the token's transfer fee.

Both outcomes are fund-loss/fund-lock conditions rooted purely in escrow-accounting logic, unreachable by any privileged actor and requiring no relayer/prover assumptions — a normal user calling public `placeOrder` with a standard ERC-20 that happens to levy a transfer fee (a category of token this protocol explicitly anticipates elsewhere in the codebase) triggers it.

### Likelihood Explanation
Likelihood is directly tied to whether a fee-on-transfer token is listed as a supported input asset on the Tron deployment. The comment block and identical fix already merged into the mainline EVM `IntentGatewayV2.sol` show the team is aware fee-on-transfer tokens are a real, expected input case for this contract family — they just didn't port the fix to the Tron fork. No malicious relayer, governance, or oracle compromise is required; any unprivileged user calling `placeOrder` with such a token triggers the mismatch on every call.

### Recommendation
Port the balance-diff pattern from `evm/src/apps/IntentGatewayV2.sol` (lines 281-298 and 229-280) into `evm/tron/contracts/apps/IntentGatewayV2.sol`: snapshot `balanceOf(address(this))` (and the dispatcher's balance where applicable) before each transfer, and after the transfer set `order.inputs[i].amount` to the measured delta before computing `reducedInputs`/the commitment/escrow credit, exactly as the mainline contract already does.

### Proof of Concept
1. Governance/deployer lists a fee-on-transfer ERC-20 token (fee currently 0, can be changed by the token's own admin — no Hyperbridge privilege needed) as a valid `order.inputs[i].token` on the Tron `IntentGatewayV2`.
2. User A calls `placeOrder` with `order.inputs[0].amount = 1000`. Token charges a 1% transfer fee, so the gateway's real balance only increases by 990. `_orders[commitmentA][token]` is nonetheless credited with `reducedInputs[0].amount` (≈1000 minus protocol fee), i.e. 10 more than what was actually received.
3. Repeat with User B placing a similar order; the ledger deficit accumulates (contract owes 20 more tokens than it holds across the two commitments).
4. When solvers/relayers process withdrawals (`RedeemEscrow`/`RefundEscrow` via `onAccept` → `withdraw`) for both commitments in sequence, the second withdrawal's `token.call(transfer...)` either reverts (insufficient balance → fund lock) or, since escrow credits are commingled per-token rather than backed 1:1, an earlier withdrawal can drain balance that nominally belongs to a still-open order, leaving that order's holder unable to redeem their full escrowed amount (fund loss).
