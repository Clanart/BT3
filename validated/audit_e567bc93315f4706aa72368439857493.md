## Title
Unbounded `challengePeriod` in `EvmHost.updateHostParamsInternal` can permanently brick request/response/timeout processing, locking all escrowed funds — (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.updateHostParamsInternal` validates several `HostParams` fields (host manager, handler, consensus client, `hyperbridge` id, `stateMachines` length, and a *minimum* `unStakingPeriod`) but never enforces an upper bound on `challengePeriod`. `HandlerV2` gates every inbound POST request, GET response, and both timeout paths on `challengePeriod > delay` reverting with `ChallengePeriodNotElapsed`. Setting `challengePeriod` to an extreme value (e.g. close to `type(uint256).max`) makes that condition permanently true, so no request, response, or timeout can ever be delivered again — freezing every fund-moving flow that depends on message delivery (intent-gateway escrow refunds/settlements, bandwidth-manager purchases, relayer fee withdrawals, paymaster governance). This is the direct functional analog of the QuantConfig/`ConfigTimelockController` report: an unbounded delay parameter that, once set too high, renders the whole system's core state-mutating paths permanently unusable.

### Finding Description
`HostParams.challengePeriod` is stored and consumed unconditionally in the message handler: [1](#0-0) [2](#0-1) [3](#0-2) 

The setter that writes this value performs several sanity checks but has no maximum bound on `challengePeriod`: [4](#0-3) 

Compare this with `SimplexPaymaster.sol`, where the team explicitly caps every governance-configurable numeric parameter (`MAX_MARKUP_BPS`, `MAX_ORACLE_AGE`, `MAX_SWAP_SLIPPAGE_BPS`) precisely to prevent this class of "unbounded governance value bricks the contract" bug: [5](#0-4) 

`EvmHost.updateHostParams` is the one place in the codebase holding a similarly critical delay-style parameter (`challengePeriod`) without that same defensive cap, even though the value flows straight into the four gatekeeping checks in `HandlerV2` shown above. `updateHostParams` itself is only reachable through the authenticated `hostManager` cross-chain governance channel: [6](#0-5) [7](#0-6) 

but authentication of the *caller* does nothing to bound the *value* — a single legitimate/careless governance update (e.g., a unit mismatch, or a typo like an extra zero) with an outsized `challengePeriod` is accepted and immediately bricks the host, exactly as an outsized `minDelay` bricked `QuantConfig`.

### Impact Explanation
Once `challengePeriod` is set too high, `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` all revert forever (`delay` can never exceed the now-enormous `challengePeriod`). Every flow that depends on delivering a request/response/timeout to this host is permanently frozen:
- Intent-gateway cross-chain order fills, `RefundEscrow`/`RedeemEscrow` settlements, and cancellations can never be delivered — user and solver funds already escrowed are locked indefinitely.
- Relayer fee withdrawals delivered via POST requests can never land — accrued relayer rewards are permanently unclaimable.
- Bandwidth purchases/credits and paymaster governance messages routed through ISMP likewise stop working.
- There is no recovery path other than another governance `updateHostParams` call — but that call is itself an ISMP dispatch that must pass through the very same bricked pipeline, so the host cannot self-heal without an entirely separate emergency mechanism.

This matches the bounty's accepted impact class of "stealing or loss of funds" / fund lock via a broken invariant in request/response/timeout handling.

### Likelihood Explanation
The only path is a legitimate call to `updateHostParams` through the `hostManager`/cross-chain governance channel, i.e., no malicious relayer, prover, or unauthenticated flow is required, but this remains a governance-set value. It is included here strictly as a config-validation gap (missing upper bound), analogous to the original report's own scope (an unbounded config field, not a privilege-escalation exploit). Likelihood of a mistaken or oversized value is non-trivial given `challengePeriod` is a raw `uint256` in seconds with no sanity ceiling enforced anywhere in `updateHostParamsInternal`, unlike the `unStakingPeriod` lower-bound check right next to it.

### Recommendation
Add an explicit upper bound check in `updateHostParamsInternal`, mirroring the pattern already used in `SimplexPaymaster` (`MAX_ORACLE_AGE`, etc.):
```solidity
uint256 public constant MAX_CHALLENGE_PERIOD = 7 days; // or another sane ceiling
...
if (params.challengePeriod > MAX_CHALLENGE_PERIOD) revert InvalidChallengePeriod();
```
This guarantees `challengePeriod` can never exceed a value that would permanently block `handlePostRequests`/`handleGetResponses`/timeout handling, closing the same class of bug the QuantConfig report identified.

### Proof of Concept
1. Governance (via `HostManager.onAccept` → `IHostManager(_params.host).updateHostParams`) submits a `HostParams` update with `challengePeriod = type(uint256).max - 1`.
2. `updateHostParamsInternal` passes all existing checks (hostManager/handler/consensusClient valid, `hyperbridge` non-empty, `stateMachines` non-empty, `unStakingPeriod >= 1 day`) and stores the new `challengePeriod`.
3. Any subsequent call to `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, or `handleGetRequestTimeouts` computes `delay = timestamp - updateTime` (bounded by realistic block timestamps) and compares against `challengePeriod`; since `challengePeriod > delay` is always true, every call reverts with `ChallengePeriodNotElapsed`.
4. All pending and future cross-chain requests/responses/timeouts to this host are permanently undeliverable — escrowed funds in `IntentGatewayV2`/`ExtrinsicIntents`, unclaimed relayer fees, and bandwidth/paymaster governance messages are locked with no on-chain recovery path.

    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams
        uint256 stateMachinesLen = params.stateMachines.length;
        if (stateMachinesLen == 0) revert InvalidStateMachinesLength();

        // otherwise cannot process new datagrams
        if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();

        address oldFeeToken = feeToken();
        if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
            uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
            if (balance != 0) revert CannotChangeFeeToken();
        }

        // safe to emit here because invariants have already been checked
        // and don't want to store a temp variable for the old params
        emit HostParamsUpdated({oldParams: _hostParams, newParams: params});

        _hostParams.feeToken = params.feeToken;
        _hostParams.admin = params.admin;
        _hostParams.handler = params.handler;
        _hostParams.hostManager = params.hostManager;
        _hostParams.uniswapV2 = params.uniswapV2;
        _hostParams.unStakingPeriod = params.unStakingPeriod;
        _hostParams.challengePeriod = params.challengePeriod;
        _hostParams.consensusClient = params.consensusClient;
        _hostParams.stateMachines = params.stateMachines;
        _hostParams.hyperbridge = params.hyperbridge;

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }
