## Finding: Naive `+`-concatenation hash used as repository identity is not collision-resistant

### Title
Repository/GitHubRepository identity `hash` is a naively-joined string, allowing distinct objects to collide - (File: `app/src/models/equality-hash.ts`)

### Summary
`createEqualityHash` builds the `hash` property that `Repository` and `GitHubRepository` rely on for "structural equality," but it simply `Array.prototype.join('+')`s the field values without escaping or length-prefixing them. [1](#0-0)  This is the same broken invariant as the Fabric advisory: concatenating variable-length, attacker-influenced strings without a delimiter/escaping scheme lets different tuples of input produce an identical "hash," even though the code's own documentation promises "objects with the same hash are guaranteed to be structurally equal." [2](#0-1) [3](#0-2) 

### Finding Description
`GitHubRepository.hash` is computed from API-derived fields — `name`, `owner.login`, `htmlURL`, `cloneURL`, plus booleans/permissions and the parent's hash — joined with `'+'`. [4](#0-3)  `Repository.hash` is likewise built by joining `path`, `id`, `gitHubRepository?.hash`, `missing`, `alias`, the fork-contribution preference and `isTutorialRepository`. [5](#0-4) 

Because none of these string-valued fields (repository `name`, `owner.login`, `htmlURL`, `cloneURL`, local `path`, `alias`) are escaped before joining with `'+'`, a value that itself contains a `'+'` shifts the effective field boundaries in the resulting string. Two structurally different tuples can therefore serialize to the identical hash string — e.g. `['a+b', 'c']` and `['a', 'b+c']` both join to `'a+b+c'`. This mirrors the Fabric bug's root cause: hashing/serializing structured data via naive concatenation instead of a length-prefixed or otherwise unambiguous encoding, so the resulting digest/identifier does not uniquely determine the input.

The attacker-reachable surface is the GitHub API object: `name`, `owner.login`, `htmlURL`, and `cloneURL` are populated from repository metadata returned by whatever GitHub/GitHub Enterprise endpoint the user is connected to. [6](#0-5)  On a GitHub Enterprise Server under attacker control, none of these fields are constrained to GitHub.com's login-character rules, so an attacker operating (or proxying) such a server can freely choose `htmlURL`/`cloneURL` strings containing `'+'` to try to collide the resulting `hash` with that of a different, legitimate repository the user has open in Desktop.

I confirmed via search that `.hash` is consumed as an identity/lookup key by `app/src/lib/stores/git-store-cache.ts` and `app/src/lib/stores/repository-state-cache.ts` (both reference `.hash` multiple times), which are the per-repository caches for git state and UI/history state, but I was not able to fully read those files' internals in this session to confirm the exact collision-triggering code path — this remains unverified and should be checked directly.

### Impact Explanation
If the `hash` is genuinely used as a de-duplication/lookup key for per-repository caches (`GitStoreCache`, `RepositoryStateCache`), a crafted collision could cause Desktop to associate a cloned/attacker-controlled repository with the cached git state (diffs, branch/working-directory status) of a different, legitimate repository the user has open, or vice versa. That falls under "silent corruption of what the user commits or pushes," since the UI could present stale/foreign diff or status data for the wrong repository without any error being surfaced.

### Likelihood Explanation
Exploitability depends on (a) confirming that `.hash` is actually used as a cache/dedup key rather than just a React re-render optimization, and (b) the practical difficulty of getting Desktop to load two repositories whose full field tuples collide under `'+'`-join given the other fixed fields (numeric `dbID`, booleans, `owner.login`/`name` character restrictions on GitHub.com). Collisions are much easier to engineer against a self-hosted/attacker-controlled GitHub Enterprise instance, where `htmlURL`/`cloneURL` are fully attacker-chosen, than against GitHub.com. I could not verify actual downstream exploitation in this session due to not reading `git-store-cache.ts`/`repository-state-cache.ts` contents.

### Recommendation
Replace the naive `join('+')` in `createEqualityHash` with an unambiguous encoding — e.g., hash each field's length-prefixed representation (or JSON-stringify with escaping, or feed each field into a cryptographic hash with explicit separators/length prefixes) so that distinct input tuples cannot produce the same output string. Independently, audit `git-store-cache.ts` and `repository-state-cache.ts` to confirm whether `.hash` is used as a strict identity key, and if so, prefer the repository's local database `id`/full unique tuple (not a lossy joined string) as the cache key.

### Proof of Concept
Conceptual collision against `createEqualityHash` (`app/src/models/equality-hash.ts:15-17`):
```ts
createEqualityHash('a+b', 'c') // => 'a+b+c'
createEqualityHash('a', 'b+c') // => 'a+b+c'  (identical output, different inputs)
```
Applied to `GitHubRepository`, an attacker-controlled GitHub Enterprise server can return a repository whose `htmlURL`/`cloneURL` contains a `'+'` sequence engineered so that the concatenation of `name + owner.login + dbID + isPrivate + htmlURL + cloneURL + issuesEnabled + isArchived + permissions + parent?.hash` matches that of a different, legitimate `GitHubRepository` already known to the client, per the construction in `app/src/models/github-repository.ts:32-43`. Full exploitation still requires confirming how `git-store-cache.ts`/`repository-state-cache.ts` use `.hash`, which I was unable to verify in this session — treat the cache-collision impact as unconfirmed pending that review.
