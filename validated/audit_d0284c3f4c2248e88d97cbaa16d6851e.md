### Title
FROST preprocess seed cached per context is reused for every `share_internal`/`complete` invocation, enabling nonce reuse and secret-share/key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

`SigningProtocol::preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:100-148) caches the FROST preprocess *seed* keyed only by `self.context` (e.g. `(b"DkgConfirmer", attempt)`), decrypts it, and rebuilds the sign machine via `AlgorithmSignMachine::from_cache` on every call. `share_internal` calls `preprocess_internal` unconditionally (line 156), so every invocation of `share()` and `complete()` re-derives *identical FROST nonces* (`seeded_preprocess` at crypto/frost/src/sign.rs:121-144 regenerates `d`, `e` deterministically from the cached seed). This directly violates the documented precondition on `CachedPreprocess` — "a preprocess MUST only be used once. Reuse will enable third-party recovery of your private key share" (crypto/frost/src/sign.rs:83-92).

### Finding Description

The upstream bug class is "a party authorized to write certain objects can extract secrets held by the system." The analog here: a participant who can cause the coordinator to run `share_internal`/`complete` with *different* inputs under the same context forces the honest signer to sign multiple distinct challenges with the same `(d_i, e_i)` nonces.

Concretely, `DkgConfirmer::share` and `DkgConfirmer::complete` (lines 288-327) both route into `share_internal`, each time reconstructing the machine from the *same* cached seed. The signed message is `set_keys_message(set, removed, key_pair)`, where `key_pair` is supplied per call by the caller (lines 296-300), and the preprocess map is likewise caller-supplied per call. If `share` is executed for `key_pair_A` and `complete` (or a further confirmation path) is executed for a different `key_pair_B`, or with a different valid preprocess set (different included members / different honest preprocess bytes, which the attacker controls since they are a signer contributing their own preprocess), then:

- the binding factor `rho_i = hash_binding_factor(msg_hash || commitments)` differs,
- the Schnorr challenge `c` differs,
- but `d_i` and `e_i` are identical.

Each invocation emits a broadcast `SignatureShare` `z_i = d_i + e_i·rho_i + lambda_i·s_i·c`. With `k` distinct `(msg, preprocess-set)` combinations under one cached seed, an observer obtains `k` linear equations in only three unknown scalars (`d_i`, `e_i`, `s_i`); `k ≥ 3` uniquely determines `s_i`, the validator's FROST secret share over the MuSig-aggregated set key. With two equations the system is underdetermined by one dimension, but any third distinct signing under the same context closes it — and there is no usage counter, no deletion of `CachedPreprocesses` after first use, and no check that the msg/participant set matches what the seed was originally generated for.

### Impact Explanation

Recovery of a validator's secret share `s_i` for the set key compromises that validator's threshold signing capability permanently for the session (the share is the long-lived MuSig/FROST key material, `self.key`, not a per-session nonce). Combined with a threshold worth of similarly recovered shares — all honest nodes reuse their seeds the same way — the group key itself is exposed, enabling forgery of `set_keys` signatures and any subsequent signatures for that validator set's substrate key. This is key-share recovery reachable purely by feeding crafted-but-valid public inputs (preprocesses, confirmation `key_pair` values) into reachable signing APIs.

### Likelihood Explanation

The mechanism is deterministic: reuse is not a probabilistic edge case, it happens on *every* call past the first within a context, by construction. The residual requirement is that the attacker drive `share_internal`/`complete` to `sign()` multiple times with differing `msg` or differing valid preprocess sets under one `(context, attempt)`. The confirmation flow accepts `key_pair` and `preprocesses` from tributary transactions authored by validators, so a validator participant has a realistic path to trigger repeated `share_internal` executions with differing inputs. I could not fully trace `coordinator/src/tributary/handle.rs` to confirm how many times `complete` is invoked with distinct data per attempt; if it is provably invoked exactly once with the identical `key_pair`, the exploit requires the differing-preprocess-set variant instead (an attacker supplying a different subset/membership still changes `rho`/`c` while nonces stay fixed).

### Recommendation

Bind the cached preprocess to a single use:

- Delete or tombstone `CachedPreprocesses` after the machine is first used to produce a share, and refuse to `sign()` a second time under the same seed.
- Alternatively, record the exact `(msg, included-set)` bound to the cached seed at first `sign()` and reject (`Err`) any subsequent `share_internal`/`complete` call whose message or signer set differs, rather than deterministically re-signing.
- Prefer deriving the preprocess fresh in `share()`/`complete()` from a stored `AlgorithmSignMachine` (keeping the machine alive in memory/DB) instead of re-seeding, matching the design already used by `processor/src/signer.rs` and `processor/src/batch_signer.rs`, which keep machines and explicitly delete them on re-attempt.

### Proof of Concept

1. During a DKG confirmation attempt, all honest validators emit `preprocess()` and `share()` for `key_pair_A`. Each `share` is `z_1 = d + e·rho_A + lambda·s·c_A`, broadcast publicly.
2. A malicious validator submits a confirmation completion path (or an additional confirmation transaction) carrying `key_pair_B != key_pair_A` (or a preprocess map with a different valid membership). `DkgConfirmer::complete` → `share_internal` → `preprocess_internal` reloads the *same* cached seed, regenerates identical `d, e`, and computes a new share `z_2 = d + e·rho_B + lambda·s·c_B` over the different challenge.
3. A third distinct combination yields `z_3`. The attacker solves the 3×3 linear system in `(d, e, s)` over `C::F` and recovers the victim's secret share `s`.
4. Repeating this against `t` validators (all reuse seeds identically) recovers enough shares to reconstruct the set's aggregate private key, enabling arbitrary signature forgery for the validator-set key.

Root-cause lines: unconditional reuse at `share_internal` line 156; seed cache/read and `from_cache` at lines 123-145; deterministic nonce regeneration at crypto/frost/src/sign.rs:121-144; the violated single-use contract documented at crypto/frost/src/sign.rs:83-92 and 216-224.
