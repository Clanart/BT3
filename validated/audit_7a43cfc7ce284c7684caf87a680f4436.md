Based on my investigation, I found a concrete analog: the merge-completion commit path bypasses Desktop's hook-interception/guard layer that every other commit-producing operation goes through.

### Title
`createMergeCommit` Skips Hook Interception, Letting an Attacker-Controlled `commit-msg`/`post-commit` Hook Run Unmonitored When Resolving Conflicts From a Malicious Clone - (File: `app/src/lib/git/commit.ts`)

### Summary
GitHub Desktop added a "hooks interception" layer that wraps every git command capable of triggering repository-defined hooks (`pre-commit`, `commit-msg`, `post-commit`, etc.) in a proxy so the app can surface hook output/failures and let the user abort [1](#0-0) . This is invoked via the `interceptHooks` option that `git()` reads before running any command [2](#0-1) . `createCommit` (used for a normal commit) correctly declares the hook set it expects and wires `onHookFailure`/`onHookProgress` callbacks so a failing or malicious hook can be surfaced/aborted [3](#0-2) . `createMergeCommit`, used to finalize a merge after the user resolves conflicts, calls `git(['commit', '--no-edit', '--cleanup=strip'], ...)` with **no `interceptHooks`, no `onHookFailure`, and no `onHookProgress`** at all [4](#0-3) .

### Finding Description
The broken invariant is: "every commit-producing git invocation must run through the hooks-interception guard so Desktop can observe/gate hook execution." `withHooksEnv` only activates the proxy/interception when `opts?.interceptHooks` is supplied [5](#0-4) ; if it is omitted, `git()` runs the command directly with the caller's raw environment, so Git will invoke whatever `commit-msg`/`post-commit`/`pre-commit` hooks exist in the repository's actual `core.hooksPath`/`.git/hooks` directory, without ever routing through the `createHooksProxy` server that the rest of the app relies on for progress reporting and, more importantly, for giving the user the *"abort"* choice on hook failure (`onHookFailure`) [6](#0-5) .

`createMergeCommit` is exactly the code path exercised when a user resolves merge conflicts in a repository that was cloned/fetched from an attacker (the classic "malicious repo contains a `.git/hooks/commit-msg` or `.git/hooks/post-commit` script" primitive, further empowered by Desktop's own hooks feature which explicitly warns that untrusted repos "may automatically execute files in the repository" [7](#0-6) ). Because this call path skips the `interceptHooks` gate, the very safety net (hook-failure prompt, terminal-output capture, ability to abort) that Desktop introduced for `createCommit`, `pull`, `push`, and `merge` [8](#0-7)  simply does not exist for merge-completion commits — the hook runs with full user privileges and Desktop has no visibility or abort control over it.

This is a structural analog of the Polygon report's core flaw: a security control (the "lock"/hook-interception guard) is applied per code path rather than being an invariant enforced uniformly at the primitive level (`git()`), so one specific call site (`createMergeCommit`, analogous to the `multicall`-driven refund+fill combo) falls outside the guard and lets attacker-supplied logic run with the trust/control-flow the guard was meant to withhold.

### Impact Explanation
An attacker who controls a repository the victim clones/adds (or a fork the victim pulls from) can plant a `commit-msg`, `pre-commit`, or `post-commit` hook. When the victim later resolves a conflicting merge in Desktop and finishes it, `createMergeCommit` executes `git commit` directly, running that hook with the user's OS-level privileges and no Desktop-mediated interception, abort prompt, or terminal-output capture. This yields arbitrary local code execution outside any sandbox, corruption of the resulting commit content, or silent credential/token exfiltration from the hook's execution environment (which inherits the user's shell/session).

### Likelihood Explanation
Reaching this path requires only normal Desktop usage: clone/add a repository containing a merge conflict scenario, let a merge produce conflicts, resolve them, and click "commit merge" — a common workflow, not requiring local/physical access, admin rights, prior malware, or social engineering beyond "the user resolves a conflict from a repo they added." The attacker fully controls the repository's hook scripts, satisfying the "attacker controls a cloned/fetched repository" condition for a valid Desktop analog.

### Recommendation
Route `createMergeCommit`'s `git(['commit', ...])` call through the same `interceptHooks` mechanism used by `createCommit`, listing the hooks a merge commit can trigger (`pre-commit`, `commit-msg`, `post-commit`, `post-merge`, `pre-auto-gc`), and thread `onHookProgress`/`onHookFailure`/`onTerminalOutputAvailable` callbacks from the caller so failures can be surfaced and aborted consistently with every other commit-producing code path.

### Proof of Concept
1. Attacker creates/hosts a repository containing a divergent branch that is guaranteed to conflict with the victim's branch, plus a malicious executable `commit-msg` (or `post-commit`) hook script in `.git/hooks/`.
2. Victim clones or adds this repository in GitHub Desktop and attempts to merge the attacker's branch, producing conflicts.
3. Victim resolves the conflicts in Desktop's guided flow and clicks to complete the merge; internally this calls `_finishConflictedMerge`/`createMergeCommit` [9](#0-8) .
4. Because no `interceptHooks` option is passed, `withHooksEnv` returns immediately (`if (!opts?.interceptHooks...) return fn(opts?.env)`) [5](#0-4) , and Git invokes the attacker's hook directly and unmonitored, with no chance for the user to see/abort it via Desktop's `onHookFailure` UI, unlike a regular commit made via `createCommit`.

export async function createMergeCommit(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  manualResolutions: ReadonlyMap<string, ManualConflictResolution> = new Map()
): Promise<string> {
  // apply manual conflict resolutions
  for (const [path, resolution] of manualResolutions) {
    const file = files.find(f => f.path === path)
    if (file !== undefined) {
      await stageManualConflictResolution(repository, file, resolution)
    } else {
      log.error(
        `couldn't find file ${path} even though there's a manual resolution for it`
      )
    }
  }

  const otherFiles = files.filter(f => !manualResolutions.has(f.path))

  await stageFiles(repository, otherFiles)
  const result = await git(
    [
      'commit',
      // no-edit here ensures the app does not accidentally invoke the user's editor
      '--no-edit',
      // By default Git merge commits do not contain any commentary (which
      // are lines prefixed with `#`). This works because the Git CLI will
      // prompt the user to edit the file in `.git/COMMIT_MSG` before
      // committing, and then it will run `--cleanup=strip`.
      //
      // This clashes with our use of `--no-edit` above as Git will now change
      // it's behavior to invoke `--cleanup=whitespace` as it did not ask
      // the user to edit the COMMIT_MSG as part of creating a commit.
      //
      // From the docs on git-commit (https://git-scm.com/docs/git-commit) I'll
      // quote the relevant section:
      // --cleanup=<mode>
      //     strip
      //        Strip leading and trailing empty lines, trailing whitespace,
      //        commentary and collapse consecutive empty lines.
      //     whitespace
      //        Same as `strip` except #commentary is not removed.
      //     default
      //        Same as `strip` if the message is to be edited. Otherwise `whitespace`.
      //
      // We should emulate the behavior in this situation because we don't
      // let the user view or change the commit message before making the
      // commit.
      '--cleanup=strip',
    ],
    repository.path,
    'createMergeCommit'
  )
