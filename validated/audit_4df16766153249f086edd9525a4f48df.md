### Title
Silent overwrite of an already-resolved/staged conflict file by stale Copilot resolution content - ([File: app/src/lib/stores/app-store.ts])

### Summary
`_applyCopilotConflictResolutions` in `app-store.ts` writes AI-generated resolution content to disk when the user clicks "Continue Merge/Rebase/Cherry-pick". It contains a single guard meant to prevent clobbering a file the user has already fixed by hand while the Copilot turn was running, but that guard only fires while the file's status is *still reported as `Conflicted`*. Once the file leaves the conflicted state (e.g. the user finished resolving it and staged it, or git otherwise reports it as `Modified`/absent from the working-directory list), the guard is bypassed and the stale, pre-computed `resolution.resolvedContent` is written over the user's own resolution and staged with `git add`. [1](#0-0) 

### Finding Description
The write path is:
```
const onDiskFile = state.changesState.workingDirectory.files.find(f => f.path === resolution.path)
if (onDiskFile !== undefined && isConflictedFileStatus(onDiskFile.status) && !hasUnresolvedConflicts(onDiskFile.status)) {
  continue // skip — the user already resolved this file
}
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
``` [1](#0-0) 

This is a two-condition check analogous to the audit finding's pattern: the code assumes the *only* way a user can resolve a file outside of the Copilot flow is for it to remain classified `Conflicted` with zero remaining markers (`isConflictedFileStatus(...) && !hasUnresolvedConflicts(...)`). But `hasUnresolvedConflicts`/`isConflictedFileStatus` are derived from `AppFileStatusKind`, which is only `Conflicted` for files that are still unmerged in the git index: [2](#0-1) [3](#0-2) 

If the file transitions to any other status — e.g. the user resolves and stages it themselves (`git add`) while the async Copilot SDK turn is still streaming (turns can take up to the configured timeout, default 600s) — `onDiskFile.status` is no longer `Conflicted`, so `isConflictedFileStatus(onDiskFile.status)` is `false`. The "skip" branch is never taken, and the code falls through unconditionally to `writeFile(...)`, overwriting the user's staged, resolved content with Copilot's resolution computed from the original (still-conflicted) file content it read minutes earlier via `buildConflictContext`/`reassembleResolvedFile`. [4](#0-3) 

The `resolvedContent` being written is derived purely from `ctx.rawContent` (a snapshot of the conflicted file taken before the AI turn started) spliced with the model's proposed hunks — it has no relationship to what is now staged in the index. This lets an attacker who controls the branch/commit history that produces the conflict (e.g. a malicious PR the victim merges/rebases against) shape which content the AI model is likely to retain (via prompt-influenceable conflict markers, commit messages, or PR descriptions consumed by the system prompt) so that if the victim manually strips the attacker's payload and stages the fix while Copilot is still "thinking," Desktop will silently reintroduce the attacker's version on "Continue Merge" — without any diff review, since the dialog's diff preview was computed at proposal time, not at commit time.

### Impact Explanation
This breaks the invariant that "what the user explicitly staged is what gets committed." A crafted upstream branch/PR can cause GitHub Desktop to silently discard a user's manual fix and commit attacker-influenced file content instead, corrupting the resulting commit without any further user action or warning — squarely inside "silent corruption of what the user commits or pushes" from an attacker-controlled repository/PR.

### Likelihood Explanation
Requires a specific race: the user must resolve and stage the conflicted file manually while the Copilot resolution turn (which can run for a long time, default timeout 600s) is still in flight, and then click "Continue" from the result dialog without re-checking the diff. This is a plausible but narrow timing window, and the existing partial guard shows the developers already anticipated the "user resolves externally" case — they just didn't cover the case where the file's status kind changes away from `Conflicted` (staged) rather than staying `Conflicted` with zero markers. Likelihood is moderate: it depends on user behavior/timing, not purely attacker action, but no privileged access or malware is required — only a normal merge/rebase against attacker-controlled history.

### Recommendation
Do not gate the skip solely on `isConflictedFileStatus`. Compare the working-directory file's actual on-disk/staged content (or its absence from `workingDirectory.files` altogether) against `ctx.rawContent`/the original conflicted snapshot, and skip the write whenever the file is no longer in the same unresolved-conflict state it was in when the Copilot turn started — regardless of what `AppFileStatusKind` it now reports as. At minimum, treat "not found in `workingDirectory.files`" and "found with any non-conflicted kind" the same as "resolved externally, skip".

### Proof of Concept
1. Attacker crafts a branch/PR that, when merged/rebased into the victim's branch, produces a conflicting file (e.g. a config or lockfile) where the attacker's side contains a subtly malicious value.
2. Victim starts merge/rebase in Desktop, clicks "Resolve with Copilot"; `_startCopilotConflictResolution` kicks off a Copilot turn against `copilot-store.ts`'s `runConflictResolutionTurn`, which can take a long time.
3. While waiting, the victim manually edits the file in an external editor to strip the malicious content, then runs `git add` (staging it) — status kind changes from `Conflicted` to e.g. `Modified`/staged, no longer matching `isConflictedFileStatus`.
4. Copilot's turn completes and populates `copilotResolutions` with content reassembled from the original (attacker-tainted) snapshot.
5. Victim clicks "Continue Merge" on the result dialog; `_applyCopilotConflictResolutions` runs, finds `onDiskFile.status` is no longer `Conflicted`, so the skip guard at lines 7250-7256 does not trigger, and `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` at line 7258 overwrites the victim's manually-fixed, staged file with the stale AI-resolved content, which is then `git add`-ed and committed — reintroducing the attacker's payload without the victim's knowledge. export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
