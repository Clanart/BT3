## Analysis

The Olympus bug's core invariant: a **cheap, permissionless action can seize and hold a shared, single-slot/limited-capacity resource**, causing a disproportionate loss/denial to others until a "grace period" (cooldown) passes. The local Hyperbridge analog is in `pallet-bandwidth`'s FIFO subscription queue.

### Title
Unprivileged attacker can grief-evict another payer's prepaid bandwidth allowance via cheap repeated purchases into a shared FIFO capped at 1024 entries - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` stores every `(app_chain, app)`'s paid bandwidth balance as a FIFO `BoundedVec<Subscription, 1024>` keyed only by chain+app, not by payer. Any account able to call `BandwidthManager.purchase()` on any source chain (the pallet's own doc says sponsorship is deliberately open — "any deployment can sponsor any app on any chain") can push new subscriptions onto that same shared list. When the list is full, `push_subscription` unconditionally evicts index 0 (oldest) regardless of its remaining value, permanently destroying whatever bytes a legitimate payer had funded and not yet consumed.

Because tiers are configured by admins with arbitrary `(bytes, duration_secs)`, and purchases scale by `msg.months` with no minimum purchase size or per-payer isolation, an attacker can:
1. Buy the cheapest configured tier with `months = 1` repeatedly (each purchase is a separate ISMP POST from `BandwidthManager.sol`, each creating one FIFO entry).
2. Target the exact same `(app_chain, app)` pair that a legitimate, well-funded payer (e.g., an app that just bought a large multi-month tier) is using.
3. Once the list is at 1024 entries, each additional cheap purchase evicts the oldest entry — eventually reaching and evicting the victim's large, mostly-unconsumed subscription, which is silently destroyed (only a `SubscriptionEvicted` event is emitted; no refund path exists).

This mirrors the Olympus bug-class: a comparatively low-cost, permissionless action (many cheap tier-1/month-1 purchases) is used to seize and manipulate a shared, capacity-limited resource (the FIFO subscription list) in a way that destroys or denies a legitimate, costlier claim on that same resource, with no way for the victim to prevent it since the queue is keyed by app identity, not by payer.

### Impact Explanation
This is a direct loss-of-funds vector: a paying user's prepaid bandwidth allowance (real, escrowed value credited via `BandwidthManager.purchase()`) can be permanently destroyed by an unrelated, unprivileged third party at comparatively trivial cost, with the pallet offering no restitution. It also functions as a denial-of-service: an attacker can perpetually keep an app's queue saturated with cheap entries so that legitimate large purchases are evicted before ever being drained by `try_consume`, similarly to how the Olympus attacker held governance hostage by repeatedly re-occupying the single "active proposal" slot.

### Likelihood Explanation
No privileged role, relayer collusion, or malformed proof is required — only the ability to call the public `BandwidthManager.purchase()` entrypoint with the cheapest configured tier and a chosen `(chain, app)` target, which is explicitly a supported, documented pattern ("any deployment can sponsor any app on any chain"). The cost asymmetry (many cheap purchases vs. one large legitimate purchase) makes this economically attractive whenever a victim's subscription value exceeds the cumulative cost of ~1024 minimum-tier purchases.

### Recommendation
- Bind eviction/ordering to payer identity or reject sponsorship for accounts other than a designated payer/allowlist, or
- Evict by remaining value (e.g., always evict the smallest/soonest-expiring entry) rather than strict FIFO position, or
- Increase `MAX_SUBSCRIPTIONS` dynamically / charge an anti-spam cost proportional to queue pressure, or refund evicted `lost_bytes` pro-rata to the evicted subscription's original payer instead of only emitting `SubscriptionEvicted`.

### Proof of Concept
1. Admin configures `Tiers[0] = { bytes: small, duration_secs: small }` (cheapest tier) and `Tiers[N] = { bytes: large, duration_secs: large }`.
2. Victim purchases tier `N` for `(app_chain=X, app=A)` via `BandwidthManager.purchase()`, crediting a large `Subscription` at the tail of `Allowance[X][A]`.
3. Attacker (any account) repeatedly calls `BandwidthManager.purchase()` on tier `0`, `months=1`, targeting the same `(chain=X, app=A)`, 1024+ times.
4. Each purchase triggers `on_accept` → `push_subscription`; once the list length hits `MAX_SUBSCRIPTIONS`, subsequent pushes evict index 0 in insertion order.
5. Once the victim's entry reaches index 0 (or is pushed to eviction because the attacker's cheap entries fill the remaining slots ahead of drain), it is evicted and its `remaining_bytes` are lost forever, logged only as `SubscriptionEvicted { lost_bytes }` with no compensation.
