Based on my investigation, this Desktop fork is unusually well-hardened against the "attacker-controlled path" bug class: it has `resolveWithin` (`app/src/lib/path.ts`), `sanitizeCloneName` and `isClonePathSensitive` (`app/src/lib/git/clone.ts`, `app/src/lib/remote-parsing.ts`), and explicit traversal checks in the deep-link handler (`app/src/ui/dispatcher/dispatcher.ts:1957-1971`) and in the Copilot conflict-context reader (`app/src/lib/copilot-conflict-context.ts:390-407`). However, those guards are applied inconsistently — several other code paths that build a filesystem path from git-reported, attacker-influenced file names still use a bare `Path.join(repository.path, path)` with no containment check, which is the same "validation added in one call site but not its sibling" pattern described in the report.

### Title
Inconsistent path-containment validation when opening files/submodules named in commit, PR-diff, and stash data - (File: `app/src/ui/history/selected-commits.tsx`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `app/src/lib/app-shell.ts`, `app/src/ui/repository.tsx`)

### Summary
`resolveWithin` was introduced specifically to stop a path reported by an external/attacker-controlled source (a deep-link `filepath` query param, and Copilot conflict file paths) from resolving outside the repository root, and is exercised in `dispatcher.ts` and `copilot-conflict-context.ts`. [1](#0-0) [2](#0-1)  The same class of attacker-influenced string — a file path reported by git for a commit, a PR diff, or a stash — is used elsewhere via unguarded `Path.join(repository.path, path)` calls before being handed to `openFile`, `revealInFileManager`, or `openOrAddRepository`, with no equivalent `resolveWithin`/containment check: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

### Finding Description
`revealInFileManager` and the various `onOpenItem`/`onOpenFile` handlers accept a `path` that ultimately originates from git-reported file names for a commit, PR diff, or working directory status entry (`CommittedFileChange.path`, `WorkingDirectoryFileChange.path`). None of these call sites normalize the joined path back against the repository root the way `resolveWithin` does elsewhere in the same codebase, so if that path string contains traversal segments it is passed straight to `shell.showItemInFolder`, `shell.openPath` (via `openFile`), the external editor launcher, or — in the submodule case — `dispatcher.openOrAddRepository(fullPath)`, which offers to add an arbitrary filesystem path as a tracked repository. [8](#0-7) [9](#0-8) 

### Impact Explanation
If a git tree/diff entry name can be made to contain a traversal-style component, the corrupted value is the joined filesystem path (`Path.join(repository.path, path)`), and the resulting operations (`shell.showItemInFolder`, `openPath`, `openInExternalEditor`, `openOrAddRepository`) act on a location outside the repository the user opened — a read/reveal outside the repo, or (via `openOrAddRepository`) tricking the victim into adding an unrelated directory as a Desktop-tracked repository. This is the same "trusted-without-validation" pattern as the Solana report: one code path (deep links, Copilot conflicts) received a containment fix, but the functionally identical file-open/reveal/submodule-open paths did not.

### Likelihood Explanation
This is a partial finding, not a fully proven exploit chain. I could not confirm from local code alone whether the underlying git object model/`dugite` layer that produces `file.path` for commits/diffs/PRs would actually surface a traversal-style component (`..`) rather than being rejected upstream by git's own `fsck`/`receive.fsck` protections on fetch/clone. Because of index size limits I also could not fully trace every intermediate producer of `file.path` for PR-diff data to rule out sanitization elsewhere. The concrete, verifiable fact is the inconsistency in the code itself: some sinks are hardened with `resolveWithin`, structurally identical sinks are not.

### Recommendation
Route every place that turns a git-reported file/submodule path plus `repository.path` into a filesystem path (`selected-commits.tsx`, `sidebar.tsx`, `pull-request-files-changed.tsx`, `binary-file.tsx`, `app-shell.ts#revealInFileManager`, `repository.tsx#onOpenSubmodule`) through the same `resolveWithin` containment check already used in `dispatcher.ts` and `copilot-conflict-context.ts`, and refuse to open/reveal/add-as-repository when the resolved path escapes `repository.path`.

### Proof of Concept
Not independently reproduced — reproducing it would require confirming that a crafted repository/PR branch can cause git to report a `file.path` containing a traversal segment through Desktop's normal commit/diff/PR listing flow (rather than being filtered by git's fsck), which I was unable to verify with the tools available in this session. I recommend a background Devin session with full repository/terminal access to attempt constructing such a tree object and tracing it end-to-end through `git diff`/`git status`/PR-file APIs into `CommittedFileChange.path` to confirm or rule out exploitability before treating this as a confirmed vulnerability.
