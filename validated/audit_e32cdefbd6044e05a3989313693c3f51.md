### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` account keys allows stack-overflow denial of service - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively re-decodes each embedded role key via `rlp.DecodeBytes(b, &serializer)` into a fresh `AccountKeySerializer`, which itself can be another `AccountKeyRoleBased`, before any "nested composite type not allowed" validation is ever performed. This mirrors the Vapor `URLEncodedFormDecoder` issue: attacker-controlled, unbounded recursive decoding of nested structures leads to uncontrolled stack growth and a crash (denial of service), reachable from a single submitted `TxTypeAccountUpdate`/`TxTypeAccountCreation`/`TxTypeAccountUpdateWithFeeDelegation*` transaction sent by any unprivileged transaction sender (e.g. via `eth_sendRawTransaction` or the p2p tx pool ingestion path).

### Finding Description
`AccountKeySerializer.DecodeRLP` decodes the key type, instantiates the corresponding `AccountKey` via `NewAccountKey`, and then calls `s.Decode(serializer.key)`: [1](#0-0) 

When the resolved type is `AccountKeyTypeRoleBased`, this dispatches to `AccountKeyRoleBased.DecodeRLP`, which first decodes a `[][]byte` list, then **for every element `b` of that list, calls `rlp.DecodeBytes(b, &serializer)` using a brand-new `AccountKeySerializer`**: [2](#0-1) 

Because each element `b` is itself an arbitrary RLP-encoded `AccountKeySerializer` blob, an attacker can set its `keyType` to `AccountKeyTypeRoleBased` again, causing `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → … to recurse to an attacker-chosen depth. This recursion occurs purely as a byproduct of decoding the raw transaction bytes; there is no depth limit enforced anywhere in this call chain or in the underlying `rlp` package decode path.

The only defense against composite-type nesting, `CheckInstallable`/`CheckUpdatable`, only inspects **one level** of nesting (`(*a)[i].IsCompositeType()`), and — critically — it runs only **after** decoding has already fully materialized the (attacker-controlled-depth) recursive structure: [3](#0-2) 

This is confirmed by the project's own regression test, which shows the nested-key rejection (`kerrors.ErrNestedCompositeType`) only happens at `txpool.AddRemote` / block-apply validation time — i.e., strictly after the transaction (and its nested `AccountKeyRoleBased` payload) has already been fully RLP-decoded: [4](#0-3) 

Since RLP encoding of nested structures is compact (only a few bytes of overhead per nesting level), an attacker can pack a very large number of nesting levels within an ordinary transaction/tx-pool size limit, each level driving several additional Go stack frames through `rlp.DecodeBytes` → `Stream.Decode` → reflection-based decoder → `Decoder.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` (recursion). This is directly analogous to the reported Vapor `URLEncodedFormDecoder` bug class: unbounded, attacker-controlled stack growth during decoding of untrusted input, leading to a stack overflow/process crash.

### Impact Explanation
A crafted `TxTypeAccountUpdate` (or `TxTypeAccountCreation`, or their fee-delegated variants) with a sufficiently deeply nested `AccountKeyRoleBased` key blob can crash any node that attempts to decode it — this includes nodes receiving the transaction over public RPC (`eth_sendRawTransaction`), the tx pool during gossip propagation, and validators/block-builders decoding it from a block or the pool. A crash of block-producing/consensus nodes constitutes a denial-of-service against network liveness, which meets the "High" severity bar of the source advisory (CWE-674 uncontrolled recursion / stack overflow).

### Likelihood Explanation
The attack requires only a single self-crafted transaction that can be RLP-encoded and submitted like any ordinary transaction by an unprivileged sender — no special privileges, validator status, or state pre-conditions are required. The complexity is limited to constructing nested byte-blobs, which is straightforward given `AccountKeyRoleBased.EncodeRLP`/`DecodeRLP`'s structure is public.

### Recommendation
Enforce a maximum recursion/nesting depth check inside `AccountKeyRoleBased.DecodeRLP` (or centrally in `AccountKeySerializer.DecodeRLP`) before recursively decoding nested account keys, rejecting any key whose declared type is `AccountKeyTypeRoleBased` when already inside a role-based decode context (i.e., disallow nested composite types at decode time, not only at `CheckInstallable`/`CheckUpdatable` time). Additionally, consider adding a general depth/size guard in the `rlp` package's stream decoding to bound worst-case recursion for any recursively-defined RLP `Decoder` implementation.

### Proof of Concept
Construct nested `AccountKeySerializer` blobs recursively (conceptually):
```
innermost = RLP(AccountKeyTypeLegacy-key-bytes)  // any valid leaf key
level_N   = RLP([ AccountKeyTypeRoleBased, RLP([ level_(N-1) ]) ])
...
level_1   = RLP([ AccountKeyTypeRoleBased, RLP([ innermost ]) ])
```
Embed `level_N` (with N chosen large enough, e.g. tens/hundreds of thousands of levels, still fitting within ordinary transaction size limits due to compact RLP overhead per level) as the `KeyData`/`Key` field of a `TxTypeAccountUpdate` transaction, per the encoding used in `TxInternalDataAccountUpdate.toSerializable`/`fromSerializable`: [5](#0-4) 
Sign it and submit via `eth_sendRawTransaction` (or directly to `txpool.AddRemote`). Decoding the transaction (`rlp.DecodeBytes` on the raw tx) will recurse through `AccountKeyRoleBased.DecodeRLP` N times before `ErrNestedCompositeType` validation is ever reached, exhausting the goroutine stack and crashing the process.

Note: I was not able to execute this PoC or measure the exact depth required to trigger a crash on Go's default goroutine stack limits within the ask-only tooling available; this would need to be verified empirically in a Devin session with code execution access.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (t *TxInternalDataAccountUpdate) toSerializable() *txInternalDataAccountUpdateSerializable {
	serializer := accountkey.NewAccountKeySerializerWithAccountKey(t.Key)
	keyEnc, _ := rlp.EncodeToBytes(serializer)

	return &txInternalDataAccountUpdateSerializable{
		t.AccountNonce,
		t.Price,
		t.GasLimit,
		t.From,
		keyEnc,
		t.TxSignatures,
	}
}

func (t *TxInternalDataAccountUpdate) fromSerializable(serialized *txInternalDataAccountUpdateSerializable) error {
	t.AccountNonce = serialized.AccountNonce
	t.Price = serialized.Price
	t.GasLimit = serialized.GasLimit
	t.From = serialized.From
	t.TxSignatures = serialized.TxSignatures

	serializer := accountkey.NewAccountKeySerializer()
	if err := rlp.DecodeBytes(serialized.Key, serializer); err != nil {
		return err
	}
	t.Key = serializer.GetKey()

	return nil
}
