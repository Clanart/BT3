### Title
Unbounded token-array loop in escrow settlement (`_withdraw`) can permanently lock cross-chain escrowed funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`_withdraw()` in `IntentsBase.sol` iterates over `body.tokens`, a list whose length is fully attacker-controlled at `placeOrder()` time via `order.inputs` / `order.output.assets`, with no cap found anywhere in `IntentsBase.sol`, `IntrinsicIntents.sol`, or `ExtrinsicIntents.sol`. This mirrors the SmartSession `onUninstall()` bug class: a storage-cleanup/settlement loop whose gas cost scales with a value the caller chooses, with no upper bound, executed from a path that must succeed to release escrow.

### Finding Description
`_withdraw` walks `body.tokens.length` performing a `safeTransfer`/native `.call` per entry: [1](#0-0) 

This function is invoked from the cross-chain settlement callback `onAccept` → `RedeemEscrow`/`RefundEscrow` handling, which is triggered permissionlessly once a relayer delivers a valid ISMP proof — a path that cannot be aborted by the caller and must complete atomically to release funds. The token list length is sourced directly from `order.inputs`/`order.output.assets`, which are provided unchecked by the user at `placeOrder()`. I did not find any `MAX_ASSETS`/length-cap validation in `IntentsBase.sol`, `IntrinsicIntents.sol`, or `ExtrinsicIntents.sol` bounding `order.inputs.length` or `order.output.assets.length`.

Because a user constructs and signs the `Order` themselves before escrowing funds, they can supply an order with an enormous `inputs` array (or output `assets` array), each entry requiring its own external token-transfer call in `_withdraw`. Once escrowed on the source chain, the only path to move funds out of escrow is through `_withdraw`, invoked either by the local fill/cancel flow (`IntrinsicIntents`) or the cross-chain settlement message handler (`ExtrinsicIntents`/`onAccept`). If the array is large enough that the required gas for `_withdraw` exceeds the block gas limit, the escrow release transaction can never fit in a block — regardless of how much gas the relayer/caller is willing to provide.

### Impact Explanation
Any order with a sufficiently long `inputs` (or `output.assets`) array becomes permanently unwithdrawable: the escrowed tokens are locked in the `IntentGatewayV2` contract with no way to trigger a successful `_withdraw` call, since the loop's gas requirement exceeds the block gas limit. This is a direct loss/permanent lock of user funds reachable by an ordinary, unprivileged user simply by crafting a pathological order at `placeOrder()` time — no malicious relayer, prover, or admin is required. Unlike the original `onUninstall()` finding (a module-owner DoS), here the victim can be the order's own creator (self-inflicted lock, low severity) or, more concerning, an order can be crafted so that the destination-side settlement (`RedeemEscrow`) becomes unexecutable, freezing the solver's expected reward while the user's input side still executed — a cross-chain fund-lock rather than mere inconvenience.

### Likelihood Explanation
Reaching a gas-exceeding array size requires a large but not implausible number of entries (each loop iteration performs an `SLOAD`, a token external call, and an `SSTORE`); with EVM block gas limits around 30M gas and typical ERC-20 transfer costs, a few hundred to low-thousands of distinct token entries in the order would suffice to exceed the block limit. This is entirely reachable by an EOA calling `placeOrder()` — no special privileges needed. It's not clear from the excerpts reviewed whether `placeOrder()` performs any other implicit bound (e.g. gas-limited pre-validation) that would revert before escrow; this should be verified against the full `placeOrder()` implementation, which I could not fully inspect within the tool budget.

### Recommendation
Add an explicit maximum length check on `order.inputs.length` and `order.output.assets.length` in `placeOrder()`/order validation (mirroring the `onInstall` cap suggested in the reference report), sized so that the worst-case `_withdraw` loop provably fits well within the block gas limit with margin for other transaction overhead (proof verification, dispatch, etc.).

### Proof of Concept
1. Attacker calls `placeOrder()` with an `Order` whose `inputs` array contains N distinct token addresses (or the `output.assets` array contains N distinct output tokens), where N is large enough that iterating `_withdraw`'s loop (one `SLOAD` + external transfer + `SSTORE` per entry) exceeds the destination chain's block gas limit.
2. The order is escrowed successfully (escrow deposit loops, if any, may be equally unbounded but are a separate concern).
3. When settlement is triggered — either same-chain fill/cancel (`IntrinsicIntents._withdraw`) or cross-chain `onAccept` handling of `RedeemEscrow`/`RefundEscrow` (`ExtrinsicIntents`/`IntentsBase._withdraw`) — the required gas for the `_withdraw` call exceeds the block gas limit.
4. No relayer or user can ever provide enough gas to include the transaction in a block; the escrowed tokens remain locked in the `IntentGatewayV2` contract indefinitely. [1](#0-0)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
