### Title
PedPoP accepts identity / known-discrete-log ECDH encryption keys, forcing the per-message "shared secret" to a publicly computable constant - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG encrypts each secret share with a ChaCha20 key derived from an ECDH between an ephemeral scalar and the recipient's registered encryption key (`enc_key`). The `enc_key` is read with `C::read_G` (`Ciphersuite::read_G`), which validates canonicity but does **not** reject the identity point, and no proof of possession/knowledge is ever demanded for `enc_key`. A participant can therefore register `enc_key = identity` (or any point whose discrete log is public, e.g. `generator`). The resulting ECDH shared secret is `identity * k = identity` — a fixed, publicly known value — so the ChaCha20 key `H(context || identity_bytes)` is derivable by anyone. Every share encrypted "to" that participant is decryptable by any observer of the authenticated channel.

### Finding Description
- `EncryptionKeyMessage::read` calls `C::read_G(reader)` for `enc_key` with no identity rejection and no accompanying PoK (crypto/dkg/pedpop/src/encryption.rs:57-59).
- `Ciphersuite::read_G` only checks canonical encoding (crypto/ciphersuite/src/lib.rs:91-100). Note FROST's `Curve::read_G` *does* reject identity (crypto/frost/src/curve/mod.rs:125-131), but PedPoP uses the weaker ciphersuite-level reader.
- The per-participant Schnorr PoK in `verify_r1` binds only `commitments[0]` — the first Pedersen commitment — never `enc_key` (crypto/dkg/pedpop/src/lib.rs:323-329).
- `encrypt` computes `ecdh(&key, to) = to * key`; with `to = identity`, the shared secret is unconditionally `identity` (encryption.rs:95-97, 153-154).
- `cipher` derives the ChaCha20 key by transcripting `context` and `ecdh.to_bytes()` (encryption.rs:101-118). For a forced-identity ECDH, this key is a deterministic public constant — exactly the "derived key is a fixed/zero value instead of an unpredictable value" bug class of CVE-2024-9355.
- On decrypt, the attacker-side check `self.enc_key * msg.key` cannot equal `identity` for honest `msg.key` (they hold no scalar for identity), but that only affects the malicious slot; the *confidentiality* of the ciphertext is what is destroyed, and the blame protocol still resolves correctly against the accuser.

### Impact Explanation
PedPoP's encryption exists precisely because the shares travel over an *authenticated but not confidential* channel (in Serai's coordinator, DKG shares are posted to the public Tributary chain). A participant registering a known-discrete-log `enc_key` (identity or `generator`) causes all honest participants to publish shares for that index encrypted under a world-computable key. The share `f_i(malicious_idx)` of every participant's polynomial becomes public, meaning that participant slot contributes zero secrecy — an attacker who compromises `t-1` *other* key-holding slots effectively reaches threshold with `t-1` compromises, or in a 1-of-n equivalent view the threshold is silently reduced by one. This is key-share confidentiality loss reachable entirely via crafted public DKG messages.

### Likelihood Explanation
Requires only that the attacker is a DKG participant (or can inject an `EncryptionKeyMessage` for a slot in protocols where registration is permissionless relative to the attacker). No collusion assumption is needed for the confidentiality break itself — the shares are decrypted by *any* third party with the transcript context, which is derivable from public parameters. The failure is silent: honest senders cannot detect the attack since all PoKs still verify.

### Recommendation
Reject identity and non-prime-subgroup points when reading `enc_key` in `EncryptionKeyMessage::read` (use the identity-rejecting reader pattern from `Curve::read_G`), and require a Schnorr PoK over `enc_key` bound to `context` and `participant` in `Commitments`/round-1 verification, so that a registered encryption key is guaranteed to have a discrete log known only to its owner.

// valid Commitments (with valid PoK for commitments[0]) followed by
