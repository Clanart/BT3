### Title
Stale-token escrow: `TRANSACTION_FEES` amount is redeemed using the *current* `feeToken` instead of the token actually escrowed at `placeOrder` time - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2.placeOrder` escrows `order.fees` by pulling the token returned by `IDispatcher(hostAddr).feeToken()` **at placement time** [1](#0-0) , but records only a bare `uint256` amount under the sentinel key `TRANSACTION_FEES` in the `_orders` mapping — the token's identity is never stored [2](#0-1) . When the escrow is later released in `_withdraw`, the contract re-reads `IDispatcher(host()).feeToken()` **at withdrawal time** and pays that amount of *whatever token is currently configured* to the beneficiary [3](#0-2) . If the host's `feeToken` is updated by governance between order placement and order fulfillment/cancellation, the escrow accounting silently desyncs from the token that was actually collected.

### Finding Description
This is a direct structural analog of the reported bug class: a mapping/record used to gate a financial settlement (`isTokenSupport` in SecondSwap, `TRANSACTION_FEES` here) has no mechanism to bind or invalidate the specific asset it refers to once the "supported"/"current" pointer changes elsewhere in the system.

- At `placeOrder`, `feeToken = IDispatcher(hostAddr).feeToken()` is read and the caller's tokens of that type are pulled into escrow [4](#0-3) . Only the numeric `order.fees` value is persisted; the token address used for the transfer is discarded.
- `EvmHost.updateHostParamsInternal` allows `feeToken` to be changed via cross-chain governance, gated only by the *host's own* zero-balance check (`if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) { revert if host balance != 0 }`) [5](#0-4) . This check only inspects the **EvmHost** contract's balance — it has no visibility into balances escrowed inside `IntentGatewayV2`, so a `feeToken` change can proceed while `IntentGatewayV2` is still holding old-feeToken fee escrows for in-flight orders.
- At settlement (`_withdraw`, invoked from both `fillOrder`/`ExtrinsicIntents` redemption paths and cancellation paths), the contract reads `feeToken()` again and transfers `fees` units of it to the beneficiary [3](#0-2) , with **no comparison** to the token that was actually collected at placement.

Existing guards do not stop this path because: (1) `EvmHost`'s `CannotChangeFeeToken` check is scoped to the host's own balance, not any downstream app's escrow, so it provides no protection for `IntentGatewayV2`; (2) `IntentGatewayV2`/`IntentsBase` never records which token an order's `TRANSACTION_FEES` entry corresponds to, so there is no way at redemption time to detect or reject a mismatch.

### Impact Explanation
This falls squarely under "unauthorized transaction or execution", "transaction manipulation", and "stealing or loss of funds" from the bounty scope, because a legitimate governance action (changing the fee token — a normal, expected protocol operation, not an attack) silently corrupts settlement for any order placed before the change and settled after it:
- If `IntentGatewayV2` holds no balance of the new `feeToken`, the `safeTransfer` reverts, permanently blocking `_withdraw`/finalization for that order (locking the user's/solver's principal escrow alongside it, since `_withdraw` finalizes both token transfer and fee transfer in one call).
- If `IntentGatewayV2` happens to hold balance of the new `feeToken` (e.g., from other users' concurrently placed orders, protocol dust, or partially filled orders), that balance is paid out to an unrelated order's beneficiary — i.e., other users'/solvers' escrowed funds are misappropriated to pay a stale fee obligation denominated in a different token, a genuine wrong-beneficiary/wrong-asset fund movement.

### Likelihood Explanation
`feeToken` changes are a supported, documented governance operation on `EvmHost` (`updateHostParams`) [6](#0-5) , and cross-chain intent orders routinely stay open across the deadline window (until filled/cancelled). No malicious actor, relayer, or prover is required — any governance-approved fee-token migration performed while any order is outstanding triggers this automatically for all such orders.

### Recommendation
Store the fee token address alongside the fee amount when escrowing (e.g., a `(token, amount)` pair keyed by commitment, or a dedicated `_orderFeeToken[commitment]` mapping) at `placeOrder` time, and use that recorded token — not the live `feeToken()` — when releasing fees in `_withdraw`. Additionally, extend the `EvmHost.updateHostParamsInternal` `CannotChangeFeeToken` safety check (or add an equivalent check in `IntentGatewayV2`) to prevent/flag `feeToken` migrations while `IntentGatewayV2` (and any other app escrowing the fee token) still holds outstanding balances tied to unsettled orders.

### Proof of Concept
1. User calls `placeOrder` with `order.fees = 100` while `IDispatcher(host).feeToken() == TokenA`. `IntentGatewayV2` pulls 100 `TokenA` from the user and sets `_orders[commitment][TRANSACTION_FEES] = 100` [4](#0-3) .
2. Before the order is filled, governance calls `updateHostParams` changing `feeToken` from `TokenA` to `TokenB` (allowed since `EvmHost`'s balance of `TokenA` may be zero — that check does not consider `IntentGatewayV2`'s balance) [5](#0-4) .
3. A solver fills the order; `_execute`/`_withdraw` finalizes and executes: `IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees)`, which now resolves to `TokenB`, transferring 100 units of `TokenB` (not the escrowed `TokenA`) to the beneficiary [3](#0-2) .
4. Either the call reverts (if `IntentGatewayV2` holds no `TokenB`, DoS-locking the whole withdrawal including principal escrow), or it succeeds by draining `TokenB` balance belonging to other orders/users, paying the wrong asset to the wrong economic value to this order's beneficiary.
