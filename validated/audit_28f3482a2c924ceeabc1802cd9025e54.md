### Title
Instant reward capture via front-run lock() before queueNewRewards() lets an attacker skim rewards proportional to instantaneous balance instead of time-weighted contribution - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`queueNewRewards` updates `rewardPerTokenStored` as a one-shot lump-sum distribution using `totalStaked()` sampled only at call time, with no rate-based vesting (unlike a standard Synthetix `rewardRate`-over-`rewardsDuration` model). An attacker who front-runs a pending `queueNewRewards` call with `VLMGP.lock(largeAmount)` becomes part of the `totalStaked()` denominator the instant the reward lands, then calls `getReward()` immediately afterward to claim a full, unpenalized proportional share, before ever calling `startUnlock`.

### Finding Description
`queueNewRewards` (and `_queueNewRewardsWithoutTransfer`) computes:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 1e18) / totalStaked();
``` [1](#0-0) 
`totalStaked()` returns `vlMGP.totalSupply()`, the instantaneous sum of all locked + cooldown MGP [2](#0-1) . There is no time-weighting: a balance that existed for one block counts identically to a balance held for months when a lump-sum reward lands.

Attack flow:
1. Attacker observes a pending `queueNewRewards()` tx in the mempool and front-runs it with `VLMGP.lock(largeAmount)`. `_lock` transfers MGP in and calls `MasterMagpie.depositVlMGPFor`, which increases `totalAmount` (and thus `totalStaked()`) before the reward lands [3](#0-2) .
2. `queueNewRewards` executes, inflating `rewardPerTokenStored` using the now-larger `totalStaked()` that includes the attacker's fresh deposit.
3. Attacker calls `getReward()`, which runs `updateReward` → `_updateFor`, computing `earned = balanceOf(account) * (rewardPerToken - paid) / 1e18` [4](#0-3) . Since the attacker's `userRewardPerTokenPaid` was only set at lock time (before the reward index jumped), they are credited a full, instantaneous share of the newly queued reward.
4. Critically, `_sendReward` applies an early-exit forfeit via `_calExpireForfeit`, but this is based on `vlMGP.getRewardablePercentWAD(_account)`, which is 100% ("fully locked") at this point because the attacker has not yet called `startUnlock` [5](#0-4) [6](#0-5) . So the reward is paid out with zero penalty.
5. Only after collecting the reward does the attacker call `startUnlock(largeAmount)` to begin exiting; this only starts a cooldown timer and does not claw back the reward already paid in step 3-4 [7](#0-6) .

Existing protections do not stop this: `onlyManager` restricts who can call `queueNewRewards`, but not when a large observable reward lands relative to lock timing; `nonReentrant`/`whenNotPaused` are irrelevant here; the forfeit mechanism (`_calExpireForfeit`) is checked at claim time against current lock state, not against how long the balance existed prior to the reward being queued, so it does not prevent a same-block/near-instant lock-then-claim.

### Impact Explanation
This is a theft of unclaimed yield: long-term lockers' expected share of a newly queued reward is diluted because the attacker's freshly-locked balance is added to `totalStaked()` and used to compute `rewardPerTokenStored`, and the attacker walks away with a proportional cut of the reward that was never economically earned by time-weighted participation. This matches "theft of unclaimed yield from long-term lockers."

### Likelihood Explanation
Feasibility depends on: (a) the attacker being able to observe a pending `queueNewRewards` transaction in the mempool (feasible on public chains without private mempools), and (b) having enough MGP capital to lock a meaningfully large amount relative to `totalStaked()` to capture a non-trivial share, and (c) the attacker being willing to have that capital locked and go through `coolDownInSecs` before it can be withdrawn (extraction of yield happens immediately regardless of that lockup). This is repeatable for every future `queueNewRewards` call the attacker can observe in advance, so it is a systemic, recurring MEV-style extraction rather than a one-off exploit.

### Recommendation
Replace the lump-sum, instant-index-update reward model with a time-weighted / streamed distribution (e.g., Synthetix-style `rewardRate` accrued linearly over a `rewardsDuration`), or require a minimum lock duration/cliff before a balance becomes eligible for a given reward epoch's rewardPerToken increase, so newly-added stake cannot immediately participate in rewards that were queued based on contributions accrued before it joined.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder`, and a mock reward ERC20; set up a `rewardManager`.
2. Have "long-term locker" B call `lock(1000e18)` and let time pass.
3. Simulate attacker A observing a pending `queueNewRewards(1000e18 rewardToken)` call: A calls `lock(9000e18)` in the block immediately before.
4. Manager calls `queueNewRewards(1000e18, rewardToken)`.
5. A immediately calls `getReward()` and records `toSend` from the `RewardPaid` event/return value; assert A receives ~90% of the reward (9000/10000 share) despite holding the position for 0 elapsed time versus B's long holding period.
6. A then calls `startUnlock(9000e18)`.
7. Assert: A's captured reward share (≈9000/10000 * 1000e18) vastly exceeds any time-weighted fair share (which should be ≈0, since A contributed 0 time-weighted stake before the reward accrued), while B's actual share is diluted from what it would have been absent A's front-run (B would have received the full 1000e18 had A not intervened, but now only gets ~100e18).

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
