### Title
Missing minting/overflow guard before fee computation in mempool spend-bundle validation causes unhandled exception - (File: chia/full_node/mempool_manager.py)

### Summary
`MempoolManager.validate_spend_bundle()` computes the transaction fee by subtracting the sum of created-coin amounts (`addition_amount`) from the sum of spent-coin amounts (`removal_amount`) and casting the result directly to `uint64`, with no prior check that `removal_amount >= addition_amount`. This mirrors the reported bug class: an unchecked subtraction between two attacker-influenced values (`protocolFee - createFeeDiscount` in the original report vs. `removal_amount - addition_amount` here) that can underflow and abort execution instead of failing gracefully.

### Finding Description
In `validate_spend_bundle`, the removal/addition totals are accumulated purely from the submitted spend bundle's own coin spends and CLVM-derived `CREATE_COIN` conditions: [1](#0-0) [2](#0-1) 

The fee is then computed as `fees = uint64(removal_amount - addition_amount)` with no preceding check that `removal_amount >= addition_amount` (i.e., no equivalent of consensus's `MINTING_COIN` guard).

By contrast, the consensus-level block body validator explicitly performs this check before computing fees: [3](#0-2) 

Because CLVM execution does not itself prevent a spend bundle from creating coins whose total value exceeds the value of the coins being spent (that is precisely what `MINTING_COIN` is meant to catch at the consensus layer), a submitter can craft a spend bundle whose `addition_amount` exceeds `removal_amount`. When such a bundle reaches `validate_spend_bundle`, `removal_amount - addition_amount` is negative, and casting a negative Python int to `uint64` raises an exception rather than returning a controlled `Err`.

### Impact Explanation
An attacker-submitted spend bundle can trigger an unhandled exception deep in the mempool admission path instead of a clean rejection (e.g., `Err.MINTING_COIN`). This is a spend-bundle-triggered transaction-processing fault: rather than being cleanly rejected with `MempoolInclusionStatus.FAILED`, the validation call raises, which can surface as an unexpected exception in the caller chain (`add_spend_bundle` → RPC/protocol handler processing `respond_transaction`), representing a processing-halt/DoS-class defect analogous to the reported `amountWithFee()` revert causing `initiateBatchAuction` to fail. This is the same bug class as the report: a subtraction of two values without an ordering check, causing the surrounding function to fail instead of behaving predictably.

### Likelihood Explanation
Any unprivileged spend-bundle submitter can construct such a bundle themselves (spend a small coin, create a larger coin via `CREATE_COIN`); no privileged access or coordination with other peers is required, making this trivially and repeatably reachable by any mempool participant.

### Recommendation
Add an explicit guard mirroring the consensus-level check before computing fees in `validate_spend_bundle`:
```python
if removal_amount < addition_amount:
    return Err.MINTING_COIN, None, []
fees = uint64(removal_amount - addition_amount)
```
This converts the unhandled exception into the same clean, expected `Err` path already used at the consensus layer.

### Proof of Concept
1. Construct a `SpendBundle` spending a coin of amount `1` mojo.
2. In its solution, emit a `CREATE_COIN` condition creating a new coin with amount `2` (or any amount greater than the coin's own value); the CLVM engine will happily execute and report this in `SpendBundleConditions` since minting-limit enforcement is not part of clvm execution itself.
3. Submit this bundle to the node (e.g., via `respond_transaction`/`push_tx`).
4. `validate_spend_bundle` computes `addition_amount (2) > removal_amount (1)`, hits `fees = uint64(removal_amount - addition_amount)` with a negative operand, and raises instead of returning `Err.MINTING_COIN` cleanly — reproducible directly by reading the code path referenced above.
