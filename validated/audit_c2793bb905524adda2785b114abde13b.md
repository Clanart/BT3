The report describes a case where a value used to route/attribute a signed request (`offset`) is not itself covered by the signature, letting an attacker manipulate that value while keeping a valid signature. The closest analog in `shopify_app` is in webhook verification, where the HMAC is computed only over the raw body, while the shop identity (`X-Shopify-Shop-Domain` header) used to route processing is not covered by that signature at all.

### Title
Webhook HMAC verification does not bind the shop domain header, enabling cross-shop webhook forgery - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates a webhook solely by checking `hmac_valid?(request.raw_post)`, which HMACs the raw body against the app's shared secret. It never binds the `X-Shopify-Shop-Domain` header (exposed via the `shop_domain` helper) into that signature. [1](#0-0) [2](#0-1) 

### Finding Description
`hmac_valid?` computes `OpenSSL::HMAC.digest(sha256, secret, data)` over `request.raw_post` only, then compares it against the `HTTP_X_SHOPIFY_HMAC_SHA256` header using `secure_compare`. [3](#0-2) 
The `shop_domain` value used by apps to attribute the webhook to a specific shop is read straight from the `X-Shopify-Shop-Domain` header, which is completely outside the HMAC computation: [4](#0-3) 
This is documented as the intended integration pattern for custom webhook controllers, where `shop_domain` (from the unverified header) is passed directly into background jobs: [5](#0-4) 

Because the webhook secret is the app's shared client secret (identical for every installed shop), any merchant who has installed the app can capture a legitimate, validly-signed webhook delivered to their own shop and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim shop's domain. `hmac_valid?` will still pass because it only checks the body digest, not the header, so `verify_request` accepts the forged request and the app processes/queues a job attributing the (attacker-supplied) body/content to the victim shop. This is structurally identical to the reported bug class: a value (`offset` in the report, `shop_domain` here) that influences what data is retrieved/attributed is not included in the signed message, allowing an attacker to manipulate it while reusing a validly-signed payload.

### Impact Explanation
An app relying on the documented `shop_domain` helper (or the built-in `WebhooksController`/`ShopifyAPI::Webhooks::Registry` shop resolution) to route webhook data into per-shop storage or jobs can have data misattributed cross-shop: a malicious merchant can inject their own webhook content (e.g., order/customer/product data they control) under a victim shop's identity, potentially corrupting victim data, triggering victim-shop side effects, or bypassing per-shop authorization checks that trust `shop_domain` as verified.

### Likelihood Explanation
Exploitation requires only that the attacker (1) be a real, unrelated merchant who has installed the app (any merchant can self-register/install), (2) capture one legitimate webhook payload+signature sent to their own store (trivial — they control their own endpoint/network), and (3) replay it to the app's public webhook endpoint with a modified shop-domain header. No secret material or privileged access is required beyond normal app installation, so likelihood is moderate-to-high for apps that trust `shop_domain` from `WebhookVerification` for cross-shop-sensitive logic.

### Recommendation
Do not treat `X-Shopify-Shop-Domain` as authenticated data derived solely from `hmac_valid?`. Either:
1. Cross-check the shop domain against a shop that is actually registered/installed and has an active session/webhook subscription matching the payload's own shop reference (e.g., verify against `SessionRepository` before trusting `shop_domain`), or
2. Incorporate the shop domain (and other routing-critical headers) into the HMAC-verified data, or
3. Rely on `ShopifyAPI::Webhooks::Registry`/topic-specific handlers that independently validate the resource ownership rather than trusting the raw header value for authorization-sensitive operations.

### Proof of Concept
1. Merchant A installs the app and triggers a webhook (e.g., `orders/create`) for their own shop, capturing the raw POST body and the valid `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Merchant A replays this exact body/HMAC to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `WebhookVerification#verify_request` (or `PayloadVerification#hmac_valid?`) validates successfully because only the raw body is HMAC'd. [6](#0-5) 
4. Any custom controller/job following the documented pattern (`shop_domain: shop_domain`) processes attacker-controlled webhook data as if it belonged to `victim-shop.myshopify.com`. [5](#0-4)

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
