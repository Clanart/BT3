## Finding: Missing state validation in `authenticateWithBrowser` success path allows OAuth flow/account binding confusion

### Summary
In `authenticateWithBrowser` (`app/src/lib/stores/sign-in-store.ts:260-330`), the `.then()` success handler that calls `emitAuthenticate(account)` only checks that `this.state.kind === SignInStep.Authentication` — it never verifies that `this.state.oauthState?.state` still equals the `csrfToken` captured for *that* flow. The `.catch()` handler right below it (lines 318-329) *does* perform this exact check. This asymmetry is real and confirmed in the code. [1](#0-0) [2](#0-1) 

### Finding Description
Each call to `authenticateWithBrowser` generates a fresh `csrfToken` and stores it in `this.state.oauthState.state`, along with `resolve`/`reject` closures unique to that call's `Promise` [3](#0-2) . If `authenticateWithBrowser` is invoked a second time while the store is still in `SignInStep.Authentication` (i.e., without going through `reset()`, which would reject the prior promise via `onAuthError`), the second call overwrites `this.state.oauthState` with a new `csrfToken`, while the first call's `Promise` (with its own `resolve`) is still pending.

Separately, `resolveOAuthRequest` (lines 332-359) validates `this.state.oauthState.state === action.state` *before* the `await requestOAuthToken(...)` / `await fetchUser(...)` calls, but does **not** re-validate it after the await, right before calling `this.state.oauthState.onAuthCompleted(account)` [4](#0-3) . If a second flow (B) is started during that await window, `onAuthCompleted` still resolves flow A's original promise object, but `this.state` now reflects flow B. Because the `.then()` handler in `authenticateWithBrowser` (flow A) only checks `this.state.kind`, not the identity of `this.state.oauthState.state`, it will proceed to call `emitAuthenticate(account)` using flow A's account while `this.state` (and the UI) reflect flow B's session, then overwrite it to `SignInStep.Success`.

### Impact Explanation
This produces silent corruption of the account/OAuth-state binding: an account resolved from one OAuth exchange can be emitted and bound to the app while the sign-in UI/state believes a different flow is active. This falls into the "unauthorized OAuth or account binding" impact category in scope.

### Likelihood Explanation
Exploitability is limited by real preconditions: it requires two `authenticateWithBrowser` invocations to occur while the store remains in `SignInStep.Authentication` without an intervening `reset()` (normal UI flows like `beginDotComSignIn`/`beginEnterpriseSignIn` call `reset()` first, which rejects the pending promise instead) [5](#0-4) . It also requires the first flow's deep-link callback (`resolveOAuthRequest`) to already be past its `state` check and in-flight during the `requestOAuthToken`/`fetchUser` await when the second flow replaces `oauthState`. This is a genuine TOCTOU race in the state machine, but it is not trivially triggerable by a remote/unprivileged attacker alone — it needs a specific timing window involving two concurrent sign-in attempts, which is an unusual (though not impossible) sequence of app usage/deep-link delivery.

### Recommendation
- In the `.then()` handler of `authenticateWithBrowser`, add the same guard used in `.catch()`: verify `this.state.oauthState?.state === csrfToken` before calling `emitAuthenticate` and transitioning to `SignInStep.Success`.
- In `resolveOAuthRequest`, re-check `this.state.oauthState?.state === action.state` immediately before calling `onAuthCompleted`/`onAuthError`, after the `await requestOAuthToken` / `await fetchUser` calls complete, not only before them.

### Proof of Concept
1. Call `authenticateWithBrowser()` (flow A) — store sets `oauthState.state = tokenA`, opens browser.
2. Deep link for flow A arrives; `resolveOAuthRequest` passes the state check (`tokenA === tokenA`) and begins `await requestOAuthToken(...)`.
3. Before that await resolves, call `authenticateWithBrowser()` again (flow B) without an intervening `reset()` — `this.state.oauthState.state` becomes `tokenB`.
4. Flow A's `requestOAuthToken`/`fetchUser` await completes; `resolveOAuthRequest` calls `this.state.oauthState.onAuthCompleted(accountA)`, which is actually flow A's original `resolve`.
5. Flow A's `.then()` fires: `this.state.kind === SignInStep.Authentication` is true (it's flow B's state), so it calls `emitAuthenticate(accountA)` and transitions to `Success`, even though the active session/UI was flow B's.
