### Title
Missing zero-value validation on `Kip71GasTarget` governance parameter leads to division-by-zero panic in base fee calculation - (File: `params/kip71_config.go`)

### Summary
The `Kip71GasTarget` governance parameter is registered with a `noopFormatChecker` in `kaiax/gov/param.go`, meaning any `uint64` value—including `0`—is accepted as valid. This value is later used as a divisor in `NextMagmaBlockBaseFee`, which computes the KIP-71 dynamic base fee for every block. If `GasTarget` is set to `0` and a block's gas usage is nonzero, the function performs a division by zero on a `big.Int`, which panics in Go.

### Finding Description
`params/kip71_config.go` defines `KIP71Config.NextMagmaBlockBaseFee`, called from `VerifyMagmaHeader` (and consensus/base-fee calculation paths) for every block after Magma activation: [1](#0-0) [2](#0-1) [3](#0-2) 

`gasTarget` is taken directly from governance config with no zero check, unlike `BaseFeeDenominator`, which explicitly guards against zero a few lines above: [4](#0-3) 

Whenever `parentGasUsed != gasTarget` (the common case), the code does `x.Div(x, new(big.Int).SetUint64(gasTarget))`. If `gasTarget == 0`, this is a division by zero, which causes a runtime panic in Go's `math/big` package.

The root cause is the same class of bug flagged in the external report: governance-facing setter/parameter paths lack input validation. Here, the `Kip71GasTarget` parameter definition uses `noopFormatChecker`, unlike other KIP-71 parameters such as `Kip71BaseFeeDenominator`, which enforces `v != 0`: [5](#0-4) [6](#0-5) 

The value flows unchecked from the governance vote/param-set mechanism (`ParamSet.Set`) directly into consensus-critical base-fee computation: [7](#0-6) 

### Impact Explanation
A `GasTarget` value of `0` propagated through governance (vote or `GovParam` contract `setParamIn`) would cause every node computing `NextMagmaBlockBaseFee` for the next block with nonzero gas usage to panic, since the value is used to build `params.ChainConfig` consumed on every block header verification. This is a consensus-halting/DoS condition across the entire network (all honest nodes crash identically when processing the first block with `gasUsed != 0` after the bad parameter takes effect), which is a state-transition/consensus-availability issue rather than a benign parameter setting. This aligns with "acceptance of an invalid governance parameter causing state divergence/consensus failure" in the allowed analog categories.

### Likelihood Explanation
Reachability depends on the governance-parameter-setting path (vote via header extra data pre-Permissionless, or the governing node/`GovParam` contract post-Kore/Permissionless) accepting `0` for `Kip71GasTarget`. I was only able to confirm that the `FormatChecker` for this parameter is a `noopFormatChecker` that accepts any `uint64`, including `0`; I was not able to fully trace, within the remaining budget, every additional access-control layer between an "unprivileged" caller and successful application of this parameter (e.g., whether `GovParam.setParamIn` enforces owner-only, or whether pre-Permissionless voting from a non-governing validator can be the source of this value, as suggested by `TestVerifyVote_SingleMode` allowing non-governing-node votes pre-Permissionless). This detail should be verified further before treating it as fully unprivileged-reachable; if governance parameter changes require a privileged governance/validator role rather than any transaction sender, the practical likelihood is lower, but the underlying missing-validation bug and its severe (panic/DoS) consequence remain valid regardless of exact privilege level required.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and defensively for `Kip71MaxBlockGasUsedForBaseFee`) that rejects `0`, consistent with the existing check on `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, as defense-in-depth, guard the division in `NextMagmaBlockBaseFee` (mirroring the existing `BaseFeeDenominator == 0` fallback) so that a `0` `GasTarget` cannot cause a panic even if it slips through parameter validation.

### Proof of Concept
1. Via the governance mechanism, set `Kip71GasTarget = 0` (accepted because `kaiax/gov/param.go`'s entry for `Kip71GasTarget` uses `noopFormatChecker`, which returns `true` unconditionally: [8](#0-7) ).
2. Once this parameter takes effect at the target block, produce/process any block after Magma activation where `parentHeaderGasUsed != 0` (trivial, any transaction executed in the parent block).
3. In `NextMagmaBlockBaseFee`, `gasTarget := kc.GasTarget` is `0`; since `parentGasUsed > gasTarget` (0), execution reaches:
```go
y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // gasTarget == 0
```
`big.Int.Div` by zero panics, crashing every node that verifies or builds this block header, since `VerifyMagmaHeader`/base fee computation runs on all nodes during block validation.
