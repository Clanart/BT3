### Title
Refunded/forwarded outputs whose value cannot cover the transaction fee are permanently locked — the plan consumes the input and no retry or input-restoration path exists - ([File: processor/src/multisigs/mod.rs])

### Summary
The external report describes funds locked because releasing them depends on another party's optional action. The Serai analog: when a scanned Bitcoin output yields a `PlanFromScanning::Refund` (or `Forward`) whose only input cannot cover the median fee, `prepare_send` returns `tx: None`. The plan was already saved as active and the output was removed from the newly-received set, while a `TODO` explicitly notes inputs are never restored to the scheduler. The output is never rescheduled and never spendable again — permanently locked in the multisig.

### Finding Description
- A scanner-observed external output without a parseable `InInstruction` produces `PlanFromScanning::Refund(output, refund_to)` in `scanner_event_to_multisig_event` (`processor/src/multisigs/mod.rs:936-938`), later expanded via `refund_plan` (`processor/src/multisigs/scheduler/utxo.rs:587-605`), which builds a plan whose sole input is that output and whose sole payment equals `output.balance()` with `change: None`.
- In `plans_from_block`, these outputs are removed from the pending set because the plan lists them as inputs (`mod.rs:623-631`), and the plan is persisted via `PlanDb::save_active_plan` before sending (`mod.rs:726-732`).
- `Network::prepare_send` calls `needed_fee`; on Bitcoin, `make_signable_transaction` maps `TransactionError::NoOutputs | NotEnoughFunds` to `Ok(None)` (`processor/src/networks/bitcoin.rs:457-458`), so `needed_fee` returns `None` and `prepare_send` returns `PreparedSend { tx: None, .. }` (`processor/src/networks/mod.rs:442-455`).
- Back in `plans_from_block`, a `None` tx is silently skipped; the in-code TODO states: "If the TX is None, restore its inputs to the scheduler for efficiency's sake" (`processor/src/multisigs/mod.rs:792`). Nothing re-registers the output: the scanner already recorded it as seen (`processor/src/multisigs/scanner.rs:594-622`, `700`), so no future block re-emits it.
- The same applies to `PlanFromScanning::Forward` outputs during `RotationStep::ForwardFromExisting`: if the forwarding TX isn't created, the comment admits the plan "will be dropped as this did here, letting it die out" (`mod.rs:879-882`).

### Impact Explanation
Any received output whose value is between `N::DUST` (the scan filter at `processor/src/multisigs/scanner.rs:564`) and the prevailing spend fee is permanently locked inside the multisig UTXO set. For refunds, this is a user's deposit that should have been returned; for forwards during key rotation, it is user funds stuck in the retiring key. `DUST` only "should" exceed spend cost "by an order of magnitude" (`processor/src/networks/mod.rs:296-301`) — a soft margin, not a guarantee — so a median-fee spike converts otherwise-acceptable deposits into locked funds.

### Likelihood Explanation
Triggerable by an unprivileged party: anyone can send a Bitcoin transaction paying the multisig's external address with an amount in the `(DUST, needed_fee)` band, or make a deposit while fees are elevated. The fee is computed from the median of a single block (`median_fee` in `make_signable_transaction`, `bitcoin.rs:430-431`), so transient fee spikes suffice. No privileged access or collusion required.

### Recommendation
When `prepare_send` yields `tx: None` for a refund/forward plan, restore the plan's inputs to the scheduler (implement the `mod.rs:792` TODO) so the output is retried when fees drop, or queue it into the normal `schedule` path where it can be batched with other inputs to amortize the fee.

### Proof of Concept
1. Observe a multisig's external P2TR address (public, derived from the group key via `p2tr_script_buf`, `networks/bitcoin/src/wallet/mod.rs:80-86`).
2. Send an output of value `v` where `N::DUST <= v < needed_fee(1 in, 1 out)` with no `InInstruction`, so `instruction_from_output` yields `refund_to` (the presumed origin).
3. Scanner emits the output (`>= DUST` passes the filter); `scanner_event_to_multisig_event` pushes `PlanFromScanning::Refund`.
4. `plans_from_block` expands it via `refund_plan` (input = the output, payment = `v`, `change: None`), removes the output from `outputs`, saves the active plan.
5. `prepare_send` → `needed_fee` → `SignableTransaction::new` returns `NotEnoughFunds`/`NoOutputs` → `Ok(None)` → `tx: None`.
6. No eventuality is registered, the plan's input is never restored, and the output's ID is already marked seen — the `v` sats are locked in the multisig forever.
