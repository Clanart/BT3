### Title
Attacker-controlled participant count causes ~500,000× memory amplification in `ThresholdKeys::read` — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::<C>::read` deserializes `n` (the participant count) directly from untrusted bytes and immediately performs `Vec::with_capacity(usize::from(n))` for `Interpolation::Constant` coefficients, before any of the `n` elements have been read. A 6-byte input header (`t=1, n=65535, i=1`, interpolation byte `0`) forces an allocation of `65535 × size_of::<C::F>()` (~2 MiB for 32-byte fields) even though deserialization then fails on the first missing coefficient. The allocation is neither bounded by the remaining input length nor charged to any resource budget — the exact "unbounded object count not limited by resource accounting" shape of CVE-2022-0480 (POSIX locks not limited by memcg).

### Finding Description
In `ThresholdKeys::read`, `n` is read as a `u16` from the stream and used twice: to size the `Interpolation::Constant` coefficient vector via `Vec::with_capacity(usize::from(n))`, and to drive two loops reading `n` scalars / `n` group elements plus a `HashMap` insertion per participant. [1](#0-0) 

The loop bodies read incrementally and fail fast on EOF, so they do not amplify. The `with_capacity` does: it commits `n × 32` bytes of heap for a message whose attacker-supplied prefix is only ~7 bytes. By contrast, `Commitments::read` in `crypto/dkg/pedpop/src/lib.rs` derives its capacity from `params.t()` — locally-configured, not attacker-chosen — showing the codebase otherwise bounds deserialization by caller-supplied parameters. [2](#0-1) 

The same pattern is reachable in the wild: `GeneratedKeysDb::read_keys` loops `ThresholdKeys::read` over attacker-influenced DB byte strings, and `read` is part of the public deserialization surface listed for untrusted input.

### Impact Explanation
Availability loss via heap memory exhaustion. Each 7-byte request inflates to ~2 MiB of committed memory (and the allocation is only dropped after the read errors, so concurrent calls multiply it). ~500 parallel calls per GiB of victim memory; there is no per-caller accounting, so the amplification cost is borne entirely by the host — mirroring the kernel's unbounded POSIX lock exhaustion. On allocation failure of a large `Vec`, Rust aborts the process, turning this into a crash primitive.

### Likelihood Explanation
Reachable by any party able to deliver bytes to `ThresholdKeys::read`/`read_keys` (peer messages carrying serialized key material, DB corruption surfaces, or any integrator passing network input through). No authentication, threshold collusion, or leaked secrets are required — the amplification happens before semantic validation (`ThresholdParams::new` is only invoked after all reads succeed). Medium severity: DoS only, no confidentiality or correctness impact.

### Recommendation
- Validate `n` against `ThresholdParams` bounds (and against the caller's expected participant set) *before* allocating; parse `t`, `n`, `i` first, reject `n` exceeding the caller-known participant count.
- Replace `Vec::with_capacity(n)` with an incremental `Vec::push` loop, so memory committed never exceeds bytes actually present.
- Optionally require `n` elements to be read into bounded chunks and reject trailing garbage, matching the "extra bytes" check already applied to PedPoP commitments in `processor/src/key_gen.rs`.

### Proof of Concept
```rust
// crypto/dkg — conceptual PoC over any in-scope Ciphersuite C
let mut bytes = vec![];
bytes.extend(&(C::ID.len() as u32).to_le_bytes()); // id_len
bytes.extend(C::ID);                             // id
bytes.extend(&1u16.to_le_bytes());               // t = 1
bytes.extend(&u16::MAX.to_le_bytes());           // n = 65535 (attacker-chosen)
bytes.extend(&1u16.to_le_bytes());               // i = 1
bytes.push(0);                                   // Interpolation::Constant

// ~7 meaningful bytes -> Vec::with_capacity(65535) of C::F (~2 MiB),
// then errors on the first coefficient read. Repeat N times concurrently
// to exhaust host memory.
let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
```

Note: I could not fully verify whether integrator plumbing exposes `ThresholdKeys::read` on unauthenticated network bytes versus only on trusted storage (`GeneratedKeysDb` reads from a local DB); the amplification itself is confirmed in `crypto/dkg/src/lib.rs:591–623`, but the external reachability depends on deployment plumbing outside the indexed scope.
