### Title
Unbounded recursion in `AccountKeyRoleBased` RLP decoding causes unrecoverable Go stack-overflow crash via a single attacker-submitted transaction - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each element of a role-based account key as a new `AccountKeySerializer`, and `AccountKeySerializer.DecodeRLP` in turn instantiates whatever `AccountKeyType` the attacker specifies (including `AccountKeyTypeRoleBased` again) and recurses into `AccountKeyRoleBased.DecodeRLP`. There is no depth limit on this mutual recursion, and it executes *before* any semantic validation (`CheckInstallable`/`CheckUpdatable`/`checkAccountKeyZeroValues`) that rejects nested composite keys ever runs.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of byte blobs and, for each blob, decodes a fresh `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type tag from attacker-controlled bytes, constructs the corresponding `AccountKey` via `NewAccountKey`, and decodes into it — if the type tag is again `AccountKeyTypeRoleBased`, this re-enters `AccountKeyRoleBased.DecodeRLP`: [2](#0-1) 

This mirrors the mistune bug class exactly: recursive parsing driven by attacker-supplied nested structure, with no cycle/depth guard, until the runtime's recursion limit is hit. The semantic guard that Kaia does have — `AccountKeyRoleBased.CheckInstallable` rejecting composite sub-keys via `kerrors.ErrNestedCompositeType`: [3](#0-2) 
and the JSON-path guard `checkAccountKeyZeroValues` that also rejects nested `RoleBased` keys: [4](#0-3) 
— only run *after* the object has already been fully decoded. They cannot prevent the crash that happens during decoding itself.

Crucially, unlike Python's `RecursionError` (which mistune fails to catch but which is at least a catchable exception in principle), Go's stack overflow on excessive recursion is a **fatal, unrecoverable runtime error** (`fatal error: stack overflow`) that terminates the entire process — it cannot be caught by `recover()`. This makes the Go analog strictly more severe than the referenced Python bug: a single crafted transaction can kill the whole node process, not just fail one request.

### Impact Explanation
An attacker who can submit a single `TxTypeAccountUpdate` (or `TxTypeAccountCreation`/fee-delegated variants) transaction to any public RPC node's `sendRawTransaction` endpoint can embed a deeply self-nested `AccountKeyRoleBased` structure (`RoleBased → RoleBased → RoleBased → ...`) in the `AccountKey` field. RLP does not support reference sharing, so each nesting level costs a small constant number of bytes; within the node's max transaction size limit, thousands of nesting levels are achievable, enough to exhaust the default Go goroutine stack growth ceiling. Decoding this transaction — which happens as soon as the raw bytes are parsed, before tx-pool admission checks such as `CheckInstallable` run — triggers unbounded mutual recursion between `AccountKeySerializer.DecodeRLP` and `AccountKeyRoleBased.DecodeRLP`, crashing the node process with an unrecoverable stack overflow. This is a network-wide denial-of-service: every honest full node/RPC node that receives and decodes the transaction (via RPC submission, block propagation, or historical block re-sync) crashes, causing state divergence/availability loss across the network — matching the "acceptance of/exposure to an invalid, unbounded-cost transaction" and "state/availability divergence between honest nodes" impact categories.

### Likelihood Explanation
High likelihood of reachability: the code path is reachable by any unprivileged sender of a `TxTypeAccountUpdate`/`TxTypeAccountCreation` transaction through the standard public `sendRawTransaction` RPC, requiring no special privileges, no validator/peer compromise, and no prior on-chain state. The only precondition is being able to submit or broadcast a sufficiently large raw transaction, which is a completely standard capability of any transaction sender.

### Recommendation
Add an explicit nesting-depth (or type) check in `AccountKeyRoleBased.DecodeRLP` / `AccountKeySerializer.DecodeRLP` that rejects `AccountKeyTypeRoleBased` as an element type before recursing — i.e., enforce the "no composite type inside RoleBased" invariant *during decode*, not only in the post-decode `CheckInstallable`/`CheckUpdatable` paths. Alternatively/additionally, introduce a global recursion-depth counter threaded through `rlp.Stream`/`AccountKeySerializer.DecodeRLP` that aborts decoding with an error once a small fixed depth (e.g. 1, matching the "RoleBased cannot contain RoleBased" business rule) is exceeded.

### Proof of Concept
1. Construct nested RLP bytes representing `AccountKeyRoleBased` containing one element whose type is `AccountKeyTypeRoleBased`, which itself contains one element of type `AccountKeyTypeRoleBased`, repeated N times (N large, e.g. tens of thousands), still fitting inside the max transaction size.
2. Wrap this in a `TxTypeAccountUpdate` transaction's `AccountKey` field, RLP-encode the transaction, and submit it via `eth_sendRawTransaction`/`klay_sendRawTransaction` to any Kaia node.
3. When the node calls `rlp.DecodeBytes`/`tx.DecodeRLP` on the received bytes, `AccountKeySerializer.DecodeRLP` ↔ `AccountKeyRoleBased.DecodeRLP` recurse N times before any `CheckInstallable`/`checkAccountKeyZeroValues` validation is reached, causing a Go `fatal error: stack overflow` that terminates the node process.

Note: I was unable to fully trace the exact call site where the top-level `Transaction.DecodeRLP` invokes decoding of the `AccountKey` field (tool budget exhausted before confirming `tx_internal_data_account_update.go`'s decode wiring in detail), so the precise transaction-size/depth threshold required to overflow the default Go stack was not empirically measured in this pass — this would need to be confirmed with a runnable PoC in a full development environment.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}

func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
