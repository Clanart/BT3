### Title
Immature coinbase outputs are reported as spendable `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` scans every transaction in `block.txdata`, including `txdata[0]` (the coinbase), and returns matching outputs as ordinary `ReceivedOutput`s with no maturity marker. `SignableTransaction::new` later consumes `ReceivedOutput`s solely as spendable inputs, without checking whether the outpoint is an immature coinbase output. A miner or RPC-fed block can therefore cause Serai wallet code to report funds as received and eligible for signing even though Bitcoin consensus forbids spending them for 100 blocks.

### Finding Description
The rejected-milestone analog is a missing state gate before an object is consumed as actionable. Here, `scan_block` does not distinguish the coinbase transaction from normal transactions and forwards every transaction to `scan_transaction`, which emits a `ReceivedOutput` solely based on `script_pubkey` matching. The only guard is a comment saying callers must post-process coinbase outputs if they need immediately spendable funds; the returned type carries no `is_coinbase`/maturity state and no API enforces the requirement. Downstream, `SignableTransaction::new` accepts `Vec<ReceivedOutput>`, sums their values, builds `TxIn`s from their outpoints, and never checks coinbase maturity before producing a signable transaction.

### Impact Explanation
A `ReceivedOutput` derived from a coinbase is consensus-immature and cannot be spent until 100 confirmations. If wallet/scheduler code treats `scan_block` output as spendable, it can account for balance that cannot actually fund a withdrawal and can construct/sign a transaction that Bitcoin nodes reject as invalid. This matches the accepted impact class of funds reported received that are not spendable and can additionally waste a signing attempt on an unbroadcastable transaction.

### Likelihood Explanation
The unsafe path is reachable from public Bitcoin block data: any block whose coinbase pays a scanned script produces a `ReceivedOutput`. The main processor integration currently avoids this by explicitly skipping `block.txdata[0]` in `get_outputs`, which reduces exposure for that path. However, `scan_block` remains a public production API in the in-scope wallet crate, and its return type gives callers no way to distinguish immature coinbase outputs from spendable outputs except by re-checking the block position themselves.

### Recommendation
Make spendability explicit instead of relying on caller post-processing. Either change `Scanner::scan_block` to skip `block.txdata[0]` by default and provide a separate `scan_block_including_coinbase`/ maturity-aware API, or extend `ReceivedOutput` with an `immature_coinbase`/confirmation-height flag and have `SignableTransaction::new` reject immature inputs. At minimum, return an error or empty result for coinbase matches in `scan_block` unless the caller supplies enough context to prove maturity.

### Proof of Concept
Conceptual reproduction against `networks/bitcoin/src/wallet/mod.rs` and `send.rs`:

```rust
  &[(destination_script, payment_amount)],
  None,
  None,
  fee_per_vbyte,

// Signing succeeds structurally, but publishing the resulting transaction is invalid
// under consensus while the coinbase is younger than 100 blocks.
```

The vulnerable behavior is that `scan_block` iterates all `block.txdata` and returns coinbase matches as normal `ReceivedOutput`s. [1](#0-0)  `scan_transaction` creates `ReceivedOutput` purely from a script match and outpoint, with no coinbase/maturity field. [2](#0-1)  `SignableTransaction::new` then treats each `ReceivedOutput` as an input and funding source without checking maturity. [3](#0-2)  The processor integration separately skips the coinbase, confirming the hazard exists for direct `scan_block` consumers. [4](#0-3)
