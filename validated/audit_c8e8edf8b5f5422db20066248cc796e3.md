## Analysis Summary

I searched the Aptos-native publish stack (`aptos_framework::code`, `object_code_deployment`, `resource_account`, `large_packages`, `init`, and the CLI publish/verify tooling) for a local analog to the "unverified value silently trusted as safe" pattern from the BarnBridge report (a value that is *supposed* to represent ground truth but is never actually validated against the thing it claims to describe).

The strongest candidate is in the CLI's package-verification path, not the on-chain module — the on-chain `code::publish_package` / `object_code_deployment` / `init` logic is heavily fortified (formal specs marked "Critical, manually audited", exhaustive e2e tests for ownership/compat/dependency edge cases), so I did not find a fresh unprivileged bypass there.

### Title
`aptos move verify-package` never compares on-chain bytecode to local compilation, so it falsely certifies unverified module bytes as matching source - (File: `aptos-move/cli/src/stored_package.rs`)

### Summary
The Aptos CLI documents `verify-package` as the tool that "checks that on-chain bytecode matches a local source tree" [1](#0-0) . In practice, `VerifyPackage::execute` only downloads `PackageRegistry` metadata and calls `CachedPackageMetadata::verify`, which compares self-reported `PackageMetadata` fields (`name`, `deps`, `modules`, `manifest`, `upgrade_policy`, `extension`, `source_digest`) between the locally rebuilt metadata and the on-chain metadata [2](#0-1) . It never fetches the actual deployed bytecode (`client.get_account_module`) nor diffs it against the locally compiled bytecode, even though `CachedPackageRegistry::get_bytecode` exists for exactly that purpose [3](#0-2)  and is used only by the separate `DownloadPackage` command, not by `VerifyPackage` [4](#0-3) .

### Finding Description
`PackageMetadata.source_digest`, `manifest`, and each `ModuleMetadata.source`/`source_map` are entirely self-reported by the publisher at publish time and computed purely from local source text by the compiler [5](#0-4) . The on-chain `code::publish_package` function never recomputes or cross-checks these fields against the actual bytecode bytes being loaded — it only checks module *names* match (`expected_modules`) and bytecode dependency addresses via `request_publish`/`request_publish_with_allowed_deps` [6](#0-5) ; the metadata (`source`, `manifest`, `source_digest`) is stored verbatim without ever being tied to the actual bytecode bytes deployed.

Given that decoupling, the CLI's `verify-package` was meant to be the safety net that a reviewer/auditor relies on to confirm "the code I'm looking at is the code that's really running." But `verify()` only proves internal self-consistency: that recompiling the claimed source produces a `source_digest`/`manifest`/`modules` list identical to what the *publisher already wrote* on chain. It never touches the executable bytecode that the Move VM will actually run. A publisher can therefore submit arbitrary/malicious bytecode alongside metadata (source text, manifest, source_digest) describing an unrelated, benign package, and `verify-package` will print "Successfully verified source of package" [7](#0-6)  even though the deployed bytecode has nothing to do with the shown source.

### Impact Explanation
This is a direct instance of "mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" reaching an unprivileged, user-facing trust decision: anyone who runs `aptos move verify-package` to audit a third-party package (before depending on it, granting it permissions, or interacting with it) receives a false assurance. Because the check is advertised in official docs as bytecode verification, this can mislead integrators, auditors, and downstream tooling into trusting malicious modules as verified, enabling supply-chain-style attacks on Aptos dApps/integrators that rely on this CLI feature as an integrity gate.

### Likelihood Explanation
No privilege is required to trigger the mismatch: any package publisher can submit metadata (`source`, `manifest`, `source_digest`) that is disconnected from the actual bytecode, since the framework never validates the correspondence. Any user of `verify-package` (a normal CLI workflow encouraged by the documentation) is silently exposed, making this a high-likelihood, zero-privilege gap in a security-relevant tool.

### Recommendation
Have `VerifyPackage::execute` always fetch on-chain bytecode via `CachedPackageRegistry::get_bytecode` (or `with_bytecode = true`) and compare it byte-for-byte (or by hash) against the freshly compiled local bytecode, in addition to the existing metadata comparison. Optionally, also enforce/validate `source_digest` on-chain at publish time by deriving it from the actual compiled units rather than trusting the publisher-supplied value, closing the root decoupling between metadata and code.

### Proof of Concept
1. Build package `A` with source `S1` (benign, e.g. a no-op module) and note its resulting `source_digest`/`manifest`.
2. Hand-craft a `PackageMetadata` whose `source`/`manifest`/`source_digest` fields byte-for-byte equal what `A` produces, but pair it in the publish transaction with a different, malicious compiled module bytecode `code` (must keep the same module name to satisfy `expected_modules` in `code::publish_package`) [8](#0-7) .
3. Publish via `code::publish_package_txn(owner, metadata_serialized, code)`; this succeeds because the framework never checks that `source`/`manifest`/`source_digest` correspond to `code`.
4. Run `aptos move verify-package --account <owner>` after recompiling the original benign source `S1` locally: `CachedPackageMetadata::verify` compares only metadata fields, all of which were crafted to match, so it reports "Successfully verified source of package" [9](#0-8)  — despite the actually running bytecode being entirely different (malicious) code.

## Picking a publication pattern

Two patterns are supported side by side; pick based on how you want the package's address to behave:

- **Account publishing** (`publish` / `deploy`): the modules live at the **signer's account address**. Simplest pattern. Upgrades happen by re-publishing from the same account. The signer owns upgrade authority and can't transfer it.
- **Code-object publishing** (`deploy-object` / `upgrade-object`): the modules live at a **separate, derived object address**. Upgrade authority is held in a code object and can be transferred. Use this when modules need an address independent of any single account.

For code review and reproducibility, [`verify-package`](#aptos-move-verify-package) checks that on-chain bytecode matches a local source tree.

                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name

            bail!(
                "Dependencies don't match {:?} : {:?}",

                self_metadata.deps

                self_metadata.modules

                self_metadata.manifest

            )

#[async_trait]
impl CliCommand<&'static str> for VerifyPackage {
    fn command_name(&self) -> &'static str {
        "VerifyPackage"
    }

    async fn execute(self) -> CliTypedResult<&'static str> {
        // First build the package locally to get the package metadata
        let build_options = BuildOptions {
            install_dir: self.move_options.output_dir.clone(),
            bytecode_version: fix_bytecode_version(
                self.move_options.bytecode_version,
                self.move_options.language_version,
            ),
            ..self.included_artifacts.build_options(&self.move_options)?
        };
        let w = self.env.writer();
        let pack = BuiltPackage::build_to(&w, self.move_options.get_package_path()?, build_options)
            .map_err(|e| CliError::MoveCompilationError(format!("{:#}", e)))?;
        let compiled_metadata = pack.extract_metadata()?;

        // Now pull the compiled package
        let client = self.rest_options.client(&self.profile_options)?;
        let registry = CachedPackageRegistry::create(client, self.account, false).await?;
        let package = registry
            .get_package(pack.name())
            .await
            .map_err(|s| CliError::CommandArgumentError(s.to_string()))?;

        // We can't check the arbitrary, because it could change on us
        if package.upgrade_policy() == UpgradePolicy::arbitrary() {
            return Err(CliError::CommandArgumentError(
                "A package with upgrade policy `arbitrary` cannot be downloaded \
                since it is not safe to depend on such packages."
                    .to_owned(),
            ));
        }

        // Verify that the source digest matches
        package.verify(&compiled_metadata)?;

        Ok("Successfully verified source of package")
    }
