### Title
`ReceivedOutput::read` accepts an offset/script_pubkey mismatch, producing outputs reported as received which are not spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary

The Dokploy bug class is insufficient validation/sanitization of attacker-supplied input before it is consumed by a trusted operation. In `bitcoin-serai`, `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122) deserializes three independent fields — a scalar `offset`, a `TxOut`, and an `OutPoint` — with no check that the claimed `offset` actually derives the `script_pubkey` contained in the `TxOut`. The deserialized value is treated as "a spendable output" of the scanning key, yet spending is only possible when `p2tr_script_buf(key + G * offset) == output.script_pubkey`, a relation `read` never verifies.

### Finding Description

`ReceivedOutput` is defined as "a spendable output" carrying `offset`, `output`, and `outpoint` (networks/bitcoin/src/wallet/mod.rs:88-97). Its constructor-by-deserialization reads each field independently:

- `offset` is read via `Secp256k1::read_F` — any canonical scalar is accepted (line 123).
- `output` is any consensus-decodable `TxOut` — the `script_pubkey` is not even required to be P2TR (lines 128-129).
- `outpoint` is any decodable `OutPoint` (lines 130-131).

The only place this relation is checked is much later, inside `SignableTransaction::multisig`, which returns `None` when `p2tr_script_buf(offset.group_key()) != self.prevouts[i].script_pubkey` (networks/bitcoin/src/wallet/send.rs:273-279). Between `read` and `multisig`, the `ReceivedOutput` is indistinguishable from a genuine scan result: `value()` reports its satoshi amount, `outpoint()` reports a claimable UTXO, and `Output::key()` in the processor will happily compute `key - G * offset` to yield a *different* key than the one the output actually pays to (processor/src/networks/bitcoin.rs:112-122).

Note that `Ciphersuite::read_F` correctly enforces canonical scalars (crypto/ciphersuite/src/lib.rs:74-83) — the gap is semantic validation, not encoding validation, exactly mirroring how Dokploy's `sanitizeCommand` performed superficial checks while passing semantically malicious content to the shell.

### Impact Explanation

Any flow where an untrusted party supplies serialized `ReceivedOutput` bytes (the type is explicitly designed for transport/storage via `read`/`write`/`serialize`) causes the consumer to treat a received payment as wallet-controlled funds that the wallet cannot actually spend: `SignableTransaction::multisig` returns `None`, or worse, the output is tallied at face value while the spend key doesn't correspond. This matches the accepted "funds reported received that are not spendable" impact class. A related variant: an offset/script combination matching a *different* registered offset (or a non-P2TR script entirely) misattributes the output's spending conditions, e.g., reporting a script-path-spendable output as key-path-spendable — the exact concern the `register_offset` docs raise (networks/bitcoin/src/wallet/mod.rs:177-179), but reachable here via bytes rather than via the guarded registration API.

### Likelihood Explanation

Reachability requires the consumer to deserialize `ReceivedOutput`s from a source an attacker can influence (e.g., `Output::read` at processor/src/networks/bitcoin.rs:145-166, which wraps `ReceivedOutput::read` and is used for persisted/communicated outputs). Within that precondition the attack is deterministic: no race, no cryptographic hardness assumption, just bytes. Severity is Medium: it corrupts wallet state/accounting and can burn fees or lock funds in attempted spends, but does not directly leak key material.

### Recommendation

Validate internal consistency at deserialization time or at the `Scanner` boundary: after reading, recompute `p2tr_script_buf(expected_key + G * offset)` and require equality with `output.script_pubkey` (this requires threading the expected key, or providing a `Scanner::read_output`/`ReceivedOutput::read_for(key, ...)` API). At minimum, require `output.script_pubkey.is_p2tr()` and document that `read` does not establish spendability. `SignableTransaction::multisig`'s existing check confirms the invariant the type is supposed to maintain.

### Proof of Concept

```rust
// networks/bitcoin context; `key` is the scanner's even-Y group key
use bitcoin_serai::wallet::{ReceivedOutput, p2tr_script_buf};
use bitcoin::{TxOut, OutPoint, Amount, ScriptBuf, Txid, hashes::Hash};
use frost::curve::Secp256k1;
use k256::{ProjectivePoint, Scalar};
use ciphersuite::Ciphersuite;

// Craft bytes: offset = 1, but the TxOut pays to the *unoffset* key
let mut buf = vec![];
buf.extend(Scalar::ONE.to_bytes()); // any canonical scalar is accepted
let txout = TxOut {
  value: Amount::from_sat(50_000),
  script_pubkey: p2tr_script_buf(key).unwrap(), // corresponds to offset = 0, not 1
};
buf.extend(bitcoin::consensus::serialize(&txout));
buf.extend(bitcoin::consensus::serialize(&OutPoint {
  txid: Txid::all_zeros(),
  vout: 0,
}));

// Deserialization succeeds despite the offset/script inconsistency
let output = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(output.value(), 50_000);          // reported as received funds
assert_eq!(output.offset(), Scalar::ONE);

// ...but it can never be spent: multisig() detects the mismatch only at
// signing time and returns None
let tx = SignableTransaction::new(vec![output], &payments, None, None, 1).unwrap();
assert!(tx.multisig(&keys).is_none());       // funds reported, not spendable
```

Uncertainty note: severity hinges on whether an attacker controls bytes reaching `ReceivedOutput::read` in production paths (e.g., coordinator-supplied or stored `Output`s); the rules explicitly whitelist `ReceivedOutput::read` as an untrusted-bytes entry point, and the missing invariant is provable from the code regardless.
