## Title
Discarding multiple files can permanently delete some files while leaving the working tree/index unrestored when a later file's trash-move fails - (File: `app/src/lib/stores/git-store.ts`)

## Summary
`GitStore.discardChanges()` iterates over the list of files to discard and calls `this.shell.moveItemToTrash()` for each one *before* performing any `git reset`/`git checkout-index` recovery step. If the trash-move for one file in the middle of the batch throws (e.g., OS trash disabled/misconfigured, permissions, or "askForConfirmationOnDiscardChangesPermanently" flow) the function throws a `DiscardChangesError` and aborts immediately - but the files that were *already* moved to trash earlier in the same loop are never checked out from the index. The recovery step (`resetPaths` + `checkoutIndex`) that restores working-directory content from the index only runs after the entire loop completes without error, so any file processed before the failing one is left deleted on disk with no restoration performed in that same call.

## Finding Description
`discardChanges` in `app/src/lib/stores/git-store.ts` processes `files` sequentially: [1](#0-0) 
For each file it calls `this.shell.moveItemToTrash(...)`. If that call throws and `askForConfirmationOnDiscardChangesPermanently` is `true`, the function throws `new DiscardChangesError(e, this.repository, files)` immediately, aborting the `for` loop: [2](#0-1) 

The recovery logic that actually restores content into the working directory - `resetPaths` (unstage) followed by `checkoutIndex` (write index content back into the working tree) - is only reached *after* the loop over all `files` completes: [3](#0-2) 

This mirrors the reported bug-class exactly: an early, irreversible mutation (deleting the on-disk file / moving it to a shared, un-tracked OS trash) is performed per-item, while the "make the user whole again" step (checkout-index from the index) is deferred to the very end and is only executed if *every* item in the batch succeeds. When a later file in the same batch fails, the app throws and skips this restoration path entirely for the files that already succeeded — just like `LaunchEvent.emergencyWithdraw()` reverting because the WAVAX reserve was already consumed by `createPair()`, leaving users with neither their WAVAX nor their LP tokens.

Making this worse, the caller (`AppStore._discardChanges`) treats `DiscardChangesError` as a "retryable" condition: [4](#0-3) 
and surfaces `DiscardChangesRetryDialog`, whose "Permanently Discard Changes" button calls `dispatcher.performRetry(retryAction)` with the **original, unmodified `files` list** (`RetryActionType.DiscardChanges`): [5](#0-4) [6](#0-5) 
Retrying re-invokes `discardChanges` for the *entire* file list, including the files whose on-disk copies were already moved to trash and whose original working-tree content was never checked back out — those files are simply skipped over on retry (since `moveItemToTrash` on a non-existent path either no-ops or errors), and the loop never performs `checkoutIndex` for them because they're gone.

The application's own documentation asserts that discard-changes is composed of three ordered steps (trash → reset → checkout) as if they were part of one atomic transaction, but the implementation only performs steps 2–3 once, at the very end, for the whole batch: [7](#0-6) 

## Impact Explanation
This causes silent, irrecoverable loss of a user's uncommitted work. Because Desktop's UI communicates that discarded changes are safely preserved ("Changes can be restored by retrieving them from the {TrashNameLabel}"), users reasonably expect the file to be recoverable via the OS trash even in a partial-failure scenario: [8](#0-7) 
but when discard is invoked on a multi-file selection and any single file's trash operation fails mid-batch, files processed earlier in the loop are deleted from the working directory with no `git checkout-index` performed to restore them, and the flow the user is shown (retry dialog) does not repair this because it re-submits the full original file list rather than distinguishing already-trashed files from pending ones. The end state is: modified/uncommitted content is gone from the working tree, and Desktop's index-based recovery mechanism never fires for those specific files in that operation.

## Likelihood Explanation
This requires no attacker privileges or local malware — it can be triggered by ordinary environmental conditions that end users encounter: OS trash disabled by policy, OneDrive/network-drive paths where `shell.trashItem` frequently fails, restricted file permissions, or antivirus locking a file mid-operation. `askForConfirmationOnDiscardChangesPermanently` is a normal Desktop setting, and multi-file discard (via "Discard All Changes" or multi-select discard) is a common day-to-day action, so hitting this partial-failure path only requires one file in a batch discard to fail trash-move for an environmental reason unrelated to attacker control.

## Recommendation
Restructure `discardChanges` so that the trash-move step and the reset/checkout recovery step are performed per-file (or wrapped so that a failure partway through the batch still runs `resetPaths`/`checkoutIndex` for every file that was already trashed) rather than deferring recovery until the entire loop completes without error. Alternatively, collect trash-move failures without aborting the loop, still run the reset/checkout recovery for all successfully-trashed files, and only surface the retry dialog for the subset of files that actually failed to move to trash.

## Proof of Concept
1. Select two or more modified tracked files (e.g., `A.txt`, `B.txt`) in Desktop's Changes list and choose "Discard Changes."
2. Ensure `askForConfirmationOnDiscardChangesPermanently` is `true` (default confirmation flow) and arrange for the trash operation on the *second* file (`B.txt`) to fail (e.g., point the repository at a path on a filesystem/mount where `shell.trashItem` throws, such as certain network shares, or temporarily disable the OS trash for that volume).
3. In `discardChanges` (`app/src/lib/stores/git-store.ts:1555-1584`), the loop successfully calls `moveItemToTrash` for `A.txt` (deleting it from the working directory), then throws `DiscardChangesError` when processing `B.txt`.
4. Because the exception is thrown before `await this.performFailableOperation(...)` at line 1636 is ever reached, `checkoutIndex` is never invoked for `A.txt`, even though its on-disk copy is already gone.
5. `AppStore._discardChanges` catches the error and calls `this.emitError(error)`, presenting `DiscardChangesRetryDialog`.
6. Clicking "Permanently Discard Changes" calls `dispatcher.performRetry` with the original `files: [A.txt, B.txt]`, re-running `discardChanges` for both files — but `A.txt` no longer exists on disk to be re-trashed, and no `checkoutIndex` call restores its content, since the code path that would do so was never reached for it in the original invocation.
7. Net result: `A.txt`'s uncommitted modifications are permanently lost, with no explicit user action to "delete `A.txt` specifically" — only the initial multi-file "Discard Changes" click.

```markdown
The `Discard Changes` flow is composed of multiple steps.

### Moving Files to Trash

Electron provides the [`shell.trashItem(fullPath)`](https://www.electronjs.org/docs/api/shell#shelltrashitempath)
API to manage moving files into the OS-specific trash.

Desktop uses this API to move _all new or modified files_ out from the
repository as a way to preserve changes, in case the user wishes to recover
them later. Files moved to the Trash are moved over as-is, so ensure you have
the ability to view hidden files if you wish to recover files that are prefixed
with `.`.

### Reset Paths

The next step is identifying any files that have been listed for discard that
are also staged in the index. While Desktop doesn't stage files itself, a user
might be using other tools alongside Desktop, so this is a sanity check before
proceeding to the next stage.

**Git CLI equivalent**: `git reset HEAD -- [path]`

### Checkout Paths

The last step is to replace the modified files in the working directory with
whatever is currently in the index - this ensures that Desktop only replaces
files that the user has chosen to discard.

**Git CLI equivalent**: `git checkout-index -f -u -- [path]`
```
