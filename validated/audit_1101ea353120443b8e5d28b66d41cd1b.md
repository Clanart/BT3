## Title
Automatic remote-URL rewriting driven by untrusted GitHub API `clone_url` allows silent redirection of pushes/fetches to an attacker-controlled repository - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically re-fetches metadata for the repository associated with the current `origin` remote and, based on a heuristic comparison of URLs, will silently call `git remote set-url` to point the local repository at whatever `clone_url` the GitHub API returns — with no user confirmation dialog. Because the `owner`/`name` used to make that API call are derived directly from the existing remote URL (which is fully controlled by whoever created/renamed the repository the user cloned), a malicious repository owner can rename/transfer their repository so that the next background refresh silently rewrites the victim's `origin` remote to a different repository, redirecting future `push`/`fetch` operations without any indication to the user. This mirrors the FeeVault report's underlying invariant break: a background transition (setting a new fee calculator / refreshing repo metadata) silently discards or overwrites a value the user relied on (unclaimed fees / the user's intended push destination) based on unchecked external input, with the maintainers' current mitigation (heuristic checks) being insufficient to fully prevent it.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app-store.ts` derives `owner`/`name` from the *current* remote via `matchGitHubRepository`, calls the GitHub API for that repo, and — if a `GitHubRepository` association already exists — feeds the API response straight into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` then compares the API's `clone_url` to the locally configured remote using only a loose heuristic (matching protocol, and comparing the *previously cached* `gitHubRepository.cloneURL` to the current remote) and, if it decides the remote is "stale", calls `gitStore.setRemoteURL` automatically: [2](#0-1) 

The comparison logic in `urlMatchesRemote`/`repositoryMatchesRemote` only checks hostname/owner/name equality parsed out of the URL strings — it does not verify that the *new* clone URL still refers to the same underlying repository identity (e.g. same repo ID) as the one the user originally added, nor does it ask for confirmation before rewriting: [3](#0-2) 

`GitStore.setRemoteURL` performs the actual `git remote set-url` mutation with no additional gating and immediately updates in-memory/cached remote state: [4](#0-3) 

Because `owner`/`name` for the API lookup are taken from the very remote that a malicious repository owner controls (they can rename the repo, causing `api.fetchRepository` to return a fresh `clone_url` for the renamed/transferred identity), the attacker can engineer a scenario where the next repository refresh (which happens automatically on numerous operations such as pull, fetch, push — see `withRefreshedGitHubRepository` call sites) silently repoints `origin` away from the repository the user originally cloned.

### Impact Explanation
If exploited, a user's local `origin` remote can be silently rewritten to point at a different repository without any dialog, confirmation, or visible diff of the change. Because pushes/fetches use the remote's `url` (and `envForRemoteOperation(remote.url)` for credential/proxy resolution), this can cause the user's future commits to be silently pushed to a repository the attacker controls instead of the one intended — corrupting the destination of what the user commits/pushes, one of the explicitly valid impact classes (silent corruption of what the user pushes). It could also be leveraged to redirect fetch/pull traffic, influencing credential negotiation for the new remote.

### Likelihood Explanation
The trigger requires only that the victim has cloned/added as a remote a repository owned or controlled by the attacker (a normal, attacker-controlled GitHub object — no local access, no leaked credentials, no malware needed) and that Desktop performs one of its many automatic background "refresh GitHub repository" operations, which happens routinely (on push, pull, fetch, and periodic background refresh). The heuristic gate (`protocolsMatch && remoteUrlUnchanged && !urlsMatch`) is not a strong authorization check — it is intended purely to detect "the GitHub repo was renamed," and does not verify same-repository identity (e.g., there's no cross-check against a stable ID), so it does not stop an attacker-controlled rename/redirect chain.

### Recommendation
- Never silently mutate `origin` (or any tracked remote) based on API-provided `clone_url`; at minimum, prompt the user before rewriting a remote URL, showing the old and new URLs.
- Validate repository *identity* (e.g., GitHub's stable repository `id`) rather than relying solely on owner/name/hostname string matching in `urlMatchesRemote`, so a renamed/transferred repository can't be conflated with an unrelated one.
- Rate-limit or otherwise constrain how often/aggressively this auto-correction can occur, and log/surface the change prominently in the UI so users can detect unexpected redirection.

### Proof of Concept
1. Attacker creates and shares a public GitHub repository `attacker/legit-tool`; victim clones it in GitHub Desktop, so `origin` is set to `https://github.com/attacker/legit-tool.git` and Desktop records the association in `gitHubRepository.cloneURL`.
2. Attacker renames the repository (or transfers it) such that its GitHub API record now reports `clone_url: https://github.com/attacker/malicious-repo.git` (e.g., renaming and creating a decoy at the old name, or via GitHub's rename-redirect semantics).
3. On the victim's next push/pull/fetch, `repositoryWithRefreshedGitHubRepository` (`app-store.ts:4874`) calls `api.fetchRepository(owner, name)`, gets the updated `clone_url`, and passes it to `updateRemoteUrl` (`update-remote-url.ts:7`).
4. Because `protocolsMatch` and `remoteUrlUnchanged` hold (the local remote still matches the previously cached `cloneURL`) and `urlsMatch` is false (owner/name changed), `updateRemoteUrl` calls `gitStore.setRemoteURL(...)`, silently rewriting `origin` to the attacker's new destination with no confirmation dialog shown to the victim.
5. Subsequent `git push` from the victim now targets `attacker/malicious-repo` transparently.

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
