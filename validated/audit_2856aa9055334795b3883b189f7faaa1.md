## Title
Unchecked ERC20 `transfer` return value in escrow withdrawal finalizes settlement even when the token transfer silently fails, permanently locking escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` (the Tron variant of the intents-v2 gateway) releases escrowed tokens to a beneficiary using a raw low-level `.call` encoding `IERC20.transfer`, and only checks that the *call itself* did not revert — it never inspects the ABI-encoded boolean return value that `IERC20.transfer` is supposed to produce. Any ERC20/TRC20 token that returns `false` on failure instead of reverting (a well-known non-standard-but-common token behavior) will make `success == true` while no tokens actually move. The function nevertheless decrements the escrow ledger and unconditionally finalizes the order (`_filled[body.commitment] = beneficiary`), permanently blocking any retry and leaving the tokens stuck in the contract while the on-chain accounting and emitted events (`EscrowReleased`/`EscrowRefunded`) claim the payout succeeded.

### Finding Description
`withdraw()` is the terminal step for both `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund), reached via `onAccept()` after `authenticate()`, and also via `onGetResponse()` for source-side cancellations: [1](#0-0) 

Note that `using SafeERC20 for IERC20;` is imported and correctly used elsewhere in the same file for escrowing inputs (`safeTransferFrom`), but the payout path deliberately uses the unchecked raw-call pattern instead: [2](#0-1) 

The same unchecked pattern also appears in the dust-sweep path: [3](#0-2) 

`success` from a raw `.call` only reflects whether the callee *reverted*; it says nothing about the semantic result encoded in the returned bytes. A token contract that returns `abi.encode(false)` on a failed transfer (rather than reverting) — which is legal per the ERC20 spec and observed in real deployed tokens, and is even more plausible on Tron/TVM where TRC20 tokens frequently diverge from strict EVM ERC20 semantics — makes `success == true` here. The code path then proceeds as if the transfer succeeded:
- `_orders[body.commitment][token] -= amount;` — decrements escrow accounting even though the tokens never left the contract.
- `_filled[body.commitment] = beneficiary;` — marks the order as finalized, which the `cancelOrder`/`onGetResponse` guard (`_filled[commitment] != address(0)) revert Filled();`) uses to block any future settlement attempt for that commitment.
- `emit EscrowReleased(...)` / `emit EscrowRefunded(...)` — signals success to indexers/SDK/users.

Because the order is now permanently marked filled/refunded, there is no code path to retry the transfer or recover the escrowed tokens: they remain custodied by the gateway forever while every off-chain and on-chain signal says the beneficiary was paid.

### Impact Explanation
This is a direct loss/lock of bridged funds in the intent-settlement custody logic: the rightful beneficiary (solver on `RedeemEscrow`, or the user on `RefundEscrow`/GET-based cancellation) never receives their tokens, escrow accounting is silently corrupted, and the finalized `_filled` marker forecloses any remediation through the contract's own public entrypoints. This matches the bounty's in-scope class of "stealing or loss of funds" / "false proof/state acceptance" arising from ordinary, unprivileged use of the intents gateway — no malicious relayer, prover, or admin is required.

### Likelihood Explanation
Reachable by any unprivileged user or solver simply by using an input/output/fee token whose `transfer` implementation returns `false` on failure instead of reverting (a real, documented ERC20/TRC20 pattern, not a hypothetical). No special privileges, governance action, or compromised infra are needed — only a token behaving in a standard-but-non-strict way combined with a transfer that legitimately fails (e.g., a paused/frozen recipient, blacklist, or insufficient allowance-adjacent edge case implemented via boolean return rather than revert).

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (and in the `sweepDust`/dust-sweep loop) with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in this file. `safeTransfer` correctly decodes and checks the boolean return data (and tolerates tokens with no return data), reverting the whole transaction — including the `_filled`/escrow-ledger mutations — if the transfer did not actually succeed, exactly mirroring the pattern already used for `safeTransferFrom` on escrow deposit.

### Proof of Concept
1. Create a same-chain or cross-chain intents-v2 order whose input/output token is an ERC20/TRC20 implementation that returns `false` (instead of reverting) when a `transfer` cannot be completed (e.g., recipient blacklisted, or a custom token used for testing this exact behavior).
2. Have a solver fill the order (or the user cancel it), driving execution into `withdraw()` via `onAccept`/`onGetResponse`.
3. Arrange for the token's `transfer(beneficiary, amount)` call to return `false` for the beneficiary address (e.g., token-side blacklist or paused state), while the low-level `.call` itself does not revert.
4. Observe: `success` is `true`, so `TransferFailed()` is never triggered; `_orders[commitment][token]` is decremented, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — yet the beneficiary's token balance is unchanged and the escrowed tokens remain stuck in the gateway with no further code path to release them.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
