## Title
`IntentGatewayV2.placeOrder` (Tron variant) escrows a nominal amount instead of the actual balance received for fee-on-transfer tokens, permanently locking order funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2.placeOrder()` credits escrow (`_orders[commitment][token]`) with the *requested* input amount rather than the amount the contract actually received. For any ERC-20 that charges a fee on transfer, the contract's real token balance ends up lower than what accounting says is escrowed. Since `withdraw()` unconditionally tries to move the full recorded escrow amount and the transaction reverts if the contract lacks the balance, the entire order (including any unaffected tokens bundled in the same order) becomes permanently unredeemable and unrefundable.

### Finding Description
This is the direct local analog of the `ConvexMasterChef` bug: that contract computed rewards from `pool.lpToken.balanceOf(address(this))`, a value that could be silently inflated/deflated by activity unrelated to the actual staked amount, corrupting the accounting invariant "recorded balance == real balance." Here the same invariant is violated in the opposite direction — the code trusts a *nominal* value instead of measuring the real balance.

In the non-predispatch branch of `placeOrder`:

`reducedInputs[i].amount` is derived from `order.inputs[i].amount` (the amount the caller *claims* to be depositing), computed before the transfer even occurs: [2](#0-1) 

No balance snapshot before/after the `safeTransferFrom` is taken, so if `token` deducts a fee on transfer, the escrow map records more than the gateway actually holds.

Contrast with the sibling, non-Tron `IntentGatewayV2.sol`, which explicitly guards against exactly this by measuring the real delta:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [3](#0-2) 

and is covered by a dedicated fee-on-transfer regression test asserting the escrow equals the actual received amount: [4](#0-3) 

The Tron variant has no equivalent guard or test, and the "predispatch" branch above it computes `dust = balance - requiredAmount` purely to emit a `DustCollected` event — it still stores `reducedInputs[i].amount` (the nominal amount) into escrow rather than the true measured `balance` for that leg: [5](#0-4) 

When settlement occurs, `withdraw()` only guards against a fully-zeroed escrow slot, then unconditionally transfers the requested `amount` and subtracts it from the (inflated) escrow — the actual token transfer will revert if the gateway's real balance is short:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
...
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [6](#0-5) 

Both `RedeemEscrow` and `RefundEscrow` call the same `withdraw()` internal function, so the failure mode blocks recovery in either direction: [7](#0-6) 

### Impact Explanation
Because `withdraw()` iterates over all of an order's tokens in a single transaction and reverts entirely on any transfer failure, an order containing even one fee-on-transfer input token becomes permanently stuck: neither the solver's redemption (`RedeemEscrow`) nor the user's cancellation refund (`RefundEscrow`) can succeed, since both hit the same undercollateralized token slot. All tokens escrowed for that order — including any unaffected, fully-backed tokens in the same order — are then permanently locked in the contract with no governance recovery path (the only recovery mechanism, `SweepDust`, requires knowing exact per-token dust amounts and does not touch per-order `_orders` accounting). This is a direct loss/lock of user funds reachable by any unprivileged user simply by placing an order whose input token happens to charge a transfer fee — no relayer, prover, or admin compromise is required.

### Likelihood Explanation
Likelihood is moderate to high: it requires the intent-order input token to be a fee-on-transfer ERC-20 (a known, common token category — e.g. some rebasing/tax tokens), and no attacker privilege beyond calling the public `placeOrder()` is needed. The non-Tron sibling contract in the same repo already treats this as a first-class threat model (explicit balance-diff handling plus dedicated tests), confirming the protocol intends to support such tokens, making this omission in the Tron deployment a genuine regression rather than an out-of-scope edge case.

### Recommendation
In the Tron `IntentGatewayV2.placeOrder()`, replace the nominal-amount escrow bookkeeping with an actual balance-diff measurement (snapshot `balanceOf(address(this))` before and after each `safeTransferFrom`/predispatch sweep) and credit `_orders[commitment][token]` with the measured delta rather than `reducedInputs[i].amount`, matching the pattern already implemented in `evm/src/apps/IntentGatewayV2.sol`. Additionally, `withdraw()` should validate `amount <= _orders[body.commitment][token]` explicitly (rather than relying on unchecked-subtraction revert) to fail fast with a clear error instead of leaving the order in an ambiguous stuck state.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer ERC-20 (e.g. 1% fee) registered as a valid input token, `protocolFeeBps = 0`.
2. User calls `placeOrder` with `inputs = [{token: FOT, amount: 1000e18}]`, approving `1000e18`.
3. `IERC20(token).safeTransferFrom(msg.sender, address(this), 1000e18)` actually delivers only `990e18` to the gateway (1% fee burned/redirected).
4. `_orders[commitment][FOT] += reducedInputs[0].amount` records `1000e18` (protocolFeeBps=0 so `reducedInputs == inputs`), while `IERC20(FOT).balanceOf(gateway) == 990e18`.
5. Order gets filled on the destination chain; Hyperbridge dispatches `RedeemEscrow` with `body.tokens = [{token: FOT, amount: 1000e18}]`.
6. `withdraw()` attempts `token.call(transfer(beneficiary, 1000e18))` against a contract holding only `990e18` of FOT — the low-level call returns `success = false`, triggering `revert TransferFailed()`, and the entire redemption reverts. The same happens for a `RefundEscrow` attempt. The order's escrow is permanently unredeemable.
