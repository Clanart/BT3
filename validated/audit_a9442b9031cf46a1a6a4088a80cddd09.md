### Title
KIP-71 `GasTarget` governance parameter lacks a non-zero check, enabling a division-by-zero panic in base fee calculation - (File: `params/kip71_config.go`)

### Summary
The `NextMagmaBlockBaseFee` function, which computes the KIP-71 dynamic base fee for every block after the Magma hardfork, divides by the governance-controlled `GasTarget` parameter without any zero-check. While the sibling parameter `BaseFeeDenominator` is explicitly guarded against a zero value both in the governance format checker and defensively inside `NextMagmaBlockBaseFee` itself, `GasTarget` receives no such protection at either layer, mirroring the external report's root cause: a value derived from a governance-controllable input is used as a divisor without accounting for the full valid range of that input.

### Finding Description
`NextMagmaBlockBaseFee` divides by `gasTarget` twice, once in the "gas used above target" branch and once in the "gas used below target" branch: [1](#0-0) [2](#0-1) 

Unlike `BaseFeeDenominator`, which has an explicit `if kc.BaseFeeDenominator == 0` fallback inside this same function: [3](#0-2) 

`gasTarget` has no equivalent fallback and is used directly as-is: [4](#0-3) 

The governance parameter registry confirms this asymmetry: `Kip71BaseFeeDenominator` has a `FormatChecker` that explicitly rejects zero (`v != 0`), while `Kip71GasTarget` uses `noopFormatChecker`, which performs no validation at all: [5](#0-4) 

Since `GasTarget` is a standard governance/header-vote parameter (`reward.gastarget` equivalent, part of the `ParamSet` consumed by `NextMagmaBlockBaseFee` via `BlockValidator`), it can be set to `0` through the normal governance voting mechanism (single-governance node vote or on-chain governance contract, depending on chain mode) without being rejected by the parameter format checker.

Once `GasTarget = 0` is active, any block whose `parentGasUsed > 0` (i.e., essentially any real block) falls into the "gas used above target" branch (`parentGasUsed(0) is compared, and since gasTarget=0, parentGasUsed > gasTarget for any nonzero gas usage`), and the code executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`. `big.Int.Div` panics on division by zero in Go's standard library.

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked by every node during block header validation (`VerifyMagmaHeader`) and during block assembly/finalization to compute the base fee for the next block. A panic here is not merely "sub-optimal fee collection" (as in the original Panoptic report) but a full node crash / consensus halt: every node that validates or builds the affected block will panic identically, since this is deterministic per the governance-visible `GasTarget` value. This satisfies the "acceptance of an invalid transaction or block" / "state divergence between honest nodes" bar, because nodes running older/patched code that guards against zero would compute a different (non-panicking) result than nodes without the guard, causing a chain split, or if all nodes share this code, a total chain halt.

### Likelihood Explanation
Reaching this requires only a governance parameter change (`GasTarget = 0`), which is reachable by:
- The single governing node in `single` governance mode, or
- A successful on-chain governance proposal/vote in `contract` mode.

This is analogous to the original bug's "Uniswap governance sets an unexpectedly low fee tier" scenario — an authorized-but-plausible governance action (misconfiguration, not necessarily malicious) that the code fails to defensively validate, unlike the sibling `BaseFeeDenominator` parameter which the developers clearly recognized needed such a guard.

### Recommendation
Add the same zero-value defensive fallback for `GasTarget` inside `NextMagmaBlockBaseFee` (mirroring the existing `BaseFeeDenominator == 0` handling), and/or change `Kip71GasTarget`'s `FormatChecker` in `kaiax/gov/param.go` from `noopFormatChecker` to a checker that rejects `v == 0`, consistent with `Kip71BaseFeeDenominator`.

### Proof of Concept
1. Governance sets `Kip71GasTarget` (a.k.a. `reward.gastarget`) to `0` via a vote, which passes because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` (no zero check): [6](#0-5) 
2. On the next block, `parentGasUsed` (any nonzero gas usage) is compared against `gasTarget = 0`; since `parentGasUsed > 0 = gasTarget`, execution enters the "gas used above target" branch: [7](#0-6) 
3. The code computes `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`: [8](#0-7) 
4. `big.Int.Div` panics on division by zero, crashing any node validating or building this block (via `BlockValidator.ValidateHeader` calling into `VerifyMagmaHeader`/`NextMagmaBlockBaseFee`), as exercised in the header validation test harness: [9](#0-8)
