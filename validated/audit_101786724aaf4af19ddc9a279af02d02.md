### Title
Single reverting output token permanently locks all escrow for an order in `IntentsBase._withdraw` - (File: evm/src/apps/intentsv2/IntentsBase.sol / evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`_withdraw` (and its tron-fork twin `withdraw`) is the sole exit path that releases all of an order's escrowed input tokens to a beneficiary. It iterates over `body.tokens[]` and does an unconditional `safeTransfer`/`.call` per token inside a single atomic loop, with no ability to skip, retry-individually, or remove a problematic token entry. If any single token in that list reverts on transfer (blacklist-style token, paused token, a token the beneficiary address cannot receive, or one deliberately chosen to always revert), the entire transaction reverts, and *every other legitimately transferable token in the same order's escrow* is locked with it — this exactly mirrors the reported bug class: no mechanism to exclude a bad entry from an all-or-nothing distribution loop.

### Finding Description
`IntentsBase._withdraw` [1](#0-0)  releases escrow for a `WithdrawalRequest` by looping over `body.tokens` and transferring each one to the beneficiary:

```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    ...
    for (uint256 i; i < len; i++) {
        ...
        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            IERC20(token).safeTransfer(beneficiary, amount);
        }
    }
    ...
}
```
There is no per-token try/catch, no partial-success bookkeeping, and no admin/governance path to drop or re-route a single failing token entry from the withdrawal request — the exact structural flaw the external report describes (an enumerable set of "recipients"/entries that all must succeed together, with no removal mechanism).

The tron fork of `IntentGatewayV2.sol` has the identical pattern in `withdraw()` [2](#0-1) , using low-level `.call` and reverting with `TransferFailed()` on the first failing token.

Order `inputs` (the tokens that get escrowed and later released via this same loop) are attacker/user-supplied at `placeOrder` time — a user constructing an order can include an arbitrary ERC-20 address among the input tokens. If that token is one that reverts unconditionally on transfer to a specific address (e.g. a blacklist token where the *solver/beneficiary* address gets blacklisted after order placement, or a token that simply reverts past a certain condition), the withdrawal call for the whole order — which also carries the other, legitimate tokens and the accumulated `TRANSACTION_FEES` — can never succeed. `_withdraw` is invoked both on refund (timeout) and on release (fill) paths, so this can:
- Block a legitimate solver from ever collecting escrowed input tokens after filling an order (loss of solver funds / broken settlement), or
- Block a user from ever getting a timeout refund, if a single co-escrowed token becomes non-transferable.

### Impact Explanation
This breaks the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" invariant — here, funds don't move at all, they get permanently stuck. Because the loop is atomic and there is no mechanism to isolate the reverting token, an entire order's escrow (potentially including unrelated ERC-20s and the accumulated protocol fee balance in `TRANSACTION_FEES`) becomes irrecoverable. This satisfies the "loss/lock of funds" impact category in the bounty scope. Multiple orders sharing the same problematic token type (or any order containing an intentionally malicious token supplied by its own placer) are all exposed.

### Likelihood Explanation
An unprivileged user fully controls the `inputs` token list when calling `placeOrder` (no allowlist enforcement of input token addresses is evident in the reviewed code), so constructing an order with one benign-looking token that reverts under some condition (or a standard blacklist token where the beneficiary later gets blacklisted by the token issuer, independent of Hyperbridge) is straightforward and requires no privileged role, malicious relayer, or prover — matching the "unprivileged attacker" requirement. The likelihood of a full self-inflicted lock is high; likelihood of griefing another party's escrow depends on whether tokens are shared across orders, but at minimum a user can lock their own placed order's total escrow (including fees) by picking such a token, and — more critically — a solver who fills an order with such an input token will find their earned escrow permanently unrecoverable through no fault of their own.

### Recommendation
Change `_withdraw`/`withdraw` to be resilient to a single token's transfer failure:
- Wrap each token transfer in a try/catch (or use a low-level call with a success flag) and, on failure, skip that token, keep it escrowed, and emit a `TransferFailed`/`TokenSkipped` event instead of reverting the whole function.
- Provide a follow-up, per-token retry/claim entrypoint so a beneficiary can retry a single previously-failed token transfer without needing to re-run the full withdrawal (mirrors the report's recommendation of giving operators/beneficiaries a way to remove/bypass a bad entry rather than having it block the whole batch).
- Alternatively, decouple `TRANSACTION_FEES` and each `body.tokens[i]` release into independent external calls/transactions so a bad token cannot hold hostage the rest of the escrow.

### Proof of Concept
1. Deploy a malicious ERC-20 `EvilToken` whose `transfer` reverts whenever `to == solverAddress` (or reverts unconditionally after a flag is flipped by the token owner post-deployment, simulating a blacklist/pause).
2. User calls `placeOrder` with `inputs = [ {token: USDC, amount: X}, {token: EvilToken, amount: Y} ]`.
3. A solver fills the order; escrow for both USDC and EvilToken plus accumulated fees is now held under the order's commitment in `_orders[commitment][...]`.
4. When the withdrawal/redeem path triggers `_withdraw(body, false, true)` to pay out the solver's escrow, the loop reaches the `EvilToken` transfer, which reverts.
5. The entire `_withdraw` call reverts — the USDC portion (and fees) that would have succeeded are never paid out, and there is no alternate function to release only the USDC leg. The solver's legitimate USDC escrow is now permanently locked behind the malicious token.

Note: I could not fully trace every caller of `_withdraw` (e.g., the exact `onGetResponse`/`onAccept` wiring in `ExtrinsicIntents.sol`/`IntrinsicIntents.sol`) due to tool/file-read errors in the final iteration, so the exact set of external call paths that reach this function is based on the tron-fork equivalent (`onGetResponse` → `withdraw(body, true)` [3](#0-2) ) and the doc comment on `_withdraw` itself; a Devin session with full file access should confirm all invocation sites before remediation.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

        uint256 len = body.tokens.length;

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));

            if (token == address(0)) {

                if (!success) revert TransferFailed();
            }
