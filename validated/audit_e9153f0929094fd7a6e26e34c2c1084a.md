### Title
Deposits sent to internal offset addresses are misclassified as `Change`/`Forwarded`/`Branch` and never reported as external deposits - (File: `processor/src/networks/bitcoin.rs`)

### Summary
`Bitcoin::get_outputs` classifies every scanned output purely by which `script_pubkey` it matched, mapping the matched offset to an `OutputType`. Because the `Branch`, `Change`, and `Forwarded` offset scalars are deterministic, publicly derivable constants (`hash_to_F(KEY_DST, b"branch"/"change"/"forward")` over a publicly known group key), any unprivileged party can send BTC to an address the processor treats as *internal* traffic. The same address-space is thus conflated between "external user deposit" and "protocol-internal output" — exactly the bug class in the reference report, where one identifier (the wrapped-native-token address) is silently overloaded between two modes and the wrong branch is taken.

### Finding Description
The scanner (`networks/bitcoin/src/wallet/mod.rs:199-214`) matches outputs only on `output.script_pubkey` against `self.scripts`, a `HashMap<ScriptBuf, Scalar>` populated by `Scanner::new` (external key, `Scalar::ZERO`) and `register_offset` for the three internal offsets. In `processor/src/networks/bitcoin.rs`, `scanner()` registers all four offsets and builds `kinds: HashMap<Vec<u8>, OutputType>` keyed by offset repr (lines 313-346). `get_outputs` then does:

- `let kind = kinds[offset_repr_ref];` — classification decided solely by the matched script/offset (line 695).
- `extract_serai_data` (the `InInstruction` memo a depositor attaches) is only assigned `if output.kind == OutputType::External` (lines 730-734).

So a transaction paying the `Change`, `Branch`, or `Forwarded` offset address — addresses any party can derive from the public group key and the fixed `KEY_DST` hashes — is emitted as an internal output. Per `OutputType` documentation (`processor/src/networks/mod.rs:48-82`), `External` outputs are "processed/sent up to Substrate" (credited as deposits), while `Change` is silently added to the UTXO pool and `Forwarded` is treated as a rotation payment from the prior multisig. There is no second signal (e.g., presence/shape of the `InInstruction`, or whether the TX spends a multisig input) used to distinguish a genuinely internal output from an externally-sent one; the sole discriminator is which script was matched — the same kind of single-field conflation as `_tokenAddress == wrappedNativeToken`.

### Impact Explanation
- An external sender paying the `Change`/`Forwarded`/`Branch` address has their funds absorbed into the multisig's UTXO set **without ever being reported as an `External` output**: no `data` is attached and no deposit is emitted to Substrate. The BTC is received but the depositor is never credited — funds received that are not credited to anyone.
- For `Forwarded` specifically, an attacker can fabricate what appears to be a forwarding output from the retiring multisig (the comment on `Branch` even acknowledges "Eve … has sent us a forged TX"), polluting the internal-output accounting and the scheduler's amount-keyed plan queues (`queued_plans`/`plans` keyed by `u64` amount only, `processor/src/multisigs/scheduler/utxo.rs:36-37`).
- Unlike the reference bug (a revert), the failure here is silent misattribution rather than an explicit error, making it harder to detect and recover from.

### Likelihood Explanation
Medium-low but reachable: it requires no privileged position, only an on-chain Bitcoin transaction crafted by an unprivileged party (either a mistaken/maliciously-instructed depositor, or an attacker deliberately dusting the internal offsets). The internal addresses are trivially computable: `p2tr(group_key + G*hash_to_F(KEY_DST, tag))`. Harm to a *self-inflicted* sender is the clearest case; protocol-level harm via `Forwarded` spoofing depends on downstream handling of forwarded outputs, which I could not fully trace within this iteration.

### Recommendation
Disambiguate the two roles the same script-space is forced to play, mirroring the report's fix of introducing a separate identifier for the native token:

- Keep the internal offset addresses, but do not classify by script alone. Require `Change`/`Forwarded`/`Branch` classification to be corroborated — e.g., only treat an output as internal if the spending transaction consumes a known multisig input (for `Change`/`Branch`, which are only ever produced by Serai's own transactions) or matches a registered forwarding eventuality (for `Forwarded`).
- Alternatively/additionally, treat any output arriving in a transaction *not* authored by the multisig as `External`, so externally-sent funds are always surfaced to Substrate (credited or at least logged), rather than silently absorbed into the internal UTXO pool.

### Proof of Concept
```rust
// Attacker (or confused depositor) with only public data:
let key = <public group key>; // published multisig key
let change_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change");
let change_addr = address_from_key(key + (ProjectivePoint::GENERATOR * change_offset));

// Send BTC to change_addr with an attached InInstruction memo.
// In get_outputs (processor/src/networks/bitcoin.rs:686-739):
//   scanner.scan_transaction matches script_pubkey -> offset == change_offset
//   kinds[change_offset.to_repr()] -> OutputType::Change
//   `if output.kind == OutputType::External` is false -> `data` is dropped
//   Output is pooled as internal change; no deposit is ever reported to Substrate.
// The depositor's funds are inside the multisig yet uncredited.
```
Note: verification that a spoofed `Forwarded` output additionally corrupts rotation accounting was not completed; the misclassification path itself is fully supported by `wallet/mod.rs:199-214`, `bitcoin.rs:313-346`, and `bitcoin.rs:686-739`.
