### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s without a maturity check - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`Scanner::scan_block` iterates over every transaction in a block, including `block.txdata[0]` (the coinbase), and emits a `ReceivedOutput` for any output whose `script_pubkey` matches a registered script. Coinbase outputs are unspendable for 100 blocks, yet they are reported identically to normal outputs with no coinbase/maturity discrimination in the returned `ReceivedOutput` type. [1](#0-0) 

### Finding Description

The external bug class is a missing state precondition check: `RFPSimpleStrategy#_distribute` pays a milestone without verifying `milestoneStatus == Status.Pending`, so a rejected/unsubmitted milestone can still be paid.

The analog in Serai is that `Scanner::scan_block` treats outputs as received-and-usable without verifying they are in a spendable state. `scan_transaction` matches only on `output.script_pubkey` (`self.scripts.get(&output.script_pubkey)`), and `scan_block` feeds it every transaction including the coinbase:

```rust
// networks/bitcoin/src/wallet/mod.rs:221-227
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

`ReceivedOutput` (lines 90–97) carries only `offset`, `output`, and `outpoint` — there is no field distinguishing a coinbase output, and no `is_coinbase()` check on the transaction before its outputs are emitted. Nothing else in `networks/bitcoin/src` filters coinbase transactions; the only mitigation is a doc comment (lines 218–220) telling callers to post-filter or call `scan_transaction` on `block.txdata[1..]`. Any consumer that calls the natural API (`scan_block`) receives an output that cannot be spent until maturity.

### Impact Explanation

A `ReceivedOutput` is the object consumed downstream to build `SignableTransaction` inputs. A coinbase output reported by `scan_block` references an outpoint that the Bitcoin network will reject as a transaction input for 100 blocks. The result is funds reported received that are not spendable: the wallet/scanner will credit the multisig balance, and any spend built from it produces a transaction that fails relay (`bad-txns-premature-spend-of-coinbase`), causing denial-of-service for the batch containing that input and stuck funds accounting.

### Likelihood Explanation

Reachability requires the payer to be a miner: an unprivileged party who mines a Bitcoin block can set the coinbase payout script to Serai's P2TR `script_pubkey` (registered via `Scanner::new`/`register_offset`, both public). Mining a block is costly but requires no privilege, no collusion, and no malformed input — the coinbase transaction is entirely valid consensus data. However, the failure mode is partially mitigated by the documented warning on `scan_block`, so integrators who heed the comment and post-filter are unaffected. That caveat is a documented API trap rather than a caller-supplied-input requirement, so I rate this Medium, at the lower confidence end — it hinges on a downstream consumer using `scan_block` directly.

### Recommendation

Enforce the state check inside the library rather than relying on a doc comment:

- In `scan_block`, skip `block.txdata[0]` if `block.txdata[0].is_coinbase()`, or accept a `block_height`/confirmation parameter and mark immature outputs.
- Alternatively, add an `is_coinbase: bool` (or maturity height) field to `ReceivedOutput` so consumers cannot mistake an immature output for a spendable one.

### Proof of Concept

```rust
// Conceptual PoC against networks/bitcoin/src/wallet/mod.rs
// A miner creates a block whose coinbase pays to Serai's P2TR script:
let key: ProjectivePoint = /* the multisig group key */;
let script = p2tr_script_buf(key).unwrap();

let coinbase_tx = Transaction {
  input: vec![TxIn {
    previous_output: OutPoint::null(), // coinbase input
    ..Default::default()
  }],
  output: vec![TxOut { value: Amount::from_sat(100_000), script_pubkey: script }],
  ..Default::default()
};
let block = Block { header: /* ... */, txdata: vec![coinbase_tx] };

let scanner = Scanner::new(key).unwrap();
let outputs = scanner.scan_block(&block);
// outputs.len() == 1, a ReceivedOutput is emitted even though the outpoint
// is unspendable for 100 blocks. Any SignableTransaction built from it is
// rejected by the network as a premature coinbase spend.
assert_eq!(outputs.len(), 1);
```

The root cause is that `scan_transaction` (lines 199–214) checks only `script_pubkey` membership and `scan_block` (lines 221–228) applies no transaction-level status check — the same "missing status check on an object before acting on it" flaw as the original `RFPSimpleStrategy` report.
