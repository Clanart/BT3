### Title
Reward-tier gaming via `mWomSV.startUnlock` manipulation of `getUserTotalLocked` lets an unprivileged user repeatedly re-earn low-tier vlMGP reward multipliers from `ArbWomUp3.incentiveDeposit` - ([File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3.getRewardAmount` (used by `incentiveDeposit` with `_mode == 2`) computes the marginal reward for a new WOM deposit as `tieredReward(newAmount + mWomSV.getUserTotalLocked(account)) - calDoubledCounted(account)`, both of which read `mWomSV.getUserTotalLocked` live at call time instead of tracking a persistent "amount already rewarded" per user. Because `mWomSV.startUnlock` is a public, unguarded function that immediately removes the amount from `getUserTotalLocked` (moving it to cooldown) with no delay, a user can shrink their apparent locked balance between two `incentiveDeposit` calls and repeatedly collect low-tier reward multipliers for WOM that was never actually removed from the reward-tier system, and eventually just gets unlocked back to the user after the cooldown.

### Finding Description
`incentiveDeposit` calls `this.getRewardAmount(_amount, msg.sender, _mode==2)` **before** performing `_deposit`, which for `_mode == 2` locks (effectively) the entire converted WOM amount into `mWomSV` for the caller: [1](#0-0) 

The tiered reward math is: [2](#0-1) 

and the "already counted" reward for the existing position is: [3](#0-2) 

Both functions call `mWomSV.getUserTotalLocked(_account)`, which explicitly **excludes** any amount currently in cooldown: [4](#0-3) 

`mWomSV.startUnlock` is a public, unprivileged function that instantly decreases `getUserTotalLocked` by moving the chosen amount into a cooldown slot — the underlying mWom tokens remain custodied by `mWomSV`, but they no longer count toward "locked" balance immediately (no delay is required to trigger this state change, only to complete `unlock()` afterwards): [5](#0-4) 

Exploit flow:
1. Attacker calls `incentiveDeposit(amount1, ratio, true, 2)`. `getUserTotalLocked` is ~0, so `getRewardAmount` grants the full low-tier (highest multiplier bracket, since low tiers usually have larger multiplier relative to amount, or at minimum the bracket up to `amount1`) reward, and `_deposit` locks the WOM-equivalent mWom into `mWomSV` for the attacker.
2. Attacker immediately calls `mWomSV.startUnlock(amount1)` directly (no relation to `ArbWomUp3`, fully permissionless). This drops `getUserTotalLocked(attacker)` back toward 0 instantly, with the tokens merely parked in a cooldown slot inside `mWomSV`.
3. Attacker calls `incentiveDeposit(amount2, ratio, true, 2)` again. Because `getUserTotalLocked` has been artificially reset, `calDoubledCounted` subtracts almost nothing, and `getRewardAmount` again computes the reward as if this were a fresh low balance, granting another full low-tier reward for `amount2` even though the attacker's earlier `amount1` is still economically staked (in cooldown) and will fully return to them once the cooldown elapses.
4. This cycle (deposit → `startUnlock` → deposit) can be repeated to accumulate vlMGP rewards far beyond `rewardMultiplier[finalTier] * totalDeposited / DENOMINATOR`, because the contract has no persistent bookkeeping of cumulative reward already paid to an account — only a stale/manipulable snapshot of `mWomSV.getUserTotalLocked`. Notably, the contract even has a `bracketRewarded` mapping stub for this purpose that is explicitly marked `// not in use`: [6](#0-5) 

No existing modifier (`nonReentrant`, `whenNotPaused`) prevents this, since the two `incentiveDeposit` calls and the intervening `mWomSV.startUnlock` call are three separate, non-reentrant top-level transactions from the attacker; the vulnerability is a logic/state-tracking gap, not a reentrancy issue.

### Impact Explanation
This results in theft of unclaimed vlMGP reward paid out of `ArbWomUp3`'s MGP balance (`vlMGP.lockFor(rewardToSend, msg.sender)` at [7](#0-6) ), draining the finite MGP the program allocated for rewarding real net-new WOM commitment. Since `getRewardAmount` caps output at the contract's current MGP balance (`mgpleft`) [8](#0-7) , the practical effect is that the attacker can drain the reward pool disproportionately faster than legitimate depositors, exhausting funds meant for genuine new stakers — a theft of unclaimed yield from the protocol's reward budget.

### Likelihood Explanation
- Requires only WOM tokens the attacker already holds (no privileged role).
- All calls used (`incentiveDeposit`, `mWomSV.startUnlock`) are public/external and unguarded against this pattern.
- No flash loan or MEV timing is even required — the loop can be executed slowly, once per cooldown-independent cycle (since `startUnlock` itself has no cooldown to trigger, only `unlock()` to retrieve tokens does).
- Fully repeatable, bounded only by the reward pool's remaining MGP balance and gas cost.

### Recommendation
Track cumulative reward already granted per account persistently (e.g., actually use the existing `bracketRewarded` mapping, or record a monotonically non-decreasing "high-water mark" of locked/rewarded WOM per account) instead of deriving the "already counted" baseline from the live, attacker-manipulable `mWomSV.getUserTotalLocked`. Alternatively, have `getRewardAmount`/`calDoubledCounted` use a value that also includes amounts in cooldown (`balanceOf`, which sums locked + cooldown) so that `startUnlock` cannot lower the tier baseline, and/or require that `ArbWomUp3` be the exclusive locker for these positions with its own ledger of amounts it has already rewarded per user.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbWomUp3`, `mWomSV`, `mgp`, `wom`, `mWom`, a mock `smartWomConvert`, and `vlMGP` mocks/mocks-lite versions consistent with existing test harness (see `mocks/wombat/*`), with `setMultiplier` configured with at least two tiers (e.g., tier0=0 mult=X, tier1=T mult=Y, Y<X i.e. lower tiers pay more per-unit, or any configuration where per-unit reward is non-flat).
2. Fund `ArbWomUp3` with a fixed MGP balance `R`.
3. Attacker mints/holds WOM `2*amount1` where `amount1` is sized to land in tier0.
4. Call `incentiveDeposit(amount1, ratio, true, 2)` from attacker; record `vlMGP` locked amount `r1` and confirm `mWomSV.getUserTotalLocked(attacker) ≈ amount1`.
5. Call `mWomSV.startUnlock(amount1)` from attacker; assert `mWomSV.getUserTotalLocked(attacker)` drops back to ~0 while tokens remain in `mWomSV` (cooldown).
6. Call `incentiveDeposit(amount1, ratio, true, 2)` again; record `vlMGP` locked amount `r2`.
7. Assert `r1 + r2 > rewardMultiplier[finalTierFor(2*amount1)] * (2*amount1) / DENOMINATOR`, proving the cumulative reward exceeds what a single continuous deposit of `2*amount1` would have earned — violating the conservation invariant stated in the question.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
