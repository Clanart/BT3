### Title
Presumed deposit origin taken solely from the first input's spent output assumes all inputs share one owner - (File: processor/src/networks/bitcoin.rs)

### Summary
Analogous to the SimpleTokenSale `reclaimTokens` bug — which sent tokens to the `Trustee` contract's `owner` under the unchecked assumption it equaled the `Token` contract's `owner` — the Bitcoin network layer attributes a deposit's "presumed origin" to whoever funded `tx.input[0]`, under the unchecked assumption that the first input's owner is the party responsible for the entire transaction (including the Serai-bound outputs and the InInstruction data). No check verifies that the entity paying to Serai is the same entity that owns `input[0]`.

### Finding Description
In `get_outputs`, after scanning a transaction for outputs paying to the multisig's scripts, the code determines `presumed_origin` by resolving only `tx.input[0].previous_output` and taking that prevout's `script_pubkey` as the origin `Address`:

```rust
// processor/src/networks/bitcoin.rs:714-729
let spent_output = {
  let input = &tx.input[0];
  let mut spent_tx = input.previous_output.txid.as_raw_hash().to_byte_array();
  spent_tx.reverse();
  ... tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
};
Address::new(spent_output.script_pubkey)
```

This `presumed_origin` is then stamped onto every scanned output of the transaction (line 735). The in-code comment already acknowledges the assumption is shaky — noting the origin may be "the P2WSH output embedding the InInstruction" rather than a normal sender output — yet the code still unconditionally attributes origin to `input[0]`'s funder.

Bitcoin transactions can have inputs signed by multiple independent parties (CoinJoin, PayJoin, collaborative/batched spends). In such a transaction, `input[0]`'s owner is not necessarily the party who created the Serai deposit or who controls the embedded instruction data. The code equates "owner of input[0]" with "owner of the deposit", the same incorrect-identity-equation as `owner` vs `tokenContract.owner` in the report.

### Impact Explanation
`presumed_origin` is the address Serai associates with the deposit for refund/attribution purposes (refunds on failed `InInstruction`s are routed back to this origin). An attacker can craft a multi-input transaction — e.g., a PayJoin/CoinJoin where another participant's UTXO occupies `input[0]`, or any transaction the attacker gets a third party to co-sign — such that:

- Funds credited against an `InInstruction` carrying attacker-chosen `data` are attributed to a different party's address (the victim's prevout script).
- On a refund path, funds may be sent to an address the depositor does not control, or conversely a victim's deposit can be attributed to an attacker's script so subsequent refund logic pays the attacker for the victim's funds.

This yields "funds reported received" with a wrong spendable-by identity — deposits and refunds can be systematically misattributed/misrouted, enabling theft or loss of refunds.

### Likelihood Explanation
Reachable by any unprivileged party: constructing a multi-input Bitcoin transaction paying to a Serai address with `input[0]` funded by a co-signer other than the instruction's author only requires a standard collaborative-spend flow (PayJoin-style), not any validator compromise. Impact requires the protocol to act on `presumed_origin` for refunds/attribution, which is its documented purpose; severity is Medium (misattribution/misrouted refunds rather than direct key compromise).

### Recommendation
Do not derive a single origin from `input[0]` unconditionally. Either collect the origins of all inputs and reject multi-party transactions (distinct input prevout script families), or refuse to assign a `presumed_origin` when inputs are not demonstrably controlled by the same entity (e.g., require all input scripts equal, or require an explicit refund address inside the InInstruction data rather than inferring it from the transaction graph).

### Proof of Concept
```rust
// Conceptual: attacker Alice wants a deposit refunded to her, funded partly by victim Bob.
// Alice and Bob co-sign (PayJoin/CoinJoin-style) a TX where input[0] spends Bob's UTXO:
Transaction {
  input: vec![
    TxIn { previous_output: bob_outpoint, .. },       // index 0: Bob's UTXO
    TxIn { previous_output: alice_outpoint, .. },
  ],
  output: vec![
    TxOut { script_pubkey: serai_p2tr, value: deposit }, // to Serai external address
    TxOut { script_pubkey: op_return_ininstruction_for_alice, value: 0 },
    ...
  ],
}
// Serai's get_outputs resolves input[0] -> Bob's script_pubkey and stamps
// presumed_origin = Bob's address on Alice's deposit carrying Alice's data.
// Refunds/attribution for Alice's instruction are then bound to Bob's identity.
// Symmetrically, placing the malicious instruction but crediting a victim as
// origin lets attribution be poisoned in either direction.
```
