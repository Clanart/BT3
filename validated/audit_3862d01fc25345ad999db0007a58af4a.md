### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes disproportionate heap allocation before input validation - ([File: crypto/dkg/src/lib.rs])

### Summary
The REXML advisory (CVE-2024-41946) is a resource-amplification bug class: a small untrusted input forces work/allocation vastly larger than the input itself. The analog in Serai is `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`, which trusts a two-byte `n` field from the input to size a `Vec::with_capacity` allocation and two deserialization loops before any bound check is applied.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` as raw little-endian `u16`s straight from the reader. `n` is fully attacker-controlled and can be as large as `u16::MAX` (65535). It is then used unvalidated in two places:

```rust
// crypto/dkg/src/lib.rs
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));   // ~2 MB allocation from a 2-byte field
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
...
let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
ThresholdKeys::new(
  ThresholdParams::new(t, n, i).map_err(io::Error::other)?,   // bounds checked only *after* the work
  ...
)
```

The `Vec::with_capacity(usize::from(n))` executes before a single scalar byte is read. A ~15–40 byte input (curve ID + `t`/`n`/`i` + interpolation tag `0`) with `n = 0xffff` immediately forces allocation of a ~2 MB vector (65535 × 32-byte field elements). `ThresholdParams::new(t, n, i)` — the only place `n` would be rejected as exceeding the supported set size — runs only after all reads complete, so it never gates the allocation. This mirrors the REXML pattern: a tiny length field controls memory consumption with no proportionality to actual input size.

### Impact Explanation
An unprivileged party able to feed bytes to `ThresholdKeys::read` (e.g., an untrusted key blob submitted to a sign / verify / key-loading path, per the accepted attack surface) can cause repeated multi-megabyte allocations at a cost ratio of roughly 130×–5000× input bytes per call. Issued in a loop, this creates sustained memory pressure and allocator churn on the victim process — a denial of service against a threshold-signing node — without needing a large bandwidth budget, matching the CWE-400/CWE-770 class of the original advisory.

### Likelihood Explanation
Likelihood depends on an integrator path deserializing `ThresholdKeys` from untrusted input; where such a path exists, exploitation is trivial — a single crafted buffer of under 64 bytes, repeatable indefinitely. The same pattern (`Vec::with_capacity` sized by an unvalidated length) is not mitigated elsewhere in the function, and no size cap exists between reading `n` and allocating.

### Recommendation
Validate `t`, `n`, `i` via `ThresholdParams::new` (or an explicit `n <= MAX_PARTICIPANTS` check) immediately after reading them, before the `Interpolation` branch. Replace `Vec::with_capacity(n)` with `Vec::new()` or cap the capacity at a protocol-maximum participant count, so the allocation cannot be driven by the length field.

### Proof of Concept
```rust
use std::io;
use dkg::{ThresholdKeys, Participant};
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ristretto; // any Ciphersuite

fn main() {
  // Crafted input: valid curve ID, t=1, n=0xffff, i=1, interpolation=Constant(0)
  let mut buf = vec![];
  buf.extend(u32::try_from(Ristretto::ID.len()).unwrap().to_le_bytes());
  buf.extend(Ristretto::ID);
  buf.extend(1u16.to_le_bytes());      // t
  buf.extend(u16::MAX.to_le_bytes());  // n = 65535
  buf.extend(1u16.to_le_bytes());      // i
  buf.push(0);                         // Interpolation::Constant

  // A <40-byte input forces Vec::with_capacity(65535) — ~2 MB allocated
  // before the first read_F fails on EOF.
  let res: io::Result<ThresholdKeys<Ristretto>> =
    ThresholdKeys::read(&mut buf.as_slice());
  assert!(res.is_err()); // fails *after* the oversized allocation
}
```

Caveat: I could not fully trace every call path from network input to `ThresholdKeys::read` within the in-scope crates; the finding assumes (per the allowed surface) that untrusted bytes can reach this function.
