## Title
Stale absolute-line-index selection bitmap after hunk expansion silently changes which lines are staged/discarded - (File: `app/src/ui/diff/text-diff-expansion.ts`, `app/src/models/diff/diff-selection.ts`, `app/src/lib/patch-formatter.ts`)

## Summary
The `TraitForgeNft` report is fundamentally about a piece of derived state (price) being computed against a counter (`generationMintCounts`/`currentGeneration`) that is mutated in the wrong order/place relative to the read, so the price no longer corresponds to the actual mint that is happening. GitHub Desktop has a structurally identical pattern: partial-staging line selections are keyed by an *absolute diff-line index* (`hunk.unifiedDiffStart + lineIndex`), but the "expand hunk" (load-more-context) feature shifts `unifiedDiffStart`/`unifiedDiffEnd` for hunks after the expansion point without ever recomputing or remapping the already-recorded selection indices held by `DiffSelection`. The index that used to point at a specific line the user explicitly (de)selected now points at a *different* line, and this stale index is what `formatPatch`/`formatPatchToDiscardChanges` uses to build the patch that is applied to the index and ultimately committed/pushed.

## Finding Description
`DiffSelection` stores per-line selection state purely as a `Set<number>` of "diverging" absolute line indices (`divergingLines`), with no notion of what content those indices represent: [1](#0-0) [2](#0-1) 

Those absolute indices are derived from `hunk.unifiedDiffStart + lineIndex`, both when the user toggles a checkbox and when the patch is generated: [3](#0-2) [4](#0-3) 

When the user clicks "Load more" to expand a hunk's context, `expandTextDiffHunk` inserts new context lines into the expanded hunk and then shifts `unifiedDiffStart`/`unifiedDiffEnd` for every hunk that comes after it by `numberOfNewDiffLines`: [5](#0-4) [6](#0-5) 

This new `ITextDiff` (with shifted `unifiedDiffStart` values) is stored only in the diff-rendering component's local state — it never touches the `WorkingDirectoryFileChange.selection` (the `DiffSelection` bitmap) that the user has already built up: [7](#0-6) 

The only place where selection state is reconciled with a changed diff is `updateChangesWorkingDirectoryDiff`, and that reconciliation is limited to recomputing which indices are *selectable* (to drop lines that no longer exist) — it does not shift/remap `divergingLines`, and it only runs when the working-directory diff is reloaded from Git (e.g., after a file-system change), not when a hunk is expanded in the UI: [8](#0-7) 

Net effect: after expansion, the same raw index number that used to identify "line N, an unwanted/sensitive change the user explicitly deselected" now identifies a different line (one of the newly inserted context lines, or a line from a later hunk that shifted into that slot). Since `formatPatch`/`formatPatchToDiscardChanges` blindly trust `selection.isSelected(absoluteIndex)` against the *new* hunk layout, the wrong lines end up included in (or excluded from) the patch that is `git apply --cached`'d to the index via `applyPatchToIndex`: [9](#0-8) 

## Impact Explanation
This is a silent corruption of what the user commits or pushes: a line the user thought they had deselected (e.g., a leftover debug secret, an unwanted change from a merge, or a line they intentionally chose not to include) can be silently re-included in the commit after expanding a hunk, or conversely a line the user intended to stage can be silently dropped. Because the UI still shows the checkbox states from before expansion is preserved conceptually but the underlying index/line mapping shifted, the user has no visual indication that their selection now applies to different content. Since the file being diffed (its exact line count/content, hence exactly how many lines shift by how much) is attacker-controlled content in a cloned/fetched repository, an attacker can craft file contents specifically to make deselected sensitive/malicious lines land on indices that will be re-selected after a routine "expand hunk" click, or to make a benign-looking hunk expansion silently drop a security check the reviewer deselected for exclusion.

## Likelihood Explanation
The hunk-expansion feature ("Load more"/context expansion) is a commonly used, ordinary part of the partial-staging review workflow — it is not an obscure code path. Any working directory diff with more than one hunk, or a hunk that isn't already showing full context, is eligible. The only user action required is expanding a hunk after having made a partial line selection, both of which are normal review actions on an attacker-influenced file (fetched/cloned repository content). No admin rights, local access, or social engineering beyond normal review of a diff are needed.

## Recommendation
When `expandTextDiffHunk`/`expandWholeTextDiff` shift `unifiedDiffStart`/`unifiedDiffEnd` for hunks, the corresponding `DiffSelection.divergingLines` for the affected file must be remapped in lock-step (shifting each recorded index by the same `numberOfNewDiffLines` delta applied to the hunk it belongs to), instead of leaving the selection bitmap keyed to pre-expansion indices. Alternatively, key `DiffSelection` by a stable line identity (e.g., old/new line number pair) rather than a position-dependent "absolute unified-diff index" that changes whenever hunks are merged, expanded, or reflowed.

## Proof of Concept
1. Working directory diff for a file contains two hunks; the second hunk starts at a position that is a candidate for merging with the first hunk if expanded ("Short" expansion type, per `getHunkHeaderExpansionType`).
2. The user reviews the diff and unchecks a specific `Delete`/`Add` line inside the second hunk (e.g., a line that removes a security check) — this records that line's absolute index (computed as `hunk.unifiedDiffStart + lineIndex` for the *pre-expansion* hunk layout) into `DiffSelection.divergingLines`.
3. The user clicks "Load more" on the first hunk to expand context, triggering `expandHunk` → `expandTextDiffHunk`. Because the gap is short, the two hunks merge (`shouldMergeWithAdjacent`), and the second hunk's lines are renumbered with a new `unifiedDiffStart` shifted by `numberOfNewDiffLines`; the app only calls `this.setState({ diff: updatedDiff })`, never touching `file.selection`.
4. The old divergent index recorded in step 2 now points at a *different* line in the merged hunk (e.g., a context line or a different Add/Delete line).
5. The user commits. `formatPatch` computes `absoluteIndex = hunk.unifiedDiffStart + lineIndex` against the *new* hunk and calls `file.selection.isSelected(absoluteIndex)` — the line the user actually deselected in step 2 is no longer excluded (a different line is excluded/included instead), so the patch applied via `applyPatchToIndex`/`git apply --cached` stages content the user did not intend, silently corrupting the resulting commit.

Note: I was not able to run the app to empirically confirm the exact merge/shift scenario end-to-end (this would need a live Desktop session with a crafted repository); the analysis above is based on tracing the index derivation and lack of remapping through `text-diff-expansion.ts`, `diff-selection.ts`, `patch-formatter.ts`, and `side-by-side-diff.tsx` in the indexed source.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
