Confirms the `resolve` in `v0-egroup.clar` errors with `ERR-NO-EGROUP-FOUND` (no fallback default egroup) if no mask matches, and `find` uses pure subset/bucket search with no protection for currently-open positions when `update` mutates `MASK`. This is enough to finalize the analog.

### Title
DAO `update` of an egroup silently reassigns already-open positions to a different (or no) LTV/liquidation configuration - ([File: mainnet/contracts/registry/v0-egroup.clar])

### Summary
`egroup.update` (mirrored in `local-testing/contracts/registry/egroup.clar` and `mainnet/contracts/registry/v0-egroup.clar`) lets the DAO change an existing egroup's `MASK` and risk parameters (`LTV-BORROW`, `LTV-LIQ-PARTIAL`, `LTV-LIQ-FULL`, penalties, curve) in place. This atomically deletes the old `MASK -> id` mapping from the `reverse` map/bucket and inserts the new one. Any position whose asset combination previously matched the old `MASK` is never re-pointed to any equivalent config; the next time `market.clar`'s `resolve`/`get-egroup` is invoked for that same, unchanged position mask, it is resolved against the *new* registry state — either landing on a different (validly ordered but unrelated) egroup or on no egroup at all. This mirrors the Audius `ServiceTypeManager`/`ServiceProviderFactory` bug: governance-driven config edits are not reconciled with already-committed per-account state (in Zest's case, a position's *effective* risk parameters, since Zest resolves the egroup live rather than caching a snapshot — but the update erases the very mapping that resolution depends on). [1](#0-0) 

### Finding Description
`resolve(mask)` calls `find(mask)`, which performs a subset/superset search across population-count buckets and returns `ERR-NO-EGROUP-FOUND` if nothing matches — there is no default/catch-all fallback in the actual code path (only mentioned as an aspiration in `docs/egroups.md`): [2](#0-1) 

`update` is DAO-gated but only validates the new egroup against the *superset LTV-ordering invariant* relative to other egroups — it performs no check on whether user positions are currently resolved to `this` id via `prev-MASK`: [1](#0-0) 

Because `MASK` is the *sole* key that ties a position's actual asset combination to its risk parameters, and Zest never stores a position-level snapshot of `LTV-BORROW`/`LTV-LIQ-PARTIAL`/`LTV-LIQ-FULL` (it always calls `.egroup resolve mask` fresh on every `borrow`, `liquidate`, `collateral-add`, and `get-user-position` call), an `update` that changes `MASK` for id `this` — while `prev-MASK` still describes the exact holdings of live borrowers — instantaneously and retroactively changes what risk parameters apply to those live positions, without their owners taking any action: [3](#0-2) 

Two failure directions follow directly from the `check-egroup-invariant` ordering rule (superset masks must have LTV ≤ subset masks' LTV):

1. **DoS / frozen bad debt**: If no other registered mask is a superset of a borrower's asset combination once `prev-MASK` is removed, every subsequent `resolve` for that borrower's mask reverts with `ERR-NO-EGROUP-FOUND`. Since `liquidate`, `borrow`, and `collateral-add` all call `(try! (get-egroup mask))`/`(try! (contract-call? .egroup resolve mask))` and propagate the error, the position becomes **permanently un-liquidatable** even while genuinely underwater — freezing lender funds and risking protocol insolvency.
2. **Unwarranted liquidation exposure**: If the borrower's mask now resolves to a different superset egroup (per the invariant, one with LTV values ≤ their old exact-match egroup), a position that was healthy under the old, more permissive LTV-LIQ-FULL/LTV-LIQ-PARTIAL thresholds can become instantly liquidatable under the new, stricter thresholds — with no oracle price move and no borrower action. Liquidators can then seize collateral plus the liquidation penalty from a position that was solvent moments earlier, i.e., theft of user collateral driven purely by a governance-timed registry edit landing on an existing wrong-egroup mask resolution.

Both paths trace to the same root cause as the Audius report: a registry-side "risk requirement" update is not reconciled against already-open positions that were implicitly relying on the pre-update mapping.

### Impact Explanation
- Direction 2 is **Critical**: direct theft of user collateral via forced liquidation triggered solely by a DAO-side egroup `update`, not by any real change in the user's collateral/debt/price.
- Direction 1 is also **Critical/High**: permanent freezing of funds — genuinely unhealthy positions become impossible to liquidate (`ERR-NO-EGROUP-FOUND` reverts every `liquidate` call for that mask), leaving bad debt on the books and risking protocol insolvency for depositors in the affected vaults.

### Likelihood Explanation
`update` is DAO/governance-gated (`check-dao-auth` requires `tx-sender == .dao-executor`), so this cannot be triggered by an ordinary attacker directly. However, unlike a pure "DAO misconfiguration" (explicitly out of scope), this is a **structural code defect**: even a well-intentioned, correctly-parameterized `update` call (e.g., re-tuning LTV for a mask that legitimately still has open positions, which is an expected/likely governance action as the protocol tunes risk over time) is unsafe by design, because the contract itself provides no mechanism to detect or block updates that orphan live positions. This is exactly the same "protocol allows a routine admin action that is unsafe against existing state" pattern as the Audius report, not a one-off misconfigured deployment.

### Recommendation
Follow the same remediation direction as the original Audius fix (PR #555): disallow in-place `MASK`/LTV mutation of an existing egroup id. Instead:
- Make egroups immutable once inserted (only `insert` new ones, versioned).
- Add an `active`/deprecated boolean so new positions can no longer be routed to a deprecated egroup id, while existing positions keep resolving to the original, unchanged `MASK -> id -> params` mapping until they are wound down.
- If dynamic re-pricing of open positions is truly intended, explicitly re-run the health check for every affected open position before finalizing an `update`, or require a migration path that lets affected borrowers exit before the change takes effect.

### Proof of Concept
1. DAO inserts Egroup `E` with `MASK = sBTC_collateral | USDC_debt`, `LTV-BORROW = 60%`, `LTV-LIQ-PARTIAL = 65%`, `LTV-LIQ-FULL = 70%` (as in `proposal-protocol-init.clar` egroup 0).
2. Alice deposits sBTC collateral and borrows USDC up to 68% LTV — healthy under `E`'s exact-match resolution.
3. DAO calls `egroup.update(E, { MASK: <different asset combo>, ...})` to retune a different pairing, or to fix a typo — this deletes the `reverse[old-MASK] -> E` entry and bucket slot for Alice's exact mask.
4. Next `resolve(Alice_mask)`:
   - If no other superset mask is registered for Alice's holdings, any subsequent `liquidate`/`borrow` call for Alice reverts with `ERR-NO-EGROUP-FOUND` — Alice's now-unhealthy position (if price drops) can never be liquidated, and vault lenders bear the loss.
   - If a superset egroup exists (e.g., a broader multi-asset egroup with `LTV-LIQ-PARTIAL = 40%` per the invariant), Alice's position at 68% LTV instantly becomes liquidatable under the new resolved parameters, and any liquidator can immediately call `liquidate` to seize her collateral plus penalty — with no change in her actual holdings or oracle prices.         (out (fold iter-find
                      actv
                      init)))

(define-public (update
                (this uint)
                (params {
                    MASK: uint,
                    BORROW-DISABLED-MASK: uint,
                    LIQ-CURVE-EXP: uint,
                    LIQ-PENALTY-MIN: uint,
                    LIQ-PENALTY-MAX: uint,
                    LTV-BORROW: uint,
                    LTV-LIQ-PARTIAL: uint,
                    LTV-LIQ-FULL: uint,
                  }))
  (let ((prev (lookup this))
        (id (get id prev))
        (new (try! (serialize-and-validate-input this params)))
        (prev-MASK (get MASK prev))
        (new-MASK (get MASK new)))

    (try! (check-dao-auth))        

    (try! (validate-superset-invariant
            new-MASK
            (get LTV-BORROW params)
            (get LTV-LIQ-PARTIAL params)
            (get LTV-LIQ-FULL params)
            (var-get nonce)
            (some this)))  ;; update: max-id=(var-get nonce) (check all IDs), exclude-id=(some this)

    (map-set registry id new)
    (asserts! (and
        (map-delete reverse prev-MASK)
        (remove-bucket prev-MASK)
      ) ERR-MASK-UPDATE-FAILED)

    (asserts! (and
        (map-insert reverse new-MASK id)
        (insert-bucket new-MASK))
      ERR-ALREADY-REGISTERED)
