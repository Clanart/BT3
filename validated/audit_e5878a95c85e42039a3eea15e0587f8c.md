### Title
Chia daemon RPC keyring-passphrase validation has no attempt limit or lockout, enabling unlimited local brute-force of the master passphrase - (File: chia/daemon/server.py)

### Summary
The Element Android CVE describes an authentication bypass where the app fails to enforce a lockout after too many failed PIN attempts, letting an attacker with local access brute-force the PIN. The Chia daemon has the analogous gap: the local daemon RPC endpoints that check the keyring master passphrase (`unlock_keyring` and `validate_keyring_passphrase`) perform no attempt counting, throttling, or lockout at all, unlike the CLI path which enforces `MAX_RETRIES = 3` with a fixed delay.

### Finding Description
`WebSocketServer.unlock_keyring()` and `WebSocketServer.validate_keyring_passphrase()` in `chia/daemon/server.py` call `Keychain.master_passphrase_is_valid(key, force_reload=True)` directly against whatever `key` value is submitted over the daemon websocket, and return a simple success/failure response with no state tracked between calls. [1](#0-0) [2](#0-1) 

The only place in the codebase that enforces a retry limit and delay (`MAX_RETRIES = 3`, `FAILED_ATTEMPT_DELAY = 0.5`) is the interactive CLI helper `obtain_current_passphrase()` in `chia/util/keyring_wrapper.py`, which is a client-side convenience for terminal prompts, not something the daemon RPC handler invokes or enforces. [3](#0-2) 

The underlying check itself, `FileKeyring.check_passphrase()`, simply attempts to decrypt the keyring content with the supplied passphrase and returns a boolean — there is no rate limiting, exponential backoff, or lockout counter maintained anywhere in this path. [4](#0-3) 

Any client that can open a websocket connection to the local daemon (i.e., possesses the daemon's mTLS client certificate) can therefore send an unbounded number of `unlock_keyring` / `validate_keyring_passphrase` requests, each testing one guessed passphrase, with no server-side attempt limit, cooldown, or account lockout stopping repeated retries.

### Impact Explanation
If an attacker has (or obtains) network/local access to the daemon socket along with valid daemon client TLS certs — e.g., via another local process, a compromised GUI/service component, or reuse of certs on disk — they can brute-force the master keyring passphrase without being throttled by the daemon itself. A successful guess unlocks the keyring, exposing all private keys (`check_keys()` runs post-unlock and private-key material becomes accessible via subsequent keychain RPCs), enabling unauthorized signing/spending of coins controlled by those keys. This satisfies the "concrete unsigned/unauthorized coin movement" bar because keyring compromise directly yields spend authority.

### Likelihood Explanation
Likelihood is constrained by the requirement that the attacker already hold a valid daemon mTLS client certificate to open the websocket at all — this is the primary access-control gate described in the daemon's TLS listener setup. Given that gate, however, there is no additional defense-in-depth (rate limiting/lockout) once connected, so the effective passphrase-guessing surface is unprotected. This mirrors the "local, low complexity, no privileges beyond initial access, no user interaction" profile of the original CVSS 5.1 rating.

### Recommendation
Add attempt-counting and lockout/backoff logic to the daemon-side `unlock_keyring` and `validate_keyring_passphrase` handlers in `chia/daemon/server.py` (or centrally in `KeyringWrapper`/`Keychain`), tracking failed attempts per connection/process and enforcing an increasing delay or hard lockout after a small number of consecutive failures, rather than relying solely on the CLI's client-side `MAX_RETRIES` prompt loop which the daemon RPC path bypasses entirely.

### Proof of Concept
1. Connect to the local daemon websocket with valid daemon client certs (as any local RPC client would).
2. Repeatedly send `validate_keyring_passphrase` (or `unlock_keyring`) messages with different guessed passphrases, as in the existing test `test_validate_keyring_passphrase_rpc`. [5](#0-4) 
3. Observe that each request is answered immediately with `{"success": False, "error": None}` for wrong guesses, with no increasing delay, error indicating remaining attempts, or lockout after any number of failures — unlike the CLI path bounded by `MAX_RETRIES`. [6](#0-5)

    async def unlock_keyring(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        success: bool = False
        error: str | None = None
        key: str | None = request.get("key", None)
        if type(key) is not str:
            return {"success": False, "error": "missing key"}

        try:
            if Keychain.master_passphrase_is_valid(key, force_reload=True):
                Keychain.set_cached_master_passphrase(key)
                success = True
                # Inform the GUI of keyring status changes
                self.keyring_status_changed(await self.keyring_status(), "wallet_ui")
            else:
                error = "bad passphrase"
        except Exception as e:
            tb = traceback.format_exc()
            self.log.error(f"Keyring passphrase validation failed: {e} {tb}")
            error = "validation exception"

def obtain_current_passphrase(prompt: str = DEFAULT_PASSPHRASE_PROMPT, use_passphrase_cache: bool = False) -> str:
    from chia.util.keyring_wrapper import KeyringWrapper

    """
    Obtains the master passphrase for the keyring, optionally using the cached
    value (if previously set). If the passphrase isn't already cached, the user is
    prompted interactively to enter their passphrase a max of MAX_RETRIES times
    before failing.
    """

    if use_passphrase_cache:
        passphrase, validated = KeyringWrapper.get_shared_instance().get_cached_master_passphrase()
        if passphrase:
            # If the cached passphrase was previously validated, we assume it's... valid
            if validated:
                return passphrase

            # Cached passphrase needs to be validated
            if KeyringWrapper.get_shared_instance().master_passphrase_is_valid(passphrase):
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(passphrase, validated=True)
                return passphrase
            else:
                # Cached passphrase is bad, clear the cache
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(None)

    # Prompt interactively with up to MAX_RETRIES attempts
    for i in range(MAX_RETRIES):
        colorama.init()

        passphrase = prompt_for_passphrase(prompt)

        if KeyringWrapper.get_shared_instance().master_passphrase_is_valid(passphrase):
            # If using the passphrase cache, and the user inputted a passphrase, update the cache
            if use_passphrase_cache:
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(passphrase, validated=True)
            return passphrase

        time.sleep(FAILED_ATTEMPT_DELAY)
        print("Incorrect passphrase\n")
    raise KeychainMaxUnlockAttempts

        """
        Attempts to validate the passphrase by decrypting keyring.data
        contents and checking the checkbytes value
        """
        if force_reload:
            self.cached_file_content = FileKeyringContent.create_from_path(self.keyring_path)

        try:
            self.cached_file_content.get_decrypted_data_dict(passphrase)
            return True
        except Exception:
            return False

    }

        "success": False,
        "error": "missing key",
    }

        "success": False,
        "error": None,
    }
