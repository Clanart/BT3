## Finding Assessment: Valid

### Title
Unvalidated `html_url` scheme from GitHub API repository object flows to `shell.openExternal` via `LinkButton` - (File: `app/src/lib/stores/repositories-store.ts`)

### Summary
`_upsertGitHubRepository` writes `gitHubRepository.html_url` directly into `IDatabaseGitHubRepository.htmlURL` with no scheme/protocol validation, and this value is later exposed as `GitHubRepository.htmlURL` throughout the UI layer, where it is passed as the `uri` prop to `LinkButton`, whose `onClick` handler calls `shell.openExternal(uri)` unconditionally.

### Finding Description
In `_upsertGitHubRepository`, the API-provided `html_url` field is copied verbatim into the persisted database record: [1](#0-0) 

No check exists at this call site (or anywhere upstream in `app/src/lib/api.ts` parsing of `IAPIFullRepository`) to confirm `html_url` begins with `https://` or `http://`. This stored value is later reconstructed into the in-memory `GitHubRepository` model and consumed by numerous UI components (e.g. `app/src/ui/app.tsx`, `app/src/ui/check-runs/ci-check-run-popover.tsx`, `app/src/ui/notifications/pull-request-checks-failed.tsx`) as a clickable link, ultimately rendered via `LinkButton`: [2](#0-1) 

`LinkButton.onClick` performs no scheme allow-listing before invoking `shell.openExternal(uri)`. The renderer-side `shell` wrapper (`app/src/lib/app-shell.ts`) simply forwards to the main-process `openExternal` IPC proxy without any URL validation: [3](#0-2) 

I was not able to locate a scheme-validation layer in the main process (`main.ts` / `main-process-proxy.ts`) that would filter non-`http(s)` schemes before calling Electron's `shell.openExternal`; the only main-process safety wrapper found (`app/src/main-process/shell.ts`) is `UNSAFE_openDirectory`, which is unrelated to `openExternal` and explicitly warns it must never be used with untrusted paths — reinforcing that no equivalent guard exists for `openExternal`.

### Impact Explanation
If a GitHub API (or GitHub Enterprise Server) response returns a repository object with a `html_url` using a non-http(s) scheme (e.g., `file://`, a custom protocol handler registered by another installed application, or an OS-level `javascript:`-adjacent handler on some platforms), that string would be persisted unmodified and later handed to `shell.openExternal`. Electron's `shell.openExternal` on Windows can invoke arbitrary registered protocol handlers or, in some historical Electron/OS combinations, be abused for command injection via crafted URIs. At minimum this breaks the intended invariant that only http(s) URLs reach `shell.openExternal`, and depending on the OS/registered handlers could lead to unexpected local application invocation.

### Likelihood Explanation
Exploitation requires the attacker to control or spoof a GitHub API response's `html_url` field (e.g., a malicious/compromised GHES instance, or a MITM on the API endpoint), which is within the stated in-scope threat model ("attacker controls...a GitHub API object"). No user interaction beyond clicking a rendered "View on GitHub"-style link is required, which is a normal, expected user action in the app.

### Recommendation
Validate `html_url` (and similarly `clone_url`) against an `https:`/`http:` scheme allow-list at ingestion time in `_upsertGitHubRepository` before persisting to `IDatabaseGitHubRepository`, rejecting or sanitizing values with other schemes. As defense in depth, add scheme validation inside `LinkButton.onClick` (or a shared `openExternal` wrapper) so any `uri` prop passed with a non-http(s) scheme is refused before reaching `shell.openExternal`.

### Proof of Concept
1. Stub an `IAPIFullRepository` object with `html_url: 'x-github-client://malicious'`.
2. Call `RepositoriesStore._upsertGitHubRepository(endpoint, apiRepo, false)`.
3. Assert `updatedGitHubRepo.htmlURL` at [4](#0-3)  equals the malicious value unchanged, and that this value flows into `GitHubRepository.htmlURL` returned by `toGitHubRepository`.
4. Render a `LinkButton` with `uri={repository.htmlURL}` and simulate a click; observe `shell.openExternal('x-github-client://malicious')` is invoked without any scheme check, per `LinkButton.onClick` at [5](#0-4) .
