### Title
Unvalidated `old_move_txid` in `ReplacementDeposit` allows minting a new N-of-N-backed vault UTXO with no real prior deposit - ([File: core/src/verifier.rs])

### Summary
`Verifier::is_deposit_valid` never verifies that `ReplacementDepositData.old_move_txid` actually names a real prior move-to-vault transaction that was spent by the security council multisig. An unprivileged attacker can self-fund a fresh outpoint with a taproot script matching `ReplacementDepositScript::new(nofn_xonly_pk, old_move_txid)` + `Multisig::from_security_council`, pick any arbitrary fabricated `old_move_txid`, and pass all of `is_deposit_valid`'s checks, causing verifiers to N-of-N presign a brand-new move-to-vault transaction backed by no real prior deposit.

### Finding Description
The claimed binding: for a legitimate `ReplacementDeposit`, `old_move_txid` must equal the txid of a real, prior move-to-vault transaction that the security council actually spent via `Multisig::from_security_council` to create the replacement outpoint.

`Verifier::is_deposit_valid` (core/src/verifier.rs:541-731) only performs these checks on a `DepositData`:
- security council equality with local config [1](#0-0) 
- watchtower/verifier/operator uniqueness and count limits [2](#0-1) 
- operator set membership consistency with the DB [3](#0-2) 
- that the deposit outpoint's on-chain scriptPubkey matches `get_deposit_scripts()` output, that its value equals `bridge_amount`, and that it is confirmed at or after `start_height` [4](#0-3) 

For `DepositType::ReplacementDeposit`, `get_deposit_scripts` builds the expected taproot leaves purely from `ReplacementDepositScript::new(nofn_xonly_pk, old_move_txid)` and `Multisig::from_security_council(security_council)` [5](#0-4) . Nothing in this function, nor anywhere else in `is_deposit_valid`, dereferences `old_move_txid` to check that it corresponds to an actual, previously-created move-to-vault transaction, nor that such a transaction was ever spent by the security council multisig into the current deposit outpoint. The check is purely local script-matching: any `old_move_txid` value (including a fabricated one) produces a self-consistent script, and as long as the attacker funds an outpoint with that exact scriptPubkey and `bridge_amount`, the check passes.

Exploit flow: the attacker picks an arbitrary Txid (e.g., their own unrelated confirmed Bitcoin transaction, or any 32-byte value formatted as a Txid), constructs `DepositType::ReplacementDeposit(ReplacementDepositData{ old_move_txid })`, computes the corresponding taproot address via `ReplacementDepositScript`+`Multisig::from_security_council`, funds that address with `bridge_amount` from their own wallet, and submits the deposit through `Aggregator::new_deposit` → `Verifier::deposit_sign`/`deposit_finalize`. Both call `is_deposit_valid` before signing [6](#0-5) [7](#0-6) , and since it never checks the binding, verifiers proceed to N-of-N sign the new move-to-vault transaction.

No other guard closes the gap: `is_deposit_valid` treats `BaseDeposit` and `ReplacementDeposit` identically in terms of on-chain script/value/height checks, and the code that would normally establish the "spent by security council" link (`create_replacement_deposit_txhandler`/`send_replacement_deposit_tx`) exists only as CLI/test tooling to *produce* legitimate replacement deposits — it is never invoked as a *validation* step inside `is_deposit_valid` or the deposit_sign/finalize call path.

### Impact Explanation
A successful attack lets an unprivileged party obtain a fully N-of-N presigned move-to-vault UTXO for the price of the `bridge_amount` self-funding (which they retain control over via the script structure, since they choose `old_move_txid` and control the funding tx) plus fees, with no genuine prior deposit or withdrawal record ever existing. This matches the Critical impact category: minting a vault entry / move-to-vault UTXO with no corresponding backing, since the resulting bridge-side accounting (Citrea vault credit derived from the move tx) would not correspond to any real BTC that "should" be locked as a replacement — the attacker's own self-funded UTXO becomes an officially bridge-controlled UTXO indistinguishable from a legitimate deposit. This is repeatable per attacker-chosen fabricated `old_move_txid` and does not require any operator, verifier, or security council collusion.

### Likelihood Explanation
The only precondition is the ability to broadcast a Bitcoin transaction funding a specific taproot script with `bridge_amount` and to talk to the aggregator's public gRPC (both within the stated attacker capability). No key compromise, no verifier/operator/security-council access is needed. Cost is simply the `bridge_amount` (which the attacker can structure so it circulates back to the same value being bridged) plus miner fees. This is a highly feasible, low-cost, repeatable attack given the described attacker capabilities.

### Recommendation
In `is_deposit_valid` (or `get_deposit_scripts`/a dedicated check called before it), for `DepositType::ReplacementDeposit`, verify that `old_move_txid` corresponds to a transaction that was: (1) a real move-to-vault transaction previously recorded in the verifier's DB/known deposit history, and (2) actually spent on-chain by an input satisfying `Multisig::from_security_council(security_council)` into the current deposit outpoint (i.e., trace that the deposit outpoint's funding transaction's input(s) spend `old_move_txid`'s output through the security council multisig path). Reject the deposit if this chain cannot be established.
