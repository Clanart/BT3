### Title
Unauthenticated shop identity spoofing via `params[:shop]` bypasses cryptographic session verification in legacy `EnsureInstalled` flow - (File: `app/controllers/concerns/shopify_app/ensure_installed.rb`)

### Summary
`ShopifyApp::EnsureInstalled#current_shopify_domain` derives the "authenticated" shop identity purely from the unauthenticated, attacker-controlled `params[:shop]` query parameter (only passed through format sanitization), rather than from a cryptographically verified session token (JWT) or HMAC-signed payload. `check_shop_known` then loads and trusts whatever offline/online session is on file for that domain, mirroring the reported `get_public_key()` pattern of treating an unverified client-supplied identity claim as an authenticated principal.

### Finding Description
In the legacy (non–token-exchange) authentication path of `shopify_app`, `EnsureInstalled` runs `check_shop_domain` → `check_shop_known` → `validate_non_embedded_session` as `before_action`s: [1](#0-0) 

`current_shopify_domain` is computed solely from `params[:shop]`, run through `ShopifyApp::Utils.sanitize_shop_domain` — a purely syntactic check (confirms the string looks like a `*.myshopify.com`/trusted domain), not a cryptographic proof of the caller's identity: [2](#0-1) [3](#0-2) 

`check_shop_known` then loads whatever previously-stored session exists for that domain and assigns it to `@shop`, again with no proof the current requester is that shop: [4](#0-3) 

Crucially, `validate_non_embedded_session` — the only step that makes a live call to Shopify to confirm the stored access token is still valid for that shop — is skipped entirely when the request is "loaded directly from admin" (i.e. simply carries `embedded=1` and `embedded_app?` is configured), which is also just a client-supplied param, not a verified claim: [5](#0-4) [6](#0-5) 

This is architecturally analogous to the reported vulnerability: an unauthenticated caller supplies a plaintext identity claim (`Authorization: PublicKey <value>` in the report vs. `?shop=<domain>&embedded=1` here), and the server treats it as sufficient proof of who is making the request, activating that shop's stored access-token session and granting access to controller actions gated by `EnsureInstalled` — without any nonce/challenge, HMAC, or JWT signature check tying the request to the claimed shop.

By contrast, the modern `TokenExchange`/`WithShopifyIdToken` path (used when `use_new_embedded_auth_strategy?` is true) properly derives shop identity from a signed JWT (`shopify_id_token`) verified via `ShopifyAPI::Auth::JwtPayload`, and `TokenExchange#reject_mismatched_requested_shopify_domain` cross-checks the `shop` param against the token-derived domain. The vulnerable pattern only exists in the legacy non-embedded/non-token-exchange branch that remains supported by the gem for backward compatibility.

### Impact Explanation
If an app is configured with the legacy `EnsureInstalled` flow (not the newer Token Exchange strategy) and is embedded, an attacker who knows or guesses a victim merchant's `*.myshopify.com` domain (often public/discoverable) can request any `EnsureInstalled`-protected controller action with `?shop=<victim>.myshopify.com&embedded=1`. This bypasses the live-session-validation call (`validate_non_embedded_session` is skipped for `embedded=1`) and activates the victim's stored offline session, letting the attacker's request execute application logic in the context of that shop's access token — a cross-shop authentication bypass with no cryptographic proof of possession of any secret, JWT, or HMAC.

### Likelihood Explanation
Moderate-to-high for apps still on the legacy (non-token-exchange) `EnsureInstalled` flow with `embedded=1` requests reachable directly (not routed only through the Shopify Admin iframe with actual signed App Bridge session tokens). Exploitability depends on the app not layering additional CSRF/Origin checks and on the shop domain being guessable/known, both realistic in practice since shop names are frequently public. Apps that have migrated to `use_new_embedded_auth_strategy?` (Token Exchange) are not affected, which limits but does not eliminate exposure across the ecosystem of apps using this gem.

### Recommendation
- Do not skip `validate_non_embedded_session` based solely on the client-supplied `embedded` param; always confirm the caller's identity via a signed session token (JWT) before trusting `params[:shop]`.
- Require and verify a cryptographically-bound session token (`WithShopifyIdToken`/`ShopifyAPI::Auth::JwtPayload`) for every request that activates a shop session, matching the approach already used in the Token Exchange strategy, and deprecate/harden the legacy `EnsureInstalled` path so that `params[:shop]` is only ever a hint, never sole proof of identity.
- Encourage/force migration to `use_new_embedded_auth_strategy?` (Token Exchange) as the default, since it already implements the correct signed-token verification and shop-domain cross-check (`reject_mismatched_requested_shopify_domain`).

### Proof of Concept
Given an app using the legacy `EnsureInstalled` concern (i.e., `ShopifyApp.configuration.use_new_embedded_auth_strategy?` is `false`) with an existing installed/offline session for `victim-shop.myshopify.com`:

```
GET https://target-app.example.com/protected_action?shop=victim-shop.myshopify.com&embedded=1
```

- `check_shop_domain` passes because `sanitize_shop_domain("victim-shop.myshopify.com")` returns a valid-looking domain (format check only).
- `check_shop_known` loads the stored session for `victim-shop.myshopify.com` and sets `@shop`.
- `validate_non_embedded_session` returns immediately because `loaded_directly_from_admin?` is true (`embedded_app?` configured and `params[:embedded] == "1"`), skipping the only live verification call.
- The controller action executes using `victim-shop`'s installed session/access token, with the request having supplied no cryptographic proof (no JWT, no HMAC) of being sent by or on behalf of that shop — mirroring the `get_public_key()` flaw where a bare `Authorization: PublicKey <value>` header was accepted as identity proof.       redirect_to(ShopifyApp.configuration.login_url) unless current_shopify_domain

    def check_shop_known
      @shop = installed_shop_session
      unless @shop
        if embedded_param?
          redirect_for_embedded
        else
          redirect_to(shop_login)
        end
      end
    end

    def shop_login
      url = URI(ShopifyApp.configuration.login_url)

      url.query = URI.encode_www_form(
        shop: params[:shop],
        host: params[:host],
        return_to: request.fullpath,
      )

      url.to_s
    end

    def validate_non_embedded_session
      return if loaded_directly_from_admin?

      client = ShopifyAPI::Clients::Rest::Admin.new(session: installed_shop_session)
      client.get(path: "shop")
    rescue ShopifyAPI::Errors::HttpResponseError => error
      ShopifyApp::Logger.info("Shop offline session no longer valid. Redirecting to OAuth install")
      redirect_to(shop_login) if error.code == 401
      raise error if error.code != 401
    end

        end
        nil
      end
