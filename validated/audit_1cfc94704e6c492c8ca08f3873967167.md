### Title
`init_module` verifier does not check the `entry` flag, allowing a private-entry `init_module` to remain externally callable after publish-time auto-init - (`aptos-move/aptos-vm/src/verifier/module_init.rs`)

### Summary
`verify_init_module_function` (and its legacy counterpart) enforce private visibility, zero return values, a single `signer`/`&signer` parameter, and zero type parameters. None of these checks reject the `is_entry` flag on the function definition. In Move, `entry` makes a function directly invocable via a user transaction **regardless of its declared visibility** — this is explicitly documented and enforced elsewhere in the codebase (the `unsafe_friend_package_entry` lint, the Move book, and the API layer's comment "Private entry functions are still callable by entry function transactions"). Consequently, a module author (or, more importantly, an attacker publishing a malicious package under their own address) can define:

```move
module 0x42::evil {
    entry fun init_module(s: &signer) { /* re-runs on demand */ }
}
```

This function is `Visibility::Private`, has 0 return values, exactly 1 `&signer` parameter, and 0 type parameters — so it passes `verify_init_module_function` cleanly at publish time.

### Finding Description
The VM's publish path invokes `init_module` automatically exactly once, immediately after a module is staged (checked via `unmetered_check_module_exists` and only run for brand-new modules), as seen in [2](#0-1) . That verifier function only checks visibility/return/param/ty-param shape: [3](#0-2) . Because `is_entry` is stored as a completely separate field from `visibility` in the loaded `Function` struct [4](#0-3) , a function can simultaneously be `Visibility::Private` and `is_entry = true`.

Normal entry-function transaction execution (`validate_and_execute_entry_function`) does not special-case the function name `init_module`; it only requires `function.is_entry_or_err()` to succeed [5](#0-4) . Since `entry fun init_module(s: &signer)` satisfies `is_entry_or_err()`, any account can submit a normal `EntryFunction` transaction targeting `0x42::evil::init_module` and re-execute it with an arbitrary signer (their own), any number of times after publication — directly contradicting the intended invariant that `init_module` is a VM-only, run-once-at-publish hook that user transactions can never reach. This is also corroborated by the API layer's own module-export logic, which explicitly documents that private entry functions remain externally callable: [6](#0-5) .

### Impact Explanation
Any module deployer (which, per the review's unprivileged-input framing, is effectively any account that can submit a publish transaction) can craft an `init_module` that both passes verification and remains a permanently re-invokable entrypoint. Depending on what logic the author places inside `init_module` (or, in a supply-chain/social-engineering scenario, what a malicious template/SDK encourages users to copy), this can be used to re-trigger "run-once" initialization semantics that downstream code or other modules assume execute exactly once — e.g., re-minting/resetting counters, re-registering capabilities, or bypassing constructs that rely on `init_module`'s publish-time-only guarantee. The severity is bounded by the fact that the attacker can only run this against modules under their own control (their own account's `init_module`), so it does not by itself let an attacker corrupt a *victim's* already-published module's init logic; the impact is scoped to breaking a security invariant relied upon by any code that assumes `init_module` cannot be called by users, which could matter for object/resource-account patterns whose owner or authority reasoning presumes single-execution semantics.

### Likelihood Explanation
Trivial to trigger — no special privileges beyond normal package publication are required, and it only requires appending the `entry` modifier to an otherwise-fully-compliant `init_module` function. No existing extended check (`extended_checks.rs::check_init_module`) or verifier check (`verify_init_module_function`/`legacy_verify_module_init_function`) rejects it, based on the code paths reviewed.

### Recommendation
Add an explicit check in both `verify_init_module_function` (move-vm runtime path) and `legacy_verify_module_init_function`, and in `extended_checks.rs::check_init_module`, rejecting `init_module` definitions where `is_entry`/`fdef.is_entry` is `true`, in addition to the existing visibility/signature checks.

### Proof of Concept
```move
module 0x42::evil {
    entry fun init_module(s: &signer) {
        // arbitrary logic that the author intends to run exactly once at publish time,
        // but which is actually callable by anyone, anytime, via a normal transaction:
        // 0x42::evil::init_module(sender_signer)
    }
}
```
Publish this module; `verify_init_module_function` accepts it because visibility is `Private`, it returns nothing, takes a single `&signer`, and has no type parameters. After publication, submit a standard `EntryFunction` transaction with `module = 0x42::evil`, `function = init_module`, no type args, no args (the VM auto-fills the transaction sender as the `&signer`) — this succeeds and re-executes `init_module`'s body, which the codebase's stated invariant claims should be impossible outside of the one automatic publish-time call.

**Note on scope of what I could verify**: I confirmed the verifier logic, the `is_entry`/`visibility` field separation, and the generic entry-function execution path (`validate_and_execute_entry_function`) does not special-case `init_module`. I did not find (nor did search surface) any additional guard elsewhere in the transaction-validation or prologue path that blocks entry-function transactions specifically named `init_module`; if such a guard exists outside the indexed portions of the codebase, it would neutralize this finding, and I'd recommend a Devin session with full repo access to grep exhaustively for any `"init_module"` string comparisons in the transaction validation/prologue code before treating this as fully conclusive.

pub(crate) fn verify_init_module_function(function: &Function) -> Result<(), VMStatus> {
    let err = |msg| Err(VMStatus::error(StatusCode::INVALID_INIT_MODULE, Some(msg)));

    if !function.is_private() {
        return err("init_module function must be private, but it is not".to_string());
    }

    if !function.return_tys().is_empty() {
        return err(format!(
            "init_module function must return 0 values, but returns {}",
            function.return_tys().len()
        ));
    }

    let param_tys = function.param_tys();
    if param_tys.len() != 1 {
        return err(format!(
            "init_module function should have a single signer or &signer parameter, \
             but has {} parameters",
            param_tys.len()
        ));
    }

    let arg_ty = &param_tys[0];
    if !arg_ty.is_signer_or_signer_ref() {
        return err(
            "init_module function expects a single signer or &signer parameter, \
             but its parameter type is different"
                .to_string(),
        );
    }

    if function.ty_params_count() != 0 {
        return err(format!(
            "init_module function expects 0 type parameters, but has {} type parameters",
            function.ty_params_count()
        ));
    }

    Ok(())
}
