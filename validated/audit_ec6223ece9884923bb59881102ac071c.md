### Title
Gasless swap admission relies on live, unprotected DEX spot price, allowing single-transaction AMM manipulation to bypass repayment collateral checks - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The Aloe report flags that `Borrower.liquidate()` trusts a spot oracle price with no manipulation-aware pause, letting a single actor move the price and trigger unintended liquidations. The closest reachable analog in this Kaia codebase is the `kaiax/gasless` module's `checkBalanceForSwap`, which validates a user's `GaslessSwapTx` (repayment sizing for gas lent by the block proposer) against the **live, current-block DEX reserves** of the `GaslessSwapRouter`/underlying AMM (`routerContract.GetAmountIn`), with no TWAP, staleness check, or manipulation-detection pause analogous to what Borrower.sol lacks for liquidation.

### Finding Description
`checkBalanceForSwap` in `kaiax/gasless/impl/tx_pool.go` (via `GetCheckBalance`, called during tx-pool admission/`PreAddTx`/`Ready`) computes the amount of token the user must have supplied for a `swapForGas` request by directly querying the AMM router for the current exchange rate: [1](#0-0) 

The check `swapArgs.AmountIn.Cmp(requiredAmountIn) < 0` only guards that the declared `amountIn` is *currently* sufficient to obtain `minAmountOut` per the router's live view of reserves — obtained via `GetAmountIn`, which is standard Uniswap-V2-style spot-price math with no time-weighting: [2](#0-1) 

`minAmountOut` must only be `>= amountRepay` (the amount the CN/proposer needs back for lending gas): [3](#0-2) 

Because this admission-time check and the final on-chain `swapForGas` execution both derive their pricing from the same manipulable pool reserves within (or across) a single block/bundle (`LendTxGenerator, ApproveTx, SwapTx` bundle built by `ExtractTxBundles`), an attacker who controls (or sandwiches) the pool used by `GaslessSwapRouter` can transiently shift reserves so that a small `amountIn` appears sufficient to satisfy `minAmountOut >= amountRepay` at admission/build time, while the true, unmanipulated market rate would not support the declared `amountIn`/`minAmountOut` relationship. This is the same class of bug as the report: a value-bearing decision (liquidation there; loan-repayment sizing/settlement here) is made from an oracle/spot-price source without a manipulation-resistant pause or TWAP guard.

### Impact Explanation
If the attacker can influence the AMM pool backing `GaslessSwapRouter` (e.g., by sandwiching the gasless bundle since bundles are asembled by the block builder using the current chain state, or by controlling both sides of the pool momentarily), they can get gas fees lent by the consensus node (`GaslessLenderMinBal`-funded CN) without providing an amount of token whose *true* value covers `amountRepay`. This is a fee-delegation-style abuse: the CN funds `LendTxGenerator` up front expecting `amountRepay` back via the swap, but the swap's sizing was validated against a manipulated rate, risking the lender (CN) being under-repaid or the repayment happening at a distorted worse rate for the protocol/CN. This constitutes value movement/fee abuse in the gasless subsystem, reachable by any ordinary token holder submitting a public RPC-visible gasless bundle.

### Likelihood Explanation
Medium. It requires the attacker to control or momentarily distort the specific liquidity pool that `GaslessSwapRouter.getAmountIn`/`getAmountsOut` reads (e.g., a low-liquidity or attacker-created pool for an allowed token, since `AllowedTokensFlag` can include "all" tokens by default: [4](#0-3) ), and to time the manipulation so it is reflected in the state read at `checkBalanceForSwap`/bundle-building time. Given the gasless module is explicitly designed to trust arbitrary allowed tokens and their DEX pricing without a manipulation-resistant price source, this is realistically triggerable by a single, unprivileged transaction sequence (flash-swap + gasless swap in the same block) rather than requiring any privileged/network-level access.

### Recommendation
- Use a manipulation-resistant price source (e.g., TWAP or an external oracle with staleness/deviation checks) instead of instantaneous `GetAmountIn`/`GetAmountsOut` reserve ratios when validating `minAmountOut`/`amountIn` sufficiency for `checkBalanceForSwap`.
- Add a deviation check between the price used at tx-pool admission time and the price at actual execution/bundle-building time; reject or re-validate if it moved beyond a safe threshold, similar to how the Aloe report recommends pausing liquidation/repayment when manipulation is detected.
- Consider requiring the swap's on-chain execution in `GaslessSwapRouter.swapForGas` to itself enforce a manipulation-aware minimum-output check anchored to a longer-window price rather than solely the caller-supplied `minAmountOut` compared to spot reserves.

### Proof of Concept
1. Attacker deploys or targets a low-liquidity pool for an "allowed" gasless token used by `GaslessSwapRouter`.
2. In the same bundle/block, attacker (or accomplice) executes a large swap against that pool to skew reserves so that `GetAmountIn(token, minAmountOut)` returns an artificially small `requiredAmountIn`.
3. Attacker submits `ApproveTx` + `SwapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` with `amountIn` just above the manipulated `requiredAmountIn`, satisfying `checkBalanceForSwap`'s checks at `kaiax/gasless/impl/tx_pool.go:128-141` and `102-120`.
4. The bundle (`LendTxGenerator, ApproveTx, SwapTx`) is built by `ExtractTxBundles` (`kaiax/gasless/impl/builder.go:28-72`) and executed; the CN has already fronted gas via `LendTxGenerator`, and the swap settles at the manipulated rate, netting the attacker a discounted/free gas-lending service relative to the token's real market value.

*Note: I was unable to inspect the Solidity source of `GaslessSwapRouter.sol` (only generated Go bindings were indexed) to confirm exactly how `swapForGas` enforces `minAmountOut` on-chain at execution time; if that contract independently re-derives the rate from a manipulation-resistant source, the practical exploitability may be lower than described. A Devin session with full repo access would be needed to confirm this contract-level detail.*

func (g *GaslessModule) checkBalanceForSwap(swapArgs *SwapArgs, swapNonce uint64) error {
	token := swapArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	g.gaslessInfoMu.RLock()
	swapRouter := g.swapRouter
	g.gaslessInfoMu.RUnlock()

	// tx.minAmountOut >= tx.amountRepay
	minAmountOut := swapArgs.MinAmountOut
	amountRepay := swapArgs.AmountRepay
	if minAmountOut.Cmp(amountRepay) < 0 {
		return fmt.Errorf("insufficient minAmountOut: minAmountOut=%s, amountRepay=%s", minAmountOut.String(), amountRepay.String())
	}

	if g.GaslessConfig.ShouldCheckSenderCode() {
		if g.getCurrentHasCode(swapArgs.Sender) {
			return errors.New("sender with code is not allowed")
		}
	}

	if g.GaslessConfig.ShouldCheckSwapAmount() {
		// tx.amountIn >= gsr.getAmountIn(minAmountOut)
		routerContract, err := kip247.NewGaslessSwapRouterCaller(swapRouter, bc)
		if err != nil {
			return err
		}
		// Required token amountIn, given the current exchange rate and the declared minAmountOut.
		requiredAmountIn, err := routerContract.GetAmountIn(nil, token, minAmountOut)
		if err != nil {
			return err
		}
		if swapArgs.AmountIn.Cmp(requiredAmountIn) < 0 {
			return fmt.Errorf("insufficient amountIn: have=%s, want=%s", swapArgs.AmountIn.String(), requiredAmountIn.String())
		}
	}
