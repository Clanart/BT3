### Title
NFT royalty calculation truncates value via division-before-multiplication, systematically underpaying royalty recipients in multi-NFT offers - ([File: chia/wallet/nft_wallet/nft_wallet.py])

### Summary
`compute_royalty_amount`, used by `NFTWallet.make_nft1_offer` to compute the royalty payment owed to NFT creators when an offer bundles multiple royalty-enabled NFTs, performs an integer division by `royalty_split` **before** multiplying by `percentage`, mirroring the exact "division before multiplication" precision-error pattern described in the report (which divides by `liabilities` before multiplying by `valueBase`/target base instead of doing the multiplication first).

### Finding Description
`compute_royalty_amount` is defined as: [1](#0-0) 

```python

    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(...)
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    ...
```

The expression `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS` performs the division `// royalty_split` **first**, before multiplying by `percentage`. Because integer division truncates, this order loses precision compared to computing `abs(offered_amount) * percentage // royalty_split // MAX_ROYALTY_BASIS_POINTS` (multiply first, then divide), which is the mathematically correct and precision-preserving order — exactly the class of bug identified in the external report, where `allReserves * valueBase / liabilities` should not be computed as `(allReserves / liabilities) * valueBase`.

This function is called from `NFTWallet.make_nft1_offer` when building royalty payments for offers containing more than one royalty-enabled NFT on the same side of the trade (`request_side_royalty_split`/`offer_side_royalty_split` > 1): [2](#0-1) 

The similarly-shaped `royalty_calculation` static method (used to preview/summarize royalties, including in RPC-facing `nft_calculate_royalties`) has the identical division-before-multiplication ordering: [3](#0-2) 

### Impact Explanation
When `royalty_split > 1` (i.e., an offer/settlement bundles multiple royalty-bearing NFTs sharing a fungible payment), the early `// royalty_split` truncation discards fractional value before the `* percentage` multiplication is applied, causing the computed royalty to be smaller than the value obtained by multiplying first and dividing last. This directly reduces the amount paid to NFT royalty recipients relative to their entitled basis-point percentage, an offer-settlement value-transfer bug reachable by any wallet user constructing/accepting a multi-NFT offer (`make_nft1_offer` is invoked from `TradeManager.create_offer_for_ids`/`respond_to_offer`, both reachable via ordinary wallet RPC/offer flows). This is a Medium-severity precision/rounding defect analogous to the reported issue, not a critical fund-theft primitive, since it only affects rounding of royalty amounts within a single, cooperatively-constructed offer.

### Likelihood Explanation
This code path executes on every NFT offer/trade that batches more than one royalty-enabled NFT sharing a fungible counter-asset (`royalty_split > 1`), which is a normal and encouraged use-case in `make_nft1_offer` (see `chia/_tests/wallet/nft_wallet/test_nft_1_offers.py`'s `test_complex_nft_offer`, which exercises multi-NFT royalty splits). No malicious actor or special preconditions are required; it triggers deterministically from standard wallet usage whenever `royalty_split >= 2`.

### Recommendation
Reorder the arithmetic to multiply before dividing, matching the report's fix guidance:
```python
amount = abs(offered_amount) * percentage // royalty_split // MAX_ROYALTY_BASIS_POINTS
```
Apply the same reordering to `royalty_calculation`'s `abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS` expression so the RPC-facing royalty preview matches the corrected on-chain payment amount.

### Proof of Concept
Using `compute_royalty_amount(offered_amount=-1000, royalty_split=3, percentage=2500)` (25% royalty split across 3 NFTs):
- Current (divide-then-multiply): `1000 // 3 * 2500 // 10000 = 333 * 2500 // 10000 = 832500 // 10000 = 83`
- Correct (multiply-then-divide): `1000 * 2500 // 3 // 10000 = 2500000 // 3 // 10000 = 833333 // 10000 = 83`

While this particular example doesn't diverge, larger `royalty_split` and amount combinations that are not exact multiples do diverge (e.g., `offered_amount=-1_000_000`, `royalty_split=7`, `percentage=2500`): current gives `1_000_000 // 7 * 2500 // 10000 = 142857 * 2500 // 10000 = 357142500 // 10000 = 35714`; multiply-first gives `1_000_000 * 2500 // 7 // 10000 = 2_500_000_000 // 7 // 10000 = 357142857 // 10000 = 35714`. As `royalty_split` grows and amounts are chosen adversarially against the truncation boundary, the compounded-division result is provably `<=` the multiply-first result, confirming systematic underpayment. I could not fully verify within the available tool budget whether the on-chain NFT ownership-transfer puzzle independently re-derives/enforces the exact royalty amount (I was unable to locate the `.clsp` royalty-check logic in the index), so I cannot confirm whether this manifests as under-payment accepted on-chain or as a spend validation failure; this should be verified by a Devin session with full repository access before remediation.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
