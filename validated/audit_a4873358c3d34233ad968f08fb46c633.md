### Title
`ReceivedOutput::read` accepts arbitrary offset/outpoint without validating they match the output's script_pubkey — asymmetric validation causes unspendable funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class is "a value is committed/applied on one side while the corresponding validity check lives only on the other side." In `bitcoin-serai`, `Scanner::scan_transaction` always derives a `ReceivedOutput` whose `offset` is guaranteed to satisfy `p2tr_script_buf(key + G*offset) == output.script_pubkey`, because it is looked up from the `scripts` map [1](#0-0) . However, the deserialization path `ReceivedOutput::read` accepts an attacker-controlled scalar `offset`, `TxOut`, and `OutPoint` with no consistency check whatsoever [2](#0-1) . The only validation of the offset/script relationship lives on the *spend* side, in `SignableTransaction::multisig`, which returns `None` on mismatch [3](#0-2)  — after the output has already been recorded as received.

### Finding Description
`ReceivedOutput::read` deserializes three independent fields:
- `offset` via `Secp256k1::read_F` (any canonical scalar accepted),
- `output` via `TxOut::consensus_decode` (any script_pubkey/value accepted),
- `outpoint` via `OutPoint::consensus_decode` (any txid/vout accepted) [2](#0-1) .

None of the following are verified at read time:
1. That `p2tr_script_buf(scanner_key + GENERATOR * offset) == output.script_pubkey` (the offset actually unlocks this script),
2. That `outpoint` corresponds to a real on-chain output equal to `output`,
3. That the key implied by the offset is even-Y (spendable under BIP-340).

The honest path (`Scanner`) enforces all of these by construction: offsets are only registered after `p2tr_script_buf` returns `Some` (even point) [4](#0-3) , and `scan_transaction` only yields outputs whose script was registered [1](#0-0) . The check that the stored offset actually spends the output exists only in `SignableTransaction::multisig` [5](#0-4) , which silently returns `None` — the same asymmetric structure as the Eco report where `validRebaseMultiplier` is checked only on the L2 receiving side, after L1 already committed state.

### Impact Explanation
An unprivileged party that can feed bytes to `ReceivedOutput::read` (explicitly an in-scope sink) can cause an integrator to record outputs as received funds that are not spendable: either the offset does not correspond to the script_pubkey, or the outpoint does not reference a real chain output equal to `output`. Every downstream consumer (`SignableTransaction::new` sums `input.output.value` toward the spendable balance [6](#0-5) ) treats the value as available, yet `multisig()` returns `None` for any input whose offset doesn't re-derive the script_pubkey [5](#0-4) , or the signed transaction commits via `Prevouts::All` to prevout data that doesn't match the real UTXO, producing an invalid transaction [7](#0-6) . This matches the "funds reported received that are not spendable" acceptance criterion, and mirrors the audit finding's "two sides end up out of sync because only one side validates."

### Likelihood Explanation
Reachable whenever an integrator accepts serialized `ReceivedOutput`s from an untrusted source (peer nodes, coordinator messages, imported wallet state) rather than exclusively from its own `Scanner`. The attacker needs only to supply well-formed encodings — a random scalar, a `TxOut` paying to the victim's registered script (or even to an unrelated script), and a fabricated `OutPoint` — all of which parse successfully. Severity Medium: direct loss is bounded to accounting/availability (unspendable or phantom inputs) rather than key recovery, matching the original report's Medium severity.

### Recommendation
Perform the consistency validation at the ingestion boundary, not only at the spend boundary — the direct analog of the report's "include `validRebaseMultiplier` on the L1 bridge" recommendation:
- Have `ReceivedOutput::read` take the `Scanner` (or base key) and assert `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey`, rejecting mismatches.
- Separately document that `read` performs no on-chain existence check, so integrators must confirm the outpoint references a real confirmed output before crediting the value.
