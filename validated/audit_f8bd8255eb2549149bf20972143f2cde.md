### Title
Relayer fee `Fees` balances become permanently unclaimable if the credited delivery address is a smart-contract wallet - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-ismp-relayer` credits accrued delivery fees to whatever address the destination chain's request receipt attributes as the deliverer, and only allows the exact holder of that address's private key to withdraw via a signature-gated `withdraw_fees` extrinsic. There is no path for any other account, nor any privileged/admin override, to move funds out of a `Fees` entry once credited. If the credited address is a smart-contract wallet (e.g. a Safe, AA account, or relayer-orchestration contract that has no ECDSA/Sr25519/Ed25519 private key), the accrued balance is permanently frozen, mirroring the `TimeLock.claim()` bug class where only the beneficiary itself may invoke the payout and an immutable-contract beneficiary can never do so.

### Finding Description
Fees accrue keyed by `(StateMachine, Vec<u8> address)` in [1](#0-0) . The address is derived purely from proof/receipt data — `decode_receipt_relayer` decodes whichever account is recorded as having delivered the message on the destination chain (an EVM `msg.sender`-style address, or a substrate signer/pubkey) [2](#0-1) . That address becomes the sole key that can later withdraw the accrued balance.

The only extrinsic that moves funds out of `Fees`, `withdraw_fees` → `Pallet::withdraw`, requires a signature that recovers to (or is signed by) that exact address: [3](#0-2) 

If `withdrawal_data.signature` doesn't verify against the stored `address`, the call fails; there is no alternate authorization path. Reviewing the pallet's `Config` and calls confirms no `AdminOrigin`/sudo-gated rescue or force-withdraw function exists for `Fees`: [4](#0-3) 

The same single-key claim requirement is repeated in the beneficiary-redirect path of `accumulate`, and in the treasury reward claims (`process_outbound_request_delivery_claim`, `process_outbound_consensus_delivery_claim`), all of which require a signature recoverable to a specific address with no fallback: [5](#0-4) [6](#0-5) 

This is the direct analog of the `TimeLock` report: the protocol picks a beneficiary identity from external data (here, "whoever's address the destination chain's receipt attributes delivery to") without any guarantee that identity is capable of producing a signature. A smart-contract relayer wallet — a legitimate, common operational setup (Gnosis Safe multisig, account-abstraction wallet, or an orchestration contract that submits delivery transactions on behalf of an operator) — can never produce `Signature::Evm`/`Signature::Sr25519`/`Signature::Ed25519` because it has no private key, so any fees credited to that address are permanently stuck.

### Impact Explanation
Any relayer that operates its delivery submissions through a smart-contract account (rather than a plain EOA/keypair) has all of its accrued protocol-paid delivery fees permanently locked in the `Fees` map with no recovery mechanism — neither self-service (no alternate signer/claim-by-proxy) nor governance (no admin override exists in the pallet). This is a genuine loss-of-funds condition inherent to the withdrawal design, matching the "funds may freeze" impact class of the original report, and it recurs across all three claim/withdrawal surfaces in this pallet (`withdraw_fees`, `accumulate`'s beneficiary redirect, and the outbound delivery reward claims) since they all share the same "must produce a signature recoverable to the recorded address" invariant.

### Likelihood Explanation
This triggers automatically and non-maliciously whenever a relayer operator's on-chain delivering address happens to be a contract account rather than an EOA — an increasingly common relayer/operator pattern (multisig or AA-based infrastructure wallets used for operational security). No attacker action, malicious peer, or privileged actor is required; the condition is purely a property of which address the destination-chain receipt records as the deliverer.

### Recommendation
Decouple the payout identity from the strict signature-recovery requirement: allow the recorded delivery address's controlling logic to be routed elsewhere (e.g., letting the address itself register a persistent, admin-free "beneficiary" mapping ahead of time via a mechanism not gated purely on ECDSA/Ed25519/Sr25519 signature verification, or adding a governance-gated fallback/rescue extrinsic scoped to a specific `(StateMachine, address)` `Fees` entry) so contract-controlled relayer addresses are not permanently unable to access legitimately earned fees.

### Proof of Concept
1. A relayer's destination-chain delivery transactions are submitted from a smart-contract wallet address `C` (e.g. a Safe or AA account) rather than an EOA — this address ends up recorded in the destination's request-receipt trie as the deliverer.
2. `accumulate_fees` runs `decode_receipt_relayer` and credits `Fees::<T>::insert(state_machine, C, amount)` per [7](#0-6) .
3. To withdraw, `withdraw_fees` requires a `WithdrawalInputData::signature` that recovers to `C` per [8](#0-7) . Since `C` is a contract with no private key, no valid signature can ever be produced.
4. `Pallet::withdraw` therefore always errors with `Error::<T>::InvalidSignature`/`InvalidPublicKey` for this address, and the funds under `Fees[state_machine][C]` remain permanently inaccessible — there is no other extrinsic in `modules/pallets/relayer` capable of moving that balance.

	/// Decode a proven `RequestReceipts[commitment]` value into the delivering
	/// relayer's bytes. EVM stores the address RLP encoded, substrate stores the
	/// signer bytes or a signature to recover the signer from. Used by both fee
	/// accumulation and the outbound request delivery claim.
	pub fn decode_receipt_relayer(state_id: StateMachine, raw: &[u8]) -> Result<Vec<u8>, Error<T>> {
		match state_id {
			s if crate::is_pharos(&s) =>
				if raw.len() == 32 {
					Ok(Address::from_slice(&raw[12..]).0.to_vec())
				} else {
					Err(Error::<T>::ProofValidationError)
				},
			s if s.is_evm() => {
				use alloy_rlp::Decodable;
				Ok(Address::decode(&mut &*raw)
					.map_err(|_| Error::<T>::ProofValidationError)?
					.0
					.to_vec())
			},
			s if s.is_substrate() => {
				use codec::Decode;
				let bytes =
					<Vec<u8>>::decode(&mut &*raw).map_err(|_| Error::<T>::ProofValidationError)?;
				Ok(if bytes.len() > 32 {
					Signature::decode(&mut &*bytes)
						.map_err(|_| Error::<T>::SignatureDecodingError)?
						.signer()
				} else {
					bytes
				})
			},
			_ => Err(Error::<T>::MismatchedStateMachine),
		}
	}
