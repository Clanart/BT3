### Title
Unbounded-Length Passphrase in Daemon Keyring RPC Handlers Enables Event-Loop-Blocking Denial of Service - ([File: chia/daemon/server.py])

### Summary
The Chia daemon's WebSocket RPC handlers `unlock_keyring`, `validate_keyring_passphrase`, and `set_keyring_passphrase` accept a caller-supplied `key`/`new_passphrase` string with only a type check and, for new passphrases, a *minimum*-length check — there is no maximum length enforced anywhere in the passphrase pipeline. This mirrors CVE-2023-25816 (Nextcloud), where an unbounded password string is forwarded straight into an expensive, synchronous cryptographic key-derivation routine.

### Finding Description
`unlock_keyring` and `validate_keyring_passphrase` only check that `key` is of type `str` before passing it to `Keychain.master_passphrase_is_valid()`: [1](#0-0) [2](#0-1) 

`set_keyring_passphrase` only enforces `Keychain.passphrase_meets_requirements()`, which checks a *minimum* length (`MIN_PASSPHRASE_LEN = 8`) and never a maximum: [3](#0-2) [4](#0-3) [5](#0-4) 

The validated string is fed directly into `check_passphrase`/`get_decrypted_data_dict`, which calls `symmetric_key_from_passphrase`, a synchronous PBKDF2-HMAC-SHA256 derivation over the entire passphrase with 100,000 iterations, followed by a ChaCha20Poly1305 decryption attempt: [6](#0-5) [7](#0-6) [8](#0-7) 

All of this executes synchronously inside an `async def` handler on the daemon's single asyncio event loop (`chia/daemon/server.py`, `WebSocketServer`), with no `run_in_executor` offload and no upper bound on input size. A caller connected to the daemon's local RPC WebSocket can submit an arbitrarily large string (megabytes to gigabytes) as `key`/`new_passphrase`, forcing the daemon to allocate, UTF-8 encode, and cryptographically process that entire buffer on the event loop before it can service any other request.

### Impact Explanation
Because the daemon multiplexes all connected services (wallet, farmer, harvester, plotter, UI) over one asyncio event loop, blocking that loop with a single oversized-passphrase RPC call stalls every other pending RPC call/message across all connected services for the duration of the encode + PBKDF2 + decrypt work. This can be repeated cheaply by any local caller with a valid daemon connection, degrading or halting wallet transaction-processing RPCs (e.g., spend submission, sign requests) that go through the same daemon process — a resource-consumption-driven processing halt analogous to the Nextcloud long-password DoS.

### Likelihood Explanation
Any process capable of opening a WebSocket connection to the local daemon (the same "local RPC caller" trust tier as GUI/CLI/wallet processes) can trigger this without needing a valid passphrase, valid keys, or elevated privileges — it only requires reaching the `unlock_keyring`/`validate_keyring_passphrase`/`set_keyring_passphrase` routes with an oversized string, which the handlers accept unconditionally.

### Recommendation
Enforce a reasonable maximum length (e.g., a few hundred bytes) on `key`/`new_passphrase`/`current_passphrase` inputs in `unlock_keyring`, `validate_keyring_passphrase`, and `set_keyring_passphrase` before any encoding or PBKDF2 work occurs, and consider offloading the PBKDF2/decrypt work to a thread/executor so a single expensive call cannot block the shared event loop.

### Proof of Concept
1. Connect to the daemon's local WebSocket RPC endpoint as any authenticated local client (e.g., using the same certs the wallet/GUI use).
2. Send a `validate_keyring_passphrase` (or `unlock_keyring`) request with `"key"` set to a multi-megabyte/gigabyte string.
3. Observe the daemon process blocking on encoding + PBKDF2-HMAC-SHA256 (100,000 iterations) + ChaCha20Poly1305 decrypt attempt over the oversized buffer, stalling all other concurrent RPC traffic (wallet, farmer, etc.) routed through the same daemon event loop until the call completes.

```python
    @staticmethod
    def passphrase_meets_requirements(passphrase: str | None) -> bool:
        """
        Returns whether the provided passphrase satisfies the passphrase requirements.
        """
        # Passphrase is not required and None was provided
        if (passphrase is None or passphrase == "") and Keychain.passphrase_is_optional():
            return True

        # Passphrase meets the minimum length requirement
        if passphrase is not None and len(passphrase) >= Keychain.minimum_passphrase_length():
            return True

        return False
```
