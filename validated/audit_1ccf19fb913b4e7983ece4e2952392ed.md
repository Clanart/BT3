### Title
Front-runnable `getRewardablePercentWAD` allows attacker to reduce their own forfeiture on manager-relayed `queueMGP` calls - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`queueMGP()` computes the forfeited (redistributed) portion of a vesting MGP payout by calling `_calExpireForfeit()`, which reads `vlMGP.getRewardablePercentWAD(_account)` at the moment the manager's transaction executes. Since this percentage is derived from the account's *current* locked/cooldown balances rather than a historical or time-weighted snapshot, an attacker who is the intended `_account`/`_receiver` of a pending `queueMGP` transaction can front-run it with a fresh `VLMGP.lock()` call to inflate `fullyInLock`, artificially raising `getRewardablePercentWAD` and shrinking the forfeited amount that would otherwise be redistributed to other vlMGP holders.

### Finding Description
`queueMGP` is restricted to `onlyManager` [1](#0-0) , but the amount forfeited is computed purely from the *recipient account's* on-chain lock state via `_calExpireForfeit`: [2](#0-1) 

This in turn calls `VLMGP.getRewardablePercentWAD(_account)`: [3](#0-2) 

The percentage is `fullyInLock / (fullyInLock + inCoolDown)` plus a time-weighted contribution from cooling-down slots. `fullyInLock` comes from `getUserTotalLocked`, which reads the user's live staked amount in `MasterMagpie` minus whatever is currently in cooldown [4](#0-3) .

Because this is a live read with no snapshotting, timelock, or minimum-holding-period requirement, the attacker (who is not a manager but is the legitimate recipient of a manager-relayed vesting payout) can observe the manager's pending `queueMGP(_amount, attacker, attacker)` transaction in the mempool and front-run it with `VLMGP.lock()` funded by freshly acquired MGP. This immediately increases `fullyInLock` for their account, pushing `getRewardablePercentWAD` toward 100% just before the manager's transaction lands, thereby shrinking `forfeitAmount` and enlarging `rewardableAmount` transferred to the attacker in `queueMGP` [5](#0-4) . The `onlyManager` modifier only restricts who can *call* `queueMGP`; it does nothing to protect the read of `_account`'s state from being manipulated by that same account beforehand. There is no `nonReentrant`-style protection against this because it's not reentrancy — it's ordinary transaction ordering/front-running, and the vulnerable state (`_account`'s lock ratio) is fully attacker-controlled since `_account` is the attacker.

### Impact Explanation
The reduced `forfeitAmount` is the amount that would otherwise be queued via `_queueNewRewardsWithoutTransfer` and distributed pro-rata to all vlMGP holders [6](#0-5) . By inflating their own rewardable percentage right before a manager-relayed vesting payout, the attacker directly reduces the yield redistributed to the rest of the vlMGP holder pool and increases their own payout beyond what their genuine locked history entitles them to — this is a theft of unclaimed/forfeited yield from other holders, matching the "theft of unclaimed yield" impact class.

### Likelihood Explanation
This requires the attacker to be the designated recipient (`_account`/`_receiver`) of a pending manager-triggered `queueMGP` call (e.g., MGP emissions vesting relayed through `WombatStaking`) and requires them to observe the manager's transaction in the mempool and front-run it with a `lock()` call funded by capital they control. This is realistic: manager relay transactions for reward distribution are periodic and predictable, `lock()` is a normal unprivileged user action, and the capital used for the front-run lock is not lost (it remains locked, and the attacker can later unlock it) — only borrowed briefly to shift the ratio for one block. It is repeatable every time a vesting/queueMGP payout to that account occurs.

### Recommendation
Compute `_calExpireForfeit`/`getRewardablePercentWAD` based on a time-weighted or snapshot-based lock history (e.g., average locked balance over the relevant vesting/accrual period, or a minimum lock duration requirement) rather than the instantaneous on-chain lock ratio at the moment `queueMGP` executes. Alternatively, require that increases to `fullyInLock` only count toward `getRewardablePercentWAD` after they have been held for a minimum period, preventing single-block/front-run manipulation of the ratio.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder`, and MGP token; register a manager.
2. Have attacker acquire a small initial lock in `VLMGP` and let part of it enter cooldown via `startUnlock`, so `getRewardablePercentWAD(attacker)` is well below 100%.
3. Record baseline: call `vlMGP.getRewardablePercentWAD(attacker)` and compute expected `forfeitAmount` for a hypothetical `queueMGP(amount, attacker, attacker)`.
4. Simulate the manager's transaction pending in mempool (build calldata but don't send yet).
5. In the same block, have attacker front-run with `VLMGP.lock()` using freshly minted/transferred MGP to significantly increase `fullyInLock`.
6. Execute the manager's `queueMGP(amount, attacker, attacker)` transaction in the same block after the lock.
7. Assert: `forfeitAmount` (from the `MGPHarvested` event) after front-running lock is materially lower than the baseline `forfeitAmount` computed in step 3 for the same nominal `_amount`, and `rewardableAmount` paid to attacker is correspondingly higher — demonstrating the manipulation succeeded without any manager or admin action beyond the routine `queueMGP` call.

    function queueMGP(uint256 _amount, address _account, address _receiver) override external onlyManager nonReentrant returns (bool) {
        IERC20(vlMGP.MGP()).safeTransferFrom(msg.sender, address(this), _amount);
        
        uint256 forfeitAmount = _calExpireForfeit(_account, _amount);
        uint256 rewardableAmount = _amount - forfeitAmount;
        
        if (forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, address(vlMGP.MGP()));

        if (rewardableAmount > 0) {
            IERC20(vlMGP.MGP()).safeTransfer(_receiver, rewardableAmount);
            emit MGPHarvested(_account, rewardableAmount, forfeitAmount);
        }

        return true;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
