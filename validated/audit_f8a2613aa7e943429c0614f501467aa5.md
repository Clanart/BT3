### Title
NULL-pointer-dereference crash parsing an overlong ProtoJSON `Duration` seconds value in the upb JSON decoder - (File: upb/json/decode.c)

### Summary
The upb JSON decoder's `google.protobuf.Duration` handler passes the raw return value of an integer-overflow-detecting helper directly into a subsequent parsing step without checking for the sentinel failure value. When an attacker supplies a `Duration` string whose integer-seconds portion is long enough to overflow `int64_t`, the helper returns `NULL`, that `NULL` is stored as the new parse cursor, and the next helper immediately dereferences it, crashing the process. This mirrors the phonenumber CWE-1284/CWE-248/CWE-392 pattern: an attacker-controlled numeric substring exceeds the parser's internal integer capacity, the failure is signaled through a sentinel return value, and the caller fails to check it before continuing to use the result.

### Finding Description
`jsondec_duration` parses a JSON string like `"3.000000001s"` for a `Duration` field: [1](#0-0) 

Line `ptr = jsondec_buftoint64(d, ptr, end, &seconds.int64_val, &neg);` calls the overflow-checked integer parser (`upb_BufToInt64`): [2](#0-1) 

`upb_BufToInt64` explicitly returns `NULL` when the parsed magnitude exceeds `INT64_MAX` (line 41-43: `if (!ptr || u64 > (uint64_t)INT64_MAX + neg) return NULL;`). `jsondec_duration` never checks whether this returned pointer is `NULL` — it unconditionally assigns it to `ptr` and immediately calls `jsondec_nanos(d, &ptr, end)`.

`jsondec_nanos` then dereferences the cursor without validating it: [3](#0-2) 

`const char* p = *ptr;` loads `p = NULL`; the guard `if (p != end && *p == '.')` short-circuits to `*p` because `NULL != end` is true, dereferencing the null pointer and crashing.

The exact same amalgamated logic is compiled into the PHP and Ruby extensions: [4](#0-3) [5](#0-4) 

This is the direct structural analog of the phonenumber bug: both have a numeric-substring parser that signals "value too large to represent" via a sentinel (an assert-triggering internal state for phonenumber, a `NULL` return for upb), and both have a caller that proceeds to use the invalid result instead of treating it as a hard parse failure.

### Impact Explanation
Any consumer that accepts untrusted ProtoJSON and parses it through upb (the core parsing engine for the PHP extension, Ruby extension, and any C/C++/Python code linking upb's JSON decoder) can be crashed by a single crafted request. Because `Duration` is a first-class well-known type, an attacker only needs a schema containing a `google.protobuf.Duration` field reachable from a JSON parsing entry point — no privileged access, malicious schema, or forged MiniTable is required. The result is an unrecoverable process crash (SIGSEGV), i.e., availability impact consistent with the CVSS `A:H` component of the phonenumber advisory, not a catchable exception.

### Likelihood Explanation
High. The trigger is a single JSON string field value, e.g. a Duration string whose seconds portion has ~20+ digits, which is trivially constructible by any client sending ProtoJSON to a public parse API (e.g. `JsonToBinary`, `Message::mergeFromJsonString` in PHP, `JSON.parse` in Ruby's protobuf gem). No authentication, precondition, or race is needed; the code path is deterministic.

### Recommendation
In `jsondec_duration` (and defensively in `jsondec_nanos`), check the return value of `jsondec_buftoint64`/`jsondec_buftouint64` for `NULL` immediately after the call and invoke `jsondec_err(d, "Malformed duration")` before using the cursor for any further parsing, mirroring the existing NULL-check pattern already used correctly in `jsondec_tsdigits` (`upb/json/decode.c:1081-1084`). Apply the same fix to the duplicated logic in `php-upb.c` and `ruby-upb.c` (these appear to be generated/vendored copies of `decode.c`, so the upstream fix should be propagated through the amalgamation build).

### Proof of Concept
Send the following ProtoJSON payload for any message containing a `google.protobuf.Duration` field, through any upb-backed JSON parsing entry point (PHP `Message::mergeFromJsonString`, Ruby `JSON.parse`, or a C/C++ program calling `upb_JsonDecode`):
```json
{"optionalDuration": "99999999999999999999999999999999999999s"}
```
Trace of execution:
1. `jsondec_duration` (`upb/json/decode.c:1208`) calls `jsondec_buftoint64` on `"99999999999999999999999999999999999999"`.
2. `upb_BufToInt64` (`upb/lex/atoi.c:30-48`) detects `u64 > INT64_MAX` overflow and returns `NULL`.
3. `ptr` is set to `NULL` without a check.
4. `jsondec_nanos(d, &ptr, end)` (`upb/json/decode.c:1092-1096`) loads `p = *ptr = NULL` and evaluates `*p`, dereferencing a null pointer and crashing the process.

I was not able to execute this PoC in a sandboxed build within this session; the crash path is derived from static analysis of the sentinel-return contract of `upb_BufToInt64` and the unchecked propagation of its result through `jsondec_duration` → `jsondec_nanos`. A background Devin session with build/test access could confirm this dynamically (e.g., via `upb/json/decode.c` unit tests or a fuzz harness feeding oversized `Duration`/`Timestamp` fractional-second strings).

static int jsondec_nanos(jsondec* d, const char** ptr, const char* end) {
  uint64_t nanos = 0;
  const char* p = *ptr;

  if (p != end && *p == '.') {
    const char* nano_end = jsondec_buftouint64(d, p + 1, end, &nanos);
    int digits = (int)(nano_end - p - 1);
    int exp_lg10 = 9 - digits;
    if (digits > 9) {
      jsondec_err(d, "Too many digits for partial seconds");
    }
    while (exp_lg10--) nanos *= 10;
    *ptr = nano_end;
  }

  UPB_ASSERT(nanos < INT_MAX);

  return (int)nanos;
}

static void jsondec_duration(jsondec* d, upb_Message* msg,

  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  upb_MessageValue seconds;
  upb_MessageValue nanos;
  upb_StringView str = jsondec_string(d);

const char* upb_BufToInt64(const char* ptr, const char* end, int64_t* val,
                           bool* is_neg) {
  bool neg = false;
  uint64_t u64;

  if (ptr != end && *ptr == '-') {
    ptr++;
    neg = true;
  }

  ptr = upb_BufToUint64(ptr, end, &u64);
  if (!ptr || u64 > (uint64_t)INT64_MAX + neg) {
    return NULL;  // integer overflow
  }

  *val = neg ? -u64 : u64;
  if (is_neg) *is_neg = neg;
  return ptr;
}
