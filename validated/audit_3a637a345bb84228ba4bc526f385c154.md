### Title
Zero-valued `Interpolation::Constant` coefficients silently remove participants from the group key and signing set - ([File: crypto/dkg/src/lib.rs])

### Summary
The external report (LooksRare H-2) shows a loop accepting `depositAmount == 0` because `0 % x == 0`, so an entry is recorded with `currentEntryIndex` unincremented — violating the "strictly increasing, no-repetition index" invariant and corrupting winner selection. The Serai analog lives in `ThresholdKeys::new` / `ThresholdKeys::read`: `Interpolation::Constant(Vec<F>)` coefficients are read via `C::read_F` (which only enforces canonical encoding) and are never checked for `F::ZERO`. A zero coefficient means participant `i`'s verification share contributes the identity point to `group_key` (the share "doesn't increment the index"), while the participant is still counted in `params.n()` and passes `IncorrectAmountOfVerificationShares`/`InvalidParticipant` validation. During signing, `view()` interpolates that participant's `secret_share` to `0`, producing a consistent-but-empty contribution — so the remaining signers produce valid signatures under a group key that never included that member.

### Finding Description
`Interpolation::Constant(c)` stores one coefficient per participant, applied as `c[i-1]` in `interpolation_factor`: [1](#0-0) 
`ThresholdKeys::new` computes the group key as `sum(verification_shares[i] * factor(i))` over participants `1..=t` and validates only share count and index range — no nonzero check on factors: [2](#0-1) 
`ThresholdKeys::read` deserializes `n` arbitrary field elements as the Constant coefficients with only canonical-encoding enforcement (`C::read_F`), so all-zero or partially-zero factor lists are accepted: [3](#0-2) 
The only constraint imposed is `t == n` for Constant interpolation: [4](#0-3) 
In `view()`, the interpolation factor multiplies both the secret share and the verification share, so a zero factor yields `secret_share = 0` and a verification share of identity for that signer — self-consistent, producing a valid signature that omits them: [5](#0-4) 

### Impact Explanation
Like the 0-deposit that registers an entry without advancing `entryIndex`, a zero coefficient registers a participant in `n`/`verification_shares` without advancing their contribution to `group_key`. An attacker who can supply serialized `ThresholdKeys` bytes (e.g., distributed key material, backups, or any channel feeding `ThresholdKeys::read`) can set a victim's coefficient to `0`, silently converting an n-of-n multisig into an (n−1)-of-(n−1) one: signatures verify under `group_key` while the zeroed participant's key share is never required. This breaks the core threshold invariant — the declared participant count no longer bounds who must cooperate to sign — enabling unauthorized signatures/fund control.

### Likelihood Explanation
Requires the attacker to control bytes deserialized by `ThresholdKeys::read` into `Interpolation::Constant` form (interpolation byte `0`). `read_F` enforces canonical scalar encoding but accepts `0`, so no malformed-encoding rejection occurs; the crafted blob is fully "valid." In-house producers (`musig`, `promote`) compute factors honestly, so exploitation depends on an integrator accepting external serialized key material — the exact reachable surface listed for `ThresholdKeys::read`.

### Recommendation
In `ThresholdKeys::new` (or at `Interpolation::Constant` construction/deserialization), reject any coefficient equal to `F::ZERO`:
```rust
Interpolation::Constant(c) => {
  if params.t() != params.n() { Err(InapplicableInterpolation(...))? }
  if c.iter().any(|f| bool::from(f.is_zero())) {
    Err(DkgError::ZeroParameter { t: 0, n: 0 })?; // or a new ZeroCoefficient error
  }
}
```
Optionally also assert `group_key != identity` so a fully-zeroed coefficient list cannot produce an identity group key.

### Proof of Concept
Conceptual: build a serialized `ThresholdKeys<Secp256k1>` blob with `t = n = 2`, `i = 1`, interpolation byte `0`, coefficients `[F::ONE, F::ZERO]`, secret share `s1`, and verification shares `[G*s1, G*s2]`. `ThresholdKeys::read` succeeds; `group_key()` equals `G*s1` — participant 2's share `s2` never enters the key. In FROST signing, `view([1,2])` assigns participant 2 `secret_share = 0 * s2 = 0` with verification share `identity`, so the pair produces a signature valid under `G*s1` even if participant 2 is unresponsive or hostile — and, symmetrically, signer 1 alone (with `included=[1]`, since `t` can be effectively satisfied without 2's contribution) determines the key. The zero coefficient "deposit" occupies participant slot 2 while contributing nothing, mirroring the zero-amount deposit that occupies a round entry without incrementing `entryIndex`.
