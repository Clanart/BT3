### Title
Path-traversal guard `resolveWithin` uses substring `startsWith` without separator boundary check, allowing deep-link `filepath` to escape the repository root - (File: app/src/lib/path.ts)

### Summary
GitHub Desktop's `x-github-client://openRepo/...` deep link handler accepts an attacker-controlled `filepath` query parameter and uses it to reveal a file via `shell.showItemInFolder` after checking that the resolved path stays "within" the opened repository. The containment check in `_resolveWithin` (`app/src/lib/path.ts`) compares paths with `realResolved.startsWith(realRoot)`, which is a naive string-prefix comparison with no path-separator boundary. This allows a sibling directory whose name merely begins with the repository's directory name (e.g. `repo` vs. `repo-backup`) to pass the "inside root" check even though it is a completely different folder outside the repository.

### Finding Description
The deep-link action is parsed in `parseAppURL` (`app/src/lib/parse-app-url.ts:98-125`), which extracts `filepath` from the `openRepo` action's query string with no path validation beyond being a query string value: [1](#0-0) 

This action is handled in `Dispatcher.openRepositoryFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1940-1973`), which after cloning/opening the target repository, blocks only absolute paths and otherwise defers all traversal protection to `resolveWithin`: [2](#0-1) 

The actual containment check lives in `_resolveWithin` (`app/src/lib/path.ts:36-72`). It normalizes and resolves the `filepath` against the repository root, then validates containment with:
```
return realResolved.startsWith(realRoot) ? resolved : null
``` [3](#0-2) 

`startsWith` performs a raw substring comparison. If `realRoot` is `/Users/alice/Documents/GitHub/myrepo` and the resolved path is `/Users/alice/Documents/GitHub/myrepo-secrets/notes.txt`, the latter string does start with the former string even though it lives in a completely different, sibling directory. There is no check for a trailing path separator (e.g. `realResolved === realRoot || realResolved.startsWith(realRoot + path.sep)`), so a relative `filepath` such as `../myrepo-secrets/notes.txt` can escape the intended root as long as any sibling directory happens to share the repository directory name as a prefix — a very common situation for Desktop users who clone multiple related repos or forks into the same parent folder (e.g. `github-desktop`, `github-desktop-i18n`, `myrepo`, `myrepo-old`, `myrepo.bak`, etc.).

This exactly mirrors the report's bug class: a security-relevant invariant (`filepath` must stay inside the repo, analogous to `shareLockPeriod`) is enforced through a path/flag that looks correct in isolation but the actual guard (`_afterPublicDeposit` / `startsWith`) has a boundary flaw that a crafted external input can slip through.

### Impact Explanation
An attacker who controls a GitHub repository/PR page can craft a "Open in Desktop" style deep link (`x-github-client://openRepo/<attacker-repo-url>?filepath=../sibling-dir-with-prefix/secret-file`) and get a victim to click it. Once Desktop opens/clones the attacker's repo, it will resolve the crafted `filepath` and, because of the missing separator check, may resolve to a file **outside** the intended repository if any sibling folder name happens to share the repo's directory name as prefix. The resolved path is then passed to `shell.showItemInFolder`, revealing (and giving Explorer/Finder access to) files outside the repository the attacker's repo is scoped to — a "read outside the repo" impact directly reachable from a link the user clicks, without local access, admin rights, or prior malware.

### Likelihood Explanation
The likelihood is Medium: the crafted deep link is the sole "unnatural" step (clicking a link), which is within the accepted "link/deep-link" attacker vector. Exploitation additionally requires the resolved path to coincide with a directory literally beginning with the repository's own directory name — this is plausible in real Desktop usage (users routinely clone forks/variants of the same project side-by-side, e.g., `desktop` / `desktop-fork`, or repos with generic parent-folder names), but it is not guaranteed for every victim, making full weaponization environment-dependent.

### Recommendation
Fix the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to require an exact match or a trailing path separator boundary, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Apply the same fix to all path-prefix comparisons derived from this pattern, and add regression tests covering sibling-directory-prefix collisions (e.g. root `/a/repo` vs. resolved `/a/repo-2/x`).

### Proof of Concept
1. Victim has two folders side by side: `~/Documents/GitHub/project` (an existing repo) and `~/Documents/GitHub/project-secrets` (containing sensitive files, e.g. `.env` or notes) — a realistic layout for anyone who names variant/backup folders with a shared prefix.
2. Attacker hosts/controls a public repo and crafts a link:
   `x-github-client://openRepo/https://github.com/attacker/project?filepath=..%2Fproject-secrets%2Fnotes.txt`
3. Victim clicks the link. Desktop's `parseAppURL` extracts `filepath = ../project-secrets/notes.txt` [1](#0-0) .
4. `openRepositoryFromUrl` clones/opens `attacker/project` at `~/Documents/GitHub/project`, then calls `resolveWithin(repository.path, filepath)` since the path is not absolute [2](#0-1) .
5. Inside `_resolveWithin`, `resolved` becomes `~/Documents/GitHub/project-secrets/notes.txt`; `realResolved.startsWith(realRoot)` evaluates true because `"…/project-secrets/notes.txt".startsWith("…/project")` is true in plain string comparison [3](#0-2) .
6. `shell.showItemInFolder(resolved)` opens/reveals `notes.txt` from the unrelated `project-secrets` folder, outside the cloned repository.
