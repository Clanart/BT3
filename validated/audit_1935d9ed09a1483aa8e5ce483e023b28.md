### Title
Broad exception handler in `add_crcat_coin` deletes unrelated, legitimate CR-CAT coin and transaction records on unrelated parsing errors - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
`CRCATWallet.add_crcat_coin()` wraps CR‑CAT coin recognition in a single broad `except Exception` intended only for the case "the parent is not a CAT" [1](#0-0) . In practice the `try` block can raise for reasons unrelated to the parent's CAT-ness (e.g. a missing hint for one specific sibling output), yet the handler unconditionally purges every coin record and transaction record that shares the same parent coin id and belongs to this wallet — including coins that were already correctly recognized and recorded. This is the same bug class as CVE-2022-27778: an error-path cleanup routine removes the wrong (unrelated, still-good) item instead of only the item that actually failed.

### Finding Description
`add_crcat_coin` computes hints for all outputs of the spent parent coin and looks up `hint_dict[coin.name()]` for the currently-processed coin: [2](#0-1) 

If this particular output coin lacks a proper memo/hint (or any other unrelated exception occurs while classifying this one child), a `KeyError`/exception propagates to the outer handler: [1](#0-0) 

That handler's comment states the intent is to scrub children only when "the parent is not a CAT," but the `except Exception:` is not scoped to that specific failure mode. It instead looks up *all* coin records whose `coin_parent` equals the spent parent coin id via `get_coin_records_by_parent_id`, and for every one that belongs to this wallet, deletes both the `WalletCoinRecord` and the associated `TransactionRecord` keyed by that coin's name.

Because a single CAT/CR-CAT spend can create multiple output coins from one parent (e.g., a payment output to the wallet plus a change output, or multiple recipients), a counterparty crafting such a spend can intentionally omit/garble the hint on one sibling output while a legitimate, previously-tracked CR-CAT coin owned by the victim shares the same parent. When the wallet later processes that malformed sibling coin (via `coin_added` → `add_crcat_coin`), the resulting exception causes it to delete the victim's legitimate, already-confirmed CR-CAT coin record and its transaction record from local wallet storage — data that was correct and unrelated to the actual parsing failure.

This mirrors the curl CVE precisely: an error-triggered cleanup step, meant to remove state related to the failing item, instead removes unrelated, valid state (a "wrong file" in file-system terms; here, a wrong coin/transaction record).

### Impact Explanation
The victim wallet silently loses its local record of an owned, valid CR-CAT coin and the transaction that created it. This is a coin-identity/wallet-state integrity bug: the wallet's coin store diverges from the true on-chain state for that user, corrupting balance accounting and transaction history for a credential-restricted CAT (CR-CAT) coin that the user still legitimately owns on-chain, without any user action or malicious peer being required beyond a specifically crafted spend from a counterparty. Recovery requires a full wallet resync. This fits the Business Logic Errors weakness class and produces a concrete, reachable data-loss/availability impact from a single spend bundle a normal CAT/CR-CAT counterparty can construct.

### Likelihood Explanation
Reachable by any unprivileged party who can construct/broadcast a CAT/CR-CAT spend bundle with multiple outputs sharing one parent coin (a standard, unprivileged capability — e.g., an offer counterparty or payer sending a CR-CAT payment plus change). No special network position, malicious peer, or timelord/harvester access is required; the trigger condition (one sibling output lacking a proper hint/memo while another is a real payment to the victim) is fully attacker-controlled at spend-construction time. The `# pragma: no cover` markers on this branch indicate it is untested, increasing likelihood the overly-broad behavior has gone unnoticed.

### Recommendation
Narrow the `except` clause in `add_crcat_coin` to only trigger the sibling-scrub cleanup for the specific, verified condition "parent puzzle is not a valid CAT" (e.g., by explicitly checking `CRCAT.get_next_from_coin_spend` failure modes), rather than catching all exceptions from CR-CAT recognition of a single coin. Failures specific to one child coin (e.g., missing hint for `coin.name()`) should only affect that coin's own record, not sibling coins already correctly tracked. Add test coverage for the previously `# pragma: no cover` cleanup branch to validate it does not delete unrelated valid coins/transactions.

### Proof of Concept
1. Counterparty builds a CR-CAT spend bundle where the spent parent coin creates two outputs: output A goes to the victim wallet with a correct memo/hint (a normal CR-CAT payment), output B goes to the victim's puzzle hash set (or any coin the wallet will attempt to classify) but omits/garbles the CREATE_COIN memo so `compute_spend_hints_and_additions` produces no hint entry for output B's coin name.
2. Victim's wallet receives and successfully records output A via `add_crcat_coin` (added to `coin_store` normally).
3. Wallet is later notified of output B (same parent coin id) and calls `add_crcat_coin`; `hint_dict[coin.name()]` for output B raises `KeyError`, hitting the broad `except Exception` handler.
4. Handler calls `get_coin_records_by_parent_id(coin_spend.coin.name())`, finds output A's coin record (belonging to this wallet), and deletes it plus its `TransactionRecord`, even though output A was valid and previously confirmed.
5. Victim's wallet no longer shows output A in balance/history until a full resync, despite it remaining a valid, spendable on-chain coin.
