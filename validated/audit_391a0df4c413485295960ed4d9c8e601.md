Based on my investigation of `EvmHost.sol`, I found a genuine analog: `_requestCommitments[commitment]` (the `FeeMetadata` for an outgoing `GetRequest`, holding the relayer fee) is **read and paid out** on response delivery but **never deleted**, while the timeout path independently checks and clears the same mapping to pay a refund. This mirrors the Velodrome bug's core pattern: a shared accounting slot that is updated/consumed on one path without being cleared, allowing a second, independent path to also act on the stale value — resulting in double payment from one fee slot. [1](#0-0) 

### Title
Double payment of relayer GET-request fee via response delivery followed by timeout claim - (File: evm/src/core/EvmHost.sol)

### Summary
`dispatchIncoming(GetResponse, address relayer)` pays the relayer the fee stored in `_requestCommitments[commitment].fee` upon successful response delivery, but does not delete that entry afterward. `dispatchTimeOut(GetRequestTimeout, ...)` independently reads and deletes the same `_requestCommitments[commitment]` entry to refund the fee to the original sender. Because both code paths key off the same commitment/mapping and only one of them clears it, the fee for a single `GetRequest` can be paid out twice if both a response and a timeout proof are submitted for the same request.

### Finding Description
On the response path: [2](#0-1) 
`dispatchIncoming(GetResponse memory response, address relayer)` sets a `_responseReceipts[commitment]` (keyed by `response.request.hash()`) for replay protection of the *response*, then transfers `_requestCommitments[commitment].fee` to the relayer — but it never deletes or zeroes `_requestCommitments[commitment]`.

On the timeout path: [3](#0-2) 
`dispatchTimeOut(GetRequestTimeout memory timeout, FeeMetadata memory meta, bytes32 commitment)` deletes `_requestCommitments[commitment]` up front (replay protection for the *timeout*), and if the module callback succeeds, refunds `meta.fee` back to `meta.sender`.

The two guards are on different mappings (`_responseReceipts` vs `_requestCommitments`), and each path only protects itself against its own kind of replay — neither path checks whether the *other* path has already consumed the fee. Because `_requestCommitments[commitment]` is left populated with the original fee after a successful response, a relayer/attacker who can also produce a valid timeout proof for the same (non-yet-actually-timed-out or still-outstanding) request commitment can trigger `dispatchTimeOut`, which will still find `meta.fee != 0` and pay it out a second time to `meta.sender`.

This is structurally the same class of bug reported for CLPool: state that is supposed to be cleared as a side effect of one action (`response` handling should invalidate the fee slot) is instead left intact, and a second, independently-guarded code path (`timeout` handling) later "recomputes"/re-consumes that stale value, corrupting the accounting — in this case leading to fund duplication rather than a skewed liquidity value.

### Impact Explanation
This directly causes loss of protocol/bridge funds: the fee escrowed for a single outgoing `GetRequest` can be disbursed twice — once to the relayer on response delivery, and again to the original fee payer via a timeout refund — draining the fee token balance held by `EvmHost` beyond what was ever deposited for that request. This matches the bounty's "stealing or loss of funds" and "duplicate settlement/double-claim" categories.

### Likelihood Explanation
Exploitability depends on whether the message-handler layer (`HandlerV2.sol` / the router that calls `dispatchTimeOut`) independently re-verifies that a response was not already delivered before allowing a timeout proof to be processed for the same request commitment. I was not able to fully trace that cross-check within the available iterations — this is the main open uncertainty. If such a check exists upstream (e.g., verifying `_responseReceipts` state or requiring `req.timed_out()` strictly after successful delivery is impossible), the path may be blocked; if it is missing or bypassable (e.g., through a race between a slow relayer response and a timeout submission, or a proof crafted after the response commitment for an unrelated request), the double-payment is directly reachable by an unprivileged relayer without needing a malicious peer, admin, or leaked key.

### Recommendation
In `dispatchIncoming(GetResponse memory response, address relayer)`, delete `_requestCommitments[commitment]` (or otherwise zero the `fee` field) immediately after successfully paying the relayer, mirroring the replay-protection pattern already used for `_requestReceipts` and `_responseReceipts`. This ensures a later `dispatchTimeOut` call for the same commitment finds `meta.fee == 0` and cannot pay out a second time. Additionally, `dispatchTimeOut` should explicitly assert that no response has been recorded (via `_responseReceipts`) for the corresponding request commitment before authorizing any refund.

### Proof of Concept
1. App on the source chain dispatches a `GetRequest`, source `EvmHost` stores `_requestCommitments[commitment] = FeeMetadata{sender, fee}` [4](#0-3) .
2. A relayer delivers a valid `GetResponse` for the request; `dispatchIncoming(GetResponse, relayer)` runs, `onGetResponse` succeeds, and `fee` is transferred to `relayer` — but `_requestCommitments[commitment]` is left populated with the same `fee` value [5](#0-4) .
3. Before (or regardless of) the response, a timeout proof for the same request commitment is submitted through the handler, invoking `dispatchTimeOut(GetRequestTimeout, meta, commitment)`.
4. `dispatchTimeOut` deletes `_requestCommitments[commitment]`, calls `onGetTimeout`, and on success transfers `meta.fee` to `meta.sender` [6](#0-5) .
5. Net result: the same escrowed fee has been paid out twice — once to the relayer, once refunded to the sender — with no reconciliation between the two mappings involved.

Note: I could not fully verify within the available tool budget whether `HandlerV2.sol` enforces mutual exclusivity between response and timeout submission for the same commitment before reaching `dispatchTimeOut`; this should be confirmed against `evm/src/core/HandlerV2.sol` and the Rust-side timeout handler at `modules/ismp/core/src/handlers/timeout.rs` before treating this as fully exploitable end-to-end.

```text
    /**
     * @dev Dispatch an incoming GET response to source module
     * @param response - get response
     */
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```

```text
    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
