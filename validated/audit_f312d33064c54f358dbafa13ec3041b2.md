## Analysis

The reported bug class is: *a defensive pause, triggered to stop one bad actor's harmful actions, also blocks legitimate exit/refund paths for everyone else, causing users to be stuck holding claims they cannot cancel/redeem while the market moves against them.*

The Hyperbridge local analog is the `HyperFungibleToken` (and its `Upgradeable`/`Wrapped` variants) cross-chain token bridge, where the same `whenNotPaused` guard is applied to both the "harmful" outbound path (`send`) and the "recovery" refund path (`onPostRequestTimeout`), so pausing to stop new transfers also blocks refunding tokens that already timed out.

### Title
Pausing `HyperFungibleToken` blocks timeout refunds, permanently locking already-burned tokens - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.send()` burns the caller's tokens immediately and dispatches an ISMP POST request; the tokens are only returned via `onPostRequestTimeout()` if the message times out without delivery. Both `send()` and `onPostRequestTimeout()` are gated by the same `whenNotPaused` modifier [1](#0-0) [2](#0-1) . If the contract is paused after a user has already burned tokens via `send()` but before their message times out, the legitimate refund path is also disabled, leaving the user's tokens burned with no way to recover them until the owner unpauses.

### Finding Description
`send()` burns `params.amount` from `msg.sender` up front and dispatches the ISMP request [3](#0-2) . The only path that returns those tokens to the sender if delivery fails is `onPostRequestTimeout()`, which re-mints the burned amount to the original sender [2](#0-1) .

Both functions share the exact same `whenNotPaused` gate. This is invoked from `EvmHost.dispatchTimeOut`, which makes a low-level call into the app's `onPostRequestTimeout` selector and only clears the commitment / refunds the relayer fee if that call succeeds; if it reverts (e.g., because the app is paused), the commitment is intentionally kept so the timeout can be retried later [4](#0-3) . Per the handler documentation, `handlePostRequestTimeouts()` is permissionless and "Timeout can be resubmitted until callback succeeds" [5](#0-4) .

This mirrors the reported bug class precisely: a single boolean pause state disables both the "harmful" action (new `send()`s / new orders) and the legitimate exit/recovery action (`onPostRequestTimeout` refund / liquidity removal), with no separate flag to keep recovery paths open. The same pattern repeats in `HyperFungibleTokenUpgradeable.sol` [6](#0-5)  and both `WrappedHyperFungibleToken*.sol` variants [7](#0-6) [8](#0-7) .

### Impact Explanation
Any user who called `send()` before a pause has their tokens burned and in cross-chain transit. If the destination message subsequently times out while the source contract remains paused, the refund mint is blocked, so the user's balance is stuck at zero for that amount with no recovery mechanism except waiting for the owner to `unpause()`. Since pausing is a normal incident-response action (e.g., in response to a detected exploit, oracle manipulation, or bridge compromise elsewhere in the system) rather than a rare edge case, honest users who transacted just before the pause can be locked out of their funds for an indefinite period, exactly matching the "restricts user access to their funds during market/security shifts" characterization of the original report.

### Likelihood Explanation
This requires no malicious actor, relayer, or governance compromise — it is a direct consequence of normal, intended contract behavior (the owner pausing the contract, which is an expected operational action, not an attack). Any timeout that lands while paused, or any pause that occurs while in-flight transfers exist, triggers this condition, and cross-chain timeouts (destination congestion, dropped relayer messages, chain outages) are a normal occurrence in a bridge, making this reasonably likely to occur in production usage.

### Recommendation
Split the pause gate so that outbound risk-creating actions (`send()`, `onAccept()` minting from new inbound messages) can be paused independently from the recovery path (`onPostRequestTimeout`). At minimum, `onPostRequestTimeout` should not be gated by `whenNotPaused`, so that already-burned tokens can always be refunded to their rightful owner regardless of pause state — mirroring the report's recommendation to let a dedicated flag block only the source of harm while allowing exits/refunds to proceed.

### Proof of Concept
1. User calls `HyperFungibleToken.send()` with `amount = 1000`; tokens are burned and an ISMP POST request with `timeout = T` is dispatched [3](#0-2) .
2. Before the request is delivered or times out, the owner calls `pause()` (e.g., in response to an unrelated incident) [9](#0-8) .
3. Time passes; the request times out on the destination without delivery.
4. Anyone calls `IHandler.handlePostRequestTimeouts()` (permissionless) to process the timeout; `EvmHost.dispatchTimeOut` performs the low-level call to `onPostRequestTimeout` [10](#0-9) .
5. The call reverts because `HyperFungibleToken.onPostRequestTimeout` is `whenNotPaused` [2](#0-1) ; the host keeps the commitment for retry but the user's 1000 tokens remain unminted/locked.
6. The user has no way to recover the 1000 tokens until the owner calls `unpause()`, during which the user cannot use, sell, or exit that value even as market/security conditions change — the same restriction pattern flagged in the source report.

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
