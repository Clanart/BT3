### Title
Malicious/compromised Registry owner can redirect the gasless swap-router address, allowing theft of proposer-lent KAIA and user token approvals via KIP-247 fee delegation - (File: kaiax/gasless/impl/getter.go)

### Summary
The `kaiax/gasless` module trusts whatever address the KIP-149 `Registry` contract reports as the active `GaslessSwapRouter` and blindly uses it to validate, promote, and fund KIP-247 gasless approve/swap transactions. Because `Registry.register()` is callable by the Registry `owner` at any time (a single admin/governance-controlled key), that owner can register a malicious contract as the `GaslessSwapRouterName` record. Every unprivileged user's approve/swap transaction, and every honest proposer's KAIA "lend" transaction, is then automatically routed to trust this attacker-controlled address, mirroring exactly the pattern described in the external report ("admin sets a malicious feeBurner/pool that just takes the funds for itself").

### Finding Description
`GaslessModule.updateAddresses` re-reads the current swap router and allowed-token set on every block from the Registry/MultiCall system contract, with no validation beyond "code exists": [1](#0-0) 

That `g.swapRouter` value is what determines:
- whether a user's `approve()` call is treated as a valid `GaslessApproveTx` (`A3: spender is a whitelisted SwapRouter contract`), [2](#0-1) 
- whether a user's `swapForGas()` call is treated as a valid `GaslessSwapTx` (`S1: tx.to is a whitelisted SwapRouter contract`), [3](#0-2) 
- and the exchange-rate check used to size how much KAIA the block proposer will lend to the user (`GetAmountIn` is queried directly against `g.swapRouter`): [4](#0-3) 

The swap router address itself comes from the Registry contract's `getActiveAddr`/`register()` mechanism (KIP-149), whose `register(string name, address addr, uint256 activation)` function is restricted only by `owner` — a single admin address, not by any transaction-sender permission check: [5](#0-4) 

The gasless flow's block-building logic prepends a `LendTxGenerator` transaction that sends real KAIA from the node/proposer to the user to cover the swap+approve gas fee, expecting to be repaid via the swap transaction's `amountRepay` inside `swapForGas`: [6](#0-5) 

If the Registry `owner` (admin/governance) registers a new `GaslessSwapRouterName` address pointing at a malicious contract instead of the legitimate audited `GaslessSwapRouter`, then:
1. `g.swapRouter` is updated to the malicious address at the next block via `updateAddresses`, with no on-chain check that the new contract implements correct swap/repay/commission semantics — the same "just takes the funds for itself" pattern the external report calls out for `feeBurner`.
2. All future approve/swap gasless transactions from ordinary users are validated against, and routed through, that malicious contract.
3. The proposer still lends real KAIA to the user based on `AmountRepay`/`Fee()` accounting performed against `g.swapRouter`'s `GetAmountIn`, but the malicious router can accept the user's ERC20 token, swap for less than expected, refuse to repay the lending party, or divert the swapped proceeds/commission to an address the admin controls — exactly analogous to `RewardHandler.burnFees()` forwarding all pool fees to an attacker-controlled `feeBurner` in the original report. [7](#0-6) 

### Impact Explanation
A single admin key (Registry `owner`) can, without any user consent or on-chain vote, redirect the entire KIP-247 gasless fee-delegation pipeline to a contract they control. This lets them:
- Steal the ERC20 tokens approved by unprivileged gasless users (approval is granted to whatever address is `g.swapRouter` at approve time).
- Steal or default on the KAIA the block proposer pre-lent to users, since the "repay" leg is executed inside the attacker's contract logic.
- Manipulate `GetAmountIn`/exchange-rate reporting to under/over price swaps, extracting value from ordinary users on every gasless swap while the change is live.

This is a direct unauthorized value-movement/fee-delegation abuse vector reachable purely by a single admin transaction (`Registry.register`) combined with ordinary users' own submitted gasless transactions — no other privileged or malicious-node behavior is required.

### Likelihood Explanation
The Registry owner key is a normal admin/governance-controlled EOA or multisig, not protected by any additional on-chain safeguard visible in this module (e.g., no timelock enforced within `updateAddresses` beyond an `activation` block number that the admin also controls, and no allow-list of previously-known-good router bytecode). The `activation` parameter of `register()` gives the admin full control over exactly which block the swap becomes live, enabling silent, precisely-timed redirection. Given that gasless transactions are processed automatically by the tx-pool/block-builder without additional user-side verification of the router contract's bytecode, likelihood of exploitation by a malicious or compromised admin is high once registry write access is obtained.

### Recommendation
- Do not let `kaiax/gasless` trust an arbitrary Registry-supplied address for `swapRouter` without additional verification (e.g., pinning to an expected bytecode hash/hardcoded allow-list, similar to the "Bytecode regression" pin already used in tests: [8](#0-7) ), rather than trusting `updateAddresses`'s no-op fallback logic.
- Require a timelock/delay and on-chain announcement before a new `GaslessSwapRouter` record becomes active and is honored by `updateAddresses`, so users and proposers can react to malicious changes.
- Consider requiring multi-party (governance vote) approval, not a single `owner` key, for changing security-critical Registry records such as `GaslessSwapRouterName`.
- Add sanity checks in `checkBalanceForSwap`/`GetLendTxGenerator` that validate expected repay/commission invariants independent of the registered router's self-reported `GetAmountIn`.

### Proof of Concept
1. Attacker/compromised admin holds the `owner` key of the `Registry` system contract (`system.RegistryAddr`).
2. Admin calls `Registry.register("GaslessSwapRouterName", <MaliciousRouter>, activation=<nextBlock>)` — a single ordinary transaction, exactly as exercised in the test harness: [9](#0-8) 
3. At the activation block, every full node's `GaslessModule.PostInsertBlock` → `updateAddresses` picks up the new address as `g.swapRouter`, with no additional validation: [10](#0-9) 
4. An ordinary, unprivileged user submits a normal-looking `approve` + `swapForGas` pair; the gasless tx-pool logic validates it against `g.swapRouter` (now malicious) and the node's proposer sends a `LendTxGenerator` KAIA transaction to the user in good faith.
5. `swapForGas` executes inside the attacker-controlled contract, which can withhold repayment, redirect swapped proceeds, or manipulate `GetAmountIn`, capturing user tokens and/or the proposer's lent KAIA — the exact "malicious feeBurner takes the fees for itself" pattern from the source report, reproduced through Kaia's KIP-247/KIP-149 admin-controlled address mechanism.

func (g *GaslessModule) updateAddresses(header *types.Header) error {
	g.gaslessInfoMu.Lock()
	defer g.gaslessInfoMu.Unlock()

	swapRouter, tokens, err := getGaslessInfo(g.Chain, header)
	// proceed even if there is something wrong with multicall contract
	if err != nil {
		g.swapRouter = common.Address{}
		g.allowedTokens = map[common.Address]bool{}
		logger.Warn("there is something wrong with multicall contract", "err", err.Error())
		return nil
	}

	g.swapRouter = swapRouter

	g.allowedTokens = map[common.Address]bool{}
	for _, addr := range tokens {
		// all tokens are allowed if nil
		if g.GaslessConfig.AllowedTokens == nil {
			g.allowedTokens[addr] = true
		}
		for _, allowed := range g.GaslessConfig.AllowedTokens {
			if addr == allowed {
				g.allowedTokens[addr] = true
			}
		}
	}

	return nil
}

### Block building rules

Upon detection of GaslessTxs, the following logics are executed:

- Per sender, if exists, GaslessApproveTx is relocated before GaslessSwapTx.
- LendTxGenerator is prepended before GaslessApproveTx.
- A new bundle is generated which contain either `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` or `[LendTxGenerator, GaslessSwapTx]`
- If the bundle has conflict with any previous bundles, it is excluded from the returned bundle list.
