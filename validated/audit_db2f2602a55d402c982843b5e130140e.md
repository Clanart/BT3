### Title
Unchecked u64 addition/multiplication overflow in `SignableTransaction::new` bypasses the insufficient-funds check and creates a signable consensus-invalid transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The fuel-core bug class — an arithmetic operation (`abs()` on `i128::MIN`) that overflows on an edge-case input — maps directly onto `SignableTransaction::new` in `bitcoin-serai`, which performs multiple unchecked `u64` additions and one multiplication over attacker-influenced payment amounts and fee parameters. Wrapping arithmetic defeats the `NotEnoughFunds` solvency check, and `SignableTransaction::fee()` then performs an unchecked subtraction that can underflow.

### Finding Description
In `SignableTransaction::new`:

- `payment_sat` is a plain `sum::<u64>()` over caller-supplied payment amounts (`send.rs:187`). Two payments of e.g. `u64::MAX / 2 + 1` sats each pass the per-payment `DUST` check (`send.rs:165-169`) but wrap to a small value on addition.
- `needed_fee = fee_per_vbyte * vbytes` is an unchecked multiply (`send.rs:206`) which can wrap or panic.
- The solvency check `if input_sat < (payment_sat + needed_fee)` (`send.rs:215`) uses unchecked `+`; if `payment_sat` already wrapped, or the addition itself overflows, the comparison is evaluated against a wrapped value and `NotEnoughFunds` is never raised.
- The change path computes `input_sat.checked_sub(payment_sat + fee_with_change)` (`send.rs:228`) — the inner addition `payment_sat + fee_with_change` is still unchecked and can wrap before the `checked_sub`.
- `SignableTransaction::fee()` (`send.rs:139-141`) computes `sum(inputs) - sum(outputs)` with a raw `-`; once the solvency check is bypassed, outputs can exceed inputs and this underflows — a panic in debug builds, silent wrap in release.

The resulting `SignableTransaction` is passed to `multisig()` → `TransactionMachine`, which produces valid FROST/Schnorr signature shares (`send.rs:383-391`) over a sighash committing to output values exceeding `MAX_MONEY` and the true input sum.

### Impact Explanation
The signers' solvency invariant (`NotEnoughFunds`) is bypassed by wrapped arithmetic. The multisig signs a transaction that is consensus-invalid (outputs exceed inputs / 21M cap), so `complete()` returns a transaction that can never be mined — the signing round is wasted and, in debug builds, the wrapping arithmetic or the `fee()` underflow panics outright, crashing the signing participant. This is a reachable, deterministic abort of threshold signing plus reporting of a fabricated fee value, analogous to fuel-core's overflow panic in `da_change()`.

### Likelihood Explanation
Payment amounts and `fee_per_vbyte` flow into `SignableTransaction::new` from transaction data constructed for signing; nothing in this function validates that amounts are ≤ `Amount::MAX_MONEY` or that sums fit in `u64`. Any input producing `sum(amounts) > u64::MAX` or `fee_per_vbyte * vbytes > u64::MAX` triggers the wrap. The counter-consideration is that the final transaction is invalid on the Bitcoin network, limiting impact to DoS of the signing session and incorrect fee reporting rather than theft — hence Medium rather than High.

### Recommendation
Use `checked_add`/`checked_mul`/`checked_sum` for `payment_sat`, `input_sat`, `payment_sat + needed_fee`, `payment_sat + fee_with_change`, and `fee_per_vbyte * vbytes`, mapping failures to `TransactionError::NotEnoughFunds`/`TooLowFee`. Additionally validate each payment amount against `bitcoin::Amount::MAX_MONEY` and make `fee()` use `checked_sub` with an invariant assertion that outputs cannot exceed inputs.
