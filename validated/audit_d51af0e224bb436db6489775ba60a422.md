### Title
Operator Automation Reimbursement Permanently Blocked When All Kickoff Connectors Are Used — (`core/src/operator.rs`)

### Summary

In the operator's automation path, `create_burn_unused_kickoff_connectors_txhandler` is called unconditionally with a list of unused kickoff connector indices that can be empty when all connectors have been legitimately used. Because `create_burn_unused_kickoff_connectors_txhandler` hard-errors on an empty input, the `?` propagation aborts the entire function before `ReadyToReimburse` and the next round tx are ever queued. The operator's fronted BTC (one full `bridge_amount`) is stuck until manual intervention.

### Finding Description

In `core/src/operator.rs` the automation function that queues the `ReadyToReimburse` and next-round transactions first builds `unspent_kickoff_connector_indices` by iterating over every kickoff slot and checking the database for an associated kickoff txid: [1](#0-0) 

When a kickoff txid exists for every slot (i.e., the operator used all `num_kickoffs_per_round` connectors — the normal busy-bridge case), the loop exits with `unspent_kickoff_connector_indices` empty. The code then unconditionally calls: [2](#0-1) 

`create_burn_unused_kickoff_connectors_txhandler` explicitly rejects an empty slice: [3](#0-2) 

The `?` on line 1139 propagates this error upward, so neither the `ReadyToReimburse` tx nor the next round tx is ever inserted into the tx-sender queue: [4](#0-3) 

The manual `get_reimbursement_txs` path handles the all-used case correctly (it checks `unspent_kickoff_utxos.is_empty()` before branching), but the automation path has no such guard: [5](#0-4) 

### Impact Explanation

The operator fronts `bridge_amount` of BTC for each withdrawal. Reimbursement requires the `ReadyToReimburse` → next-round → `Reimburse` chain to execute. When automation is enabled and all kickoff connectors are used, the automation function errors out before queuing any of those transactions. The operator's fronted BTC remains locked in the `MoveToVault` UTXO indefinitely until a human notices the silent failure and manually calls `GetReimbursementTxs`. In a production bridge running unattended automation, this constitutes a material, time-sensitive liveness loss of operator collateral.

### Likelihood Explanation

The trigger condition — all `num_kickoffs_per_round` connectors used — is the **expected steady-state** for a bridge with continuous withdrawal demand. Every round in which the operator services the maximum number of withdrawals hits this path. No attacker action is required; normal bridge operation is sufficient.

### Recommendation

Guard the burn-tx creation and queuing with an emptiness check, mirroring the logic already present in the manual path:

```rust
if !unspent_kickoff_connector_indices.is_empty() {
    let mut burn_tx = create_burn_unused_kickoff_connectors_txhandler(
        &current_round_txhandler,
        &unspent_kickoff_connector_indices,
        &self.signer.address,
        self.config.protocol_paramset(),
    )?;
    self.signer.tx_sign_and_fill_sigs(&mut burn_tx, &[], Some(&mut tweak_cache))
        .wrap_err("Failed to sign burn unused kickoff connectors tx")?;
    self.tx_sender.insert_try_to_send(dbtx, /* ... */ burn_tx.get_cached_tx(), /* ... */).await?;
}
// then unconditionally queue ReadyToReimburse and next round tx
```

### Proof of Concept

1. Operator has `num_kickoffs_per_round = N` kickoff connectors in the current round.
2. All N connectors are used for deposits; each has a kickoff txid recorded in the DB.
3. Automation triggers the function that queues `ReadyToReimburse`.
4. The loop at lines 1089–1130 finds a kickoff txid for every connector → `unspent_kickoff_connector_indices` is empty.
5. `create_burn_unused_kickoff_connectors_txhandler(&current_round_txhandler, &[], ...)` is called.
6. The function returns `Err("create_burn_unused_kickoff_connectors_txhandler called with no unused kickoff connectors")`.
7. The `?` at line 1139 propagates the error; lines 1150–1217 are never reached.
8. `ReadyToReimburse` and the next round tx are never queued.
9. The operator's fronted BTC remains locked in `MoveToVault` until manual intervention.
