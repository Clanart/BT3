## Title
Wallet auto-converts an existing CAT wallet into an RCAT/CR-CAT wallet based on asset-ID collision, silently exposing previously-freely-spendable CAT balances to revocation/authorized-provider restrictions - (File: chia/wallet/cat_wallet/cat_wallet.py)

### Summary
`CATWallet.identify()` decides, per incoming coin state, what kind of CAT wallet a coin belongs to by uncurrying the puzzle and matching the TAIL hash (`asset_id`). If the observed coin is a revocation-layer CAT (RCAT) or credential-restricted CAT (CR-CAT) whose TAIL hash equals the `limitations_program_hash` of an already-existing plain `CATWallet`, the wallet state manager silently upgrades/replaces that CAT wallet in place with an `RCATWallet` or `CRCATWallet` via `RCATWallet.convert_to_revocable()` / `CRCATWallet.convert_to_cr()`. [1](#0-0) 

### Finding Description
`identify()` uncurries the coin's puzzle; if it doesn't match a plain CAT puzzle for the known TAIL hash, it checks whether the inner layer is a `revocation_layer` (→ `RCATWallet`) or a CR credential-restriction layer (→ `CRCATWallet`). [2](#0-1) 

If a matching plain `CATWallet` already exists for that same TAIL hash (`asset_id`), the code performs an automatic, permissionless conversion of the *existing* wallet object into the new revocable/credential-restricted type, rather than treating the new coin as unrelated or untrusted: [3](#0-2) 

This is the same bug class as the KyberSwap `isRToken` report: a third party can, by simply causing the wallet to observe *one* coin of a particular shape sharing an asset identity with an existing pool/asset the victim already trades, flip global per-asset classification state that changes how the victim's coins are treated going forward — without the victim's consent and potentially without their knowledge, since this happens automatically during sync (`determine_coin_type` → `identify`). [4](#0-3) 

For `RCATWallet`, there is a guard: conversion is refused if the existing CAT wallet's lineage store is not empty, i.e. it already holds/held CAT coins: [5](#0-4) 

I was **not able to fully verify** whether `CRCATWallet.convert_to_cr()` has an equivalent "reject if not empty" guard — my last read attempts to inspect `chia/wallet/vc_wallet/cr_cat_wallet.py` lines ~750–804 failed due to a tool/parameter error before the session ended, and I could not re-issue the call. This is the crux of whether the CR-CAT path is actually exploitable against a wallet that already holds a plain-CAT balance of the same TAIL, or is likewise gated to only convert empty/newly-created wallets.

### Impact Explanation
If the CR-CAT conversion path lacks the same "lineage store must be empty" guard that `RCATWallet.convert_to_revocable` has, then an attacker who can mint (or otherwise cause a spend of) a CR-CAT coin sharing the same TAIL hash as an existing, freely-tradeable CAT that a victim already holds could cause the victim's wallet to silently reclassify their existing CAT wallet as a `CRCATWallet`. From that point on, the victim's own coin-selection, spend construction (`make_inner_solution`, `select_coins`) and puzzle derivation logic (`puzzle_hash_for_pk`, `inner_puzzle_for_cat_puzhash`) would go through the CR-CAT / revocation-layer code paths, which require VC-based authorization or backdoor access controlled by the credential's `authorized_providers`/`proof_provider` (a DID chosen by whoever minted the CR-CAT), not by the victim. This could disrupt or block the victim's ability to spend their own previously-liquid CAT balance, or, if combined with a matching `authorized_providers` an attacker controls, could impact the victim's ability to freely move funds. This maps to the "spend-triggered transaction-processing halt" / coin-identity-forging class explicitly listed as acceptable impact.

### Likelihood Explanation
The trigger is fully reachable by an ordinary, unprivileged party: any wallet user or spend-bundle submitter can create a CR-CAT/RCAT eve coin using an existing TAIL hash (assuming the TAIL program itself permits re-issuance, e.g. permissionless/anyone-can-mint TAILs), and the victim's wallet performs this classification automatically during normal chain sync (`_add_coin_state` → `determine_coin_type` → `CATWallet.identify`) with no user confirmation. This requires no privileged access, no malicious peer/node behavior, and no cryptographic breaks — it is a pure wallet-logic/state-machine issue triggered by an ordinary spend.

### Recommendation
1. Confirm (and if missing, add) a guard in `CRCATWallet.convert_to_cr()` mirroring `RCATWallet.convert_to_revocable()`'s check that the target `CATWallet`'s lineage store is empty before converting, so wallets holding an existing balance of a plain CAT of a given TAIL are never silently reclassified.
2. Beyond the empty-lineage guard, consider not doing automatic, silent wallet-type conversion at all for TAILs the user has already actively used as a plain CAT; instead, surface a new/separate wallet entry (as already happens for genuinely new "stray" CATs) and require explicit user action to treat mixed-type coins of the same TAIL as one unified wallet.
3. Add regression tests analogous to `test_cat_change_detection` that specifically exercise: existing populated `CATWallet` for TAIL `X` receiving a CR-CAT/RCAT coin also minted under TAIL `X`, asserting no silent conversion occurs and the existing CAT balance/authority remains unaffected.

### Proof of Concept
1. Victim runs a wallet with a `CATWallet` for TAIL `X` (a TAIL program that supports permissionless re-issuance) and has already received/spent CAT coins under it — `lineage_store` is non-empty.
2. Attacker mints an "eve" CR-CAT coin (or RCAT coin) using the same TAIL `X`, curried with an `authorized_providers`/DID or `hidden_puzzle_hash` the attacker controls, and gets it confirmed on chain (e.g. sent to any address, including one the victim's wallet is watching, or observed via `automatically_add_unknown_cats`).
3. Victim's wallet syncs this coin. `WalletStateManager._add_coin_state` calls `determine_coin_type`, which calls `CATWallet.identify()`. [6](#0-5) 
4. `identify()` uncurries the new coin, detects it is not a plain CAT puzzle, matches it as CR-CAT (or RCAT), finds the existing plain `CATWallet` for TAIL `X`, and — for the RCAT path — checks `cat_wallet.lineage_store.is_empty()`. Because the CR-CAT path's equivalent check could not be verified in this session, if it is absent, `CRCATWallet.convert_to_cr()` proceeds to overwrite the wallet DB entry for that wallet id with a `CRCATInfo` for `authorized_providers` chosen by the attacker. [7](#0-6) 
5. Going forward, the victim's wallet (`self.wallets[wallet_info.id]`) is a `CRCATWallet`, and any subsequent spend of the victim's pre-existing CAT balance under TAIL `X` is now constructed via CR-CAT puzzle/solution logic gated on VC approval from the attacker-chosen `authorized_providers`, rather than the victim's original unrestricted CAT puzzle logic.

**Caveat / open item:** Full confirmation requires inspecting `CRCATWallet.convert_to_cr()` (`chia/wallet/vc_wallet/cr_cat_wallet.py`, function definition location not fully retrieved in this session) to check whether it contains a lineage-emptiness guard equivalent to `RCATWallet.convert_to_revocable`. If it does contain an equivalent guard, the practical impact of this finding is limited to newly-created/empty wallets receiving their first coin as CR-CAT/RCAT rather than plain CAT — a narrower race-condition-style issue rather than a live-balance hijack, and would likely not meet the Medium+ bar on its own.
