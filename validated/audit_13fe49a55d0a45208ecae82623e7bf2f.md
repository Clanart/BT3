[1](#0-0) ### Title
Malformed per-input signature-share vector causes remote signing-session panic - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`TransactionSignatureMachine::complete` accepts one `Vec<SignatureShare<Secp256k1>>` per participant and assumes each vector contains one share for every transaction input. [2](#0-1)  A participant can provide an empty or truncated vector, causing `shares.remove(0)` to panic before the inner FROST machine can validate the participant map. [3](#0-2) 

### Finding Description
For a transaction with `n` inputs, `TransactionSignatureMachine` stores `n` per-input `AlgorithmSignatureMachine` instances. [4](#0-3)  Its associated share type is `Vec<SignatureShare<Secp256k1>>`, implicitly requiring one share per input. [5](#0-4) 

`complete` iterates over all transaction inputs and calls `shares.remove(0)` on every participant-provided vector. [3](#0-2)  There is no prior check that each vector has length equal to `self.tx.input.len()` or that it is non-empty. [1](#0-0)  Consequently, a participant can submit a syntactically valid but empty `Vec`, making `Vec::remove(0)` panic while constructing the argument to `schnorr.complete`. [3](#0-2) 

Although `read_share` reads the locally expected number of shares from a byte stream, the public completion boundary still accepts attacker-controlled structured messages and does not defensively validate their semantic length before indexing them. [6](#0-5) 

### Impact Explanation
An unprivileged signing participant can terminate the local transaction-completion task by submitting an empty or truncated per-input share vector. [7](#0-6)  In an application that does not isolate this call or treats signing-machine completion as infallible, repeated malformed submissions can deny transaction-signing availability. [8](#0-7) 

### Likelihood Explanation
The trigger requires only control of a participant key in the supplied share map and a malformed `SignatureShare` vector; it does not require a valid scalar, signature share, or proof. [7](#0-6)  The panic occurs before `AlgorithmSignatureMachine::complete` can perform its participant-map validation. [3](#0-2) [9](#0-8) 

### Recommendation
Validate every participant’s share vector before draining it. In `TransactionSignatureMachine::complete`, reject vectors whose length differs from `self.sigs.len()` / `self.tx.input.len()` and replace `remove(0)` with checked removal that returns `FrostError` rather than panicking.

### Proof of Concept
```rust
use std::collections::HashMap;

use frost::{curve::Secp256k1, Participant};
use frost::sign::{SignatureMachine, SignatureShare};
use serai_bitcoin::wallet::TransactionSignatureMachine;

fn malformed_share_vector_crashes(
  machine: TransactionSignatureMachine,
  attacker: Participant,
) {
  let mut shares: HashMap<Participant, Vec<SignatureShare<Secp256k1>>> = HashMap::new();

  // Well-typed attacker message, but missing every per-input share.
  shares.insert(attacker, vec![]);

  // Panics at `shares.remove(0)` before validating the signing set.
  let _ = machine.complete(shares);
}
```

The vulnerable operation is `shares.remove(0)` inside the per-input loop. [3](#0-2)

impl SignatureMachine<Transaction> for TransactionSignatureMachine {
  type SignatureShare = Vec<SignatureShare<Secp256k1>>;

  fn read_share<R: Read>(&self, reader: &mut R) -> io::Result<Self::SignatureShare> {
    self.sigs.iter().map(|sig| sig.read_share(reader)).collect()
  }

  fn complete(
    mut self,
    mut shares: HashMap<Participant, Self::SignatureShare>,
  ) -> Result<Transaction, FrostError> {
    for (input, schnorr) in self.tx.input.iter_mut().zip(self.sigs.drain(..)) {
      let sig = schnorr.complete(
        shares.iter_mut().map(|(l, shares)| (*l, shares.remove(0))).collect::<HashMap<_, _>>(),
      )?;

      let mut witness = Witness::new();
      witness.push(sig);
      input.witness = witness;
    }

    Ok(self.tx)
  }
