## Analysis

**Bug class in the report:** libpango failed to validate/sanitize a Unicode text buffer before further processing it, so a downstream consumer (hexchat) that trusted the text to be well-formed Unicode crashed on invalid sequences.

**Consuming-application exposure assumption:** any Protobuf embedder that (a) accepts a bounded binary Protobuf message from an untrusted client via a public parse API, and (b) later re-serializes that message to ProtoJSON for a downstream system that expects RFC 8259-valid JSON (valid UTF-8 text). Protobuf itself has no RPC endpoint, but the JSON encoder is a public serialization API whose contract is "produce valid JSON," and many callers (browsers, JSON parsers, logging pipelines) assume that contract holds.

## The Protobuf analog

`upb`'s wire decoder only enforces UTF-8 validity for **proto3** string fields by default. For **proto2** string fields, UTF-8 is *not* validated unless the caller explicitly passes `kUpb_DecodeOption_AlwaysValidateUtf8`: [1](#0-0) 

and validation for proto2 can only be forced after the fact, confirming it's off by default: [2](#0-1) 

That means an attacker can send a bounded, otherwise well-formed binary Protobuf message through the public `upb_Decode` API with a proto2 `string` field containing structurally invalid UTF-8 bytes, and the parse **succeeds**.

The upb JSON encoder (`upb/json/encode.c`, and its vendored copies embedded in the Ruby and PHP native extensions) then serializes that string field by copying non-ASCII bytes through verbatim, with an explicit comment acknowledging the unchecked trust assumption: [3](#0-2) [4](#0-3) [5](#0-4) 

No UTF-8 check exists anywhere in this encode path — `jsonenc_string`/`jsonenc_stringbody` call straight into `jsonenc_put_escaped_char`, which only special-cases ASCII control characters and otherwise blindly emits the raw byte. The result is JSON output containing byte sequences that are not valid UTF-8 inside a JSON string literal, violating the JSON spec's requirement that string values be valid Unicode text.

This is a genuine, non-hypothetical gap because the C++ ProtoJSON writer in the same codebase *does* defend against exactly this case: it decodes each UTF-8 scalar and substitutes a safe placeholder (a literal space) whenever decoding fails, rather than emitting the raw invalid bytes: [6](#0-5) [7](#0-6) 

So the invariant "JSON output is always valid UTF-8/JSON" is enforced in the C++ ProtoJSON path but is missing in the `upb`-based JSON encoder that backs Ruby, PHP, and other `upb`-based language runtimes, for any proto2 string field (default UTF-8 checking off) whose value reaches JSON encoding.

### Title
Malformed proto2 string bytes are echoed unvalidated into ProtoJSON output by the upb JSON encoder - (File: `upb/json/encode.c`)

### Summary
`upb_Decode` does not validate UTF-8 for proto2 `string` fields by default, and `upb_JsonEncode` (shared by upb, Ruby, and PHP bindings) has no UTF-8 validation/sanitization step of its own when writing string values to JSON, relying entirely on the (absent) decode-time check. An attacker-controlled bounded binary Protobuf message with invalid UTF-8 in a proto2 string field parses successfully and is re-emitted as syntactically-invalid JSON text.

### Finding Description
- `upb_Decode` skips UTF-8 validation for proto2 string fields unless `kUpb_DecodeOption_AlwaysValidateUtf8` is explicitly passed [1](#0-0) .
- The JSON encode path (`jsonenc_scalar` → `jsonenc_string` → `jsonenc_stringbody` → `jsonenc_put_escaped_char`) performs no UTF-8 structural check; non-ASCII, non-control bytes are written through verbatim under the comment "We rely on the string being valid UTF-8" [3](#0-2) .
- The identical unchecked pattern is vendored into the Ruby and PHP extension sources, so this affects every language binding built on `upb`'s JSON encoder [4](#0-3) [5](#0-4) .
- By contrast, the C++ ProtoJSON writer explicitly decodes each UTF-8 scalar and substitutes a safe space character on decode failure before writing, proving the missing check is not an accepted cross-language design decision but a genuine gap in the `upb` C implementation [8](#0-7) .

### Impact Explanation
The produced JSON document contains byte sequences that are not valid UTF-8 inside a string literal, violating RFC 8259. Any downstream system that assumes the Protobuf-produced JSON is well-formed (browsers, strict JSON parsers, logging/indexing pipelines, other language JSON libraries) may fail to parse it, throw unexpected exceptions, silently corrupt data, or — mirroring the referenced Pango CVE's application-crash outcome — crash when a fragile consumer processes the malformed Unicode text. This is an integrity/availability issue in the JSON *serialization* contract rather than in the binary decoder itself.

### Likelihood Explanation
High for reachability: proto2 schemas with `string` fields are common (many long-lived production `.proto` files predate proto3), and JSON output is a first-class supported feature. An attacker only needs a public, bounded binary Protobuf parse API in front of a service, plus that service later JSON-encoding the received message (a very common pattern for logging, gateways, or REST/gRPC-transcoding proxies built on `upb`, Ruby, or PHP protobuf bindings).

### Recommendation
Add a UTF-8 structural validity check (mirroring `utf8_range::IsStructurallyValid`/the C++ writer's `ConsumeUtf8Scalar` handling) inside `jsonenc_put_escaped_char`/`jsonenc_stringbody` in `upb/json/encode.c` (and keep the Ruby/PHP vendored copies in sync), replacing invalid byte sequences with `U+FFFD` or an equivalent safe escape instead of copying raw bytes through. Alternatively, make UTF-8 validation mandatory for all string fields at decode time regardless of proto2/proto3 syntax when the message will be JSON-encoded, or document and gate this explicitly for callers relying on `upb_JsonEncode`.

### Proof of Concept
Conceptual, using existing test helpers already present in the repo:
1. Build a proto2 message type with a `string` field (e.g., using `upb_test_TestUtf8Proto2String` as in `upb/message/utf8_test.cc`).
2. Set the field to `"\xff"` (invalid UTF-8) and serialize it to bytes with `upb_test_TestUtf8Proto2String_serialize` — this mirrors `GetBadUtf8Payload` [9](#0-8) .
3. Call `upb_Decode(...)` with default options (`0`) — parse succeeds because proto2 strings aren't validated by default [1](#0-0) .
4. Call `upb_JsonEncode` on the resulting message — the output buffer will contain the raw `\xff` byte embedded in a JSON string literal, verifiable by checking that `!utf8_range::IsStructurallyValid(json_output)` for the string-value region, since `jsonenc_put_escaped_char` performs no such check [10](#0-9) .

// Parses a single UTF-8-encoded Unicode scalar from `str`. Returns a pair of
// the scalar and the UTF-8-encoded content corresponding to it from `str`.
//
// Returns U+FFFD on failure, and consumes an unspecified number of bytes in
// doing so.
static Utf8Scalar ConsumeUtf8Scalar(absl::string_view& str) {
  ABSL_DCHECK(!str.empty());
  uint32_t scalar = static_cast<uint8_t>(str[0]);
  const char* start = str.data();
  size_t len = 1;

  str = str.substr(1);

  // Verify this is valid UTF-8. UTF-8 is a varint encoding satisfying
  // one of the following (big-endian) patterns:
  //
  // 0b0xxxxxxx
  // 0b110xxxxx'10xxxxxx
  // 0b1110xxxx'10xxxxxx'10xxxxxx
  // 0b11110xxx'10xxxxxx'10xxxxxx'10xxxxxx
  //
  // We don't need to decode it; just validate it.
  int lookahead = 0;
  switch (absl::countl_one(static_cast<uint8_t>(scalar))) {
    case 0:
      break;
    case 2:
      lookahead = 1;
      scalar &= (1 << 5) - 1;
      break;
    case 3:
      lookahead = 2;
      scalar &= (1 << 4) - 1;
      break;
    case 4:
      lookahead = 3;
      scalar &= (1 << 3) - 1;
      break;
    default:
      scalar = kErrorSentinel;
      break;
  }

  for (int i = 0; i < lookahead; ++i) {
    if (str.empty()) {
      scalar = kErrorSentinel;
      break;
    }

    uint8_t next = str[0];
    str = str.substr(1);
    ++len;

    // Looking for top 2 bits are 0b10.
    if (next >> 6 != 2) {
      scalar = kErrorSentinel;
      break;
    }
    next &= (1 << 6) - 1;
    scalar <<= 6;
    scalar |= next;
  }

  if (scalar > kMaxCodePoint) {
    scalar = kErrorSentinel;
  }

  return {scalar, absl::string_view(start, len)};
}

// Decides whether we must escape `scalar`.
//
// If the given Unicode scalar would not use a \u escape, `custom_escape` will
// be set to a non-empty string.
static bool MustEscape(uint32_t scalar, absl::string_view& custom_escape) {
  switch (scalar) {
    // These escapes are defined by the JSON spec. We do not escape /.
    case '\n':
      custom_escape = R"(\n)";
      return true;
    case '\r':
      custom_escape = R"(\r)";
      return true;
    case '\t':
      custom_escape = R"(\t)";
      return true;
    case '\"':
      custom_escape = R"(\")";
      return true;
    case '\f':
      custom_escape = R"(\f)";
      return true;
    case '\b':
      custom_escape = R"(\b)";
      return true;
    case '\\':
      custom_escape = R"(\\)";
      return true;

    case kErrorSentinel:
      // Decoding failure turns into spaces, *not* replacement characters. We
      // handle this separately from "normal" spaces so that it follows the
      // escaping code-path.
      //
      // Note that literal replacement characters in the input string DO NOT
      // get turned into spaces; this is only for decoding failures!
      custom_escape = " ";
      return true;
