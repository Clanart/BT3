### Title
Out-of-range participant index in blame adjudication causes `HashMap` index panic (DoS) - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
CVE-2022-43035 is a heap-buffer-overflow on attacker-controlled bytes causing a crash (DoS). The closest Serai analog is unbounded indexing into `HashMap`s keyed by `Participant` during blame resolution: `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `self.enc_keys[&decryptor]` and `self.commitments[&sender]` without verifying the participant indexes are in `1..=n`, so an accusation naming an out-of-range participant panics the evaluating party.

### Finding Description
`Participant::new` accepts any non-zero `u16`, i.e. up to 65535, independently of the actual `n` of the DKG ( [1](#0-0) ). `Participant` values carried in accusations are therefore not constrained to `1..=n`.

During blame evaluation, `BlameMachine::blame` / `AdditionalBlameMachine::blame` pass a caller/attacker-influenced `sender` and `recipient` into `blame_internal`, which calls `Decryption::decrypt_with_proof` ( [2](#0-1) ). Inside `decrypt_with_proof`, when a `proof` is supplied, the DLEq verify arguments evaluate `self.enc_keys[&decryptor]` directly ( [3](#0-2) ). `enc_keys` only contains the registered participants (`1..=n`, populated via `register`), so a `recipient`/`decryptor` outside that set causes `HashMap`'s `Index` impl to panic.

Likewise, if the decryption succeeds, `blame_internal` evaluates `self.commitments[&sender]` ( [4](#0-3) ), which panics for any `sender` not present in the commitments map — e.g. a participant index `> n`, since `commitments` is only keyed by `all_participant_indexes()` (`1..=n`) in both `calculate_share` and `AdditionalBlameMachine::new` ( [5](#0-4) ).

Notably, `AdditionalBlameMachine` is explicitly designed for parties who did *not* participate in the DKG to adjudicate blame, so this code path is reachable purely by evaluating third-party accusations/messages.

### Impact Explanation
A participant (or, via `AdditionalBlameMachine`, any party able to get an accusation evaluated) can supply a blame statement whose `sender` or `recipient` is a valid non-zero `Participant` greater than `n`. The evaluating node hits `self.enc_keys[&decryptor]` or `self.commitments[&sender]` and panics — the same crash-on-malformed-input class as the CVE's heap-buffer-overflow DoS. The panic aborts blame adjudication (and, depending on the caller, the DKG completion flow), rather than returning an error identifying a faulty party.

### Likelihood Explanation
Reachability requires a blame accusation naming an out-of-range participant to be evaluated. The library trusts the `sender`/`recipient` arguments (which arrive alongside `EncryptedMessage::read`/`EncryptionKeyProof::read` inputs) without a bounds check, even though it bounds-checks participant indexes elsewhere (e.g. `ThresholdParams::new` rejects `i > n`, and `sign` rejects `included[last] > n`). Exploitation is trivial — one crafted accusation — but only fires during the blame path, so it is a conditional rather than steady-state DoS, consistent with Medium severity.

### Recommendation
Validate `sender` and `recipient` against the known participant set (`1..=n` / presence in `commitments`/`enc_keys`) at the top of `blame_internal` and `decrypt_with_proof`, returning a defined `PedPoPError`/blame result instead of indexing. Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get()` + error handling.

### Proof of Concept
Conceptual: construct an `AdditionalBlameMachine` via `AdditionalBlameMachine::new(context, n, commitment_msgs)` for a DKG with `n` participants (so `enc_keys`/`commitments` cover `Participant(1)..=Participant(n)`). Then call:

```rust
machine.blame(
    Participant::new(n + 1).unwrap(),        // sender: valid Participant, not in commitments
    Participant::new(1).unwrap(),            // recipient
    any_validly_parsed_encrypted_message,    // EncryptedMessage::read output
    Some(encryption_key_proof),              // EncryptionKeyProof::read output
);
```

With `recipient` in range but `sender = n + 1`, execution reaches `self.commitments[&sender]` in `blame_internal` and panics on the missing key. Alternatively, `blame(Participant::new(1).unwrap(), Participant::new(n + 1).unwrap(), msg, Some(proof))` panics earlier on `self.enc_keys[&decryptor]` inside `decrypt_with_proof` ( [6](#0-5) ).

Caveat: whether an accusation with an out-of-range participant reaches `blame` depends on the integrator (e.g. coordinator transaction parsing), which is out of scope; the panic itself is fully within the in-scope `pedpop` crate.
