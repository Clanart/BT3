### Title
Attacker-controlled duplicate DKG message panics the node via `assert!` in `Decryption::register` (CVE-2017-2544 analog: crafted input → application crash) - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2017-2544 is a WebKit memory-corruption/crash reachable by crafted remote content. Serai is memory-safe Rust, so the honest analog of the class is a reachable panic (abort-level crash) on attacker-controlled input. In PedPoP's encryption layer, `Decryption::register` — fed by `Encryption::register` with messages deserialized via `EncryptionKeyMessage::read` from untrusted peer bytes — panics with `assert!` if the same `Participant` submits a second encryption-key message.

### Finding Description
`EncryptedMessage::read` / `EncryptionKeyMessage::read` accept arbitrary peer-supplied bytes (`C::read_G`, `SchnorrSignature::read`, `E::read`), all of which correctly enforce canonical encodings — so no corruption occurs in parsing itself. However, after deserialization, the caller hands each message to `Encryption::register` → `Decryption::register`: [1](#0-0) 

The `assert!(!self.enc_keys.contains_key(&participant))` fires on any second registration for the same `Participant`. The codebase itself acknowledges the library "does not handle networking, it is unable to detect if any participant is so faulty" (crypto/dkg/pedpop/src/lib.rs:98-101) — meaning a duplicated/malformed delivery of a participant's `EncryptionKeyMessage` reaches `register` twice and panics the process.

A second reachable panic on the same data flow exists in `decrypt_with_proof` / `encrypt`, which index `self.enc_keys[&decryptor]` / `self.enc_keys[&participant]` directly; indexing a `HashMap` panics on a missing key if the accusation/blame flow is invoked for a participant whose registration was never recorded: [2](#0-1) [3](#0-2) 

### Impact Explanation
An unprivileged DKG participant causes the victim node's key-generation/blame-handling code path to panic, aborting the session (and, depending on the caller's panic strategy, the entire process — analogous to the "application crash" impact of the CVE). Since DKG/reshare sessions are not restartable without re-coordination, a single crafted duplicate message reliably kills the victim's participation.

### Likelihood Explanation
The trigger requires only that the attacker emit two `EncryptionKeyMessage`s under their own `Participant` index — no collusion, no leaked material, no special timing. It depends on the integrator forwarding all received messages to `register` rather than deduplicating by participant, which the library's own comments admit it cannot enforce.

### Recommendation
Replace the `assert!` in `Decryption::register` with an error return (`Err(io::Error::other("duplicate encryption key registration"))`), and replace `enc_keys[&participant]` / `enc_keys[&decryptor]` indexing with `.get(...).ok_or(...)` so unregistered or duplicate participants produce graceful failures instead of panics.

### Proof of Concept
```rust
// Two messages read from attacker bytes for the same Participant index
let msg1 = EncryptionKeyMessage::<C, M>::read(&mut bytes1, params)?;
let msg2 = EncryptionKeyMessage::<C, M>::read(&mut bytes2, params)?;
enc.register(p, msg1);
enc.register(p, msg2); // panics: "Re-registering encryption key for a participant"
```

Note: this is a crash/DoS analog only (Medium). I did not find a reachable path from public inputs that produces secret leakage or signature forgery from this class — deserialization in `read_F`/`read_G`, `Commitments::read`, `ThresholdKeys::read`, and `EncryptedMessage::read` all enforce canonical encodings and bounded allocations.
