### Title
Hookify `RuleEngine` tool/field matching gap lets `MultiEdit` bypass `old_text`/`old_string` block rules and `tool_matcher`-scoped rules meant for `Edit`/`Write` - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field` and `RuleEngine._matches_tool` hard-code exact tool-name equality and per-tool field mappings for only `Bash`, `Write`, `Edit`, and `MultiEdit` (partially). `MultiEdit` — a tool that performs the same find/replace file mutation as `Edit` and is explicitly documented as part of the same "file" event class — is missing `old_text`/`old_string` field support and fails exact-string `tool_matcher` checks scoped to `"Edit"`/`"Write"`. An attacker (or a prompt-injected/model-driven action) can perform the exact same dangerous file mutation via `MultiEdit` instead of `Edit`/`Write` and have a configured block rule silently never fire.

### Finding Description
`RuleEngine.evaluate_rules` → `_rule_matches` → `_check_condition` → `_extract_field` is the path exercised on every `PreToolUse` call [1](#0-0) .

Two related gaps allow a rule to "accept only one representation" of an operation and miss the equivalent one:

1. **Missing `old_text`/`old_string` support for `MultiEdit`.** For `Write`/`Edit`, `_extract_field` supports `old_text`/`old_string` by returning `tool_input.get('old_string', '')`, but the `MultiEdit` branch only implements `file_path` and `new_text`/`content` — there is no case for `old_text`/`old_string`, so the function falls through and returns `None`: [2](#0-1) 
`_check_condition` treats a `None` field value as "doesn't match" (`return False`), so any condition on `old_text`/`old_string` can never be satisfied for a `MultiEdit` call, regardless of the actual content being replaced: [3](#0-2) 
Yet `old_text` is a documented, supported field for the `"file"` event, and the docs explicitly state the `"file"` event covers `Edit, Write, MultiEdit tools` [4](#0-3) . The hook dispatcher itself routes `MultiEdit` into the same `'file'` event bucket as `Edit`/`Write`, reinforcing the expectation that `MultiEdit` receives identical protection: [5](#0-4) 

2. **Exact-string `tool_matcher` equality excludes `MultiEdit` from `Edit|Write` scoped rules.** `_matches_tool` splits the matcher on `|` and requires literal membership (`tool_name in patterns`), with no normalization or alias handling: [6](#0-5) . The plugin's own documented example for scoping rules to file-editing tools is `"matcher": "Write|Edit"` [7](#0-6) , which silently omits `MultiEdit` even though `MultiEdit` performs the same class of operation.

Because of these two gaps, an operation that would be reliably blocked when done via `Edit` (e.g., replacing a security check's `old_string` with a malicious `new_string`, or matching a `tool_matcher: "Edit|Write"` rule) is not blocked when the identical semantic edit is performed via `MultiEdit`, since the same-content edits are simply expressed as a list under `edits` rather than top-level `old_string`, and `_extract_field`/`_matches_tool` don't normalize between the two representations.

### Impact Explanation
This is a genuine Security-control bypass: a rule author configures a `block` rule intending to prevent a specific dangerous file mutation (e.g., stripping an auth check, injecting a credential, modifying a `.env`/`CI` file) using the `old_text`/`old_string` field or a `tool_matcher` scoped to `Edit|Write`, and the engine advertises coverage of `MultiEdit` under the same `"file"` event — but the block silently never triggers for `MultiEdit` calls. This routes around the intended blocking/review boundary without any error or indication to the user, matching the "Security-control bypass that silently disables or routes around blocking… boundaries" impact category.

### Likelihood Explanation
No special privilege is required beyond normal use of Claude Code with the hookify plugin's `PreToolUse` enforcement enabled. The bypass is triggered simply by using `MultiEdit` instead of `Edit`/`Write` for the same file change — a completely ordinary tool choice that Claude itself (or a prompt-injected instruction) can make with no user awareness that a different tool sidesteps the configured rule. It is fully deterministic and repeatable.

### Recommendation
- In `_extract_field`, add `old_text`/`old_string` handling for `MultiEdit` by concatenating `old_string` values across `tool_input.get('edits', [])`, mirroring the existing `new_text`/`content` handling.
- In `_matches_tool`, treat `Edit`, `Write`, and `MultiEdit` as an equivalence class (or require rule authors to always include all three), and/or add a canonical "file-edit" tool group that `tool_matcher` values like `Edit|Write` automatically expand to include `MultiEdit`.
- Add regression tests asserting that identical `old_string`/`new_string` content changes are matched identically regardless of whether they are delivered via `Edit` or `MultiEdit`.

### Proof of Concept
Unit test against `RuleEngine.evaluate_rules` in `plugins/hookify/core/rule_engine.py`:

```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-auth-check-removal",
    enabled=True,
    event="file",
    conditions=[
        Condition(field="old_text", operator="contains", pattern="if not is_admin")
    ],
    action="block",
    message="Removing auth check is blocked",
)
engine = RuleEngine()

# Case 1: via Edit -> correctly blocked
edit_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Edit",
    "tool_input": {
        "file_path": "app.py",
        "old_string": "if not is_admin: return",
        "new_string": "",
    },
}
assert engine.evaluate_rules([rule], edit_input) != {}  # expected: blocked

# Case 2: identical semantic change via MultiEdit -> NOT blocked (bug)
multiedit_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "MultiEdit",
    "tool_input": {
        "file_path": "app.py",
        "edits": [
            {"old_string": "if not is_admin: return", "new_string": ""}
        ],
    },
}
assert engine.evaluate_rules([rule], multiedit_input) == {}  # bypass: rule never fires
```

Second PoC for `tool_matcher` gap:
```python
rule2 = Rule(
    name="block-write-edit-secrets",
    enabled=True,
    event="file",
    tool_matcher="Edit|Write",
    conditions=[Condition(field="new_text", operator="contains", pattern="API_KEY")],
    action="block",
    message="Secret detected",
)
multiedit_input2 = {
    "hook_event_name": "PreToolUse",
    "tool_name": "MultiEdit",
    "tool_input": {"file_path": "x.py", "edits": [{"old_string": "", "new_string": "API_KEY=abc"}]},
}
assert engine.evaluate_rules([rule2], multiedit_input2) == {}  # tool_matcher exact-match excludes MultiEdit
```
Both assertions demonstrate that `evaluate_rules` fails to deny an operation that is functionally identical to one it reliably blocks, purely because the operation was expressed through the `MultiEdit` tool representation instead of `Edit`/`Write`.

    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True
```

    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns
```
