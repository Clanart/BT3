### Title
Weight/Fee Calculation Omits the OP_RETURN Output, So Size and Fee Checks Pass on an Undervalued Quantity - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the transaction's weight, virtual size, required fee, and maximum-standard-weight compliance using only the payment outputs. The OP_RETURN `data` output (up to 80 bytes of caller-controlled data) is pushed onto `tx_outs` before the weight calculation but is never fed into `calculate_weight_vbytes`. As a result, all checks derived from the weight (minimum relay fee, `needed_fee`, `MAX_STANDARD_TX_WEIGHT`) are validated against a transaction that is smaller than the one actually constructed — the same bug class as checking `price >= minPrice` before fees reduce the actual payout.

### Finding Description
In `calculate_weight_vbytes`, the transaction template is built only from `payments` and an optional `change` script — there is no parameter for the `data` output [1](#0-0) . However, in `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the weight is computed, and the computed `weight`/`vbytes` never account for it [2](#0-1) . Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is computed on vbytes that exclude the OP_RETURN output (~7–83+ bytes: 1-byte opreturn opcode, push opcode, up to 80 bytes data, 8-byte value, script length) [3](#0-2) .
- The minimum-relay-fee gate `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` and the `weight > MAX_STANDARD_TX_WEIGHT` check both validate the wrong (smaller) transaction [4](#0-3) [5](#0-4) .
- The final `SignableTransaction` embeds `tx_outs` including the OP_RETURN, so the actual broadcast transaction is larger than what was checked [6](#0-5) .

Even when `change` is supplied, `calculate_weight_vbytes` is called with `payments` only, so the OP_RETURN remains uncounted in both the no-change and with-change calculations [7](#0-6) .

### Impact Explanation
- The effective fee rate of the constructed transaction is lower than the requested `fee_per_vbyte`, since `needed_fee` pays for fewer bytes than the transaction actually occupies. For an 80-byte payload this understates the fee by ~80+ bytes worth of weight, which can drop the real fee rate below the relay minimum even though the `TooLowFee` check passed.
- A transaction whose true weight exceeds `MAX_STANDARD_TX_WEIGHT` (400,000 WU) passes the `TooLargeTransaction` check whenever the excess is contributed by the uncounted OP_RETURN output, producing a non-standard transaction that Bitcoin Core nodes will not relay — funds committed as inputs are locked in a TX that cannot propagate.

### Likelihood Explanation
Any caller supplying `data` (a fully public input to `SignableTransaction::new`) triggers the miscalculation deterministically; no special timing or state is needed. The severity scales with payload size and with how close the payments bring the TX to the fee/weight limits, but the underestimation itself is unconditional whenever `data.is_some()`.

### Recommendation
Include the OP_RETURN output in the weight calculation: pass the constructed `data` output (or its serialized size) into `calculate_weight_vbytes`, or compute `weight`/`vbytes` from the finalized `tx_outs` vector instead of from `payments`. Re-derive `needed_fee`, the minimum-fee check, and the `MAX_STANDARD_TX_WEIGHT` check from the complete output set.

### Proof of Concept
```rust
// payments sized so the TX is just under MAX_STANDARD_TX_WEIGHT
let payments = vec![(addr(), 1000); 10000];
// SignableTransaction::new checks weight WITHOUT the OP_RETURN output:
//   calculate_weight_vbytes(tx_ins.len(), payments, None)
// Adding ~83 bytes of output pushes the real TX over the limit,
// yet this returns Ok instead of TooLargeTransaction.
let tx = SignableTransaction::new(inputs, &payments, None, Some(vec![0; 80]), FEE).unwrap();
// tx.transaction().weight() > MAX_STANDARD_TX_WEIGHT, and
// tx.fee() / actual_vsize < FEE, though needed_fee() was computed for FEE.
```

Alternatively, with a minimal `data` payload near the fee floor: `SignableTransaction::new(inputs, &payments, None, Some(vec![0; 80]), 1, ...)` passes the `TooLowFee` check at the vbytes calculated without OP_RETURN, while the real transaction's fee rate is below the relay minimum and will not propagate.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
