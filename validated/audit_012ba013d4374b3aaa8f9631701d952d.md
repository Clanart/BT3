### Title
DkgConfirmer reuses one cached FROST nonce across `sign()` calls whose message (`set_keys_message` over a re-writable `DkgKeyPair`) can change — same-nonce shares over distinct messages leak the validator's MuSig secret key - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
`SigningProtocol::preprocess_internal` derives the FROST preprocess deterministically from a seed cached in `CachedPreprocesses`, keyed only by `context = (b"DkgConfirmer", attempt)`. Neither the message being signed nor the participant set is bound into that key. Every call to `share_internal`/`complete` rebuilds a sign machine via `AlgorithmSignMachine::from_cache` with the *same* seed, hence the *same* nonces, and then calls `machine.sign(preprocesses, msg)` where `msg = set_keys_message(set, removed, key_pair)`. The `key_pair` is attacker-influenceable state: `generated_key_pair` stores it via an unconditional `DkgKeyPair::set` (no guard that a pair was already recorded or already signed for this attempt), and `DkgConfirmed` handling later reads whatever is currently stored. The kernel bug class — a resource that survives the event that should have invalidated it, re-resolved by index at use time — maps exactly: the consumed nonce is re-resolved from the DB cache while the object it was bound to (the key pair/message) is looked up fresh each time.

### Finding Description
- `preprocess_internal` loads-or-creates `CachedPreprocesses[context]` and calls `from_cache`, which seeds `ChaCha20Rng` from the same 32 bytes every time, producing identical `nonces`/`commitments` (signing_protocol.rs:123-147; `seeded_preprocess` in crypto/frost/src/sign.rs:121-144).
- `share_internal` calls `preprocess_internal` and then `machine.sign(preprocesses, msg)` — a fresh `sign` under the cached nonces (signing_protocol.rs:150-180).
- `generated_key_pair` performs `DkgKeyPair::set(txn, genesis, attempt, key_pair)` unconditionally — overwriting any prior pair — and then signs `set_keys_message(..., key_pair)` (handle.rs:47-60). There is no check that a share was already produced for this attempt under a different pair.
- `complete` (invoked from the `DkgConfirmed` accumulation path) again runs `share_internal` → `sign` with the same cached nonces, but with `key_pair` read back from `DkgKeyPair::get` — i.e., whatever was last written (handle.rs:526-535; signing_protocol.rs:312-327).
- The file's own header concedes safety depends on sign never being called again over distinct messages, and marks the on-chain consistency check `TODO` (signing_protocol.rs:25-54).

If `share()` ever signs `msg(key_pair_A)` and a later `share()`/`complete()` signs `msg(key_pair_B)` with `A != B` (e.g., a second `GeneratedKeyPair` report after a coordinator/processor reboot or DB divergence — a scenario the codebase explicitly acknowledges elsewhere: "this is an error if we didn't reboot"), the same nonce `k` produces two shares `s_A = k + e_A·λ·x` and `s_B = k + e_B·λ·x` with `e_A ≠ e_B` (the FROST challenge binds `hash_msg`/`msg`). The published `DkgConfirmed` share for `A` is on-chain; `s_B` is recoverable from the published aggregate `set_keys` signature by subtracting the other validators' on-chain shares. Then `x = (s_A − s_B) / ((e_A − e_B)·λ)` — the validator's MuSig secret key share.

### Impact Explanation
Recovery of a validator's MuSig key share lets an attacker forge that validator's participation in the DKG-confirmation `set_keys` MuSig and any future validator-set signing, undermining the root-of-trust rotation of the whole network. This is concrete key-share recovery, in the accepted impact class.

### Likelihood Explanation
Requires two distinct `key_pair` values to be signed under one `(DkgConfirmer, attempt)` context. The code provides no guard: `DkgKeyPair::set` overwrites blindly, `share()` has no "already signed" check, and the cache is never invalidated after use. The trigger is a second `GeneratedKeyPair` for the same attempt — reachable on reboot/replay paths the code itself flags as expected-error cases, rather than requiring collusion. Likelihood is moderate; the missing invalidation is the same root cause as the reference CVE (cleanup bound to a lookup that races state changes) and is exploitable whenever the presumed-stable message diverges.

### Recommendation
- Bind the signed message into the cache key: store `CachedPreprocesses` under `(context, msg_hash)` or store the signed `key_pair`/`msg` alongside the seed and `assert_eq!` on reuse.
- Make `generated_key_pair` reject a second pair for the same attempt (`assert!(DkgKeyPair::get(...).is_none())` or equality-check the existing value) before signing.
- Delete the cached preprocess after a successful `share()` so a stale seed can never be re-resolved, and implement the TODO check that on-chain commitments match the presumed preprocess before publishing shares.

### Proof of Concept
1. Attempt `n` DKG completes; coordinator stores `seed` at `CachedPreprocesses[("DkgConfirmer", n)]`, publishes confirmation nonces `R`, and `generated_key_pair` signs `set_keys_message(set, removed, K_A)`, publishing share `s_A` in `DkgConfirmed`.
2. A second `GeneratedKeyPair` (reboot replay, DB divergence, or processor re-emission) calls `generated_key_pair` with `K_B ≠ K_A`: `DkgKeyPair` is overwritten and `sign` re-derives nonce `k` from `seed`, producing `s_B` over `msg_B`.
3. When `DkgConfirmed` accumulation completes, `complete` re-signs `msg(K_B)` with `k` and the aggregate signature for `K_B` is published on Substrate; the attacker recovers `s_B` by subtracting all other validators' public `DkgConfirmed` shares.
4. Attacker computes `x = (s_A − s_B)·((e_A − e_B)·λ_i)⁻¹ mod l`, recovering the validator's secret key share.
