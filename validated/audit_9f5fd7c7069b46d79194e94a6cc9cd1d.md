### Title
Quadratic transcript hashing DoS in MuSig key aggregation - (File: crypto/dkg/musig/src/lib.rs)

### Summary
The `nuxt-api-party` advisory (GHSA-q6hx-3m4p-749h) is a CWE-400 uncontrolled-resource-consumption bug: an attacker-controlled parameter (`retry`) multiplies the server-side work induced by a single small request. The same class exists in Serai's MuSig key aggregation, where the size of an attacker-influenced key list is squared into hash/transcript work by `binding_factor`.

### Finding Description
`musig_key_multiexp` builds `binding_factor_transcript`, a `Vec<u8>` containing the context, the key count, and the serialization of every key (O(n) bytes, ~32·n). It then calls `binding_factor` once per key, and `binding_factor` does `transcript.clone()` — an O(n) copy — before handing the whole buffer to `C::hash_to_F`, which hashes all ~32·n bytes: [1](#0-0) [2](#0-1) 

So for a key list of length n, the aggregation performs n clones + n full-buffer hashes = O(n²) byte-operations. `check_keys` caps the list at `u16::MAX` (65,535) keys but does not otherwise restrict n: [3](#0-2) 

The same quadratic cost is incurred by `musig` itself, which additionally clones the transcript per key inside its binding-factor loop: [4](#0-3) 

An unprivileged party who can cause a node/validator to aggregate over an attacker-supplied key list — e.g., when registering a MuSig-based n-of-n multisig or a validator set — supplies only ~2 MB of point encodings (65,535 × 32 bytes) yet forces on the order of 65,535² × 32 ≈ 10¹¹ bytes of hashing plus equivalent memory copying, alongside an O(n²)-statement `multiexp`. This is direct input-size amplification exactly as in the advisory: a bounded public input triggers disproportionate CPU/memory work in a single call.

### Impact Explanation
A single call to `musig` / `musig_key` / `musig_key_vartime` with a maximal key list performs ~10¹¹ hash-input bytes of work and billions of scalar-point statement preparations, stalling the calling thread for an extended period. Where this runs inside consensus-critical key registration or multisig setup, repeated calls yield a practical denial of service from small, validly-encoded inputs. No secret material is needed; the keys are public inputs by design.

### Likelihood Explanation
Reachability is conditional: the attacker must control or heavily influence the key list passed to these functions, and the lists are capped at 65,535 keys, so this is not an unbounded single-packet kill. However, the API explicitly accepts keys from counterparties in a distributed key-aggregation protocol, the cap is very high, and there is no documented warning that cost is quadratic rather than linear — making a several-orders-of-magnitude amplification achievable with one ~2 MB input. Medium severity.

### Recommendation
Compute the transcript once and reuse a pre-hashed/fixed-size digest per index instead of cloning and re-hashing the entire key list per `binding_factor` call — e.g., hash `transcript` once into a digest, then `hash_to_F(b"dkg-musig", digest || i)`. Additionally, bound the transcript clone cost by hashing `i` into a hasher instance that already absorbed the key list (streaming) rather than `Vec::clone`, and consider a documented lower maximum on `keys.len()` than `u16::MAX`.

### Proof of Concept
```rust
// ~2 MB input -> ~10^11 bytes hashed
let keys: Vec<C::G> = vec![some_point; u16::MAX as usize]; // passes check_keys
// check_keys rejects duplicates, so supply 65535 distinct points:
// keys[i] = C::generator() * C::F::from(i as u64 + 1)
let _ = musig_key_vartime::<C>(context, &keys);
// Internally: 65,535 calls to binding_factor::<C>(transcript.clone(), i),
// each cloning and hashing ~2 MB -> quadratic work from a linear input.
```

Caveat: I could not fully trace every call path from a deployed processor/coordinator entry point to `musig`/`musig_key`, so whether the key list is attacker-controlled in a live deployment depends on the integrator's usage; the quadratic behavior in the library itself is confirmed in the code above.

fn check_keys<C: Ciphersuite>(keys: &[C::G]) -> Result<u16, MusigError<C>> {
  if keys.is_empty() {
    Err(MusigError::NoKeysProvided)?;
  }

  let keys_len = u16::try_from(keys.len())
    .map_err(|_| MusigError::TooManyKeysProvided { max: u16::MAX, provided: keys.len() })?;

  let mut set = HashSet::with_capacity(keys.len());
  for key in keys {
    let bytes = key.to_bytes().as_ref().to_vec();
    if !set.insert(bytes) {
      Err(MusigError::DuplicatedParticipant(*key))?;
    }
  }

  Ok(keys_len)
}

fn binding_factor_transcript<C: Ciphersuite>(
  context: [u8; 32],
  keys_len: u16,
  keys: &[C::G],
) -> Vec<u8> {
  debug_assert_eq!(usize::from(keys_len), keys.len());

  let mut transcript = vec![];
  transcript.extend(&context);
  transcript.extend(keys_len.to_le_bytes());
  for key in keys {
    transcript.extend(key.to_bytes().as_ref());
  }
  transcript
}

fn binding_factor<C: Ciphersuite>(mut transcript: Vec<u8>, i: u16) -> C::F {
  transcript.extend(i.to_le_bytes());
  C::hash_to_F(b"dkg-musig", &transcript)
}

#[allow(clippy::type_complexity)]
fn musig_key_multiexp<C: Ciphersuite>(
  context: [u8; 32],
  keys: &[C::G],
) -> Result<Vec<(C::F, C::G)>, MusigError<C>> {
  let keys_len = check_keys::<C>(keys)?;
  let transcript = binding_factor_transcript::<C>(context, keys_len, keys);
  let mut multiexp = Vec::with_capacity(keys.len());
  for i in 1 ..= keys_len {
    multiexp.push((binding_factor::<C>(transcript.clone(), i), keys[usize::from(i - 1)]));
  }
  Ok(multiexp)
}
