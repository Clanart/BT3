### Title
Unauthenticated duplicate DKG registration message panics the recipient - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
`Decryption::register` enforces "one registration per participant" with a hard `assert!` instead of returning an error. Any DKG participant who sends a second `EncryptionKeyMessage` under their own `Participant` index causes the victim's process to panic when the message is registered, mirroring the reported bug class (a remote party repeatedly crashing the application by feeding it an input path the application fails to reject gracefully).

### Finding Description
During PedPoP key generation, each participant broadcasts an `EncryptionKeyMessage` containing their encryption public key, deserialized via `EncryptionKeyMessage::read` (`crypto/dkg/pedpop/src/encryption.rs:57`) and handed to `Encryption::register`, which forwards to `Decryption::register`. That function does:

```rust
// crypto/dkg/pedpop/src/encryption.rs:356-360
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
self.enc_keys.insert(participant, msg.enc_key);
```

The bytes are fully attacker-controlled and parse successfully — `read` only requires a valid `M` and a non-identity `C::G`. No validity check on "already registered" exists at parse time; the duplicate condition is only detected inside `register`, where it panics. The doc comment on `Commitments` acknowledges "if any participant sends multiple sets of commitments, they are faulty" (`crypto/dkg/pedpop/src/lib.rs:98-101`), but the library still crashes rather than returning a `FrostError`/`io::Error`.

Related reachable indexing panics in the same file: `self.enc_keys[&decryptor]` in `decrypt_with_proof` (`encryption.rs:388`) and `self.decryption.enc_keys[&participant]` in `encrypt` (`encryption.rs:466`) panic if the referenced participant never registered — i.e., a participant who withholds their `EncryptionKeyMessage` while the victim proceeds to encrypt/decrypt for them also crashes the process. (Uncertainty noted: whether the higher-level caller guards these calls depends on the integrator, but `register` double-registration is directly triggered by a second wire message regardless.)

### Impact Explanation
A single malicious DKG participant aborts the victim's key-generation session by crashing the host process. Since DKG sessions are re-run after failure, the attacker can repeat this indefinitely — a persistent denial of service against every honest participant that registers messages without an external dedup guard, preventing the threshold key from ever being established. This matches the report's impact class (remote, repeatable crash / availability loss, CVSS A:H).

### Likelihood Explanation
Requires only that the attacker is a DKG participant able to send two protocol messages — the lowest bar in the threat model, no threshold collusion, no BFT assumptions broken. The crash is deterministic: the second `register` call for the same `Participant` unconditionally hits the `assert!`. Exploitation cost is one extra serialized `EncryptionKeyMessage`.

### Recommendation
Replace the `assert!` in `Decryption::register` with a fallible check returning an error (e.g., a `DkgError`/`io::Error` variant for duplicate registration), and have `register` propagate it so the caller can mark the participant faulty instead of aborting. Similarly, replace the `HashMap` indexing in `decrypt_with_proof` (`encryption.rs:388`) and `encrypt` (`encryption.rs:466`) with `get(...).ok_or(...)` lookups that report "participant never registered an encryption key" as an error rather than panicking.

### Proof of Concept
```rust
// Conceptual: an honest node running PedPoP processes two wire messages
// from participant `p` in the same session.

let params = ThresholdParams::new(t, n, our_i).unwrap();
let mut enc = Encryption::<C>::new(context, our_i, &mut rng);

// Attacker sends EncryptionKeyMessage #1 (valid bytes over the channel)
let msg1 = EncryptionKeyMessage::<C, M>::read(&mut bytes1, params).unwrap();
enc.register(p, msg1); // succeeds, inserts p -> enc_key

// Attacker sends EncryptionKeyMessage #2 (also perfectly valid encoding)
let msg2 = EncryptionKeyMessage::<C, M>::read(&mut bytes2, params).unwrap();
enc.register(p, msg2); // PANIC: "Re-registering encryption key for a participant"
```

Both messages deserialize cleanly through `EncryptionKeyMessage::read` (`encryption.rs:57-59`); the crash is in `Decryption::register` at `crypto/dkg/pedpop/src/encryption.rs:356`, reachable purely from attacker-supplied DKG traffic.
