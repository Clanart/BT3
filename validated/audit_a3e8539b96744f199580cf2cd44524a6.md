### Title
ThresholdKeys::new derives the group key from only the first `t` verification shares without verifying all `n` shares interpolate to it — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The report's bug class is an initializer with no access control: whoever calls it first gets to define the privileged state. The analog in Serai's scope is `ThresholdKeys::new` / `ThresholdKeys::read`, which "initialize" a threshold keyset from caller/untrusted-supplied `verification_shares` and compute `group_key` by interpolating only participants `1..=t`. No check verifies that the remaining shares `t+1..=n` lie on the same polynomial, so anyone feeding crafted bytes to `ThresholdKeys::read` (explicitly in-scope untrusted input) can declare an arbitrary `group_key` and arbitrary extra verification shares that were never produced by any real DKG.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::new` builds the group key as:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

Only the structural checks `IncorrectAmountOfVerificationShares` (map length == n) and `InvalidParticipant` (index ≤ n) are applied to `verification_shares`. Nothing proves the shares are evaluations of a single polynomial at points `1..=n`. `ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation variant, the secret share, and `n` group elements straight from the reader and calls `ThresholdKeys::new` — so untrusted bytes fully control the initialized state, including the "admin" of the set: the group key everyone is told they belong to. Like `initAuctionLauncher`, whoever supplies the initialization input defines the authority; there is no binding that the declared group key corresponds to an honestly-generated keyset.

### Impact Explanation
Two concrete consequences:

1. **Funds reported received that are not spendable.** `Scanner::new`/`register_offset` in `networks/bitcoin/src/wallet/mod.rs` scan for outputs paying to `key + G*offset` where `key` comes from `keys.group_key()`. If a deserialized `ThresholdKeys` reports a `group_key` derived from inconsistent shares, deposits scanned under that key (and under `tweak_keys`-derived offsets) cannot actually be signed for, because the `n` secret shares held by participants don't reconstruct that key — participants `t+1..=n` carry verification shares off the polynomial used to define `group_key`.
2. **Inconsistent `ThresholdView`.** `view()` interpolates each included participant's verification share from the attacker-controlled map and adds the offset to `included[0]`'s share. A view including participants whose shares don't belong to the declared polynomial produces signature shares that fail verification against `group_key` — or, worse, lets the initializer dictate which subsets appear valid.

### Likelihood Explanation
Reachable by any unprivileged party able to feed bytes to `ThresholdKeys::read` or parameters to `ThresholdKeys::new`, both in-scope surfaces. Exploitation requires the consumer to trust a deserialized keyset rather than one produced by an honest DKG `complete()` (which derives shares from verified commitments), so severity is bounded by integrator flow — analogous to the report's note that the init function was *intended* to be called right after deployment by a trusted party but was publicly callable. Medium.

### Recommendation
When `interpolation` is `Constant` (a public additive/known-combination scheme) or `Lagrange`, verify the supplied `verification_shares` are consistent: either interpolate over all `n` shares with a subset check that any `t` of them reconstruct the same `group_key` (e.g., verify shares `t+1..=n` against the polynomial defined by `1..=t`), or require `ThresholdKeys::read` output to be accompanied by the DKG transcript/`EncryptedMessage` proofs that produced it. At minimum, document that `read` does not establish share consistency and must only be used on self-produced serializations.

### Proof of Concept
1. Pick arbitrary `n` group elements `V_1..V_n` and any scalar `s`. Serialize `t`, `n`, `i=1`, interpolation `Lagrange`, secret share `s`, then `V_1..V_n` via the `ThresholdKeys::write` format.
2. `ThresholdKeys::<Secp256k1>::read` accepts this and returns `group_key = Σ_{i=1..t} V_i·λ_i` even though no polynomial passes through all `n` points.
3. `Scanner::new(tweak_keys(keys).group_key())` yields an address; deposits sent there appear in `scan_block`, but `keys.view(included)` for any set containing a participant `j > t` whose `V_j` is off-polynomial yields verification shares inconsistent with `group_key`, so honest co-signers' shares verify while the reconstructed key does not — the received funds are unspendable.

Uncertainty: I could not fully inspect `crypto/dkg`'s PedPoP/`promote` modules (`pedpop.rs` path not found in index), so whether the DKG `complete` path itself validates share consistency before constructing `ThresholdKeys` is unverified; the finding stands for the `read`/`new` surfaces regardless.
