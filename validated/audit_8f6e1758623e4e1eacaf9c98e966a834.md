## Analog Found

### Title
Single-step, unvalidated `admin` field replacement in `EvmHost.updateHostParamsInternal` can permanently brick the freeze/unfreeze control - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost` stores a single `admin` address that is the *only* account capable of freezing/unfreezing the bridge, as documented directly in the storage layout: `// Frozen status of the host, only the admin or handler can change this.` [1](#0-0)  This role is replaced in one atomic, single-step write inside `updateHostParamsInternal`, with none of the sanity checks that are explicitly applied to the other critical addresses in the same struct.

### Finding Description
`updateHostParamsInternal` validates `hostManager`, `handler`, and `consensusClient` for non-zero address, deployed code, and correct interface support, with an explicit comment stating the purpose is to prevent the host from being bricked: [2](#0-1) 

Immediately after these checks, the function performs a direct, single-step overwrite of every field, including `admin`, with **zero validation** on `params.admin`: [3](#0-2) 

There is no "pending admin" staging step and no acceptance/claim call — the new `admin` value takes effect the instant the transaction executes, exactly the single-step ownership-transfer pattern flagged in the external report. Unlike `hostManager`/`handler`/`consensusClient`, an incorrect `admin` (including `address(0)`, or any address without the corresponding private key/contract logic) is accepted without complaint, because the code explicitly reasons about bricking for the other three fields but omits `admin` from that same protection, per the comment at line 582 ("check the params to prevent the host from getting bridged") that only covers `hostManager`, `handler`, and `consensusClient`.

Once `admin` is set incorrectly, the freeze/unfreeze capability described at `evm/src/core/EvmHost.sol:150-151` becomes permanently unreachable, since `updateHostParams` itself is gated by `restrict(_hostParams.hostManager)` [4](#0-3)  and the caller cannot subsequently be the old admin to self-correct — there is no rollback or two-step claim path anywhere in `EvmHost.sol` or `HostManager.sol`.

### Impact Explanation
If the freeze/unfreeze admin field is ever set to a wrong or uncontrolled address in one `updateHostParams` call, the emergency-freeze mechanism for the entire `EvmHost` bridge contract is permanently lost with no recovery mechanism — this is a full, irreversible loss of a critical safety control for the live bridge deployment, matching the "High impact / bricked protocol" characterization of the seed report.

### Likelihood Explanation
Low — this requires the `HostParams.admin` field to be populated incorrectly in a single `updateHostParams`/`SetHostParam` governance call routed through `HostManager.onAccept` [5](#0-4) , with no built-in guard to catch the mistake, exactly mirroring the "Low likelihood because it requires an error on the admin side" framing from the source report.

### Recommendation
Apply the same non-zero/self-consistency validation used for `hostManager`, `handler`, and `consensusClient` to the `admin` field in `updateHostParamsInternal`, and/or convert admin rotation to a two-step pattern (stage `pendingAdmin`, require an explicit accept call from that address) so a bad value can never take effect without confirmation from the intended new admin.

### Proof of Concept
1. Cross-chain governance (via `HostManager.onAccept`) submits a `SetHostParam` action with a `HostParams` struct where `admin = address(0)` (or any address not controlled by the intended operator), while `hostManager`, `handler`, and `consensusClient` remain valid so all existing checks pass.
2. `EvmHost.updateHostParams` → `updateHostParamsInternal` executes; all validated fields pass, and `_hostParams.admin` is overwritten with the bad value in the single unconditioned assignment at line 628.
3. From this point on, no address can call the admin-only freeze/unfreeze path, since the modifier compares against the corrupted `_hostParams.admin`, and there is no pending/claim step to recover — the bridge's freeze mechanism is permanently disabled.

**Uncertainty note:** I could not locate the actual `freeze`/`unfreeze` function bodies within the indexed portion of `EvmHost.sol` (only the storage declaration and comment were retrieved) due to index size limits; a full review of `evm/src/core/EvmHost.sol` in a Devin session would confirm the exact modifier used and whether any secondary recovery path exists that isn't visible from the indexed excerpts.

    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }
