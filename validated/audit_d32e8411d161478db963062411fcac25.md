## Title
Silent, unconfirmed rewrite of a repository's `origin` remote URL from GitHub API `clone_url`, redirecting future pushes/fetches without any protocol/hostname-integrity check beyond scheme comparison - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Sherlock report's core defect is: a value the user implicitly trusts to be stable and safe (the `NapierPool` fee) can be silently changed by a party who returns data to the client (the pool owner), and the app applies that change automatically before/around the user's intended action (a swap), without any user confirmation or delay. The closest Desktop analog is `updateRemoteUrl()`, which automatically rewrites the git `origin` remote to whatever `clone_url` a remote GitHub/GHES API server returns, gated only by a same-scheme check (`http` vs `https` vs `ssh`), not by hostname/owner/repo identity. This function is invoked as part of the "refresh GitHub repository" step that precedes push/fetch flows, so a malicious or compromised API server (a "git remote/proxy response" - explicitly in scope per the task's Valid Impact list) can cause Desktop to silently repoint `origin` to an attacker-controlled host.

### Finding Description
`updateRemoteUrl` compares the currently configured remote against the previously cached `gitHubRepository.cloneURL`, and if they still match (`remoteUrlUnchanged`) and the URL scheme is unchanged (`protocolsMatch`), it unconditionally calls `gitStore.setRemoteURL(...)` with whatever `apiRepo.clone_url` the API just returned, with no host/owner/name equality check and no user prompt: [1](#0-0) 

Note that `protocolsMatch` only compares the URL *scheme* (`http:`/`https:`), never the hostname: [2](#0-1) 

This is invoked from `repositoryWithRefreshedGitHubRepository`, which calls `api.fetchRepository(owner, name)` against the account's configured endpoint (which can be a self-hosted GitHub Enterprise Server the user added), then unconditionally applies the returned `clone_url` via `updateRemoteUrl` before persisting the refreshed GitHub repository association: [3](#0-2) 

This refresh path is wired into the push flow itself (`_push` → `withRefreshedGitHubRepository` → conditionally `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`) and into the publish-repository flow: [4](#0-3) [5](#0-4) 

Once the remote URL is silently rewritten, `git push`/`git fetch` operations resolve their target and proxy purely from that URL: [6](#0-5) 

### Impact Explanation
A GitHub Enterprise Server the user has added an account for (or any man-in-the-middle able to tamper with API responses to that endpoint) can, on any repository-refresh cycle, return an `apiRepo.clone_url` pointing at an attacker-controlled host while keeping the same scheme (e.g. `https://evil.example.com/x/y.git`). Because `protocolsMatch` never checks hostname, and `remoteUrlUnchanged` only requires the *previous* remote to still match the previously-cached `cloneURL` (which is the common, unmodified case for most users), Desktop will call `setRemoteURL` and rewrite the local `origin` remote to the attacker's URL with zero UI confirmation. The next push from the user will silently send their code (and whatever credentials/env are resolved for that new URL) to the attacker's server instead of the intended repository - i.e., silent corruption of where a commit/push is delivered, one of the explicitly valid impact classes.

### Likelihood Explanation
This requires the attacker to control an API endpoint the app already trusts (e.g., a malicious/compromised GHES instance the victim has added an account for, matching the task's allowed "git remote/proxy response" primitive) - it does not require local access, leaked credentials, or social engineering. This is a plausible but non-trivial attack surface: it depends on the account's configured endpoint being attacker-influenced, and requires the previous remote to still exactly match the cached `cloneURL` (`remoteUrlUnchanged`), a condition true for the default, unmodified case.

### Recommendation
`updateRemoteUrl` should verify full identity (hostname, owner, and repo name structure, not just scheme) before silently rewriting a remote, or require explicit user confirmation before changing `origin`'s URL, analogous to introducing a "delay"/confirmation gate as recommended in the source report for fee changes. At minimum, compare the new `clone_url`'s hostname against the known/expected endpoint hostname before calling `setRemoteURL`.

### Proof of Concept
1. Add an account for a GitHub Enterprise Server endpoint controlled/compromised by the attacker.
2. Have a repository whose `origin` remote matches the cached `gitHubRepository.cloneURL` exactly (default state after clone).
3. Attacker-controlled server, on the next `GET repos/{owner}/{name}` call (triggered via `repositoryWithRefreshedGitHubRepository`, e.g. during account refresh or publish flow), returns a `clone_url` with the same scheme but a different host: `https://attacker.example.com/owner/name.git`.
4. `updateRemoteUrl` at [1](#0-0)  passes both checks (`protocolsMatch` true because scheme unchanged, `remoteUrlUnchanged` true) and silently calls `gitStore.setRemoteURL(name, 'https://attacker.example.com/owner/name.git')`.
5. Any subsequent push/fetch from the user now targets the attacker's server without any dialog or warning.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
