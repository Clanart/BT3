### Title
Unauthenticated shop-param spoofing lets attackers obtain a victim's offline session via `EnsureInstalled#check_shop_known` / `installed_shop_session` - ([File: app/controllers/concerns/shopify_app/ensure_installed.rb])

### Summary
When an app uses the legacy (non-`use_new_embedded_auth_strategy`) `EnsureInstalled` flow, `check_shop_known` only verifies that a `params[:shop]`-derived domain has a stored offline session — it performs no JWT/ID-token or HMAC verification of the requester's identity. Any anonymous client can set `shop=victim_shop`, pass all before_actions, and have the controller call `installed_shop_session`, which returns the victim's real, live `ShopifyAPI::Auth::Session` (with access token) for use in API calls.

### Finding Description
The relevant before_action chain for the legacy flow is: [1](#0-0) 

`check_shop_domain` only sanitizes the format of `params[:shop]` (regex/domain validity), it does not authenticate the caller: [2](#0-1) 

`check_shop_known` then does a pure existence lookup: it fetches `installed_shop_session` (a DB lookup keyed only by the attacker-supplied `shop` domain) and treats a non-nil result as "shop known," setting `@shop`: [3](#0-2) 

There is no comparison against any session token, ID token, HMAC, or Rack session — `@shop` is considered valid purely because *some* offline session exists for that domain in `SessionRepository`. The only remaining gate is `validate_non_embedded_session`, but it does not authenticate the caller either — it uses the same (victim's) `installed_shop_session` to make a live `GET /shop` API call, and only redirects if Shopify itself returns 401 (i.e., if the token happens to be revoked). If the victim's offline token is still valid, this check passes and actually exercises the victim's credentials: [4](#0-3) 

Because `embedded_param?`/`loaded_directly_from_admin?` only gate the redirect behavior on failure and are based on the same attacker-controlled `params[:embedded]`, they provide no protection either: [5](#0-4) 

Thus, for a controller that includes `EnsureInstalled` and calls `installed_shop_session` to make Shopify API calls (a pattern the gem exposes via a public helper method with no guard against non-embedded misuse), an attacker who knows or guesses a victim's `myshopify.com` domain and sends a bare request with `shop=victim_shop` (no session token, no HMAC, no App Bridge context) reaches the action using the victim's real offline access token.

### Impact Explanation
Concrete impact: an unauthenticated/unprivileged attacker can trigger authenticated Shopify Admin API calls against a victim shop's data using the victim's offline access token, purely by supplying `shop=victim_shop`. This maps to Shopify's HackerOne "Authentication Bypass" / "Improper Access Control leading to cross-shop data access" impact class — the attacker effectively impersonates the victim shop's session for any controller action gated only by `EnsureInstalled`.

### Likelihood Explanation
Requires: (1) the victim shop has previously installed the app (offline session persisted), (2) the host app uses the legacy `EnsureInstalled` flow (not the new token-exchange/embedded-auth strategy) and a controller action calls `installed_shop_session` to perform API actions — an acknowledged-unsupported but code-reachable pattern. No secrets, tokens, or insider access are needed by the attacker; only knowledge of the victim's shop domain, which is often guessable/public. This is fully reproducible with a single crafted HTTP request.

### Recommendation
`check_shop_known`/`installed_shop_session` should not be treated as (and should not be usable as) an authentication mechanism. Either: (a) remove/deprecate the legacy `EnsureInstalled` flow in favor of the token-exchange/ID-token-verified strategy for all controllers that make API calls, or (b) have `installed_shop_session` require and validate an ID token / session token bound to the current request (e.g., verify via `ShopifyApp::JwtToken` and match the shop encoded in a verified token against `params[:shop]`) before returning a usable session, rather than trusting the raw `shop` query parameter.

### Proof of Concept
```ruby
class WidgetsController < ApplicationController
  include ShopifyApp::EnsureInstalled

  def index
    client = ShopifyAPI::Clients::Rest::Admin.new(session: installed_shop_session)
    render json: client.get(path: "shop").body
  end
end

# Test
test "unauthenticated request with only shop param returns victim's live session" do
  victim_domain = "victim-shop.myshopify.com"
  ShopifyApp::SessionRepository.store_shop_session(
    ShopifyAPI::Auth::Session.new(shop: victim_domain, access_token: "victim-token")
  )

  get widgets_path, params: { shop: victim_domain } # no session token, no HMAC

  assert_response :success
  # installed_shop_session inside controller resolved to victim's real session/token
end
```

    def current_shopify_domain
      if params[:shop].blank?
        ShopifyApp::Logger.info("Could not identify installed store from current_shopify_domain")
        return
      end

      @shopify_domain ||= ShopifyApp::Utils.sanitize_shop_domain(params[:shop])
      ShopifyApp::Logger.info("Installed store:  #{@shopify_domain} - deduced from Shopify Admin params")
      @shopify_domain
    end

    def installed_shop_session
      @installed_shop_session ||= SessionRepository.retrieve_shop_session_by_shopify_domain(current_shopify_domain)
    end

    private

    def check_shop_domain
      redirect_to(ShopifyApp.configuration.login_url) unless current_shopify_domain
    end

    def check_shop_known
      @shop = installed_shop_session
      unless @shop
        if embedded_param?
          redirect_for_embedded
        else
          redirect_to(shop_login)
        end
      end
    end
