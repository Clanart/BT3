### Title
Unregistered-instance authentication fallback in `IntentGatewayV2.authenticate()` lets a spoofed source-chain contract forge escrow settlement messages - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` resolves the expected sender for a source chain via `instance(stateMachineId)`, which — unlike the canonical EVM implementation's `_instance()` — returns `address(this)` instead of reverting when no gateway instance has been registered for that chain. `authenticate()` uses this value to validate `request.from` for `RedeemEscrow`/`RefundEscrow` messages, so any state machine without a registered instance is implicitly authenticated against the destination gateway's own address, rather than being rejected as unknown.

### Finding Description
`instance()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is defined as: [1](#0-0) 
```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```
This `authenticate()` function gates the fund-moving `RedeemEscrow`/`RefundEscrow` paths inside `onAccept`: [2](#0-1) 

Compare this to the canonical EVM implementation, `ExtrinsicIntents.sol` / `IntentsBase.sol`, which reverts with `UnknownInstance` when no gateway is registered for a source chain: [3](#0-2) [4](#0-3) 

The Tron variant's fallback to `address(this)` means: for **any** whitelisted state machine that Hyperbridge routes messages for but for which the gateway operator has not yet dispatched a `NewDeployment` registration (a routine, expected, un-privileged operational state — new chains are added to Hyperbridge's consensus/state-machine whitelist before every application deploys and registers its own instance), `instance(source)` resolves to the destination gateway's own address. `authenticate()` then only checks that `request.from == address(this)`.

Because IntentGateway deployments are deliberately deployed via deterministic CREATE2 with a shared salt across chains (as documented in `TestnetHost.sol`'s CREATE2 comment), an attacker can deploy an arbitrary contract using the same public deployer/salt/init-code scheme so that its address on the unregistered chain matches the destination gateway's address. The attacker's contract then dispatches a crafted `RedeemEscrow`/`SweepDust`-shaped POST request (with `from` = its own, matching, address) through the legitimate ISMP pipeline. Once it is proven and delivered, `authenticate()` passes because `module == address(this)`, and `onAccept` will run `withdraw()`, releasing escrowed input tokens and accumulated fees to an attacker-chosen beneficiary — a false-state acceptance that drains real escrowed funds without needing any relayer, admin, or prover compromise; the delivered proof is completely valid, it's the authentication logic that is broken.

### Impact Explanation
This is a direct "false proof/state acceptance" + "unauthorized execution" + "wrong beneficiary" bug per the bounty's impact gate: an unprivileged attacker can drain escrowed input tokens and protocol-collected fees for any order routed through a not-yet-registered/deregistered destination instance, by forging a message that self-authenticates against the gateway's own address. Impact is high because it results in direct loss of user-escrowed funds.

### Likelihood Explanation
Likelihood is elevated relative to the analog original report because it requires no leaked key, no compromised relayer, and no governance action — only (a) a state machine that Hyperbridge has whitelisted but for which `NewDeployment` hasn't (yet) registered an instance, which is a normal transient/permanent operational state, and (b) the ability to deploy a contract at a CREATE2 address matching the destination gateway, which the protocol's own deterministic-deployment design makes achievable.

### Recommendation
Change `instance()` to revert (e.g., `UnknownInstance()`) when `_instances[keccak256(stateMachineId)]` is unset, mirroring the canonical `_instance()` in `evm/src/apps/intentsv2/IntentsBase.sol`, instead of silently falling back to `address(this)`. Audit all callers of `instance()` in the Tron variant to ensure none rely on the `address(this)` fallback for legitimate same-chain flows; if a same-chain self-referencing case is intended, handle it explicitly (e.g., compare `request.source` against the local state machine id) rather than through an implicit address(0)→address(this) substitution.

### Proof of Concept
1. Hyperbridge whitelists state machine `X` in `EvmHost.hostParams().stateMachines`, but `IntentGatewayV2` on the destination chain has never received a `NewDeployment` message for `X` (`_instances[keccak256(X)] == address(0)`), which is the default state for any newly-added chain until an operator explicitly registers it.
2. Attacker computes the CREATE2 address of the target `IntentGatewayV2` (public bytecode + shared deployer + shared salt, as documented) and deploys an arbitrary contract to that same address on chain `X`.
3. From that contract, attacker dispatches an ISMP POST request to the destination gateway with `from = <own address>` and a body encoding `RequestKind.RedeemEscrow` (or `SweepDust`) with an attacker-controlled `beneficiary` and any live `commitment`/`tokens` values matching escrowed orders.
4. A relayer (unaware of the malicious intent) delivers the proof; the message is fully valid per ISMP.
5. `onAccept` decodes `RequestKind.RedeemEscrow`, calls `authenticate(request)`, where `instance(X) == address(0) → address(this)`, and `module == address(this)` (attacker's contract address matches by construction) — authentication passes.
6. `withdraw()` executes, transferring escrowed tokens/fees to the attacker-controlled beneficiary.
