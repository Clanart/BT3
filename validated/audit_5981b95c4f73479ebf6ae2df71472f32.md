### Title
OP_RETURN data output excluded from fee/weight estimation causes underpaid fees and unbroadcastable transactions locking funds - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the Perennial "protocol fee locked" issue (value credited but permanently unwithdrawable), `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` appends a caller-controlled OP_RETURN output to the transaction *after* computing the transaction's weight/vbytes, so the fee charged never accounts for the data output's size. The resulting signed transaction pays a lower effective fee rate than requested — potentially below `DEFAULT_MIN_RELAY_TX_FEE` — making it unrelayable/unconfirmable and leaving the consumed `ReceivedOutput` funds effectively locked in a transaction that cannot enter the mempool.

### Finding Description
`SignableTransaction::new` builds `tx_outs` from `payments`, then pushes an OP_RETURN output carrying up to 80 bytes of caller-supplied `data` (networks/bitcoin/src/wallet/send.rs:193-202). Only afterwards does it compute the fee:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
``` [1](#0-0) 

`calculate_weight_vbytes` constructs a template `Transaction` whose `output` vector is built **only** from `payments` (plus an optional change output) — the OP_RETURN output added to `tx_outs` is never included in the template (send.rs:85-99). The same omission occurs in the change path, where `vbytes_with_change` is again computed from `payments` and `change` only (send.rs:224-233). The minimum-fee sanity check at send.rs:211 also uses this underestimated `vbytes`.

The final signed `Transaction` (send.rs:245-255) includes the OP_RETURN output (~83-92 extra bytes: 8-byte amount, script length, `OP_RETURN` + push opcode + up to 80 bytes data). `Prevouts::All` commits to these exact outputs in the sighash (send.rs:373-390), so the fee deficiency cannot be corrected post-signing — the signed transaction is what it is.

### Impact Explanation
- The actual transaction is up to ~92 vbytes larger than the size used to compute `needed_fee`. The real fee rate is `needed_fee / actual_vbytes < fee_per_vbyte`.
- If `fee_per_vbyte` was chosen near the relay minimum, the produced transaction falls below `DEFAULT_MIN_RELAY_TX_FEE` once the uncounted OP_RETURN bytes are included, despite passing the `TooLowFee` check. Nodes will reject it (`min relay fee not met`), so it can never confirm.
- The inputs (`ReceivedOutput`s) are consumed by this signed transaction. Until an entirely new plan/transaction is constructed and re-signed by the threshold group, the funds it spends are immobile — the same "credited but unwithdrawable" shape as the reference bug: accounting (fee bookkeeping) diverges from what the network will actually accept.
- In Serai's flow, arbitrary `data` originates from user `InInstruction`s embedded into outbound transactions, so an unprivileged party controls the exact bytes/size that trigger the underestimation.

### Likelihood Explanation
Any transaction created with non-empty `data` and a near-minimum `fee_per_vbyte` produces a transaction below the relay fee floor. Even when it does relay, every such transaction systematically underpays relative to the requested rate, degrading confirmation reliability during congestion. Triggering requires only supplying the maximum-allowed ~80 bytes of OP_RETURN data on a withdrawal/forward that carries data — fully within an unprivileged user's control.

### Recommendation
Include the OP_RETURN output in the template transaction inside `calculate_weight_vbytes` (pass the serialized `data` length or a `Option<&ScriptBuf>` for the data output), in both the no-change and change estimation paths, so `needed_fee`, the `TooLowFee` check, and `fee_with_change` all reflect the true transaction size. Alternatively compute the fee over the final `tx_outs` vector after all outputs are known.

### Proof of Concept
In `SignableTransaction::new`:

1. `tx_outs.push(OP_RETURN output)` at send.rs:194-202 happens **before** fee estimation.
2. `calculate_weight_vbytes(tx_ins.len(), payments, None)` at send.rs:204 builds a `Transaction` whose `output` contains only `payments` (send.rs:85-94) — the data output is absent.
3. `needed_fee = fee_per_vbyte * vbytes` and the `DEFAULT_MIN_RELAY_TX_FEE` check (send.rs:206-213) therefore validate a smaller transaction than the one returned at send.rs:245-255, which includes the OP_RETURN.
4. With `fee_per_vbyte = 1` (1 sat/vB, the relay minimum) and 80 bytes of `data`, the check passes using a vbytes that omits ~92 bytes; the actual signed TX weighs ~92 vbytes more, so its real rate is < 1 sat/vB and it is rejected by `sendrawtransaction` as `min relay fee not met` — the spent `ReceivedOutput`s cannot be moved via this transaction despite a valid threshold signature.
