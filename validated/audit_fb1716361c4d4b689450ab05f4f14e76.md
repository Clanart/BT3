## Finding: Output-token duplicate check compares raw `bytes32` instead of the normalized token address, unlike the input-side check

### Title
Non-normalized `bytes32` token comparison in `placeOrder`'s output duplicate-check allows dirty-upper-bits token aliases to bypass the same "duplicate token" safeguard the input side already had to fix - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
The float-equality bug's core invariant break is: *equality/duplicate logic operates on a raw bit-level representation, while the semantic value used everywhere else is a decoded/normalized form, so two different raw representations of the same real value slip past a check that assumes canonical encoding.* The same pattern exists in `IntentGatewayV2.placeOrder`'s duplicate-output-token guard.

### Finding Description
In `placeOrder`, the input-token duplicate check is done **after** normalizing to the real ERC20 address: [1](#0-0) 
```
address token = address(uint160(uint256(order.inputs[i].token)));
if (_orders[commitment][token] != 0) revert InvalidInput();
_orders[commitment][token] = reducedInputs[i].amount;
```
This normalization (`address(uint160(uint256(token)))` — i.e., truncating to the low 160 bits) is exactly the semantic value used everywhere downstream (transfers, escrow, fills), and the comment/tests confirm this was deliberately hardened: `testRevert_PlaceOrder_DuplicateInputTokens` guards against "same-chain partial fills over-release repeated input escrow."

The **output**-token duplicate check, however, compares the **raw, un-normalized `bytes32`** value directly, before any truncation to an address: [2](#0-1) 
```
bytes32 token = order.output.assets[i].token;
assembly ("memory-safe") {
    if tload(token) { ... revert ... }
    tstore(token, 1)
}
```
`TokenInfo.token` is a `bytes32`, but every place that actually *uses* the token as an ERC20/asset identity (fill accounting, escrow release, beneficiary transfers) does `address(uint160(uint256(order.output.assets[i].token)))`, discarding the upper 96 bits. The upper 96 bits are attacker-controlled arbitrary data — nothing in `placeOrder` requires `token = bytes32(uint256(uint160(addr)))` (fully zero-padded). An attacker can therefore submit two output legs whose `bytes32` values differ only in the unused upper 96 bits (e.g. `0x000...0<DAI>` and `0x111...1<DAI>`), both of which decode to the *same* DAI address. The `tload`/`tstore` duplicate check sees two different `bytes32` keys and lets both through, exactly reproducing the "duplicate output tokens" bug class the repo's own regression test `testRevert_PlaceOrder_DuplicateOutputTokens` was written to close for the canonical case: [3](#0-2) 

Since downstream partial-fill/escrow bookkeeping keys by the truncated `address` (as evidenced by every other accounting path in this file: lines 208, 234, 262, 284, 289–291, 316 all use `address(uint160(uint256(token)))`), two "distinct" output legs that alias to the same address will collapse into a single accounting bucket at fill time — the same failure mode ("shares one `_partialFills` bucket") the test suite explicitly calls out as dangerous.

### Impact Explanation
This breaks order-output accounting invariants for the intents/order-settlement pathway: a maliciously-crafted order with two aliased output legs for the same token can pass `placeOrder`'s duplicate guard, then at fill time the solver-side/beneficiary-side per-token bucket collapses two logically distinct amount requirements into one address key. This is the exact class of bug (documented by the repo's own regression tests) that causes either under-collateralized fills, incorrect partial-fill accounting, or premature finalization of an output leg, all of which are within the bounty's "logic attacks / transaction manipulation / wrong beneficiary or amount" impact category for order escrow/settlement.

### Likelihood Explanation
Any unprivileged user can call `placeOrder` directly with an order they craft themselves — no relayer, prover, or admin involvement is required, and the `bytes32` output token field is fully attacker-controlled calldata with no on-chain enforcement that its upper 96 bits are zero.

### Recommendation
Normalize `order.output.assets[i].token` to its address form (`address(uint160(uint256(token)))`) — or explicitly require the upper 96 bits to be zero — before using it as the duplicate-check key in `placeOrder`, matching the pattern already used for input tokens.

### Proof of Concept
1. Construct `outputAssets[0] = { token: bytes32(uint256(uint160(address(dai)))), amount: 400e18 }`.
2. Construct `outputAssets[1] = { token: bytes32(uint256(uint160(address(dai))) | (uint256(1) << 200)), amount: 600e18 }` — same DAI address in the low 160 bits, but with a non-zero high bit that the `tload`/`tstore` guard treats as a distinct key.
3. Call `placeOrder` with these two output legs — unlike `testRevert_PlaceOrder_DuplicateOutputTokens`, this call succeeds because the two `bytes32` values differ, even though both decode to the same DAI address used later by `_fillSameChain`/`_fillCrossChain` accounting.

Note: I was unable to fully retrieve `IntrinsicIntents.sol`'s `_partialFills` implementation in this session to trace the exact downstream collision mechanics in full detail; however, the address-truncation pattern is consistent and pervasive throughout `IntentGatewayV2.sol`, and the repo's own comments/tests confirm this exact "two output legs sharing one bucket" failure mode is the concern the duplicate check exists to prevent. A full Devin session should read `evm/src/apps/intentsv2/IntrinsicIntents.sol` to confirm the exact keying used in `_partialFills`/escrow release for output assets.
