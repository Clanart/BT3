### Title
DataLayer mirror URLs are unvalidated attacker-controlled strings that trigger SSRF-style outbound HTTP requests from any node that syncs/subscribes to a store - (File: chia/data_layer/data_layer.py / chia/data_layer/download_data.py)

### Summary
Chia's DataLayer lets any wallet owner publish "mirror" URLs for a DataLayer store on-chain via `dl_new_mirror` with no validation of the URL contents. Any other node that subscribes to that store (an unprivileged, automatic sync action) will read these attacker-supplied strings from wallet state and use them directly as the target of outbound `aiohttp` HTTP requests (`http_download()` / `get_downloader()` / `download_file()`), with no scheme allow-listing or address restriction. This is analogous to the CXF WADL SSRF: a low-trust, user-controllable "URL-like" parameter (there: `stylesheet`, here: on-chain mirror `urls`) is passed unchecked into a network fetch performed by the victim service, letting an attacker cause the victim node to make requests to attacker-chosen hosts (internal services, cloud metadata endpoints, etc.) from the node's network vantage point.

### Finding Description
`DataLayerWallet.create_new_mirror()` writes the caller-supplied `urls: list[bytes]` directly into the coin memo of a "mirror" coin with no format/scheme validation: [1](#0-0) 

The wallet RPC endpoint `dl_new_mirror` (and the CLI `data add_mirror`) forward the caller's `urls` list verbatim into this call: [2](#0-1) [3](#0-2) 

Any node watching this launcher id observes the mirror coin and stores the attacker-chosen URLs into its local `dl_store` as trusted server metadata, with only a check that the URL list is non-empty: [4](#0-3) 

`DataLayer.update_subscriptions_from_wallet()` (part of the periodic, automatic `periodically_manage_data()` sync loop that any DataLayer-enabled node runs for its subscriptions) pulls these URLs from the wallet RPC and stores them as `ServerInfo` entries used for downloading: [5](#0-4) 

`fetch_and_validate()` iterates these server URLs and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs an `aiohttp` GET straight to `server_info.url + "/" + filename` with no scheme or host restriction: [6](#0-5) [7](#0-6) 

Additionally, when downloader/uploader plugins are configured, the raw mirror URL is placed into a JSON body POSTed to the plugin's `/handle_download` endpoint, again unvalidated: [8](#0-7) 

No component in this path validates that the mirror URL scheme is `http(s)`, resolves to a non-internal address, or otherwise restricts the target — the documentation itself notes "Plugin and mirror URLs are external trust inputs," but the trust boundary is only enforced for the *downloaded content* (verified against the wallet root), not for *where the request goes*: [9](#0-8) 

### Impact Explanation
An attacker who owns any DataLayer singleton (trivially creatable by any wallet user via `create_new_dl`) can publish a mirror URL pointing at an internal address (e.g., `http://169.254.169.254/latest/meta-data/`, `http://localhost:<admin-port>/...`, or an internal service on the victim's LAN). Any third party that subscribes to that store — which is the normal, expected DataLayer usage pattern for consuming another party's public data store — will have their node's DataLayer service issue outbound HTTP requests to that attacker-chosen endpoint on a recurring basis (`periodically_manage_data()`), from the victim node's own network position. This can be used for internal network reconnaissance/pivoting, interacting with unauthenticated internal admin endpoints, or triggering unwanted requests to arbitrary hosts, entirely without direct network access to the victim. It does not directly produce coin-state divergence or fund theft, but it is a genuine SSRF triggerable by an unprivileged singleton owner against any subscriber's node.

### Likelihood Explanation
Likelihood is moderate: creating a DataLayer singleton and adding a mirror with a malicious URL requires only normal wallet operations available to any user (`create_new_dl`, `dl_new_mirror`), and getting a victim to subscribe requires the victim to voluntarily subscribe to the attacker's store id — which is the standard way DataLayer consumers discover/replicate third-party stores (e.g., following a publicly advertised store id). No malicious peer/network-layer position is required.

### Recommendation
Validate mirror/server URLs before they are used as HTTP fetch targets: restrict scheme to `http`/`https`, resolve and reject requests targeting loopback/link-local/private/metadata address ranges (or route all such fetches through an explicit, operator-configured egress policy), and apply the same validation to plugin `download`/`handle_download` request URLs. Treat mirror URLs as adversarial input requiring the same allow-list style validation already applied to downloaded filenames (`is_filename_valid`), rather than only validating that the list is non-empty.

### Proof of Concept
1. Attacker creates a DataLayer store: `chia data create_data_store`, obtaining `store_id`.
2. Attacker publishes a mirror pointing at an internal/sensitive endpoint: `chia data add_mirror -id <store_id> -u http://169.254.169.254/latest/meta-data/ -a 1` (uses `dl_new_mirror`, validated only for non-empty URL list, see `data_layer.py:965-970`).
3. Victim, wanting to replicate the attacker's published data store, runs `chia data subscribe -id <store_id> -u <any_seed_url>`. The victim's `periodically_manage_data()` loop calls `update_subscription()` → `update_subscriptions_from_wallet()`, which pulls the attacker's mirror URL from chain/wallet state into the victim's local server list (`data_layer.py:979-985`).
4. On the next sync cycle, `fetch_and_validate()` selects the attacker's mirror URL and issues an outbound GET via `http_download()` (`download_data.py:311-319`) to `http://169.254.169.254/latest/meta-data/<filename>` from the victim node's process, demonstrating SSRF against internal/metadata infrastructure reachable from the victim's node.

```python
    async def get_downloader(self, store_id: bytes32, url: str) -> PluginRemote | None:
        request_json = {"store_id": store_id.hex(), "url": url}
        for d in self.downloaders:
            async with aiohttp.ClientSession() as session:
                try:
                    async with session.post(
                        d.url + "/handle_download",
                        json=request_json,
                        headers=d.headers,
                        timeout=self.client_timeout,
                    ) as response:
                        res_json = await response.json()
                        if res_json["handle_download"]:
                            return d
                except Exception as e:
                    self.log.error(f"get_downloader could not get response: {type(e).__name__}: {e}")
        return None
```

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
