### Title
Silent auto-repointing of origin remote to an attacker-controlled repository via `updateRemoteUrl` — (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl` automatically rewrites the user's `origin` remote URL whenever the GitHub API's `clone_url` for the repo differs from the locally configured one, using only superficial checks (protocol match + "remote hasn't been manually edited"). It never verifies that the API repository returned for a given `owner/name` is actually the *same* repository (by GitHub's immutable numeric ID) as the one the user originally added. This mirrors the reported `borg-core` flaw: one function conflates "add" and "update" semantics without verifying the target's prior identity, letting an attacker who can make the API return different repository data for a known `owner/name` (e.g., via repo-name squatting after a rename) silently redirect the local remote.

### Finding Description
`updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:7-45`) is invoked from `repositoryWithRefreshedGitHubRepository` (`app/src/lib/stores/app-store.ts:4904-4907`), which runs during routine background refreshes: repository selection (`app-store.ts:2255` → `repositoryWithRefreshedGitHubRepository` at `app-store.ts:2257`), account sign-in/out (`refreshSelectedRepositoryAfterAccountChange`, `app-store.ts:4921-4933`), and adding new repositories (`app-store.ts:8148-8151`).

That refresh flow resolves the repo purely by `owner/name` string matching: [1](#0-0) 

The match itself comes from parsing the *existing local remote URL* to extract owner/name (`matchGitHubRepository`, `app/src/lib/repository-matching.ts:29-46`) and then calling `api.fetchRepository(owner, name)` — i.e., whatever repository GitHub currently resolves for that `owner/name` pair, with no verification that it's the same repository entity as before.

`updateRemoteUrl` then decides to rewrite the remote based only on: [2](#0-1) 

The three guards are:
1. `protocolsMatch` — trivially satisfied (https vs https).
2. `remoteUrlUnchanged` — compares the current remote URL against the **previously stored** `gitHubRepository.cloneURL` (structural/string comparison only).
3. `!urlsMatch` — the new URL differs from the current remote.

None of these confirm that the *new* `apiRepo` is the same underlying repository. `GitHubRepository.dbID` is explicitly documented as local-only and unrelated to the API ID: [3](#0-2)  — the app has no persisted GitHub API repository ID to pin identity across refreshes, so an `owner/name` squat is indistinguishable from a legitimate URL change (e.g., HTTPS↔SSH normalization, which is the feature's intended use case, per `app/test/unit/stores/updates/update-remote-url-test.ts:68-81`).

### Impact Explanation
If an attacker gains control of the `owner/name` namespace previously associated with a tracked repository (e.g., the legitimate owner renames/deletes the repo, or transfers/deletes the account, freeing the name; the attacker recreates a repository under that same `owner/name`), the next background refresh will:
- Fetch the attacker's repository object via `api.fetchRepository(owner, name)`.
- Pass its `clone_url` into `updateRemoteUrl`, which silently calls `gitStore.setRemoteURL(...)` (`app/src/lib/stores/git-store.ts:1534-1543`) to repoint `origin` to the attacker's server — with no user prompt or confirmation.

Consequences:
- Subsequent `git push` by the user sends their commits/source code to the attacker-controlled remote (credential/code exfiltration).
- Subsequent `fetch`/`pull` merges attacker-controlled history/content into the user's local repository ("silent corruption of what the user commits or pushes").
- Because the change happens transparently via a background metadata refresh (repository selection, sign-in, periodic refresh), the user has no indication their remote changed.

### Likelihood Explanation
Requires the attacker to control (or later claim) the `owner/name` slot that GitHub Desktop resolves through its API, and requires that the user hasn't diverged their local remote URL from the app's last-known `cloneURL` (a common, default state for most users who never manually edit remotes). Namespace-squatting after repository rename/deletion or account deletion is a well-documented class of GitHub abuse and doesn't require local access, admin rights, or social engineering of the victim — it's triggered purely by routine background app behavior. This is more constrained than a fully generic "any attacker" scenario (it needs the specific owner/name to become available), which should be weighed when prioritizing.

### Recommendation
Persist and check GitHub's own immutable repository ID (not just `dbID`/owner+name) when refreshing `GitHubRepository` records and before invoking `updateRemoteUrl`. Only auto-update the local remote URL if the newly fetched API repository's ID matches the previously stored ID (i.e., it's genuinely the same repository that changed its clone URL, such as a protocol change or rename-with-redirect) — mirroring the audit's recommendation to split "add" vs "update" and require proof the target previously existed. If the ID differs (or is unknown, e.g., first-time association), treat this as a new repository association and require explicit user confirmation before silently rewriting `origin`.

### Proof of Concept
1. User clones `https://github.com/victim-org/project` in GitHub Desktop; Desktop stores `GitHubRepository` with `cloneURL = https://github.com/victim-org/project` (owner/name based, no API-side ID pinning).
2. `victim-org` renames/deletes `project` (or the account is deleted), freeing the `victim-org/project` namespace.
3. Attacker creates a new repository at the exact same `owner/name`, `victim-org/project`, with `clone_url = https://github.com/victim-org/project` pointing to attacker infrastructure (or a repo they push malicious commits to).

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
