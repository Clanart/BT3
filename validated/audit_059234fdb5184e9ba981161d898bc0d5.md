### Title
DkgConfirmer cached preprocess is shared across distinct validator sets/tributaries, causing deterministic nonce reuse that leaks the validator's signing key - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches the FROST preprocess seed (`CachedPreprocess`) in `SigningProtocolDb::CachedPreprocesses`, keyed only by `context`. For `DkgConfirmer`, the context is `(b"DkgConfirmer", attempt)` — it does not include the tributary genesis, `TributarySpec`, validator set, or network. Because DKG attempt counters reset per validator set (per tributary), the same DB key is hit for unrelated signing sessions, and `seeded_preprocess` deterministically regenerates identical nonces for different messages. Publishing two signature shares under identical nonces over different `set_keys_message`s allows an observer to recover the validator's MuSig secret share — i.e., its root-of-trust key.

### Finding Description
In `preprocess_internal`, a random 32-byte seed is generated only if `CachedPreprocesses::get(txn, &context)` is empty; otherwise the stored seed is XOR-decrypted and passed to `AlgorithmSignMachine::from_cache`, which reruns `seeded_preprocess` — `ChaCha20Rng::from_seed(*seed.0)` — regenerating the exact same nonces and commitments (coordinator/src/tributary/signing_protocol.rs:123-147, crypto/frost/src/sign.rs:121-144).

`DkgConfirmer::signing_protocol` builds `context = (b"DkgConfirmer", self.attempt)` (coordinator/src/tributary/signing_protocol.rs:275). `DkgConfirmer::new`/`preprocess`/`share`/`complete` are invoked per DKG attempt via `dkg_confirmation_nonces` and `generated_key_pair` in coordinator/src/tributary/handle.rs:36-60, and again inside `DkgConfirmed` handling (handle.rs:533-535). Nothing namespaces the cache by `spec.genesis()` or `spec.set()`. When a validator participates in a later DKG (new session/set, new tributary genesis — e.g., after set rotation or for another network's tributary handled by the same coordinator DB), `attempt` restarts at 0/1 and the stale seed is reused. The header comment itself acknowledges nonce reuse leaks the key and that safety is only derived from "re-deciding nonces" on rebuild — but the DB-persisted cache survives the rebuild and is keyed too coarsely.

The signed message `set_keys_message(&self.spec.set(), &removed, key_pair)` (signing_protocol.rs:296-300) differs across sets, so the same nonce signs two different challenges: classic Schnorr nonce reuse → `s1 - s2 = k(c1 - c2)`-style recovery of the secret share.

### Impact Explanation
All preprocess commitments and signature shares are published on the public tributary (`Transaction::DkgShares` carries `confirmation_nonces`, `Transaction::DkgConfirmed` carries `confirmation_share`). Any unprivileged observer who sees two DKG confirmations under the same `attempt` index for the same validator key observes identical nonce commitments and two shares over distinct messages, enabling offline recovery of that validator's MuSig secret — the validator root-of-trust key used for DKG confirmation and slashing votes. That is key-share recovery of a high-value key.

### Likelihood Explanation
Requires the same validator key to confirm two DKG attempts bearing the same `attempt` number under different `spec`/`set` while sharing the coordinator DB — precisely the cross-session state-sharing condition the reference bug class describes, and it occurs naturally across validator-set rotations since contexts omit genesis/session. I could not fully confirm whether `SigningProtocolDb` is instantiated per-tributary (which would isolate the cache) or shared coordinator-wide; `DkgConfirmer` receives `spec` as a parameter on a shared `txn`, suggesting a shared DB, but if the DB were per-tributary the collision would not occur.

### Recommendation
Include the tributary genesis (or `spec.set()`/session) in the `CachedPreprocesses` context key — e.g., `context = (b"DkgConfirmer", spec.genesis(), attempt)` — and likewise mix it into the encryption-key preimage. Additionally, delete (`del`) the cache entry once `complete`/`share` succeeds, and enforce the noted TODO of verifying the on-chain published preprocess equals the locally presumed one before emitting shares.

### Proof of Concept
1. Validator V participates in tributary A's DKG, attempt 0. `dkg_confirmation_nonces` → `preprocess_internal` stores seed S under key `(b"DkgConfirmer", 0)`, and publishes nonce commitments `D, E` in `DkgShares`.
2. Tributary B (new genesis, possibly overlapping validator set including V) runs DKG attempt 0. `preprocess_internal` finds `(b"DkgConfirmer", 0)` already set, decrypts S, and `seeded_preprocess` regenerates the identical `D, E` — visible publicly as reused commitments.
3. `share`/`complete` for each confirmation sign `set_keys_message(set_A, ...)` and `set_keys_message(set_B, ...)` — different messages → different challenges `c_A, c_B`, same nonce `k`.
4. From the two published shares `z_A = k + c_A·x` and `z_B = k + c_B·x` (modulo the known MuSig binding/Lagrange coefficients), the observer solves `x = (z_A - z_B)/(c_A - c_B)`, recovering V's secret share.
