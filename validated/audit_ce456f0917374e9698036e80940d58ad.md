### Title
Untrusted Repository Symlinks Cause `discardChanges` to Move/Delete Files Outside the Repository via `moveItemToTrash` - (File: `app/src/lib/stores/git-store.ts`)

### Summary
The original report flags a destructive operation (`resetAllocationsByUser`) that acts on data it does not properly scope-check, and is accepted only because it is admin-gated. Desktop's `GitStore.discardChanges` implements an analogous unchecked destructive operation over paths derived from `git status`, but unlike privileged-only contract code, it is reachable by any user who opens/clones an attacker-controlled repository and clicks "Discard Changes." The path used for the filesystem-destructive operation is never validated to stay inside the repository root, even though the codebase has a dedicated helper (`resolveWithin`) for exactly this purpose used elsewhere.

### Finding Description
`GitStore.discardChanges` resolves each working-directory file path directly against the repository root and passes it straight to Electron's trash API: [1](#0-0)

```
        Path.resolve(this.repository.path, file.path)
```

`file.path` originates unmodified from parsing `git status --porcelain=2 -z` output in `app/src/lib/status-parser.ts`, where the path field is taken verbatim from git's output with no traversal/symlink checks: [2](#0-1) 

The codebase already contains `resolveWithin`, which resolves a path underneath a root and rejects it if `realpath` shows it escapes the root (i.e., it explicitly accounts for symlink traversal): [3](#0-2) 

This helper is used elsewhere specifically to stop path escape via attacker-supplied paths (e.g., deep-link file opening): [4](#0-3) 

But `discardChanges` in `git-store.ts` does not call `resolveWithin`/`realpath` at all — it uses plain `Path.resolve`, which does not dereference symlinks. If a cloned repository contains a tracked directory entry that is actually a symlink pointing outside the repository (e.g., `link -> ../../../Users/victim/.ssh`), and git status reports a change under that path (e.g., `link/authorized_keys` shown as new/modified/untracked), `Path.resolve(repoPath, 'link/authorized_keys')` produces a path that, at the OS level, resolves through the symlink to a location outside the repo. `shell.moveItemToTrash` then trashes (or, in the untracked/no-trash-support fallback branch, `rm`'s) a file outside the repository, entirely outside user intent and outside the guard that exists elsewhere in the codebase.

### Impact Explanation
An attacker who controls repository content (a cloned/forked repo, a repo added via "Add Local Repository", or a repo received via a PR checkout) can craft a working tree so that ordinary use of Desktop's "Discard Changes" feature silently deletes or moves arbitrary files outside the repository that the OS user has permission to access (e.g., SSH keys, other project files, browser profile data). This is a write/delete-outside-repo primitive achieved purely through repository content, matching the "file write/read outside the repo" impact category. Severity is bounded by requiring symlink support on the host OS/filesystem and the user taking the ordinary "Discard Changes" action on files that appear in the Changes list.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to (1) clone or open an attacker-supplied repository and (2) invoke "Discard Changes" on the affected paths — both very common Desktop workflows, especially "Discard all changes" which a user might click without inspecting every path. No admin rights, local access, or pre-existing malware are needed; the entire attack surface is repository content, matching the "unprivileged attacker controls a cloned/fetched repository" criterion. Windows' more restrictive symlink creation could reduce likelihood there relative to macOS/Linux, but the underlying repo can still be cloned cross-platform.

### Recommendation
Route all filesystem paths used for destructive operations in `discardChanges` (and any other function under `git-store.ts` that resolves `file.path`/`file.status.oldPath` against `repository.path`) through `resolveWithin` (from `app/src/lib/path.ts`) before calling `shell.moveItemToTrash` or `rm`, rejecting/aborting the operation if the resolved real path escapes the repository root, consistent with the existing protection pattern in `dispatcher.ts`.

### Proof of Concept
1. Attacker creates and hosts a repository containing a tracked symlink `payload -> ../../../../Users/victim/.ssh` (relative traversal to escape the clone directory), committed to the repo.
2. Attacker adds a second commit that creates/modifies a file `payload/id_rsa` (which, via the symlink, is actually a file living outside the repo on checkout) so `git status` reports it as untracked/modified.
3. Victim clones the repository with Desktop and opens the Changes view; `payload/id_rsa` appears as a change.
4. Victim clicks "Discard Changes" (or "Discard All Changes").
5. `GitStore.discardChanges` computes `Path.resolve(repoPath, 'payload/id_rsa')` and calls `shell.moveItemToTrash` on it without verifying via `resolveWithin`/`realpath` that the target is inside the repository, resulting in the victim's real `~/.ssh/id_rsa` (or similar) being moved to trash/deleted outside the cloned repository.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
