### Title
Deep-link `branch` parameter validation omits leading-dash/flag-prefix check, allowing crafted `x-github-client://openrepo` links to smuggle a git option into branch checkout - (File: `app/src/lib/parse-app-url.ts`, `app/src/lib/sanitize-ref-name.ts`)

### Summary
The external report's bug class is: a value that is trusted to be "safe" is accepted into a sensitive operation without an upper/format bound check (fee > 100%, draining funds). The Desktop analog is the `branch` parameter accepted from the `x-github-client://openrepo/...` protocol handler: it is validated only against a ref-name "invalid character" regex, which does not reject a leading `-`/`--`, before being forwarded to branch checkout logic that ultimately becomes a positional argument to `git`.

### Finding Description
`parseAppURL` extracts `branch` from the deep-link query string and validates it with `testForInvalidChars`: [1](#0-0) 

`testForInvalidChars` is backed by `invalidCharacterRegex`, which blocks control characters, space, `~^:?*[\|"<>`, `@{`, consecutive/leading/trailing dots, `.lock` suffix, and trailing slash — but it does **not** reject a value that begins with `-` or `--`: [2](#0-1) 

Note that `sanitizedRefName` (used elsewhere, e.g. worktree branch names) explicitly strips a leading `-`/`+` via `.replace(/^[-\+]*/g, '')`, but `testForInvalidChars` (the function actually used to gate the untrusted deep-link `branch` value) performs no equivalent check. This asymmetry is the exact "missing limit/bound check" pattern from the report: one code path (`setFees`/`sanitizedRefName`) enforces the bound, another entry path (`constructor`/`parseAppURL`) does not.

The accepted `branch` value flows to `Dispatcher.openBranchNameFromUrl`, which calls `this.checkoutLocalBranch(repository, branchName)` after cloning/fetching the attacker-influenced remote: [3](#0-2) 

### Impact Explanation
If the branch string is passed as a bare positional argument to a `git` subcommand (e.g. `checkout`/`branch`) without a `--` end-of-options marker, a value starting with `-`/`--` can be interpreted by git as an option rather than a ref name (classic git argument-injection pattern, e.g. `--upload-pack=`, `-c`, or similar option-style values). Since the attacker fully controls the deep-link URL that a user clicks (`x-github-client://openrepo/<url>?branch=<payload>`), this satisfies the "attacker controls a link/deep link the user clicks" criterion, and a successful injection could result in unintended git behavior or code execution outside the expected scope, or silent corruption of the checkout state.

### Likelihood Explanation
I was not able to fully confirm, within the available tool budget, whether the concrete `git` invocation reached by `checkoutLocalBranch` appends a `--` separator (as `getBranchCheckoutArgs` in `app/src/lib/git/checkout.ts` does for existing `Branch` objects) or passes the raw string as an unguarded positional argument when the branch does not yet exist locally and must be created/tracked from a remote ref. This is the piece of the chain I could not fully trace before running out of iterations, so I cannot state with certainty that the injection reaches an unguarded git argument list — only that the **validation gap itself** (missing leading-dash rejection in `testForInvalidChars`) is confirmed in local code and is inconsistent with the stricter `sanitizedRefName` used elsewhere. [4](#0-3) 

### Recommendation
Harden `testForInvalidChars` (or add a dedicated check at the `parseAppURL` boundary) to reject any `branch` value beginning with `-`, mirroring the stripping behavior already implemented in `sanitizedRefName`. Additionally, audit every call site that forwards an externally-supplied ref/branch string into a `git` argument array and ensure a `--` end-of-options marker precedes the ref, consistent with `getBranchCheckoutArgs`.

### Proof of Concept
1. Craft a deep link: `x-github-client://openrepo/https://github.com/<attacker>/<repo>?branch=--upload-pack%3D%2Ftmp%2Fpayload`
2. `testForInvalidChars` does not reject the leading `--`, so `parseAppURL` returns `{ name: 'open-repository-from-url', branch: '--upload-pack=/tmp/payload', ... }`.
3. User clicks the link; Desktop clones/opens the repo and calls `checkoutLocalBranch(repository, '--upload-pack=/tmp/payload')`.
4. If the underlying git invocation does not prepend `--`, git may parse the value as an option rather than a ref name.

Given the unresolved step (3→4 exact git argument construction), I recommend this be verified with full repo access (a Devin session) before treating it as a confirmed, exploitable vulnerability rather than a validation-gap finding.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
