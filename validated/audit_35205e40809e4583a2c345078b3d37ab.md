## Title
Unvalidated `order.inputs` in `fillOrder` → `VWAPOracle.recordSpread` allows fabricated, self-funded orders to pollute the spread bucket of any arbitrary `(sourceChain, token)` pair - (File: evm/src/apps/IntentGatewayV2.sol / evm/src/utils/VWAPOracle.sol)

### Summary
`IntentGatewayV2.fillOrder` forwards the raw, attacker-supplied `order.inputs` array (not the internally-validated `escrowedInputs`) directly into `VWAPOracle.recordSpread`, together with `options.outputs`. The only consistency check performed anywhere in the fill path binds `options.outputs[i].token` to `order.output.assets[i].token` — there is no check binding `order.inputs[i].token`/`amount` to any real escrow, nor any requirement that the `Order` being "filled" was ever actually placed via `placeOrder`. This lets an unprivileged caller submit a wholly fabricated `Order`, self-fill it for a trivial cost, and drive `recordSpread`'s volume-weighted spread bucket for any pre-configured `(sourceChain, inputToken)` with an arbitrary input token and arbitrary (attacker-chosen) volume.

### Finding Description
`fillOrder` calls the oracle with unvalidated data: [1](#0-0) 

The only binding check in the same-chain fill path is between `options.outputs[i].token` and `order.output.assets[i].token`: [2](#0-1) 

Nothing constrains `order.inputs[i].token` or `order.inputs[i].amount` to a real, previously-escrowed order. `placeOrder` computes `commitment` from `keccak256(abi.encode(order))` and only ever writes to `_orders[commitment][token]` when a matching order was actually placed. `fillOrder` never verifies that such a placement occurred — it merely checks `_filled[commitment] == address(0)`: [3](#0-2) 

If a commitment was never placed, `_orders[commitment][token]` is simply `0`, and `_fillSameChain` silently computes `escrowedAmount = 0` for that leg rather than reverting: [4](#0-3) 

An attacker can therefore construct a fresh (never-placed) `Order` with:
- `order.inputs[0].token` = any token address with configured decimals in `_tokenDecimals[sourceChainHash][...]` (attacker picks which bucket to pollute, including adjacent/neighboring token addresses),
- `order.inputs[0].amount` = an arbitrary huge value (this becomes the VWAP volume weight),
- `order.output.assets[0]` / `options.outputs[0]` = a trivial (e.g. 1 wei) transfer of some ERC20 they control, with `beneficiary` set to themselves.

`recordSpread` then uses `inputToken` from `order.inputs[i].token` as the storage key and `inputAmountNormalized` (derived from the attacker-chosen `amount`) as the VWAP volume weight: [5](#0-4) 

Because the storage key (`inputToken`) and the weight (`inputAmountNormalized`) both come from data that was never verified against a real escrow or real fill, an attacker can update the spread bucket of any configured `(sourceChain, token)` pair — including tokens they never actually filled or even transacted meaningfully in — at near-zero cost (only the tiny self-paid `options.outputs` amount).

### Impact Explanation
This breaks the invariant that "spread accounting must remain injective per `(sourceChain, token)` and never alias adjacent tokens." Any downstream consumer of `VWAPOracle.spread()`/`decimals()` (e.g. pricing/reward logic that trusts the oracle's per-token VWAP) can be manipulated by an unprivileged actor to report an arbitrary spread for a target token, skewing derived values such as reward amounts, fill valuations, or beneficiary payouts that depend on `spread(sourceChain, token)`. This matches the "wrong token amount, wrong reward amount, or wrong order value" High-impact category.

### Likelihood Explanation
High. The attack requires no privileged role, no relayer/prover collusion, and no proof forgery — only a self-crafted `Order` struct and a trivial self-funded token transfer, callable directly through the public `fillOrder` entrypoint. It works for any account holding a small amount of any ERC20 usable as the "output" leg.

### Recommendation
- Pass the internally-computed `escrowedInputs`/`outputFills` (which are derived from validated, actually-escrowed amounts) into `recordSpread`, not the raw `order.inputs`/`options.outputs` calldata.
- Require that `commitment` corresponds to a real, previously placed order (e.g., revert if no escrow exists for any input token) before treating a fill as valid for both settlement and oracle accounting.
- Add an explicit binding check between `order.inputs[i].token` and `order.output.assets[i].token`/`options.outputs[i].token` if the oracle is documented as "same-token swaps only," so mismatched pairs cannot be recorded.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.fillOrder(order, options)` where `order` was never submitted through `placeOrder` (so `commitment` has no escrow).
2. `order.inputs[0] = {token: <targetToken>, amount: 1_000_000e18}` (huge, fabricated volume; `<targetToken>` has decimals configured in the oracle).
3. `order.output.assets[0] = options.outputs[0] = {token: <cheapToken>, amount: 1}`, `order.output.beneficiary = attacker`.
4. `_fillSameChain` passes the output-token equality check (line 68), computes `escrowedAmount = 0` (line 118, since no real escrow exists), marks the order fully filled, and transfers only 1 wei of `<cheapToken>` from attacker to attacker.
5. `fillOrder` then calls `recordSpread(commitment, order.source, order.inputs, options.outputs)`, updating `_tokenSpreads[sourceChainHash][<targetToken>]` with a weight of `1_000_000e18` and a spread computed from `1_000_000e18` input vs `1` wei output — an extreme, fully attacker-chosen skew of `<targetToken>`'s VWAP bucket, for the cost of 1 wei.         uint256 tokensLen = inputs.length;
        for (uint256 i = 0; i < tokensLen; i++) {
            address inputToken = address(uint160(uint256(inputs[i].token)));
            address outputToken = address(uint160(uint256(outputs[i].token)));

            // Get decimals for input token from storage (remote chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 inputDecimals = inputToken == address(0) ? 18 : _tokenDecimals[sourceChainHash][inputToken];
            if (inputDecimals == 0) continue; // Skip if decimals not configured

            // Get decimals for output token directly from contract (local chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();

            // Normalize both amounts to 18 decimals for comparison
            uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
            uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

            // Calculate spread for this token: (output - input) / input * 10000
            // Positive spread = filler provided more tokens (good for user)
            // Negative spread = filler provided fewer tokens (filler captured spread)
            int256 spreadBps = 0;
            if (inputAmountNormalized > 0) {
                int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
                spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
            }

            // Update cumulative spread data for this token (weighted by volume)
            int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
            _updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);

            // Emit event for each token
            emit SpreadRecorded(commitment, outputToken, spreadBps);
        }
