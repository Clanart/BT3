### Title
Clone protection against malicious recursive-submodule repositories is explicitly disabled (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: `app/src/lib/git/clone.ts`)

### Summary
The C4 report describes a reentrancy pattern: an attacker-controlled callback (ERC-777 hook) fires in the middle of a state-transition sequence, before the invariant-protecting update is finished, letting the attacker repeat the transition in an inconsistent state and drain funds. The generalizable "broken invariant" is: *a safety mechanism that is supposed to gate a multi-step operation against attacker-controlled input is bypassed/disabled, so the attacker's payload executes during a step that assumes it is safe.*

In GitHub Desktop, `clone()` performs exactly this kind of unsafe multi-step, attacker-influenced operation: it runs `git clone --recursive` against a remote URL supplied by the user (which resolves to an attacker-controlled repository the moment the user clones/adds a malicious remote), and it explicitly sets `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment for that command. [1](#0-0) 

### Finding Description
Git 2.45.1+ introduced `GIT_CLONE_PROTECTION_ACTIVE` (and the related submodule protections) specifically as a fix for CVE-2024-32002 — a case where a malicious repository with crafted (case-insensitive/symlinked) nested `.git`/submodule paths could, during a recursive clone, cause files to be written into `.git/hooks` and have those hooks *automatically executed* as part of the clone/checkout sequence (i.e., attacker-controlled content executed as a side effect of a "safe" operation, analogous to the ERC-777 hook firing mid-transaction). Git's built-in protection refuses such clones unless explicitly disabled.

Desktop's `clone()` function unconditionally sets:
```
GIT_CLONE_PROTECTION_ACTIVE: 'false'
```
merged into the execution environment for every `git clone --recursive ... -- <url> <path>` invocation. [1](#0-0) 

This means the very guard Git ships to stop the "hostile recursive submodule → hook execution" class of attacks is turned off for every clone Desktop performs — including clones of arbitrary/unverified remotes that a user pastes into the "Clone repository" dialog or that a deep link/`x-github-client` URL scheme feeds into Desktop. The other safety check present, `isClonePathSensitive`, only guards the *destination directory* (blocking cloning into `~/.ssh`, `~/.gnupg`, etc.) — it does nothing to validate the *contents* of the attacker-controlled repository itself, and does not compensate for the disabled Git-level protection. [2](#0-1) 

Additionally, submodule updates after checkout (`updateSubmodulesAfterOperation`, used by `checkoutBranch`/`checkoutCommit`) run `git submodule update --init --recursive` against repository-controlled `.gitmodules` content, and can even be run with `protocol.file.allow=always`, without any additional path-sanitization of submodule targets before invoking Git. [3](#0-2) [4](#0-3) 

### Impact Explanation
Because Desktop disables `GIT_CLONE_PROTECTION_ACTIVE`, cloning a malicious repository (attacker-controlled — satisfies the "attacker controls a cloned/fetched repository" impact criterion) can result in Git writing attacker-supplied files into `.git/hooks` via crafted submodule paths during the recursive clone, and having those hooks executed by Git itself as part of the clone/checkout flow. That is code execution on the user's machine triggered purely by cloning a URL, without any further "unnatural" user action — squarely inside the valid impact class ("attacker controls a cloned/fetched repository ... result is code execution").

### Likelihood Explanation
Likelihood is high for any environment where the underlying Git binary embeds/enforces the CVE-2024-32002 mitigation by default (recent `dugite`/Git for Windows or system Git ≥ 2.45.1): Desktop actively opts out of that mitigation for every clone, rather than opting in only when a trusted/verified source is used. No local access, admin rights, or pre-existing malware is required — only that the user clones (or is induced via a deep link / "Open in Desktop" flow) a repository the attacker controls.

### Recommendation
- Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()`; let Git's built-in clone protection remain active by default.
- If disabling protection is required for legitimate use cases (e.g., known-safe local test fixtures), scope it narrowly and never apply it to clones of arbitrary/unverified remote URLs, especially those originating from deep links or user-pasted URLs.
- Audit `updateSubmodulesAfterOperation` and other `git submodule update --recursive` call sites for the same exposure, and ensure hook execution paths (`getRepoHooks`/`withHooksEnv`) cannot be seeded from submodule-written content.

### Proof of Concept
1. Attacker publishes a public repository containing a submodule whose configured path is crafted (case-variant/symlink trick per CVE-2024-32002) so that, on a case-insensitive filesystem, `git submodule update --init --recursive` writes a file into the top-level `.git/hooks` directory (e.g., `post-checkout`).
2. Victim opens GitHub Desktop and clones the attacker's repository URL (via the Clone dialog or a `x-github-client://` deep link).
3. Desktop calls `clone()`, which runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment, per [1](#0-0) .
4. Because the protection is disabled, Git proceeds with the recursive submodule clone instead of aborting, the malicious hook file lands in `.git/hooks`, and it is executed automatically as part of the checkout that follows the clone — achieving code execution on the victim's machine without any further action.

*Note: I was not able to execute Git itself to confirm end-to-end exploitation against the specific `dugite`-bundled Git version in this repo (that requires running the actual Git binary/CVE-2024-32002 payload, which is outside the scope of static code inspection). The finding is based on the confirmed presence of the explicit protection-disabling environment variable in the clone code path, which is a real, verifiable deviation from Git's upstream security defaults.*

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
