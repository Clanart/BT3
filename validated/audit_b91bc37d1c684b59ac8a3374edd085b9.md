### Title
Webhook `shop_domain` is not covered by HMAC verification, allowing cross-shop webhook spoofing - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates only the raw request body via HMAC, while the `shop_domain` helper reads the shop identifier from a separate, unauthenticated HTTP header. Because the two values are never cross-checked, an attacker who legitimately owns a valid HMAC-signed webhook body (from their own installed shop) can replay it against the endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, causing the app to process the payload as if it originated from a different, victim shop. This mirrors the reported bug class: an identifier used to select which "record"/tenant the data belongs to (`requestId` in the report; `shop_domain` here) is not validated against the cryptographically verified data.

### Finding Description
`verify_request` computes and checks the HMAC only over `request.raw_post`: [1](#0-0) 

`shop_domain` is derived independently from the `X-Shopify-Shop-Domain` header, which is not part of the HMAC input: [2](#0-1) 

The HMAC itself is computed purely over `data = request.raw_post` using the app's shared secret, with no binding to any header: [3](#0-2) 

The gem's own documentation recommends exactly the vulnerable pattern for custom webhook controllers — pass the unverified `shop_domain` straight to a background job alongside the verified body: [4](#0-3) 

The generated privacy webhook jobs follow the same shape: they look up a `Shop` record purely by the `shop_domain` parameter and then operate `with_shopify_session` on that shop, with no verification that `shop_domain` matches the shop whose data actually produced the signed body: [5](#0-4) [6](#0-5) 

Because the shared secret is the same for all shops on a given app (it's the app's client secret, not per-shop), any merchant who installs the app on their own store can obtain a validly-HMAC'd body/signature pair for their own webhook traffic, then resend that exact body+HMAC to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at any other shop. `verify_request` will accept it because it never inspects the header.

### Impact Explanation
An attacker-controlled webhook body can be attributed to an arbitrary victim shop domain, since only the body — not the shop association — is authenticated. Depending on the app's job implementations (which the gem's own docs and generators encourage to trust `shop_domain` directly), this enables cross-shop data confusion: triggering shop-scoped background jobs (including the mandatory privacy jobs `shop/redact`, `customers/redact`, `customers/data_request`, or any app-specific `*_job`) against a shop the attacker does not own, using attacker-chosen body content. This is a cross-shop access/data-integrity issue reachable from an unrelated, unprivileged merchant account.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to install the app on their own shop (a normal, unprivileged action any Shopify merchant can take) and then send a crafted HTTP POST to the app's public webhook endpoint with a forged header — no secret leakage or special privilege is needed beyond having a legitimate, low-cost installation to harvest one valid `(body, HMAC)` pair.

### Recommendation
- Short term: Bind the shop identity to the authenticated payload. Either compute the HMAC over the shop domain plus body, or (preferably) rely solely on the shop identifier embedded and covered within the verified webhook body/registration context (as most Shopify webhook payloads include shop-identifying fields) rather than trusting the `X-Shopify-Shop-Domain` header independently of HMAC verification.
- Long term: Update `ShopifyApp::WebhookVerification` and the generator/documentation examples so `shop_domain` is only trusted after confirming it corresponds to the same request whose body was HMAC-verified (e.g., document that a webhook registered for the app is scoped per-shop by Shopify's own delivery, but explicitly flag reliance on the header as unauthenticated, and provide a verified alternative for apps that must strictly bind the two).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `carts/update`), capturing the resulting POST request: body `B` and valid header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's shared secret over `B`).
2. Attacker sends a new POST to the app's webhook endpoint (e.g., `/webhooks/carts_update`) with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyApp::WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which succeeds because it only re-derives the HMAC from `B` and the shared secret — it never inspects the domain header. [7](#0-6) 
4. The controller (following the gem's documented pattern) enqueues a job with `shop_domain: "victim-shop.myshopify.com"` and `webhook: B`, causing victim-scoped processing of attacker-supplied data. [8](#0-7)

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```markdown
If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
```
