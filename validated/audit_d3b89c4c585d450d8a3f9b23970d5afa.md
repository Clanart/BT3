### Title
Non-standard/non-bool-returning ERC20 `approve()` in IBC receive-callback flow permanently freezes user funds in an unrecoverable isolated address - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
`ContractKeeper.IBCReceivePacketCallback` in `x/ibc/callbacks/keeper/keeper.go` uses the fixed standard `contracts.ERC20MinterBurnerDecimalsContract.ABI` (which declares `approve()` returning `bool`) to call `approve` on an arbitrary registered token-pair ERC20 contract, then strictly requires the returned bytes to unpack into a `bool`. This is the same bug class as the reported `setSwapperAllowance` finding: any ERC20 (native or externally registered) that does not conform exactly to that ABI — e.g. a USDT-style token whose `approve()` returns no data — will cause the mandatory `UnpackIntoInterface` step to fail, aborting the callback with `ErrAllowanceFailed`.

### Finding Description [1](#0-0) 

The flow is:
1. An IBC ICS20 transfer completes and funds are moved/minted into a deterministically-derived "isolated address" (`types.GenerateIsolatedAddress`) before the callback runs. [2](#0-1) 
2. The keeper then attempts to grant the target contract an allowance over the isolated address's ERC20 tokens by directly calling `approve` via `CallEVM`, using the hardcoded `erc20.ABI` (a standard OpenZeppelin-style ABI expecting a `bool` return): [3](#0-2) 
3. If the target contract is a non-standard ERC20 (no bool return value on `approve`, like real-world USDT), `res.Ret` will be empty/malformed and `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` returns an error, or unpacks to `false`, causing the whole callback to fail with `ErrAllowanceFailed`.
4. Per the callback's own documented security model, tokens are already resident in the isolated address at this point, and that address is a hash-derived account (`GenerateIsolatedAddress(channel, sender)`) with **no known private key** — it exists purely as a transient routing address for this callback mechanism. The function's own doc comments state the isolated address exists "to prevent unauthorized access" and warns that failure paths can leave "funds getting stuck in the isolated address, since they would become irretrievable" (this exact concern is called out for the *subsequent* step, i.e., after a successful approve/transferFrom, at lines 229-239) — the same terminal-loss condition is reached even earlier if `approve` itself fails for a non-standard token, because no code path exists to move funds out of the isolated address once the automated approve→transferFrom sequence cannot proceed.
5. Because `IBCReceivePacketCallback` errors are executed against a `CacheContext` and only committed via `writeFn()` on success, an approve failure means the whole cached execution (including any partial recovery) is discarded, leaving the transferred coins permanently at the isolated address with no admin, contract, or user having a way to spend from it (no private key, no allowance, no code at that address).

### Impact Explanation
This satisfies the Critical "permanent freezing/locking of user funds" allowed impact: any ICS20 transfer that uses the destination-callback feature to interact with a token pair backed by a non-standard ERC20 (i.e., an ERC20 whose `approve` doesn't return a `bool`, matching the exact bug class from the external USDT report) results in user funds being irreversibly stranded in an address nobody controls. This is not a mere isolated auth-bypass or fee issue — it is unrecoverable loss of user-owned value transferred cross-chain.

### Likelihood Explanation
Likelihood is Medium-to-High: any relayer/user can trigger a destination callback via ICS20 packet memo; the vulnerable code path executes automatically whenever a token pair's underlying ERC20 contract does not strictly conform to the OpenZeppelin `approve() returns (bool)` interface. Non-standard tokens (USDT-style, missing return value) are common in the wild, and `RegisterERC20` allows registering pre-existing, externally-deployed ERC20 contracts as token pairs, so the chain cannot guarantee that all registered contracts return a proper bool from `approve`.

### Recommendation
- Do not hard-require a `bool` return from `approve`; use a `SafeERC20`-style low-level call check (verify call succeeded and, if return data is present, that it decodes to `true`; treat empty return data as success) instead of `erc20.ABI.UnpackIntoInterface`.
- Additionally, add a recovery/rescue path for the isolated address (e.g., allow the original sender or module governance to reclaim funds stuck there) so that any failure in the approve/transferFrom chain does not result in permanent, unrecoverable loss.

### Proof of Concept
1. Register (via `MsgRegisterERC20`) a token pair backed by a bespoke ERC20 contract whose `approve(address,uint256)` function is implemented to not return any data (mirroring mainnet USDT bytecode behavior), while still accepting the standard `transfer`/`transferFrom` selectors.
2. Perform an ICS20 transfer into this chain with a destination-callback memo pointing at a valid contract address (passes the `IsContract` check).
3. Observe `IBCReceivePacketCallback`: tokens are transferred to `isolatedAddr` (from the underlying ICS20 receive, executed by ibc-go before/independently of the callback), then the callback calls `CallEVM(... "approve" ...)` against the non-standard token.
4. `res.Ret` is empty/non-bool; `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` errors out (or returns `approveSuccess == false`), and the function returns `types.ErrAllowanceFailed`.
5. Because the underlying ICS20 receive is not rolled back by a callback error (per ibc-go callbacks middleware semantics — callback failures do not revert the packet acknowledgement/transfer), the tokens remain permanently held at `isolatedAddr`, an address with no corresponding private key, contract code, or approved spender — funds are irrecoverable. func (k ContractKeeper) IBCReceivePacketCallback(
	ctx sdk.Context,
	packet ibcexported.PacketI,
	ack ibcexported.Acknowledgement,
	contractAddress string,
	version string,
) error {
	data, err := transfertypes.UnmarshalPacketData(packet.GetData(), version, "")
	if err != nil {
		return err
	}

	cbData, isCbPacket, err := callbacktypes.GetCallbackData(data, version, packet.GetDestPort(), ctx.GasMeter().GasRemaining(), ctx.GasMeter().GasRemaining(), callbacktypes.DestinationCallbackKey)
	if err != nil {
		return err
	}
	if !isCbPacket {
		return nil
	}

	// `ProcessCallback` in IBC-Go overrides the infinite gas meter with a basic gas meter,
	// so we need to generate a new infinite gas meter to run the EVM executions on.
	// Skipping this causes the EVM gas estimation function to deplete all Cosmos gas.
	// We re-add the actual EVM call gas used to the original context after the call is complete
	// with the gas retrieved from the EVM message result.
	cachedCtx, writeFn := ctx.CacheContext()
	cachedCtx = evmante.BuildEvmExecutionCtx(cachedCtx).
		WithGasMeter(evmtypes.NewInfiniteGasMeterWithLimit(cbData.CommitGasLimit))

	// receiver := sdk.MustAccAddressFromBech32(data.Receiver)
	receiver, err := sdk.AccAddressFromBech32(data.Receiver)
	if err != nil {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress,
			"acc addr from bech32 conversion failed for receiver address: %s", data.Receiver)
	}
	receiverHex, err := utils.HexAddressFromBech32String(receiver.String())
	if err != nil {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress,
			"hex address conversion failed for receiver address: %s", receiver)
	}

	// Generate secure isolated address from sender.
	isolatedAddr := types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)
	isolatedAddrHex := common.BytesToAddress(isolatedAddr.Bytes())

	acc := k.authKeeper.NewAccountWithAddress(ctx, receiver)
	k.authKeeper.SetAccount(ctx, acc)

	// Ensure receiver address is equal to the isolated address.
	if receiverHex.Cmp(isolatedAddrHex) != 0 {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress, "expected %s, got %s", isolatedAddrHex.String(), receiverHex.String())
	}

	contractAddr := common.HexToAddress(contractAddress)

	// Check if the contract address contains code.
	// This check is required because if there is no code, the call will still pass on the EVM side,
	// but it will ignore the calldata and funds may get stuck.
	if !k.evmKeeper.IsContract(ctx, contractAddr) {
		return errorsmod.Wrapf(types.ErrContractHasNoCode, "provided contract address is not a contract: %s", contractAddr)
	}
