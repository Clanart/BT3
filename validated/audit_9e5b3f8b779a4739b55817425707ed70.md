### Title
A malicious FROST participant can force the BIP-340 aggregate nonce to infinity, panicking every signer - (File: `networks/bitcoin/src/crypto.rs`)

### Summary
`bitcoin-serai`’s BIP-340 adapter passes the combined FROST nonce to `x(R)`, which unconditionally panics if `R` is the point at infinity. Because an attacker-controlled signer can choose its preprocess after learning every other participant’s preprocess, it can select nonce commitments whose bound contribution cancels the aggregate `R` to infinity. `AlgorithmSignMachine::sign` then calls `Hram::hram` with that invalid nonce, causing a panic rather than returning `FrostError`.

### Finding Description
`AlgorithmSignMachine::sign` collects all participant preprocesses, calculates the FROST binding factors, and derives the aggregate nonce points with `B.nonces`. [1](#0-0) 

For the Bitcoin Schnorr algorithm, the nonce specification is a single nonce against the curve generator, so each participant contributes a bound commitment `D_i + rho_i * E_i`. [2](#0-1) [3](#0-2) 

Preprocess deserialization accepts arbitrary canonical curve points through `Commitments::read`, including the identity encoding, without rejecting nonce commitments that can produce an identity aggregate. [4](#0-3) 

The Bitcoin `Hram` implementation extracts the x-coordinate of `R`, but `x` panics when `R` is infinity. [5](#0-4) [6](#0-5) 

### Impact Explanation
One malicious signing participant can make all signers panic during `sign`, preventing the threshold wallet from producing the requested Bitcoin signature. Since spending requires a valid threshold signature, this creates a reachable denial of signing and can leave wallet funds temporarily unspendable until the malicious participant is excluded and the signing attempt is retried. [7](#0-6) [8](#0-7) 

This is worse than ordinary invalid-message rejection because the invalid preprocess is not converted into `FrostError`; it reaches an infallible affine-coordinate extraction and panics. [5](#0-4) 

### Likelihood Explanation
An unprivileged participant needs only the ability to submit a normal preprocess through `read_preprocess` and `sign`. [9](#0-8) 

The attack is deterministic when that participant submits its preprocess after observing the other participants’ preprocesses: it can compute their aggregate bound contribution, set `E_i = identity`, and set `D_i` to the negation of that aggregate. The attacker’s bound contribution then becomes `D_i`, regardless of its binding factor. [10](#0-9) 

Because every signer uses the same aggregate `nonce_sums` to calculate the challenge, all honest signers invoke `x(R)` on the maliciously forced infinity and hit the same panic. [11](#0-10) [6](#0-5) 

### Recommendation
Reject the point at infinity in nonce commitments during `Commitments::read`, or explicitly detect an identity aggregate nonce before invoking `Hram::hram` and return `FrostError` identifying the responsible participant where possible. [4](#0-3) 

The BIP-340 adapter should also avoid panicking on adversarial points: `x` and `x_only` should return `Option`/`Result`, and the FROST algorithm should propagate that failure as a signing or participant error rather than crashing the caller. [12](#0-11) 

### Proof of Concept
For Schnorr there is one nonce commitment pair `(D_i, E_i)` per participant, and the final nonce is:

```text
R = Σ_i (D_i + rho_i E_i)
```

A malicious participant that submits last performs the following:

```text
T = Σ_honest (D_h + rho_h E_h)
E_m = 0
D_m = -T
```

Because `E_m` is infinity, `rho_m E_m` is also infinity, so the attacker’s contribution is exactly `D_m = -T`. [10](#0-9) 

The resulting group nonce is:

```text
R = T + (-T) = 0
```

`sign_share` passes `nonce_sums[0][0]` into `Hram::hram`, which calls `x(R)`; `x(R)` then executes `expect("point at infinity")` and panics. [11](#0-10) [5](#0-4) [6](#0-5)
