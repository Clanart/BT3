## Finding: `_cancelFromDest` can refund an order's escrow to the user after a solver has already legitimately filled it, with no check against `_filled[commitment]`

### Title
Missing `_filled` check in `_cancelFromDest` lets a legitimate fill be raced/overwritten by a refund, stranding the solver's delivered output - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_cancelFromDest` decides whether to require the order-creator's authorization using only `order.deadline >= _blockNumber()`. It never checks whether the order has already been filled (`_filled[commitment]`) before overwriting that slot and dispatching a `RefundEscrow` message back to the source chain. This mirrors the UNCX bug class exactly: the code implements one boundary condition (deadline check) but omits the second condition required for the stated invariant ("this path is only for orders that were never filled"), so an order that *was* filled can still be routed down the refund path.

### Finding Description
The doc-comment for `_cancelFromDest` states the intended invariant: [1](#0-0) 

But the implementation only gates on the deadline: [2](#0-1) 

There is no `if (_filled[commitment] != address(0)) revert AlreadyFilled();` guard. `_filled[commitment]` is the same slot that `_fillCrossChain` sets when a solver delivers outputs: [3](#0-2) 

Note also that `_fillCrossChain` never validates `order.deadline` against the current block before allowing a fill, so a solver can legitimately fill an order at or after the deadline block. Once filled, `_fillCrossChain` dispatches a `RedeemEscrow` POST to the source chain to pay the solver from escrow: [4](#0-3) 

`_cancelFromDest` independently dispatches a `RefundEscrow` POST for the same commitment/escrow to the same source chain, targeting the same `onAccept` withdrawal path: [5](#0-4) 

Both `RedeemEscrow` and `RefundEscrow` messages are independent ISMP POST requests with different commitments; Hyperbridge does not guarantee any delivery ordering between them. Whichever message lands first on the source chain's `_withdraw` wins and (presumably) clears the escrow accounting; the second is a no-op. Since `_cancelFromDest` performs no check that the order was already filled, an attacker (permissionless once `_blockNumber() > order.deadline`) — or even the order's own `user` before the deadline — can trigger a `RefundEscrow` dispatch for an order the solver has *already fulfilled* on-chain (outputs delivered to the beneficiary in `_fillCrossChain`). If that `RefundEscrow` message is delivered to the source chain before the solver's `RedeemEscrow` message, the escrow is paid back to `order.user` instead of the solver: the solver has already sent output tokens to the beneficiary and receives nothing back, while the user receives both the delivered outputs and the refunded input escrow.

### Impact Explanation
This is a wrong-beneficiary / fund-loss condition that fits the bounty's live categories directly: "stealing or loss of funds," "logic attacks," and "unauthorized transaction... transaction manipulation." A solver performing honest, permissionless fills loses the value of the tokens/ETH they already transferred to the beneficiary, with no reimbursement path, purely because of a race between two independently-delivered ISMP messages that the contract's own logic fails to prevent by not checking `_filled[commitment]` before allowing the refund path.

### Likelihood Explanation
No privileged actor, malicious relayer, or prover is required — the attacker only needs to call the permissionless `_cancelFromDest` after the deadline (or be `order.user` before the deadline) for a commitment that a solver has already filled, and get the resulting `RefundEscrow` request delivered before the solver's `RedeemEscrow` request. Because relayers are economically incentivized to deliver whichever message they see first/is most profitable, and `_fillCrossChain` does not itself block fills at/after the deadline, this race window is realistically reachable, especially for orders filled close to their deadline.

### Recommendation
Add an explicit `if (_filled[commitment] != address(0)) revert AlreadyFilled();` guard at the top of `_cancelFromDest` (and consider the analogous check in `_cancelFromSource`, in addition to its existing GET-based non-filled proof) before setting `_filled[commitment]` and dispatching the `RefundEscrow` message. Additionally, `_fillCrossChain` should reject fills once `_blockNumber() > order.deadline` so that "filled" and "cancelable" are mutually exclusive states, matching the doc-comment's stated invariant precisely (the same class of fix UNCX applied: making the code's condition match the documented proposition exactly rather than leaving a gap that lets the wrong branch execute).

### Proof of Concept
1. Solver calls `fill`/`_fillCrossChain` for `order` right before/at `order.deadline`, delivering `order.output` tokens to `beneficiary` and dispatching a `RedeemEscrow` POST toward `order.source` (per `evm/src/apps/intentsv2/ExtrinsicIntents.sol:137-171`).
2. Immediately after, once `_blockNumber() > order.deadline`, any address calls `_cancelFromDest(order, options, commitment)` — no authorization required per lines 240-243 — which sets `_filled[commitment] = order.user` and dispatches a `RefundEscrow` POST toward the same `order.source` (lines 245-259), without ever checking that `_filled[commitment]` was already set to the solver's address by step 1.
3. If the relayer network delivers the `RefundEscrow` message to the source chain's `onAccept`/`_withdraw` before the `RedeemEscrow` message, the escrowed input tokens are released back to `order.user`.
4. Net result: `order.user` receives both the solver-delivered `order.output` tokens (step 1) and their original escrowed `order.inputs` back (step 3); the solver, who paid out `order.output`, receives nothing from escrow.

Note: I could not locate the source-chain `_withdraw`/`_orders` accounting implementation in the indexed portion of the repo to confirm whether it has an independent single-use guard that would fully neutralize the double-payout after the first message lands; if it does not, the second (no-op) assumption above may not hold and the race could even produce a literal double payout rather than just wrong-beneficiary redirection. This should be verified by reading the full `_withdraw`/`_orders` implementation in `IntentsBase.sol`/`ExtrinsicIntents.sol` before remediation.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
