### Title
Live re-read of mutable asset decimals lets the fungible-token pallet mint/refund a different amount than was escrowed - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token` scales cross-chain amounts using `convert_to_erc20`/`convert_to_balance` with a `local_decimals` value that is *not* fixed at the time an amount is escrowed/burned. Instead, both `send()` and the later `on_accept`/`on_timeout` handlers independently call `<T::Assets as fungibles::metadata::Inspect>::decimals(asset_id)` to re-derive that value. If the underlying asset's decimals metadata changes between the outbound `send()` and the corresponding inbound settlement (accept or timeout refund), the two conversions use different scale factors on the *same* wire amount, producing a refunded/minted quantity that differs from what was actually escrowed or burned. This mirrors the SMAOracle bug class: a scaling parameter is applied inconsistently across two code paths that must stay in sync, and nothing pins the scale factor at commitment time.

### Finding Description
- On `send()` (`modules/pallets/hyper-fungible-token/src/lib.rs:254-295`), for non-native assets the pallet reads `decimals` live via `fungibles::metadata::Inspect::decimals(asset_id)` and encodes `erc20_amount = convert_to_erc20(amount, erc_decimals, decimals)` into the outbound `Message`, after burning/escrowing `amount` in local-asset units.
- On `on_accept` and `on_timeout` (`modules/pallets/hyper-fungible-token/src/module.rs:75-91`, `239-255`), the pallet again reads `decimals` live from the *same* `Inspect::decimals()` call, and converts the wire amount back with `convert_to_balance(wire_amount, erc_decimals, decimals)`.
- `convert_to_balance`/`convert_to_erc20` (`modules/pallets/hyper-fungible-token/src/impls.rs:43-59`) use `erc_decimals.saturating_sub(local_decimals)` as the scaling exponent — a difference computed fresh each call, not a value carried in the request.
- Nothing snapshots `local_decimals` (or the resulting scale factor) into the dispatched ISMP request/commitment. The only invariant enforced is at `register_token`/`update_token` time (`erc_decimals >= local_decimals`, `lib.rs:352-355`, `403-406`), which is checked once and never re-verified against the asset's *current* decimals at settlement time.
- `pallet-assets` (the typical `T::Assets` backend, per the pallet's own docs/config) allows the asset's owner/admin to call `set_metadata` and change `decimals` at any time after asset creation — this is an ordinary, permissionless (to the asset owner) operation, not a Hyperbridge governance or relayer/prover action.
- Consequence: if decimals are lowered between `send()` and settlement, `convert_to_balance` divides by a larger power of ten than was used to encode the amount, silently truncating the refund/mint to a smaller (possibly zero) value — user funds are burned/escrowed but never fully returned. If decimals are raised, the reverse conversion divides by a *smaller* power of ten than was used to multiply on send, inflating the minted/refunded amount beyond what was ever escrowed — draining the pallet's custodial account (`Self::pallet_account()`) of other users' escrowed native-asset balance, or minting non-native supply beyond backing.

### Impact Explanation
This breaks the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" invariant. Depending on the direction of the decimals change:
- Fund loss/lock for the sender (refund/received amount silently truncated, including to zero).
- Fund theft/inflation: an inflated refund or receipt can drain the escrow custody account backing other users' native-asset transfers, or mint non-native asset supply not backed by any burn — a direct loss-of-funds / unauthorized-mint scenario, which is explicitly in scope for the bounty (stealing/loss of funds, transaction manipulation).

### Likelihood Explanation
The trigger doesn't require compromising Hyperbridge's relayers, provers, or governance — it only requires that the underlying `pallet-assets` asset used for the bridged token has its decimals metadata mutable after registration, and that some legitimate delay exists between `send()` and settlement (timeout window, or normal relay latency for `on_accept`). Asset decimals are rarely changed post-creation in practice, and whether `set_metadata` is reachable by an ordinary (non-privileged) party depends on the specific `pallet-assets` configuration used by the integrating runtime (`ForceOrigin` vs. `Owner`-signed). This uncertainty is why I flag likelihood as conditional: it is a real code-level flaw (decimals are re-derived live rather than pinned at dispatch time) but its exploitability hinges on the deployed asset's admin/owner permission model, which I could not fully verify from this index alone.

### Recommendation
Snapshot the scale factor (or the `local_decimals` value) into the dispatched `Message`/request state at `send()` time (e.g., store it in `Precisions`-keyed pending-request storage, or include it in the ISMP request body), and use that stored value — not a fresh `Inspect::decimals()` read — when processing the matching `on_accept`/`on_timeout`. This guarantees the same scale factor is used for both legs of a given transfer regardless of any later metadata changes to the asset.

### Proof of Concept
1. Governance registers non-native asset `X` (local decimals = 6) for EVM chain `C` with `erc_decimals = 18` via `register_token` (passes `18 >= 6`).
2. User calls `send({asset_id: X, amount: 1000, destination: C, timeout: T})`. Pallet burns `1000` units of `X` from the user and encodes `erc20_amount = 1000 * 10^(18-6) = 1000e12` into the outbound message.
3. Before the message is delivered/times out, the asset's owner calls `pallet_assets::set_metadata(X, decimals=0)`.
4. Timeout `T` elapses; `on_timeout` fires. It re-reads `decimals = Inspect::decimals(X) = 0`, and computes `convert_to_balance(1000e12, 18, 0) = 1000e12 / 10^18 = 0`.
5. `TokenRefunded { beneficiary, amount: 0, dest: C }` is emitted — the user's `1000` units of `X` are burned with no refund, a total loss of funds, purely from a live decimals-metadata change with no relayer, prover, or Hyperbridge-admin involvement.
