### Title
`build_investigate_prompt` truncates diffs by raw byte position rather than risk, letting a padded/large file silently drop the introduced vulnerability from the review prompt - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_investigate_prompt` calls `cap_diff_for_prompt`, which truncates each file's diff content at a fixed byte offset (`DIFF_PER_FILE_BYTES` = 80000) and the overall diff at `DIFF_TOTAL_BYTES` (400000), keeping only the head of the content (or omitting whole files entirely once the total cap is hit) with no regard to which lines are the actual `+` (newly introduced) high-risk lines. [1](#0-0)  Because Claude Code itself generates the diffs that are fed into this pipeline (e.g., via large file writes, big dependency/lockfile-style additions, or content shaped by upstream repository/PR/issue text), a large enough file or commit can push the actual vulnerable `+` lines past the truncation boundary, causing them to never reach the agentic reviewer's investigate-stage prompt.

### Finding Description
`build_investigate_prompt(touched_paths, diff_files, context_note=...)` builds the Stage-1 investigate prompt by first calling `cap_diff_for_prompt(diff_files)`, which for each `(path, content)` pair: if `len(content) > DIFF_PER_FILE_BYTES` truncates to the first `DIFF_PER_FILE_BYTES` bytes and appends a truncation marker; and if the cumulative total exceeds `DIFF_TOTAL_BYTES`, either truncates the remainder of a file or replaces it entirely with `"[omitted by security-guidance: total diff byte cap reached]"`. [2](#0-1)  This is a pure head-first byte-position cut, not a risk-aware truncation — there is no logic that keeps `+` (added) lines, keeps flagged sink patterns, or otherwise prioritizes "dangerous" content over benign padding.

`build_investigate_prompt` then assembles the final prompt text directly from this capped output and sends it to the Stage-1 investigate model. [3](#0-2)  The identical pattern (`_cap_files_for_prompt`, byte-for-byte the same logic, re-exported from `review_api`) is used by both the single-shot `analyze_code_security` Stop-hook path and the `agentic_review` Stage-1 investigate path. [4](#0-3) [5](#0-4) 

There is a file-level prioritizer (`_prioritize_diff_files` in `gitutil.py`) that scores files by security-relevant path tokens and picks the top files when the number of *files* exceeds `MAX_DIFF_FILES`, but this only operates at the whole-file granularity before the diff text is capped — it does nothing to protect against truncation *within* a single oversized file's content, nor does it reorder content inside a file so that `+` lines are prioritized over unchanged context/padding. [6](#0-5) 

Exploit flow: An attacker who can influence what Claude Code writes into a file during a session (e.g., via a poisoned repo, PR/issue text, or other content Claude Code ingests and then edits/writes) causes a single file's diff to exceed 80,000 bytes, or the total diff across files to exceed 400,000 bytes, with the actual dangerous `+` lines positioned near the end of the content (e.g., after a large legitimately-looking blob, wall of comments, vendored-looking data, or many benign additions). Because `cap_diff_for_prompt`/`_cap_files_for_prompt` keeps only the head of the content, the dangerous lines are silently dropped (or the whole file is replaced with an "[omitted]" placeholder) before the diff ever reaches `AGENTIC_INVESTIGATE_SYSTEM`/the review model, so the review has no chance to flag it. This directly violates the target invariant: "truncation must not consistently drop the high-risk lines the user expects to be reviewed."

### Impact Explanation
This is a review-bypass condition, not direct RCE. Its impact is that dangerous code changes (SSRF, backdoors, secret exfiltration, command injection, etc.) that a user believes were security-reviewed by the Stop-hook or agentic commit-review layers can silently pass without being flagged, because the vulnerable content was truncated out of the prompt sent to the reviewer model. This matches the "Sensitive code, prompt, token, diff, or local file disclosure to an unintended local or remote sink" impact category only indirectly — the more precise impact is a false sense of security / missed detection for genuinely dangerous diffs, which the security-guidance plugin's entire purpose is to catch. There's no evidence of prompt-injection-via-diff-content overriding the review model's judgment in the code reviewed (the system/user prompts explicitly treat the diff as data and instruct the model on how to interpret `+`/`-`/context lines) — the exploit found is a structural truncation gap, not an injected-instruction bypass.

### Likelihood Explanation
Feasibility is moderate: it requires the attacker to get a single reviewable file's diff (or the whole diff of the change) to exceed the fixed byte caps (80 KB per file / 400 KB total) with the malicious `+` content positioned past the cutoff. Claude Code often writes large generated files (lockfiles, migrations, vendored assets, long config), so exceeding these caps organically is plausible; deliberately padding content earlier in a file to push a malicious line past 80,000 bytes is a straightforward, repeatable manipulation once an attacker can influence what Claude writes (e.g., through content it is instructed to embed or copy from an external/repo source). This is a design limitation present on every review invoked through `build_investigate_prompt`/`cap_diff_for_prompt`, not a one-off bug, so it is consistently reproducible.

### Recommendation
Make truncation risk-aware instead of purely positional:
- When truncating within a file, preserve/prioritize `+` (added) lines over unmarked context, and prioritize lines matching security-sink keywords/patterns (exec, eval, subprocess, pickle, requests/http, sql, etc.) over generic content, only truncating the lowest-priority (context/non-matching) lines first.
- When the total diff exceeds `DIFF_TOTAL_BYTES`, apply the same file-level risk scoring already implemented in `_prioritize_diff_files` (`gitutil.py`) to decide which files get truncated/omitted first, rather than truncating in original list order.
- Emit a clear, high-visibility metric/warning (not just `diff_truncated` bytes count) when truncation removes any `+` lines, so operators/users know large-file reviews may have blind spots.
- Consider raising or making the per-file cap adaptive (e.g., allow larger caps for high-risk-scored files) instead of a single global constant.

### Proof of Concept
Unit test plan against `plugins/security-guidance/hooks/review_api.py::build_investigate_prompt` / `cap_diff_for_prompt`:

1. Construct a synthetic diff file `(path="app/routes/api.py", content=<80,000 bytes of benign "+    # padding line\n" repeated> + "\n+    os.system(user_input)  # DANGEROUS SINK\n")` such that the dangerous line lands after byte offset `DIFF_PER_FILE_BYTES` (80000).
2. Call `build_investigate_prompt(["app/routes/api.py"], [that_file])`.
3. Assert: `"os.system(user_input)"` (the dangerous line) is **NOT** present in the returned prompt string — demonstrating the invariant violation (the high-risk line was dropped).
4. Repeat with multiple files whose combined content exceeds `DIFF_TOTAL_BYTES` (400000), placing the dangerous file last in the list; assert the dangerous file's content is entirely replaced by `"[omitted by security-guidance: total diff byte cap reached]"` in the resulting prompt.
5. As a regression/fix-validation test, after applying the recommended risk-aware truncation, re-run the same test and assert the dangerous `+` line IS retained in the prompt even when total/per-file byte caps are exceeded.

def cap_diff_for_prompt(
    files: list[tuple[str, str]],
) -> tuple[list[tuple[str, str]], int]:
    """Cap per-file and total diff bytes; return (capped_files, bytes_dropped).

    Truncation markers are written inside the content so the reviewer
    knows the file is incomplete.
    """
    out: list[tuple[str, str]] = []
    dropped = 0
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            dropped += len(content) - DIFF_PER_FILE_BYTES
            content = (
                content[:DIFF_PER_FILE_BYTES]
                + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"
            )
        room = DIFF_TOTAL_BYTES - total
        if room <= 0:
            dropped += len(content)
            out.append(
                (fp, "[omitted by security-guidance: total diff byte cap reached]")
            )
            continue
        if len(content) > room:
            dropped += len(content) - room
            content = (
                content[:room]
                + "\n... [truncated by security-guidance: total diff byte cap reached]"
            )
        total += len(content)
        out.append((fp, content))
    return out, dropped
```

def build_investigate_prompt(
    touched_paths: list[str],
    diff_files: list[tuple[str, str]],
    *,
    context_note: str = "",
) -> str:
    capped, _ = cap_diff_for_prompt(diff_files)
    diff_text = "\n\n".join(
        f"=== DIFF: {fp} ===\n{content}" for fp, content in capped
    )
    return (
        "Review this change for security vulnerabilities.\n\n"
        "Changed files (you may Read these and any other file in the repo):\n"
        + "\n".join(f"  - {p}" for p in touched_paths[:50])
        + context_note
        + "\n\nUnified diff (only + lines are new):\n\n"
        + diff_text
        + extensibility.guidance_block()
        + "\n\nInvestigate per the method in your instructions, then return "
        "the findings list."
    )
```

def _cap_files_for_prompt(files):

    review prompt. Returns the capped (path, content) list. Sets module-level

    the Stop hook can emit a `diff_truncated` metric. Truncation markers are
    written INSIDE the content so the reviewer knows the file is incomplete.
    """
    global _last_review_truncated_bytes
    _last_review_truncated_bytes = 0
    out = []
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            _last_review_truncated_bytes += len(content) - DIFF_PER_FILE_BYTES
            content = content[:DIFF_PER_FILE_BYTES] + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"

        if len(content) > room:
            _last_review_truncated_bytes += len(content) - room

def _prioritize_diff_files(diff_files, cap):
    """When `diff_files` exceeds `cap`, return the top-`cap` by security
    relevance plus the count dropped. Otherwise return (diff_files, 0).

    Score = (risk_tokens_in_path, not_low_priority, added_lines). The
    added-lines proxy is `content.count('\\n+')` which counts diff additions
    cheaply without re-parsing hunks. This is a heuristic, not a guarantee —
    the goal is to review the likely-dangerous subset of an over-cap diff
    instead of reviewing nothing. Diffs that exceed the cap are typically
    large multi-file scaffolds, and the cross-file source→sink vulnerabilities
    in them concentrate in a handful of api/client/route files.
    """
    if len(diff_files) <= cap:
        return diff_files, 0

    def _score(item):
        fp, content = item
        low = fp.lower()
        # Prepend "/" so leading-slash patterns in _LOW_PRIORITY_PATH_TOKENS
        # match top-level dirs (git diff paths are repo-root-relative, e.g.
        # `migrations/001.py` not `/migrations/001.py`). Same trick as
        # _is_reviewable_source.
        low_slashed = "/" + low
        risk = sum(1 for t in _SECURITY_RISK_PATH_TOKENS if t in low)
        low_prio = (
            fp.endswith(_LOW_PRIORITY_SUFFIXES)
            or any(t in low_slashed for t in _LOW_PRIORITY_PATH_TOKENS)
        )
        # added_lines: count('\n+') over-counts by including '+++' header and
        # any literal '+' at line start in context, but it's a consistent
        # ordinal across files in the same diff which is all we need.
        added = content.count("\n+")
        return (risk, not low_prio, added)

    ranked = sorted(diff_files, key=_score, reverse=True)
    return ranked[:cap], len(diff_files) - cap
