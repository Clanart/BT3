### Title
Unbounded Recursive RLP Decoding of Nested `AccountKeyRoleBased` Causes Stack-Consumption DoS - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively invokes `rlp.DecodeBytes` on each encoded sub-key without any depth limit, and the "no nested composite key" rule is enforced only *after* decoding completes (in `CheckInstallable`/`CheckUpdatable`), not during decoding. A transaction sender can craft an `AccountUpdate` (or `FeeDelegatedAccountUpdate`) transaction whose `Key` field contains a deeply self-nested `AccountKeyRoleBased` structure. Decoding such a transaction recurses through Go's native call stack once per nesting level, with no depth cap, leading to stack exhaustion and a node crash/panic — the same bug class as CVE-2007-3409 (unbounded recursive parsing of attacker-controlled, self-referential structured data causing stack consumption).

### Finding Description
`AccountKeySerializer.DecodeRLP` reads a `keyType` byte and then decodes the key body via `s.Decode(serializer.key)`: [1](#0-0) 

When `keyType` is `AccountKeyTypeRoleBased`, this dispatches to `AccountKeyRoleBased.DecodeRLP`, which decodes a `[][]byte` list and, for **every element**, calls `rlp.DecodeBytes` on a **fresh** `AccountKeySerializer` — recreating the exact same decode entry point recursively: [2](#0-1) 

Because each nested element is decoded via an independent `rlp.DecodeBytes` call (not tail-recursive, and not bounded by any stream-wide nesting counter in the `rlp` package), an attacker can nest `AccountKeyRoleBased` inside itself arbitrarily many times within the byte budget of a single transaction's `Key` field. Each level only costs a few bytes of RLP list/type overhead, so a transaction of modest size can encode thousands of nesting levels.

The only defense against nested composite keys is a *post-decode* structural check: [3](#0-2) 

This check runs only after `DecodeRLP` has already fully unwound — i.e., only after the recursive decode has already consumed stack space proportional to the nesting depth. The test suite even documents the intended invariant ("Nested RoleBasedKey is not allowed in Kaia") but only validates it at the account-update application layer, not at decode time: [4](#0-3) 

This decode path is reached whenever any component decodes an `AccountUpdate`/`FeeDelegatedAccountUpdate` transaction, e.g. `TxInternalDataAccountUpdate.DecodeRLP` → `fromSerializable` → `rlp.DecodeBytes(serialized.Key, serializer)`: [5](#0-4) 

which in turn is triggered by ordinary transaction ingestion (RPC `eth_sendRawTransaction`, p2p tx propagation, or block processing), long before any semantic AccountKey validation such as `CheckInstallable` is invoked.

### Impact Explanation
A single unprivileged transaction sender can submit (via public RPC or p2p) an `AccountUpdate`/`FeeDelegatedAccountUpdate` transaction with a maliciously nested `AccountKeyRoleBased` key. Decoding it triggers deep, uncontrolled Go-stack recursion, which can exhaust goroutine stack and crash/panic the node process that decodes it (any node's tx pool admission or block-import path). This is a network-reachable, unauthenticated denial-of-service against consensus/RPC nodes, consistent with High severity (availability impact) similar to CVE-2007-3409.

### Likelihood Explanation
Likelihood is high: constructing the malicious payload requires no special privileges, keys, or timing — only building a nested RLP structure and submitting it as a normal signed (or even syntactically-valid-but-unsigned, since the crash happens during decode before signature validation in some paths) transaction. No consensus participation, validator role, or node compromise is required.

### Recommendation
Enforce a maximum recursion/nesting depth for `AccountKeyRoleBased` (and any other composite `AccountKey` type) directly inside the RLP decode path (e.g., pass and decrement a depth counter through `AccountKeySerializer.DecodeRLP`/`AccountKeyRoleBased.DecodeRLP`), rejecting composite-within-composite structures at decode time rather than relying solely on the later `CheckInstallable`/`CheckUpdatable` checks. Alternatively, disallow decoding `AccountKeyTypeRoleBased` (or any composite type) as an element of `AccountKeyRoleBased` at the earliest possible point in `DecodeRLP`, before recursing.

### Proof of Concept
Conceptually:
1. Build innermost key `K0 = AccountKeyPublic` (valid single key).
2. Build `K1 = AccountKeyRoleBased{K0}`, RLP-encode via `AccountKeySerializer`.
3. Build `K2 = AccountKeyRoleBased{K1}` by embedding the RLP bytes of `K1` as the single element's encoded key bytes (bypassing the "no composite" rule since that rule is not checked during encode/decode, only at `CheckInstallable`).
4. Repeat step 3 N times (e.g., N = tens of thousands, bounded only by max tx size) to produce `KN`.
5. Set this `KN` bytes as `Key` field of an `AccountUpdate` transaction and submit it via `eth_sendRawTransaction` or p2p tx broadcast.
6. When any node calls `rlp.DecodeBytes` on the transaction (`TxInternalDataAccountUpdate.DecodeRLP` → `fromSerializable` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → repeat), the call stack grows by one frame set per nesting level, eventually exhausting the goroutine stack and crashing the process. func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
