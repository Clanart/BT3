### Title
Deterministic cached-preprocess reuse across `share` and `complete` leaks the FROST secret share — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` deterministically regenerates the same FROST nonces for a given `context` by reloading a cached `CachedPreprocess` seed from `CachedPreprocesses`. `DkgConfirmer::share` and `DkgConfirmer::complete` both funnel through `share_internal`, so the same nonce pair `(d, e)` is consumed twice for the same context — once when producing the share, and once when rebuilding the machine to complete. There is no freshness/deadline binding analogous to the missing `deadline` parameter in the external report: a stale or altered preprocess set / message can be fed back into a second `sign` under the identical cached nonces, which is exactly the preprocess-reuse condition documented as leaking the private key share.

### Finding Description
`preprocess_internal` stores a 32-byte `CachedPreprocess` keyed only by `context` (`CachedPreprocesses: (context) -> [u8; 32]`, lines 86–90), and on every call reloads that same seed, decrypts it, and calls `AlgorithmSignMachine::from_cache` (lines 123–147). `from_cache` routes to `seeded_preprocess`, which regenerates the nonces via `ChaCha20Rng::from_seed(*seed.0)` — so for a fixed context, the raw nonce scalars `(d, e)` are identical on every invocation (crypto/frost/src/sign.rs:121–144, 268–274).

`DkgConfirmer` pins its context to `(b"DkgConfirmer", self.attempt)` (line 275). `share()` calls `share_internal` once (line 309), and `complete()` calls `share_internal` *again* (line 322) before completing. Each call invokes `machine.sign(preprocesses, msg)` with the same cached seed. The produced share has the form `s = d + e·ρ + c·s̄` where `ρ` is the binding factor derived from the `rho_transcript` over `group_key`, `hash_msg(msg)`, and the `preprocesses` challenge (crypto/frost/src/sign.rs:362–371), and `s̄` is the Lagrange-weighted secret share.

Because the context — and therefore the seed — is not bound to the message or to the actual participant/preprocess set used, a second `sign` under the same context with a *different* set of participant-supplied preprocesses (untrusted bytes consumed via `read_preprocess`, lines 160–168) reuses `d` and `e` with a different `ρ` and challenge `c`. The FROST spec document itself states this is the failure mode: "the only way for this seeded RNG to fail is if a preprocess is loaded multiple times" (spec/cryptography/FROST.md:57–62), and `CachedPreprocess` documents that reuse "will enable third-party recovery of your private key share" (crypto/frost/src/sign.rs:83–92).

### Impact Explanation
Two shares published under the same `(d, e)` but different `(ρ, c)` give an observer equations `s1 − s2 = e·(ρ1 − ρ2) + (c1 − c2)·s̄`; across repeated share/complete cycles (or combined with the aggregate signature, whose `R` and `s` are public) the system becomes solvable for `s̄`, recovering the signer's secret key share. Recovery of a coordinator's share undermines the MuSig/FROST confirmation key used to attest validator-set keys (`set_keys_message`), i.e., compromise of the threshold signing root for the set.

### Likelihood Explanation
The reuse is structural, not attacker-dependent: `complete` unconditionally re-derives the machine and re-signs (`.expect("trying to complete a machine which failed to preprocess")`, line 323) under the same cached seed whenever it is invoked after `share`. Whether a given deployment path emits both shares depends on coordinator message ordering and which preprocess subset accompanies the shares in `complete`, which is supplied by external participants. I could not fully trace `handle.rs` call ordering in the available iterations, so the exact frequency of the second `sign` emitting an observable distinct share is uncertain — but the code performs the forbidden reuse on every `share`→`complete` pair, and the defense relies entirely on callers never varying the inputs between the two.

### Recommendation
Do not reload a `CachedPreprocess` more than once: delete (or mark consumed) `CachedPreprocesses[context]` in `preprocess_internal` before returning the machine, and cache the live `AlgorithmSignMachine`/`AlgorithmSignatureMachine` for `complete` instead of rebuilding it via `share_internal`. Alternatively, bind the context to a digest of the exact preprocess set and message and refuse to sign twice under the same seed.

### Proof of Concept
1. Coordinator runs `DkgConfirmer::preprocess` → `share(preprocesses_A, key_pair)`, emitting share `s1 = d + e·ρ_A + c_A·s̄` for context `("DkgConfirmer", attempt)`.
2. `complete(preprocesses_B, key_pair, shares)` is invoked with any `preprocesses_B ≠ preprocesses_A` (e.g., a different participant subset or mutated commitment bytes accepted by `read_preprocess`); `share_internal` rebuilds the machine from the same `CachedPreprocesses[("DkgConfirmer", attempt)]` seed, producing `s2 = d + e·ρ_B + c_B·s̄` with identical `d, e` (crypto/frost/src/sign.rs:127–133).
3. With `s1`, `s2`, the public `ρ` values recomputed from the transcripts, and public challenges `c_A, c_B`, the nonce scalars are no longer one-time — repeated or related observations yield `s̄`, the secret share, per the documented reuse-leak in spec/cryptography/FROST.md:51–55 and crypto/frost/src/sign.rs:209–219.
