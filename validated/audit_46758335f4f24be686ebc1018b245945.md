## Analysis

The Lido bug's core invariant break: **a reward/profit tied to an aggregate state transition (the oracle report) is attributed without verifying the claimant actually earned it via the underlying entitlement at the time of that transition** — i.e. the payout logic trusts a coarse batch-level signal instead of binding the reward to the specific action that produced it.

The closest local analog is in `pallet-consensus-incentives`, where the relayer reward for a **consensus proof delivery** is derived from a single signature check on the first message in a batch, but then paid out for **every** state-machine advance recorded in that batch's events — without confirming that the same relayer's proof caused each of those advances. [1](#0-0) 

### Title
Reward misattribution across batched state-machine updates in `pallet-consensus-incentives::on_executed` - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`FeeHandler::on_executed` recovers a single `relayer_account` from `messages[0]` (only if it is a `Message::Consensus`), then iterates over **all** `IsmpEvent::StateMachineUpdated` events produced by the entire executed batch and pays that one relayer the accumulated block-cost reward for every state machine whose commitment advanced in the batch — regardless of whether that relayer's own message actually caused each specific advance. [2](#0-1) 

### Finding Description
`process_message`/`calculate_reward` compute a reward as `(latest_height - baseline) * block_cost` per `state_machine_id`, and pay it from the treasury to whichever account was derived as `relayer_account`. [3](#0-2) 

The attribution step only inspects the **first** message of the batch and requires it to decode as `Message::Consensus` with a valid signature over that specific consensus proof: [4](#0-3) 

However, the loop that decides *which* state machines get rewarded is built purely from the `events` argument, collapsed per `state_machine_id` to its highest `latest_height`, with no cross-check that the corresponding `StateMachineUpdated` event was produced by `messages[0]` specifically: [5](#0-4) 

Because `on_executed` receives the full `messages`/`events` for the batch that pallet-ismp executed together (which can contain multiple consensus messages for different chains, or a mix of consensus and request/response messages that themselves trigger commitment advances), an attacker only needs to get their own valid, signed consensus message included as the **first** message of a batch that also contains other chains' `StateMachineUpdated` events. The pallet will then pay the attacker the full block-cost reward for every one of those other advances, even though the attacker supplied no proof for them.

### Impact Explanation
This is a wrong-beneficiary / logic-attack fund-loss issue: treasury funds intended to reward the relayer who actually delivered a specific chain's consensus proof are instead paid to whoever's message happens to occupy the first slot of a batch containing unrelated `StateMachineUpdated` events. Since the reward pool comes from the treasury account via `T::Currency::transfer`, this is a direct, unauthorized transfer of protocol funds to an unentitled party, and it also mints reputation tokens (`T::ReputationAsset::mint_into`) for work not performed. [6](#0-5) 

### Likelihood Explanation
Exploitability depends on how pallet-ismp groups messages into a single `on_executed` invocation (i.e., whether a single extrinsic/block execution can legitimately contain a consensus message for chain A plus independent `StateMachineUpdated` events for chains B/C not proven by that same message). I was not able to fully trace `pallet-ismp`'s message-batching/dispatch code in the time available to confirm the exact conditions under which unrelated events land in the same `on_executed` call — this is the main open uncertainty. If batches are strictly one-message-per-call in the live runtime, this path would not be exploitable; if pallet-ismp batches multiple heterogeneous messages per call (as the existing code comment about "sequential consensus updates for the same chain" suggests it anticipates), the misattribution is straightforward for any relayer to trigger by ordering their own message first.

### Recommendation
Bind each state-machine's reward to the specific message that produced its `StateMachineUpdated` event rather than to `messages[0]`: recover and verify a distinct signer per consensus message and only reward the state machine(s) whose commitment that specific message advanced, instead of collapsing the whole batch's events under one relayer identity.

### Proof of Concept
Conceptual reproduction (not verified against a running node given the scope of this analysis):
1. Attacker constructs/observes a batch where their own signed `Message::Consensus` for chain A is ordered first, and the same batch also contains legitimate proof-delivery messages (from other relayers) for chains B and C that advance those chains' commitments.
2. `on_executed` decodes `messages[0]` as the attacker's consensus message, recovers `relayer_account = attacker`.
3. The event-collapsing loop iterates `StateMachineUpdated` for chains A, B, and C, and calls `process_message` for each with `relayer_account = attacker`.
4. Treasury pays the attacker the block-cost reward for chains B and C in addition to A, and mints reputation tokens accordingly — despite the attacker never having supplied proofs for B or C. [7](#0-6)

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}

		// Return with actual weight information
		// We use Pays::No to indicate that someone (the message sender) doesn't pay for this
		// operation, though we're using this mechanism to reward relayers rather than charge fees
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
