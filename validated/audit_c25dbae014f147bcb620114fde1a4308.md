### Title
DoS via panic in `GeneratorPromotion::complete` when a participant submits a proof under a wrong/duplicate participant index - (File: crypto/dkg/promote/src/lib.rs)

### Summary
Analogous to CVE-2025-20033 (insufficient validation of an attacker-controlled message field leading to denial of service), `GeneratorPromotion::complete` validates only the *count* and *upper bound* of the participant-indexed proof map, then unconditionally unwraps a lookup for every expected participant. A malicious participant can craft the map so a required index is absent, causing a panic (`unwrap` on `None`) inside in-scope production code.

### Finding Description
`GeneratorPromotion::complete` (crypto/dkg/promote/src/lib.rs:120-167) performs two validations on the `proofs: &HashMap<Participant, GeneratorProof<C1>>` argument:

1. `proofs.len() == params.n() - 1` (lines 125-131)
2. every key `i` satisfies `u16::from(i) <= params.n()` (lines 132-136)

It then iterates `for i in 1 ..= params.n()` and does `let proof = proofs.get(&i).unwrap();` at line 146. Because a `HashMap` cannot contain duplicate keys, a set of `n - 1` entries can satisfy both checks while still omitting some required index `j ∈ 1..=n, j != params.i()`. For example, with `n = 3`, our index `i = 1`: a map keyed `{1, 2}` (attacker registers their proof under our own index `1` instead of `3`) has length 2 = n-1 and all keys ≤ n, yet `proofs.get(&Participant(3)).unwrap()` panics.

Equally, the attacker can key their proof to a *legitimate-but-wrong* participant index that collides with another participant's entry (the later insert overwrites), again yielding a missing index. The validation never checks that the key set equals `{1..=n} \ {params.i()}` — only cardinality and range, mirroring the Mattermost bug where a post type was checked superficially but not against the set of permitted values.

### Impact Explanation
Any caller performing key promotion across an untrusted set of participants (e.g., a coordinator collecting `GeneratorProof`s over an authenticated-but-not-trustless channel, where each proof arrives labeled by a participant index the sender chooses) will panic and abort. In a node runtime this kills the promotion task/process — a denial of service reachable by a single unprivileged protocol participant with a public input (their indexed proof message). No secret material is required; the panic occurs before any DLEq verification of the missing entry.

### Likelihood Explanation
The attack requires only that a participant's proof message be attributed to a participant index they can influence — the natural design of `complete` (a `HashMap<Participant, _>` keyed externally) makes this the default integration shape. The cost is one malformed/mislabeled message; no valid proof needs to be produced for the panicking index since the unwrap precedes verification. Severity is Medium: availability loss only, no key/share compromise (the panic prevents completing promotion, so no incorrect keys are accepted).

### Recommendation
Replace the `unwrap` at crypto/dkg/promote/src/lib.rs:146 with an explicit set-membership check: before iterating, verify `proofs.keys().copied().collect::<HashSet<_>>() == (1..=params.n()).map(Participant::new).collect::<Option<HashSet<_>>>().map(|s| s minus params.i())`, or inside the loop return `PromotionError::InvalidParticipant`/a new `MissingProof(Participant)` error instead of unwrapping. Concretely:

```rust
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let Some(proof) = proofs.get(&i) else {
    Err(PromotionError::InvalidParticipant { n: params.n(), participant: i })?
  };
  ...
}
```

Also reject `proofs` containing `params.i()` itself early, since a self-keyed entry both wastes a slot and masks the genuine omission.

### Proof of Concept
```rust
// n = 3, our participant index i = 1
let (promotion, our_proof) = GeneratorPromotion::<C1, C2>::promote(&mut rng, base_keys);

// Attacker (participant 3) submits their proof labeled with our index (1),
// and participant 2 submits correctly. Map: {1: attacker_proof, 2: honest_proof}
let mut proofs = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof); // mislabeled
proofs.insert(Participant::new(2).unwrap(), honest_proof);
// proofs.len() == n - 1 == 2, all keys <= n == 3: both checks pass

// PANIC at crypto/dkg/promote/src/lib.rs:146 on proofs.get(&Participant(3)).unwrap()
let _ = promotion.complete(&proofs);
```

Note: I verified this path statically; the panic site is `proofs.get(&i).unwrap()` at line 146, gated only by the length check at line 125 and the range check at line 133, neither of which enforces that the key set covers `1..=n \ {i}`.
