### Title
Gasless swap admission can be griefed via live-reserve price manipulation, permanently DOSing legitimate gasless (fee-delegated) swap transactions - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The gasless module's transaction-pool admission check (`checkBalanceForSwap`) validates a submitted gasless swap transaction against the DEX's live, spot exchange rate rather than any time-weighted or manipulation-resistant price. Because the underlying `GaslessSwapRouter.getAmountIn()`/`UniswapV2Router.getAmountIn()` compute the rate from the pool's current, instantaneous reserves, any unprivileged pool participant can swap in the same underlying DEX pair immediately before a victim's gasless swap tx is admitted, moving the exchange rate enough that the victim's previously-valid `amountIn`/`minAmountOut` pair now fails the "insufficient amountIn" check. This is directly analogous to the Arrakis `SimpleManager.rebalance()` DOS: a manipulable spot price (`slot0()`/live reserves) gates admission of a legitimate operation, so an attacker can grief that operation on demand.

### Finding Description
`GaslessModule.checkBalanceForSwap` computes the amount of token required for a swap by calling the `GaslessSwapRouter` contract's `getAmountIn(token, minAmountOut)`, which is described in the code comment as "Required token amountIn, given the **current exchange rate** and the declared minAmountOut": [1](#0-0) 

This function is invoked by `GetCheckBalance()`, which is the balance/admission-gate function used for gasless swap transactions: [2](#0-1) 

`GaslessSwapRouter.GetAmountIn` and the underlying `UniswapV2Router02.GetAmountIn(amountOut, reserveIn, reserveOut)` derive the required input amount purely from the DEX pair's live reserves (an AMM constant-product spot price), with no TWAP or other manipulation-resistant oracle: [3](#0-2) [4](#0-3) 

Because this reserve-based price is trivially moved by any account performing a swap on the same Uniswap-compatible pool used by `GaslessSwapRouter` for that token (the `DexAddress(token)`/`getDEXInfo(token)` pair queried by the router), an attacker can:
1. Observe a pending, otherwise-valid gasless approve+swap bundle (visible in the mempool as it propagates node-to-node before being admitted, or targeted the moment a user submits it).
2. Send a swap transaction against the same DEX pair to shift reserves and push the "current exchange rate" against the victim.
3. Cause the victim's `amountIn` (fixed in their already-signed transaction) to fall below the newly recomputed `requiredAmountIn`, triggering `"insufficient amountIn"` in `checkBalanceForSwap` and rejecting the gasless swap from the pool (or from the executable check used by `IsExecutable`/`VerifyExecutable`).

This mirrors the reported bug class exactly: a legitimate, unprivileged actor's protocol interaction (there: `rebalance()`; here: fee-delegated/gasless swap admission) is gated by a spot-price check that any other unprivileged party can manipulate at will, turning a functional gate into a griefing vector.

### Impact Explanation
An attacker can repeatedly and cheaply block admission of specific (or all) gasless swap transactions for a given token by nudging the DEX pool price whenever such a transaction is observed, denying users the "gasless" transaction feature they are relying on (Kaia's fee-delegation-like gasless mechanism, reachable by any public-RPC/mempool participant). This is a availability/DOS impact against the gasless module rather than a direct fund-theft, but it can be sustained indefinitely at low cost (a wash trade / self-swap on the pool) and can selectively target victims, undermining the gasless feature's usability guarantee.

### Likelihood Explanation
High likelihood: no privileged role is required — any address can submit a swap transaction against the referenced Uniswap-compatible DEX pool used by `GaslessSwapRouter`, and mempool transactions (or even the user's own broadcast pattern) reveal enough information (token, minAmountOut) to compute a price shift that flips the `insufficient amountIn` check. The check is re-evaluated at admission time (mempool/tx-pool gate) and potentially again before block inclusion, giving multiple manipulation windows per victim transaction.

### Recommendation
Do not gate gasless swap admission solely on the DEX's instantaneous/spot reserves. Consider:
- Allowing a configurable slippage/tolerance band when comparing `AmountIn` against `requiredAmountIn`, rather than a strict `>=` against a fully live-computed value.
- Using a manipulation-resistant price source (e.g., TWAP over several blocks) for the "current exchange rate" estimate used purely for admission sanity-checking, while still enforcing the on-chain `minAmountOut`/slippage protection inside the `GaslessSwapRouter` contract itself at execution time.
- Treating a failed `checkBalanceForSwap` amountIn check as a soft/retryable condition (re-queue) rather than an outright rejection, so transient price moves don't permanently drop legitimate gasless transactions.

### Proof of Concept
1. User `A` signs and broadcasts a valid `approveTx` + `swapTx` gasless bundle with `AmountIn` computed against the current pool reserves via `gsr.getAmountIn(token, minAmountOut)`, satisfying `checkBalanceForSwap`.
2. Attacker `B` observes the pending bundle (via mempool visibility or by front-running submission timing) and sends a transaction swapping through the same underlying Uniswap-compatible pair referenced by `GaslessSwapRouter.DexAddress(token)`, shifting reserves.
3. When node re-evaluates `A`'s swap tx for pool admission (`GetCheckBalance` → `checkBalanceForSwap`, calling `routerContract.GetAmountIn(nil, token, minAmountOut)` at [1](#0-0) ), the recomputed `requiredAmountIn` now exceeds `A`'s fixed `swapArgs.AmountIn`, and the check returns `"insufficient amountIn"`, rejecting `A`'s otherwise legitimate gasless transaction.
4. `B` can repeat this whenever `A` (or any user) retries, indefinitely denying gasless-swap service for that token pair at negligible cost.

Note: I was unable to fully trace whether this same `checkBalanceForSwap` path is also re-invoked at block-building/bundle-inclusion time in `kaiax/gasless/impl/builder.go` (only `IsExecutable`/`VerifyExecutable` and `GetLendTxGenerator` were inspected); confirming all call sites where this live-price check gates final inclusion would strengthen the impact assessment but the tx-pool admission gate alone is sufficient to establish the DOS.

func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}
