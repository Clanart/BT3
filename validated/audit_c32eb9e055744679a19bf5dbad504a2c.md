### Title
Unauthenticated JSON-RPC `send_tx` Endpoint Allows Any Network Peer to Cancel Queued Bridge Transactions and Drain the Fee-Paying Wallet - (`File: crates/clementine-tx-sender/src/jsonrpc/server.rs`)

---

### Summary

The `clementine-tx-sender` JSON-RPC server exposes `send_tx` (and `send_citrea_tx`) with no authentication layer of any kind. When the server is bound to `0.0.0.0` — an explicitly supported and documented production configuration — any network-reachable peer can call `send_tx` with attacker-controlled `cancel_txids`, `cancel_outpoints`, `activate_txids`, `activate_outpoints`, and `fee_paying_type` fields. This is a direct analog to the `change_oct_token` missing-ownership-check pattern: a privileged state-mutating action (queuing, cancelling, and activating bridge Bitcoin transactions) is exposed without any caller identity check.

---

### Finding Description

**Root cause — no auth in `start_jsonrpc_server`:**

`start_jsonrpc_server` builds a plain `jsonrpsee::Server` and registers `send_tx` directly on an `RpcModule`. There is no middleware, no IP allowlist enforced in code, no API key, and no mTLS — the function signature and body contain zero authentication logic. [1](#0-0) 

Compare this with the gRPC servers, which enforce `OnlyAggregatorAndSelf` mTLS on every method: [2](#0-1) 

**`0.0.0.0` is an explicitly allowed and documented production bind address:**

The config parser explicitly permits `bind = "0.0.0.0"` with no further restriction: [3](#0-2) 

The `TxSenderJsonRpcConfig` struct documents this as a valid production value: [4](#0-3) 

**Attacker-controlled parameters with bridge impact:**

The `send_tx` handler passes the full `InsertTryToSendParams` — including `cancel_outpoints`, `cancel_txids`, `activate_txids`, `activate_outpoints`, and `fee_paying_type` — directly to `TxSenderClient::insert_try_to_send` without any caller verification: [5](#0-4) 

The `cancel_txids` / `cancel_outpoints` fields cancel already-queued bridge transactions in the DB. The `activate_txids` / `activate_outpoints` fields prematurely activate transactions that are waiting for on-chain conditions. The `fee_paying_type` field (CPFP or RBF) causes the tx-sender to spend its own wallet UTXOs to fund or bump the submitted transaction.

---

### Impact Explanation

Three concrete bridge impacts, all reachable without any privileged key:

1. **Liveness break via cancellation of queued bridge transactions.** The tx-sender DB holds queued payout, challenge, reimbursement, and kickoff transactions. An attacker who knows (or can enumerate) their txids or outpoints can call `send_tx` with `cancel_txids` / `cancel_outpoints` pointing at those entries. If a challenge or reimbursement transaction is cancelled before its timelock expires, the operator loses its collateral or the bridge enters an unrecoverable state. This maps directly to "unauthorized state transition in payout, challenge, reimbursement flow that breaks bridge safety/liveness with material fund impact."

2. **Fee-wallet drain via CPFP/RBF spam.** An attacker submits many transactions with `fee_paying_type: CPFP` or `RBF`. The tx-sender uses its own wallet UTXOs to fund child transactions or RBF replacements. Exhausting the fee wallet prevents all legitimate bridge transactions from being fee-bumped, causing them to stall in the mempool and miss timelocks.

3. **Premature activation of bridge transactions.** `activate_txids` / `activate_outpoints` can trigger transactions that are intentionally held until a specific on-chain event. Premature broadcast of a payout or kickoff transaction at the wrong block height can violate script-path spending conditions and cause the transaction to be rejected or the operator to be slashed.

---

### Likelihood Explanation

- The attacker needs only network access to the tx-sender's JSON-RPC port.
- `TX_SENDER_JSONRPC_BIND=0.0.0.0` is explicitly supported, appears in docker-compose files, and is the natural choice for any containerized or cloud deployment where the tx-sender runs on a separate host from the bridge nodes.
- No privileged key, no internal network position beyond TCP reachability, and no prior knowledge of bridge state is required for the fee-drain attack. The cancellation attack requires knowing queued txids, which are observable on-chain or in mempool.
- The `run.sh` smoke-test script demonstrates the exact `send_tx` call format, lowering the bar for exploitation. [6](#0-5) 

---

### Recommendation

Add an authentication layer to `start_jsonrpc_server` before registering any method. Concrete options in order of preference:

1. **Shared-secret bearer token**: Generate a random token at startup, require it in every request via a custom HTTP header or as a leading parameter, and reject requests that omit or mismatch it.
2. **Bind-only to loopback**: Enforce `bind = "127.0.0.1"` unconditionally in code (remove the `0.0.0.0` branch) and document that callers must use a local Unix socket or SSH tunnel for remote access.
3. **mTLS on the JSON-RPC server**: Mirror the gRPC `OnlyAggregatorAndSelf` interceptor pattern — require a client certificate signed by the bridge CA before any method is dispatched.

Additionally, the `cancel_txids` / `cancel_outpoints` / `activate_txids` / `activate_outpoints` parameters should be treated as high-privilege operations and validated against a caller-identity claim even after authentication is added.

### Proof of Concept

Preconditions: tx-sender is running with `TX_SENDER_JSONRPC_BIND=0.0.0.0` and `TX_SENDER_JSONRPC_PORT=3030`. Attacker has TCP access to port 3030.

**Step 1 — Drain fee wallet via CPFP spam (no bridge knowledge required):**

```bash
# Craft a minimal syntactically-valid transaction (zero-value, unspendable)
RAW_TX_HEX="<any valid serialized tx hex>"

for i in $(seq 1 1000); do
  curl -s -H 'content-type: application/json' \
    --data "{\"jsonrpc\":\"2.0\",\"id\":$i,\"method\":\"send_tx\",\"params\":[{
      \"tx_metadata\": null,
      \"signed_tx_hex\": \"$RAW_TX_HEX\",
      \"fee_paying_type\": \"CPFP\",
      \"rbf_signing_info\": null,
      \"cancel_outpoints\": [],
      \"cancel_txids\": [],
      \"activate_txids\": [],
      \"activate_outpoints\": []
    }]}" \
    http://<target>:3030
done
# Result: tx-sender wallet UTXOs exhausted; legitimate bridge txs cannot be fee-bumped.
```

**Step 2 — Cancel a queued bridge transaction (txid observed in mempool):**

```bash
BRIDGE_TXID="<txid of queued payout/challenge tx observed in mempool>"

curl -s -H 'content-type: application/json' \
  --data "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"send_tx\",\"params\":[{
    \"tx_metadata\": null,
    \"signed_tx_hex\": \"$RAW_TX_HEX\",
    \"fee_paying_type\": \"NoFunding\",
    \"rbf_signing_info\": null,
    \"cancel_outpoints\": [],
    \"cancel_txids\": [\"$BRIDGE_TXID\"],
    \"activate_txids\": [],
    \"activate_outpoints\": []
  }]}" \
  http://<target>:3030
# Result: the queued bridge transaction is marked cancelled in the DB;
# it will not be rebroadcast or fee-bumped, missing its timelock window.
```

Expected outcome: the tx-sender processes both requests without any authentication error, confirming the missing ownership check.

pub async fn start_jsonrpc_server(
    tx_sender_client: TxSenderClient,
    bind_addr: SocketAddr,
) -> Result<TxSenderJsonRpcServer, BridgeError> {
    let server: Server = ServerBuilder::default()
        .max_request_body_size(MAX_JSONRPC_REQUEST_BODY_SIZE)
        .build(bind_addr)
        .await
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    let local_addr = server
        .local_addr()
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    let mut module = RpcModule::new(tx_sender_client.clone());
    module
        .register_async_method("send_tx", |params, client, _| async move {
            let req: InsertTryToSendParams = params.one().map_err(jsonrpc_err)?;

            let raw_tx = hex::decode(&req.signed_tx_hex).map_err(jsonrpc_err)?;
            let signed_tx: Transaction = consensus::deserialize(&raw_tx).map_err(jsonrpc_err)?;

            let mut dbtx = client.db.begin_transaction().await.map_err(jsonrpc_err)?;

            let try_to_send_id = client
                .insert_try_to_send(
                    &mut dbtx,
                    req.tx_metadata,
                    &signed_tx,
                    req.fee_paying_type,
                    req.rbf_signing_info,
                    &req.cancel_outpoints,
                    &req.cancel_txids,
                    &req.activate_txids,
                    &req.activate_outpoints,
                )
                .await
                .map_err(jsonrpc_err)?;

            client
                .db
                .commit_transaction(dbtx)
                .await
                .map_err(jsonrpc_err)?;

            Ok::<u32, ErrorObjectOwned>(try_to_send_id)
        })
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    #[allow(clippy::result_large_err)]
    fn call(&mut self, req: Request<()>) -> Result<Request<()>, Status> {
        match self {
            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
            Interceptors::Noop => Ok(req),
        }
    }
}

#[allow(clippy::result_large_err)]
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
