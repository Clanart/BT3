## Analysis

The report's broken invariant is: **an unauthenticated, attacker-controlled signal is used to decide which endpoint is "the trusted one," instead of a hard-coded or cryptographically-verified identifier.** In gravity bridge, that signal was "whatever address emitted the event." In GitHub Desktop's git-credential trampoline, the analogous signal is the `WWW-Authenticate` response header a git remote returns during authentication — Desktop treats its content as proof that the remote is a genuine GitHub/GHE host. [1](#0-0) 

### Title
Spoofable `WWW-Authenticate: realm="GitHub"` header lets an attacker-controlled git remote be misclassified as a trusted GitHub Enterprise host, enabling OAuth/PAT credential exfiltration - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's git-credential helper (`trampoline-credential-helper.ts`) decides whether an unknown HTTPS remote is a "GitHub" or "GitHub Enterprise" endpoint largely from response headers forwarded by git during authentication, rather than from a hard-coded allowlist or a certificate/API-based trust anchor. A malicious git server (a remote the user adds/fetches from, or a MITM/compromised proxy sitting in front of a real remote) can emit `WWW-Authenticate: Basic realm="GitHub"` to be classified as `'enterprise'`, which routes the flow into GitHub's own sign-in and internal-credential-storage machinery instead of the generic/external credential path.

### Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` classifies an endpoint using, in order: known dotcom/GHE domain checks, then an unauthenticated heuristic: [2](#0-1) 

```
// When Git attempts to authenticate with a host it captures any
// WWW-Authenticate headers and forwards them to the credential helper...
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } ...
```

This value comes straight from the target server's HTTP response — i.e., attacker-controlled content when the target is a malicious/compromised remote or an intercepting proxy. Only if this header-based check and the existing-account lookup both fail does the code fall back to a real network probe (`isGitHubHost`, which checks for the `x-github-request-id` header on a `/meta` HEAD request): [3](#0-2) 

That stronger check is entirely bypassed once the spoofed realm string matches, so the "hard-coded/verifiable identity" guard that exists elsewhere in the codebase never runs for this path.

Once `getEndpointKind` returns `'enterprise'` for an attacker's host, `getCredential` treats it as a first-party GitHub-family endpoint: [4](#0-3) 

If the user has no account bound to that (attacker) endpoint yet, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, initiating the GitHub Enterprise sign-in/PAT flow *targeted at the attacker's hostname* — because `endpoint` is derived from `getCredentialUrl(cred)`, which is the URL of the remote git is currently talking to, not a vetted value. If the user completes that flow (which they have strong reason to trust, since Desktop itself just told them "this looks like GitHub"), the resulting `Account`/token becomes bound to the attacker's endpoint. From then on, every future git operation against that remote has the trampoline inject the user's real OAuth/PAT credential into the HTTP `Authorization` header sent to the attacker's server — this is the credential/token exfiltration primitive; existing guards (`isDotCom`, `isGHE`, the `isGitHubHost` network probe) exist specifically to prevent this but are short-circuited by the spoofable header check.

### Impact Explanation
- Credential/token exfiltration: the user's GitHub.com/Enterprise OAuth token or PAT can be sent, by Desktop's own trampoline, to an attacker-controlled host once that host is misclassified as `'enterprise'`.
- Unauthorized OAuth/account binding: the sign-in flow the user is prompted through binds their account credential to an endpoint they did not intend to trust as "GitHub."
- Because the trigger is the response to a normal git authentication handshake, it requires no local access, no prior malware, and no leaked credentials — only that the user add or fetch/push to a repository whose remote (or an intercepting network/proxy) returns a crafted header, matching the described "attacker controls...a git remote/proxy response" impact class.

### Likelihood Explanation
Moderate: the attacker must control (or intercept traffic to) the git remote's HTTP responses, and the user must go through the sign-in prompt Desktop shows. Compared to the classic "hard-coded contract address" analog, this is weaker because it requires the header value to actually contain `realm="GitHub"` exactly and a subsequent user interaction (completing sign-in) — but no other guard blocks the misclassification once that header is present, and the real network-based verification (`isGitHubHost`) is never reached in that branch.

### Recommendation
- Never treat externally supplied `WWW-Authenticate` header content as sufficient proof of GitHub/Enterprise identity. Always require the authoritative check (`isGitHubHost`'s `/meta` probe verifying `x-github-request-id`, or an explicit user-configured/hard-coded enterprise endpoint list) before classifying a host as `'enterprise'` or `'github.com'`.
- At minimum, treat the header as a *hint* to skip other cheaper checks, but still require the network probe (or existing account match) before granting `'enterprise'`/`'github.com'` classification, especially before invoking `ui.promptForGitHubSignIn`.

### Proof of Concept
1. Attacker sets up an HTTPS git server (or MITM proxy in front of one) at `https://evil.example.com/owner/repo.git`.
2. Victim adds/clones/fetches this remote in GitHub Desktop.
3. Git attempts authentication; the attacker's server responds `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this as a `wwwauth[...]` field to Desktop's trampoline credential helper (`createCredentialHelperTrampolineHandler` → `getCredential` → `getEndpointKind`), matching the `realm="GitHub"` branch at `app/src/lib/trampoline/trampoline-credential-helper.ts:159-160` and returning `'enterprise'` without ever calling `isGitHubHost`.
5. Since no account exists for `evil.example.com`, `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com')`, prompting the victim to "sign in" to what Desktop presents as a GitHub Enterprise instance.
6. If the victim completes sign-in (OAuth or PAT), the resulting account/token is now associated with `evil.example.com`; subsequent git operations against that remote cause Desktop's trampoline to send the victim's real token to the attacker's server in the `Authorization` header.

Note: I was unable to fully trace `findGitHubTrampolineAccount`/`getCredentialUrl` (in `app/src/lib/trampoline/find-account.ts` and `app/src/lib/trampoline/trampoline-environment.ts`) due to the tool budget running out before I could open those files, so the exact matching semantics for already-bound accounts (whether it's exact-endpoint or hostname-based) are not fully confirmed from source — this affects only how quickly an *existing* enterprise account could be reused against a spoofed host, not the core misclassification bug described above, which is confirmed directly in `trampoline-credential-helper.ts`.

```typescript
const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}
```
