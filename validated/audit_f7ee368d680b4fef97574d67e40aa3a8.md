## Title
App Proxy Signature Verification Accepts Replayed Requests With No Timestamp/Nonce Freshness Check - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#verify_proxy_request` treats a valid HMAC over the app proxy query string as sufficient proof of authenticity, but it never checks that the `timestamp` parameter embedded in that signed payload is fresh. Once a signed app-proxy query string is observed by anyone, it remains a valid, accepted "proof" forever and can be resubmitted at will — the same root-cause bug class as the `ResourceLockValidator` issue, where a signature/proof is verified but never invalidated or bound to a single use.

### Finding Description
`query_string_valid?` recomputes the HMAC over all query parameters except `signature` and compares it to the supplied `signature` using `ActiveSupport::SecurityUtils.secure_compare`: [1](#0-0) 

The `timestamp` parameter is part of the signed payload (used only as signing material), but the code never reads it back out to enforce an expiry window. There is no nonce store, no "used signature" tracking, and no comparison of `timestamp` against `Time.now`. As a result, `verify_proxy_request` (the `before_action` gatekeeper for any controller including this concern) will accept the exact same query string — including `signature` — indefinitely: [2](#0-1) 

This mirrors the `ResourceLockValidator.validateUserOp()` bug: a cryptographically valid proof is verified correctly at the byte level, but the validator has no mechanism to consume/invalidate the proof after first use, so it can be replayed by anyone who captures it.

The App Proxy request path is externally reachable: Shopify forwards storefront visitor traffic (including anonymous/unrelated-shopper requests) to the app's App Proxy endpoint with a signed query string that can include sensitive context such as `logged_in_customer_id`, `shop`, and `path_prefix`, per the documented usage pattern: [3](#0-2) 

### Impact Explanation
Because the signature is never invalidated after time passes or after first use, any query string once observed (e.g., via browser history, shared/public terminals, proxy/CDN access logs, Referer leakage, or a man-in-the-middle on a non-TLS hop) can be replayed by an attacker at an arbitrary later time and will still pass `verify_proxy_request`. If the app relies on `logged_in_customer_id` (or any other proxied parameter) from this signed request to make authorization decisions, an attacker can replay an old signed request to have the app treat the request as if it still originated, at the time of replay, from that logged-in customer/shop context — a cross-user/cross-session impersonation via an accepted forged (replayed) signed request. This is a direct instance of "accepted forged signed request" that the validation rules call out as in-scope.

### Likelihood Explanation
Exploitation only requires capturing one previously valid, signed app-proxy query string (no privileged access, no secret knowledge, and no cryptographic break required) and replaying it via a normal HTTP GET/POST to the app-proxy-mounted controller. Any controller that includes `ShopifyApp::AppProxyVerification` — including the gem's own generated `AppProxyController` template — inherits this gap. [4](#0-3) 

### Recommendation
- Extract and parse the `timestamp` query parameter in `query_string_valid?`/`verify_proxy_request` and reject requests where `Time.now.to_i - timestamp.to_i` exceeds a small allowed skew (e.g. a few minutes), mirroring the recommendation from the referenced report to add freshness/consumption checks to signature-based proofs.
- Optionally, maintain a short-lived cache of recently seen `(signature)` or `(shop, timestamp, path_prefix)` tuples and reject duplicates within the freshness window to explicitly prevent single-use signature reuse.

### Proof of Concept
1. A storefront visitor triggers a request that Shopify forwards to the app's App Proxy endpoint, e.g. `GET /app_proxy/basic?shop=some-shop.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&logged_in_customer_id=42&signature=<valid-hmac>`.
2. An attacker (e.g., someone with access to server logs, shared browser history, or a captured network request) records this full URL, including the valid `signature`.
3. At any later time, the attacker replays the identical URL directly to the app.
4. `verify_proxy_request` → `query_string_valid?` recomputes the HMAC over the same parameters and it still matches, per [5](#0-4)  — the request is accepted as if it were a fresh, legitimate proxy call from Shopify at replay time, even though the underlying customer session/context may have long since ended.

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

## Verify HTTP requests sent via an app proxy

See [`ShopifyApp::AppProxyVerification`](/lib/shopify_app/controller_concerns/app_proxy_verification.rb).

The engine provides a mixin for verifying incoming HTTP requests sent via an App Proxy. Any controller that `include`s `ShopifyApp::AppProxyVerification` will verify that each request has a valid `signature` query parameter that is calculated using the other query parameters and the app's shared secret.

### Recommended usage of `ShopifyApp::AppProxyVerification`

The App Proxy Controller Generator automatically adds the mixin to the generated app_proxy_controller.rb
Additional controllers for resources within the App_Proxy namespace, will need to include the mixin like so:

```ruby
# app/controllers/app_proxy/reviews_controller.rb
class ReviewsController < ApplicationController
  include ShopifyApp::AppProxyVerification
  # ...
end
```
```
