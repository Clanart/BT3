## Title
Symlink-based path traversal in file context-menu actions bypasses repository boundary - (File: `app/src/lib/app-shell.ts`, `app/src/ui/lib/open-file.ts`)

### Summary
The reported Hyperdrive bug is a case where a downstream safety check (`slt` under/overflow detection) is silently defeated because the code assumes an invariant ("the subtraction result can't be smaller than the input unless it truly underflowed") that a crafted input breaks. The GitHub Desktop analog is structurally the same: code that resolves a repository-relative file path (`Path.join(repository.path, path)`) assumes the resulting path always stays inside the repository, but this invariant is not enforced for symlinks, unlike the equivalent flow that already guards against exactly this in `app/src/ui/dispatcher/dispatcher.ts`.

### Finding Description
`revealInFileManager` builds an absolute path with plain string joining and hands it straight to the OS shell: [1](#0-0) 

`openFile` does the same for "Open with Default Program": [2](#0-1) 

Both are invoked with `file.path` values that originate from `git status`/diff parsing of a repository's working tree — i.e., attacker-controlled content when the repository was cloned or fetched from a remote (or opened from a PR the attacker authored), for example in the Changes list, History view, and PR file list: [3](#0-2) [4](#0-3) 

Git places no restriction on the *target* of a symlink blob (mode `120000`) — only on tree-entry *names* (e.g. `..` is rejected). An attacker can therefore commit a symlink such as `evil-link -> ../../../../.ssh/id_rsa` (or an absolute path) into a repository. When the victim clones/fetches that repository and the symlink is materialized on disk (default on macOS/Linux, and on Windows when symlink support is enabled), `file.path` for that entry is simply `"evil-link"` — a value that passes every existing length/absolute-path check because it truly is a relative, repo-scoped path.

`Path.join(repository.path, 'evil-link')` therefore correctly produces a path *inside* the repository, so the naive containment assumption (“joined path == inside repo”) holds at the string level, but the filesystem/OS shell (`shell.showItemInFolder`, `shell.openExternal('file://...')`) resolves the symlink and operates on whatever the symlink actually points to, which can be arbitrary locations on disk. This is exactly the "check passes on the wrong representation of the value" pattern from the report: the safety property (staying within the repo) is verified against the pre-resolution string, not the post-resolution (real) path.

The codebase demonstrates that this exact class of attack is known and has a fix pattern (`resolveWithin`), which explicitly resolves symlinks via `realpath` and rejects results outside root: [5](#0-4) 

and is used to guard the deep-link "open file" flow: [6](#0-5) 

There is even a unit test proving `resolveWithin` is symlink-aware: [7](#0-6) 

However, `revealInFileManager`/`openFile` (used by the Changes list, History, PR files list, and conflict-resolution menus) never route through `resolveWithin` — they only perform a plain `Path.join`/`pathExists` check, which does not defend against symlink escape.

### Impact Explanation
An attacker who controls a cloned/fetched repository (or a PR the victim opens in Desktop) can place a symlink pointing at a sensitive file or executable outside the repository. When the victim uses ordinary, expected UI actions ("Reveal in Finder/Explorer" or "Open with Default Program"/"Open in editor" from the context menu on that entry), Desktop will reveal or open the external target instead of anything inside the repo. Depending on the target this can disclose the existence/contents of credential files (e.g., SSH keys, `.netrc`, `.aws/credentials`) in the file manager or default viewer, or, if the symlink targets an executable/script, cause it to be launched via `shell.openExternal`. This matches the impact categories of file read outside the repo and, in the executable case, code execution.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to interact with a context-menu item for the specific crafted file (a normal, expected action when reviewing changes or a PR), but no other unusual steps, elevated privileges, or pre-existing compromise are needed. Git allows committing arbitrary symlink targets, and Desktop already recognizes this exact risk elsewhere (`resolveWithin`'s symlink test, and its use in the deep-link handler), indicating the missing guard here is an inconsistency rather than a defense-in-depth gap.

### Recommendation
Route `revealInFileManager` and `openFile`'s callers through `resolveWithin` (or an equivalent `realpath`-based containment check) before invoking `shell.showItemInFolder`/`shell.openExternal`/`shell.openPath`, rejecting any resolved path that escapes `repository.path`, exactly as already done in `openRepositoryFromUrl`. Add regression tests analogous to `path-test.ts`'s symlink cases, but exercised through `revealInFileManager`/`openFile` specifically.

### Proof of Concept
1. Attacker creates a repository containing a symlink entry `steal -> ../../../../../../Users/victim/.ssh/id_rsa` (or an absolute path) and pushes/publishes it, or opens a PR containing this file.
2. Victim clones/fetches the repository (or opens the PR) in GitHub Desktop; the symlink is checked out as-is in the working directory.
3. Victim opens the Changes tab, History tab, or "Files changed" view for the PR, right-clicks the `steal` entry, and selects "Reveal in Finder/Explorer" or "Open with Default Program".
4. `revealInFileManager`/`openFile` compute `Path.join(repository.path, 'steal')`, which the OS resolves through the symlink to the victim's real SSH key (or other target) outside the repository, revealing or opening it — with no `resolveWithin`/`realpath` check to stop it, unlike the equivalent deep-link code path in `dispatcher.ts`.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
