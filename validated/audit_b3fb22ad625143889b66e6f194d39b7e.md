### Title
Excess native `msg.value` sent to `EvmHost.dispatch`/`fundRequest` is silently captured by the host instead of refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` accept native token payment and swap it for `feeToken` via the configured Uniswap V2 router using `swapETHForExactTokens{value: msg.value}(...)`. This is the local analog of the reported bug class: an inner call is made with a forwarded value, but the *return path* of unused value is not forwarded back to the original caller — it is captured by `EvmHost` itself.

### Finding Description
In `EvmHost.sol`, the outgoing dispatch functions swap the full `msg.value` into the fee token: [1](#0-0) [2](#0-1) [3](#0-2) 

Each of these calls `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(exactFeeAmount, path, address(this), block.timestamp)`. A standard `swapETHForExactTokens` implementation only consumes `amounts[0] <= msg.value` (the exact amount needed to buy `exactFeeAmount` of the fee token) and refunds any dust ETH via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])`. Because `EvmHost` itself is the caller of the router (it supplied `{value: msg.value}` from its own context), that refund's `msg.sender` is `EvmHost`, not the original dispatching account (`_msgSender()`/user). The refunded dust ETH therefore lands in `EvmHost`'s own balance rather than being sent back to the user who originally overpaid.

None of the three functions checks the swap's actual cost against `msg.value` or refunds any leftover to `_msgSender()`. The only way this stranded ETH (now converted, or the ETH itself if the wrapper doesn't even swap - see `GnosisUniswapV2Wrapper.swapETHForExactTokens`, which deposits *all* of `msg.value`, not just the exact amount) can move again is via the privileged, governance-only `IHostManager.withdraw` path: [4](#0-3) 

So any ordinary, unprivileged user who calls `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest` with `msg.value` even slightly larger than the exact amount needed to purchase `post.fee`/`get.fee`/`amount` worth of `feeToken` has that excess redirected to protocol-owned funds, recoverable only by the `hostManager` governance module — never by the user.

### Impact Explanation
This causes an unauthorized loss of user funds: value that should belong to (or be refundable to) the dispatching account is instead absorbed into the host's protocol balance, which can only be withdrawn by governance to an arbitrary beneficiary. This satisfies the bounty's "loss of funds" / "wrong beneficiary or amount" criteria — the excess native payment moves to the wrong party (protocol governance) instead of remaining with, or being refunded to, the rightful payer.

### Likelihood Explanation
Any application or user integrating directly with `IDispatcher.dispatch{value: ...}` (rather than the exact-amount helper flows) is exposed whenever they send more native value than the router's exact-input requirement — e.g., due to price movement between quoting and execution, rounding, or simply providing a safety buffer as commonly done in EVM dispatch flows (`quote()` results are inherently stale by the time the transaction executes, and no slippage/refund mechanism exists here). This requires no malicious peer, relayer, or governance actor — only routine overpayment by a legitimate user.

### Recommendation
After the router swap in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, compare `msg.value` to the router's reported `amounts[0]` (or check `address(this).balance` delta) and refund the difference to `_msgSender()` via a low-level call, mirroring the refund pattern already used elsewhere in the codebase (e.g., `ExtrinsicIntents.sol` refunding unspent native tokens to the solver, and `UniV3UniswapV2Wrapper.sol`'s explicit refund logic).

### Proof of Concept
1. Configure `EvmHost` with any standard `UniswapV2Router02`-compatible `uniswapV2` wrapper (as used in `dispatch`).
2. Call `dispatch(DispatchPost)` with `post.fee = X` and `msg.value = X + Y` (Y > 0, e.g., a small safety buffer/slippage margin).
3. `swapETHForExactTokens{value: X+Y}(X, path, address(this), ...)` executes: it spends only the ETH needed to buy `X` fee tokens and refunds `Y` ETH — but to `EvmHost` (the router's caller), not to the original `_msgSender()`.
4. Inspect `EvmHost`'s native balance: it now holds `Y` ETH that is not accounted for by any user-facing accounting structure (`_requestCommitments` only tracks the fee-token amount `post.fee`).
5. The only path to move that `Y` ETH is `IHostManager.withdraw`, callable exclusively by the governance-controlled `hostManager`, confirming the original payer permanently lost the excess `Y` to protocol funds with no recovery path of their own.

        if (msg.value > 0) {
