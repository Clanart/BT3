Confirmed: the `HTTP_X_SHOPIFY_SHOP_DOMAIN` header used by `ShopifyApp::WebhookVerification#shop_domain` and passed to `ShopifyAPI::Webhooks::Request` in `WebhooksController#receive` is not part of the HMAC digest, which is computed only over `request.raw_post` in `PayloadVerification#hmac_valid?`. This is the concrete analog to the SGX report's pattern: a state-changing operation whose determination of "which entity/context this affects" relies on caller-supplied data that isn't covered by the message-integrity check, allowing an unauthorized party to redirect the effect to a victim's context.

### Title
Webhook shop context is forgeable because the HMAC only covers the request body, not the `X-Shopify-Shop-Domain` header - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates the webhook exclusively via `hmac_valid?(request.raw_post)`, which computes an HMAC over the raw POST body using the app's shared secret. The shop identity used to route and process the webhook, however, is read directly and unauthenticated from the `X-Shopify-Shop-Domain` request header in `WebhookVerification#shop_domain` and is forwarded verbatim into `ShopifyAPI::Webhooks::Request.new(headers: request.headers.to_h)` in `WebhooksController#receive`. Because the app secret is shared across all shops that install the same app, any party that can obtain one genuine, HMAC-signed webhook body for the app (e.g., because Shopify legitimately delivered a webhook to them for their own installed shop) can replay that exact body to the same endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. The HMAC check still passes because the header is not part of the signed data, but the downstream job is dispatched under the attacker-chosen shop domain.

### Finding Description [1](#0-0) 
`hmac_valid?` signs and compares only `data` (the raw request body) against the app secret(s). [2](#0-1) 
`verify_request` calls `hmac_valid?(request.raw_post)` — the body only — while `shop_domain` reads `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]` directly, with no cryptographic binding between the two. [3](#0-2) 
`WebhooksController#receive` forwards `request.headers.to_h` (including the unverified shop-domain header) into `ShopifyAPI::Webhooks::Request`, which is what ultimately determines the `shop:` value dispatched to the generated job (see the job templates that call `Shop.find_by(shopify_domain: shop_domain)`), for example: [4](#0-3) 

Because the HMAC secret is identical for every shop of a given app installation, a genuine webhook body delivered to shop A's endpoint carries a valid signature that is equally valid when replayed with a different shop-domain header — the signature says "this body is authentically from Shopify for this app," not "this body pertains to shop X." The controller conflates these two properties.

### Impact Explanation
This lets an unrelated merchant who has legitimately installed the app on their own shop (and therefore can capture one of their own genuine webhook deliveries and its valid HMAC) craft a forged request that the app will process as though it originated from a different, victim shop. Depending on the webhook topic and job logic (e.g., `shop/redact`, `customers/redact`, `app/uninstalled`), this can trigger cross-shop data mutation, deletion of a victim shop's record (`shop.destroy` in `add_app_uninstalled_job/templates/app_uninstalled_job.rb.tt`), or injection of attacker-controlled webhook payload content attributed to a victim shop — a cross-shop access/integrity violation reachable from an unrelated-merchant HTTP request with no further secrets required beyond having the app installed once.

### Likelihood Explanation
Moderate-to-high: the attacker needs only to have (or have had) the app installed on any shop so that Shopify delivers them at least one genuine, HMAC-signed webhook of the target topic; no leaked global secret or code-level access is required. The endpoint is public, unauthenticated aside from the HMAC check, and the header substitution is a single trivial HTTP replay.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or any header) as the authoritative shop identity for a webhook unless it is cryptographically bound to the signed payload. Where possible, derive/validate the shop identity from the signed body content itself (most Shopify webhook payloads include shop-identifying fields) or maintain a per-shop webhook secret/registration correlation instead of relying on the shared app secret plus an unauthenticated header, and reject webhooks whose header-declared shop does not match an independently verifiable value.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; wait for Shopify to deliver a real webhook (e.g., `app/uninstalled`) to `POST /webhooks/app_uninstalled`, capturing the exact raw body and its valid `X-Shopify-Hmac-Sha256` value.
2. Replay the identical body and HMAC header to the same endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)` — using only the body — and passes, since the body/signature pair is genuinely valid for the shared app secret.
4. `WebhooksController#receive` forwards headers into `ShopifyAPI::Webhooks::Request`, and the generated `AppUninstalledJob#perform` looks up `Shop.find_by(shopify_domain: "victim.myshopify.com")` and calls `shop.destroy`, deleting the victim's shop record despite the attacker never having installed on that shop.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
