### Title
Blame proof revealing the ECDH shared key is emitted before the message's proof-of-possession is verified, letting an attacker decrypt an honest participant's secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` returns an `EncryptionKeyProof` (which publicly reveals the ECDH shared key `bX` for a message) via the early `?` return on share-deserialization failure, before the batched Schnorr proof-of-possession (`pop`) on `msg.key` is ever verified. This reintroduces exactly the attack the `pop` field was added to prevent: Eve reuses Alice's per-message key `X` in a forged message to Bob; Bob's decrypt produces garbage, and the blame proof he publishes reveals `bX`, letting everyone decrypt Alice's genuine message to Bob.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `EncryptedMessage` carries a `pop: SchnorrSignature<C>` whose sole documented purpose is to stop an attacker from claiming another sender's encryption key, because issuing a blame proof reveals the shared ECDH key and would decrypt the honest sender's message as a side effect [1](#0-0) .

`Encryption::decrypt` unconditionally computes the ECDH shared key and builds an `EncryptionKeyProof` containing it, while only *queuing* the `pop` into the batch verifier [2](#0-1) .

In `KeyMachine::calculate_share`, the `pop`/`share` batch is only verified at line 493, but a malformed (non-canonical) share scalar triggers `PedPoPError::InvalidShare { blame: Some(blame) }` through an early `?` at lines 480–482, returning the blame proof with `pop` never checked [3](#0-2) .

The processor then serializes that blame into `ProcessorMessage::InvalidShare` [4](#0-3)  and publishes it; `VerifyBlame`/`decrypt_with_proof` would detect `InvalidSignature` later, but the shared key is already public [5](#0-4) .

### Impact Explanation
An attacker Eve copies `msg.key = X` from an honest Alice→Bob share message (public on the wire), attaches a self-made (invalid) `pop`, and picks an arbitrary ciphertext. Bob computes `ecdh(b, X)` — identical to the key protecting Alice's real message — decrypts to non-canonical bytes, and the early return attaches the `EncryptionKeyProof` revealing `bX`. Once broadcast, anyone applies `cipher(context, bX)` to Alice's original ciphertext and recovers her secret share to Bob. This is a confidentiality break of DKG secret shares: shares meant only for their recipient become publicly known, weakening the threshold key (an attacker collecting leaked shares needs fewer honest shares to reconstruct the group secret). The comment at `encryption.rs:84-90` explicitly classifies this as "a massive side effect which could break some protocols."

### Likelihood Explanation
Requires only an unprivileged DKG participant/observer who sees the encrypted share messages (they are routed publicly to the coordinator) and can submit a crafted `EncryptedMessage` to a victim's `calculate_share`. No collusion or key compromise needed. Likelihood is moderate: the attacker must target a participant before it completes the DKG, and the payoff is one leaked share per targeted recipient rather than immediate full key recovery.

### Recommendation
Do not attach the `EncryptionKeyProof` until the `pop` has been verified. Concretely: run `batch.verify_with_vartime_blame()` (or at least verify `msg.pop`) *before* the `from_repr` check, so the non-canonical-scalar path only emits blame for messages whose proof-of-possession passed. Alternatively, verify `pop` eagerly inside `Encryption::decrypt` before producing `EncryptionKeyProof`, returning `blame: None` on failure — matching the existing `BatchId::Decryption` path which correctly maps PoP failures to `None`.
