Based on my investigation, I found a genuine analog of this exact bug class in the Kaia transaction pool's slot-admission logic.

### Title
Stale pool-capacity check-then-act allows TxPool slot limit to be exceeded under concurrent submissions - ([File: blockchain/tx_pool.go])

### Summary
`AddLocal` and `checkAndAddTxs` (used by `AddRemote`/`AddRemotes`/batch admission) read the current pool size and compute remaining capacity *before* acquiring the pool's internal lock and performing the actual insertion. This is the same class of bug as the reported `findActivePromoByRefCode`/`createUserPromo` issue: a capacity/slot check is separated in time from the mutation that consumes the slot, and any unprivileged transaction sender submitting transactions concurrently (via public RPC, batches, or the gossip layer) can race that gap.

### Finding Description
`AddLocal` checks the pool size against the configured cap without holding `pool.mu`: [1](#0-0) 

Similarly, `checkAndAddTxs` (invoked from `AddRemotes`, and transitively from `handleTxMsg`/`throttleLoop` on every incoming remote-tx batch) computes `poolCapacity` from `pool.all.Count()` and slices the incoming batch to fit, again outside of the pool's lock: [2](#0-1) 

Only later, inside `pool.add()` (called via `addTx`/`addTxs`, which do take `pool.mu`), is the pool-full condition re-checked — but that check is a different, coarser gate (`ExecSlotsAll+NonExecSlotsAll` vs. `pool.all.Slots()+numSlots(tx)`), and it only rejects/evicts on a per-tx basis; it does not re-validate the batch-level "count read outside the lock" that `checkAndAddTxs` used to decide how many of the submitted transactions to admit in the first place: [3](#0-2) 

Because the size read in `AddLocal`/`checkAndAddTxs` and the actual insertion in `add()`/`enqueueTx()` are not part of one atomic critical section, multiple concurrent callers (e.g., many public-RPC `eth_sendRawTransaction` calls, or many local/remote batches arriving simultaneously) can all observe the same "room available" snapshot and each proceed to insert, allowing the pool's slot/count accounting (`pool.all.Slots()`, `pool.queuedCount`, `pool.pendingCount`) to exceed the configured `ExecSlotsAll + NonExecSlotsAll` budget — the direct structural analog of `usedSlots` being able to exceed `availableSlots` in the reported bug.

Notably, the auction module's `BidPool.insertBid` already defends against this exact race with an explicit re-check under the write lock (comment: "Re-check bidWinnerMap here — two concurrent bids can pass validateBid together"), confirming the Kaia team is aware of and has patched this bug class in that module: [4](#0-3)  — but the equivalent hardening has not been applied to the tx-pool's capacity gate in `AddLocal`/`checkAndAddTxs`.

### Impact Explanation
An attacker (any transaction sender/public-RPC caller) can flood the node with concurrent transaction submissions to make the pool exceed its configured capacity limits (`ExecSlotsAll`, `NonExecSlotsAll`). This is a resource/DoS-oriented consequence stemming from a genuine check-then-act flaw, but per the analog rules only "value movement / fee abuse / state divergence / invalid tx-block acceptance" qualify, and exceeding an internal admission-control counter by itself does not directly cause fund loss, double-spend, or state divergence between honest nodes (per-tx/per-account structural invariants such as nonce ordering are independently enforced). The impact is limited to over-admission relative to the intended capacity budget rather than a value-movement or consensus-affecting exploit.

### Likelihood Explanation
Requires precise timing of many concurrent submissions to the same node to win the race on the stale read, and node operators can mitigate via lower-level DoS protections (rate limiting, `MaxPendingPeers`, spam throttler). Likelihood is low, similar to the reported bug's "Low" rating.

### Recommendation
Perform the pool-capacity/slot check for `AddLocal` and `checkAndAddTxs` under `pool.mu` (or otherwise atomically with the actual insertion), mirroring the auction module's `insertBid` pattern of re-validating admission conditions inside the same lock that performs the mutation, so that concurrent callers cannot both observe the same "capacity available" snapshot and both be admitted beyond the configured slot budget.

### Proof of Concept
Not independently verified with a runnable reproduction in this pass — this requires spinning up a `TxPool` with a small `ExecSlotsAll+NonExecSlotsAll` and firing many goroutines against `AddLocal`/`AddRemotes` concurrently to observe whether `pool.all.Count()` can transiently or persistently exceed the configured cap. I was not able to execute code in this environment to confirm the race empirically; this assessment is based on static analysis of the lock scopes shown above (`checkAndAddTxs` capacity computation at lines 1517–1541 is outside `pool.mu`, while the actual admission/eviction logic in `add()` at lines 1139–1248 is under `pool.mu` per the surrounding function documentation "Note, this method assumes the pool lock is held").

// checkAndAddTxs compares the size of given transactions and the capacity of TxPool.
// If given transactions exceed the capacity of TxPool, it slices the given transactions
// so it can fit into TxPool's capacity.
func (pool *TxPool) checkAndAddTxs(txs []*types.Transaction, local bool) []error {
	// Single-tx fast path: bypass the slot pre-check so add()'s existing
	// missing-nonce admission can run even when the pool is at cap.
	if len(txs) == 1 {
		return []error{pool.addTx(txs[0], local)}
	}

	poolSize := uint64(pool.all.Count())
	poolCapacity := int(pool.config.ExecSlotsAll + pool.config.NonExecSlotsAll - poolSize)
	numTxs := len(txs)

	if poolCapacity < numTxs {
		txs = txs[:poolCapacity]
	}

	errs := pool.addTxs(txs, local)

	if poolCapacity < numTxs {
		for i := 0; i < numTxs-poolCapacity; i++ {
			errs = append(errs, ErrTxPoolOverflow)
		}
	}

	return errs
}
