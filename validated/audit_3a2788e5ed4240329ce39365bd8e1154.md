## Title
Incomplete macOS bundle-type allowlist in `isApplicationBundle` fails to detect non-`.app` executable bundle types (`.prefPane`, `.saver`, `.qlgenerator`, `.plugin`, etc.) - (File: `app/src/lib/is-application-bundle.ts`)

### Summary
`isApplicationBundle` is the security gate that decides whether a repository-controlled directory is safe to hand to `UNSAFE_openDirectory`/`shell.openPath`. It only checks the `mdls` content-type tree for three hardcoded UTIs and misses several other macOS bundle Uniform Type Identifiers that are also directories capable of loading/executing code when opened by Finder or a system service.

### Finding Description
The function's own docstring states the threat model explicitly: "a directory can also be an application and therefore executable making it unsafe to open directories on macOS." [1](#0-0) 

It attempts to mitigate this by querying `mdls` for `kMDItemContentTypeTree` and testing membership against a hardcoded, non-exhaustive list: [2](#0-1) 

The list only covers `com.apple.application-bundle`, `com.apple.application`, and `public.executable`. Several other macOS bundle UTIs conform to `com.apple.bundle`/`public.directory` but not to `com.apple.application` or `public.executable`, while still being loadable/executable by the OS when opened, e.g.:
- `.prefPane` (`com.apple.systempreference.prefpane`) — opened via System Preferences, executes bundled code.
- `.saver` (`com.apple.screen-saver`) — opened via System Preferences, installs and runs bundled code.
- `.qlgenerator` (`com.apple.quicklook-generator`) — loaded by QuickLook.
- `.plugin`/`.bundle` generic loadable bundles.

None of these UTIs necessarily appear as `"public.executable"` or `"com.apple.application"` in the `kMDItemContentTypeTree`, so `isApplicationBundle` would return `false` for them, even though the caller relies on this boolean to decide it is safe to call `UNSAFE_openDirectory`, whose own contract explicitly says it "should never be used to open user-provided or derived paths" without prior verification: [3](#0-2) 

The `IAppShell.showFolderContents`/`openPath` methods are similarly documented as unsafe for non-validated paths, implying `isApplicationBundle` is the validation step: [4](#0-3) [5](#0-4) 

I was not able to fully trace the exact call site in `app/src/main-process/main.ts` that consumes `isApplicationBundle`'s return value before invoking `UNSAFE_openDirectory`/`showFolderContents`, because the indexed content for that file was truncated (only the first import line was retrievable through available tools). This should be verified directly in a full checkout to confirm the exact gating logic and whether any additional check (e.g., checking the path extension for `.app` before even calling `mdls`) exists that would blunt this issue.

### Impact Explanation
If confirmed that `isApplicationBundle`'s boolean is the sole gate before `UNSAFE_openDirectory`/`shell.openPath` is invoked on a repository-controlled path, an attacker could commit a directory that is one of these sibling bundle types (e.g., a `.saver` or `.prefPane` directory) inside a cloned repository. When the victim uses "Show folder contents" (or similar), GitHub Desktop would treat the bundle as a plain, safe directory and call `shell.openPath`/`UNSAFE_openDirectory` on it. macOS would then hand it to the appropriate handler (e.g., System Preferences for `.saver`/`.prefPane`), which can execute the bundle's code — achieving code execution from attacker-controlled repository content.

### Likelihood Explanation
Likelihood depends entirely on confirming the call graph in `main.ts` (not fully verifiable via the index here). If `isApplicationBundle` is indeed the only check before opening a directory path derived from repository content, exploitation only requires the victim to clone/open a malicious repository and click "show folder contents" on the crafted directory — a normal, expected user action, making likelihood plausible if the gating is as documented.

### Recommendation
- Replace the hardcoded allowlist with a check based on UTI conformance to `com.apple.bundle` (or better, an allowlist of *safe* non-executable directory UTIs, defaulting to "unsafe" for anything unrecognized), since enumerating every executable bundle-like UTI is fragile and likely to miss future sibling types.
- Alternatively, use `com.apple.bundle` conformance itself as the "treat as unsafe" signal rather than trying to whitelist specific executable subtypes.
- Ensure the check fails closed (defaults to "is a bundle, do not open directly") on any `mdls` error or unexpected output.

### Proof of Concept
1. Create a repository containing a directory bundle whose extension/Info.plist causes Launch Services to register it as a `.saver`, `.prefPane`, or `.qlgenerator` bundle (rather than `.app`).
2. Clone this repository in GitHub Desktop and trigger "Show folder contents" (or the equivalent path handled via `UNSAFE_openDirectory`).
3. Verify via logging/instrumentation that `isApplicationBundle(path)` returns `false` for this path despite `mdls -name kMDItemContentTypeTree` showing it conforms to `com.apple.bundle`.
4. Confirm the directory is passed to `shell.openPath`, causing macOS to load/execute the bundle.

Note: Steps 2–3 assume `isApplicationBundle` gates `UNSAFE_openDirectory` in `main.ts`; this wiring should be re-verified against the full file content before treating this as conclusively exploitable, since the indexed portion of `main.ts` available to this review was incomplete.
