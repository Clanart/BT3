### Title
OP_RETURN data output excluded from weight/vbytes, fee, and MAX_STANDARD_TX_WEIGHT accounting - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes a 0-value `OP_RETURN` output carrying `data` onto `tx_outs`, but `calculate_weight_vbytes` is only ever called with `payments` and `change`. The `data` output is never included in the weight/vbytes estimate, so `needed_fee`, the min-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check all under-account for the transaction that is actually built and signed.

### Finding Description
The bug class in the reference report is "compute a limit/check on quantity A while operating on quantity B." Here the analog is exact:

- `tx_outs` gets the `OP_RETURN` output pushed before fee/weight computation: [1](#0-0) 
- `calculate_weight_vbytes` builds its scratch `Transaction` only from `payments` plus an optional `change` output — there is no `data`/`OP_RETURN` parameter at all: [2](#0-1) 
- Both calls pass only `payments` and `change`, omitting `data`: [3](#0-2) 
- `needed_fee = fee_per_vbyte * vbytes` and the minimum-relay-fee gate both use that under-counted `vbytes`: [4](#0-3) 
- When change is emitted, `value = input_sat - payment_sat - fee_with_change`, so the missing OP_RETURN bytes are silently redirected into the change output instead of the fee: [5](#0-4) 
- The standardness check `weight > MAX_STANDARD_TX_WEIGHT` uses the same under-counted `weight`: [6](#0-5) 

An 80-byte OP_RETURN output adds roughly `(1 + 8 + 1 + 82) * 4 ≈ 368 WU ≈ 92 vbytes` that is never charged for and never counted toward standardness.

### Impact Explanation
Two concrete effects, both reachable by an unprivileged party who controls the `data` payload (the instruction bytes Serai embeds via OP_RETURN) or the payment shape:

1. **Underpaid fee / non-standard transaction.** The achieved fee rate is `fee_per_vbyte` applied to the no-data vbytes, while the real transaction is ~92 vbytes larger. In the worst case `fee_per_vbyte` just passes the min-relay check on the small estimate, but the real fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`, producing a transaction that won't propagate — funds in the signed inputs are effectively stalled. Similarly, a transaction near `MAX_STANDARD_TX_WEIGHT` passes the check while the real transaction exceeds it and is rejected as non-standard.
2. **Change over-credit.** The uncharged bytes inflate `value` sent to the change output, so the transaction pays strictly less fee than `needed_fee()` reports — a mismatch between the quantity checked (weight estimate) and the quantity spent (the actual signed transaction), exactly the "slippage computed on the wrong number" pattern.

### Likelihood Explanation
`data` is an explicit `Option<Vec<u8>>` argument up to 80 bytes supplied by upstream callers (instruction commitments), and `fee_per_vbyte` is an external input. Any send path that populates `data` hits this unconditionally; no race or privileged position is required.

### Recommendation
Pass the OP_RETURN script (or its serialized size) into `calculate_weight_vbytes` so `weight`, `vbytes`, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction actually being signed. Recompute the min-relay-fee gate on the corrected vbytes.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
