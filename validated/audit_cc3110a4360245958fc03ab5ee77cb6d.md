### Title
Cross-chain escrow redemption permanently locked by a single non-transferable output token in the atomic `withdraw()` loop - (File: `evm/src/apps/IntentGatewayV2.sol`, mirrored in `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` releases all escrowed input tokens for one order commitment in a single loop over `body.tokens[]`, sending each token to one `beneficiary` and reverting the entire call (`TransferFailed()`) if any single transfer fails. Because the call is invoked from `EvmHost.dispatchIncoming` (permissionless, relayer-delivered) and the beneficiary is a user/solver-controlled address, a beneficiary that is non-transferable for even one of the escrowed tokens (e.g. a blacklisted USDC/USDT address, or a token with `revert`-on-recipient logic) makes the redemption for that entire order permanently unrecoverable — not just for the offending token, but for every other, otherwise-transferable token bundled in the same order.

### Finding Description
`withdraw()` iterates `body.tokens` and, for ERC-20 tokens, does a raw low-level `token.call(...transfer...)`, reverting the whole function on any failure: [1](#0-0) 

This function is reached two ways:
- From `RequestKind.RedeemEscrow` handling in `onAccept` (the normal solver-payout path after a cross-chain fill), and
- From `onGetResponse` on cancellation/refund flow.

The beneficiary for the `RedeemEscrow` path is set by the filler/solver at fill time on the destination chain and is fully attacker(solver)-controlled: [2](#0-1) 

The delivery of this request is permissionless — any relayer can call `handlePostRequests` → `EvmHost.dispatchIncoming`, which invokes `onAccept` via a low-level call and, on failure, simply deletes the request receipt so the *same* call can be retried later: [3](#0-2) 

The receipt-deletion-and-retry mechanism assumes failures are transient (e.g. temporary insufficient gas, reentrancy guard). It does not handle a **permanent** deterministic failure such as a beneficiary blacklisted by a stablecoin issuer. Since `withdraw()` processes *all* of an order's escrowed tokens atomically in one call, a single permanently-failing transfer (for any one token in `body.tokens`) makes the entire order's escrow (all tokens, including otherwise-redeemable ones) permanently stuck: every retry hits the exact same failing transfer and reverts, and there is no code path to skip, partially settle, or manually rescue the stuck entry (no owner rescue function exists in this contract, unlike other admin-gated flows such as `SweepDust`, which itself has the identical atomic-loop weakness for governance-driven multi-output sweeps at lines 652-673 of the same file).

This directly mirrors the CrabNetting `H-2` bug class: an unconditional `transfer`/`call` inside a loop over multiple entries/assets, where a single blocked recipient/token combination for one order permanently freezes settlement of that order with no operator-controlled recovery path.

### Impact Explanation
This is a genuine, permanent loss/lock of escrowed bridged funds reachable through the ordinary, permissionless intent-fill flow — matching the bounty's "stealing or loss of funds" and "logic attacks" categories. A solver (an ordinary, unprivileged, non-relayer/non-admin actor) who fills a cross-chain order whose input-token escrow includes a token that can later become non-transferable to the solver's own chosen beneficiary (or who deliberately picks/loses control of an address later blacklisted) locks that order's *entire* escrowed value forever — even portions denominated in tokens that have nothing to do with the blacklist. There is no `try/catch`-and-skip, no per-token partial settlement, and no owner rescue function to recover the stuck escrow, unlike the fix accepted for the original CrabNetting bug (which added `try/catch` around the transfer and an owner mechanism to unstick queued withdrawals).

### Likelihood Explanation
Likelihood is realistic but not trivial: it requires (a) an order whose input escrow spans multiple tokens or a single token that can become permanently blocked for the chosen beneficiary, and (b) the beneficiary address becoming non-transferable (blacklisting is common for USDC/USDT and is attacker-triggerable by using a beneficiary the attacker knows/expects to be sanctioned, or by choosing a malicious "receiving" contract for the native branch that always reverts). No relayer, prover, or admin collusion is needed — it only needs a normal permissionless `fillOrder`/`onAccept` delivery, which any user or solver can trigger.

### Recommendation
- In `withdraw()`, wrap each individual token transfer in a `try/catch` (or check-then-skip via low-level call return value already captured) so a failing transfer for one token/beneficiary does not block redemption of the remaining tokens in the same order; record the failed leg separately (e.g., mark as claimable via a distinct rescue mapping) instead of reverting the whole function.
- Add an owner/governance-gated rescue path (analogous to Opyn's accepted fix) allowing failed escrow legs to be redirected to an alternate address or repaid in-kind after some cooldown, so a single non-transferable token/beneficiary combination cannot permanently strand the rest of the order's value.
- Apply the same fix to the `SweepDust` loop (lines 652–673), which has an identical all-or-nothing structure across multiple unrelated beneficiaries/tokens in governance sweeps.

### Proof of Concept
1. Attacker (as solver) calls `fillOrder`/`_fillCrossChain` on the destination chain for an order whose `order.inputs` on the source chain includes both USDC and some other ERC-20 (e.g. WETH), setting `msg.sender` (the solver's own address, used later as `beneficiary` in the `WithdrawalRequest`) to an address it knows will be blacklisted by USDC (or which the attacker plans to get blacklisted, e.g. via prior sanctioned activity).
2. `RedeemEscrow` request lands on the source chain; a relayer delivers it via `handlePostRequests` → `dispatchIncoming` → `onAccept` → `withdraw()`.
3. `withdraw()` loops `body.tokens`: the WETH `token.call` transfer succeeds first (if ordered first) but the USDC `token.call` fails because the beneficiary is blacklisted; the whole `withdraw()` call reverts (`TransferFailed()`), rolling back the WETH transfer too.
4. `EvmHost.dispatchIncoming` catches the failed external call, deletes the request receipt, and returns — permitting retry.
5. Every subsequent relayer retry replays the exact same beneficiary and hits the exact same USDC blacklist failure; `withdraw()` reverts every time. Both the USDC and the WETH escrowed for that order are now permanently locked in the `IntentGatewayV2` contract with no rescue mechanism, since `_orders[body.commitment][token]` is never decremented and no owner function exists to force a partial or redirected payout.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
