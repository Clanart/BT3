### Title
Wallet sync crash / DoS via arbitrary dust sent to a PlotNFT's public p2-singleton reward address - ([File: chia/wallet/plotnft_wallet/plotnft_wallet.py])

### Summary
`PlotNFT2Wallet.coin_added()` unconditionally raises an unhandled `ValueError` when it observes *any* non-farming-reward coin sent to the wallet's public, derivable `p2_singleton_puzzle_hash`. Because this puzzle hash is not a secret and can be paid by anyone (analogous to the report's unrestricted `deposit()`), an attacker can trivially trigger this exception during normal wallet sync, which is a reachable, cheap, repeatable DoS against the pool participant's wallet — the wallet-side conceptual analog of the M-18 finding, where minimal-value, attacker-controlled deposits force an unbounded/unrecoverable cost on the honest party (here, sync failure/crash rather than gas, but the root cause pattern — "no restriction on what any user can add to a state a privileged/legitimate flow must fully process" — is the same).

### Finding Description
`PlotNFT.launcher_id_to_p2_puzzle_hash()`/`create_p2_singleton_puzzle_hash()` derive the `p2_singleton_puzzle_hash` for a plotnft from public data (`launcher_id`, delay params) [1](#0-0) . Anyone can send XCH to this puzzle hash the same way they could send XCH to any other address, exactly as in the M-18 report where anyone could call `deposit()` with a minimal, arbitrary amount.

When wallet sync sees such a new, unspent coin at this puzzle hash, `WalletStateManager._add_coin_state()` calls `coin_added()` [2](#0-1) , which for `WalletType.PLOTNFT_2` dispatches to `PlotNFT2Wallet.coin_added()`. There, the branch handling `coin.puzzle_hash == self.p2_singleton_puzzle_hash` only accepts the coin as a legitimate `PoolReward` if `coin.parent_coin_info[0:16] == GENESIS_CHALLENGE[0:16]` (the fixed prefix consensus uses for farming/pool reward parent ids); otherwise it raises:
```
raise ValueError(f"A non-pooling reward coin was paid to PlotNFT with id: {self.plotnft_id}")
``` [3](#0-2) 

This check correctly filters out forged reward coins from being *credited* as pool rewards (an attacker cannot forge the `GENESIS_CHALLENGE` parent-id prefix since coin parent linkage is enforced by consensus), but it does not gracefully ignore/skip such a coin — it raises. This call is made directly inside the wallet's coin-state processing loop (`_add_coin_state`), with no surrounding try/except at that call site for the "coin added" (unspent) path [4](#0-3) .

### Impact Explanation
Any unprivileged party who knows (or derives) a target's plotnft `p2_singleton_puzzle_hash` — a value that is effectively public since it's derived from the public `launcher_id` — can send a trivial-value coin to that address. This is functionally identical to the report's "excess receipt" spam: the attacker pays negligible cost (one small-value coin) to force the victim's own wallet software into an unhandled exception path during sync, repeatable per dust coin sent, and reachable purely from a normal spend bundle the attacker submits to the mempool. Depending on how far up the call stack this exception propagates, this can interrupt or repeatedly fail the victim's wallet sync for that wallet, which is a spend-triggered processing halt — the closest in-scope analog to the mempool/processing-halt category permitted by the rules.

### Likelihood Explanation
Likelihood is high in terms of attacker capability (any wallet user can craft and broadcast a standard transaction paying 1 mojo to a known p2-singleton puzzle hash), but I was not able to fully trace whether this specific `ValueError` is caught by an outer handler in the sync pipeline before this task's iteration budget ran out — this is the primary open uncertainty. I could not confirm within the available iterations whether callers of `_add_coin_state`/`coin_added` wrap this specific path in a broader `try/except` that would suppress or degrade the impact (some sibling branches, like the `PLOTNFT_2` spent-branch, do use local `try/except ValueError: pass`, but the new-coin/unspent branch I found does not appear to).

### Recommendation
In `PlotNFT2Wallet.coin_added()`, treat an unrecognized coin sent to `p2_singleton_puzzle_hash` as a no-op (log and ignore, do not track/import it as wallet state) rather than raising, since such dust cannot be a legitimate pool reward and does not need to halt sync. If this coin needs to be tracked for future spending/cleanup, do so in a bounded, batched way (mirroring `PoolWallet.claim_pool_rewards`'s `max_spends_in_tx` batching) so an attacker cannot force unbounded work or unhandled failures via a large number of low-value dust coins sent to the address.

### Proof of Concept
1. Determine or derive a target's plotnft `p2_singleton_puzzle_hash` from its public `launcher_id` via `launcher_id_to_p2_puzzle_hash()` [5](#0-4) .
2. Submit a standard spend bundle that creates a 1-mojo coin at that puzzle hash.
3. When the victim's wallet syncs and observes this new coin, `WalletStateManager._add_coin_state()` calls `coin_added()` [2](#0-1) , which raises `ValueError("A non-pooling reward coin was paid to PlotNFT...")` in `PlotNFT2Wallet.coin_added()` [3](#0-2)  because the coin's `parent_coin_info` prefix does not match `GENESIS_CHALLENGE[0:16]`.
4. Repeat with many dust coins to increase the frequency/cost of this failure on the victim's wallet.
