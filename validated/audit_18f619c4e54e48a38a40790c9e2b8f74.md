### Title
Unhandled `StopIteration` in wallet hint/addition computation from untrusted CAT/CR-CAT/offer coin spends can halt wallet transaction processing - ([File: chia/wallet/util/compute_hints.py])

### Summary
`compute_spend_hints_and_additions()` parses the output conditions produced by running an externally supplied `puzzle_reveal`/`solution` pair (a `CoinSpend`) without validating that each condition item is a well-formed, non-empty list before indexing into it. This mirrors the CVE-2018-6335 bug class: a malformed/edge-case payload (there, HTTP/2 priority metadata; here, a CLVM condition list) drives an unguarded low-level parsing primitive (`std::out_of_range` there, Python `StopIteration` here) that isn't caught by the surrounding code, producing a denial-of-service when processing attacker-influenced input.

### Finding Description
`compute_spend_hints_and_additions` iterates the conditions produced by executing a `CoinSpend`'s puzzle against its solution: [1](#0-0) 

For each top-level item in the result program it does:
```
atoms = condition.as_iter()
op = next(atoms).atom
``` [2](#0-1) 

`condition.as_iter()` returns an empty iterator whenever `condition` is `Program.NIL` (an empty list) or an atom whose `as_iter()` degenerates to no pairs. In that case, `next(atoms)` raises `StopIteration` immediately, and there is no `try/except` around this call inside the function. Because a puzzle's output conditions are entirely attacker-controlled (the puzzle can legally output `()` as one of its top-level "conditions" — this is valid, benign CLVM output, not a rejected/malformed spend), any counterparty who controls the puzzle_reveal/solution being processed by this helper can trigger the unguarded exception.

This helper is invoked directly with untrusted `CoinSpend` data — as evidenced by grep matches in `chia/wallet/cat_wallet/cat_wallet.py`, `chia/wallet/did_wallet/did_wallet.py`, `chia/wallet/vc_wallet/cr_cat_wallet.py`, `chia/wallet/trade_manager.py`, and `chia/wallet/trading/offer.py` — all of which process coin spends and offers that originate from wallet counterparties or peers, not the local wallet's own signed spends.

### Impact Explanation
If reached from an unguarded code path (e.g., syncing a CAT/CR-CAT/DID coin whose parent's puzzle emits an empty condition entry, or validating/taking an offer crafted by a counterparty), the unhandled `StopIteration` propagates out of `compute_spend_hints_and_additions`, aborting whatever wallet routine invoked it (coin-added processing, offer parsing, trade management). This matches the "spend-triggered transaction-processing halt" impact category: a single malicious spend or offer can stop the victim's wallet from completing hint/addition computation for that coin, which can cascade into stalled wallet sync or an inability to process/settle the associated trade, similar in kind to the HHVM h2-frame DoS (a single malformed input crashing the request-processing path).

### Likelihood Explanation
Producing a puzzle whose top-level CLVM output includes an empty list (`()`) as one of the emitted items is trivial and does not require breaking consensus rules — CLVM freely allows arbitrary output values from a puzzle, and non-condition/garbage entries are normally ignored by strict condition parsers (see `chia/consensus/condition_tools.py parse_sexp_to_condition`, which explicitly treats `None`/atom-typed `op` as a `ConsensusError` rather than crashing). `compute_hints.py`, by contrast, does not perform this defensive check before calling `next()`. This makes the trigger low-effort for any offer counterparty or CAT/DID coin creator who can influence what puzzle the victim wallet will later re-run.

### Recommendation
In `compute_spend_hints_and_additions` (chia/wallet/util/compute_hints.py), guard the `next(atoms)` call, e.g.:
```python
atoms = condition.as_iter()
op_atom = next(atoms, None)
if op_atom is None or op_atom.atom is None:
    continue
op = op_atom.atom
```
Additionally, audit and add explicit `try/except (StopIteration, ValueError, EvalError)` handling (or equivalent) at each call site in `cat_wallet.py`, `did_wallet.py`, `cr_cat_wallet.py`, `trade_manager.py`, and `offer.py` so a single malformed/edge-case spend cannot abort wallet processing of coin state or offers.

### Proof of Concept
1. Construct a CAT (or any) coin whose inner puzzle, when run, outputs a top-level list that includes an empty list `()` as one of its emitted "conditions" alongside otherwise normal `CREATE_COIN` conditions (e.g., `(q (51 <ph> <amt>) ())` — perfectly valid CLVM, not rejected by consensus condition parsing since strict condition validation only looks at recognized opcodes and ignores/rejects malformed ones through defined error codes rather than crashing).
2. Have the victim wallet observe/sync this coin (e.g., receive it via a CAT transfer, or include it as part of an offer that the victim wallet parses/takes).
3. When the wallet calls `compute_spend_hints_and_additions` on the parent spend to compute hints/additions (from `cat_wallet.py`/`did_wallet.py`/`trade_manager.py`/`offer.py`), `condition.as_iter()` on the empty-list entry yields nothing, and `next(atoms).atom` raises `StopIteration`, aborting the surrounding wallet coroutine.

**Verification note:** I was not able to fully confirm, within the available investigation budget, whether every call site (particularly the exact usages in `wallet_state_manager.py`, which showed 3 matches but whose surrounding exception-handling context I could not inspect before running out of tool calls) wraps this call in a broad exception handler that would already catch `StopIteration`. If such a handler exists at all reachable call sites, the practical impact would be reduced to a logged/caught error rather than a full processing halt. This should be verified directly in the repository (`chia/wallet/wallet_state_manager.py`, `chia/wallet/cat_wallet/cat_wallet.py`, `chia/wallet/trading/offer.py`, `chia/wallet/trade_manager.py`, `chia/wallet/vc_wallet/cr_cat_wallet.py`) before treating this as fully confirmed.
