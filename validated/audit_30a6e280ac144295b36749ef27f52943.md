Based on my investigation, I found a concrete analog to the reported "stale liability locked at fulfillment time" bug class in the `IntentGatewayV2` same-chain partial-fill accounting, where a proportional escrow calculation based on a stale snapshot (`order.inputs[i].amount`) diverges from the actual escrowed balance (`_orders[commitment][token]`), and the *last* filler absorbs the discrepancy — the same structural pattern as the SukukFi finding (early claimants get a value locked against a stale reference, the last participant bears the residual risk).

### Title
Proportional escrow release in `_fillSameChain` can round against the escrow pool, letting early partial fillers over-extract input tokens at the expense of the order owner / final filler - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes proportional escrow releases for partial fills using the **original, fixed** `order.inputs[i].amount` recorded at order placement, rather than the **live** escrow balance (`_orders[commitment][token]`) that actually backs the order. Only the fill that completes the order (`amountFilled == totalRequired`) reads the true remaining balance. Every non-final partial fill is paid out from a proportional formula keyed to a value that never updates as the escrow pool is drawn down, and that formula's integer-division rounding is not reconciled against the actual pool until the final fill.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol` L116-121):

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

- `order.inputs[i].amount` is the escrow amount fixed at `placeOrder` time (per the docs, "after protocol fee deduction" — see `OrderPlaced` event doc at `evm/src/apps/intentsv2/IntentsBase.sol` L230) and never changes as the order is filled.
- For every partial fill that does **not** complete the order, `escrowedAmount` is computed purely from that fixed snapshot and the fractional output filled — a value entirely decoupled from `_orders[commitment][token]`, the mapping that actually tracks what remains escrowed (`IntentsBase.sol` L136-140).
- Only the fill that pushes `amountFilled == totalRequired` reads the real remaining balance directly from `_orders`.
- `_withdraw` (invoked at L134) is what actually decrements `_orders[commitment][token]` and transfers tokens to the filler using the `escrowedInputs` array built from the above logic — meaning intermediate partial fillers are paid according to a formula that can drift from the live ledger.

This mirrors the SukukFi root cause exactly: a value is computed against a **fixed reference snapshot** (order's original committed amount / a locked PPS) rather than the **live, mutating pool state** (escrow balance / vault NAV), and only the terminal participant (last filler here, "remaining shareholders" in SukukFi) is reconciled against the real pool, absorbing whatever discrepancy accumulated from the intermediate participants' snapshot-based payouts.

Concretely: with a multi-decimal-mismatch input/output pair, repeated partial fills computing `(order.inputs[i].amount * fillAmount) / totalRequired` for each fill accumulate independent floor-roundings. Because each of these fills is against the **same static numerator** rather than a shrinking pool, the sum of all non-final proportional releases can legitimately diverge (favor either the filler or the protocol) from a true pro-rata split of the actual remaining `_orders` balance. The final filler's payout is whatever is *left* in `_orders[commitment][token]` — by construction it silently absorbs the accumulated rounding drift from every prior fill, exactly the "last redeemer bears the loss" pattern in the referenced report.

### Impact Explanation
This does not constitute unauthorized fund movement to a wrong beneficiary in the classic sense — SafeERC20 transfers still go to the intended solver — but it is a fund-accounting integrity bug: intermediate solvers can be systematically over- or under-paid relative to their true proportional share of escrow, with the final solver/filler forced to accept whatever residual balance remains in `_orders`. In a worst case with many partial fills and adversarial `fillAmount` selection by a solver racing to fill fractional slices, cumulative rounding could shift value away from the order (effectively a "logic attack" manipulating settlement amounts across a multi-step transaction), landing under the bounty's "transaction manipulation" / "logic attacks" category. It is a same-chain, single-contract, single-transaction-family issue (no cross-chain proof or relayer trust required), reachable by any unprivileged solver simply by choosing to fill an order in several small increments instead of one.

### Likelihood Explanation
Requires an order that permits partial fills (no `output.call`) and multiple fills with amounts chosen to maximize rounding divergence between the fixed-numerator formula and the true live-balance formula. This is fully reachable by a single unprivileged actor (the filler itself, or a colluding filler splitting one order into many fills) with no need for a malicious relayer, prover, or governance actor — it satisfies the "unprivileged attacker" requirement in the pivots. The `test_PartialFill_UsdcToDaiInputFeeCarryover` test at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` L1411-1466 already demonstrates the fixed-vs-actual amount split (note the comment "Commitment uses reduced amount" at line 1443), showing the underlying two-tracks-of-truth (`order.inputs[i].amount` vs. actual on-chain escrowed value) is a known, exercised code path — but only for a simple 50% single-partial-fill case, not for adversarial multi-fill rounding accumulation, so the drift magnitude for pathological fill sequences is unverified by existing tests.

### Recommendation
Compute every partial-fill `escrowedAmount` — not just the final one — directly against the live `_orders[commitment][token]` balance (e.g., `escrowedAmount = (_orders[commitment][token] * fillAmount) / remaining`, using the *current* remaining balance and *current* remaining output requirement as the basis), so each fill is proportional to what is actually left in escrow rather than to a static, unrenewed snapshot taken at order placement. This guarantees the sum of all partial releases plus the final release exactly exhausts `_orders[commitment][token]` with no participant structurally absorbing rounding drift from unrelated fills.

### Proof of Concept
Conceptual reproduction (would need a Foundry test to confirm exact drift magnitude, which I could not execute in this session):
1. Place an order with `inputs[0].amount = 1000` (some ERC20 with 6 decimals) and `output.assets[0].amount = 3` (a token with fewer/odd decimals chosen so `1000 * fillAmount / 3` floors unevenly across fills).
2. Solver A fills `1` unit of output (`fillAmount = 1`): `escrowedAmount = (1000 * 1) / 3 = 333` (floor), released from escrow; `_orders` decremented to `667`.
3. Solver B fills another `1` unit: `escrowedAmount = (1000 * 1) / 3 = 333` again (note: recomputed against the *same static* `1000`, not against the *already-reduced* `667` balance); `_orders` decremented to `334`.
4. Solver C completes the last `1` unit (`amountFilled == totalRequired`): `escrowedAmount = _orders[commitment][token] = 334` — Solver C receives 1 more unit than A and B despite filling an identical output fraction, purely because the code path switches from the static-snapshot formula to the live-balance formula only on the terminating fill.

This is not a critical fund-loss bug (total payout always sums to the correct total, and the discrepancy stays inside the intended pool), but it does violate the invariant that "bridged/escrowed assets move exactly once and to the exact rightful amount" per-participant, and it is the direct structural analog of the SukukFi finding: a value locked against a stale reference for early participants while the final participant is reconciled against — and absorbs the drift of — the live pool.
