### Title
Automatic, unconfirmed rewrite of a repository's `origin` remote URL from unauthenticated GitHub API data - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
When Desktop refreshes the GitHub metadata associated with a local repository, `updateRemoteUrl` silently calls `git remote set-url` on the user's `origin` (default) remote if the `clone_url` returned by the GitHub API differs from the locally configured remote, but was previously in sync with an earlier API response. Unlike the analogous "upstream remote" case, which shows the user the `UpstreamAlreadyExists` confirmation dialog, this default-remote rewrite happens with no user confirmation and is not scoped to detecting a legitimate rename/redirect — it accepts whatever `clone_url` the API/account endpoint returns as long as the hostname/owner/name-derived match passes the same-remote heuristic.

### Finding Description
`repositoryWithRefreshedGitHubRepository` (app/src/lib/stores/app-store.ts:4874-4914) fetches repository metadata from the GitHub API for the account matched to the repo's remote, and then unconditionally invokes: [1](#0-0) 

`updateRemoteUrl` performs three checks — protocol match, "was previously unchanged" (`remoteUrlUnchanged`), and "URLs differ" (`!urlsMatch`) — and if they pass, calls `gitStore.setRemoteURL(...)`, which shells out to `git remote set-url`: [2](#0-1) [3](#0-2) 

This write path is reached via `withRefreshedGitHubRepository`, which is invoked from many normal, non-privileged code paths (background repo refresh, account-change refresh, and other flows that call `repositoryWithRefreshedGitHubRepository`/`withRefreshedGitHubRepository`) — not a user-initiated "update remote" action. In contrast, when the *upstream* remote (fork parent) needs updating, Desktop explicitly surfaces `UpstreamAlreadyExists` for user confirmation before touching the remote: [4](#0-3) 

No equivalent confirmation exists for the default/origin remote update in `updateRemoteUrl`. The invariant that should hold — "the user (not a remote server response) controls what host/repo their local `origin` points to, and any change to that mapping used for pushes/fetches must be confirmed" — is broken here: the value of `apiRepo.clone_url`, which is data returned by a GitHub(.com/Enterprise) API response for the endpoint associated with the account, is trusted to rewrite the git remote that determines where the user's future `git push`/`git fetch` operations go.

The gating logic (`remoteUrlUnchanged`, `urlsMatch`, `urlMatchesRemote`) only requires that the *previously cached* `gitHubRepository.cloneURL` matched the current remote — it does not require the *new* `clone_url` to point to the same owner/repo identity that the user originally added. If the account/repository this endpoint associates with is compromised, hijacked (e.g., an org repo whose ownership is fraudulently transferred, or a GHES instance under attacker control returning attacker-chosen `clone_url` responses for the `/repos/{owner}/{name}` call), the next background refresh will automatically retarget the user's `origin` remote to the attacker's URL — with no dialog, no diff shown, nothing in the UI indicating the remote changed.

### Impact Explanation
This is a silent corruption of the destination for a user's future `git push` operations: the `origin` remote — the one Desktop uses by default for push/pull/fetch — can be repointed to an attacker-controlled repository without any user action or confirmation, purely as a side effect of a background API refresh. Consequences:
- Future pushes intended for the legitimate repository are silently redirected to the attacker's remote, disclosing source code/commit history (including potentially secrets in diffs) to the attacker.
- Future fetches/pulls could pull attacker-controlled refs into the local repository, which — combined with any other trust-on-checkout behavior — could lead to further compromise.
- The change is invisible in the UI; nothing analogous to `UpstreamAlreadyExists` warns the user that `origin` moved.

This matches the "silent corruption of what the user commits or pushes" class described in scope, driven by an attacker-influenced "GitHub API object" (`apiRepo.clone_url`).

### Likelihood Explanation
The trigger requires only that the GitHub API endpoint associated with the repository return a different `clone_url` for the same owner/name pairing than what is currently configured — something entirely outside the local user's control and achievable by:
- A malicious/compromised GitHub Enterprise Server the user is signed into, whose `/repos/{owner}/{name}` response is attacker controlled.
- Any scenario where the mapped account's API responses for that repository can be influenced (e.g., a compromised or briefly-hijacked org/repo whose settings are changed and then reverted, since the check only compares to the previously cached value at time of last refresh).

No local access, admin rights, or social engineering is required — it is a passive server-response-driven exploit that fires automatically the next time Desktop refreshes the repository (a routine background operation), not something the user has to click through.

### Recommendation
- Require explicit user confirmation before rewriting the default/origin remote URL in response to an API-provided `clone_url` change, mirroring the existing `UpstreamAlreadyExists` dialog used for the upstream remote.
- When such a change is detected, surface the old vs. new remote URL to the user and let them opt in, rather than silently calling `setRemoteURL`.
- Consider additionally validating that the new `clone_url`'s owner/name pair corresponds to a documented rename/transfer event (e.g., via the API's redirect/`full_name`-changed signal) rather than trusting any mismatch as reason to auto-update.

### Proof of Concept
1. User adds `origin` pointing at `https://github.example.com/acme/widget.git` and Desktop associates it with `gitHubRepository.cloneURL = https://github.example.com/acme/widget.git` (matches, `remoteUrlUnchanged` will be true on subsequent checks).
2. Attacker controls (or compromises) the GHES instance / API responses at `github.example.com`, or otherwise causes the `/repos/acme/widget` API response's `clone_url` to become `https://github.example.com/attacker/widget-evil.git` while keeping the protocol `https`.
3. On the next background refresh (`repositoryWithRefreshedGitHubRepository`, reachable via routine flows such as account refresh / repository refresh), `updateRemoteUrl` is called:
   - `protocolsMatch` = true (both `https`)
   - `remoteUrlUnchanged` = true (current remote still equals the last cached `cloneURL`)
   - `urlsMatch` = false (new `clone_url` differs)
   - ⇒ `gitStore.setRemoteURL('origin', 'https://github.example.com/attacker/widget-evil.git')` executes silently. [5](#0-4) 
4. The user's next `git push` from Desktop now pushes to the attacker's repository with no dialog or warning shown.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
