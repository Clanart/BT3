Confirmed root cause: `consoleLog.decode` in `blockchain/vm/contracts.go` converts attacker-controlled 32-byte words into `int` via `big.Int.Int64()` without validating the magnitude, allowing a classic "insecure sign extension" bug analogous to CVE-2016-9190.

There's no `recover()` present anywhere under `blockchain/vm/*.go`, so a panic inside precompile execution (triggered from `EVMInterpreter.Run`/opcode dispatch, which itself has no `recover`) is not caught at that layer, which supports the severity of this finding.

### Title
Out-of-bounds slice panic via insecure sign-extension in `consoleLog.decode` (CONSOLE_LOG precompile) — ([File: blockchain/vm/contracts.go])

### Summary
The `CONSOLE_LOG` precompiled contract (`consoleLog`), reachable by any contract via a normal `CALL`, decodes ABI-like parameters from raw call `input` using `big.Int.SetBytes(...).Int64()` and then truncates the result to a machine `int` without validating that the original 32-byte word actually fits in an `int64`/`int`. This mirrors the Pillow CVE-2016-9190 root cause: an "Insecure Sign Extension" where a large unsigned value is narrowed to a signed integer, producing a negative (or wrapped) length/offset value that bypasses subsequent bounds checks and is then used directly to index/slice a buffer.

### Finding Description
In `blockchain/vm/contracts.go`, `consoleLog.decode` handles `StringTy`/`BytesTy` parameters like this: [1](#0-0) 

```go
start := int(big.NewInt(0).SetBytes(params[pos : pos+registerSize]).Int64())
if len(params) < start+registerSize {
    return nil, errors.New("input too short")
}
size := int(big.NewInt(0).SetBytes(params[start : start+registerSize]).Int64())
if len(params) < start+size+registerSize {
    return nil, errors.New("input too short")
}
res = append(res, string(params[start+registerSize:start+size+registerSize]))
``` [2](#0-1) 

`big.Int.Int64()` (Go stdlib) simply returns the low 64 bits of the unsigned magnitude reinterpreted as a signed `int64` when the value does not fit in 63 bits — this is exactly an "insecure sign extension": an attacker-supplied 32-byte word with the high bit of its low 64 bits set becomes a large negative `int64`, and thus a negative `int` after the `int(...)` conversion (on 64-bit platforms `int` is 64-bit, so the same truncation issue occurs directly, no additional narrowing needed — an attacker only needs to control the low 64 bits of the 256-bit word).

Once `start` is negative:
- `len(params) < start+registerSize` — with `start` deeply negative, `start+registerSize` is negative, so `len(params) < (negative)` is `false`, and the length check is silently bypassed.
- `params[start : start+registerSize]` is then evaluated with a negative index, which in Go causes an **out-of-range/negative-index runtime panic** (not a controlled read) rather than the intended bounds-check failure.

The same pattern also affects the `size` value taken from `params[start:start+registerSize]` at line 1447 before the negative-start panic — either variable being attacker-controlled and improperly range-checked via signed-integer truncation can trigger a panic or, in principle (Go's slice-index panics prevent true OOB reads here, but the logic still demonstrates the exact insecure sign-extension flaw described in the report), a length check bypass.

This is called from `consoleLog.Run`, which is invoked for every `CALL` to the reserved `CONSOLE_LOG` precompile address: [3](#0-2) 

Crucially, there is no `recover()` anywhere in the EVM execution path (`blockchain/vm/*.go`), including `EVMInterpreter.Run` which drives opcode/precompile dispatch: [4](#0-3) 

so a panic triggered by any transaction sender calling this precompile with crafted `console.log`-style ABI parameters is not gracefully converted into an EVM execution error — it can propagate up and crash the node process handling the transaction (state processing, block execution, or `eth_call`).

### Impact Explanation
Any unprivileged transaction sender or public-RPC caller (via `eth_call`/`eth_estimateGas` or a real transaction) can craft `input` bytes for a `CALL` to the `CONSOLE_LOG` precompile address that trigger a Go runtime panic through this insecure sign-extension/bounds-check bypass. If unrecovered, this can crash the executing node (validator, full node, or RPC node), leading to denial of service across the network if triggered inside block processing, or a targeted crash of RPC nodes serving `eth_call`. This satisfies the "state divergence between honest nodes" / "acceptance-of-invalid-input-causing-crash" class of impact requested by the validation criteria, since a panic during deterministic state transition on some nodes but not others (e.g., due to differing recover middleware in RPC vs. block-processing paths) can also cause execution/consensus inconsistency.

### Likelihood Explanation
High likelihood: the precompile is called via a standard EVM `CALL` opcode from any contract, requires no special privileges, and the vulnerable arithmetic (`Int64()` truncation of an unbounded 256-bit ABI word) is trivially triggerable by choosing an appropriate low-64-bit pattern for the "offset" word of a `string`/`bytes` console.log argument.

### Recommendation
- In `consoleLog.decode`, validate that each 32-byte offset/length word fits within a safe, small range (e.g., `<= len(params)` and non-negative) using `big.Int.IsUint64()`/`BitLen()` checks (as already done correctly elsewhere in the codebase, e.g. `accounts/abi/unpack.go`'s `lengthPrefixPointsTo`, which checks `BitLen() > 63` before converting) instead of blindly calling `.Int64()` and casting to `int`.
- Reject any offset/length whose big-endian value cannot be represented as a small non-negative `uint64`/`int` before using it for slicing.
- Add a top-level `recover()` around precompile execution (or at minimum around `consoleLog.Run`) as defense-in-depth, converting any panic into a normal EVM execution error rather than allowing it to propagate and crash the process.

### Proof of Concept
1. Deploy or use any contract that performs a raw `CALL` to the `CONSOLE_LOG` precompile address (as registered in `blockchain/vm/precompiles.go`) with a 4-byte selector matching an entry in `common.ConsoleLogSignatures` for a `string` or `bytes` parameter.
2. Craft the parameter's "offset" word (bytes 4..36 of `params`, i.e., the first argument slot) so that, interpreted as a big-endian 256-bit integer, its low 64 bits form a value ≥ `2^63` (e.g., `0xFFFFFFFFFFFFFFFF` in the low 8 bytes, with the rest zero). `big.NewInt(...).Int64()` on this value returns a negative `int64` (e.g., `-1`), so `start = int(-1)`.
3. The check `len(params) < start+registerSize` (`len(params) < -1+32` i.e. `len(params) < 31`) is bypassed for any realistically sized `params`.
4. `params[start : start+registerSize]` (`params[-1:31]`) is evaluated by the Go runtime, causing an immediate panic (`slice bounds out of range`).
5. Since `consoleLog.Run` and the EVM interpreter contain no `recover()`, submitting such a transaction (or calling it via `eth_call`) can crash the node process executing it.
