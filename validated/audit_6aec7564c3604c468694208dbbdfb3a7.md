### Title
Missing zero-coefficient / round-trip check in `RecoverPolynomialCoefficients` allows acceptance of cells inconsistent with any degree<4096 polynomial - (File: internal/erasure_code/erasure_code.go)

### Summary
`DataRecovery.RecoverPolynomialCoefficients` computes the full 8192-length coefficient vector implied by the supplied cell evaluations and then silently truncates it to `numScalarsInDataWord` (4096) coefficients without ever checking that the discarded upper half is zero. `Context.RecoverCells` / `Context.RecoverCellsAndComputeKZGProofs` (`api_eip.go`, `api_eip7594.go`) call this function and never re-verify that the recovered, truncated polynomial reproduces the caller-supplied cell values, so an attacker-chosen cell set that is not an evaluation of any degree<4096 polynomial is silently accepted.

### Finding Description
The invariant this code is supposed to preserve is: for every supplied `cellIDs[i]`, `recovered[cellIDs[i]] == cells[i]`, and the recovered polynomial has degree < `ScalarsPerBlob` (4096).

Tracing `Context.RecoverCells` (`api_eip.go:8`) → `ctx.recoverPolynomialCoeffs` (`api_eip7594.go:97`) → `ctx.dataRecovery.RecoverPolynomialCoefficients` (`internal/erasure_code/erasure_code.go:110`):

- `recoverPolynomialCoeffs` only validates: `len(cellIDs)==len(cells)`, ascending order, `cellID < CellsPerExtBlob`, and a minimum count (`NumBlocksNeededToReconstruct`) — [1](#0-0) . None of these checks constrain the *values* of the cells, only their count/position.
- Inside `RecoverPolynomialCoefficients`, the erasure-decoding algorithm computes `cosetQuotientEval`, a length-`numScalarsInCodeword` (8192) vector, then does:
```go
polyCoeff := cosetQuotientEval[:dr.numScalarsInDataWord]
return polyCoeff, nil
``` [2](#0-1) 
There is no check that `cosetQuotientEval[dr.numScalarsInDataWord:]` are all zero. The algorithm's correctness (recovering the unique degree<4096 polynomial) is only guaranteed *if* the input evaluations actually come from such a polynomial. If a caller submits `cells` that are not evaluations of any degree<4096 polynomial (e.g., supplying all 128 cells with arbitrary field-element content, so `missingCellIds` is empty and no redundancy constraint is enforced at all — see `internal/erasure_code/erasure_code.go:75-90` where the vanishing polynomial for an empty missing-set is the constant `1`), the true interpolant has degree up to 8191, and the truncation to the first 4096 coefficients silently discards a nonzero high half.

The resulting truncated `polyCoeff` is then fed into `computeCellsFromPolyCoeff` (`api_eip7594.go:58`) to regenerate cells/proofs. Because the true (untruncated) interpolant differs from the truncated one, re-evaluating the truncated polynomial at the coset points corresponding to the attacker's originally supplied `cellIDs` will **not** reproduce the original `cells[i]` values — breaking `recovered[cellIDs[i]] == cells[i]` — yet no error is returned anywhere in the call chain (`recoverPolynomialCoeffs`, `RecoverCells`, `RecoverCellsAndComputeKZGProofs`). None of the existing guards (`isAscending`, `cellID < CellsPerExtBlob`, `NumBlocksNeededToReconstruct` count check) inspect coefficient values or perform any round-trip consistency check, so the divergence occurs unconditionally before/without any value-level guard.

### Impact Explanation
`go-eth-kzg` will accept a cell set and emit "recovered" cells/proofs for input that a spec-faithful implementation (which is expected to guarantee the recovered polynomial has degree < `ScalarsPerBlob` and matches all supplied cells) would either reject or handle differently. This is a client-diverging output for the same input: two conformant implementations (or `go-eth-kzg` vs. its own documented invariant) can produce different cells/proofs for identical attacker-supplied cell data, which is categorized as High under "library and consensus spec/c-kzg disagree on ... emitted commitment/proof/cell/recovered data for the same input." This is repeatable by any caller of `RecoverCells`/`RecoverCellsAndComputeKZGProofs` with arbitrary in-protocol cell bytes.

### Likelihood Explanation
Requires only calling a public, unprivileged method (`RecoverCells` / `RecoverCellsAndComputeKZGProofs`) with attacker-authored cell bytes satisfying only the cheap structural checks (correct count, ascending, in-range IDs) — no cryptographic material or privileged access is needed. Feasibility of actually constructing field elements whose recovered interpolant has nonzero high coefficients is straightforward, e.g., providing all 128 cells with values not derived from an IFFT of any degree-4096 polynomial (trivial: pick 8192 arbitrary field elements). This is fully repeatable on demand.

### Recommendation
After computing `cosetQuotientEval` in `RecoverPolynomialCoefficients`, verify that all coefficients at index ≥ `numScalarsInDataWord` are zero (reject with an error otherwise), and/or after truncation, re-encode the truncated polynomial and confirm it reproduces the exact evaluations for all supplied (non-missing) `cellIDs`/cells before returning success, mirroring the round-trip guarantee expected by the consensus spec/c-kzg.

func (ctx *Context) recoverPolynomialCoeffs(cellIDs []uint64, cells []*Cell) ([]fr.Element, error) {
