### Title
Missing delegatecall guard on the bank precompile's `send` method breaks the pointer-authorization boundary - (File: precompiles/bank/bank.go)

### Summary
Every state-changing precompile method in sei-chain enforces two independent boundaries before mutating state: a `readOnly` (STATICCALL) guard and a `ctx.EVMPrecompileCalledFromDelegateCall()` (DELEGATECALL) guard [1](#0-0) . The bank precompile's `sendNative` method follows this pattern exactly [2](#0-1) . Its sibling `send` method — the entry point through which a registered ERC20-native pointer contract moves native `usei` on behalf of arbitrary addresses — implements only the `readOnly` half of the guard and omits the delegatecall check entirely [3](#0-2) .

### Finding Description
The `send` executor authorizes the transfer solely by comparing the precompile's `caller` argument against the registered ERC20-native pointer address for the denom being moved: [4](#0-3) 

Unlike every other state-changing dispatch path in the codebase (`sendNative` in the same file, and every method in staking/distribution/pointer), `send` never checks `ctx.EVMPrecompileCalledFromDelegateCall()` before performing `p.bankMsgServer.Send`, which moves funds between the two addresses supplied in calldata [5](#0-4) . The `isFromDelegateCall` flag is threaded into the context at the dispatch layer for exactly this purpose [6](#0-5) [7](#0-6) , and the project's own regression suite treats an absent delegatecall guard as a defect worth testing for on every other precompile (e.g. `TestStakingPrecompileDelegateCallPrevention`) [8](#0-7) , and the integration spec suite documents this as an intentional, precompile-wide invariant to be copied per method [9](#0-8) . `bank.send` is the one state-mutating method that breaks this invariant.

This is the same bug class as CVE-2019-1003029: a sandbox/authorization boundary that is correctly enforced in one code path (`GroovySandbox.java`/`sendNative`) but missing in a sibling code path that reaches the same privileged operation (`SecureGroovyScript.java`/`send`), letting a caller reach the privileged operation through the path where the check was omitted.

### Impact Explanation
`send` is the sole gate that lets an ERC20-native pointer contract move real `usei` balances between two arbitrary Sei addresses supplied as calldata [10](#0-9) . If the identity-preservation semantics of `caller` across a DELEGATECALL dispatch into this method allow an unprivileged contract to present an identity accepted by the `pointer.Cmp(caller)` check (for example through an unaudited or attacker-influenced pointer/proxy contract that itself is delegatecalled into, or through future precompile-dispatch changes that alias `caller`/`callingContract` under DELEGATECALL), the missing guard would allow unauthorized native-token transfers, i.e. fund theft — a Critical-class impact matching the "unauthorized transfer via precompile" category in scope.

### Likelihood Explanation
Exploitability strictly depends on how the EVM interpreter computes and preserves the `caller` vs `callingContract` values specifically for the bank precompile address (0x1001) under a DELEGATECALL frame — code for that dispatch path (in `x/evm`) was not found in the indexed content available to this analysis, so I cannot confirm whether `caller` can be made to equal a registered pointer address without that pointer contract itself performing the call. This is a real, root-cause-provable **inconsistency** (missing guard present on every comparable method), but full exploitability is **unconfirmed** pending review of the EVM interpreter's delegatecall dispatch code for precompiles.

### Recommendation
Add the same `ctx.EVMPrecompileCalledFromDelegateCall()` rejection to `send` that `sendNative` already has, at `precompiles/bank/bank.go` inside the `send` function, mirroring the pattern used by `sendNative` and every other state-changing precompile method.

### Proof of Concept
Not executed — reachability requires confirming, from `x/evm`'s EVM interpreter, how `caller`/`callingContract` are populated for a DELEGATECALL into the bank precompile so that `pointer.Cmp(caller)` in `send` could accept an unauthorized caller. This code path could not be located in the available index; a Devin session with full repository access to `x/evm` would be needed to trace `RunAndCalculateGas`'s callers and confirm or refute exploitability before treating this beyond a "needs validation" inconsistency finding.

func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, uint64, error) {
	if readOnly {
		return nil, 0, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, 0, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, 0, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
