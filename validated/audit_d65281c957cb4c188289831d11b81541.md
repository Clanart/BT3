Based on my research, I found a concrete analog in the precompile layer's handling of `msg.value` (called `contract.Value()` in the codebase).

### Title
Precompiles (gov, staking, distribution, slashing, bank, ics20) accept `msg.value` on non-payable methods with no validation, refund, or accounting path, permanently trapping user funds - (File: `precompiles/gov/gov.go`, `precompiles/staking/staking.go`, `precompiles/distribution/distribution.go`, `precompiles/slashing/slashing.go`, `precompiles/bank/bank.go`, `precompiles/ics20/ics20.go`)

### Summary
The Golom `fillAsk()` bug is a missing-strict-equality check on `msg.value` that lets excess ETH become permanently locked because the contract only ever spends the exact required amount and has no mechanism to return or account for the rest. The Cosmos EVM analog is broader: several stateful precompiles never inspect, validate, or refund `contract.Value()` at all, even though the standard go-ethereum `Call` path transfers that value from the caller to the precompile's address before `Run()` executes.

### Finding Description
Only two of the precompiles explicitly deal with `contract.Value()`:
- `precompiles/erc20/erc20.go` rejects any non-zero value with `ErrCannotReceiveFunds` [1](#0-0) 
- `precompiles/werc20/tx.go`'s `Deposit` explicitly reads `contract.Value()` and sends the coins back to the caller via `BankKeeper.SendCoins` [2](#0-1) 

All other stateful precompiles' `Execute` dispatchers (`gov.go`, `staking.go`, `distribution.go`, `slashing.go`, `bank.go`, `ics20.go`) never call `contract.Value()`, never validate it, and never reconcile it: [3](#0-2) [4](#0-3) [5](#0-4) 

For example, `gov.Deposit` and `gov.SubmitProposal` derive the deposited coin amount purely from the ABI `args` (the `Coin[]` parameter), and move funds via `p.govMsgServer.Deposit(ctx, msg)` / `SubmitProposal` — completely independent of any native value attached to the call: [6](#0-5) 

Because the go-ethereum EVM `Call` semantics unconditionally transfer `value` from the caller to the callee address (the precompile's fixed hex address) prior to invoking `Run`, any `msg.value` a caller mistakenly (or a malicious frontend/dApp deliberately) attaches to a call into `staking.delegate()`, `gov.deposit()`, `distribution.*`, `slashing.unjail()`, `bank.*`, or `ics20.transfer()` is transferred to the precompile's account balance. None of these precompiles read or use that value, and unlike `werc20.Deposit`, none of them refund it back to the caller. The `BalanceHandler` mechanism in `precompiles/common/balance_handler.go` only reacts to explicit bank `CoinSpent`/`CoinReceived` events generated by the precompile's own `bankKeeper` calls [7](#0-6)  — it does not automatically detect or reverse the native EVM-level value transfer that occurred as part of the call itself, since that transfer is not initiated by a bank keeper call in the precompile logic.

The result: value sent to these precompile addresses accumulates in accounts that have no corresponding withdraw/sweep function, since these are fixed system-precompile addresses, not user- or module-controlled accounts with any exit path.

### Impact Explanation
This matches the "Critical permanent freezing/locking of user funds" allowed-impact category. Unlike the Golom case where only the *excess* over the required amount is locked, here the *entire* attached value can be trapped for any of these precompiles' methods, since none of them require or expect payment. Given how common it is for wallets/dApps to attach `value` to transactions (or for users to be confused about `payable` vs non-payable semantics, especially around the "deposit"-sounding `gov.deposit()` method), this is a realistic vector for accidental, irreversible loss of user native tokens with no privileged access required.

### Likelihood Explanation
Triggerable by any unprivileged EOA or contract simply by calling a precompile method (e.g. `gov.deposit()`, `staking.delegate()`) with a non-zero `msg.value`/`{value: ...}` override — no special conditions, front-running, or validator/relayer collusion needed. The `erc20` precompile's explicit `ErrCannotReceiveFunds` guard demonstrates the team is aware value-handling on precompiles needs explicit treatment, but the guard/refund pattern was not consistently applied to `gov`, `staking`, `distribution`, `slashing`, `bank`, and `ics20`.

### Recommendation
Apply the same defensive pattern uniformly across all precompiles that are not intentionally payable:
- Add a `contract.Value().Sign() == 1` check at the start of `Execute` for `gov`, `staking`, `distribution`, `slashing`, `bank`, and `ics20` precompiles, reverting with an error like `ErrCannotReceiveFunds` (as already done in `erc20/erc20.go`), OR
- If some flows are intended to accept value (unlikely for these modules), explicitly refund/account for `contract.Value()` symmetrically to `werc20.Deposit`.

### Proof of Concept
1. Deploy/call `staking` precompile's `delegate(...)` (or `gov`'s `deposit(...)`) from an EOA, attaching `msg.value > 0` via an Ethereum transaction (`to: <precompile address>, value: X, data: <encoded delegate/deposit call>`).
2. Observe that `staking.Delegate`/`gov.Deposit` execute successfully using only the ABI-specified coin amounts, ignoring `contract.Value()` entirely (see `precompiles/gov/tx.go` lines 57-84 and `precompiles/staking/staking.go` lines 99-139).
3. The native value `X` is transferred to the fixed precompile address by standard EVM `Call` value-transfer semantics, but no code path in these precompiles moves it elsewhere or returns it.
4. Since the precompile address has no user-controlled withdraw function, `X` becomes permanently unrecoverable — unlike `werc20.Deposit`, which explicitly returns `contract.Value()` to the caller (`precompiles/werc20/tx.go` lines 26-57), and unlike `erc20`, which reverts on any non-zero value (`precompiles/erc20/erc20.go` lines 148-155).

Note: I was not able to fully trace, within the available tool budget, the exact low-level `Transfer`/`CanTransfer` implementation wired into the EVM configuration (i.e., whether native value sent to a precompile call is applied via `StateDB.AddBalance` directly or is additionally synchronized through the bank keeper at block-commit time). This affects whether the locked value is truly "permanently" unrecoverable at the bank-module level versus merely inaccessible through any precompile-exposed function. I recommend a Devin session with full repository access to confirm the exact value-transfer/commit mechanics for precompile calls before finalizing severity, and to implement the guard/refund fix consistently across the affected precompiles.

// Deposit handles the payable deposit function. It retrieves the deposited amount
// and sends it back to the sender using the bank keeper.
func (p Precompile) Deposit(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
) ([]byte, error) {
	caller := contract.Caller()
	depositedAmount := contract.Value()

	callerAccAddress := sdk.AccAddress(caller.Bytes())
	precompileAccAddr := sdk.AccAddress(p.Address().Bytes())

	// Send the coins back to the sender
	if err := p.BankKeeper.SendCoins(
		ctx,
		precompileAccAddr,
		callerAccAddress,
		sdk.NewCoins(sdk.Coin{
			Denom:  evmtypes.GetEVMCoinExtendedDenom(),
			Amount: math.NewIntFromBigInt(depositedAmount.ToBig()),
		}),
	); err != nil {
		return nil, err
	}

	if err := p.EmitDepositEvent(ctx, stateDB, caller, depositedAmount.ToBig()); err != nil {
		return nil, err
	}

	return nil, nil
}

// Deposit defines a method to add a deposit on a specific proposal.
func (p *Precompile) Deposit(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
	method *abi.Method,
	args []interface{},
) ([]byte, error) {
	msg, depositorHexAddr, err := NewMsgDeposit(args, p.addrCdc)
	if err != nil {
		return nil, err
	}

	msgSender := contract.Caller()
	if msgSender != depositorHexAddr {
		return nil, fmt.Errorf(cmn.ErrRequesterIsNotMsgSender, msgSender.String(), depositorHexAddr.String())
	}

	if _, err = p.govMsgServer.Deposit(ctx, msg); err != nil {
		return nil, err
	}

	if err = p.EmitDepositEvent(ctx, stateDB, depositorHexAddr, msg.ProposalId, msg.Amount); err != nil {
		return nil, err
	}

	return method.Outputs.Pack(true)
}

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
