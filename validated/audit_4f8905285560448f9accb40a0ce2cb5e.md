### Title
Attacker-controlled offset and TxOut in `ReceivedOutput::read` let untrusted bytes write a spendable-by-attacker output into Serai's owned-output set - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`ReceivedOutput::read` deserializes three fully attacker-controlled fields — a scalar `offset`, a `TxOut`, and an `OutPoint` — and constructs a `ReceivedOutput`, which Serai treats as funds owned by and spendable by the threshold group. No check ties the serialized `offset` to the `script_pubkey` embedded in the serialized `output`. Downstream, `Output::key` (processor) derives the presumed spend key as `script_pubkey_point - G * offset`, i.e., the attacker-supplied scalar is blindly applied as a privileged key-derivation write. This is the same class as CVE-2016-4565: a plain data channel (`read`, analogous to the `write(2)` uAPI) is used to smuggle a primitive (`offset`) that performs a privileged state mutation — defining which private scalar is believed to control the funds — with no validation of that write against the actual output.

### Finding Description

In `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134), the `offset` scalar is read via `Secp256k1::read_F(r)` and stored verbatim; the `TxOut` (which includes `script_pubkey` and `value`) and `OutPoint` are consensus-decoded verbatim. There is no consistency check that `p2tr_script_buf(group_key + G*offset) == output.script_pubkey` — the only place such a binding exists is `Scanner::register_offset`/`Scanner::scan_transaction` (wallet/mod.rs:180-214), which builds `ReceivedOutput` internally from the `scripts` map. Once deserialized, nothing distinguishes a scanner-produced `ReceivedOutput` from an attacker-forged byte stream.

The privileged effect of this attacker-controlled write materializes in the processor: `Output::key` computes `Secp256k1::read_G(script_pubkey_xonly) - G * self.output.offset()` (processor/src/networks/bitcoin.rs:112-122), and `Output::balance`/`id` report the output as received funds of that key (processor/src/networks/bitcoin.rs:92-130). Signing for that output then offsets the `ThresholdView` by the same attacker-chosen scalar via `ThresholdKeys::offset`/`tweak_keys` (wallet/mod.rs:46-75). The serialized `offset` field therefore functions exactly like the kernel write primitive in the CVE: untrusted bytes submitted through a data interface silently reprogram which key is believed to own the funds.

### Impact Explanation

An unprivileged party who can feed bytes to `ReceivedOutput::read` (explicitly an in-scope reachable sink) can cause Serai to report funds as received that are not spendable by the group. Concretely, the attacker crafts a `TxOut` whose `script_pubkey` pays to a Taproot key the *attacker* controls, pairs it with any `offset`, and the resulting `ReceivedOutput`/`Output` reports `balance()` and a `key()` consistent with `P_script - G*offset`. The group believes it received `value` sats; in reality the UTXO's script_pubkey belongs to the attacker, who spends it unilaterally. Alternatively, with a legitimate-looking `script_pubkey` and a mismatched `offset`, the derived spend scalar is wrong and any attempted spend signs with the wrong key, producing unspendable "received" funds — a direct loss-of-funds-reporting integrity violation (High).

### Likelihood Explanation

Reachability is defined by scope: untrusted bytes flowing into `ReceivedOutput::read` propagate the forged `offset`/`TxOut` into `Output::key`, `balance`, and the signing path without any re-validation. The only requirement is that the deployment accepts serialized `ReceivedOutput`s from a party who isn't the group itself; no collusion, malicious validator, or leaked key is needed. Deterministic exploitation: the attacker controls every field and simply needs a syntactically valid encoding.

### Recommendation

Bind the offset to the output at deserialization or first use: after `ReceivedOutput::read` (or in `Output::key`), verify `p2tr_script_buf(group_key + G*offset) == output.script_pubkey` and reject on mismatch, mirroring the `scripts` map check in `Scanner`. Alternatively, store only `(outpoint, TxOut)` and recover the offset exclusively by `scripts.get(&script_pubkey)` lookup at use time, removing the attacker-writable scalar entirely — i.e., stop letting the data channel perform the privileged offset write.

### Proof of Concept

```rust
// networks/bitcoin/src/wallet/mod.rs context
use bitcoin::{TxOut, OutPoint, ScriptBuf, key::XOnlyPublicKey, consensus::encode::serialize};
use k256::{Scalar, ProjectivePoint, elliptic_curve::group::GroupEncoding};

// Attacker picks their own key pair.
let attacker_scalar = Scalar::from(0xdeadbeefu64);
let attacker_point = ProjectivePoint::GENERATOR * attacker_scalar;

// Build a P2TR script_pubkey paying to the ATTACKER's key (even-Y assumed).
let script: ScriptBuf = /* p2tr of attacker_point */;
let forged_output = TxOut { value: /* 1 BTC in sats */.into(), script_pubkey: script };

// Any offset will do — it is never checked against script_pubkey.
let offset = Scalar::ZERO;
let outpoint = OutPoint::null(); // or any plausible outpoint

// Serialize as ReceivedOutput::read expects: F || TxOut || OutPoint
let mut bytes = offset.to_bytes().to_vec();
bytes.extend(serialize(&forged_output));
bytes.extend(serialize(&outpoint));

// Victim deserializes untrusted bytes:
let ro = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// -> ReceivedOutput { offset: 0, output: pays-to-attacker, outpoint }
// Output::key() (processor/src/networks/bitcoin.rs:112) returns
//    attacker_point - G*0 = attacker_point, and balance() reports 1 BTC received.
// Serai credits funds it cannot spend; the attacker spends the UTXO with
// attacker_scalar independently.
```
