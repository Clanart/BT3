### Title
Malicious FROST preprocess forces aggregate nonce to the point at infinity, panicking honest signers in `Hram::hram` - ([File: networks/bitcoin/src/crypto.rs])

### Summary
Analog to CVE-2021-34147 (crafted protocol message → crash/DoS): a FROST participant who supplies a crafted preprocess message can force the aggregate nonce commitment `R` to the point at infinity. `Ciphersuite::read_G` accepts the identity element as a canonical encoding, so `read_preprocess` admits it, and `Schnorr::sign_share` → `Hram::hram` → `x()` then panics via `.expect("point at infinity")`, crashing the honest signer/validator mid-protocol. Repeating the attempt on each signing session exhausts availability of the threshold-signing process, mirroring the BrakTooth malformed-response + reconnection crash class.

### Finding Description
In `crypto/frost/src/sign.rs`, `AlgorithmSignMachine::read_preprocess` deserializes a peer's `Commitments` — the `(D, E)` nonce-commitment points — via `Commitments::read`, which calls `Curve::read_G` (`crypto/frost/src/nonce.rs:34-36`, `crypto/frost/src/sign.rs:276-281`). `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) only checks that the encoding round-trips canonically; the identity element is a canonical encoding, so it is accepted.

During `sign`, the binding factor `rho` is derived from all preprocesses, and each participant's effective commitment is `D + rho*E` (`B.nonces`, `crypto/frost/src/sign.rs:371-383`). An attacker who sets `E` to the identity makes `rho*E` the identity, so their contribution reduces to `D` regardless of `rho`. Because all other participants' preprocesses are known before `sign` is invoked, the attacker sets `D = -(sum of the other signers' effective commitments)`, forcing `R = nonce_sums[0][0]` to the point at infinity.

`Schnorr::sign_share` then calls `H::hram(&nonce_sums[0][0], &params.group_key(), msg)` (`crypto/frost/src/algorithm.rs:208`). The Bitcoin implementation `Hram::hram` calls `x(R)` (`networks/bitcoin/src/crypto.rs:65`), and `x()` executes `encoded.x().expect("point at infinity")` (`networks/bitcoin/src/crypto.rs:15`), panicking. The same panic path is reachable in `verify`/`verify_share` during `complete` (`crypto/frost/src/algorithm.rs:214-230`, `crypto/frost/src/sign.rs:465-487`). The code documents that infinity nonces "may panic" and claims negligible probability "even with malicious participants," but that reasoning assumes random nonces — a malicious signer deterministically chooses `D`/`E` in the preprocess, which is exactly untrusted bytes fed to `read_preprocess`.

### Impact Explanation
A single malicious preprocess crashes the signing process of every honest participant that calls `sign` on it. Repeated across sessions (the analog of the CVE's "multiple reconnections"), the attacker permanently prevents the multisig from producing signatures — e.g., halting Bitcoin `TransactionMachine` signing (`networks/bitcoin/src/wallet/send.rs:351-398`) — a medium-severity availability loss reachable entirely with public protocol bytes.

### Likelihood Explanation
Any party able to submit a preprocess to a signing session (a validator in the set, or anyone whose bytes reach `read_preprocess`) can mount this with a trivially constructed message: `E` = identity encoding, `D` = negation of the others' summed commitments. No collusion, leaked keys, or broken trust assumptions are required. One caveat: whether `read_G` accepts the identity depends on each curve's `GroupEncoding` — it clearly holds for Ristretto/dalek; for k256-encoded secp256k1 the infinity encoding (`0x00` prefix) acceptance should be verified, though the panic path exists regardless and may also be reachable via internally inconsistent `(D, E)` pairs summing to infinity.

### Recommendation
- Reject the identity element in `Commitments::read` / `NonceCommitments::read` (`crypto/frost/src/nonce.rs`), since a valid FROST nonce commitment is never the identity.
- Additionally, make `x()`/`x_only()` in `networks/bitcoin/src/crypto.rs` and `Hram::hram` return `Option`/`Result` instead of panicking, and have `Algorithm::sign_share`/`verify` propagate an error rather than aborting the process.
- Optionally check the aggregated `R` for identity in `AlgorithmSignMachine::sign` after `B.nonces` and return `FrostError` instead of proceeding.

### Proof of Concept
1. Honest signer creates `AlgorithmSignMachine<Secp256k1, Schnorr>` (or `TransactionSignMachine`) with threshold keys where the attacker controls `Participant` `l_a`.
2. Attacker calls `machine_i.read_preprocess` on honest machines' preprocesses, learns each `D_j, E_j`, computes each `rho_j`, and publishes a preprocess encoding `E_a = identity` (the canonical 33-byte `0x00..` encoding for secp256k1 / 32 zero bytes for Ristretto) and `D_a = -(Σ_j (D_j + rho_j·E_j))`.
3. Honest signer calls `read_preprocess` (succeeds — encodings canonical) then `sign`. `B.nonces` yields `R = identity`; `Schnorr::sign_share` calls `Hram::hram` → `x(&identity)` → `expect("point at infinity")` panics, aborting the process.
4. Repeat per session for persistent denial of signing.
