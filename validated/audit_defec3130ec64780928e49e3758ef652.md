### Title
Unchecked `git ls-tree` output allows corrupted `--cacheinfo` staging in `applyPatchToIndex` - (File: `app/src/lib/git/apply.ts`)

### Summary
`applyPatchToIndex` in `app/src/lib/git/apply.ts` mirrors the ERC20 bug class exactly: it treats a successful process exit code as proof that the *semantic content* of the result was valid, without validating that content. Just as an ERC20 `transfer()` can return `false` (or nothing) while the caller assumes success, `git ls-tree HEAD -- <oldPath>` can exit `0` with **empty stdout** when the old path doesn't exist at `HEAD`. The code blindly destructures that empty string into `mode`/`oid` and feeds them into `git update-index --add --cacheinfo`, corrupting the index entry for the file the user is about to commit.

### Finding Description
When a user performs a partial (line-by-line) commit of a renamed file, `stageFiles` -> `applyPatchToIndex` runs: [1](#0-0) 

The `git()` wrapper only validates the process **exit code** against `successExitCodes` (default `{0}`) — it never inspects whether `stdout` actually contains the expected `<mode> SP <type> SP <object> TAB <file>` record: [2](#0-1) 

`git ls-tree HEAD -- <path>` legitimately exits `0` with empty stdout whenever the path is not present in `HEAD` (e.g., it was never committed, or the app's rename detection disagrees with what's actually in the tree). In that case:
```
const [info] = oldFile.stdout.split('\t', 1)   // info === ''
const [mode, , oid] = info.split(' ', 3)       // mode === '', oid === undefined
```
Both `mode` and `oid` are then passed straight into `git update-index --add --cacheinfo mode oid file.path` with no validation that they are non-empty, well-formed values — the exact analog of "callers MUST handle false/empty return values" from the ERC20 report, applied to git's structured stdout instead of an ERC20 boolean.

The `Renamed` status itself is derived from `git status`'s rename detection, which is a heuristic based on content similarity thresholds, not an authoritative record. `WorkingDirectoryFileChange` status objects (including `oldPath`) ultimately originate from parsing status output for a working tree that can be populated by an attacker-controlled clone/fetch — e.g. a repository engineered so Desktop's rename heuristic pairs a new file with an "old path" that doesn't actually exist at `HEAD` (such as via case-only renames on case-insensitive filesystems, or content shuffled across commits to fool the similarity heuristic). There is no guard in `applyPatchToIndex` requiring `oldFile.stdout` to be non-empty or matching the expected `<mode> <type> <object>\t<file>` shape before it is consumed.

### Impact Explanation
If `mode`/`oid` end up empty or malformed, `git update-index --add --cacheinfo <mode> <oid> <file.path>` either fails loudly (best case) or, depending on git's leniency, can insert a bogus/incomplete index entry. Since this happens inside the "blow away and rebuild the index" flow used for every partial-selection commit (`stageFiles` -> `applyPatchToIndex`), a corrupted cacheinfo entry directly affects **what the user actually commits and pushes** — the core invariant this bug class protects. This can silently desync the committed tree from what the user believes they selected in the Changes view, without any error surfaced to the user (the outer `git()` call may still succeed if git tolerates the malformed cacheinfo, or throw a generic-looking error that gives no indication the root cause was an empty `ls-tree` result).

### Likelihood Explanation
This requires no local access, admin rights, or prior compromise — only that the user open/clone/fetch a repository engineered by an attacker and then perform a partial-line commit on a file that Desktop's status parser classifies as `Renamed` while `git ls-tree HEAD` disagrees about the old path's existence. Git's rename detection in `git status`/`git diff` is a similarity heuristic (not authoritative), so crafting inputs that trigger a `Renamed` classification not perfectly backed by `HEAD` state is a known class of git edge cases (case-folding renames, partial-content moves across merges, etc.), making this plausible but requiring specific repository construction — hence a moderate, not trivial, likelihood.

### Recommendation
Validate the `ls-tree` output in `applyPatchToIndex` before use: check that `oldFile.stdout` is non-empty and matches the expected `<mode> <type> <object>\t<file>` pattern (e.g. via a strict regex), and throw a clear, actionable error (rather than silently proceeding to `update-index --add --cacheinfo`) if the shape is unexpected. This mirrors "callers MUST handle false/empty returns" for git's structured output, not just its exit code.

### Proof of Concept
1. Construct a malicious repository where a working-tree file is classified by Desktop's status/rename heuristic as `AppFileStatusKind.Renamed` with `oldPath = X`, but `X` does not exist in the current `HEAD` tree (e.g., due to a prior commit removing it via a case-only rename on a case-insensitive filesystem, or content-similarity heuristics pairing unrelated files).
2. Victim clones/fetches this repository in GitHub Desktop and opens the Changes view; the file shows as renamed with partial hunks available for selection.
3. Victim selects a subset of lines to stage (partial commit) and commits.
4. `stageFiles` invokes `applyPatchToIndex`, which runs `git ls-tree HEAD -- X`; because `X` isn't in `HEAD`, stdout is empty.
5. `mode`/`oid` are derived from the empty string and passed to `git update-index --add --cacheinfo <mode> <oid> <file.path>` without validation, corrupting the staged index entry for the new file path before the commit is created — with no error surfaced in the normal case where git still exits `0`.
