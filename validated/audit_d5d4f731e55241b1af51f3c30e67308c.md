Confirmed: `purchase()` in `BandwidthManager.sol` is fully permissionless and lets any caller specify an arbitrary `app` recipient, unrelated to the payer. Combined with the pallet's fixed 1024-slot FIFO eviction, this gives an unprivileged attacker a way to destroy another app's already-paid-for bandwidth.

### Title
Permissionless `purchase()` lets an attacker evict a victim app's paid bandwidth subscriptions via FIFO-cap griefing - ([File: evm/src/apps/BandwidthManager.sol])

### Summary
`BandwidthManager.purchase()` takes an arbitrary `app` byte-string chosen by `msg.sender` with no ownership check, and `pallet-bandwidth`'s `push_subscription` unconditionally evicts the oldest subscription once an `(app_chain, app)` FIFO list hits its 1024-entry cap. An attacker can spam the cheapest configured tier against a victim app's `(chain, app)` key until the list fills, then continue purchasing to evict the victim's genuine, unexpired, large-byte subscriptions one at a time — permanently destroying bandwidth the victim already paid for, with no way to recover it.

### Finding Description
`purchase()` is public and unauthenticated with respect to the `app` field: [1](#0-0) 
Any address can pay the (often small) tier price and target any `app`/`chain` pair — this is explicitly documented as a multi-tenant "sponsorship" feature.

On the pallet side, `on_accept` credits a subscription keyed by `(msg.chain, msg.app)` — again taken entirely from attacker-controlled purchase message fields, not from `request.source`/`request.from` identity of the app being credited: [2](#0-1) 

`push_subscription` enforces a hard cap of `MAX_SUBSCRIPTIONS = 1024` per `(chain, app)` key. Once full, every further push evicts index 0 (the oldest, which under FIFO drain order is also the subscription closest to being consumed/valuable) and appends the new one: [3](#0-2) [4](#0-3) 

The eviction is unconditional — it does not distinguish "my own low-value purchase" from "someone else's large, non-expiring purchase"; it only looks at FIFO order. The test suite confirms the exact mechanics (fill to cap, then one more push evicts index 0): [5](#0-4) 

Because `purchase()` doesn't require `msg.sender == app` (by design, to support cross-chain sponsorship, per the docs: "a buyer on Ethereum can credit an app on Base"), an attacker can:
1. Observe a victim app's `(chain, app)` currently holds N valuable, long-duration subscriptions (e.g., from a legitimate large bulk purchase).
2. Call `purchase()` 1024+N times with the cheapest tier and `months = 1`, targeting the victim's exact `(chain, app)` key.
3. Each of the victim's original subscriptions is evicted in FIFO order as the attacker's cheap entries fill and overflow the list, destroying the victim's paid `remaining_bytes` before the victim's own app ever consumes them via the gate.

The gate (`try_consume`) trusts `remaining_bytes` from whatever subscriptions currently exist in the list, with no accounting for who evicted whom or refunding the evicted value: [6](#0-5) 

No existing guard stops this: there is no per-payer/per-purchaser attribution kept on the subscription entry that would let eviction preferentially target the attacker's own low-value purchases; there is no minimum-value protection preventing an attacker from griefing at low tier price relative to the bytes/time destroyed on a victim with a larger tier.

### Impact Explanation
This is a direct loss-of-funds/loss-of-value bug matching the "Bridged assets... bandwidth balances must move exactly once and only to the rightful beneficiary" pivot. A victim app that legitimately purchased and paid for bandwidth (fee-token spent, `BandwidthCredited` emitted) can have that already-paid-for allowance unilaterally destroyed by an unprivileged third party spending comparatively little, without needing to compromise any relayer, prover, admin, or governance actor — the attack is a pure sequence of public `purchase()` calls. The result is the victim's messages get rejected by `BandwidthGate::try_consume` (`GateError::Insufficient`/`NoAllowance`) despite having paid, effectively locking/losing their prepaid balance and disrupting the app's cross-chain message flow.

### Likelihood Explanation
The attack requires only capital equal to `cheapest_tier_price × (1024 - current_list_length + N)` purchases, all through the fully public `purchase()` entrypoint — no privileged role, no malicious relayer/prover, no front-running dependency. It's economically bounded by tier price and the 1024 cap, and the docs themselves note the cap "only happens under pathological repeat-buy behavior," implicitly acknowledging this path is reachable by repeated purchases without addressing the adversarial (non-owner-initiated) case.

### Recommendation
Bind bandwidth credit/eviction accounting to purchaser identity, or otherwise prevent a non-owning purchaser from evicting another payer's subscriptions:
- Require the purchase message to prove `msg.sender`/an authorized relationship to `app` (e.g., signature or `to == app` check) before crediting cross-chain, or
- Segregate subscriptions per `(chain, app, payer)` so eviction only affects the same payer's oldest entries, or
- On eviction, refund/re-credit the evicted `remaining_bytes` pro-rata to a governance-recoverable pool rather than silently discarding it, and/or emit a governance alert/require multi-purchase throttling per `(chain, app)` from non-owner callers.

### Proof of Concept
1. Victim app `A` on chain `C` legitimately buys a large multi-month Tier4 subscription via `BandwidthManager.purchase(A, TierFour, 12, C)` — pallet credits one `Subscription{remaining_bytes: big, expires_at: far_future}` at `Allowance[C][A][0]` (see `on_accept` push path, `modules/pallets/bandwidth/src/lib.rs:454-489`).
2. Attacker calls `BandwidthManager.purchase(A, TierOne, 1, C)` repeatedly (1024 times), each dispatching a `BandwidthPurchaseMsg{app: A, tier: TierOne, months: 1, chain: C}` — nothing in `purchase()` or `on_accept` checks that the caller is `A`'s owner (`evm/src/apps/BandwidthManager.sol:148-163`, `modules/pallets/bandwidth/src/lib.rs:454-489`).
3. Once `Allowance[C][A]` reaches 1024 entries, the attacker's 1025th purchase triggers `push_subscription`'s eviction branch, which `list.remove(0)` — removing the victim's original large subscription and emitting `SubscriptionEvicted{lost_bytes: big}` (`modules/pallets/bandwidth/src/lib.rs:404-437`, mirrored by the test at `modules/pallets/testsuite/src/tests/pallet_bandwidth.rs:523-574`).
4. Victim app `A`'s subsequent ISMP messages now hit `BandwidthGate::try_consume` against only the attacker's cheap remaining entries (or `GateError::NoAllowance`/`Insufficient` once those drain), even though `A` already paid for and never consumed the destroyed allowance.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

			let tier = TierIndex::try_from(msg.tier)

				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

				app: key,

				bytes,
				expires_at,

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}

/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");

		// One more push: evicts the oldest, appends the new one.
		Bandwidth::force_credit(
			RuntimeOrigin::root(),
			ForceCreditParams {
				app_chain: APP_CHAIN,
				app: app_key(),
				tier: TIER1,
				bytes: cap + 1,
				duration_secs: MONTH_SECS,
			},
		)
		.unwrap();

		assert_eq!(sub_count(APP_CHAIN), cap as usize, "still capped");
		assert_eq!(
			sub_at(APP_CHAIN, 0).unwrap().remaining_bytes,
			2,
			"former second-oldest is now front",
		);
		assert_eq!(
			sub_at(APP_CHAIN, (cap - 1) as usize).unwrap().remaining_bytes,
			cap + 1,
			"new sub is at the back",
		);
	});
}
