### Title
Hookify `_matches_tool` performs literal exact-string matching instead of regex/alias matching, silently bypassing block rules for equivalent tool invocations - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._matches_tool` treats `rule.tool_matcher` as a set of literal strings separated by `|`, requiring exact equality with `tool_name`, rather than compiling it as a regex or aliasing functionally-equivalent tools (e.g. `Edit` vs `MultiEdit`). A rule author who writes a `tool_matcher` using regex syntax (a pattern documented and encouraged elsewhere in this same repo for the same "matcher" concept) or who scopes a rule to only one of several equivalent file-editing tools will have their `block` rule silently never trigger for the unmatched representation, letting an attacker who controls which tool gets invoked (e.g. via prompt injection steering the agent to use `MultiEdit` instead of `Edit`, or an MCP tool instead of `Bash`) perform the exact operation the rule intended to block.

### Finding Description
`RuleEngine._matches_tool` at [1](#0-0)  implements matching as:
```python
if matcher == '*':
    return True
patterns = matcher.split('|')
return tool_name in patterns
```
This only supports wildcard `*` or a literal pipe-delimited allowlist of exact tool names — it never treats the matcher as a regular expression, and it never maps semantically-equivalent tools to each other.

This is significant because the same plugin ecosystem in this repo explicitly documents that Claude Code hook "matcher" strings support **regex patterns** and cross-tool groupings, e.g. `"matcher": "mcp__.*__delete.*"` to match "All MCP delete tools" and `"matcher": "Read|Write|Edit"` for "All file operations", as shown in [2](#0-1) . A hookify rule author following this same documented convention (this is the standard mental model used throughout the plugin's own documentation, e.g. `skills/writing-rules/SKILL.md` and `README.md`, for grouping `Edit, Write, MultiEdit` under a single "file" concept) would reasonably write a `tool_matcher` such as `mcp__.*__delete.*` or assume `Edit` also covers `MultiEdit`. Because `_matches_tool` performs only literal equality after splitting on `|`, such regex-style matchers never match any real `tool_name` (e.g. `mcp__github__delete_file` is never equal to the literal string `mcp__.*__delete.*`), and a matcher scoped to `Edit` alone never matches `MultiEdit` tool invocations, even though `pretooluse.py`/`posttooluse.py` both treat `Edit`, `Write`, and `MultiEdit` interchangeably as the `file` event for rule *loading* purposes ( [3](#0-2) ).

The exploit path: an attacker who can influence which tool the agent uses for a given file mutation (e.g., through prompt-injected repository content instructing the agent to prefer `MultiEdit` for "efficiency", or through use of an MCP-provided delete/write tool instead of built-in `Bash`/`Edit`/`Write`) causes `tool_name` to take a representation that is functionally equivalent to the protected operation but textually different from what the rule's `tool_matcher` literally enumerates. `_rule_matches` ( [4](#0-3) ) short-circuits to `return False` as soon as `_matches_tool` fails, so the rule's conditions are never even evaluated, and a rule with `action: block` intended to deny the operation silently allows it through `evaluate_rules` ( [5](#0-4) ).

No existing validation compensates: there is no canonicalization of tool names, no regex compilation for `tool_matcher` (unlike `_regex_match` which is used only for `pattern`/`conditions`, not for `tool_matcher`), and no equivalence table between tools that perform the same class of operation.

### Impact Explanation
A `block` rule meant to prevent dangerous operations (e.g., blocking edits to `.env`/credentials files, or blocking MCP tools that delete/exfiltrate data) can be bypassed simply by the agent using a different, but operationally equivalent, tool representation than the one literally enumerated in `tool_matcher`. This breaks the core hookify safety invariant that "a matching block rule must reliably deny the protected operation," and can lead to sensitive file/credential/token disclosure or destructive operations proceeding unblocked — matching the "Sensitive code, prompt, token, diff, or local file disclosure to an unintended local or remote sink" impact class.

### Likelihood Explanation
This requires a hookify rule to exist with a `tool_matcher` set (an optional, less-common but documented field), and requires the attacker to be able to influence which specific tool call is made for the same conceptual operation (e.g. via prompt injection in repository content that steers the agent's tool choice, which is a normal, already-assumed capability in the described threat model). Given the plugin's own documentation elsewhere teaches regex-style and multi-tool matchers as valid, misconfigured/bypassable rules are a realistic and repeatable occurrence, not a contrived edge case.

### Recommendation
- Compile `tool_matcher` with the same `compile_regex`/`_regex_match` machinery already used for `pattern`/`conditions`, so documented regex matchers (e.g. `mcp__.*__delete.*`) work correctly, or explicitly restrict `tool_matcher` to a documented literal-list-only syntax and update all documentation to remove regex examples for this field.
- Introduce explicit tool-equivalence handling (or require rule authors targeting "file" operations to use `event: file`, which already unions `Edit|Write|MultiEdit`) rather than relying on manually enumerated tool lists in `tool_matcher`.
- Add validation/linting when loading rule files to warn if a `tool_matcher` contains characters typical of regex (`.`, `*`, `(`, `)`) that will not be interpreted as such, to catch this class of silent misconfiguration.

### Proof of Concept
Unit test extending `plugins/hookify/core/rule_engine.py`'s own test harness:
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

engine = RuleEngine()

# Rule author expects this to cover any MCP delete tool (per plugin-dev docs' documented regex matcher convention)
rule = Rule(
    name="block-mcp-delete",
    enabled=True,
    event="all",
    tool_matcher="mcp__.*__delete.*",
    action="block",
    conditions=[Condition(field="file_path", operator="regex_match", pattern=".*")],
    message="Blocked dangerous MCP delete"
)

malicious_input = {
    "tool_name": "mcp__github__delete_file",
    "tool_input": {"file_path": "secrets.env"}
}

result = engine.evaluate_rules([rule], malicious_input)
# Expected (desired): result contains permissionDecision "deny"
# Actual: result == {} because "mcp__github__delete_file" != "mcp__.*__delete.*" (no regex compilation)
assert result == {}, "Demonstrates block rule bypass due to literal tool_matcher matching"
```
A second variant demonstrates the `Edit` vs `MultiEdit` equivalence gap: define `tool_matcher="Edit"` with a condition blocking edits to `.env`, then submit `tool_name="MultiEdit"` with the same sensitive `file_path`/`edits` content and assert the block rule fails to trigger (`result == {}`), while the identical content via `tool_name="Edit"` correctly triggers the block.

```python
    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns
```
