### Title
`SignableTransaction::new` computes fee, minimum-fee, and max-weight checks on a transaction that omits the OP_RETURN `data` output — ([File: `networks/bitcoin/src/wallet/send.rs`])

### Summary
`SignableTransaction::new` pushes the caller-supplied `data` output into `tx_outs`, but `calculate_weight_vbytes` (which computes `weight`/`vbytes` for both the fee estimate and the `MAX_STANDARD_TX_WEIGHT` bound) only receives `payments` and `change`. The resulting `SignableTransaction` therefore embeds an output that was never accounted for: the declared `needed_fee`/`fee_per_vbyte` is understated, the `TooLowFee` minimum-relay check uses a too-small `vbytes`, and the `TooLargeTransaction` check can pass a transaction that actually exceeds `MAX_STANDARD_TX_WEIGHT`. This is the same class as the Lend report: a bound computed over an incomplete aggregate (here, the serialized transaction weight missing the data output) causes the validation to accept/reject on wrong values.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is appended to `tx_outs` before the weight calculation:

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
...
if weight > u64::from(bitcoin::policy::MAX_STANDARD_TX_WEIGHT) {
  Err(TransactionError::TooLargeTransaction)?;
}
```

`calculate_weight_vbytes(inputs, payments, change)` (lines 62–127) rebuilds a `Transaction` containing only the inputs, the `payments` outputs, and optionally `change`. It has no `data` parameter, so the OP_RETURN output — up to ~90 bytes (8-byte value + script + 80-byte push) plus its weight — is simply absent from every derived quantity. `data` is untrusted bytes supplied by the caller (it is the mechanism Serai uses to embed data on Bitcoin; the processor currently passes `None`, but the API is public and reachable by any integrator/user-driven data).

### Impact Explanation
- The actual transaction is heavier than `weight`/`vbytes` used for `needed_fee`, so the real fee rate is lower than the requested `fee_per_vbyte` and can fall below `DEFAULT_MIN_RELAY_TX_FEE` even though the `TooLowFee` check passed — the signed transaction is rejected by Bitcoin Core relay/mempool.
- A transaction sized near `MAX_STANDARD_TX_WEIGHT` passes the `TooLargeTransaction` check yet exceeds the limit once broadcast → non-standard, unbroadcastable.
- In both cases the multisig has produced a transaction that the network will not accept: funds are not spendable via the produced TX, mirroring the "valid operation blocked by an incorrect cap check" impact of the reference finding.

### Likelihood Explanation
Requires the caller to supply `data` — a documented, public input of this API. No malicious peer, validator collusion, or leaked key is needed; the miscounting is deterministic whenever `data.is_some()`.

### Recommendation
Pass the constructed `data` output (or the already-built `tx_outs`) into `calculate_weight_vbytes` so `weight`, `vbytes`, `needed_fee`, the `TooLowFee` bound, and the `MAX_STANDARD_TX_WEIGHT` check all account for every output actually placed in the transaction — including the OP_RETURN and any future output types.

### Proof of Concept
```rust
// With a large number of inputs/payments and an 80-byte OP_RETURN:
let tx = SignableTransaction::new(
    inputs,                       // enough inputs to approach MAX_STANDARD_TX_WEIGHT
    &payments,
    None,
    Some(vec![0u8; 80]),          // OP_RETURN output is added to tx_outs...
    FEE,
).unwrap();                       // ...yet weight/vbytes were computed without it

// tx.tx.weight() > tx.needed_fee() / FEE * 4 — the real vsize exceeds the
// vbytes used for the fee and the standardness check.
```
Any call with `data.is_some()` deterministically under-counts the weight by the size of the OP_RETURN `TxOut` (~`8 + 1 + 1 + 2 + data.len()` bytes of witness-discount-exempt output data), so a borderline `fee_per_vbyte` or borderline weight transaction is accepted when it should have errored with `TooLowFee`/`TooLargeTransaction`, producing a relay-rejected or non-standard transaction.
