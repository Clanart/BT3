### Title
Unchecked payment and fee arithmetic wraps and bypasses the funds check - ([File: `networks/bitcoin/src/wallet/send.rs`](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` uses unchecked `u64` addition and multiplication while calculating total payments, required fees, and change eligibility. An attacker who can cause a Bitcoin transaction plan to contain sufficiently large payment amounts can make `payment_sat` wrap to a small value, causing the insufficient-funds check to pass even though the encoded outputs request vastly more Bitcoin than the inputs contain.

### Finding Description
The vulnerable calculations occur in `SignableTransaction::new`:

- `payment_sat` is computed as an unchecked `sum::<u64>()` over attacker-influenced payment amounts. [1](#0-0) 
- `needed_fee` and `fee_with_change` are calculated with unchecked multiplication. [2](#0-1) [3](#0-2) 
- The funding check uses `payment_sat + needed_fee` without `checked_add`. [4](#0-3) 
- The change calculation also repeats the unchecked `payment_sat + fee_with_change` expression. [5](#0-4) 

For example, two payments of `2^63` satoshis produce `payment_sat == 0` under wrapping arithmetic. The subsequent check compares the actual input total against `0 + needed_fee`, rather than the true requested `2^64`, and accepts the transaction. The resulting `SignableTransaction` retains both huge `TxOut` values and can be signed by `TransactionMachine`. [6](#0-5) 

This is the same root-cause shape as the reported Linux bug: arithmetic performed before validation wraps an extreme value into a small value, causing the later bound check to test the wrapped result instead of the logical size.

### Impact Explanation
The threshold signing machine can be driven to sign a Bitcoin transaction whose output total exceeds the input total. Such a transaction is consensus-invalid and cannot spend the claimed funds. Where the surrounding system treats signing or construction success as validation of a withdrawal/payment plan, this can cause an invalid or unintended transaction to receive threshold signatures and can lock the associated inputs in a failed spend.

Depending on fee calculation parameters, `fee_per_vbyte * vbytes` can also wrap, making `needed_fee` smaller than intended and weakening the explicit fee policy check.

### Likelihood Explanation
The vulnerable function accepts `payments` as a caller-provided slice and only checks each amount against `DUST`; there is no upper bound or checked total. [7](#0-6)  A party able to influence the payment list can provide multiple large outputs whose sum wraps. Exploitation does not require malformed encodings, a malicious peer, leaked shares, or invalid curve points—only extreme values in transaction data supplied to the signing path.

### Recommendation
Use checked arithmetic for every logical money total:

- Replace `sum::<u64>()` for `input_sat` and `payment_sat` with a checked accumulation that returns an overflow error.
- Replace `fee_per_vbyte * vbytes` and `fee_per_vbyte * vbytes_with_change` with `checked_mul`.
- Replace `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`.
- Reject overflowing payments with `TransactionError::NotEnoughFunds` or a distinct `AmountOverflow` error before constructing the transaction.

### Proof of Concept
Conceptually, construct a `SignableTransaction` with one valid `ReceivedOutput` and two payments whose amounts sum modulo `2^64` to a small value:

```rust
// `input` is a normally scanned ReceivedOutput with any ordinary value.
let huge = u64::MAX / 2 + 2;
let payments = vec![
  (payment_script_a, huge),
  (payment_script_b, huge),
];

// payment_sat wraps to 4, so the funding check compares against
// approximately the fee rather than the requested 2**64 satoshis.
let tx = SignableTransaction::new(
  vec![input],
  &payments,
  None,
  None,
  1,
);

// This should be rejected, but is accepted when wrapping arithmetic is used.
assert!(tx.is_ok());
```

The actual constructed transaction still contains the two huge `TxOut`s, while `payment_sat` was only `4` for validation purposes.
