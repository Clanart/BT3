### Title
Attacker-controlled `WWW-Authenticate` header spoofs GitHub Enterprise identity and triggers unauthorized sign-in flow - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The reported bug is a "trust-before-verify" pattern: a value that should only be trusted after being independently verified is instead trusted immediately, letting an external actor drive privileged behavior. The Desktop analog is in the git credential-helper trampoline's `getEndpointKind` function, which classifies a remote endpoint as a GitHub/GitHub Enterprise host based on unauthenticated, attacker-controlled `WWW-Authenticate` header content forwarded by Git, rather than on the endpoint's real identity. This causes Desktop to launch its "Sign in to GitHub Enterprise" flow against an arbitrary host chosen by whoever controls the git server the user is fetching/pushing to.

### Finding Description
When Git needs credentials for an HTTP(S) remote, it invokes the configured `credential.helper` (Desktop sets this to itself via the trampoline, see `app/src/lib/trampoline/trampoline-environment.ts:143`). Git also forwards any `WWW-Authenticate` response headers it received from the remote server as `wwwauth[]=...` fields in the credential-helper protocol input [1](#0-0) .

`getEndpointKind` uses this attacker-supplied header content, before any hostname-based validation, to decide whether the remote is a GitHub Enterprise instance: [2](#0-1) 

Specifically:
```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
```
This loop runs *before* the fallback `isGitHubHost(endpoint)` real-identity check (line 178) is ever reached, so a malicious HTTP git server can simply respond to Git's credential probe with `WWW-Authenticate: Basic realm="GitHub"` on any 401, and Desktop will classify that endpoint as `'enterprise'` regardless of its actual hostname.

Once classified as `'enterprise'`, `getCredential` checks whether an existing account matches the endpoint; if not, it calls `ui.promptForGitHubSignIn(endpoint)` [3](#0-2) , which in turn skips the normal manual-entry step for enterprise endpoints and auto-populates the sign-in flow with the attacker's own domain: [4](#0-3) 

```
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
this.dispatcher.showPopup({
  type: PopupType.SignIn,
  isCredentialHelperSignIn: true,
  credentialHelperUrl: endpoint,
})
```

The broken invariant: `getEndpointKind`'s classification of "is this a GitHub/GHE host" — which gates whether Desktop initiates its GitHub sign-in/OAuth flow and whether it later hands out a stored GitHub token via `credWithAccount` (`app/src/lib/trampoline/trampoline-credential-helper.ts:47-56`) — is derived from data the remote server fully controls (`wwwauth[]`), not from any authenticated or independently-verified property of the endpoint. The legitimate check (`isGHE`/`isDotCom`/`isGitHubHost`) exists precisely to prevent this, but the header-based shortcut is evaluated first and short-circuits it.

### Impact Explanation
This falls in the "unauthorized OAuth or account binding" category: a user who adds/clones/fetches from an attacker-controlled remote (no special privileges, no local access, no leaked credentials required) can be silently steered into a GitHub Enterprise sign-in dialog whose `credentialHelperUrl`/endpoint is the attacker's own server, presented as though it were part of normal git authentication. Because this happens automatically during an ordinary `fetch`/`push`/`clone`, not via a link click or unnatural steps, it satisfies the "attacker controls a git remote/proxy response" impact class. A user who completes this flow (entering a PAT, or completing OAuth device flow) ends up binding real GitHub-style credentials to an endpoint object under attacker control, and any legitimate GitHub token for the actual GitHub host is not sent (the `accounts.some(a => a.endpoint === apiEndpoint)` guard prevents leaking a genuinely stored token to the wrong host), but the sign-in/account-binding step itself is unauthorized and attacker-triggered.

### Likelihood Explanation
Likelihood is moderate: it requires the user to have configured or be interacting with a malicious/compromised git HTTP remote (a realistic scenario — untrusted forks, compromised mirrors, malicious proxies) and for that remote to serve a crafted `WWW-Authenticate` header on a credential challenge, which is trivial for any server operator to do. No additional user action beyond a normal git operation (fetch/push/clone through Desktop) is needed to trigger the misclassification; the only user interaction required for full impact is completing the resulting sign-in dialog.

### Recommendation
Do not trust the `wwwauth[]` realm string as a positive signal that an endpoint is a genuine GitHub/GitHub Enterprise host. At minimum, require the `isGitHubHost` (or equivalent authenticated `/meta`-style) verification to succeed before ever entering the `'enterprise'` classification, and treat the `wwwauth[]` heuristic only as a hint to *route to the correct external-credential-helper flow*, not to decide whether Desktop's own GitHub sign-in/OAuth flow should be launched against an untrusted, attacker-supplied origin.

### Proof of Concept
1. Stand up an HTTP git server (or intercepting proxy) at `https://evil.example.com/x.git`.
2. On any authenticated git request (`git-upload-pack`/`git-receive-pack` probe), have the server respond `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
3. In GitHub Desktop, add this URL as a remote (or clone/fetch it) for a repository the victim uses.
4. Trigger a fetch/push in Desktop. Git invokes the trampoline credential helper with `get`, including `wwwauth[0]=Basic realm="GitHub"` in stdin [1](#0-0) .
5. `getEndpointKind` returns `'enterprise'` without ever calling `isGitHubHost`, and since no account exists for `evil.example.com`, Desktop calls `ui.promptForGitHubSignIn('https://evil.example.com')`, which begins an Enterprise sign-in flow pre-populated with the attacker's origin [5](#0-4) .
6. The victim is shown Desktop's native sign-in dialog for what appears to be a GitHub Enterprise instance at the attacker's domain.

```typescript
const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
```

```typescript
  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
```
