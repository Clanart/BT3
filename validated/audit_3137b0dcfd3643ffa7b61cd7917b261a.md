Any CosmWasm contract that answers a `token_info`/`contract_info` query with a JSON object whose `name`/`symbol` fields are missing or non-string (e.g., a number, `null`, or absent key) will hit this unchecked type assertion, which is a Go runtime panic (`interface conversion: interface {} is nil, not string`), not an `error` return.

I traced the panic-handling for this call path: `DynamicGasPrecompile.RunAndCalculateGas` in `precompiles/common/precompiles.go` only wraps `chargeDecodeGas` with a `recover()`, and that recover only re-raises anything other than an `sdk.ErrorOutOfGas`/`sdk.ErrorGasOverflow` panic. [4](#0-3)  The subsequent call into `d.executor.Execute(...)` (which is `pointer.PrecompileExecutor.Execute` → `AddCW20`/`AddCW721`/`AddCW1155`) is NOT wrapped in any `recover()` in `RunAndCalculateGas`. [5](#0-4)  Unlike other precompiles (e.g. `precompiles/addr`, `precompiles/solo`) that explicitly guard their `Execute` with `defer func(){ recover() ... }()` to convert panics into reverts, the `pointer` precompile's `Execute` has no such guard. [6](#0-5) 

I was not able to fully trace what happens above `RunAndCalculateGas` at the go-ethereum EVM interpreter/`vm.EVM` level within this timeframe (i.e., whether the interpreter's `Call`/`Run` loop for `vm.DynamicGasPrecompiledContract` has its own top-level `recover()` that would catch an unrecovered panic and turn it into a `nil` output / reverted call, versus letting it propagate up through `baseapp`'s tx-level recovery in `sei-cosmos/baseapp/recovery.go`). If the panic is only caught at the `baseapp` DeliverTx level, the transaction fails but the node does not crash; if there is no recovery layer between the EVM interpreter and this point, this could produce a validator-node panic during block processing, which would be consensus-affecting. This distinction is critical for scoring severity (execution-reverted vs. node crash / consensus halt) and could not be confirmed with the tools available — a Devin session with the ability to run/trace the code end-to-end would be needed to determine definitively whether the go-ethereum interpreter or `sei-cosmos` recovery middleware intercepts this panic before it destabilizes the node.

Given this uncertainty about ultimate impact, I can present the finding but flag the severity/likelihood explanation as conditional.

### Title
Unchecked type assertions on attacker-controlled CosmWasm query results in pointer precompile - (File: precompiles/pointer/pointer.go)

### Summary
The `pointer` precompile's `AddCW20Pointer`, `AddCW721Pointer`, and `AddCW1155Pointer` methods let any EVM caller register a permanent ERC pointer to an arbitrary CosmWasm contract address, but they only sanity-check the target by querying `token_info`/`contract_info` and casting the JSON response fields directly to `string` (`formattedRes["name"].(string)`, `formattedRes["symbol"].(string)`), without verifying field existence or type.

### Finding Description
`AddCW20`, `AddCW721`, and `AddCW1155` in `precompiles/pointer/pointer.go` take a CW address supplied entirely by the caller, resolve it, and query it with a hard-coded smart-query payload (`{"token_info":{}}` or `{"contract_info":{}}`). [7](#0-6)  There is no interface/type check on the target contract — analogous to the `updateRouter`/`setRedeemable` issue in the external report, where a contract address is accepted without verifying it implements the expected interface. Here the "interface check" that does exist is an unchecked Go type assertion on parsed JSON: if the returned map lacks a `"name"` or `"symbol"` key, or if those keys hold a non-string JSON value (number, bool, object, array, or `null`), `formattedRes["name"].(string)` panics instead of returning an error. The same defect is repeated identically for `AddCW721` and `AddCW1155`. [8](#0-7) 

Because `cwAddr` is fully attacker-controlled (any bech32 CosmWasm address, including a contract the caller just instantiated), an attacker can deploy a trivial CosmWasm contract whose `token_info`/`contract_info` query handler returns `{"name": 123, "symbol": null}` (or omits the fields), then call `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` on it via the pointer precompile at `0x000000000000000000000000000000000000100b`.

### Impact Explanation
The precompile execution path (`DynamicGasPrecompile.RunAndCalculateGas` in `precompiles/common/precompiles.go`) does not wrap the call into `pointer.PrecompileExecutor.Execute` with a `recover()`, unlike sibling precompiles (`addr`, `solo`) that explicitly guard against panics. [5](#0-4)  This means the panic from the bad type assertion propagates out of the precompile call, into the EVM execution path, and up through whatever calls `RunAndCalculateGas`. Depending on whether an upstream `recover()` exists in the go-ethereum-fork interpreter or only at the `baseapp`/ABCI transaction boundary, this can range from "transaction always fails/reverts" (low impact, availability-only) up to a crash of the node processing the block (validator halt / chain-halt if deterministic across all validators, since every validator executing the same block would hit the identical panic).

### Likelihood Explanation
Any unprivileged EVM account can trigger this: deploying a CosmWasm contract with a controlled `token_info`/`contract_info` query response and invoking the public `pointer` precompile's `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` requires only a standard transaction and no special privileges. This makes the likelihood of triggering the panic itself high; the likelihood that this constitutes a validator/chain-halting bug rather than a merely-reverted transaction depends on the unverified interpreter-level recovery behavior noted above.

### Recommendation
Replace the unchecked type assertions with checked ones (`name, ok := formattedRes["name"].(string); if !ok { return nil, 0, fmt.Errorf(...) }`) in all three functions (`AddCW20`, `AddCW721`, `AddCW1155`) in `precompiles/pointer/pointer.go`, and add a `defer recover()` guard in `pointer.PrecompileExecutor.Execute` (matching the pattern used in `precompiles/addr` and `precompiles/solo`) so that any unexpected panic from malformed CW query responses is converted into a reverted transaction rather than potentially propagating past the precompile boundary.

### Proof of Concept
1. Deploy a CosmWasm contract whose `{"token_info":{}}` (or `{"contract_info":{}}`) query handler returns valid JSON but with `"name"` or `"symbol"` as a non-string value or omitted entirely, e.g. `{"decimals":6,"total_supply":"0"}` (no `name`/`symbol` keys).
2. From any EVM account, call `addCW20Pointer(cwAddr)` (or `addCW721Pointer`/`addCW1155Pointer`) on the pointer precompile at `0x000000000000000000000000000000000000100b`, passing the bech32 address of the contract from step 1.
3. Execution reaches `formattedRes["name"].(string)` in `precompiles/pointer/pointer.go` line 154 (or 186/218), which panics with `interface conversion: interface {} is nil, not string` because the key is absent.
4. Observe that no `recover()` exists between this call site and `DynamicGasPrecompile.RunAndCalculateGas`, so the panic is not converted to a normal precompile-level error as it would be for other precompiles like `addr` or `solo`.
