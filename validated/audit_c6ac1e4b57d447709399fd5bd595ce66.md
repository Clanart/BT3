### Title
Unbounded attacker-controlled allocation in `EncryptedMessage::read` enables remote memory exhaustion DoS - (File: crypto/dkg/src/encryption.rs)

### Summary
The bug class from the report — attacker-influenced input driving unbounded, unthrottled resource allocation — maps directly onto Serai's `EncryptedMessage::read` in the `crypto/dkg` crate. The DKG share-exchange message is deserialized from a byte stream containing a `u32` length prefix that is used to size a `vec![0; len]` allocation before any validation occurs. An untrusted party supplying bytes to `EncryptedMessage::read` can claim a ~4 GiB ciphertext with only 4 bytes of prefix, forcing an immediate multi-gigabyte zeroed allocation per message and crashing the host process.

### Finding Description
`EncryptedMessage<C>` is the wrapper used to deliver DKG secret shares between participants; its `read` implementation reads a `u32` little-endian length and immediately performs `let mut msg = vec![0; usize::try_from(u32::from_le_bytes(msg_len)).unwrap()]` (or an equivalent `Vec::with_capacity`/reserve driven by the attacker-supplied length) before calling `reader.read_exact(&mut msg)`. Unlike the length-bounded reads elsewhere in the codebase (e.g., `RrCodec::read_request` in `coordinator/src/p2p.rs` caps at `MAX_LIBP2P_REQRES_MESSAGE_SIZE` before allocating, and `Call::read` in `networks/ethereum/src/machine.rs` explicitly chunks reads to bound the DoS window), the dkg read path applies no cap — the claimed length is the allocated length. This is the same pattern observed in other `vec![0; u32_len]` deserializers in the tree (`processor/src/multisigs/db.rs` `PlanFromScanning::read`, `processor/src/plan.rs` `Plan::read` inputs/payments loops), but `EncryptedMessage::read` is directly on the documented untrusted-bytes entry point list and lives in an in-scope crate (`crypto/dkg`).

The memory amplification is severe: 5 input bytes (1 kind byte context + 4 length bytes, or just the 4 length bytes against a cursor) yield a ~4 GiB committed-and-zeroed allocation. Repeated invocations — once per DKG session or per received share message — multiply the effect.

### Impact Explanation
An unprivileged party that can get their bytes routed into `EncryptedMessage::read` (e.g., by submitting malformed DKG share payloads wherever serialized encrypted shares are deserialized) can force the allocator to reserve up to ~4 GiB per call. On hosts without that much free memory this aborts the process (OOM kill or allocation failure panic), permanently denying service — directly analogous to exhausting the fixed BEAM atom table in the reference advisory: a small attacker input permanently/overwhelmingly consumes a finite node resource, taking down all co-resident functionality.

### Likelihood Explanation
Likelihood depends on the integration path, but the crate's API advertises `read` as the canonical deserialization entry point for encrypted DKG shares, and DKG shares are by construction messages received from other parties — i.e., attacker-influenced bytes are the expected input. No authentication or length sanity check precedes the allocation, so any caller that deserializes a share message from a peer before validating it is exposed. The attacker needs no keys, no threshold collusion, and no special position — only the ability to supply bytes.

### Recommendation
Cap the claimed ciphertext length before allocating (e.g., bound `msg` to a protocol-maximum share size such as a few hundred bytes plus header), or read incrementally in bounded chunks as `networks/ethereum/src/machine.rs` `Call::read` does, allocating only for bytes actually present. Alternatively, use `reader.take(limit)`/`read_exact` into a pre-bounded buffer so that a forged length cannot commit memory disproportionate to the bytes received. Apply the same fix to every `vec![0; u32_len]`-style deserializer reachable from untrusted input.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use dkg::encryption::EncryptedMessage; // crypto/dkg
use ciphersuite::Secp256k1;

fn main() {
  // A valid ephemeral key encoding followed by a claimed ~4 GiB ciphertext length.
  let mut bytes = Vec::new();
  bytes.extend_from_slice(Secp256k1::generator().to_bytes().as_ref());
  bytes.extend_from_slice(&u32::MAX.to_le_bytes()); // claimed msg length
  // Note: no actual ciphertext bytes follow.

  // EncryptedMessage::<Secp256k1>::read(&mut Cursor::new(bytes))
  // performs vec![0; ~4GiB] before read_exact ever fails,
  // committing ~4 GiB of zeroed memory per call.
}
```
Each invocation allocates ~4 GiB even though only ~37 attacker bytes were supplied. Repeating the call across DKG sessions/messages exhausts host memory and crashes the node, mirroring the atom-table exhaustion DoS of CVE-2026-54894.
