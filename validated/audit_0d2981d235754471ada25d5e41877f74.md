## Title
Missing zero-amount guard in `IntentGatewayV2.withdraw()` permanently locks escrowed order funds on a weird-ERC20 token - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2.withdraw()` iterates over `body.tokens` and unconditionally attempts a low-level `transfer` call for every entry, including entries with `amount == 0`. The mainline EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`) explicitly guards this case with `if (amount == 0) continue;`, but the Tron `IntentGatewayV2.sol` copy of the same withdrawal logic lacks this guard.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` runs: [1](#0-0) 

For each token in `body.tokens`, it calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and reverts the entire function with `TransferFailed()` if that call fails — with no check that `amount > 0` before attempting the transfer.

By contrast, the corresponding logic in the primary EVM codebase already contains the exact mitigation recommended in the external report: [2](#0-1) 

```
uint256 amount = body.tokens[i].amount;
if (amount == 0) continue;
```

This confirms the maintainers are aware of and have already patched the "transfer-of-zero-amount can revert" bug class for the EVM path, but the Tron contract — which implements the identical `IntentGatewayV2`/`WithdrawalRequest` flow — was not updated with the same fix.

Since an order's `inputs` (the `body.tokens` used at withdrawal time) are fully attacker/user-controlled at `placeOrder` time, a malicious order creator can include a zero-amount `TokenInfo` entry referencing an ERC-20 that reverts on zero-value transfers (a known "weird-ERC20" behavior class, https://github.com/d-xo/weird-erc20#revert-on-zero-value-transfers) alongside their legitimate escrowed input token(s).

### Impact Explanation
`withdraw()` is the single internal function invoked from every settlement path — `onAccept` for `RedeemEscrow` (solver fill payout) and `RefundEscrow` (cancellation refund), as shown by test usage of `WithdrawalRequest{ commitment, tokens: inputs, beneficiary }`. Because the low-level transfer call is not gated on `amount > 0`, and the token address/amount pair is fixed inside the order commitment (baked into the cross-chain message body once dispatched), every future attempt to execute `withdraw()` for that specific commitment will deterministically hit the same reverting zero-transfer call and abort the entire transaction — including the `_filled` finalization and the transfer of the *legitimate*, non-zero escrowed tokens in the same array.

This means:
- The solver who filled the order can never claim their rightfully earned escrowed input tokens (loss/permanent lock of bridged assets).
- The user's ability to get a refund via `RefundEscrow` on cancellation is likewise permanently blocked for that commitment.
- Because the ISMP request is deterministic and the withdrawal path always replays the same `body.tokens`, there is no legitimate retry path that avoids the revert — funds tied to that commitment become permanently stuck in escrow.

This matches the bounty's "stealing or loss of funds" / "unauthorized... fund loss/lock" impact category and is reachable purely by an unprivileged user crafting their own order at `placeOrder` time — no relayer, prover, or admin compromise is required.

### Likelihood Explanation
Likelihood is bounded by whether the Tron `IntentGatewayV2` deployment is actually the production/live contract for this chain (uncertain from the retrieved context — this file lives under `evm/tron/contracts/apps/`, suggesting it is Tron-specific, separate from the primary `evm/src/apps/intentsv2/IntentsBase.sol` which already carries the fix). Assuming this Tron contract is deployed and used for real cross-chain intents (which its structure, imports of `@hyperbridge/core` interfaces, and `HyperApp`/ISMP wiring strongly suggest), the attack requires only a single `placeOrder` call with a crafted `inputs` array containing a zero-amount entry for a known revert-on-zero ERC-20 (e.g., certain LEND/OpenZeppelin `ERC20` variants). No special privileges, timing, or races are needed, making this straightforward to trigger.

### Recommendation
Apply the same guard already present in `IntentsBase.sol` to the Tron `IntentGatewayV2.withdraw()`:

```solidity
for (uint256 i; i < len;) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (amount == 0) { unchecked { ++i; } continue; }
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();
    ...
}
```
Additionally, validate at `placeOrder` time that no `TokenInfo` entry in `order.inputs` has `amount == 0`, to prevent zero-amount entries from ever being committed into an order in the first place.

### Proof of Concept
1. A user calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [ {token: USDC, amount: 1000e6}, {token: WEIRD_TOKEN, amount: 0} ]`, where `WEIRD_TOKEN` reverts on `transfer(to, 0)`.
2. A solver fills the order on the destination chain and the fill flow dispatches a `RedeemEscrow` message back to the source chain with `WithdrawalRequest.tokens = order.inputs` (unchanged, per `evm/src/apps/intentsv2/ExtrinsicIntents.sol` lines 140-147 pattern, mirrored in the Tron contract).
3. On the source chain, `onAccept` decodes the message and calls `withdraw(body, false)`.
4. In the loop, `withdraw` reaches the `WEIRD_TOKEN` entry with `amount == 0`, calls `token.call(transfer(beneficiary, 0))`, which reverts; `success == false` triggers `revert TransferFailed()`, aborting the whole transaction.
5. The solver's legitimately earned USDC (and every future retry of the identical `RedeemEscrow` message) is permanently unwithdrawable — funds are locked in the gateway indefinitely. [1](#0-0) [3](#0-2)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
