### Title
Incorrect Cobb-Douglas-style exponentiation in graduated-liquidation curve produces wrong liquidation penalty / debt cap — (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`calc-liq-factor-exp` is supposed to raise the linear liquidation factor to the configured `curve-exponent` power (`liq-factor^alpha`), exactly analogous to the Venus Cobb-Douglas score computation `xvs^alpha * capital^(1-alpha)` that was found to mishandle the edge case `alpha = 1`. Here the implementation similarly special-cases only `exp == BPS` and silently substitutes a fixed, hardcoded square-root approximation for every other sub-unity exponent, and an integer-truncated exponent for every super-unity value that is not an exact multiple of `BPS`. Any configured `curve-exponent` other than exactly `5000` (0.5) or `10000` (1.0) is computed incorrectly, producing a `liq-pct-scaled` value that diverges from the value the LTV-based liquidation-severity curve was designed to produce.

### Finding Description
The graduated liquidation flow computes:
```
liq-pct-linear = calc-liq-factor(current-ltv, ltv-liq-partial, ltv-liq-full)
liq-pct-scaled = calc-liq-factor-exp(liq-pct-linear, curve-exponent)
liq-penalty    = calc-liq-factor-bound(liq-pct-scaled, liq-penalty-min, liq-penalty-max)
max-debt-usd   = calc-liq-debt-repay(total-debt-usd, liq-pct-scaled)
``` [1](#0-0) 

`calc-liq-factor-exp` is the exponent stage:
```
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
``` [2](#0-1) 

Two implementation errors exist here, both stemming from the same class of bug as the Venus finding — an exponent function that only handles special-cased values correctly and silently mis-computes everything else:

1. **Sub-unity branch (`exp < BPS`)**: regardless of the actual configured `curve-exponent` (e.g. 1000, 3000, 7000, 9000 bps), the code always computes `sqrt(factor)`, i.e. hardwires `alpha = 0.5`. Any configured exponent other than exactly `5000` is silently ignored and replaced with 0.5.
2. **Super-unity branch (`exp > BPS`)**: `exp / BPS` uses integer (truncating) division. For any `curve-exponent` in `(BPS, 2*BPS)` — e.g. `15000` (1.5) — `exp / BPS` truncates to `1`, and `pow BPS (1 - 1) = pow BPS 0 = 1`, so the whole expression collapses to `factor^1 / 1 = factor`, i.e. it silently behaves as if `curve-exponent == BPS` (no curvature at all), even though the operator configured a super-linear curve.

Because `liq-pct-scaled` feeds directly into both `calc-liq-factor-bound` (which sets `liq-penalty`, the liquidator bonus rate) and `calc-liq-debt-repay` (which sets `max-debt-usd`, the amount of debt that can be forcibly repaid), an incorrect exponent produces an incorrect—wrong-direction—liquidation-severity curve versus what was configured, in the same way the Venus bug produced an incorrect score for any `alpha` that hit an unhandled special case.

### Impact Explanation
- If the true (intended) exponent curve at the current LTV would yield a *smaller* `liq-pct-scaled` than the erroneous sqrt/truncated value, the position is over-penalized: more collateral than the configured curve intends is seized by the liquidator (`calc-liq-collateral-repay`) and more debt than intended is forced closed — a wrongful transfer of value from the borrower to the liquidator.
- If the true exponent curve would yield a *larger* `liq-pct-scaled`, the position is under-penalized: less collateral is seized than the risk parameters intend, leaving unhealthy debt only partially cleaned up and increasing the protocol's exposure to bad debt / insolvency for that position.
- Since `curve-exponent` is a risk parameter set by the DAO/config per egroup (not attacker-controlled and not third-party oracle data), any deployed value other than exactly `5000` or `10000` bps causes systematically wrong liquidation-severity math on every liquidation for that egroup — this is a code bug in `v0-4-market.clar`, not a bad oracle feed or a DAO misconfiguration by intent.

### Likelihood Explanation
Triggering the bug requires no attacker action beyond a normal liquidation of an unhealthy position — it fires deterministically whenever `curve-exponent != BPS` (and is not exactly `5000` for the sub-unity path). Whether it is currently *reachable* in production depends on the exact `curve-exponent` value(s) configured for live egroups (set in the registry/init proposal contracts), which was not fully confirmed in this review — I could not verify the concrete deployed `curve-exponent` values within the available context, so likelihood should be validated against the current egroup configuration before treating this as actively exploited.

### Recommendation
Implement the general fractional power correctly (e.g. via a fixed-point `ln`/`exp` based power function, or a proper rational-exponent approximation), rather than special-casing only `exp == BPS` and falling back to a fixed `sqrt` (0.5) or a truncated-integer power for all other values. At minimum, explicitly validate/restrict `curve-exponent` to values the implementation can compute exactly, and reject/round any other configured exponent rather than silently substituting a different curve.

### Proof of Concept
1. Configure (or observe) an egroup with `curve-exponent = 3000` (intended `alpha = 0.3`).
2. Trigger liquidation math with `liq-pct-linear = factor` (0 < factor < BPS).
3. Expected: `liq-pct-scaled = factor^0.3` (in bps terms).
4. Actual: `calc-liq-factor-exp` takes the `exp < BPS` branch and returns `sqrti(factor * BPS)`, i.e. `factor^0.5`, not `factor^0.3` — a materially different (larger) value than intended, changing `liq-penalty` and `max-debt-usd` from what the configured curve specifies.
5. Similarly, configure `curve-exponent = 15000` (intended `alpha = 1.5`): `exp / BPS` truncates to `1`, so `calc-liq-factor-exp` returns `factor` unchanged (as if `alpha = 1.0`), silently discarding the super-linear curve.
