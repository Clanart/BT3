### Title
ThresholdKeys::read accepts untrusted key files without validating the secret share matches the claimed verification share — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes a key file (curve ID, `(t, n, i)`, interpolation coefficients, `secret_share`, and `n` verification shares) and passes it to `ThresholdKeys::new`, which only validates structural properties — share count, participant range, and interpolation applicability. Neither function ever checks the fundamental invariant `C::generator() * secret_share == verification_shares[i]`. The group key is then derived solely from the attacker-controlled verification shares of participants `1..=t`, so a maliciously crafted or corrupted key file yields a `ThresholdKeys` object that reports a coherent `group_key()` while holding a completely unrelated secret share.

### Finding Description
- `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reads `(t, n, i)`, the interpolation variant, the raw `secret_share` via `C::read_F`, and `n` verification shares via `C::read_G`, then calls `ThresholdKeys::new`.
- `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) checks `verification_shares.len() == n`, `participant <= n`, and the `Constant`-vs-`Lagrange`/`t == n` rule. It then computes `group_key` as `Σ verification_shares[i] * interpolation_factor(i, 1..=t)` — entirely from the file-supplied verification shares — and stores `secret_share` verbatim. There is no binding check between `secret_share` and `verification_shares[i]` (contrast `musig::musig`'s `debug_assert_eq!(our_pub_key, verification_shares[&params.i()])` and the dealer's construction where the relation holds by construction — neither protects the deserialization path).
- Downstream, `group_key()` is used to register scan keys / derive deposit addresses (bitcoin-serai `Scanner::new(key)`, `register_offset`), and `view()` produces `secret_share` and `verification_shares` interpolated independently, so the inconsistency is never detected until a signature produced from the share fails `verify_share` — at which point the node can only blame an innocent-looking participant set.

### Impact Explanation
Analogous to CVE-2024-7004 (insufficient validation of untrusted input via a malicious file bypassing discretionary checks): a crafted `ThresholdKeys` serialization is accepted as valid, causing the node to treat a group key as its own and to accept/report deposits to addresses derived from it (via `Scanner`), even though the stored `secret_share` cannot produce valid signature shares for that key. Funds reported received are unspendable, and FROST signing sessions degrade into blame rounds or produce uncompletable signatures — a silent loss-of-funds / liveness failure rather than an immediate decode error.

### Likelihood Explanation
Requires an attacker to influence the serialized `ThresholdKeys` bytes consumed by `ThresholdKeys::read` (key import/backup-restore/migration tooling), which is a narrower reachability than a pure network input — hence Medium rather than High. When reachable, exploitation is deterministic: no consistency check exists to reject the file.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`, which is the untrusted-input boundary), assert `C::generator() * *secret_share == verification_shares[&params.i()]` and reject the input otherwise. Optionally also verify the verification shares interpolate consistently under the declared interpolation for `1..=t`.

### Proof of Concept
```rust
// Craft bytes for ThresholdKeys::<Ristretto>::read where secret_share is
// unrelated to verification_shares[i]:
//   id_len || Ristretto::ID || t || n || i || interpolation(1=Lagrange)
//   || arbitrary_scalar              // secret_share: attacker-chosen
//   || n * point                     // verification_shares: honest-looking
// read() succeeds; group_key() reflects the verification shares, but every
// signature share produced by view()/signing fails verify_share — and any
// deposit to an address derived from group_key() is unspendable.
```
Root cause confirmed at `crypto/dkg/src/lib.rs:349-391` (`ThresholdKeys::new` derives `group_key` from verification shares without binding `secret_share`) and `crypto/dkg/src/lib.rs:574-632` (`ThresholdKeys::read` is the untrusted-deserialization entry point). Caveat: the exploitability rating assumes an integrator path that feeds externally influenced key files into `ThresholdKeys::read`; if all key material is strictly locally generated, the impact reduces to corrupted-file robustness.
