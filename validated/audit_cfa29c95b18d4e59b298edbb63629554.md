### Title
Forged `ReceivedOutput` records can report non-existent Bitcoin funds as spendable - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`ReceivedOutput::read` accepts a caller-supplied scalar offset, `TxOut`, and `OutPoint` without proving that the outpoint exists on-chain or that the encoded amount belongs to the referenced UTXO. A forged serialized record can therefore represent an arbitrary balance under a Serai-controlled P2TR script while naming a non-existent or already-spent outpoint. `SignableTransaction::new` subsequently trusts the serialized output value and outpoint when constructing the spendable transaction.

### Finding Description
The original bug class is an unprivileged caller triggering an asset/accounting operation for another principal. The analogous Serai path is untrusted `ReceivedOutput` bytes being treated as authoritative evidence of spendable wallet funds.

`ReceivedOutput::read` independently deserializes `offset`, `output`, and `outpoint`, then returns the object without checking the `outpoint` against Bitcoin consensus state or proving that the `TxOut` is the actual output at that location. [1](#0-0)  By contrast, a legitimate `ReceivedOutput` produced by `Scanner::scan_transaction` is derived from an observed transaction and records the actual transaction ID and vout. [2](#0-1) 

When the forged object reaches transaction construction, `SignableTransaction::new` sums `input.output.value` as available funds and uses `input.outpoint` as a transaction input. [3](#0-2)  It then stores the claimed `TxOut` values as the prevouts committed to by Taproot sighashes. [4](#0-3)  `multisig` checks that the supplied script corresponds to the threshold key after applying the supplied offset, but it does not verify that the referenced outpoint exists or contains the claimed amount. [5](#0-4) 

### Impact Explanation
A forged `ReceivedOutput` can cause funds to be reported as received even though they are not spendable. The attacker can select any public Serai threshold key `K`, choose a scalar `offset`, construct the script for `K + offset*G`, assign it an arbitrary value and an arbitrary outpoint, and serialize the result.

If downstream accounting treats the decoded value as a received balance, the attacker can obtain credit for funds that were never received. If the forged input reaches signing, the threshold participants sign a transaction committing to a false prevout amount or a non-existent input; the resulting transaction is invalid and cannot actually spend the claimed funds.

### Likelihood Explanation
The serialized format is externally supplied and does not authenticate that it originated from `Scanner::scan_transaction` or `Scanner::scan_block`. The required script can be computed entirely from public information because the threshold group key and the attacker-chosen offset are public inputs to the P2TR construction. No private key, validator compromise, malformed curve point, or threshold collusion is required.

### Recommendation
Do not treat `ReceivedOutput::read` as proof of a spendable UTXO. Bind each decoded record to a scanner/key context and verify, against a trusted Bitcoin view, that:

- `outpoint` identifies an existing, unspent output;
- the decoded `TxOut` exactly equals the on-chain output;
- `script_pubkey` equals the expected P2TR script for `base_key + offset*G`;
- the output is mature and otherwise eligible for spending.

Prefer making deserialization return an unverified representation and only constructing `ReceivedOutput` after successful chain validation.

### Proof of Concept
Let `K` be the public threshold group key and `offset` an attacker-selected scalar.

1. Compute `P = K + offset*G` and derive `script = p2tr_script_buf(P)`.
2. Construct `TxOut { value: victim_reported_amount, script_pubkey: script }`.
3. Choose an arbitrary `OutPoint`, such as a non-existent transaction ID and vout.
4. Serialize `offset || TxOut || OutPoint` in the field order consumed by `ReceivedOutput::read`.
5. Feed those bytes to `ReceivedOutput::read`; it returns a `ReceivedOutput` whose `value()` reports `victim_reported_amount`. [6](#0-5) 
6. Pass it to `SignableTransaction::new`; the forged amount is included in `input_sat`, and the forged outpoint is included in `tx_ins`. [3](#0-2) 
7. `multisig` accepts the key/script relationship because the crafted script equals `p2tr_script_buf(K + offset*G)`, despite the underlying UTXO being absent. [7](#0-6)

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
