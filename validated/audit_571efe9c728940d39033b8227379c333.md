### Title
Quadratic Lagrange interpolation in `ThresholdKeys::read` enables asymmetric CPU exhaustion - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts an attacker-controlled participant count and Lagrange interpolation mode, then derives the group key using an interpolation routine that evaluates every threshold participant against every other threshold participant. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The serialized format lets untrusted input select `t`, `n`, the participant index, and `Interpolation::Lagrange`, followed by exactly `n` verification shares. [4](#0-3)  `ThresholdParams::new` only requires `t <= n` and `i <= n`, allowing both `t` and `n` to reach `u16::MAX`. [5](#0-4)  The constructor permits Lagrange interpolation without imposing a practical participant bound, then computes one interpolation factor for each participant `1..=t`. [6](#0-5)  Each Lagrange factor iterates through the entire threshold set and performs two field multiplications for each other participant, so `t = n = 65535` requires approximately 8.6 billion field multiplications before accounting for 65,535 inversions and group scalar multiplications. [7](#0-6) 

### Impact Explanation
A relatively small serialized key containing 65,535 canonical group elements can therefore consume orders of magnitude more CPU work than its input size suggests. [8](#0-7)  Any service that accepts `ThresholdKeys` bytes from an untrusted party can have a worker tied up inside deserialization before ordinary policy checks or signature processing begin. [9](#0-8) 

### Likelihood Explanation
The input is completely deterministic and does not require a valid secret share, signature, proof, or protocol role; all group elements may even encode the same canonical generator because they are stored under distinct participant indexes. [10](#0-9)  The expensive path is entered automatically by `ThresholdKeys::new` during deserialization, so no additional attacker interaction or malformed message is required. [11](#0-10) 

### Recommendation
Enforce a deployment-appropriate maximum `n` and `t` before constructing `ThresholdKeys`, or extend the read API with explicit parameter bounds rather than trusting the encoded `u16` values. [12](#0-11)  For large supported sets, replace the per-participant quadratic Lagrange derivation with a cheaper aggregate construction or derive and cache interpolation coefficients using an algorithm with a documented bound. [2](#0-1)  Reject unusually large threshold configurations as early as possible so malformed inputs cannot trigger expensive field inversions and group scalar multiplications. [3](#0-2) 

### Proof of Concept
```rust
use ciphersuite::{Ciphersuite, group::{ff::Field, GroupEncoding}};
use dalek_ff_group::Ristretto;
use dkg::ThresholdKeys;

let n = u16::MAX;
let mut bytes = Vec::new();

// Curve ID expected by ThresholdKeys::read.
bytes.extend_from_slice(&(Ristretto::ID.len() as u32).to_le_bytes());
bytes.extend_from_slice(Ristretto::ID);

// t = n = 65535, participant i = 1.
bytes.extend_from_slice(&n.to_le_bytes());
bytes.extend_from_slice(&n.to_le_bytes());
bytes.extend_from_slice(&1u16.to_le_bytes());

// Interpolation::Lagrange.
bytes.push(1);

// Canonical secret-share scalar: one.
let mut scalar_one = vec![0u8; 32];
scalar_one[0] = 1;
bytes.extend_from_slice(&scalar_one);

// n canonical verification shares; duplicate points are accepted here.
let generator = Ristretto::generator().to_bytes();
for _ in 0 .. n {
  bytes.extend_from_slice(generator.as_ref());
}

// Enters the quadratic group-key derivation before returning.
let _ = ThresholdKeys::<Ristretto>::read(&mut bytes.as_slice());
```

This encoding passes the format's parameter checks because `t`, `n`, and `i` are nonzero, `t <= n`, and `i <= n`. [5](#0-4)  Selecting Lagrange mode avoids the constant-interpolation restriction while still causing `ThresholdKeys::new` to calculate all `t` interpolation factors. [6](#0-5)

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
