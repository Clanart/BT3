## Title
Copilot conflict resolution splices AI-generated content into the wrong conflict hunk by positional index instead of content matching, silently corrupting committed/pushed code - (File: `app/src/lib/copilot-conflict-resolution.ts`)

## Summary
`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` rebuilds a conflicted file by walking the on-disk file (which still has `<<<<<<<`/`=======`/`>>>>>>>` markers from a merge/rebase/cherry-pick against an attacker-influenced branch) and splicing in AI-generated resolutions **by positional order, not by matching content**, exactly the same class of flaw as the reported `OmoVault.topOff()` bug: a critical operation trusts a value/index derived from one source (the model's ordered hunk list) to line up perfectly with another independently-computed structure (the hunks parsed from the actual file), with no cross-check that the two agree.

## Finding Description
`buildConflictContext` in `app/src/lib/copilot-conflict-context.ts` reads each conflicted file's on-disk content and extracts conflict hunks (`extractConflictHunks`), guarding only against path traversal and outsized files: [1](#0-0) 

The Copilot model then returns per-hunk resolutions for that file, and `reassembleResolutions`/`reassembleResolvedFile` splice them back into the original raw content **by matching order, not by line number or content**, as the function's own doc comment states: [2](#0-1) 

The reassembly loop increments `hunkIndex` for every conflict-marker block encountered in the file and pulls `hunkResolutions[hunkIndex]` regardless of whether that resolution actually corresponds to that hunk's content: [3](#0-2) 

There is no verification that `hunkResolutions.length` equals the number of conflict blocks actually present in `rawContent`, nor any content-based correlation (e.g., hashing the `ours`/`theirs` text) between a returned resolution and the hunk it's being spliced into. If the model's response for a file has a different hunk count/ordering than what's actually in the file — which can happen because the untrusted repository content (an attacker-controlled merge/rebase/cherry-pick target) is fed to the model and can influence how many "hunks" it perceives (e.g., via content that looks like extra/missing conflict markers, unusual formatting, or prompt-injection-style text inside the diff/rules blocks noted elsewhere in the code as "untrusted"), the wrong resolved content silently lands in the wrong hunk location. This corrupts the file that is then written to disk and staged automatically: [4](#0-3) 

This precisely mirrors the report's broken invariant: an accounting/positional value from an untrusted or manipulable source (`agentBalance` / `hunkResolutions[hunkIndex]`) is blindly trusted to correspond 1:1 with the value it's meant to represent (`record.assets` / the actual hunk at that position), and no independent check enforces that correspondence before the value is applied to critical state (vault accounting / the user's committed file content).

## Impact Explanation
If hunk count/order desynchronization occurs, the tool silently writes attacker-influenced or simply misaligned code into the wrong location of a file that the user believes represents a specific, reviewed conflict resolution, then stages it (`git add`) for commit. Because the UI's diff preview (`getResolutionDiff`) is keyed by file path and computed separately, a user could still catch this via the shown diff before clicking "Continue Merge" — but the underlying reassembly logic itself has no invariant enforcement, so the diff review is the *only* safety net, not the code. This falls under "silent corruption of what the user commits or pushes," which is explicitly in scope.

## Likelihood Explanation
Triggering requires the user to invoke "Resolve Conflicts with Copilot" during a merge/rebase/cherry-pick against a branch/remote containing attacker-crafted content — no local access, admin rights, or social engineering beyond a normal collaborative workflow (pulling/merging a branch) is needed. The likelihood that an attacker can reliably desynchronize the model's per-file hunk count from the true count in the file is uncertain — I could not fully verify (given the final-iteration cutoff) whether `parseCopilotConflictResolution` or `resolveConflicts` in `copilot-store.ts` independently validates the resolution's hunk count against the context's known hunk count before reassembly. If such validation exists, its absence in `reassembleResolvedFile` itself is still the enforcement gap and the guard could plausibly be bypassed via a hunk count that still numerically matches but is semantically mismatched (e.g., two structurally-identical-looking conflict blocks with swapped content).

## Recommendation
In `reassembleResolvedFile`/`reassembleResolutions`, do not correlate hunks purely by array order. Instead, either (a) include the original hunk's exact `ours`/`theirs` text (or a hash of it) in the resolution payload requested from the model and verify it matches the corresponding on-disk hunk before splicing, or (b) reject/flag the whole file's resolution (falling back to manual resolution) if `hunkResolutions.length` doesn't exactly equal the number of conflict blocks found in `rawContent`, rather than silently proceeding with a best-effort positional splice.

## Proof of Concept
Not independently reproducible from static analysis alone — verifying an end-to-end exploit requires confirming (1) whether `copilot-store.ts`/`parseCopilotConflictResolution` enforces a hunk-count match before calling `reassembleResolutions`, and (2) whether prompt-injection-style content in a conflicted file can realistically cause the model to return a mismatched/reordered `hunks` array for that file. `app/test/unit/copilot-conflict-resolution-test.ts` shows the reassembly is tested only for well-formed 1:1 ordered cases (e.g., lines 450–500), not for hunk-count mismatch or adversarial reordering, suggesting this negative case is currently untested.

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
