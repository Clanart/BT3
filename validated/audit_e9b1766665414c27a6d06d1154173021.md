### Title
Panic on out-of-set participant index in PedPoP blame handling aborts the node - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
The upstream issue (ALPINE-CVE-2020-35521) is a crafted-input → abort denial of service. The analog in Serai's in-scope PedPoP DKG code is that `BlameMachine::blame` / `AdditionalBlameMachine::blame` index `self.commitments[&sender]` and `self.enc_keys[&decryptor]` without validating that the supplied `Participant` indexes belong to the DKG set, so an accusation naming a participant index outside `1..=n` causes an unhandled `HashMap` indexing panic (process abort).

### Finding Description
`blame_internal` resolves blame using two unchecked map lookups:

- `self.encryption.decrypt_with_proof(...)` reads `self.enc_keys[&decryptor]` inside `Decryption::decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:388). [1](#0-0) 
- `self.commitments[&sender]` at crypto/dkg/pedpop/src/lib.rs:599. [2](#0-1) 

Both `sender` and `recipient`/`decryptor` are caller-supplied `Participant` values taken from an accusation, and `Participant::new` accepts any nonzero `u16` — there is no bound against `params.n()`. `commitments`/`enc_keys` only contain entries for the registered DKG set (`1..=n`, populated in `verify_r1` at crypto/dkg/pedpop/src/lib.rs:313-331 or `AdditionalBlameMachine::new` at crypto/dkg/pedpop/src/lib.rs:656-660). An accusation whose `accuser`/`faulty` fields (as carried on wire by the coordinator's `InvalidDkgShare` transaction, which parses arbitrary u16 participant indexes, coordinator/src/tributary/transaction.rs:346-354) reference a `Participant` not in the set reaches these indexing operations and panics.

`AdditionalBlameMachine::new` explicitly documents that its inputs are "assumed... fully authenticated", but `blame` itself performs no membership check on the accused/accuser pair, and the documented panic surface is reachable purely from the accusation contents.

### Impact Explanation
A single malformed blame/accusation message referencing participant index > n (or 0-adjacent out-of-set values) crashes the process evaluating blame via an unhandled panic at `self.commitments[&sender]` or `self.enc_keys[&decryptor]`. This matches the CVE class: a crafted input causes an abort, yielding denial of service of the DKG/validator process during the blame-resolution phase, which is exactly when liveness is most needed.

### Likelihood Explanation
Any party able to submit an accusation (a DKG participant claiming a bad share) can encode arbitrary `Participant` u16 values for sender/recipient. No cryptographic validity is required to reach the panic — the lookups occur before/while verifying the share and proof. Cost is one message; reliability is deterministic.

### Recommendation
Replace map indexing with `get` + graceful error: in `blame_internal`, check `self.commitments.get(&sender)` and have `decrypt_with_proof` take `enc_keys.get(&decryptor)`, returning the accusing/accused party or a dedicated `InvalidParticipant` error rather than panicking. Additionally validate `u16::from(sender) <= n` and `u16::from(recipient) <= n` at the `blame`/`AdditionalBlameMachine::blame` entry points.

### Proof of Concept
```rust
// Setup: AdditionalBlameMachine::new(context, n, commitment_msgs)
// with n = 2, registering participants 1 and 2.
// Attacker submits a blame evaluation request:
let machine = AdditionalBlameMachine::<Secp256k1>::new(context, 2, msgs).unwrap();
// sender = Participant(7) — not in 1..=n, but Participant::new(7) is valid.
let sender = Participant::new(7).unwrap();
let recipient = Participant::new(1).unwrap();
// Panics at self.enc_keys[&decryptor] or self.commitments[&sender]
machine.blame(sender, recipient, forged_encrypted_msg, None);
```
Alternatively with `recipient = Participant::new(7)` the panic fires first at `self.enc_keys[&decryptor]` in `decrypt_with_proof` (encryption.rs:388), reached with any bytes as `msg` since the lookup precedes share validation.

Caveat: I could not fully trace the coordinator/processor call path that feeds `InvalidDkgShare`'s accuser/faulty fields into `blame`; the panic itself is confirmed in the in-scope crate, and reachability depends on the integrator passing accusation participant indexes through unchecked (which the wire format permits).
