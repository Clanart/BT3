### Title
Hardcoded zero minimum-received bypasses slippage protection in `ArbWomUp3.incentiveDeposit` (mode 2 WOM→mWom conversion) - ([File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3._deposit` (invoked from the unprivileged, user-facing `incentiveDeposit` function) forwards half of a user's deposited WOM to `SmartWomConvert.convert()` with the minimum-received parameter hardcoded to `0`, which completely defeats the slippage/minimum-output check that `SmartWomConvert._convertFor` is supposed to enforce on the WOM→mWom AMM swap.

### Finding Description
Any wallet can call `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, _bullMode, _mode)` with `_mode == 2`. This routes into `_deposit`, which splits the deposited WOM in half and sends the swap-portion through `SmartWomConvert.convert`: [1](#0-0) 

```
} else if (_mode == 2) {
    uint256 toDeposit = _amount / 2;
    uint256 toSwap = _amount - toDeposit;
    ...
    IERC20(wom).safeApprove(smartWomConvert, toSwap);
    IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0);
    ...
```

The call passes `_minRec = 0` unconditionally — there is no way for the calling user of `incentiveDeposit` to influence or set a meaningful minimum. Inside `SmartWomConvert`, this value is used as the final safety check: [2](#0-1) 

and [3](#0-2) 

```
if (buybackAmount > 0) {
    ...
    amountRec = IWombatRouter(router).swapExactTokensForTokens(
        tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp
    );
}
...
if (convertAmount + amountRec < _minRec)
    revert MinRecNotMatch();
```

The underlying router call to `IWombatRouter.swapExactTokensForTokens` also hardcodes its own `minimumToAmount` to `0`, so the only remaining protection against a bad/sandwiched swap price is the post-swap `_minRec` check — and `ArbWomUp3` sets that check's threshold to `0`, making it a no-op. As a result, the WOM→mWom leg of the conversion executed on behalf of the user has no slippage protection whatsoever.

### Impact Explanation
Because `_minRec` is forced to `0`, an attacker can sandwich the swap inside `SmartWomConvert._convertFor` (front-run to worsen the WOM/mWom pool price, let the victim's `incentiveDeposit(..., _mode=2)` transaction execute at an unfavorable rate, then back-run to restore price and capture the difference). The victim's WOM is irreversibly locked into `mWomSV` via `ILocker(mWomSV).lockFor(mWomBal, _account)` at whatever degraded `mWom` amount resulted, so the user permanently receives less value than a fair swap would have produced — a direct loss of user funds during an unprivileged, reachable transaction path.

### Likelihood Explanation
The path is triggered simply by any user calling the public `incentiveDeposit` function with `_mode == 2`, which is a normal/advertised usage mode of the contract (locking mWom via `mWomSV`). No privileged role or special conditions are required; only a well-timed sandwich around the user's transaction is needed, which is a standard MEV technique on any public mempool.

### Recommendation
Do not hardcode `_minRec` to `0` when `ArbWomUp3` calls `SmartWomConvert.convert`. Either compute an acceptable minimum from `SmartWomConvert.estimateTotalConversion` with a configurable slippage tolerance and pass it through, or expose a `_minRec`/slippage parameter on `incentiveDeposit` that the caller can set and forward down to `convert`. Additionally, `SmartWomConvert._convertFor` itself should not hardcode `0` as the router-level `minimumToAmount` for the `swapExactTokensForTokens` call — it should derive a bound from `_minRec` before executing the swap, not only check the total after the fact.

### Proof of Concept
1. User calls `ArbWomUp3.incentiveDeposit(amount, convertRatio, bullMode, 2)`.
2. `_deposit` computes `toSwap = amount - amount/2` and calls `IConverter(smartWomConvert).convert(toSwap, convertRatio, 0, 0)`.
3. Attacker front-runs with a large WOM→mWom (or mWom→WOM) swap on the `womMWomPool` to push the price unfavorably for the victim, since `SmartWomConvert._convertFor` swaps with `minimumToAmount = 0` at the router level.
4. Victim's swap executes at the manipulated price; `_convertFor`'s check `convertAmount + amountRec < _minRec` never reverts because `_minRec == 0`.
5. Attacker back-runs to restore the pool price, pocketing the value difference; the victim's resulting (reduced) `mWom` amount is locked into `mWomSV` on their behalf, permanently realizing the loss.
