### Title
`ThresholdKeys::read`/`new` derive the group key from attacker-supplied verification shares without checking the secret share is consistent, so crafted bytes produce a signer for a fully attacker-controlled group key - (File: crypto/dkg/src/lib.rs)

### Summary
The external report describes a parameter (`collateralizationRatio`) being settable outside its valid range, which silently disables a safety invariant (liquidation). The Serai analog is in `ThresholdKeys::read` / `ThresholdKeys::new` (`crypto/dkg/src/lib.rs`): the threshold `t`/`n` and the entire `verification_shares` map are attacker-controlled bytes, and while `ThresholdParams::new` bounds `t`/`n` (`t != 0`, `t <= n`), nothing bounds or checks the *content* of the verification shares or their consistency with `secret_share`. `group_key` is simply *computed* from the untrusted shares (`t.iter().map(|i| verification_shares[i] * interpolation_factor(...)).sum()`), so the resulting key set is valid-by-construction for whatever group key the byte supplier chose — including a key whose discrete log they know.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, `i`, the interpolation variant, `secret_share`, and `n` verification shares straight from the reader, then calls `ThresholdKeys::new`. `new` enforces only:

- `verification_shares.len() == n`
- all participant indices `<= n`
- `Constant` interpolation only when `t == n`

It then derives `group_key` by interpolating shares `1..=t` — it never verifies that `C::generator() * secret_share == verification_shares[i]`, nor that the shares are consistent with any expected key. Analogous to the report, the "bound check" that would pin the keys to an expected value is absent: any well-formed bytes are accepted and `group_key()` will report whatever the attacker encoded.

Reachability: `ThresholdKeys::read` is explicitly listed as an untrusted-bytes sink, and it is reached in production via `GeneratedKeysDb::read_keys` (`processor/src/key_gen.rs`), which deserializes key material from storage and uses `keys[0].group_key()` as a database key for the key set.

If a party can feed crafted bytes into `ThresholdKeys::read`, they can set `verification_shares[j] = G * s_j` for self-chosen `s_j` and pick `secret_share` arbitrarily. The deserialized `ThresholdKeys` then participates in `AlgorithmSignMachine`/`sign`/`complete` producing FROST signature shares that aggregate into valid signatures under the attacker's chosen group key — while the node believes it is operating under `group_key()` as reported.

### Impact Explanation
A node deserializing attacker-crafted `ThresholdKeys` will produce valid FROST signature shares for a group key entirely of the attacker's choosing. Wherever `group_key()` is used as identity (e.g., the `GeneratedKeysDb` storage key binding a key set to a session), the attacker controls the reported identity: funds routed to or signatures accepted under that group key are spendable/forgeable by the attacker, who knows the underlying secret. This mirrors the report: an unvalidated value silently replaces the security-critical invariant (real collateral backing / real DKG-produced key) with an attacker-set one.

### Likelihood Explanation
Requires the attacker to control the bytes passed to `ThresholdKeys::read` (serialized key material). The struct is explicitly designed to be deserialized and is read from persistent storage in the processor; any path where key blobs are restored, migrated, or supplied externally exposes this. No cryptographic break or collusion is needed — only the missing consistency check.

### Recommendation
In `ThresholdKeys::new` (which `read` funnels through), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject inconsistent input. Optionally accept an expected `group_key`/`thresh` digest parameter on restore paths so the group key is checked against an independent value rather than derived purely from the same untrusted bytes.

### Proof of Concept
```rust
// Attacker crafts serialized ThresholdKeys with a group key they fully control.
let x = <C as Ciphersuite>::F::random(&mut OsRng);       // attacker-known secret
let n = 2u16; let t = 2u16;                              // e.g. 2-of-2, Lagrange
// verification_shares[1] = verification_shares[2] = G * x
// => interpolation over participants 1..=t yields group_key = G * x
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(t.to_le_bytes());
buf.extend(n.to_le_bytes());
buf.extend(1u16.to_le_bytes());          // i = 1
buf.push(1);                             // Interpolation::Lagrange
buf.extend(x.to_repr().as_ref());        // secret_share (consistent with shares[1])
for _ in 1 ..= n {
  buf.extend((C::generator() * x).to_bytes().as_ref());  // attacker-chosen shares
}
let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();
assert_eq!(keys.group_key(), C::generator() * x);        // attacker-controlled key
// keys can now be fed into AlgorithmMachine::new(...).preprocess()/sign()/complete()
// producing valid FROST signatures under G*x, which the attacker can also sign for alone.
```
The only "validation" performed is structural (`t <= n`, indices `<= n`, share count `== n`); the semantic check pinning `secret_share`/shares/`group_key` to a trusted value is missing — the same missing-bound class as `updateCollateralizationRatio`.
