### Title
Missing lower-bound validation of the KIP-71 `GasTarget` governance parameter causes a division-by-zero panic in base fee computation - (File: `params/kip71_config.go`)

### Summary
The `early-purchase` report describes a class of bug where a privileged parameter-setting instruction accepts values that create "impossible" or degenerate configurations (e.g., zero denominators/targets) because no bounds/format validation is enforced. The Kaia codebase has a directly analogous defect in the KIP-71 dynamic base-fee governance parameter set: `Kip71GasTarget` (and `Kip71MaxBlockGasUsedForBaseFee`) are registered with a `noopFormatChecker`, so a governance vote can set `GasTarget = 0`. This value is later used as a divisor in `NextMagmaBlockBaseFee`, which is invoked by every node during block header validation, leading to a `division by zero` panic.

### Finding Description
In `kaiax/gov/param.go`, most KIP-71 parameters are registered with format checkers, but `Kip71GasTarget` and `Kip71MaxBlockGasUsedForBaseFee` use `noopFormatChecker`, which always returns `true`: [1](#0-0) 

Only `Kip71BaseFeeDenominator` is protected against zero: [2](#0-1) 

The vote-consistency checker in header-based governance (`checkConsistency`) only cross-validates `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` against each other; it performs no check at all for `Kip71GasTarget`: [3](#0-2) 

The resulting `GasTarget=0` value flows unguarded into `NextMagmaBlockBaseFee`, which is the core KIP-71 base-fee computation used during block validation: [4](#0-3) 

When `gasTarget == 0`, and any nonzero gas is used in the parent block, execution takes the "gas used > target" branch and performs `x.Div(x, new(big.Int).SetUint64(gasTarget))`, i.e., division by the big.Int zero value, which panics in Go's `math/big` package. Unlike `BaseFeeDenominator`, there is no zero-guard fallback for `GasTarget`.

### Impact Explanation
`NextMagmaBlockBaseFee` is called from block validation (`blockchain/block_validator.go`), block assembly (`work/worker.go`, `blockchain/chain_makers.go`), the tx pool (`blockchain/tx_pool.go`), and gas price oracle/fee history RPC (`node/cn/gasprice/gasprice.go`, `node/cn/gasprice/feehistory.go`). Once a governance vote sets `Kip71GasTarget = 0` and it takes effect, every honest node computing the next block's base fee (validators validating headers, the proposer building a block, and RPC nodes serving `eth_feeHistory`) will panic on the very next block with nonzero gas usage. This causes a network-wide node crash / consensus halt — a state-transition validity/availability failure reachable through the standard governance parameter-update path, matching the "acceptance of an invalid transaction/block" and "state divergence between honest nodes" impact classes (nodes panicking rather than processing blocks constitutes denial of the chain's liveness).

### Likelihood Explanation
Likelihood is Medium: setting `Kip71GasTarget` requires a valid governance vote (via header-vote or GovParam contract), which is a privileged action restricted to council/governing entities — not an arbitrary unprivileged EOA. However, this exactly mirrors the reported bug class ("no thorough input validation... allowing arbitrary parameter values with off-chain/on-chain implications") — the same privilege model as the `early-purchase` program's sale-initializer that was still flagged as a valid, unresolved finding. Because the format checker is a no-op and no additional runtime guard exists (unlike `BaseFeeDenominator`, which has an explicit zero-fallback of 64), a single vote or contract update (accidental misconfiguration, compromised governing key, or malicious governor) is sufficient to trigger it deterministically on the next non-idle block.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and `Kip71MaxBlockGasUsedForBaseFee`) in `kaiax/gov/param.go` rejecting zero values, matching the existing pattern used for `Kip71BaseFeeDenominator`. Additionally, add a defensive zero-check fallback inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` (analogous to the existing `BaseFeeDenominator == 0` fallback) so that even a pre-existing or misconfigured `GasTarget = 0` cannot cause a division-by-zero panic.

### Proof of Concept
1. A governance vote (header vote or GovParam contract update) sets `kip71.gastarget = 0` and it becomes effective at some epoch/block, passing both `Kip71GasTarget`'s `noopFormatChecker` and `checkConsistency` unchecked, as shown in: [1](#0-0) [5](#0-4) 
2. On the following block, any nonzero `parentHeaderGasUsed` causes `NextMagmaBlockBaseFee` to enter the increase branch and execute `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`: [6](#0-5) 
3. `big.Int.Div` panics with "division by zero" inside block header validation/creation code paths that call this function, crashing the node process that processes/validates the block.
