### Title
Fully-unlocked vlMGP slots incorrectly decay reward-eligibility over time, misrouting a victim's yield to concurrent large stakers - (File: VLMGP.sol / rewards/vlMGPBaseRewarder.sol)

### Summary
`VLMGP.getRewardablePercentWAD` (VLMGP.sol:193-218) applies a time-decaying formula to slots that are already past `endTime` (the "fully unlocked" branch, VLMGP.sol:206-209), even though such slots should count at full 100% weight (as `getFullyUnlock`, VLMGP.sol:184-191, correctly does with no decay). The longer an unprivileged user delays calling `unlock()`/triggering a harvest after their cooldown has expired, the smaller their "rewardable" percent becomes, artificially inflating the "forfeit" amount computed in `vlMGPBaseRewarder._calExpireForfeit` (rewards/vlMGPBaseRewarder.sol:386-400). This forfeited amount is queued into the shared reward pool via `_queueNewRewardsWithoutTransfer` (rewards/vlMGPBaseRewarder.sol:331-347), where it is captured pro-rata by whichever accounts hold a large vlMGP balance at that moment (rewards/vlMGPBaseRewarder.sol:159-166, :379-384).

### Finding Description
`getRewardablePercentWAD` computes, for a slot whose `endTime` has already passed:
```
percent += amountInCoolDown * 1e18 * (endTime - startTime) / userTotalVlmgp / (timeNow - startTime);
``` [1](#0-0) 

At `timeNow == endTime` this correctly reduces to `amountInCoolDown * 1e18 / userTotalVlmgp` (full weight). But as `timeNow` grows past `endTime`, the ratio `(endTime-startTime)/(timeNow-startTime)` monotonically shrinks toward 0, so the contribution of an already fully-unlocked slot keeps decreasing the longer the user (an unprivileged, ordinary user with no special role) simply fails to call `unlock()`. This directly contradicts `getFullyUnlock` (VLMGP.sol:184-191), which treats any slot past `endTime` as 100% unlocked with no decay, and contradicts the "still in cool down" branch (VLMGP.sol:210-212), which applies flat, non-decaying weight.

This percent is consumed by `vlMGPBaseRewarder._calExpireForfeit`:
```solidity
uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
...
uint256 forfeitAmount = _amount - rewardableAmount;
``` [2](#0-1) 

This is invoked both from `queueMGP` (called during a MasterMagpie harvest that emits new MGP rewards to a user, rewards/vlMGPBaseRewarder.sol:274-289) and `_sendReward`/`getReward` (rewards/vlMGPBaseRewarder.sol:363-377). The `forfeitAmount` (inflated purely due to the victim's delay, not any real forfeiture rule) is pushed into the shared accumulator: [3](#0-2) 
which increases `rewardPerTokenStored` proportional to `totalStaked()`. Any account already holding a large vlMGP balance (locked MGP, obtained by anyone permissionlessly via `VLMGP.lock`/`lockFor`, VLMGP.sol:254-268) benefits from this bump the next time they call `_earned`/`getReward`, in proportion to their share of `totalStaked()` — with no time-weighting requirement tying the payout to when the balance was acquired: [4](#0-3) 

None of the existing guards (`nonReentrant`, `whenNotPaused`, `onlyMasterMagpie`, `onlyManager`) address this — they gate *who* can call the harvesting functions, not the correctness of the percent calculation. The bug is a pure arithmetic/logic defect reachable by any user's ordinary, permissionless action sequence: victim locks → starts unlock → waits past `endTime` → calls `unlock()` (or any action that triggers `multiclaimFor`) → the vlMGPBaseRewarder computes an inflated forfeit and credits it to the shared pool → attacker (a pre-existing or freshly-locked large vlMGP holder) calls `getReward`/harvest and receives a disproportionate slice of that forfeiture that rightfully belonged to the victim's already fully-vested position.

### Impact Explanation
This is a "theft of unclaimed yield" issue: value that should have remained with the victim (100% of the rewards accrued on an already fully-unlocked, cooldown-completed balance) is misrouted to the shared reward pool and captured disproportionately by large concurrent vlMGP stakers, purely as a function of how long the victim delays calling `unlock()`. No tokens are minted from nothing (conservation of total token supply holds), but the *entitlement* to that yield is redirected away from the rightful owner to unrelated third parties — this matches the "theft of unclaimed yield" / "misrouted forfeiture" impact class specified in scope.

### Likelihood Explanation
- No privileged role is required; both the "victim" behavior (delaying `unlock()`) and the "attacker" behavior (holding a large vlMGP balance and calling harvest/`getReward`) are ordinary permissionless user actions.
- The precondition (an expired but unclaimed cooldown slot) is common and easy to reach — users are not forced to unlock promptly, and any delay past `endTime` triggers the bug.
- Capital requirement for the attacker scales with how large a share of the forfeiture they want to capture, but even modest vlMGP holders benefit proportionally whenever any other user forfeits due to delay.
- The exploit is fully repeatable and does not depend on timing races, front-running, oracle manipulation, or governance/admin actions.

### Recommendation
In the `block.timestamp > userUnlocking[i].endTime` branch of `getRewardablePercentWAD` (VLMGP.sol:206-209), remove the time-decay entirely and treat the slot at full weight, consistent with `getFullyUnlock`:
```solidity
if (block.timestamp > userUnlocking[i].endTime) {
    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
}
```
This ensures that once a cooldown slot is genuinely past its `endTime`, it is never treated as partially forfeitable regardless of how long the user delays claiming, eliminating the artificial, time-dependent forfeiture and the associated misrouting of yield.

### Proof of Concept
Foundry test outline:
1. Deploy `VLMGP`, `MasterMagpie`, and `vlMGPBaseRewarder` with a short `coolDownInSecs` (e.g., 7 days) for fast testing.
2. Victim locks `X` MGP, calls `startUnlock(X)` to open a cooldown slot with `startTime = t0`, `endTime = t0 + coolDownInSecs`.
3. Attacker locks a large amount `Y >> X` of MGP via `VLMGP.lock`, becoming the dominant vlMGP holder.
4. Warp time to `t0 + 10 * coolDownInSecs` (well past `endTime`, simulating victim's delay).
5. Trigger an MGP reward emission for the victim (e.g., via MasterMagpie's harvest path that calls `vlMGPBaseRewarder.queueMGP` for the victim), so `_calExpireForfeit(victim, amount)` is invoked.
   - Assert `getRewardablePercentWAD(victim)` returns a value significantly `< 1e18` even though the victim's cooldown slot amount is entirely past `endTime` (i.e., should be 100%).
   - Assert `forfeitAmount > 0` is queued via `_queueNewRewardsWithoutTransfer`.
6. Victim then calls `unlock(slotIndex)` and receives less than the full principal-associated reward share due to the forfeiture.
7. Attacker calls `getReward`/harvest on the vlMGPBaseRewarder and receives a reward amount proportional to `attackerBalance / totalStaked() * forfeitAmount`.
8. Assert: attacker's claimed reward from this single forfeiture event exceeds what their own MGP emission accrual (based purely on their own staking duration/amount, excluding the misrouted forfeiture) would justify, demonstrating that yield rightfully belonging to the victim's fully-unlocked position was captured by the attacker.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
```
