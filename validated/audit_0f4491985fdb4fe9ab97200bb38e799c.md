### Title
Unchecked ERC20 `transfer` return value in `incentiveDeposit` can silently fail while still crediting the reward as claimed - ([File: wombat/ArbWomUp.sol])

### Summary
`ArbWomUp.incentiveDeposit()` sends the computed USDT incentive reward via a raw `IERC20(usdt).transfer(...)` call whose boolean return value is never checked, while the contract unconditionally records the reward as `claimedReward[msg.sender]` before/regardless of whether the transfer actually succeeded.

### Finding Description
`incentiveDeposit` is a fully public, unprivileged-wallet function. It computes `rewardToSend`, deposits the user's WOM via `_deposit`, increments `claimedReward[msg.sender] += rewardToSend`, and then attempts to pay out USDT using a plain (non-`safe`) `transfer` call whose return value is discarded: [1](#0-0) 

Unlike `_deposit`, which correctly uses `safeTransferFrom` from OpenZeppelin's `SafeERC20`: [2](#0-1) 

the reward payout path at line 76 uses the raw ERC20 interface method without `SafeERC20`, even though the contract already imports and uses `SafeERC20` elsewhere in the same file. If the token configured as `usdt` is a non-standard ERC20 (e.g., real Tether USDT semantics, a blacklist/pausable stablecoin, or any token that returns `false` instead of reverting on failure — which is exactly the class of token the variable name `usdt` implies), a failed transfer (e.g., recipient blacklisted, or transfer fails for any other non-reverting reason) will return `false` but not revert. Because the return value is never checked:

- `claimedReward[msg.sender]` is permanently incremented as though the reward was paid.
- `getRewardAmount()` subtracts `claimedReward[_account]` from all future reward computations, so the user's future entitlement is permanently reduced by the amount that was never actually delivered.

### Impact Explanation
This causes permanent loss of the user's legitimately earned incentive reward: the accounting state (`claimedReward`) is updated as if payment succeeded even when it silently failed, and there is no mechanism to re-claim the undelivered USDT. This matches "permanent freezing/theft of unclaimed yield" — the user deposited real WOM (via `safeTransferFrom`, which does succeed) but is deprived of the promised USDT incentive with no recovery path, since the deposit and reward accounting are not atomic with respect to transfer success.

### Likelihood Explanation
Likelihood depends on the actual `usdt` token deployed being non-fully-compliant (e.g., blacklisting or other silent-failure semantics) — which is plausible given the contract is explicitly named around USDT and reward emission by an ordinary caller (`incentiveDeposit` has no access control). Any wallet calling `incentiveDeposit` while affected by the underlying token's failure conditions (e.g., blacklisted address, paused token state) triggers the bug without needing any privileged actor.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported via `using SafeERC20 for IERC20;`) for the USDT payout in `incentiveDeposit`, and only update `claimedReward` after the transfer is confirmed to succeed (or perform the transfer before updating accounting and revert on failure), consistent with the standard already applied in `_deposit`.

### Proof of Concept
1. Deploy `ArbWomUp` with `usdt` set to a token that returns `false` on failed transfers instead of reverting (e.g., blacklist-style token, or a mock replicating real Tether's non-standard behavior).
2. Cause the transfer condition to fail for a specific recipient (e.g., blacklist the caller in the mock token, or drain the contract's USDT balance so the transfer fails without reverting).
3. Call `incentiveDeposit(_amount)` as that user — `_deposit` succeeds (WOM pulled in), `claimedReward[msg.sender]` is incremented by `rewardToSend`, and `IERC20(usdt).transfer(msg.sender, rewardToSend)` returns `false` without reverting; the call completes successfully and emits `USDTRewarded`.
4. The user never receives USDT, yet `claimedReward[msg.sender]` permanently reflects the reward as paid, reducing all future reward computations in `getRewardAmount()` by that amount. [3](#0-2)

    function getRewardAmount(uint256 _amount, address _account) external view returns (uint256) {
        if (_amount == 0 || rewardMultiplier.length == 0) return 0;
        uint256 accumulated = _amount + userWOMDeposited[_account];

        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accumulated > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }
        rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];

        uint256 usdtReward = (rewardAmount / DENOMINATOR) - claimedReward[_account];
        uint256 usdtleft = IERC20(usdt).balanceOf(address(this));

        return usdtReward > usdtleft ? usdtleft : usdtReward;
    }
