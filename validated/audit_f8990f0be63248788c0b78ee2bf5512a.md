## Analysis

**Core broken invariant in the seed report:** `FlashLoans.flashLoan` trusts an ambient state (tokens sitting somewhere after a callback) instead of directly and exclusively controlling custody/authorization of that transfer — the contract doesn't itself enforce who is allowed to move the escrowed funds at that point.

**Local analog found:** `CallDispatcher.dispatch()` — the shared, singleton contract that `IntentGatewayV2` uses to custody and move funds mid-`placeOrder`/`fillOrder`/output-execution flow — has **no caller restriction whatsoever**. It is a plain `external` function, callable by anyone, that executes arbitrary attacker-supplied `Call[]` as the `CallDispatcher` itself, against any target, with any value. [1](#0-0) 

`IntentGatewayV2.placeOrder` relies on this contract as a temporary custodian: it transfers `predispatch.assets` into the dispatcher, runs the user-supplied `predispatch.call`, then measures the dispatcher's **token balance** (not a delta tied to a specific transfer) to decide how much to sweep back into escrow. [2](#0-1) [3](#0-2) 

The sweep only forwards tokens/ETH that correspond to `order.inputs`; the `_execute`/output-call path likewise dispatches arbitrary output calldata through the same shared dispatcher and only sweeps the tokens listed in `order.output.assets`. [4](#0-3) 

Any assets that land on the dispatcher outside of the exact set the gateway chooses to sweep (extra predispatch outputs, dust from partially-filled multi-asset unwraps, stray ETH from `receive()`) remain custodied by `CallDispatcher` between transactions. Because `dispatch()` has zero access control, **any unprivileged address can call it directly** and instruct the dispatcher to transfer out any ERC20/ETH it currently holds — this is not limited to `IntentGatewayV2`.

### Title
Unauthenticated `CallDispatcher.dispatch()` allows anyone to drain funds in transit through the IntentGateway escrow flow - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher`, the shared custodian contract used by `IntentGatewayV2` for predispatch escrow and output-call execution, exposes `dispatch(bytes)` as a fully public function with no `msg.sender` check. `IntentGatewayV2` assumes it is the only actor that can move funds through this contract (it trusts the dispatcher's balance state after its own calls), exactly the pattern the seed report criticizes: custody/authorization enforced by ambient state rather than an explicit access check. Any unprivileged attacker can call `CallDispatcher.dispatch()` directly to seize any ERC20/native balance the dispatcher is holding at that moment.

### Finding Description
`placeOrder` funds the dispatcher with `order.predispatch.assets`, executes the caller-supplied `order.predispatch.call` via `ICallDispatcher(dispatcher).dispatch(...)`, and then sweeps only the token amounts referenced in `order.inputs` back to the gateway using a balance snapshot rather than an exact accounted transfer: [5](#0-4) 

Order fulfillment reuses the same dispatcher for arbitrary `order.output.call` execution and sweeps only the listed output assets afterward: [6](#0-5) 

`CallDispatcher.dispatch` itself has no restriction on the caller: [1](#0-0) 

Because the dispatcher is a **single shared, long-lived contract address** (`_params.dispatcher`) reused across every order and every user, any token/ETH balance it accumulates outside the exact "swept" set (extra assets produced by a predispatch/output unwrap that aren't part of `order.inputs`/`order.output.assets`, or ETH sent via its `receive()`) is left sitting at that address with no protection. Since `dispatch()` performs no authorization check, an attacker can, at any time, submit their own transaction calling `CallDispatcher.dispatch()` with a `Call[]` such as `{to: token, data: transfer(attacker, balance)}` or `{to: attacker, value: address(this).balance}` to steal those funds — completely bypassing `IntentGatewayV2`'s escrow/order accounting.

### Impact Explanation
This is a direct, unauthenticated theft-of-funds primitive against a contract that is explicitly designed to hold user escrow assets mid-flow. It matches "stealing or loss of funds" / "unauthorized transaction or execution" in the bounty scope: an unprivileged attacker, with no relayer/prover/admin/governance role and no malicious-peer assumption, can drain value custodied by the protocol's own dispatcher contract.

### Likelihood Explanation
High. `dispatch()` requires only a normal, permissionless transaction. The precondition — the dispatcher holding some non-zero balance outside the currently-swept set — is realistic any time a predispatch/output call produces more token types than the order explicitly lists, or when native ETH is sent to the dispatcher (its `receive()` accepts it unconditionally), or during the brief windows where multiple `Call[]` legs execute in the same order flow. No special timing, front-running, or malicious relayer is needed once such a balance exists.

### Recommendation
Restrict `CallDispatcher.dispatch()` to an authorized caller only (e.g., an immutable `owner`/`intentGateway` address set at construction, with an `onlyAuthorized` modifier), or make each `CallDispatcher` instance single-use / ephemeral per order rather than a shared, indefinitely-reusable contract. Additionally, ensure all assets moved onto the dispatcher during a call are fully accounted for and swept before the transaction ends, so no residual balance can ever persist between transactions.

### Proof of Concept
1. Wait for (or induce, via a normal `placeOrder`/`fillOrder` predispatch/output call that produces an extra token type not listed in `order.inputs`/`order.output.assets`, or via anyone sending ETH to the dispatcher) a non-zero balance on the shared `_params.dispatcher` contract.
2. From any unprivileged EOA, call `CallDispatcher.dispatch(abi.encode(calls))` where `calls = [Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(token).balanceOf(dispatcher))})]` (or a native-value `Call` targeting `attacker` for ETH).
3. The dispatcher executes the transfer as itself with no check that the caller is `IntentGatewayV2`, and the funds move to the attacker. [1](#0-0)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
