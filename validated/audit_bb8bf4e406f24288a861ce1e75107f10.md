### Title
NFT Royalty Fee Avoidance via Integer Division Truncation - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
The Chia NFT1 royalty enforcement mechanism computes royalty payments using floor (integer) division of the offered/requested fungible amount by `MAX_ROYALTY_BASIS_POINTS` (10000). When the fungible payment amount is small relative to the royalty percentage, the computed royalty rounds down to zero, letting a counterparty in an NFT offer completely avoid paying the royalty that the NFT creator configured, analogous to the reported Allo `_fundPool` fee-rounding loophole.

### Finding Description
Royalty amounts for NFT1 offers are computed with plain floor division in two places: [1](#0-0) 

and [2](#0-1) 

Both `compute_royalty_amount` and `royalty_calculation` perform `amount * percentage // MAX_ROYALTY_BASIS_POINTS` style arithmetic. If `amount * percentage < MAX_ROYALTY_BASIS_POINTS` (10000), the result truncates to `0`. For example, with a 1% royalty (`percentage = 100`), any fungible payment amount below 100 mojos/units produces a royalty of exactly `0`, as demonstrated by the repository's own test: [3](#0-2) 

This computed royalty amount directly drives whether a royalty payment coin is even created in the offer construction flow. When the royalty payment for an asset sums to zero, the code explicitly skips generating the royalty-payout spend altogether: [4](#0-3) 

Additionally, on the offering side, trade prices for offer_mod settlement are filtered out entirely when the royalty computed from them would be zero: [5](#0-4) 

Because royalty enforcement is derived entirely from these per-trade truncating calculations (rather than from a cumulative/minimum-fee-guaranteed model), a counterparty constructing or accepting an offer can deliberately structure the fungible payment amount(s) to be small enough that `amount * percentage // 10000 == 0`, resulting in the NFT transfer proceeding with no royalty paid to the creator's `royalty_address`.

### Impact Explanation
This is a Medium-severity issue: the NFT creator/royalty beneficiary configured in the NFT's transfer program is guaranteed a percentage of the payment by design, but the truncating-division computation allows that guarantee to be bypassed for small-value trades or by splitting a larger trade into many small ones (e.g., via multiple sequential offers or multiple small fungible payment legs), each individually rounding the royalty down to zero. This undermines the economic mechanism NFT creators rely on for ongoing revenue, similar to how the Allo `_fundPool` fee could be avoided by contributing amounts small enough to round the fee to zero.

### Likelihood Explanation
Any unprivileged offer maker or taker who controls the payment amount in an NFT offer (a normal wallet operation reachable via `chia wallet make_offer` / `take_offer` or the wallet RPC) can trigger this by choosing small per-trade fungible amounts, or by decomposing a larger intended payment into many sub-threshold trades. No special privileges, node control, or protocol-level exploit is required — it is purely a function of the arithmetic used in constructing/accepting standard NFT1 offers.

### Recommendation
- Enforce a minimum royalty floor (e.g., round up rather than truncate, or reject trades whose royalty rounds to zero when `percentage > 0`) in `compute_royalty_amount` and `royalty_calculation` in `chia/wallet/nft_wallet/nft_wallet.py`.
- Consider rejecting offers where `amount > 0` and `percentage > 0` but the computed royalty is `0`, forcing a minimum trade size sufficient to produce a non-zero royalty.
- Audit `make_nft1_offer`'s skip-on-zero-royalty logic (`if sum(p.amount for _, p in payments) == 0: continue`) to ensure it isn't itself exploited to avoid the royalty spend construction for legitimately non-zero (but rounded-down) trades.

### Proof of Concept
1. Configure an NFT1 with a royalty of 1% (`royalty_percentage = 100` basis points) via `create_ownership_layer_puzzle`.
2. Construct (or take) an offer requesting a fungible payment (XCH or CAT) of `50` units in exchange for the NFT.
3. `compute_royalty_amount(offered_amount=-50, royalty_split=1, percentage=100)` returns `uint64(0)` as shown directly by the existing unit test `test_small_amount_truncates_to_zero` in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py:42-44`.
4. The offer settles with the NFT transferred and the full payment going to the seller, while the royalty beneficiary receives `0`, despite the NFT's configured 1% royalty.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```

```python
    ) -> dict[Any, list[dict[str, Any]]]:
        summary_dict: dict[Any, list[dict[str, Any]]] = {}
        for id, royalty_info in royalty_assets_dict.items():

            summary_dict[id] = []
            for name, amount in fungible_asset_dict.items():

                    {
                        "asset": name,
                        "address": address,
                        "amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
                    }
                )

        return summary_dict
```
