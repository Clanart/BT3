### Title
ReDoS in RuleEngine._regex_match allows attacker-controlled hookify rule patterns to hang PreToolUse hook enforcement - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._regex_match` compiles and executes user/attacker-controlled `pattern` strings from `.claude/hookify.*.local.md` files with no timeout, complexity check, or safe-regex validation. Since `pretooluse.py` calls `load_rules()` → `evaluate_rules()` → `_regex_match()` on every Bash/Edit/Write/MultiEdit tool call, a single catastrophic-backtracking pattern (e.g. `(a+)+$`) written into a rule file causes the hook process to hang indefinitely on any matching input, blocking the hook enforcement path for that call.

### Finding Description
The `/hookify` command (`plugins/hookify/commands/hookify.md`) explicitly instructs the model to write regex patterns supplied via `$ARGUMENTS` or inferred from conversation content into rule frontmatter fields (`pattern:` or `conditions[].pattern`) without any sanitization or complexity check [1](#0-0) . These files are parsed by `extract_frontmatter`/`load_rule_file` in `config_loader.py` with a hand-rolled YAML parser that performs no validation on the `pattern` value [2](#0-1) .

On every Bash/Edit/Write/MultiEdit tool invocation, `pretooluse.py` calls `load_rules()` then `RuleEngine.evaluate_rules()` [3](#0-2) , which for each rule with `operator == 'regex_match'` calls `self._regex_match(pattern, field_value)` [4](#0-3) . `_regex_match` compiles the pattern via the `lru_cache`-wrapped `compile_regex` and calls `regex.search(text)` with no timeout, size limit, or ReDoS-safety check: `re.error` is caught, but a hang during matching is not [5](#0-4) . `_extract_field` supplies attacker/agent-influenced text (e.g. `command`, `new_string`, `content`) as the subject string being matched against [6](#0-5) , so any tool call whose relevant field contains a string that triggers exponential backtracking against the stored pattern (e.g. a run of `a` characters followed by a non-matching character against `(a+)+$`) will make `_regex_match` hang.

Because `pretooluse.py`'s top-level `try/except` only catches exceptions that actually raise (not hangs) and always calls `sys.exit(0)` in a `finally` block only after `main()` returns [7](#0-6) , a hang in `regex.search` blocks the whole hook process from ever printing output or exiting, stalling every subsequent PreToolUse-gated Bash/Edit/Write/MultiEdit call until the process is killed or times out at the Claude Code hook-execution layer.

### Impact Explanation
This is a persistent denial-of-service against the hook enforcement path: once such a rule file exists in `.claude/`, every qualifying tool call whose target field content matches the vulnerable pattern's backtracking trigger will hang the PreToolUse hook. Since `pretooluse.py` fails open only on exceptions/timeouts handled by the outer Claude Code hook runner (not by hookify itself), this can either freeze tool execution or, if the outer runner enforces its own hook timeout and then treats a timed-out hook as "no decision" (fail-open), silently disable rule enforcement for all subsequent dangerous Bash/Edit/Write calls — undermining the "hook enforcement availability must not be attacker-disruptable" invariant.

### Likelihood Explanation
Feasible and repeatable: the `/hookify` command flow (`hookify.md`) actively encourages generating rule `pattern` values from conversation content or `$ARGUMENTS`, and there is no allowlist, complexity/timeout guard, or regex-safety validation anywhere in `config_loader.py` or `rule_engine.py`. Any workflow where regex patterns originate from less-trusted text (explicit user instruction text, agent-extracted "problematic patterns" from repo/conversation content) can introduce a ReDoS pattern into a `.claude/hookify.*.local.md` file, and it will be exercised on the very next matching tool call.

### Recommendation
Add a hard wall-clock timeout around `regex.search`/`regex.match` calls in `_regex_match` (e.g., via a worker thread/process with `concurrent.futures` and a timeout, since `signal.alarm`-based timeouts are not thread-safe/portable), and/or validate patterns at rule-load time with a ReDoS-detection library (e.g. rejecting nested unbounded quantifiers) before caching them in `compile_regex`. Also cap the length of the text being matched (`field_value`) to bound worst-case backtracking cost, and ensure `pretooluse.py`/`posttooluse.py`/`stop.py`/`userpromptsubmit.py` treat a timeout as fail-open (return `{}`) rather than hanging indefinitely.

### Proof of Concept
Unit/fuzz test in `plugins/hookify/core/rule_engine.py` test suite:
```python
import time
from hookify.core.rule_engine import RuleEngine
from hookify.core.config_loader import Rule, Condition

def test_regex_match_redos_timeout():
    rule = Rule(
        name="evil",
        enabled=True,
        event="bash",
        conditions=[Condition(field="command", operator="regex_match", pattern=r"(a+)+$")],
        message="x",
    )
    engine = RuleEngine()
    evil_input = {
        "tool_name": "Bash",
        "tool_input": {"command": "a" * 40 + "!"},  # triggers catastrophic backtracking
    }
    start = time.monotonic()
    engine.evaluate_rules([rule], evil_input)
    elapsed = time.monotonic() - start
    assert elapsed < 1.0, f"_regex_match hung for {elapsed}s on ReDoS pattern"
```
Expected today: the assertion fails (call takes seconds-to-minutes depending on input length, growing exponentially), demonstrating the hang. After a fix (timeout/safe-regex enforcement), the call should return quickly with a fail-open `{}` result instead of hanging.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:

            content = f.read()

            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule

    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
