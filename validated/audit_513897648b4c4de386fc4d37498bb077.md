### Title
Embedded fake conflict-marker text in an attacker-controlled merge side causes Copilot conflict resolution to mis-locate the real conflict boundary and silently commit corrupted/leftover marker content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's AI-assisted merge-conflict resolution feature parses conflicted files twice with two independently-implemented, non-identical marker scanners: `extractConflictHunks()` in `app/src/lib/copilot-conflict-context.ts` (used to build the prompt sent to the model) and `reassembleResolvedFile()` in `app/src/lib/copilot-conflict-resolution.ts` (used to splice the model's per-hunk answer back into the file that gets written to disk and staged for commit). Both scanners locate the *closing* `>>>>>>>` marker of a hunk by taking the **first** line that matches the theirs-marker regex, rather than the one that actually corresponds to the real conflict block. If the "theirs" side of a real merge conflict (fully attacker-controlled, e.g. a PR/branch the user merges) contains literal text that matches the conflict-marker regexes (`<{7}`, `={7}`, `>{7}` at line start), the real conflict block gets truncated at the fake marker, and the remaining real content — including a literal `>>>>>>>` line — is copied through as ordinary, "already resolved" text into the final file that Desktop writes back to the working directory. ### Finding Description
`extractConflictHunks()` collects the "theirs" side of a hunk with a loop that stops at the **first** line matching `theirsMarker` (`/^>{7}(?:\s|$)/`): [2](#0-1) 

`reassembleResolvedFile()` independently re-derives the same "closing marker" position for the raw file on disk, again by scanning forward for the first line matching `reassemblyTheirsMarker`: [3](#0-2) 

Neither scanner verifies that the `<<<<<<<`/`=======`/`>>>>>>>` triad it finds is *balanced* (i.e., that there isn't another, unrelated triad of the same characters nested inside the "theirs" text). If the incoming ("theirs") side of a genuine merge conflict — content fully controlled by whoever authored the branch/PR being merged — contains a line consisting of exactly 7 `<`, `=`, or `>` characters at the start of a line (plausible in heredocs, diff/patch fixtures, ASCII banners, changelog dividers, or content deliberately crafted to look like this), both parsers will treat that embedded text as the real closing marker:

- `extractConflictHunks()` ends the hunk's `theirsContent` early, hiding the real trailing content from the model and from the hunk count sent for validation.
- `reassembleResolvedFile()` independently truncates the *replaceable span* at the same fake marker when splicing the model's answer back into the original file.

Because both stages agree on hunk *count* (each only sees "1 hunk" for this block), `validateResolutionPaths()`'s count check does not catch the discrepancy: [4](#0-3) 

The consequence is that everything *after* the fake closing marker (the real remaining theirs content and the real `>>>>>>>` line) falls outside the recognized conflict block. In `reassembleResolvedFile()`'s main loop, that leftover text is not re-checked against `reassemblyOursMarker` and is copied through verbatim as ordinary, already-resolved file content: [5](#0-4) 

The only marker sanity check in the pipeline operates on the *model's returned hunk text*, not on the final reassembled file, so it cannot catch corruption introduced by mis-splitting the *original* content: [6](#0-5) 

The result: `reassembleResolutions()` returns a `resolvedContent` that Desktop treats as a fully "resolved" file (no further marker scan is performed downstream), even though it still contains a literal `>>>>>>>` line and/or the real trailing content merged in the wrong place. [7](#0-6) 

### Impact Explanation
This lets an attacker who only controls a git ref that the victim merges (a branch, a PR "theirs" side, or a fetched remote update — no local access, no credentials, no social engineering beyond a normal collaborative merge) cause Desktop's Copilot conflict-resolution feature to silently write and stage a corrupted file: dangling/garbled conflict-marker text embedded in what is presented to the user as a clean, fully-resolved file. This matches the requested impact class "silent corruption of what the user commits or pushes" — the user reviews a resolution dialog that reports success, then commits/pushes a file containing residual marker syntax or subtly misplaced code that was never actually seen or approved as such by the AI or the user.

### Likelihood Explanation
Requires only that the attacker's branch/PR content contains, anywhere within a real conflicted region's "theirs" side, a line matching `^<{7}`, `^={7}`, or `^>{7}` — a plausible, easily craftable pattern (heredocs, ASCII dividers, embedded diff/patch snippets, deliberately crafted "poison" lines) that a reviewer casually skimming a diff is unlikely to notice as significant. The feature is opt-in per merge/rebase/cherry-pick conflict, but once invoked, the corruption is fully automatic and silent — no additional unnatural user steps are required beyond normal use of the AI conflict-resolution flow.

### Recommendation
Make `extractConflictHunks()` and `reassembleResolvedFile()` share a single, robust parser that matches the closing `>>>>>>>` to its corresponding `<<<<<<<`/`=======` by tracking nesting depth (or, simpler, reject/flag any hunk whose "ours"/"theirs" content itself contains lines matching the conflict-marker regexes, treating it as unparseable and falling back to manual resolution). Additionally, after `reassembleResolvedFile()` produces the final content, re-scan the output for any of the `oursMarker`/`separatorMarker`/`theirsMarker` patterns and refuse to treat the file as "resolved" (surface it in `copilotSkippedFiles` instead) if any are still present.

### Proof of Concept
1. On `main`, create `bad.txt` with real conflicting content on the `theirs` (incoming) side that embeds a fake nested marker triad, e.g.:
```
<<<<<<< HEAD
ours line
=======
theirs line A
<<<<<<< fake
fake ours
=======
fake theirs
>>>>>>> fake
theirs line B (real, should survive)
>>>>>>> feature
```
2. Trigger a merge that produces this exact conflict (ours = `HEAD` branch content, theirs = `feature` branch content including the embedded fake triad).
3. Invoke Desktop's "Resolve with Copilot" conflict-resolution flow on this conflict.
4. Observe: `extractConflictHunks()` reports only "theirs line A" (missing "theirs line B"), so the model never sees or resolves "theirs line B (real, should survive)". `reassembleResolvedFile()` then splices the model's single hunk answer in place of everything from `<<<<<<< HEAD` through `>>>>>>> fake`, leaving `theirs line B (real, should survive)` and the literal `>>>>>>> feature` line in the final "resolved" file content that Desktop writes to disk and reports as successfully resolved.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
