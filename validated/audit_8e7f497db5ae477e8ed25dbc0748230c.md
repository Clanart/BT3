### Title
Post-OAuth redirect can be sent to an attacker-controlled path via unsanitized `return_to`/`host` concatenation - (File: app/controllers/shopify_app/callback_controller.rb)

### Summary
`CallbackController#redirect_to_app` builds the final post-install redirect URL by concatenating `decoded_host` (derived from the `host` query param) with `return_to` (an app-relative path taken from `session[:return_to]`) when `return_to` is not already a fully-formed URL. A phishing check (`deduced_phishing_attack?`) is computed to catch untrusted `host` values, but it is only used to override the redirect when it evaluates true — the underlying string concatenation building `redirect_to` from `decoded_host` and `return_to` is otherwise sent to `redirect_to(..., allow_other_host: true)` without re-verifying that the resulting composed value stays within the intended shop origin.

### Finding Description [1](#0-0) 
`redirect_to_app` computes `return_to = session.delete(:return_to)` and, if it's not a fully-formed URL, builds `redirect_to = "#{decoded_host}#{return_to}"` where `decoded_host` comes from `ShopifyAPI::Auth.embedded_app_url(params[:host])`: [2](#0-1) 
The `deduced_phishing_attack?` check sanitizes the host derived from `params[:host]` and only forces a safe fallback (`root_url`) when the sanitized host is `nil`. However, `return_to` itself — sourced originally from `session[:return_to]` populated via `RedirectSafely.make_safe(params[:return_to], "/")` earlier in the flow — is only guaranteed to be a "safe" relative path (via `RedirectSafely`), not validated against the shop context. Because `redirect_to(..., allow_other_host: true)` is used, once `decoded_host` passes the "is it a trusted domain" check, the composed URL is sent with `allow_other_host: true`, bypassing Rails' open-redirect protection for the final composed string, with no re-verification step that ties the corrected/validated host or path to the actual authenticated `api_session.shop`.

### Impact Explanation
If `return_to` or the composition logic can be influenced to encode a path that, when appended to a legitimately-trusted `decoded_host`, resolves outside the intended app route (e.g., via `//evil.com` styled relative paths or path traversal within the return_to value), the app will issue a redirect with `allow_other_host: true`, which explicitly disables Rails' host-safety check on the final target. This does not by itself steal tokens or bypass authentication, so it should be treated with likelihood/impact caveats. I could not confirm a concrete bypass of `RedirectSafely.make_safe` producing an off-origin string within this session, so I cannot assert conclusively this is exploitable without further investigation of `RedirectSafely.make_safe`'s guarantees.

### Likelihood Explanation
Low-to-medium: reaching this path requires completing (or partially completing) an OAuth callback with attacker-controlled `return_to`/`host` params, which is possible since these are anonymous, pre-auth query parameters accepted at `/login` before being copied into the session by `copy_return_to_param_to_session` in `SessionsController` (see `app/controllers/shopify_app/sessions_controller.rb#L109-L111`). The actual exploitability hinges on whether `RedirectSafely.make_safe` fully closes off open-redirect vectors, which was not verifiable from the available index.

### Recommendation
Re-validate the fully composed `redirect_to` string against the app's own trusted origin (not just the `host` param) immediately before calling `redirect_to`, and avoid `allow_other_host: true` unless the final composed URL has been confirmed to match a Shopify-trusted domain computed via `ShopifyApp::Utils.sanitize_shop_domain`, applying the corrected/sanitized value directly into the value passed to `redirect_to` rather than only using the check to trigger a fallback in the negative case.

### Proof of Concept
Not independently verified against live code (no test/terminal access in this mode); recommend a Devin session to trace `RedirectSafely.make_safe` behavior and attempt to craft a `return_to` value that survives sanitization yet composes into an off-origin URL when concatenated with `decoded_host`, then confirm via `test/controllers/callback_controller_test.rb` that `redirect_to_app` accepts it.

      if ShopifyAPI::Context.embedded?
        return_to = session.delete(:return_to)

        else

      sanitized_host = ShopifyApp::Utils.sanitize_shop_domain(URI(decoded_host).host)
      if sanitized_host.nil?
        ShopifyApp::Logger.info("host param from callback is not from a trusted domain")
