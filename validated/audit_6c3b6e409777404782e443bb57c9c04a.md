Based on the investigation, the closest analog to the reported bug class ("missing verification that a caller-supplied type matches the authoritative type before performing a privileged operation") is the git credential helper's host-classification logic in `app/src/lib/trampoline/trampoline-credential-helper.ts`.

### Title
Attacker-controlled `WWW-Authenticate` header spoofs GitHub host classification, triggering unauthorized GitHub sign-in/account-binding flow for arbitrary remotes - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Move report's root cause is that `place_market_order`/`place_limit_order` trusted caller-supplied generic type parameters as if they were verified against the market's actual stored types, with no assertion tying the two together. The Desktop analog is `getEndpointKind()`, which is responsible for classifying whether a remote Git host is "GitHub-like" (and therefore eligible for Desktop's internally-stored GitHub credentials/sign-in flow) versus a truly third-party ("generic") host. Instead of relying solely on an authoritative source (known endpoint list, TLS identity, or a verified network probe), it partially trusts a value that is fully attacker-controlled: the `WWW-Authenticate` response header sent by the remote Git server itself.

### Finding Description
`getEndpointKind` is invoked from `getCredential`, `storeCredential`, and `eraseCredential` [1](#0-0) . When neither `isGist`, `isDotCom`, nor `isGHE` (all safe, string-based checks against `endpoint`) match, the function falls back to inspecting `wwwauth[]` entries that were parsed straight from Git's credential-helper stdin protocol: [2](#0-1) 

These `wwwauth[...]` values originate from the `WWW-Authenticate` HTTP header that the remote Git server returned during the authentication challenge — a header fully controlled by whatever server the user's `git fetch`/`push`/`pull`/`clone` targets. If that value contains the substring `realm="GitHub"`, the function immediately returns `'enterprise'`, i.e., it treats the third-party host as if it were a verified GitHub Enterprise Server, with no cryptographic binding, no cross-check against a known-endpoint list, and no network probe (the network probe (`isGitHubHost`) is only used as the last-resort fallback, after the header check already short-circuits the classification).

This mirrors the reported bug precisely: the code path that should distinguish "verified GitHub type" from "arbitrary/generic type" instead accepts an unauthenticated, attacker-supplied label as ground truth.

### Impact Explanation
Once `getEndpointKind` returns `'enterprise'` for a malicious host:
- `getCredential` skips the "generic" credential path entirely (`if (endpointKind !== 'generic') return undefined` after the account-check branch) [3](#0-2) , and — if no existing account's `endpoint` matches — calls `ui.promptForGitHubSignIn(endpoint)` for the attacker's arbitrary host [4](#0-3) . This causes Desktop to initiate a GitHub-branded sign-in/OAuth account-binding flow for a host the user never explicitly registered as an Enterprise endpoint, based purely on a claim embedded in a network response from that same host.
- `storeCredential`/`eraseCredential` silently skip persisting/removing the user's generic credentials for that host (since the "GitHub.com/GHE creds are only stored internally" branch is taken), which can corrupt or drop the user's intended generic-auth configuration for what may in fact be a legitimate non-GitHub server that merely echoes a spoofed realm string.

This satisfies the impact category "unauthorized OAuth or account binding" triggered purely by fetching/pushing to an attacker-controlled remote or proxy response — no local access, malware, or leaked credentials required.

### Likelihood Explanation
Any attacker who controls, or can man-in-the-middle/proxy, a Git HTTP(S) remote that a Desktop user adds, clones, or is redirected to can trivially include `WWW-Authenticate: Basic realm="GitHub"` (or similar) in a 401 response during the standard Git smart-HTTP authentication handshake. No special crafting beyond a standard HTTP header is needed, and the classification runs automatically whenever Desktop's `desktop-trampoline` credential helper is invoked during `fetch`/`pull`/`push`/`clone` [5](#0-4) . Existing guards (`isGist`, `isDotCom`, `isGHE` in `app/src/lib/endpoint-capabilities.ts`) are strictly hostname-based and do not stop this path since the header check is reached only when those hostname checks already fail — i.e., precisely for hosts that are *not* known GitHub domains. [6](#0-5) 

### Recommendation
Remove or de-prioritize the `WWW-Authenticate` realm heuristic as a basis for classifying a host as GitHub-like, or at minimum treat it only as a weak hint that must still be confirmed via the authoritative network probe (`isGitHubHost`) rather than short-circuiting classification. Any host not matching `isDotCom`/`isGHE`/a stored account endpoint should require an explicit, verifiable check (e.g., the existing `isGitHubHost` HTTP probe with response header validation) before being treated as `'enterprise'` and before invoking `promptForGitHubSignIn`.

### Proof of Concept
1. Stand up a malicious Git-over-HTTP server (or a MITM proxy in front of a legitimate non-GitHub remote) that responds to Git's authentication probe with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, add this server as a remote (e.g., `git remote add evil https://attacker.example.com/repo.git`) or clone directly from it, then perform a `fetch`.
3. Git invokes the `desktop-trampoline` credential helper, forwarding the spoofed `wwwauth[]=Basic realm="GitHub"` value in the credential-helper protocol input.
4. `getEndpointKind` returns `'enterprise'` for `attacker.example.com` purely from this header [7](#0-6) .
5. Since no account exists for `attacker.example.com`, Desktop calls `ui.promptForGitHubSignIn('https://attacker.example.com')`, surfacing a GitHub-style sign-in/OAuth prompt scoped to the attacker's domain [8](#0-7) , despite the user never having configured this host as a GitHub Enterprise endpoint.

**Note on completeness:** I could not fully trace the downstream `promptForGitHubSignIn`/`ui.ts` implementation and the OAuth device/browser flow it triggers within the indexed context, so I cannot confirm with certainty whether this flow could be abused to phish or bind real GitHub.com/Enterprise account tokens to the attacker's endpoint, versus simply initiating a (harmless) sign-in against the attacker's own server. If you need to verify that downstream behavior precisely, a full Devin session with complete repository access would be needed to trace `trampoline-ui-helper.ts` and the sign-in store logic in detail.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

## What's a Trampoline?

There are many different descriptions for "trampoline" in computing but in this
situation the trampoline is a component to pass inputs and outputs between
programs that are otherwise challenging to integrate.

On one side, we have Git, which has a number of ways it can authenticate the
user against a HTTPS remote.

On the other side, we have GitHub Desktop - an Electron app that is primarily
running as a GUI. Electron also supports
[environment variables](https://electronjs.org/docs/api/environment-variables)
that allow us to run it like a command-line program.

To set an AskPass program for Git, we set the `GIT_ASKPASS` environment variable
to our executable on disk. This is done by Desktop whenever it needs to spawn a
Git operation that might require authentication.

The equivalent Bash shell code looks like this:

```sh
  # environment variable
  GIT_ASKPASS="C:/some/path/to/desktop-askpass-trampoline.exe" \
  # ensure Git doesn't block the process waiting for the user to provide input
  GIT_TERMINAL_PROMPT=0 \
  git \
  # unset the credential.helper defined in config
  -c credential.helper= \
  clone https://github.com/shiftkey/my-private-repo.git
```

Desktop also sets these environment variables when spawning Git, as it's the
only way to pass information down to the authentication process:

- `DESKTOP_USERNAME` - the account associated with the current repository
- `DESKTOP_ENDPOINT` - the endpoint associated with the account

With this trampoline, all this info can be passed from GitHub Desktop to Git,
and then back to GitHub Desktop via a TCP socket when Git requires us the user
credentials, so Desktop can act based on that username and endpoint.

export const isDotCom = (ep: string) => {
  if (ep === getDotComAPIEndpoint()) {
    return true
  }

  const { hostname } = new URL(ep)
  return hostname === 'api.github.com' || hostname === 'github.com'
}

export const isGist = (ep: string) => {
  const { hostname } = new URL(ep)
  return hostname === 'gist.github.com' || hostname === 'gist.ghe.io'
}

/** Whether or not the given endpoint URI is under the ghe.com domain */
export const isGHE = (ep: string) => new URL(ep).hostname.endsWith('.ghe.com')
