## Title
CPI account data-length compute cost is divided per-account instead of on the aggregate sum, causing systematic compute-cost underpricing - (File: `program-runtime/src/cpi.rs`)

### Summary
During a cross-program invocation (CPI), the compute cost charged for translating caller `AccountInfo`/`SolAccountInfo` account *data* is computed once **per account** by dividing that account's raw data length by `cpi_bytes_per_unit` and truncating the result, rather than summing all accounts' data lengths first and dividing once. This mirrors the Isomorph `Vault_Velo` bug class: two logically equivalent valuations (single aggregate division vs. per-item division) diverge due to repeated integer-division truncation, and the version that divides item-by-item under-reports the true cost.

### Finding Description
In `program-runtime/src/cpi.rs`, `CallerAccount::from_account_info` and `CallerAccount::from_sol_account_info` each charge the compute meter for an individual account's data length independently: [1](#0-0) [2](#0-1) 

These functions are invoked once per translated account inside the CPI account-translation loop in `translate_accounts_common`, which calls `do_translate` (i.e. `from_account_info`/`from_sol_account_info`) separately for every `caller_account_index`: [3](#0-2) 

Each call performs `data.len().checked_div(cpi_bytes_per_unit)` independently, truncating the remainder of up to `cpi_bytes_per_unit - 1` bytes' worth of cost on every single account. By contrast, the same file computes the cost for the fixed-size `AccountInfo`/`SolAccountInfo` struct array as one aggregate division over the total byte count in `translate_account_infos`: [4](#0-3) 

This is the exact truncation asymmetry described in the reference report: summing before dividing (as in `translate_account_infos`) yields the mathematically correct, minimally-truncated cost, while dividing before summing (as in the per-account `data.len()` cost, repeated for every account in `translate_accounts_common`) truncates once per item and therefore under-charges the compute meter relative to the "correct" aggregate cost. With up to `MAX_CPI_ACCOUNT_INFOS` (255) accounts translatable per CPI call, and `cpi_bytes_per_unit = 250` by default: [5](#0-4) [6](#0-5) 

a malicious program can choose account data lengths that maximize the per-account truncation remainder (e.g., each account's data length modulo 250 close to 249), losing up to 249 CU of unbilled cost on every account instead of that remainder being computed only once against the aggregate sum. This can be repeated on every CPI call within the instruction trace, compounding the underpricing across a single transaction.

### Impact Explanation
This is a compute-metering correctness bug: the CPI path exists precisely to bound compute consumption for cross-program interactions, and account-data translation cost is one of the priced resources (`cpi_bytes_per_unit`). Systematically under-metering this cost lets programs perform more "free" work (more/larger account translations) than the cost model intends, which is the class of "materially underpriced compute" that the validation criteria call out as in-scope.

### Likelihood Explanation
This is trivially triggerable by any unprivileged BPF program performing CPI with many small/medium accounts whose data lengths are chosen to maximize truncation remainder — no special permissions, mocked components, or validator/operator role is required. It only requires normal `invoke_signed`/CPI usage available to any on-chain program, exercised through the already-existing `translate_accounts_common` / `CallerAccount::from_account_info` / `from_sol_account_info` code paths.

### Recommendation
Compute the compute-unit cost for account-data translation once, over the aggregate sum of all translated accounts' `data.len()` (or `data_len` for the C ABI), analogous to how `translate_account_infos` already aggregates the `account_infos_bytes` cost, instead of calling `checked_div(cpi_bytes_per_unit)` separately inside each `CallerAccount::from_account_info` / `from_sol_account_info` invocation.

### Proof of Concept
Conceptually: construct a CPI instruction (via `sol_invoke_signed`) referencing `MAX_CPI_ACCOUNT_INFOS` (255) distinct accounts, each with data length `k` such that `k % cpi_bytes_per_unit == cpi_bytes_per_unit - 1` (e.g. `k = 249`). Under the current per-account division in `CallerAccount::from_account_info`/`from_sol_account_info` (`program-runtime/src/cpi.rs:358-362`, `472-477`), each account contributes `0` extra CU beyond `mem_op_base_cost`-independent charges for its 249 bytes (truncated away), for a total truncation loss of up to `255 * 249 ≈ 63,495` CU versus what a single aggregate-sum-then-divide computation (`(255*249) / 250 = 253` CU) would charge. This gap can be repeated across every CPI call permitted within the instruction trace, amplifying the total underpriced compute for the transaction.
