Based on the report's core invariant — **rewards (state) computed at time T1 get attributed/applied based on a different, freshly-observed state at time T2, with no check that the underlying context hasn't shifted in between** — I found a structurally analogous flaw in GitHub Desktop's partial-commit staging path.

### Title
Stale line-selection bitmap applied against a freshly re-fetched diff during partial-file staging causes silent commit-content corruption - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages only some lines of a modified file ("partial commit"), Desktop stores the user's line selection as a bitmap of *absolute diff-line indices* on the `WorkingDirectoryFileChange` object [1](#0-0) . At commit time, instead of reusing the diff the user actually reviewed and selected lines against, `applyPatchToIndex` re-fetches a brand-new diff straight from disk via `getWorkingDirectoryDiff(repository, file)` [2](#0-1)  and then feeds that fresh diff together with the *old* selection bitmap into `formatPatch` [3](#0-2) . Inside `formatPatch`, each line of the new diff is checked against the old selection purely by absolute index: `file.selection.isSelected(absoluteIndex)` [4](#0-3) . There is no verification that the new diff's hunk layout (line counts, offsets, content) still matches the diff the indices were computed from.

### Finding Description
This is the same broken invariant as the Sherlock report: settlement (staging/committing) is performed against "whoever/whatever is present now" rather than "what actually earned/was reviewed during the accrual period." Here, the accrual period is the time between the user visually reviewing/selecting diff hunks in the Changes view and the moment they click "Commit." If the on-disk content of the file changes during that window (e.g. a build tool, formatter-on-save, dev server hot-reload script, or a postinstall/watch task bundled in a cloned/fetched repository rewrites the tracked file), `getWorkingDirectoryDiff` at staging time returns a diff with different hunk boundaries and line offsets than the one the selection bitmap was built against [2](#0-1) . The stale absolute-index selection is then silently reapplied to the new hunk structure, so `formatPatch` can select/deselect the wrong lines, drop hunks whose indices moved, or crash with `git apply` failure that is caught upstream without alerting the user to the real cause [5](#0-4) . The higher-level orchestrator `_commitIncludedChanges` in `app-store.ts` also snapshots `selectedFiles` from cached state without re-validating the diff right before staging [6](#0-5) , so there's no guard anywhere in the commit path against this drift.

### Impact Explanation
The result is silent corruption of what the user actually commits/pushes relative to what they reviewed and explicitly approved in the diff viewer — the same class of impact called out as valid (commit/push content corruption). A user who staged only a safe subset of lines could end up committing unreviewed/malicious lines introduced by repo-bundled tooling, or could silently drop their own intended changes, with no error surfaced.

### Likelihood Explanation
This requires an external process to touch the tracked file's content between diff display and commit — most plausibly a build/watch/format-on-save script shipped with a cloned/fetched project that the user runs as part of a normal workflow (not an "unprompted unnatural" step). This is a narrower trigger than a fully remote, no-interaction attack, so likelihood is moderate rather than high, but the code path itself has zero staleness protection, so any such natural workflow (editor auto-format, linter --fix, hot-reload writing generated files back into source) reliably triggers it.

### Recommendation
`applyPatchToIndex` should not silently re-fetch a new diff at staging time. It should either (a) reuse the exact diff object the user's selection was computed against and fail loudly/re-prompt if the on-disk content hash has changed since that diff was generated, or (b) re-derive the user's selected *content* (not raw indices) against the fresh diff before formatting the patch, aborting the commit and surfacing an explicit "file changed since review" error rather than proceeding with a possibly mismatched patch.

### Proof of Concept
1. Open a repository in Desktop and modify `file.txt`, selecting only some lines for the commit (partial selection) in the Changes view.
2. Before clicking "Commit," have any external process (e.g. `npm run build`/formatter/watch script from the repo) rewrite `file.txt` with different line offsets (add/remove lines above the previously selected hunk) without the user re-opening the diff.
3. Click "Commit." `applyPatchToIndex` fetches the new diff [2](#0-1)  and `formatPatch` applies the old absolute-index selection to it [5](#0-4) , producing a patch that stages different lines than the ones the user reviewed/selected — or fails with a generic `git apply` error that doesn't indicate the real cause.
