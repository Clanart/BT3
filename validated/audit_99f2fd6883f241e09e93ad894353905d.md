### Title
Divergent conflict-marker parsing between `extractConflictHunks` and `reassembleResolvedFile` causes mis-spliced (silently corrupted) Copilot merge-conflict resolutions - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The external report's broken invariant is: **two functions that are supposed to agree on the meaning/scale of the same index disagree, and the mismatch is never validated, so data meant for one target is silently applied to another.** In `depositAndAllocateForPartyB`, `amount` meant 18-decimals in one call and native-decimals in the sibling call. In GitHub Desktop's Copilot-assisted merge-conflict resolution feature, the analogous invariant is the **ordinal index of a conflict hunk**: `extractConflictHunks` (used to build the prompt sent to the model) and `reassembleResolvedFile` (used to splice the model's per-hunk answers back into the file) each independently re-parse the same raw file text to find conflict-marker blocks, but they use subtly different boundary-detection rules. On attacker-crafted marker sequences the two parsers disagree about how many hunks exist and where they start/end, so hunk *N* as understood by the prompt-builder is not hunk *N* as understood by the splicer. The splice is matched "by order, not by line number" [1](#0-0) , with no re-validation against the original markers, so resolved content ends up in the wrong place in the committed file with no error surfaced to the user.

### Finding Description
`extractConflictHunks` scans for hunks like this: once it sees a `<<<<<<<` line it collects "ours" lines in an inner loop that terminates **only** on a base marker (`|||||||`) or separator (`=======`) — it never checks for the closing `>>>>>>>` marker in that inner loop: [2](#0-1) 

If a `<<<<<<<...>>>>>>>` block is present **without** a `=======` separator (a malformed/attacker-crafted block, or even just literal `<<<<<<<` text that appears in a file being merged, e.g. inside a code sample, changelog, or generated diff-like content on the attacker's branch), this loop does not stop at the `>>>>>>>` line — it keeps swallowing lines as "ours" content until it finds the *next* `=======` or `|||||||` anywhere later in the file, which may belong to an entirely different, legitimate conflict hunk further down. This silently merges two hunks into one and desynchronizes the hunk count/boundaries that get sent to the model via `formatConflictContextForPrompt` (`### Conflict i of N`) [3](#0-2) .

`reassembleResolvedFile`, used later to splice the model's answers back into the on-disk file, parses the **same raw content** with a different rule: it looks ahead for a separator and then a `>>>>>>>`, and if the `>>>>>>>` is found *before* any `=======`, it treats the leading `<<<<<<<` line as plain non-conflict text and does not skip past the block: [4](#0-3) 

Because these two parsers can disagree on hunk boundaries/count for the exact same input, the number and identity of "hunks" the model was asked about (from `extractConflictHunks`) can differ from the number and identity of marker blocks `reassembleResolvedFile` actually finds when splicing. The only cross-check that exists, `validateResolutionPaths`, compares the model's returned hunk count against `expectedFiles` hunk counts — but `expectedFiles` hunk counts come from the *same* (buggy) `extractConflictHunks` call [5](#0-4) , so this check cannot detect the divergence against `reassembleResolvedFile`'s independent parse. The splice itself performs no sanity check that the marker block it is about to replace corresponds to the hunk index it is using: `hunkResolutions[hunkIndex].resolvedContent` is applied purely positionally [6](#0-5) .

### Impact Explanation
`buildConflictContext` reads the raw file directly off disk during a live merge/rebase/cherry-pick conflict [7](#0-6) , i.e. content that originates from a remote branch/PR the user is merging — attacker-controlled if the user merges a malicious fork/branch. If that content contains a crafted `<<<<<<<...>>>>>>>` sequence lacking a `=======` (which can occur naturally from a poisoned file that itself contains diff/merge-marker-like text, or is deliberately planted), the hunk count/boundaries fed to the LLM diverge from what `reassembleResolvedFile` will later locate on disk. The result is that a resolution intended for conflict hunk *k* gets spliced into a different marker block than the one it was written for, silently corrupting the merge result that Desktop then stages for commit — exactly the "silent corruption of what the user commits" impact category. Because the whole point of the Copilot conflict-resolution feature is to let the user trust the automated merge without manually re-reading every hunk, this corruption can go unnoticed until much later (analogous to the original report's "user trusts the outcome and only later discovers the divergence").

### Likelihood Explanation
Exploitation requires only that the victim merge/rebase/cherry-pick a branch or PR containing crafted file content and then use the built-in "Resolve with Copilot" conflict-resolution flow — no local access, admin rights, or prior compromise is needed; the attacker only needs to control content in a branch/PR that ends up being merged, which is squarely within the allowed threat model ("attacker controls a cloned/fetched repository"). The trigger condition (a `<<<<<<<`/`>>>>>>>` pair without an intervening `=======`) is a narrow but realistic malformed-input case, since real-world files (code samples containing literal conflict-marker-like text, minified diffs, documentation about git, etc.) can plausibly contain such sequences, and an attacker can trivially engineer one deliberately.

### Recommendation
Make `extractConflictHunks` and `reassembleResolvedFile` share a single canonical marker-block scanner (or have `reassembleResolvedFile` re-derive hunk boundaries from the exact same hunk list produced by `extractConflictHunks`, e.g. by returning line ranges from `extractConflictHunks` and having the splice function operate on those ranges instead of re-parsing the file independently). Additionally, `extractConflictHunks`'s inner "ours" collection loop should terminate on encountering a `>>>>>>>` (closing) marker as well as `=======`/`|||||||`, so malformed blocks are rejected consistently instead of silently absorbing subsequent real hunks. Finally, `reassembleResolvedFile` should verify, at minimum, that the number of well-formed hunk blocks it locates equals `hunkResolutions.length`, and abort/report an error rather than silently mis-splicing or dropping remainder content when the counts disagree.

### Proof of Concept
1. Set up a merge conflict where the incoming ("theirs") branch content for `file.ts` is:
```
line before
<<<<<<< HEAD
ours-A
class Foo {
  // example marker text a user pasted: <<<<<<< example
  code
>>>>>>> incoming
}
line between
<<<<<<< HEAD
ours-B
=======
theirs-B
>>>>>>> theirs
line after
```
   Here the first `<<<<<<< HEAD ... ours-A ... >>>>>>> incoming` block has **no `=======`** before its `class Foo {...}` body which itself contains a stray `<<<<<<< example` and closes with `>>>>>>> incoming`.
2. `extractConflictHunks` starts collecting "ours" content at the first `<<<<<<<`, and because its inner loop only breaks on `|||||||`/`=======`, it keeps consuming lines — including the `>>>>>>> incoming` line and everything after it — until it hits the real `=======` that belongs to the *second*, legitimate hunk (`ours-B` / `theirs-B`). This merges what should be two hunks into one malformed "ours" blob and reports a hunk count of 1 to the model instead of 2 (or a different miscount depending on exact content) via `parts.push('### Conflict ${i+1} of ${file.hunks.length}')` [8](#0-7) .
3. The model, following the prompt's instruction that `hunks` is "an ordered array with one entry per conflict in the file, matching the 'Conflict 1 of N' order" [9](#0-8) , returns 1 resolution for what it was told was a single conflict.
4. `reassembleResolvedFile` independently re-walks the same raw text. Since it treats the leading `<<<<<<< HEAD` (with no `=======` before the first `>>>>>>>`) as plain, non-conflict text (`hasSeparator` stays false because `>>>>>>> incoming` is hit before any `=======`), it copies that entire block through verbatim and instead recognizes the **second** block (`ours-B`/`theirs-B`) as "hunk 0" [10](#0-9) .
5. The model's single resolution — which was written under the assumption it was resolving the first (`ours-A`/incoming) conflict — is spliced by `reassembleResolvedFile` into the *second*, unrelated `ours-B`/`theirs-B` conflict block, while the original literal `<<<<<<<`/`>>>>>>>` markers for the first block remain in the "resolved" file content. This corrupted content becomes `IFileResolution.resolvedContent`, which is what Desktop writes to disk and stages for the user's commit [11](#0-10) , with no error thrown anywhere in the pipeline.

**Note on limitations:** I was unable to trace the exact UI-level write path that consumes `IFileResolution.resolvedContent` and the final commit/staging call (index size limits may exclude some of that file's content); the analysis above is based on the two parsing/splicing functions and their exported contract, which are fully present in the indexed code and directly demonstrate the divergent-parsing/positional-splice defect. A Devin session with full repo access could confirm the exact downstream write-to-commit call site and validate the PoC end-to-end.
