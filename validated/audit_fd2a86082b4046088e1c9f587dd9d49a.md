Audit Report

## Title
Precompile signature count (`data[0]`) drives both real CPU verification cost and cost-model billing but is decoupled from actual bytes hashed/recovered, and precompile execution bypasses compute-unit metering entirely - (File: `runtime-transaction/src/signature_details.rs`, `precompiles/src/secp256k1.rs`, `precompiles/src/ed25519.rs`, `program-runtime/src/invoke_context.rs`)

## Summary
The cost model bills secp256k1/ed25519/secp256r1 precompile cost strictly from a single self-reported byte (`data[0]`) multiplied by a fixed per-signature constant, via `get_num_signatures_in_instruction` and `CostModel::get_signature_cost`. However, `secp256k1::verify()` and `ed25519::verify()` allow each of the `count` signature-offset entries to independently reference arbitrary, reusable byte ranges (`message_data_offset`/`message_data_size`) from any instruction in the transaction, and — critically — `InvokeContext::process_precompile` invokes this verification logic completely outside of the compute-unit-metered execution path (`process_executable_chain`), so the real CPU cost of these hashes/EC-recoveries is neither bounded by the transaction's compute budget nor proportional to the flat cost billed for scheduling.

## Finding Description
`PrecompileSignatureDetailsBuilder::process_instruction` and `get_num_signatures_in_instruction` derive the entire signature count purely from `instruction.data.first()`: [1](#0-0) . This value feeds `CostModel::get_signature_cost`, which multiplies raw counts by fixed constants `SECP256K1_VERIFY_COST`/`ED25519_VERIFY_STRICT_COST`/`SECP256R1_VERIFY_COST`: [2](#0-1) .

The actual `secp256k1::verify()` routine loops `count` times, and for each entry independently resolves a `message_data_offset`/`message_data_size` pair that can point at any instruction's data (including a large, attacker-reused buffer), performing a fresh `keccak256` hash and `libsecp256k1::recover` per entry: [3](#0-2) . `get_data_slice` performs no dedup/overlap checks across entries: [4](#0-3) . The ed25519 precompile has the analogous structure with `verify_strict` per entry: [5](#0-4) .

Separately, and more significantly, `InvokeContext::process_message` dispatches precompile instructions via `process_precompile`, which calls straight into the verify callback and bypasses `process_executable_chain` (the path that runs the metered VM and tracks `compute_units_consumed`): [6](#0-5) [7](#0-6) . This means the real CPU cost of the hash/recovery work performed by `verify()` consumes zero compute units and is not bounded by the transaction's `compute_unit_limit`; the only "cost" ever attributed to it is the flat per-count constant used by the cost model for block-cost/scheduling purposes, which is unrelated to the actual bytes hashed or number of EC recoveries performed for a given reused buffer.

Existing guards are insufficient: transaction size is capped at `PACKET_DATA_SIZE` (1232 bytes, or up to `solana_message::v1::MAX_TRANSACTION_SIZE` for v1 transactions when `enable_tx_v1` is active), verified in `Bank::verify_transaction_with_serialized_message`: [8](#0-7) . This bounds `count` and reused message sizes relative to the report's literal PoC (255 entries each referencing a ~900-byte buffer is not simultaneously achievable within 1232 bytes), but a smaller-scale amplification (tens of offset entries repeatedly hashing/recovering against a shared several-hundred-byte buffer from one packet-sized transaction) remains achievable and is not gated by CU metering or any cap on offset-entry reuse.

Note that this execution path — `process_precompile` — runs during actual bank/runtime transaction execution (bank processing/replay of a transaction that has been scheduled), not merely upon receipt of a packet over TPU/QUIC before fee deduction. The report's characterization that this cost is incurred "irrespective of the transaction ultimately landing in a block" and "before any bank-level fee deduction... is even reached" is not accurate for this specific code path — the precompile `verify()` cost described here is charged during execution of an admitted transaction (i.e., after fee/blockhash checks), not during raw packet ingestion.

## Impact Explanation
This matches the "non-RPC remote exhaustion" category for the runtime/transaction-execution scope: any unprivileged, fee-paying transaction can be crafted so its precompile instruction's `count` byte drives disproportionate, CU-unmetered real CPU work (repeated `keccak256` hashing and `libsecp256k1`/`ed25519_dalek` operations over attacker-chosen, reusable message slices) relative to the flat per-signature cost the cost model bills for scheduling. Because this work bypasses compute-unit metering in `process_precompile`, it also escapes the compute-budget-based bound that constrains ordinary program execution cost, meaning the flat scheduling cost genuinely can be much smaller than real CPU time consumed by leaders/replaying validators for that instruction.

## Likelihood Explanation
Constructing such a transaction requires no special privilege beyond a funded fee payer and a valid recent blockhash — standard requirements for any transaction submission. Within the `PACKET_DATA_SIZE` (1232-byte) or v1 (4096-byte, feature-gated) limit, an attacker can fit tens of `SecpSignatureOffsets`/ed25519 offset entries that all reference the same large buffer in a second instruction, forcing repeated hashing/recovery per entry while the cost model only reflects `count * SECP256K1_VERIFY_COST`. The magnitude is bounded by transaction size limits, which somewhat tempers the severity compared to the report's literal 255-signature claim, but the underlying decoupling between real CPU cost and billed cost — and the complete absence of CU metering for precompile execution — is real and verifiable in code.

## Recommendation
- Meter precompile verification cost through the compute-unit budget in `InvokeContext::process_precompile` (e.g., charge CUs proportional to bytes hashed/recovered) rather than bypassing `process_executable_chain` entirely.
- Bill the block-cost-model's signature cost proportional to actual bytes referenced (sum of `message_data_size` across offset entries) rather than solely the `count` byte.
- Disallow or cap duplicate/overlapping `message_data_offset`/`message_data_size` references across offset entries within a single precompile instruction, or cap total referenced bytes per instruction/transaction independent of `count`.

## Proof of Concept
1. Construct a legacy or v0 transaction (≤1232 bytes) with a secp256k1 instruction whose `data[0] = N` for the largest `N` fitting in the remaining space alongside a second instruction containing a large (e.g., ~500–900 byte) reusable data buffer.
2. Populate `N` `SecpSignatureOffsets` entries, each pointing `message_instruction_index`/`message_data_offset`/`message_data_size` at the same large buffer in the second instruction.
3. Fund a fee payer, sign the transaction with a valid recent blockhash, and submit it for execution (e.g., via a local test validator or unit test calling `Bank::process_transaction`).
4. Observe via `InvokeContext::process_precompile` / `secp256k1::verify` that `N` independent `keccak256` hashes plus `N` `libsecp256k1::recover` calls are performed against the shared buffer, none of which consume compute units (`accumulated_consumed_units` unaffected by this instruction), while `CostModel::get_signature_cost` only reflects `N * SECP256K1_VERIFY_COST`. fn get_data_slice<'a>(
    instruction_datas: &'a [&[u8]],
    instruction_index: u8,
    offset_start: u16,
    size: usize,
) -> Result<&'a [u8], PrecompileError> {
    let signature_index = instruction_index as usize;
    if signature_index >= instruction_datas.len() {
        return Err(PrecompileError::InvalidDataOffsets);
    }
    let signature_instruction = &instruction_datas[signature_index];
    let start = offset_start as usize;
    let end = start.saturating_add(size);
    if end > signature_instruction.len() {
        return Err(PrecompileError::InvalidSignature);
    }

    Ok(&instruction_datas[signature_index][start..end])
}

    pub fn process_message(
        &mut self,
        message: &'ix_data impl SVMMessage,
        execute_timings: &mut ExecuteTimings,
        accumulated_consumed_units: &mut u64,
    ) -> Result<(), (u8, InstructionError)> {
        self.prepare_top_level_instructions(message)?;

        for (top_level_instruction_index, (program_id, instruction)) in
            message.program_instructions_iter().enumerate()
        {
            let mut compute_units_consumed = 0;
            let (result, process_instruction_us) = measure_us!({
                if self.is_precompile(program_id) {
                    self.process_precompile(
                        program_id,
                        instruction.data,
                        message.instructions_iter().map(|ix| ix.data),
                    )
                } else {
                    self.process_instruction(&mut compute_units_consumed, execute_timings)
                }
            });

            *accumulated_consumed_units =
                accumulated_consumed_units.saturating_add(compute_units_consumed);
            // The per_program_timings are only used for metrics reporting at the trace
            // level, so they should only be accumulated when trace level is enabled.
            if log::log_enabled!(log::Level::Trace) {
                execute_timings.details.accumulate_program(
                    program_id,
                    process_instruction_us,
                    compute_units_consumed,
                    result.is_err(),
                );
            }
            self.timings = {
                execute_timings.details.accumulate(&self.timings);
                ExecuteDetailsTimings::default()
            };
            execute_timings
                .execute_accessories
                .process_instructions
                .total_us += process_instruction_us;

            result.map_err(|err| (top_level_instruction_index as u8, err))?;
        }
        Ok(())
    }
