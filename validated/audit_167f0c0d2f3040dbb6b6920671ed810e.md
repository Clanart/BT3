### Title

Integer overflow in Bitcoin payment total permits signing consensus-invalid transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

`SignableTransaction::new` computes the aggregate payment amount with `sum::<u64>()` and then adds `needed_fee` using unchecked integer arithmetic. An attacker-controlled transaction plan can select payment amounts whose `u64` sum is near `u64::MAX`, causing `payment_sat + needed_fee` to wrap to a small value and bypass the insufficient-funds check. [1](#0-0) 

### Finding Description

The bug class from CVE-2018-11236 maps to integer-overflow-triggered boundary bypass rather than a pathname buffer overflow. In `SignableTransaction::new`, each payment amount is an unrestricted `u64`, with only the Bitcoin dust lower bound enforced. [2](#0-1) 

The implementation calculates:

```rust
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();
```

and later tests solvency with:

```rust
if input_sat < (payment_sat + needed_fee) {
```

Both the aggregate sum and the addition are unchecked. In a release build without `overflow-checks`, they wrap modulo `2^64`. [3](#0-2) [4](#0-3) 

If `payment_sat + needed_fee` wraps to a value below `input_sat`, `NotEnoughFunds` is not returned even though the encoded outputs exceed the available inputs by an enormous amount. The resulting `SignableTransaction` is accepted and returned for signing. [5](#0-4) 

A similar unchecked addition exists in the change calculation, where `payment_sat + fee_with_change` may wrap before `checked_sub`, so `checked_sub` does not protect the calculation. [6](#0-5) 

### Impact Explanation

An unprivileged party who can cause arbitrary Bitcoin payment data to be signed can cause the threshold wallet to construct and sign a transaction that does not reflect the requested fee and balance rules and is consensus-invalid. This is unintended-message signing: the signature is valid for the malformed transaction even though the transaction cannot validly spend the declared inputs. [7](#0-6) 

The signing path then creates one Taproot signature per input and inserts those signatures into the transaction witness, completing the malformed spend request. [8](#0-7) 

### Likelihood Explanation

The vulnerable quantities are direct transaction-construction inputs: `payments`, `inputs`, and `fee_per_vbyte`. No malformed curve encoding, trusted RPC response, leaked key, malicious validator, or unsafe operation is required. An attacker only needs payment amounts chosen so that their sum and the calculated fee wrap `u64`. [9](#0-8) [10](#0-9) 

### Recommendation

Use checked arithmetic throughout transaction construction:

- Replace `sum::<u64>()` for inputs and payments with `try_fold(0u64, u64::checked_add)`.
- Replace `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `payment_sat.checked_add(...)`.
- Replace `fee_per_vbyte * vbytes` and `fee_per_vbyte * vbytes_with_change` with `checked_mul`.
- Reject any input or payment amount exceeding Bitcoin’s monetary range, and reject total outputs exceeding total inputs before constructing `TxOut` values.
- Return explicit overflow errors rather than panicking or wrapping.

### Proof of Concept

The arithmetic condition is direct:

```rust
let needed_fee = 1u64;
let payment_sat = u64::MAX;
let input_sat = 546u64;

// In a wrapping release build this becomes zero.
let wrapped_total = payment_sat.wrapping_add(needed_fee);
assert_eq!(wrapped_total, 0);
assert!(!(input_sat < wrapped_total));
```

With the implementation’s unchecked expression, `payment_sat = u64::MAX` and `needed_fee = 1` make `payment_sat + needed_fee == 0`, so an input valued at only 546 satoshis passes the insufficient-funds test while an output valued at `u64::MAX` satoshis is constructed. [1](#0-0) 

Conceptual API-level trigger:

```rust
let payments = vec![
  (script_pubkey.clone(), u64::MAX - needed_fee / 2),
  (script_pubkey, needed_fee / 2 + 1),
];

let result = SignableTransaction::new(
  vec![received_output_with_546_sats],
  &payments,
  None,
  None,
  fee_per_vbyte,
);
```

When the checked expression `payment_sat + needed_fee` wraps below `input_sat`, `result` can be `Ok(_)` instead of `Err(TransactionError::NotEnoughFunds { .. })`, allowing the malformed transaction to proceed through `multisig`, `sign`, and `complete`. [11](#0-10) [12](#0-11)
