### Title
Deep-link/API-supplied clone or remote URLs are never restricted to safe transports, allowing `git://ext::`-style remote-helper command execution - (File: `app/src/lib/git/clone.ts`, `app/src/lib/git/remote.ts`)

### Summary
GitHub Desktop clones and (re)configures remotes using URLs that can originate from untrusted, attacker-influenced sources: the `x-github-client://openRepo/<url>` OS deep link (parsed by `parseAppURL`) and the GitHub API `clone_url`/`head.repo.clone_url` fields consumed when checking out a pull request or updating a remote. None of the code paths that ultimately invoke `git clone`, `git remote add`, or `git remote set-url` restrict the URL to safe transports (`https`, `ssh`, `git`). Git itself supports “remote helper” pseudo-protocols such as `ext::<command>` and `fd::` that execute an arbitrary local command as part of a fetch/clone. This mirrors the ELFi bug pattern: a value (the remote/clone URL) is validated in one narrow way at one call site while other call sites that mutate the same underlying resource skip validation entirely, allowing the invariant "only network transports are used" to be silently broken.

### Finding Description
`parseAppURL` (`app/src/lib/parse-app-url.ts:66-128`) extracts the URL segment straight from the deep link path with no scheme allow-list: [1](#0-0) 

That value flows to `openOrCloneRepository` (`app/src/ui/dispatcher/dispatcher.ts:2215-2233`), which just pre-fills the Clone dialog with `initialURL: url` and, once the user proceeds, ends up in `clone()`: [2](#0-1) 

`clone()` (`app/src/lib/git/clone.ts:68-126`) only guards the **destination path** against sensitive locations via `isClonePathSensitive`; the **source URL** is passed to `git … clone … -- <url> <path>` with zero validation of scheme: [3](#0-2) 

Similarly, `addRemote`/`setRemoteURL` (`app/src/lib/git/remote.ts:28-64`) perform no URL validation at all before shelling out to `git remote add`/`git remote set-url`: [4](#0-3) 

These are invoked with API-controlled data in `_findPullRequestBranch` (`app/src/lib/stores/app-store.ts:8633-8660`, using `headCloneUrl` from the PR API object) and in `ensureUpstreamRemoteURL` (`app/src/lib/stores/git-store.ts:1358-1380`), and with user-typed data in the Repository Settings remote editor (`app/src/ui/repository-settings/repository-settings.tsx:296-313`), none of which reject non-network schemes.

Grepping the codebase for any protocol allow-listing mechanism (`GIT_ALLOW_PROTOCOL`, `protocol.allow`, `GIT_PROTOCOL_FROM_USER`) returns no results, confirming Desktop relies entirely on Git's own defaults, which historically permitted the `ext::` remote helper to run shell commands (`ext::sh -c "id > /tmp/pwn"`) until sufficiently new Git versions disable it by default only in specific transport contexts — and even where disabled, Desktop does nothing to enforce a stricter policy itself. The `envForRemoteOperation`/`envForProxy` code (`app/src/lib/git/environment.ts:76-139`) only special-cases `http(s)` for proxy resolution and otherwise passes the URL through untouched, again with no scheme filtering.

This is directly analogous to the ELFi report: input validation (`minOrderMarginUSD` check on order creation vs. no check on the leftover margin after a decrease) exists at one entry point but is missing at another entry point that mutates the same invariant (position margin ↔ remote/clone URL transport safety). `isClonePathSensitive` is proof the maintainers are already defending against crafted-URL attacks in the clone flow (path traversal), but they only checked the destination, not the source scheme, and none of the sibling `addRemote`/`setRemoteURL` call sites got any equivalent treatment.

### Impact Explanation
If an attacker can get a victim to click a `x-github-client://openRepo/ext::sh,-c,"<payload>"` link (or a `github-mac://…`/`github-windows://…` legacy variant, all registered as OS-level protocol handlers per `app/src/main-process/main.ts:105-116`), and the victim proceeds through the pre-filled Clone dialog, `git clone` will invoke the `ext::` remote helper and execute an attacker-chosen command with the privileges of the Desktop user — full local code execution outside of any repository sandbox. The same class of URL could be planted via a forked PR's `clone_url`/`head.repo.clone_url` if an attacker-controlled Git hosting endpoint (non-github.com, e.g., GHE/enterprise or a compromised API response) is used, feeding into `addRemote`/`setRemoteURL`/`ensureUpstreamRemoteURL`, where the first subsequent fetch/pull silently runs the helper command.

### Likelihood Explanation
Exploitation requires the victim to click a link (a natural, expected action for GitHub Desktop's own advertised "Open in Desktop" feature) and to confirm the Clone dialog — no admin rights, local access, or pre-existing malware are needed, satisfying the “unprivileged … link or deep link the user clicks” criterion. Whether the currently bundled Git binary still honors `ext::`/`fd::` by default is a detail that would need runtime verification (recent Git versions increasingly restrict these helpers unless explicitly allowed for local operations), but Desktop's code has no defense-in-depth layer of its own (no `GIT_ALLOW_PROTOCOL` env variable is ever set), so any residual permissiveness in the underlying `dugite`/Git version is directly exploitable through this path.

### Recommendation
- Add scheme validation immediately after parsing/receiving a remote or clone URL and before it's ever passed to `git`: allow only `https:`, `ssh:`, `git:`, and (if truly required) `file:` restricted to existing local directories — reject `ext:`, `fd:`, and any other transport helper scheme. Apply this centrally, e.g., inside `envForRemoteOperation`/`clone()`/`addRemote()`/`setRemoteURL()`, not just at the deep-link parsing layer.
- Explicitly set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or equivalent `-c protocol.ext.allow=never -c protocol.fd.allow=never`) in every environment built by `envForRemoteOperation`/`envForAuthentication`, so that even if a malicious URL slips through UI-level checks, Git itself refuses the helper.
- Extend `isClonePathSensitive`-style defensive validation from `clone.ts` to `remote.ts`'s `addRemote`/`setRemoteURL`, since both mutate the same trust boundary (what remote git will talk to).

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}

export async function envForRemoteOperation(remoteUrl: string) {
  return {
    ...envForAuthentication(),
    ...(await envForProxy(remoteUrl)),
  }
}

/**
 * Not intended to be used directly. Exported only in order to
 * allow for testing.
 *
 * @param remoteUrl The remote url to resolve a proxy for.
 * @param env       The current environment variables, defaults
 *                  to `process.env`
 * @param resolve   The method to use when resolving the proxy url,
 *                  defaults to `resolveGitProxy`
 */
export async function envForProxy(
  remoteUrl: string,
  env: NodeJS.ProcessEnv = process.env,
  resolve: (url: string) => Promise<string | undefined> = resolveGitProxy
): Promise<Record<string, string | undefined> | undefined> {
  const protocolMatch = /^(https?):\/\//i.exec(remoteUrl)

  // We can only resolve and use a proxy for the protocols where cURL
  // would be involved (i.e http and https). git:// relies on ssh.
  if (protocolMatch === null) {
    return
  }

  // Note that HTTPS here doesn't mean that the proxy is HTTPS, only
  // that all requests to HTTPS protocols should be proxied. The
  // proxy protocol is defined by the url returned by `this.resolve()`
  const proto = protocolMatch[1].toLowerCase() // http or https

  // We'll play it safe and say that if the user has configured
  // the ALL_PROXY environment variable they probably know what
  // they're doing and wouldn't want us to override it with a
  // protocol-specific proxy. cURL supports both lower and upper
  // case, see:
  // https://github.com/curl/curl/blob/14916a82e/lib/url.c#L2180-L2185
  if ('ALL_PROXY' in env || 'all_proxy' in env) {
    log.info(`proxy url not resolved, ALL_PROXY already set`)
    return
  }

  // Lower case environment variables due to
  // https://ec.haxx.se/usingcurl/usingcurl-proxies#http_proxy-in-lower-case-only
  const envKey = `${proto}_proxy` // http_proxy or https_proxy

  // If the user has already configured a proxy in the environment
  // for the protocol we're not gonna override it.
  if (envKey in env || (proto === 'https' && 'HTTPS_PROXY' in env)) {
    log.info(`proxy url not resolved, ${envKey} already set`)
    return
  }

  const proxyUrl = await resolve(remoteUrl).catch(err => {
    log.error('Failed resolving Git proxy', err)
    return undefined
  })

  return proxyUrl === undefined ? undefined : { [envKey]: proxyUrl }
}
