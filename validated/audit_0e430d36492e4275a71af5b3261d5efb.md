## Title
Panic-on-Overflow in Epoch Reward Point Scaling Crashes Validators at Epoch Boundary - (File: `runtime/src/inflation_rewards/mod.rs`)

### Summary
The external report flags `getVestedAmount()` reverting when `totalGrantAmount * bps` (or `* elapsedTime`) overflows because the code relies on unguarded checked-math that simply propagates a revert instead of clamping/bounding the inputs. The equivalent pattern exists in Agave's stake-reward distribution math: `calculate_stake_rewards()` scales `tower_points` (`stake * credits_delta`, itself already a `u128`) by `point_value.rewards` and then narrows the result back into a `u64`, using `.expect(...)` on the intermediate `checked_mul`/`try_from` instead of returning a graceful error. [1](#0-0) [2](#0-1) 

### Finding Description
`calculate_stake_rewards()` is invoked for every delegated stake account at every epoch boundary as part of consensus-critical, protocol-wide reward distribution (run identically by every validator, not gated behind any single transaction). For the `Tower` reward path it computes:

```rust
tower_points
    .checked_mul(u128::from(point_value.rewards))
    .expect("Rewards intermediate calculation should fit within u128")
    .checked_div(point_value.points)
    .unwrap()
```
and then
```rust
let rewards = u64::try_from(rewards).expect("Rewards should fit within u64");
``` [3](#0-2) 

`tower_points` is derived from `credits_delta * stake` in `calculate_stake_points_and_credits()` (`runtime/src/inflation_rewards/points.rs`), where `stake` is the user-controlled delegated lamport amount (up to the account's balance) and `credits_delta` is the number of vote credits accrued since the last reward redemption. Both `.expect()` calls are `panic!`-equivalent — unlike the Solidity report's `revert`, which only aborts a single transaction, a Rust panic inside bank-processing code during epoch-boundary reward distribution is fatal to the validator process (or at minimum aborts an unrecoverable code path in consensus-critical logic), which every validator executes identically for every rewarded stake account.

This is confirmed by the repo's own test harness, which documents the exact overflow/panic conditions as expected behavior rather than as a handled error path:

```rust
#[test_case(u64::MAX, 1_000, u64::MAX => panics "Rewards intermediate calculation should fit within u128")]
#[test_case(1, u64::MAX, u64::MAX => panics "Rewards should fit within u64")]
fn calculate_rewards_tests(stake: u64, rewards: u64, credits: u64) { ... }
``` [4](#0-3) 

Unlike `commission_split_preserve_lamports`/`commission_split`, which are exercised with `proptest` invariants proving they never overflow or panic across the full `u16`×`u64` input domain, `calculate_stake_rewards()`'s intermediate `tower_points * point_value.rewards` multiplication has no such proven bound and instead documents panicking test vectors as acceptable.

### Impact Explanation
If `tower_points` (bounded by `stake_lamports * credits_delta`) and `point_value.rewards` (the epoch's inflation reward pool) combine to exceed `u128::MAX`, or if the final division result exceeds `u64::MAX`, the `.expect()`/`.unwrap()` calls panic. Because this code runs identically on every validator processing the same epoch-boundary rewards, a value that triggers the panic on one validator triggers it on all validators simultaneously — this is a shared-fate crash across the fleet rather than an isolated node fault, i.e., a consensus-halt-class DoS rather than a single-node RPC crash.

### Likelihood Explanation
Under today's economic bounds (total SOL supply ≪ `u64::MAX`, and single-epoch inflation reward pools several orders of magnitude below `u64::MAX`), the multiplication is unlikely to overflow `u128` in practice — the code's own tests only trigger the panic using artificial `u64::MAX` inputs that are not currently reachable through normal token-economics. This keeps current likelihood low, but the invariant is enforced only by "the numbers happen to stay small," not by an explicit bound/clamp on `stake`, `credits_delta`, or `point_value.rewards` at the point of multiplication — the same root cause (`.expect()` after `checked_mul` instead of graceful degradation/bounding) that the external report flagged as Medium severity. Any future change to inflation parameters, supply caps, or reward-pool accounting that pushes `point_value.rewards` or accumulated `tower_points` closer to `u64`/`u128` boundaries would resurface this as a live, fleet-wide panic.

### Recommendation
Replace the panicking `.expect()`/`.unwrap()` calls in `calculate_stake_rewards()` with graceful handling (e.g., saturate/clamp the intermediate product, or explicitly cap `stake`/`point_value.rewards` before multiplying, mirroring the safe pattern already used in `commission_split`/`commission_split_preserve_lamports`, which are proven overflow-free via `proptest`). At minimum, add the same `proptest`-based invariant coverage over the full realistic input domain to `calculate_stake_rewards()`/`calculate_stake_points_and_credits()` that already exists for `commission_split`, so any overflow condition is caught before merge rather than accepted as a documented panic test vector.

### Proof of Concept
1. Construct a `Stake` with `delegation.stake` set to a very large `u64` (e.g., near `u64::MAX`) and a `VoteStateV4` with a correspondingly large `credits_observed` delta.
2. Call `calculate_stake_rewards()` with a `PointValue { rewards: <large u64>, points: 1 }` such that `tower_points * rewards` exceeds `u128::MAX`, or such that the resulting `rewards` value exceeds `u64::MAX`.
3. Observe the panic, exactly as reproduced by the repository's own test:
