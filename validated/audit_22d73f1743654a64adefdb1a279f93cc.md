### Title
Permanent freezing of ICS20-transferred tokens in unreachable isolated addresses when the EVM destination callback fails to fully forward funds - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
`ContractKeeper.IBCReceivePacketCallback` (the EVM analog of `StargateLbpHelper.sgReceive()`) receives ICS20 tokens that are converted/minted into an ERC20 representation and credited to a deterministic, keyless "isolated address" *before* the callback contract is ever invoked. If the target contract's `approve`/`transferFrom` flow does not fully sweep the balance out of that isolated address — due to a contract bug, a malicious/incompatible contract, gas exhaustion, or any other non-transient failure — the tokens become permanently and irrecoverably locked, exactly mirroring the "stuck tokens with no recovery path" pattern from the external report.

### Finding Description
`IBCReceivePacketCallback` is invoked by the ibc-go callbacks middleware only *after* the underlying ICS20 transfer + `x/erc20` `OnRecvPacket` conversion has already run and been committed to the (non-cached) `ctx` — i.e., the ERC20 tokens are already minted/unescrowed to the deterministic isolated receiver address (`types.GenerateIsolatedAddress`, computed purely from `channelId` + `sender`, with no corresponding private key) before this function executes: [1](#0-0) 

The callback then attempts to move the tokens out of the isolated address via `approve` + an arbitrary EVM call to the sender-supplied `contractAddress` with sender-supplied `calldata`: [2](#0-1) 

Critically, `writeFn()` — which commits the cached EVM execution context (approve + contract-call side effects) back into `ctx` — is called *before* the code validates that the isolated address balance was actually drained: [3](#0-2) 

If `receiverTokenBalance` is non-zero (the contract accepted the call but didn't call `transferFrom` for the full amount, reverted partway in a way that still leaves tokens, or is simply a contract that doesn't implement the expected pull-based transfer), the function returns an error. Since the underlying coin transfer/mint into the isolated address happened earlier in the packet-processing pipeline (in the always-committed, non-cached IBC receive-packet context, not in this function's `cachedCtx`), returning an error here only causes ibc-go to produce an `ErrorAcknowledgement` — it does not, and cannot, retroactively unwind the mint/unescrow that already happened to the isolated address. The result is that the tokens sit permanently in `receiverHex` (the isolated address), which — per the module's own documentation — has no corresponding signer and can never be spent: [4](#0-3) 

This is corroborated by the test suite, which explicitly asserts that funds land and remain "trapped" in the isolated address when the erc20 conversion/callback path doesn't fully succeed: [5](#0-4) 

The "unrecoverable tokens" check added at lines 234-239 only *detects* the stuck-funds condition and turns it into an error acknowledgement for telemetry/observability purposes — it does not prevent, reverse, or provide any way to reclaim the already-locked balance. There is no sweep/rescue function, no owner/admin recovery path, and no way for the original sender or intended recipient to later claim funds sitting in the isolated address, since it is a hash-derived address with no key material at all.

### Impact Explanation
Any unprivileged ICS20 sender can trigger this by directing a transfer's `memo.dest_callback` at a contract that is a legitimate contract from the packet-sender's perspective but fails to implement (or only partially implements) the required pull pattern (`transferFrom` of the exact full amount), or that reverts/runs out of gas partway through more complex logic while still having received `approve`. Because the tokens are already minted to the isolated address in the committed IBC receive path prior to the callback executing, this leads to a permanent, unrecoverable loss of user funds — matching the "Critical permanent freezing/locking/theft of user funds" impact category. This does not require any privileged actor, malicious relayer, or validator misbehavior; it can be triggered by ordinary transaction/packet flow initiated by any cross-chain user.

### Likelihood Explanation
Medium-to-High. Any IBC sender fully controls the `dest_callback.address` and `calldata` fields in the packet memo and can point them at any contract on the destination chain, including contracts they do not control or that behave unexpectedly under specific inputs/gas limits. Because the completeness of fund-forwarding logic in the target contract is entirely outside the receiving chain's control, this condition is reachable in ordinary usage (e.g., a contract that reverts on some inputs, or one that only forwards part of the balance), not merely in adversarial edge cases.

### Recommendation
Do not commit the ERC20 mint/unescrow into the isolated address as an unconditional, always-final step of `OnRecvPacket` when a destination callback is specified. Instead, either: (1) perform the callback's fund-forwarding attempt within the same atomic/cached context as the underlying conversion so that a failed forward can revert the whole receive (causing a true error acknowledgement that also unwinds the mint), or (2) if a non-zero balance remains in the isolated address after the callback, automatically sweep/refund it back to a recoverable address (e.g., back through the ICS20 refund flow or to a chain-controlled recovery account) rather than merely returning an error while leaving funds parked at an address nobody can ever control.

### Proof of Concept
1. Attacker (or any user) sends an ICS20 transfer to the EVM chain with `memo.dest_callback.address` pointing to a contract `C` that they deploy, which accepts the `approve` call but implements `onRecv`-style calldata logic that reverts under certain conditions, or that only calls `transferFrom` for a partial amount.
2. The receiving chain's `x/erc20` `OnRecvPacket` mints the ERC20 representation of the transferred coin to the deterministic isolated address (`types.GenerateIsolatedAddress(destChannel, sender)`) — this state change is committed to `ctx` as part of normal packet processing, independent of the callback's outcome.
3. `IBCReceivePacketCallback` runs, `approve`s contract `C` for the full amount, and calls `C` with the sender-controlled calldata.
4. Contract `C`'s logic executes as designed (from the packet sender's perspective) but doesn't fully drain the isolated address's balance (e.g., a bug, or a contract designed to retain part of funds under specific conditions).
5. `writeFn()` commits the approve/call state; the subsequent balance check sees a non-zero `receiverTokenBalance` and returns `ErrEVMCall` → `ErrorAcknowledgement`.
6. Despite the error acknowledgement, the previously-minted ERC20 tokens remain in the isolated address, which has no private key and thus can never be moved by anyone, permanently locking the transferred value — reproduced by the existing test's `trappedBal` assertion at [6](#0-5) .

## Limitations

The receiver side callback **must** receive funds to an ephemeral address generated from the channelId and packet
sender address. Note that since this is a generated address, no user has the ability to sign messages on behalf of
this account even though it is a cross-chain representation of the packet sender.

Thus, a contract that receives the funds and calldata from the isolated receiver address **must** send the tokens
onwards to a desired address that is specified in the calldata. If tokens are deposited back into the isolated address,
they are unreachabe. If you wish to interact with a contract that does not implement functionality for sending the
tokens to a different address then you must interact with that contract through some wrapper contract interface that
can receive the funds, call the contract which deposits funds back to `msg.sender` and then the wrapper contract
can move the funds to a final desired address.
