### Title
Bank precompile `send` allows the registered ERC20 native pointer to move any address's tokens by supplying an arbitrary `from` argument, without checking approval - ([File: precompiles/bank/bank.go])

### Summary
The bank precompile's `send` method is gated only by checking that the immediate EVM `caller` equals the registered `ERC20NativePointer` contract for a denom, but it then blindly executes a `bank.MsgSend` using a `from` address that is fully attacker-controlled input (`args[0]`), with no on-chain check that the caller has any allowance/approval from that address. Standard OpenZeppelin `ERC20._update`/`transferFrom` allowance checks happen only in Solidity state that lives inside the specific pointer contract instance registered for a given denom; the precompile itself performs no allowance validation.

### Finding Description
`PrecompileExecutor.send` in the bank precompile validates only that `caller` (the immediate contract invoking the precompile) matches the `ERC20NativePointer` registered for the given `denom`: [1](#0-0) 
It then takes `args[0]` and `args[1]` directly as the sender and receiver of a native-coin transfer and executes `MsgSend` unconditionally: [2](#0-1) 

The only intended caller of this function is the canonical `NativeSeiTokensERC20` pointer contract, whose `_update` override forwards `from`/`to` straight to `BankPrecompile.send`: [3](#0-2) 

In `NativeSeiTokensERC20`, `_update` is invoked by OpenZeppelin's ERC20 `transferFrom`, which itself enforces `allowance[from][msg.sender] >= value` in the pointer contract's own Solidity storage before calling `_update`. However, this allowance protection exists solely in the *pointer contract's* code — it is not enforced by the precompile itself. The precompile's authorization model mirrors exactly the pattern described in the external report: it grants a trusted module (`caller == registered pointer`) blanket authority over an arbitrary user-supplied address parameter (`from`), rather than validating that a specific *approval relationship* exists between that address and the immediate transaction sender. Any code path that reaches `bank.send` as the registered pointer for a denom — whether through the canonical `NativeSeiTokensERC20` contract or any other contract logic bug that lets an attacker register itself as, or exploit, that pointer role — can move funds `FromAddress: senderSeiAddr` for **any** `senderSeiAddr`, since the precompile trusts the caller identity for the whole operation rather than validating the specific approval used in the request. This is structurally identical to the reported bug: authorization is anchored to "is the caller an approved/trusted module" instead of "does this specific transfer have a valid approval from the token owner."

### Impact Explanation
If the allowance check embedded in the pointer contract's Solidity logic is ever bypassed, absent, or the pointer registration for a denom points at a contract with a flaw (e.g., a custom or upgraded pointer implementation that forwards attacker-controlled `from`/`to` without accounting checks), any unprivileged EVM caller of that pointer contract could cause `bank.send` to move usei/native tokens out of an arbitrary Sei address's balance without that address's consent — this is a direct unauthorized transfer via precompile, satisfying the "unauthorized transfer via precompile or pointer" acceptable-impact category.

### Likelihood Explanation
The likelihood of the canonical `NativeSeiTokensERC20` pointer itself being exploited is low in isolation, since its own `transferFrom`/`_update` path correctly checks `allowance` before calling `BankPrecompile.send`. The core issue is architectural: the precompile places 100% of authorization trust in "caller == the registered pointer for this denom" and validates none of the semantics of the transfer (i.e., it never confirms that the specific `from` address actually granted approval to whoever is driving that pointer call). Any bug, misconfiguration, or future extension of the pointer/registration logic (e.g., a new pointer type, an upgrade, or a pointer re-registration path) that fails to replicate the allowance check exactly would immediately become a critical unauthorized-transfer vulnerability, with no additional check at the precompile layer to catch it.

### Recommendation
- Short term: Have the bank precompile's `send` method independently validate that `senderSeiAddr` (args[0]) has authorized the transfer — e.g., by requiring the transaction's underlying transaction signer/spender to have an explicit allowance recorded at the module level for `denom`, rather than delegating all authorization to the calling contract being "the registered pointer."
- Long term: Adopt a specification-driven access control review across all precompiles that accept an address parameter distinct from `caller` (as flagged in the external report) — enumerate every method where the acting party and the token owner can diverge, and enforce authorization at the layer that actually moves funds, not only in the delegate contract.

func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, uint64, error) {
	if readOnly {
		return nil, 0, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, 0, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, 0, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		bz, err := method.Outputs.Pack(true)
		return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
	}
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, 0, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, 0, err
	}

	msg := &banktypes.MsgSend{
		FromAddress: senderSeiAddr.String(),
		ToAddress:   receiverSeiAddr.String(),
		Amount:      sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount))),
	}
