### Title
`collateral_check` Does Not Detect Active Challenge Window, Allowing Deposit Signing With a Challenged Operator — (`core/src/extended_bitcoin_rpc.rs`, `core/src/verifier.rs`)

---

### Summary

The `collateral_check` function used to gate deposit signing only tests whether the operator's collateral UTXO is **already spent**. It does not detect an **active challenge window** — the period between a challenge transaction landing on-chain and the eventual disprove transaction burning the collateral. During this window, `collateral_check` returns `true` (collateral usable), so `is_deposit_valid` accepts a new deposit that includes the challenged operator. If the operator is subsequently disproved, the newly deposited BTC is permanently locked in the bridge vault with no operator able to front a payout.

---

### Finding Description

**`collateral_check` logic (core/src/extended_bitcoin_rpc.rs, lines 154–239)**

The function walks the deterministic round-tx chain:

1. For each `RoundIndex`, it reconstructs the `Round` and `ReadyToReimburse` transaction handlers.
2. It advances `current_collateral_outpoint` along the chain as long as each round tx is confirmed on-chain.
3. At the end it returns `!is_utxo_spent(current_collateral_outpoint)`.

During an active challenge the state is:

| On-chain state | Value |
|---|---|
| Round tx | ✅ confirmed |
| `CollateralInRound` UTXO (burn connector) | ❌ **not yet spent** |
| `ReadyToReimburse` tx | ❌ not sent (requires all kickoffs finalized first) |
| Disprove tx | ❌ not yet sent |

Because `CollateralInRound` is unspent, `collateral_check` returns `true` — the operator appears fully active.

**`is_deposit_valid` (core/src/verifier.rs, lines 541–731)**

`is_deposit_valid` is called in both `deposit_sign` (line 876) and `deposit_finalize` (line 994). Its operator-status check is exclusively:

```rust
let is_collateral_usable = self
    .rpc
    .collateral_check(&operator_data, &kickoff_wpks, self.config.protocol_paramset())
    .await?;
// if operator is in deposit, but the collateral is not usable, return false
if operators_in_deposit_data.contains(xonly_pk) && !is_collateral_usable {
    return Err(BridgeError::InvalidDeposit(reason));
}
```

There is no query to the `KickoffStateMachine`, no check of the `Challenge` UTXO spend status, and no inspection of the DB for an in-flight challenge. The `CHECK_KICKOFF_LOCK` write-guard used in the round state machine (line 284 of `core/src/states/round.rs`) is only held during `CheckIfKickoff` duty dispatch; `deposit_sign` / `deposit_finalize` never acquire it as a reader, so it provides no protection here.

**Consequence**

A new deposit signed during the challenge window produces a fully valid move-to-vault transaction. The deposited BTC enters the bridge vault. When the disprove transaction subsequently burns the operator's collateral:

- The operator exits the protocol.
- No operator can front a payout for this deposit (kickoff slots are operator-specific).
- The depositor's BTC is locked in the bridge vault indefinitely; recovery requires an out-of-band N-of-N emergency-stop action.

---

### Impact Explanation

Deposited BTC (fixed at `bridge_amount`, currently 10 BTC per deposit) is permanently locked in the bridge vault. The depositor cannot withdraw through the normal payout path because the only operator associated with their deposit has been slashed. Recovery requires privileged N-of-N emergency-stop intervention, which is not guaranteed and is outside the normal protocol flow. This satisfies the allowed impact criterion: **permanent lock of bridged BTC**.

---

### Likelihood Explanation

The challenge-response game spans multiple Bitcoin confirmation rounds:

1. Challenge tx confirmed.
2. Watchtower challenges + operator acks (each requiring confirmations).
3. Operator asserts (multiple transactions, each requiring confirmations).
4. Disprove tx.

This window can span dozens to hundreds of blocks. Any deposit ceremony initiated during this window — which is a normal user action with no visible warning — will be accepted by all verifiers and finalized. The only signal that something is wrong is the on-chain challenge tx, which is not surfaced to the deposit path at all.

---

### Recommendation

1. **Extend `collateral_check` or add a parallel check** that queries whether any kickoff UTXO belonging to the operator's current round has its `Challenge` UTXO spent (but not by the `ChallengeTimeout` tx). A spent `Challenge` UTXO that is not the timeout means an active challenge is in progress.

2. **Alternatively**, expose a DB query (analogous to the Karak mitigation's getter) that returns whether any `KickoffStateMachine` for a given operator is in the `challenged` state, and call it from `is_deposit_valid`.

3. **Block new deposits** that include an operator with an active challenge, or at minimum surface the pending-challenge status to the aggregator so it can refuse to initiate the ceremony.

---

### Proof of Concept

```
Block N:   Operator sends kickoff tx for deposit A.
Block N+1: Verifier sends challenge tx (Challenge UTXO spent, not by ChallengeTimeout).
           → CollateralInRound UTXO is still UNSPENT.
           → collateral_check() returns true.

Block N+2: User initiates deposit B with the same operator.
           → is_deposit_valid() calls collateral_check() → true.
           → deposit_sign() proceeds, verifiers sign all NofN sighashes.
           → deposit_finalize() proceeds, move-to-vault tx created.
           → Deposit B BTC enters bridge vault.

Block N+K: Verifier sends disprove tx.
           → CollateralInRound UTXO is NOW spent (burned).
           → Operator exits protocol.

Result:    Deposit B's BTC is locked in the bridge vault.
           No operator can front a payout for deposit B.
           Depositor's 10 BTC is permanently inaccessible via normal protocol flow.
```

**Root cause**: `collateral_check` at [1](#0-0)  returns `true` whenever `current_collateral_outpoint` is unspent, which is always the case during an active challenge because the disprove tx has not yet fired.

**Trigger site**: `is_deposit_valid` at [2](#0-1)  relies solely on `collateral_check` for operator liveness and has no awareness of the `KickoffStateMachine` challenge state.

**Called from**: `deposit_sign` at [3](#0-2)  and `deposit_finalize` at [4](#0-3) , meaning both signing phases are affected.

**Challenge state is tracked** in `KickoffStateMachine.challenged` at [5](#0-4)  but is never consulted during deposit validation.
