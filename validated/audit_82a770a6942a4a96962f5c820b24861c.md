Based on my research, I've confirmed the concrete analog in the commit/staging pipeline: `applyPatchToIndex` in `app/src/lib/git/apply.ts` re-fetches the diff from disk with `getWorkingDirectoryDiff` right before staging, and applies the user's line-index-based `DiffSelection` (computed against the diff the UI showed earlier) to that freshly re-fetched diff via `formatPatch`. Since `DiffSelection` tracks *line indices*, not content, any change to the file's on-disk diff shape between the moment the UI diff was generated and the moment `createCommit` → `stageFiles` → `applyPatchToIndex` runs will cause the wrong lines to be staged and committed — this is the analog of the Curve bug's "storage updated with an assumed value instead of the actual verified result."

### Title
Partial-commit line selection is applied against a diff re-fetched at staging time, causing silent commit of unreviewed content - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop's partial-staging feature lets a user select individual diff lines/hunks to commit. That selection (`DiffSelection`) is stored as a set of **line indices** relative to the diff object shown in the UI when the selection was made. When the commit is actually created, `applyPatchToIndex` discards that diff and calls `getWorkingDirectoryDiff` again to obtain a **fresh** diff from disk, then blindly reuses the old index-based selection against this new diff via `formatPatch`. If the working-directory file's diff shape changes between the time it was rendered/selected and the time the commit executes, the selection indices silently point at different lines than the ones the user reviewed and checked, and those unintended lines get staged and committed instead. [1](#0-0) [2](#0-1) 

### Finding Description
The flow is:
1. The UI computes a diff and lets the user pick lines to include, producing a `WorkingDirectoryFileChange` with a `DiffSelection` whose `isSelected(absoluteIndex)` checks are keyed on the line's position in that specific diff (`hunk.unifiedDiffStart + lineIndex`). [3](#0-2) 
2. `_commitIncludedChanges` in `app-store.ts` takes the currently selected files from `repositoryStateCache` and calls `createCommit`. [4](#0-3) 
3. `createCommit` calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex(repository, file)`. [5](#0-4) [6](#0-5) 
4. `applyPatchToIndex` does **not** use the diff the user actually looked at; it re-runs `getWorkingDirectoryDiff(repository, file)` against the working tree at commit time, and feeds this brand-new diff plus the old `file.selection` into `formatPatch`. [7](#0-6) 
5. `formatPatch` walks the new diff's hunks and, for every non-context line, asks `file.selection.isSelected(absoluteIndex)` — purely a numeric index lookup with no correlation to the line's content or to which diff it came from. [8](#0-7) 

There is a partial mitigating check for the *in-app rendering path*: `updateChangesWorkingDirectoryDiff` recomputes `selectableLines` when the diff is reloaded and calls `withSelectableLines` to drop selections that no longer correspond to includable lines. But that reconciliation only happens as a side effect of the UI's own diff-refresh cycle for whichever file is currently being *viewed*; it does not run inside `applyPatchToIndex`/`stageFiles`, and it does not protect files that are staged for commit but not the one currently selected/viewed in the Changes list. [9](#0-8) 

This is structurally identical to the Curve bug class: a stored/derived value (the line-index selection) is trusted and reused as-is against a later, independently re-fetched piece of state (the new diff), instead of being validated against or regenerated from the actual data present at execution time.

### Impact Explanation
If an attacker can influence the on-disk content of a tracked file between the moment its diff is rendered in Desktop's Changes view and the moment the user clicks "Commit" — for example, a build tool, a file watcher-triggered formatter/linter, a pre-existing background process in the repo's tooling, or a malicious `.git/hooks`-adjacent script that touches tracked files — the hunk boundaries and line offsets in the newly fetched diff can shift relative to the diff the user reviewed. Because `DiffSelection` only remembers integer offsets, the commit can silently include lines the user never selected (or omit lines they did select), corrupting exactly "what the user commits" without any error or warning shown to them. This matches the report's "Valid Impact" criterion of silent corruption of committed/pushed content caused by an attacker-influenceable repository/working-tree state.

### Likelihood Explanation
Requires a specific timing window (file mutated between diff render and commit execution) and an external actor/process capable of modifying a tracked file in that window — this is plausible in real developer workflows (auto-formatters, linters-on-save, build watchers, CI-adjacent local tooling) but is not trivially attacker-triggerable purely through a malicious remote/clone without some local write access to the working tree during that window. This lowers likelihood relative to a fully remote-triggerable bug, though the "attacker controls a cloned/fetched repository" angle applies if the repository ships tooling/hooks/scripts that legitimately touch tracked files as part of normal use (e.g., a `post-checkout`/editor plugin driven by repo config) and a malicious repo author intentionally engineers this race.

### Recommendation
`applyPatchToIndex` should not re-fetch the diff independently of the diff the user actually made selections against. Either:
- Pass the exact `IDiff` object the UI used to build the selection through the commit pipeline (`_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex`) instead of re-querying git, or
- If re-fetching is required (e.g., to avoid staleness), diff-compare the freshly fetched diff against the one the selection was built from and abort/re-prompt the user if hunk content/positions have changed, rather than silently reapplying stale index-based selection.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file so it has two separate hunks; view the diff and select only hunk 1 for a partial commit.
2. Before clicking "Commit", externally rewrite the file so that its diff against `HEAD` now has different line offsets in the position previously occupied by hunk 1 (e.g., insert lines earlier in the file so hunk boundaries shift), while keeping the total change set such that Desktop doesn't refresh/invalidate the selection UI in time.
3. Click "Commit" in Desktop.
4. Inspect the resulting commit with `git show`: because `applyPatchToIndex` re-fetches the diff at line 60 of `app/src/lib/git/apply.ts` and applies the stale `absoluteIndex`-based selection via `formatPatch`, the committed hunk corresponds to different content than what was displayed and checked in the UI.
