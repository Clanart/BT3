### Title
CR-CAT holders can have withdrawals permanently disabled by an authorized-provider-controlled VC dependency - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
The external report describes a pool factory `withdraw()` that requires a set of reward-token transfers to succeed atomically before a user's principal deposit is released, so a single malicious/paused reward token can permanently strand user funds. The Chia analog is the CR-CAT (Credential Restricted CAT) spend path: spending a CR-CAT coin the user legitimately owns is not possible with the user's own signature alone — it structurally requires a valid, currently-provable `VerifiedCredential` (VC) issued/maintained by an "authorized provider" (a DID). If that provider revokes/withdraws proofs, lets its proof root go stale, or the user simply has no VC with the right provider, the CR-CAT holder's own coin becomes permanently unspendable through the normal path, exactly mirroring "malicious/absent external dependency blocks withdrawal of the user's own principal."

### Finding Description
`CRCATWallet._generate_unsigned_spendbundle` (the function that generates every ordinary CAT-wallet spend, including a plain `cat_spend`/withdraw) unconditionally requires a `VCWallet` and a `VerifiedCredential` object with proofs matching the CR-CAT's `authorized_providers`/`proofs_checker` before it will build a spend: [1](#0-0) 
```

            if WalletType(wallet.type()) == WalletType.VC:

            raise RuntimeError("CR-CATs cannot be spent without an appropriate VC")  # pragma: no cover
```

The `VerifiedCredential` itself is a singleton controlled by the "provider" DID, which can unilaterally revoke it via a backdoor spend: [5](#0-4) 
```

        """
        Activates the backdoor in the VC to revoke the credentials and remove the provider's DID.

```
and the wallet-side `revoke_vc` flow that composes this DID-authorized spend is in `chia/wallet/vc_wallet/vc_wallet.py` (`revoke_vc`, lines 376-437). Once revoked (or if proofs simply lapse/are never (re)issued), `get_vc_with_provider_in_and_proofs` will return `None` (or a VC without a fresh `proof_hash`), and every code path above raises before a spend bundle can even be constructed — there is no fallback or emergency path in `CRCATWallet` that lets the coin owner move the coin using only their own key.

This is structurally the same defect class as the reported bug: a withdrawal/spend of a user's own asset is gated on cooperation/availability of an external, non-owner-controlled component (the authorized provider's VC/proof), and if that component becomes unavailable/malicious/paused, the user's principal is permanently stuck, with no "emergency withdraw" bypass.

### Impact Explanation
Any user holding CR-CAT coins that has their VC revoked by the authorized provider (or whose VC proofs are not/no longer valid for the CR-CAT's `authorized_providers`/`proofs_checker`) cannot spend, transfer, or claim their own CR-CAT balance through the wallet's standard code paths. This is a permanent, coin-level denial-of-withdrawal for legitimate funds the user actually owns — matching the "malicious token reward could disable withdrawals" impact of stuck user funds, but for an entire asset class (CR-CAT) rather than only reward tokens. Given CR-CATs are explicitly designed to restrict transferability to holders of valid credentials, this is an acknowledged design trade-off rather than a pure bug, but from the perspective of an unprivileged holder whose provider becomes unresponsive/hostile, the practical effect (funds frozen, no recourse) is identical to the referenced finding.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the CR-CAT's `authorized_providers` to include a provider that can and does revoke or fails to keep proofs current, and (b) the holder to have no alternate VC satisfying `authorized_providers`/`proofs_checker`. This is squarely within the reach of a CAT/CR-CAT holder — an unprivileged wallet user — since revocation and proof lifecycle are entirely under the authorized provider's control, not the coin owner's, and the wallet code offers no bypass.

### Recommendation
- Document/confirm (as FactoryDAO did for the original finding) that this is intentional CR-CAT design, since credential restriction is the explicit product goal; if so, ensure UX/docs make the risk of provider-controlled freezing explicit to holders before they accept CR-CATs.
- If not intended to be permanent, add an "emergency" or fallback spend path in `CRCATWallet`/`CRCAT` driver (e.g., a melt/self-custody exit or grace-period unlock) that lets the coin owner recover value (even into an unrestricted CAT or XCH) without requiring a live, provider-signed VC proof, analogous to the `emergencyWithdraw` mitigation recommended in the original report.
- Consider adding wallet-level warnings when `get_vc_with_provider_in_and_proofs` fails so users are alerted immediately that their CR-CAT balance is currently unspendable, rather than only surfacing a `RuntimeError` at spend time.

### Proof of Concept
1. Mint a CR-CAT with `authorized_providers = [provider_did]` and a `proofs_checker` requiring specific flags, per `CRCAT.launch` (`chia/wallet/vc_wallet/cr_cat_drivers.py`).
2. Issue the holder a `VerifiedCredential` from `provider_did` satisfying the proofs checker.
3. Have the provider call `VCWallet.revoke_vc` (`chia/wallet/vc_wallet/vc_wallet.py:376`), which spends the DID and drives `VerifiedCredential.activate_backdoor` (`chia/wallet/vc_wallet/vc_drivers.py:757`) to permanently kill the VC singleton (comment confirms sync attempts after this are expected to fail).
4. Holder now attempts any CR-CAT spend (`cat_spend` RPC → `CRCATWallet._generate_unsigned_spendbundle`) or a pending-approval claim (`claim_pending_approval_balance`). Both immediately raise `RuntimeError` because `get_vc_with_provider_in_and_proofs` can no longer find a valid VC, per the code cited above — the holder's CR-CAT balance is now stuck with no path to move it via the standard wallet.
