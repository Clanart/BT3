### Title
Value sent to the distribution precompile's non-payable-unchecked `rewards()` view is permanently locked with no withdrawal path - (File: `precompiles/distribution/distribution.go`)

### Summary
The distribution precompile at `0x0000000000000000000000000000000000001007` is **not** included in the `payablePrecompiles` allow-list used by the EVM value-transfer hook, so any `msg.value` attached to a call into it is moved into the precompile's Sei-mapped bank account by the standard native transfer path, exactly as it would be for a normal contract. Unlike every other state-mutating method on the same precompile, the `rewards()` case in `Execute` neither calls `pcommon.ValidateNonPayable(value)` to reject the value, nor calls `pcommon.HandlePaymentUsei` to refund it. The transferred `usei` therefore lands in an account that has no controlling key and no code path that sweeps or exposes it, permanently freezing the funds — the same "received funds with no withdraw function" bug class as the referenced BorrowLiquidation report.

### Finding Description
Precompile value-transfer semantics in sei-chain are controlled centrally in the EVM block context's `Transfer` hook: [1](#0-0) 

`IsPayablePrecompile` only allow-lists `bank`, `staking`, `gov`, and `wasmd`: [2](#0-1) 

Because the distribution precompile address is **not** in this map, any EVM call carrying `msg.value` to `0x1007` goes through the ordinary `core.Transfer` path, which — via the StateDB bridge — actually moves `usei`/`wei` out of the caller's Cosmos bank balance and into the bank balance mapped to the precompile's Sei address: [3](#0-2) 

Inside the distribution precompile's dispatcher, every state-mutating method that is meant to reject value explicitly calls `pcommon.ValidateNonPayable(value)` (e.g. `WithdrawValidatorCommissionMethod`), and payable methods (e.g. staking's `delegate`) explicitly refund the payer via `pcommon.HandlePaymentUsei` because "the following precompile logic will debit the payments from payer's account": [4](#0-3) [5](#0-4) [6](#0-5) 

However, the `RewardsMethod` case is dispatched with **no non-payable check and no refund**: [7](#0-6) 

This gap is explicitly documented by the project's own integration test comment: *"rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)"*: [8](#0-7) 

Since the destination is a precompile-derived Sei address with no associated private key, no CosmWasm contract, and no EndBlock sweep back to the sender or fee collector, any `usei`/`wei` sent this way becomes permanently unrecoverable — mirroring the audited `closeThePositionInSynthetix` bug where assets land in a contract lacking a withdrawal function.

### Impact Explanation
Any unprivileged EVM transaction sender can call `rewards(...)` on the distribution precompile with a non-zero `value` and permanently lose those funds; there is no admin, owner, or user-callable function anywhere in the codebase that can recover `usei`/`wei` credited to a precompile's Sei-mapped address. This is a concrete, permanent freezing/loss of user funds reachable from a single public transaction, satisfying the Medium/High bar for fund loss.

### Likelihood Explanation
Trivially reachable: any externally owned account (or contract) that already interacts with the distribution precompile (e.g. through a wallet UI or contract that blindly forwards `msg.value`) can trigger this by mistake or via a malicious front-end/contract encouraging users to attach value to a `rewards()` call. No special privileges, timing, or preconditions are required beyond having an EVM-Sei address association and a nonzero balance.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to the `RewardsMethod` (and audit all other view/query methods on every precompile) so value-bearing calls to non-payable functions revert instead of transferring funds to an unrecoverable address. Additionally, consider adding a generic sweep/refund mechanism in the EVM `Transfer` hook or precompile dispatch layer that automatically returns any `value` sent to non-payable precompile methods, matching the safety net already implemented in `HandlePaymentUsei` for legitimately payable methods.

### Proof of Concept
1. Associate an EVM address with a Sei address and fund it with `usei`.
2. From that EVM account, send a transaction to `0x0000000000000000000000000000000000001007` calling `rewards(...)` (or any ABI-encoded call matching `RewardsMethod`) with a non-zero `value`.
3. The EVM `Transfer` hook (not being in `payablePrecompiles`) performs a real `SubBalance`/`AddBalance` transfer, debiting the caller's Cosmos bank balance and crediting the precompile's Sei-mapped address.
4. `Execute`'s `RewardsMethod` branch runs the read-only rewards query, packs a return value, and returns success — the call does **not** revert and does **not** refund the value.
5. The transferred `usei` remains on the precompile's Sei address indefinitely; no existing keeper, module, or CLI/RPC path can move it out, confirming permanent loss.

func HandlePaymentUsei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Coin, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	if !wei.IsZero() {

	coin := sdk.NewCoin(sdk.MustGetBaseDenom(), usei)
	// refund payer because the following precompile logic will debit the payments from payer's account

	if err := bankKeeper.SendCoins(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, sdk.NewCoins(coin)); err != nil {
		return sdk.Coin{}, err
	}
