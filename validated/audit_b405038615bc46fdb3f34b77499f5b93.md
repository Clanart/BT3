Confirmed: `handle_finalized_payout` (`core/src/operator.rs:839`) never checks that the operator itself actually broadcast or funded the payout transaction — it only reads `payout_payer_operator_xonly_pk` from the DB (via `get_deposit_data`/`get_unused_and_signed_kickoff_connector`), which is populated purely from the OP_RETURN of whatever transaction happened to spend the withdrawal UTXO on chain. ### Title
Payout attribution relies on an unauthenticated OP_RETURN output not covered by the user's `SinglePlusAnyoneCanPay` signature, letting anyone attribute a self-funded payout to an uninvolved operator - (File: core/src/builder/transaction/operator_reimburse.rs / core/src/verifier.rs)

### Summary
`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) puts the attributed operator's x-only pubkey in output index 2 (OP_RETURN) of the payout transaction, while the user's mandatory `SinglePlusAnyoneCanPay` signature (enforced in `parser::operator::parse_withdrawal_sig_params`, `core/src/rpc/parser/operator.rs:182-187`) only commits to input 0 and output 0. Because outputs 1 and 2 are never covered by any signature, anyone who controls the withdrawal's dust input signature (including the withdrawing user themselves, acting as an unprivileged attacker) can construct and broadcast their own payout transaction that pays the correct output 0 but places an arbitrary operator's x-only pubkey in the OP_RETURN, without that operator ever being involved.

### Finding Description
The binding claimed by the protocol is: `payout_payer_operator_xonly_pk` (stored via `Verifier::update_finalized_payouts`, `core/src/verifier.rs:2283-2353`, using `get_first_op_return_output`/`parse_op_return_data`) == the operator that actually fronted the user's BTC.

Trace:
- `parse_withdrawal_sig_params` forces the user's signature sighash type to `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:174-187`).
- `Operator::withdraw` verifies this signature with `SECP.verify_schnorr` against `payout_txhandler.calculate_sighash_txin(0, ...)` (`core/src/operator.rs:630-637`).
- Under BIP-341, `SIGHASH_SINGLE|ANYONECANPAY` commits only to input 0's own prevout/scriptPubkey/amount/sequence and to output index 0. It does **not** commit to output 1 (anchor) or output 2 (OP_RETURN with `operator_xonly_pk.serialize()`), as encoded in `taproot_encode_signing_data_to_with_annex_digest` (`circuits-lib/src/bridge_circuit/mod.rs:719-800`, and mirrored by rust-bitcoin's sighash algorithm used by `calculate_sighash_txin`).
- `Verifier::update_finalized_payouts` blindly trusts whichever OP_RETURN ends up in the confirmed transaction that spends the withdrawal UTXO, with no signature check tying that OP_RETURN to the operator who actually paid (`core/src/verifier.rs:2312-2342`).
- `Operator::handle_finalized_payout` (`core/src/operator.rs:839-900`) and `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) act purely on this DB-recorded attribution — there is no check that the operator's own wallet/UTXOs funded output 0, or that the operator itself broadcast the transaction.

Because the signature never binds output 2, the attacker (who, per the threat model, is themselves the withdrawing party and thus already possesses a valid `SinglePlusAnyoneCanPay` signature over their own dust input/output 0) can build and broadcast an entirely independent payout transaction: same input 0 UTXO/signature, same output 0 (must match exactly, since that is signed), but self-funded additional inputs and an OP_RETURN naming any registered operator's x-only pubkey. This transaction never touches any operator's key or wallet, yet once mined it is indistinguishable from a legitimate operator payout to `update_finalized_payouts`.

None of the existing guards catch this: `SECP.verify_schnorr` only proves the *user* authorized spending their own dust UTXO to output 0, not who paid; `is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) only compares the payout's OP_RETURN pubkey against the kickoff's claimed operator — which will match, since the framed operator's automation will pick up the false attribution via `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`) and issue its own legitimately-signed kickoff for it; `validate_payer_is_operator` (`core/src/operator.rs:1686-1740`) again just re-reads the same unauthenticated DB column.

### Impact Explanation
This directly enables the Critical category "an operator reimbursed for a payout it never funded": an attacker (the withdrawing user, or anyone who obtains the user's `SinglePlusAnyoneCanPay` signature/UTXO before confirmation) can self-fund a withdrawal's output 0 and stamp any operator's public x-only key into the OP_RETURN, at which point that operator's own automated `PayoutCheckerTask` will treat the withdrawal as fronted by them and proceed to kickoff/Reimburse for BTC they never actually paid the user (Reimburse pays from the operator's presigned/collateral round chain regardless of the fact that the operator's wallet never sent any funds). It equally supports the complementary "honest operator permanently unable to be reimbursed" variant when the honest operator's real payout is mempool-raced and replaced before confirmation, since the withdrawal UTXO can only be spent once, and the DB attribution is set from whichever transaction is actually mined. Both variants are repeatable per withdrawal and are not limited to a single deposit/operator; the blast radius covers any operator whose x-only pubkey is public (all operator pubkeys are fetched via `fetch_operator_keys`).

### Likelihood Explanation
The framing variant ("operator reimbursed for a payout it never funded") requires the attacker to fully fund output 0 themselves — i.e., pay the withdrawal amount out of pocket to their own address — so the attacker gains nothing financially and only griefs a targeted operator by falsely triggering that operator's reimbursement flow for a "gift" the attacker gave themselves. This still meets the Critical impact bar (operator gets reimbursed/attempts reimbursement for a payment it never made) with a moderate cost equal to the withdrawal amount and no special privileges beyond being a Citrea withdrawal initiator, which is explicitly in-scope for the unprivileged attacker model. The griefing variant (racing to deny the honest operator attribution) additionally requires winning a fee/mempool race before the honest operator's transaction confirms, which is feasible if the attacker (as withdrawer) simply never lets an honest operator complete the payout and self-broadcasts instead, or outbids the honest operator's RBF replacement.

### Recommendation
Bind the OP_RETURN operator attribution (and ideally the anchor output) into the committed sighash, e.g., require the user to sign with `SIGHASH_ALL` (or `SIGHASH_ALL|ANYONECANPAY` if additional funding inputs must remain flexible) once the operator's identity output is finalized, or have the operator co-sign a commitment (e.g., a second signature/covenant) that binds output 2 to the specific operator's key before broadcasting. Alternatively, require `update_finalized_payouts`/`handle_finalized_payout` to additionally verify that at least one input of the confirmed payout transaction is provably controlled by the attributed operator (e.g., matches a UTXO the operator's own `TxSender` recorded as used for funding), rather than trusting the OP_RETURN alone.

    output_txout: TxOut,

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }

    let input_outpoint: OutPoint = params
        .input_outpoint
        .ok_or_else(error::input_ended_prematurely)?
        .try_into()?;

    let users_intent_script_pubkey = ScriptBuf::from_bytes(params.output_script_pubkey);

    Ok((
        params.withdrawal_id,
        input_signature,
        input_outpoint,
        users_intent_script_pubkey,
        Amount::from_sat(params.output_amount),
    ))
}
