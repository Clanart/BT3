## Title
Path-containment check in `resolveWithin` uses raw string prefix match, allowing sibling-directory escape when reading conflicted files - (File: app/src/lib/path.ts)

### Summary
The reported Notional bug is a broken-identity-check pattern: a strict equality comparison (`address(tokens[i]) == address(asset)`) fails to recognize that two different representations (ETH vs WETH) refer to the "same" trusted value, so a guard that is supposed to skip an operation on the trusted asset silently fails to fire. The closest reachable analog in this GitHub Desktop checkout is the boundary check in `_resolveWithin` in `app/src/lib/path.ts`, which decides whether a resolved file path is "inside" a trusted root directory using a raw string `startsWith` comparison instead of a path-boundary-aware comparison. Just like the Notional bug, the check *looks* correct but silently fails to enforce the intended invariant for a specific input shape, allowing an operation (reading a file) meant to be constrained to the repository root to reach outside it.

### Finding Description
`_resolveWithin` computes the real, symlink-resolved root and target paths and then decides containment purely with: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` performs a raw character-prefix comparison with no path-separator boundary check. Because of this, a resolved path in a *sibling* directory whose name happens to extend the root directory's name as a string (e.g. root `/Users/victim/repo` and target `/Users/victim/repo-secrets/file.txt`) is incorrectly classified as "inside" the root, exactly the same class of bug as the report: a comparison intended to enforce identity/containment accepts an input that only superficially resembles the trusted value.

This function is the sole guard used by `buildConflictContext` in `app/src/lib/copilot-conflict-context.ts` to sanitize attacker-influenced, repository-relative file paths before reading file contents from disk: [2](#0-1) 

The `file.path` values passed into `buildConflictContext` originate from the list of conflicted files reported by Git for the working tree (merge/rebase/cherry-pick conflicts), i.e., paths that can be influenced by the contents of a cloned/fetched repository (submodule paths, unusual filenames, or a crafted merge that introduces conflict entries with path-like relative segments such as `../repo-more/…`). Because the containment check can be satisfied by a `../`-escaping path that lands in a sibling directory sharing the root's name as a prefix, `readFile(absolutePath, 'utf8')` at line 431 can read file content from outside the intended repository root and feed it into the Copilot conflict-resolution prompt, disclosing its content to a third-party model/service.

The same `resolveWithin` primitive is also relied upon in `app/src/ui/dispatcher/dispatcher.ts` (for deep-link `filepath` handling) and `app/src/lib/stores/app-store.ts`; both inherit the same weak boundary check, so any attacker-influenced relative path handled by those call sites is subject to the identical flaw.

### Impact Explanation
This matches the accepted impact category "silent... file read... outside the repo" driven by "a cloned/fetched repository" or "a git remote/proxy response" object (the list of conflicted paths derived from repository/merge state is not something the user directly types). A successful escape lets Desktop read and, in the Copilot conflict-resolution flow, exfiltrate the contents of a file located outside the repository the user believes they are working in, to an external Copilot/LLM backend — this is data disclosure with a real trust-boundary violation, not merely a hardening gap.

### Likelihood Explanation
The check itself is unconditionally reachable whenever `buildConflictContext` (or the dispatcher/app-store call sites) processes a relative path that resolves outside the root; the flaw is a genuine logic bug in the boundary comparison rather than requiring any special privileges, local access, or social engineering — an attacker only needs to shape repository/merge state (e.g., via a crafted repo/submodule or conflict entry) so that the derived `file.path` traverses to a sibling directory whose absolute path happens to share the repository root's name as a string prefix. The main mitigating factor is that the target sibling directory name must literally extend the root directory's basename (e.g. `repo` → `repo-secrets`), which constrains exploitability to specific directory-naming coincidences rather than an arbitrary path; I could not find any additional guard elsewhere in the codebase (e.g., checking a trailing separator) that would otherwise prevent this, so likelihood is directly tied to how an attacker can arrange for such directory names to exist on the victim's machine, which I was not able to fully verify from static analysis alone.

### Recommendation
Change the containment check to require a path-separator boundary (or use `path.relative()` and verify it doesn't start with `..` and isn't absolute), e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Apply the fix once in `_resolveWithin` in `app/src/lib/path.ts` so all consumers (`resolveWithin`, `resolveWithinPosix`, `resolveWithinWin32`) inherit the corrected boundary check.

### Proof of Concept
Conceptual PoC (not executed, based on static code reading of `app/src/lib/path.ts` and `app/src/lib/copilot-conflict-context.ts`):
1. Attacker arranges a repository/merge state such that Git reports a "conflicted file" whose repository-relative path is something like `../repo-secrets/config.json` (or a submodule/symlink structure that resolves similarly) where `repo-secrets` is a directory that exists as a sibling of the victim's repository root `repo`.
2. `buildConflictContext` calls `resolveWithin(workingDirectory, file.path)` with `workingDirectory = /Users/victim/repo`.
3. Inside `_resolveWithin`, `resolved` becomes `/Users/victim/repo-secrets/config.json`; `realRoot` is `/Users/victim/repo`.
4. `realResolved.startsWith(realRoot)` evaluates to `true` (string-prefix match) even though `/Users/victim/repo-secrets` is not a subdirectory of `/Users/victim/repo`.
5. `absolutePath` is returned non-null, and `readFile(absolutePath, 'utf8')` at [3](#0-2)  reads the out-of-repo file, whose content is then embedded into the conflict-resolution prompt sent to the Copilot backend.

Note: I was not able to fully trace how `file.path` values are produced upstream (i.e., confirm whether Git's conflict-file listing can be made to emit a `../`-style relative path under attacker control) within the available tool budget; this would need to be validated in a live Desktop session to confirm end-to-end exploitability, but the boundary-check flaw in `_resolveWithin` itself is confirmed directly from the source.
