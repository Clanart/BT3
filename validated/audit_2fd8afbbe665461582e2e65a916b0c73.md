### Title
Attacker-controlled Bitcoin transaction overwrites `data`/`presumed_origin` of unrelated scanned outputs in the same block - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` accumulates matching outputs across all non-coinbase transactions of a block into a single `outputs` vector, but then applies the *current* transaction's `presumed_origin` and Serai instruction `data` to every accumulated output — including outputs produced by earlier, unrelated transactions in the same block. An unprivileged party can send an arbitrary Bitcoin transaction (it need not pay the multisig at all) in the same block as a victim's deposit, and its embedded data / origin will be stamped onto the victim's `External` output, causing the deposit to be processed with attacker-controlled metadata.

### Finding Description
In `get_outputs` (`processor/src/networks/bitcoin.rs:686-739`):

```rust
let mut outputs = vec![];
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) {
    ...
    outputs.push(output);
  }

  if outputs.is_empty() {
    continue;   // only skips when NOTHING has been collected yet
  }

  let presumed_origin = { /* derived from tx.input[0] */ };
  let data = Self::extract_serai_data(tx);
  for output in &mut outputs {            // mutates ALL outputs, not just this tx's
    if output.kind == OutputType::External {
      output.data.clone_from(&data);      // overwrites data from earlier txs
    }
    output.presumed_origin.clone_from(&presumed_origin);
  }
}
```

`outputs` is never scoped per-transaction. Once any earlier transaction in the block produced a scanned output, the `outputs.is_empty()` guard is permanently false for the remainder of the block, so every subsequent transaction triggers the origin/data population pass over the entire accumulated vector. `data` for `External` outputs and `presumed_origin` for all kinds are therefore always those of the *last* transaction in the block, not of the transaction that actually created each output. The `assert_eq!(output.tx_id(), tx.id())` inside the scan loop only covers newly pushed outputs, not the mutation pass.

### Impact Explanation
`Output.data` for `External` outputs carries the Serai InInstruction payload extracted via `extract_serai_data(tx)`, and `presumed_origin` attributes the funding source. These outputs are emitted via `ScannerEvent::Block` (`processor/src/multisigs/scanner.rs:704`) and drive downstream handling of received funds. An attacker's transaction — which only needs a valid first input and an OP_RETURN Serai payload, and doesn't need to send anything to the multisig — placed later in the same block overwrites the instruction data and origin of a victim's genuine deposit. Result: funds are reported received with attacker-controlled `data`/`presumed_origin`, enabling misrouting/misattribution of deposits (e.g., crediting/refunding/forwarding per the attacker's embedded instruction instead of the depositor's). This is a reachable exploit from a purely public input: a Bitcoin transaction the attacker broadcasts.

### Likelihood Explanation
Requires the attacker's transaction to land in the same block as a victim deposit and after it in `txdata` ordering — achievable by watching the mempool for transactions paying the known multisig external address and broadcasting a crafted tx with higher fee or equivalent ordering. No key material, validator status, or authenticated channel is needed; the trigger is an ordinary on-chain transaction, matching the unauthenticated-remote-input bug class of the reference report.

### Recommendation
Scope origin/data assignment to the outputs produced by the current transaction only, e.g.:

```rust
let start = outputs.len();
for output in scanner.scan_transaction(tx) { ...; outputs.push(output); }
let new_outputs = &mut outputs[start ..];
if new_outputs.is_empty() { continue; }
...
for output in new_outputs { ... }
```

Additionally, assert per-output that the populated metadata corresponds to the output's own `outpoint().txid`.

### Proof of Concept
1. Victim broadcasts tx A paying `amount` to the multisig's external P2TR address, embedding their intended Serai data payload.
2. Attacker observes tx A in the mempool and crafts tx B spending any of their own UTXOs (valid `input[0]`), with an `extract_serai_data`-parseable payload of their choosing (e.g., a forwarding/refund instruction to an attacker address). Tx B contains no output to the multisig.
3. Both txs confirm in one block with B ordered after A (`block.txdata` order).
4. `get_outputs` scans tx A → pushes the victim `External` output with `data = vec![]` initially; then scans tx B → pushes nothing, but since `outputs` is non-empty, sets `victim_output.data = extract_serai_data(tx_B)` and `victim_output.presumed_origin = attacker_origin`.
5. The scanner emits the victim output carrying the attacker's instruction data and origin; downstream processing attributes/handles the deposit per attacker-supplied metadata.
